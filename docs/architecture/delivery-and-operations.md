# Delivery and operations

How work is specified, reviewed, merged, released, deployed and run on the host. Procedures
live in `docs/operations/` and `deploy/README.md`; this document states the rules they
implement. Migration and seed rules are in [migrations-and-seeding.md](migrations-and-seeding.md).

## Cross-cutting principle: no speculative generality

- No new abstraction, helper, config flag or generalisation beyond what the current issue's
  Task asks for, on every platform. Review flags it as scope creep (medium severity).
- Cross-cutting architecture (a new choke-point capability, gateway adapter, shared layer) is
  built when an issue's Task asks for it, never as a side effect of an unrelated issue. A
  capability that is needed but not yet asked for waits for its own issue.
- Each pull request stays auditable against exactly the issue (or source records) it delivers.

## Repository layout

One repository holds the whole product, so a change to the API and its clients is one pull
request in one history:

- `backend/` — the pnpm workspace (`packages/*`, `services/*`);
- `web/` — the React/TypeScript web client;
- `mobile/` — the Gradle root with `mobile/shared/` (Kotlin Multiplatform), `mobile/android/` and
  `mobile/apple/` (one SwiftUI codebase for iOS/iPadOS and macOS, generated by Tuist);
- `shared/` — code shared across products (`shared/block-model`);
- `deploy/` — host provisioning, units, firewall and the deploy script;
- `issues/` — the issue catalog (see [Issues](#issues)).

Every platform has its own `review-rules/`; the code-review bot assigns each file to the platform
whose directory is the longest prefix of its path. `mobile/` is three platforms:
`mobile/review-rules/` (shared Kotlin and the Gradle build), `mobile/android/review-rules/` and
`mobile/apple/review-rules/`.

## Branches and pull requests

- `develop` is the integration branch; every change targets it through a pull request.
- `main` holds released versions only and advances only through a `develop -> main` promotion
  pull request (`promotion-source` check), reviewed under release-readiness rules (migrations,
  config, rollback, security) rather than per-issue acceptance criteria.
- Both branches are protected: pull request required, required checks strict, rules apply to
  administrators, no force push or deletion.
- The required contexts are a contract; renaming or removing a `ci.yml` job is a contract change
  that also updates branch protection, Relay's `wait-checks` and the release command. See
  [docs/operations/required-checks.md](../operations/required-checks.md).

## Releases

- The monorepo has exactly one version: a `vMAJOR.MINOR.PATCH` annotated git tag on `main`. Every
  `package.json` keeps `version: "0.0.0"`, enforced by a unit test in `backend/packages/release`.
- A tag is created only by the guarded command in `backend/packages/release`
  (`releaseTag.ts`). It refuses unless `main` is protected and its head is exactly the given full
  SHA, the tag does not exist, no other release tag points at that SHA, and every push-triggered
  `ci.yml` job's newest run on that SHA succeeded. It re-reads `main` right before tagging and
  pushes without force.
- A release is a deliberate maintainer act; a green `main` commit may stay untagged, and a commit
  is tagged at most once. Pushing a tag deploys nothing.
- Mobile apps carry their own store build identifiers (`mobile/gradle/project.properties`); they
  identify app builds, not repository releases.

Procedure: [docs/operations/releases.md](../operations/releases.md).

## Deploy

`deploy/deploy.sh <tag>`, run as root on the host, is the only way code reaches production:

1. **Immutable release per tag.** The tagged commit is exported with `git archive` into a hidden
   staging directory under `/opt/semprec/releases/`, installed with `pnpm install --frozen-lockfile`
   (copied packages) and built there. An existing `releases/<tag>` is never rebuilt or overwritten.
2. **Native entrypoint check.** Every compiled entry the units start is run as plain `node`
   with no configuration (`backend/scripts/check-native-entrypoints.mjs`) and must reach its own
   configuration refusal, not a module-resolution failure.
3. **Migrate, seed, verify tenancy** while the previous release still serves, each in a transient
   `systemd-run` unit that loads `shared/env/migrate.env` (the script never reads the secret).
4. **Promote and activate.** The staging directory becomes `releases/<tag>`; `current` is
   replaced by `rename(2)` of a fresh symlink, so it always names a complete release.
5. **Restart, then report.** Every unit in `LONG_RUNNING_SERVICES` is restarted in order, and the
   deploy fails unless each running process carries the tag as `APP_VERSION`
   (`releases/<tag>/release.env`, loaded last by every long-running unit).

Rules that follow:

- The database is expected to be empty: the operator wipes it before a deploy, and `deploy.sh`
  never drops data ([migrations-and-seeding.md](migrations-and-seeding.md#one-baseline-no-versions)).
- Any failure before activation removes the staging directory and changes nothing but the
  database.
- A failure after the swap exits non-zero but does not roll itself back.
- Mail live-sync runs inside `semprec-api` and restarts, reports and shuts down with it; it is
  not a separately deployed service. A separate process would be a new decision.
- Old releases stay on disk as complete directories.

Procedure: `deploy/README.md` ("Deploying a release").

## Rollback

- `deploy.sh --rollback <tag>` builds, fetches and migrates nothing: it repoints `current` with
  the same atomic swap, restarts the same services and checks each reports `<tag>`.
- Only one release back: `<tag>` must be the complete release directly before the newest on disk
  (semver order, staging directories excluded), its `release.env` must declare
  `APP_VERSION=<tag>`, and `current` must still name the newest release. Every refusal happens
  before anything changes; a second consecutive rollback is refused.
- The database is not touched, and nothing keeps its schema compatible with older code: a
  rollback is safe only between releases with the same baseline. Otherwise the way forward is a
  fixed release deployed onto a wiped database.

Procedure: [docs/operations/migrations.md](../operations/migrations.md) and `deploy/README.md`
("Rolling back").

## Host

### Secret groups

- Every production key lives in exactly one group: a values-free template
  `deploy/shared/env/<group>.env.example`, installed as `/opt/semprec/shared/env/<group>.env`
  (`root:root 0600`, directory `0700`).
- A unit's `EnvironmentFile=` lines are its allowlist; it loads only the groups it needs, with
  `current/release.env` last on long-running units.
- The migrate URL (`migrate.env`) is loaded by no unit; only `deploy.sh` hands it to the
  transient migration, seed and tenancy-verification units.
- A key two units need is placed in a group both load, never duplicated. A new key picks one
  group and is added to its template.
- `provision.sh` installs a missing group file from its template and never overwrites an existing
  one or prints a value.

### Egress filtering

`deploy/nftables.conf` filters outbound traffic by uid, as the host layer under the
application's outbound address checks
([edges-io-and-errors.md](edges-io-and-errors.md)):

- The `output` chain (`policy accept`) jumps to `semprec_egress` for `meta skuid "semprec"` and to
  `semprec_mcp_egress` for `semprec-mcp`. Root, Caddy, Docker and apt are untouched.
- The chains are deny-lists (tenants choose IMAP, SMTP and MCP ports): established/related
  accept, DNS to any address, then reject (`icmpx admin-prohibited`, rate-limited log as a
  separate rule) for the `semprec_blocked_v4` / `semprec_blocked_v6` sets (loopback, RFC 1918,
  link-local and metadata, CGNAT, ULA, NAT64, multicast and similar).
- Only `semprec_egress` has a loopback exception, for Postgres `5432` and the gateway `3002`,
  matched on the conntrack original destination. `AI_GATEWAY_PORT` therefore stays `3002`.
- Consequence: an SMTP, IMAP or MCP server on a private or loopback address is unreachable.

### stdio MCP sandbox

A `stdio` MCP server never runs as a child of the service that uses it:

- It runs as system user `semprec-mcp` (own group, not in `semprec`), started per connection by
  `semprec-mcp-launch.socket` (`/run/semprec-mcp-launch.sock`, `root:semprec 0660`, `Accept=yes`,
  at most 16 connections) → `semprec-mcp-launch@.service`.
- The launcher `deploy/bin/semprec-mcp-launch` reads exactly one JSON header line
  (`{"command", "args", "env"}`, at most 65536 bytes, strict validation) and refuses anything else
  with exit 64, running nothing and never echoing the header. Otherwise it `exec`s the command
  with only `PATH`, `HOME`, `LANG`, `USER`, `LOGNAME` plus the header's `env`.
- The unit is sandboxed (`NoNewPrivileges`, `ProtectSystem=strict`, `ProtectProc=invisible`, no
  capabilities, `AF_UNIX`/`AF_INET`/`AF_INET6` only, `InaccessiblePaths=` for shared secrets, data,
  backups and Caddy config, `RuntimeMaxSec=300`, `MemoryMax=1G`, `TasksMax=64`), and its egress
  chain has no loopback exception.
- Client side, `SandboxedStdioClientTransport`
  (`backend/packages/data/src/mcp/sandboxedStdioTransport.ts`) writes the header (config `env` plus
  the decrypted credential, nothing from the service's environment). `mcpConnectionFactory.ts`
  uses it when `SEMPREC_MCP_LAUNCH_SOCKET` is set, spawns in-process only under `NODE_ENV=test`,
  and otherwise refuses with `stdio_sandbox_unavailable` before decrypting the credential.
- All `stdio` servers share one uid, which is acceptable only because `stdio` configs are
  confined to admin tenants
  ([agents-approvals-and-ai.md](agents-approvals-and-ai.md#actors-and-agent-identity)).

Procedure: `deploy/README.md` ("stdio MCP sandbox", "Host firewall").

### Host scripts that record results

A host script that must record an outcome in Postgres runs a small Node entrypoint compiled into
`@semprec/data`'s `dist/` in the current release, which calls data-layer functions (for example
`backend/packages/data/src/observability/restoreTestResultCli.ts` for the monthly restore test).
The script passes only non-secret, validated arguments within a closed contract; it never writes
SQL itself and no HTTP endpoint is added for it. The entrypoint connects as the role its tables
need (`semprec_side` for side tables) and is the single writer of its rows.

## Issues

### Repository Markdown issues

- Issues are files `issues/items/<id>.md` with schema-versioned frontmatter
  (`issues/schema.json`; one physical line per key, JSON-syntax values, no aliases, implicit
  types or duplicate keys) and the issue body. The catalog is authoritative
  (`issues/migration/state.json`: `authority: "repository"`); GitHub hosts pull requests, reviews
  and checks only, and missing local data stops work instead of falling back to GitHub.
- Identities: imported issues `gh-<number>`, new issues `sp-<UUIDv4>`. Files keep their path when
  title or state changes. History, attachments and handovers live under `issues/history/`,
  `issues/attachments/` and `issues/handovers/`.
- `node .github/scripts/issues.mjs` is the only writer (`create`, `approve`, `queue`, `block`,
  `reopen`, `complete`, `validate`, `ready`). Mutations require the file's expected SHA-256,
  reserve the record by exclusive directory creation and replace it by rename.
- Approval covers title, kind, parent and the exact body by SHA-256; any change invalidates it.
  Creation produces an unapproved proposal; approval and queueing are separate; agents never
  approve their own proposals; protected-path work stays manual.
- Completion is proposed on the implementation branch and becomes authoritative only when the
  reviewed branch reaches the integration branch. A cancelled or rejected dependency is not a
  delivery. The pull request carries the canonical id (`Repository-Issue: <id>`).
- Relay keeps numeric run keys through checked aliases (`gh-N` → `N`; `sp-` ids →
  `1000000000 + (first eight SHA-256 hex digits mod 1000000000)`); a collision fails closed.
  Runtime reservations and retry state live in Relay's journal, not in Git.

Format and commands: `issues/README.md`, `.github/ISSUE_FORMAT.md`,
[docs/operations/repository-issues-cutover.md](../operations/repository-issues-cutover.md).

### Issue batches are dependency DAGs

- `Blocked by:` names a real dependency only: a capability another issue delivers, or a
  shared-file overlap that cannot be split. It is never added just because an issue is later in
  a batch. Issues without such an edge are concurrently eligible.
- Every implementation issue has a `## Touches` section listing the files or narrow areas it
  changes. Two issues that can be eligible at the same time must not overlap; an overlap becomes a
  `Blocked by:` edge or a shared change extracted into an earlier issue. `.github/ISSUE_FORMAT.md`
  lists the known hotspots (the baseline schema, registries, barrels, catalogs).
- A batch's `NN/MM` is topological creation order, not execution order.

### Model tiers

- Implementation issues carry `**Model tier:** low|medium|high` on the line after `Blocked by:`,
  with a short English rationale in Context. `.github/ISSUE_FORMAT.md` owns the grammar;
  `.github/scripts/model-tier.mjs` is the one parser used by creation, audit and follow-up
  publication. Epics and harvest payloads are exempt.
- Relay selects workers by exact tier and freezes the model at admission. Missing metadata or
  capacity holds work; there is no cross-tier fallback. Review, fix, recovery and triage runs use
  `high`. See [docs/operations/relay-model-tiers.md](../operations/relay-model-tiers.md).

## Relay automation and review

### Pre-review draft pull requests

`.relay/workflows/implement-issue.md` reviews before it verifies:

- After implementation the branch is pushed as a **draft** pull request (the Actions review job
  skips drafts). The pinned code-review bot reviews it (`pre-review-1`); findings go back to the
  implementing thread, which fixes, replies, resolves and commits (`self-fix-1`); a second
  unrolled round follows.
- Every exit (clean review, findings left after round two, bot outage, fix giving up) continues
  to `verify-backend` and `verify-web`. Only a passing verify marks the pull request ready with
  `review:ready`.
- `review-pull-request` remains the merge gate on the verified head.
- Findings are addressed per the `fix-review-findings` skill.

### Owner-controlled review pause

- `.relay/review-policy.json` holds `enabled` and a non-empty `reason`; only a committed change
  to it pauses or restores automated review, never a provider error.
- While disabled, the required `review` job publishes a `neutral` `code-review` check that
  states the owner pause and claims no review; Relay skips pre-review and its review flow
  publishes the same neutral check before `review:passed`, which then means "waived". Builds,
  tests, protected-path guards and conversation resolution stay enforced, and manual merges
  require a local review.
- Missing, malformed or unreadable policy fails closed. See
  [docs/operations/required-checks.md](../operations/required-checks.md#owner-controlled-review-pause).

### Review findings become follow-up issues

- A scheduled workflow (`.github/workflows/harvest-review-followups.yml`) harvests the open
  findings of merged pull requests deterministically (no model) through
  `.github/scripts/issues/maintenance.mjs` and `.github/scripts/review-followups/`, with a fixed
  floor `HARVEST_MIN_PR` rather than a watermark.
- Relay's `triage-review-followups` workflow verifies each finding against `develop` and
  decomposes valid ones into issues. Every created issue is an unapproved proposal; nothing is
  dispatched until a human approves and queues it.
- State is markers in the versioned catalog and labels; changes are proposed through one reviewed
  maintenance pull request at a time, which holds further harvests until merged or closed.
  Closing a proposed follow-up retires its findings; reopening it is the undo.
- Relay writes to GitHub as the Relay App through its loopback token proxy; agent steps get no
  GitHub access.

### Merge

`.relay/workflows/merge-pull-request.md` merges one pull request at a time: it rebases
deterministically onto the base (a conflict goes to a resolution agent with full context), sends
a changed head back through review as a draft, waits for every required context plus
`protected-paths`, and only then merges.

## Architecture decision records

ADRs for mobile and web stay at permanent paths in the flat catalog `docs/adr/`; backend and
cross-cutting rules live in `docs/architecture/`. `node .github/scripts/adr.mjs --platform <p>`
lists accepted decisions for a platform plus `cross-cutting` (mobile selections include the
historical `apple` tag); `--all` includes other statuses. Results are candidates; read each
decision's scope before applying it. Decisions are append-only (`adr-conventions` skill).

## Backend delivery program

The backend backlog in `issues/batches/backend/` is delivered by a controller-run program
(`issues/batches/backend/README.md`, `CONTROLLER.md`) instead of Relay dispatch:

- **Unit.** The source record `issues/items/<id>.md` is the unit of approval, review, evidence and
  completion. Sources are routed by `delivery:` labels and `manifest.json`, carry
  `execution:batch-source` and `agent:blocked`, and are never cancelled or falsely completed.
  `node issues/batches/backend/verify.mjs` checks routing, hashes and dependency placement.
- **Chains.** A worker branch `chain/<key>`, in its own worktree, carries one to four sources of
  one area in dependency order, one contiguous commit segment each, and lands as one merge. At
  most six chains are implemented at once. Workers do not edit issue records, run
  `approve`/`complete` or push.
- **Queue runner.** The integration worktree has one writer, the queue runner: it performs every
  merge (`git merge --no-ff`), every issue-record mutation and every catalog read a landing
  depends on.
- **Edges.** `Blocked by` lines are never edited. A blocker the source's own text marks as
  `Shared-file ordering` gates landing only, and may still be open at landing (the receipt names
  it); every other blocker gates the start and must be completed with a handover, or be an earlier
  member of the chain. A later landing of such a blocker keeps both sides in shared files and
  places order-sensitive entries before those of the sources that named it.
- **Landing gate**, on the exact candidate: review of each segment by two other contexts (a third
  security reviewer for authentication, secrets, public routes, destructive data changes or agent
  approval), at most one full review and one focused recheck, no open finding of medium or
  higher; one evidence row per acceptance criterion (PASS, FAIL, BLOCKED or NOT RUN); and on the
  merged tree lint, format, build, unit tier, verify's static checks, e2e, the validating suites
  of every touched shared file and every integration file the chain changed. Then each source is
  completed with `issues.mjs complete`, one handover and one receipt under
  `issues/batches/backend/acceptance/sources/`.
- **Trains.** Up to three chains may land as one train: merged one after another (each with its
  own merge commit after a passing build), one gate on the combined tree. On any failure the
  runner hard-resets to the commit recorded before the train (discarding only merges it created),
  and those chains land singly; a chain that failed in a train never joins another.
- **Full integration tier** on the integration tip after every eight landed chains and before
  every publication, one full run on the host at a time. A failure that reproduces alone stops
  landings; a load-only failure is recorded with both logs, never reported as a pass. Timeouts
  are not raised.
- **Shared files.** Registry, barrel, manifest, catalog and baseline schema conflicts keep both
  sides and rerun that file's validating suites.
- **Authority and gates.** The controller acts under the owner's delegation: it approves exact
  specification hashes at dispatch, adjudicates findings and scope, and accepts results; no
  worker approves its own scope. Local acceptance is never production authorization: a criterion
  that needs production or a live provider stays NOT RUN and open, a failed verify stays a
  failure, and push, deploy, production access and provider calls need separate owner
  authorization.
