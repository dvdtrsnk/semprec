# A user edge write on a link rule's via relation locks the rule's target item before ending value links

## Context

The link engine locks the target item row of a rule before that item's value link row. The propagation job (`valueLinks/linkPropagation.ts`) and the engine's edge-changed hook (`valueLinks/linkRuleEdgeHook.ts`) call `lockItemById` and then `lockValueLink`. [[2026-11-05-value-link-propagation-keeps-separate-hop-budgets]] makes this the rule for the propagation job, and [[2026-11-01-value-link-item-updates-lock-item-before-handoff]] gave item updates the same order.

An edge write of a user or an agent does the opposite. `createRelationWithClient`, `createRelationIfAbsentWithClient` and `deleteRelationWithClient` write or delete the edge row, then call `breakValueLinksForRelationEdge`, which ends the `on` link of each side with one `UPDATE` and so holds the link row, and only afterwards run the edge-changed hooks, where the engine's hook locks the item row when the relation is the via relation of a rule. For a relation that is the target of one rule and the via relation of another, this closes a cycle. `Transcripts.project` is the target of `transcriptProjectFromEvent` and the via relation of `transcriptCompanyFromProject` (see [[2026-11-10-transcript-values-are-inherited-by-link-rules-whichever-process-writes-the-edge]]); `Files.projects` is the via relation of `fileCompaniesFromProjects`. A user removing a project from an item whose project link is `on` holds the link row and waits for the item row, while the propagation job of the Event's project holds the item row and waits for the link row. PostgreSQL ends one of the two with `40P01`, which no error mapping covers. A propagation job that loses is retried up to three times and then dropped, which leaves the old value on an item whose link is still `on`.

[[2026-11-01-value-link-relations-use-nonblocking-admission-and-scoped-lock-waits]] left the link break of ordinary edge writes unchanged, named a blocking item row lock at the break and a blocking item row lock before the edge write as conflicting orders, and said that a newly confirmed remaining cycle is another design decision. This ADR is that decision for the cycle the three ADRs above left open: the link break of ordinary edge writes. It does not edit their bodies.

The first design of the source that delivers this ADR ran the edge-changed hooks directly after the edge write, before the link break. It ended the cycle above and was withdrawn: the engine's hook for `Transcripts.project` locks the transcript's `company` link row (rule `transcriptCompanyFromProject`) and the break then locks the `project` link row, while moving the transcript's Event to the Trash takes the two the other way round and without the transcript row (`valueLinkSourceDeleteHook` deletes the `project` link, then `transcriptCompanyLinkReleaseItemDeleteHook` locks the `company` link). The release of a removed `event` edge takes `project`, `people`, then `company` as well, as [[2026-11-10-transcript-values-are-inherited-by-link-rules-whichever-process-writes-the-edge]] records. With a third transaction holding the `company` link row, the user's write started first ended one of the two with `40P01`, while both commit on the unchanged write path.

The lock this ADR adds has to reach the item row from `relationOps.ts`, which the dependency rule `chokepoint-knows-no-domain` keeps from naming a domain, and which is imported by `linkPropagation.ts`; [[2026-09-30-choke-point-domain-hooks-through-a-per-process-registry]] says how: a hook registry. This ADR extends that one by one kind of hook. [[2026-11-12-an-agent-write-that-ends-a-value-link-requires-approval]] adds an approval check and a destructive projection check that lock `on` link rows; their place against the lock is stated below.

## Decision

### The order of the rows of one item

The rows of one transcript, file or task that the paths below take are the item row, then the `project` link row, then the `people` link row, then the `company` link row; a path takes the ones it needs, in this relative order. This ADR does not call the order total of every path. On the tree it is followed by:

- the propagation job and the engine's edge-changed hook, which take the item row and then link rows;
- the release of a removed `Transcripts.event` edge, which takes `project`, `people` and `company` under the item row the engine's hook locked;
- the trash of an Event, for the `company` link of each transcript, which it takes last and for a transcript without the item row;
- the edge write of a user or an agent on a via relation, with the lock decided below.

Three paths of the tree take value link rows against it and end with `40P01` against a writer that follows it. They were measured with production calls for the decision record of the delivering source (`issues/decisions/sp-5419cac1-f4a7-4717-b870-4f244b1ad166.md`) and not re-run for this ADR, and none is repaired here:

1. The trash of an Event takes the `project` and `people` links it feeds in the order of their link ids (`deleteValueLinkSourcesBySourceItem` selects `ORDER BY l.id FOR UPDATE`), while the release of a removed `event` edge takes `project` and then `people`. A user `deleteRelation` of the transcript's `event` edge against `softDeleteItem` of its Event, with a third transaction holding the `project` link row, ends with `40P01` when the `people` link has the smaller id.
2. The trash of an Event that hosts a task which is also sourced from it takes the task's `project` and `people` links in the source detach and then the task row in `eventHostedTasksDeleteHook`, while the propagation of `taskProjectFromEvent` takes the task row and then its `project` link. With a third transaction holding the task row, the propagation started first and the trash second, one of the two ends with `40P01`.
3. The replay of an approved agent `relation.delete`, `relation.put` or `relation.set` (`replayApprovedGenericOperation`) runs the destructive projection check on the same transaction before the write, which share-locks the `on` links of the edge's sides (`reserveEdgeLinks`). It holds the `project` link row before the new lock takes the item row, so schedule A with the propagation waiting for the transcript row first ends with `40P01` for the replay.

A later path that locks more than one of these rows of an item follows the order, or is recorded as a limit with a measured schedule. A later link rule needs no change here, because the new hook reads the rules.

### The lock

A user or agent edge write takes the item rows that the engine's hook would lock for the written edge, right after the edge row is written or deleted and before anything in the write locks a value link row. For each link rule in catalog order that resolves and whose via relation is the written definition, the target item is locked with `lockItemById` and its blocking wait, the call `linkRuleEdgeHook` makes. The edge-changed hooks, the link break, the rollup enqueue and the announcement keep their order and their arguments after it, and the engine's hook finds the row already locked by its own transaction.

- **Place.** `createRelationWithClient` and `createRelationIfAbsentWithClient` call it right after the insert reported that the edge was inserted, `deleteRelationWithClient` right after the delete returned an edge. In `createRelationWithClient` it is before the approval check of an agent under a run, because that check share-locks `on` link rows. A replayed create, a delete of an absent edge and an insert of an edge that exists call nothing.
- **Which writes.** Only a `user` or an `agent` writer, because a `system` write never ends a link. The protected writes of the `valueLinks` process keep their nonblocking admission untouched.
- **Which relations.** Only a relation that is the via relation of a link rule. A relation that is no rule's via relation locks no item row and ends the link as before.
- **Which row.** The one the engine's hook locks for this edge: the target item of each such rule, computed by one helper that `linkRuleEdgeHook` and the new hook share, so they cannot name different rows. The new hook locks and reads no value link row.

### The hook kind

`chokePoint/hooks.ts` gets a registry of relation edge before-link-break hooks next to the three registries of relation edge hooks: `RelationEdgeBeforeLinkBreakHook` (its context is `RelationEdgeChangedHookContext`), `registerRelationEdgeBeforeLinkBreakHook` and `runRelationEdgeBeforeLinkBreakHooks`, which awaits the hooks in registration order inside the write's transaction, and `clearHooksForTests` empties it. `linkRuleEdgeLockHook` in `valueLinks/linkRuleEdgeHook.ts` is registered in `domainWriteHooks.ts` directly after `linkRuleEdgeHook`. The lock goes through a registry because a direct call from `relationOps.ts` to `linkRuleEdgeHook.ts` closes an import cycle through `linkPropagation.ts`, which imports `relationOps.ts`, and because a call of only the rule catalog would make the generic write path import the link domain by name, which the registry ADR replaced. `relationOps.ts` skips the registry for a `system` writer, and the hook skips a `system` writer and an `update` as well.

### What was not done

- **A blocking item row lock at the link break, for every relation.** It would come after the definition advisory lock that the cardinality trigger takes on every edge insert (`db/migrations/0013_relation_cardinality.sql`) and holds to the end of the transaction. `setRelationWithClient`, the update preconditions of a proposal and the Threads merge lock the item row first and that definition afterwards. For a relation that is the target of a rule and no rule's via relation (`Transcripts.company`, `Files.companies`) such a lock would open a cycle that does not exist today.
- **A blocking item row lock before the edge write.** It conflicts with a transaction that already holds the definition lock from an earlier insert of the same definition (`createItemWithRelationsWithClient` writes several edges of one definition), while a single edge write holds the item row and waits for that definition.
- **A nonblocking reservation of the item row with a busy refusal for user and agent writes.** It would refuse requests that wait today.
- **Running the edge-changed hooks before the link break.** Withdrawn, as the Context says: it takes the `company` link before the `project` link, against the trash of an Event and the release of a removed `event` edge, which take them the other way round.

## Consequences

The measurements below are production calls on pools of the runtime role `semprec_data` with a third transaction holding a row, in `backend/packages/data/src/__tests__/valueLinkEdgeBreakLockOrder.test.ts`; "the tree before" is the integration branch without the lock.

- **Schedule A** (the `valueLinksPropagate` handler for a change of the Event's project against a user `deleteRelation` of the transcript's `project` edge, both waiting for the transcript row). Before: when the propagation waited first, one of the two ended with `40P01` (the user's write in the run that was inspected, which held the link row and waited for the item row); when the user's write waited first, both committed. After: no order ends with `40P01`. When the propagation waits first it ends with the busy refusal of the relation admission (`value_link_busy`), the user's write commits the removed edge and the link it broke, and the propagation run again commits and writes nothing to the transcript. When the user's write waits first, both commit and the propagation writes nothing. The user's write now waits for the row before it holds a link row, so the propagation that gets the row first meets no link row of the user and is refused by the nonblocking admission of its own relation write.
- **Schedule B** (a user `relation.set` against a user edge write of the same relation for the same transcript, which reaches the transcript row only in the engine's hook). The eight cases are the same before and after. On `company` (a rule's target and no rule's via relation) the four cases commit and the write does not wait for the row. On `project`, the two cases in which the write that deletes or creates the edge waits first commit. The two cases in which the set waits first, against a delete and against a create of the edge, end one of the two with `40P01` before and after the lock: the set holds the item row and waits for the edge row (or, for a create, the definition advisory lock), while the write holds that edge row or advisory lock and waits for the item row in the engine's hook. This deadlock is not repaired here, it has no permanent test, and it is the engine's own: the hook already waited for that row at that position. A user who runs `relation.set` and an edge write on the same transcript's project concurrently can still meet it.
- **Schedule C** (a user `deleteRelation` of the transcript's `project` edge against `softDeleteItem` of its Event, with a third transaction holding the transcript's `company` link row). Both orders commit before and after, and the transcript keeps its company edge with no value link left. The user's write takes the item row and `project` before `company`, as the trash takes `project` before `company`, so whichever of them gets `project` first, the other waits for it.
- **A write that waits.** While a third transaction holds the item row, a user edge write and an agent edge write that needs no approval on `Transcripts.project`, and a user create of the edge, wait for the row and hold no value link row of the transcript, checked while they wait with `SELECT ... FOR UPDATE NOWAIT` on another connection. On the tree before they held the `project` link row while they waited. The same holds for the file in a user delete of `Files.projects`, the via relation of `fileCompaniesFromProjects`. A relation that is no rule's via relation does not wait for a transaction that holds its item's row.
- **The three schedules the relation ADR measured** (link `SHARE` against the seeded Inbox type hook's source row, against a paired Files/Projects definition advisory, and against a populated rollup job key) concern writes of the `valueLinks` process, which run no before-link-break hook and keep their admission. Their permanent tests (`valueLinkWrites.test.ts` and the others named in the handover) pass with the lock. The lock moves the item row of a user edge write ahead of the rollup enqueue and the link break; before, the engine's hook took it after them. A user write that holds a keyed rollup enqueue and then waits for the item row of a transaction that holds that row and waits for the same key meets the nonblocking admission and the one-millisecond lock wait of the protected write, which end with the busy refusal, not with a cycle. That composition was reasoned from the protocol and not re-measured with the new lock.
- **A transaction that already holds proposal, definition or edge locks.** The lock comes after the edge row is written or deleted, so after the definition advisory lock of the cardinality trigger and after every lock the edge-write hooks and the proposal took, exactly where the engine's hook takes the same row. For a relation that is the via relation of a link rule it therefore adds no position the write does not already have, and it opens no cycle with `setRelationWithClient`, the update preconditions of a proposal or the Threads merge that the engine's hook did not already open; the schedule B deadlocks above are the example. Existing tests of the relation write path, the link rules and the transcript, task and mail write hooks pass.
- **The approval check of an agent write** (`valueLinkApproval.ts`) share-locks `on` link rows before it ends them and refuses the write when it finds one. In `createRelationWithClient` the new lock comes before that check, and the checks for a replaced edge are not changed. A test shows the before-link-break hook runs, and the approval refusal follows, for an agent under a run.
- **Limits.** The lock does not cover a transaction that ends a link in one edge write and reaches the same item's row only in a later statement. The replay of an approved agent write is not repaired, nor are the two trash schedules of the Decision (the order of the `project` and `people` links the trash takes, and a hosted task that is also sourced from its Event). Every deadlock of schedule B that exists on the tree and that this ADR does not repair stays. Not measured with the new lock: the three paths of the Decision, and an edge write of a user on `Files.projects` when the file's `projects` link is `on` (the rule that makes it so, `fileProjectsFromEvents`, is not on the tree).
- A user or agent edge write on a via relation now waits for a transaction that holds the item row before it holds a value link row; before, it held the link row while it waited. The same transactions wait as before, since the engine's hook locked that row in the same transaction.
