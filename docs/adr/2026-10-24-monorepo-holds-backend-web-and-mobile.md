# One repo holds backend, web and mobile, and mobile is reviewed as three platforms

## Context

[[2026-09-10-single-monorepo-for-the-whole-product]] put the whole product in one repository:
`backend/`, `web/` and `apple/`, a shared Swift codebase for iOS and macOS that never got past an
empty scaffold. `apple/` held only its review rules (`apple/review-rules/`), a short README and
`apple/auth-bridge.md`, the native session contract of issue #141.

The mobile apps now share their logic below the UI in Kotlin Multiplatform
([[2026-10-24-kotlin-multiplatform-below-native-mobile-ui]]). One Gradle build compiles the shared
Kotlin modules, the Android app consumes them as Gradle projects, and the Apple app links and
embeds the framework that its Xcode build phases ask the same Gradle build to produce. Keeping the
Apple app in a top-level `apple/` beside separate top-level directories for Android and for the
shared code would split that one build across three roots. A separate repository for mobile was
rejected for the reason the superseded decision gives for the whole product: an issue that changes
the API and its clients would span several repositories and several histories.

## Decision

The repository holds three products, each in its own top-level directory:

- `backend/` — the pnpm workspace of services and packages;
- `web/` — the React/TypeScript web client;
- `mobile/` — the mobile platform. `mobile/` is the Gradle root (`mobile/settings.gradle.kts`, the
  wrapper, `mobile/gradle/libs.versions.toml`, the included build `mobile/build-logic/`, the
  detekt configuration in `mobile/config/`, and `mobile/scripts/`) and holds:
  - `mobile/shared/` — the Kotlin Multiplatform modules `core`, `domain`, `data`, `presentation`
    and `umbrella`;
  - `mobile/android/` — the Android app;
  - `mobile/apple/` — one SwiftUI codebase, with Xcode projects generated by Tuist, that builds
    the iOS/iPadOS app and the macOS app.

The top-level `apple/` directory is gone. Its review rules moved to `mobile/apple/review-rules/`
and `auth-bridge.md` to `mobile/apple/docs/auth-bridge.md`, both with `git mv`.

Every platform keeps its own `review-rules/`, and the code-review bot assigns each file to the
platform whose directory is the longest prefix of its path (`review-rules/context.md`). `mobile/`
is three platforms:

- `mobile/review-rules/` — everything under `mobile/` that is not under `mobile/android/` or
  `mobile/apple/`: the shared Kotlin modules together with the Gradle root, `build-logic/`,
  `config/` and `scripts/` that build and check them;
- `mobile/android/review-rules/` — the Android app;
- `mobile/apple/review-rules/` — the Apple app.

The shared Kotlin code is not a platform of its own. It is compiled by the convention plugins in
`mobile/build-logic/` and consumed by both apps, so its review sits with the build that configures
it. One platform fewer also keeps a pull request that touches the repository root and all of
`mobile/` at four platforms: the code-review bot starts at most four platform agents at a time
(`MAX_CONCURRENT_PLATFORM_AGENTS`, default 4) and waits for that batch before it starts more.

## Consequences

- An issue that changes the shared Kotlin layer and both apps is one pull request in one history,
  reviewed by each platform it touches; a change confined to one app is reviewed only by that
  app's platform.
- ADRs gain the `area` value `mobile`. ADRs dated before 2026-10-24 keep `apple`, which there
  names the Apple client, now `mobile/apple/`; decisions that govern the mobile apps are found by
  grepping `area` for both values.
- The repository root has no Gradle or Xcode project. Gradle runs from `mobile/` (`./gradlew`),
  Tuist and `xcodebuild` from `mobile/apple/`.
- `.github/workflows/ci.yml` builds and tests `backend/` and `web/` only; nothing in CI builds or
  tests `mobile/`.
- The mobile apps carry their own version name and build number (`versionName` and `versionCode`
  in `mobile/gradle/project.properties`, mirrored in
  `mobile/apple/Tuist/ProjectDescriptionHelpers/ProjectConfiguration.swift`), because Google Play
  and the App Store identify every uploaded build by them. They identify app builds, not releases
  of the repository: [[2026-09-24-monorepo-release-tag-from-guarded-command]] still defines the
  one release tag.
