## Specification

The record is `issues/items/gh-1844.md`. No decision record exists. Worker summary: Page operations are held to the agent project's per-database grant. resolvePageOwnerDatabase (docs/pageOwnerDatabase.ts, exported from the barrel) answers the item's own database, the root host's database for a Pages subpage (parentItemId walk, trashed ancestors followed, bounded at 1000, cycle/orphan refused) and the Journal database for a Journal day. assertAgentPageAccess runs it plus assertAgentDatabaseAccess inside the transaction of each page read (page.get both formats, page.changes) and write (ensure, createSubpage including a Journal-period parent, duplicate, rename, insert, replace via its writer, restoreVersion via its approval projection). OPERATION_METADATA: every page operation now holds core.item.read or core.item.write. page.replace is no longer REST-only: an agent's call is held for approval (new PageReplaceCheck / computePageReplaceProjection, snapshot kind page_replace, description key approval.pageReplace with en/cs notification catalog entries); the approved replay runs replacePageMarkdown authored user; page.restoreVersion's projection now carries the agent project. Stale etag, invalid Markdown and bad page links answer at the call and create no request. ADR 2026-11-13-page-operations-follow-the-owner-database-grant.md records the decisions.

Deviations and spec seams declared by the worker: (1) Issue says every page operation carries core.item.read/write; the code had core.page.read/write (ADR 2026-10-28 section 3, ADR 2026-11-06). Followed the issue, reconciled in the new ADR; core.page.* ids stay registered and the 2026-11-06 manifest exclusion is untouched but now has no operation behind it, so project agents now discover all page operations (AgentTool/contract/gateway tests updated accordingly). (2) The Task says to apply the grant check in genericOperationGateway.ts; per ADR 2026-09-17 / 2026-11-12 the check lives in the data layer in each operation's transaction (docStore methods take agentProjectItemId; the gateway only gained the page.replace approval wiring and the agent project on the restore check). (3) Journal restriction: see BLOCKED row; the issue's 'Journal restricted to read' cannot be produced by a grant row under the delivered model. (4) page.replace left REST_ONLY_OPERATION_NAMES (needed for 'held for approval'); a run credential over REST PUT page.md now gets 403 approval_required instead of 404. (5) Spec seam: the web approval catalog (web/src/i18n/messages.ts) has no approval.pageReplace entry; web/ is out of scope, backend en/cs notification catalogs have it. (6) page.changes checks access in its lookup transaction, not inside the later REPEATABLE READ replay (documented in the ADR). (7) page.get breadcrumbs are not filtered by grants of ancestor databases (documented in the ADR). (8) MAX_SUBPAGE_CHAIN and UUID_RE moved from pageOperations.ts into pageOwnerDatabase.ts and imported back (one definition). (9) ReplacePageMarkdownInput.actingUserId became optional so the approved replay can pass the executor's optional user. (10) Existing tests that assumed REST-only page.replace or core.page.* run credentials were updated (gateway, operationCatalog, AgentTool and MCP contracts, pageChangesHandler, pageMarkdownInsert, pageMarkdownReplace).
