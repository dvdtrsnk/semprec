Observations recorded without a finding, not changed and not filed as issues:

- Requirements reviewer, for an owner decision: the production typed capture (item create plus type edge in one transaction) now queues the `create` and the `update` tick. After a successful first tick the second is a no-op. When the AI gateway fails or the budget is exceeded, both jobs record: `writeComputeFailure` clears the fingerprint, so the second job computes again and appends a second "Computing the proposal failed" history entry, with twice the gateway attempts. `inboxTick.test.ts` removes the `update` job to keep its #1485 assertion of exactly one entry, so no test shows the combined outcome. The reviewer recommends a follow-up issue; the behaviour conforms to the Task as written.
- The worker (deviation 6) and both reviewers: `deleteInboxTypeWithClient` clears edges source by source, so it now holds the day's keyed recompute job of an earlier source while it waits for the row lock of a later one, and a writer that takes the source lock first and the day key second can deadlock with it (40P01). The function has no caller outside tests at this commit and is not exported from the data barrel; the follow-up should land before a route calls it.
- Rules reviewer, derived from the code and not reproduced: a type edge writer now takes the day's keyed job while it holds the source row and the card rows, and the tick's read phase takes the same day key first and then, in three branches, a blocking card lock. One of the two is aborted with 40P01, a retried tick job or a failed `PUT` or `DELETE`. Confirm, reject and revise have the same exposure to the read phase today; the fix belongs to the tick's read phase, outside `Touches`.
- Rules reviewer: the adapted writer-first "change type" arm of `inboxTickProposal.test.ts` no longer exercises the post-model source lock wait for a type change. The discard of a stale answer after a type edge change stays covered by "discards recognition after a source type-edge change" (PASS at landing), and the wait itself by the two attachment arms.
