Observations recorded without a finding, none of them changed:

- Requirements reviewer, for the owner to confirm: an Email that sits only in a folder the user trashed before the removal is not a member, stays live and is still returned by the generic Emails list. It follows from the counting rules of gh-1501, which the Task tells the job to follow, and it is in tension with the literal wording of the first acceptance criterion. The first test pins it.
- Requirements reviewer: the job leaves the Threads items live. The Task names only Folders and Emails, and no existing path trashes a Threads item when its last message is trashed, so a counted thread is one that leaves the thread list.
- Requirements and rules reviewers, not traced by either: a sync pass already running when the mailbox is removed could still ingest Emails after the job's cursor has passed them. The review fixes of gh-1690 (`dc15efaf`, `c8eb45e5`) changed the sync job after these reviews: the removal waits for a pass that is in its write transaction, and a pass that starts its write transaction after the removal ends without work. The recheck judged those fixes. No test drives the job against a concurrent sync pass.
- Security reviewer: `deletedAtExact` can backdate `deleted_at`, which the trash purge counts retention from. Every caller of `itemDeleteWithClient` and `softDeleteItem` was checked at the commit; only the job passes the option, with a value read under `FOR SHARE` from the tenant's own Mailboxes item. The security reviewer did not recompute the write-safety fingerprint; the requirements and rules reviewers did, and `check:write-safety` passed at landing.
