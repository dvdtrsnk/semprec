## Specification

The record is `issues/items/gh-1838.md`. Worker summary: Added sleep/sleepResync.ts: enqueueSleepResync (key sleep-resync:<tenantId>, replace, run 30 s ahead), the strict payload schema { tenantId }, runSleepResync and the module-task handler handleSleepResync. The handler runs in the tenant of the job envelope, sends nothing when the payload names another tenant, loads the user through users.tenant_id, sends { kind: 'sleepResync' } with sendApnsBackgroundPush to each active apns/ios registration, revokes a permanent-failure registration, throws an AggregateError after trying all on transient-failure, and is a no-op without user or registration. The task is declared in the sleep manifest (taskNames sleep.resync, queueAffinity api). sleepWriteHooks.ts gained create, update (also System settings with timezone in the patch), delete and restore hooks that enqueue in the write transaction, registered in domainWriteHooks.ts after the gh-1784 and gh-1799 hooks. No heartbeat, action id or seeded row. ADR added for the job-key and transaction decisions.

Deviations and spec seams declared by the worker: 1. Shared-file ordering blocker #1819 is open: when it lands, its entries in domainWriteHooks.ts go before the gh-1838 block (directly after the gh-1799 hooks); #1835 is the earlier member of this chain. 2. The tenant of a sleep write is read with SELECT app_tenant_default() inside the hook, and the handler cross-checks the payload tenantId against the scope of the job envelope instead of trusting the payload; a mismatch sends nothing. 3. The debounce key makes all sleep writes of one tenant wait for each other at the enqueue (add_job on one key). Two existing tests asserted that a write of another night or plan does not wait for an open sleep transaction: sleepWriteHooks.test.ts 'does not hold a creator of a different night behind the open transaction' and sleepPlanDayExclusivity.test.ts 'lets two moves that do not cross both succeed, the second while the first is still open' now assert that the only wait is the add_job statement and that both writes complete. 4. ADR docs/adr/2026-11-13-a-sleep-change-enqueues-one-debounced-resync-job-per-tenant-in-its-write-transaction.md added (not in Touches) because of that lock and the enqueue-in-transaction decisions. 5. No maxAttempts is set: the queue default applies to the transient-failure retry. 6. Tests outside Touches: sleepModuleManifest.unit.test.ts (task declaration), the two edited tests above, and the new API-level file sleepResyncWritePaths.test.ts (REST, agent gateway, PUT route, notifications unread). 7. The handler and the schema are exported from sleepModuleManifest.ts as the Task says; sleepResync.ts is not in the @semprec/data barrel.
