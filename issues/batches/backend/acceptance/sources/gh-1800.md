Worker summary: calendar/timelineBirthdaySource.ts: one batched query over People with a birthday, one all-day read-only entry (kind birthday, id birthday:<personId>:<year>, personId, personName, title, date, allDay true, calendarId of the live birthdays system calendar or null, readOnly true) per person and per year the range touches, 29 Feb on 28 Feb in a common year, trashed people excluded, an unreadable stored birthday left out with one log line carrying the id. Title from calendar.birthday.title (cs 'Narozeniny – {name}', en 'Birthday - {name}') with the first word of the name, in the tenant user's locale (cs default). Registered in timelineSources.ts. Helpers calendarCatalog.ts and systemCalendar.ts. The timeline entry type became the union CalendarTimelineEntry (stored item | derived entry); the merge sorts through sortKey (birthdays before all-day Events of their day); compact shape returns a derived entry unchanged. Item routes tested to refuse birthday ids.

Deviations and spec seams declared by the worker: (1) The tests reach the item-route rejection through a new semprec-api test file (services/semprec-api/src/__tests__/calendarDerivedIds.test.ts, real HTTP server via createDispatcher) because the item routes live in semprec-api; Touches names only data tests. (2) ADR 2026-11-10 says CalendarTimelineItem.kind is the closed union event|task and a new kind extends the union and comparator in its own issue: CalendarTimelineItem stays the stored shape and a new union CalendarTimelineEntry carries the derived entries; the compact shape returns a derived entry as it is (the spec names no compact fields). journal/journalRouteHandlers.ts: the filter on kind 'event' became a type predicate so the Pick over CalendarTimelineItem still type-checks. (3) The existing test 'lists the core sources as events, then tasks' of timelineRead.test.ts now checks the first two ids; the items() helper of that file filters to event/task. (4) Birthday source sort group: before all-day Events of the day (the spec is silent).
