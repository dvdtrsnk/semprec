## Deviations

Spec seams: (1) updateProposalValuesWithClient is in inbox/proposalValueUpdates.ts, not proposalActions.ts (gh-1892 handover); the Touches line for proposalActions.ts is therefore this sibling. (2) Unknown refs cannot be known while the body is parsed, so the handler's parser (inboxRouteHandlers.ts) checks shapes, UUID ids and the per-list cap, and unknown refs and the primary step switched off are refused by updateProposalValuesWithClient before any write (the primary is found by role, destinationRef, so it also covers a multi-step primary whose ref is not 'primary'). A body with none of set, relations, steps keeps the gh-1892 error details.field 'set'. (3) set refuses the keys relations and enabled as reserved (ADR), so a database property named enabled (the Sleep settings database has one) cannot be edited through set. A stored userOverrides whose ref holds a non-boolean enabled or a malformed relations is now 'Malformed userOverrides' (plain Error); no such row can be produced by the route. (4) A switched-off step's relation lists are left out of userEditedKeys as well as its fields (the Task names field keys; the hidden-field rule it cites covers the whole step). (5) reviseProposalWithClient (gh-1924) keeps only property keys of the new destination, so it drops relation lists and step switches and reports them as dropped; changing that is out of scope. (6) An update step's own relations are touched only for a key it already holds; its new targets are written to after.relations, which validation requires to agree. (7) mergeUserOverrides keeps its signature (the third argument is now the request's edits, set plus the reserved keys).
