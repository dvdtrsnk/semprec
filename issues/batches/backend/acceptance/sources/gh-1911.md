Sweep `notifyHeartbeatError` raises `agents:heartbeat:<id>` next to `heartbeat_error`; `finishAgentRunWithErrorNotification` raises the heartbeat problem for a tick run or `agents:run:<first run of the retry chain>` (with `project_item_id`) for a supervisor or MCP run, skipping chat turns; `finishTickRunWithMessage` raises the heartbeat problem for a done tick reply that left a failed tool call. Key builders in `semp/agentProblemKeys.ts`, raise helpers in `semp/agentProblems.ts`, chain root lookup `getRetryChainFirstRunId` in `agentRunsStore.ts`.

Deviations and spec seams declared by the worker: (1) the Task names `scheduler/actions.ts`, but the final failed attempt closes through `finishTickRunWithMessage` into `finishAgentRunWithErrorNotification`, so the raise sits there and `actions.ts` is unchanged; a startup repair or cancellation of a supervisor/MCP run or of a tick run naming a heartbeat now also raises a problem. (2) `context.heartbeatId` is always set, so the agentRun branch is reached from the store. (3) The tick reply stores no steps, so the failed-tool-call check derives them from the run events and applies `deriveReplyOutcome` of #1890; `TickThreadRef` gained `heartbeatId`; `getRetryChainFirstRunId` is exported through the store barrel and listed in `publicSurface.test.ts`. (4) Heartbeat problems carry no `project_item_id`; a cancelled run still raises.
