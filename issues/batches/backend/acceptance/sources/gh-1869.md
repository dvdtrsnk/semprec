## Specification

The record is `issues/items/gh-1869.md`. Worker summary: Threads.company and Threads.project are inherited through two resolver link rules. The link engine had no rule whose value is computed, so the manifest schema and registry gained a resolver rule variant (key, target, resolverExport; getLinkResolverRules) and the engine (valueLinks/linkResolver.ts, linkPropagation.ts, linkResolverTriggers.ts) evaluates it: item lock then link lock, own value kept, broken link untouched, link created before the write, sources replaced, empty answer removes the inherited value and the link, job paged by 100. mail/threadLinkRules.ts holds the freemail list, the web-host matching, the first-inbound-sender query (incoming copies by activity then item id), the company resolver (known person: one company of People.companies whose host matches, source the person/companies; unknown sender: one matching company, source senderDomain/web; freemail, none or several give nothing), the project resolver (exactly one company; one project with status inProgress or longTerm; source company/projects), the declared inputs (People.companies, Companies.projects, Threads.company edges; Companies.web, Projects.status) and the affected-thread lookups. linkRuleEdgeHook and linkRuleItemHook queue valueLinksPropagate for declared inputs; ingest queues both rules for the thread after the folder edge when the new message is now its first inbound message. relinkValue of a resolver link reruns the resolver (409 value_link_conflict when it has no value, e.g. no company has the sender domain in its web any more). threadValueEdgeChangedHook publishes the mailThread invalidation for every created or deleted Threads.company/project edge. reassignThread plans the merge (own beats inherited, equal kinds older mail_threads.created_at wins, tie keeps the winner, company and project decided apart), transferMailThreadRelationsWithClient replaces the winner's edge when the loser's value wins, the link moves with the value, loser links are deleted and the rules whose source is Threads.project are scheduled through scheduleDownstream. ADR 2026-11-14-a-thread-inherits-its-company-and-project-through-resolver-link-rules added.

## Deviations

1. Task step 2 (a migration for the `senderDomain` source) was not needed: `0089_value_links.sql` has `source_kind` item or senderDomain, a nullable `source_item_id` and a `domain` column, and the store, the read shape and `shared/rows.ts` already carry the variant; only relink for a `senderDomain` source was added. 2. The link engine knew no resolver (gh-1593 lists sender-domain sources as out of scope), so the resolver rule variant, its evaluation, triggers and relink were added, with the ADR. 3. Relink of a resolver link reruns the resolver for the thread's current sender, not the stored domain. The project link's source is the company item with property `projects` (the Task says 'source Threads.company'); the company link's sender-domain source uses the property key `web`. 4. Edits outside Touches, all needed: `relationOps.ts`, `valueLinksStore.ts`, `valueLinkOps.ts`, `linkPropagation.ts`, the two link rule hooks, `threadValueEdges.ts`, `domainWriteHooks.ts`, the module-registry files and new `valueLinks/*` modules. 5. Existing tests changed because of the new behaviour: three merge tests of `threadValueEdges.test.ts` create the winner first, `fileCompaniesLinkRule.test.ts` drains the queue lane, and `proposalActions.test.ts`, `inboxTickProposal.test.ts` and `schemaHandler.test.ts` write People, Projects edges inside the tenant-zero scope because those writes now queue propagation. 6. A merge does not queue the thread rules explicitly: the edge changes of the transfer queue the project rule. 7. The first inbound message is read with the CTEs of `mailThreadCopyCtes`, not from a stored flag. 8. Not covered: a change of `People.emails` or a folder move queues nothing (ADR consequence); no backfill of existing threads; trashing a company is not an input of the rules.
