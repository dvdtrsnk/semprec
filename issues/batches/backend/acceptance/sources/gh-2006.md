## Specification

The record is `issues/items/gh-2006.md`. Worker summary: calendar.ingestInvitation now also applies iMIP METHOD:CANCEL (first VEVENT without RECURRENCE-ID) in the same per-email transaction and under the same per-tenant/UID advisory lock as REQUEST. For a live invitation of that UID, sent from the invitation's organizerEmail (case-insensitive, via normalizeEmailAddress on mail_message_meta.envelope.from) and with CANCEL SEQUENCE >= stored, it trashes the live linked Event (itemDeleteWithClient), writes status cancelled and the CANCEL sequence as the calendar module system owner (respondedAt kept) and resolves the notification (resolveNotificationsBySource items/invitation id). Sender mismatch and stale sequence are logged (email id, invitation id, reason code sender_not_organizer / stale_sequence). Unknown UID, trashed invitation, already cancelled: no-op. Any failing step rolls the email back.
