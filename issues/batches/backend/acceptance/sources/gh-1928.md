## Deviations

Spec seams: (1) updateProposalValuesWithClient now lives in inbox/proposalValueUpdates.ts (gh-1892 handover); it returns {item, warnings} instead of the ItemRow, so the test helper edit() in proposalActions.test.ts maps .item. (2) The item envelope is built in services/semprec-api/src/adapter/adapterRoute.ts; there is no sendItemResponse in adapter/http.ts, so the optional warnings field was added to AdapterHandlerResult and the envelope there. ProposalWarning is exported as a type on the existing ConfirmationResult line of packages/data/src/index.ts (that file is at the 900-line cap). (3) New code is in siblings (proposalEditorRules.ts; the pure functions in editorSchema.ts); the Touches list names editorSchema.test.ts, the existing file is editorSchema.unit.test.ts (unit tier) and the DB-backed tests are in the new proposalEditorRules.test.ts. Decisions where the Task left room, recorded in the new ADR: the schema is not applied to a relation envelope, a multi-step envelope whose primary step is update or link, a legacy block-shape pageContent envelope, or a destination that deriveInboxCardKind maps to a clarify card (otherwise any non-system database such as MCP servers would be held to the page schema); a pageContent envelope answers the pseudo fields page and day with its target (otherwise no journal or page card could be confirmed); a field of a multi-step card is read from the first step that has its key and a missing one is reported on the primary step; a pseudo key is accepted under any ref the card has. The values route always returns warnings (an empty array when none). Confirm reads stored userOverrides only when a schema applies; malformed stored userOverrides then throw a plain Error (as in gh-1892). The module registry for getEditorSchemas() is cached per process in proposalEditorRules.ts, like the three similar caches elsewhere.
