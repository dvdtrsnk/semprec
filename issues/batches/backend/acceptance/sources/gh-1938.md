(2) Spec seam: reviseProposalFromThreadWithClient lives in the new sibling proposalThreadRevision.ts and is re-exported from proposalActions.ts, because proposalActions.ts is near the 900-line ESLint cap. (3) index.ts has no free line under the cap, so loadInboxCardThreadContext and renderInboxCardThreadContext are re-exported from inboxAgentTools.ts (already star-exported); publicSurface.test.ts lists them. (4) Attachment names do not exist (gh-1623): attachments are listed as { attachmentId, name: null }. (5) The Task is silent on an edited key that the revised envelope no longer holds: it is removed from the overrides and from aiProposal (the instruction removed the field), tested. (6) The Task is silent on several cards per source: the newest live card is used. (7) Shared files touched beyond the Touches list: sempThreadsStore.ts (getSempMessageTurn returns subjectInboxItemId), inboxCardsStore.ts (loadItemTypes exported), testSupport/testDb.ts (test-only re-exports of confirmProposalWithClient and updateProposalValuesWithClient), inboxAgentTools.ts and proposalOverrides.ts. (8) reviseProposalFromThreadWithClient takes an optional actingUserId (as reviseProposalWithClient does) for the realtime addressing. (9) The send guard still refuses a new message to the thread of a confirmed or rejected card (gh-1620, not in this Task), so a confirmed-card turn is reached when the card is confirmed after a message was queued; the test does exactly that.
