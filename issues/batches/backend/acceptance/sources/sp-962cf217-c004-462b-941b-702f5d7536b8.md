Observations recorded without a finding, none of them changed:

- Worker, fixer and all three reviewers, behaviour that predates this chain: the locked read does not compare the locked row's `deletedAt` with the cutoff, so a row restored and trashed again between the walk and its delete is still removed although its trash is fresh (`itemsStore.hardDeleteItem` guards only `deleted_at IS NOT NULL`; `itemsStore.ts` is not in `Touches`). Proposed follow-up: compare the locked row's `deletedAt` with the cutoff before the delete, in a source of its own, preferably before gh-1691.
- Rules and security reviewers, worker: `trash/purgeExpiredTrash.ts` (unchanged) logs the raw error object of a failed purge call, so a consumer hook must not put user content into an error it throws.
- Requirements reviewer: the test of the re-trashed row uses a cutoff in the year 2999, so it does not pin the removal of a row newer than a real cutoff.
- Worker: `purgeExpiredTrashSubtree` now reads the database row of each removed row, one read per distinct database of a call, also when no hook is registered.
