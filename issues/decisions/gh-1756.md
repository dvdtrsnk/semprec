# Decision: gh-1756 (Inherit an Event attachment's project from its Event)

## Question

Chain e1-026-misc implemented gh-1756 (`[calendar-events 09/12]`): the link
rule `fileProjectsFromEvents` (source `Events.project`, target
`Files.projects`, via `Files.events`) and its tests. After one review, one fix
round and one focused recheck the chain is held on six findings, two of which
are one defect seen by two reviewers:

1. Acceptance criterion 3 is not met: after the attachment is removed the
   file's company is still inherited, from the project the file keeps.
2. After the Event's project changes from P to Q the attachment keeps P's
   company as an own value.
3. Task step 2 asks for a backfill of existing `Files.events` edges through a
   mechanism of #1593 that does not exist.
4. Attaching a file to an Event whose project is in the Trash is refused with
   400 `validation_failed` (requirements reviewer and rules reviewer).
5. `Files.projects` is now the target of one rule and the via relation of
   another, and a user edge write on it takes the link row before the file
   row, against the engine's item-before-link order (`40P01`).

The fixer confirmed every one of them, five by execution, changed one test
and rejected the rest as needing a decision. Decide each finding and what
happens to the chain.

Finding 1, company link after the removal:

- Revise criterion 3 so that the company keeps following the file's project:
  rejected. The criterion repeats a product owner decision in the epic
  ("Unlink only; file stays in Files, inherited project and company stay as
  own values (#1756)") and in the Context. gh-1697 implements the same
  decision for transcripts. A requirement that is right is not a
  specification defect.
- A follow-up source for the release, landing gh-1756 with the criterion
  failing: rejected. It is this source's own acceptance criterion.
- The unconditional release of the transcript module (end the company link
  on every removal): rejected. A file can have a project of its own before it
  is attached and can be attached to several Events. Ending its company link
  on any removal would change what gh-1653 delivered for such a file.
- A step in this source that ends the link when the removed Event was the
  only source of the file's `projects` link: chosen. The Task had no step and
  Touches no file for it, which is the defect. The engine ends only the link
  whose via edge was removed (`linkRuleEdgeHook.ts:33`, `64-72`), so the step
  is a Files hook like Task step 4 of gh-1697. Its condition can be read only
  before the engine deletes the `projects` link, so it is registered before
  `linkRuleEdgeHook`. The hook also detaches the Event from a `projects` link
  the user had broken, which the engine leaves in place; otherwise the
  project would not read as own, as the criterion says.
- After the challenge: the release reads the file's `projects` link. When the
  Event was moved to the Trash before the attachment is removed, the source
  detach of gh-1656 has already deleted that link
  (`valueLinkSourceDeleteHook.ts:35-41`) and a restore relinks nothing, so
  the hook changes nothing and the company keeps following the project. That
  path cannot be told from a file with a project of its own and needs the
  Trash hook the owner has not decided. It does not hold the source; it is
  stated in Task step 5 and in the scope, Task step 6 has the ADR state it,
  and it is listed below.
- After the second challenge, a second limit of the chosen release. When the
  removed Event was the only source of the file's `projects` link, the
  release deletes the `companies` link whatever its state. For a `projects`
  link that is `on` this is exact: every project of the file came from the
  Event. For a `projects` link the user had broken by adding a project of
  their own while the file was attached it is wider. The user's write breaks
  only the link of the written relation (`valueLinkWrites.ts:62-94`), and the
  engine makes the added project a source of the `companies` link, which
  stays `on` (`linkRuleEdgeHook.ts`, the create branch,
  `addValueLinkItemSource`). When the attachment is then removed, the release
  ends that link as well: the company of the project the user added stays on
  the file as an own value and no longer follows that project. A file whose
  own project predates the attachment has no `projects` link and keeps
  following (criterion 6). A narrower release is not chosen. It would have to
  tell the Event's projects from the user's on a broken link, criterion 3
  asks for own values, and the transcript release of gh-1697 is
  unconditional. The outcome is decided here as a limit. It is the case that
  the test "The same holds for a file whose project link the user had broken
  before the removal" of Task step 3 pins, and it follows from the condition
  of the release, which Task step 6 has the ADR record.

- What the prerequisite source does, changed after the challenge. The first
  version made it take a blocking item row lock at the place of the link
  break. That lock would come after the definition advisory lock which the
  cardinality trigger takes on every edge insert
  (`db/migrations/0013_relation_cardinality.sql:28`), and it would open a new
  cycle with callers that lock the item first and that definition afterwards
  (`setRelationWithClient`, `relationOps.ts:670`; the Threads merge,
  `relationOps.ts:536-542`) for relations that are a rule target and no
  rule's via relation. The lock before the edge write, which the challenge
  proposed, conflicts by reading with a transaction that already holds the
  definition lock (`createItemWithRelationsWithClient` writes several edges

  source therefore adds no lock: it runs the edge-changed hooks before the
  link break, so the item row lock the engine's hook already takes comes
  before the link row. This was derived by reading. The source reproduces
  first, measures the item-first callers as a baseline and stops without a
  committed change when the reproduction contradicts the order. A
  nonblocking reservation with a busy refusal for user writes is left out:
  it would refuse requests that wait today, which is a product-visible
  decision.

## Decision

DEFECT, corrected. This decision corrects the specification of gh-1756. No
code is changed for it in this program.

- Finding 1: code fix in this source on a corrected Task and Touches (new
  steps 5 and 6, two more skills on the load line).
- Findings 2 and 4 (both lenses): specification corrected. #1697 is a
  blocker; the outcomes are tested and are acceptance criteria.
- Finding 3: specification corrected. Nothing is backfilled.
- Finding 5: new prerequisite source `sp-5419cac1-f4a7-4717-b870-4f244b1ad166`,
  "[value-link-edge-lock-order 01/01] Run the edge-changed hooks before a
  user or agent edge write ends its value links" (high tier, waits for #1697
  only). Its record is created with this decision, approved and routed.
  gh-1756 names it on its Blocked-by line and gets a test and an acceptance
  criterion for the same schedule on `Files.projects`.

What happens to the chain. A decision that needs a code change gives a held
chain one more fix round and one focused recheck (`CONTROLLER.md`, "Decisions
on held chains"). That round is not run. The owner stopped further
implementation on 2026-11-11 (`CONTROLLER.md`, "Program state";
`docs/adr/2026-11-11-a-reviewed-chain-may-land-ahead-of-an-open-shared-file-ordering-blocker.md`):
chains that had passed review, the fix round and the recheck are landed, and

The implementation the chain delivered (`fad96144f..7f5c60fc4`: the rule
`fileProjectsFromEvents` in the manifest, the new test file, the changed
fixture rule of `linkRuleEdgeHook.test.ts` and two adapted tests) is partial

A later implementation of gh-1756 starts from the corrected specification on
`develop` and not from the chain. What it must do is in the corrected Task,
Touches and acceptance criteria below; the blockers it waits for are on the
Blocked-by line.

Limits of the release of step 5, decided here:

- An attachment removed after its Event was in the Trash keeps a company
  that follows its project (Finding 1, "After the challenge").
- When the user added a project to the file while it was attached and the
