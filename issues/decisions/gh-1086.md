# Decision: gh-1086 (security gate sign-off)

## Question

The security gate gh-1086 requires that "every finding is fixed (each in its own issue) or accepted in writing". Three
independent reports were produced at commit `e6387779b` (whose tree is identical to the integration tip `30753cc6e`):
the database part of an adversarial review (`r2-db-review.json`, findings R2-DB-1 to R2-DB-5, reviewer model
`claude-fable-5-2`), the application part (`r2-app-review.json`, R2-APP-1 to R2-APP-4, reviewer model
`claude-opus-5-5`) and a local scratch rehearsal of the gate's restore item (`rehearsal-findings.json` and
`rehearsal.md`, RH-1 to RH-6). Which disposition does each finding get, and which new sources carry the fixes?

removed afterwards):

- R2-DB-1 on `postgres:16-alpine` 16.15, the production image the review did not use: a superuser-owned `SECURITY
  DEFINER` plpgsql function with `SET search_path = pg_catalog, public` whose body evaluates `database_id::text`, called
  by a non-superuser login role that had created `pg_temp.pwn(pg_catalog.text)` and
  `CREATE DOMAIN pg_temp.text AS pg_catalog.text CHECK (pg_temp.pwn(value))`. Output: `NOTICE: pwn as
  current_user=postgres session_user=r` and `rolsuper` = `t` (rolled back). After
  `ALTER FUNCTION ... SET search_path = pg_catalog, public, pg_temp` the same script printed no notice and `rolsuper`
  stayed `f`. The finding therefore holds on the production major version.
- R2-APP-4: `git archive e6387779b` into a private directory, install and build, then the integration tier on a

  20 files failed (119 tests failed, 52 skipped, of 351), 10 passed. The same 20 files under `warn`: 20 passed, 273 of
  273 tests. About two thirds of the tier depends on `warn`.

For the global tables of R2-APP-1 and R2-DB-3 the options were: (a) row-level security on `users` (and through it
`sessions`, which has no `tenant_id`) with a policy that lets a system scope see every row; (b) column-level revokes
of `users.password_hash` and the token-hash columns from the runtime roles; (c) revoking from `alldots_side` what no
side process uses; (d) accepting the identity plane in writing. (a) changes the policy shape that the tenancy invariants
and the RLS ADR fix for global tables, needs a join policy on `sessions`, and touches 34 production reads of `users`
including login, session resolution, invitation acceptance, the admin plane and the purge; it is not cheap and could
not be proven here not to break them. (b) is impossible for `alldots_data`: login verifies the Argon2 hash in Node and
session lookup filters on `token_hash`, and a column used in `WHERE` needs `SELECT`; for `alldots_side`, `getUserById`
(reached by the restore-test recorder through `writeNotification`) selects `password_hash`, so a column revoke would
break the previous release after a rollback and is a contract step for a later release. (c) is cheap and verified:
no side process reads or writes the tables concerned. Chosen: (c) as a fix, (d) for the rest.

### R2-DB-1 and R2-DB-5: FIX, source 01

Evidence: `create_items_partition(uuid)` (last body `0072_attach_items_partitions.sql`) and `drop_items_partition(uuid)`
(`0061_tenant_checked_partition_functions.sql`) are `SECURITY DEFINER`, owned by the migrating superuser, with
`SET search_path = pg_catalog, public`; their bodies use the unqualified types `text` and, through
`app_current_tenant()` (`0056_tenants.sql`), `uuid`. PostgreSQL searches `pg_temp` first for relation and type names
when it is not listed. The review escalated `alldots_data` to superuser and to membership in `alldots_router` this way;
this decision reproduced the mechanism on 16.15. The five router functions (0069, 0071, 0073, 0075, 0076) carry the same
setting; they were not broken because their bodies name no type at run time, and they get the same fix as defence in
depth. `findDefinerFunctionViolations` (`db/tenancyInvariants.ts`) counts any `search_path=` entry as pinned, so
`tenancy: verified` is printed for the exploitable catalog. Source 01 adds `pg_temp` last on all seven functions with
`ALTER FUNCTION ... SET search_path` (owner, ACL and body unchanged, so rollback compatible), makes the verifier refuse
a path that does not end with `pg_temp`, lists it earlier, or names a missing or runtime-writable schema, proves the
verifier fails on the exact catalog of R2-DB-1, and replays the exploit as `alldots_data` with a control that fails on
the unfixed function. The requested check for "unqualified type names" is implemented as the search_path rule rather
than a body scan: plpgsql bodies cannot be parsed reliably from `pg_proc.prosrc`, and with `pg_temp` last an
unqualified type name resolves in `pg_catalog` before any temporary object, which is the property the guarantee needs.
`REVOKE TEMPORARY` on the database is not done: integration tests create temporary tables themselves. The verifier
checks definer functions in every schema except `pg_catalog` and `information_schema`, not only in `public`.

### R2-DB-2: FIX, source 02

Evidence: `alldots_side` holds full DML on `agent_runs` and `approval_requests` (0040) and on
`agent_run_mcp_credentials` (0055); the review minted a credential for an attacker-chosen token in tenant B, and the
API's own lookups in `mcp/mcpRunCredentialsStore.ts` resolved it to a tenant-B actor. Verified that no side process
(`alldots-ai-gateway`, the restore-test recorder) writes these tables or reads `agent_run_mcp_credentials`; the gateway
reads `agent_runs` (`reserveGatewayCall` checks that an attributed run exists), so that `SELECT` stays. Every writer
connects as `alldots_data`, which reaches them only through its membership in `alldots_side`. Source 02 grants them directly to
`alldots_data` and revokes the side role's writes (and its read of the credentials), the pattern of
`0057_identity_tables_api_role_only.sql`, which keeps the previous release working.

Accepted in writing for the side role after source 02 (residual of R2-DB-2):

- Reasoning: `alldots_side` keeps full DML on the module side tables in any tenant it names with `set_config`, and on
  every `graphile_worker` table. The AI gateway enqueues jobs (`enqueueAiBudgetReset`), graphile-worker has no per-row
  ownership, and a job envelope's `tenantId` is trusted by `runInTaskScope`, so a compromised side process can make a
  `alldots_data` worker run a registered task with a chosen payload in any tenant. RLS defends against application
  code that forgets a tenant predicate, not against SQL execution under a runtime role (the review lists this as by
  design).
- Residual risk: after a compromise of `alldots-ai-gateway` or `alldots-restore-test` the attacker reads and writes every module side table of any tenant. That includes document and mail content (`docs`, `doc_updates`, `mail_*`, `semp_messages`), the encrypted rows of `external_credentials` and the wrapped keys in `tenant_keys` (neither process holds the master key; deleting `tenant_keys` rows makes a tenant's stored credentials unrecoverable), mail server settings and OAuth states, and the authorization rows `agent_database_grants`, `project_mcp_grants`, `agent_run_read_allowances`, `mcp_tool_registrations` and `project_heartbeats`, plus every queued job. Source 02 closes only the direct paths: it can no longer insert or retarget an `agent_runs` row, mint an MCP run credential, decide an approval request, read a session, reset token, invite or MCP credential hash, or register a push endpoint.
- Revisit when: a side process needs to enqueue a task that writes items or identity rows; a new process gets the side
  role; job envelopes get an authentication mechanism; a task handler starts trusting payload fields as an actor; or the two-tier grant model is revisited so that the side role holds only the tables its two processes use.

### R2-DB-3: FIX for the side-role part (source 02), the rest accepted

Evidence: the catalog has no RLS on the global tables `users`, `sessions`, `password_reset_tokens`, `login_attempts`,
`invites`, `push_subscriptions`, `agent_run_mcp_credentials`, `tenant_ai_budgets`, `tenant_deletions`,
`admin_audit_log`, `tenants`, `process_heartbeats`, `observability_checks` and `schema_migrations`, all classified
`alldots:tenancy=global` (0058 and the migrations that created them). Source 02 removes `alldots_side`'s writes on
`push_subscriptions` and its reads of `agent_run_mcp_credentials`, `push_subscriptions`, `sessions`,
`password_reset_tokens`, `login_attempts`, `invites`, `admin_audit_log` and `tenant_deletions`.

Tables that remain global and readable, and why:

- `users`: read by `alldots_data` for login, session resolution, the admin plane, invitations, exports and the purge;
  read by `alldots_side` because the operator alert of the restore-test recorder lists the admins of every active
  tenant (`listAdminRecipients`) and `writeNotification` reads the recipient (`getUserById`, which also selects
  `password_hash`).
- `tenants`: read by both roles before a tenant is known (status checks of the gateway, `app_sole_tenant()`, the
  restore tooling).
- `tenant_ai_budgets`: read by the gateway to enforce the caps.
- `sessions`, `password_reset_tokens`, `login_attempts`, `invites`, `push_subscriptions`, `agent_run_mcp_credentials`,
  `admin_audit_log`, `tenant_deletions`: read and written only by `alldots_data` after source 02; they resolve who a
  request is before any tenant is known, or are the admin plane and the purge ledger.
- `process_heartbeats`, `observability_checks`, `schema_migrations`: operator tables without user content.

The acceptance of the remainder is the one written under R2-APP-1.

### R2-APP-1: ACCEPT-IN-WRITING

Evidence: as `alldots_data` inside `runInTenant(B)` the review read all users, sessions and tenants, an Argon2 hash
prefix of a tenant-A user and a tenant-A session token hash. Tenant-scoped readers look users up by id without a tenant
predicate (`notifications/notify.ts` `writeNotification` through `getUserById`, `views/viewQuery.ts` `findUserLocale`,
`mail/mailAgentTools.ts` around line 463). No route that returns another tenant's identity data was found.

- Reasoning: the identity plane must be resolved before a tenant is known (login by e-mail, session by token hash, MCP
  credential by token hash, invitation acceptance), and the RLS ADR keeps these tables global by decision. Row-level
  security with a system-scope exception would change the policy shape of the tenancy invariants and touch 34
  production reads, which could not be proven safe for this gate; column revokes are impossible for the role that
  verifies passwords and tokens. Argon2id hashes and SHA-256 token hashes are not directly usable credentials, but the role that reads them can also write them.
- Residual risk: an application bug, an id confusion or SQL injection in tenant-scoped code under `alldots_data` can read every account's e-mail, display name, locale, role, Argon2 hash, session, reset-token, invite and MCP-credential hashes and push endpoints, and can write the same tables: insert a session or an MCP run credential for a user of another tenant, or replace a password hash. The database gives no backstop on these tables for a missing tenant predicate or for injected SQL; a successful injection in any tenant is therefore an account takeover in every tenant. Not traced for this gate (review, notChecked): whether any notification, agent or approval path lets one tenant persist another tenant's user id.
- Revisit when: a second process gets the `alldots_data` role for anything other than the three current hosts; a
  route or tool returns or lists user rows; a tenant-scoped code path reads `users` or `sessions` by an id that a
  client or an agent supplies; the identity plane moves behind a narrow `SECURITY DEFINER` lookup; or a security
  review finds a cross-tenant read of these tables. Before then, the column-level contract step for `alldots_side`
  (a reader of the notification recipient without `password_hash`, then a revoke of the column in a later release) is
  the next narrowing to take.

### R2-DB-4: ACCEPT-IN-WRITING

Evidence: `pgNotifyPublisher.ts` builds the envelope in SQL from `app_tenant_default()` (`publishEnveloped`) and
`parseEnvelope` trusts the payload's `tenantId`; `tenancy/tenantStatusSignal.ts` and `semp/sempTurnCancellation.ts`
publish with an explicit tenant. PostgreSQL has no privilege on `LISTEN` or `NOTIFY`: the review's `alldots_side`
listener received tenant B's agent-stream delta, and its forged `{tenantId: B}` envelope reached the API listener. The same transport carries `alldots_tenant_status` (`tenancy/tenantStatusSignal.ts`) and `semp_turn_cancel` (`semp/sempTurnCancellation.ts`); their listeners act on the payload without re-reading the database.

- Reasoning: the property is inherent to the transport. Envelope authentication needs a new secret distributed to the
  three `alldots_data` processes, signing in every publisher (three sites) and verification in every listener, and it
  would still leave content readable unless payloads carry only ids; that is a design change, not a cheap fix. Every
  role that can listen already holds a database login, and `alldots_side` can read the side tables of any tenant
  anyway.
- Residual risk: a process with any database login reads the realtime payloads of every tenant, including agent-stream deltas with model output, and can inject messages into another tenant's connected clients. It can also disrupt any tenant without touching a row: a forged tenant-deactivation signal closes that tenant's sockets and voice sessions, stops its mail live sync and aborts its running agent runs (which are written as `error`); a forged turn-cancel aborts a running Semp turn; a forged `session_revoked` closes a session's sockets. This is an availability risk across tenants, not a read or write of tenant data.
- Revisit when: a new database login role or process is added; a payload starts carrying more than ids and model output deltas; a notification starts triggering anything beyond the teardown, abort and socket-close actions listed above (a data write, a grant, an authorization decision in favour of the sender); or a deployment shares the PostgreSQL cluster with another application.
- Next narrowing to take, not required for this gate: the deactivation handlers re-read `tenants.status` before tearing a tenant down.

### R2-APP-3: FIX for definition-mounted routes (source 05), the rest accepted

Evidence: `routeMatrixInventory.unit.test.ts` checks duplicates only, `adapterTenantScope.test.ts` filters the matrix by
the mounted definitions, and the doc comment of `ROUTE_MATRIX` says an unlisted route "simply isn't covered". The
review's probe found the 130 mounted routes complete at this commit. Source 05 adds the failing direction for the module

Accepted in writing: the prefix-routed paths of the listener chain in `app.ts` (`/api/server-info`, `/api/schema`,
`/mcp`, `/api/approval-requests`, `/api/agent-runs/`, `/api/auth/`, `/api/notifications`, `/api/setup`,

### R2-APP-4: FIX, staged, source 06

Evidence: `globalSetup.ts` sets `ALLDOTS_TENANT_SCOPE ??= "warn"` and the tier sets `LOG_LEVEL=error`; the measurement
above shows that about two thirds of the 888 integration files fail under `strict` today because their fixtures write
outside a scope. Source 06 makes `strict` the default for every file not on a frozen, shrink-only list and proves a new
file runs strict. Accepted until the later stages land: a scope lost in production code that is reached only by listed
files still passes CI. The controller creates the conversion sources (package by package, each removing the files it
converts from the list) after source 06 lands; the gate is not blocked on them. The
list shrinks by mechanism, not by a review rule: a frozen byte copy of the first list is pinned by its SHA-256 in a
unit test, every entry must be in it, and a source scan fails when a file outside a constant list of the scope-mode
suites sets `warn` for itself. The e2e tier reuses the same `globalSetup.ts` and keeps `warn` through its own
`test.env` (measured by the challenge: 47 of 52 e2e tests fail under `strict` today).

### RH-1: FIX, source 04

Evidence: after the purge, `graphile_worker._private_job_queues` kept `<lane>:<tenantId>` rows of the deleted tenants
(`residual-job-queues.log`); `purgeQueuedJobs` in `tenancy/tenantPurgeJob.ts` completes jobs and never deletes queue
rows, and queue names come from `tenancy/tenantLane.ts`. Source 04 erases the idle rows in `finalise` and refuses to
finalise while one remains. It does so as the last statements of the finalise transaction under
`LOCK TABLE graphile_worker._private_jobs IN SHARE ROW EXCLUSIVE MODE` with `lock_timeout = '2s'`: `add_job` takes no
lock on a queue row and `job_queue_id` has no foreign key, so without the table lock a job enqueued by a still-open
transaction would be left pointing at a deleted queue row and never run (measured by the challenge). The lock stalls
every enqueue for at most that bound until the commit.

### RH-2, RH-3 and RH-4: FIX, source 03

Evidence: `restore_postgres` in `deploy/systemd/scripts/alldots-restore-test.sh` runs
`pg_restore --exit-on-error --no-owner --no-privileges` into a fresh cluster and creates only `alldots_restore`
afterwards; `--no-privileges` does not skip `CREATE POLICY ... TO alldots_side`, which `grantQueueSchemaPrivileges`
creates on the `graphile_worker` tables. The rehearsal's restore of a real dump failed with `role "alldots_side" does
not exist` and succeeded once the three roles existed; the script's tests use synthetic dumps without role references.
`deploy/README.md` gives no `pg_restore`, role, password, blob or key-selection command, and `validateRestoreLedgerCli.ts`
prints one fixed line for every failure, so a missing privilege reads as `Restore ledger validation failed`. Source 03
creates the roles in the disposable cluster first, tests a real migrated catalog, writes and tests the exact restore
commands, picks the newest key dump by path, and gives the validator a content-free failure class. Not done: a
timestamp inside the key dump or a refusal of an older dump by the CLI; the replay of the activation block deletes a
resurrected key again and key snapshots expire after 7 days.

### RH-5: recorded only

The migration CLI prints graphile-worker's `Your pool doesn't have all of the error handlers!` once (`migrate1.log`).
The CLI is one-shot and exits 0; an idle-client error during a deploy would surface as a failed deploy step. Not a
gate defect; it may be fixed opportunistically by giving the pool handed to `ensureQueueSchema` an `error` listener.

### RH-6: recorded only

A database migrated with this code has no physical second-tenant guard: `0123_drop_single_tenant_guard.sql` removes

account before the owner signs the gate. The checklist wording "guard dropped there only" cannot hold for a database
migrated with this code; the owner reads that item accordingly.
