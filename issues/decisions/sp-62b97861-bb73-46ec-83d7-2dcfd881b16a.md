The four service failures are identical with a complete configuration (database URL, master key, gateway token, ports): module loading fails first, because ESM imports are resolved before any code runs. They are not specific to Node 26 (which type-strips `.ts` natively): Node 22.19.0 fails with the same `ERR_MODULE_NOT_FOUND`. The cause is the one the follow-up describes, now observed on the other four entries: every workspace package outside the four repaired roots still has `"main": "src/index.ts"`, so `@alldots/data`, `@alldots/realtime`, `@alldots/application`, `@alldots/notifications`, `@alldots/ai-gateway-client`, `@alldots/ai-gateway` and `@alldots/agent-runtime` (and `@alldots/credentials`, which `data` reaches) resolve to TypeScript source whose relative `./x.js` imports name files that do not exist there. The seven data-package CLIs start only because they import their own package by relative path and reach nothing but the four repaired roots (the static import graph of each was checked).

Options:

- A. Treat the follow-up as stale and only reword it. Rejected: four of the eleven deploy-started entries fail from a plain `node <entry>`, and `deploy.sh` restarts exactly those four (`LONG_RUNNING_SERVICES`) after it activates the release, so a release would be promoted whose services cannot start. The migration, seed and tenancy steps run before activation and pass, which makes the failure appear only after `current` has moved.
- B. Keep the follow-up as it is. Rejected: its sentence "other entrypoints were not proved affected" is now false (they are proved affected), and its batch 19 section correctly records only the migration entry.
- C. A new source that applies the accepted root-export contract to the eight further roots the services reach, proves it with a native-entrypoint test of every compiled entry and adds a native check to `deploy.sh` before activation. Chosen. A bundle of changed manifests found by an experiment (below) shows the repair is bounded, and the ADR of sp-62b97861 itself says a newly reached root needs concrete analysis and a parent decision rather than a wildcard manifest change; this record is that analysis.

Experiment that bounds the repair (private copy only, nothing committed): the same eight manifests were changed to the ADR's pattern (`main: dist/index.js`, `types: src/index.ts`, root export `types`/`browser` to `./src/index.ts`, `default` to `./dist/index.js`, the existing `data` test-support subpaths kept) and the backend was rebuilt (exit 0). Then, under Node 22.19.0, with a scratch database and the runtime roles: `alldots-ai-gateway` logged `alldots-ai-gateway listening`, `alldots-agents` logged `alldots-agents queue runtime started`, `alldots-transcribe` logged `alldots-transcribe queue runtime started`, and each exited 0 after SIGTERM with its shutdown log; with no configuration at all every service refuses in its own application code (`... is not set`). These eight roots are the closed set: a static walk of the compiled import graphs of all eleven entries finds exactly the twelve workspace packages `agent-runtime`, `ai-gateway`, `ai-gateway-client`, `application`, `block-model`, `credentials`, `data`, `module-registry`, `notifications`, `queue`, `realtime`, `shared`, with no `@alldots/*` subpath import in any compiled file. `e2e`, `module-boundaries`, `realtime-client` and `release` are reached by none.

A second, independent finding of the same run: `alldots-api` does not stay up even after the packaging experiment unless `ALLDOTS_TENANT_SCOPE=warn`. With the variable unset (which is strict, and `deploy/shared/env/*.example` set it nowhere, while `docs/operations/tenancy.md` requires strict) it exits with `TenantScopeMissingError: No tenant scope is active at withTransaction`, thrown by `runHeartbeatFireQueueSplitMigration(pool)` called without a scope at the top of `createApiQueueRuntime` (`services/alldots-api/src/queueRuntime.ts`, called from `serve.ts`); under `warn` the API logs `tenant_scope_missing`, then listens and answers `401` to an unauthenticated request. Agents and transcribe start under strict. This is not packaging and is not decided here; it must be its own source.

## Decision

Option C. sp-62b97861 delivered what it claimed (the migration entry and its six sibling data-package CLIs resolve natively) and nothing more. The follow-up's status "unresolved operational prerequisite" stays correct, but its premise is narrower than written: the unresolved part is now known exactly, namely the four compiled services (`alldots-api`, `alldots-agents`, `alldots-ai-gateway`, `alldots-transcribe`), caused by eight workspace roots that still select source. No text edit of the follow-up or of F5 is made by this record: the new source owns the packaging repair and updates both with its own native evidence, so the follow-up is closed by evidence and not by rewording. The separate `alldots-api` strict-scope startup defect is reported for its own source and is not hidden inside the packaging one.
