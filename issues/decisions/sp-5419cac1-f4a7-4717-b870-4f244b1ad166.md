# Decision: sp-5419cac1-f4a7-4717-b870-4f244b1ad166 (Run the edge-changed hooks before a user or agent edge write ends its value links)

## Question

The worker of chain e1-033-chokepoint reproduced the deadlock of the source (Task step 1, 12 tests, commit `a53af05ec`),
implemented the Task step 2 reorder (`90e5ce5fb`: `runRelationEdgeChangedHooks` before `breakValueLinksForRelationEdge` in
`createRelationWithClient`, `createRelationIfAbsentWithClient` and `deleteRelationWithClient`) and withdrew it (`46663be90`).
The reorder ends the reported cycle (a user removing the project edge of a transcript against the propagation of the
Event's project) in both orders and keeps the six `relation.set` cases that settled on the tip, but it opens a new
`40P01` between a user or agent edge write on `Transcripts.project` and the move of the transcript's Event to the Trash.
That schedule is not one the Task lists; the worker's stop rule fired on it. Decide a lock order that removes both
cycles, or narrow the Task. gh-1756 is blocked behind this source and gh-1702 starts after it is decided.

## Options considered

report and logs (`worker.json`, `e1-033-chokepoint/*.log`), the reproduction test and the candidate from the archived

The order `L_item`, `L_project`, `L_people`, `L_company` is followed by the propagation job, the engine's hook and the
release of a removed `event` edge, and the ordinary edge write on the unchanged tip breaks it (it takes `L_project` before
`L_item`: the reported cycle); the first design takes `L_company` before `L_project` (the new cycle with the trash, which
takes no `L_item` of a transcript and so cannot be ordered by the item row). It is not a total order of every path: the
challenge measured three paths of the tip that take value link rows against it and end with `40P01` against a writer that
follows it (listed under "What stays open"); this decision repairs the ordinary edge write only. The worker's deadlock detail agrees: the two backends wait for each
other on the `project` and `company` link rows (`re-tip-baseline-on-candidate-*.log`), and the added baseline failed on
the candidate in five runs.

Options:

- A. The Task as written (hooks before the break): rejected. It is the withdrawn candidate. The cycle with the trash is a
  true deadlock of a production schedule, not a limit that can be recorded away: a user removing a transcript's project
  while the Event is trashed would end with `40P01`, which no error mapping covers.
- B. Keep the first design and reorder the trash (take `L_company` before `L_project` in the item delete hooks): rejected.
  The release of a removed `event` edge takes `project`, `people`, then `company` under the item row, and the ADR of
  2026-11-10 records that order as a consequence. The trash would then take `company` first and the edge removal
  `project` first, which is the same cycle between those two. It would also change two delivered hooks of other sources
  (`valueLinkSourceDeleteHook` of #1656, the release of #1697) that this Task has no business with.
- C. A blocking item row lock before the edge write: rejected, as in the Context. It conflicts with a transaction that
  holds the definition advisory lock from an earlier insert of the same definition.
- D. A blocking item row lock inside the link break for every relation: rejected, as in the Context. For a relation
  that is the target of a rule and no rule's via relation (`Transcripts.company`, `Files.companies`) the lock would come
  after the definition lock and open a cycle with `setRelationWithClient` that does not exist today; the baseline cases
  on `company` (the edge write does not wait for the held transcript row) would change.
- E. The same lock, taken only for a relation that is a link rule's via relation, right after the edge row is written or
  deleted and before anything locks a value link row, for a user or agent write only: chosen. The item row it locks is
  exactly the one the engine's hook locks for this edge after the edge row (`linkRuleEdgeHook.ts:62`), so relative to the
  definition advisory lock, the edge rows and every lock the transaction held before it takes the same position the engine
  already takes; for a relation that is no rule's via relation it takes nothing. The Context's two objections to a
  blocking lock do not apply: the lock is not before the edge write (C) and not for non-via relations (D). It restores
  the total order above for the one path that broke it. The earlier Context decision "no lock is added" is replaced by this
  one; the prohibition in the Context concerned the two places named there.
- F. Take that lock by a call from `relationOps.ts` into the link engine: rejected. `linkRuleEdgeHook.ts` imports
  `linkPropagation.ts`, which imports `relationOps.ts`; a direct import closes a cycle that the dependency rule
  `no-choke-point-rollup-cycle` forbids, and the registry ADR of 2026-09-30 says a domain's side effect on the generic
  write path registers a hook and does not add an import. The call goes through a new registry of hooks, so the hook kind
  is part of the change. A call of only `linkRuleCatalog.ts` from `relationOps.ts` would avoid the cycle but makes the
  generic write path import the link domain by name, which that ADR replaced.
- G. A nonblocking reservation with a busy refusal for user and agent writes: rejected, as in the Task's Out of scope; it
  refuses requests that wait today.
- H. Narrow the Task to what can be done without a new deadlock, that is, drop the repair: rejected. The defect is
  reproduced with `40P01` on the tip (schedule A) and the repair needs one lock and one hook kind. A narrower Task would
  leave gh-1756 and the transcript rule exposed.

What the prototype shows for the schedules in the order the lock now gives: in schedule A the user's write waits for the
row before it holds any link row, so the propagation that gets the row first meets no link row of the user and is refused
with `value_link_busy` by the nonblocking admission of its own relation write (`withValueLinkRelationAdmission`; the measured
outcome is `["busy", "committed"]`, the exact statement that refuses is not established here), and a user who waits first commits before the propagation looks at the link, which is
then broken. In schedule C the user takes the item row and `project` before `company`, as the trash takes `project` before
`company`, so whichever of them gets `project` first, the other waits for it and nothing waits in a loop.

An ADR is needed. It states a lock order that future code must follow, adds a kind of hook to the registry of an accepted
ADR and withdraws the Task's own design for a measured reason. It supersedes and narrows nothing, so no accepted ADR body
is edited: it is standalone and references the three ADRs the Task names, the ADR of 2026-11-10 (the order of the release
hooks it relies on) and the registry ADR (the new hook kind). The name in Task step 4 changes because the decision
changed.

## Decision

Option E. The order of the rows of one item is: the item row, then its `project`, `people` and `company` value link rows.
Every path already follows it except the ordinary edge write of a user or agent. That write takes the item rows that the
engine's hook would lock for the written edge first, right after the edge row is written or deleted and before the
approval check or the link break, through a new registry of before-link-break hooks that `linkRuleEdgeLockHook` joins.
Nothing else of the write path moves: the edge-changed hooks, the link break, the rollup enqueue and the announcement
keep their order, a relation that is no rule's via relation and every `system` write take no new lock, and the engine,
the trash hooks, the Threads merge and the admission protocol do not change. The Task is rewritten accordingly (steps 1
to 4, Touches, Scope and one acceptance criterion); the first design is recorded as withdrawn with its evidence.
