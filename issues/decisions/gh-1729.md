# Decision: gh-1729 (List Semp threads with kind filter, preview and pending approval)

## Question

Chain `e1-020-semprec-api` (gh-1729, then gh-1737) of the parallel backend
program was implemented, reviewed, fixed once and rechecked once under
`docs/adr/2026-11-10-parallel-backend-delivery-through-a-serialized-merge-queue.md`.
The focused recheck holds the chain on one finding against gh-1729: Task step 2
defines the `subject` of an item thread as `{ inboxItemId, proposalId, label,
proposalTarget: { entityKind, databaseKey }, capturedAt, exists }` "taken from
the thread's stored subject snapshot", Scope names `subject` as in scope, and
the implementation returns `{ inboxItemId, proposalId, exists }`. A second
finding on gh-1729, of low severity, was deferred by the fixer and not judged
by the recheck: the text preview is built from the first 1000 code points of
the stored message, so a long message with much Markdown syntax in that window
gets fewer than 140 code points and still an ellipsis. Decide both findings and
what happens to the chain.

## Options considered

Subject fields `label`, `proposalTarget` and `capturedAt`. The Task takes all
three from a stored subject snapshot, and that snapshot does not exist.
`semp_threads` has only `subject_inbox_item_id` and `subject_proposal_id`
(migration `0087_semp_threads_and_messages.sql`; the only later migration that
names the table, `0096`, adds a foreign key from `agent_runs`). gh-1367
(closed) specifies exactly those two columns. The only writer of the subject
is the `INSERT` in `sendSempMessage`
(`backend/packages/data/src/sempThreads/sempThreadsStore.ts`), and it writes
the two ids. Beyond that the three fields differ: the caption and the proposal
target have no defined source of any kind, while the capture time has a
defined live source and is weighed on its own below.

- Store the snapshot inside gh-1729: rejected. It needs a migration, a write
  in the send path of gh-1620 and a definition of the stored values, all
  outside Touches.
- A new prerequisite source that stores the snapshot when an item thread is
  created and lands before this chain: rejected. Its content cannot be written
  from the repository. The epic gh-1304 lists the premise as an open question
  for the product owner: "`subject.label` (card caption such as "Soubor +
  úkol"): assumed to be stored in the thread's subject snapshot by #1367;
  confirm the source of the label". Nothing in the code produces such a
  caption: `inbox/inboxCardKind.ts` derives one kind per card and describes it
  as "derived on read and stored nowhere". "The" proposal of a thread is not
  defined either:
  `docs/adr/2026-11-06-inbox-thread-sends-reserve-current-proposals.md` calls
  the stored `subject_proposal_id` a hint and not a current association proof,
  a thread may exist before a card does (gh-1367: the proposal id "stays NULL
  until the capture has a proposal card"), and
  `docs/adr/2026-10-25-thread-may-split-an-inbox-source.md` allows several
  cards for one Inbox source. Choosing among these is a product decision that
  the epic leaves to the product owner, and
  `docs/adr/2026-09-10-no-speculative-generality-beyond-issue-scope.md` makes a
  capability that nobody has specified wait for its own issue. Holding the
  chain for it would also hold gh-1737 and, behind the chain, gh-1766,
  gh-1736, gh-1783 and gh-1854, none of which needs the fields.
- Derive `label` and `proposalTarget` at request time from the current card:
  rejected. The rules named above are missing for a live value as much as for
  a stored one, and under
  `docs/adr/2026-09-11-additive-only-rest-contract-no-url-versioning.md` a
  field that has shipped is never removed or repurposed, so a guessed meaning
  would be permanent.
- Return `capturedAt` live, in one more fix round: rejected, and not because
  no source exists. The repository defines the capture instant of an Inbox
  item: its `date` and `time` properties, which the client supplies on capture
  and the server stores as given, read in the system time zone, and null when
  either is missing or unparseable (`inboxCaptureInstant` in
  `backend/packages/data/src/inbox/proposalActions.ts`; the `inboxCapture`
  basis of `docs/adr/2026-10-31-item-origin-capture-time-provenance.md`). The
  list query already joins the live Inbox item, so the value would be cheap to
  return. It is not delivered here for four reasons.
  1. It is not the value the Task describes. The Task puts a stored snapshot
     next to a live `exists` flag: values that still describe the subject when
     the Inbox item is gone. A live capture time is null exactly when `exists`
     is false, and it follows later edits of `date` and `time`, which are
     user-owned properties.
  2. A shipped field keeps its meaning (the additive-only contract above). If
     the owner decides for a stored snapshot, which is what the epic assumes,
     the capture time belongs in it, and a `capturedAt` already shipped as a
     live value could not take that meaning. Shipping it now would settle part
     of the open question as a side effect.
  3. gh-1543 states the subject of the list and of the detail as one shape. A
     field on the list alone would split them, and the detail store and the
     private helper are both outside Touches.
  4. Nothing needs the value on the row. No acceptance criterion and no
     dependent names it, and the user-visible behaviour the epic states for
     the chat list is a title, a preview and the approval indicator. A client
     that wants the time holds `inboxItemId` and reads `date` and `time` of
     that item (`GET /api/items/:id`), which are the same two values.
- Minimal spec correction (DEFECT): chosen. Task step 2 takes three values
  from a snapshot that does not exist, and it contradicts a delivered issue:
  gh-1543 (closed, completed) defines the subject of the thread detail as
  `{ inboxItemId, proposalId }` and calls it "the same shape the thread list
  uses in #1729". The corrected subject is that shape plus `exists`, which is
  what the chain implements and tests. Out of scope names the three fields
  with the reason for each, including the live source of the capture time.
  The narrowed object can be extended later without breaking a client.

Preview window:

- Read the whole message when the window shows 140 code points or fewer (the
  fix the reviewer proposed): rejected. `stripMarkdown`
  (`shared/block-model/src/markdown.ts`) parses its whole input, and the
  inline parser scans the rest of the line again for every `[` that has no
  closing bracket (`findLinkTextEnd`) and for every emphasis marker without a
  closer (`findDelimiter`). The fixer measured 37 s for a run of 200 000 `[`.
  A message text has no cap of its own below the 1 MiB request body, a page
  has up to 100 rows and the API process serves every tenant, so one stored
  message could block it on every list request that shows the thread. The
  Task loads `io-hardening`, which requires a size cap on what a request
  processes, and a cap would be needed with a linear parser as well.
- Leave the deviation unrecorded and file a follow-up: rejected. The fourth
  acceptance criterion would stay untrue for the affected messages while the
  suite pins the other behaviour, and a source is not completed against a
  criterion it does not meet.
- Record the bound in the Task and in the criterion (DEFECT): chosen. The cut
  to 140 code points stays. The Task now says that the text preview is built
  from the first 1000 code points of the stored text, and what follows from
  that. Both consequences are rare and cosmetic. A message longer than 1000
  stored code points whose first 1000 show 140 visible code points or fewer,
  in practice a very long link target, gets a shorter preview that ends in an
  ellipsis; the suite pins this case. A Markdown construct that the window
  cuts off before it closes is left as written by the parser: for a link whose
  target runs past code point 1000, `parseDestination` finds no closing
  parenthesis and the `[` stays text, so the preview can show raw syntax and
  the start of the URL. This second case was read in the parser only; no test
  pins it.

Checks, all read-only. No build and no test was run for this decision,
because a full integration run was in progress; test results are those of the
fixer's logs, as the recheck read them. The decision was checked on
integration tip `dfe0e25d8` (chain tip `420277b26`, merge base `581923410`):
`issues/items/gh-1729.md` is unchanged since `745aea3f6`, its approval hash
equals the member hash in `issues/batches/backend/manifest.json`, and the four
old lines below are each present once. On the chain tip `SempThreadSubject`
and `mapSempThreadSubject`
(`backend/packages/data/src/semp/sempThreadsListStore.ts`) return
`{ inboxItemId, proposalId, exists }`, and the row schema of
`backend/services/semprec-api/src/__tests__/sempThreadsList.test.ts` is a
strict object of exactly those keys. `getSempThread`
(`sempThreads/sempThreadsStore.ts`) returns `{ inboxItemId, proposalId }` for
the detail. No file under `web/` or `mobile/` reads `/api/semp/threads` or the
three fields. The dependents gh-1737, gh-1766, gh-1736, gh-1783 and gh-1854
were read: none names the three fields; gh-1766 needs only the shared title
resolver, which exists as `loadSempThreadTitleResolver`. Blocker gh-1683 is
closed with a handover. Blocker gh-1725, a shared-file ordering edge, is open
and has no handover. No acceptance criterion of gh-1729 names the three
fields. No ADR body and no protected path is touched.

## Decision

DEFECT, two corrections of gh-1729 and no code change. The list subject is
`{ inboxItemId, proposalId, exists }`. The caption and the proposal target
are out of scope until their source is decided; the capture time is out of
scope because the row would only repeat, for as long as the Inbox item
exists, the `date` and `time` that the item itself carries. The text preview
is built from the first 1000 code points of the stored message. The chain
lands as implemented at `420277b26` once the corrected record is approved
again; gh-1737 is unchanged and lands with it. The landing gate of the program
still applies: gh-1725 must be completed on the integration tip first.

## What stays open

- The product owner decides whether an item thread row carries a card caption
  and a proposal target, and where each comes from (the open question on
  `subject.label` in the epic gh-1304). This decision does not answer it.
  Until it is answered and a new source delivers it, the list and the detail
  return only the ids and `exists`, and a client that wants a caption reads
  the Inbox item and its card itself.
- The capture time is left off the row by this decision, not by a missing
  source. The owner may overrule it: a live `capturedAt` (the Inbox item's
  `date` and `time`, null when the item is gone) on the list and the detail is
  a small source of its own. If the owner wants a value that outlives the
  Inbox item, it belongs to the snapshot question above. Any of the three
  fields can be added to `mapSempThreadSubject` for both responses without
  changing the delivered ones.
- Test gap, not scheduled. The corrected Task names `subject_proposal_id`, and
  no list test reads a `proposalId` that is not null: every expectation of
  `sempThreadsList.test.ts` has `proposalId: null`, because the fixture sends
  `subject: { inboxItemId }` only. The mapper passes the column through
  (`proposalId: row.subject_proposal_id`), so the code is right by reading and
  the chain is not held for it, but a mapper that always returned null would
  pass the suite. The missing case: create an item thread through
  `POST /api/semp/threads` with a `proposalId` of a current card of the Inbox
  item and expect that id in `subject.proposalId` of the list row. No open
  source touches the subject, so the controller decides whether to schedule it
  as a test-only source; the acceptance receipt of gh-1729 carries this gap.
- The cut-off Markdown case of the preview (syntax left as written when the
  1000 code points end inside a construct) is stated in the Task and pinned by
  no test.
- `pendingApproval.sourceKind` returns `genericOperation` or `mcpInvoke`, the
  rule of `safeSummary.kind` in the approval queue. The epic lists its value
  set as an open question for the product owner as well; no reviewer reported
  it and it is not decided here.
- The Markdown parser of `shared/block-model/src/markdown.ts` takes time that
  grows with the square of the length of a line with unmatched `[` or emphasis
  markers. This exists on the integration tip independently of this chain and
  is reachable from authenticated write routes that parse Markdown values of
  up to the 1 MiB request body (`assertMarkdownValues` in
  `chokePoint/itemWrites.ts`, `docs/pageMarkdown.ts`,
  `inbox/proposalEnvelopeValidation.ts`), in a process that serves every
  tenant. The shape was read in the code; the timing is the fixer's
  measurement and was not repeated. This chain bounds its own use to 1000 code
  points per row. No source was written here, because the remedy is a design
  choice in a shared package that the browser also loads (a bound on the
  scanning can change how some lines with unmatched markers parse; a size cap
  changes which values a write accepts) and should be made by an agent that
  can run the parser. The controller adds this to "Open items" of
  `issues/batches/backend/CONTROLLER.md` before the next publication and plans
  the source.
