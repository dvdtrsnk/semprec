# Decision: gh-1986 (Remember an explicit no-event decision for a recording)

## Question

The worker of chain e1-218-transcription refused gh-1986 at preflight and committed nothing. The Context and Task
say that `recording_requests.event_decision` holds `none` or null, that null means the user did not decide, and that
the confirm of the transcription card writes `event_decision = 'none'` for an explicit "no event" choice and keeps null
otherwise. The delivered gh-1574 created the column as `event_decision text NOT NULL DEFAULT 'none'` with no CHECK
constraint (migration `0137_recording_requests.sql`) and wrote in its own Decisions "`event_decision` is created with
default `'none'` and no CHECK constraint; #1986 defines further values". A row written without a choice therefore holds
`'none'` already, so gh-1986 as written either makes the match step skip the "recording without an event" card for every
recording or needs a migration that makes the column nullable. About a dozen later sources depend on its chain.

## Options considered

Read for this decision, from the integration tip `fb6604b3a`: gh-1986, gh-1574 and its handover, gh-1978,
`issues/decisions/gh-1702.md` and `gh-1756.md` (format), the worker's preflight record, the db-migrations,
canonical-keys and adr-conventions skills, `docs/adr/2026-11-05-recording-intake-coordinates-files-and-transcription.md`,
`docs/adr/2026-11-14-inbox-recording-cards-confirm-into-recording-intake.md`, and the code of `recordingIntake.ts`,
`recordingCardConfirm.ts`, `recordingCardEnvelope.ts`, `recordingCardValidation.ts`, `proposalRetention.ts`,
`transcriptEventMatch.ts`, `eventRecommendationStep.ts`, `transcriptionActions.ts` and
`undoConfirmedProposal.ts`. Nothing was built or run for this decision.

What the column means today, established from the code:

- Only `0137_recording_requests.sql` mentions `event_decision`. No later migration alters it, no TypeScript reads or
  writes it, and no test names it. `recordRecordingIntake` (`recordingIntake.ts`, the only writer of the table) inserts
  the row without the column, so every row holds the default `'none'`; `readRecordingRequest` does not select it.
  Today `'none'` is the default that nobody decided, not a decision. gh-1574 itself reserves the further values for
  this issue.
- `recordRecordingIntake` keeps the first accepted values of a request (`ON CONFLICT DO NOTHING`), and its callers are
  the upload endpoint and `confirmRecordingCard` of the card of gh-1978.
- The match step has two callers of the shared read half: `matchTranscriptToEvent` and
  `readEventRecommendationContext`. The caller of the match is `runEventMatch` in
  `alldots-transcribe/src/eventRecommendationStep.ts`, not `transcriptionTask.ts`; it already returns for any string
  outcome, so a new outcome needs no change there. `readEventRecommendationContext` is the snapshot that decides
  whether a paid recommendation call is due, so a check only in `matchTranscriptToEvent` would still pay for a call
  whose result is thrown away.
- A second finding that the worker did not report: the card of gh-1978 has no representation of an explicit "no event".
  Its envelope `properties` hold an optional `eventId`, and the accepted ADR says a cleared parameter is `null`, which
  means the same as an absent one. gh-1978 says "Choosing 'no Event' simply leaves the Event unset; remembering that
  explicit decision ... is #1986". Task step 1 ("the explicit 'no event' value") therefore presupposes a value that
  does not exist, and `RECORDING_PROPERTY_KEYS` (`recordingCardEnvelope.ts`, used by the revise retention in
  `proposalRetention.ts`) and the strict schema reject any new key until it is added.
- The recording request store of Task step 1 and the Touches ("`recordingRequestsStore.ts`") do not exist; the store is
  `transcription/recordingIntake.ts`. The confirm is `confirmRecordingCard` in `inbox/recordingCardConfirm.ts`,
  not `proposalActions.ts`, which only calls it. The grant is present: `0137` grants `SELECT, INSERT, UPDATE, DELETE`
  to `alldots_side`, and the transcription process already reads the table in its prepare and create steps.

Options:

- A. Keep the column, its default and its constraint as gh-1574 delivered them, and define a different stored value
  for the explicit decision: chosen. `'none'` stays the default meaning "not decided" (what every row holds today and
  what gh-1574 specified), the explicit decision is `noEvent` (the English camelCase key of `canonical-keys`), and the
  match step honours `noEvent` only. No DDL at all, nothing to roll back, no row to rewrite, no contradiction with the
  delivered migration, handover or ADR of gh-1574. The cost is that the name `none` reads as the opposite of its
  meaning; the ADR of Task step 6 and the column's value contract in the code comments record it, and the older
  summary lines of the epics (gh-1315 and gh-1319 still say `none`) are history that this record supersedes.
- B. A migration that makes the column nullable with default NULL and resets the existing rows. Rejected. It is
  allowed by `db-migrations` as a relaxed constraint, but it rewrites the contract of a delivered source (gh-1574's
  Task fixes `NOT NULL DEFAULT 'none'`), it needs a data reset of every row, which the skill says belongs in a separate
  data migration, and gh-1986 allows a migration only for a grant. It also gains nothing over A: a nullable column and
  a value are two encodings of the same bit, and the card still needs a new envelope property either way.
- C. A new boolean column `no_event` next to `event_decision`. Rejected: an additive migration that is not needed,
  and it leaves the column gh-1574 reserved for this purpose unused.
- D. A Transcripts property or a card-side record. Rejected: gh-1986 decides that the decision is stored only in the
  recording request, and a Transcripts property would add a schema and a writer in another owner's database.
- E. Make the match step treat `'none'` as the decision and change the confirm to write another value for "undecided".
  Rejected: it defeats gh-1574's default, every upload through `/api/recordings` would then be a request that suppresses
  the card unless it also wrote a value, and that changes the upload endpoint's delivered behaviour.

For the explicit choice on the card, the options were a new boolean envelope property `noEvent` (chosen), reading a
present `eventId: null` as the choice (rejected: the accepted ADR of the card says a cleared parameter means the same as
an absent one, so the producer's envelope and a cleared Event would be indistinguishable from a choice, and changing
that is an edit of an accepted decision), and a sentinel string in `eventId` (rejected: `eventId` is a UUID and the
validation of a live Events item depends on it).

For where the write happens, the options were passing the value through `recordRecordingIntake`'s insert (rejected:
`ON CONFLICT DO NOTHING` would silently drop the user's choice when the Files item already has a request, for example
from an earlier upload, which breaks the acceptance criterion) and a small setter that the confirm calls after the
intake (chosen: this is also what the Task says, "a small store function next to the one #1574 introduces"). The
confirm holds the Files row lock by then (`recordRecordingIntake` locks it `FOR UPDATE NOWAIT`), so the UPDATE is
serialized with every other writer of the request, and the decision commits with the request and the jobs, before the
worker can run the match. A confirm without the choice writes nothing and never clears a stored decision (the request
keeps its first accepted values, as the ADR of the card says for the other columns).

The decision needs an ADR: it adds a value contract on a column that another process reads, a new property of the
envelope that an accepted ADR lists as exact, and a second function that writes `recording_requests` while the intake
ADR names `recordRecordingIntake` the only writer; the card ADR says "a later change of the recording request's writers
needs its own decision". Task step 6 adds it; it supersedes nothing and narrows nothing, so no accepted ADR body is
edited.

## Decision

Option A. The column, its default and its constraint stay as gh-1574 delivered them: `'none'` is the default and means
the user did not decide. The explicit "no event" decision is the stored value `noEvent`. The card's envelope gets a
boolean property `noEvent` (`true` is the choice, refused together with an `eventId`); `confirmRecordingCard` calls a new
`setRecordingEventDecision` in `recordingIntake.ts` after the intake when it is `true`; the shared read half of the
match step (`readOpenMatch`) calls a new `readRecordingEventDecision` first and returns the new outcome `noEventChosen`,
so `matchTranscriptToEvent` writes nothing and `readEventRecommendationContext` makes no paid call. No migration.

## Consequence

- gh-1986 can be implemented on the integration tip: its Task needs no change to a delivered contract, and the
  dependants of its chain no longer wait for a column migration. The touched files are
  `transcription/transcriptEventMatch.ts`, `transcription/recordingIntake.ts`, `inbox/recordingCardEnvelope.ts`,
  `inbox/recordingCardConfirm.ts`, the three test files of the Touches and the new ADR.
- Neither `eventRecommendationStep.ts` nor `transcriptionTask.ts` changes; the first already ends the step for every
  string outcome. `readRecordingRequest` keeps its result shape, so the `toEqual` assertions of
  `recordingIntake.test.ts` stay valid. The new functions are not exported from the package barrel, so
  `publicSurface.test.ts` is not touched.
- `matchTranscriptToEvent` with `noEvent` returns before the `alreadyLinked` check, so a transcript that has a live
  Event edge and a stored `noEvent` reports `noEventChosen` instead of `alreadyLinked`; both write nothing.
- A request that already exists keeps its Event and first values; a later confirm that sets `noEvent` stores the
  decision on it, and a later confirm that does not never clears it. The edge written for an Event named by an earlier
  upload stays.
