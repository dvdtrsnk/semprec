# Decision: approve catching up after every IMAP IDLE reconnect and ending a connection that stopped idling

- Question: May the proposal (sp-9119ea92-f147-4597-8df1-2dfa2baf1615) be approved as specified against the branch tip?
- Owner instruction (David, 2026-11-22): fix the findings of the end-to-end test campaign against Purelymail on follow-up branches, each finding or tight cluster as a repository issue under the internet-accounts epic; this one covers F33 (a message delivered seconds after a send was not synced until an unrelated trigger three minutes later, with no IDLE record in the log).
- Options considered: a catch-up sync only on reconnects and not on the first session after `start()` (rejected: `start()` enqueues before discovery, so a delivery during discovery has the same gap, and the enqueue coalesces by job key); attaching the listeners earlier without a catch-up (rejected: a fresh connection never signals a message that was already there at SELECT); re-issuing IDLE on the same connection when it ended (rejected: a server that keeps ending IDLE would loop without backoff; ending the session reuses the reconnect backoff and the catch-up); a shorter socket timeout (rejected: it would not distinguish a quiet IDLE from a stopped one).
- Decision: approve the specification as written.
- Exact spec change: none.
