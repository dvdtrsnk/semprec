# Decision: the backend assumes the first version until the first production deployment

- Question: May the proposal (sp-bf1af999-3e92-4eec-9f5a-308d80753973) be approved, given that the repository still carries schema-upgrade rules, a seed reconcile of already seeded tenants, production cutover tooling and compatibility code for older data shapes?
- Owner decision (David, 2026-11-21), verbatim: "Alldots has never been released. Until the owner's first real production deployment, the backend must assume it is the very first version: NO schema versioning, NO migrations beyond the single baseline, NO upgrade/carry/reconcile paths for existing databases, NO compatibility code for older data shapes. The dev VPS database is simply wiped and recreated on every deploy. When the owner first deploys for real, the project will switch to proper production rules (that switch is a future, separate change — do not implement it, but say in the docs that it will happen at the first production deployment)."
- Options considered: keeping the "after the first production release" rules in the documents as dormant guidance next to the baseline rule, or stating only the current rule and naming the first production deployment as the point where production rules are introduced; keeping the expand/contract and ordinal checks as dormant guards, or removing them with the machinery they police; adding a database reset to `deploy.sh`, or leaving the wipe to the operator as the owner decided.
- Decision: state only the current rule; remove the reconcile, the cutover tooling, the compatibility and ordinal checks and upgrade-only code; `runMigrations` keeps applying the baseline to an empty database; no reset step in `deploy.sh`. The spec is sound against the branch tip; approved.
- Exact spec change: none.
