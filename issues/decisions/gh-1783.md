# Decision: gh-1783 (Index Semp messages for Czech full-text search)

## Question

The implementation proposal gh-1783 (`[semp-threads 19/19]`: a stored
`search_vector` on `semp_messages`, maintained by every writer of message
text, a batched reindex helper, and a message-text rule in the `q` filter of
the thread list) is open without `spec:approved`. Approve it, or make the
minimal correction that makes it approvable.

## Options considered

- Approve unchanged (SOUND): rejected, for four reasons.
  1. Task item 1 put a one-time `UPDATE` that fills the vector of existing
     messages into the same migration as the DDL. The accepted
     `docs/adr/2026-09-10-expand-contract-forward-only-migrations.md` says
     backfills are separate from DDL, idempotent and batched, and the
     `db-migrations` skill (its record) says structural and data migrations
     stay in separate files and a deploy never blocks on a backfill; the
     `2026-09-10-app-code-post-migration-steps` ADR adds that a row-by-row
     SQL backfill belongs in a batched data step, not in the deploy. The
     implementation would have been blocked in review.
  2. Blocked-by named only #1589 and #1737, but Task item 2 hooks the
     message inserts, which #1620 delivers
     (`backend/packages/data/src/sempThreads/sempThreadsStore.ts`, write
     functions), and the assistant-text update, which #1727 delivers (the
     batch's later issues #1860, #1885, #1907, #1926 and #1930 all place it
     in `semp/sempMessagesStore.ts`, "extending the store of #1727"). Neither
     is reachable through #1737 (its chain is #1729, #1683, #1725), so the
     issue could have been dispatched before the code it edits exists. The
     Task also pointed the implementer at "the PRs of #1367 and #1727"; the
     PR of #1367 created the tables only (migration 0087) and no store.
  3. The tip already has a third writer of non-system message text that
     Touches omitted: `finishTickRunWithMessage` in
     `backend/packages/data/src/semp/sempTickThreadStore.ts` inserts an
     `assistant` message with `text` for a tick thread (d1e58380). Tick
     threads are listed and searched (`kind=tick` in #1729 and #1737), so a
     reply left without a vector would never be found.
  4. Task item 3 defined `reindexSempMessageSearch(client, { limit })` over
     "messages that have text and no vector" and at the same time as the
     helper operators run after the Hunspell activation to replace old
     lemmas; messages that already carry a vector would never be selected,
     so the helper could not do the job it was defined for. Once the
     migration no longer fills existing rows the helper also has to serve the
     one-time fill, which needs a cursor to make progress in batches.
  5. The acceptance criterion "with Hunspell active" was not testable with a
     harness the Task named: CI has no Hunspell dictionary, and the only
     harness is the module-private `withFreshDatabase` and `installAssets`
     of `backend/packages/data/src/__tests__/czechHunspellSearch.test.ts`
     with the `fixtures/czech-hunspell/cs_cz.dict` fixture (which does list
     "faktura").
- Minimal spec correction (DEFECT): chosen. Migration becomes DDL only; the
  batched helper takes the shape of `enqueueItemSearchBackfill`'s options
  from #1397 (`afterMessageId?`, `onlyMissing`) with a returned cursor, and
  covers both the one-time fill and the Hunspell recompute; Blocked-by gains
  #1620 and #1727; Task item 2 and Touches name the three writers; Task
  item 5 names the Hunspell harness. No new behaviour, test or file beyond
  what the Task already required.
- A new ADR (ADR CONFLICT): rejected. The spec does not need a rule an
  accepted ADR forbids; it needed to follow the accepted one.
- Scheduling the fill as a queued core task like `itemSearchBackfill`
  (#1397) or from `runMigrationsCli.ts`: rejected. The spec deliberately
  leaves scheduling out of scope ("it is not scheduled here", Out of scope:
  scheduling after the Hunspell activation), the feature sits behind a
  product decision, and a queued task would add a task name, tenancy,
  worker registration and a deploy hook the Task never asked for.

Checks run on the integration tip (27c02eca): Blocked-by #1589, #1620,
#1727 and #1737 are open and `spec:approved`/`agent:ready`, so the issue

vector; `search/itemSearchIndexer.ts` owns `SEARCH_VECTOR_SQL`
(`to_tsvector('czech', $3)`) and `mail/search.ts` still has its own
expression; `backend/packages/data/src/semp/` holds
`sempTickThreadStore.ts`, `sempProblemsStore.ts`, `sempProblemsPrune.ts`,
`guidanceProblemWriter.ts`, `sourceProblemKeys.ts` and `__tests__/`;
`backend/packages/data/src/sempThreads/` and `semp/sempThreadsListStore.ts`

barrel. No `review-rules/` line mentions search vectors or backfills; no
`docs/adr/` body is edited. No protected path is touched; Touches names
none, so `queue` accepted it.

## Decision

DEFECT: corrected the migration to DDL only, gave the reindex helper a
cursor and an `onlyMissing` switch, added #1620 and #1727 to Blocked-by,
named the three writers of message text in Task item 2 and Touches, and
named the Hunspell test harness in Task item 5. Approved and queued.
