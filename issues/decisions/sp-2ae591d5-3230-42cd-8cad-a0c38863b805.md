# Decision: approving the decoded mail refusals in the mobile mail screens

- Question: May the proposal (sp-2ae591d5-3230-42cd-8cad-a0c38863b805) be approved, and how does a refusal code reach the screens: in the failure value, through an exception, or as content?
- Options considered: a reason field on `RepositoryResult.Failure` (changes the core result every port shares), a third `RepositoryResult` case (breaks every exhaustive `when` in the shared layer), or a mail-only `MailOutcome` answered as content on the nine mail writes that can be refused, as `MailConnectOutcome` already is for the password connect; on Apple, a refusal inside `FailureKind` or a separate optional field next to it.
- Decision: `MailOutcome` as content on the nine writes, one code table and one moved error-code decoder in the data layer, an exported `MailRefusalReason` with separate optional state fields beside the existing failures, and one `mail.refusal.*` copy key per case on Apple. Android has no mail screens and is out of scope. The spec is sound against the branch tip; approved.
