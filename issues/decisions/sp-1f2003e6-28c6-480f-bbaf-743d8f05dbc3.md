# Decision: approving the atomic, idempotent creation of an event in a chosen calendar

- Question: May the proposal (sp-1f2003e6-28c6-480f-bbaf-743d8f05dbc3) be approved, and how are three open points settled: where the idempotency key lives, how a refused create is reported, and whether moving an existing event to another calendar needs a change?
- Options considered: for the key, the exported `NewItemState` (a Swift mapping change for a value no screen renders) or a private value of the shared ViewModel handed to the domain draft; for the refusal, reading the server's error code in the data layer, a new `FailureKind` (an exported enum every consumer renders), or a domain outcome that tells a form the rules refuse from a refusal by the server; for the move, a delete-then-add of the edge or the existing single-valued replace route.
- Decision: the key is kept in `NewCalendarItemViewModel` and carried by `NewCalendarItem.submissionKey`; it is reused only for the same form submitted again, because the server replays a key without reading the body. `CreateCalendarItem` answers `NewCalendarItemOutcome`, so the form message stays for the rules' refusals and every server refusal is the generic unexpected failure. The only calendar move in the app is the generic item picker, which already uses `PUT /api/items/:id/relations/:propertyKey` with `targetItemId` (`relation.set`, one transaction); nothing changes there. No backend change. The spec is sound against the integration tip; approved.
