# Decision: approve connecting a password mailbox with one IMAP login and concurrent verifications

- Question: May the proposal (sp-10221c41-bd37-4331-8bc0-538033a580ae) be approved as specified against the branch tip?
- Owner instruction (David, 2026-11-21): on the dev VPS `POST /api/mail/mailboxes` for a Purelymail password account takes 6.5 s (3.0–3.5 s before the connect-time folder discovery); make the connect as fast as possible without weakening verification: reuse the verification IMAP connection for the folder LIST, run IMAP+folders, SMTP and CalDAV concurrently with the existing timeouts, close everything on every failure path, keep network I/O out of transactions; review `PUT /api/mail/mailboxes/:id/password` the same way; prove it with a latency test against the fake servers; track it as a repository issue under the internet-accounts epic.
- Options considered: keeping the second connection and only running it concurrently with SMTP (rejected: still two TLS connects and logins against the same server); listing the folders with STATUS as the sync pass does (rejected: the connect needs only path and special-use, and a STATUS per folder costs a round trip each); handing the verified imapflow client to the route (rejected: the verification owns its sockets and their close accounting; the client would escape it); stopping the SMTP verification once IMAP refused (rejected: it would need a cancellation path through nodemailer for at most one saved round trip on a refusal).
- Decision: approve the specification as written; the OAuth connects and the deadlines stay out of scope.
- Exact spec change: none.

## Specification correction (2026-11-21)

- Question: The approved Decisions name imapflow `list({ listOnly: true })` for the connect's LIST. imapflow 1.7.6 returns `listOnly` entries before it assigns `specialUse` (`lib/commands/list.js`), so the Drafts and Sent folders would never be recognised. May the listing use `list()` without a status query instead?
- Decision: yes, a minimal correction of a specification defect; it still sends no STATUS, and its special-use assignment is the sync pass's.
- Old line: sends `LIST` (imapflow `list({ listOnly: true })`: no LSUB, no STATUS; the connect needs only path and special-use)
- New line: sends `LIST` (imapflow `list()` without a status query: LIST and, on a server without extended LIST, LSUB, but no STATUS; the connect needs only path and special-use, and `listOnly` would return before imapflow assigns special-use)
