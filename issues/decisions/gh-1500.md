# gh-1500 decision

## Question

1. Which fingerprint represents an untyped source after #1606 without losing its inputs?
2. Does an existing recognized type or direct target bypass recognition after a source text edit?
3. What should a low-confidence card offer when fewer than two valid active types exist?

## Options considered

1. Write legacy `computeInboxFingerprint("", text)`: rejected because it drops #1606's date, time and attachment coverage. Use the recognized type in v2: rejected because recognition would change its own input identity. Keep v2 with an empty source type id and preserve legacy comparison: selected.
2. Reuse `recognizedTypeId` unconditionally: rejected because it contradicts recognition on every text change. Persist a separate text-only recognition version: unnecessary additional state. Recognize again whenever the existing fingerprint gate requires computation, with the existing empty-content and locked-card exceptions: selected.
3. Invent or duplicate types to reach two: rejected. Skip the clarification card: rejected because it hides the unresolved source. Offer the distinct valid types that exist, including an empty list, and explain the shortage: selected.

## Decision

1. DEFECT — preserve v2 with `typeId: ""` for untyped sources, all current #1606 inputs, and stored-v1 comparison; recognition output never enters the source fingerprint.
2. DEFECT — apply the source fingerprint gate before recognition; a changed fingerprint reruns recognition regardless of the previous recognized type or direct target, and stale writes compare source edge state rather than the model's result.
3. DEFECT — retain `needsClarification` with zero or one candidate when the valid active catalog has fewer than two types, no proposal, and a localized shortage reason; otherwise retain the two-to-four bound.

Both blockers gh-1434 and gh-1451 are closed in `issues.mjs list`; their local handovers were read, as was gh-1606's. The working tree code confirms that `readTickSnapshot` and the shared write check use v2, `computeInboxFingerprint` remains only for legacy comparison, `recognizedTypeId` is a card property, and `resolveRecognizedType` currently reads the source's `type` edge. `listActiveInboxTypes` filters active, undeleted items but does not guarantee a minimum catalog size or validate processing configuration; candidate validation must do that.

The corrections preserve the accepted single-writer ownership and agent-proposal ADRs (2026-09-10), the snapshot/call/staleness-check ADR (2026-09-10), and the primary-card fingerprint rule in the thread-splitting ADR (2026-10-25). The proposal producer ADR (2026-09-23) was also inspected. No ADR mandates the legacy fingerprint or a minimum active catalog size. These are local specification defects, not an ADR conflict, an external precondition or a protected-path change. No Task code was implemented.

## Spec change

### Change 1

Old:

```text
Decision: the fingerprint of an untyped item stays `computeInboxFingerprint("", text)`; it never uses the recognized type's emoji, so recognizing does not change the fingerprint and cannot trigger a recomputation loop.
```

New:

```text
Decision: new fingerprints remain v2 (#1606). For an untyped source use `computeInboxFingerprintV2` with `typeId: ""` and the current source text, date, time, attachment hashes and transcribedText (still `""` on this tip); never include the recognized type or direct target. Preserve `isFingerprintCurrent` compatibility for stored v1 values, using `legacyEmoji: ""` and the source text for an untyped source. Recognition therefore cannot change its own fingerprint or trigger a recomputation loop; `fingerprint.ts` behavior is unchanged.
```

### Change 2

Old:

```text
Decision: at or above the threshold the tick computes the proposal for the best candidate exactly as for a typed item and stores `recognizedTypeId` (type-id candidates only; a direct target is remembered by the stored envelope's target database and needs no extra field). Below it the card is `needsClarification` with a localized `reason` and two to four `typeCandidates` `{ typeId, label, targetDatabaseKey }` taken from the ranked type-id candidates, padded with the first active types in list order when the model gave fewer than two.
```

New:

```text
Decision: at or above the threshold the tick computes the proposal for the best candidate exactly as for a typed item and stores `recognizedTypeId` (type-id candidates only; a direct target is remembered by the stored envelope's target database and needs no extra field). Below it the card is `needsClarification` with a localized `reason` and up to four distinct `typeCandidates` `{ typeId, label, targetDatabaseKey }` taken from the ranked valid type-id candidates, padded to two with unused valid active types in list order. If fewer than two valid active types exist, offer all that exist (zero or one), keep `needsClarification` with no proposal, and explain the shortage in the localized reason; never invent or duplicate types. Valid types belong to the tenant, are active and undeleted, and have a supported processing method and a valid target for that method.
```

### Change 3

Old:

```text
1. In `readTickSnapshot` replace the early `needsClarification` return for an untyped item with a recognition path: resolve the type as `type` edge, else the existing card's `recognizedTypeId`, else "recognize". When an existing, unlocked card already carries `recognizedTypeId` or a recognized direct target and the fingerprint is unchanged, return without a call. Add `recognition: true` and the active-type catalog (id, name, emoji, processing method, target) to the snapshot and to `ProposalComputationInput`.
```

New:

```text
1. In `readTickSnapshot` preserve the existing typed path when a valid `type` edge resolves. For an untyped item, honor the existing locked-card and fingerprint gates first: an unchanged fingerprint reuses the existing recognition result without a call. Otherwise enter recognition again, including after every text change and every change covered by v2; neither the existing card's `recognizedTypeId` nor its recognized direct target bypasses recognition after such a change. Preserve the no-text/no-content exception. Add `recognition: true` and the valid active-type catalog (id, name, emoji, processing method, target) to the snapshot and to `ProposalComputationInput` for this recognition path.
```

### Change 4

Old:

```text
3. In `inboxTickAction.ts` apply the threshold. Above: build the envelope as for a typed item (type-id candidate: the type's processing method and target; direct target: `entityKind: "database"` with that database's id), write the card with `recognizedTypeId` (when applicable), and clear `typeCandidates`. Below: write `needsClarification` with `typeCandidates`, `recognizedTypeId` null, no proposal and the localized reason of #1495 when that issue is present.
```

New:

```text
3. In `inboxTickAction.ts` apply the threshold. At or above: build the envelope as for a typed item (type-id candidate: the type's processing method and target; direct target: `entityKind: "database"` with that database's id), write the card with `recognizedTypeId` (when applicable), and clear `typeCandidates`. Below (including no valid candidates): write `needsClarification` with up to four distinct valid type candidates, padding to two from unused valid active types in catalog order; if only zero or one exists, offer that many and explain the shortage in the localized reason. Set `recognizedTypeId` null, no proposal and the localized reason of #1495 when that issue is present. Never invent types or use a direct target as a type candidate.
```

### Change 5

Old:

```text
4. Add `recognizedTypeId` and `typeCandidates` to the tick's `allowedSystemKeys`, and keep the staleness check (`writeTickResult`) comparing the same fingerprint and the same type resolution, so a later edit that does not change the fingerprint never turns a recognized card into `needsClarification`.
```

New:

```text
4. Add `recognizedTypeId` and `typeCandidates` to the tick's `allowedSystemKeys`. Keep the staleness check (`writeTickResult` and its shared source check) comparing the same v2 source fingerprint and source type-edge resolution captured before the call: an untyped snapshot must still have no type edge, and a typed snapshot must still resolve the same source type. Do not compare an untyped source with the newly recognized type or target as if it were a source edge. Store the source v2 fingerprint on the recognition result, including clarification cards, so an unrelated edit cannot change or repeatedly recompute it.
```

### Change 6

Old:

```text
5. Tests with a stubbed computation: an untyped item with confidence 0.9 produces a `proposed` card and the `type` edge stays absent; a later unrelated update of the item leaves the card unchanged; confidence 0.5 produces `needsClarification` with two to four candidates; an unknown or archived type id from the model is ignored; a model response with only one valid type gets padded; an item with no text and no content makes no call; a locked card is never recomputed; the tick never writes `Inbox.type`.
```

New:

```text
5. Tests with a stubbed computation: an untyped item with confidence 0.9 produces a `proposed` card and the `type` edge stays absent; a later unrelated update leaves the card unchanged; a text edit reruns recognition for both a prior recognized type and a prior direct target; changes to date, time or attachment hashes rerun recognition under v2 while stored v1 compatibility is preserved; setting the recognition result does not change the source fingerprint; a source edit or type-edge change during computation discards the stale result; confidence 0.5 produces `needsClarification` with two to four distinct candidates when at least two valid active types exist; an unknown or archived type id is ignored; one valid model candidate gets padded when another catalog type exists; catalogs with zero or one valid active type yield respectively zero or one candidate, no proposal and a localized shortage reason; an item with no text and no content makes no call; a locked card is never recomputed; the tick never writes `Inbox.type`.
```

### Change 7

Old:

```text
- When an untyped item is recognized with confidence at or above 0.7, then a `proposed` card exists for the best candidate, the item still has no `type` edge, and a later update that does not change the text leaves the card as it is.
```

New:

```text
- When an untyped item is recognized with confidence at or above 0.7, then a `proposed` card exists for the best candidate, the item still has no `type` edge, and a later update that leaves the fingerprint current leaves the card as it is. A changed source fingerprint reruns recognition even if the card already has a recognized type or direct target; new results store v2 with an empty source type id, preserving #1606 inputs and stored-v1 compatibility.
```

### Change 8

Old:

```text
- When confidence is below 0.7, then the card is `needsClarification` with two to four type candidates and a reason.
```

New:

```text
- When confidence is below 0.7 (or no valid candidates remain), then the card is `needsClarification` with a reason and two to four distinct valid type candidates when at least two exist. With fewer valid active types, it carries all that exist (zero or one), no proposal and a localized reason explaining the shortage; no type is invented or duplicated.
```
