# Decision: approving the password sign-in again and the refusal codes

- Question: May the proposal (sp-fd844365-bc0a-46da-8429-3af7a1b2d230) be approved, and how are three open points settled: how the error code reaches the repository without changing what other callers get from `ApiClient`, where the error code sits in the body, and how the password sign-in treats the user name the server does not return?
- Options considered: (a) a new `FailureKind` per refusal, which changes every caller of a 400; (b) the error body kept on `ApiResponse.Failure` and decoded only by the two mailbox routes; for the body, the documented `{ code }` or the `{ error: { code } }` that `toErrorResponseBody` writes; for the user name, prefilling the address (which would overwrite a custom stored one) or an optional field that is sent only when filled.
- Decision: (b), reading `error.code` and accepting a top-level `code` as well; the user name is an optional field with the address as its placeholder, omitted when blank so the stored one is kept. The spec is sound against the integration tip; approved.
