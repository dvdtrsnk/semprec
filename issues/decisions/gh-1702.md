# Decision: gh-1702 (Inherit a task's project onto its attachments)

## Question

The worker of chain e1-037-misc refused gh-1702 at preflight and committed
nothing. The Task allows one rule declaration and "no custom propagation
code", and the Out of scope section excludes the link store and the
propagation. The Context and Task step 3 presuppose two behaviours that the
link engine of gh-1593 does not have:

1. A file attached to two tasks follows only the task it was uploaded to
   first and never holds the union of the two tasks' projects.
2. An existing file that has its own project gets a link that starts broken.

The worker also reported two things the record does not say: the rule breaks
existing tests that are not in Touches, and it makes `Files.projects` the
target of one rule and the via relation of another, the composition for which
`issues/decisions/gh-1756.md` confirmed a deadlock. About 100 sources depend
on gh-1702 directly or through chains (gh-1720 already landed ahead of it as a
shared-file-ordering blocker, gh-1882 and gh-1869 declare it). Decide what
the record says and what the implementation does.

## Options considered

Read for this decision, from the integration tip `045dc1cee`, not from the
worker's words: gh-1702, gh-1593, gh-1654, gh-1653, gh-1724 and their
handovers where present, the epics gh-1326 and gh-1341, `issues/decisions/gh-1756.md`,

What exactly does not hold, established from the code:

- Two tasks. `linkRuleEdgeHook.ts:78` adds the second via edge's source to
  the file's existing `on` link (`addValueLinkItemSource`), and the value is
  recomputed with `sourceUnion` (`linkPropagation.ts:108`, `distinct` over all
  sources). `Files.projects` is many-to-many (`targetIsMany`,
  `linkPropagation.ts:67`), so the file holds both projects. The only
  single-valued guard (`linkRuleEdgeHook.ts:68`, `applyInheritedValues`)
  does not apply. `value_link_sources` has no order column
  (`0089_value_links.sql`: random `id`, no timestamp), so "first" is not
  recorded anywhere. The union is decided in gh-1593 (Decisions, fourth
  bullet) and tested by `linkRuleEdgeHook.test.ts`.
- Own project. `linkRuleEdgeHook.ts:66` skips a target that already holds a
  value and has no link row. gh-1593 says in its Decisions that this "also
  decides the case of a file that already has projects of its own when it is
  attached to a task", and the epic gh-1326 records it as decided by the
  product owner. gh-1654 (completed) already holds that a file with its own
  project keeps it, and leaves the rest to this source. gh-1653 shipped the
  same own-value behaviour for the file's companies.
- A link cannot start broken. `value_links.broken_by` is `CHECK (broken_by IN
  ('user', 'agent'))` and the state check demands `broken_by` for a broken
  row (`0089_value_links.sql`). A link that starts broken would need a
  migration, a third kind of breaker in the links API and the approval
  contracts that read it, or a false attribution to a user.
- What does hold, as the worker observed with the rule declared in the
  working tree only: the rule `fileProjectsFromTasks` validates with no
  findings and no drift, and every behaviour of Task step 2 and all five
  acceptance criteria hold through the choke point (attach, `relation.set` on
  `Tasks.project` including to none, user write breaking the link, the next
  change leaving the file alone, `link.relink`, `link.unlink`). The two
  Context decisions are the only contradictions. They come from the epic
  gh-1341, where both are recorded as "adopted" while drafting, with
  "conservative" as the reason and without an owner decision (the own-value
  rule it contradicts is an owner decision in gh-1326).

Options for the two contradictions:

- A. Correct the Task and Context to what the engine does, and keep every
  acceptance criterion that holds: chosen. The Task's own constraints (only
  the mechanism's operations, no custom propagation code, the link store and
  propagation out of scope) already describe a declaration. The two Context
  decisions are drafting notes that contradict a closed, tested engine
  specification (gh-1593) and an owner decision (gh-1326), so they are the
  defect. The own project case is the owner's rule; the two-task case is the
  engine's union, which also matches what a file attached to two tasks of two
  projects is: it belongs to both.
- B. Extend gh-1702 with the smallest engine change that makes the Context
  true: rejected. It is not small. "First task wins" needs a new field in the
  rule declaration of gh-1411 (`module-registry` types, validation and
  fixtures), an order for the sources that the store does not keep (a
  migration under expand/contract), a rule for what happens when the first
  task is detached, moved to the Trash or loses the file while the second
  stays (the worker named these cases), and an ADR for the new engine
  contract. "Link starts broken" needs the schema change above. All of it
  would sit in a source whose Touches is one manifest entry and whose tier is
  medium, against the repository rules: implement exactly the Task, nothing
  speculative. Neither behaviour has an owner decision behind it.
- C. A prerequisite source for the engine option, with gh-1702 blocked by it:
  rejected for the same reason B is, and it would hold gh-1702 and about 100
  dependants behind a design nobody decided and nothing requires. If the
  product owner later wants a file to follow only one task, that is a new
  source with its own Context, and it can supersede the union by an ADR.
- Declare the rule and say nothing about the Context: rejected. A source
  whose text demands a behaviour the code cannot have fails review for an
  "unmet Task step", and the contradiction would be found again by every
  reviewer.

Ownership handoff and the ADR:

The lock-order cycle (worker second point):

- Add a test and a criterion for the schedule, as gh-1756 did: rejected. It

## Decision

DEFECT, corrected. Option A. gh-1702 stays a declaration of one rule. The
Task, Context, Touches, Scope and Acceptance criteria now state what the
engine does: a file attached to two tasks of different projects holds both
projects; an existing file with its own project keeps it and gets no link
(no `projects` link entry, `link.relink` answers 409); a link never starts
broken. The criteria the worker observed to hold stay as they are. Three
additions follow from the code: the existing tests the rule breaks are named
in Task step 4 and Touches; Task step 5 and the Touches line add one ADR for
the rule and the ownership handoff of `Files.projects`; Out of scope names
the missing backfill, the rejected engine option and the lock-order limit.

No prerequisite source is needed and none is created. The Blocked-by line
and the Model tier are unchanged. No code is changed for this decision in
this program, no protected path is touched.

## Challenge

An independent agent challenged this decision on 2026-11-14 and accepted it with changes. The facts about the link engine of gh-1593 were confirmed from the code: a many-valued target takes the union of its sources, a target with its own value gets no link, link.relink answers 409 and the engine needs no change. Four points are carried here and decided by the controller:

- The lock-order cycle between a Tasks.project edge write and link propagation is relevant to the new rule: a user edge write takes the link and then the row of the file, propagation takes the row and then the link. As gh-1756 was refused to land with a recorded open cycle, gh-1702 starts only after sp-5419cac1-f4a7-4717-b870-4f244b1ad166 is decided and landed. This is a start constraint of the controller; the Blocked by line is unchanged.
- The observations of the first worker are from the base dde23e02b, 568 commits before the tip of this decision. The implementation re-runs every integration file that writes Tasks.project and checks the chain taskProjectFromEvent, the new rule and fileCompaniesFromProjects.
- A recurring task carries its Files relation to every next instance (CARRIED_RELATION_KEYS in advanceTaskRecurrenceWithClient.ts), so a file has all instances as sources and keeps the projects of old finished ones. The implementation records this in the ADR and covers it with a test; changing it is outside this source.
- The decision was written by a Sonnet 5.5 agent, not by the strongest model that the section Autonomy asks for, and so was its challenge.
