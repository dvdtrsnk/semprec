# Decision: a page write names the text it was edited from, and the files it touches

- Question: The Task of sp-0fcb29a1-fc26-41a8-8490-bd655f82521b sends a write against the kept base's `ETag`, the caller's only when no base is kept. Once the kept page moved past the version an editor read (the background writer saved or merged it, or another window of the device wrote it), that write would replace what changed meanwhile without a merge, and a merge against the kept base would repeat the text the server already holds. How does a write find the text it has to merge against, what does a `404` do to a kept page, how do a write in the background and a window's write avoid interleaving, and how does an editor reread after its own save (the server sends `doc` frames to the writer too) without moving the caret? The Touches also missed files the Task needs and named `JournalSDK.kt`, which needs no change.
- Options considered: (a) the device remembers which text it handed to each editor at each version, which breaks with two editors of one page and needs a version for every kept text; (b) the write carries the Markdown the editor edited from (`base`), so the device merges three ways against it when its own text is another, with no history to keep. For `404`: keep the text forever and retry it on every replay, or forget the page as a `404` read does. For interleaving: compare-and-set inside the store, or one lock around every page read and write. For the reread: apply it as a load, or keep the ids of the blocks it holds unchanged as a merge does.
- Decision: (b); a `404` forgets the page with its text, since the server has no item to write it to; one lock that every window shares; the reread keeps the ids. `Merged` covers a merge the device holds until the server can be reached; every merge is announced on the page change bus, so the other windows read it again.
