# gh-1518 decision

## Question

1. How does bare REST include=relations behave when the database has more than five relation keys?
2. Which request shape preserves existing value links while adding relation expansion?
3. Where does blob metadata of projected file/image properties live, and what is its exact shape?

## Options considered

1. Reject above five keys: selected, preserving both all-key selection and the cap. A deterministic subset hides requested relations; an exception weakens the cap.
2. Replace the legacy array: rejected as a regression. Keep the legacy array and add a strict object with optional links boolean and relations projection map: selected. A mixed array of strings and objects adds unnecessary complexity.
3. Add a per-property blob array: rejected because #1412 defines no such shape. Reuse the top-level per-property metadata map on each expanded target, with unchanged projected property values: selected.

## Decision

1. DEFECT — bare REST selects all relation keys and rejects more than five with 400 validation_failed and field include.relations; explicit projection parameters select only their named keys, including empty projections.
2. DEFECT — preserve [] and ["links"], add { links?: boolean, relations?: Record<string, string[]> }, and allow REST path, links and relations together without regressing links.
3. DEFECT — expanded targets use optional top-level blobs: Record<propertyKey, { blobId: string, byteSize: number, mimeType: string, filename: string | null }>, only for projected visible file/image blobs, omitted when empty; property values remain unchanged.

Both blockers gh-1412 and gh-1509 are closed in issues.mjs list; both handovers were read. At tip ba2b5b662fee5d8ae7b16f555a5b7f91d9c47127, schemas.ts accepts the legacy include array for all three operations; genericApplicationService.ts attaches links on all three reads, and the REST handlers pass them through. ItemEnvelope and blobMetadata.ts confirm the map shape, nullable filename, omission rules and unchanged properties.

The accepted additive REST contract (2026-09-11), neutral generic application port (2026-09-17), REST-only extension limits (2026-10-01), tenant RLS (2026-10-03), blob deletion (2026-09-28) and export blob lookup (2026-10-18) ADRs were inspected. These local contract corrections preserve those decisions and introduce no cross-cutting pattern. No ADR CONFLICT, external PRECONDITION or PROTECTED-path change is required. Touches and Out of scope remain unchanged. No agent:blocked label was present. No Task implementation, build or test was performed.

### Change 2

Old:


New:

```text
1. Define the expansion contract in `shared/genericOperations`: an optional `include` input on `item.get`, `database.query` and `view.query` accepting the existing array form (`[]` or `["links"]`) or a strict object `{ links?: boolean, relations?: { <propertyKey>: string[] } }`; `links: true` requests the existing value links, while false or omission does not, and both fields may be supplied together. An omitted `relations` field requests no expansion; an empty relations map selects no keys. The relations map carries the projections (an empty array means expand the key with no projected properties). Define an output `relations: { [propertyKey]: ExpandedRelationTarget[] }` plus `relationsTruncated: string[]` on each returned item. `ExpandedRelationTarget` is `{ id, databaseId, databaseKey, title, color?, icon?, metadata, properties?, blobs? }`. For projected file and image properties, `blobs` is a top-level field on each expanded target, alongside `properties`, with shape `Record<propertyKey, { blobId: string, byteSize: number, mimeType: string, filename: string | null }>` as in #1412 and `ItemEnvelope`. Only projected file/image keys with visible blob metadata appear; omit `blobs` when none qualify. Keep the projected property values unchanged; do not add per-property blob arrays.
```

## Decision 4

### Question

Which color/icon values do full and reduced nested relation targets return, who resolves manifest metadata, what happens when no value resolves, and does expansion write data?

### Options considered

- Database columns only: rejected; system database writes forbid icon/color and seeded rows leave them null.
- Collection manifest values only: rejected; this loses an Area item's own icon/color and a Project item's own color.
- Item values followed by existing collection metadata resolution: selected explicitly for both target shapes. Reusing CollectionMetadataResolver also preserves existing non-system database defaults instead of creating a competing collection rule.
- Loading manifests inside the expansion store: rejected in favor of caller-supplied resolution already used by database envelopes, with no per-target registry load or SQL.
- Present null fields: rejected; omission preserves Task 1's optional color?/icon? contract.

### Decision

a. DEFECT — for each field independently, use a non-empty string in the schema-defined item property (color of type color, icon of type text), then caller-supplied CollectionMetadataResolver output: manifest metadata for system databases; stored non-null values then existing defaults for non-system databases. Apply identically to full and reduced nested targets, without requiring projection. The store does not load manifests or a registry.
b. DEFECT — explicitly omit each unresolved color/icon field; never return null for those fields.
c. SOUND — expansion remains read-only; make explicit that no resolved value is persisted and no database write is added.

Evidence at integration tip a7b97ab751b2d8a78b269a4c081a45954c1504f1: databasesStore.ts forbids system icon/color writes; seedTenDatabases.ts declares Areas.icon/color and Projects.color; systemDatabasesModuleManifest.ts supplies collection defaults; manifest/collectionMetadata.ts already resolves system manifests and non-system stored/default values; adapter/databaseEnvelope.ts consumes caller-supplied metadata. Both gh-1412 and gh-1509 are closed in issues.mjs list and their handovers were read.

The ADR search for icons, colors, manifests and envelopes found no accepted icon/color precedence specific to relation expansion. The accepted additive REST contract (2026-09-11), manifest custom routes (2026-09-11), neutral generic application service port (2026-09-17) and custom-route composition-root dependencies (2026-10-29) were read. This decision specifies only the new relation response and reuses existing metadata resolution and dependency injection; it does not change database envelopes or introduce a cross-cutting mechanism. No ADR CONFLICT, PRECONDITION or PROTECTED change is required. Existing limits, tenant/archive filtering and scope remain unchanged. No agent:blocked label was present. ## Decision 5

### Question

May the missing resolver plumbing and its regression-test callers be added to Touches, are there additional generic roots, and must caller-supplied metadata resolution remain required without manifest loading in the store?

### Options considered

- Leave Touches unchanged: rejected because Task 4 and Decision 4 cannot reach REST, MCP and agent production reads through the existing pool-only factories.

- Add exactly the missing composition files and their factory-call regression tests: selected. Pass an explicit required resolver through the existing synchronous factories; build it asynchronously from the loaded registry at the composition roots. This avoids making the tool factory asynchronous or introducing another registry lifecycle.

### Decision

a. DEFECT — add the three proposed source files and the exact test paths in the Touches edit below, plus the additional production composition file identified in (b); changes are limited to resolver construction, forwarding and regression assertions for that wiring.
b. DEFECT — also add backend/services/semprec-agents/src/agentSessionComposition.ts: it calls both createGenericOperationAgentTools and listGrantedGenericOperationAgentTools. The latter constructs another gateway in the already-added genericOperationAgentTools.ts and must receive the resolver too. No other production root needs a new Touches entry.

Pass it explicitly through both agent helpers as well; permission-context tests may still pass undefined for their separate moduleRegistry argument, but must supply the resolver. Build it with createCollectionMetadataResolver from the loaded registry in app.ts and agentSessionComposition.ts. Neither the expansion store nor its read facade loads manifests or a registry, and no optional/default resolver may silently omit system metadata.
