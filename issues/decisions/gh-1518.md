# gh-1518 decision

## Question

1. How does bare REST include=relations behave when the database has more than five relation keys?
2. Which request shape preserves existing value links while adding relation expansion?
3. Where does blob metadata of projected file/image properties live, and what is its exact shape?

## Options considered

1. Reject above five keys: selected, preserving both all-key selection and the cap. A deterministic subset hides requested relations; an exception weakens the cap.
2. Replace the legacy array: rejected as a regression. Keep the legacy array and add a strict object with optional links boolean and relations projection map: selected. A mixed array of strings and objects adds unnecessary complexity.
3. Add a per-property blob array: rejected because #1412 defines no such shape. Reuse the top-level per-property metadata map on each expanded target, with unchanged projected property values: selected.

## Decision

1. DEFECT — bare REST selects all relation keys and rejects more than five with 400 validation_failed and field include.relations; explicit projection parameters select only their named keys, including empty projections.
2. DEFECT — preserve [] and ["links"], add { links?: boolean, relations?: Record<string, string[]> }, and allow REST path, links and relations together without regressing links.
3. DEFECT — expanded targets use optional top-level blobs: Record<propertyKey, { blobId: string, byteSize: number, mimeType: string, filename: string | null }>, only for projected visible file/image blobs, omitted when empty; property values remain unchanged.

Both blockers gh-1412 and gh-1509 are closed in issues.mjs list; both handovers were read. At tip ba2b5b662fee5d8ae7b16f555a5b7f91d9c47127, schemas.ts accepts the legacy include array for all three operations; genericApplicationService.ts attaches links on all three reads, and the REST handlers pass them through. ItemEnvelope and blobMetadata.ts confirm the map shape, nullable filename, omission rules and unchanged properties.

## Spec change

### Change 1

Old:

```text
Every screen that shows an item's links (a person's companies and projects, a project's area as a colored label, a movie's "watched with" people) currently needs one edge read per item and one item read per target. `GET /api/items/:id` returns only the stored envelope (`itemEnvelope.ts`), with `?include=path` as the single supported include, and `database.query` / `view.query` return `{ items, nextCursor }` with no link data at all. #1404 adds the edge read; this issue adds the one inline expansion that all callers use, so clients render a list of 50 projects with their area labels in one request.
```

New:

```text
Every screen that shows an item's links (a person's companies and projects, a project's area as a colored label, a movie's "watched with" people) currently needs one edge read per item and one item read per target. `GET /api/items/:id` returns only the stored envelope (`itemEnvelope.ts`), with `?include=path` and `?include=links` already supported; `item.get`, `database.query` and `view.query` already accept `include: ["links"]` from #1403 to attach value links. Relation target expansion is not yet available. #1404 adds the edge read; this issue adds the one inline expansion that all callers use, so clients render a list of 50 projects with their area labels in one request.
```

### Change 2

Old:

```text
1. Define the expansion contract in `shared/genericOperations`: an `include` input on `item.get`, `database.query` and `view.query` carrying `{ relations: { <propertyKey>: string[] } }` (an empty array means expand the key with no projected properties), and an output `relations: { [propertyKey]: ExpandedRelationTarget[] }` plus `relationsTruncated: string[]` on each returned item. `ExpandedRelationTarget` is `{ id, databaseId, databaseKey, title, color?, icon?, metadata, properties? }`; file and image properties inside `properties` also carry `blobs: { blobId, byteSize, mimeType, filename }[]` as defined by #1412.
```

New:

```text
1. Define the expansion contract in `shared/genericOperations`: an optional `include` input on `item.get`, `database.query` and `view.query` accepting the existing array form (`[]` or `["links"]`) or a strict object `{ links?: boolean, relations?: { <propertyKey>: string[] } }`; `links: true` requests the existing value links, while false or omission does not, and both fields may be supplied together. An omitted `relations` field requests no expansion; an empty relations map selects no keys. The relations map carries the projections (an empty array means expand the key with no projected properties). Define an output `relations: { [propertyKey]: ExpandedRelationTarget[] }` plus `relationsTruncated: string[]` on each returned item. `ExpandedRelationTarget` is `{ id, databaseId, databaseKey, title, color?, icon?, metadata, properties?, blobs? }`. For projected file and image properties, `blobs` is a top-level field on each expanded target, alongside `properties`, with shape `Record<propertyKey, { blobId: string, byteSize: number, mimeType: string, filename: string | null }>` as in #1412 and `ItemEnvelope`. Only projected file/image keys with visible blob metadata appear; omit `blobs` when none qualify. Keep the projected property values unchanged; do not add per-property blob arrays.
```

### Change 3

Old:

```text
2. REST: `?include=relations` on `GET /api/items/:id`, combinable with `path` (`?include=path,relations`); projections via `relations.<propertyKey>=name,date` query parameters. `database.query` / `view.query` bodies take `include: { relations: { <key>: [propertyKeys] } }`. `?include=relations` without any projection expands every relation key of the item's database with no extra properties.
```

New:

```text
2. REST: `?include=relations` on `GET /api/items/:id`, combinable with the existing `path` and `links` tokens (`?include=path,links,relations`); projections via `relations.<propertyKey>=name,date` query parameters. `database.query` / `view.query` bodies accept both Task 1 include forms, including `include: { links: true, relations: { <key>: [propertyKeys] } }`. `?include=relations` without any `relations.<propertyKey>` parameters selects every relation key of the item's database with no extra properties, then applies the 5-key cap: more than 5 keys fails the whole request with `400 validation_failed`, `field: "include.relations"`, even if some keys have no targets. Never choose a subset or exempt a database. When such parameters are present, expand only their named keys; `relations.<propertyKey>=` selects that key with no projected properties, allowing callers to select at most 5 keys explicitly.
```

### Change 4

Old:

```text
- When a request names an unknown key or exceeds 5 keys or 10 projected properties, then it fails with `400` naming the field.
```

New:

```text
- When a request names an unknown key or exceeds 5 keys or 10 projected properties, then it fails with `400` naming the field. This includes a bare REST `include=relations` on a database with more than 5 relation keys (`field: "include.relations"`); explicit selection of at most 5 keys remains valid.
```

### Change 5

Old:

```text
- When a projected property is a file or image, then its blob metadata is included.
```

New:

```text
- When a projected property is a file or image, then its unchanged value is in `properties` and its visible blob metadata is in the expanded target's top-level `blobs[propertyKey]` map entry with `blobId`, numeric `byteSize`, `mimeType` and nullable `filename`; no per-property blob array is added, and `blobs` is omitted when empty.
```

### Change 6

Old:

```text
- When the caller belongs to another tenant, then no foreign target appears.
```

New:

```text
- Existing `include: []` and `include: ["links"]` requests remain valid on all three operations; `{ links: true }` returns the same links, and `{ links: true, relations: { <key>: [] } }` returns both. REST `include=path,links,relations` preserves path and links alongside the selected relation expansion.
- When the caller belongs to another tenant, then no foreign target appears.
```
