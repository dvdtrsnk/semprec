# Decision: approving the offline-first mobile data batch

- Question: May the seven proposals of the offline-first batch (sp-0412eb00-5180-4208-bb49-0e4c38ce9600, sp-c5c1294b-c8bd-407d-945b-6ce0daae5eae, sp-c12f129d-e765-4ef1-967c-a1e4070e162b, sp-a177a00b-7349-48f3-abbf-d0f02e2d78a6, sp-0fcb29a1-fc26-41a8-8490-bd655f82521b, sp-a4e32028-4e3a-4320-9191-522c2edc851c, sp-fa398954-b313-4063-8b82-1fcf401e221f) be approved, and how are the open design points settled: a sync library or the shared layer itself, replicated rows or kept answers, a server change feed or none, and a Yjs replica or a three-way merge for notes?
- Options considered: PowerSync (complete Kotlin Multiplatform sync over Postgres logical replication, which bypasses row-level security, needs another service and a Postgres restart), Realm device sync (ended in September 2025), Couchbase Lite and Ditto (their own servers), ElectricSQL (no mobile write path), Store5 (reads only), a local row database with a server change feed, a Yjs replica on the device through Yrs and Gobley (a Rust toolchain in every mobile build), and the shared data layer keeping the answers of the routes the screens call, queueing writes as requests and merging note Markdown three ways on the device.
- Decision: the last option, without a backend change: the server keeps its read models and tenant isolation unchanged, a reconnecting device reads again as the realtime decisions already prescribe, and notes merge on the device on the Markdown the native editor already writes. The batch is ordered as a chain because each issue changes the files of the one before. The specs are sound against `origin/develop` 27016b96d; approved on the owner's instruction of 2026-11-23 to plan and implement the batch.

# Decision: the defects the simulator acceptance run found

- Question: Driving the app of this branch on an iOS simulator against the deployed v0.7.4, with a proxy that takes the server away, found two defects of the batch. The offline banner covered the buttons of the navigation bars, because the tab view laid them out under its top safe-area inset. Completing or renaming offline a task that had only been listed reported "Could not save" and reverted the row although the change was queued, because the item repository reads the item back after each change and that read had no kept answer. How are they fixed?
- Options considered: for the banner, an inset on the stack of every tab, the bottom accessory of the iOS 26 tab view (none on macOS), or the banner above the tab view in a stack; for the read back, the repository answering the write's own answer when the read back fails (which leaves a listed item unopenable offline), or the offline set answering an item's own read that has no kept answer with the newest copy of the item that another kept answer holds.
- Decision: the banner sits above the tab view, the same view on iOS and macOS, with a clear background while it shows no line. An item's own read without a kept answer takes the newest copy that names its `databaseId`, so the target of a relation is never taken for the item; a listed item now also opens offline. The offline set's decision states the copy.
