# Decision: gh-1739 (Gmail watch lifecycles and the Pub/Sub dispatcher)

## Question

The implementation proposal gh-1739 (`[mail-accounts 26/30]`: host the Gmail
watch lifecycles through `hosted.gmail_api`, start one
`createGmailPubSubDispatcher` per api process, stop it as an ordered step of
`createGracefulShutdown`, and read the three Pub/Sub keys from the `api`
secret group) is open without `spec:approved`. Approve it, or make the
minimal correction that makes it approvable.

## Options considered

- Approve unchanged (SOUND): rejected, for two reasons.
  1. The last Touches line required adding a step to
     `docs/adr/2026-09-27-semprec-api-shutdown-ordering.md` "if the ADR
     lists the order". The ADR is accepted and lists the order, so the line
     instructed an edit of an accepted ADR body, which `issues/README.md`
     (section "Autonomy"), `docs/adr/README.md`, `review-rules/rules.md`
     (high-severity finding) and `adr-conventions` forbid; the implementation
     would have been blocked in review. Task item 3 left the step's position
     open ("before the pool ends and before the live-sync root's database use
     ends"), which is a real ordering decision with alternatives (before or
     after the HTTP drain, before or after the mail root), not a detail for
     the implementation to choose. The repository's precedent for a new
     shutdown step is a standalone ADR
     (`2026-10-17-tenant-deactivation-tears-down-in-process-state` records
     the listener close as a step of its own without touching the 2026-09-27
     ADR).
  2. Task item 4 said "check `deploy/provision.test.sh` still passes". That
     test asserts the exact number of keys across all
     `deploy/shared/env/*.env.example` templates (`all_template_keys`,
     `-eq 52`, last changed in d0061b68). On the integration tip the templates
     carry 59 keys (seven were added since by other issues without updating
     the count), so the assertion cannot hold after three more keys are
     added unless the count is updated; the file was not in Touches.
- Minimal spec correction only (DEFECT), leaving the step's position to the
  implementation and dropping the ADR line: rejected. The dispatcher's stop
  position is a lifecycle contract that later loops will follow (the
  `adr-conventions` trigger "a lifecycle, shutdown, retry or ordering
  contract"), and recording it only in a `shutdown.ts` comment is the exact
  missing-ADR finding the convention exists to prevent.
- New narrowing ADR plus the minimal spec corrections (ADR CONFLICT): chosen.
  The new ADR fixes the step after the HTTP drain and immediately before
  `mailLiveSync.stop()`, with the reasons and the rejected positions; the
  spec points at it, and the `provision.test.sh` count update is added to
  Task item 4 and Touches.
- Add `#1546` (voice channel; also touches `serve.ts` and `shutdown.ts`) or
  `#1734` (also touches `serve.ts`) to Blocked-by as shared-file overlaps:
  rejected. The two shutdown steps are disjoint and each has its position
  fixed by an ADR (the voice socket server must close before the HTTP drain
  per the 2026-09-27 consequence; the dispatcher stops after it), so the
  overlap is splittable and resolves mechanically on merge; the owner has
  already approved the same class of cross-epic `serve.ts` overlap without
  an edge (gh-1550 and gh-1546), and an edge would serialize the mail epic
  (including its dependant #1745) behind the voice epic.
