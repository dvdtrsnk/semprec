# Decision: gh-1992 (Detect duplicate companies and people in proposals)

## Question

The worker of chain e1-229-semprec-api refused gh-1992 at preflight and committed nothing. Its Task says that a
duplicate company or person "is replaced by the link step to its id" and Acceptance criteria 1 and 3 say that the
proposal "links to" the existing company or person and creates none. When the duplicate is the proposal's own record
(the company of a Companies card, the person of a People card), that record is the primary step of the envelope. The
envelope validation delivered by gh-1479 refuses it: `assertValidEnvelopeOperations`
(`backend/packages/data/src/inbox/inboxTickAction.ts`) throws "the primary step cannot be a link step". The worker
measured a card stored as `needsClarification`. gh-1993, the next source of the chain, waits behind gh-1992.

## Options considered

Read for this decision, from the worker's integration tip `cbbb9e204` and the current worktree: gh-1992, gh-1993,
gh-1987 and gh-1989 (the delivered neighbours of the computation), gh-1479 with its handover, gh-1486 and gh-1648,
`docs/adr/2026-10-25-multi-step-proposal-envelope.md`, `docs/adr/2026-09-10-no-speculative-generality-beyond-issue-scope.md`,
`issues/decisions/gh-1986.md` (format), the README section "Autonomy", and the code of `inboxTickAction.ts`
(`assertValidEnvelopeOperations`, `assertValidStep`), `proposalEnvelopeValidation.ts` (`assertUpdateStepShape`),
`proposalSteps.ts` (`executeProposalSteps`, `executeStep`), `proposalOperations.ts` (`buildProposalSteps`),
`inboxTickSnapshot.ts` (`buildProposalEnvelope`), `proposalActions.ts` (the confirm of a multi-step envelope),
`undoConfirmedProposal.ts`, `proposalEditorRules.ts`, `journalInboxCompute.ts`, `proposalChanges.ts` and
`services/semprec-api/src/proposalComputation.ts`.

What the code says:

- The refusal is one line (`inboxTickAction.ts`, in the primary-step loop of `assertValidEnvelopeOperations`). It is
  not in the Task or the Acceptance criteria of gh-1479, and not in `2026-10-25-multi-step-proposal-envelope.md`,
  which lists `link` among the operations and says only that the top level mirrors the primary step. It appears in the
  handover of gh-1479 as an implementer's note ("A `link` step cannot be primary"). No test asserts it.
- A multi-step envelope with an `update` primary is accepted and executed today. `assertUpdateStepShape` requires
  `before` and `after` only for the keys an update changes, so an `update` with no `properties` and no `relations`
  needs neither. `executeStep` for it runs `assertUpdateBefore` (locks the item, checks that it is live), writes no
  property (`Object.keys(propertiesPatch).length > 0` guards the write) and moves no edge, and `executeProposalSteps`
  returns the existing item as the primary result. The confirm (`proposalActions.ts`) takes `executed.primaryItemId`
  generically and inserts item origins only for created items; the undo classifies `update` and `link` results alike
  (`undoConfirmedProposal.ts`); `proposalEditorRules.schemaDescribes` and `journalInboxCompute` already treat an
  `update` or `link` primary as "an item that already has its values". An existing confirm test
  (`proposalActions.test.ts`, the project that moves to another area) already confirms a primary `update` with
  `properties: {}`.
- Measured on the integration tip in a scratch integration test (in the worktree of the stopped chain, reverted, the
  worktree is clean again): a Companies envelope with a primary `update` of an existing company with no properties
  validates, with the properties spelled `{}` as well; a People envelope with a primary `update` of an existing person
  and a secondary create of a company validates; a Companies envelope with a primary `link` is refused with "the
  primary step cannot be a link step"; a People envelope with a secondary `link` to an existing company that the
  primary person create's relation refers to validates.
- The replacement cannot be done by the computation alone, whichever step kind is used for the primary. First,
  `buildProposalSteps` picks the primary as the first `create` into the target database and otherwise the first
  operation, which validation then refuses as not mirroring the top level; once the own create is replaced, a People
  answer `[create company, replaced person]` would make the company the primary. Second, `buildProposalEnvelope`
  builds a multi-step envelope only for more than one operation, so one replaced operation would be stored as an
  ordinary create of `result.properties`, which is the very create to be avoided. Both need a small change in
  `backend/packages/data/src/inbox`, and both are the same for every option below.
- gh-1993 is not affected: its Task adds a context section and an instruction line in `proposalComputation.ts`, it
  neither reads nor writes `operations`, and it lists only #1987 as blocked-by. It waits behind gh-1992 only because
  both change `proposalComputation.ts` in one chain.

Options:

- A. Keep the validation of gh-1479 as it is and represent the duplicate primary as the existing-item primary step it
  accepts already, an `update` with no properties and no relations, while a nested duplicate is a `link` step as the
  Task says: chosen. No delivered contract changes, nothing of gh-1479 or gh-1486 is touched, the shape is already
  validated, confirmed and undone by existing tests, and the existing record is locked and checked at confirm. The cost
  is that the step kind `update` names "an item that exists" rather than "a link", which the Decision, the new ADR and
  the Acceptance criteria say in so many words.
- B. Lift the refusal of a primary `link` in `assertValidEnvelopeOperations` and emit a `link` primary. Rejected as the
  larger change for the same result. It edits a delivered validation of gh-1479, needs new validation and confirm
  tests for a primary `link` that nothing exercises today (the confirm and undo paths for it are untested, even though
  they read as generic), and still needs the same marker and one-operation change as A. It gains only the name `link`
  for the primary step. It would also make the ADR a narrowing of a rule that lives in code, which is more than this
  issue needs.
- C. Keep the primary a `create` and drop the duplicate card or answer `needsClarification` for a duplicate primary.
  Rejected: it contradicts Acceptance criteria 1 and 3 ("creates no company", "links to that person") and the owner's
  decision that a duplicate must not create a second record.
- D. Change the model's operation list so that the existing record is never primary (for example a primary
  `update` chosen by the model). Rejected: the primary is the card's own record and is decided by the server's exact
  match, not by the model; the model answer schema stays as it is.
- E. A `duplicateOf` field on the envelope or the step. Rejected as a new field for a shape the multi-step ADR already
  covers; its last consequence says a step added by a future module must use that shape and not a new field.

Choices where the issue is silent:

- The replacement drops `properties` and `relations` of the create it replaces and keeps its `alias`. Dropping the
  properties is the Decision "no field of the existing record is changed"; dropping the relations keeps the existing
  record unwritten as well (a link or update would otherwise add edges to it), and keeping the alias keeps every
  `{ alias }` target of the other steps valid.
- A result without `operations` is detected on its top-level `properties` and gets its one operation from the
  replacement, because the tick builds the envelope from the result and the envelope builder ignores the top-level
  `properties` of a multi-step result.
- The marker `primary` is set only by the duplicate step, the zod schema of the model's operations strips it, and
  `buildProposalSteps` does not copy it into the stored step. The stored envelope stays within the schema of gh-1479.
- A card whose primary step refers to an existing item has no editable fields in the editor (`schemaDescribes` is
  false for it); how such a card is presented or overridden is the separate design request that the issue already
  puts out of scope.

The decision needs an ADR: it fixes how a duplicate is represented in a stored proposal, which the card, the confirm
and the undo all read, and it adds a marker to the shape that `buildProposalSteps` consumes; no ADR or review rule
covers it. Task step 7 adds it; it supersedes nothing and narrows nothing, so no accepted ADR body is edited.

## Decision

Option A. Validation (`assertValidEnvelopeOperations`) and confirm are unchanged. A duplicate found by exact IČO or
e-mail address replaces the create by an operation that refers to the existing item and writes nothing: a `link` for a
nested record, and for the proposal's own record an `update` with no properties and no relations marked `primary`.
The operation shape gets the optional `primary` marker, honoured by `buildProposalSteps`, and `buildProposalEnvelope`
builds a multi-step envelope for any marked operation. No change to the files of gh-1479 and gh-1486.

## Consequence

- gh-1992 can be implemented on the integration tip without a change to a delivered validation. The touched files are
  `services/semprec-api/src/proposalComputation.ts`, the new `inbox/companyIcoLookup.ts` and its export,
  `inbox/proposalOperations.ts`, `inbox/inboxTickSnapshot.ts`, the test files of the Touches and the new ADR.
  `inboxTickAction.ts`, `proposalSteps.ts` and `proposalActions.ts` are read, not changed.
- A multi-step answer that is not a duplicate is built exactly as before: the marker is absent, the primary rule of
  `buildProposalSteps` is unchanged and a single unmarked operation is stored as an ordinary create.
- When the own person of a People answer is a duplicate and the answer also creates a new company, the company create is
  kept (Task 4) but no edge to the existing person is written, because the existing record is not written at all. The
  user can add the edge or merge by hand; a Task that wants the edge written needs its own decision.
- The confirm of such a card answers the existing item as `resultItemId` and creates no item, so no item origin or
  Inbox origin note is written for it. Its undo writes nothing either, but it is refused with 409 `version_conflict` once
  the existing item has changed after the confirm, because the undo checks the item of an `update` step (a `link` step is
  not checked); measured.
- The same holds for a nested duplicate person in a Companies answer: its `link` carries no relation, so the new company
  is left without that person.
- gh-1993 needs no spec change and continues after gh-1992 in the same chain.
