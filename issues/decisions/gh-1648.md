# Decision: gh-1648 (Store and return per-step confirm results)

## Question

The implementation of gh-1648 (`[inbox-proposals 07/19]`) was refused as
BLOCKED: Task item 1 (`followUp`), Task item 4 (the transcription-queuing
test) and Acceptance criterion 2 require `confirmProposalWithClient` to set
`followUp` in the same transaction that enqueues a transcription or MCP sync
job, but no such confirm-path enqueue exists on the tip. Resolve the block
so the implementation can be retried.

## Options considered

- Approve unchanged (SOUND): rejected. The refusal is correct on the tip.
  The only enqueue in `confirmProposalWithClient`
  (`backend/packages/data/src/inbox/proposalActions.ts`) is
  `enqueueJournalInboxRecomputeForProposal`. `enqueueTranscriptionJob`
  (`transcription/transcriptionJob.ts`) is called only from the Files create
  heartbeat (`transcriptionActions.ts`, after commit, and it skips files with
  an Inbox origin) and from `transcriptionRouteHandlers.ts`; no MCP sync
  enqueue exists at all (`mcpSync.ts` has only the human-triggered
  `syncMcpServerTools`). A confirm that queues a transcription, and the test
  and criterion built on it, cannot be written.
- Add the missing blockers (DEFECT): chosen. The confirm-path enqueues are
  owned by two open, approved issues: #1978 adds the `transcription` card
  whose confirm enqueues `transcriptionCreate` and `transcriptionJob` for the
  Files item, and #1976 adds `enqueueMcpServerSync` to the MCP-server confirm
  branch. #1984 (Blocked by #1943, #1976, #1978) states that both
  confirmations record `followUp` in `results[]` of #1648, and the accepted
  `docs/adr/2026-10-25-undoing-a-confirmed-proposal-reverses-its-recorded-writes.md`
  ("Follow-up processes") needs the queued jobs recorded at confirm. Neither
  #1976 nor #1978 mentions `results` or `followUp` in its own Task, so the
  only way the field gets set without editing other issues is for #1648 to
  run after both and set it next to their enqueues. No cycle: neither #1976
  nor #1978 reaches #1648 or #1943 through Blocked-by. #1943 and #1938, the
  issues blocked by #1648, already wait on 287 and 254 open issues; #1984
  already waits on #1976 and #1978.
- Narrow `followUp` to always `null` and drop the transcription test and
  criterion: rejected. It keeps #1648 dispatchable now, but leaves no issue
  that writes `followUp`; #1976 and #1978 would add their enqueues without
  recording them, and #1984 would find nothing to cancel. Fixing that would
  mean editing other issues' specs, which is outside this decision.
- Derive `followUp` by looking up queued jobs by key after the steps: rejected.
  It invents a mechanism the Task does not ask for, and the MCP sync job key
  does not exist before #1976.
- A new ADR (ADR CONFLICT): rejected. No accepted ADR forbids what the spec
  needs; `docs/adr/2026-09-10-side-effects-follow-the-commit.md` already
  covers enqueueing inside the confirm transaction.

Checks run on the integration tip (d764facf; the refused run was on
b88c180f, and the only later changes are outside `inbox/`, `transcription/`
and `mcp/`): Blocked-by #1451 and #1486 are closed; #1976 and #1978 are open
with `spec:approved`/`agent:ready`, so the issue waits on them after
queueing. `confirmProposalWithClient`, `resolveResultLabel`,
`allowedSystemKeys` in the confirm patch and `createConfirmProposalRouteHandler`
exist; the system-owned `results` json property is declared on Processing
proposals (`seed/seedInboxPipeline.ts`, cutover
`processingProposalsCardStateCutoverMigration.ts`); `executeProposalSteps`
(`inbox/proposalSteps.ts`) writes `create`, `update`, `link` and
`fileFromAttachment` steps; a `pageContent` confirm inserts the block whose
id is the proposal id. `inbox/__tests__/` exists. No `review-rules/` line or
`docs/adr/` body is in conflict; no ADR body is edited. No protected path is
touched.

## Decision

DEFECT: added #1976 and #1978 to Blocked-by and named their enqueues as the
source of each `followUp` value in Task item 1. Approved and queued.
