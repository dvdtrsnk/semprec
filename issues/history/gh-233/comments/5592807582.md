## Summary

Implements issue #233: a `/setup` API flow that bootstraps the deployment's first (and only) account.

- **`createAccount`** (`backend/packages/data/src/auth/authActions.ts`): the single email/password-validating, Argon2id-hashing account-creation function, shared by setup today and available to a future signup route without exposing one now.
- **`bootstrapFirstAccount`**: available only while `users` is empty and the caller's token matches `SETUP_TOKEN`. A cheap unlocked pre-check short-circuits the common post-bootstrap case; the actual decision runs inside a transaction holding a Postgres advisory lock, so concurrent attempts produce exactly one winner. Returns 404 both when a user already exists (checked before the token) and for a wrong token, so the route never confirms whether setup is still open.
- **`anyUserExists`** (`usersStore.ts`): backs the emptiness check.
- **`setupHandler.ts`**: `POST /api/setup?token=...`, unauthenticated by design, wired into `serve.ts` alongside a new required `SETUP_TOKEN` env var (same convention as `SEMPREC_API_TOKEN`; provisioning the production secret file is out of scope per the issue).
- Tests at both the action layer (including a concurrency race test) and the HTTP handler layer.

The branch was also merged with `develop` (which had landed issue #142's password-reset flow in the meantime) to resolve a conflict in `usersStore.ts` and `serve.ts` — both sides' additions were kept side by side, no logic changes.
