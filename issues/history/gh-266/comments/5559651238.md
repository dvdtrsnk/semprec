## Summary

Fixes #266: `AccountQueue.setLimit()` in `backend/packages/data/src/mail/imapConnectionLimiter.ts` woke up queued waiters based on `this.active < this.limit`, but `this.active` was never incremented inside that loop — a woken waiter only bumps it later, when its `run()` continuation resumes on a subsequent microtask. As a result, a single limit change could resolve every queued waiter regardless of actual free capacity, letting far more concurrent IMAP connections run than the configured `limit` once those waiters' tasks started.

Fixed by introducing a `wakeWaiters()` helper that grants (and counts) a slot synchronously at the moment a waiter is woken — both when the limit is raised and when a running task completes — and by routing `run()`'s own immediate-start path through the same increment site, so a freshly granted waiter is never invisible to a concurrently admitted caller within the same tick.

Added a regression test (`imapConnectionLimiter.test.ts`) reproducing the exact scenario (5 tasks queued behind limit 1, then limit raised to 3): confirmed it fails against the pre-fix code (over-admits to 5 concurrent) and passes with the fix (caps at 3).
