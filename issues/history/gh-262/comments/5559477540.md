## Summary

`passesItemRelationFilter` (in `backend/packages/data/src/scheduler/itemRelationFilter.ts`), which gates the `newEmail` heartbeat's `core.agentRun` action on a fired item's related-folder properties, had two bugs:

1. **No partition pruning**: `items` is `PARTITION BY LIST (database_id)`, but the query joined `items related` purely on `id`, forcing Postgres to scan every database's partition to find the related row instead of pruning to the one it actually lives in.
2. **No soft-delete guard**: the query didn't filter `deleted_at`, so a soft-deleted folder (e.g. a Junk folder that was later removed) could still count toward the `include`/`exclude` sets, potentially suppressing or wrongly allowing the `newEmail` event based on folder state that no longer exists.

Fix: resolve the related item's `database_id` via the relation definition's *other-side* property (a small join against the unpartitioned `properties` table) and pin it in the `items` join condition — the same pattern already used in `rollup/recompute.ts` — plus add `related.deleted_at IS NULL`.

Added a regression test in `newEmailHeartbeat.test.ts` that soft-deletes a Junk folder after ingest (before the heartbeat job drains) and verifies the `newEmail` action now fires correctly since the deleted folder no longer blocks it.

Full test suite (314 tests, 24 files) and a full workspace `tsc --noEmit` both pass.
