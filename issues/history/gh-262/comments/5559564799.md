## Summary

`passesItemRelationFilter` (in `backend/packages/data/src/scheduler/itemRelationFilter.ts`), which gates the `newEmail` heartbeat's `core.agentRun` action on a fired item's related-folder properties, had two bugs:

1. **No partition pruning**: `items` is `PARTITION BY LIST (database_id)`, but the query joined `items related` purely on `id`, forcing Postgres to scan every database's partition instead of pruning to the one the related item actually lives in.
2. **No soft-delete guard**: the query didn't check `deleted_at`, so a soft-deleted folder (e.g. a removed Junk folder) could still count toward the `include`/`exclude` sets.

**Fix**: resolve the related item's `database_id` via the relation definition's other-side property (joining the small unpartitioned `properties` table) and pin it in the `items` join condition — mirroring the pattern already used in `rollup/recompute.ts` — plus add `related.deleted_at IS NULL`.

**Test coverage**:
- `newEmailHeartbeat.test.ts` — soft-deletes a Junk folder mid-flight and verifies the `newEmail` action still fires once the deleted folder no longer blocks it.
- `itemRelationFilter.test.ts` (new) — runs `EXPLAIN (ANALYZE, FORMAT JSON)` against a database seeded with ~19 `items_p_*` partitions and asserts only the related item's own partition is actually executed at runtime, verifying the partition-pruning fix.

Both review findings from the earlier CI pass (missing join predicate risking a cross-item match, unguarded non-null assertion) were fixed in the test file.
