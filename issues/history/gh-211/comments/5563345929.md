## Summary

This implements issue #211: normalizing the relation edge contract and making create/update/delete operations idempotent, with endpoint validation.

**Changes:**
- Standardized types: `RelationEdge` (was `ItemRelationRow`), `CreateRelationInput`, `UpdateRelationInput` — all keyed on `(relationPropertyId, callerItemId, targetItemId)`.
- Renamed every relation-edge caller's `itemId` field to `callerItemId` (mail ingest/draft/send/attachments/folder-discovery/reconcile, `advanceTaskRecurrence`, `inbox/*`, and tests) — no relation edge input accepts `itemId` anymore.
- Added `updateRelationWithClient`/`updateRelation`: requires an existing normalized edge, replaces metadata in full, otherwise raises `404 not_found` with `{ resource: 'relationEdge', relationPropertyId, callerItemId, targetItemId }`.
- `createRelationWithClient`/`createRelation`: idempotent on the normalized tuple, full metadata replacement (including back to `{}` when omitted), now returns the normalized `RelationEdge`.
- `deleteRelationWithClient`/`deleteRelation`: idempotent, returns `void`, and deliberately skips endpoint validation so cleanup of a dangling edge to a since-deleted item still succeeds.
- Added endpoint validation: a caller/target item must exist, not be soft-deleted, and belong to the database declared by the relation property's own `database_id` (source) and `config.targetDatabaseId` (target) — rejects missing, soft-deleted, reversed, or cross-database endpoints with `validation_failed`. A relation property with a missing/invalid `relationDefinitionId`/`targetDatabaseId` in its config is rejected at load, never inferring the target.
- Added `__tests__/relationEdgeContract.test.ts` (13 new integration tests against real Postgres) covering all of the above.

**Verification:** typecheck clean, full backend build passes, full backend test suite passes 326/326 (including the 13 new tests), no regressions.
