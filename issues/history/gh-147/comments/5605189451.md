## Summary

Closes #147 ("[system-i18n 05/05] Localize API and agent-manifest projections").

`generatePermissionManifest` (`backend/packages/data/src/manifest/permissionManifest.ts`) now accepts an optional `{ moduleRegistry, locale }` and resolves database names, property names, and select/multi_select option labels through the `resolveCatalogLabel` fallback chain (explicit stored override → requested locale → English → raw key). A database's `owner_module_id` column stores the database *key*, not the owning `ModuleManifest.id`, so the resolver first builds a `key -> moduleId` map from `ModuleRegistry.getDatabases()` before loading catalogs — getting this wrong would have silently resolved nothing. `createDriftCheckAction` threads the same options through so its resolvability check also validates catalog resolution when a registry is supplied. Callers that omit `moduleRegistry` (every existing call site) keep the exact pre-#147 raw-key placeholder behavior, so nothing regresses.

No live HTTP endpoint currently serializes databases/properties/options/agent-tools (confirmed `routeMatrix.ts` is exhaustive), so this issue's "API response serializers" requirement is delivered as the shared, reusable resolver wired into the one real projection that exists today (the AGENT.md manifest), ready for a future endpoint to reuse without further resolver work.

New integration tests cover: cs/en catalog resolution for a system database's name, a property's name, and select-option labels; English fallback; raw-key fallback when no registry is given; explicit overrides winning over the catalog in every locale; and byte-for-byte preservation of user-authored (non-system) database names.
