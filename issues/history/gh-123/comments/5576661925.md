## Summary

Implements issue #123: seeds a Semprec-owned `mcpServers` system database and wires it into the propose/confirm flow so a human can attach credentials without ever exposing them to the AI-authored proposal path.

- **New system database** `mcpServers` (`seedMcpModule.ts`): `name`, `connectionConfig` (strict `stdio`/`sse`/`http`-discriminated JSON schema in `mcp/mcpConnectionConfig.ts`), `active`, plus system-owned `syncStatus`/`lastSynced`. Seeded via a dedicated "MCP" project item, following the existing `seedEmailModule` pattern, wired into `seedSystem.ts`.
- **Proposal validation** (`mcp/mcpServerProposal.ts`, hooked into `assertValidProposalEnvelope`): rejects any credential-shaped field (`credential`, `apiKey`, `token`, `secret`, `password`, etc.) outright, and enforces `connectionConfig` strictness for any proposal targeting `mcpServers`.
- **Credential attachment on confirm** (`proposalActions.ts`): `confirmProposalWithClient` gained an optional `credential` parameter — a human-supplied secret stored via the existing `external_credentials` store in the same transaction as the item creation (atomic: either both persist or neither does), and rejected for any non-`mcpServers` target.
- `syncStatus`/`lastSynced` are `owner: 'system'`, which structurally blocks both the proposal path and any future agent path from touching them or triggering a sync — no MCP-specific sync-blocking code needed (sync itself is out of scope, deferred to issue #125).
