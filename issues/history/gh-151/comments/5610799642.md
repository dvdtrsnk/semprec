## Summary

Implements issue #151: delivering committed notifications through Web Push and APNs.

- **`writeNotification`** enqueues one `notificationFanout` graphile-worker job per genuinely-new notification, keyed by the notification's own id.
- **`notificationFanout` job handler** loads every active `push_subscriptions` registration for the notification's user and dispatches each through its channel's adapter — Web Push (VAPID) or APNs (HTTP/2, cached ES256 provider JWT, sandbox/production host from `apns_environment`).
- **`push_deliveries`** (migration 0032) is the durable per-(notification, registration) dedup key guaranteeing exactly-once delivery across job retries.
- Transient failures retry via graphile-worker; permanent provider rejections (404/410/`BadDeviceToken`) invalidate only the reported registration via #150's invalidation mechanism.
- Payloads to providers are limited to `notification_id`, `title`, and `link_href`.

## Review fixes (this update)

Addressed all four findings from the latest automated code review round on PR #362:
- **High:** `getNotificationById` and `getPushDeliveryStatuses` called `client.query()` without a generic type parameter, so `rows` was `any[]` and the hand-written row shapes on the consuming code performed no actual check. Both now use `client.query<RowShape>(...)`.
- **High:** the APNs response `reason` field was read via an unchecked `as` cast on parsed JSON from an external API; a non-string value would have silently defeated the `BadDeviceToken` comparison and retried a permanently-dead device token forever. Extracted into `extractReason()`, which validates the shape before returning it.
- **Medium:** the APNs response body accumulator had no size bound. Added a 64 KiB ceiling that fails the request if exceeded.

(A prior review round's three findings — duplicated alert body, missing request timeout, and a socket leak on HTTP/2 client-level errors, all in `apnsAdapter.ts` — were already fixed and confirmed by CI as resolved.)
