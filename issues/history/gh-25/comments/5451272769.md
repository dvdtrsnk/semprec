Done. Merged to develop as b1de2fcc85511b3f5e11d38e2b38ae6f43ba10a4.

Implemented the generic library-module contract on top of the schema engine (issue #21), with Books and Movies/TV as two concrete instantiations sharing the same seven-slot contract (coverKey/subtitleKey/ratingKey/secondaryRatingKey+Label/sourceUrlKey/statusKey/coverGlyph). Key pieces: `item_automation` table (status/error/attempts/last_attempt_at, locked settable only by explicit user/AI-permission call, never by the heartbeat) replacing the old ad-hoc processed boolean; cover images through the existing `blobs` table (issue #24); a `processLibraryMetadata` graphile-worker job (`max_attempts: 3`, `jobKey: library-metadata:${itemId}`) plus a separate daily heartbeat that re-queues `status='error'` rows; a single generic create-item path shared by UI and AI (no special AI path); the Movies→People "Watched with" ratable relation storing `{ rating }` on the `item_relations.metadata` edge, not on either item; `year` changed to type `number`.

Note for the next issue's agent: this PR needed one manual fix before merge — issue #25's original `item_automation` DDL specified `item_id uuid PRIMARY KEY REFERENCES items(id) ON DELETE CASCADE`, which is impossible under Postgres given `items` (issue #21) is `PARTITION BY LIST (database_id)` with composite PK `(database_id, id)`. The issue text has been corrected to the same no-FK, app-layer-referential-integrity pattern already used in migrations 0001-0004 (`item_relations`, `task_recurrence`, `view_items.item_id`, `docs.item_id`). If a future issue in this queue specifies a bare `REFERENCES items(id)` FK, that is very likely the same stale-spec issue, not a real requirement — check the established pattern before implementing literally.
