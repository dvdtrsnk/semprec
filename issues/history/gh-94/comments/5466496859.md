## What was implemented

- **Background PEEK semantics**: confirmed the underlying `imapflow` library builds `BODY.PEEK[...]` internally for every `fetch()`/`download()` call with no non-peek option — so `ImapFlowMailClient`'s existing background fetch paths (`fetchMessagesSince`, `downloadText`, attachment streaming) already never set `\Seen`, structurally, by construction. Added `ImapMailClient.markSeen(path, uid)` (`imapFlowClient.ts`) as the **one** explicit mark-read path, backed by `STORE ... +FLAGS (\Seen)` — nothing in the reconcile pipeline calls it; it exists for a future explicit user/UI mark-read action to call.
- **Per-account IMAP concurrency limiter** (`mail/imapConnectionLimiter.ts`): an in-process, per-account semaphore (`createImapConnectionLimiter`/`sharedImapConnectionLimiter`) with provider-aware default caps (Gmail 5, iCloud/Outlook 3, generic 2 — deliberately well under documented provider maximums since this worker is never an account's only IMAP client), overridable via a new `Mailboxes.connectionLimit` property (`owner: 'user'`). Wired around the IMAP branch of `handleSyncMailAccountTask`. Queued callers past the limit wait up to 3 minutes before timing out (rather than hanging forever behind a stalled connection); raising the limit mid-wait wakes queued callers immediately.
- **Provider-aware connection-limit backoff**: added `MailConnectionLimitError` (`providerTypes.ts`) and `isImapConnectionLimitError` (`imapFlowClient.ts`) — the latter detects imapflow's connect-failure shape (an untagged `BYE`/`ClosedAfterConnectTLS`/`ClosedAfterConnectText`) **and** requires the reason text to actually match a connection-limit phrase (Gmail's "Too many simultaneous connections" etc.), so a TLS-cert failure or other pre-auth closure sharing the same imapflow error code is never misclassified as contention. `handleSyncMailAccountTask` catches this specifically, records a provider-aware backoff via the new `recordConnectionLimitBackoff` (`mailAccountSyncStateStore.ts`, reusing the existing `next_expected_activity_at`/sweep mechanism, just with a longer, provider-tuned delay than the generic 15-minute backoff), sets `syncStatus: 'error'` (mail genuinely isn't syncing, and it clears back to `'ok'` the same way any other error does, via the next successful pass), and **returns instead of rethrowing** — so the retry comes only from the existing periodic sweep, not also from graphile-worker's own immediate job-level retry stacked on top of it.
- No DB migration needed: the connection-limit backoff reuses `mail_account_sync_state`'s existing columns; `connectionLimit` is a new Mailboxes item property (JSONB, seed-layer only).

## Notes for dependent issues

- There is still no real composition root anywhere in this repo that opens an actual `ImapFlow` connection (`createImapClient` is only ever a test fake) — whoever builds that composition root is expected to catch `ImapFlow.connect()`'s rejection, run it through `isImapConnectionLimitError`, and throw `MailConnectionLimitError` when it matches; this issue only wired the detection + backoff + limiter machinery on the `@semprec/data` side, not the actual socket layer.
- `markSeen` has no caller yet — a future mailbox-UI/API issue that adds an explicit "mark as read" action should call `ImapMailClient.markSeen(path, uid)` (or the Gmail/Graph adapters' own equivalents, which this issue did not touch — only IMAP was in scope) inside the same per-account `imapConnectionLimiter` used by background sync, to keep the concurrency guarantee intact once a second real caller exists.
- `Mailboxes.connectionLimit` is a plain optional `number` property with no validation UI yet; a future settings/onboarding UI should surface it as an advanced override, not a default-visible field.
