Done. Merged to develop as 71c26766d80af278b879163e933cb578a903b58e.

Implemented the Yjs CRDT layer for page blocks and canvas per the issue spec: `docs`/`doc_snapshots`/`doc_updates`/`doc_snapshot_history` tables (migration `0003_docs.sql`, with the same no-Postgres-FK deviation on `docs.item_id` as `item_relations`/`view_items`, since `items` is list-partitioned); lazy doc creation on first content-write (`docsStore.getOrCreateDoc`); a headless `Y.Doc` engine (`docPersistence.ts`) with `gc=false`, `mutateDoc`/`doc.transact(fn, origin)` capturing each write as a `doc_updates` row with `created_by` attribution; compaction (lazy-on-read + a `docCompactionSweep` queue job every 5 min, threshold 200, single-transaction store-then-delete) that also drops a `doc_snapshot_history` checkpoint at the same instant, so version reconstruction can't silently lose granularity to a compaction that ran between two periodic squash sweeps; a daily `docHistorySquash`/`docHistoryCleanup` pair for the general case; `openDocVersionAt` reconstructs "nearest checkpoint + remainder," and now raises a clear `ValidationError` (instead of returning wrong data) for a timestamp that falls in a window a compaction has already made unrecoverable — this is a structural limit of periodic-checkpoint designs, not a bug, and is documented as such. Blocks (`Y.Map` with `sys:id`/`sys:flavour`/`sys:children`) and canvas elements (typed, `xywh` + fractional `index`) get generic CRUD via `createDocStore(pool)`, itemId-based, sufficient for both a future editor UI and direct agent writes.

`@semprec/realtime` was an empty stub; this issue built its first real implementation: a minimal Postgres LISTEN/NOTIFY → WebSocket fan-out (`startRealtimeServer`) on one shared channel (`semprec_realtime`), carrying both `item_invalidation` and `doc_update` frames distinguished only by `type`. `wireRealtimeHooks(pool)` wires the data layer's `realtimeHook.ts` (now also exposing `setDocUpdateHook`/`notifyDocUpdate`) to real `pg_notify` publishing — call it once at whichever process's startup owns the write pool.

Notes for dependent issues (the ten hardcoded databases, #24, will be the first real consumer):
- `createDocStore` is deliberately a separate mechanism from `createChokePoint` — two independent persistence/merge stores, per the issue's design, not unified.
- The direct `ai_agent` write path in `createDocStore` (no approval-queue routing) is an explicit, issue-scoped exception to the state-writes "agent proposes, never writes" rule, documented at `docStore.ts`'s top comment — `created_by` attribution is the substitute audit mechanism until agent-runtime/approval-queue exist.
- Realtime presence/Awareness is still not implemented (deferred per the issue) — the WS envelope's `type` discriminator is ready for it to ride the same channel later.
- `pg_notify` has an ~8000-byte payload cap; an oversized `doc_update` frame just skips the live push (logged) — the update is already durably persisted in `doc_updates` by that point, so a client recovers by reloading. Chunking wasn't built (kept to the issue's "minimal fan-out" scope).
