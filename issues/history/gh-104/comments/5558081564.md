## Summary

Implements issue #104: extends `semprec.tick` (from #223) to close the remaining gaps so every Inbox source ends in an explicit state.

- **Missing/deleted type → `needsClarification`**: a source with no `type`, or one whose `type` references a deleted Inbox item type, now goes through the same single code path into `needsClarification` with no pre-filled `proposal`, creating the row if none exists or revising an unlocked one.
- **Deleted source → `invalid`**: when the tick's source item no longer exists, its unlocked proposal transitions to `invalid`; a locked (`confirmed`/`rejected`) proposal is left untouched.
- **History log**: every create, revise, or status change now appends one `{ author: 'ai', message, at }` entry to `history`, replacing the `[]` stub from #223.
- **Envelope validation**: a computed `{ entityKind, target, properties }` envelope is validated against its destination's actual requirements before being stored as `proposed` (existing non-archived target database and only known, writable, non-relation/rollup/system properties for `database`; an existing target item and a `flavour` block field for `pageContent`). A failing envelope is stored as `needsClarification` instead, and validation never writes to the destination.
- Both new needsClarification/invalid transitions are locked-card-aware and idempotent, so repeated ticks against an unresolvable item don't spam history or re-invoke the injected AI compute function.

Existing `#223` tests were updated where they asserted the now-superseded stub behavior (`history: []`, "no type creates no proposal"), and a new test group covers deleted-type parity with no-type, deleted-source invalidation (locked vs. unlocked vs. absent), and envelope-validation rejections.
