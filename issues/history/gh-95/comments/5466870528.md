## What was implemented

- **`email.draft.create`** (`mail/draft.ts`): the generic item-create path (`createItemWithClient` + `allowedSystemKeys`, same convention as `mail/ingest.ts`), linked into the mailbox's Drafts folder. No authorization check at all — per issue #95/epic #92, drafting is always allowed for any actor.
- **`email.send`** (`mail/send.ts`): `assertEmailSendAuthorized` runs first, before any DB write or SMTP call — a `{ type: "user" }` actor always passes; a `{ type: "ai_agent", manifest }` actor needs `manifest.capabilities.email.send.autonomous === true`, else `ForbiddenError` (403), with the draft completely untouched and no approval-queue row (none exists in this codebase, by design). `capabilities.email.send.autonomous` is a new field on `PermissionManifest` (`manifest/permissionManifest.ts`), sourced from a deliberately **undeclared** raw item property (`emailSendAutonomous`) on the Email project's own item — not part of Projects' formal schema (so no other project gets an unused field), and with **no writer anywhere in the code**: granting it requires direct DB access, which is the intended "project-level authorization decision."
- **Sending flow**: validates `from.address` against the mailbox's registered `Mailboxes.addresses` (rejects From-header spoofing), generates an RFC 5322 Message-ID, then *claims* the draft by writing `mail_message_meta` **before** calling SMTP — `item_id` is that table's primary key, so two concurrent/retried sends of the same draft can't both get through; the loser gets `ConflictError` before ever reaching SMTP. On successful send, the draft item is finalized (subject/body/date) and its folder membership moves from any `specialPurpose: 'drafts'` folder to the mailbox's `specialPurpose: 'sent'` folder. On SMTP failure, the claim is deleted (best-effort) so a genuine retry can still send.
- **SMTP transport**: `mail/smtpClient.ts`'s `NodemailerSmtpClient` wraps an already-authenticated `nodemailer` transporter (mirrors `ImapFlowMailClient`'s "no real composition root yet" shape) with a 30s send timeout enforced independently of the transporter's own config. `nodemailer`/`@types/nodemailer` added as direct deps of `@semprec/data`.
- **Reconciliation**: reuses `ingestEmailMessage`'s existing `mail_message_meta.message_id` dedup — a later IMAP/Gmail/Graph sync pass that observes this same generated Message-ID in the real Sent folder converges onto the same item instead of duplicating it (covered by a dedicated test).
- Test coverage: `packages/data/src/__tests__/mailSend.test.ts` (16 cases) — draft creation, authorization for user/ungranted-agent/granted-agent, exactly-once send + folder move + Message-ID storage, the 403-leaves-draft-unchanged case, concurrent-send race, SMTP-failure-then-retry, From-address spoofing rejection, missing-adapter error, and IMAP-reconcile dedup convergence.

## Notes for dependent issues

- No HTTP/agent-tool layer exists yet anywhere in this repo (confirmed empty stubs in `backend/modules/`, `agent-runtime`, `module-registry`) — `createEmailDraft`/`sendDraftEmail` are library functions a future composition root will call directly, the same relationship `mailSyncJob.ts`/`ingestEmailMessage` already have to their still-nonexistent HTTP layer. Whoever builds that layer needs to derive `SendEmailActor` from the real request context (`{ type: "user" }` for an authenticated session, `{ type: "ai_agent", manifest }` — generated via `generatePermissionManifest` — for a call made from inside an agent run).
- `NodemailerSmtpClient` takes an already-constructed `nodemailer.Transporter`; building that transporter (OAuth2 token exchange vs. app-password, per `Mailboxes.provider`) is that same future composition root's job, not `@semprec/data`'s — exactly mirroring `ImapFlowMailClient`'s existing "no real composition root yet" note.
- Granting `capabilities.email.send.autonomous` today requires a raw `UPDATE items SET properties = properties || '{"emailSendAutonomous": true}' WHERE id = <email-project-item-id>` — there is no settings/admin UI for it, intentionally out of scope here.
- Mailbox UI (issues #96-98) can rely on: Emails items becoming "Sent" via folder-relation membership to a `specialPurpose: 'sent'` Folder (no separate status field), and drafts being identifiable via `specialPurpose: 'drafts'` folder membership with no `mail_message_meta` row at all (a draft has no Message-ID until sent).
