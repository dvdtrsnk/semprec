**What I verified directly (not just inferred):**

1. **`web/` is a true empty scaffold.** It contains only `README.md` and `review-rules/`. `web/review-rules/context.md` states explicitly: *"The codebase is currently an empty scaffold — no framework has been chosen yet... These rules apply from the first real implementation PR onward."* `git log -- web/` shows zero feature commits, ever. So #96 would be the very first web implementation PR — yet its body asks me to "follow the existing client tokens, i18n, loading, empty, and error conventions," none of which exist anywhere in the repo (no `cs.json`/`en.json`, no design-token file, no component library, no test setup).

2. **No transport layer exists between any client and the backend.** `packages/realtime/src/wsServer.ts` is a one-way LISTEN/NOTIFY change-broadcast only, and its own doc comment says *"the caller owns `wss` (and whatever HTTP server it's attached to)"* — but no HTTP server exists anywhere in this repo (`express()`/`fastify(`/`app.listen` all return zero hits outside one unrelated test file). There is no request/response channel at all for a browser to call `listItems`, `queryView`, or anything else in the choke point.

3. **No public generic API exists to read items across a relation.** `ChokePoint`'s public surface (`backend/packages/data/src/chokePoint/chokePoint.ts`) only exposes `createRelation`/`deleteRelation` — writes, not reads. The actual relation-read helpers (`listRelationsForItem`, `otherSide` in `relationsStore.ts`) aren't even exported from the package's `index.ts`, and the view filter DSL (`filterTree.ts`/`filterCompiler.ts`) has no relation-type filter node. "Filter through the Emails-to-Folders relation... use generic query/item operations" has no existing generic path to call today, in-process or otherwise.

4. **No `read`/unread field exists on Emails.** `backend/packages/data/src/mail/search.ts` has a standing comment: *"there is no read/flags property anywhere in this issue's scope... belongs to whichever issue adds a 'mark as read' UI action."* #96 explicitly puts "triage shortcuts" out of scope (that's #97, "Add mailbox triage interactions"), so the "unread counts" acceptance criterion has no backing data field and no in-scope way to add one here.

**Why I'm not building these myself:** picking a web framework, designing and exposing an authenticated HTTP/WS API surface over the choke point, and adding a public generic relation-read method are irreversible architectural and security decisions that affect the whole `web/` platform going forward, not just this view. They're well beyond "no new abstraction... beyond what the current issue's Zadani asks for," and getting the auth/transport model wrong here would be expensive to unwind later.
