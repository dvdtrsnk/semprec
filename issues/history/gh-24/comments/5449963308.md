Implemented all ten hardcoded databases (areas, projects, tasks, people, files, events, healthRecords, companies, transcripts, journal) as full instances of the generic schema engine (issue #21), with real `relation_definitions`/`item_relations` for every relation the spec names — including the bidirectional pairs and the three explicit mock-inconsistency fixes (Projects↔Companies, Events↔Companies unified into real relations; Health records↔Areas made bidirectional). Seeded a default `created_by: 'system'` Table view for every database, plus Journal's own `temporal-switcher` view type (scoped to Journal only, not built as a general concept). Added the shared `blobs` table backing Files' `file` property, and the `task_recurrence` table with a fully-atomic rolling-model advance (`advanceTaskRecurrence`, single transaction, row-locked to survive concurrent advances, carries forward relation edges including one-directional ones). Journal gets lazy, idempotency-key-based item creation on first write — no manual "+ New". `segments`/`summaryByInstruction` were deliberately *not* added as Transcripts properties (they belong in `items.computed`, written later by the transcription pipeline).

Notes for dependent issues:
- Existing `seed/seedSystem.ts` (issue #21) now composes `seedTenDatabasesInTransaction` for the Projects database (which already existed with a minimal schema) rather than defining a second, competing Projects DB — the Semprec bootstrap project and System settings DB are created after it.
- The ten databases are addressable by `databases.owner_module_id` (not a new `databases.key` column — `owner_module_id` already served that purpose from issue #21's seed) using the constants in `seed/tenDatabaseKeys.ts` (`AREAS_MODULE_ID`, `PROJECTS_MODULE_ID`, etc., values exactly `areas`/`projects`/.../`journal`).
- The choke-point gained `createItemWithClient`/`updateItemWithClient`/`createRelationWithClient`/`createRelationPropertyWithClient` (chokePoint.ts) — client-scoped versions of the public API for callers that need multiple writes to be atomic within one transaction (or, for Journal, a narrowly-scoped `allowedSystemKeys` escape hatch to write its own owner:'system' fields). Issue #26 (Email/inbox, owner:system fields like `person_email_index`) or the future transcription pipeline (Transcripts.status/date/link, also owner:system) should reuse this pattern rather than bypassing the choke-point directly.
- `PROPERTY_TYPES` (types.ts) gained `title`/`checkbox`/`time`/`longText`/`color`/`file`/`url` — filter/sort compilers treat all new types as plain text unless a type-specific need arises later.
- Issue #25 (Books/Movies) can reuse the shared `blobs` table for cover images as planned.
