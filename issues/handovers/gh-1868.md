## What was delivered

A new id-less realtime invalidation scope `sempStatus` that tells every socket of the tenant that the Semp status (problems and the service state derived from them) changed.

- Frame: `{ type: "invalidate", scope: "sempStatus" }` and nothing else. `parseRealtimeMessage` and `parseServerFrame` keep nothing but the scope, so a message that carries more is delivered without the extra fields and no problem text can leave the server. Added to `InvalidationEvent`, `RealtimeMessage`, `OutboundFrame` and the invalidate case of `syncServer.ts` (`sendToTenant`, tenant-wide).
- Publisher: `publishSempStatusInvalidation(client)` in `data/src/sempStatus/sempStatusInvalidation.ts` (`runAfterCommit`).
- Publication points in `data/src/semp/sempProblemsStore.ts`: `raiseProblem` publishes when it created a problem, escalated it or counted a new occurrence of an active one; `resolveProblem` publishes when it resolved a row. A replay of an already counted occurrence that raises no severity, a resolve that changes nothing, a second resolve, an unknown key, an unknown resolution kind and a raise refused for an invalid project publish nothing.

## Entry points and contracts dependents build on

- Wire scope `sempStatus` with exactly the keys `type` and `scope`. A client refetches the Semp status on it.

- Semp problems have two writers only, `raiseProblem` and `resolveProblem`; the prune task deletes only already resolved rows, which are not part of the status.

## Deviations and spec seams

1. The problems store of gh-1459 is `semp/sempProblemsStore.ts` with `raiseProblem` and `resolveProblem` only. There is no separate merge or service-change function: a merge is a raise that finds an active problem, and the service state is derived from the problems at read time, so those two functions cover every stored change.
2. The `InvalidationEvent` variant carries an optional `userId` for the same union-wide reason as `projectAgent`; the frame is tenant-wide and the parser drops it.
3. One frame per write rather than per transaction, as the `projectAgent` precedent and the wording "once per such write" prescribe.
4. The serverFrame test is in the existing `serverFrame.unit.test.ts`, not `serverFrame.test.ts` named in Touches.
