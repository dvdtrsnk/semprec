## What was delivered

- The Semp turn handler (`services/semprec-agents/src/sempMessageTask.ts`) raises the active `agents` problem of a reply (kind `reply`, severity `warning`, source `semp_messages` / the failed message id, dedupe key `agents:reply:<reply_to_message_id>`, occurrence key the message id) in the same transaction that stores an error result or a done-but-incomplete result (`deriveReplyOutcome` of the summary steps is `incomplete`). A turn that ends with error code `cancelled` raises nothing. An interrupted turn raises like an error.
- The same handler resolves the problem as `recovered` in the transaction that stores a complete successful result.
- A failed retry merges into the same problem (occurrence count 2, 3, ...), because every attempt of one reply shares the key.
- Fix round: the store option `followLatestSource` moves `source_id` to the newest failed attempt on a merge that counts a new occurrence, so the status view's retry and open-chat actions (built from `source_id`) target the attempt that can be retried. `repairInterruptedSempMessages` (startup repair of a crashed process) now raises the problem of each repaired reply in its own transaction.

## Entry points and contracts dependents build on

- `raiseAgentReplyProblem(client, assistantMessageId)` and `resolveAgentReplyProblem(client, assistantMessageId)` (`semp/agentReplyProblems.ts`, exported from `@semprec/data`). Both read `reply_to_message_id` of the assistant message themselves and run in the caller's open transaction. `raiseAgentReplyProblem` returns `null` and raises nothing for a message that answers nothing or a tenant with no bound user; `resolveAgentReplyProblem` returns whether a problem was active.
- `agentReplyProblemKey(replyToMessageId)` in `semp/agentProblemKeys.ts` builds `agents:reply:<id>`.
- `RaiseProblemInput.followLatestSource` (`semp/sempProblemsStore.ts`, default `false`): a merge that counts a new occurrence sets `source_id` to the new source; a replayed occurrence cannot move it back. Other raisers are unchanged.
- The problem holds no user content; the thread is reached through `source_id` -> `semp_messages.thread_id` (there is no references column), which `sempStatusReport` already does for kind `reply`.

## Deviations from the specification and spec seams

1. The adapter is `semp/agentReplyProblems.ts`, not `sempProblems.ts`, next to `agentProblems.ts` of gh-1911; the key builder sits in `agentProblemKeys.ts`.
2. The adapter reads `reply_to_message_id` from the assistant message row itself and gets the tenant user through `getTenantUserId`, so it works when the handler's turn lookup found no source.
3. `semp_problems` has no references column; the thread id is reached through `source_id`.
4. The first version left `source_id` on the first failed attempt after a failed retry (the store never moved it); both reviewers raised it and the fix round added the opt-in store option `followLatestSource`, a small change in the store that owns `semp_problems`, outside the original Touches.
5. The commit trailer of the worker used the session's attribution line instead of the line in the task text.
