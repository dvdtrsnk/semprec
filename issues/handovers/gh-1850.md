## What was delivered

- The transcript match step also considers virtual occurrences of live recurring standup and meeting series: `expandEventOccurrences` over the local days of the recording, with the same strict interval rule as stored Events. A virtual occurrence is never linked directly. `matchTranscriptToEvent` returns `ambiguous` with the stored candidates first and `{ seriesId, occurrenceDate }` candidates after them.
- `createTranscriptEventCard` stores the candidates in `context.candidates`; when the one candidate is an occurrence it proposes a relation to the synthetic id `<seriesId>@<date>`. The worker writes the card and nothing else: no Event and no edge.
- `assertValidProposalEnvelope` accepts a synthetic relation target through the new `calendar/eventOccurrenceTarget.ts` (`assertValidOccurrenceTarget`): the series is live and recurring and its rule gives the date. A confirm materializes the occurrence with `materializeEventOccurrence` inside the confirm transaction and links the real item, so the edge and the confirm result are the occurrence's item.
- The inbox card listing (`inbox/inboxCardsStore.ts`) reads a synthetic target through its series Event, so the listing does not fail on the uuid cast.
- A cancelled date, a stored occurrence item and a series of a type that is not matchable are not offered as virtual candidates.
- The series Event itself is not a stored candidate on a day on which its own rule gives an occurrence (`standsForItsFirstOccurrence` in `transcription/transcriptEventMatch.ts`), since that day is offered as the occurrence. A series whose own date its rule skips stays a stored candidate (fix `38d715708`).
- ADR `docs/adr/2026-11-13-a-transcript-card-links-a-virtual-occurrence-by-its-synthetic-id-and-confirm-materializes-it.md`.

## Entry points and contracts dependents build on

- `transcription/transcriptEventMatch.ts`: `TranscriptMatchCandidate = TranscriptEventCandidate | TranscriptOccurrenceCandidate`; `AmbiguousTranscriptEventMatch.candidates` and the input of `createTranscriptEventCard` carry that union.
- `transcription/transcriptEventCardContext.ts`: `transcriptEventCardContextSchema.candidates` is a union of the stored-Event object and `z.strictObject({ seriesId: uuid, occurrenceDate: string })`; its minimum length is 1 (a card may carry one occurrence), earlier 2.
- `calendar/eventOccurrenceTarget.ts`: `assertValidOccurrenceTarget`, the check of a synthetic relation target at card validation and revision.
- A `transcript` card's relation proposal may target a synthetic occurrence id `<seriesId>@<date>`; `confirmProposalWithClient` materializes it in the confirm transaction.
- No route, table, migration, job name or generic operation is added or changed.

## Deviations from the specification and spec seams

1. The series Event is excluded from the stored-candidate query on a day its rule gives, so that day is not offered twice; the Task does not state it. The first version excluded it always; the requirements reviewer found that a series whose own date its rule skips then matched nothing (regression of the stored-Event matching), and `38d715708` restricts the exclusion to days the rule gives.
2. The `context.candidates` schema became a union and its minimum became 1; the two assertions of `transcriptEventMatch.test.ts` on candidate fields were narrowed with an `'id' in` check.
3. The synthetic-target check lives in the new module `calendar/eventOccurrenceTarget.ts`, outside `Touches`, to keep `inboxTickAction.ts` small.
4. `inbox/inboxCardsStore.ts` changed (outside `Touches`): the listing cast the envelope target to `uuid[]`, which a synthetic id would fail; it reads the series Event instead.
5. The model recommendation still considers stored Events only (ranking by content is #1848, out of scope); a recommendation that names an occurrence is dropped.
6. The relation checks at card validation run against the series Event as a stand-in for the item that does not exist yet.
7. A confirm after the occurrence was cancelled is refused by the relation write (a `ValidationError` on `targetItemId`); the card stays proposed.
8. `transcriptionTask.ts` is untouched; only its test file got one test.
