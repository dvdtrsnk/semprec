# Handover: create an event in its chosen calendar in one idempotent request

Implementation commit `d45c3e094` on `fix/calendar-create-atomic` (from `feat/internet-accounts`). No backend change.

**Root cause.** `HttpCalendarRepository.createIn` created the Event with properties only. The server's create hook linked it to the default calendar in the same transaction, and `Events.calendar` is single-valued. The follow-up `PUT /api/items/:id/relations/calendar/:calendarId` then answered 409 `cardinality_violation`, which `ApiClient` maps to `REJECTED`. The sheet showed `newItem.rejected` ("Check the title and the time…"), the Event stayed in the default calendar, and the next tap created a second Event.

**Shared (KMP).**
- Data: the create `POST /api/databases/:id/items` sends the chosen calendar of an event as `relations: [{ propertyKey: "calendar", targetItemIds: [id] }]` (`CalendarCreateRequest.relations`, `CalendarCreateRelation`). An event without a chosen calendar and every task send no `relations`. There is no follow-up relation write any more; the task repetition (`PUT /api/tasks/:id/recurrence`) is unchanged.
- Every create sends `Idempotency-Key: <NewCalendarItem.submissionKey>`. `ApiClient.send` already had typed `extraHeaders`, so it did not change.
- Domain: `NewCalendarItem.submissionKey` (required). `CreateCalendarItem` answers `RepositoryResult<NewCalendarItemOutcome>`: `Created(itemId)` or `BreaksRules` (no title, a kind that is neither an event nor a task, an option out of range). Server failures stay `RepositoryResult.Failure`.
- Presentation: `NewCalendarItemViewModel` keeps the current submission privately (the form and its key, `Uuid.random()`). The same `Create` sent again after a failure reuses the key. `Edited`, or a form that differs from the last one, starts a new key. A form is compared because the server replays a key without reading the body again. After a created item the phase stays `SAVING` and the sheet closes, so the next sheet is a new ViewModel with its own key.
- Refusals: `REJECTED` (the form message) now means a form the rules refused (`BreaksRules`, or a schedule that cannot be one). A refusal by the server (400/409/422 → `REJECTED`) is shown as an unexpected failure (`failure = null`, `sheets.failure.unexpected`, "Something went wrong."). Other kinds pass through unchanged. The exported state, actions and effects did not change, so there is no Swift or Android change.

**Other create paths checked.** None makes a create plus a follow-up single-valued relation write, so nothing else changed:
- `HttpCalendarCatalogRepository.create`: properties only.
- Invitation answers and event duplicate: dedicated server routes.
- `HttpTaskRepository` and `HttpMeetingRepository`: already send relations in the create (`ItemWrites.create`).
- A task created from the calendar sends no relations.

**Moving an event to another calendar.** The calendar screens have no calendar picker for an existing event. The only path is the generic item screen's relation picker (`ItemPickerFlow.choose`). It calls `CollectionWrites.setRelation`, which sends `PUT /api/items/:id/relations/:propertyKey` with `{ "targetItemId" }`. On the server that is `relation.set`: one transaction that replaces the single target. It falls back to adding an edge only when the server refuses the replace as not single-valued (`REJECTED`). Existing tests cover it (`ItemViewModelTest` picker choice, `HttpCollectionWritesTest.relationsAreSetLinkedAndUnlinkedByTheirPropertyKey`), so nothing changed there.

**Tests.**
- `HttpCalendarRepositoryTest`: 27 tests.
  - A chosen calendar gives exactly one write: a `POST` with `relations` and the key, and no `PUT`.
  - The default calendar and a task send no `relations`.
  - Each create sends its own submission's key.
  - A 400 or 409 refusal fails without a change, and a missing database is not found.
- `CalendarUseCasesTest`: `BreaksRules` for a form that breaks the rules; a server refusal stays a failure.
- `NewCalendarItemViewModelTest`: 15 tests.
  - The key survives an unavailable and a refused attempt up to the success.
  - An edit, another title and another calendar each get a new key.
  - A new sheet gets its own key.
  - A server refusal is `failure = null`.

**Notes.**
- With initial relations, the server checks the chosen calendar through its relation edge hooks: `accountCalendarEventEdgeWriteHook` refuses a read-only account calendar. The hook's `lockChosenCalendar` does not run on this path. The sheet offers only calendars that take new events.
- If an attempt timed out but the server created the item, and the person then edits the form, the edited form is a new submission and creates a second item. That is intended: a different form is a different item.
