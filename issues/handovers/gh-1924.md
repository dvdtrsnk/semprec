## What was delivered

- `retainOverridesForEnvelope(previousAiEnvelope, nextEnvelope, overrides, targetPropertyKeys)` in `proposalOverrides.ts`, returning `{ userOverrides, userEditedKeys, reset, droppedKeys }`. The previous destination is `{ entityKind, target } | null`; with `null` (no or malformed stored envelope) nothing is retained and nothing is reported as dropped. When the destination (entity kind or target) changes, all overrides are cleared and `reset` is true; when it stays, only the overrides of the next envelope's primary ref whose key is a property of the target stay (for a non-database envelope, the keys of its `properties`); overrides of any other ref are dropped; an override that became equal to the new assistant value is removed silently.
- `reviseProposalWithClient` (user revise) loads the target database's property keys on the same client under its existing row lock, calls the helper, writes `userOverrides` and `userEditedKeys` (added to `allowedSystemKeys`), and when something was dropped appends a history entry of kind `reset` after the revise entry, listing the dropped `ref.key` names (no values). Wording when only some keys were dropped: "These manual values do not fit the new proposal, so they were dropped".
- After the review fix, the kept manual values are laid over the revise: `proposal` is `composeEffectiveEnvelope(envelope, retained.userOverrides)` (validated with `assertValidEnvelopeForCard` when edits stay), while `aiProposal` keeps the revise envelope as given, so confirm creates the entity with the kept values and a later values edit does not flip them back.

## Deviations from the specification and spec seams

1. Controller decision 2026-11-13: the retention code moved out of `proposalActions.ts` into `proposalRetention.ts` to keep that file under the 900-line cap after the integration tip grew (see gh-1892's handover). No behaviour change; the refreshed candidate was rechecked as pass.
2. The Task writes the reset history entry as an alternative to the revise entry; the Context says an entry is added. The revise entry carries the user's message, so it stays and the reset entry follows it, only when a value was dropped.
3. The previous destination is read with a zod `safeParse` of `aiProposal ?? proposal`, so a card with a malformed stored envelope can still be revised as before.
4. Overrides of refs other than the next envelope's primary ref are dropped, because the helper cannot know their databases (the multi-step branch is reachable only from #1947).
5. Originally the retained values were not laid over `proposal`; the requirements review found that this broke the #1892 invariant on the user revise path, and it was fixed (above). Thread revisions through `inbox.proposal.revise` stay with #1938.
