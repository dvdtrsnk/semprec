# Handover: catch up after every IMAP IDLE reconnect, keep reconnecting after a server close and end a connection that stopped idling

Commit on `fix/followup-idle-catchup`: `5d9939308`.

**Changes.**
- `imapIdleLifecycle.ts`: every established IDLE session (the first after `start()` included) enqueues `mailAccountSync` through the same tracked path as a signal (`requestSync`, joined by `stop()`, nothing once stop began). Info logs: `IMAP IDLE session started`, `IMAP IDLE session ended` with `reason` `server-closed` / `error` (+ `errorName`, `errorCode`) / `recycle` / `stop`, `IMAP IDLE reconnecting` with `attempt` and `delayMs`; fields `mailboxItemId` and `folder` only. Backoff schedule unchanged.
- `imapIdleClient.ts`: `closeClient` skips the LOGOUT when the close was already observed and treats imapflow's `NoConnection` refusal of it as the connection already gone; signal listeners attached before the SELECT; a watchdog (`IMAP_IDLE_CHECK_INTERVAL_MS` 60 s, `idleCheckIntervalMs` option) ends the session with `ImapIdleStoppedError` after two consecutive checks finding `client.idling` false, cleared before logout.
- `testSupport/fakeImapServer.ts`: `disconnectAll()` (BYE, then end of stream).
- `docs/architecture/domain-mail-and-inbox.md`: catch-up, watchdog, logs.

**Root cause found beyond the brief.** Before this change any server-side close (BYE or reset) made `close()` fail on imapflow's `NoConnection` LOGOUT refusal; the lifecycle took it as an owned cleanup failure and ended the folder's loop, so IDLE stayed dead until the lifecycle restarted, logged only as one `IMAP IDLE lifecycle failed` warning. This matches F33 (no IDLE record, no job) better than the reconnect gap alone; the unit tests mocked `logout`, so they never saw it.

**Checked, no gap.** imapflow's `maxIdleTime` renewal (same socket; the server reports buffered changes at the next IDLE and imapflow compares the EXISTS count); `mailboxClose` (only on our own commands or connection close). A server without IDLE capability is polled with NOOP every 2 minutes (latency, not a gap; Purelymail's capability was not checked against the server).

**Tests.** `imapIdleLifecycle.test.ts`: a reconnect after a clean close and after an error each enqueue exactly one sync (graphile `revision`) after the new session and none while it connects, with the session logs; stop during a reconnect enqueues nothing; loopback `FakeImapServer`: a delivery while the server had closed the connection is synced after the reconnect. `imapIdleClient.unit.test.ts`: signal during SELECT, close of an already closed connection without logout, `NoConnection` LOGOUT refusal, another refusal still fails, watchdog (fake timers, one non-idle check tolerated), watchdog stopped during close. `imapIdleLatency.unit.test.ts`: a server ending IDLE on an open connection ends the session (imapflow sent one IDLE only). Each new behaviour test failed against the code before the fix (the stop and other-refusal tests are guards).
