## What was delivered

- Relation `Threads.attachments` (system-owned by the emails process, `one_to_many` to Files, one-directional) in the shared Threads builder (`seed/seedEmailModule.ts`) and, for existing tenants, `runThreadAttachmentsCutoverMigration` (`mail/threadAttachmentsCutoverMigration.ts`), registered after the gh-1883 entry and before the area-note cutover in `db/tenantCutoverMigrations.ts`. The cutover is additive and idempotent and returns when Threads or Files is missing.
- `ingestAttachments` takes `threadItemId` and writes the `Threads.attachments` edge for every Files item it creates; `ingestEmailMessage` passes it (new `getMailThreadItemId` in `mailMessageMetaStore.ts`).
- Link rule `fileProjectFromThread` (`Threads.project` to `Files.projects` via `Threads.attachments`) declared in the mail manifest; the rule edge hook writes the `on` link row in the ingest transaction, also while the thread has no project. A change of the thread's project reaches the file through the `valueLinksPropagate` job.
- A merge of two threads (`reassignThread`): `repointThreadAttachmentLinks` moves the loser's attachment links to the winner before the generic edge move (`moveValueLinkItemSources` gained an optional `ruleKey`), and `propagateThreadAttachmentLinks` queues the recomputation for the winner. ADR `2026-11-14-an-attachment-inherits-the-project-of-its-thread-by-a-link-rule`.

## Entry points and contracts dependents build on

- Property `Threads.attachments` (relation to Files) and rule key `fileProjectFromThread` (`THREAD_ATTACHMENT_PROJECT_RULE_KEY` in `mail/threadAttachmentLinks.ts`); `Files.projects` stays `owner: user` and the `valueLinks` process writes it only while the file's link is `on`.
- `ingestAttachments(..., threadItemId)`; a tenant without the relation fails the ingest before any byte is stored, with nothing written.
- `repointThreadAttachmentLinks(client, loserItemId, winnerItemId)` must run after both Threads items are locked and before the generic move of the loser's edges. At the landing `reassignThread` plans the value merge of gh-1869 first, then repoints, then transfers the relations with the plan, finishes the value merge and queues the attachment propagation when links were repointed.
- A file attached to a draft from an existing Files item gets no edge and keeps its project.

1. Spec seam, merge order: the Task says to repoint after the generic edge move; that move deletes an `on` link whose last source is the loser, so the repoint runs before it (recorded in the ADR). 2. The relation is owned by the emails process because that process already writes the Emails attachments edge. 4. Edits beyond Touches: `threadAttachmentLinks.ts`, the optional `ruleKey` of `moveValueLinkItemSources`, `getMailThreadItemId`, an ADR, `testSupport/mailAttachmentFixtures.ts`, tests brought in line with the new relation and rule, and three tests that call `ingestAttachments` for a draft. 5. A file whose `Threads.attachments` edge moves before the winner's project edge in a merge can hold no project until the queued propagation job runs (ADR). 6. Landing: the thread value merge of gh-1869 queues the propagation jobs of every rule that follows `Threads.project` of the winner on every merge, so the attachment propagation is queued whether or not a link was repointed; three assertions of `threadAttachmentProject.test.ts` about an otherwise empty queue were changed (receipt).
