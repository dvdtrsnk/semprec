# Handover: notify about others' changes in synced calendars

Implementation commit `bfed67415` on `feat/internet-accounts`.

**What changed.**
- Kinds `calendar_event_added`, `calendar_event_changed`, `calendar_event_cancelled` in `NOTIFICATION_KINDS`, `notifications_kind_check` (baseline, edited in place) and `NOTIFICATION_KIND_POLICY`. They use a new category `calendarChanges`, are pushed, and arrive at `active`.
- Preference `calendarChanges`:
  - Column `notification_preferences.calendar_changes boolean DEFAULT true NOT NULL`. A missing row still answers the defaults.
  - Read and written by `notificationPreferencesStore.ts`; accepted by `PATCH /api/notification-preferences`.
  - Honoured by `pushInterruptionLevelFor`. With the switch off the row is still stored for the in-app list, but no push is sent.
- New `calendar/sync/calendarChangeNotifications.ts` (`notifyCalendarChanges`), called by `applyCalendarSync` inside its transaction, just before `recordCalendarSyncSuccess`.
  - What is notified:
    - Nothing in the account's initial sync (`initial_sync_completed_at` null).
    - Nothing from a calendar first created in this pass, since that is its own first sync.
    - Only calendars whose `notify` is true.
    - An added Event, a cancelled Event (one the provider deleted that was not already trashed locally), and a changed Event whose provider patch touches `name`, `date`, `endDate`, `timeFrom`, `timeTo`, `timeZone` or `place` with a value the Event did not already have locally.
  - That last comparison is the echo rule. A provider change that only repeats a local edit is not news. This covers a write-back echo and also a user edit that comes back from the provider.
  - Batching: up to 3 changes per calendar per pass give one notification each. More than 3 give one summary, kind `calendar_event_changed`, body "5 changes" / "5 změn" ("4 změny" for 4), `source_id` = calendar id, `link_href` null.
  - Copy:
    - Title `{calendar}`: the calendar's own name, else the provider's name, else the account name.
    - Body examples: "Peter added Dinner, Fri 19:00", "New event Swim, Sat", "Peter changed …", "Cancelled event …". There are en and cs versions.
    - The person is the snapshot organizer's name. It is left out when the organizer has no name or its address is one of the account's `addresses`.
  - Dedupe:
    - `transition_instance` = `<added|changed|cancelled>:<etag>`, or a sha256 of the canonical snapshot when there is no etag.
    - For a summary it is `summary:<sha256 of the sorted member instances>`.
    - These go through `notifications_tenant_dedupe_idx`, so a replay writes nothing.
  - Payload `{ eventId, calendarId }` (summary: `{ calendarId, count }`). `link_href` is `?page=event&id=<eventId>`.
- Fan-out (`apnsFieldsFor`): calendar change kinds send the APNs custom keys `event_id` and `calendar_id`. A summary sends only `calendar_id`. These are the keys the iOS `DeviceNotifications.target` reads (`event_id` opens the Event).
- `writeNotification` has a new optional `bodyParamKeys`: body parameters given as catalog keys and rendered in the recipient's locale. It is used for the weekday.
- `EventOutcome` in the apply now carries `news` for an update. The apply result shape (`added` / `changed` / `cancelled`) is unchanged.
- Doc: a "Change notifications" bullet in `docs/architecture/domain-calendar-tasks-and-media.md`.

**Tests.**
- New `__tests__/calendarChangeNotifications.test.ts`: 8 tests, runtime-role pool, fake provider, APNs fan-out with a fake sender. They cover:
  - initial sync is silent;
  - a remote add in a notify calendar gives one row and one APNs push with `event_id`/`calendar_id`, while a notify-off calendar in the same pass gives none;
  - the person is named or left out (own address, no organizer, all-day), and three changes stay individual;
  - a provider change of time and place is notified, a description-only change is not, and a deletion gives a cancellation;
  - five changes give one summary with only `calendar_id`;
  - a local edit sent back by the provider gives nothing (a mutation that disabled the echo check failed this test);
  - with the preference off the row is stored but there is no push;
  - a replay is written once.
- Updated: `notificationKindPolicy.unit.test.ts`, `notificationFanoutJob.test.ts` (calendarChanges switch), `notificationPreferences.test.ts` (new default and field).

**Deviations and seams.**
- "Someone else's change" means: applied by `calendarSync`, not in an initial sync, and not an echo of a local value. A change the user makes at the provider themselves (for example in Google's web UI) is notified without a person when they are the organizer. There is no reliable last-modifier field in the adapter contract.
- The write-back (`calendarEventPush`, sp-f10163b5) does not exist yet. Echo suppression therefore relies on the value comparison, plus the snapshot comparison the write-back will update. If a provider normalises a pushed value (for example whitespace), that would show as a change. The write-back issue should store the provider's returned snapshot, or skip notifying Events whose push is pending.
- "Changed" uses the organizer as the person, although the organizer need not be the one who changed the Event (spec decision).
- The weekday and time are the Event's own wall clock in its `timeZone`. They are not converted to the tenant zone, and no date is shown, matching the "Fri 19:00" example. A series shows the weekday of its first start.
- `link_href` `?page=event&id=` has no web page yet. The app opens the Event from `event_id`.
- The summary uses kind `calendar_event_changed`, because the spec allows only three kinds.
- The en and cs titles are both `{calendar}`, so the calendar name is the push title and the sentence is the body.
- Mobile: the shared `AccountNotificationDto` decodes with `ignoreUnknownKeys = true`, so the new `calendarChanges` key is tolerated. The settings screen does not show the switch yet (client follow-up). `SyncFrame`'s `TOPICS_BY_NOTIFICATION_KIND` does not map the new kinds.
- The new test repeats a slim account/provider setup instead of sharing `calendarAccountSync.test.ts`'s private helpers.
