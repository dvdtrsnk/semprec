## Delivered behavior

- **Relation cardinality** (`seed/seedTenDatabases.ts`): `Events.transcript` is `one_to_many` with Events as property A, the "one" side. The inverse `Transcripts.event` and both relation keys are unchanged. The trigger from `0013_relation_cardinality.sql` still refuses a second Event for one transcript (`item_b`), with `cardinality_violation`.
- **Populated-tenant cutover** (`transcription/eventTranscriptCardinalityCutoverMigration.ts`, new): takes the same `LOCK TABLE properties IN EXCLUSIVE MODE` as the other properties cutovers, then `UPDATE relation_definitions SET cardinality = 'one_to_many'` for the definition whose property A is `Events.transcript`, only where it is not already `one_to_many`. It writes no edge. A tenant without an Events database is skipped. Registered in `db/tenantCutoverMigrations.ts` right after `runTranscriptsCatalogCutoverMigration`.
- **Match** (`transcription/transcriptEventMatch.ts`, `matchTranscriptToEvent`): a single candidate Event is linked directly with `createRelationWithClient` even when that Event already holds other transcripts. The `eventEdges.length === 0` condition and the "single candidate already linked" branch are removed. Zero or several candidates still create one `kind = 'transcript'` proposal card. The `TranscriptEventMatchOutcome` and `matchTranscriptToEvent` JSDoc describe the new behavior.
- **Confirm** (`inbox/proposalActions.ts`): behavior unchanged; a link-existing card now succeeds for a second transcript on an occupied Event, and still returns `cardinality_violation` when the card's transcript is already linked to another Event. Only the comment at the edge-write description changed.
- **ADR**: `docs/adr/2026-10-29-events-hold-many-transcripts.md` (new, `accepted`, `supersedes: []`). It references `[[2026-09-23-transcription-worker-writes-event-match-results]]` and `[[2026-09-10-app-code-post-migration-steps]]`. The 2026-09-23 file is not edited.
- **Write-safety baseline** (`.github/scripts/write-safety-baseline.json`): one new entry for the cutover's idempotent `UPDATE`, the same shape as the Emails precedent. The regenerated baseline also dropped an unrelated stale entry (`mail/mailAccountSyncStateStore.ts::00bf30e2b322`); that line was restored so this change touches nothing else.
- No migration was added. The cutover is a TypeScript data cutover, so no migration number was reserved.

## Deviations and conflicts

1. **The Task asks for an "ADR addendum" to `2026-09-23-transcription-worker-writes-event-match-results.md`.** The Touches list says "new ADR file amending the transcription-worker ADR", and the repository's ADR rules forbid changing the body of an accepted ADR. The change is therefore a new standalone ADR that cross-references the old one and supersedes nothing, because the in-process write decision stays in force. The reviewer should confirm this reading.
2. **Acceptance 1 names `PUT /api/items/<eventId>/relations/transcript/<transcriptId>`.** No HTTP-level test was added (the Touches list names data tests only). The route's `putRelation` (`backend/packages/application/src/genericApplicationService.ts`) calls `chokePoint.createRelation`, which is the write the data tests exercise.
3. **The one test that asserted the 1:1 refusal was rewritten, not deleted.** `transcriptProposalActions.test.ts`: "leaves no edge and the card proposed when the relation write fails for a link-existing card" asserted that a second transcript on an occupied Event was refused. It is now two tests: the same transcript already linked to another Event is still refused (Acceptance 2, through confirm), and a second transcript on an occupied Event is accepted (Acceptance 1, through confirm). `transcriptEventMatch.test.ts`: "proposes a card rather than a second edge ..." now expects `linked` and no card (Acceptance 3).
4. **Pre-check in `relationOps.ts`.** `assertRelationTargetLinkableWithClient` still rejects a target that already holds an edge when the target is on side B of a `one_to_many`. Its only production caller is `assertValidEnvelopeRelations` in `inbox/inboxTickAction.ts`, for the `relations` of a `'database'` proposal envelope. For `Events.transcript` that target is the transcript, so an Event proposal that would link a transcript already linked elsewhere is still refused at proposal time, as the database would refuse it. This matches the new contract and needed no change.
5. **Web and mobile.** Neither `web/src` nor `mobile/` names a cardinality or assumes one transcript per Event; neither was changed.

## Notes for dependants

- **Rollback safety.** The schema change is a definition-only update, and old application code keeps working on the new definition: the old match still creates a card when the Event already holds a transcript, and the old confirm simply no longer meets the refusal. No edge is rewritten, so a rollback needs no schema work.
- **#1574, #1813, #1942 and #1743** can rely on an Event holding many transcripts and a transcript holding at most one Event. The database enforces only the second rule; code that needs "one transcript per Event" must check it itself.
- **v1 summaries.** Each part keeps its own summary. A combined summary is not built; a meeting-level summary may come later as notes on the Event.
- **Still out of scope:** a lightweight list of transcripts per Event (#1636), matching by interval overlap (#1813), recurring events and virtual occurrences (#1850).
