## What changed

- **Hook in `updateItemWithClient`** (`chokePoint/itemWrites.ts`): after `itemsStore.updateItemProperties`, a Tasks write whose patch sets `status: 'done'` calls `advanceTaskRecurrenceWithClient` with the system timezone (`getSystemTimezone(client)`). Because it runs inside the choke point's transaction, a failed `done` write (for example a stale `ifVersion`) also rolls back the new instance.
- **`advanceTaskRecurrenceWithClient`** is the client-scoped advance. It locks the recurrence row, creates the next `notDone` instance, carries the recurrence over, deactivates the old one and copies the relation edges. It does not write `done` itself; the caller's write does that. It does nothing when the task has no active recurrence. A second `done` write is also a no-op, because the first one set `active = false` under the row lock.
- **`advanceTaskRecurrence(pool, input)`** keeps its signature. It is now a transaction around `advanceTaskRecurrenceWithClient` followed by the `done` write. That write goes back through the hook, which finds the recurrence already inactive and does nothing.

## One departure from the issue

The issue said to put the new function in `advanceTaskRecurrence.ts` and have `itemWrites.ts` import it, accepting the import cycle between the two files. That cycle fails `pnpm run check:boundaries`: the repository's `no-choke-point-rollup-cycle` dependency rule forbids any import cycle involving `chokePoint/`. So instead:

- `advanceTaskRecurrenceWithClient` and `copyRelationEdges` live in a new module, `tasks/advanceTaskRecurrenceWithClient.ts`, which does not import `itemWrites.ts`.
- The item-create function (`createItemWithClient`) is passed in by the caller as a third parameter, typed `CreateTaskInstance`.
- `advanceTaskRecurrence.ts` keeps the pool-level wrapper and re-exports `AdvanceTaskRecurrenceInput`, so the public barrel export is unchanged.

The dependency check now reports no violations.

## Tests (`tenDatabases.test.ts`, integration)

All through `chokePoint.updateItem`, with no direct call to `advanceTaskRecurrence`:
- A recurring task set to `done` produces exactly one new `notDone` instance. The recurrence is carried over and still active on the new instance, and the old task's recurrence is `active = false`.
- A second `done` write on the old task creates nothing.
- A `done` write on a task without recurrence creates nothing.
- A `done` write with a stale `ifVersion` throws `ConflictError`. No instance is created, the task stays `notDone` and its recurrence stays active.

The existing recurrence tests pass without changes.
