Before every Inbox tick write to an existing proposal, the tick now re-reads the card under a row lock and checks it again. A confirm or reject that commits while the tick is waiting on the AI call is no longer overwritten; the tick skips its write instead.

## Why

`createSemprecTickAction` read the existing Processing proposal without a lock through `findExistingProposal`, called the injected `computeProposal` (the AI call), and then wrote `status: "proposed"` back with no version check. If a user's confirm committed in that window, the confirmed card went back to `proposed` with an out-of-date envelope. `writeNeedsClarification` and `invalidateProposalForDeletedSource` wrote from the same stale snapshot. `backend/review-rules/rules.md` requires the check that allows a write to run in the write's own transaction, on the row it writes.

## Changes

**`backend/packages/data/src/inbox/inboxTickAction.ts`**
- A new private helper, `lockUnlockedProposal(client, config, snapshot)`, re-reads the card with `itemsStore.lockItemById` (`SELECT … FOR UPDATE`). It returns the locked row only when all of these hold:
  - the row still exists;
  - it is not soft-deleted;
  - its status is not in `LOCKED_PROPOSAL_STATUSES`;
  - its `updatedAt` equals the snapshot's.
- Otherwise it logs `logger.info({ proposalId, reason }, "Skipping proposal write")`, with `reason` one of `gone | deleted | locked | changed`, and returns `null`. The logger is a module-level `createLogger("inbox-tick")` from `@semprec/shared`, following `docs/adr/2026-09-13-shared-structured-process-logging.md`.
- All three writes to an existing proposal call the helper first and return without writing on `null`: the revise write, `writeNeedsClarification`'s update branch, and `invalidateProposalForDeletedSource`. Each write now passes `ifVersion: locked.updatedAt`, so the choke point's version check backs up the helper. The `history` entry is appended to the locked row's history, not the snapshot's.
- The existing no-op checks on the snapshot (locked status, same fingerprint, already `invalid`) stay as they were, so ticks that write nothing still take no lock.

**`backend/packages/data/src/__tests__/inboxTickProposal.test.ts`**: two new integration tests in a new `describe` block.
1. **Confirm during the AI call:** the fake `computeProposal` runs `confirmProposalWithClient` on the card in its own `withTransaction(pool, …)` and waits for it, then returns a new envelope. After the tick, the card is still `confirmed`, its `proposal` and `fingerprint` are unchanged, and its history has no "Revised the proposal" entry.
2. **Soft-delete during the AI call:** the fake soft-deletes the card instead. The tick does not throw, leaves the deleted row unchanged, and creates no replacement card.

Both tests fail against the unfixed code and pass with the change. The existing 23 tests in the file pass unchanged.

**Test setup detail:** the first test removes the source item's `journalDay` link before the tick runs. The tick and the confirm both queue the same Journal-day recompute job (same job key), so the confirm would otherwise wait on the tick's open transaction and the test would deadlock. Without the link, the proposal row is the only thing the two transactions compete for, which is the race this issue is about.
