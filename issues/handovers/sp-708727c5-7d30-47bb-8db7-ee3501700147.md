# Handover: resolve a generic account's CalDAV server from its well-known delegation and keep the login there

Commit on `fix/followup-caldav`: `ff6d6f954`.

**Changes.**
- `caldavHttp.ts`: `withCalDavSession({ resolveServer })`. With a well-known start, only the first hop of the session's first request may redirect off the scope, to a server `allowsWellKnownDelegation` accepts (production: `isStorableCalDavUrl`, i.e. https, a DNS name that is no local name, the default port, no userinfo; test policy: no userinfo). The scope then moves to that server (`CalDavSession.delegatedServer()`). Every other redirect or href off the scope is refused as before.
- `caldavConnectVerification.ts`: `VerifyCalDavServerInput.resolveServer` (required); resolves with `{ delegatedServerUrl }`.
- `caldavAdapter.ts`: an account that is not iCloud and has no `caldav_url` resolves in `listCalendars`, and the rest of the adapter starts at the delegated server; `delegatedServerUrl()` (optional on `CalendarSyncAdapter`).
- `calendarAccountSyncJob.ts`: stores it after the listing through `recordResolvedCalDavUrl` (mail store: Mailboxes item `FOR SHARE`, update only while `caldav_url IS NULL`).
- `mailboxPasswordRouteHandlers.ts`: connect verifies with `resolveServer: true` and stores the delegated server instead of the body's `caldavUrl`; replacement uses `resolveServer: false`. `customRouteMount.ts`: `verifyCalDav` resolves with `CalDavVerification`.
- No schema change: the resolved server is `mail_account_server_settings.caldav_url`.
- Docs: `domain-calendar-tasks-and-media.md` (CalDAV), `edges-io-and-errors.md`.

**Behaviour to know.** A same-origin well-known redirect stores nothing new. A connect body without `caldavUrl` still has no CalDAV verification, so for it the first sync pass does the resolving. If a stored `caldav_url` is itself a well-known address it never delegates.

**Tests.** `caldavAdapter.test.ts`: the delegation is followed at connect and reported, with the login only on the delegated server after the well-known request. The same redirect is refused with `resolveServer: false` and by a sync from a stored address, and the other server gets no request. After the delegation, a home back on the first origin is refused, and so is a second redirect. A delegation to `10.0.0.1` fails as unreachable. Seven `allowsWellKnownDelegation` cases run under the production policy (http, private and loopback literal, `.local`, port, userinfo). A pass of an account without `caldav_url` stores the delegated server and the next pass starts there, and an existing address is kept. `mailboxPasswordRoutes.test.ts`: the connect stores the delegated server, and the expected verification inputs now include `resolveServer`. With the fix reverted, every new test failed.

**Review follow-up** (`51ff60540`). The delegation was first allowed only on the very first redirect hop, which refused the common chain `/.well-known/caldav` -> `/.well-known/caldav/` -> provider. The rule is now that the discovery's first request, made to the well-known start, follows any redirects within the start's origin (still at most three redirects in all), and its first redirect off that origin is the one delegation, held to every other rule as before. The scope then moves to the delegated server and stays there. A second cross-origin hop is refused, so `www.<domain>` -> provider stays refused: the `www.` host is the delegation, and trusting a host because it shares a registrable domain would need a public-suffix list. New tests: "is followed after redirects within the well-known address's origin", which failed before the change, and "refuses a second hop off the delegated server, as from www. of the domain to its provider". `caldavAdapter.test.ts` 56/56 green; docs updated (`domain-calendar-tasks-and-media.md`, `edges-io-and-errors.md`).
