# gh-1604 — [inbox-editing 06/23] Return a proposal to proposed when its source is restored

## Delivered behavior

- **Restore triggers the update heartbeats** (`backend/packages/data/src/chokePoint/itemTrash.ts`, `restoreItemWithClient`): each restored row calls `triggerOnItemEventHeartbeats(client, row.databaseId, "update", row.id, queueAffinity)` in the restore transaction, right after `itemsStore.restoreItem`, where the delete side calls it with `"delete"`. `queueAffinity` is passed from `createItemTrashOps`'s deps. A restore of an item whose database has no `update` heartbeat enqueues nothing.
- **The restored card** (`readTickSnapshot` and the new helper `reopenRestoredSourceProposal` in `backend/packages/data/src/inbox/inboxTickAction.ts`): a card that `isFinalInvalid` (status `invalid`, `invalidReason.code` `sourceDeleted`) is locked with `lockUnlockedProposal` in the read transaction, before the fingerprint gate.
  - If its stored `proposal` still passes `assertValidProposalEnvelope`, the card goes to `proposed` with `invalidReason: null` and one history entry `{ author: "ai", kind: "reopened" }`.
  - Otherwise it goes to `needsClarification` through `writeNeedsClarification`: `proposal` and `aiProposal` are nulled, `aiVersion` is incremented, and the stored fingerprint is kept.
  - The fingerprint gate then applies: an unchanged fingerprint returns the card with no AI call, a changed one takes the normal recompute path.
- **`writeNeedsClarification` clears `invalidReason`** when it moves a card out of `invalid`, as `reviseProposalWithClient` does. This also covers a restored source that has no recognized type.
- **Docstrings** updated where they claimed `sourceDeleted` is final without qualification: `invalidReasonSchema`, `reviseProposalWithClient`, `readTickSnapshot`, `createSemprecTickAction`.
- No migration. No new export, so `publicSurface.test.ts` is unchanged.

## Deviations from the Task

- The envelope-invalid branch also nulls `proposal` and `aiProposal`. That is `writeNeedsClarification`'s convention for `needsClarification` cards; the Task named only the status.
- `updateItemProperties` refuses trashed rows (`NotFoundError`), so "edited while trashed" is modelled by editing the text before the trash, with no tick in between. The fingerprint then differs at restore, which is the path the Task asks to recompute.
- Card-level tests trash and restore through `itemsStore.softDeleteItem` and `itemsStore.restoreItem`, which fire no heartbeat, as the existing delete tests do. The heartbeat wiring is tested through `chokePoint` in `inboxTick.test.ts`.
