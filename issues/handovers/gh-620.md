## Reserve AI budget under a lock before each provider call, then settle it

Closes #620

Before this change the gateway checked spend, called the provider, and only then wrote the `ai_gateway_calls` row. Nothing serialized those steps, so N calls that started together near the cap could all pass the check and overshoot it by N × the call's cost. Now each call reserves its estimated cost under a lock before the provider runs, and settles the row with the real cost afterwards.

`pnpm run verify` passes in `backend/`. I did not run it in `web/` because this change touches no web files.

### Migration `0049_ai_gateway_calls_status.sql` (expand-only)
- Adds `status text NOT NULL DEFAULT 'settled'`, restricted to `reserved`, `settled` or `failed`. The previous release's INSERT still gets `'settled'`, which is correct for its rows.
- Adds an index `ai_gateway_calls_at_idx` on `(at)`, so the spend query no longer scans the whole table.

### Store (`aiGatewayCallsStore.ts`)
- New `AiGatewayCallStatus` type. Rows now return `status`, checked against the allowed values with `assertKnownValue` when read.
- `reserveGatewayCall` inserts a `reserved` row at the estimated cost, with all usage columns NULL.
- `settleTokenGatewayCall` and `settleAudioGatewayCall` update only a `reserved` row. They throw if the row is not `reserved` or does not exist.
- `failGatewayCall` sets a `reserved` row to `failed` with `cost_usd = 0`, so it drops out of every existing `SUM(cost_usd)`.
- The four new functions are added to `publicSurface.test.ts`.

### Gateway (`gateway.ts`, `types.ts`)
- `GatewayCallContext` has a new required `estimatedCostUsd` field.
- `complete`, `embed`, `transcribe` and `diarize` now take a `Pool`.
- Before the provider call, one transaction takes `pg_advisory_xact_lock(hashtext('ai_gateway_budget'))`, runs the existing budget check (which now also counts other in-flight reservations), and inserts the reservation. The lock is released at commit, before the provider call starts.
- If the provider call fails, the row is marked `failed`. If marking it fails too, that error is logged and the original provider error is still rethrown. If the provider call succeeds, the row is settled once with the real numbers.

### Callers
- **`completeHandler.ts`**: estimated input tokens are the prompt's character count divided by 4. Output is reserved at `RESERVED_OUTPUT_TOKENS = 4096`, which mirrors the Anthropic provider's `MAX_OUTPUT_TOKENS`. Both are priced with the configured rates.
- **`audioHandler.ts`**: both routes compute the exact price once and use it as both the estimate and the settled cost.

### Behavior change: audio rows now keep `agent_run_id`
Because the Task makes the reservation identical for both paths, audio calls now record the caller's `agentRunId`. The old gateway test "diarize() always stores a null agent_run_id" contradicted this, so it now asserts that the id is kept. The audio HTTP handlers don't pass an agent run id, so rows from those routes are unchanged.

### Tests
- **Gateway:**
  - Two concurrent calls whose estimates each reach the cap: exactly one reaches the provider, the other gets `BudgetExceededError` first, and one `settled` row remains.
  - A failed call leaves one `failed` row at cost 0, and the next call at the same cap is accepted.
  - If marking the row `failed` also errors, the logger is called and the original provider error is what the caller gets.
  - A successful call is settled with the real values, not the estimate (token and audio paths).
- **Store:** reserve, settle and fail work as specified; settling or failing an already-settled row throws; `pg_indexes` lists `ai_gateway_calls_at_idx`.
- **Handlers:** a provider failure now leaves one `failed` row at cost 0 (complete route, both audio routes, and the unexpected-error case). There is a new 403 `budget_exceeded` test for the transcribe route, and the shutdown test also checks that its surviving row is `settled`.

### One addition beyond the issue text
The settle functions call `requireAffectedRows` before unwrapping the row, because the repo's `check:write-safety` step requires every targeted UPDATE to check its row count.
