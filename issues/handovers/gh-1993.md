## What was delivered

For a proposal whose target is the Events database, the request context sent to the AI gateway carries a `pastEventDurations` section: per person of the context's People group, up to five of that person's most recent same-day Events as `{ eventId, minutes, startDate }`, newest first, with no names or free text.

- `readPastEventDurations(client, personIds)` (`backend/packages/data/src/inbox/pastEventDurations.ts`, new) is one read-only statement for all persons. It lists live Events linked through `Events.people` (event is `item_a`, person is `item_b`), computes the length in minutes from `timeFrom` and `timeTo` (HH:MM, 24:00 allowed only as `timeTo`), and skips an Event with an `endDate`, without or with unreadable times, with a non-positive length, or in the Trash. A person with no counted Event has no key. An empty id list reads nothing. Isolation is by the tenant transaction (RLS); the query carries an explicit row type and parameterised values.
- `proposalContext.ts` adds the section only when `targetModuleId` is `events` and the workspace has both a People and an Events group (the Alldots project's grants), under the 900 KiB request budget: durations count in the size, and a person dropped from the People group to fit loses its entry. An Events target with no counted Event has the section as `{}`.
- `proposalComputation.ts` adds one user-message line `Past event durations (JSON): ...` and a `buildSystemPrompt` parameter; the system prompt mentions the section only when it is present.
- The section is omitted for any other target, when the Alldots project may not read People or Events, and for an untyped item that recognition resolves (the target is unknown when the context is read).

Entry points and contracts dependents build on:

- `@alldots/data` exports `readPastEventDurations` and its type, through the re-export line of `inbox/inboxTickAction.ts` (as gh-1992, because `index.ts` is at the 900-line cap) and the `publicSurface.test.ts` list.
- `ProposalContext.pastEventDurations` (optional, keyed by person id) in `backend/services/alldots-api/src/proposalContext.ts`; keys `pastEventDurations`, `eventId`, `minutes`, `startDate`.
- No route, operation, table, migration, job name or ADR was added or changed (the pattern follows the gh-1987 request budget and the gh-1992 re-export precedent).

Files: `backend/packages/data/src/inbox/pastEventDurations.ts`, `inbox/inboxTickAction.ts`, `backend/services/alldots-api/src/proposalContext.ts`, `proposalComputation.ts`.

## Deviations from the specification and spec seams

1. Besides the instruction text, `proposalComputation.ts` has one user-message line and a new `buildSystemPrompt` parameter, because `buildUserMessage` serializes context fields one by one.
2. The re-export through `inbox/inboxTickAction.ts` instead of `index.ts` (the 900-line cap).
3. An untyped item resolved by recognition gets no section, because the target is not known when the context is read.
4. An Events target with no counted Event has the section as `{}`.
5. The read takes no capture date, so it also lists Events after the capture day, as the Task's function (person ids only) implies; a person with many future timed Events shows those first.
6. Persons are read from the context's People group, so at most 20 persons (`CONTEXT_LIMIT_PER_KIND`).
7. The endDate and missing-timeTo test states need a raw `UPDATE` in the test, because the Events validation refuses the first state and a `timeFrom`-only write gets a `timeTo`.
