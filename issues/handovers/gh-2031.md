## What was delivered

- `mailboxDeleteHook` (`backend/packages/data/src/mail/mailboxDeleteHook.ts`), an item delete hook. When the trash cascade soft-deletes a row of the tenant's Mailboxes database for a writer of kind `user` or `agent`, it rejects with `ForbiddenError` (status 403, code `forbidden`). The rejection rolls the cascade back: the item, its credential, its sync state and its server settings stay as they were and no invalidation is sent.
- The Mailboxes database is the system database whose owner module is `mailboxes`, the way `removeMailbox` finds it. A row of any other database passes whoever trashes it, the Folders and Emails of a mailbox included, and so does a row of a database that carries the module id without being a system database.
- The marker of the removal is the writer kind `system`, which the hook context already carries. `removeMailbox` has passed `SYSTEM_WRITER` to the trash since gh-1690, so `mailboxRemoval.ts` changes in comments only. No field was added to the choke point.
- No generic path can name the system writer. The generic REST route and the `/mcp` operation derive their writer through `writerIdentityOf` (`user` or `agent`), and the executor of an approved request writes as `agent`.
- A delete approval guard (fix commit `0f26c4db8`). `backend/packages/data/src/chokePoint/hooks.ts` has a new registry keyed by module id: `registerItemDeleteApprovalGuard(moduleId, guard)` and `getItemDeleteApprovalGuard(moduleId)`. The `item.delete` case of `computeDestructiveResourceProjection` (`chokePoint/destructiveProjection.ts`) asks the guard of the item's owning module after its own checks and, for a message, throws `ForbiddenError` (403, `forbidden`) with the projection as `currentResource`.
- `mailboxDeleteApprovalGuard` is registered for the `mailboxes` module. Hook and guard apply one function, `mailboxDeleteRefusal`; the guard applies it with the writer kind `agent`.
- Both are registered in `backend/packages/data/src/domainWriteHooks.ts`.
- ADR `docs/adr/2026-11-11-a-mailboxes-item-is-trashed-only-by-the-system-writer.md` (accepted) records four decision points and the consequences. It extends `2026-09-18-exactly-once-execution-of-approved-destructive-operations` and `2026-11-07-item-delete-and-restore-domain-hooks` without editing them.
- No migration, table, column, route, generic operation, job name, tenant cutover entry, export from the data barrel, module manifest entry, stored key or i18n key was added.

## Contracts dependents build on

- `DELETE /api/items/:id` on a live Mailboxes item answers 403 with the body `{ "error": { "code": "forbidden" } }`. A mailbox is removed through `DELETE /api/mail/mailboxes/:id`.
- An MCP client's `item.delete` of a Mailboxes item is refused with the same error as a JSON-RPC error. Its message is `Mailbox <id> cannot be deleted as an item; it is removed through DELETE /api/mail/mailboxes/:id`.
- An agent run's `item.delete` of a Mailboxes item answers `ForbiddenError` (403, `forbidden`) when it is requested. No approval request and no `approval_pending` notification is created.
- An approval request for such a delete that was stored before the guard existed ends as a `conflict` with the reason `forbidden` when it is executed, and the run's thread, when it has one, receives the conflict outcome.
- A delete of a Mailboxes item that is already in the trash answers as before (the trashed item, nothing written): the cascade runs no hook for it.
- **A delete hook that refuses an agent's trash by a rule registers a delete approval guard with the same rule** (ADR decision point 4). Nothing checks this. A refusing hook without a guard leaves an approved request failing on every job attempt.
- `registerItemDeleteApprovalGuard` accepts one guard per module and throws `Duplicate item delete approval guard` for a second. `clearHooksForTests` clears the registry. A guard receives `{ client, database, item }` for the live item the request names and returns the refusal message or `null`.
- `ItemDeleteApprovalGuard`, `ItemDeleteApprovalGuardContext` and the two registry functions are exported from `chokePoint/hooks.ts` only, not from `backend/packages/data/src/index.ts`.
- Backend code that trashes a Mailboxes item as the system writer, or without a `writer` option (which defaults to `system`), passes the hook and skips what the removal does. `removeMailbox` is the only production caller that does. Tests build a trashed mailbox that way. A new caller that needs a mailbox gone calls `removeMailbox`.
- Order in `domainWriteHooks.ts`: the two entries of this source stand after the mailbox connection limit hooks and directly before the purge hook entry of gh-1691. `mailboxDeleteHook` is therefore the second item delete hook to run, after `itemSearchDeleteHook` and before the delete hooks of value links, People last contact, the transcript company link and Pages. A source that names gh-2031 as an ordering blocker puts its entries after these two.
- gh-1691 (landed earlier) cleans up the mail rows of a purged Mailboxes item. A mailbox that the generic delete trashed before this change keeps its credential and sync rows until it is restored and removed, or purged.
- gh-2032 (restore a removed mailbox as needing reauthorization): this hook does not act on a restore.

## Deviations from the specification and spec seams

1. The marker is the writer kind `system`, not a new field of the hook context. The `Touches` entry of `mailboxRemoval.ts` is delivered by comments only.
2. The fix round added the delete approval guard registry to the choke point (`hooks.ts`, `destructiveProjection.ts`), which is outside `Touches`. It is what makes Task step 3 hold for an agent run: before it, such a request was queued for approval and failed on every attempt after the approval.
3. The hook also requires `database.system`, as `getDatabaseByModuleId` and the mail purge hook do.
4. A delete of a Mailboxes item already in the trash answers as before and not with 403.
5. REST accepts only human sessions for `DELETE /api/items/:id`. "The same request from an agent" is therefore tested as `item.delete` through `/mcp` and through the gateway.
6. Files beyond `Touches`: `mailboxDeleteWritePaths.test.ts`, the three choke point files of point 2 and the ADR.
7. The position of the registry entries is the queue runner's, not the worker's (see "Merge").
8. The segment is not contiguous on the chain branch: two fix commits of gh-2030 stand between its two commits.
