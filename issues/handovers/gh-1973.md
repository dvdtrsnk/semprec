## What was delivered

`mcpServers` is a selectable and valid target of an Inbox item type with `processingMethod: database`. The seed adds the option after the ten hardcoded databases; a per-tenant cutover appends it for populated tenants; the create and update hooks accept the target only when the writing tenant has the MCP servers database; the option has English and Czech labels.

## Entry points and contracts dependents build on

- `INBOX_TYPE_MODULE_TARGET_DATABASES` (currently `[mcpServers]`) and `INBOX_TYPE_TARGET_DATABASES` (the eight hardcoded databases, then the module targets), now in the new store-free module `packages/data/src/inbox/inboxTypeTargets.ts`; `inboxTypesStore.ts` re-exports them and `InboxTypeTargetDatabase`, so existing imports keep working. A later module that ships its own database is appended to `INBOX_TYPE_MODULE_TARGET_DATABASES`, with a seed option and the cutover reading the same constant.
- `runInboxTypeTargetOptionsCutoverMigration(pool)` in `inbox/inboxTypeTargetOptionsCutoverMigration.ts`, registered in `runTenantCutoverMigrations` after the gh-1971 entry and before the area-note cutover. Per tenant: no-op without the Inbox item types database; `LOCK TABLE properties IN EXCLUSIVE MODE`; appends only absent module-target keys without reordering or removing options; `requireAffectedRows`; idempotent. It throws (reported as an `AggregateError` naming the tenant) when the database exists but its `targetDatabase` property is missing or malformed.
- Write hooks `inboxTypeItemCreateHook` and `inboxTypeItemUpdateHook` (`inbox/inboxTypeWriteHook.ts`): after `assertValidProcessingConfig`, a `database` type naming a module target is refused with a 400 `validation_failed` on field `targetDatabase` when `getDatabaseByModuleId` finds no such database on the write's own client (the writing tenant). The update hook judges the pair as it would be stored. A type that targets `journal` or `transcripts` is still refused.
- `seedInboxPipeline.ts`: the `targetDatabase` select options are `[...TEN_DATABASE_MODULE_IDS, ...INBOX_TYPE_MODULE_TARGET_DATABASES]`. i18n keys `property.inboxItemTypes.targetDatabase.option.mcpServers` in `inbox/i18n/en.json` ("MCP servers") and `cs.json` ("MCP servery").
- `inbox/inboxRecognition.ts` now takes its target list from `inboxTypeTargets.ts` (`RECOGNITION_TARGETS` is that list), so a `mcpServers` type is a valid recognition type, accepted as a `typeId` candidate and offered in a clarification; a `journal` type stays excluded.

## Deviations from the specification and spec seams

1. The cutover throws on a missing or malformed `targetDatabase` property instead of returning silently; the Task specifies only the no-op for a missing database. It is an invariant check.
2. The existence check applies to the targets of the new constant `INBOX_TYPE_MODULE_TARGET_DATABASES`, which seed, cutover and hook all read, rather than to `mcpServers` by name.
3. Beyond the Touches list (done in the fix round, review finding below): the constants moved to `inboxTypeTargets.ts` and `inboxRecognition.ts` uses them; a direct import of `inboxTypesStore.ts` would create a cycle through `inboxSourceGuard.ts`.
