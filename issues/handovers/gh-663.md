## Changes

- **`0051_module_migration_progress.sql`** (new). Adds the `module_migration_progress` table exactly as specified. It is keyed by `(module_id, database_key, from_version, to_version)`, the same key as the advisory lock and the `module_migrations` row. The header comment says the row is deleted when the transition is recorded and that `databases.migration_cursor` stays in place, unused. It grants `semprec_side` access, following the side-table convention from `0040`.
- **`migrationJob/itemBatch.ts`** (new). `lockItemBatch(client, { databaseId, afterId, pageSize, skipLocked })` runs `SELECT id, properties … ORDER BY id LIMIT $2 FOR UPDATE [SKIP LOCKED]`. It must run inside the caller's transaction, and the rows stay locked until that transaction commits.
- **`migrationJob/moduleDataMigration.ts`**
  - `convertInBatches` is now keyed by the transition and reads and writes `module_migration_progress`. The old `readCursor` and all `databases.migration_cursor` writes are gone.
  - Pass 1 locks each batch and skips rows another transaction holds. Pass 2 starts again from the first id and waits on a held row instead of skipping it.
  - Each row is written with a full replace guarded by `properties IS DISTINCT FROM $3::jsonb`. The replace is safe because the row stays locked for the whole batch transaction. The guard leaves `updated_at` (the `ifVersion` token) alone when the converter returns the row unchanged.
  - The `(pass, cursor)` progress commits in the same transaction as each batch. When pass 1 finishes, progress resets to `{ pass: 2, cursor: NULL }`. A resumed run continues from the recorded pass and cursor.
  - After pass 2, one transaction inserts the `module_migrations` row and deletes the progress row. The delete is checked with `requireAffectedRows`, because the progress row always exists at that point.
  - `readProgress` rejects any `pass` value other than 1 or 2 instead of silently narrowing it.
- **`ModuleDataMigrationConverter` doc comment.** It now states the idempotency contract: `converter(converter(p))` deep-equals `converter(p)`. It also says what the two passes guarantee: every row is converted at least once and rewritten only when the converter changes it.
- **`testSupport/testDb.ts`**. The new table is truncated between tests.
- **`.github/scripts/write-safety-baseline.json`**. Regenerated with `--update-baseline`. It adds the guarded item `UPDATE`, which legitimately affects zero rows when a row already has its converted shape. It drops the fingerprints of the old runner's removed statements.

## Tests (`__tests__/moduleDataMigration.test.ts`)

The four existing cases are kept and adapted. Two of them had converters that were not idempotent (one threw when it saw a converted row, one counted conversions inside the properties), which breaks the new contract:
- "Exactly once" is now checked with converter call counts (items × 2 passes) and with `updated_at` staying unchanged on rows that were already converted.
- The "resume" case now asserts `{ pass: 1, cursor }` progress after the crash.

New cases:
- **(a) Concurrent choke-point update.** A second connection locks the first item with `FOR UPDATE`. The migration runs with `pageSize: 1`: pass 1 skips the locked row and pass 2 waits on it (detected with `pg_blocking_pids`). The second connection then applies a choke-point patch through `updateItemWithClient` and commits. The row ends up with both the patch and the converter's change.
- **(b) Row inserted below the pass-1 cursor.** The first batch's converter call inserts an item with the nil UUID. A held lock on the progress row stops that batch from committing until the insert has committed, which makes the test deterministic. Pass 2 converts the new row before the transition is recorded.
- **(c) Two transitions on one database.** Runs to `2.0.0` and `3.0.0` execute concurrently. Both record their `module_migrations` rows, no progress rows are left, and every item carries both conversions.
- **(d) Crash in pass 2.** After a crash in pass 2, the resumed run continues in pass 2 with only 2 converter calls and no pass-1 re-run, and `updated_at` is unchanged on every row.
