## What was delivered

- `POST /api/mail/mailboxes/:id/reauthorize`, a custom route of the mail module (`mailboxReauthorize`, justification `transactional-semantics`), handler `createMailboxReauthorizeRouteHandler(pool, dependencies)` in `backend/packages/data/src/mail/mailOauthRouteHandlers.ts`. It needs a session; the tenant is the session's. The request body is ignored.
  - One transaction locks the Mailboxes item (`lockItemById`), reads the mailbox's `mail_account_sync_state` row without a lock, stores a one-time `mail_oauth_states` row that carries the mailbox id (`createMailOauthState` with `mailboxItemId`) and answers 200 `{ authorizeUrl }`. The URL is built like the start route's, for the mailbox's provider.
  - A mailbox can be reauthorized when its `provider` property is `gmail` or `outlook` and its sync state row, when one exists, holds that provider's sync mode (`gmail_api`, `graph_api`). The helper is `reauthorizationProvider(mailbox, syncState)`. A mailbox without a sync state row is decided by `provider` alone.
- `POST /api/mail/mailboxes/oauth/complete` handles a state that carries a mailbox id. Until this source it refused such a state with 400.
  1. The state is consumed as before.
  2. The `mailLiveSync` member of the route dependencies is read. A deployment without it fails here with a plain error, before any provider request.
  3. The code exchange and the provider's address lookup run outside any transaction, as in the connect flow.
  4. One READ COMMITTED transaction (`replaceMailboxCredential`): an unlocked read of the Mailboxes item, `ensureMailAccountSyncState` (an existing row keeps its sync mode), `lockMailAccountSyncState` (`FOR UPDATE`), `lockItemById` on the Mailboxes item and the re-check on the locked rows, the address comparison, `storeCredential` with type `oauth2_refresh_token`, `enqueueMailAccountSync`.
  5. After the commit the route awaits `mailLiveSync.restartAccount(mailboxItemId)` and answers 200 `{ mailboxId }`.
- The address rule of step 4: the signed-in address, after `normalizeEmailAddress`, must equal the stored `provider_account_address`. When none is stored, `recordProviderAccountAddress` stores the signed-in one; the unique index `mail_account_sync_state_tenant_provider_address_uq` refuses an address another mailbox of the tenant records.
- Not written by the reauthorization: `Mailboxes.syncStatus`, the history cursor, the delta link, `Mailboxes.addresses` and `gmail_watch_email_address`.
- `MailLiveSyncRoot.restartAccount(mailboxItemId)` in `backend/packages/data/src/mail/mailLiveSyncRoot.ts`. It stops the hosted entry through `stopHosted` and hosts a new lifecycle from the root's factory for the entry's tenant and sync mode, also when the old `start()` had failed. The pass's host step was extracted into a shared `host()` function, with the same behaviour.
- `semprec-api`: `MailLiveSyncControl` (`backend/services/semprec-api/src/adapter/customRouteMount.ts`) gained `restartAccount(mailboxItemId)`. The new module `backend/services/semprec-api/src/mailLiveSyncControl.ts` exports `createMailLiveSyncControl()`, which returns `{ control, bind(root) }`. `serve.ts` puts `control` into the custom-route dependencies and calls `bind(mailLiveSync)` right after it creates the root, before `mailLiveSync.start()` and before the server listens. The proxy object that `serve.ts` held before is gone.
- The error code `mail_reauth_wrong_account` in `ITEM_ERROR_CODES` and `ITEM_ERROR_STATUS_BY_CODE` (400) of `backend/services/semprec-api/src/adapter/errorContract.ts`.
- The route matrix entry `{ name: "mailbox reauthorize", method: "POST", path: "/api/mail/mailboxes/<id>/reauthorize", surface: "api", public: false, tenancy: "tenant" }` in `backend/services/semprec-api/src/routeMatrix/mail.ts`, its `ROUTE_CASES` case in `tenantIsolationRoutes.test.ts` and its `ROUTE_HANDLER_FILES` mapping to `packages/data/src/mail/mailOauthRouteHandlers.ts`, all in the same merge.
- The ADR `docs/adr/2026-11-11-mailbox-reauthorization-restarts-the-hosted-lifecycle-in-the-live-sync-roots-context.md` (accepted, area backend, standalone). ## Contracts dependents build on

For gh-2032 (restore a removed mailbox as needing reauthorization, capability blocker), gh-1747 (names this source as a shared-file-ordering blocker only) and gh-1481 (a rotated token; the text of gh-1742 says it may reuse `restartAccount`).

- Answers of the reauthorize route:
  - 200 `{ authorizeUrl }`.
  - 404 `not_found` for an unknown, malformed, trashed or foreign mailbox id, and in a tenant without a Mailboxes database. All of them read the same and none stores a state.
  - 400 `validation_failed` with `details.field` `provider` for a mailbox that `reauthorizationProvider` names no provider for: a `provider` other than `gmail` or `outlook`, or a sync state row with another sync mode than the provider's. No state is stored.
  - A generic 500 when the provider's OAuth client is not configured (a plain error, as the start route). No state is stored.
  - 401 without a session.
- Answers of the complete route for a state with a mailbox id:
  - 200 `{ mailboxId }`. The connect flow answers 201; this one answers 200.
  - 400 `mail_reauth_wrong_account`, the code alone, when another account signed in, and when the mailbox records no address and another mailbox of the tenant records the signing-in one. Nothing is written and no restart is called.
  - 400 `validation_failed` with `details.field` `state` when the mailbox is gone, trashed, foreign, changed its `provider` or does not sync in its provider's mode. Nothing is written.
  - 400 `validation_failed` for a code the provider refuses, as in the connect flow.
  - A generic 500 when the composition root set no `mailLiveSync` member (before the provider call, nothing replaced) and when the restart rejects after the commit (the token is replaced and the sync is queued).
  - The state is consumed in every case.
- Lock order of the write: the `mail_account_sync_state` row first, the Mailboxes item second. The sync job's failure paths and `removeMailboxWithClient` of gh-1690 take the two rows in the same order. A new transaction that takes both rows keeps this order. The reauthorize route locks only the item and reads the sync state row without a lock.
- While it holds the two locks, the write can wait for the mailbox's `external_credentials` row, which `refreshAndPersistAccessToken` holds across its provider request. The statement timeout bounds the wait.
- For gh-2032: a mailbox without a sync state row is accepted by both guards when its `provider` is `gmail` or `outlook`, and the completion creates the row with that provider's sync mode and records the signing-in address when no other mailbox of the tenant holds it. `removeMailboxWithClient` deletes the sync state row and the credential, so for a restored mailbox the row the restore creates decides: a row with another sync mode than the label's provider is refused by both guards.
- `MailLiveSyncRoot.restartAccount(mailboxItemId: string): Promise<void>`:
  - It resolves once the new lifecycle started, or once its failed start was reported through `onLifecycleError`. A lifecycle factory that throws rejects it and leaves the account unhosted until the next discovery pass.
  - An account the root does not host is left alone; the next discovery pass hosts it. That covers an account not discovered yet, a retired one, one that a pass or another restart is replacing at that moment, and every account after `stop()`.
  - A caller inside a tenant scope restarts only an entry hosted for that tenant. An entry of another tenant is treated as not hosted. A caller that needs another tenant's mailbox calls from a system scope.
  - The work runs in the async context the root was created in (`AsyncLocalStorage.snapshot()`), inside `runAsSystem("mail:liveSync")`. A root created inside a tenant scope cannot restart.
  - When a discovery pass hosted the account while the old lifecycle stopped, that lifecycle is kept and no second one is created. `stopTenant` waits for a restart in flight. A restart whose old lifecycle is still stopping when `stop()` runs hosts nothing.
  - gh-1481 can call it from a tenant scope as it is.
- Container members:
  - `MailLiveSyncControl.restartAccount(mailboxItemId: string): Promise<void>` is required. Every object of that type needs the member; the fixture of `customRouteMount.test.ts` passes it. `startMailbox` and `stopMailbox` still refuse on every call with `CustomRouteConfigurationError`.
  - `MailOauthRouteDependencies.mailLiveSync?: { restartAccount(mailboxItemId: string): Promise<void> }` in the data package. `CustomRouteDependencies` of `semprec-api` is assignable to it. It is read per request, never while the factory runs.
  - `createMailLiveSyncControl(): { control: MailLiveSyncControl; bind(root: Pick<MailLiveSyncRoot, "restartAccount">): void }`. `control.restartAccount` called before `bind` refuses with `CustomRouteConfigurationError`.
- A test that drives the completion of a reauthorization passes a `mailLiveSync` member. The dispatcher of `tenantIsolationRoutes.test.ts` has none: its case "mailbox reauthorize" calls the reauthorize route only.
- `createMailboxReauthorizeRouteHandler` is exported from the mail module manifest (`backend/packages/data/src/mail/mailModuleManifest.ts`), not from the `@semprec/data` barrel. `publicSurface.test.ts` is unchanged.
- The isolation case seeds one Mailboxes item per tenant (`mailboxNeedingReauthorization`) and leaves one unused `mail_oauth_states` row with a mailbox id in each tenant. Later cases of that file see them; the file passes as a whole (247 tests).
- The existing test "refuses a reauthorization state, which is consumed, until issue #1742 handles it" of `mailOauthRoutes.test.ts` was removed; the new tests cover the branch.
- No SQL migration, no table, no column, no index, no job name, no write hook, no cutover entry, no generic operation, no i18n key and no barrel export was added. The queued job is the existing `mailAccountSync` with job key `mail-account-sync:<mailbox id>`.

## Review

Three reviewers read `26b8dbe2a^..73114908a` (three commits), read-only, without a build or a test: requirements and tests (verdict findings: one medium; all four criteria covered), project rules and architecture (verdict clear) and security (verdict findings: one medium). The focused recheck read `73114908..434bbf22` (one commit) and gave verdict pass, with no unresolved and no new finding.

- Medium, requirements lens and security lens, the same defect, fixed in `434bbf22`: both guards decided "password-based" from the user-editable `provider` label alone. An IMAP mailbox relabelled `gmail` or `outlook` had its password replaced by an OAuth refresh token, which the IMAP sync then sent as the login password. The fixer reproduced it and also the mirror case (a Gmail mailbox relabelled `outlook` got a Microsoft token). Both guards now also require the sync mode of the mailbox's sync state row to be the provider's. Six new tests, all failing on the unfixed handler.

Follow-ups, none of them a finding against the candidate:

- The guard relies on the sync state row. A mailbox without one is decided by its label. On the merged tree the password route of gh-1736 creates the row with mode `imap` in the transaction that stores the password, which is what the fixer asked of it. The Task of gh-2032 has the restore create the default sync state of a restored mailbox; the sync mode of that row decides whether the mailbox can be reauthorized and where the new token is sent.
- The optional refusal by the stored credential's type was not added. The fixer's reason, accepted by the recheck: the sync mode decides where the credential is sent, and a guard on the credential row would add a lock on `external_credentials`, which `refreshAndPersistAccessToken` holds across its provider request.
- A `restartAccount` that begins while `stopTenant` is already waiting is not waited for and can host a lifecycle of a just-deactivated tenant until the next discovery pass retires it. The ADR records it; the exposure is one discovery interval and does not cross tenants.
- A restart that fails after the commit answers 500 for a reauthorization whose database part succeeded. The user signs in again, which repeats the restart.
- The response of the completion waits for the old lifecycle's `stop()` and the new one's `start()`. Each of those has its own timeout; the restart adds none.
- A mailbox whose `provider` is `gmail` or `outlook` and whose sync mode was changed to `imap` by hand is now refused instead of overwritten. It can be reauthorized again once its `provider` names what it syncs with.
- `worker.json` describes the contract before the fix round (deviation 10 there). This handover describes the contract after it.
