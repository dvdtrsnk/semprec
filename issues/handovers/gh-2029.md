## What was delivered

- The core task `mailboxRemoval` (`CORE_TASK_NAMES.MAILBOX_REMOVAL`): affinity `api`, tenancy `tenant`, handler registered in `createCoreTaskList` (`backend/packages/data/src/worker.ts`).
- The removal transaction of gh-1690 queues it as its last statement, on the transaction's own client, under the job key `mailbox-removal-<mailboxItemId>` on the lane `mailbox-removal:<tenantId>`. The job therefore exists only when the removal commits.
- `handleMailboxRemovalTask` in `backend/packages/data/src/mail/mailboxRemovalJob.ts` trashes the mailbox's Emails (drafts included) and then its Folders, in committed chunks of 100 rows in id order, each row through the choke point's trash cascade (`itemDeleteWithClient`) as the system writer.
- Members are the rows the removal impact report of gh-1501 counts: the non-deleted Emails in the mailbox's non-deleted Folders, and those Folders. The job and the report start from one SQL text, `MAILBOX_REMOVAL_MEMBERS_CTE_SQL`. Mail of another mailbox, rows already in the trash and the attachments' Files items and blobs are not touched. The job writes no Threads item and no `mail_threads` row.
- Every row the job trashes gets the Mailboxes item's own `deleted_at`. Each chunk first locks the Mailboxes item `FOR SHARE` and reads its trash epoch; when the mailbox is live again or gone, the job ends there. A restore of the mailbox waits for a running chunk.
- A chunk that throws rolls itself back and fails the job; earlier chunks stay committed. A rerun selects only rows that are still live and rewrites none of the others.
- ADR `docs/adr/2026-11-10-a-mailbox-removal-job-joins-the-mailbox-trash-epoch.md` records the job, the members, the chunks, joining the epoch and the lock.

## Contracts dependents build on

- Task name `mailboxRemoval`, job key `mailbox-removal-<mailboxItemId>`, queue lane `mailbox-removal:<tenantId>`, payload exactly `{ mailboxItemId: <uuid> }` (strict; any other payload is rejected).
- `mail/mailboxRemovalJob.ts`, not in the barrel: `handleMailboxRemovalTask(pool, payload, options?: { chunkSize? })`, `enqueueMailboxRemoval(client, mailboxItemId)` and `mailboxRemovalJobKey(mailboxItemId)`.
- Choke point, `chokePoint/itemTrash.ts`: `itemDeleteWithClient` takes the optional `deletedAtExact`. With it, every row the call soft-deletes (the root and its inline subtree) gets that `deleted_at` instead of the transaction's `now()`, and the delete hooks receive it. The value must be UTC text with six fraction digits (`YYYY-MM-DDTHH:MI:SS.ffffffZ`); any other text throws before a row is written. The cascade does not check that the value is the `deleted_at` of any item: the caller reads it under a lock. Only the job passes it; no route, agent tool or `/mcp` operation does.
- Choke point, `chokePoint/itemsStore.ts`: `softDeleteItem(client, databaseId, itemId, deletedAtExact?)` writes `COALESCE($3::timestamptz, now())`, and the new `lockItemTrashEpoch(client, databaseId, itemId): Promise<string | null>` locks the item `FOR SHARE` and returns its `deleted_at` in that text format, or `null` for a live or unknown item.
- `MAILBOX_REMOVAL_MEMBERS_CTE_SQL`, exported from `mail/mailboxRemovalImpact.ts` (not in the barrel): the leading CTEs `mailbox_folders (id, is_drafts)` and `mailbox_emails (email_id, is_draft)` of a statement whose parameters are `$1` the mailbox item id, `$2` the Folders database id and `$3` the Emails database id.
- For gh-2032 (restore): the rows the removal trashed are exactly the Folders and Emails items whose `deleted_at` equals the Mailboxes item's `deleted_at`. A row the user trashed before the removal keeps its own time. Equal timestamps are not a transaction identity.
- The trash purge counts its retention from `deleted_at`, so the job's rows become eligible together with the mailbox.
- No table, no migration, no route, no generic operation, no MCP tool, no hook registration and no error code was added.

## Deviations from the specification and spec seams

1. Files beyond the issue's `Touches`, each needed by a Task step: `chokePoint/itemTrash.ts` and `chokePoint/itemsStore.ts` (the Task requires every row to carry the Mailboxes item's own `deleted_at`, and the choke point could only stamp the transaction's `now()`), `mail/mailboxRemovalImpact.ts` (one membership definition for the report and the job), `.github/scripts/write-safety-baseline.json`, `tenantIsolationJobs.test.ts` (its inventory requires one case per api-affinity task), `itemTrash.test.ts` and the ADR.
2. Threads: the Task tells the job to soft-delete Folders and Emails. It writes no Threads item. A thread the impact report counted is one left with no live message, and the test counts the threads that leave the thread list.
3. Following the counting rules of gh-1501, an Email that sits only in a folder the user trashed before the removal is not a member: it stays live and is still returned by the generic Emails list. The requirements reviewer noted that this is in tension with the literal wording of the first acceptance criterion and left it to the owner to confirm.
4. Emails are trashed before Folders, because membership is read through the live Folders.
5. Between the removal's commit and the end of the job the mailbox's folders and messages are still live and listed.
6. `chokePoint/itemTrash.ts` was also changed on the tip (the item purge hooks). The statements merged without conflict; only the list of ADRs in the file's header comment conflicted and now names both.
