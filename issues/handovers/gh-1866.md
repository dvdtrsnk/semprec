## What was delivered

A new realtime invalidation scope `projectAgent` that tells every socket of the tenant that the agent setup of one project changed.

- Frame: `{ type: "invalidate", scope: "projectAgent", projectItemId: string }`. Added to `InvalidationEvent`, `RealtimeMessage` with `parseRealtimeMessage` (UUID check), `OutboundFrame`, the invalidate case of `syncServer.ts` (`sendToTenant` with no user narrowing, so it is tenant-wide whatever the message carries) and `parseServerFrame` (UUID check). A malformed project id is dropped by the listener and by the client parser.
- Publisher: `publishProjectAgentInvalidation(client, projectItemId)` in `data/src/projectAgent/projectAgentInvalidation.ts` (`runAfterCommit` on a transaction client, at once on a bare pool; accepts `Pool | PoolClient`).
- Publication points: `projectAgentGuidanceStore` upsert and delete (the save path), `setProjectMcpGrant` (reached by `setProjectMcpGrantForAgentPage`), `createHeartbeat`, `updateHeartbeatRule` and `setHeartbeatEnabled` for user-origin heartbeats only, and the guidance drift findings store: `upsertActive` (raised or reactivated), `resolve` (active to resolved) and `decide`. A call that finds nothing to change announces nothing.

## Entry points and contracts dependents build on

- Wire scope `projectAgent` with exactly the keys `type`, `scope`, `projectItemId`. A client refetches the project's agent setup (guidance, grants, heartbeats, drift findings) on it.
- `publishProjectAgentInvalidation` is not exported from the `@semprec/data` barrel; `publicSurface.test.ts` is unchanged.
- Any new writer of the project's guidance, MCP grants, user heartbeats or drift findings must call the publisher in the same transaction as the write.
- No route, table, migration or job name was added.

## Deviations and spec seams

1. Only user-origin heartbeats publish; seeded and internal system heartbeats, including the guidance drift heartbeat, publish nothing.
2. No heartbeat deletion function exists, so the "deleting" publication point has no code to hook.
3. Guidance transfer (owner change only) and heartbeat rename or task edits are not publication points of the Task and publish nothing.
4. A guidance delete (saving empty sections) publishes because it is part of the save path.
5. A finding observed again while already active and a resolve of an already resolved finding publish nothing; `decide` (resolve or dismiss by the owner) publishes.
6. The `InvalidationEvent` variant carries an optional `userId` although publishers pass none and delivery is tenant-wide whatever it says, because existing tests read `event.userId` on the whole union.
7. `schedulerStore.ts` is now 918 lines (under the ESLint counted-lines cap of 900; ESLint passes).
