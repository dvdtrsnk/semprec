## Summary

Adds step 6 (`match`) to the `semprec-transcribe` pipeline (issue #247). It runs after `summarize` and before `finalize`. It doesn't call a model.

- **Candidate query** (`packages/data/src/transcription/transcriptEventMatch.ts`, `matchTranscriptToEvent`): finds live Events with `type` of `standup` or `meeting` whose `date` falls inside `[recordingStart − 30 min, recordingEnd]`. The start is the transcript's `date` and the end is start plus step 1's checkpointed `durationSeconds`. Both edges of the window count as inside. An Events `date` is free user input, so it is parsed in TypeScript rather than cast in SQL, where one bad value would fail the whole query. Date-only and unparseable values are never candidates.
- **Exactly one candidate:** writes the existing Transcripts `event` ↔ Events `transcript` 1:1 edge through `createRelationWithClient`. No card is created.
- **Zero or several candidates:** writes no edge and creates one Processing proposal with `kind = 'transcript'` and `status = 'proposed'`, linked by `sourceTranscript`. Its `proposal` uses the existing create-Event shape: `{ entityKind: 'database', target: <Events id>, properties: { name, type: 'meeting', date } }`, with `name` and `date` taken from the transcript. The proposal is checked with `assertValidProposalEnvelope` before it is stored.
- **Idempotency:** everything runs in one transaction that row-locks the transcript first, so concurrent runs wait for each other. If the transcript already has an Event edge, the step writes nothing. The card is created with a fixed idempotency key, `transcript-suggestion:<transcriptId>`. If that key is already taken, the step returns without writing, whatever the card's status and even if it was deleted. A re-run never makes a second card, and never adds an edge next to an existing card, even if exactly one Event matches later.
- **One case the issue didn't cover:** if the single candidate is already linked to a different transcript, a second edge would break the 1:1 relation. The step creates the card instead of guessing.
- **ADR:** `docs/adr/2026-09-23-transcription-worker-writes-event-match-results.md`. The accepted ADR `2026-09-22-transcription-worker-choke-point-access` limits this worker to creating Transcriptions items and writing its computed checkpoints. The new ADR adds exactly these two writes and leaves the old ADR's text unchanged. `docs/operations/database-roles.md` now points to it.
- **Existing test changed:** in the step-1 "concurrent run finished first" test, the simulated concurrent run now also writes its `date` in the same transaction as its checkpoint, as a real run does. The old version left a transcript with no `date`, a state the match step correctly rejects.

Out of scope, left for later issues: `entityKind: 'relation'`, the link-existing proposal shape, the edge write inside `confirm`, `revise` (#184), and speaker mapping (#185).
