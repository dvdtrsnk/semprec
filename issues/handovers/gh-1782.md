# Handover for gh-1782

Reveal a task when its last event ends. ## What was delivered

- A new tenant-scoped api core task `taskHostEventEnded`: `CORE_TASK_NAMES.TASK_HOST_EVENT_ENDED`, `CORE_TASK_AFFINITY` `api`, `TASK_TENANCY` `tenant`, handler registered in `createCoreTaskList` (`packages/data/src/worker.ts`).
- `recomputeTaskHostState(client, taskId)` now enqueues `taskHostEventEnded` with payload `{ taskId }`, `runAt` = the computed `hiddenUntil`, `jobKey` `taskHostEventEnded:<taskId>` and `jobKeyMode: "replace"`, in the caller's transaction, whenever the computed state leaves `hiddenUntil` set, also when nothing else is written. A rolled-back recomputation leaves no job.
- `handleTaskHostEventEndedTask(pool, payload)` validates the payload strictly (`{ taskId: uuid }`, no extra field), then recomputes through `recomputeTaskHostState` in one transaction in the job's tenant. A missing or trashed task and an unchanged state end without a write; a `hiddenUntil` still in the future leaves the next run queued; a moved end is written and queued again.

## Contracts dependents build on

- Job name `taskHostEventEnded`, payload `{ taskId }`, one pending job per task (key `taskHostEventEnded:<taskId>`, no tenant segment: a task id is a server-generated UUID).
- `taskHostEventEndedJobKey(taskId)` and `handleTaskHostEventEndedTask(pool, payload)` exported from `packages/data/src/tasks/taskHostEventState.ts`.
- The reveal is an ordinary Tasks-owner write through `updateItemWithClient`, so the client gets the usual item update frame with the stored `updatedAt`.
- No new route, table, operation or migration. No export added to the data barrel.

## Deviations from the specification and spec seams

1. No ADR: the job follows the queue, tenancy and affinity ADRs and the ADR of gh-1780, whose sentence "time passing is not a trigger" describes the stored derivation and names this job as its counterpart.
2. The job key has no tenant segment, exactly as the Task says. No queue lane and no `maxAttempts` are set because the Task names none.
3. Test seams: graphile's public jobs view has no payload column, so the tenant stamp is proven by behaviour (each tenant's task is revealed by its own job). The fake clock moves JS `Date` only while graphile compares `run_at` with the database clock, so tests that need the job to re-queue itself call the production handler after consuming the pending row. The rules reviewer checked in graphile-worker 0.17.3 that a replace of a locked job clears its key and inserts a new row, so the in-flight path behaves as modelled.
4. Known limit: if the application clock is behind the database clock, a job that runs before `hiddenUntil` re-queues itself at an instant the database already considers past and runs again immediately until the clocks agree (bounded by the skew). The Task prescribes `runAt = hiddenUntil`, so it was left as specified.
