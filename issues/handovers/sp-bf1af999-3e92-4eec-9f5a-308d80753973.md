# Handover: the backend assumes the first version

Implementation commit `c755eac7e` on `feat/internet-accounts`.

Owner decision (David, 2026-11-21), recorded verbatim in `issues/decisions/sp-bf1af999-3e92-4eec-9f5a-308d80753973.md`. Nothing was run against any server.

**Rule.** `.bb/AGENTS.md` (strict item 3), `.bb/skills/db-migrations/SKILL.md`, `.bb/skills/implement-issue/SKILL.md` (the migration-ordinal step is gone), `.claude/skills/finish/SKILL.md`, `backend/review-rules/rules.md` and `tasks/architecture.md`, `.github/ISSUE_FORMAT.md` (hotspot: the baseline), `docs/architecture/migrations-and-seeding.md` (new section "One baseline, no versions"; the migrations CLI and Hunspell sections now describe the code as it is), `docs/architecture/README.md` (former-ADR rows retargeted, expand/contract and module-data-migration rows marked dropped), `docs/architecture/delivery-and-operations.md`, `docs/operations/migrations.md` (rewritten), `docs/operations/releases.md` and `deploy/README.md`. They all say the same thing: no versions and no migrations. A schema change edits `0001_baseline.sql` and the seed in place. There are no backfills, cutovers, reconciles or compatibility branches. The operator wipes the deployed database before every deploy, and `deploy.sh` never drops data. Production rules arrive with the owner's first production deployment.

**Removed, with the reason:**
- `seed/seedReconcile.ts`, `readFreshSystemSeed`, `createTenantWithId` (its only caller), the reconcile pass and `SeedResult.reconcile` in `runSeed`, `seedExitCode`, `runSeedCli --strict` and its argument check, and `__tests__/seedReconcile.test.ts`. They reconciled already-seeded tenants with a newer seed. The seed now provisions each tenant and leaves an already-provisioned tenant as it is. `formatSeedLines` became `formatSeedLine`. `lockTenantSeedInTransaction` is no longer exported (its only other caller was the reconcile).
- `deploy/scripts/cutover-dry-run.sh` and `docs/operations/production-cutover-to-develop.md`: tooling for carrying a production database over.
- `db/migrationCompatibility.ts`, `db/migrationExamples/`, and `migrationCompatibility.test.ts` and `.unit.test.ts`: expand/contract checks for future migrations.
- `scripts/check-migration-numbering.mjs`, its package script, its step in `pnpm run verify`, and the CI step in `.github/workflows/ci.yml`. It only policed future migration files. `ci.yml` is a Relay-protected path; this was an owner-instructed change outside Relay.
- `reindexSempMessageSearch` (plus its export, public-surface entry and tests). It was an operator reindex for messages written before `search_vector` existed, or before Hunspell activation. Activation happens only as the last statement of the baseline, on an empty database.
- `assignMissingPurgeDeadlines` and `purgeDeadlineIsCurrent`, and their three tests. They repaired archived databases that an older release left without a current `purge_at`. Archive always sets `purge_at` and restore clears it.
- The `onlyMissing` mode of the item search backfill (`itemSearchBackfill.ts`, and `indexItem`'s `onlyMissing` and upsert guard). It indexed only items with no index row, for rows written before the index existed. Every production caller used the full rebuild, which stays (property changes, language change). The test cases written only for that mode are removed. The rest of the tests now use the full mode, and the payload table now asserts that `{ onlyMissing: true }` is refused.
- `mail_message_meta.migration_status` (baseline column and check, store field). No reader existed, and every writer stored `'stable'`.
- The `persistent` field of task recurrence templates, with `publicTaskRecurrenceTemplate` and `PublicTaskRecurrenceTemplate`. The field was legacy: stored templates kept it and new ones stored `false`.
- The purge of global `mail:`/`process:mailsync:` observability rows, `deleteOrphanedObservabilityChecks` (public-surface entry included), and the matching `NOT LIKE` filter in the operator report, with their tests. No writer produces those rows; mailbox checks live in `tenant_observability_checks`.
- `__tests__/mailThreadBackfillCli.test.ts`. It was evidence for the removed mail-thread backfill; the compiled-CLI behaviour is covered by `nativeEntrypoints.e2e.test.ts`.
- `__tests__/viewsCreatorProjectItemIdMigration.test.ts`. It tested a view row "written before the column existed". The runtime null-creator case (`ON DELETE SET NULL`) stays covered in `views.test.ts`.
- The removed files' entries in `testSupport/tenantScopeWarnFiles.json`. The hash-pinned `.frozen.json` is unchanged by design.

**Kept deliberately:**
- `runMigrations` and `schema_migrations`. Deploy and `globalSetup` need them to apply the baseline. They also make a repeated run a no-op; tests and the e2e module fixtures rely on that.
- The manifest `migrations` field.
- `deploy.sh --rollback`. Its docs now say it is safe only between releases with the same baseline.
- `startupRunsNoDataMigration.unit.test.ts`. It still enforces that services run no data steps.

**Deploy on a wiped database.** `deploy.sh` is unchanged apart from comments. It runs migrations (baseline plus the queue schema), then the seed (provisions tenant zero), then `verifyTenancyCli`, in that order. No reset step was added.

**Not removed (candidates for the owner).** Reader fallbacks that may be legacy-only but were not proven:
- `agentRunsStore.mapErrorCode` reads an `error` row with no code as `internal`; the test is in `agentRunHandler.test.ts`.
- `guidanceDrift` accepts a finding without `kind` or `subject`.
- The `aiProposal`→`proposal` fallbacks in `inbox/proposalEnvelope.ts`, `proposalRetention.ts` and `inboxTypeChange.ts`.
- The `aiVersion` default in `transcriptCardRecomputeStore.ts`.
- `transcriptSpeakerSuggestion` checkpoint optional fields.
- The legacy status-only tolerance in `taskPreWriteTransform.ts`.
- `classifyUnclassifiedMailSyncErrors`. Current writers can still produce its input.
- The nullable `purgeAt` in the trash list.
- The `legacy_creator_unknown` reason name. The case itself is reachable at runtime.
- `issues/batches/backend/CONTROLLER.md` still describes ordinal renumbering for the historical program.
