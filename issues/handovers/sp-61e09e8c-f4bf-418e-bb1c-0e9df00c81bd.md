# Handover: add the seed's missing system definitions to carried tenants

Implementation commit `80d818e6d` on `feat/ia-seed` (from `feat/internet-accounts`). Nothing was run against production or any remote host.

**Design.**
- One source of truth: the reference definitions are read from the seed itself. `readFreshSystemSeed` (`seed/seedSystem.ts`) creates a scratch tenant inside one transaction (`createTenantWithId`), runs the full system seed for it (`seedSystemInTransaction`, the body of `seedSystem` extracted unchanged), lets a reader read and then rolls the whole transaction back by throwing a private sentinel (tenant row, databases, queued jobs, after-commit callbacks all discarded). It takes `LOCK TABLE properties IN EXCLUSIVE MODE` first so it never upgrades a weaker lock against a concurrent seed. `readSeedDefinitions` (`seed/seedReconcile.ts`) reads databases (by `owner_module_id`, `system`), their properties and relation definitions.
- `reconcileSeedDefinitions(pool, reference)`: one `withTransaction` per tenant, `lockTenantSeedInTransaction` then the exclusive `properties` lock (as the seed does before writing into locked schemas), reads the tenant's definitions, plans without writing, then inserts with raw SQL the way the seed writes into locked schemas (`assertValidPropertyConfig` first; explicit pre-generated ids so every config is final at insert). A missing property gets key, name, type, owner, owner process, locked, initial position and config; a relation definition is created only when all its sides are missing. Every reference id in a config (database, property, relation definition, as value or key) is mapped to the tenant's; any other UUID makes the property `unmappable` (dropped together with its relation partner, to a fixpoint).
- Reported, never changed: `missingDatabase`, `type`, `owner` (owner or owner process), `config` (deep equal after id mapping), `relation` (other sides, other cardinality, or only some sides exist), `unmappable`. When the sides match but the cardinality differs, the definition id is still mapped so the sides' configs do not also report.
- `runSeed`: pass 1 provisions every maintained tenant (unchanged), pass 2 reads the reference once (only if some tenant is already provisioned) and reconciles those tenants, each in its tenant scope. Failures of both passes are isolated per tenant, logged (`errorName`, `tenantId`) and thrown together as one `AggregateError` naming the tenant ids. `SeedResult` gained `reconcile: SeedReconcileReport | null`. `formatSeedLines` prints `seed: tenant <id> reconcile created N properties, M relation definitions` and `seed: tenant <id> conflict <tag> <database>.<key>`; `runSeedCli.js --strict` exits 1 when any tenant reports a conflict (`seedExitCode`); an unknown argument fails.
- `deploy/scripts/cutover-dry-run.sh`: the seed CLI (with its reconcile) still runs after the load; carried-table row counts are now taken right after the load, rows the seed added are listed separately, the seed delta is measured after the seed, and reconcile conflicts are listed under "existing definitions that differ" without changing the exit status (the CLI's non-strict default).
- Docs: `docs/architecture/migrations-and-seeding.md` (new "Reconcile of already seeded tenants"), `docs/operations/production-cutover-to-develop.md` (status, option 1 taken, procedure step 5/6, "a run is good when", preconditions, go/no-go rows, how it was tested).

**Open items for the owner.**
- `calendars.kind` on carried data lacks the `account` option (v0.1.12: `own`, `system`, `subscription`). Item writes refuse an unlisted option, so account calendar sync fails on carried data until the option exists. The reconcile does not change existing definitions (Task); this needs a decision and a follow-up (for example an additive select-option reconcile or a forward-only data cutover). The runbook marks it as blocking the go.
- Views, rollup dependencies and other artefacts that reference properties are not reconciled (out of scope); new properties may not appear in carried views' column lists.
- The runbook's wrapper uses `docker exec -w "$PWD"`, which only works when the current directory is the mounted work dir; the test ran the script from the work dir. Not changed here.
- Not tested: a real production dump, more than one carried tenant in the dry run (multi-tenant isolation is covered by the integration test), Hunspell active.

**Deviations.**
- Task 1's "definitions usable as data" is met by reading them from a rolled-back seed of a scratch tenant rather than by restructuring the ~3,700 lines of seed modules into data; the seed stays the one source.
- Task 4's "run the reconcile between load and seed": the reconcile is part of the seed CLI run (Task 2), which already sits between the load and the delta report; there is no separate reconcile step.
- The acceptance criterion "exits 0" holds because differing definitions do not count as seed delta (same default as the CLI without `--strict`); the `calendars.kind` difference is listed in the report.
