## What was delivered

Three custom routes of the systemDatabases module that write the system-owned relation `Tasks.hostEvents` (inverse `Events.hostedTasks`, owner process `tasks`, schema from gh-1540). The handlers are in the new file `backend/packages/data/src/tasks/taskHostEventRouteHandlers.ts`. The file holds no SQL. Each handler runs one `withTransaction`, locks the task's item row first (`itemsStore.lockItemById`), and writes edges through `createRelationWithClient` / `deleteRelationWithClient` with the context `{ ownerProcess: "tasks" }`, the writer `{ writerKind: "user" }` and the acting user id.

- `PUT /api/tasks/:id/host-events/:eventId`, handler `createTaskHostEventPutRouteHandler(pool)`, manifest route `putTaskIntoEvent`. Puts a task into an event. After the task lock it reads the event (not locked), then the task's `task_recurrence` row `FOR UPDATE` (items before `task_recurrence`, `docs/adr/2026-10-25-task-and-event-recurrence-model.md`). The edge is created, or its metadata replaced, with `{ addedAt }` filled by the server. The request body is not read.
- `DELETE /api/tasks/:id/host-events/:eventId`, handler `createTaskHostEventRemoveRouteHandler(pool)`, manifest route `removeTaskFromEvent`. Removes that one edge and keeps the others.
- `DELETE /api/tasks/:id/host-events` with an optional body `{ date?, timeFrom?, timeTo? }`, handler `createTaskHostEventsClearRouteHandler(pool)`, manifest route `removeTaskFromAllEvents`. Removes every host event edge of the task, edges to trashed events included, and, when the body has a key, patches the task through `updateItemWithClient` as the user in the same transaction. A value the Tasks write refuses fails the request and the edges stay.
- All three are declared in `customRoutes` of `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` with the justification `transactional-semantics`, and the handlers are re-exported from that module and from the `@semprec/data` barrel.
- Three route matrix entries, tenancy `tenant`, in the slice `backend/services/semprec-api/src/routeMatrix/tasks.ts`: "task host event put", "task host event remove", "task host events clear". Each has its `ROUTE_CASES` case in `tenantIsolationRoutes.test.ts` and its `ROUTE_HANDLER_FILES` mapping to `packages/data/src/tasks/taskHostEventRouteHandlers.ts`, all in the same merge.

No migration, no ADR, no job, no write hook, no cutover entry, no generic operation and no i18n key was added.

## Contracts dependents build on

gh-2012 (place one occurrence of a recurring task into an event) declares this source as its blocker. gh-1765 names it as a `Shared-file ordering` blocker only. gh-1780, gh-1781, gh-1801 and gh-1957 read or wrap what these routes store but do not declare this source.

- Answer of all three routes: 200 `{ taskId, hostEvents: [{ eventId, addedAt }] }`, read after the write in the same transaction, ordered by `addedAt` ascending; two edges with the same `addedAt` are ordered by event id. An edge whose event is in the Trash stays stored and is left out of the list, as the generic relation list leaves it out; it is listed again after a restore.
- Edge metadata: every `hostEvents` edge these routes write carries `{ addedAt }` in the form `Date.prototype.toISOString` produces (UTC, milliseconds), so two values compare as instants when compared as strings. `addedAt` is the server clock, or one millisecond after the latest `addedAt` the task already stores when the clock is not past it. Per task the values are strictly increasing: the event put last is last. A put of an event the task already sits in replaces the metadata and keeps one edge per event. A client `addedAt` is never used.
- Refusals:
  - 400 `validation_failed`, `details.field` `id` or `eventId`, for a path parameter that is not a UUID. Ids are accepted in upper case and answered in the stored lower-case form.
  - 400 `validation_failed`, `details.field` `taskId`, on PUT for a task whose `task_recurrence` row is active. A task whose recurrence was turned off is accepted.
  - 404 `not_found` for the task on all three routes: an id that names nothing, a task in the Trash, another tenant's task and a tenant without a Tasks database, alike.
  - 404 `not_found` for the event on PUT: an id that names nothing, an event in the Trash, an id that names a task and another tenant's event, alike.
  - `DELETE` of one event answers 200 with the current list for an event the task does not sit in, an event id that names nothing and another tenant's event, identically.
  - `DELETE` of all events: a body that is not an object is 400 on `body`; a key other than `date`, `timeFrom`, `timeTo` is 400 on that key; both before anything is written. The values are validated by the Tasks write (400 on the property, for example `timeFrom`), which rolls the removals back. An empty body removes the edges and leaves the task as it is.
  - A generic relation write on `hostEvents` or `hostedTasks` is still 403 `owner_violation` (create, update and delete through the choke point facade, and `PUT /api/items/:id/relations/{hostEvents,hostedTasks}/:target` over HTTP).
  - 401 without a session, with `Cache-Control: no-store` (`routeMatrix.test.ts` and `cacheControl.test.ts`, by the matrix names).
- Lock rule a later writer of these edges follows: lock the task's item row first, then read or write its `hostEvents` edges in that transaction. `nextAddedAt` and the clear route's edge list are read under that lock. The event row is not locked; the edge write checks both endpoints again.
- Realtime: the routes send nothing themselves. The relation announcements of the choke point reach the task and the event (one frame per item and property key), and the clear route's task patch sends the item update.
- A done task can be put into an event; nothing else on it changes.
- Exports from the `@semprec/data` barrel: `createTaskHostEventPutRouteHandler`, `createTaskHostEventRemoveRouteHandler`, `createTaskHostEventsClearRouteHandler`. They are in the sorted expected list of `publicSurface.test.ts`. The manifest version is unchanged.

For gh-2012, read on the merged tree and not covered by a test: the recurrence guard is `getTaskRecurrence(client, taskId, true)`, which finds a `task_recurrence` row by `item_id`. The tip has gained gh-1720 since the chain was cut. An occurrence that `POST /api/tasks/series/:seriesId/occurrences/:date` stores carries `seriesId` and `occurrenceDate` but gets no `task_recurrence` row of its own, so such an item is not refused by the guard when it is not the item the series row points at. The Task of gh-1764 names `getTaskRecurrence` as the guard, so this is the specified behaviour; what a stored occurrence in an event means is gh-2012.

## Deviations from the specification and spec seams

1. Spec seam: the three route entries are in the slice module `backend/services/semprec-api/src/routeMatrix/tasks.ts`, not in `routeMatrix.ts`.
2. Outside `Touches`: `backend/packages/data/src/__tests__/publicSurface.test.ts`, which freezes the barrel and needs the three new names.
3. The generic `PUT /api/items/:id/relations/hostEvents/:target` assertion of Task step 3 is made over HTTP inside the "task host event put" isolation case and at the choke point facade in the data test, because a `packages/data` test cannot reach the HTTP adapter.
4. `addedAt` is the server clock or, when the clock is not past the task's latest stored `addedAt`, that value plus one millisecond. A plain "now" would let two puts in the same millisecond, or a clock that stepped back, break "the event put last is last".
5. The response list leaves out an edge whose event is in the Trash; the edge stays stored. `DELETE` of all events removes such edges too.
6. `DELETE` of all events answers the same body shape `{ taskId, hostEvents }`; the Task names no response for it.
7. `DELETE` of one event answers 200 with the current list for an event id that names nothing or another tenant's event, as for an event the task does not sit in, following the Task's idempotency rule. The 404 of the third acceptance criterion applies to the task id on all three routes and to the event id on PUT.
8. The body of `DELETE` of all events must be an object whose keys are among `date`, `timeFrom`, `timeTo`; the values are validated by the Tasks write, not by the route.
9. A malformed UUID path parameter is 400 on `id` or `eventId`, as on the sibling task routes.
10. PUT does not read the request body.
11. The event row is not locked on PUT, to avoid a task-then-event lock order against paths that lock an event first. The edge write checks both endpoints again; an edge to an event trashed in that gap is the state that trashing it after the request leaves.
12. A stored `hostEvents` edge whose metadata has no valid `addedAt` (not writable through these routes) fails PUT and `DELETE` of one event with a 500; `DELETE` of all events removes it.
13. A missing `Tasks.hostEvents` relation fails with a 500 (plain `Error`); a missing Tasks database is 404.
14. `lockLiveTask` repeats the five-line private `lockTask` of `taskRecurrenceRoutes.ts` instead of exporting it, because that file is not in `Touches`.
