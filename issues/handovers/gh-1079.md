## What changed

- **Session role** (`web/src/api/authOperations.ts`): `sessionUserSchema` now has `role: "admin" | "member"`. `login` gets the user from `getSession()` after a 2xx, because the login body carries no role. If that session read finds no session, `login` rejects as `retryable`. All three `SessionUser` fixtures now include `role`.
- **Admin adapter** (`web/src/api/adminOperations.ts`): `createAdminOperations` with `listAccounts`, `suspendAccount`, `reactivateAccount` and `changeRole`. Ids are URL-encoded and every response is zod-parsed. Status `401/403/404/501` maps to `unavailable`. Other failures map to `retryable`. A non-2xx message is the server's `error.code` when present, such as `last_admin`. Otherwise it is `Request to <path> failed with <status>`. A malformed success body is also `retryable`.
- **Route and gate** (`web/src/main.tsx`, `web/src/App.tsx`): `?page=admin` builds the adapter with the session-bound `fetchImpl`. Only an admin session renders `AdminPage`. Any other user sees `admin.notAvailable` and makes no admin request. The header shows an `Admin` link only to admins.
- **Page and panel** (`web/src/views/admin/AdminPage.tsx`, `AccountsPanel.tsx`): The panel uses `useAsyncResource` with loading, error-with-retry and empty states. Each row shows email, role, status, created and last seen (`—` when null). Actions depend on status:
  - `active`: Suspend, and Make admin or Make member.
  - `suspended`: Reactivate, and Make admin or Make member.
  - `provisioning` and `deleting`: none.
  
  Nothing is updated optimistically. The list reloads after a success. After a failure the row stays as it was and shows the message in a `role="alert"`.
- **i18n**: the `admin.*` keys are in both `en` and `cs`.
- **Tests**: new `adminOperations.test.ts` and `AccountsPanel.test.tsx`, plus additions to `authOperations.test.ts` and `App.test.tsx`.

## Choices and deviations

- **Pending label**: only the clicked button shows "Saving…". The other buttons in that row are disabled. The issue asked for disabled buttons, so this is my reading of the pending state.
- **Make admin / Make member**: the label is chosen from the account's current role. The request sends the opposite role.
- **Login now makes two requests** (login, then session). This follows the Task.
