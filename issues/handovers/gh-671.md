## Changes

**`backend/packages/data/src/db/pool.ts`** (`withTransaction` only)
- The `ROLLBACK` on the failure path is now wrapped. If it rejects, the rollback error is logged (`withTransaction: ROLLBACK failed; discarding the connection`) and kept in a local `releaseError`. A non-`Error` rejection is wrapped in an `Error`. The original error from `fn` or `COMMIT` is always what gets rethrown.
- `finally` now calls `client.release(releaseError)`. When the rollback failed, `pg` destroys that connection instead of handing it to the next caller, who would otherwise get `current transaction is aborted`. When the rollback succeeds, the argument is `undefined` and the client goes back to the pool as before.
- A `COMMIT` failure already lands in the same `catch`, so whether that connection is kept also depends on its rollback.
- The doc comment now states both guarantees: the original error is what propagates, and a connection whose rollback failed never returns to the pool.

**`backend/packages/data/src/__tests__/pool.unit.test.ts`** — a new `withTransaction` block using a fake client:
- **`fn` throws, `ROLLBACK` rejects:** the call rejects with `fn`'s error, `release` is called once with the rollback error, and the failure is logged.
- **`ROLLBACK` rejects with a non-`Error` value:** the client is still discarded, with a wrapped `Error`.
- **`fn` throws, `ROLLBACK` succeeds:** the call rejects with `fn`'s error and `release` gets no error argument.
- **Success:** `BEGIN` and `COMMIT` run, the after-commit callbacks run after `COMMIT`, and `release` gets no error argument.
- **`COMMIT` and `ROLLBACK` both reject:** the call rejects with the commit error, the after-commit callbacks don't run, and `release` gets the rollback error.

Not changed, as the issue scopes them out: `createPoolClientTransactionRunner`, `withClient`, and how `runAfterCommit` behaves.
