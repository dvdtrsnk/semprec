## What was delivered

- `backend/packages/data/src/calendar/calendarRowHooks.ts` (new) exports `calendarItemCreateHook`, `calendarItemUpdateHook` and `calendarItemUpdatePreLockHook`. They act on an item of the system database whose `ownerModuleId` is `calendars` and return at once for any other database. Registered in `domainWriteHooks.ts` after the gh-1761 `defaultCalendarCreateHook`: `registerItemCreateHook(calendarItemCreateHook)`, `registerItemUpdateHook(calendarItemUpdateHook)` and `registerItemUpdatePreLockHook(CALENDARS_MODULE_ID, calendarItemUpdatePreLockHook)`.
- Name: a patch that names `name` on a calendar of `kind` `system` or `subscription` is 403 `forbidden` on `name`, for a user, an agent and the system writer alike. The update hook does not see the row before the update, so a patch that sends the stored name again is refused too. Any other kind, an absent one included, can be renamed.
- Colour: a named `color` must be a string `#RRGGBB` (either case), otherwise 400 `validation_failed` on `color`; `null` is refused as well, which the generic colour check lets through.
- Default: a write of `isDefault` true (update or create) takes `pg_advisory_xact_lock` keyed by the Calendars database id, locks the other marked rows `FOR UPDATE` in id order and clears them through `updateItemWithClient` after the new default is written, in the same transaction, so exactly one default remains and a later failure undoes both writes. `isDefault` on a system or subscription calendar, and clearing the mark while no other live own calendar holds it, is 400 `validation_failed` on `isDefault`. A calendar in the Trash is not the default that stays. A tenant that held several defaults before the rules has every other mark cleared by the next switch.
- A generic write of `kind` or `systemKey` is still 403 `owner_violation` from the choke point (unchanged, pinned by a test).
- Fix of the review round: a new update pre-lock hook registry in `chokePoint/hooks.ts` (`registerItemUpdatePreLockHook(moduleId, hook)`, `runItemUpdatePreLockHooks`, types `ItemUpdatePreLockHook` and `ItemUpdatePreLockHookContext`), run by `updateItemWithClient` in `chokePoint/itemWrites.ts` after the patch checks and before the first row lock, for the database's owner module. Calendars registers the hook that takes the advisory lock when the patch names `isDefault`, so every writer of the mark orders its locks advisory lock first and rows after; two concurrent writes of `isDefault` no longer deadlock. A create needs no pre-lock because its row is invisible to others until commit.
- Two new ADRs: `docs/adr/2026-11-12-calendar-rows-keep-one-default-under-an-advisory-lock.md` and `docs/adr/2026-11-12-an-update-takes-the-module-locks-before-it-locks-the-row.md`.

## Review

Two reviewers read the segment read-only: requirements and tests (clear; all five criteria covered) and project rules (one medium finding). The finding: the default switch took the advisory lock after the written row was locked, so concurrent writes of `isDefault` could deadlock and one would fail with a raw database error, contradicting the issue's Decision. The fixer confirmed it and fixed it in `a301c6f13` with the pre-lock registry; four new lock-order tests fail with the registration disabled and pass with it. The recheck passed with no unresolved and no new finding.

Follow-ups, none of them a finding:

- `CALENDAR_COLOR` in `calendarRowHooks.ts` duplicates the choke point's `HEX_COLOR` pattern (style only).
- The clearing write of the previous default carries no `actingUserId`, because `ItemUpdateHookContext` does not carry it; this is a limit of the update hook contract shared by every update hook.
- The residual lock order of decision 3 above, should a path ever write a calendar row and `isDefault` in two steps.
