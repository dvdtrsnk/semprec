# gh-1844 handover: Classify page operations for agents with capabilities, approval and database grants

Delivered on the integration branch by merge `14a0e2214f2f3c46ca736f680addfc5617c45d1f` of chain `e1-095-shared` (members gh-1844 and gh-1861), candidate `15431c339a0a3211535eb62af5d9e0c24136cffe`. The merge was automatic, with no conflict and no migration.

## What was delivered

Every page operation is now held to the agent project's per-database grant and carries a capability, and `page.replace` is held for approval for an agent.

- `resolvePageOwnerDatabase` (`backend/packages/data/src/docs/pageOwnerDatabase.ts`, exported from the `@semprec/data` barrel) answers the database that owns a page: the item's own database, the root host's database for a Pages subpage (walk over `parentItemId`, trashed ancestors followed, bounded at 1000 hops, a cycle or an orphan refused), and the Journal database for a Journal day.
- `assertAgentPageAccess` runs that resolver plus `assertAgentDatabaseAccess` inside the transaction of each page read (`page.get` in both formats, `page.changes`) and each page write (`page.ensure`, `page.createSubpage` including a Journal-period parent, `page.duplicate`, `page.rename`, `page.insert`, `page.replace` through its writer, `page.restoreVersion` through its approval projection). A person's session and a human `/mcp` session are not checked.
- `OPERATION_METADATA`: every page operation now holds `core.item.read` or `core.item.write`.
- `page.replace` is no longer REST-only: an agent's call is held for approval (`PageReplaceCheck`, `computePageReplaceProjection` in `docs/pageReplaceApproval.ts`, snapshot kind `page_replace`, description key `approval.pageReplace` with `en` and `cs` notification catalog entries). The approved replay runs `replacePageMarkdown` authored `user`. A stale etag, invalid Markdown and bad page links answer at the call and create no request. The projection of `page.restoreVersion` now carries the agent project; a revoked grant or an edit after the request ends the request as a conflict.
- Review fix: `page.get` breadcrumbs for an agent return an ancestor that lives in a database the project may not read as `{ itemId, title: "", databaseKey: null, hidden: true }` (`PageSummary.breadcrumbs` gained the optional `hidden`); a person and a project with a read grant see the full entry.

## Deviations and spec seams

- The issue says every page operation carries `core.item.read` or `core.item.write`; the code had `core.page.read` or `core.page.write` (ADR 2026-10-28 section 3, ADR 2026-11-06). The issue was followed and reconciled in the new ADR. The `core.page.*` ids stay registered and the 2026-11-06 manifest exclusion is untouched but has no operation behind it, so project agents now discover all page operations.
- The Task puts the grant check in `genericOperationGateway.ts`; per ADR 2026-09-17 and 2026-11-12 it lives in the data layer in each operation's transaction.
- `page.changes` checks access in its lookup transaction, not inside the later repeatable-read replay (documented in the ADR). The unreadable-database set of the breadcrumb is read in a separate transaction from `getItemPath` (same stance).
- After this change a human-session `/mcp` caller (no run credential) can call `page.replace` without approval, as it already can for `item.delete`; only a run credential is approval-gated.
- Spec seam: the web approval catalog (`web/src/i18n/messages.ts`) has no `approval.pageReplace` entry; `web/` is out of scope, the backend `en` and `cs` notification catalogs have it.
- Several existing tests that assumed REST-only `page.replace` or `core.page.*` run credentials were updated (gateway, operation catalog, AgentTool and MCP contracts, `pageChangesHandler`, `pageMarkdownInsert`, `pageMarkdownReplace`).

## Not run, BLOCKED

- BLOCKED: the literal acceptance criterion "a run whose project has the Journal grant read-only gets 403 on a write to a day's page" (a read row on the shipped, non-sensitive Journal). The delivered grants model (`effectiveAccessSql`, ADR 2026-11-12 per-database agent grants, gh-1810 and gh-1841) opens every non-sensitive system database and ignores stored rows, so a read row cannot restrict the shipped Journal. The same code path is proven with the Journal flagged `sensitive` by a raw `UPDATE databases SET sensitive = true` (restored in `finally`, labelled `setJournalSensitive` in the test). The criterion stays unproven for the shipped Journal until the owner decides: let a stored row restrict an open system database, or amend the criterion.
- The whole `pnpm run verify` integration tier is not part of this landing (queue runner checkpoint); the known macOS baseline case of `mcpConnectionFactory.test.ts` was not run.
- No live provider or production criterion exists.

## Follow-ups from review

- The BLOCKED Journal read-only scenario above (three findings of medium, high and high severity with one root cause, rejected in the fix round because the fix would narrow an accepted ADR and change every guarded path, not only pages; the recheck agreed and asked that the criterion stay reported as BLOCKED).
- `web/src/i18n/messages.ts` needs an `approval.pageReplace` entry (client work, out of scope).
- Item operations (`item.get`, `item.list`) on rows of the always-open hidden Pages database still return titles and `parentItemId` of subpages whose root host is in a restricted database; they are item operations and listed as later paths by the gh-1810 ADR.
