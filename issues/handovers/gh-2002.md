# Handover for gh-2002

Let the user hide the Recipes collection from the overview. Candidate commit `02a0cc148739de150256525b97449a61834b6ff3` landed on `feature/backend-parallel` with merge `0fc8851fe6be7cc335afc51f5846e25f0461fa8e` (chain `e1-035-shared`, its only member). The segment of this source is that one commit. The chain landed alone, not as part of a train, at its first landing attempt. The acceptance receipt is `issues/batches/backend/acceptance/sources/gh-2002.md`.

## What was delivered

- A stored flag per database, `databases.overview_hidden boolean NOT NULL DEFAULT false` (migration `0149_database_overview_hidden.sql`). Every existing row reads false without a backfill, and an `INSERT` of the previous release, which omits the column, still succeeds. No grant, policy or role changed: the runtime role `semprec_data` holds table-level privileges on `databases` and writes the column.
- An optional descriptor field `overviewHideable` on a module's database descriptor. Only `true` has an effect. The `recipes` descriptor declares it; no other module does.
- `database.patch` accepts an optional boolean `overviewHidden` in its `patch`. The choke point writes it in the one `UPDATE` that writes `name`, `icon` and `color`, and only for a system database whose module descriptor declares `overviewHideable: true`. For every other database (a system database without the declaration, a user-created database) the patch is refused with `ForbiddenError` ("This database cannot be hidden from the overview") before the statement runs, so none of its other fields is written either. Over REST that is 403 `forbidden`. A value that is not a boolean answers 400 `validation_failed` with `details.field` `patch.overviewHidden`.
- The schema invalidation `notifyInvalidation({ scope: "schema", databaseId, userId })` is published after the commit as for any other database patch, once per successful patch. A refused patch publishes nothing.
- The database envelope of every `/api/databases` route carries `overviewHidden`, and so does each database of the schema projection (`GET /api/schema` and the "Data schema" text of the agent thread prompt).
- Hiding changes nothing else: `overviewOrder`, `switcherOrder`, `clientVisible`, the position of the database in `GET /api/databases`, `database.query`, search and the refusal to archive a system database are as before. No server-side list filters on the flag; the client decides what the overview shows.

## Deviations from the specification and spec seams

1. `Touches` names `services/semprec-api/src/databasesHandler.ts`. It is unchanged: its PATCH route already forwards the whole body as the patch of `database.patch`. The envelope field is added in `adapter/databaseEnvelope.ts`, which `Touches` does not list and which is the one place every `/api/databases` route builds its body.
2. The choke point holds no module registry, so the store cannot read a descriptor itself. `databasesStore.patchDatabase` and `chokePoint.patchDatabase` take the optional last argument `resolver`, the seam `chokePoint/itemReads.ts` already uses for `collectionFilter`. No ADR was added; the rules reviewer judged it an extension of an existing seam.
3. Owner decision left open: Task step 3 puts `overviewHidden` on `CollectionMetadata`, and `manifest/schemaProjection.ts` spreads the resolver's result, so `GET /api/schema` and the "Data schema" text of the agent thread prompt carry `overviewHidden` per database as well. The Task names only the database envelope. The field is typed on `SchemaDatabaseProjection` and one handler test pins that both endpoints agree. Recipes is still listed there, so the out-of-scope line about hiding from agents is not touched. If the schema projection must stay as it was, the field has to be dropped there explicitly.
4. `resolve()` takes `overviewHidden` as an optional input, because `relationExpansion.ts` calls it with `key`, `system`, `icon` and `color` only.
5. The guard reads the database row inside the patch transaction without a row lock, like the icon and color guard of the same function. It depends on `system` and `key`; no request path updates either (only the deploy-time mail key cutover rewrites `key`). No serialization is claimed.
6. Tests outside `Touches`: the 24 resolver stubs, two `DatabaseRow` fixtures, the re-recorded hash in `jsonSchema.unit.test.ts`, and the exact shapes in `collectionMetadata.unit.test.ts`, `recipesModuleManifest.unit.test.ts` and the envelope schema of semprec-api `recipesModule.test.ts`.

Spec seam: `migrationCompatibility.test.ts`, case "adds the move state table over populated mail without changing existing metadata", ran the current database writer on a schema migrated only up to 0128. The writer's `RETURNING` now names `overview_hidden`, so the fixture writes its two databases and their items partitions with SQL in that schema's shape, as it already did for the item rows. A later column on `databases` meets the same seam in any test that runs current writers on a partially migrated schema.
8. The two-tenant runtime-role test over HTTP is in semprec-api `recipesModule.test.ts`, which has that harness. `databasesHandler.test.ts` keeps its superuser pool and one tenant; its tests prove the acceptance criteria, not isolation.
