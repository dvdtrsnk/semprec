## What was delivered

A file attached to an Event (a `Files.events` edge) now takes over that Event's project, and its company follows from that project.

- The link rule `fileProjectsFromEvents` is declared in `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts`: source `Events.project`, target `Files.projects`, via the `Files.events` relation. `Files.projects` stays `owner: user`; the `valueLinks` process writes it only while the file's link for that property is `on`. The company then follows through the existing rule `fileCompaniesFromProjects` (#1653). No new property or relation, no i18n label (the catalogs have no label for any link rule).
- `eventAttachmentLinkReleaseEdgeChangedHook` (`backend/packages/data/src/blobs/eventAttachmentLinkRelease.ts`, new) is a relation-edge-changed hook that acts only on the removal of a `Files.events` edge. It is registered in `backend/packages/data/src/domainWriteHooks.ts` directly before `linkRuleEdgeHook`, because it has to read the file's `projects` link before the engine's hook deletes it. Lock order: file row (through `lockItemById` on the Files database, `itemA` then `itemB`), then the `projects` link row, then the `companies` link row. Branches:
  - the removed Event is the only source of the file's `fileProjectsFromEvents` link, whatever its state: the hook deletes that link and the file's `fileCompaniesFromProjects` link (if any, whatever its state) with their source rows and announces the file after the commit. Project and company stay as the file's own values;
  - another Event also feeds the link: the removed Event is detached from the sources when the link is not `on` or the file is in the Trash (the engine skips a trashed target, review round 1 finding), and the file is announced; a live link that is `on` is left to the engine's hook, and the `companies` link is left alone;
  - the link does not name the removed Event, belongs to another rule, or the file has none: nothing changes, so a company that follows a project the file had on its own keeps following it.
- ADR `docs/adr/2026-11-15-an-event-attachments-company-link-ends-with-the-attachment.md`: the rule, the ownership of `Files.projects`, the release with its condition, place and lock order, no backfill, that moving the Event to the Trash leaves the company link on, and the order of a user edge write on `Files.projects` against the propagation (set by the value-link-edge-lock-order source; this source adds no order of its own).

Entry points and contracts dependents build on:

## Deviations from the specification and spec seams

1. `linkRuleEdgeHook.test.ts` is listed in Touches for a fixture rule that would close a cycle with the new rule; with the rule declared that file passes unchanged (the fixture rule runs from `Files.projects` to `Tasks.project`, not back to `Events.project`), so it was not touched.
2. The hook announces the file also in the branch where it only detaches the Event from a link that is not `on` or from a link of a trashed file; the Task names the announcement only for the release branch. The transcript hook announces whenever a link changed.
3. No i18n label was added: the catalogs have no label for any link rule.
4. The hook finds the Files side of the edge by locking with `lockItemById` on the Files database, `itemA` then `itemB`, instead of a separate read, so the first lock is the file row.
5. The release hook is registered before `linkRuleEdgeHook`, which departs from the controller convention that a later source registers after its blockers; the Task and the ADR require it.
6. A few tests build states the API cannot produce (a raw SQL `Files.events` edge written without hooks, links of another rule written through the store), each marked in the test.
7. The multi-source branch also detaches the removed Event when the file is in the Trash (Task step 5 says the engine does this for a link that is `on`; it does not for a trashed target). The hook comment and the ADR state the corrected condition.
