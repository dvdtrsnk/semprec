# Handover for gh-1470

Transcripts now has project, company and people relations with inverses on Projects, Companies and People, for fresh installs (seed) and populated tenants (cutover). The work is committed locally; I did not push or open a PR.

The targeted integration tests pass: `transcriptsCatalogCutoverMigration`, the new `transcriptRelations`, `tenDatabases`, `systemI18nCatalogCoverage` and `tenantCutoverMigrations`. Prettier and `tsc` pass for the touched files. I did not run the full `pnpm run verify`.

- **Seed:** three `relate(...)` calls in `seedTenDatabases.ts`. `Projects.transcripts` and `Companies.transcripts` are property A of `one_to_many`, with the single-valued inverses `Transcripts.project` and `Transcripts.company`. `Transcripts.people` is `many_to_many` with the inverse `People.transcripts`. All six are `owner: user`. Names were added to `en.json` and `cs.json`.
- **Cutover:** `runTranscriptsCatalogCutoverMigration` loops over a pair table and, per pair, skips when the Transcripts-side property exists or the other database is missing. Otherwise it inserts both properties (name `NULL`, like the seed), the `relation_definitions` row and the config on both sides. It runs under the existing `properties` table lock.
- **Tests:** the cutover test reverts the three pairs, checks both sides, target databases, cardinality and which side is property A, and that a second run changes no properties or definitions. `transcriptRelations.test.ts` covers a fresh install, `CardinalityViolationError` for a second company or project, and several people visible from both sides.
- **Notes for dependants:** the people edges live in `item_relations` under the definition whose `property_id_a` is `Transcripts.people`. For project and company the "one" side is the Projects/Companies `transcripts` property, so a write from the transcript uses `Transcripts.project`/`company` as the relation property. The properties are `owner: user`; #1697 changes who may write them.
