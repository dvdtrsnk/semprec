## Delivered behavior

- Shared input schemas preserve [] and ["links"] and accept a strict { links?, relations? } object. Relation maps are limited to five keys and projections to ten properties; validation errors retain the offending include.relations path. Shared Item output types expose expanded and reduced targets and the optional per-property blob metadata map.
- Item, database and view generic reads pass expansion into the existing tenant transactions. Empty database/view pages still validate keys against their owning database where one is defined. The existing port and bindings derive these input/output types, so no separate dispatch changes are needed there.
- relationExpansion.ts batches source/target property catalogs, edges, target databases, target rows, projected blob metadata, and an optional nested read. Target reads remain grouped by database ids in one statement. Edges are filtered for visible live targets in unarchived databases before SQL ranking; at most 51 edges per source/key reach the application, the first 50 are returned and overflow is named in relationsTruncated. Nested relations return only the reduced shape and are bounded to 50 per source/key. Ordering uses stored metadata.addedAt text where present, otherwise edge id, with edge id as tie-breaker.
- Target read projections run with the owning module resolved from the batched database read. Appearance uses non-empty item schema values first, then the required supplied CollectionMetadataResolver, omitting unresolved fields independently. Blob reads use one tenant-scoped SQL lookup over projected file/image references, retaining property values, omitting invisible/missing metadata and empty maps, and matching #1412's filename contract. The choke point imports no blob domain implementation and loads no manifests.
- REST supports path, links and relations together; explicit relations.key parameters select keys including empty projections. Bare relations selects all relation properties and rejects more than five. Breadcrumb and final item still come from the same path transaction; expansion of that final item runs inside it. Item envelopes preserve relations and truncation markers.
- app.ts and agentSessionComposition.ts construct metadata resolvers from their loaded registries. The service, gateway, agent execution helper and discovery helper require and forward that dependency. Existing factory-call tests receive explicit inert resolvers when they test unrelated behavior; production has no optional fallback resolver. Agent composition unit tests assert forwarding to both helpers.
- No new choke-point method or runtime data-package barrel export is required: the existing read methods carry the expansion option. No migration or persisted data write is introduced.
