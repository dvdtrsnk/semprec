## What was delivered

`importSubscribedEvents(client, { calendarItemId, body })` is the consumer for the downloaded ICS feeds of gh-1960. It parses the body with `ical.js` 2.2.1 (exact pin, `@semprec/data` dependency, lockfile updated) completely before any write. A malformed, truncated, empty, multi-calendar or non-VCALENDAR text throws `CalendarFeedParseError` (constant message, no feed text) and the sweep records a failed consumer and keeps its validators. Each VEVENT becomes a `subscribedEvents` item matched by `(calendar, uid)`:

- timed events are converted to the tenant wall clock with `calendarTime.ts` (TZID and `Z` forms; the original zone is kept in `timeZone`, UTC is named `UTC`); floating times are stored unchanged without `timeZone`; DURATION ends are read in the start's zone;
- all-day events are stored at midnight of the first day and of the inclusive last day (exclusive DTEND minus one day; no end for a single day);
- components with RECURRENCE-ID are skipped, a component with RRULE is stored once at its own start (gh-1966 replaces that);
- a new UID is created with the calendar edge; a differing row gets only the changed values; an unchanged row is not written (no `updated_at` change); a live row whose UID left the feed goes to the Trash through `itemDeleteWithClient` (restorable, a reappearing UID creates a new item); a UID whose VEVENT became unreadable keeps its row.

All writes go through the choke point with `systemOwnerProcess` `calendar`, so user, agent and `/mcp` writes stay refused.

## Deviations from the specification and spec seams

1. The Task says the import runs in chunked transactions for large feeds. It does not. The reason, as corrected by the review fix (the worker's original text overstated it with the validators): the gh-1960 consumer contract hands the consumer the sweep's one per-calendar client, so this function cannot commit chunks; a chunked import needs a contract change in gh-1960, which this issue's Out of scope assigns elsewhere. The work is bounded by the 5 MiB body cap and is linear in the feed. A per-feed event cap was declined because it would make large feeds fail permanently. A failure rolls everything back and the old validators stay, so the feed is requested again.
2. `startsAt` and `endsAt` are stored as zone-less wall-clock text, as above.
3. An event with no UID, an unreadable time or a zone the server does not know is skipped and counted (`unreadable`, and in the log); an unreadable entry keeps the stored row of its UID.
4. A repeated UID in one feed keeps the first VEVENT; several live rows of one UID keep the oldest and trash the rest.
5. `ical.js` 2.2.1 is imported as the default ESM export; it was published 2025-08-08.
6. Spec seam: the Touches list says "the registration site of the calendar module's process hooks"; that is `domainWriteHooks.ts`, where the gh-1960 purge hook already sits.
