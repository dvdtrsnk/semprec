# Handover: Overview and account summary on one connection, IMAP fetch outside transactions, smaller mail sync job fan-out

Implementation commits on `feat/internet-accounts`: `e4788b5b0` (IMAP pass), `37333619d` (reads), `666e88783` (job fan-out). Nothing was run against the dev VPS or production.

**Dataset.** Embedded Postgres 18 (the VPS runs 16), one tenant seeded through the production writers: 15 000 Emails in 14 000 threads over INBOX, Archive, Sent, Trash and Junk, 1 704 Events in 6 account calendars (a fake CalDAV pass), 600 Tasks, 199 Journal days. Medians of 7 calls on a shared, loaded host.

**Root causes and changes.**
- Mail summary statement, 145 ms of both the Overview and the account summary. The thread copy CTE ran a lateral folder lookup per Email (15 000 loops), re-evaluating the inlined `folder_definition` CTE in each. It now aggregates the folder edges once per Email and hash-joins them. In detail mode the aggregate is restricted to the thread, and in the new `unreadCandidatesOnly` mode to the candidate threads. Every caller keeps its results; the existing list, detail, facet, folder and action tests are unchanged and green.
- Account summary: five transactions at once through `Promise.all`, plus the full mail summary statement for two mailbox figures. It now reads in one REPEATABLE READ transaction on one connection, and the mailbox figures come from `getMailAccountsSummary`.
- Overview: three transactions in sequence. It now uses one, and its unread count comes from `countUnreadInboxThreads`, which reads the thread CTE only over threads that have a copy not read. That count equals the mail summary's `unreadInbox`; `mailSummary.test.ts` asserts it in every scenario. The Semp status report reads its catalogs once per process, and `readSempStatusSummary(client)` runs in the caller's transaction.
- `heartbeatFireCore`: no sweep is involved. Each new Email fires three deterministic `onItemEvent` heartbeats: `mail.linkPeopleByEmail`, `calendar.ingestInvitation` and `calendar.applyInvitationReply`. These now get one job per heartbeat and transaction, payload `itemIds`. The fire task runs the handler per item and fails after all items ran when one failed; a retry runs all of them again. The action ids moved to `calendar/invitationActionKeys.ts` and `mail/personLinkingKeys.ts`, so the scheduler can name them without an import cycle.
- `itemSearchReindexDependents`: each Email's edges queued an `item` reindex of the Email, which `indexItem` skips. The edge hook no longer queues it for an Email end.
- `valueLinksPropagate`: two jobs per new thread, not per Email. The project rule is now queued at the first inbound message only for a thread with a live company or a project link. Otherwise the company rule's edge write queues it.
- IMAP pass: see `e4788b5b0`. Provider calls run with no transaction open, attachments are spooled to temp files first, and writes happen in short transactions (prepare, one per folder batch, final). Each transaction re-enters under the mailbox sync guard, then takes the mail-thread lock. A batch writes only while its folder state matches the snapshot its fetch started from. A failed batch deletes only its own attachment bytes.

`EXPLAIN ANALYZE` found no statement slow for lack of an index (everything but the mail statement is under 6 ms), so no index was added. A partial index for unread Emails was rejected: its predicate cannot exclude non-Email items.

**Tests added or changed.**
- `profileAccountSummary.test.ts`: one connection and no `pool.query` per call. The all-or-nothing failure test now refuses each statement on that connection.
- `overviewSummary.test.ts`: one connection per call.
- `mailSummary.test.ts`: the Overview count and the mailbox figures equal the route in every scenario.
- `threadLinkRules.test.ts`: a new thread queues the company rule only; a thread that already has a company queues both rules.
- `mailSyncJobFanout.test.ts`: the job counts above through a real IMAP pass with a fake client, and the batched fire's per-item handling.
- IMAP pass tests (see `e4788b5b0`): no transaction or advisory lock during a slow fetch or attachment download; an overtaken pass writes nothing; failed batches clean up only their own bytes.

**Behaviour that changed on purpose.** A removal or the Mail switch waits only for the IMAP pass's current transaction, and the pass stops at its next one. Two passes of one mailbox can fetch at the same time; the state check keeps the result correct, but the provider work is repeated. Flag write-back confirmations are written in the final transaction, so a pass that fails after an IMAP flag write sends that write again next pass. A batched heartbeat fire's failure notification and `last_error` are recorded once per batch, not per Email.

**Not done (follow-ups).**
- The Gmail and Graph passes still call their provider inside their transaction.
- The timeline (70 queries, 21 of them `databases` row lookups) and the mailbox list (one permission manifest per project) were not changed. Locally they take 30–40 ms and 10–15 ms. The VPS numbers were measured during the initial mail sync, so pool waits behind long transactions likely account for much of them; measure again once this is deployed.
- Pool size (10) and worker concurrency (4) were not changed.
- `services/semprec-api/src/__tests__/adminHandler.test.ts` ("operations health … no tenant content") fails independently of this change. It still seeds a global `mail:` observability row, which the first-version commit `c755eac7e` stopped filtering out of the operator report.
