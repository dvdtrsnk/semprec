## What was delivered

- A new relation between two system databases: `Tasks.healthRecords` with the inverse `HealthRecords.tasks`. It is `many_to_many`, both properties are owner `user`, `locked` false and `name` NULL, and `Tasks.healthRecords` is property A of the relation definition.
- New tenants get the pair from the relations pass of `seedTenDatabasesInTransaction` (`backend/packages/data/src/seed/seedTenDatabases.ts`), after "Health records -> Projects" and before the schemas are locked.
- Existing tenants get it from the new per-tenant cutover `runHealthRecordTasksCutoverMigration(pool)` in `backend/packages/data/src/seed/healthRecordTasksCutoverMigration.ts`, registered in `runTenantCutoverMigrations`. In one transaction it resolves the tenant's Tasks and Health records databases by module id and returns when either is missing, takes `LOCK TABLE properties IN EXCLUSIVE MODE`, returns when `Tasks.healthRecords` exists, and otherwise inserts both properties, the `relation_definitions` row and each property's `config` `{ relationDefinitionId, targetDatabaseId }` with raw SQL, checked with `requireSingleRow` and `requireAffectedRows`. `databases.schema_locked` is not written, so both databases stay locked. A second run writes nothing.
- The seed catalogs carry the labels: `property.tasks.healthRecords.name` is "Zdravotní záznamy" in `cs.json` and "Health records" in `en.json`; `property.healthRecords.tasks.name` is "Úkoly" and "Tasks".
- Confirm code was not changed. The multi-step confirm of gh-1486 already writes a task step with `relations: { healthRecords: [{ ref }] }` once the relation exists; this source adds the tests that prove it for a health record with a follow-up task.

## Contracts dependents build on

- Property keys: `healthRecords` on the Tasks database (module `tasks`) and `tasks` on the Health records database (module `healthRecords`). Both are relation properties with `config = { relationDefinitionId, targetDatabaseId }`; `GET /api/schema` (through `generateSchemaProjection`) returns each with `config { targetDatabaseId, cardinality: "many_to_many" }` and the Czech or English label.
- Direction: `Tasks.healthRecords` is property A, `HealthRecords.tasks` property B. An edge is written from either side with the choke point's `createRelation` and read with `listItemRelations`; `queryDatabaseItems` on Health records accepts a `relation_contains` filter on `tasks`. One task may be linked to several records and one record to several tasks.
- A multi-step proposal links the follow-up task to the record created in the same proposal with a step relation `healthRecords -> { ref: <record step> }`. Confirm writes the record, the task, the edge and the card status in one transaction. A confirmed health record has no `area` edge unless the user sets one or a project derives it (gh-1595).
- Export: `runHealthRecordTasksCutoverMigration(pool: Pool): Promise<void>` from `backend/packages/data/src/seed/healthRecordTasksCutoverMigration.ts`. It is not re-exported from `backend/packages/data/src/index.ts`; its only production caller is `runTenantCutoverMigrations`. It must be called inside a tenant scope on a pool that row-level security applies to.
- Registry order in `backend/packages/data/src/db/tenantCutoverMigrations.ts`: the step stands directly after `runTaskRecurrenceSeriesCutoverMigration` and before `runJournalProjectCutoverMigration`, and so after `runSelectOptionColorsCutoverMigration`, the step that carries the entry of the in-chain blocker gh-1705. gh-1486 has no step. The cutover has no functional order dependency on another step.
- Order for gh-1833: when it lands, its step in `db/tenantCutoverMigrations.ts` goes before `runHealthRecordTasksCutoverMigration`, unless its Task names another position.
- The step runs after `runTaskRecurrenceSeriesCutoverMigration`, which can throw for a tenant by design (`docs/adr/2026-11-07-task-series-cutover-uses-bounded-owner-backfill.md`). In such a run that tenant does not get the relation until the cause is repaired and the deploy is run again.
- Failure contract: when `HealthRecords.tasks` exists without `Tasks.healthRecords`, the second insert raises a unique violation (23505), the transaction rolls back and `runTenantCutoverMigrations` reports that tenant; the later steps of that tenant's run do not run. No seed, cutover or production write leaves that state, because both schemas are locked.
- The cutover takes an `EXCLUSIVE` table lock on `properties` for the length of its transaction, once per tenant per deploy. Plain reads are not blocked; writes to `properties` wait for it.
- Not carried on recurrence: `CARRIED_RELATION_KEYS` in `backend/packages/data/src/tasks/advanceTaskRecurrenceWithClient.ts` does not list `healthRecords`, so the next instance of a recurring task does not keep the link.
- No route, table, SQL migration, generic operation, MCP tool, job name, barrel export or ADR was added.

Follow-ups, none of them filed as an issue:

- `CARRIED_RELATION_KEYS` does not list `healthRecords`: a recurring follow-up task loses its link to the record at the next instance. The docstring of that constant already says that a relation added later is not carried until its key is added.
- Health records items are not in the proposal workspace context, so a proposal can link a follow-up task only to a record created in the same proposal, not to an existing one.
- The idempotency check keys on `Tasks.healthRecords` only. A tenant that held `HealthRecords.tasks` alone would fail on every run and skip the later steps of its run. No write can leave that state today.
- Three private copies of `insertUserRelationProperty` exist (`blobs/eventsFilesRelationCutoverMigration.ts`, `transcription/transcriptsCatalogCutoverMigration.ts` and this cutover).
