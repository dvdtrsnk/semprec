# Handover for gh-1516

The choke point now maintains value link state on writes. A `user` or `agent` write that changes a linked value ends the link (`state = 'broken'`, `broken_by`, `broken_at`); `system` writes never do. The work is committed locally; I did not push or open a PR.

- **New module:** `chokePoint/valueLinkWrites.ts` exports `VALUE_LINKS_OWNER_PROCESS` (`"valueLinks"`, also exported from the data barrel), `breakValueLinks(client, { itemId, propertyKeys, writerKind })` (returns the item ids whose state changed; no-op for `system`, a missing row or an already broken row), `assertValueLinkHandoff(client, { itemId, propertyKey })` (403 `owner_violation` unless an `on` row exists; it reads the row `FOR SHARE`) and `breakValueLinksForRelationEdge(client, { reldef, itemA, itemB, writerKind })`. The last resolves both sides of the definition (item A with the key of `propertyIdA`, item B with the key of `propertyIdB` when set), breaks both and sends one `item`/`update` invalidation per changed item after commit.
- **Store:** `valueLinksStore.ts` gained `breakOnValueLinks` (one `UPDATE ... WHERE state = 'on' RETURNING property_key`, so the first `broken_by` and `broken_at` are kept) and `lockOnValueLink`.
- **Item path:** `updateItemWithClient` compares each patched input key with `previous` (already read under the update's row lock, from #2048) using deep equality and breaks the changed keys. With `options.systemOwnerProcess === "valueLinks"` it asserts the handoff for every patched key before anything is written.
- **Relation path:** `createRelationWithClient` breaks only when the edge was inserted. `relationsStore.createItemRelationReportingInsert` is new and reports this through `(xmax = 0)` on the upsert, so a repeat put is not a change; `createItemRelation` wraps it unchanged. `deleteRelationWithClient` breaks only when a row was deleted. `updateRelationWithClient` (metadata only) breaks nothing. Item path and relation path each use the `writer` they already received.
- **Handoff on relations:** `relationEdgeContext.assertRelationValueLinkHandoff(client, property, context, callerItemId)` runs in create, update, delete and `assertRelationCreatableWithClient` for a user-owned property when `context.ownerProcess` is `valueLinks`. `owner: "system"` properties behave as before.
- **Tests:** `valueLinkWrites.test.ts` (20 cases): user, agent and system patches, same value, mixed keys, first `broken_by` kept, rollback with the write, second project edge (also through the project's `files` property), delete present and absent edge, existing edge and metadata replace, invalidation after commit, the handoff for create, update and delete with no row, broken row and `on` row, the same for a plain property, and a two-tenant case on a runtime-role pool. `publicSurface.test.ts` lists the new export. I ran these with `relationOps.test.ts` and `writerKind.test.ts`; typecheck, eslint, prettier and dependency-cruiser pass.
- **Not covered:** the REST and MCP routes were not driven end to end (the writer reaches the choke point from #1415, tested there); I tested at the choke point with explicit writers.

Notes for dependants:

- #1593 must insert the `on` row before it writes the value, and write through `updateItemWithClient` with `systemOwnerProcess: "valueLinks"` or a relation call with `{ ownerProcess: "valueLinks" }`; its writer stays `system`, so the state stays `on`.
- #1521 (single-valued replace) can call `breakValueLinksForRelationEdge` with the edge it added or removed.
- The handoff check on relations covers the caller item and property only, not the other side of the edge.
