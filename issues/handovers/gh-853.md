**What changed in `lifecycleAdapter.ts`**
- A small private helper, `closeAtomically`, opens one transaction with `withTransaction` when the caller passes a bare `Pool`. It reuses the client as-is when the caller passes a `PoolClient`, so that caller's own `ROLLBACK` still decides.
- On the success path, `finishAgentRun(..., "done")` and `pushRunStatus(..., "done")` share that transaction. If either throws, neither commits and the existing catch block's error close is the only terminal state that lands. That rules out a `done` event followed by an `error` event.
- On the error path, `finishAgentRunWithErrorNotification` and `pushRunStatus(..., "error")` share one transaction.
- On either path, when the close returns `false` (another closer got there first) the terminal event is skipped. The success path still returns the row as `getAgentRun` reads it, and the error path still rethrows the session error.
- The `logger.error` for a failed error-path close and the rethrow of the session error are unchanged.

**Tests**
- Nine new tests in `lifecycleAdapter.test.ts` cover each acceptance criterion. Failures are injected with temporary Postgres triggers, so the pool stays a real `Pool` and the failure happens in the actual write.
- They check the bare-pool `done` and `error` closes (one terminal event each) and persistent `pushRunStatus` failure on both paths (row stays `running`, no terminal event).
- They also check a one-time `done` event failure falling back to a single `error` event, `finishAgentRun` throwing on the success path, and the row closed elsewhere on each path.
- A caller-supplied `PoolClient` test shows the caller's `ROLLBACK` leaves the row `running` with no terminal event from the session.
- I moved the pool `afterAll(pool.end())` to file level so both `describe` blocks can share the pool.
