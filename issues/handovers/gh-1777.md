## Contracts dependents build on

- **`ItemCreateHookContext.initialRelations`** is what a create hook reads to learn which relations its create is about to write.
  - A create through `createItemWithRelationsWithClient` carries the relations it was given, each with its relation property id and target item ids. A create given no relations carries an empty list.
  - A relation whose property key the caller could not resolve (`kind: "unresolved"`) is not listed; that create throws `ValidationError` "Unknown relation property" after the hooks.
  - A create through `createItemWithClient` leaves the field absent. `createItemReportingReplay` has exactly two callers, `createItemWithClient` and `createItemWithRelationsWithClient`.
  - **The field is an announcement, not a fact.** When the hooks run, none of those edges is stored and none of the relations is checked: the property may belong to another database, a target may not exist, a single-valued relation may name no target or several. A hook may use the field to leave a write to the create; it must not treat it as a stored edge.
  - `ItemCreateInitialRelation` is exported from `chokePoint/hooks.ts` only. The barrel still exports `createItemWithRelationsWithClient` and `InitialItemRelation`, as before.
- **Create order.** Insert, pre-existing create hooks in their registered order, then each relation in the order given through `createRelationWithClient`. The first refused relation throws.
- **The Event's calendar when `relations` name it.** The hook writes no edge. The create writes the calendar relation itself, as a write of the create's own writer (the hook's edge is a system write). `Events.calendar` is single-valued, so the create stores exactly one calendar edge or throws; with `chokePoint.createItemWithRelations` the whole create runs in one `withTransaction` and rolls back.
- **A create hook cannot rely on finding the Event's calendar edge**, wherever it is registered: when the relations name the calendar, the edge is written after every hook. A hook that needs the calendar reads the stored edge and, when there is none, the calendar named in `initialRelations`, unchecked at that point.
- **The calendar named in `relations` is judged as a generic relation target**: a live item of the tenant's calendars database. The rule of gh-1761 for a calendar chosen with `withChosenCalendar` (`kind` empty or `own`) and its `FOR SHARE` lock do not apply on this path, as they do not apply when a user changes the calendar of an existing Event through the relation endpoint. A system calendar such as Birthdays can therefore be named at create. A calendar chosen with `withChosenCalendar` is ignored and not checked when the relations name the calendar.
- **The default calendar is not read** when the relations name the calendar, so a tenant without a live default calendar still creates the Event in the named calendar.
- **Without a calendar relation** (no relations, an empty list, or relations that name other properties only) the hook links the default calendar exactly as gh-1761 delivered it.
- **Replay.** An idempotency-key replay runs no hook and writes no relation; it returns the stored item whatever properties and relations the replay names.
- **Errors on this path.** An unknown target id, another tenant's id and a trashed item are answered alike. The date and time refusals are those of `eventValidationHook.ts` (gh-1663): 400 `validation_failed` on `timeTo` or `date`.
- **Transport.** `POST /api/databases/:id/items` with `relations` and the `Idempotency-Key` header reaches this path (the route and the `relations` input are gh-1590's; nothing in the transport changed).
- **Type.** An Event created without `type` stores no `type` key. No code was needed for it.
- **Not covered: the Inbox proposal confirm** (`inbox/proposalActions.ts`). It creates with `createItemWithClient` and writes the envelope's relations itself, so its create hooks get no `initialRelations`. What the handover of gh-1761 says about an Event proposal whose relations name another calendar still holds.

## Deviations from the specification and spec seams

1. Mechanism: the Task allows either writing the relation edges before the Events create hooks or passing the relations to them. The second was chosen and the order of the create path is unchanged; the ADR says why (edges first would change the order for every database, so edge hooks would run for an item whose create hooks had not run).
2. Task step 2 says the hook is a no-op when the Event already has a calendar edge in this transaction. That branch exists since gh-1761 and is unchanged. The new no-op is for the edge the same create is about to write, which is not stored yet when the hook runs.
3. Task step 1 asks to describe the mechanism in the pull request. This program has no pull request per source; the mechanism is in the commit body and the ADR.
4. Files outside `Touches`: `chokePoint/hooks.ts`, `chokePoint/itemCreateWithRelations.ts`, the new ADR, the new HTTP test under `services/semprec-api`, and two tests added to gh-1590's `itemCreateWithRelations.test.ts`. Listed in `Touches` and not edited: `domainWriteHooks.ts`.
5. The calendar named in `relations` is not held to the own-kind rule of `withChosenCalendar` and is not locked `FOR SHARE`. The Task has no step for it; a test pins the behaviour and the ADR names it.
6. The Inbox proposal confirm is not covered (see above); its file is not in `Touches`.
7. gh-1675 lists #1777 among the issues where the Event description declares the Markdown format. The Task of gh-1777 has no such step, so `Events.description` stays a `longText` without a declared format; the tests store and read back a Markdown string with a `- [ ]` line unchanged.
8. Acceptance criterion 1 says "one transaction". It is shown by the rollback of a caller-supplied transaction and by `chokePoint.createItemWithRelations` running the create in one `withTransaction`. No concurrency claim is made and no concurrent test exists.
