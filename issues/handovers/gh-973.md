Row-level security is now on for all 43 tenant tables, and `pnpm run verify` in `backend/` passes (exit 0). I didn't run `web/verify`, since nothing under `web/` changed.

**What changed (one commit)**
- **Migration:** `0060_tenant_row_level_security.sql` runs a `DO` block over the explicit array of the 43 tables. For each table it enables RLS and adds the restrictive `tenant_isolation` policy and the permissive `tenant_rows` policy, exactly as the issue specifies. There is no `FORCE`. The header comment covers why there is no `FORCE`, why the previous release is unaffected, and that the later strict switch redefines `app_tenant_default()`.
- **Catalog tests:** `tenancyCatalog.test.ts` now checks four things:
  - every tenant table has RLS enabled and not forced;
  - each table's policies are exactly the two expected ones, compared structurally;
  - neither runtime role is a superuser, has `BYPASSRLS`, or owns a table in `public`;
  - neither role has any privilege on an `items_p_*` partition.
- **Behaviour tests:** the new `rowLevelSecurity.test.ts` runs each case in a rolled-back transaction under `SET LOCAL ROLE` for both roles. It covers every acceptance case:
  - a single tenant with no scope sees every row, and `semprec_data` can insert, update and delete as tenant zero;
  - a second tenant's scope sees nothing, and `UPDATE`/`DELETE` of tenant-zero rows affect 0 rows;
  - an insert naming tenant zero under that scope fails with `42501`;
  - two tenants with no scope see nothing and refuse a scope-less insert;
  - a committed transaction's local `app.tenant_id` reverts to `''` afterwards, so the next statement sees tenant zero's rows again.

**Scope-less insert with two tenants:** my test accepts either `42501` or `23502`. In this run it was refused with `42501`. `0059` documents `23502`, so Postgres checks the RLS `WITH CHECK` before the `NOT NULL` constraint. The issue only requires that the insert is refused, so I didn't pin the code.
