# gh-1773 — Render a body for approval notifications

Repository-Issue: gh-1773

## Delivered behavior and production wiring

- Migration `backend/packages/data/src/db/migrations/0122_notifications_body.sql`: `ALTER TABLE notifications ADD COLUMN body text`. Nullable, no default, no backfill; expand-only. Every row written before it keeps NULL.
- `notificationsStore.ts`: `NotificationRow.body: string | null`, selected in `NOTIFICATION_COLUMNS` and mapped in `mapRow`. The unread list, `getNotificationById` (the `notification` realtime frame) and `visitNotification` / `markAllNotificationsRead` return it.
- `writeNotification` (`notify.ts`): optional `bodyKey` and `bodyParams`. The body is rendered through the notifications catalog in the recipient's `users.locale` (fallback `en`), at write time, and stored in the same INSERT. No `bodyKey` gives NULL. A `null` param renders as `notification.body.unnamed` in that locale. A replayed transition keeps the body of the first insert (the `ON CONFLICT` branch does not touch it).
- `notifications/approvalNotificationBody.ts` (new, exported from `@semprec/data`): maps the seven description keys of #1683 to body keys `notification.approval_pending.body.<name>` and passes the description's params through. A request without a description yields no body. A description key with no body entry throws inside the producer's transaction, so the request and its notification roll back together.
- Producers: `preflightDestructiveApproval` (`application/src/genericOperationGateway.ts`) and `createApprovalGatedMcpInvokeTool` (`agent-runtime/src/mcpInvokeTool.ts`) drop `titleParams` and spread `approvalNotificationBody(created.description)`. The approval title no longer takes the tool name.
- Copy (`notifications/i18n/{en,cs}.json`): `notification.approval_pending.title` is "Semp needs approval" / "Semp potřebuje schválení". Seven `notification.approval_pending.body.*` entries per locale, one per description key, and `notification.body.unnamed` ("unnamed" / "bez názvu").
- Push: `NotificationPushPayload.body: string | null` (`push/pushSenders.ts`), filled from `notification.body` in `notificationFanoutJob.ts`. `sendApnsNotification` puts `aps.alert.body` on the wire only when the body is non-null. `sendWebPushNotification` adds `body` to the JSON payload only when it is non-null (the key is absent otherwise).
- `realtime-client/src/serverFrame.ts`: `isNotificationRow` checks `body` (`string | null`). The only consumer of this validator is the `reconnect.e2e` test, which talks to the in-repo server.

## Body text and reversibility

- Each body entry is one sentence about the action followed by its fixed reversibility sentence. The undo sentence ("This can be undone later." / "Lze ji později vzít zpět.") goes with `item.delete`, `database.archive` and `page.restoreVersion`, which `OPERATION_METADATA` flags `reversible` (#1730). The irreversible sentence ("This action is irreversible." / "Tuto akci nelze vzít zpět.") goes with `property.delete`, `view.delete`, `relation.delete` and every MCP call.
- The body names items, databases, views, relations and MCP server/tool names. It does not carry counts, `restorableDays` or canonical database keys, and it never carries an MCP argument value (the MCP description holds only the server and tool names).

## Notes for dependants

- #1831 (APNs category, approval request id in the payload, interruption level): the alert now has a body, so the category can rely on `aps.alert.body` being present for approvals and absent for other kinds.
- #1829 (collapse id): an approval notification's `source_table` is `approval_requests` and its `source_id` the request id.
- Existing approval notifications keep their old title (`"<tool>" needs approval`) and a NULL body. Only notifications written after this change carry the new text.
- Rollback: migration 0122 is additive. The previous release names its columns explicitly and never reads `body`, so it keeps working. New approval notifications would then show the old title and no body, and the push carries no body.
- Decision for review, not settled by the issue: an MCP call is always described as irreversible, including a `write`-class one (which #1730 marks as not `irreversible`). Semp has no undo for an external tool, so promising one would be false. `outbound` and `breaksLink` requests also get the irreversible sentence, because Semp cannot undo a sent message or an ended link.
- Decision for review: the body entries are composed, one per description key, each ending with its own sentence. The issue asked for separate sentence entries. The writer renders one catalog key, so separate sentences would need a second lookup in the writer. The sentence per key is fixed, and a unit test ties it to `OPERATION_METADATA.reversible`.
