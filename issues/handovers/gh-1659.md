# gh-1659 implementation handover

Implementation base: `80cf870f4463f9befb8d8a10cc1e80772af58001`.
Blocked by gh-1486 (multi-step proposals on confirm).

## What changed

- Migration `0114_item_origins.sql`: tenant table `item_origins` (`tenant_id`, `item_id`, `proposal_id`,
  `inbox_item_id` and `source_transcript_id` nullable, `captured_at`, `capture_channel` in
  `inbox | transcript`), primary key `(tenant_id, item_id)`, index `(tenant_id, proposal_id)`, row-level
  security with the two standard policies, `semprec:tenancy=tenant`, grants to `semprec_side` like
  `mail_drafts`. No foreign keys to item ids: `items` is partitioned and has no `(tenant_id, id)` key, so
  only `tenant_id -> tenants` is referenced.
- New `inbox/itemOriginsStore.ts`: `insertItemOrigins` (one statement, `ON CONFLICT DO NOTHING`) and
  `deleteItemOrigin`.
- `executeProposalSteps` now also returns `createdItemIds` (items written by `create` steps, in execution
  order; `update` and `link` steps are not listed).
- `confirmProposalWithClient` inserts the origin rows for a `database` envelope right after the items are
  written, in the confirming transaction: the single-step item, or `createdItemIds` of a multi-step
  envelope. `relation` and `pageContent` confirms create nothing and write nothing. A repeated confirm
  returns early on the `confirmed` status, so no row is added or changed.
- `deleteItemDependents` deletes the item's row.
- Tenant export and purge are catalog-driven (`semprec:tenancy=tenant`), so they need no change;
  `tenancyCatalog.test.ts` lists the table and `rowLevelSecurity.test.ts` counts 55 tenant tables.

## Tests

`proposalActions.test.ts` block "item origins": two-step confirm writes two rows with card id, source
Inbox item id, capture time and channel `inbox`; single-step writes one; a patched item gets no row; a
failing confirm leaves none; repeated confirm leaves rows identical; `deleteItemDependents` removes only
the deleted item's row. New `itemOriginsTenant.test.ts`: on a `semprec_side` pool, tenant B sees none of
tenant A's rows and cannot insert a row stamped for A. `tenancyCatalog`, `rowLevelSecurity`,
`tenantPurge`, `tenantForeignKeys`, `tenantUniqueKeys` and `publicSurface` pass. `tenantExport.test.ts`
has one failing assertion (expiry is 7 days plus one hour) that is a DST artifact of the sandbox clock
and is unrelated to this change.

## Notes for dependants

- Items carry no creation timestamp. `captured_at` for an Inbox card is the Inbox item's `date` + `time`
  properties read in the system timezone; when they are missing or unparseable, or the `sourceInbox` edge
  is gone, it falls back to the card's `updatedAt`. For a transcript card it is the card's `updatedAt`
  (stand-in for creation time). Channel is `transcript` and `source_transcript_id` is set exactly when the
  card has a transcript edge.
- The transcript-card branch and the `updatedAt` fallback have no dedicated test.
- `item_origins` rows are not removed on soft delete or on undo of a confirmation (#1943).
- The store is not exported from the package index; readers (#1967, #1716) add their own read functions.
