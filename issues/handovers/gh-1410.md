# gh-1410 — Detect file type from content on upload

## Delivered behavior

`detectFileType(head: Buffer)` (`blobs/fileTypeDetection.ts`, exported from `@semprec/data`) is a pure, non-throwing sniffer: PDF (`%PDF-` in the first 1024 bytes), JPEG, PNG, HEIC (ISO-BMFF `ftyp` major or compatible brand), m4a/m4b (`audio`, `audio/mp4`), mp3 (`ID3` or an MPEG Layer III frame header at offset 0; `audio`, `audio/mpeg`), and xlsx/docx from `xl/` or `word/` entry names in the ZIP local headers within the first 64 KiB (streamed entries with zero sizes are walked by searching the next local header). Anything else, including a plain ZIP, returns `null`. `FILE_TYPE_DETECTION_HEAD_BYTES` (64 KiB) is exported from the module file for the caller that reads the head.

`ingestUploadedFile` now reads the first 64 KiB back through `storage.readStream(key, { start, end })` after the write and before the transaction, stores the detected mime (or `application/octet-stream`) as the blob mime, and creates the Files item with `type` only when detected. `contentType` is still accepted but ignored. A failing head read goes through the existing catch, which deletes the just-written bytes. A dedup hit returns the existing item unchanged (the blob keeps the first upload's mime).

Files `type` options gain `png`, `heic`, `audio` in `seedTenDatabases.ts` and cs/en labels (`Zvuk` / `Audio`). `runFilesTypeOptionsCutoverMigration` appends the absent keys (idempotent, no-op without a Files database) and is registered in `runTenantCutoverMigrations`.

## Tests

- `blobs/__tests__/fileTypeDetection.test.ts`: every type, m4a/mp3 with and without ID3, plain ZIP, empty/truncated input.
- `blobs/__tests__/filesTypeOptionsCutoverMigration.test.ts`: populated install gains options once, second run unchanged, fresh install unchanged, no Files database.
- `__tests__/fileUploadStore.test.ts`: PDF sent as `image/jpeg`, unknown and empty content, identical re-upload returns the same item.
- Existing fixtures that uploaded fake bytes under a claimed type were updated to real signatures (`filesAndBlobsHandler`, `tenantIsolationRoutes`: `ID3` prefix so transcription accepts the audio file), the fake storages in `blobsPerTenant` and `fileUploadStore` tests implement `readStream`, and `publicSurface` lists `detectFileType`.

Ran from `backend/`: lint, format:check, build, check:boundaries, check:write-safety pass; the integration tests above pass (Postgres needed an unsandboxed run). `tenantExport.test.ts` fails on a DST-dependent 1 h difference (608400000 vs 604800000), unrelated to this change and not touched. ## Notes for dependants

- #1401 must call `detectFileType` on the first `FILE_TYPE_DETECTION_HEAD_BYTES` of the stored bytes (same read-back pattern as `readHead` in `fileUploadStore.ts`, which is not exported).
- Any test uploading to `POST /api/files` must now send real signatures if it depends on mime or `type`; otherwise the blob is `application/octet-stream` and has no `type`.
- Existing Files items are not backfilled; only the options are added.
