## What changed

- `proposalEnvelopeSchema` (`backend/packages/data/src/inbox/inboxTickAction.ts`) has an optional
  `relations: { [relationPropertyKey]: string[] }` (arrays of non-empty strings). A stored envelope
  keeps it when parsed. `ReviseProposalInput` has the same optional field and
  `reviseProposalWithClient` copies it into the envelope when present (absent stays absent).
- `assertValidProposalEnvelope` validates `relations` for a `database` envelope: every key must be a
  relation-type property of the target database (`ValidationError`, `field: <key>`), the ids of one key
  must be unique (same error), and each target must pass `assertRelationTargetLinkableWithClient`.
  An empty array is valid and means no edge. `relations` on a `pageContent` or `relation` envelope is
  a `ValidationError` with `field: "relations"`.
- `assertRelationTargetLinkableWithClient(client, { relationPropertyId, targetItemId }, context?, writer?)`
  in `chokePoint/relationOps.ts`. The shared part of `loadCreatableRelationEdgeContext` (edge context,
  both databases unarchived, property writable) was factored into `loadWritableRelationEdgeContext`
  and both use it. Failures carry `details.field` = the relation property key:
  `code: "targetNotFound"` (missing in the relation's other database, which includes another tenant's
  item), `"targetDeleted"`, `"targetArchived"` (target in the Projects database with `status: archived`;
  `done` stays linkable), `owner_violation` / `database_archived` as for edge writes, and a
  `CardinalityViolationError` (409, `details: { field, code: "cardinalityViolation", ... }`) when the
  target already holds the only edge a `one_to_one` relation, or the single-valued side of a
  `one_to_many`, allows. The cardinality check only reports; the database trigger still enforces at write.
- The three producers need no new code: the tick's write phase and the edit route already call
  `assertValidProposalEnvelope`, and `reviseProposalWithClient` reaches it through
  `assertValidEnvelopeForCard`.

## Notes for dependants

- Edge-metadata hooks run with a nil-UUID caller because the proposed item has no id. Every current
  hook returns before using the caller unless metadata is present (the Transcripts `speakers` hook
  rejects the missing metadata with `field: "metadata"`), so a `speakers` key in `relations` is
  rejected; a future hook that reads the caller without metadata must handle the placeholder.
- Hook errors keep their own `details.field` (`metadata`), not the relation key.
- Writing the edges on confirm is #1476, derived relations #1991, computing/editing are #1488/#1920;
  none of that is here. Nothing in this change writes an edge, and confirm ignores `relations` for now.
- The "one" side of a conflict is reported, not turned into a move (#1479).
- The migration number, `publicSurface` and tenant-table counts are unaffected (no schema change,
  no new public export).
- Branch name: `wf/gh-1426` already existed locally (empty, at the tip, checked out in another
  worktree), so this work is on `wf/gh-1426-b`.
