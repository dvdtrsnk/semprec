## What was delivered

- Catalog operation `page.convertToBlock`: input `{ parentItemId, blockId, type, confirmedPageCount }` (strict; `type` is any block type except `page`; the count is an integer from 1 to 2147483647), output `{ blockId, trashedPageCount }`. A destructive write on `core.item.write`, so an agent's call needs approval. Port method, binding, capability metadata and application service method `convertPageToBlock`.
- REST route `POST /api/items/:id/page/convert` (path item is the parent, body exactly `{ blockId, type, confirmedPageCount }`, answer 200), with its route matrix entry in `routeMatrix/items.ts` and the tenant-isolation REST and MCP cases.
- `convertPageToBlockWithClient` in `docs/pageOperations.ts`: in one transaction it locks the parent, the page and the rows of the pages below it (level by level, `lockSubpageTree`), compares `confirmedPageCount` with `collectSubpageTree` plus one (409 `ConflictError` with `currentPageCount` in the details, nothing changed), trashes the page through `itemDeleteWithClient` (the trash hook removes the block and records its place), and inserts the new block of the requested type at the recorded position with the page block's title (normalized like a page title) and its indent. Any failure rolls the trash back.
- Approval flow: projection kind `page_convert` (`docs/pageConvertApproval.ts`, `computePageConvertProjection`), `destructiveProjection.ts`, `approvalDescription.ts` and the exhaustive mapping in `genericOperationGateway.ts` (check, project, replay with the agent writer, authored user after approval). The approval description and notification name the page by the title its page block shows, not by the mirrored item title; the notification body has localised keys `approval.pageConvertToBlock.<type>` (cs, en).
- ADR `docs/adr/2026-11-13-page-convert-to-block-trashes-the-page-tree-after-a-confirmed-count.md` (accepted) records the route, the lock order, the count contract and the origin split.
- Merge reconciliation: `agentStep.title.operation.page.convertToBlock` in the agentRuns cs and en catalogs (the tip's step-title test requires a title for every generic operation).

## Deviations from the specification and spec seams

1. The ADR of #1394 does not record the route; this source chose `POST /api/items/:id/page/convert` and recorded it in a new ADR.
2. Besides `collectSubpageTree`, the rows of the pages below the page are locked before the count (`lockSubpageTree`); recorded in the ADR as a lock-order decision.
3. Order follows the Task (trash first, then insert), so when the page block was the only block of the document the emptied-document rule leaves an empty text block behind the new block (documented, tested).
4. `genericOperationGateway.ts` changed because its exhaustive destructive mapping needs the new name. `capabilities.ts` registers the operation as destructive, which the agent-approval criterion requires; the classification of #1844 itself is untouched.
5. Added notification body keys `approval.pageConvertToBlock.<type>` so the block type is shown localised.
6. At the merge, the two exports from `./blobs/openBlobFromRoots.js` and from `./mcp/approvalDecisionAction.js` became `export *` each (identical surface) because `packages/data/src/index.ts` was at the 900 line cap.
