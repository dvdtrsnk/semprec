# Handover for gh-1499

Reply-To is now parsed by all three mail adapters into an optional `MailEnvelope.replyTo` (`MailEnvelopeAddress[]`). It is stored unchanged in `mail_message_meta.envelope` because `ingest.ts` passes the envelope through as is, so there is no migration.

- **IMAP:** `imapFlowClient.ts` reads ImapFlow `envelope.replyTo` through the existing address-list helper.
- **Gmail:** `gmailRestClient.ts` reads the `Reply-To` header from the mailparser header parse. Gmail is fetched with `format=full`, so there is no header allow-list to extend.
- **Graph:** `graphRestClient.ts` reads the `replyTo` recipients, and `replyTo` is added to the delta query `$select`.
- **Absent, not empty:** when a message has no Reply-To (or it is unparsable), the key is omitted rather than set to `[]`. Messages synced before this change have no `replyTo` either; there is no backfill, so the reply prefill (#1899) must fall back to From.
- **Tests:** new cases in `gmailRestClient.unit.test.ts` and `graphRestClient.unit.test.ts`, plus a new `imapFlowClientReplyTo.unit.test.ts` that calls the private `parseFetchedMessage` with a fake ImapFlow. All pass; tsc, eslint and prettier are clean for the touched files. I did not run the full verify.
- **Notes for dependants:** `send.ts` builds its own outgoing envelope and does not set `replyTo`.
