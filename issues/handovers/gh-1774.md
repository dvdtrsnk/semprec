## What was delivered

Meeting invitations by email as a queue task of the calendar module.

- `calendar/icalendarWriter.ts` serializes iTIP `METHOD:REQUEST` and `METHOD:CANCEL` (UTC instants, DATE values with an exclusive DTEND for all-day Events, text escaping, 75-octet folding, validated addresses).
- `calendar/eventInvitationJob.ts` holds the payload schema, `enqueueEventInvitation` (commit-coupled with the writer's transaction; job key `event-invitation:<eventId>:<personId>:<method>:<sequence>`), the Event snapshot used by CANCEL, and the handler of the task `calendarSendEventInvitation`. REQUEST reads the live Event; CANCEL runs from the snapshot alone, even after the edge and the Event are gone. The message is built with `buildOutgoingMime`, subject and text from the calendar i18n catalog in the language of the tenant's user (cs when the tenant has no user), and sent through the transport of the mailbox's sync mode. After a REQUEST is accepted, `invitation.sentAt` is written on the participant edge as the system writer under the Event row lock.
- `calendar/eventInvitationHooks.ts` registers an Events update hook (an `icalSequence` change queues a REQUEST for each invited person with `sentAt` who has not declined) and an Events delete hook (a CANCEL with a snapshot for every person with an invitation). There is no restore hook: a restore sends nothing.
- Failure handling: a transient failure rethrows so the queue retries and the invitation stays without `sentAt`. Mailbox deleted, no address, no usable transport (a `ValidationError` or the new `MailTransportUnavailableError` of the factory), a recipient the server refused, and a `sentAt` refusal that no retry can change (a trashed Person, an archived database) end the job with a logged reason code. A failing `sentAt` write is retried twice (200 ms, 1 s) and then rethrown so the queue retries the job. If the Event moved while the message was on its way, the same transaction that writes `sentAt` queues a REQUEST at the current sequence (not when the invitation was declined or the Event is trashed, and not twice when the update hook already queued one).
- The API runtime binds the mail transports and the pool for the task: `createApiQueueRuntime` calls `setEventInvitationDelivery` before it starts the runner and unbinds on stop or on a failed start. ADR `docs/adr/2026-11-12-module-queue-tasks-read-their-composition-root-dependencies-from-a-binding.md` records that binding.

## Deviations and spec seams

1. A module task handler receives only `(payload, helpers)`, so the pool and the mail transports reach it through a per-process binding set by the API runtime (ADR above). gh-1953 will meet the same need.
2. The Task's payload has no sequence; `enqueueEventInvitation` takes a sequence for a REQUEST only to build the job key. The handler reads the live sequence, so two REQUESTs queued before either runs send the same latest sequence twice.
3. Beyond the Task's permanent list, a recipient the server refused also ends the job with a reason code instead of retrying; so does a `sentAt` refusal that retrying cannot change (added in the last fix round).
4. Subject and body are not specified by the Task; they are the new catalog keys above.
5. The delete hook builds the snapshot from the Event and throws `validation_failed` when the Event has no iCalendar UID or no readable date, which would refuse the trash of such an Event; Events carry a UID since the gh-1599 cutover.
6. An Event with `timeFrom` and no `timeTo` (not reachable through the Events rules) is written to end at the midnight ending its last day.
7. The enqueue on invite and on removal of one person is gh-1790 (Out of scope) and applying replies is gh-1950; the first REQUEST for a new invitation therefore has no producer in production code yet.
8. The Task names no ADR; one was added for deviation 1.
