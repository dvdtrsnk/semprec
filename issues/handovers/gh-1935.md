## What was delivered

- `GET /api/projects/:id/agent-summary`, a `single-consumer-read` custom route of the schema core manifest, for the row "Semp in this project" of the project detail and its attention dot.
- Body: `{ hasGuidance, guidanceUpdatedAt, grantedToolCount, enabledHeartbeatCount, attention: { activeDriftFindings, failingHeartbeats, pendingApprovals, needsAttention } }`. `needsAttention` is true when any of the three counts is above zero. `grantedToolCount` counts effective grants only (a grant on an inactive server is not counted); `enabledHeartbeatCount` counts enabled user-origin heartbeats only; `activeDriftFindings` counts `status = 'active'` rows; `pendingApprovals` counts pending requests of the project's runs; `failingHeartbeats` counts user heartbeats whose last finished occurrence failed, by the display-status and reply-outcome rule of the heartbeat list (gh-1910).
- A foreign, trashed or unknown project answers the same 404; an id that is not a UUID answers 400.

2. The rule "no per-row queries" conflicts with "failingHeartbeats from the listing of gh-1910", whose route reads run detail and reply per heartbeat; `getProjectAgentSummary` therefore batches the last-run status (`listLastFinishedOccurrenceRuns`, `getAgentRunsByIds`, one pending-approval count, one reply read) and reuses the pure functions `deriveRunDisplayStatus` and `replyOutcomeOfStoredSteps`. The batched reply read is a copy of the owner's rule (done, not an MCP run, with a thread, exactly one assistant reply in the run's thread), pinned by the cross-check test.
3. Interpretations: `guidanceUpdatedAt` is the record's `updated_at` whenever a record exists (`hasGuidance` is false for a blank record); `failingHeartbeats` counts a user heartbeat whose last occurrence failed even when it is switched off, as the heartbeat list shows it.
