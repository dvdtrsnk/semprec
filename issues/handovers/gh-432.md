## Summary

`resolveRelationProperty` (`backend/services/semprec-api/src/itemsHandler.ts`) used to call `property.list` for the caller item's whole database and filter the result in memory. That was O(N) in the property count on every `PUT`/`DELETE /api/items/:id/relations/:propertyKey/:targetItemId`. It now makes one call to a new `property.getByKey` generic operation. That operation runs an indexed query on `(database_id, key)` and applies the RELATION type filter in SQL.

### Catalog addition (`packages/shared/src/genericOperations`)
- **Operation name:** `property.getByKey`, added to `GENERIC_OPERATION_NAMES`. The catalog now has 29 operations.
- **Input schema:** `PropertyGetByKeyInputSchema` is a strict object `{ databaseId, key, type? }`. `type` must be one of the values in `PROPERTY_TYPES`.
- **Port and binding:** port method `getPropertyByKey(actor, input)` returns `Property[]`, and its binding is in `GENERIC_OPERATION_BINDINGS`.
- **Metadata:** `nonDestructive("core.schema.read")`, the same as `property.list` and `property.get`.
- **Why a list:** it returns every match instead of one row, so the caller decides what none, one or several matches mean. Each transport keeps its own response shapes that way.

### Data layer (`packages/data`)
- `propertiesStore.findPropertiesByKey(client, databaseId, key, type?)` runs `WHERE database_id = $1 AND key = $2 AND ($3::text IS NULL OR type = $3)`. The `UNIQUE(database_id, key)` index covers it.
- `chokePoint.findPropertiesByKey(...)` exposes it, and `genericApplicationService.getPropertyByKey` delegates to it.

### Route
- `resolveRelationProperty` dispatches `property.getByKey` with `{ databaseId: item.databaseId, key: propertyKey, type: "relation" }`.
- The 404 `not_found` shape `{ resource: 'relationProperty', databaseId, propertyKey }` is unchanged.
- The 409 `validation_failed` shape `{ field: 'propertyKey', reason: 'ambiguous' }` is unchanged.
- The docstring no longer describes the O(N) approach as deliberate.

### Out of scope, left alone
- Other `property.list` call sites (`propertiesHandler.ts`, `databasesHandler.ts`).
- The existing `chokePoint.getPropertyByKey`.
- ADR bodies that mention "28 operations". ADRs are append-only, and adding an operation to the existing catalog applies an existing pattern rather than creating a new one.
- Code comments that stated the catalog size were updated to 29.

## Tests
- **Schemas (`schemas.unit.test.ts`):** valid input with and without `type`; an unknown `type` is rejected; `databaseId` and `key` are required; spoofed actor fields are rejected, as for every other operation.
- **Catalog (`operationCatalog.unit.test.ts`):** the new row maps to the right schema, port method and metadata; the count is now 29.
- **`chokePoint.findPropertiesByKey` (`chokePoint.test.ts`):**
  - finds the property without a type filter;
  - finds it when the type matches;
  - returns nothing when the key exists but the type doesn't match;
  - returns nothing for an unknown key, or for a key that only exists in another database.
- **Routes (`itemsHandler.test.ts`):**
  - A same-database non-relation property with the requested key answers 404, and the test checks the exact `relationProperty` error body.
  - The ambiguous branch answers the exact 409 body for both `PUT` and `DELETE`. A real database can't produce two matches because of `UNIQUE(database_id, key)`, so this test uses the real service with only `getPropertyByKey` replaced to return two rows. It also checks that the route sent `type: "relation"`.
- **Adapter contract tests (REST, MCP, AgentTool):** each has a case for `property.getByKey`. The REST case checks that a relation key resolves (200) and that a non-relation key is filtered out (404).
