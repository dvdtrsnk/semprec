# Handover: Show device captures in the diary Inbox at once

ADR: `docs/adr/2026-11-27-inbox-captures-wait-in-a-device-outbox-that-outlives-the-session.md`, narrowed in place
(still unmerged on `develop`) with the bullets "Shown at once" and "Fresh after a capture" and two consequences.

**Projection** (`mobile/shared/data/src/commonMain/kotlin/cz/semprec/app/data/CaptureProjection.kt`).
`OfflineLayer.read` applies `CaptureViews.project(session, account, request, answer)` after `QueuedViews.project`, to
every successful answer of `GET /api/journal/periods/day/<YYYY-MM-DD>` (kept or from the server; a failure is left
alone). It reads the captures of the read's session owner (`CaptureOutbox.waitingOf(session)` →
`KeptCaptures.captures(owner)`, a read-only listing that neither deletes stray `.bin` files nor touches `waiting`),
keeps those whose `day` equals the path's day and whose id is not among the answer's `inbox[].id`, and appends them
after the server's entries in creation order. The kept answer on disk stays the server's; the projection is applied
per read. `CaptureProjection.apply` is pure.

A projected entry is exactly:

```json
{"id":"<captureId>","time":"HH:mm","text":"<text>","type":{"emoji":"🧾"} | null,
 "status":"waiting","attachments":[{"name":"<file name>"}] | []}
```

- `id` is the capture id (the outbox file name and the `Idempotency-Key`), not a server item id. The attachment
  opening issue (sp-25a1187e-24aa-4323-9d82-41f05b679e61) can recognise a projected entry by
  `JournalInboxStatus.WAITING` (or this id) and find its bytes at `<dataDirectory>/captures/<owner>/<id>.bin`; nothing
  exposes them yet.
- `type` is set only when the capture has a type id and the kept answer of `GET /api/inbox-types` of the account names
  it with a non-blank emoji.
- No `processing`, `date`, `proposalSummary` or attachment ids/blob ids/mime type: the attachment entry has only the
  name.
- Through `JournalInboxDto.toDomain()` it becomes `JournalInboxEntry(status = "waiting", processing = null,
  attachmentName, attachmentCount)`, and `JournalMapping.inboxStatus` maps `waiting` to the new
  `JournalInboxStatus.WAITING` (exported; the server never sends it, `WAITING_INBOX_STATUS` in data).

**Stale and emit.** `CaptureOutbox.add` calls `LayerState.changed()` after the files are written (kept answers stale
as after a write, `OfflineLayer.changes` emits), then starts a round. A capture the server created already did the
same (`files.delete` then `state.changed()`). Every window's `ItemChanges` merges `OfflineLayer.changes`, so the open
diary reloads; another SDK of the process (the Action-button shortcut's `InboxCaptureSDK`) shares the layer through
`OfflineLayer.shared`, so its captures emit to the windows too.

**Apple.** CoreKit `JournalInboxStatus.waiting` and its mapping (`SharedJournalValues.swift`, case in
`SharedJournalActionMappingTests.testInboxStatusesMapEveryCase`). `JournalInboxRow` shows no status text for
`waiting`, and a trailing `clock` symbol with the accessibility label `journal.inbox.status.waiting` ("Waiting to be
sent" / "Čeká na odeslání"), listed under `appleOnly` of `JournalFeature` in the policy. Android does not map
`JournalInboxStatus` anywhere, so no Android code changed.

**Open points.**
- The server's Inbox entry carries no capture id, so the id check only rules out a repeated id. A read that reaches the
  server between its creating the item and the device deleting the capture lists both until the read the deletion's
  emission starts a moment later (recorded as a consequence in the ADR).
- `JournalViewModel` skips a change that arrives while a load runs (existing behaviour); a capture added exactly
  during a period load shows on the next change or selection.
- Each capture made online makes the next reads of every screen wait for the server, as any write does.
