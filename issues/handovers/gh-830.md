## Why

The `integration` and `e2e` tiers exited 0 even when tests failed, so both required checks went green regardless.
- Importing `embedded-postgres` in `globalSetup` registers `async-exit-hook`.
- That hook's `beforeExit` handler calls `process.exit(0)`, which overwrites the `process.exitCode = 1` vitest sets on a failed run.
- Two #662 lock-race tests in `inboxTickProposal.test.ts` have failed on develop unnoticed since 5f3a326 (#792), which moved the tick to `repeatable read`.
- Evidence: CI run 36628903406 on `16bc764` reports `2 failed | 1995 passed` yet concluded `success`. PR #829's shard 1 shows the same.

Everything the hole hid has to land together with the fix for it: restoring the exit code alone would turn `integration` red on every pull request. The last 48 integration jobs on develop and pull requests show 43 with at least one masked failure. Besides the two `inboxTickProposal` tests, the following were affected: `moduleDataMigration` (27 jobs), `transcriptionTask` (12), `piMessagesHandler` (4), `processHeartbeats` (2), `queueRuntime` (1) and `syncServer` (1). A `startupRepair` failure in one job came from a branch that predated 681441e; develop already has that fix.

## What

- **`inboxTickAction.ts` — `lockUnlockedProposal`.**
  - Under `repeatable read`, `FOR UPDATE` on a card written after the snapshot raises `40001` instead of returning the newer row. That is exactly the "a write committed since the snapshot" case the function already documents as a logged skip.
  - The lock now runs under a savepoint. A serialization failure rolls back to the savepoint, logs reason `changed` and returns `null`; any other error propagates.
  - This follows the savepoint idiom already used in `mail/ingest.ts`.
- **`testSupport/preserveFailingExitCode.ts`**, called first in `globalSetup`.
  - It records `process.exitCode` in a prepended `beforeExit` listener, which runs before async-exit-hook's handler.
  - It restores that code in the `exit` event if something reset it to 0. Node reads `process.exitCode` after emitting `exit`.
  - The SIGINT/SIGTERM exit codes (130/143) are non-zero and pass through untouched.

- **Masked flaky tests.** None of these is a production defect. Each test read state before the write it asserts on had committed:
  - `moduleDataMigration.test.ts` asserted the locked row's `n` as `0`. Item ids are random UUIDs, so the lowest id's seeded `n` can be any of 0..2; the test now reads it.
  - `piMessagesHandler.test.ts` read the gateway call row right after the response ended. The handler ends the response after `done`/`error`, before the row leaves `reserved`; the tests now wait for `settled`. The handler docstring now states that order.
  - `syncServer.test.ts` (LISTEN outage) raced a new socket against the reconnect's `pool.connect()`. The test now holds that call so it controls the gap. It asserts that a socket connected during the gap is closed with 1012, and that one connected after the reconnect stays open and receives a broadcast.
  - `@semprec/queue` `runOnce` (tests and one-off drains only; `runWorker` is unchanged) could resolve while graphile-worker's `complete_job`/`fail_job` was still in flight. That broke the transcription retry and requeue tests. It now routes both through the zero-delay release batchers, which the worker pool's shutdown awaits.
  - `processHeartbeats.test.ts` read the row before the tick's un-awaited UPSERT committed; the test now awaits each tick's query.
  - `semprec-api` `queueRuntime.test.ts` read `_private_known_crontabs` before graphile-worker's background cron registration committed; the test now waits for it.
