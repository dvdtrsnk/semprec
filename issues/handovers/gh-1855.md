## What was delivered

- `GET /api/trash/items` no longer returns a row for a Pages item whose `parentItemId` names an item (a page or a host item) deleted with the same `deleted_at`. The condition is in the shared `ROOTS_WHERE`, so the row statement, the paging cursor and `totalCount` use one filter and stay consistent. It reads the parent link only, no document.
- A row whose item belongs to the hidden `pages` database carries `page: { title, path }`. `path` is the chain of ancestors from the host to the parent as `[{ itemId, title, trashed }]`, trashed ancestors included, read with one recursive statement per page of results (none when the page has no Pages row), in the same REPEATABLE READ snapshot as the list. The walk has a visited-set guard and, after the fix round, a depth bound of `MAX_SUBPAGE_CHAIN` (1000, imported from `docs/pageOwnerDatabase.ts`): it keeps the nearest 1000 ancestors and cuts at the root end, as `getItemPath` does (ADR 2026-11-09, subpage parent chains are bounded while walked).
- Titles: a page's title is the title-typed property of its Pages item; a host's title is the title-typed property of the host item (alphabetically first key, as `listDatabaseLabelsByIds` does); a missing or non-text title reads as the empty string. A row of any other database gets no `page` object; `databaseName` stays the localized name of the hidden database.
