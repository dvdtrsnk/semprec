**What changed**
- **Migration `0076_ai_tenant_spend.sql`** adds `ai_tenant_spend()`. It is a `SECURITY DEFINER` function owned by `semprec_router`, with a pinned `search_path`, executable by `semprec_data` only. It returns one row per tenant: id, spend today and spend this month, in UTC windows. `semprec_router` gets `SELECT (tenant_id)` on `ai_gateway_calls`; `(at, cost_usd)` was already granted by 0073.
- **Store** (`tenantAiBudgetsStore.ts`):
  - `listTenantAiBudgetOverview` returns each account's caps and its tenant's spend. An account with no budget row reports `hasBudget: false` and null caps.
  - `setTenantAiBudget` is the only writer of `tenant_ai_budgets`. It upserts and runs inside the caller's transaction.
- **Routes** (`adminHandler.ts`, both `admin: true`):
  - `GET /api/admin/ai-budgets` returns `{ spendWindow: "utc", accounts }`.
  - `PUT /api/admin/accounts/:userId/ai-budget` validates first. The UUID is checked with `assertUuid`. Each cap must be `null` or a finite number ≥ 0; anything else is a 400 naming the field. Then, in one transaction, it upserts the caps and writes a `tenantAiBudgetSet` audit row.
- **Route matrix**, handler-file mapping, `EXPECTED_RUNTIME_EXPORTS`, and one row in `docs/operations/database-roles.md`.
- **Tests:** new `tenantAiBudgetsAdmin.test.ts`, plus route cases in `adminHandler.test.ts`. They cover the upsert, the spend windows from the acceptance example (1.75 / 3.75 and 3.00 / 3.00), the validation refusals with no row and no audit row, 400 for a non-UUID id, 404 for an unknown one, and the privilege check on `ai_tenant_spend()`.

**Choices you should know about**
- **User → tenant lookup uses `COALESCE(tenant_id, app_sole_tenant())`.** The issue said `SELECT tenant_id FROM users`. I matched `listAccounts`, which has the same fallback. If a user has no tenant id, the write goes to the sole tenant instead of failing.
- **`CREATE FUNCTION` without `OR REPLACE`**, as the issue wrote it. Migrations run once, so this is fine.
- **The spend test has one assumption.** Its "earlier this month" fixture sits at the first instant of the UTC month. On the 1st of a month that row counts as today, so the test's `spentToday` assertion would fail that day. It is not a code defect, but it is a latent flake.
