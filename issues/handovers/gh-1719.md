## What was delivered

- `backend/packages/data/src/calendar/reminderFireTime.ts`, a module of pure functions with no database access. It exports `ALL_DAY_REMINDER_HOUR = 9`, the types `ReminderInput` and `ReminderSuppression`, `reminderSuppression(input)` and `computeReminderFireAt(input, zone)`.
- `ReminderInput` is a union by `kind`. Every member carries `calendarNotify: boolean`, `trashed: boolean` and `cancelled: boolean`.
  - `event`: `date`, `timeFrom?: string | null`, `alertMinutes?: number | null`, `travelMinutes?: number | null`.
  - `task`: `date`, `timeFrom?: string | null`, `notifications: boolean`, `status: string | null`.
  - `birthday`: `date`. `holiday`: `date`.
  - `date` is `YYYY-MM-DD` and `timeFrom` is `HH:MM`, both on the wall clock of the tenant time zone. An absent or `null` `timeFrom` means the item has no time (an all-day Event, an untimed Task).
- `reminderSuppression(input)` returns the reason an item has no reminder, or `null`. The first that applies, in this order: `trashed`; `cancelled`; `taskClosed` (a Task whose status is `done` or `wontDo`); `notificationsOff` (a Task whose `notifications` is off); `calendarMuted` (an Event, a birthday or a holiday whose `calendarNotify` is false; never a Task); `noAlert` (an Event whose `alertMinutes` is absent or `null`; `0` is an alert).
- `computeReminderFireAt(input, zone)` returns an ISO 8601 instant in UTC (for example `2026-10-16T07:15:00.000Z`), or `null` exactly when `reminderSuppression(input)` names a reason.
  - A timed Event fires `travelMinutes` plus `alertMinutes` of elapsed time before `wallClockToInstant(date, timeFrom, zone)`.
  - An all-day Event counts `alertMinutes` back from 09:00 of its `date` on the wall clock and converts afterwards, so 1440 is 09:00 the previous day on the days of a daylight-saving change too, and 15 is 08:45. Its `travelMinutes` is not read.
  - A Task fires at its `timeFrom`, or at 09:00 of its `date` without one. It has no alert offset, and its calendar's `notify` never mutes it.
  - A birthday and a holiday fire at 09:00 of their `date`.
  - Every wall-clock value becomes an instant through `wallClockToInstant` of `backend/packages/data/src/calendarTime.ts` (gh-1418): a time a daylight-saving change skips moves forward, a repeated time takes its first occurrence.

## Contracts dependents build on

- gh-1858 (the upcoming reminders feed) is the first caller. The module is not exported from the data barrel `backend/packages/data/src/index.ts`, because `Touches` does not list the barrel. Code inside `@semprec/data` imports `./calendar/reminderFireTime.js` by path; a caller outside the package has to add the export to the barrel, and with it the entry in the sorted expected list of `packages/data/src/__tests__/publicSurface.test.ts`.
- The caller passes one item or one occurrence at a time and supplies the facts: `trashed`, `cancelled`, the calendar's `notify` as `calendarNotify`, and the tenant time zone as `zone`. The function reads nothing from the database and expands no series.
- The input has no field for a calendar's visibility. A hidden calendar therefore mutes nothing; only `calendarNotify` does.
- `null` means "no reminder" and nothing else. An input that has a reminder but cannot be computed throws a `ValidationError` (code `validation_failed`) with `details.field`:
  - `timezone` for an invalid zone, `date` for an invalid date, `time` for an invalid `timeFrom`, as `calendarTime.ts` raises them;
  - `instant` (message `Invalid reminder instant`) when the offset is not a finite number or moves the result out of the range of dates.
  - A suppressed item is not read further: its date, time and zone are not converted, so an invalid one returns `null` and does not throw. The code decides the suppression before any conversion for every reason; the test asserts it for a trashed Event with an invalid date and an invalid zone.
- `timeFrom` must be absent or `null` for an untimed item. An empty string is an invalid time and throws with field `time`, while `calendarTime.taskEffectiveEnd` reads an empty string as untimed. No current write path stores an empty string (the Events format rule refuses it, the Tasks transform stores `null`), but a caller that reads older rows has to pass `null` for it.
- The Task statuses that end a reminder are `done` and `wontDo`. `notDone`, `missed` and `null` fire.
- A Task carried over to a later day reminds on its stored `date` only; the caller passes that date.
- The values `alertMinutes` and `travelMinutes` are taken as numbers of minutes. gh-1714 guarantees the allowed sets for Events written after its landing; an Event stored earlier can hold another finite number, which this function computes with as given.
- No SQL migration, no table, no route, no generic operation, no MCP tool, no job name, no stored key, no hook, no barrel export and no ADR was added.

## Deviations from the specification and spec seams

No file or symbol seam: `wallClockToInstant` and `calendarTime.ts` are where the record names them. Five readings of the rule table that the record leaves open, each stated in the docstrings and tested, all accepted by the requirements reviewer:

1. A timed Event subtracts elapsed time from its start instant; an all-day Event subtracts on the wall clock, because the record fixes "1 day before" of an all-day Event at 09:00 the previous day. A timed Event with `alertMinutes` 1440 fires 24 elapsed hours before its start.
2. An Event with no `alertMinutes` has no reminder (`noAlert`), also when it carries a `travelMinutes`.
3. A birthday is muted by `calendarNotify` false like a holiday, following the general rule that an item whose calendar has `notify` false does not fire. The record states the calendar condition only for a holiday.
4. The suppression codes and their precedence are this module's choice; the record asks only for "a string code".
5. An input that cannot be computed throws a `ValidationError` instead of returning `null`.

The segment has three commits. The second adds a named test for the hidden-calendar clause of the fourth criterion; the third reorders the suppression table so its titles print the reason. Neither changes production code.
