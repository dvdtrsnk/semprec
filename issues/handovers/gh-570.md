## What's in it

- **`validateFindingRecord(value)`** returns the value if it is a valid finding record. Otherwise it throws an `Error` naming the first field that is wrong:
  - The record must have exactly the fields listed in #570, with the types and ranges given there.
  - A missing field or an extra field is also rejected.
  - Reply problems are reported per field, for example `replies[0].excerpt`.
  - Description and excerpt lengths are counted in Unicode characters, not UTF-16 units.
- **`renderHarvestBlock({ prs, findings })`** checks its input and throws on anything the parser would reject. It writes:
  - the line `<!-- crb-followup-data:v1 -->`;
  - a `json` code fence holding `{ "version": 1, prs, findings }` with two-space indentation;
  - every `<` as `\u003c`, so marker text quoted in a finding can't form an HTML comment;
  - a newline at the end.
- **`parseHarvestBlock(body)`** reads the block out of a whole issue body, which may use Windows (CRLF) line endings, and returns `{ prs, findings }`. It throws when:
  - the marker is missing, appears twice, or is not on a line of its own;
  - the ```` ```json ```` fence is missing or never closed;
  - the JSON doesn't parse, or `version` is not `1`;
  - there are top-level fields other than `version`, `prs` and `findings`;
  - `prs` is empty, out of order or has duplicates;
  - a record's `pr` is not in `prs`, two records share the same `(pr, key)`, or a record is invalid.
- The header comment of `records.mjs` names the ADR, `docs/adr/2026-09-26-merged-review-findings-become-proposed-follow-up-issues.md`.

## Tests

All six acceptance criteria are covered:

- **Criterion 1:** a missing field and several wrong or out-of-range values for every field, bad replies, and an extra field.

- **Criteria 4 and 5:** every failure case listed above, for both the renderer and the parser.
