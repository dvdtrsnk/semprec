### Rollback: `deploy/deploy.sh --rollback <tag>`
- **No build, no fetch, no migration.** It points `current` at `releases/<tag>`, which is already on disk. It uses the same atomic `rename(2)` swap and restarts the same services, including active mailsync instances. It fails unless every process reports `<tag>`, and it takes the same lock as a deploy.
- **It refuses before changing anything** in any of these cases:
  - the target is missing, is a symlink, or its `release.env` does not declare `APP_VERSION=<tag>`
  - the target is not the release directly before the newest release on disk (versions sorted semver-style, hidden staging directories ignored)
  - `current` no longer points at the newest release, so a second rollback in a row is refused
- `deploy/deploy.test.sh` covers every refusal and checks that `current` is unchanged and no command ran after each one. It also covers a successful rollback: only `systemctl restart` commands are issued, the release directories are untouched, and each process reports `<tag>`.

### Forward-only migration rules
- **`findIncompatibleStatements`** (`backend/packages/data/src/db/migrationCompatibility.ts`) is a lexical check that flags statements the previous release can't survive:
  - drop table / drop column
  - rename
  - column type change
  - `SET NOT NULL`
  - a new `NOT NULL` column without a default
- Tables created in the same file are never flagged. Comments and string literals are ignored. A file can opt out only with `-- expand-contract-exemption: <reason>`.
- **Unit tier:** the check runs over every file in `db/migrations/`, so CI fails on a new incompatible migration. `0025_auth_schema.sql` is the one existing file it does not accept. It was written before any release existed, and the test lists it by name.
- **Concrete examples** in `db/migrationExamples/`:
  - accepted: 8 (nullable column, `NOT NULL` with a default, new table, new index, relaxing `NOT NULL`, widening a type, rename step 1, the contract step)
  - rejected: 6
- **Compatibility fixture** (integration tier): the real migration runner applies each example on top of `previous-release.sql`. The previous release's queries are then run against the result. They keep working after every accepted example, and the database rejects them (with an SQLSTATE error) after every rejected one.
- **Docs:**
  - `docs/operations/migrations.md`: the accepted/rejected table, the two-release rename/removal procedure, and fix-forward instead of down migrations
  - ADR `2026-09-24-rollback-one-release-back-with-checked-migrations.md`: why rollback only goes one release back, and why migrations are checked lexically
  - rollback sections in `deploy/README.md` and `docs/operations/releases.md`

Down migrations and per-package rollback are out of scope, as the issue says.
