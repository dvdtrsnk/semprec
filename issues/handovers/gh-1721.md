## What was delivered

- The Journal day response carries `events`. `createJournalPeriodReadRouteHandler` (`backend/packages/data/src/journal/journalRouteHandlers.ts`, behind `GET /api/journal/periods/day/:period`) sets `result.events` in its `day` branch from the module-private `readJournalDayEvents(client, day)`. That function calls `readCalendarTimeline(client, { from: day, to: day, shape: "full" })` on the handler's own transaction client, keeps the items of kind `event` in the timeline's order (all-day Events first, as the timeline orders them) and projects each to twelve fields: `id`, `title`, `type`, `date`, `endDate`, `timeFrom`, `timeTo`, `allDay`, `place`, `project { id, name, color } | null`, `calendarId`, `transcript { id, status } | null`.
- `events` is `[]` for a day without Events. Week, month, quarter and year responses have no `events` key and do not read the timeline.
- A timeline error fails the day read. It is not caught and the day is not answered without `events`.
- The Journal has no calendar query, ordering, day-bound or trash rule of its own. Which Events belong to the day (a multi-day Event that spans it is in, a trashed Event is out) is the timeline's decision.
- The calendar timeline item gained `transcript: { id: string; status: string | null } | null` (`CalendarTimelineItem` in `backend/packages/data/src/calendar/timelineSources.ts`). The field is additive in the full shape; the compact shape (`CalendarTimelineCompactItem`) is unchanged.
- The Events source fills it. `readEventTimelineItems` (`backend/packages/data/src/calendar/timelineRead.ts`) calls the module-private `readEventTranscripts`, which sends one statement, `EVENT_TRANSCRIPTS_SQL`, for all Events of the range: a `DISTINCT ON (e.item_a)` over the edges of the relation property `Events.transcript`, joined to the transcript items in the property's target database, returning the transcript id and its stored `status`.
  - An Event with several live transcripts carries the first one in the order of the relation's edges: `coalesce(metadata->>'addedAt', id::text)`, then the edge id. This is the order `readEdges` returns and the rule the timeline already applies to `project`.
  - A trashed transcript is not joined, so the next live one is taken, and an Event whose transcripts are all trashed gets `null`.
  - `status` is the transcript's stored `status` when that is a string, else `null`.
  - An Event without a live transcript gets `null`. Every Task gets `null`: `toTimelineItems` returns every item with `transcript: null` and only the Events source overwrites it.
- `readCalendarTimeline` has a typed overload: with `shape: "full"` it returns the new exported interface `CalendarTimelineInFullShape` (`items: CalendarTimelineItem[]`). The implementation and the existing signature are unchanged; `timelineRouteHandler.ts` passes the union and resolves to the general signature.
- No migration, table, column, route, generic operation, job name, hook registration, tenant cutover entry, export from the data barrel, stored key, label or i18n key was added. No ADR was added or edited.

## Contracts dependents build on

- Response contract of `GET /api/journal/periods/day/:period`: the key `events`, an array in the timeline's order whose elements have exactly the twelve fields above. The heading count of the Journal day is the length of `events`. The other period types have no such key.
- `CalendarTimelineItem.transcript` is a required field of the type. **Every code path that constructs a `CalendarTimelineItem` must set it**, or the build fails: a new timeline source (birthdays gh-1800, occurrences gh-1877, public holidays, sleep nights) sets `transcript: null` on entries that are not stored Events. A test with a strict schema of the full item needs the key as well (`timelineRoute.test.ts` shows the form).
- `GET /api/calendar/timeline` in the full shape now carries `transcript` on every item, Tasks included (`null`). The compact shape does not carry it.
- `readCalendarTimeline(client, { from, to, shape: "full" })` returns full items without a cast. `CalendarTimelineInFullShape` is exported from `calendar/timelineRead.ts` only, not from `backend/packages/data/src/index.ts`.
- Statement count of the timeline: the Events source sends one more statement per read, also for a range without Events and also for the compact shape (a source is not told the shape). The count does not depend on the number of Events.
- `EVENT_TRANSCRIPTS_SQL` reads the relation in its stored direction: `Events.transcript` is property A of its definition (`docs/adr/2026-10-29-events-hold-many-transcripts.md`), so an edge holds the Event in `item_a`. It does not handle the property being side B. It casts `config->>'targetDatabaseId'` of the relation property to `uuid`, as `chokePoint/relationExpansion.ts` does.
- gh-2015 (blocked by this source and by gh-1800) adds `birthdays` to the day response "from the timeline call that #1721 already makes". That call is inside `readJournalDayEvents`, which returns only the projected Events; gh-2015 has to reshape it so that one timeline read serves both keys. `events` keeps only `kind === "event"`, so an item of kind `birthday` stays out of it without a change. The stand-in test "leaves a Task with a time and a derived birthday entry out of events" builds a `CalendarTimelineItem` of kind `task` by hand and spies the `tasks` source; gh-2015 owns the assertion with a real birthday.
- gh-1881 (blocked by this source and by gh-1877) covers recurring, overnight and multi-day Events in the Journal day and the calendar id guarantee. This source asserts one multi-day Event that spans the day and the default calendar's id on two Events; it adds no rule for those cases.
- The unmerged chain `e1-028-calendar` also changes `backend/packages/data/src/calendar/__tests__/timelineRead.test.ts`. This was read from its branch, not merged or built here.

## Deviations from the specification and spec seams

1. Outside `Touches`: `timelineRead.test.ts` and `timelineRoute.test.ts` (the tests of the transcript lookup are in the timeline module, and its strict schemas had to carry the new field) and the extended case in `tenantIsolationRoutes.test.ts`.
2. The typed overload of `readCalendarTimeline` and the exported `CalendarTimelineInFullShape`. Type level only; it lets the Journal read full items without a cast.
3. Spec seam: the Task names a single `transcript`, while `Events.transcript` is one-to-many since gh-1464. The item carries the first live transcript in edge order. An Event whose first part is `done` therefore reports `done` while a later part is still processing. No acceptance criterion covers several transcripts; the choice is documented on the field and tested in `timelineRead.test.ts`.
4. The statement reads the relation with `Events.transcript` as property A only (see "Contracts").
5. The birthday of the third criterion is a stand-in (see above and "NOT RUN and BLOCKED").
6. Spec seam: the fixture says "Standup 09:00" without an end. The Events write rule stores `timeTo` one hour after `timeFrom` for a timed Event without an end, so the test expects `timeTo` `10:00` for Standup.
7. `transcript` appears on every item of the full shape of `GET /api/calendar/timeline` as well, because the Task puts the field on the timeline item. The lookup also runs for the compact shape and for a range without Events.
8. The cast of the relation property's `config.targetDatabaseId` to `uuid` in the join. It is schema metadata, not a stored user value, and the generic relation expansion uses the same expression.
9. No ADR was added. `docs/adr/2026-11-10-calendar-timeline-merges-a-list-of-sources.md` covers a later consumer that calls the one read (decision 1) and batched lookups of a source (decision 3). Its decision 3 lists the core sources' lookups without the new one; the ADR was not edited, and both reviewers judged that correct.
