## What was delivered

- The generic operation `page.rename` in the catalog (`backend/packages/shared/src/genericOperations/`): capability `core.item.write`, non-destructive, risk class `write`, reversible, no approval.
  - Input `PageRenameInputSchema`: `{ pageItemId, title }`, strict, `pageItemId` a canonical UUID, `title` a string of any length; the operation normalizes it and refuses one that is too long.
  - Output `PageRenameOutput`: `{ pageItemId, title }` with the title as stored.
  - Port method `GenericApplicationPort.renamePage(actor, input)`. `createGenericApplicationService` implements it as `docStore.renamePage(input, origin)` with `origin` from the actor (`user` or `ai_agent`).
- Data layer, `backend/packages/data/src/docs/pageOperations.ts`:
  - `renamePageWithClient(client, { pageItemId, title }, origin)` runs in the caller's transaction; `docStore.renamePage(input, origin)` in `docs/docStore.ts` wraps it in one `withTransaction`.
  - It reads the page without a lock (missing, trashed or foreign: `NotFoundError`; a live item of another database: `ValidationError` with `field: "pageItemId"`, `reason: "not_a_page"`, before the title is looked at), normalizes the title with `normalizePageTitle` (every run of line breaks becomes one space, trimmed; more than 500 code points is a `ValidationError` on `title`; an empty title is valid), takes `FOR UPDATE` on the row of the item `parentItemId` names when it exists, live or trashed, and then on the page's row, and checks under the page's lock that the page is live.
  - A title equal to the stored one returns without writing.
  - Otherwise it writes the item's `title` through `updateItemWithClient` with the allowed system key `title` under the `pages` owner process, and then, in one `mutateDocWithClient` call with the caller's origin, gives the first `page` block of the parent's document that names the page the new title as plain text, through the block model's `writeBlock` with the block's own indent and `pageId`. A block that already reads the title is not written again.
  - A page no block of the parent names (an orphan), and a page whose `parentItemId` is not an id, names no item or names an item without a document, has only its item renamed and the call succeeds. No document is created for a parent that has none. The document of a parent that is in the trash is written like any other.
  - If the document write fails, the item keeps its old title: both writes are in the one transaction.
- `PATCH /api/items/:id/page/title` in `backend/services/semprec-api/src/itemsHandler.ts`: `:id` is the Pages item, the body is exactly `{ title }`, the answer is 200 with the operation output.
- The route matrix entry `{ name: "rename page", method: "PATCH", path: "/api/items/<id>/page/title", surface: "api", public: false, tenancy: "tenant" }` in `backend/services/semprec-api/src/routeMatrix/items.ts`, its `ROUTE_CASES` case and its `MCP_CASES` case `page.rename` in `tenantIsolationRoutes.test.ts`, and its `ROUTE_HANDLER_FILES` mapping to `services/semprec-api/src/itemsHandler.ts`.
- ADR `docs/adr/2026-11-10-page-rename-writes-the-item-title-and-the-parent-block-together.md`: the contract, what is written, the first-block rule, the no-op, the lock order and the capability exception to the family table.

## Contracts dependents build on

For #1765 (replace a page from Markdown, which renames a subpage whose link text changed), #1844 (agent approval classification) and gh-1729, which names this source as a shared-file-ordering blocker only.

- Inside the data package: `renamePageWithClient(client, input, origin)` for a caller that already holds a transaction, which is what #1765 needs inside its own transaction, and `docStore.renamePage` for one that does not. Nothing was added to the data barrel; `backend/packages/data/src/index.ts` did not change.
- Transports: REST `PATCH /api/items/:id/page/title` with body `{ title }` answers 200 with `{ pageItemId, title }`; the MCP tool `semprec.page.rename` and the agent tool derived from the catalog take `{ pageItemId, title }` and return the same object.
- REST refusals: 400 `validation_failed` with `details.field` `title` for a title over 500 code points after normalization, for a `title` that is not a string and for an absent body or a missing `title`; with the name of any other body field for an extra field (a `pageItemId` in the body included); without a field for a body that is not a JSON object; with `details.field` `pageItemId` for a host item; with `details.field` `id` for a malformed path id; 404 for an unknown, trashed or foreign page, a foreign page answering exactly like an unknown id; 401 without a session.
- The returned `title` is the stored one. A caller shows it instead of what it sent, because line breaks and surrounding spaces are normalized away.
- Only the first block in document order that names the page is retitled; it is the block the title mirror job reads. Another block that names the same page keeps its caption.
- The unchanged check compares with the item's stored `title`. A block that differs from an unchanged item title is left for the mirror job.
- Lock order: the parent's row, then the page's row, then the item update, then the parent's document last. It is the order of the title mirror job and of `page.duplicate`, so a rename waits while a mirror job, a duplicate or a subpage creation holds the row of the same parent. A new writer that touches a Pages item and its host takes the host's row first.
- Breadcrumbs (gh-2014), the trash and item reads show the new title as soon as the rename commits, because they read the item. The document update of a rename enqueues the mirror job of the parent like any page write; when it runs it finds block and item equal and writes nothing.
- Renaming the root page of a host (`meta.title`, section 6 of the family record) is not delivered here.
- An agent that holds `core.item.write` can rename a subpage, and with it rewrite the text of a `page` block in a host document, without approval. #1844 owns the agent classification and may change it in a record of its own.
- Order for gh-1729: its entries in the shared registries go after the entries of this source, unless its Task names another position. Neither `domainWriteHooks.ts` nor `db/tenantCutoverMigrations.ts` is touched by this source.
- The catalog has 42 operations on the integration tip; `issues/handovers/gh-1722.md` lists what a source that adds one has to change.
- No SQL migration, no table, no column, no index, no job name, no write hook, no stored key and no user-facing label was added.

## Deviations from the specification and spec seams

1. Spec seam: the route entry is in the slice module `backend/services/semprec-api/src/routeMatrix/items.ts`, not in `routeMatrix.ts`.
2. Spec seam: the function is `renamePageWithClient`, with `docStore.renamePage` opening the transaction, where the Task says `renamePage`.
3. Against the family record `2026-10-28-page-operation-family`, decided for the Task and recorded in the new ADR: capability `core.item.write` instead of `core.page.write`.
4. Lock order differs from the Task's wording. The Task names only the row lock the item update takes; the operation takes `FOR UPDATE` on the parent's row and then on the page's row before it compares and writes, because item-then-document without the parent's row would be the reverse of the mirror job's document-then-item order. The live check and the unchanged check run under the page's lock.
5. Decided where the issue is silent: the first block in document order that names the page is retitled and other blocks naming it keep their caption; the block is written through `writeBlock` with its current indent and `pageId`; a block that already reads the title is not rewritten; the document of a trashed parent is written; a parent that is gone, unusable or without a document means item only; a host item is refused before the title is validated; an extra body field is a 400 naming it and an absent body is a 400 on `title`; the route answers 200.
6. `backend/packages/application/src/genericOperationGateway.ts`, in `Touches` "only if its exhaustive mapping needs the name", did not change.
7. The acceptance criterion says breadcrumbs are composed "without loading the parent document". The test proves it as a finite observation: a spy over every statement that names `docs`, `doc_snapshots` or `doc_updates` finds no ancestor item id and no document id, the method of the gh-2014 test.
