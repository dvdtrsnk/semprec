## What was delivered

Three calendar write tools, capability `calendar.write`, each approval-gated for a run (`approval: always`, `requiresApproval`): `calendar.respondToInvitation` (risk class outbound), `calendar.placeTaskInEvent` and `calendar.removeTaskFromEvent` (risk class write). Each handler runs the owning route handler (respond route, task host-event put and remove routes) and returns the route's payload as JSON; a refusal of the route is the tool's error result, another tenant's ids behave as unknown ones. Agent (Semp) sessions get them when the run's project owns the calendar databases, through the existing `moduleTool` approval flow; the approved request answers the invitation or changes the relation exactly once.

Over `POST /mcp`:
- A run credential is offered the tools only when its own capability list names `calendar.write` (the mint accepts it as a capability id of the calendar module) and the run's project holds the grant. A read-only credential, a credential that does not name `calendar.write` and a project without the grant see them as an unknown tool (-32601, the message of an unknown name) and nothing is filed.
- A `tools/call` of a `requiresApproval` tool validates the arguments (-32602 on a mismatch), files the `moduleTool` request through `createModuleToolApprovalRequest` and answers -32001 without running the handler (Task step 3).
- A human session gets the tools through `resolveModuleAgentToolsForUser` and runs the human handlers as the user at once, with no request (a session has no run; ADR 2026-10-28 section 3), written as an agent for the user with the external-client marker.
- Writes of an approved run are agent writes: `{ writerKind: agent, agentRunId, agentProjectItemId, onBehalfOfUserId }` with no human writer. The route handlers take an optional writer and default to the user, so the routes are unchanged. A run without a project is refused 403.

## Deviations from the specification and spec seams

1. Spec seam, resolved on the second fix round: the Task says the capability is "granted" over `/mcp`. The first implementation admitted `calendar.write` from the project's grants (`MCP_PROJECT_GRANTED_MODULE_CAPABILITIES`); the tip's mechanism (credential stores module capability ids, gh-1956) replaced that, so the list was removed and `calendar.write` comes from the credential's own list.
2. Because `/mcp` now offers approval-gated module tools to a run credential, the approval-gated heartbeat tools (gh-1846) that a credential's capabilities reach are also listed and deferred over `/mcp`; recorded in the ADR consequences.
3. A human-token MCP client answers invitations without an approval, so the reply email is sent at once, as a session's mail send is; a run credential gets the approval gate. Recorded in the ADR.
4. The handlers write as an agent for the user (not as a human user), following the ADRs on agent-write attribution; the invitation's `status` and `respondedAt` stay written by the calendar owner process.
5. The tool result is the item as `ItemRow` JSON, equal to the route's item (the envelope's `blobs` is absent for an invitation).
6. Barrel: `packages/data/src/index.ts` is at the 900-line ESLint cap, so no barrel export of the tools was added (the registry resolves them from the manifest, which re-exports them) and `publicSurface.test.ts` was not changed for this source.
7. No `snapshotExport` is declared (not in the Task).
8. The `schemaHandler.test.ts` case "no agent tool (issue #1600)" was updated to the three tools, and the gh-1791 test in `moduleTools.test.ts` that asserted gated tools absent over MCP was rewritten.
9. The handover of gh-1764 describes a `task_recurrence` guard on the put route that is no longer in the code (gh-2012); the tests follow the code.
