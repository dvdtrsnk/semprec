# gh-1827 handover: Redact sensitive tool results from agent run history

Delivered on the integration branch by the merge of chain `e1-097-agent-runtime` (single member gh-1827), candidate `dccf47011c6ca60b60e1c52b6066d0fc54cf0ecf`. The merge was automatic, with no conflict and no migration.

## What was delivered

The stored `tool_result` event of a content-bearing generic operation on a sensitive database is `[redacted: sensitive]`; the running turn and the live stream still see the real result.

- Marking (`packages/agent-runtime/src/tools/generic/genericOperationAgentTools.ts`): after a successful `item.get`, `item.create`, `item.patch`, `item.delete`, `item.restore`, `database.query` or `view.query` the tool reads the `sensitive` flag of every database the answer contains and marks the result (`sensitive: true`) when any of them is sensitive. The databases examined are the queried database (or the database of a queried view), the database of each returned item, the database of every non-hidden relation target expanded through `include.relations`, and the target database of every relation property projected on such a target. The flag is read through `createChokePoint(pool).getDatabase` / `getView` in the caller's tenant scope, after the operation answered. An unknown database, a lookup failure, or expanded relation content that names no database counts as sensitive (fail closed). Structure-only operations (`database.get`, and so on), refusals and the deferred `item.delete` are not marked.
- Carrier: `AgentToolResult.sensitive` (`types.ts`); the composition root (`services/semprec-agents/src/agentSessionComposition.ts`, one line) copies it into the pi result `details`.
- Redaction (`packages/agent-runtime/src/sensitiveToolResult.ts`, not exported from the package index): `redactSensitiveToolResult` replaces the content of a marked tool result with the fixed marker, drops the mark, and keeps only the keys of `details.changes` (before/after dropped, since `before` is an item value). `runAgentTurn` in `lifecycleAdapter.ts` applies it before persisting the event; `onEvent` receives the real message.
- Reconstruction (`conversationReconstruction.ts`) is unchanged: the redacted event keeps its `toolCallId` and is an ordinary tool result, so every call stays paired and a resumed run continues from the marker.
- ADR `docs/adr/2026-11-13-sensitive-tool-results-are-marked-by-the-tool-and-stored-redacted.md` records the mark, its single consumer, the fail-closed rules, the post-commit flag read (sound only while `databases.sensitive` is never turned off) and the key-only `changes` rule. It extends `2026-11-03-item-patch-change-redaction-uses-write-metadata`.

## Deviations and spec seams

1. `agentSessionComposition.ts` is outside Touches: one line carries the mark into the pi result details; without it the mark never reaches the lifecycle adapter. Tests in `agentSessionComposition.unit.test.ts`, `piConversationHistory.unit.test.ts` and `agentRun.e2e.test.ts` are likewise outside Touches.
2. The redaction lives in a new module `sensitiveToolResult.ts` to keep `lifecycleAdapter.ts` small.
3. `conversationReconstruction.ts` needed no change.
4. `details.changes` of a marked `item.patch` keep only their keys; the Task names only the content.
5. The sensitivity lookup is a separate read after the operation answered, not inside its transaction. It is sound because the flag is only ever set to true.
6. Review finding fixed after the first review: relation targets expanded into a non-sensitive item are examined too (see Task seam: the Task text names only the item's database and the queried database, the Context and the first criterion cover the expansion).
7. The chain used the commit trailer named in its task text.
