## What was delivered

- `eventParticipantEdgeWriteHook` (`backend/packages/data/src/calendar/eventParticipantEdgeHook.ts`), a relation edge write hook registered in `backend/packages/data/src/domainWriteHooks.ts`. It judges every add and every metadata replace of an edge of the relation between `Events.people` and its inverse `People.events`, whichever of the two properties the write names. A removal does not run it. A write on any other relation returns after one lookup of the relation's properties.
- The edge metadata has the shape `{ role?: "organizer" | "attendee", invitation?: { status: "pending" | "accepted" | "tentative" | "declined", email: string, mailboxId: uuid, sentAt?: ISO instant, respondedAt?: ISO instant } }`, both objects strict. Absent metadata and `{}` mean an attendee without an invitation.
- Refusals, each a `ValidationError` (`validation_failed`):
  - `field: "metadata"`, reason `invalidParticipantMetadata`: an unknown key, a role outside the two roles, an invitation of another shape, an invitation on an organizer edge.
  - `field: "metadata"`, reason `organizerNotSelf`: an organizer edge to a person other than the tenant's self person (`getSelfPersonId`), also when no person is linked.
  - `field: "metadata"`, reason `organizerAlreadySet`: an organizer edge while another edge of the same Event is an organizer edge.
  - `field: "metadata"`, reason `invitationReadOnly`: from a writer whose kind is not `system`, an `invitation` that is not deeply equal to the stored one. That includes adding one, changing one and leaving a stored one out. A `user` or `agent` write that repeats the stored invitation passes.
  - `field: "callerItemId"` or `"targetItemId"`, reason `nonCanonicalItemId` (fix `cc8d1eb64`): an Event id or person id that is not in the 8-4-4-4-12 form. Either letter case is accepted and lower-cased. The check runs before any lock or lookup, for every writer, on create, metadata replace, insert-only writes and the checks that write nothing.
- Lock. The hook takes the Event row lock (`FOR UPDATE`; `NOWAIT` under the value-link admission, reported as busy) before it reads the Event's edges, so two participant writes of one Event run one after the other. An insert-only write that carries no invitation and is not an organizer edge returns after the shape check, without the lock and without the edge read (fix `d21043c70`).
- `insertOnly` (`backend/packages/data/src/chokePoint/hooks.ts`, `relationOps.ts`): a new optional field of `RelationEdgeWriteHookContext`, set to `true` by `createRelationIfAbsentWithClient` alone.
- `GET /api/events/:id/people` (`createListEventPeopleRouteHandler` in `backend/packages/data/src/calendar/eventParticipantsRouteHandlers.ts`). For a live Event of the caller's tenant it answers `200 { people: [{ personId, name, relationship, emails, role, invitation }] }`. `name` and `relationship` are the person's stored values or `null`; `emails` are the distinct normalized addresses of `People.emails` in stored order; `role` is `attendee` for an edge without a role; `invitation` is the stored object or `null`. The organizer comes first, the others by name in the caller's locale (`Intl.Collator`, Czech or English), equal names by person id. A person in the trash is left out. An unknown id, a trashed Event, an item of another database, another tenant's Event and a tenant without an Events database all answer `404 not_found` ("Event not found"). An id that is not a UUID answers `400 validation_failed` on `id`.
- The route is declared as `listEventPeople` in `customRoutes` of `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` (justification `single-consumer-read`, handler re-exported there), exported from `backend/packages/data/src/index.ts` and listed in the frozen export list.
- The ownership handoff is recorded in the header comment of `backend/packages/data/src/calendar/calendarModuleManifest.ts`: the edge and its `role` stay the user's, the `invitation` object is written by the calendar module's invitation code with the system writer kind.
- ADR `docs/adr/2026-11-11-event-participant-invitations-are-written-by-system-writers.md` (accepted, backend): the handoff, the writer-kind rule, the Event row lock and its order, the insert-only exemption, item ids in one text form.
- No migration, table, column, generic operation, job name, tenant cutover entry, stored key or i18n key was added.

## Contracts dependents build on

- Writers of invitations (gh-1790, gh-1774, gh-1950) write the participant edge with the system writer kind. Internal code that names no writer writes as `system`. A relation write replaces the whole metadata object, so a system writer that changes one field sends the whole object.
- A public client (REST `PUT /api/items/:id/relations/people/:personId`, MCP `semprec.relation.put`, the agent gateway) that changes the `role` of an invited participant must send the stored `invitation` back unchanged. Otherwise it gets `400 validation_failed`, field `metadata`, reason `invitationReadOnly`, and the stored edge stays.
- Exports of `eventParticipantEdgeHook.ts` for code inside `@semprec/data`: `EVENT_PEOPLE_PROPERTY_KEY`, `parseEventParticipantMetadata`, `readEventParticipantMetadata`, the types `EventParticipantRole`, `EventParticipantInvitation`, `EventParticipantMetadata`, and the hook. `readEventParticipantMetadata` reads a stored role outside the two roles as `attendee` and a stored invitation of another shape as none. Only `createListEventPeopleRouteHandler` is exported from the data barrel.
- An Event has at most one organizer edge, and only to the tenant's self person. Creating that edge is left to gh-1790; this source only validates it.
- Lock order for a participant write that takes the lock: Event row first, then the edge row, then the People `lastContact` job key that the changed-edge hook takes. That is the order of an Event update. A transaction that composes several writes and already holds a person's job key before a locking participant write can still deadlock with an Event update; the ADR records this residual.
- `createRelationIfAbsentWithClient` on the participant relation (the speaker confirmation of `inbox/proposalActions.ts`) passes a stored edge with an invitation untouched and takes no Event lock, as long as it carries no invitation and no organizer role.
- Route matrix: the entry `event people` is in the new slice `backend/services/semprec-api/src/routeMatrix/events.ts` (`EVENTS_ROUTES`), spread last in `ROUTE_MATRIX`. Later routes of the `/api/events` family go into that slice. `ROUTE_HANDLER_FILES` and `ROUTE_CASES` have the matching entries.
- Order in `domainWriteHooks.ts`: `registerRelationEdgeWriteHook(eventParticipantEdgeWriteHook)` follows `mailboxItemRestoreHook` of gh-2032 and precedes `defaultCalendarCreateHook` of gh-1761, which is the last entry.
- For tests and fixtures of later sources: metadata on an `Events.people` or `People.events` edge must have the defined shape; free-form metadata is refused. An edge with a legacy shape can only be planted with raw SQL.

## Deviations from the specification and spec seams

- The hook applies to the relation definition, so a write through `People.events` (added by gh-1664 after the record was written) is judged like a write through `Events.people`. The Task says "only to the `people` property of the Events database"; applied literally, the invitation rule could be bypassed from the person's side.
- Files outside `Touches`: `chokePoint/hooks.ts` and `chokePoint/relationOps.ts` (`insertOnly`), `routeMatrix/events.ts` (the entry is in a slice, not in `routeMatrix.ts` itself), the ADR, and the two transcription test files.
- Reasons beyond the three the Task names as examples: `organizerAlreadySet` and `nonCanonicalItemId`. An invitation on an organizer edge is `invalidParticipantMetadata`.
- Not in the Task: the Event row lock, the insert-only exemption from it, and the refusal of other UUID text forms.
- The route answers an id that is not a UUID with `400 validation_failed` on `id`; the Task names only 404.
- The Context decision that an organizer edge is not copied into a recording's people or into task people has no Task step, `Touches` entry or acceptance criterion. Nothing was built for it here. On this tip the task inheritance of gh-1724 omits the tenant's self person, the only person an organizer edge can name; that was not tested in this landing.
- Existing tests were changed: `transcriptSpeakerSuggestion.test.ts` (fixtures use the defined invitation shape, one legacy shape is stored with raw SQL and its row count is asserted) and `transcriptionSpeakerEdges.test.ts` (the free-form metadata example moved to a Tasks people edge).
