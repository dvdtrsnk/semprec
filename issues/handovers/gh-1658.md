# gh-1658 — page and Journal text in the item search index

Repository-Issue: gh-1658

## What changed

- Migration `0120_item_search_index_body.sql` (expand only): nullable `body text` and `page_text text` on `item_search_index`. No default and no backfill; an existing page is converted on its next edit.
- `CORE_TASK_NAMES.ITEM_SEARCH_PAGE_TEXT` (`itemSearchPageText`) in `@semprec/queue`, with `api` affinity and `tenant` tenancy. Its handler is registered in `worker.ts`.
- `docs/docPersistence.ts`, `appendDocUpdateWithClient`: the `docs` update now returns `item_id` and `kind`. For a `page` doc the same transaction enqueues the job with `jobKey` = the owner item id, `jobKeyMode: "preserve_run_at"`, `runAt` 30 seconds ahead and lane `tenantLane("item-search-index")`. A `canvas` doc queues nothing.
- `search/pageTextJob.ts`, `handleItemSearchPageTextTask(pool, payload)`: one transaction. It finds the owner item's `page` doc (item not soft-deleted, not in Emails), loads the doc, and converts it with `readPageBlocks` → `serializeBlocks` (#1608) → `stripMarkdown(…, 100000)`. It then calls `indexItem(client, itemId, { pageText })`. A missing item, a soft-deleted or Emails item, or an item with no page doc returns without writing.
- `search/stripMarkdown.ts`: re-exports `stripMarkdown` from `@semprec/block-model`. #1608 already ships it, so the file adds no second implementation.
- `search/itemSearchIndexer.ts`, `indexItem(client, itemId, { onlyMissing?, pageText? })`:
  - `pageText` is passed only by the page job. Otherwise the stored `page_text` is read in its own statement after the item lock, so a concurrent page-job commit is seen.
  - The vector includes the page text. The upsert writes `body`. Its conflict branch writes `page_text` only when the page job supplied it, so an item write leaves the column as it is.
- `search/itemSearchDocument.ts`: `pageText` is a new input. The new `buildItemSearchBody` returns a Journal day's Inbox entry texts followed by its page text, or the page text alone for every other item, and null when neither exists.
- `inbox/journalInboxCompute.ts`, `recomputeJournalInboxDay`: calls `indexItem(client, dayId)` in the same transaction as the `computed` write, so a day's `body` follows its Inbox entries. The stored page text is kept and the page is not reconverted.
- `testSupport/pageFixtures.ts`, `writePageTextBlocks(pool, itemId, texts)`: appends text blocks through the block-model writer and `mutateDoc`, re-exported from `testSupport/testDb.ts`.

## Tests

- `packages/data/src/__tests__/itemSearchPageText.test.ts` (new, integration, runtime-role pool, one tenant). It covers:
  - a page edit makes its text searchable after the job runs, and `page_text` holds the converted text;
  - a burst of three edits queues one job whose run time is the first edit's, and the job converts the whole page;
  - a canvas doc write queues no job, and the canvas item's job completes without writing;
  - a soft-deleted item's job completes without writing (index row unchanged);
  - a missing item's job completes without writing;
  - an Emails item's job completes without writing (no index row);
  - page text is capped at 100000 characters;
  - an item write rebuilds the row and keeps `page_text`, and the page is still searchable;
  - a Journal day's page is searchable by its phrase, and `body` is the Inbox entry followed by the page text;
  - an Inbox entry change rewrites the day's `body` and leaves `page_text` unchanged.
- `packages/data/src/search/__tests__/itemSearchDocument.unit.test.ts`: page text is in the document; the body is the Inbox text followed by the page text for a Journal day, the page text alone for other items, and null when both are absent; a non-day Journal item quotes no Inbox text.
- `services/semprec-api/src/__tests__/tenantIsolationJobs.test.ts`: a two-tenant case for the new `api` task, as the test requires for every task of the affinity set.

## Notes for dependants

- Excerpts: `item_search_index.body` holds the excerpt source. Producing `snippet` with `ts_headline` is #1996; this issue only stores `body`.
- Stored text is per owner item. A page hit is the item's own hit, and no separate result group exists.
- Freshness: a page is converted about 30 seconds after the first edit of a burst, because the run time is kept while the job waits. An edit after the job has started queues a new job. A Journal day's `body` follows its Inbox entries through the recompute, which now reindexes the day. The fan-out for other computed-cache changes remains #1652's.
- An item write never changes `page_text`. Only the page job replaces it, and a missing or stale page text is repaired by its next edit.
- A canvas doc has no page text and queues nothing.
- Existing pages keep `page_text` NULL until their next edit, as the Task specifies.
- `stripMarkdown` is implemented once, in `@semprec/block-model`. `search/stripMarkdown.ts` only re-exports it.
- Blocks written through the legacy flat-map API (`docs/blocks.ts`, still used by the proposal path until #1681) go through the same block-model reader. This issue did not test what text that path yields.
- The job key is the item id, as the Task specifies. Item ids are server-generated UUIDs, and the job runs in the owner's tenant.
- `writePageTextBlocks` is a test fixture re-exported from `@semprec/data/testSupport`. Other tests may reuse it.
- Integration: gh-1441 merged first and took ordinal `0119` (`0119_notification_preferences.sql`). The integrator renamed this migration from `0119_item_search_index_body.sql` to `0120_item_search_index_body.sql`, the next free ordinal. The file has no internal reference to its name, and no other code refers to it. The migration numbering check and the tests were not re-run at integration.
