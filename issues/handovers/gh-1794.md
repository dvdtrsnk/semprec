## What was delivered

- `findSleepMuteUntil(client, now)` in the new file `backend/packages/data/src/sleep/sleepMuteWindow.ts`. It reads the tenant's non-deleted sleep settings item, the non-deleted plans and the night exceptions of yesterday and today (tenant time zone, `getSystemTimezone`), resolves those two nights with `resolveSleepNights` and returns, as a `Date`, the latest wake time of a night whose window contains `now` (bedtime inclusive, wake time exclusive) when `enabled` and `muteSemp` are both exactly `true`; otherwise `null`.
- `handleNotificationFanoutTask` in `backend/packages/data/src/notifications/notificationFanoutJob.ts`: after the preference filter of gh-1443 and before registrations are loaded or `push_deliveries` rows are claimed, it calls `findSleepMuteUntil` unless the category of the kind's policy is `approvals`. Inside the window it enqueues the same task for the wake time and returns without claiming or sending.
- The deferred job is the same handler and makes the same check: a wake time that moved later holds again under a new key; otherwise the existing claim and send path runs.
- A sleep read that throws is logged with `logger.error` and the fields `notificationId` and `errorName` only, and the push is sent. A failing deferred enqueue fails the job (it is retried by the queue).
- An injectable clock: the handler's third parameter is now `NotificationFanoutDependencies` (`PushSenders` plus an optional `now: () => Date`). Production (`worker.ts`, unchanged) passes no clock.
- ADR `docs/adr/2026-11-12-a-push-inside-the-sleep-window-is-held-by-a-deferred-fan-out-job.md` (accepted, backend).
- No migration, table, route, generic operation, MCP tool, new job name, write hook, stored key or i18n key was added.

## Contracts dependents build on

- **The deferred job.** Task name `notificationFanout` (`CORE_TASK_NAMES.NOTIFICATION_FANOUT`), payload `{ notificationId }`, `jobKey` `notification-fanout-deferred:<notificationId>:<wake time as Date.toISOString()>` (UTC with milliseconds, for example `...:2026-10-17T06:30:00.000Z`), `jobKeyMode: "preserve_run_at"`, `maxAttempts` 10, `runAt` equal to the wake time. It is enqueued inside the job's tenant scope, so its envelope carries the tenant. The first job keeps its key `notification-fanout:<notificationId>`.
- **`findSleepMuteUntil(client: PoolClient, now: Date): Promise<Date | null>`.** It is exported from its module only; it is not in the `@semprec/data` barrel, so `publicSurface.test.ts` is unchanged. It returns `null` when the tenant has no sleep settings item or no sleep database. It throws when the tenant has more than one non-deleted settings item, when a stored plan or exception has wrong value types (zod: `wakeDays`, `bedTime`, `wakeTime`, `position` for a plan; `night`, `bedTime`, `wakeTime`, `alarm` for an exception, an unset field read as `null` as the gh-1792 handover requires), and with whatever the time zone lookup or the resolver throws.
- **`NotificationFanoutDependencies`** is a new exported type and reaches the `@semprec/data` barrel through the existing `export *` (type only). Callers that pass `PushSenders` compile unchanged.
- **Order in the handler**, for gh-1829, gh-1831 and gh-1826, which change the same file after this source: load notification, read preferences, preference filter, sleep check (skipped for category `approvals`), then registrations, claim and send. `push_deliveries` rows are created only at the real send.
- **What is not done, by decision of the record.** A held push is not released early when the wake time moves earlier or the mute is switched off after the hold. The tenant's time zone is used, also while travelling.
- **The sleep read uses its own SELECT** on the three sleep databases after `getDatabaseByModuleId`. `loadSleepNights` of gh-1809 is not delivered and is not a blocker; when it lands, this reader can be replaced by it. gh-1784 (not delivered) will refuse a second settings item; until it validates sleep writes, a stored plan with a wrong shape makes every check throw, which sends the push at once and logs an error.
- **Tests that run the fan-out job for a seeded tenant on the real clock** now depend on the hour, because the default plans hold a push at night. Such a test passes a fixed daytime clock or switches `muteSemp` off in its seed, as the two adjusted tests do.

## Deviations from the specification and spec seams

1. `findSleepMuteUntil` returns a `Date`; the Task says "the latest `wakeAt`", which in the resolver is an ISO string with a zone offset. The `<wakeAt ISO>` of the job key is `Date.toISOString()`, so one instant always gives one key.
2. The handler's third parameter changed from `PushSenders` to `NotificationFanoutDependencies` (Task step 4 asks for an optional `now` in its dependencies).
3. The check sits directly after the preference filter, before the registrations are loaded; the Task says "before `claimPushDeliveryTargets`".
4. Reader decisions the Task leaves open: a missing sleep database reads as empty; more than one settings item throws; `enabled` or `muteSemp` that is not exactly `true` gives `null`; a plan's name and alarm and the prep reminder are not read.
5. Files outside `Touches`: the ADR and the two adjusted tests (`sempProblemNotification.test.ts`, `tenantIsolationJobs.test.ts`). Both ran the job for a seeded tenant on the real clock and would have failed at night.
6. The acceptance text speaks of a notification "created at" an instant; the tests set the job's clock to that instant, the row's `created_at` is the real time.
7. `jobKeyMode: "preserve_run_at"` cannot be told apart from `replace` by a test here, because a repeated hold has the same run time.
