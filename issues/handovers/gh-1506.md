# Handover for gh-1506

A mailbox that is not syncing has one Semp problem, key `mail:<mailboxId>`. The sync job and the `mail:<mailboxItemId>` stall check both raise it, so their reports merge. A completed pass resolves it, and so does the check's return to `ok`. Implementation committed as `5d6e0863` on `wf/gh-1506-n3`, with this handover as a second commit. I did not push. The full `pnpm run verify` was not run.

- **Key:** `mailProblemKey(mailboxItemId)` in `semp/sourceProblemKeys.ts`. It is internal, not exported from `@semprec/data`, so `publicSurface.test.ts` is unchanged.
- **Sync job (`mail/mailSyncJob.ts`):** the failure transaction raises the problem after `recordSyncError` and the `syncStatus` write. The problem is `category` `mail`, `kind` `mailSyncError`, `severity` `critical` for `needsReauthorization` and `warning` otherwise. `since` is the `failing_since` that `recordSyncError` now returns, and `occurrenceKey` is the job id. A revoked credential gets the problem but still no `mail_sync_error` notification. The IMAP, Gmail and Graph success transactions resolve the problem (`recovered`) right after their `ok` write.
- **Store (`mail/mailAccountSyncStateStore.ts`):** `recordSyncError` returns `Date | null`. It is `null` when no state row matched, and then nothing is raised. Its callers that ignore the return are unaffected.
- **Stall check (`observability/observabilityCheckSystem.ts`):** on the alerting transition it raises the same problem, with `occurrenceKey` `<jobId>:mail:<mailboxId>` and `since` set to `failing_since`, or to now when that is null. Severity is `critical` when the stored failure kind is `reauthorization`, otherwise `warning`. On the transition from alerting to `ok` it resolves the problem. A tenant with no user gets no raise, like the notification.
- **Connection limit:** the `MailConnectionLimitError` branch is unchanged and raises nothing.
- **Tests:** `__tests__/mailSync.test.ts` has the new describe "mailbox Semp problem raised by the sync job (issue #1506)", with six tests. They cover the merge across failing passes with a redelivery counted once and `since` equal to `failing_since`, `critical` for a revoked token with no notification, no problem before a user exists, no problem when the state row vanishes mid-pass, resolve followed by reopen, and no problem for a connection-limit rejection alone. `__tests__/observabilityCheckSystem.test.ts` has the new describe "mailbox Semp problem on the stall check (issue #1506)", with six tests. They cover one `warning` on the first stall and none on later ticks, `critical` after a revocation, `since` equal to `failing_since`, a merge with a real sync-job failure into one problem with count 2, resolve on `ok`, and no user. The Touches list names `__tests__/mailSyncJob.test.ts`, which does not exist. As in gh-1497, the sync job tests live in `mailSync.test.ts`.
- **Checks run:** `pnpm run lint`, `format:check`, `build`, `check:boundaries` and `check:write-safety` pass with no new baseline entry. The zero-row branch reads `rowCount` explicitly. The integration files touched or named by the change pass, 11 files and 223 tests, including `mailSync`, `observabilityCheckSystem`, `tenantObservabilityChecks`, `sempProblemsProducers`, `sempProblemsStore` and `sempProblemsPrune`. Notes for dependants:

- Both reporters use one kind, `mailSyncError`. `ON CONFLICT` keeps the first kind stored, so the order of the reports does not matter. A revocation is shown by `severity` `critical`, not by a separate kind.
- `raiseProblem` returns an `outcome` (`created`, `merged`, `escalated`). Neither raise here reads it, so no push goes out for a mail problem yet. #1466 must read it if mailbox problems are to be pushed.
- A stall-check transition counts as an occurrence, once per job tick. So `occurrence_count` is the sync reports plus the stall transitions, not the number of failing passes alone.
- The resolve in the sync job's success transaction is in the same transaction as the `ok` write by construction. The tests assert the resulting state, not the transaction boundary.

Open follow-ups, not fixed in this issue:

1. **Removed mailbox:** `deleteOrphanedTenantObservabilityChecks` deletes the `mail:` check row of a removed mailbox but does not resolve its problem. The problem then stays active with no mailbox behind it. The removal issue (#1690) should resolve it.
2. **Stale snapshot in the stall check:** `checkMailSync` decides `ok` or `alerting` from the account snapshot read before the per-account transactions. A sync failure committed in between can have its fresh problem resolved by the check's `ok` transition. The next tick then alerts again, which means a second `mail_sync_stalled` notification and a new problem. The fix is to re-read the account inside each per-account transaction.
