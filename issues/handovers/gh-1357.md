# Handover for gh-1357

Provisioning now renders an Apple App Site Association file from two new `monitor` group keys, and Caddy serves it. The work is committed locally; I did not push or open a PR.

- **Keys:** `SEMPREC_APPLE_TEAM_ID` and `SEMPREC_IOS_BUNDLE_ID` are added to `deploy/shared/env/monitor.env.example` (empty). No value appears in the repository.
- **Provisioning:** `render_apple_app_site_association` in `deploy/provision.sh` runs before `render_caddy_environment`, so before Caddy reloads. With both keys set it installs `/etc/caddy/apple-app-site-association` (root, 0644) with the single `appIDs` entry `<TEAMID>.<BUNDLE_ID>` and one component matching only `/` with query `page=password-reset`. With either key empty it removes the file and warns naming the key, never a value. It runs even while `SEMPREC_DOMAIN` is empty.
- **Caddy:** `deploy/Caddyfile` has a handler for exactly `/.well-known/apple-app-site-association`, before the catch-all. It serves `{$SEMPREC_AASA_DIR:/etc/caddy}/apple-app-site-association` with `Content-Type: application/json` and no `try_files`, so a missing file is a 404.
- **Tests:** `deploy/Caddyfile.test.sh` starts Caddy twice (file present, then absent) and asserts 200, `application/json`, the exact body, and 404 without HTML; the access-log assertions are unchanged. `deploy/provision.test.sh` covers empty keys, both keys set (exact JSON, mode 0644), one key emptied (file removed, only that key named) and that no value is printed.
- **Not run:** this host is macOS without `caddy`, and both test scripts use GNU `sed -i`, so I ran only `bash -n` on the three scripts. Run `deploy/provision.test.sh` and `deploy/Caddyfile.test.sh` on Linux with Caddy in CI.
- **Notes:** `apple/README.md` did not exist at this tip, so I created it holding only the Associated Domains paragraph. The Associated Domains entitlement and the new-password screen are left to the app issues. The invitation link is deliberately not claimed.
