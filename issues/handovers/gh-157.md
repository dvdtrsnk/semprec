## Summary

Implements issue #157: typed queries and relation mutations for the generic REST layer.

- `POST /api/databases/:id/query` and `POST /api/views/:id/query` accept `{ filter, sort, cursor, limit, inTrash? }`, compile through the same shared typed filter/sort engine (`queryItemsCore` in `viewQuery.ts`), and return `{ items, nextCursor }`. Ad-hoc database queries and view queries over equivalent input produce identical results.
- Deterministic keyset pagination via `id > cursor` under default order; limit defaults to 50 (upstream caps at 200); deleted rows excluded unless `inTrash: true`.
- `PUT`/`DELETE /api/items/:id/relations/:propertyKey/:targetItemId` resolve `:propertyKey` to a property id and go solely through the existing audited relation choke-point (issue #82) — direction normalization, cardinality, paired properties, and ownership are enforced there, never re-implemented at the route layer.
- Both routes always return the full authoritative envelope (item page or relation edge), never an empty 204.
- Added `cardinality_violation` (409) to the closed error-code enum.
- `deleteRelation`'s return type widened from `void` to `RelationEdge | null` so the DELETE route can return the deleted edge or a proper 404.

Tests cover query parity between database/view routes, stable non-duplicating pagination, `inTrash` visibility, `validation_failed` for malformed filter/sort/limit/cursor/inTrash, and relation-route coverage for direction normalization, every cardinality, paired definitions, foreign/missing property keys, and owner violations.
