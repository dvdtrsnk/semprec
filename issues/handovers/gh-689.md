## Summary

Implements issue #689: `core.agentRun` now notifies once per failed heartbeat occurrence, not once per retry attempt, and never masks the original `runAgent` error with a close/notify failure.

### Changes

- **`actions.ts`**: Added `ActionContext.isFinalAttempt?: boolean`, documented as set by the heartbeat fire task from `attempts >= max_attempts`, `undefined` for a direct caller (treated as final). In `coreAgentRunAction`'s catch:
  - `isFinalAttempt === false` → `finishAgentRun(pool, run.id, "error", message)` (no notification).
  - otherwise (final attempt or direct caller) → `finishAgentRunWithErrorNotification` in its own transaction, same as before.
  - The close/notify call is now wrapped in its own `try/catch`; on failure it's logged via `createLogger("scheduler")` and the original `runAgent` error is what gets rethrown, never the close failure.
- **`sweep.ts`**: Both handler call sites (`createHeartbeatFireTaskForAffinity` and `runScheduledOccurrenceFire`) now pass `isFinalAttempt`, hoisted above the `try` blocks (the first site's was previously computed only inside its `catch`).
- **New test file** `backend/packages/data/src/__tests__/coreAgentRunAction.test.ts` (integration tier) covering: two non-final + one final attempt → 3 `error` runs, 1 `agent_run_error` notification on the last run's id; direct caller with `isFinalAttempt` omitted → pre-existing one-run/one-notification behavior; close transaction's `connect()` failing → handler rejects with the original error, run stays `running`, no notification; through the real fire task with `attempts=3/max=3` vs `attempts=1/max=3`.

`pnpm run verify` passed in `backend/` (lint, format, build, unit, integration — including the two pre-existing `core.agentRun` cases in `scheduler.test.ts` unchanged — e2e, write-safety, boundaries). No `web/` changes, so its verify wasn't run.
