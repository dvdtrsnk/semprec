## What it does
`deploy/systemd/scripts/semprec-restore-test.sh` replaces the skeleton. It runs monthly as root, like the backup service, because it drives Docker and restic.

1. **Restore:** it restores the newest restic snapshot (`restic restore latest`) into a temporary directory under `/var/tmp`.
2. **Disposable containers:** it starts a throwaway PostgreSQL and MinIO on a new Docker network created with `--internal`. It never touches the production Compose containers or volumes. MinIO credentials are passed as environment variables, never on the command line.
3. **Checks, in order:**
   - `pg_restore --exit-on-error --no-owner --no-privileges` succeeds.
   - `items` count is above 0.
   - The newest `items.updated_at` is at most 48 hours old.
   - `doc_snapshots` count is above 0, and no row has an empty `state`.
   - 20 random `blobs` rows that have a hash (or all of them, if there are fewer) read back from the disposable MinIO with exactly the recorded size and SHA-256.
4. **Cleanup:** the containers, network and restored files are removed on every exit path, including SIGTERM. If cleanup fails, the exit path tries again, and a cleanup that still fails counts as a failed run.
5. **Success:** only after every check passes and cleanup succeeds does it record the pass and ping `HEALTHCHECKS_RESTORE_PING_URL`, once.
6. **Failure:** it records the step that failed, writes one `backup_restore_failed` notification through `writeNotification`, pings `${HEALTHCHECKS_RESTORE_PING_URL}/fail` and exits non-zero. It never sends the success ping on failure.

## Backend (`@semprec/data`)
- **`observability/restoreTestResult.ts`:** sets the `backup:restoreTest` observability check to `ok` or `alerting`. On failure it writes one `backup_restore_failed` notification per run. The run id is the dedupe key, so recording the same run twice doesn't notify twice. If no user exists yet, nothing is notified and the CLI logs that.
- **`observability/restoreTestResultArgs.ts`:** checks the CLI arguments against a closed list of step names and a run-id pattern.
- **`observability/restoreTestResultCli.ts`:** the entry point the script calls. It connects as `semprec_side` (`SEMPREC_SIDE_DATABASE_URL`), with a 60 s `timeout`.
- The `backup_restore_failed` title is added in English and Czech.

## Tests
- **`deploy/systemd/scripts/semprec-restore-test.test.sh`:** a mocked behavior test. It checks that a valid fixture passes and pings once. Each injected failure (snapshot restore, PostgreSQL start, `pg_restore`, items count, freshness, doc snapshot count, empty state, MinIO start, unreadable blob, wrong blob, cleanup, missing config) must produce exactly one failure record for that step, one `/fail` ping, no success ping and a non-zero exit. Every case must leave nothing behind. It also checks that no secret appears on a command line and that nothing touches the production containers or volumes.
- **`restoreTestResult.test.ts` (integration):** covers the notification contents, no duplicate for the same run, a new notification for each new failed run, a passing run resetting the check to `ok`, and the case with no user.
- **`restoreTestResultArgs.unit.test.ts`:** covers argument parsing.

## Decisions to review
- **`observability_checks` holds the failure:** the notification needs a real source row, so the failure is stored there. As a result, a failed restore shows in the system health report until a later run passes. That meant the passing path also has to write to the database, which the issue didn't ask for.
- **New variables:** `MINIO_BLOB_BUCKET` and `HEALTHCHECKS_RESTORE_PING_URL` are added to `.env.example`. Nothing in the repo defined a MinIO bucket before.
- **No objects is a pass:** the app still stores blobs on local disk, not in MinIO. If the `blobs` table has no hashed rows, the blob check logs that and passes.
- **Freshness is measured from when the test runs**, not from when the snapshot was taken.
- **New ADR:** `docs/adr/2026-09-23-host-scripts-record-results-through-a-data-layer-cli.md` records the pattern of host scripts calling a data-layer CLI instead of writing raw SQL or adding an HTTP route.
- **Docs:** `deploy/README.md` and `docs/operations/database-roles.md` are updated.

The existing `semprec-backup.test.sh` uses `! rg`, and `rg` isn't installed here, so the "no secrets on the command line" check silently does nothing in that test. That file is outside this issue and I left it unchanged.
