## Summary

This PR adds a guarded release command. It creates the monorepo's only version, a `vMAJOR.MINOR.PATCH` git tag, and only on the current head of protected `main` after the required CI has passed for that exact commit.

```sh
cd backend
pnpm --filter @semprec/release run release-tag v1.2.3 <full-sha-of-main-head>
```

If the tag is refused, the command exits with code 2 and prints the reason; nothing is created. Exit code 1 means an operational failure (git, `gh` or the network).

## What changed

- **`backend/packages/release`** (new package `@semprec/release`)
  - `releaseTag.ts` holds the eligibility rules. It talks to git and GitHub only through a `ReleaseHost` port, so the rules can be unit-tested without a network. It refuses:
    - a malformed tag: leading zeros, a pre-release or build suffix, no `v` prefix;
    - a target that is not a full 40-character SHA;
    - a SHA that is not the current head of `main`, or a `main` that is not protected;
    - a tag name that already exists on the remote;
    - a SHA that already has a release tag;
    - any required job that is missing, still running, failed or cancelled on that SHA.
  - The required jobs are the `ci.yml` jobs that run on a push to `main`: `promotion-source`, `ci`, `unit`, `integration`, `dependency-check`, `e2e`, `pi-agent-contract`. Only check runs created by GitHub Actions count, and for a re-run job only the newest run counts. `review` and `code-review` run only on pull requests, so they are not part of this check.
  - Just before tagging, it reads `main`'s head again. It then tags the SHA itself (never a branch name) and pushes without force, so the remote also refuses a duplicate.
  - `githubReleaseHost.ts` is the `git`/`gh api` adapter:
    - every command has a timeout and an output size cap;
    - GitHub responses are validated with zod;
    - more than 100 check runs on one commit is an error (it fails closed rather than reading only one page);
    - an annotated tag is matched to the commit it points to, not the tag object;
    - if the push fails, the local tag is deleted, without letting a failed delete hide the push error.
  - `cli.ts` is the entry point.
- **No per-package versions:** `noPerPackageVersions.unit.test.ts` checks every `package.json` in the repo and fails on any version other than the `0.0.0` placeholder.
- **ADR** `docs/adr/2026-09-24-monorepo-release-tag-from-guarded-command.md`: a standalone decision that narrows how releases are tagged. It links to the develop/main ADR and leaves that ADR's body unchanged.
- **Docs:** new `docs/operations/releases.md` (how to run the command and the refusal rules). `required-checks.md` now says that renaming a `ci.yml` job also means updating the release command's list of required jobs.

## Acceptance criteria

| Criterion | Where |
|---|---|
| A green `main` SHA can be tagged once | `releaseTag.unit.test.ts`: the happy path, plus refusal of a second tag on a released commit |
| Malformed, duplicate, non-`main` and non-green tags are rejected | table-driven refusal tests for each case, including a `main` head that moves during the check and a re-run that failed |
| No per-package versions | `noPerPackageVersions.unit.test.ts` |
| Eligibility is bound to the exact SHA | the check runs are read for the given SHA, the tag is created on that SHA, and `main`'s head is re-checked just before tagging |

## For the maintainer

`.github/workflows/release.yml` still creates a tag from `backend/package.json`'s version on every push to `main`. The new placeholder-version test keeps that version at `0.0.0`, so the workflow now always skips and never tags. Retiring it, or pointing it at release tags, is a protected-path change and fits the deployment issue that will use these tags. Deploying when a tag is pushed is out of scope here.
