## Delivered behavior

- `backend/packages/data/src/inbox/inboxTickAction.ts`: `createSemprecTickAction` catches an `AiGatewayFailedError` from `computeProposal`. When the reason is `budget_exceeded`, or `context.isFinalAttempt` is `true`, it logs a warning, runs `writeComputeFailure` in a `repeatable_read` transaction and returns without throwing. Any other gateway failure on a non-final attempt is rethrown, so the queue retries the heartbeat job. Every other error propagates unchanged.
- `writeComputeFailure`, placed after `writeTickResult`: it calls `currentSourceFingerprint` first. A deleted source, a lost recognized type or a changed fingerprint writes nothing. It then locks the existing card with `lockUnlockedProposal`, using the snapshot's card or one found in the write transaction; a locked card is skipped. The write sets `status: computeFailed` and `fingerprint: null`, and appends `{ author: "ai", message: "Computing the proposal failed: <reason>." }`. It does not write `proposal`, so an existing proposal stays stored. Without a card it creates one (`kind: inbox`, `sourceInbox` edge). The Journal-day recompute is enqueued after the write, as the other status writes do.
- `currentSourceFingerprint`: the source re-check moved out of `writeTickResult` unchanged, with the same log reasons. Both writes use it.
- `backend/packages/data/src/inbox/proposalHistory.ts` (new): the proposal history kinds, the entry schema and `appendHistoryEntry`, moved without change from `inboxTickAction.ts`. `inboxTickAction.ts` re-exports them, so `proposalActions.ts` and the transcription modules keep their imports.
- Production wiring is unchanged: `actionRegistryComposition.ts` already registers `createSemprecTickAction(pool, computeProposal)`, and `proposalComputation.ts` calls `gateway.complete` without a `catch`, so the typed error reaches the tick.

## Deviations from the Task

- `isFinalAttempt` is compared with `=== true`, as the Task states it. The `ActionContext` doc comment says `undefined` (a direct caller) is treated as final, and `coreAgentRunAction` tests `=== false`. The queue always passes a boolean (`sweep.ts`), so the difference only reaches a direct caller that omits the flag, where a non-budget gateway failure is rethrown. This needs a reviewer decision if the other reading is wanted.
- The `proposalHistory.ts` move is not in the Task. `inboxTickAction.ts` was at 916 code lines against the `max-lines` cap of 900 (`backend/eslint.config.mjs`, ADR `2026-09-24-choke-point-composed-from-domain-modules`). Trimming the new code alone would not have reached the cap without hurting readability. The move is mechanical and the re-export keeps every import path.

## Notes for dependants

- A failed computation is recorded only while the source still matches the snapshot. If the item changed during the call, nothing is written, because the edit has queued a newer tick.
- A `computeFailed` card has `fingerprint: null`, which never matches a current fingerprint. The next tick for that item therefore computes again, even without a source change. The recompute route (#1955) can rely on this.
- The failure write never touches `proposal`, so it does not touch `aiProposal` either (see the gh-1451 backfill note). The success paths (`writeTickResult`, `reviseProposal`, `writeNeedsClarification`) are unchanged here.
- The failure message is built from the closed `AiGatewayFailureReason` union, so provider text never reaches the card.
- Notifications for failures and the Inbox list display (#1807, #1489) are not part of this change.
