# gh-1411 — Declare link rules in module manifests and validate them

Repository-Issue: gh-1411

This completion is proposed on an isolated implementation branch; it becomes canonical only after reviewed integration. No PR has been published by this worker.

## Delivered behavior

- `ModuleManifest` has an optional `linkRules` array of `ModuleLinkRuleDescriptor` (`{ key, source: { databaseKey, propertyKey }, target: { databaseKey, propertyKey }, via: { databaseKey, relationKey } }`). The zod schema is strict at every level and all keys are non-empty strings. `ModuleLinkRuleDescriptor`, `ModuleLinkRuleEndpoint` and `ModuleLinkRuleProjection` are exported from `@semprec/module-registry`. A manifest without `linkRules` loads exactly as before.
- `ModuleRegistry.loadModule` claims each rule `key` through the existing duplicate checks (label `link rule key`), so a duplicate across modules or inside one manifest fails the load.
- `ModuleRegistry.validateLinkRules()` runs over every loaded module (activation is ignored) and throws on an unknown `databaseKey` (source, target or via; the message names the rule), a `via.databaseKey` that is neither the source's nor the target's database, and a cycle in the graph of `databaseKey.propertyKey` nodes with one edge per rule (the message lists the rules on the cycle, a self-loop included).
- `ModuleRegistry.getLinkRules()` returns the rules of active modules with their `moduleId`, in load order then manifest order.
- `loadFullModuleRegistry()` calls `validateLinkRules()` after the last `loadModule`.
- `findInvalidLinkRuleReferences(client, registry)` (exported from `@semprec/data`) checks the rules of active modules against the tenant schema and returns `{ ruleKey, moduleId, reason, property }` entries. Reasons: `missingSourceProperty`, `missingTargetProperty`, `missingViaProperty`, `viaNotRelation`, `viaDoesNotLeadToOtherDatabase`. "Leads to the other database" is read from the via property's `config.targetDatabaseId`, the same source of truth as `loadRelationEdgeContext`.
- `createDriftCheckAction` inserts one `link_rule_schema_drift` row (`LINK_RULE_SCHEMA_DRIFT_FINDING_KIND`) into `manifest_drift_findings` per run when there are findings; payload is `{ projectItemId, invalidLinkRules }`. It runs only when the action was created with a `moduleRegistry` option, like the other registry-aware checks.
- No real rule is declared and no stored data changes.

## Notes for dependants

- #1593 reads rules with `registry.getLinkRules()`; no rule extension fields exist yet, so add them to the strict schema in `manifest.ts` together with the code that uses them.
- A module adding a rule must declare the relation property it names in its seed; the guard test in `linkRuleDrift.test.ts` fails otherwise. Rules naming a database of another module are fine because validation runs after all modules are loaded.
- `via` and the source property are not required to be related to the target by type; only existence, relation-ness and relation target are checked.
