**Contracts for adapter implementers (CalDAV/tsdav, Google, Graph).**

- **Interface** (`CalendarSyncAdapter`):
  - `listCalendars(signal)` returns `RemoteCalendar[]`: `{ remoteId, url, name, color (#RRGGBB|null), readOnly, ctag }`.
  - `fetchChanges(calendar, cursor | null, { window, signal })` returns `{ full, upserts: RemoteEvent[], deletions: remoteId[], nextSyncState: { syncToken, ctag } }`.
  - `putEvent(calendar, { ref | null, fields }, signal)` returns `RemoteEventRef`.
  - `deleteEvent(calendar, ref, signal)`.
  - Every call must honour `signal`. It is one 5-minute deadline for the whole pass.
- **Cursors.**
  - A `null` cursor (a new calendar, or a stored `sync_token` of NULL) asks for a full fetch of `window`.
  - `window` is `{ start, end }`, `YYYY-MM-DD` in the tenant zone, from one year back to two years ahead. It is passed on every fetch.
  - With `full: true`, any stored Event of the window that is missing from `upserts` is trashed. A series (a stored `recurrenceRule`) counts as inside the window, so list a series whenever it has an occurrence in the window. Events outside the window stay.
  - When an incremental token has expired (CalDAV 403/410, Google 410), return a full fetch.
  - `nextSyncState` is stored only when the apply commits.
- **Payload** (`RemoteEvent`):
  - `{ remoteId, href, etag, seriesRemoteId, fields, organizer, attendees }`.
  - `fields` are the Events keys: `name, date, endDate, timeFrom, timeTo, timeZone, recurrenceRule (no "RRULE:"), exceptionDates, recurrenceId, place, description, url, alertMinutes`.
  - Times are wall clock in `timeZone` (an IANA zone, or null for the tenant zone).
  - An all-day Event has `timeFrom`/`timeTo` null and `endDate` set to its last day.
  - `exceptionDates` and `recurrenceId` are local starts (`YYYY-MM-DD` or `YYYY-MM-DDTHH:MM`).
  - An override is its own `RemoteEvent` with `seriesRemoteId` (the master's remoteId in the same calendar) and `fields.recurrenceId`. The apply writes it with `seriesId` set to the master's item. An override whose master is not stored is skipped.
  - `organizer`/`attendees` are `{ email, name, role, status }`, raw provider strings, and are only stored in `base_snapshot` (for invitations).
  - Output is validated strictly by zod with bounds: 200 calendars, 25,000 upserts or deletions per calendar, ids up to 2048 characters, texts up to 100,000, 500 participants. Duplicate ids are refused. Any violation is `CalendarSyncProviderError("invalidResponse")`.
  - Normalise colours to `#RRGGBB` or null.
- **`base_snapshot`** = `{ fields, seriesRemoteId, organizer, attendees }` of the last applied fetch.
  - Equal to the new fetch: nothing is written (only `href`/`etag` when they differ).
  - Different: only the fields that differ from the snapshot's fields are patched, so a local edit of any other field stays.
  - The write-back issue should read the base from here for its three-way merge.
- **Errors to statuses** (`failureRecordOf` in the job):
  - `CalendarSyncReauthorizationRequiredError` (401) or `MailReauthorizationRequiredError` (the shared OAuth refresh), and also no stored credential: `needsReauthorization`, code `reauthorizationRequired`. Critical problem, not retried.
  - `CalendarSyncConsentRequiredError` (missing scope / 403 on the calendar API): `needsConsent`, code `consentRequired`. Critical, not retried.
  - `CalendarSyncProviderError(code)`, where `code` is one of `rateLimited | providerUnavailable | invalidResponse | timeout`: `error` with that code. Warning, rethrown (the queue retries, 3 attempts).
  - The pass deadline expired: `error`/`timeout`. Anything else: `error`/`unexpected`.
  - Logs carry only ids, the error name and the code. Adapters must not put secrets in error names.
- **Registering an adapter:** add a factory `(account: CalendarSyncAccount) => CalendarSyncAdapter` to `CALENDAR_SYNC_ADAPTERS` in `calendar/sync/adapters/index.ts`, keyed by sync mode (`imap`, `gmail_api`, `graph_api`).
  - `CalendarSyncAccount` is `{ accountItemId, provider, syncMode, primaryAddress, credential }`. `credential` is the decrypted stored secret: an IMAP password, or the OAuth credential JSON the mail adapters use.
  - The factory holds no DB client. Read whatever else is needed (server URL) without a transaction, or extend `CalendarSyncAccount`.
  - Tests pass a registry through `handleCalendarAccountSyncTask(pool, payload, { adapters })`. `testSupport/fakeCalendarSyncAdapter.ts` (`FakeCalendarProvider`, `remoteFields`) is an in-memory provider whose sync token is a change counter.
- **Apply result, the notification hook:** `handleCalendarAccountSyncTask` returns `applyCalendarSync`'s `CalendarSyncApplyResult`:
  - `applied`, with `{ initialSync, added, changed, cancelled: { eventItemId, calendarItemId, remoteId }[], skippedEvents }`. `initialSync` is true for the account's first completed pass, whose Events are not news. `cancelled` lists the Events trashed because the provider deleted them.
  - `skipped`, `superseded`, or `null` (nothing ran).
  - The notification issue should write its rows inside `applyCalendarSync`'s transaction, next to `recordCalendarSyncSuccess`, from these lists.
- **Manual sync route:** `POST /api/accounts/:id/calendars/sync`, session auth, no body.
  - 202 `{ id, queued }`. `queued` is false within 60 s of the last recorded request; the debounce is a conditional upsert of `manual_sync_requested_at` under the account row's `FOR SHARE`.
  - 404 `not_found` for an unknown, malformed, foreign or trashed id.
  - 409 `calendars_disabled` (`details.accountId`) with Calendars off.
- **Lifecycle:**
  - Switched on, or created on: a pass is queued.
  - Switched off, or account removed: the state row and every `calendar_remote_state` row of the account are deleted, the problem is resolved `sourceDeleted`, and `calendarAccountCleanup` is queued.
  - The cleanup trashes, in chunks of 200 under the guard, the live Events of the account's untracked calendars (account calendars without a `calendar_remote_state` row), deletes their `event_remote_state`, then trashes each calendar.
  - A calendar the provider stops listing is untracked the same way and cleaned up.
  - Switching on again creates new calendars.
- **Guard and lock order:**
  - Advisory lock `calendar-account-sync:v1:<tenant>:<account>`.
  - Apply: guard (≤ 5 s, else the pass is skipped) → state row → calendar rows → Event rows.
  - Switch: mailbox guard (Mail) → calendar guard (≤ 15 s, else 409 `calendar_sync_busy`) → mail state row (Mail) → Mailboxes item. Removal takes the same order.
  - The failure record also takes the guard (≤ 5 s), and writes only while Calendars is on.
- Writes:
  - Calendars are written with `{ writer: CALENDAR_SYNC_WRITER, allowedSystemKeys: [kind, remoteName, remoteColor, readOnly], systemOwnerProcess: "calendar" }`.
  - Events are written with `{ writer: CALENDAR_SYNC_WRITER, allowedSystemKeys: [timeZone, recurrenceRule, exceptionDates, recurrenceId, seriesId] }` and no owner process. A master never carries a `seriesId` key.

**Deviations and spec seams.**
- Calendar removal (Calendars off, account removed, calendar no longer listed) is done by the cleanup job rather than in the apply or switch transaction. The calendars stay visible until the job's first chunks commit, which is seconds after the commit in a running worker.
- "Removes": the account's calendars and Events go to the Trash, as Mail off does with mail, and are purged by the normal retention. Their remote state rows are deleted.
- The sweep's "due" means: Calendars on and (no state row, status not `ok`, or the last success at least 4 minutes ago). Accounts in `needsReauthorization`/`needsConsent` are retried every sweep too: one refused request per 5 minutes. Nothing else would notice a reauthorization.
- `needsConsent` from scopes is a precheck (no network, nothing written). A stored `needsConsent` comes only from an adapter's consent error on an account whose recorded scopes look sufficient.
- A refused credential or consent is not rethrown (no queue retries); only `error` is. Mail rethrows its reauthorization failure.
- No `mail_sync_error`-style notification row is written for calendar failures; notifications are out of scope.
- "A second pass writes nothing" holds for items and `event_remote_state`. `calendar_remote_state` (cursor, `last_synced_at`) and `calendar_account_sync_state` (`last_successful_sync_at`) are rewritten on every applied pass.
- An Event that the user trashed locally in a writable account calendar is skipped by the pass; it is left to write-back.
- An Event that an Event rule refuses (`ValidationError`, e.g. a bad `url`) is skipped in a savepoint and logged. It keeps no remote state, so an incremental pass does not offer it again until it changes.
- Beyond Touches: `db/tenantAdvisoryGuard.ts`, `mail/mailboxSyncGuard.ts` (refactor), `mail/mailboxRemoval.ts`, `mail/mailboxRouteHandlers.ts`, `mail/oauthServiceScopes.ts`, `mail/mailAccountSyncStateStore.ts`, `domainWriteHooks.ts`, the `semp/*` files, `testSupport/fakeCalendarSyncAdapter.ts`, the two other architecture docs, and the test expectations above.
