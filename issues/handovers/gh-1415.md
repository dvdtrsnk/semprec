# Handover for gh-1415

The choke point now knows who made a write. `WriterIdentity` (`user`, `agent` or `system`, plus optional `agentRunId`, `agentProjectItemId` and `onBehalfOfUserId`) is exported from `@semprec/data` together with `SYSTEM_WRITER`. It is threaded through item and relation writes and into every hook context. No decision uses it yet. The work is committed locally; I did not push or open a PR.

Typecheck (data, application, semprec-api), eslint, prettier and dependency-cruiser pass. **I could not run any integration test (this includes the fix round).** The embedded Postgres failed to start for the whole session (`shmget` / "No space left on device": the host's SysV shared-memory IDs were exhausted by other processes), so `writerKind.test.ts` (data), `writerKind.test.ts` and `approvedExecutorWriter.test.ts` (application) and the two new cases in `itemsHandler.test.ts` are written and typechecked but unexecuted. Relay's verify has to run them first.

- **Data layer:**
  - `chokePoint/writerKind.ts` is new.
  - `ItemCreateHookContext`, `ItemUpdateHookContext` and `RelationEdgeWriteHookContext` carry a required `writer` next to `humanWriterUserId`.
  - `createItemWithClient` / `updateItemWithClient` take `options.writer`, defaulting to `SYSTEM_WRITER`.
  - `createRelationWithClient`, `updateRelationWithClient`, `deleteRelationWithClient` and `assertRelationCreatableWithClient` take a trailing `writer` after the unchanged positional `context`.
  - `itemDeleteWithClient` takes `options.writer`, and `restoreItemWithClient` takes a trailing writer.
  - The facade methods `createItem`, `updateItem`, `createRelation`, `updateRelation`, `deleteRelation`, `softDeleteItem` and `restoreItem` accept the writer last.
- **Derivation:** `writerIdentityOf(actor)` in `genericApplicationService.ts` is the single derivation (both run ids give an agent run; `restSession` gives `user`; anything else gives an agent without run ids). Every agent value carries `onBehalfOfUserId`. It is used by `createItem`, `patchItem`, `deleteItem`, `restoreItem`, `putRelation` and `deleteRelation`. Nothing reads a writer from a body, so the strict input schemas still return 400.
- **Executor and Inbox:** the approved-operation executor in `genericOperationGateway.ts` passes `agent` with the request's `agentRunId`, the payload's `agentProjectItemId` and the actor's user as `onBehalfOfUserId`. `confirmProposalWithClient` passes `user` to its create, relation and proposal-update writes. Internal callers were not edited and stay `system`.
- **Test support:** `@semprec/data/testSupport` now re-exports the hook registration functions and context types so application and API tests can record the writer a request reaches the hooks with. Two existing hook-context literals (`mcpServerWriteHook.test.ts`, `hooks.unit.test.ts`) gained `writer: SYSTEM_WRITER` because the field is required.

**Relation delete and the edge hook:** the acceptance criteria say `relation.delete` by an agent reaches an edge hook with `agent` and the run id. `RelationEdgeWriteHook`s validate edge metadata (Transcripts speakers) and would reject every speaker-edge removal, so delete does not run them. Instead `hooks.ts` has a separate delete seam, `registerRelationEdgeDeleteHook` / `RelationEdgeDeleteHookContext` (`client`, `edgeContext`, `callerItemId`, `targetItemId`, `writer`), run by `deleteRelationWithClient` before the edge is removed. No production hook is registered on it yet; #1530 builds on it. The Transcripts hook is unchanged. Tests observe the writer through this seam, including for an approved `relation.delete` executed by `approvalExecute`.

Notes for dependants:

- #1530 can register on `registerRelationEdgeDeleteHook`; #1601 can read the writer already passed into `itemDeleteWithClient` and `restoreItemWithClient`, which were not changed beyond accepting it.
- An `agent` without `agentRunId` is an MCP client on a human session. A consumer that needs a run must check `agentRunId` / `agentProjectItemId`.
