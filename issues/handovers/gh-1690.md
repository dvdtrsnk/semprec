## What was delivered

- `DELETE /api/mail/mailboxes/:id` (mail module custom route `mailboxRemoval`, justification `transactional-semantics`), authenticated and tenant-scoped. Success answers 200 with `{ id }`. An unknown id, a malformed id, another tenant's mailbox, a tenant without a Mailboxes database and a mailbox already in the trash answer the same 404 `not_found` ("Mailbox not found") and write nothing.
- `removeMailbox` in `backend/packages/data/src/mail/mailboxRemoval.ts` runs one READ COMMITTED transaction in the caller's tenant scope. In this order it takes the mailbox's sync guard, locks the `mail_account_sync_state` row and then the Mailboxes item `FOR UPDATE`, sets `syncStatus` to `needsReauthorization` through `updateItemWithClient` (`allowedSystemKeys: ["syncStatus"]`), trashes the item through the choke point's cascade (`itemDeleteWithClient`) as the system writer, and deletes the credential (`deleteCredential`), the account sync state row, the folder sync state rows of every Folders item related to the mailbox through `Folders.mailbox` (trashed folders included) and the server settings row, each through the store that owns the table. Any failure rolls all of it back.
- Each of the four deletes may match no row: a mailbox that never connected has none of them. That is not a failure.
- Review fix `dc15efaf`: the removal and the write transaction of a sync pass of the same mailbox both take a per-mailbox, transaction-scoped advisory guard before any row lock (`lockMailboxSync` in the new `backend/packages/data/src/mail/mailboxSyncGuard.ts`, key `mailbox-sync:v1:<tenant>:<mailbox>`). A removal that arrives during a pass waits for it and holds no row lock while it waits; a second removal of the same mailbox waits and then answers 404.
- Review fix `c8eb45e5`: under the guard a sync pass reads the Mailboxes item and the `mail_account_sync_state` row again (`enterSyncPass` in `backend/packages/data/src/mail/mailSyncJob.ts`, all three sync modes). When the item is in the trash or gone, or the row is gone, the pass makes no reconcile call and writes nothing, so a pass that read the mailbox before the removal committed does not create the deleted rows again.
- ADR `docs/adr/2026-11-10-mailbox-removal-is-one-transaction-that-also-writes-sync-status.md` records the single transaction, the sync guard, the re-read, the row lock order, the removal as second writer of `Mailboxes.syncStatus` and what stays outside the guard.

Follow-ups, none of them fixed in this chain:

- Recheck, low: a removal can also wait for a sync pass of another mailbox of the tenant. A pass takes the mailbox's sync guard first and the tenant's mail-thread mutation guard second, so the pass of mailbox B can hold B's guard while it waits for a long pass of mailbox A, and a removal of B waits for it. Nothing is written and the request can be repeated. The ADR's Consequences do not state this case. The ADR is accepted and merged now, so its body is frozen; a correction needs a new ADR.
- Recheck, low: `lockMailboxSync` checks only the tenant scope. It does not check that its client is inside a READ COMMITTED transaction, as `lockMailThreadMutation` does. Both callers run inside `withTransaction` at its default level, so there is no defect today.
- No owning issue: the live-sync root's discovery (`mail/mailLiveSyncRoot.ts`) calls `ensureMailAccountSyncState` for every live mailbox it lists, without the guard. A discovery that listed the mailbox just before the removal committed can insert a `mail_account_sync_state` row after it, and a restored mailbox gets a row again at the next discovery. gh-2030 does not cover it. It needs a follow-up issue.
- No owning issue: a removal that waits for a sync pass longer than the pool's 60-second statement timeout is cancelled with nothing written and the route answers 500. A retryable answer would be a new API decision.
- gh-2031: the generic `DELETE /api/items/:id` can still trash a Mailboxes item without this cleanup. Such a mailbox answers 404 on this route and keeps its credential until it is restored and removed, or purged (gh-1691).
- gh-2030: the hosted lifecycle, the Gmail watch or Graph subscription and the provider token of a removed mailbox are not stopped, cancelled or revoked.
