## Summary

Implements issue #108: `ModuleManifest` type and `ModuleRegistry` in `backend/packages/module-registry`.

- **`manifest.ts`** — `ModuleManifest` interface and a zod schema covering `id`, `version`, `name`, `removable`, `systemProject`, `databases`, `capabilities`, `agentTools`, plus optional `viewTypes`, `heartbeatActions`, `heartbeatRuleKinds`, `taskNames`, `workers`, `migrations`. Task descriptors are exactly `{ name, payloadSchemaExport, handlerExport }`.
- **`registry.ts`** — `ModuleRegistry.loadModule(path)` uses an explicit known-path dynamic `import`, validates the manifest's structural shape, verifies every named `handlerExport`/`payloadSchemaExport` actually exists on the imported module, and rejects duplicate module ids/names or duplicate database keys/agent-tool/task/worker names across modules — all failing synchronously so a bad module blocks startup loudly. Activation is resolved fresh on every call via an injected `ActiveModuleIdsSource` (not cached at load time), so deactivating a module drops it from every projection immediately. Only narrow, per-aspect projection methods are exposed (databases, capabilities, agent tools, view types, heartbeat actions/rule kinds, tasks, workers, migrations, system-project ids) — no method returns the raw manifest, and an agent tool whose capability isn't granted is omitted entirely rather than returned as denied.
- Added fixtures and a 9-test suite covering valid loads, invalid shape, missing exports, duplicate ids/keys, activation filtering, capability filtering, and dynamic re-evaluation.
