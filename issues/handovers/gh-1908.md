## What was delivered

- `POST /api/agent-runs/:id/retry` in `agentRunHandler.ts`. Eligibility order: `409 not_retryable` (the run was not triggered by a heartbeat, has no occurrence, no heartbeat id, is not in a retryable display status, already has a successor, or the occurrence was cancelled), then `409 retry_pending` while the occurrence is queued or running, then the refusals of the manual trigger (`heartbeat_disabled`, `heartbeat_event_triggered`). It checks the run's own actor like the sibling GET routes, so another actor's run, another tenant's run and an unknown id all answer 404. Eligibility and the enqueue run in one transaction after the heartbeat row lock. It answers `202 { jobKey }`.
- The job is queued through `enqueueManualHeartbeatFire` (new optional `jobKey` and `maxAttempts`, new trigger member `{ retryOfRunId }`) under the key `heartbeat-fire:retry:<runId>` with `maxAttempts` 1 on the agent-run lane; `refuseWhileActive` is false for the retry.
- `scheduler/sweep.ts` accepts `retryOfRunId` as a fifth payload discriminator and passes `ActionContext.retryOfRunId`; `coreAgentRunAction` (`scheduler/actions.ts`) creates the next attempt with `createChainedAgentRun` (attempt = retried attempt + 1, same heartbeat, project, task and occurrence, actor inherited), and starts no agent when the retried run is gone or already has a successor.
- `GET /api/agent-runs/:id` carries `retriedByRunId` (null before the retry run exists). `NotRetryableError` and `RetryPendingError` (409) in `errors.ts`; `not_retryable` and `retry_pending` in `ITEM_ERROR_CODES` and `ITEM_ERROR_STATUS_BY_CODE`.
- `retryHeartbeatFireJobKey` and `getHeartbeatOccurrenceStatus` in `scheduler/schedulerStore.ts`.
