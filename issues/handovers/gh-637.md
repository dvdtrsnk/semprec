## Summary

Path ids that aren't UUIDs used to reach a `uuid` column. Postgres then raised `22P02`, which surfaced as a 500. Now they get `400 validation_failed` with `details: { field: "<param name>" }` and the message `'<param name>' must be a UUID string`. This is the same response the transcription routes already give. The route regexes are unchanged: validation happens after the match, so the error still names the field. A well-formed but unknown id behaves as before (404, or `revoked: false`).

### Changes
- **`adapter/requestValidation.ts`**: new `assertUuid(value, name)`, which accepts either letter case and matches the whole string, and `requireUuidParam(params, name)`.
- **Adapter route families** switched from `requireStringParam` to `requireUuidParam`:
  - `databasesHandler.ts`: `id`
  - `propertiesHandler.ts`: `id`
  - `viewsHandler.ts`: `id` and `itemId`
  - `itemsHandler.ts`: `id` and `targetItemId`. `propertyKey` stays a plain string check.
- **Bespoke handlers**: each captured group now goes through `assertUuid` right after the regex match:
  - `authHandler.ts` (revoke), `agentRunHandler.ts`, `approvalRequestsHandler.ts`, `notificationsHandler.ts`, `blobsHandler.ts`: field `id`
  - `mcpAgentPageHandler.ts`: the project id as `id`; the registration id as `mcpToolRegistrationId` in both routes, and on the grants route only when that group is present

  Each handler's existing `catch` already maps a `ValidationError` to 400 in its own top-level shape, so no `catch` block changed.
- **`push/pushRouteHandlers.ts`**: the revoke route checks `ctx.params.id` with a module-level `z.string().uuid()` schema, the same way `transcriptionRouteHandlers.ts` does. The local `requireParam` helper had no other caller left, so I removed it.

### Tests
- Unit tests for `assertUuid`: lowercase and uppercase UUIDs pass; `"foo"`, a UUID with a trailing character, and `""` are rejected, each naming the field.
- One integration case per route family with the literal id `foo`, checking status 400, `validation_failed` and the field name:
  - items: `GET /api/items/foo`, and the relation route, which reports `targetItemId`
  - views: `PUT /api/views/<id>/items/foo` reports `itemId`
  - databases, properties, session revoke, agent runs, approval requests, blobs, push-subscription revoke
  - MCP grants and registrations: all three extractions
- New `notificationsHandler.test.ts`, which also checks that a valid but unknown UUID still returns 404.
