# Handover for gh-1700

Add the blood-pressure and prevention health-record tags for new and existing tenants. Candidate commit `84ff68a1cc96a267c9b1ed34bb4bae067155a752` (one segment, one commit) landed on `feature/backend-parallel` with merge `22a9fd5bf2020dbf7c193fdb40e0b8a6c86244ba` (chain `p0-03-misc`). The acceptance receipt is `issues/batches/backend/acceptance/sources/gh-1700.md`.

## What was delivered

- The seed (`seedTenDatabasesInTransaction` in `seedTenDatabases.ts`) declares six options for the Health records `tags` property: the four existing keys `bloodTests`, `medication`, `epilepsy`, `dentalHygiene`, followed by the new keys `bloodPressure` and `prevention`. A tenant seeded from this commit on stores all six, in that order, as `{ key }` objects.
- The seed i18n catalogs carry the labels of the two new options: `property.healthRecords.tags.option.bloodPressure` is "Krevní tlak" in `cs.json` and "Blood pressure" in `en.json`; `property.healthRecords.tags.option.prevention` is "Prevence" and "Prevention". `GET /api/schema` resolves them like every other option label and returns `{ key, label }` in the user's locale.
- The per-tenant cutover `runHealthRecordTagsCutoverMigration` brings the two options to tenants seeded earlier. In one transaction it resolves the tenant's Health records database by module id and returns when there is none, takes `LOCK TABLE properties IN EXCLUSIVE MODE`, reads the `tags` property of that database and returns when there is none, parses the row with zod, and appends `{ key }` for each of the two keys that is not stored yet, after the stored option objects. It runs `UPDATE properties SET config = jsonb_set(config, '{options}', ...) WHERE id = $1` with `requireAffectedRows` only when at least one key was missing, so a second run writes nothing.
- The cutover is registered in `runTenantCutoverMigrations`, which the deploy CLI `runMigrationsCli.ts` and the integration tier's `globalSetup.ts` call on a `semprec_data` role pool for every maintained tenant, each in its own scope.

## Contracts dependents build on

- Option keys of the Health records `tags` property (`multi_select`, owner `user`, database of module `healthRecords`): `bloodTests`, `medication`, `epilepsy`, `dentalHygiene`, `bloodPressure`, `prevention`. The stored shape is `properties.config = { options: [{ key }, ...] }`. The order carries no meaning; the issue decides only that the two new options are appended.
- After the cutover an older tenant's catalog holds its stored option objects unchanged and in their stored order, followed by the missing new keys in the order `bloodPressure`, `prevention`. Extra fields on a stored option object (for example a color) and other keys of `config` are kept. Code that reads the catalog must not assume that an upgraded tenant's order equals a fresh seed's order when the tenant's stored catalog differed from the original four.
- Catalog keys: `property.healthRecords.tags.option.bloodPressure` and `property.healthRecords.tags.option.prevention` in `backend/packages/data/src/seed/i18n/cs.json` and `en.json`.
- Export: `runHealthRecordTagsCutoverMigration(pool: Pool): Promise<void>` from `backend/packages/data/src/seed/healthRecordTagsCutoverMigration.ts`. It is not re-exported from `backend/packages/data/src/index.ts`; its only production caller is `runTenantCutoverMigrations`. It must be called inside a tenant scope on a pool that row-level security applies to.
- Registry order in `backend/packages/data/src/db/tenantCutoverMigrations.ts`: the entry stands directly after `runSelectOptionOrderCutoverMigration` (gh-1578) and directly before `runSelectOptionColorsCutoverMigration`. It is after `runTranscriptionTriggerEventsCutoverMigration`, the entry of the declared blocker gh-1698. Both neighbours list only the `status` property of Health records, not `tags`, so the position has no effect at this commit. The rules reviewer notes that the colors cutover colors only options that already exist, so when gh-1705 adds colors for these tags its step must stay after this one.
- Failure contract: a stored `tags` config that is not an object, or whose `options` is not an array of objects with a string `key`, makes the cutover throw a `ZodError` and roll back. `forEachMaintainedTenant` then reports that tenant in the runner's `AggregateError` and continues with the other tenants.
- The cutover takes an `EXCLUSIVE` table lock on `properties` for the length of its transaction, once per tenant per deploy. Plain reads are not blocked; writes to `properties` and row-locking reads of it wait for it.
- No route, no table, no SQL migration, no generic operation, no job name and no export from the package index was added or changed. No ADR was added.

## Deviations from the specification and spec seams

1. `Touches` places the new tests in `backend/packages/data/src/__tests__`. `GET /api/schema` is served by `createSchemaRequestListener` in `services/semprec-api`, which a data-package test cannot start, so the HTTP test that Task step 4 and the first criterion name was added to `backend/services/semprec-api/src/__tests__/schemaHandler.test.ts`. No production code outside `Touches` changed.
2. The Task does not say what happens when the Health records database exists but has no `tags` property. The cutover does nothing in that case, as `seed/peopleRelationshipOptionsCutoverMigration.ts` does, and a test covers it. The case has no production trigger, because the schema-locked database rejects deleting the property.
3. No SQL migration. The task header's "adds a migration" is the application-code per-tenant cutover the Task specifies, so no ordinal was taken.
4. The Task names `transcriptsCatalogCutoverMigration.ts` as the pattern. The code follows `seed/peopleRelationshipOptionsCutoverMigration.ts`, which has the same shape (table lock, zod parse, `jsonb_set` update, `requireAffectedRows`). The rules reviewer found it an existing pattern covered by `docs/adr/2026-09-10-app-code-post-migration-steps.md` and `docs/adr/2026-10-08-deploy-time-tenant-work-runs-as-the-runtime-role.md`; no ADR was added.
5. Tests beyond the list in Task step 4: one per branch the diff adds (no `tags` property, no `options` array, malformed catalog), a two-tenant isolation test and a real-concurrency test of the table lock.
6. Test seams the worker declared: an older catalog cannot be produced through a production write, because Health records is schema-locked. The tests therefore write the old `config`, delete the `tags` property and hold an open catalog write with raw SQL, each filtered by tenant and checked for its row count, each with a reason comment. In the cutover test file these writes use the admin pool; in the schema HTTP test the revert runs on the runtime-role pool inside the tenant's scope.
