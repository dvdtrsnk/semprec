# gh-1492 implementation handover

Implementation base: `883d84fb1216972e0506d4dbdddb9ac99173a883`.

## What changed

- `proposalComputation.ts` (semprec-api): the response schema and zod validation accept `operations` (`op` create|update|link, `database` module id, `itemId`, `alias`, `properties`, `relations` whose targets are item ids or `{ alias }`). For a `database` entity kind the request now also carries a "Writable target catalog (JSON)": per writable system database its module id, name, plain-property catalog and relation property keys. The instructions explain when to use several operations, aliases, ids only from the context, and the limit of 6.
- After parsing, the first 6 operations are kept, then operations are dropped that cannot become a step (create without a catalog database, update or link without `itemId`). More than one remaining operation is returned as `operations`; one remaining create into the type's target database is returned as the ordinary `properties`.
- `inbox/proposalOperations.ts` (data, new): `MAX_PROPOSAL_OPERATIONS`, `listWritableProposalTargets(client)` (system databases except the Inbox ones and processingProposals), `buildProposalSteps`. Exported from `index.ts` (`publicSurface.test.ts` updated). Kept out of `inboxTickAction.ts` because of the max-lines lint rule.
- `inboxTickAction.ts`: `ProposalComputationInput.targetModuleId`, `ProposalComputationResult.operations`; `buildProposalEnvelope` builds the multi-step envelope for more than one operation (refs are the alias or `op<n>`, primary is the first create into the target database, else the first operation, which validation then rejects as not mirroring the top level). The single-write path is unchanged.

## Notes for dependants

- The "link" of the example is the relation on the person step pointing at the company's alias; a `link` operation needs an existing `itemId` (#1479).
- `proposalContext.ts` (#1987) does not exist yet, so the writable catalog is read in `proposalComputation.ts`, and the model has no existing item ids until #1987 supplies them.
- An `update` operation gets only `after`; `before` is not filled (the computation has no current values), so an update of properties fails envelope validation and ends in `needsClarification` until a later issue fills `before`.
