## Summary

Implements issue #83: item and relation mutations are now rejected once their database is archived.

- Introduced one reusable guard in the choke-point data layer (`backend/packages/data/src/chokePoint/chokePoint.ts`) that returns a canonical `403 database_archived` instead of the previous generic `400 validation_failed`.
- Applied it to every item mutation (create, property patch, soft delete, restore) and to both sides of relation create/update/delete.
- Item creation carries the one explicit exception the issue calls for: a replay of an idempotency key that already committed a row before archival returns that existing row with no write and no side effects; a new key, or a key reservation whose row is missing, still gets `database_archived`.
- Reads and restoring the database itself remain unaffected, as required.
- Extended `backend/packages/data/src/chokePoint/itemsStore.ts` with a read-only `findIdempotentReplay` helper backing that carve-out.
- Updated/added tests in `backend/packages/data/src/__tests__/chokePoint.test.ts` covering archived create/update, soft-delete/restore, relation mutations from either side, and the idempotent-replay-vs-new-key behavior.
