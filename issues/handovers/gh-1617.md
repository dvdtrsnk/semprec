# gh-1617 — Restore a page to an earlier version

Repository-Issue: gh-1617

## Delivered behavior and production wiring

- Restore (`backend/packages/data/src/docs/docPageRestore.ts`, `restorePageVersionWithClient(client, itemId, at, retentionDays)`). It resolves the live item's `page` document (an unknown or trashed item, another tenant's item, an item without a document and a canvas item all answer 404 `not_found` with `resource: "page"`). It takes the `doc_snapshots` row lock, reads the historical state with `openDocVersionAtWithClient`, and applies the block-level difference through `mutateDocWithClient(…, "user", …)`. The result is one update authored `user`. A restore that changes nothing writes no update.
- Difference, per id in `blocks` (the raw map, so legacy and block-model blocks both work): present now but not then, the block is removed; present then but absent or different now, it is written again from a copy of the historical block (fields, `Y.Text` as its delta, plain JSON, a reset); identical in both, nothing is written. `order` is set to the historical order when it differs (delete plus insert, nothing when equal).
- Refactor in `docs/docHistory.ts`: `openDocVersionAt(pool, …)` now delegates to `openDocVersionAtWithClient(client, …)`, which calls `assertDocVersionReadable(client, …)` (future `at` 400, unknown doc 404, outside the window 410) and then replays. Behavior is unchanged; the existing retention and history suites pass.
- Store method: `createDocStore(pool).restoreVersion(itemId, at)` (`docs/docStore.ts`), in one transaction. Barrel exports in `packages/data/src/index.ts`: `restorePageVersionWithClient`, `computePageRestoreProjection`, type `PageRestoreCheck`.
- Operation `page.restoreVersion` (catalog now 31 names, `operationNames.ts` last entry).
  - Input `{ itemId, at }`, `at` an ISO 8601 datetime with offset (`PageRestoreVersionInputSchema`, strict).
  - Output `{ itemId, at, blockIds }`. `at` is the normalized ISO string; `blockIds` are the page's block ids in document order after the restore (`readPageBlocks`, order array first, then remaining ids sorted). This is my reading of "the new block ids summary".
  - Metadata: `destructive("core.item.write", true)`. Binding, port method `restorePageVersion`, output type `PageRestoreOutput` in `shared/.../rows.ts`.
- Application: `genericApplicationService.restorePageVersion` calls `docStore.restoreVersion`.
- Approval for agent callers (the acceptance criterion "held for approval" needs it; the gateway hard-coded five operations):
  - `application/src/genericOperationGateway.ts`: the destructive set has six members. `page.restoreVersion` is dispatched to `computePageRestoreProjection` (the approval snapshot, `ResourceSnapshotKind` gains `page_restore`) and to `restorePageVersionWithClient` on replay (author `user`).
  - The projection takes the document lock before it reads `lastEditedAt`, so the replay compares against the page as it is when the restore runs. A page edited after the request makes the replay end as `conflict` with nothing restored.
  - Preflight refuses an unknown or non-page item (404), a future `at` (400) and an `at` outside the window (410) before any request row is written.
  - `data/src/mcp/approvalDescription.ts`: template `approval.pageRestore {itemName, databaseKey, databaseName}`. The instant is an argument value, so it is not in the description. English and Czech entries in `web/src/i18n/messages.ts`.
  - The decision and its carve-outs are recorded in `docs/adr/2026-10-29-page-restore-joins-approval-gated-destructive-operations.md` (new file; the accepted ADRs are unchanged).
- REST: `POST /api/items/:id/page/restore` (`services/semprec-api/src/itemsHandler.ts`), body `{ at }`, 200 with the output. Route matrix entry `restore page version` (`routeMatrix.ts`, tenancy `tenant`).
- MCP: `semprec.page.restoreVersion` from the catalog (`tools/list` checked). AgentTool `page.restoreVersion` from the catalog, approval-gated for agents.

## Notes for dependants

- #1615 adds `core.page.read` and `core.page.write`. `page.restoreVersion` deliberately uses `core.item.write` until then (the page-operation ADR assigns `core.page.write`; the new ADR above records the carve-out). A later decision moves it to a new ADR.
- #1844 (grant rules for page operations): `page.restoreVersion` is already approval-gated for agents and reversible; a grant rule for it should not reopen the approval gate.
- #1680 (Semp's changes): a restore is authored `user`, so it never appears in an `ai_agent` listing. Anything that needs to show restores must list `user` updates on the page.
- Title: the root page title lives in `meta.title` only after #1615. This restore touches blocks and the `order` array only, so a title change is not undone by it. Decide that in #1615 or #1844 if titles must be restored too.
- Archived databases: the restore does not refuse an archived database, because the existing page write path (`docStore.putBlock`) does not refuse one either. Follow the same rule for other page operations unless an ADR says otherwise.
- Legacy and block-model documents: the restore copies raw entries, so `sys:children` (legacy) and `order` (block model) both survive a round trip. Its output `blockIds` follows the block-model normalization, which is also what the legacy reader sees.
- The concurrent-client test is a replica applied after the restore, not a true race. The race itself is covered by the lock order, not by a test. A dependant that changes the lock order must re-check the approval replay (approval row, then `agent_run`, then the document lock).
- `openDocVersionAt`'s signature is unchanged; `openDocVersionAtWithClient` and `assertDocVersionReadable` are internal to `packages/data`.
