## What was delivered

`PUT /api/inbox/items/:id/type` (custom route of the Inbox module, transactional-semantics). `changeInboxItemTypeWithClient` (`inbox/inboxTypeChange.ts`) locks the live Inbox item, takes a shared `NOWAIT` lock on the chosen active type and reserves the item's card `NOWAIT`; refuses a confirmed or rejected card with `ProposalLockedError` (409 `proposal_locked`) and a stale `ifVersion` with 409 `version_conflict` carrying the current card; replaces every type edge; writes the card as `computing` with `userOverrides` and `userEditedKeys` kept or cleared against the destination derived from the type, clears `invalidReason` on leaving `invalid` and appends a `typeChosen` history entry; publishes the card change after commit and triggers the update heartbeats of the Inbox. The tick (`readTickSnapshot`) skips the fingerprint gate for a card in status `computing`. An item without a card needs no `ifVersion` and the tick creates the card.

## Entry points and contracts dependents build on

- Route `PUT /api/inbox/items/:id/type`, body `{ typeId, ifVersion? }` (strict); response `{ itemId, typeId, card }` (`card` is null when the item has none). Handler `createChangeInboxItemTypeRouteHandler` (`inbox/inboxRouteHandlers.ts`), manifest custom route entry in `inboxModuleManifest.ts`, route matrix name `change inbox item type` in the new slice `routeMatrix/inboxItems.ts` (`INBOX_ITEMS_ROUTES`), `ROUTE_HANDLER_FILES` mapping and an isolation case in `tenantIsolationRoutes.test.ts`.
- `changeInboxItemTypeWithClient`, `ChangeInboxItemTypeInput`, `ChangeInboxItemTypeResult` (not exported from the data barrel, like the other inbox handlers).
- History entry kind `typeChosen`. A card in status `computing` is recomputed by the tick whatever its fingerprint says; lock order of the route: source, type (shared `NOWAIT`), cards (`NOWAIT`) (ADR `docs/adr/2026-11-14-a-computing-card-is-recomputed-by-the-tick-regardless-of-its-fingerprint.md`, which also states that recording a failure is a separate issue).
- A type whose target database is missing or archived answers 400 on `typeId`, with or without a card.

## Deviations from the specification and spec seams

1. The Task says the card is found with `findExistingProposal` (private to the capped `inboxTickAction.ts`); the function uses `reserveInboxTypeCards`, which finds the same card through the `sourceInbox` edges and locks it `NOWAIT` in the order of ADR 2026-11-09.
2. `ProposalLockedError` and the codes already exist, so `errors.ts` and `errorContract.ts` are unchanged; the route is not exported from the data barrel.
3. The route entry sits in a new slice because no slice fits `/api/inbox/items`.
4. The handler and function tests live in the new `inboxTypeChange.test.ts`, because `inboxRouteHandlers.test.ts` does not register the domain write hooks that the type-lock rules and the tick trigger depend on.
5. Spec gaps decided by the worker: the response body shape; an `ifVersion` for an item without a card is a 400 on `ifVersion`; a busy chosen type or card is a 409; `invalidReason` is cleared when the card leaves `invalid`; a same-type request is not special-cased (edges replaced, card recomputed); `proposal` and `aiProposal` stay as they were until the tick writes them; a page type's destination is assumed to be the previous page destination (the tick re-judges with the real envelope).
6. The explicit `triggerOnItemEventHeartbeats` call is redundant with the gh-1718 edge hook (same job key); a test proves the route's own trigger through the job revision.
