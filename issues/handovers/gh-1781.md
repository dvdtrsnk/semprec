## What was delivered

- `backend/packages/data/src/tasks/taskCompletedInEventHook.ts`: `taskCompletedInEventHook`, an `ItemUpdateHook` on Tasks registered in `domainWriteHooks.ts` after the gh-1780 hooks and the recurrence advance.
  - When a write moves a task into `done` (detected from the `completedAt` the Tasks transform stores with exactly that move) and the task has no `completedInEvent` edge, it creates the edge, as the Tasks process, to the last live dated host event by edge `addedAt` when that event's end is later than now.
  - When a write names `notDone`, `wontDo` or `missed`, it deletes the edge.
  - It writes only the edge, through `createRelationWithClient` / `deleteRelationWithClient`, in the status write's transaction; it changes no property.
- A recurring task gets its next instance in the same transaction as the edge; a repeated `done` writes nothing.

## Contracts dependents build on

- The edge `Tasks.completedInEvent` / `Events.completedTasks` is now written for every route that sets a status, because the hook runs at the choke point. Generic relation writes (PUT and DELETE, both sides) still answer 403 `owner_violation`.
- The rule "completed in the event" is decided once, at the move into done, against the event end at that time; a later extension of the event does not create the edge for a repeated done.
- No export, route, table, job or operation was added (the hook is not exported from the barrel).

## Deviations from the specification and spec seams

1. The hook decides "the write moves the task into done" from the `completedAt` the Tasks transform stores with that move, since the hook context carries no previous status; a repeated done never creates an edge even when the event was later extended.
2. The statuses that remove the edge include `missed` besides `notDone` and `wontDo`, because the Tasks transform turns a `notDone` write that reopens a series occurrence into `missed` (issue #1668).
3. An event without a date is not a host event for the completion, consistent with the gh-1780 visibility rule.
4. No barrel export in `index.ts`: nothing outside the package imports the hook.
5. The 13:30 / 14:30 boundary is tested with a controlled clock at the data layer (`cp.updateItem`) and, after review, also through `PATCH /api/items/:id` with a fake `Date` only; the other HTTP cases use events two days ahead and behind the real clock.
6. The existing test `taskHostEventOccurrenceRoutes.test.ts` case "creates the next instance once when the placed current instance is completed" now also sees the edge and was updated.
7. The worker's commit trailer used the system attribution (Claude Sonnet 5.5) instead of the Fable line.
