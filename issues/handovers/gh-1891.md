## What was delivered

Every visible APNs push now carries `aps.badge`, and a debounced badge-only push keeps the icon badge current when a count or a badge switch changes.

- `computeBadgeForUser(client, userId)` in `notifications/badgeCount.ts` reads the user's preferences and the three counts and returns the sum of the enabled ones (0 when none is enabled). The count read moved from `badgeCountsRoute.ts` into `loadBadgeCounts(client, userId)` in the same new file, so `GET /api/badge-counts` and the badge share one definition; the route behaviour is unchanged. Invitation and Inbox counts are still the constant 0 of gh-1828, so only approvals contribute today.
- `handleNotificationFanoutTask` computes the badge once per job and passes it as `NotificationPushPayload.badge` (optional, so Web Push and old fixtures compile); `sendApnsNotification` sends it as `aps.badge` (0 is sent and clears the badge).
- `sendApnsBadgeUpdate(target, badge)` in `push/apnsAdapter.ts`: alert push type, `apns-priority` 5, `apns-collapse-id` `badge`, payload `{ aps: { badge } }` only, no alert, no sound, no `apns-expiration`. The badge is validated as a non-negative integer before any request.
- Core task `pushBadgeRefresh` (`CORE_TASK_NAMES.PUSH_BADGE_REFRESH`, affinity `api`, tenancy `tenant`), handler `handlePushBadgeRefreshTask` in `push/pushBadgeRefreshJob.ts`, registered in `worker.ts`. It reads the tenant user, the APNs registrations and the badge in one transaction, treats a foreign `userId` as missing, sends to APNs registrations only, revokes a registration on a permanent failure, tries every registration and rethrows a transient failure afterwards so the job retries, and logs (does not mask) a not-configured sender.
- `enqueueBadgeRefresh(client, userId)` in `push/badgeRefreshEnqueue.ts`: job key `badge-refresh:<userId>`, `replace` mode, 5 s delay, 3 attempts, on the caller's own client so a rollback drops the job.
- Triggers: an approval request is created (`insertPendingApprovalRequest`; the owner is `agent_runs.actor_user_id`; a replayed tool call enqueues nothing), an approval request is decided (`decideAndEnqueueApprovalRequest`; an already-decided or foreign id enqueues nothing), and `PATCH /api/notification-preferences` whose body names `badgeApprovals`, `badgeInvites` or `badgeInbox`.

## Entry points and contracts dependents build on

- `computeBadgeForUser`, `loadBadgeCounts`, `sendApnsBadgeUpdate`, `handlePushBadgeRefreshTask`, `enqueueBadgeRefresh`. None is exported from the `@semprec/data` barrel (see deviation 2): inside `packages/data` they are imported by relative path.

7. `tenantIsolationJobs.test.ts` requires one case per api task; the `pushBadgeRefresh` case uses the real APNs adapter with `APNS_*` unset (not-configured, no network) and proves the job runs for its tenant and revokes nothing. 8. Invitation and Inbox counts remain 0 (gh-1828), so "sum of the three enabled counts" and the Inbox-off part of the first criterion are proven for approvals only; the Inbox switch cannot discriminate until #1954.
