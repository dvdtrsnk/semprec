Both declared blockers are completed on the tip with a handover: gh-1728 (thread activity bump on a new request) and gh-1766 (the source of an approval request). Neither is marked `Shared-file ordering`, and no blocker was open at this landing.

**Every new `approval_pending` notification now links to the place its request came from and names the request; the user id is no longer in the link.** A request raised in a chat links to `?page=semp-chats&tab=semp&approvalRequestId=<id>`; every other request links to `?page=inbox&approvalRequestId=<id>`. Details under "Contracts dependents build on".

## What was delivered

- `approvalNotificationLinkHref(source, approvalRequestId)` in the new file `backend/packages/data/src/notifications/approvalNotificationLink.ts`. `source` is the kind of the request's source (`ApprovalRequestSourceKind`: `chat`, `tick` or `mcp`) or `null`. `chat` gives `?page=semp-chats&tab=semp&approvalRequestId=<id>`; `tick`, `mcp`, `null` and any other value give `?page=inbox&approvalRequestId=<id>`.
- `getApprovalRequestSourceKind(client, agentRunId)` in `backend/packages/data/src/mcp/approvalRequestsQueue.ts`. gh-1766 stores no source on the request and derives it from the run when a request is read, so a producer needs the derivation at creation. The function reads the run, its thread and, for a run without a visible thread, the root run that `getRootAgentRuns` reaches, and returns the kind, or `null` when the run is not visible to `client`.
- The two kind rules of the private `loadApprovalSources` were moved into the private helpers `threadSourceKind` and `rootSourceKind` in the same file. The queue read and the new function both call them, so the rule is written once in TypeScript (it also exists in SQL for the filter of gh-1785). The result of the queue read is unchanged.
- Both producers of the `approval_pending` notification build `linkHref` with these two functions, inside the transaction that creates the request:
  - `preflightDestructiveApproval` in `backend/packages/application/src/genericOperationGateway.ts`;
  - `createApprovalGatedMcpInvokeTool` in `backend/packages/agent-runtime/src/mcpInvokeTool.ts`.
  Each calls `approvalNotificationLinkHref(await getApprovalRequestSourceKind(client, created.agentRunId), created.id)`. `sourceTable`, `sourceId`, `transitionInstance`, the recipient, the title and the body are unchanged.
- No migration, table, route, generic operation, MCP tool, job name, write hook, stored key, i18n key or ADR was added. The `link` of `ApprovalRequiredError` returned to the agent (`?page=approvals&id=...`) is unchanged. Notifications that already exist keep their old link.

## Contracts dependents build on

- **Exports of `@semprec/data`** (barrel `backend/packages/data/src/index.ts`), both new:
  - `approvalNotificationLinkHref(source: ApprovalRequestSourceKind | null, approvalRequestId: string): string`
  - `getApprovalRequestSourceKind(client: Queryable, agentRunId: string): Promise<ApprovalRequestSourceKind | null>`
- **The link values.** `?page=semp-chats&tab=semp&approvalRequestId=<id>` for a `chat` source, `?page=inbox&approvalRequestId=<id>` for every other one. `<id>` is the id of the `approval_requests` row, the same value as the notification's `sourceId`. No user id is in either link. The links are written to `notifications.link_href` when the request is created and are not recomputed later. No backend code parses `link_href`; the push adapters and the fanout job pass it through.
- **A third producer must call the same pair.** gh-1791 (deferred module agent tools, blocked by this source) creates the `approval_pending` notification "linked by source": it should pass `approvalNotificationLinkHref(await getApprovalRequestSourceKind(client, created.agentRunId), created.id)` on the client of the transaction that inserts the request, as the two producers do. `createPendingApprovalRequest` does not write the notification itself.
- **Which kind a run has** is the rule of gh-1766, unchanged: a run of a tick thread is `tick`, a run of a chat or item thread is `chat`; a run without a visible thread takes the kind of the `triggered_by` of its root run (`mcp` is `mcp`, `heartbeat` is `tick`, anything else is `chat`). `getApprovalRequestSourceKind` returns the kind the approval queue shows for a request of the same run; one test compares the two for every shape of source.
- **Tenant scope.** The derivation reads `agent_runs` and `semp_threads` on the caller's client. A run of another tenant is answered as `null`, like a run that does not exist (tested with two tenants on the runtime role `semprec_data`). `null` links to the Inbox.
- **Failure.** An unknown `semp_threads.kind` makes the derivation throw (`assertKnownValue`, as the queue read does). In a producer this rolls back the request together with its notification. The CHECK constraint on `semp_threads.kind` keeps the value inside `chat`, `item`, `tick`, so nothing triggers it today.
- **Cost.** One request now costs the producer more reads in its transaction: the run, then its thread or, for a run without a visible thread, the walk to the root run (one query per level, bounded by `AGENT_RUN_ROOT_MAX_HOPS`, 32). `preflightDestructiveApproval` reads the run a second time through the derivation.
- gh-1773 (push body and title) and gh-1831 (APNs category) name this source for the link target only; they are not blocked by it.

## Deviations from the specification and spec seams

1. **Spec seam: the Task speaks of "the source recorded on the request by #1766"; nothing is recorded.** gh-1766 derives the source from the run when a request is read. The source therefore adds `getApprovalRequestSourceKind` in `backend/packages/data/src/mcp/approvalRequestsQueue.ts`, a file outside `Touches`, and moves the two kind rules into `threadSourceKind` and `rootSourceKind`. All three reviewers confirmed in the code that the queue read is unchanged.
2. The first parameter of `approvalNotificationLinkHref` is the source kind (`ApprovalRequestSourceKind | null`), not the whole `ApprovalRequestSource` object. Only the kind decides the link; `null` stands for an unknown or missing source.
3. **For the controller and the owner: a run without a thread whose root run a person or a supervisor started is `chat`, so its notification links to the Semp chats page although no thread holds the request.** This is the rule of gh-1766 and the same open seam as point 6 of the gh-1766 handover. The existing producer tests use such runs and now expect the chat link. The requirements reviewer notes that in production a user-rooted run is created only by `sempConversation`, with a thread.
4. `Touches` puts the producer tests in `backend/packages/data/src/__tests__`. The data package cannot import its dependants, so they are in the producers' own suites. The test of identical links is in `mcpInvokeTool.test.ts`, because agent-runtime already depends on `@semprec/application`.
5. The criterion "A request with no recorded source links to the Inbox" is proven on the link function (`null`) and on the derivation (a run that cannot be read gives `null`), not through a producer. A request's run always exists in the creating transaction (tenant-composite foreign key), and every readable run has a kind, so no producer can reach that branch through a production path.
6. `publicSurface.test.ts`, outside `Touches`, lists the two new exports.
7. An unknown thread kind makes the derivation throw instead of falling back to the Inbox. No test covers it; the CHECK constraint keeps it from happening.
8. The push and fanout tests that pass `?page=approvals&user=...` as their own fixture input were left as they are.
9. No ADR was added. The destinations are a product decision recorded in the issue.
