## What was delivered

- `POST /api/mail/mailboxes` counts each login verification of the session's user in an in-process limiter. A user who already has 10 counted attempts inside 900 seconds is answered 429 with the body `{ "error": { "code": "rate_limited" } }` and a `Retry-After` header. The verification is not called for that request.
- The limiter of `backend/services/semprec-api/src/clientIpThrottle.ts` has a fifth action, `mailboxCredentialVerification`: 10 events per 900 seconds. Its key is the user id exactly as given. The four public actions keep the address grouping of `throttleKeyForIp` and their limits. `tryAcquire`, `record`, `retryAfterSeconds` and `release` are reused unchanged.
- The handler `createMailboxPasswordConnectRouteHandler` (`backend/packages/data/src/mail/mailboxPasswordRouteHandlers.ts`) calls `tryAcquire("mailboxCredentialVerification", userId)` directly before the verification, with no `await` between the count and the call. A refusal throws `RateLimitedError`.
- `RateLimitedError` (`backend/packages/data/src/errors.ts`) is a new `ChokePointError`: status 429, code `rate_limited`, property `retryAfterSeconds`.
- The REST adapter (`backend/services/semprec-api/src/adapter/adapterRoute.ts`) writes a `Retry-After` header for that error class. The seconds are not in the body.
- `createDispatcher` (`backend/services/semprec-api/src/app.ts`) creates one limiter for its lifetime and hands it to the custom routes as the member `throttle` of the custom-route container. A container that already carries a `throttle` keeps it. `serve.ts` is unchanged.
- ADR `docs/adr/2026-11-12-mailbox-credential-verification-is-throttled-per-user.md` (accepted) records seven decision points: the per-user key, the in-process state, the dispatcher-created instance, the fail-closed mount, the placement of the count, the attempt that is never released, and the header written by the adapter. It extends `2026-10-17-per-ip-auth-throttles-held-in-process` without editing it.
- No migration, table, column, route, generic operation, job name, write hook, tenant cutover entry, module manifest entry, stored key or i18n key was added.

## Contracts dependents build on

- Order inside the handler: body validation (400), read of the container members `mailServerClients.verifyPassword` and `throttle`, default mailbox name, first read of the duplicate rule (409 `provider_account_already_connected`), the count (429 `rate_limited`), the verification, the write transaction.
- What is counted: every request that calls the verification. An accepted login, a refused login, an unreachable server, an unexpected failure of the verification and a 409 of the write transaction all stay counted. The route never calls `release`.
- What is not counted: a request with an invalid body (400) and a request whose address the first read of the duplicate rule refuses (409). The limiter is not asked for either, so a user at the limit gets the same answers. A test asks an invalid body at the limit and gets 400 without `Retry-After`; no test asks a held address at the limit.
- `Retry-After` holds the whole seconds until the oldest counted attempt of that user leaves the window.
- Accepted logins count, so a user can connect at most 10 password mailboxes in 15 minutes.
- The state is in the memory of the semprec-api process. A restart gives every user a full budget, and a second process would give each its own budget.
- `RateLimitedError` is exported from `@semprec/data` (through `export *` of `errors.ts`; `index.ts` itself did not change). The constructor takes the seconds. Any route behind the REST adapter that throws it is answered 429 with `Retry-After`.
- `rate_limited` is not in `ITEM_ERROR_CODES` (`adapter/errorContract.ts`). `statusForError` falls back to the error's own 429, as it does for `provider_account_already_connected`.
- `CustomRouteDependencies` (`adapter/customRouteMount.ts`) has the optional member `throttle?: ClientIpThrottle`. `MailboxPasswordRouteDependencies` in `packages/data` declares it structurally as `throttle?: { tryAcquire(action: "mailboxCredentialVerification", userId: string) }`.
- A mount that goes through `createDispatcher` always has a limiter. A test that needs its own clock passes `createClientIpThrottle({ now })` as `customRouteDependencies.throttle`.
- A mount that bypasses the dispatcher (`mountCustomRoutes` directly) and has no `throttle` fails each request of the password connect route that has a valid body with a plain `Error`, which the adapter answers as a generic 500 before any server is contacted. A test that mounts the route that way adds the member.
- The dispatcher's limiter is a separate instance from the ones `authHandler.ts` and `invitationHandler.ts` create for themselves. Those listeners and their limits are unchanged.
- The parameter `ip` of the three methods of `ClientIpThrottle` is now named `subject`. No caller changed.
- `createDispatcher` now adds two keys to the custom-route container: `heartbeatRuleKinds` and `throttle`. `customRouteMount.test.ts` asserts exactly these keys for a caller that gives no container; a source that adds a third key updates that test.
- Only the password connect route is limited. The OAuth connect routes, the reauthorization route and every other authenticated route have no limit of this kind (out of scope of gh-1750).

## Deviations from the specification and spec seams

1. Placement of the count. The handover of gh-1736 left open on which side of the first duplicate-rule read the count goes. It goes after it, directly before the verification. A request answered 409 by that read contacts no server and is not counted.
2. Task step 2 asks to release the reservation only when the body failed validation. The count is taken after the validation, so no validation can fail while it is held and the route never calls `release`. The ADR records this and the rejected alternative, which would answer an invalid body at the limit with 429 instead of 400.
3. Files beyond `Touches`: `packages/data/src/errors.ts`, `adapter/adapterRoute.ts`, `adapter/customRouteMount.ts`, the ADR and the tests listed above. The handler lives in `packages/data` and answers through the REST adapter, which had no way to send a header with an error.
4. The 429 body is the adapter's envelope `{ error: { code: "rate_limited" } }`, not the bespoke `{ error: message, code }` of `authHandler.ts`. Status, code and `Retry-After` match it.
5. The limiter instance is created by `createDispatcher`, not by `serve.ts`.
6. A mount without the limiter throws a plain `Error`, not `CustomRouteConfigurationError`, because `packages/data` cannot import `requireCustomRouteDependency`. It repeats `requireVerifyPassword` of gh-1736.
7. No spec seam applied: no route entry, no migration and no statement text changed.
