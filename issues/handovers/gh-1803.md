## What was delivered

- `calendar/calendarTrashHooks.ts`: `calendarItemDeleteHook` and `calendarItemRestoreHook`, registered in `domainWriteHooks.ts` for the Calendars database. Delete: a system or subscription calendar is `403 forbidden` (`details.field` is `kind`); under the default-mark advisory lock the oldest other live own calendar (by `created_at`, then `id`) is read, and none left is `409 last_own_calendar`; a deleted default hands `isDefault` to that calendar through `updateItemWithClient` as the system writer; every live Event on the `Calendars.events` edges is locked `FOR UPDATE` and trashed through `itemDeleteWithClient` with the calendar's exact deletion epoch (usual Event hooks, heartbeats and after-commit invalidations); Events trashed earlier are untouched. Restore: Events of exactly the calendar's epoch are restored through `restoreItemWithClient`, and a stale `isDefault: true` on the restored calendar is cleared.
- Review fix (medium finding, lock order): `chokePoint/hooks.ts` gained delete and restore pre-lock registries (`registerItemDeletePreLockHook`, `registerItemRestorePreLockHook`, `runItemDeletePreLockHooks`, `runItemRestorePreLockHooks`, types `ItemDeletePreLockHook`, `ItemRestorePreLockHook`, `ItemTrashPreLockHookContext`), run by `itemDeleteWithClient` and `restoreItemWithClient` in `itemTrash.ts` before `lockItemById`. `assertDatabaseNotArchived` (`databaseGuards.ts`) now returns the database row. Calendars registers `calendarItemDeletePreLockHook` and `calendarItemRestorePreLockHook`, which take `lockDefaultMark` before the calendar row is locked, the order of every other writer of the mark. Only the root item's database is pre-locked; nested Event trashes are unaffected because `isCalendarsDatabase` excludes the Events database.
- `ConflictError` (`errors.ts`) takes an optional third argument `code`, default `version_conflict`; no existing caller changed.
- ADR `docs/adr/2026-11-12-deleting-a-calendar-takes-the-default-mark-lock-and-its-events-into-its-epoch.md` (lock and epoch decisions, corrected after the fix to the real behaviour and its limits).

## Contracts dependents build on

- Hooks: `calendarItemDeleteHook`, `calendarItemRestoreHook`, `calendarItemDeletePreLockHook`, `calendarItemRestorePreLockHook` (inside `packages/data`, not in the barrel). `calendarRowHooks.ts` now exports `lockDefaultMark`, `isCalendarsDatabase` and `isSystemOrSubscription`.
- A new module that must take its own lock before the trashed row registers a delete or restore pre-lock hook with the owning module id; it runs once for the root item of a delete or restore.
- Errors: `403 forbidden` with `details.field: "kind"` for system or subscription calendars; `409` with code `last_own_calendar` for the last own calendar.
- Trash semantics: a calendar and its live Events share one deletion time; restore brings back only Events of that epoch. Readers of the default mark look at live rows only.
- No route, operation id, table, migration or job name is added.

## Deviations from the specification and spec seams

1. Spec seam: the choke point refuses to update a trashed row, so the delete hook cannot clear `isDefault` on the calendar it just trashed. The trashed row keeps `isDefault: true` until a restore, where the restore hook clears it. Readers of the default look at live rows only.
2. The worker's original deviation about a possible deadlock (delete hook took the advisory lock after the calendar row) was withdrawn by the review fix: the pre-lock registries remove the inverted order. Residual stated in the ADR: the pre-lock covers the root item only.
3. The successor and the restored calendar are written as the system writer.
4. Tests that trashed the default calendar generically to build a tenant without a live default (`calendarRowHooks.test.ts`, `defaultCalendarCreateHook.test.ts`, `eventDefaultCalendarWritePaths.test.ts`) now use a raw `UPDATE` of `deleted_at`, because the hook moves the mark.
5. A default calendar trashed before this source with no other default cannot be restored (`400` on `isDefault`); documented, not repaired.
6. Two extra test files beyond Touches (`calendarTrashWritePaths.test.ts`, `conflictErrorCode.unit.test.ts`), and the choke-point files `hooks.ts`, `itemTrash.ts`, `databaseGuards.ts` were changed by the review fix, outside the original Touches list.
7. Blocker gh-1799 (Shared-file ordering) was not needed.
8. At the merge, `itemTrash.ts` conflicted with the per-database grant check of gh-1810 (`assertWriterDatabaseAccess`); both are kept, the grant check first.
