# gh-1703 — Move an Inbox attachment into Files on confirm

Repository-Issue: gh-1703

## Delivered behavior and production wiring

- New step kind `fileFromAttachment` in the multi-step proposal envelope (`proposalStepSchema.op` in `backend/packages/data/src/inbox/inboxTickAction.ts`). Recorded in `docs/adr/2026-10-29-file-from-attachment-proposal-step.md`, a new standalone ADR; the accepted multi-step ADR is not edited.
- Validation: `assertValidFileFromAttachmentStep` (inboxTickAction.ts) calls `parseFileFromAttachmentProperties` (`backend/packages/data/src/inbox/fileAttachmentStep.ts`). Properties are exactly `attachmentId` (UUID), `name` (non-empty) and an optional `date`; `file`, `type` and any other key are a 400 with `details: { ref, field }`. The step names neither `databaseKey` nor `itemId` and writes the system Files database. Its relations are checked as a create step's are (Files relation keys such as `projects`, `companies`). It is never the primary step: the envelope's top-level `properties` mirror the primary step and are checked against the target database's properties, where `attachmentId` is not a property.
- Execution: `executeFileFromAttachment` in `backend/packages/data/src/inbox/proposalSteps.ts`, reached through `executeProposalSteps`, which `confirmProposalWithClient` runs in the confirm transaction.
  1. `getInboxAttachment`; the attachment must have `inboxItemId === sourceInboxItemId`, otherwise 400 `validation_failed`.
  2. `lockBlobById` (new, `blobs/blobsStore.ts`): a row lock on the blob for the rest of the transaction.
  3. `itemsStore.findFileItemByBlobId`. A live Files item names the blob: the step resolves to it, changes none of its properties or relations, and writes no origin row.
  4. Otherwise `createItemWithClient` on Files with `name`, `date` (when given), `file: { blobId }` and `type`. `type` comes from `filesTypeForMimeType` (`backend/packages/data/src/blobs/fileTypeDetection.ts`) and is set only when the Files `type` select offers that key, read at confirm. The step's relations are written for a created item only.
  5. `deleteInboxAttachment` removes the attachment row in both cases. A zero-row delete is a `ConflictError` (409), which rolls the transaction back. The blob is not deleted here.
- `confirmProposalWithClient` (`proposalActions.ts`) now resolves the origin source before it runs the steps and passes `sourceInboxItemId: origin.inboxItemId` to `executeProposalSteps` (a new required option). The Files items a move creates are in `createdItemIds`, so the existing `insertItemOrigins` gives them an `item_origins` row with capture channel `inbox`.
- `executeProposalSteps` returns `fileFromAttachments: [{ ref, fileItemId, movedAttachmentId, created }]`, one per file step, in execution order.
- `core.filesTranscriptionTrigger` (`backend/packages/data/src/transcription/transcriptionActions.ts`) returns early for a Files item that `withFromInbox` (`chokePoint/itemOriginReads.ts`) reports as `fromInbox`.
- `publicSurface.test.ts` lists `lockBlobById`, which `blobs/blobsStore.ts` exports through `export *`.
- No migration, no schema change, no tenant-table count change.

## Tests

`backend/packages/data/src/__tests__/inboxAttachmentMove.test.ts` (24 integration tests on the seeded database, through `confirmProposalWithClient`, the executor, and the trigger action):

- A photo moved with a project: one Files item on the same blob, with `name`, `date`, `type` `jpg`, the project edge, an origin row (card, Inbox item, channel `inbox`); the attachment row is gone and the blob count is unchanged.
- The step result carries `movedAttachmentId` and `created: true`; a PDF gets `type` `pdf`.
- No Files `type` for `application/zip`, for a `png` the Files select lacks, and for a select with no options.
- A Files item already naming the blob: no second item, the existing row's `properties` and `updated_at` unchanged, no origin row, attachment removed.
- Another Inbox item's attachment and an unknown id: 400 `validation_failed` with `details: { ref: "file", field: "attachmentId" }`; attachment rows, blobs, Tasks and the card unchanged.
- A proposal with no source Inbox item: 400.
- Invalid steps (file property, `type`, empty name, missing or non-UUID `attachmentId`, `databaseKey`, `itemId`, a relation key that is not a relation property): 400, nothing written.
- A file step as the primary step: 400 with `field: "op"`.
- A later step fails at the choke point: the move is rolled back (no Files item, no Task, attachment kept, card `proposed`).
- An audio attachment confirmed into Files enqueues no transcription job; an audio file created directly in Files, with no origin, is still enqueued (contrast in the same test).
- Deleting the Files item of a move (`deleteItemDependents`) keeps the blob that an unconfirmed attachment still names.
- Concurrency with two connections: a first confirm holds its transaction open, a second confirm of the same bytes waits on the blob lock (the test polls `pg_stat_activity`), the first commits, and the second reuses the item. Result: one Files item, both attachments removed, one origin row.
- Concurrency at executor level: a second move of the same attachment waits, then fails with 409 `version_conflict`, and nothing is written.
- Missing Files database (raw fixture update inside a rolled-back transaction, reason commented): 404 `not_found`, attachment kept, no Task written.

Existing suites run with the new code: `proposalActions`, `transcription`, `inbox`, `blobs`, `publicSurface`, `itemOriginsTenant`, `fileUploadStore`, `inboxTick`, `inboxTickProposal`, `itemFromInbox`, `inboxPipeline`, `rowLevelSecurity`, `tenancyCatalog` and the new file: 30 files, 384 tests, all pass. The existing `transcriptionActions.test.ts` case "enqueues a transcription job once for a standalone audio recording" still covers a Files item with no origin, the shape `POST /api/files` creates.

Checks run: `tsc --noEmit` for `@semprec/data` and `semprec-api`; eslint and prettier on every touched file and on the ADR; `depcruise` (`check:boundaries`) and `check-write-safety`, both run directly because `pnpm run` hit the store lock in the sandbox.

NOT RUN: the full `pnpm run verify` in `backend/`, `pnpm -r run build`, the `web/` pipeline and the mobile pipeline (not touched). The integration tests need the embedded Postgres in `globalSetup`, which the sandbox blocks (shared memory); they were run with the sandbox disabled.

## Notes for dependants

- Per-step results (#1648) are not stored. `executeProposalSteps` returns `movedAttachmentId` for each file step, but nothing persists it. The undo (#1943) cannot recognise a Files item that received a moved attachment until #1648 stores it at confirm.
- The card does not report that a file already existed. The step result carries `created: false` for that case; the card-level message is not built here and belongs with #1648 or the card UI.
- Nothing produces a `fileFromAttachment` step yet. The Inbox tick builds only `create`, `update` and `link`, and `reviseProposalWithClient` takes no `operations`. A producer (#1965, #1969 or a later issue) has to store the step as a secondary step of a multi-step envelope whose primary is another step, and it must pass the proposal's source Inbox item.
- `executeProposalSteps` requires `sourceInboxItemId` (`null` when the proposal has no source Inbox item). Any new caller must pass it.
- The relations of a file step are written only for a created Files item; a reused item keeps its relations unchanged (decided).
- Concurrent moves of the same bytes serialise on the blob row lock, which the Files lookup also needs. A Files item created by one confirm is visible to a waiting confirm only after that confirm commits. If the first one rolls back, the waiting one creates its own item.
- The Files `type` options are read at confirm. The seed and the #1410 cutover already declare `png`, `heic` and `audio`; a tenant whose select lacks an option gets no `type` for that file.
- Undoing a confirmation does not remove the `item_origins` row of a Files item it created. That is decided in #1943.
- Audio moved by confirm is not transcribed; proposing its transcription is #1978.
- A Files item created by a move is deleted through `deleteItemDependents` like any other; its blob stays while any Files item or Inbox attachment still names it.
- Migration ordinal: none. This change adds no migration.
