## What was delivered

- `backend/packages/data/src/transcription/transcriptSpeakerAssignment.ts` (new): `assignTranscriptSpeaker` assigns, replaces or clears a speaker key in one transaction. It locks the key's card, then the transcript row, validates the key and the live person, refuses a person already mapped to another key (`personAlreadyMapped`), deletes a replaced edge, writes the `speakers` edge through the choke point with `{ speaker }`, adds the person to the linked Event's `people` with the insert-only `createRelationIfAbsentWithClient` (attendee, no invitation, an existing edge and its invitation are kept) and settles the card. `listSpeakerCandidates` returns the Event's participants with invitation state and the key each is mapped to, and the own person as `self`.
- `settleSpeakerCardWithClient` in `backend/packages/data/src/inbox/proposalActions.ts`: locks the card, settles only `proposed` and `needsClarification` cards, `confirmed` when the stored proposal is exactly this person for this key and relation, otherwise `rejected`, with a history entry; a confirmed, rejected, invalid or trashed card is left alone.
- Review fixes: after the transcript lock the card is looked up again when none was found and locked with NOWAIT (a busy card answers 409 `version_conflict` and rolls back, so the confirm's card-then-transcript order is never inverted); `ownerProbes` for both routes in the isolation test; an exact-match test of the card settling; the docstring's lock description corrected; ADR written.

## Deviations from the specification and spec seams

1. The route entries are in `routeMatrix/transcripts.ts`, not in `routeMatrix.ts`.
2. The Event participant edge uses `createRelationIfAbsentWithClient` (the insert-only variant), not plain `createRelationWithClient`, so a participant who already has an edge is never rewritten and an invitation's metadata is kept. The rules reviewer confirmed it is the case the ADR `2026-11-06-speaker-confirm-inserts-participants-without-metadata-replacement` defines.
3. Clearing a key (`personId: null`) leaves the key's open card as it is: the Task's card-settling step is read as belonging to an assignment of a person. A test pins this. The requirements reviewer judged the reading defensible.
