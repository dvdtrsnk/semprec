# Handover for gh-1550

The api process now hosts the IMAP IDLE lifecycle for IMAP accounts. A dispatcher picks the lifecycle factory by the account's sync mode, so `imap` accounts get IDLE and every other mode keeps the noop lifecycle, which the periodic sweep relies on. The IDLE connections open through `openImapFlow`, the address-checked connect step that `openImapConnection` now wraps.

## What was added

- **`backend/packages/data/src/mail/mailServerConnections.ts`**: `openImapFlow(settings, credential, options)` resolves with the connected `ImapFlow`. It holds the IP-literal refusal, the client construction, the connect, the close after a failed connect and the `MailServerUnreachableError` mapping. `openImapConnection` now only wraps its result in `ImapFlowMailClient`. `MailServerConnectionOptions` gains optional `maxIdleTime` and `socketTimeout`, forwarded to the `ImapFlow` constructor and ignored by `createSmtpTransporter`.
- **`backend/packages/data/src/mail/imapIdleClient.ts`**: `CreateIdleTunedImapFlowClient` returns a connected client. The transport no longer calls `connect()` in `resolveFolders` or `connect`.
- **`backend/packages/data/src/index.ts`**: exports `openImapFlow`, `createBoundedImapIdleLifecycleFactory`, `createImapFlowIdleTransport`, `imapConnectionLimitForProvider`, `sharedImapConnectionLimiter`, `getDecryptedCredential` and the IDLE types the Task lists. `publicSurface.test.ts` lists the six runtime names.
- **`backend/services/semprec-api/src/mailLiveSyncLifecycles.ts`** (new):
  - `createMailLiveSyncLifecycleFactory({ pool, hosted })` dispatches on `account.syncMode`. A mode without a `hosted` entry gets the noop lifecycle.
  - `createImapIdleLifecycleFactory(pool)` builds `hosted.imap`. `createClient` reads the settings with `getMailServerSettings` and returns `openImapFlow` with the IDLE options. A missing settings row or a missing `imap` endpoint is a configuration error naming the mailbox. `getCredential` reads `imap_idle` through `getDecryptedCredential` on the pool and throws when no credential exists. `getConnectionLimit` reads the mailbox item as `mailSyncJob.ts` does. `onError` logs the mailbox id, the folder path, and the error's name and code.
  - `connectionLimitOf` and `errorNameAndCode` are exported for the tests.
- **`backend/services/semprec-api/src/serve.ts`**: the root receives `createMailLiveSyncLifecycleFactory({ pool, hosted: { imap: createImapIdleLifecycleFactory(pool) } })` in place of the noop factory. The shutdown order is unchanged: `mailLiveSync.stop()` runs before the pool closes.

## Tests

- `backend/services/semprec-api/src/__tests__/mailLiveSyncLifecycles.test.ts` (new, integration tier, 11 cases). With a fake IDLE transport:
  - an `imap` account opens its connection, and a signal enqueues a sync;
  - a `gmail_api` account gets the noop lifecycle and the transport never sees it;
  - `root.stop()` closes every connection of every hosted account;
  - a connect the policy refuses backs off, retries, and reports the error without a lifecycle error.

  With the production host, a missing credential and a missing or SMTP-only settings row each fail the start, naming the mailbox. A host that resolves to `10.0.0.1` is refused before any connection, and the start fails with `MailServerUnreachableError` that names no address. `connectionLimitOf` reads the configured limit, then the provider's, then the default.

- `backend/packages/data/src/__tests__/mailServerConnections.test.ts`: `openImapFlow` resolves with a connected, logged-in client; a refused name maps to `MailServerUnreachableError` with no connection; `maxIdleTime` and `socketTimeout` are forwarded, and imapflow's own defaults apply when they are omitted.
- `backend/packages/data/src/__tests__/imapIdleClient.unit.test.ts`: the fake client arrives connected, and the transport never calls `connect()` on it.

## Coverage gaps and known defects

- **A refusal present at start is not retried (Acceptance criterion 4 only partly holds).** `start()` in `imapIdleLifecycle.ts` awaits `transport.resolveFolders`, and that call opens its own connection through `createClient`, outside any backoff. A refused host therefore rejects `start()`. The root logs the `start` phase, keeps the entry, and never retries the lifecycle, because the entry matches the sync mode. The periodic sweep still syncs the account. Connect failures after a successful start do back off, and the test covers that path. Fixing the start path needs a change to `imapIdleLifecycle.ts`, which is outside this issue's Touches list.
- **A database error in `getConnectionLimit` can take the api process down.** `runFolderLoop` in `imapIdleLifecycle.ts` calls `getConnectionLimit` outside its `try`. A rejection there is an unhandled rejection, and `installFatalHandlers` exits the process. This was latent while no IMAP lifecycle ran in the api. Follow-up for `imapIdleLifecycle.ts`: move that call inside the `try`.
- The production `onError` closure is not exercised by a test. It runs only on a connect failure after a successful start, and reaching that needs a server that answers LIST and then refuses the IDLE connect.
- The fake IDLE transport does not speak IMAP. Nothing here runs IDLE against a live server; that remains the gap recorded for #196.

## Notes for dependants

- Gmail (#1739) and Graph (#1745) add their factories as `hosted.gmail_api` and `hosted.graph_api` in `serve.ts`. The dispatcher already routes those modes.
- Every IDLE or other long-lived IMAP connection to a tenant-chosen host goes through `openImapFlow`. A transport that receives a client must not connect it.
- An IMAP client opened outside the sync job must be closed by its owner. The IDLE lifecycle closes its own connections on stop and on every failed round.
