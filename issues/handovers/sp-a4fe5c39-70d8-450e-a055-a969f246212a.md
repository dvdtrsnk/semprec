# Handover: serialise calendar Event pushes and make every provider create idempotent

Commit on `fix/ia-push`: `3753e91c3`. Review findings 1, 2, 4 and 13 of the local review of PR #2089. Nothing was run against a real provider.

**Changes.**
- `calendar/sync/adapter.ts`: `PutRemoteEventInput.createKey`, the local Event's id on every create the push makes.
- Graph (`graphEventMapping.ts`, `graphCalendarAdapter.ts` create path): `transactionId` from calendar, `createKey` and fields. Two Events with equal fields no longer share one; a repeat of the same Event with the same fields still does. The fields stay in the id because Graph does not document its answer to a repeated `transactionId`.
- Google (`googleCalendarAdapter.ts` create path): `googleEventIdOf` (base32hex of a hash of calendar, `createKey`, generation 0–7) as the event `id`; a 409 reads the id: a live event gets the fields (`PATCH`, `If-Match`), a cancelled one moves to the next generation, an unknown one stays the plain 409 refusal; after eight deleted generations Google names the event.
- CalDAV (`caldavAdapter.ts` create path): resource name (and, without `icalUid`, UID) from a hash of `createKey`; a create's 412 there reads the resource and replaces it with the fields.
- `eventPushJob.ts`: `createKey` passed; the duplicate branch trashes another Event holding the created remote id only when it has no push state, else the push is `conflict` and both stay; the prologue claims the push's lease (`claimEventPush`), a held lease re-enqueues the push for the lease's end and answers `deferred`, `finally` releases it and enqueues a newer pending revision at once (a release failure is logged, never replaces the push's outcome); `baseFieldsOf` parses with `remoteEventFieldsSchema` (exported from `calendarSyncApply.ts`).
- `calendarSyncStore.ts`: `claimEventPush`, `releaseEventPush`; `calendarAccountSyncEnqueue.ts`: optional `runAt`; `0001_baseline.sql`: `calendar_event_push_state.lease_id`, `lease_until` with a both-or-neither CHECK.
- `testSupport/fakeCalendarSyncAdapter.ts`: a create with a known `createKey` writes onto the first create's Event; `beforeNextPutAnswer` runs after a put landed and before it answers.
- `docs/architecture/domain-calendar-tasks-and-media.md`, `transactions-and-side-effects.md`.

**Tests** (each checked to fail with its fix reverted). `calendarEventPush.test.ts`: "repeats a create whose answer was lost onto the provider's Event the first attempt made", "trashes the Event a pass made for a create meanwhile, but never one changed here", "runs one push of an Event at a time, and a change made meanwhile is pushed after it", "refuses to push from a stored base whose fields break their contract". `graphCalendarAdapter.test.ts`: "creates in the calendar with a transactionId that a retried create of the same Event repeats". `googleCalendarAdapter.test.ts`: "a create for a local Event names the Google event after it, so a repeat writes onto the first one". `caldavAdapter.test.ts`: "names a local Event's resource after it, so a repeated create writes onto the first one's resource".
