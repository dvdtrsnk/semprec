## What changed
Only `backend/packages/data/src/trash/__tests__/purgeExpiredTrashPerTenant.test.ts` changed:

- **`trash`**: the backdate UPDATE is now the constant `BACKDATE_SQL`. The helper checks `rowCount` and throws `trash: backdating item <itemId> in database <databaseId> affected <n> rows, expected 1` unless exactly one row was affected. This covers findings `ec01677db8` and `4e623975d4`: a wrong database/item pair, or an item the current tenant cannot see, now fails during fixture setup, before any purge assertion runs.
- **`makeFilesItem`**: the blob-property UPDATE is now the constant `FILE_PROPERTY_SQL`. The helper throws `makeFilesItem: assigning blob <blobId> to item <itemId> affected <n> rows, expected 1` instead of returning the item (finding `ee2bfc6bdd`).
- **`withZeroRowResult(sql, fn)`**: a narrow `vi.spyOn(pool, "query")` double. It returns a zero-row `QueryResult` only for calls whose SQL text exactly matches the target, without running them, and passes every other query through to the real pool. It is restored in `finally`, so a failed assertion inside `fn` still restores it. It returns the parameters of each intercepted call.
- **Two new tests** under `fixture writes must affect exactly one row (issue #1250)`:
  - `trash` rejects with the exact diagnostic naming the item and database, and exactly one UPDATE was intercepted.
  - `makeFilesItem` rejects with the exact diagnostic naming the blob and the intercepted item id, and returns no item.
- Each raw-SQL fixture now has a comment explaining why it is raw SQL.

Choke-point creation and deletion are unchanged, and so are the five existing real-database purge scenarios. They now run with both guards on, which shows the tenant-scoped success paths affect exactly one row.

Not touched (out of scope): production purge code, the unrelated multi-row `UPDATE ... WHERE id = ANY($1)` in the inline-database scenario, and any shared fixture framework.
