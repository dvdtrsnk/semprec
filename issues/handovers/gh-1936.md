## What was delivered

An `agentRun` Semp message ref that carries a `messageId` now means one answer of the chat run, not the whole run. Posting such a ref is validated by one statement of its own (`validateRunAnswerRefs`): the message must be an assistant message of the run's thread whose `agent_run_id` is the named run, in the caller's tenant. Every miss (another run, a user or system message, an unknown id, another tenant's message, a run without a thread) raises the store's existing `Invalid reference` validation error with field `context[index]`, the same error as for an unknown target. When Semp reads such a ref (`readRunAnswerContext`), the context holds only that answer: its question, its result and the stored steps summary. A ref without `messageId` keeps its statement and its whole-run context unchanged.

## Entry points and contracts dependents build on

- Ref shape: `{ kind: "agentRun", agentRunId, messageId? }`. `messageId` was already optional on the schema and rejected on every other kind by the strict objects (delivered by gh-1369); this source adds no schema change and tests both.
- Identity: `messageRefKey` (`packages/shared/src/sempMessageRef.ts`) is now `agentRun:<agentRunId>:<messageId or empty>`. A whole-run ref and each answer ref of one run are distinct refs; the same answer posted twice in one message dedupes to the first.
- Validation: `validateRunAnswerRefs` in `packages/data/src/semp/sempRunAnswerRef.ts`, called from `validateSempMessageRefs` for the refs with `messageId`; one real statement per nonempty kind stays for the other kinds (whole-run refs still JOIN `agent_runs`).
- Read: `readRunAnswerContext` in the same module, called from `sempRefReadContext.ts`; context keys are English camelCase (question, result, steps), question and result cut at 8000 characters with a `truncated` flag, steps from `semp_messages.steps` (bounded to 100). Unavailable (null) for every miss of the validation rule.
- Every `messageId` that the answer list of gh-1932 hands out satisfies the rule (role assistant, same thread, `agent_run_id` = the run).
- No route, table, migration, job name, i18n entry or ADR is added. The new module is a sibling of the data barrel and is not exported from `packages/data/src/index.ts`.

## Deviations from the specification and spec seams

1. Task step 1 (optional `messageId` on `agentRun`) and step 5 (rejection on other kinds) were already delivered by gh-1369; this source adds tests only.
2. The membership rule is stricter than the Task text: the message must have `agent_run_id` equal to the named run, not only be an assistant message of the run's thread.
3. The existing handler test that used random messageIds now binds a real assistant message of the run.
4. Dedup identity changed from the first draft (decision 4 of the worker, "messageId ignored by the key") by the fix round: `messageRefKey` now includes `messageId`, because once `messageId` selects content two answers of one run are not the same ref. The gh-1369 docstring and unit test were updated.
5. The "steps summary" is the stored `semp_messages.steps`; question and result are cut at 8000 characters.
6. No new i18n error message: the existing `Invalid reference` error is reused.
7. Residual, not introduced here: `z.uuid()` accepts mixed-case ids, so the same id in different case yields different keys, as for every other id-keyed ref kind.
