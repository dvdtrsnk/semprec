## What was delivered

- The editor schema's rules (`required`, `visibleWhen`, as the module manifests declare them) are evaluated on the card's effective values: the envelope properties of the active steps overlaid with the pseudo field values stored in `userOverrides`. New pure functions in `inbox/editorSchema.ts`: `isFieldVisible`, `findMissingRequired`, `visibleKeys`, `buildEditorValues`, `toProposalWarnings`; type `ProposalWarning` (`{ ref?, field, code: "required" }`).
- `confirmProposalWithClient` refuses the first visible required field that has no value with `ValidationError` (`details.field`, and `details.ref` for a multi-step card) before any write. It runs after the envelope validation and inside the confirm's own transaction.
- `updateProposalValuesWithClient` accepts the pseudo keys of the card's schema in `set` (stored in `userOverrides`, kept out of the effective envelope and out of the created item), leaves hidden fields out of `userEditedKeys`, and returns `{ item, warnings }` instead of the bare item.
- `PATCH /api/proposals/:id/values` answers a top-level `warnings` array (empty when none) beside the card; the adapter envelope in `adapterRoute.ts` carries it. A repeat of an `Idempotency-Key` (gh-1894) answers the warnings of the first call, because the stored body is now `{ item, warnings }` (merge resolution, see below).
- New sibling `inbox/proposalEditorRules.ts` resolves the card's schema through `getEditorSchemas()` (full module registry, cached per process). New ADR `docs/adr/2026-11-13-inbox-editor-schema-rules-read-the-cards-effective-values.md`.

## Entry points and contracts dependents build on

- `updateProposalValuesWithClient(client, config, proposalId, input)` returns `UpdateProposalValuesResult { item: ItemRow; warnings: ProposalWarning[] }`; both types are exported through `proposalActions.ts`, `ProposalWarning` also on the existing `ConfirmationResult` export line of `packages/data/src/index.ts`.
- `assertRequiredFieldsHaveValues` and `loadCardEditorRules` in `proposalEditorRules.ts`, both taking an optional declaration source (default: the process-wide registry).
- Stored idempotent response body of `PATCH /api/proposals/:id/values` (table `idempotent_responses`, route `PATCH /api/proposals/:id/values`) is `{ item, warnings }` since this landing; the replay parses it with `storedUpdateSchema` in `inboxRouteHandlers.ts`. Rows stored by the earlier shape (bare card, at most 24 hours old, no production data in this program) no longer parse.
- Routes: no route was added. Response shape of the values route gained `warnings`. No table, column, job name or migration.

## Deviations from the specification and spec seams

1. `updateProposalValuesWithClient` lives in `inbox/proposalValueUpdates.ts` (gh-1892 handover) and returns `{ item, warnings }`; callers that need the card read `.item`.
2. The item envelope is built in `adapter/adapterRoute.ts` (there is no `sendItemResponse` in `adapter/http.ts`); the optional `warnings` field was added to `AdapterHandlerResult` there.
3. `packages/data/src/index.ts` is at the 900-line cap, so `ProposalWarning` is exported as a type on an existing line.
4. New code is in siblings; the Touches list names `editorSchema.test.ts`, the existing file is `editorSchema.unit.test.ts`, the DB-backed tests are in the new `proposalEditorRules.test.ts`.
5. The schema is not applied to a relation envelope, to a multi-step envelope whose primary step is update or link, to a legacy block-shape `pageContent` envelope, or to a destination that `deriveInboxCardKind` maps to a clarify card; a `pageContent` envelope answers the pseudo fields `page` and `day` with its target; a field of a multi-step card is read from the first step that has its key, a missing one is reported on the primary step; a pseudo key is accepted under any ref the card has. All recorded in the ADR.
6. Four existing Files-card fixtures had to carry a file value, because the Files editor schema declares `file` required.
7. Merge resolution (queue runner): the gh-1894 idempotent replay of the values route stored the bare card; it now stores `{ item, warnings }` so a replay answers the first call's warnings. The `editValues` helper of `inboxTickProposal.test.ts` reads `.item`. A route-handler test pins the warnings replay.
