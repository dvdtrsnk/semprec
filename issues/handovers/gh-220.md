## Summary

Implements issue #220: exposes Semprec's generic 28-operation catalog through in-process AgentTools (`packages/agent-runtime`) and an authenticated `POST /mcp` JSON-RPC endpoint (`services/semprec-api`), both dispatching through a new shared `GenericOperationGateway` (`packages/application`) over the neutral `GenericApplicationPort` from #219.

- `createGenericOperationAgentTools` / `listGrantedGenericOperationAgentTools`: one AgentTool per generic operation, actor identity derived exclusively from the persisted `agent_run` row (`runId`, `agentProjectItemId`, `actorUserId`), never from tool input.
- `POST /mcp`: `tools/list` / `tools/call` over the same catalog, tool names prefixed `semprec.`; actor derived from the authenticated session/Bearer context.
- `GenericOperationGateway`: shared capability gate (absent-not-forbidden for ungranted operations) and approval interceptor — a destructive agent-originated call queues a pending approval request through #32's writer and returns a synthetic success; REST/MCP surface it as a transport-level error. `replayApprovedGenericOperation` handles the approved-request replay, rejecting provenance mismatches as `owner_violation`.
- `agent_runs.actor_user_id`: added nullable, backfilled via a post-migration cutover (parent-chain walk, then sole account), then set `NOT NULL`.
- Registered the eight core capability ids on the schemaCore module manifest and projected them through `permissionManifest.grantedCapabilities`.
- Full test coverage across all three layers, including spoofed-actor rejection, capability filtering, approval/replay, and MCP JSON-RPC error/success projections.

## Review round (2026-09-18): findings A–H

The bot's review output was lost in transport for this round, so its 8 findings (A–H) were relayed as text rather than posted as PR review threads. Handled directly here, no GitHub threads to reply to:

**Fixed:**
- **G** (`ApprovalRequestSafeSummary.mcpToolRegistrationId`/`mcpServerItemId` widened to optional): the backend type was already an all-optional shape, but the web client's Zod schema (`web/src/api/approvalQueueOperations.ts`) still required those two fields unconditionally. Every generic-operation-originated approval entry — i.e. every pending destructive agent write, the exact thing this queue exists to surface — failed `safeParse` and rendered as a malformed placeholder, hiding the Approve/Reject controls. Fixed by replacing the all-optional shape with a discriminated union (`kind: "mcpInvoke" | "genericOperation"`) on both the backend type and the web Zod schema, with matching test coverage in `approvalRequestsQueue.test.ts`, `approvalQueueOperations.test.ts`, and `ApprovalQueue.test.tsx`.
- **C** (unchecked cast of `canonicalInput`, `operationName`) — half of this was already fixed (see below); the remaining half was real: `replayApprovedGenericOperation` cast `canonicalInput as InputByOperation[typeof operation]` instead of validating it. This contradicted the function's own doc comment and issue #220's Task text, which says replay bypasses *only* the approval check, never validation. Fixed by routing it through the operation's own `parseInput` instead of a cast, so schema drift between queue time and replay time (e.g. a deploy landing in between) fails cleanly as `validation_failed` rather than an unchecked cast reaching the binding. Added a regression test simulating a corrupted stored payload.

**Already fixed on this branch (commit `48d05a3`), rebutted with evidence:**

- **C** (operationName cast): `assertGenericOperationName` already validates the DB-sourced string before use; not a raw cast.
