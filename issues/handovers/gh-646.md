## Summary

The API queue runtime now runs approved generic operations. When an `approvalExecute` job arrives for an approved generic-operation request (for example an agent's `item.delete`), the operation executes and the request ends as `succeeded`. Before this change it always ended as `conflict` with "No generic-operation approval replay handler is configured for this worker."

### Changes
- **`backend/services/semprec-api/src/queueRuntime.ts`**
  - Imports `replayApprovedGenericOperation` from `@semprec/application` and passes it to `createApiCoreTaskList` as `genericOperationApprovalReplay` (position 11).
  - `pushSenders` (position 10) stays `undefined`, with a comment naming it.
  - The docstring now says the approval replay is wired. The adapters still on their no-op defaults are the library metadata fetcher, the mail sync transports and the push senders.
- **`backend/services/semprec-api/src/__tests__/approvalReplayComposition.test.ts`** (new, integration tier)
  - Setup follows `genericOperationGateway.test.ts`'s `createPendingDeleteAndApprove`: seed the system, create an account, an item and a persisted agent run, then call `item.delete` through `createGenericOperationGateway`. The test catches the `ApprovalRequiredError` and approves the request with `decideAndEnqueueApprovalRequest`.
  - It then starts `createApiQueueRuntime(pool, await loadFullModuleRegistry())` and waits until `execution_status` is terminal.
  - Assertions:
    - the status is `succeeded`
    - `executed_at` is set
    - `execution_result.result.id` equals the item id
    - the "No … replay handler is configured" text does not appear in the result
    - the item is gone
  - **Redelivery:** the test enqueues `approvalExecute` a second time for the same request, waits for that job to drain, and asserts the request row is exactly the same.
