## What was delivered

Three agent tools of the `schemaCore` module that change a project's heartbeat automations. Each is declared `requiresApproval` with a `snapshotExport`, so an agent session only creates a `moduleTool` approval request and the handler runs after the person approves, once, through the gh-1791 claim.

- `heartbeat.create`: a new automation of origin `user` with action `core.agentRun` and `action_config.task`, in a live Projects item inside the run's scope. The rule goes through `parseHeartbeatRule`, which includes the rule kinds of active modules.
- `heartbeat.update`: name, task and rule; `heartbeat.setEnabled`: the enabled flag. Both lock the row, require it inside the run's heartbeat scope and origin `user` (a system automation is a tool error with no write), and apply in one transaction.
- The snapshot hashes name, rule, `action_config` and enabled (for create: the existence of the project). A change between request and approval yields the execution status `conflict` and writes nothing.
- After commit the tools announce `projectAgent` (once) and, when the heartbeat already has a tick thread, `sempThread`.
- Review fix: the approval description shows what will be written. It carries the stored form of the rule (the result of `parseHeartbeatRule`, cut to 300 characters; a module rule kind shows its kind alone; an invalid core rule is refused), a task excerpt (500 characters with a marker) and, for update, each changed field with its new value. A Semp chat run reaches the same projects as the heartbeat read tools minus the projects excluded by the sensitive-grant rule, and `heartbeat.create` applies that exclusion to the target project too.

## Deviations and spec seams

1. The factories are in the sibling file `heartbeatWriteAgentTools.ts`, not in `heartbeatAgentTools.ts` as Touches say; the run-scope helper moved to `heartbeatRunScope.ts` so the tools and the description builder share it.
2. `schedulerStore.ts` needed only the new `isProjectReachableByChatRun`; the origin argument and the name and task store functions already existed. An update of name or task alone announces `projectAgent` from the tool, because the store does not.
3. The "snapshot mechanism of #1683" is the description built in `createModuleToolApprovalRequest`, a file outside Touches; the templates are also in `notifications/i18n` because `approvalNotificationBody` throws for an unknown description key.
4. The Task says `projectItemId` can be any project of the tenant. The tools follow the read scope of the heartbeat tools, so a project run reaches its own project only and a Semp chat run every project of the tenant minus the sensitive exclusion. A project or automation outside the scope answers as not found; this is stricter than the literal text for non-chat runs.
5. A system automation, an unknown or invisible automation and a rejected rule are refused by the snapshot, so no approval request exists and the agent session reports "Module tool failed." The handler repeats the checks and returns the tool error.
6. `heartbeat.create` has a snapshot (the project's existence) although no automation exists yet; a trashed project is a conflict.
7. The `sempThread` invalidation is published only when the heartbeat already has a tick thread, so create announces only `projectAgent`.
8. The candidate's commit trailers name Claude Sonnet 5.5 instead of the line the task text names.
