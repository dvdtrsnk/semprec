## What was delivered

- `POST /api/trash/restore`, handler `createTrashRestoreRouteHandler(pool)` in `packages/data/src/trash/trashRouteHandlers.ts`. One `withTransaction`; databases are restored first, then items, each id in its own `withSavepoint`. Body: strict zod object with optional `itemIds` and `databaseIds` (UUID lists), at least one id and at most 100 after a case-insensitive duplicate merge, otherwise `400 validation_failed`. Response `200 { results: [{ id, kind: "item" | "database", status }] }` in request order, databases first.
- Per-id statuses: `restored` (also for an item that is not trashed and a database that is not archived), `not_found` (unknown or another tenant's id, or an item gone at its row lock, or a database gone at its row lock), `database_archived` (a `ForbiddenError` with code `database_archived`), `conflict` (any `ChokePointError` with status 409, for example the Journal restore hook). Any other error aborts the request and rolls everything back.
- `withSavepoint(client, fn)` in `packages/data/src/db/pool.ts`: `SAVEPOINT` / `RELEASE`; on an error `ROLLBACK TO` and `RELEASE`, discards the `runAfterCommit` callbacks, search-lane jobs and keyed slots queued since the savepoint began (earlier ones survive), rethrows the original error, marks the transaction rollback-only when the cleanup itself fails. It refuses a client that is not the active managed transaction's.
- `databaseRestoreWithClient(client, id, actingUserId)` in `chokePoint/databaseOps.ts`; `createDatabaseOps().restoreDatabase` uses it (its reader check stays before it). `restoreItemWithClient` was already exported from `itemTrash.ts`; only its docstring changed.
- `databasesStore.lockDatabase` (`SELECT id FROM databases WHERE id = $1 FOR NO KEY UPDATE`), the lock the purge takes, now decides `not_found` for a database, so a purge that committed first is `not_found` and a later one waits (review fix).
- ADR `docs/adr/2026-11-14-a-savepoint-step-discards-what-it-queued-for-after-the-commit.md`.

## Deviations from the specification and spec seams

1. The route entry is in the slice `routeMatrix/trash.ts`, not in `routeMatrix.ts`.
2. `packages/data/src/index.ts` (named in Touches) was not edited: nothing outside the data package needs `withSavepoint` or `databaseRestoreWithClient`, and `publicSurface.test.ts` freezes the barrel.
3. `withSavepoint` also discards keyed slots and search-lane jobs queued in the undone step, beyond the Task's `runAfterCommit` wording, because a stale keyed slot would swallow a later registration and a search job would be flushed for a rolled-back row. That needed the new ADR.
4. Unit tests of `withSavepoint` are in `withSavepoint.unit.test.ts` (fake connection) in addition to the named integration file `withSavepoint.test.ts`.
5. A database id is resolved with an in-transaction locked lookup (`lockDatabase`; null gives `not_found`) instead of catching `NotFoundError`, so an unrelated `NotFoundError` is never mapped; a database purged later than the lock waits for the transaction.
6. `itemIds` and `databaseIds` are both optional in the body; unknown keys are rejected; ids are lower-cased before duplicates are merged.
7. `conflict` is any `ChokePointError` with status 409 from an item restore.
8. The route reads `trashRouteHandlers.ts`, which gh-1903 also changed (count helpers `countTrashItemRoots` and `countArchivedTrashDatabases`); the two edits are in different functions and merged without conflict.
