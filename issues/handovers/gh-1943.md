## What was delivered

`POST /api/proposals/:id/reopen` (added by gh-1937) now also reopens a `confirmed` card. In one transaction it reverses the writes the confirmation recorded and returns the card to `proposed` with its envelope intact and `resultItemId`, `resultLabel` and `results` set to null. The answer carries `keptItems` (always an array).

## Entry points and contracts dependents build on

- `undoConfirmedProposalWithClient` in the new `inbox/undoConfirmedProposal.ts`, called from `reopenProposalWithClient` (`inbox/proposalReopen.ts`, re-exported from `proposalActions.ts`) for a confirmed card. Precondition, before any write and with the rows locked in id order after the card: every created, updated or page-inserted result item is live with the stored `updatedAt`; otherwise 409 `version_conflict` with `details { itemId, databaseKey, label }` (also when the item is in the Trash or gone). Then, in order: (a) delete the edges the confirmation recorded as inserted (`writtenRelations` of its history entry); restore the metadata of edges it replaced or removed (`removedRelations`); (b) restore the before values of update steps; (c) remove the inserted page blocks (`deleteBlocksWithClient` in `docs/docStore.ts`); (d) trash the created items with `itemDeleteWithClient` and remove their `item_origins` rows (`deleteItemOriginsOfProposal` in `inbox/itemOriginsStore.ts`); (e) delete the credential of a created MCP server. A failing step rolls the whole reopen back. A reopen of a `proposed` card still answers unchanged with `keptItems: []`.
- Confirm now records its edge writes: `inbox/proposalEdgeRecording.ts` (`createEdgeRecorder`, `writeRecordedEdge`, `deleteRecordedEdge`, `readEdge`, `edgeIsAsWritten`) writes link-step, update-step and transcript edges insert-if-absent then replace, and the confirmation's history entry (`inbox/proposalHistory.ts`) stores `writtenRelations` and `removedRelations`. The undo reverses only recorded edges, so an edge that already existed before the confirm survives the undo, and an edge the user changed since is left. A card confirmed before this change has no record and its edges stay in place (the side that loses no user data).
- `keptItems`: `KeptItem` (type, exported from `packages/data/src/index.ts`) is `{ itemId, databaseKey, label, reason }`; the only reason is `attachmentMovedToFiles`, for the Files item that received an Inbox attachment, which stays live (it is the user's file). `adapter/adapterRoute.ts` carries `keptItems` in the item envelope (`AdapterHandlerResult` and `CustomRouteResult` got an optional member).
- A card closed by `settleSpeakerCardWithClient` (manual speaker assignment) records no edges, so nothing is reversed or checked, per the 2026-11-12 ADR.
- ADR `docs/adr/2026-11-14-the-undo-of-a-confirmation-reverses-only-the-edges-it-recorded.md` narrows the 2026-10-25 undo ADR.

## Deviations from the specification and spec seams

1. Production code lives in the Touches file `undoConfirmedProposal.ts` and the sibling `proposalReopen.ts` (the 900-line cap).
2. The Task says use `deleteBlock` of `docs/blocks.ts`; page order must stay consistent, so removal uses the block-model `deleteBlocks` through the new `deleteBlocksWithClient` (outside Touches).
3. `keptItems` needs a member of the item envelope, so `adapter/adapterRoute.ts`, the `CustomRouteResult` type and `index.ts` changed (outside Touches); `keptItems` is present, empty, on every reopen answer.
4. Not reversed, and documented in the ADR and the module: the Events item that a synthetic occurrence target materialised (trashing it would read as a cancelled occurrence), and the Trash release of an earlier trashed Event edge (a relation to a Trash endpoint cannot be recreated). A removed edge whose target was trashed since refuses the undo. Items the confirmation only linked are not part of the `updatedAt` precondition.
5. Edges written from a created item stay with it (restoring it from the Trash brings them back); edges written from an existing item are deleted even when their target is a created item.
6. The gh-1937 test of the confirmed refusal was replaced by the gh-1943 tests. Two test additions outside `inboxRouteHandlers.test.ts`: `adapterRoute.test.ts` (keptItems serialization) and the reopen case of `tenantIsolationRoutes.test.ts` (asserts `keptItems: []`).
7. Job cancellation (gh-1984) is out of scope and not delivered: a transcription or MCP sync job queued by the confirmation is not cancelled by the undo.
