# Handover: push local changes of synced events to the provider

Implementation commits on `feat/internet-accounts`: `5cbe2ec65` (shared adapter contract) and `c3213ef9d` (write-back).

**What changed.**
- Shared adapter contract (`calendar/sync/adapter.ts`):
  - `CalendarSyncEventConflictError` is the one 412 / ETag-mismatch error of all three adapters. The CalDAV class in `caldavErrors.ts`, Google's `GoogleCalendarEventConflictError` and Graph's `ConflictError` `calendar_remote_conflict` are gone. `GooglePutRemoteEventInput` is gone too.
  - `PutRemoteEventInput` has two new optional fields:
    - `icalUid`: Google `iCalUID`, the CalDAV `UID` of a new resource (the file name stays a random UUID). Graph ignores it.
    - `seriesRef`: the series of a new override.
  - New `getEvent(calendar, ref, { window, signal })`: the provider's current version, or `null` when it is gone or cancelled.
  - New optional `moveEvent(from, to, ref, signal)`. Only Google has it.
  - New `CalendarSyncWriteUnsupportedError`; `GraphCalendarWriteUnsupportedError` extends it.
  - `CalendarSyncAccount.tenantTimeZone`.
- Graph:
  - Graph names a zone with a Windows id. When the tenant's IANA zone has the same Windows id, Graph reads it as the tenant's zone (a Prague tenant gets `Europe/Prague`, not `Europe/Budapest`).
  - An Event without its own zone is written in the tenant's zone.
  - A new override is a PATCH of the series' occurrence found through `instances`. An occurrence the series does not have is `GraphCalendarWriteUnsupportedError`.
- Google:
  - `getEvent` reads the event, `calendarList/{id}` (zone and default reminders) and, for a series, its cancelled instances.
  - `moveEvent` is `events.move` with `sendUpdates=none`.
  - A new override patches the instance whose original start matches `recurrenceId`, read through `instances` around that day.
- CalDAV:
  - `getEvent`.
  - A new override is written into its series' resource.
  - The single-resource read is a plain GET (`fetchResource`) instead of a one-href multiget. tsdav's multiget fails as a whole on a 404 member, so a put or delete on a gone resource used to be `unexpected` instead of a conflict.
  - `fakeCalDavServer` serves GET.
- Baseline, edited in place:
  - New table `calendar_event_push_state`. Columns: `event_item_id` (PK `(tenant_id, event_item_id)`), `operation` `create|update|delete|move`, `desired_revision`, `status` `pending|sent|conflict|failed`, `attempts`, `last_error_code`, `updated_at`.
  - The table has tenancy=tenant, both RLS policies, the tenant FK, an item FK with `ON DELETE CASCADE DEFERRABLE INITIALLY DEFERRED`, a partial index on pending rows and grants to `alldots_side`.
  - `notifications_kind_check` gains `calendar_change_overwritten`.
- Notification kind `calendar_change_overwritten`: category `calendarChanges`, pushed. Title `{calendar}`; body key `calendarChange.overwritten` in en and cs. APNs gets `event_id`/`calendar_id` through the existing category rule.
- Queue task `calendarEventPush`: tenant scope, `api`, key `calendar-event-push:<event>`, replace mode, `maxAttempts` 10. The handler is in `worker.ts`.
- Hooks (`calendar/sync/eventPushHooks.ts`, registered in `domainWriteHooks.ts`). They fire on any writer except `systemProcess === "calendarSync"`:
  - a create, after `defaultCalendarCreateHook`;
  - an update naming `name`, `date`, `endDate`, `timeFrom`, `timeTo`, `place`, `description`, `url`, `alertMinutes` or `recurrence`;
  - a trash or a restore;
  - an edge created or deleted on `Events.calendar` / `Calendars.events`.
- What a hook records: it upserts the push row (`desired_revision + 1`, `pending`, attempts 0) and enqueues the job, in the write's transaction.
  - An Event the sync never had, outside writable tracked account calendars, records nothing.
  - So does a system write to an Event of a read-only or untracked calendar that the provider holds there.
- Trash and restore hook contexts now carry `systemProcess` (`chokePoint/itemTrash.ts`, `hooks.ts`), and the calendar trash cascade passes it on (`calendarTrashHooks.ts`). Without this, a cleanup trash by the sync would have pushed deletions.
- Job (`calendar/sync/eventPushJob.ts`):
  - A read transaction decides what the provider needs. The adapter calls run with no transaction open.
  - Each result is stored in its own transaction. It takes the account's calendar sync guard (≤ 30 s), then the Event's account calendar `FOR SHARE`, then the Event row. The status is set only while the pushed revision is current. Remote state is always stored, because the provider took the write.
  - After a push the sent fields become `base_snapshot`, so the next fetch is unchanged and nothing is notified. Participants are kept from the old base.
  - Sent fields: a timed Event without a zone goes in the tenant's zone, and a `recurrence` rule is serialised to an RRULE (`FREQ=WEEKLY;BYDAY`, `FREQ=MONTHLY;BYMONTHDAY`, `FREQ=MONTHLY;BYDAY=nXX`).
- How the job handles each case:
  - **Create** uses the Event's `icalUid`. A remote id that a racing sync pass already stored as another Event: that duplicate is trashed as the sync.
  - **Update** is skipped when the local fields equal the base.
  - **Conflict on update:**
    1. `getEvent` reads the provider's version.
    2. `mergeEventFields` (`eventMerge.ts`) merges per field against the base: local wins where the remote is unchanged, remote wins where it changed.
    3. A field changed on both sides to different values counts as overwritten. That writes one `calendar_change_overwritten`, deduped by the remote etag.
    4. The merge is applied locally as the sync, and the base becomes the remote version.
    5. The merge is pushed once more. A second 412 is `conflict` / `remoteConflict`.
    - A remote deletion wins: the Event is trashed as the sync, and the user is notified if a local change was lost.
  - **Delete**: a conflict re-reads the Event and deletes it once more at its current etag.
  - **Move**:
    - Google uses `moveEvent`, then the update.
    - Otherwise the job deletes in the old calendar and creates in the new one, with `icalUid` = the old remote id within the same account, or the Event's `icalUid` across accounts.
    - A series or an override is not moved (`failed`, `moveUnsupported`).
  - **New override**: `putEvent(ref null, seriesRef)`. If its series has no remote state yet: `failed`, `seriesNotSynced`.
  - **Cancelled occurrence** with no remote override: the master is put with the extra exception date, and the date is also written to the master locally as the sync.
- Failures:
  - `CalendarSyncWriteUnsupportedError`: `failed` / `unsupported` at once.
  - Reauthorization or consent: attempt counted, row stays `pending`, the account's `calendar_account_sync_state` and Semp `calendarSyncError` are recorded (`recordCalendarAccountFailure`, no rethrow).
  - Provider or unexpected: counted and rethrown. On the 5th attempt the push is `failed` with the code.
- Apply (`calendarSyncApply.ts`):
  - Per calendar it takes the calendar `FOR SHARE`.
  - Before writing or trashing an Event it locks the Event row and reads its push state. A pending push is left untouched, with no item or remote-state write, and its job is re-queued.
  - It also re-queues pending pushes of the target calendars whose last error is `reauthorizationRequired` / `consentRequired`.
- Zone edit (`calendar/zonedEventEdit.ts`): an Events pre-write transform registered right after the time transform. It applies to a user or agent update of `date` / `endDate` / `timeFrom` / `timeTo` on a timed Event whose `timeZone` differs from the tenant's. It shows the stored schedule in the tenant's zone, lays the patch over it, converts back and recomputes `time`. An all-day result is not moved. The calendar sync and other system writers store their values as sent. Its preparation is the identity, so the executed write converts.
- Shared helpers:
  - `calendarAccountSyncJob.ts` exports `readCalendarSyncAccount`, `openCalendarSyncAdapter`, `recordCalendarAccountFailure`, `failureRecordOf` and `syncWindow`; the pass uses them.
  - `calendarSyncStore.ts` gains the push-state functions and lookups.
  - `upsertEventRemoteState` now also updates `calendar_item_id` and `remote_id` on conflict.
  - `itemsStore.lockItemForShare`.
- Docs:
  - `transactions-and-side-effects.md` (Provider write-backs).
  - `domain-calendar-tasks-and-media.md`: Adapters, Graph, CalDAV, Apply, the new Write-back bullet, Event times and zones.
  - The FK table in `data-model-and-writes.md`.

**Deviations and spec seams.**
- **Item 5:** the apply does not write an Event whose push is pending. It re-queues the push, whose conflict path fetches the provider's version and merges.
- **Snapshot after a push:** it holds the fields that were sent, not a snapshot the provider returned. `putEvent` returns only a ref, and Google and Graph cannot give a series' exception dates from a write response. If a provider normalises a value it was sent, the next fetch shows that as a change.
- **CalDAV move:** it deletes then creates (keeping the UID), not PUT then DELETE, so a retry needs no extra state. If the create fails after the delete, the retry creates with the Event's own `icalUid`.
- **Not moved:** series and overrides (`moveUnsupported`).
- **Delete conflict:** a trash still wins; the job deletes again at the current etag, without a per-field merge.
- **Remote deletion vs. a local edit:** the remote deletion wins.
- **Waiting for the account:** a push that waits on reauthorization or consent still counts attempts. It is re-queued only by a later pass that reaches the provider.
- **Store result vs. a running pass:** storing a result waits up to 30 s for the guard while a pass runs. Past that the attempt is retried and the write is repeated. A create can then be duplicated at Google; Graph dedupes by `transactionId`, and CalDAV may refuse the UID.
- **Agent approval:** the application gateway's approval for agent operations is unchanged. The data-layer test covers the approved replay and a direct agent update; the gateway's approval gate itself is not re-tested here.
- **Touches:** files changed beyond the issue's list are the adapters, `adapter.ts`, `calendarAccountSyncJob.ts`, `calendarSyncStore.ts`, `calendarAccountSyncEnqueue.ts`, `chokePoint/hooks.ts`, `itemTrash.ts`, `itemsStore.ts`, `calendarTrashHooks.ts`, `zonedEventEdit.ts`, `worker.ts`, queue `index.ts`, the fakes, the two other docs and the test expectations.
