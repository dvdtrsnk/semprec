# gh-1482 — [inbox-editing 05/23] Store a structured invalidReason and separate fixable from final invalid cards

## Delivered behavior

- **Reason shape** (`backend/packages/data/src/inbox/inboxTickAction.ts`): `invalidReasonSchema` (zod) and the type `InvalidReason` are exported. `code` is one of `sourceDeleted`, `targetArchived`, `targetDeleted`; `field` is a string (empty for the source); `itemId` is a non-empty string; `label` is a string. `isFinalInvalid(properties)` is true only when `status` is `invalid` and the stored `invalidReason` parses with `code` `sourceDeleted`. Both names are re-exported through `packages/data/src/index.ts`, so they are part of the package's runtime surface.
- **Deleted source** (`invalidateProposalForDeletedSource`, same file): the unlocked card becomes `status` `invalid` with `invalidReason` `{ code: "sourceDeleted", field: "", itemId: <source id>, label }`, and one history entry with `author` `ai` and `kind` `invalidated`. `invalidReason` is added to the write's `allowedSystemKeys`.
- **Label**: the first line of the source's text, trimmed, at most 80 characters counted by code point, a longer one ending with `…`. A source with no text, or a hard-deleted source row, gives the empty string. The label is captured when the card is invalidated and is not updated afterwards.
- **Revise** (`reviseProposalWithClient`, `backend/packages/data/src/inbox/proposalActions.ts`): a card for which `isFinalInvalid` is true is refused with a `ValidationError` whose `details.field` is `status`, before any write. The card is unchanged. A fixable `invalid` card (any other reason, or none) is revised as before, and the same `updateItemWithClient` call sets `invalidReason` to `null`. `invalidReason` is added to that write's `allowedSystemKeys`. A card that is not `invalid` gets no `invalidReason` key in the write.
- **Sentence** (`backend/packages/data/src/inbox/invalidReason.ts`, new): `renderInvalidReason(reason, locale): Promise<string>` picks `invalidReason.<code>` from the Inbox catalog for the locale (`toManifestLocale`), falls back to `en` through `resolveCatalogLabel`, and fills `{label}` through a replacer function, so a `$` in the label stays literal. The catalogs are loaded once per process, the same way `auth/authMailCatalog.ts` loads its own.
- **Catalog**: `invalidReason.sourceDeleted`, `invalidReason.targetArchived` and `invalidReason.targetDeleted` in `backend/packages/data/src/inbox/i18n/en.json` and `cs.json`. `sourceDeleted` names the item and says the proposal can no longer be completed. The two fixable sentences end with the offer to choose another target or ask Semp to recompute.

## Deviations from the Task

- `renderInvalidReason` is `async` and returns a `Promise<string>`, because `loadModuleCatalogs` reads the JSON files asynchronously. The Task did not state a return type.
- The 80-character label cap is my choice; the Task asked for an excerpt without a length.
- `packages/data/src/__tests__/publicSurface.test.ts` gained `invalidReasonSchema` and `isFinalInvalid` in its sorted runtime export list. The Task did not name this file, but `index.ts` re-exports the whole of `inboxTickAction.ts`, so the frozen list had to change.
- `renderInvalidReason` is not exported from `index.ts`. Nothing outside the data package needs it yet.

## Notes for dependants

- **Only `sourceDeleted` is written so far.** `targetArchived` and `targetDeleted` are written by #1916. Until it lands, the fixable branch is reached only by a card that holds such a reason written through the choke point, as the revise test does.
- **The tick's own writes do not clear `invalidReason`.** `reviseProposal` and `writeNeedsClarification` in `inboxTickAction.ts` write `status` `proposed` or `needsClarification` with `allowedSystemKeys` that exclude `invalidReason`. A card that leaves `invalid` through the tick keeps its stored reason while its status is no longer `invalid`. `isFinalInvalid` is then false, so revise is not affected, but the stored value is stale. #1604 (returning to `proposed` when the source is restored) and #1916 must clear it when they write those transitions.
- **The tick does not guard final cards.** When the source exists again and is not deleted, `readTickSnapshot` recomputes an unlocked `invalid` card whose stored fingerprint no longer matches, and `reviseProposal` then sets `proposed` with the reason still stored. A card whose fingerprint still matches stays `invalid`. The refusal in `reviseProposalWithClient` covers only the chat-driven revise route. This is existing behaviour, and #1604 owns it.
- **An empty label renders as an empty pair of quotes.** A hard-deleted source gives `label` `""`, and `renderInvalidReason` then produces `The source Inbox item “” was deleted…`. The sentence does not yet handle that case; a decision is needed if it can happen in practice.
- Catalog keys are `invalidReason.<code>`, which are unique across modules (the catalog loader rejects duplicates, and the coverage test loads every module).
