## What it does

`runHarvest(api, { minPr, dryRun })` does these steps in order:
1. **Backpressure.** If any open issue carries `followups:harvest`, or both `followups:issue` and `spec:proposed`, it returns `pending` and makes no other call.
2. **Ledger.** It builds the ledger from every `followups:harvest` issue (with its comments) and every `followups:issue` issue, in any state, and reads the `develop` tree.
3. **Scan.** It goes through the merged pull requests from `minPr` up that lack `followups:harvested`, in ascending order:
   - A pull request already listed in a harvest issue's marker is only labelled.
   - A trusted review memory that cannot be decoded fails the run before any write, with an error naming the pull request.
   - Review threads are read only when an open finding not yet in the ledger has a numeric thread id.
   - The scan stops at the first pull request the cap of 30 refuses.
4. **Hints.** It adds `touchedAfterLastSeen` and `laterPrsTouchingPath` to each harvested record and checks every record with `validateFindingRecord`.
5. **Render.** It builds the title and body. A body over 60,000 characters fails the run before any write.
6. **Write** (skipped in a dry run). It creates the issue first and only then labels every planned pull request `followups:harvested`:
   - with harvested findings, the issue gets `followups:harvest` and `followups:ready`;
   - with only skipped findings, it gets `followups:harvest` only and is closed at once;
   - with no findings at all, no issue is created.

The body starts with the harvest marker, then:
- a sentence naming the workflows that collect and triage the issue;
- the "Findings to triage" and "Skipped — fixed on the pull request" tables;
- one finding marker per line;
- the data block from `renderHarvestBlock`.

In table cells, `|` becomes `\|`, newlines become spaces and `<` becomes `&lt;`, so text from a finding cannot form a marker line.

`main(env, api)` checks `HARVEST_MIN_PR` (a positive integer) and `DRY_RUN` (exactly `true` or `false`) before building a client. It prints the report and appends it as Markdown to `GITHUB_STEP_SUMMARY` when that is set. Run directly, the module prints any error and exits 1.

## Choices worth reviewing

- **Pending report shape.** When the run is held back, the report still has every field; `pending` is filled and the rest are empty or `null`. The text and summary output then need only one format.
- **Title wording.** The title says "1 finding" or "N findings" rather than the literal "finding(s)".
- **Empty findings table.** In a record-only issue, the "Findings to triage (0)" section shows `None.`, like the empty Skipped section does.
- **Record-only crash gap.** A crash between creating a record-only issue and closing it leaves an open `followups:harvest` issue with no `followups:ready`. No triage picks it up, so it holds back every later harvest until someone closes it by hand. GitHub cannot create an issue already closed, and changing the backpressure rule belongs to `select.mjs`, which is out of scope here. The header comment says this plainly instead of claiming the run is always safe to repeat.

## Tests

`harvest.test.mjs` uses an in-memory fake `api` that records every call and every write, and covers all Acceptance criteria:
- backpressure makes only the two open-issue listings;
- pull requests below the floor or already labelled are never read;
- an undecodable memory rejects the run with no write;
- the 12/15/5 cap case takes the first two pull requests' 27 findings;
- the issue is created before any label, and a failed `createIssue` labels nothing;
- ledger reuse, the record-only issue and the empty run;
- the markers and data-block round trip, including the hint fields;
- the escaping case, the 60,000-character limit and the dry run;
- `main`'s input checks and its step summary.
