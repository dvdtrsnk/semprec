## Which Task step applied: step 3 (the lifecycle adapter is not at fault; the test hook reordered delivery)

**Evidence:** `runAgentSession` in the lifecycle adapter awaits each `agent_run_events` write before starting the next. So two event writes for one run are never in flight at once, and `id` order matches commit order. What reordered delivery was the test's own hand-rolled agent-run hook. It fired `publishRealtimeMessage` for each event without waiting for the previous one, so each `pg_notify` ran on its own pooled connection. Under load, those NOTIFYs could commit, and so be delivered, out of order, which explains the observed `[1, 3, 2, 4, 5]`. Production's `wireRealtimeHooks` chains one run's publishes through a per-run tail promise, so it does guarantee ordered announcement. The test now uses that production hook and keeps the ordered `eventId` assertion. No production code changed.
