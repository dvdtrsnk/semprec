## What was delivered

The tenant-wide `overview` realtime scope end to end and its publisher, announced at the end of the nightly day rollover.

- `InvalidationEvent` gained `{ scope: "overview" }`; `RealtimeMessage` and `parseRealtimeMessage` accept it with no user; `OutboundFrame` gained `{ type: "invalidate"; scope: "overview" }`; `syncServer.ts` sends it with `sendToTenant(tenantId, frame)` to every socket of the envelope's tenant; `parseServerFrame` parses it and keeps nothing but `type` and `scope`.
- `overview/overviewInvalidation.ts` exports `publishOverviewInvalidation(client)`, which defers `notifyInvalidation({ scope: "overview" })` with `runAfterCommit`. It must run inside the tenant's scope, which the publisher reads the tenant from.
- `createTasksDayRolloverAction` publishes it once, in its own final `withTransaction`, after the recurring closing passes and both chunk passes have committed, whether or not a task moved (the number of tasks for today changes with the day itself). A run that throws before that point (a rolled-back chunk, an invalid config) announces nothing.

## Entry points and contracts dependents build on

- Wire frame: `{"type":"invalidate","scope":"overview"}`, no other field, to every socket of the tenant whose rollover ran. The client refetches the overview numbers.
- Job behaviour: `core.tasksDayRollover` now always ends with one `overview` announcement per tenant run; a repeat run that moves nothing still announces once (an existing test that expected no events was changed accordingly).
- `publishOverviewInvalidation(client)` is exported from `overview/overviewInvalidation.ts`, not from the `@semprec/data` barrel (`index.ts` is at its line cap).
- No table, migration, route, operation or job name was added.

## Deviations and spec seams

1. The Task allows the call after the writes are committed or in the transaction that holds them; the run has no single transaction (each chunk and closing pass has its own), so the publication is its own final transaction.
2. The existing test "leaves a weekly occurrence open before its next day..." asserted that a repeat run sends no events; it now asserts exactly one `overview` event.
3. The data-level tests use a temporary trigger on `items`, created and dropped in the test, to force a chunk to fail.
4. The serverFrame tests are in `serverFrame.unit.test.ts`.
5. The realtime end-to-end test runs the action over an empty `tasksDatabaseId`, so the frame is the whole of what the run announces; the moved-task behaviour is covered in `tasksDayRollover.test.ts`.
