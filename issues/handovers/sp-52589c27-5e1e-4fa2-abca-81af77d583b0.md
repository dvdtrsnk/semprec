# Handover: lock the endpoint rows of a relation delete before reserving its value links in the approval check

Delivered on chain `e1-238-value-link-locks`, candidate commit `2a30a51923336051170e98a1ed73ef0cb6a82b9a`, landed by a `--no-ff` merge on `feature/backend-parallel`.

**What changed.** In `backend/packages/data/src/chokePoint/destructiveProjection.ts`, the `relation.delete` case of `computeDestructiveResourceProjection` now calls a small helper, `lockEdgeEndpointRowsNowait`, after the edge is read and before `reserveEdgeLinks`. The helper locks the edge's two endpoint item rows with `lockItemByIdNowait` (`FOR UPDATE NOWAIT`): the caller's row in the property's database and the target's row in the target database, sorted by database id and then item id, as the `relation.put` and `relation.set` case does. A missing row is skipped (an edge to a purged item can still exist). SQLSTATE `55P03` becomes `ApprovalResourceBusyError` after `markManagedTransactionRollbackOnly`; any other error propagates. The snapshot, `currentResource` and `valueLinks` of the result are unchanged, so the snapshot hash is unchanged. The item ids are lowercased before locking and sorting, as the put/set case does (relation.delete had not lowercased them before).

**Why.** The replay of an approved agent `relation.delete` of a link rule's via relation held the share lock of the `on` value link (from `reserveEdgeLinks`) and then waited, in the write's before-link-break hook, for the rule's target item row. A propagation job holding that row and wanting the link ended the schedule with `40P01`. With the endpoint rows locked first and without waiting, the replay is refused as busy and the propagation commits. Reproduced with the production calls on runtime-role pools; the new lock-order test fails with outcome `deadlock` on the tree without the change.

**Contracts dependents build on.** No new export, route, operation, table, migration or job name. Behaviour a caller may now rely on: a `relation.delete` approval check (a request-time projection or a replay) is refused as `ApprovalResourceBusyError` (`approval_resource_busy`) at once, with no wait, while another transaction holds the row of either endpoint of the edge, also for a relation that is no rule's via relation (put and set already behave so). The approval queue retries the replay. The projections of `relation.put`, `relation.set` and the other kinds are untouched.

**ADR.** `docs/adr/2026-11-15-the-approval-check-of-a-relation-delete-locks-the-edges-endpoint-rows-before-it-reserves-its-value-links.md` (area backend, supersedes none, standalone) states the lock order of the approval check for the three relation kinds and the busy-refusal consequences. It references the three accepted ADRs it repairs or builds on and edits none of them. It states what was measured and what was not.

**Files.** `backend/packages/data/src/chokePoint/destructiveProjection.ts`, `backend/packages/data/src/__tests__/relationDeleteApprovalLockOrder.test.ts` (new), `backend/packages/data/src/__tests__/destructiveResourceProjection.test.ts`, the new ADR.

**Tests.** `relationDeleteApprovalLockOrder.test.ts`: the replay of a `relation.delete` against the propagation job that holds the transcript row ends busy, the propagation commits and there is no `40P01`; the same schedule for `relation.put` and `relation.set` ends the same way (pins them unchanged); with nothing held the replay commits and ends the edge and its link. `destructiveResourceProjection.test.ts`: busy at once and rollback-only while the caller's row is held and while the target's row is held, not refused for a bystander row, the snapshot hash equals one derived independently when no row is held, and an edge whose other endpoint row no longer exists still projects. The worker saw the lock-order schedule end in deadlock and the two held-row cases fail with the production change reverted.

**Deviations and spec seams.** No spec seams. In `destructiveResourceProjection.test.ts` the file-level `afterAll` that ends the pool moved from inside the first `describe` to module level so the new `describe` can use the pool. The lowercasing of the item ids is described above. The Task's reservation order of the write's own item lock is documented as already held, because the before-link-break hook locks an endpoint of the written edge.

**Criteria NOT RUN or BLOCKED.** None. Not measured, and stated as such in the ADR: the replay through `replayApprovedGenericOperation` itself with an approval request row, and an agent with grants.

**Review.** Requirements and tests lens: clear, no finding. Rules and architecture lens: clear, no finding. No security review was run by the program for this chain, although the source sits on the destructive-approval path. No fix round. The non-`55P03` propagation branch of the helper has no test of its own, which the Task does not require.
