## Summary

**`.github/scripts/review-followups/publish.mjs`**: a zero-dependency ES module and CLI.

- **`publishProposal(api, { input, proposal })`** first runs every check that writes nothing:
  - `validateProposal` must return no violations; the error lists them.
  - No `(pr, key)` of the proposal may already be in the ledger's `terminal` set. The ledger is built from every `followups:issue` issue plus issue H and its comments. If one is there, it throws "stale, restart from prepare".
  - The triage-result comment, rendered with every number as `#999999`, must fit in 60,000 characters.
- **Then it writes, in this order:**
  1. The epic: it reuses `ledger.epics.get(H)` if there is one, otherwise it creates it labelled `followups:issue` with the epic marker appended.
  2. Each draft, in array order. It replaces every `{{draft:<id>}}` with the real `#<n>`, appends the finding markers and creates the issue labelled `followups:issue` + `spec:proposed`. It prints `created #<n> <title>`, then links the issue as a sub-issue of the epic by its `id`.
  3. The result comment on H, only when there are drafts or rejections.
  4. It removes `followups:ready` from H and closes it as completed.
- **Result comment**: result marker, `### Triage result`, `Epic: #n`, the list of created issues, the `#### Rejected (<count>)` table, one finding marker per rejection, and `#### Advisories`. Table cells escape `|`, turn newlines into spaces and write `<` as `&lt;`; reasons are clipped to 1,000 characters.
- **`main(argv, api)`** reads `--input` with `parseInputFile` and `--proposal` with `JSON.parse`. It uses `clientFromEnv` when no `api` is passed, and prints the summary as JSON. It returns exit code 1 on any error, after whatever it already printed.
- **Header comment**: explains the write order and why a restart from `prepare` is safe. Each write that publishes a finding carries that finding's marker, the epic is found again by its marker, and H stays open with `followups:ready` until the last step.

## Beyond the issue text

- **Extra pre-write check.** The issue doesn't ask for it, but it prevents a half-finished publish. The validator only checks draft order on the `**Blocked by:**` line. A `{{draft:x}}` elsewhere in a body that points to a *later* draft can't be resolved when that issue is created. `publishProposal` now rejects that before writing anything, and a test covers it.
- **Newlines collapsed.** Advisories and titles in the result comment have newlines turned into spaces. Otherwise an advisory could contain a line that `computeLedger` would read as a finding marker.
- **Gaps a restart doesn't repair.** The header states these instead of claiming full restart safety; in both cases the maintainer fixes it by hand:
  - A failure between creating an issue and linking it to the epic leaves that issue unlinked.
  - An epic created before a failure stays as it is if the restarted proposal has no epic.

## Tests (`publish.test.mjs`)

They use a fake in-memory `api` that records every call in order and can be told to fail the n-th call of any method. They cover all ten acceptance criteria:

- Invalid, stale (by issue body and by result comment) and oversized proposals, plus a forward placeholder: each rejects with no write.
- Write order and placeholder substitution, labels and markers.
- Epic reuse, and a single draft with no epic.
- Result comment content, and the ledger afterwards puts every drafted and rejected finding in `terminal`.
- No drafts and no rejections: no comment, but H is still closed.
- A failure mid-run, including the second `createIssue`: the first issue exists and H stays open with `followups:ready`.
- The CLI: success output, and exit 1 on bad arguments, unparsable or missing files, and an api failure after something was already printed.
