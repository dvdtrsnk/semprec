## Why

`integration-shard (1)` of CI run 36830666135 (push to `develop`, 2026-10-01) failed in `queueConcurrency.test.ts` with `expected 1790840083688 to be less than 1790840083686`. The test proved that unaffinitized jobs run concurrently by requiring two 300 ms probes to overlap in wall-clock time. That holds only if graphile-worker picks the second job up within 300 ms of the first, which graphile-worker does not promise. A `jobs:insert` notification nudges only a worker that is idle at that moment. A job no idle worker was nudged for waits until a worker frees up or the next 2 s poll runs.

The failing run's graphile log shows exactly this. Only two of the four workers ran jobs. Task 3 (the first unaffinitized job) started only after task 1 (a tick) completed, about 30 ms later, and task 4 ran after task 3 on the same worker. Production concurrency was not broken; the test measured pickup latency. Sharding (#657) is not a factor, because the file runs alone in its own vitest worker either way.

## What

- Each unaffinitized probe now stays in flight until both unaffinitized probes have started, bounded by `UNAFFINITIZED_OVERLAP_WAIT_MS` (5 s, above graphile-worker's 2 s `pollInterval`). It records whether the other probe started before it stopped waiting, and the test asserts both did (`[true, true]`). Comparing timestamps would be wrong here too: in the concurrent case the first probe's end and the second's start can land in the same millisecond.
- The `vi.waitFor` bound becomes `2 * UNAFFINITIZED_OVERLAP_WAIT_MS`. A serialized pair now takes over 5 s to finish, and the test should fail on the overlap assertion, not on the wait. This bound only shapes the failure path. The passing path finishes as soon as both probes have started.
- The semprec-tick half (the second tick run starts no earlier than the first one ended) is unchanged. That ordering is enforced by the named queue's lock, not by timing.
