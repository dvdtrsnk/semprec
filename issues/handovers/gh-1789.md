## What was delivered

- Message and frame types: `RealtimeMessage` gains `{ type: "invalidate"; scope: "approvalRequest"; approvalRequestId; userId? }`, `parseRealtimeMessage` (`packages/realtime/src/protocolV1.ts`) validates both ids as UUIDs and returns null otherwise, `InvalidationEvent` (`packages/data/src/realtimeHook.ts`) and the outbound frame carry the new scope, and `parseServerFrame` in `packages/realtime-client` validates the id.
- Routing in `packages/realtime/src/syncServer.ts`: an `approvalRequest` message is delivered only to sockets of the envelope's tenant whose user id equals the message's `userId`. A message with no owner is dropped with the warning `realtime_approval_request_without_owner` (type and scope only) and is never widened to the tenant.
- New module `backend/packages/data/src/mcp/approvalRequestRealtime.ts`: `publishApprovalRequestChange` reads the run's `actor_user_id`, `thread_id` and `tenant_id` inside the writing transaction (`requireManagedTransaction`), and registers through `runAfterCommit` the `approvalRequest` event for the owner and, when the run has a Semp thread, `publishSempThreadInvalidation` for that thread. `createPendingApprovalRequestAndPublish` publishes only when the row was actually inserted, not for a repeated (run, toolCallId).
- Publishing is wired after the pending insert in `preflightDestructiveApproval` and `createApprovalGatedMcpInvokeTool`, after a decided (approved or rejected, not unchanged, not null) decision in `decideAndEnqueueApprovalRequest`, after the generic conflict and success writes in `replayApprovedGenericOperation`, and, in `handleApprovalRequestExecuteTask`, after the no-replay-handler outcome, the stale-claim settlement and the MCP outcome. A discarded outcome, a request found already terminal, the claim write and a rolled-back transaction publish nothing.

## Contracts dependents build on

- Wire message and client frame: `{ type: "invalidate", scope: "approvalRequest", approvalRequestId }` (the frame to a client carries only the request id; the message on the channel also carries `userId` for routing). It is thin by design: the client refetches.
- Delivery rule: the owner is `agent_runs.actor_user_id`, the same column `getApprovalRequestForOwner` and `decideApprovalRequest` use. A run without an actor user (legacy run) serializes `userId` as null, fails validation and is dropped, so it fails closed.
- The `approvalRequest` event carries no tenant; Postgres stamps it from the publishing scope as for item invalidations. The paired `sempThread` event takes the run's `tenant_id` from `agent_runs`.
- Exports from `@semprec/data`: `createPendingApprovalRequestAndPublish`, `publishApprovalRequestChange`. `approvalRequestsStore.ts` gains `insertPendingApprovalRequest`, which reports whether it inserted; `createPendingApprovalRequest` delegates to it with unchanged behaviour.
- All three publishing processes (`semprec-api`, `semprec-agents`, the worker host) already call `wireRealtimeHooks`, so no new wiring was needed.
- No route, table, migration, job or operation.

## Deviations from the specification and spec seams

1. The publish helper is not inline in `genericOperationGateway` and `mcpInvokeTool`: both creation paths call `createPendingApprovalRequestAndPublish` from the new data module, because a repeated (run, toolCallId) returns the existing row and must not be announced; for that, `createPendingApprovalRequest` delegates to the new `insertPendingApprovalRequest`.
2. Task item 5 (publish through the `semprec-agents` publisher from #1383): no new wiring was needed, since `serve.ts` already calls `wireRealtimeHooks(pool)` and the event rides `InvalidationEvent`. `realtimeWiring.test.ts` proves it on the agents pool with `createPendingApprovalRequestAndPublish`, the function the `mcpInvokeTool` path calls; `mcpInvokeTool.test.ts` proves the tool calls it.
3. The `approvalRequest` event carries no tenant (the Task shape has none).
4. `userId` is optional in the message type as the Task specifies, but `syncServer` drops a message without one instead of broadcasting it, to keep delivery owner-only.
5. Existing tests that asserted an empty or unchanged invalidation list around approval writes (three assertions in `genericOperationGateway.test.ts`, a switch in `projectDerivedValueInvalidation.test.ts`) were adjusted because the union gained a member and those writes now announce the request.
6. `tenantIsolationRealtime.test.ts` (semprec-api) was extended because it is the two-tenant runtime-pool proof of the realtime surface; the Touches list names only `packages/realtime` tests.
