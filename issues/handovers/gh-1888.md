## What was delivered

`GET /api/semp/threads/:id/messages` now returns, for each message with stored changes (gh-1885), a `changes` array of cards. A page is resolved with a constant number of batched statements (about seven), independent of the card count.

- Card (`SempThreadChange`, `packages/shared/src/sempThreadMessage.ts`): `{ itemId, databaseId, change: "created" | "updated" | "deleted" | "restored" | "revised", changedKeys, before?, proposalId?, resolved: { label, databaseKey, state: "active" | "trashed" | "purged", values? } }`. `itemId` and `databaseId` are present in every state. `before` is the stored previous value and does not change as the item changes later.
- `resolveSempHistoryChanges(client, storedChanges)` (new `packages/data/src/semp/sempChangeHistory.ts`) validates the stored JSONB with a zod schema, resolves item, label, database key and state with the extracted `resolveSempItemRefs` (the item statement of the reference-history resolver, same SQL text, now exported from `semp/sempRefHistory.ts`), and reads the current values of the changed keys under the caller's tenant scope.
- An item in a sensitive database, or one that inherits sensitivity (gh-1999), resolves with label and state only: no `values` and no `before`. An item not visible in the tenant scope, an unknown id or a wrong database resolves as `purged` with no label and no values. A key the item holds no value for gives `null`; long values are bounded; a relation key of the item's database is left out of `resolved.values`, because a link is not a property value (and resolving link targets could expose sensitive or unreadable items).
- A message without stored changes, a reply that changed nothing and a delete still pending approval have no `changes` key. Entries that do not match the stored shape are left out.
- `listSempThreadMessages` attaches `changes` to any row with stored changes; the route handler passes rows through unchanged.

## Deviations and spec seams

1. The files named in Touches do not exist: the history endpoint is `GET /api/semp/threads/:id/messages` in `sempThreadsHandler.ts` (no change needed) and its mapper is `listSempThreadMessages`; the batched resolver is `semp/sempRefHistory.ts`; tests live in `sempThreadsHandler.test.ts` and `sempRefHistory.test.ts`.
2. The Task says one query per kind; the resolution uses a fixed number of batched statements independent of the card count.
3. Where the Task is silent: `values` is omitted for a sensitive and a purged item; `before` is also dropped for a currently sensitive item even if stored; the `changes` key is not filtered by role; a stored entry whose `databaseId` differs from the item's database resolves as purged.
4. At the merge with gh-1890, `listSempThreadMessages` was resolved by keeping both sides: the single parse of the stored steps and the outcome fields of gh-1890, plus `resolveSempHistoryChanges` and the `changes` field. The gh-1888 side called a `stepsOf` helper that no longer exists on the tree, so its steps spread was replaced by the gh-1890 one.
