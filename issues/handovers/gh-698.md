## Summary

Fixes #698. When `semprec-api` shuts down, it now closes the realtime sync server first. Before this change, every connected `/api/sync` socket kept `server.close()` from finishing, so each deploy restart:

- waited the full 60 s `SHUTDOWN_DRAIN_TIMEOUT_MS`;
- dropped clients with an abnormal 1006 instead of the 1012 their reconnect logic expects;
- left the sync server's `LISTEN` client for `pool.end()` to release, which ran out its 5 s bound and logged a failure.

### Changes

- **`backend/services/semprec-api/src/shutdown.ts`**
  - `CreateGracefulShutdownOptions` gains `syncServer: { close(): Promise<void> }`. It is a structural type, so tests can pass a fake, and the real `SyncServer` fits it.
  - `runShutdown` calls `syncServer.close()` right before `drainServer`. If that call rejects, the error is logged as `syncServer.close() failed` and shutdown carries on, the same way `queueRuntime.stop()` failures are handled. Closing first is safe because `SyncServer.handleUpgrade` rejects any upgrade that arrives after `close()` has run.
  - The docstring lists the new order: close the sync server (1012 to every client, `LISTEN` client released), drain HTTP, stop the queue runtime, end the pool.
- **`backend/services/semprec-api/src/serve.ts`**: passes `syncServer` into `createGracefulShutdown`. Nothing else in the file changed.
- **`backend/services/semprec-api/src/__tests__/shutdown.test.ts`** (new, integration tier). Each test runs a real `http.Server` whose `/api/sync` upgrade routing matches `serve.ts`. The sync server and the shutdown both use a separate `Pool`, so the shared test pool is never ended. Because the sync server's `LISTEN` client lives on that same pool, `pool.end()` finishing within its bound is part of what the tests check.
  - **One connected client:** a `ws` client signs in with a Bearer session. Shutdown with the default drain timeout finishes in under 5 s, the client receives close code 1012, the queue runtime is stopped once, the pool ends, and no error lines are logged.
  - **`syncServer.close()` rejects:** the fake first closes the real sync server, so its `LISTEN` client is released, then rejects. Shutdown still resolves, the HTTP server stops listening, `queueRuntime.stop` is called, and the pool ends. `syncServer.close() failed` is logged exactly once with the original error, and no `pool.end()` error is logged.
  - **No sync client connected:** the sequence runs as before (drain, queue stop, pool end) and logs exactly the two usual info lines.
