## Summary

Implemented issue #781: `syncMcpServerTools`'s `finally` block called `handle?.close()` unguarded, so a close failure after a sync failure replaced the original error (JS `finally`-wins semantics) before it reached the caller.

Fixed in `backend/packages/data/src/mcp/mcpSync.ts` by moving the close call out of `finally` into two explicit call sites:
- **Error path** (inside `catch`): `handle?.close()` failures are caught and logged via `console.error`, mirroring the existing `recordingErr` handling — the original sync error (`err`) is still what gets thrown.
- **Success path** (after the `try`/`catch`): `handle.close()` is awaited unguarded, so a close failure there still propagates to the caller exactly as before.

Added two integration tests to `mcpSync.test.ts` that mock `connectMcpServer` (via `vi.hoisted` + `vi.mock`, defaulting to the real implementation) to inject a `close()` that rejects:
1. A sync error (duplicate tool name) plus a close failure → caller still rejects with the original `ValidationError`, close failure only logged.
2. A successful sync plus a close failure → caller rejects with the close error (unchanged behavior).

Ran `pnpm run verify` in `backend/` to completion: lint, format, build, and all test tiers (170 files / 2065 tests, including the new ones) passed with exit code 0.
