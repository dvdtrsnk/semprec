## What was delivered

The proposal computation reads the photos of an Inbox item before its own model call and caches what each photo says on the attachment.

- Migration `0174_inbox_attachments_extraction.sql`: nullable `inbox_attachments.extraction jsonb`, additive.
- `packages/data/src/inbox/attachmentExtraction.ts` (exported from the data barrel): `attachmentExtractionSchema` (every field nullable, a missing field is null), `extractAttachmentDocument` (gateway operation `inbox_attachment_extraction`, temperature 0, attributed to the Semprec project item; one text block with the person's text, the capture date and time and the tenant time zone, plus an image block with the reduced copy), `classifyForExtraction` (`extract`, `awaitingMetadata`, `skip`) and `MAX_EXTRACTED_ATTACHMENTS = 4`.
- `inboxAttachmentsStore.ts`: `recordInboxAttachmentExtraction` (one `UPDATE ... WHERE extraction IS NULL`, bound to the Inbox item; returns the stored winner when two runs race, `null` when the row is gone) and `hasAttachmentAwaitingMetadata`.
- `services/semprec-api/src/proposalAttachmentExtraction.ts` (`resolveAttachmentDocuments`) and `proposalComputation.ts`: up to four photos with a reduced copy, by position, are read before the `inbox_proposal` call; a stored extraction is reused without a gateway call; the values go into the proposal request as a line "Attachment documents (JSON)". Gateway calls run with no transaction open. A failed call caches nothing and goes to the tick's compute-failure handling (gh-1485); an answer that does not match the schema is `AiGatewayFailedError` with reason `invalid_response`. PDFs, audio and unreadable images are skipped.
- `inboxTickAction.ts` (`readTickSnapshot`): while an image attachment has no metadata the tick returns and writes nothing; the metadata job's update announcement starts it again.
- `createProposalComputation` takes a new required `openBlob` port; `actionRegistryComposition.ts` builds it over the files root then the mail attachments root.
- ADR `docs/adr/2026-11-14-inbox-photos-are-read-by-the-proposal-computation-and-cached-on-the-attachment.md`.

## Entry points and contracts dependents build on

- Column `inbox_attachments.extraction` and `InboxAttachmentRow.extraction: AttachmentExtraction | null`.
- Data barrel exports: `MAX_EXTRACTED_ATTACHMENTS`, `attachmentExtractionSchema`, `classifyForExtraction`, `extractAttachmentDocument`, `hasAttachmentAwaitingMetadata`, `recordInboxAttachmentExtraction` (and the types); the sorted list of `publicSurface.test.ts` has them.
- Gateway operation name `inbox_attachment_extraction`.
- The cache key is the attachment row; the person's text is a hint and not part of the key (an edited text does not re-read the photo).
- The extraction is not returned by the attachment agent tool, the thread card context or the capture response.
