## Changes
- **`views/sortCompiler.ts`**: `compileSort` and `compileSortKeyset` now take a map from property key to `{ type, config }` instead of a map of types. The shared per-key expression reads `computed` for a rollup and `properties` otherwise. A new `sortKeyCast` picks a rollup's cast from its aggregation: `earliest`/`latest` sort as `::timestamptz`, every other aggregation as `::numeric`. `number` and `date` properties keep their casts, and the SQL for non-rollup properties is unchanged byte for byte.
- **`views/filterCompiler.ts`**: `compileCondition` uses `computed` for rollup properties in both its text and JSON forms. Everything else is unchanged.
- **`views/viewQuery.ts`**: `queryItemsCore` builds the new map from the `listPropertiesByDatabase` result it already loads.

## Beyond the issue's stated scope
The issue said to change only the map argument in `viewQuery.ts`, but two more changes there were needed for paging through a rollup sort to work:
- **Cursor encoding:** `encodeSortCursor` now takes a rollup key's value from `item.computed`. Before, it read `item.properties`, which is always null for a rollup, so page 2 onward was wrong.
- **Cursor validation:** `castableTo` in `decodeSortCursor` now checks a cursor value against the cast from `sortKeyCast`, so a rollup key is validated the same way the query compares it.
