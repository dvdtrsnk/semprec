## What was delivered

- `Threads.company` and `Threads.project` are inherited through two resolver link rules. The link engine had no rule whose value is computed, so the manifest schema and the registry gained a resolver rule variant (`key`, `target`, `resolverExport`; `getLinkResolverRules`) and the engine (`valueLinks/linkResolver.ts`, `linkPropagation.ts`, `linkResolverTriggers.ts`) evaluates it: item lock then link lock, the user's own value is kept, a broken link is untouched, the link is created before the write, sources are replaced, an empty answer removes the inherited value and its link, and the job pages by 100.
- Company rule: the sender of the thread's first inbound message (earliest incoming copy, not own, not Sent, not Drafts) is matched against `Companies.web`. A known person gets the one company of `People.companies` whose host matches (source: the person and `companies`); an unknown sender gets the one matching company (source: sender domain, property `web`); a freemail domain, no match or several matches give nothing. Project rule: the thread's company must be exactly one and have exactly one project with status `inProgress` or `longTerm` (source: the company item, property `projects`).
- Recomputation: a change of `People.companies`, `Companies.projects`, `Companies.web` or `Projects.status` queues `valueLinksPropagate` for the affected threads; a company created with a web, or restored from the Trash, does so too (fix round); ingest queues both rules when the new message is the first inbound message of its thread. Setting a value by hand ends the link and later changes do not touch it; `relink` restores it (a resolver link reruns the resolver and answers 409 `value_link_conflict` when it has no value). Setting 'no company' clears the inherited project.
- Merge of two threads: the own value beats the inherited one, with equal kinds the older `mail_threads.created_at` wins, company and project are decided apart, the link moves with the value, and the rules whose source is `Threads.project` are scheduled downstream.
- Every created or deleted `Threads.company` or `Threads.project` edge publishes the thread's `mailThread` invalidation after the commit.
- ADR `docs/adr/2026-11-14-a-thread-inherits-its-company-and-project-through-resolver-link-rules.md`.

## Deviations from the specification and spec seams

1. Task step 2 (a migration for the `senderDomain` source) was not needed: `0089_value_links.sql` has `source_kind` item or senderDomain, a nullable `source_item_id` and a `domain` column, and the store, the read shape and `shared/rows.ts` already carry the variant; only relink for a `senderDomain` source was added. 2. The link engine knew no resolver (gh-1593 lists sender-domain sources as out of scope), so the resolver rule variant, its evaluation, triggers and relink were added, with the ADR. 3. Relink of a resolver link reruns the resolver for the thread's current sender, not the stored domain. The project link's source is the company item with property `projects` (the Task says 'source Threads.company'); the company link's sender-domain source uses the property key `web`. 4. Edits outside Touches, all needed: `relationOps.ts`, `valueLinksStore.ts`, `valueLinkOps.ts`, `linkPropagation.ts`, the two link rule hooks, `threadValueEdges.ts`, `domainWriteHooks.ts`, the module-registry files and new `valueLinks/*` modules. 5. Existing tests changed because of the new behaviour: three merge tests of `threadValueEdges.test.ts` create the winner first, `fileCompaniesLinkRule.test.ts` drains the queue lane, and `proposalActions.test.ts`, `inboxTickProposal.test.ts` and `schemaHandler.test.ts` write People, Projects edges inside the tenant-zero scope because those writes now queue propagation. 6. The first inbound message is read with the CTEs of `mailThreadCopyCtes`, not from a stored flag. 8. Not covered: a change of `People.emails` or a folder move queues nothing (ADR consequence); no backfill of existing threads; trashing a company is not an input of the rules.
