## What was delivered

- Migration `0152_database_sensitive.sql`: `ALTER TABLE databases ADD COLUMN sensitive boolean NOT NULL DEFAULT false`. Additive; an insert of the previous release that omits the column creates a database that is not sensitive.
- `sensitive` is carried through `DatabaseRow`, `databasesStore` (column list and mapping), the shared `Database` type (`packages/shared/src/genericOperations/rows.ts`), the database envelope (`GET /api/databases`, the detail read) and the schema projection (`GET /api/schema`).
- `createDatabase` accepts `sensitive` for system databases only; for a non-system database it throws a `ValidationError` on field `sensitive` before any statement runs. The REST create and patch inputs are strict, so a body that carries `sensitive` answers 400 `validation_failed` without any new production code. `patchDatabase` never sets the flag.
- `SENSITIVE_DATABASE_KEYS` (`healthRecords`, `sleepSettings`, `sleepPlans`, `sleepNights`) in `seed/sensitiveDatabaseKeys.ts`, exported from the data barrel. `seedTenDatabases` and `seedSleepModule` decide the flag with it, so a newly provisioned tenant has exactly those four databases sensitive.
- `runSensitiveDatabasesCutoverMigration(pool)` (`seed/sensitiveDatabasesCutoverMigration.ts`): one UPDATE in the current tenant scope that touches only system rows of the four keys that are not yet sensitive; returns the number of rows marked (zero is valid, a second run marks none). Registered in `runTenantCutoverMigrations`.

## Deviations from the specification and spec seams

1. `schemas.ts` was not edited: the shared database output type does not live there, so only `rows.ts` carries `Database.sensitive`.
2. The flag was added to two `DatabaseRow` literals in `hooks.unit.test.ts` and `mailboxConnectionLimitHook.unit.test.ts` because the required field broke their type check.
3. The HTTP criteria are tested in `services/semprec-api` (outside Touches) because semprec-api serves the routes.
4. The cutover returns the number of rows it marked (`check:write-safety` needs the row count read).
5. Both seeds decide the flag with `SENSITIVE_DATABASE_KEYS.includes(key)`.
6. Placement of the cutover: after the sleep step (gh-1779); gh-1798 had no entry on the branch to order against. At landing the step also sits after the library cover step of gh-1793, which neither source names as a blocker.
7. A tenant seeded before the sleep module gets its sleep databases already flagged by the sleep cutover, so the new step marks only rows that existed without the flag (the registration comment says so after the review fix).
