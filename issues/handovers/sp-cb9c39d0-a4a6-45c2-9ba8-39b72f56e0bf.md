# Handover: move production from the hotfix line to develop

Implementation commit `3e5ca6191` on `feat/internet-accounts`. Documentation and an operator script only; no backend, web or mobile code changed. Nothing was run against production or any remote host.

**What changed.**
- `docs/operations/production-cutover-to-develop.md` (new): production facts to verify (12 rows: release v0.1.x from `hotfix/v0.1.1-mail-sync`, last tag `v0.1.12`, Debian VPS with `deploy.sh` from a server-local bare repo, partitioned `items` without `version`, `jit=off`, per-tenant sealed credentials, tenant count, Postgres 16 container, `POSTGRES_USER`/`POSTGRES_DB`, backups, Hunspell files, blob directories, env layout); what the code says; what is carried and lost; procedure (backup and restore test, tenant export as user archive, dry run, cutover window with restore of the emitted dump next to the old database and a database rename, `provision.sh` + `deploy.sh`, mail reconnection, verification checklist); rollback (cases A and B, old database kept as `semprec_v01`); an empty owner go/no-go table; how the dry run was tested.
- `deploy/scripts/cutover-dry-run.sh` (new): restores a custom-format dump into `<name>_src`, migrates and seeds `<name>_ref`, probes the develop migrations on a copy (`<name>_inplace`) and compares its columns with `_ref`, migrates `<name>_dst`, deletes the baseline's own tenant row and AI budget and loads every common table except the exclusions in one transaction (`pg_dump --data-only --load-via-partition-root`, `session_replication_role = replica`), checks every foreign key for orphans, runs the develop seed and `verifyTenancyCli`, reports items per database (live/trashed) before/after, rows per carried table before/after, excluded and dropped tables with source row counts, sealed credentials by type, queued graphile-worker jobs, and the seed delta against `_ref`. `--emit-dump` writes the carried database as a custom dump (only on PASS, or GAP with `--allow-seed-delta`); `--keep` leaves the databases. Exit 0 PASS, 3 GAP, 1 FAIL, 2 refused/usage.
- Guards: `--name` must match `^cutover_scratch_[a-z0-9_]{1,30}$`; the cluster must hold no database other than `postgres`, templates and `cutover_scratch_*` (the script creates cluster roles); the connecting user must be a superuser; client tools must be the server's major version; the admin URL is read from `CUTOVER_SCRATCH_ADMIN_URL` and split into libpq variables, never passed as an argument. All four scratch databases are dropped at the start and on exit.

**Findings from code (the answer to "can develop import a v0.1.x export").**
- No. The tenant export (format version 1, identical in `v0.1.12`) has no importer in develop.
- Develop's migrations do not upgrade a v0.1.x database: its ledger lists `0001_core_schema.sql`..`0177_*.sql`, so `0001_baseline.sql` is applied and fails (`function "activate_czech_hunspell_search" already exists`, observed).
- Develop's seed skips an already seeded tenant, so carried system databases keep the v0.1.x shape. Against a database built by `v0.1.12`, the develop seed (this branch's build) defines 11 system properties the carried data lacks: `mailboxes.mailEnabled`, `mailboxes.calendarsEnabled`, `mailboxes.calendars`, `calendars.account`, `calendars.readOnly`, `calendars.remoteColor`, `calendars.remoteName`, `events.exceptionDates`, `events.recurrenceId`, `events.recurrenceRule`, `events.timeZone`. This blocks the go; the runbook names three options for the owner (an additive reconcile issue, accept, or reseed).
- Schema differences v0.1.12 → this branch: tables only in v0.1.12 `module_migrations`, `module_migration_progress`; only in develop the three calendar sync state tables; new columns all nullable or defaulted (`items.version` default 1).

**Owner-attested preconditions (an agent cannot attest these).**
1. Production facts 1–12 of the runbook confirmed on the host.
2. A backup of the production database taken in the window and restored successfully into a scratch cluster.
3. The dry run passed (or GAP with an accepted delta) against that backup with the build of the exact release commit.
4. The seed-delta decision (option 1, 2 or 3) made; with option 1 the follow-up exists and the dry run reports no delta.
5. A develop release tag exists and the server's deploy origin (bare repo, its `main`) can serve it.
6. Rollback target `v0.1.12` on disk and the rollback procedure read.
7. Users informed about downtime, signing in again and reconnecting mail.
8. The go/no-go itself. Current status in the runbook: NO-GO.

**Tests (local only).** Disposable `postgres:16-alpine` containers with `jit=off`, PostgreSQL 16.15 tools (wrappers running the container's own `psql`/`pg_dump`/`pg_restore`), this branch's backend build as "develop". Synthetic v0.1.x dump: a database migrated and seeded by a `v0.1.12` build (built from `git archive v0.1.12`), filled through the v0.1.12 choke point (user database with 5 items, 1 trashed; tasks, projects, people; 4 relations) plus a raw-SQL user and a sealed-credential row, dumped as the backup job does. Results: in-place refused; 72 carried tables equal; 29 databases equal live/trashed; no orphans; `already seeded`; `tenancy: verified`; seed delta as above; exit 3. Emitted dump restored with owners into a new database, then develop migrations, seed and tenancy verifier passed, router functions owned by `semprec_router`, and the develop choke point created an item, updated a carried task (version 1 → 2) and listed its relation. Develop-shaped dump: in-place probe reported the baseline column `mail_account_server_settings.caldav_url` missing; carry PASS. Refusals (exit 2, no database touched; a non-scratch database's contents intact): bad names, non-scratch database present, non-superuser, 18.x tools vs 16 server, missing build, missing URL; a non-dump file fails with exit 1 and no leftovers; a repeated run after `--keep` dropped leftovers and passed. `shellcheck -S warning` clean.

**Not tested.** A real production dump, a dump with the Czech Hunspell dictionary active (the scratch cluster then needs the dictionary files), more than one tenant, real mail account reconnection (whether `reauthorize` accepts a mailbox with no credential at all is marked to confirm), `deploy.sh`/`provision.sh` on a host, the database rename and the rollback.

**Deviations and seams.**
- The Task says "import"; no importer exists, so the carry is a catalog-driven table copy from the restored backup, and the tenant export is kept as a user-held archive and a count cross-check.
- `deploy.sh` requires the tag on the origin's `main`; how the server's bare repo tracks the hotfix line is unknown and listed to verify.
- Password (iCloud/IMAP) accounts have no password-only replacement route in develop; the runbook says remove and re-add, which re-downloads their mail.

**Follow-ups.** If the owner picks option 1: an issue for an additive reconcile of system properties and relation definitions for carried tenants, run between load and seed, after which the dry run must report no seed delta.
