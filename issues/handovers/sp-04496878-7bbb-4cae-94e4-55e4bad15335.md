# Handover: lock the value links an Event feeds in item order, then rule order, when the Event is trashed

Delivered on chain `e1-235-value-link-locks`, candidate commit `17f18117e8647eb2aff441bc0a52f89cef9f712c`, landed by a `--no-ff` merge (`87698f26ef3b9c6b461cc3d9794cebac49b194dc`) on `feature/backend-parallel` as the first chain of a train with `e1-237-db-roles` and `e1-244-purge`. The segment commit of this source is `3c00ec0a8278077371e072b39b8d94969f471258`.

**What changed.**
1. `deleteValueLinkSourcesBySourceItem` (`backend/packages/data/src/chokePoint/valueLinksStore.ts`) takes a third parameter `ruleKeyOrder` (a list of rule keys, default empty) and locks the links it detaches with `ORDER BY l.item_id, array_position($2::text[], l.rule_key), l.id FOR UPDATE`, bound as a parameter. An empty or omitted order gives item id then link id; a partial order gives item id, then the links of the named rules in the given order, then the other links by link id (NULL positions sort last).
2. `valueLinkSourceDeleteHook` (`backend/packages/data/src/valueLinks/valueLinkSourceDeleteHook.ts`) passes the rule keys of `loadLinkRules()` in catalog order, so the trash of an Event locks the links of the items it feeds in the same order as the link propagation job (item id, then rule order, then link id). This removes the lock cycle between the removal of a transcript's event edge and the trash of the Event when a third transaction holds the transcript's project link row.
3. `itemTrash.ts` is untouched: the permanent purge keeps the empty default.
4. New ADR `docs/adr/2026-11-15-the-trash-of-an-event-locks-the-value-links-it-feeds-in-item-order-then-rule-order.md` (accepted, backend, standalone; it edits no accepted ADR).

**Contracts dependents build on.** The signature `deleteValueLinkSourcesBySourceItem(client, sourceItemId, ruleKeyOrder = [])`. A caller that detaches the links of an Event inside a trash passes the catalog order; the purge and any other caller may omit it. No route, table, migration, operation or job name changed.

**Files.** `backend/packages/data/src/chokePoint/valueLinksStore.ts`, `backend/packages/data/src/valueLinks/valueLinkSourceDeleteHook.ts`, the ADR above.

**Tests.** `backend/packages/data/src/__tests__/eventTrashValueLinkLockOrder.test.ts` (new; four combinations of start order and link-id order on separate runtime-role pools, third transaction holding the project link; asserts both calls commit and the final state: no value link, project and company edges kept, Event trashed). `backend/packages/data/src/__tests__/valueLinksStore.test.ts` (three new cases: lock order by item id, rule position and link id; empty or omitted order; a rule the order does not name). The worker verified that on the tree without the change only the combination "edge removal first, people link has the smaller id" ends in a deadlock.

**Deviations and spec seams.** None. The two paths of the 2026-11-15 record that the ADR lists as not repaired stay as they were.

**Criteria NOT RUN or BLOCKED.** None. "The purge of a trashed Event is unchanged" has no dedicated new test; it rests on `itemTrash.ts` being untouched, the purge calling without the argument, the default-order case in `valueLinksStore.test.ts` and the unchanged `itemTrash.test.ts`.

**Review.** Requirements and tests lens: one low finding (the ADR described a partial rule order as item id then link id; the tested order puts the named rule's link first). Rules and architecture lens: clear. The finding was confirmed and fixed in the ADR (commit `1051bbeb87531512a7a6cab5c0ccd40fe20e9017`); documentation only, no recheck (low severity, no behaviour change).

**Follow-ups.** The concurrency test asserts that the second call waits (`blockedBy[1]` not null) but does not name the lock it waits for; a reviewer noted this as a minor weakness, not reported as a finding.
