# Handover for gh-1698

Skip transcribing audio attached to an Event. Candidate commit `85994eb0aa4d52cec8018f27dd0ee03e828b58bb` (one segment, one commit) landed on `feature/backend-parallel` with merge `83101b108ff870223d7bd32872b8e59f18b18702` (chain `p0-02-transcription`). The acceptance receipt is `issues/batches/backend/acceptance/sources/gh-1698.md`.

## What was delivered

- The Files transcription trigger (`createFilesTranscriptionTriggerAction`, action id `core.filesTranscriptionTrigger`) skips an audio file that has at least one `Files.events` edge. The check runs in the action's own transaction, after the `Emails.attachments` check and before both enqueues: it resolves the relation definition of the config's `eventsRelationPropertyId` with `relationsStore.getRelationDefinitionByPropertyId` and lists the file's edges with `relationsStore.listRelationsForItem`. With one edge or more it returns, so neither `transcription-create:<fileItemId>` nor `transcription-job:<fileItemId>` is queued and the transcribe service writes no Transcriptions row.
- `filesTranscriptionTriggerConfigSchema` has the optional uuid key `eventsRelationPropertyId`. A config without the key still parses and that one check is skipped; a value that is not a uuid is rejected by the schema.
- `seedSystem` resolves the `Files.events` property with `propertiesStore.getPropertyByKey(client, tenDatabases.files.id, "events")`, throws `Files.events property not found after seedTenDatabasesInTransaction` when it is missing, and stores its id as `eventsRelationPropertyId` in the `Files transcription trigger` heartbeat's `actionConfig`.
- The per-tenant cutover `runTranscriptionTriggerEventsCutoverMigration` sets the same key on heartbeats seeded earlier. One transaction; it returns early when the tenant has no Files database or no `events` property on it; it selects the `core.filesTranscriptionTrigger` heartbeats whose `action_config` lacks the key `FOR UPDATE` and updates each by id with `requireAffectedRows`. A second run selects nothing and writes nothing.

## Contracts dependents build on

- Stored shape of the `Files transcription trigger` heartbeat (`project_heartbeats.action_config`, `action_id = 'core.filesTranscriptionTrigger'`): `{ filesDatabaseId, attachmentsRelationPropertyId, eventsRelationPropertyId }`, all uuid strings. `eventsRelationPropertyId` is the id of the `events` property of the tenant's Files database. It is optional in the schema, so code that reads the config must accept a heartbeat that does not carry it yet.
- An audio file attached to an Event is a plain attachment, not a recording: the Files trigger creates no transcription work for it. A recording is created only through the recording upload path of gh-1574, whose intake request the trigger checks first (`readRecordingRequest`) and which this source did not change.
- When `eventsRelationPropertyId` resolves to no relation definition the trigger does not block: it enqueues, as the existing `Emails.attachments` branch does.
- Export: `runTranscriptionTriggerEventsCutoverMigration(pool: Pool): Promise<void>` from `backend/packages/data/src/transcription/transcriptionTriggerEventsCutoverMigration.ts`. It is not re-exported from `backend/packages/data/src/index.ts`; its only caller is `runTenantCutoverMigrations`.
- Registry order in `backend/packages/data/src/db/tenantCutoverMigrations.ts`: the entry stands directly after `runInboxMarkdownFormatCutoverMigration` (gh-1675, the declared blocker) and therefore after `runEventsFilesRelationCutoverMigration` (gh-1588), whose `Files.events` property it reads. It must stay after the gh-1588 entry; the test "one registered run sets the key on a tenant that also gets Files.events from that run" fails otherwise. A later source that declares gh-1698 as a blocker (gh-1700 does, as shared-file ordering) puts its entry after this one.
- The heartbeat fire reads `action_config` at run time, so the cutover takes effect without a restart. The previous release's config schema is a non-strict `z.object`, so it ignores the extra key after a rollback.
- No route, no table, no SQL migration, no generic operation and no job name was added or changed. The job keys `transcription-create:<fileItemId>` and `transcription-job:<fileItemId>` are the existing ones.

## Deviations from the specification and spec seams

1. No SQL migration. The "[adds a migration]" of the plan is the application-code per-tenant cutover, so no ordinal was taken.
2. The Task places the check before `enqueueTranscriptionJob`. The action has since gained `enqueueTranscriptionCreate` in front of it, so the check stands before both enqueues.
3. The Task calls the tests in `transcriptionActions.test.ts` unit tests. The file runs against real Postgres in the integration tier and stays there.
4. The Task says to follow `transcriptionRequeueHeartbeatCutoverMigration.ts`, which takes `LOCK TABLE project_heartbeats` before a check-then-insert. This cutover updates existing rows, so it locks only the rows it selects (`SELECT ... FOR UPDATE`) and updates them by id with `requireAffectedRows`. A concurrent-writer test covers the lock. The rules reviewer found the row-locked shape to be an existing pattern that needs no new ADR.
5. Two test files outside `Touches` were added, and no production code outside it: `seedSystemFilesEventsProperty.test.ts` for the seed's new throw, and `eventAttachmentTranscription.test.ts` in semprec-transcribe for the "no Transcriptions row" clause of the first criterion, because the row is written by the transcribe service's create task, which a data-package test cannot import.
6. The new action tests are a second describe in `transcriptionActions.test.ts` on a `semprec_data` pool; the existing describe is unchanged.
7. The property key literal `"events"` is used in the seed and in the cutover, as `seedTenDatabases.ts` and `eventsFilesRelationCutoverMigration.ts` do. No shared constant was added.
8. Test seams the worker declared: the file and its `Files.events` edge are written in one transaction through `createItemWithClient` and `createRelationWithClient`, as the upload attach of gh-1645 does; the upload endpoint itself is not driven. The seed's throw cannot be reached with real data, so its test makes `propertiesStore.getPropertyByKey` answer null for the key `events` through `vi.mock` with `importOriginal`. The pre-cutover config and the missing heartbeat are produced with raw SQL on the admin pool, with a reason comment, because the current seed cannot produce them.

## Review

Two reviewers read `85994eb0^..85994eb0` read-only: requirements and tests (verdict clear, no findings) and project rules and architecture (verdict clear, no findings). There was no fix round and no recheck. No security review report exists for this source.

Observations the reviewers recorded without a finding, left as they are:

- The property key literal `"events"` is repeated in `seedSystem.ts` and the cutover instead of a shared constant.
- When `eventsRelationPropertyId` resolves to no relation definition the action goes on to enqueue, mirroring the `Emails.attachments` branch; a test covers it.
- The cutover reads the Files database and its `events` property with plain reads. Both are schema-locked seed rows with no concurrent deleter other than tenant purge, so the reviewer reported no concrete race.

Follow-up proposed by the worker, not changed here:

- `.github/scripts/check-write-safety.mjs` matches UPDATE statements with `/update\s+\S+\s+set/`, so an unchecked `UPDATE <table> AS <alias> SET ...` is not detected. An early draft of this cutover passed the check for that reason before it was rewritten to check its affected rows.
