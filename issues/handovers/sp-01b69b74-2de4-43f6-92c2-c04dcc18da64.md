# Handover: append the seed's missing select options to carried tenants

Implementation commit `6896a371b` on `feat/ia-seed-options` (from `feat/internet-accounts`). Nothing was run against production or any remote host.

**Design.**
- `planReconcile` (`seed/seedReconcile.ts`) handles an existing system property whose config differs from the fresh seed's (after id mapping): when both are `select` or both `multi_select`, both `options` are arrays of `{ key, … }` objects, the config apart from `options` is deep-equal and every option present in both is deep-equal, the seed's options the tenant lacks (by key) are planned for appending, in the seed's order, with the seed's option definition, after the tenant's own options. The tenant's options, their order and options the seed does not define are kept; no existing option is changed.
- The write runs in the same per-tenant reconcile transaction, under the seed lock and the exclusive `properties` lock already held: `assertValidPropertyConfig`, then a raw `UPDATE properties SET config` (as the seed writes locked schemas), `requireAffectedRows`.
- Reporting: any other config difference is reported as `config` and left unchanged (including an existing option with another label or colour, even when options are also missing). A property that keeps options the seed does not define is reported as `config` too, after its missing options were appended. A difference in option order alone is not reported (otherwise a property would report forever after an append when the seed inserted an option mid-list).
- `SeedReconcileReport.appendedOptions: { database, key, options }[]`. `formatSeedLines` prints `reconcile created N properties, M relation definitions, appended K select options` and one `appended options <database>.<key> <k1>,<k2>` line per property (fixed tags and keys only). `--strict` still counts only conflicts.
- Docs: `docs/architecture/migrations-and-seeding.md` (the reconcile rule), `docs/operations/production-cutover-to-develop.md` (status, step 5, what is lost, the `calendars.kind` blocker removed, "a run is good when", how it was tested).

**Findings for the owner.**
- The issue's premise that the calendar sync fails without the option does not hold for the sync itself: `assertSelectValuesKnown` (`chokePoint/itemWrites.ts`) skips system writers, and `CALENDAR_SYNC_WRITER` is one, so the integration test shows the sync creating an account calendar before the append as well. The append still makes the carried definition match develop's (option catalog, facets, labels, `--strict`). The test asserts the AC's positive side only.
- The develop calendar sync apply logs a `pg` deprecation warning (concurrent `client.query` on one client, `Promise.all` in `resolveCalendarSyncIds`). Pre-existing, not touched.
- Still open from the previous handover: views and other artefacts referencing properties are not reconciled; the runbook wrapper needs the work dir as cwd; on this host a bind mount under `/private/tmp` was not visible to the container, a directory under `$HOME` was.
- Not tested: a real production dump, more than one carried tenant in the dry run, Hunspell active.

**Deviations.**
- Options the seed does not define do not prevent the append (the decision keeps them) but are still reported as `config`; a pure option-order difference is no longer reported. Both are in the architecture document.
- The dry-run fill was smaller than the previous one (tasks not related to the project).
