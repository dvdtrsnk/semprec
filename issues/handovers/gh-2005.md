## What was delivered

A timeline source, `readSubscribedEventTimelineItems` (`calendar/timelineSubscribedEventSource.ts`), registered as source `subscribedEvents` in `CALENDAR_TIMELINE_SOURCES` (`calendar/timelineSources.ts`). It reads live `subscribedEvents` rows that overlap the requested range (candidate SQL on text days, as the core Events source does), one batched lookup of calendar edges joined to the calendar item for its trash state, and maps each row to an entry with `kind: 'event'`, `readOnly: true`, `date`/`endDate` from `startsAt`/`endsAt`, wall-clock times `null` when `allDay`, `effectiveTo` and `hasEnd` as for Events, `calendarId` from the edge (`null` without an edge), `tasks` and `counts` `null`. Rows of a trashed calendar and trashed rows are omitted. A row with an unreadable `startsAt`, `endsAt` or `allDay` is omitted with a warn log that carries only `itemId`, `databaseId` and the property key, and the response stays 200.

## Entry points and contracts dependents build on

- Entry shape: `kind: 'event'`, `readOnly: true`, `id` = item id of the stored row, `databaseId` = id of the `subscribedEvents` database. A consumer tells it from an Event by `databaseId`. ADR `docs/adr/2026-11-14-a-subscribed-event-in-the-timeline-is-a-read-only-stored-row.md` records this and how it narrows decision 6 of the timeline-sources ADR: `readOnly: true` no longer implies that the id is no item id. `attachTaskInEventState` leaves the entry untouched.
- The compact shape (`shape=compact`) carries `readOnly` and the calendar.
- Stored values are read as zone-less wall-clock `YYYY-MM-DDTHH:mm[:ss[.fff]]` in the tenant's time zone; a value with an offset or a date-only value is unreadable and omitted. gh-2004 (the import, not yet landed) must write that format; the conversion from the feed's zone happens there, not in the source.
- The number of statements does not grow with the number of rows; the reading is tenant-scoped through the runtime role.
- No route, table, migration or job is added.

## Deviations from the specification and spec seams

1. Stored `startsAt`/`endsAt` are read as zone-less wall-clock values; an offset or a date-only value is unreadable (the Task says the import stores the tenant's wall-clock time; gh-2004 must write that format).
2. A row with `endsAt` before `startsAt`, or a non-boolean `allDay`, is also unreadable.
3. A row without a calendar edge is returned with `calendarId: null` (no default-calendar fallback).
4. A row whose `startsAt` is absent, null or empty is not selected and not logged, like an Event without a date.
5. `tasks` and `counts` are `null` on these entries.
6. The doc comment of `CalendarTimelineItem.readOnly` in `timelineSources.ts` was corrected and points at the new ADR; the ADR is a result of the review (medium finding), not of the Task.
