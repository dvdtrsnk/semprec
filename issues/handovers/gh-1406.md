# Handover for gh-1406

`database.query` and `view.query` accept an opt-in `includeCount: true` and then return `totalCount`, the number of items matching the filter. The count ignores `limit`, `cursor` and `sort`, and excludes soft-deleted items unless `inTrash` is true. Without the flag the response has no `totalCount` and no count query runs.

- **Schema and types:** `includeCount` is in the shared `queryFields` in `schemas.ts`. `ItemPage` in `rows.ts` has an optional `totalCount`. The MCP and agent tools derive from the catalog, so they needed no code.
- **Data layer:** `viewQuery.ts` validates `includeCount` like `inTrash` (a non-boolean is a 400 with `field: "includeCount"`). `queryItemsCore` runs `countItems` with the same compiled filter and `includeDeleted` as the page, in the same transaction. A view uses its effective filter, either the request override or the stored one. A curated view counts live members through the new `countLiveViewItems` in `viewItemsStore.ts`, or all members with `inTrash`.
- **Pass-through:** `genericApplicationService.ts`, both REST handlers and `toItemQueryEnvelope`, which adds `totalCount` only when the result carries it.
- **Tests:** new `viewQueryTotalCount.test.ts` covers 13 matches with limit 5 across pages, sort ignored, flag omitted or false, soft-delete and restore, `inTrash`, a view over the database, a curated view, and non-boolean rejection. `itemsHandler.test.ts` covers the REST envelope, database-versus-view equality and the 400 on both routes. Build, lint, prettier and the unit suite pass. The integration tests I ran are the new file, the pagination test and both handler tests. I did not run the full verify.
- **For dependants (#1709, #1857):** the count reuses `countItems(client, databaseId, { includeDeleted, buildFilterSql })`. A `q` parameter must not feed `buildFilterSql` for the count.
