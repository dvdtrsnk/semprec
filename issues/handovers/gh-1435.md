# Handover for gh-1435

Closes #1435

The scheduler store can now rename a heartbeat and change the task of an agent-run heartbeat. Both are new functions in `backend/packages/data/src/scheduler/schedulerStore.ts`. The work is committed locally and not pushed.

The new integration test `heartbeatNameTask.test.ts` passes (12/12). Lint, prettier and the data package typecheck also pass. I did not run the full `pnpm run verify`.

- **`updateHeartbeatName(client, id, name, moduleRuleKinds?)`:** trims the name and throws `ValidationError` (field `name`) when it is empty or over 200 characters. It updates only `name` and returns the row, or null when the id is not visible to the caller's tenant. It reads the row back with `tolerateUnknownRuleKind`, so a rename works even when the rule's module is inactive.
- **`updateHeartbeatTask(client, id, task, moduleRuleKinds?)`:** validates the task (non-empty after trimming, at most 4000 characters, else `ValidationError` on field `task`). It then runs a single `UPDATE ... jsonb_set(action_config, '{task}', ...) WHERE id = $1 AND action_id = 'core.agentRun'`, so other `action_config` keys survive and the action check has no race with the write. When no row matched, a follow-up `SELECT` returns null for an unknown id (or another tenant's) and throws `ValidationError` (field `actionId`) for a different action.
- **Exports:** the constants `HEARTBEAT_NAME_MAX_LENGTH` and `HEARTBEAT_TASK_MAX_LENGTH` are also exported. The data barrel already re-exports the whole store file, so `index.ts` is unchanged.
- **Untouched columns:** `rule`, `enabled` and `next_fire_at` are never written by either function.
- **Tenant isolation:** the tests run these functions on a `semprec_data` runtime-role pool scoped to another tenant (`withTenantTransaction`), so RLS is what hides the row and both functions return null.

Notes for dependants (#1846): the task string is stored as given (only validated, not trimmed), while the name is stored trimmed. Both functions take a `Pool | PoolClient` and do not open a transaction, so the caller owns transaction and approval handling. A caller that needs both writes atomic should pass one `PoolClient`.
