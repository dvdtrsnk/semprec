## Summary

Implemented all three fixes from issue #680 in `backend/packages/data/src/migrationJob/propertyTypeMigration.ts` and `worker.ts`:

1. **`text → date` conversion**: `CONVERTERS.text.date` now validates against an ISO 8601 regex before calling `Date.parse`, rejecting shapes like `"March 5"` that `new Date()` used to silently accept. `isAlreadyTargetType('date', value)` now only recognizes the converter's own `toISOString()` output shape, not any string, so it no longer treats unconverted source text as already-done.
2. **Per-batch locking**: each batch of `runPropertyTypeMigrationJob`'s loop now runs inside `withTransaction`, using the existing `lockItemBatch` (`FOR UPDATE`, `skipLocked: false`) to hold the batch's rows for the transaction's lifetime. The drop-mark and the `properties - key` delete are in the same transaction, so a crash can't leave one without the other.
3. **Terminal status on exhaustion**: `handlePropertyTypeMigrationTask` now takes `{ isFinalAttempt: boolean }`; on the last graphile-worker attempt's failure it settles the property to a terminal status (`markPropertyMigrationDroppedValues` + `settlePropertyMigrationStatus`) before rethrowing, guarding that settle step so it never replaces the original error. `worker.ts` passes `helpers.job.attempts >= helpers.job.max_attempts`.

Also fixed a `check:write-safety` finding (raw `pool.connect()` outside `db/pool.ts`) by switching to `withClient`, and added the unit/integration tests the issue specifies.

`pnpm run verify` passed lint, format, build, unit tests, write-safety, boundaries, and my new/updated integration tests. Two unrelated integration-test failures (`moduleDataMigration.test.ts`, `transcriptionTask.test.ts`) appeared in that run; I confirmed `moduleDataMigration.test.ts`'s failure reproduces identically on `develop` with my changes stashed out, so it's pre-existing and out of this issue's scope.
