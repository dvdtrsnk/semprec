# gh-1445 — Send APNs background pushes without a notification row

Repository-Issue: gh-1445

## Delivered behavior and production wiring

- `sendApnsBackgroundPush(target, data, config?)` in `backend/packages/data/src/push/apnsAdapter.ts`. It sends the body `{"aps":{"content-available":1}, ...data}` with the headers `apns-push-type: background` and `apns-priority: 5`. The body has no `alert`, `sound` or `badge` key. The caller's `data` keys are sent unchanged, beside `aps`.
- A `data` object with an own `aps` key throws `ValidationError` (`backend/packages/data/src/errors.ts`, status 400, code `validation_failed`). The check runs before any request and before any configuration lookup, and `http2.connect` is not called.
- Results:
  - 200 is `delivered`.
  - 410, or reason `BadDeviceToken`, is `permanent-failure`. Its `error` is the APNs reason, or `status <n>` when there is none.
  - Any other failure, and a connection that cannot be opened, is `transient-failure`. The thrown error is kept as `error`.
  - Missing `APNS_*` configuration, or an unreadable key file, is `not-configured`, with no request.
- The request, provider token and result mapping live once, in a private `sendApnsRequest(target, body, extraHeaders, config)` in the same file. `sendApnsNotification` now builds its alert body and calls the helper with no extra headers. Its payload and headers are unchanged, and an alert carries no `apns-push-type` or `apns-priority`.
- No production caller in this issue, by design. The function is not reached from any runtime path yet. The first caller is the debounced sleep resync (#1838), which picks registrations and revokes dead ones. The adapter does neither.
- The adapter module is not re-exported from the `@semprec/data` index, so `publicSurface.test.ts` does not change.
- No schema change, no migration, no write to `notifications` or `push_deliveries`. `pushSenders.ts` is unchanged: `PushSenders` still has only `sendWebPush` and `sendApns`.

## Notes for dependants

- The adapter checks only for `aps`. It does not check the other `data` keys, or the size of the encoded payload. Callers own the shape of their `data`.
- The adapter does not retry. A `transient-failure` goes back to the caller, which decides whether to retry.
- On `permanent-failure`, the caller revokes the registration. The fan-out job does this for alerts through `revokePushSubscriptionByProviderInvalidation`. On `not-configured`, the caller must not revoke, as stated on `PushSendResult`.
- APNs does not guarantee delivery of background pushes, so no caller may rely on one arriving.
- Not in this change: selecting registrations, revoking dead ones and debouncing (#1838), the sleep-window hold (#1794), silent dismiss pushes (#1826), the reminders resync (#1879), alert changes (#1443 and #1829), per-device settings (decided: not in v1), any `notifications` or `push_deliveries` row, and any web push variant.
- Migration ordinal: none. This change adds no migration.
