## Reuse `collectItemSubtree` in `purgeExpiredTrashSubtree` (#518)

`itemTrash.ts` now has a single subtree walk. The purge had its own hand-copied version of that walk, and it now calls the shared one with a filter instead. What the purge removes is unchanged.

### Changes
- **`collectItemSubtree(client, root, include?)`** in `backend/packages/data/src/chokePoint/itemTrash.ts` takes a new optional `include` parameter. If `include(row)` returns `false`, that row is left out and the walk doesn't go below it. The root is always included. Without `include`, the function behaves exactly as before, so the soft-delete and restore callers are untouched. The JSDoc describes the new parameter.
- **`purgeExpiredTrashSubtree`** no longer has its inline BFS. It calls `collectItemSubtree(client, root, (row) => row.deletedAt !== null && new Date(row.deletedAt) < cutoff)`, which keeps the same rule as before: only rows trashed before the cutoff are walked. The root eligibility check, the archived-database check, the delete loop and the return value are unchanged. The one docstring line that said the purge "mirrors" the walk now says it "uses" it.

### Tests
There are new cases in `backend/packages/data/src/trash/__tests__/purgeExpiredTrash.test.ts`. They call `chokePoint.purgeExpiredTrashSubtree` directly, because the sweep runs one call per expired candidate and that would hide what the walk itself does. They cover:
- A subtree where every row was trashed before the cutoff is purged completely.
- Under an expired root, one eligible sibling is purged. A sibling trashed after the cutoff, a live (restored) sibling, and each of their nested leaves are all kept. The leaf under the too-recent sibling is itself expired, so this shows the walk really stops at a row it isn't allowed to include.
- A `parent_item_id` cycle, where the root's database is re-parented under a descendant, finishes and returns the expected ids.

`publicSurface.test.ts` and the existing trash tests were not changed.
