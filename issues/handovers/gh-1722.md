## What was delivered

- The generic operation `page.duplicate` in the catalog (`backend/packages/shared/src/genericOperations/`): capability `core.item.write`, non-destructive, risk class `write`, reversible, no approval.
  - Input `PageDuplicateInputSchema`: `{ pageItemId }`, strict, a canonical UUID. No target is accepted.
  - Output `PageDuplicateOutput`: `{ pageItemId, docId, blockId }` of the root of the copy: its Pages item, its document and its `page` block in the parent's document.
  - Port method `GenericApplicationPort.duplicatePage(actor, input)`. `createGenericApplicationService` implements it as `docStore.duplicatePage(input.pageItemId, { origin, locale })` with `origin` from the actor (`user` or `ai_agent`) and `locale` from `chokePoint.findUserLocale(actor.userId)`, English when that user is not found.
- Data layer, `backend/packages/data/src/docs/pageOperations.ts`:
  - `duplicatePageWithClient(client, pageItemId, { origin, locale })` runs in the caller's transaction; `docStore.duplicatePage(pageItemId, options)` in `docs/docStore.ts` wraps it in one `withTransaction`.
  - It reads the page without a lock (missing, trashed or foreign: `NotFoundError`; a live item of another database: `ValidationError` with `field: "pageItemId"`, `reason: "not_a_page"`), takes `FOR UPDATE` on the parent's row and then on the page's row and checks each live, plans the whole tree breadth first by reading, and only then creates rows.
  - Every page of the copy is a new Pages item (through `createItemWithClient` with the allowed system keys `title` and `parentItemId` under the `pages` owner process) with a new document. Blocks keep order, type, indent, `done` and text runs with inline attributes; every block id is new.
  - A `page` block is followed when its `pageId` names a live item of the Pages database that is not the page being copied or one of its ancestors within the copy. Every other `page` block (trashed, purged, missing, not a page, malformed id, ancestor) is left out. A page named by two blocks is copied once per block.
  - `MAX_DUPLICATE_PAGES = 500`, the root included. A tree that needs a 501st page is a `ValidationError` with `field: "pageItemId"`, `reason: "too_many_pages"`, thrown before the first write.
  - The root of the copy is titled from the text of the first `page` block of the parent's document that names the original (normalized and cut like the mirror job stores it), read after both row locks are held; only an orphan falls back to the `title` of the locked row. The suffix follows, from the docs catalog key `page.duplicate.titleSuffix` (`" (kopie)"` for `cs`, `" (copy)"` for every other locale); the original's title is cut so that title plus suffix fit 500 code points. Nested copies get no suffix: their item takes the mirrored `title` of the page they copy and their block keeps the source block's text.
  - The root's `page` block is inserted into the parent's document right after the first block that names the original, at that block's indent, or at the end with indent 0 for an orphan. It is the last write, through `mutateDocWithClient` with the caller's origin.
- `POST /api/items/:id/page/duplicate` in `backend/services/semprec-api/src/itemsHandler.ts`: `:id` is the Pages item, nothing of the request body is used, the answer is 201 with the operation output.
- The route matrix entry `{ name: "duplicate page", method: "POST", path: "/api/items/<id>/page/duplicate", surface: "api", public: false, tenancy: "tenant" }` in `backend/services/semprec-api/src/routeMatrix/items.ts`, its `ROUTE_CASES` case and its `MCP_CASES` case `page.duplicate` in `tenantIsolationRoutes.test.ts`, and its `ROUTE_HANDLER_FILES` mapping to `services/semprec-api/src/itemsHandler.ts`.
- The docs i18n catalog entries `page.duplicate.titleSuffix` in `backend/packages/data/src/docs/i18n/cs.json` and `en.json`.
- ADR `docs/adr/2026-11-10-page-duplication-copies-the-subtree-as-new-pages.md`: the contract, what is copied, the title source, the lock order, what the copy is a snapshot of, and the capability exception to the family table.

## Deviations from the specification and spec seams

1. Spec seam: the route entry is in the slice module `backend/services/semprec-api/src/routeMatrix/items.ts`, not in `routeMatrix.ts`.
2. Spec seam: the function is `duplicatePageWithClient`, with `docStore.duplicatePage` opening the transaction, where the Task says `duplicatePage`; it follows `createSubpageWithClient`.
3. Against the family record `2026-10-28-page-operation-family`, decided for the Task and recorded in the new ADR: capability `core.item.write` (the family table says `core.page.write`) and no "optional target" input.
4. Lock order: the parent's row is locked before the page's row, where the Task says "lock and read the original", because the title mirror records fix host before Pages item. The page is read unlocked first and rechecked under its lock.
5. The title of the root of the copy comes from the original's block in the parent, not from the item's mirrored `title` (fix round, after the medium review finding). The Task says only "Title (kopie)".
6. The copied documents are read without locks and without compaction and nested pages are not locked, so the copy is not one snapshot of the tree.
7. Decided where the issue is silent: a page whose parent is missing, trashed or unusable is a 404; the copy's block takes the indent of the original's block; a block naming an ancestor on the path, a non-Pages item or a malformed id is left out; error details carry `reason` `not_a_page` or `too_many_pages`; the route answers 201 and uses nothing of the request body.
8. `backend/packages/application/src/genericOperationGateway.ts`, in `Touches` "only if its exhaustive mapping needs the name", did not change.
9. In `tenantIsolationRoutes.test.ts` the pages of both tenants for the MCP case are seeded in a `beforeAll` of the MCP describe, because every MCP case runs inside `leavesAUnchanged`.

## Review

Two reviewers read `1627cf93^..c5900473`, read-only, without a build or a test: requirements and tests (verdict findings: one medium, one low; all five criteria covered) and project rules and architecture (verdict clear). Both findings were confirmed against the code and fixed; the focused recheck of `04160d2c..6b8f3c66` gave verdict pass with nothing unresolved and no new finding.

- Medium, fixed in `02841cce`: the root of the copy was titled from the lagging title mirror, so a page retitled in the editor was duplicated under its old title for good. The title now comes from the original's block in the parent after both row locks are held.
- Low, fixed in `8c9bebe1`: the 501-page data test built its nested pages with a superuser INSERT. The fixture now goes through production writes, and a test for a nested page without a document was added.

Follow-ups, recorded without a finding, not changed and not filed as issues:

- Rules reviewer: `page.duplicate` does not run the parent-chain walk of `2026-11-09-subpage-parent-chains-are-bounded-while-walked` that `createSubpage` runs. Fresh ids cannot close a cycle and copies sit at the depth of their originals, so a deeper chain needs a block that names a page of another parent near depth 1000, or hand-edited data.
- Rules reviewer: `copyBlockInput` hardcodes the type `todo` for `done` instead of reading `BLOCK_TYPE_RULES[type].hasDone`; today only `todo` carries `done`.
- Requirements reviewer: the 404 of a page whose parent is trashed carries the parent's id in its details, the 404 of an unusable `parentItemId` the page's id.
- Recheck: the title is read before, and the placement block is resolved inside, the final locked write of the parent's document, so a sync edit that commits in between can make title and placement come from different states of the parent. The ADR states that a title committed after the read is not in the copy.
- Host: integration tests that listen on port 0 and call 127.0.0.1 can be answered by another program's loopback listener on this delivery host. No source covers it.
