## Deviations and conflicts

1. **Context vs. tip.** The Context says `mail/send.ts` writes only a single sender edge. On the tip it writes no `senderPeople` edge; it only sets the `sender` text property. The only writer of this edge is `mail/personLinkingActions.ts`. Sender edges for sent mail are #1480's work. The seed comment states this as "today the only writer".
2. **One sender per email is not enforced by the database.** Under `many_to_many` the cardinality trigger no longer refuses a second sender edge. The writer creates one sender edge per run for the email's From address and does not remove an edge to another Person. If an address moves from one Person to another through the People reindex, a second sender edge becomes possible. The Task covers only re-linking with the same Person, and that is what the test asserts. The reviewer should decide whether #1571 or a follow-up owns that case.
3. **Missing relation.** The Task does not say what happens when an Emails database exists without `senderPeople`. The cutover throws, which fails that tenant and is reported by `runTenantCutoverMigrations`. This follows the Mailboxes addresses cutover, because the seed never produces that shape.

## Tests

- `backend/packages/data/src/__tests__/tenantCutoverMigrations.test.ts`, describe "emails senderPeople cardinality tenant cutover (issue #1457)": upgrades every tenant in its own scope; a second run changes no row; a tenant without an Emails database is left untouched; a tenant whose Emails database has no `senderPeople` relation fails and is named, while the other tenant is still upgraded.
- `backend/packages/data/src/mail/__tests__/emailsSenderPeopleCardinality.test.ts`: a fresh install declares `many_to_many`; one person sends two emails on a fresh install and both emails get a sender edge with no rollback; a populated tenant (`one_to_many` fixture) refuses the second link with `CardinalityViolationError` and leaves no sender edge, then accepts it after the cutover; re-linking an email whose sender edge exists leaves exactly one sender edge.

## Notes for dependants

- **#1480 (sender edges for sent mail) and #1571 (older mail on a new address)**: the database no longer refuses a second sender edge on one email. Writers must keep one sender per email themselves.
- **#1638, #1535, #1660 (person-level mail)**: a Person may now be the sender of many emails.
- **Populated installs** are switched by `runTenantCutoverMigrations` in each tenant's scope. A tenant whose Emails database lacks `senderPeople` fails that tenant instead of being skipped.
