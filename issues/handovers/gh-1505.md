# Handover for gh-1505

Gmail-mode mail accounts now sync through the api runtime. `createApiQueueRuntime` builds its mail sync adapters with `createMailSyncAdapters` (`backend/services/semprec-api/src/mailSyncAdapters.ts`) instead of passing none, so a Gmail sync pass downloads its mail. I did not push or open a PR.

The targeted tests pass: `mailSyncAdapters.test.ts` (9), `publicSurface.test.ts` and `mailOAuthAccess.test.ts`. The api composition suites (`queueRuntime`, `mailSyncComposition`, `approvalReplayComposition`, `actionRegistryComposition`, `shutdown`) and the data suites `mailSync.test.ts` and `gmailLabelFolders.test.ts` pass too (151 tests in 7 files). Typecheck, lint and prettier pass for the touched files. I did not run the full `pnpm run verify`.

- **`createMailSyncAdapters({ pool, env, fetchImpl? })`:** fills `createGmailClient(mailboxItemId)`, which returns a `GmailRestClient`. Its token source calls `refreshAndPersistAccessToken` (gh-1481) with `GOOGLE_TOKEN_URL`, the client id and secret from `GMAIL_OAUTH_CLIENT_ID` and `GMAIL_OAUTH_CLIENT_SECRET`, and `purpose: "gmail_api_sync"`.
- **Token reuse:** the token is kept for the life of that one client object (one sync pass). It is refreshed 60 s before its expiry. A failed refresh keeps nothing new, so the next request tries again.
- **Credential argument:** the sync job passes the credential it decrypted for the pass. `createGmailClient` ignores it on purpose, because the refresh reads the stored token under its row lock.
- **Missing configuration:** with either Gmail key unset, the factory has no `createGmailClient` and logs one `warn` naming the missing keys, never their values. The process starts. A Gmail sync then fails with "No Gmail adapter configured for this composition root".
- **Failure path:** a 400/401 from the refresh is `MailReauthorizationRequiredError`. It passes through the client unchanged, and the sync job sets `needsReauthorization`. No Gmail request is made without a token.
- **`fetchImpl` seam:** optional on `GmailRestClient`'s constructor, `refreshAccessToken` and `refreshAndPersistAccessToken`. Each defaults to the global `fetch`. The factory's `fetchImpl` option passes through to all three, so a fake Google covers both the token endpoint and the Gmail API.
- **Exports:** `GOOGLE_TOKEN_URL`, `GmailRestClient` and the type `MailSyncAdapterFactory` are exported from `@semprec/data`. The frozen list in `publicSurface.test.ts` is updated to match.
- **Config:** the Gmail keys comment in `deploy/shared/env/api.env.example` names the real consumer.

Tests (`backend/services/semprec-api/src/__tests__/mailSyncAdapters.test.ts`):

- A factory test for each unconfigured case (id unset, id empty, secret unset, both unset): no Gmail client and one warning naming the missing keys.
- A token test for reuse within expiry, a refresh inside the 60 s margin before the request, and no token shared between clients.
- A rejected refresh (401) that makes no Gmail request and leaks neither the secret nor the refresh token.
- Sync passes through `createApiQueueRuntime` against a fake Google endpoint: one refresh for the whole pass and the messages ingested; a 401 gives `needsReauthorization` with no secret or refresh token in `last_error` or the job error; the unconfigured case fails with the adapter message.

Notes for dependants (#1686, #1746, #1637, #1739, and the IMAP and Graph transports #1510 and #1508, which fill the same factory):

- Get a Gmail client only through the factory's `createGmailClient`. Build `new GmailRestClient(...)` directly only in tests.
- The first Gmail request of a pass runs its token refresh on a second pooled connection, while the reconcile transaction holds the first. Check pool sizing before adding parallel Gmail calls.
- The token refresh needs the ambient tenant scope. The sync job provides it. Code that builds a client elsewhere needs its own scope.
- Calls that overlap on one client can each refresh. The row lock in `refreshAndPersistAccessToken` serialises them, so the result stays correct.
- This issue reads the stored credential and the sync-state row. It writes the credential back only when the provider sends a rotated refresh token. It never creates either row. Connecting a mailbox (#1686) creates them in production. The tests seed them with `storeCredential` and `ensureMailAccountSyncState`.
- Known gap, not fixed here: `GmailRestClient.request` and `refreshAccessToken` read the whole response body with no size cap. This predates the issue and is outside its Touches list. It is a candidate follow-up under the io-hardening outbound rule.
- Scope note: the issue named `handleMailAccountSyncTask`. The job's entry point is `handleSyncMailAccountTask` in `mailSyncJob.ts`. The tests run through the composition root instead.
