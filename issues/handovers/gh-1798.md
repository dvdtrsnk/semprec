## What was delivered

- `config.systemKey` (optional, non-empty string) on `viewConfigSchema` (`views/viewConfig.ts`). Migration `0153_views_system_key_unique.sql` adds the partial unique index `views_database_system_key_uq` on `views (database_id, (config->>'systemKey')) WHERE config ? 'systemKey'`. A unique violation on create or patch of a view is mapped to `ConflictError` in `viewsStore`.
- `packages/data/src/tasks/todayView.ts`: `TASKS_TODAY_VIEW_KEY = "today"`, `tasksVisibleFilter()`, `tasksTodayFilter({ openOnly })`, `createTasksTodayView(client, tasksDatabaseId, viewTypeRegistry)` and `countTasksToday(client, now?)`.
- The Today view (table type, `isDefault: false`, `createdBy: "system"`, `config.systemKey: "today"`, stored name `Today`) is seeded after phase 3 of `seedTenDatabases` and created for existing tenants by `runTasksTodayViewCutoverMigration` (`tasks/todayViewCutoverMigration.ts`), registered in `runTenantCutoverMigrations`. It is idempotent (an existing view with the key is left untouched) and skips a tenant without a Tasks database.
- `assertViewWritable` refuses any view whose config has `systemKey` for every actor (user, ai_agent, system) as 403 `owner_violation` with `details.reason: "system_owned"`, ahead of the agent rules, which are unchanged for other views.
- Review fix: `assertSystemKeyWritable` (`chokePoint/authorization.ts`) makes the system the only writer of the key. `viewOps.createView` and `viewOps.patchView` refuse a config that contains `systemKey` from a `user` or `ai_agent` actor with 403 `owner_violation` / `system_key_reserved`; the seed and cutover keep calling `viewsStore.createView` with `createdBy: "system"`.
- New accepted ADR `docs/adr/2026-11-13-a-view-system-key-is-unique-per-database-and-written-by-the-system-alone.md` (key, partial unique index, refusal of every actor, who may write the key, adoption by later system views).

## Deviations from the specification and spec seams

1. The Task says `403 system_owned`; the existing agent refusal is 403 with code `owner_violation` and `details.reason: "system_owned"`, so human and agent refusals share that shape.
2. `countTasksToday` takes an optional `now` and runs the `countItemsGrouped` statement in the caller's transaction instead of `countItemsBatch`, which opens its own transaction.
3. The `ConflictError` mapping of the new unique index in `viewsStore.createView` and `patchView` is outside Touches, needed so a violation is not a 500.
4. `tenDatabases.test.ts` was brought in line (Tasks now has a second, non-default view). The HTTP test in `services/semprec-api/.../viewsHandler.test.ts` and the ADR are outside Touches.
5. The stored view name `Today` is an English fallback name like other seeded view names; clients look the view up by `systemKey`.
6. `assertViewWritable` is also called by the `view_items` membership paths, so a curated view with a `systemKey` is refused there too, as extending the shared helper implies.
