## What was delivered

Each step of `GET /api/agent-runs/:id/steps` now carries a localized `title`, `targetName`, `change {property, from, to}`, `summary` and `approvalRequestId`. A tool step whose stored result has `details.approvalRequestId` has kind `approval`. No step exposes tool arguments, result content, model text, thinking or raw error text.

- Catalog: `packages/data/src/agentRuns/agentStepCatalog.ts` (`stepTitle`, `stepSummary`, `stepKindTitle`) over `agentStep.*` keys added to the existing module catalogs `agentRuns/i18n/{cs,en}.json` (the catalog `agentRunErrorSummary` already reads). `getAgentRunCatalogs` (renamed from the private `getAgentRunErrorCatalogs`) is exported from `agentRunErrorSummary.ts` so both share the loader.
- Projection: `buildAgentRunStepPage` now returns `AgentRunStepDraft` (core shape plus internal facts); `projectAgentRunStepPage` (new `agentRunStepProjection.ts`) loads the targets and turns drafts into the response shape. Targets (item display name, database owner module) are resolved in at most three queries per page by `loadAgentRunStepTargets`; the `end` step summary uses `countAgentRunToolSteps` (one SQL count in `agentRunEventsStore.ts`).
- Handler: `agentRunHandler.ts` passes `identity.user.locale`; the 404 rule of gh-1821 is unchanged.
- Barrel: `projectAgentRunStepPage`, `stepSummary`, `stepTitle` and `countAgentRunToolSteps` are exported from `@semprec/data` and listed in the frozen list of `publicSurface.test.ts`.

## Deviations and spec seams

1. The catalog keys live in the module catalog `agentRuns/i18n`, not in `seed/i18n` (the Task allows this when the seed files are not the catalog for server-produced strings).
2. `agentRunStepProjection.ts` (database glue) is outside the Touches list; the pure projection and the shape stay in `agentRunStepPages.ts`. Two existing assertions in `agentRunStepPages.unit.test.ts` strip the facts and gain `approvalRequestId: null`.
3. `countAgentRunToolSteps` was added to `agentRunEventsStore.ts` for the `end` step summary.
4. The stored result has no structured result count (`details` holds only error, approvalRequestId and changes), so summaries carry no result count; counts are the changed properties of `item.patch` and the tool and approval counts of the `end` step.
5. Target ids written by the model are used only for generic operations, never for MCP tools; ids that are not uuids are skipped before the batched lookup; trashed items are included so an `item.delete` keeps its name.
6. New users have locale `cs`, so integration tests set the locale explicitly.
7. The redaction of gh-1827 is detected defensively by the fixed marker `[redacted: sensitive]` in the stored result (text, content string or text block). The marker `REDACTED_SENSITIVE_MARKER` is now on the tip in `agent-runtime/src/sensitiveToolResult.ts`; the data package does not import it (no dependency of data on agent-runtime), so the string is duplicated by design.

7a. Catalog reconciliation at the landing: the tip had gained the generic operations `page.ensureJournalPeriod` and `page.mergeJournalDuplicates` after the chain was cut, and the chain's own test "has a title for every generic operation in both locales" failed on the merged tree. The landing added `agentStep.title.operation.page.ensureJournalPeriod` and `...page.mergeJournalDuplicates` to `agentRuns/i18n/cs.json` and `en.json` (data only, no logic). Any generic operation added later needs a title key there, or that unit test fails.
