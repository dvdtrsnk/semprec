# gh-1527 implementation handover

## Behavior and interfaces

The stored pi tool result `details` now carries two optional structured fields next to `error`:

- `approvalRequestId`: set when the call created an approval request. Generic operations take it
  from `ApprovalRequiredError.details.approvalRequestId`; MCP tools from the request created in
  `createApprovalGatedMcpInvokeTool`. The sentence the model sees is unchanged.
- `changes: {key, before?, after?}[]`: set only for a successful `item.patch`. `before` is read from
  the `previous` field of the operation output (added by gh-1429, written inside the write
  transaction); a key without a reported previous value has no `before`. `after` is the call argument.
  Strings (and JSON-serialized objects) longer than `TOOL_CHANGE_VALUE_MAX_LENGTH` (200) are shortened.
  A `longText` property records only `{key}`. Property types are read with
  `listPropertiesByDatabase` in a separate read transaction (metadata only, not a previous value); if
  that read fails the error is logged and `changes` is omitted entirely, so no `longText` content can
  leak and the successful patch is not reported as failed.

Types: `GenericOperationAgentToolResult` gained `approvalRequestId?` and `changes?`; `mcpInvokeTool.ts`
exports `McpInvokeToolResult` (`McpInvokeResult & {approvalRequestId?}`) as the `McpInvokeTool` return
type. `agentSessionComposition.ts` copies both fields into `details` for generic and MCP tools.
`toolEventPayload.ts` exports `ToolResultChange`, `ToolResultDetails` and `ToolResultEventPayload.details`;
`parseToolEventPayload("tool_result", ...)` fills `details` from `result.details`, dropping malformed
`changes` entries and ignoring a non-string id instead of throwing.

## Tests

- `genericOperationAgentTools.test.ts` (integration): approval id equals the `approval_requests.id` with
  unchanged text; due-date patch gives `{key, before, after}`; long string shortened and `longText`
  stores no content; failed patch and read store neither field.
- `mcpInvokeTool.test.ts`: `approvalRequestId` equals the created request id.
- `agentSessionComposition.unit.test.ts`: both fields reach `details` for generic and MCP tools; absent otherwise.
- `toolEventPayload.unit.test.ts`: details parsing and malformed-entry dropping.

Ran: tsc -b for agent-runtime and semprec-agents, ESLint and Prettier on both, the unit files (84 passed)
and the two integration files (37 passed; the latter outside the sandbox for embedded Postgres).
The "operation without previous values omits before" case is covered by the parser/composition
shape and the `Object.hasOwn(previous, key)` branch only indirectly; the real `item.patch` always
returns `previous`.

## Notes for dependants

Readers (gh-1618, gh-1885, gh-1860, gh-1847) should use `parseToolEventPayload(...).details`. Changes
are keyed by canonical property keys exactly as in the call arguments. No schema, migration or
data-package change; full verify and review remain with the integrator.
