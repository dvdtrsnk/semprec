# gh-1463 — resolve notifications when their source is handled

Implemented from integration tip 6a87f7ce06d21248f9f8fdebd08c287f16dce017.

Migration 0098_notifications_resolved_at.sql adds nullable `notifications.resolved_at timestamptz` and the partial index `notifications_resolved_idx` on `(tenant_id, user_id, resolved_at) WHERE resolved_at IS NOT NULL`. `NotificationRow` gains `resolvedAt` and `NOTIFICATION_COLUMNS` selects `resolved_at`.

`resolveNotificationsBySource(client, { sourceTable, sourceId })` in `notifications/notificationsStore.ts` (exported through `index.ts`) runs one locked UPDATE over the unresolved rows of that source: `resolved_at = now()`, `read_at = COALESCE(read_at, now())`. It returns the resolved rows and, after commit, publishes one `notification_read_state` per user for the rows whose `read_at` this call newly set. Already resolved rows are not matched, so a replay changes and publishes nothing. An already-read row is resolved but keeps its `read_at` and is not re-announced.

`decideAndEnqueueApprovalRequest` calls it with `approval_requests` and the request id only on outcome `decided`, in the decision transaction. `unchanged` and `null` outcomes resolve nothing.

Tests (notificationsStore.test.ts, four new cases): decision resolves and reads the notification with exactly one event; replay changes nothing and sends no event; rolled-back decision leaves it untouched with no event; by-source resolve is scoped to the named source, spans users and keeps an already-read `read_at`. publicSurface.test.ts lists the new export. Targeted vitest of notificationsStore, approvalRequestExecution and publicSurface, plus tsc and eslint on touched files, were run; full verify NOT RUN.

Notes for dependants: #1915 and #1944 call the same helper with their own `sourceTable`/`sourceId`. Silent dismiss (#1826) and open-time reconcile (#1559) can read `resolved_at` (`resolvedAt`); the unread list query is unchanged and still filters on `read_at`.
