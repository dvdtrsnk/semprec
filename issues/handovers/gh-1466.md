# gh-1466 — Push Semp problems once per problem

Repository-Issue: gh-1466

## Delivered behavior and production wiring

- Migration `backend/packages/data/src/db/migrations/0121_notification_kind_semp_problem.sql` drops and recreates `notifications_kind_check` with the eleven existing kinds plus `semp_problem`, the pattern of migration 0035. Widening only; no data change.
- `raiseProblem` (`backend/packages/data/src/semp/sempProblemsStore.ts`) writes a `semp_problem` notification in the caller's transaction when its outcome is `created` or `escalated`. A `merged` outcome writes nothing. The notification has `userId` of the problem, `sourceTable` `semp_problems`, `sourceId` the problem id, `transitionInstance` `<problemId>:<severity>`, `payload { severity }` read back from `RETURNING`, and `linkHref` `?page=semp-status&id=<problemId>`.
- Kind policy (`backend/packages/data/src/notifications/notificationKinds.ts`): `semp_problem` is `{ category: "problems", severity: "payload", push: true }`, typed by the new `PayloadSeverityKindPolicy`. The problem sources `mail_sync_error`, `mail_sync_stalled`, `backup_restore_failed`, `process_stale`, `agent_run_error`, `heartbeat_error`, `automation_error`, `agent_guidance_drift` and `queue_backlog` are now `push: false`. Together with `agent_guidance_drift_resolved` (already `push: false`), only `approval_pending` and `semp_problem` are pushed.
- Fan-out (`backend/packages/data/src/notifications/notificationFanoutJob.ts`): `policyForNotification` takes a `semp_problem`'s severity from `payload.severity`. A payload without a severity throws `has no severity in its payload`; a value other than `critical` or `warning` throws through `assertKnownValue`. Both throw before any `push_deliveries` row is claimed. `pushInterruptionLevelFor` is unchanged.
- Copy: `notification.semp_problem.title` in `notifications/i18n/en.json` ("Something needs your attention") and `cs.json` ("Něco vyžaduje vaši pozornost"). The title takes no parameter; see the notes below.
- Fixtures moved from source kinds to `semp_problem`: the default fixture and the warning fixtures of `notificationFanoutJob.test.ts` (the warnings were `heartbeat_error`, which is never pushed now, so those tests would have passed for the wrong reason), and the `notificationFanout` seed of `services/semprec-api/src/__tests__/tenantIsolationJobs.test.ts`.
- `restoreTestResult.test.ts`: `listNotifications` filters to `backup_restore_failed`. A failed restore test also raises its problem, which writes a `semp_problem` notification per admin.
- `notificationKindPolicy.unit.test.ts`: the "pushes every other kind" assertion became "pushes only `approval_pending` and `semp_problem`".

## Tests

`backend/packages/data/src/__tests__/sempProblemNotification.test.ts` (new, integration, 17 tests):

- A new critical problem writes one notification (kind, transition instance, payload, link, catalog title) and the fan-out sends one `time-sensitive` push.
- Four critical sync failures of one mailbox write one problem with four occurrences, one `semp_problem` notification, four stored `mail_sync_error` notifications and one push.
- Four warning failures send nothing at the default `critical` level and one push once the level is `all`.
- Raises at the same or a lower severity give `created`, `merged`, `merged` and one notification.
- A warning followed by a critical raise gives `escalated`, two notifications (`:warning`, `:critical`) and one push, for the critical one.
- A rolled-back caller transaction leaves no problem and no notification.
- The `notifications_kind_check` definition contains `'semp_problem'`.
- Each of the ten problem kinds, including `agent_guidance_drift_resolved`, is stored and never pushed, even at problems level `all`.

## Notes for dependants

- Pushes now depend on the problem's severity. Under the default `critical` level a warning problem is stored and not pushed: an ordinary mail sync failure (`mailSyncJob`), guidance drift and a failed library automation are all `warning`. Before this change `mail_sync_error` was pushed as critical on every failure, so ordinary sync failures are no longer pushed by default. The critical raises still push: a revoked mailbox credential (`mailSyncJob`), a failed backup restore test (`observability/restoreTestResult.ts`) and a stale agents process (`observability/observabilityCheckSystem.ts`). This is a visible behaviour change; the reviewer should confirm it is intended.
- A problem source's own notification still appears in the in-app list and is never pushed. A producer that raises a Semp problem must not count on its own kind to push.
- `raiseProblem` writes the notification in the caller's transaction, so the caller must already hold a tenant-scoped transaction (it already must, for the problem row).
- `semp_problem` notifications carry `source_table` `semp_problems` and `source_id` the problem id. #1829's collapse id can key on that id.
- Title: the push text is the generic catalog entry. The problem's own text is rendered at read time (#1555) and the store holds no user text, so no problem title exists at write time. The Task asked for a title parameter; it is not implemented for that reason.
- Rollback: migration 0121 is additive, but the previous release has no `semp_problem` in `NOTIFICATION_KINDS`. Its `mapRow` in `notificationsStore.ts` throws on such a row, so unread-notification reads fail for a user who has one, and its fan-out finds no policy for the kind. Decide this before rolling back once `semp_problem` rows exist.
- Migration ordinal: 0121, the next free one on the integration tip. The sibling worktrees `wf_1f8d1835-203-37` and `-38` had no 0121 file when checked; a collision is for the integrator to renumber.
