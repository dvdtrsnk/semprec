## What was delivered

`POST /api/calendar/invitations/:id/respond`, the user's answer to an incoming invitation. One transaction locks the invitation row `FOR UPDATE` and then applies, in this order: 404 for an unknown, foreign or trashed invitation (the same error for all three); 400 for a kind pairing that does not hold (`acknowledged` on an invite, `accepted`, `tentative` or `declined` on a shared-calendar notice); 409 `conflict` for a cancelled invitation; no write at all when the answer equals the stored status. For `accepted` and `tentative` it creates a meeting Event in the chosen calendar (`calendarId` of the body, else the `suggestedCalendar` edge, else the default calendar through the create hook of ADR 2026-11-11), links the invitation to it through its `event` relation as the calendar module, keeps a live linked Event as it is, and restores a trashed linked Event instead of creating a second one. For `declined` it moves the linked Event to the trash (soft delete) and keeps the edge. `status` and `respondedAt` are the last write, made as the calendar owner process with `allowedSystemKeys`, so a generic PATCH of `status` stays 403 (`owner_violation`).

## Entry points and contracts dependents build on

- Route: `POST /api/calendar/invitations/:id/respond`, body `{ response: "accepted" | "tentative" | "declined" | "acknowledged", calendarId?: uuid }`, strict (an unknown key is 400 on that key). It returns the invitation, its linked Event and its suggested calendar. Route matrix entry `calendar invitation respond` (tenant class, not public) in the slice `backend/services/semprec-api/src/routeMatrix/calendar.ts`; `ROUTE_HANDLER_FILES` maps it to `packages/data/src/calendar/invitationRouteHandlers.ts`; the isolation case of the same name is in `tenantIsolationRoutes.test.ts`.
- Handler: `createRespondToInvitationRouteHandler` in `packages/data/src/calendar/invitationRouteHandlers.ts`, exported from `index.ts` and re-exported by `calendarModuleManifest.ts`; the manifest declares the custom route `respondToInvitation` with justification `transactional-semantics`. `publicSurface.test.ts` lists the new export in sort order.
- Writer: the Event is written through `createEventInCalendar` (the calendar is passed at creation, so the create hook adds no second edge); the event edge through `createRelationWithClient` with owner process `calendar`; trash and restore through `itemDeleteWithClient` and `restoreItemWithClient`; the answer through `updateItemWithClient`. No direct SQL beyond store reads and row locks.
- Event shape: Event title property is `name` (the Events seed key), `type` is `meeting`, times are wall clock in the tenant zone; an all-day invitation gives `date` and, when it spans days, `endDate` (the parser stores the inclusive last day).
- No table, migration, job name or operation is added.

## Deviations from the specification and spec seams

1. The Task says to add the route to `routeMatrix.ts`; the entry lives in the slice `routeMatrix/calendar.ts` that `routeMatrix.ts` spreads (spec seam).
2. The Event title property is `name`, not `title`.
3. The generic PATCH 403 is proven at the choke point and, additionally, over HTTP in the isolation case.
4. Decisions the Task leaves open: a trashed invitation answers the same 404 as an unknown id; an invitation without `kind` is an invite; with no `calendarId` and no `suggestedCalendar` edge the Event takes the default calendar; a `suggestedCalendar` that is no longer a live own calendar fails 400 `validation_failed` on `calendarId`; a stored `status` or `kind` that does not read, or a start that does not read, fails with a plain error (500) and writes nothing; the body is strict.
5. A timed invitation ending at midnight of the next day becomes an Event with `endDate` and `timeTo` 00:00 (not 24:00).
6. Fix round: a timed invitation whose end is its start (a zero-length meeting) is treated as no end, so the Events pre-write default end applies; an end before the start stays refused with 400 on `timeTo`.
7. Fixtures: invitations are created in tests with `createItemWithClient` as the calendar module (the ingest's own write), because the ingest is the only production writer.
