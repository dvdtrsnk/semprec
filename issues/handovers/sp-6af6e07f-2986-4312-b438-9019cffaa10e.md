# Handover: erase a purged tenant's idle graphile-worker queue rows

Delivered on chain `e1-239-backup-restore`, candidate commit `2bb495b0d058aefb64696559b94b5f0aa070a323`, landed by a `--no-ff` merge on `feature/backend-parallel` as the first chain of a train with `e1-242-route-matrix-test`. The chain name does not match the topic of the source (the queue rows of the tenant purge); the source was implemented as specified.

**What changed.** In `backend/packages/data/src/tenancy/tenantPurgeJob.ts`, the finalisation of the tenant purge now ends with `eraseIdleQueues`, inside the same finalise transaction and after the `tenants` delete. It sets a transaction-local `lock_timeout` of 2 s with `set_config(..., true)`, runs `LOCK TABLE graphile_worker._private_jobs IN SHARE ROW EXCLUSIVE MODE`, and deletes the tenant's idle rows of `graphile_worker._private_job_queues`: `right(queue_name, 37) = ':' || <tenantId>`, `locked_at IS NULL`, and no `_private_jobs` row refers to the queue. The statement is fully parameterised. It logs a count only, with step `queues`. A check after the delete throws `Tenant purge left rows behind in: graphile_worker._private_job_queues` (the table name only, no queue name and no tenant id) when a matching row remains, which rolls the whole finalisation back, so the tenant stays `deleting` with no tombstone and the next sweep retries.

**Why.** The tenant lanes of the queue (`<lane>:<tenantId>`) leave idle rows in graphile-worker's private queue table after the purge removed the tenant's jobs. The rows carried the id of a purged tenant. The table lock makes the presence check and the delete atomic with respect to `add_job`, which inserts the queue row with `on conflict do nothing` and has no foreign key from `job_queue_id`, so a concurrent enqueue cannot be orphaned.

**Contracts dependents build on.** No new export, route, operation, table, migration or job name. Behaviour a caller may rely on: after a completed purge no `_private_job_queues` row ends with `:<purged tenant id>`; only the tombstone in `tenant_deletions` carries the id. Another tenant's queue rows are never touched, including a name that contains the purged id elsewhere. A queue that is locked by a running job or still holds a job defers the purge to a later sweep. While another transaction holds an open enqueue into the tenant's lane, finalisation fails with SQLSTATE `55P03` and the tenant stays `deleting`. The lock stall is bounded by the 2 s `lock_timeout` and happens once per finalisation attempt (a tenant deferred by a held queue takes the lock again on each sweep).

**ADR.** `docs/adr/2026-11-15-tenant-purge-erases-the-tenants-queue-rows.md` (area backend, standalone) extends the accepted purge ADR of 2026-10-18 and the queue-lanes ADR of 2026-10-08 without editing them. It states the decision, the bounded enqueue stall and the safety argument against `add_job`.

**Files.** `backend/packages/data/src/tenancy/tenantPurgeJob.ts`, `backend/packages/data/src/__tests__/tenantPurge.test.ts`, the new ADR.

**Tests.** `tenantPurge.test.ts`: the first test is extended to enqueue into two lanes and assert that no queue row of the purged tenant remains and that no job has a missing queue, and that tenant A's idle and busy lane rows are unchanged. New cases: a lookalike queue whose name holds the purged id outside the `:<tenantId>` suffix is kept; a deleting tenant stays deleting while one of its queues is locked (with a locked job, then a locked queue without a job) and completes once idle, with the message naming only the table; a committed job enqueued between the jobs step and finalisation defers the purge and the next run erases the queue; an open enqueue from another transaction makes finalisation fail with `55P03` and the next run, after commit, completes with no job without a queue. The worker reports four manual mutations of the statement (no `LOCK TABLE`, no `locked_at` predicate, no `NOT EXISTS`, `LIKE` instead of the suffix), each failing exactly the intended test; this was the worker's evidence and the queue runner did not repeat it.

**Deviations and spec seams.** None from the Task. The test reads graphile-worker's private tables only through local helpers that name the version checked (0.17.3); the locked-queue state is set with raw `UPDATE`s, with a reason comment, because only a running task produces it.
