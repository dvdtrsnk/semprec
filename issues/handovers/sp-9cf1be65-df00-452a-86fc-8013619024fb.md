## What was delivered

- A Tasks create or update that names `status` with `null`, an empty string or a non-string is refused with a `ValidationError` on `status`, and nothing is stored. A create that does not name `status` stores `notDone` through the property default. An update that does not name `status` passes through unchanged, so a stored task without a status can still be renamed or moved. A proposal is refused the same way, because `prepareTaskProposal` calls `prepareTaskWrite`.
- A converter `backfillTaskStatus` gives every task without a status (missing, null or empty) the status `notDone`, trashed tasks included. It keeps a task that has a status with its status and its `updated_at`, and a second run changes nothing. It is registered as the Tasks data transition 1.3.0 to 1.4.0.
- The tasks of a mail thread detail (`GET /api/mail/threads/:threadId`) list a trashed project or person as `{ id, state: "trashed" }` with no name; live ones carry `state: "active"`. Trashed people come after the live ones (live by name, trashed by id). Tasks are ordered by `status = 'notDone'` first and then as before; the stored status string is returned. A task in the trash is still not listed.
- New ADR `docs/adr/2026-11-13-a-task-always-has-a-status.md`.

## Deviations from the specification and spec seams

1. No numbered migration was needed, so `check-migration-numbering` does not apply to this source.
2. The status ordering follows the Task literally: `(status = 'notDone') DESC` has no branch for a missing status. Before the 1.3.0 to 1.4.0 transition has run for a tenant, a stored status-less task sorts first and fails `taskRow.parse` (status is `z.string()`) in that tenant's own thread detail. The new ADR records this window under Consequences; it is an availability matter confined to the tenant, not a security defect.
3. `taskStatusRequired.test.ts` inserts one legacy status-less row with raw SQL (commented: the choke point can no longer produce it) to prove that a write naming no status still succeeds.
4. A `prepareTaskProposal` test case was added beyond the listed tests, since the Task names that call site; the title of the `eventDateMigration` test now says "four Tasks migrations".
