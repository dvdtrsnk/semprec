## What was delivered

- Operation `database.facets`, capability `core.item.read`, non-destructive (`nonDestructive("core.item.read", "read")` in `capabilities.ts`, as `item.count`). Input (`DatabaseFacetsInputSchema`, strict): `{ databaseId, filter?, facets: [propertyKey | { path: [relationKey, relationKey] }], extra?: { open: <filter> } }`, one to twenty facets, the same filter limits as `database.query` (`filterNodeSchema`, re-validated in `facetQuery.ts`).
- Output `DatabaseFacet[]` in request order: `{ property | path, all, open?, values: [{ value, label?, color?, count }] }`. `all` is the count under the filter without the facet's own conditions; the "no value" entry is `{ value: null, count }`; `open` is present exactly when the call carried `extra.open` and counts the items matching the filter AND the open filter.
- Exclude-self: `excludeFacetConditions(filter, facet)` removes every condition on the facet's property that is a direct child of the top-level `and` (or the root when it is such a condition), at any depth of nested `and`; for a path facet it removes conditions with the same path (`relation_path_contains`). A condition on the facet's own property under `or` or `not` is a 400 `validation_failed` naming `filter`. Free-text search is never applied. Trashed items are never counted.
- Per property type: group selects (status-like) list every option in `config.options` order including count 0; other selects and multi-selects list only occurring values; text lists the 20 most frequent values (equal counts in byte order); checkbox returns `true` and `false`; date returns one entry per relative-date preset with a count above 0 and a "no date" entry only when some item has none (a custom range gets no entry); number returns one entry per stored numeric preset counted by its comparison; a relation lists the 20 related items most items have (an item counts in each of its targets) with label and color from the target; the areas facet and every relation or path the area filter declared by a module manifest takes the area through list every area including 0. `label` and `color` come from the stored option, the related item or the catalog of the caller's language, never from client text; a stored color is returned only when it is `#RRGGBB`.
- Archived databases: targets in an archived database are not listed and items linked only there count under "no value"; every count of an archived database is 0 and returns to the normal count when it is restored; no area is listed while the database of the areas is archived.
- One counting statement per facet over the items of the database, every value a bound parameter. The only interpolated identifiers are `item_a` and `item_b`, chosen by `relationHop` from two fixed names.
- Tenancy: the database is resolved with `databasesStore.getDatabase` inside the same `withTransaction` as every counting statement, so a foreign id and an unknown id fail alike with the not-found a database query gives. Module-manifest metadata is loaded before the transaction (`loadFacetMetadata`, memoized, cleared on failure) and does not depend on the id.
- REST `POST /api/databases/:id/facets` (route entry `database facets` in `routeMatrix/items.ts`; the comment of `routeMatrix/databases.ts` names it), handled in `itemsHandler.ts`, which rejects unknown body fields and takes the actor from the identity. MCP and agent-tool tools derive from the catalog.
