## What changed
- **Signal** (`backend/packages/data/src/tenancy/tenantStatusSignal.ts`):
  - `TENANT_STATUS_CHANNEL` is `semprec_tenant_status`.
  - `publishTenantDeactivated` sends the NOTIFY inside the caller's transaction. Postgres only delivers it on commit and drops it on rollback.
  - `startTenantDeactivationListener` runs in system scope on one dedicated client:
    - It accepts only `{ tenantId: <uuid> }` payloads; anything else is logged and dropped.
    - It reads the `suspended`/`deleting` tenants on the first connect and on every reconnect.
    - After a connection error it retries with backoff from 200 ms up to 5 s.
    - A failing handler is logged and the listener keeps going.
    - It releases its client on every exit path. A `closed` flag set first means a reconnect that finishes after `close()` releases its client instead of attaching it.
  - It is exported from the package index and added to `EXPECTED_RUNTIME_EXPORTS`.
- **Publisher:** `suspendAccount` publishes in the same transaction as the status change. Reactivation publishes nothing.
- **Consumers** (calling any of them twice does nothing the second time):
  - `SyncServer.closeTenant` closes that tenant's sockets with 4401 and the reason `account deactivated`.
  - `MailLiveSyncRoot.stopTenant` waits for any discovery pass in progress, then stops that tenant's hosted lifecycles.
  - `SempConversation.dropTenant` handles the idle case and the turn-in-progress case as the issue describes. It has a test but isn't wired into any process, as the issue specifies.
- **Wiring:** `semprec-api` starts the listener after the sync server and mail root exist. On shutdown, `createGracefulShutdown` closes the listener first.
- **ADR:** `docs/adr/2026-10-17-tenant-deactivation-tears-down-in-process-state.md`.
