## What was delivered

- Three link rules in the `linkRules` of the system-databases manifest: `transcriptProjectFromEvent` (`Events.project` to `Transcripts.project` via `Transcripts.event`), `transcriptPeopleFromEvent` (`Events.people` to `Transcripts.people` via `Transcripts.event`, without the tenant's own person) and `transcriptCompanyFromProject` (`Projects.company` to `Transcripts.company` via `Transcripts.project`).
- The first copy and its value-link rows are written in the transaction that writes the via edge, in whichever process writes it: the match step and the create step of `semprec-transcribe`, the generic relation endpoint and the card confirm of `semprec-api`, Semp's `relation.put` in `semprec-agents`. A rule fills only an empty property; a property that already holds a value keeps it and gets no link.
- Later changes of the Event's project or participants, or of the project's company, reach the transcript through the existing `valueLinksPropagate` job while the link is `on`. A value the user or Semp changed stops following.
- The company follows a replaced project. When the Event's project changes, the transcript gets the new project and the new project's company, and all three links stay `on`. When the Event loses its project, the transcript loses project, company and the company link; a project the Event gets later brings both back.
- Link rule schema: a rule may carry `valueFilter: { omit: { databaseKey, propertyKey } }`. The items that relation points to are left out of the copied values. The people rule names System settings `selfPerson`. The filter is applied on the first copy, in the propagation job and on `link.relink`, and the links are recomputed when the own person is chosen, changed or cleared afterwards.
- A rule copies only live items of a relation source. An Event's trashed project or participant, or a project's trashed company, no longer fails the write of the via edge.
- The company link ends with the Event. When the Transcripts `event` edge is removed or the Event is moved to the Trash, the transcript's `company` value link is deleted with its source rows in the same transaction, the company edge stays, and the transcript is announced after the commit. The removal of the edge also detaches the Event from the transcript's `project` and `people` links whatever their state. Restoring the Event reconnects nothing.
- `GET /api/transcripts/:id` returns `context: { project, company, people }` with the link state and the sources of each value.
- ADR `docs/adr/2026-11-10-transcript-values-are-inherited-by-link-rules-whichever-process-writes-the-edge.md` (accepted, standalone).
- Existing transcripts are not backfilled. A transcript whose `event` edge was written before the rules existed takes over nothing from that Event.

## Contracts dependents build on

- Rule keys: `transcriptProjectFromEvent`, `transcriptPeopleFromEvent`, `transcriptCompanyFromProject`, declared in `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` after `fileCompaniesFromProjects`.
- Manifest type and schema (`backend/packages/module-registry/src/manifest.ts`): `ModuleLinkRuleDescriptor.valueFilter?: { omit: ModuleLinkRuleEndpoint }`, strict in the zod schema. `omit.databaseKey` is the owner module id of a system database (`systemSettings`), not a `databases.key`, because System settings has none. `ModuleRegistry.getLinkRules()` projects `valueFilter` only for a rule that declares one. `ModuleRegistry.validateLinkRules()` does not check the filter's keys.
- Drift check (`backend/packages/data/src/manifest/driftCheck.ts`): `InvalidLinkRuleReasonKind` gained `missingValueFilterProperty` and `valueFilterNotRelation`.
- Rule resolution (`backend/packages/data/src/valueLinks/linkRuleCatalog.ts`): `ResolvedLinkRule.valueFilter: ResolvedValueFilter | null`, `resolveValueFilter(client, omit)`, `readOmittedItemIds(client, filter)`. A rule whose filter cannot be resolved in the tenant's schema is unresolved as a whole and copies nothing; a relink of its link answers 409.
- Store functions, not exported from the data barrel: `lockAllItemsInDatabaseForShare(client, databaseId)` in `chokePoint/itemsStore.ts` and `listOnValueLinkSourceItemIds(client, ruleKey)` in `chokePoint/valueLinksStore.ts`.
- Hooks: `transcriptCompanyLinkReleaseEdgeChangedHook` (relation edge changed, `op: "delete"` of a Transcripts `event` edge) and `transcriptCompanyLinkReleaseItemDeleteHook` (item delete of an Events item) from `backend/packages/data/src/transcription/transcriptCompanyLinkRelease.ts`. They are the last two entries of `backend/packages/data/src/domainWriteHooks.ts`, after `linkRuleEdgeHook`, `valueLinkSourceDeleteHook` and the People last-contact hooks. The order is meaningful: the release runs after the link engine's hook on the same edge removal. No restore hook and no purge hook is registered.
- Order for gh-1691: when it lands, its entries in `domainWriteHooks.ts` go before the two entries of this source, unless its Task names another position.
- Detail response: `context.project` and `context.company` are `{ id, name, valueKind, sources } | null`; `context.people` is a list of `{ personId, name, valueKind, sources }` ordered by name and then by id. `valueKind` and `sources` are those of `getValueLinksForItems`; a value without a link reads `valueKind: "own"` with `sources: []`. Items in the Trash are left out. A relation the tenant's Transcripts database does not have reads as no value.
- Engine behaviour that changed for every link rule, not only for transcripts:
  - a relation source's items in the Trash are not copied (first copy, propagation job, relink), and a target that held one loses that edge at the next recomputation;
  - a via edge removed by the `valueLinks` process (the propagation job, or a relink) clears the target's inherited value while the link is `on` and then deletes the link; a via edge removed by a user, an agent or another system process still keeps the value as own;
  - `link.relink` runs its relation writes in the propagation context with hop 0;
  - an edge of the relation a rule's `valueFilter` names queues `valueLinksPropagate` for every source of an `on` link of that rule, after locking the filter's row `FOR UPDATE`; `readOmittedItemIds` share-locks every row of the filter's database.
- Side effects later sources and tests meet:
  - every write of an Events `project` or `people` edge queues a `valueLinksPropagate` job and must run in a tenant scope. An unscoped write in a test fails with `TenantScopeMissingError`; the adapted tests use `inTenantZero` or `bindToTenantZero`;
  - a transcript linked to an Event also holds the Event's participants in `people`, so a test that reads every edge between a transcript and a person, or the first value link of a transcript, has to name the relation it means;
  - each relation edge create or delete resolves four link rules instead of one;
  - choosing, changing or clearing the own person queues one job per Event that feeds an `on` people link, in the transaction of that write.
- No table, no migration, no route, no generic operation, no MCP tool, no new job name and no i18n key was added. The job is the existing `valueLinksPropagate` with the `api` task affinity.
- gh-1724 (task from an action item) and gh-1743 (a trashed Event's edge) build on this source.

## Deviations from the specification and spec seams

1. The link engine of gh-1593 was changed, although the issue lists it under Out of scope. Acceptance criterion 2 (the company changes with the Event's project) could not be met by transcript-specific code: the engine deleted the company link when the propagation removed the old project edge and kept the old company. The fix round changed the engine's removal rule for a via edge that the `valueLinks` process itself removes, and made a relink run in the propagation context. The first-round reviewer asked for the product owner's decision before this change. The fixer could not obtain it, the recheck passed the change and asked that the owner confirm it, and no decision record `issues/decisions/gh-1697.md` exists. The rule is recorded in the ADR.
2. Three more engine changes outside `Touches`, each required by a criterion: trashed items of a relation source are left out (criterion 1, the via-edge write failed otherwise), an edge of the filter's relation queues a recomputation (criterion 6), and `link.relink` applies the filter (criterion 6). Files outside `Touches`: `valueLinks/linkRuleCatalog.ts`, `valueLinks/linkPropagation.ts`, `valueLinks/linkRuleEdgeHook.ts`, `chokePoint/valueLinkOps.ts`, `chokePoint/itemsStore.ts`, `chokePoint/valueLinksStore.ts`.
3. Filter database key: `valueFilter.omit.databaseKey` is the owner module id of a system database. `validateLinkRules` cannot check it; the manifest schema checks the shape and the drift check the property.
4. Detail shape: the Task lists a people entry as `{ personId, name, valueKind }`. Each entry also carries `sources`, because criterion 5 asks for the source name of each of the three. A value without a link is `valueKind: "own"`, a value the value-link read does not define.
5. Handoff declaration: the value-link mechanism has no declaration registry. The handoff of `Transcripts.project`, `company` and `people` to `valueLinks` is stated in a comment next to the three rules and in the ADR.
6. The release ends the company link whatever its origin or state, also a link that follows a project chosen on the recording card and a link the user had broken. The edge-removal hook also ends `project` and `people` links the user or Semp had broken, which the Task does not name; criterion 3 needs it.
7. The release locks link rows only, not the transcript row.
8. Five existing test files outside `Touches` were adapted, because Events `project` and `people` edges are link-rule sources now.
9. The worker implemented while gh-1691 and gh-1693 were open. gh-1693 was completed on the tip at landing; gh-1691 was not.

Follow-ups, none of them filed as an issue:

- For the owner: confirm the changed removal rule of the link engine (deviation 1).
- Low finding of the recheck: an item restored from the Trash does not return to the targets that inherit it until the source changes again or the user relinks. Proposed: an item restore hook that queues the propagation for the sources whose relation names the restored item. It also holds for `fileCompaniesFromProjects`.
- A company link the user or Semp had broken keeps naming the project it was first taken from after the project is replaced, so a relink of the company takes that project's company.
- A user who replaces the transcript's project by hand keeps the old company as an own value.
- A copy in a transaction with a fixed snapshot has no ordering guarantee against a change of the own person. A writer of `selfPerson` other than `setSelfPersonId` can end in a PostgreSQL deadlock error with a concurrent copy.
- Observation of the requirements reviewer: the case "keeps the company link when the transcript itself, not its Event, is moved to the Trash" would also pass without the Events guard in `transcriptCompanyLinkReleaseItemDeleteHook`.
