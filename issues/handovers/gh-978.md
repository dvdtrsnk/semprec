The tenant scope primitive is in, and `withTransaction`, `pool.query` and `pool.connect()` now apply it. `pnpm run verify` in `backend/` passed (exit 0). I did not run `web/`'s verify because nothing under `web/` changed. Everything is committed on this branch.

**What changed**
- **Scope primitive:** `backend/packages/shared/src/tenantScope.ts` has `runInTenant`, `runAsSystem`, `runDetachedAsSystem`, `currentTenantScope` and `enforceTenantScope`. It also has the two error classes and the `warn`/`strict` modes read from `SEMPREC_TENANT_SCOPE`. It is exported with one line in `shared/src/index.ts`.
- **`withTransaction`:**
  - It enforces the scope before acquiring a client.
  - With a scope, it sets `app.tenant_id` right after `BEGIN`, for every isolation level.
  - A failing `set_config` takes the existing rollback/release path.
  - On a `createPool` pool it acquires the client without the session-level hook.
- **`createPool`:**
  - `connect()`, in promise and callback form, sets the GUC for the session. Release runs `RESET`, and a failed reset destroys the connection.
  - A scoped promise-form `pool.query` runs as `BEGIN`, a transaction-local `set_config`, the statement and `COMMIT`. `ROLLBACK` runs on failure, and a failing `ROLLBACK` destroys the client.
  - With no scope in warn mode, `pool.query` passes straight through to pg-pool and enforces only once.
  - Every physical connection opens inside `runDetachedAsSystem("database-connection", …)`.
- **ADR:** `docs/adr/2026-10-05-tenant-scope-propagation.md`.
- **Tests:** `tenantScope.unit.test.ts` (21 tests) and `tenantScopePool.test.ts` (9 tests, on `createPool(process.env.TEST_DATABASE_URL)`) cover the acceptance criteria.

**Behaviour to know about**
- A callback-form `pool.query` is not scoped per statement. It goes through pg-pool's own `connect`, which is now the scoped one, so it still gets the session-level scope. The issue only specified the promise forms, so I recorded this in the ADR.
- A second `release()` on a scoped checkout is a silent no-op, because the issue requires `release()` never to throw. pg-pool normally throws on a double release.
