## Summary

This implements issue #197, adding Gmail Pub/Sub history synchronization as the Gmail-mode analogue of #196's bounded IMAP IDLE lifecycle:

- **`gmailWatchLifecycle.ts`** — `createGmailWatchLifecycleFactory` hosts two long-lived loops per account: a renewal loop that registers/renews `users.watch` daily (well inside its 7-day validity) and persists only `gmail_watch_expires_at` (never `gmail_history_id`, which stays `reconcileGmailAccount`'s exclusive write), and a pull loop that consumes Cloud Pub/Sub notifications, filters by the account's own email, and turns a match into the existing idempotent `enqueueMailAccountSync` call — acknowledging only after that durably commits.
- **`gmailPubSubClient.ts`** — the real fetch-based transport over Gmail's REST `users.watch` and Cloud Pub/Sub's REST pull/acknowledge endpoints, following the same "untested in CI, no live GCP project" precedent as `gmailRestClient.ts`.
- **`mailAccountSyncStateStore.ts`** — added `recordGmailWatchExpiry`, a single-purpose writer scoped to just the watch-expiry column.
- **`gmailWatchLifecycle.test.ts`** — 8 tests against a fake transport and the real test Postgres, covering registration/persistence, notification handling and jobKey dedup, account-validation filtering, duplicate/redelivery safety, pull-error backoff, renewal cadence, and stop() semantics.

Type-check is clean, and the new tests pass consistently across isolated and full-suite runs. The full suite otherwise passes except for intermittent `out of shared memory` Postgres errors in the embedded test cluster, which hit a different, non-overlapping set of unrelated pre-existing test files on each run and pass cleanly when re-run in isolation — confirmed as environment resource contention, not a regression from this change.
