## Delivered behavior and production wiring

- `ModuleDatabaseDescriptor.searchFields` is optional, validated by the manifest schema and retained by `ModuleRegistry.getDatabases()`. Explicit empty lists differ from absence; unknown property keys are ignored. All ten system databases declare their seeded textual and select fields and the specified relation fields. People includes `emails`, which already exists through the email module's seed; no `phones` or Events `place` field is invented.
- `search/itemSearchDocument.ts` builds pure text from declared fields, or the generic title/text/longText/url/select/multi_select rule when no declaration exists. It uses existing catalog resolution, honoring explicit user option labels before locale/English/catalog-key fallback. Locale comes from the current tenant's earliest-created bound user (currently unique per tenant), defaults to `cs`, and uses the existing unsupported-locale-to-English behavior.
- `search/itemSearchIndexer.ts` resolves and locks a live item under the caller's tenant, loads its database/schema and batches relation titles in both edge directions. Linked Projects, Areas, People and Companies are included independently of declarations, plus each linked project's `area`; declared relation fields also include titles from other databases such as Files' Health records. Deleted targets are excluded. Journal days include text from the existing `computed.inboxItems` cache. Emails is excluded by `owner_module_id`, preserving the mail module's richer index document.
- `domainWriteHooks.ts` registers create and update hooks; the `@semprec/data` barrel imports that composition root first. The real `createItemWithClient`/`updateItemWithClient` transaction invokes `indexItem` before commit. Index failure propagates and rolls back the item write. The generic vector expression is owned by `SEARCH_VECTOR_SQL` in the indexer and currently uses `to_tsvector('czech', document)`. No schema migration or body column is added.
- `itemSearchBackfill` is a core API-affinity, tenant-tenancy task, registered by `worker.ts`. Its validated payload is `{ databaseId?, afterItemId?, onlyMissing }`. Each invocation processes at most 100 live non-Emails items in item-id order, commits the chunk with its continuation, and releases the transaction before another invocation. The job key includes tenant, database filter, mode and cursor, so tenants and running chunks cannot absorb each other's jobs. Its lane is `tenantLane("item-search-index")`.
- `enqueueItemSearchBackfill(client, options)` and `indexItem` are public data-package exports for follow-on work. The enqueue helper requires an actual tenant scope. `onlyMissing` filters candidates and also guards the final conflict update, preserving a row that appeared after selection.
- `runItemSearchBackfillCutover(tenantPool)` is called from the deploy migration CLI immediately after queue schema grants. It refuses a pool without active RLS, enumerates maintained tenants with `forEachMaintainedTenant`, and transactionally enqueues `{ onlyMissing: true }` for each. Repeated enqueue collapses per tenant. Standard worker policy still controls whether a suspended tenant's queued job executes.

## Consumers, follow-ups and limits

- #1652 owns edge/title/trash/schema/locale freshness and computed-cache change fan-out. Creating an item and then its edges still indexes the pre-edge state until an item update or explicit backfill. Journal's cached Inbox text is consumed when indexing; this change adds no recompute hook.
- #1589 can change the generic vector expression in the indexer. Mail's existing writer is preserved.
- #1658 owns page/journal body content; no body column or page extraction is delivered here. #1842/#1857 own index consumers; no search route is added. Mail sender/reindexing remain #1591/#1741.
- Writers that intentionally bypass item hooks, including existing raw seed/store writes, need the backfill helper or their designated follow-on wiring. No provisioning or unrelated seed repair was added.
