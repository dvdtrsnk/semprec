## What was delivered

A debounced silent resync push to a tenant's active iOS APNs registrations after any change of sleep data.

- `sleep/sleepResync.ts`: `enqueueSleepResync` (job key `sleep-resync:<tenantId>`, job mode replace, run 30 s ahead, payload `{ tenantId }` under a strict schema), `runSleepResync` and the module-task handler `handleSleepResync`. The handler runs in the tenant of the job envelope and sends nothing when the payload names another tenant, loads the user through `users.tenant_id`, sends `{ kind: "sleepResync" }` with `sendApnsBackgroundPush` to each active apns/ios registration (not macOS, web or revoked), revokes a registration APNs answers with a permanent failure (410), throws an `AggregateError` after trying all registrations on a transient failure, and is a no-op without a user or a registration. It writes no `notifications` or `push_deliveries` row.
- `sleep/sleepWriteHooks.ts`: create, update, delete and restore hooks (`sleepResyncCreateHook`, `sleepResyncUpdateHook`, `sleepResyncDeleteHook`, `sleepResyncRestoreHook`) that enqueue in the write transaction, for the three sleep databases and for a System settings patch that names `timezone`.
- The task `sleep.resync` (queue affinity `api`) is declared in the sleep manifest; `handleSleepResync` and `sleepResyncPayloadSchema` are exported from `sleepModuleManifest.ts`.
- ADR `docs/adr/2026-11-13-a-sleep-change-enqueues-one-debounced-resync-job-per-tenant-in-its-write-transaction.md` records the job key, the enqueue inside the write transaction and the per-tenant serialization at `add_job`.

## Entry points and contracts dependents build on

- Job name `sleep.resync`, job key `sleep-resync:<tenantId>`, payload `{ tenantId }`; push payload `{ kind: "sleepResync" }`, silent, one per active iOS APNs registration.
- Hook registration in `domainWriteHooks.ts`: the four resync hooks are registered after the gh-1784 and gh-1799 sleep hooks and, in this landing, after the #1819 event-hosted-task hooks (Shared-file ordering: the entries of the later source go after those of its blocker). Registration order among them does not change behaviour, since they act on different databases.
- No heartbeat, action id, seeded row, table or migration was added. `sleepResync.ts` is not in the `@semprec/data` barrel.
- A client that wants the new data refetches on the push; no visible notification is created and `GET /api/notifications/unread` is unchanged.

## Deviations and spec seams

1. #1819 (Shared-file ordering) was open for the worker; it is delivered. The landing put the gh-1838 block after the #1819 hooks.
2. The tenant of a sleep write is read with `SELECT app_tenant_default()` inside the hook, and the handler cross-checks the payload tenant against the job envelope's scope instead of trusting the payload.
3. The single replace key makes all sleep writes of one tenant wait for each other at the enqueue (`add_job`). Two existing tests (`sleepWriteHooks.test.ts` "does not hold a creator of a different night behind the open transaction", `sleepPlanDayExclusivity.test.ts` "lets two moves that do not cross both succeed...") now assert that the only wait is the `add_job` statement and that both writes complete. Recorded in the ADR.
4. The ADR was added though it is not in Touches, because of that lock and the enqueue-in-transaction decision.
5. No `maxAttempts` is set; the queue default applies to the transient-failure retry.
6. Tests outside Touches: `sleepModuleManifest.unit.test.ts`, the two edited tests, and `sleepResyncWritePaths.test.ts`.
7. The handler and schema are exported from `sleepModuleManifest.ts`, not the barrel.
8. After the tip gained per-database agent grants, the agent run of `sleepResyncWritePaths.test.ts` needs an `agent_database_grants` write row for the agent project on the Sleep plans database; the fixture inserts it with the statement of `setAgentDatabaseGrant` (the admin store is not exported from `@semprec/data`).
