## What was delivered

- `GET /api/agent-runs/:id` and `GET /api/agent-runs/:id/steps` take an optional `messageId`, validated as one UUID (400 `validation_failed` naming the field otherwise). Without it nothing changes.
- `resolveAgentRunReply` (`packages/data/src/agentRuns/agentRunDetail.ts`) loads the assistant message of the run in the caller's tenant. Another run, another tenant, a user message and an unknown id all answer 404 like a random id. A session run resolves a retried reply to its latest attempt (the newest assistant message of the run and thread with the same `reply_to_message_id`). A heartbeat (invocation) run accepts a valid `messageId` and answers the whole run.
- The detail of a reply: `title` (text of the user message it answers, or an `agentRun.replyTitle.*` i18n title of the system message's `system_key`, with a generic fallback), `startedAt` (first event of the reply, else the message's `created_at`), `durationMs` (stored `duration_ms`), `approvals` (requests whose tool call id is a `tool_use` event of the reply's range or a `toolCallId` of the steps stored on the message), `usage` (`getAgentRunUsage` filtered by `semp_message_id`) and `displayStatus` from the reply's own outcome (message error or stored error step: error; queued or running: running; else done) and its approvals.
- The steps are read inside the reply's event range through `listAgentRunEventsForStepPage(range)`; the cursor and pairing rules of `buildAgentRunStepPage` are unchanged, the end-step counts are bounded to the range, and `truncatedHistory` is true when the event the message names as its first is gone (`isAgentRunReplyHistoryTruncated`).

## Deviations from the specification and spec seams

1. No attempt column exists on `semp_messages` (gh-1926 not landed), so "latest attempt" is the newest assistant message of the same run and thread with the same `reply_to_message_id`. The second attempt is inserted by SQL in the fixture (no production writer yet).
2. A reply that stored no `event_to_id` (failed or running turn) ends before the first event of the next reply of the run, or at the end of the run.
3. Approval attribution is the union of `tool_use` events in the reply's range and the `toolCallId` of the stored steps, so it survives retention; a request stored without a tool call id belongs to no reply.
4. A heartbeat run ignores the scope after the message was verified.
5. The tenantIsolationRoutes cases seed two case-specific rows by SQL and remove them in `finally`.
6. Files outside the Touches list were needed: the fixture, i18n keys, range passthroughs and a test-only export.
7. The worker's commit trailer names Claude Sonnet 5.5.

## Follow-ups from review

One medium finding (the heartbeat branch of `resolveAgentRunReply` had no test of its refusals) was fixed in `1789a90c4` and confirmed by the recheck. Rules and security reviews were clear.

New seam from the merge, a recorded follow-up and not a defect of either source: gh-1889 leaves "a reply with an unfinished tool call counts as failed" to gh-1890, and gh-1890 applies its incomplete-reply outcome to a whole run only. A reply-scoped detail therefore does not turn an incomplete reply into `error`, although the message list shows that reply as incomplete. Aligning the two (apply `deriveReplyOutcome` to the scoped reply, and give the scoped error fields its summary) needs a specification decision.
