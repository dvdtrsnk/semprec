# Handover for gh-1433

Item writes now validate `color` property values at the choke point. `createItemWithClient` and `updateItemWithClient` in `backend/packages/data/src/chokePoint/itemWrites.ts` call a new `assertColorValues` right after `assertWritableProperties`. Every writer goes through those two functions, so REST, `/mcp`, agent tools, proposal confirms and system writers share the answer, including calls that pass `allowedSystemKeys`.

- **Rule:** for each key in the write whose property has `type: "color"`, `null` is accepted and anything else must match `^#[0-9A-Fa-f]{6}$`. Otherwise it throws `ValidationError` (400 `validation_failed`) with `details.field` set to the key. The value is stored as written.
- **Stored data:** keys absent from the write are not inspected, so rows that already store `red` are neither migrated nor rejected until that key is written again.
- **Tests:** a new `color value validation` block in `itemWrites.test.ts` covers upper and lower case hex, rejected values (`Červená`, `red`, `#FFF`, empty string, number, object, bad digits, leading space) on create and update, `null` clearing, an unrelated update on a row storing `red`, and the client-level writers with `allowedSystemKeys`. The data package has no HTTP layer, so the 400 is asserted as `status: 400`, `code: "validation_failed"` on the thrown error. I did not add a REST, `/mcp` or proposal-confirm test; they use the same functions. `itemWrites.test.ts` passes 35/35; tsc, eslint and prettier are clean on the touched files.
- **For dependants:** seeds or tests that write a non-hex string to a `color` property now fail with 400. Select option colors and the `Areas.color` palette are out of scope (#1584).
