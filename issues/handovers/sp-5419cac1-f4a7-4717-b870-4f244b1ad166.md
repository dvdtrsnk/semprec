The title names the first design (run the edge-changed hooks before the link break). That design was withdrawn by `issues/decisions/sp-5419cac1-f4a7-4717-b870-4f244b1ad166.md`, because it takes the `company` link before the `project` link, against the trash of an Event and the release of a removed `event` edge. The Task, as decided there, is what was delivered: lock the rule's target item before the write ends a value link.

## What was delivered

A user or agent edge write on the via relation of a link rule now locks the rule's target item row right after the edge row is written or deleted and before the write locks any value link row. Before, the write held the `project` link row and reached the item row only in the link engine's edge-changed hook, while the `valueLinksPropagate` handler takes the item row first, so one of the two ended with `40P01`.

Entry points and contracts dependents build on:

- `backend/packages/data/src/chokePoint/hooks.ts`: new hook kind `RelationEdgeBeforeLinkBreakHook` (context `RelationEdgeChangedHookContext`, `op` is `create` or `delete`), `registerRelationEdgeBeforeLinkBreakHook` (a Set, registering the same function twice is a no-op) and `runRelationEdgeBeforeLinkBreakHooks` (awaits the hooks sequentially in registration order inside the write's transaction; a throwing hook ends the write). `clearHooksForTests` empties the registry.
- `backend/packages/data/src/chokePoint/relationOps.ts`: `createRelationWithClient`, `createRelationIfAbsentWithClient` and `deleteRelationWithClient` call `runRelationEdgeBeforeLinkBreakHooks` for a `user` or `agent` writer, right after the insert reported the edge as inserted or the delete returned an edge, before the approval check of an agent under a run and before `breakValueLinksForRelationEdge`. A `system` writer, a replayed create, an insert of an existing edge and a delete of an absent edge call nothing. The edge-changed hooks, the link break, the rollup enqueue and the announcement keep their order and arguments.
- `backend/packages/data/src/valueLinks/linkRuleEdgeHook.ts`: `linkRuleEdgeLockHook` (exported) locks, with `lockItemById` and its blocking wait, the target item of each link rule that resolves and whose via relation is the written definition; it skips `system` writers and `update`, and writes and logs nothing. `viaEdgeItems` is the one helper that `linkRuleEdgeHook` and the new hook share to compute the target item, so they cannot name different rows.
- `backend/packages/data/src/domainWriteHooks.ts`: `registerRelationEdgeBeforeLinkBreakHook(linkRuleEdgeLockHook)` directly after `registerRelationEdgeChangedHook(linkRuleEdgeHook)`. This is the only registration entry; entry order for later sources goes after it.
- No route, operation, table, migration or job name was added or changed. The generic edge write path behaves as before for relations that are no rule's via relation (no wait, no lock).
- ADR `docs/adr/2026-11-15-a-user-edge-write-on-a-link-rules-via-relation-locks-the-rules-target-item-before-ending-value-links.md` (accepted, area backend): the order of the rows of one item (item, then project, people, company links), the paths that follow it and the three that do not, the lock and its place, the hook kind and why it is a registry (a direct call closes an import cycle through `linkPropagation.ts` and `relationOps.ts`), the blocking locks not taken, and the limits.
