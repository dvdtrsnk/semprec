## What was delivered

Semp can now propose a task from a mail thread. The mail module declares the agent tool `mail.thread.proposeTask { threadId, name }` (capability `mail.taskProposal`, approval `none`, risk class `write`). A call creates one `proposed` Processing proposals card of kind `mailThread` with a Tasks envelope carrying the name and a `sourceThread` edge to the thread. It creates no task and no `Threads.tasks` edge; the user's confirm (gh-2034) does that.

## Entry points and contracts dependents build on

- Tool `mail.thread.proposeTask` in `agentTools` of `mail/mailModuleManifest.ts`, handler `proposeThreadTask` in `mail/threadTaskProposals.ts` (also re-exported through the manifest). Arguments are a strict zod object: `threadId` a UUID, `name` trimmed, 1 to 500 characters, no U+0000 and no unpaired surrogate, no further key. The tool description lives on the argument schema (the descriptor has no description field) and tells Semp to suggest, not to create thread tasks itself. It is offered to a run only when the run's project holds `mail.taskProposal`, which the module's capability declaration grants over the four mail databases (so the Email project has five mail tools now).
- `proposeThreadTask` runs in one READ COMMITTED tenant transaction: the mail-thread guard `resolveMailThreadForAction` (merged-away ids resolve to the current thread; unknown and foreign threads give the same 404), then a row lock on the thread's Threads item (a trashed item is 404), then the duplicate rule, then the create. The duplicate rule: a live `proposed` `mailThread` card of the same thread whose current proposal name equals the new name trimmed and case folded is returned as it is. Rejected, confirmed and trashed cards are not duplicates. The answer is `{ proposalId, status }`.
- The card is written as the system writer with `createItemWithClient` (system keys `kind`, `proposal`, `aiProposal`, `aiVersion`, `history`, `status`), its `sourceThread` edge with `createRelationWithClient` under the Processing proposals relation context, and announced after commit through `publishInboxCardChange`. The history has one AI entry naming the thread's subject (no subject is named when the thread has none or the latest live message has a blank subject).
- ADR `docs/adr/2026-11-14-mail-thread-cards-are-produced-by-the-mail-module-when-semp-proposes-a-task.md` records the mail module as the producer of `mailThread` cards; the ownership-handoff comment of `inbox/inboxModuleManifest.ts` (comment only) names it. Tenants seeded earlier need `runThreadTaskProposalCutoverMigration` (gh-2034); without the `sourceThread` relation the handler throws a plain error and writes nothing.

## Deviations from the specification and spec seams

1. The Task names the system keys `kind`, `proposal`, `history`, `status`; the card also sets `aiProposal` and `aiVersion` as every other producer does, because revise and reset read the assistant's baseline from `aiProposal`. `referencedItemIds` is not written (the envelope refers to no item).
2. The issue's tool description cannot sit on the module descriptor; it is the description of the zod argument schema.
3. The card is written as the system writer, not as the run's agent writer, because the capability carries no write grant on Processing proposals.
4. A Threads item in the Trash is a 404, as `createThreadTask` does.
5. A thread without live messages may be proposed for; the Task does not restrict it.
6. The gh-2034 ADR left the producer process open for this issue, so a new ADR was added in the same segment.
7. Tests outside the Task list were brought in line for the fifth mail tool (`mailModuleManifestAgentTools.unit.test.ts`, the composition test of `mailAgentTools.test.ts`, and `answerExpectedFilter.test.ts` after review).
