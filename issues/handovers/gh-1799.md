## What was delivered

- `keepWakeDaysInOnePlan` in `packages/data/src/sleep/sleepWriteHooks.ts`, registered as an item create hook and an item update hook in `domainWriteHooks.ts` directly after the gh-1784 sleep validation hooks. It acts only for databases owned by the sleep plans module.
- After a plan write whose merged item has non-empty `wakeDays`, it selects the other non-deleted plans of the same database that hold any of those days (`SELECT ... ORDER BY id FOR UPDATE`) and removes the days from each through `updateItemWithClient` without `ifVersion`, in the write's own transaction. So the lowered plans get their hooks, realtime invalidation and a new `updatedAt`. A plan that loses all its days keeps `wakeDays: []` and is not deleted.
- The select is repeated as a new statement; the loop ends after two consecutive statements that return no row (see deviations).
- A Postgres deadlock (`40P01`) raised by the hook's own lock statement is rethrown as `ConflictError` (HTTP 409, code `version_conflict`, fixed message); any other error passes through unchanged.
- A per-client `WeakSet` guard makes the nested removal skip the hook so it does not cascade into further plans; it is released in `finally`.
- New accepted ADR `docs/adr/2026-11-12-a-sleep-plan-takes-its-wake-days-from-the-other-plans-under-row-locks.md` for the lock order, the repeat loop and the deadlock mapping.

## Deviations from the specification and spec seams

1. Spec seam: the Context says no pre-write hook exists before the row lock; the accepted ADR `2026-11-12-an-update-takes-the-module-locks-before-it-locks-the-row` has added a pre-lock registry since. The Task prescribes row locks and a `40P01` to 409 mapping, so the registry is not used; the new ADR states why (create and a patch without `wakeDays` have no pre-lock point that knows the days, a pre-lock lock on the named plans would not remove the exchange cycle).
2. The loop ends after two consecutive empty statements, not after the first: a `FOR UPDATE` statement that waited rechecks only the locked row and does not see a plan the other transaction committed meanwhile. The deterministic test fails with the single-empty variant (worker mutation check).
3. Added a per-client guard so the nested removal does not run the hook again (a pre-existing overlap would otherwise cascade).
4. Tests outside the Touches folder: `services/semprec-api/src/__tests__/sleepWritePaths.test.ts` (REST and gateway `item.patch` with an agent actor, no `approval_requests` row). The ADR is outside Touches too.
5. Known limit, documented in the code and the ADR: two transactions that put the same free day (held by no plan) into two plans are not serialized. The two-empty-statements loop narrows but does not logically close the stale-snapshot window when the second statement itself waits on a third concurrent transaction (a three-writer interleaving; recorded by the rules reviewer as an observation).
6. The 409 is asserted at the data layer (`ConflictError.status`), not through a REST request; the MCP transport was not exercised, the generic operation gateway was.
