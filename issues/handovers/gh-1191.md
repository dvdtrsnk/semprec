Closes #1191

The gateway answered a suspended tenant and an unknown tenant differently, so an internal-token caller could tell which tenant ids exist:
- A suspended tenant keeps its `tenant_ai_budgets` row, passes the budget gate, and is refused by the reservation's `status = 'active'` predicate: `403 attribution_refused`.
- An unknown tenant has no budget row, so the budget gate refuses it first: `403 budget_exceeded`.

The two-tenant suite in #1184 (#1057) found this.

**Change**
- `aiGatewayCallsStore.ts`: new `assertGatewayTenantActive(client)`. It runs `SELECT EXISTS (… tenants WHERE id = app_tenant_default() AND status = 'active')` with a row type and throws the same `ForbiddenError` `attribution_refused` with no details. That error now comes from one private `attributionRefused()` that `reserveGatewayCall` also uses, so the two refusals cannot drift apart. `reserveGatewayCall` keeps its own `status = 'active'` predicate as the write-time guard.
- `gateway.ts` `reserve()`: the order is now advisory lock → `assertGatewayTenantActive` → `assertWithinBudget` → conditional insert, all in one transaction. The docstring states that order.

**Tests**
- `aiGatewayCallAttribution.test.ts`: `assertGatewayTenantActive` resolves for an active tenant and rejects a `provisioning`, `suspended` and `deleting` tenant, and an unknown tenant id, all with `attribution_refused` and no details.
- `callerTenant.test.ts`: the unknown-tenant test now requires the same status and the same body as a suspended tenant (`attribution_refused`), with no row and no provider call, on every route.
- An active tenant with no budget row is still refused with `budget_exceeded`. This is the existing `gateway.test.ts` test "refuses a tenant with no budget row and writes no row", which is unchanged and passes.

The issue's acceptance criterion says only the `callerTenant.test.ts` expectation changes; this second expectation changes because of Task step 2.
