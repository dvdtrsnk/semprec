Implemented issue #686: `agentRunWatch.ts`'s `watch` now authorizes `agent:watch` against `agent_runs.actor_user_id` instead of the stale "earliest account owns every run" rule, which predated migration `0042_agent_runs_actor_user_id.sql` making that column `NOT NULL`.

**Changes** (`backend/packages/realtime/src/agentRunWatch.ts`):
- Dropped the `getEarliestUserId` import and its parallel query.
- `watch` now loads only `getAgentRun(pool, runId)` and authorizes with `run !== null && run.actorUserId === userId`.
- Rewrote the authorization comment to describe the `actor_user_id` invariant and that no fallback exists.

**Tests** (`backend/packages/realtime/src/__tests__/syncServer.test.ts`, `createSyncServer watched agent runs` describe block):
- New test: a user-triggered run with an explicit `userId` is watchable by that actor and denied to the earliest account.
- New test: a heartbeat-triggered run (no `userId`, falls back to the earliest account) is watchable only by that earliest account.
- Updated the "cancels a watch when agent:unwatch arrives while its authorization query is pending" test. Since `watch()`'s authorization is now a plain (non-locking) `SELECT` against `agent_runs`, a row-level `FOR UPDATE` from the test's blocking transaction would not actually block it (confirmed empirically — Postgres never blocks a plain reader on another session's row lock). The test now takes `LOCK TABLE agent_runs IN ACCESS EXCLUSIVE MODE` instead, which does conflict with the plain `SELECT`, correctly holding the watch pending while the `agent:unwatch` frame arrives.
- Fixed the mock call count in "keeps the existing watcher live when a replacement replay fails" — authorization is now one query, not two.
