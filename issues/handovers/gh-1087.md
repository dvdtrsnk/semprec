## Delivered behavior

- **Migration `0123_drop_single_tenant_guard.sql`:** `DROP INDEX tenants_single_tenant_guard;`. Its comment marks the change as a relaxation whose previous release is strict. It states that rolling back after a second tenant exists is not safe. It does not lift the multi-tenant security gate (#1086).
- **`acceptInvitation(pool, { token, password }, provision = provisionTenant)`** in `backend/packages/data/src/tenancy/acceptInvitation.ts`, exported from the data package index and listed in `EXPECTED_RUNTIME_EXPORTS`. It runs inside `runAsSystem("invitation-acceptance", …)`:
  1. A password shorter than `MIN_PASSWORD_LENGTH` raises `ValidationError` before any lookup.
  2. An unlocked lookup finds a usable invitation. If none exists, it raises `NotFoundError("Not found")`. Only after that is the password hashed.
  3. One transaction re-selects the invitation `FOR UPDATE` and re-checks its usability. It creates the tenant in `provisioning` through `createTenant(client, status)`, which the commit added to `tenantsStore.ts`. It creates the `member` user with the invitation's email. A `23505` on `users_email_key` becomes `NotFoundError`, and any other error is rethrown. It marks the invitation accepted and checks the affected row count with `requireAffectedRows`.
  4. After the commit, `provision(pool, tenantId)` runs. On failure it logs `invitation_provisioning_failed` with the tenant id only, then rethrows. The tenant stays `provisioning`.
  - The tenant id is generated by the database and never read from the request. No `tenant_ai_budgets` row is created.
- **`createInvitationRequestListener`** in `backend/services/semprec-api/src/invitationHandler.ts`, mounted in `app.ts` beside `/api/setup`. It serves only `POST /api/invitations/accept`:
  - The `invitationAccept` per-IP throttle is checked before the body is read. A throttled request gets 429 with `code: "rate_limited"` and `Retry-After`.
  - Only a `NotFoundError` keeps its reservation. Validation failures, oversized bodies and successful acceptances release it.
  - The body is capped at 64 KiB (413). A missing or non-string field, or a short password, gets 400.
  - Success gets 200 `{ user }`. A `ChokePointError` goes through `toPublicErrorBody`. Anything else is logged with the error name only and answered with a generic 500.
  - Other methods and paths get 404 `{ error: "Not found" }`.
- **Route matrix:** the `accept invitation` entry is `public: true` with `tenancy: "anonymous"`. `ROUTE_HANDLER_FILES` maps it to `invitationHandler.ts`.

## Notes for dependants

- **Deployment precondition:** dropping the guard makes a second tenant possible. The issue requires that the second tenant not be deployed before the multi-tenant security gate #1086 is signed. This migration does not lift that gate.
- **#1088 (invitation page in the web client)** must call `POST /api/invitations/accept` with `{ token, password }`, taking the token from the `#token=` fragment. It must treat every 404 the same way.
- **Stuck provisioning:** a tenant left in `provisioning` cannot authenticate. The next deploy's seed step (#1005) provisions it.
