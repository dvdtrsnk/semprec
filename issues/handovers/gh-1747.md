## What was delivered

- `GET /api/mail/threads/facets[?areaId=<uuid>][&projectId=<uuid>]`, a custom route of the mail module (`mailThreadFacets`, justification `single-consumer-read`), handler `createMailThreadFacetsRouteHandler(pool)` in `backend/packages/data/src/mail/mailThreadRoutes.ts`. It needs a session; the tenant is the session's. It reads in one `withTransaction` and writes nothing.
- Answer 200 `{ total, areas: { total, items: [{ id, count }] }, projects: { total, items: [{ id, areaId, count }] } }`, computed by one SQL statement (`readMailThreadFacets` in the new `backend/packages/data/src/mail/mailThreadsFacetsStore.ts`), so both groups read one snapshot:
  - `total`: every visible thread, whatever is selected.
  - `areas.items`: one row for every area that is not in the trash, with count 0 for an area that counts no thread. Each count is the number of visible threads whose project is in that area, narrowed by `projectId` when given. `areas.total` is the number of visible threads, narrowed by `projectId` when given.
  - `projects.items`: one row for every project whose count is above 0, with its `areaId` (null for a project without an area). The counts are narrowed by `areaId` when given. `projects.total` is the number of visible threads, narrowed by `areaId` when given.
  - Neither group is narrowed by its own selection. Both item lists are ordered by id. A thread without a project counts in `total`, in a group's total while no selection narrows that group, and in no item.
- The counting rule. A thread is visible when it has a visible copy in the thread list's own `copies` CTE (`mailThreadCopyCtes` in list mode, which leaves drafts out). No box, folder or mailbox filter applies. A copy is visible when both hold:
  - It has a folder other than Junk and Trash, or no folder (the list's column `has_non_junk`).
  - None of its folders is a live Junk or Trash folder with `behavior` 'label' (the new CTE `junk_labels`). In a mailbox of labels (Gmail API) a copy is one message and each folder edge is a label, so a message that carries Trash or Junk is hidden whatever else it carries (Sent, a user label). In a mailbox of folders (IMAP, Graph) each folder edge is a message of its own, so the first condition alone decides.
- A deleted message has no copy. A thread whose messages are all deleted, all drafts, or all in Junk or Trash is in no count.
- A project in the trash is not read: its threads count like threads without a project. An area in the trash is not listed, and a project whose area is in the trash is listed with `areaId` null.
- The route matrix entry `{ name: "mail thread facets", method: "GET", path: "/api/mail/threads/facets", surface: "api", public: false, tenancy: "tenant" }` in `backend/services/semprec-api/src/routeMatrix/mail.ts`, its `ROUTE_CASES` case in `tenantIsolationRoutes.test.ts` and its `ROUTE_HANDLER_FILES` mapping to `packages/data/src/mail/mailThreadRoutes.ts`, all in the same merge.
- The ADR `docs/adr/2026-11-10-custom-routes-are-matched-in-declaration-order.md` (accepted, area backend). The prescribed path is also matched by the existing `GET /api/mail/threads/:threadId`. The ADR records that a request is answered by the first custom route in declaration order whose method and pattern match, and that a module declares the narrower route before the wider one.
