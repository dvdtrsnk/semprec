## Entry points and contracts dependents build on

- Manifest: an agent tool descriptor may declare `mcp: { humanHandlerExport }` (`packages/module-registry/src/manifest.ts`, checked at manifest parse: the tool needs a capability, `approval: "none"` and no `requiresApproval`; `registry.ts` checks at load that the export is a function). A tool without the declaration keeps its old exposure. The four mail tools declare it in `packages/data/src/mail/mailModuleManifest.ts`. Gh-1957 (calendar tools) opts in with the same declaration.
- Run credential: `resolveModuleAgentToolsForRun` (`packages/data/src/agentTools/moduleAgentTools.ts`) takes an `mcpExposure` option. A tool that declares `mcp` is offered when the credential's own list names the tool's capability and the run's project holds it; a credential that lists core ids only exposes no module tool. The mint (`POST /api/agent-runs/mcp-credentials`, `createAgentRunRequestListener` in `services/semprec-api/src/agentRunHandler.ts`, given the module registry from `app.ts`) accepts the capability ids of the active modules besides the core ids and refuses an unknown id or any module id when no registry is given. They are stored in the existing `capabilities text[]` column (no migration). `resolveRunCredentialCaller` (`mcp/callerActor.ts`) returns the credential's `moduleCapabilities`. The calls run as the credential's run; the approval request of `mail.draft.send` has source `mcp`, derived from the run's `triggered_by`.
- Human session: `resolveModuleAgentToolsForUser` (new, exported from the data barrel with type `ResolvedHumanModuleAgentTool`) lists the tools of active modules that declare `mcp`; no project grant is evaluated. `mcpHandler.resolveModuleTools` picks the branch: run credential first, human (`actor.externalClient`) second, otherwise none. `humanHandlerExport` is a factory `(pool, dependencies)` returning `(userId, args)`; `dependencies` is the composition-root container of the custom routes (`CustomRouteDependencies`), passed from `app.ts` to the MCP listener. The mail user handlers (`mailAgentTools.ts`, now on a `MailToolCaller` run or user) write drafts as `writerKind: "agent"` with `onBehalfOfUserId` and the external-client marker, no run and no project. `mail.draft.send` of a human session calls `sendMailDraft` and files no approval request.
- Moved: `requireSendAdapters` and its dependency type now live in `mail/mailDraftSend.ts` (type re-exported from `mailDraftRouteHandlers.ts`). `testSupport/testDb.ts` re-exports the mail send fakes. The data barrel `index.ts` exports `moduleAgentTools` with `export *` (net zero lines, the file sits near its cap), which adds `resolveModuleAgentToolsForUser` and `ResolvedHumanModuleAgentTool` to the public surface (`publicSurface.test.ts` updated).
- No table, route, operation, job name or migration was added; no route-matrix entry.

## Tests

`mailTools.test.ts` drives HTTP `/mcp` on the runtime-role pool with two tenants: a run credential lists and calls the tools per capability it names and gets "method not found" for the rest, gains nothing in a project that does not hold the capability, files the send approval request with source mcp and sends nothing, is refused for a foreign tenant's draft and an inactive module; a human session lists the four tools, creates, updates and sends a draft as the user with no request and an agent author without a run, is refused for a foreign tenant, an inactive module and, with no send adapters, fails the send with an internal error and leaves the draft unsent. `mailMcpTools.test.ts` covers the resolver and each user tool including 400, 404 and 409 refusals; `agentRunHandler.test.ts` the mint accepting an active module capability and refusing an unknown one or one without a registry. The worker's mutation check (the mcp filter made to accept every tool) failed `mailTools.test.ts`.

## Deviations from the specification and spec seams

1. The MCP tests sit in `services/semprec-api/src/mcp/__tests__/` next to the existing MCP tests.
2. The issue says the mechanism of #1580 suffices; it did not: a credential listed core capability ids only, so a module capability never reached the filter, and a human session had no module tools (ADR 2026-11-04 deferred both to gh-1956). The `mcp` descriptor, `resolveModuleAgentToolsForUser`, `mcpExposure` and the mint's acceptance of module capability ids decide this; the new ADR records it, and reverses for `mcp` tools the rejection of module capability ids in ADR 2026-11-04.
3. Malformed arguments are refused by the generic module tool path as JSON-RPC -32602 before the handler runs.
4. Human writes use the agent writer with the external-client marker set by the mail user handlers, not by the generic gateway.
5. Edits outside Touches: module-registry `manifest.ts` and `registry.ts`, the data files listed above, `app.ts`, `testSupport/testDb.ts`, `publicSurface.test.ts`.
