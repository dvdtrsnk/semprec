## Changes

**`backend/packages/data/src/rollup/recompute.ts`**
- **Row lock:** `recomputeRollupCell` now runs inside `withTransaction` and takes `itemsStore.lockItemById` (`FOR UPDATE`) on the target item before it aggregates. When two jobs for the same cell overlap, the second waits until the first commits and then aggregates the current source state. So the value that lands last is always computed from the newest source state.
- **Load order:** the rollup property is loaded just before the lock, not after it as the issue listed. The lock needs the target item's `databaseId`, and that comes from the property.
- **Purged target:** if the lock finds no row (the item was purged), the job returns without writing.
- **Invalidation after commit:** the announcement now goes through `runAfterCommit`, so it fires only once the write is committed. It carries the locked row's `updatedAt`, which `writeComputed` deliberately never changes. The old post-write `getItemById` and its comment are removed.
- **Date guard:** `earliest`/`latest` now guard the `::timestamptz` cast with a shared module-level `ISO_DATE_PATTERN`, the same way the numeric aggregations pre-filter. A garbage date such as `"tomorrow"` contributes nothing, just as a garbage number does for `sum`.

**`backend/packages/data/src/__tests__/rollup.test.ts`** (integration)
- **Bad date:** a `latest` rollup over three children, one holding `"tomorrow"`, gives the later of the two valid dates, and the job is gone from `graphile_worker._private_jobs` after the first run, meaning it didn't fail and get rescheduled.
- **Serialisation:** a second connection holds `FOR UPDATE` on the parent row. `recomputeRollupCell` is still unresolved after 200 ms. A child's value is then changed through the choke point and the lock released, and the cell ends up holding the aggregate that includes the change.
- **Purged target:** with the target row deleted directly, `recomputeRollupCell` returns without throwing and writes nothing.
