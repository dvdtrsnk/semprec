# Handover for gh-1710

Invalidate a project's items when its area or company changes. Candidate commit `b6f33db404fcc10e2fa32e7a07bbe51a60e1c235` landed on `feature/backend-parallel` with merge `3220c9b2635696a41d6cfcce3439b446171479b1` (chain `e1-014-derived`, its only member). The source is that one commit. The acceptance receipt is `issues/batches/backend/acceptance/sources/gh-1710.md`.

Both declared blockers are completed on the tip: gh-1621 (an edge write announces the two items it joins) and gh-1707, which the record names for shared-file ordering. No blocker was open at this landing.

## What was delivered

- The queue task `derivedValuesInvalidate` (`CORE_TASK_NAMES.DERIVED_VALUES_INVALIDATE` in `backend/packages/queue/src/index.ts`), with affinity `api` in `CORE_TASK_AFFINITY` and tenancy `tenant` in `TASK_TENANCY`. Its handler is an entry of `createCoreTaskList` in `backend/packages/data/src/worker.ts`, so `registerTask` runs it in the tenant of the job envelope.
- The edge-changed hook `projectDerivedValueEdgeChangedHook` in `backend/packages/data/src/derived/projectDerivedValueHook.ts`, registered with `registerRelationEdgeChangedHook` in `backend/packages/data/src/domainWriteHooks.ts`. For a created or deleted edge it reads, in one query filtered by `app_tenant_default()`, whether the edge's relation definition is the one behind the relation property `area` or `company` of the tenant's system Projects database, and which end of the edge is the project. The answer comes from the definition, not from the caller, so a write through either of the definition's two properties (`Projects.area` or `Areas.projects`) names the same project. For such an edge it calls `enqueueJob` on the edge write's own client, so the job commits or rolls back with the edge. An `update` of an edge (metadata only) and an edge of any other relation queue nothing.
- The job `handleDerivedValuesInvalidateTask(pool, payload)` in `backend/packages/data/src/derived/projectDerivedValueInvalidation.ts`. It parses the payload with a strict zod schema (`{ projectItemId: uuid }`, no other field), then pages: each batch is one `withTransaction` that checks the project is a live item of the tenant (`getItemsByIds`), resolves the tenant's relations behind `DERIVED_VALUE_SOURCES`, reads the next 100 live items linked to the project through them in id order (keyset on the item id) and registers one `runAfterCommit` announcement per item. It stops at the first batch shorter than 100. It writes nothing, takes no row lock and keeps no cursor between runs.

## Contracts dependents build on

- Task: name `derivedValuesInvalidate`, payload `{ projectItemId }`, affinity `api`, tenancy `tenant`.
- Job as the hook queues it: job key `derived-values-invalidate:<projectItemId>`, queue name `tenantLane("derived-values-invalidate")`, which is `derived-values-invalidate:<tenantId>` inside a tenant scope, `maxAttempts` 3. Several edge changes of one project that arrive before the job starts collapse into one job on the key.
- Announcement: `notifyInvalidation({ scope: "item", databaseId, itemId, op: "update", updatedAt })`, one per live item, sent after the commit of the batch that read the item. `updatedAt` is the item's stored `updated_at`; the job does not write the item, so the value is the one the item already had. No `userId` is set; `realtimeHook.ts` documents such an event as delivered to every socket of the publisher's tenant.
- Which items: every live item linked to the project through a relation of `DERIVED_VALUE_SOURCES` (`derived/derivedValueSources.ts`, from gh-1595), by owner module and property key: `tasks.project`, `events.project`, `files.projects`, `healthRecords.projects` and `journal.project`. A later entry of that list is covered without a change here. The project itself, its area and its company are not announced by this job; gh-1621 announces the two ends of the edge.
- A project that is missing, in the Trash or another tenant's announces nothing and the job completes without a failed attempt. A payload that fails the schema throws before anything is announced, so the job fails.
- A batch that throws fails the job; the batches before it stay announced and the retry starts again from the first item, so an item can be announced more than once. The announcement is a refetch trigger and carries no state.
- Registry order in `backend/packages/data/src/domainWriteHooks.ts`: the registration of `projectDerivedValueEdgeChangedHook` is the last entry of the file, after the two entries of gh-1697 and after the entries of gh-1707. The hook needs no other hook's result.
- Order for gh-1714, which names gh-1710 as a `Shared-file ordering` blocker: its two registration lines in `domainWriteHooks.ts` go after the entry of this source, unless its Task names another position.
- gh-1826 names gh-1710 as a blocker and adds a core task to the same catalogs. In `CORE_TASK_NAMES`, `CORE_TASK_AFFINITY` and `TASK_TENANCY` and in `createCoreTaskList` the entries of this source stand directly after the `peopleLastContact*` entries of gh-1660; the `mailboxRemoval` entries of gh-2029 stand elsewhere in the same lists.
- Side effects later sources and tests meet:
  - every create and every delete of a relation edge inside a tenant scope now runs this hook's one read; outside a tenant scope `app_tenant_default()` is NULL, the read finds no row and nothing is queued;
  - a test that writes or removes an edge of `Projects.area` or `Projects.company` (from either side) and then reads `graphile_worker.jobs` finds a `derivedValuesInvalidate` job;
  - `backend/services/semprec-api/src/__tests__/tenantIsolationJobs.test.ts` requires one case per task of the api affinity set and has the case of this task; it records announcements through `setInvalidationHook`, because the job changes no row.

## Deviations from the specification and spec seams

1. Journal entries are announced. The issue text lists tasks, events, files and health records and tells the job to use the configured project properties of gh-1595. That list, `DERIVED_VALUE_SOURCES`, also holds `journal.project`, so a project's Journal entries are announced too. The first test asserts it. Both reviewers accepted it.
2. A file outside `Touches`: `backend/services/semprec-api/src/__tests__/tenantIsolationJobs.test.ts`. That inventory requires exactly one case per task of the api affinity set, so the new task got its case there.
3. A file outside `Touches`: `backend/packages/queue/src/__tests__/taskAffinity.unit.test.ts`, one case for the three catalog entries of Task step 1.
4. The edge-changed hook also receives `op: "update"` (a metadata change). The Task names created and deleted edges only, so `update` queues nothing; a test asserts it.
5. The hook enqueues without a guard for a producer without a tenant scope, like `enqueueRollupRecompute`. The envelope's tenant and the lane come from the producer's scope. Outside a tenant scope the hook's read finds no row, so it does not reach the enqueue.
6. The job has no cap on the number of batches per run; it pages until a batch comes back short. The chunked-transaction ADR's heartbeat sweeps have a cap. The handler's header states the difference, and the rules reviewer found an existing consumer with the same shape (`mail/mailThreadBackfillJob.ts`).
7. "A failing batch retries without announcing items twice in a way that matters": a retry announces the items of the earlier batches a second time, with the same event. The test asserts exactly that.

Follow-ups, none of them filed as an issue:

- Observation of the worker for the controller, not changed: `realtimeHook.ts` documents `updatedAt` as a value a client may compare with its cached copy to skip a stale echo. This job announces items that were not written, so their `updatedAt` is unchanged, as the Task prescribes and as the rollup recompute already does. A client that skips an event with an equal `updatedAt` would keep showing the old derived area or company. The backend cannot show which a client does.
- Observation of both reviewers, not changed and older than this source: `createRelationWithClient` runs the edge-changed hooks with `op: "create"` also for a repeated create of an edge that is already stored (gh-1530), so such a replay of a `Projects.area` or `Projects.company` edge queues one redundant fan-out. It is harmless.
- Observation of the requirements reviewer: the test of a job that names a project that does not exist would also pass without the liveness check, because an id that never existed has no edges. The liveness check is covered by the Trash test.
- Out of scope of the issue and not delivered: reindexing search documents when a project's area changes. The record says it waits for a product decision.
