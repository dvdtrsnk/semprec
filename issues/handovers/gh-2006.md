## What was delivered

The calendar heartbeat action `calendar.ingestInvitation` now also applies an iMIP `METHOD:CANCEL` (the first VEVENT without a RECURRENCE-ID). For a live invitation of the UID, sent from the invitation's organizer address, with a CANCEL SEQUENCE not lower than the stored one, the linked Event goes to the Trash, the invitation gets status `cancelled` and the CANCEL's sequence, and the invitation's notification is resolved, so `pendingInvites` drops. The respond route answers 409 `conflict` for a cancelled invitation.

## Entry points and contracts dependents build on

- `calendar/invitationIngestAction.ts`, `applyCancel` (not exported), in the same per-email transaction as `applyRequest` and under the same tenant and UID advisory lock (`lockInvitationOfUid`). The invitation is read with `listItemsByTextProperty(..., lock = true)`. Sender rule: `normalizeEmailAddress` of `mail_message_meta.envelope.from` equals the stored `organizerEmail` (case-insensitive); a missing sender or organizer fails closed. Stale rule: the CANCEL's SEQUENCE must be greater than or equal to the stored one.
- Writes: the live linked Event through `itemDeleteWithClient` (a soft delete, restorable; `respondedAt` and the answer are kept); the invitation `status` and `sequence` through `updateItemWithClient` as the calendar module system owner with `allowedSystemKeys` limited to those two; the notification through `resolveNotificationsBySource` with source table `items` and the invitation id, as the respond route does. Lock order: UID advisory lock, invitation row, Event row, the same as the respond route.
- No-ops: an unknown UID, a trashed invitation and an already cancelled invitation change nothing and log nothing; a sender mismatch and a stale sequence change nothing and log email id, invitation id and a reason code (`sender_not_organizer`, `stale_sequence`), never content. A REQUEST with a higher SEQUENCE for a cancelled invitation changes nothing. Any failing step rolls the whole email back; a malformed or unmatched message does not make the action throw.
- No route, table, hook, job name, migration or export is added.

## Deviations from the specification and spec seams

1. A trashed invitation with the UID is left alone by CANCEL, consistent with REQUEST (no resurrection); the Task says only "when there is none, do nothing".
2. Only the sender mismatch and the stale sequence log a reason code, as the Task says; the other no-ops are silent.
3. Parts of one message are processed in the order `readCalendarPartsOfEmail` returns them (by attachment id), not MIME order.
4. A CANCEL VEVENT without DTSTART or UID is rejected by the existing parser as malformed and skipped (existing behaviour).
5. The commit trailer of the segment is `Co-Authored-By: Claude Sonnet 5.5`, the model that wrote it, not the trailer named in the dispatch.
6. A shared test helper file was added rather than editing the large existing test.
