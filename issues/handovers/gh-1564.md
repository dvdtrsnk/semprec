# gh-1564 — Store Inbox attachments as counted blob references

Repository-Issue: gh-1564

## Delivered behavior and production wiring

- Migration `backend/packages/data/src/db/migrations/0118_inbox_attachments.sql` (next free ordinal on the integration tip `c94e6466`; 117 migrations there, `origin/develop` has 86). Additive only. Table `inbox_attachments` with `attachment_id` primary key, `tenant_id` (default `app_tenant_default()`, references `tenants`), `inbox_item_id` (no foreign key to `items`, which is partitioned), `blob_id`, `position`, `source` (CHECK over `camera`, `scan`, `photoLibrary`, `files`, `share`) and `created_at`. Keys: unique `(tenant_id, inbox_item_id, position)`, index `(tenant_id, blob_id)`. Foreign keys: `blob_id` references `blobs(id)` and the composite `(tenant_id, blob_id)` references `blobs (tenant_id, id)`, the pair 0083 uses for every reference between tenant rows. The single-column reference is an addition beyond the Task's list, made for that convention. The table is classified `semprec:tenancy=tenant`, has the restrictive `tenant_isolation` and permissive `tenant_rows` policies as in 0078, and grants `SELECT, INSERT, UPDATE, DELETE` to `semprec_side` (`semprec_data` inherits it).
- `backend/packages/data/src/inbox/inboxAttachmentsStore.ts`: `insertInboxAttachments(client, inboxItemId, [{ blobId, source }])` appends after the current maximum position in one statement, with no lock on the item. `listInboxAttachments(client, itemIds)` and `getInboxAttachment(client, attachmentId)` return `{ attachmentId, inboxItemId, blobId, mimeType, byteSize, source, position }` joined with the blob. `deleteInboxAttachment(client, attachmentId)` returns whether a row existed and leaves the blob alone. `deleteInboxAttachmentsForItem(client, inboxItemId)` is an addition beyond the Task's list: it deletes every row of an item in one statement and returns the blob ids, which the purge needs. All five are exported from `@semprec/data` (`index.ts`), and `publicSurface.test.ts` lists them.
- `blobsStore.ts` `deleteBlobIfUnreferenced`: adds `AND NOT EXISTS (SELECT 1 FROM inbox_attachments WHERE blob_id = $1)` after the mail-attachment check. A blob an attachment names is not deleted, so the unreferenced-blob sweep of gh-1401 keeps it too.
- `chokePoint/itemTrash.ts` `deleteItemDependents`: deletes the item's attachment rows first, then calls `deleteBlobIfUnreferenced` once per distinct blob they named. Bytes of released blobs are returned in `blobStorageKeys` and removed by `purgeExpiredTrash` after the commit, as before. The return value was already a `blobStorageKeys` list on the tip, so its shape did not change.
- Trashing an Inbox item does not touch its attachment rows (`softDeleteItem` does not call `deleteItemDependents`). Only the permanent purge removes them.
- Tenant export and tenant purge need no code change: both read the tenant tables from the catalog comment, and purge orders deletes children first from the catalog foreign keys, so `inbox_attachments` goes before `blobs`.

## Notes for dependants

- #1963 (capture attaches uploaded blobs): call `insertInboxAttachments` inside the capture transaction, after the Inbox item exists. The store does not check that `inboxItemId` names an existing Inbox item (there is no foreign key, and nothing else in the store checks it), so the capture route must establish that. The row's tenant is stamped from the scope, and the blob must belong to the same tenant. Positions come from a `MAX` read with no lock, so two inserts for one item running at once fail on `inbox_attachments_item_position_uq` with 23505 instead of taking a duplicate position. A capture that can run concurrently for one item needs to serialize on the item or handle that error.
- #1703 (move into Files on confirm): `deleteInboxAttachment` removes only the row. Create the Files item that names the blob in the same transaction, before or with the row delete, so the blob is never unreferenced. `deleteInboxAttachment` has no production caller yet.
- #1606, #1965, #1969 read through `listInboxAttachments` and `getInboxAttachment`. `byteSize` is a string, as on `BlobRow`.
- A purge that races a concurrent attach of the same blob: the blob `DELETE` is refused by the foreign keys, so that item's purge fails and is logged, and the item stays trashed for a later run. No dangling reference is left.
- Migration ordinal `0118` was chosen on `c94e6466`. A parallel issue that also takes `0118` collides at integration; renumber only the later branch's file.
