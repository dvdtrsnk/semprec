# gh-1453 — [ticks 03/11] Trigger a heartbeat manually over HTTP

Repository-Issue: gh-1453

## Delivered behavior and production wiring

- `enqueueManualHeartbeatFire(client, request, moduleRuleKinds)` in `backend/packages/data/src/scheduler/heartbeatAgentTools.ts` is the one enqueue behind every manual fire. It runs in the caller's transaction: the lookup (`lockHeartbeatForManualFire`, a `FOR UPDATE` read in `schedulerStore.ts`), the not-found check, the `onItemEvent` rejection, the enabled check, the optional active-run refusal, then the enqueue. Refusals are typed errors, not result objects.
- `heartbeat.trigger` calls it inside `withTransaction` with `refuseWhileActive: false`. Its refusals are mapped back to the tool's earlier result strings (`refusalForAgentTool`), so its results do not change.
- `POST /api/heartbeats/:id/trigger` is `createTriggerHeartbeatRouteHandler` in `backend/packages/data/src/scheduler/triggerHeartbeatRoute.ts`. It is declared as a custom route in `schemaCoreModuleManifest.ts` (`transactional-semantics`), listed in `routeMatrix.ts` with tenancy `tenant`, mapped in `ROUTE_HANDLER_FILES`, and covered by a case in `tenantIsolationRoutes.test.ts`. The caller is the authenticated session user, read from the identity and never from the body. The answer is `202 {jobKey, activeRun: null}`; the run does not exist yet. A malformed id is `400 validation_failed`. An unknown id and another tenant's id are both `404 not_found`.
- The HTTP route refuses with `HeartbeatRunningError` (`409 heartbeat_running`) while a run of the heartbeat is `running` or a fire job of it is waiting. `details.activeRun` is that run as `{id, status, triggeredBy, startedAt, threadId}`, or `null` while only a job waits. The lookups are `getRunningAgentRunOfHeartbeat` (`agentRunsStore.ts`) and `hasWaitingHeartbeatFireJob` (`schedulerStore.ts`). The second one counts a `graphile_worker.jobs` row whose key is the manual key or starts with `heartbeat-fire:<id>:`, and only while the row is locked or has attempts left.
- `HeartbeatDisabledError` (`409 heartbeat_disabled`) is new. `HeartbeatEventTriggeredError` (`409 heartbeat_event_triggered`) was already defined and is now thrown. All three classes are in `backend/packages/data/src/errors.ts`, and the barrel re-exports them.
- `heartbeat_disabled` and `heartbeat_running` are in `ITEM_ERROR_CODES` and `ITEM_ERROR_STATUS_BY_CODE` (409 each) in `backend/services/semprec-api/src/adapter/errorContract.ts`. `toErrorResponseBody` projects `heartbeat_running.details.activeRun` field by field, because the generic branch drops nested `details`.
- Attribution: the fire payload gains `triggeredByUserId` as a fourth discriminator in `sweep.ts`. Exactly one discriminator is still required. `ActionContext.triggeredByUserId` carries it to `coreAgentRunAction`, which passes it as `userId` to `createAgentRun`. The new run has `parent_run_id` null, `triggered_by` `heartbeat`, and `actor_user_id` set to the person.
- The tick-thread invalidation was already published by `coreAgentRunAction` when it creates a run (`publishSempThreadInvalidation`). Nothing new was needed for it.
- No migration. No ADR: the row lock and the graphile-job read both follow existing patterns (`state-writes` §4, `findTranscriptionJobId`).

## Decisions

- **The active-run refusal is on the HTTP path only.** `refuseWhileActive` is `true` for the route and `false` for the agent tool. The agent tool keeps merging a repeat trigger into a waiting job, and it still enqueues while a run is active. That is what the existing test "collapses repeated pending manual triggers onto a single job" pins, and what the acceptance criterion "keeps its previous results" requires. Consequence: an agent can still start a second run of a heartbeat that is running. If that should change, it is a follow-up.
- **Both paths lock the heartbeat row.** The old comment said a concurrent `setHeartbeatEnabled(false)` could not slip a job past the disabled check, but under READ COMMITTED without a lock that was not true. The `FOR UPDATE` in `lockHeartbeatForManualFire` makes it true.
- **Scheduled fires block a manual Run.** The issue says "a fire job is already waiting", so a scheduled occurrence queued for the same heartbeat gives `409 heartbeat_running` with `activeRun: null`.
- **Exhausted jobs do not block.** A permanently failed job keeps its key until `queueFailedJobsPrune` deletes it. A keyed enqueue revives an unlocked row, and graphile-worker 0.17.3's `add_job` resets its `attempts` (`sql/000018.sql`, `where jobs.locked_at is null`). So a job counts only while it is locked or has attempts left.
- **Attribution cannot be told apart from the tenant fallback in tests.** `users_tenant_id_key` (`0056_tenants.sql`) allows one user per tenant, so the person who presses Run is always the tenant's fallback actor. The test asserts `actorUserId` equals that person. It cannot show that the `userId` path was taken rather than the fallback.
- The HTTP handler is built from the pool alone, so it passes no module rule-kind registry. Module-kind heartbeats are read with the tolerant parse the agent tool uses without a registry. The worker still resolves the rule with its registry.

## Tests

- `backend/packages/data/src/__tests__/heartbeatManualTrigger.test.ts` (new, 13 tests, integration tier):
  - 202 with the job key, and one job attributed to the person.
  - The worker creates the run with no parent and the person as actor.
  - A second trigger while the run is running gives 409 `heartbeat_running` with that run, and one run exists afterwards.
  - A second trigger while the job waits gives 409 with `activeRun` null, and nothing new is queued.
  - An exhausted waiting job does not block, and the new trigger revives it.
  - A job locked on its final attempt blocks.
  - A waiting scheduled occurrence blocks.
  - A disabled heartbeat gives 409 `heartbeat_disabled`, and nothing is queued.
  - An `onItemEvent` heartbeat gives 409 `heartbeat_event_triggered`, and nothing is queued.
  - An unknown id gives 404, and a malformed id gives 400.
  - The agent tool still enqueues while a run is running, and merges a repeat into a waiting job.
  - The agent tool gives not-found for a heartbeat outside the calling run's project.
  - A fire payload with both `triggeredByRunId` and `triggeredByUserId` is refused with `validation_failed`.

## Notes for dependants

- **#1908 (failed-run retry)** should call `enqueueManualHeartbeatFire`. Pick `refuseWhileActive` on purpose: a retry usually follows a closed run, so the refusal rarely applies.
- **#1562 (thread header `canTrigger`/`activeRun`)**: the 202 always carries `activeRun: null`. The active run is in the 409 `details`, or in the thread after the worker's invalidation.
- The manual job key is `heartbeat-fire:manual:<heartbeatId>`, and the route returns it as `jobKey`.
- The fire payload now has four discriminators, exactly one of which must be present. A new consumer of the payload must accept `triggeredByUserId`.
- A new route that raises `HeartbeatRunningError` gets its `activeRun` projection through `toErrorResponseBody`. A bespoke handler using `toPublicErrorBody` would drop the nested `details`.
