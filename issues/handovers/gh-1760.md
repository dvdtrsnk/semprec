## Contracts dependents build on

Response for a live area of the caller's tenant:

`{ activeProjectCount, todayTaskCount, openTaskCount, upcomingEventCount, upcoming: [{ kind, itemId, title, date, timeFrom, timeTo, status, recurrence, project: { id, title, color } }] }`

- **Eligible projects** are the live projects of the area that are not archived and store no `systemActive` value. Done projects stay eligible. A system project, active or deactivated, is neither eligible nor active.
- **`activeProjectCount`**: user projects with status `inProgress` or `longTerm`, counted with `itemsStore.countItemsGrouped` grouped by area, inside the handler's transaction. The filter is the module-private constant `ACTIVE_PROJECTS_FILTER`; **gh-1837 needs the same rule and nothing is exported for it.**
- **`openTaskCount`**: the `notDone` tasks of eligible projects, dated or not. **`todayTaskCount`**: those dated today or earlier. Both are computed in code from the rows of every open task; there is no SQL aggregate and no row limit on that read.
- **`upcoming`**: the open tasks dated up to the 14th day counting today (overdue ones included) and the events of eligible projects that start from now to the end of that day; ordered by date, then untimed entries before timed ones, then time, then title (`Intl.Collator` in Czech or English by the caller's `users.locale`), then item id; cut to 20. **`upcomingEventCount`** is counted before the cut.
- **Entry fields**: `status` is `"notDone"` for a task and null for an event. `recurrence` is `{ mode, rule }` of the active `task_recurrence` row whose item is the task (`getTaskRecurrence`, one lookup per listed task, at most 20), otherwise null. An event starts at `timeFrom` on its date, an all-day event at 00:00; an all-day event of today is not upcoming once the day has begun.
- **Time**: today, now and the horizon are computed in the tenant's time zone.
- **Consistency**: all statements run in one REPEATABLE READ transaction in the caller's tenant scope.
- **Errors**: a non-UUID id answers 400 `validation_failed` on `id`; an unknown id, a trashed area, an item of another database, another tenant's area and a tenant without an Areas database answer the same 404 `not_found`. A tenant that holds the area and lacks the Projects database or a resolvable area, tasks or events relation of Projects fails with a plain Error (generic 500).
- **Legacy values**: an item whose stored date is not a calendar date `YYYY-MM-DD` (a legacy Event date-time that gh-1797 has not converted) has no place in the list; an event of that kind is not counted, a task of that kind counts in `openTaskCount` only. An unreadable stored time is returned as null; a missing name is an empty title.
- **Not built**, named in Out of scope: event end, tasks hidden in events, original day, flag, realtime invalidation, a global summary.

## Deviations from the specification and spec seams

1. Spec seam: the route entry is in a new slice module `routeMatrix/areas.ts`, because no slice for `/api/areas` existed.
2. `countItemsGrouped` is called directly instead of `chokePoint.countItemsBatch`, which opens a transaction of its own while the Task asks for one transaction.
3. "Not systemActive" is read as "stores no `systemActive` value".
4. The shape of `recurrence`, the start of an event, the order beyond date and time, the handling of legacy values and the `status` of an entry are decisions where the issue is silent; they are listed above and each has a test.
5. The transaction is REPEATABLE READ (the existing isolation option of `withTransaction`). No ADR was added.
6. Files outside `Touches`: `chokePointWriteBoundary.unit.test.ts`, `routeMatrix.ts`, `routeMatrix/areas.ts`, `publicSurface.test.ts`.
