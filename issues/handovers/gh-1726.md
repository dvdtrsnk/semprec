# Handover for gh-1726

Merge duplicate journal entries of one period. Candidate commit `cf2c11858f4c96ecb4057fce1ee85c4af3c86478` (one segment of three commits: the implementation `cc54c50f24949ae757df4a6c12f7e3ad21b6a524` and the review fixes `76111795cf6a7fcfaad480aa9f3cdc98b594c791` and `cf2c11858f4c96ecb4057fce1ee85c4af3c86478`) landed on `feature/backend-parallel` with merge `7a5707676fadda792700bbf9dfaa56251fc91c97` (chain `p0-05-journal`). The acceptance receipt is `issues/batches/backend/acceptance/sources/gh-1726.md`.

## What was delivered

- `mergeJournalDuplicates(client, { periodType, period })` in `backend/packages/data/src/journal/mergeJournalDuplicates.ts`, exported from the `@semprec/data` barrel. It merges the two live Journal entries of one period that were created first: the older one survives, the newer one is merged into it and moved to the Trash. It runs on the client of the caller's `withTransaction`, so every step is part of that transaction. It returns `{ survivorId, mergedItemId, refusedEdges }`, or `null` when the period has fewer than two live entries; a repeated call reads that and writes nothing. A period with more than two live entries takes one call per duplicate, the two oldest first.
- Lock order, in the new `lockJournalDuplicatePair` (`journal/journalStore.ts`): a plain read finds the pair and returns `null` before anything is locked or written when there is none; then the period reservation row (`idempotency_keys`, key `journal:<journalDatabaseId>:<type>:<period>`) is taken with the statement the restore of gh-1666 uses, inserted for the older entry when it is missing; holding it, the same read runs again with `FOR UPDATE` and row-locks both entries; last, the reservation is pointed at the survivor. The survivor is chosen by `created_at`, then `id`.
- Page: the duplicate's page is read as canonical Markdown and appended to the end of the survivor's page through `insertPageMarkdown` (gh-1679) with placement `end` and origin `system`, in block order. The duplicate's first block is left out when it is a heading and the survivor's page starts with a heading of the same level and the same inline content. The duplicate keeps its own page.
- User-owned Journal relations (seeded: `area`, `project`): every relation property of the Journal database with owner `user` is moved by the new choke-point helper `moveRelationEdgesWithClient` (`chokePoint/relationOps.ts`), each edge as `deleteRelationWithClient` plus `createRelationIfAbsentWithClient`, as the system writer. An edge the survivor already has keeps its own metadata there and the duplicate's copy is only deleted.
- System-owned relations are written by their owners. `events` (owner process `journalEventLinks`): the merge calls `syncJournalEventLinks` on the survivor's page as it stands after the append; the duplicate's own `events` edges are left as they are. Inbox `journalDay`: the new `moveJournalDayEdges` (`inbox/moveJournalDayEdges.ts`) calls the same move with `ownerProcess: 'inbox'` (delete, then create) and, when it deleted at least one edge from the duplicate, enqueues the existing Inbox recompute of both entries.
- Trash: the duplicate is moved to the Trash through `itemDeleteWithClient` as the system writer. Nothing is hard-deleted.
- Edges the choke point refuses for the survivor with a `ValidationError` stay on the trashed duplicate and the merge still succeeds: an edge to an item in the Trash, a stored Journal `area` while the survivor's `area` is derived from its project, the `journalDay` edge of a trashed Inbox item, an edge a domain edge-write hook refuses. Each one is returned in `refusedEdges` and written as one `info` line of the new `journal` logger (`journal/logger.ts`) after the caller's transaction has committed.
- The decisions are recorded in the new ADR `docs/adr/2026-11-10-journal-duplicate-merge-locks-the-reservation-before-both-entries.md`.

## Contracts dependents build on

- Exports added to `@semprec/data` (`backend/packages/data/src/index.ts`): the function `mergeJournalDuplicates` and the types `MergeJournalDuplicatesInput`, `MergeJournalDuplicatesResult` and `RefusedRelationEdge`. `mergeJournalDuplicates` is the one new runtime name in the expected list of `publicSurface.test.ts`.
- Signature: `mergeJournalDuplicates(client: PoolClient, input: { periodType: JournalPeriodType; period: string }): Promise<MergeJournalDuplicatesResult | null>`. `period` is the canonical period key as stored in the entries' `period` property. The function does not validate `periodType` or `period`: both are bound as SQL parameters, and a value that matches no entry yields `null`. gh-2017 asks for 400 on an unknown type or a malformed period and names its input `{ type, period }`, so it validates and maps the fields itself.
- Result: `{ survivorId, mergedItemId, refusedEdges }`. `refusedEdges` is an array of `{ relationPropertyId, otherItemId, code, field }` and is empty when the survivor took every edge. `code` is the `code` of the refusing `ValidationError`, which is always `validation_failed` today; `field` is that error's `details.field` (`callerItemId` or `targetItemId` for an endpoint in the Trash or missing, the property key such as `area` for a derived value) or `null`. The Task of gh-1726 and the output of gh-2017 name the two-field result `{ survivorId, mergedItemId }`; `refusedEdges` is a third field added by the review fix, so gh-2017 maps the fields explicitly and its owner decides whether the operation shows `refusedEdges`. `null` is the "no duplicate" answer that gh-2017 maps to `{ merged: false }`.
- The caller owns the transaction. A client that is not the one of an active `withTransaction` is refused with `Error("Protected relation requires an active managed transaction")` before any write (`requireManagedTransaction`). The function does not mark the transaction rollback-only: "a failure changes nothing" holds when the caller lets the error escape its `withTransaction`.
- Errors: `NotFoundError("Journal database not found")` in a tenant without a Journal database; `ConflictError` (409) when the period's reservation key belongs to another database; `Error("Inbox 'journalDay' relation not found")` when the Inbox relation is missing; the `ValidationError` of `insertPageMarkdown` (`details.field` `markdown`) when the duplicate's page holds a subpage block or a link to an item that is not live. Such a duplicate cannot be merged until that content is removed; the merge fails and changes nothing.
- The function has no approval gate and no caller on this branch other than its tests. The approval-gated operation is gh-2017; gh-1883 only lists duplicated periods and does not call it.
- Reservation: after a merge the period reservation points at the survivor, so the next `getOrCreateJournalItem` for the period returns the survivor and creates no third entry. A transaction that takes the reservation after the merge took it (`getOrCreateJournalItem`, a restore of an entry of the period, another merge) waits until the merge ends. This is the second purpose for which the Journal module writes that `idempotency_keys` row; the first is the restore of gh-1666.
- Log line: logger `journal`, level `info`, message `Journal duplicate merge left a refused edge on the merged entry`, fields `survivorId`, `mergedItemId`, `relationPropertyId`, `otherItemId`, `code`. One line per refused edge, registered with `runAfterCommit`; a merge that is rolled back logs nothing.
- Inside the data package, not in the barrel: `moveRelationEdgesWithClient(client, { relationPropertyId, side, fromItemId, toItemId }, context?)` returning `{ moved, refused }` (`chokePoint/relationOps.ts`), `moveJournalDayEdges(client, { fromDayItemId, toDayItemId })` returning the refused edges (`inbox/moveJournalDayEdges.ts`), `lockJournalDuplicatePair` and the type `JournalDuplicatePair` (`journal/journalStore.ts`), and the `journal` logger. `moveRelationEdgesWithClient` does not check cardinality before it writes: on a `one_to_one` or `one_to_many` relation whose receiving item already holds its only edge, the move fails with `CardinalityViolationError` after the delete, so the caller's transaction must roll back. The three relations the merge moves are seeded `many_to_many`. Neither helper calls `requireManagedTransaction` itself; the merge does.
- `repointJournalPeriodReservation` (gh-1666) keeps its statements and its `ConflictError`; its two reservation statements now live in the private helpers `takeJournalPeriodReservation` and `pointJournalPeriodReservation`, which the merge reuses.
- No route, no generic operation, no MCP tool, no job name, no hook registration, no table and no migration was added. The merge enqueues the existing job `CORE_TASK_NAMES.JOURNAL_INBOX_RECOMPUTE` through `enqueueJournalInboxRecompute`. No module manifest and no i18n catalog is touched; the function has no user-visible text.

## Deviations from the specification and spec seams

1. Files beyond the issue's `Touches`: `journal/journalStore.ts` (the locked pair read and the reused reservation statements), `chokePoint/relationOps.ts` (the generic re-point of Task step 3), `inbox/moveJournalDayEdges.ts` (the Inbox edges are moved by an Inbox-module function, as `journalDayRelinkHook.ts` of gh-1603 keeps that identity in the Inbox module), `journal/logger.ts`, `publicSurface.test.ts` (expected export list) and the ADR.
2. The period reservation is taken first and pointed at the survivor. The Task does not mention it. Without it the next `getOrCreateJournalItem` creates a third entry whenever the reservation pointed at the merged entry.
3. Task step 3 says every relation property of the Journal database. The system-owned `events` relation is not moved by the merge: its owner `syncJournalEventLinks` is called on the merged page in the same transaction, so the survivor has the event edges at commit and the duplicate keeps its own. A system-owned relation property of the Journal database added later is not moved until its owner takes part in the same way.
4. The acceptance criterion says the survivor has all relation edges. An edge the choke point refuses for the survivor stays on the trashed duplicate; the merge succeeds and reports it in `refusedEdges` and in the log. An edge to a trashed item does not reach the survivor when that item is restored later, and every refused edge is deleted with the duplicate when the Trash purge removes it.
5. Task step 4 names the result `{ survivorId, mergedItemId }`. The result has a third field, `refusedEdges`, added by the review fix; "do nothing" is `null`.
6. "Skipping an edge the survivor already has" is implemented as: the survivor's edge and its metadata stay, the duplicate's edge is deleted.
7. A duplicate whose page holds a subpage block or a link to an item that is not live cannot be merged: the Markdown insertion path the Task prescribes refuses it, the merge fails with that `ValidationError` and changes nothing. Lifting it needs another insertion path or an owner decision.
8. The duplicate's page content is appended to the survivor and also stays on the trashed duplicate (the Context says "move", the Task says "append"). A document update that reaches the duplicate's page after the merge read it is not carried over.
9. "Equal heading" is implemented as: both pages start with a heading of the same level and the same inline content.
10. The issue says the Inbox edges are changed "as #1666 does for a reservation". The code that does delete plus create for `journalDay` is the hook of gh-1603, which was the model.
11. A relation property of another database that targets Journal, other than Inbox `journalDay`, is not re-pointed. Task step 3 limits the generic move to relation properties of the Journal database, and no such relation is seeded.
12. The test file is in `packages/data/src/__tests__/`, as the issue's `Touches` says, not in `journal/__tests__/`.

## Review

Three reviewers read `cc54c50f^..cc54c50f` read-only and ran no build and no test: requirements and tests (verdict findings, one medium and one low; all three acceptance criteria rated covered), project rules and architecture (verdict findings, one medium) and security (verdict clear, no finding). The two medium findings describe one defect: edges the survivor cannot take stayed on the trashed duplicate while the merge reported a complete merge, with no log line and nothing in the result. The fixer confirmed it and fixed it in `76111795`: `moveRelationEdgesWithClient` returns `{ moved, refused }`, `moveJournalDayEdges` returns its refused edges, the merge returns them as `refusedEdges` and logs each after commit. The low finding (a docstring claimed the pre-check answers whether the create would succeed, while cardinality is checked only by the write) was fixed in `cf2c1185` with docstrings and one test. One focused recheck read `cc54c50f..cf2c1185`, ran no test, and returned verdict pass with nothing unresolved and two new low findings, which are follow-ups below.

Follow-ups and open decisions recorded by the worker, the reviewers, the fixer and the recheck, none of them done:

- Recheck, low, not fixed: `moveRelationEdgesWithClient` asks whether the edge can be created on the receiving item before it looks whether that item already has the edge. When both entries are linked to the same item and that item is in the Trash, the merge reports a refused edge and logs it although the survivor already carries that link and nothing is lost. The ADR sentence "An edge to a trashed item does not reach the survivor when that item is restored later" is not true for such an entry, and a caller that tells the user from `refusedEdges` would report a lost link that is not lost. Proposed: do not report a refused edge the receiving item already has, or say so in the docstring and the ADR.
- Recheck, low, not fixed: the `code` of a refused edge is always `validation_failed`, so the log line does not say why an edge was refused; only `field`, which the result carries and the log line leaves out, tells the refusals apart. Proposed: add `field` to the log line, or drop the constant `code` from it.
- For gh-2017: map the result fields explicitly; decide whether `refusedEdges` is shown; decide how the operation reports a merge refused by the page insertion (subpage block or dead link), whose `ValidationError` names the field `markdown`, which is no input of the merge.
- The merge locks entry rows before page document rows, the order `insertPageMarkdown` already uses. `handleItemSearchPageTextTask` locks the document first and the entry row after, so the two can deadlock and Postgres aborts one. This order predates the change, and the ADR claims no deadlock freedom beyond the reservation and the two entries.
- When the reservation row is missing and the locked re-read finds fewer than two live entries, the `null` return leaves the reservation row that the lock step inserted for the entry seen by the unlocked read. The rules reviewer judged this no worse than the missing row.
- The contended-transaction test harness is now copied in `journalRestore.test.ts` and `mergeJournalDuplicates.test.ts` and could move to `testSupport`.
- `journalDayRelinkHook.ts` could use `moveRelationEdgesWithClient`.
