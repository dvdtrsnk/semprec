## What was delivered

- `itemsStore.findItemsDeletedBefore` restricts its database-id list to databases with `archived_at IS NULL`, so expired trashed items inside an archived database are no candidates of the item trash sweep and no `Failed to purge trashed item` error is logged for them. When the database is restored, the next sweep purges those items.
- `purgeExpiredTrash` treats a `ForbiddenError` with code `database_archived` from `purgeExpiredTrashSubtree` as a quiet skip with a debug line (the item id only), for a database archived between the candidate read and the purge. Every other failure is still logged as an error.

## Entry points and contracts dependents build on

- No new export, route, operation, table or job name. Behaviour change in the existing sweep (`purgeExpiredTrash`, `handleItemTrashPurgeSweepTask`): items of an archived database are left to the archived-database purge of gh-1875 (which deletes the whole database after its own deadline) or to a restore.
- `findItemsDeletedBefore` keeps the database ids bound as one array parameter, so the partition pruning that `itemLookupPruning.test.ts` checks still holds.

## Tests

`purgeExpiredTrash.test.ts`: an item deleted 40 days ago in an archived database is left alone with no error; the same item is purged on the next run once the database is restored; an expired item of a live database is purged as before, next to one in an archived database; an item whose database was archived between the candidate read and the purge is skipped quietly; a refusal that is not the archived one is still logged as an error. `purgeExpiredTrashPerTenant.test.ts`: tenant B's trashed item in an archived database is left alone without an error while the rest is purged. All passed in the landing gate on the merged tree.

2. `purgeExpiredTrashPerTenant.test.ts` is not in `Touches`; it asserted the old error line for an archived database and was brought in line (spec seam).
3. The old test 'never hard-deletes an eligible item whose database has since been archived' would now pass for another reason (the item is no candidate), so it was replaced by the Task's four cases plus one for a non-archived refusal; `purgeExpiredTrash.test.ts` gained a `hardDeleteItem` passthrough spy in its `itemsStore` mock to inject that refusal.
