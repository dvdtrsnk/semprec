## What was delivered

- A relation edge changed hook, `threadTaskPeopleEdgeChangedHook` (`mail/threadTaskPeople.ts`), registered as the last registration of `domainWriteHooks.ts`. For a create of an `Emails.senderPeople` or `Emails.recipientsPeople` edge on a message that belongs to a thread it enqueues the module task `mailSyncThreadTaskPeople` with `{ threadItemId, personId }` in the edge's own transaction (rolled back with it). Updates, deletes, other properties, unthreaded messages and writes without a tenant scope enqueue nothing.
- The module task `mailSyncThreadTaskPeople` (api queue affinity), declared in the `taskNames` of `mailModuleManifest.ts`, handler `handleMailSyncThreadTaskPeople`, payload schema `mailSyncThreadTaskPeoplePayloadSchema` (strict, two uuids). Job key `mailSyncThreadTaskPeople:<tenantId>:<threadItemId>:<personId>`.
- The job resolves the thread's tasks through `Threads.tasks`, row-locks each task and then its `Tasks.people` value link (`FOR UPDATE`, the lock order of `valueLinks/linkPropagation.ts`), re-reads the link under the locks, and adds the person as the `valueLinks` process only when the task is live, the link is `on`, its rule key is `mailThreadTaskPeople` and an item source names this thread, and the person is not already present. A task whose people were changed by hand (link broken) is left alone. The person must still be in the thread's conversation (live message, live person, not the tenant's own mailbox address). One item invalidation per changed task after the commit.
- ADR `docs/adr/2026-11-14-thread-task-people-follow-the-conversation-by-additions-under-the-task-lock.md` records the hook-queues-job-writes-under-lock pattern and the per-person job key.

## Deviations from the specification and spec seams

1. Job key includes the person and the tenant, not the thread alone: a per-thread key would replace the payload of a queued job when a second person joins the same thread.
2. Module task handlers get no pool, so `setThreadTaskPeopleDelivery` was added and `queueRuntime.ts` changed (outside the Touches list), as the binding ADR requires; `publicSurface.test.ts` lists the new export.
3. `tenantIsolationJobs.test.ts` needs one case per api task, so a case was added, and `createThreadTask` is re-exported from `testSupport/testDb.ts` for its fixture.
4. `CONVERSATION_PEOPLE_SQL` of `threadTasks.ts` is wrapped in the new exported `listConversationPersonIds` so the job and the creation share one definition.
5. "Unbroken" is read as: link state `on` and rule key `mailThreadTaskPeople` and an item source naming this thread. A link of another rule, no link, or a link naming another thread is left alone.
6. The job also requires the person to still be among the conversation's people.
7. The manifest header comment, which said the module declares no `taskNames`, was updated; at the landing it names both module tasks (`mailTriageThreadProject` of gh-1872 and this one).
8. The hook treats op `create` as an added edge; a repeated put of an existing edge also has op `create` and queues the same key (idempotent). The hook SQL assumes the Emails property is side A of the relation (the seed makes both properties one-directional).
9. Shared-file ordering: gh-1916 is still open, and gh-2033 was not landed when the worker ran (it has since landed in chain `e1-180-mail` and registers no hook). The registration is the last one in `domainWriteHooks.ts`; when gh-1916 lands, its entries in `domainWriteHooks.ts` and `db/tenantCutoverMigrations.ts` go before this one.
