# Handover: fail a test when a mounted API route has no ROUTE_MATRIX entry

Delivered on chain `e1-242-route-matrix-test`, candidate commit `7c095cc9f9a68dae3adca6b955f4a7217e0bc4e7`, landed by a `--no-ff` merge on `feature/backend-parallel` as the second chain of a train with `e1-239-backup-restore`.

**What changed.** In `backend/services/alldots-api/src/app.ts`, the nine-factory array of resource routes that `createDispatcher` built inline moved, with the same factories in the same order and the same arguments, into the exported `createResourceRouteDefinitions(pool, options, heartbeatRuleKinds, genericApplicationService, collectionMetadataResolver)`. `createDispatcher` calls it and passes the result to `mountRoutes`. A new unit test `backend/services/alldots-api/src/__tests__/routeMatrixCoverage.unit.test.ts` holds a pure helper `findUnmatchedRoutes` and a coverage case that builds `getCustomRouteDefinitions()` of the full module registry and `createResourceRouteDefinitions()` (with a `new pg Pool()` that opens no connection, a real generic application service and a real collection metadata resolver) and asserts that every definition has a `ROUTE_MATRIX` entry with the same method, surface `api` and a path its pattern matches. The doc comment of `ROUTE_MATRIX` in `routeMatrix.ts` now says which routes are checked.

**Contracts dependents build on.** New export `createResourceRouteDefinitions` from `app.ts` (no change of behaviour). A route added later to a module's custom routes or to one of the nine resource-route families without an entry in `ROUTE_MATRIX` fails `routeMatrixCoverage.unit.test.ts` in the unit tier, naming the method and path. No entry of `ROUTE_MATRIX`, `ROUTE_CASES` or `ROUTE_HANDLER_FILES` changed, no route, table, migration, operation or job name.

**Files.** `backend/services/alldots-api/src/app.ts`, `backend/services/alldots-api/src/routeMatrix.ts` (doc comment only), `backend/services/alldots-api/src/__tests__/routeMatrixCoverage.unit.test.ts` (new).

**Tests.** `routeMatrixCoverage.unit.test.ts`: helper cases (a definition without an entry is reported and only that one; an entry with another method or a `ws` surface does not match; multi-segment, empty-segment, literal-mismatch and query-string cases); coverage cases that remove the real entry of one custom route and one resource route and assert exactly those are reported; the pass case asserts both route lists are non-empty. Existing route tests (`routeMatrix.test.ts`, `adapterTenantScope.test.ts`, `routeMatrixInventory.unit.test.ts`, `chokePointWriteBoundary.unit.test.ts`) are unchanged.

**Deviations and spec seams.** No spec seam. `createResourceRouteDefinitions` takes five arguments, the distinct values the nine factories take. The test builds the real generic application service and metadata resolver instead of stubs, because their construction opens no connection.

**Criteria NOT RUN or BLOCKED.** None. The worker did not run `tenantIsolationRoutes`, `cacheControl`, `bespokeListenerTenantScope` and `adminHandler`; the landing gate ran them.

**Review.** Requirements and tests lens: clear. Rules and architecture lens: clear. No security review (no authentication, secret, public route or destructive change). No fix round. Both reviewers read statically and ran no tests.
