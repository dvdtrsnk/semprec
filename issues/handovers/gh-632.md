Closes #632. A push registration now belongs to the user who created it. If another user tries to register the same endpoint or device token while it is still active, the request fails with 409 `version_conflict` and the owner's row is left untouched.

## Changes

**`backend/packages/data/src/push/pushSubscriptionsStore.ts`**
- `upsertWebPushSubscription` and `upsertApnsSubscription` now add `WHERE push_subscriptions.user_id = EXCLUDED.user_id` to their `ON CONFLICT ... DO UPDATE`. I also removed `user_id = EXCLUDED.user_id` from the `SET` list, because under that predicate it could never change anything.
- If the insert returns no row, the active row for that endpoint or token must belong to someone else. The store then throws:
  - `ConflictError("'endpoint' is already registered to another account", { field: "endpoint" })` for web push;
  - `ConflictError("'deviceToken' is already registered to another account", { field: "deviceToken" })` for APNs.

  Before, this case would have reached `requireSingleRow` and raised a generic error.
- Registering again as the same user still updates the existing row in place: same `id`, and refreshed `session_id`, keys and `updated_at`.
- Once a registration is revoked, registering the same endpoint or token is a plain insert, as before.
- Both docstrings now describe the ownership rule. To move an endpoint or token to another account, the old account must revoke it first (via `POST /api/push-subscriptions/:id/revoke`, logout or session revocation), and the new account's registration is then a new row.
- `registerPushSubscription` and the route handler are unchanged. The error passes through `withTransaction`, and the custom-route mount returns it as a 409.

**`backend/packages/data/src/__tests__/pushSubscriptions.test.ts`** — four new tests in `describe("registration and reactivation")`, covering web push and APNs:
- **Cross-user registration is rejected:** the call throws `ConflictError` with `status: 409` and the right `details.field`. A's row still deep-equals what A originally got back (`userId`, keys and `sessionId` included). B has no registrations.
- **Registration after revoke:** after A revokes, B gets a new active row with a different `id`, and A's row stays revoked.

The existing same-user re-registration test passes without changes.
