## Summary

Implemented issue #708: `provision.sh` now installs and enables an nftables ruleset that owns its own table and leaves Docker's alone.

- **`deploy/nftables.conf`**: rewritten to own exactly `table inet semprec` using the `table` + `flush table` idempotence idiom instead of `flush ruleset`. Dropped the `forward` chain (Docker owns forward policy for its bridges) and the `output` chain (it only restated the default accept). Only `input` remains, with the same loopback/established/invalid/22/80/443/ICMP rules as before.
- **`deploy/provision.sh`**: added `nftables` to the `apt-get install` list, a `readonly NFTABLES_CONFIG=/etc/nftables.conf` constant, and two new functions called from `main` after the Caddy calls — `install_nftables_config` (copies the ruleset into place) and `apply_nftables` (`nft -c -f` syntax check, then `systemctl enable`/`reload-or-restart nftables`).
- **`deploy/README.md`**: updated the `nftables.conf` bullet and added a `## Host firewall (nftables)` section after the Caddy section, both noting the ruleset is installed/enabled by `provision.sh`, owns only its own table, never flushes, and that container-to-container traffic is governed by Docker's own chains.
- **`deploy/provision.test.sh`**: added the `NFTABLES_CONFIG` `sed` redirection, an `nft` mock, and an assertion block directly after Caddy's, checking the installed file contains `table inet semprec` and no `flush ruleset` line, and that `nft -c -f`, `systemctl enable nftables`, and `systemctl reload-or-restart nftables` were recorded, plus `nftables` in the apt-get command.

Ran `bash deploy/provision.test.sh` (passes) and the full `pnpm run verify` in both `backend/` and `web/` — both green.
