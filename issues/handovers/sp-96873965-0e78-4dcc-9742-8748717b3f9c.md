# Handover: do not report a refused edge the survivor already holds in a Journal duplicate merge, and log the field of each refusal

Delivered on chain `e1-240-journal`, candidate commit `45f9bbaa6833cde77f9ffaad88c0d4b876a4169a`, landed by a `--no-ff` merge on `feature/backend-parallel`.

**What changed.** `moveRelationEdgesWithClient` (`backend/packages/data/src/chokePoint/relationOps.ts`) now reads the receiving item's edge by tuple (`normalizeRelationSides` and `relationsStore.getItemRelationByTuple`) before it asks `relationCreationRefusal`. An edge the receiving item already holds is deleted from the giving item with `deleteRelationWithClient`, counted in `moved`, and nothing is written or refused: the survivor keeps its own metadata, and a trashed other endpoint no longer makes the edge a "refused edge". Every other edge keeps the old path (refusal check, then delete plus `createRelationIfAbsentWithClient`), so a cardinality limit still fails with the insert's `CardinalityViolationError` and changes nothing. The tuple read takes no row lock; the code comment and the ADR say why the race is benign (a concurrent delete or insert leaves a state equal to some serial order). `mergeJournalDuplicates` (`journal/mergeJournalDuplicates.ts`) now puts `field` of each `refusedEdges` entry on its `info` line "Journal duplicate merge left a refused edge on the merged entry" (`field` is `callerItemId`, `targetItemId`, a property key such as `area`, or `null`); message text and `runAfterCommit` registration are unchanged. Docstrings of `moveRelationEdgesWithClient`, `RefusedRelationEdge` and `mergeJournalDuplicates` are updated.

**Contracts dependents build on.** No new export, route, operation, table, migration or job name. `RefusedRelationEdge` and the `refusedEdges` result keep their shape (`field` was already in the entry). Behaviour a caller may now rely on: `refusedEdges` never lists an edge the survivor holds, and the log line's `field` equals the `field` of the matching `refusedEdges` entry. `inbox/moveJournalDayEdges.ts` is not edited and inherits the rule through the helper.

**ADR.** `docs/adr/2026-11-15-a-journal-merge-does-not-refuse-an-edge-the-survivor-holds-and-logs-the-field-of-each-refusal.md` narrows two statements of the accepted `2026-11-10` Journal merge ADR (the refusal "for an item in the Trash", and "The line carries no field, name or content") and its "restored later" consequence. The accepted ADR is not edited.

**Files.** `backend/packages/data/src/chokePoint/relationOps.ts`, `backend/packages/data/src/journal/mergeJournalDuplicates.ts`, `backend/packages/data/src/__tests__/mergeJournalDuplicates.test.ts`, the new ADR.

**Tests.** `mergeJournalDuplicates.test.ts` gains the cases for a shared trashed item (refusedEdges empty, no log line, survivor keeps its edge, duplicate keeps none; hooks that fail on any check or create on the survivor are armed), a mix of a held and a not-held trashed item, a held live edge with other metadata (survivor's metadata kept, no check, no write), and the `field` of each log call (`targetItemId`, `area`, `callerItemId`, `null`, and per property). The worker saw 8 of those cases fail with the production change reverted. The existing cardinality test is unchanged.
