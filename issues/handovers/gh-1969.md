## What was delivered

Each element of `computed.inboxItems` of a Journal day now carries `attachments`, and the cache is recomputed and the day announced whenever an Inbox item's attachments change.

- `journalInboxCompute.ts`: every element of `computed.inboxItems` has `attachments: [{ attachmentId, blobId, name, mimeType, byteSize, pageCount, thumbnailBlobId, source }]` (`[]` for an item without attachments), read with one `listInboxAttachments` call per day, in position order. `byteSize` is a number, `pageCount` is read from `metadata.pages`, `thumbnailBlobId` is the derived preview blob (null until the metadata job made one) and is never the original blob.
- `inboxAttachmentsStore.ts`: `insertInboxAttachments` (when rows were added), `deleteInboxAttachment` (when the row existed, which covers the move into Files on confirm) and `recordInboxAttachmentMetadata` (when it recorded) enqueue the day's recompute through `enqueueJournalInboxRecomputeForInboxItem` in the caller's transaction, after the source row lock. Failure and no-op paths enqueue nothing. `InboxAttachmentRow` gained `name`, derived from the blob storage key (`filenameFromStorageKey`).

## Entry points and contracts dependents build on

- Shape of an element of the cached `computed.inboxItems[].attachments` (`JournalInboxAttachmentSummary`), as above. A cached day row computed before this change lacks the key until its next recompute.
- `InboxAttachmentRow.name: string | null`: the file name an upload recorded in the blob storage key, `null` for a blob stored without one. Only a Files upload (`ingestUploadedFile`) writes a key with a file name. A blob made by `POST /api/blobs` (`ingestUploadedBlob`), which is what a capture attaches, has a bare uuid key, so the name of every attachment captured that way is `null` today.
- Recompute triggers: job enqueued in the same transaction as the attachment write (existing pattern of #1390 and #1718; lock order Inbox item, then the day's job key).
- After the merge of gh-1970 the same row reader also carries `extraction` (see gh-1970).

## Deviations from the specification and spec seams

1. The Task says each attachment has a name, but no store holds one: capture accepts only `{blobId, source}`. `name` is derived from the blob storage key and is null for every blob made by `POST /api/blobs`. A real attachment name needs a column and a capture change, which is outside this Task.
2. `pageCount` is read from `metadata.pages`, and gh-1965 always records `pages: null` (PDFs get no page count by product decision), so `pageCount` is null for every attachment; the key is present for a PDF.
3. The thumbnail is about 128 px in gh-1965 (the Task says about 34 px); the summary only carries the blob id.
4. `deleteInboxAttachmentsForItem` (permanent delete or purge of the item) does not enqueue: the item is in the Trash, which the day does not list, or is purged with its day edges.
5. A recompute is also enqueued for an attachment change on an item in the Trash; it rewrites the same list (harmless, not guarded).
6. Existing test adapted: `inboxTickProposal.test.ts` "serializes insert/remove attachment with tick in both acquisition orders". Adding or removing an attachment now takes the recompute job key like a type edge write, so a tick that starts after the writer waits and then proposes on the committed state; the writer-first expectations equal those of the "change type" case. The tick-first order still covers the serialization.
7. Import cycle `inboxAttachmentsStore` <-> `journalInboxCompute` (each uses the other only inside functions; `check:boundaries` passes).
8. The tick fingerprint follow-up from the gh-1965 handover (`inbox/inboxSourceFingerprint.ts` does not cover attachment metadata) is not addressed.
9. The commit trailers name Claude Sonnet 5.5 (the session attribution), not the model the Task named.
