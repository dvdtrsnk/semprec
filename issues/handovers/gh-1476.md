# gh-1476 implementation handover

Implementation base: `6a87f7ce06d21248f9f8fdebd08c287f16dce017`.
Blocked by gh-1426 (relations on the envelope and their validation).

## What changed

- `confirmProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) now calls a new
  private `writeEnvelopeRelations` for a `database` envelope, after the item, its credential and the
  transcript-card edge. For every key of `envelope.relations`, in envelope order, it resolves the
  relation property of the target database (`requireRelationPropertyId`) and calls
  `createRelationWithClient` per target id with the new item as caller and the confirming-user writer.
- Everything runs in the caller's confirm transaction: any failing edge aborts the item and the earlier
  edges, and the card stays `proposed`.
- A `ChokePointError` from an edge write is rethrown with the same `status`, `code` and `message` and
  `details` extended with `field: <relation key>` (the subclass is not preserved, only the fields the
  HTTP layer reads). Non-canonical errors pass through untouched.
- Empty or absent `relations` writes nothing. The early return for an already `confirmed` proposal is
  unchanged, so a repeated confirm writes no edge.

## Notes for dependants

- The card's pre-checks from gh-1426 run first inside confirm (`assertValidEnvelopeForCard`), so a
  missing target usually fails there with its own `field`; the write is the authoritative check and
  catches cardinality conflicts only the database trigger sees.
- No schema, migration, public export or tenant-table count changed.
