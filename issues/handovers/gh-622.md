The gateway now allows at most two `/internal/diarize` or `/internal/transcribe` requests at a time and answers any request over that limit with a 503. `pnpm run verify` in `backend/` passes: lint, format, build, and unit, integration and e2e tests. I did not run it in `web/` because this change doesn't touch the frontend. Everything is committed on this branch.

## What changed

- **`audioConcurrencyLimit.ts`** (new): the limit is a simple counter inside the process, set by `MAX_CONCURRENT_AUDIO_REQUESTS = 2`. `createAudioConcurrencyLimit(max)` gives back a release function while fewer than `max` requests are running, and `null` once the limit is reached. Calling a release function a second time does nothing.
- **`app.ts`**: `createDispatcher` creates one limit, with no new parameter and no environment variable.
  - **Over the limit:** the gateway answers `503` with `Retry-After: 1` and `{ "error": "Audio capacity exhausted", "code": "audio_capacity_exhausted" }`, before the audio handler runs. It does not read the request body, call a provider or reserve budget.
  - **Under the limit:** the slot is freed on `res.on("close")`, which fires both when the response finishes and when the client drops the connection.
  - **`/internal/complete`:** never counts toward the limit.

## Tests

- **`audioConcurrencyLimit.unit.test.ts`**: requests up to `max` are admitted and the next gets `null`, releasing frees a slot, and a second release call does nothing.
- **`audioConcurrencyLimit.test.ts`** (integration tier, runs `createDispatcher` against the test Postgres):
  - **Over the limit:** a fake diarization provider holds two requests open. While they are running, a third `/internal/diarize` and a `/internal/transcribe` each get the 503 with its body, `Retry-After` and `Content-Type`. Neither reaches a provider, and no rows are added to `ai_gateway_calls`. When the held requests are let through, both return 200, and a fourth request afterwards also returns 200.
  - **Rejected requests:** after three requests rejected with 400 or 401, a valid request is still admitted.
  - **Dropped connection:** when a client drops an in-flight request, its slot is freed and the next audio request gets through. The issue's test list didn't ask for this one, but the acceptance criteria require the behaviour, so I added it.
  - **Completions:** with both audio slots taken, `/internal/complete` still reaches its provider.

I left alone everything the issue marks out of scope: `audioHandler.ts`, `completeHandler.ts`, `serve.ts`, `startupConfig.ts`, making the limit configurable through an environment variable, and the transcribe service's gateway client.
