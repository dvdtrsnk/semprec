## What was delivered

- The system-owned `invitations` database of the calendar module: `INVITATIONS_MODULE_ID = "invitations"` (`seed/invitationsKeys.ts`) and `seedInvitationsDatabaseInTransaction(client, calendarsDatabase)` (`seed/seedInvitationsDatabase.ts`). It creates 13 system-owned properties (`title`, `startsAt`, `endsAt`, `timeZone`, `allDay`, `place`, `organizerName`, `organizerEmail`, `status` with options `pending`, `accepted`, `tentative`, `declined`, `acknowledged`, `cancelled`, `respondedAt`, `uid`, `sequence`, `kind` with options `invite`, `sharedCalendarNotice`) and four one-directional `many_to_many` system-owned relations (`suggestedCalendar` to Calendars, `event` to Events, `sourceEmail` to Emails, `mailbox` to Mailboxes). Owner process of every property and relation is the calendar module; the database is owned by the Calendars project item, its schema is locked, and no rows are created. The locked target schemas gain no property because the relations have no inverse.
- `seedSystem` calls the seed after the Calendars seed (and after the email seed). `runInvitationsDatabaseCutoverMigration` (`calendar/invitationsDatabaseCutoverMigration.ts`) gives an existing tenant the same database in one transaction under the tenant seed lock; it is a no-op for a tenant that has the database or has no Calendars database, and it rolls back (throws) when Events, Emails or Mailboxes or the Calendars owner project item is missing. It is registered in `runTenantCutoverMigrations` after the gh-2034 entry, before the area-note cutover.
- The calendar module manifest declares the database (name "Invitations", after `calendars`); `calendar/i18n` cs and en carry `database.invitations.name`, `property.invitations.<key>.name` and the status and kind option labels.

## Entry points and contracts dependents build on

- Database module id `invitations`; property keys and option values as above. Rows are writable only by the calendar module owner process: a generic write of `status`, `title` or `startsAt` by a user is refused at the choke point with 403 and code `owner_violation`.
- `seedInvitationsDatabaseInTransaction(client, calendarsRow)` takes the Calendars `DatabaseRow` and looks Events, Emails and Mailboxes up by module id; it throws when one is missing.
- Producer and answering code (later issues of the calendar-invites series) writes rows as the calendar module's system writer; nothing in this source creates a row.
