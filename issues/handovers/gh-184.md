Closes #184

A transcript card can now be confirmed to create a new Event, or revised to link an existing one, and either way the Transcription↔Event edge is written in the same transaction. Backend `pnpm run verify` exited 0: 489 unit, 1605 integration and 9 e2e tests passed. Nothing under `web/` changed, so I didn't run the web verify.

**Envelope** (`inbox/inboxTickAction.ts`)
- `ProposalEntityKind` gains `'relation'`. The shape is `{ entityKind: 'relation', target: <existing item id>, properties: { propertyKey } }`, and it maps directly onto `PUT /api/items/:id/relations/:propertyKey/:targetItemId`. The item the relation is written from is the card's source, so it is not stored in the envelope.
- `assertValidProposalEnvelope` checks this shape: `target` must be an id and `properties` must be exactly `{ propertyKey }`.
- The Inbox tick can still only produce `'database'` or `'pageContent'`. A `'relation'` proposal only ever comes from a human `revise`.

**Confirm and revise** (`inbox/proposalActions.ts`)
- Confirm and revise both check the new envelope against the card it belongs to:
  - `'relation'` is only accepted on a `kind = 'transcript'` card.
  - A transcript card takes exactly two shapes: `'database'` targeting Events (create a new Event), or `'relation'` through the transcript's `event` property (link an existing one). Anything else is `validation_failed`.
  - A link-existing envelope is checked against the relation's integrity and ownership rules when it is revised, with the canonical #82 codes: `validation_failed` for a target in the wrong database, `database_archived`, and `owner_violation`. Confirm checks it all again, because it goes through the normal relation write.
- `confirm` gets a third branch for `'relation'`. It uses the existing generic relation write (`createRelationWithClient`), not a new write path. The result is the linked Event and its title.
- For a transcript card's create-Event shape, `confirm` writes the edge from the source transcript to the new Event right after creating it.
- Everything runs in the caller's one transaction. If the edge write fails (for example `cardinality_violation` because the transcript or Event is already linked elsewhere), there is no Event, no edge, and the card stays `proposed`.
- `revise` still replaces the whole envelope, so one call can flip a card between the two shapes. Existing locking still applies: a confirmed or rejected card can't be revised, and confirming again returns the already-confirmed card.

**Choke point** (`chokePoint/chokePoint.ts`)
- I moved the four checks `createRelationWithClient` runs before writing into one helper. The new `assertRelationCreatableWithClient` runs those same checks without writing, so revise raises the same errors confirm would. Cardinality is not part of it; it is still enforced by the write at confirm time.

**Tests** (`transcription/__tests__/transcriptProposalActions.test.ts`, integration tier; the cards come from the real match step)
- Confirming either shape writes the Event (or not) and exactly one edge; a failing edge write leaves nothing behind for both shapes.
- Confirm retried on each shape creates no second Event or edge.
- Flipping create → link → create and link → create → link, then confirming, gives exactly one edge.
- Revise rejects a wrong-database target, an archived database, an unauthorized relation, a property other than `event`, extra properties, a non-Events create target, `pageContent`, and `'relation'` on an `inbox` card.
- Confirm re-checks a stored envelope (a database archived after the revise is rejected), and a confirmed card can't be revised.

I didn't add an ADR: this extends the confirm/revise path that `2026-09-23-processing-proposals-card-creation-owned-per-kind` already assigns to this issue. I also updated the seed comment that describes the envelope.
