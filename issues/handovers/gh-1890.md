## What was delivered

A read-time derivation of whether an assistant reply left a failed tool call, and its use in the message list and in the run detail. No column, migration or write was added.

- `deriveReplyOutcome(steps)` (new `packages/data/src/agentRuns/replyOutcome.ts`) is pure. A step is failed when its status is `error` or it carries an error code; a failure is cancelled by a later `ok` step of the same operation, MCP tool registration or legacy tool name. The reason comes from the last uncancelled failed step: `toolTimeout`, `toolUnavailable` or `toolError` (`REPLY_INCOMPLETE_REASONS`). An incomplete outcome carries `mcpServerItemId`, `connectorName` and `timeoutMs` when known. `replyOutcomeOfStoredSteps(steps)` applies it to a stored column value through the checked reader.
- The step projector (`semp/sempReplySteps.ts`) stores `mcpToolRegistrationId` on MCP steps and `mcpServerItemId`, `connectorName` and `timeoutMs` on failed MCP steps (additive optional fields; old stored steps lack them and fall back to matching on tool name). The shared tool event parser (`shared/toolEventPayload.ts`) reads `timeoutMs` from the result details.
- The single reader of `semp_messages.steps` is `parseStoredSempReplySteps` of gh-1887; it also parses the MCP fields. `listSempThreadMessages` parses each row once and derives the outcome from the parsed steps (`sempThreadsStore.ts`).
- `GET /api/semp/threads/:id/messages`: every `SempThreadMessage` carries `outcome: "complete" | "incomplete"`; only an incomplete reply carries `incompleteReason`, `mcpServerItemId` and `timeoutMs`. A NULL column is complete. A malformed column fails the page read with the gh-1887 text `Malformed semp_messages.steps in database row`.
- `getAgentRunReplyOutcome(client, runId)` (in `agentRunDetail.ts`) returns the outcome of the single assistant reply of the run in its thread; it is null for an MCP-triggered run, a run without a thread, and a run with no reply or several replies (a chat session is not reclassified).
- `deriveRunDisplayStatus` takes an optional `replyOutcome` and reclassifies only a finished run (done, nothing pending) as `error`; running, waiting approval and error keep their status. `agentRunErrorFields` takes the incomplete reply and returns the `agentRun.incomplete.*` summary (cs and en catalogs, seconds from `timeoutMs`; the unnamed variants `toolUnavailable.unnamed` and `toolError.unnamed` are used when no connector name is known). `agentRunHandler.ts` reads the reply once and passes it to both.

## Deviations and spec seams

1. Spec seam: gh-1860 added no reply read model with step fields to the messages endpoint; the message read model is `listSempThreadMessages` / `SempThreadMessage`, which selects `m.steps` in its single query (gh-1887 later made the checked reader the one parser).
2. The stored step of gh-1860 carried no MCP registration, server id, connector name or timeout, so the projector and `ToolResultDetails` were extended additively.
3. There is no run-keyed reply list, so `getAgentRunReplyOutcome` runs its own single statement on `semp_messages` (thread and run) and shares the derivation with the list. A run with several replies is not reclassified.
4. For a generic operation failure the connector name falls back to the tool name, then the operation, so the summary text is never empty; it is not served on the message read.
5. `fill()` moved from `agentStepCatalog.ts` to `catalogFill.ts` to avoid an import cycle; `agentRunErrorFields` and `getAgentRunDetail` gained optional trailing parameters.
6. After the merge with gh-1887 two parsers disagreed on `semp_messages.steps`; the fix (`34d1c9ba2`) dropped the second parser, so gh-1887 `parseStoredSempReplySteps` is the only reader. That fix was the extra round of the controller decision of 2026-11-13.
