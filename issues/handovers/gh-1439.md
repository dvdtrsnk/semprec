# gh-1439 — return processing method and target from GET /api/inbox-types

Repository-Issue: gh-1439

## Delivered behavior

- `backend/packages/data/src/inbox/inboxTypesStore.ts`: `InboxTypeSummary` gains `processingMethod` and `targetDatabaseKey`, read from the stored `processingMethod` and `targetDatabase` properties. A missing value is `null`. `listActiveInboxTypes` returns both for every active type.
- `backend/packages/data/src/inbox/inboxRouteHandlers.ts`: `createInboxTypesRouteHandler` takes the request context. Each entry of `types` carries `processingMethod`, `targetDatabaseKey` and `targetLabel`. `targetLabel` is the target database's display name in the caller's `users.locale`, or `null` when the type has no target. Each distinct target is resolved once per response.
- Label order: the name the target database was given (`databases.name`), then its catalog label (`database.<key>.name` of the owning module, through `createCatalogResolver` and `resolveDatabaseName`), then the key itself.
- `id`, `emoji`, `label`, the response status and the `{ types }` body are unchanged. Archived types are still not listed.
- No migration, no schema change, no new error code, no write.

## Behavior notes

- The custom-route factory receives only the pool and the dependency container, so the handler cannot take the composition root's `ModuleRegistry`. It builds one with `loadFullModuleRegistry()` on first use and caches the catalog resolver for the process, the way `transcriptionRouteHandlers.ts` caches its catalogs. A failed load is not cached, so the next request retries.
- `processingMethod` is the stored value, not narrowed to `ProcessingMethod`. Writes have been validated since #1436. A value the database already holds passes through as stored, and its target label is still resolved from the key.
- A stored target that the catalog does not know returns the key as its label, and the list still answers 200.
- A user-renamed target database shows the new name in both locales. This is the same name `GET /api/databases` returns for that database.

## Notes for dependants

- The response change is additive. `web/` and `mobile/` do not read `GET /api/inbox-types` today.
- `listActiveInboxTypes` returns the stored values only. A caller that needs a target's name resolves it through the catalog resolver, as the route does.
- A new target database (#1973 `mcpServers`, for example) needs a `database.<key>.name` entry in its owning module's catalog, in `en` and `cs`. Without it the label is the key.
- A custom route that needs the full registry follows the lazy pattern here, or the registry is threaded through `CustomRouteDependencies`. That second option touches `serve.ts` and `customRouteMount.ts`, which are outside #1439's Touches.
