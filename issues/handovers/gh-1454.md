## Delivered behavior

- **Migration `0125_mail_provider_account_address.sql`**: nullable `provider_account_address text` on `mail_account_sync_state`; partial unique index `mail_account_sync_state_tenant_provider_address_uq` on `(tenant_id, provider_account_address) WHERE provider_account_address IS NOT NULL`; backfill from `gmail_watch_email_address` for `gmail_api` rows, normalized with `lower(btrim(...))`. The router grants and `route_gmail_address` are unchanged.
- **Store** (`mail/mailAccountSyncStateStore.ts`): `recordProviderAccountAddress(client, itemId, address)` normalizes the address, writes it with `requireAffectedRows`, and maps the unique violation to `ProviderAccountAlreadyConnectedError` (409, `provider_account_already_connected`). `getProviderAccountAddress` reads it. An empty address is a `validation_failed`.
- **Seed** (`seed/seedEmailModule.ts`): `Mailboxes.addresses` is `owner: "system"` for fresh tenants.
- **Cutover** (`mail/mailboxAddressesOwnerCutoverMigration.ts`, registered in `db/tenantCutoverMigrations.ts` after the processing-proposals step): flips an existing `addresses` property to `owner = 'system'` under `LOCK TABLE properties IN EXCLUSIVE MODE`. A second run changes nothing. A tenant without a Mailboxes database is skipped. A Mailboxes database without an `addresses` property throws, so the tenant is reported.
- **System writer** (`mail/mailboxAddresses.ts`): `writeMailboxAddresses(client, { mailboxesDatabaseId, mailboxItemId, address, aliases? })` normalizes the primary address, appends the normalized aliases, drops duplicates and empty entries, and writes through `updateItemWithClient` with `allowedSystemKeys: ["addresses"]`. No route is added.
- **Refusal code** (`chokePoint/itemWrites.ts`): a caller that writes a `system`-owned item field without `allowedSystemKeys` now gets `403 owner_violation` instead of `403 forbidden`. This is the same code as the relation refusal in `relationEdgeContext.ts`.

## Deviations and conflicts

1. **Acceptance criterion vs. partial unique index on existing data.** The criterion "every existing `gmail_api` row with a watch address has the same value in `provider_account_address`" cannot hold when two `gmail_api` rows of one tenant watch the same Google account. The Task's unique index forbids that value on both rows, and `gmail_watch_email_address` is not unique, so such rows can exist. The backfill keeps the address on the lowest `item_id` of each `(tenant, address)` group and leaves the others null, so the migration does not fail. Null blocks nothing. The reviewer must decide whether this is acceptable.
2. **Backfill inside the structural migration.** The Task places the backfill in the migration file. `db-migrations` prefers backfills in separate, batched data jobs. The Task is followed as written. The backfill touches at most one row per Gmail mailbox.
3. **Refusal code changed for every system-owned item field.** The Acceptance criterion requires `owner_violation`. The change sits in the shared `assertWritableProperties` path, so it applies to every `owner: 'system'` item field, not only `addresses`. No existing test pins `forbidden` for that path (checked by grep).
4. **Three existing fixtures** (`mailSend.test.ts`, `mailDraftsStore.test.ts`, `mailMessagePreview.test.ts`) created Mailboxes items with `addresses` through the generic create. They now call `writeMailboxAddresses`. Only the fixture set-up changed.
5. **No manifest change.** `mailModuleManifest.ts` and `systemDatabasesModuleManifest.ts` declare no cutovers, so no data-migration entry was added.

## Tests

`backend/packages/data/src/__tests__/mailProviderAccountAddress.test.ts`, with the runtime `semprec_data` pool for every production write and isolation check:

- Seed: `addresses` is `system` in a fresh tenant.
- A generic `updateItem` and a generic `createItem` that include `addresses` are refused with `owner_violation`, and no row changes.
- System writer: the stored value is normalized, aliases are appended and duplicates dropped; an empty address is rejected.
- Recorder: two mailboxes of one tenant with one address (in different letter case) conflict, and the second keeps null. The same address in two tenants is allowed. A null address blocks nothing. Re-recording the mailbox's own address is accepted. An empty address is rejected.
- Migration 0125 backfill: re-applied inside a transaction that first drops the column and index, then rolls back. `gmail_api` rows get the normalized watch address; `imap` and `gmail_api` rows without a watch address stay null; two watch addresses that normalize to one value keep the lowest item id.
- Cutover: flips the property in every tenant, a second run changes no property row, and a tenant without Mailboxes is skipped.

## Notes for dependants

- **#1686 and #1736 (connect flows)**: write the address with `writeMailboxAddresses` and record it with `recordProviderAccountAddress` in the same transaction. A duplicate raises `ProviderAccountAlreadyConnectedError`. Postgres aborts that transaction, so roll it back and map the error to "already connected".
- **Aliases**: `writeMailboxAddresses` replaces the whole list. Pass every alias the flow keeps, or it is dropped.
- **#1739 (Gmail watch)**: routing stays on `gmail_watch_email_address`. A watch registration does not write `provider_account_address`.
- **Generic writers**: any code that patches `Mailboxes.addresses` through the generic path or an agent `item.patch` now gets `owner_violation`. No write path for addresses was found in `web/src`.
- The new column is not in any `ON CONFLICT` target, so no existing insert changes behavior.
