# Handover: sync Google calendars

Implementation commit `2aefc7007` on `feat/ia-google` (from `feat/internet-accounts`).

**What changed.**
- New `backend/packages/data/src/calendar/sync/adapters/google/`:
  - `googleCalendarHttp.ts`: requests to `https://www.googleapis.com/calendar/v3`, with these rules:
    - A bearer token on each request.
    - A 30 s deadline per request, combined with the pass's signal through `AbortSignal.any`.
    - `redirect: "error"`.
    - Response bodies are capped at 16 MiB and error bodies at 16 KiB. Error bodies are read only for their `reason` codes, never their messages.
    - Defines `GoogleCalendarEventConflictError` (HTTP 412).
  - `googleCalendarMapping.ts`: zod schemas of the Google resources, the event → `RemoteEvent` mapping and the fields → event body mapping.
  - `googleCalendarAdapter.ts`: contains these parts:
    - `GoogleCalendarAdapter`.
    - The runtime binding `setGoogleCalendarSyncRuntime({ pool, clientId, clientSecret, fetchImpl? } | null)`.
    - The registry factory `createGoogleCalendarSyncAdapter`.
- `calendar/sync/adapters/index.ts`: `gmail_api: createGoogleCalendarSyncAdapter` (the only registry edit).
- `setGoogleCalendarSyncRuntime` and `GoogleCalendarSyncRuntime` are exported from `@semprec/data`. `publicSurface.test.ts` was updated for this.
- `services/semprec-api/src/queueRuntime.ts` sets the binding before the runner starts, from the Gmail OAuth client (`GMAIL_OAUTH_CLIENT_ID`/`_SECRET`, `null` without it). It clears the binding on a start failure and in `stop()`. The comment in `worker.ts` at the calendar task was updated.

**Behaviour.**
- **`listCalendars`** reads `users/me/calendarList`, 250 per page, with more than 200 calendars refused as `invalidResponse`.
  - `name` is `summaryOverride ?? summary`.
  - `color` is `backgroundColor` uppercased, or null when it is not `#RRGGBB`.
  - `readOnly` is set for `accessRole` `reader` and `freeBusyReader`.
  - `ctag` is the entry's etag, and `url` is null.
- **`fetchChanges`** calls `events.list` with `singleEvents=false`, `showDeleted=true`, `maxResults=250` and `maxAttendees=500`. Reading stops with `invalidResponse` past 25,000 events.
  - With a stored sync token, the fetch is incremental.
  - Without one, or when the token request answers 410, the calendar is listed in full with `full: true`. Only that calendar starts over.
  - A full listing is bounded by `timeMin = window.start − 1 day` and `timeMax = window.end + 2 days`, as UTC midnights. The window is in the tenant zone, which the adapter does not know.
  - `nextSyncState` is `{ syncToken: nextSyncToken ?? null, ctag: calendar.ctag }`.
- **Series** (`singleEvents=false`):
  - A changed instance (`recurringEventId` + `originalStartTime`) becomes an override with `seriesRemoteId` = the master id. Its `recurrenceId` is the original start as a local start in the master's zone (`YYYY-MM-DDTHH:MM`, or the day for an all-day series).
  - A cancelled instance becomes an exception date of its master, in addition to the master's `EXDATE` lines (`TZID=`, `Z` and `VALUE=DATE` forms are all converted to the series' zone). Cancelled instances count only when they fall inside the window bounds, so full and incremental fetches agree.
  - In an incremental fetch, every series touched by the batch is read again: its master, or `events.get` when the master is not listed, and its cancelled instances (`events/{id}/instances?showDeleted=true`, window-bounded, at most 10,000). The master is then re-emitted with the complete exception list. A cancelled event's id always goes to `deletions`, which covers a stored override that was later cancelled.
  - A cancelled single event or master is a deletion. In a full fetch it is simply not listed.
- **Times:**
  - All-day: `date`, with the exclusive `end.date` minus one day as `endDate` when that day is after `date`. `timeZone` is null.
  - Timed: read in `start.timeZone`, or the calendar's `timeZone` from the listing when the event has none.
    - An end on the next midnight is `24:00`.
    - An end on a later day sets `endDate`.
    - An end that is not after the start leaves `timeTo` empty; the Events transform then sets one hour.
- **`alertMinutes`:** with `reminders.useDefault` (or no `reminders`), the first `popup` of the listing's `defaultReminders`, which are the calendar's defaults for the signed-in user. Otherwise the first `popup` override. With no popup it is null.
- **Other fields:**
  - `url` is `source.url`.
  - `organizer` is `{ email, name: displayName, role: null, status: null }`.
  - `attendees` have `role` `resource` | `optional` | `required` and `status` = `responseStatus`.
- **`putEvent`:**
  - With `ref` null, it calls `events.insert`, passing `iCalUID` when the input carries `icalUid` (see the deviations).
  - Otherwise it calls `events.patch` with `If-Match: ref.etag`.
  - Both send `sendUpdates=none`.
  - Every mapped field is sent; an empty one is sent as `null` or `[]`.
  - Reminders are written as `{ useDefault: false, overrides: [popup alertMinutes] }`.
  - An override is sent without `recurrence`. An override with no `ref` throws.
  - A timed Event without its own zone is written in the Google calendar's zone, read with `GET calendars/{id}`.
  - It returns `{ remoteId: id, href: null, etag }`.
- **`deleteEvent`:** `DELETE` with `If-Match` and `sendUpdates=none`. A 404 or 410 counts as deleted.
- **Tokens:**
  - The first request of a pass calls `refreshAndPersistAccessToken`, which takes the credential row lock and logs purpose `google_calendar_sync`.
  - The access token is kept in memory for the adapter's lifetime, which is one pass. It is never persisted.
  - The credential the engine decrypts is ignored, as the mail adapters ignore theirs.
  - On a 401, the adapter refreshes once and repeats the request. A second 401 is `CalendarSyncReauthorizationRequiredError`.
  - A refused refresh is `MailReauthorizationRequiredError`, which the engine maps to `needsReauthorization`.
- **Errors:**
  - 403 with reason `insufficientPermissions` or `ACCESS_TOKEN_SCOPE_INSUFFICIENT`, or `WWW-Authenticate: … insufficient_scope`: `CalendarSyncConsentRequiredError` → `needsConsent`.
  - 429, or 403 with a rate or quota reason: `rateLimited`.
  - 5xx: `providerUnavailable`.
  - A transport failure: `providerUnavailable`, or `timeout` once the pass signal has fired.
  - A bad shape, bad JSON or an oversized body: `invalidResponse`.
  - 412: `GoogleCalendarEventConflictError`.
  - Any other 4xx: a plain `Error` naming the status, recorded as `unexpected`.
- **Logs** carry `accountItemId`, fixed tags and property names only. They never carry calendar ids (Google's are addresses), provider text or tokens. The tags are:
  - `googleUnsupportedRecurrenceLine`, with `property`: RDATE, EXRULE or a second RRULE.
  - `unreadableTimes`.
  - `unreadableExceptionDate`.
  - `unreadableOverride`.

**Tests.** New `__tests__/googleCalendarAdapter.test.ts` has 16 integration tests on the runtime-role pool with two tenants. They go through the production registry, `handleCalendarAccountSyncTask` with no `adapters` option, using an injected fetch over the fixture JSON in `__tests__/fixtures/googleCalendar/`. They cover:
- **First pass:**
  - Two calendars: owner and reader, with colours and the summary override.
  - A two-page listing.
  - An all-day multi-day event: 2026-12-07..10 exclusive → `endDate` 2026-12-09.
  - A New York weekly series listed in +01:00 → 09:00–09:30 `America/New_York`, with EXDATE plus a cancelled instance as exception dates, the default popup reminder as the alert, and RDATE logged with its fixed tag.
  - The override's `seriesId`, `recurrenceId` and popup override.
  - An event ending at midnight → `24:00` in the calendar zone, with `source.url` as its `url`.
  - Attendees and organizer in `base_snapshot`.
  - Sync tokens stored, query parameters asserted, one token refresh, and the stored credential is still the refresh token.
- **Reader calendar:** a user rename of its Event gets 403 `calendar_read_only`, while a rename in the owned calendar succeeds.
- **410:** the primary calendar is listed again in full, and the dropped event is trashed. The reader calendar stays incremental: one request, and its Event row's `xmin` is unchanged. Both tokens are updated.
- **Incremental cancellation:** one cancelled instance → master `events.get` + instances → the master's exception dates gain the date, and the override stays.
- **Failure table** on the calendar list (scope body, scope challenge header, 403 rate limit, 503): `needsConsent`/`consentRequired` or `error`/`rateLimited`|`providerUnavailable`, with nothing written.
- **401:** one 401 is retried after a second refresh; two 401s give `needsReauthorization`. A refused refresh token gives `needsReauthorization` with no Calendar API request.
- **Writes:**
  - An insert carries `iCalUID`, `sendUpdates=none` and the full body: zoned times, RRULE + `EXDATE;TZID=`, the popup reminder.
  - An all-day insert has an exclusive end and an empty recurrence.
  - A patch with `If-Match`; a stale etag → conflict error.
  - An override patch has no `recurrence`.
  - A delete with `If-Match`, where 410 counts as done and 412 is a conflict.
  - An adapter running in the other tenant cannot read the credential and makes no request.
- **Mutations:** removing the 410 handling failed the 410 test; emptying the consent reasons failed the scope-body case.
- The fixtures are hand-written in the documented Google Calendar v3 response shapes. They were not captured from a live account.

**Deviations and spec seams.**
- **Update uses `events.patch`, not `events.update`.** `update` replaces the whole event and would drop everything the Events model does not carry: conference data, attachments, extended properties, attendee details beyond the cap, colour.
- **The adapter interface has no UID and no conflict signal.**
  - `putEvent` accepts `GooglePutRemoteEventInput = PutRemoteEventInput & { icalUid?: string | null }`. A caller through the plain `CalendarSyncAdapter` type cannot pass the UID yet.
  - The 412 error is `GoogleCalendarEventConflictError`, which is local to this adapter.
  - The CalDAV adapter needs both too. When the branches merge, one shared `icalUid` on `PutRemoteEventInput` and one shared conflict class in `adapter.ts` should replace these.
- **RDATE cannot be kept "raw in the snapshot".** The engine validates adapter output with strict zod and stores `base_snapshot` = `{ fields, seriesRemoteId, organizer, attendees }`, so there is no place for it. RDATE/EXRULE lines are dropped and logged with the fixed tag `googleUnsupportedRecurrenceLine`. The series syncs with its RRULE and EXDATEs. Keeping the raw lines needs an engine payload field.
- **`alertMinutes` defaults** come from the `defaultReminders` of the `events.list` response, which are the same per-user calendar defaults that `calendarList` returns. This keeps `fetchChanges` independent of an earlier `listCalendars` on the same instance.
- **Production wiring is a runtime binding.** The registry factory has no pool or OAuth client, and the registry is a module constant, so the API queue runtime calls `setGoogleCalendarSyncRuntime`, the same pattern as `setEventInvitationDelivery`. Without the Gmail OAuth client, a Google pass fails as `error`/`unexpected` with "no OAuth client configured".
- **The write mapping overwrites some Google settings.** An Event with no alert is written with `useDefault: false` and no overrides, which removes Google email reminders. `url` is written as `source` with `{ title: name ?? url, url }`.

**Open items (verifiable only against real Google).**
- Whether `events.list` with `timeMin`/`timeMax` and no sync token returns a `nextSyncToken`, and whether later incremental results then cover the whole calendar. Without a token the adapter stores `null` and lists in full on every pass, which is correct but costs more.
- Whether a `timeMin`/`timeMax` listing with `singleEvents=false` includes every series that has an occurrence in the window, and its cancelled instances.
- Whether `freeBusyReader` calendars can call `events.list`. If Google answers 403 there, the whole pass fails as `unexpected` until that calendar is excluded or handled.
- Whether `events.patch` clears fields sent as JSON `null`: `location`, `description`, `source`.
- Whether `events.insert` with a client-chosen `iCalUID` behaves like an import for an existing UID (409?). A 409 is currently a plain error.
- The real wording of reasons on 403 refusals: scope, rate limit, API not enabled for the project. A disabled API (`accessNotConfigured`) is recorded as `unexpected`.
- Push channels and notifications are not built; they are out of scope.
