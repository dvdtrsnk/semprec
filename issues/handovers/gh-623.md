## Summary

A settle UPDATE that fails no longer throws away a provider result that has already been paid for. When `ai_gateway_calls` can't be settled after a successful provider call, the gateway now retries with backoff. If it still fails, the gateway logs the row and returns the result to the caller. So a settle failure can no longer turn into a 500 from `/internal/complete` or the audio routes.

Closes #623.

## Changes

**`backend/packages/ai-gateway/src/gateway.ts`**
- Adds the module constants `SETTLE_MAX_ATTEMPTS = 3` and `SETTLE_BACKOFF_MS = [100, 300]`.
- Adds a private `settleWithRetry(row, settle, ctx)`, used by both `withTokenAccounting` and `withAudioAccounting`:
  - If the settle rejects and attempts remain, it logs a warning (`"ai_gateway_calls settle failed, retrying"`, with `err`, `callId`, `attempt`, `provider`, `model`), waits the backoff and tries again.
  - After the last failure it logs an error (`"ai_gateway_calls settle failed; row left reserved at its estimate"`, with `callId`, `attempts`, `provider`, `model`, `estimatedCostUsd`) and returns normally. The row stays `reserved` at its estimate, so it keeps counting against the budget cap.
  - A `null` settle means no `reserved` row matched, because another writer already settled or failed it. That case is not retried: it logs one error line with `callId` and returns.
- The failure path of `failGatewayCall` from E1 is unchanged.
- **One deviation from the spec:** the issue's signature included a `pool` parameter. I left it out because the `settle` closure already captures the pool, and `noUnusedParameters` would reject an unused one.

**`backend/packages/data/src/aiGateway/aiGatewayCallsStore.ts`**
- `settleTokenGatewayCall` and `settleAudioGatewayCall` now return `AiGatewayCallRow | null`. They return `null` when the UPDATE matched no `reserved` row (checked via `rowCount`) instead of throwing through `requireAffectedRows`. The caller still acts on the zero-row case by logging it.

## Tests

**`gateway.test.ts`**
- The old "propagates a settle failure" test is replaced by a `settle retry` block. It intercepts `pool.query` for the settle UPDATE and passes every other query through to the real pool.
- The block covers four cases:
  - **Two failures, then success:** the result is returned, the row ends `settled` with the real usage, there are exactly two warnings (attempts 1 and 2) and no error.
  - **Three failures (token path):** the result is returned, the row stays `reserved` with `cost_usd` equal to the estimate, and there is one error line carrying `callId`, `attempts: 3` and `estimatedCostUsd`.
  - **Three failures (audio path, `transcribe`):** the result is returned, the row stays `reserved` at the estimate, and there is one error line with `callId`.
  - **Concurrent writer:** `failGatewayCall` runs inside the first intercepted settle. There is exactly one settle attempt, no warning, one error line with `callId`, the result is returned and the row stays `failed`.

**`aiGatewayCallsStore.test.ts`**
- Settling an already-settled token row now resolves to `null` and leaves the row untouched.
- A new test checks that settling an already-failed audio row resolves to `null` and leaves the row untouched.
