# Handover: refresh the app live from the sync socket

Implementation commit `286d84cd9` on `feat/internet-accounts`.

**What changed.**
- `:shared:data`: `ApiClient.openSocket` opens a WebSocket (Ktor `WebSockets` plugin installed on the one client; OkHttp on Android/JVM, Darwin on Apple, no new engine). The handshake is bounded to 15 s; the socket runs detached from the caller's job so a cancelled caller first sends a normal close frame (bounded, 2 s for the close and 4 s overall) and then rethrows. The end is a value, `SocketEnd.Closed(code)` or `SocketEnd.Failed`. `AuthenticatedApi.openSocket` uses the stored server and bearer token (as REST) and calls `onSessionRejected` on close code 4401.
- `SyncSocket` (`data/SyncSocket.kt`): one `WS /api/sync` per window. It mirrors `@semprec/realtime-client`: backoff `nextReconnectDelayMillis` (1 s floor, ceiling doubling to 30 s, jittered, attempt reset on connect), no reconnect after 4401, and every topic raised once after each successful connect (the TS `refetchActiveState`). On connect it reads `GET /api/schema` for database id to key. If that fails, a database frame raises every topic. Frames within 300 ms raise once.
- `SyncFrame.kt`: parses `invalidate` scope `item`/`relation` and `notification` with the field checks of the TS `parseServerFrame` for those frames; everything else is dropped. Topic map: `calendars`/`events`/`tasks` raise `CALENDAR`, `invitations` raises `INVITATIONS`, `mailboxes`/`folders`/`emails` raise `MAIL_ACCOUNTS`. Notification kinds: `calendar_invitation` raises `INVITATIONS`; `mail_sync_error` and `mail_sync_stalled` raise `MAIL_ACCOUNTS`.
- `:shared:domain`: `SyncChanges` (the bus, one conflated revision per `SyncTopic`) and `SyncTopic`.
- `:shared:presentation`: `CalendarViewModel` reloads (through its `Refresh` rules) on `CALENDAR` and `INVITATIONS`. `CalendarListViewModel` reloads on `CALENDAR` and `InvitationsViewModel` on `INVITATIONS`, neither while its own job runs. `MailAccountsViewModel`, `MailFoldersViewModel` and `MailAccountViewModel` reload on `MAIL_ACCOUNTS` instead of polling (the account screen still updates only the status fields). `MAIL_SYNC_POLL_MILLIS` is gone.
- `:shared:umbrella`: `HomeSDK.sync: SyncSDK` (`start()`/`stop()`), with one `SyncChanges` shared with `CalendarSDK` and `MailSDK`.
- Apple: `ScreenModelFactory.startLiveUpdates()`/`stopLiveUpdates()` (CoreKit forwards to `sdk.sync`). The app's `LiveUpdates` modifier on the signed-in tabs of `AppScene` starts the socket whenever `scenePhase` is not `.background` and stops it on `.background` and on disappear (sign-out, window closed).
- Docs: new ADR `docs/adr/2026-11-20-mobile-screens-follow-the-sync-socket.md`, and a "Live updates" section in `mobile/docs/architecture.md`.

**Deviations and seams.**
- The issue names a mail-account polling removal "where the socket covers it". It is removed in all three mailbox screens. An IMAP backfill batch that ends the initial sync but ingests no message and changes no folder emits no frame, so such an account stays "syncing" on screen until the next frame or the next foreground.
- The client sends no pings of its own. The server's pings are answered by the engines. A connection that dies without the engine noticing stays silent until the scene comes back from the background.
- The TS client gates `invalidate` frames while its post-connect refetch runs. Here the refetch is a revision raise, so there is no in-flight window to gate.
- Android starts no socket. Its app has no sign-in or any of these screens, and without a session `start()` connects nothing.
- `AppScene`: the modifier sits on the tabs inside `SessionGate`. Placed inside the `tabs(...)` chain, it made `MailNavigationTests.testTheSceneShowsTheMailboxesTheAccountsAndAnAccount` fail twice; the cause was not investigated.
