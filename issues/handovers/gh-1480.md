## Delivered behavior

- **Shared linking** (`mail/personLinkingActions.ts`): `linkEmailEnvelopeToPeople(client, { itemId, envelope, emailsDatabaseId, senderPeopleKey, recipientsPeopleKey })` holds the logic that was inside `createLinkEmailToPeopleAction`. It resolves both relation properties, looks up each address with `lookupPersonIdByEmail`, dedupes recipients across To, Cc and Bcc, and writes edges with `createRelationWithClient` and `EMAILS_RELATION_CONTEXT`. The heartbeat action `mail.linkPeopleByEmail` keeps its behaviour and now calls it.
- **Finalization** (`mail/send.ts`): the finalization transaction of `sendDraftEmail` calls the same function with the envelope of the send (from, to, cc, bcc), after the Sent folder edge is created. A failure there rolls back the body update, the folder move and the people edges together.
- **Module ids**: `SendEmailModuleIds` gained required `senderPeopleKey` and `recipientsPeopleKey`. The seed's `EmailModuleResult` already exposes both keys.
- **No migration, no seed change, no write-safety baseline change.**

## Deviations and conflicts

1. **"Skipped" reading.** The Task says an edge that already exists is skipped. The implementation does not pre-check for the edge. A repeated link goes through `createRelationWithClient`, which upserts on the normalized tuple (`ON CONFLICT ... DO UPDATE SET metadata`), so it adds no duplicate and raises no error. The write path still runs, which means the edge-write hooks run and a rollup recompute is enqueued, and the metadata is replaced with `{}` (these edges carry none). A pre-check would repeat the choke point's own idempotency and add a branch that no observable test can tell apart from the upsert. The reviewer should decide whether the pre-check is wanted.
2. **Key sourcing.** `sendDraftEmail` receives the two relation property keys through `SendEmailModuleIds`. It does not hard-code the seeded literals, so the seed, the heartbeat config and the send path read the same keys from one place.
3. **No production caller yet.** On the tip, nothing outside tests calls `sendDraftEmail`: `services/semprec-api/src/adapter/customRouteMount.ts` mentions it only in a comment. The finalization linking therefore runs only under tests until the HTTP send (#1896) supplies a composition root.
4. **Existing behaviour, unchanged.** When the finalization fails after SMTP has accepted the message, the send claim stays in place, so a retry gets `ConflictError`. The new rollback test asserts the draft keeps its draft subject and stays in Drafts. It does not change the claim behaviour.

## Tests

- `backend/packages/data/src/__tests__/mailSend.test.ts`, describe "people linking of sent mail (issue #1480)":
  - a message to an address a person owns gets a `recipientsPeople` edge to that person, and no `senderPeople` edge;
  - a message from a mailbox address a person owns gets a `senderPeople` edge to that person, and no `recipientsPeople` edge;
  - an address no person owns leaves both relations empty;
  - two sent emails to the same person both link on both sides, and neither send fails;
  - a person listed in To and Cc gets a single `recipientsPeople` edge;
  - linking an already linked email again adds no duplicate edge and raises no error;
  - a link that fails (a Person soft-deleted while the address index still maps to it) rolls back the finalization: the draft keeps its subject, stays in Drafts, and gets no `recipientsPeople` edge.
- `mail/__tests__/emailsSenderPeopleCardinality.test.ts` and `__tests__/mailSync.test.ts`: the existing heartbeat tests still pass unchanged.
- `__tests__/publicSurface.test.ts`: `linkEmailEnvelopeToPeople` added to the expected runtime exports, because the package index re-exports `personLinkingActions`.
- `__tests__/mailMessagePreview.test.ts`: the `moduleIds` fixture gained the two keys.

## Notes for dependants

- **#1896 (sending over HTTP):** the composition root that builds `SendEmailModuleIds` must pass `senderPeopleKey` and `recipientsPeopleKey`, taken from the seed's `EmailModuleResult`. The route needs no separate linking call, because `sendDraftEmail` links in its own finalization transaction.
- **Sender cardinality:** `linkEmailEnvelopeToPeople` only adds edges. It never removes a `senderPeople` edge to another Person, so the open point from gh-1457 (deviation 2) still applies: one sender per email is kept by the writers, not by the database.
- **Reuse for existing mail:** the function takes an envelope and an item id, so a reconciler for mail already stored can call it with each stored envelope.
