## Summary

This adds three integration suites, one per queue composition root, that check background tasks keep data, notifications and side effects inside the tenant they run for (#1056). It changes no production code, and no case found a leak. All 77 tests pass locally. In `backend/`, `pnpm run lint`, `format:check` and `build` pass.

- `backend/services/semprec-api/src/__tests__/tenantIsolationJobs.test.ts` covers the `api` set: 25 tasks, 12 `tenant` and 13 `system`.
- `backend/services/semprec-agents/src/__tests__/tenantIsolationJobs.test.ts` covers the `agents` set: `heartbeatFireAgent`, `agentRun` and `delegatedAgentRun`.
- `backend/services/semprec-transcribe/src/__tests__/tenantIsolationJobs.test.ts` covers the `transcribe` set: `transcriptionJob`.

### What each suite does
- **Setup:** strict scope is switched on in `beforeAll` and restored in `afterAll`. All three suites run on a `semprec_data` pool from `createRuntimeRolePool`, which is also the role semprec-agents uses. Tenants A and B come from `createTestTenant` and are set up with `provisionTenant`. Tenant zero is set up the same way, so a leak into it would show in its fingerprint. Each tenant gets its own user.
- **Composition:** each task list is built the way its runtime's `create*QueueRuntime` builds it.
  - **api:** `createApiActionRegistry` + `createApiCoreTaskList(…, replayApprovedGenericOperation)` + `mergeModuleTaskListForAffinity`, with the blob roots pointed at temp dirs through the env vars the defaults read.
  - **agents:** the session wiring from `serve.ts`, with the faux model.
  - **transcribe:** `createTranscriptionTask`, with fake audio and summary gateways.
- **Exhaustiveness:** the set comes from `resolveTaskAffinitySets(await loadFullModuleRegistry())`. The test fails and lists any task in the set with no case, and any case outside the set. A second test checks each case's kind against `TASK_TENANCY`; module tasks count as `tenant`.
- **Fingerprint:** for each table commented `semprec:tenancy=tenant`, read inside `runInTenant(T)`: the row count plus an md5 over the ordered row texts.
- **Cases:** jobs go in with `enqueueJob` and are drained with `runOnce`. Job outcomes are read from graphile-worker's public `jobs` view.
  - **(a)** A's job runs, has its effect in A, and leaves B's and tenant zero's fingerprints unchanged. Every new notification goes to A's user.
  - **(b)** B's job naming A's ids ends with the same state and error (ids replaced with `<id>`) as one naming random ids, and A is unchanged.
  - **System tasks:** work is seeded in both tenants. One run does each tenant's work inside that tenant, notifications go to each tenant's own user, and bystander tenants are unchanged. `queueFailedJobsPrune` checks that all three fingerprints stay the same.

**Checking the suite can fail:** as a temporary test, I made the queue run every tenant task in tenant zero (since reverted). Every tenant case (a) failed except `docHistorySquash`, plus three system cases.

### Where this differs from the issue
1. **`mailAccountSync` can't complete in the api root.** `createApiQueueRuntime` wires no mail transport, so the job always fails with `No IMAP adapter configured for this composition root`. I kept the composition as it is. Case (a) checks that error and that the failure is recorded in A, with the `mail_sync_error` notification sent to A's user. Case (b) works as written.
2. **`tenantPurge` uses two extra tenants.** Purging erases the tenants it works on, so its work is set up in two fresh tenants put into `deleting`. A, B and tenant zero are bystanders and must stay unchanged. Each purged tenant must end with no rows and its own tombstone.
3. **Fixture side-jobs are cleared first.** Some fixture writes queue jobs of their own (rollup backfill, notification fanout, the export a request queues). Tenant cases clear them, without running them, before the job under test is queued.
4. **Some timestamps are backdated with raw SQL.** Where no production code can make work due (heartbeat `next_fire_at`, trash `deleted_at`, doc history, run events, MCP credential expiry, export expiry), the tests set the timestamp directly. Each spot has a comment saying why. The prune case updates graphile-worker's private `_private_jobs` table, because 0.17.3 has no public way to age a failed job.
5. **`docHistorySquash` checks almost nothing.** Its handler is still an empty placeholder, so its case only checks that the job completes.

The credential re-encryption task doesn't exist yet; #1062 will add it with its case.
