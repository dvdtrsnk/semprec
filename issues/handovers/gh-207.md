## What changed

- **Migration `0046_czech_hunspell_search.sql`** adds an idempotent function, `activate_czech_hunspell_search()`, and calls it once.
  - **Dictionary files present:** it creates the `czech_hunspell` dictionary and puts it ahead of `unaccent, simple` for the Czech word token types. A word the dictionary doesn't know still goes through the old `unaccent`/`simple` path.
  - **Files missing:** it catches only that one error (`config_file_error`), logs a `WARNING`, returns `false` and leaves the old setup as it was. The migration still succeeds and is recorded as applied. Any other error still fails the migration.
  - **Already active:** it returns early without touching the catalogs. A transaction-scoped advisory lock stops two deploys running it at the same time. Only the migrating role can run it.
- **Deploy-time activation:** `runMigrationsCli.ts` calls the new `activateCzechHunspellSearch()` helper after `runMigrations` on every deploy, and `testSupport/globalSetup.ts` does the same. A database migrated before the files were installed is therefore upgraded by the next deploy.
- **File name change in `provision.sh`:** PostgreSQL only accepts lowercase dictionary file names, so provisioning now installs the files as `cs_cz.dict` and `cs_cz.affix`, and `provision.test.sh` checks for those names.
- **Search queries are untouched:** `websearch_to_tsquery`, ranking and operators still read the same `czech` configuration. The only edit to `search.ts` is a doc comment.
- **ADR** `docs/adr/2026-09-23-host-asset-dependent-database-features-activate-on-every-deploy.md` records the pattern: a database feature that needs files installed on the host is switched on by a function that runs on every deploy.
- **Deploy docs:** `deploy/README.md` explains the behaviour. Two operational points:
  - Messages indexed before activation keep their old search terms until they are reindexed.
  - The dictionary files live in the `postgres` container, not in a volume. Once Czech search is active, PostgreSQL needs them to index or search any message, so `provision.sh` must be rerun whenever that container is recreated.

## Tests (`czechHunspellSearch.test.ts`)

Each test runs on its own fresh UTF-8 database, using small test dictionary files in `fixtures/czech-hunspell`:

| Acceptance criterion | Covered by |
|---|---|
| With the files, `ts_lexize` and inflected terms prove stemming | `ts_lexize('czech_hunspell', 'fakturu')` gives `{faktura}`; searching `fakturu zpráva` finds a message indexed as "…faktury ve zprávách" |
| Without the files, migration and search fall back | Activation returns `false`, no dictionary is created, the old `unaccent`/`simple` output is unchanged and search still matches |
| Installing the files later and activating upgrades an existing DB | Migrate without the files, add them, activate, and words are then stemmed |
| Repeated activation is a no-op | The `pg_ts_config_map` rows, including their `xmin`, are identical after a second call, and there is still exactly one dictionary |
