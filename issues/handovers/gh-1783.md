## What was delivered

The Semp thread list finds a thread by the text of its messages, with inflected forms (once Hunspell search is active) and without diacritics.

- Migration `0157_semp_messages_search_vector.sql` adds the nullable `semp_messages.search_vector tsvector` and a GIN index `semp_messages_search_vector_idx`; DDL only. The chain wrote it as `0152`; that ordinal was taken on the tip by `0152_database_sensitive.sql`, so the queue runner renamed the chain's own file to the next free ordinal `0157`. Nothing referenced the old name.
- `semp/sempMessageSearch.ts` (new): `sempMessageSearchVectorSql(textSql)` is the one expression of the vector, `to_tsvector('czech', left(text, N)) || to_tsvector('czech_simple', left(text, N))` with N = `SEMP_MESSAGE_SEARCH_MAX_CODE_POINTS` = 50,000; `reindexSempMessageSearch(client, { limit, afterMessageId?, onlyMissing })` recomputes the vector in id order, in batches, under a row lock, tenant-scoped, inside the caller's managed transaction, and returns the last processed id or null; `buildSempThreadMessageSearch` builds the per-term message rule over the shared `buildItemSearchQuery`.
- The vector is set in the same statement that writes message text in `insertSempUserTurn`, `finishSempMessageTurn` and `finishTickRunWithMessage`. System messages (with a `system_key`) and messages without text have a NULL vector.
- The `q` filter of `listSempThreads` has a third OR rule next to the title and preview rules of #1737: every word of `q` must be found in some non-system message of the thread (the same or different messages).

## Deviations and spec seams

1. Task step 4 says a thread matches when a message matches the whole tsquery, but the acceptance criterion requires two words in different messages to match. Implemented per term: a subquery selects messages matching any term (GIN-usable) and groups by thread with `bool_or` per term. The per-term piece is built by the shared builder from a fixed word at the term's bind position.
2. The Task's explain-plan check runs on the superuser pool with sequential and index scans disabled (40,000 seeded rows). Under the runtime role, row-level security makes Postgres refuse the non-leakproof `@@` as an index condition, so the plan check proves the statement can use the GIN index, not that the production runtime plan does. The same limit holds for the existing `item_search_index` search. See follow-ups.
3. The migration holds DDL only (the decision record of the source moved the backfill to the batched helper).
4. A review fix bounds the indexed text to the first 50,000 code points of a message, because Postgres refuses a tsvector above 1 MiB and no code caps message text; the text is stored whole, only words after the prefix are not searchable.
5. Three #1737 tests in `sempThreadsList.test.ts` were brought in line with the new rule and two route-level tests were added; `voiceSessionHandler.test.ts` matched the exact text of the old user-message INSERT and now identifies the statement by its start and role.
6. A phone-like query is normalised by the shared builder to 420-prefixed digits, while message vectors are not phone-normalised, so a phone number written in a message is not found by that number outside the preview window. Out of scope.
7. The new test file carries its own small copy of the `withFreshDatabase`/`installAssets` helpers of `czechHunspellSearch.test.ts`, which are not exported.
8. Reconciled at the merge: the tip dropped `result` from the error variant of `TickRunOutcome`; the chain's test `sempMessageSearch.test.ts` passed `result: "Chyba spojeni"` for a failed tick run and no longer compiled, so the merge removes that property (test input only, no production change).
