# gh-1404 — Add the relation.list operation

Repository-Issue: gh-1404

## Delivered behavior and production wiring

- Catalog (`backend/packages/shared/src/genericOperations/`): `relation.list` is appended to `GENERIC_OPERATION_NAMES` (30 operations). Its input is `RelationListInputSchema`, strict `{ itemId, relationPropertyId? }`. Its output is `RelationListEntry[]` (`rows.ts`), each entry `{ relationPropertyId, propertyKey, targetItemId, targetDatabaseId, metadata }`. Metadata is `nonDestructive("core.item.read", "read")`, so no approval is required. The binding calls `GenericApplicationPort.listRelations`.
- Application (`packages/application/src/genericApplicationService.ts`): `listRelations` calls the new choke-point read `chokePoint.listItemRelations`. A `null` answer (unknown, trashed or foreign item) becomes `NotFoundError("Item <id> not found", { resource: "item", itemId })`, the same error `requireItem` throws, so the three cases cannot be told apart.
- Data (`packages/data/src/chokePoint/`): `listItemRelationsWithClient` in the sibling module `relationReads.ts`, run in one transaction by the facade method in `chokePoint.ts`. It resolves the item's relation properties, reads each edge from the item's own side (side A holds `item_a` and reads `item_b`, side B the reverse; a one-directional definition has side A only), and keeps only targets that are not trashed and whose database is not archived. The result is ordered by property key, then target id. Two store reads in `relationsStore.ts` back it: `listRelationEdgesForItemOnDefinitions` (one query for every definition, both columns) and `listLiveRelationTargets`.
- Validation: a `relationPropertyId` that is not a relation property of the item's own database fails with `400 validation_failed` and `field: "relationPropertyId"`, and returns no data. The id is compared case-insensitively.
- REST (`services/semprec-api/src/itemsHandler.ts`): `GET /api/items/:id/relations` returns `{ relations: [...] }`. The optional `?propertyKey=` is resolved with the existing `resolveRelationProperty`, so an unknown or non-relation key is `404 not_found` (`resource: relationProperty`) and an ambiguous key is the same defensive 409 the write routes return. The route is listed as `list relations` in `routeMatrix.ts`. Tenant scope comes from the existing adapter, as for every other tenant route.
- MCP and AgentTool: `semprec.relation.list` and `relation.list` appear automatically from the catalog. A non-destructive call queues no approval request.
- Count references: the "29 operations" comments and counts in the catalog, the application, agent-runtime, data and API comments and tests now say 30. The ADR `2026-10-28-page-operation-family.md` still says "29 today", which is its historical record; ADRs are append-only, so it was left as is.

## Notes for dependants

- #1518 (`include=relations`) should reuse `listItemRelationsWithClient` and its two store reads, so the resolution rules stay in one place, rather than calling the port once per item.
- #1839 (related-items grouping) can group on `targetDatabaseId` and `relationPropertyId`, which each entry already carries.
- The result has no `limit` or cursor, because the Task does not ask for one. An item's edges are returned in full, so a follow-up is needed if an item can carry very many edges.
- The MCP and AgentTool path passes `itemId` through as a plain string, as `item.get` does, so a non-UUID value reaches the database's UUID cast. This is the existing behaviour of the item operations and was not changed here.
- A relation property whose definition is missing contributes no entries, without an error. The data cannot be produced by a choke-point write and is covered by a test with raw SQL.
- `packages/data/src/index.ts` gained no export. The facade method is the public entry point, so no new runtime or type export was needed.
