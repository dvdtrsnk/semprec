## What was delivered

- `mailboxItemRestoreHook` (`backend/packages/data/src/mail/mailboxRestoreHook.ts`), an item restore hook, registered last in `backend/packages/data/src/domainWriteHooks.ts`. It acts on a restored item of the tenant's system Mailboxes database (`database.system` and owner module `mailboxes`) and returns before its first statement for an item of any other database.
- Sync state. The hook reads the mailbox's `mail_account_sync_state` row with `getMailAccountSyncState`, without a lock. When there is none it calls `ensureMailAccountSyncState` with `defaultSyncModeForProvider` of the item's `provider`; a `provider` that is not a string counts as `generic`, so the mode is `imap`. The inserted row is the one a newly connected mailbox starts with: `sync_mode` set, every cursor, activity, error and address column null. A row that exists is neither locked nor written.
- Folders and messages. In the same transaction the hook selects and locks `FOR UPDATE`, in id order, the Folders related to the mailbox through `Folders.mailbox` whose `deleted_at` equals the hook context's `deletedAtExact` (compared by Postgres), and restores each through `restoreItemWithClient`. It then does the same for the Emails of that epoch related through `Emails.folder` to any of the mailbox's Folders, whatever that folder's own trash state. A folder or message trashed at another instant stays in the trash.
- The nested restores carry the mailbox restore's queue routing, acting user, writer kind and agent run id, so their restore hooks, heartbeats and invalidations run as for any restore.
- `syncStatus`. The hook writes nothing on the Mailboxes item. The removal of gh-1690 wrote `needsReauthorization`, and the item returns with it. The credential, the folder sync state rows and the server settings row stay deleted.
- Any error from the hook or from a nested restore rolls the whole restore back: the mailbox, its folders and its messages stay in the trash and an inserted sync state row is gone.
- Sync job (fix commit `51bd47c1e`). `handleSyncMailAccountTask` throws `MailReauthorizationRequiredError` when a pass finds no stored credential and the `syncStatus` it read in its prologue is `needsReauthorization`. The existing catch branch then keeps the status, stores failure kind `reauthorization`, raises the `mailSyncError` problem as critical and writes no `mail_sync_error` notification. With any other status a missing credential stays the ordinary failure it was (`error`, failure kind `other`, the notification).
- ADR `docs/adr/2026-11-12-a-restored-mailbox-gets-its-sync-state-and-its-mail-back-in-the-restore-transaction.md` (accepted, backend) records the decision: one transaction as large as the mailbox, no sync guard, no wait for a sync state row that exists, `syncStatus` keeps its two writers, and what a sync pass before the sign-in does. It delivers what `2026-11-10-a-mailbox-removal-job-joins-the-mailbox-trash-epoch` left to this issue.
- No migration, table, column, route, generic operation, job name, tenant cutover entry, export from the data barrel, module manifest entry, stored key or i18n key was added.

## Contracts dependents build on

- A restore of a trashed Mailboxes item (`chokePoint.restoreItem`, which the generic `POST /api/items/:id/restore` calls) returns a live mailbox with exactly one `mail_account_sync_state` row, its Folders and Emails of the mailbox's deletion epoch live again, and `syncStatus` as it was stored. For a mailbox that `removeMailbox` trashed that is `needsReauthorization`.
- The mailbox has no credential after the restore. The user signs in again through the reauthorization routes of gh-1742 (`reauthorize`, `oauth/complete`); the pass after the sign-in ends with `syncStatus` `ok`, reuses the restored Folders and Emails items and adds only new messages.
- Until the sign-in the default row is due for the periodic sync sweep (`next_expected_activity_at` is null). Every pass before the sign-in fails as a reauthorization case: status kept, failure kind `reauthorization`, critical `mailSyncError` problem, no `mail_sync_error` notification, the mailbox stays in `accountsNeedingReauth` of the mail summary. `recordSyncError` moves the next sweep 15 minutes out.
- `MailReauthorizationRequiredError` (`mail/providerTypes.ts`) is now also thrown by the sync job itself, not only by a provider adapter. The condition is the status the pass read, not the missing credential alone.
- A sync pass that reaches its write transaction after the mailbox was removed and restored now finds a live item with a row (`enterSyncPass` returns `true`) and reconciles once with the credential it read before the removal deleted it. Before this source it did no work. `enterSyncPass` still returns `false` for a live mailbox without a row; no production flow leaves one in that state any more.
- Lock order. The paths that take both rows take the sync state row first and the Mailboxes item second. The hook runs with the item locked and therefore never waits for a row that exists. A new write path of that table that also locks the Mailboxes item keeps this order. The only callers of `deleteMailAccountSyncState` are `mailboxRemoval.ts` and `mailPurgeHook.ts`, and both delete the row while they hold the Mailboxes item; the hook's unlocked read relies on that. A third caller that deletes the row without the item lock breaks the hook's assumption.
- The restore transaction grows with the mailbox: one nested choke-point restore per folder and message of the epoch, all row locks held to the commit.
- Order in `domainWriteHooks.ts`: `registerItemRestoreHook(mailboxItemRestoreHook)` is the last entry of the file, after `pageItemDeleteHook` and `pageItemRestoreHook` of gh-1723. It is the sixth item restore hook to run (after search, transcript, journal, People last contact and page). A source that names gh-2032 as an ordering blocker (gh-1757 does) puts its entries after it.
- `mailboxItemRestoreHook` is exported from `mail/mailboxRestoreHook.ts` only, not from `backend/packages/data/src/index.ts`.
- A table that a later mail feature keeps per mailbox and the removal deletes is not written again by this hook; that feature extends the hook or accepts the gap.

## Deviations from the specification and spec seams

- Files outside `Touches`: the ADR; `mailSyncJob.ts` (code, from the fix round); `providerTypes.ts` (docstring); `mailboxRemoval.test.ts`, where a test of gh-1690 relied on a restored mailbox having no sync state.
- The Task says the hook "keeps `syncStatus` `needsReauthorization`". It is implemented as not writing the Mailboxes item. A mailbox that reached the trash another way than `removeMailbox` returns with the status, sync state and credential it had. Since gh-2031 a user or an agent can no longer trash a mailbox with the generic delete; mailboxes trashed that way before gh-2031 and backend callers that trash as the system writer remain.
- The Task names "the Mailboxes database"; the hook gates on `database.system` and owner module `mailboxes`, as the removal does.
- The epoch is compared with the context's `deletedAtExact` (ADR 2026-11-08), not with the millisecond `deletedAt`. A row trashed on its own at exactly the mailbox's microsecond returns with it.
- An Email of the epoch is restored whatever the trash state of its folder, because the removal job trashes Emails before Folders.
- The sync job decides from the status the pass read. A pass that fails before it reaches the credential (a database error, for instance) writes `error`, and later passes then report the missing credential as an ordinary failure until the sign-in. Whether a missing credential of every mailbox should read as `needsReauthorization` is undecided; the fixer proposed a follow-up source.
- A restored iCloud or generic mailbox gets an `imap` row, but the reauthorization of gh-1742 refuses password mailboxes and no flow stores a new password for an existing mailbox. "The user then signs in again" cannot happen for it. No Task step of this issue covers that.
- With no row, the hook's `INSERT` comes after the lock on the Mailboxes item. It can meet the reauthorization's uncommitted insert only when the mailbox, without a row, was trashed and its restore begun between two statements of that transaction; PostgreSQL then ends one of the two with `40P01`, unmapped and not retried. Documented in the ADR, not tested.
- One sentence of the new ADR's Consequences is stale on this tip: it names the generic `DELETE /api/items/:id` as one way a trashed mailbox keeps its sync state row. gh-2031, which landed before this chain, refuses that delete for a user and an agent. The other case the sentence names (the live-sync discovery's insert) stays valid. The ADR was not edited at landing.

## Review

Two reviewers read the first commit `5c774cf84`; neither ran a build or a test. Each had one finding of medium severity, both were confirmed against the code and fixed, and the recheck at `23b953d07` passed with nothing unresolved and no new finding.

- Requirements: the restored mailbox kept `needsReauthorization` only until the first periodic sync pass, which wrote `error` and a sync failure notification. Fixed in `51bd47c1e` (sync job), narrower than the reviewer's wording: only for a mailbox that shows `needsReauthorization`.
- Rules: the hook wrote the sync state row after the Mailboxes item lock and waited there, against the documented lock order. Fixed in `23b953d07` (read first, insert only without a row).

Follow-ups for the owner, none of them blocking:

- Decide whether a missing credential of every mailbox should read as `needsReauthorization` in the sync job (a follow-up source).
- A flow that stores a new password for a restored password mailbox does not exist.
- The stale ADR sentence about the generic delete (above) can be corrected by a later record.
- The owner should accept the change of `mailSyncJob.ts` knowingly, since the record's `Touches` does not name it.
