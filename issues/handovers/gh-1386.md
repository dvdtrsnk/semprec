# Handover for gh-1386

`item_automation` now stores a stable `error_code` beside the diagnostic `error`, and the permanent-failure notification for a transcription links to the transcript. I ran lint, build, prettier check and the vitest integration files `transcriptionTask.test.ts`, `library.test.ts` and `publicSurface.test.ts`; I did not run the full `pnpm run verify`.

**What changed**
- **Migration:** `0092_item_automation_error_code.sql` adds `error_code text NULL`. Additive, no backfill.
- **`itemAutomationStore.ts`:**
  - Exports `ITEM_AUTOMATION_ERROR_CODES` and the `ItemAutomationErrorCode` type (`budgetExceeded | mediaUnreadable | providerFailed | unknown | deleted`). The type is re-exported from `@semprec/data`.
  - `ItemAutomationRow.errorCode` is validated on read with `assertKnownValue`.
  - `recordItemAutomationFailure` takes an optional fifth argument `errorCode` (default `null`, which clears the stored code).
  - `markItemAutomationDone` and `markItemAutomationError` clear the code with the error.
  - `startItemAutomationAttempt` leaves the code in place, like `error`.
- **`transcriptionTask.ts`:**
  - New exported `classifyTranscriptionFailure`:
    - Budget rejections map to `budgetExceeded`.
    - `MediaToolError` maps to `mediaUnreadable`.
    - `AudioGatewayCallError` and other `AiGatewayFailedError` map to `providerFailed`.
    - Everything else maps to `unknown`.
  - `recordTranscriptionFailure` stores the code with the message.
  - The notification `linkHref` is `?page=transcript&id=<transcriptId>`.
  - The budget-rejection log line no longer includes the exception, only the code.
- **`mediaNormalization.ts`:** new `MediaToolError`, thrown for ffmpeg/ffprobe non-zero exits and for the missing or non-numeric duration. A failure to spawn the binary stays a plain error and maps to `unknown`.

**Tests** (`transcriptionTask.test.ts`)
- Each failure class maps to its code, checked through the stored row.
- The notification row does not contain the message.
- A successful retry clears `error` and `error_code`.
- The notification link is asserted.
- The existing retry and replay tests still show a single notification per attempt.

**Notes for dependants**
- `error` is still diagnostic only and must not be returned by any API (#1576, #1636).
- #1582 and #1945 can pass `"deleted"` as the `errorCode` argument; nothing writes it yet.
- Clients need a `transcript` page for `?page=transcript&id=...`.
- The rethrown exception still reaches graphile-worker's own failure logging, which this issue does not change.
