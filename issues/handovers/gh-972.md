## What changed
- **Migration** `backend/packages/data/src/db/migrations/0059_tenant_id_columns.sql`:

  - Its header comment explains why there is no rewrite and why the previous release keeps working.
  - It adds no index on `tenant_id`.
  - It needs no exemption marker for the migration-compatibility check.
- **`tenancyCatalog.test.ts`**:
  - One catalog-driven check covers every table classified `semprec:tenancy=tenant`.
  - It asserts the column is `uuid`, `NOT NULL`, defaults to `app_tenant_default()` and has a single-column foreign key to `tenants(id)`.
  - It asserts the same column, type, not-null and default on every `items_p_*` partition.
  - A failing assertion names the table.
- **`tenantIdColumn.test.ts`** (new):
  - **Upgrade test:** on a scratch database migrated to just before this migration, a database, an item and a `notifications` row all read tenant zero afterwards. The `relfilenode` of `databases`, of the `items_p_*` partition and of `notifications` is unchanged, so there was no rewrite.
  - **Previous-release writes:** a database, an item and a `notifications` row inserted without naming `tenant_id` get tenant zero.
  - **Unknown tenant:** a `tenant_id` not in `tenants` fails with `23503`.
  - **Second tenant:** inside a rolled-back transaction, a scope-less insert fails with `23502`. With `app.tenant_id` set to the second tenant, the same insert succeeds and stores that tenant's id.
