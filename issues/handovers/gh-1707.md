## What was delivered

- A module `recipes` (`backend/packages/data/src/recipes/recipesModuleManifest.ts`): not removable, a system project module, one database descriptor with key `recipes`, name `Recipes`, `defaultViewType: "gallery"`, icon `fork-knife`, color `#FF9500`, `overviewOrder: 9`, `switcherOrder: 9`. It is in `ALL_MODULE_IDS` and `MANIFEST_PATHS` of `manifest/fullModuleRegistry.ts` and exported from the data barrel as `recipesModuleManifest`.
- The seed `seedRecipesModuleInTransaction(client, projectsDatabaseId, viewTypeRegistry)` in `backend/packages/data/src/seed/seedRecipesModule.ts`. In the caller's transaction it creates the system project item "Recipes" in the Projects database (`systemActive: true`, an `agents` text), the system database `recipes` owned by that item, six properties, the default `gallery` view, and then sets `schema_locked`. It resolves with `{ projectItemId }`. It is not idempotent on its own.
- The six properties, all owner `user`, all with `name` null (labels come from the catalog): `name` (title), `category` (select; options `main` `#FF9500`, `breakfast` `#FFCC00`, `dessert` `#FF2D55` in `config.options[].color`), `prepMinutes` (number; `config.filterPresets` 15, 30, 60 with `op: "lte"` and a `labelKey` each), `servings` (number), `favorite` (checkbox), `photo` (image, `{ blobId }`).
- The default view: type `gallery`, name `Recipes`, `isDefault: true`, created by `system`, config `{ columns: 2, aspect: "4:3", coverKey: "photo" }`.
- New tenants: `seedSystem` calls the seed after the calendars seed.
- Existing tenants: `runRecipesModuleCutoverMigration(pool)` in `backend/packages/data/src/recipes/recipesModuleCutoverMigration.ts`, registered in `runTenantCutoverMigrations`. One transaction per tenant: it takes the seed lock through `lockTenantSeedInTransaction` (advisory lock `(2331, hashtext(tenant_id))` and tenant admission), returns when `getDatabaseByModuleId(client, "recipes")` finds the database, returns when the tenant has no Projects database, and otherwise calls the same seed function. When the tenant has an account (`getTenantUserId`), the same transaction writes the `project_agent_guidance` row of the new project and its `core.agentGuidanceDrift` heartbeat through `seedProjectAgentGuidanceFromLegacyText`. A tenant without an account gets that row at account creation, like every system project. Active and suspended tenants are both served, because the runner iterates the maintained tenants.
- Catalogs `backend/packages/data/src/recipes/i18n/cs.json` and `en.json`: the database name ("Recepty" / "Recipes"), the search placeholder, six property names, three category option labels and three preset labels.
- The write hook `recipePhotoWriteHook` in `backend/packages/data/src/recipes/recipePhotoHook.ts`, one function registered for item create and item update. On a write to an item of the `recipes` database that sets `photo`: `null` passes; any other value must be `{ blobId }` with a UUID that `getBlob` finds in the caller's tenant scope and whose `mime_type` starts with `image/`. Every refusal is the same `ValidationError` (HTTP 400, `details.field` `photo`), so a blob of another tenant answers exactly like an unknown one. A create is judged by its final properties, an update by the keys of its patch.
- `defaultViewType` on the database envelope (fix round): every database route of `semprec-api` (list, create, detail, patch, archive, restore) returns `defaultViewType: string | null`, the view type the database's module manifest declares for its default view. `recipes` answers `gallery`.
- The `agents` text of the Recipes project is the entry `recipes` of `SYSTEM_PROJECT_AGENT_GUIDANCE_SEED_TEXTS` (`seed/systemProjectAgentGuidance.ts`), so account creation seeds a guidance row and a drift heartbeat for the Recipes project too.

## Contracts dependents build on

- Module id, database key and `owner_module_id` are all the string `recipes`: `RECIPES_MODULE_ID` in `backend/packages/data/src/seed/recipesModuleKeys.ts`. It is not exported from the data barrel; the barrel exports only `recipesModuleManifest`. `seedRecipesModuleInTransaction`, `runRecipesModuleCutoverMigration` and `recipePhotoWriteHook` are not exported from the barrel either.
- The pattern for a later system module (gh-1776 names it): a manifest beside its `i18n/` folder, registered in `fullModuleRegistry.ts`; a seed function called from `seedSystem.ts`; one cutover step in `runTenantCutoverMigrations` that takes the seed lock, checks `getDatabaseByModuleId` and calls the same seed function; a copy step for the catalog folder in the build script of `backend/packages/data/package.json`; the domain folder in the two domain lists of `backend/dependency-cruiser.rules.json` (`chokepoint-knows-no-domain`, `item-trash-domain-imports-are-purge-only`).
- Catalog location: a module's labels must be in the `i18n/` folder beside its manifest. `loadModuleCatalogs` reads that folder and the registry refuses a catalog key claimed by two modules, so labels of a database declared by `recipes` do not resolve from `seed/i18n`.
- Registry order in `backend/packages/data/src/db/tenantCutoverMigrations.ts`: `runRecipesModuleCutoverMigration` stands after `runJournalEventsCutoverMigration` and directly before `runAreaNoteCutoverMigration`, which stays last. It is after `runHealthRecordTagsCutoverMigration` of gh-1700 and after `runProjectAgentGuidanceCutoverMigration`. A step that creates a system project after the guidance cutover has to write that project's guidance row itself, as this one does.
- Registry order in `backend/packages/data/src/domainWriteHooks.ts`: `registerItemCreateHook(recipePhotoWriteHook)` directly after `mcpServerItemCreateHook`, `registerItemUpdateHook(recipePhotoWriteHook)` directly after `mcpServerItemUpdateHook`, both after `blobReferenceItemCreateHook` and `blobReferenceItemUpdateHook`. Through the choke point an unknown, foreign or malformed blob id is therefore refused first by the blob reference hook, with the same 400 on field `photo`.
- Order for gh-1710 and gh-1712, which name gh-1707 as a `Shared-file ordering` blocker: their entries in `domainWriteHooks.ts` and `tenantCutoverMigrations.ts` go after the entries of this source, and a cutover entry still goes before `runAreaNoteCutoverMigration`, unless their Task names another position.
- `DatabaseEnvelope` (`backend/services/semprec-api/src/adapter/databaseEnvelope.ts`) has the new required field `defaultViewType: string | null`, and `toDatabaseEnvelope` takes it as a fifth argument. The value is the manifest declaration, read once per request from `moduleRegistry.getDatabases()`; it is not a read of the stored views. Today only `journal` (`temporal-switcher`) and `recipes` (`gallery`) answer a value. Every other system database and every user-created database answers `null`, Books, Movies and Emails included, although their seeds create a default view of their own type. `CollectionMetadata` and `GET /api/schema` are unchanged and carry no such field.
- The schema of `recipes` is locked (`schema_locked = true`), so the property store refuses a schema change with `SchemaLockedError`. A later source that adds a property (gh-1974 names `sourceUrl`) writes it through the raw stores in the seed and in a cutover step of its own.
- `listPropertiesByDatabase` orders by `initial_position` and then by key, and the seed sets no position, so the six properties are listed by key (`category`, `favorite`, `name`, `photo`, `prepMinutes`, `servings`), not in the Task's order.
- The mime check is `startsWith("image/")` on `blobs.mime_type`, not on `detected_mime_type`.
- Side effects later sources and tests meet:
  - every seeded tenant has one more system database, one more Projects item ("Recipes", `systemActive: true`), six more properties and one more view;
  - `GET /api/databases` lists `recipes` as the ninth entry (switcher position 9), so Books and Movies moved by one;
  - account creation writes six `project_agent_guidance` rows and six drift heartbeats instead of five, and five instead of four when one system project is deleted or not active (`systemProjectAgentGuidanceSeeding.test.ts` pins both);
  - a test that asserts a whole database envelope with `toEqual` needs `defaultViewType`;
  - the test global setup runs `runTenantCutoverMigrations` before the seed, so the cutover meets tenants without a Projects database and skips them;
  - the mirrored lists of `moduleRegistryLoadAll.unit.test.ts`, `coreModuleManifests.unit.test.ts` and `smoke.test.ts` now contain `recipes`, and the expected export list of `publicSurface.test.ts` contains `recipesModuleManifest`.
- No SQL migration, no table, no route, no generic operation, no MCP tool, no job name and no ADR was added. The heartbeat `core.agentGuidanceDrift` is the existing one.
- gh-2002 (hide Recipes from the overview) and gh-1776 (the sleep module) declare this source as a blocker. gh-1974 (recipes from the Inbox) adds `sourceUrl` to the `recipes` database through the same seeding path and does not declare it as a blocker.

## Deviations from the specification and spec seams

1. `defaultViewType` in `GET /api/databases` (acceptance criterion 2). The criterion asks for it, but no Task step and no blocker adds a field to the database envelope. The worker reported the clause as BLOCKED. The requirements reviewer asked for the owner's decision. The fix round added the field without that decision, with the first option the reviewer offered: the value of the module descriptor, a string or null. The recheck passed it. No decision record `issues/decisions/gh-1707.md` exists.
2. Catalog location. Task step 4 names `seed/i18n/cs.json` and `en.json`. The labels are in `recipes/i18n/`, because `seed/i18n` is the catalog of the `systemDatabases` module and a key cannot be claimed by two modules. This needed the copy step in the build script.
3. Three preset labels (`property.recipes.prepMinutes.preset.15`, `.30`, `.60`) are added although step 4 does not list them, because `NumberFilterConfigSchema` requires a `labelKey` on every preset. No `emptyPreset` is seeded.
4. The cutover also writes the Recipes project's guidance row and drift heartbeat for a tenant that has an account. The Task does not ask for it; both first-round reviewers found that the project otherwise has no guidance until the next deploy.
5. The cutover has its own file, `recipes/recipesModuleCutoverMigration.ts`; `Touches` lists only the call.
6. The Context says the cutover pass runs through `runSeedCli` and `provisionTenant`. In the code `runTenantCutoverMigrations` is called by `db/runMigrationsCli.ts` and by the test global setup, before the seed. That is why the cutover skips a tenant without a Projects database.
7. Values the Task leaves open and the worker chose: icon `fork-knife`, color `#FF9500`, `switcherOrder: 9`, manifest version `1.0.0`, the gallery config, the labels of the properties, options and presets, the placeholder text. The project item name is the literal "Recipes" the Task gives; it is not localized.
8. The hook also refuses a non-null `photo` that is not `{ blobId: <uuid> }` (a string, a number, an array, an object without `blobId`, a malformed id), with the same error. `null` clears the photo.
9. The HTTP criteria are tested in `backend/services/semprec-api/src/__tests__/recipesModule.test.ts`, outside the folder `Touches` names.
10. Files outside `Touches`: `seed/systemProjectAgentGuidance.ts`, `backend/packages/data/package.json`, `backend/dependency-cruiser.rules.json`, `databaseEnvelope.ts`, `databasesHandler.ts`, and the seven adapted test files.
11. No ADR. The cutover uses the existing per-tenant runner and the existing seed lock helper; the hook uses the existing create and update registries.

Follow-ups, none of them filed as an issue:

- For the owner: confirm the contract of `defaultViewType` (deviation 1). The low finding of the recheck is part of it: the value is the manifest declaration, so Books, Movies and Emails answer `null` although their stored default view is not a table. Either `null` means "the manifest declares none", or the library and mail manifests declare their type, or the route reads the type of the stored default view.
- No REST route lists the views of a database (`view.list` returns curated views only), so a client cannot find the id of the default view over HTTP. The test reads it through the choke point.
- Observation of the requirements reviewer, outside this source: `POST /api/blobs` stores the mime type detected from the bytes, and detection knows JPEG, PNG and HEIC as images. An uploaded WebP or GIF gets an unknown type and is refused as a recipe photo. Uploading image blobs belongs to gh-1401.
- Observation of the rules reviewer: the system project item is named with the literal "Recipes", as the Task prescribes and as the library, MCP and Email seeds do, while the calendars seed takes its project name from the module catalog.
