## What was delivered

- `inbox/threadCardContext.ts`: `loadInboxCardThreadContext(client, itemId)` returns the card context of an Inbox item: for an open card the source (text, date, time, type name, attachment ids with `name: null`), the effective envelope, `userEditedKeys`, the history and the card `version` (its `updatedAt`); for a confirmed card the source, the status and the items it created; `null` for no card, a rejected card, a trashed or non-Inbox item, or another tenant's item. `renderInboxCardThreadContext` renders it bounded (field limits, capped lists), with `<` written as `<`, between `inbox-card-data` tags and a fixed sentence that it is data.
- `sempMessageTask.ts` adds that text to the per-turn prefix for item threads (`getSempMessageTurn` now also returns `subjectInboxItemId`), so it is read again on every turn and is never stored with the turn (the run task and `user_message` events carry the raw message only).
- `reviseProposalFromThreadWithClient` (new file `inbox/proposalThreadRevision.ts`, re-exported by `proposalActions.ts`) with the pure rule helper `retainOverridesForThreadRevision` in `proposalOverrides.ts`: a manual key keeps its previous assistant value in `aiProposal` and takes the revised value as the user's; other keys go to `aiProposal`; a kind or target change drops the manual values with a `reset` history entry; `aiVersion` grows; history gets `{ ai, threadRevision, threadId, messageId }`; the envelope is validated with `assertValidEnvelopeForCard` (the MCP credential guard included). It refuses a card whose source is not the thread's subject (same NotFound as a missing card, edge read `FOR SHARE`) and a locked or source-deleted card.
- Review fixes: a manual value of a key the revised envelope omits is kept (only an explicit `null` clears it); a revision composed from a stale snapshot is refused with `version_conflict` (`ifVersion` against the card's `updatedAt`, checked under the card lock after the own-card and open-status checks); `inbox.proposal.get` and the card context carry `version`; the tool answer returns the new version.
- `inbox.proposal.revise` (gh-1906) now calls `reviseProposalFromThreadWithClient` with the thread and message ids of the run.

## Deviations from the specification and spec seams

1. The per-turn card context is composed in `sempMessageTask.ts` (next to the date prefix), not in `agentSessionComposition.ts`, which builds one system prompt per run; a cached session would otherwise show a stale card after the first revision. `agentSessionComposition.ts` is unchanged.
2. `reviseProposalFromThreadWithClient` lives in the sibling `proposalThreadRevision.ts` because `proposalActions.ts` is near the 900-line cap.
3. Loader and renderer reach the public surface through `inboxAgentTools.ts` because `index.ts` has no free line; `publicSurface.test.ts` lists them.
4. Attachment names do not exist (gh-1623): attachments are `{ attachmentId, name: null }`.
5. The Task is silent on an edited key that the revised envelope omits. Originally it was removed; after review it is kept, and only `null` clears it.
6. The Task is silent on several cards per source: the newest live card is used.
7. Shared files touched beyond the Touches list: `sempThreadsStore.ts`, `inboxCardsStore.ts`, `testSupport/testDb.ts`, `inboxAgentTools.ts`, `proposalOverrides.ts`.
8. The send guard still refuses a new message to the thread of a confirmed or rejected card (gh-1620, not in this Task), so a confirmed-card turn is reached when the card is confirmed after a message was queued; the test reopens the running reply by SQL for that reason.
9. For the confirmed-card criterion the edit of the created task uses the generic `item.patch` implementation under the thread's run, because the thread's own tool set is out of scope.
10. `ifVersion` and `version` were added in the fix round (see the gh-1906 handover, deviation 9); the review demanded them as a data-loss guard.
