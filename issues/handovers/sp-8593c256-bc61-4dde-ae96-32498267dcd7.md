# Handover: let a provider deletion win over an update and map Graph 403 and redirects by what they mean

Commit on `fix/ia-provider`: `27eb96251`.

**Changes.**
- `graphCalendarHttp.ts`: `GraphRequest.forbiddenMeansConsent`; a 403 is `CalendarSyncConsentRequiredError` only with it or with an `insufficient_scope` challenge, otherwise `GraphCalendarRequestError(403)`; every request is sent with `redirect: "error"`.
- `graphCalendarAdapter.ts`: the calendar listing sets `forbiddenMeansConsent`; the update `PATCH` tolerates 404/410 and throws `CalendarSyncEventConflictError`; `eachPage` takes request options.
- `googleCalendarAdapter.ts`: the update `PATCH` handles 404/410 as the conflict.
- Docs: `domain-calendar-tasks-and-media.md` (adapter contract, Graph).

**Not changed.** Graph 429 was already retried within `Retry-After` and otherwise `rateLimited` (existing test "maps 429 asking for minutes"). Deletes of a gone Event already succeeded on every provider, and CalDAV already answered a gone resource on update as a conflict. The override create path (PATCH of an occurrence) is untouched.

**Follow-up.** A non-consent Graph 403 for one shared calendar still fails the whole pass (`unexpected`, retried); per-calendar isolation in the pass would need the apply to keep an unfetched calendar as it is.

**Tests.** Graph and Google: an update answered 404 and 410 rejects with the conflict and `getEvent` answers `null`; Graph: a 403 on a calendar's delta is `GraphCalendarRequestError(403)`, with `insufficient_scope` it is consent; every request of a fetch and a listing carries `redirect: "error"`.
