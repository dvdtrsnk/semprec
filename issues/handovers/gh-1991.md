## What was delivered

A proposal envelope can no longer offer a relation that the project derives, so a card cannot be confirmed only to fail at the choke point.

- `inbox/proposalDerivedRelations.ts` (new): `assertNoDerivedRelations(targetDatabase, envelope)` reads the choke point's existing exported rule table `GUARDED_DERIVED_VALUE_SOURCES` (gh-1662), matched on the database key exactly as the choke point does. For a database envelope, a non-empty `relations.<derived property>` next to a non-empty `relations.<project property>` of the same entry is a `ValidationError` (`details.field` is the relation key, code `derivedRelation`). Nothing from the table is duplicated or newly exported.
- `assertValidProposalEnvelope` calls it for database envelopes right after the relations check.
- `assertJournalEntryAreaNotDerived(properties)` (`inbox/journalEntryEnvelope.ts`) refuses a `journalEntry` envelope with both `projectId` and `areaId` on field `area` (code `derivedRelation`); it is called from `assertValidJournalEntryEnvelope`, which `assertValidProposalEnvelope` delegates to.
- Because every writer reaches `assertValidProposalEnvelope`, the tick, revise, the edit route and confirm refuse it the same way (the tick records `needsClarification`, revise and the edit route leave the card unchanged, confirm writes nothing).

## Entry points and contracts dependents build on

- `assertNoDerivedRelations` from `packages/data/src/inbox/proposalDerivedRelations.ts` and `assertJournalEntryAreaNotDerived` from `inbox/journalEntryEnvelope.ts` (neither is in the package barrel).
- Contract: an Event with a company or area, or a File with an area, is refused when its project is set; the same relation without a project (absent or empty) is valid. A journalEntry envelope never stores both `projectId` and `areaId`. A future derived relation is guarded by adding it to `GUARDED_DERIVED_VALUE_SOURCES`; no change here is needed.
- Error shape: `ValidationError`, status 400, `details.field` the relation key (or `area`), `details.code` `derivedRelation`.
- No new route, operation, table, migration or job name.

## Deviations from the specification and spec seams

1. Spec seam: `inboxTickAction.ts` is at the 900-line cap, so `assertNoDerivedRelations` lives in the sibling `proposalDerivedRelations.ts` and the journal rule is called from `assertValidJournalEntryEnvelope` instead of inline in `assertValidProposalEnvelope`.
2. The signature is `assertNoDerivedRelations(targetDatabase, envelope)` without the client argument the Task lists: the rule is the exported table matched on the database key, so no query is needed. The choke point's own `assertNotDerivedValueWrite` works on an existing item's edges and cannot be reused for an envelope.
3. Only the top-level `relations` of a database envelope are checked, as the Task says; relations inside the steps of a multi-step envelope are not (documented in the docstring).
4. Existing tests changed: gh-1975's "accepts an area, a project, and both" lost its "both" case, and gh-1981's confirm test "writes only the project edge when the envelope names both" became "is refused at confirm for a card that already holds it". The defensive both-ids branch of `confirmJournalEntry` (`journalEntryConfirm.ts`) is now unreachable through validation and was left untouched (outside this Task).
5. The edit route has no editable fields for a journalEntry card (`proposalOverrides.ts` refuses `areaId` as "has no field"), so the journal rule is exercised through the tick write, revise and confirm; the edit route is exercised with Event cards.
