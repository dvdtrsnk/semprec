## What was delivered

Confirming an Inbox card that creates an MCP server now queues the load of its tools.

- Core task `mcpServerSync` (`CORE_TASK_NAMES.MCP_SERVER_SYNC`), runtime affinity `api`, tenancy `tenant` (`TASK_TENANCY` in `packages/queue/src/index.ts`), tenants task lane unchanged, no queue lane. Payload `{ mcpServerItemId, actingUserId }`, both validated with `requireString` in `createCoreTaskList` (`packages/data/src/worker.ts`). Job key `mcp-server-sync-<mcpServerItemId>`, `maxAttempts` 1, so a second enqueue for the same server collapses onto the pending job and a failed sync is not retried by the queue.
- `enqueueMcpServerSync(client, payload)`, `mcpServerSyncJobKey(id)`, `handleMcpServerSyncTask(pool, payload)` and the type `McpServerSyncPayload` in `mcp/mcpSync.ts`, exported through the data barrel. The handler runs `syncMcpServerTools` as `actingUserId` and swallows `McpConnectionError`, the tool-list `ValidationError` and `NotFoundError` (the sync has already recorded `syncStatus: error` with a safe message, or the item is gone or in the Trash); any other error reaches the queue, which does not retry it.
- `confirmProposalWithClient` enqueues the job on the confirm's own client after the item and the optional credential are written, when the target database is the MCP servers database and an acting user is known. The job exists exactly when the confirm commits. The results entry of the created server stores `followUp: "mcpSyncQueued"` in the same transaction; a replay of an already confirmed card returns the stored results and enqueues nothing. A confirm without an acting user enqueues nothing and reports `followUp: null`.
- The payload carries no credential: the sync reads the stored credential at connect time and logs the access in `credential_access_log` with `actingUserId` as actor.

1. `TASK_TENANCY` in `packages/queue/src/index.ts` is a required record over `CORE_TASK_NAMES`, so `MCP_SERVER_SYNC` got a `tenant` entry beyond the two lists the Task names.
2. `confirmProposalWithClient` already took `actingUserId` and the route handler already passed it, so no signature or route change was needed.

6. A failure of `syncMcpServerTools` to record `syncStatus: error` (logged by the sync) is also swallowed when the error type is one of the swallowed types, because the Task defines the swallow by type; changing the sync is out of scope.
7. At the merge: the line-cap repairs and the `followUp` conditional described above.
8. `mcpSync.test.ts`: the first describe's `pool.end` afterAll moved to a file-level afterAll; payload assertions read `graphile_worker._private_jobs` because the public jobs view has no payload column.
