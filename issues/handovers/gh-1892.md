## What was delivered

- Route `PATCH /api/proposals/:id/values`, body `{ set: { <ref>: { <propertyKey>: value } }, ifVersion?: string }`. It edits the manual values of an Inbox proposal card: it locks the card, checks status and `ifVersion`, merges `set` into the stored `userOverrides` (a value set back to the assistant's value is dropped), composes the effective envelope, validates it, and writes `proposal` (effective envelope), `userOverrides`, `userEditedKeys`, `status: proposed`, a cleared `invalidReason` for an invalid card, a `userEdit` history entry listing the keys, and a materialized `aiProposal` for legacy rows, in one `updateItemWithClient` call.
- Refusals, all before any write: a card that is confirmed, rejected, computing, computeFailed, locked, or invalid with `invalidReason.code` `sourceDeleted` (ValidationError); a card without an envelope; an empty `set`; an unknown ref or key (naming it); a credential key or a stdio connection config on an MCP server target; a stale `ifVersion` (ConflictError, `409 version_conflict`, current card in `details.currentItem`); and, from the review fix, any ref of `set` that the active-step selection skips (a disabled step, or an optional step no active step refers to), as a ValidationError naming `{ref, field}`.
- The generic `PATCH /api/items/:id` of `proposal`, `status` and `history` still answers 403.
