# gh-1716 implementation handover

Implementation base: `b30d3d392367cd5dda03eb5c47dce63f73781900`.
Blocked by gh-1659 (item origins).

## What changed

- `inbox/itemOriginsStore.ts`: new `withFromInbox(client, items)`. One statement
  (`item_id = ANY($1::uuid[]) AND capture_channel = 'inbox'`, tenant-scoped by row-level security) per page;
  an empty page issues no query. Returns the items with `fromInbox: boolean`.
- `chokePoint/itemReads.ts`: `getItem`, `findItem` and `listItems` stamp the flag.
  `findItemIncludingDeleted` (trash and restore routes) and `getItemPath` do not.
- `chokePoint/viewQueryOps.ts`: `queryView`, `queryDatabaseItems` and `queryViewItems` stamp every result
  page, including curated views.
- `ItemRow` (data) and `Item` (shared) gain an optional `fromInbox?: boolean`. It is optional because write
  results (create, update, restore) are not read results and do not carry it; reads always set it.
  Existing fields and ordering are unchanged. No schema change.

## Tests

New `itemFromInbox.test.ts`: a query with one Inbox-origin and one hand-created item returns true and false;
`findItem`, `getItem` and `listItems` carry the flag; a `transcript` origin and a deleted origin row give
false; the lookup issues exactly one query for 1 or 50 ids and none for an empty page, and a 50-row query
page flags the right 25. Two existing tests that deep-compared a `getItem` result (`itemWrites.test.ts`,
`genericOperationGateway.test.ts`) now expect `fromInbox: false`.
`mcpConnectionFactory` and `tenantIdColumn` fail in the data suite for reasons unrelated to this change.

## Notes for dependants

- Clients should treat the field as optional: write responses omit it.
- `GET /api/items/:id/origin` (#1967) is the place for full origin details; this flag is only the boolean.
- Undo of a confirmation (#1943) removing the origin row makes the flag false with no further change.
