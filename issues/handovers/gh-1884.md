## What was delivered

- A new timeline source `taskTraces` (`calendar/timelineTaskTraceSource.ts`, function `readTaskTraceTimelineItems`), registered last in `CALENDAR_TIMELINE_SOURCES`. `GET /api/calendar/timeline` now returns, for a Task with a stored `since`, one read-only derived entry per past day from `since` up to the day before the live day (`taskDisplayDay`) and before today, clipped to the requested range: `{ kind: "trace", id: "trace:<taskId>:<day>", taskId, day, firstDay, sinceTime, outcome, readOnly: true }`.
- `firstDay` is the stored `since` and is returned in full even when the first day lies outside the range. `sinceTime` (`{from, to}`) is set on the first-day trace only and is null on the others.
- `outcome` is a property of the Task's end state and is the same on every trace of the Task. Precedence: `doneOn` `{date}` (from `completedOn`) over `missed` over `movedToEvent` `{id, title}` (the host event the Task was added to last) over `carried`.
- The live Task entry carries `carriedFrom` (the stored `since`) unless the Task is done on a day before today.
- A Task completed before its planned day is shown as done on its completion day; its day chain ends on the completion day (the live day comes from `taskDisplayDay`, not from the planned date).

## Entry points and contracts dependents build on

- Source module `calendar/timelineTaskTraceSource.ts`, one entry in `CALENDAR_TIMELINE_SOURCES` after `eventOccurrences`. Its order is the registration order; gh-1886 (recurring occurrence expansion) should register its source after this one.

- `timelineRead.ts` `sortKey` places a trace by its `day` with the Tasks (all-day group before the timed group, by `sinceTime.from`).
- Routes, operations, tables and jobs: none added. The agenda and the journal day read ignore the new kind; the compact shape returns traces as they are (no `carriedFrom` in the compact shape).
- Reads only, a fixed number of statements (database lookup, one candidate query, one host-event lookup), under the caller's runtime-role tenant scope.

## Deviations from the specification and spec seams

1. The Task says the types go in the shared timeline contract file that #1717 creates; no such file exists in `backend/packages/shared/src`, so the types were added to `calendar/timelineSources.ts`.
2. The carry-over part is a new source module registered in `CALENDAR_TIMELINE_SOURCES` (decision 2 of ADR 2026-11-10 on the timeline sources), plus `carriedFrom` in `readTaskTimelineItems`.
3. The display-day SQL expression moved to `tasks/taskDisplayDaySql.ts` (a leaf module, to avoid an import cycle with `timelineRead.ts`), and two helpers of `timelineTaskInEvent.ts` are exported.
4. Interpretations: traces are past days only (the last trace is yesterday at the latest), so a Task moved to a future day has no trace for the days between today and its live day; a `wontDo` Task has no traces (it has no live entry either); a done Task without a valid `completedOn` is left out with a warn log; the rule that a recurring occurrence is carried at most until the day before its next occurrence holds without extra code, because the live day of an occurrence is its `occurrenceDate`; trace entries carry `id` and `readOnly` (the derived-entry contract of ADR 2026-11-10) in addition to the fields the Task names.
5. No ADR was added.
