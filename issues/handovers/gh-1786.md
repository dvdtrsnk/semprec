## What was delivered

- `GET /api/approval-requests/:id`: returns the request through `getApprovalRequestForOwner` and `toApprovalRequestDecisionView`, which is the view the PATCH answers (it already carries `source` and `riskClass` since gh-1766; no payload). An unknown id, a foreign request and an id of another tenant answer one identical 404 body (the existing not-found body); a malformed id is 400 `validation_failed` naming `id`, as PATCH does.
- `GET /api/approval-requests/count`: returns `{ count }` for the owner. `status` accepts only `pending` (absent means pending); `source` is an optional comma list of `chat`, `tick`, `mcp` (duplicates collapse); an unknown value, an unknown status or a repeated parameter is 400 naming the field. A method other than GET on the count path is 404 and makes no decision.
- The literal count path is served before the `:id` pattern, so it is never read as an id. `app.ts` already forwards the whole `/api/approval-requests/` prefix and was not changed.
- `countPendingApprovalRequests(client, { ownerUserId, sourceKinds })` in `packages/data/src/mcp/approvalRequestsStore.ts`: one SQL statement that shares the source-derivation fragments (`sourceJoinSql`, `SOURCE_KIND_SQL`) and the pending predicate (`LIST_STATUS_SQL.pending.predicate`) with `listApprovalRequestsPage`, so the count equals the number of rows the list returns over all pages for the same filter. The source SQL of the list was extracted into those shared fragments with no change of behaviour.
