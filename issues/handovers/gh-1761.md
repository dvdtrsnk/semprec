Candidate commit `fea3a22f1899b2bf706626a46f076ebca2916df2` landed on `feature/backend-parallel` with merge `c2eb4421859df3fa27daf24bb0f1db906c8e3379` (chain `e1-028-calendar`, second of its two members; gh-1757 is the first). The chain landed alone, not as part of a train. The acceptance receipt is `issues/batches/backend/acceptance/sources/gh-1761.md`.

Declared blocker: gh-1757, which the text of gh-1761 marks as `Shared-file ordering`. It is the earlier member of this chain and was completed in the same landing (`issues/handovers/gh-1757.md`). No blocker of this source was open at landing.

**Every Event create now writes one more edge, and one existing public path changed.** A new Event of a tenant that has calendars always has a `calendar` edge when its create commits. An `item.create` for an Event whose `relations` name a calendar other than the default is refused with `409 cardinality_violation` and stores no Event, until gh-1777 changes the order of that path. Both are described below.

## What was delivered

- `defaultCalendarCreateHook` (`backend/packages/data/src/calendar/defaultCalendarCreateHook.ts`), an item create hook, registered as the last entry of `backend/packages/data/src/domainWriteHooks.ts`. It acts on a new item of the tenant's system Events database and returns at once for any other database. It runs inside the create's transaction after a real insert and not on an idempotency-key replay.
- What it does for a new Event:
  - The tenant has no calendars database: it writes nothing, and a chosen calendar is not checked.
  - The Event already has a `calendar` edge when the hook runs: it writes nothing; that edge wins, and a chosen calendar is not checked.
  - Otherwise it writes one edge of `Events.calendar`, to the calendar chosen with `withChosenCalendar` or, without a choice, to the live calendar whose `isDefault` is true. Should several be marked, the lowest id is taken, as the calendars cutover does.
- The edge is written with `createRelationWithClient` without a writer, so as a system write, whoever created the Event. It runs that write's guards, the cardinality trigger, the edge hooks, the rollup enqueue and the invalidation, and it commits or rolls back with the Event.
- The chosen calendar must be a live item of the tenant's calendars database whose `kind` is absent, null, empty or `own`. An id that is not a UUID, an unknown id, another tenant's calendar, a calendar in the trash and a system or subscription calendar are all refused with the same `ValidationError` (`validation_failed`, `field: "calendarId"`), and no Event is stored.
- A calendars database without a live default calendar fails a create that takes the default with a plain error (a transport answers 500) after the error log line `default_calendar_missing`, which carries the calendars database id and the Event id. A create with a chosen calendar and a create whose Event already has a calendar edge do not read the default. A calendars database without the `Events.calendar` relation fails the create with a plain error in every case.
- Locks. The chosen calendar and the calendars marked default are read `FOR SHARE` in the create's transaction. The default read runs a second time when the first returns nothing, for a default mark that moved while the read waited.
- `withChosenCalendar(calendarId, fn)`: an `AsyncLocalStorage` scope private to the hook's module. `createEventInCalendar(client, input, calendarId, options?)`: resolves the tenant's Events database, runs `createItemWithClient` inside the scope and returns the item row; it throws `NotFoundError` in a tenant without an Events database.
- `createEventInCalendar` is exported from `backend/packages/data/src/index.ts` and is in the frozen export list. `withChosenCalendar` and the hook are exported from their file only.
- ADR `docs/adr/2026-11-11-new-events-get-their-calendar-in-a-create-hook.md` (accepted, backend): the hook, the system write, the async scope, the check in the hook, the row locks and the consequences.
- No migration, table, column, route, generic operation, job name, tenant cutover entry, module manifest entry, stored key or i18n key was added.

## Contracts dependents build on

- gh-1944 and gh-1777 create an Event in a chosen calendar with `createEventInCalendar` from `@semprec/data`, inside their own transaction. The refusal reaches them as a thrown `ValidationError` with `details.field` `calendarId` (status 400, code `validation_failed`). No HTTP route calls the helper yet.
- An idempotency-key replay of `createEventInCalendar` returns the Event stored earlier with the calendar it has; the calendar the replay names is not checked.
- `withChosenCalendar` is ambient: every Event inserted inside `fn` takes the chosen calendar. A caller keeps `fn` to the one create.
- **`item.create` with relations (gh-1590) and the Inbox proposal confirm write their relations after the create hooks.** An Event create whose `relations` name a calendar other than the default meets the edge the hook wrote and is refused with `409 cardinality_violation`; naming the default calendar succeeds with one edge. gh-1777 owns that order for the create path (its Task step 1). Its `Touches` do not name `inbox/proposalActions.ts`; the reviewers found no production trigger on the confirm path today.
- Each Event insert the hook links also inserts one edge of the `Calendars.events` definition and takes that definition's transaction-scoped advisory lock (migration `0013_relation_cardinality.sql`) until the create's transaction ends. Event creates of one tenant wait for each other from that insert on. The hook takes the calendar row lock before that advisory lock.
- Order in `domainWriteHooks.ts`: `registerItemCreateHook(defaultCalendarCreateHook)` is the last entry of the file, after `eventParticipantEdgeWriteHook` of gh-1757 and after every create hook that holds an Events rule. A later source that registers a create hook which must see the Event's calendar registers after it; one that writes a calendar edge itself registers before it.
- **For tests and fixtures of later sources:** an Event created through the choke point with the domain hooks registered has a calendar edge. A test that counts an Event's edges, jobs or invalidations after a create sees one more. A fixture that needs an Event without a calendar removes the edge with the single-valued relation set (`setRelation` with `targetItemId: null`), as `timelineRead.test.ts` does with its `setCalendar` helper.
- The single default calendar and the protection of system calendars are not guarded yet (gh-1778). Until then a user can mark a second calendar as default or leave none.
- A tenant whose calendars cutover has not run gets Events without a calendar; the next run of the cutover links them.

## Deviations from the specification and spec seams

- The chosen calendar is checked only when the hook writes the edge: not in a tenant without a calendars database, not when the Event already has a calendar edge and not on an idempotency-key replay.
- Not in the Task: the `FOR SHARE` reads of the chosen and of the default calendar, and the second default read.
- States the Task does not name: a calendars database without the Events `calendar` relation fails the create with a plain error; several live calendars marked default give the one with the lowest id.
- `createEventInCalendar` takes the create input without `databaseId`, resolves the Events database itself and throws `NotFoundError` when there is none.
- The Task test "an Event that already has a calendar edge before the hook runs keeps it" uses an earlier create hook as the first writer, because no production path writes a calendar edge before the create hooks run. The record's example "relations given at creation" does not hold in the code: those relations are written after the hooks (see "Contracts").
- Acceptance criterion 3 says "the response is 400". The 400 is asserted on the error `createEventInCalendar` throws (status 400, code `validation_failed`, `details.field` `calendarId`); no HTTP route calls the helper yet, so there is no HTTP response to assert.
- Files outside `Touches`: the ADR, `eventDefaultCalendarWritePaths.test.ts` under `services/semprec-api`, and the five existing test files brought in line.
