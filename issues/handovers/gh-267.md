## Summary

Fixes issue #267: two mail-code paths held an open PostgreSQL transaction across external I/O.

**`backend/packages/data/src/mail/mailSyncJob.ts`** — `handleSyncMailAccountTask` used to open one write transaction, and inside it call `imapConnectionLimiter.run(...)`, which can wait up to 3 minutes for a free IMAP connection slot while pinning a pooled database connection. This is now split into:
- a short, read-only prologue transaction for the schema/mailbox lookups,
- per-branch write transactions, with the IMAP branch's `imapConnectionLimiter.run(...)` wait now happening *outside* any transaction — the write transaction only opens once a slot is actually granted.

The `gmail_api`/`graph_api` branches keep the same one-transaction-per-pass structure, just rebuilt from the prologue's already-read ids.

**`backend/packages/data/src/migrationJob/mailLegacyEmailMigration.ts`** — `fetchRawMime` (an injected, potentially remote fetch) is now called before `withTransaction` opens rather than as the first statement inside it. `migrateLegacyItem` takes the already-fetched buffer. One transaction per item is preserved.

**Tests added** to `mailSync.test.ts`:
- A `Proxy`-based recording pool wrapper proving the migration's fetch always precedes its item's `BEGIN`.
- A pooled-connection-checkout test proving a sync pass queued behind a connection-limit slot holds zero extra database connections while waiting.

Both new tests were verified to fail against the pre-fix code and pass against the fix. Full backend build and test suite (24 files, 315 tests) pass.
