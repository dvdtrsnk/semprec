# gh-1849 handover: Let a user-attached context ref grant one-run read access

Delivered on the integration branch by merge `8e9060754800e2501ae07847ddf914a9eed38c92` of chain `e1-096-semprec-agents`, candidate `626a82158c9fa05f98ad2e561cb0f50b8f0692e8`. The chain landed alone; the gate ran on the merged tree.

## What was delivered

A Semp chat message that attaches an item (a ref of kind `item`, `block` or `transcriptSegment`) lets the agent of that run read that one item during that turn without a database grant, even when the item is in a sensitive or user-switched-off database. The allowance is read-only, per item, per run, and lives only for the turn.

- Migration `0155_agent_run_read_allowances.sql`: tenant table `agent_run_read_allowances` (`tenant_id`, `agent_run_id`, `item_id`, `created_at`). Primary key `(tenant_id, agent_run_id, item_id)`, composite foreign key to `agent_runs(tenant_id, id)` with `ON DELETE CASCADE`, `semprec:tenancy=tenant` comment, RESTRICTIVE `tenant_isolation` and PERMISSIVE `tenant_rows` policies, DML grant to `semprec_side` as for `agent_database_grants`. `item_id` has no foreign key (`items` is partitioned).
- `agentGrants/agentRunReadAllowancesStore.ts`: `allowItemsForTurn`, `clearForRun`, `isItemAllowed` (a `FOR SHARE` read).
- `assertAgentDatabaseAccess` takes an optional `readAllowance {agentRunId, itemId}`. Only for an access of kind `read` that the project's grants refused, it passes when the run holds an allowance row for that item. A write is never allowed by it.
- The read paths `findItem` (`chokePoint/itemReads.ts`) and the generic `item.get` (`genericApplicationService.ts`) pass the run id taken from the run credential.
- `services/semprec-agents/src/sempTurnReadAllowances.ts`: `readAllowedItemIds` (item ids from the persisted refs), `openTurnReadAllowances` (clear stale rows, insert), `closeTurnReadAllowances`. Wired in `sempMessageTask.ts`: `onTurnStart` opens the rows in the same transaction as `startSempMessageTurn`; the rows are cleared after the model turn and in the error path (a cleanup failure fails the turn, or joins the `AggregateError` with the original failure).
- The ref expander (`expandSempRefs`, `readSempRefContext`, `sempHistoryReconstruction.ts`) takes the Semprec project and lists related items of unreadable databases as `{ id, hidden: true }` instead of naming them.
- Review fix: `chokePoint.getValueLinksForItems` takes `agentProjectItemId`; a link source in a database the project cannot read is left out of `sources` (like a missing one). `view.query`, `item.get` and `database.query` with `include` links pass the writer's project. Derived values name only projects, areas and companies (open system databases) and need no filter.
- ADR `docs/adr/2026-11-13-a-user-attached-ref-grants-one-turn-read-access.md` records the allowance, its lifetime, the read-only rule, the value-link rule and the deviation from Task step 4.

## Tests

All seven evidence rows of the worker are PASS: the attached record is read in the turn without a grant and another record of the database is refused; the next turn without the ref is refused again; `item.patch` without a write grant is 403; no allowance row remains after a successful, failed or cancelled turn, nor after a crash leftover (cleared at the next turn start), including cleanup failures; relation targets in unreadable databases are `{ id, hidden: true }` (tool path and prompt path, history reconstruction, task trace and task occurrence refs); tenants and runs are isolated; which refs allow a read.

## Deviations and spec seams

- Task step 4 says the expander reads the item as the run's agent identity. For a waking turn the run row does not exist when the prompt is built, so the expander cannot use the run's rows. It reads the attached item because the user attached it, and filters related items by the Semprec project's access. The rows are opened in the `onTurnStart` hook, and the turn-end cleanup is in `sempMessageTask.ts` (no change to `agentRunTasks.ts`). Recorded in the ADR.
- Files outside Touches: `genericApplicationService.ts`, `itemReads.ts`, `sempRefReadContext.ts`, `sempHistoryReconstruction.ts`, `sempTurnReadAllowances.ts`, `chokePoint.ts`, `valueLinkReads.ts`, the ADR, and the `rowLevelSecurity`, `tenancyCatalog` and `publicSurface` inventories.
- Refs are accepted only on chat threads, so the project of the expander is always the Semprec project; there is no heartbeat-project branch.
- The test grant fixture writes `agent_database_grants` with SQL because `setAgentDatabaseGrant` is not exported from `testSupport` on this tree.
- Commit trailer: the one named in the task text.

## Follow-ups from review

- Other single-item read paths for agents (`getItem` by database, page reads) remain closed to the allowance; no caller needs them yet.
- A row left for a run that no later turn continues stays until the run is deleted (cascade); it is readable only by a call authenticated as that run, and the next turn of the run clears it.
- The medium finding (link-source titles) and the low finding (untested task trace and occurrence relation hiding) were fixed and the focused recheck passed; none is open.

## Note for chains that land after this one

`sempTurnReadAllowances.test.ts` (first case) reads the stored `tool_result` of `item_get` on a health record and expects the item title in it. A train attempt that merged chain `e1-097-agent-runtime` (gh-1827) before this one failed that case, because the stored result of a sensitive database is then redacted to `[redacted: sensitive]`. Each chain passes on its own base. The chain that lands second (gh-1827) must be checked against this test; the expectation has to read the live result or tolerate the redacted stored form.
