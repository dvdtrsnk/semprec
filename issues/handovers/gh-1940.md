## What was delivered

A user's instruction on a transcript card (a message-only revise of an Event card or a speaker card) now gives the instruction's history entry an id and enqueues the job `transcriptCardRecompute` in the same transaction. `semprec-transcribe` runs it on a new third runner for short model tasks: a repeatable-read snapshot, one gateway call (operation `transcript_card_recompute`, no project) outside any transaction, then one transaction that row-locks the card, re-checks lock status, answered marker and `aiVersion`, composes the answer with the user's manual values, validates it with `assertValidEnvelopeForCard` and writes `aiProposal`, `aiVersion`, `proposal`, `status` and a `threadRevision` entry. An unusable, role-switching, non-candidate or unsatisfiable answer leaves the card unchanged and adds an entry; a permanently failing run adds a "could not be applied" entry; a gateway budget refusal ends the job at once with that entry. A confirmed, rejected, trashed, source-deleted or other-kind card is never changed.

## Entry points and contracts dependents build on

- Job name `transcriptCardRecompute` (`CORE_TASK_NAMES.TRANSCRIPT_CARD_RECOMPUTE`, affinity `transcribe`, tenant lane, `maxAttempts` 3); payload `{ proposalId, instructionEntryId }` (`transcriptCardRecomputePayloadSchema`), job key `transcriptCardRecomputeJobKey`, `enqueueTranscriptCardRecompute` (`transcription/transcriptCardRecompute.ts`, exported by star export of the data barrel).
- Guarded read and write in `transcription/transcriptCardRecomputeStore.ts`: `readTranscriptCardRecomputeSnapshot`, `applyTranscriptCardRecompute` (outcome `applied | unchanged | discarded | skipped`), `recordTranscriptCardRecomputeFailure`, `TranscriptCardChangedError`.
- The message-only branch of the revise lives in `inbox/transcriptCardInstruction.ts` (`recordTranscriptCardInstruction`).
- `services/semprec-transcribe`: `createTranscriptCardRecomputeTask` (`transcriptCardRecompute.ts`), the pure request builder and answer parser `transcriptCardRecomputeRequest.ts`; `queueRuntime.ts` starts three runners of one slot, each with the task list of its own kind, and its start and stop logic handles any number of runners.
- Gateway operation `transcript_card_recompute` (project item id must be null; a project id answers 400).
- History entries may carry an optional `id` (the instruction entry) and `instructionEntryId` (on the answering `threadRevision` entry); an answer entry with the instruction's id marks the instruction answered for every outcome.
- ADR `docs/adr/2026-11-14-transcript-cards-are-recomputed-by-their-producer-on-instruction.md`; the Processing proposals manifest comment names the producer's post-creation write.

## Deviations from the specification and spec seams

1. The Task names no runner that exists (the #1624 runner holds only `transcriptionCreate`): a third runner (concurrency 1) for short model tasks was added.
2. History entries had no id, so `proposalHistory.ts` gained the optional `id` and `instructionEntryId`.
3. The guarded read and write sit in a sibling module to avoid an import cycle with `proposalActions.ts`; the message-only branch moved to `inbox/transcriptCardInstruction.ts` because `proposalActions.ts` and `index.ts` sit at the 900-line cap (`index.ts` uses `export *` lines; `publicSurface.test.ts` list updated).
4. The `responseSchema` lets `entityKind` and `target` be null (the model's "cannot be satisfied" answer), stored as unchanged.
5. "Only for a card whose status is not locked" is satisfied by the existing refusal that precedes the message-only branch; no extra check.
6. History entry messages are English literals; the model's reason (bounded to 300 characters) is the entry text for an applied change.
7. A gateway budget refusal ends the job at once; this is a small addition beyond the Task, judged consistent with it by the reviewer.
