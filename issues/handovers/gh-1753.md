# Handover for gh-1753

Graph mailboxes can send. `createGraphMailTransport` (`backend/packages/data/src/mail/graphTransport.ts`, new) is the `graph_api` transport, and `createMailTransportFactory` builds it from a new `graphOAuthClient` option. Nothing supplies that option from a composition root yet, so no production send goes through Graph until one does (#1896). I did not push or open a PR.

## What was added

- **`GraphRestClient`** (`graphRestClient.ts`):
  - `sendMime(raw)` posts the MIME to `POST /me/sendMail`, base64 encoded, with `Content-Type: text/plain`.
  - `createDraft(draft)` posts `POST /me/messages` with the subject, body, recipients, `internetMessageId` and `internetMessageHeaders`. It returns the draft id.
  - `createUploadSession(draftId, attachment)` posts `.../attachments/createUploadSession` and returns the upload URL. A URL that is not HTTPS is refused before any byte is sent to it.
  - `uploadChunk(uploadUrl, chunk, start, total)` PUTs one chunk with its `Content-Range`. It sends no bearer token, since the upload URL is pre-authenticated, and has a 120 s timeout.
  - `sendDraft(draftId)` posts `.../send`. `deleteMessage(id)` sends `DELETE`.
  - `GRAPH_SEND_MAIL_MAX_RAW_BYTES = 3_000_000`. Base64 turns 3 raw bytes into 4 characters, so this is the largest raw message whose request body fits 4 000 000 characters, the stricter reading of the 4 MB limit.
  - Every bearer write has a 30 s timeout and one failure classifier. A refusal that names an invalid recipient (searched in the first 4 096 bytes of the body) becomes `MailRecipientRejectedError`. A 400 or 401 becomes `MailReauthorizationRequiredError`. Any other status is a plain `Error` that names only the status.
  - A create response is read up to 32 MiB. A response over that fails the call rather than being parsed short.
- **`createGraphMailTransport`** (`graphTransport.ts`):
  - Each Graph request refreshes the token through `refreshAndPersistAccessToken`, with `MICROSOFT_TOKEN_URL`, purpose `graph_api_send` and no `scope`.
  - A raw message up to `GRAPH_SEND_MAIL_MAX_RAW_BYTES` goes through `sendMime`.
  - A larger one takes the draft path. It is parsed with `simpleParser(raw, { keepCidLinks: true })`, so inline `cid:` references stay intact. A message with no Message-ID, or with an empty attachment, is refused before any draft exists. Then the draft is created, each attachment gets an upload session and 5 MiB chunks, and the draft is sent.
  - Once the draft exists, any failure deletes it, best effort. A failed delete is logged with its error name and the draft id only, and the send's own error still propagates.
  - The MIME has no Bcc header, so the draft's `bccRecipients` are the envelope recipients that To and Cc do not name.
  - Both paths return `{}`. No provider message id is reported.
- **Factory** (`mailTransport.ts`): a `graph_api` branch. Without `graphOAuthClient` it throws `No Microsoft Graph OAuth client is configured for this composition root` before reading anything. The `providerThreadId` and `fetchImpl` docs now name the Graph transport too.
- **`smtpTransport.test.ts`**: the assertion "refuses a sync mode with no transport yet" used `graph_api`, which now has a transport. It now uses a value outside `SYNC_MODES`, which is the only way left to reach that guard.

They cover the request shape of each write, the recipient, 400 and 401 mapping, a plain error for 503, the create-response cap, non-JSON and id-less responses, the non-HTTPS upload URL, and the chunk `Content-Range` with no bearer token.
- `graphTransport.test.ts`: 16 tests in the integration tier, against the real test database and a fake Microsoft that enters through `fetchImpl`. The token endpoint rotates the refresh token on each refresh and accepts only the current one.
  - Acceptance: the sendMail path submits the MIME, and the Message-ID is in the bytes it submits. The draft path carries the Message-ID in `internetMessageId` and the reply headers, uploads in chunks with the expected `Content-Range` values, and sends the draft. A revoked token throws `MailReauthorizationRequiredError` and sends nothing. A failure after the draft deletes it.

## Decisions for the reviewer

1. **Bcc recipients are not delivered on the sendMail path.** Graph's sendMail takes MIME without an envelope, and the MIME carries no Bcc header. A message of at most 3 000 000 bytes therefore reaches To and Cc only, as far as I can tell from the MIME semantics. I have not verified this live. The draft path delivers bcc through `bccRecipients`. The Task routes by size alone, and I implemented that as written. Sending messages with bcc through the draft path would fix this. The Gmail transport (gh-1637) builds the same MIME without a Bcc header, and I did not check it live either.
2. **A timed-out send can delete the sent copy.** The Task says a failure after the draft exists deletes it. If `sendDraft` times out after Graph accepted the send, the draft is already sent, and `deleteMessage` then targets the sent item. I implemented the rule literally. #1896 should treat a send timeout as "delivery unknown" and not assume the draft still exists.
3. **400 maps to reauthorization.** As the Task says, every 400 or 401 becomes `MailReauthorizationRequiredError`, the same as the Gmail transport. A 400 that is not a recipient refusal, such as a malformed draft or a rejected `internetMessageHeaders` value, will mark the mailbox `needsReauthorization`.
4. **Not verified against live Graph.**
   - Graph accepting `internetMessageId`, `In-Reply-To` and `References` in `POST /me/messages`. If Graph refuses or drops any of them, the draft path does not keep the Message-ID, and a synced copy would not deduplicate.
   - The `ErrorInvalidRecipients` and "invalid recipient" wording, which I inferred and did not capture.
   - The 4 MB limit, the 320 KiB chunk multiple and the 5 MiB chunk size, which come from Microsoft's documentation as I read it.
5. **One token refresh per request.** As in the Gmail transport, each Graph request refreshes. A large send with N attachments therefore makes N+3 refreshes, each recorded in `credential_access_log` as `graph_api_send`, and rotates the refresh token that many times. Caching one token per send would be a possible follow-up.
6. **Empty and nameless attachments.** An empty attachment on the draft path is refused before the draft exists, because the chunk loop would write no bytes and Graph would never see it. A nameless attachment is uploaded as `attachment`.

## Notes for dependants

- **#1896 (send route):** build the transport through the factory and supply `graphOAuthClient`. The result is `{}`, so there is no provider message id to store. Ingest matches on the Message-ID. Map `MailRecipientRejectedError` and `MailReauthorizationRequiredError` to their statuses, and treat a timeout as "delivery unknown" (decision 2). `providerThreadId` is ignored, because Graph threads a reply from its headers.
- **Composition root:** `createMailSyncAdapters` (gh-1508) reads the Graph keys for sync, but nothing passes them to the mail transport factory. The send route must do that.
- **`GraphRestClient`:** the GET paths are unchanged, including the uncapped `response.json()` that the gh-1508 handover records as a known gap. The new write responses are capped as described above.
- **Gmail transport:** unchanged by this issue. Its gaps (the bcc note above, the 400 mapping and the uncapped success body) stay with gh-1637.
- In production the large path's MIME comes from `buildOutgoingMime`. The tests build theirs directly with nodemailer's composer, the same library.
