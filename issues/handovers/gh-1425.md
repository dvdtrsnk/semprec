# Handover for gh-1425

Adds the pure derivation of an Inbox card's canonical kind in `backend/packages/data/src/inbox/inboxCardKind.ts`. Nothing calls it yet; the card list route (#1807) is the first consumer.

- **API:** `InboxCardKind` declares the whole union. `deriveInboxCardKind({ kind, status, envelope, ownerModuleId })` returns `{ cardKind, baseKind }`. `deriveApprovalCardKind()` returns the approval pair. `transcriptCardRole` is now exported from `proposalActions.ts`.
- **Input contract for #1807:** `status` is the stored status, or `computing` / `computeFailed` for a card listed with its compute state. `ownerModuleId` is `databases.owner_module_id` of the target database for a `database` envelope. For a `pageContent` envelope it is the owner module of the database holding the target page (a Journal day page gives `journal`); pass `null` when unknown, which gives `page`.
- **Rules:** `needsClarification` gives `clarify`/`clarify`. `invalid` gives `invalid` with the baseKind taken from the envelope, or `invalid` when none exists. Any other status, `computing` and `computeFailed` included, resolves from the envelope, and a card without one is `clarify`/`clarify`. A transcript card is `speaker` (baseKind `speaker`) or `transcriptEvent` (baseKind `event`). An unknown module, unknown entity kind, or a `relation` envelope on an inbox card yields `cardKind` `clarify` with `baseKind` `page`, and never throws.
- **Not produced yet:** `journal` entry kind (#1975), `recording` (#1978), `mcp` (#1973), and the multi-step primary step (#1492). Those issues extend the same function.
- **Tests:** `inboxCardKind.unit.test.ts` is table-driven and has 19 cases, all passing. Lint, prettier and the data package typecheck pass.
