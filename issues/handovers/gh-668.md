## Summary

Fixes #668. Doc history rebaselines now pick their folded range by contiguous `update_id`, not by timestamp order. Before this change, an update that was never folded into a baseline could be deleted and lost from history for good.

### Root cause
`rebaselineDocHistory` replayed rows with `created_at <= cutoff` in `(created_at, update_id)` order. It then took the last row's id as `through_update_id` and deleted `update_id <= through_update_id`. `created_at` is the appending transaction's *start* time, but `update_id` is assigned at *insert*. When two appends overlap, the lower id can carry the later timestamp. If the cutoff falls between them, the lower-id row was deleted without being folded, and `openDocVersionAt` could never replay it.

### Changes
- **`backend/packages/data/src/docs/docHistory.ts`**
  - `rebaselineDocHistory` now replays every row after the checkpoint up to, but not including, the first row (in id order) whose `created_at` is past the cutoff. It orders by `update_id ASC`. `throughUpdateId` is the last replayed id, or the checkpoint's own boundary when nothing was replayed, so every row the delete removes has been folded. `represented_at` stays `cutoff`: rows past the gap with `created_at <= cutoff` are kept and replayed by `openDocVersionAt`, and because Yjs updates are commutative the state at `cutoff` is the same. The doc comment now states this boundary rule and why timestamp order can't be used.
  - `openDocVersionAt` replays in `update_id ASC` order only, and its doc comment is updated to match.
- **`backend/packages/data/src/docs/docHistoryCutoverMigration.ts`** (comment only): the `LOCK TABLE docs IN EXCLUSIVE MODE` comment now says what the lock really does. It serialises concurrent cutover runs and blocks inserts/updates of `docs` rows. It does not exclude appends to existing docs, which the one-time cutover tolerates.
- **`backend/packages/data/src/__tests__/docHistoryRetention.test.ts`** (new, integration tier):
  - **Id-contiguous updates before the cutoff:** they are folded into the new baseline (`through_update_id` = the folded id) and deleted, and the later row is kept, as before.
  - **Inverted order across the cutoff** (lower id has the later timestamp): neither history row is deleted, the new baseline's `through_update_id` stays at the checkpoint boundary (`0`), and `openDocVersionAt(now)` rebuilds both edits.

  The task describes inserting the two rows with ids 10 and 11. Instead, the tests create both updates with real `putBlock` appends so the Yjs payloads are valid, then rewrite their `created_at` in `doc_updates` and `doc_history_updates` to produce the same inverted order.

Out of scope and not done: deleting by `expires_at`, and sibling issues C14 and C2.
