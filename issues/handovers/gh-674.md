## Why

`ingestEmailMessage` deduplicated on the RFC 5322 `Message-ID` alone. That id is global, so a message delivered to two mailboxes (a CC to a work and a private address, say) turned into one item linked to folders of both. Its `read`/`flagged` state and its pending IMAP flag writes were shared too. Marking it read in mailbox A wrote `\Seen` to its copy in mailbox B.

## Changes

  - Backfills existing rows through the message's `Emails.folder` edge and that folder's `Mailboxes.folders` edge. Both relation definitions are found by property key on the database the module owns. ## Decision for review: index column order

The issue's DDL gives the index as `(mailbox_item_id, message_id)`; I created it as **`(message_id, mailbox_item_id)`**.
- **Why:** dropping `UNIQUE (message_id)` removes the only index on `message_id`. `threading.ts` looks up `message_id = ANY(...)`, and the legacy collision check also looks up by `message_id` alone. Putting `message_id` first keeps both indexed.
- **Effect on uniqueness:** none. The upsert's `ON CONFLICT (mailbox_item_id, message_id)` still matches this index, because Postgres matches the conflict target by the set of columns, not their order.

## Breaking change: fix-forward only

This is the breaking change the issue's Task explicitly calls for. The migration file carries an `-- expand-contract-exemption:` line saying so.
- **Why it breaks rollback:** `UNIQUE (message_id)` has to be dropped in the same release, or two rows with one `message_id` could not exist. After this release, the previous release's `ON CONFLICT (message_id)` has no unique index to target.
- **Consequence:** a `deploy.sh --rollback` past this migration would break mail ingest, so this release can only be fixed forward.
- **Deferred:** `NOT NULL` on `mailbox_item_id` is a later cleanup step and is not in this PR.
