Repository-Issue: gh-1500

## Delivered behavior

- The typed path remains; untyped sources pass the locked-card and fingerprint gates before entering recognition. Empty source text makes no model call; attachment extraction remains deferred.
- Recognition uses v2 with empty source type id, preserving date/time/attachment hashes and empty transcribedText. Existing v1 values still compare with empty emoji. Recognition output never enters the source fingerprint.
- The request includes recognition mode and the valid active type catalog. The production computation asks for ranked candidates and the proposal in one gateway call. Invalid type ids, unsupported direct keys and invalid confidences are dropped, and valid candidates are ranked by confidence.
- The tick revalidates the active catalog on return. At the single 0.7 threshold it builds the typed-style or direct-target envelope and writes recognizedTypeId and an empty candidate list, without writing Inbox.type.
- Below threshold it writes needsClarification, no proposal, null recognizedTypeId and at most four distinct valid type choices, padding toward two. Catalogs with zero/one valid types offer only those types. Localized catalog entries explain the shortage and provide a fallback reason.
- Both outcomes store the source fingerprint. The shared stale-source check compares source edge identity and source fingerprint rather than the recognized output; a change after the call discards the result. Existing proposal locking/version checks also guard clarification writes.
- Extracted snapshot/envelope construction and source identity helpers, and moved existing step-validation helpers into proposalEnvelopeValidation, to preserve the action's enforced max-lines limit. Public tick type re-exports remain. Updated the frozen public export list for the provider's shared recognition filter and targets.
