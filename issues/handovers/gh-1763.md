## What was delivered

- `hostItemDeleteHook` and `hostItemRestoreHook` in `backend/packages/data/src/docs/pageTrash.ts`, registered in `domainWriteHooks.ts` with `registerItemDeleteHook` and `registerItemRestoreHook` for every database. Both act on a row of any database except the tenant's Pages system database (`system` and owner module id `pages`), whose rows stay with `pageItemDeleteHook` and `pageItemRestoreHook`. They sit after the `defaultCalendarCreateHook` registration (gh-1761) and before the gh-1778 calendar registrations.
- Delete: the hook sends no statement for a Pages item, one read for a tenant without a Pages database, and two reads and no write for a host without live subpages. Otherwise it selects the live Pages items whose `parentItemId` is the row and locks them `FOR UPDATE` in one statement in id order, reads the row's own deletion epoch at full precision with `itemsStore.lockItemTrashEpoch` and trashes each subpage in id order through `itemDeleteWithClient` with that value as `deletedAtExact`, the host's writer kind, agent fields, acting user and queue routing. A host whose trash joined an earlier epoch (the mailbox removal job) therefore gives its subpages that epoch.
- Restore: the hook selects the Pages items whose `parentItemId` is the row and whose `deleted_at` equals the hook's `deletedAtExact` (compared by Postgres), locks them `FOR UPDATE` in id order and restores each through `restoreItemWithClient` in descending id order. A subpage trashed on its own at another instant stays in the Trash.
- Fix of the review round: `pageItemDeleteHook` now reads the page's own epoch with `lockItemTrashEpoch` when the page has live subpages and passes it as `deletedAtExact` to the nested trash of each, so the pages below a subpage keep the host's epoch at every depth and the restore of a subpage finds them. A page without live subpages makes no extra read; a page with subpages and no deletion epoch throws instead of trashing the tree with a wrong time.
- New ADR `docs/adr/2026-11-12-a-trashed-host-takes-its-subpages-into-its-deletion-epoch.md` (epoch rule, lock order, writer routing, rejected alternatives).

## Deviations from the specification and spec seams

1. The delete hook passes the host's exact deletion epoch (`lockItemTrashEpoch`) as `deletedAtExact`, not the transaction's `now()`, so subpages join a host trash that itself joined an earlier epoch. Recorded in the new ADR. The restore hook compares with `context.deletedAtExact` where the Task says `deletedAt`, the more exact form of the same rule.
2. Existing tests that built a live page under a trashed host now restore the page on its own first, because a host trash now takes the page with it; the intent of each test is kept.
3. `pageTitleMirrorJob.ts` only had a lock-order comment updated.
4. The chain began from `851263340`; the integration tip had advanced and was merged at landing (no conflict).
5. The segment was begun by an earlier interrupted run of the worker; a later run re-verified it and committed it.

## Review

Three reviewers read the segment read-only: requirements and tests (one medium finding), project rules (one medium finding, the same defect) and security (clear). Both findings said the pages below a subpage did not join the host's epoch when the host's trash joined an earlier one, so the host's restore stranded them in the Trash. The fixer confirmed it and fixed both in `de5701963` (see above), with a joined-epoch test that now has a nested page and a page below it; the new tests fail on the old code. The recheck passed with no unresolved finding and no new one.

Follow-ups, none of them a finding: none recorded by the recheck. The ADR keeps the decision that no index is added for the lookup by `parentItemId` because a tenant's Pages partition is small; revisit if the delete path of a host shows in profiles.
