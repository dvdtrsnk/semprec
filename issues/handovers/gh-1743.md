## What was delivered

- For the match step and for the confirm of a pairing card, a transcript's `event` edge to an Event in the Trash is no link. The edge itself still stays stored while the Event is in the Trash, as before; the cardinality trigger is unchanged and still counts it.
- New module `backend/packages/data/src/transcription/transcriptEventEdges.ts` with two functions:
  - `readTranscriptEventEdges(client, eventRelationDefinitionId, transcriptId)` returns `{ liveEventIds, trashedEventIds }`. Each Event at the other end of the transcript's `event` edges is read without a lock first. An Event that reads as live is live and is not locked. An Event that reads as trashed is locked `FOR SHARE` and read again through `itemsStore.lockItemTrashEpoch`; if it is still in the Trash it is trashed. If the lock returns no trash epoch the row is read once more with `itemsStore.getItemById`: a row that is there was restored in between and is live, a row that is gone was purged and the Event is in neither list.
  - `releaseTrashedEventEdges(client, { eventPropertyId, transcriptId }, writer?, actingUserId?)` calls `readTranscriptEventEdges` and deletes the edge to every trashed Event through `deleteRelationWithClient` on the caller's client. An edge to a live Event is left alone. A delete that finds nothing, because another transaction removed the edge after the read, is not an error.
- `matchTranscriptToEvent` (`transcription/transcriptEventMatch.ts`) returns `alreadyLinked` only when `liveEventIds` is not empty. When it links its one candidate it calls `releaseTrashedEventEdges` first, in the same transaction, as the `system` writer. When it creates the pairing card instead (zero or several candidates) it deletes nothing and the edge to the trashed Event stays stored.
- `confirmProposalWithClient` (`inbox/proposalActions.ts`) calls the local helper `releaseTrashedEventOfPairingCard` right before a transcript card writes its edge, in both shapes: the `database` envelope that creates the Event and the `relation` envelope that links an existing one. The helper returns for any card whose role is not `event`, so a speaker card removes nothing. The removal is written as the confirming user (`CONFIRMING_USER_WRITER` with `actingUserId`) in the confirm's transaction.
- The removal runs the hooks and announcements of any edge removal. The release hook of gh-1697 (`transcriptCompanyLinkReleaseEdgeChangedHook`) therefore ends a `company` link the transcript got after the trash, for example from a project chosen by hand; the company stays as an own value. After the commit the removed edge is announced as a relation `delete` for the trashed Event's `transcript` key and the new edge as a `put` for the transcript's `event` key, both with the acting user's id in the confirm.
- The generic relation write is unchanged: `createRelationWithClient` behind `PUT /api/items/:id/relations/:propertyKey/:targetItemId` and behind `relation.put` still answers 409 `cardinality_violation` for a transcript whose Event is in the Trash, from either side.
- The first acceptance criterion (the transcript keeps its project, company and people as own values, and a restore reconnects nothing) is behaviour of gh-1656 and gh-1697. This source adds no code for it, only the test that proves it in the whole sequence.
- New ADR `docs/adr/2026-11-11-an-edge-to-a-trashed-event-is-no-link-for-the-match-and-a-pairing-card.md` (accepted, area backend): the rule, the lock, the purge case, the one added write of `semprec-transcribe`, and the narrowed consequence of `2026-11-10-transcription-create-writes-the-uploads-event`. No accepted ADR was edited.
- `services/semprec-transcribe/src/transcriptionTask.ts`: the docstring of `runMatchStep` only.
- No migration, no table, no column, no route, no generic operation, no job name, no hook registration, no tenant cutover entry, no export from the data barrel and no i18n key was added.

## Contracts dependents build on

- Exports of `backend/packages/data/src/transcription/transcriptEventEdges.ts`, from the module only (not from `backend/packages/data/src/index.ts`): the interface `TranscriptEventEdges`, `readTranscriptEventEdges` and `releaseTrashedEventEdges`. Its two importers are `transcriptEventMatch.ts` and `inbox/proposalActions.ts`.
- Lock contract of `readTranscriptEventEdges`: every Event in `trashedEventIds` is locked `FOR SHARE` until the caller's transaction ends, so a restore or a purge of that Event (both lock the row `FOR UPDATE`) waits for the caller. A live Event is not locked. A caller has to run it in the transaction that acts on the answer. The match holds the transcript's row lock when it takes the share lock, the confirm holds its card's row lock; both run at READ COMMITTED.
- `TranscriptEventMatchOutcome` is unchanged in shape. `alreadyLinked` now means an edge to an Event that is not in the Trash. A transcript whose only edge is to a trashed Event gets `linked` (the stale edge is replaced), `suggested` (a pairing card; the stale edge stays) or `alreadySuggested`.
- While a transcript has only its pairing card, the edge to the trashed Event is still stored. A reader that needs the transcript's Event has to leave out an Event in the Trash, as the match does. The ADR states this as a consequence.
- After a replacement, a restore of the first Event brings no edge back: the Event is restored without that transcript.
- `semprec-transcribe` now makes one more write than `2026-09-23-transcription-worker-writes-event-match-results` names: the removal of its transcript's `event` edge to a trashed Event, directly before the edge the match writes.
- gh-1748 names this source as a `Shared-file ordering` blocker in its text (both edit `inbox/proposalActions.ts`); that record is closed as not planned. No open record declares gh-1743 as a blocker.
- The worker reports `inbox/proposalActions.ts` as near the cap of the lint rule `max-lines` (900 counted lines) and put the shared logic in the new module for that reason. The file has 870 lines in all, and lint passed on the merged tree.

## Review

Three reviewers read `78d323302^..78d323302` read-only: requirements and tests (one low finding, all four acceptance criteria rated covered), project rules and architecture (one low finding) and security (clear, no finding). Both findings were fixed in the fix round:

1. Low, requirements: the two-tenant test read tenant B's transcript through tenant A's relation definition, so its read assertion passed with or without row-level security. Fixed in `58a13c1e6`: the test reads tenant B's edge with tenant B's definition and transcript, inside tenant B (the row exists) and inside tenant A (no edge).
2. Low, rules: an Event purged while the match reads it was counted as live, so the match answered `alreadyLinked` for a transcript with no edge left. Fixed in `d179afe83` as described above, with three tests under "against a purge of the trashed Event".

No recheck followed. The security reviewer's sentence that an Event which is not visible or not found is classified as live describes `78d323302`; at the candidate such an Event is in neither list. Nothing is deleted for it either way, because the removal uses `trashedEventIds` only.

Follow-ups, none of them changed by this source:

- The confirm of a speaker card for a transcript whose Event is in the Trash fails with `validation_failed` (`details.field` `callerItemId`): the speaker step of `confirmProposalWithClient` reads the transcript's event edge without leaving out a trashed Event and then tries to write that Event's `people` edge. The worker saw it in a scratch run that was not committed, and both reviewers read it in the code. It predates this source, whose Task names pairing cards only. No source covers it yet.
- `assertRelationTargetLinkableWithClient`, used for the relations of a `database` proposal envelope (for example `Events.transcript`), still counts an edge to a trashed Event as the transcript's one edge. Read in the code by the worker, not run.
- The match step does not run for a transcript whose status is `done` (issue #1712), so a finished transcript without a pairing card gets no other Event through this source. Read in the code by the worker, not run.
- Wording of the new ADR, noted by the requirements reviewer: "The edge stays until the card's confirm replaces it or the Event is restored" is loose. A restore does not remove the edge, and a user's `DELETE` of the edge or a purge of the Event also ends it.
- The generic relation write still refuses another Event for such a transcript. An explicit "assign to event" action is a product decision that has not been made.
