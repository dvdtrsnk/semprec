# gh-1517 — Related collection order in module manifests

Repository-Issue: gh-1517
Implementation commit: `2fb05fc9a231074413cac5f804d6ca12f3ad398f`.

## Delivered behavior

- Adds the optional relatedOrder descriptor with required order and optional omit arrays. The schema requires non-empty keys and rejects duplicates within either list and across them. The exported ModuleRelatedOrderDescriptor type is shared by the descriptor and registry projection.
- getDatabases returns a detached copy of each full declaration. getRelatedOrder(databaseKey) resolves against the current active database projection: unknown/inactive keys disappear from both lists, omitted omit resolves to [], and an undeclared, unknown or inactive source database returns undefined. Declared empty order remains distinguishable from no declaration. Returned arrays cannot mutate the registry's declaration.
- Areas, Projects and People declare the exact corrected lists. Projects omits Tasks; People keeps Tasks second. Areas omits Journal and lists Books/Movies but no recipes. Existing constants are used except the expressly future threads key. The manifest version remains 1.2.0: no test versions manifest content, so Task 3's conditional bump is not needed.
- The accessor applies no fallback sorting and computes no related rows; those belong to the consumer issue.

## Decision applied

Decision issues/decisions/gh-1517.md, commit 1d802cbb, resolves the original overlap contradiction. This implementation follows variant (a): tasks is absent from projects.order and retained in projects.omit, while people.order explicitly retains tasks. Duplicate rejection is preserved without an omit-precedence exception. No additional spec decision was needed.
