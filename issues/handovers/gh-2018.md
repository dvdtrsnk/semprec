# gh-2018 handover: Let Semp chat runs read the heartbeats of every project

Delivered on the integration branch by merge `4e45eed9f9e4279a2da653de45bb051db86752c0` of chain `e1-098-scheduler`, candidate `49cde4e5496ccb7975cf55f29bac423197aeef15`.

## What was delivered

`heartbeat.list` and `heartbeat.history` now resolve a read scope from the calling run's persisted `agent_runs.project_item_id` and `agent_runs.thread_id` (`resolveHeartbeatReadScope` in `backend/packages/data/src/scheduler/heartbeatAgentTools.ts`). A run whose thread is a Semp thread of kind `chat` (a delegated run inherits the thread, gh-1452) reads the heartbeats of every project of the tenant, minus the projects excluded by the sensitive rule. Every other run (no thread, `item` thread, `tick` thread, heartbeat run) keeps its own project and the old entry shape. The project never comes from tool arguments. `heartbeat.trigger` is unchanged and stays own-project for chat runs too.

The sensitive rule: a heartbeat is left out when its project holds a `read` or `write` grant (`agent_database_grants`, gh-1810) on a database flagged `sensitive` and the calling run's project holds no `read`/`write` grant on that same database. A `none` row counts as no grant on either side; a grant on a non-sensitive database is not counted; the caller's own project is never excluded from itself.

## Entry points and contracts dependents build on

- `schedulerStore.ts`: `listHeartbeatsVisibleToChatRun(client, callingProjectItemId, moduleRuleKinds?)` (oldest first) and `getHeartbeatVisibleToChatRun(client, callingProjectItemId, heartbeatId, moduleRuleKinds?)`. Both are runtime exports of `@semprec/data` through `export *`; they are in the frozen list of `publicSurface.test.ts`. They share one SQL condition, `SENSITIVE_PROJECT_HEARTBEAT_EXCLUSION`. Tenant isolation is the row-level security of the tables involved, on the tenant-scoped pool.
- `heartbeatAgentTools.ts`: new type `TenantHeartbeatListEntry` (`HeartbeatListEntry` plus `projectItemId: string` and `projectName: string | null`, the project item's `name`, `null` when unnamed or gone). Tenant-scope `heartbeat.list` returns these; every other run returns `HeartbeatListEntry[]` as before.
- `heartbeat.history` in tenant scope uses one scoped statement, so an unknown id, another tenant's id and an id excluded by the sensitive rule all give the identical `Heartbeat <id> not found` error.
- No route, operation, table, migration or job name is added or changed.
- ADR `docs/adr/2026-11-13-a-semp-chat-run-reads-the-heartbeats-of-every-project.md` records the scope, the grant semantics, why trigger stays own-project and that it delivers the item gh-2018 that `2026-11-04-mcp-exposes-module-agent-tools` deferred. A future tool that widens a chat run's read scope should reuse or consciously depart from it.

## Tests

`heartbeatAgentToolsChatScope.test.ts` covers: a chat run listing the Semprec project's and another project's heartbeats with names, a null project name, a delegated run inheriting the tenant scope, another tenant never listed (runtime-role pool, two tenants), the sensitive rule in seven cases (absent without the caller's grant, present with read or write, dropped after the grant is removed, an explicit `none` on the caller, a `none` row on the heartbeat's project, a grant on a non-sensitive database, partial grants over two sensitive databases), the history of another project's heartbeat, identical not-found answers, non-chat runs keeping their own project and entry shape, and `heartbeat.trigger` refusing another project's heartbeat with no job enqueued. The worker's mutation check (dropping `d.sensitive`, the caller access filter or the own-project access filter each fails exactly one test) was not repeated at landing.

## Deviations and spec seams

- "Holds a grant" is read as a stored `agent_database_grants` row with access `read` or `write`; a `none` row is a refusal and counts as no grant on either side.
- The tenant-wide queries live in `schedulerStore.ts`, as the Touches line says. Project names are read in `heartbeatAgentTools.ts` through `getItemsByIds`.
- Test fixtures use raw SQL for one `INSERT` of an item-kind `semp_threads` row (no production writer needed), with a comment. Runs are finished through `finishAgentRun`.
- The Task did not name an ADR; the rules reviewer found the new authorization pattern needs one, and it was added in the fix round.
- No spec seam moved.
