## What was delivered

- The seed (`seedTenDatabasesInTransaction` in `backend/packages/data/src/seed/seedTenDatabases.ts`) stores four colors on the options of the Health records `tags` property, through the existing `selectConfig(keys, colors)` shape of gh-1584: `bloodTests` `#FF9500`, `medication` `#AF52DE`, `bloodPressure` `#FF2D55`, `prevention` `#34C759`. `epilepsy` and `dentalHygiene` get no `color` field. A tenant seeded from this commit on stores `{ key, color }` for the four and `{ key }` for the two.
- The color table of the existing per-tenant cutover `runSelectOptionColorsCutoverMigration` (`backend/packages/data/src/seed/selectOptionColorsCutoverMigration.ts`) has one more entry: Health records, `tags`, the same four colors. The cutover's code and rules are unchanged: only an option that has no `color` field of its own is colored, a color that is already stored stays, and the row is written only when something changed.
- A tenant seeded before gh-1700 and gh-1705 gets all of it in one run of `runTenantCutoverMigrations`: the tags cutover of gh-1700 appends `bloodPressure` and `prevention`, the colors cutover that runs directly after it colors them together with `bloodTests` and `medication`.

## Contracts dependents build on

- Stored shape of the Health records `tags` property (`multi_select`, owner `user`, database of module `healthRecords`): `properties.config.options` is, for a fresh seed, `[{ key: "bloodTests", color: "#FF9500" }, { key: "medication", color: "#AF52DE" }, { key: "epilepsy" }, { key: "dentalHygiene" }, { key: "bloodPressure", color: "#FF2D55" }, { key: "prevention", color: "#34C759" }]`. `GET /api/schema` returns `color` only on an option that stores a valid hex string, so `epilepsy` and `dentalHygiene` have no `color` field in the response.
- An upgraded tenant has the same six options when its stored catalog was the original four. A color a tenant already stored on any option, listed or not, is kept, and so are extra fields of a stored option object. Code must not assume that every tenant's `tags` colors equal the table.
- Registry order in `backend/packages/data/src/db/tenantCutoverMigrations.ts`, which this source needs and did not edit: `runHealthRecordTagsCutoverMigration` (gh-1700) runs before `runSelectOptionColorsCutoverMigration`. With the two swapped, an older tenant gets `bloodPressure` and `prevention` without a color in the first run and with one only in the next. The comment next to the new table entry states the dependency; the test "colors four Health records tags of an older tenant, keeps colors that are already set and does not rewrite on replay (issue #1705)" fails when the two steps are swapped (worker's mutation check).
- The runner keeps no ledger of applied steps and `runMigrationsCli.ts` calls it on every deploy, so the new table entry reaches tenants that already ran the colors cutover.
- No route, table, SQL migration, generic operation, job name, i18n key, barrel export or ADR was added. `tenantCutoverMigrations.ts` was not edited by this source.

## Deviations from the specification and spec seams

1. `Touches` places the tests in `backend/packages/data/src/__tests__`. `GET /api/schema` is served by `createSchemaRequestListener` in `services/semprec-api`, so the HTTP test the Task and the first criterion name is in `backend/services/semprec-api/src/__tests__/schemaHandler.test.ts`, next to the schema tests of gh-1584 and gh-1700. The data-layer tests are in `tenantCutoverMigrations.test.ts`.
2. Three existing tests of gh-1700 in `healthRecordTagsCutoverMigration.test.ts` (fresh seed, the tenant runner, second run) asserted the uncolored catalog. A fresh seed and the whole runner now leave the colored one, so their expected value changed and `toEqual` became `toStrictEqual`. The tests that run the tags cutover alone are unchanged.
3. In the existing test "colors each listed catalog for an existing tenant and preserves unlisted options" the map of row versions was keyed by module id. Health records now has two listed catalogs, so it is keyed by module and property.
4. The Task says "four table entries". The table holds one entry per property with a map of option colors, so the four colors are one entry.
5. No SQL migration and no ordinal: the cutover is the existing application-code step.
6. Test seam: an older catalog cannot be produced through a production write, because Health records is schema-locked. The tests store it with raw SQL, each with a reason comment and a checked row count.
