# Handover: connect a password mailbox with one IMAP login and concurrent verifications

Commit on `feat/internet-accounts`: `a1d1924f7`. Nothing was run against Purelymail, the VPS or any other real server.

**Root cause.** `POST /api/mail/mailboxes` ran its network steps one after the other: the IMAP verification (TLS, LOGIN, closed), the SMTP verification, the CalDAV verification, and then a second IMAP connection through `mailServerClients.openImap` (TLS, LOGIN again, LIST with one STATUS per folder on a CONDSTORE server, LSUB, LOGOUT) for the connect-time folder discovery. `PUT /api/mail/mailboxes/:id/password` had the same sequential IMAP → SMTP → CalDAV chain.

**Changes.**
- `mail/mailServerConnections.ts`: `verifyImapServerConnectionAndListFolders` runs the owned-socket verification attempt and, once its login succeeded, sends imapflow `list()` without a status query (no STATUS; `listOnly` returns before imapflow assigns special-use, see the decision record's spec correction) on the same connection before closing it, under a 15 s deadline. What the client and its sockets report while the LIST runs (and during the close after a failed LIST) is the listing's and never fails the verification; a failed or expired listing is logged (`stage: "listing"`, `errorName`) and answers `folders: null`. `verifyImapServerConnection` keeps its result.
- `mail/mailCredentialVerification.ts`: input `listFolders`, result `folders`; IMAP and SMTP verified concurrently (each still tries its candidates in order), both settled before it returns, the IMAP failure thrown first.
- `mail/mailboxPasswordRouteHandlers.ts`: `verifyLogins` starts the mail and the CalDAV verification together for both routes, waits for both, answers the mail failure first and logs a CalDAV failure behind it (`verification`, `errorName`). The connect asks for the folders and maps them with `imapProviderFolder`; `openImap`, `requireOpenImap` and `listImapFolders` are gone. No transaction is open across any of it.
- `services/semprec-api`: `openImap` removed from `MailServerClients` and `serve.ts`.
- `docs/architecture/domain-mail-and-inbox.md`: connection helpers, password connect, credential verification, password sign-in again.

**Behaviour change to know.** A wrong password now reaches both the IMAP and the SMTP server (before, an IMAP refusal skipped SMTP). The throttle counts per request, so the verifications a user can trigger are unchanged.

**Timing** (new `mailboxConnectLatency.test.ts`: the production handler with `verifyMailCredentialsForTests` and the real CalDAV discovery against a TLS-fronted loopback `FakeImapServer`, a TLS fake SMTP server and `FakeCalDavServer`, 420 ms per TLS connect and 100 ms per command): before 4.4 s with two IMAP connections and two LOGINs (`LOGIN,LIST,ENABLE,LOGIN,LIST,ENABLE,LIST,STATUS×6,LSUB,LOGOUT`); after 1.7 s with one connection and one LOGIN (`LOGIN,LIST,ENABLE,LIST,LSUB`). Network time from the request to the last server connection closing is about 1.05 s (the IMAP span; SMTP 0.73 s and CalDAV 0.24 s overlap it). The remaining ~0.68 s is the mailbox's write transaction in the test database.

**Tests.** New `mailboxConnectLatency.test.ts`: exactly one IMAP connection and LOGIN, no STATUS, Drafts and Sent written, the three verification spans overlap and the network phase is below 0.75 × their sum and within 300 ms of the longest; IMAP, SMTP and CalDAV login refusals each answer 400 with their code, write no mailbox and leave no connection open on any fake; a refused LIST still connects (201) without compose folders and logs no password or address. New in `mailboxPasswordRoutes.test.ts`: both routes start the CalDAV verification while the mail verification runs (each waits for the other to start, so a sequential route fails), and a mail refusal is answered only after a later CalDAV refusal settled, which is logged without the password. Test support: `testSupport/latentMailServers.ts` (test certificate, TLS front with connection latency, fake SMTP), `FakeImapServer` `password` option and `refusedVerbs`, `FakeCalDavServer` `latencyMs` and `openConnections()`. Changed: stubs return `folders`; connect-path spies target `verifyImapServerConnectionAndListFolders`; the IMAP-refusal cases expect SMTP to have been verified concurrently; `mailComposeAfterConnect` hands listed folders through the verification (its opener-missing case is gone with the member); the unused `openPurelymailAccount` fixture is removed.

**Verified** (backend/): `pnpm run lint`, `pnpm run format:check`, `pnpm -r run build`, `test:unit` (4816 + 172), `check:write-safety`, `check:boundaries`. Integration, all green: `mailboxConnectLatency` (three runs), `mailboxPasswordRoutes`, `mailComposeAfterConnect`, `mailServerConnections`, and in semprec-api `mailboxCredentialThrottle`, `tenantIsolationRoutes`, `mailSyncAdapters`, `customRouteMount`. Not run: full `test:integration`, `test:e2e`, web and mobile pipelines.
