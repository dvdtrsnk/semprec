# Handover for gh-1641

An IMAP mailbox's SMTP send now keeps a copy of the accepted message in the account's Sent folder. Gmail and Graph file sent mail by themselves; an IMAP server does not, so the copy is appended here. The copy is best effort: a failure is logged by error name and never fails the send, because the message has been delivered.

## What was added
- **`backend/packages/data/src/mail/imapReconcile.ts`**: `ImapMailClient.appendMessage(path, raw, flags)`. Only the sent-copy path calls it; the reconcile pass never does.
- **`backend/packages/data/src/mail/imapFlowClient.ts`**: `ImapFlowMailClient.appendMessage`, IMAP APPEND through imapflow's `append`. The whole message travels in one command, so the call races a 60 second timer (`IMAP_APPEND_TIMEOUT_MS`), the same way `fetchOneWithTimeout` does. A timeout rejects while the command may still be in flight; the caller's `close()` ends it. A server refusal rejects with imapflow's own error.
- **`backend/packages/data/src/mail/mailTransport.ts`**:
  - `createSmtpMailTransport` takes an optional fifth argument, `saveSentCopy`. It runs after the SMTP transporter has closed and the submission succeeded. Its failure is logged as `Keeping a copy of the sent message in the Sent folder failed` with `errorName` only, and the send still resolves.
  - `createSentCopySaver(pool, mailboxItemId, credential, openImap?, limiter?)` builds the copy. It reads the mailbox's stored IMAP endpoint and username at send time. It finds the Sent folder with `findFolderBySpecialPurpose` (the same lookup `sendDraftEmail` uses) and takes that folder item's `providerId`, which is the IMAP path the sync recorded. It opens the connection through `openImapConnection`, so the outbound address policy applies. The append runs under `sharedImapConnectionLimiter`, keyed by the mailbox, at the limit `imapConnectionLimitForProvider` gives, the same limit the sync worker uses. It appends with `\Seen`, and it closes the connection in a `finally`.
  - `createMailTransportFactory` passes a saver into the `imap` transport. Its options gain `openImapConnection`, so tests can inject a fake IMAP server.
- **`backend/packages/data/src/__tests__/mailSync.test.ts`**: the 19 `ImapMailClient` fakes written as object literals gain a no-op `appendMessage`. Three fakes that spread a full client already get the method from the spread. The build typechecks `src/__tests__`, so the new method has to exist on every fake.

## Behaviour of the copy
- The bytes appended are the same `raw` the SMTP server accepted, so the Message-ID is the one `sendDraftEmail` claimed. A later sync that reads the copy converges onto the item created at send time. That is the existing dedup in `ingestEmailMessage`, covered by the existing test in `mailSend.test.ts` ("a later IMAP-style reconcile pass observing the same generated Message-ID in Sent converges onto the same item").
- A mailbox with no Sent folder yet (no sync has discovered one) logs `reason: no_sent_folder` and keeps no copy. Nothing is opened.
- A mailbox with no IMAP settings fails the copy with a `ValidationError` whose `details.field` is `imap`. The send still succeeds.
- A send the server refuses (535, a refused recipient, an unreachable host) keeps no copy. The copy is made only after a successful submission.
- The IMAP password is the one `sendDraftEmail` already decrypted for the send, so no second `credential_access_log` row is written for the append. The access stays logged once, under `smtp_send`.

## Tests
- `imapFlowClientAppend.unit.test.ts` (unit tier; the Task's Touches listed `imapFlowClient.test.ts`, but a file with no database belongs to the unit tier by name, and the existing IMAP-client tests follow that pattern). Four cases: the same bytes appended to the folder with the flags, a server refusal propagated as-is, the timer cleared once the server answers, and the deadline rejecting at exactly 60 seconds and not before.
- `smtpTransport.test.ts` (integration tier), eight new cases in a describe named "Sent-folder copy of an accepted SMTP send (issue #1641)":
  - the copy is the accepted bytes with `\Seen`, the IMAP connection is opened with the IMAP endpoint, and the event order is SMTP close, IMAP open, append, IMAP close;
  - no copy on a refused submission;
  - a refused copy leaves the send successful, the IMAP connection is closed, and the log has the error name only, with no message content;
  - no Sent folder: nothing is opened and the reason is logged;
  - no IMAP settings: a `ValidationError` naming `imap`, and nothing opened;
  - the append runs under the provider default limit (2 for a provider with no table entry) and under the mailbox's own `connectionLimit`;
  - the production factory keeps no copy of a send the outbound policy refuses.
- Mutation checks, each caught by the matching test, with the file restored byte for byte after each: removing the copy call, not closing the SMTP transporter, letting a copy failure fail the send, dropping `\Seen`, not closing the IMAP connection after the append, and ignoring the mailbox's limit.
- Ran: `tsc` on `packages/data` (includes the tests), eslint and prettier on every touched file, `pnpm --filter @semprec/data run build` and the `@semprec/semprec-api` build, `check:boundaries` (depcruise, no violations), the unit tests of the IMAP client (10 passing), and the integration files `smtpTransport`, `mailSync`, `mailSend`, `mailServerConnections`, `publicSurface` and `mailMessagePreview` (194 passing). The full `verify` was not run.

## Not covered
- A real successful SMTP submission through the production factory. Stored settings accept only the standard mail ports (993, 143, 465 and 587; `docs/adr/2026-10-25-mail-server-settings-allow-the-standard-mail-ports.md`), and the test process cannot bind them. The factory's wiring of the copy is therefore covered by the protocol-level test (the real `createSentCopySaver` behind `createSmtpMailTransport` on a loopback fake server) plus the factory's refusal test, not by a factory-level success.
- A live IMAP server. `openImap` is injected in every test.
- Retry of a failed append. Out of scope by the issue.

## Notes for dependants
- **Send route (#1896)**: the copy is awaited inside `transport.send`, so the send request waits for it. The worst case is bounded but long: up to 3 minutes queued behind the account's connection slot (`ACCOUNT_QUEUE_WAIT_TIMEOUT_MS`), then the connect and greeting timeouts (30 s and 15 s), the 60 second append deadline, and the 10 second logout deadline. A busy sync pass on the same account holds the slot. If the route should answer before the copy is kept, #1896 can hand the saver to a background job; the transport's contract does not change for that.
- **Partial refusal**: when the server accepts the message for some recipients, `sendDraftEmail` reports `MailRecipientRejectedError` and no copy is kept, while some recipients already have the message. That is the #1634 behaviour, unchanged here. It is a follow-up for #1896, which already has to handle "delivery unknown".
- **No Sent folder** until the first sync pass has discovered one. `sendDraftEmail` refuses the send in that case before SMTP is called, so the copy path reaches `no_sent_folder` only when the folder disappears between that check and the copy.
- **Credential reuse**: the copy reuses the password that `forMailbox` decrypted for the send. A future change that moves the password out of the factory must keep the copy on the same credential, or add its own `credential_access_log` purpose.
- **Limiter injection**: `createSentCopySaver`'s `limiter` parameter exists for tests, the same way `handleSyncMailAccountTask` takes one. Production uses the process-wide `sharedImapConnectionLimiter`, so the sync pass and a send share one queue per account.
