## What was delivered

An item of the `files`, `transcripts` or `inbox` system database that has a live relation edge to an item of a sensitive database is treated as sensitive for an agent. The rule is decided in the transaction of the read or write it guards and is documented in the ADR `docs/adr/2026-11-13-items-linked-to-a-sensitive-record-inherit-its-sensitivity.md`.

- An agent project reads an inheriting item only with `read` (and writes it only with `write`) on every sensitive database the item is linked to, in both edge directions, the other endpoint not soft-deleted. The refusal is the existing `ForbiddenError` with code `forbidden`; its message names the item, never the record or database. The decision rows are locked `FOR SHARE`. The per-turn read allowance of #1849 for the item opens a read. Humans and external clients on `/mcp` are unchanged.
- Agent lists, `database.query`, filtered and curated `view.query` exclude denied items inside the SQL, so page, cursor and `totalCount` agree. Relation targets (top level, projected nested entries, `relation.list`) that fail the check are returned as `{ id, hidden: true }`.
- The generic-operation agent tool marks an answer sensitive when a returned item, an expanded target or a non-hidden projected relation entry is an inheriting item linked to a sensitive database, so the stored tool result is the redaction marker.
- Review fixes extended the rule to: `transcript.get` and `transcript.segment.get` (item.get check in the read's transaction, project-less run refused for a linked transcript, `sensitive: true` carried into the pi result details by `agentSessionComposition.ts`); every page operation of a linked item (`resolvePageOwner` returns the host item, a subpage walks to its first non-Pages ancestor, the `page.replace` and `page.restoreVersion` projections included); and the related-item names of the Semp attached-item context.

## Deviations and spec seams

1. The files outside the Touches list that were changed: the real list engine is `views/viewQuery.ts` and `chokePoint/viewItemsStore.ts`; relation targets in `relationExpansion.ts` and `relationReads.ts` (Task step 3); writes in `itemWrites.ts`, `itemTrash.ts`, `valueLinkOps.ts`, `destructiveProjection.ts` (the Context decision "readable and writable"); the constant in `seed/sensitiveDatabaseKeys.ts`; the barrel and `publicSurface.test.ts` for `sensitiveSourceDatabaseIdsByItem`; later `pageOwnerDatabase.ts`, `sempRefReadContext.ts`, `moduleAgentTools.ts`, `transcriptAgentTools.ts` and `agentSessionComposition.ts` for the review findings.
2. The item asked about is not filtered by `deleted_at` in `sensitiveSourceDatabaseIds` (the Task says endpoints not soft-deleted); only the other endpoint is, so a trashed linked file stays as sensitive as a live one.
3. Inheriting databases are matched by `owner_module_id` AND system.
4. A per-turn read allowance for the item opens the inherited refusal for a read.
5. A transcript or an Inbox entry has no relation to Health records in the seeded schema; the tests unlock `schema_locked` with a commented superuser UPDATE and create the relation property through the choke point. The rule applies as soon as such a property exists.
6. The agent tool looks up uuid-shaped answer ids only.
7. The ADR lists what is not covered: counts and facets over an inheriting database, search, the titles of value-link sources and of page breadcrumb ancestors, redaction of tool call arguments for a write to a linked item (#2001 decides it by the target database), relation writes that name a linked item only as the edge source. The edge is not locked between the check and commit (narrow race, stated in the ADR).
