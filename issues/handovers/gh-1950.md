## What was delivered

A second heartbeat action of the calendar module, `calendar.applyInvitationReply`, runs on the creation of an Emails item. It reads the calendar part of the message the same way the ingest action of gh-1929 does, and applies an iMIP `METHOD:REPLY` to the invitation on the participant edge of the answering person. Rules: the `ATTENDEE` address, normalized, must equal the normalized sender of the message; a live person must be found for that address (`lookupPersonIdByEmail`); that person must have an edge to the one live Event with that `UID` and the edge must already carry an invitation. Only `PARTSTAT` ACCEPTED, TENTATIVE and DECLINED map to the statuses `accepted`, `tentative` and `declined`; the edge metadata is rewritten with the stored role and invitation fields kept and only `status` and `respondedAt` changed. The write is `updateRelationWithClient` with the system writer kind, under the Event row lock and then the person row lock, in one transaction per email that also locks the Emails row. Anything else (no calendar part, another METHOD, an unknown UID, a sender that differs from the attendee, no invitation, trashed email, Event or person) changes nothing and does not fail the heartbeat.

## Deviations from the specification and spec seams

1. Idempotency: a reply whose PARTSTAT already equals the stored status is skipped (reason `unchanged`). `respondedAt` is therefore the time the current status was first recorded, and only a change of status moves it; a distinct later email repeating the status does not refresh it. The docstrings and a test state this (fix round).
2. Events with a `RECURRENCE-ID` are ignored (`recurrence_instance`): the single participant edge cannot record an answer for one occurrence.
3. More than one live Event with the same UID is ignored (`ambiguous_uid`).
4. A trashed person is ignored (`unknown_attendee`) so the edge write cannot throw.
5. The parser is called with the fallback time zone UTC since a reply reads no time; the gh-1929 parser rejects a VEVENT without a readable DTSTART as malformed, so such a REPLY is ignored (parser behavior, out of scope).
6. Spec seam: `index.ts` is at its line cap, so the export goes through `calendar/calendarHeartbeatActions.ts`.
7. The cutover entry sits after the gh-1929 entry and before the gh-1958 entry, as the comment on that entry requires for gh-1950.
8. Test fixtures index person addresses with `reindexPersonEmails` because the asynchronous reindex heartbeat does not run in these tests.
9. Accepted by product decision: no SPF or DKIM check, so a forged From header of an invited person is accepted (security reviewer's note, not a defect).
