# Handover for gh-1779

Backfill the sleep module into existing tenants through the per-tenant cutover. Candidate commit `4778b46381be96b981e126dc68a72732fe59803c` landed on `feature/backend-parallel` with merge `d87390066db91e751a5c3f687f0fbcb8e3d3101e` (chain `e1-046-misc`, its only member). The source is one commit, `4778b4638` "Deliver the sleep module to tenants seeded before it". The chain landed alone, not as part of a train, on its first landing attempt, without a fix round. The acceptance receipt is `issues/batches/backend/acceptance/sources/gh-1779.md`.

Both declared blockers are completed on the tip with a handover: gh-1776 (the sleep module and its seed) and gh-1712, which the record names for `Shared-file ordering`. No blocker was open at this landing.

**Every run of the cutover runner now gives a tenant that has a Projects database and no `sleepSettings` database the whole sleep module.** That is one Sleep project item, three databases, 20 properties, three views and three items more. Details under "Contracts dependents build on".

## What was delivered

- The per-tenant cutover `runSleepModuleCutoverMigration(pool)` in `backend/packages/data/src/sleep/sleepModuleCutoverMigration.ts`. For the current tenant, in one transaction, it:
  1. takes the tenant's structural seed lock and admits the tenant through `lockTenantSeedInTransaction(client, "runSleepModuleCutoverMigration")`, the helper `seedSystem` uses: the advisory lock `(2331, hashtext(tenant id))`, then the tenant admission;
  2. returns when `getDatabaseByModuleId(client, "sleepSettings")` finds the database;
  3. returns when the tenant has no Projects database (it has not been seeded yet);
  4. otherwise calls the unchanged `seedSleepModuleInTransaction(client, projects.id, createViewTypeRegistry())` of gh-1776.
- The registration in `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`): one import and one entry.
- One comment in `backend/packages/data/src/seed/seedSystem.ts`, at the call of the sleep seed: the sentence "Issue #1779 will deliver the module to tenants seeded before it" now names `runSleepModuleCutoverMigration`. No code of `seedSystem` changed.
- No migration, table, route, generic operation, MCP tool, job name, write hook, stored key, barrel export or ADR was added. `seed/seedSleepModule.ts`, `provisionTenant` and the per-tenant module data migrations are unchanged.

## Contracts dependents build on

- `runSleepModuleCutoverMigration` is exported from its module only. Nothing was added to the data barrel `backend/packages/data/src/index.ts`.
- **After a deploy, every maintained tenant has the sleep module of gh-1776**: the Sleep project item (`systemActive: true`), the databases `sleepSettings`, `sleepPlans` and `sleepNights` (system, `schema_locked`, `clientVisible` false), one settings item and the two default plans. The rows are written by the same function as for a new tenant, and the test compares a delivered tenant with a freshly seeded one: properties, views, items and the Czech schema projection are equal. gh-1833, gh-1838, gh-1808, gh-1784 and gh-1799 can rely on the databases existing for every seeded tenant once the runner has passed.
- **Who runs it.** `runTenantCutoverMigrations` is called by `db/runMigrationsCli.ts` (the `run_migrations` step of `deploy/deploy.sh`, which runs before `run_seed`) and by the test global setup. `provisionTenant` runs no cutover. A tenant is therefore delivered by the migration step of a deploy, not by `provisionTenant` and not by a request. See deviation 1.
- **Which tenants.** The runner iterates the maintained tenants (status `provisioning`, `active` or `suspended`) through `forEachMaintainedTenant` on the runtime role's pool, each in its own tenant scope under row-level security. A suspended tenant is delivered like an active one (tested). The admission inside the step refuses a missing or deleting tenant (by reading; no test of this source builds one).
- **The guard is existence of `sleepSettings` only.** The step does not repair or alter a sleep database that exists. A source that changes an already delivered sleep database (gh-1833) needs its own idempotent step. A tenant that holds `sleepPlans` or `sleepNights` without `sleepSettings`, a state no production path creates, is not skipped: the seed fails on the key conflict, the tenant's transaction rolls back and the runner reports that tenant on every pass.
- **Plan names** are taken from the catalog in the tenant user's `users.locale` at the moment the cutover runs ("Pracovní dny" and "Víkend" for a Czech user, "Weekdays" and "Weekend" for an English user) and stored as plain titles, as gh-1776 does for a new tenant.
- **No guidance row.** The Sleep project has no entry in `SYSTEM_PROJECT_AGENT_GUIDANCE_SEED_TEXTS`, so the step writes no `project_agent_guidance` row and no drift heartbeat, unlike the Recipes cutover of gh-1707. The first test asserts that a delivered tenant's Sleep project has no guidance row.
- **Registry order** in `backend/packages/data/src/db/tenantCutoverMigrations.ts`: `runSleepModuleCutoverMigration` stands directly after `runMeetingNotesBackfillCutoverMigration` (gh-1712), which follows `runRecipesModuleCutoverMigration` (gh-1707), and directly before `runAreaNoteCutoverMigration`, which stays last. It needs no other step's result. This is the position the handover of gh-1712 prescribes.
- Side effects later sources and tests meet:
  - every runner pass takes each maintained tenant's seed lock `(2331, hashtext(tenant id))` once more, in a transaction of its own;
  - a test that builds a tenant with a Projects database and without the sleep databases and then runs `runTenantCutoverMigrations` finds one more project item, three more databases, 20 more properties, three more views and three more items;
  - `seedSleepModuleInTransaction` now has two callers, `seedSystem` and this cutover, so it also runs for populated tenants. Its docstring (unchanged, Task step 2) still names only `seedSystem`.

## Deviations from the specification and spec seams

1. **Criterion 1 names `provisionTenant` as the delivering call; the code delivers through the cutover runner.** The record's Context says the cutover pass runs "on every deploy through `runSeedCli` and `provisionTenant`". In the code `runTenantCutoverMigrations` is called by `db/runMigrationsCli.ts` and by the test global setup; `provisionTenant` runs no cutover and was not changed. The step is registered in the runner, as Task step 1 says. The test of criterion 1 runs the runner and then `provisionTenant`, the order of `deploy/deploy.sh`. `provisionTenant` alone does not deliver the module. Both reviewers confirmed the seam in the code and did not rate it a defect; the same seam is deviation 6 of the gh-1707 handover. No decision record `issues/decisions/gh-1779.md` exists. For the owner: the criterion is met for a deploy, not for a call of `provisionTenant` on its own.
2. The record's Context expects to register the sleep module "with that same step" of gh-1707 "instead of writing a module-specific cutover". gh-1707 delivered a module-specific file (`recipes/recipesModuleCutoverMigration.ts`) and no shared step exists, so this source follows its Decision and Task step 1 with its own file `backend/packages/data/src/sleep/sleepModuleCutoverMigration.ts`, which `Touches` does not list.
3. `backend/packages/data/src/seed/seedSystem.ts` is outside `Touches`: one comment that would otherwise be stale.
4. The step skips a tenant without a Projects database, a branch the Task does not name. The runner meets tenants that are not seeded yet (the test global setup runs it before the seed), and the seed needs the Projects database id.
5. The existence check reads `sleepSettings` only, as Task step 1 says. The Decision's wording is "any of the three sleep databases".
6. No `project_agent_guidance` row and no drift heartbeat, unlike the Recipes pattern the Task refers to, because the Sleep project has no guidance seed text.
7. `clientVisible` false of criterion 1 is asserted through `generateSchemaProjection`, the data-layer function behind `GET /api/schema`, not through an HTTP request for a cut-over tenant.
8. No ADR was added. The step follows `docs/adr/2026-09-10-app-code-post-migration-steps.md` (the guard inside the transaction, after the lock) and reuses the runner and the seed lock helper.
