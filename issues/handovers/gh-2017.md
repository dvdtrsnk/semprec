## What was delivered

A new catalog operation `page.mergeJournalDuplicates` that lets the assistant propose merging the two live entries of a Journal period, and merges only after the user approves the exact pair that was shown.

- Operation: input `{ type, period }` (`type` one of year, quarter, month, week, day; `period` the canonical key of that type), output `{ survivorId, mergedItemId }` or `{ merged: false }`. Capability `core.item.write`, `requiresApproval: true`, risk class destructive, `reversible: false`. The catalog now has 48 operations. MCP name `semprec.page.mergeJournalDuplicates`.
- Agent call: held by `GenericOperationGateway` as a pending approval request with the new snapshot kind `journal_merge` (`chokePoint/destructiveProjection.ts`). The description key is `approval.journalMerge`; its params carry the period type, the period key and the stored titles of the survivor and the merged entry, never page content. The notification body is chosen per period type from the catalog entries `approval.journalMerge.<year|quarter|month|week|day>` in `en.json` and `cs.json`, so the Czech text reads for example "za den <period>". A request is also created for a period without a duplicate, so that `{ merged: false }` can be the approved result.
- Approved replay: re-projects the period under the request row lock, compares the snapshot hash, and merges through `mergeJournalDuplicates` (gh-1726) in the same transaction only when the merged pair equals the approved pair (or no pair was approved and none is found). Otherwise a `ConflictError` (409) is thrown outside the conflict-terminalising block, the transaction rolls back and the next attempt ends as a conflict. Rejecting the request leaves both entries live and the request cannot be replayed.
- Person actor (REST session or human `/mcp` session without a run): merges at once, as `item.delete` and `page.replace` already do. There is no REST route.
- Validation: unknown type or malformed or non-existent period is 400 with `details.field` (`type` or `period`), before any request is created. The write grant on the Journal database is checked through `assertWriterDatabaseAccess` before the period validation, both in the projection and in the merge, so a read-only project gets 403 and a malformed period is no oracle.

## Deviations and spec seams

1. Touches say `journal/` is export only. Two sibling modules and `findJournalDuplicatePair` were added because the grant check, validation and merge must share one data-layer transaction and the approval projection may not live in `chokePoint/` (it may not import `journal/`). This follows the `page.replace` precedent.
2. Files beyond Touches: `destructiveProjection.ts`, `approvalDescription.ts`, `approvalNotificationBody.ts`, the two i18n catalogs, `genericOperationGateway.ts`, `data/src/index.ts` and an ADR.
3. The output omits the refused edges of gh-1726; the merge only logs them.
4. The request is created also for a period without a duplicate.
5. Risk class destructive with `reversible: false` is this source's choice; the issue names only capability and `requiresApproval`.
6. No REST route (out of scope). The REST contract case dispatches the binding through `dispatchGenericOperation` as a REST person session.
7. The isolation probe interface in `tenantIsolationRoutes.test.ts` gained `touchesNoneOfA`, because a run credential's call is held and the existing `excludesA` helper rejects error answers.
8. Older comments still say "46-operation"; left alone.

## Not run, BLOCKED

- BLOCKED: "a run whose project has Journal restricted to read gets 403" on the literal shipped Journal. The grants model ignores a stored read row on a non-sensitive system database (`2026-11-12-per-database-agent-grants`), so the shipped Journal cannot be restricted to read without a change of that model. It needs the owner decision already recorded in the gh-1844 and gh-1861 handovers. The same code path is proven PASS with the Journal flagged sensitive in the test (raw `UPDATE databases SET sensitive`, restored in `finally`).
- The whole integration tier is not part of this landing. The known macOS baseline case of `mcpConnectionFactory.test.ts` was not run.
- The race in which the 409 of the post-merge pair comparison escapes `replayApprovedGenericOperation` and the retry that follows is not tested at the gateway; the data-level 409 with rollback is.
- Web and mobile (a merge action in the app) are out of scope.

Fixed in `71ce308c7` with one catalog entry per period type in en and cs, a unit test per type and locale, and an integration test asserting the real Czech body. The recheck of the fix was done by the fixer's own commands only; no separate recheck report exists.
- Security reviewer: clear. Noted, not a finding: after approval the merge writes as the system writer and is not limited by the agent's grants on other databases; this is the user-approved decision of the issue and the ADR.
- Requirements reviewer, non-blocking: the `touchesNoneOfA` case treats any answer containing `"error"` as held for approval, so an unrelated error would pass vacuously; the isolation property it asserts holds either way and the success paths are covered elsewhere.
