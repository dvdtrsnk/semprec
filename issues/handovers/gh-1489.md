# gh-1489 implementation handover

Implementation commit: cc9c1a64. Frozen base: e4e30e006f23b65368ffef0d8b5c68b25570fe06.

## Delivered behavior

- `backend/packages/data/src/inbox/journalInboxCompute.ts`: each element of `computed.inboxItems` gains two fields, and `status` keeps its meaning.
  - `processing`: `pending` when no live card exists or the card status is `computing`; `failed` when it is `computeFailed`; otherwise the card status (null when the card has none).
  - `proposalSummary`: present only when the card status is `proposed`, otherwise null. Fields: `entityKind`, `documentKind`, `targetDatabaseKey`, `targetItemId`, `targetItemName`, `projectItemId`, `projectName`, `areaItemId`, `areaName`, `followUps`.
- The summary is read from the card's stored `proposal` envelope with `parseStoredProposalEnvelope`. An unknown kind or a missing envelope yields a summary of nulls with `followUps: []`.
  - Target: for a `database` envelope, `targetDatabaseKey` is the key of `envelope.target` and `targetItemId` is the primary step's `itemId` when that step is `update` or `link`. For `pageContent` and `relation` envelopes, the target is the item `envelope.target`, and its database key and name are read from that item.
  - Project and area: the relation targets of the primary step (or of the top-level envelope when there are no steps) that resolve to an item of the Projects or Areas database. The relation key is not fixed by name, because Files uses `area` and Tasks uses `project`.
  - Follow-ups: the active non-primary steps of `selectActiveSteps`. `databaseKey` is the step's `databaseKey`, `name`, `amount` and `currency` are read from the step's properties.
- `resolveInboxPipelineDatabases` also resolves the Projects and Areas system databases. The recompute returns without writing when either is missing, as it already does for the other pipeline databases.
- New exported types `JournalInboxProposalSummary` and `JournalInboxFollowUp`. `JournalInboxItemSummary` gains `processing` and `proposalSummary`.

## Deviations from the Task

- The Task does not name the source of a proposal's project and area. I read them from the stored envelope's relations, classified by the database of the related item. On this tip a single-step tick result cannot carry relations, because the computation returns no relation field and `buildProposalEnvelope` stores a single operation as `properties`. Only a multi-step answer (two or more operations) carries relations, on its primary step. The Files test therefore uses two operations.
- `documentKind` is always null. No card field on this tip stores a document recognition result, so the Task's "when it exists" condition never holds yet.
- For `update` and `link` follow-up steps, `databaseKey` is null, because the step names an item and not a database. I did not add a lookup through the item.
- Import cycle: `journalInboxCompute.ts` now imports `parseStoredProposalEnvelope` and `selectActiveSteps` from `inboxTickAction.ts`, and `inboxTickAction.ts` already imports `journalInboxCompute.ts`. The runtime cycle is safe because both modules only use each other inside functions. The dependency-cruiser `circular` rule covers only `chokePoint` and `rollup`, and ESLint has no cycle rule. A reviewer may prefer the envelope schema moved to a leaf module.
- The Task's test "the cache contains no localized strings" has no separate scan. The exact canonical values asserted in the tests (`processing`, `entityKind`, `targetDatabaseKey`, and the follow-up `databaseKey`) are what prove it. The Task's "day item is announced after each recompute" is covered by the existing `publishes exactly one item invalidation` test, which I did not change.

## Tests

`backend/packages/data/src/__tests__/journalInboxCompute.test.ts`, new describe `processing state and proposal summary (issue #1489)`, 10 tests on the real database:

- No card gives `pending`. A `computing` card gives `pending`, and that status is written directly in the test, with a comment, because nothing on this tip writes `computing`. A `computeFailed` card gives `failed`, produced through the production tick with `AiGatewayFailedError("budget_exceeded")`.
- A proposed Files card gives the full summary through the tick: `targetDatabaseKey` `files`, the project and area names, and one follow-up step. A card naming only a project leaves the area null. A single-step Tasks card has no project, area or follow-up.
- An unknown envelope kind gives the empty summary. A `pageContent` target gives its item id, name and database key. A primary `update` step gives its existing item as the target. A follow-up step's `amount` and `currency` are read. The last three write the envelope directly, with a comment, because the tick cannot store those shapes on this tip.

Results: `journalInboxCompute.test.ts` and `inbox/__tests__/inboxTickRecompute.test.ts` pass on the integration config, 28 tests. The embedded Postgres needs shared memory, so the run was made outside the sandbox.

Gates: prettier, eslint and `tsc --noEmit` for `@semprec/data` are clean; dependency-cruiser reports no violations; `check-write-safety` reports no new writes.

Not run: `pnpm run verify`, and the lint, format and build scripts across `backend/`. `web/` and `mobile/` are not touched.

## Notes for dependants

- After a tick writes a card, the day's cache is recomputed by the job of gh-1390, so a `proposed` card reaches `processing: 'proposed'` with its `proposalSummary` without any change to the Inbox item.
- Project and area are only filled from relations on stored envelopes. Until the relations of gh-1488 reach single-step cards, a single-step proposal shows no project or area.
- `documentKind` needs a card field and a writer from the attachment recognition (gh-1965). The reader must then read that field.
- `selectActiveSteps` throws on a malformed step graph. The tick validates each envelope before storing it (`assertValidProposalEnvelope`), so a stored envelope is well-formed. A malformed value written some other way would make the whole day's recompute fail.
- The summary is computed for every item whose card is `proposed`, as the decision in gh-1320 records. The client chooses what to show.
