## What was delivered

- Core task `pushDismiss` (`CORE_TASK_NAMES.PUSH_DISMISS` in `@semprec/queue`, affinity `api`, tenancy `tenant`), payload `{ userId, notificationIds }`, handler `handlePushDismissTask(pool, payload, senders?)` in `backend/packages/data/src/push/pushDismissJob.ts`, exported from the `@semprec/data` barrel and registered in `worker.ts`.
- `resolveNotificationsBySource` (`notifications/notificationsStore.ts`) enqueues the job on the caller's client, so it commits or rolls back with the resolve: one job per user, only for notifications whose kind policy has `push: true` (read or not), ids split in chunks of `PUSH_DISMISS_MAX_IDS_PER_JOB` (50, to keep an APNs payload under 4096 bytes), `maxAttempts` 3. A kind that is never pushed enqueues nothing.
- The handler sends a silent background push `{ dismiss: [ids] }` (`sendApnsBackgroundPush`) to every active APNs registration of the user and a Web Push `{ dismiss: [ids] }` (`sendWebPushDismiss`) to every active Web Push one. A registration reported dead is revoked; a transient failure is thrown after the other registrations were tried, so the queue retries; `not-configured` neither revokes nor fails and is logged once per channel. It writes no `push_deliveries` row. A user other than the tenant's own gets nothing sent.
- Visible Web Push payloads now carry `tag` = the notification id, so a device can replace or remove the notification by tag.

## Deviations from the specification and spec seams

1. Chunking of the ids at 50 per job is an addition of the implementation (not in the Task), to stay inside the APNs payload limit.
2. `webPushTarget` and `apnsTarget` moved into `push/pushTargets.ts`; the Touches list does not name those files. The move is behaviour-preserving.
3. The dismiss is enqueued for `approval_pending` notifications even when the user's approvals preference suppressed the visible push; the Task keys on the kind policy `push` flag.
4. The worker handler uses the default senders, not the `pushSenders` injected into the fan-out; tests inject through the handler argument. A retry re-sends to registrations that already succeeded (a dismiss is idempotent on the device; documented in the handler's comment).
