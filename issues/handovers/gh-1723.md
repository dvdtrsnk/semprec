## What was delivered

- `backend/packages/data/src/docs/pageTrash.ts` (new) with the choke point's delete hook and restore hook for Pages items and the subtree walk. Both hooks act on a row only when its database is the tenant's Pages system database (`database.system` and owner module id `pages`). There is no `DELETE /api/pages/:id` and no new route, operation, table, migration or job: deleting a page stays `DELETE /api/items/:id` (`item.delete`), restoring it stays `POST /api/items/:id/restore` (`item.restore`).
- `pageItemDeleteHook`, run inside the trash cascade's transaction after the page's own soft delete:
  1. selects the live Pages items whose `parentItemId` is the page and locks them `FOR UPDATE` in that one statement, in id order, then trashes each in that order through `itemDeleteWithClient` with the hook context's writer kind, agent run and acting user. Each subpage's own run of the hook continues one level down, so the whole subtree is trashed with the transaction's `deleted_at`.
  2. removes, in one `mutateDocWithClient` call on the document of the item `parentItemId` names, the first block whose `pageId` is the page and records where it stood in the top-level `Y.Map` `trashedPages` of that document. The update is authored `user`, `ai_agent` or `system` by the writer kind.
  - Nothing is written when `parentItemId` is not a UUID, the parent has no document of kind `page`, or that document holds no block for the page.
- `pageItemRestoreHook`, run inside the restore cascade's transaction after the page's own restore:
  1. selects the Pages items whose `parentItemId` is the page and whose `deleted_at` equals the context's `deletedAtExact` (compared by Postgres), locks them `FOR UPDATE` in id order, and restores them in descending id order through `restoreItemWithClient` with the context's queue routing, writer and acting user. A subpage trashed at another instant stays in the Trash.
  2. puts the page's block back into the parent's document with the item's current `title` as its text (empty when the stored title is not a string) and deletes the page's `trashedPages` entry. Place: first when the recorded `afterBlockId` is `null`; after the recorded neighbor when that block still exists; otherwise (neighbor gone, or no valid entry) after the last block. Nothing is inserted when the parent has no page document or already holds a block for the page; the entry is deleted either way. The block returns with its recorded id and indent, or with a new UUID when another block has taken the id or no valid entry exists.
- An error from either hook rolls the whole trash or restore back (no catch, no retry, no `NOWAIT`).
- `collectSubpageTree(client, rootItemId)`: the ids of the live Pages items below an item (a host or a page) at any depth, breadth first, each level in id order, the root excluded, with a visited set that ends the walk on a stored `parentItemId` cycle. It follows live pages only, and returns `[]` for a tenant without a Pages database.
- Both hooks are registered at the end of `backend/packages/data/src/domainWriteHooks.ts`; `collectSubpageTree` is exported from the data barrel.
- ADR `docs/adr/2026-11-10-trashed-pages-leave-the-parent-document-and-record-their-position.md` (accepted, area backend, web, mobile): the uniform rule, the deletion-epoch rule for subpages, the `trashedPages` encoding, the placement of a restored block, authorship and queue routing, the lock order and its limits.
- The lock-order comment in `backend/packages/data/src/docs/pageTitleMirrorJob.ts` was brought in line (its sentence that the trash locks none of the host's Pages items no longer holds for the trash of a page). No code of the job changed.

## Contracts dependents build on

For gh-1763 (trash a host's subpages), gh-1749 (orphan sweep), gh-1855 (trash list), gh-1856 (delete impact preview), gh-1876 (restyling a page block) and gh-2032.

- `collectSubpageTree(client: PoolClient, rootItemId: string): Promise<string[]>`, exported from `@semprec/data` (`backend/packages/data/src/index.ts`, after the `pagesDatabase` export). It returns item ids, not rows. Its length is the number of nested live pages a trash of `rootItemId` takes with it; gh-1856 and gh-1876 count with it. It takes no row locks. A live page below a trashed page (a subpage restored on its own) is not reached.
- `pageItemDeleteHook` and `pageItemRestoreHook` are exported from `docs/pageTrash.ts` only; the barrel does not export them. gh-1763 adds its `hostItemDeleteHook` and `hostItemRestoreHook` to the same file.
- Registry order in `domainWriteHooks.ts`: the two comment lines and the two registrations of this source are the last entries of the file, behind the entry of gh-1718. In the delete registry `pageItemDeleteHook` runs last, after `itemSearchDeleteHook`, `valueLinkSourceDeleteHook`, `peopleLastContactItemDeleteHook` and `transcriptCompanyLinkReleaseItemDeleteHook`; in the restore registry `pageItemRestoreHook` runs last, after `itemSearchRestoreHook`, `transcriptRestoreHook`, `journalItemRestoreHook` and `peopleLastContactItemRestoreHook`. gh-2032 names gh-1723 as a `Shared-file ordering` blocker: its entries in this file go after the two of this source, unless its Task names another position. gh-1749 names gh-1723 as a capability blocker: its sweep trashes through the choke point so that these hooks run.
- The synced document type: `doc.getMap("trashedPages")` on the parent's page document, keyed by the id of the trashed Pages item, value a plain JSON object `{ blockId: string (non-empty), afterBlockId: string | null, indent: integer 0-5 }`. It is not a block and not part of `blocks` or `order`. On the server only these two hooks write it; it still arrives through `WS /api/sync`, so the restore hook parses an entry with zod and treats an invalid one as absent. Clients must leave the map alone. The entry of a purged page stays in the document.
- Every trash of a Pages item through the choke point now removes the page's block from its parent's document, in the same transaction. A test or a feature that needs "a document that names a page in the Trash" cannot get it from a trash alone. The two gh-1722 tests reach it by restoring the parent's page to a version from before the trash (`page.restoreVersion`, `POST /api/items/:id/page/restore`). Other ways the state arises: a block stored over the sync socket after the trash, and a second block naming the same page (the hook removes only the first).
- Every restore of a Pages item puts the block back into its parent's document, also when that parent is itself in the Trash. A page restored on its own is then live below a trashed parent.
- Subpages follow their parent by deletion epoch: only the subpages whose `deleted_at` equals the restored page's exact epoch come back with it. A host hook (gh-1763) that trashes subpages has to give them the host's epoch for the same rule to work, and has to keep the reverse order on restore if it wants adjacent blocks back in their order.
- Lock order of one trash or restore of a page: the page's row (taken by the cascade), the rows of the direct subpages the hook acts on (one statement, id order), then subpage by subpage everything below it in the same order followed by the page's own document, and the document of the page's parent last. The row of the page's parent is not locked. A hook that adds locks for the same rows has to fit this order.
- Authorship: a hook's document update is authored by the writer kind of the trash or restore (`user`, `agent` as `ai_agent`, `system`). The approved replay of an agent's `item.delete` runs with writer kind `agent`.
- Test helper: `PageHttpHarness.mintRunCredential(tenantId, capabilities)` in `backend/services/semprec-api/src/__tests__/pageHttpHarness.ts` now takes `CapabilityId[]` (it took only the two page capabilities before).
- No table, no migration, no job name, no route, no generic operation, no tenant cutover entry, no module manifest entry and no i18n key was added.

## Deviations from the specification and spec seams

1. A delete hook's context carries no queue routing, so the nested trash of a subpage runs with `createActionQueueAffinity()`, the production routing table. The nested restore passes the context's `queueAffinity`.
2. The restore compares the epoch with the context's `deletedAtExact` in SQL (`deleted_at = $3::timestamptz`), as ADR `2026-11-08-restore-hooks-carry-exact-deletion-epochs` requires, not with the millisecond `deletedAt` string the Task text names.
3. `collectSubpageTree` returns page ids (`string[]`), not item rows.
4. The hooks gate on `database.system && ownerModuleId === "pages"`; the Task names only `ownerModuleId`.
5. A recorded `afterBlockId` of `null` means the block stood first and is restored as the first block. "The end" applies when the recorded neighbor is gone or no valid entry exists. When several blocks name the page only the first is removed and recorded.
6. Tests outside `Touches`: the Task names `GET /api/items/:id`, the agent approval flow and the cross-tenant 404, so three HTTP-level tests live in `services/semprec-api/src/__tests__/pageTrash.test.ts`, and `PageHttpHarness.mintRunCredential` was widened for them.
7. Files outside `Touches`: the ADR, the comment in `pageTitleMirrorJob.ts`, `publicSurface.test.ts`, `pageHttpHarness.ts`, and the two gh-1722 test files of the second fix round.
8. Review fix inside the segment: the delete hook locks all live direct subpages in one statement before the first nested trash (the Task describes only "trash every live direct child page"); the restore hook restores in descending id order.
9. Known limit, recorded in the ADR and not removed: the trash or restore of a page locks the page's row and then the parent's document, while the page title mirror job of the parent locks the parent's document and then the page's row. When both run at once PostgreSQL can abort one of them with `40P01`. Nothing maps or retries it.
10. The approved replay of an agent's `item.delete` authors its document updates as `ai_agent`, as the Task's mapping says, whereas `page.restoreVersion` authors its approved replay as `user`.
11. A page block that was the only block of its parent leaves the block model's empty `text` block behind, which stays after the restore.
12. The ADR (decision 4, line 83) and the Out of scope of gh-1723 say the permanent purge runs no hook. On the tip the purge runs the hooks of `registerItemPurgeHook` (`docs/adr/2026-11-10-item-purge-domain-hooks.md`); only `mailItemPurgeHook` is registered, none for Pages items. The `trashedPages` entry of a purged page therefore still stays, as the ADR says; only the stated reason is out of date. A later source can remove the entry with a purge hook.

## Review

Three reviewers read `253b58cc0^..253b58cc0` (now `49bd24262`) read-only: requirements and tests (verdict findings), project rules and architecture (verdict findings) and security (verdict clear).

- Finding, high, requirements lens: restoring a page put adjacent subpage blocks back in the wrong order or at the end. Fixed in `8ea965310` (now `db5d130bf`). Recheck: resolved.
- Finding, medium, requirements and rules lens (one defect): the delete hook locked the page's own document before the rows of its later subpages and could deadlock with a trash of one of them. Fixed in `a2caecec2` (now `6c061e516`). Recheck: resolved.
- Finding of the landing gate, medium: two tests of gh-1722 failed on the merged tree. Fixed in `acf15cd54`, test files only. Recheck of that delta and of the rebuild: pass. The three reviewers did not read the rebuilt commits; the second recheck did.
- New finding of the first recheck, low, not fixed: the last bullet of decision 8 of the ADR says the trash or restore of a parent always locks the subpage's row. That holds for a trash against a trash and for a restore against a restore of the same epoch, not for a mixed pair, where the parent's operation takes no lock at or below the subpage. No wait cycle follows; only the stated reason is too wide.

Follow-ups, none of them changed by this source:

- The wording of decision 8 of the ADR (the low finding above). The Consequences bullet on the page title mirror job also names a restore as a partner of that wait cycle, which the requirements reviewer calls overstated: the mirror job locks only live pages.
- The `40P01` wait cycle between a page's trash and the title mirror job of its parent could be closed in the mirror job, which this source does not own.
- gh-1763 should know: `itemDeleteWithClient` has the option `deletedAtExact`, which makes a cascade join an earlier trash epoch. A delete hook's context carries only the millisecond `deletedAt`, and the nested trash in `pageItemDeleteHook` passes no epoch. A page trashed by a caller that joins an earlier epoch would get that epoch while its subpages get the transaction's `now()`, and `pageItemRestoreHook`, which matches the exact epoch, would not restore them. The only production caller that passes `deletedAtExact` today is `mail/mailboxRemovalJob.ts`, for Folders and Emails items.
- `pageTrash.ts` compares a block's `pageId` exactly, while `pageOperations.ts` and `pageTitleMirrorJob.ts` compare it in lower case. A block that stores the id in upper case (only the sync socket can write one) is not removed by the trash.
- `page.restoreVersion` can write back the block of a page that is still in the Trash and leaves that page's `trashedPages` entry in place. A later restore of the page finds the block, inserts no second one and deletes the entry, so the state is coherent, and `page.duplicate` leaves the block out. If a later source makes `page.restoreVersion` skip such blocks, the two gh-1722 fixtures need another way to that state.
- Security reviewer, observed: the approval snapshot of an agent's `item.delete` describes the root item only, so subpages created under the page between the request and its approval are trashed by the approved replay without appearing in the request. The trash is reversible; the impact preview is gh-1856.
- The ADR's statement that the purge runs no hook is out of date (deviation 12), and the entry of a purged page still waits for a product decision.
- The helpers `instantAfterWrites` and `namedPageIds` exist in two copies, one per gh-1722 test file, because the second fix round was allowed to change these two files only.
- The `trashedPages` table of the ADR is not in Prettier's column padding; `docs/` is outside the backend format check.
