# gh-1618 implementation handover

## Behavior and interfaces

An approval request now records the model-runtime tool call that created it.

- Migration `0116_approval_requests_tool_call_id.sql`: nullable `approval_requests.tool_call_id text`
  (no default, expand-only) plus the partial unique index `approval_requests_run_tool_call_unique` on
  `(tenant_id, agent_run_id, tool_call_id) WHERE tool_call_id IS NOT NULL`. Existing rows stay NULL.
- `ApprovalRequest.toolCallId: string | null` (validated when the row is mapped).
  `CreatePendingApprovalRequestInput.toolCallId?: string | null`.
- `createPendingApprovalRequest` inserts with `ON CONFLICT (tenant_id, agent_run_id, tool_call_id)
  WHERE tool_call_id IS NOT NULL DO NOTHING`; on conflict it reads and returns the existing request, so a
  redelivered call yields the same request id and one row. The callers' `approval_pending` notification
  keeps its dedupe because `transitionInstance` is the (same) request id.
- Plumbing: `execute(toolCallId, ...)` in `agentSessionComposition.ts` passes `{ toolCallId }` (merged with
  `reason`) to the generic operation agent tool, which hands `options` to
  `GenericOperationGateway.invoke(..., { reason?, toolCallId? })` and on to `preflightDestructiveApproval`.
  For MCP tools the function returned by `createApprovalGatedMcpInvokeTool` takes a third argument
  `invokeOptions?: { toolCallId?: string }` (`McpInvokeTool` type). REST and `/mcp` pass nothing, so NULL.

## Tests

- `approvalRequestsStore.test.ts`: store round trip, NULL when absent (several per run allowed), repeated
  `(run, tool call id)` returns the same request with one row, distinct runs/ids stay separate.
- `genericOperationGateway.test.ts` and `mcpInvokeTool.test.ts`: both creation paths store the id, a
  redelivery returns the same request id, and a call without an id stores NULL.
- `agentSessionComposition.unit.test.ts`: the generic tool now receives `toolCallId` in its options.

Ran: backend build, ESLint and Prettier, `check-migration-numbering`, and the four test files above (unit and
integration; integration outside the sandbox for embedded Postgres).

## Notes for dependants

- The thread of a request is still derived via `agent_runs.thread_id`; nothing exposes `toolCallId` to clients yet
  (gh-1887).
- A redelivered call returns the existing request whatever its status (it may already be decided).
