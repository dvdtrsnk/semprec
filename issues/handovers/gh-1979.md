## What was delivered

A tool sync now chooses a default `risk_class` and `requires_approval` from the annotations the MCP server advertises, and records who owns the two columns.

- Migration `0175_mcp_tool_classification_source.sql`: `mcp_tool_registrations.classification_source text NOT NULL DEFAULT 'annotation'` with the named CHECK `mcp_tool_registrations_classification_source_check` (`annotation` or `manual`). The whole change, including the backfill, runs inside a DO block guarded by the column's absence, so a second run changes nothing. Backfill: a row with the defaults (`unclassified`, approval required) stays `annotation`, every other row becomes `manual`.
- `classifyMcpToolFromAnnotations(hints | null)` in `mcp/mcpToolAnnotationClassification.ts` (pure). Order: no annotations object gives `unclassified` with approval; `readOnlyHint` true gives `read`, no approval; `destructiveHint` not explicitly false gives `destructive`, approval; `openWorldHint` explicitly true gives `outbound`, approval; otherwise `write`, approval.
- `mcpSync.ts` reads only the three boolean hints from each listed tool's `annotations` (non-boolean values dropped, a non-object becomes null) and passes the derived classification to the store.
- `upsertClassifiedMcpToolRegistration` (new, in `mcpToolRegistrationsStore.ts`, not in the barrel) writes the classification on insert and, on conflict, rewrites `risk_class` and `requires_approval` only for rows whose `classification_source` is `annotation` (CASE expressions; the snapshot, description and active flag of a `manual` row still refresh). The exported `upsertMcpToolRegistration` keeps its old signature, takes no classification and drops one smuggled past the type.
- `setMcpToolRiskClass` and `setMcpToolRequiresApproval` (`mcpGrantsAdminStore.ts`, still off the barrel) set `classification_source = 'manual'` in the same UPDATE and check the affected row count. `reclassifyMcpTool`, the writer behind `PATCH /api/mcp-tool-registrations/:id`, goes through them, so an approval-only or class-only PATCH makes the row manual; a display-label-only PATCH leaves it `annotation`.
- ADR `docs/adr/2026-11-14-mcp-tool-classification-is-owned-by-the-annotation-sync-until-a-person-sets-it.md`: the sync owns the two columns while `annotation`, a person owns them once `manual`, the transition is one-way, plus the READ COMMITTED interleaving, the public-surface rule, the openWorldHint rule and the backfill guard. It references the single-writer ADR without editing it.

## Deviations from the specification and spec seams

1. The Task says the upsert updates the two columns `WHERE classification_source = annotation`; a WHERE on DO UPDATE would also skip the refresh of schema, description and active of a manual row, so the two columns use CASE expressions on the source.
2. The two admin UPDATEs check `rowCount`/row (like `setMcpToolDisplayLabel`) because `check:write-safety` keys on statement text; behaviour unchanged.
3. The migration wraps ADD COLUMN and the backfill in a DO block guarded by the column's absence (running twice changes nothing); the inline CHECK is a named table constraint.
4. Spec seam: the first acceptance criterion words "only `openWorldHint: true`" as `outbound` and "annotations present but none of these" as `write`, but the Context's ordered mapping (rule 2, `destructiveHint` not explicitly false) classifies both as `destructive`. The code follows the ordered mapping; `outbound` and `write` need `destructiveHint` explicitly false. Both `{ openWorldHint: true }` and `{}` (or a title only) are pinned as `destructive` in the mapping table. The criterion wording should read "`destructiveHint: false` and `openWorldHint: true`".
5. The sync tests fake the MCP connection (the contract servers cannot advertise annotations and `testSupport` is not in `Touches`); the real SDK `ToolSchema` keeping `annotations` is not exercised end to end.
6. Docstrings that said the sync never touches `risk_class`/`requires_approval` were updated in `mcpSync.ts`, `mcpToolRegistrationsStore.ts` and `mcpGrantsAdminStore.ts`.
7. `mcpToolAnnotationClassification.test.ts` has the file name from `Touches` (integration tier) although the function is pure.
8. After review: the classifying upsert was split from the exported one and an ADR was added (not in `Touches`), both required by review findings.
