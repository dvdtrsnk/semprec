## Summary

Implements issue #105: confirm, reject, and revise for Processing proposals.

- **`inbox/proposalActions.ts`** (new): `confirmProposalWithClient`, `rejectProposalWithClient`, `reviseProposalWithClient`.
  - Confirm is the sole cross-destination write path: `database` envelopes go through the existing `createItemWithClient` choke point; `pageContent` envelopes go through a new `putBlockWithClient`. Persists `resultItemId`/`resultLabel` and locks `confirmed`. Idempotent under retry.
  - Reject locks `rejected` with no destination write; idempotent; refuses an already-confirmed proposal.
  - Revise replaces the complete envelope (including `entityKind`, so it can switch atomically between `database` and `pageContent`), appends a user-authored history entry, and refuses a locked proposal.
- **`docs/docPersistence.ts` / `docs/docStore.ts`**: added client-scoped `mutateDocWithClient`/`putBlockWithClient` so a page-content block append commits in the same transaction as the proposal's `confirmed` lock.
- **`inbox/inboxTickAction.ts`**: exported `appendHistoryEntry` (now with a selectable author) and `assertValidProposalEnvelope` for reuse.
- **`manifest/permissionManifest.ts`**: added `writable` to `ManifestDatabase` and scoped Semprec's own project grant so Inbox/Inbox item types are read-only and only Processing proposals is writable (grant separation).
- New tests in `proposalActions.test.ts` and a grant-separation test in `manifest.test.ts`.
