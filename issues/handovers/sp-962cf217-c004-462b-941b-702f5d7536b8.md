## Contracts dependents build on

- Import from `backend/packages/data/src/chokePoint/hooks.ts`: `registerItemPurgeHook`, `runItemPurgeHooks`, `ItemPurgeHook`, `ItemPurgeHookContext`. None of them is exported from the package barrel `backend/packages/data/src/index.ts` or from `testSupport/testDb.ts`. A consumer inside `@semprec/data` registers its hook in `backend/packages/data/src/domainWriteHooks.ts`; entry order there is meaningful, and a later source's entries go after those of the sources it declares as blockers.
- `ItemPurgeHookContext` is `{ client, database, item, rootItemId }`:
  - `client`: the `PoolClient` of the purge transaction, in the purging tenant's scope. What the hook writes through it commits or rolls back with the purge.
  - `item`: the `ItemRow` read under the row lock immediately before its delete, every field of it.
  - `database`: the `DatabaseRow` of `item.databaseId`. Its `ownerModuleId` tells a consumer which module's database the purged item belonged to.
  - `rootItemId`: the item the `purgeExpiredTrashSubtree` call was started for; it equals `item.id` for that item itself. It is not necessarily the item a user trashed: the sweep (`trash/purgeExpiredTrash.ts`) starts a call for each expired trashed item it reads, nested rows included.
- Registry semantics: a `Set`. Registering the same function twice is a no-op, hooks run one after another in registration order, and the first rejection propagates and stops the hooks registered after it for that row. There is no unregister.
- When a hook runs: the row and its built-in dependents (what `deleteItemDependents` deletes) are already gone for the hook's `client`. Rows are purged root first in the order of the subtree walk, so the rows later in that walk, the row's descendants among them, are not yet removed.
- A hook runs under the tenant's purge advisory lock of `docs/adr/2026-11-01-trash-purge-coordinates-roots-and-transactions.md`, so its work delays every other purge call of that tenant, and inside the transaction for which that record allows no storage or provider I/O. The hook returns nothing: there is no channel for work after the commit, and the sweep still removes blob bytes only for the storage keys `deleteItemDependents` returns.
- Not called by `softDeleteItem`, by `restoreItem` or by the tenant erase (`handleTenantPurgeTask`). The purge runs no delete hook and no restore hook. A domain that reacts to all three registers three hooks.
- A hook that throws keeps the whole subtree in the trash. The sweep logs the failed call with the raw error object and continues; the failed root is a candidate again on the next sweep. A consumer hook must therefore not put user content into the message of an error it throws.
- A test that calls `clearHooksForTests()` or imports a choke-point module by its deep path sees only the purge hooks it registers itself.
- No route, no generic operation, no MCP tool, no table, no migration, no job, no barrel export, no error code and no entry in `domainWriteHooks.ts` or `tenantCutoverMigrations.ts` was added.

## Review

Three reviewers read the segment read-only: requirements and tests (`8ab512e2^..b2f32a59`, verdict clear, all eight acceptance criteria rated covered), project rules and architecture (`8ab512e2^..8ab512e2`, one medium finding) and security (`8ab512e2^..b2f32a59`, verdict clear). The rules reviewer did not read the fix commit; the focused recheck, the requirements reviewer and the security reviewer did.

- Finding (medium, rules): the purge hook's `item` was an unlocked snapshot read before the delete, not the row the purge removed. Fixed in `b2f32a59` as the reviewer prescribed, for both consumers of the snapshot in the loop (the hook and `deleteItemDependents`), with three new tests. The recheck's verdict is pass with nothing unresolved.

Follow-ups, none of them changed in this chain:

1. Recheck, low: the locked read keeps a row lock on a race-restored live row until the purge transaction ends. A write to that row waits for the rest of the purge call, and a writer that holds another row of the same walk while it waits can deadlock with the purge; PostgreSQL aborts one side, and the sweep retries a failed call on its next run. It needs a restore that commits between the walk and the row's turn in the loop. The decision record states it.
2. Worker, fixer and all three reviewers, behaviour that predates this chain: the locked read does not compare the locked row's `deletedAt` with the cutoff, so a row that is restored and trashed again between the walk and its delete is still removed although its trash is fresh (`itemsStore.hardDeleteItem` guards only `deleted_at IS NOT NULL`). Proposed: compare the locked row's `deletedAt` with the cutoff before `hardDeleteItem`. It changes which rows the purge removes, so it belongs in a source of its own, preferably before gh-1691 lengthens the per-row work of the purge.
3. Rules and security reviewers, worker: `trash/purgeExpiredTrash.ts` logs the raw error object of a failed purge call, in logs that are not tenant-scoped. This matters to the consumer hook of gh-1691.
4. Requirements reviewer: the test of the re-trashed row uses a cutoff in the year 2999, so it does not pin the removal of a row newer than a real cutoff and would keep passing if follow-up 2 is done.
