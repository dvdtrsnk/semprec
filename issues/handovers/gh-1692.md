## What was delivered

- `GET /api/mail/threads/:threadId` answers a new `tasks` array: the not-deleted Tasks items that have a `Threads.tasks` edge from the thread's Threads item, each as `{ id, name, date, status, project, people, links }`.
- `project` is the task's live project as `{ id, name }` or `null`. `people` are the task's live people as `{ id, name }`, ordered by name and then id. A project or a person in the trash is left out.
- `links` holds the value-link entries of gh-1403 for `project` and `people` only, and only for a property that has a value-link row. A value link on any other property of the task does not appear.
- Order: tasks with status `notDone` first; every other task, one without a status included, after them. Inside each group by `date` ascending with undated tasks last, then by creation time and id.
- `name` is the stored name or an empty string. `date` and `status` are the stored canonical values or `null`; no label is resolved on the server.
- The tasks are read for the resolved thread id, so a merged-away id answers the tasks of the thread it was merged into. A thread without tasks answers an empty array.
- One statement reads the tasks with their projects and people (`THREAD_TASKS_SQL`) and one batched read (`getValueLinksForItems`) the links, so the number of statements does not grow with the number of tasks. A thread without tasks costs one extra statement per detail read.

## Deviations from the specification and spec seams

1. `backend/packages/data/src/mail/mailThreadsStore.ts`, which the issue's `Touches` names, does not exist. gh-1632 delivered the detail in `mail/mailThreadDetail.ts`, so the tasks read is there.
2. `mailThreadRouteHandlers.ts` of `Touches` is `mail/mailThreadRoutes.ts`. Its handler returns the read model unchanged, so the file needed no edit.
3. `ROUTE_CASES` has one case per route entry, so the isolation assertions were added to the existing "mail thread detail" case, with rows seeded inside the case.
4. "Not-done" is read as the status value `notDone`. `done`, `wontDo`, `missed` and a task without a status form the second group. The issue's wording can also be read as every task that is not done; the requirements reviewer left this to the owner.
5. A project or a person in the trash is left out of a task (`project` is `null`). The issue does not state it.
6. The test fixtures write the inherited value links with `insertValueLink` and a test rule key, because no link rule makes a task inherit from its thread yet (creating tasks is gh-1900). The break to `inheritedBroken` is produced by a real user relation write through the choke point.
