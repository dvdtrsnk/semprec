## Summary

This implements #185. Speaker keys now render from the `speakers` relation metadata: a mapped key shows the person's name, and an unmapped one shows a localized "Speaker N" / "Mluvčí N". Mappings are added, replaced and removed through the generic relation operation. AI can only suggest a mapping as a `kind = 'transcript'` card, built from the linked Event's participants and how people address each other in the transcript. Only confirming that card writes the user-owned edge.

This worktree started behind `develop` and didn't include #184's work (#469). I fast-forwarded the branch to `origin/develop` before starting, because this issue builds on #184's `'relation'` proposal shape.

### Rendering
- **Speaker list:** `listTranscriptSpeakers` returns each distinct speaker key in the order it first appears in the segments, with its 1-based number and the mapped person, or `null` if unmapped. `computed.segments` is only read, never rewritten, so a mapping change never touches segments or card fingerprints.
- **New route:** `GET /api/transcripts/:id/speakers` returns `{ speakers: [{ speaker, label, personId }] }`.
  - The label is resolved in the caller's `users.locale` from the new `transcription/i18n/{cs,en}.json` catalog.
  - A person with no name also falls back to "Speaker N".
  - It is registered in the systemDatabases manifest as a `single-consumer-read` custom route and added to the route matrix.

### Mapping through the generic relation operation
- **Checks on every write:** the choke point's `createRelationWithClient`, `updateRelationWithClient` and `assertRelationCreatableWithClient` now validate `speakers` edges. The metadata must be exactly `{ speaker }`, the key must occur in the transcript's segments, and it can't already be mapped to another person. The transcript row is locked, so concurrent writes for the same key run one after the other. Every rejection is the canonical `validation_failed` on `metadata`, with `reason` set to `unknownSpeaker` or `speakerAlreadyMapped`.
- **Add, replace, remove:**
  - `PUT` adds a mapping, or moves a person to a different key.
  - Giving a key to a different person takes two requests: `DELETE` the current person's edge, then `PUT` the new one.
  - `DELETE` removes a mapping.
  - Ownership and archived-database errors are unchanged.
- **Removed:** `writeTranscriptSpeakerEdge`. Nothing in production called it, and the generic write now enforces the same rules.

### AI suggestion is a proposal only
- **Envelope:** the `'relation'` envelope now takes an optional `metadata` object. A speaker card's envelope is `{ entityKind: 'relation', target: personId, properties: { propertyKey: 'speakers', metadata: { speaker } } }`.
- **Confirm and revise:** confirm writes the edge through the generic relation write, in the same transaction as the card update. A transcript card keeps its role: revise can change the person or the Event, but it can't turn an Event card into a speaker mapping or back.
- **New pipeline step 7, `suggestSpeakers`** (finalize is now step 8):
  - It runs only when the transcript is linked to an Event that has named participants who aren't mapped yet, and some keys are still unmapped.
  - It makes one gateway `complete()` call with the new `transcript_speaker_suggestion` operation (no project). The gateway allowlist now accepts that operation.
  - The response is validated. A suggestion is dropped if its key isn't open, its person isn't a participant, or it repeats a key or person already suggested.
  - It then creates idempotent cards and writes its checkpoint in one transaction. It never writes an edge.

### Docs
- New ADR `docs/adr/2026-09-23-speaker-mappings-are-edges-proposed-on-transcript-cards.md`. The existing ADRs say that a second producer of `transcript` cards, or any further write by the transcription worker, needs a new decision. This ADR records that decision and the new edge-metadata check in the choke point.
