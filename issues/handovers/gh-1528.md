# gh-1528 — icon and color on custom databases

Repository-Issue: gh-1528

This completion is proposed on an isolated implementation branch; it becomes canonical only after reviewed integration. No PR has been published by this worker.

## Delivered behavior

- Migration `0111_database_icon_color.sql` adds nullable `databases.icon` and `databases.color` with CHECK constraints `databases_icon_format` (`^[a-z][a-z0-9-]{0,63}$`) and `databases_color_format` (`^#[0-9A-F]{6}$`). Existing rows stay `NULL`. The runtime role has table-level privileges on `databases`, so no grant change was needed.
- `Database` (shared), `DatabaseRow` and the store mapping carry `icon` and `color`. `DatabaseCreateInputSchema` accepts optional `icon` / `color`; `DatabasePatchInputSchema.patch` accepts optional nullable `icon` / `color`. The color is upper-cased by the schema transform and again in the store.
- `databasesStore.patchDatabase(client, id, { name?, icon?, color? })` updates the given fields in one statement; `null` resets icon or color. `renameDatabase` is a thin caller. The choke point exposes `patchDatabase` (schema invalidation after commit), and `genericApplicationService.patchDatabase` now calls it. `renameDatabase` stays on the choke point for other callers.
- Setting icon or color on a system database (create or patch) throws `ForbiddenError` (HTTP 403); renaming one still works.
- `createCollectionMetadataResolver().resolve` returns the stored value or `DEFAULT_DATABASE_ICON` (`database`) / `DEFAULT_DATABASE_COLOR` (`#FF9500`) for user-created databases; system databases keep the manifest values. Both constants are exported from `@semprec/data`. Defaults are never written.
- `POST` and `PATCH /api/databases` forward `icon` and `color`.

- #1592 can pass `icon` and `color` through the create input; the create input schema and `createDatabase` store input already accept them.
