## What was delivered

A per-tenant cutover step, `runSempProblemsBackfillCutoverMigration(pool)` (`semp/sempProblemsBackfillCutoverMigration.ts`), that raises the Semp problems of the failures that already exist at deploy, under the dedupe keys of the producers, with the occurrence key `backfill`. It reads five current states in keyset pages of 100 rows, one transaction per page, source rows locked `FOR SHARE` and the problem key locked before it is checked:

- mailboxes with `syncStatus` `error` or `needsReauthorization`, or an alerting `mail:<id>` stall check: `mail:<mailboxItemId>`, critical for `needsReauthorization` or a reauthorization failure kind, `since` = `failing_since`, else `last_activity_at`, else now;
- active guidance drift findings: `guidance:<project>:<fingerprint>`, through the producer's writer (`createGuidanceProblemWriter`);
- heartbeats with `last_error`: `agents:heartbeat:<id>`, through `raiseAgentHeartbeatProblem`;
- non-transcript library items with `item_automation` error: `automation:<databaseId>`, one per database;
- transcripts with `item_automation` error: `transcription:<id>`.

A key that already has a problem (active or resolved) is skipped, a tenant without a user is skipped, a failing source does not stop the other sources of the tenant (one `AggregateError` after all five ran), and `forEachMaintainedTenant` keeps the other tenants running.

## Deviations from the specification and spec seams

1. The Task says to register after the existing steps; the step is registered before `runAreaNoteCutoverMigration`, which every recent entry documents as staying last.
2. Blocker gh-1950 is open (`Shared-file ordering`) and has no handover; its entry goes before this one when it lands.
3. Beyond the Task text, a key that already has a problem, active or resolved, is skipped: `raiseProblem` counts an occurrence when the occurrence key differs from the stored one, so an existence check is the only way to keep a producer's count and `first_seen_at` unchanged; the resolved case keeps a recovered source from being raised again at every deploy (the step runs on every deploy). An existing warning problem is not escalated for a `needsReauthorization` mailbox.
4. Exclusions mirror the producers: done transcripts, error code `deleted` and trashed rows raise nothing; guidance for a trashed or purged project is skipped because `raiseProblem` rejects a project reference outside the Projects database.
5. `since` is set only for mail (the Task defines it only there); the other sources start now.
6. Each created problem also writes its `semp_problem` notification (inherent to `raiseProblem`), so one deploy can push one notification per backfilled problem.
7. The Touches list names a barrel export "if the step is exported"; none was added.
