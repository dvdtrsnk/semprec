# Handover: take the sync state row before the mail-thread guard in a Mail-off chunk, as a sync pass does

Commit on `fix/ia-mail`: `f1e762008`. Nothing was run against a real server.

**Root cause.** `lockMailOffEpoch` (`mail/mailboxRemovalJob.ts`) took the mail-thread guard and then the paused sync state row `FOR SHARE`, with a comment calling that the pass's order. A pass's transaction renews its lease on the sync state row (`enterSyncPass`) and only then takes the mail-thread guard, so a chunk and a pass of an account switched on again while the Mail-off job still runs could deadlock. The documented lock order for the pass was equally untrue.

**Changes.**
- `mail/mailboxRemovalJob.ts`: sync state row `FOR SHARE` → mail-thread guard → Mailboxes item `FOR SHARE`; the comment states that order and why.
- `docs/architecture/domain-mail-and-inbox.md`: the Mail-off job paragraph and the lock orders (sync pass: mailbox sync guard → sync state row → mail-thread guard → Gmail folder-state guard → folder/item rows; Mail-off chunk: sync state row → mail-thread guard → Mailboxes item → member rows).

**Tests** (`__tests__/mailboxServices.test.ts`): a transaction that renews the lease and then, once the Mail-off chunk waits for the row, takes the mail-thread guard; both finish and the mail is removed. With the old order Postgres reports `deadlock detected`.
