# Handover for gh-1390

The write phase of the Inbox tick now enqueues the Journal day's `JOURNAL_INBOX_RECOMPUTE` job in the same transaction as each card write, so `computed.inboxItems[].status` follows the card the tick creates or revises. The work is committed locally; I did not push or open a PR.

- **Code:** in `inbox/inboxTickAction.ts`, `enqueueJournalInboxRecomputeForInboxItem` runs after the card write in four places: the create path of `writeTickResult`, `reviseProposal`, and both the create and revise branches of `writeNeedsClarification`. `reviseProposal` gained a `sourceItemId` parameter for this. Paths that write nothing (stale skips, locked or same-fingerprint no-ops, a lost lock race) enqueue nothing.
- **Tests:** the new `inbox/__tests__/inboxTickRecompute.test.ts` has six cases. Each clears the pending recompute jobs inside the compute step, so only a write-phase enqueue is observed. They cover create, revise, needs-clarification create and revise (the job key is the day's key and the drained job sets the new status), and a skip after the item changed and after it was deleted (no job). The targeted run together with `inboxTickProposal` and `journalInboxCompute` passes (53/53); prettier, eslint and the `data` package typecheck pass. I did not run the full `pnpm run verify`.
- **For dependants (#1489):** after any tick that writes a card, the day's cache is recomputed once the job runs. The job key is `journal-inbox-recompute:<dayId>`, so repeated enqueues collapse.
