# gh-1592 — create a custom database with its properties in one call

Repository-Issue: gh-1592

This completion is proposed on an isolated implementation branch; it becomes canonical only after reviewed integration. No PR has been published by this worker.

## Delivered behavior

- `DatabaseCreateInputSchema` accepts optional `titlePropertyName` (non-empty) and `properties` (at most 50). An entry is `{ key, name, type, config? }` for `text`, `number`, `select`, `date`, `checkbox`, `url`, `file`, or `{ key, name, type: "relation", targetDatabaseId, cardinality }`. Keys must be unique and differ from `name`; a duplicate is a validation issue naming the key. `title`, `rollup`, `multi_select` and every other type fail validation. `DATABASE_CREATE_TITLE_PROPERTY_KEY` (`name`) and the `DatabaseCreateProperty` type are exported from `@semprec/shared`.
- New choke-point operation `createDatabaseWithProperties(input, titlePropertyName, properties, actingUserId?)` in `databaseOps.ts`. In one `withTransaction` it creates the database (with `icon`/`color`), the `title` property `name`, then each listed property through `propertiesStore.createProperty` or `createRelationPropertyWithClient` (unlocked, no inverse). The computed-key collision guard runs for every key. One schema invalidation is published after commit; any error rolls back the database, partition and properties.
- `createRelationPropertyWithClient` and its input types moved to the new `chokePoint/relationPropertyWrites.ts` (still re-exported from `relationPropertyOps.ts`), because the `no-choke-point-domain-cross-import` rule forbids `databaseOps.ts` importing `relationPropertyOps.ts`. No behavior change.
- `genericApplicationService.createDatabase`: with `properties` present, a non-REST actor (no `restSession`) gets `ForbiddenError` before any write; otherwise it calls the new operation (title name defaults to `"Name"`). Without `properties` the path is unchanged and still returns a `Database`.
- `POST /api/databases` forwards `properties` and `titlePropertyName`; the latter defaults to `"Název"` for a Czech user and `"Name"` otherwise.

## Notes for dependants

- Issue wording conflict: the acceptance example lists properties in creation order (`name`, `recipient`, `when`, `status`), but `GET /api/databases/:id/properties` orders by `key` (`propertiesStore.listPropertiesByDatabase`: `ORDER BY key`), and `properties` has no position column. Creation order is therefore not observable; the handler test uses keys whose alphabetical order matches creation order. Changing the listing order was outside this issue's scope.
- The `PropertyCreateInputSchema`-style union gives a generic union error for an invalid entry, but the missing field of a relation entry is still named in the issue path.
- The MCP and agent tool contract tests needed no change; the wider create schema only adds optional fields.
