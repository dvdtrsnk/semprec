# Handover for gh-1637

Gmail API mailboxes can send. `GmailRestClient.sendMessage` posts the raw MIME to `users.messages.send`, and a new `gmail_api` transport (`backend/packages/data/src/mail/gmailTransport.ts`) refreshes the access token and submits it. The factory picks that transport for the `gmail_api` sync mode. Nothing supplies the factory's Gmail OAuth client from a composition root yet, so no production send goes through Gmail until one does (#1896). I did not push or open a PR.

## What was added

- **`GmailRestClient.sendMessage(raw, threadId?)`** (`gmailRestClient.ts`): base64url-encodes the raw MIME into `raw`, adds `threadId` only when one is given, and returns `{ id, threadId }`. It uses the same 30 second `AbortSignal.timeout` as the other Gmail calls. A response that lacks either id is an ordinary error.
- **Error mapping** (`sendFailure`): when the failed response's body names an invalid recipient, the error is `MailRecipientRejectedError`, whatever the status. Otherwise a 400 or 401 is `MailReauthorizationRequiredError`, and any other status is a plain `Error`. The body is read for at most 4 096 bytes, and the stream is cancelled after that. Thrown messages carry the status only, never the body or a token.
- **`createGmailMailTransport`** (`gmailTransport.ts`, new): each send builds a fresh `GmailRestClient`. Its token source calls `refreshAndPersistAccessToken` with `GOOGLE_TOKEN_URL` and the purpose `gmail_api_send`. The send passes `message.providerThreadId` as `threadId` and returns `{ providerMessageId }`. No access token is cached between sends.
- **Factory** (`mailTransport.ts`): `createMailTransportFactory(pool, options?)` takes `MailTransportFactoryOptions { gmailOAuthClient?, fetchImpl? }`. For `gmail_api` without `gmailOAuthClient` it throws `No Gmail OAuth client is configured for this composition root` before reading anything. `graph_api` still has no branch (#1753).
- **Type comment**: `MailTransportMessage.providerThreadId` is now documented as the thread of the message being replied to. The SMTP transport still ignores it.

## Notes for dependants

- **#1896 (send route)**: `sendDraftEmail` (`send.ts`) does not set `providerThreadId` yet. It calls `transport.send({ raw, envelope })` only. Until the send path resolves the source message's `mail_message_meta.provider_thread_id` and passes it, a production reply is sent without a thread id. The transport handles the id correctly when it is given.
- **#1896, delivery unknown**: a Gmail send that times out after the server accepted the message surfaces as the raw abort error. It is not mapped to a Mail error, and `sendDraftEmail` undoes the claim on any error. A retry can then resend the message, as the SMTP note in #1634 describes. Treat a timeout as "delivery unknown" in the route.
- **#1896, status mapping**: `MailRecipientRejectedError` and `MailReauthorizationRequiredError` carry no address or token. Map them to their statuses. A 400 that is not about a recipient, such as a malformed MIME, also becomes `MailReauthorizationRequiredError`, because the Task maps every 400 or 401 that way. A caller that marks the mailbox `needsReauthorization` on that error will mark it wrongly.
- **#1753 (Graph)**: add a `graph_api` branch to `forMailbox` the same way. The factory options are where its client settings would go.
- **Composition root**: `createMailTransportFactory` is not yet called with `gmailOAuthClient`. The Gmail OAuth keys are read by `createMailSyncAdapters` (#1505) and are not passed here.
- **Credential access log**: the send's token refresh is recorded with actor `sync_worker` (hard-coded in `refreshAndPersistAccessToken`) and purpose `gmail_api_send`. Tooling that counts sync-worker reads by actor will count sends too. Changing the actor needs an `actorType` option on `refreshAndPersistAccessToken`, which this issue did not add.
- **Recipient wording is inferred**: the `RECIPIENT_REFUSAL` pattern in `gmailRestClient.ts` (`invalid to/cc/bcc header`, `invalid recipient`, `recipient address rejected`) comes from Gmail's error text as understood, not from a captured live response. A refusal worded differently falls through to the status mapping. Check it against a real refusal before relying on the recipient error.
- **Known gap, same as #1505**: the success response of `sendMessage` is read with `response.json()` and no size cap, as the other Gmail calls are. The io-hardening outbound cap is a candidate follow-up, not part of this issue.
