## What was delivered

- The generic operation `item.count`, the 40th entry of the catalog (`backend/packages/shared/src/genericOperations/`): capability `core.item.read`, non-destructive, risk class `read`, no approval.
  - Input `ItemCountInputSchema`: `{ items: [{ databaseId, filter?, groupBy?, collection? }] }`, strict at both levels, 1 to 20 entries, `databaseId` a canonical UUID, `filter` the shared `filterNodeSchema` that `database.query` takes, `groupBy` a non-empty string, `collection` a boolean.
  - Output `ItemCountEntry[]` in input order: `{ databaseId, count, groups? }` with `groups: [{ key: string | null, count }]` present exactly when the entry named a `groupBy`. `databaseId` repeats the entry's own value.
  - Port method `GenericApplicationPort.countItems(actor, input)`; `createGenericApplicationService` implements it as `chokePoint.countItemsBatch(input.items, { resolver })`.
- Data layer:
  - `itemsStore.countItemsGrouped(client, databaseId, { buildFilterSql?, grouping? })` in `backend/packages/data/src/chokePoint/itemsStore.ts`: one statement per call, every value a bound parameter. It never counts a soft-deleted item, and a database whose `archived_at` is set counts nothing (`count: 0`, and `groups: []` when a grouping was asked for).
  - A `select` grouping returns one group per stored value that occurs: the declared options in `config.options` order, then any other stored value in byte order, then `null` for a missing, JSON null or empty-string value.
  - A `relation` grouping returns one group per target item that occurs, ordered by target id, then `null`. A target counts only while it is a live item of the property's target database and that database is not archived; an item whose every edge ends at a trashed item or in an archived database is in the `null` group. An item with several targets is in each of their groups and once in `count`.
  - `chokePoint.countItemsBatch(entries, { resolver, now? })` in `backend/packages/data/src/chokePoint/itemReads.ts`: one transaction for the whole batch under the caller's tenant. Each entry resolves its database first, so an unknown and a foreign id throw the same `NotFoundError` (`Database <id> not found`, `{ resource: "database", databaseId }`) that `database.query` gives, and that error fails the whole batch. With `collection: true` the caller's filter is ANDed with the collection filter the resolver declares for the database; a database without one is counted unfiltered. `groupBy` is resolved against the database's own properties; an unknown key, a property type other than select or relation and a relation without a resolvable definition or target database throw `ValidationError` with `field: "groupBy"`.
- `CollectionMetadataResolver.collectionFilter(database)` in `backend/packages/data/src/manifest/collectionMetadata.ts`: the filter tree the module manifest declares for a system database (issue #1647), a fresh copy each call, `undefined` for a user-created database and for a system database without one. The REST, MCP and agent composition roots already pass the resolver, so they serve the declared filter without new wiring.
- `POST /api/items/count` in `backend/services/semprec-api/src/itemsHandler.ts`: the body is a JSON object with the one key `items`; it dispatches `item.count` and answers 200 `{ counts: [...] }`.
- The route matrix entry `{ name: "count items", method: "POST", path: "/api/items/count", surface: "api", public: false, tenancy: "tenant" }` in `backend/services/semprec-api/src/routeMatrix/items.ts`, its `ROUTE_CASES` case, its owner probe and its `MCP_CASES` case `item.count` in `tenantIsolationRoutes.test.ts`, and its `ROUTE_HANDLER_FILES` mapping to `services/semprec-api/src/itemsHandler.ts`.
- `operationInputJsonSchema("item.count")` in `backend/packages/shared/src/genericOperations/jsonSchema.ts` shares local definitions under `properties.items` for every transport, decided in `docs/adr/2026-11-10-item-count-schema-shares-local-definitions.md`. The worker measured 10,494 bytes instead of 37,127,114 for the unrolled default; the queue runner did not recompute the figures.

- `count` is always the total of the filtered items, whatever the grouping. Counts never include soft-deleted items and there is no `inTrash` option.

- The catalog has 40 operations. A source that adds an operation changes `operationNames.ts`, the exhaustive records of `capabilities.ts`, `bindings.ts`, `port.ts` and `schemas.ts`, the count assertions of `operationCatalog.unit.test.ts` and the `defaultHashes` of `jsonSchema.unit.test.ts`.

- `selectOptionKeys` is now exported from `backend/packages/data/src/views/sortCompiler.ts` (inside the package, not from the barrel) and decides the option order of a select grouping.
- The number of groups of a relation grouping is not capped; a response is bounded by the caller's own tenant data.
- The operation publishes no realtime invalidation. A relation-based count follows edge changes through the invalidation of gh-1621, not through anything added here.
- No SQL migration, no table, no column, no index, no job name, no write hook, no stored key and no user-facing label was added.

## Deviations from the specification and spec seams

1. Spec seam: the route entry is in the slice module `backend/services/semprec-api/src/routeMatrix/items.ts`, not in `routeMatrix.ts`.
2. `Touches` names `chokePoint.ts` and the data `index.ts`; neither changed. The choke point type is derived from `createChokePoint` and no type needed a barrel export.
3. Not in `Touches`: `CollectionMetadataResolver.collectionFilter`. The Task does not say how the application layer reaches the manifest's collection filter; the resolver that relation expansion already receives carries it.
4. Not in `Touches`: the JSON Schema change in `jsonSchema.ts` and its ADR. Without it the complete agent tool catalog exceeds the 4 MiB request limit. Test files changed for it: `jsonSchema.unit.test.ts`, `agentQuerySchema.unit.test.ts`, the native transport fixture `refExpansionGateway.ts` and `sempMessageTask.test.ts` (a third schema observation; the fixture's message cap went from 512 to 768 characters).
5. REST envelope: `{ counts: [...] }`, like `{ relations }` and `{ databases }` of the same family. The Task defines only the operation output, which MCP and agent tools return bare.
6. A soft-deleted relation target is treated like a target in an archived database (no group, the item counts under `null`), as `relation.list`, relation expansion and `relation_is_empty` treat it. The Task names only archived databases.
7. Orders the Task leaves open: relation groups by target id with `null` last; in a select grouping a stored value that is not a declared option comes after the declared options in byte order and before `null`.
8. An archived database with `groupBy` answers `groups: []`; without `groupBy` there is no `groups` key.
9. `selectOptionKeys` of `views/sortCompiler.ts` is exported and reused for the option order (not in `Touches`).
10. `countItemsBatch` takes a `now` option, the clock seam `listItems` and `countItems` already have. Only the `date_relative` test passes it.
11. "Nine overview collections": eight databases declare an `overviewOrder` on this tree (projects, events, people, companies, files, healthRecords, books, movies), so the test counts those eight plus Tasks.
12. A malformed entry filter answers exactly what `database.query` answers for it, which for some shapes carries no `field`.
13. Comments that counted the catalog's operations now say 40 in the files this source touches.

## Review

Three reviewers read `0d0b67ae^..331f8352` at the candidate commit, read-only, and ran no build and no test: requirements and tests (verdict clear, no finding, all eight criteria covered), project rules and architecture (verdict clear, no finding) and security (verdict clear, no finding). Observations recorded without a finding, not changed and not filed as issues:

- Rules reviewer: `countItemsEntry` parses and compiles the module-declared collection filter together with the caller's filter. A declared filter that the grammar or the tenant's schema refused would answer 400 `validation_failed` to a caller that sent only `collection: true`, where `views/areaFilter.ts` turns a refused declared area filter into a configuration error. No trigger exists on this tree: the module manifests are a fixed in-repo list, their declared filters are grammar-checked and executed in tests, and the one declared collection filter (Projects: `is_empty systemActive`) names a seeded system property. A source that lets a tenant or a new module declare a collection filter should revisit this.
- Security reviewer: the number of groups of a relation grouping is uncapped (the Task sets no cap), so a response is bounded only by the caller's own tenant data; and `core.item.read` now also allows filtered counting of a database by id, which is what the Task specifies.
- Requirements and rules reviewers: the byte counts the ADR states were not recomputed.
