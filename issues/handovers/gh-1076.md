Issue #1076 is implemented and committed on the checked-out branch in two commits. The reset link now carries its token in the URL fragment, and the web app has a password-reset page. Both verify pipelines pass.

## What changed

**Backend**
- `passwordResetActions.ts`: the emailed link is now `<APP_BASE_URL>/?page=password-reset#token=<token>`. The query string carries no token.
- Two backend test files updated to read the token from the fragment. A third, `identityTablePrivileges.test.ts`, also parsed the query token and failed in the first verify run. It is not in the issue's Touches list, but the change is a direct consequence of the Task, so I updated its one line.

**Web**
- `authOperations.ts`: `requestPasswordReset` and `resetPassword`. A rejected reset token (any of the three `password_reset_token_*` codes, status 400) maps to `unavailable`. Everything else maps to `retryable`. The consume body is read once.
- `main.tsx` and `App.tsx`: a `password-reset` route, rendered outside `SessionGate` like `setup`, with `useSession` skipped.
- `views/passwordReset/PasswordResetPage.tsx` (+ CSS): the email request form and the new-password form. The fragment is cleared with `history.replaceState` on mount. The page has success, invalid-link and retryable states.
- `LoginPage.tsx`: a "Forgot password?" link to `?page=password-reset`.
- `i18n/messages.ts`: `login.forgotPassword` and `passwordReset.*` in both `en` and `cs`.

**ADR**
- `docs/adr/2026-10-17-secret-link-tokens-travel-in-the-url-fragment.md` records the fragment rule. It covers the reset link and the invitation link, which already builds `?page=invite#token=`. The setup wizard's `?token=` is deliberately left unchanged.

## Choices I made
- The ADR says only the password-reset page clears the fragment. I did not verify the invitation page, so the ADR does not claim it does.
- The `#token=` fragment is not part of the setup wizard change, as the issue says.
