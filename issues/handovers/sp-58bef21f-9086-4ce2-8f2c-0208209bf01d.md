# Handover: Add a capture to the diary Inbox without reloading the page

**Cause (reproduced on the simulator before the fix).** A capture sent from the diary's capture row did two things:
`CaptureOutbox.add` emitted the change signal (sp-256f9fba-cc77-4439-ba05-e29662015dbb), whose handler in
`JournalViewModel` dropped every kept period and started an in-place read of the shown day; then the Swift page's
`onChange(of: capture.captured)` called `onCaptured`, which `JournalScreen` wires to `viewModel.retry`. The shared
`Retry` ran `load()` without `keepsContent`, and since the change had just emptied `kept`, the diary went to
`JournalPhase.LOADING`. `JournalScreen.content` then swapped the whole `ScrollView` for `StatusView(.loading)` and
back: the page was made again, the note editor was re-created and read its page again, and the scroll went back to the
top. Observed on "Semprec iPhone 18 Pro" (iOS 27) against a local API behind a logging proxy: with the diary scrolled
so only the day row of the axis was pinned, a capture left the page scrolled back to the top (full axis visible) and
the proxy logged `GET /api/items/<day note id>/page.md` (the note editor's read) right after the capture, besides three
reads of the day.

**Fix (shared).** `JournalAction.Retry` over a shown period (`phase == CONTENT`) now loads with `keepsContent`: the
period stays on screen until the answer replaces it (`show`, which keeps the page ref, so the note editor's identity
`.id(page.ref)` is unchanged), and `load` leaves it shown when the selected period is the shown one and the read fails
(`stays`). A retry from an error still passes through LOADING as before. Swift is unchanged; the capture row still
asks for a retry, which also covers a capture made while a period load was running (the gap named in the blocker's
handover), because a retry cancels that load and reads again.

**Tests** (`JournalRetryTest`, beside `JournalViewModelTest`, which is at detekt's class size limit): "the write of a capture and the retry after it add the entry in place without
loading" (change signal, then Retry while the read is held: still CONTENT with the same page and Inbox; after the
answer the Inbox has the new entry appended and page, events, birthdays, weeks, axis and shown are unchanged) and "a
retry after a write over a shown period that cannot be read keeps it shown". Both failed against the previous
`JournalViewModel` (`:shared:presentation:jvmTest --tests JournalRetryTest`, 2 tests, 2 failed) and pass with the
fix.

**Simulator after the fix** (screenshots in the thread storage under `diary-reload/`; `before-fix-*` are the
reproduction):
- Online: diary scrolled (only the day row pinned), capture "Online capture after fix" sent; the row was inserted at
  the end of the Inbox, the scroll position, axis, week, events and note stayed; no `page.md` read was logged
  (`after-fix-online-*`).
- Offline (the local endpoint stopped): the offline banner appeared; capture "Offline capture after fix" was inserted
  as a waiting row with the clock symbol, scroll position and the rest of the page kept, banner "1 change waiting"
  (`after-fix-offline-*`).
- Back online (endpoint started again): the waiting row became the server's row in place, scroll kept
  (`after-fix-back-online.png`). The `page.md` read logged then belongs to the offline warm-up after reconnecting
  (`OfflineWarmup` reads the kept days and their notes), not to the editor.
- Not driven: a capture from the Action-button shortcut while the diary is open. It reaches the diary only through
  the change signal, whose handler already updates in place (no Retry, no LOADING); covered by the existing shared
  test "a write elsewhere in the window reads the period again but keeps the page and the axis".

**Open points.** Each capture made in the diary still reads the shown day more than once (the change signal's read, the
retry's read, which cancels the former while it still runs, and the read after the server created the item); the page stays in place for all of
them. The neighbours of the shown period are dropped on a change and read again (existing behaviour); they lie
outside the view.
