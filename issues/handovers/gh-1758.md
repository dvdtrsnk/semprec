## What was delivered

- An agent under a run (`agentRunId` set, no `approvedRequestId`) whose write would end an active value link is deferred through `ApprovalRequiredForWrite` with a `{kind: 'breaksLinks'}` reason, raised inside the write transaction before the link is broken: `item.patch` (changed linked key, in `updateItemWithClient`), `relation.put` (inserted edge with an `on` link on either side, in `createRelationWithClient`), `relation.set` (a removed edge by replacement or clearing; onto an empty relation it stays immediate), `link.unlink` (new `changeValueLinkWithClient`, extracted from the transaction wrapper). `relation.delete` adds no trigger (it stays destructive and only reports the links).
- `chokePoint/valueLinkApproval.ts` holds the detection and the no-wait reservation used by the projection. `valueLinksStore` gains `lockOnValueLinksOfProperties` and `listOnValueLinksFollowing`.
- `destructiveProjection.ts` returns `valueLinks` and hashes the links (id, rule, sources) and the linked values (for `item.patch` instead of the item version, unless the owning module contributes a patch snapshot) into the `item_patch`, `relation_put`, `relation_set` and new `link_unlink` snapshots.
- The gateway (`genericOperationGateway.ts`) sets risk class `breaksLink` and the description key `approval.breaksLink` for the four operations, stores `breaksLinks` and `endsInheritance` in the `approval_requests.description` jsonb, replays `link.unlink` with `approvedRequestId`, and the queue entry and the decision view (list, PATCH, GET `:id`) carry both lists as top-level fields (always arrays). A flagged write of a non-deferrable operation (for example `item.create` with initial relations onto a linked target) is refused with `ValidationError` `validation_failed` carrying the reasons; nothing is written and no request exists.
- `approval.breaksLink` in `seed/i18n` and `notifications/i18n` (cs, en) and the notification body mapping. ADR `2026-11-12-an-agent-write-that-ends-a-value-link-requires-approval` narrows `2026-11-04-flagged-agent-writes-require-approval`.

## Deviations from the specification and spec seams

1. Replay lives in `genericOperationGateway.replayApprovedGenericOperation`, not in `mcp/approvalRequestExecution.ts` (that file handles MCP invokes).
2. The lists are stored in the existing `description` jsonb and returned as top-level fields; no migration.
3. Files outside the Touches list that the Task cannot work without (see Files above, plus the notification catalogs and the narrowing ADR).
4. `item.patch` and `relation.put` defer on any change that ends an active link; `relation.set` defers only when it removes an edge, so `relation.put` onto an empty linked relation defers while `relation.set` onto it does not.
5. `endsInheritance` lists the active links that follow the broken (item, property); `sourceName` is the name of the broken link's source item.
6. The item.patch snapshot hashes the links and linked values instead of the item version, except that a module-contributed patch snapshot keeps the whole item in the hash (recorded in the ADR).
7. Existing tests that asserted an agent run ends a link at once now assert the approval request or break the link first.
8. At the merge with the train, `preflightDestructiveApproval` publishes the new request after commit with `createPendingApprovalRequestAndPublish` (from the tip) using this source's description and risk class.
