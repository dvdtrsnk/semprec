# Handover: model synced calendars and their remote identity

Implementation commit `fd939c382` on `feat/internet-accounts`.

**What changed.**
- Calendars `kind` has a new option `account` (`seed/seedCalendars.ts`). New Calendars properties, all `owner: system`, owner process `calendar`: `remoteName` (text), `remoteColor` (color, `#RRGGBB`), `readOnly` (checkbox). New relation `Mailboxes.calendars` (property A) ↔ `Calendars.account` (property B), `one_to_many`, both sides system-owned by owner process `calendar` (edge writes need `SystemRelationWriteContext { ownerProcess: "calendar" }`). The labels are in `calendar/i18n` and `mail/i18n` (`property.mailboxes.calendars.name`).
- Writer identity: `WriterIdentity.systemProcess?: SystemWriterProcess` (`"calendarSync"`) and `CALENDAR_SYNC_WRITER` in `chokePoint/writerKind.ts`.
- Calendar row rules (`calendar/calendarRowHooks.ts`): only `CALENDAR_SYNC_WRITER` may create a calendar of kind `account` or write `remoteName`/`remoteColor`/`readOnly` (403 `owner_violation`; another calendar-module process passing `allowedSystemKeys` is refused too). Remote fields on a non-account calendar give 400 `validation_failed`. `name` and `color` may be `null` only on an account calendar, where null means the remote value. A null or blank value is refused on every other kind, for system writers as well. Users may rename, recolour, mute and hide an account calendar. It can never be made default (400 `validation_failed`, "An account calendar cannot be the default calendar"). Account calendars do not count as own calendars for the default mark or for `last_own_calendar`.
- Trash (`calendar/calendarTrashHooks.ts`): a user or agent trash of an account calendar answers 403 `forbidden` (field `kind`). A `system` writer may trash it, and its live Events go with it as for any calendar. Restore of an account calendar is not guarded.
- Event writes (`calendar/accountCalendarWriteGuard.ts`, new; registered in `domainWriteHooks.ts`): in a read-only account calendar, a user or agent create (`createEventInCalendar`/`withChosenCalendar`, or an initial `calendar` relation), update, trash, or move into or out of it (an `Events.calendar`/`Calendars.events` edge written or deleted) answers **403 `calendar_read_only`** with `details.calendarId`. An agent's `item.delete` is refused with the same code by the approval projection. For this, `ItemDeleteApprovalGuard` may now return `{ message, code }`, a generic change in `chokePoint/hooks.ts` and `destructiveProjection.ts`. A writable account calendar is a valid chosen calendar.
- Lock order: the Events update and delete pre-lock hooks lock the Event's account calendar row `FOR SHARE` before the Event's row, the order a calendar trash uses. The post hooks read `readOnly` under that lock.
- Timeline: `readCalendarIds` also returns `readOnlyCalendarIds`. Stored Events of a read-only account calendar are `readOnly: true`, all others `false`.
- Side tables (baseline edited in place): `calendar_remote_state` (PK `(tenant_id, calendar_item_id)`, `remote_id text NOT NULL`, `remote_url`, `sync_token`, `ctag`, `last_synced_at`, `last_error_code`) and `event_remote_state` (PK `(tenant_id, event_item_id)`, `calendar_item_id NOT NULL`, `remote_id text NOT NULL`, `remote_href`, `etag`, `base_snapshot jsonb NOT NULL DEFAULT '{}'`, CHECK object; unique `(tenant_id, calendar_item_id, remote_id)`). Both have tenancy=tenant, RESTRICTIVE `tenant_isolation` and permissive `tenant_rows` policies, FKs `(tenant_id, item)` → items `ON DELETE CASCADE DEFERRABLE INITIALLY DEFERRED` (event_remote_state on both item columns), and grants to `alldots_side`. There is no store module yet, because no writer exists.
- Docs: `docs/architecture/domain-calendar-tasks-and-media.md` (Tenancy, Calendars, Event creation, Timeline, Event trash lock order) and the FK table in `data-model-and-writes.md`.

**Contracts dependents build on.**
- Kind `account`; relation keys `Calendars.account` / `Mailboxes.calendars` (owner process `calendar`); fields `remoteName`, `remoteColor`, `readOnly`. The calendar sync writes them through the choke point with `{ writer: CALENDAR_SYNC_WRITER, allowedSystemKeys: [...], systemOwnerProcess: CALENDAR_MODULE_ID }` (see `createAccountCalendar` in `__tests__/accountCalendars.test.ts`).
- `CALENDAR_SYNC_WRITER` / `writer.systemProcess === "calendarSync"` is how later hooks recognise the sync (the push issue: "any writer except calendarSync"). Delete and restore hook contexts carry only `writerKind`, not `systemProcess`, so a later trash hook that must recognise the sync has to add it to `hookWriterFields` in `chokePoint/itemTrash.ts`.
- Error code `calendar_read_only` (403, `details.calendarId`).
- Tables `calendar_remote_state`, `event_remote_state` as above. They are exported with the tenant: they hold no secret, the same as `mail_account_sync_state`.

**Deviations and spec seams.**
- "Refused unless the writer is calendarSync": every `system` writer passes the event guard and the account-calendar trash, not only `calendarSync`. Refusing other system writers would break the internal writers of derived fields: the daily `nextOccurrenceDate` refresh, which updates every stale recurring Event as the system writer, and value-link propagation. It would also break cascades that pass the system writer kind on (a calendar trash trashes its Events with the trash's writer kind). Users and agents are refused as the acceptance criteria say. The sync identity alone is required for the account calendar fields.
- `remoteName`/`remoteColor`/`readOnly` use owner process `calendar`, the same as `kind`, not `calendarSync`. The choke point checks a single `systemOwnerProcess` per write, and the sync's create writes `kind` together with them. Exclusivity to the sync is enforced by the writer check in the row hooks.
- "Allow name null": a user cannot set an account calendar's `name` back to null, because the generic choke-point title rule refuses a blank title from users and agents. A user can clear `color` with null. The sync, as a system writer, can store a null `name`.
- "The calendars list exposes kind, accountId, …": there is no dedicated calendars endpoint; clients read the Calendars database through the generic item and query routes. `kind`, `readOnly`, `remoteName` and `remoteColor` are ordinary properties. The account is the `account` relation, read through the query's relation expansion (`relations.account[0].id`); there is no stored `accountId`. Additive for `HttpCalendarCatalogRepository`, which skips a calendar without `name`/`color` (account calendars with null name/color stay invisible on mobile until the client falls back to `remoteName`/`remoteColor`).
- `tenantExportJob.ts` is unchanged (see export above).
- Other user writes on read-only Events are not refused: participant, project and other relation edges, and restore from the Trash.
- Rare deadlock window: the nextOccurrence refresh and edge writes lock the Event before the calendar share lock. That is the opposite order to a calendar trash, so the two can deadlock if they run at the same moment on the same account calendar. Postgres detects it and aborts one of the transactions.
