## What was delivered

- `POST /api/semp/threads/:id/messages/:messageId/retry` queues another attempt of the latest assistant reply of a thread when it is in status `error`, or `done` with incomplete steps. Response 202 `{ messageId }` of the new message. `retrySempReply` (`semp/sempMessagesStore.ts`) takes the thread row lock, then the message row lock, inserts a queued assistant message with the same `reply_to_message_id` and the next `attempt`, updates the thread's last activity and enqueues the turn in the same transaction.
- Anything else (not the latest message, a successful reply, a queued or running reply, a user message, an assistant message that answers no message) is 409 `retry_not_latest` and changes nothing; an unknown, foreign or other-thread thread or message id is 404 `not_found`, identical to a random id.
- Fix round: the retry (and the regeneration of gh-1930) runs the Inbox send guard for a thread of an Inbox item, so a decided proposal answers the same 409 `proposal_locked` as the send path; the guard runs before the thread lock (the lock order of `sendSempMessage`).
- Migration `0168_semp_messages_attempt.sql`: `semp_messages.attempt integer NOT NULL DEFAULT 1` and the partial unique index `semp_messages_reply_attempt_uq` on `(tenant_id, reply_to_message_id, attempt) WHERE role = 'assistant'`.
- The history response returns `attempt` on every assistant message.
