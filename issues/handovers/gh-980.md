I did not run the rest of `pnpm run verify` (unit and e2e tests, the migration-numbering and repo-script checks) or anything in `web/`; Relay's verify step will.

- **Tenant lookup:** `getUserTenantBinding` and `TenantStatus` are in `tenantsStore.ts`. They run the one query from the issue and check `status` and `role` against their unions. An unknown value throws a plain `Error` naming the column, so it surfaces as a 500, never a 401.
- **Identity:** `AuthenticatedIdentity` gains `tenantId` and `role`. `verifySessionToken` looks up the binding after the user and before `touchSessionLastSeen`. A missing binding or a non-`active` status throws the same `UnauthorizedError` as a bad token, and `last_seen_at` is not bumped.
- **`authenticateRequest`:** the transaction now runs inside `runAsSystem("authenticate")`.
- **Auth listener:** the whole request runs inside `runAsSystem("auth")`. I put the wrapper around the `handleRequest` call in `handleRequestSafely` rather than inside the function body. `GET /api/auth/session` now returns `user.role`.
- **Adapter:** after authentication, body parsing, parameter extraction and the handler call run inside `runInTenant(identity.tenantId, …)`. The error mapping is untouched and stays outside.

**Tests:** I added cases to `authActions.test.ts`, `authHandler.test.ts` and `adapterRoute.test.ts`, plus the new `adapterTenantScope.test.ts`. Together they cover:
- the bound, unbound and non-active tenant cases;
- 401 bodies byte-identical to the garbage-token response, with `last_seen_at` unchanged;
- `user.role` in the session response;
- the scope the adapter handler sees, and 401 without credentials;
- the 500 for an unexpected handler error;
- strict-versus-warn parity for the adapter-served `ROUTE_MATRIX` routes and the `/api/auth/*` routes;
- the `TenantScopeConflictError` when `authenticateRequest` is called inside a tenant.

The strict-versus-warn route tests treat a `ROUTE_MATRIX` entry as adapter-served if its path starts with `/api/databases`, `/api/properties`, `/api/views` or `/api/items`, or it matches a module custom route definition. Bespoke listeners are left out because #981 covers them.
