## What was delivered

A finished Semp turn stores the list of items it changed on the assistant message.

- Migration `0159_semp_messages_changes.sql` adds the nullable `semp_messages.changes jsonb`. The chain wrote it as `0158`; the chain's other migration and the tip's `0157_semp_messages_search_vector.sql` took the lower ordinals, so the queue runner renamed the chain's own file to `0159`. Nothing referenced the old name.
- `semp/sempReplyChanges.ts`: pure projector `projectSempReplyChanges` over the paired tool calls with a mapping table keyed by generic operation: `item.create` gives `created` (item id from the result, keys from the arguments, relation keys of `relations` included), `item.patch` gives `updated` (`changedKeys` and `before` from `details.changes`), `item.delete` gives `deleted`, `item.restore` gives `restored`, `relation.put` and `relation.delete` give `updated` on `callerItemId` with the relation property key.
- Failed, approval-pending and unfinished calls make no entry. Several changes of one item are merged: union of keys, `before` of the first change of each key, a created item stays `created` unless it is deleted later, otherwise the entry takes the kind of its last change.
- The database of an entry is the one the item is found in under the caller's tenant scope (`sempReplyTargets.ts`; relation properties resolve through the new `listPropertiesByIds` in `propertiesStore.ts`). `before` is dropped when the result is redacted, the database is sensitive or cannot be placed.
- `buildSempReplySummary` returns `changes` next to the steps and `finishSempMessageTurn` writes them in the same UPDATE as the status; a finished turn that changed nothing stores `[]`.
- Review fix: `item.create` returns `createdItemId` in `details` (tool, composition, shared parser); the redactor keeps it, so a create in a sensitive database makes an entry with `changedKeys: []` and no `before`. `piAgentSession.targetsOf` puts `callerItemId` into `targetItemId` of the events of a relation call, so a link written after a sensitive read is still recorded. ADR `docs/adr/2026-11-13-a-redacted-create-result-keeps-the-id-of-the-item-it-created.md` records this.

## Entry points and contracts dependents build on

- From `@semprec/data`: `projectSempReplyChanges` and the type `SempReplyChange` (frozen in `publicSurface.test.ts`); `listPropertiesByIds(client, ids)` in the choke-point `propertiesStore.ts`.
- Stored entry: `{ itemId, databaseId, change: "created" | "updated" | "deleted" | "restored" | "revised", changedKeys: string[], before?: Record, proposalId?: string }`, English camelCase. `changes` is NULL for a message without a finished turn summary and `[]` for a turn that changed nothing, so a consumer (issue #1930) can read a non-empty list as "this reply wrote something".
- `details.createdItemId` on a successful `item.create` tool result.
- Any new operation or module tool whose effect the list must record needs an entry in the mapping and, when its result is redacted, must keep the identity it needs in `details` or in the target ids of its events (ADR above).

## Deviations and spec seams

1. The mapping entry `inbox.proposal.revise` to `revised` with `proposalId` from its result is NOT implemented. The tool and its result shape belong to gh-1906 (open, absent from the tree; gh-1885 names only gh-1860 as blocker), and Out of scope says each module that adds such a tool adds its entry. The `revised` kind and the optional `proposalId` stay in the stored type, but no mapping produces them yet. The recheck accepted the deferral.
2. The database of an entry is the one the item is found in under the tenant scope, never the one the result text names; an item not found there (for example of another tenant) makes no entry.
3. Merge rule where the Task is silent: a created item stays `created` and has no `before` unless later deleted; otherwise the entry takes the kind of its last change.
4. `relation.put` and `relation.delete` are resolved through `callerItemId` and `relationPropertyId`; other write operations (`relation.set`, `link.relink`, `page.*`) are absent from the Task's mapping table and make no entry.
5. Events stored before the review fix have no `createdItemId`; a create in a sensitive database from such a run still makes no entry.
6. Reconciled at the merge: see the gh-1860 handover (same merge commit, same index.ts and sempMessagesStore.ts reconciliation).
