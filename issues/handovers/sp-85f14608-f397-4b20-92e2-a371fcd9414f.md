## What was delivered

- Generic operation `property.option.remove` (`PropertyOptionRemoveInputSchema`: `propertyId`, `key`), REST only
  (`REST_ONLY_OPERATION_NAMES`), metadata `destructive("core.schema.write", false)`, bound to
  `GenericApplicationPort.removePropertyOption`, which calls `chokePoint.removePropertyOption(propertyId, key,
  actingUserId)`.
- `DELETE /api/properties/:id/options/:key` answers 204 with no body; 404 for an unknown property (another tenant's
  included) or option key, 400 `validation_failed` for a non-choice property (`field: propertyId`), a system-owned
  property (`reason: system_owned`) and a malformed `:key` segment; 403 `property_locked` for a locked property.
  Route matrix entry "remove property option".
- In one transaction: the option and a `config.default` naming it are removed; every live and trashed item holding the
  key is cleared (select becomes `null`, multi_select loses the key). Live items go through `updateItemWithClient` as
  the system writer (hooks, item invalidation, search reindex); trashed items through
  `itemsStore.setTrashedItemProperty`. A database search backfill and the schema invalidation follow, as for the other
  option writes.

## Contracts dependents build on

- Lock order of the removal: property row `FOR UPDATE` -> items holding the key (`itemsStore.lockItemsHoldingOption`,
  `FOR NO KEY UPDATE`, id order) -> each live item's update path.
- User and agent `createItem`/`updateItem` lock the select/multi_select property rows their own keys name `FOR SHARE`
  (`propertiesStore.lockChoicePropertiesForShare`) before the option check and the item row. System writers do not.
  Documented in docs/architecture/transactions-and-side-effects.md (Item update) and data-model-and-writes.md
  (Properties).
- View filters or sorts naming the removed key are not touched.
