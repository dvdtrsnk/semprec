## Summary

This adds steps 4–6 of the `semprec-transcribe` pipeline for #183: merge the segments, summarize the transcript and finalize it as `done`. The worktree was behind `develop` and had none of the #182 transcription code, so I fast-forwarded it to `origin/develop` (62c4b3f) first. `pnpm run verify` passes in `backend/` and in `web/`.

### Step 4 — merge (`segmentMerge.ts`, pure, no I/O)
- **Overlap dedup:** two neighbouring ASR chunks share an overlap band, and the cut is at the band's midpoint. The earlier chunk keeps segments whose midpoint falls before the cut; the later chunk keeps those at or after it. Every instant has exactly one owner, so no text is duplicated or lost.
- **Speaker assignment:** the ASR endpoint only returns segment-level times, so the spec's segment-level fallback applies. A segment gets the diarization turn it overlaps most. If no turn overlaps it, it gets the nearest turn in time; ties go to the earliest turn. If diarization returned no turns at all, every segment gets `SPEAKER_00`.
- **Grouping:** consecutive segments from the same speaker are joined unless a pause longer than 1.5 s separates them.
- **Times:** they are rounded to milliseconds and kept monotonic, so each segment starts no earlier than the previous one ended.
- **Output:** `computed.segments` (`{ speaker, text, startsAt, endsAt }`) and `computed.language` are written onto the Transcripts row in one transaction, with the row locked. They are written once: if `segments` already exists, a replay leaves it alone, so speaker keys are never rewritten.

### Step 5 — summarize (`transcriptSummary.ts`)
- The summary is requested through the gateway's `/internal/complete` route via `@semprec/ai-gateway-client`, for the selected instruction (default `meetingSummary`, selectable through `createTranscriptionTask`).
- The result is cached under the instruction's key in `computed.summaryByInstruction`, next to any other instruction's summary. An instruction that already has a summary is never sent to the gateway again.
- No transaction is held open during the gateway call. The write transaction re-checks the cache under a row lock, and the gateway's response is validated with zod before it is used.
- A transcript with no speech gets an empty summary and no paid call.

### Step 6 — finalize
- `status = done` (written as the owning `transcribe` process) and `item_automation` → `done` are set in one transaction.
- That transaction first requires the committed `segments` and this instruction's summary to exist. If an earlier step failed, the exception goes to the job's normal failure path and the row stays `processing` / `pending`.

### Gateway and realtime changes
- **Gateway:** `/internal/complete` now accepts `operation: "transcript_summary"` with `projectItemId: null`. The summary has no project, so its `ai_gateway_calls` row has no project item. `agent_guidance_drift` still requires a UUID. The `AiGatewayCompletionInput.projectItemId` type is widened to `string | null`.
- **Realtime:** `semprec-transcribe` never wired `wireRealtimeHooks`, so its choke-point writes (including the existing step 1 `date` patch) reached no client. `serve.ts` now wires it. Steps 4 and 5 also send an item-update invalidation after commit, because `writeComputed` doesn't send one itself.
- **Data layer:** `language` is registered as a declared computed key, and `runAfterCommit` and `markItemAutomationDone` are now exported.

### Decisions for review
- **Error path:** I read "use shared error path otherwise" as "don't finalize, let the job's failure path handle it". Retry policy, `status = error` and the `automation_error` notification belong to #248, so none of that is built here.
- **`item_automation` in step 6:** setting it to `done` overlaps a little with #248. I included it so a `done` row never has its automation left `pending`; #248 can build on it.
- **`language` is reserved in every database:** like the existing transcription keys, it now blocks any new property named `language`, in any database.
- **No ADR added:** wiring realtime in this process is what `wireRealtimeHooks`' own docstring already describes (call it in whichever process owns the write path), and the gateway change only extends the existing operation list.
