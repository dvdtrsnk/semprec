## What was delivered

- An optional text `q` (1 to 200 characters) on `database.query`, `view.query` and, per entry of `items`, `item.count`. The query routes are POST with a JSON body, so `q` is a body field of `POST /api/databases/:id/query` and `POST /api/views/:id/query`.
- The match predicate of global search is extracted into `search/itemSearchMatch.ts` (`ITEM_SEARCH_MATCH_FROM`, `itemSearchMatchWhere`, `andItemSearchMatch`); `searchItemsQuery.ts` builds its count and page SQL from it. `q` uses the same tsquery builder as global search, so diacritic-free, partial and multi-word text behave as in global search.
- `q` is validated in `views/viewQuery.ts` (field `q`, the message never repeats the text), ANDed with the filter inside `listItems` and `countItemsGrouped` as an `items.id IN` subquery on `item_search_index` restricted to the queried database; text without a searchable word matches nothing. `totalCount` is built from the filter alone, so it stays the filter-only count. On `item.count`, `q` applies to the total and the groups of an entry. A request without `q` produces the same statements as before.
- A curated view (no single database) refuses `q` with a 400 on field `q`.

## Deviations from the specification and spec seams

1. The query routes are POST with a JSON body, not query strings.
2. On `item.count`, `q` sits on each entry of `items` (each entry has its own database, filter and groupBy), not at the top level.
3. A curated view refuses `q` with a 400, like `filter` and `sort`, since the match is restricted to one database; the Task does not say. The requirements reviewer rated this an acceptable addition.
4. Text with no searchable word matches nothing (condition `FALSE`), as in global search.
5. `SEARCH_MAX_QUERY_LENGTH` moved above `queryFields` and is exported from the shared `schemas.ts`.
6. The global search SQL is now built from the shared predicate; its conditions are in a different order (`deleted_at` after the match), with no change of behaviour.
7. The first requirements review found that the inflected form was only asserted as a non-match, which held only because the shared test database has no Czech dictionary. The fix `634577edc` removed that assertion and added a hunspell-activated test in `czechHunspellSearch.test.ts`, so the inflected-word criterion is now proven. The chain then needed a second fix round (`0e41e17df`): `viewsHandler.test.ts` read `totalCount`, which its local `ItemQueryBody` interface did not declare, so `semprec-api` did not build; the interface now declares `totalCount?: number` (test-only change). This round followed an earlier landing attempt of this chain alone that stopped at the build; the controller note reads "controller decision 2026-11-13". The focused recheck of the second fix passed.
