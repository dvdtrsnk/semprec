## What was delivered

An Inbox proposal for a database record may now name a new select or multi_select option, and confirming the card creates the option and the record in one transaction.

- Envelope: a single-step database envelope may carry `newOptions: [{ propertyKey, label, color? }]` (schema in `proposalEnvelope.ts`). A `select` or `multi_select` value in `properties` may name a new option as `{ newOption: label }`.
- Validation: `assertValidProposalEnvelope` (through the new `proposalNewOptions.ts`, so it runs on tick, revise, values edit and confirm) checks that `newOptions` appears only on a single-step database envelope, has at most 3 entries (`MAX_PROPOSAL_NEW_OPTIONS`), names an existing select or multi_select property of the target, has a label of 1-60 characters and an optional `#RRGGBB` color (the `property.option.add` input schema), no duplicate label per property, and that every `{ newOption }` value names a listed option. A label that an option of the property already has (stored label, or the Czech or English catalog label, folded) and that a value names is `OptionLabelExistsError` (409 `option_label_exists`, `details.key` the existing key). A listed option that no value names is not label-checked and is not created.
- Confirm: `confirmProposalWithClient` calls `createEnvelopeNewOptions` before `createItemWithClient`. Each named option is added on the confirm's client through `propertiesStore.addPropertyOption` (row lock, label and limit rules, generated key) and its key replaces the label in the values. The schema invalidation is sent after commit; the option rolls back with the confirm. An option no value names is not created. Confirming a confirmed card again creates nothing; two concurrent confirms serialise on the card lock.
- Tick: `OptionLabelExistsError` is an envelope refusal in the tick (`needsClarification` card) and in `storedEnvelopeStillValid`.
- Computation: `ProposalComputationResult.newOptions` flows to the envelope (`buildProposalEnvelope` in `inboxTickSnapshot.ts`); `proposalComputation.ts` adds `newOptions` to the answer schema, to `PROPOSAL_RESPONSE_SCHEMA` and a prompt note next to the gh-1990 catalog note, and says a new tag may be proposed only when the target database has a select.
- Review fixes (commit `b5b2b7881`): reopening a confirmed card rewrites `proposal`, `aiProposal` and `userOverrides` so each `{ newOption }` value whose option now exists becomes its key and the option leaves `newOptions` (`adoptCreatedNewOptions`, called by `proposalReopen.ts`), so the card can be confirmed again with one option and one item; both revise paths (`reviseProposalWithClient`, `reviseProposalFromThreadWithClient`) carry `newOptions` over like `pageSections` with `carryNewOptions` (only options a value still names); the label-free rule applies only to options a value names, so a values edit to the existing key makes the card confirmable.
- ADR `docs/adr/2026-11-15-a-database-proposal-may-create-select-options-when-it-is-confirmed.md` records the pattern, the import-cycle reason for the store function, the unqueued search reindex, and the reopen, revise and values-edit behaviour.

## Deviations from the specification and spec seams

1. The Task names `proposalTargetCatalog.ts` for the prompt note; the prompt lives in `services/semprec-api/src/proposalComputation.ts` and the note is there.
2. To make the note true, the answer schema, `PROPOSAL_RESPONSE_SCHEMA`, `ProposalComputationResult.newOptions` and `buildProposalEnvelope` were extended, which the Task does not list.
3. The gh-1699 handover says no transaction-scoped option add exists. `chokePoint/propertyOps.ts` cannot be imported from `inbox/` (cycle through `search/itemSearchBackfill` and `tenancy/provisionTenant` back to `inbox`, forbidden by `no-choke-point-rollup-cycle`), so the confirm calls `propertiesStore.addPropertyOption`, the store function behind `property.option.add`. It queues no search reindex (no item holds a new option and the confirm writes the item after it); recorded in the ADR.
4. `OptionLabelExistsError` is not a `ValidationError`, so `inboxTickAction.ts` treats it as an envelope refusal through a local `refusesEnvelope`.
5. Rules beyond the listed ones, for coherence: `newOptions` valid only on a single-step database envelope; duplicate labels per property refused; every `{ newOption }` value must name a listed option; a listed option no value names is accepted and not created.
6. The Task example of a missing title is refused by the required-field check before any write; the rollback is proved by an injected item-create failure and an explicit rolled-back transaction test.
7. The chain commit trailers name Claude Fable 5.2, as the task prompt prescribes.
