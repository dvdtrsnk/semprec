# gh-1471 — [inbox-editing 04/23] Maintain aiProposal for every proposal writer

## Delivered behavior

- **Helpers** (`backend/packages/data/src/inbox/inboxTickAction.ts`):
  - `aiProposalPatch(existingProperties, envelope | null)` returns `{ aiProposal: envelope, aiVersion: previous + 1 }`. A row without an `aiVersion` counts as 0, so a legacy card gets 1 on its next automated write. The caller passes the row as read under its row lock; a row being created passes `{}`.
  - `readAiProposal(properties, proposalId)` returns the parsed `aiProposal` when it is set, else the parsed stored `proposal`, else `null`. The Task named the signature `readAiProposal(properties)`; the proposal id is the second argument so that a malformed envelope names its row, as `parseStoredProposalEnvelope` does.
- **Writers.** Each spreads `aiProposalPatch` next to `proposal` in its `propertiesPatch` or create properties, and adds `aiProposal` and `aiVersion` to its `allowedSystemKeys`:
  - `writeNeedsClarification` in `inboxTickAction.ts`, both branches (revise and create), with envelope `null`;
  - `reviseProposal` in `inboxTickAction.ts` (tick recompute of an unlocked card);
  - the create branch of `writeTickResult` in `inboxTickAction.ts`;
  - `reviseProposalWithClient` in `proposalActions.ts`;
  - the create of the transcript Event card in `transcriptEventMatch.ts`;
  - the create of the transcript speaker card in `transcriptSpeakerSuggestion.ts`.
- **Writers that touch only `status` or `history`** (confirm, reject, invalidation on source deletion) are unchanged, so `aiProposal` and `aiVersion` keep their values.
- **No migration and no backfill.** A legacy row with no `aiProposal` is read through the `proposal` fallback, and its first automated write sets `aiProposal` at `aiVersion` 1. The cutover from gh-1451 still copies `proposal` into `aiProposal` for those rows.
- **Repo-wide test:** `backend/packages/data/src/__tests__/publicSurface.test.ts` gained `aiProposalPatch` and `readAiProposal` in its frozen runtime export list, because `index.ts` re-exports `inboxTickAction.ts` wholesale.

## Notes for dependants

- **Write `aiProposal` in the same statement as `proposal`.** The gh-1451 cutover copies `proposal` into `aiProposal` on every run for any card whose `aiProposal` is absent or JSON null. A producer that writes `proposal` without `aiProposal` therefore has its envelope mirrored at the next cutover run as if the assistant had written it. Later producers (#1495, #1500, #1648, #1482, #1848, #1978, #1640, #1975, #1485, #1850, #1870) must spread `aiProposalPatch` as the writers above do.
- **`reviseProposalWithClient` mirrors into `aiProposal`.** The Task requires it, so a revision through this route becomes the card's assistant output. The Context describes `aiProposal` as the assistant's latest output, so the route must stay the assistant's path. A manual user edit (#1892) must not go through `reviseProposalWithClient` if it should stay out of `aiProposal`.
- **Legacy rows** have `aiProposal` only after the gh-1451 cutover, and never an `aiVersion` until their first automated write. `aiProposalPatch` treats a missing `aiVersion` as 0; `readAiProposal` treats a missing or JSON null `aiProposal` as "use `proposal`".
- `aiProposalPatch` takes its counter from the row it is given, so that row must be read under the write's own lock. Every current caller does this: `lockUnlockedProposal` for the tick and `needsClarification` revisions, `lockLiveProposal` for `reviseProposalWithClient`, and a fresh row for the creates.
