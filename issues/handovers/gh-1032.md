`getDecryptedCredential` now reads credentials sealed under either the master key or the tenant key. Every write still uses the master key, so no stored secret changes. I did not run the full `pnpm run verify` or the `web/` checks. The Relay steps do that after this turn.

The change is committed on this branch. Lint, format and the migration-numbering check pass. The new suite (8 tests) and the existing mail sync, mail send, MCP connection and tenant-key suites pass (158 tests in total).

- **Migration:** `0063_external_credentials_scheme.sql` adds `scheme text NOT NULL DEFAULT 'master'` with a check that it is `master` or `tenant`. The constant default means no table rewrite. The previous release's inserts omit the column and get `master`, which is what they write.
- **`externalCredentialsStore.ts`:**
  - `storeCredential` is otherwise unchanged. Both the insert and the `ON CONFLICT` update set `scheme = 'master'`, so re-storing over a `tenant` row turns it back into a `master` row.
  - `getDecryptedCredential` also selects `tenant_id` and `scheme` and validates the scheme with `assertKnownValue`. The access-log insert still runs before any decrypt attempt, and `master` rows go through today's path.
  - A `tenant` row needs the tenant's data key. If the key is missing, or belongs to a different tenant than the row, it throws a plain `Error("No data key for this credential's tenant")` with no `code`, so `connectMcpServer` still maps it to `credential_decryption_failed`. Otherwise it opens the row with the new module-private `credentialAssociatedData(tenantId, itemId)`.
  - The header and function comments now say the file reads both schemes.

**Note for reviewers:** the `tenant` branch reads rows that nothing writes yet. It ships first so that a rollback from the release that starts writing `tenant` rows (#1060) can still open them. The doc comment says so too. It is not dead code.

**Tests:** `externalCredentialsStore.test.ts` covers every acceptance case from the issue:
- master rows, including a row inserted without `scheme` and one log row per attempt;
- a fabricated `tenant` row decrypting and being logged;
- re-storing over a `tenant` row;
- ciphertext copied across items and across tenants being refused;
