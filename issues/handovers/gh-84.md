## Summary

Implements #84: reactivating heartbeat occurrences under a generation protocol, closing the race where a rule edit/re-enable that recomputes an occurrence back onto an existing `cancelled` or stale-`queued` row would leave it stuck instead of firing.

- Added an additive `generation integer not null default 1` column on `heartbeat_occurrences` (migration `0024_heartbeat_occurrence_generation.sql`).
- `insertHeartbeatOccurrence` in `schedulerStore.ts` now reactivates a `cancelled` occurrence (fresh snapshot, `status='queued'`, cleared `first_started_at`/`last_error`, generation bumped, enqueued with `jobKeyMode: 'replace'`) or replaces a `queued` occurrence whose `rule_snapshot` no longer matches (in place, same id/status, generation bumped, enqueued with `jobKeyMode: 'preserve_run_at'`), while `queued`(matching)/`running`/`succeeded`/`failed` stay untouched no-ops.
- Job payload/key now carry `generation` (`{heartbeatId, occurrenceId, generation}`, `heartbeat-fire:${heartbeatId}:${occurrenceId}:${generation}`), superseding #213's plain shape.
- `prepareHeartbeatOccurrenceFire` checks the caller's `generation` against the row's current generation before touching any state, so a handler running against a superseded generation becomes a safe no-op rather than racing the reactivated occurrence.
- Added integration tests covering both reactivation paths end-to-end (cancelled→reactivated, queued-stale→replaced), including an explicit assertion that a stale-generation call is a no-op while the new generation still fires exactly once. Updated existing tests for the new signature/job-key format.
