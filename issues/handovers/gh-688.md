## Summary

Implemented issue #688: chunked the heartbeat sweep and moved its next-fire computation to the database clock.

**`schedulerStore.ts`** — `sweepDueHeartbeats` now takes an `afterId` cursor, selects at most `SWEEP_CHUNK_SIZE` (100) due rows keyset-paginated by `id` (`ORDER BY id`, not `next_fire_at`, so a row the sweep deliberately leaves due is visited at most once per sweep instead of resurfacing at the head of every later page), and returns `SweepChunkResult { fired, lastId, exhausted }`. Each row's `now()` is read alongside it as `db_now` and used as `computeNextFireAt`'s `after` argument instead of the JS `new Date()` — the fix for the clock-skew stall described in the issue.

**`sweep.ts`** — `handleHeartbeatSweepTask` now runs a `for` loop of at most `MAX_SWEEP_CHUNKS` (50) iterations, each `sweepDueHeartbeats` chunk in its own `withTransaction`, stopping when a chunk reports `exhausted`. A chunk that throws propagates as before, but earlier committed chunks stay committed.

**`scheduler.test.ts`** — adapted every existing `sweepDueHeartbeats` caller to the new `{ fired, ... }` shape, and added a `describe("chunked sweep (issue #688)")` block with the three required integration tests: 250 due heartbeats fire in exactly 3 chunk transactions (100+100+50), a failing second `connect()` leaves the first 100 committed and the remaining 50 pickable by a follow-up sweep, and a two-hour-lagging application clock (`vi.useFakeTimers`) still produces a `next_fire_at` in the future because the database clock is used instead.

Loaded `state-writes` per the implement-issue skill contract — the sweep's writes already went through the existing choke-point-adjacent pattern this file used before (system-owned scheduler state, not item state), so no changes were needed there.

`pnpm run verify` passed backend lint/build/unit/write-safety/boundaries; `test:integration` had 2 unrelated failures (`packages/realtime/src/__tests__/syncServer.test.ts` and `services/semprec-ai-gateway/src/__tests__/piMessagesHandler.test.ts`, neither touching the scheduler) that I confirmed pass in isolation — pre-existing flakiness under full-suite contention, not caused by this change. The scheduler test file itself (48 tests, including the 3 new ones) passed cleanly in isolation. `web/` is untouched by this issue.
