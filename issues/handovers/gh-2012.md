## What was delivered

- `PUT /api/tasks/:id/host-events/:eventId` (`createTaskHostEventPutRouteHandler` in `backend/packages/data/src/tasks/taskHostEventRouteHandlers.ts`) puts an item of a recurring series into an event like any other task. This holds for the series' current instance and for another stored occurrence. The read of the task's `task_recurrence` row (`getTaskRecurrence(client, taskId, true)`, `FOR UPDATE`), the 400 it fed and the import of `getTaskRecurrence` are removed. Nothing was added to the handler.
- The handler writes the `Tasks.hostEvents` edge of that item only, through `createRelationWithClient` as the Tasks process with the user writer, as before. It neither reads nor writes `task_recurrence` or another occurrence of the series: the series row (`item_id`, rule, anchor date, template, `active`) and the other stored occurrences stay as they are.
- The handler's docstring was rewritten to state this.
- No route, manifest entry, route matrix entry, migration, table, column, write hook, tenant cutover entry, generic operation, job name, export from the data barrel, stored key, i18n key or ADR was added or changed.

## Contracts dependents build on

- Route, handler name, manifest route (`putTaskIntoEvent`), request and response are those of gh-1764. The answer is 200 with `{ taskId, hostEvents: [{ eventId, addedAt }] }`, `addedAt` ascending.
- Refusals of the PUT after this source:
  - 404 `not_found` for a task or an event that is missing, in the trash or another tenant's, alike. Unchanged, and now tested for both kinds of occurrence.
  - 400 `validation_failed` on `id` or `eventId` for a path parameter that is not a UUID. Unchanged.
  - The 400 on `taskId` for an active recurrence is gone. No request is refused because of a recurrence.
- Placing an occurrence changes nothing of its series. Placing the current instance does not advance or deactivate the series.
- Completing the placed current instance advances the series as before (gh-1670): one new instance for the next date. The advance carries only the `project`, `people` and `files` relations, so **the next instance sits in no event**. The placed item keeps its edge when it is done.
- Completing a placed occurrence that is not the series' current instance advances nothing: `advanceTaskRecurrenceWithClient` returns early unless the series row names the completed item (gh-1670; by reading, not tested here).
- Locks: the handler locks only the task's item row (`lockItemById`, `FOR UPDATE`). It takes no `task_recurrence` lock, so the order of `docs/adr/2026-10-25-task-and-event-recurrence-model.md` (items, then `task_recurrence`) holds trivially. A PUT and a completion of the same occurrence serialize on the item row.
- A future occurrence without an item is placed by the caller in two requests: `POST /api/tasks/series/:seriesId/occurrences/:date` (gh-1720), then this PUT with the returned item id. No route does both.
- **Nothing hides a hosted task yet.** No code derives visibility or the effective day from `hostEvents`; that is gh-1780 (open). The projection of gh-1672 still returns a placed occurrence as a stored occurrence. gh-1780 reads the edge this route writes; its record names no occurrence case.
- No record declares gh-2012 as a blocker.
- For tests of later sources: since gh-1761 an Event created through the choke point with the domain hooks registered has a calendar edge. The occurrence tests therefore compare an Event's edges before and after a refused PUT instead of expecting none. A test that reads all edges of an Event should do the same.

## Deviations from the specification and spec seams

1. The handler no longer reads `task_recurrence` at all. The Task allows it ("Keep the lock order items, then `task_recurrence`, if the row is read"). Consequence without a test: a task whose `task_recurrence` row is active while the item has no `seriesId` is now placed as a plain task instead of being refused. Production writes cannot create such a row; the series cutover of gh-1605 can leave one (`docs/adr/2026-11-07-task-series-cutover-uses-bounded-owner-backfill.md`: a legacy instance that was done at cutover, or rows of an interrupted run). Such an item never advances, so there is no series to hide.
2. Two tests of gh-1764 were removed from `taskHostEventRoutes.test.ts`: "refuses a task with an active recurrence with 400 on taskId and writes nothing" and "waits for a transaction that holds the task's recurrence row and refuses the task it made recurring". Both assert the rule this source replaces.
3. The occurrence tests are in a new file next to the route tests of gh-1764, with their own fixtures.
4. "Hidden until the event ends" of the second acceptance criterion cannot be observed: nothing in the tree derives visibility from `hostEvents` (gh-1780, open, Out of scope of this record). The test asserts the edge on that occurrence alone and the projection of the following date.
5. The completion test uses the series' current instance, the case Task step 2 names. The follow-up recorded in the handover of gh-1720 (the next date already stored, so the series pointer stays on the done item) is untouched.
6. The tests call the handler factory in a tenant scope on the runtime-role pool. The HTTP mount of the route is exercised only by the unchanged isolation case "task host event put" of `tenantIsolationRoutes.test.ts`, which has no occurrence case.
7. No ADR: the change removes a validation rule by the product owner's decision recorded in the record, and the lock order of the recurrence ADR is kept.
8. Since the second round the two isolation cases compare the Event's edges before and after the refused PUT instead of expecting none. The record does not name the calendar edge of gh-1761.
