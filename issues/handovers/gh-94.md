## Summary

- Background/AI IMAP body fetches (`ImapFlowMailClient.fetchMessagesSince`/`downloadText`/attachment streaming) already ride `imapflow`'s internally-forced `BODY.PEEK[...]`, which has no non-peek option — confirmed by a regression test that a real fetched message never triggers `messageFlagsAdd`. Added `ImapMailClient.markSeen(path, uid)` as the one explicit mark-read path, backed by `STORE ... +FLAGS (\Seen)`.
- Added a per-account, in-process IMAP connection limiter (`mail/imapConnectionLimiter.ts`) with provider-aware default caps (Gmail/iCloud/Outlook/generic), overridable via a new `Mailboxes.connectionLimit` property; wired around the IMAP branch of `handleSyncMailAccountTask`.
- Added `MailConnectionLimitError` + `isImapConnectionLimitError` (detects a provider's simultaneous-connection `BYE`, e.g. Gmail's "Too many simultaneous connections") and a `recordConnectionLimitBackoff` sync-state write with a provider-aware delay. `handleSyncMailAccountTask` now catches this error, persists the backoff (and still surfaces `syncStatus: 'error'`, since mail genuinely isn't syncing), and **returns instead of rethrowing** — so the next attempt comes only from the existing `next_expected_activity_at` sweep, not also from graphile-worker's own immediate job retry stacked on top of it.
