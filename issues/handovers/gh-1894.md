## What was delivered

- Migration `0165_idempotent_responses.sql`: tenant table `idempotent_responses` (`tenant_id` default `app_tenant_default()` with FK, `user_id` without FK, `key`, `route`, `request_hash`, `status`, `body` jsonb, `created_at`, `expires_at`), primary key `(tenant_id, user_id, key, route)`, `COMMENT ... 'semprec:tenancy=tenant'`, RLS with the RESTRICTIVE `tenant_isolation` and PERMISSIVE `tenant_rows` policies, grants like `tenant_exports` (`semprec_side`), index `idempotent_responses_expires_at_idx` on `expires_at`.
- Store `packages/data/src/inbox/idempotentResponsesStore.ts`: `runIdempotent(client, { tenantScope, userId, key, route, requestHash }, action)` runs in the caller's managed transaction, takes a per-tuple `pg_advisory_xact_lock`, answers a live row of the same hash as stored without running the action, throws `ValidationError` (`validation_failed`, field `Idempotency-Key`) for a live row of another hash, otherwise runs the action and stores a response with status below 400 (a 4xx/5xx response is returned and not stored; a thrown error rolls the transaction back and leaves the key free). An expired row is replaced; each stored response also deletes one bounded batch (100) of the tenant's expired rows. Also exported: `hashIdempotentRequest`, `readIdempotencyKeyHeader` (empty header is absent; a multi-value header or one over 255 characters is a `ValidationError`), `deleteExpiredIdempotentResponses`, `IDEMPOTENT_RESPONSE_TTL_HOURS` (24), `MAX_IDEMPOTENCY_KEY_LENGTH`.
- `createUpdateProposalValuesRouteHandler` in `inbox/inboxRouteHandlers.ts` (the handler of `PATCH /api/proposals/:id/values`) uses `runIdempotent` when an `Idempotency-Key` header is present; without the header it is unchanged. The request hash covers the resolved card id and the body.
- Purge hook `idempotentResponsesPurgeHook` (`inbox/idempotentResponsesPurgeHook.ts`), registered in `domainWriteHooks.ts` with `registerItemPurgeHook`: the permanent deletion of a Processing proposals card sweeps one batch of the tenant's expired rows.
- `idempotent_responses` is in `EXPORT_EXCLUDED_TABLES` (`tenancy/tenantExportJob.ts`); the tenant purge set is catalog-derived, so tenant erase covers it.
- ADR `docs/adr/2026-11-13-card-actions-replay-the-stored-response-of-an-idempotency-key.md` records the lock, replay and sweep contract.

## Entry points and contracts dependents build on

- The other card routes (reset-overrides, reopen and the like, issues that mount them) apply the same helper: build the request hash with `hashIdempotentRequest` over everything that changes what the request does (path parameters included), read the header with `readIdempotencyKeyHeader`, pass the route template (never the resolved path), and run the whole action inside `runIdempotent` in the route's one transaction. `action` must return `{ status, body }` with a JSON object body.
- `runIdempotent` requires a managed transaction and a `tenant`-kind `TenantScope` (`currentTenantScope()`); a missing or system scope throws.
- Table: `idempotent_responses` (tenant table). No route, job name or generic operation was added. `idempotency_keys` (item creation) is untouched.
- Not exported from `packages/data/src/index.ts` (`publicSurface` unchanged).

2. `tenantScope` is the `TenantScope` of `@semprec/shared` as `currentTenantScope()` returns it (the Task names the field, not its type).
3. The replay body is stored as the item row (ItemRow JSON) and parsed back through a zod schema in the handler; the adapter still builds the item envelope, so first call and replay answer from the same stored row.
4. The Task's "permanent-delete path of the card item" is an item purge hook (docs/adr/2026-11-10-item-purge-domain-hooks.md) that sweeps one batch of the tenant's expired rows, because rows do not name the card.

6. An ADR was added (new lock, replay and sweep contract). `rowLevelSecurity.test.ts` and `tenantExport.test.ts` were changed besides the Touches list because they enumerate tenant tables.
7. The different-user criterion is proven at handler and store level, not over HTTP: `users_tenant_id_key` allows one user per tenant, so the HTTP harness cannot create a second user.
