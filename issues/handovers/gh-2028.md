## What was delivered

`GET /api/inbox/cards` now says what the update steps of a proposal change. Every card whose active steps contain an `update` step carries a `changes` array with one entry per changed key.

- `inbox/proposalChanges.ts` (new): `describeUpdateSteps(client, activeSteps, locale)` returns `Map<cardId, ProposalChange[]>`. One `ProposalChange` per changed key of an active update step: `ref`, `itemId`, `itemLabel`, `field` (canonical property key), `fieldLabel`, and `from` / `to` as `{ value, labels }`. Property keys come before relation keys.
- Labels are resolved on read and never stored. A field and a select or multi-select option are labelled through `resolveProperty` / `resolveCatalogLabel` and the catalog of the module that owns the item's database; relation ids are labelled by the current title of the target item (trashed items included); a `{ ref }` target is labelled by the title the referenced create step would create (an update or link step by the name of its item, a `fileFromAttachment` step like a create into Files).
- The whole page is read once: one items lookup, `listAllDatabases`, one properties lookup, so the number of queries does not grow with the number of cards.
- `inboxCardsStore.ts` passes the active steps of every envelope of the page to `describeUpdateSteps` and adds the optional `changes?: ProposalChange[]` to `InboxCard`. The key is absent when the card has no active update step (an approval, a card without envelope, a card whose update steps are disabled or skipped).
- Review fix: only UUID-shaped ids (the item id, before and after relation targets) are passed to the items lookup, which casts with `::uuid[]`; any other stored id falls back to being its own label instead of failing the whole card list.

## Entry points and contracts dependents build on

- `describeUpdateSteps`, `ProposalChange` and `ProposalChangeSide` from `inbox/proposalChanges.ts` (not exported from the `@semprec/data` barrel).
- The `changes` key of `InboxCard`, present in the body of `GET /api/inbox/cards`. `field` is the canonical key, `from.value` / `to.value` are stored values (item ids and `{ ref }` objects for a relation, canonical option keys for a select), `labels` are the display strings in the caller's locale, one per entry of `value` for relations and selects.

## Deviations and spec seams

1. The Task names `describeUpdateSteps(client, envelope, locale)`; one items lookup for a page needs the whole page, so it takes `activeSteps: ReadonlyMap<cardId, ProposalStep[]>` (the active steps `inboxCardsStore` already computes) and returns a map by card.
2. A card whose update steps yield no entry (no changed key) is absent from the result and carries no `changes`, not `changes: []`.
3. Spec seam: field and option labels come from the catalog of the module that owns the item's database, not from the Inbox catalogs; `proposalChanges.ts` builds a process-cached `CatalogResolver` from `loadFullModuleRegistry`, the pattern of `chokePoint/propertyOps.ts`.
4. Fallbacks the Task does not state: an unreadable item or relation target is labelled with its id; a `{ ref }` naming no active step, or a create step without title, with the ref; a select value that is not an option of the property, and a property the database does not have, with their key.
5. At the merge with gh-1823 (same train) the import block of `inboxCardsStore.test.ts` was reconciled; no production code was affected.
