## Prepare the triage input from a harvest issue

Closes #577.

This adds `.github/scripts/review-followups/prepare.mjs`, the triage workflow's `prepare` step. It turns a harvest issue into `<dir>/input.json`, so the triage agent never has to touch GitHub. The script only reads from GitHub and never writes to it. `node --test .github/scripts/review-followups/prepare.test.mjs` passes 16/16 with no network access, and the whole `review-followups` suite passes 343/343. I did not run `pnpm run verify` in `backend/` and `web/` myself; this change touches neither, and Relay runs it after this step.

### `prepareInput(api, harvestIssue)`
- **Harvest issue check:** it throws unless the issue is open and labelled `followups:harvest`. It parses the data block with `parseHarvestBlock`.
- **Already published findings:** it builds the terminal ledger with `computeLedger` from every `followups:issue` issue (open or closed, no comments) plus the harvest issue and its comments. Findings in that ledger are dropped, so a re-run never proposes a finding twice.
- **Full text:** for each finding with a `discussionId`, it looks for the thread whose root comment's `databaseId` matches. Each pull request's threads are fetched at most once.
  - If the root was written by a trusted bot and starts with the `**… | …**` header, `fullText` is the description and `suggestedFix` is the fenced fix after `**Suggested fix:**` (or `null` when there is none). This matches the format `code-review-bot`'s `publish.py` writes.
  - Any other root becomes `fullText` as a whole.
  - Later comments become `threadReplies`, in order.
  - A finding with no thread gets `null` / `null` / `[]`.
- **`prSummaries`:** one entry per pull request that has one — its newest `## AI Code Review Summary` comment by a trusted bot, judged by `createdAt`.
- **`openIssues`:** open issues labelled `agent:ready`, `spec:approved` or `spec:proposed`, listed once each and sorted by number, with their `## Touches` section (`""` when missing).

### `main(argv, api)` / CLI
- Usage: `node prepare.mjs --harvest-issue <n> --out <dir>`. Without an `api`, it builds one from `clientFromEnv`.
- It checks the input with `renderInputFile` before creating `<dir>` and writing `input.json`. It then prints how many findings are pending and how many were already published.
- It exits 0 even when nothing is pending.
- Arguments are checked before any GitHub call. A missing, unknown, repeated or non-positive-integer argument, or any error, rejects `main` and exits non-zero without writing a file.

### Tests (`prepare.test.mjs`)
Written against a fake `api`, one or more tests per acceptance criterion (1–9):
- harvest checks
- the ledger: open and closed follow-up issues, and a result comment from the trusted author versus another author
- the bot format with and without a fix, a human root, a root without the header, and reply order
- a missing or deleted thread, and one thread fetch per pull request
- summary selection
- `openIssues` deduplication and `## Touches` parsing
- a round trip through `parseInputFile(renderInputFile(...))`
- `main` writing the file, including with zero pending findings
- `main` rejecting bad arguments or a throwing `api` without writing anything
- the CLI exiting non-zero when an argument is missing or `GITHUB_TOKEN` is not set
