## What was delivered

After a successful MCP tool sync the model proposes a Czech and an English label for each active tool that has none, through the AI gateway.

- Gateway: `mcp_tool_label` is a new operation in `OPERATION_REQUIRES_PROJECT_ITEM` of `services/semprec-ai-gateway/src/completeHandler.ts` with `false`. It is called with `projectItemId: null`; a non-null id or a missing requirement mismatch is rejected with 400 `validation_failed` like `transcript_summary`. The call is recorded in `ai_gateway_calls` with operation `mcp_tool_label` and no project item.
- `suggestMcpToolLabels(pool, gateway, mcpServerItemId)` in `packages/data/src/mcp/mcpToolLabelSuggestion.ts`, exported from `@semprec/data`. It pages through the active registrations of the server with `display_label IS NULL` by `tool_name` (keyset, 50 per page, description cut to 500 characters) and makes one gateway call per page, with the tool data as JSON in the user message and a system prompt that states the text is data. Each answer entry is validated on its own: the name must be one that was asked, `cs` and `en` both 1-120 characters with no control or line-separator characters and no angle brackets, the first entry of a name decides. Each valid label is stored with `UPDATE ... WHERE id = $1 AND display_label IS NULL`, in one transaction per page; no transaction is open during the model call. It returns the number of labels stored. A gateway failure (`AiGatewayFailedError`, logged by reason) or any other error (logged by name) never throws; a failed page leaves only its tools empty, `budget_exceeded` ends the loop.
- Two entry points: `POST /api/mcp-servers/:id/sync` (`createMcpAgentPageRequestListener(pool, gateway?)`, the gateway is `routeDependencies.aiGateway` in `app.ts`, called after the sync and before the 200 answer) and the queued `mcpServerSync` task (`handleMcpServerSyncTask(pool, payload, gateway?)`). A failed sync asks the gateway nothing. Without a gateway client the step is skipped.
- `createCoreTaskList`'s twelfth positional parameter `titleGateway` is renamed `aiGateway` (same position), because the MCP sync task now shares the client with the Semp thread title task.
- ADR `docs/adr/2026-11-14-mcp-tool-label-suggestions-fill-only-empty-display-labels.md`: `display_label` stays user-owned; `suggestMcpToolLabels` is the one other automated writer and writes only where the label is empty; overwriting, regenerating or another automated writer needs a new ADR.

## Deviations from the specification and spec seams

1. The Task and the rules say "in one call". The code makes one call per page of at most 50 tools (the gateway reserves a bounded output) and labels every unlabeled tool; the first version labeled only the first 50 and was changed after a review finding. The rule's "one call" is relaxed to a bounded chunk, which the first acceptance criterion (each such registration gets labels) requires.
2. A description is cut to 500 characters before it is sent (not in the Task).
3. The sync route listener takes the gateway as an optional second argument; the route is awaited inline, so a slow gateway delays the sync response by up to the gateway client's 60 s timeout (the Task says to call it in the sync flow).
4. "Markup" in the label rule is implemented as: control characters, line and paragraph separators and angle brackets are rejected.
5. Files beyond `Touches`: `worker.ts`, `mcpSync.ts`, `app.ts`, `mcpAgentPageHandler.ts` and the tests of the two entry points, `publicSurface.test.ts`, `mailSendApproval.test.ts` (comment only), the headers of the two store files, and the ADR (required by review).
6. The suggestion function is tested against a stub gateway port; the gateway row in `ai_gateway_calls` is tested through the real gateway handler with a fake provider. No real provider is called.
