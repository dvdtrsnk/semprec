## What was delivered

- `GET /api/items/:id/delete-impact`: a REST-only read, no catalog operation, answering `{ related, subtreeItemCount, subtreePageCount, linksToOwn }` from one repeatable-read transaction.
  - `related`: `{ databaseKey, count }` per collection, the counts of `relation.related` in its declared order but without the manifest `omit` list, so the Tasks of a project and the Journal of an area are counted.
  - `subtreeItemCount`: live records inside the item's inline databases, recursively, the item not counted.
  - `subtreePageCount`: live pages below the item at any depth, the item not counted.
  - `linksToOwn`: `{ itemId, propertyKey }` of every live item of a readable database that holds a value link, in any link state, with an item source naming the deleted item.
- Unknown, trashed and other-tenant ids answer the same 404 as `GET /api/items/:id`. The endpoint changes no data.
- `computeDeleteImpact(client, itemId, resolver, reader?)` in `data/src/trash/deleteImpact.ts` composes `listRelatedWithClient`, `collectItemSubtree`, `collectSubpageTree` and the new store query `listValueLinksBySourceItem` (`chokePoint/valueLinksStore.ts`, select only, tenant scoped). With a `reader` (agent grants, external client) it counts only what the reader may read; the REST route passes none (a person).

## Deviations from the specification and spec seams

1. `collectItemSubtree` already lives in `chokePoint/itemSubtreeAccess.ts` and is exported; `itemTrash.ts` is unchanged.
2. The Task puts `deleteImpact.ts` in `chokePoint/`, but the dependency-cruiser rule `chokepoint-knows-no-domain` forbids that folder to import `docs/`, and the subpage count needs `docs/pageTrash.collectSubpageTree`. The module is `data/src/trash/deleteImpact.ts` and has no choke-point facade method; the handler runs `computeDeleteImpact` inside a transaction on the pool.
3. `relation.related` omits Tasks for a project (manifest omit list), which contradicts the acceptance criterion; the read keeps the declared order and drops the omit list.
4. `linksToOwn` reading: each entry is the item that holds the link and its property key (`value_links.item_id`, `property_key`), for every link of any state with an item source naming the deleted item; holders in the Trash or in unreadable databases are left out.
5. Reader filtering is database-level (agent grants, external client sensitive databases); inherited per-item sensitivity is not applied, as in `relation.related`.
6. The new store query `listValueLinksBySourceItem` is outside `Touches`.
7. The route entry is in the slice module `routeMatrix/items.ts`.
