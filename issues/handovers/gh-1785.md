## What was delivered

- `GET /api/approval-requests` takes the query parameters `status` (`pending` or `decided`), `source` (comma list of `chat`, `tick`, `mcp`), `q`, `order` (`desc` or `asc`), `cursor` and `limit` (1 to 100, default 50). With any of them present the answer is `{ rows, nextCursor }`. With none it is the unchanged `{ rows }` of the owner's pending requests, oldest first.
- The handler (`backend/services/semprec-api/src/approvalRequestsHandler.ts`, `parseListQuery`) validates every parameter and answers `400 validation_failed` with `details.field` naming the parameter.
- `listApprovalRequestsPage` (`backend/packages/data/src/mcp/approvalRequestsStore.ts`) runs one query: owner scoped by `agent_runs.actor_user_id` as `listPendingApprovalRequests` is, ordered by `requested_at` (pending) or `decided_at` (decided) with the request id as the tie-break, a keyset cursor over (instant with microseconds, id), and `limit + 1` rows to set `nextCursor`.
- The source filter and the search run inside that query, before the page is cut, so a page is short only when no further row matches. The source kind is derived in SQL by the rule of gh-1766: the kind of the run's thread, otherwise `triggered_by` of the run a recursive climb of `parent_run_id` reaches within `AGENT_RUN_ROOT_MAX_HOPS` hops.
- `q` is matched through `unaccent` and `ILIKE` as a substring of `tool_name`, of the string values of `description.params`, of the stored chat title, of the Inbox item text of an item thread and of the heartbeat name. A backslash, `%` and `_` match only themselves. `payload` is not searched.
- `listApprovalRequestsQueuePage` (`backend/packages/data/src/mcp/approvalRequestsQueue.ts`) projects the page with the projection of the unpaged queue. Rows of the decided list also carry `status`, `decidedAt`, `executionStatus` and `conflictReason` (the translation key from `approvalConflictReason` of gh-1437).
- Migration `0150_approval_requests_list_indexes.sql`: index `approval_requests_tenant_status_requested_idx` on `(tenant_id, status, requested_at DESC)`, partial index `approval_requests_tenant_decided_idx` on `(tenant_id, decided_at DESC) WHERE status <> 'pending'`, and `CREATE EXTENSION IF NOT EXISTS unaccent`. Additive only.
- No table, column, route entry, generic operation, job name, hook, tenant cutover entry, module manifest entry, stored key or i18n key was added. The route existed; only its query parameters grew.

## Contracts dependents build on

- `GET /api/approval-requests?<parameters>`:
  - an absent `status` is `pending`; an absent `order` is `desc` (newest first) for both lists; an absent `source` is every source; an absent `limit` is 50;
  - `nextCursor` is an opaque base64url token, `null` on the last page; a client passes it back as `cursor` with the same other parameters;
  - a blank `q` is no filter but still selects the paged answer; `q` is trimmed and holds at most 100 code points;
  - `400 validation_failed` for: `limit` that is 0, above 100, not a plain positive integer (sign, fraction, leading zero, empty); an unknown or empty `status`, `order` or `source` entry, also in another letter case; a `cursor` of another shape; `q` that is too long or holds a NUL character; any of the six parameters given twice.
- **The parameterless answer orders oldest first; the paged pending list orders newest first by default.** `order=asc` gives oldest first.
- **A decided request without `decided_at` is in neither list.** The one-time cutover of issue #89 (`approvalRequestExecutionStatusCutoverMigration.ts`) rejected the requests that were pending when it ran and set no decision time. On a database that had such rows they are visible nowhere. The worker and two reviewers left this as a product question for the controller.
- Runtime exports of `@semprec/data` added by this source, all in the expected list of `publicSurface.test.ts`: `listApprovalRequestsQueuePage(client: PoolClient, input)`, `parseApprovalRequestListCursor(value)` and `APPROVAL_REQUEST_SOURCE_KINDS`. Type exports: `ApprovalRequestSourceKind`, `DecidedApprovalRequestQueueEntry`. `listApprovalRequestsPage` itself is not exported from the barrel.
- `listApprovalRequestsQueuePage` takes a `PoolClient` inside a tenant transaction (it reads the Inbox database id), and its input is `{ ownerUserId, status, sourceKinds, search, order, cursor, limit, locale }`.
- The source rule now exists twice: in SQL (`listApprovalRequestsPage`) and in `loadApprovalSources` (gh-1766). The test "filters by the derived source kind" asserts that the kind the query filters by is the kind each row shows, for every branch. A change of the rule changes both places.
- The search covers what a title is resolved from (stored chat title, heartbeat name, current Inbox item text), not the fixed words of the localized item-thread template.
- gh-1807 (the Inbox card list) builds on this list. gh-1786 reads one request and counts pending ones.

## Deviations from the specification and spec seams

1. Default order: the Task lists `order=desc|asc` without a default. An absent `order` is `desc` for both lists; an absent `status` is `pending`.
2. Decided rows without `decided_at` are in neither list (see "Contracts"). For a product decision.
3. The source filter derives the kind in SQL with a recursive CTE bounded by `AGENT_RUN_ROOT_MAX_HOPS`, the first option Task step 4 names. The ADR on iterative parent-chain traversal covers walks in the choke point; the reason for SQL here is that the filter must run before the page is cut.
4. "Thread title" in the search means what the title is resolved from. The heartbeat name of a run without a thread below a heartbeat root run is searched too, because the row shows it.
5. `conflictReason` is the real value from `approvalConflictReason`, since gh-1437 is delivered.
6. Validation decided where the Task is silent: see the 400 list under "Contracts"; a repeated kind in `source` is taken once.
7. `publicSurface.test.ts` is outside `Touches`; the barrel change requires it.
8. The fixture helpers gh-1766 had inside its describe block in `approvalRequestsQueue.test.ts` moved to file level so both blocks share them; no test of gh-1766 changed.
9. No route entry changed, so no route matrix slice, `ROUTE_CASES` or `ROUTE_HANDLER_FILES` entry was touched.
