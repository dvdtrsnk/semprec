## What was delivered

A new realtime invalidation scope `agentRuns`, delivered only to the sockets of the run's actor user.

- Frame: `{ type: "invalidate", scope: "agentRuns", projectItemId: string | null, agentRunId: string }` and nothing else. It is added to `InvalidationEvent` (`data/src/realtimeHook.ts`), `RealtimeMessage` and `parseRealtimeMessage` (`realtime/src/pgNotifyPublisher.ts`), `OutboundFrame` (`realtime/src/protocolV1.ts`), the invalidate case of `syncServer.ts` and `parseServerFrame` (`realtime-client/src/serverFrame.ts`). Run id, project id (when not null) and user id are checked as UUIDs by the listener and by the client parser; a malformed message is dropped on both sides.
- Delivery: the `syncServer` case sends through `sendToTenant(tenantId, frame, userId)`, so only the sockets of that user in that tenant receive it. A message with no user id is dropped with the warning `realtime_agent_runs_without_user`; it is never widened to the tenant. The user id is the run's `actor_user_id` read from the database.
- Publisher: `publishAgentRunInvalidation(client, agentRunId)` in `data/src/agentRuns/agentRunInvalidation.ts` reads `project_item_id` and `actor_user_id` under RLS, defers `notifyInvalidation` through `runAfterCommit` on a transaction client (a rollback publishes nothing), publishes at once on a bare pool and publishes nothing for an unknown or invisible run.
- Publication points: `createAgentRun`, `createChainedAgentRun` and `finishAgentRun` (only when this call closed the run, which covers `finishAgentRunWithErrorNotification` and the startup repair), and `publishApprovalRequestChange`, the one shared helper behind every approval-request announcement (pending creation, decision, execution outcome, success and conflict transitions, replay of an approved generic operation).

## Entry points and contracts dependents build on

- Wire scope `agentRuns` with exactly the keys `type`, `scope`, `projectItemId`, `agentRunId`. A client refetches the run or the run list on it; the frame carries no run content.
- `publishAgentRunInvalidation` is not exported from the `@semprec/data` barrel (internal to the data package), so `publicSurface.test.ts` is unchanged.
- Any new site that creates or closes an agent run must go through `createAgentRun`, `createChainedAgentRun` or `finishAgentRun`; any new approval-request announcement must go through `publishApprovalRequestChange`, so the two cannot drift.
- No route, table, migration or job name was added.

## Deviations and spec seams

1. `parseRealtimeMessage` lives in `realtime/src/pgNotifyPublisher.ts` (the handover of gh-1789 says `protocolV1.ts`); the code was followed.
2. The client test file is `serverFrame.unit.test.ts`, not `serverFrame.test.ts`; the client barrel exports no frame type, so nothing was added there.
3. The approval sites of the Task are covered by one call inside the existing shared helper `publishApprovalRequestChange`, not by separate calls at each site.
4. `createChainedAgentRun` also publishes, because it creates a run and the criterion "a run is created" requires it; the Task names only `createAgentRun` and `finishAgentRun`.
5. The message requires a user id in `syncServer`, as `approvalRequest` does.
6. Existing tests that counted or listed all frames or events were brought in line, because run creation and approval changes now announce the run: `lifecycleAdapter.test.ts`, `genericOperationGateway.test.ts` (three expected lists), `syncServer.test.ts` (the request-creation case expects 4 frames; the watch-tenancy helper leaves out `agentRuns` frames), `tenantIsolationRealtime.test.ts`, `approvalRequestRealtime.test.ts`, `approvalRequestExecution.test.ts`.
