# gh-1570 — backfill of missing and split mail threads

Repository-Issue: gh-1570

## What changed

- `CORE_TASK_NAMES.MAIL_THREAD_BACKFILL` (`mailThreadBackfill`) in `@semprec/queue`, with `api` affinity and `system` tenancy (the task enumerates tenants itself, like `mailMessagePreviewBackfill`). Its handler is registered in `createCoreTaskList` in `worker.ts`, so the api runtime runs it.
- `mail/mailThreadBackfillJob.ts`: `handleMailThreadBackfillTask(pool)` runs `forEachActiveTenant`, and per tenant two passes over keyset pages of 200, one transaction per page.
  - Pass 1 walks rows whose `thread_id` is NULL in `item_id` order. Each is locked `FOR UPDATE OF m`, given `resolveThreadId` with its headers and its item's `name` as the subject hint, and written with `UPDATE ... WHERE thread_id IS NULL` checked by `requireAffectedRows`.
  - Pass 2 walks `Message-ID`s that occur in more than one mailbox and name more than one thread, in `message_id` order. Each candidate is re-read with `lockMailMessageThreads` (`FOR UPDATE`, distinct thread ids lowest first), and the lowest thread absorbs the others with `reassignThread`. That deletes the emptied `mail_threads` rows and records the aliases.
- `mail/mailMessageMetaStore.ts`: `listUnthreadedMailMessagePage`, `listSplitMailMessageIdPage`, `lockMailMessageThreads` and the `UnthreadedMailMessage` type. Additions only.
- `enqueueMailThreadBackfill(pool)` enqueues under the fixed job key `mail-thread-backfill` with `maxAttempts: 3`. It is exported from `@semprec/data` and called from `db/runMigrationsCli.ts` after the other one-off enqueues.
- No migration, no schema change, no RLS change.

## Tests

- `mail/__tests__/mailThreadBackfill.test.ts` (new; runtime-role pool, two tenants). It covers:
  - a sent message gets its parent's thread, and a send with no ancestors gets a new thread named by its subject;
  - a child listed before its parent is merged into the grandparent's thread;
  - copies of one `Message-ID` in two mailboxes end in one thread, with no orphan `mail_threads` row;
  - a `Message-ID` whose threads an earlier merge in the same run already joined is left alone;
  - a second run changes no row;
  - more than one page of unthreaded rows, and more than one page of split copies;
  - copies are merged inside each tenant;
  - a failing tenant does not stop the others, the failing page rolls back, and the job rejects with an `AggregateError`. A `vi.mock` passthrough on `resolveThreadId` injects the failure for one `Message-ID`.
- `services/semprec-api/src/__tests__/tenantIsolationJobs.test.ts`: a case for the new `api` task, which the test requires for every task in the affinity set.
- `packages/queue/src/__tests__/tenantEnvelope.unit.test.ts`: the task is added to the expected `system` list.
- `packages/data/src/__tests__/publicSurface.test.ts`: `enqueueMailThreadBackfill` is added to the export list.

## Notes for dependants

- The job repairs stored mail on the first deploy after this change lands. #1384 and #1474 fix new traffic, and nothing else needs a thread backfill.
- `resolveThreadId` is unchanged. The backfill calls it with the same arguments live ingest uses.
- The subject hint is the item's `name`. Ingest stores `(no subject)` for a message without a subject, so a backfilled hint can read `(no subject)`. The hint is debug-only, as before.
- The enqueue runs on every deploy under the fixed key, so each deploy re-scans every tenant's `mail_message_meta` once. The run is idempotent, but a follow-up should remove the enqueue call once every deployed tenant has run it.
- Pass 2's candidate query aggregates `mail_message_meta` on every page, so its cost is pages times rows. That is acceptable for a one-off backfill, not for a recurring job.
- `db/runMigrationsCli.ts` was edited although the issue's Touches list does not name it. "Enqueue once at deploy" needs that call.
- `enqueueMailThreadBackfill` has no direct test. It is a thin wrapper over `enqueueJob`.
- The `requireAffectedRows` check in pass 1 is an invariant under `FOR UPDATE`. No test reaches it.
- Not changed here: `mail_message_meta_mailbox_message_uq` on `(message_id, mailbox_item_id)` is not tenant-leading, so it works as an existence oracle across tenants (see the `db-migrations` skill). It is a candidate for a separate issue.
