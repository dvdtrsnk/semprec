# Handover: seed a mailbox's sync state in live-sync discovery only under a non-waiting share lock on its live item

Delivered on chain `e1-236-mail-sync`, candidate commit `53e44bc3d89b3f74dbbd43eb11d81d26c06d4da5`, landed by a `--no-ff` merge on `feature/backend-parallel` as the first chain of a train with `e1-243-blob-writer` and `e1-246-mail-oauth`.

**What changed.** New `ensureMailAccountSyncStateOfLiveMailbox` in `backend/packages/data/src/mail/mailAccountSyncStateStore.ts`. It returns an existing sync state row as it is, with no lock and no write. Otherwise it runs `SELECT id FROM items ... deleted_at IS NULL FOR SHARE SKIP LOCKED` on the mailbox item and then `ensureMailAccountSyncState`. It returns `null`, having written nothing, when the item is in the trash, belongs to another tenant under row-level security, is not in the given Mailboxes database, or is row-locked by another transaction. `discoverActiveAccounts` in `mail/mailLiveSyncRoot.ts` calls it with the page's `mailboxesDatabaseId` and leaves an account with a `null` result out of `found` without reporting `onLifecycleError`; a later pass picks it up. The share lock is held until the page transaction ends, so a removal that starts after discovery took the lock waits for the page transaction and then leaves the mailbox without a row. New ADR `docs/adr/2026-11-15-live-sync-discovery-seeds-a-sync-state-only-under-a-non-waiting-share-lock-on-the-live-mailbox.md`.

**Contracts dependents build on.** `ensureMailAccountSyncStateOfLiveMailbox(client, ...)` as the only way discovery seeds a missing row; `ensureMailAccountSyncState` is unchanged for its other callers. A mailbox removed between discovery's read and its seeding gets no row and no lifecycle. No route, table, migration, operation or job name changed.

**Files.** `backend/packages/data/src/mail/mailAccountSyncStateStore.ts`, `backend/packages/data/src/mail/mailLiveSyncRoot.ts`, the ADR above, `backend/packages/data/src/__tests__/mailAccountSyncStateLiveMailbox.test.ts` (new), `backend/packages/data/src/__tests__/mailLiveSyncRoot.test.ts`.

**Tests.** Store tests (existing row returned with no lock and no write, trashed item, another tenant under RLS with a same-tenant control, item in another database, item held `FOR UPDATE` by another transaction, share lock kept until the transaction ends). Root tests on runtime-role pools (removal committed between the page's read and its seeding, provider default sync mode for gmail and outlook, a locked item does not make discovery wait, a removal after the share lock waits for the page transaction). The existing savepoint-isolation tests are unchanged and pass.

**Deviations and spec seams.** The Task says discovery "never waits, so it cannot be part of a cycle". That is true of the item lock statement only. The insert can wait for another transaction's uncommitted insert of the same `item_id`, and `replaceMailboxCredential` (`mail/mailOauthRouteHandlers.ts`, reauthorization) inserts a missing row before it locks the item. In that one interleaving discovery (holding the share lock) and the reauthorization form a deadlock cycle and Postgres aborts one statement. The ADR states this and does not claim cycle freedom beyond the removal's lock order. The Task fixes the design and puts the connect flows out of scope, so the code is unchanged. The issue refers to an existing pool wrapper that intercepts `SAVEPOINT discover_account`; none existed, so the worker wrote a new wrapper in the test.

**Criteria NOT RUN or BLOCKED.** None.

**Review.** Requirements and tests lens: clear. Rules and architecture lens: one medium finding (the cycle above), deferred. Both reviewers read statically and ran no tests. The recheck (one focused round) confirmed that the deferral is correct.

**Follow-ups.** Open a source that makes the reauthorization (and the other seeding callers of the connect flows) take the item lock before it inserts a missing sync state row, or seed through `ensureMailAccountSyncStateOfLiveMailbox`; it needs an ADR on the lock order against the sync job (state row, then item) and a two-transaction test. Alternatively record in an ADR that the cycle is accepted, with discovery as the likely victim. Do not repeat the Task wording "cannot be part of a cycle" as a claim. The follow-up source is only proposed; it is not created by this landing.
