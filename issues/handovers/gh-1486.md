# gh-1486 implementation handover

Implementation base: `883d84fb1216972e0506d4dbdddb9ac99173a883`.
Blocked by gh-1476 (single-step relations on confirm) and gh-1479 (multi-step envelope validation).

## What changed

- New `backend/packages/data/src/inbox/proposalSteps.ts` with `executeProposalSteps`. It takes the
  active steps (`selectActiveSteps` from `inboxTickAction.ts`, now exported, so disabled and
  unreferenced optional steps are dropped by the same rule as validation), orders them so a step
  follows every step whose `ref` it names (in `relations` or `after.relations`), and writes them in the
  caller's transaction:
  - `create`: `createItemWithClient`, then `createRelationWithClient` per target; `{ ref }` targets use the
    id created by that step.
  - `link`: edges only, from the existing item.
  - `update`: `updateItemWithClient` with the step `properties` (same validation, approval and risk rules
    as any update, a project's `status` included), then `deleteRelationWithClient` for `before` targets
    missing from `after`, then `createRelationWithClient` for new ones.
  - A `ChokePointError` from a write is rethrown with the same status/code/message and `details`
    extended with `{ ref, field }` (`field` is the relation key, or `properties` for an item write).
  - Resolves to the primary step's item id and database id.
- `confirmProposalWithClient` gets an optional `actingUserId` (5th argument). It is passed to the item
  creation, to the steps, and to the card's own status update, so invalidations go to that user only.
  A single-step envelope keeps the old path (item, credential, transcript edge, `writeEnvelopeRelations`).
  A multi-step envelope runs the executor instead of the item write and of `writeEnvelopeRelations`; the
  credential gate and the transcript-card edge then apply to the primary step's item. `resultItemId` and
  `resultLabel` are the primary step's.
- `createConfirmProposalRouteHandler` reads `ctx.identity?.user.id` and passes it (`identity` is an
  optional field of the duck-typed context, as in the push and transcription handlers).
- `selectActiveSteps` is exported from `inboxTickAction.ts`, which `index.ts` re-exports with `export *`,
  so `publicSurface.test.ts` lists it.

## Tests

`__tests__/proposalActions.test.ts`, new block "multi-step proposals on confirm (issue #1486)": company
plus person (listed first) creates both and the `People.companies` edge, result is the company; failing
person rolls back company and edge and the 400 carries `ref: "person"`; disabled follow-up task leaves
only the health record; unreferenced optional person is not created; `update` moves a project's
`Projects.area`; `update` writing `status: "done"` with a failing later step leaves the old status and
edge, then succeeds alone; repeated confirm creates nothing twice; invalidations carry the acting user.
`inbox/__tests__/inboxRouteHandlers.test.ts`: the route handler addresses invalidations to
`identity.user.id`. `proposalActions`, `inboxRouteHandlers` and `publicSurface` tests pass; `tsc
--noEmit` on `packages/data`, eslint and prettier are clean. No full verify.

## Notes for dependants

- `before` is not compared with the item's current value (no stale-edit guard); the `update` step only
  deletes the `before` targets that `after` drops. Moving relations assumes the `before` edges exist; the
  delete is idempotent.
- Per-step results (#1648) are not stored; the executor only returns the primary item.
- The block-author rule for page-content and journal confirm paths mentioned in the issue context was not
  part of the Task list and is not implemented here.
- Blocks inserted by multi-step envelopes do not exist (steps are database items only).
- No schema, migration or tenant-table count changed.
