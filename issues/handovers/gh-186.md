## Summary

This implements #186. There are now two ways to put a transcription that failed for good back into the pipeline: a daily heartbeat and a manual rerun route. Both skip rows set to `locked`.

The worktree was checked out at a commit from before #248 was merged, so I fast-forwarded the branch to `origin/develop` first. That brings in #248's retry policy and `item_automation` state machine, which this work depends on.

### Daily requeue heartbeat
- New action `core.transcriptionRequeueSweep` (`createTranscriptionRequeueSweepAction` in `transcriptionActions.ts`). For every non-trashed Transcriptions row whose `item_automation.status` is `error`, it reads `fileItemId` from the row's `link` and enqueues `transcriptionJob` under the original key, `transcription-job:${fileItemId}`, with a fresh 3-attempt batch.
- The sweep only lists `error` rows, so `done`, `pending` and `locked` rows are never requeued. It makes no writes of its own and never sets `locked`.
- If the sweep runs again while a job is still queued, graphile-worker replaces that job under the same key. If the job already used up its attempts, graphile-worker detaches it from the key (it never runs again) and the fresh batch takes the key. Either way there is one runnable job per row.
- If a row's `link` is not a Files item link, the sweep logs a warning, skips it and carries on with the other rows.
- Scheduling: `seedSystem` adds a `dailyTime` 04:30 heartbeat on the Semprec project. The next fire time is computed from the time the heartbeat is created, using the existing scheduler rules (#84).
- Existing installs: the seed never runs again once the system databases exist. So a new step, `runTranscriptionRequeueHeartbeatCutoverMigration`, runs from `runMigrationsCli` and from the test `globalSetup`. It adds the heartbeat to the project that already owns the Files transcription trigger. It holds a table lock so two concurrent runs can't both add it, and it does nothing if the heartbeat already exists or if there is nothing to attach it to yet.
- The seed and the migration take the heartbeat's name and rule from one shared constant, `TRANSCRIPTION_REQUEUE_HEARTBEAT`, so the two can't drift apart.

### `POST /api/transcriptions/:id/rerun`
- Added to the `systemDatabases` manifest's `customRoutes` in the same way as `POST /api/transcriptions` (`justification: "transactional-semantics"`), and to the route matrix and the write-boundary test.
- In one transaction it row-locks the `item_automation` row and then enqueues the same `jobKey`. It writes nothing to the item. Holding the lock means a user's lock arriving at the same time either lands before the check or waits until the enqueue commits.
- Responses:

  | Case | Response |
  |---|---|
  | `done` or `error` row (or any other row that isn't locked) | `202 { id, fileItemId }` |
  | `locked` row | `403 transcription_locked` (`ForbiddenError`, standard error contract) |
  | `:id` is not a UUID | `400` |
  | Unknown id, or an item with no `item_automation` row or no Files item link | `404` |

### Shared link helpers
`transcriptionSourceLink` builds a row's `link`. The pipeline's step 0 now uses it, so the pipeline and the new readers share one format. `readTranscriptionSourceFileItemId` validates the JSONB value when reading it back.

Neither path creates a second row or repeats a paid stage. The job resumes the existing row from the #182/#183 checkpoints, and every pipeline step still checks the lock (#248).

## Tests
- **`transcriptionRequeue.test.ts`** (new, data layer, 24 tests):
  - the sweep requeues only `error` rows, not `done`, `pending` or `locked`;
  - repeated sweeps collapse onto one job;
  - an exhausted job gets a fresh batch under the same key;
  - the sweep leaves `item_automation` unchanged;
  - rows with a bad link and trashed rows are skipped;
  - the heartbeat is seeded, and the upgrade step adds it once, is idempotent, and does nothing when there is no trigger or no seed;
  - the rerun route returns 202 with the original key and no item write for `done` and `error` rows, collapses repeats onto one job, and returns 403 for `locked` (nothing enqueued), 400 for a bad id, and 404 for the three not-found cases;
  - the link helpers.
- **`transcriptionTask.test.ts`** (semprec-transcribe, running the real pipeline with fake gateways through graphile-worker):
  - after a permanent failure, the daily sweep resumes the same row to `done`; the fake gateway sees exactly one diarize call and one ASR call, and one Transcriptions row exists;
  - a manual rerun of a `done` row makes no paid call at all;
  - a manual rerun of an `error` row resumes from its checkpoints;
  - a `locked` row is rerun by neither path.
