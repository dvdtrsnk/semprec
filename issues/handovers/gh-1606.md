# gh-1606 — Version the Inbox fingerprint and include type id, capture time and attachments

Repository-Issue: gh-1606

## Delivered behavior and production wiring

- `backend/packages/data/src/inbox/fingerprint.ts`:
  - `computeInboxFingerprintV2(input)` returns `v2:<hex>`, the SHA-256 of `canonicalizeJson` (from `@semprec/shared`) of `{ v: 2, typeId, text, date, time, attachmentHashes, transcribedText }`. `attachmentHashes` is sorted with `compareByCodePoint` on a copy, so the caller's array is not reordered.
  - `isFingerprintCurrent(stored, { v2Input, legacyEmoji, legacyText })`: a stored value starting with `v2:` is compared with the version 2 value of `v2Input`. Any other stored value (a version 1 string, or `null`) is compared with `computeInboxFingerprint(legacyEmoji, legacyText)`.
  - `computeInboxFingerprint` is unchanged and is now used only for that comparison.
- `backend/packages/data/src/inbox/inboxTickAction.ts`:
  - `readAttachmentHashes(client, itemId)` reads the item's `inbox_attachments` rows joined with `blobs` on the client it is given. It returns `COALESCE(b.content_hash, b.id::text)` for each row.
  - `inboxFingerprintInput(client, item, type)` builds the version 2 input: type id, text, date, time, attachment hashes and `transcribedText: ""`.
  - The gate in `readTickSnapshot` skips the AI call when `isFingerprintCurrent` holds for the existing unlocked proposal. The snapshot carries the version 2 value.
  - The stale check in `writeTickResult` recomputes the version 2 value from the fresh state and compares it with the snapshot's version 2 value. That same value is what `reviseProposal`, the create path and the validation-failure `writeNeedsClarification` store. The no-recognized-type path still stores `fingerprint: null`, as before.
- No migration. Nothing is added to the `@semprec/data` exports (`fingerprint.ts` is not re-exported from `index.ts`).

Decisions the Task left open (named for review):

- The Task says `blobs.content_hash`, which is nullable. A blob without one is covered by its id, so adding or removing such an attachment still changes the value. Uploads always store a hash (`blobs/fileUploadStore.ts`), so this only applies to a blob attached without one.
- Version 2 does not include the type's emoji, because the Decision's object has no emoji field. A version 2 card therefore does not recompute when only its type's emoji changes. A version 1 card does (see the compatibility rule above).

## Notes for dependants

- The tick runs only from `onItemEvent` heartbeats, and `chokePoint/itemWrites.ts` is the only writer that enqueues them (create, update and delete of an item). `relationOps.ts` enqueues nothing, and `insertInboxAttachments` and `deleteInboxAttachment` enqueue nothing either. So an attachment change or a type change reaches the tick only when the caller also writes the Inbox item, or enqueues the tick itself. This is not wired by this issue. The Task's Touches do not include the trigger, and no production caller of these writes exists yet.
  - #1963 (capture): an item create enqueues the tick in the capture transaction and the job runs after commit. The attachment rows must be inserted in that same transaction, as the gh-1564 handover asks, so the first tick sees them.
  - #1703 (move into Files) and any route that attaches or detaches on an existing item, including a type choice: add the trigger there.
- A version 1 card is recomputed only when its emoji or text changed. After its first recompute it holds a `v2:` value.
- A later audio-transcription change populates `transcribedText` from `inboxFingerprintInput`. That changes the value of every stored version 2 card that has audio, so it needs its own decision and cannot be done silently.
- Forced recompute (#1947, #1955) is not part of this gate and is not implemented here.
