# Handover for gh-1367

Two tenant tables, `semp_threads` and `semp_messages`, now exist. Nothing reads or writes them yet. The work is committed locally on `wf/gh-1367`; I did not push or open a PR.

The targeted integration tests pass: `sempThreadsSchema` (new), `tenancyCatalog`, `tenantPurge` and `agentRunEventsRetention`, plus the `tenantPurgeOrder` unit test. Prettier, eslint on the new test and migration numbering also pass. I did not run the full `pnpm run verify`. `tenantExport.test.ts` has one failure unrelated to this change: an expiry delta of 608400000 ms instead of 604800000 ms, a one-hour difference that looks like a DST artefact of the host clock.

- **Migration:** `0087_semp_threads_and_messages.sql`, additive and rollback-safe. Both tables carry `semprec:tenancy=tenant`, RLS with `tenant_isolation` and `tenant_rows`, and DML grants to `semprec_side`. Every foreign key is created valid. `agent_runs (tenant_id, id)` already had a unique index (`agent_runs_tenant_id_id_uq`), so none was added.
- **Constraint names:** the composite foreign keys are named `*_fkey` (for example `semp_messages_agent_run_fkey`), deliberately not `*_tenant_fkey`. The tenancy catalog test treats every `*_tenant_fkey` as the twin of a plain single-column foreign key. These tables have only the composite keys, so that suffix would break its assertion.
- **Extra CHECK:** `semp_threads_title_chat_check` requires `title` to be NULL unless `kind = 'chat'`, which enforces the "set only for chat" rule. An item thread may carry a NULL `subject_proposal_id`.
- **Uniqueness:** a tick thread is unique per `(tenant_id, heartbeat_id)` and an item thread per `(tenant_id, subject_inbox_item_id)`, both as partial unique indexes.
- **Delete behaviour:** deleting a thread cascades its messages. Deleting an agent run that a message references, or a heartbeat that a thread references, fails with SQLSTATE 23001 (restrict violation), not 23503.
- **Purge and export:** `tenantPurgeOrder.ts` needed no edit. The purge job derives the table list from the tenancy comment and the order from the foreign keys, so messages are deleted before threads and the agent run and heartbeat tables come after them. There is no foreign key cycle (the self-reference on `reply_to_message_id` is handled by the purge job). The tenant export enumerates tables by the same comment, so it needed no change.
- **Tests:**
  - **`sempThreadsSchema.test.ts` (new):** RLS isolation for reads, writes and cross-tenant references, uniqueness per kind, the kind/column CHECK matrix, role/status/system column checks, cascade and restrict behaviour, and survival of old messages through `agentRunEventsRetention`.
  - **`tenancyCatalog.test.ts` (outside the issue's Touches list):** I added both tables to `TENANT_TABLES`, which the catalog invariants require.
