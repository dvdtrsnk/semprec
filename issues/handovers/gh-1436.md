# gh-1436 — validate Inbox item type processing config in create and update hooks

Repository-Issue: gh-1436

## Delivered behavior

- `backend/packages/data/src/inbox/inboxTypeWriteHook.ts` (new): `inboxTypeItemCreateHook`, an `ItemCreateHook`, and `inboxTypeItemUpdateHook`, an `ItemUpdateHook`, both for the database whose `ownerModuleId` is `inboxItemTypes`. The create hook checks the written `processingMethod` and `targetDatabase`. The update hook checks the resulting item's pair, and only when the patch contains `processingMethod` or `targetDatabase`.
- `backend/packages/data/src/inbox/inboxTypesStore.ts`: exports `INBOX_TYPE_TARGET_DATABASES` (`areas`, `projects`, `tasks`, `people`, `files`, `events`, `healthRecords`, `companies`), its type `InboxTypeTargetDatabase`, and `assertValidProcessingConfig`. The target check uses the constant, so `journal` and `transcripts` are refused with `ValidationError` on `field: targetDatabase`. The other rules and messages are unchanged.
- `CreateInboxTypeInput.targetDatabase` is narrowed to `InboxTypeTargetDatabase`. This is a type-only change.
- `createInboxTypeWithClient` and `updateInboxTypeWithClient` no longer call the check and keep their input shaping. `updateInboxTypeWithClient` still reads the item first, so the not-found message is unchanged.
- `backend/packages/data/src/domainWriteHooks.ts`: registers both hooks.
- No migration, no schema change, no new error code. `seedInboxPipeline.ts` is unchanged.

## Behavior notes

- Every Inbox item type create and update through the choke point is checked: REST, agent tools and `/mcp`. The check runs inside the write's transaction, so a refusal rolls the write back. The create hook does not run on an idempotency replay, which keeps the type it already stored.
- A type already stored with `journal` or `transcripts` stays readable and stays editable in its other fields, such as `name`. Only a write that touches `processingMethod` or `targetDatabase` is checked, against the pair as it would then be stored.
- The helpers validate only while `domainWriteHooks.ts` is loaded. `index.ts` loads it first in every process. A test that imports an Inbox helper by its deep path must import `../domainWriteHooks.js` itself, as `inboxPipeline.test.ts` now does.
- A type with neither `processingMethod` nor `targetDatabase` is still accepted, as before.
- Not changed: the `targetDatabase` select in `seedInboxPipeline.ts` still lists all ten system keys (`selectConfig([...TEN_DATABASE_MODULE_IDS])`). Clients therefore still see `journal` and `transcripts` as options, and a write of either is refused. The Task changes the check only.

## Tests

- `backend/packages/data/src/__tests__/inboxTypeWriteHook.test.ts` (new, real Postgres, 76 cases). Every refused and accepted case runs through three writers: REST (`writerKind: user` with `humanWriterUserId`), an agent tool (agent with a run identity) and `/mcp` (agent without a run). Refused creates: `journal`, `transcripts`, `nonsense`, a non-string target, a `database` type without a target, a `pageContent` type with a target, a target without a processing method, and an unknown processing method. Each refusal is a 400 `validation_failed` on the named field and leaves no row. Accepted creates: each of the eight targets, a `pageContent` type without a target, and a type with neither. Updates: moving the target to `journal`; turning a `database` type into `pageContent` while the target stays set; an unknown method; switching to another allowed target; `pageContent` with the target cleared in the same patch (accepted); renaming a type stored with `journal` (accepted); writing the stored invalid pair again (refused). A database outside `inboxItemTypes` with the same property keys is not checked.
- The stored invalid state is produced by a raw `UPDATE items` fixture (`storeTargetDirectly`), because the choke point now refuses that state. The fixture has a comment saying so.
- `backend/packages/data/src/__tests__/inboxPipeline.test.ts`: imports `../domainWriteHooks.js`, so its existing helper rejection tests still reach the hook. No other existing test changed.
- Mutation checks, run and reverted: without the update hook registration, 12 update-refusal tests fail (four per writer). With the `hasOwn` guard removed, the 3 rename tests fail.
