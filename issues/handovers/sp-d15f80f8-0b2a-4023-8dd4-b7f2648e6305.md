# Handover: batched calendar sync passes, non-blocking manual sync request

Implementation commit `261519a87` on `feat/internet-accounts`. Nothing was run against production or any remote host.

**Root cause (reproduced locally, embedded Postgres 18, 1980 fake events in 6 calendars, 14 000 trashed Emails).** The fetch already ran with no transaction open; `applyCalendarSync` then wrote every calendar and Event in one transaction: 67.6 s on its own, 92.9 s with concurrent readers (~30 ms per Event created through the choke point; the reminders resync create hook's `SELECT app_tenant_default()` is the last query `pg_stat_activity` showed in production). That transaction held the account guard, the `calendar_account_sync_state` row `FOR UPDATE` (the manual request's upsert waited on it until the 60 s statement timeout) and one of the `alldots-api` pool's 10 connections. `countRoots` is not slow: 6.8 ms over 14 000 trashed rows (`items_deleted_at_idx` + `items_database_id_id_idx` bitmap scan, anti-join on `items_pkey`), and it waits on no row lock. No index was added.

**Design.**
- `applyCalendarSync(pool, input)` opens its own transactions, each under the account guard (lock order unchanged: guard → state row → calendar rows → Event rows):
  - *prepare*: re-check account and tracked snapshot, calendar writes (a new calendar gets a `calendar_remote_state` row with no cursor), untrack vanished calendars, compute deletions, claim the account (`calendar_account_sync_state.apply_pass_id`, new baseline column);
  - *batches* of `CALENDAR_SYNC_BATCH_EVENTS` = 25 Event operations (deletions, masters, overrides): check the account is live with Calendars on (else `skipped`) and the claim is still this pass's (else `superseded`), take the calendars' share locks, re-read the batch's remote states, apply, re-queue pending pushes, reconcile the batch's invitations;
  - *final*: same checks, store every cursor, re-queue waiting pushes, write the collected change notifications, record `ok` (clears the claim), resolve the problem.
- A pass that ends early keeps the batches it committed and the old cursors; the next pass re-applies by remote id and snapshot. A newer pass's claim supersedes an older one at its next step.
- `POST /api/accounts/:id/calendars/sync`: inside a savepoint with a 50 ms transaction-local `lock_timeout`, reads the account `FOR SHARE` and runs the debounce upsert. If a lock is held (55P03), it checks the account without the lock and queues the pass without recording the request, answering 202 `queued: true`. The 404 and 409 `calendars_disabled` answers are unchanged.
- Test seams: `CalendarAccountSyncOptions.batchEvents` and `afterBatch`. `CreatePoolOptions.max` and `createRuntimeRolePool(…, { statementTimeoutMs, max })` let the load test build a constrained pool.

**Measured.** Longest `alldots_data` transaction during a 2000-event pass went from 67.6 s (92.9 s in the load test) to 1.5 s. Concurrent account summary reads: p50 14 ms, max 31 ms. The manual request during the pass took 21 ms. The manual request against a held state row or account row went from blocking until the statement timeout to answering 202 in under 1 s.

**Not changed (follow-ups).**
- The mail IMAP pass holds a transaction, plus the tenant's mail-thread guard, across IMAP I/O for 10 messages per pass. It uses one pooled connection per pass. A fetch-then-apply split for mail is a separate issue.
- `getProfileAccountSummary` checks out 5 pool connections at once per request.
- The `alldots-api` pool has pg's default of 10 connections. They are shared by HTTP, graphile-worker (`QUEUE_CONCURRENCY` 4) and the LISTEN clients.
- The per-Event cost of choke-point creates.
- Several passes for one account can run at once (job key replacement while one runs). The newest claim wins, so overlapping passes repeat fetches but stay correct.
