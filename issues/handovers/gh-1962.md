## What was delivered

The `subscribedEvents` system database of the calendar module, for the events of subscribed calendars, read-only for every user, agent and `/mcp` client. Properties `uid` (text), `title` (title), `startsAt` and `endsAt` (date with time), `timeZone` (text), `allDay` (checkbox), `place` (text), all `owner: 'system'` with owner process `calendar`, and a `one_to_many` relation pair `Calendars.subscribedEvents` (A) / `SubscribedEvents.calendar` (B), both sides system-owned by the calendar module, schema locked. It is created for a fresh tenant by `seedSubscribedEventsInTransaction`, called last from `seedCalendarsInTransaction`, and for an existing tenant by the cutover `runSubscribedEventsCutoverMigration` (takes the tenant seed lock, skips a tenant without Calendars, no-op when the database exists). Labels in the calendar catalogs (cs, en); the manifest declares the database and the module version is 1.1.0.

The review fix adds a guard in the choke point: `assertCallerMayWriteDatabase` (`chokePoint/itemWrites.ts`), called from `createItemReportingReplay` and `updateItemWithClient` after the key check, refuses with 403 `owner_violation` a user or agent write, empty or not, into a system database that has no user-owned property. The system writer and a caller with `allowedSystemKeys` are unaffected, and so is a database the user created. Before it, `{}` or `{"properties":{}}` inserted a blank row.

## Entry points and contracts dependents build on

- Database key `subscribedEvents` (`SUBSCRIBED_EVENTS_MODULE_ID` in `seed/calendarsKeys.ts`), owner module `calendar`; property keys as above. The feed import (gh-2004) writes with the calendar module's system owner process (`ownerProcess: 'calendar'`); any other writer is refused.
- The inverse property `Calendars.subscribedEvents` was added to the locked Calendars schema by raw SQL under an exclusive `properties` lock, as `Calendars.events` is; it is system-owned, so a user cannot write an edge from either side.
- `runSubscribedEventsCutoverMigration(pool)` in `runTenantCutoverMigrations`, after the gh-1958 entry and before the area-note cutover.
- Generic writes into the database answer 403 with code `owner_violation` (not `forbidden`), the answer of the generic write path for any system-owned property in this repository. This holds for REST `POST`/`PATCH` and `/mcp` `semprec.item.create` and `semprec.item.patch`.
- `assertCallerMayWriteDatabase` is a choke-point rule for every caller (REST, `/mcp`, Inbox proposal steps): only `subscribedEvents` and the mail folders database are seeded without a user-owned property.
- The date format stored in `startsAt` and `endsAt` is not validated by the seed; the timeline source of gh-2005 reads zone-less wall-clock values `YYYY-MM-DDTHH:mm[:ss[.fff]]`, which gh-2004 must write.

## Deviations from the specification and spec seams

1. The i18n keys are in `calendar/i18n/{cs,en}.json` (where the Calendars labels live), not `seed/i18n` as the Touches list says.
2. The relation is a pair; the inverse property `Calendars.subscribedEvents` was added to the locked schema to get "one calendar has many subscribed events" enforced by `one_to_many` cardinality, as `Events.calendar` does. The issue did not name the inverse.
3. Generic writes answer 403 `owner_violation`, not `forbidden`.
4. The seed code is in `seed/seedSubscribedEvents.ts` (called from `seedCalendars.ts`) instead of growing `seedCalendars.ts`.
5. The REST and `/mcp` tests are in a new `semprec-api` test file, because the data package has no HTTP dispatcher; the Touches list names only the data test.
6. Existing tests changed because the database exists in every seeded tenant: `calendars.test.ts`, `smoke.test.ts`, `moduleRegistryLoadAll.unit.test.ts`.
7. The security fix touched `chokePoint/itemWrites.ts`, which the Touches list does not name; the Task requires that no user, agent or `/mcp` write reaches the database, and the empty write was a way in.
