**What changed**
- **Limiter:** `clientIpThrottle.ts` is new and has the exports the issue lists, with the specified limits.
  - The key is IPv4 as is, `::ffff:a.b.c.d` as its IPv4, and any other IPv6 as its `/64`.
  - State is per `(action, key)`, expired events are pruned on access, and it holds at most `maxKeys` keys. When full, it drops keys with only expired events first, then the least recently recorded one.
  - The docstring states the single-process assumption and that a restart clears all windows.
- **Wiring in `authHandler.ts`:**
  - `AuthRequestListenerOptions` gains `clientIpThrottle?`, defaulting to one limiter per listener.
  - A throttled request answers `429 { error: "Too many attempts; try again later", code: "rate_limited" }` with `Retry-After`, before the body is read.
  - Login records an `UnauthorizedError`, a reset request records every accepted request before `requestPasswordReset`, and consume records a `PasswordResetTokenError`. Validation failures count toward none.
  - The per-account reset cap and the *(email, IP)* login lockout are unchanged.
- **Timing floor:** `PASSWORD_RESET_REQUEST_MIN_DURATION_MS = 400` in `passwordResetActions.ts`. Every path that returns waits out the floor, and the mail send stays un-awaited after commit. I updated the docstring. Because of the floor, each reset request in the tests now takes about 400 ms.
- **ADR:** `docs/adr/2026-10-17-per-ip-auth-throttles-held-in-process.md` records the in-memory decision, the rejected Postgres table with a retention sweep, the single-process assumption, the `/64` grouping, and that the DB lockout keeps its role.
- **Tests:**
  - `clientIpThrottle.unit.test.ts` covers the criteria for window and retry-after, action and address independence, and both eviction orders, with an injected clock. It also covers the limits constant, IPv6 key forms, rounding, and recency across actions.
  - `authHandler.test.ts` gets integration tests for login, reset request and consume, with a small-limit throttle injected. They check that successes, 400s and other addresses are unaffected, that no token row is created past the limit, and that a valid token is not consumed once throttled.
  - `passwordResetActions.test.ts` checks the 400 ms floor for an unknown email, a capped account and a fresh token. The existing "answers a known email before the mail send has resolved" test still passes.
