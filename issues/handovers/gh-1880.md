## What was delivered

The calendar timeline now answers task-in-event state.

- The core Tasks source selects and places a Task by `taskDisplayDay` (the item date is the display day), drops a Task whose stored `hiddenUntil` is later than the read instant and a Task with a `completedInEvent` edge.
- A new step `attachTaskInEventState` (`calendar/timelineTaskInEvent.ts`) runs after the sources. Event entries (stored, real and virtual occurrences) get `tasks` and `counts` from the new batched `readEventsTasks`; Task entries get `hostEvent { id, title, ended, date, timeFrom, timeTo, state }`. The compact shape carries counts only.
- A Task in an event that has not ended appears only inside the event's `tasks`; once the event has ended it is a separate all-day item on its derived day with `hostEvent.ended` true and state `missed`; a Task added to a later event reports `moved` on the earlier one with the later event's name. A done Task is on its completion day.
- The number of statements does not depend on the number of events (tested 2 versus 10).
- A new ADR, `docs/adr/2026-11-13-the-timeline-adds-task-in-event-state-after-its-sources-are-read.md`, records the post-sources step.

## Entry points and contracts dependents build on

- `readCalendarTimeline` (`calendar/timelineRead.ts`) calls `attachTaskInEventState`; the timeline route and the agenda route, which returns timeline items, now carry `hostEvent`, `tasks` and `counts` on every stored item (null where not applicable).
- `readEventsTasks(client, eventIds, now)` in `tasks/taskStateInEvent.ts` (not exported from the data barrel); `buildEventTasks` takes `now` as a parameter, and `eventTaskCounts` and `readEventTasks` use it with unchanged behaviour. The tasks and counts of an Event equal those of `GET /api/events/:id/tasks`.
- `CalendarTimelineContext` has a required field `at: Date`, the read instant, so `hiddenUntil`, `ended` and the states compare with one clock.
- No route, operation, table, migration or job name is added; `publicSurface` is unchanged.

## Deviations from the specification and spec seams

1. The batched reader for tasks per event did not exist, so `taskStateInEvent.ts` (outside Touches) exports the new `readEventsTasks`.
2. `CalendarTimelineContext` gets the required field `at`; `eventOccurrences.test.ts` and the context assertion in `timelineRead.test.ts` were updated.
3. The new sibling module and the call from `readCalendarTimeline` were not foreseen by decision 2 of the 2026-11-10 ADR ("does not change the merge"); the new ADR documents it.
4. Interpretations: the compact Task shape gets counts only; `hostEvent` is the last live host event that has a date; an entry a source made up (read-only, no occurrence) is unchanged; a virtual occurrence carries the tasks of its series Event, a real occurrence those of its own item; a Task keeps its own `timeFrom` and `timeTo`; an unreadable display day is logged with the property `date`; a `hiddenUntil` that is not an instant does not hide. A Task whose `completedInEvent` edge points to a trashed Event is dropped from the timeline, which follows the Task text literally.
5. Existing tests were adapted to deliberate behaviour (completion day via a fake clock, strict item schemas, compact expectation, `effectiveDate` outranking `date`, one more Event in the journal statement-count test).
