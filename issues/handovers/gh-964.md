I loaded `error-handling` for the 404 handling and the failure paths. I did not separately load `io-hardening`: the change adds no routes and no new outbound call beyond re-pointing the existing fetches.

**What changed in `web/src/api/httpGenericOperations.ts`**
- **`listItems`:** posts to `/databases/:db/query` and parses the response with `itemPageSchema`.
- **`countItems`:** pages through that same route with `limit: 200`, following `nextCursor` until it is `null`, and sums `items.length`. A failure on any page rejects the whole call with the existing status classification.
- **`getItem`:** reads `GET /items/:id` and resolves `null` on a 404 or when the item's `databaseId` isn't the requested one.
- **`updateItem`:** reads the item first, then sends `PATCH /items/:id` with `{ properties, ifVersion: updatedAt }`.
  - If the read finds nothing, or finds an item in another database, it rejects as `unavailable` (404) and sends no PATCH.
  - A 409 on the PATCH surfaces as `retryable`, with no automatic retry.
- **`linkItem`:** sends a body-less `PUT /items/:id/relations/:key/:target` and discards the response, so a 200 with JSON or a 204 both work.
- **`unlinkItem`:** sends `DELETE` to the same path.
  - `request` takes a new `notFoundBody` option for this call. A 404 whose body matches `{ error: { code: "not_found", details: { resource: "relationEdge" } } }` resolves `undefined`.
  - Any other 404 (another resource, non-JSON, or no body) still rejects as `unavailable`, and other statuses keep their existing classification.
- **Left alone:** `getView` and `callOperation`. I removed the unused `relationPath` helper, and every path segment goes through `encodeURIComponent`.

**Tests in `web/src/api/__tests__/httpGenericOperations.test.ts`** cover each acceptance criterion. I also changed the `callOperation` case's description to say no backend route currently serves it.
