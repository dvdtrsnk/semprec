# Handover: keep the CalDAV login on the account's server and read an edited resource whole

Commit on `fix/ia-provider`: `185f3b6fc`.

**Changes.**
- `caldavHttp.ts`: `caldavCredentialScope(start)` (the start's origin; for an iCloud start also https `icloud.com`/`*.icloud.com` on the default port without userinfo). `withCalDavSession` takes `start`; the session fetch refuses any request or redirect hop outside the scope (`invalidResponse`) before it is sent; `CalDavSession.inScope`.
- `caldavClient.ts`: every server-named address (principal, home, resources, sync-collection and listing hrefs) is resolved through the scope and refused outside it; a calendar of the home listing outside it is left out.
- `caldavAdapter.ts`, `caldavConnectVerification.ts`: pass the start.
- `caldavIcal.ts`: `editableParts` reads every value of every component first; an ical.js read failure is `CalendarResourceUnreadableError` (with cause), answered as `invalidResponse` by the adapter.
- `fakeCalDavServer.ts`: `withAuthorization` on each recorded request, `calendarHomeOrigin`.
- Docs: `domain-calendar-tasks-and-media.md` (CalDAV), `edges-io-and-errors.md`.

**Behaviour change to know.** A generic account whose domain's well-known address redirects to another host no longer syncs (`invalidResponse`; connect answers `caldav_server_invalid`); it is set up with the CalDAV server's address. The review asked to drop the credential on such a hop; refusing was chosen because the foreign server's 401 would otherwise read as a wrong password (`needsReauthorization`). An invitation answer on a resource with an unreadable value now fails instead of writing the PARTSTAT.

**Tests** (`caldavAdapter.test.ts`): a redirect to another origin refused by sync and connect with no request reaching it; a foreign calendar home refused and never requested; every request to the own server carries the login; eight scope cases (iCloud allow-list, look-alike, http, port, generic start); update, invitation answer and occurrence cancellation of a resource with `DTEND` `garbage` fail as unreadable after one GET with the resource unchanged. The existing redirect test now asserts `invalidResponse` (the scope refuses the hop before the address policy would) and is renamed accordingly.

Each new test was run against the code before the fix and failed. Not run: full `test:integration`, `test:e2e`, web and mobile pipelines. Nothing ran against a real provider.
