# gh-1526 — filter relations by emptiness

Added the conditions `{ type: "relation_is_empty" | "relation_is_not_empty", property }` (no `value`, strict object) to both filter-tree copies: `FILTER_CONDITION_TYPES`, the `FilterCondition` union and the zod schema in `packages/data/src/views/filterTree.ts` and `packages/shared/src/genericOperations/filterSort.ts`.

`filterCompiler.ts` compiles `relation_is_empty` to `(NOT EXISTS ...)` and `relation_is_not_empty` to `EXISTS ...` over `item_relations` for the property's relation definition and side. The edge counts only if its other end is a live item: a `CROSS JOIN LATERAL` over `items` pinned to `property.targetDatabaseId` with `deleted_at IS NULL` and `OFFSET 0`, the same partition-pruning shape as `relation_path_contains`. The definition id and database id are bound parameters; only the `item_a`/`item_b` side names (from the registered definition) are interpolated. A relation property without a resolvable definition, side or target database raises a 400 `ValidationError` on that property and adds no parameters.

The guard in `compileCondition` now treats the two new types as relation conditions, so they fail with the existing 400 on a non-relation property. The `is_empty` on a relation message now names `relation_is_empty/relation_is_not_empty` too.

Tests: `filterCompiler.unit.test.ts` (SQL shape for both sides and both types, bound parameters, non-relation and unresolved-property rejection, message, parity of accepted/rejected inputs with the shared schema), `filterSort.unit.test.ts` (shared schema), and the new database-backed `relationEmptinessFilter.test.ts` (no project, only soft-deleted project, mixed live/deleted, live project, soft-deleted file excluded, reverse relation side inside `not`, non-relation 400, `is_empty` message).

Verification: lint, prettier, tsc for `data` and the unit tests (277 in the shared genericOperations files plus the data compiler tests) passed. `relationEmptinessFilter.test.ts` was NOT RUN: this sandbox has neither Postgres nor Docker access, so the integration suite needs the integrator or CI. No migration, no public-surface or tenant-table count changed.
