## Summary

Implements issue #223: the `semprec.tick` handler's fingerprinting and create/revise/skip gate over `processingProposals`.

- **`inbox/fingerprint.ts`** (new): SHA-256 fingerprint of an Inbox source's canonical type emoji + text.
- **`inbox/inboxTickAction.ts`**: resolves the source item's recognized type, computes the fingerprint, and implements create-if-absent / revise-if-unlocked-and-changed / skip-otherwise, plus the locked-card rule (`confirmed`/`rejected` proposals are never recomputed). The content-level decision (target page/database properties) is delegated to an injected `ComputeSemprecProposalFn`, mirroring the existing `RunAgentFn`/`coreAgentRunAction` pluggable-function convention, since the actual LLM call (ai-gateway) is out of this issue's scope. The handler itself is the only thing that writes to `processingProposals` — the injected function never writes to any target database or page.
- **`chokePoint/databasesStore.ts`**: added `getDatabaseByModuleId` to resolve a type's `targetDatabase` module key to a real database id.
- **`seed/seedInboxPipeline.ts`**: extended the tick heartbeats' `actionConfig` with the two new database ids the handler needs.
- **`inboxTypesStore.ts`**: exported the existing `LOCKED_PROPOSAL_STATUSES` set for reuse.
- Tests: updated `inboxTick.test.ts` for the new required parameter, added `inboxTickProposal.test.ts` covering all acceptance criteria (exact envelope shape, fingerprint correctness, skip/revise/lock behavior, untyped-item stub, no writes outside `processingProposals`).
- **`testSupport/testDb.ts`**: fixed a pre-existing test-infra bug found while validating — `resetDatabase` never dropped the per-database `items_p_*` partitions `createDatabase` creates, causing catalog/lock bloat that exhausted Postgres's shared memory partway through a full-suite run. Now drops accumulated partitions on every reset.
