## What was delivered

- Every card with status `invalid` in `GET /api/inbox/cards` carries `invalidReason { code, field, itemId, label, text }` (`inbox/inboxCardsStore.ts`): the stored reason is parsed with `invalidReasonSchema` (gh-1482) and `text` is `renderInvalidReason` in the locale of the list (English fallback).
- A card with no stored reason, or one that does not parse, carries `{ code: "unknown", field: "", itemId: null, label: "", text }` with the generic sentence from the new catalog entry `invalidReason.unknown` (en and cs).
- Cards in other statuses, approvals and transcript cards have no `invalidReason` key (absent, not null).

## Contracts dependents build on

- `InboxCard.invalidReason?` (optional) on the cards of `GET /api/inbox/cards`; code `unknown` is the fallback code. The catalog key `invalidReason.unknown` in `inbox/i18n/en.json` and `cs.json`.
- No route, table, migration or export added.

## Deviations from the specification and spec seams

1. `invalidReason.ts` is outside Touches: the parameter type of `renderInvalidReason` is widened so the generic sentence goes through the same function.
2. A stored reason that does not parse is treated like a missing one (`unknown`) so the card stays in the list; the Task names only the missing case.
3. The field is optional on the `InboxCard` type and absent on other cards.
4. Test seam: the reason is written through `updateItemWithClient` with `allowedSystemKeys` because the writer of target reasons (gh-1916) does not exist yet; legacy state is made with commented raw SQL.
