## What was delivered

A file attached to a task (a `Files.tasks` edge) now takes over that task's project and follows it.

- The link rule `fileProjectsFromTasks` is declared in `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts`: source `Tasks.project`, target `Files.projects`, via the `Files.tasks` relation, with the ownership-handoff comment. `Files.projects` stays `owner: user`; the `valueLinks` process writes it only while the file's link for that property is `on`. No engine, route, operation, table, migration, hook or job change: the existing link engine (gh-1593 and later) does all of it.
- Behaviour that dependents can rely on, all recorded by tests:
  - a file without a project that is attached to a task gets a link in state `on` and the task's project; a task without a project gives the file no project and the link is `on`, so the file gets the project when the task later gets one; setting the task's project to none leaves following files with no project and the links on;
  - a file attached to two tasks holds the union of both projects once each, and a change of one task's project replaces only that task's contribution; detaching one task keeps the other, detaching the last leaves the value as the file's own;
  - a file that already has a project of its own when attached keeps it and gets no link (the engine creates a link only into an empty property without a link); `link.relink` on it answers `409 value_link_conflict`;
  - a user or agent change of a following file's project breaks the link (`brokenBy` `user` or `agent`) and the task's next change leaves the file alone; `link.relink` restores following, `link.unlink` keeps the value and stops following;
  - the file's company follows from the project in a second hop through `fileCompaniesFromProjects`;
  - a recurring task: the advance moves the link's source from the finished instance to the next one (issue #1673), so the file follows the current instance only;
  - a change of the task's project reaches the file through the `valueLinksPropagate` job, so the file holds the old project until that job has run; a write of a `Tasks.project` edge now queues one such job for this rule, so a test that writes one must run in a tenant scope.
- ADR `docs/adr/2026-11-15-a-files-projects-follow-its-tasks-by-a-link-rule.md`: the rule and the ownership handoff, the union for two tasks, own project gets no link, no backfill, the second hop, that the rule graph stays acyclic, that it adds no order for a user or agent edge write on `Files.projects` (the order of the 2026-11-15 user-edge-write ADR applies), and the first-link-wins composition with `fileProjectFromThread`.

Entry points and contracts dependents build on:

- Link rule key `fileProjectsFromTasks`; the stored keys of the existing properties and relation (`Tasks.project`, `Files.projects`, `Files.tasks`).
- No export, route, operation, table, migration or job name was added or changed.

## Deviations from the specification and spec seams

1. The decision record's challenge point 3 (a file keeps the projects of all instances of a recurring task) does not hold on this tree: the advance moves the link's sources to the next instance (gh-1673), so the file follows the current instance only. The ADR and a test record the actual behaviour.
2. The fixture rule of `linkRuleEdgeHook.test.ts` was replaced (see above), and `inboxTickProposal.test.ts`, `inboxRouteHandlers.test.ts` and `taskSeriesTrash.test.ts` were changed beyond the three tests the Task names.
3. `Files.projects` has several rules and one link per property; the first rule that links a file keeps it, because `linkRuleEdgeHook` skips a link of another rule. The ADR records this for `fileProjectFromThread` (a file brought by mail has the thread's `on` link from ingest, so attaching it to a task gives it no project from the task). **Seam after the merge:** gh-1756 landed `fileProjectsFromEvents` (`Events.project` to `Files.projects` via `Files.events`) on the tip after this chain was cut, so `Files.projects` is now the target of three rules and the ADR text "two rules" is out of date. The same first-link-wins reasoning applies to the Event rule, but no test of either source attaches one file to both a task and an Event, so that composition is not proven by a test. The ADR was not edited at landing because it is the chain's own reviewed text.
