# Handover for gh-1465

Guidance drift, library automation, restore-test failures and a stale `agents` process now raise a Semp status problem next to their existing notification, in the same transaction. The work is committed locally on `wf/gh-1465`; I did not push or open a PR.

- **Keys (`semp/sourceProblemKeys.ts`):** `guidanceProblemKey(projectItemId, fingerprint)` gives `guidance:<projectId>:<fingerprint>`, `automationProblemKey(databaseId)` gives `automation:<databaseId>`, and the constants `BACKUP_RESTORE_PROBLEM_KEY` (`backup:restoreTest`) and `AGENTS_PROCESS_PROBLEM_KEY` (`agents:process`).
- **Guidance drift:** `driftAction.ts` has a new required dep `problems: GuidanceProblemWriter<Tx>` (port and `RaiseGuidanceDriftProblemInput` in `@semprec/shared`'s `guidanceDrift.ts`), called right after the active notification with `occurrenceKey` `<fingerprint>:<seenAt>`. The `PoolClient` adapter is `createGuidanceProblemWriter()` in `@semprec/data` (category `guidance`, kind `guidanceDrift`, `warning`, source `agent_guidance_drift_findings`). No production composition root builds the action yet, so whoever wires it must pass this adapter.
- **Library automation:** `libraryMetadataJob.ts` raises inside the failure transaction, only when the tenant has a user (like the notification). The database id is read from the loaded item (`item.databaseId`), `occurrenceKey` is the job id, so a redelivered job does not count twice.
- **Operator alerts:** `OperatorAlertInput` has an optional `problem` descriptor; `writeOperatorAlert` raises it per administrator in the same tenant transaction as `writeNotification`, with `occurrenceKey` suffixed by the admin's user id. `restoreTestResult.ts` passes it for a failed run only; `observabilityCheckSystem.ts` passes it only when the stale process is `agents` (the process name in the heartbeat table, which the issue calls `semprec-agents`). `queue_backlog` and the other processes pass none.
- **Tests:** `__tests__/sempProblemsProducers.test.ts` (new, 9 tests, passing) covers the acceptance criteria: one problem per finding and one for another finding, three failing library jobs giving `occurrence_count` 3 and a redelivery not counting, a failed restore giving a critical problem per administrator in two tenants and none for a member, a passed run raising nothing, the stale `agents` process, a stale `transcribe` and `queue_backlog` raising nothing, and a rolled-back raise leaving none. `driftAction.unit.test.ts` got a fake `problems` port and asserts the raise. The existing restore, observability, library and publicSurface integration tests still pass. I did not run the full verify.

Notes for dependants:

- The `outcome` of `raiseProblem` is not used here; the push for a new or escalated problem (#1466) needs `writeOperatorAlert` and the guidance port to return it if wanted.
- `writeOperatorAlert` still rolls back and retries as before; because `semp_problems` rows are written in each admin's own committed transaction, a retry re-raises with the same `occurrenceKey` and adds no occurrence.
- Recovery (#1915) should resolve `backup:restoreTest` and `agents:process` per tenant, since the problems are one row per administrator tenant.
