# gh-1451 — [inbox-core 08/22] Add card-state properties to Processing proposals

## Delivered behavior

- **Seed** (`backend/packages/data/src/seed/seedInboxPipeline.ts`): Processing proposals gains twelve system-owned properties: `aiProposal`, `userOverrides`, `userEditedKeys`, `typeCandidates`, `candidates`, `invalidReason`, `referencedItemIds`, `results` and `context` (json); `aiVersion` (number); `reason` and `recognizedTypeId` (text). `status` gains the options `computing` and `computeFailed`; the existing options and their order are unchanged. Every new property has `owner_process` NULL, as the database's other system properties already do.
- **Per-tenant cutover** (`backend/packages/data/src/inbox/processingProposalsCardStateCutoverMigration.ts`): `runProcessingProposalsCardStateCutoverMigration(pool)`, registered in `runTenantCutoverMigrations` after the project-guidance step. In one transaction it:
  - returns at once when no `processingProposals` database exists;
  - takes `LOCK TABLE properties IN EXCLUSIVE MODE`, which locks the whole `properties` table for that tenant's transaction;
  - inserts each missing property with raw SQL, because `propertiesStore.createProperty` refuses a schema-locked database;
  - appends each missing `status` option;
  - backfills `aiProposal = proposal` on the items of that database where `proposal` is set and not JSON null, and `aiProposal` is absent or JSON null.

  A database that exists without a `status` property makes the cutover throw, the tenant's transaction rolls back, and the registry reports the tenant by id.
- **i18n** (`backend/packages/data/src/inbox/i18n/en.json` and `cs.json`): `property.processingProposals.<key>.name` for the twelve properties and `property.processingProposals.status.option.computing` and `...computeFailed`.
- **Shape parity:** the property list and the option list are written out twice, in the seed and in the cutover. A test asserts that a fresh seed and a populated tenant end with the same shape.

## Notes for dependants

- **Write `aiProposal` together with `proposal`.** The backfill matches any card that has a `proposal` and no `aiProposal` at the moment it runs. A card written by a pipeline that does not yet set `aiProposal` therefore gets `aiProposal` copied from its `proposal` on the next run of the cutover. Producers and the revise route (#1471, #1495, #1500, #1648, #1482, #1848, #1978, #1640, #1975, #1485, #1850, #1870) must write both in one statement, or the copy will hold a revised proposal as "the last automated proposal".
- The cutover runs inside each tenant's transaction, and `LOCK TABLE properties IN EXCLUSIVE MODE` blocks property inserts and updates for every database while it runs. The transcripts cutover does the same.
- The new properties are NULL-`owner_process` system properties. `findOrphanedOwnerProcessProperties` in `backend/packages/data/src/manifest/driftCheck.ts` reports a NULL `owner_process` as orphaned, so these count as orphans exactly as the existing system properties of this database already do.
- Display labels for these properties are the `property.processingProposals.*` entries of `en.json` and `cs.json`. The seed and the cutover also write an English `name` on each property row.
