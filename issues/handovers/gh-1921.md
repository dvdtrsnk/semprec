## What was delivered

- `lockUnlockedProposal` (`inbox/inboxTickAction.ts`) now decides whether the assistant result is stale by `fingerprint` and `aiVersion` (a missing `aiVersion` counts as 0), through `assistantSideChanged`, instead of by `updatedAt`. A manual `PATCH values` that commits while the assistant call runs therefore no longer discards the result. The reasons `gone`, `deleted` and `locked` (confirmed or rejected), the serialization/busy branch and the `changed` log line are unchanged; `changed` is logged when either value differs.
- `reviseProposal` (also the create-or-revise path of `writeTickResult`) writes only the assistant side: `aiProposal` (through `aiProposalPatch`, so `aiVersion` grows by one), `fingerprint` and one history entry of kind `recompute`. The manual values stored on the locked row are laid over the new envelope: `proposal` is the effective envelope, `userOverrides` and `userEditedKeys` are recomputed. Overrides that cannot apply (another `entityKind` or `target` than the previous `aiProposal`, a key the new target lacks, a step other than the destination) are dropped and the `recompute` history message names the dropped `ref.key`s (never values). A key whose manual value now equals the new assistant value leaves `userEditedKeys` silently.
- `writeNeedsClarification` is unchanged in behaviour: the overrides stay stored, `proposal` and `aiProposal` become null, and a later valid output lays them over the new envelope. A docstring sentence and a test were added.

## Entry points and contracts dependents build on

## Deviations from the specification and spec seams

1. The new code lives in the sibling module `tickRecompute.ts` because `inboxTickAction.ts` had 15 counted lines of room under the 900-line ESLint cap (the rule skips blanks and comments).
2. As in gh-1924, only overrides of the destination ref (primary) are kept; overrides of another step are dropped because their databases are unknown here (tick envelopes are single-step).
3. The effective envelope is not re-validated with `assertValidProposalEnvelope` after the manual values are laid over it: a kept value that no longer validates (for example a removed select option) is stored and refused at confirm, which re-validates the stored proposal. Throwing in the tick write would make the job retry forever, and dropping silently would lose a user edit. Same remark as in the gh-1924 handover.
4. One history entry of kind `recompute` names the dropped keys (not a separate `reset` entry as gh-1924 writes); its `keys` field is unset because the schema documents it as the user-edit keys.
5. The Task's Out of scope stays out: the explicit recompute route (gh-1955), a thread-driven protected-key change (gh-1938), the destination-change reset in revise, fingerprint versioning.
6. The commit trailer of the segment names Claude Sonnet 5.5, the model that wrote it.
