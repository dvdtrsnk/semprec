## What was delivered

`GET /api/semp-status` now returns `resolvedRecent: [{ id, category, resolutionTitle, resolvedAt }]`: the tenant's problems resolved within the last seven days, newest first (`resolved_at DESC, id DESC`), capped at 100, without problems closed with the resolution kind `sourceDeleted`.

- `semp/sempStatusResolved.ts` exports `readSempResolvedRecent`; it reads the rows, then the names in batched statements (items through `getItemsByIds`, heartbeats, reply thread titles, databases, the guidance finding payload kind), so the number of statements does not depend on the number of problems.
- `semp/sempResolutionTitles.ts` exports `renderResolutionTitle(catalogs, kind, resolutionKind, params, locale)`. It has no Postgres import. Titles come from the catalog keys `status.resolved.<resolutionKind>.<kind>` in `semp/i18n/cs.json` and `en.json` (mail, reply, heartbeat, guidance permission and behavior variants, backup, process, library). A name that cannot be read becomes the neutral word `(unnamed)` / `(bez názvu)`; a kind or resolution kind without an entry gets the generic title `A problem was resolved` / `Problém byl vyřešen`. Names are placed literally (`$&` and `{placeholders}` in a name are safe).
- Migration `0162_semp_problems_resolved_idx.sql`: partial index `(tenant_id, resolved_at DESC, id DESC) WHERE resolved_at IS NOT NULL`. Additive.
- After the review fix, `readSempStatusReport` is a thin wrapper over a shared transaction body with no extra reader (the summary and overview paths therefore do not run the resolved read); `getSempStatusReport` passes `readSempResolvedRecent` as the extra reader, which runs last in the same transaction.

## Deviations from the specification and spec seams

1. The status catalogs are `semp/i18n/cs.json` and `en.json` (the loader reads one `cs.json` and `en.json` per module directory), not `status.cs.json` and `status.en.json`; the entries are `status.resolved.*`.
2. `renderResolutionTitle` takes the loaded `ModuleCatalogs` as its first parameter because catalogs load asynchronously and are already loaded once per report.
3. The reader and the renderer are sibling modules; `sempStatusReport.ts` only calls `readSempResolvedRecent`.
4. The initial catalog has no entry for `agentRun` problems; a resolved `agentRun` (and any unlisted kind) gets the generic title instead of being dropped.
5. The recovery title for a reply reads the thread title through `semp_messages`; the reply producer does not exist in the tree yet, so its test fixture is a synthetic row, like the existing report test. The sync job itself was not driven in the mailbox test: the problem is resolved with the same `resolveProblem` call.
6. Before the review fix, `readSempStatusReport` always ran the resolved read; after it, only the full endpoint does.
