## What was delivered

- `backend/packages/data/src/inbox/inboxTypeEdgeHook.ts` exports the relation-edge-changed hook `inboxTypeEdgeChangedHook` (`RelationEdgeChangedHook` of gh-1530). It is registered with `registerRelationEdgeChangedHook` in `backend/packages/data/src/domainWriteHooks.ts`.
- For each `op: 'create'` and each `op: 'delete'` the registry reports, the hook reads in one statement, keyed by the relation definition id, whether the definition belongs to the property with key `type` of the system database owned by module `inbox`, and on which stored side that property is. For any other relation it returns. For the Inbox `type` relation it takes the Inbox item from that side (stored side A or B, whichever property the write named) and calls, on the edge write's own client:
  1. `triggerOnItemEventHeartbeats(client, inboxDatabaseId, 'update', inboxItemId)`: one job per enabled `onItemEvent` heartbeat that watches `update` on the Inbox database. With the seeded pipeline that is the `semprec.tick` heartbeat: task `heartbeatFireCore`, payload `{ heartbeatId, itemId }`, job key `heartbeat-fire:<heartbeatId>:<inboxItemId>`, on the queue lane the production routing table gives the tick.
  2. `enqueueJournalInboxRecomputeForInboxItem(client, inboxItemId)`: task `journalInboxRecompute`, payload `{ journalDayItemId }`, job key `journal-inbox-recompute:<journalDayItemId>`. The recompute is not queued when the pipeline databases or the item's Journal day edge cannot be resolved; that function is unchanged.
- Both jobs are written in the transaction of the edge write, so they commit or roll back with the edge. The hook writes no row of its own, does not touch the card and calls no model: whether the changed type needs a new proposal is the decision of the tick's fingerprint, and the day cache keeps its single writer, the recompute job.
- `op: 'update'` (`updateRelationWithClient`, a metadata replacement on an existing edge) queues nothing.
- A repeated create of an edge that already exists is reported by `createRelationWithClient` as `create`, so a repeated `PUT` of the type an item already has queues both jobs again. The docstring, the file header and the registration comment say so, and a test pins it.
- The creatability dry run `assertRelationCreatableWithClient` runs the write hooks only and no edge-changed hook, so it queues nothing. No code was needed for that.
- The hook sits in the `*WithClient` functions of the choke point, so it fires for every writer of the edge: the REST endpoints `PUT` and `DELETE /api/items/:id/relations/type/:typeId`, the generic operation gateway (`relation.put`, also for an agent-run actor), the MCP tool `semprec.relation.put`, and the internal writers, a capture with a type (`createInboxItemWithClient`) and `deleteInboxTypeWithClient`.
- No SQL migration, no table, no column, no index, no route, no generic operation, no new job name, no export from the data barrel, no stored key, no user-facing label and no ADR was added. The pattern is the one of `docs/adr/2026-09-30-choke-point-domain-hooks-through-a-per-process-registry.md`.

## Contracts dependents build on

- Export, from the module only: `inboxTypeEdgeChangedHook`. Nothing was added to `backend/packages/data/src/index.ts`.
- After any accepted create or delete of an Inbox type edge, the Inbox `update` tick of the item and the recompute of its Journal day are queued. A later writer of that edge needs no trigger of its own for either. The record of gh-1947 (replace an Inbox item's type in one action) says that its own trigger and this hook can both fire and that the tick job key replaces a pending job, so a double trigger is harmless; both jobs here are keyed (`heartbeatFireJobKey`, `journalInboxRecomputeJobKey`).
- Registry order in `backend/packages/data/src/domainWriteHooks.ts`: the two comment lines and the registration of this source are the last entries of the file, behind the two entries of gh-1714. In the edge-changed registry the hook therefore runs last, after `itemSearchEdgeChangedHook`, `inboxTypeLockChangedHook`, `linkRuleEdgeHook`, `peopleLastContactEdgeChangedHook`, `transcriptCompanyLinkReleaseEdgeChangedHook` and `projectDerivedValueEdgeChangedHook`. It runs after `inboxTypeLockChangedHook` of gh-1669, so a delete that hook refuses has queued nothing when it throws; the jobs would roll back with the transaction in any case. The hook needs no other hook's result.
- Order for gh-1723, which names gh-1718 as a `Shared-file ordering` blocker: its entries in `domainWriteHooks.ts` go after the entry of this source, unless its Task names another position.
- Side effects later sources and tests meet:
  - A capture with a type (`createInboxItemWithClient` with a type, in production `createItemWithRelationsWithClient`) now queues two tick jobs for the new item, the `create` tick and the `update` tick. After a successful first tick the second is a no-op on an unchanged fingerprint. A test that follows the `create` tick through its attempts and counts jobs or history entries removes the `update` job first, as `inboxTick.test.ts` does with `graphile_worker.remove_job(heartbeatFireJobKey(updateHeartbeatId, itemId))`.
  - `deleteInboxTypeWithClient` queues one `update` tick per Inbox item whose type edge it clears.
  - An open transaction that wrote a type edge holds the uncommitted keyed job `journal-inbox-recompute:<day>`. The tick's read phase enqueues the same key, so a tick that starts while such a writer is open waits there, before it calls the model, takes the serialization failure `withTickTransaction` already retries and computes from the committed type.
  - Every edge create and edge delete of every relation costs one more statement, the lookup above. A test that counts the statements of an edge write counts it.
  - A test that asserts the exact content of the job queue after a write of an Inbox type edge sees the two jobs.

Follow-ups, recorded without a finding, not changed and not filed as issues:

- Requirements reviewer and the worker, needs an owner decision: a typed capture queues the `create` and the `update` tick. When the AI gateway fails or the budget is exceeded, both jobs retry, `writeComputeFailure` clears the fingerprint, and the second job's final attempt appends a second "Computing the proposal failed" history entry with twice the gateway attempts. No test shows the combined outcome, because `inboxTick.test.ts` removes the `update` job. Removing the duplicate needs the creating writer to tell the hook (the context of gh-1530) or the failure write of #1485 to not repeat itself; both are outside this issue. The reviewer recommends a follow-up issue.
- The worker and both reviewers, lock order of `deleteInboxTypeWithClient`: it clears edges source by source, so it now holds the day's keyed recompute job of an earlier source while it waits for the row lock of a later one. A tick write phase, a proposal confirmation or another type edge write on that later source of the same day takes the source lock first and the day key second, so the two can deadlock and Postgres aborts one with 40P01. `deleteInboxTypeWithClient` has no caller outside tests at this commit; the follow-up should land before a route calls it.
- Rules reviewer, derived from the code and not reproduced: a type edge writer takes the day key while it holds the source row and the card rows (order: source, cards, heartbeat key, day key). The tick's read phase takes the day key first and then, in three branches, a blocking card lock. Example: an item is restored from the trash and its type is set while the restore's tick is in its read phase; Postgres aborts one with 40P01, a retried tick job or a failed `PUT` or `DELETE`. Confirm, reject and revise already have the same exposure. The fix belongs to the tick's read phase. With the entry moved to the end of the file, the hooks registered between `inboxTypeLockChangedHook` and this hook run before the heartbeat key and the day key are taken; for an Inbox type edge the queue runner did not analyse what they lock.
- Requirements reviewer: item purge deletes edges with raw SQL (`chokePoint/itemTrash.ts`) and runs no edge-changed hook. A trashed type already reads as no type in the tick and the day summary, so nothing observable changes there.
