## What changed

Only `backend/packages/data/src/__tests__/gmailWatchLifecycle.test.ts` changed. This fixes finding `421021068d` from PR #1146.

- Added `withFailingEnqueueTarget(failingMailboxItemId, body)`. It is a small helper used only in this file and only for this one enqueue override. It makes the mocked `enqueueMailAccountSync` reject for the failing mailbox and pass every other id to the actual implementation. It runs `body` inside `try` and puts the actual implementation back in `finally`. If `body` rejects, the error still reaches the caller.
- The dispatcher test "leaves a message unacknowledged when one target's enqueue rejects, while the other target still runs" now runs its whole body inside that helper. The old restore, which only ran when the test reached its last line, is gone.
- Clearing recorded calls is still separate from restoring the implementation. The `mockClear` calls in `beforeEach`/`afterEach` and the `vi.useRealTimers()` calls are unchanged.
- New regression: "restores the actual enqueue implementation when the failing-target override's body rejects". Inside the override it first checks that an enqueue for the failing mailbox is rejected with the simulated error. Then it throws a sentinel error. Outside the helper it checks that the helper rejects with that same sentinel and that no job was queued. Finally it makes a real enqueue for the same mailbox in tenant zero and checks three things:
  - the mock was called exactly once;
  - exactly one `mailAccountSync` job now exists for that mailbox;
  - the job's envelope carries tenant zero.

  If the `finally` restore is removed, this last enqueue would hit the override, be rejected, and the test would fail.

No production code, other transport overrides or timer cleanup were touched.
