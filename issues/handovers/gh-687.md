## Summary

A floating heartbeat (`interval`/`everyNDays`) could stop being scheduled without any sign of it. The sweep sets its `next_fire_at` to `NULL` and relies on the fire job's first attempt to compute the next one. That step, `prepareHeartbeatOccurrenceFire`, ran outside the fire task's final-attempt handling, and so did the affinity check and the handler lookup. If any of them threw on all three attempts, the job was dead-lettered with no `last_error`, no notification, a stuck occurrence and no `next_fire_at`.

`pnpm run verify` in `backend/` passes. I didn't run it in `web/`, because nothing there changed.

### Changes

- **`schedulerStore.ts`: new `recordHeartbeatFireSetupFailure`**, the counterpart of `failHeartbeatOccurrence` for a failure that happens before or instead of the action handler. Inside the caller's transaction it:
  - locks the heartbeat row with `FOR UPDATE` and returns `null` if the row is gone;
  - if the heartbeat is enabled and `next_fire_at IS NULL`, recomputes `next_fire_at` from the database clock and stores it together with `last_error`;
  - if the rule can't be parsed or computed, records `last_error` as `<message>; schedule could not be restored: <reason>` and leaves the heartbeat unscheduled;
  - otherwise only records `last_error`;
  - marks the occurrence `failed` only if it is still `queued` or `running`;
  - returns `{ id, name }` for the notification.
- **`sweep.ts`**
  - **Scheduled path (`runScheduledOccurrenceFire`):** preparation, the affinity check and the handler lookup are now inside a `try`. On the final attempt, a throw from any of them runs one transaction that calls `recordHeartbeatFireSetupFailure` and `notifyHeartbeatError`, and then the original error is rethrown. The existing handler `try/catch` is unchanged.
  - **Manual/`onItemEvent` path (`createHeartbeatFireTaskForAffinity`):** the affinity check and handler lookup moved inside the existing `try`, so their final-attempt failure records `last_error` and the notification like a handler failure does.
  - Both docstrings now say this covers preparation, affinity and handler-lookup failures.
- **`publicSurface.test.ts`:** added `recordHeartbeatFireSetupFailure` to `EXPECTED_RUNTIME_EXPORTS`.

### Two things beyond the issue text

- **Close-out failure.** If writing the failure record itself fails (for example, the database is still down), the close-out error is logged with `console.error` and the original error is still rethrown. Without this, the close-out's error would replace the one that actually failed the job.
- **Write-safety check.** The new heartbeat `UPDATE`s target a row this function has just locked, so they use `requireAffectedRows`. The occurrence `UPDATE` can legitimately match zero rows when the occurrence is already terminal. I added it to `.github/scripts/write-safety-baseline.json` (one line), as that script instructs for legitimate cases. This is outside the issue's Touches list, but `check:write-safety` fails without it.

`getSystemTimezone` is read before the parse/compute `try`. A database failure there propagates as itself instead of being recorded as "schedule could not be restored".

## Tests (`scheduler.test.ts`, integration)

- **Floating heartbeat, preparation fails on the final attempt:** the pool's first `connect()` rejects with `simulated database outage`. The task rethrows it; `next_fire_at` is non-null and in the future; `last_error` is set; the occurrence is `failed` with the same message; exactly one `heartbeat_error` notification exists.
- **Same failure on a non-final attempt:** nothing is recorded (`next_fire_at` still `NULL`, no `last_error`, occurrence still `queued`, no notification).
- **The close-out fails too:** the original error is rethrown and nothing is recorded.
- **Scheduled fire with no registered handler, final attempt:** the occurrence is `failed`, `last_error` names the missing handler, the fixed rule's `next_fire_at` is unchanged, and one notification exists.
- **Manual (`triggeredByRunId`) fire with no registered handler, final attempt:** `last_error` is set and one notification exists.
- **`recordHeartbeatFireSetupFailure` with an unparseable rule:** `last_error` says the schedule could not be restored, and the occurrence is `failed`.
- **`recordHeartbeatFireSetupFailure` edge cases:** a terminal occurrence is left alone, and a deleted heartbeat returns `null`.
