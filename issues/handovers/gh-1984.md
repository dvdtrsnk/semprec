## What was delivered

Undoing a confirmed Inbox card now cancels the follow-up jobs its confirmation queued, in the undo's own transaction (step (f) of `undoConfirmedProposalWithClient`, `cancelFollowUps`).

- A result whose `followUp` is `transcriptionQueued` (a recording card): removes the `transcriptionCreate` and `transcriptionJob` of the Files item, locks the Files row first and then removes the jobs (the producers' lock order: file, then job rows), then reads the checkpoint of the Files item. A Transcripts item that a job already checkpointed goes to the Trash through `itemDeleteWithClient` with the user writer; a transcript that is already in the Trash, or purged, is left as it is; a checkpoint that is not an item id, or whose transcript links to another file, refuses the whole undo and rolls it back.
- A result whose `followUp` is `mcpSyncQueued` (an MCP server card confirmed by a user): removes the `mcpServerSync` job of the server item.
- A result without `followUp` touches no job, whatever jobs other cards have queued.
- Handlers: `syncMcpServerTools` re-locks the server item (`FOR UPDATE`) in its write transaction and in its failure-recording transaction, and writes nothing, announces nothing and records no status for an item that is gone or in the Trash; the handler task ends as a no-op on the resulting `NotFoundError`. The transcription handlers already wrote nothing for a Files item in the Trash or gone when no transcript exists; tests pin it and no production change was made there.
- Review fix: `recordRecordingIntake` now returns `enqueued` (true only when it added a job itself) and `confirmRecordingCard` records `transcriptionQueued` only then, so the undo never cancels the jobs of the user's own upload when the card reused a live Files item. The confirm still reads both jobs back and fails when one is missing.
- ADR `docs/adr/2026-11-14-a-recording-card-claims-a-transcription-follow-up-only-for-the-jobs-it-enqueued.md` narrows the Result rule of the recording-card ADR accordingly. No ADR for the cancellation itself: `2026-10-25-undoing-a-confirmed-proposal-reverses-its-recorded-writes` already decides it.

## Entry points and contracts dependents build on

- `cancelJob(client, jobKey)` exported from `@semprec/queue`: the inverse of `enqueueJob` through `graphile_worker.remove_job($1)` on the caller's client. An unlocked job is deleted; a running job keeps running but its key is cleared and its attempts used up, so its failure is not retried. A key that names no job removes nothing. The caller builds the key from ids of its own tenant (the job table is not partitioned by tenant).
- `cancelTranscriptionJobs(client, fileItemId)` and `transcriptionCreateJobKey(fileItemId)` in `packages/data/src/transcription/transcriptionJob.ts` (the key `transcription-create:<id>`; the old `transcription-job:<id>` helper is unchanged); `cancelMcpServerSync(client, mcpServerItemId)` in `packages/data/src/mcp/mcpSync.ts`.
- `recordRecordingIntake` returns `{ ..., enqueued: boolean }`.
- `testSupport/testDb.ts` re-exports `reopenProposalWithClient` for the cross-package test in `semprec-transcribe`.
- Rule for later follow-up kinds: a confirm records a `followUp` only for work it enqueued itself, and the undo cancels exactly the recorded follow-ups in its own transaction.
- No new route, operation, table, migration or job name.

## Deviations from the specification and spec seams

1. Spec seam: the Task names `handleTranscriptionJobTask` in `transcriptionJob.ts` as the transcription handler, but it is a payload-only stub; the real handlers are `createTranscriptionCreateTask` and `createTranscriptionTask` in `services/semprec-transcribe/src/transcriptionTask.ts`. No production change there (900-line cap).
2. Both jobs the confirm queues are cancelled (`transcription-create:<id>` and `transcription-job:<id>`); the Task names only the second. Removing only it would leave the create step to create the Transcripts item.
3. `cancelJob` is a new helper in `@semprec/queue` (outside `Touches`) because the graphile_worker SQL lives there; it has three callers.
4. `testSupport/testDb.ts`, `mcpSync.test.ts` and `undoRecordingTranscript.test.ts` are outside `Touches`; so is `recordingIntake.ts`/`recordingCardConfirm.ts` and the ADR, which the review fix required.
5. `syncMcpServerTools` was already safe by accident for a server trashed mid-sync (the failing status update rolled the registrations back and logged an error); the re-lock makes it explicit and quiet.
