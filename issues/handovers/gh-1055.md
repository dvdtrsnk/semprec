**What changed:**
- **Migration `0079_tenant_deletions.sql`:** adds the tombstone table, classified `global`. `semprec_side` can only read it and `semprec_data` can only insert, as specified.
- **`tenantPurgeOrder.ts`:** `orderTablesForPurge` is a pure function that puts children before parents. A self-reference is accepted, and any other cycle throws naming the tables.
- **`tenantPurgeJob.ts`:** `handleTenantPurgeTask` takes a per-tenant advisory lock on a dedicated connection that is unlocked and released on every path. It then runs the steps in the specified order:
  1. Delete the tenant key.
  2. Remove the tenant's unlocked queued jobs.
  3. Delete blob and export bytes, then the tenant's directories under both roots.
  4. Drop the `items` partitions.
  5. Delete rows in chunks.
  6. Finalise: assert nothing remains, erase the user's identity rows, write the tombstone and delete the tenant.

  The task stops between chunks on `abortSignal`. One tenant's failure is collected and the others still run. The run rethrows an `AggregateError` at the end, and logs carry only tenant ids, step names and counts.
- **Wiring:** `tenantPurge` is a system task with `api` affinity and a `* * * * *` crontab entry. `createCoreTaskList` has the new trailing `tenantBlobStorageDirs` parameter. I updated the `queueRuntime`, `tenantEnvelope` and `leastPrivilegeRoles` tests as the issue lists.
- **ADR `2026-10-18-tenant-purge-erases-outside-the-choke-point.md`:** records the decisions the issue lists and cross-references the best-effort blob-deletion ADR as a carve-out.
- **Tests:** `tenantPurge.test.ts` covers every acceptance case with two tenants on a runtime-role pool. I added one extra case: a tenant that another run finished between listing and locking is skipped. `tenantPurgeOrder.unit.test.ts` covers the ordering function.

**Deviations from the issue and follow-ups:**
- **Blob keys:** the issue says to delete each key from its own root. I delete each key from both roots, because the existing cross-root ADR says deduplicated bytes can sit in either, and the delete is idempotent.
- **Partitioned tables:** `items` and any other partitioned table skip the `ctid` chunking, since a `ctid` is only unique within one partition. They get a plain `DELETE … WHERE tenant_id = $1`, which should affect nothing after the partitions are dropped. A non-zero count logs a warning instead of failing the tenant. A failure there would roll back its own delete and wedge the tenant forever.
- **Test title:** I changed "the 12 sweeps" to "13" in the `tenantEnvelope` catalog test title, because the old number would have been false.
- **Warning logs:** `seedTenant` calls a few store functions outside `runInTenant`. That produces `tenant_scope_missing` warnings in the test output but does not fail anything. `deleteAccount.test.ts` does the same.
