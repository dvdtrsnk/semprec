## What was delivered

- A per-process registry of the groups of global search, `search/searchGroupRegistry.ts`: item groups (`registerItemSearchGroup({ type, ownerModuleIds })`, an allow-list of databases by owner module) and thread groups (`registerThreadSearchGroup(group)` with `prepare` and `run`, the group searches threads on its own). Registering the same object again does nothing; registering a different one for the same type throws.
- `searchItemGroups` (`search/searchItemsQuery.ts`) reads the registry in the fixed order of `SEARCH_GROUP_TYPES`. The former `GROUP_MODULES` allow-list and the inline `chat` block are removed. Item groups run the existing code over the union of their `ownerModuleIds`; thread groups run after them, in the same repeatable-read transaction, through the run that their `prepare` returned. A requested type without a registration contributes nothing and raises no error.
- `sempThreadSearchGroup` (the `chat` group) is exported from `search/sempThreadSearch.ts`. `domainWriteHooks.ts` registers the seven item groups (task, event, project, area, contact, journal, file) with exactly their owner modules, and `chat`.
- New ADR `docs/adr/2026-11-13-search-groups-register-through-a-per-process-registry.md`.

## Entry points and contracts dependents build on

- `registerItemSearchGroup`, `registerThreadSearchGroup`, `getSearchGroup` and `clearSearchGroupsForTests` (refuses outside `NODE_ENV=test`) in `search/searchGroupRegistry.ts`. Nothing is added to the data barrel `index.ts`.
- The mail group of #1864 registers itself as a thread group with `registerThreadSearchGroup`; its entries then appear after the item groups and before `chat`, with its own total, limited by `perGroupLimit`. For a scope of exactly that group a cursor token is handed to its `prepare`, and the run receives the parsed cursor; a cursor with a scope of more than one group is refused as before. A cursor that the owning group refuses is a `ValidationError` for a person, an agent and a query without a searchable word, and nothing is searched.
- No route, operation, table, migration or job name is added.

## Deviations from the specification and spec seams

1. For a scope of exactly one type that has no registration (mail until #1864) a cursor is still checked in the item cursor shape, as before the change, since no group owns a token there; once a thread group registers, its `prepare` decides.
2. `prepare` is called for every requested registered thread group before anything is searched (with the token only for a scope of exactly that group, else `undefined`), so a refusal precedes the early return for a query without a searchable word.
3. Registration identity is object identity, per the Task ("the same object").
4. The comment on `SearchGroupType` in `shared/genericOperations/schemas.ts` that says mail is filled by a later issue was left alone: shared files are out of scope.
5. Observed by the rules reviewer, not a finding: an agent searching the scope `["chat"]` alone now opens the repeatable-read transaction and gets an empty chat page, where before it returned early with no transaction. The answer is identical.
