## What was delivered

- Module agent tool `inbox.proposal.revise` of the Inbox module (approval `none`, risk class `write`, no capability), next to the read tool `inbox.proposal.get`. Arguments (strict): `{ proposalId, ifVersion, entityKind?, target?, properties, message? }`. The thread, the acting user and the running assistant message are read from the persisted run, never from arguments.
- Any card that is not the calling run's own thread card (a card of the same tenant, another tenant's card or run, a chat-thread run, a run without a thread, a tenant without the Processing proposals database) is answered exactly as a missing card. NUL characters in `properties`, `target` or `message` and a message over 2000 characters are refused.
- The write goes through `reviseProposalWithClient`, which gained a sixth parameter `revisedBy` (default `user`, so the revise route is unchanged); the tool records `{ author: ai, kind: threadRevision, threadId, messageId, message }` in the card's history (default text "Revised by assistant." when no message). A locked card (confirmed or rejected) or an invalid envelope gives an error result and writes nothing. Nothing is created in a target database.
- The card's `inboxCards` invalidation is published after the commit (`runAfterCommit`); the answer is `{ proposalId, revised: true, version }`.
- The own-card proof reads the source edge `FOR SHARE` in the write's transaction after the card is locked; the order and its reasons are recorded in the new ADR `docs/adr/2026-11-13-an-item-thread-tool-proves-its-card-with-a-shared-lock-on-its-source-edge.md` (review finding, fixed). The manifest comment in `inboxModuleManifest.ts` that said there was no revise tool is corrected; i18n labels in `en.json` and `cs.json`.

## Deviations from the specification and spec seams

1. `index.ts` is at the 900-line ESLint cap, so its export line became `export * from "./inbox/inboxAgentTools.js"` (same line count); it exports exactly the names of that file.
2. The NUL check and the 2000-character cap moved to `reviseInputChecks.ts`, shared by the route and the tool.
3. After gh-1938 the tool calls `reviseProposalFromThreadWithClient`, so the `revisedBy` parameter of `reviseProposalWithClient`, required by this Task, has tests but no production caller.
4. Item threads still compose no module tools (`agentSessionComposition.ts` offers read-only generic operations), so the tool is registered, classified and invokable through the registry but not yet offered to an item thread's model. That wiring is the thread's tool set and is outside gh-1906 and gh-1938.
5. The tool writes with the choke point's default writer, as the route does, not an agent writer.
6. "Revised by assistant." is the default history text; the Task specifies none.
7. The thread-step mapping of the reply is not added, as the Task says.
8. The reset entry that records dropped manual values keeps author `user`.
9. The required argument `ifVersion` and the `version` in the answer extend the argument list the Task names. They were added in the fix round for a review finding on gh-1938 (a revision composed from a stale snapshot overwrote a manual edit); the Task's own list is `{ proposalId, entityKind?, target?, properties, message? }`.
