# Handover: show account calendars in the iOS calendar

Implementation commits `0c0b09561` (code) and `b8c6c2dc0` (mobile architecture doc) on `feat/internet-accounts`.

**What changed.**
- `:shared:domain`:
  - `CalendarKind.ACCOUNT`.
  - `CalendarInfo` gains `accountId`, `readOnly`, `remoteName`, `remoteColor`, `usesRemoteColor` (all defaulted) and the computed `takesNewEvents` (OWN, or ACCOUNT and not read-only).
  - `CalendarEdit.useRemoteColor`.
  - `EditCalendars` lets OWN and ACCOUNT calendars be renamed, lets only ACCOUNT calendars go back to the provider colour, and still deletes only own non-default calendars.
  - New `SyncAccountCalendars(InternetAccountRepository, TimeSource, interval = 60 s)`. It reads the accounts and posts `syncCalendars` for each one with `calendarsEnabled`, at most once per interval. The answers are ignored (404 included). When the accounts read fails, the next call goes through at once.
- `:shared:data`:
  - `CalendarStoredItem.relations` holds the expanded relations, by key, as `{id}` targets.
  - `HttpCalendarCatalogRepository.calendars()` queries with `{"include":{"relations":{"account":[]}}}` (`CalendarDatabases.items(key, query)`).
  - `toCalendar()` reads kind `account`. For an account calendar, a null name falls back to `remoteName` and a null colour to `remoteColor`, then to `#8E8E93`. An account calendar with no name at all is skipped. Other kinds keep the old rule (no name or colour means skipped) and never carry the remote fields.
  - `edit(useRemoteColor = true)` patches `color: null`.
  - The timeline window (`HttpCalendarRepository`) uses the same mapping, so account events get the provider colour. Its query does not expand the relation (no `accountId` there).
- `:shared:presentation`:
  - `CalendarGroup.ACCOUNT`.
  - `CalendarRow` gains `accountId` (empty when the server named no account, `null` outside the group), `readOnly`, `remoteName`, `remoteColor` and `usesRemoteColor`. `canRename` is true for account calendars and `canDelete` false.
  - `CalendarListState.accounts: List<CalendarAccountSection(id, name?, provider?, status: InternetServiceStatus?)>`: the accounts in the order the server lists them, then any unknown ids. The accounts are read only when an account calendar exists. If that read fails, the sections have no name, provider or status, and the list still shows.
  - New actions `CalendarListAction.Refresh` (pull to refresh) and `Change.UseRemoteColor`.
  - `CalendarViewModel` asks `SyncAccountCalendars` when it starts and on each `Navigation.Refresh`. That action is sent when the scene becomes active and when the screen reappears. Server `CALENDAR`/`INVITATIONS` changes only reload, so a sync cannot trigger the next one.
  - `CalendarViewModelFactory` takes an `InternetAccountRepository` (new required 5th parameter) and shares one `SyncAccountCalendars` across its ViewModels.
  - `NewCalendarItemViewModel` offers `takesNewEvents` calendars, so read-only ones are left out.
  - `requestAccountSync` (`AccountCalendarSync.kt`) launches the request without waiting.
- `:shared:umbrella`: `CalendarSDK` passes `HttpMailboxRepository(api)`.
- Apple CoreKit:
  - The calendars-list models moved to `Models/CalendarListScreenModel.swift`, and their bridge values to `Shared/SharedCalendarListValues.swift` (file-length limit).
  - `CalendarListAction` is now `.retry`, `.refresh`, `.change(CalendarListChange)`, … . `CalendarListChange` holds `toggleHidden`, `rename`, `setColor`, `setNotify` and `useRemoteColor`, mirroring Kotlin's `Change`. This keeps the mapping under SwiftLint's complexity limit.
  - `CalendarAccountSection` and the new row fields are mapped.
- DesignSystem: `InternetAccountProviderBadge` moved here from the Account feature (now public) so the Calendar feature can show the same badge.
- Calendar feature:
  - `CalendarListScreen` shows one section per account between My Calendars and From Semprec. The header is a `CalendarAccountHeader` with the badge, the account name (or "Internet account") and its calendar status, in red when it needs attention.
  - The list has `.refreshable { send(.refresh) }`.
  - `CalendarListRow` shows a lock (`lock.fill`, labelled "Read only") on read-only calendars.
  - `CalendarDetailPage`:
    - an account calendar gets the rename field, plus a footer with the provider's name once it is renamed;
    - a "Provider's color" row, checked while the colour is the provider's; choosing it sends `useRemoteColor`;
    - account-specific hints, one for read-only calendars;
    - no delete button.
  - New copy: 13 `calendars.*` keys in `Sheets.xcstrings` (en + cs), listed under the CalendarFeature `appleOnly` copy of the policy. New identifiers: `calendars.account.<id>`, `calendars.readOnly.<id>`, `calendars.color.remote`.
- `mobile/docs/architecture.md` (Live updates) describes the sync request.

**Contracts dependents build on.**
- `SyncAccountCalendars` is the one client-side sync trigger. Android can reuse it through the same factory.
- `CalendarAccountSection` / `CalendarRow.accountId` is the grouping key.
- `CalendarEdit.useRemoteColor` writes `color: null`.

**Deviations and seams.**
- Pull to refresh is on the calendars sheet, the only `List` of the calendar. The day, month and year views are custom pagers with no pull gesture. On macOS `.refreshable` gives no gesture, so there the sync is asked when the calendar opens or the app becomes active.
- The 60 s client pause is one per `CalendarSDK` (per window) for all accounts, not one per account.
- The sync request ignores every answer, as the server's account status carries failures. A 409 `calendars_disabled` cannot normally happen, because only accounts with Calendars on are asked.
- A user cannot set an account calendar's name back to the provider's: the generic title rule refuses a null or blank name from users (backend handover). Only the colour has a "provider's" choice, and the detail page shows the provider's name when it differs.
- `InternetAccountProviderBadge` moved out of the Account feature (not in Touches) so both features share it.
- The Swift `CalendarListAction` per-calendar cases are nested under `.change(...)`, which touched the existing call sites.
