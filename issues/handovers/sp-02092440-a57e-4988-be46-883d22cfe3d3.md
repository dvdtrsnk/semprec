# Handover: run every integration test file under strict tenant scope unless it is on a shrink-only list

Delivered on chain `e1-247-test-infra` (one member), candidate commit `df6a699ba8ee9e73ae802322f51603f46383b33c`, landed by a `--no-ff` merge (`35d705a50a1c7f9a7fb92ab3654e9879662bfb97`) on `feature/backend-parallel`. The segment commit of this source is `42428ed1f1965a6c53918bfedeecb24d6ce4ffb0`; the review fixes are `b703c4b9d8fef79cb0fcdf464b96df40aea293c8` (two stale comments) and `df6a699ba8ee9e73ae802322f51603f46383b33c` (pin of the set of frozen scope-mode suites).

**What changed.**
1. New setup file `backend/packages/data/src/testSupport/tenantScopeMode.ts`, registered in `setupFiles` of `backend/vitest.integration.config.ts`. Before the first test of each integration file it sets `process.env.ALLDOTS_TENANT_SCOPE` to `warn` when the running file (from `expect.getState().testPath`) is on `tenantScopeWarnFiles.json` and to `strict` otherwise. An explicit value in the environment of the vitest process is kept for every file; a file whose path cannot be determined fails.
2. `tenantScopeWarnFiles.json` (sorted, 895 entries: every integration test file that existed at the tip, the first variant of Task step 1; the full tier was not run under strict to measure failures) and `tenantScopeWarnFiles.frozen.json`, a byte copy that is never edited again.
3. `globalSetup.ts` no longer defaults `ALLDOTS_TENANT_SCOPE` to `warn`; `backend/vitest.e2e.config.ts` pins `ALLDOTS_TENANT_SCOPE: process.env.ALLDOTS_TENANT_SCOPE ?? "warn"` in `test.env`, so the e2e tier keeps `warn`.
4. Tests: `tenantScopeWarnFiles.unit.test.ts` (sorted, unique, existing, integration-only, not the source's own test files, subset of the frozen list whose SHA-256 is pinned, the set of frozen scope-mode suites pinned against additions by a literal and a pinned hash, e2e config keeps `warn`), `tenantScopeMode.unit.test.ts` (selection, override, undeterminable path, list parsing) and `tenantScopeModeDefault.test.ts` (an integration file not on the list: mode is `strict`, an unscoped query through `createPool` rejects with `TenantScopeMissingError`, the same query runs inside an explicit system scope; skipped with a reason under an explicit override).
5. ADR `docs/adr/2026-11-15-integration-tests-run-strict-unless-listed.md` (extends `2026-10-05-tenant-scope-propagation` without editing it). Comment-only edits in `tenantScopePool.test.ts`, `queueRuntimeStrictScope.test.ts` and `nativeEntrypoints.e2e.test.ts`, whose comments said that `globalSetup` sets `warn`.

**Contracts dependents build on.** A new integration test file runs under `strict`. A file runs under `warn` only when it is on `tenantScopeWarnFiles.json` or is one of the eight frozen scope-mode suites that switch the mode themselves. Each later conversion source removes the files it converts from the list; the list may only shrink, because every entry must be in the frozen copy (pinned hash). `vitest.integration.config.ts` also provides `explicitTenantScopeMode` through `test.provide` so the probe can tell a developer override from a default. No route, table, operation, migration file, export of `@alldots/data` or job name changed; no production code changed.

**Files.** `backend/vitest.integration.config.ts`, `backend/vitest.e2e.config.ts`, `backend/packages/data/src/testSupport/{globalSetup.ts,tenantScopeMode.ts,tenantScopeWarnFiles.json,tenantScopeWarnFiles.frozen.json}`, `backend/packages/data/src/testSupport/__tests__/{tenantScopeMode.unit.test.ts,tenantScopeModeDefault.test.ts,tenantScopeWarnFiles.unit.test.ts}`, the three comment-only test edits above, and the ADR.

**Tests.** The queue runner ran the unit tier (245 files, 4878 tests, plus 4 files and 172 tests of block-model), the e2e tier (10 files, 67 tests), the three integration files the chain added or changed (`tenantScopePool.test.ts`, `tenantScopeModeDefault.test.ts`, `queueRuntimeStrictScope.test.ts`: 15 tests) and an extra sample of ten integration files that are on the list (352 tests, all PASS under the new setup file).

**Deviations and spec seams.** (1) First variant of Task step 1: the list holds all 895 existing integration files, not the measured strict failures; nothing states how many of them really need `warn`. (2) A third new test file, `tenantScopeMode.unit.test.ts`, covers the branches of the setup file. (3) `test.provide { explicitTenantScopeMode }` in the integration config goes beyond `setupFiles`, because the process.env of a worker cannot tell a developer override from the default. (4) The eight frozen scope-mode suites are the measured set of integration files that mention both `ALLDOTS_TENANT_SCOPE` and `"warn"`; some only name the string for another reason.

NOT RUN: the whole integration tier (neither on strict nor on the new default; the queue runner ran the changed files and a ten-file sample of listed files), and the worker's fail-before mutation checks on the unfixed code and on each list mutation were not repeated by the queue runner.

**Review.** Requirements lens: one medium finding (the set of frozen scope-mode suites could be extended without a failing test) and one low finding (stale comments). Rules lens: one low finding (the same stale comments). All were confirmed and fixed (`df6a699ba`, `b703c4b9d`); the focused recheck of `df6a699ba` passed with no unresolved or new findings.
