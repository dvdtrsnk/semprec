## Summary

Implements issue #173: extends `backend/dependency-cruiser.rules.json` with the full nine-rule static dependency-boundary matrix between `packages/`, `modules/`, and `services/`:

- `no-module-to-module` (kept)
- `no-service-to-service`, `no-service-to-module`, `no-module-to-service` — the five processes talk only through Postgres, never by importing each other or crossing the service boundary
- `core-knows-nobody` — core packages import no module or service code
- `pi-only-in-agent-runtime` — `pi-agent-core` may only be imported inside `packages/agent-runtime`
- `agent-runtime-only-in-agents` — `packages/agent-runtime` may only be imported by `services/semprec-agents`; the API never runs the agent loop
- `no-deep-imports` — packages are reachable only through their entry points
- `items-store-private` — the item store is only visible inside `packages/data` (CI half of choke-point control; runtime half is #243)

Each rule has a failing fixture proving it fires and a passing fixture proving documented valid imports still work, built against a synthetic node_modules-backed mini-repo scanned in isolation via `checkModuleBoundaries`'s `baseDir`. The real full-repo `.dependency-cruiser.cjs` scan excludes that fixtures directory (its nested path would otherwise trip the new anchored rules), and `.gitignore` was given a targeted negation so the fixture's stub `@earendil-works/pi-agent-core` package stays tracked despite the repo-wide `node_modules/` ignore. `packages/agent-runtime/README.md`'s "Enforced boundaries" section was updated to drop a stale reference to the removed combined rule and document the two rules specific to that package.
