## What was delivered

- Two link rules in `linkRules` of the `systemDatabases` manifest (`backend/packages/data/src/seed/systemDatabasesModuleManifest.ts`), after `transcriptCompanyFromProject`:
  - `taskProjectFromEvent`: `Events.project` to `Tasks.project`, via `Tasks.sourceEvents`;
  - `taskPeopleFromEvent`: `Events.people` to `Tasks.people`, via `Tasks.sourceEvents`, with the value filter that omits System settings `selfPerson` (the tenant's own person).
- The ownership handoff of `Tasks.project` and `Tasks.people` to the `valueLinks` process, declared the way gh-1697 declared it for the transcript relations: a comment next to the rules and the ADR `docs/adr/2026-11-11-action-item-tasks-inherit-project-and-people-by-link-rules.md` (accepted). Both relations stay `owner: user`; the `valueLinks` process writes them as a system writer only while the value link of that item and property is `on`.
- From the fix round, an edge-changed hook `taskSourceEventLinkDetachEdgeChangedHook` (`backend/packages/data/src/tasks/taskSourceEventLinkDetach.ts`), registered in `backend/packages/data/src/domainWriteHooks.ts`. On the delete of a Tasks `sourceEvents` edge, written from the task or from `Events.actionItems` and by any writer, it removes that Event from the sources of the task's `project` and `people` value links whatever their state, deletes a link left without a source, and announces a live task after the commit. The link engine alone releases only a link that is `on` and only for a task that is not in the Trash.
- No route, migration, table, column, generic operation, job name, tenant cutover entry, export from the data barrel, stored key or i18n key was added. The link engine, the value-link store, the item create with relations and the choke point are unchanged.

## Contracts dependents build on

- A task that gets a `sourceEvents` edge to an Event, by the generic item create with `relations: [{ propertyKey: "sourceEvents", targetItemIds: [event] }]`, by the relation endpoint on `Tasks.sourceEvents` or on `Events.actionItems`, or by the confirm of an Inbox card whose task names a source Event, takes the Event's project and its participants without the own person into the properties that are empty, in the transaction that writes the edge. Each inherited property has a value link with state `on`, the rule key above and the Event as its source.
- Validating an action-item proposal (the Inbox tick, a revision) writes no edge and so no value.
- A property that already holds a value when the edge is written keeps it as the task's own value and gets no link.
- **The item create writes its relations in the order the request lists them.** `project` or `people` listed before `sourceEvents` are own values. A `project` listed after `sourceEvents` is refused with `409 cardinality_violation` and nothing is written when the Event has a project; when the Event has none, the listed project is written and ends the link just created (state `broken`, the Event still named as source). The ADR records this; the worker and the rules reviewer left it for the owner to confirm.
- A request repeated with the same `Idempotency-Key` returns the committed task and writes no edge.
- A change of the Event's project or participants reaches the tasks that still follow it through the existing `valueLinksPropagate` job. A write of an Events `project` or `people` edge now queues one such job for each rule that reads the property: the transcript rule and the task rule.
- A user or agent write that changes the task's project or people ends that link; for the project this includes a write from `Projects.tasks`, the inverse side.
- When the `sourceEvents` edge is removed, no link of the task names that Event any more. A link left without a source is deleted, the value stays as the task's own, and a relink of that property answers `409 value_link_conflict`. A link that another source Event still feeds keeps that Event and its state.
- A task with several source Events has the union of their participants; while those Events name different projects, the engine leaves the task's project as it is.
- **For tests and fixtures of later sources:** every write of an `Events.actionItems` or `Tasks.sourceEvents` edge now creates value links on the task and copies into empty `Tasks.project` and `Tasks.people`. A fixture link rule from `tasks.project` to `events.project` closes a cycle with `taskProjectFromEvent` and fails `validateLinkRules`; a fixture rule that targets `tasks.project` or `tasks.people` over the action-item edge collides with the production rules.
- Order in `domainWriteHooks.ts`: the entry of this source stands after `linkRuleEdgeHook` (the hook relies on the engine having handled the `on` links first; a test pins it) and after the transcript link release hooks of gh-1697, and before the entries of gh-1710, gh-1714, gh-1718 and gh-1723. A source that names gh-1724 as an ordering blocker puts its entries after it. gh-1754 named it and landed earlier; it has no entry in `domainWriteHooks.ts` or `db/tenantCutoverMigrations.ts`.
- The hook is exported from its module only, not from `backend/packages/data/src/index.ts`.
- Nothing is backfilled: a task whose `sourceEvents` edge was written before the rules existed has no value link and takes over nothing. In a tenant whose Tasks database has no `sourceEvents` relation both rules are unresolved and copy nothing.
- The company is not a task value. The derived read gives a task its area through its project and derives a company only for an Event.
- gh-1767 (a task from a transcript action item) and gh-1702 (an attachment's project from the task) build on these rules.
