## What was delivered

- `backend/packages/data/src/tasks/taskHostEventState.ts`: the pure `computeTaskHostState({ date, hostEvents, timezone, now })` and `recomputeTaskHostState(client, taskId)`. The recomputation locks the task row, reads the live host events (edge `addedAt` order, trashed Events ignored), and writes only the values that differ (`hiddenUntil`, `effectiveDate`, and `since` / `sinceTime` when the first planned day rule fires) through `updateItemWithClient` as the Tasks process. It is a no-op for a missing or trashed task and for a tenant without the `hostEvents` relation.
- Rule: while any live dated host event has not ended, `hiddenUntil` is the latest end in the tenant zone and `effectiveDate` is the day of the event added last; once every event has ended `hiddenUntil` is null and `effectiveDate` is the later of the task's `date` and the day of the event added last; with no host events `effectiveDate` equals `date`.
- Three triggers, all in the writing transaction: (1) `taskHostEventEdgeChangedHook` on edges of `Tasks.hostEvents`; (2) `taskHostEventScheduleItemUpdateHook` on an Events update naming `date`, `endDate`, `timeFrom`, `timeTo` or `time` (`taskHostEventHooks.ts`), registered in `domainWriteHooks.ts`; (3) the Tasks pre-write transform (`taskPreWriteTransform.ts`) stores `effectiveDate` on create and on a write naming `date`.
- Migration: `backfillTaskEffectiveDate` (`tasks/backfillTaskEffectiveDate.ts`, re-exported from `systemDatabasesModuleManifest.ts`) and a `dataMigrations` entry tasks `1.2.0` to `1.3.0`. It sets `effectiveDate = date` on every dated task whose value differs and changes nothing on a second run. It reads no Event.
- `taskSinceRule.ts`: the second half of `taskSinceRule` is extracted unchanged as the exported `firstPlannedDay(stored, today)`, which the recomputation reuses.
- ADR `docs/adr/2026-11-12-task-host-state-is-recomputed-in-the-writing-transaction.md` (accepted): stored derived state recomputed by three triggers, Events read without a lock.

## Deviations from the specification and spec seams

1. The systemDatabases manifest version is already 1.5.0, above the 1.3.0 the Task says to raise it to; it is not lowered, and the `dataMigrations` entry 1.2.0 to 1.3.0 is added (same precedent as the 1.1.0 to 1.2.0 entry of gh-1657).
2. `taskSinceRule(stored, patch, today)` of gh-1602 requires a patch naming a different date, which a host-state recomputation does not have; its second half is extracted unchanged as `firstPlannedDay`.
3. `backfillTaskEffectiveDate` treats an empty-string date like no date.
4. Existing tests were brought in line with the new stored values: `tasksDayRollover.test.ts`, `taskHostEventRoutes.test.ts`, `taskHostEventOccurrenceRoutes.test.ts` (a place or remove now also writes and announces the task's host state), `normalizeTaskDatesAndTimes.test.ts` (registered migration list).
5. The transform reads the host events through the context client only for a write that names `date`; a create reads none because its edges come after it.
6. The worker's commit trailer used the system attribution (Claude Sonnet 5.5) instead of the Fable line named in the worker prompt.
7. Known limitation recorded in the ADR: the recomputation reads Events without locking them (lock order against the #1764 routes), so a concurrent uncommitted Event update or edge can leave the state stale until the next trigger. The backfill reads no Event, so a task that already sits in an Event keeps `effectiveDate = date` until its next trigger.
