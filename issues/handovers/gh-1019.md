Operator alerts now go to every admin of an active tenant, and mailbox stalls go to the tenant's own user. The three integration test files I touched pass (28 tests). The build, eslint and prettier are clean on the data package. I did not run the full `pnpm run verify`, so Relay's verify step is the first full run. It's committed as `10be4c4a`.

- **Recipients:** `listAdminRecipients` in `usersStore.ts` returns admins of `active` tenants, ordered by creation.
- **Operator writer:** the new `observability/operatorAlerts.ts` has `writeOperatorAlert(pool, client, input)`, which is not re-exported from `index.ts`. It writes one row per admin in that admin's tenant, with `transitionInstance` suffixed by the admin's user id.
  - A failed admin write is logged with `{ err, tenantId }`, and the others still get theirs.
  - After the loop, any failure is rethrown as an `AggregateError`, so the caller's transition rolls back and the job retries.
- **Check system:** `process_stale` and both `queue_backlog` call sites use `writeOperatorAlert`. Both mailbox-stall producers use `getTenantUserId` inside the tenant transaction and skip when it returns null. `getEarliestUserId` is gone from the file.
- **Restore result:** a failed run uses `writeOperatorAlert` with `kind: "backup_restore_failed"`. The outcome is now `{ notificationIds: string[] }`. The CLI runs under `runAsSystem("restore-test-result", …)` and prints the new "no admin exists to notify" message on an empty result.
- **Public surface:** `listAdminRecipients` is added to the runtime-export list in `publicSurface.test.ts`.
- **Tests:** both test files now use tenant zero's admin as their account fixture, and a new multi-tenant block covers the acceptance criteria. A `BEFORE INSERT` trigger on `notifications` injects the failure for one admin.

**Retry caveat:** the per-admin dedupe key includes the check's row id as `source_id`. If a transition is the first ever for a check, the rollback also removes the check row. The retry then inserts it with a new id, so an admin whose row was already committed gets a second one. This only affects the first-ever transition of a check; normally the row already exists as `ok`. The failure-and-retry test runs one healthy tick first so the row exists. A fix would need a stable check id, which is outside this issue's scope.
