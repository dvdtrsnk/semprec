# Handover for gh-1644

Link a transcript to its upload's event in the create step. Candidate commit `1e78482c3b4e7279f3b0cd1bce4da4740a8c4bed` (one segment, one commit) landed on `feature/backend-parallel` with merge `7d23c2e9a9e79bc8dd408d90668748d2aa5314f7` (chain `p0-06-semprec-transcribe`). The acceptance receipt is `issues/batches/backend/acceptance/sources/gh-1644.md`.

## What was delivered

- Step 0 of the transcription pipeline (`runCreateStep` in `backend/services/semprec-transcribe/src/transcriptionTask.ts`) writes the Transcripts `event` edge when the upload's `recording_requests` row names an Event (`readRecordingRequest(...).eventId`). The write runs in the create transaction, after the requested-project edge and before `ensureItemAutomation` and the `create` checkpoint, so the Transcripts row, the edge, the automation row and the checkpoint commit together or not at all.
- The write itself is `linkTranscriptToUploadEvent` in the new module `backend/services/semprec-transcribe/src/uploadEventLink.ts`. It resolves the tenant's Events database (`getDatabaseByModuleId(client, EVENTS_MODULE_ID)`) and the `event` property of the Transcripts database, reads the Event with `lockItemById` (`SELECT ... FOR UPDATE`, filtered by the Events database id), and writes the edge with `createRelationWithClient`.
- No edge is written, and no error is raised, when the Event is not a row of that database (purged, unknown id, another tenant's id) or is in the Trash. The transcript is then left to the match step like a recording uploaded without an Event.
- A missing Events database throws `Events database not found`; a missing Transcripts `event` property throws `Transcript event relation not found`. Both roll the create transaction back, so no transcript, no edge and no checkpoint is left.
- A second run of step 0 returns at the `create` checkpoint before any write. Both entry points of step 0 (the fast create task and the pipeline task's own step 0) go through the same `runCreateStep`.
- New ADR `docs/adr/2026-11-10-transcription-create-writes-the-uploads-event.md`: the worker may write the Transcripts `event` edge in the create step, only from `recording_requests.event_item_id` of the transcript's source file. It is a standalone addendum to `2026-09-23-transcription-worker-writes-event-match-results`; no accepted ADR was edited.
- `backend/services/semprec-transcribe/src/serve.ts` is unchanged. The relation-edge hooks are registered by the `@semprec/data` barrel (`domainWriteHooks.ts`) in every process that loads it, and a new test shows they run for this edge.

## Contracts dependents build on

- A transcript whose upload named a live Event has its `event` edge from step 0, while its status is still `processing` and before any media step. The match step then returns `alreadyLinked`: it creates no pairing card and never replaces the edge. Speaker suggestion reads the participants of that Event.
- The upload's choice is not checked against the match's time window. An Event can therefore hold a transcript whose recording does not overlap it in time.
- Order in the create transaction: requested project edge first, then the Event edge. The rules of gh-1697 that fill only an empty transcript value from the Event will find the explicit project already in place.
- Row locks of step 0, in order: source Files item, transcript, requested project, requested Event. All are held until the create transaction ends. The ADR claims no global deadlock freedom for that order.
- While step 0 holds the Event's row lock, an upload naming the same Event is answered `409 recording_busy` by the intake's `NOWAIT` reservation, and is accepted afterwards. A concurrent trash of the Event waits for the commit and then goes through with the edge in place.
- The relation-edge hooks of the worker process run for this edge inside the create transaction. A hook that rejects rolls the whole create step back, the Transcripts row included, and the queue retries the job within its attempts. The inheritance rules of gh-1697 attach through that registry; they do not exist yet.
- Export: `linkTranscriptToUploadEvent(client: PoolClient, transcript: Pick<ItemRow, "id" | "databaseId">, eventId: string): Promise<void>` from `backend/services/semprec-transcribe/src/uploadEventLink.ts`. It is internal to the service; its only caller is `runCreateStep`.
- The edge is written with the default system writer and without an owner-process context, exactly as the match step writes it. The Transcripts `event` relation is not system-owned.
- No route, no table, no SQL migration, no generic operation, no job name and no stored key was added or changed. The job keys `transcription-create:<fileItemId>` and `transcription-job:<fileItemId>` are the existing ones.
- `transcriptionTask.ts` is close to the cap of the backend ESLint `max-lines` rule: by the rules reviewer's count 891 of the 900 counted lines, 889 before this source. A later source that adds code to it will hit the cap; this is why the edge write lives in a sibling module.

## Deviations from the specification and spec seams

1. The Task places the edge write in `runCreateStep` of `transcriptionTask.ts`. That file was at 889 of the 900 counted lines of the ESLint `max-lines` rule and the inline block failed the rule (906). The write lives in the sibling module `uploadEventLink.ts`, and `runCreateStep` calls it in its transaction with one line.
2. `serve.ts` is not changed. `Touches` says "only if not already active", and the hooks are registered by the `@semprec/data` barrel in every process. The hooks test proves it through the job `item-search-reindex:item:<eventId>`, which only the registered `itemSearchEdgeChangedHook` produces.
3. No test was added under `backend/packages/data/src/__tests__/`. No data-layer code changed, and the create step cannot be imported from `packages/data`. All create-step tests are in `transcriptionTask.test.ts`.
4. Test seam: the upload in the tests is the recordings route's data composition (`ingestUploadedFileWithTransaction` with `recordRecordingIntake` and the Event id in one transaction), not an HTTP request that carries `X-Event-Id`. Header parsing and the stored Event id belong to gh-1574 and are covered by `recordingsHandler.test.ts`.
5. Test seam: another tenant's Event id and a random id are planted in the request row by a commented raw UPDATE, because `recordRecordingIntake` refuses such an id. A missing Events database and a missing `event` property are produced by a commented raw UPDATE of the catalog, a state the normal APIs cannot produce.
6. Tests beyond the ones the Task lists were added: the two tenant-isolation cases, the two concurrency tests for the row lock, the hooks test and the two catalog-failure cases.
7. The Task says "amend the ADR". The accepted ADR is not edited; the amendment is a new ADR file that refers to it, as `docs/adr/README.md` and the `adr-conventions` skill require.
8. The Event in the first acceptance test is date-only, so the match step could not have linked it by time. The edge the test sees is step 0's own.
