# Handover for gh-1712

Backfill meeting notes for older transcripts. Candidate commit `0112be7e4ce01a1d47021d848293cfb925b1e89b` landed on `feature/backend-parallel` with merge `c2be0b0b1eced177f7541423cfba417d38ebc6d0` (chain `e1-013-transcription`, its only member). The source is three commits: the implementation `2475ce48`, and two commits of the fix round, `76a60a46` and `0112be7e`. The acceptance receipt is `issues/batches/backend/acceptance/sources/gh-1712.md`.

Both declared blockers are completed on the tip: gh-1695 (the pipeline stores `computed.meetingNotes`) and gh-1707, which the record names for shared-file ordering. No blocker was open at this landing.

## What was delivered

- The per-tenant cutover `runMeetingNotesBackfillCutoverMigration(pool)` in `backend/packages/data/src/transcription/meetingNotesBackfillCutoverMigration.ts`, registered in `runTenantCutoverMigrations`. For the current tenant, in one transaction, it selects in id order at most 200 transcripts (`MEETING_NOTES_BACKFILL_BATCH_SIZE`) and calls the existing `enqueueTranscriptionJob(client, { fileItemId })` for each, with the Files item id read from the transcript's `link` through `readTranscriptionSourceFileItemId`. The jobs are the only thing it writes. A tenant without a Transcripts database is skipped.
- The selection. A transcript is selected when all of this holds: it is in the tenant's Transcripts database and not in the Trash; `properties.status` is `done`; `computed` has `segments` and has no `meetingNotes`; it has an `item_automation` row whose status is not `error`, `locked` or `pending`; and, when its `link` starts like a Files item link, that link is the link of an item of the tenant's Files system database that is not in the Trash (fix round, `0112be7e`). A selected transcript whose `link` is not a Files item link is skipped with a warning that logs only the transcript id; it still takes one place of the batch.
- The failure recording. In `recordTranscriptionFailure` (`backend/services/semprec-transcribe/src/transcriptionTask.ts`) a permanent failure of a run of a transcript whose `status` is already `done` is written to `item_automation` only (status `error` with the message and the code, the attempt counted). The transcript's `status` stays `done` and no `automation_error` notification is written. The function comment says so. A transcript that is not yet `done` gets `status = error` and one notification as before.
- Fix round, `76a60a46`: the match step (`runMatchStep`, step 6) and the speaker suggestion step (`runSuggestSpeakersStep`, step 7) do nothing for a transcript whose `status` is `done`. No Event is linked, no pairing card and no speaker card is created, no `transcript_speaker_suggestion` call is made and no `suggestSpeakers` checkpoint is written. The status is read from the transcript row the step's transaction locked: in the match transaction before the match, in step 7 before the gateway call, and again in the transaction that would write the cards and the checkpoint. `requireTranscriptionUnlocked` now returns the transcript row it locked.
- The ADR `docs/adr/2026-11-10-finished-transcripts-are-not-matched-or-suggested-again.md` (accepted, area backend) records that decision and the two alternatives it rejects.

## Contracts dependents build on

- `runMeetingNotesBackfillCutoverMigration` and `MEETING_NOTES_BACKFILL_BATCH_SIZE` (200) are exported from their module only. Nothing was added to the data barrel `backend/packages/data/src/index.ts`.
- The job is the existing transcription job: task `CORE_TASK_NAMES.TRANSCRIPTION_JOB`, key `transcription-job:<fileItemId>`, queue `transcription:<tenantId>`, `maxAttempts` 3, payload `{ fileItemId }`. No job name, no payload field and no mark for a backfill job was added. A repeated enqueue collapses on the key, so the cutover, the daily requeue sweep, `POST /api/transcriptions` and `POST /api/transcriptions/:id/rerun` still share one runnable job per file.
- Registry order in `backend/packages/data/src/db/tenantCutoverMigrations.ts`: `runMeetingNotesBackfillCutoverMigration` stands directly after `runRecipesModuleCutoverMigration` (gh-1707) and directly before `runAreaNoteCutoverMigration`, which stays last. It needs no other step's result.
- Order for gh-1779, which names gh-1712 as a `Shared-file ordering` blocker: its cutover entry goes after the entry of this source and before `runAreaNoteCutoverMigration`, unless its Task names another position.
- A finished transcript is never matched or asked about again, by any run of its job, whoever enqueued it. This also holds for a manual rerun through `POST /api/transcriptions/:id/rerun`: a rerun of a transcript whose `status` is `done` stores only what the summarize step is still missing. A transcript in any other status (a first run, a retry, a resumed run, the requeue or rerun of a transcript whose `status` is `error`) is matched and asked about as before. This narrows "a later run can still ask" of `docs/adr/2026-09-23-speaker-mappings-are-edges-proposed-on-transcript-cards.md`; that record is not edited.
- A finished transcript can now have `item_automation` in `pending` (while its re-run is queued or running) or in `error` (after a re-run failed permanently or was refused by the gateway budget) while its `status` property is `done`. The transcript list and detail report `automation.status` from that row. An `error` row of a live transcript is picked up by the daily requeue sweep, which this source does not change.
- A source file that is in the Trash, was purged or is not an item of the tenant's Files database keeps its transcript out of the selection, so such a transcript takes no place of the batch and keeps its settled `item_automation`. A source file moved to the Trash after the selection still stops its job with `error`/`deleted`, as `docs/adr/2026-11-01-transcription-stop-guards-lock-items-before-automation.md` prescribes.
- The selection takes no row lock. The job checks the user's lock, the Trash and each step's checkpoint when it runs.
- Side effects later sources and tests meet:
  - every run of `runTenantCutoverMigrations` now enqueues a transcription job for each selected transcript of each maintained tenant, so a test that leaves a `done` transcript with segments and without `meetingNotes` and then runs the cutover runner finds a job in `graphile_worker.jobs`;
  - the runner iterates the maintained tenants, suspended ones included (see the follow-ups);
  - a test that runs the transcription job twice on a finished transcript now stops at the status guard in steps 6 and 7 on the second run.
- No SQL migration, no table, no route, no generic operation, no MCP tool, no job name, no stored key and no barrel export was added. One ADR was added.

## Deviations from the specification and spec seams

1. Scope beyond `Touches`. `Touches` limits the change in `transcriptionTask.ts` to `recordTranscriptionFailure`. Task step 3 requires that a re-run of a `done` transcript creates no new speaker or Event card. Both first-round reviewers showed that this does not hold for a transcript finished by an earlier pipeline without the `suggestSpeakers` checkpoint, or for one whose Event edge the user removed. The fix round therefore changed `runMatchStep`, `runSuggestSpeakersStep` and `requireTranscriptionUnlocked`. The change applies to every run of the job, a manual rerun included. The recheck passed it and names it for the owner. No decision record `issues/decisions/gh-1712.md` exists.
2. An ADR was added in the fix round, as the rules reviewer asked. The worker's first report had none.
3. The selection requires an `item_automation` row (inner join), so a transcript without a row is not selected. The issue says "whose `item_automation` is not `error`, `locked` or `pending`"; the existing rerun route treats a transcript without a row as not a pipeline transcription.
4. The selection leaves out a transcript in the Trash, which the issue's predicate does not name. The requeue sweep skips those too.
5. The selection leaves out a transcript whose source file is in the Trash, purged or not a Files item (fix round), which the issue's predicate does not name. A link that starts with the Files item prefix but names no live Files item is left out without a log line.
6. The batch is one transaction of at most 200 transcripts per tenant per run. A transcript skipped for its link still takes a place of the batch on every run. Whether a tenant can hold enough such transcripts to fill a batch was not examined at landing.
7. Registry position: the Task says only "register it". The entry stands after the entry of gh-1707 and before the area-note cutover.
8. The pipeline tests are a describe inside "retries and permanent failures (issue #248)" of `transcriptionTask.test.ts`, to reuse its helpers.
9. The state "finished without notes" is produced in the tests by removing the key with SQL, because no production write produces it since gh-1695. The state "finished without the checkpoint and the speaker cards" is produced by purging the cards through the Trash and removing the checkpoint with SQL.

## Review

Two reviewers read `2475ce48^..2475ce48` read-only and ran no build and no test: requirements and tests (one high and two medium findings) and project rules and architecture (one high and one medium finding). The five entries are three distinct defects. All were confirmed and fixed in `76a60a46` and `0112be7e`. One recheck read the delta `2475ce48..0112be7e` read-only: verdict pass, nothing unresolved, one new low finding.

Follow-ups, none of them filed as an issue:

- Low finding of the recheck, open: the source-file condition of the selection is an `IN` subquery under an `OR`, so each cutover run builds the link text of every live Files item of the tenant and compares each candidate transcript with that list. It is reasoned from the query shape and was not measured. A lookup by id (take the id text from the link only when it has the uuid form and compare `f.id` with it) would avoid it.
- For the owner: accept or revise the scope of deviation 1. A manual rerun of a finished transcript no longer matches an Event or proposes speakers; suggesting speakers for finished transcripts would be a separate operation and a new decision, as the ADR says.
- Observation of the worker, not changed: `forEachMaintainedTenant` includes suspended tenants, and `registerTask` completes a suspended tenant's job without work. Such a tenant's transcripts are therefore enqueued again on each deploy, without a paid call, until the tenant is active again.
- Observation of the worker, not changed: a tenant without a `tenant_ai_budgets` row gets its re-runs refused by the gateway. Each such transcript stays `done` with `item_automation` `error`/`budgetExceeded` and is enqueued again by the daily requeue sweep.
- Observation of the rules reviewer, not changed: the docstring of `enqueueTranscriptionJob` (`transcriptionJob.ts`, outside `Touches`) lists every producer and does not name the new cutover.
