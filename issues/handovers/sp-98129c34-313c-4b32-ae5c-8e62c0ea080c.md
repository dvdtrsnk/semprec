# Handover: bound the mailbox removal's wait for the sync guard, answer busy, and check the guard's transaction

Delivered on chain `e1-236-mail-sync`, candidate commit `53e44bc3d89b3f74dbbd43eb11d81d26c06d4da5`, landed by a `--no-ff` merge on `feature/backend-parallel` as the first chain of a train with `e1-243-blob-writer` and `e1-246-mail-oauth`. It is the second source of its chain, after `sp-1272c2b9-82dd-4fde-b6ef-103f53945435`.

**What changed.** In `backend/packages/data/src/mail/mailboxSyncGuard.ts`, `lockMailboxSync(client, id, { maxWaitMs })` now requires a READ COMMITTED transaction of the active tenant and throws before it locks anything otherwise (`TenantScopeMissingError` still comes first). With `maxWaitMs` it sets `lock_timeout` transaction-locally for the advisory lock statement only, restores the previous value in the next statement, and maps SQLSTATE `55P03` to the exported `MailboxSyncBusyError` (a `ChokePointError`, 409, code `mailbox_sync_busy`). `MAILBOX_REMOVAL_SYNC_WAIT_MS = 15_000` is exported. `removeMailboxWithClient` in `mail/mailboxRemoval.ts` passes `options.syncWaitMs ?? 15 s` (new `RemoveMailboxOptions.syncWaitMs`). `enterSyncPass` and `mailSyncJob.ts` are untouched and keep their unbounded wait. New ADR `docs/adr/2026-11-15-a-mailbox-removal-waits-a-bounded-time-for-the-sync-guard-and-answers-busy.md`.

**Contracts dependents build on.** `lockMailboxSync` option `maxWaitMs`; exports `MailboxSyncBusyError` and `MAILBOX_REMOVAL_SYNC_WAIT_MS`; `RemoveMailboxOptions.syncWaitMs`. A removal whose guard is still held after the bound answers 409 `mailbox_sync_busy`, writes nothing, runs no cleanup and enqueues no job; a repeated request succeeds once the guard is free. The API layer maps the error through its generic `ChokePointError` mapping, which was not changed. No route, table, migration, operation or job name changed.

**Files.** `backend/packages/data/src/mail/mailboxSyncGuard.ts`, `backend/packages/data/src/mail/mailboxRemoval.ts`, the ADR above, `backend/packages/data/src/__tests__/mailboxRemoval.test.ts`.

**Tests.** `mailboxRemoval.test.ts`, section "the bounded wait for the sync guard (sp-98129c34)": busy after the bound with a snapshot equal before and after, no removal job and no cleanup call, then a repeated removal that succeeds; release within the bound; `lock_timeout` as it was after the grant (values 0 and 7s) and after a real wait; the transaction precondition (outside a transaction, REPEATABLE READ, another tenant's transaction); the route handler answering 409 (it waits the real 15 s default); and, from the fix round, a spy test that a no-option call sends no `set_config` of `lock_timeout` and a two-transaction test that a no-option waiter under the transaction's own 200 ms `lock_timeout` ends with SQLSTATE `55P03`, not `MailboxSyncBusyError`. The existing IMAP, Gmail and Graph pass cases run unchanged.

**Deviations and spec seams.** A `RangeError` for a `maxWaitMs` that is not a positive integer (`lock_timeout` 0 means no timeout), with a test; it is not in the Task text. The transaction, tenant and previous `lock_timeout` are read in one statement. The route-handler 409 test waits the real 15 s default because the Task adds `syncWaitMs` only to `RemoveMailboxOptions`, not to the route handler's options.

**Criteria NOT RUN or BLOCKED.** None.

**Review.** Requirements and tests lens: one medium finding (no test failed if a no-option call applied and restored a default bound), fixed in `53e44bc3d89b3f74dbbd43eb11d81d26c06d4da5` with two new tests and a mutation check by the worker. Rules and architecture lens: clear. Security lens: clear. The recheck found the fix resolved the finding.

**Follow-ups.** None for this source. The sibling source `sp-1272c2b9-82dd-4fde-b6ef-103f53945435` has a proposed follow-up about the reauthorization lock order.
