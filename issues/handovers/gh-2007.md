## What was delivered

An organizer's higher-SEQUENCE REQUEST for an invitation the user has already answered (accepted, tentative or declined) now updates the invitation's parsed fields, sequence and source email, keeps the status and `respondedAt`, and updates the linked live Event field by field, writing a field only when the user has not changed it. No notification is written and nothing is sent.

## Entry points and contracts dependents build on

- `calendar/invitationEventFields.ts`: `invitationEventFields(invitation, timeZone)`, the pure invitation-to-Event mapping moved out of the respond handler; `calendar/invitationRouteHandlers.ts` now calls it with the tenant zone (behaviour unchanged).
- `calendar/invitationIngestAction.ts`, answered branch of `applyRequest`, under the per-UID lock: it runs only when the message comes from the invitation's organizer (`isFromOrganizer`, the helper `applyCancel` of gh-2006 uses too; another sender or none changes nothing and logs `sender_not_organizer` with ids). The live Event is written through `updateItemWithClient` with only the keys `name`, `place`, `type`, `date`, `endDate`, `timeFrom`, `timeTo` whose stored value equals the previously computed mapping (passed through `deriveEventTimeProperties`) and whose new computed value differs. The derived `time` property is never compared. An absent new value clears place, end and the other optional fields when the Event still holds the previous value; the title is never cleared (an update with no or a blank SUMMARY keeps the Event name). A trashed or missing Event is not touched. `cancelled` and `acknowledged` invitations, an equal or lower SEQUENCE and a trashed invitation change nothing. A failing Events validation is logged (email id, invitation id, reason `event_validation_failed`) and rethrown, so the whole email rolls back; a failure that is no Events rule is rethrown without that reason code.
- ADR `docs/adr/2026-11-14-an-organizers-update-is-adopted-into-an-event-by-the-calendar-module-until-the-user-changes-the-field.md` records the handoff: the calendar module writes six user-owned Event properties as the system writer, the per-field comparison is stateless, the organizer-only rule, the title is never cleared, the whole email rolls back. The header of `calendar/calendarModuleManifest.ts` has the handoff paragraph and the ingest file header cites the ADR.

## Deviations from the specification and spec seams

1. "Not changed by the user" is compared against the previous mapping passed through `deriveEventTimeProperties`, because the Events write adds a default `timeTo` (start plus one hour) for an invitation without an end; comparing the raw mapping would treat that stored default as a user change.
2. A new value that is absent is written as null for place and end when the Event still holds the previous value; the title is the exception (review fix).
3. The Task says a failing Event validation "rolls back and is logged": the ValidationError is logged with a reason code and rethrown, so the heartbeat action fails and does not swallow it.
4. The tenant zone is the one the action already reads (`getSystemTimezone`), the same setting the respond route reads.
5. The organizer check on the answered branch is not in the Task; it was added by review (security, high). The pending path (gh-1929) is unchanged and out of scope.
6. The ADR and the handoff comment were added by review; the Task states no ADR.
7. The commit trailer of the segment is `Co-Authored-By: Claude Sonnet 5.5`.
