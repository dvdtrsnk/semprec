## Changes

- **Lock in `seedSystem`** (`backend/packages/data/src/seed/seedSystem.ts`): adds `SEED_ADVISORY_LOCK_KEY = 2331n`, a different key from `SETUP_ADVISORY_LOCK_KEY` (2330n). `SELECT pg_advisory_xact_lock($1)` is now the first statement in the seed transaction, before the "is it already seeded?" check. A second concurrent seed waits for the first to commit, then sees its rows and returns early. `runModuleDataMigrations` still runs after the transaction, outside the lock.
- **`runSeed(pool)`** (`backend/packages/data/src/db/runSeed.ts`, new):
  - It first reads whether a `systemSettings` database already exists, using a typed `SELECT`.
  - It then calls `seedSystem` with fresh view-type and computed-key registries.
  - Finally it runs `runModuleDataMigrations` with `loadFullModuleRegistry()`, so every active module's data migrations run, not just `systemDatabases`.
  - It returns `"created"` or `"already-seeded"`.
- **Seed CLI** (`backend/packages/data/src/db/runSeedCli.ts`, new): works like `runMigrationsCli.ts`. It throws `DATABASE_URL is not set` when the variable is missing, closes the pool in `finally`, and prints either `seed: created system databases` or `seed: already seeded`. It never prints the connection string. The existing `build` script emits it to `dist/db/runSeedCli.js`.
- **`deploy/deploy.sh`**: new `run_seed()`, built the same way as `run_migrations()` and also using `SEMPREC_MIGRATE_DATABASE_URL`. `deploy()` calls it after `run_migrations` and before `promote_release`. If it fails, the deploy stops with `seed failed` before activation, leaving `current` and the services unchanged.
- **`deploy/deploy.test.sh`**:
  - A successful deploy must now record exactly one `runMigrationsCli.js` call and exactly one `runSeedCli.js` call, both under `SEMPREC_MIGRATE_DATABASE_URL`, with the migrations call first.
  - The `systemd-run` mock has a new `fail-seed` marker that fails only the call containing `runSeedCli.js`.
  - A new `expect_refused 'seed failed' v1.1.0` case covers that failure. The existing checks that follow it confirm `current` stays at `v1.0.0`, there is no `releases/v1.1.0`, no partial release and no service restart.
- **Docs**: step 3 of "Deploying a release" in `deploy/README.md` now mentions the seed CLI. New `docs/operations/seeding.md` covers what the seed creates, that it is idempotent and lock-protected, that it runs on every deploy, and how to run it by hand.

## Tests

`backend/packages/data/src/__tests__/runSeedCli.test.ts` (integration tier):
- **Empty database:** `runSeed` returns `created`, and one `systemSettings` and one `projects` database exist afterwards.
- **Second call:** it returns `already-seeded`. Every `databases` row is compared in full with `to_jsonb`, and the item count is unchanged.
- **Two calls at once** (`Promise.all`): exactly one `systemSettings` and one `projects` database exist afterwards.

I removed the lock temporarily and the concurrency test failed; with the lock back it passes.

## Note

When two runs race on an empty database, both can report `created` even though only one of them wrote. That's because the outcome comes from the read taken before `seedSystem`, as the issue specifies. The line is only a report; the lock is what keeps a second copy from being written. The docstring on `runSeed` says this.
