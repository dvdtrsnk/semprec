## What was delivered

- A user-owned one-to-one relation `sleepSettings.area` (key `area`, constant `SLEEP_SETTINGS_AREA_KEY`) to the Areas database: no inverse property, property name null, no default edge. A new tenant gets it from `seedSleepModule.ts`; `seedSystem.ts` passes the Areas database id.
- A tenant seeded earlier gets it from the new cutover `sleep/sleepSettingsAreaCutoverMigration.ts` (`runSleepSettingsAreaCutoverMigration`): one transaction, `LOCK TABLE properties`, raw SQL, idempotent, a second run changes nothing and a user-set area is kept. It does nothing for a tenant without the sleepSettings or Areas database. It is registered in `db/tenantCutoverMigrations.ts` after the gh-1830 step and before the area-note step that stays last.
- `loadSleepNights` and `GET /api/sleep/nights` return `areaId`: the target of the settings item's `area` edge, or null while none is set (a trashed target is still returned).
- Label `property.sleepSettings.area.name` in the cs and en catalogs.
- A second edge to another area answers 409 `cardinality_violation`; `relation.set` (choke point `setRelation`) moves the single edge without a 409.

## Entry points and contracts dependents build on

- Property key `area` on the `sleepSettings` database (relation to Areas, cardinality one-to-one, user-owned, no inverse); edges are written through the generic relation routes, e.g. `PUT /api/items/:id/relations/area/:targetId`.
- Field `areaId: string | null` in the `GET /api/sleep/nights` response (and the `loadSleepNights` result).
- `runSleepSettingsAreaCutoverMigration` in the cutover list; `seedSleepModuleInTransaction(client, projectsDatabaseId, areasDatabaseId, viewTypeRegistry)` now requires the Areas database id.
- No table, numbered migration, route or job name was added.
