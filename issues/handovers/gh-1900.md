## What was delivered

- `POST /api/mail/threads/:threadId/tasks`, custom route `mailThreadTaskCreate` (justification `transactional-semantics`), handler `createMailThreadTaskCreateRouteHandler(pool, dependencies)` in `mail/mailThreadTaskRouteHandlers.ts`. Body: strict object `{ name?, date? }` (`name` 1..500 characters, `date` a calendar date), otherwise `400 validation_failed`. Answers `201 { id, name, date }`.
- With a `name` no model call is made. Without one the route reads the thread's snapshot in a REPEATABLE READ transaction, asks the gateway outside any transaction (operation `mail_thread_task_name`, no project item) and writes in a READ COMMITTED transaction that takes the mail thread guard, locks the Emails items of the live messages `FOR SHARE` in item id order and answers `409 conflict` (code `conflict`) when the thread or the set of messages differs from the snapshot. No connection is held during the gateway call.
- `mail/threadTasks.ts`: `createThreadTask` (writes the Tasks item, the `Threads.tasks` edge, the inherited project through the link rule and the people link, in the caller's transaction, reusable by the confirm of a Semp proposal), `readThreadTaskSnapshot`, `deriveThreadTaskName`, `writeTaskOfThread`, `THREAD_TASK_NAME_MAX_LENGTH`, `THREAD_TASK_PEOPLE_RULE_KEY` (`mailThreadTaskPeople`).
- Link rule `taskProjectFromThread` in the mail module manifest (`Threads.project` to `Tasks.project` via `Threads.tasks`); a later change of the thread's project reaches the task through the `valueLinksPropagate` job until the task's project is changed by hand. The task's people are an inherited `Tasks.people` value link with the thread item as source and rule key `mailThreadTaskPeople`, with one edge per person of the conversation written as the `valueLinks` process (the tenant's own people and people in the Trash are left out).
- Failure mapping: the gateway's budget refusal is `403 budget_exceeded`; any other `AiGatewayFailedError` or an unusable model answer is `502 upstream_unavailable`; an unknown or another tenant's thread id is the same `404`; an error that is not the gateway's propagates unchanged. No task exists after any of them.
- Review fix in `chokePoint/valueLinkOps.ts`: `sourceValues` now throws `value_link_conflict` (409) for a live source whose property its database lacks, for every link. Without it a relink of the people link read the missing property as empty and deleted every person of the task. The people link can be unlinked but not relinked.
- ADR `docs/adr/2026-11-14-a-task-made-from-a-mail-thread-inherits-its-project-and-people.md`.

## Deviations from the specification and spec seams

1. The route entry is in `routeMatrix/mail.ts`, with its isolation case and handler-file mapping, not in `routeMatrix.ts`.
2. The Touches omit files the Task cannot work without: `completeHandler.ts` (the gateway rejects every unlisted operation), `aiGatewayClient.ts` documentation and its test, and `customRouteMount.ts` plus `serve.ts` (the `aiGateway` dependency, per the 2026-10-29 composition-root ADR).
3. The new link rule changes what a thread task gets when its `Threads.tasks` edge is written, so `mailThreadDetailTasks.test.ts` (its `newThreadTask` removes the rule's auto-created project link row with a commented raw DELETE) and `actionItemInheritance.test.ts` (its rule-list filter also requires module id `systemDatabases`) were brought in line.
4. Spec seam: the Task says "the gateway's budget error"; it is mapped to `403 budget_exceeded` (the gateway's own status and code); other gateway failures are `502 upstream_unavailable`.
5. The people link uses rule key `mailThreadTaskPeople` and source property `people`; no rule of that key exists and Threads has no such property (documented in the ADR); hence the relink refusal above.
6. The gateway dependency is read after the snapshot read, so an unknown thread answers 404 also on a mount without a gateway.
7. The Task says "conflict" for 409: sent as code `conflict` through `ConflictError(..., 'conflict')`.
8. #1869 and #1898 are not in this tree. #1898 is a `Shared-file ordering` blocker still open; the thread's project is the existing `Threads.project` relation.
