## Changes
`backend/packages/data/src/migrationJob/moduleDataMigration.ts`
- **Tenant check:** right after `pool.connect()`, the runner reads `SELECT app_tenant_default()::text AS tenant_id` on its dedicated client. If that is `NULL` (no tenant scope while several tenants exist), it throws a plain `Error` saying the migration must run inside a tenant scope. This happens before any advisory lock is taken, and the existing `finally` still releases the client.
- **Lock key:** `lockKey(tenantId, transition)` now returns `module-data-migration:<tenantId>:<moduleId>:<databaseKey>:<from>:<to>`. Lock and unlock use the same key.
- **Arbiters:**
  - The `module_migrations` marker insert uses target-less `ON CONFLICT DO NOTHING`, so every unique index acts as an arbiter.
  - `writeProgress` upserts on `ON CONFLICT (tenant_id, module_id, database_key, from_version, to_version)`, i.e. the tenant-leading index.
  - The reads have no hand-written `tenant_id` predicates; row-level security does the scoping.
- **Docstrings:** `runModuleDataMigration` and `runModuleDataMigrations` now describe one tenant's transition, run inside that tenant's scope (or with no scope while there is only one tenant).

## Tests
New file `backend/packages/data/src/__tests__/moduleDataMigrationPerTenant.test.ts`, on the two-tenant harness of #975 (`createTestTenant()` plus a `semprec_data` pool). Each tenant gets its own system fixture database and items, created in its own scope.
- **Per-tenant data:** tenant zero runs and records T. A run of T in tenant B's scope then converts all of B's items. Tenant zero's marker and its items (including `updated_at`) stay unchanged, and tenant zero's rerun is still a no-op.
- **Per-tenant lock:** the test holds tenant zero's advisory lock on its own connection and confirms it through `pg_locks`. A run in B's scope converts B's items; a run in tenant zero's scope converts nothing and records nothing.
- **Same-tenant exclusivity:** two concurrent runs in B's scope record T once, and the converter runs over each item at most once per pass (20 items × 2 passes = 40 calls).
- **Progress per tenant:** a run in B's scope that fails mid-way leaves only B's progress row, and none is visible in tenant zero's scope. The retry resumes from B's recorded pass and cursor, and the already committed rows are not rewritten.
- **No scope, two tenants:** the run rejects with the tenant-scope error. Nothing is converted, and `pg_locks` shows no lock for either tenant's key.
- **Single tenant:** the existing `moduleDataMigration.test.ts` is unchanged and passes.

Out of scope: dropping the legacy primary keys and asserting a second tenant's own done-marker (both #1065). Until #1065, B's marker insert for a transition tenant zero already recorded is silently skipped by the legacy key, as the issue describes, so the tests do not assert B's marker in that case.
