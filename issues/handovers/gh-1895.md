## What was delivered

- `POST /api/mail/drafts/:id/attachments` with strict body `{ fileItemId }` (answers 200 with the draft view) and `DELETE /api/mail/drafts/:id/attachments/:fileItemId`. Custom routes `mailDraftAttachmentAdd` and `mailDraftAttachmentRemove` (`transactional-semantics`), handlers `createMailDraftAttachmentAddRouteHandler` and `createMailDraftAttachmentRemoveRouteHandler` in `mail/mailDraftRouteHandlers.ts`, exported through the existing `export *` of that module.
- `mail/mailDraftAttachments.ts`: `attachFileToDraft` locks the draft item, the draft row, then the file; refuses with the draft's own errors (404, 409 not editable, 409 already sent), 404 for an unknown, trashed, foreign-tenant or non-Files item, 400 for a file without stored content, and `413 mail_attachment_too_large` when the total passes the provider limit (Gmail 25 MB, Outlook 20 MB, iCloud 20 MB, any other mailbox the `MAX_FILE_SIZE_MB` upload cap; a megabyte is 1024*1024 bytes). It writes `Emails.attachments` with `EMAILS_RELATION_CONTEXT`, creates a new Files item over the same blob when another email holds the file, and is a no-op (no write, no announcement) for a file already on the draft, including a repeat post of a file another email holds (the draft already lists a file of the same name over the same blob; checked before the size limit, so a retry at the limit is not a 413). `detachFileFromDraft` removes the edge (404 when absent) and leaves the Files item.
- `mail/mailDraftAttachmentFiles.ts`: the attachment list of the draft view (filled in the read, update and create answers), the attachment owners, and `deleteFilesOfDiscardedDraft`: `discardEmailDraft` soft-deletes through the choke point the attached files that have no relation edge to any other item and were created at or after the draft's Emails item. A file older than the draft is kept (the safe side; a file uploaded before the draft exists is kept).
- `MailAttachmentTooLargeError` (413, code `mail_attachment_too_large`) in `mail/draft.ts`, exported from `index.ts` and registered in `adapter/errorContract.ts`.
- Each change announces the `{ scope: mailThread, threadId }` invalidation once; refused and no-op calls announce none.
- The `MAX_FILE_SIZE_MB` upload cap reaches the data package through the custom-route container: `adapter/customRouteMount.ts` gained `maxFileSizeBytes`, set in `createDispatcher` of `app.ts` from its `maxFileSizeBytes` option.
- ADR `docs/adr/2026-11-14-a-mail-draft-attaches-copies-of-held-files-and-trashes-the-files-that-are-its-own.md`.

## Deviations from the specification and spec seams

1. The DTO builder and the discard are in `mail/draft.ts`, not `mailDraftRouteHandlers.ts`; to avoid an import cycle the queries and the discard cleanup are in the extra module `mailDraftAttachmentFiles.ts` and the attach and detach operations in `mailDraftAttachments.ts`.
2. The route entries are in the slice module `routeMatrix/mail.ts`.
3. `customRouteMount.ts` and `app.ts` (not in Touches) carry the upload cap; `index.ts` is at the 900-line cap, so the error is added to an existing export statement and the handlers arrive through the existing `export *`.
4. Interpretations: a file "attached nowhere else" is a file with no relation edge to any item other than the draft (nothing records where a Files item came from, and no migration is allowed); after review a file created before the draft's Emails item is also kept. The POST answers 200 with the draft view; attaching a file already on the draft is an idempotent no-op. The ADR records the copy and discard rules.
5. `mailDraftAttachmentsHttp.test.ts` was added in semprec-api to cover the composition wiring and the 413 mapping.
6. At the landing merge the route entries and manifest entries of this source were kept next to the `mail thread task create` entries of gh-1900 and the `mailThreadFlag` entry of gh-1893 (conflicts in `routeMatrix/mail.ts`, `mailModuleManifest.ts`, `chokePointWriteBoundary.unit.test.ts` and `tenantIsolationRoutes.test.ts`, resolved by keeping both sides).

## Follow-ups from review

Three reviewers (requirements, rules, security) read the segment. Findings: the discard trashed any attached file without a relation edge, including a pre-existing file that was not uploaded for the draft (medium, security; fixed in `ed689da8d`: files older than the draft are kept; the consequence that a file uploaded before the draft exists is kept is named in the ADR); attaching a file another email holds twice made a second copy (low; fixed in `e37e910ed`). The focused recheck returned `pass` with no unresolved or new finding; its one cosmetic note is a docstring line in `mailDraftAttachmentFiles.ts` wider than the usual wrap (lint and format check passed on the merged tree). Noticed, not changed: nothing records which Files items were uploaded for a draft, so the discard rule is a heuristic (no other relation edge, created at or after the draft).
