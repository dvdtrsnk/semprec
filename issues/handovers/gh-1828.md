## What was delivered

`GET /api/badge-counts` answers the counts the app icon badge and its preview show: `{ pendingApprovals, pendingInvites, openInboxItems }`.

- `notifications/badgeCountsRoute.ts`: `createBadgeCountsRouteHandler(pool)` (custom route, justification `single-consumer-read`). It reads `pendingApprovals` in one transaction (`withTransaction`, tenant scope from the session) with the user id taken only from `ctx.identity.user.id`; no query, path or body input, no writes. `pendingInvites` and `openInboxItems` are `0`.
- `pendingApprovals` is the existing `countPendingApprovalRequests(client, { ownerUserId, sourceKinds: null })` of `mcp/approvalRequestsStore.ts`, the function that backs `GET /api/approval-requests/count` (#1786), with every source kind counted (chat, heartbeat, mcp). The badge therefore equals the approval queue pending count by construction.
- The route is declared in `chokePoint/schemaCoreModuleManifest.ts` (`getBadgeCounts`, handler export `createBadgeCountsRouteHandler`), has the route matrix entry `badge counts` (tenancy `tenant`, not public) in the new slice `routeMatrix/badgeCounts.ts`, the `ROUTE_HANDLER_FILES` mapping and a `tenantIsolationRoutes.test.ts` case.

## Entry points and contracts dependents build on

- Route: `GET /api/badge-counts`, authenticated, tenant-scoped, response `{ pendingApprovals: number, pendingInvites: number, openInboxItems: number }` (type `BadgeCounts`, exported from `notifications/badgeCountsRoute.ts`; not re-exported from `@semprec/data` index.ts).
- The issues that introduce the invitation count (#1954, #1901) and the Inbox count (`countOpenInboxCards`, already delivered by #1823) wire their values into `createBadgeCountsRouteHandler`; today both fields are the constant `0`.
- #1891 (badge on pushes) and #1918 (realtime invalidation of counts) consume this route; which counts enter the badge is decided by the user's switches, not here.

## Deviations and spec seams

1. Task step 1 asks for a new `countPendingApprovalRequests(client, ownerUserId)` in `mcp/approvalRequestsQueue.ts`. A function of that name already exists in `mcp/approvalRequestsStore.ts` (#1786, signature `(client, { ownerUserId, sourceKinds })`) and backs `GET /api/approval-requests/count`; it was reused with `sourceKinds: null` instead of adding a duplicate, so there is one definition of the count. `approvalRequestsQueue.ts` is unchanged. Both reviewers judged this sound.
2. The route matrix entry lives in a new slice module `routeMatrix/badgeCounts.ts` (`BADGE_COUNTS_ROUTES`) registered in `routeMatrix.ts`, not as an inline entry.
3. The Touches list names `index.ts` export lines; none were added, because route handlers are reached through the manifest module exports (as the notification preferences handlers are). `publicSurface.test.ts` passes.
4. `openInboxItems` stays `0` although #1823 delivered `countOpenInboxCards`: the Decisions, Out of scope and acceptance criteria say it is 0 until the issue that introduces the count wires it in.
5. The isolation case asserts deltas of the counts (A +3, B +1), like the neighbouring `inbox cards count` case.
