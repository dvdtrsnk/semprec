## What was delivered

- The `journal` processing method of an Inbox item type (`PROCESSING_METHODS`). `assertValidProcessingConfig` accepts `journal` only without a `targetDatabase`; `database` with the Journal database as target is refused with a message that names the `journal` method. All three writers (REST, agent tool, `/mcp`) go through the same write hook. The seed option and the en/cs labels come from `PROCESSING_METHODS`.
- A per-tenant cutover `inbox/inboxJournalMethodCutoverMigration.ts` (`runInboxJournalMethodCutoverMigration`), registered in `db/tenantCutoverMigrations.ts` after the gh-1973 entry. It appends the `journal` option to the `processingMethod` select and converts every `database` type that targets the Journal database into a `journal` type. Live types are written through the choke point; trashed types, which the choke point refuses, by one SQL statement that locks the rows first and checks the affected-row count (ADR `docs/adr/2026-11-14-the-journal-method-cutover-converts-trashed-types-with-one-statement.md`). Both shapes store `targetDatabase: null` (the choke point has no key removal); every reader treats null as unset. A second run changes nothing.
- The `journalEntry` envelope kind: `proposalEnvelope.ts` (`ProposalEntityKind`, `proposalEnvelopeSchema` moved there from `inboxTickAction.ts`) and the new `inbox/journalEntryEnvelope.ts`, validated from `assertValidProposalEnvelope`: strict `{date, markdown, areaId?, projectId?}`, calendar-day date, non-blank Markdown that parses without page blocks, target is the tenant Journal database, an area or project is a live (not trashed, not archived) item of Areas or Projects in the caller's tenant. `assertValidEnvelopeForCard` rejects it on a transcript card (`ValidationError` on `entityKind`) and accepts it on any other card; revise accepts it and replaces the stored one.
- `proposalActions.ts` is back under the line cap: `relationEnvelopeMetadata` and `writeEnvelopeRelations` moved verbatim into `inbox/proposalEnvelopeRelations.ts`; the writer is a parameter now and the one caller passes `CONFIRMING_USER_WRITER`.

## Deviations from the specification and spec seams

1. The cutover leaves a stored `targetDatabase: null` rather than removing the key (the choke point has no key removal); trashed types get the same null so both shapes match. Recorded in the ADR and the docstrings.
2. The trashed-type conversion is a raw statement outside the choke point, a narrow exception recorded in an ADR.
3. The Markdown of a `journalEntry` is validated with `parseMarkdown` (page blocks refused), not `parseCheckedMarkdown`, because importing `pageMarkdown` from the `inboxTickAction` chain makes the forbidden choke-point rollup cycle; a link to a missing item or an unknown block type is therefore refused at confirm, not at envelope validation.
4. `inboxTickAction.ts` is at the 900-line cap, so the check is one line there and the code is in `journalEntryEnvelope.ts`; for the same reason the relation helpers were moved out of `proposalActions.ts`.
5. Spec seam: the Task's "envelope schema" is `proposalEnvelope.ts`; tick-write validation is exercised through `assertValidProposalEnvelope`, because the tick cannot produce a `journalEntry` before gh-1982.
6. Commit trailers of the segments name Claude Sonnet 5.5 (the session attribution line).
