# gh-1441 — Store per-user notification preferences

Repository-Issue: gh-1441

## Delivered behavior and production wiring

- Migration `backend/packages/data/src/db/migrations/0119_notification_preferences.sql` creates `notification_preferences` with primary key `(tenant_id, user_id)` and the columns and defaults of the Task. `problems_level` is checked against `off|critical|all`. The table carries `semprec:tenancy=tenant`, row-level security with the restrictive `tenant_isolation` and the permissive `tenant_rows` policy, and `GRANT SELECT, INSERT, UPDATE, DELETE ... TO semprec_side`. `semprec_data` inherits that grant, as it does for the other side tables written by `semprec-api`.
- The migration also adds the tenant-consistent twin `notification_preferences_user_id_tenant_fkey (tenant_id, user_id) -> users (tenant_id, id)` next to the plain `user_id -> users(id)` reference. The tenancy catalog requires that twin for every reference between tenant rows (migration 0083 convention). The reference has no `ON DELETE` action: account purge (`tenancy/tenantPurgeJob.ts`, `purgeRows`) deletes a tenant's rows before `finalise` deletes the users.
- Store `backend/packages/data/src/notifications/notificationPreferencesStore.ts`:
  - `getNotificationPreferences(client, userId)` returns the stored row, or the defaults with `updatedAt: null` when there is no row. It never writes.
  - `patchNotificationPreferences(client: PoolClient, userId, patch)` returns the current values without a write when the patch has no field. Otherwise it runs `INSERT ... ON CONFLICT (tenant_id, user_id) DO NOTHING` and then one `UPDATE` in which each column is `COALESCE($n, column)`. The update's result is checked with `requireAffectedRows`, then read with `requireSingleRow`.
  - Exports `NOTIFICATION_PROBLEMS_LEVELS`, the types `NotificationPreferences`, `NotificationPreferencesPatch` and `NotificationProblemsLevel`, and the two functions. They are re-exported from `backend/packages/data/src/index.ts`.
- Routes `backend/packages/data/src/notifications/notificationPreferencesRoutes.ts`:
  - `createGetNotificationPreferencesRouteHandler(pool)` and `createPatchNotificationPreferencesRouteHandler(pool)`.
  - `parseNotificationPreferencesPatch(body)` runs before the transaction opens. It throws `ValidationError` with `details.field` for an unknown key (including `updatedAt`), a non-boolean boolean field, or a `problemsLevel` outside the set. A body that is not a JSON object is a 400 with no field.
- Manifest `backend/packages/data/src/chokePoint/schemaCoreModuleManifest.ts` declares `GET /api/notification-preferences` (justification `single-consumer-read`) and `PATCH /api/notification-preferences` (justification `transactional-semantics`), tenancy `tenant`. Both handler factories are re-exported from the manifest module.
- Response of both routes is the camelCase object `{ approvals, invites, reminders, problemsLevel, problemsSummary, badgeApprovals, badgeInvites, badgeInbox, updatedAt }`.
- Defaults, written in the store as `DEFAULT_VALUES` and declared as the column defaults of migration 0119: `approvals`, `invites`, `reminders` true; `problemsLevel` `critical`; `problemsSummary` true; `badgeApprovals` and `badgeInvites` true; `badgeInbox` false.

## Notes for dependants

- #1443 (push filter) and #1891 (badge) should read through `getNotificationPreferences(client, userId)` from the package index. A user without a row gets the same defaults, so no caller has to special-case a missing row.
- The PATCH emits no realtime event and no `NOTIFY`. #1918 adds the other-device invalidation after the commit (`runAfterCommit`). This issue does not add it.
- `updatedAt` is `null` until the first change. The defaults live in two places, `DEFAULT_VALUES` in the store and the column defaults in migration 0119. A change to one must change the other; the defaults tests pin them together.
- Migration ordinal: `origin/develop` ends at `0086`, while the integration tip `5a1ac0d6` ends at `0118`. `0119` is the next free ordinal on this branch's base. The integrator must keep `0119` unless another issue merged first takes it.
- Account purge deletes this table's rows through the catalog before it deletes users. Any future path that deletes a user outside that purge must delete the row first, because the reference has no cascade.
- The GET and PATCH routes are tenant-classified, not account-classified, as the Task specifies. The table is tenant-classified, so the isolation case for each route runs in the tenant class.
