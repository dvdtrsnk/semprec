## What was delivered

A heartbeat or agent run failure now raises one deduplicated `agents` problem in the same transaction as the failure record.

- `scheduler/sweep.ts` `notifyHeartbeatError` raises `agents:heartbeat:<heartbeatId>` next to the `heartbeat_error` notification.
- `finishAgentRunWithErrorNotification` (`agentRuns/agentRunsStore.ts`), the one producer of `agent_run_error`, raises the heartbeat problem for a tick run (heartbeat id from `run.heartbeat_id`) and `agents:run:<first run of the retry chain>` (with `project_item_id`) for a supervisor or MCP run. A chat turn raises nothing.
- `finishTickRunWithMessage` (`semp/sempTickThreadStore.ts`) raises the heartbeat problem for a tick reply whose run ended done but left a failed tool call, in the transaction of the message write.
- Review fix: `raiseAgentRunProblem` retries without the project reference only when `raiseProblem` rejects `projectItemId` (the item was purged), so a dangling reference can neither block the run close nor the whole-tenant startup repair.

## Entry points and contracts dependents build on

- `semp/agentProblemKeys.ts`: `agentHeartbeatProblemKey(heartbeatId)` gives `agents:heartbeat:<id>`; `agentRunProblemKey(firstRunId)` gives `agents:run:<id>`. Dedupe keys are tenant scoped, so the prefixes carry the category.
- `semp/agentProblems.ts`: `raiseAgentHeartbeatProblem(client, { userId, heartbeatId, occurrenceKey })` (kind `agentHeartbeat`, source `project_heartbeats`, severity warning, no project) and `raiseAgentRunProblem(client, { userId, firstRunId, failedRunId, projectItemId })` (kind `agentRun`, source `agent_runs`, severity warning). Neither is in the `@semprec/data` barrel.
- `getRetryChainFirstRunId` (read-only recursive CTE over `retry_of_run_id`, tenant RLS, NotFound for another tenant's run) is exported through the store's `export *`, so it is in the `@semprec/data` surface and in `publicSurface.test.ts`.
- `TickThreadRef` gained `heartbeatId`, set by `getOrCreateTickThread`.
- No table, migration, route, operation or job name was added.

## Deviations and spec seams

1. The Task names `scheduler/actions.ts`; the final failed attempt of a run closes through `finishTickRunWithMessage`, which calls `finishAgentRunWithErrorNotification`, so the raise sits there and `actions.ts` is unchanged. Side effect, declared: a startup repair or cancellation of an interrupted supervisor/MCP run, or of a tick run naming a heartbeat, now also raises a problem, mirroring the `agent_run_error` notification. A heartbeat-triggered run with no heartbeat id and user runs raise none.
2. `context.heartbeatId` in `ActionContext` is always set, so the "otherwise agentRun" branch is reached from the store (run without `heartbeat_id`).
3. The tick reply of #1557 stores no steps (`semp_messages.steps` is NULL), so the failed-tool-call check derives steps from the run events between the message's `event_from_id` and `event_to_id` and applies `deriveReplyOutcome` of #1890.
4. Heartbeat problems carry no `project_item_id` (the Task does not name one). A cancelled run still raises, as the notification does.
