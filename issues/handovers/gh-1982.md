## What was delivered

The Inbox tick now proposes a journal entry for an Inbox item whose type has processing method `journal`.

- `inbox/inboxTickTarget.ts` (new): `resolveTickTarget` maps the processing method to the envelope kind and resolves the target. For `journal` it resolves the tenant's Journal database (by the Journal module id) in the read transaction; a tenant without a Journal database fails the tick and writes no card. The `database` and `pageContent` branches moved here verbatim from `readTickSnapshot` because `inboxTickAction.ts` sits at the 900-line cap.
- `TickSnapshot` and `ProposalComputationInput` carry `journalDatabaseId` and `sourceDate`; `ComputedProposalEntityKind` includes `journalEntry`.
- `buildProposalEnvelope` (`inbox/inboxTickSnapshot.ts`) builds `{journalEntry, target: Journal database, properties}`: `date` defaults to the source item's date, `areaId` is dropped when `projectId` is also present, and a computation result that carries its own `target` is a `ValidationError` (field `target`). `buildTickEnvelope` returns that refusal to `writeTickResult`, which records the card as `needsClarification` with no stored envelope, as for an envelope that fails validation (no card with an invalid envelope).
- semprec-api computation (`services/semprec-api/src/proposalComputation.ts`, new `journalEntryProposal.ts`): asks the model for `{date?, markdown, areaId?, projectId?}` only, with its own instruction (`JOURNAL_ENTRY_INSTRUCTION`) and JSON schema (`JOURNAL_ENTRY_RESPONSE_SCHEMA`), returns `{properties, reason?, confidence?}` with no target, and drops areas and projects the workspace context did not list (logs a count, never the ids). The prompt addition for the database and page instructions now applies to `pageContent` only.
- Review fix (medium finding): `inbox/inboxCardKind.ts` maps a `journalEntry` envelope to `cardKind` `journal` and base kind `journal`, `inboxCardsStore.ts` (`buildTargets`) labels the Journal database as the card target, and `proposalEditorRules.ts` no longer describes a `journalEntry` card with the journal editor schema (that schema requires `day`; with the card kind change alone, confirm refused every journalEntry card).

## Deviations from the specification and spec seams

1. Spec seam: `inboxTickAction.ts` is at the 900-line cap, so target resolution moved into `inboxTickTarget.ts` and the envelope and computation-input code sits in `inboxTickSnapshot.ts`. The compute function lives in semprec-api (`proposalComputation.ts`, `journalEntryProposal.ts`), files the Touches do not list but Task step 3 requires.
2. The refusal of a result with its own target is a `ValidationError` thrown by `buildProposalEnvelope`; the tick calls `buildTickEnvelope`, which returns it, and `writeTickResult` (parameter widened to `ProposalEnvelope | ValidationError | null`) records `needsClarification`.
3. `inboxCardKind.ts` was beyond the Task and Touches; it was added by the review fix because the gh-1975 and gh-1981 handovers name it, together with the `buildTargets` label and the `schemaDescribes` exclusion.
4. A model answer with keys outside the journal schema (for example a target) is ignored (non-strict zod); a missing markdown from the model throws like any schema mismatch in that module, so the tick propagates it for a job retry rather than recording `needsClarification`. The "no markdown" refusal is reached by a result built directly (tested at the data layer).
5. `ProposalComputationInput.journalDatabaseId` and `sourceDate` are carried as the Task requires, but the production compute function reads `sourceItem.properties.date` and the server supplies the target afterwards.
