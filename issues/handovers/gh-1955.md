## What was delivered

`POST /api/proposals/:id/recompute` sends a card of kind `inbox` back to the tick: the card becomes `computing`, a `recompute` history entry is written for the user and the tick is triggered for the source Inbox item, in one transaction.

## Entry points and contracts dependents build on

- `inbox/proposalRecompute.ts`: `recomputeProposalWithClient(client, { processingProposalsDatabaseId }, proposalId, { userId, ifVersion? })`, re-exported from `proposalActions.ts` (type `RecomputeProposalInput`). It locks the live card (`lockLiveProposal`), then in order: `kind` other than `inbox` (also `mailThread`, `transcript` or no kind) is a `ValidationError` on `kind` (400); `confirmed` or `rejected` is `ProposalLockedError` (409 `proposal_locked`); an `invalid` card with `sourceDeleted` is a `ValidationError` on `status`; a card that is `computing` is returned unchanged (no write, no job, before the `ifVersion` check, like reject); a stale `ifVersion` is 409 `version_conflict` with `details.current`; the live source Inbox item is read through the `sourceInbox` edge without a lock (`NotFoundError` when missing or trashed). The write is one `updateItemWithClient` of `status: computing` plus the history entry; `invalidReason` is cleared only when leaving `invalid`. `userOverrides`, `userEditedKeys`, `proposal` and `aiProposal` are never touched. The card change is published after commit; `triggerOnItemEventHeartbeats(update)` for the source runs in the same transaction.
- Lock order is card first, source not locked, as in the other card-first writers; the tick write phase and the type change reserve the card NOWAIT, so no wait arises.
- `inbox/inboxRouteHandlers.ts`: `createRecomputeProposalRouteHandler(pool)`: strict body `{ ifVersion? }` (ISO 8601 UTC), UUID `id`; the handler is exported by the module manifest (`inboxModuleManifest.ts`, custom route `recomputeProposal`, justification `transactional-semantics`), not by the data barrel (as the other inbox handlers).
- Route matrix entry `recompute proposal` (`POST /api/proposals/:id/recompute`, tenant, not public) in `routeMatrix/proposals.ts`, its `ROUTE_HANDLER_FILES` mapping in `chokePointWriteBoundary.unit.test.ts`, its isolation case and owner probe in `tenantIsolationRoutes.test.ts`.
- gh-2026 builds on this: the `computing` early return now applies only to a card that has not timed out.

## Deviations from the specification and spec seams

1. The action lives in the new sibling `inbox/proposalRecompute.ts` and is re-exported from `proposalActions.ts` (file size cap; precedent `proposalReset.ts`, `proposalReopen.ts`).
2. The route matrix entry sits in `routeMatrix/proposals.ts`, not `routeMatrix.ts`.
3. The handler is not exported from the data barrel; the manifest module re-exports it.
4. Where the issue is silent: a card of any kind but `inbox` is a `ValidationError` on `kind`; a card without a live source item is `NotFoundError`; the `computing` answer comes before the `ifVersion` check; the body is strict (an unknown key is 400, a non-UUID id is 400 on `id`); the source is read without a lock.
5. Spec seam, not handled: a split sibling card (`splitFromProposalId`) is accepted by the issue's rules, but the tick recomputes only the source's primary card, so a recompute of a sibling would leave it `computing` (and, since gh-2026, it would be reported as `computeFailed` after ten minutes).
6. The tests of `proposalActions.test.ts` and `inboxRouteHandlers.test.ts` use the superuser pool in tenant zero like the rest of those files; isolation is proved over HTTP on the runtime role in `tenantIsolationRoutes.test.ts`.
