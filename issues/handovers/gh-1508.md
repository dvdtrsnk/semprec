# Handover for gh-1508

Graph-mode mail accounts now sync through the api runtime. `createMailSyncAdapters` (`backend/services/semprec-api/src/mailSyncAdapters.ts`) fills `createGraphClient` next to the Gmail member, so a Graph sync pass downloads its mail through delta instead of failing with "No Graph adapter configured". I did not push or open a PR.

The targeted tests pass: `mailSyncAdapters.test.ts` (18 tests, 7 of them run the sync through `createApiQueueRuntime` against a fake Microsoft endpoint) and `graphRestClient.unit.test.ts` (8). The data suites `mailOAuthAccess.test.ts`, `oauthTokenExchange.test.ts` and `publicSurface.test.ts`, and the api suites `queueRuntime`, `mailSyncComposition`, `approvalReplayComposition` and `tenantIsolationJobs`, pass too (115 tests in those 7 files). The backend build, eslint and prettier pass for the touched files. I did not run the full `pnpm run verify`.

- **`createMailSyncAdapters`:** each provider's client keys are read on their own. `createGraphClient` is filled when `MS_GRAPH_OAUTH_CLIENT_ID` and `MS_GRAPH_OAUTH_CLIENT_SECRET` are both set. Its token source calls `refreshAndPersistAccessToken` (gh-1481) with `MICROSOFT_TOKEN_URL`, `purpose: "graph_api_sync"` and no `scope`, so Microsoft keeps the scopes the account already granted.
- **Shared token source:** the Gmail and Graph members use one `createOAuthAccessTokenSource`, renamed from the Gmail-only helper. Its behaviour is unchanged: one kept token per client object, refreshed 60 s before expiry, and a failed refresh keeps nothing new.
- **Missing configuration:** with either Graph key unset or empty, the factory has no `createGraphClient` and logs one `warn` that names the missing keys, never their values. The Gmail warning is unchanged. A Graph-mode sync then fails with "No Graph adapter configured for this composition root".
- **Failure path:** a 400 or 401 from the Microsoft token endpoint is `MailReauthorizationRequiredError`, as before, and the sync job sets `needsReauthorization`. A rotated refresh token is stored by gh-1481's `refreshAndPersistAccessToken`. No new failure path was added.
- **`fetchImpl` seam:** `GraphRestClient` takes an optional second argument, `fetchImpl`, defaulting to the global `fetch`, the same as `GmailRestClient`. The factory's `fetchImpl` option passes through to the token endpoint and the Graph API. This is the only change to `graphRestClient.ts`, as the Touches list allows.
- **Exports:** `GraphRestClient` and `MICROSOFT_TOKEN_URL` are exported from `@semprec/data`, and `publicSurface.test.ts` lists them. Neither is in the issue's Touches list. The Gmail transport (gh-1505) added its exports the same way.
- **Docstrings and config:** the Graph keys' comment in `deploy/shared/env/api.env.example` names the real consumer and the missing-configuration behaviour. The `queueRuntime.ts` docstring and inline comment no longer say Graph is unwired. The `GraphRestClient` class docstring no longer says it is untested.

Tests (`backend/services/semprec-api/src/__tests__/mailSyncAdapters.test.ts`):

- Factory: the four unconfigured Graph cases (id unset, id empty, secret unset, both unset). Each gives no Graph client and one warning that names the missing keys.
- Factory: a Graph client built with an injected `fetchImpl` sends its token request and its Graph requests through that fetch. The global fetch is never called.
- Runtime, Graph-mode account: a pass ingests two messages through delta against a fake Graph API. It uses one token for the whole pass, the token request carries no `scope`, and the delta link is stored.
- Runtime, rotation: the fake token endpoint accepts only the currently valid refresh token and rotates it on every refresh. The first pass stores the rotated token. The second pass presents it, completes, and stores the second delta link.
- Runtime, revoked: a 400 `invalid_grant` gives `needsReauthorization`. No Graph request is made and no delta link is stored. Neither the client secret nor the refresh token appears in the recorded errors.
- Runtime, unconfigured: with Gmail configured and Graph not, the process starts with one Graph warning, and a Graph-mode sync fails with the adapter message.

Notes for dependants (#1745, #1686, #1746, #1753; IMAP #1510 fills the same factory):

- Get a Graph client only through the factory's `createGraphClient`. Build `new GraphRestClient(...)` directly only in tests, and pass a `fetchImpl` when you need a fake.
- A Graph request's token refresh runs on a second pooled connection while the reconcile transaction holds the first. Check pool sizing before adding parallel Graph calls. The same holds for Gmail.
- The refresh needs the ambient tenant scope. The sync job provides it. Code that builds a client elsewhere needs its own scope.
- Microsoft rotates the refresh token on every refresh. `refreshAndPersistAccessToken` stores the new one under the same row lock. Do not keep a copy of a refresh token outside it.
- This issue reads the stored credential and the sync-state row. It never creates either. Connecting a mailbox (#1686) creates them in production. The tests seed them with `storeCredential` and `ensureMailAccountSyncState`.
- `graphSubscriptionClient.ts` makes its own `fetch` calls and does not go through `GraphRestClient`. The `fetchImpl` seam does not cover it. #1745 must decide how its tests inject a fake.
- Known gap, not fixed here: `GraphRestClient.request` reads the whole JSON response with no size cap (`response.json()`), and `fetchDelta` accumulates every page into memory. This predates the issue and is outside its Touches list. It is a candidate follow-up under the io-hardening outbound rule. The Gmail client has the same gap (see the gh-1505 handover).
