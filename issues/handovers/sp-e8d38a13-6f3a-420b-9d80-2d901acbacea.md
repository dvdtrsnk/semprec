# Handover: CalDAV change detection by ETags on servers without a sync-token

Implementation commit `900449c1d` on `feat/internet-accounts`. Nothing was sent to Purelymail or any other real server; every behaviour below was reproduced on the in-process fake CalDAV server.

**Root cause.** With no sync-token and no ctag (Purelymail answers both as a 404 propstat), every pass was a full fetch: `collectionVersion`, then `listEventHrefs`, a calendar-query `VCALENDAR > VEVENT` with the window's time-range, then calendar-multiget of everything it listed. That calendar-query is the only request in which the server filters, and Purelymail evaluates its VEVENT comp-filter only partly (empty without a time-range). An empty answer to the adapter's query explains everything seen on the dev server: a pass `applied` in 2 s with no upserts, and, since the fetch was full, the window's stored remote state dropped, so a later server-side deletion found nothing to delete. This is inferred, not proven. The fake server given exactly the curl-verified behaviour (time-ranged query answering) does not reproduce the empty answer: the old adapter then does see creations and deletions, but re-reads the whole calendar on every pass. Which detail of the adapter's query (the three-year range, its exact XML) Purelymail answers empty was not probed. The fix removes the dependency on any server-side filter for such servers.

**Design.**
- `fetchChanges(calendar, cursor, { window, signal, known })`. `known` holds the calendar's `event_remote_state` refs (remote id, href, ETag), read in the pass's prologue transaction by `listEventRemoteRefs` (one query for all tracked calendars). Google and Graph ignore it.
- CalDAV without a sync-token: an unchanged ctag is still no change. Otherwise `listResourceEtags` (PROPFIND `Depth: 1`, `resourcetype` + `getetag`; member collections and the collection itself are left out; a 507 member is `invalidResponse`, so a truncated listing never reads as deletions) lists the resources. Only a resource that is new, has no ETag, or whose ETag differs from its stored Events' (all of one resource's Events must carry that one ETag) is read by calendar-multiget in batches of 50. A stored Event whose resource is not listed, or that a re-read resource no longer holds (an override removed), is a deletion. The answer is `full: false`; upserted remote ids are never deletions. Hrefs are compared percent-decoded.
- A first fetch (no cursor) and a full fetch from the sync-token path read `collectionVersion` first; without a sync-token they reconcile by ETags, with one they keep the window's calendar-query. The sync-token path (iCloud, Fastmail, Nextcloud) is otherwise unchanged.
- Fake server: a calendar's members by PROPFIND `Depth: 1` with ETags, the 404 propstat for version properties it lacks, `ctagSupported`, `syncTokensSupported` (sync-collection answers only an empty token, listing everything with no token, and refuses others with 403), `eventFilterNeedsTimeRange`, `behaveLikePurelymail()`, and `requests[].hrefs` (what each multiget asked for). Its calendar-query also leaves out resources without a VEVENT when it has a VEVENT filter.

**Behaviour changes to know.**
- On a server without a sync-token, Events outside the one-year-back/two-years-ahead window are imported too. The listing has no window, and the incremental answer is not bounded by the window.
- The ctag-only path (a server with a ctag but no sync-collection) now reads only the changed resources when the ctag changes. It used to do a full calendar-query + multiget, and its test was updated to match.
- A resource that holds no Event (a VTODO, one `ical.js` cannot read) is stored nowhere, so every pass that lists the calendar reads it again by multiget.

**Tests.** `caldavAdapter.test.ts`: the Purelymail describe (first fetch by PROPFIND + multiget with no calendar-query or sync-collection; with unchanged ETags, only the two PROPFINDs; a table of create, change, delete and removed override, each found while reading only the touched resource and sending no GET), the updated ctag-only test, and a pass through `handleCalendarAccountSyncTask` on the Purelymail fake (server-side create → `added`, delete → `cancelled` with the Event trashed, then a pass without changes sends only PROPFINDs). The other 220 calendar sync tests pass unchanged.

**Verified.** In `backend/`: lint, format:check, `pnpm -r run build`, test:unit, check:write-safety, check:boundaries, plus the integration files for CalDAV and calendar sync (accountCalendars, calendarAccountSync, calendarChangeNotifications, calendarEventPush, calendarWebhooks, google/graph adapters, syncedInvitations, acceptInvitation, mailboxPasswordRoutes). `publicSurface.test.ts` fails on `ITEM_EVENT_BATCH_ACTION_IDS`. That export comes from another agent's uncommitted scheduler work in the same worktree, not from this change.

**Follow-ups (not built).**
- Purelymail may return a token from sync-collection with an empty token. That answer is unverified; if it does, storing the token would make passes incremental.
- The sync-token path still re-reads the window on a deletion or a changed series. With `known` it could be made incremental.
- Remembering resources that hold no Event, so they are not re-read.
- `fetchResources` claims "a resource gone meanwhile is left out". In fact `tsdav`'s collectionQuery throws a plain Error on a 404 member, so a resource deleted between the listing and the multiget fails the pass as `unexpected` (it is retried).
- Confirm on the dev server that the next Purelymail pass imports the server-side Events: PROPFIND + multiget in its log, no calendar-query.
