## What was delivered

Problems raised for a failed source now close when the source recovers, in the same transaction as the write that proves the recovery.

- Tick recovery: `finishTickRunWithMessage` (`semp/sempTickThreadStore.ts`) resolves `agents:heartbeat:<heartbeatId>` and `agents:run:<first run of the retry chain>` together with the run close and the message write, only when the reply left no failed tool call (the outcome of gh-1890). A done run whose reply left a failed tool call raises or merges and resolves nothing.
- Deterministic heartbeats: `recordHeartbeatHandlerSuccess` (`scheduler/sweep.ts`) resolves `agents:heartbeat:<id>` in the transaction of `recordHeartbeatSuccess` for every action except `core.agentRun`, on the item-event path and on the scheduled-occurrence path.
- Guidance drift: `GuidanceProblemWriter` gained `resolve()`. Every production path that ends a finding resolves its `guidance:<projectId>:<fingerprint>` problem as `recovered` through the shared `resolveGuidanceDriftProblem`: the permission and behavior passes of `driftAction.ts`, `resolveGuidanceDriftFinding` (allow, forbid and dismiss) and `saveGuidanceSections` when the guidance is emptied.
- Operators: `resolveOperatorAlertProblems` (`observability/operatorAlerts.ts`) resolves a key for each administrator inside that administrator's tenant. `recordRestoreTestResult` calls it for a passed run (`backup:restoreTest`); the process check calls it when `process:agents` goes from alerting to ok (`agents:process`).
- Library: `libraryMetadataJob` resolves `automation:<databaseId>` when a job completes an item (found or not found) and no non-deleted item of the database has an automation error left. The check and the resolve run after taking the problem key's advisory lock (`lockProblemKey`).
- `sourceDeleted` was added to the resolution kinds.

## Deviations and spec seams

1. The Task names `scheduler/actions.ts` for the run action; the done close of a tick goes through `finishTickRunWithMessage`, so the resolve is there and `actions.ts` is unchanged.
2. The issue names the process `semprec-agents`; the heartbeat table and check key are `process:agents`, as in gh-1465.
3. Library: resolved on both completion paths (found and not found); soft-deleted items with an error are not counted. The deleted-item shortcut paths of the job resolve nothing, and the `sourceDeleted` kind has no caller because the Task only adds the constant.
4. The `resolve()` method of `GuidanceProblemWriter` is required: the action reaches the problem store only through that port.
5. The tick close resolves the chain key `agents:run:<first run>` for a run with or without a predecessor (one recursive CTE per done tick, then an idempotent update). Today only heartbeat ticks form retry chains and their failure raises the heartbeat key, so the chain-key resolution is exercised by tests that raise a chain problem directly. Non-tick run closers (`lifecycleAdapter`, `delegationRegistry`, `startupRepair`, `sempConversation`) were not changed (not in Touches).
6. Beyond the Task as written, the fix round hooked the user's own decision (`resolveGuidanceDriftFinding`), the emptied-guidance path and deterministic heartbeats, because the Task says to hook the findings store "so every kind is covered" and the criterion is stated for any resolved finding.
