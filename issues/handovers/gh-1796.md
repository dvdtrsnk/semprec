## What was delivered

- `POST /api/calendar/items/:id/duplicate` (201, item envelope), body `{ date, timeFrom?, timeTo?, endDate? }` (strict), optional `Idempotency-Key` header (one header, at most 255 characters; empty means none).
- `duplicateCalendarItem(...)` (barrel export of `@semprec/data`, `calendar/duplicateCalendarItem.ts`): locks the source Event or Task row (404, identical to a random id, for an unknown, trashed, foreign-tenant or other-database id), returns the live copy of an earlier request with the same key, creates the copy through the choke point as the requesting user and copies the whitelisted live edges. The Event copy is created in the source's calendar (`withChosenCalendar` plus `createItemReportingReplay`); the Task copy is `notDone` without completion data, and a Task whose recurrence is active starts a new series (`createTaskRecurrence`, the copy's date as anchor). The invitation metadata of participant edges is dropped and the organizer role is kept. Everything runs in one transaction, so a failure while copying an edge leaves no item and no kept key.
- `createDuplicateCalendarItemRouteHandler` (barrel export), the `duplicateCalendarItem` entry in `customRoutes` of the systemDatabases manifest (justification `transactional-semantics`), the matrix entry `calendar item duplicate` in `routeMatrix/calendar.ts`, its handler-file mapping and its two-tenant isolation case.

## Contracts dependents build on

- Route: `POST /api/calendar/items/:id/duplicate` as above; the copy gets a new id (and a new `icalUid` for an Event); a two-day all-day Event moved to a new date keeps its length (`endDate` shifted, or taken from the body).
- Idempotency: the key is per tenant; a repeated key returns the first copy and copies nothing again; a key whose earlier copy is in the Trash makes a new copy; a request that waits for a first one with the same key copies nothing; a key used for an Event and then for a Task surfaces the choke point's 409.
- Task copy times: the body's `timeFrom`/`timeTo` when it names either, otherwise the source's; a body `endDate` for a Task is 400 on `endDate`. Event copy times come from the body only.
- No table, migration or job.

## Deviations from the specification and spec seams

1. The Task names `createEventInCalendar`; the Event copy uses `withChosenCalendar` plus `createItemReportingReplay`, the two parts it is built from, because `createEventInCalendar` returns only the row and cannot tell a lost idempotency race from a real insert (a second source's edges would be copied onto the winner's item). A source Event with no calendar edge gets the default calendar; a source whose calendar is no longer an own live calendar is refused 400 on `calendarId` by the create hook.
2. The "series-identity function of #1605" is `createTaskRecurrence`; the stored recurrence keeps the source's preset only when its mode and rule equal the active series row's.
3. The whitelist copies `timeFrom`/`timeTo` but the Decision takes date and times from the body; see the contract above.
4. The route entry is in the `routeMatrix/calendar.ts` slice per the slice seam.
5. `Events.area`, `Events.files` and `Events.company` exist in the seeded schema, so the test of a missing relation removes them in a fixture with raw SQL.
6. The commit trailers of the worker name Claude Sonnet 5.5 (the attribution the harness gave it).
