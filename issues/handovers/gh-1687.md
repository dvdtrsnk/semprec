# Handover for gh-1687

Replace the previous session of the same installation at login. Candidate commit `42dfd3d0c4dc7bf0ec4a00e3287da38d592cc600` (one segment of two commits: `bc5c49c0abe63158631077cfcc707dd2845efe3a` and the review fix `42dfd3d0c4dc7bf0ec4a00e3287da38d592cc600`) landed on `feature/backend-parallel` with merge `716453421eec18af0e1daea1e57692c6abbec787` (chain `p0-04-auth`). The acceptance receipt is `issues/batches/backend/acceptance/sources/gh-1687.md`.

## What was delivered

- A login whose `device` carries a `deviceId` replaces the earlier sessions of that installation. In its success transaction, after `lockUserTenantBinding` confirmed an active tenant and after `createSession`, `login` (`backend/packages/data/src/auth/authActions.ts`) calls `revokeSessionsForDevice` and then `revokePushSubscriptionsForSession` for every revoked id on the same client. The session insert, the revocations and the push-registration revocations commit or roll back together.
- `revokeSessionsForDevice(client, userId, deviceId, exceptSessionId)` in `backend/packages/data/src/auth/sessionsStore.ts` runs one statement, `UPDATE sessions SET revoked_at = now() WHERE user_id = $1 AND device_id = $2 AND id <> $3 AND revoked_at IS NULL RETURNING id`, registers `fireSessionRevoked` for each returned id (deferred to the commit through `runAfterCommit`) and returns the ids. Zero rows is a normal outcome and returns `[]`.
- Before it creates the session, `login` calls `lockSessionDevice(client, userId, deviceId)` from the new module `backend/packages/data/src/auth/sessionDeviceLock.ts`. It takes the transaction-scoped two-key advisory lock `pg_advisory_xact_lock(2334, hashtext('semprec_device:' || <user id>::uuid::text || ':' || <device id>::uuid::text))`. Of two overlapping logins of one installation the second waits for the first one's transaction to end and then revokes the session that one committed, so one active session per `(user, deviceId)` remains.
- A login without a `deviceId` revokes nothing: a web login (the handler's `parseLoginDevice` forces `deviceId` to `null` for platform `web`, whatever the body carries) and a native login that sends none. A rejected login (wrong password, lockout, non-active tenant) creates no session and reaches neither the lock nor the replacement.
- The decision is recorded in the new ADR `docs/adr/2026-11-10-login-replaces-the-sessions-of-its-installation.md` (scope of the replacement, one transaction, the lock, its class, the lock order and the consequences).

## Contracts dependents build on

- Invariant: when a login with a `deviceId` commits, the session it created is the only unrevoked session of that user and `deviceId`. It holds while every writer that creates a session with a `deviceId` calls `lockSessionDevice` before its insert. `login` is the only caller of `createSession` today; a new session writer must take the same lock.
- Export from the package index (`@semprec/data`, through `export * from "./auth/sessionsStore.js"`): `revokeSessionsForDevice(client: PoolClient, userId: string, deviceId: string, exceptSessionId: string): Promise<string[]>`. It takes a `PoolClient` only, the caller's `withTransaction` client, because it defers its realtime events to that transaction's commit. Its name is in the expected list of `backend/packages/data/src/__tests__/publicSurface.test.ts`, in JavaScript sort order between `revokeSessionForUser` and `revokeUserSession`.
- Not exported from the package index: `lockSessionDevice` and `SESSION_DEVICE_LOCK_CLASS` in `auth/sessionDeviceLock.ts`. `backend/packages/data/src/index.ts` is unchanged.
- Advisory lock class `2334` is claimed for the installation lock. The two-key classes in use are 2331 (`seed/seedSystem.ts`), 2332 and 2333 (`db/pool.ts`, search flush) and 2334 (`auth/sessionDeviceLock.ts`). The list exists in prose only: the comment above `SEARCH_FLUSH_TENANT_LOCK_CLASS` in `backend/packages/data/src/db/pool.ts`, the docstring in `sessionDeviceLock.ts` and the ADR. A source that adds a two-key class must take another number and extend that comment.
- Lock order of `login`: user row (`FOR KEY SHARE`) and tenant row (`FOR SHARE`) through `lockUserTenantBinding`, then the installation lock, then the replaced session rows, then their push-registration rows. Only `login` takes the installation lock. The ADR states why this cannot close a cycle with the admin mutations, which take the single-key membership lock before the user row.
- `login` must stay at READ COMMITTED. The second login's `UPDATE` sees the first one's committed session only because its snapshot is taken after the wait; the ADR records this.
- Scope of a match: the same user, the same non-null `device_id`, not yet revoked, not the new session. Another user's sessions with the same `deviceId` and sessions without a `deviceId` are never matched. Both spellings of one `deviceId` (upper and lower case) take the same lock key, because both ids are cast through `uuid`.
- Effects a client sees for the replaced session: its token answers 401, its push registrations are revoked, and its open sync socket is closed with 4401 after the commit. `GET /api/auth/sessions` lists one entry per `deviceId` after repeated logins.
- Sessions that already share a `deviceId` are not cleaned up by a migration. The next login of that installation revokes all of them.
- No route, no response field, no table, no migration, no generic operation, no job name and no hook was added or changed.

## Deviations from the specification and spec seams

1. Lock form. The Task writes the single-key expression `pg_advisory_xact_lock(hashtext('semprec_device:' || $1 || ':' || $2))`. The code takes the two-key form with the class 2334. Reason: the single-key form shares its key space with `hashtext('semprec_admin_membership')`, which the admin mutations take before the user row, and the client chooses the `deviceId`; a chosen value could make a login and a suspension, role change or account deletion deadlock. Two reviewers reported this at medium severity and the fixer reproduced the deadlock with a test before the fix. The Task's intent is kept: transaction-scoped, keyed on the user and the `deviceId`, taken before `createSession`. The deviation is declared in the ADR and in the fix commit message.
2. Lock key text. Both ids are cast through `uuid` (`$n::uuid::text`), because the login handler's `assertUuid` accepts any letter case and does not normalise, while `device_id` is a `uuid` column. With the raw text two spellings of one `deviceId` would match the same rows under different lock keys.
3. `revokeSessionsForDevice` accepts a `PoolClient` only, while its siblings accept `Pool | PoolClient`. Its only caller is the login transaction and the Task asks for commit-deferred events. It reads `result.rowCount`, which `check:write-safety` requires.
4. Files outside `Touches`: the ADR, `auth/sessionDeviceLock.ts` and the comment in `db/pool.ts`. The ADR was added because the Task introduces a new lock and a session-ownership contract no existing ADR covers; the other two came with the review fix.
5. Harness. The Task names none. The new cases run `login` on a `semprec_data` runtime-role pool (the data layer inside `runAsSystem`, HTTP through the auth listener). The HTTP cases are a new top-level describe with its own server and socket helpers; the helpers of the #1650 describe are scoped to that describe and were left untouched, so some helper code is similar in both.
6. An extra failure-path case fails the login transaction after the replacement with a temporary test trigger on `login_attempts` (constant body, dropped in `finally`), following the precedent in `pushSubscriptions.test.ts`.
7. Spec seams: none reported by the worker; every file and symbol the issue names is where it says.
