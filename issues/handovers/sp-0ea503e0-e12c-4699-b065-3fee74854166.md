# Handover: take invitations from synced calendars and answer them through the provider

Implementation commit `f4d4fead0` on `feat/internet-accounts`.

**What changed.**
- Adapter contract (`calendar/sync/adapter.ts`):
  - `RemoteEvent` has three optional fields: `icalUid`, `sequence` and `selfStatus`. `selfStatus` is the account's own answer when the provider reports it apart from `attendees`.
    - Google sets `iCalUID`, `sequence` and the `responseStatus` of the attendee marked `self`.
    - Graph sets `iCalUId`, and `responseStatus.response` unless `isOrganizer`. Graph has no sequence.
    - CalDAV sets `UID` and `SEQUENCE`. It reports no `selfStatus`, so the attendee is found by address.
  - The apply validates the three fields strictly. `snapshotOf` stores them in `base_snapshot` when they are present, so a change of the account's answer alone counts as a change. The push job keeps them from the old base.
  - New required method `respondToInvitation(calendar, ref, { response, attendeeEmails }, signal)` returning `"answered" | "gone"`. I chose this over reusing `putEvent` with an attendee patch, because `putEvent` carries no participants and each provider answers in its own way:
    - Google: `PATCH events/{id}?sendUpdates=all` with `{ attendees: [<own attendee, new responseStatus>], attendeesOmitted: true }`, so the other attendees stay as they are. The own attendee is the one marked `self`, else the one with an account address. 404/410 is `gone`.
    - Graph: `POST /me/events/{id}/accept|tentativelyAccept|decline` with `{ sendResponse: true }`. 404 is `gone`.
    - CalDAV: GET the resource, set `PARTSTAT` and drop `RSVP` on every `ATTENDEE` with an account address (series and overrides), then PUT with `If-Match` (`setAttendeeParticipation` in `caldavIcal.ts`). The server's scheduling is what replies. A 412 is a `CalendarSyncEventConflictError`, which is rethrown and retried.
    - A provider with no matching attendee throws `CalendarSyncWriteUnsupportedError`.
  - `InvitationResponse` type. `FakeCalendarProvider` implements `respondToInvitation` and records `responses`.
- New `calendar/sync/syncedInvitations.ts` (`reconcileSyncedInvitations`, `accountOwnAddresses`). `applyCalendarSync` calls it after its Event writes and before `notifyCalendarChanges`.
  - Candidates: Events the pass created or updated, or whose snapshot changed without a field write (new `unchanged.restated`). An Event whose snapshot equals the stored one is never looked at.
  - What counts as an invitation: a master or single Event (overrides are skipped) whose organizer is not one of the account's addresses, and whose own status is NEEDS-ACTION.
    - The account's addresses are `Mailboxes.addresses` plus a password account's login name when it is an address, normalized.
    - The own status mapping: `NEEDS-ACTION`, `needsAction`, `notResponded`, or a matched attendee with no `PARTSTAT` (the iCalendar default). Answers: `accepted`; `tentative` / `tentativelyAccepted`; `declined`. Anything else (`DELEGATED`, Graph `none`/`organizer`) is not an invitation.
  - New invitation, under the same `invitationUid:` advisory lock as the iMIP ingest:
    - Properties: `kind` `invite`, `status` `pending`, `uid` = `icalUid` (else the remote id), `sequence`. The fields use the iMIP formats: UTC instants; an all-day day as its midnight UTC, with `endsAt` its last day.
    - Edges: `event`, `mailbox` (the account) and `suggestedCalendar` (the Event's calendar).
    - An existing invitation with that UID that has no `event` edge (one an e-mail delivered earlier) is adopted by linking the Event to it. One that is trashed, or linked to another Event, is left alone and nothing is created.
  - Notification `calendar_invitation`, written through the shared `notifyInvitation` (exported from `invitationIngestAction.ts`):
    - `transition_instance` is `sequence:<n>`, so there is one per invitation and SEQUENCE.
    - Nothing is notified in the account's initial sync.
    - An Event whose invitation was notified gets no `calendar_event_added`/`changed` notice in the same pass, so the user is not notified twice. `calendar_event_cancelled` is kept.
  - An existing invitation follows the Event:
    - Its fields are updated.
    - NEEDS-ACTION at a higher SEQUENCE makes an answered or cancelled invitation `pending` (`respondedAt` null) and notifies it again.
    - A `pending` invitation that the provider shows as answered takes that answer, and its notification is resolved.
    - An answer given here while the provider still shows NEEDS-ACTION is kept, because its job is sending it.
  - Cancellation: an Event that the apply trashes because the provider deleted it sets a `pending`/`accepted`/`tentative` invitation to `cancelled` and resolves its notification. The Event is trashed by the existing apply path. A `declined` invitation stays declined, because Graph removes a declined meeting from the calendar.
- New job `calendar/sync/invitationRespondJob.ts`:
  - Task `calendarInvitationRespond` (core task, `api`, tenant), key `calendar-invitation-respond:<invitation>`, replaced by a newer answer, 5 attempts. Registered in `@alldots/queue` and `worker.ts`, which passes `isFinalAttempt`.
  - A read transaction plans the call. It ends `superseded` unless the invitation still holds the payload's status and `respondedAt`. It needs the Event's remote state and an endpoint (`endpointOf`, now exported from `eventPushJob.ts`).
  - The adapter call runs with no transaction open and a 60 s deadline.
  - On success a pass is queued, which brings the answer back.
  - `gone`, `CalendarSyncWriteUnsupportedError`, a missing remote state or account, or the queue's last attempt: the invitation goes back to `pending` (`respondedAt` null), but only while it still holds that answer. This is logged as a warning with a reason code.
  - Reauthorization or consent errors also record the account's status and Semp problem (`recordCalendarAccountFailure`). Every non-final failure is rethrown so the queue retries it.
- Respond route (`invitationRouteHandlers.ts`, `POST /api/calendar/invitations/:id/respond`, also used by the agent tool):
  - When the linked Event is held by an account calendar (`getEventAccountCalendar`), the route writes only `status`/`respondedAt`, resolves the notification and queues `calendarInvitationRespond` in the same transaction. It answers 200 with the new local status.
  - The Event is not trashed, restored or created, and no `calendarSendInvitationReply` (iTIP e-mail) is queued.
  - If that Event has no remote state any more, the route answers 409 `conflict`.
  - Every other invitation keeps the e-mail path unchanged.
- iMIP ingest (`invitationIngestAction.ts`): inside its transaction, after the Emails row lock, it reads the receiving mailbox `FOR SHARE`. With Calendars on it writes nothing and logs `calendars_synced`. The REPLY action (organizer side) is unchanged.
- Agent tool description: the answer goes "by email or through the internet account's calendar provider".
- Doc: `docs/architecture/domain-calendar-tasks-and-media.md`. A new "Invitations" bullet in the sync section, plus the Tenancy and Apply (`base_snapshot`) bullets.
- No schema change. No new Invitations field: the existing `event`, `mailbox`, `suggestedCalendar` relations, `uid` and `sequence` are enough. The seed is untouched.

**Tests.**
- New `__tests__/syncedInvitations.test.ts`: 18 tests, runtime-role pool, fake provider. They cover:
  - A Google-shaped invitation gives one Invitations row (fields, `event` and `mailbox` edges), one Event and one timeline item. It gives exactly one `calendar_invitation` (`sequence:0`) and no `calendar_event_added`. An unchanged pass and a full re-read add nothing.
  - Initial sync: the row is written without a notification.
  - No invitation (table of 4): the account is the organizer, the account already answered, the account is no attendee, there is no organizer.
  - A CalDAV-shaped attendee is matched by address case-insensitively, and no `PARTSTAT` counts as NEEDS-ACTION.
  - Accept: the route answers `accepted`. The respond job is queued and no reply e-mail is queued. The job answers through the provider with the account's addresses, queues a pass, and the next pass keeps the invitation and the Event.
  - Decline: the Event is not trashed by the route. A provider that then removes the Event leaves the invitation `declined`.
  - The organizer cancels: the invitation is `cancelled`, the Event is trashed, the notification is resolved, and `calendar_event_cancelled` is kept.
  - Answered at the provider: the invitation follows. A higher SEQUENCE asks again (`pending`, a second notification `sequence:1`, new times).
  - A local answer is kept while the provider still shows NEEDS-ACTION.
  - Back to pending (table of 2): the provider no longer has the Event; a provider failure on the final attempt.
  - A non-final failure is rethrown with the answer kept, and the retry succeeds.
  - 409 for a synced Event that was trashed here and deleted at the provider by its push.
  - The same iMIP e-mail with Calendars on gives 0 invitations and 0 notifications, and with Calendars off 1 (the allowed side).

**Deviations and seams.**
- **Decline keeps the Event.** For a synced invitation the route leaves the Event to the provider, unlike the e-mail path, which trashes it. Google and CalDAV keep a declined meeting, so it stays in the timeline. Graph removes it, so the next sync trashes it. I did this to avoid writing the Event as the sync from a user route, and to avoid a local trash pushing a provider delete.
- **Answers given at the provider** are mirrored only from `pending`. An invitation answered here is not overwritten by a different provider answer, because the job state cannot tell "in flight" from "changed elsewhere later".
- **Graph has no SEQUENCE**, so a Graph meeting change never asks again.
- **CalDAV `STATUS:CANCELLED`** is not mapped by the CalDAV adapter. A server that keeps the cancelled VEVENT instead of deleting it does not cancel the invitation. Item 4 is delivered for deletions, which is how Google (`status: cancelled`, listed as a deletion) and Graph (`isCancelled`) report a cancellation.
- **Pre-existing write-back bug, not fixed here.** `defaultCalendarCreateHook` creates the `Events.calendar` edge without the sync's writer. So `eventPushEdgeChangedHook` records a `create` push for every Event a later sync pass adds. Its job finds the remote state and ends `sent` without a provider call. Until that job runs, a pass leaves the Event alone (pending push), and its invitation is updated one pass later. The new test drains these pushes after each pass, as the queue does. Proposed follow-up: pass the writer through to the edge in `defaultCalendarCreateHook`.
- **Lock order.** The apply holds Event rows, then takes the `invitationUid:` advisory lock and the invitation row. The iMIP ingest holds the advisory lock and may lock an invitation's linked Event. These can only meet when the same meeting arrives by e-mail at a second account with Calendars off and its invitation was adopted by the sync. Postgres would then abort one of them as a deadlock, and the queue retries it.
- The first pass after deployment rewrites `event_remote_state.base_snapshot` of synced Events whose provider now reports the new fields (no item writes, no notifications). Events that did not change get no invitation until they change.
- Touches beyond the list: the adapters and their mappings, `adapter.ts`, `eventPushJob.ts` (snapshot carry-over, `endpointOf` export), `calendarSyncApply.ts`, `invitationRespondJob.ts`, queue `index.ts`, `worker.ts`, the fake, `calendarAgentTools.ts` (description), the doc, and the test expectations.

**Open items (only real providers can confirm).**
- Google:
  - `attendeesOmitted: true` with only the own attendee updates just that response and keeps the guest list.
  - `sendUpdates=all` on an attendee's patch sends the organizer the reply.
  - `self` is present on the attendee's copy.
- Graph:
  - `calendarView/delta` returns `iCalUId`, `isOrganizer` and `responseStatus`.
  - `accept`/`decline` on an event of a non-default calendar through `/me/events/{id}`.
  - A declined meeting leaves the calendar.
- CalDAV (iCloud, Fastmail, Nextcloud): a PUT that changes the attendee's `PARTSTAT` triggers the server-scheduled REPLY (RFC 6638), and the server accepts it with `If-Match`.
- Clients: no client change. The invitation rows and `calendar_invitation` payload are as before.
