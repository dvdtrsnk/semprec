# gh-1861 handover: Let Semp read and write Journal periods

Delivered on the integration branch by merge `14a0e2214f2f3c46ca736f680addfc5617c45d1f` of chain `e1-095-shared` (members gh-1844 and gh-1861, landed together), candidate `15431c339a0a3211535eb62af5d9e0c24136cffe`. The merge was automatic, with no conflict and no migration.

## What was delivered

A new catalog operation `page.ensureJournalPeriod` lets the assistant create (lazily, idempotently) the Journal entry of a period and then write to it through the existing page operations.

- Input (strict zod): `{ type, date | period }`, `type` an enum of the Journal period types, exactly one of `date` (ISO calendar date) and `period` (period key). Output `{ itemId, docId, period, range }`.
- `ensureJournalPeriodForWriter` (`backend/packages/data/src/journal/journalPeriodForWriter.ts`, exported from the `@semprec/data` barrel) checks the agent project's write access to the Journal database first (so a malformed period is also a 403 for a read-only project), turns a date into the period key of that type in the system time zone (the week containing 2026-10-16 is `2026-W42`) and delegates to `ensureJournalPeriodDoc` (the lazy creation of gh-1541). A malformed or non-existent period or date is a 400; an existing live entry is reused, so no second entry is created. All of it runs in one transaction.
- The operation is in the catalog (now 47 operations) with the port method, the binding in `bindings.ts`, metadata `core.item.write` and `requiresApproval: false`, and the application service method. Its AgentTool name and its `semprec.`-prefixed MCP name come from the one catalog entry and resolve to the same handler.
- ADR `docs/adr/2026-11-13-journal-periods-reach-the-assistant-through-the-page-family.md` records variant (a): Journal periods are reached through the page family.

## Tests

Covered by `journalPeriodForWriter.test.ts` (date to period for each type, existing live entry reused, malformed period refused, read-only project refused before anything is created, tenant keeps its entries to itself on a runtime-role pool with two tenants) and `genericOperationJournalPeriod.test.ts` (week of 2026-10-16 created as `2026-W42`, the agent's text appended after a person's earlier block, update authors `user` then `ai_agent`, no approval request; period by key and by date return the same entry; 400 for unknown type, malformed or non-existent period, a date that is no day, and neither or both of date and period; 403 with the sensitive Journal and a read grant, served with a write grant). The AgentTool, MCP and gateway names are proven in their own packages. The tenant-isolation MCP case seeds the 2026-10-16 day entry for both tenants, requires the second tenant's own ids and excludes the first tenant's.

## Deviations and spec seams

- The Touches say `journal/` is "export only"; the date-to-period conversion and the Journal grant check had to run in one data-layer transaction (ADR 2026-09-17), so a small sibling module `journalPeriodForWriter.ts` was added and exported from the barrel.
- No REST route was added (out of scope).
- The generated JSON schema cannot express "exactly one of date and period" (`superRefine`); the strict shape and the 400 message carry it.
- Stale "46-operation" wording remains in a few comments (`genericApplicationService.ts`, `itemsHandler.ts`, test docblocks); not corrected.

## Not run, BLOCKED

- BLOCKED: the literal acceptance criterion "when a run's project has the Journal restricted to read, the call returns 403 forbidden" (a read row on the shipped, non-sensitive Journal). Same limit as gh-1844: the delivered grants model ignores rows on a non-sensitive system database, so a read row cannot restrict the shipped Journal. The same code path is proven with the Journal flagged `sensitive` and a read grant. It stays unproven for the shipped Journal until the owner decides (see the gh-1844 handover).
- The whole `pnpm run verify` integration tier is not part of this landing; the known macOS baseline case of `mcpConnectionFactory.test.ts` was not run.
- No live provider or production criterion exists.
