# gh-1479 implementation handover

Implementation base: `ec41851e0de8339efcfb07ef0c83e08f799fd8ee`.

## What changed

- `proposalEnvelopeSchema` (`backend/packages/data/src/inbox/inboxTickAction.ts`) has an optional
  `operations` array of steps (`ref`, `op`, `databaseKey` | `itemId`, `properties`, `relations`, `role`,
  `optional`, `enabled`, `before`, `after`). A relation target in a step is an item id or `{ ref }`. All
  step fields except `ref`, `op` and `role` are optional; an absent key stays absent, so single-step
  envelopes parse and stringify byte for byte as before. `ProposalStep` is exported as a type only;
  the step schema is not exported (the public surface is unchanged).
- `before` is `{ properties?, relations? }` (relations as id lists); `after` is the same with the target union.
- `assertValidProposalEnvelope` validates `operations` first (then the top level as before):
  entityKind must be `database`; refs unique and non-empty; exactly one `primary`, which cannot be
  disabled and must be a `create` or `update` step whose database equals the envelope `target` and whose
  `properties` deep-equal the envelope's; `{ ref }` targets must name another step; no cycle among active steps.
- Skipping: `enabled: false` steps and optional (non-primary) steps that no active step refers to, or that
  refer to a skipped step, are dropped (to a fixed point) and not validated. A required step referring to a
  skipped or missing step is a `ValidationError`.
- Per step: `create` resolves `databaseKey` through the new `databasesStore.getDatabaseByKey`, requires an
  unarchived, non-read-only database, and runs the single-step checks (MCP server properties, writable
  property keys, relations with `{ ref }` targets skipped). `update`/`link` need an existing `itemId`, the
  item's database must be writable, relations go through `assertRelationTargetLinkableWithClient` (targets
  already listed in `before.relations` are not re-checked for cardinality), a `link` step cannot write
  properties, and an `update` step needs every changed property and relation key in both `before` and `after`.
- Failures carry `details: { ref, field }`. Failures from the shared checks (validation, forbidden,
  cardinality) are re-raised with the step `ref` added.
- The property key rules of the single-step branch were extracted into `assertWritableProposalPropertyKeys`
  and are shared.

## Notes for dependants

- `before` is checked for the presence of the changed keys, not compared to the item's current value;
  confirm (#1486) should re-check under the row lock if it wants a stale-edit guard.
- Property value types are not checked beyond what the single-step envelope checks (key rules); the
  choke point's value checks run at write time on confirm.
- Required and hidden fields per step are not validated (editor schema work).
- A `link` step cannot be primary; the primary mirrors the envelope as `entityKind: "database"`.
- The tick (#1492) does not produce `operations` yet; nothing writes steps (#1486).
