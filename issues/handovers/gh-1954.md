## What was delivered

A newly created pending calendar invitation now notifies the tenant's user once, in the same transaction as the invitation. The push carries the APNs category `CALENDAR_INVITATION` and the invitation id so the app can offer Accept, Maybe and Decline. Answering the invitation resolves the notification (and queues the silent dismiss push), and `pendingInvites` of the badge counts is now the real number of live pending invitations of the tenant.

## Deviations from the specification and spec seams

1. `NotificationPushPayload` already carried an `apns` object (issue 1831), so the optional apns category of the Task is `NotificationApnsFields.category` and the custom data is the new `NotificationApnsFields.data`; the fan-out sets `invitation_id` from the notification's `source_id`, only for source table `items`.
2. The invites policy has no severity field, so the Task's "lowest severity" has nothing to set.
3. The Task gives no fallback for a missing organizer or summary; they render as an empty text (tested).
4. A tenant with no bound user: the invitation is created and the skip is logged (`no_tenant_user`), no notification.
5. `pendingInvites` is counted by the new `countPendingInvitations` (not named in Touches) and wired in `loadBadgeCounts` (gh-1891), not in `badgeCountsRoute.ts`; the count is kind-agnostic (status pending, live).
6. Two existing tests were brought in line: `notificationKindPolicy.unit.test.ts` (pushed kinds now include `calendar_invitation`) and the `tenantIsolationRoutes.test.ts` case "badge counts" (asserted `pendingInvites` 0, now deltas with case-specific invitations).
7. `enqueueBadgeRefresh` (gh-1891) is not called when an invitation is created or answered (not in the Task), so the app icon badge changes only with the next visible push or refresh.
