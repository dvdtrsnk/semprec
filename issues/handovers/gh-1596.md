# Handover for gh-1596

## Summary

Every pooled connection now runs in UTC and date-only comparisons no longer depend on a time zone.

- `db/pool.ts`: `createPool` always passes the startup option `-c TimeZone=UTC`, combined as `-c TimeZone=UTC -c role=semprec_data` when the `role` option is set.
- `views/filterCompiler.ts`: `dateComparisonCast` picks `::date` when every operand of `before`, `after`, `on_or_before`, `on_or_after` and `date_range` is a `YYYY-MM-DD` string (the stored property is cast to `::date` too), otherwise `::timestamptz` as before. A `date_range` with one date-only and one datetime bound uses `::timestamptz`.
- `views/sortCompiler.ts`: `castSortKey` wraps a `::timestamptz` sort key (date properties, earliest/latest rollups) as `CASE WHEN x ~ '^\d{4}-\d{2}-\d{2}$' THEN x::date::timestamp AT TIME ZONE 'UTC' ELSE x::timestamptz END`, in both `ORDER BY` and the keyset cursor side. `sortKeyCast` itself is unchanged (`viewQuery.ts` still uses it for cursor validation).

## Tests

New `__tests__/dbTimeZone.test.ts`: `SHOW TimeZone` is `UTC` for the plain and the `role` pool; filters (date-only before / on-or-after / one-day range, datetime with offset) and asc/desc date sorts return identical rows with the test database session set to UTC, `Pacific/Auckland` and `America/Los_Angeles`. Existing view tests pass unchanged.

## Notes for dependants

- A stored date-only value compared with a datetime operand is still read as an instant in the session zone, which is now UTC (the decision in the issue). A stored datetime compared with a date-only operand is compared by its own written date (`::date` ignores the offset).
- The date-only sort branch uses `AT TIME ZONE 'UTC'` on purpose: a plain `date::timestamptz` would use the session zone and break the zone independence.
- No migration, no database-level `ALTER DATABASE ... SET TimeZone` was added; only connections made through `createPool` are pinned.
