## What changed

- **`sortCompiler.ts`**
  - The `(properties ->> $key)::cast` expression is now built by one private helper, `sortKeyExpression`. Both `compileSort` and the new `compileSortKeyset` use it, so the sort order and the paging condition always compare the same expression.
  - `compileSortKeyset` builds the "rows after this cursor" condition for the `ORDER BY` that `compileSort` produces (every key `NULLS LAST`, then `id ASC`):
    - A non-null cursor value is followed by greater values (`asc`) or smaller values (`desc`), then by all nulls.
    - After a null value, nothing on that key comes later; ties are matched with `IS NULL`.
    - Each cursor value is bound as JSON and read back with `#>> '{}'` before the key's cast. The comparison therefore uses exactly the text `properties ->> key` gives for the stored value, including select values and other non-numeric keys.
    - Every value is a bound parameter; nothing from the cursor is put into the SQL text.
- **`itemsStore.listItems`**
  - `ListItemsOptions` gains `keyset: { buildAfterSql, encodeCursor }`. When it is set, it replaces the `id > $cursor` condition and builds `nextCursor`, and `options.cursor` is ignored.
  - The options comment now says a custom order pages through `keyset`.
  - `nextCursor` is still `null` on the last page.
- **`viewQuery.ts`**
  - A sorted page's cursor is `base64url(JSON.stringify({ v: [sort values of the last row], id }))`.
  - `queryItemsCore` decodes it and throws `ValidationError('Invalid cursor', { field: 'cursor' })` in these cases:
    - the token is malformed;
    - `v` is not an array, or its length differs from the number of sort keys;
    - `id` is not a UUID;
    - a value would fail its key's `::numeric` / `::timestamptz` cast. This turns a foreign cursor into a 400 rather than a SQL cast error.
  - Only a `SyntaxError` from `JSON.parse` is turned into the validation error; anything else is rethrown.
  - Unsorted queries keep the plain item-id cursor and `parseCursorInput`'s UUID check.

## Deviation from the issue

`keyset.buildAfterSql` returns `string | undefined` rather than `string`. The first page of a sorted query has no cursor, so there is no condition to add. This matches the existing `buildFilterSql` and `buildOrderBySql` hooks.

## Tests

New integration test `backend/packages/data/src/__tests__/viewQueryPagination.test.ts`, using 7 items with `number`, `date` and `select` properties, some of them null:

- **Number sort, `asc` and `desc`**, `limit: 3`: paging through the cursors matches the unpaged order exactly, with no duplicates or gaps, and nulls come last in both directions.
- **Date sort, `asc` and `desc`**: same check, with null dates last.
- **Stored view with `groupBy` on the select plus `due desc`**: paged both through `queryViewItems` (the request route) and through `queryView` (the view's own page).
- **Tampered cursors are rejected** with 400 `validation_failed` and `{ field: "cursor" }`: garbage text, a raw item id, a non-object payload, a wrong-length `v`, a non-UUID `id`, a non-array `v`, a non-numeric value for a number key, and an unparseable date.
- **Limit cap**: `limit: 500` is capped to 200, `nextCursor` is non-null when 202 rows match, and the second page returns the remaining 2.
- **Unsorted query**: the cursor is still the last item id.
