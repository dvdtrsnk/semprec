# Handover: sign in to Google and Microsoft from iOS

Implementation commit `3a8922f47` on `feat/internet-accounts`.

**What changed.**
- `:shared:domain` (`InternetAccounts.kt`): `OAuthProvider` (GOOGLE, MICROSOFT), `OAuthSignIn(authorizeUrl, state)`, `OAuthOutcome` (`Connected(accountId)`, `Declined`). `InternetAccountRepository` gains `startSignIn(provider, services)`, `startReauthorization(accountId, services)` and `finishSignIn(signIn, callbackUrl)`.
- `:shared:data` (`HttpMailboxRepository`):
  - `startSignIn` posts `oauth/start` with `provider` (`gmail`/`outlook`), `services` (Mail always added) and `redirectTarget: "app"`.
  - `startReauthorization` posts `:id/reauthorize` with `redirectTarget: "app"`. It sends `services` (Mail added) only when it is asked for more; an empty set lets the server renew what the account has.
  - Both read `state` from the returned `authorizeUrl`. A URL without a state is `INVALID_DATA`.
  - `finishSignIn` parses the callback with ktor's `parseUrl`. It needs scheme `semprec`, host `oauth` and the same `state`, or it returns `INVALID_DATA` without sending anything. An `error` parameter is `Declined`, also without sending anything. Otherwise it posts `oauth/complete {state, code}`. A 400 or 409 is `REJECTED`.
- `:shared:presentation`: `BrowserSignInFlow` (internal) runs one sign-in at a time. It starts the sign-in and emits the page through `open`. It keeps the `OAuthSignIn` until the browser reports back, ignores late or repeated answers, and finishes the sign-in. Both ViewModels use it.
  - `InternetAccountsViewModel`: `SignIn.Start(provider, calendars)` / `Returned(callbackUrl)` / `Cancelled` / `Failed`, effect `OpenSignIn(url)`. It reuses `connecting` and `connectFailure`; `InternetConnectFailure` gains `DECLINED`. Success emits `Connected` (the sheet closes) and reloads the list.
  - `InternetAccountViewModel`: `SignIn.Again` / `AllowCalendarAccess` / `Returned` / `Cancelled` / `Failed`, effect `OpenSignIn(url)`, state `signingIn` and `signInFailure` (cleared by `DismissFailure`).
    - `InternetAccountDetail` gains `signsInInBrowser` (provider `gmail`/`outlook`) and computed `canSignInAgain` (Mail or Calendars NEEDS_REAUTHORIZATION) and `canAllowCalendarAccess` (Calendars NEEDS_CONSENT). The actions run only while these are true.
    - Again asks for no extra services. AllowCalendarAccess asks for mail+calendars. Success reads the account again.
- Apple:
  - CoreKit models and bridges mirror all of the above. The detail action is `.signIn(InternetAccountSignIn)` (nested, to keep the mapping under SwiftLint's complexity limit). The list uses flat `.startSignIn` / `.signInReturned` / `.signInCancelled` / `.signInFailed`.
  - Account feature: `BrowserSignIn` (`Sources/Extensions`) wraps SwiftUI's `webAuthenticationSession` environment value (`authenticate(using:callback: .customScheme("semprec"))`). Outcomes:
    - the callback URL comes back as `.returned`;
    - `ASWebAuthenticationSessionError.canceledLogin` or `CancellationError` is `.cancelled`;
    - any other error, or an address that is no URL, is `.failed`.
  - The view that starts a sign-in builds the `BrowserSignIn` from its own environment, so the browser sheet is anchored to that view's window. It hands the `BrowserSignIn` to the feature ViewModel, which uses it when `openSignIn` arrives. There is no UIKit and no `#if`.
  - `AddInternetAccountSheet`: Google and Microsoft push `InternetAccountSignInForm`, which has Mail (fixed on), a Calendars switch (on by default) and a "Sign in" button. The "next update" alert and its key and identifier are removed.
  - `InternetAccountScreen`:
    - "Sign in again" sits in the reauthorization section. A browser account gets its own text without "on the web"; password accounts keep the web text.
    - "Allow calendar access" sits under the needs-consent notice.
    - A sign-in failure alert is shown.
  - `AuthenticationServices` is added to `apple.systemModules` in the architecture policy.
- App: `CFBundleURLTypes` registers the scheme `semprec` (Project.swift). There is no `onOpenURL`. The `mobile/docs/architecture.md` table row says so.
- Copy (Account catalog, en+cs, policy updated):
  - new: `internetAccounts.add.signIn.hint`, `internetAccounts.add.signIn.submit`, `internetAccounts.add.error.declined`, `internetAccount.signInAgain`, `internetAccount.allowCalendars`, `internetAccount.reauth.signIn`;
  - changed: `internetAccount.consent` (no longer "on the web");
  - removed: `internetAccounts.add.oauthLater`.
- Identifiers: `internetAccounts.addSheet.signIn.calendars`, `internetAccounts.addSheet.signIn.submit`, `internetAccount.signInAgain`, `internetAccount.allowCalendars`. `internetAccounts.addSheet.oauthNotice` is removed.

**Deviations and seams.**
- macOS: the Task puts macOS sign-in out of scope, but the code is one SwiftUI codebase without platform branches. The macOS app gets the same flow. It compiles but was never run.
- After "Allow calendar access" the server reports `calendarStatus: pending` (shown as "Starting", PENDING) until the calendar sync engine reports its own status. The acceptance criterion's "syncing" holds once the engine reports `never`/syncing. The client shows whatever the server returns after the re-read.
- The server's error codes are not exposed past `FailureKind`. Wrong account, an already connected account, admin consent and an expired state all show the generic "refused, or already connected" text.
- A provider error (`&error=`) is reported as DECLINED, with no request to the server. The unused state expires on the server.
- Not in Touches: `BrowserSignInFlow.kt` (detekt function limit), `InternetConnectFailure+Message.swift` (shared by the form and detail), `architecture-policy.json`, `mobile/docs/architecture.md`.
