## What was delivered

- `GET /api/mail/threads` answers a real `hasSempDraft` for each row. It is true when the thread has a Semp draft: a `mail_drafts` row of this tenant with `created_by = 'agent'` and `sent_at IS NULL`, whose `email_item_id` is a not-deleted item of the Emails database. A draft of the user, a sent draft, a draft whose item is in the trash and a draft without a thread never count.
- A draft belongs to the thread its `thread_id` names and, after that thread is merged away, to the thread that absorbed it. `reassignThread` does not re-point `mail_drafts.thread_id`, so the predicate matches the thread's own id or the `from_thread_id` of an alias in `mail_thread_aliases` whose `to_thread_id` is the thread. Aliases are one step, so one lookup also covers repeated merges.
- `GET /api/mail/threads?box=sempDrafts` is accepted and returns the threads that have a Semp draft and a counted message outside Junk and Trash. The box predicate sits in the same place of the list's predicate list as `inbox` and `flagged`, so it is combined with `unread`, `mailboxId`, the relation filters and the search as they are, and a `folderId` replaces it as it replaces the other boxes (gh-1633). A test covers the combination with `unread` and with `folderId`; the other combinations follow from the code and have no test of their own. Any other `box` value still answers 400 with `details.field` equal to `box`.
- `GET /api/mail/summary` answers a real `sempDrafts`: the number of threads `box=sempDrafts` returns (threads, not drafts). It is no longer the constant 0 of gh-1688.
- The flag is an `EXISTS` expression in the final `SELECT` of the list's single statement, evaluated for the rows of the page, so a page costs no extra statement. The box filter and the summary count use the same predicate over the same `copies` and `copy_stats` CTEs, one statement each.

## Contracts dependents build on

- `mailThreadHasSempDraft(threadId)` in `backend/packages/data/src/mail/mailThreadPredicates.ts` is the one definition of "the thread has a Semp draft". It takes the closed union `"l.thread_id" | "p.thread_id"` and reads the query's `schema_ids` CTE, so it can only be used inside a statement built on `mailThreadCopyCtes`. `mailThreadPredicates.sempDrafts` is that predicate plus the Junk and Trash rule. The list row, the box and the summary count all follow from this one function.
- `MailThreadFilters.box` is now `"inbox" | "flagged" | "sempDrafts"`.
- Response shapes: the thread list row keeps its field set, `hasSempDraft` is now a boolean that can be true (the row schema is `z.boolean()`, before `z.literal(false)`). The summary keeps its five fields; `sempDrafts` is an integer from the statement.
- gh-1941 (creating Semp drafts) makes a thread appear here by inserting a `mail_drafts` row with `created_by = 'agent'`, the thread id and an Emails item; nothing else has to be written. gh-1902 (retiring a draft) removes it from the flag, the box and the count by soft-deleting the draft's item or by marking the draft sent; the `mail_drafts` row may stay.
- A thread whose messages are all in Junk or Trash keeps `hasSempDraft` true in its folder's list but is neither in `box=sempDrafts` nor in `summary.sempDrafts`. Box and count are equal by construction.
- The detail route `GET /api/mail/threads/:threadId` does not expose `hasSempDraft`. It was not asked for.
- No export, no route, no manifest entry, no route matrix entry, no table, no migration, no index, no job, no generic operation, no MCP tool, no hook registration, no i18n key and no error code was added.

## Deviations from the specification and spec seams

1. `mail/mailThreadsStore.ts` and `mail/mailSummaryStore.ts`, which the issue's `Touches` names, do not exist. The list lives in `mail/mailThreadListQuery.ts`, `mail/mailThreadPredicates.ts` and `mail/mailThreadRoutes.ts` (gh-1633) and the summary in `mail/mailSummary.ts` (gh-1688); those were changed.
2. Requirement reading, for the owner: the box and its count require a counted message outside Junk and Trash, as the flagged box does. Task step 3 asks for "the same visibility rule as the other boxes" and gh-1633 decided that a thread only in Junk or Trash never appears without a `folderId`. Read literally, the second acceptance criterion ("returns exactly those threads") would also list a Junk-only or Trash-only thread that has an agent draft. Dropping the `has_non_junk` clause of `mailThreadPredicates.sempDrafts` and one test gives the literal reading. Both reviewers judged the delivered reading consistent with gh-1633 and left the confirmation to the controller and the owner.
3. Two existing tests were changed because their expectation described the state before this issue: `mailThreadFilters.test.ts` asserted 400 for `box=sempDrafts` and now asserts it for `box=unknown`; `mailThreadList.test.ts` expected the row unchanged after an agent draft and now expects `hasSempDraft: true`.
4. The predicate follows `mail_thread_aliases`, which the issue does not mention. It was added by the review fix: gh-1493 decided that a holder of a thread id translates it through the alias table, and the predicate is the first reader that joins `mail_drafts.thread_id` to live threads. No storage was changed, so "Draft metadata storage (#1504)" stays out of scope.

Follow-ups, none of them changed here:

- Low, from the recheck, open: no merge test keeps an unrelated thread in the list. A predicate whose alias arm lost `a.to_thread_id = <thread>` would flag every thread of the tenant as soon as one merged-away thread has a Semp draft, and all ten tests of the file would still pass. The production predicate carries the correlation; this is a gap in the tests only. Proposed: in the first merge test ingest one more inbox message that starts an unrelated thread and expect `{ survivor: true, bystander: false }`, only the survivor in the box and the count 1.
- For gh-1941 or gh-1902, or for the merge code of gh-1493 and the storage of gh-1504: `reassignThread` (`mail/mailMessageMetaStore.ts`) does not re-point `mail_drafts.thread_id`. After a merge of two threads that each hold an unsent agent draft the surviving thread logically has two, and the partial unique index `mail_drafts_one_unsent_agent_per_thread_uq` does not stop a new agent draft for the survivor when the existing one names the merged-away id. Whoever re-points the column has to decide that collision. This read copes with either state.
- For gh-1902 and gh-1941, an observation of the worker that was not checked against their specifications: the same index does not look at the item's `deleted_at`, so a soft-deleted, unsent agent draft still occupies the one-per-thread slot for a later agent draft.
- No production code creates an agent draft at this commit (gh-1941 is open), so `hasSempDraft` true, a non-empty box and a non-zero count are reached only by tests until then.
