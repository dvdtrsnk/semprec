# Handover for gh-1582

A deleted transcript or deleted source Files item is now a clean stop of the transcription pipeline. I ran tsc, eslint, prettier check and the vitest integration files for `semprec-transcribe` and `systemHealthReport.test.ts`; I did not run the full `pnpm run verify`.

**What changed**
- **`transcriptionTask.ts`:**
  - New exported `TranscriptionStoppedError`.
  - `requireTranscriptionUnlocked` now takes `{ filesDatabaseId, fileItemId, transcriptId }`. After the lock check it reads the transcript and the source and throws the new error when either is in Trash or gone. Every step transaction already calls it first, so no write or paid call follows a deletion.
  - Step 0 throws the same error for a deleted source before any transcript exists. The handler then returns without writing, since there is no `item_automation` row to mark.
  - The handler catches the error and, in one transaction, sets `item_automation` to `error` with code `deleted` through `recordItemAutomationFailure`. It leaves the `items` row alone, writes no notification, and the job ends successfully. A `locked` row is left untouched.
  - `recordTranscriptionFailure` now returns `"recorded" | "locked" | "deleted"`. On a permanent failure for a transcript in Trash it marks `error`/`deleted` instead of the `status` update that threw NotFound and rolled back. The handler then ends the job successfully.
- **`systemHealthReport.ts`:** `getItemAutomationErrorCounts` ignores items with `deleted_at` set.

**Tests**
- `transcriptionTask.test.ts`:
  - Deleting the transcript, and separately the source, during diarize skips ASR and summarize, writes no notification, leaves `error`/`deleted` and a successful job.
  - A last-attempt failure on a trashed transcript falls back to `deleted` and does not rethrow.
  - Restoring the transcript and rerunning the job reaches `done`.
  - The existing "rolls back and discards its audio when the write transaction fails" test now expects a clean stop; the audio is still discarded.
- `systemHealthReport.test.ts`: an errored item in Trash is not counted.

**Notes for dependants**
- A deleted source with no existing transcript is skipped silently, with an info log only.
- `error` holds the stop message (`... was deleted`), diagnostic only.
- A retry-attempt failure (not permanent) on a trashed transcript still rethrows; the next attempt stops cleanly.
- #1945 closes the Semp problem; nothing here touches it.
