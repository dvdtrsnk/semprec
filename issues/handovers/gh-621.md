## Summary

Fixes #621. The Anthropic adapter now checks the provider's response against a zod schema. A malformed response now fails as a `ProviderCallError`, which `completeHandler.ts` turns into a 502 `provider_failed`, instead of a stray `TypeError` that became a 500. A missing `usage` is rejected instead of being recorded as a call that cost nothing. On a non-2xx status the connection is released.

## Changes

- **`backend/services/semprec-ai-gateway/package.json`** and **`backend/pnpm-lock.yaml`**: added `zod@^4.1.11`, the version the other workspace packages use.
- **`anthropicProvider.ts`**:
  - Replaced the `AnthropicContentBlock` / `AnthropicMessagesResponse` interfaces and `isAnthropicMessagesResponse` with two module-level schemas, `anthropicContentBlockSchema` and `anthropicMessagesResponseSchema`. Both are `z.looseObject`. `usage.input_tokens` and `usage.output_tokens` are required non-negative integers.
  - When `safeParse` fails, the error is `ProviderCallError("Anthropic response did not match the expected shape: <path> <message>")`, built from the first issue. It names the schema path only and never includes response content.
  - A `tool_use` block without `input` now throws `ProviderCallError("Anthropic tool_use block carried no input")`.
  - Token counts are read from the parsed `usage` with no `?? 0` fallback.
  - On `!res.ok`, the adapter calls `await res.body?.cancel().catch(() => {})` before it throws. `cancel()` is used rather than `text()` so an error body is never buffered. The empty `.catch` is what the issue's Task asks for, and a one-line comment explains why the cancel result doesn't matter: it only hands the connection back, so it must not replace the `ProviderCallError` that follows.
- **`anthropicProvider.unit.test.ts`**: five new unit tests, each stubbing `fetch` with inline fixtures:
  - a `null` content block rejects with `ProviderCallError` (not `TypeError`) and the message contains `content.0`;
  - a response with no `usage` rejects with a message containing `usage`;
  - `input_tokens: "12"` rejects with a message containing `usage.input_tokens`;
  - a `tool_use` block without `input` rejects;
  - a 529 response built over a `ReadableStream` rejects with `ProviderCallError`, and the stream's `cancel` callback has run.

  The existing "well-formed response" test is unchanged and still passes.

Nothing in `completeHandler.ts`, `types.ts` or the audio adapters changed, and retries (E6) and passing an abort signal (E3) are left to their own issues, as the issue specifies.
