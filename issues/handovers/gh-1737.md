## What was delivered

- `GET /api/semp/threads` takes the optional query parameter `q` (`parseThreadListQuery` in `backend/services/semprec-api/src/sempThreadsHandler.ts`). The value is trimmed; a blank value is no filter; more than 100 Unicode code points of the trimmed value, a NUL character or `q` given twice is 400 `validation_failed` with `details.field` `q`.
- `listSempThreads` in `backend/packages/data/src/semp/sempThreadsListStore.ts` takes `search: string | null` and applies it inside the list query, before the page is cut, so `limit` and `nextCursor` keep their meaning and it combines with `kind`, `subjectInboxItemId` and `cursor`.
  - A thread matches when the search text is a substring, without regard to case or diacritics (`unaccent` and `ILIKE`), of either of two values. The first is what its title is resolved from: the stored title of a chat, the current heartbeat name of a tick thread, the current Inbox item text of an item thread. The second is the first 140 code points of the stored text of the message the preview shows.
  - The search text is a bound parameter. The pattern is built in the query, in a one-row `MATERIALIZED` CTE `needle`: the text is folded with `unaccent` first, then a backslash, `%` and `_` of the folded text are escaped, backslash first, then the text is wrapped in `%`. Both `ILIKE ... ESCAPE '\'` comparisons read `needle.pattern`.
  - A text of which folding leaves nothing, such as a lone combining mark, is no filter, as a blank one is.
  - Every row field is produced by the same code as without `q`.

## Contracts dependents build on

For gh-1783 (message full-text search, extends this filter) and gh-1854 (the chat group of global search, same match rule and visibility).

- REST: `GET /api/semp/threads?q=<text>`; everything else of the route is as in `issues/handovers/gh-1729.md`. An unknown word answers `{ rows: [], nextCursor: null }`.
- Store: `ListSempThreadsInput.search`; null is no filter. The handler passes null for a blank `q`, and the store itself ignores a text that folds to nothing, so the two rules overlap for a blank value.
- What is searched and what is not:
  - An item thread is searched by its Inbox item text, not by the words of the title template (`Edit:` / `Úprava:`). An Inbox item in the trash gives no title and does not match.
  - The preview window is the first 140 code points of the stored text, which still has its Markdown syntax, while the row shows the text with Markdown removed. Syntax and link targets inside the window can match, a phrase that syntax interrupts does not, and a word the preview shows near its end can lie beyond the window. Text that is found on the preview side is always inside the first 140 stored code points.
  - The key and parameters of a system message are not searched. An earlier message of a thread is not searched.
- Escaping order for anyone who adds a comparison: fold first, escape second. `unaccent` itself produces the three pattern characters (`%` from U+FF05 and U+FE6A, `_` from U+FF3F, a backslash from U+FF3C, U+FE68 and U+2216) and removes combining marks, so an escape applied before the fold is not enough. A new comparison of this query reads `needle.pattern`.
- gh-1783 extends the `WHERE` clause next to the two comparisons; the title and preview matches stay.
- The `unaccent` extension is the one installed by migration 0006. No SQL migration, no table, no column, no index, no job name, no write hook, no stored key and no user-facing label was added. No route matrix entry was added: the route, its isolation case and its handler-file mapping are those of gh-1729.

## Deviations from the specification and spec seams

1. Limit of "searched as displayed". The issue defines the searched preview as the first 140 code points of the last message text, and the filter reads exactly that from the stored text. The preview a row shows has Markdown removed before its cut, so for a message with Markdown the two differ as described above. The requirements reviewer judged this as following the issue's literal definition and its third acceptance criterion. Whether search should follow the displayed text is a product decision that `issues/decisions/gh-1737.md` leaves open.
2. Decided where the issue is silent, in the fix round: a `q` of which folding leaves nothing is no filter and returns the whole list. `issues/decisions/gh-1737.md` keeps the rule; the owner may overrule it (one `CASE` in the list query and one test).
3. Not in the issue: `q` with a NUL character is refused with 400, because Postgres cannot bind one in a text value and the request would otherwise fail with 500.
4. The cap of 100 code points applies to the trimmed value.
5. The JavaScript escape function of the first commit was removed by the fix; the escape is in SQL. The equivalents in `views/filterCompiler.ts` and `mail/personEmailIndexStore.ts` were not touched.
6. No migration and no `ROUTE_CASES` change; the tenant isolation of `q` is tested in `sempThreadsList.test.ts`.
