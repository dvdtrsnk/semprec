## What was delivered

After a user answers an invitation (accepted, tentative or declined) and the answering transaction commits, one iMIP `METHOD:REPLY` message reaches the organizer from the mailbox that received the invitation. The respond route queues the job inside its own transaction, so a rollback queues nothing; the job sends through the transport of the mailbox's sync mode.

## Entry points and contracts dependents build on

- `buildItipReply` in `packages/data/src/calendar/icalendarWriter.ts` (extends the file gh-1774 created; `checkIdentity`, `toCalendarText` and `instantOf` were extracted from existing helpers, behaviour unchanged). It takes `{ uid, sequence, organizerEmail, attendeeEmail, attendeeName?, partstat, summary, startsAt, endsAt (string or null), allDay }` and returns a VCALENDAR with `METHOD:REPLY` and one VEVENT; DTSTAMP is the current time.
- Job name `calendarSendInvitationReply` (manifest `taskNames`, `queueAffinity` `api`), payload schema `{ invitationId, response, respondedAt }` (strict zod), module `calendar/invitationReplyJob.ts`: `enqueueInvitationReply(client, ...)` with job key `invitation-reply:<invitationId>:<respondedAt>`, and the handler. The handler ends without sending when the invitation's `respondedAt` differs from the payload's. Attendee address is `mail_message_meta.delivered_to_address` of the source email, else the mailbox's first address; the message is sent From the mailbox's first address.
- Failure policy: transient failures rethrow for the queue's backoff; permanent ones (invitation or mailbox missing, no address, no organizer, no transport, recipient refused, unbuildable message) log a reason code (`noOrganizerAddress`, `mailboxMissing`, `noMailboxAddress`, `noTransport`, `recipientRejected`, `invalidMessage`, superseded) and end the job.
- Composition-root dependency: `setInvitationReplyDelivery` and type `InvitationReplyDelivery`, exported from the data barrel (`packages/data/src/index.ts`) and bound and unbound by `createApiQueueRuntime` in `services/semprec-api/src/queueRuntime.ts` (also on start failure and stop), per ADR 2026-11-12 (module queue tasks read their composition-root dependencies from a binding). Any later source that sends mail from a module task follows the same binding pattern.
- i18n keys `calendar.invitation.reply.<response>.subject` and `.text` (three responses, six keys) in the calendar `en.json` and `cs.json`.
- No table, migration, route or operation was added. The respond route (`createRespondToInvitationRouteHandler` in `invitationRouteHandlers.ts`) now enqueues for accepted, tentative and declined; an unchanged repeated answer and a notice acknowledged (shared calendar notice kind) enqueue nothing.

## Tests

`invitationReply.test.ts` runs a real respond-route call on the runtime role pool and the job through the real queue: one REPLY with PARTSTAT=ACCEPTED from the receiving mailbox with the delivered-to attendee (and the first-address fallback); nothing queued when the transaction fails after the enqueue (trigger on the notification update) or the answer is refused; transient failure rescheduled through the queue (`graphile_worker.reschedule_jobs`), one reply delivered and an empty queue afterwards; a repeat of the same answer collapses onto one job; DECLINED and TENTATIVE; accepted changed to tentative sends a new reply; changed again before the first job ran sends only the latest; a superseded job run alone sends nothing; missing organizer address, trashed mailbox, no mailbox edge, no mailbox address end without retry; another tenant's invitation answers like an unknown one. The worker's mutation checks (superseded check removed, always-mailbox attendee, enqueue removed, job key without respondedAt) each failed the corresponding tests.

## Deviations from the specification and spec seams

1. Subject and body come from the calendar i18n catalog in the tenant user's language; the en text is exactly `Accepted: <title>`, `Tentative: <title>`, `Declined: <title>`, while a cs tenant sends `Přijato:`, `Předběžně přijato:`, `Odmítnuto:` (review rule: labels through i18n).
2. `icalendarWriter.ts` already existed (gh-1774), so `buildItipReply` extends it; `endsAt` is `string | null` (an invitation may have none) and there is no stamp parameter.
3. The module task handler receives only its payload, so pool and transports come from the binding `setInvitationReplyDelivery`; no new ADR (ADR 2026-11-12 names #1953).
4. The enqueue is unconditional for the three replying answers of an invite; a missing organizer address is handled by the job (`noOrganizerAddress`).
5. The attendee CN is optional in `buildItipReply` as specified, but the job passes no name.
6. A mailbox with no address ends the job (`noMailboxAddress`).
7. Fixtures extended additively: `INVITATION_KEYS` gained `organizerName` and `organizerEmail`; mail fixture receive and deliver gained optional `deliveredTo`.
8. `tenantIsolationJobs.test.ts` requires one case per api-affinity task, so a case for `calendarSendInvitationReply` was added there although it is outside the Touches list.
