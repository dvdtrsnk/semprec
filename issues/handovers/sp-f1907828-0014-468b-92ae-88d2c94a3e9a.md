Implementation commit `19cd33898` on `feat/ia-webhooks` (from `feat/internet-accounts` 1decd3983).

**What changed.**
- Baseline, edited in place:
  - New table `calendar_push_channels`. PK `(tenant_id, provider, channel_id)`. Columns: `provider` (`google|graph`), `channel_id`, `account_item_id`, `calendar_item_id` (Google only), `resource_id` (Google only, a CHECK ties both to the provider), `secret`, `expires_at`, `created_at`. It has tenancy=tenant, RLS (restrictive + permissive), FKs to items on both item columns (`ON DELETE CASCADE DEFERRABLE INITIALLY DEFERRED`), indexes `(tenant_id, account_item_id)`, `(tenant_id, calendar_item_id)` and `(provider, channel_id)` for the routers, and grants to `semprec_side`.
  - Router functions `route_google_calendar_channel(text)` and `route_graph_calendar_subscription(text)`: SECURITY DEFINER, owner `semprec_router`, `search_path = pg_catalog, public, pg_temp`, `EXECUTE` only for `semprec_data`. Both return `TABLE(tenant_id uuid)`. The router role has column SELECT on `tenant_id`, `provider` and `channel_id` only.
- `calendar_push_channels` is in `EXPORT_EXCLUDED_TABLES`: it holds the secrets.
- New in `packages/data/src/calendar/sync/`:
  - `calendarPushChannelsStore.ts`: the table's only writer, plus `routeCalendarPushChannel`. That function answers `null` when an id exists in no tenant or in more than one.
  - `googleChannels.ts`: `events.watch` (a server-chosen UUID, a 32-byte random hex token, `ttl` 7 days, the answered `expiration` stored), `channels.stop` (a 404 counts as done) and `handleGoogleCalendarNotification`.
  - `graphCalendarSubscriptions.ts`: a subscription on `/me/events` with `created,updated,deleted` and a random `clientState`, 4230 minutes. Renewal PATCHes the subscription; a 404 returns `null`. Delete treats a 404 as done. Also `handleGraphCalendarNotification`.
  - `calendarPushNotifications.ts`: routes the channel, re-reads it in its tenant and compares the secret in constant time (sha256 + `timingSafeEqual`, against a dummy secret when no channel is stored). On a match it enqueues `calendar-account-sync:<account>`. Google's `sync` message is accepted but queues nothing.
  - `calendarPushChannelsJob.ts`: the per-account maintenance (task `calendarPushChannels`, key `calendar-push-channels:<account>`, 3 attempts, tenant lane, `api`) and the sweep (`calendarPushChannelsSweep`, system lane, cron `35 * * * *`). Also the runtime binding `setCalendarPushRuntime`.
  - `calendarPushChannelsEnqueue.ts`.
  - `calendarPushRemoval.ts`: the channel stops on account removal.
  - `calendarPushComposition.ts`: exports for the composition root.
- Maintenance rules:
  - A channel is wanted only while all of these hold: Calendars is on, the account is live, the grant has calendar consent, the sync state is `ok`, the sync mode is `gmail_api` or `graph_api`, and the runtime has that provider's `notificationUrl`.
  - Google keeps one channel per tracked calendar (one with a `calendar_remote_state` row).
  - Graph keeps one subscription per account.
  - A Google channel within 24 h of its expiry is replaced: the new channel is created first, then the old one is stopped. If the replacement fails, the old channel is kept.
  - A Graph subscription within 24 h of its expiry is PATCHed. A 404 deletes the row and subscribes anew.
  - Every other channel is stopped and its row deleted, even when the stop fails. This covers older duplicates, channels of untracked calendars, channels of the wrong provider, and accounts that are off or unhosted.
  - Each provider call and its row write is a separate step, with no transaction open across the call.
  - A failed step is logged with ids, provider, step and error name. When any step failed, the job throws `CalendarPushMaintenanceError` after all steps ran.
  - Tokens come from `refreshAndPersistAccessToken`, purpose `calendar_push`.
- Shared files touched:
  - `calendarAccountSyncLifecycle.ts`: `stopCalendarAccountSync` also queues the maintenance (one line).
  - `mail/mailboxRemoval.ts`: the removal transaction calls `takeRemovedAccountCalendarPush` before the credential is deleted. That deletes the rows (RETURNING) and decrypts the refresh token, purpose `calendar_push_removal`, only when channels exist. After the commit, `removeMailbox` calls `stopRemovedAccountCalendarPush` before `cleanUpRemovedMailbox`, because the mail cleanup may revoke the Google grant. That stop refreshes the token without storing it and never rejects.
  - `queue/src/index.ts`: two task names, their affinity and lanes.
  - `worker.ts`: handlers and crontab.
  - `index.ts`: one `export *`.
- API (`services/semprec-api`):
  - `calendarWebhookHandlers.ts`, wired in `app.ts` next to the mail Graph webhook.
    - Google: POST only (otherwise 404). The body is drained up to a 16 KiB cap (413 over it). `X-Goog-Channel-ID` must match `^[A-Za-z0-9\-_+/=]{1,64}$` and the token may be at most 256 characters. An accepted notification answers 200 with an empty body. An unknown channel, a wrong or missing token, or a malformed or missing id all answer the same empty 404. Nothing is fetched.
    - Graph: the `validationToken` handshake first (at most 1024 characters, otherwise 400; answered as `text/plain` with `nosniff`). Every batch answers 202; rejected notifications are logged with their outcome only.

**Deviations and spec seams.**
- **Storage:** a dedicated table instead of `channel_id`/`channel_expires_at` columns on `calendar_remote_state`.
  - The tenant export excludes whole tables, and the token must be excluded.
  - The Graph subscription is per account, not per calendar.
  - A channel must outlive the deletion of its `calendar_remote_state` row (calendar vanished, Calendars off) to be stopped. With the columns, every deleting path in the sync engine (including `calendarSyncApply.ts`, which the write-back issue is editing) would have had to stop channels.
- **Router functions:** they return `TABLE(tenant_id)` rows instead of a scalar, like `route_mail_oauth_state`. An id found in two tenants names neither.
- **Creation timing:** channels are created by the hourly sweep, so up to about an hour after an account's first `ok` pass, not immediately on Calendars on. Renewal also runs hourly with a 24 h margin.
- **Configuration gate:** Google channel creation needs `GOOGLE_CALENDAR_WEBHOOK_ENABLED=true` in addition to an https `APP_BASE_URL`, because only the operator knows whether the domain is verified. This is an operations flag the Task did not name.
- **Removal with a failed stop:** a failed stop still forgets the row. The provider ends the channel at its expiry, and the webhook answers its notifications as unknown.
- **Insert race:** if a watch succeeds but its row insert fails, or the account is switched off between the plan and the insert, the channel can exist at the provider with no row or a stale row. The next hourly sweep stops a stale row, and a channel without a row expires.
- **Not built:** no rate limit on the public webhooks, the same as the mail Graph webhook. Graph lifecycle notifications (`lifecycleNotificationUrl`) are not used.

**Open items (need real providers and public HTTPS).**
- Google:
  - Whether `events.watch` is refused for an unverified domain, and how. Some calendars (holiday, birthday, other users' read-only calendars) may refuse push (`pushNotSupportedForRequestedResource`, a 400). Today that fails the step every hour; it is logged and retried, but such calendars should be skipped.
  - The longest `ttl` Google grants for Calendar channels.
  - That notifications carry `X-Goog-Channel-Token` as sent.
  - That `channels.stop` answers 204 or 404 as assumed.
- Microsoft:
  - Whether `/me/events` notifies about calendars other than the default one. The List events documentation says the default calendar only, so changes in secondary calendars may arrive only through the 5-minute sweep; per-calendar subscriptions (`/me/calendars/{id}/events`) would cover them.
  - Whether 4230 minutes is accepted. A longer value is possible for Outlook events.
  - That the validation handshake works through the deployed proxy within 10 s.
- The handshake and all provider shapes are tested only against hand-written fakes.
