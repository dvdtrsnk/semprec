## What was delivered

`POST /api/proposals/:id/confirm` and `POST /api/proposals/:id/reject` accept an optional `ifVersion`, the card's `updatedAt`.

- `ifVersion` must be an ISO 8601 UTC timestamp string (`z.iso.datetime`, the shape of `updatedAt`); any other value (number, null, empty string, non-date string, date-only string, array) is a 400 `validation_failed` on field `ifVersion` and writes nothing.
- Order of checks in both actions, after the row lock: 404 for a missing card; an idempotent terminal state (confirm on `confirmed`, reject on `rejected`) answers 200 unchanged and ignores `ifVersion`; an incompatible status answers 400 `validation_failed` with field `status` and the new `details.currentStatus` (null when the card holds no status), also with a stale `ifVersion`; an `ifVersion` that is not the locked card's `updatedAt` answers 409 `version_conflict` with `details.currentItem` set to the card and writes nothing; otherwise the action proceeds. Without `ifVersion` behaviour is as before.

## Entry points and contracts dependents build on

- New module `packages/data/src/inbox/proposalPreconditions.ts` exports `assertProposalVersion(proposal, ifVersion)` (throws `ConflictError` with `{ current: proposal }`, which the error contract projects to `details.currentItem`) and `incompatibleStatusError(message, status)` (the 400 with `field` and `currentStatus`). Routes that later accept `ifVersion` on a card (#1892, #1912, #1937, #1870) can reuse both.
- `confirmProposalWithClient` and `rejectProposalWithClient` take a new optional trailing parameter for the version; other callers (for example `transcriptionRouteHandlers.ts`) are unaffected.
- The REST change is additive (ADR `2026-09-11-additive-only-rest-contract-no-url-versioning`). Body parsing of both handlers now goes through a shared `bodyObject` helper with unchanged messages. No route, table, operation, migration or job name is added.

## Tests

`inboxRouteHandlers.test.ts` (ifVersion on confirm and reject, both actions): stale version on an open card is a 409 with the card and nothing written, current version succeeds, stale version on an already decided card is a 200 unchanged, incompatible status is a 400 with `currentStatus` also with a stale version (pins the check order), card without a stored status gives `currentStatus` null, malformed `ifVersion` values are 400 on the field, unknown card is 404 before the version is compared, no `ifVersion` behaves as before. `tenantIsolationRoutes.test.ts` has the wire-level test through the real adapter asserting `error.details.currentItem`, the 200 replay and the 400 of the opposite decision. All passed in the landing gate.

## Deviations from the specification and spec seams

1. The helpers are in a sibling module `proposalPreconditions.ts` because `proposalActions.ts` is near the 900-line ESLint cap (the rules reviewer measured about 776 counted lines, so the stated reason is overstated; the split is not a rule violation).
2. `ifVersion` is validated as an ISO 8601 UTC timestamp rather than any string, so a garbled value is a 400 on the field instead of a 409.
3. The wire-level test in `tenantIsolationRoutes.test.ts` is outside the Touches list; it is the only coverage of the `details.currentItem` projection.
