# Handover: sign password accounts in again and name why a connect was refused

Implementation commits `ce0bf8ac6`, `d91f51a11` and `730e46ce3` on `feat/internet-accounts`. The backend route (`33d9c0495`, `160c8633f`) was built in parallel by another agent; the mobile code was checked against its final contract.

**Shared (KMP).**
- `ApiResponse.Failure` keeps the error answer's body (`body`, `null` by default); `ApiClient.send` fills it. `failureKind` is unchanged, so every other caller keeps its `FailureKind` (400/409/422 are still `REJECTED`).
- Domain: `MailConnectRefusal` and `MailConnectOutcome` (`Connected` / `Refused`). `MailboxRepository.connect` returns `RepositoryResult<MailConnectOutcome>`; new `updatePassword(mailboxId, password, username?)`.
- `HttpMailboxRepository`: `PUT /api/mail/mailboxes/:id/password` (`username` only when given, the 200 s connect timeout). Both routes decode `error.code` (a top-level `code` is accepted too) through `ApiErrorDto` with caught serialization errors. Codes: `mail_auth_failed` → WRONG_CREDENTIALS, `mail_app_password_required` → APP_PASSWORD_REQUIRED, `mail_server_unreachable` → SERVER_UNREACHABLE, `mail_tls_failed` → TLS_FAILED, `caldav_auth_failed` → CALDAV_REFUSED, `caldav_server_unreachable` and `caldav_server_invalid` → CALDAV_UNREACHABLE, `provider_account_already_connected` → ALREADY_CONNECTED, `rate_limited` or any 429 → RATE_LIMITED. Anything else (`validation_failed`, `mailbox_not_password`, `not_found`, `payload_too_large`, `internal_error`) stays its `FailureKind`. A success body is not read.
- Presentation: `InternetConnectFailure` gains the eight reasons. `PasswordSignInFlow` (shared by both ViewModels) holds `InternetPasswordSignIn` in state, with `InternetPasswordSignInStep.Submit/Cancel`. An empty password gives INVALID_INPUT and sends nothing, and a blank user name keeps the stored one. A refusal stays open with its reason. On success the sign-in closes and the account (or the list) is read again.
- `canSignInAgain` (detail, and new on `InternetAccountItem`) covers `gmail`/`outlook` (browser) and `icloud`/`generic` (password) whenever mail or calendars report needs-reauthorization. Mail status already maps `syncStatus: needsReauthorization`, which the server now reports for a missing credential.
- List: `SignInAgain(accountId)` starts the existing reauthorization browser flow (its own `signingIn`/`signInFailure`, no `Connected` effect) or the password sign-in. A connect refused as ALREADY_CONNECTED sets `existingAccountId` to the listed account with that address (case-insensitive), and `OpenExisting` opens it.

**Apple.** The CoreKit values and bridges cover the new cases. Account feature:
- `PasswordSignInSheet`: password, or app-specific password for iCloud, plus an optional user name with the address as placeholder, the iCloud hint, progress and the failure text.
- The account's reauthorization section offers "Sign in again" to every account that can.
- The list shows a "Sign in again" row under each account that needs it, and a failure alert.
- The connect form offers "Open the account".
- en/cs copy is in the catalog and the copy policy; identifiers are in `AccountIdentifiers`.

**Android.** It has no Internet accounts screen (`AccountFeature` is Apple-only), so nothing changed there.
