## Context

Model tier rationale: One new send function beside an existing adapter with an HTTP/2 test seam and existing payload tests, but it fixes the header and payload contract that several later features rely on.

`backend/packages/data/src/push/apnsAdapter.ts` can send only a visible alert today: `sendApnsNotification` posts `{ aps: { alert: { title } }, link_href, notification_id }` with the topic and bearer headers and no `apns-push-type` or `apns-priority`, and it maps 410 and `BadDeviceToken` to a permanent failure. The fanout job (`notifications/notificationFanoutJob.ts`) is tied to a row in `notifications` and `push_deliveries`, so a push without a notification does not exist. Apps that schedule local alarms and reminders need a silent wake-up instead: a background push that tells the device to reload its data.

This issue adds a general silent push to the APNs adapter. It builds on the preference-aware fan-out work of #1443, which also edits `apnsAdapter.ts`. Later issues use it: the debounced sleep resync (#1838), holding delivery inside the sleep window (#1794), silent dismiss pushes (#1826) and the reminders resync (#1879).

Decision: the adapter only sends. Finding a user's registrations and revoking a dead one stays with the caller (the same split as the fanout job), and nothing is written to `notifications` or `push_deliveries`.

## Task

Load `io-hardening` and `testing`.

1. In `backend/packages/data/src/push/apnsAdapter.ts` add `sendApnsBackgroundPush(target: ApnsTarget, data: Record<string, unknown>, config?: ApnsConfig): Promise<PushSendResult>`. The body is `{ aps: { "content-available": 1 }, ...data }`: no alert, no sound, no badge. A `data` object that contains the key `aps` is rejected with a thrown `ValidationError` before any request. The headers are those of `sendApnsNotification` plus `apns-push-type: background` and `apns-priority: 5`.
2. Share the request, provider-token and result mapping with `sendApnsNotification` (no duplicated HTTP code): 200 is `delivered`; 410 or reason `BadDeviceToken` is `permanent-failure`; any other failure is `transient-failure`; missing `APNS_*` configuration is `not-configured`. Existing behavior and payload of `sendApnsNotification` do not change.
3. Tests in `backend/packages/data/src/push/__tests__/apnsAdapter.unit.test.ts` with the stubbed `node:http2` approach the file already uses: `data` `{ kind: "sleepResync" }` and `{ dismiss: ["n1"] }` are sent unchanged inside the payload, both with `apns-push-type: background` and `apns-priority: 5` and without an alert; a `data` containing `aps` is rejected; 410 gives `permanent-failure`; the existing alert tests still pass.

## Scope

### In scope

- The silent background push send function, its header and payload contract, and its adapter-level tests.

### Out of scope

- Selecting a user's registrations, revoking dead registrations and debouncing: #1838.
- Per-device settings or device names for registrations: decided: not in v1; every iOS registration, iPhone and iPad alike, is treated the same.
- Changing the alert push (category, interruption level, collapse id): #1443 and #1829.
- Any `notifications` row, `push_deliveries` row or web push variant.

## Acceptance criteria

- When `sendApnsBackgroundPush` is called with `{ kind: "sleepResync" }`, then the request body is `{"aps":{"content-available":1},"kind":"sleepResync"}` with `apns-push-type: background` and `apns-priority: 5` and no alert or sound.
- When it is called with `{ dismiss: ["n1"] }`, then the payload carries `dismiss: ["n1"]` unchanged.
- When APNs answers 410 or `BadDeviceToken`, then the result is `permanent-failure`; when the key configuration is missing, `not-configured`.
- When `data` contains an `aps` key, then the call is rejected without a request.
