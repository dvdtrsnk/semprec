**Model tier:** high

## Context

Model tier rationale: Transactional deactivation signals require three idempotent consumers and bounded shutdown.

When an account is suspended (#1041), and later when it is deleted (#1049), its tenant leaves `active`. Access ends at once:

- every session is revoked, which closes its sockets with 4401 through `session_revoked` (`backend/packages/realtime/src/syncServer.ts:325-333`, with a heartbeat fallback at `:204-208`);
- `verifySessionToken` refuses sessions of a non-active tenant (#980);
- new queue jobs of a non-active tenant complete as no-ops (#982);
- per-tenant sweeps visit active tenants only.

What still survives is per-process in-memory state that keeps running for that tenant. This issue adds the cross-process deactivation signal and tears down the state below. In-flight agent runs in `semprec-agents` are cancelled by #1050, which consumes the same signal.

- **Mail live sync.** The root (`backend/packages/data/src/mail/mailLiveSyncRoot.ts:101-248`) keeps hosting the tenant's mailbox lifecycles until its next discovery pass. That pass runs every 60 s (`:107`) and, since #990, discovers mailboxes per active tenant. #998 made the Gmail Pub/Sub dispatch run through that root.
- **Sync server sockets.** Since #1025 every sync-server socket identity (`SyncIdentity`, `backend/packages/realtime/src/syncServer.ts:20-23`) carries its `tenantId` and deliveries are routed per tenant. Sockets of a deactivated tenant are closed only indirectly, through session revocation.
- **Semp conversation.** Since #1015 it is keyed per tenant, so a tenant's wake session and TTL timer survive in memory (`backend/packages/agent-runtime/src/sempConversation.ts:96-263`). No production process composes a `SempConversation` yet: `new SempConversation` appears only in tests.

The status changes in whichever process runs the admin or account route. The state lives in `semprec-api` here, and in `semprec-agents` for #1050. These processes share only Postgres, so the deactivation must travel as a NOTIFY. Postgres delivers a NOTIFY issued inside a transaction only when that transaction commits, and drops it on rollback. Publishing it inside the status-changing transaction therefore follows the commit atomically, and a crash between commit and publish cannot lose it. NOTIFY is not persisted, so a listener must re-read the current non-active tenants whenever it (re)connects, the way the sync server reconnects its own LISTEN client with capped backoff (`syncServer.ts:73-75`, `:393-420`).

## Task

Load `io-hardening` (LISTEN consumer, release on every path, shutdown that cannot hang), `error-handling`, `state-writes` (NOTIFY tied to the commit) and `adr-conventions`.

1. **Signal** — new `backend/packages/data/src/tenancy/tenantStatusSignal.ts`:
   - `TENANT_STATUS_CHANNEL = "semprec_tenant_status"`.
   - `publishTenantDeactivated(client: PoolClient, tenantId: string)` runs `SELECT pg_notify($1, json_build_object('tenantId', $2::uuid)::text)` in the caller's transaction. Document why no `runAfterCommit` is needed.
   - `startTenantDeactivationListener(pool, onDeactivated: (tenantId: string) => Promise<void>): Promise<TenantDeactivationListener>`, where the listener exposes `close(): Promise<void>`. It:
     - runs its whole lifetime inside `runAsSystem("tenantDeactivationListener", …)`. Long-lived listeners start in system scope, and a consumer re-enters a tenant explicitly when it needs one;
     - takes one dedicated client and runs `LISTEN`;
     - validates each payload as `{ tenantId: <uuid> }`, logging and dropping anything else (no unchecked cast);
     - on the first connect and every reconnect, reads `SELECT id FROM tenants WHERE status IN ('suspended','deleting')` under `runAsSystem("tenantDeactivationResync", …)` and calls `onDeactivated` for each id;
     - reconnects after a connection error with capped exponential backoff (200 ms to 5 s);
     - logs a handler rejection without stopping the listener;
     - releases the client on every exit path;
     - sets a `closed` flag before teardown, so a reconnect resolving after `close()` releases its client instead of attaching it.

   Export it from `backend/packages/data/src/index.ts` and update `EXPECTED_RUNTIME_EXPORTS`.
2. **Publishers** — `suspendAccount` in `backend/packages/data/src/tenancy/accountsAdminStore.ts` calls `publishTenantDeactivated` after its status transition, in the same transaction. Reactivation publishes nothing.
3. **Consumers.** Each is idempotent: a second call for the same tenant is a no-op.
   - `SyncServer.closeTenant(tenantId: string): void` in `backend/packages/realtime/src/syncServer.ts` closes every open socket whose identity has that `tenantId`, using `SESSION_REVOKED_CLOSE_CODE` (4401) and reason `"account deactivated"`.
   - `MailLiveSyncRoot.stopTenant(tenantId: string): Promise<void>` waits for any in-flight discovery pass, then stops every hosted lifecycle of that tenant through the existing `stopHosted`. Record the tenant on each hosted entry if #990 did not.
   - `SempConversation.dropTenant(tenantId: string): Promise<void>` clears the tenant's TTL timer.
     - With no turn in flight, it closes the wake run as `error` ("account deactivated") through the existing `failRun` inside `runInTenant(tenantId, …)` and removes the entry.
     - With a turn in flight (`busy` or `waking`), it marks the tenant's conversation as dropped. When that `send` settles, the entry is discarded and its run closed as `error` instead of kept. The turn itself is not aborted mid-stream.
     - Production wiring waits until a process composes `SempConversation`. This issue adds the method and its test only.
4. **Wiring** — `semprec-api` (`backend/services/semprec-api/src/serve.ts`) starts one listener after the sync server and mail root exist. Its handler calls `syncServer.closeTenant(id)` and then `await mailLiveSync.stopTenant(id)`. `createGracefulShutdown` (`backend/services/semprec-api/src/shutdown.ts`) takes the listener as a new option and closes it first, before `syncServer.close()`.
5. **ADR** `docs/adr/<YYYY-MM-DD>-tenant-deactivation-tears-down-in-process-state.md`. It records:
   - the channel and its payload;
   - NOTIFY inside the status-changing transaction;
   - resync on (re)connect;
   - that any future per-process registry keyed by tenant must subscribe.

## Scope

### In scope
- The deactivation signal, its publication on suspension, and the three consumers listed above.
- The listener wiring and shutdown in `semprec-api`.

### Out of scope
- Cancelling in-flight agent runs in `semprec-agents`, including the `AbortSignal` through `runAgentTurn`, the in-flight run registry and the agents listener (#1050).
- Aborting an in-flight Semp turn mid-stream.
- Publishing on deletion: #1049 calls `publishTenantDeactivated` from its own transaction.
- Composing `SempConversation` or `DelegationRegistry` into a process. Neither is composed today, and no issue in this batch does it.
- Cancelling delegated sessions held by `DelegationRegistry`.
- Rejecting new jobs of non-active tenants (#982).
- Moving `console.*` calls in the realtime package to the logger (#1074).

## Acceptance criteria

- When `suspendAccount` commits for tenant B, the listener's handler is called once with B's id. When the suspending transaction rolls back, no notification arrives (integration, `tenantStatusSignal.test.ts`).
- When B is suspended while the listener's connection is down, then after the reconnect the handler is called for B through the resync, with no NOTIFY involved (integration, `tenantStatusSignal.test.ts`, the listen client terminated with `pg_terminate_backend`).
- When a payload that is not `{ tenantId: <uuid> }` arrives on the channel, it is logged and dropped, and the listener keeps working (integration, `tenantStatusSignal.test.ts`).
- When `close()` is called, including while a reconnect attempt is in flight, its client is released and no further handler calls happen (integration, `tenantStatusSignal.test.ts`).
- When `closeTenant(B)` runs with sockets of A and B connected, every B socket receives close code 4401 with reason `account deactivated`, and A's sockets stay open (integration, `syncServer.test.ts`, two tenants via `createTestTenant()` from #975).
- When `stopTenant(B)` runs, B's hosted lifecycles are stopped and their `mailsync:<id>` heartbeats stop, and A's stay hosted. A following discovery pass does not re-host B's mailboxes (integration, `mailLiveSyncRoot.test.ts`).
- When `dropTenant(B)` runs with an idle B entry, B's wake run is closed as `error`, the entry is gone and the TTL timer is cleared. When it runs during an in-flight B turn, the turn completes, after which the entry is gone and the run is closed as `error`. A's conversation is untouched in both cases (integration, `sempConversation.test.ts`).
- When `semprec-api` shuts down, the listener is closed before the sync server stops. The existing shutdown tests still pass with the listener added (integration, `services/semprec-api/src/__tests__/shutdown.test.ts`; unit, `shutdown.unit.test.ts`).
