**Blocked by:** #114

## Context

The contract is credible only when every module delivered before it loads through it. #108–#114 built `ModuleManifest`, `ModuleRegistry`, task and rule-kind registration, worker derivation, migrations, drift detection, boundary checks, and the test tiers — all against a contract with no real manifests yet. This part authors manifests for the first group of existing modules: the schema/data core, views, blocks/docs, and the ten system databases. The sibling #227 authors the second group (library, mail sync/mailbox, Inbox pipeline), and #115 then removes the remaining module-id branches from core and adds the load-all and inactive-projection tests.

## Task

Create a `ModuleManifest` for each of the following existing modules, based on their actual databases, capabilities, tools, views, actions, rules, tasks, workers, and migrations — a retrofit of existing data logic, not a rewrite:

- the schema/data core (`packages/data`: the choke point and system tables),
- views (`0002_views.sql` and the registered view types),
- blocks/docs (`0003_docs.sql` and the block-append mechanism),
- the ten system databases (`0004_ten_databases.sql`, `seedTenDatabases.ts`).

For each manifest, verify that `ModuleRegistry.loadModule()` loads it and that it passes the load-time structural check without modifying the module's data behavior; add a load test per manifest in the integration tier from #225.

## Scope

### In scope

- Manifests for the four modules above and their per-manifest load tests.

### Out of scope

- Manifests for library, mail sync/mailbox, and Inbox pipeline (#227).
- Removing core module-id branches, the load-all test, and inactive-projection tests (#115).
- Agent runtime implementation and new module behavior.

## Acceptance criteria

- Each of the four modules loads through `ModuleRegistry.loadModule()` and passes structural validation.
- Loading the manifests changes no stored data and no module data behavior.
