## Context

Model tier rationale: One module agent tool following the descriptor and handler pattern of the mail tools of #1927 that writes a single proposal card and its source edge in one transaction, with an idempotence rule; no new authorization contract.

The thread detail offers "Semp suggests another task from the thread". The product owner decided that Semp must not create items silently: the suggestion is a proposal in the Inbox that the user can edit before confirming, and only the confirm creates the task. The confirm of such a card (a Processing proposals card with `kind` `mailThread`, linked to the thread through `sourceThread`, with a `database` envelope targeting Tasks) is #2034; it creates the task through the function of #1900, so the task gets the Threads.tasks edge and the thread's project and people as inherited values.

Semp's mail tools are declared in `agentTools` of `mail/mailModuleManifest.ts` with handlers in `mail/mailAgentTools.ts` (#1927), under the approval and grant rules of the ADR of #1385. A transcript card shows how a module writes a proposal card: `createItemWithClient` on Processing proposals with `allowedSystemKeys` for `kind`, `proposal`, `history` and `status`, then the source edge with the Processing proposals relation context (`transcription/transcriptEventMatch.ts`).

Decisions:
- The tool is `mail.thread.proposeTask { threadId, name }`. Semp writes the name from the conversation; the tool takes no due date, because the user sets the date and the AI does not infer it (the user can add a date while editing the card).
- The tool creates only a card in status `proposed`; it never creates a Tasks item or a Threads.tasks edge. Its approval mode is `none` and it is granted with the read grants of the mail databases, because nothing outside the Inbox changes until the user confirms.
- A call for a thread that already has a `proposed` `mailThread` card with the same name (compared after trimming and case folding) returns that card instead of creating a second one.

## Task

Load `state-writes`, `io-hardening`, `canonical-keys` and `testing`.

1. Declare `mail.thread.proposeTask` in `agentTools` of `mail/mailModuleManifest.ts` (capability `mail.taskProposal`, approval mode `none`) with its handler export in `mail/mailAgentTools.ts`. The tool description tells Semp to use it to suggest a task from a thread and not to create thread tasks itself.
2. Handler, in `mail/threadTaskProposals.ts`: validate `threadId` (resolve a merged-away id to the current thread; unknown or foreign is a not-found error) and `name` (trimmed, non-empty, up to 500 characters). In one transaction: apply the duplicate rule above under a row lock on the thread's Threads item; otherwise create the Processing proposals item with `kind` `mailThread`, `status` `proposed`, the envelope `{ entityKind: "database", target: <Tasks database id>, properties: { name } }` (validated with `assertValidProposalEnvelope`) and a history entry authored by the AI naming the thread's subject, then the `sourceThread` edge to the thread's Threads item.
3. Return `{ proposalId, status }` to the agent.
4. Tests: the tool creates one `proposed` card with the name and the source edge and no task; a repeated call with the same name returns the same card; a different name creates a second card; a merged-away thread id creates the card for the current thread; an unknown or foreign thread is not found; an empty or too long name is rejected and writes nothing.

## Scope

### In scope

- The `mail.thread.proposeTask` tool, the card it writes with its source edge, and the duplicate rule.

### Out of scope

- Confirming a `mailThread` card into a task, and its schema (the `mailThread` kind and the `sourceThread` relation): #2034.
- Creating a thread task directly from Semp: not done, because Semp proposes through the Inbox.
- AI extraction of a due date.
- Exposing the tool over MCP.

## Acceptance criteria

- When Semp calls `mail.thread.proposeTask` with a thread and a name, then one `proposed` card with `kind` `mailThread`, a Tasks envelope with that name and a `sourceThread` edge to the thread exists, and no task and no Threads.tasks edge was created.
- When the same name is proposed again for the thread while the first card is still `proposed`, then the existing card is returned and no second card exists.
- When the thread id is merged away, then the card is linked to the current thread.
- When the thread is unknown or foreign, or the name is empty or longer than 500 characters, then the call fails and nothing is written.
