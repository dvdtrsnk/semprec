**Blocked by:** #1695, #1707
**Model tier:** medium

## Context

Model tier rationale: A per-tenant sweep that re-enters the existing idempotent job and checkpoint seams, plus a small change to how a failed re-run of a finished transcript is recorded; paid-call fan-out is bounded by the selection predicate and per-tenant budgets.

#1695 makes structured meeting notes (`computed.meetingNotes`) part of every finished transcript. Transcripts finished before that change have segments and a free-text summary but no notes, so their detail view would stay without title, decisions and action items. Re-running the pipeline for such a transcript is cheap and safe: `enqueueTranscriptionJob` (`backend/packages/data/src/transcription/transcriptionJob.ts`) re-enqueues under the original job key and every step resumes from its checkpoint, the summarize step skips when its key exists, so the paid audio stages (diarization, speech recognition) are not repeated. Only the summarize call is paid again.

System work runs per tenant (`docs/adr/2026-10-06-system-work-fans-out-per-tenant.md`); the post-migration cutovers already do (`runTenantCutoverMigrations` in `backend/packages/data/src/db/tenantCutoverMigrations.ts`, which runs every registered cutover once for each maintained tenant in that tenant's scope).

Decision: the sweep is a tenant cutover that enqueues only transcripts that are `done`, have `computed.segments`, have no `computed.meetingNotes`, and whose `item_automation` is not `error`, `locked` or `pending`. Failed rows are already handled by the daily requeue sweep, a locked row must never be touched, and a pending row is already being worked on. Because the predicate selects on the missing key, running the cutover repeatedly converges and does not enqueue a transcript whose notes exist.

Shared-file ordering: this issue also waits for #1707 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `testing`, `state-writes` and `ai-gateway`.

1. Add `backend/packages/data/src/transcription/meetingNotesBackfillCutoverMigration.ts` exporting `runMeetingNotesBackfillCutoverMigration(pool)`: in the current tenant's scope, select the transcripts matching the predicate above and call `enqueueTranscriptionJob(client, { fileItemId })` for each, with the `fileItemId` read from the transcript's `link` (`readTranscriptionSourceFileItemId`); a transcript whose `link` is not a Files item link is skipped with a warning, like the requeue sweep does. Process at most a bounded batch per run (for example 200 transcripts), so a very large tenant is finished over several runs rather than in one transaction.
2. Register it in `runTenantCutoverMigrations` (`tenantCutoverMigrations.ts`).
3. Make sure a re-run of a `done` transcript does not regress visible state: its `status` property stays `done` throughout (only `item_automation` moves through `pending`), no new speaker or Event card is created (match and suggest steps converge on their existing edge, card or checkpoint), and the summarize step writes `meetingNotes` and nothing else. In `recordTranscriptionFailure` (`transcriptionTask.ts`), a permanent failure of a re-run on a transcript whose `status` is already `done` records the failure in `item_automation` only: it does not set `status = error` and does not write the `automation_error` notification, because the user's finished transcript is still complete. Document that in the function's comment.
4. Tests in `backend/packages/data/src/transcription/__tests__/meetingNotesBackfillCutoverMigration.test.ts`: a done transcript without notes is enqueued once; transcripts with notes, in error, locked or pending are not; a second run enqueues the same one only while notes are still missing; the batch limit; and pipeline tests in `backend/services/semprec-transcribe/src/transcriptionTask.test.ts` showing a rerun of a done transcript pays only the summarize call, and that a permanent failure of such a rerun leaves `status` as `done` and writes no notification.

## Scope

### In scope

- The per-tenant, bounded, idempotent enqueueing of transcripts that lack meeting notes.
- Keeping a finished transcript's `status` and notifications unchanged when such a re-run fails permanently.

### Out of scope

- Producing the notes: #1695.
- Re-running speech recognition, diarization, speaker suggestion or Event matching for old transcripts.
- Changing the daily requeue sweep for failed transcripts.
- Backfilling the recording duration or finish time of old transcripts (#1469 owns that).

## Acceptance criteria

- When the cutover runs for a tenant with finished transcripts that have no notes, each gets exactly one job under its original key, and after the jobs run each has `meetingNotes`.
- Transcripts that are in error, locked, pending, or already have notes are not enqueued.
- Running the cutover again after the jobs finished enqueues nothing.
- A re-run of a finished transcript makes no diarization or speech recognition call and creates no new card.
- When a backfill re-run fails permanently, the transcript still shows `status` `done` and no failure notification is created.
- The cutover for one tenant never reads or enqueues another tenant's transcripts.
