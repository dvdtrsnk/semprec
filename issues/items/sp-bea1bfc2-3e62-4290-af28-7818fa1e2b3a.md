### Requirement gh-1763: [subpages 10/12] Trash a host's subpages together with the host

#### Context

Model tier rationale: The same hook mechanism as for pages applied to every other database, with an existing helper for the subtree and trash fixtures, but it runs on every deletion in the system so the no-subpage path must be cheap and safe.

Pages that hang under a host item (a project's notes, an area, an event, a Journal day) are items of the hidden `pages` database with a `parentItemId` pointing at the host (#1676). The generic cascade of `itemDeleteWithClient` (`backend/packages/data/src/chokePoint/itemTrash.ts`) knows only inline databases, so deleting a host leaves its subpages live and reachable by link, and restoring it restores nothing of them. #1723 registers delete and restore hooks for Pages items and a helper that collects a page's subtree; the hooks of #1601 run for every row of the cascade, including the rows of a host's inline databases.

This issue extends the same hooks to every other database so that deleting a host trashes its subpages (with the host's `deletedAt`), and restoring the host restores the subpages trashed with it. Each trashed subpage removes its block from the host's document and records its position, exactly as #1723 defines, so after the restore the host's notes look as before.

Decisions:
- The hooks run for items of every database except `pages` (that case is #1723) and exit immediately when the tenant has no `pages` database or the item has no live subpages; no schema change or index is added because the `pages` partition is small.
- A subpage that was already in the trash before the host was deleted stays there when the host is restored.

Shared-file ordering: this issue also waits for #1761 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

Load `state-writes`, `error-handling` and `testing`.

In `backend/packages/data/src/docs/pageTrash.ts` add `hostItemDeleteHook` and `hostItemRestoreHook`, registered in `domainWriteHooks.ts` for all databases: the delete hook finds live Pages items whose `parentItemId` is the item just trashed and trashes each with `itemDeleteWithClient` (writer kind, agent fields and acting user from the hook context), whose own hooks from #1723 remove the blocks, record positions and trash nested pages; the restore hook restores Pages items whose `parentItemId` is the item just restored and whose `deletedAt` equals the context's `deletedAt`.
2. Skip quickly when the item's database is `pages` or no `pages` database exists for the tenant.

Tests: deleting a project trashes its two subpages and their nested page, hides them, and removes their blocks from the project's notes; restoring the project returns all of them and the blocks; a subpage trashed earlier stays trashed after the host is restored; deleting an area, an event and a Journal day with a subpage behaves the same; a project without subpages deletes exactly as before; a subpage hosted by an item inside an inline database is trashed when the cascade reaches that item; a failing hook rolls back the host deletion.

### Requirement gh-1765: [block-editor 13/13] Replace a page from Markdown with an If-Match version

#### Context

Model tier rationale: Replacing a page applies a content diff under optimistic concurrency and, in the same transaction, trashes subpages whose links disappeared, so it combines concurrency control, id-preserving CRDT edits and destructive cascades.

Pages can be read as Markdown with a version token (#1678) but cannot be written back. Today all doc writes go through `mutateDocWithClient(client, docId, origin, fn)` in `backend/packages/data/src/docs/docPersistence.ts`; `getOrCreateDoc` in `backend/packages/data/src/docs/docsStore.ts` creates the doc lazily. Clients (web, desktop, the assistant) edit a page as one Markdown text and must not overwrite a concurrent edit.

This issue adds replacing the whole page body from Markdown, guarded by the ETag that #1678 returns. It builds on #1610 (atomic multi-block operations), #1676 (subpages: how a page link relates a block to a child page), #1725 (renaming a subpage, which a link-text change triggers) and #1723 (trashing a page with its subpages and parent block, which a vanished link triggers). #1844 classifies the operation for agents.

Decisions:
- A page link that disappears from the Markdown sends the subpage to the trash in the same transaction, using the trash operation of #1723. The sweep of orphaned subpages (#1749) remains a safety net only. Reason: the user removed the line, so the result must be visible immediately and atomic with the edit. Decided by the product owner: the client shows a toast with Undo for each trashed subpage, and the page stays restorable for 30 days; Undo is the restore of #1723 (`POST /api/items/:id/restore`), which puts the block back at its place.
- The title is never changed by replace. A leading `# Heading` is an ordinary `h1` block.
- A page link may only point to an existing subpage of this same page. A link to an unknown id or to a page with another parent is rejected with `400`; moving a page is not done through Markdown. Replace never creates a subpage.
- A link whose text changed renames the subpage through the rename operation of #1725.

### Requirement gh-1767: [transcripts 09/19] Create an Event task from a transcript action item

#### Context

Model tier rationale: A multi-write transaction (task, relation, state row) guarded by an idempotency key and a row lock, with an undo that must not resurrect or double a task, across the transcript, Tasks and People seams and a new cross-database read; the double-click, undo and trashed-task cases are concurrency and cleanup-ownership problems, so the higher tier is warranted.

Meeting notes (#1695) hold the action items of a recording, and #1754 stores what the user did with each (followed it). This issue lets the user turn one of their own action items into a task of the recording's Event and take it back, and it shows the state of each item and the proposals an Event offers.

Today nothing connects action items to tasks: the Events `actionItems` relation (Events to Tasks) is never filled by anything except a recurring task carrying it forward, and the `computed` cache has no user write path. Item creation supports an `Idempotency-Key` through `insertItemWithReplay` (`backend/packages/data/src/chokePoint/itemsStore.ts`): a replay returns the live item, and a reservation whose item is in the trash or purged is released so the same key creates a new item. That is exactly the double-click and undo behavior wanted here.

This issue builds on #1695 (the notes), #1754 (the state table), #1509 (the tenant's own person, which decides which items are "mine"), #1590 (create an item together with its relations in one write) and #1724 (a task linked to an Event inherits the Event's project and people by rule, so this issue does not copy them).

Decisions:

- By the product owner: undo ("Back" after "Added") soft-deletes the task (30-day trash, so it stays restorable) and clears the state; it does not merely detach the task from the item.
- An item is "mine" when its `ownerSpeaker` is mapped through the transcript's `speakers` edge to the person that is the tenant's own person (#1509); everything else, including an item with no owner, is not mine. The task route itself does not refuse another person's item (the client decides what to offer).
- By the product owner: the Event's proposals list offers only items that are open and either mine or without an owner. Another person's item is never offered there, because it belongs to that person. The transcript detail endpoint and this list use one shared function, so the two cannot disagree.
- `added` is only reported while the task is alive; a task deleted or purged elsewhere makes the item `open` again on the next read, and a new task can then be created (the old idempotency reservation is released by the store).
- Following an item (`noted`) does not block adding it: adding replaces the `noted` state.

### Requirement gh-1770: [transcripts 10/19] Assign a transcript speaker atomically and settle its card

#### Context

Model tier rationale: One transaction that combines existing, already guarded writes (the `speakers` edge with its validation hook, a proposal status settle) behind a new route, plus one read route; the care points are the single-person-per-key rules and the edge-then-card ordering, both covered by existing tests of `transcriptionSpeakerEdges.ts`.

A transcript's speakers are anonymous keys (`SPEAKER_00`, ...) that a user maps to people. Today a client maps one through the generic relation endpoint `PUT /api/items/<transcriptId>/relations/speakers/<personId>` with `{ metadata: { speaker } }`. The choke point validates the edge (`assertSpeakerEdgeWritable` in `backend/packages/data/src/transcription/transcriptionSpeakerEdges.ts`: metadata exactly `{ speaker }`, the key must occur in the transcript, no other person may already hold the key), but replacing the person of a key takes two client calls (remove the old edge, add the new one), the write does not settle the Inbox card that asks "who is this speaker" (`transcript-speaker-suggestion:<transcriptId>:<speaker>`), and a client has no way to list the people it could offer: `Events.people` is one-directional and item responses do not include relations.

This issue adds two routes of the systemDatabases module next to the transcript routes it builds on (#1576 owns the manifest and the transcript detail read): `PUT /api/transcripts/:id/speakers/:speaker` assigns, replaces or clears a speaker's person atomically and settles the card, and `GET /api/transcripts/:id/speaker-candidates` returns the people a client can offer. It uses the tenant's own person (#1509), the invitation state on Event participant edges (#1757), and the relation-edge realtime invalidation of #1621 (the edge write publishes it, so other devices refresh).

Decisions:

- By the product owner: the people offered for a speaker are the named participants of the transcript's Event and the user's own person; a person already mapped to a speaker is not offered. The candidates endpoint returns every participant, each with its invitation state and the speaker key it is already mapped to, so the client can hide mapped people; the server applies no invitation filter.
- A person already mapped to another key is refused with `400 validation_failed` and reason `personAlreadyMapped`; nothing is moved silently.
- The response carries `title: null` and the existing `relationship` of the person. By the product owner: no job-title property is added to People in v1, so `title` stays empty.
- By the product owner: a confirmed assignment adds the person to the participants of the transcript's linked Event when they are not among them yet (as the confirm of a speaker card does, #1671). Replacing or clearing an assignment never removes anyone from the Event's participants.
- The organizer of the Event is the tenant's own person and is returned separately as `self`, not in `participants`.

Shared-file ordering: this issue also waits for #1767 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1758: [links 12/12] Require approval when Semp would break a value link

#### Context

Model tier rationale: This adds one more trigger and payload to an already existing deferral mechanism across known gateway, snapshot and store seams with existing fixtures, so it is medium.

A value link records that a target item's value (for example a file's project) is inherited from a source item (for example the task the file belongs to). #1516 makes a user or agent write that changes such a value break the link (the link goes from on to broken and records who broke it). Without this issue an agent could end such a link silently, the file would stop following the task's project and nobody would be told.

#1713 provides the generic mechanism: inside the write transaction the choke point flags an agent write, throws `ApprovalRequiredForWrite`, the gateway turns it into an approval request with a resource snapshot, and the approved write is revalidated and replayed exactly once; `item_patch`, `relation_put` and `relation_set` are already snapshot kinds, but nothing triggers it yet: a plain `relation.set` that replaces an edge is an ordinary non-destructive write with the `write` risk class and needs no approval (decided by the product owner). #1587 adds `link.unlink`, which also ends a link. This issue adds the first trigger: an agent write that would break a value link.

Decision: only agent writers with a run (`agentRunId`, #1415) are deferred; a user write that breaks a link stays immediate (as #1516 defines), and so does an `/mcp` call with a human session, which #1415 records as an agent write without a run (the link still records `broken_by` agent). A write by an agent to a property that has no active link stays immediate, including a `relation.set` that replaces an edge of such a property. `relation.delete` already requires approval; only its payload gains the same link information.

Decision (product owner): the request text describes the operation that really runs, so the approval is not misleading. For a file whose project follows a task, it names the write of the file's project relation to the new project, not a generic "change the file's project".

Decision (product owner): no separate detail route. The approval detail view reads one request with the existing `GET /api/approval-requests/:id` (#1786), so the link information is returned there too.

#### Task

Load `state-writes`, `error-handling` and `testing`.

1.
