## Context

Model tier rationale: One known mechanism (two system-owned Events properties computed by a pre-write transform, plus a per-tenant backfill cutover) across defined seed, choke point and cutover seams, but the backfill touches every existing Event and the properties are an external identity contract.

An iCalendar invitation identifies a meeting by a stable `UID` and orders its revisions by `SEQUENCE`. Events have neither today: the Events database (`backend/packages/data/src/seed/seedTenDatabases.ts`) has no identity that can be sent to another calendar and matched on a reply. #1774 (sending invitations, updates and cancellations) and #1950 (applying replies) both need it.

The Events database is `schema_locked` once seeded, so an existing tenant gets new properties only through a code-level cutover that writes SQL directly, as `transcription/transcriptsCatalogCutoverMigration.ts` does and as the Events cutover from #1416 does; the cutover of this issue runs after that one. Values are computed inline by the per-module pre-write property transform that #1422 adds to the choke point, following `docs/adr/2026-09-19-derived-system-properties-computed-inline-at-choke-point.md`, so no caller supplies or can forge them: both properties are `owner: 'system'` and `locked: true`, so a generic `PATCH` of either is rejected with 403 `forbidden`.

Rules computed by the transform:

- On create, `icalUid` is `<random uuid>@semprec` (the item id is not known to the transform yet) and `icalSequence` is 0. A value a caller passes on create is overwritten.
- On update, `icalSequence` increases by 1 when the effective value of any of `date`, `endDate`, `timeFrom`, `timeTo` or `place` differs from the stored one. Comparing effective values means values after the Events time normalization of #1598 when that transform is registered (this transform must then run after it, so that `9:00` written as `09:00` does not count as a change); otherwise the raw trimmed values are compared. An update that changes none of the five keys leaves the sequence alone.

Decision: the sequence changes for any change of those five keys, whether or not anybody was invited; the invitation code decides whether to send anything.

Shared-file ordering: this issue also waits for #1594 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

1. In `backend/packages/data/src/seed/seedTenDatabases.ts`, add to the Events property list: `icalUid` (type `text`, owner `system`, `locked: true`) and `icalSequence` (type `number`, owner `system`, `locked: true`), declared the way the derived `time` property of #1416 is.
2. Add the pre-write transform for Events in `backend/packages/data/src/calendar/eventIcalIdentityTransform.ts` implementing the create and update rules above, and register it through the registry added by #1422 (the Events entry) in `backend/packages/data/src/domainWriteHooks.ts`, after the Events time transform if it exists.
3. Add the cutover `backend/packages/data/src/calendar/eventsIcalIdentityCutoverMigration.ts`: per tenant, in the order of `docs/adr/2026-09-10-app-code-post-migration-steps.md`, insert the two property definitions into the existing Events database by direct SQL (identical to the seed's; no-op when already present or when the tenant has no Events database), then backfill every Events item (including trashed ones) that has no `icalUid` with `<item id>@semprec` and `icalSequence` 0 in batches of 500 ids, each batch in its own transaction, idempotent through `NOT (properties ? 'icalUid')`. Register it in `runTenantCutoverMigrations` in `backend/packages/data/src/db/tenantCutoverMigrations.ts` after the cutover from #1416.
4. Add the display names under `property.events.icalUid.name` and `property.events.icalSequence.name` to `backend/packages/data/src/seed/i18n/cs.json` and `en.json`.
5. Tests: a created Event has a UID ending in `@semprec` and sequence 0, and a caller-supplied value is ignored; changing `timeFrom`, `date`, `endDate`, `timeTo` or `place` bumps the sequence by 1, changing `name` or normalizing `9:00` to `09:00` does not; a generic `PATCH` of either property is 403; the cutover adds the properties and backfills existing and trashed Events with unique UIDs, a second run changes nothing, and a tenant without Events is skipped; a fresh seed and a cut-over tenant have identical definitions.

## Scope

### In scope

- `Events.icalUid` and `Events.icalSequence`, their computation at the choke point, and the per-tenant backfill.

### Out of scope

- Building or sending any iCalendar message: #1774.
- Applying replies by `UID`: #1950.
- Participant roles and invitation state on edges: #1757.
- Generating a new UID when an Event is duplicated: a duplicate is a create, which the transform already covers.

## Acceptance criteria

- When an Event is created through any path (generic API, Semp, MCP, Inbox), then it has an `icalUid` of the form `<uuid>@semprec` and `icalSequence` 0.
- When `date`, `endDate`, `timeFrom`, `timeTo` or `place` of an Event changes, then `icalSequence` increases by 1; when only other properties change, it does not.
- When a client sends a generic `PATCH` of `icalUid` or `icalSequence`, then the response is 403 `forbidden`.
- When the cutover runs for a tenant with existing Events, then every Event (trashed ones included) has a distinct `icalUid` and sequence 0; a second run changes nothing.
