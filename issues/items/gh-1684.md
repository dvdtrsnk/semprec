## Context

Model tier rationale: batched tenant read projection, no write or new isolation. #1543 serves history; #1682 stores ID-only refs, while older turns may have labeled refs. Resolve names at read time so old messages survive rename/move. Items use their database's title property; soft trash sets deleted_at, restore reverses it, and purgeExpiredTrash removes rows after 30 days. Mail attachments have filename. #1888 adds changed-item cards later. Structured approval descriptions and nullable names/keys follow the batch reconciliation, without rendered fallback text.

## Task

Load `canonical-keys` and `testing`.

1. In the thread-history read from #1543, resolve every ref of the returned page of messages in batches (one query per kind, keyed by id, not per ref) and add to each ref a `resolved` object `{ label, databaseKey, state }`:
   - `item`, `block` and `transcriptSegment`: `label` is the item's current `name`; `databaseKey` is the key of the item's database (for example `tasks`); for a block ref the label is the item's name as well.
   - `mailAttachment`: `label` is the attachment's `filename`; `databaseKey` is the key of the Emails database of its message.
   - `agentRun`: label is the first 120 Unicode code points of task, without an added ellipsis; databaseKey is null. `approvalRequest`: label is the validated structured ApprovalDescription (key, params, optional endsInheritance), or null for legacy NULL, and databaseKey is null; it is not rendered text. Share the response type without a data-to-shared reverse import.
   - label is otherwise string or null; databaseKey is string or null. Missing/null item names yield null; preserve valid strings, including empty strings. Read the actual title property rather than inventing a name. For item/block/transcriptSegment, state follows the underlying item's deleted_at/absence; gh1733 separately handles unavailable blocks/ranges. Attachment state follows its own row, not parent item trash; resolve its nullable database key through the actual message. Present agent runs/approvals are active regardless of workflow status.
   - Enrich recognized strict unlabeled refs and historical strict labeled refs, preserving stored labels and context bytes in storage. Pass unrecognized historical context/entries through unchanged, without target lookup; resolve recognized entries independently in mixed arrays. No new locks, common snapshot, write or access grant. Validate structured JSON through its existing owner; malformed non-null descriptions fail as data corruption, not purged.
   - `state` is `active` for an existing live object, `trashed` when `deleted_at` is set, and `purged` when the row no longer exists (then `label` and `databaseKey` are null).
2. Define the response type in the shared package next to the message ref schema and export it.
3. Tests: a renamed item shows its new name; a soft-deleted item gives `trashed`; after the purge job runs, `purged`; an attachment shows its filename; one history page with many refs of one kind issues one query for that kind (assert by query count or a spy on the store function).

## Acceptance criteria

- When an attached task is renamed, then the next history read shows the new name for the old message.
- When an attached item is soft-deleted, then its ref has `state: "trashed"`; when it has been purged, then `state: "purged"` with null label.
- When an attached e-mail attachment is read, then its label equals the stored filename.
- A history page of 50 messages with refs of one kind runs a constant number of resolver queries.
