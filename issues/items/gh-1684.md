## Context

Model tier rationale: A batched read-side resolver over existing tables with a small response contract, covered by fixtures; no write path or new isolation rule.

#1543 serves a Semp thread's message history, and #1682 stores validated refs in each message's `context`. A stored ref carries only ids. The client needs, for each ref, a current display name and whether the object still exists, so a chip such as "Call the plumber" can be drawn after the object was renamed, moved or deleted.

Today deletion of an item is soft: `items.deleted_at` is set, `item.restore` brings it back, and `backend/packages/data/src/trash/purgeExpiredTrash.ts` removes it for good after 30 days. An item's name is its `name` property (the `title`-typed property of its database). An e-mail attachment is a `mail_attachments` row with a `filename`.

This issue adds the resolved view of each ref to the history response. #1888 builds on it for changed-item cards.

Decision: refs survive renames and moves because they store ids only; the label is always resolved at read time, never stored.

## Task

Load `canonical-keys` and `testing`.

1. In the thread-history read from #1543, resolve every ref of the returned page of messages in batches (one query per kind, keyed by id, not per ref) and add to each ref a `resolved` object `{ label, databaseKey, state }`:
   - `item`, `block` and `transcriptSegment`: `label` is the item's current `name`; `databaseKey` is the key of the item's database (for example `tasks`); for a block ref the label is the item's name as well.
   - `mailAttachment`: `label` is the attachment's `filename`; `databaseKey` is the key of the Emails database of its message.
   - `agentRun` and `approvalRequest`: `label` is the run's task text truncated, or the approval's description; `databaseKey` is null.
   - `state` is `active` for an existing live object, `trashed` when `deleted_at` is set, and `purged` when the row no longer exists (then `label` and `databaseKey` are null).
2. Define the response type in the shared package next to the message ref schema and export it.
3. Tests: a renamed item shows its new name; a soft-deleted item gives `trashed`; after the purge job runs, `purged`; an attachment shows its filename; one history page with many refs of one kind issues one query for that kind (assert by query count or a spy on the store function).

## Scope

### In scope

- Batched label, database key and state resolution for the refs of returned messages.

### Out of scope

- Validating refs on write: #1682.
- Changed-item cards in the history: #1888.
- Localized client wording for trashed and purged objects; the backend returns only the state.
- Restoring a trashed object; `item.restore` already exists.

## Acceptance criteria

- When an attached task is renamed, then the next history read shows the new name for the old message.
- When an attached item is soft-deleted, then its ref has `state: "trashed"`; when it has been purged, then `state: "purged"` with null label.
- When an attached e-mail attachment is read, then its label equals the stored filename.
- A history page of 50 messages with refs of one kind runs a constant number of resolver queries.
