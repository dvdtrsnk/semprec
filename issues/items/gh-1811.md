**Model tier:** high

## Context

Model tier rationale: This adds a new realtime message across the publisher, the wire protocol and the client package, with tenant-scoped fan-out and after-commit emission from several processes, so an error leaks data to another tenant or loses updates.

Cards change without any client action: a new capture produces a proposal, a tick or the transcription process writes or updates a card, a chat revision rewrites it, an approval arrives, and a decision on another device closes it. Clients need to learn that the stack and the count are stale and then re-read `GET /api/inbox/cards` and `GET /api/inbox/cards/count` (#1807, #1823).

Today `RealtimeMessage` in `backend/packages/realtime/src/pgNotifyPublisher.ts` knows invalidations with scope `item` and `schema`, delivered only to sockets of the tenant (`docs/adr/2026-10-16-tenant-scoped-realtime-fan-out.md`, which replaced the thin user-scoped invalidations). Item invalidations are emitted for each item by `backend/packages/data/src/realtimeHook.ts`, and for `approval_requests` only the `approval_pending` notification is sent. The agents process did not publish at all before #1383.

This issue adds an invalidation scope `inboxCards` with the operation `created`, `updated` or `closed`, the `cardId` and an optional `userId`, emitted after commit from every place that changes a Processing proposals card: the tick, the transcription process, the card actions (confirm, reject and the other card actions) and the revision from a Semp thread. Changes to approval requests are announced by the separate approval request invalidation (#1789); a client refreshes the stack on either.

Decision: delivery is to the sockets of the tenant only; `userId` only narrows the delivery within the tenant and is never the sole access boundary. The message is thin: no card content.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. In `pgNotifyPublisher.ts` add to `RealtimeMessage` the message `{ type: "invalidation", scope: "inboxCards", op: "created" | "updated" | "closed", cardId: string, userId?: string }` and its parse/serialize branch, with the tenant resolved by Postgres from the publisher's scope as for the other scopes.
2. In `backend/packages/realtime/src/protocolV1.ts` add the matching outbound frame, following the pattern used for the existing invalidation frames, and handle it in `backend/packages/realtime/src/syncServer.ts` fan-out (tenant sockets, `userId` narrowing).
3. In `backend/packages/realtime-client` add the frame to the typed server frames (`src/serverFrame.ts`) and expose it through `syncClient.ts` and the package `src/index.ts`.
4. In `backend/packages/data/src/realtimeHook.ts` add the event type and a `setInboxCardsInvalidationHook` pair (default no-op), and wire it in `backend/packages/realtime/src/wireHooks.ts` so the agents, api and transcribe processes publish it.
5. Emit the event with `runAfterCommit` from every writer of Processing proposals cards: card creation and updates in `inbox/inboxTickAction.ts` (including the compute-failure write of #1485, because cards in `computing` and `computeFailed` appear in the list), the transcription card producers (`transcription/transcriptEventMatch.ts`, `transcription/transcriptSpeakerSuggestion.ts`), and the confirm and reject paths in `inbox/proposalActions.ts` (`op: closed` when a card leaves the stack, `created` for a new card, `updated` otherwise). Put the emission in one helper in a new file `inbox/inboxCardsRealtime.ts` so writers call a single function.
6. Tests: a confirm on one device sends `inboxCards` with `op: closed` to a second socket of the same tenant; a write from an agent run (using the wiring from #1383) is published; a socket of another tenant receives nothing; the message carries no card content; `protocolV1.unit.test.ts` and `realtime-client` unit tests cover the new frame.

## Scope

### In scope

- The `inboxCards` invalidation across publisher, protocol, client package and hook, and its emission from the existing writers of cards.

### Out of scope

- Approval request invalidations: #1789.
- Emission from writers added by later issues (the revise route #1870, the edit routes, reject #1845); they call the helper when they are built.
- Content in the message; clients re-read the list and the count.
- Badge counts and push badge updates.

## Acceptance criteria

- When a card is confirmed on device A, then device B of the same tenant receives an `inboxCards` invalidation with `op: closed` and the card id, and re-reading the count shows one fewer.
- When a run in `semprec-agents` or `semprec-transcribe` writes a card, then the tenant's sockets receive `created` or `updated`.
- When the tick records a compute failure on a card, then the tenant's sockets receive `created` or `updated` for that card.
- A socket of another tenant never receives an `inboxCards` message.
- The message contains no card content, and a failed NOTIFY does not roll back or fail the card write.
