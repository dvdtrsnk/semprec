## Behavior specification

Mail as items: company and project of a thread, triage, attachments and tasks.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: mail-items-1 (Threads database, company and project, filters, attachments)

#### (a) Decisions adopted from open questions

- Is the thread sender the author of the first or the last inbound message? -> first inbound message -> the company/project of a thread should not flip with every reply. -> Decided by the product owner: the first inbound message; the thread's company and project stay stable (#1869).
- Should triage by Semp be written as an agent run with the generic relation put, or by a system job that owns Threads.project? -> agent writer through the generic relation put, no ownership change -> conservative, keeps the single-writer ownership ADR untouched and Threads.project stays user-owned. -> Decided by the product owner: an agent run through the generic relation put; Threads.project stays user-owned, matching the single-owner model and Semp acting only through defined tools (#1872).
- Souvislosti for a person: count threads or messages? -> threads (client copy showing 4 must be corrected to 1). -> Decided by the product owner: threads are counted and the client copy is corrected (#1874).
- Should an attachment sent from an existing file keep the project from its event or take the thread's? -> keeps its own source; only Files items created by ingest are linked. -> Decided by the product owner: it keeps its own source; only files from mail ingest are linked to the thread (#1898).
- Existing attachments of existing threads: backfill the inheritance? -> no -> it would overwrite values users already set. -> Decided by the product owner: no; values a user already set must not be overwritten (#1898).
- Item name of a Threads item: renamed with later messages? -> no, first message subject only. -> Decided by the product owner: no, the first message's subject only; the name stays stable (#1573).
- Facets independent of box/folder/mailbox filters, counting visible threads (not deleted, not Junk/Trash) -> simplest well-defined rule. -> Decided by the product owner: independent, counting only visible threads (#1747).

#### (b) Open questions for the product owner

- Merge precedence is own value over inherited, then older thread; confirm that a winner without a value taking the loser's value is wanted.
- How a user replaces a thread's project (delete the edge and put another, or a replace semantic of the generic relation put) is not settled; the single-value hook only rejects a second different edge.
- Which actor identity and run record Semp triage writes under when no agent run exists (it writes as an agent writer without a run row in this draft).
- Whether a thread could still need Threads.project/company writable by Semp without breaking ownership if the module-owned moves in the merge are rejected for user-owned relations (merge may need the explicit ownership handoff of the single-writer ADR).
- Files list for the thread-level paths of the read model (mailThreadsStore.ts, mailThreadRouteHandlers.ts) are assumed names for files created by the thread list/detail issues.

#### (c) Behavior delivered

Every mail thread becomes an item of a Threads database, so it can carry a company and a project. Both are inherited: the company from the sender's person or the sender's domain matched against company websites (never for freemail), the project from the company's single active project; a manual change by the user or Semp ends the inheritance and relinking restores it, and Semp sorts the remaining threads into a project on its own when confident. Attachments take the thread's project and follow its changes. The mailbox can be filtered by project, area and person, with per-area and per-project counts in one call, and a person's related list shows the count of their threads. Thread list and detail return company, project and the link state, and merged threads keep one Threads item with the right values.


### Decisions: mail-items-2 (tasks from a thread)

#### (a) Decisions adopted from open questions

- Should "Semp suggests another task from the thread" create the task directly or a proposal in the Inbox? -> the draft created it directly through the generic item create and relation put. -> Decided by the product owner: a proposal in the Inbox; Semp must not create items silently and the proposal can be edited before confirming. #2034 adds the thread task card and its confirm (through the creation function of #1900) and #2035 the Semp tool that proposes it; #1900 no longer lets Semp create thread tasks directly. The fallback the product owner allowed (a direct create only on the user's explicit request in chat, if the proposal mechanism were unavailable) is not needed, because the Inbox proposal mechanism exists.
- Should AI extract the due date too? -> no, the name only; the date comes from the request. -> Decided by the product owner: no, the name only; the user sets the date and the AI does not infer it (#1900).
- Are removals of participants propagated to task people? -> no, additions only -> conservative, avoids deleting people a user may have accepted. -> Decided by the product owner: additions only; people a user may have accepted are not removed silently (#1923).
- List order of a thread's tasks: not-done first, then due date ascending (undated last), then creation time. -> Decided by the product owner: as stated (#1692).
- Tasks created by Semp (not the HTTP route) get the project by the link rule but get people only when a new participant arrives. -> Decided by the product owner: the project by the link rule, people only on a new participant (#1923). With the Inbox proposal decision above Semp no longer writes thread tasks itself; a task from a confirmed Semp proposal is created by the user's confirm through the function of #1900 and so also gets the conversation's people at creation, like a task from the route.

#### (b) Open questions for the product owner

- The source descriptor of an inherited value whose source is the conversation (not a property of one item) is defined by the value-link store; the draft uses the thread's Threads item as the source and the implementer must follow that store's shape for a computed source.
- Rule that a task has one inheritance source (thread or event action item) is not enforced anywhere yet.

#### (c) Behavior delivered

A task can be linked to a mail thread through the relation Threads.tasks. Creating a task from a thread through the API names it by AI from the conversation when no name is given (a thread changed in the meantime gives 409, an exhausted AI budget gives an error and no task) and gives it the thread's project and the conversation's people as inherited values. Semp suggests further tasks from a thread as Inbox proposals that the user can edit and confirm; only the confirm creates the task, with the same thread link and inherited values. New participants in the thread are added to the people of its tasks unless the people were changed by hand. The thread detail lists exactly the tasks made from the thread with their project, people and link state.
