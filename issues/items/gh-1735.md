## Context

Model tier rationale: Shared owners.

When an item is created from an Inbox capture, its page should say where it came from, as editable text: "Created from Inbox: <name of the Inbox item>". Today the confirm path (`confirmProposalWithClient` in `backend/packages/data/src/inbox/proposalActions.ts`) creates the item and writes no page content for it. #1679 adds inserting Markdown at a placement in a page, which this issue uses.

Decision: the server writes the paragraph at confirm time, rather than the client composing it from the origin, because the note must be ordinary editable page content (the user can rewrite or delete it) and must exist for every client, including agents reading the page as Markdown. The note is written once at creation and never rewritten afterwards. Decision (product owner): the note reads "Created from Inbox: <item name>", where the item name is the text of the source Inbox item, and it is written only for items the confirmation created, never for items it only patched or linked. The fixed phrase is an i18n catalog entry so it follows the user's language. Like every block a confirmation inserts, the paragraph is authored by the user who confirmed.

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. In the confirm transaction, after the created item exists and its origin is recorded, insert one paragraph at the start of the created item's page using the page-insert operation from #1679. Only items created by the confirm step receive it; patched or merely linked items do not.
2. Build the text as the localized fixed phrase followed by the source Inbox item's text; nothing else is added (no capture time and no sentence about other steps).
3. Add the fixed phrase as an i18n catalog entry (Czech and English) in the seed message catalogs.
4. A failure to write the note rolls the whole confirmation back, like any other step; a repeated confirm does not add a second note.
5. Tests: confirmed item page contains the paragraph as an ordinary block reading exactly the localized phrase and the source item's text; an item the confirmation only patched gets no paragraph; repeated confirm leaves one paragraph; editing the paragraph afterwards is not overwritten.

## Acceptance criteria

- When a proposal creating a Files item is confirmed, then reading the item's page as Markdown starts with the origin paragraph "Created from Inbox: <source Inbox item text>" in the user's language.
- When a confirmation only patches or links an existing item, then that item's page gets no origin paragraph.
- When the user edits or deletes the paragraph, then no later operation restores or rewrites it.
- When confirm is repeated on the confirmed card, then the page still has exactly one origin paragraph.
- When the page insert fails, then the confirmation is rolled back and the card stays `proposed`.
