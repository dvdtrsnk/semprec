## Context

Model tier rationale: Eight invariants are precisely defined, but each catalog query must be written by the implementer and the deploy step needs a hermetic shell test.

The catalog test (`backend/packages/data/src/__tests__/tenancyCatalog.test.ts`, built up by #971–#1067) proves the tenancy invariants on the ephemeral test database, but nothing checks the production database, where a manual `ALTER ROLE … BYPASSRLS`, a dropped policy, a grant on an `items_p_*` partition or a hand-edited function would silently re-open a hole that every service would then run on. `deploy/deploy.sh` already runs one-off CLIs before activation — the migrations CLI (`run_migrations`, `deploy.sh:134-141`) and the seed CLI (`run_seed`, `:145-152`) — and any failure up to activation leaves `current` and every service untouched (`deploy.sh:262-280`; `deploy/README.md:63-81`). #996 reorganised which environment file and URL variable those steps use; mirror `run_migrations` exactly as it is when you start. CLIs follow the shape of `backend/packages/data/src/db/runSeedCli.ts:1-14` (`docs/adr/2026-09-23-host-scripts-record-results-through-a-data-layer-cli.md`). `deploy/deploy.test.sh` is the hermetic behaviour test of `deploy.sh`; its `systemd-run` mock (`:80-92`) records each command and fails on marker files.

The invariants, as decided in the tenant-isolation ADR (#968) and built by #971–#973, #997, #1066 and #1067: every table classified by a `semprec:tenancy=tenant|global` comment; every tenant table with `tenant_id uuid NOT NULL DEFAULT app_tenant_default()`, RLS enabled, a RESTRICTIVE `tenant_isolation` policy and a PERMISSIVE `tenant_rows` policy; `app_tenant_default()` strict; the runtime roles `semprec_data` and `semprec_side` neither superuser nor `BYPASSRLS`, not members of such a role and not owners of any table; no runtime-role privilege on any `items_p_*` partition; every `SECURITY DEFINER` function with a pinned `search_path`, not executable by `PUBLIC`, owned by `semprec_router` or by the owner of `items`; every tenant foreign key validated.

## Task

Load `io-hardening` (a pooled connection in a one-off process) and `error-handling` (a verification failure must fail the deploy, never be logged and ignored).

1. Create `backend/packages/data/src/db/tenancyInvariants.ts` exporting `type TenancyViolation = { invariant: string; object: string; detail: string }` and `findTenancyViolations(client: Queryable): Promise<TenancyViolation[]>`, one catalog query per invariant, each row typed:
   - `classification` — a table in `public` (ordinary or partitioned, not a partition) whose comment is not exactly `semprec:tenancy=tenant` or `semprec:tenancy=global`;
   - `tenantColumn` — a tenant table whose `tenant_id` is missing, not `uuid`, nullable, or whose default is not `app_tenant_default()`;
   - `rowLevelSecurity` — a tenant table with `relrowsecurity = false`, without a restrictive `tenant_isolation` policy for all commands, or without a permissive `tenant_rows` policy;
   - `strictDefault` — `pg_get_functiondef` of `app_tenant_default()` references `app_sole_tenant`;
   - `runtimeRole` — `semprec_data` or `semprec_side` missing, `rolsuper`, `rolbypassrls`, a member (`pg_has_role(…, 'MEMBER')`) of a superuser or `BYPASSRLS` role, or a member of the owner of any relation in `public`;
   - `partitionPrivilege` — `has_table_privilege(<runtime role>, <items_p_* oid>, 'SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER')` true;
   - `definerFunction` — a `prosecdef` function in `public` whose `proconfig` has no `search_path=` entry, whose ACL grants `EXECUTE` to `PUBLIC` (a NULL `proacl` counts, being the default), or whose owner is neither `semprec_router` nor the owner of `public.items`;
   - `foreignKey` — an FK whose columns include `tenant_id` with `convalidated = false`.
   In the same file export `verifyTenancy(pool: Pool, output: { info(line: string): void; error(line: string): void }): Promise<0 | 1>`: runs `findTenancyViolations` inside `runAsSystem("verify-tenancy", …)`; with no violation writes `tenancy: verified` to `info` and returns 0, otherwise writes each violation as `tenancy violation [<invariant>] <object>: <detail>` to `error` and returns 1.
2. Create `backend/packages/data/src/db/verifyTenancyCli.ts` in the shape of `runSeedCli.ts`: reads `DATABASE_URL` (throws if unset), `createPool`, sets `process.exitCode = await verifyTenancy(pool, …)` with `console.log`/`console.error`, and ends the pool in `finally`. It never prints the connection string.
3. In `deploy.sh`, add `verify_tenancy()` running `node packages/data/dist/db/verifyTenancyCli.js` with exactly the `systemd-run` properties, environment source and database URL that `run_migrations` uses, failing with `fail "tenancy verification failed"`; call it in `deploy()` right after `run_seed` and before `promote_release`. A rollback does not run it.
4. In `deploy.test.sh`, make the `systemd-run` mock fail when `$TEST_STATE/fail-verify` exists and the command contains `verifyTenancyCli.js`; assert the verify command runs once per deploy after the seed command, and that a `fail-verify` deploy is refused with `tenancy verification failed`, leaves `current` unchanged and restarts nothing.
5. Add step 3's verification to the numbered list in `deploy/README.md`'s "Deploying a release" section.

## Scope

### In scope

- The invariant checks, the CLI, the deploy step and their tests.

### Out of scope

- Changing `tenancyCatalog.test.ts`, which keeps proving the same invariants in CI.
- The per-process startup role assertion (#1051).
- Running the check on `--rollback` (no schema changes there) or on a timer.

## Acceptance criteria

- Integration (`tenancyInvariants.test.ts`): on the migrated test database `findTenancyViolations` returns an empty list.
- Integration: each of the eight invariants, broken inside a transaction that is rolled back afterwards — a table with no tenancy comment; a tenant table's `tenant_id` default dropped; its `tenant_rows` policy dropped; `app_tenant_default()` redefined with the transitional body; `ALTER ROLE semprec_data BYPASSRLS`; `GRANT SELECT` on an `items_p_*` partition to `semprec_data` (not `semprec_side`, which `semprec_data` inherits through `0040_least_privilege_roles.sql:47`, so breaking it would flag both roles); a `SECURITY DEFINER` function without `SET search_path`; a composite tenant FK re-added `NOT VALID` — yields exactly one violation naming that invariant and object.
- Integration: `verifyTenancy` returns 1 and writes one `tenancy violation [<invariant>] …` error line per violation when one exists, and returns 0 writing only `tenancy: verified` otherwise.
- Script (`deploy/deploy.test.sh`, run by hand): a deploy runs migrate, seed and verify in that order before restarting anything; with `fail-verify` the deploy is refused with `tenancy verification failed`, `current` still names the previous release, and no `systemctl restart` is issued.
