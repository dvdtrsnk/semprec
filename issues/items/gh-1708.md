## Context

Model tier rationale: One persisted-state change (a CHECK widening plus two columns) and the job and sweep behavior that use it, on existing fixtures, but the migration touches a tenant-keyed table and the error-text rule is security relevant.

`item_automation` (`backend/packages/data/src/db/migrations/0005_library_module.sql`) has `status` (`pending | done | error | locked`), `error` text, `attempts` and `last_attempt_at`; the store is `backend/packages/data/src/library/itemAutomationStore.ts`. The job (`library/libraryMetadataJob.ts`) writes `done` for any run that did not throw, so "the source found nothing" and "the source found something" are the same state, and on failure `markItemAutomationError` stores the exception message, which can contain URLs and secrets. The 04:00 retry sweep (`library/libraryMetadataActions.ts`, `listErroredItemAutomationForDatabases`) retries only `error` rows, so a title that was not found is never tried again.

After #1655 and #1706, fetchers return an outcome (`found | notFound | error`, `errorCode`, `source`). This issue records that outcome and retries what is worth retrying.

Decisions:
- The stored `done` value is kept and means "found" (the response mapping to `found` belongs to #1768); a new status `notFound` is added to the CHECK.
- `notFound` is decided by the source returning no match, not by a missing cover: a user may remove a cover, and a movie can have data without a cover; neither is `notFound`.
- The exception text is never stored or logged; an error code is stored instead.

## Task

Load `db-migrations`, `error-handling`, `state-writes` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_item_automation_not_found_and_error_code.sql (next free ordinal at commit time)`: widen the `status` CHECK with `notFound`; add `error_code text` and `source text` (CHECK `source IN ('openLibrary','googleBooks','tmdb')` or NULL). Make it compatible with the previous release (additive; see `docs/adr/2026-09-24-rollback-one-release-back-with-checked-migrations.md`) and keep the table's tenant policy intact. Note that the previous release's `mapRow` rejects an unknown status through `assertKnownValue`; the pull request must state how the rollback rule is met (for example by the previous release not reading `item_automation` for rows the new job writes, or by the checked-migration mechanism of that ADR) and follow it.
2. In `itemAutomationStore.ts` extend `ITEM_AUTOMATION_STATUSES`, the row type and mapping with `notFound`, `errorCode`, `source`; add `markItemAutomationNotFound` and let `markItemAutomationDone` and `markItemAutomationError` record `source` and `error_code`. Rows locked by the user are never changed (keep the `status != 'locked'` guards).
3. In the job: outcome `found` writes the data and `done` with `source`; `notFound` writes `notFound` with `source` when known, and applies no property writes; `error` writes `error` with `error_code` and increments `attempts`, then rethrows so the queue's own retry applies; a thrown exception with no outcome maps to `error` with `sourceUnavailable`. The column `error` is no longer written with exception text (write `NULL` or the fixed code); no exception message goes to the logs either.
4. In `libraryMetadataActions.ts` the retry sweep selects `status IN ('error', 'notFound')`; `done` and `locked` are never retried. Rename or generalize `listErroredItemAutomationForDatabases` accordingly.
5. Tests: a not-found fixture gives `notFound`; a 503 fixture gives `error`, `error_code = 'sourceUnavailable'`, `attempts + 1`, and the exception text is in neither the row nor the captured logs; the sweep re-enqueues `error` and `notFound`, not `done` or `locked`; an item whose cover the user removed but that was found stays `done`.

## Scope

### Out of scope

- The fetchers themselves: #1655 and #1706.

## Acceptance criteria

- When a source returns no match, then the row is `notFound` with the source, and the 04:00 sweep tries it again.
- When a source is unavailable (HTTP 503 fixture), then the row is `error` with `error_code` `sourceUnavailable` and `attempts` increased by one; neither the database nor the log contains the exception text.
- When a run finds data, then the row is `done` with the `source`, and the sweep does not retry it.
- When the user removed an item's cover but the source found the item, then the row is not `notFound`.
- When a row is `locked`, then no run or sweep changes it.
- When the migration is applied, then existing rows keep their status and the previous release still reads the table.
