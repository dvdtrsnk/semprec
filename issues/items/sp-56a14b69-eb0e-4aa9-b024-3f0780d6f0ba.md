### Requirement gh-1676: [subpages 02/12] Create a subpage under an item's page

#### Context

Model tier rationale: One transaction must create an item, its document and a block in another document, optionally also create a Journal period, under tenant isolation, with a new hidden system database created at runtime and a catalog operation that every transport exposes.

#1393 records that a subpage is an item of a hidden `pages` system database, with a document of kind `page`, a parent link in `parentItemId`, and a `page` block in the parent document whose `pageId` is the item id and whose text is the title. Nothing of that exists yet: there is no Pages database, no way to create a subpage, and no way to turn an existing block into one. Existing pieces: `getOrCreateDoc` (`backend/packages/data/src/docs/docsStore.ts`) creates the document of a live item idempotently; `mutateDocWithClient` (`docs/docPersistence.ts`) writes a document inside the caller's transaction; the shared block model with its multi-block operations (#1610) cannot convert a block to or from `page` and refuses those cases with a typed error; `ensureJournalPeriodDoc` (#1541) creates a Journal period entry and its page; `getItemPath` (`chokePoint/itemReads.ts`) follows `databases.parent_item_id` only; `page.get` (#1615) returns `breadcrumbs` as null for items outside an inline-database chain. Page operations are members of the generic catalog (#1394).

This issue adds the `pages` database and the `page.createSubpage` operation for one new subpage. Later issues build on it: converting selected blocks into subpages and the breadcrumb walk through `parentItemId` (#2013 and #2014, split out of this one), duplication (#1722), renaming (#1725), title mirroring (#1715), deletion and restore (#1723), and Markdown page replacement (#1765).

Decisions:
- The `pages` database is created on first use (inside the first `page.createSubpage`) under an advisory lock and is `schema_locked`; no seed and no backfill. It has two system-owned properties (owner process `pages`): `title` (title type) and `parentItemId` (text).
- A `page` block carries its title as plain `text` (see the amendment in #1393). The block-model validation and registry therefore accept `text` on `page` blocks and still reject inline attributes there; Markdown conversion (#1608) already writes the title as the link text.
- A host is any live item; its document is created if missing. Only Pages items and hosts with a full editor are meaningful; the server does not know which editor a client shows, so it only refuses a parent that is trashed or foreign.
- Agent classification of the operation is a non-destructive write on the item-write capability; #1844 refines it.

Shared-file ordering: this issue also waits for #1667 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Decision (batch 38 R1 reconciliation): R1 reconciliation: createSubpage remains a non-destructive core.item.write operation, a scoped exception to the older page-family capability table; no page grants are added. Reuse the existing item path owner for subpage breadcrumbs. Clarifications are append-only; accepted ADR bodies remain unchanged.

### Requirement gh-1678: [block-editor 11/13] Read a page as Markdown

#### Context

Model tier rationale: One new read-only HTTP route with a version header over existing doc-loading and serialization seams, but the ETag must stay stable across compaction, which needs a careful, tested derivation.

Pages (docs of kind `page`) have no HTTP surface today: `backend/services/semprec-api/src/routeMatrix.ts` lists no doc route, and the only way to read a page is the realtime doc sync. A doc also has no version a client can compare: `DocDbRow` in `backend/packages/data/src/docs/docsStore.ts` is `{id, item_id, kind, created_at}`, and `backend/packages/data/src/docs/docPersistence.ts` compaction deletes the `doc_updates` ids, so row ids cannot serve as a version.

Clients (web, desktop, the assistant) need to read a page as Markdown and later write it back safely. This issue delivers the read half: the page body as canonical Markdown plus a version token. #1608 provides the serializer that turns the doc's blocks into canonical Markdown; #1394 records the page operation family (names, naming of the read operation, and the rule that a read never creates a doc). The write halves #1765 (replace, guarded by this token with If-Match) and #1679 build on it; #1844 and #1751 consume the read operation for agents.

The title is not part of the Markdown. A root page stores its title separately and a subpage's title is the link text in its parent, so the body never starts with the title.

Decision: the version is `base64url(sha256(Y.encodeSnapshot(Y.snapshot(doc))))`, sent as a strong quoted ETag. A Yjs snapshot is the state vector plus the delete set, so a write that only deletes text changes it (the state vector alone does not change on pure deletion), while compaction rewrites storage but not the logical doc and so leaves it unchanged.

Shared-file ordering: this issue also waits for #1676 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Decision (batch 38 R1 reconciliation): R1 reconciliation: repeated page blocks referencing one page id retain each block's own caption. page.get with format markdown is the catalog read; page.md is its HTTP binding. Snapshot-hash equality is not equality of visible content across distinct CRDT histories.

### Requirement gh-2013: [subpages 03/12] Convert selected blocks into subpages

#### Context

Model tier rationale: One transaction creates several items and their documents and rewrites several blocks of another document in place, so a partial failure would leave pages without blocks or blocks pointing at missing pages; it extends a catalog operation that every transport exposes.

In the editor the user can restyle selected blocks into subpages: each selected block becomes its own empty subpage and its text becomes the subpage's name. #1676 adds the hidden `pages` database, plain-text `text` on `page` blocks in the block model, `normalizePageTitle`, and the catalog operation `page.createSubpage` (`backend/packages/data/src/docs/pageOperations.ts`) that creates one new subpage, with output `{ pages: [{ pageItemId, docId, blockId }] }`. The shared block model (#1610) refuses every conversion to or from `page` with a typed error, so this needs a dedicated operation step. This issue was split out of #1676 so that each issue carries one mechanism.

Decisions:
- `fromBlockIds` converts blocks in place: the block id stays, its type becomes `page`, its plain text becomes the title and the new page is empty. Blocks that are already `page` blocks are rejected.
- With `fromBlockIds`, `afterBlockId` and `title` are ignored; the pages are returned in document order.

Block model: in the module directory fixed by the ADR of #1366, add `convertBlocksToPages(doc, ids, pageIdFor)` as a single Yjs transaction that changes the type of non-page blocks to `page`, sets `pageId` and keeps the plain text as the title. Keep every operation of #1610 refusing page conversions as it does today.
2. Extend the strict input schema of `page.createSubpage` with the optional `fromBlockIds: string[]` (at least one id, no duplicates); the output shape is unchanged.
