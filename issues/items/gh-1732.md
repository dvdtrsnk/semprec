**Blocked by:** #1568, #1727
**Model tier:** high

## Context

Model tier rationale: It adds crash and shutdown cleanup across the database, the queue's lock state and an in-flight session, and incorrect ownership of that cleanup either loses a reply or answers one twice.

When the agents process restarts or stops while a Semp turn is running, the assistant message stays `running` forever, its thread can look busy, and the lane's queue lock held by the dead process blocks the tenant's next Semp turn until graphile-worker considers the lock stale, which takes 4 hours. This issue makes a restart or a shutdown end cleanly: the interrupted message becomes an error and the next message of the thread is processed.

Today `repairInterruptedRuns` in `backend/packages/agent-runtime/src/startupRepair.ts` closes only `agent_runs` rows left `running` (writing a synthetic `tool_result` for an unpaired tool call and an `agent_run_error` notification) and runs per active tenant before the queue starts (`serve.ts`). Nothing looks at Semp messages. `backend/services/semprec-agents/src/shutdown.ts` closes the tenant deactivation listener, calls `queueRuntime.stop()` (graphile-worker `Runner.stop()`) and ends the pool. The rules for long-running tasks are in `docs/adr/2026-09-30-graceful-shutdown-for-long-running-graphile-worker-tasks.md`.

It builds on the queued turn task (#1727: statuses, lane `semp-chat` per #1370, `maxAttempts` 1) and on closing idle thread sessions on shutdown (#1568, which owns the session-close part of shutdown and the pairing of dangling tool calls in stored transcripts). The error code `interrupted` it writes is classified further by #1907. Retrying an interrupted reply is #1926.

Decision: a turn that cannot finish within the stop window is cancelled and written as an error, not continued after restart, because continuing would repeat tool writes.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In `startupRepair.ts` extend the per-tenant repair so that, in the same transaction that closes the orphaned runs, every Semp assistant message with status `running` is set to `error` with `error_code` `interrupted`, and its thread's last-activity time and a `sempThread` invalidation are updated using the helpers delivered by #1395 and the thread tables. A `running` message whose run is not orphaned (it was not a `running` `agent_runs` row) is still repaired, because the in-memory session is always empty after a start.
2. Release the lane lock left by a dead process: at startup, after the repair and before the queue runner starts, unlock the `semp-chat:<tenantId>` queue rows of the lane whose lock is held by a worker that no longer exists (`graphile_worker.job_queues.locked_by` not matching any live worker lock), using graphile-worker's own tables under the system scope. It must never touch a lock held by a live worker.
3. In `shutdown.ts`, extend the stop sequence for running Semp turns: abort every in-flight turn that does not finish within the stop window (`TimeoutStopSec` minus a margin kept as a named constant), by aborting the in-flight controllers through `InFlightAgentRuns`, and write each aborted message as `error` with `error_code` `interrupted` before the pool is ended. A turn that finishes inside the window completes normally. Closing idle sessions is #1568 and must keep its position in the sequence.
4. Tests: a `running` assistant message left by a simulated crash is `error` / `interrupted` after startup repair and the next message of the same thread is processed; a stale lane lock is released and a live one is not; a shutdown with a slow turn aborts it and stores the error before the pool closes.

## Scope

### In scope

- Repair of `running` Semp messages at startup, the lane-lock release for dead workers, and abort-and-record on shutdown.

### Out of scope

- Closing idle sessions on shutdown and pairing dangling tool calls (#1568).
- Classifying failures by the shared run error codes beyond writing `interrupted` (#1907).
- Raising a problem for the failed reply (#1931) and retrying or regenerating (#1926, #1930).
- Any change to non-Semp runs' repair behavior.

## Acceptance criteria

- After a restart in the middle of a turn, the assistant message has status `error` and `error_code` `interrupted`, and the next message sent to the thread gets a normal reply.
- After a restart, a stale `semp-chat:<tenantId>` lock does not delay the next turn by hours; a lock of a live worker is left alone.
- When shutdown begins during a turn that does not finish in time, the turn is cancelled and its message is `error` before the process exits; a turn that finishes in time is `done`.
- Repair is idempotent: running it twice changes nothing the second time.
