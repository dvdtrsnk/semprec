## Behavior specification

Inbox cards: company, person, task, event, project, recording, speaker and MCP server.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: inbox-cards-1

#### (a) Decisions adopted from open questions
- friend vs closeFriend, family vs parent: new keys or mapping? -> No new keys; the list is the six existing keys plus colleague, craftsman, doctor, and clients map friend/family wording onto closeFriend/parent (#1549). Reason: the design note leans to the additive list and the collection and card must share one list. -> Decided by the product owner: no new keys; friend and family wording maps onto the existing keys.
- Job title ("Designerka") on a person: new property? -> Not added (#1549, #1671). -> Decided by the product owner: no; the default People schema is not extended and system collections get no custom properties in v1 (the module manifest owns the schema); a position can be written in the person's note.
- ARES lookup failures: -> best effort; timeout, 404, malformed body leave the computed values unchanged and never fail the tick (#1989). Reason: a register outage must not block capture. -> Decided by the product owner: best effort.
- ARES scope: only the registered name is taken over; address and tax id are not stored (#1989). IČO is checked for format only, not check digit, so numbers ARES knows are never skipped. -> Decided by the product owner: only the name is taken over.
- ARES base URL: a fixed https constant in code, not an env variable, to avoid a new deploy secret-group key (#1989).
- Duplicates: exact match only (normalized IČO, normalized e-mail via person_email_index); the create becomes a link step and the existing record is not changed (#1992). Phone matching waits for People.phones. -> Decided by the product owner: exact IČO or e-mail match only; the create becomes a link.
- Past Event durations: only for an Events target, only same-day events with timeFrom and timeTo, up to 5 per known person, minutes only (#1993). -> Decided by the product owner: as drafted.
- Color validation: exactly #RRGGBB (any case), null clears, stored as written, only keys present in the write; old values are not migrated (#1433).
- Explicit "no event": stored only as recording_requests.event_decision = none; match step then creates no card and no edge (#1986).
- Rejected speaker cards after rerun: the existing idempotency key is the memory; pinned by tests, no new storage (#1671). -> Decided by the product owner: a rejection is remembered and the card is not proposed again.
- Speaker confirm adds the person to Events.people only when the transcript has a linked Event and the person is not already a participant, in the same transaction (#1671). -> Decided by the product owner: yes, in the same transaction.

#### (b) Open questions that remain for the product owner
- Default content of a new project's AGENT.md (empty or template); not covered by any issue in this job.
- If a transcription rerun can ever re-diarize and relabel speakers (for example after the speaker count is passed through), rejected speaker cards need a stronger memory; #1671 only pins today's behavior.
- How the Inbox card presents a duplicate (link vs create anyway) is a design request; #1992 only emits the link.
- Whether mismatched sample data (existing Karel Zlaty, Lucie Benesova, Brainz) should be reconciled in the design.

#### (c) User-visible behavior of this chunk
Capturing a company with a Czech registration number now fills in its official name from the public register, and a company or person that already exists (same registration number, same e-mail) is proposed as a link instead of a duplicate. People get three more relationship choices (colleague, craftsman, doctor) everywhere the list is used. A proposed event gets a sensible length based on how long earlier events with the same people lasted. Colors written to any record must be valid hex values. A recording confirmed as "no event" stays without an event and no longer produces a "recording without an event" card, even after a rerun. Confirming a speaker also adds that person to the linked event's participants.


### Decisions: inbox-cards-2

#### (a) Decisions adopted from open questions
- Sync route runs inline or as a job? -> Inline for the human route (#1972), queued only after a card confirm (#1976). Reason: the user waits for the result in one case and not in the other.
- Failed sync after confirm: retry? -> No queue retries (maxAttempts 1); the failure is recorded as syncStatus error with a safe message and the user retries through the route (#1976). -> Decided by the product owner: no automatic retry; the error is recorded and the user retries.
- Connection failure on the route -> 502 with a typed reason; tool-list validation failure keeps 400 validation_failed (#1972).
- May a human confirm set project grants? (#1382) -> Decided by the product owner: no. Confirming the card only pre-fills the permissions (read-class tools of the server for the chosen projects) and the user grants them in the project's permissions on the AGENT page; even read tools send data to a third party, so a grant must be explicit. #1382 records this in an ADR; no confirm body field, sync job payload or other writer of grants is added.
- Tools added by later syncs are not granted automatically. -> Decided by the product owner: new tools get no grant.
- stdio from the card: out of this chunk (already refused by the stdio policy); http vs sse remains the existing connectionConfig choice.

#### (b) Open questions that remain for the product owner
- http versus sse: user choice or connection probe? Not decided; no issue in this job depends on it.
- #1972 is listed as blocked by #1963 (batch ordering); there is no code dependency, only shared route-matrix and isolation-test entries. Consider dropping the edge.

#### (c) User-visible behavior of this chunk
Confirming an "add this MCP server" card in the Inbox stores the server and its key, then loads the server's tools in the background; the server shows whether the sync worked. A user can also press a sync button for any server. Projects picked on the card only pre-fill the project permissions with the server's read tools; the user grants every tool explicitly on the project's AGENT page, and tools added by later syncs stay ungranted.
