### Requirement gh-1916: [inbox-editing 12/23] Invalidate open proposals when a referenced item is archived or deleted

#### Context

Model tier rationale: Registers write hooks that lock and rewrite other rows inside the triggering transaction, with lock ordering against concurrent confirm and a new index-backed lookup across every database, so concurrency and cross-database isolation are the main risks.

An open proposal that points at an existing item (the project a task would be created in, a person to link, a company, the page an entry would be appended to) becomes unusable when that item is archived or deleted in the meantime. Nobody notices today: the card stays `proposed` and `confirm` re-checks only the envelope shape and target database. The card should flip to `invalid` at the moment the referenced item changes, in the same transaction, and flip back when the item is restored or un-archived. #1482 defines `invalidReason` and the fixable/final distinction; #1426 defines how a referenced item's state (archived, done, deleted) is evaluated, which this issue reuses; #1601 adds the item delete and restore hooks to the choke point (`registerItemDeleteHook`, `registerItemRestoreHook`, next to the existing `registerItemUpdateHook` in `backend/packages/data/src/chokePoint/hooks.ts`).

Decision: Processing proposals get a system property `referencedItemIds` (an array of item ids; created with the card-state properties, see #1451) holding every item the effective envelope refers to: relation targets of `entityKind: relation` and of relation parts of database envelopes, the page of a `pageContent` envelope, and the targets of any further steps. Every writer of `proposal` writes it from one helper, `referencedItemIdsOf(envelope)`.

Decision: the hooks apply to items of any database (the referenced target can be a project, area, person, company, journal day or a subpage); the lookup uses the existing `items_props_gin` index (`properties @> {"referencedItemIds": [<id>]}`) restricted to the Processing proposals database and status `proposed`. Only `archived` projects (Projects `status = archived`) and deleted items invalidate; a project that is merely `done` stays selectable and keeps open proposals valid (decided by the product owner: a done project is a valid target and nothing is invalidated silently).

Decision: the hook locks matched proposals with `FOR UPDATE SKIP LOCKED`, so it never waits for a confirm that holds the proposal lock first (the opposite lock order would deadlock). A proposal skipped because it is being confirmed right now is not invalidated; that confirm validates its targets through the evaluation from #1426.

Shared-file ordering: this issue also waits for #1905 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1917: [mail-threads 27/28] Archive or trash a mail thread

#### Context

Model tier rationale: Moves a conversation's messages across accounts by rewriting system-owned folder edges and recording durable provider moves in one transaction, with provider-specific failure cases.

Archiving and deleting a conversation do not work today. The web triage (`web/src/views/mailbox/triage.ts`) changes the `Emails.folder` edges through the generic relation API, but that relation is system-owned by the Emails module (`chokePoint/relationEdgeContext.ts`), so the write fails with 403 `owner_violation`. Moves are not written to providers (#1746 adds the durable queue and the provider writes). Gmail archived mail needs the synthetic Archive folder (#1496). Flag state for moved messages is handled by earlier issues (#1893).

Decisions: both routes act on the counted messages of the thread in every account; `archive` moves only messages currently in an inbox folder, `trash` moves all of them; the target folder is the one with the matching `specialPurpose` in each message's own mailbox (for a Gmail API account the synthetic Archive); the local edge move uses `EMAILS_RELATION_CONTEXT` and the desired move is recorded in the same transaction; nothing is deleted permanently, and an archived or trashed thread can be restored to the inbox (decided by the product owner; the restore route is #2033, building on these routes). If a mailbox has no Archive folder (IMAP without an `\Archive` folder) the call fails with 409 `mail_archive_folder_missing` and nothing is changed; a trash of a thread whose messages are all already in Trash or Junk fails with 409 `mail_thread_already_trashed`; a mailbox without a Trash folder fails with 409 `mail_trash_folder_missing`. Each successful call sends one `mailThread` invalidation after commit.

### Requirement gh-2033: [mail-threads 28/28] Restore a mail thread from Archive or Trash to the inbox

#### Context

Model tier rationale: One more thread action route that reuses the thread helpers, the local folder-edge move and the desired-move recording of #1917 and the durable move queue of #1746; the new parts are the target rule per message and three 409 cases, all with existing fixtures.

Archiving and trashing a conversation (#1917) move its messages into the Archive or Trash folder of each mailbox, locally and, through the durable move queue of #1746, at the provider. Nothing is ever deleted permanently. The product owner decided that everything archived or trashed can be restored: a thread in Archive or Trash can be moved back to the inbox. Today there is no way to do that; the only writes to `Emails.folder` are system-owned (`EMAILS_RELATION_CONTEXT`), so a client cannot move the edges itself.

#1746 accepts the desired purposes `inbox` and `sent` and performs the provider writes for them (IMAP move to the Inbox or Sent folder, Gmail untrash and the `INBOX` label, Graph move to `inbox` or `sentitems`). This issue adds the route that records those moves and moves the folder edges locally.

### Requirement gh-1923: [mail-items 14/15] Keep thread-task people in sync with the conversation

#### Context

Model tier rationale: A write hook that enqueues a job in the writer's transaction plus a job that edits values other users may have changed by hand creates concurrency and ownership questions on a data path used by mail ingest.

The people of a task made from a thread follow the conversation: when a new person joins the thread (copied in, or the sender of a later message), the task gets them too, unless the people of that task were changed by hand. Senders and recipients are linked to people by the heartbeat action `mail.linkPeopleByEmail` after ingest (asynchronously) and for sent mail by #1480, so edges `Emails.senderPeople` and `Emails.recipientsPeople` appear at different times. The edge-changed hook after a write is #1530. Tasks created from a thread already carry their people as inherited values (#1900); a manual change ends following (#1516).

Decisions: only additions are propagated; removing an edge never removes a person from a task. A person who belongs to the tenant's own mailbox addresses is never added.

### Requirement gh-2035: [mail-items 15/15] Let Semp propose a task from a mail thread in the Inbox

#### Context

Model tier rationale: One module agent tool following the descriptor and handler pattern of the mail tools of #1927 that writes a single proposal card and its source edge in one transaction, with an idempotence rule; no new authorization contract.

### Requirement gh-1926: [semp-replies 06/08] Retry a failed Semp reply

#### Context

Model tier rationale: One new endpoint that creates a queued assistant message through an existing enqueue path, with a uniqueness constraint for the race and fixtures from the thread and queue issues, but it depends on the history reconstruction accepting an interrupted tool call, so the tests must pin that seam.

When Semp's reply fails or comes back incomplete, the chat offers "Try again" (and the same action is offered from the status view). Today there is no retry: a broken turn simply drops the session (`backend/packages/agent-runtime/src/sempConversation.ts`), and the user would have to retype the question. The REST error contract (`backend/services/semprec-api/src/adapter/errorContract.ts`, closed `ITEM_ERROR_CODES` with `ITEM_ERROR_STATUS_BY_CODE`) has no code for a refused retry.

After this issue the user can retry the latest failed reply of a thread: a new assistant message is queued as another attempt of the same reply, runs through the queued turn handler of #1727, and takes the place of the failed one in the chat. The failed attempt stays stored with its own steps, so the history still shows what was tried.

It builds on: failure classification and the stored error (#1907, which also decides what counts as an incomplete reply); the thread turn queue (#1727); closing idle sessions and pairing dangling tool calls (#1568); and the interrupted tool result shape (#1374). The same retry also serves the status view action (#1931, #1931), and #1932 lists replies as separate rows using `attempt`.

A reply that failed has already told the agent what it did: the tool results of the failed attempt stay in the history the agent sees for the retry, so it knows which changes were made. A tool call left without a result by the failed attempt is paired with a synthetic tool result in the regular tool result shape (#1568, #1374); the shape written by the startup repair in `backend/packages/agent-runtime/src/startupRepair.ts` would make waking the thread for a retry throw, and must not be what is used.

Decision: the retry sends the original user message again as a new user turn, resolved through `reply_to_message_id`. The duplicate user turn in the model history is accepted: it is the simplest solution and breaks nothing.

Decision: a retry is allowed on the latest message of the thread when it is an assistant message with status `error`, or with status `done` and an incomplete reply (the function of #1890 reports a reason). Anything else, including an older message or a successful reply, is refused with `retry_not_latest`.

Shared-file ordering: this issue also waits for #1922 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

It checks, in one transaction under the thread's row lock, that `messageId` is the last message of the thread, is an assistant message, and is retryable as decided above. Otherwise it answers 409 `retry_not_latest`. It then inserts a new assistant message with the initial status used by the send path, the same `reply_to_message_id`, `attempt` = previous attempt + 1, and calls `enqueueSempMessage` for it in the same transaction. It answers 202 `{ messageId }`.
