**Blocked by:** #974

## Context

`person_email_index` maps a normalized email address to the People item that owns it. Its primary key is `email` (`backend/packages/data/src/db/migrations/0006_mail_sync.sql:122-131`, constraint `person_email_index_pkey`). It is written and read only through `backend/packages/data/src/mail/personEmailIndexStore.ts`:
- `lookupPersonIdByEmail` reads `WHERE email = $1` (`:7-12`).
- `reindexPersonEmails` (`:26-53`):
  - reads the addresses already claimed (`:33-37`) and treats those owned by another Person as `conflicts`;
  - releases this Person's dropped addresses (`:40-43`);
  - claims the rest with `INSERT ... ON CONFLICT (email) DO NOTHING` (`:46-49`).

The callers are the People `onItemEvent` reindex action and the Emails person-linking action (`backend/packages/data/src/mail/personLinkingActions.ts:28-43,62-119`).

Because the key is global, one tenant's People entry for `alice@example.com` owns the address for everyone: another tenant's contact with the same address can never be indexed or linked. Once #1065 drops the legacy key, `ON CONFLICT (email)` matches no constraint, and every claim fails.

Tenancy state this issue builds on:
- `person_email_index` is a tenant table: `tenant_id DEFAULT app_tenant_default()`, plus the RESTRICTIVE `tenant_isolation` policy `tenant_id = (SELECT app_tenant_default())`.
- `app_tenant_default()` is `COALESCE(app_current_tenant(), app_sole_tenant())` over the GUC `app.tenant_id`.
- Under a runtime role, every read and the `DELETE` in this store are therefore already per tenant, and so are both actions' lookups.
- #974 added the tenant-leading unique index `person_email_index_tenant_email_uq` on `person_email_index (tenant_id, email)` beside `person_email_index_pkey`, which stays until #1065.

Arbiter choice:
- The claim moves to `ON CONFLICT DO NOTHING` with no conflict target, so every unique index is an arbiter: both today, the tenant-leading one after #1065.
- An explicit `(tenant_id, email)` target would leave the legacy key as a non-arbiter. Two concurrent reindexes in one tenant claiming the same address would then fail with a raw unique violation instead of "first writer keeps it".

## Task

Load `state-writes` (the claim is a write whose conflict outcome the caller relies on).

1. **Claim.** `reindexPersonEmails`'s insert (`:46-49`) uses `ON CONFLICT DO NOTHING` with no conflict target. Do not add hand-written `tenant_id` predicates; RLS confines the reads and the `DELETE`.
2. **Docstrings.** In `reindexPersonEmails` and `lookupPersonIdByEmail`, the guarantee "one address never belongs to two people" holds within a tenant. It is enforced by the tenant-leading unique index, not the global primary key.
3. **Tests.** New `backend/packages/data/src/__tests__/personEmailIndexPerTenant.test.ts`. Cases needing a second tenant, or the post-#1065 schema, run in one transaction on `getTestPool()` (the owner), rolled back at the end:
   - `DROP INDEX IF EXISTS tenants_single_tenant_guard`;
   - `ALTER TABLE person_email_index DROP CONSTRAINT person_email_index_pkey`;
   - insert a second `tenants` row;
   - `SET LOCAL ROLE semprec_data`;
   - switch tenants with `SELECT set_config('app.tenant_id', $1, true)`.

   Person ids may be random UUIDs: the table has no foreign key to `items`. Integration files run one at a time (`fileParallelism: false`, `backend/vitest.integration.config.ts:20`).

## Acceptance criteria

All integration tests (`*.test.ts`).
- With one tenant, every existing person-index and person-linking case in `backend/packages/data/src/__tests__/mailSync.test.ts` passes unchanged.
- With `person_email_index_pkey` dropped (rolled-back transaction), in one tenant:
  - claiming `a@example.com` for person P1 and then for P2 reports `conflicts: ["a@example.com"]` for P2;
  - `lookupPersonIdByEmail` still returns P1.

  This proves the code no longer needs the legacy key.
- With the legacy key dropped and two tenants under `semprec_data`:
  - P1 in tenant A and P2 in tenant B both claim `a@example.com` with no conflict;
  - `lookupPersonIdByEmail("A@Example.com ")` returns P1 in A's scope and P2 in B's scope.
- With the legacy key dropped, B's P2 releasing `a@example.com` (reindexed without it) leaves A's row in place: A's lookup still returns P1.
- On today's schema (legacy key present, one tenant, two connections), two concurrent reindexes claiming the same address for different people end with exactly one row for that address. Neither rejects.
