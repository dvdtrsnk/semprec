## Behavior specification

Agent runs: steps, detail, failure reasons, retries and project runs.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: agent-runs-1

#### (a) Decisions adopted

- Where do target ids on tool events come from? -> From the tool call arguments only (`databaseId`, `itemId`), never parsed from result text -> arguments are validated input; result text is model-facing prose. Item-only calls resolve their database at read time.
- How does `item.patch` get `before` values? -> From the operation output added in the write transaction by the previous-values issue; no best-effort read outside the transaction -> a separate read can report a value that was never the real previous one.
- What is stored for `longText` changes? -> The key only, no content; other values are shortened -> keeps payloads bounded and avoids storing large user text.
- How is an interrupted call recorded? -> As an ordinary error result (`isError: true`, `result.details.error: true`, content text), copying identity fields from the call but not its arguments -> one failure rule for all readers; the conversation rebuild already requires this shape. Old rows are not rewritten; readers keep tolerating the legacy top-level `error: true`.
- Who may read a run? -> A different `actorUserId` answers 404 on the whole detail route -> defense in depth, same as the realtime watch.
- Duration of a run? -> Only for invocation runs not triggered by MCP; null otherwise -> session and MCP runs stay open for hours, so end minus start is not work time.
- Truncated history flag? -> `truncatedHistory` is true when the run's first stored event is not its opening status event -> retention deletes only the early part of a finished session run.
- Thinking blocks? -> Decided by the product owner: never shown -> the user sees steps, tools and the result, which is enough for an audit.
- Redaction? -> Decided by the product owner (approvals batch question on the "details in the agent run" link): a step exposes only its structure: tool, state, time, link to the approval request and a localized result summary; tool arguments, tool results, the model's text and raw errors are never returned, as for `conflictReason` (#1847). Structured field changes stay, and a result redacted as sensitive yields none.
- Token usage step? -> Decided by the product owner: token usage appears only in the per-reply summary (#1860); a run's steps show only real actions.
- Realtime frames? -> Stay raw signals; clients re-read `GET ...steps?after=<nextCursor>` -> projection stays server-side.
- Display status of an approved-and-queued request? -> `done`, not waiting -> the user has already decided.

#### (b) Open questions remaining for the product owner

- Server-side step titles: confirm whether the seed i18n catalogs (`seed/i18n/cs.json`, `en.json`) are the right home for server-produced strings, or a dedicated catalog module should be used. The step projection issue allows either.

#### (c) User-visible behavior of this chunk

A user can open any Semp run, including a finished one and a single chat reply inside a longer conversation, and see a titled header with the project, what started it (a chat message, a scheduled tick or an MCP client), how long the work took and how many approvals it needed, with a status that shows "waiting for approval" instead of a misleading "done". The run's progress is a paged list of steps (start, plan, tool calls, approvals, answer, end) with localized titles such as "changing a task", the affected item, the before and after value of a changed property, the server name for external tools, and a short localized result summary, never the raw arguments or results. Approval steps show live whether the request is pending, executing, executed, failed, in conflict or rejected, and a call interrupted by a restart reads as an ordinary failed step. For a chat reply, the same detail, steps, approvals and cost can be limited to just that reply.


### Decisions: agent-runs-2

#### (a) Decisions adopted from open questions

- Derive incomplete replies from steps, or let Semp announce incompleteness in structured output? -> Derive from stored steps at read time, no new column, no model-announced status -> the model's own wording is not trusted for status and the steps already exist.
- How to phrase "connection to the calendar timed out" given Czech declension? -> Decided by the product owner: summaries use the server name in the nominative ("Calendar unavailable", "GitHub unavailable", "tool GitHub returned an error"); the final answer text is the model's own, never composed by code -> a name cannot be inserted into a declined phrase.
- Design says 30 s, backend uses 60 s: which wins? -> Decided by the product owner: the seconds in the text come from the stored `timeoutMs` (60 s for a call, the connection timeout for a handshake); the design is corrected -> text must match the real bound.
- Is a failed tool call followed by a successful call of the same tool still incomplete? -> Decided by the product owner: no, the later success cancels it; the state is derived from the stored steps, not from the model's claim.
- Manual retry only, or a retry chain for ticks? -> Decided by the product owner: both. Scheduled tick runs have the automatic chain of attempts, and after the chain failed they can be retried manually from the run detail (#1908). Runs without a scheduled occurrence are not retried.
- Which runs can be retried? -> Decided by the product owner: only heartbeat runs linked to a scheduled occurrence (runs from manual fires and item events have no occurrence, so a pending automatic attempt cannot be ruled out); the others answer `not_retryable`.
- Should the user retry get automatic attempts too? -> Decided by the product owner: no, the retry job is enqueued with a single attempt -> a failed retry is final, notifies, and can be retried again.
- Connection timeout vs refused connection? -> New connection error reason `connect_timeout`; refused stays `handshake_failed` (classified as `connection`).
- Is `error_code` required by the database? -> No, nullable column plus a required compiler-enforced parameter and a test over every closing site (a rolled-back release still closes runs without it); null reads as `internal`.
- Where does a localized summary come from? -> Read-time catalog lookup by the reading user's locale; stored `result` of a new failure is the canonical code.
- How is the budget refusal detected? -> A response header `x-semprec-error-code: budget_exceeded` on the gateway's unchanged 403, captured per call by the agents service.

#### (b) Open questions for the product owner

- The exact module and file of the shared display-status derivation, the Semp message read model and `enqueueManualHeartbeatFire` are created by blocking issues; their paths are given by role in Touches and need confirming when those issues merge.
- Whether the messages endpoint that returns `outcome`/`incompleteReason` is owned by an issue outside this chunk (its route file does not exist on the current branch).
- Whether the Czech/English wording of the five error summaries and three incomplete-reply summaries needs product review before merge.

#### (c) User-visible behavior delivered

When a Semp tool call fails or times out, the backend now knows why: timeout, unavailable server, connection, authentication or tool error, with the server and the real time limit. A reply that ended after such a failure without a later success is derived as incomplete, shows as an error in lists, and carries a short reason such as "GitHub unavailable". Every failed agent run now has a stable error code (limit used up, model error, cancelled, interrupted, internal) and a short Czech or English reason chosen by the user's language, with no raw exception text stored or logged; a spent AI budget is recognized as such. A failed scheduled tick can be tried again from the API: the retry starts one new linked run (attempt n + 1) of the same task, two simultaneous requests start only one, and the automatic queue attempts of one occurrence are chained so a tick that failed twice and then succeeded reads as one story.


### Decisions: agent-runs-3

#### Adopted decisions
- Which module owns the list route -> the module owning `agent_runs` (schemaCore manifest, `GET /api/agent-runs`, single-consumer-read) -> custom-routes ADR and single-writer ownership ADR; `app.ts` unchanged.
- Whose runs the list shows -> `actor_user_id` = session user, never `triggered_by = 'supervisor'` -> design note "jen behy uzivatele session"; heartbeat runs carry the tenant user as actor, so they appear for that user.
- Unknown/foreign `projectItemId` -> empty list, not 404 -> foreign ids indistinguishable from empty.
- Collapsed retries -> row shows the status and duration of the latest attempt; decided by the product owner: the row's cost is the sum over all attempts and the cost of each attempt is shown when the row is expanded (#1914) -> the user sees the real price of the run.
- Chat answer rows -> one per assistant message, retries collapsed to latest attempt; session runs without messages stay one row -> interim behavior from the design note.
- Tick-thread turns -> triggerLabel "Tik" by `semp_threads.kind`; system-triggered turns -> title localized by `system_key`.
- `agentRun` ref -> `messageId` optional; mismatch errors identical to unknown target.
- Localization of trigger labels and system-key titles -> Decided by the product owner: the mechanism of #1824 (the user's language, default `cs`); no special case for triggers.
- Index -> `(tenant_id, project_item_id, started_at DESC, id DESC)` (design note plus id tie-break for the specified ordering).

#### Open questions remaining for the product owner
- Exact module/file paths for the ref schema and validation (#1369/#2) and the shared status/duration functions do not exist yet; the bodies refer to them by role.

#### User-visible behavior (epic paragraph)
The project agent page shows the four to twenty most recent runs of a project, newest first: each with a title, an icon-worthy trigger label (Chat, Tik, MCP), start time, duration, cost and a status that distinguishes waiting for approval and failed runs with a short localized reason. A tick that was retried automatically appears once, with its attempt number and the total cost of all attempts; expanded, it shows the cost of each attempt. In a chat, every answer of the agent is its own entry with its own question, duration and cost, rather than the whole conversation being one entry. Any row can be opened, and a row can be dragged into the chat as an attachment; for a chat answer the attachment refers to exactly that answer.
