## Context

Model tier rationale: Every query, lock, refusal and invocation point of the stamping step is specified exactly.

Every job carries the envelope defined in `backend/packages/queue/src/index.ts` (`queueJobEnvelopeSchema`, `:19-22`; built by `enqueueJob`, `:209-236`; unwrapped by `registerTask`, `:275-310`). #982 made it `{ traceId, tenantId?: string | null, payload }` — `tenantId` stamped by `enqueueJob` from the current scope (the tenant id in a tenant scope, `null` in a system scope or with no scope in warn mode) — and added `TASK_TENANCY: Record<CoreTaskName | AgentTaskName, "tenant" | "system">` (a task name outside it, i.e. a module task, is `tenant`). For a tenant task whose envelope has no string `tenantId` (a legacy envelope from before that change, a `null`, or a raw payload), `registerTask` still falls back: it reads `SELECT app_sole_tenant()`, logs `tenant_task_without_tenant` at warn level and runs the handler in that tenant.

That fallback guesses the tenant from the database rather than from the job. It is only correct while exactly one tenant exists, and once a second tenant can exist (#1087) `app_sole_tenant()` returns NULL and such a job fails on every retry. This issue removes it: legacy jobs still queued are converted at deploy time, then a tenant task without a tenant is refused. It ships in a release after the checkpoint release (#1058), which confirmed in production that no `tenant_task_without_tenant` fallback ran for seven days and no pending legacy envelope remained; the deploy-time step is the safety net for anything left.

The precedent for rewriting queued jobs at deploy time is `backend/packages/data/src/scheduler/heartbeatFireQueueSplitMigration.ts:36-109`: only graphile-worker's public functions for writes (reads of `payload` go through `graphile_worker._private_jobs`, as `backend/packages/data/src/observability/queueFailedJobsPrune.ts:50-55` does, because the `graphile_worker.jobs` view of graphile-worker 0.17.3 does not project `payload`), re-enqueue through `enqueueJob` inside the original trace, key/queue/max attempts preserved; it runs from `backend/packages/data/src/db/runMigrationsCli.ts:36` and `backend/packages/data/src/testSupport/globalSetup.ts:120`, after `ensureQueueSchema`/`grantQueueSchemaPrivileges` (`docs/adr/2026-09-10-app-code-post-migration-steps.md`). The scope API (`runAsSystem`, `runInTenant`, `TenantScopeMissingError`) is in `@semprec/shared` (#978).

## Task

Load `state-writes` (queue rows rewritten in one transaction, affected-row checks) and `error-handling` (a refusal that must stay visible, never swallowed).

1. Create `backend/packages/data/src/tenancy/legacyJobEnvelopeStampMigration.ts` exporting `runLegacyJobEnvelopeStampMigration(pool: Pool): Promise<{ stamped: number }>`, all inside `runAsSystem("legacy-job-envelope-stamp", …)` and one `withTransaction`:
   1. Return `{ stamped: 0 }` if `to_regprocedure('graphile_worker.complete_jobs(bigint[])')` is null.
   2. `SELECT pg_advisory_xact_lock(hashtext('legacyJobEnvelopeStamp'))`.
   3. Select from `graphile_worker._private_jobs j JOIN graphile_worker._private_tasks t ON t.id = j.task_id LEFT JOIN graphile_worker._private_job_queues q ON q.id = j.job_queue_id` (using `t.identifier` as the task name and `q.queue_name` as the queue name) the jobs with `payload::jsonb ? 'traceId'`, `jsonb_typeof(payload::jsonb -> 'tenantId') IS DISTINCT FROM 'string'` and `attempts < max_attempts`, keeping only tenant tasks per `TASK_TENANCY` (unknown names count as tenant). None → return `{ stamped: 0 }`, whatever the tenant count.
   4. Otherwise `SELECT id FROM tenants`: anything but exactly one row → throw an `Error` naming the tenant count and the number of legacy jobs. Any selected job with `locked_at IS NOT NULL` → throw naming those job ids and task names (the operator re-runs the deploy once they finish).
   5. For each job: parse the envelope (its `payload` must be an object), remove the job with `SELECT * FROM graphile_worker.complete_jobs(ARRAY[$1::bigint])` and require exactly one returned row, then `runInTenant(soleTenantId, () => withTraceContext({ traceId }, () => enqueueJob(client, task_identifier, payload, { jobKey, queueName, runAt: run_at, maxAttempts: max_attempts })))`. The docstring notes the new job's attempt count starts at zero.
2. Call it in `runMigrationsCli.ts` directly after `runHeartbeatFireQueueSplitMigration(pool)` (line 36) and in `globalSetup.ts` directly after line 120.
3. In `registerTask`, replace the sole-tenant fallback for a tenant task without a string `tenantId`: do not query `app_sole_tenant()` and do not call the handler; log `tenant_task_without_tenant` at **error** level with `jobName`, `jobId` and `traceId` (never the payload) and throw `TenantScopeMissingError`. graphile-worker records the failure and retries until the job is permanently failed, where `observabilityCheckSystem`'s failed-jobs check reports it. System tasks, and tenant tasks with a string `tenantId`, keep #982's behaviour.
4. Update #982's tests that exercised the fallback so they assert the refusal, and drop the sole-tenant answers from fake helpers that no longer need them.

## Scope

### In scope

- The deploy-time stamping step, its two invocation points, and refusing tenant tasks without a tenant.

### Out of scope

- The strict `app_tenant_default()` and the strict default mode (#1067).
- Proving per-task isolation (#1056).
- Removing permanently failed legacy jobs (a maintainer decision recorded at #1058).

## Acceptance criteria

- Integration: with one tenant and a pending tenant-task job inserted through `graphile_worker.add_job` with a hand-built `{ traceId, payload }` envelope, the step returns `{ stamped: 1 }`, and the queue then holds exactly one job for that task with the same key, queue name, `run_at`, `max_attempts`, business payload and `traceId`, and `tenantId` equal to the sole tenant's id.
- Integration: the same holds for an envelope with `tenantId: null` on a tenant task; a second run returns `{ stamped: 0 }` and changes no job.
- Integration: a system task's envelope with `tenantId: null`, a crontab-shaped payload, an already stamped envelope and a permanently failed legacy job are left exactly as they were.
- Integration: with two tenants (`createTestTenant` from `@semprec/data/testSupport`, #975) and one legacy tenant-task job the step throws naming the tenant count and the job is unchanged; with two tenants and no legacy job it returns `{ stamped: 0 }`.
- Integration: a legacy job with `locked_at` set makes the step throw naming its id, and no job changes.
- Unit: for a tenant task, an envelope without `tenantId`, one with `tenantId: null` and a raw payload each reject with `TenantScopeMissingError`, never call the handler, send no query through the helpers, and log `tenant_task_without_tenant` at error level with `jobName`, `jobId` and `traceId` and no payload field.
- Unit: a system task with a legacy envelope still runs its handler in system scope; a tenant task with a string `tenantId` still runs its handler in that tenant.
