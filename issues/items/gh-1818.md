## Context

Model tier rationale: This changes the confirm path of transcript cards into an atomic multi-write (Event, project relation, participant edges, transcript edge) driven by values the user can revise, across the Events, People and Transcripts isolation seams; a partial write or a cross-tenant id would corrupt data, and the confirm path is shared with every other card.

When no existing Event fits a recording, the pipeline's match step creates a card in Processing proposals that proposes a new Event (`backend/packages/data/src/transcription/transcriptEventMatch.ts`, confirm in `backend/packages/data/src/inbox/proposalActions.ts`). Today that Event is only `{ name: <transcript name>, type: meeting, date: <recording time> }`: the name is whatever the transcript was called (often the source file name), it has no start and end, no project, and no participants. The envelope cannot carry relations (`assertValidProposalEnvelope` in `backend/packages/data/src/inbox/inboxTickAction.ts` rejects relation properties in a `database` envelope), and confirm writes the Transcripts `event` edge after creating the Event.

This issue makes the proposed meeting complete. The card proposes a meeting named "Schůzka D. M." / "Meeting D. M." (day and month of the recording), with the recording's wall-clock start and end in the tenant's time zone, the project of the Event the card recommends (if any), and, on confirm, the participants taken from the speakers already mapped to people. It builds on #1416 (the Events calendar properties `timeFrom`, `timeTo`, `endDate`), on #1509 (the tenant's own person, who must not be added as a participant), and on #1640, which also lets a transcript card's Event proposal carry relations (the envelope relation rules are those of #1426 and #1476). #1830 relies on this issue so that no proposed meeting ever has an empty name. Matching itself is #1813, whose version of `transcriptEventMatch.ts` this issue edits (it already switched the envelope date to a date-only value); the recommendation that supplies the project's source Event is #1848.

Decisions:

- Participants are read at confirm time from the transcript's `speakers` edges as they are then, not frozen into the card; the tenant's own person is excluded. By the product owner: a speaker assignment confirmed after the confirm only adds the person to the Event's participants (the speaker card confirm, #1671, and the manual assignment, #1770, do that); changing or clearing an assignment never removes a participant. This issue writes nothing for later assignments.
- The project is taken from the recommended Event (`context.recommendedEventId` of the card); a card without a recommendation proposes no project.
- By the product owner: when no Event overlapped the recording at all, the card proposing a new meeting is still created (with the complete envelope of this issue) and the user can reject it; a variant without a card is not built.
- The meeting ends on the next day only when the recording crosses local midnight; then `endDate` is set, otherwise it is left unset.

## Task

Load `state-writes`, `canonical-keys`, `error-handling` and `testing`.

1. Envelope builder: in `transcriptEventMatch.ts` replace the new-Event envelope with `buildNewMeetingEnvelope`: `entityKind: "database"`, target Events, `properties { name, type: "meeting", date, timeFrom, timeTo, endDate? }` and top-level `relations { project: [projectId] }` when a project applies (the envelope relations shape of #1426). `name` comes from the new i18n key `transcript.newMeeting.name` in `backend/packages/data/src/transcription/i18n/{cs,en}.json` ("Schůzka {day}. {month}." / "Meeting {day}/{month}") rendered in the tenant user's `users.locale` for the recording's local day and month; it is never empty. `date`, `timeFrom` (the recording start) and `timeTo` (start plus duration) are wall-clock values in the tenant's time zone, converted with the calendar time module of #1418, as `YYYY-MM-DD` and `HH:mm`; `endDate` only across local midnight.
2. Pass the recommended Event's project into the builder from the call sites (the zero-candidate card and the recommendation card of #1848); a missing, trashed or project-less recommended Event gives no project.
3. Confirm: in `confirmProposalWithClient` (`proposalActions.ts`), for a transcript card with a `database` envelope on Events, in the same transaction as the Event create: write the envelope's `project` relation (through the atomic relations write of #1476); write the Events `people` edges for every person mapped by a Transcripts `speakers` edge at that moment, except the tenant's own person (#1509); then write the Transcripts `event` edge (as today). An envelope `project` that is not a live Projects item of the tenant, or any other failing write, rolls back everything: no Event, no edges, the card stays `proposed`, and the response is `400 validation_failed` for an invalid project.
4. Keep `revise` valid: the revised envelope for this shape is checked by `assertValidEnvelopeForCard` with the same rules (project must exist, `timeTo` after `timeFrom` unless `endDate` is set, per the Events validation).
5. Tests: `transcriptEventMatch.test.ts` (envelope for a recording 14 Oct 13:52, 47:10 long: `timeFrom` `13:52`, `timeTo` `14:39`, name "Schůzka 14. 10."; a recording crossing midnight; with and without a recommended project), `transcriptProposalActions.test.ts` (confirm writes Event, project, participants without the own person, and the transcript edge atomically; an invalid project writes nothing and returns 400; an unmapped speaker adds no participant; confirm run twice is idempotent).

## Scope

### In scope

- The complete proposed-meeting envelope (name, wall-clock start and end, project) and the atomic confirm that writes it with participants and the transcript edge.

### Out of scope

- The overlap matching and the recommendation of an Event: #1813, #1848.
- Suggesting speakers again for the new meeting's participants after confirm: #1942.
- Adding participants for speaker assignments confirmed later: #1671 (card confirm) and #1770 (manual assignment); removing participants when an assignment changes is not done.
- Leaving a transcript without a card when nothing overlapped: not built (decided by the product owner).
- Attaching a transcript to an Event later by hand: not planned yet; it waits for a product decision.
- Participant roles and invitations on Event people edges: #1757.
- The display name of the transcript itself: #1830.

## Acceptance criteria

- When the card for a recording of 14 Oct 13:52 lasting 47:10 is confirmed, an Event exists with `timeFrom` `13:52`, `timeTo` `14:39` (Europe/Prague), the card's project, the mapped speakers (without the own person) as people, and the Transcripts `event` edge, all written atomically.
- When the envelope names a project that does not exist in the tenant, nothing is written, the card stays `proposed` and the response is `400 validation_failed`.
- When no speaker is mapped, the Event has no participants and the confirm still succeeds.
- When the recording crosses midnight, the Event has an `endDate` on the next day.
- No proposed new meeting has an empty `name`.
