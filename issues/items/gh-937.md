## Context

Harvest issue #934 collected findings about targeted `UPDATE` statements that never confirm a row was matched (the repository's state-writes rule requires an affected-row check on every targeted write).

- PR #774 and PR #774 (the same defect, reported twice), `backend/packages/data/src/__tests__/docHistoryRetention.test.ts:45`: the first `UPDATE docs SET history_available_from = $2 WHERE id = $1` in `backdateBaseline` does not check `rowCount`, while the second `UPDATE` in the same helper and both updates in the neighbouring `setUpdateCreatedAt` assert `rowCount` is 1. A wrong `docId` would silently leave the original value in place.
- PR #791, `backend/packages/data/src/migrationJob/propertyTypeMigration.ts:175` and `:185`: the two targeted `UPDATE items` statements (`jsonb_set` at 175, `properties - $3` at 185) never check `rowCount`. The rows come from a `lockItemBatch` `FOR UPDATE` held until commit, so a zero count is theoretically impossible, but a silent no-op would leave the migration looking clean.

## Task

1. In `backdateBaseline` (`docHistoryRetention.test.ts`), capture the result of the first `UPDATE` and `expect(rowCount).toBe(1)` for it, the way the second `UPDATE` in the helper does.
2. In `propertyTypeMigration.ts`, pass the result of each of the two targeted `UPDATE items` statements to `requireAffectedRows` (`backend/packages/data/src/db/pool.ts:147`) with a context string naming the statement, so a zero-row update throws and rolls the batch's transaction back.
3. In `propertyTypeMigration.test.ts`, add a test for each of the two statements that makes it affect zero rows and expects the rejection. The batch's rows are held under `lockItemBatch`'s `FOR UPDATE`, so a real concurrent delete cannot produce the zero count; instead pass `runPropertyTypeMigrationJob` a `Pool` wrapper whose clients answer the one targeted statement (matched by its SQL text: `jsonb_set` for the first, `properties - $3` for the second) with `{ rowCount: 0, rows: [] }` without running it and forward every other query unchanged — the same proxy technique `failingSeedPool` uses in `backend/packages/data/src/__tests__/mailLiveSyncRoot.test.ts:84`.

## Touches

- backend/packages/data/src/migrationJob/propertyTypeMigration.ts

## Scope

### In scope

The two checks above.

### Out of scope

Every other finding of harvest issue #934 and anything adjacent to the lines named in the Task, even in the same file.

## Acceptance criteria

- In `backdateBaseline`, the result of the first `UPDATE docs` is captured and its `rowCount` is asserted to be 1, the same way the helper's second `UPDATE` already is.
- When one of the two targeted `UPDATE items` statements of `propertyTypeMigration.ts` affects zero rows, the batch's transaction rejects with the error `requireAffectedRows` throws, and no later row of the batch is written; a test in `backend/packages/data/src/__tests__/` exercises this for each of the two statements.
- When both statements affect a row, the existing `propertyTypeMigration` tests still pass unchanged.
