**Blocked by:** #26

## Context

The mail-sync foundation stores messages, folders, MIME metadata, aliases, and credentials. The mailbox experience needs stable recipient identity, delivery-failure linkage, People linkage, and a safe upgrade path before UI or sending can rely on those facts.

## Task

Persist `deliveredToAddress` at ingest using this exact precedence: highest `Delivered-To` occurrence, `X-Original-To`, `Envelope-To`, first registered mailbox alias matching structured `To`/`Cc`, then the mailbox primary address. Do not recompute it during rendering. Detect `multipart/report` with `message/delivery-status` as DSN/bounce mail and link it to the original outgoing message through `References`; do not treat it as an ordinary human reply. Add user-owned `People.emails` and maintain deterministic `person_email_index` address linkage without AI.

Add a numbered mail-module data migration for legacy Emails rows. Parse stored raw MIME when available; otherwise reconstruct `envelope`, `threadId`, and `messageId` as far as possible from legacy sender/recipient fields and set `migrationStatus = 'partial'`. Resume safely through the module-migration mechanism and never silently discard threading information.

## Scope

### In scope

- Alias precedence, DSN linkage, People email index, and populated legacy migration.
- Structured To/Cc/Bcc data already supplied by the mail-sync foundation.

### Out of scope

- Mailbox UI, SMTP sending, provider throttling, and full-text search.

## Acceptance criteria

- Tests cover every alias fallback and multiple `Delivered-To` headers.
- A DSN links to its outgoing message and is distinguishable from a person reply.
- Person linkage is deterministic for normalized addresses.
- Both raw-MIME and partial-reconstruction migrations preserve rows and record migration state.
