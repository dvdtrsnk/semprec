**Blocked by:** #267

## Context

Two mail paths read a Mailboxes item and then use it through optional chaining, so a mailbox that is gone produces a confusing outcome instead of a clear one. Both were flagged by post-merge reviews (of #93's and #95's pull requests), neither was addressed, and both are still on `develop`.

An important detail for both halves: `itemsStore.getItemById` selects by `database_id`/`id` with **no** `deleted_at IS NULL` filter, and nothing in this repository hard-deletes items — `chokePoint.softDeleteItem` sets `deleted_at`. A removed mailbox therefore comes back as a row with `deletedAt` set, not as `null`, and its `addresses` are still readable.

**1. `backend/packages/data/src/mail/mailSyncJob.ts`.** For a soft-deleted mailbox the pass runs to the end — full credential decrypt, full provider reconcile, Email items written — and only then fails: the closing `updateItemWithClient({ syncStatus: "ok" })` goes through `itemsStore.updateItemProperties`, which throws `NotFoundError` when the row is missing or soft-deleted. That aborts the write transaction; the `catch` block then tries to record the failure, and its own `updateItemWithClient` throws `NotFoundError` again, rolling back the `recordSyncError` in the same transaction. The task rejects with a `NotFoundError` that says nothing about the real cause, and the worker retries it forever. For the (in practice unreachable) case of a genuinely absent row, `parseAddressListProperty(undefined)` additionally yields `[]`, so the whole reconcile also runs with alias matching and the primary-address fallbacks silently disabled.

**2. `backend/packages/data/src/mail/send.ts`.** `sendDraftEmail` fetches draft and mailbox together, then null-guards only the draft (`if (!draft) throw new NotFoundError(...)`). The mailbox is used as `parseAddressListProperty(mailbox?.properties.addresses)`; when `mailboxItemId` matches no item this yields `[]`, and the from-address guard immediately below raises `ForbiddenError("From address X is not a registered address for mailbox Y")`. A caller that passed a wrong id is told it is forbidden rather than that the mailbox does not exist.

## Task

**`send.ts`** — add the missing guard directly after the existing draft guard, before the alias check:

```ts
if (!mailbox || mailbox.deletedAt) throw new NotFoundError(`Mailbox ${input.mailboxItemId} not found`);
```

The `deletedAt` half is deliberate and not optional: per the Context, a removed mailbox is a soft-deleted row, so a null-only guard would leave sending over a deleted mailbox working. Then use `mailbox.properties.addresses` without optional chaining. `NotFoundError` is already used in this file. Keep the existing `ForbiddenError` for a mailbox that exists but does not own the `from` address.

**`mailSyncJob.ts`** — treat a missing or soft-deleted mailbox item as "there is nothing to sync":

- Guard on the mailbox item that #267's prologue read produces, `if (!mailboxItem || mailboxItem.deletedAt)`, and return from `handleSyncMailAccountTask` immediately: no credential decrypt, no provider call, no `syncStatus` write. #267 places that prologue read at the top of the task, before the `mail_account_sync_state` read and before `getDecryptedCredential`, so this guard runs before any of them.
- Add a comment stating why this is a terminal no-op rather than a thrown failure: the mailbox item is the very row a sync status would be written to, so there is nothing to record a failure on — the `catch` block's `updateItemWithClient` throws `NotFoundError` on a soft-deleted item and rolls back the `recordSyncError` in the same transaction — and a task that can never succeed must not be retried by the worker forever.
- Use the non-optional `mailboxItem.properties` after that guard, including for `mailboxProvider` and `mailboxAliases`.

Add tests:

- `backend/packages/data/src/__tests__/mailSend.test.ts` — sending with a `mailboxItemId` that does not exist rejects with `NotFoundError`, not `ForbiddenError`; and sending over a soft-deleted mailbox rejects the same way.
- `backend/packages/data/src/__tests__/mailSync.test.ts` — a sync task whose Mailboxes item has been soft-deleted through the normal delete path **resolves** instead of rejecting, and never invokes the injected IMAP/Gmail/Graph adapter. Both assertions discriminate: on current code the task rejects with `NotFoundError` and the adapter has already run.

## Scope

### In scope

- The missing-or-deleted guards in `send.ts` and `mailSyncJob.ts`, plus the two tests above.

### Out of scope

- The `catch` block's error recording in `mailSyncJob.ts`, which stays exactly as it is — the guard exists precisely so that path is never reached for a removed mailbox.
- Soft-delete handling for the **draft** item in `send.ts`: the existing draft guard stays a null check, because the finding this issue closes is about the mailbox.
- The from-address authorization rule itself, unchanged for an existing mailbox.

## Acceptance criteria

- `sendDraftEmail` with an unknown or soft-deleted `mailboxItemId` throws `NotFoundError` naming that mailbox and never reaches the from-address check.
- A mail sync task whose mailbox item has been soft-deleted resolves as a no-op without calling the provider adapter — where today it reconciles first and then rejects with an unrelated `NotFoundError` that the worker retries forever.
- A normal sync pass for an existing mailbox, and sending from a registered address of an existing mailbox, both behave exactly as before.
