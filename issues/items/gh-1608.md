**Model tier:** high

## Context

Model tier rationale: A new persisted text format with a hand-written parser and serializer must round-trip exactly, escape correctly, and be reproduced by a second runtime (the WebView editor), so ambiguity or an escaping gap silently corrupts user content.

Every editor hands its content to the host as Markdown, and Semp, the web client and the desktop client read and write pages as Markdown; the app itself never shows Markdown syntax. Today the backend has no Markdown parser or serializer: a block's text is a plain field in `backend/packages/data/src/docs/blocks.ts`, and the only text-in-Markdown storage is the `project_agent_guidance.markdown` column. #1539 adds the shared block model (type registry, order array, `Y.Text` with `bold`, `italic`, `code`, `link` attributes). This issue adds the conversion between that model and canonical Markdown, in the same shared module so the server and the WebView editor run identical code.

The canonical format:

- One non-empty line is one block (no CommonMark soft line wrapping or lazy continuation: two lines from Semp are two blocks). A blank line is written between blocks except between adjacent list items.
- Block markers: `# `, `## `, `### ` for h1-h3; `- ` bullet; `1. ` number (always written as `1.`); `- [ ] ` and `- [x] ` todo (on read also `[X]` and `* ` bullets); `> ` quote; two spaces of indentation per level for bullet, number and todo; a subpage as `[Title](semprec://page/<id>)` alone on its line.
- Inline: `**bold**`, `_italic_` (and `*italic*` inside a word), `` `code` ``, `[text](url)` (a URL without a scheme gets `https://` on read). A soft line break inside a block is `<br>`. Crossed bold and italic inside a word is written as `<strong>` and `<em>`; on read, inline HTML `strong`, `b`, `em`, `i` and `br` are accepted.
- Characters `\ * ` [ ] <` and `_` at a word edge are escaped when written.

Decisions:

- Decision: line-start markers that appear in plain text (for example `16. 10. jsme...`, `# not a heading`, `- not a list`, `> not a quote`, `[ ] x`) are escaped on write (`16\. 10. jsme...`, `\# ...`, `\- ...`, `\> ...`, `\[ \]`) and unescaped on read, so a text block never changes type through a round trip or through text written by an agent. A naive serializer would not escape such prefixes; the WebView editor must adopt the same rule from the shared fixtures.
- Decision: the lossy parts (an unknown block type, and the indent of blocks that are not bullet, number or todo, which the model keeps for every type) are preserved as a comment line before the block: `<!-- semprec:block id=<id> type=<key> indent=<n> -->`. Without the comment, a block of an unknown type reads as `text` and indent on a non-list block reads as 0.
- Decision: an optional serializer mode writes the id comment before every block, for agents that need to address blocks by id (the Markdown page reads of #1678 can use it); the default mode writes no ids.
- Decision: the page block title is not stored in the model. The serializer takes a caller-supplied title resolver (`resolvePageTitle(pageId)`), writing an empty title when none is supplied; the parser reads only the id from the link and discards the title.
- Decision: no Markdown library is added. The format is a deliberate line-oriented subset and the code must run in a browser WebView.

## Task

Load `testing`. Implement in the shared block model module (location per the ADR from #1366).

1. `serializeBlocks(blocks, options?)` returns canonical Markdown from `PageBlock[]` (options: `resolvePageTitle`, `withIds`). `parseMarkdown(md, options?)` returns block inputs validated by the registry of #1539 (options: `allowPage`, default true; when false, a page link line makes parsing fail with a validation error naming the line). Both are pure functions.
2. Block mapping exactly as described in Context, including the indent rule (two spaces per level, clamped to 0-5 on read, written only for list blocks without a comment).
3. Inline conversion between `Y.Text` delta attributes and Markdown, including escaping and unescaping, soft breaks as `<br>`, `<strong>`/`<em>` for crossed formatting inside a word, and `https://` defaulting for scheme-less links.
4. Preservation comments as decided above, and the `withIds` mode.
5. `stripMarkdown(md, maxChars)` returns plain text (markers, emphasis, links reduced to their text, soft breaks to a space) truncated to `maxChars`, for subtitles and full-text indexing by later consumers. Embeddings are out of scope.
6. A shared JSON fixture file of Markdown to blocks vectors (including the cases below), stored in the module directory so both the server test and the WebView editor can load it, plus the server-side test runner that executes every vector in both directions and a round-trip check (canonical Markdown parses and serializes back unchanged).
7. Fixtures must include: a project-notes sample (h2, a second-level bullet, a done todo, a quote, inline code such as `` `0.4 (52)` ``, a link, a subpage link); `16. 10. jsme...` written as `16\. 10. jsme...` and read back as the same text; two lines without a blank line parsed as two text blocks; one block with `<br>` as a single block with a soft break; an unknown-type block and a non-list indented block each preserved through the comment; a page link with `allowPage: false` rejected.

## Scope

### In scope

- Markdown serialization and parsing for page blocks, inline formatting, escaping, preservation comments, `stripMarkdown`, the shared fixtures and their server-side runner.

### Out of scope

- Validating Markdown stored in item properties: #1675.
- Reading a page as Markdown, replacing and inserting Markdown through the API: #1678, #1679.
- Making the journal and area text flows use it: #1613, #1619, #1711, #1975, #1643, #1614.
- Full-text indexing of page text: #1658.
- The WebView editor adopting the fixtures and the new escaping rule (client work, not planned here).
- Embeddings of page text.

## Acceptance criteria

- When the project-notes fixture is parsed and serialized again, then the output equals the input exactly.
- When a text block contains `16. 10. jsme...`, then `serializeBlocks` writes `16\. 10. jsme...` and `parseMarkdown` returns a `text` block with the original text.
- When two lines are separated by a single newline, then `parseMarkdown` returns two `text` blocks; when a block contains a soft break, then it serializes as one line with `<br>`.
- When the Markdown contains a subpage link and `allowPage` is false, then parsing fails with a validation error.
- When a block of an unknown type or a non-list block with indent 3 is serialized and parsed again, then type and indent survive through the `semprec:block` comment.
- Every vector of the shared fixture file passes in both directions.
