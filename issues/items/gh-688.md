**Blocked by:** #687

## Context

`sweepDueHeartbeats` (`backend/packages/data/src/scheduler/schedulerStore.ts:437-480`) selects every due row with `SELECT id, rule, next_fire_at, action_id FROM project_heartbeats WHERE enabled AND next_fire_at IS NOT NULL AND next_fire_at <= now() FOR UPDATE SKIP LOCKED` — no `ORDER BY`, no `LIMIT` — and then, still inside the single transaction `handleHeartbeatSweepTask` (`sweep.ts:60-65`) opened, inserts one occurrence, updates `next_fire_at` and calls `enqueueJob` per row. Two consequences:

- The sweep is all-or-nothing and unbounded: after downtime, every heartbeat in the system is due at once; one failing `enqueueJob`/occurrence write (a constraint error, a connection drop) rolls back every other row's advance and enqueue, and the next minute repeats the whole batch.
- The due check uses Postgres `now()`, but the next occurrence is computed from the JS clock: `const now = new Date()` (line 449) feeds `computeNextFireAt(rule, timezone, now)`. With the application clock behind the database clock by more than the distance to the due time, a fixed rule (`dailyTime`/`weekly`) is computed as due again at the same `next_fire_at` (`computeNextFireAt` only moves past `after`), the row is re-selected next minute, `insertHeartbeatOccurrence` (line 467) hits the `(heartbeat_id, scheduled_for)` conflict on a non-reactivatable occurrence, returns `null`, and the `continue` (line 468) never advances `next_fire_at` — the heartbeat is stuck, re-selected every minute, never firing again.

This issue lands after D4 because both edit `sweep.ts` and the scheduler test file; D4's changes are confined to the fire task functions, this one to the sweep.

## Task

1. **Chunked, keyset-paginated select.** Change the signature to `sweepDueHeartbeats(client: PoolClient, moduleRuleKinds: HeartbeatRuleKindRegistry = new Map(), afterId: string | null = null)` and the select to
   `SELECT id, rule, next_fire_at, action_id, now() AS db_now FROM project_heartbeats WHERE enabled AND next_fire_at IS NOT NULL AND next_fire_at <= now() AND ($1::uuid IS NULL OR id > $1) ORDER BY id LIMIT $2 FOR UPDATE SKIP LOCKED` with `$2` = a module-private `const SWEEP_CHUNK_SIZE = 100`.
   Return type becomes `SweepChunkResult = { fired: SweptHeartbeat[]; lastId: string | null; exhausted: boolean }` (`lastId` = the last selected row's id in `id` order, `null` when none; `exhausted` = the select returned fewer than `SWEEP_CHUNK_SIZE` rows). Export the `SweepChunkResult` type only. Document in the docstring why pagination is by `id` and not by `next_fire_at`: a row the sweep deliberately leaves due (an unparseable rule, `recordHeartbeatFailure` + `continue` at 456-465) must be visited at most once per sweep, and `ORDER BY next_fire_at` would put such rows first in every chunk.
2. **Next fire from the database clock.** Delete `const now = new Date()`; use the row's `db_now` (a `Date` from `now()`) as the `after` argument of `computeNextFireAt` for that row. `getSystemTimezone` stays read once per chunk.
3. **One transaction per chunk, loop until a short chunk.** In `sweep.ts` `handleHeartbeatSweepTask`: `let afterId: string | null = null; for (let chunk = 0; chunk < MAX_SWEEP_CHUNKS; chunk++) { const result = await withTransaction(pool, (client) => sweepDueHeartbeats(client, moduleRuleKinds, afterId)); if (result.exhausted) return; afterId = result.lastId; }` with a module-private `const MAX_SWEEP_CHUNKS = 50` in `sweep.ts` (5 000 rows per minute-tick; anything beyond waits for the next tick — state the bound in the docstring). A chunk that throws propagates as today (the task fails, the remaining rows are picked up next minute) — but the chunks already committed stay committed.
4. **Existing callers/tests**: `scheduler.test.ts` calls `sweepDueHeartbeats(client, ...)` directly in several cases and reads its return value; adapt them to `.fired`. Any other caller found by `grep -rn "sweepDueHeartbeats" backend/` is adapted the same way (there is none in production code besides `handleHeartbeatSweepTask` at the time of writing). No new runtime export, so `publicSurface.test.ts` is untouched.
5. **Tests** (`backend/packages/data/src/__tests__/scheduler.test.ts`, integration):
   - 250 due `dailyTime` heartbeats (insert directly with `next_fire_at = now() - interval '1 minute'`): one `handleHeartbeatSweepTask(pool)` call fires all 250 exactly once (250 occurrences, 250 jobs) and every `next_fire_at` is in the future; instrument via a pool wrapper counting `connect()` calls that the sweep opened 3 transactions (100 + 100 + 50).
   - Chunk isolation: 150 due heartbeats and a pool wrapper whose second `connect()` rejects with `new Error("simulated outage")`: `handleHeartbeatSweepTask(wrappedPool)` rejects with that error, the first chunk's 100 rows are fired and advanced (100 occurrences, 100 jobs), the remaining 50 are untouched and still due; a second `handleHeartbeatSweepTask(pool)` call on the real pool fires exactly those 50.
   - Clock skew: a `dailyTime` heartbeat due at `T` in the past; stub `Date.now`/`vi.useFakeTimers` so the JS clock reads `T - 2h` while Postgres `now()` is real; after one sweep the row's `next_fire_at` is `> now()` (the next calendar occurrence after the database clock) and a second sweep selects nothing for that heartbeat.

## Scope

### In scope
- Keyset-chunked `sweepDueHeartbeats`, one transaction per chunk with a bounded loop, DB-clock `computeNextFireAt`, and the tests above.

### Out of scope
- Changing the `continue` path for a non-reactivatable occurrence conflict (`schedulerStore.ts:467-468`): once the next fire is computed from the database clock, the skew path that reached it is closed; the existing "idempotent no-op ... no second next_fire_at advance" test keeps its meaning.
- The fire task's failure handling (D4) and `core.agentRun`'s retry behaviour (sibling issue D11).
- `recomputeAllForTimezoneChange` and the onItemEvent trigger path, which have their own selects.

## Acceptance criteria

- When more than 100 heartbeats are due, one sweep tick fires all of them exactly once, in ceil(n/100) separate transactions, and a failure inside chunk k leaves chunks 1..k-1 committed (their occurrences, jobs and advanced `next_fire_at` persist) and chunk k's rows still due.
- When the application clock is behind the database clock, a fixed-rule heartbeat that fires is advanced to the next calendar occurrence after the database's `now()` and is not re-selected by the next sweep.
- When a chunk contains a row whose rule cannot be parsed, that row records `last_error`, stays due, and does not prevent the sweep from reaching every other due row in the same tick.
- A sweep tick never opens more than 50 chunk transactions.
