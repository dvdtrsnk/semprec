Subpages: storage, creation, duplication, deletion and orphans.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: subpages-1 (storage, creation, duplication, deletion, orphans)

#### (a) Decisions adopted from open questions and gaps

- Where subpages live -> hidden system database `pages` (one item per page, doc kind `page`, `parentItemId` text property, `title` mirror), created on first use under an advisory lock, not by the seed -> the issue chain of #1676 does not depend on the generic system-module delivery step, and a lazy create needs no tenant backfill.
- Title source -> the text of the `page` block in the parent is the source of truth; Pages `title` is a mirror (rename op + 10 s debounced job) -> as the design note specifies. This conflicts with the block-model issues, which define `page` blocks without `text`; #1393 records the amendment and #1676 allows plain-text `text` on `page` blocks in the block model.
  -> Decided by the product owner: the text of the block in the parent is the source of truth and the Pages item is its mirror.
- Position of a trashed page's block -> stored in the parent document in a top-level Y.Map `trashedPages` (the choke point does not update trashed rows, so the Pages item cannot carry it) -> every trashed page removes its block and every restored page re-inserts it (uniform rule, descendants included).
- Duplicate copy suffix -> localized by the caller's locale (" (kopie)" / " (copy)"), root only; a cap of 500 pages per copy; trashed or missing nested pages are left out of the copy.
  -> Decided by the product owner (#1722).
- Rename of an orphan page (no block in the parent) -> changes only the item title.
- Orphan sweep rule -> parent document has no block with the page id and the document's last update is at least 1 hour old; daily core cron task; trashing goes through the normal item delete (restorable for 30 days). Moving a page block to another document is not supported by the server (parent link is not updated) and is treated as an orphan.
  -> Decided by the product owner: a daily sweep sends pages without a block in their parent, whose parent document is at least an hour old, to the trash, restorable for 30 days (#1749).
- page -> other block type (#1876) -> Decided by the product owner: an explicit confirmed operation `page.convertToBlock` with `confirmedPageCount` (409 with the current count on mismatch); the subpages go to the trash and stay restorable.
- `createSubpage` output -> `{ pages: [{ pageItemId, docId, blockId }] }` (an array because `fromBlockIds` creates several) instead of the single object in the design note.
- Breadcrumbs through `parentItemId` -> path walk plus `page.get` breadcrumbs for Pages items; split out of #1676 into #2014 (one mechanism per issue), as was the conversion of selected blocks into subpages (`fromBlockIds`, #2013). #1676 keeps the Pages database and `page.createSubpage` for a single new subpage.
- Delete impact: #1723 exports `collectSubpageTree` for #1856.
  -> Decided by the product owner: the delete confirmation states the total number of all nested pages ("also deletes 7 subpages"), because a confirmation must state the full impact. #1856 therefore counts the whole subtree (`subtreePageCount`), distinct from page.get's `subpageCount` (root page blocks); the change to #1856 is handed to its batch.

#### (b) Open questions that remain for the product owner

- Moving a page block between documents (cut and paste): should the server update `parentItemId` (reparent) instead of the sweep trashing the page?
- Should entries in `trashedPages` of purged pages be cleaned up?
- Is a depth or size limit for page trees wanted beyond the 500-page duplicate cap?
- The exact HTTP method and path of `page.createSubpage`, `page.duplicate`, `page.rename` and `page.convertToBlock` are left to the ADR of #1394 (the issues say "the route recorded by that ADR").

#### (c) User-visible behavior

A page can contain subpages of any depth. The user can turn an empty block into a new subpage, or restyle selected blocks into subpages that take the block text as their name; the subpage opens full screen with breadcrumbs (for example "Notes > Release checklist") and its title can be edited at the top, which also renames the block in the parent. A page can be duplicated with all its nested subpages as an independent copy named "<title> (kopie)". Subpages also work under Journal days that do not exist yet (the day is created with the first subpage). Deleting a page or a host (project, area, event, Journal day) sends its subpages to the trash with it and removes the page block from the notes; restoring within 30 days brings back the pages and the block at its place. The trash shows a deleted page as a page with its title and path, not as a collection, and nested pages do not clutter the list. Pages whose block was deleted directly in the editor are tidied into the trash automatically. Converting a page block back to a normal block asks for confirmation of how many pages will be removed and sends them to the trash, restorable for 30 days. A delete confirmation states how many nested pages are deleted in total.
