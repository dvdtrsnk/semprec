## Context

Model tier rationale: Declares one link rule on top of the link-rule engine and exercises it with tests across Events, Projects and Files, with no new engine code, but the behavior depends on three blockers' semantics so the tests must pin the chain carefully.

An Event can have files attached through the `Files.events` relation added by #1588. Today nothing connects such a file to the Event's project: `Events.project` and `Files.projects` are independent, so an attachment of a meeting for a client project is not found under that project, and its company is empty.

The link-rule engine built by #1411 (declaration and validation in module manifests) and #1593 (propagation of inherited values) lets a manifest say that a target property inherits its values from a source property along a relation. #1653 adds the next hop for files: a file's companies are inherited from the file's projects. #1516 makes a user or agent write to an inherited value break that value's link, after which the value is kept as the item's own.

This issue declares the Event-to-attachment rule and proves the whole chain: when a file is attached to an Event, the file's project is inherited from the Event's `Events.project`, and its company follows from that project through the rule from #1653.

Decision: removing an attachment only deletes the `Files.events` edge. The file stays in Files, and the project and company it inherited stay on it as its own values (the inherited links are detached, the values are kept). Moving the file to the trash on removal is not done.

Decision: changing an inherited value by Semp is deferred to the approval flow from #1758; this issue adds no approval logic.

Shared-file ordering: this issue also waits for #1754 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys`, `state-writes`, `error-handling`, `adr-conventions` and `testing`.

1. In the system databases module manifest, declare one link rule with source `Events.project`, target `Files.projects`, joined through the `Files.events` relation, using the declaration format and validation from #1411. Use the stored keys of the existing properties; do not introduce new properties or relations.
2. Seed: make sure a fresh install gets the rule from the manifest. Nothing is backfilled: the engine of #1593 creates a link only when a via edge is written and has no replay of existing edges, so a `Files.events` edge written before the rule existed gives its file no inherited project until that edge is written again, as #1653 decided for its rule. Write no migration, no manifest data-migration entry and no cutover.
3. Integration tests (see the `testing` skill) covering the chain end to end:
   - Attaching a file to an Event that has a project gives the file that project as an inherited value, and the file's company is then inherited through the project.
   - Changing `Events.project` on the Event updates the inherited project on its attachments, and their inherited company becomes the company of the new project. The link engine clears the old company when the `valueLinks` process replaces the project edge; that rule is delivered with #1697.
   - Removing the attachment (deleting the `Files.events` edge) leaves the file in Files with its project and company as its own, no longer inherited: the file has no value link left, and a later change of the project's company or of the Event's project does not reach it. The same holds for a file whose project link the user had broken before the removal.
   - Removing the attachment of a file that had its own project before it was attached leaves the file's company inherited from that project (#1653).
   - Removing one of two Events a file is attached to leaves the file following the other Event: its `projects` link stays `on` with that Event as its only source, and its `companies` link stays `on`.
   - A user write of the file's project or company breaks the inherited link and the value stays.
   - Attaching a file to an Event whose project is in the Trash writes the attachment and gives the file no project. The link engine leaves out values that are in the Trash; that rule is delivered with #1697.
   - A `Files.events` edge that existed before the rule (a fixture row written without the hooks, as `fileCompaniesLinkRule.test.ts` does for #1653) gives its file no project and no value link, and a later change of the Event's project does not reach that file.
   - Removing the attachment while another transaction holds the file row waits for that row without holding a value link row of the file, and completes after the release.
   - A user removal of the file's project (a `Files.projects` edge of a file whose `projects` link is `on`) while the propagation of its Event's project works on the same file settles in both orders in which the two reach the file row: no transaction ends with a deadlock error (`40P01`), the user's removal is committed and the link is broken by the user. The order of such an edge write is delivered by the source `[value-link-edge-lock-order 01/01]`; this issue adds no lock to that path.
4. If the project's seed i18n catalogs contain a label for the new rule, add it to `seed/i18n/cs.json` and `seed/i18n/en.json`; otherwise do not touch them.
5. Company ends with the attachment: the file keeps its project when the attachment is removed, so the rule of #1653 alone would keep the company following that project. In `backend/packages/data/src/blobs/eventAttachmentLinkRelease.ts` (new) export a relation-edge-changed hook (#1530) that acts only on the removal of a `Files.events` edge, and register it in `domainWriteHooks.ts` immediately before `linkRuleEdgeHook`, because it has to read the file's `projects` value link before the engine deletes it. It works through the value-link store of #1516, as `transcription/transcriptCompanyLinkRelease.ts` of #1697 does, and locks the file row first, then the `projects` link row, then the `companies` link row. It does not look at whether the file is in the Trash.
   - When the removed Event is the only source of the file's `projects` link of rule `fileProjectsFromEvents`, whatever that link's state, the hook deletes that link with its source row and deletes the file's `companies` link of rule `fileCompaniesFromProjects` with its source rows, whatever its state. The project and company edges are not touched, so both read as the file's own values. The file is announced to clients after the commit.
   - When another Event still feeds that `projects` link, the hook removes the removed Event from the sources of a link that is not `on` (the engine does this for a link that is `on` and recomputes the projects) and leaves the `companies` link alone.
   - When the file's `projects` link does not name the removed Event, or the file has none, the hook changes nothing, so a company that follows a project the file had on its own keeps following it. A file whose Event was in the Trash before the removal is in this case too: the source detach of #1656 has already deleted its `projects` link, so its company keeps following its project (see Out of scope).

ADR: add `docs/adr/<date it is written>-an-event-attachments-company-link-ends-with-the-attachment.md` (`status: accepted`, `area: [backend]`, `supersedes: []`), referencing the ADR of #1697 (`transcript-values-are-inherited-by-link-rules-whichever-process-writes-the-edge`), `[[2026-11-01-value-link-relations-use-nonblocking-admission-and-scoped-lock-waits]]`, `[[2026-11-05-value-link-propagation-keeps-separate-hop-budgets]]`, `[[2026-09-10-single-writer-ownership-model]]` and the ADR that the source `[value-link-edge-lock-order 01/01]` added. It records: the rule, and that `Files.projects` stays `owner: user` and is written by the `valueLinks` process only while the file's link is `on`; the release of step 5 with its condition, its place before the engine's hook and its lock order; that nothing is backfilled; that moving the Event to the Trash leaves the company link on, and that an attachment removed after its Event was in the Trash therefore keeps a company that follows its project; and the relation composition the rule creates. `Files.projects` is the target of this rule and the via relation of `fileCompaniesFromProjects`, so a user or agent edge write on it meets the propagation job, the engine's hook for a `Files.events` edge and the hook of step 5 on the same file row and `projects` link row. ## Acceptance criteria

- When a file is attached to an Event whose project is P, then the file's projects contain P as an inherited value, and the file's company is the company of P, also inherited.
- When the Event's project changes from P to Q, then the attached file's inherited project becomes Q and its inherited company becomes the company of Q.
- When the attachment is removed, then the file still exists in Files and keeps P and its company as its own (not inherited) values.
- When a user sets a different project on the file, then the inherited link for that value is broken and the user's value is kept.
- When a file is attached to an Event whose project is in the Trash, then the attachment is written and the file gets no project.
- When the attachment of a file that had its own project before it was attached is removed, then the file's company still follows that project.
- A file attached to an Event before the rule existed is not changed by deploying the rule.
- When a user removes the file's project while the propagation of its Event's project works on the same file, then both transactions settle without a deadlock error, in both orders.
