**Model tier:** medium

## Context

Model tier rationale: One flow (upload bytes as a standalone blob, then create the item and its relations in one transaction) built from already-delivered operations, with an existing store and fixtures, but the dedup and cleanup semantics need care.

The New file form uploads the bytes first ("Uploading... 40 %"), and only Save creates the Files item; until then the user can still remove the file. Today the only upload route that makes a Files item is `POST /api/files` (`backend/services/semprec-api/src/filesHandler.ts` into `ingestUploadedFile` in `blobs/fileUploadStore.ts`), which creates the item immediately and, when the bytes match an existing live item by content hash, returns and later edits that earlier file (HTTP 200 instead of 201). Using it for the form would let a cancelled form leave an item behind, or let Save modify an unrelated earlier file with the same bytes.

Decisions:
- The form uses the standalone blob upload from #1401 (bytes only, deduplicated at blob level, unused blobs collected by its garbage collector), then Save creates the item. Cancelling leaves no item; an earlier file with identical bytes is untouched.
- Save is the `item.create` operation with relations from #1590, in one transaction: `{ name, type, date, file: { blobId } }` plus `projects` (and any other Files relations the form sends).
- `date` defaults to today in the tenant's time zone through the property defaults from #1389, so this issue only declares the default and the caller may override it.
- `type` is not sent by the client for uploads: the server fills it from the blob content. The default is therefore also applied when the client omits it.
- Attaching an uploaded file to a task, event or health record from the originating screen is a different flow (#1645); it is not this issue.

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. Declare the Files `date` property default as "today in the tenant time zone" in the Files seed and its per-tenant schema update mechanism provided by #1389, and a derived default for `type` from the blob (the server resolves `file.blobId` to the blob's detected type, using the content-based mime stored by the upload path, when `type` is absent).
2. Make the create path accept a `file: { blobId }` for the Files database that refers to a blob created by the standalone upload, rejecting a blob id that is not visible to the caller with the same answer as an unknown id (no distinction), and a second create for the same blob id is allowed (two items may point at one deduplicated blob).
3. Verify the whole flow end to end in a test: upload bytes as a blob, create the item with a project relation in one call, read it back with `date` set to today in the tenant time zone and `type` filled in; a cancelled flow (blob uploaded, no create) leaves no Files item and, after the collector's grace period, no blob; uploading bytes identical to an earlier Files item and then creating a new item leaves the earlier item unchanged.
4. Add the API documentation for the flow next to the existing Files upload description.

## Scope

### In scope

- Creating a Files item from a previously uploaded standalone blob with relations in one transaction, the `date` default and the derived `type`.

### Out of scope

- The standalone blob upload route and the unused-blob collector (#1401).
- Content-based type detection (#1410); this issue only reads its result.
- Relation creation with the item itself (#1590).
- Attaching an upload to another item from the originating screen (#1645).
- Converting HEIC to JPEG: not planned (the client converts HEIC to JPEG before upload).
- Inbox-origin of the created item (#1659).

## Acceptance criteria

- When a blob is uploaded and then an item is created with `file.blobId` and a project, then one Files item exists with that project, `date` equal to today in the tenant time zone and `type` taken from the blob content.
- When the form is cancelled after the upload, then no Files item exists and the unused blob is collected later.
- When the uploaded bytes equal those of an earlier Files item, then the earlier item is not changed and a new item is created.
- When `file.blobId` is unknown or not visible to the caller, then the answer is identical in both cases and no item is created.
- When the client sends an explicit `date`, then it is stored instead of the default.
