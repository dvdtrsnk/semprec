## Behavior specification

Library: metadata lookup, catalog, covers and automation.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: library-1

#### Adopted decisions
- Store "Unknown author" or leave `author` empty? -> leave empty, client shows the placeholder -> avoids storing display text and keeps the fill-if-empty rule meaningful.
- Source rating for movies: TMDB or ČSFD? -> TMDB (the label derives from the host of `sourceUrl`, not a stored field or a hardcoded domain) -> TMDB has a usable API; ČSFD/IMDb/Databáze knih wait for a verified API.
- Add `secondaryRating` to books or fix the sheet text? -> no source rating for books -> conservative, no schema growth.
- Who owns author/year/type/isbn when automation fills them? -> explicit handoff in the library module contract: automation writes them only into empty values and never on a locked item (alternative `sourceAuthor`/`sourceYear` not adopted) -> keeps one writer per value at a time, no second field per property.
- `books.isbn` and `books.year` owners -> `user`.
- Heartbeat config cutover sets `source` to `openLibrary`/`tmdb` together with the new keys in 02; the fetchers arrive in 03/04 (the dispatcher refuses unknown sources, noop result for `none`).
- TMDB token: v4 read token in the Authorization header, env var `TMDB_READ_TOKEN`; no token means `sourceUnavailable`.
- Stored `done` maps to `found` in the response (no CHECK rename); `notFound` is added to the CHECK; exception text is never stored (error codes instead).
- `notFound` means the source returned no match, not a missing cover.
- Automation state exposed as additive `include=automation` on `item.get`, `database.query`, `view.query` (generic, not library-only); `locked` is reported as stored but no lock toggle is added.
- Locking a whole item (a lock toggle and a "Locked" state row in the item detail) -> not built; the lock is dropped from the design in v1 -> Decided by the product owner: not needed in v1, undo and the trash already make changes reversible.
- Item creation time: general `items.created_at` column with `updated_at` backfill; sort spec gets a separate `{system: ...}` variant -> Decided by the product owner: the general creation-time column, one mechanism for every database instead of a property in each.
- Ratings: integer 0-5 (0 = none) on items, integer 1-5 on `watchedWith` edge metadata.
- Splitting book authors for filtering -> not done -> Decided by the product owner: not in v1; authors stay text, splitting is an extension beyond v1.

#### Open questions for the product owner
- `include=automation` depends on an `include` parameter existing in generic operation schemas; if the relations include lands first it is extended, otherwise `library-metadata 06` adds it.
- Rollback: widening `item_automation.status` with `notFound` conflicts with the previous release's strict status mapping; the implementer of `library-metadata 05` must satisfy the one-release rollback rule (may need to be split across two releases).
- Provisioning `TMDB_READ_TOKEN` in the deployment secret groups (not planned yet).
- Notes unification (library-catalog 05) is excluded and waits for a product decision.

#### User-visible behavior
A user adds a book or a movie or series by title only. The item appears at once as "searching" and the backend looks up author, year, ISBN and cover from Open Library (falling back to Google Books) for books, and year, type, cover, source rating and source link from TMDB for movies. Values the user typed or locked are never overwritten. The app can show whether the lookup is still running, found nothing, or failed, when it will be tried again (nightly), and is told as soon as a run ends. The list can be sorted by when an item was added, ratings are validated (whole stars 0-5, per-person ratings 1-5), and Czech labels match the app ("Filmy a seriály", "Chci číst", "Viděno", "Hodnocení zdroje", "Viděl jsem s").


### Decisions: library-2

#### Adopted decisions
- Manual cover without a second writer -> separate user-owned `coverOverride`, `coverRemoved`, `coverSource` properties; the job keeps writing only `cover` -> display rule is "removed ? none : override ?? cover".
- Removing a cover: only `coverRemoved`, or also lock the whole item? -> only `coverRemoved` (recommended); the item is not locked and the automation still fills other data.
- Lock/unlock routes -> not added; the retry route lifts a stuck `locked` state.
- Whole-item lock from the design -> Decided by the product owner: dropped from the design in v1 (undo and the trash provide reversibility), so no lock/unlock routes and no state row.
- Databáze knih, ČSFD and IMDb candidate sources -> Decided by the product owner: not added until a usable API is verified; scraping is not used because it is fragile.
- "Search again" -> clears the three override properties, resets the automation to pending and enqueues the job immediately (202).
- User photo / user image -> uploaded through the standalone blob upload, then plain item PATCH; no Files item.
- Candidates -> stored by the job (max 3, replaced each run); GET reads storage only; refresh enqueues the job; select downloads through the outbound address checks.

#### Open questions for the product owner
- Reference counting of cover blobs depends on the upload/collection issue; the implementer must confirm that purging an equal-bytes Files item cannot delete a cover blob.

#### User-visible behavior
A user can replace a book or movie cover with a photo or an image of their own, remove the cover, ask Semp to search again immediately (instead of at 04:00), and see up to three alternative covers found by the lookup and pick one. A manual choice is never overwritten by later lookups, which keep filling the other details. Removing a cover keeps it removed.
