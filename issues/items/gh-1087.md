## Context

Model tier rationale: The acceptance flow is pinned step by step, but its locked re-check, provisioning failure path and e2e wiring across many seams warrant a stronger worker.

Accounts are created only by an admin's invitation; `bootstrapFirstAccount` (`backend/packages/data/src/auth/authActions.ts:174-190`) stays the only way to create the very first one. #1040 lets admins create, list and revoke invitations in the global table `invites(id, email, token_hash, invited_by, created_at, expires_at, accepted_at, revoked_at)`; the raw token appears once in `<APP_BASE_URL>/?page=invite#token=<token>` and only its `hashToken` digest is stored (`backend/packages/data/src/auth/token.ts:23-25`). Nothing accepts an invitation yet, and `tenants_single_tenant_guard` (`ON tenants ((true))`, #968) makes a second tenant impossible. The security gate #1086 is signed, so this issue drops the guard and adds acceptance — the only path to a second account.

Decided behaviour: acceptance is public and throttled per client IP (#1073's limiter already defines the `invitationAccept` action, 10 per hour); every unusable token (unknown, expired, revoked, used) gets the same 404; one transaction creates the tenant (`provisioning`), the user (`member`, bound to it) and consumes the invitation; then `provisionTenant(pool, tenantId)` (#1005) seeds the tenant's own system databases and makes it `active`, and only an `active` tenant authenticates (#980). The new tenant gets no `tenant_ai_budgets` row (AI refused until an admin sets caps). Its id is created server-side, never read from the request.

Follow `backend/services/semprec-api/src/setupHandler.ts:27-80` (public route, 64 KiB cap, `toPublicErrorBody`, `handleRequestSafely`) and its branch in `backend/services/semprec-api/src/app.ts:141-144`, `MIN_PASSWORD_LENGTH` (`authActions.ts:35`), the unlocked-check-then-locked-recheck of `authActions.ts:180-189`, the unique-violation check of `backend/packages/data/src/chokePoint/databasesStore.ts:10-13`, and `clientIpFromRequest` (`backend/services/semprec-api/src/clientIp.ts:15-22`). The test harness of #975 already drops the guard in the test database (`DROP INDEX IF EXISTS`, which keeps working).

## Task

Load `db-migrations`, `state-writes`, `io-hardening` and `error-handling` (a migration, a multi-row write, a new public route, and failure mapping).

1. **Migration** (next free ordinal at commit time): `DROP INDEX tenants_single_tenant_guard;`, commented as a relaxation whose previous release is strict (#1086).
2. **`backend/packages/data/src/tenancy/acceptInvitation.ts`**: `acceptInvitation(pool, input: { token: string; password: string }, provision = provisionTenant): Promise<PublicUser>`, all inside `runAsSystem("invitation-acceptance", …)`:
   1. `input.password.length < MIN_PASSWORD_LENGTH` → `ValidationError`, before any lookup.
   2. Unlocked lookup of a usable invitation (`token_hash = hashToken(token) AND accepted_at IS NULL AND revoked_at IS NULL AND expires_at > now()`); none → `NotFoundError("Not found")`. Then `hashPassword` outside any transaction.
   3. `withTransaction`: re-select the same invitation `FOR UPDATE` (none → `NotFoundError("Not found")`); insert the tenant with status `provisioning` through `backend/packages/data/src/tenancy/tenantsStore.ts` (add a `createTenant(client, status)` there only if it has none); `createUser` with the invitation's email, the new tenant id and role `member` (as #968 extended it); a `23505` on `users_email_key` → `NotFoundError("Not found")` (rethrow anything else); `UPDATE invites SET accepted_at = now() WHERE id = $1 AND accepted_at IS NULL` checked with `requireAffectedRows`.
   4. After the commit, `await provision(pool, tenantId)`. On failure log `invitation_provisioning_failed` with the tenant id only (never email or token) and rethrow; the tenant stays `provisioning`, the account cannot authenticate, and the next deploy's seed step provisions it (it iterates `provisioning`, `active` and `suspended` tenants, #1005).
3. Export `acceptInvitation` from `backend/packages/data/src/index.ts` beside the other `./tenancy/*` exports and add it, in sorted position, to `EXPECTED_RUNTIME_EXPORTS` in `backend/packages/data/src/__tests__/publicSurface.test.ts:44`.
4. **`backend/services/semprec-api/src/invitationHandler.ts`**: `createInvitationRequestListener(pool, { trustProxy, clientIpThrottle? })` serving only `POST /api/invitations/accept` (anything else → 404 `{ error: "Not found" }`). With `ip = clientIpFromRequest(req, { trustProxy })` and the throttle from `createClientIpThrottle()` (`backend/services/semprec-api/src/clientIpThrottle.ts`, #1073; default one per listener), a non-null `retryAfterSeconds("invitationAccept", ip)` answers before the body is read exactly as login's throttled response does (429, `code: "rate_limited"`, `Retry-After`). Body `{ token: string, password: string }`, both non-empty (else 400), capped at 64 KiB (413). A `NotFoundError` is recorded with `record("invitationAccept", ip)` before answering 404; validation failures are not recorded. Success → 200 `{ user }`. `ChokePointError` → `toPublicErrorBody`; anything else → logged 500 without token, email or password.
5. Mount it in `app.ts` beside `/api/setup`. Add the `routeMatrix.ts` entry `accept invitation` (`POST /api/invitations/accept`, `surface: "api"`, `public: true`, `tenancy: "anonymous"`, `publicReason`: no session exists yet; the single-use token is the credential and every unusable token gets the same 404), its `ROUTE_HANDLER_FILES` mapping in `backend/services/semprec-api/src/__tests__/chokePointWriteBoundary.unit.test.ts:17` (that test fails for an unmapped route), and its `anonymous` case in `tenantIsolationRoutes.test.ts` (#1053).

## Acceptance criteria

- Integration (`acceptInvitation.test.ts`): a valid invitation yields an `active` tenant, a `member` user with the invitation's email bound to it, `accepted_at` set, the tenant's own system databases inside `runInTenant(<new tenant>)`, no `tenant_ai_budgets` row, and tenant zero unchanged.
- Integration: unknown, expired, revoked and used tokens, and an invitation whose email already has an account, each reject with the same `NotFoundError` and write nothing.
- Integration: two concurrent acceptances of one token create exactly one tenant and one user; the other rejects with `NotFoundError`.
- Integration: a short password rejects with `ValidationError` for a valid and for an unknown token alike, and nothing is written.
- Integration: when `provision` throws, the error propagates, `invitation_provisioning_failed` is logged with the tenant id only, and the tenant stays `provisioning`.
- Integration: on a freshly created database migrated with `runMigrations` alone (the `withFreshDatabase` pattern of `backend/packages/data/src/__tests__/czechHunspellSearch.test.ts:40,135`, since the shared test setup already drops the guard), `tenants_single_tenant_guard` does not exist and a second `tenants` row can be inserted.
- Integration (`invitationHandler.test.ts`): 200 `{ user }`; byte-identical 404 bodies for every unusable token; 400 for a missing field or short password; 413 for an oversized body; 429 past the per-IP limit while another IP is still served, where unusable-token 404s count toward the limit and 400 responses and successful acceptances do not; other methods → 404.
- E2e (`invitationAcceptance.e2e.test.ts`): an admin creates an invitation with `POST /api/admin/invites` (#1040; the token is the `#token=` fragment of the returned `inviteUrl`), the invitee accepts it, logs in, sees only the new tenant's own system databases in `GET /api/databases`, and gets 404 for one of the admin's item ids.
- Integration: `routeMatrix.test.ts` and `tenantIsolationRoutes.test.ts` pass with the new entry.
