## Context

Model tier rationale: The acceptance flow is pinned step by step, but its locked re-check, provisioning failure path and e2e wiring across many seams warrant a stronger worker.

Accounts are created only by an admin's invitation; `bootstrapFirstAccount` (`backend/packages/data/src/auth/authActions.ts:174-190`) stays the only way to create the very first one. #1040 lets admins create, list and revoke invitations in the global table `invites(id, email, token_hash, invited_by, created_at, expires_at, accepted_at, revoked_at)`; the raw token appears once in `<APP_BASE_URL>/?page=invite#token=<token>` and only its `hashToken` digest is stored (`backend/packages/data/src/auth/token.ts:23-25`). Recovered local code already contains invitation acceptance and migration0123 removing `tenants_single_tenant_guard`. Reconcile and verify that implementation rather than add a duplicate or claim a production strict release. Under the owner-directed continuation ADR2026-11-03-local-development-continues-with-open-production-gates, the four batch19 corrective issues are local development prerequisites. Gh-1086 is NOT signed: it remains an unsatisfied production/release prerequisite before any real deployment or second-account exposure. All functional criteria below apply only to owned local tests in this program.

Decided behaviour: acceptance is public and throttled per client IP (#1073's limiter already defines the `invitationAccept` action, 10 per hour); every unusable token (unknown, expired, revoked, used) gets the same 404; one transaction creates the tenant (`provisioning`), the user (`member`, bound to it) and consumes the invitation; then `provisionTenant(pool, tenantId)` (#1005) seeds the tenant's own system databases and makes it `active`, and only an `active` tenant authenticates (#980). The new tenant gets no `tenant_ai_budgets` row (AI refused until an admin sets caps). Its id is created server-side, never read from the request.

Follow `backend/services/semprec-api/src/setupHandler.ts:27-80` (public route, 64 KiB cap, `toPublicErrorBody`, `handleRequestSafely`) and its branch in `backend/services/semprec-api/src/app.ts:141-144`, `MIN_PASSWORD_LENGTH` (`authActions.ts:35`), the unlocked-check-then-locked-recheck of `authActions.ts:180-189`, the unique-violation check of `backend/packages/data/src/chokePoint/databasesStore.ts:10-13`, and `clientIpFromRequest` (`backend/services/semprec-api/src/clientIp.ts:15-22`). The test harness of #975 already drops the guard in the test database (`DROP INDEX IF EXISTS`, which keeps working).

## Acceptance criteria

- Integration (`acceptInvitation.test.ts`): a valid invitation yields an `active` tenant, a `member` user with the invitation's email bound to it, `accepted_at` set, the tenant's own system databases inside `runInTenant(<new tenant>)`, no `tenant_ai_budgets` row, and tenant zero unchanged.
- Integration: unknown, expired, revoked and used tokens, and an invitation whose email already has an account, each reject with the same `NotFoundError` and write nothing.
- Integration: two concurrent acceptances of one token create exactly one tenant and one user; the other rejects with `NotFoundError`.
- Integration: a short password rejects with `ValidationError` for a valid and for an unknown token alike, and nothing is written.
- Integration: when `provision` throws, the error propagates, `invitation_provisioning_failed` is logged with the tenant id only, and the tenant stays `provisioning`.
- Integration: on a freshly created database migrated with `runMigrations` alone (the `withFreshDatabase` pattern of `backend/packages/data/src/__tests__/czechHunspellSearch.test.ts:40,135`, since the shared test setup already drops the guard), `tenants_single_tenant_guard` does not exist and a second `tenants` row can be inserted.
- Integration (`invitationHandler.test.ts`): 200 `{ user }`; byte-identical 404 bodies for every unusable token; 400 for a missing field or short password; 413 for an oversized body; 429 past the per-IP limit while another IP is still served, where retained unusable-token 404s and currently in-flight reservations count toward admission; reservations are released for 400/413, successful acceptances and unexpected infrastructure failures, so these completed outcomes do not remain counted; other methods → 404.
- E2e (`invitationAcceptance.e2e.test.ts`): an admin creates an invitation with `POST /api/admin/invites` (#1040; the token is the `#token=` fragment of the returned `inviteUrl`), the invitee accepts it, logs in, sees only the new tenant's own system databases in `GET /api/databases`, and gets 404 for one of the admin's item ids.
- Integration: a deterministic held-request/body handler control proves a concurrent same-address burst reserves at most the configured budget before any completed 404, the next same-address request is refused before its body is read, a different address is served, and admitted outcomes release or retain reservations according to Task 4. All owned requests/server resources settle.
- Integration: `routeMatrix.test.ts` and `tenantIsolationRoutes.test.ts` pass with the new entry.
