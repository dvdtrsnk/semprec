### Requirement gh-1594: [library 05/11] Add items.created_at and sort by system timestamps

#### Context

Model tier rationale: It adds a column to the partitioned `items` table with a backfill over existing tenant data and changes the sort specification and keyset cursor shared by every collection query, a wide persisted-data and query contract.

The library list's default order is "most recently added first". The `items` table has `updated_at` (used as the optimistic-concurrency version `ifVersion`) and `deleted_at` but no creation time (`backend/packages/data/src/db/migrations/0001_core_schema.sql`). A sort by `updated_at` would reorder items whenever they are edited, and a sort spec can only name property keys: `lookupSortProperty` in `backend/packages/data/src/views/sortCompiler.ts` resolves `sort.property` against the database's properties, and a user-created collection may legitimately have its own property called `createdAt`, so a system field must not share the namespace of property keys.

Decision: creation time is stored in a general `items.created_at timestamptz NOT NULL DEFAULT now()` column, not as a per-database property.
Decision: existing rows get their creation time approximated by their last change time (`updated_at`), because the true time is unknown; rows of the same age therefore sort by last edit.

Plan:
- Migration adds the column. Adding it to the partitioned parent is a metadata-only change; existing rows read as the time of the `ALTER`. Partitions created later are created `LIKE items`, so they carry the column.
- A per-tenant data cutover backfills in batches: `UPDATE items SET created_at = updated_at WHERE created_at > updated_at` is both the filter and the idempotency check (a row written after the `ALTER` has `created_at <= updated_at`, an old row not yet backfilled has `created_at > updated_at`). It must never change `updated_at`.
- The item envelope gets an additive `createdAt`.
- `SortSpec` accepts either `{ property, direction }` or `{ system: "createdAt" | "updatedAt", direction }`, validated with zod; the keyset cursor encodes and compares the system column; all keys keep `NULLS LAST` and an `id ASC` tie-break.

#1524 (Czech collation and title tie-break) is the preceding change to `sortCompiler.ts`; this issue builds on it. The Tasks data migration #1657 rewrites `updated_at`, so its backfill ordering relative to this one matters: this backfill must run before it, which is why #1657 waits for this issue.

### Requirement gh-1597: [collection-query 10/12] Declare area filters per database in module manifests

#### Context

Model tier rationale: It composes already-built filter conditions into per-database filter trees and publishes them through an existing schema endpoint, so the mechanism is known, but the trees differ per database and must be checked against real seed data.

"Show everything in the Health area" must give the same answer in every collection, and the answer differs by database. A task has no area of its own; it counts only through its project. A file, a health record or an event may have a project, in which case the project's area counts, or no project, in which case its own area counts. Journal entries and companies only have their own area. If each client assembles these trees itself, the rules drift between clients. This issue puts the rule next to the data, in the module manifest, and publishes it in the schema so a client only substitutes an area id.

What it builds on: the two-hop condition #1363, the emptiness conditions #1526, the Events to Areas relation #1538, and the schema projection of relation properties #1360. It is a dependency of facets (#1759) and related collections (#1839).

Existing code: the manifest of the ten system databases is `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` (`databases: [{ key, name }, ...]`, validated against the `ModuleManifest` type in `backend/packages/module-registry/src/manifest.ts`). ### Requirement gh-1598: [calendar-events 05/12] Normalize Events times and derive Events.time before the write

#### Context

Model tier rationale: One known mechanism (a per-module pre-write transform) reusing the existing Tasks time derivation pattern and a shared helper, with deterministic inputs and outputs, but it touches the write path of every Events create and update.

#1416 adds `endDate`, `timeFrom`, `timeTo` and the system-owned `time` to Events. Today nothing derives or normalizes them. Tasks already do: `deriveTaskTime` (`backend/packages/data/src/tasks/deriveTaskTime.ts`) is called inline from `backend/packages/data/src/chokePoint/itemWrites.ts` before the row is written (decision record `docs/adr/2026-09-19-derived-system-properties-computed-inline-at-choke-point.md`). Item hooks in `chokePoint/hooks.ts` run only after the write and return void, so they can reject but cannot change a value; this is why the transform must run in the pre-write step that #1422 adds to the choke point, which receives the stored state and the patch. #1536 introduces `normalizeWallClockTime(value, { allow2400 })` in `backend/packages/data/src/timezone.ts` for the Tasks time fields; this issue reuses it (if the helper's ownership or options differ in the merged version, align this issue to the merged helper rather than duplicating it).

Events created from a transcript today carry `date` as a UTC instant (`transcription/transcriptEventMatch.ts`, confirmed through `createItemWithClient` in `inbox/proposalActions.ts`), and older clients may still send such a value. Those must keep working.

Decisions:
- A timed Event with a start and no end gets an end one hour later, clipped to `"24:00"`. Reason: the assistant and imports create such Events, and rejecting them would break those callers.
- The transform works on the wall-clock in the tenant time zone (`getSystemTimezone` in `backend/packages/data/src/systemSettings.ts`, default Europe/Prague).

This issue changes values only. Rejecting invalid combinations is #1663.

### Requirement gh-1601: [choke-point-hooks 04/04] Add item delete and restore hooks to the choke point

#### Context

Model tier rationale: One known mechanism (two hook registries called from the existing trash cascade in the same transaction) with an existing trash test fixture, but the per-row epoch semantics of restore and the all-or-nothing rollback need care.

Moving an item to the trash and restoring it are implemented in `backend/packages/data/src/chokePoint/itemTrash.ts`. `itemDeleteWithClient` collects the item's subtree (`collectItemSubtree`: the item, the inline databases it owns, their rows, recursively), soft-deletes every row with one shared `deletedAt` (Postgres `now()` is fixed inside the transaction), and `restoreItemWithClient` restores only the subtree rows whose `deletedAt` equals the root's (the "cascade epoch"), so rows trashed earlier or later on their own stay trashed. Neither function runs any hook: the dependency-cruiser rule `chokepoint-knows-no-domain` (`backend/dependency-cruiser.rules.json`) exempts `itemTrash.ts` with the comment that "no domain needs a delete hook today". Domains now do: calendar deletion with events, journal day restore, recording and transcription cleanup, search reindexing, last-contact derivation, invitations, mailbox removal, recurring-series trash and value-link detaching all need to run inside the same transaction as the trash or restore and be able to veto it.

This issue adds an item delete hook and an item restore hook to the registry in `chokePoint/hooks.ts`, the same way ADR `2026-10-09-item-create-domain-hooks` added the create hook. It builds on #1530 (the three hook issues share `hooks.ts` and `domainWriteHooks.ts`, so they land in order) and on #1415 for the `writerKind` it passes. Decisions:
- The delete hook runs for every row of the cascade that was actually soft-deleted in this call (not for rows already in the trash), root first, after that row's soft delete.
