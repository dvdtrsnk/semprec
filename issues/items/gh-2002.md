## Context

Model tier rationale: One new persisted column with its patch path, a manifest flag and an envelope field, following the icon and color pattern of #1528 across the migration, store, shared schemas, application service and REST seams with existing fixtures; it is a persisted-data contract, so not low.

Recipes is a system module (#1707). The product owner decided that the user cannot delete it, only hide it from the overview. Deleting is already impossible: `DELETE /api/databases/:id` refuses a system database (`ForbiddenError` in `backend/packages/data/src/chokePoint/databasesStore.ts`), so a system database never reaches the trash. Hiding has no mechanism yet: the overview position of a system database comes only from its module manifest (`overviewOrder`, declared through #1407 and resolved by `backend/packages/data/src/manifest/collectionMetadata.ts`), and `database.patch` accepts only `name`, `icon` and `color` after #1528, with icon and color forbidden on system databases.

This issue adds a stored "hidden from the overview" flag that the user can switch on and off for a system database whose module declares it hideable, and declares Recipes hideable. Hiding changes nothing else: the collection keeps its items, views, switcher position and searchability, and it can be shown again at any time.

Decisions:
- The flag is stored per database row (`databases.overview_hidden`), defaulting to false, so existing rows need no backfill.
- Only a database whose module descriptor declares `overviewHideable: true` accepts the flag; in this issue that is the `recipes` database only. Any other database rejects it with a forbidden error, so built-in collections such as Projects cannot be hidden by accident.
- Hiding affects only the overview; `switcherOrder`, `clientVisible`, queries and search are unchanged.

## Scope

### In scope

- The stored `overviewHidden` flag, the `overviewHideable` descriptor field, the patch that sets and clears it, and the envelope field.

### Out of scope

- Deleting or archiving the Recipes database: refused like for every system database; not changed here.
- Hiding any other system collection: only Recipes is declared hideable.
- Hiding from the collection switcher, from search or from agents: not changed.
- The Recipes module itself: #1707.

## Acceptance criteria

- When `GET /api/databases` is called for a fresh tenant, then every database has `overviewHidden: false`.
- When `PATCH /api/databases/:id` sets `{ "overviewHidden": true }` on the `recipes` database, then its envelope has `overviewHidden: true`, its `overviewOrder` and `switcherOrder` are unchanged, its items are still returned by `database.query`, and a schema invalidation is published.
- When the same patch sets `{ "overviewHidden": false }`, then the envelope shows `overviewHidden: false` again.
- When `overviewHidden` is patched on a database whose descriptor does not declare `overviewHideable` (for example Projects or a user-created collection), then the response is 403 and nothing changes.
- When `overviewHidden` is not a boolean, then the response is 400.
- When `DELETE /api/databases/:id` is called for the `recipes` database, then it is still refused and the database stays live.
