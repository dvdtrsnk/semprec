## Context

Model tier rationale: An additive seed property plus one new optional manifest descriptor field validated by the
module registry and published by the schema endpoint; it follows the existing `quickFilters`/`pickerFilter` pattern,
but crosses the registry, seed and API packages.

Areas are being removed (see the parent epic) and projects get tags instead. The projects collection on mobile will
show a bar of tag chips; which property feeds that bar is declared by the server so the schema-driven collection
engine stays free of per-database code.

Precedent: Health records `tags` (`backend/packages/data/src/seed/seedTenDatabases.ts`, `type: "multi_select"`,
`owner: "user"`). Options are stored in `properties.config.options`; `POST /api/properties/:id/options` appends one
on a schema-locked database; `assertSelectValuesKnown` rejects unknown values; the `in` filter on a `multi_select`
means overlap (`views/filterCompiler.ts`); `/api/databases/:id/facets` counts `multi_select` values.

## Task

1. Seed a `tags` property on Projects: `type: "multi_select"`, `owner: "user"`, no shipped options, with en/cs
   catalog names (`property.projects.tags.name`: "Tags" / "Štítky").
2. Add `tags` to the Projects `searchFields` and as a field of the `project` editor schema.
3. Add an optional `facetBarProperty` (a property key) to the module manifest database descriptor in
   `@semprec/module-registry`, validated by its Zod schema and projected by the registry like `quickFilters`.
4. Declare `facetBarProperty: "tags"` on the Projects descriptor and publish it per database in `GET /api/schema`
   (absent when a database declares none). The schema handler refuses to publish a key that is not a `select` or
   `multi_select` property of that database.

## Scope

### In scope

- The `tags` property, its catalog names, search and editor field, and the `facetBarProperty` declaration.

### Out of scope

- Any mobile change (sibling 02/04).
- Removing areas (siblings 03/04 and 04/04).
- Renaming, recoloring or deleting tags beyond the existing option operations.

## Acceptance criteria

- A new tenant's Projects database has a `tags` `multi_select` property owned by the user with no options.
- `POST /api/properties/:id/options` on Projects `tags` adds a tag; setting it on a project succeeds and an unknown
  tag key is refused with 400.
- `POST /api/databases/:id/query` with `{type: "in", property: "tags", value: [a, b]}` returns exactly the projects
  having tag a or b.
- `POST /api/databases/:id/facets` for `tags` returns each tag with its project count.
- A project is found by search through a tag label.
- `GET /api/schema` returns `facetBarProperty: "tags"` for Projects and no `facetBarProperty` for other databases.
- A manifest whose `facetBarProperty` is not a string key is refused by the registry; a declared key that is not a
  `select`/`multi_select` property is refused when the schema is published.
- Tenant isolation: another tenant's tag options and projects are never returned by query, facets or schema.
