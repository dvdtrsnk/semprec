**Blocked by:** #1828, #1831, #1782
**Model tier:** high

## Context

Model tier rationale: Computes a per-user badge from preferences and several counts, attaches it to every visible push, and adds a debounced job that pushes badge-only updates on count changes, touching the shared push path and background queue with races between count changes and sends.

The app icon badge must show the sum of the counts the user switched on, and update when a count changes without the user opening the app. The ingredients exist after the blockers: the per-user switches (`badgeApprovals`, `badgeInvites`, `badgeInbox`) in the preferences table (#1441); the counts from `GET /api/badge-counts` (#1828); and the APNs request carrying collapse and thread ids (#1829, approvals with time-sensitive category in #1831). Today APNs payloads carry no `aps.badge` (`backend/packages/data/src/push/apnsAdapter.ts`).

Decisions: every visible APNs push carries `aps.badge` = the sum of the enabled counts at send time (0 when none, which clears the badge); when a count changes, a push of the alert type that carries only `aps.badge` (no alert text, no sound, `apns-priority` 5, `apns-collapse-id` `badge`) is sent, so it does not wake the app; updates are debounced per user (the queue job key `badge-refresh:<userId>` with `replace` and a few seconds delay); Web Push is not affected. Count changes that trigger a refresh in this issue are: an approval request created or decided, and a change of the user's badge switches. Invitation and Inbox changes call the same enqueue helper from their own issues (#1954).

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. Add `computeBadgeForUser(client, userId)` in `notifications/badgeCount.ts`: reads preferences and the three counts and returns the sum of the enabled ones.
2. In `handleNotificationFanoutTask`, compute the badge once per job and pass it in `NotificationPushPayload.badge`; `sendApnsNotification` sends it as `aps.badge`.
3. Add `sendApnsBadgeUpdate(target, badge)` in `push/apnsAdapter.ts` with the headers above and a payload of `{ aps: { badge } }` only.
4. Add a core task `pushBadgeRefresh` (`CORE_TASK_NAMES`, handler in `worker.ts`) and `enqueueBadgeRefresh(client, userId)` using the job key and a delay of 5 seconds; the handler computes the badge and sends it to the user's APNs registrations (permanent failures revoke the registration, transient failures retry).
5. Call `enqueueBadgeRefresh` when an approval request is created or decided and when `PATCH /api/notification-preferences` changes a `badge*` field.
6. Add tests: a visible push carries the computed badge; with approvals 3 and Inbox off the badge is 3, and with 0 the badge is 0; several changes in a few seconds produce one badge-only push; the badge-only push has no alert; a switch change sends a refreshed badge; another user's counts are never included.

## Scope

### In scope

- The badge value on visible pushes and the debounced badge-only refresh job for approval changes and switch changes.

### Out of scope

- The count route: #1828; preferences storage: #1441.
- Refresh triggers for invitations and Inbox items: #1954 and the Inbox issues.
- Realtime invalidation of preferences and counts to other devices: #1918.

## Acceptance criteria

- When approvals count 3 and the Inbox switch is off, then a visible push carries `aps.badge` 3; when no count is enabled or all are 0, then it carries 0.
- When an approval request is created or decided, then a badge-only push is sent to the user's iOS devices after the debounce, and several changes within the debounce window send one push.
- When the user changes a badge switch, then the badge is refreshed.
- A badge-only push contains no alert or sound.
