## Context

Model tier rationale: A lock-order decision on a path that races a destructive removal, in a root that decides which mail accounts a process hosts. The change is small, but a wrong lock mode would either let a removed mailbox get its sync state row back or make discovery wait behind a removal and drop hosted accounts, so the schedule has to be proven with real concurrent transactions.

The live-sync root (`mail/mailLiveSyncRoot.ts`, `createMailLiveSyncRoot`) discovers the accounts to host in `discoverActiveAccounts`. Per active tenant it reads the live Mailboxes items in pages with `listItems`, and in the same page transaction, per item under its own `SAVEPOINT discover_account`, calls `ensureMailAccountSyncState` (`mail/mailAccountSyncStateStore.ts`), which inserts the `mail_account_sync_state` row with `INSERT ... ON CONFLICT (item_id) DO NOTHING` when the account has none. Every account that returns a row is hosted.

`removeMailbox` (`mail/mailboxRemoval.ts`, #1690) takes the mailbox sync guard, locks the account sync state row and then the Mailboxes item `FOR UPDATE`, trashes the item and deletes the credential, the sync state row, the folder sync state rows and the server settings row, in one transaction. A sync pass takes the same guard and re-reads the mailbox under it (`enterSyncPass` in `mail/mailSyncJob.ts`), so a pass cannot create the deleted rows again. Discovery takes no guard and no row lock. The handover of #1690 recorded the race this leaves (`issues/handovers/gh-1690.md`, "Follow-ups", verified against the code at the integration tip): discovery's `listItems` statement reads the Mailboxes item as live, the removal then commits (item in the Trash, sync state row deleted), and discovery's `ensureMailAccountSyncState` inserts a row for the removed mailbox, because the row is absent and the conflict check finds nothing. The removed mailbox then has a `mail_account_sync_state` row again, the root hosts a lifecycle for it until the next pass retires it, and a mailbox that is restored later finds a row it did not have to be given. No issue covers it (gh-2030 does not).

The removal ADR (`docs/adr/2026-11-10-mailbox-removal-is-one-transaction-that-also-writes-sync-status.md`) records the guard as the lock that keeps a removal and a sync pass apart, and the row-lock order guard, sync state row, item row. This source does not touch that order. It decides how discovery takes part, and it must not wait: the root drops an account whose seeding failed from the active set of the pass (`onLifecycleError(..., "discover", ...)` and no entry in `found`), and the pool's `statement_timeout` is 60 s, so a discovery that waited behind a removal that waits behind a long sync pass would stall the tenant and retire hosted accounts.

Decision: discovery seeds a sync state row only for an account that has none, and only while it holds a non-waiting share lock on the account's live Mailboxes item row. `SELECT ... FOR SHARE SKIP LOCKED` on the live row conflicts with the removal's `FOR UPDATE`, never waits, and under READ COMMITTED a row that was trashed before the statement is not returned. An account whose item is trashed, gone or row-locked by another transaction is left out of this pass; it is not an error and nothing is logged. An account that already has a row is returned as it is, with no lock, as today.

## Task

Load `state-writes`, `error-handling`, `testing` and `adr-conventions`.

1. In `mail/mailAccountSyncStateStore.ts` add `ensureMailAccountSyncStateOfLiveMailbox(client, { itemId, mailboxesDatabaseId, syncMode })`, returning `MailAccountSyncStateRow | null`:
   - first `getMailAccountSyncState(client, itemId)`; a row is returned as it is, with no lock and no write;
   - otherwise one statement `SELECT id FROM items WHERE database_id = $1 AND id = $2 AND deleted_at IS NULL FOR SHARE SKIP LOCKED`; no row means the item is trashed, gone or locked by another transaction, and the function returns `null` having written nothing;
   - otherwise `ensureMailAccountSyncState(client, { itemId, syncMode })` (unchanged) and its row. The share lock is held until the caller's transaction ends.
   Document the contract in its docstring: it never waits for a lock, and why (discovery must not wait behind a removal).
2. In `mail/mailLiveSyncRoot.ts`, `discoverActiveAccounts` calls it instead of `ensureMailAccountSyncState`, passing the `mailboxesDatabaseId` the page transaction already resolved. A `null` result leaves the account out of `found` for this pass without calling `onLifecycleError`; the `SAVEPOINT` handling stays as it is. Update the comments that say discovery seeds the state with `ensureMailAccountSyncState`.
3. Add `docs/adr/<date>-live-sync-discovery-seeds-a-sync-state-only-under-a-non-waiting-share-lock-on-the-live-mailbox.md` (the date is the day it is written; `area: [backend]`, `supersedes: []`, standalone). Its Context references `[[2026-11-10-mailbox-removal-is-one-transaction-that-also-writes-sync-status]]` and says it decides the race that record left open without editing it. The Decision states: discovery takes no guard; it seeds a row only for an account without one, under `FOR SHARE SKIP LOCKED` on the live item row; why it cannot wait (the pass drops an account whose seeding failed and the 60 s statement timeout); the outcomes (a removal that committed first leaves nothing to seed, a removal that runs after the share lock waits for the end of the discovery page transaction, finds the row discovery inserted and deletes it, since its row delete is a later statement under READ COMMITTED; a removal in flight is skipped, and the account is seen again by the next pass). Its Consequences state the lock order: discovery takes only the item share lock and a new row of a table it holds no lock of, never waits, so it cannot be part of a cycle with the guard, the state row and the item row of the removal; an account that has no row and is skipped is not hosted, which delays a never-connected account by one discovery interval; the share locks of a page's items are held until the page transaction commits, so a removal of one of them waits for that transaction at its item lock, after it took the guard and the state row lock.
4. Tests, in `__tests__/mailLiveSyncRoot.test.ts` (runtime-role pool, the existing harness and its pool wrapper that intercepts `SAVEPOINT discover_account`) and a new `__tests__/mailAccountSyncStateLiveMailbox.test.ts` for the store function:
   - the store function: an account with a row returns it and takes no lock; a live account without a row gets its row with the given `syncMode` and the item stays share-locked by the transaction (an `UPDATE`/`FOR UPDATE NOWAIT` on another connection fails while it is open); a trashed item returns `null` and inserts nothing; an item that another transaction holds `FOR UPDATE` returns `null` at once (the call ends while the other transaction is still open, observed through the result, not through a timeout) and inserts nothing; another tenant's item returns `null` under row-level security;
   - the race: a discovery pass whose page transaction has listed a live mailbox without a sync state row, and a `removeMailbox` of that mailbox that commits on a second pool before the pass seeds it (the wrapper holds the pass at `SAVEPOINT discover_account` until the removal resolves): afterwards the mailbox has no `mail_account_sync_state` row, no lifecycle is hosted for it, `onLifecycleError` was not called and the other accounts of the page are hosted;
   - the removal after the share lock: the removal started while discovery holds the share lock waits (observed with `pg_blocking_pids`), and when the discovery transaction commits it deletes the row discovery inserted, so the mailbox ends removed with no row;
   - the existing tests of the root (seeding on first discovery, the savepoint isolation of a failing account, per-tenant discovery) pass unchanged.

## Scope

### In scope

- Keeping discovery from inserting a sync state row for a mailbox whose removal committed, without making discovery wait.

### Out of scope

- The sync guard, the lock order of the removal, and the sync pass's re-read (`enterSyncPass`): unchanged.
- The removal waiting longer than the statement timeout for a sync pass: a separate source.
- Hosting or stopping lifecycles for removed mailboxes beyond what discovery's active set already does (#2030), and the restore of a removed mailbox (#2032).
- `ensureMailAccountSyncState` itself and its other callers (the connect flows, the reconcile jobs and the restore hook seed rows inside transactions that already own the mailbox).
- Any change to the pool's `statement_timeout`.

## Acceptance criteria

- When a mailbox is removed between discovery's read of its item and its seeding, then no `mail_account_sync_state` row exists for it afterwards and the root hosts no lifecycle for it.
- When a live mailbox has no sync state row, then discovery gives it one with the provider's default sync mode, and hosts it.
- When another transaction holds the mailbox item's row lock, then discovery does not wait: the account is left out of that pass and is picked up by a later one.
- When a removal starts after discovery took its share lock, then the removal completes after the discovery transaction commits and leaves the mailbox without a sync state row.
- When a discovery pass fails to seed one account, then the other accounts of the page are still hosted, as before.
