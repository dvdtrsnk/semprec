## Context

Model tier rationale: One mechanism (adding the inverse side of an existing relation to a `schema_locked` database in the seed and through a direct-SQL cutover) following an established pattern, but it changes the persisted relation definition of a tenant-owned database.

An Event's participants are the `people` relation of the Events database (`backend/packages/data/src/seed/seedTenDatabases.ts`: many-to-many from Events to People, declared one-directionally, so People has no property that lists the Events a person attends). A person's page cannot show their meetings, and later participant work needs an edge that can be read from both ends. The inverse is fixed when a relation is created: the inverse and the cardinality are set only at creation (`backend/packages/data/src/chokePoint/relationPropertyOps.ts`), so existing tenants cannot be fixed by editing the property through the API. People is `schema_locked`, so they need a code-level cutover with direct SQL that adds the new People property and points the existing relation definition at it (`relation_definitions.property_id_b`). The pattern is `transcription/transcriptsCatalogCutoverMigration.ts`, which adds the `speakers` relation to People for existing tenants, run per tenant by `runTenantCutoverMigrations` in `backend/packages/data/src/db/tenantCutoverMigrations.ts`.

This issue is the single owner of that inverse. The work that stores a participant's role and invitation state on the edge (#1757) and the work that adds birthday properties to People (#1795) build on it. It must run after the calendars seed (#1600) in the Events and People seed order.

Decision: the inverse property is `events` on People, named "Events" in the i18n catalogs, owned by the user like `People.projects` and `People.companies`.

Shared-file ordering: this issue also waits for #1660 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `canonical-keys` and `testing`.

1. In `seedTenDatabases.ts`, declare `Events.people` with the inverse `{ key: "events" }` on People, following the existing `relate` usage for the other People inverses (for example `Companies.meetings` to `Events.company`), so a fresh tenant gets `People.events`.
2. Add a cutover (for example `backend/packages/data/src/calendar/peopleEventsInverseCutoverMigration.ts`) that for each existing tenant: adds the People `events` property, sets `relation_definitions.property_id_b` of the existing `Events.people` definition to it, leaves all existing edges untouched, is idempotent, and no-ops when Events or People is missing. Register it in `runTenantCutoverMigrations`. The resulting definitions must equal the fresh seed.
3. Add `property.people.events.name` (Czech "Události", English "Events") to `backend/packages/data/src/seed/i18n/cs.json` and `en.json`.
4. Tests: a fresh tenant has `People.events` and reading a person's events returns the Events that list them; the cutover on a previous-seed tenant gives existing `Events.people` edges a readable inverse; a second run changes nothing.

- When the cutover runs on an existing tenant, then existing participant edges are preserved and a second run changes nothing; a tenant without an Events database is skipped without failing.
