## Context

Model tier rationale: Applies a new rule engine (visibility conditions and required-ness) to the confirm path and to the edit route and extends the REST item response contract with warnings, so a mistake either blocks valid confirms or lets incomplete cards through.

The Inbox card marks required fields that have no value (red label, the "Process" button disabled) and hides fields whose condition is false. Today neither the schema nor the choke point knows required-ness, and `confirmProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) checks only status, envelope shape and target. #1825 puts a localized `editorSchema` with `required` flags and `when` conditions on every card; #1892 added `PATCH /api/proposals/:id/values`, which today accepts only property keys and counts every edited key.

This issue makes the server apply the schema's rules, with one evaluation shared by confirm and edit.

Decision: the values a condition is evaluated against are the card's effective values: the envelope properties overlaid with the pseudo field values the user set (stored in `userOverrides` under the pseudo key, never written to the created item). A field is hidden when its `when` is false; a hidden field is neither required nor validated. A value counts as empty when it is `undefined`, `null`, an empty or whitespace-only string, or an empty array.

Decision: `confirm` returns a `ValidationError` with `details.field` (and `details.ref` for a multi-step card) for the first visible required field without value. `PATCH values` never fails for a missing required field; it returns the missing ones as `warnings` so a half-filled card can be saved. A selected option that is disabled (archived project) blocks like a missing value but is handled by the target-state rules, not here.

## Task

Load `error-handling`, `io-hardening` and `testing`.

1. In `backend/packages/data/src/inbox/editorSchema.ts` (from #1825) add pure functions `isFieldVisible(field, values)`, `findMissingRequired(schema, values)` returning `{ ref?, field }[]` in schema order, and `visibleKeys(schema, values)`.
2. In `confirmProposalWithClient`, resolve the card's base kind and unlocalized schema (`getEditorSchemas()`), build the effective values and throw `ValidationError("Required field '<key>' has no value", { field, ref? })` before any destination write when something is missing. A card whose base kind has no schema is unchanged.
3. In `updateProposalValuesWithClient` (`proposalActions.ts`): accept the pseudo field keys of the card's schema in `set` (stored in `userOverrides`, excluded from the envelope that is validated against the target database, never written to the created item); compute `warnings` with `findMissingRequired`; and exclude keys of hidden fields from `userEditedKeys` so the server and client show the same count (an edited follow-up date hidden by switching the follow-up task off is not counted).
4. Return the warnings: extend the `{ status, item }` result of a custom route with an optional `warnings` array and have `sendItemResponse` (`backend/services/semprec-api/src/adapter/http.ts` / `adapterRoute.ts`) add it to the item envelope as a top-level `warnings` field when present (additive REST contract); `createUpdateProposalValuesRouteHandler` returns `warnings: [{ ref?, field, code: "required" }]`.
5. Tests: confirm of a task without a name fails with `field: "name"`; confirm of a file card with the follow-up task switched off and no `followDate` succeeds; `PATCH values` that clears the name saves and returns a `required` warning; a hidden edited key is excluded from `userEditedKeys`; pseudo key `allDay` is accepted, stored in `userOverrides`, and absent from the created item.

## Scope

### In scope

- Evaluating `when` and `required` on confirm and on edit, pseudo field values in `PATCH values`, hidden keys excluded from the edited count, and `warnings` in the edit response.

### Out of scope

- Emptying hidden fields in what confirm writes (#1934).
- Blocking a selected archived or deleted target (#1482, #1916).
- Relation and step-toggle edits (#1920).
- Validating select values against option catalogs.

## Acceptance criteria

- When a task card without `name` is confirmed, then the response is 400 with `details.field` equal to `name` and no item is created.
- When the follow-up task switch is off and no `followDate` is set, then confirm does not require the date.
- When `PATCH values` empties a required field, then the card is saved and the response carries a `warnings` entry for that field.
- When `followDate` was edited and the follow-up task is then switched off, then `userEditedKeys` has no `followDate` entry.
- When a pseudo field such as `allDay` is set, then it appears in `userOverrides` and never as a property of the created item.
- A card with no declared editor schema confirms exactly as before.
