### Requirement gh-1682: [semp-turns 04/12] Validate and store message refs

#### Context

Model tier rationale: One validation-and-store mechanism on an existing endpoint, but it is a tenant-isolation check on user-supplied ids, so both the foreign-tenant and the mismatched-pair cases need explicit tests.

#1369 defines the message ref schema. #1620 adds the HTTP endpoint that accepts a chat message for a Semp thread and stores it in the thread's messages table, whose `context` column is meant to carry the attached refs. This issue makes that endpoint validate the refs it receives and store the cleaned list there.

Without it, a client could attach a reference to an object of another tenant, to a deleted-for-good object or to an item filed under the wrong database, and later expansion of the ref (#1733) would fail or leak. Row level security already hides foreign rows, so existence checks run inside the request's tenant scope and a foreign id simply does not exist.

Decisions:
- The limit of 20 refs applies to the submitted array before duplicates are merged. 21 submitted refs are rejected even if some are duplicates.
- A trashed item is a valid ref (the user can still restore it); only a purged or foreign one is rejected.
- For a `block` ref, the item must exist and the block id must exist in the item's document. For a `transcriptSegment` ref, the item must be a Transcripts item; the range is not matched against segments.
- For an `agentRun` ref only the run's existence is checked here. The optional `messageId` is checked by #1936.

What builds on this: #1684, #1733, #1948, #1834, #1771, #1853 and #1849.

#### Task

Load `io-hardening`, `error-handling`, `canonical-keys` and `testing`.

1. In the message endpoint from #1620, parse the request's `context` array with the schema from #1369. More than 20 entries, or an entry that does not parse, is rejected with a `ValidationError` (HTTP 400) whose `field` is `context[i]` for the offending index (`context` for the length error). Nothing is stored on rejection.
2. Add a store function that checks existence of each ref inside the caller's tenant transaction, batching by kind:
   - `item`: the `(itemId, databaseId)` pair matches an `items` row; a mismatching database is rejected like a missing item.
   - `block`: the item exists and its document contains the block id (read via `backend/packages/data/src/docs/blocks.ts`).
   - `transcriptSegment`: the item exists in the Transcripts database.
   - `mailAttachment`: a `mail_attachments` row with that id exists.
   - `agentRun`: the `agent_runs` row exists. `approvalRequest`: the approval request exists.
3. Merge duplicates by `messageRefKey` (keep the first, preserve order) and store the cleaned list in the message's `context`.
4. Tests (integration, real tenants via the tenant harness): a ref to another tenant's item gives 400 `context[i]` and stores nothing; an `(itemId, databaseId)` pair that does not match gives 400; the same ref twice is stored once; 21 refs give 400; each kind has an accepted and a rejected case; a trashed item is accepted.

#### Touches

- The Semp message endpoint and its store introduced by #1620 (context handling only)
- backend/packages/data/src/semp/ (new ref-existence checker; folder name follows the layout #1620 creates)
- backend/packages/data/src/index.ts (new export line)
- backend/packages/data/src/__tests__/ (new integration test file for ref validation)

#### Scope

##### In scope

- Parsing, limit, existence checks, duplicate merge and storing `context`.

##### Out of scope

- The schema itself: #1369.
- Resolving labels and trash state when history is read: #1684.
- Expanding refs into the agent turn: #1733.
- Checking `messageId` of an agent run ref: #1936.
- Ref kinds added by #1933, #1771 and #1853, which add their own existence check.

#### Acceptance criteria

- When a message carries a ref to an item of another tenant, then the response is 400 naming `context[i]` and no message row is written.
- When the `(itemId, databaseId)` pair does not match the item, then the response is 400 naming `context[i]`.
- When the same object is attached twice, then the stored `context` holds it once.
- When 21 refs are submitted, then the response is 400.
- When a ref points at a soft-deleted item, then the message is accepted.

### Requirement gh-1684: [semp-turns 05/12] Resolve ref labels and trash state in thread history

Model tier rationale: A batched read-side resolver over existing tables with a small response contract, covered by fixtures; no write path or new isolation rule.

#1543 serves a Semp thread's message history, and #1682 stores validated refs in each message's `context`. A stored ref carries only ids. The client needs, for each ref, a current display name and whether the object still exists, so a chip such as "Call the plumber" can be drawn after the object was renamed, moved or deleted.

Today deletion of an item is soft: `items.deleted_at` is set, `item.restore` brings it back, and `backend/packages/data/src/trash/purgeExpiredTrash.ts` removes it for good after 30 days. An item's name is its `name` property (the `title`-typed property of its database). An e-mail attachment is a `mail_attachments` row with a `filename`.

This issue adds the resolved view of each ref to the history response. #1888 builds on it for changed-item cards.

Decision: refs survive renames and moves because they store ids only; the label is always resolved at read time, never stored.

### Requirement gh-1733: [semp-turns 06/12] Expand refs into the agent turn context

#### Context

Model tier rationale: This reads many kinds of tenant data into a model prompt under size limits, and must keep that content out of persisted events and logs, so a mistake leaks user data or bloats every stored run.

#1682 stores validated refs on a Semp message. #1727 runs queued Semp thread turns in `semprec-agents`. Today there is no resolver: `SempConversation.send` (`backend/packages/agent-runtime/src/sempConversation.ts`) takes only a string and the turn goes into `agent_runs.task`. A turn that carries refs must give the model the referenced objects and their surroundings, so it can answer and edit them.

This issue adds the resolver that runs in `semprec-agents` before the prompt and renders each ref into a structured context block of that turn. It is the base for file text (#1740), images (#1752), and the ref kinds that other issues add: #1771, #1853, #1948 and #1849.

Decisions:
- The expanded block is built per turn and is not persisted. The user message stored for replay (#1566) keeps only the refs in their stored shape, with labels. After a thread wakes from idle, the agent reloads content with its read tools, which are added by #1623 and the domain read tool issues.
- Limits: at most 8000 characters per ref and 32000 per turn (decided by the product owner; keep them as named constants). A truncated ref is marked in the block with an explicit truncation notice.
- A trashed item is expanded with a `trashed` marker, not dropped. A purged one is rendered as "no longer exists".
- Ref contents are never written to logs (only counts and kinds).

#### Task

Load `io-hardening`, `error-handling` and `testing`.

1. Add a ref expander module in `backend/services/semprec-agents/src/` that takes the turn's refs and a tenant-scoped client and returns one text block, one section per ref, in order:
   - `item`: the item's properties plus the names of relation targets (project, company, people).
   - `block`: the block, its sibling blocks and the parent page (via `sys:children`).
   - `transcriptSegment`: the segment and up to three segments either side, with speaker names; a Transcripts `item` ref: summary, speakers and segments up to the limit.
   - Inbox item: the capture plus its proposal card; a proposal card: envelope, history and source.
   - `agentRun`: task, status and steps.
   - `approvalRequest`: its summary and status.
   - `mailAttachment`: its filename, content type and size (text and images are added by #1740 and #1752).
   - An `item` ref to an e-mail: the thread's newest messages up to the limit; if the mail thread read tool of #1927 is available, reuse its reader, otherwise read the thread's message items directly.
2. Apply the per-ref and per-turn caps with a visible truncation marker.
3. Call the expander when a thread turn starts and prepend its block to the user content sent to the model; do not write it into `agent_runs.task` or any `agent_run_events` row.
4. Expansion runs under the turn's tenant scope; an expansion failure for one ref renders that ref as unavailable and does not fail the turn.
5. Tests: each ref kind expands; a block shows its neighbours; an over-limit ref is cut and marked; `agent_runs.task` and the events table contain no expanded text; a trashed item is marked; a ref of another tenant yields nothing.

- backend/packages/agent-runtime/src/sempConversation.ts (turn input carries the refs)
- backend/services/semprec-agents/src/__tests__/refExpansion.unit.test.ts (new)

#### Scope

##### In scope

##### Out of scope

- Image attachments: #1752.

#### Acceptance criteria

- When a turn carries a ref to an e-mail item, then the model sees the thread's messages; with a block ref, the sibling blocks too.
- When a ref's content exceeds 8000 characters, then it is cut and marked as truncated; the whole block never exceeds 32000 characters.

### Requirement gh-1752: [semp-turns 09/12] Pass image attachments into the agent turn

#### Context

Model tier rationale: It crosses three processes (agents, conversation history, AI gateway) with a hard request-size limit and a provider capability flag, and has to keep binary data out of stored events.

#1733 expands refs into the turn context. An attached image (a Files item or e-mail attachment of an image type) should reach the model as an image, not as text. Today:

- `backend/packages/agent-runtime/src/sempConversation.ts` `send` takes only a string.
- `backend/services/semprec-agents/src/piConversationHistory.ts` knows `ImageContent` only inside tool results; it does not replay user messages with content blocks (#1566 persists and replays user turns as run events).

- Images are never stored as base64 in `agent_run_events`; the stored user message keeps the ref. When the history is rebuilt, the image is loaded again from its blob, or, if it cannot be loaded or the budget is exhausted, replaced by a text placeholder naming the file.

### Requirement gh-1643: [journal-inbox 02/07] Accept Markdown page-content proposals with a placement into a page host

#### Context

Model tier rationale: One validation mechanism over a new envelope shape with a coexisting old shape, using existing fixtures, but the old-shape compatibility and the page-host rule need careful verification.

Today a `pageContent` proposal envelope is `{entityKind: "pageContent", target, properties: {flavour, fields?, children?}}` (`assertValidProposalEnvelope` in `backend/packages/data/src/inbox/inboxTickAction.ts`). `target` may be any live item (checked through `getItemsByIds`), and confirm appends exactly one block with no position (`confirmProposalWithClient` in `backend/packages/data/src/inbox/proposalActions.ts`). Users want to put several lines of Markdown on a page, optionally under a chosen heading, for example "- Grey 60x120, **matte**" under a heading "Tiles".

This issue introduces a second `pageContent` shape ("v2") beside the old one, validation only:

`properties: { markdown: string (required, non-empty), placement: "end" | "start" | { afterHeading: <blockId> } | { afterHeadingText: <string> }, heading?: string }`

The shape is discriminated by the presence of `markdown`: an envelope with `flavour` and no `markdown` is the old shape and keeps validating and confirming exactly as today.

Rules:

- `markdown` must parse with the page-Markdown parser from #1608 and contain only allowed blocks; a `page` block is refused.
- `afterHeading` must be the id of an `h1`-`h3` block that exists in the target page; the headings are read with the non-creating page summary from #1615.
- `afterHeadingText` is accepted as input only from the tick, and is converted to `afterHeading` (or to `end` when nothing matches) by #1649; a stored v2 envelope never contains it. This issue therefore accepts it only in the write-side schema used by the tick and rejects it in revise.
- The target must be a page host: a project, an area, a Journal day, or a sub-page of Pages. Any other target (for example a task or a company item) gives 400. This tightens v2 only; the old shape keeps accepting any live item.
- A target that has no page document yet is valid; confirm creates it (#1681).

Decision: when the heading the user wants disappears before confirm, confirm answers 409 and the card is revised by the user (handled in #1681).

#1681 builds on this to write the content; #1649 builds on it for the tick; #1959 (options endpoint) builds on it.

#### Task

Load `error-handling`, `state-writes` and `testing`.

1. Extend the `pageContent` schema in `inboxTickAction.ts` with the v2 shape and its types; keep the old shape typed and parsed unchanged. `parseStoredProposalEnvelope` accepts both.
2. ### Requirement gh-1734: [semp-voice 07/09] Run voice turns in Semp threads

#### Context

Model tier rationale: It joins four concurrent subsystems (voice channel, streaming speech-to-text, a queued agent turn, streaming text-to-speech) with interruption, budget exhaustion and tenant scoping, so lifecycle and cleanup ownership are the hard part.

Builds on: #1396 (streaming speech-to-text), #1399 (streaming text-to-speech), #1546 (the authenticated voice channel and its handler port), #1620 (accepting a chat message for a Semp thread) and #1727 (queued thread turns running in `semprec-agents`). The design is the voice ADR from #1371.

Today a Semp thread turn starts from a text message. The agent's streamed answer is already published as `agent:delta` frames for the run (`backend/packages/realtime/src/agentRunWatch.ts`), and approval requests created by a run show up as cards in its thread. This issue adds the handler for the voice channel so a spoken question becomes a normal thread turn and the answer is spoken.

Decisions:
- The final transcript becomes a user message of the thread through the same code path as the HTTP message endpoint of #1620, marked as originating from voice. A voice session started without a thread creates the thread on the first final transcript, exactly as creating a thread by message does.
- The turn is an ordinary queued turn: same tools, same steps, same approval cards. The only difference is how its input arrived and how its output is delivered. In an Inbox item thread the usual tool set for that thread kind applies.
- The voice session subscribes to the run's text deltas, splits them into sentences and sends each sentence to text-to-speech as it completes; the audio goes to the client as binary frames, with `speaking` control messages around it.
- Speech from the user while Semp is speaking stops the audio output and starts a new transcript; it does not cancel the running agent turn. A new final transcript becomes the next message and waits in the thread's queue. Only an explicit stop command cancels the turn, which #2019 adds on top of this one.
- Mute means the client stops sending audio; the server does nothing special. `end` or closing the socket closes the speech streams; the thread and its messages remain.
- When a speech stream reports budget exhaustion, the session sends an `error` message with code `budget_exceeded` and closes.

#### Task

Load `ai-gateway`, `io-hardening`, `error-handling`, `state-writes` and `testing`.

1. Implement the `VoiceSessionHandler` from #1546 in `semprec-api`: on `start`, open a speech-to-text stream through the gateway client; forward audio frames; relay partial and final transcripts to the client as `transcript` messages.
2. On each final transcript, create the thread message (and the thread, when none exists) through the #1620 code path with source `voice`, in the session's tenant and as the session's user. If the message store has no field for the origin of a message, add one in a migration.
3. After the message is queued, subscribe the session to that turn's run deltas (reuse the agent run watch from the realtime package), build sentences, and stream each to text-to-speech; forward audio frames in order with `speaking` start and end messages.
4. Handle barge-in: when speech-to-text reports new speech while audio is playing, stop playback (abort the synthesis request, drop queued sentences) and send `speaking` end; keep the agent turn running.
5. Handle failure and teardown: abort both streams on socket close or error; ensure no `ai_gateway_calls` row stays `reserved`; map gateway budget and capacity errors to `error` messages; never log transcripts, answer text or audio.
6. Tests with fake gateway streams: a spoken question yields partials, a final transcript, a thread message with source `voice` and speech output of the answer; a first transcript without a thread creates one; barge-in stops audio but not the turn; a second question during an answer waits in the queue; budget exhaustion ends the session with `budget_exceeded`; an approval request created in a voice turn appears as the usual card in the thread; closing the socket releases all streams.
