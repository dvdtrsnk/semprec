## Context

Model tier rationale: This adds a new AI operation, a 14-day aggregation over agent run events whose payload shape comes from a blocker, and a second reconcile loop in a tick that already brackets a non-transactional gateway call, so races and the blocker's data contract carry real uncertainty.

Add behavior findings to the existing core.agentGuidanceDrift tick, composed by API from application/shared/data owners. It compares the project's actual fourteen-day tool_use events (#1424) with guidance sections (#1548); fingerprints use #1375. Finding listing/resolution remains #1630/#1685.

`/internal/complete` accepts only the operations in `OPERATION_REQUIRES_PROJECT_ITEM` (`backend/services/semprec-ai-gateway/src/completeHandler.ts`), so the new operation must be registered there.

Decisions:

- A behavior is a group of tool calls: the pair (operation or MCP tool, target database id) taken from `tool_use` events of the project's runs (`agent_runs.project_item_id`) whose `at` is within the last 14 days. The exact payload field names are those #1424 adds; read its pull request description before starting. A call without a recorded target database uses a null database id.
- A group is considered only when at least 3 distinct runs contain it (threshold constant `BEHAVIOR_DRIFT_MIN_RUNS = 3`, window constant `BEHAVIOR_DRIFT_WINDOW_DAYS = 14`).
- The AI receives the groups (key, operation or tool, database name, run count) plus the `allowed` and `notAllowed` section texts and the owner's locale, and answers, per group not mentioned in either section, with `claim`, `suggestedAllowedLine` and `suggestedNotAllowedLine`, written in the owner's language (`users.locale`). A group that either section already mentions, allowing or forbidding, is not reported (forbidden-but-done is a permission concern, not this check).
- Evidence stored with each finding is `{ runIds, count }`: `count` is the number of distinct runs, `runIds` the most recent 20. Severity is `warning`.
- The two kinds reconcile independently: the permission pass resolves only active `permission` findings it no longer reports, and the behavior pass resolves only active `behavior` findings it no longer reports. Both are done by the nightly tick itself. If one pass throws, the other still runs and the first error is rethrown afterwards.
- A newly active behavior finding writes the existing `agent_guidance_drift` notification, with `kind` added to the payload; a resolved one writes `agent_guidance_drift_resolved` with `kind` in its payload.
- No group above the threshold: the gateway is not called and active behavior findings are resolved.

## Acceptance criteria

- When 3 runs in the last 14 days each called `item.create` in Tasks and the sections do not mention it, then after the tick there is exactly one active `behavior` finding with evidence `count` 3, `suggestedAllowedLine` and `suggestedNotAllowedLine` in the owner's language, and one `agent_guidance_drift` notification.
- When the tick runs again with unchanged inputs, then no second finding or notification is created and `lastSeenAt` advances.
- When fewer than 3 runs contain the group, or either section already mentions it, then no finding is created and the gateway is not called when no group qualifies.
- When the behavior stops (outside the window) or a section starts to mention it, then the next tick resolves the finding and writes `agent_guidance_drift_resolved`; permission findings are untouched by the behavior pass and the reverse.
- When the guidance changes while the gateway call is in flight, then no behavior finding is written.
- `/internal/complete` accepts `agent_behavior_drift` with a project id and refuses it without one.
