**Blocked by:** #570

## Context

In the review follow-ups pipeline (epic #565), a harvest issue is triaged by Relay's `triage-review-followups` workflow. Its first deterministic step, `prepare`, writes one local file into the run's worktree: the **triage input file**. That file holds everything the triage agent needs, so the agent never touches GitHub:
- the findings still to triage, as #570's finding records enriched with the full inline comment text, the bot's suggested fix and the thread replies;
- each pull request's latest review summary;
- the open queued issues with their `## Touches` sections, for cross-batch overlap checks.

Two things read this file: the triage agent, and the deterministic `validate` and `publish` steps. Both steps check that the agent's proposal accounts for every finding in it. Because an agent's step writes into the same worktree, the file is a boundary (repository rule 6): everything that reads it validates it.

This issue defines the format, with a renderer that refuses to write an invalid file and a parser that validates everything. The `prepare`, `validate` and `publish` scripts, later issues in this batch, only call these exports.

It builds on #570's `.github/scripts/review-followups/records.mjs`: `validateFindingRecord(value)` accepts exactly the finding-record fields (`pr`, `key`, `severity`, `category`, `path`, `line`, `anchor`, `description`, `descriptionTruncated`, `discussionId`, `threadResolved`, `replies`, `pathExists`, `touchedAfterLastSeen`, `laterPrsTouchingPath`, `firstSeenSha`, `lastSeenSha`) and throws naming the first offending field.

## Task

Create `.github/scripts/review-followups/input-file.mjs`, a zero-dependency ES module whose header comment is the reference description of the triage input file, exporting:

1. `renderInputFile(input)` and `parseInputFile(text)`. The file is JSON with two-space indentation and a trailing newline: `{ "version": 1, "harvestIssue": <positive integer>, "findings": [...], "prSummaries": [...], "openIssues": [...] }`.
   - Each `findings` entry is a finding record plus exactly three more fields: `fullText` (string or `null`), `suggestedFix` (string or `null`) and `threadReplies` (array of `{ author: non-empty string, body: string }`). The record part must pass `validateFindingRecord`, and no two entries share `(pr, key)`.
   - `prSummaries` is an array of `{ pr: positive integer, body: string }`, at most one per `pr`.
   - `openIssues` is an array of `{ number: positive integer, title: string, labels: string[], touches: string }`, with no duplicate `number`.
   - No object may carry a field not listed above.

   The renderer validates before writing and throws on violation. The parser validates everything and throws an `Error` naming the first offending field.
2. `input-file.test.mjs` next to it, using `node:test` and `node:assert/strict`, covering every Acceptance criterion below.

## Scope

### In scope

- The triage input file format, its renderer and parser, and tests.

### Out of scope

- Building the file's content from GitHub. That is the `prepare` issue in this batch.
- The triage proposal file. The `validate` issue of this batch owns its format.
- Changing the finding record (#570).

## Acceptance criteria

1. `parseInputFile(renderInputFile(x))` returns `x`. `renderInputFile`'s output ends with a newline and uses two-space indentation.
2. `parseInputFile` throws, naming the field, for:
   - a missing `harvestIssue`;
   - `version: 2`;
   - an entry without `threadReplies`;
   - a `fullText` that is a number;
   - an entry whose record part fails `validateFindingRecord` (for example, a nine-character `key`);
   - an entry with an extra field;
   - a duplicate `(pr, key)`;
   - two `prSummaries` for one `pr`;
   - a duplicate `openIssues` number.
3. `renderInputFile` throws for each invalid input from criterion 2 and returns text only for valid input.
4. Text that is not JSON makes `parseInputFile` throw with a message saying it does not parse.
5. `node --test .github/scripts/review-followups/input-file.test.mjs` passes with no network access.
