## Behavior specification (approved)

This epic opens the **multi-tenancy program**: Semprec changes from a system with exactly one human account into one where many users each own a completely isolated environment. This body is the program-level specification and decision log; every other `mt-*` epic refers back here. This epic itself delivers the prerequisites: fixes for pre-existing defects the program depends on, the tenant entity, the governance changes (review rules, skills), and the expand phase of the schema (a `tenant_id` on every tenant-owned row, transitional row-level security, tenant-leading unique keys, a two-tenant test harness).

Program behaviors:

1. **A tenant is one user's complete, isolated Semprec environment.** Every user has exactly one tenant (1:1) holding their own full set of system databases (Tasks, Projects, People, Files, Events, Emails, Mailboxes, Folders, Journal, Inbox, Library, MCP servers, System settings, …), items, views, docs, files and blobs, mailboxes, Semp supervisor conversation, agents, heartbeats, MCP servers and grants, credentials, settings (timezone) and AI budget.
2. **No user ever sees, infers or is notified about another user's data or agents.** No sharing exists now or as a planned feature. A foreign id behaves exactly like a non-existent id (same status, same body); global uniqueness never acts as an existence oracle.
3. **Accounts are created only by an admin's invitation.** No public signup. The setup-token bootstrap stays the single way to create the very first account of a fresh install.
4. **The current user becomes the first admin and all existing data becomes their tenant ("tenant zero").** Nothing changes for them functionally.
5. **Admin role:** manages accounts and invitations, suspends, reactivates and deletes accounts, changes roles (at least one admin always remains), sets per-user AI caps and sees operational health as content-free counts. An admin never sees another user's content through the product and there is no impersonation. Admins have their own tenant for their own content. Every admin mutation is audit-logged.
6. **AI:** the operator's global provider keys; per-user daily and monthly caps set only by an admin (a missing cap refuses — fail closed); a global safety cap from the environment. A refusal for the user's own cap and for the global cap look identical to the caller.
7. **MCP `stdio` transport** (spawns a host process) is allowed only in an admin's tenant, only when configured by a human (never by an agent), and runs sandboxed. Everyone else uses remote MCP over `https` to a public DNS host, with resolved addresses re-checked at connect time.
8. **Export and deletion:** a user can download a complete export of their data. A user (after password re-authentication) or an admin can delete an account: access is revoked at once, the tenant's secrets are crypto-shredded, all rows, partitions and files are purged, and only a PII-free tombstone remains. A backup restore re-applies recorded deletions.
9. **Defence in depth, failing closed:** isolation is enforced by Postgres row-level security and by an explicit tenant scope on every code path. Missing scope means "nothing visible, write refused", never "everything visible". Creating a second tenant is physically impossible until enforcement is strict and a maintainer has signed the security gate.
10. **Every existing principle of this codebase holds:** the choke point, single writer, expand/contract forward-only migrations with one-release rollback, the AI gateway monopoly, agent writes as proposals, side effects after commit, typed boundaries, canonical keys with i18n labels, no speculative generality, an ADR for each new cross-cutting pattern, and issue batches as dependency DAGs.

## Decisions

- **Which isolation mechanism?** → One shared schema, `tenant_id` on every tenant-owned row, Postgres row-level security. → Schema-per-tenant runs every migration N times per deploy and breaks one-pass deploy and one-release rollback, and a `search_path` slip fails open; database-per-tenant multiplies pools, LISTEN connections and crons; application-only `WHERE tenant_id` across ~434 query sites fails open on the first miss; an instance per user is not one system. RLS is enforced whatever the query shape, and it turns today's singleton lookups (`getDatabaseByModuleId`, the settings `LIMIT 1`, `listAllDatabases`) into per-tenant lookups.
- **What is a tenant?** → A global `tenants(id, status ∈ provisioning|active|suspended|deleting, created_at, status_changed_at)` table; `users.tenant_id UNIQUE` (exactly one environment per user) and `users.role ∈ admin|member`. → `tenant_id = user_id` was rejected because deletion must outlive the PII-bearing user row and a tenant exists (`provisioning`) before its user may log in; memberships were rejected because sharing is forbidden.
- **How does RLS fail closed while every release stays rollback-safe?** → SQL functions `app_current_tenant()` (`NULLIF(current_setting('app.tenant_id', true), '')::uuid` — the `NULLIF` matters because a transaction-local setting reads `''` afterwards), `app_sole_tenant()` (the id when exactly one tenant exists) and `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())` during the transition. Tenant columns are `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)`; each tenant table gets a RESTRICTIVE policy `tenant_isolation` (`tenant_id = (SELECT app_tenant_default())`) plus a PERMISSIVE `tenant_rows` (`true`). → While one tenant exists, scope-less code (including the previous release) behaves exactly as today; the strict switch later redefines `app_tenant_default()` to `app_current_tenant()` and flips every default and policy at once. Restrictive means no later permissive policy can widen access.
- **What prevents a second tenant before enforcement is strict?** → A unique index `tenants_single_tenant_guard ON tenants ((true))`, dropped only by the go-live issue, which waits on the maintainer's security sign-off; test databases drop it in setup only. → A database guard cannot be bypassed by any code path.
- **FORCE row-level security?** → No. Tables are owned by the migrating superuser, which bypasses RLS anyway; instead each service refuses to start as a superuser, `BYPASSRLS` or table-owner role, and a catalog test asserts runtime roles have no privilege on any `items_p_*` partition (addressing a partition directly would bypass the parent's policy).
- **How is the tenant carried through the code?** → An `AsyncLocalStorage` scope in `backend/packages/shared/src/tenantScope.ts` (`runInTenant`, `runAsSystem`, `currentTenantScope`); `withTransaction` sets `app.tenant_id` transaction-locally right after `BEGIN`; the pool applies the same scope to autocommit queries and raw client checkouts; `SEMPREC_TENANT_SCOPE=warn|strict`. → An explicit handle on every call would touch nearly every file and still need a runtime guard. Long-lived loops, listeners and registries start in `runAsSystem` and enter a tenant explicitly per message or job; tenant identity never comes from request bodies, model output or untrusted headers.
- **Where may a tenant scope come from?** → Only: the HTTP session (the tenant must be `active`); the WebSocket identity fixed at upgrade; the queue envelope `{traceId, tenantId, payload}` stamped by `enqueueJob` from the current scope; the NOTIFY payload `tenantId`; the internal AI-gateway header `x-semprec-tenant-id` checked against the internal token and an RLS-visible run; the MCP run credential; router functions for external identifiers.
- **How does system work that spans tenants run?** → Cron sweeps enumerate tenants (`forEachActiveTenant`) and do the existing work inside each tenant; external identifiers (Graph subscription id, Gmail address) and operator aggregates go through `SECURITY DEFINER` functions owned by a NOLOGIN `BYPASSRLS` role `semprec_router` with column-level `SELECT`, returning only ids or numbers. → No runtime role ever bypasses RLS.
- **How are tables classified?** → `COMMENT ON TABLE … IS 'semprec:tenancy=tenant'|'semprec:tenancy=global'` in the creating migration, checked by a catalog test. → A TypeScript registry would be a merge hotspot. Global: users, sessions, login_attempts, password_reset_tokens, push_subscriptions, agent_run_mcp_credentials (gains `tenant_id`), process_heartbeats, observability_checks, schema_migrations, the queue schema, and the new tenants, invites, tenant_ai_budgets, admin_audit_log, tenant_deletions. Every other table is tenant-owned.
- **What about global uniqueness?** → Every unique index on a tenant table leads with `tenant_id` unless it is a server-generated surrogate key or a key scoped by the server-generated id of a parent row in the same tenant (e.g. `properties (database_id, key)`), because a collision there needs another tenant's unguessable id and the composite tenant foreign keys bind parent and child to one tenant; composite foreign keys `(tenant_id, x_id) → parent(tenant_id, id)`. → Unique and foreign-key checks ignore RLS, so a global key is an existence oracle, a collision or a cross-tenant link. Order: expand (add composite keys) → switch each subsystem → contract (drop the legacy keys) in a later release.
- **How are a tenant's system databases created?** → `provisionTenant(tenantId)` runs today's seed and module data migrations inside the tenant's scope under a per-tenant advisory lock; status goes `provisioning → active`.
- **Who receives what used to go to "the earliest user"?** → Tenant events go to the tenant's user; operator alerts go to every admin as content-free rows; `getEarliestUserId` and `getEarliestUserLocale` are deleted.
- **Secrets?** → A per-tenant data key wrapped by `CREDENTIALS_MASTER_KEY`, AEAD with associated data `tenant_id‖item_id`; tenant keys are excluded from the long-retention backup and dumped separately with 7-day retention. → A deleted tenant's secrets become unrecoverable within 7 days even with the master key.
- **Backups and deleted tenants?** → Content stays in backup snapshots until retention expiry (12 months), accepted for disaster recovery and documented; a restore replays the deletion ledger so a deleted tenant never returns to the live system.
- **Who can technically read the database?** → The operator with root on the host can. Protecting content from the operator would need client-side encryption, which is incompatible with server-side agents, search and mail sync; out of scope and documented.
- **How is the rollout gated, given Relay merges continuously while releases are promoted by the maintainer?** → Two maintainer-only issues, never labelled `agent:ready`: a release checkpoint (a context-complete release runs in production with zero `tenant_scope_missing` warnings for 7 days) before the strict switch and every contract step, and a security-gate sign-off (strict release deployed, the previous release also strict, external adversarial review) before invitations can be accepted.
- **Pre-existing defects found while planning?** → Fixed first in this epic: two tables without runtime-role grants (`agent_run_mcp_credentials`, `mail_message_flag_sync_state`); `semprec-agents` connecting as `semprec_side` while performing choke-point writes; the web generic adapter calling item and relation URLs the backend does not serve; an in-transaction `SET TRANSACTION` in the transcription task; a journal-inbox invalidation fired outside its transaction; Caddy logging full URIs including setup and reset tokens; `APP_BASE_URL` and the SMTP settings missing from the production environment template, so emailed links point at `localhost`.

## Out of scope (whole program)

Sharing between users; multi-member workspaces; public signup; impersonation or support access; bring-your-own AI keys; SSO or OAuth login; per-user content encryption; calendar provider integration; wiring the currently unwired mail transports and OAuth (only their tenancy constraints are fixed); Apple client work.
