## Context

PR #379's review flagged that `PATCH /api/properties/:id`
(`propertiesHandler.ts:48-70`) opens a second, separate transaction
(`dispatchGenericOperation(service, "database.get", ...)`, line 63) after
`property.patch` (line 60) has already committed, purely to resolve the owning
database for catalog/locale resolution. If the database is deleted between those two
calls, `database.get` returns a not-found result and the handler must handle that as
a distinct failure mode, even though the property update itself already succeeded —
a structural TOCTOU gap between two independently-committed operations. The review
noted this mirrors the same two-transaction shape a `viewsHandler.ts` route had
before PR #380 fixed it by returning the state read inside the write's own
transaction instead of re-fetching it afterward (commit e942392).

## Task

In `backend/packages/data/src/chokePoint/` (wherever `updateProperty`/`property.patch`
currently owns its transaction), expose a way for `propertiesHandler.ts`'s
`PATCH /api/properties/:id` handler to read the property's owning `Database` row
inside `property.patch`'s own transaction — via a callback or a direct query using
the same transaction client `updateProperty` already opens — without changing
`OutputByOperation["property.patch"]`'s shape, since that shared type is also the
verbatim result every MCP agent tool call to `property.patch` returns
(`genericOperationAgentTools.ts:91`). Update the `PATCH` handler to use that database
instead of calling `dispatchGenericOperation(service, "database.get", ...)` as a
second step.

## Touches

- backend/services/semprec-api/src/propertiesHandler.ts (`PATCH /api/properties/:id`
  handler)
- backend/packages/data/src/chokePoint/ (wherever `updateProperty`/`property.patch`
  is implemented — extending its return shape to include the owning database row)

## Scope

### In scope

- Resolving the owning database inside `property.patch`'s own transaction, for the
  `PATCH` handler only, without changing `property.patch`'s generic-operation output
  type.

### Out of scope

- The equivalent gap on `DELETE /api/properties/:id` (line 82-90) or on
  `POST /api/databases/:id/properties` (`databasesHandler.ts:131`, a pre-existing,
  separate gap) — neither was flagged by this finding.

## Acceptance criteria

- `PATCH /api/properties/:id` no longer calls
  `dispatchGenericOperation(service, "database.get", ...)`; the database used for
  catalog/locale resolution is read inside `property.patch`'s own transaction
  without widening `OutputByOperation["property.patch"]`.
- A property update whose owning database is concurrently deleted between the old
  two-transaction calls can no longer produce a separate not-found result for the
  database step, since both reads now happen inside `property.patch`'s single
  transaction.
- The response body and status code for a successful `PATCH` are unchanged from
  today.
