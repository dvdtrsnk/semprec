## Context

Model tier rationale: It relaxes the schema-lock rule for a defined class of schema writes on system databases, adds a new operation across the shared catalog, authorization, REST and approval seams, and needs a lock to avoid lost concurrent updates.

Options of a select or multi-select can be changed only through `PATCH /api/properties/:id` with the whole `config.options` array (operation `property.patch`, capability `core.schema.write`, not destructive), and only on a database that is not schema-locked (`updatePropertyConfig` calls `assertPropertySchemaMutable` in `backend/packages/data/src/chokePoint/propertiesStore.ts`, which throws `SchemaLockedError` or `PropertyLockedError`). Every system database is schema-locked, so Health records (and every other system select) cannot get a new tag. Also, replacing the whole array loses a concurrent addition.

This issue adds two narrow operations, `property.option.add` and `property.option.update`, that may change only the option list of a select or multi-select on a locked database, and records that exception to the lock rule in an ADR. It builds on #1584, which defines the optional `color` on options and its validation (`assertValidSelectOptions`). #1994 uses it to create an option while confirming an Inbox proposal.

Decisions:
- Exposed over REST and the generic catalog only. It is not exposed as an agent tool or MCP tool; the assistant proposes a new option through an Inbox proposal (#1994) and a person confirms it. Reason: a schema change is sensitive and must be approved by the user, so the assistant can never create an option through a tool.
- The key is generated by the server from the label: ASCII camelCase without diacritics ("Dentální hygiena" gives `dentalniHygiena`); a collision with an existing key gets a numeric suffix (`bylinky2`). An empty result uses `option`.
- A label that matches an existing option's label, case- and diacritics-insensitive, in the stored label or in the Czech or English catalog label of that option ("léky" equals Medication), is refused with 409 and the new additive error code `option_label_exists` carrying the existing option's `key`.
- At most 100 options per property and a label of 1 to 60 characters; otherwise 400 `validation_failed`.
- Removing an option is out of scope.
- A property that is itself `locked` still refuses (`PropertyLockedError`), and `property.patch` on a locked database still refuses with `SchemaLockedError`.

Shared-file ordering: this issue also waits for #1693 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `adr-conventions`, `state-writes`, `error-handling`, `canonical-keys` and `testing`.

1. Add an ADR under `docs/adr/` (dated; narrows the rule that a system database's schema changes only by a code-level migration): adding or renaming select options is allowed on a schema-locked database through these two operations; every other schema change stays forbidden. Record the decisions above.
2. Add the two operations to the generic catalog: names, input schemas (`property.option.add` `{ propertyId, label, color? }` returning `{ key, label, color? }`; `property.option.update` `{ propertyId, key, label?, color? }` returning the same), capability `core.schema.write`, non-destructive metadata, port methods and bindings. Keep them out of the agent tool and MCP exposure lists, with a comment pointing to #1994. Update the operation-count comments and catalog tests.
3. Add store functions in `propertiesStore.ts` that, in one transaction, lock the property row (`SELECT ... FOR UPDATE`), check the property is a `select` or `multi_select` (otherwise 400 `validation_failed`, `field: "propertyId"`) and not `locked`, apply the add or update to `config.options` (validate color with the existing option validation; rename writes the `label` of that option and keeps its key), and return the option. Two concurrent adds both survive. Bypass only the database-level `schema_locked` check, nothing else.
4. Add the choke-point operations in `propertyOps.ts` and the facade in `chokePoint.ts`; after commit, send the schema invalidation for the database (`notifyInvalidation({ scope: "schema", databaseId })`, as `propertyDeleteWithClient` does).
5. Add the application service methods and the REST routes `POST /api/properties/:id/options` (body `{ label, color? }`, 201) and `PATCH /api/properties/:id/options/:key` (body `{ label?, color? }`) in `propertiesHandler.ts`; register both in `routeMatrix.ts` and `__tests__/tenantIsolationRoutes.test.ts` (cross-tenant property ids answer like unknown ones).
6. Tests: adding "Bylinky" to Health records `tags` returns 201 with key `bylinky` and the option appears in `GET /api/schema`; adding "léky" returns 409 `option_label_exists` with key `medication`; adding a second "Bylinky"-like label gets a suffixed key; renaming and recoloring an option keeps its key; two concurrent adds leave both options; a `text` property returns 400; `property.patch` of the same property on the locked database still fails with `SchemaLockedError`; a locked property still refuses; a member of another tenant cannot touch the property; the schema invalidation is sent.

## Scope

### In scope

- The two operations, their locking and key and label rules, the REST routes, catalog registration, the schema invalidation and the ADR.

### Out of scope

- Option colors and their validation: #1584.
- Removing an option, reordering options and changing an option key.
- Exposing the operations to the assistant or MCP; proposing a new option from the Inbox: #1994.
- Any UI for adding or renaming options; this issue is implemented only once a design for it exists.

## Acceptance criteria

- When `POST /api/properties/:tagsId/options` is sent with label "Bylinky", then the response is 201 with `key` `bylinky` and the option appears in the schema.
- When the label is "léky" and Medication exists, then the response is 409 `option_label_exists` carrying `medication`.
- When two adds run concurrently, then both options exist afterwards.
- When the property is not a select or multi-select, then the response is 400.
- When `property.patch` changes `config` of a property on a schema-locked database, then it still fails with `SchemaLockedError`.
- When another tenant's property id is used, then the answer equals the answer for an unknown id.
