## Context

Model tier rationale: A single user-owned longText property added through the same seed plus populated-install cutover pattern that `People.emails` already uses, with no new lifecycle, authorization or tenant contract.

The People collection has `name`, `relationship` and `contact` (phone or e-mail as the preferred channel) in `backend/packages/data/src/seed/seedTenDatabases.ts`, and a user-owned longText `emails` property (one address per line) added by `backend/packages/data/src/seed/seedEmailModule.ts`. A person has no phone number at all, so the preferred contact "phone" has nothing behind it and the search results cannot show a number.

This issue adds `People.phones`: a user-owned longText property, one number per line, modelled exactly on `emails` (but with no index table). The People schema is `schema_locked` once seeded, so populated tenants receive the property through a code-level cutover that inserts the row directly, the way `seedEmailModule.ts` does for `emails` and `backend/packages/data/src/transcription/transcriptsCatalogCutoverMigration.ts` does for Transcripts. Fresh installs get it from the seed.

This builds on #1457 (which also edits the tenant cutover registry, so the two are ordered to avoid a conflict in `db/tenantCutoverMigrations.ts`) and on #1413 (which edits the Czech catalog `seed/i18n/cs.json`, so this issue's new key is added after it). The derived last-contact issue #1660 builds on this one because both register in the same cutover list. Search over phone numbers is not built here: People joining the searched fields is done by #1397, and matching a number written as "777 123 456" or "+420777123456" to the same token is done by #1589.

Decision: the number is stored exactly as the user typed it, one per line; no normalization happens at write time.

Shared-file ordering: this issue also waits for #1529 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `canonical-keys` and `testing`.

1. In `seed/seedTenDatabases.ts`, add to the People property list `{ key: "phones", name: "Phones", type: "longText", owner: "user" }`, next to `contact`. Keep the canonical key `phones` (English camelCase).
2. Create `backend/packages/data/src/seed/peoplePhonesCutoverMigration.ts` exporting `runPeoplePhonesCutoverMigration(pool)`: in one transaction, resolve the People database with `getDatabaseByModuleId`; return when it does not exist; insert the `phones` property (`longText`, owner `user`, empty config) with `ON CONFLICT (database_id, key) DO NOTHING`. It must be idempotent and must not use the schema-locked property store.
3. Register it in `runTenantCutoverMigrations` in `db/tenantCutoverMigrations.ts`, after the existing cutovers.
4. Add the label `property.people.phones.name` to `seed/i18n/en.json` ("Phones") and `seed/i18n/cs.json` ("Telefon").
5. Tests: the property exists after a fresh seed; the cutover adds it on a People database seeded without it and is a no-op on the second run; a user can write and read `phones` through the generic item endpoints.

## Scope

### In scope

- The `phones` property on People for fresh and populated tenants, and its Czech and English labels.

### Out of scope

- Adding People `phones` to the searched fields: #1397.
- Normalizing numbers in documents and queries: #1589.
- Deriving the last contact date: #1660.
- A phone-number format validator or a phone-typed property.
- Showing phones in any UI.

## Acceptance criteria

- When a tenant is freshly seeded, then the People schema contains a user-owned longText property `phones`.
- When the cutover runs on a tenant whose People database has no `phones`, then the property is added; when it runs again, then nothing changes and no error is raised.
- When a user writes `phones` of a person as "777 123 456", then reading the person returns it unchanged.
- The Czech label of the property is "Telefon" and the English label is "Phones".
