## Context

Model tier rationale: A new read operation that compiles many per-property aggregate queries from a caller-supplied filter, with an exclude-self rewrite of the filter tree, several property-type-specific rules and a tenant-isolation surface, spanning shared catalog, data layer and REST, so a subtle error silently produces wrong counts on every filter screen.

A filter sheet on a collection shows, next to each choice, how many items would remain if that choice replaced the selection in that property while every other filter stayed (Status: In progress 7, Long-term 6). Nothing in the backend can produce these counts: counts exist only as the choke-point `countItems`, there is no aggregation by property value, and `is_empty` is rejected on relations by `backend/packages/data/src/views/filterCompiler.ts`.

This issue adds one operation, `database.facets`, that returns for each requested property its choices with counts, computed under the caller's filter with that property's own conditions removed ("exclude-self"), with no free-text search. It builds on the batched counts (#1709), the relative-date and numeric conditions (#1522, #1534), numeric filter presets stored on number properties (#1622), the one-extra-hop relation path condition (#1363), relation emptiness (#1526) and the per-database area filters declared in manifests (#1597). Proposal grounding builds on it (#1990).

Decision (product owner): a view variant is not added; a caller that wants facets under a stored view's filter sends that filter as `filter`, with no special operation. Decision: a condition on the facet's own property nested inside `or` or `not` cannot be removed safely, so it is a 400 with `field: "filter"` rather than a guess. Decision (product owner): an archived database is in the trash and is left out of facets as it is of `item.count` (#1709): facets of an archived database count 0, and relation and path facets leave out targets and intermediate items in archived databases (an item whose only edges point there falls into "no value").

Shared-file ordering: this issue also waits for #1757 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `canonical-keys`, `error-handling` and `testing`.

1. Add the operation `database.facets` (capability `core.item.read`, non-destructive): name, capability, schemas, port method, binding in the shared `genericOperations` files, `genericApplicationService.ts` method, and REST `POST /api/databases/:id/facets` in `itemsHandler.ts` plus `routeMatrix.ts` and the cross-tenant route cases in `tenantIsolationRoutes.test.ts`. Input (`.strict()`): `{ databaseId, filter?, facets: [propertyKey | { path: [relationKey, relationKey] }], extra?: { open: <filter> } }` with a bounded number of facets (at most 20) and the same filter-size limits as `database.query`. An unknown database id and a foreign one answer identically.
2. Output per requested facet: `{ property | path, all, values: [{ value, label, color, count }] }` where `all` is the count under the filter without the facet's conditions, and the "no value" entry is `{ value: null, count }`. `extra.open` adds `open`: the count under the filter AND the `open` filter.
3. Exclude-self: remove from the filter every condition on the facet's property that is a direct child of the top-level `and` (or the root itself when the root is such a condition); a condition on that property under `or` or `not` is a 400. For a `path` facet, remove conditions with the same path (`relation_path_contains` from #1363). Never include free-text search. Soft-deleted items are never counted. One SQL query per facet, all values bound as parameters.
4. Per property type: a group select (status, type, relationship) returns every option in `config.options` order including count 0; any other select, a multi-select and a relation return only values that occur (top 20 by count for text and relation values), plus "no value" (relation emptiness via #1526); a relation to projects returns the project's area color as `color`; an area facet returns every area of the area filter declared in #1597 with its color, including 0; a text property returns the top 20 values by count; a checkbox returns yes and no; a date returns one entry per `date_relative` preset (#1522) that has count above 0, a "no date" entry only when some item has no date, and no count for a custom range; a number returns one entry per numeric filter preset stored on the property (#1622) counted by that preset's comparison. `label` and `color` come from the stored option or related item, never from client text.
5. Tests: status facet under `status = inProgress` AND `area = Work` returns every status with counts inside Work, including archive with 0; a project facet returns only occurring projects with the area color and a no-value entry; a `path` facet `[project, area]` over Tasks returns counts per area and `extra.open` returns the not-done count; exclude-self leaves other properties' conditions in place; own-property condition inside `or` is a 400; a date facet omits zero-count presets; a relation facet whose targets lie in an archived database lists none of them and counts those items under "no value"; facets of an archived database count 0; foreign database id equals unknown.

## Scope

### In scope

- The `database.facets` operation with exclude-self counts, per-type value rules, relation path facets and the `extra.open` count.

### Out of scope

- Board column counts and the batched counts themselves: #1709.
- A view variant of facets (decision above).
- Free-text `q` in facets: facets never apply it.
- New filter conditions the facets read: #1522, #1534, #1363, #1526.

## Acceptance criteria

- When the filter is `status = inProgress` AND `area = Work` and the facet is `status`, then the response lists every status option in option order with its count inside Work, including options with count 0, and the in-progress count is unaffected by the status condition.
- When the facet is a project relation, then only projects that occur are listed, each with its area color, plus a no-value entry.
- When the facet is `path: [project, area]` over Tasks with `extra.open`, then counts per area of the task's project are returned and `open` is the count of not-done tasks under the filter.
- When the filter has a condition on the facet's own property under `or` or `not`, then the request fails with a 400 naming `filter`.
- When a date facet is requested, then presets with count 0 are absent and a "no date" entry appears only if some item has no date.
- When a relation facet's targets lie in an archived database, then those targets are not listed and the items linked only to them are counted under "no value"; when facets are requested on an archived database, then every count is 0.
- When a database id belongs to another tenant, then the response is identical to the one for a nonexistent id.
