## Context

Model tier rationale: This turns a hard authorization failure into a deferred, exactly-once outbound action with a new approval kind, and the permission evaluation (actor project, thread project, heartbeat project) is a security contract.

Sending mail by an agent or an MCP client with a run credential is decided in the ADR of #1385: it creates an approval request instead of a 403. Decided by the product owner: in v1 every send by an agent or a run-credential MCP client creates an approval request with risk class `outbound`; the project permission `emailSendAutonomous` does not let a mail leave without approval in v1. Today `assertEmailSendAuthorized` in `backend/packages/data/src/mail/send.ts` lets a user through, lets an agent through only with `capabilities.email.send.autonomous` (project property `emailSendAutonomous`, `manifest/permissionManifest.ts`), and otherwise throws a 403 `email_send_not_autonomous` without queueing anything. `approval_requests` (migration `0021`, `agent_run_id NOT NULL`, tool, risk class, payload, status) and the execution flow of `mcp/approvalRequestExecution.ts` replay only generic operations and deferred MCP calls. The approval gate of `/mcp` applies only to a run credential; a human session acts as the user. The send over HTTP is #1896 (`sendDraftEmail`). Related building blocks: deferral of module tools with the `moduleTool` request variant (#1791), the localisable description (#1683), the source of a request (#1766), the closed risk class set (#1423), flagged agent writes (#1713), and the exactly-once rule in `docs/adr/2026-09-29-exactly-once-execution-of-deferred-mcp-tool-calls.md`.

Decisions: an approval description never contains argument values of the send (decided by the product owner); the recipients and the subject are shown only from the request detail to its owner (#2021). The request records the draft hash, so a changed draft is never sent; a rejected request leaves the draft; at most one pending request per draft.

## Task

Load `state-writes`, `error-handling`, `io-hardening`, `testing` and `canonical-keys`.

1. Approval requirement: replace the 403 for an agent or run-credential actor in `mail/send.ts`: every such send creates the request of step 2, whatever `capabilities.email.send.autonomous` says on the actor's own project (the run's `agentProjectItemId`, or that of the run credential), on the draft's thread project or on a `newEmail` heartbeat's project; no permission lets an agent send without approval in v1, and a project written on a thread by an agent or by Semp's sorting never changes this. A user, and an MCP client with a human session, send as before without approval.
2. Approval kind: declare the tool `mail.draft.send` as a `moduleTool` request with `requiresApproval` always for an agent or run-credential actor (descriptor of #1791), risk class `outbound`, `snapshotExport` = `draftHash` (hash of from, to, cc, bcc, subject, body, attachments and mailbox), payload `{ draftId, draftHash, mailboxId, to, subject, body }`, and a description template key `approval.emailSend` with `{ mailboxName, recipientCount }` (no recipient address or name and no subject, which are argument values) rendered by the client, not stored as Czech text. The request carries the source (`chat`, `tick` or `mcp`) and the operation label `<mailbox name> · <tool name>`.
3. At most one pending request per draft; deciding one request closes any other pending request of that draft as superseded.
4. Execution (`approvalExecute`): claim, re-compute the draft hash, send through `sendDraftEmail`, record the result, and recover a stuck claim, all as in the exactly-once ADR. A hash mismatch ends with execution status `conflict`. Rejecting a request leaves the draft unchanged.
5. Add the i18n template key for the description to `seed/i18n/cs.json` and `seed/i18n/en.json`.

## Acceptance criteria

- An agent or run-credential send in a project without permission creates one approval request and sends nothing; after approval the mail leaves exactly once.
- In a project with `emailSendAutonomous`, an agent send still creates one approval request with risk class `outbound` and sends nothing until it is approved.
- After Semp moves a thread into a project that has permission, a send by an agent still creates a request.
- The rendered description of a send request names the mailbox and the number of recipients and contains no recipient and no subject.
- A second pending request for the same draft is not created; a changed draft at execution time ends with `conflict` and nothing is sent; a rejection leaves the draft.
- A user or human-session send is unchanged and creates no request.
