## Context

Model tier rationale: One bounded wait on an existing advisory lock, one error answer on an existing route and one precondition check copied from an existing guard. It adds no table, route or column, but the wait sits in front of a destructive removal and must leave nothing written and no changed session setting behind, which the tests have to prove on real concurrent transactions.

`removeMailbox` (`mail/mailboxRemoval.ts`, #1690) starts with the mailbox sync guard, `lockMailboxSync` (`mail/mailboxSyncGuard.ts`), a transaction-scoped `pg_advisory_xact_lock` keyed by tenant and mailbox that a sync pass's write transaction takes too (`enterSyncPass` in `mail/mailSyncJob.ts`). A removal that arrives during a pass waits for it, holding no row lock. The recheck of #1690 recorded two things that were left open (`issues/handovers/gh-1690.md`, "Follow-ups", verified against the code at the integration tip):

1. The wait is unbounded except by the pool's `statement_timeout` (60 s, `db/pool.ts`). A pass takes the mailbox's sync guard first and the tenant's mail-thread mutation guard second (`lockMailThreadMutation`), so the pass of mailbox B can hold B's guard while it waits for a long pass of mailbox A, and a removal of B waits for that too. When the wait exceeds 60 s the database cancels the statement (SQLSTATE 57014), the transaction rolls back with nothing written, and the route answers a generic 500, which says nothing about a retry. The accepted ADR of #1690 does not say that a removal can wait for a pass of another mailbox. A correct answer is a retryable one, and it needs a bound that is shorter than the statement timeout so the failure is told apart from every other cancelled statement.
2. `lockMailboxSync` checks only that a tenant scope is active. `lockMailThreadMutation` (`mail/mailThreadMutationGuard.ts`) also checks that its client is inside a READ COMMITTED transaction of the scope's tenant, and its ADR relies on it: an advisory transaction lock taken outside a transaction (or at another isolation level, where the removal's later reads would not see a sync pass that committed while it waited) is a silent defect. Both callers run inside `withTransaction` at its default level, so nothing is wrong today.

Decision: the removal waits for the sync guard for at most 15 s. When the guard is still held then, the removal fails with 409 `mailbox_sync_busy` ("The mailbox is being synchronized; try again shortly"), writes nothing, and the request can be repeated. The sync pass keeps its unbounded wait. The bound is a per-call option of `lockMailboxSync`, enforced with `lock_timeout` for that one statement, and the session setting is put back afterwards, so no later statement of the removal inherits it. `lockMailboxSync` refuses a client that is not in a READ COMMITTED transaction of the active tenant, as `lockMailThreadMutation` does.

## Task

Load `state-writes`, `error-handling`, `io-hardening`, `testing` and `adr-conventions`.

1. In `mail/mailboxSyncGuard.ts`:
   - `lockMailboxSync(client, mailboxItemId, options?: { maxWaitMs?: number })`. Before it locks, it requires that the client is inside a transaction (`client.getTransactionStatus() === "T"`) and that `current_setting('transaction_isolation')` is `read committed` and `app_current_tenant()` equals the active scope's tenant, and throws `Error("The mailbox sync guard requires a READ COMMITTED tenant transaction")` otherwise, before any lock. The existing `TenantScopeMissingError` for a missing scope stays and comes first.
   - With `maxWaitMs`, it reads the current `lock_timeout`, sets it transaction-locally (`set_config('lock_timeout', <ms>ms, true)`) for the advisory lock statement only, and sets the previous value back in the next statement once the lock is granted. When the lock times out (SQLSTATE `55P03`), the transaction is aborted by the database, so there is nothing to restore: it throws `MailboxSyncBusyError`, which ends the caller's transaction by rollback. Without `maxWaitMs` the behaviour is exactly as today.
   - Export `MailboxSyncBusyError extends ChokePointError` with status 409 and code `mailbox_sync_busy`, and the constant `MAILBOX_REMOVAL_SYNC_WAIT_MS = 15_000`.
2. In `mail/mailboxRemoval.ts`, `removeMailboxWithClient` calls `lockMailboxSync(client, mailboxItemId, { maxWaitMs: options.syncWaitMs ?? MAILBOX_REMOVAL_SYNC_WAIT_MS })`. Add the optional `syncWaitMs` to `RemoveMailboxOptions` (a test seam like `cleanupStepTimeoutMs`). The `MailboxSyncBusyError` propagates out of `withTransaction`, so the whole removal rolls back, no cleanup after the commit runs, and `createMailboxRemovalRouteHandler` answers 409 with the code. Update the docstrings of `removeMailboxWithClient` and `removeMailbox` ("waits there ... until the statement timeout cancels the removal").
3. `mail/mailSyncJob.ts` (`enterSyncPass`) is not edited; it keeps calling `lockMailboxSync(client, mailboxItemId)` without an option and now meets the transaction check.
4. Add `docs/adr/<date>-a-mailbox-removal-waits-a-bounded-time-for-the-sync-guard-and-answers-busy.md` (the date is the day it is written; `area: [backend]`, `supersedes: []`, standalone). Its Context references `[[2026-11-10-mailbox-removal-is-one-transaction-that-also-writes-sync-status]]` and `[[2026-11-02-mail-oauth-rotation-holds-the-credential-lock-through-refresh]]` (the existing `lock_timeout` pattern) and says it decides what the first left open without editing it. The Decision states the bound, the answer, that a removal which today succeeds after a wait of 15 to 60 s now answers 409 and must be repeated, why the bound is below the statement timeout (a lock timeout is told apart from any other cancelled statement and rolls back with nothing written), that the sync pass's wait is not bounded, that the removal can wait for a pass of another mailbox (the pass holds its own guard while it waits for the tenant's mail-thread mutation guard) and so a busy answer does not mean this mailbox is syncing, and the READ COMMITTED precondition of the guard with the reason (a lock taken outside a READ COMMITTED transaction would not order the removal against a pass that committed while it waited). It claims no deadlock freedom beyond the lock order of the removal ADR.
5. Tests, in `__tests__/mailboxRemoval.test.ts` (runtime-role pool; the existing harness holds the guard with a second transaction):
   - a second transaction holds the guard (`lockMailboxSync`) and `removeMailbox(..., { syncWaitMs: 300 })` rejects with `MailboxSyncBusyError` (status 409, code `mailbox_sync_busy`) after about that wait; every row of the mailbox (item, credential, account and folder sync state, server settings) equals its snapshot before the call, and no removal job and no cleanup call was made; after the holder ends, the same removal succeeds;
   - the route handler answers 409 with `code: "mailbox_sync_busy"` in the same situation;
   - the guard released within the wait lets the removal succeed (the existing "waits holding no row lock" case still passes with the default bound);
   - `lockMailboxSync` with `maxWaitMs` leaves `current_setting('lock_timeout')` as it was once the lock is granted (a test reads it in the same transaction); without the option it does not touch the setting;
   - `lockMailboxSync` throws before any query when the client is outside a transaction and when the transaction is REPEATABLE READ (a test begins one by hand), and still throws `TenantScopeMissingError` outside a tenant scope;
   - the sync pass cases of the existing file (an IMAP, a Gmail and a Graph pass against a removal) pass unchanged.

## Scope

### In scope

- A bounded wait for the sync guard in the removal, its busy answer, and the transaction check of `lockMailboxSync`.

### Out of scope

- The sync pass's own wait for the guard, and any change to what a pass holds while it waits for the tenant's mail-thread mutation guard.
- Discovery inserting a sync state row for a removed mailbox: a separate source.
- A `Retry-After` header or any new field of the 409 body beyond the existing error envelope.
- The pool's `statement_timeout`, and the generic `DELETE /api/items/:id` of a Mailboxes item (#2031).
- The cleanup after the commit (#2030).

## Acceptance criteria

- When the sync guard of the mailbox is still held after the bound, then the removal fails with 409 `mailbox_sync_busy`, writes nothing and runs no cleanup, and a repeated request succeeds once the guard is free.
- When the guard is released within the bound, then the removal succeeds exactly as before.
- When the removal got the guard, then the transaction's `lock_timeout` is what it was before the call, and the removal's later row locks are not bounded by it.
- When `lockMailboxSync` is called outside a READ COMMITTED transaction of the active tenant, then it throws before it locks anything.
- A sync pass keeps its unbounded wait for the guard.
