## Context

Model tier rationale: This adds a persisted snapshot written in the same transaction as destructive approval creation at two separate call sites, with impact counts computed over tenant data and a localisation contract that clients, results and pushes all depend on, so a mistake is both wide and hard to correct after rows exist.

Product behavior: an approval request tells the user in plain words what Semp wants to do ("Delete the task 'Tax return - documents' in the Tasks database", "Delete the property 'Mood' in Journal - clears values on 214 items") and what the action will affect, in the user's language, and the text never changes after the fact.

Today `approval_requests` (migrations 0021, 0022, 0044) stores `tool_name`, `risk_class`, `payload`, `resource_snapshot` and `execution_status` only. `createPendingApprovalRequest` in `backend/packages/data/src/mcp/approvalRequestsStore.ts` takes `agentRunId`, `toolName`, `riskClass`, `payload` and `resourceSnapshot`; it is called from `preflightDestructiveApproval` in `backend/packages/application/src/genericOperationGateway.ts` (the five destructive generic operations) and from `createApprovalGatedMcpInvokeTool` in `backend/packages/agent-runtime/src/mcpInvokeTool.ts`. Operation inputs are strict (`ItemDeleteInputSchema {itemId}`, `PropertyDeleteInputSchema {propertyId}`), so a client cannot derive names or counts from the request. `databases.name` and `databases.key` exist; the key is canonical and lets a client choose the word and its grammatical form. The backend does not know singular forms or declension of a database name and must not try. Users have `users.locale`.

This issue builds on #1618 (the request linked to its tool call, which shares the two creation call sites). #1729, #1728, #1791, #1846, #1785, #1730, #1772, #1773, #1913 and #1713 read or extend the description.

Decision: the description stores a template key and parameters, never rendered text. Clients and push notifications render it from the user's locale catalogs. Rows created before this migration have `description` NULL and clients fall back to the operation label.

Decision: parameters contain names and counts taken at the moment of the request; later renames or data changes do not alter them.

Decision (product owner): the impact on linked items (`linkedCount`, and `endsInheritance` once the value-link work fills it) applies to requests raised by Semp too; the approval card in a Semp chat shows it, so Semp never ends a link silently. The description is returned on the queue entry and the decision view for every source.

Decision (product owner): an approval description never carries argument values. This issue's `approval.mcpInvoke` carries only `{serverName, toolName}`. The owner sees the values of an MCP request only in the detail of that one request, which is #2021.

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_approval_requests_description.sql` (next free ordinal at commit time): `ALTER TABLE approval_requests ADD COLUMN description jsonb NULL` (expand only; no backfill, no CHECK).
2. Define the description type in `approvalRequestsStore.ts`: `{key: string, params: Record<string, string | number | null>, endsInheritance?: Array<{itemId: string, propertyKey: string, sourceName: string}>}`, validated at the row read. Add `description` to `ApprovalRequest` and to `CreatePendingApprovalRequestInput`; `createPendingApprovalRequest` writes it.
3. Compute the description in the same transaction and client as the insert, in both call sites, with a shared builder module (for example `backend/packages/data/src/mcp/approvalDescription.ts`). Templates and params:
   - `approval.itemDelete {itemName, databaseKey, databaseName, projectName?, linkedCount, restorableDays}` (`linkedCount` = items related to the deleted item; `restorableDays` = the trash retention in days);
   - `approval.propertyDelete {propertyName, databaseKey, databaseName, affectedCount}` (`affectedCount` = items with a value in that property);
   - `approval.databaseArchive {databaseName, affectedCount}`;
   - `approval.viewDelete {viewName, databaseName}`;
   - `approval.relationDelete {fromItemName, fromDatabaseKey, toItemName, toDatabaseKey}`;
   - `approval.mcpInvoke {serverName, toolName}`.
   Template keys are English camelCase; `endsInheritance` is omitted in this issue (the value-link work fills it later).
4. Return `description` in the queue entry and decision view (`approvalRequestsQueue.ts`), as `null` for old rows.
5. Add the English and Czech catalog entries for the six templates where the client and push renderers read them, parameterised exactly as above, and document the template contract in a code comment next to the builder.

## Scope

### In scope

- The `description` column, its type, the six template builders, the two creation call sites and the read projections.

### Out of scope

- The agent's stated reason: #1420.
- The risk level and reversibility badges: #1730.
- The `approval.breaksLink` template, `endsInheritance` content and module tool templates: #1713 and #1791.
- Rendering to text on the server (clients and push render from the catalogs).
- Searching descriptions: #1785.
- Argument values in any description.

## Acceptance criteria

- When a `property.delete` request is created, its description has key `approval.propertyDelete` with `propertyName`, `databaseKey`, `databaseName` and `affectedCount` equal to the number of items with a value at that moment; changing data or renaming the property afterwards does not change the stored description.
- When an `item.delete` request is created, its description carries `itemName`, `databaseKey`, `linkedCount` and `restorableDays`.
- The description holds names and the canonical database key, never ids as display values.
- A request row created before the migration returns `description: null` and every other field unchanged.
- The row insert and the description are in one transaction: when the destructive preflight throws, no row exists.
- The Czech and English clients render the same row from the same stored description (both catalogs contain all six templates).
