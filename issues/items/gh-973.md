## Context

After #972, every table classified `semprec:tenancy=tenant` (43 tables, by table comment, #971) has `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)`. #968 created the functions involved:

- `app_current_tenant()` returns `NULLIF(current_setting('app.tenant_id', true), '')::uuid`.
- `app_sole_tenant()` returns the only tenant's id, or NULL.
- `app_tenant_default()` returns `COALESCE(app_current_tenant(), app_sole_tenant())`. This definition is transitional.

#968 also created the `tenants_single_tenant_guard` index, which keeps the deployment at one tenant until go-live.

This issue switches on the database half of isolation, as recorded in the tenancy ADR from #968:
- RLS is enabled on every tenant table.
- A **RESTRICTIVE** policy `tenant_isolation`: `USING (tenant_id = (SELECT app_tenant_default())) WITH CHECK (tenant_id = (SELECT app_tenant_default()))`.
- A **PERMISSIVE** policy `tenant_rows`: `USING (true) WITH CHECK (true)`. RLS denies everything without some permissive policy. The isolation policy is restrictive, so no permissive policy added later can widen it.
- **No `FORCE ROW LEVEL SECURITY`.**

While one tenant exists and no scope is set, the policy resolves to the sole tenant, so the previous release and all scope-less code behave as today. Nothing changes in production on deploy:

- **Tables and migrations.** Every table is owned by the migrating superuser, and owners and superusers bypass RLS.
- **Runtime roles.** `semprec_data` and `semprec_side` (`backend/packages/data/src/db/migrations/0040_least_privilege_roles.sql:33-89`) see tenant zero's rows, which are all rows.
- **Backups.** `pg_dump` runs as `$POSTGRES_USER`, the compose superuser (`deploy/systemd/scripts/semprec-backup.sh:47`). The restore test queries and restores as `postgres` (`deploy/systemd/scripts/semprec-restore-test.sh:104,149`).
- **The relation-cardinality trigger.** `enforce_relation_cardinality` (`0013_relation_cardinality.sql:23-63`) is `SECURITY INVOKER`. Its lookups therefore run under the caller's policy, which is the same tenant.
- **The partition DDL functions.** `create_items_partition` and `drop_items_partition` (`0048`, `0050`) are `SECURITY DEFINER`. Their tenant check is #1021.

RLS on the partitioned `items` parent does not cover a query that addresses an `items_p_*` partition directly. Those partitions are created by the migrating role, or by the definer function, and receive no grant: 0040 grants named tables only, and 0047's default privileges cover sequences only (`0047_side_role_default_sequence_privileges.sql:13-14`). This issue pins that in the catalog test.

Superuser test pools bypass RLS, so the existing suites are unaffected. Isolation must be proven under a runtime role.

## Acceptance criteria
- Every tenant-classified table has RLS enabled and not forced. Its only policies are the restrictive `tenant_isolation` and the permissive `tenant_rows`, both `FOR ALL TO PUBLIC` (integration, `tenancyCatalog.test.ts`).
- Neither runtime role is superuser or `BYPASSRLS` or owns a table in `public`, and neither holds any privilege on any `items_p_*` partition (integration, `tenancyCatalog.test.ts`).
- With one tenant and no `app.tenant_id`, both runtime roles see every seeded row. `semprec_data` inserts, updates and deletes through the choke point's tables exactly as before, and new rows get tenant zero (integration, `rowLevelSecurity.test.ts`).
- With `app.tenant_id` set to a second tenant:
  - `SELECT count(*)` on every tenant-classified table returns 0 for both roles;
  - an `UPDATE` or `DELETE` of a tenant-zero row affects 0 rows;
  - an `INSERT` naming `tenant_id` = tenant zero fails with SQLSTATE `42501` (row-level security violation).

  (integration)
- With two tenants and no `app.tenant_id`, both roles see no rows of either tenant, and a scope-less insert is refused. The previous release behaves this way once a second tenant exists without scope (integration).
- On one dedicated client running as `semprec_data` (session-level `SET ROLE`, reset before release), a committed transaction that set `app.tenant_id` locally to a random uuid sees 0 rows inside it, and the next statement after its `COMMIT` sees tenant zero's rows again, because the setting then reads `''` (integration).
- The existing integration suite, including `leastPrivilegeRoles.test.ts`, passes unchanged (integration).
