## Context

The backend integration tier is 143 `*.test.ts` files that `backend/vitest.integration.config.ts` runs with `fileParallelism: false` against one embedded Postgres, about 13 minutes wall-clock. `.github/workflows/ci.yml` runs it as the single `integration` job (`timeout-minutes: 20`), so the tier is the slowest required check by a factor of two and the one closest to its timeout, and Relay's `merge-pull-request` re-runs `verify` (which includes the tier) up to three times per issue. vitest supports splitting one run's file list across processes with `--shard=<index>/<count>`; every shard is its own vitest process, so `packages/data/src/testSupport/globalSetup.ts` gives each its own Postgres on a kernel-chosen free port (`choosePort`) — no backend code change is needed to run three shards on three runners.

The `integration` status check context is required on `develop` and `main` (`docs/operations/required-checks.md`), waited on by Relay (`.relay/workflows/merge-pull-request.md` `wait-checks` `names:`) and checked by the release command (`backend/packages/release/src/releaseTag.ts` `REQUIRED_CHECKS`). A matrix job reports one context per shard (`integration (1)`, …), so the shards must run under another job id and a fan-in job must keep reporting `integration`.

**Protected path — maintainer-implemented.** This issue edits `.github/workflows/ci.yml`, which is under `.relay/config.yml`'s `protected-paths`; Relay's `guard-paths` step blocks such a run and `merge-pull-request` waits on the `protected-paths` check. It is labeled `spec:approved` only, never `agent:ready`, and a maintainer opens the pull request. Sibling issue #656 of this batch (teardown of an interrupted run) is backend code and independent of this one.

## Task

- In `.github/workflows/ci.yml`:
  - Rename the existing `integration` job to `integration-shard` and give it `strategy: { fail-fast: false, matrix: { shard: [1, 2, 3] } }`, `timeout-minutes: 12`, and change its last step to `run: pnpm run test:integration --shard=${{ matrix.shard }}/3` (pnpm forwards the flag to `vitest run`). Keep the ffmpeg install step and its comment; update the job comment to say the tier runs as three shards, each with its own ephemeral Postgres.
  - Add a job `integration` with `needs: integration-shard`, `if: ${{ always() }}`, `runs-on: ubuntu-latest`, `timeout-minutes: 2`, and one step that exits 0 only when `needs.integration-shard.result == 'success'` (read the result through `env`, never interpolated into the script; `exit 1` with an `::error::` line naming the failed result otherwise). Comment on the job: it exists so the required context keeps the name `integration` while the work runs in the matrix above; renaming it is a branch-protection contract change (`docs/operations/required-checks.md`).
  - No other job changes; `permissions`, `concurrency` and the pinned action versions stay as they are.
- In `docs/operations/required-checks.md`, update the `integration` row's "Produced by" text: job `integration`, a fan-in over the `integration-shard` matrix (three vitest shards, each against its own ephemeral PostgreSQL).
- `.relay/workflows/merge-pull-request.md`, `backend/packages/release/src/releaseTag.ts` and branch protection need no change — the required context name is unchanged; state that in the pull request description.
- Tests: none in the repository (a workflow change); the pull request's own CI run is the check — its `integration-shard (1)`, `(2)`, `(3)` and `integration` checks must all be green and the three shards together must run the same test files one serial run does (compare the summed "Tests" counts in the three shard logs with a `develop` run's).

## Scope

### In scope

- The three-way matrix for the integration tier and the fan-in job that preserves the `integration` required context.

### Out of scope

- Any backend code change (`globalSetup.ts`, `vitest.integration.config.ts`) — none is needed; the interrupted-run teardown is sibling issue #656.
- Sharding the `e2e` job, or running test files in parallel inside a shard.
- Changing branch protection, `.relay/**`, or `releaseTag.ts`.
- Caching `pnpm install` or the ffmpeg apt step across shards.

## Acceptance criteria

- When a pull request is opened after this change, its checks include `integration-shard (1)`, `integration-shard (2)`, `integration-shard (3)` and `integration`; `integration` is green only when all three shards are, and red (not skipped) when any shard fails or is cancelled.
- When the three shard logs' vitest summaries are added up, the file and test counts equal those of one unsharded `pnpm run test:integration` on the same commit.
- Each shard finishes in under 8 minutes on the GitHub-hosted runner (the whole tier under the previous 13 minutes wall-clock).
- Branch protection on `develop` and `main`, `.relay/workflows/merge-pull-request.md` and `releaseTag.ts` are unchanged, and `docs/operations/required-checks.md` describes the new shape.
