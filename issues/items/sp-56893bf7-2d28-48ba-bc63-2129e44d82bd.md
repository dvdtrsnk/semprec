### Requirement gh-1972: [inbox-cards 05/10] Add POST /api/mcp-servers/:id/sync for human writers

#### Context

Model tier rationale: One new human-only route over an existing, tested sync function, plus the route-matrix and tenant-isolation entries every route needs; the outbound connection and error mapping are already handled by the sync code.

`syncMcpServerTools` (`backend/packages/data/src/mcp/mcpSync.ts`) connects to a stored MCP server, lists its tools, validates the list and materializes `mcp_tool_registrations`, recording `syncStatus` (`ok` or `error`), `lastSynced` and `syncError` on the server item. It is exported from `backend/packages/data/src/index.ts` and deliberately has no agent or `/mcp` operation. Today nothing calls it: there is no HTTP route, so a user who connects a server has no way to load its tools. Outbound connections already go through the connect-time address check (`docs/adr/2026-10-16-connect-time-outbound-address-checks.md`) and a stdio server is refused unless the tenant allows it.

The "Tools" block of a project's AGENT page lives in `backend/services/semprec-api/src/mcpAgentPageHandler.ts` (`GET`/`PATCH /api/projects/:projectItemId/mcp-grants`, `PATCH /api/mcp-tool-registrations/:id`), mounted by `app.ts` as the fallback listener. MCP servers have no module manifest, so a manifest custom route cannot own a route for them; the route is added by hand next to the MCP grants routes and needs its entries in `backend/services/semprec-api/src/routeMatrix.ts` and `backend/services/semprec-api/src/__tests__/tenantIsolationRoutes.test.ts`. The route is a prerequisite of #1976, which queues the same sync after an MCP server card is confirmed, and of the tool-label and default-classification work that runs during sync (#1979, #1983). It is ordered after #1963 because both add entries to the route matrix and the tenant isolation test.

Decision: the route runs the sync inline in the request (it is bounded by the connection factory's timeouts) and answers with the result; there is no job in this issue.

Decision: a connection failure answers 502 `{ error, reason }` where `reason` is the typed `McpConnectionError` reason, a tool-list validation failure keeps its 400 `validation_failed`, and in both cases `syncStatus: error` and `syncError` have already been recorded on the server item by the sync function.

Decision: only a signed-in human session can call it. Agents, run credentials and the `/mcp` endpoint have no path to it.

Shared-file ordering: this issue also waits for #1967 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

It authenticates with `authenticateRequest`, runs inside `runInTenant(identity.tenantId, ...)`, and calls `syncMcpServerTools(pool, id, { actorId: identity.user.id })`.
2. Success returns 200 `{ toolCount, syncStatus: "ok" }`. A server id that does not exist in the caller's tenant (including another tenant's id) returns the same 404 as an unknown id.
3. Map `McpConnectionError` to 502 as in the Decision; keep the existing `ChokePointError` mapping for the rest. The response never contains a secret or the server's own error text.
4. Add the route to `ROUTE_MATRIX` in `routeMatrix.ts` (`surface: "api"`, `public: false`, `tenancy: "tenant"`) and a handler in the `tenantIsolationRoutes.test.ts` table that proves a foreign id answers like a random id and leaves tenant A's data unchanged.

Tests in `backend/services/semprec-api/src/__tests__/mcpAgentPageHandler.test.ts`: an unauthenticated call is refused; a call against a test MCP server with two tools returns `toolCount: 2` and creates two registrations; an unreachable server returns 502 and the item shows `syncStatus: error`; an unknown id returns 404.

### Requirement gh-1976: [inbox-cards 06/10] Queue an MCP tool sync after confirming an MCP server proposal

#### Context

Model tier rationale: One new core queue task enqueued in an existing transaction, following the established approvalExecute pattern, with an outbound call that already goes through the connect-time address check; the failure and retry semantics are the part to get right.

Confirming an Inbox card that proposes an MCP server creates the `mcpServers` item and stores the optional credential in the same transaction (`confirmProposalWithClient` in `backend/packages/data/src/inbox/proposalActions.ts`, credential through `storeCredential`). Nothing then loads the server's tools, so the new server has no `mcp_tool_registrations` and the user would have to find and press a separate button. #1972 adds the human route that runs `syncMcpServerTools` (`backend/packages/data/src/mcp/mcpSync.ts`); this issue runs the same sync automatically after the confirm.

The side effect follows the commit (`docs/adr/2026-09-10-side-effects-follow-the-commit.md`): the confirm transaction enqueues a queue job, and the job runs after the commit, so the sync never sees an uncommitted server or credential and never blocks the confirm. Core tasks are declared in `CORE_TASK_NAMES` and `CORE_TASK_AFFINITY` of `backend/packages/queue/src/index.ts` and given a handler in `createCoreTaskList` (`backend/packages/data/src/worker.ts`); `approvalExecute` is the model (`decideAndEnqueueApprovalRequest` enqueues with a derived `jobKey`). The sync records `syncStatus` (`ok` or `error`), `lastSynced` and `syncError` on the server item through the choke point, which also announces the change to connected clients. Later issues build on the job key: the tool-annotation defaults (#1979), the tool-label suggestions (#1983) and the cancellation of follow-up jobs when a confirmation is undone (#1984). The job never writes project grants: the user grants tools on the project's AGENT page (#1382).

Decision: the task is `mcpServerSync` with payload `{ mcpServerItemId, actingUserId }`, runtime affinity `api`, and the stable job key `mcp-server-sync-<mcpServerItemId>`, so a second enqueue for the same server collapses onto the pending job.

Decision: no queue retries (`maxAttempts` 1). A failed sync is already recorded as `syncStatus: error` with a safe `syncError`, so the handler swallows a recorded `McpConnectionError` or tool-list `ValidationError`; the user retries through the route of #1972. An unexpected error still throws.

Decision: the enqueue happens for any confirm that creates an `mcpServers` item, with or without a credential (servers with browser-based authorization have none).

Transferred atomic result obligation from #1648: after the actual enqueue succeeds, persist followUp:mcpSyncQueued on its matching executed-step result in the SAME confirmation transaction. Enqueue, result and card/resources roll back together. Already-confirmed replay returns unchanged stored results and enqueues nothing. See [[2026-11-03-confirm-results-report-only-enqueued-follow-ups]]. This future producer is not authorized for implementation during batch21.

In `mcpSync.ts` add `enqueueMcpServerSync(client, { mcpServerItemId, actingUserId })` using `enqueueJob` with the job key above and `maxAttempts: 1`, and `handleMcpServerSyncTask(pool, payload)` that calls `syncMcpServerTools(pool, mcpServerItemId, { actorId: actingUserId })` and swallows only the recorded failure types. A server item that no longer exists is a no-op.
3. Register the handler in `createCoreTaskList` in `worker.ts` (`requireString` on both payload fields) and make sure `createApiQueueRuntime` still passes its affinity check.
4. In `confirmProposalWithClient`, after the item is created and the credential stored, call `enqueueMcpServerSync` when the target database is `mcpServers`. Pass the acting user from the confirm route (`createConfirmProposalRouteHandler` in `inboxRouteHandlers.ts` reads it from the request identity) as a new optional parameter.
5. Export what the other packages need through `backend/packages/data/src/index.ts`.
6. Tests: the job exists after the confirm commits and not when the confirm rolls back; confirming twice leaves one pending job; running the handler against a test MCP server registers its tools and sets `syncStatus: ok`; against an unreachable server it records `syncStatus: error`, does not throw and is not retried; a confirm for a non-MCP target enqueues nothing; the credential is never part of the payload.

### Requirement gh-1984: [inbox-proposals 18/19] Cancel follow-up jobs when a confirmation is undone

#### Context

Model tier rationale: Cancels asynchronous work across processes whose state may already have advanced (running, finished, or half-written), where a race leaves orphan items or double execution.

A confirmation can queue follow-up work: a transcription job for an uploaded recording, and a tool sync for a newly connected MCP server. #1943 reopens a confirmed card and reverses its synchronous writes, but a job queued by the confirmation would still run afterwards and recreate what the undo removed.

- The transcription job is keyed `transcription-job:<fileItemId>` (`backend/packages/data/src/transcription/transcriptionJob.ts`, `transcriptionJobKey`, `findTranscriptionJobId`) and creates the Transcripts item only when it runs, so before it runs there is nothing to remove, and after it ran there is a Transcripts item to soft-delete.
- #1978 adds the confirmation that queues that transcription, and #1976 queues the MCP tool sync after an MCP server proposal is confirmed. Both record `followUp` (`transcriptionQueued`, `mcpSyncQueued`) in the card's `results[]` (#1648).

Decision: cancellation is best effort for a job that is already running: the undo marks the job cancelled and soft-deletes whatever it already created; a job that finishes later finds its input gone and completes as a no-op (the job handlers re-check their source item). A speaker mapping needs nothing here, since deleting the edge in #1943 is the whole undo.

#### Task

Load `state-writes`, `error-handling` and `testing`.

1. In the reopen-from-`confirmed` transaction of #1943, for every `results[]` entry with `followUp`:
   - `transcriptionQueued`: remove the queued job by its key if it has not started; if a Transcripts item already exists for the file, soft-delete it (and let the file's own removal follow the item's step as already reversed).
   - `mcpSyncQueued`: remove the queued sync job for the server item if it has not started; if it already ran, the tool registrations it wrote are removed with the soft-deleted server item by the existing server-removal hook.
2. Make the job handlers (transcription job and MCP sync) return without writing when their source item is soft-deleted or gone.
3. Use the jobs' existing enqueue-in-transaction helpers' inverse so that the job removal is part of the same transaction; do not add a new job table.
4. Tests: undo before the worker picks up the job removes the job; undo after a finished transcription soft-deletes the Transcripts item; a handler invoked after the undo writes nothing; undo of a card with no follow-up touches no job.

- backend/packages/data/src/inbox/__tests__/ (follow-up cancellation tests)

##### Out of scope

- When it is undone after the transcription finished, then the Transcripts item is in the trash.
- When a transcription or MCP sync handler runs for an already removed source item, then it completes without writing.
- When the confirmation queued no follow-up, then no job is touched.

### Requirement gh-1977: [inbox-core 21/22] Seed the default Inbox item type catalog per tenant

#### Context

Model tier rationale: It writes user-visible data into every tenant once and must never bring back a type the user deleted or edited, which needs a persisted marker and exact idempotency across fresh provisioning and the repeated per-deploy cutover; a mistake duplicates or resurrects data in all tenants.

A tenant starts with no Inbox item types (`seedInboxPipelineInTransaction` creates the database empty), so the type picker in the capture UI is empty and an item can only be typed after the user has created types by hand. The product has a fixed starting set: Idea, Task, Event, Thought, Mood, Note and Contact, each with an emoji. This issue creates them, using the validation of #1436, the target list as extended by #1973 and the journal processing method of #1975. Other issues build on the existing catalog: the voice-note transcription (#1980).

Types are items of the Inbox item types database (`name`, `emoji`, `status`, `processingMethod`, `targetDatabase`). `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`) runs for every maintained tenant on every deploy, so a seeding step there must be idempotent and must remember which defaults it already created, or a type the user deleted or renamed would reappear at the next deploy. `provisionTenant` (`backend/packages/data/src/tenancy/provisionTenant.ts`) seeds a new tenant without running the cutovers, so a new tenant needs the same seeding on its own path.

Decision: the defaults are

| key | English name | Czech name | emoji | processingMethod | targetDatabase |
|---|---|---|---|---|---|
| idea | Idea | Nápad | light bulb | pageContent | none |
| task | Task | Úkol | check mark | database | tasks |
| event | Event | Událost | calendar | database | events |
| thought | Thought | Myšlenka | thought balloon | journalEntry | none |
| mood | Mood | Nálada | smiling face | journalEntry | none |
| note | Note | Poznámka | memo | pageContent | none |
| contact | Contact | Kontakt | bust in silhouette | database | people |

The key is a stable English camelCase identifier of the default, used only by the marker below; it is not stored on the type. The emoji column names the Unicode character to store in `emoji`. The targets of Idea, Thought and Mood are proposals (decided by the product owner): they are seeded as listed and can be changed later through the type write path without touching this seed.

Decision: the marker is per default, not one flag: a system-owned `json` property `seededDefaultInboxTypes` on the System settings item holding the list of keys already seeded. The cutover adds the property with raw SQL if it is missing (the settings database is `schema_locked`; see the `transcriptsCatalogCutoverMigration.ts` shape). The seeding creates only the defaults whose key is not in the list and appends their keys in the same transaction. A type the user deleted or renamed is therefore never re-created, and a tenant whose types were all deleted is not re-seeded. A module added later that brings its own default type adds one row to the table; existing tenants then receive that one type once at the next deploy, and nothing else changes.

Decision: names use the locale of the tenant's user when one exists, otherwise Czech; `status` is written as `active` explicitly. The locale is fixed at seeding time.

Decision: a default whose target database does not exist in the tenant is skipped and its key is not recorded, so it is created at the first run after that database exists. All seven defaults above target databases that every tenant has.

### Requirement gh-1980: [inbox-attachments 07/08] Transcribe short voice notes into transcribedText

#### Context

Model tier rationale: It adds a system-owned property to a schema-locked database for all tenants and a new cross-process write into the Inbox from the media process, with single-writer ownership and a gateway audio call that must stay idempotent.

A short voice note ("at the doctor: blood pressure 135/85, measure it for two weeks") should become the text of the Inbox item so the assistant can read it and the card can quote it. Today the Inbox has `text`, which the person owns (`backend/packages/data/src/seed/seedInboxPipeline.ts`), and the single-writer rule (`docs/adr/2026-09-10-single-writer-ownership-model.md`) forbids the server from writing it. Audio is transcribed only for Files items (#1965 classifies an audio attachment as `voiceNote` below `INBOX_RECORDING_MIN_SECONDS`, `recording` at that boundary or longer). `semprec-transcribe` already calls the gateway's transcription route through `audioGatewayClient.ts`.

This issue adds the system-owned property `Inbox.transcribedText` and a job that fills it from the voice-note attachments. The assistant reads `text ?? transcribedText`; that choice, and the fingerprint, are made by #1987 and #1606.

Decisions:
- `transcribedText` is a `text` property, owner `system`, owner process `transcribe` (`TRANSCRIPTION_OWNER_PROCESS`), with the Czech label "Přepis" and English "Transcribed text".
- The job collects every `voiceNote` attachment of the item in position order and writes their transcripts joined by a blank line; it is keyed per Inbox item and replaces itself, so a second attachment re-runs it over all.
- A transcript is written even when `text` is non-empty; `text` is never changed.
- A recording at or above the shared threshold of #1965 is not transcribed here (#1985).

Add the per-tenant cutover `backend/packages/data/src/seed/inboxTranscribedTextCutoverMigration.ts` (raw SQL after `LOCK TABLE properties IN EXCLUSIVE MODE`, pattern `transcription/transcriptsCatalogCutoverMigration.ts`; skips a missing Inbox database or an existing property), registered in `runTenantCutoverMigrations`.

Unchanged text writes nothing. A gateway failure fails the job for retry and never alters `text`.

### Requirement gh-1987: [inbox-core 22/22] Pass capture time, timezone and bounded workspace context into proposal computation

#### Context

Model tier rationale: It decides which of a user's records leave the database for a model call, including the rule that sensitive databases are excluded without a grant, and it bounds the request under a hard size limit; a mistake leaks data or breaks every proposal.

The computation built by #1434 sends the model the item's text and the target database's properties, and nothing else. It cannot resolve "tomorrow at 9", cannot pick an existing project, person or company by id, and cannot say "you had no meeting then". The Inbox item carries `date` and `time` (the user's wall clock at capture) and, after #1964, `captureChannel`; the text of a voice note is stored in `transcribedText` by #1980. The tenant timezone is read by `getSystemTimezone` (`backend/packages/data/src/systemSettings.ts`). Databases can be marked sensitive (#1808, for example health records), and per-database grants for a project are enforced in the data layer by #1810. ### Requirement gh-1991: [inbox-proposals 19/19] Reject derived relations in proposal envelopes

#### Context

Model tier rationale: A narrow validation rule reusing an existing choke point predicate at the envelope validation point, with a small number of known databases, within existing fixtures and no new lifecycle or authorization contract.

Some relation values are derived and not the user's to set when an item belongs to a project: the company of an event and the area of a file (and, later, of other items) are inherited from the project, so the choke point refuses to write them on an item that has a project (#1662). A proposal is validated before anything is written, so without a matching rule a card could offer such a relation, let the user confirm, and fail only at confirm time with a confusing error. The envelope's `relations` field and its validation exist from #1426. The journal card kinds and entity kinds added in #1419, #1975, #1981 and #1982 must not trip on the new rule.

Decision: the proposal-side rule reuses the choke point's predicate from #1662 (if it is not exported, export it instead of duplicating the rule table). An envelope for a database whose relation `X` is derived is rejected with a `ValidationError` (`details.field` = the relation key, `code: "derivedRelation"`) when `relations.X` is non-empty and the envelope also sets a project relation. Values inherited from the project may still be proposed as the item's own values when no project is set. Decision (product owner): a journal entry may carry an area like any other item: with a project the area is derived, without a project it is the entry's own value. A `journalEntry` envelope that sets both `projectId` and `areaId` is therefore rejected with a `ValidationError` (`details.field` = `area`, `code: "derivedRelation"`), and one with only `areaId` is valid.

2. Tests: an Event envelope with `relations: { project: [<id>], company: [<id>] }` is rejected on `company`; an Event envelope with only `company` is accepted; a File envelope with `project` and `area` is rejected on `area`; an envelope for a database with no derived relations is unaffected; a `journalEntry` envelope with `projectId` and `areaId` is rejected on `area` and one with only `areaId` is accepted; the check also runs on revise and on the edit route (through the shared validator).
