**Blocked by:** #1021, #1049
**Model tier:** medium

## Context

Model tier rationale: Every purge step, lock and order is pinned, but the chunked destructive sweep and its wide two-tenant fixture still need a stronger worker than transcription.

After a deletion request (#1049) the tenant is `deleting`:

- every session and push registration is revoked;
- its `tenant_keys` row is gone (crypto-shred);
- every process has dropped its in-memory state for it;
- its queued jobs complete as no-ops.

This issue erases what remains (every row, item partition and stored file) and leaves only a PII-free tombstone. A backup restore replays the tombstones (#1078).

Facts the purge must respect:

- **Tenant tables.** They carry `tenant_id` and the comment `semprec:tenancy=tenant`, and row-level security limits every query to the current scope (`runInTenant(tenantId, fn)` from `@semprec/shared`).
  - `items` is partitioned per database (`backend/packages/data/src/db/migrations/0001_core_schema.sql`, `PARTITION BY LIST (database_id)`) and no foreign key references it; item ids are application-enforced.
  - Partitions are dropped through `drop_items_partition(uuid)` (`0050_drop_items_partition_function.sql:20-29`). That function takes an `ACCESS EXCLUSIVE` lock on the partition and on `items` for the rest of the transaction (`:9-11`), and since #1021 it refuses a database outside the current tenant.
- **Foreign keys across planes.** Tenant rows reference the global `users` (`notifications.user_id`, `approval_requests.decided_by`, `agent_runs.actor_user_id`, `project_agent_guidance.owner_user_id`, `resource_grants.grantee_user_id`). The tenant table `push_deliveries` references the global `push_subscriptions` (`0032_push_deliveries.sql`). The global `agent_run_mcp_credentials` (which carries `tenant_id` since #994) references `agent_runs` (`0043_agent_run_mcp_credentials.sql`). `agent_runs.parent_run_id` is self-referencing.
- **Identity rows.** They live in global tables: `users`, `sessions`, `push_subscriptions`, `password_reset_tokens`, `login_attempts` (keyed by email, no FK; `0025_auth_schema.sql:37-43`), `invites` (email; `invited_by … ON DELETE SET NULL`, #1040) and `tenant_ai_budgets` (`tenant_id … ON DELETE CASCADE`, `updated_by … ON DELETE SET NULL`; `semprec_data` has no `DELETE` on it, #1004). `admin_audit_log` keeps ids only and has no FK; it stays.
- **Blob bytes.** They live under `FILES_STORAGE_DIR` or, for blobs referenced by `mail_attachments.blob_id`, under `MAIL_ATTACHMENTS_DIR` (`resolveBlobStorageDir`, `backend/packages/data/src/mail/blobStorage.ts:62`). `LocalFsBlobStorageWriter.delete` is an idempotent `rm(…, { force: true })` (`:123-125`). Since #1008, new keys are prefixed `<tenantId>/`. Export archives live at `tenant_exports.storage_key` in the files root (#1043).
- **Byte-deletion order.** `docs/adr/2026-09-28-blob-bytes-deleted-best-effort-after-the-commit.md` deletes the row first and the bytes after the commit, skipping failures. It states that a hard erasure requirement needs a different decision. Account deletion is such a requirement: here the bytes go **first**, and a failure stops finalisation. The tenant is unreachable, so a row pointing at missing bytes harms nobody.
- **Queue internals.** Queued jobs carry the tenant in their envelope (`payload->>'tenantId'`). Removing rows follows `backend/packages/data/src/observability/queueFailedJobsPrune.ts`: it reads `graphile_worker._private_jobs … FOR UPDATE SKIP LOCKED` and deletes through `graphile_worker.complete_jobs`, pinned to graphile-worker 0.17.x.
- **Sweep conventions.**
  - Task wiring uses `CORE_TASK_NAMES` / `CORE_TASK_AFFINITY` (`backend/packages/queue/src/index.ts:29-119`), with tasks declaring `tenancy` (#982), plus `createCoreTaskList` / `CORE_CRONTAB` (`backend/packages/data/src/worker.ts:81-227`).
  - Chunked commits follow `docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`.
  - A per-key try-lock on a dedicated connection follows `backend/packages/data/src/migrationJob/moduleDataMigration.ts:66-104`.
  - Shutdown follows `docs/adr/2026-09-30-graceful-shutdown-for-long-running-graphile-worker-tasks.md`.

## Task

Load `state-writes` (affected-row checks, chunked writes), `db-migrations`, `error-handling` (never report a purge that did not happen), `io-hardening` (dedicated lock connection released on every path) and `adr-conventions`.

1. **Migration** (take the next free migration ordinal at commit time; additive):
   ```sql
   CREATE TABLE tenant_deletions (
     tenant_id uuid PRIMARY KEY,
     requested_at timestamptz NOT NULL,
     completed_at timestamptz NOT NULL DEFAULT now()
   );
   COMMENT ON TABLE tenant_deletions IS 'semprec:tenancy=global';
   GRANT SELECT ON tenant_deletions TO semprec_side;
   GRANT INSERT ON tenant_deletions TO semprec_data;
   ```
   It holds no email, no user id and no content.
2. **Purge** — new `backend/packages/data/src/tenancy/tenantPurgeJob.ts`, with `handleTenantPurgeTask(pool, dirs: { files: string; mailAttachments: string }, helpers)`. In system scope it reads `SELECT id, status_changed_at FROM tenants WHERE status = 'deleting' ORDER BY status_changed_at`. For each tenant:
   - **Lock.** Take `pg_try_advisory_lock(hashtextextended('semprec_tenant_purge:' || $1, 0))` on a dedicated client held with `try/finally`. If it is not acquired, skip this tenant in this run.
   - **Steps.** Every remaining step runs inside `runInTenant(tenantId, …)`, uses an explicit `tenant_id = $1` predicate in addition to RLS, is idempotent, and is resumable after a crash.
     1. `DELETE FROM tenant_keys WHERE tenant_id = $1`.
     2. Remove the tenant's unlocked queued jobs (`payload->>'tenantId' = $1`) in the `queueFailedJobsPrune.ts` way.
     3. **Bytes.** Page the tenant's `blobs` rows by id, 500 at a time. Delete each key from its root (the mail root when a `mail_attachments` row references the blob, otherwise the files root), then every `tenant_exports.storage_key`, then `rm(join(root, tenantId), { recursive: true, force: true })` under both roots. Any failure throws for this tenant.
     4. **Partitions.** For each of the tenant's `databases` rows, run one transaction with `SET LOCAL lock_timeout = '5s'` and `SELECT drop_items_partition($1)`.
     5. **Rows.** Delete `agent_run_mcp_credentials WHERE tenant_id = $1` first. Then delete every table classified `semprec:tenancy=tenant` (`relkind IN ('r','p')`, not a partition), children before parents.
        - The order comes from the pure function `orderTablesForPurge(tables, foreignKeys)` in new `backend/packages/data/src/tenancy/tenantPurgeOrder.ts` (no database import), fed from `pg_constraint` (`contype = 'f'`). A self-referencing FK is allowed; any other cycle throws naming the tables.
        - Each table is deleted with `DELETE FROM <t> WHERE ctid = ANY(ARRAY(SELECT ctid FROM <t> WHERE tenant_id = $1 LIMIT 1000))`, repeated, one transaction per chunk, until 0 rows.
        - A table with a self-referencing FK is deleted in one statement, so the FK check sees the whole set. `items` is cleared by step 4, and a plain `DELETE … WHERE tenant_id = $1` must then affect 0 rows.
        - Quote table names with `pg`'s `escapeIdentifier`.
     6. **Finalise**, in one transaction:
        - Assert that no tenant table and no `agent_run_mcp_credentials` row still has `tenant_id = $1`; otherwise throw.
        - For the tenant's user U, delete `push_subscriptions`, `sessions` and `password_reset_tokens` of U, plus `login_attempts` and `invites` matching U's email.
        - Delete the `users` row (`requireAffectedRows` when U exists). `invites.invited_by` and `tenant_ai_budgets.updated_by` references to U are nulled by their `ON DELETE SET NULL`.
        - Insert `tenant_deletions(tenant_id, requested_at = tenants.status_changed_at)`.
        - Run `DELETE FROM tenants WHERE id = $1 AND status = 'deleting'` with `requireAffectedRows`. The tenant's `tenant_ai_budgets` row goes with it through `ON DELETE CASCADE`; do not delete it directly.
   - **Shutdown.** Between chunks, if `helpers.abortSignal?.aborted`, stop and return normally; the next run resumes.
   - **Failure isolation.** One tenant's failure does not skip the others. All failures are collected and rethrown together after the loop, so the run reports failure while every other tenant's progress stays committed.
   - **Logging.** Log only the tenant id and per-step counts, never content or the email.
3. **Wiring:**
   - Add `CORE_TASK_NAMES.TENANT_PURGE = "tenantPurge"` with `CORE_TASK_AFFINITY` `api` and `TASK_TENANCY` `system`, and add it to the system-name list asserted by #982's catalog case. It must be a system task: a tenant task of a `deleting` tenant completes as a no-op (#982), and `forEachActiveTenant` skips such tenants. The purge enumerates `deleting` tenants itself and enters each one explicitly with `runInTenant`.
   - Register the handler in `createCoreTaskList` with a new trailing parameter `tenantBlobStorageDirs = { files: resolveBlobStorageDir("FILES_STORAGE_DIR"), mailAttachments: resolveBlobStorageDir("MAIL_ATTACHMENTS_DIR") }`.
   - Add `* * * * * tenantPurge` to `CORE_CRONTAB`, and add `tenantPurge` to `EXPECTED_CRONTAB_IDENTIFIERS` in `backend/services/semprec-api/src/__tests__/queueRuntime.test.ts:12-24`. Add `tenant_deletions` to the grant-coverage exceptions in `backend/packages/data/src/__tests__/leastPrivilegeRoles.test.ts` (#962's assertion; `SELECT` only for `semprec_side`, no `UPDATE`/`DELETE` for `semprec_data`). The purge starts within a minute of a deletion request, and a crashed run is picked up by the next tick.
4. **ADR** `docs/adr/<YYYY-MM-DD>-tenant-purge-erases-outside-the-choke-point.md`. It cross-references `[[2026-09-28-blob-bytes-deleted-best-effort-after-the-commit]]` as a carve-out (it does not supersede it) and records:
   - bulk deletion outside the choke point for a tenant nobody can observe;
   - bytes before rows, with failures blocking finalisation;
   - catalog-driven FK ordering;
   - the per-minute sweep with a per-tenant try-lock;
   - the tombstone contents.

## Scope

### In scope
- The purge sweep, the tombstone table, and erasure of rows, partitions, files, queued jobs and identity rows.

### Out of scope
- The deletion request, re-authentication and key shredding at request time (#1049).
- Writing the tombstones into backups and replaying them after a restore (#1078).
- Removing a deleted tenant's data from existing restic snapshots: it ages out with the 12-month retention, and secrets are already shredded.
- Composite tenant foreign keys (#1066).
- Creating partitions without an exclusive lock (#1036).

## Acceptance criteria

- The API runtime installs `tenantPurge` in its crontab (integration, `queueRuntime.test.ts`).

- With tenants A and B both provisioned and holding items, relations, views, docs, mail with attachments, uploaded files, an export, agent runs with MCP credentials and events, notifications with push deliveries, sessions, push registrations, reset tokens and login attempts, after `beginTenantDeletion` for B and one purge run:
  - no row with `tenant_id = B` exists in any tenant-classified table or in `agent_run_mcp_credentials`;
  - none of B's `items_p_*` partitions exists;
  - none of B's blob or export files, and neither `<root>/<B>` directory, exists in either root;
  - B's user, sessions, push registrations, reset tokens, login attempts, invites and budget row are gone, and no table contains B's email;
  - `tenants` has no B row, and `tenant_deletions` has B with `requested_at` equal to B's former `status_changed_at`;
  - A's per-table row counts and files are unchanged, and audit rows naming B remain.

  (integration, `tenantPurge.test.ts`, two tenants via `createTestTenant()` from #975)
- When deleting one of B's file bytes fails during a run, the run fails, B's `tenants` row stays `deleting`, no tombstone is written, and the B rows not yet reached remain. The next run completes the purge (integration, `tenantPurge.test.ts`).
- When tenants C and D are both `deleting` and C's purge throws, D is still fully purged in the same run, and the run rethrows C's failure (integration, `tenantPurge.test.ts`).
- When two purge runs start concurrently, the second skips the locked tenant. Both finish without error and the final state equals a single run (integration, `tenantPurge.test.ts`).
- When `helpers.abortSignal` is aborted mid-purge, the handler returns normally with partial progress committed, and the next run finishes (integration, `tenantPurge.test.ts`).
- When a queued, unlocked job carries `tenantId = B` and another carries A, the purge removes only B's job (integration, `tenantPurge.test.ts`).
- When an `active` or `suspended` tenant exists, the purge never touches it (integration, `tenantPurge.test.ts`).
- When `orderTablesForPurge` gets FKs `child→parent`, it orders `child` first. A self-reference is accepted, and a two-table cycle throws naming both tables (unit, `tenantPurgeOrder.unit.test.ts`).
- When connected as `semprec_data`, `UPDATE`/`DELETE` on `tenant_deletions` fail with a privilege error, and the catalog test passes with the table classified `global` (integration, `tenantPurge.test.ts`).
