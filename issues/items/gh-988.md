**Blocked by:** #983

## Context

Before installing its queue runtime, `semprec-agents` awaits `repairInterruptedRuns(pool)` at top level (`backend/services/semprec-agents/src/serve.ts:35-40`). A rejection there is fatal: `installFatalHandlers` exits non-zero before any queue job can touch an orphaned run.

`repairInterruptedRuns` (`backend/packages/agent-runtime/src/startupRepair.ts:41-67`) does the following in a single `withTransaction`:
- reads `listRunningAgentRuns` (`backend/packages/data/src/agentRuns/agentRunsStore.ts:271-282`), i.e. every `status = 'running'` run;
- skips `triggered_by = 'mcp'` runs;
- for each remaining run, appends a synthetic `tool_result` when the last event is an unpaired `tool_use`, then calls `finishAgentRunWithErrorNotification(client, run.id, 'interrupted_by_restart')`.

It runs with no tenant scope. Tenancy state this issue builds on:
- `agent_runs` and `agent_run_events` carry `tenant_id` under a RESTRICTIVE RLS policy `tenant_isolation` (`tenant_id = (SELECT app_tenant_default())`, with `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())` over the GUC `app.tenant_id`).
- `withTransaction` sets that GUC from the ambient scope: `runInTenant(tenantId, fn)` sets the tenant and `runAsSystem(reason, fn)` sets `''` (`@semprec/shared`).
- A scope-less transaction logs `tenant_scope_missing` (warn mode) or throws (strict).
- In system scope, rows are visible only while exactly one tenant exists. With two tenants, or after the strict switch (#1067), the repair would see no running runs, and every tenant's orphaned runs would stay `running` forever.
- #983 added `forEachActiveTenant` (`backend/packages/data/src/tenancy/forEachActiveTenant.ts`, exported from `@semprec/data`). Called from a system scope, it runs the callback inside `runInTenant(tenantId, …)` for each tenant with `status = 'active'`, starting at a rotating offset. A throwing tenant does not stop the others. After all tenants were attempted, the failures are rethrown as one `AggregateError`.
- This issue calls it as `forEachActiveTenant(pool, async () => …)`. If the merged signature differs, use the merged one.

**Failure semantics.** A tenant whose repair fails no longer blocks the other tenants' repair. The call still rejects in the end, so `semprec-agents` refuses to start exactly as today rather than run a queue over unrepaired runs. Atomicity becomes per tenant: a crash between tenants leaves the later tenants for the next startup, whose repair is idempotent.

#1018 later addresses the `agent_run_error` notification to the tenant's own user; today it goes to `getEarliestUserId`, `agentRunsStore.ts:190`.

## Task

Load `state-writes` (the repair writes events and finishes runs in one transaction per tenant) and `error-handling` (aggregate failures, keep startup fail-closed).

1. **Per-tenant repair (`startupRepair.ts`).** `repairInterruptedRuns(pool): Promise<{ repairedRunIds: string[] }>` keeps its export and signature.
   - It enters `runAsSystem("agents:startupRepair", …)` itself. Its only production caller runs at top level with no scope, and `serve.ts` is not edited here.
   - Inside, it calls `forEachActiveTenant(pool, …)`. The callback runs the existing per-run repair, unchanged, inside one `withTransaction` per tenant and collects that tenant's repaired ids.
   - It returns the ids of all tenants. If any tenant failed, it rejects after every tenant was attempted, and the ids of tenants that committed are not returned.
   - Rewrite the docstring: "Runs in one transaction" becomes one transaction per active tenant, with the crash and failure semantics above.
2. **Store docstring (`agentRunsStore.ts`).** The `listRunningAgentRuns` SQL is unchanged. Rewrite only its docstring: it returns the running runs visible in the current tenant scope, and startup repair calls it once per tenant.
3. **Tests.**
   - New `backend/packages/agent-runtime/src/__tests__/startupRepairPerTenant.test.ts` covers the acceptance criteria below. It uses the two-tenant runtime-role harness of #975: `createTestTenant()` and a runtime-role pool from `@semprec/data/testSupport`. The superuser pool bypasses RLS.
   - Create tenant B's runs and events inside `runInTenant(B, …)`.
   - The existing `backend/packages/agent-runtime/src/__tests__/startupRepair.test.ts` and `backend/services/semprec-agents/src/__tests__/startupRepairComposition.test.ts` must keep passing. The COMMIT-failure case (`startupRepair.test.ts:187-223`) passes a fake `Pool` that stubs only `connect`. If the merged `forEachActiveTenant` reads `tenants` through another pool method, extend that fake so the case still fails at the repair transaction's `COMMIT`. Its rejection assertion (`startupRepair.test.ts:216`) changes to an `AggregateError` whose `errors[0]` message is "commit failed"; keep its no-notification assertions.

## Scope

### In scope
- Startup orphan repair once per active tenant, in system scope entered by the repair itself.
- The tests.

### Out of scope
- The `agent_run_error` recipient (#1018).
- Running agent jobs inside their job's tenant, and any edit to `backend/services/semprec-agents/src/serve.ts` (#991).
- Cancelling a tenant's running runs when it is deactivated (#1042). A suspended tenant's runs are not repaired here.
- MCP-triggered runs, which still close through credential expiry (#987).

## Acceptance criteria

All of these are integration tests (`*.test.ts`), with two tenants under the runtime role unless stated otherwise.
- **Per-tenant repair.** Tenant zero and tenant B each have one orphaned `running` session run whose last event is an unpaired `tool_use`, plus one `running` mcp run. One `repairInterruptedRuns(pool)` call, made with no ambient scope, produces all of the following:
  - both orphaned runs are closed as `error` with result `interrupted_by_restart`;
  - each gets exactly one synthetic `tool_result`, carrying its run's `tenant_id`;
  - both ids are returned;
  - both mcp runs stay `running`.
- **Failure isolation.** A test-only trigger raises on `agent_run_events` inserts for B's run. Tenant zero's run is repaired and committed. B's run stays `running` with no synthetic event, and the call rejects.
- **Inactive tenant.** A `running` run of a tenant whose `status` is `suspended` is left `running`.
- **No orphans.** With two tenants and no running runs, the call resolves `{ repairedRunIds: [] }`.
- **Single tenant unchanged.** With only tenant zero, every existing case in `startupRepair.test.ts` and `startupRepairComposition.test.ts` passes, including one `notification_created` hook per repaired run and none when the repair transaction's `COMMIT` fails.
