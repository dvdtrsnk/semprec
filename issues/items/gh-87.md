**Blocked by:** #86, #22, #121

## Context

Views currently record only `created_by = ai_agent`. That distinguishes AI from user/system creation but cannot distinguish two concrete project agents, so any agent can mutate every AI-created view. Issue #30 provides the concrete agent-run/project identity available at the caller boundary.

## Task

Add nullable `views.creator_project_item_id uuid` and index it. It stores the stable owning project item id, not an `agent_run` id; no FK is possible to partitioned `items`, so creation validates existence through the data layer. Add response field `creatorProjectItemId: string | null`. Authenticated actor context gains server-derived `agentProjectItemId`; request bodies may never set either field. Creating with `created_by = 'ai_agent'` requires and stores `actor.agentProjectItemId`. Patch, delete, add/remove/reorder curated membership require equality. User patch or curated-membership write adopts in the same transaction by setting `created_by = 'user', creator_project_item_id = NULL` before applying the mutation; user delete simply deletes and needs no surviving adoption record. System views never adopt. Existing AI rows migrate with NULL and are unwritable by agents but adoptable by a user. Because those legacy rows prevent an immediate database CHECK, enforce non-null creator identity for every new AI write at the service boundary and add a migration test proving legacy safety.

Every rejected agent operation uses HTTP/service error `403 owner_violation` with `details = { field: 'creatorProjectItemId', viewId, reason }`: `reason = 'creator_mismatch'` when another agent owns the AI view, `reason = 'legacy_creator_unknown'` for a legacy AI view with NULL owner, `reason = 'user_owned'` for a user-created/adopted view, and `reason = 'system_owned'` for a system view. AI creation without `actor.agentProjectItemId` uses `403 owner_violation` with `details = { field: 'agentProjectItemId', reason: 'missing_authenticated_agent_identity' }`; an authenticated identity whose Projects item does not exist uses the same code/status with `reason: 'unknown_authenticated_agent_identity'`. These identity failures occur before any view row or membership write.

## Scope

### In scope

- View ownership schema, choke-point enforcement, adoption, API-facing row shape, and tests.

### Out of scope

- General resource sharing or `resource_grants`.
- Approval queues for editing another agent's view.
- View rendering.

## Acceptance criteria

- Agent A cannot patch, delete, or reorder membership in a view created by Agent B.
- Agent A can mutate its own view.
- A user adoption clears concrete agent ownership atomically and prevents further agent mutation.
- Legacy identity-less AI views are safe by default and remain user-adoptable.
- Cross-agent and legacy-owner rejections return the exact `owner_violation` details defined above.
- Missing or nonexistent authenticated agent identity returns the exact `owner_violation` details defined above and persists nothing.
- Agent mutations of user-owned and system-owned views return the exact `user_owned` and `system_owned` error details above.
