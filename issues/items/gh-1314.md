## Behavior specification

Inbox attachments: attachment model, upload and recognition.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: inbox-attachments-1

#### Adopted from open questions
- One attachment per Inbox item or several -> the model supports several (`position`), cap 10 per capture; whether the Journal UI limits itself to one is a client rule (#1564, #1963). -> Decided by the product owner: one general attachment model for every kind of attachment, at most 10 per capture; limiting the Journal to one attachment is a client rule.
- Voice note vs recording threshold -> 120 seconds, one constant (`INBOX_VOICE_NOTE_MAX_SECONDS`) computed with the metadata (#1965). -> Decided by the product owner: 120 seconds; the same threshold decides which audio attachment gets the recording card (#1985).
- HEIC -> not accepted by the Inbox allowlist. -> Decided by the product owner: the iPhone client converts HEIC to JPEG before upload; server-side conversion is not built in v1 (it may come back if it is ever needed, for example for uploads from the web).
- Allowlist -> PDF, JPEG, PNG, XLSX, DOCX, M4A, MP3 by detected mime type (#1963); unsupported types answer 415 `unsupported_attachment_type`. -> Decided by the product owner: this list; further types are added when they are needed.
- Existing Files item with the same bytes -> link, no second item and no change to the existing item (#1703). -> Decided by the product owner: link only; no duplicate is created and the existing item is not changed.
- Auto-transcription of audio filed from the Inbox -> skipped via the Inbox origin row; transcription is proposed explicitly (#1703, #1978). -> Decided by the product owner: transcription is only offered on the card and started by the user, because it costs AI budget and processes the content.
- PDF previews and page counts -> not computed; images and audio only (#1965). -> Decided by the product owner: no PDF previews and no page count, consistent with Files, which has no previews.
- Client-supplied audio duration/recording time -> not accepted; the server probe is authoritative.
- Image to the model -> a reduced JPEG (long side at most 1568 px) inline in a message block, 8 MiB body cap only for requests with an image (#1381).
- Extraction failure -> not cached, recorded as a compute failure (#1970).
- Long recording plus other content -> the recording proposal wins (#1985). -> Decided by the product owner: the recording proposal wins; the rest of the item is handled within that card.

#### Open questions for the product owner
- Should Files `type` gain png and audio options (#1410 owns it; until then a PNG or audio file has no type)?
- Undoing a confirmation should return the attachment to the Inbox; no issue covers it in this chunk.
- How does the Journal replace its single attachment (delete + capture again, or a dedicated route)? No route is specified here.
- `GET /api/blobs/:id` with an `Authorization` header for AVURLAsset: not covered by an issue in this chunk; check that the current route already accepts it.

#### Delivered behavior
A photo, scan, voice note or shared file can be attached to an Inbox item: the app uploads the bytes, then captures the item with the attachments; unsupported file types are refused with a clear error. No Files item appears until the person confirms; the attachment survives discarding the item and is freed only on permanent delete. After upload the server computes image size, a small preview, a reduced copy and audio length. A short voice note is transcribed into the item's text for the assistant, a long recording becomes a "new recording" card, and a photographed invoice is read by the assistant so the card arrives with supplier, amount and due date filled in. On confirm the attachment moves into Files without copying the bytes (or links to an identical existing file), with the proposed project and company.
