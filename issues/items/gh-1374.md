## Context

Model tier rationale: A single-file change that makes an existing synthetic event match an already-defined payload shape, with an existing test file to update and no new lifecycle, authorization or schema contract.

New startup-repair results use the existing pi failure shape, safe interruption text and permitted identities. Preserve call matching and old rows.

Decision: the failure is recorded as `isError: true` with `result.details.error: true`, the same as a tool that returned an error result, so every reader needs only one rule. Rows already stored in the old synthetic shape are not rewritten; readers that need them still accept a top-level `error: true` (that tolerance belongs to the readers, not this issue).

Later issues build on this: the per-reply failure detection #1890, the step projection #1847, retrying a failed reply #1926 and pairing dangling calls on shutdown #1568.

## Task

Load `testing` and `error-handling`.

1. In `startupRepair.ts`, change the synthetic `tool_result` to exactly: `{kind: "tool_result", toolCallId, name, result: {content: [{type: "text", text: <interruption message>}], details: {error: true}}, isError: true}`. Copy `toolCallId`, `name` and, when present on the `tool_use`, the identity fields `operation`, `mcp`, `targetDatabaseId`, `targetItemId` from the `tool_use` payload; do not copy `arguments` or any other field. 2. Keep the existing defensive handling of a `tool_use` payload that is not an object; a missing `toolCallId` or `name` must still produce a well-formed row (empty identity fields are not invented, the `name` falls back to an empty string only if the stored payload had none).

Update `backend/packages/agent-runtime/src/__tests__/startupRepair.test.ts` (and the per-tenant test if it asserts the old shape): the repaired row has `isError: true`, `result.content[0].text` containing the interruption reason, `result.details.error === true`, no top-level `error` or string `result`, and the stored history passes `conversationReconstruction`'s protocol check and `piConversationHistory`'s tool result conversion. Prove that complete chain over the actual repaired stored rows in the existing service-level `startupRepairComposition.test.ts`; do not import a service converter into the runtime package.

## Scope

### In scope

- The shape of the synthetic `tool_result` written for an unmatched `tool_use` at startup repair.

### Out of scope

- Rewriting synthetic rows already stored in the old shape.
- Pairing dangling calls when an idle thread session is closed on shutdown: #1568.
- Reading or projecting failed steps: #1890, #1847.
- Recording `operation` / `mcp` on regular tool events: #1424 (this issue only copies those fields when they are present).

## Acceptance criteria

- When a run is interrupted with a trailing `tool_use`, then startup repair appends a `tool_result` with `isError: true`, `result.content` text naming the restart interruption, `result.details.error: true`, and the same `toolCallId` and `name` as the call.
- The repaired row has no `arguments`, no top-level `error` and no string `result`.
- When the `tool_use` carried `operation` or `mcp`, the synthetic result carries the same values.
- A run repaired this way can be reconstructed into a conversation without error.
- An eligible interrupted run gets no synthetic result when no unmatched `tool_use` remains anywhere in its history; earlier unmatched calls still get repaired after a later ordinary event, preserving existing matching and eligibility.
