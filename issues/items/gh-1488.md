## Context

Model tier rationale: One extension of the computation's schema and post-processing to fill relations from known ids, validated by the envelope check that #1426 provides; the main risk (invented ids) is closed by an explicit membership check.

Proposal computation must use only disclosed existing IDs, with typed relation metadata and strict matching-target membership.

Decision: the request describes the target database's relation properties (key, name, the target database's module id and whether it holds one or many) next to its plain properties. The model answers with `relations`, a map from relation property key to an array of existing item ids.

Decision: every returned id must be an id that appeared in the request's workspace context for the matching target database. Any other id, a key that is not a relation of the target database, or a relation owned by the system is dropped before the envelope is built; a dropped entry is logged by a checked canonical key and count only; unknown model keys use a fixed `relations` marker, never reflected content. The envelope that remains is validated by the check of #1426; if that check still fails, the tick's existing `needsClarification` path applies.

Decision: a one-valued relation keeps at most one id (the first valid one). A many-valued relation keeps at most 10 ids.

## Acceptance criteria

- When a task is captured with a mention that matches a project in the context, then the stored proposal links the task to that project's id.
- When the model returns an id not sent for the exact relation target database, then it is not stored, including foreign and same-tenant wrong-target IDs. Runtime-role request evidence excludes foreign, archived/deleted and non-allowlisted records; context/compute writes nothing and no transaction remains open during gateway I/O.
- When a one-valued relation gets two ids, then one is kept.
- The stored envelope passes envelope validation.
