## Context

Model tier rationale: One extension of the computation's schema and post-processing to fill relations from known ids, validated by the envelope check that #1426 provides; the main risk (invented ids) is closed by an explicit membership check.

A proposed record is more useful when it is already connected: a task to its project, an event to its people and project, a person to a company. Until now a proposal envelope can carry only plain properties, and the validation `assertValidProposalEnvelope` (`backend/packages/data/src/inbox/inboxTickAction.ts`) rejects relation properties in `properties`. #1426 lets a database envelope carry relations and validates them; #1434 builds the computation and #1987 gives it a bounded list of existing projects, areas, people, companies and events with ids. This issue makes the computation use both. Records that do not exist yet are created by multi-step proposals (#1492), not here.

Decision: the request describes the target database's relation properties (key, name, the target database's module id and whether it holds one or many) next to its plain properties. The model answers with `relations`, a map from relation property key to an array of existing item ids.

Decision: every returned id must be an id that appeared in the request's workspace context for the matching target database. Any other id, a key that is not a relation of the target database, or a relation owned by the system is dropped before the envelope is built; a dropped entry is logged by key and count only. The envelope that remains is validated by the check of #1426; if that check still fails, the tick's existing `needsClarification` path applies.

Decision: a one-valued relation keeps at most one id (the first valid one). A many-valued relation keeps at most 10 ids.

## Task

Load `state-writes`, `ai-gateway`, `canonical-keys` and `testing`.

1. In `backend/services/semprec-api/src/proposalContext.ts` (#1987) add the target database's relation catalog to the request when the entity kind is `database`; read it with the property and relation-definition stores in the same short read transaction as the rest of the context.
2. In `proposalComputation.ts` add `relations` to the model's response schema and its zod validation, filter it as in the Decision, and return the filtered relations in the result in the shape the envelope of #1426 expects. Extend `ProposalComputationResult` and `buildProposalEnvelope` (`inboxTickAction.ts`) to carry them into the stored envelope.
3. Add the instruction text: use ids only from the provided lists, never invent one, leave a relation empty when unsure.
4. Tests with a stubbed gateway: a task proposal with a project id from the context stores the edge in the envelope; an id not in the context, a system-owned relation key and an unknown key are dropped; a one-valued relation with two ids keeps one; the envelope passes validation; an id from another tenant is never in the context and therefore never accepted.

## Scope

### In scope

- Asking the model for relations to existing records, filtering them to known ids and carrying them into the stored envelope.

### Out of scope

- The relation-aware envelope and its validation, and confirming relations (#1426).
- Creating missing records together with the proposal (#1492), and duplicate detection (#1992).
- Editing relations on a stored card.

## Acceptance criteria

- When a task is captured with a mention that matches a project in the context, then the stored proposal links the task to that project's id.
- When the model returns an id that is not in the context, then it is not stored.
- When a one-valued relation gets two ids, then one is kept.
- The stored envelope passes envelope validation.
