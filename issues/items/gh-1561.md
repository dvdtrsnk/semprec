**Blocked by:** #1377, #1555
**Model tier:** medium

## Context

Model tier rationale: A read-side extension that combines five sources (runs, mailboxes with their sync state, a global check row, active problems, later the queue) behind one stable shape, with tenant and role boundaries to respect, but all of them are reads over existing fixtures.

The Semp status view has a Services list: "Semp and agents - last run 2 min ago", "Mail - Gmail - synced 1 min ago", "Mail - Outlook - synced 3 min ago", "Meeting transcripts - queued 0", "Backups - last restore test Oct 1". A service shows "Running", or "Error" with the time it started when an active problem exists for it. Today nothing like this exists: `GET /api/system-health` returns per-mailbox `lastActivityAt` and `lastError` without provider or name, and global process data; the operator view is separate.

This issue adds `services` to `GET /api/semp-status` (#1555). Each service combines a source of activity with the state derived from the active problems (#1459). It uses the stored time of the last backup test (#1377). The transcription service entry is added by #1945, which builds on this issue.

Decision: the services are `agents`, one `mail:<mailboxItemId>` per mailbox, `backup`, and later `transcription`. The calendar entry is omitted until calendar subscriptions provide a source for it (#1960); the list then gains it additively with the tenant's first ICS subscription (decided by the product owner). Public holidays computed in code do not create a calendar entry.

Decision: `state` is `error` when an active problem exists for the service, otherwise `ok`, and `since` is that problem's `first_seen_at`. A problem belongs to a service by category (`agents`, `transcription`, `backup`) or, for mail, by the mailbox in its dedupe key `mail:<mailboxItemId>`. Guidance and library automation problems belong to no service.

Decision: a tenant sees only `{ lastTestAt, ok }` of the backup test and never the failed check name.

## Task

Load `io-hardening`, `canonical-keys` and `testing`.

1. In `backend/packages/data/src/semp/sempStatusReport.ts` add `services: [{ key, name, state, since, lastActivityAt, detail }]` to the response:
   - `agents`: `lastActivityAt` = the latest `agent_runs.started_at` of the tenant (null if none);
   - `mail:<mailboxItemId>` for every mailbox: `name` from the Mailbox item's name and provider (for example "Mail - Gmail"), `lastActivityAt` from the mailbox sync state;
   - `backup`: `detail` = `{ lastTestAt, ok }` from `readRestoreTestOutcome` (#1377) over the `backup:restoreTest` check row; `lastActivityAt` = `lastTestAt`;
   - other services have `detail` `null`.
   Names come from the i18n catalog (`backend/packages/data/src/semp/i18n/status.cs.json` and `status.en.json`), with the mailbox name and provider passed as parameters.
2. Derive `state` and `since` from the active problems read by #1555, as decided above, in the same read, not by a second query per service.
3. Tests: two mailboxes produce two `mail:<id>` services with name, provider and `lastActivityAt`; an active mail problem turns that mailbox to `error` with the problem's `since` and leaves the other `ok`; the backup service returns the date of the last test on repeated passing runs and no failure detail; a tenant with no runs has `lastActivityAt` null; a tenant without calendar subscriptions has no calendar entry; another tenant's mailboxes and problems are not included.

## Scope

### In scope

- The `services` list for agents, mailboxes and backup, with state and since derived from active problems.

### Out of scope

- The transcription service (#1945).
- The calendar service until subscription feeds exist (#1960).
- Recording the last backup test time (#1377) and the problems themselves (#1459, #1555).
- Operator-level process data (the admin health endpoint).

## Acceptance criteria

- When a tenant has two mailboxes, then `services` contains two `mail:<id>` entries with name, provider and `lastActivityAt`.
- When an active problem exists for one mailbox, then its service has `state` `error` and `since` of the problem, and the other mailbox stays `ok`.
- When the restore test passed repeatedly, then the `backup` service returns the date of the latest test, and when it failed, `ok` is false without any failed-check detail.
- When another tenant has data, then it never appears in the list.
