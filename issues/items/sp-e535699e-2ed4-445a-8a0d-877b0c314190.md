## Context

Model tier rationale: One method of one class changes (the order in which it attaches to its source and prepares its directory), the contract that method belongs to gets an ADR, and two tests prove it. It adds no table, route, column or dependency and changes no authorization, so it is not high; but it moves stream consumption ahead of an await and re-orders the cleanup of two chained pipelines, where a wrong order loses bytes, swallows the real error or leaves a producer undestroyed, so it is not low.

The hosted-CI flake `mediaUnreadable` in the `transcriptionTask` tests of `services/alldots-transcribe` has a production cause that the test-only repair of the flake did not and could not touch (the `notRepaired` entry of the hosted-CI repair). It is verified here at HEAD (`30753cc6e`) in a private copy of the tree:

`LocalFsBlobStorageWriter.writeStream` (`backend/packages/data/src/mail/blobStorage.ts`, the production writer of every deployment: `FILES_STORAGE_DIR` and `MAIL_ATTACHMENTS_DIR` in `serve.ts` of the api, the agents and the transcribe processes, and `worker.ts`) starts with `await mkdir(dirname(path), { recursive: true })`. Only after that await does it call `pipeline(source, hasher, createWriteStream(path))`, which is the first thing that reads the source. So for the duration of that `mkdir` (a libuv threadpool job, slow whenever the pool or the disk is busy) the source is unread and has no `error` listener.

`streamFfmpegToStorage` (`services/alldots-transcribe/src/mediaNormalization.ts`, used by `normalizeAudio`, `renderPlaybackAudio` and `renderImageJpeg`) spawns `ffmpeg` and in the same tick passes `child.stdout` to `blobStorage.writeStream`. When `ffmpeg` finishes inside that window (a normalized recording of a few seconds is a few kilobytes, smaller than the pipe), Node's child-process exit handling resumes and drains every stdio stream nobody is reading, so the bytes are dropped. `writeStream` then attaches to an ended, empty stream and stores 0 bytes; `normalizeAudio` returns `byteSize: 0` without an error; `probeNormalizedDuration` fails with `MediaToolError: ffprobe exited with code 1 ... Invalid data found when processing input`, which `classifyTranscriptionFailure` maps to `mediaUnreadable` for step 1 of the transcription task. The repair's scratch proof: the same call stored 10843 bytes on an idle threadpool and 0 bytes with the threadpool saturated by 24 `pbkdf2` jobs.

Verified again for this source, with the writer's `mkdir` delayed (a `vi.mock` of `node:fs/promises` that awaits a gate before the real `mkdir`):

- A child process that writes 8192 bytes to stdout and exits, handed to `writeStream` while the `mkdir` waits for the child's `close`: stored `byteSize` 0 (expected 8192).
- `normalizeAudio` of a 5-second sine wav with `mkdir` delayed by 1.5 s: `byteSize` 0 and an empty file on disk; the same test passes with the change of this Task (and `probeNormalizedDuration` then reads about 5 s).
- Under plain Node, a source that fails while the `mkdir` is pending (for example `sempSpeechHandler.ts` destroys its `Readable` with an error when the request is aborted, and an upload request can fail the same way) has no `error` listener when it emits, so the process gets an `uncaughtException`, although `writeStream` also rejects with that error afterwards. The same cause, a different loss.

Every producer a `BlobStorageWriter` can be handed was checked. `LocalFsBlobStorageWriter` is the only implementation outside tests (there is no S3 or MinIO writer; the docstring only anticipates one). Callers of `writeStream` in production code: `streamFfmpegToStorage` (a child's stdout: exposed to the loss above), `ingestUploadedFile` and `ingestUploadedBlob` in `blobs/fileUploadStore.ts` (the HTTP request body: paused until read, so no bytes are lost, but exposed to the error window), `sempSpeechHandler.ts` (a `Readable.from` destroyed on abort: exposed to the error window), `mail/attachments.ts` (an IMAP, Gmail or Graph download stream or a buffered `Readable.from`), `library/libraryCoverStorage.ts` (`Readable.from` of a buffer) and the archive of `tenancy/tenantExportJob.ts` (the `yazl` output, a pass-through that buffers). The test doubles that implement the interface (`recordingStorage`, `trackWrittenKeys` in `mailSyncJob.ts`, the fakes of the calendar and inbox tests) read the source in the tick they are called. Two test wrappers wait before they delegate to the real writer: `gatedStorage` in `services/alldots-api/src/__tests__/filesAttachOnUpload.test.ts` (an HTTP request body, which stays paused) and `ObservedStorage.beforeWrite` in `services/alldots-transcribe/src/inboxAttachmentMetadata.test.ts` (`ffmpeg` stdout from `renderImageJpeg`, the same loss in a test). So one fix in the one real writer removes every exposure; no caller has to change.

The smallest correct fix is in the writer, not in `streamFfmpegToStorage`. A guard at that one call site (a `PassThrough` between `ffmpeg` and the writer) would leave the contract of `BlobStorageWriter.writeStream` unwritten, leave the HTTP and speech callers exposed to the error window, and have to be repeated by every future caller and by the future object-storage writer, which will also need an await (credentials, a multipart upload) before its first byte. The header comment of the interface already says "`writeStream` is the one and only write path ... 'memory-safe' is a structural property of the writer, not something each call site has to get right"; the same holds for "does not lose the producer's bytes". No ADR or `review-rules` line states when a writer must start reading its source; that is decided here and recorded in an ADR (`adr-conventions`: a lifecycle and ordering contract that later writers will follow, written so far only in code comments). Bare `.pipe()` stays excluded for the reason the file's header gives (#65): the source is attached with `pipeline()`.

Designs that were rejected: `mkdirSync` (blocks the event loop on every upload and is the same call a hosted disk makes slow); creating the directory at startup (a key's directory is `<tenantId>/...` and is created on demand); buffering the source in memory (unbounded, against the header of the file); `source.pipe(new PassThrough())` (the worker's proposal; no error propagation and the #65 truncation under backpressure).

## Task

Load `io-hardening`, `error-handling`, `testing` and `adr-conventions`.

1. In `LocalFsBlobStorageWriter.writeStream` (`mail/blobStorage.ts`) attach to `source` before the first `await`, with `pipeline()` (never `.pipe()`):
   - Build the `hasher` as today (size, `maxBytes` and hash stay in the `Transform` spliced into the pipeline). Create `staged = new PassThrough()` and start `const intake = pipeline(source, hasher, staged)` as the first asynchronous step of the method, before `mkdir`. The default high-water marks bound what is buffered while the directory is created (a producer such as `ffmpeg` then blocks on a full pipe instead of exiting). Mark `intake` as observed (`intake.catch(() => undefined)`) so its rejection is never unhandled; its outcome reaches the caller through `staged`.
   - Then, inside the existing `try`: `await mkdir(dirname(path), { recursive: true })`, then `await pipeline(staged, createWriteStream(path))`, then `await intake`.
   - In the existing `catch`: `staged.destroy(err)` with the caught error (wrapped in an `Error` when it is not one). `intake` then destroys the source and the hasher with that same error when `mkdir` or the file write failed. A bare `staged.destroy()` would destroy the source with `ERR_STREAM_PREMATURE_CLOSE`, and a caller that observes its own source (`TenantExportArchive` races `finished(output)` against the write) would report that instead of the storage error. Then wait for `intake` to settle without letting its rejection replace the error, then run the existing partial-byte cleanup through `this.delete` with its existing logged failure, and rethrow the first error unchanged (the identity of the source's error, of `MaxBytesExceededError` and of the `mkdir` error is kept; a failure of the cleanup never replaces it).
   - Keep the return value, `delete` and `readStream`, the `maxBytes` semantics (the write aborts and no bytes stay behind once the count exceeds it) and the log message text.
2. Update the docstrings: the class comment of `LocalFsBlobStorageWriter` and the comment of `BlobStorageWriter.writeStream` state the contract (an implementation consumes `source` and observes its errors from the tick it is called, before any await; asynchronous preparation runs while the source is consumed into a bounded buffer or after the pipeline is attached; on a preparation failure it destroys the source and removes partial bytes). In `streamFfmpegToStorage` (`mediaNormalization.ts`) add one comment that `child.stdout` is handed over unread on the strength of that contract; no code of that file changes.
3. Add `docs/adr/2026-11-15-a-blob-writer-consumes-its-source-from-the-tick-it-is-called.md` (the date is the day it is written; `status: accepted`, `area: [backend]`, `supersedes: []`, `superseded-by: null`; Context, Decision, Evidence, Alternatives and consequences, like `2026-11-06-blob-open-cleanup-observes-stream-closure.md`). Decision: every `BlobStorageWriter.writeStream` implementation attaches to the source and observes its errors before its first await, and any later or slower preparation (directory, credentials, multipart upload) runs behind a bounded buffer or after attaching; a caller may hand over a producer that blocks on a full pipe or that can fail, without having read it; on a failed preparation the writer destroys the source and removes partial bytes and rethrows the first error. Reasons: the production loss of a child's output and the uncaught source error, with the measured 0 bytes against 8192 and about 10 KB. Alternatives rejected: the four above, plus a guard in each caller. Consequences: while the writer prepares, up to the high-water marks of its intake chain are buffered per write (the writable and readable sides of the hashing Transform and of the staging PassThrough, about 256 KiB at the 64 KiB default of Node 22 and later) on top of the source's own buffer; a future object-storage writer follows the same rule and a test double that stands in for a writer reads its source in the tick it is called. A wrapper that waits before it delegates to a real writer models a slow caller, not a writer, and must not hold a producer that can exit while it waits (the two existing wrappers named in Context are left to a follow-up). Do not edit an accepted ADR.
4. Tests (they must fail on the code at HEAD):
   - `mail/__tests__/blobStorageStreamAttach.unit.test.ts` (new, unit tier, real `LocalFsBlobStorageWriter` on a temporary directory, `vi.mock` of `node:fs/promises` whose `mkdir` awaits a gate the test controls and otherwise calls the real one, the same technique as `testSupport/__tests__/stalePostgresDirs.unit.test.ts`):
     - a real child process (`process.execPath -e`) writes 8192 bytes to stdout and exits; the `mkdir` gate is the child's `close` event; the stored `byteSize` is 8192, the file on disk has 8192 bytes and `contentHash` is the sha-256 of those bytes;
     - right after `writeStream` is called, while the gate is closed, the source already has an `error` listener and is flowing; a source destroyed with an error while the gate is closed makes `writeStream` reject with that very error once the gate opens, and no file is left;
     - a gate that rejects (a `mkdir` failure) makes `writeStream` reject with that error, destroys the source with that same error (`source.errored` is it) and leaves no file;
     - `maxBytes` exceeded while the gate is closed rejects with `MaxBytesExceededError` and leaves no file; a multi-chunk source of several megabytes (more than the buffered high-water marks) is stored completely with the right hash when the gate opens late.
     Existing tests of `blobStorage.unit.test.ts` (error identity with a failing `delete`, ranges and roots) stay and pass unchanged.
   - `services/alldots-transcribe/src/mediaNormalizationSlowStorage.test.ts` (new, same tier and ffmpeg fixtures as `mediaNormalization.test.ts`, `generateOggFixture` or the sine fixture of `__tests__/fixtures/mediaFixtures.js`): with the same `mkdir` gate (held for about 1.5 s, or released when the process has exited) `normalizeAudio` through a real `LocalFsBlobStorageWriter` returns a `byteSize` above zero equal to the size of the stored file, `probeNormalizedDuration` of the stored audio is within the usual tolerance of the input's duration, and no `MediaToolError` is raised.

## Scope

### In scope

- The order in which `LocalFsBlobStorageWriter.writeStream` attaches to its source relative to its first `await`, and the cleanup of the two chained pipelines that follows from it.
- Writing the contract of `BlobStorageWriter.writeStream` down (interface and class docstrings, one ADR).
- Proving it with a deterministic delay of `mkdir` (an injected gate, not a load, a sleep race or a saturated threadpool), once at the writer and once through `normalizeAudio`.

### Out of scope

- `transcriptionTask.test.ts` and its helper `storageWithMidNormalizationHook`: the test-only part of the flake is repaired elsewhere and is not touched. This source fixes one proven production cause of `mediaUnreadable`; it does not claim to explain the CI failure at line 1644 of that test (the call there performs no storage access at HEAD), nor to remove every other possible cause of the flake.
- A check that `normalizeAudio` or `renderPlaybackAudio` refuse an empty successful output (`renderImageJpeg` already does). It would hide a writer that loses bytes, and it is a separate decision.
- Any change to `streamFfmpegToStorage` beyond the one comment, to `probeNormalizedDuration`, to `classifyTranscriptionFailure` or to the `ffmpeg` timeout.
- The callers of `writeStream` (`fileUploadStore.ts`, `attachments.ts`, `sempSpeechHandler.ts`, `libraryCoverStorage.ts`, `tenantExportJob.ts`), the `readStream` and `delete` methods, key construction and the `maxBytes` limit values.
- An object-storage (S3 or MinIO) writer: none exists; the ADR only binds a future one.
- The two test wrappers that wait before they delegate (`gatedStorage` in `filesAttachOnUpload.test.ts`, `ObservedStorage.beforeWrite` in `inboxAttachmentMetadata.test.ts`); changing them is a separate test-debt source.
- `mkdirSync`, an in-memory buffer of the whole source, a new dependency, an injectable file-system parameter on the writer's constructor.

## Acceptance criteria

- When `LocalFsBlobStorageWriter.writeStream` is handed a child process's stdout and the child exits while the directory is still being created, then the whole output is stored: `byteSize`, the file size and the `contentHash` match the bytes the child wrote (8192 in the test; at HEAD `byteSize` is 0).
- When `writeStream` is called with its `mkdir` still pending, then the source already has an `error` listener and is being consumed; when the source fails in that window, then `writeStream` rejects with that very error, no file is left and no uncaught exception is raised.
- When `mkdir` fails, then `writeStream` rejects with the `mkdir` error, the source is destroyed with that same error (not `ERR_STREAM_PREMATURE_CLOSE`) and nothing is stored, and the existing tenantExport.test.ts case "marks the export failed and settles output errors when storage initialization fails before pipeline attaches" passes unchanged; when `maxBytes` is exceeded, then it rejects with `MaxBytesExceededError` and leaves no bytes; when the partial-byte cleanup also fails, then the first error is the one thrown (the existing test passes unchanged).
- When a source larger than the buffered high-water marks is written with a late `mkdir`, then it is stored completely with the correct hash (backpressure holds, no bytes are dropped or duplicated).
- When `normalizeAudio` runs through a real `LocalFsBlobStorageWriter` whose `mkdir` is delayed, then the stored audio is non-empty, `probeNormalizedDuration` succeeds and no `MediaToolError` is raised (at HEAD the stored file is empty and the probe fails).
- The new unit test and the transcribe test fail on the code at HEAD (the cases of the first, second and fifth criterion and the mkdir-failure case of the third) and pass with the change; the `maxBytes`, cleanup-failure and large-source cases are regression guards that also pass at HEAD; no sleep, no load and no saturated threadpool is used to make them fail.
- The ADR of this source exists, states the contract of the first bullet of Task 3, and no accepted ADR is edited.
