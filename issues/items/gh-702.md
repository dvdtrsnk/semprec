## Context

`deploy/Caddyfile` is the deployment's only public entry point (issue #174): `{$SEMPREC_DOMAIN}` site, automatic TLS, HSTS, the two `request_body` ceilings, `reverse_proxy 127.0.0.1:8080`. `deploy/provision.sh` installs the `caddy` package (`install_host_packages`, line 95) and then never touches it: the file is not copied to `/etc/caddy/Caddyfile`, `caddy.service` is not enabled, and nothing supplies `SEMPREC_DOMAIN` to it — the Debian package's unit runs as user `caddy` with no `EnvironmentFile`, so even a hand-copied Caddyfile expands to an empty site address. On a freshly provisioned host, Caddy serves its package default page on :80 and the application is unreachable. `deploy/README.md` (line 8-10) describes the Caddyfile as installed configuration.

A second gap makes the proxy target wrong even once the file is in place: `semprec-api` listens on `PORT` with default `3001` (`backend/services/semprec-api/src/serve.ts` lines 48-50), `deploy/shared/.env.example` lists no `PORT`, and the Caddyfile targets `8080`. The Caddyfile's own header comment (lines 5-7) already says the two must agree "via /opt/semprec/shared/.env's PORT".

`provision.sh` is idempotent and its hermetic test (`deploy/provision.test.sh`) mocks `install`, `systemctl` and `apt-get` and asserts installed files by path; the same mocks cover this issue's additions. The web-client epic depends on this issue for the served site.

## Task

1. **Drop-in unit** — add `deploy/systemd/caddy-semprec.conf` (new):
   ```
   # Installed by deploy/provision.sh as /etc/systemd/system/caddy.service.d/semprec.conf.
   # Caddy gets exactly one value from the deployment's secrets file, not the file itself.
   [Service]
   EnvironmentFile=/etc/caddy/semprec.env
   ```
2. **provision.sh** — add, after `enable_timers` (line 239) and before `main`, two functions, and call them from `main` after `enable_timers`:
   - `install_caddy_config`: `install -o root -g root -m 0644 "$SCRIPT_DIR/Caddyfile" /etc/caddy/Caddyfile`; `install -d -o root -g root -m 0755 /etc/systemd/system/caddy.service.d`; `install -o root -g root -m 0644 "$SCRIPT_DIR/systemd/caddy-semprec.conf" /etc/systemd/system/caddy.service.d/semprec.conf`. Make `/etc/caddy` and `/etc/systemd/system/caddy.service.d` overridable constants (`CADDY_CONFIG_DIR`, `CADDY_UNIT_DROPIN_DIR`) like `SYSTEMD_UNIT_DIR`, so the test can redirect them.
   - `render_caddy_environment`: read `SEMPREC_DOMAIN` from `$SEMPREC_ROOT/shared/.env` (parse the `SEMPREC_DOMAIN=` line with `sed -n 's/^SEMPREC_DOMAIN=//p'`, no `source`, so nothing else in the secrets file is evaluated). If it is empty, print `SEMPREC_DOMAIN is not set in $SEMPREC_ROOT/shared/.env; Caddy stays unconfigured until it is set and provision.sh is rerun` to stderr and return 0 — a first run against the freshly copied template must still succeed. Otherwise write `SEMPREC_DOMAIN=<value>` to `$CADDY_CONFIG_DIR/semprec.env` (`root:root 0600`, via a temp file + `install`), run `systemctl daemon-reload`, `systemctl enable caddy`, then `SEMPREC_DOMAIN=<value> caddy validate --config "$CADDY_CONFIG_DIR/Caddyfile"` and `systemctl reload-or-restart caddy`. Rerunning with the same domain must be a no-op apart from the validate/reload.
3. **Environment template** — append to `deploy/shared/.env.example` (after the last line, `HEALTHCHECKS_RESTORE_PING_URL=`) a `# ---- Listeners ----` section with `PORT=8080` and a comment that `semprec-api` must listen where `deploy/Caddyfile`'s `reverse_proxy 127.0.0.1:8080` points and that `SEMPREC_DOMAIN` above is also what `provision.sh` hands to Caddy. Fix the Caddyfile header comment (line 6) to point at `deploy/shared/.env.example` instead of `services/semprec-api/.env.example`.
4. **README** — in `deploy/README.md`, extend the `Caddyfile` bullet (lines 8-10) with "installed to `/etc/caddy/Caddyfile` by `provision.sh`, which also enables `caddy.service` and hands it `SEMPREC_DOMAIN` through `/etc/caddy/semprec.env`", and add a short `## Front door (Caddy)` section after `## Czech full-text search` describing the rendered env file, the empty-domain first-run behaviour, and that `PORT=8080` in the shared `.env` is required.
5. **Tests** — `deploy/provision.test.sh`: add `sed` redirections for `CADDY_CONFIG_DIR` and `CADDY_UNIT_DROPIN_DIR` next to the existing ones (lines 22-37), a `caddy` mock (`write_mock caddy 'echo "caddy $*" >> "$TEST_STATE/commands"'`) placed directly after the `docker` mock block (line 81), and — appended as one block immediately after the `test "$(grep -c '^docker cp ' "$TEST_STATE/commands")" -eq 2` line (136), not next to the unit-file greps — assertions that: `/etc/caddy/Caddyfile` and the drop-in exist under `$TEST_ROOT`; on the first run (template `.env`, empty domain) no `semprec.env` was written and `systemctl enable caddy` was not recorded; after writing `SEMPREC_DOMAIN=example.test` into the test `.env` and rerunning, `semprec.env` contains exactly `SEMPREC_DOMAIN=example.test`, `caddy validate` and `systemctl reload-or-restart caddy` were recorded, and a third run records them again without changing the file.

## Acceptance criteria

- When `provision.sh` runs on a host whose shared `.env` has `SEMPREC_DOMAIN=example.test`, `/etc/caddy/Caddyfile` matches `deploy/Caddyfile`, `/etc/caddy/semprec.env` contains that domain, `caddy.service` is enabled and (re)loaded, and `https://example.test/healthz` reaches `semprec-api` on `127.0.0.1:8080` once `PORT=8080` is in the shared `.env`.
- When the shared `.env` has an empty `SEMPREC_DOMAIN`, `provision.sh` still exits 0, prints the warning, and leaves Caddy unconfigured.
- Rerunning `provision.sh` never changes an unchanged `semprec.env` and never fails on an already-enabled `caddy.service`.
- `bash deploy/provision.test.sh` passes.
