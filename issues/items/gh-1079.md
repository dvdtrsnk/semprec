## Context

Model tier rationale: The session role, adapter, route gate, page shell and accounts panel are all specified field by field in existing web conventions.

Every account carries a role, `users.role ∈ admin|member` (#968). Admins manage accounts, but they never see another user's content and there is no impersonation. The backend admin plane lives under `/api/admin/*`:

- Its routes are adapter routes flagged `admin: true`. They run in system scope and audit every mutation.
- A member calling one gets `403 { error: { code: "admin_required" } }`, never a 401.
- The account list comes from #1037. Suspend, reactivate, role change and the last-admin guard come from #1041.

This issue adds the web side of that: the session role, the admin page shell and its accounts panel.

In the web client today:

- **The session has no role.** `sessionUserSchema` is `{ id, email, locale, createdAt }` (`web/src/api/authOperations.ts:11-16`). `POST /api/auth/login` and `GET /api/auth/session` both serialize the backend `PublicUser`, which is `Omit<UserRow, "passwordHash">` (`backend/packages/data/src/auth/authActions.ts:25`; serialized at `backend/services/semprec-api/src/authHandler.ts:161-170` and `227-234`). Only `GET /api/auth/session` carries `role` (#980); the login response does not (`UserRow` has no `role`, `backend/packages/data/src/auth/types.ts:22-28`).
- **Routing.**
  - `?page=` parameters are resolved once, in `web/src/main.tsx:28-66`.
  - Session-bound adapters get the shared `fetchImpl` (`main.tsx:36`), so a 401 reloads to `/` (#1075).
  - Routed content is chosen in `RoutedContent` (`web/src/App.tsx:229-271`).
  - The header (`App.tsx:212-222`) has no navigation.
- **Adapters.** Each bespoke route family gets one `create*Operations({ baseUrl, fetchImpl })` adapter that zod-parses at the edge (`docs/adr/2026-09-29-web-client-calls-the-api-through-operations-adapters.md`). The request/error pattern is in `web/src/api/approvalQueueOperations.ts:85` and `:106-127`.
- **Error body.** Adapter routes answer errors as `{ error: { code, details? } }` (`backend/services/semprec-api/src/adapter/errorContract.ts:113-126`), with no message string.

**Backend contract.** If a merged handler (`backend/services/semprec-api/src/adminHandler.ts`) differs from this, bind to the merged handler and say so in your PR description.

`AdminAccountSummary = { userId, email, role: "admin"|"member", status: "provisioning"|"active"|"suspended"|"deleting", createdAt, lastSeenAt: string|null }`

- `GET /api/admin/accounts` → `200 { accounts: AdminAccountSummary[] }`.
- `POST /api/admin/accounts/:userId/suspend` and `POST /api/admin/accounts/:userId/reactivate` → `200 { account }`.
- `PUT /api/admin/accounts/:userId/role` with `{ role }` → `200 { account }`.
- Refusals:
  - `409` with code `last_admin` (at least one active admin must remain);
  - `409` with code `invalid_account_status`;
  - `404`.

## Task

Load `canonical-keys` (route key `admin`, labels for role and status values) and `error-handling` (adapter status mapping, action failures).

1. **Session role** — add `role: z.enum(["admin", "member"])` to `sessionUserSchema`. Make `login` in `authOperations.ts` resolve its user through `getSession()` after a successful login instead of parsing the login body, which carries no `role`. Add `role` to every `SessionUser` fixture: `web/src/__tests__/App.test.tsx:10-15`, `web/src/views/login/__tests__/LoginPage.test.tsx:9` and `web/src/api/__tests__/authOperations.test.ts:5`.
2. **Adapter** — add `web/src/api/adminOperations.ts` with `createAdminOperations({ baseUrl, fetchImpl })` and the `AdminOperations` interface: `listAccounts()`, `suspendAccount(userId)`, `reactivateAccount(userId)`, `changeRole(userId, role)`. Rules:
   - Ids go through `encodeURIComponent`, and every response is zod-parsed.
   - Status mapping: `401/403/404/501` → `unavailable`. Any other non-2xx, a transport failure or a parse failure → `retryable`.
   - A non-2xx's message is `error.code` when the body `safeParse`s as `{ error: { code: string } }`. Otherwise it is `Request to <path> failed with <status>`.

   Later admin panels extend this one interface.
3. **Route** — in `web/src/main.tsx`, when `page === "admin"`, build `admin = { operations: createAdminOperations({ baseUrl: apiBaseUrl, fetchImpl }) }` with the session-bound `fetchImpl`, and document `?page=admin` in the doc comment.
4. **App** — in `web/src/App.tsx`, add `export interface AdminRoute { operations: AdminOperations }` and an `admin?` prop, and pass the session user into `RoutedContent`. When `admin` is set:
   - A user whose `role === "admin"` gets `<AdminPage operations={…} />`.
   - Any other user gets `<EmptyState message={t("admin.notAvailable")} />`, and no admin request is made.

   In the header, render a link to `?page=admin` labelled `admin.link`, only when `role === "admin"`.
5. **Page** — add `web/src/views/admin/AdminPage.tsx`: an `admin.title` heading followed by `AccountsPanel`. Later issues add further panels after it.
6. **AccountsPanel** — add `web/src/views/admin/AccountsPanel.tsx`:
   - It loads through `useAsyncResource` (`web/src/views/mailbox/useAsyncResource.ts`) and renders `LoadingState`, `ErrorState` (with retry) and `EmptyState` (`web/src/components/StateViews.tsx`).
   - One row per account shows email, role label, status label, created and last seen (`—` when null). Dates use `formatDateTime(useLocale(), iso)` (`web/src/i18n/format.ts:3-8`).
   - Actions: **Suspend** for `active`; **Reactivate** for `suspended`; **Make admin** / **Make member** for `active` and `suspended`. No actions for `provisioning` or `deleting`.
   - While an action is pending, that row's buttons are disabled.
   - On success, reload the list.
   - On failure, keep the list as it was (no optimistic update) and show an error in a `role="alert"` element: `admin.accounts.lastAdmin` when the message is `last_admin`, otherwise `admin.accounts.actionFailed` with the message.
7. **i18n** — add `admin.link`, `admin.title`, `admin.notAvailable` and the `admin.accounts.*` keys (including role and status labels) to `en` and `cs` in `web/src/i18n/messages.ts`.

## Acceptance criteria

All criteria below are web unit tests (Vitest + jsdom).

- **Session role** (`authOperations.test.ts`): `getSession` parses `role`, and `login` resolves its user through `getSession()` after a 2xx. A user object whose `role` is missing, or is neither `admin` nor `member`, rejects as `retryable`.
- **Adapter calls** (`adminOperations.test.ts`): each of the four `AdminOperations` methods calls its documented path and method with same-origin credentials, sends a JSON body where one is defined, and parses the documented response.
- **Adapter rejections** (`adminOperations.test.ts`):
  - 403 and 404 reject as `unavailable`.
  - A 409 with body `{ error: { code: "last_admin" } }` rejects as `retryable` with message `last_admin`.
  - A malformed body or a network failure rejects as `retryable`.
- **Header link** (`App.test.tsx`): an admin session shows the `admin.link` link; a member session does not.
- **Role gate** (`App.test.tsx`): with the `admin` route, a member sees `admin.notAvailable` and no `AdminOperations` method is called; an admin sees the page with the accounts panel.
- **Accounts panel** (`web/src/views/admin/__tests__/AccountsPanel.test.tsx`):
  - It lists email, role, status, created and last seen for each account.
  - It offers only the actions valid for each status, and a successful action reloads the list.
  - A `last_admin` rejection shows `admin.accounts.lastAdmin`; any other rejection shows its message. In both cases the row stays as it was.
  - A failed load shows the error state, and its retry reloads the list.
- Every new key exists in `en` and `cs`, and `pnpm run verify` passes in `web/`.
