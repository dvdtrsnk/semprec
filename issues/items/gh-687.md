**Blocked by:** #641

## Context

`sweepDueHeartbeats` (`backend/packages/data/src/scheduler/schedulerStore.ts:437-480`) sets `project_heartbeats.next_fire_at = NULL` for a floating rule (`interval`/`everyNDays`, line 471-472) when it enqueues the occurrence fire job, and relies on the fire job's first attempt — `prepareHeartbeatOccurrenceFire` (`schedulerStore.ts:519-609`, the `first_started_at === null` branch at 578-595) — to compute and store the next occurrence from the real start time (issue #213). In `backend/packages/data/src/scheduler/sweep.ts` `runScheduledOccurrenceFire`, that call (line 238) sits **before** the `try` (line 249) whose final-attempt branch (257-264) writes `last_error`, marks the occurrence `failed` and writes the `heartbeat_error` notification. `assertActionAffinity` and the `registry.get(...)` lookup (lines 245-247) are outside the `try` as well, and the same two calls are outside the `try` on the manual/onItemEvent path (`createHeartbeatFireTaskForAffinity`, lines 177-179 vs. the `try` at 181).

Consequence: when `prepareHeartbeatOccurrenceFire` throws on all `maxAttempts: 3` attempts (a transient database failure, `getSystemTimezone` failing, a module `nextFireAt` calculator throwing), graphile-worker dead-letters the job and the floating heartbeat is left with `next_fire_at IS NULL`, `enabled = true`, no `last_error`, an occurrence stuck at `queued`, and no notification — it is silently unscheduled until someone edits or re-enables it. A missing handler or affinity mismatch after a successful prepare leaves the occurrence `running` forever with the same silence.

#641 registers the seeded handlers in both queue runtimes and adds composition tests that fire heartbeats through this file; this issue lands after it so those tests keep describing the same handler path. Sibling issues D5 (sweep chunking) and D11 (`core.agentRun` retry notifications) of this batch build on the structure this issue leaves in `sweep.ts`.

## Task

1. **Store: `recordHeartbeatFireSetupFailure`** — new exported function in `schedulerStore.ts`, next to `failHeartbeatOccurrence`:
   `recordHeartbeatFireSetupFailure(client: PoolClient, heartbeatId: string, occurrenceId: string | undefined, message: string, moduleRuleKinds: HeartbeatRuleKindRegistry = new Map()): Promise<{ id: string; name: string } | null>`. Inside the caller's transaction it:
   - `SELECT id, name, rule, enabled, next_fire_at, now() AS db_now FROM project_heartbeats WHERE id = $1 FOR UPDATE`; returns `null` when the row is gone.
   - When `enabled AND next_fire_at IS NULL`: `parseHeartbeatRule(rule, moduleRuleKinds)` and `computeNextFireAt(rule, await getSystemTimezone(client), db_now, moduleRuleKinds)`; on success `UPDATE project_heartbeats SET next_fire_at = $2, last_error = $3 WHERE id = $1`; when parsing/computing throws, `UPDATE ... SET last_error = $2` with `message` followed by `; schedule could not be restored: <compute error message>` (the row stays unscheduled until the next edit/enable, which recomputes it, but the failure is now visible).
   - Otherwise `UPDATE project_heartbeats SET last_error = $2 WHERE id = $1`.
   - When `occurrenceId` is given: `UPDATE heartbeat_occurrences SET status = 'failed', last_error = $2 WHERE id = $1 AND status IN ('queued', 'running')` (a terminal occurrence is left alone).
   - Returns `{ id, name }` for the notification. Docstring: this is the fire task's "the failure happened before or instead of the action handler" close-out, the counterpart of `failHeartbeatOccurrence` for a handler failure.
2. **`sweep.ts` — every failure after payload validation is inside final-attempt handling.** In `runScheduledOccurrenceFire`: wrap `prepareHeartbeatOccurrenceFire`, `assertActionAffinity` and the `registry.get` lookup so that any throw from them, on the final attempt (`helpers.job.attempts >= helpers.job.max_attempts`), runs one `withTransaction` that calls `recordHeartbeatFireSetupFailure(client, heartbeatId, occurrenceId, message, moduleRuleKinds)` and, when it returns a heartbeat, `notifyHeartbeatError(client, heartbeat, helpers.job.id)`; then rethrows. The existing handler `try/catch` (lines 249-266) stays as is for handler failures. Apply the same shape to the manual/onItemEvent path in `createHeartbeatFireTaskForAffinity`: move `assertActionAffinity` and the `registry.get` lookup (177-179) inside the existing `try`, so their final-attempt failure records `last_error` (through `recordHeartbeatFailure`, as the existing catch does) and the notification. Update the docstring of `runScheduledOccurrenceFire` and the paragraph above `createHeartbeatFireTaskForAffinity` ("On the final retry attempt ... a failure is recorded") to state that this now covers preparation, affinity and handler-lookup failures.
3. **`publicSurface.test.ts`**: add `"recordHeartbeatFireSetupFailure"` to `EXPECTED_RUNTIME_EXPORTS` (it is reached through `export * from "./scheduler/schedulerStore.js"`).
4. **Tests** (`backend/packages/data/src/__tests__/scheduler.test.ts`, integration; invoke the task function directly with a `helpers` stub as the existing "a retried fire attempt reuses the persisted occurrenceId" case does):
   - A floating (`interval`) heartbeat is swept (so `next_fire_at IS NULL` and a `queued` occurrence exists). Run `createHeartbeatFireCoreTask(failingPool, registry)` with `helpers.job.attempts = 3, max_attempts = 3`, where `failingPool` is a thin wrapper around the real pool whose first `connect()` rejects with `new Error("simulated database outage")` and every later call delegates → the task rethrows that error; afterwards `project_heartbeats.next_fire_at` is non-null and later than `now()`, `last_error = "simulated database outage"`, the occurrence is `failed` with the same `last_error`, and exactly one `heartbeat_error` notification exists for the heartbeat.
   - Same setup with `attempts = 1` → the task rethrows and nothing is recorded (`next_fire_at` still `NULL`, `last_error IS NULL`, occurrence still `queued`, no notification).
   - A scheduled occurrence whose action id has no registered handler, final attempt → `No handler registered ...` is rethrown, the occurrence is `failed`, `last_error` names the missing handler, `next_fire_at` (fixed rule, already advanced by the sweep) is unchanged, one notification exists.
   - The manual path (`triggeredByRunId` payload) with no registered handler on the final attempt → `last_error` set and one notification.

## Scope

### In scope
- The pre-handler failure close-out (schedule restore, `last_error`, occurrence `failed`, notification) on the final attempt of both fire paths, and its tests.

### Out of scope
- Sweep chunking, `ORDER BY`/pagination and DB-clock next-fire computation in `sweepDueHeartbeats` (sibling issue D5).
- `coreAgentRunAction`'s per-attempt notifications and error masking (sibling issue D11).
- Changing what `prepareHeartbeatOccurrenceFire` itself does on its own success path, or the `maxAttempts` of fire jobs.
- Retrying a dead-lettered job automatically.

## Acceptance criteria

- When every attempt of a floating heartbeat's occurrence fire job fails before `prepareHeartbeatOccurrenceFire` commits, the final attempt leaves the heartbeat with a non-null `next_fire_at` in the future, `last_error` set to the failure message, the occurrence `failed` with that message, and exactly one `heartbeat_error` notification.
- When a non-final attempt fails the same way, nothing is recorded and the job is left to retry.
- When the fire job fails after preparation because no handler is registered or the affinity does not match, on the final attempt the occurrence is `failed`, `last_error` is set and one `heartbeat_error` notification exists — on both the scheduled and the manual path.
- A heartbeat whose rule can no longer be parsed at close-out time is still marked with `last_error` (mentioning that the schedule could not be restored) instead of the close-out throwing.
