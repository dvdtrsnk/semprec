**Model tier:** low

## Context

Model tier rationale: One helper and three enqueue-site changes are specified line by line.

In production, agent sessions in the `semprec-agents` process are started by heartbeat fire jobs whose action is `core.agentRun`:
- `resolveHeartbeatFireTaskName` routes them to the `heartbeatFireAgent` task (`backend/packages/data/src/scheduler/actions.ts:141-145`);
- `coreAgentRunAction` creates the `agent_runs` row and then drives the session (`actions.ts:77-125`), through `createRunAgentForHeartbeats` (`backend/services/semprec-agents/src/agentRunTasks.ts:106-131`).

Such jobs are enqueued at three places, none with a queue name for agent work:
- `onItemEvent` fires: `backend/packages/data/src/scheduler/schedulerStore.ts:320-325`. Its `queueName` comes only from the action-affinity map, which holds no agent entry.
- Swept fires: `schedulerStore.ts:509-514`.
- Manual triggers from the `heartbeat.trigger` agent tool: `backend/packages/data/src/scheduler/heartbeatAgentTools.ts:207-212`.

The `agentRun` and `delegatedAgentRun` tasks share a handler (`agentRunTasks.ts:72-98`), but no production code enqueues them; only tests do.

The only concurrency limit is the worker's global `QUEUE_CONCURRENCY_DEFAULT = 4` (`backend/packages/queue/src/index.ts:313`). So one tenant with many due agent heartbeats can hold every agents-process slot and every gateway call, and starve the others.

A count of `agent_runs` rows cannot express "currently running":
- `status` is only `running|done|error` (`backend/packages/data/src/db/migrations/0001_core_schema.sql:122`), and a row is `running` from its insert;
- idle delegated sessions stay `running` for up to 24 h (`backend/packages/agent-runtime/src/delegationRegistry.ts:19`);
- MCP-credential runs stay `running` until the credential expires;
- a handler-side cap could only block a worker slot while waiting, or throw and use up the fire job's `maxAttempts: 3` after `coreAgentRunAction` already opened a row.

Graphile Worker runs jobs that share a `queue_name` strictly one at a time, without using attempts or slots. #1016 added `tenantLane(lane)` (`backend/packages/data/src/tenancy/tenantLane.ts`), which returns `` `${lane}:${tenantId}` `` inside a tenant scope and `undefined` outside one, together with `docs/adr/<date>-per-tenant-queue-lanes.md`. This issue follows that ADR, so no new ADR is needed. The cap is therefore one executing heartbeat agent session per tenant. Other tenants are unaffected. Tenant zero's agent heartbeats, which could run in parallel before, now run in sequence; only throughput changes.

#1018 made every heartbeat run's actor the tenant's own user. `heartbeatFireAgent` is a `tenant` task in `TASK_TENANCY` (#982), so its job runs in the tenant whose scope enqueued it, the same tenant its lane names.

## Task

Load `state-writes` (enqueues inside the sweep and trigger transactions) and `error-handling`.

1. **Lane helper.** In `actions.ts`, beside `resolveHeartbeatFireTaskName`, add an exported function and a module-private constant `AGENT_RUN_LANE = "agent-run"`:
   `resolveAgentRunLane(actionId: string): string | undefined` returns `tenantLane(AGENT_RUN_LANE)` when `resolveHeartbeatFireTaskName(actionId) === AGENT_TASK_NAMES.HEARTBEAT_FIRE_AGENT`, and `undefined` otherwise.
2. **Every agent-fire enqueue gets the lane.**
   - At `schedulerStore.ts:320-325`, `queueName` becomes `resolveAgentRunLane(row.action_id)` when defined, otherwise the existing affinity expression from #1016.
   - At `schedulerStore.ts:509-514` and `heartbeatAgentTools.ts:207-212`, add `queueName: resolveAgentRunLane(<actionId>)`.
   - Job keys, `maxAttempts` and `jobKeyMode` are unchanged. Non-agent fires keep exactly today's queue name.
   - Outside a tenant scope the lane is `undefined`, matching today's behaviour.
3. **Tests.** New `backend/packages/data/src/__tests__/agentRunLane.test.ts` covers the criteria below. Read `queue_name` as `backend/packages/data/src/__tests__/inboxTick.test.ts:39-48` does. Enqueue-site cases run inside `runInTenant(<sole tenant id>)` (`SELECT app_sole_tenant()`), because their heartbeat rows need a real tenant. The two-tenant case calls `resolveAgentRunLane` directly inside two `runInTenant` scopes with arbitrary UUIDs, which is enough because it reads only the scope.

## Scope

### In scope
- One per-tenant lane for every heartbeat fire that starts an agent session, at all three enqueue sites.

### Out of scope
- The lane helper and the other lanes (#1016).
- Producers for the `agentRun` and `delegatedAgentRun` tasks; none exist. A future producer must use `resolveAgentRunLane`'s lane, per the lane ADR.
- In-process delegated sessions (#1045).
- Semp conversations in the API process.
- The worker's global concurrency.
- Agent-run attribution (#1018).

## Acceptance criteria

- **Lane on every enqueue site.** Inside `runInTenant(T)` with T the sole tenant, each of these enqueues its `heartbeatFireAgent` job with `queue_name = 'agent-run:<T>'`:
  - a swept `core.agentRun` heartbeat;
  - an `onItemEvent` `core.agentRun` heartbeat;
  - a manual `heartbeat.trigger`.

  (integration, `agentRunLane.test.ts`)
- **Distinct lanes per tenant.** `resolveAgentRunLane("core.agentRun")` returns `agent-run:<T>` inside `runInTenant(T)` and `agent-run:<U>` inside `runInTenant(U)`. (integration, `agentRunLane.test.ts`)
- **Other actions untouched.** A non-agent heartbeat fire, e.g. `semprec.tick`, keeps the queue name #1016 gives it, or none. (integration, `agentRunLane.test.ts`)
- **No scope, no lane.** With no tenant scope, agent fires are enqueued with a NULL `queue_name`, exactly as before. (integration, `agentRunLane.test.ts`)
- **Lane serializes.** With a worker running, two `heartbeatFireAgent` jobs in the same lane never execute at the same time: a blocking first handler delays the second until it returns. Two jobs in different tenants' lanes do run concurrently. (integration, `agentRunLane.test.ts`)
- **Job keys unchanged.** Job keys and attempt counts are unchanged, so existing `scheduler.test.ts` dedupe and retry cases pass. (integration)
