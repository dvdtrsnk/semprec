## Context

Issue #252 defined the generic operation catalog and #219 its neutral application service; #220 exposed it through AgentTools and `POST /mcp` and routed destructive agent calls into #32's pending-request writer with a plain binding replay on approval. That replay is not yet bound to the reviewed resource state and has no exactly-once guarantee under crashes or retries. This issue completes the audit fix: a transactional, mutation-free preflight that persists a resource snapshot together with the pending request and its notification, a locked approval-execution transaction that executes each of the five destructive operations exactly once, deterministic conflict terminalization, and a migration that makes pre-feature approvals non-executable.

## Task

Extend `approval_requests` with `execution_status text not null default 'not_approved' check (execution_status in ('not_approved','queued','succeeded'))`, `execution_result jsonb`, and `executed_at timestamptz`; approving atomically sets approval status to `approved`, execution status to `queued`, and enqueues `approvalExecute`. The job opens one database transaction, locks the request `FOR UPDATE`, and: returns persisted `execution_result` without mutation when already succeeded; rejects any non-approved/non-queued row; otherwise revalidates persisted actor/capability/input and executes the destructive choke-point `*WithClient` operation on that same transaction/client, then stores its authoritative wrapper result, sets succeeded/executed_at, and commits. Crash/error before commit rolls back mutation and status together, leaving queued for graphile retry; crash after commit retries into the succeeded branch. No durable `running` state is needed. Define internal `ApprovedOperationExecutor<Tx>.execute(tx, actor, operationName, input)` for the five destructive bindings (`database.archive`, `property.delete`, `view.delete`, `item.delete`, `relation.delete`); it is implemented over transaction-scoped data functions and is never externally callable. This row lock plus atomic mutation/result commit is the mandatory `approvedRequestId` dedup key and exactly-once effect protocol for all five operations; it replaces the non-transactional binding replay of #220 while keeping its `owner_violation` provenance check and its rule that the `{ approvedRequestId }` context bypasses only the already-satisfied approval check, never validation/capability/authz.

Define `DestructiveApprovalPreflight<Tx>.authorize(tx, actor, operationName, input): Promise<{ canonicalInput, resourceVersionSnapshot }>` in the neutral application layer. It performs no mutation: strict schema validation first, capability check second, persisted actor-provenance check third, then the same resource existence/ownership/locked/archive/version authorization reads used by the destructive command. Error precedence follows that order, and any failure rolls back with no approval row/notification. On success, in that same transaction call #32's approval-request writer and #36's notification writer to atomically insert the pending request plus `approval_pending` notification using `canonicalInput`/snapshot. The interceptor of #220 now invokes this preflight instead of the plain writer call; the authenticated actor invariant of #220 is enforced before preflight. Execution later repeats full authorization; changed state fails safely. Tests prove unknown/unauthorized/locked/version-conflicting calls create neither row.

Add `approval_requests.resource_snapshot jsonb not null` and persist payload exactly as `{ operationName, canonicalInput, actor: { runId, agentProjectItemId, userId }, resourceSnapshot }`. `resourceSnapshot = { kind, resourceId, sha256 }`, where lowercase SHA-256 is over the self-contained canonical JSON serializer from #85 applied to these exact projections: archive database → full `Database` row; delete property → full `Property` row plus `{ databaseSchemaLocked, databaseArchivedAt }`; delete view → full `View` row including concrete creator identity from #87; delete item → `{ id, databaseId, updatedAt, deletedAt, databaseArchivedAt }`; delete relation → full `RelationEdge` plus the authorizing relation property's `{ id, owner, ownerProcess, locked }`. Preflight returns and persists this typed snapshot.

The exact kind/id mapping is: `database_archive` / input `databaseId`; `property_delete` / input `propertyId`; `view_delete` / input `viewId`; `item_delete` / input `itemId`; `relation_delete` / the loaded authoritative `RelationEdge.id` (not the property/endpoint tuple). No other kind is valid for a new request.

During the locked approval-execution transaction, after current authz and before mutation, rebuild the same projection and require `kind/resourceId/sha256` equality. Mismatch performs no mutation, stores `execution_status='conflict'` and `execution_result={ error: { code: 'version_conflict', details: { currentResource } } }`, sets `executed_at`, and commits as a terminal non-retry result. Extend the execution-status check to include `conflict`; retries return that persisted result. Equality proceeds to the exactly-once mutation protocol. Thus destructive operations need no external `ifVersion` but approval is bound to the exact reviewed resource state.

Execution classifies revalidation deterministically. Any current domain failure `not_found`, `owner_violation`, `schema_locked`, `property_locked`, `database_archived`, `version_conflict`, or `validation_failed` is a terminal conflict: catch it inside the locked transaction, perform no mutation, persist `execution_status='conflict'` and `execution_result={ error: { code: 'version_conflict', details: { reason: originalCode, currentResource } } }`, then commit. `currentResource` is `null` for not-found; otherwise it is the current projection above. Capability revocation is `reason: 'owner_violation'`. Only infrastructure failures (database connection/serialization exhaustion/process crash) escape and roll back to queued for graphile retry. Snapshot comparison happens after current projection load but before destructive authorization can throw indefinitely; all listed domain failures are terminalized.

For populated upgrades, first add `resource_snapshot`, `execution_status`, `execution_result`, and `executed_at` nullable and extend execution status with `legacy_terminal`. Lock existing approval rows and remove any pending `approvalExecute` queue jobs referencing them. Existing `pending` rows become `status='rejected'`; existing `approved` or `rejected` keep that decision status. Every legacy row gets `resource_snapshot={ kind: 'legacy_unavailable', resourceId: approvalRequestId, sha256: null }`, `execution_status='legacy_terminal'`, `execution_result={ error: { code: 'validation_failed', details: { reason: 'approval_snapshot_unavailable' } } }`, and `executed_at=migration timestamp`. Unknown legacy status aborts migration. Then apply NOT NULL/default/check constraints for new rows. `approvalExecute` treats legacy_terminal as a persisted no-op result, so no pre-feature approval can execute without reviewed snapshot. A populated-upgrade test covers pending/approved/rejected rows and queued jobs.

Parameterized tests cover one-time replay parity for all five destructive operations across the AgentTool and incoming MCP projections of #220.

## Scope

## Acceptance criteria

- Approval replay tests inject crashes before and after commit for all five destructive operations and prove one effect plus stable persisted result.
- Deleted/changed/unauthorized reviewed resources terminalize with exact conflict results; populated legacy approvals are made non-executable before NOT NULL constraints apply.
- Unauthorized destructive calls create no approval/notification; a successful preflight inserts the pending request and the `approval_pending` notification atomically with the typed snapshot.
- Every new request carries exactly one of the five snapshot kinds with the specified resource id and a SHA-256 over the specified projection; any other kind is rejected.
- A retried `approvalExecute` for a succeeded, conflict, or legacy_terminal row performs no mutation and returns the persisted `execution_result`; a non-approved/non-queued row is rejected.
- Only infrastructure failures leave a request `queued`; every listed domain failure commits a `conflict` result with `reason: originalCode` and the correct `currentResource`.
