**Model tier:** medium

## Context

Model tier rationale: Three producers of the same kind (a deduplicated problem next to an existing notification) over existing paths with fixtures, with one cross-tenant detail for operator alerts that is already solved by the existing alert writer.

Several existing failures should appear in the Semp status view, one entry per cause. Today each only writes a notification: guidance drift (`agent_guidance_drift`, written by `backend/packages/application/src/projectAgentGuidance/driftAction.ts`), library automation errors (`automation_error`, written by `backend/packages/data/src/library/libraryMetadataJob.ts` with source `item_automation`), and operator alerts (`backup_restore_failed` from `backend/packages/data/src/observability/restoreTestResult.ts`, `process_stale` from `backend/packages/data/src/observability/observabilityCheckSystem.ts`, written to administrators by `operatorAlerts.ts`).

This issue raises a problem for each, next to its notification and in the same transaction, using the store of #1459. Heartbeat and run failures, chat replies, mail and transcription are separate issues (#1911, #1931, #1506, #1945). The readers are the same as for all problems; recovery is #1915 and the backfill is #1958.

It builds on the deterministic fingerprint of drift findings (#1375).

Decision: dedupe keys. Guidance drift: `guidance:<projectId>:<fingerprint>`, one problem per finding (category `guidance`, kind `guidanceDrift`, severity `warning`, `project_item_id` set). Library automation: `automation:<databaseId>` (category `automation`, kind `libraryAutomation`, severity `warning`; the database is read from the failing item). Backup restore failure: `backup:restoreTest` (category `backup`, kind `backupRestore`, severity `critical`). Stale `semprec-agents` process: `agents:process` (category `agents`, kind `processStale`, severity `critical`).

Decision: `backup_restore_failed` and `process_stale` problems are written only for users with the administrator role, one per administrator in that administrator's own tenant, exactly where `writeNotification` writes the operator alert. `queue_backlog` stays a notification only. Other processes than `semprec-agents` do not raise a problem here.

## Task

Load `state-writes` and `testing`.

1. In `driftAction.ts`, where a drift finding transitions to an active notification, call `raiseProblem` with the guidance key built from the fingerprint of #1375; the source is the finding (`source_table` `agent_guidance_drift_findings`, `source_id` the finding id) and the `occurrenceKey` is the fingerprint with the activation time, like the notification's transition instance.
2. In `libraryMetadataJob.ts`, in the failure transaction that calls `markItemAutomationError` and writes `automation_error`, read the item's database id and raise the automation problem; `occurrenceKey` is the job id.
3. In `restoreTestResult.ts` and `observabilityCheckSystem.ts`, raise the operator problems per administrator in the same per-recipient transaction as the operator notification. A `backup_restore_failed` raise happens only for a failed run; a stale process raises only for `semprec-agents`.
4. Add the key builders to `backend/packages/data/src/semp/sourceProblemKeys.ts`.
5. Tests: two drift notifications for one finding give one problem and two findings give two; three failing library jobs of one database give one problem; a failed restore test gives a `critical` problem for each administrator and none for a non-administrator; `queue_backlog` raises nothing; a rollback leaves no problem.

## Scope

### In scope

- Raising guidance drift, library automation, backup restore and stale-agents-process problems with the keys above.

### Out of scope

- The problem store (#1459), recovery (#1915) and the backfill (#1958).
- Heartbeat, run, reply, mail and transcription problems (#1911, #1931, #1506, #1945).
- The date of the last restore test shown in the services list (#1377).
- A problem for `queue_backlog` or for other processes.

## Acceptance criteria

- When drift is reported twice for one finding, then one active `guidance:<projectId>:<fingerprint>` problem exists; a different finding has its own.
- When library automation fails three times for items of one database, then one `automation:<databaseId>` problem exists with `occurrence_count` 3.
- When a restore test fails, then each administrator has one `critical` `backup:restoreTest` problem and a user without the administrator role has none.
- When the `semprec-agents` process becomes stale, then administrators get a `critical` `agents:process` problem; a stale `queue_backlog` does not.
- When the failing transaction rolls back, then no problem is created.
