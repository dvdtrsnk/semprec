## Context

Model tier rationale: The cause has to be found in the running app (which part of the diary is rebuilt or reloaded when a change signal arrives) before a targeted fix in the shared ViewModel or the SwiftUI page; one screen, existing test fixtures.

Since sp-256f9fba-cc77-4439-ba05-e29662015dbb, adding an Inbox capture makes the kept answers stale and the offline layer's change flow emit, and the open diary reads its period again, so the new entry appears at once. The owner tested build 85: when a capture is added, the whole diary page visibly reloads (the page is rebuilt instead of only the Inbox list gaining a row). The owner wants only the new entry to be added to the Inbox list; the rest of the page (the note, events, birthdays, the axis, the scroll position, the focus of the note editor) must stay as it is, without any loading state, flash or re-creation.

## Task

1. Reproduce on an iOS simulator with a signed-in account: open today's diary, add a capture from the diary's capture row, and record what is rebuilt or reloaded (the note editor reading its page again, the pager re-creating the page, a loading state, an animation, a scroll jump). Write the finding into the pull request description.
2. Fix it so that a change signal caused by a capture updates the shown period in place: only the Inbox list changes (the new row inserted with an ordinary list insertion), and the note, events, birthdays, axis, scroll position and note focus stay untouched; if other parts of the period answer did change, they update in place without re-creating the page or reloading the note.
3. Validate in the simulator after the fix with the same steps, online and offline (Network Link Conditioner or the airplane-mode equivalent of the simulator, or by stopping the server reachability), and attach before/after screenshots or a short description of what was observed to the handover.
