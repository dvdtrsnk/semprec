## Behavior specification

Tasks: schema, write rules, details, attachments, completion, deletion and Today.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions for job tasks-core-1

#### (a) Decisions adopted

- Task description storage (longText with Markdown vs per-item page) -> longText with Markdown -> readable by Semp and search, easy to copy; the design note recommends it. (#1540)
- One schema step vs schema per feature issue -> one idempotent cutover in #1540 -> fewer hotspot conflicts in the manifest, seed, cutover list and i18n. (#1540)
- Do people and attachments carry into the next recurring instance? -> yes, with project (allowlist project, people, files; flag and description too); hostEvents, actionItems, sourceEvents, completedInEvent do not. -> losing user data silently is worse than keeping it. (#1673)
- Task end time equal to start time -> 400 (field timeTo), not "store null". -> the later version of the write rules supersedes the older notes. (#1536)
- Blank task title -> rejected, value not rewritten (no trimming of stored title). (#1536)
- Unreadable stored dates and times in migration 1.2.0 -> null (not left as is). -> a corrupt date breaks ordering. (#1657)
- completedOn may not be in the future; may be earlier than date or since. -> conservative, per the design note's lean; early completion of a future occurrence uses today. (#1544) -> Decided by the product owner: completedOn may be earlier than the planned day; the user enters it as it really happened. A completed task is sorted and shown by its completion day; the planned date is never rewritten. (#1544, #1798; timeline: cross change for #1880)
- File with its own project attached to a task -> file keeps its own project (link starts broken). -> conservative. (#1654, #1702)
- File attached to two tasks -> link only to the task it was uploaded to first, no union. -> a file has one visible project. (#1702)
- Series trash -> whole series under one shared deletedAt; one restore of any instance restores all and re-activates exactly one recurrence rule. Events keep their edges and ignore the deleted task. (#1882)
- Today badge -> counts only notDone tasks of the Today list; the list itself includes done tasks of today. (#1798)
- Stable view key -> config.systemKey with a partial unique index, not owner_module_id (createView refuses ownerModuleId for built-in view types). (#1798)
- Semp refs for virtual occurrences -> {kind taskOccurrence, seriesId, occurrenceDate} and {kind taskTrace, itemId, databaseId, traceDay}; an ordinary task uses the existing item ref. (#1771)
- Label of the open status option (key stays notDone) -> en "Open", cs "Otevřeno". -> Decided by the product owner: "Otevřeno" / "Open". (#1540)
- Action-item tasks: one source event or many; all attendees or only assigned ones -> Decided by the product owner: handled in #1724, not in this batch.
- persistent and notifications on Tasks: explain or remove? -> Decided by the product owner: remove; properties without described behavior are not kept in v1 (no speculative generality) and come back with concrete behavior if needed. Applied to `persistent` (#2009; cross change for #1796). `notifications` is kept because #1719 (calendar reminders) gives it concrete behavior as the task reminder switch.
- wontDo on a repeating task: stop the series or advance it? -> today it stops the series. -> Decided by the product owner: advance to the next occurrence; wontDo concerns only this occurrence and the user ends a series explicitly, which is predictable and reversible (cross change for #1670, which owns the series advance).

#### (b) Open questions for the product owner

- Whether recurrence storage (seriesId, occurrenceDate, recurrence property types and owners) stays as assumed in #1540 after the recurrence ADR (#1365) is written; #1673 is dropped if virtual occurrences are chosen.
- Path problems (not product questions): see report.

#### (c) User-visible behavior delivered by this chunk

Tasks gain the fields and rules the new task screens need: a flag, a Markdown description, people and file links (shown on the person and in Files), validated dates, titles and start/end times (an end time can be 24:00; changing the date off clears the times), and a recorded completion day and time so a task completed early or late shows on the right day. Photos and files can be uploaded straight onto a task, and an attachment follows the task's project until the user chooses another one. A repeating task carries its flag, description, project, people and files into the next instance. A completed task is shown on the day it was completed, also in Today, and setting one occurrence of a repeating task to won't do moves the series on to the next occurrence. Deleting any instance of a repeating series trashes the whole series for 30 days, restoring brings it back with the repeat rule on, and the confirmation tells how many attachments, instances and events are affected. Semp can be asked about a task, a future occurrence or a past trace. The server provides one definition of the Today list (due today plus unfinished overdue tasks, minus tasks hidden in running events or completed in events), a protected system view for it and the open-task count for the overview badge.
