## Context

`propertyDeleteWithClient` in `backend/packages/data/src/chokePoint/propertyOps.ts` (lines 28-58) guards a *relation* property's deletion with `assertRelationDeletable` (`backend/packages/data/src/rollup/mirror.ts`, lines 12-19: refuses when `rollup_dependencies.relation_definition_id` references it), but a non-relation property gets no check at all before `propertiesStore.deleteProperty` (line 52). A rollup with `targetPropertyKey` records that source in `rollup_dependencies.source_property_key` (`backend/packages/data/src/rollup/dependencies.ts`, `upsertRollupDependency`; index `rollup_dependencies_source_idx` in `0001_core_schema.sql`). Deleting that source property leaves the dependency row pointing at a key no property has: `findDependenciesBySource` keeps firing recompute jobs for writes to the now-free key if a user recreates it with another type, `assertSourceRetypeAllowed` (`mirror.ts`, lines 25-52) guards a property that no longer exists, and the rollup itself silently aggregates `properties ->> 'gone'` — NULL everywhere — until someone notices. The retype path already has the symmetric guard (`assertSourceRetypeAllowed`, called at `propertyOps.ts` line 97); delete has none.

## Task

1. `rollup/mirror.ts`: new exported `assertSourceDeletable(client: PoolClient, sourceDatabaseId: string, sourcePropertyKey: string): Promise<void>` that calls `findDependenciesBySource` and, when any row exists, throws `new ValidationError("Cannot delete a property that dependent rollups still aggregate", { dependentRollups: [...rollupPropertyId] })` — the same error class, message shape and `dependentRollups` detail as `assertRelationDeletable`, so the API surface is uniform (both refusals are 400 `validation_failed` naming the dependent rollup property ids).
2. `propertyDeleteWithClient`: for a property whose `type !== 'relation'`, call `assertSourceDeletable(client, property.databaseId, property.key)` before `propertiesStore.deleteProperty(client, id)`; the check runs inside the same transaction as the delete (it already does — the function receives the caller's client).
3. Test in `backend/packages/data/src/__tests__/propertyOps.test.ts` (integration): a parent database with a `sum` rollup over a child database's `amount` property; `chokePoint.deleteProperty(amount.id)` rejects with `ValidationError` whose `details.dependentRollups` contains the rollup property id and the `amount` row still exists; after `chokePoint.deleteProperty(rollup.id)` (which cascades its `rollup_dependencies` row by FK), deleting `amount` succeeds; deleting an unrelated property of the child database was never blocked.

## Scope

### In scope
- The source-property delete guard and its test.

### Out of scope
- The duplicate-key 409 on `createProperty` (sibling issue C18).
- Rollup recompute correctness (sibling issue C10).
- Cascading a rollup's deletion when its source goes (explicitly refused instead, matching the relation case: the user's path is delete the rollup first).

## Acceptance criteria

- When a property is the `targetPropertyKey` of at least one rollup, `DELETE /api/properties/:id` (and the approved-operation executor's `propertyDeleteWithClient`) responds 400 `validation_failed` with `details.dependentRollups` listing those rollup property ids, and the property row is unchanged.
- When no rollup depends on the property, deletion behaves exactly as before.
- When the dependent rollup is deleted first, the source property can then be deleted.
