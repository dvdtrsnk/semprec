**Blocked by:** #1386
**Model tier:** high

## Context

Model tier rationale: It changes cancellation semantics across every pipeline step that makes paid calls, with concurrency against deletion, retries and the failure path, so a gap would either bill for deleted data or leave jobs failing permanently.

Soft-deleting a transcript or its source Files item does not stop a running `transcriptionJob`: `getItemById` and `lockItemById` return deleted rows, so diarize, ASR and summarize keep running and paying. On the last attempt `recordTranscriptionFailure` (`backend/services/semprec-transcribe/src/transcriptionTask.ts`) calls `updateItemWithClient(status error)`, which throws `NotFound` for a row in Trash; the transaction rolls back, no notification is written, `item_automation` stays `pending` with the previous attempt's error, the transcript stays `processing` and the job ends permanently failed (counted in `queue.permanent` of `GET /api/system-health`). The requeue sweep never sees it because it reads only `status error`. `listErroredItemAutomationForDatabases` already skips rows in Trash, but `getItemAutomationErrorCounts` in `observability/systemHealthReport.ts` does not filter `deleted_at`, so a deleted transcript's earlier error still counts in `itemAutomationErrorsByDatabase`.

This issue makes a deleted transcript or deleted source file a clean stop. Every step checks for it before any write or paid call and treats it as "stop": no further paid call, `item_automation.status` set to `error` with `error_code` `deleted` (#1386), no notification and no Semp problem, and the job finishes successfully (not permanently failed). A restore can be rerun by the existing rerun route. The earlier problem in Semp's status is closed by #1945.

## Task

Load `state-writes`, `error-handling`, and `testing`.

1. Extend `requireTranscriptionUnlocked` (or a sibling used by every step's first transaction) to also load the transcript and the source Files item and throw a `TranscriptionStoppedError` when either has `deleted_at` set or is gone.
2. In the task wrapper catch `TranscriptionStoppedError`: in one transaction set `item_automation` to `error` with code `deleted` (without touching the `items` row, which may be in Trash) and end the job successfully; write no notification.
3. Make `recordTranscriptionFailure` fall back to this same path when the transcript is in Trash instead of attempting the `status` update.
4. In `getItemAutomationErrorCounts` count only automation rows whose item has `deleted_at IS NULL`.
5. Tests: deleting the transcript during diarize makes the next step skip the paid ASR call; no `automation_error` is written; `item_automation` is `error`/`deleted` and the job is not permanent; deleting the source file does the same; a deleted item does not count in `itemAutomationErrorsByDatabase`; rerun after restore works.

## Touches

- backend/services/semprec-transcribe/src/transcriptionTask.ts (all step guards, wrapper, failure path)
- backend/packages/data/src/observability/systemHealthReport.ts (`getItemAutomationErrorCounts`)
- backend/services/semprec-transcribe/src/transcriptionTask.test.ts and backend/packages/data/src/__tests__/ (stop and health tests)

## Scope

### In scope

- The stop on deletion in every step, the `deleted` error code, the failure-path fix, and the health count.

### Out of scope

- Adding the `error_code` column: #1386.
- Closing the Semp problem of a deleted transcript: #1945.
- Deleting a recording as a user action: #1642.
- Purging derived blobs: #1421.

## Acceptance criteria

- When a transcript is deleted during diarization, then the next step makes no paid call, no `automation_error` notification is written, `item_automation` is not left `pending`, and the job does not end as permanently failed.
- When the source Files item is deleted, then the pipeline stops the same way.
- When a transcript in Trash had an error, then it is not counted in `itemAutomationErrorsByDatabase`.
- When the item is restored and rerun is requested, then the pipeline runs again.
