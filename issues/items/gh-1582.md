## Context

Model tier rationale: It changes cancellation semantics across every pipeline step that makes paid calls, with concurrency against deletion, retries and the failure path, so a gap would either bill for deleted data or leave jobs failing permanently.

Deleting a transcript or source must stop checkpointed transcription rather than leave automation pending or exhaust retries. Existing item reads include Trash: guards and failure recording must handle missing/deleted rows. Stop leaves automation error/deleted without an item-row write, notification or Semp problem and completes the job. Health excludes Trash; restore uses the existing rerun route. #1386 owns error codes, #1421 derived purge and #1945 problem closure. Only committed checkpoints are reusable; in-flight uncheckpointed work may repeat.

## Task

Load `state-writes`, `error-handling`, and `testing`.

1. Guard every step/checkpoint, attempt start and failure transaction per `docs/adr/2026-11-01-transcription-stop-guards-lock-items-before-automation.md`: source Files FOR UPDATE -> transcript FOR UPDATE -> automation FOR UPDATE. Use uniform item-first order, not a failure-only reversal. Keep locks out of slow work. Step0 locks source before checkpoint/create; a deleted replay settles existing automation. If source was purged before a retry, recover an earlier transcript only via the existing exact transcription idempotency-key read, lock/recheck it and never create/reserve a replacement. Throw `TranscriptionStoppedError` for deleted/gone targets; no broad SQL-error relabeling.
2. Catch `TranscriptionStoppedError` and finish successfully: mark only existing unlocked automation error/deleted, change no items and write no notification. Do not fabricate purged automation. Deleted targets still finish when an existing automation row is locked, leaving it unchanged; with live targets preserve existing locked handling. Missing automation on live targets is an invariant error, not deletion/locked. Start may ensure only under live item locks. Automation-only stop settlement need not take later item locks.
3. Before ANY normal failure recording, including transient and throwing-provider paths, check BOTH locked source and transcript. Missing/deleted targets use the same stop, never normal error notification/status writes; retain actual diagnostics and safe outward errors for unrelated failures. Do not catch arbitrary NotFound/FK/40001 as deletion.
4. In `getItemAutomationErrorCounts` count only automation rows whose item has `deleted_at IS NULL`.
5. Tests: deleting the transcript during diarize makes the next step skip the paid ASR call; no `automation_error` is written; `item_automation` is `error`/`deleted` and the job is not permanent; deleting the source file does the same; a deleted item does not count in `itemAutomationErrorsByDatabase`; rerun after restore works through actual authenticated HTTP restore/rerun, the real queued production transcription task and completion. Use the isolated child fixture of `docs/adr/2026-11-01-transcription-http-evidence-uses-an-isolated-producer.md`; assert stopped state, enqueue/consumption and only committed-checkpoint reuse, without cross-service imports or repeated-work guarantees for uncheckpointed calls. Add actual queued purge-before-start, create/start gap, in-flight throwing-gateway and prior-checkpoint source-purge controls; bounded identified-PID overlaps in both relevant orders, rollback, live/locked/unrelated-error positives, and tenant-scoped key recovery. Preserve invalid-fixture logs separately.

## Acceptance criteria

- When a transcript is deleted during diarization, then the next step makes no paid call, no `automation_error` notification is written, `item_automation` is not left `pending`, and the job does not end as permanently failed.
- When the source Files item is deleted, then the pipeline stops the same way.
- When a transcript in Trash had an error, then it is not counted in `itemAutomationErrorsByDatabase`.
- When the item is restored and rerun is requested, then the pipeline runs again.
