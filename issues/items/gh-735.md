## Context

Review follow-ups harvested in #728, both in the Inbox proposal flow:

- PR #286 — `backend/packages/data/src/__tests__/inboxTickProposal.test.ts:448`: both `describe` blocks define identical `findProposalForItem` and `runTick` helpers (lines 46-71 and 448-473), so a change to the proposal lookup must be made twice.
- PR #328 — `backend/packages/data/src/inbox/proposalActions.ts:257`: when a credential is supplied, `confirmProposalWithClient` calls `databasesStore.getDatabase(client, envelope.target)` to check `ownerModuleId`, although `assertValidProposalEnvelope` (`backend/packages/data/src/inbox/inboxTickAction.ts:229`), reached through `assertValidEnvelopeForCard` at `proposalActions.ts:251`, already fetched that row in the same transaction.

Issues #655, #662 and #676 edit `inboxTickAction.ts`, `proposalActions.ts` and `inboxTickProposal.test.ts`; this issue starts from those files as they leave.

## Task

1. In `inboxTickProposal.test.ts`, define `findProposalForItem` and `runTick` once at module scope, taking the database ids they need as parameters, and make both `describe` blocks call them; delete the two local copies.
2. Make `assertValidProposalEnvelope` return the target `DatabaseRow` it fetched for a `'database'` envelope and `null` for every other `entityKind`; make `assertValidEnvelopeForCard` pass that row back to `confirmProposalWithClient` alongside the transcript-card edge; and have the credential guard in `confirmProposalWithClient` check `ownerModuleId` on that row instead of calling `databasesStore.getDatabase`. The guard's error (`ValidationError`, field `credential`) is unchanged. Existing callers that ignore the return value keep compiling.

## Touches

- backend/packages/data/src/__tests__/inboxTickProposal.test.ts
- backend/packages/data/src/inbox/inboxTickAction.ts (`assertValidProposalEnvelope` only)
- backend/packages/data/src/inbox/proposalActions.ts (`assertValidEnvelopeForCard` and the confirm credential guard only)

## Scope

### In scope

- The two changes above.

### Out of scope

- Any other validation or read in `assertValidProposalEnvelope` or the confirm path.

## Acceptance criteria

- `inboxTickProposal.test.ts` defines `findProposalForItem` and `runTick` exactly once each, and every test in it passes.
- `confirmProposalWithClient` in `proposalActions.ts` contains no `databasesStore.getDatabase` call.
- The existing tests in `mcpServerProposal.test.ts` still pass: confirm with a credential on an MCP server proposal stores the item and the encrypted credential, and confirm with a credential on a non-`mcpServers` target is rejected with "A credential may only be supplied when confirming an MCP server proposal".
- `assertValidProposalEnvelope` resolves to the target database row for a valid `'database'` envelope and to `null` for a valid `'pageContent'` envelope, each asserted in a test.
