## Context

Model tier rationale: This writes a permanent, user-visible summary of tool inputs and results that must exclude sensitive-database content and survives event retention, and it spans the tool result shape, a new migration and token attribution, so a mistake leaks data or mis-states what the agent did.

A Semp reply in chat shows a summary line ("3 steps - 4 s", "2 steps - waiting for you", "2 steps - failed", "3 steps - 9 s - on the second try") and an expandable list of steps, each with a description, a short detail line, a duration and a state of ok, waiting or error. Today none of this is stored with the reply. The raw material exists only as `agent_run_events` (`backend/packages/data/src/agentRuns/agentRunEventsStore.ts`): `tool_use { toolCallId, name, arguments }` and `tool_result { toolCallId, name, result, isError }` as written by `backend/services/semprec-agents/src/piAgentSession.ts`, with `at` as the write time. They can only be read through the realtime `agent:watch` channel, and the retention job (`agentRunEventsRetention.ts`) deletes events older than 30 days for completed session runs. Token usage is only in `ai_gateway_calls` (`aiGatewayCallsStore.ts`), without a link to a reply until #1744 adds `ai_gateway_calls.semp_message_id`.

This issue computes the summary once, at the end of a turn, and stores it with the assistant message so it is available in message history after retention and without joining events.

It builds on the queued turn handler (#1727), which writes `agent_run_id`, `event_from_id` and `event_to_id` on the assistant message; on structured tool results (#1527: `details.approvalRequestId` and `details.changes` of `{ key, before, after }`); on the typed step projection (#1847: title, target name and change as i18n keys); on token attribution (#1744); on MCP failure kinds (#1444); and on the Semp-thread run model of heartbeat ticks (#1557). #1885 (changed items), #1890 (whether a reply left a failed tool call), #1889, #1887 and #1932 read what is stored here.

Decision: a step of kind `model` is recorded only for an intermediate model generation, that is an assistant message in the turn that carries text and is followed by further tool calls or by a later assistant message in the same turn. The final assistant message of a turn is the reply itself and is never a step. "N steps" counts tool steps plus model steps.

Decision: `errorCode` on a generic operation tool result is introduced here: when a generic operation fails with a `ChokePointError`, the tool result carries `details.errorCode` equal to `ChokePointError.code` (today `genericOperationAgentTools.ts` only puts the code into the result text). For MCP tool results the code is the `failureKind` from #1444.

Decision: what a step may show of inputs and results is conservative. `detail.params` carry only counts, durations, timestamps, names of targets and the `before -> after` of fields from `details.changes`. They never carry free text from tool arguments or results, and for items in a database marked sensitive they carry neither `detail.params` nor `before -> after` (the same redaction as #1827). Steps are stored permanently, outside event retention, so this rule is applied when writing, not when reading.

## Task

Load `state-writes`, `canonical-keys`, `io-hardening`, `db-migrations` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_semp_messages_steps.sql` (next free ordinal at commit time): add to `semp_messages` the columns `steps jsonb`, `duration_ms integer` and `tokens jsonb` (`{ input, output }`), all nullable (a reply that has no finished turn has none). Keep the tenant row-level security and composite foreign key conventions of the table; add no new table.
2. In `genericOperationAgentTools.ts` and `backend/services/semprec-agents/src/agentSessionComposition.ts`, return `details.errorCode` on a failed generic operation result as described above, and pass `details` through from the tool result (today the session composition returns only `{ error }`). Tool-call ids (`toolCallId`) already reach `execute`; use them so a step can be matched to its `tool_use` and `tool_result` events.
3. Add a pure projector `backend/packages/data/src/semp/sempReplySteps.ts` that turns the events of one turn (`agent_run_id` = the message's run AND `id BETWEEN event_from_id AND event_to_id`) into the stored array. Each element: `kind` (`tool` | `model`), `toolCallId?`, `toolName?`, `operation?`, `label { key, params }`, `detail { key, params }`, `status` (`ok` | `wait` | `error`; the same set as the state of a step in #1847, `running` only while the turn runs and never stored), `startedAt`, `durationMs`, `approvalRequestId?`, `errorCode?`, `tokens?` (only if the message event of a model step carries usage). `label` and `detail` are i18n keys with params taken from the shared projection of #1847 (`step.itemPatch { itemName, changedKeys }`, `step.modelSummary`); a tool call that is waiting for approval has status `wait` and the `approvalRequestId` from its result. Unknown tools get a generic key, never raw argument text.
4. Add the writer in the same module family (`backend/packages/data/src/semp/sempMessagesStore.ts`, extending the store of #1727; confirm the file name against that PR): at the end of the turn, in the transaction that stores the final message status, write `steps`, `duration_ms` (time from the `turn_start` event to the `turn_end` event of the turn, not the sum of steps) and `tokens` (the sum of `input_tokens` and `output_tokens` of `ai_gateway_calls` rows with `status = 'settled'` and `semp_message_id` = this message; `reserved` and `failed` calls are ignored, and two replies of one thread each have their own). Call it from the turn handler of #1727 (`backend/services/semprec-agents/src/sempMessageTask.ts`), also when the turn ends in an error (steps up to the failure are kept).
5. Tests: a reply with two tool calls has two `tool` steps with the right `durationMs` and `status`, and `duration_ms` is the turn time, not the sum; a delete awaiting approval has `status` `wait` and the same `approvalRequestId` as the `approval_requests` row; steps remain readable after the events are deleted by retention; tokens count only settled calls of this reply; a step on an item of a sensitive database has no `detail.params` and no `before -> after`; a failed generic operation yields `errorCode` equal to the choke point code.

## Scope

### In scope

- The `steps`, `duration_ms` and `tokens` columns, the projector, the end-of-turn write, and `details.errorCode` for generic operations.

### Out of scope

- The list of items a reply changed (#1885).
- Deriving whether a reply left a failed tool call (#1890) and classifying a failed reply (#1907).
- Live approval state of a waiting step (#1887).
- The full step list and cost of a run (#1821, #1822) and the Semp-message scoped run detail (#1889).
- Redacting events themselves in run history (#1827).
- Showing summaries for heartbeat tick replies beyond what the tick thread run model (#1557) already stores.

## Acceptance criteria

- When a reply makes two tool calls, then its `steps` has two `tool` steps with correct `durationMs` and `status`, and `duration_ms` is the time of the whole turn.
- When a call to a delete is pending approval, then its step has status `wait` and an `approvalRequestId` equal to the stored approval request.
- When the 30-day event retention has removed the events, then the stored `steps` are unchanged.
- When a turn makes gateway calls, then `tokens` equals the sum of the settled calls attributed to that reply, and a second reply in the same thread has its own totals.
- When a step touches an item in a sensitive database, then the stored step has no field values and no free text from arguments or results.
- When a generic operation fails with a choke point error, then its step has `status` `error` and `errorCode` equal to that error's code.
