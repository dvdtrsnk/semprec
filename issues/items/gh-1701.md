**Model tier:** high

## Context

Model tier rationale: A new authenticated credential-change route that re-verifies the password under a row lock, shares the login lockout, and revokes sessions, push registrations and outstanding reset tokens atomically, so it is an authentication and concurrency contract.

A signed-in user can change the password only by asking for a reset email (`POST /api/auth/password-reset/request`, then `consume`). `consume` revokes every session and push registration of the account, which also signs out the device the change was started from, and the user never proves they know the current password. There is no authenticated password change.

`deleteOwnAccount` (`backend/packages/data/src/tenancy/deleteAccount.ts`) already shows the pattern for re-verifying a signed-in user's password: it reads the failure streak with `getFailureStreak` before verifying (a locked (email, IP) pair is not verified), records a failed `recordLoginAttempt` on a wrong or locked attempt, throws `ReauthenticationFailedError` (HTTP 403 `reauthentication_failed`, deliberately not 401, which clients treat as "signed out"), and compares `password_hash` under a `FOR UPDATE` row lock. `passwordResetStore.ts` can create, count and consume reset tokens but cannot invalidate unconsumed ones. This issue builds on #1650, whose `revokeOtherUserSessions` keeps the caller's session and revokes the rest with push registrations.

Decision: the profile "change password" action is a proper change (current password plus new password), not a reset email. Resetting by email stays available for the sign-in screen.

Shared-file ordering: this issue also waits for #1699 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Add `POST /api/auth/password-change` in `authHandler.ts` with body `{ currentPassword, newPassword }`, authenticated with `authenticateRequest`. Missing or non-string `currentPassword` is 400 `validation_failed` (`details.field` `currentPassword`); a `newPassword` shorter than `MIN_PASSWORD_LENGTH` (8) is 400 with `details.field` `newPassword`.
2. Add an action `changePassword(pool, input)` in a new `backend/packages/data/src/auth/passwordChangeActions.ts` modelled on `deleteOwnAccount`: first `getFailureStreak(email, ip)` and, when the pair is locked, skip verification, record `recordLoginAttempt({ succeeded: false })` and throw `ReauthenticationFailedError`; otherwise verify `currentPassword` with `verifyPassword`; a wrong password records a failed attempt and throws the same error. The client IP comes from `clientIpFromRequest` like login.
3. On a correct password, in one `withTransaction`: lock the user row `FOR UPDATE`, compare its `password_hash` with the verified one (different means a concurrent change, throw `ReauthenticationFailedError`), write the new Argon2id hash, call `revokeOtherUserSessions` (#1650) with the current session id, and mark every unconsumed reset token of the user consumed. Record a successful attempt so the lockout streak resets.
4. In `passwordResetStore.ts` add `consumeAllPasswordResetTokensForUser(client, userId)` (`UPDATE password_reset_tokens SET consumed_at = now() WHERE user_id = $1 AND consumed_at IS NULL`). A reset link issued before the change then fails with `password_reset_token_consumed`.
5. Respond 200 `{ "ok": true }`. The current session and its push registrations stay valid.
6. Register the route in `routeMatrix.ts` ("change password", `POST /api/auth/password-change`, `account`), add its case to `__tests__/tenantIsolationRoutes.test.ts` and map it to `authHandler.ts` in `ROUTE_HANDLER_FILES` of `__tests__/chokePointWriteBoundary.unit.test.ts`.
7. Add tests for each acceptance criterion below, including the concurrent-change race and lockout sharing with login.

## Scope

### In scope

- The route, the re-authenticating action, the reset-token invalidation and the route-matrix registration.

### Out of scope

- The email reset flow and its rate limits (unchanged).
- Opening the reset link in the iOS app: #1357.
- Any client text about being signed out of other devices.
- Notifying the user by email about the change (decided: v1 sends no system notification emails; the user sees the change in the sessions and devices list).

## Acceptance criteria

- When `currentPassword` is wrong, then the response is 403 `reauthentication_failed` (not 401), a failed attempt is recorded toward the (email, IP) lockout, and the calling token still works.
- When the (email, IP) pair is locked out, then the password is not verified and the response is 403 `reauthentication_failed`.
- When `currentPassword` is correct and `newPassword` is valid, then the response is 200, the new password logs in and the old one does not; the calling token keeps working; every other session of the user gets 401 and its push registrations are revoked.
- When a reset link was requested before the change, then consuming it afterwards returns 400 `password_reset_token_consumed`.
- When `newPassword` has 7 characters, then the response is 400 `validation_failed` with `details.field` `newPassword`.
- When two changes race with the same current password, then at most one succeeds and the other is 403.
