## Context

Model tier rationale: Two property checks added as one create hook and one update hook, following the Events validation hooks from the dependency and its fixtures, with no new lifecycle, tenant or persisted-data contract.

An Event can carry a reminder before it starts (`alertMinutes`) and a travel time that moves the reminder earlier (`travelMinutes`). #1416 adds both as `number` properties on Events; nothing checks them, so any number a client sends would be stored and later turn into a nonsensical reminder time. #1663 introduced the Events create and update hooks (`backend/packages/data/src/calendar/eventValidationHook.ts`, registered in `backend/packages/data/src/domainWriteHooks.ts`) for the date and time fields. Item hooks (`backend/packages/data/src/chokePoint/hooks.ts`) run inside the write's transaction and can reject a write by throwing `ValidationError` (`backend/packages/data/src/errors.ts`), which becomes HTTP 400 `validation_failed` with `details.field`. Because the choke point is shared, REST, the assistant's `item.patch` and MCP all get the same error.

Product behavior: an Event reminder is one of "at event time", 5 minutes, 15 minutes, 1 hour or 1 day before, or none; travel time is one of 15 minutes, 30 minutes, 1 hour, or none. An empty value means none.

#1719 computes reminder times from these values and assumes they are valid. #1761 also adds an Events create hook; hook order is registration order and this issue does not depend on it.

Decision: values are validated only for keys present in the write, so Events that predate these properties stay editable. Decision: `0` is a valid `alertMinutes` ("at event time") and must not be treated as empty.

Shared-file ordering: this issue also waits for #1710 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `error-handling`, `state-writes` and `testing`.

1. Add `backend/packages/data/src/calendar/eventReminderValuesHook.ts` exporting an Events create hook and an Events update hook. Declare the allowed sets once as constants: `EVENT_ALERT_MINUTES = [0, 5, 15, 60, 1440]` and `EVENT_TRAVEL_MINUTES = [15, 30, 60]`.
2. On create, and on update only when the patch contains the key: `alertMinutes` must be `null`/absent or one of the allowed numbers; `travelMinutes` likewise. Anything else (7, -5, 15.5, a string, a boolean) throws `ValidationError` with `field` `alertMinutes` or `travelMinutes`. A patch that sets a key to `null` clears it and is accepted.
3. Do nothing for databases other than Events.
4. Register both hooks in `backend/packages/data/src/domainWriteHooks.ts`.
5. Tests for REST, an agent `item.patch` and MCP (identical error body): each valid value, `null` clearing, and the rejections.

## Scope

### In scope

- Rejecting invalid `alertMinutes` and `travelMinutes` on Event create and update, on every write path.

### Out of scope

- Adding the two properties to the Events schema: #1416.
- Validating Event dates and times: #1663.
- Computing when a reminder fires: #1719.
- Reminders for Tasks: the existing `notifications` checkbox needs no validation.
- Letting the details screen edit these values after creation; that is a client change and needs no server work.

## Acceptance criteria

- When an Event is created with `alertMinutes` 7, then the response is 400 `validation_failed` with `details.field` `alertMinutes`.
- When an Event is created with `travelMinutes` 20, then the response is 400 with `details.field` `travelMinutes`.
- When an Event is created with `alertMinutes` 0 and `travelMinutes` 30, then it is stored.
- When a patch changes only `name` on an Event, then it succeeds even if the stored values are unusual.
- When a patch sets `alertMinutes` to `null`, then the value is cleared and the response is 200.
- When an assistant `item.patch` or an MCP write sends `alertMinutes` 7, then it receives the same error body as REST.
