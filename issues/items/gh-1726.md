**Blocked by:** #1666, #1679
**Model tier:** high

## Context

Model tier rationale: It merges two live records atomically across page content, several relation kinds and the trash, including edges owned by another process, so a partial failure would lose content or links.

A period (day, week, month) should have exactly one Journal entry, and #1666 stops a restore from creating a second live entry. Duplicates can still exist from earlier data. Journal entries have a page (document), relations such as the area and, after #1545, a project; Inbox items point at a day through a relation owned by the inbox process (`journalDay`), which must be changed with delete plus create using `ownerProcess: 'inbox'`, as #1666 does for a reservation. The page content of the duplicate can be appended to the survivor with Markdown insertion (#1679).

This issue adds `mergeJournalDuplicates` in the journal store: for a period with two live entries, keep the one created first as the survivor, move the other's page content to the end of the survivor's page, re-point every relation edge of the duplicate to the survivor (skipping an edge the survivor already has; Inbox `journalDay` edges by delete plus create with the inbox owner process), and move the duplicate to the trash, all in one transaction.

Decision: the oldest entry survives; the duplicate is trashed (recoverable for 30 days), never hard-deleted.

Decision: a merge changes links, so it never runs silently. The assistant prevents duplicates and only proposes a merge; this function runs after the user approves it, through an approval-gated operation added by #2017. The weekly cleanup heartbeat (#1883) finds the duplicated periods for the assistant and does not call this function itself.

## Task

Load `state-writes`, `error-handling`, `canonical-keys` and `testing`.

1. Add `mergeJournalDuplicates(client, { periodType, period })` in the journal module: lock both entries, verify both are live and for the same period, otherwise do nothing.
2. Append the duplicate's page content to the survivor with the Markdown insertion path (#1679, placement end, author `system`), preserving block order, with the duplicate's heading removed when it equals the survivor's.
3. Re-point relation edges generically for every relation property of the Journal database that the duplicate has; handle the Inbox `journalDay` edges as described; deduplicate against the survivor's existing edges.
4. Move the duplicate to the trash through the choke-point trash operation; return `{ survivorId, mergedItemId }`.
5. Tests: two live entries of one day yield one with the content of both pages and all edges; the second is in the trash; a repeated call is a no-op; a failure in the middle changes nothing; Inbox items of the duplicate day now point at the survivor.

## Acceptance criteria

- When two live entries exist for the same day, then after the merge one entry remains with the content of both pages and all relation edges, and the other is in the trash.
- When the merge is run again, then nothing changes.
- When the transaction fails halfway, then both entries are unchanged.
