## Context

`createHeartbeatTriggerTool` (`backend/packages/data/src/scheduler/heartbeatAgentTools.ts:163-192`) resolves the calling run's project, loads the heartbeat with `getHeartbeatForProject`, rejects an `onItemEvent` rule, and enqueues a `heartbeatFireCore`/`heartbeatFireAgent` job with `triggeredByRunId`. It never reads `heartbeat.enabled`. The manual-fire branch of `createHeartbeatFireTaskForAffinity` (`sweep.ts:158-199`) does not check `enabled` either — only the sweep (`WHERE enabled AND next_fire_at IS NOT NULL`, `schedulerStore.ts:442-443`) and `prepareHeartbeatOccurrenceFire` (`schedulerStore.ts:552-555`, scheduled occurrences only) do. So an agent can fire a heartbeat the user disabled through `setHeartbeatEnabled` (`schedulerStore.ts:205-235`), and the action runs.

The rule this issue enforces: a disabled heartbeat is never fired by the system. `heartbeat.trigger` is the only production entry point that bypasses the `enabled` check today.

## Task

1. In `createHeartbeatTriggerTool` (`heartbeatAgentTools.ts`), after the `isOnItemEventRule` check and before `enqueueJob`, add: `if (!heartbeat.enabled) return { error: true, result: HEARTBEAT_DISABLED_ERROR };` where `HEARTBEAT_DISABLED_ERROR` is a module-private `const HEARTBEAT_DISABLED_ERROR = "this heartbeat is disabled; enable it before triggering it"` (not exported, so `publicSurface.test.ts` is untouched). Extend the docstring above the factory with one sentence stating that a disabled heartbeat is refused without enqueueing.
2. **Test** (`backend/packages/data/src/__tests__/heartbeatAgentTools.test.ts`, integration): create a heartbeat, disable it with `setHeartbeatEnabled(client, id, false)`, call the trigger tool from a run in the same project → the result is `{ error: true, result: <the message above> }` and `graphile_worker` has no job for `manualHeartbeatFireJobKey(heartbeat.id)` (use the same job-count helper the existing "enqueues a manually-attributed fire job" case uses). Then re-enable it and assert the same call enqueues exactly one job.

## Touches

- backend/packages/data/src/scheduler/heartbeatAgentTools.ts (`createHeartbeatTriggerTool` and its docstring)

## Scope

### In scope
- The `enabled` refusal in `heartbeat.trigger` and its test.

### Out of scope
- An `enabled` check inside the fire task's manual/onItemEvent branch in `sweep.ts` (not an audit finding; `sweep.ts` is owned by sibling issues D4, D5 and D11 of this batch).
- `guidanceDriftHeartbeatStore.upsertDriftHeartbeat` setting `enabled = true` on conflict — this is the behaviour issue #85 specified and `guidanceDrift.test.ts` pins; it is not changed.
- Any change to `heartbeat.list`/`heartbeat.history`.

## Acceptance criteria

- When an agent run calls `heartbeat.trigger` for a heartbeat in its own project whose `enabled` is `false`, the tool returns an error result naming the disabled state and no `heartbeatFireCore`/`heartbeatFireAgent` job is enqueued.
- When the same heartbeat is re-enabled and triggered again, exactly one manual fire job exists under `manualHeartbeatFireJobKey(heartbeat.id)`.
- An unknown heartbeat id, a heartbeat of another project, and an `onItemEvent` heartbeat keep their existing responses.
