### Requirement gh-1658: [global-search 04/09] Index page and journal text after doc updates

#### Context

Model tier rationale: One background-job mechanism (enqueue from the doc write path, convert a page to text, update the index row) over existing doc persistence and queue primitives, with a small migration.

Text on pages, and the notes of a Journal day, is not searchable: pages are Yjs documents (`0003_docs.sql`, `docs.item_id` is unique per item) and are never turned into text, and `item_search_index` has no column that holds readable text, so a result also cannot show an excerpt. Today every doc write goes through `mutateDocWithClient`, which calls `appendDocUpdateWithClient` (`docs/docPersistence.ts`) inside the caller's transaction; the realtime path reaches it the same way.

This issue makes page text searchable and keeps readable text for excerpts. It builds on the document builder and indexer from #1397 and on the page-to-Markdown serializer delivered by #1608. The journal period result fields (#1859), journal entry titles (#1711) and subpage title mirroring (#1715) rely on the shape introduced here.

Decisions:
- A page edit schedules a reindex 30 seconds out with `jobKeyMode: "preserve_run_at"`. The default `replace` mode would keep pushing the run time while a user types without pause, so the job would never run.
- Two columns: `page_text` holds the converted text of the item's own page and is written only by the page-text job; `body` holds the excerpt source (for a Journal day, the text of its Inbox entries followed by the day's page text; for every other item, the page text) and is written by the indexer, so a change to an Inbox entry rebuilds the day's `body` without reconverting the page.
- `stripMarkdown(md, maxChars)` is not delivered by the serializer issue, so this issue implements it (plain text from Markdown, truncated at `maxChars`; page text is capped at 100000 characters).
- Only docs of kind `page` are converted; docs of kind `canvas` are skipped.

2. Add `search/stripMarkdown.ts` exporting `stripMarkdown(md, maxChars)`.
3. In `appendDocUpdateWithClient`, after the update row is inserted, enqueue the core task `itemSearchPageText` (name, `api` affinity and tenant tenancy in `packages/queue/src/index.ts`, handler in `worker.ts`) with `jobKey` = the doc's item id, `jobKeyMode: "preserve_run_at"`, `runAt` 30 seconds ahead and `queueName: tenantLane("item-search-index")`. Look the item id up from `docs.item_id`; skip docs of kind `canvas`.
4. The job handler loads the doc, serialises its blocks to Markdown with the serializer from #1608, runs `stripMarkdown`, writes `page_text`, and calls `indexItem` so the vector and `body` are recomputed. It is a completed no-op for a missing, soft-deleted or Emails item.
5. Change `indexItem` and the document builder from #1397: the document appended to the vector includes the stored `page_text`; `body` is written as described under Decisions. Keep `page_text` when the row is rewritten by an item write.
6. Tests: editing a page makes its text searchable after the job runs; a burst of edits yields one job with its original run time; a Journal day's text plus its Inbox entries are searchable and `body` holds both; an Inbox entry change rewrites the day's `body` without losing `page_text`.

### Requirement gh-1746: [mail-threads 22/28] Write message moves back to the mail provider

#### Context

Model tier rationale: A new durable desired/current-state table and write-back across three providers (UID MOVE with fallback, Gmail labels, Graph move with id change), with failure and idempotency ownership in the sync worker.

Archiving or deleting a message in Semprec must also move it at the mail provider, otherwise the next sync puts it back. Today nothing moves messages at the provider: `imapFlowClient.ts` only has `setMessageFlag`, `graphRestClient.ts` only `patchMessage`, and the Gmail client `modifyMessageLabels` (`backend/packages/data/src/mail/`). Flag changes already follow the desired/current-state pattern of `docs/adr/2026-09-20-desired-current-state-sync-for-provider-writebacks.md` (`mail_message_flag_sync_state`, drained by the reconcile of the sync owner, `mail/mailFlagWriteback.ts`). Moves follow the same pattern. The provider sync transports are built by #1510 (IMAP), #1505 (Gmail) and #1508 (Graph).

Facts: on IMAP the UID lives on the `Emails.folder` relation edge's metadata (`mail/folderMembershipStore.ts`) and a moved message gets a new UID in the target folder; the flag write-back targets a UID, so the edge's UID must be updated after a move or later flag writes hit a wrong UID. Gmail archive means removing the `INBOX` label, delete means `users.messages.trash`. Graph moves with `POST /me/messages/{id}/move` to `archive` or `deleteditems` and returns a new message id, which replaces `mail_message_meta.provider_message_id`.

The routes that record moves are #1917 (archive and trash) and the restore route of #2033 (back to the inbox); this issue builds the durable queue and the provider writes for all four targets.

Decisions: the table holds one row per message; a pending move is never undone by the reconcile (the folder edge is not restored while desired and current differ); after a bounded number of attempts (default 5) a row is marked `failed` with a reason (for example the message no longer exists at the provider) and stops being retried; `desired_purpose` is `archive`, `trash`, `inbox` or `sent`: restoring a thread from Archive or Trash records `inbox` for an incoming message and `sent` for the user's own message (the product owner decided that everything archived or trashed can be restored); a row whose desired purpose already matches the message's location at the provider is confirmed without a mutating provider call; a bounded read-only observation may verify current provider identity and location for that attempt, followed by guarded desired-revision/operation revalidation.

- When a bounded provider observation verifies absence, then after the attempt limit the row is `failed` with a fixed missing reason and is not retried. No claim of definite IMAP absence or automatic missing-message termination from that unsupported observation is made.

- New move/observation provider failures and cleanup retain original internal failures but expose fixed safe unknown errors, stored reasons and closed diagnostics, with no credentials or arbitrary provider/error text; unrelated SQL/token errors keep their contract. An elapsed IMAP deadline requests close and forbids continuation; it never releases ownership on a race alone. Public-library nonsettlement remains owned and readiness-blocking, not a guaranteed total shutdown bound or a completed move.
