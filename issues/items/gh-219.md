**Blocked by:** #252, #88, #115, #121, #152, #158, #173

## Context

Issue #252 turned the generic operation catalog into transport-independent data in `packages/shared`: the closed 28-operation catalog, the strict Zod input schemas, `GenericApplicationPort`, `GENERIC_OPERATION_BINDINGS`, the `AuthenticatedActor` shape, and the capability and approval/risk metadata. Nothing consumes it yet.

This part gives the port its one neutral implementation and makes REST dispatch through the bindings, so the existing HTTP surface of #158/#37 and every later adapter share a single execution path with no second write path. #220 then builds the AgentTool and MCP adapters, capability registration/filtering, agent actor derivation, and the approval interceptor over the same descriptors; #89 adds the snapshot-bound exactly-once approval execution protocol.

## Task

The concrete `GenericApplicationPort` implementation lives in neutral `packages/application/src/genericApplicationService.ts`, built only over the public `packages/data` choke-point facade; it is not owned by or imported from `semprec-api`. `semprec-api` instantiates it locally in its composition root with its own injected data-package connection and routes every generic REST operation through the bindings; there is no second write path. The data package owns use of the privileged `semprec_data` connection internally, consistent with #40; the service imports no store or SQL.

Rebase the REST adapter of #158/#37 onto the bindings. Every REST adapter assembles route params, query, headers, and body into its canonical command object, then validates that object with the binding's schema; for item create specifically, `databaseId` comes from the path and optional `idempotencyKey` from `Idempotency-Key`. REST human actors are derived from the authenticated session context and omit the agent fields.

Issue #37's REST relation route remains `/api/items/:id/relations/:propertyKey/:targetItemId`. Its route-only validator is not the canonical command validator: the REST adapter resolves `propertyKey` against caller item `id`'s database to exactly one relation property, returning `404 not_found` with `{ resource: 'relationProperty', databaseId, propertyKey }` for no match and `409 validation_failed` with `{ field: 'propertyKey', reason: 'ambiguous' }` for multiple matches. It then constructs `{ relationPropertyId, callerItemId: id, targetItemId, metadata }` and validates `RelationPutInputSchema`; DELETE constructs the metadata-less command. AgentTool/MCP callers (#220) supply the stable `relationPropertyId` directly. Relation property-key resolution is the only semantic lookup during assembly.

Surface the runtime rejections implied by the catalog schemas: empty patch objects return `400 validation_failed` with `{ reason: 'empty_patch' }`, and when the stored property is `relation` a supplied `patch.type` or `patch.config` returns `400 validation_failed` with `{ field: 'type' | 'config', reason: 'relation_definition_required' }` while rename remains allowed.

Implement the relation branch of `createProperty`: the application mapping converts `databaseId` to #82's `sourceDatabaseId`, supplies `owner: 'user'` and no `ownerProcess` on source and inverse, and passes target/cardinality/locked/inverse exactly to #82's public relation-definition creator. Non-relation creation defaults `locked=false`, `owner='user'`; relation-shaped fields on a non-relation branch are rejected.

Add `POST /api/databases/:id/restore` to the REST adapter. It assembles strict `DatabaseRestoreInputSchema`, calls `restoreDatabase(actor, input): Promise<Database>`, and returns the authoritative restored row. Expose property list and get through REST, returning the authoritative raw `Property[]`/`Property` rows so agents can discover relation property ids.

Use the evolved shared `{ code, details }` domain-error union, explicitly including #83's `database_archived`; the REST parity test must cover that error (the MCP/AgentTool legs are added in #220). Runtime-validate every boundary and add parameterized contract tests across all 28 operations for the REST adapter.

## Scope

### In scope

- `packages/application/src/genericApplicationService.ts` as the sole `GenericApplicationPort` implementation, instantiated in the `semprec-api` composition root.
- The REST adapter rebase onto `GENERIC_OPERATION_BINDINGS`, including command assembly, relation property-key resolution, the relation `createProperty` mapping, `POST /api/databases/:id/restore`, property list/get, and the empty-patch and relation-definition rejections.
- Parameterized REST contract tests across all 28 operations and the `database_archived` parity test.

### Out of scope

- The catalog, schemas, port, bindings, actor shape, capability and approval/risk metadata, and the `packages/shared` → `services/*` dependency rule; #252 delivered these.
- AgentTools, `POST /mcp`, ModuleRegistry capability registration/filtering, agent actor derivation and `agent_runs.actor_user_id`, and the approval interceptor, delivered by #220.
- Snapshot-bound exactly-once approval execution, delivered by #89.
- Third-party MCP server transports, owned by #31.
- Domain-specific tools or a second persistence API.
- Automatic approval of agent writes.

## Acceptance criteria

- Every generic REST route dispatches through `GENERIC_OPERATION_BINDINGS` into `genericApplicationService`, all existing generic REST routes remain green, and a parameterized contract test covers all 28 operations over REST.
- External payloads are runtime validated and no `any` crosses the adapter boundaries; spoofed identity fields are rejected before reaching the service.
- Empty patches return `400 validation_failed` `{ reason: 'empty_patch' }`; relation type/config patch rejection returns `{ field, reason: 'relation_definition_required' }` through REST.
- REST relation route resolution returns the specified `404`/`409` details and assembles the canonical command; `database_archived` parity is covered on REST.
- Database restore and property list/get are available through REST and return authoritative rows.
- `semprec-api` neither owns nor exports `genericApplicationService`, and the service imports no store or SQL.
- Creating a relation property through REST produces #82's definition with `owner: 'user'` on both sides and the requested target, cardinality, locked, and inverse values.
