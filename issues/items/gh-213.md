**Blocked by:** #83, #136

## Context

The heartbeat sweep currently records `last_fired_at` and computes the next floating occurrence when it enqueues a job. Queue delay therefore shifts `interval` and `everyNDays` away from the action's actual execution time. Fixed calendar rules must remain calendar-anchored, and the sweep's `FOR UPDATE SKIP LOCKED` guarantee must remain intact.

This first part introduces the `heartbeat_occurrences` table, moves floating scheduling to the first handler attempt, and makes the fire handler discriminate scheduled, event, and manual jobs. #84 builds on it with the reactivation and generation protocol for occurrences that conflict on the same `scheduled_for`.

## Task

Add `heartbeat_occurrences(id uuid primary key, heartbeat_id uuid not null references project_heartbeats(id) on delete cascade, scheduled_for timestamptz not null, rule_snapshot jsonb not null, first_started_at timestamptz, status text not null check (status in ('queued','running','succeeded','failed','cancelled')), last_error text, unique(heartbeat_id, scheduled_for))`. The sweep atomically inserts one `queued` occurrence with the exact current rule snapshot and enqueues `{ heartbeatId, occurrenceId }` with `jobKey = heartbeat-fire:${heartbeatId}:${occurrenceId}` while holding its existing row lock (#84 extends this payload and key with a generation). Distinct scheduled occurrences therefore never replace each other. In this part, an insert that conflicts on `(heartbeat_id, scheduled_for)` with any existing row is an idempotent no-enqueue result and never advances `next_fire_at` a second time; #84 defines the cancelled/queued reactivation rules on top of this. `dailyTime` and `weekly` are fixed calendar rules and advance `next_fire_at` immediately to the next calendar occurrence; `interval` and `everyNDays` are floating and set `next_fire_at = NULL` until first execution starts. On the first attempt, lock heartbeat plus occurrence. A missing occurrence/heartbeat (including cascade after deletion) is a successful no-op. Compare current rule and snapshot with PostgreSQL `jsonb` equality inside that lock transaction. If disabled or unequal, set the occurrence `cancelled`, do not execute, and do not touch heartbeat scheduling; the disable/rule-edit transaction owns recomputing or clearing `next_fire_at`. Otherwise atomically set `first_started_at = now()`, `status = 'running'`, `project_heartbeats.last_fired_at` to that same value, and calculate floating `next_fire_at` from the snapshot and `first_started_at`. Retries reuse the persisted `occurrenceId` and timestamp and never advance again. Final success/failure changes only occurrence status/error plus existing heartbeat error reporting. Subsequent occurrences are therefore schedulable even after failure. `actual execution time` means the first attempt's handler-start timestamp, not enqueue time or a later retry.

`heartbeat_occurrences` applies to all sweep-driven `dailyTime`, `weekly`, `interval`, and `everyNDays` rules. Preserve two non-occurrence paths unchanged: event payload `{ heartbeatId, itemId }` with its existing event job key/context, and #33's manual payload `{ heartbeatId, triggeredByRunId }` with its manual job key and propagation to `agent_runs.parent_run_id`. Event and manual jobs create no occurrence and never modify `last_fired_at` or `next_fire_at`; manual execution still runs the selected time-based heartbeat action immediately. The handler accepts exactly one discriminator among `occurrenceId`, `itemId`, and `triggeredByRunId`, rejecting zero or multiple with `validation_failed`. Tests cover all three branches and manual attribution, plus fixed, floating, retry, catch-up, and overlapping-sweep behavior.

## Scope

### In scope

- Core heartbeat scheduling state and fire-task behavior: the occurrence table, sweep insertion, fixed versus floating `next_fire_at`, first-attempt locking and snapshot comparison, and the handler discriminator.
- Fixed, floating, retry, and catch-up tests.

### Out of scope

- Reactivating cancelled occurrences, reusing queued stale-snapshot occurrences, and the `generation` protocol with generation-specific payloads/job keys; #84 delivers these.
- Starting the long-lived worker process; the final issue in this batch owns that composition root.
- New rule kinds or module registry integration.
- UI/history tooling for heartbeats.

## Acceptance criteria

- A floating heartbeat delayed in the queue schedules its next occurrence from actual handler execution, not enqueue time.
- A fixed heartbeat remains aligned to its calendar rule after delay or catch-up.
- Daily and weekly fixed rules both remain calendar-aligned and occurrence-backed.
- Retries advance scheduling state at most once for an occurrence.
- Two overlapping sweeps enqueue a due heartbeat exactly once.
- Multiple item events retain independent `{ heartbeatId, itemId }` jobs and execute without occurrence rows or scheduling-state changes.
- Manual `{ heartbeatId, triggeredByRunId }` jobs retain parent-run attribution and execute without occurrence or scheduling-state mutation.
- Distinct scheduled occurrence ids have distinct job keys; disabling, deleting, or editing a heartbeat before start cannot execute stale work or overwrite the newly computed schedule.
- A payload with zero or more than one of `occurrenceId`, `itemId`, and `triggeredByRunId` is rejected with `validation_failed`.
