## Context

Model tier rationale: Changes when the IMAP IDLE lifecycle asks for a reconcile pass and when an IDLE connection counts as ended, on the path that decides how fast a delivered message reaches the inbox.

End-to-end finding on the dev server against Purelymail, verified in the code:

- **A message that arrives between two IDLE sessions is not synced until another trigger.** `mail/imapIdleLifecycle.ts` enqueues `mailAccountSync` once in `start()`, before discovery. `runFolderLoop` reconnects after a clean server close (immediately), after an error or a failed connect (after backoff) and after the hard recycle, without any sync. A fresh imapflow connection never signals a message that was already there when it selected the folder: `untaggedExists` ignores the SELECT's count (no mailbox yet) and the count IDLE repeats is equal, so no `exists` event. A message delivered while the folder had no connection therefore waits for the next unrelated trigger (observed: 3 minutes, no `mailAccountSync` job enqueued for it).
- **Any server-side close ends the folder's IDLE for good.** After the server's BYE or a reset, the connection's `close()` still logs out; imapflow refuses the LOGOUT with `NoConnection` (no socket), `closeClient` reports it as a cleanup failure, the round rethrows it as an owned failure and `runFolderLoop` returns: the folder has no IDLE until the lifecycle is restarted, and nothing logs it beyond one `IMAP IDLE lifecycle failed` warning. Reproduced against the loopback IMAP server.
- **A session end is invisible.** A clean server close is not logged at all and a reconnect is never logged, so the server log cannot show whether IDLE was running when a message was missed.
- **An IDLE that ends on a still-open connection leaves the connection silent.** imapflow runs IDLE from auto-IDLE; when the IDLE command ends without our DONE (a tagged OK/NO from the server, a failed IDLE), `run()` does not re-arm auto-IDLE for IDLE itself, `idling` stays false, and the connection stays open without receiving notifications until the 35-minute socket timeout ends it.
- Checked and not a gap: imapflow's `maxIdleTime` renewal (DONE/IDLE on the same socket; the server reports buffered changes at the next IDLE and imapflow compares the count), `mailboxClose` (only emitted for our own commands or on connection close, which already ends the session).

## Task

Load `error-handling`, `io-hardening`, `testing`.

1. `imapIdleLifecycle.ts`: once a connection for a folder is established (folder selected, so a later change is reported once IDLE runs), enqueue the idempotent `mailAccountSync` through the same tracked path a signal uses, for every session including the first after `start()`; nothing once `stop()` has begun. Log at info every session start, every session end with its reason (`server-closed`, `error` with the error's name and code, `recycle`, `stop`) and every reconnect with its attempt and delay; fields `mailboxItemId`, `folder` and those only.
2. `imapIdleClient.ts`: a connection whose close was already observed is not logged out, and imapflow's `NoConnection` refusal of the LOGOUT counts as the connection already gone (the close still awaited), not as a cleanup failure; attach the signal listeners before the folder is selected; a watchdog ends the session with an `ImapIdleStoppedError` when the connection is found not idling on two consecutive checks (default every 60 s, configurable for tests), stopped before `close()` logs out.
3. `docs/architecture/domain-mail-and-inbox.md`: the reconnect catch-up and the watchdog.

## Scope

### In scope

- When the IDLE lifecycle enqueues a reconcile, when an IDLE connection counts as ended, and the lifecycle's session logs.

### Out of scope

- The reconcile pass itself, the backoff schedule, the hard-recycle cadence, imapflow's options, Gmail/Graph live sync and any other provider.

## Acceptance criteria

- A reconnect after a clean server close and after a connection error each enqueue exactly one `mailAccountSync` after the new session is established, and none before it.
- A message delivered while the folder had no connection (signalled by nothing) is synced: a `mailAccountSync` job is pending after the reconnect.
- `stop()` while a reconnect is connecting enqueues nothing.
- After the server closes the IDLE connection, the lifecycle reconnects (it does not end the folder's loop), and closing a connection the server already closed, or whose LOGOUT imapflow refuses with `NoConnection`, succeeds; any other LOGOUT refusal still fails the cleanup.
- Against a loopback IMAP server, a message delivered while the IDLE connection was down leads to a pending sync after the reconnect, and an IDLE the server ends on an open connection ends the session.
- The existing IDLE lifecycle, client and latency tests stay green.
