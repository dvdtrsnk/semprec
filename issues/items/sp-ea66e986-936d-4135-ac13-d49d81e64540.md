### Requirement gh-1369: [semp-turns 01/12] Define the Semp message ref schema

#### Context

Model tier rationale: A single zod module in the shared package, but it fixes a persisted wire contract that three later issues store, validate and expand, so the closed variants need care.

A user can attach objects (a task, an e-mail, a note block, a transcript passage, a file, a person and so on) to a message sent to Semp. Semp receives a reference, not text: it reads the whole object and its surroundings itself and may edit it. Today the backend has no message refs at all. The only existing link to an object is the `semprec://items/<fileItemId>` string in `Transcriptions.link` (`backend/packages/data/src/transcription/transcriptionJob.ts`), and the shapes of the referable objects differ: a note block is a `Y.Map` inside the item's document (`backend/packages/data/src/docs/blocks.ts`, document unique per `(tenant_id, item_id)`), an e-mail attachment is a `mail_attachments` row rather than a Files item, and a transcript passage is an entry of `computed.segments` (`{speaker, text, startsAt, endsAt}` in seconds) on a Transcripts item.

This issue defines the single, closed schema of a message ref. #1682 validates and stores refs with it, and several later issues extend or consume the same schema: #1936 (agent run refs), #1933 (mail thread refs), #1771 (task occurrence and trace refs) and #1853 (sleep night refs).

Decisions:
- A recording is referenced as an `item` ref to its Transcripts item, which carries the summary, speakers and segments; the audio file stays reachable from it. No separate recording kind.
- A person, company, recipe, invitation, Inbox item and proposal card are all plain `item` refs.
- An e-mail is an `item` ref to the Emails item. A mail thread kind is added by #1933, not here.
- Kinds whose data does not exist yet (sleep nights, task occurrences and traces, mail threads and drafts, event occurrences, birthdays, holidays, page property values, journal periods) are not defined here; the issue that introduces the data adds its variant to this same union.

#### Task

Load `canonical-keys` and `testing`.

1. In `backend/packages/shared/src/`, add a message-ref module exporting a zod discriminated union on `kind` (strict objects, canonical camelCase keys) with these variants:
   - `{ kind: "item", itemId, databaseId }` (UUID strings)
   - `{ kind: "block", itemId, blockId }`
   - `{ kind: "transcriptSegment", itemId, startsAt, endsAt }` (seconds, finite numbers, `0 <= startsAt < endsAt`)
   - `{ kind: "mailAttachment", attachmentId }`
   - `{ kind: "agentRun", agentRunId, messageId? }`
   - `{ kind: "approvalRequest", approvalRequestId }`
2. Export the inferred `SempMessageRef` type, the list of kinds, and a pure `messageRefKey(ref)` function returning the dedup identity: kind plus the id fields, plus `blockId` for blocks and the range for segments. `messageId` of an agent run ref is not part of the identity.
3. Export the schema through the shared package index.
4. Unit tests: each variant accepts a valid value and rejects a missing field, an extra field, a non-UUID id and (for segments) an empty or reversed range; an unknown `kind` is rejected; `messageRefKey` is equal for two equal refs and different for refs differing in block id or range.

### Requirement gh-1375: [agent-md 01/07] Fingerprint guidance drift findings deterministically

#### Context

Model tier rationale: A pure shared function with a contract change to the stored finding payload and the AI response schema, touching a few seams that already have unit-test fixtures.

A guidance drift finding is a nightly-detected mismatch between a project's instructions and what the agent can or does do; the owner sees it as a notification and, later, as a card with actions. Findings are stored in `agent_guidance_drift_findings` (`fingerprint`, `payload`, `status` `active|resolved`, unique per `(project_item_id, fingerprint)`). `upsertActive` reopens a resolved finding with the same fingerprint, and the "decided findings are not reopened" rule the resolve action needs (#1685) also hangs on the fingerprint.

Today the fingerprint is `fingerprintGuidanceDriftContradiction` in `backend/packages/shared/src/guidanceDrift.ts`: a SHA-256 over the AI-written `claim`, `guidanceExcerpt` and `manifestFacts`. The AI rewords those strings from one nightly run to the next, so the same real problem gets a new fingerprint each night: it resolves one finding and opens another, and a reopened/decided state cannot be remembered. The tick `core.agentGuidanceDrift` (`backend/packages/application/src/projectAgentGuidance/driftAction.ts`) is the only caller.

This issue makes the fingerprint depend only on deterministic facts. It is used by the existing permission check now and by the behavior check in #1629, and by the problem-raising work in #1465.

Decisions:

- A finding's identity is its subject: `{ kind: "permission" | "behavior", operation | mcpTool, databaseId | null }`. The fingerprint is the SHA-256 (hex) of the canonical JSON (`canonicalizeJson`) of `{ projectItemId, kind, operation, mcpTool, databaseId }`, where exactly one of `operation` and `mcpTool` is a string and the other is `null`. Nothing generated by AI text enters it.
- For the existing permission check the AI response schema gains a required `subject` per contradiction: `{ operation: string, databaseId: string | null }`, taken from the permission manifest the AI is given (the operation the guidance contradicts and the target database id, or null when the contradiction is not database specific). The prompt tells the AI to copy these values from the manifest, never to invent them.
- The stored payload gains `kind` and `subject`. A payload row written before this change has no `kind`; reading it treats it as `permission` with no subject, and the next nightly run resolves it (its old fingerprint is no longer reported) and opens the new one. The findings table is empty in production today, so no data migration is written.

#### Task

Load `canonical-keys` and `testing`.

1. In `backend/packages/shared/src/guidanceDrift.ts` add the type `GuidanceDriftSubject`, add `kind` and `subject` to the contradiction payload type (kind `permission`; the behavior variant is added by #1629) with `validateGuidanceDriftContradiction` accepting rows without them as legacy, and add `fingerprintGuidanceDriftSubject(projectItemId, kind, subject)` implementing the decision above. Remove `fingerprintGuidanceDriftContradiction`.
2. In `driftAction.ts` add `subject` to `AGENT_GUIDANCE_DRIFT_RESPONSE_SCHEMA` (required), validate it, switch the ranking and upsert to the new fingerprint, and extend the system instruction so the AI copies `operation` and `databaseId` from the manifest. When two contradictions share a subject, keep the one with the higher severity (the finding is unique per fingerprint).
3. Update `backend/packages/shared/src/__tests__/guidanceDrift.unit.test.ts` and `backend/packages/application/src/projectAgentGuidance/__tests__/driftAction.unit.test.ts` for the new function and schema.

### Requirement gh-1381: [inbox-attachments 01/08] Accept image content in /internal/complete

#### Context

Model tier rationale: It changes the shared gateway request contract to carry binary image content, which touches cost reservation, body limits and the provider adapter for every operation, and so affects budget enforcement for all AI calls.

The AI gateway's structured-completion route `POST /internal/complete` (`backend/services/semprec-ai-gateway/src/completeHandler.ts`) accepts only text: `AiGatewayMessage.content` is a string (`backend/packages/shared/src/aiGatewayClient.ts`), the request body is capped at 1 MiB (`MAX_BODY_BYTES`) and the budget estimate counts characters (about 4 per token). To read a photographed invoice the assistant must be able to send an image. The conversational route `POST /internal/pi/messages` already carries images, but it has no structured output and is not the right path for extraction.

This issue lets a message carry text and image blocks. It adds the transport only; #1970 uses it for extraction. The gateway stays the only process that calls a provider (`docs/adr/2026-09-10-ai-gateway-monopoly-on-provider-calls.md`).

Decisions:
- The addition is backward compatible: `content` stays a string, or becomes an array of blocks `{ type: "text", text }` and `{ type: "image", mimeType, data }` with `data` base64 and `mimeType` `image/jpeg` or `image/png`. The caller sends a reduced JPEG, not a blob id; the gateway does not read the blob store.
- At most 4 images per request and 1.5 MiB of decoded bytes per image; the whole body cap rises from 1 MiB to 8 MiB only for requests that contain an image, and stays 1 MiB otherwise.
- The reservation estimate adds a fixed 1600 tokens per image (the provider's ceiling for an image of about 1568 px), on top of the text estimate; the real cost is still settled from the provider's reported usage.
- Any accepted operation may send images; the operation list stays closed.

#### Task

1. In `aiGatewayClient.ts` change `AiGatewayMessage.content` to `string | AiGatewayContentBlock[]`, exporting the block types, and make `packages/ai-gateway-client/src/httpAiGatewayClient.ts` send them (the request size cap and timeouts there are unchanged except the larger allowed request).
2. In `completeHandler.ts` validate blocks (`type`, string `text`, `mimeType` in the two allowed values, base64 `data` within the size limit, at most 4 images), keep `isStructuredCompletionMessage` for the string form, raise the body cap to 8 MiB for a request containing an image (read the body with the existing capped reader, then check), and add 1600 tokens per image to `estimatedInputTokens`.
3. Map blocks to the provider format in `structuredProviders/anthropicProvider.ts` and update `structuredProviders/types.ts` (`StructuredCompletionMessage.content`). A string message maps exactly as before.
4. Tests in `completeHandler.test.ts`: a request with a text block and an image block dispatches and the provider receives both; a plain string message is unchanged; a fifth image, an `image/gif`, invalid base64, an image above the size limit and a 9 MiB body are 400 or 413; the reservation includes the per-image estimate and the audit row records real usage; a text-only request above 1 MiB is still 413.

5. For the streaming 8 MiB cap refusal, apply `docs/adr/2026-11-01-completion-body-rejection-uses-bounded-discard.md`: send fixed JSON413/Connection:close before bounded non-accumulating discard (2097152 additional bytes/2000ms), then destroy with idempotent owned timer/listener cleanup. Preserve no provider/reservation and existing valid input behavior; prove actual 9 MiB response plus bounded slow/excess/abort controls. No other route adopts this policy.

#### Context

Model tier rationale: A new long-lived streaming route in the gateway with budget reservations of unknown audio length, concurrency limits and disconnect propagation, touching the accounting path every provider call relies on.

Voice mode needs the user's speech turned into text as it is spoken. The gateway today transcribes only whole recordings: `POST /internal/transcribe` (`backend/services/semprec-ai-gateway/src/audioHandler.ts`) reads a base64 body, knows `audioSeconds` up front, reserves the exact price, calls the provider (`audioProviders/deepInfraWhisperProvider.ts`) and settles. The decisions of the voice ADR written in #1371 (provider, chunk length, formats, limits) apply.

This issue adds a streaming speech-to-text adapter to the gateway. #1734 uses it for voice turns; dictation into the message field runs on the device and does not use it (#1372).

Decisions:
- Transport inside the host: a loopback WebSocket route `/internal/stt/stream`, authenticated with the internal token and carrying the caller's tenant exactly like the other internal routes. The ADR's choice prevails if it differs.
- The audio length is unknown, so the stream reserves budget in chunks of a fixed number of seconds (value from the ADR): one `ai_gateway_calls` row per chunk with operation `voice_transcribe_stream`, reserved before the chunk is consumed, settled with the seconds actually used. When the next chunk cannot be reserved (budget exceeded), the stream ends with an error message to the caller.
- Audio is held in memory only for the duration of forwarding and is never written to disk or logged.
