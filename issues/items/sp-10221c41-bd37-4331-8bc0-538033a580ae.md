## Context

Model tier rationale: Restructures the IMAP verification's owned-socket accounting to run a LIST on the verified connection, and runs the IMAP, SMTP and CalDAV verifications concurrently, with every refusal and failure path releasing what it opened and no network I/O inside a transaction.

Production evidence (dev VPS, a real Purelymail password account): `POST /api/mail/mailboxes` now answers in 6.5 s; before the connect-time folder discovery (sp-01cb2670-f7d1-4013-ba52-8bf7d1bfaaf1) it took 3.0–3.5 s. Purelymail costs about 0.42 s per TLS connect, 0.10 s for LOGIN and 0.10 s per command.

Root cause, from the code:

- **Two IMAP logins.** `verifyMailCredentials` (`mail/mailCredentialVerification.ts`) connects and logs in through `verifyImapServerConnection` and closes the connection. The connect route (`mail/mailboxPasswordRouteHandlers.ts`) then opens a second connection through `mailServerClients.openImap` (`openImapConnection`), which logs in again, lists the folders through `ImapFlowMailClient.listFolders` (on a CONDSTORE server with one STATUS per folder, unless it has LIST-STATUS, and an LSUB), and LOGOUTs.
- **Everything is sequential.** `verifyMailCredentials` verifies SMTP only after IMAP finished, and the route verifies CalDAV only after both and lists folders only after that. The three servers are independent; the total is their sum.
- `PUT /api/mail/mailboxes/:id/password` has the same sequential IMAP → SMTP → CalDAV verification (no folder listing).

Decisions:

- **The verification connection lists the folders.** `verifyImapServerConnection`'s owned-socket attempt, when asked, sends `LIST` (imapflow `list()` without a status query: LIST and, on a server without extended LIST, LSUB, but no STATUS; the connect needs only path and special-use, and `listOnly` would return before imapflow assigns special-use) on the connection whose login just succeeded, before it closes it. The listing has its own 15 s deadline (on expiry the connection is closed). A failed or expired listing never fails the verification: the login is verified, the failure is logged (error name only) and the result carries no folders, as today. Observations (client and socket errors) made while the listing runs are the listing's and are kept out of the verification's failure accounting. `verifyMailCredentials` returns the listed folders (`folders`, `null` when not asked or failed), the route maps them with `imapProviderFolder` and `createPasswordMailbox` writes the compose folders as today. The `mailServerClients.openImap` member is removed from the route, `MailServerClients` and `serve.ts`.
- **Independent verifications run concurrently.** In `verifyMailCredentials` the IMAP candidates and the SMTP candidates are tried concurrently (each protocol still tries its candidates in order). Both settle before it returns; when both fail the IMAP failure is reported, as today. In both routes the CalDAV verification runs concurrently with `verifyPassword`; both settle before the route answers; the mail failure is reported before a CalDAV failure, and a failure that is not reported is logged (error name only). The deadlines are unchanged (15 s per IMAP/SMTP attempt, 45 s CalDAV).
- With concurrency a wrong password is presented to both the IMAP and the SMTP server (before, an IMAP refusal skipped SMTP). The throttle counts per request, so the number of verifications a user can trigger is unchanged.
- No transaction is open across any of it; the mailbox transaction runs after every verification settled.

## Task

Load `io-hardening`, `error-handling`, `state-writes`, `testing`.

1. `mail/mailServerConnections.ts`: an IMAP verification attempt that lists the folders on the verified connection, with its own deadline and its observations kept apart; `verifyImapServerConnection` keeps its result for callers that do not list.
2. `mail/mailCredentialVerification.ts`: `listFolders` input, `folders` result, IMAP and SMTP verified concurrently, both settled before returning, IMAP failure first.
3. `mail/mailboxPasswordRouteHandlers.ts`: the connect asks for the folders and drops its second connection (`openImap`, `listImapFolders`); both routes verify CalDAV concurrently with the mail verification, report the mail failure first and log an unreported failure.
4. `services/semprec-api/src/adapter/customRouteMount.ts` and `serve.ts`: remove `openImap`.
5. A latency test (`mailboxConnectLatency.test.ts`): the production connect handler with the production verification (`verifyMailCredentialsForTests`) against a TLS-fronted loopback `FakeImapServer`, a TLS fake SMTP server and the `FakeCalDavServer`, each with an injected per-connection and per-command latency.
6. Update `docs/architecture/domain-mail-and-inbox.md` (password connect, password sign-in again).

## Acceptance criteria

- Through the production connect handler and the production verification against loopback fakes with injected per-connection and per-command latency: exactly one IMAP connection and one IMAP LOGIN during the connect; the mailbox has its Drafts and Sent folders; the IMAP (with LIST), SMTP and CalDAV verifications overlap in time and the connect takes clearly less than their sum.
- Each refusal path (IMAP login refused, SMTP login refused, CalDAV login refused) answers 400 with its code, writes no mailbox, and leaves no open connection on any fake server when the route returns.
- A failing LIST on the verified connection still connects (201) without the compose folders and logs the failure without user content.
- `PUT /api/mail/mailboxes/:id/password` verifies CalDAV concurrently with the mail verification and keeps its refusal codes.
- The existing mailbox connect, password, compose-after-connect, credential verification, throttle and isolation test files stay green.
