### Source behavior: [08/22] Inbox as a real database

## Context

The mock (`mock.html`/`index.html`) already models the Inbox fairly deeply as a list of cards with a hardcoded set of six emoji and a periodic sweep that decides where an item gets written based on a string comparison against the type's label text. This task is the backend transformation of that idea into the real system: the Inbox stops being a JSONB field on the Deník (Journal) and becomes a real database, owned by the system project Semprec, with real rows, real identity, and explicit, configurable processing logic — but on the outside, in the daily note, it stays visually indistinguishable from a plain list. The user only discovers it's a database if they click through into the Semprec project themselves.

Issue #24 (ten hardcoded databases) introduces ten hardcoded system databases, but the three databases this task revolves around — **Inbox**, **Inbox item types**, and **Processing proposals** — are **not** among them, and no other issue creates them. This task therefore also owns their baseline creation: the three `databases` rows (canonical keys `inbox`, `inboxItemTypes`, `processingProposals`) and their properties, plus their interrelated behavior, state machine, API contract, and event-driven processing mechanism — everything that turns the Inbox into a functioning pipeline rather than three isolated tables.

A note on naming: canonical stored keys (database keys, property keys, select-option values) are English camelCase throughout; Czech names such as "Deník" or "Návrhy zpracování" are display labels only, delivered per the app language setting by the i18n system (issue #35), never stored as keys.

## Task

Implement three interlinked databases and their behavior:

**1. Inbox** (database key `inbox`; rows, not JSONB) with properties:
- `date`/`time` — owner: user, **both mandatory** (the client always sends them; the server never derives them as "today" server-side, because of offline capture from a phone and delayed batch submission after a connectivity outage)
- `text` — owner: user
- `type` — relation → Inbox item types, owner: user
- `journalDay` — relation → Deník (Journal), owner: system — computed from `date` at write time, using the exact same lazy mechanism that creates the Journal entry for a given date

No extra database is added for the relation to the daily record — it reuses the existing Journal relation.

**2. Inbox item types** (database key `inboxItemTypes`) — replaces the hardcoded label-text comparison with an explicit `processingMethod` select property:
- `pageContent` — write as a new item into page content (the same block-append mechanism used elsewhere, issue #23)
- `database` — a new item in any system database; this method additionally carries `targetDatabase` (relation → `databases`), populated only for this method

For example: "☑️ Task" → `database` + Tasks, "🗓️ Plan/event" → `database` + Events, "💭 Thought"/"🌈 Feeling" → `pageContent` (a note appended into the most relevant project's page). **Which specific project/item** it lands on stays an AI/heuristic decision made at runtime (the same role as the mock's `heuristickyNajdiProjekt`, now backed by a real LLM call and `typDef.prompt`) — it is not configured on the type, because that's precisely the part that should be decided from the content of the text, not from settings.

References to a type are always by its `id`, never by emoji — `GET /api/inbox-types` returns `[{ id, emoji, label }]`, and an Inbox item stores `type` as a relation to that `id`. This means the emoji (or anything else) on an existing type can be freely renamed without breaking anything.

A type can be both **archived** (existing `status` select — disappears from the picker for new items, while old items keep pointing at it validly) and **deleted** outright. Deleting a type that existing Inbox items still reference does not leave those items dangling with a dead reference — they fall into the same path as an item with no type at all (see "Processing proposals" below, the clarification-needed state) — no special-case handling code just for deleted references, just reuse of the existing "unknown type" mechanism.

**3. Processing proposals** (database key `processingProposals`) — an expanded state space for the card:

```
status = needsClarification | proposed | confirmed | rejected | invalid
         (Czech display labels via i18n: návrh upřesnění | návrh | potvrzeno | zamítnuto | neplatný)
```

`needsClarification` is a new first state that covers exactly what the mock used to silently skip forever — an item with no recognizable type (or with a type that was deleted, see above) gets a card in the `needsClarification` state: no pre-filled proposal, just a chat window where you clarify with the AI what should happen to it. Once a clear `processingMethod`/target emerges from the conversation, the card switches to `proposed` and from then on behaves exactly like any other — nothing is half-edited; the "no silent no-op" principle from `item_automation` (issue #24) applies here too.

The card's payload (the `proposal` property, jsonb) is a single generic shape regardless of `processingMethod`: `{ entityKind, target, properties }` — `entityKind` ("pageContent"/"database"), `target` (target id — a page id or a target database id), `properties` (a map of values — for "database" exactly the properties that concrete target database requires, for "pageContent" the content of the new block). Because of this uniform envelope, a chat-driven clarification can **completely rewrite** the proposal (switch a task into an event, change the target project), and the card UI just re-renders from the new shape — there is no need for separate code paths for "patch a field" versus "change the whole kind"; it's the same operation (`revise` overwrites the entire `proposal`, not individual fields).

Properties (items-engine, not a new table):

```
kind             select 'inbox' | 'transcript'
sourceInbox      relation → Inbox, nullable (populated when kind='inbox')
sourceTranscript relation → Transkripce (Transcripts), nullable (populated when kind='transcript')
fingerprint      text — sha256({emoji,text}) or {text,startsAt,endsAt}, dedup/change detection
proposal         jsonb — { entityKind, target, properties }, as above
history          jsonb — [{ author: 'ai'|'user', message, at }], chat + decision log
status           select needsClarification | proposed | confirmed | rejected | invalid
resultItemId     uuid, nullable — filled in by confirm
resultLabel      text, nullable — display label for the UI link
```

The rest of the earlier logic is unchanged: the fingerprint still gates AI calls (a new card only when none exists, or one exists-unlocked-and-the-fingerprint-differs — zero wasted calls on an unchanged source), a locked card (`confirmed`/`rejected`) is never recomputed again, and a source deleted out from under an unlocked card flips it to `invalid` rather than making it disappear.

**Forced separation of proposing from writing — confirmation is the only path to a real write, enforced technically, not just documented in AGENT.md.** The mock's AGENT.md already states in prose "never write silently outside of a confirmed card" — per the two-layer model from issue #21, this is exactly the kind of rule that deserves to be promoted from a guided boundary to an enforced one. Semprec's grant (the permission its own `agent_runs` executes under) does not include write access to any target database/page at all — only the right to create/modify a row in "Processing proposals." The real cross-database write exists in exactly one place in the entire system: inside the `confirm` action, callable only in the context of a logged-in user (never from the agent's own run). This means the agent literally *cannot* write outside a card, whether it wants to or not — not merely that it shouldn't. One ordering caveat: auth itself arrives only in issue #34 — until #34 lands there is no login, so the "logged-in user context" half of this guarantee is unenforced by design; issue #34 retrofits the actual enforcement onto `confirm`. The grant-based half (Semprec's agent grant lacking write access to target databases) is enforced from the start.

Inside `confirm`: for `entityKind: 'database'` it calls the same generic create-item endpoint (issue #21's choke-point) used by the UI and by MCP tools — no hand-rolled write per entity type. For `entityKind: 'pageContent'` it calls the same block-append mechanism (issue #23) used by ordinary page editing. Neither mechanism is reinvented for Semprec — both are simply reused as they already exist elsewhere in the system.

**Event-driven tick per item — safely concurrent, not a periodic sweep.** Processing changes from the mock's "periodically walk every item and diff fingerprints" to: a new Inbox item = one tick for that item; editing a not-yet-confirmed item = a new tick that updates or fully recomputes the proposal; deleting an item = a tick that invalidates an unlocked card (a locked card is left alone — once decided, it stays decided, even if the source disappears). Mechanism: a new trigger type `onItemEvent` on `project_heartbeats` (added as part of issue #21), for which the Inbox database is registered for `create`/`update`/`delete`.

Safe concurrency (an open question raised earlier — "what if a tick on the same source fires twice concurrently") is solved by the generic queue mechanism introduced elsewhere in the heartbeat/event layer: `onItemEvent` emits `enqueueJob(TASK_NAMES.heartbeatFire, { heartbeatId, itemId }, { jobKey: 'heartbeat-fire:${heartbeatId}:${itemId}' })` — the general heartbeat event path, whose action here is Semprec's own tick (`semprec.tick`) — not a bespoke SKIP LOCKED table just for the Inbox. A new event for an item that already has a pending job with the same `jobKey` replaces it instead of enqueuing a second one — so rapid successive edits collapse into a single fresh tick over the most current state, rather than a queue of stale ones, exactly as the open question demanded.

**API:**
- `GET /api/inbox-types` — active types, `[{ id, emoji, label }]`, the source for the Shortcuts picker
- **creating an Inbox item** — no bespoke endpoint; the generic create-item endpoint (issue #21) over the Inbox database, body `{ date, time, text, type: typeId }`; both `date` and `time` are mandatory from the client (never derived as "today" on the server) because of offline capture on a phone and delayed batch submission. This is also exactly the case the choke-point's idempotency key (issue #21) was built for — a batch resubmitted after a connectivity outage and safely retried does not create duplicate Inbox items
- **editing/deleting an Inbox item** — the same generic choke-point, no special path; it just fires `onItemEvent` as a side effect
- `POST /api/proposals/:id/confirm` — the single place where a real cross-DB write happens, only in the context of a logged-in user — see above
- `POST /api/proposals/:id/reject` — locks the card, writes nothing
- `POST /api/proposals/:id/revise` — body `{ message }` — chat-driven clarification/rewrite, allowed to overwrite the entire `proposal` including `entityKind`

## Scope

### In scope
- Baseline creation of the Inbox, Inbox item types, and Processing proposals databases themselves (`databases` rows with canonical keys `inbox`, `inboxItemTypes`, `processingProposals`, plus their properties) — issue #24's ten databases do not include these three, so this task owns their creation, then their full schema and behavior
- The Processing proposals state machine (`needsClarification` → `proposed` → `confirmed`/`rejected`/`invalid`) including transitions
- The generic `proposal` payload (`{ entityKind, target, properties }`) and the semantics of `revise` as a full overwrite
- Fingerprint-based (`fingerprint`) dedup/change detection and the locked-card principle
- The explicit `processingMethod` on the type (`pageContent`/`database`) + `targetDatabase`, replacing label-text comparison
- Archiving and deleting a type, including the fallback of deleted references into `needsClarification`
- Forced separation of proposal from write — Semprec's grant, `confirm` as the sole cross-DB write path (reusing the choke-point and the block-append mechanism)
- The `journal-inbox` view type (Czech label "Deník inbox" via i18n) and caching the displayed state into `items.computed`
- The `onItemEvent` trigger on `project_heartbeats` and registering the Inbox database for `create`/`update`/`delete`
- Using `enqueueJob`/`jobKey` to dedup concurrent ticks on the same item (integrating with the general mechanism, not defining it)
- All six API endpoints listed above, including the idempotency key on item creation

### Out of scope
- The definition of the schema engine, items-engine, choke-point, and the idempotency key itself (issue #21) — only consumed here
- Creating the ten hardcoded databases and their baseline properties (issue #24) — those ten do not include the three Inbox-pipeline databases, which are created here (see In scope)
- The general queue/heartbeat mechanism (`project_heartbeats`, `enqueueJob`, SKIP LOCKED, etc.) — implemented by issues #21 (queue engine, scheduler, `onItemEvent`) and #29 (module-level task registration), only consumed here
- The page block-append mechanism (issue #23) and the `temporal-switcher`/`mailbox-client` view mechanisms — already exist, only reused here
- Prompt engineering / the concrete implementation of the LLM call inside `typDef.prompt` and the target-project selection heuristic — content-level decision-making is out of scope for the DB/API structure this task delivers
- The module contract, testing, and general meta-layer over modules (issue #29)
- The Shortcuts picker UI itself (it only consumes `GET /api/inbox-types`)

## Dependencies
