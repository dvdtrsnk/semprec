## Context

Harvest issue #775 collected review findings from merged pull requests. PR #331
(`mcpSync.ts`) flagged that `syncMcpServerTools`'s `finally` block calls
`await handle?.close()` unguarded. If `close()` itself throws, JavaScript's
`finally`-wins semantics replace the `throw err` re-thrown from the `catch` block
above with the close failure, so the caller never sees the actual sync error — only
a close error. The function already applies exactly this "don't let a secondary
failure replace the original" discipline one block earlier, at `mcpSync.ts:186-190`,
where a failure to record `syncStatus: 'error'` is caught and logged rather than
allowed to propagate and mask `err`. The `finally` block's `handle?.close()` is the
one place in this function that discipline was not applied.

## Task

In `backend/packages/data/src/mcp/mcpSync.ts`, change `syncMcpServerTools`'s `finally`
block so that if `handle?.close()` throws while an error is already propagating from
the `try`/`catch` above, the close failure is logged (via `console.error`, mirroring
the `recordingErr` log at line 189) and does not replace the propagating error. When
no error is propagating (the `try` block completed and returned normally), a
`close()` failure must still propagate to the caller as before — the swallow only
protects an original error already in flight from being masked by a secondary close
failure, per the same principle already applied to the `syncStatus` write at lines
186-190.

## Touches

- backend/packages/data/src/mcp/mcpSync.ts (`syncMcpServerTools`'s `finally` block)

## Scope

### In scope

- Preventing `handle?.close()`'s own failure from replacing an in-flight sync error.

### Out of scope

- Any other error-handling path in `mcpSync.ts`.

## Acceptance criteria

- When `syncMcpServerTools` throws a sync error and `handle.close()` also throws, the
  caller's rejection is the original sync error, not the close error; the close
  failure is only logged.
- When `syncMcpServerTools` completes without an in-flight error and `handle.close()`
  throws, the caller's rejection is the close failure (unchanged from current
  behavior).
- When both the sync and the close succeed, behavior is unchanged.
