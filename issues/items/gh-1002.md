**Blocked by:** #974

## Context

Item creation honours a client-chosen `Idempotency-Key` through the `idempotency_keys` table. Its primary key is `key text` (`backend/packages/data/src/db/migrations/0001_core_schema.sql:163-168`, constraint `idempotency_keys_pkey`). `insertItemWithReplay` (`backend/packages/data/src/chokePoint/itemsStore.ts:70-135`) works like this:
- it reserves the key with `INSERT ... ON CONFLICT (key) DO NOTHING` (`:75-80`);
- on a conflict it reads the reservation back `WHERE key = $1 FOR UPDATE` (`:82-85`);
- it re-reserves after releasing a stale reservation, with the same `ON CONFLICT (key)` (`:116-121`).

`findIdempotentReplay` reads `WHERE key = $1` (`:164-167`). Keys are client-controlled and partly predictable. Internal producers use `journal:...` and `transcription:<fileItemId>`.

Two problems for a multi-tenant system:
- **The arbiter is the global key.** Once #1065 drops the legacy primary key, `ON CONFLICT (key)` no longer matches any constraint and every keyed create fails. Until then, the global key turns one tenant's key into a collision for another.
- **The conflict names a database id.** When a key is reused for another database, `ConflictError` carries `details: { key, reservedDatabaseId }` (`itemsStore.ts:97-101`). The REST adapter forwards any flat record of primitives verbatim (`backend/services/semprec-api/src/adapter/errorContract.ts:102-110,120-126`), so the 409 body exposes that id.

Tenancy state this issue builds on:
- `idempotency_keys` is a tenant table: `tenant_id uuid NOT NULL DEFAULT app_tenant_default()`, plus the RESTRICTIVE policy `tenant_isolation` `tenant_id = (SELECT app_tenant_default())`.
- `app_tenant_default()` is `COALESCE(app_current_tenant(), app_sole_tenant())` over the GUC `app.tenant_id`.
- The `WHERE key = $1` reads are therefore already confined to the caller's tenant under a runtime role.
- #974 added the tenant-leading unique index `idempotency_keys_tenant_key_uq` on `idempotency_keys (tenant_id, key)` beside `idempotency_keys_pkey`. The legacy key stays until #1065, which can drop it only after the code stops depending on it.

Why a target-less `ON CONFLICT`: while both indexes exist, an `ON CONFLICT (tenant_id, key)` arbiter leaves `idempotency_keys_pkey` as a non-arbiter index. Two concurrent creates with the same key then race into a raw unique violation on the legacy key, instead of converging. The existing race test (`backend/packages/data/src/__tests__/itemWrites.test.ts:90-101`) covers exactly that case. `ON CONFLICT DO NOTHING` with no conflict target treats every unique index as an arbiter: both indexes today, only the tenant-leading one after #1065.

## Task

Load `state-writes` (the reservation is a write guarded inside the same transaction) and `error-handling` (what the conflict carries).

1. **Arbiter.** In `insertItemWithReplay`, change both reservation inserts (`itemsStore.ts:75-80` and `:116-121`) to `ON CONFLICT DO NOTHING` with no conflict target. Everything else stays as it is: the `FOR UPDATE` read-back, the stale-reservation release (`requireAffectedRows`) and `findIdempotentReplay`. Do not add hand-written `tenant_id` predicates; RLS confines the reads.
2. **Conflict details.** The different-database `ConflictError` (`itemsStore.ts:97-101`) carries `details: { key }` only. The message stays free of any id.
3. **Docstrings.** In `insertItemWithReplay` and `findIdempotentReplay`, state that a reservation is per tenant: RLS confines the reads, and the arbiter is every unique index on `idempotency_keys`.
4. **Tests.** New `backend/packages/data/src/__tests__/idempotencyPerTenant.test.ts`. The cases needing the post-#1065 schema or a second tenant run in one transaction on `getTestPool()` (the owner), rolled back at the end:
   - `DROP INDEX IF EXISTS tenants_single_tenant_guard`;
   - `ALTER TABLE idempotency_keys DROP CONSTRAINT idempotency_keys_pkey`;
   - insert a second `tenants` row, create one database per tenant with `databasesStore.createDatabase(client, ...)`;
   - `SET LOCAL ROLE semprec_data`;
   - switch tenants with `SELECT set_config('app.tenant_id', $1, true)`.

   Integration files run one at a time (`fileParallelism: false`, `backend/vitest.integration.config.ts:20`).

## Scope

### In scope
- The target-less reservation arbiter, the id-free conflict details, the docstrings and the tests.

### Out of scope
- Dropping `idempotency_keys_pkey` (#1065). Until then a key used in one tenant still blocks the same key in another tenant in a real two-tenant database; the guard prevents that state in production.
- Pruning id-only item lookups to the tenant's partitions (#1003).
- Prefixing internal idempotency keys or changing the REST error contract's shape.
- The end-to-end proof over every route (#1053).

## Acceptance criteria

All integration tests (`*.test.ts`).
- Reusing a key for a different database in the same tenant rejects with `ConflictError`, `code` `version_conflict`, and `details` exactly `{ key: "<the key>" }`. No database id appears in `details` or in the message.
- The existing cases in `itemWrites.test.ts` still pass: replay returns the original row, two concurrent creates with one key produce exactly one item, and a different-database reuse is a conflict.
- With `idempotency_keys_pkey` dropped (rolled-back transaction), a replay with the same key in the same database returns the first item with `created: false`, and only one `items` row exists. This proves the code no longer needs the legacy key.
- With the legacy key dropped and two tenants under `semprec_data`, key `k` used in tenant A and then in tenant B:
  - creates two distinct items, B's with `created: true`;
  - a replay in A still returns A's item;
  - `findIdempotentReplay` in B returns B's item and never A's.
- With the legacy key dropped, a release-and-reserve of a trashed reservation in tenant B leaves tenant A's reservation for the same key untouched.
