## Approved behavior specification

This epic preserves the complete approved behavior of source issue #73, inlined here so the epic is self-contained.

### Source behavior: [mail-sync-hardening 01/01] IMAP partial-fetch fallback, provider-side oversized/foreign attachment handling, and provider_message_id conflict hardening

## Context

Issue #26 (IMAP Sync Core, merged into `develop`) built the three sync adapters
(IMAP/imapflow, Gmail REST, Graph REST) with a shared `MAX_ATTACHMENT_BYTES`
(100MB, `providerTypes.ts`) safety cap and fully streamed attachment fetching —
`imapFlowClient.ts`'s `client.download()`, Gmail's per-attachment fetch, and
Graph's `$value` stream. Three specific edge cases in that same attachment path
were named in issue #26's own spec but deliberately deferred as non-primary,
and no later issue picked them up:

1. **IMAP partial-fetch fallback.** `imapFlowClient.ts` has exactly one fetch
   path for a body/attachment part: `this.client.download(uid, partId, { uid:
   true, maxBytes: MAX_ATTACHMENT_BYTES })`. If that call fails partway
   through (a non-RFC-conformant server, a connection drop on a very large
   message), there is no fallback — the issue's own spec named a manual
   `BODY[section]<start.count>` chunked re-fetch as "the manual fallback for
   edge cases where the library's high-level streaming fails," but it was
   never implemented; `download()` remains the only path.
2. **Gmail attachments replaced by a Drive link.** Gmail's real inline
   attachment limit is ~25MB; above that, Gmail itself replaces the file with
   a Google Drive share link inside the message body and does not serve it as
   a MIME/API attachment part at all. `gmailRestClient.ts` has no detection
   for this shape — an oversized original attachment is currently just absent
   from the synced message, with nothing in the Email item indicating a file
   was ever there.
3. **Graph `itemAttachment`/`referenceAttachment`.** `graphRestClient.ts`'s
   `classifyGraphAttachments` filters `/messages/{id}/attachments` down to
   `m["@odata.type"] === "#microsoft.graph.fileAttachment"` only (see the
   comment on `GraphAttachmentResource`: "`itemAttachment`/`referenceAttachment`
   ... are rare enough that issue #26's scope doesn't ask for them"). This
   doesn't crash, but a forwarded calendar item or a OneDrive share link
   attachment is silently dropped — no Files item, no mention in the body,
   no trace that anything was ever attached.
4. **`provider_message_id` conflict hardening.** `mail_message_meta`'s
   `upsertMailMessageMeta` (`mailMessageMetaStore.ts`) upserts via
   `ON CONFLICT (message_id) DO UPDATE` — the correct primary guard, since
   `message_id` is the one field every adapter (including IMAP, which never
   sets `provider_message_id`) always populates. The partial unique index
   `mail_message_meta_provider_msg_uq` on `provider_message_id` remains a
   real, separately enforced DB-level constraint, but has no `ON CONFLICT`
   arbiter of its own on this insert — a `provider_message_id` collision
   (two different `message_id`s the same provider happens to map to the same
   provider-side id, or an optimistic Sent-folder insert racing the next
   sync's observation of the same message) surfaces today as a raw Postgres
   unique-violation error propagating out of the sync job, rather than a
   graceful skip.

None of these four are covered by issue #72 (IMAP IDLE / push notifications /
flag write-back — a different, transport-layer set of gaps) or by any other
open issue.

## Task

1. Add a `BODY[section]<start.count>`-based chunked-read fallback to
   `imapFlowClient.ts`, used when `client.download()` throws mid-transfer for
   a given part. Retry via bounded partial fetches assembled into the same
   `Readable` contract `openStream()` already returns to `ingestAttachments`,
   still capped by the existing `MAX_ATTACHMENT_BYTES`.
2. Detect the "Gmail replaced this attachment with a Drive link" shape in
   `gmailRestClient.ts` (a part whose reported size is far smaller than what
   the message text implies, combined with a Google Drive share link
   appearing in the HTML/text body — Gmail's documented behavior above its
   inline limit) and ensure the link text is preserved in the Email item's
   body rather than silently vanishing; do not attempt to fetch the linked
   file itself (it requires separate Drive API access, out of scope here).
3. In `graphRestClient.ts`'s `classifyGraphAttachments`, stop silently
   dropping `itemAttachment`/`referenceAttachment` entries: at minimum,
   surface their presence (filename/type) so the synced message doesn't look
   like it had no attachment when Outlook shows one. Fetching/converting a
   `referenceAttachment`'s target (a real OneDrive/SharePoint file) is out of
   scope for this task — see Scope below.
4. Add an explicit `ON CONFLICT (provider_message_id) DO NOTHING` (or
   equivalent skip-and-continue) arbiter to `upsertMailMessageMeta`'s insert
   for the `mail_message_meta_provider_msg_uq` index, so a
   `provider_message_id` collision degrades to a safely-skipped duplicate
   insert (with the existing `message_id`-keyed row left untouched) instead
   of an unhandled constraint-violation error reaching the job queue.

## Scope

### In scope

- The four items above, scoped strictly to the IMAP/Gmail/Graph inbound
  (sync) attachment and dedup paths already built by issue #26.

### Out of scope

- Outgoing (send-side) attachment handling, including the >20MB
  files-to-blobs-with-link behavior — issue #27's scope (drafts/sending).
- Actually fetching a Graph `referenceAttachment`'s target file content via
  the Microsoft Graph OneDrive/SharePoint API, or a Gmail Drive-link's file
  content via the Google Drive API — both are separate, larger integrations
  (a second provider API and its own OAuth scope) beyond "don't silently
  drop the attachment's existence."
- IMAP IDLE, Gmail Pub/Sub push, Graph webhooks, and bidirectional flag
  write-back — issue #72's scope.
- Any change to the `MAX_ATTACHMENT_BYTES` cap value or the streaming
  architecture itself — both already correct per issue #26's review.

## Acceptance criteria

- A message whose IMAP body/attachment part fails a `client.download()` call
  (simulated via a fake IMAP client raising mid-download in a test) is
  retried through a `BODY[section]<start.count>` chunked path and the
  attachment is ingested successfully — observable via a passing test against
  the fake IMAP client.
- A Gmail message payload matching the "oversized attachment replaced by a
  Drive link" shape produces an Email item whose body/text contains the
  link, without a crash and without a Files item silently disappearing from
  view (no attachment row is expected for this case, but the message body
  visibly reflects that a large file was shared).
- A Graph message carrying an `itemAttachment` or `referenceAttachment`
  entry alongside a `fileAttachment` produces an Email item where the
  `fileAttachment` is ingested normally as a Files item and the
  `itemAttachment`/`referenceAttachment` entries are surfaced (name/type) in
  the message rather than vanishing without a trace.
- Two `upsertMailMessageMeta` calls with the same `provider_message_id` but
  different `message_id` no longer raise a raw Postgres unique-violation
  error out of the sync job; the second call completes without touching the
  first row's `message_id`-keyed identity.

## Decisions

- **Question:** Which boundary is load-bearing? **Adopted answer:** Retain streaming/100MB cap. **Reason:** It preserves approved source behavior.
- **Question:** Which boundary is load-bearing? **Adopted answer:** Surface placeholders, do not fetch Drive/OneDrive. **Reason:** It preserves approved source behavior.
- **Question:** Which boundary is load-bearing? **Adopted answer:** Preserve first identity on provider-id collision. **Reason:** It preserves approved source behavior.
