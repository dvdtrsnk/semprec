## Context

Model tier rationale: The per-row re-seal and sweep are specified, but locked re-sealing, keyset paging with failure aggregation and the two-tenant job case need care.

How credentials stand when this issue starts:

- #1032 added the `external_credentials.scheme` marker and made `getDecryptedCredential` read both schemes.
- The release checkpoint #1058 confirmed that a release with that dual read runs in production. A one-release rollback from the release that ships this sweep therefore lands on code that can open every row it re-seals.
- Since #1060, every new or replaced credential is sealed under its tenant's data key and bound to `tenant_id‖item_id` (`scheme = 'tenant'`).

The rows written before #1060 still have `scheme = 'master'`. They are sealed directly under `CREDENTIALS_MASTER_KEY` with no associated data, and are readable only through the dual read. Until they are re-sealed:

- deleting a tenant's key does not shred them;
- the ciphertext-swap weakness still applies to them.

The master scheme can be retired (#1069) only once no `master` row remains. The maintainer checkpoint #1068 confirms that in production.

What #1032 and #1060 provide:

- `backend/packages/data/src/credentials/externalCredentialsStore.ts`, the only file allowed to decrypt. It holds the module-private `credentialAssociatedData(tenantId, itemId)`, the UTF-8 bytes of `semprec:external-credential:v1:<tenantId>:<itemId>`.
- `getOrCreateTenantDataKey(client)` from `backend/packages/data/src/credentials/tenantKeysStore.ts` (#1031), which resolves the tenant through `app_tenant_default()`.

How core queue tasks are wired:

- **Names and runtimes.** Each task has a name in `CORE_TASK_NAMES` and a runtime in `CORE_TASK_AFFINITY` (`backend/packages/queue/src/index.ts:29-83`, `:95-119`).
- **Crontab sweeps.** Each is a line in `CORE_CRONTAB` with a handler in `createCoreTaskList` (`backend/packages/data/src/worker.ts:81-92`, `:113-227`). `queueFailedJobsPrune` is the most recent example.
- **Tenancy.** Since #982, every task declares `tenant` or `system` tenancy in `TASK_TENANCY` next to `CORE_TASK_AFFINITY`. A unit test in `backend/packages/queue/src/__tests__/tenantEnvelope.unit.test.ts` pins exactly which names are `system`.
- **Fan-out.** System sweeps use `forEachActiveTenant(pool, work: (tenantId) => Promise<void>)` from `backend/packages/data/src/tenancy/forEachActiveTenant.ts` (#983).
  - It runs inside `runAsSystem`, visits the active tenants one at a time, and calls `work(tenantId)` inside `runInTenant(tenantId, …)`.
  - One tenant's failure does not skip the others. Failures are logged, collected and rethrown as one `AggregateError`, so the job is retried.
- **Paging.** Keyset paging with independently committed chunks is recorded in `docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`.
- **Isolation proof.** Since #1056, the api runtime's two-tenant task suite `backend/services/semprec-api/src/__tests__/tenantIsolationJobs.test.ts` fails when a task name of its affinity set has no case. A new api task must add its case there.

## Task

Load `state-writes` and `error-handling`.

1. **Store** — in `externalCredentialsStore.ts`, add `reencryptCredentialUnderTenantKey(client: PoolClient, itemId: string): Promise<boolean>`. It runs inside the caller's transaction:
   - `SELECT tenant_id, ciphertext, nonce, key_version FROM external_credentials WHERE item_id = $1 AND scheme = 'master' AND tenant_id = app_tenant_default() FOR UPDATE`. If no row is returned, return `false`: the row was already re-sealed, replaced or deleted.
   - Decrypt with `decryptSecret` and `resolveMasterKeyFromEnv(key_version)`.
   - Get the key with `getOrCreateTenantDataKey(client)`. If its `tenantId` differs from the row's, throw.
   - Seal with `sealSecret(plaintext, key.dataKey, credentialAssociatedData(row.tenant_id, itemId))`.
   - Run `UPDATE external_credentials SET ciphertext = $2, nonce = $3, scheme = 'tenant', key_version = 1 WHERE item_id = $1 AND scheme = 'master'`, checked with `requireAffectedRows` (the row is locked). Return `true`.
   - Write no `credential_access_log` row. The plaintext never leaves this function and no connection is made with it, while the log records uses of a secret. Say so in the doc comment.
2. **Sweep** — new file `backend/packages/data/src/credentials/reencryptCredentialsJob.ts` with `handleCredentialReencryptSweepTask(pool: Pool): Promise<void>`:
   - Inside `forEachActiveTenant(pool, work)`, for each tenant read keyset pages of up to 100 `item_id`s, with at most 50 pages per run: `SELECT item_id FROM external_credentials WHERE scheme = 'master' AND tenant_id = app_tenant_default() AND ($1::uuid IS NULL OR item_id > $1) ORDER BY item_id LIMIT 100`.
   - Process each row in its own `withTransaction` that calls step 1. Credentials are few, and one transaction per row keeps a row that cannot be decrypted from rolling back its neighbours.
   - When a row throws, log at `error` with `{ itemId, err }` and continue. Never log ciphertext or plaintext.
   - After a tenant's pages, throw an error from `work` stating how many rows failed in that tenant, so `forEachActiveTenant` aggregates it and the job is retried.
   - Log one `info` line per tenant with the re-encrypted count.
3. **Queue registration**:
   - Add `CORE_TASK_NAMES.CREDENTIAL_REENCRYPT_SWEEP = "credentialReencryptSweep"` with `CORE_TASK_AFFINITY` `"api"`, the runtime that holds `CREDENTIALS_MASTER_KEY`.
   - Add `TASK_TENANCY.credentialReencryptSweep = "system"`, as for the other crontab sweeps, and add the name to the `system` list in `tenantEnvelope.unit.test.ts`.
   - Add the `CORE_CRONTAB` line `50 * * * * credentialReencryptSweep`. It runs hourly, is a no-op once nothing is `master`, and also re-seals any row a rolled-back previous release wrote.
   - Add a handler entry in `createCoreTaskList`.
   - Add the sweep's case to `backend/services/semprec-api/src/__tests__/tenantIsolationJobs.test.ts`. With tenants A and B both holding `master` rows, one run re-seals each tenant's rows under its own key, and no row of one tenant is opened in the other's scope.
   - To fabricate `master` rows there with `encryptSecret`, add `@semprec/credentials` (`workspace:*`) as a devDependency of `backend/services/semprec-api/package.json` and update `backend/pnpm-lock.yaml`; the api package does not depend on it today (`backend/services/semprec-api/package.json:11-25`).
   - Update `backend/packages/queue/src/__tests__/taskAffinity.unit.test.ts` and `EXPECTED_CRONTAB_IDENTIFIERS` in `backend/services/semprec-api/src/__tests__/queueRuntime.test.ts:12-24`.

## Acceptance criteria

All integration unless marked. Two-tenant cases use #975's `createTestTenant(pool)` and `createRuntimeRolePool(adminPool, "semprec_data")`. Legacy rows are fabricated with `encryptSecret` plus a raw `INSERT` that omits `scheme`.

**Re-sealing**
- Tenant zero holds 3 `master` rows and tenant B holds 2. After one run of `handleCredentialReencryptSweepTask`:
  - all 5 rows are `tenant`;
  - each decrypts to its original plaintext through `getDecryptedCredential` in its own tenant's scope;
  - `tenant_keys` holds exactly one row per tenant.
- A second run changes nothing: every ciphertext is byte-identical.
- 101 `master` rows in one tenant are all re-sealed in a single run.

**Failures and concurrency**
- A row whose master ciphertext is corrupted stays `master` while the others are re-sealed, and the run rejects. The error log carries that row's item id and contains neither ciphertext nor plaintext.
- `reencryptCredentialUnderTenantKey` on a row that `storeCredential` has already replaced (now `tenant`) returns `false` and leaves the ciphertext untouched.
- With a superuser pool in tenant A's scope, the re-seal never selects or changes a row of tenant B.

**Side effects and registration**
- The sweep writes no `credential_access_log` row.
- `CORE_TASK_AFFINITY.credentialReencryptSweep` is `"api"` and `TASK_TENANCY.credentialReencryptSweep` is `"system"` (unit).
- The api runtime's known crontab identifiers include `credentialReencryptSweep`, and `createApiCoreTaskList` registers its handler.
- The api runtime's `tenantIsolationJobs.test.ts` passes its exhaustiveness check with the new case.
