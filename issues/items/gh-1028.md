## Context

Model tier rationale: The owner-conditioned SQL, return type and every test site to update are given exactly.

An agent's destructive generic operation and its gated MCP tool calls create `approval_requests` rows. The table, created in `backend/packages/data/src/db/migrations/0021_approval_requests.sql:14-24`, has no owner column; it links to its run through `agent_run_id → agent_runs(id)`, and the run's `actor_user_id` is the user its writes are attributed to.

Approvals are listed and decided without checking who is asking:
- **Listing.** `GET /api/approval-requests` (`backend/services/semprec-api/src/approvalRequestsHandler.ts:51-55`) returns `listApprovalRequestsQueue(client)` (`backend/packages/data/src/mcp/approvalRequestsQueue.ts:99-127`). That is built on `listPendingApprovalRequests` (`backend/packages/data/src/mcp/approvalRequestsStore.ts:196-201`): `SELECT * FROM approval_requests WHERE status = 'pending'`, every request of every run.
- **Deciding.** `PATCH /api/approval-requests/:id` (`approvalRequestsHandler.ts:57-91`) calls `decideAndEnqueueApprovalRequest` (`backend/packages/data/src/mcp/approvalDecisionAction.ts:28-45`), which calls `decideApprovalRequest` (`approvalRequestsStore.ts:216-231`): `UPDATE … WHERE id = $1 AND status = 'pending'`. Any authenticated user can decide any request. `decided_by` is set to whoever called.
- **Re-read.** When the update matches nothing, the handler re-reads the row with `getApprovalRequest` in a second transaction (`:86-91`). It answers 200 with the request's current state to any caller, and 404 only when the id does not exist.

RLS hides another tenant's `approval_requests` and `agent_runs` once the request runs in its tenant scope. This issue adds the explicit owner condition the program requires on every code path: a foreign id, an unknown id and a request of another user's run must all look the same.

#1018 made every run's `actor_user_id`, heartbeat and system runs included, the tenant's own user. It also addresses `approval_pending` notifications to that user.

## Task

Load `state-writes` (the ownership check must be part of the decide statement itself) and `io-hardening` (foreign ≡ missing).

1. **Owner-conditioned decision.** In `decideApprovalRequest`, add the run-owner condition to the same `UPDATE`:
   `WHERE id = $1 AND status = 'pending' AND EXISTS (SELECT 1 FROM agent_runs r WHERE r.id = approval_requests.agent_run_id AND r.actor_user_id = $3)`
   `$3` is `decidedBy`. There is no separate pre-check.
2. **Owner-scoped reads.** In `approvalRequestsStore.ts`:
   - add `getApprovalRequestForOwner(client, id, ownerUserId)`, the row only when its run's `actor_user_id = ownerUserId`;
   - change `listPendingApprovalRequests(client, ownerUserId)` to return only pending requests of runs whose `actor_user_id = ownerUserId`, still oldest first.

   `listApprovalRequestsQueue(client, ownerUserId)` passes the owner through. `getApprovalRequest` keeps its signature for the execution paths (`approvalRequestExecution.ts`, `genericOperationGateway.ts`).
3. **One transaction for decide and re-read.** `decideAndEnqueueApprovalRequest` returns `{ outcome: "decided" | "unchanged"; request } | null`:
   - **decided:** the update matched, and an approved request is enqueued exactly as today;
   - **unchanged:** the update matched nothing, but `getApprovalRequestForOwner` finds the row in the same transaction, i.e. already decided by its owner;
   - **null:** neither.

   Do not export `getApprovalRequestForOwner` or `decideApprovalRequest` from `backend/packages/data/src/index.ts`.
4. **Handler.**
   - `GET` passes `identity.user.id`.
   - `PATCH` answers 200 with `toApprovalRequestDecisionView(result.request)` for both outcomes. For `null` it answers `404 { error: "Not found" }`, the same body as for an unknown id. Remove the second-transaction re-read.
5. **Tests.** Existing tests decide with a freshly created user who is not the run's actor, and must now decide as the run's actor:
   - `approvalRequestsHandler.test.ts:30-35,64`
   - `approvalRequestsStore.test.ts:124`
   - `approvalRequestExecution.test.ts:107`
   - `approvalRequestsQueue.test.ts:163`
   - `genericOperationGateway.test.ts:70` (`approveDestructive`), `:273` (`createPendingDelete`) and `:666-674` (`createPendingDeleteAndApprove`, whose `decided!.status` read at `:674` follows the new return type)
   - `approvalReplayComposition.test.ts:67`

   Add the criteria below. For the cross-tenant cases, use the two-tenant runtime-role harness of #975 (`createTestTenant`, `createRuntimeRolePool`, `getTenantZeroId` from `@semprec/data/testSupport`); the superuser test pool bypasses RLS.

## Scope

### In scope
- Owner-conditioned deciding, owner-scoped listing and re-read, a uniform 404 for unknown, foreign and not-owned requests, and the test updates.

### Out of scope
- Who receives `approval_pending` notifications, and runs' `actor_user_id` (#1018).
- Running the approval routes in the caller's tenant scope (#981).
- Execution-time replay checks, which are unchanged.
- The exhaustive REST isolation suite over every route (#1053).
- Web client changes. It already treats 404 as unavailable (`web/src/api/approvalQueueOperations.ts:85`).

## Acceptance criteria

- **Owner can decide.** When the run's actor PATCHes `approved` on a pending request, the response is 200 with the decided view, and exactly one `approvalExecute` job is enqueued. A repeated PATCH by the same user answers 200 with the unchanged current state. (integration, `approvalRequestsHandler.test.ts`)
- **Not-owned ≡ unknown.** When a different user PATCHes the request, the response is 404 with a body byte-identical to a PATCH on a random UUID. The row stays `pending` with `decided_by` NULL, and no job is enqueued. This holds both before and after the owner decided. (integration, `approvalRequestsHandler.test.ts`)
- **Listing is owner-scoped.** `GET /api/approval-requests` lists only requests whose run's actor is the caller. Another user's pending requests are absent. (integration, `approvalRequestsHandler.test.ts`)
- **Store-level guards.** `decideApprovalRequest` with a `decidedBy` other than the run's actor returns `null` and changes nothing. `listPendingApprovalRequests(client, userId)` excludes other owners' rows. (integration, `approvalRequestsStore.test.ts`)
- **Cross-tenant ≡ unknown.** Tenant B's user PATCHing or listing tenant A's request gets 404, or an empty list. Tenant A's request is unchanged. (integration, runtime-role harness)
- **Execution unchanged.** An approved request still executes through `approvalExecute` exactly as before. (integration, `approvalRequestExecution.test.ts`, `approvalReplayComposition.test.ts`)
