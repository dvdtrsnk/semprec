## Context

Model tier rationale: One removed call, one amended test and three new tests behind existing fixtures (the integration pool harness, the runtime-role pool, and the owned-database child-process cases of the packaging source). It adds no route, table, migration or contract and changes no authorization, but it touches the start-up of the one process that hosts the choke-point under the tenant-scope rules, and its decisive test only means something if the child process really runs under strict scope, which the e2e tier does not do by default.

The source `[native-entry 01/02] Resolve every compiled service entry through built workspace roots and check them before a release is promoted` makes the four compiled service entries loadable by plain Node. Its Context records one further defect that it deliberately leaves out, and its Task step 6 forbids any case that starts `alldots-api`: the API does not stay up under the production default of strict tenant scope. This source closes that defect and adds the start of the compiled API to the same owned-database cases.

The defect, re-verified at commit `30753cc6e` on a private export of the tree (installed with `pnpm@9.12.0 install --frozen-lockfile`, the eight manifests of the packaging source applied, `pnpm -r run build`, then plain `node services/alldots-api/dist/serve.js` from `backend/` with an environment of `PATH`, `HOME` and the service configuration only, as `alldots_data` against a scratch embedded PostgreSQL that `runMigrationsCli.js` and `runSeedCli.js` had prepared): with `ALLDOTS_TENANT_SCOPE` unset, which is strict (`enforceTenantScope` in `shared/src/tenantScope.ts`; `deploy/shared/env/*.example` set it nowhere and `docs/operations/tenancy.md` requires strict), the process exits 1 with `TenantScopeMissingError: No tenant scope is active at withTransaction` before it listens. With `ALLDOTS_TENANT_SCOPE=warn` the same build listens and `GET /healthz` answers 200. The throw comes from `createApiQueueRuntime` in `backend/services/alldots-api/src/queueRuntime.ts`, which calls `runHeartbeatFireQueueSplitMigration(pool)` right after `ensureQueueSchema` and `grantQueueSchemaPrivileges`, outside any scope. The three test tiers never saw it because `testSupport/globalSetup.ts` sets `ALLDOTS_TENANT_SCOPE` to `warn` for the whole run, and none of the tests that call `createApiQueueRuntime` (`queueRuntime.test.ts`, `mailSyncComposition.test.ts`, `approvalReplayComposition.test.ts`) sets strict.

What the migration is (`backend/packages/data/src/scheduler/heartbeatFireQueueSplitMigration.ts`, issue #222): a one-time cutover of the queue, not of a table. In one transaction it finds every job still queued under the retired task name `heartbeatFire` in `graphile_worker.jobs`, removes it with `graphile_worker.remove_job(key)`, reads its heartbeat's `action_id` from `project_heartbeats` (a tenant-scoped table under row-level security), and re-enqueues it under `heartbeatFireCore` or `heartbeatFireAgent` with the same key, queue name, `max_attempts` and envelope. It returns at once when no legacy job exists. No release since #222 enqueues `heartbeatFire`, so on any database that has only run releases of this repository it finds nothing.

Why it also runs at API start: issue #91 ("the #222 migration running at API install") put it there. The same migration is wired, by #222 itself, into the two places that the accepted decision `[[2026-09-10-app-code-post-migration-steps]]` names for a one-time application-code step: `db/runMigrationsCli.ts` (the real deploy, run by `deploy.sh` `run_migrations` before `current` moves and before any service restarts) and `testSupport/globalSetup.ts`. That decision says such a step runs "always immediately after `runMigrations`, from both `runMigrationsCli.ts` (real deploys) and `testSupport/globalSetup.ts` (tests)" and never from request-handling code. The API-start call is a third invocation that the rule does not provide for. In production it is redundant: the deploy always ran the CLI first. A `deploy.sh --rollback` runs no migration and needs none for this step: the CLI call was added with the #222 split (1a25df3c2), before the API-start call (fe93216b2), so every release that can be a rollback target has run it at its own deploy, and no release since #222 enqueues `heartbeatFire`.

Why the call cannot simply be wrapped in `runAsSystem`: with a system scope the throw is gone, but the pool of the API is the runtime role `alldots_data`, to which row-level security applies, and a system scope reads as no tenant (`[[2026-10-05-tenant-scope-propagation]]`, `[[2026-10-06-system-work-fans-out-per-tenant]]`: under strict, system scope sees no tenant rows). Measured on the same build with the call wrapped: with no legacy job queued the API listens, and with one legacy job queued (the heartbeat seeded) it exits 1 with `references heartbeat '...', which no longer exists`, a false statement that comes from the hidden `project_heartbeats` row. A wrapped call is therefore correct only when it has nothing to do. The step needs the migrating role, which sees every tenant, and that role exists only in the deploy CLI (`[[2026-10-08-deploy-time-tenant-work-runs-as-the-runtime-role]]`: the migrating role keeps the global steps; the runtime pool of a service does not run data migrations). A per-tenant fan-out is not possible either, because a legacy job's envelope carries no tenant, the heartbeat row is the only way to learn it. The deploy path was measured to do the whole job: with one legacy job queued after the first CLI run (heartbeat seeded), a second plain `node packages/data/dist/db/runMigrationsCli.js` removed it, re-enqueued it under `heartbeatFireCore` with the same key and stamped the sole tenant into its envelope (`runLegacyJobEnvelopeStampMigration`, the next step of the CLI).

The correct fix is therefore to remove the call from the API start, not to patch its scope. No new ADR is written: the invocation points of a one-time application-code step are already decided by `[[2026-09-10-app-code-post-migration-steps]]`, and scope containment of start-up work by `[[2026-10-05-tenant-scope-propagation]]` ("long-lived loops, listeners and registries start inside `runAsSystem`"); this change brings `createApiQueueRuntime` back under them. `ensureQueueSchema` and `grantQueueSchemaPrivileges`, which every one of the three queue runtimes calls at start, are not data migrations: each enters its own `runAsSystem("queue-schema", ...)`, they are idempotent schema steps, and they were measured to pass under strict in all three services.

Every other service start was measured under strict scope on the same build (scrubbed environment, no `ALLDOTS_TENANT_SCOPE`, `alldots_data` or `alldots_side` as each service uses it, SIGTERM after the log line): `alldots-agents` logs `alldots-agents queue runtime started` (after its start-up repair, `Repaired interrupted agent runs`), `alldots-transcribe` logs `alldots-transcribe queue runtime started`, `alldots-ai-gateway` logs `alldots-ai-gateway listening`, each exits 0 with its shutdown log. `alldots-api`, with the call removed, logs `alldots-api listening`, answers `GET /healthz` with 200 `{"status":"ok"}` (that handler runs in `runAsSystem("healthz", ...)` and reads the process heartbeat that `startProcessHeartbeat` wrote at start) and exits 0 with `alldots-api shutdown complete`, also on a database seeded with a tenant. Realtime is not a process: `wireRealtimeHooks(pool)` runs inside the API start and the gateway's `createGatewayServer`, and the graphile-worker runner is started by the three queue runtimes, so both are covered by those starts. No service source other than `queueRuntime.ts` of the API calls a data migration, cutover or backfill function (a search of `backend/services/*/src` outside tests). Of these start paths only the three that the packaging source's owned-database cases start have a test of any kind, and those cases do not say which tenant-scope mode their child runs in; this source makes that explicit and adds the API.

## Scope

### In scope

- Removing the `heartbeatFire` queue-split migration from the start of `alldots-api`, and the tests that prove the API starts under strict tenant scope in-process, as a compiled process and in the deploy order.
- Making the tenant-scope mode of every compiled service start in the owned-database cases explicit and strict.
- A source scan that keeps a data migration out of every service's source.
- The two records of the evidence.

### Out of scope

- Any change to `runHeartbeatFireQueueSplitMigration`, to `runMigrationsCli.ts`, to `testSupport/globalSetup.ts`, to the `@alldots/data` export or `publicSurface.test.ts`. The deploy CLI keeps running the migration on the owner pool as before; whether that tenant-row read should become a per-tenant step under `[[2026-10-08-deploy-time-tenant-work-runs-as-the-runtime-role]]` is not decided here.
- Wrapping the call in `runAsSystem` or moving it to a per-tenant scope (shown above to fail on a database that has a legacy job).
- A start-up refusal when a legacy `heartbeatFire` job is found at API start. A leftover job without a handler fails visibly in graphile-worker, and no release has enqueued the name since #222.
- `ALLDOTS_TENANT_SCOPE` itself: its default, its `warn` mode, the production environment files, and the go-live check of #1086. The tiers keep their `warn` setting from `globalSetup`.
- Any code change in `alldots-agents`, `alldots-ai-gateway` or `alldots-transcribe`: they start under strict scope today and only gain a test.
- Package resolution, the checker and the deploy check (the packaging source), a mail, restic or backup script, provider or network calls, the real systemd sandbox, and any claim about a deployed host or production readiness.

## Acceptance criteria

- When `createApiQueueRuntime` is called on a `alldots_data` runtime-role pool with `ALLDOTS_TENANT_SCOPE` unset, then it resolves and `stop()` resolves; on the unfixed code it rejects with `TenantScopeMissingError` at `withTransaction`.
- When a legacy `heartbeatFire` job is queued and the API runtime starts under that condition, then it starts and the job is unchanged (same task name, key and attempts); on the unfixed code the start fails or the job is moved.
- When the deploy-time migration has moved a legacy `heartbeatFire` job under `heartbeatFireCore`, then the API runtime executes it (`attempts >= 1`) and the `heartbeatFire` name has no job left.
- When the compiled `services/alldots-api/dist/serve.js` is started with an environment that has no `ALLDOTS_TENANT_SCOPE` against an owned scratch database as the runtime role, then it logs `alldots-api listening`, `GET /healthz` answers 200 `{"status":"ok"}`, and after SIGTERM it exits 0 within 20 seconds with `alldots-api shutdown complete`; the database is dropped and absent and no child outlives the test. On the unfixed code it exits 1 with `TenantScopeMissingError` before it listens.
- When `alldots-agents`, `alldots-ai-gateway` and `alldots-transcribe` are started in the same cases, then the environment passed to each child has no `ALLDOTS_TENANT_SCOPE` key although the test process has one, and each reaches its log line (`alldots-agents queue runtime started`, `alldots-ai-gateway listening`, `alldots-transcribe queue runtime started`) and exits 0 on SIGTERM.
- When the compiled migrations CLI is run a second time on a seeded owned database that holds one legacy `heartbeatFire` job, then the job is under `heartbeatFireCore` with the same key and the seeded tenant in its envelope, and `verifyTenancyCli.js` exits 0 with `tenancy: verified`, all under an environment without `ALLDOTS_TENANT_SCOPE`. This criterion also holds on the unfixed code; it pins that the deploy step stays the one place that moves the job.
- When any non-test source under `backend/services/*/src` names a `run...Migration`, `run...Cutover...` or `run...Backfill...` function, then the unit test fails naming the file; on the unfixed code it names `alldots-api/src/queueRuntime.ts`.
- The existing tests of `createApiQueueRuntime` that run in warn mode, `heartbeatFireQueueSplitMigration.test.ts` and `publicSurface.test.ts` pass, and the follow-up file and the F5 bullet state exactly what was started under strict scope, keep the earlier text, and claim no production readiness.
