**Blocked by:** #703

## Context
Review of pull request #434 found that in `backend/packages/data/src/push/__tests__/apnsAdapter.unit.test.ts` (currently around line 55), `expect(() => getApnsConfigFromEnv()).toThrow();` asserts no error message pattern, unlike the sibling test (line 46) which uses `.toThrow(/APNS_PRIVATE_KEY_PATH/)`. In this test case (`APNS_PRIVATE_KEY_PATH` points at a nonexistent file, so `getApnsConfigFromEnv`'s own missing-configuration guard never fires), the actual thrown error comes from `readPrivateKey`'s unguarded `fs.readFileSync(privateKeyPath)` in `backend/packages/data/src/push/apnsAdapter.ts` — a Node `ENOENT` error, not the config-validation `Error` the guard throws. The unpatterned assertion would still pass if that `fs.readFileSync` call started throwing for the wrong reason.

Issue #703 also touches `apnsAdapter.unit.test.ts` (rewriting push-delivery retry behavior) without naming a narrow region, so this issue is blocked on it to avoid a merge collision on the same file.

## Task
- In `apnsAdapter.unit.test.ts`, give the `toThrow()` assertion at the line named above a message pattern that matches the actual Node `ENOENT` error `fs.readFileSync` throws for the nonexistent `APNS_PRIVATE_KEY_PATH` file in that test case (e.g. a pattern matching `ENOENT` and/or the file path), in the same style as the sibling assertion at line 46.

## Touches
- backend/packages/data/src/push/__tests__/apnsAdapter.unit.test.ts (the one `toThrow()` assertion named above)

## Scope
### In scope
- The single assertion named above.

### Out of scope
- Any other test case in `apnsAdapter.unit.test.ts`, and any change to `getApnsConfigFromEnv` itself.

## Acceptance criteria
- The `toThrow()` assertion at the named test case fails if `getApnsConfigFromEnv` starts throwing for an unrelated reason (e.g. a missing env var instead of the file-read ENOENT) instead of the one the test intends to cover.
