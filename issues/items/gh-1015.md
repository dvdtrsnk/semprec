## Context

`SempConversation` (`backend/packages/agent-runtime/src/sempConversation.ts:96-263`) holds Semp's ongoing conversation with the user: one in-memory agent session, reused across `send()` calls, paused after a TTL of inactivity, and woken again with reconstructed history. It is a process-wide singleton by design. The class doc says "Semprec is a single-tenant system with exactly one ongoing conversation" (`:92-94`). The class keeps:
- **One entry.** A single `entry` and a single `waking` flag (`:97-99`). Its busy check (`:120-122`) therefore makes any caller wait on any other caller's turn.
- **One project.** A single `options.projectItemId` (`:75-76`) for every wake (`:156-164`).

With tenants, every tenant has its own conversation and, once provisioning runs per tenant (#1005), its own Semprec project. The project is the item `seedSystem` creates and makes the system settings database's `owner_project_item_id` (`backend/packages/data/src/seed/seedSystem.ts:130-152`). A shared singleton would:
- continue tenant A's session for tenant B's message;
- show B A's history;
- block B whenever A's turn is in flight.

The class is exported from `backend/packages/agent-runtime/src/index.ts:25-32`. No production composition root constructs it yet; only `backend/packages/agent-runtime/src/__tests__/sempConversation.test.ts` does. Changing its options shape breaks no caller.

What earlier issues provide:
- The tenant scope in `@semprec/shared`: `runInTenant(tenantId, fn)`, `runAsSystem(reason, fn)`, and `currentTenantScope()`, which returns `{ kind: 'tenant', tenantId } | { kind: 'system', reason } | undefined`.
- Entering a different tenant inside a tenant scope throws `TenantScopeConflictError`.
- `withTransaction` and the pool set `app.tenant_id` from the scope, so row-level security limits every row read and written inside it to that tenant. That covers `createAgentRun`, history reconstruction, and `finishAgentRun`.
- #991 runs the agents process inside each job's tenant.
- Long-lived in-process state must be keyed by tenant and must re-enter the tenant explicitly on timer callbacks. It never relies on whatever scope happens to be active.

## Task

Load `error-handling` (failed turns and pauses keep per-tenant state consistent) and `io-hardening` (timers and shutdown of in-process state).

1. **Per-tenant state.** Replace `entry` and `waking` with `private readonly conversations = new Map<string, { entry: ConversationRegistryEntry | null; waking: boolean }>()`, keyed by tenant id.
   - All busy, wake, reuse and failure logic of `send()` applies to the caller's tenant's state only.
   - When a tenant's state goes back to `{ entry: null, waking: false }`, delete its key, so the map holds only live conversations.
2. **Tenant from scope.** At the top of `send()`, synchronously and before any `await`, read `currentTenantScope()`. Throw `new Error("SempConversation.send must run inside a tenant scope")` unless it is `{ kind: 'tenant' }`. Nothing is read or written in that case.
3. **Project per tenant.** Replace the option `projectItemId: string` with `resolveProjectItemId: (pool: Pool) => Promise<string>`. Call it once per wake, inside the caller's tenant scope, before `reconstructHistory` and `createAgentRun`. Pass its result where `this.options.projectItemId` is used today (`:157`, `:160`). Update the option's doc comment.
4. **Timers.**
   - `scheduleTtl` takes the tenant id, and its callback runs `runInTenant(tenantId, () => this.pause(tenantId))`.
   - `pause(tenantId)` operates on that tenant's entry only and keeps its retry-on-failure behaviour (`:239-262`).
   - `touch` reschedules within the same tenant.
5. **Clear.** `clear()` remains the test and shutdown seam and clears every tenant's timer and state.
6. **Docs.** Rewrite the class doc (`:81-95`): one conversation per tenant, multiplexed by the scope's tenant id; tenants never wait on each other.
7. **Tests.**
   - Update the constructor calls in `sempConversation.test.ts` to `resolveProjectItemId`.
   - Run every existing `send()` inside `runInTenant(<tenant zero id>, ...)`.
   - Add the cases below, using the two-tenant harness from #975:
     - `createTestTenant(adminPool)` for tenant B;
     - `getTenantZeroId()` for tenant A;
     - a `createRuntimeRolePool(adminPool, "semprec_data")` pool passed to `SempConversation`.
   - Create each tenant's user bound to it with `createUser(..., { tenantId })` (#968), so the wake run has an actor in either tenant.

## Acceptance criteria

- **Scope required.** `send()` with no scope, and `send()` inside `runAsSystem(...)`, rejects with the scope error. No `agent_runs` row is created and `resolveProjectItemId` is not called. (integration, `sempConversation.test.ts`)
- **No cross-tenant busy.** Tenant A has a turn in flight. Then:
  - tenant B's `send()` is not answered with `SEMP_BUSY_ERROR_MESSAGE`;
  - B wakes its own run, with B's `project_item_id` and B's `tenant_id`;
  - a second concurrent `send()` in A is still answered with `SEMP_BUSY_ERROR_MESSAGE`.

  (integration, `sempConversation.test.ts`)
- **Per-tenant reuse.** After a completed turn in each tenant:
  - A's next `send()` continues A's session on A's `agent_runs` row;
  - B's next `send()` continues B's;
  - neither session receives the other tenant's task.

  (integration, `sempConversation.test.ts`)
- **Per-tenant history.** A wake in B reconstructs history only from B's prior runs. A's runs are never passed to B's session. (integration, `sempConversation.test.ts`)
- **TTL pause.** When A's TTL fires, A's run is finished as `done` inside A's tenant. B's entry stays live, and B's next `send()` reuses B's run. (integration, `sempConversation.test.ts`)
- **Resolver scope.** `resolveProjectItemId` runs inside the waking tenant's scope: `currentTenantScope()` within it is that tenant. (integration, `sempConversation.test.ts`)
- **Existing behaviour.** Every existing `sempConversation.test.ts` case passes inside tenant zero's scope. (integration)
