**Model tier:** medium

## Context

Model tier rationale: Two small read routes on existing owner-scoped store functions, but they add public routes that must be registered in the route matrix and tenant isolation tests.

Product behavior: a client can re-read one approval request after a live update and show an unread count badge for pending requests (optionally only those from chats).

Today `backend/services/semprec-api/src/approvalRequestsHandler.ts` serves `GET /api/approval-requests` (the list) and `PATCH /api/approval-requests/:id`. There is no route to read one request and no count. `getApprovalRequestForOwner` in `backend/packages/data/src/mcp/approvalRequestsStore.ts` already returns a request only when its run belongs to the caller and answers the same way for a foreign and an unknown id.

This issue builds on #1766 (the `source` of a request, used by the count filter). #1789 publishes invalidations that clients answer by re-reading one request through the route added here.

Decision: this issue does not return the outcome of a decision. Telling a first decision apart from a repeated one on the `PATCH` response is #2022, which builds on this one.

Shared-file ordering: this issue also waits for #1770 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `testing`, `error-handling` and `io-hardening`.

1. `GET /api/approval-requests/:id`: returns the same view the `PATCH` returns (`toApprovalRequestDecisionView`, extended with `source` from #1766 and `riskClass`), loaded with `getApprovalRequestForOwner`. An unknown, foreign or other-tenant id answers 404 with the same body as the existing not-found response. Validate `id` as a UUID (400 on malformed, as `PATCH` does).
2. `GET /api/approval-requests/count?status=pending&source=chat`: returns `{count}` for the owner. `status` accepts only `pending` in this issue; `source` is an optional comma list of `chat,tick,mcp`; unknown values answer 400. The count must equal the number of rows the list returns for the same filter.
3. Register the literal `/api/approval-requests/count` before the `:id` pattern in the handler so it is not captured as an id.
4. Add both new GET routes to `backend/services/semprec-api/src/routeMatrix.ts` and to the tenant isolation route test.

## Scope

### In scope

- Read one request and count pending requests.

### Out of scope

- Filtering, paging and listing decided requests: #1785.
- The `source` derivation: #1766.
- Realtime invalidation events: #1789.
- A count of anything other than pending requests (for example the Inbox count: #1823).
- The `outcome` field of the decision response, which tells a first decision from a repeated one: #2022, which builds on this one.
- Changing the decision semantics, the status code of a repeated decision, or the execution queue.

## Acceptance criteria

- When the owner calls `GET /api/approval-requests/:id`, the response is the request's view with `source`; another user's request, an unknown id and another tenant's id all answer 404 with identical bodies.
- When `GET /api/approval-requests/count?status=pending&source=chat` is called, `count` equals the number of pending chat-sourced rows the list returns; with no `source` it counts all pending requests of the owner.
- `/api/approval-requests/count` is served as a count and never treated as a request id.
- The two new routes appear in the route matrix and pass the tenant isolation route test.
