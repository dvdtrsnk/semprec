## Behavior specification

AI usage: cost, tokens, periods, breakdowns and limits.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions for job agent-usage-1

#### (a) Decisions adopted

- Model family coverage -> only Claude Sonnet, Claude Haiku, Whisper and diarization are mapped; any other id returns the raw id -> ids change per version, the design names only these families and unknown ids stay raw.
- Per-run usage scope -> only the run's own calls (agent_run_id equal to the run), no delegated sub-runs -> delegation is not hosted in production (ADR no-speculative-generality).
- Per-message cost -> sum of gateway calls tagged with the message id via a new per-turn header; ticks use the whole run's cost -> avoids time-window guessing.
- Foreign or unknown Semp message id at reserve -> same attribution_refused and no row -> consistent with the existing agent run and project item handling.
- Account start -> earlier of oldest tenant user and first tenant AI call, falling back to the range start -> the original tenant's created_at is only the migration time.
- Monthly series -> granularity=month lifts the 366-day cap, starts at the later of the account-start month and the month of from, returns empty daily arrays; default stays day -> keeps the existing web client unchanged and bounds the work.
- Unit classification -> by operation (transcription_* are audio), failed calls dropped from rows, estimated flag when any reserved call is in range.
- Heartbeat tick model and missing embedding/mail-triage/inbox-suggestion lines -> no new model env var and no new operations in this chunk; byModel shows only recorded calls.
- Operation labels -> raw key fallback for unknown operations; NULL operation becomes other; guidance and behavioral drift merged into one entry.
- USD/CZK rate -> not a backend concern in this chunk (no endpoint field added); left to the client.
- Exhaustion when both windows are used up -> monthly wins (blocks longer); resetsAt only while exhausted; operator-wide caps never revealed.
- Limits of past months -> not offered; only current caps exist (history in the admin audit log is an admin-plane table).
- Default cap for new accounts -> not changed; stays fail-closed with the missing-limit problem shown.
- Status problem keys -> aiBudgetMissing, aiBudgetExhausted; derived at read time, no table row or nightly job.
- USD/CZK rate: constant in the client or a value from the server? -> Decided by the product owner: a constant in the client. The rate only serves an indicative display, and a new server field would be an unnecessary extension beyond v1.
- A haiku-class model for heartbeat ticks (a separate model setting by trigger)? -> Decided by the product owner: no, v1 uses one model for every trigger. A per-trigger setting is an extra option, to be considered only once real tick consumption is known (not in v1).
- Lines for embeddings, mail triage and inbox suggestions on the usage screen? -> Decided by the product owner: not shown. A line appears generically once a feature calls the AI gateway and records its calls, with no special cases prepared in advance.
- A default AI cap for a new account? -> Decided by the product owner: no; without a cap AI is not used (fail-closed). Cost predictability matters more than first-run convenience; the owner sets the cap when the account is set up.
- Past months showing the limit that applied then? -> Decided by the product owner: no; past months show spend only, without a historical limit. Reading the global admin audit table from a tenant route would break tenant separation for little benefit.
- Oversized issue -> Decided by the product owner: one issue implements one mechanism. The budget-in-status issue #1871 keeps only the read-time derivation of the two problems; the Semp status refresh on the first tenant-cap refusal in the gateway and the refresh at the reset instant are #2023 and #2024.

#### (c) User-visible behavior

Users can see what the AI costs them. Each Semp run and each chat answer shows its cost and tokens per model with readable model names ("Claude Sonnet", "Whisper", "Diarizace") in their language, and the cost of one chat answer is told apart from the next answer in the same conversation. The AI usage screen can show the last 7 days, the whole history or a month, a month-by-month cost series from the day the account started, a breakdown by model (calls, tokens or audio minutes, cost, what it was used for) and by activity with its share of the spend, counting only real calls and marking totals as estimates while calls are in flight. Next to that, the screen and the profile show spend against the daily and monthly limits, and when a limit is used up or missing, Semp's status explains it, including when it resets, and refreshes on its own when the limit is hit and when it resets.
