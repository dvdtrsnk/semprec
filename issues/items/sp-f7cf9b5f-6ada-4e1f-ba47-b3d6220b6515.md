## Context

Model tier rationale: A small change to one route and one store function, but it decides the queue's run time and the job key semantics under concurrency, and must keep the route's non-waiting lock path.

F17, observed on the dev server: `POST /api/accounts/:id/calendars/sync` within `MANUAL_CALENDAR_SYNC_DEBOUNCE_SECONDS` (60 s) of the previous manual request is dropped. `recordManualCalendarSyncRequest` answers `false`, the route enqueues nothing and still answers 202 (`queued: false`). A change made on the server, followed by a second "sync now" 10 s after the first, was not imported within 120 s (the next sweep pass is up to 5 min away).

Decisions:
- A debounced request is coalesced, never dropped. `manual_sync_requested_at` becomes the run time of the latest requested pass. A request with none in the last 60 s records `now()` and queues the pass at once. A request inside the window of a pass that already started records `that time + 60 s` and queues the pass for then. A request while a pass is already deferred (its time is still ahead) keeps that time. The decision is one conditional upsert, so concurrent requests serialize on the state row.
- The deferred pass is queued with the account's job key (`calendar-account-sync:<account>`) and `run_at` the recorded time. Key replacement keeps one waiting job, so a window holds at most one pass from manual requests.
- The response is 202 `{ id, queued: true, runAt }` (ISO time; `now()` for a pass queued at once). The lock-not-available path stays: it queues at once without recording and answers `runAt` `now()`.
- Schema unchanged.

## Scope

### In scope

- Coalescing debounced manual sync requests into one deferred pass, and the response's `runAt`.

### Out of scope

- The sweep's interval and the job's retry policy.
- Showing `runAt` in the web or mobile apps.

## Acceptance criteria

- Two requests 1 s apart give exactly one pass queued at once and one queued at the end of the first request's window (`runAt` = first + 60 s). Both answer `queued: true` with their `runAt`.
- A third request inside that window adds no further pass and answers the same `runAt`.
- A request after the window queues at once again.
- While a writer holds the account row or the state row, the request still answers 202 at once, queues a pass, and records nothing.
- Calendars off (409), unknown, foreign and malformed ids (404) queue nothing, as before.
