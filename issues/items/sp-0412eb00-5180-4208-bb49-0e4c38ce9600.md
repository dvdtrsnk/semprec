## Context

Model tier rationale: A new persistent store shared by every window of the process, a read policy inside `AuthenticatedApi` that every signed-in request passes, connectivity detection with background probes and cross-window change announcements; concurrency and lifetime contracts are new.

Every screen of the mobile apps reads the server each time it opens: it waits on every open and shows nothing without a connection. The epic asks for the offline set (tasks, events, calendars, invitations, projects, areas, people, companies and other collections, the diary, the overview, sleep, the Inbox, the reminders the device schedules) to be kept on the device, read from there when nothing changed, and shown without a connection. Mail, files, recordings, transcripts, search and Semp stay online only.

Every signed-in request of a window goes through `AuthenticatedApi.send` (`mobile/shared/data/.../AuthenticatedApi.kt`), so the policy belongs there and no repository changes. The mail thread lists already live in JSON files written through the `expect` functions of `CacheFiles.kt` (`FileMailThreadListCache`, one directory per account named by `accountKey(session)`, a SHA-1 of the server and the token; every end of the session empties it through the `sessionEnded` hook of `HttpAuthRepository`). The sync socket (`SyncSocket`) raises every topic after each connect and turns frames into topics.

Later issues of this epic queue writes (`[offline-first 03/07]`), show them in the kept answers (`04/07`), keep note pages (`05/07`), warm the set on connect (`06/07`) and show the status (`07/07`).

## Task

Load `kmp-shared`, `testing`, `error-handling`, `adr-conventions`, `apple-swiftui` and `mobile-verify`.

1. `HomeSDK` takes `dataDirectory: String? = null`: a directory the system keeps (not a cache directory). With `null` nothing is kept and every request goes to the server exactly as today. The Apple `SharedScreenModelFactory` passes `<Application Support>/Offline` for `.keychain` (created when missing, excluded from backups) and `nil` for `.memory`; Android passes nothing.
2. `OfflineStore` in `:shared:data` keeps, under `<dataDirectory>/offline/<accountKey(session)>/answers/`, the answers of the offline set as JSON files written with `CacheFiles`: one file per request (named by a 64-bit FNV-1a hash of the request key; the file repeats the key, the account and a version, and a file that does not match reads as nothing and is deleted), plus an index of keys most recently used first. At most 500 answers (least recently used out); an answer body over 1 MiB is not kept and the answer before it stays. Keeping an answer for one account removes the directories of every other account; `clear()` removes everything and runs in the `sessionEnded` hook beside the mail thread lists. One lock per directory for the whole process, as `CacheRootLocks`; the windows of the process share one store per directory.
3. The request key is the method, the path, the query in the order sent and the body. A request is in the offline set when it is a `GET` of `/api/schema`, `/api/databases`, `/api/items/:id`, `/api/items/:id/related`, `/api/items/:id/page`, `/api/calendar/timeline`, `/api/calendar/agenda`, `/api/calendar/reminders`, `/api/badge-counts`, `/api/journal/periods/:type/:period`, `/api/overview`, `/api/sleep/nights`, `/api/inbox/cards`, `/api/inbox/cards/count` or `/api/inbox-types`, or a `POST` of `/api/databases/:id/query` or `/api/databases/:id/facets`. Nothing else is kept.
4. `OfflineLayer` decides how a request of the offline set is answered inside `AuthenticatedApi.send`:
   - A kept answer is *fresh* when this process kept it after the last change signal and less than 5 minutes ago; a fresh answer is returned without a request. Change signals: any successful request that is not a read, the sync socket connecting, and any text frame the sync socket receives. Answers read from disk after a restart are not fresh.
   - Otherwise the request goes out. An answer with a success status is kept and returned. `404` deletes the kept answer and is returned. A request that got no answer, or a `5xx` or `429`, returns the kept answer when there is one, else the failure. Any other answer is returned as it came.
   - The process is *offline* from a request that got no answer until a request gets any answer or the socket connects. While offline, a request with a kept answer returns it at once; at most once every 15 s one such request is sent in the background to check the connection, and an answer to it ends the offline state.
   - Ending the offline state, other than by a write of the window, makes every kept answer stale and tells every window through its `ItemChanges` (which gains a second source, the layer's change flow, besides its own announcements), so the open screens read again.
   - Kept answers are returned with the status, body and `ETag` the server sent. Requests outside the offline set and requests without a session behave exactly as today.
5. `SyncSocket` tells the layer when it connects and when a text frame arrives.
6. Add the ADR `docs/adr/2026-11-23-mobile-keeps-the-answers-of-the-offline-set.md` recording 1–5, the routes and the limits, why there is no database library and no server change feed (healing by reading again, as [[2026-10-16-tenant-scoped-realtime-fan-out]] keeps), and how it extends [[2026-11-22-mobile-keeps-mail-thread-lists-in-a-file-cache]], [[2026-11-16-open-mobile-screens-reload-after-any-write-of-their-window]] and [[2026-11-20-mobile-screens-follow-the-sync-socket]].

## Acceptance criteria

- With a data directory, a read of the offline set that the server answered is answered again from the device, without a request, until a change signal or 5 minutes pass.
- After a successful write, a socket connect or a socket frame, the next read of a kept answer goes to the server.
- A read that gets no answer, a `5xx` or a `429` returns the kept answer; with nothing kept it returns the failure; a `404` removes the kept answer.
- While offline, a kept read returns at once and the connection is checked in the background at most once every 15 s; when the server answers, every window is told and the next reads go to the server.
- A read outside the offline set is never kept; without a data directory nothing is written to disk and every request goes out.
- Answers are kept per account, removed for other accounts, removed entirely when the session ends, limited to 500 and to 1 MiB each, and found again after the store is created anew over the same directory.
