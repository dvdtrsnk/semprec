**Blocked by:** #1615
**Model tier:** medium

## Context

Model tier rationale: One idempotent write operation across the established catalog seams, relying on the existing create-if-missing document function that already handles concurrent first writes.

#1394 records the page operation family. Reading a page never creates it. An item has a document only after something writes content, and `getOrCreateDoc(client, itemId, kind)` (`backend/packages/data/src/docs/docsStore.ts`) is internal: it requires a live item, inserts the `docs` row with an empty snapshot, and converges on one row when two callers race (`ON CONFLICT DO NOTHING`, unique per tenant and item). Clients need an explicit call before they open the editor over `WS /api/sync`, which needs a `docId` and does not create documents itself.

This issue adds `page.ensure`: it returns the document id of an item's page, creating it if it does not exist. Calling it again returns the same id. Journal periods have their own ensure-and-create flow in the journal issues; this operation is for any other item (projects, events, people, areas). The area description is moved into an area page by #1619, which uses this operation.

Decision: `page.ensure` always uses document kind `page`. An item that already has a document of another kind (for example a drawing) returns a conflict error, as `getOrCreateDoc` already does.

Shared-file ordering: this issue also waits for #1615 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`. Follow the capability and approval classification and the path recorded by the ADR of #1394.

1. Add `page.ensure` to `GENERIC_OPERATION_NAMES` with input `{ itemId }`, output `{ docId }`; add the schema, port method, binding and metadata (non-destructive write using the item-write capability; agent-specific classification is refined later by #1844).
2. Add `ensurePage` to the application service: in one transaction, resolve the live item (404 for a missing, trashed or foreign-tenant item) and call `getOrCreateDoc(client, itemId, "page")`; return its id. No Yjs content is written.
3. Add the route `PUT /api/items/:id/page` in `semprec-api/src/itemsHandler.ts`, answering 200 with `{ docId }` for both a new and an existing document, plus its `routeMatrix.ts` entry and the tenant isolation route case.
4. If the `page.get` operation of #1615 already exists when you implement this, nothing changes there; after the call, its `docId` is the same value.
5. Tests: the first call creates one `docs` row and returns its id; a second call returns the same id and creates no new row; two concurrent first calls end with exactly one row and the same id in both responses; a trashed or foreign-tenant item returns 404; no session returns 401; an item that already has a document of another kind returns a conflict.

## Acceptance criteria

- When `PUT /api/items/:id/page` is called for an item without a document, then a document row exists afterwards and the response has its `docId`.
- When it is called again, or twice concurrently for the first time, then there is exactly one document row and every response returns the same `docId`.
- When the item is trashed, missing or in another tenant, then the response is 404; without a session, 401.
- When the item already has a document of another kind, then the response is a conflict and nothing is created.
