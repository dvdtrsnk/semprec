## Context

Model tier rationale: One additive descriptor shape carried through the module registry, three manifests, two read endpoints and a new keyset ordering, all covered by existing registry, manifest and handler test fixtures.

The app shows a fixed overview of collections (Projects, Events, People, Companies, Files, Health records, Books, Movies and series, and later Recipes), each with an icon, a color and a click-through, and a separate collection switcher in its own fixed order (Projects, Tasks, Events, Journal, People, Companies, Files, Health records, and later Recipes). Books and Movies appear only in the overview, Tasks and Journal only in the switcher. Today the backend cannot describe any of this:

- `GET /api/databases` (`backend/services/semprec-api/src/databasesHandler.ts`, envelope in `backend/services/semprec-api/src/adapter/databaseEnvelope.ts`) returns `id`, `name`, `key`, `ownerModuleId`, `system`, `schemaLocked`, `archivedAt` and so on, with no icon, color, order or visibility. `database.list` pages in memory ordered by id (`paginate` in `backend/packages/application/src/genericApplicationService.ts`), and the list includes internal databases (inbox, inboxItemTypes, processingProposals, mailboxes, folders, mcpServers, System settings).
- `ModuleDatabaseDescriptor` (`backend/packages/module-registry/src/manifest.ts`, projected by `getDatabases` in `registry.ts`) is `{ key, name, defaultViewType? }`.
- `GET /api/schema` (`generateSchemaProjection` in `backend/packages/data/src/manifest/schemaProjection.ts`) projects `databaseId`, `key`, `name` and properties only.

This issue declares the metadata per system database in the module manifests and exposes it, additively, on both read endpoints. It builds nothing for user-created databases: their icon and color come from #1528, and the search placeholder from #1525. Later issues add descriptors for their own modules on top of this shape, for example Recipes (#1707), the sleep module (#1776), related-collection ordering (#1517) and sensitive-database marking (#1808).

Decision: `clientVisible` is derived (`overviewOrder != null` or `switcherOrder != null`, or a user-created database), with an explicit optional `clientVisible: true` override on the descriptor for the three system databases that belong to neither list but are still shown to clients (Areas, Emails, Transcripts). All other system databases, including every internal one, are not client-visible.

Decision: `GET /api/databases` keeps its `{ databases, nextCursor }` shape. Because the new order cannot be expressed by the id-keyed cursor of `database.list`, the handler reads every page of `database.list` (limit 200), sorts, and pages the sorted list itself with an opaque keyset cursor that encodes the last returned row's sort tuple.

Shared-file ordering: this issue also waits for #1397 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Scope

### In scope

- Descriptor fields, their values for the existing system modules, the metadata resolver, the additive envelope and schema-projection fields, and the ordering of `GET /api/databases`.

### Out of scope

- Storing icon and color on user-created databases, and defaulting them on read: #1528.
- The search placeholder sentence per collection: #1525.
- The Recipes descriptor (overview and switcher position 9): #1707.
- Where user-created collections appear in the app overview and how they are managed: decided by the product owner, and it needs no backend change. The client shows them in a separate overview section after the system collections, ordered by name, and manages them like the system collections (rename, delete to the trash) with the existing operations; the server only marks them `clientVisible`, and the order is the client's.
- Remembering a user's view and sort per collection on the server: not planned yet (decided: not in v1); the client remembers it on the device, and server sync is added when it is needed.
- Ordering of `GET /api/schema` databases (unchanged).

## Acceptance criteria

- `GET /api/databases` lists the databases in the order Projects, Tasks, Events, Journal, People, Companies, Files, Health records (switcher order), then Books and Movies, then everything else by name.
- Envelopes of Projects, Events, People, Companies, Files, Health records, Books and Movies carry `overviewOrder` 1 to 8 as in the table, an `icon` and a `color`; Tasks and Journal have `overviewOrder: null`; Books and Movies have `switcherOrder: null` and `clientVisible: true`.
- Emails, Areas and Transcripts have `clientVisible: true` with both orders `null`; Mailboxes, Folders and the inbox, processing-proposal and MCP databases have `clientVisible: false`; a user-created database has `clientVisible: true`.
- `GET /api/schema` carries the same five fields per database.
- Walking `GET /api/databases?limit=2` with the returned `nextCursor` visits every database exactly once, and a cursor whose row was archived in between still continues without error or repeats.
- A manifest that omits all new fields still loads, and one with `color: "red"` or `overviewOrder: 0` is rejected at load.
