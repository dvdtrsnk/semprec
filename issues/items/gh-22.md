## Context

This is task 2 of 22 in a sequential queue for implementing the "Semprec" backend. The backend is the data and mechanism foundation for a Notion/AppFlowy/Anytype-like editor — a generic database layer, on top of which sit views (Table/Board/Calendar/...), page content, and an agent layer whose behavior rules are mechanically enforced, not merely suggested.

The previous task (01, "Data layer — Postgres schema engine + value owners") already delivered: a generic schema engine for databases/properties, typed properties stored on rows (`items` + JSONB `properties`), an `item_relations` table for relationships between rows, and a value-ownership mechanism for properties (`owner: 'user' | 'system'`) enforced at the generic write choke-point — note that `'ai_agent'` is not a property-owner value; it exists only in the `created_by` vocabulary (views, `doc_updates`).

This task builds the views layer on top of that: column order, filters, sorting, and property visibility are not a property of the database — they are a property of the individual view. A single database can have several views with fully independent configuration at the same time. This task also introduces curated (manually-assembled) views alongside dynamically filtered ones, the distinction between linked and inline databases, and a `created_by` mechanism on views that determines what an AI agent may do with them — analogous to the value-ownership mechanism from task 01, but as a separate carrier, because views are whole rows of their own table, not property values.

The following task (03, "Blocks and canvas on Yjs CRDT") covers page content/the editor and is NOT part of this task.

## Task

Implement the views layer on top of the existing data layer from task 01:

1. **`views` table** with the following DDL:
```sql
CREATE TABLE views (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  database_id uuid REFERENCES databases(id) ON DELETE CASCADE,  -- NULL exactly for curated views (see point 5)
  type text NOT NULL,               -- 'table' | 'board' | 'calendar' | 'list' | a key registered by a module
  name text NOT NULL,
  config jsonb NOT NULL DEFAULT '{}',  -- { propertyOrder, visibility, widths, filter, sort, groupBy, membership }
  is_default boolean NOT NULL DEFAULT false,
  owner_module_id text,              -- populated only if 'type' is a custom view type registered by a module
  created_by text NOT NULL DEFAULT 'user',  -- 'user' | 'ai_agent' | 'system'
  CONSTRAINT views_curated_no_db CHECK (
    (database_id IS NULL) = (config->>'membership' IS NOT DISTINCT FROM 'manual')
  )  -- database_id is NULL if and only if the view is curated (config.membership = 'manual')
);

CREATE UNIQUE INDEX views_one_default_per_db
  ON views (database_id) WHERE is_default;   -- at most one default view per database
```
`created_by` uses the same value vocabulary (`'user' | 'ai_agent' | 'system'`) as `doc_updates.created_by` introduced elsewhere in the specification — do not introduce a new enum, converge on the existing one.

2. **A typed filter tree compiled to SQL.** `views.config.filter` is NOT a freely-written string expression. It is a tree of nodes drawn from a closed, small set of typed condition nodes plus logical connectives. Implement:
   - The tree's data model (a JSON representation of nodes with a discriminated condition type).
   - A compiler that deterministically maps the tree onto a parameterized SQL/JSONB predicate (e.g. `properties->>'status' = $1`) — always via bind parameters, NEVER via string concatenation. The closed condition enum guarantees a filter can never be a SQL injection vector.
   - The compiler must be integrated into the generic query service from task 01 (push-down filtering directly in the DB query, not in-memory filtering over already-fetched rows).
   - **The V1 closed condition set** (extension = always a code migration of the enum, never a data change): `equals`, `not_equals`, `contains`, `not_contains`, `starts_with`, `ends_with`, `is_empty`, `is_not_empty`, `before`, `after`, `on_or_before`, `on_or_after` (date), `date_range`, `in` (membership in `select`/`multi_select` values); connectives `and`, `or`, `not`.
   - Do not implement anything beyond this list (no regex, no full-text scoring) — add it only once a concrete future view type demonstrates the need.

3. **Sorting, ordering, and property visibility** as part of the `config` jsonb: `propertyOrder`, `visibility`, `widths`, `sort`, `groupBy`. Implement read/write through the views API (see point 6) and their projection into the generic query service (result ordering, which columns/properties are returned and in what order).

4. **An extensible custom-view-type mechanism.** `view.type` can be built-in (`table`/`board`/`calendar`/`list`) or a custom type registered through `ModuleRegistry` (the same registry that already registers modules such as Emails/Personal finance today). Registering a custom view type carries three parts:
   - a data shape (a view type has properties/config like any other),
   - an optional server-side service (validation, special query logic),
   - a client-side view component (a renderer only; querying the data underneath it goes through the same generic `items` query as Table/Board/Calendar).
   Implement the registration/extension mechanism itself (the interface by which a module registers this triple, and how `owner_module_id` + `type` link to that registration) — NOT the concrete future view types themselves (see Out of scope).

5. **Curated views (manual item selection).** Alongside dynamic (filtered) views, implement curated views — the equivalent of Anytype Collections vs. Sets: membership is not derived from a filter but from explicit add/remove of items, starts empty, and can mix items from multiple databases/types at once.
```sql
CREATE TABLE view_items (             -- only for views with config.membership = 'manual'
  view_id uuid NOT NULL REFERENCES views(id) ON DELETE CASCADE,
  item_id uuid NOT NULL REFERENCES items(id) ON DELETE CASCADE,
  position integer NOT NULL,
  PRIMARY KEY (view_id, item_id)
);
```
   A curated view **has no `database_id` of its own** — `views.database_id` is nullable and is NULL exactly for curated views (enforced by the `views_curated_no_db` CHECK in the DDL above); it is read exclusively through `view_items`. A filtered view always has `database_id` set and is read through `database_id` + `config.filter`. Adding/removing an item in `view_items` goes through the same generic write choke-point as any other write (from task 01).

6. **Views API**: CRUD endpoints (create/list/get/patch/delete) over `views` and over `view_items` membership (add/remove item, reorder), built on the generic choke-point from task 01 — no special path for views outside this choke-point.

7. **Linked vs. inline databases** — implement both creation paths, clearly distinguished:
   - **Linked**: a new row in `views` pointing at an existing `database_id`. No new data, no new properties, just a different filter/sort/layout.
   - **Inline**: a new row in `databases` with `parent_item_id` = the page it was created on. Its own properties, its own rows, its own IDs — an independent object, not a copy. Always `system: false` (unlike system databases) — fully controllable through the UI/API, and later through AI as well.

8. **Enforcement of `created_by` at the choke-point** (mechanically, not just as guidance in the agent's prompt):
   - **Creation**: an agent may create both a filtered view and a curated `view_items` collection through the same choke-point as a user — no approval required (a view carries no data of its own, so the worst-case impact is clutter, not loss). The row is created with `created_by = 'ai_agent'`.
   - **Modification/deletion**: an agent may PATCH/DELETE a view, or write to `view_items`, only for views with `created_by = 'ai_agent'`. An attempt to write to a view with `created_by = 'user'` or `'system'` returns HTTP 403 with error code `owner_violation` — the same code used for writes to a property with `owner: 'system'` (task 01) — a single deterministic signal across the system. No exception for anyone.
   - **`is_default` may never be set by an agent** — not even on its own view. It always requires a user/system actor.
   - **Adoption**: if a user writes (PATCHes) a view with `created_by = 'ai_agent'`, the choke-point flips `created_by` to `'user'` within the same transaction. From that moment the agent may no longer write to it. The reverse direction (adoption from `'user'`/`'system'` back to `'ai_agent'`) never happens. For `'system'` views, a user write never changes `created_by` at all (a module may restore it via migration, and it is untouchable by the agent regardless).
   - This distinction does not go through the approval queue from layer 4 — that was a considered and explicitly rejected alternative (see Reference below). Do not implement any path where an agent's edit to someone else's view waits on per-instance user approval.

9. **API contract for UI separation of agent views**: the endpoint returning views must let the client group/distinguish views by `created_by` (agent views as a separate, labeled group, not mixed in with user views) — it is enough that `created_by` is part of the API response; the actual grouping in the UI is out of scope for this backend task, but the field must be reliably present and correctly kept up to date (see adoption above).

## Scope

### In scope
- The `views` table, including DDL, the unique index on `is_default` per database, the nullable `database_id` with the `views_curated_no_db` CHECK (NULL exactly for curated views), and the `created_by` column.
- The `view_items` table for curated (manual) views.
- The typed filter tree (data model + validation of the closed node set) and its compiler to a parameterized SQL/JSONB predicate, integrated into the generic query service from task 01.
- The V1 set of filter conditions exactly as enumerated in the Task section (point 2).
- Support for `sort`, `groupBy`, `propertyOrder`, `visibility`, `widths` in the `config` jsonb and their projection into the query service.
- CRUD API for `views` and for `view_items` membership (add/remove/reorder), built exclusively on the generic write choke-point from task 01.
- The custom-view-type registration mechanism via `ModuleRegistry` (the three-part triple: data shape / optional server service / client view component) — only the extension point itself, not concrete implementations of future types.
- The distinction and implementation of linked vs. inline database/view creation.
- Enforcement of `created_by` at the choke-point: creation without approval for the agent, patch/delete only on the agent's own views (otherwise 403 `owner_violation`), `is_default` never settable by an agent, `ai_agent → user` adoption on a user write.
- The `created_by` field in the views API response so the UI can use it for grouping.

### Out of scope
- Concrete custom view types — `temporal-switcher` (Journal, year/quarter/month switcher), `mailbox-client` (Emails), `denik-inbox` (Journal Inbox) — these are future implementations of the extension point from point 4, addressed in separate tasks for the Emails and Journal modules.
- Page content, blocks, the Yjs CRDT editor (task 03).
- Any approval queue / per-instance approval for an agent's intervention in someone else's view — this was explicitly considered and rejected (see Reference); do not implement a substitute or a hook into the queue for this case.
- Typed properties on rows, `item_relations`, the property value-ownership mechanism (`owner` on a property) — done in task 01, only reused/referenced here.
- Content versioning (the `doc_updates` table and its `created_by`) — only the same value vocabulary is reused here; the table itself is not the subject of this task.
- `project_mcp_grants` and anything around MCP grants (mentioned only as an analogous category of decisions reserved for humans).

## Dependencies


From task 01, this task specifically uses:
- **The `databases` table** — `views.database_id` references it (`ON DELETE CASCADE`); an inline database creates a new row here with `parent_item_id`.
- **The `items` table** — `view_items.item_id` references it; the typed properties on `items.properties` (JSONB) are what the filter predicates compile against (e.g. `properties->>'status' = $1`).
- **The generic query service / choke-point from task 01** — every write to `views`/`view_items` MUST go through the same generic write choke-point that task 01 introduced for writes to properties; filter predicates are pushed down into the same generic query service task 01 uses for reading `items`.
- **The `created_by` vocabulary** (`'user' | 'ai_agent' | 'system'`) — the same enum task 01 (and the subsequent content layer) uses for `doc_updates.created_by`; do not introduce a new enum.
- **The `owner_violation` error code** — the same HTTP 403 code task 01 returns for writes to a property with `owner: 'system'`; this task reuses it for writes to someone else's view, it does not introduce a new code.
- **The two-layer enforcement model** (mechanical enforcement at the choke-point vs. mere textual guidance in the agent's prompt) established philosophically in task 01 — this task applies it to views the same way.

- Curated views (`view_items`) vs. filtered views — the distinction named after Anytype Sets (dynamic filter) vs. Collections (manual selection, empty at start, can mix items across databases).

- The decision "Agents create views freely, may not modify others' — and a user's edit to an agent view adopts it": creation without approval, modification/deletion only of the agent's own (`created_by = 'ai_agent'`), otherwise 403 `owner_violation`, `is_default` never by an agent, one-way `ai_agent → user` adoption on a user write, the UI separates agent views into their own group.
- The rejected alternative "An agent's edit to a user's view via the approval queue" — rejected because the queue is reserved for risky instances of granted tools (deleting data, payments) while a view carries no data of its own (the harm is inconvenience, not loss); and because the need to edit specifically someone else's view does not actually exist — the agent builds its own view alongside, and adoption gives the user a cheap way to take over what worked well (the same pattern as the binary rule chosen for `email.send` elsewhere in the specification, instead of a queue).
