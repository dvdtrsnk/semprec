## Context

#579 added `.github/scripts/review-followups/harvest.mjs`, the review follow-ups harvest (epic #565, Part 1). This issue schedules it as the GitHub Action `harvest-review-followups`, and creates the five labels the pipeline uses.

The harvest script reads, through `fetch`, the environment the Actions runner sets:
- `GITHUB_API_URL`, `GITHUB_GRAPHQL_URL`, `GITHUB_REPOSITORY`;
- `GITHUB_TOKEN`, passed by the workflow;
- `HARVEST_MIN_PR`: required positive integer;
- `DRY_RUN`: required, exactly `true` or `false`;
- `GITHUB_STEP_SUMMARY`: optional; the script appends its report there.

It exits 0 when it wrote or deliberately wrote nothing (backpressure), and non-zero on any error. The GitHub calls it makes:

| Kind | Calls |
|---|---|
| Reads | issues by label and their comments; closed pull requests into `develop`; review threads through GraphQL; the `develop` git tree; pull-request commits, commit files, commits by path, and pull requests of a commit |
| Writes | creating an issue with labels, closing it, adding the `followups:harvested` label to merged pull requests (through the issues API) |

Behavior decided in the epic that this workflow carries:

- **Cadence.** Daily on a cron slot off the hour, plus manual dispatch. With backpressure a no-op run costs nothing, and the throughput is bounded by triage and approval, not by the calendar.
- **Dry-run default.** A manual dispatch defaults to `dry_run: true`, like `.github/workflows/close-completed-epics.yml`. A scheduled run always writes.
- **`HARVEST_MIN_PR = 266`.** A constant in this workflow, with its reason next to it: #265 audited every pull request up to #264 and found their memory tables stale. It is a fixed floor, never a watermark.
- **First real run after #494.** The first real harvest happens only after epic #494 (choke-point split) is closed. Merging this workflow is what starts it, so it merges then. Many choke-point findings will verify as already-fixed by that point.

**Protected path, maintainer-implemented.** `.github/workflows/**` is in `.relay/config.yml`'s `protected-paths`, so this issue is implemented by the maintainer, never dispatched to Relay, and must not be labelled `agent:ready`. Creating repository labels is also a maintainer action.

1. Add `.github/workflows/harvest-review-followups.yml`, modelled on `close-completed-epics.yml`:
   - A header comment explaining:
     - what the workflow does;
     - why it is a GitHub Action rather than a Relay workflow (Relay triggers only on labels of open issues or pull requests, and only while the project is enabled);
     - why it runs daily (backpressure makes a no-op run free);
     - the `dry_run` default.
   - `on:` a daily `schedule` at a minute off the hour (not `:00`, not 04:15, which `close-completed-epics` uses), and `workflow_dispatch` with the input `dry_run` (boolean, default `true`).
   - `permissions:` `contents: read`, `issues: write`, `pull-requests: read`, and nothing else, each with a comment saying which calls need it.
   - `concurrency:` group `harvest-review-followups`, `cancel-in-progress: false`.
   - One job on `ubuntu-latest` with `timeout-minutes: 15`:
     - a sparse `actions/checkout@v4` of `.github/scripts`;
     - `actions/setup-node@v4` with `node-version: 22`;
     - a step running `node .github/scripts/review-followups/harvest.mjs` with `env:`
       - `GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}`;
       - `DRY_RUN: ${{ github.event_name == 'workflow_dispatch' && inputs.dry_run || 'false' }}`, the expression `close-completed-epics.yml` uses;
