**Model tier:** medium

## Context

Model tier rationale: Reuses one existing function across two routes and adds one grouped lookup, with the main risk being that a second near-duplicate calendar read path appears.

The Journal day shows the day's events: time of start, a title, and a meta line (place, whether the recording is transcribed, or the project). Today Events carry only a name, a type and a date with optional time; `GET /api/calendar/timeline` does not exist yet, and the generic item envelope carries no relation values, so a client cannot assemble this from existing reads without several round trips.

#1717 serves a calendar timeline across Events and Tasks, with day bounds in the tenant zone, ordering, trash exclusion and per-item project and place. #1537 serves the Journal day read. Programme decision: there is one function that reads the events of a day; the Journal day calls it with `from = to = day` and no second implementation or route is added.

Decision: the Journal day is an overview of the day and stays consistent with the calendar, so it shows all-day events and birthdays as a compact row at the top, followed by the timed events. This issue lists the items of kind `event` from the timeline, all-day events included (`allDay` true, first in the timeline's own order); the client renders the all-day ones in the top row. Birthdays are added to the day response by #2015. Public holidays and tasks with a time are not included, and the count in the heading is the length of `events`.

## Task

Load `testing` and `canonical-keys`.

1. In the day response of #1537 add `events`, filled by calling the timeline function from #1717 for the day, keeping only kind `event`, all-day events included, in the timeline's order. Each element carries the timeline fields: `id`, `title`, `type`, `date`, `endDate`, `timeFrom`, `timeTo`, `allDay`, `place`, `project { id, name, color } | null`, `calendarId`, plus `transcript { id, status } | null`.
2. Add `transcript` to the timeline item (additively) in the timeline module: for the events on the page, read the Events-to-Transcripts relation and the transcripts' `status` in one grouped query, without per-event queries; `null` when the event has no transcript.
3. Keep ordering, tenant-zone day bounds and trash exclusion exactly as the timeline does; do not reimplement them.
4. Tenant scope and authentication are those of the Journal read.
5. Tests with a fixture of an all-day event "Conference" and four timed events on 2026-10-16 (Standup 09:00, meeting 10:00-11:30 with place and a `done` transcript and a project, lunch 12:00, a focus block 15:00 with a project): the order is Conference (`allDay` true), 09:00, 10:00, 12:00, 15:00; the meeting has its project name, place, `timeTo` and `transcript.status`; Standup has `project: null`; a birthday and a task with a time are not in `events`; the number of queries does not grow with the number of events.

## Scope

### In scope

- The day's events in the Journal day response, built from the shared timeline function, and the additive transcript state.

### Out of scope

- Recurring, overnight and multi-day cases and the calendar id guarantee; #1881.
- Birthdays in the Journal day: #2015 adds them. Public holidays (not shown there).
- The client's choice of meta line: place and transcript state first, then project, otherwise a generic label.
- A separate Journal events route or function.

## Acceptance criteria

- When the day 2026-10-16 of the fixture is read, then `events` has five entries in the order Conference (all-day, `allDay` true), 09:00, 10:00, 12:00, 15:00.
- When the meeting is read, then it carries `project.name`, `place`, `timeTo` and `transcript.status` `done`; Standup has `project` null.
- When the day has a birthday or a timed task, then neither appears in `events`.
- When many events exist, then the transcript state is read with one grouped query.
