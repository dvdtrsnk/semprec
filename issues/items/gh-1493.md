## Context

Model tier rationale: A new tenant-classified table with row-level security plus a change to the thread-merge write, where the chain-rewrite must keep every old id resolvable in one step, but it follows the established table conventions and has a clear invariant.

When a message bridges two previously separate threads, `resolveThreadId` (`backend/packages/data/src/mail/threading.ts`) merges the others into the first found thread with `reassignThread` (`mail/mailMessageMetaStore.ts`). `reassignThread` moves the messages' `thread_id` and deletes the old `mail_threads` row. After that the old thread id leads nowhere. Other screens and the assistant hold thread ids (a link in an approval card, a thread attached to an assistant conversation, a related-items list), so a merge would break them.

Decision: a merged-away thread id stays resolvable through an alias table, and the translation is always one step: when B is merged into C, every alias that already points at B is rewritten to point at C in the same transaction, and an alias never points at itself. Thread routes, mail actions and assistant thread references translate ids through this table: the thread detail (#1632), mark read (#1865), the thread reference kind (#1933) and the thread item mirror (#1573) build on it.

## Task

Load `db-migrations`, `state-writes` and `testing`.

1. Add the migration `backend/packages/data/src/db/migrations/NNNN_mail_thread_aliases.sql` (next free ordinal at commit time) creating `mail_thread_aliases (tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id), from_thread_id uuid NOT NULL, to_thread_id uuid NOT NULL, created_at timestamptz NOT NULL DEFAULT now(), PRIMARY KEY (tenant_id, from_thread_id), CHECK (from_thread_id <> to_thread_id))`, a composite foreign key `(tenant_id, to_thread_id)` to `mail_threads (tenant_id, id)` with `ON DELETE CASCADE`, an index on `(tenant_id, to_thread_id)`, `COMMENT ON TABLE ... IS 'semprec:tenancy=tenant'`, row-level security with both policies, and the grants from `docs/operations/database-roles.md`.
2. In `reassignThread`, when `fromThreadId` equals `toThreadId` do nothing and write no alias. Otherwise, in the same transaction and before deleting the old `mail_threads` row: insert the alias `(fromThreadId -> toThreadId)` (upsert on the primary key), then `UPDATE mail_thread_aliases SET to_thread_id = toThreadId WHERE to_thread_id = fromThreadId`.
3. Add `resolveMergedThreadId(client, threadId)` in `mail/mailMessageMetaStore.ts`, returning the alias target in a single query (or the input id when no alias exists) and `null` only when neither an alias nor a `mail_threads` row exists. Export it from the data package barrel.
4. Add tests: A merged into B then B into C makes both A and B resolve to C with one query each; merging a thread with itself writes no alias; another tenant's aliases are invisible; the tenant export and purge handle the new table (extend their table-list fixtures if they have one).

## Scope

### In scope

- The alias table, its maintenance in `reassignThread`, and the one-step resolver.

### Out of scope

- Using the resolver in routes and actions: #1632, #1865, #1933.
- Realtime invalidation of merged threads: #1816.
- Backfilling aliases for merges that happened before this change; those old ids are already lost.

## Acceptance criteria

- When thread A is merged into B and then B into C, then resolving A and resolving B each returns C with one query.
- When a thread is merged with itself, then no alias row is written.
- When a thread id is unknown and has no alias, then the resolver returns null.
- A second tenant cannot read or resolve the first tenant's aliases.
