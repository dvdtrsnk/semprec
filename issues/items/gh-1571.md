## Context

Model tier rationale: A queued, chunked job plus one index, each following an existing pattern, but it writes relation edges across a tenant's mail and must be idempotent.

When a person gains an email address, the existing mail from that address is not linked to them. `reindexPersonEmails` (`backend/packages/data/src/mail/personEmailIndexStore.ts`) only updates `person_email_index`, which maps an address to a person. Links from emails to people (`Emails.senderPeople`, `Emails.recipientsPeople`) are written only when an email is ingested (`mail/personLinkingActions.ts`), so earlier emails of that address stay unlinked. There is also no index over `mail_message_meta.envelope` (migration `0006_mail_sync.sql`), so finding emails by address would scan the table.

This builds on #1457, which allows one person to be the sender of many emails.

Decision (product owner): removing an address from a person does not remove the edges already created; this issue only adds links. Removing edges is deferred.

## Task

Load `state-writes`, `db-migrations` and `testing`.

1. Add the migration `backend/packages/data/src/db/migrations/NNNN_mail_message_meta_envelope_gin.sql` (next free ordinal at commit time) creating a GIN index on `mail_message_meta.envelope` with `jsonb_path_ops`. The migration must not change tenant rows.
2. Add a core task `mailLinkPersonEmails` to `CORE_TASK_NAMES` and a handler in `worker.ts` taking `{ personId, addresses }`.
3. In the transaction where `reindexPersonEmails` claims a new address for a person (called from `createPersonEmailReindexAction`), enqueue that task with `jobKey: "mail-link-person-emails:" + personId` and the newly claimed addresses (the addresses claimed in this call that were not in the index before). Addresses that were not newly claimed enqueue nothing.
4. The handler pages through emails whose `envelope` contains the address in `from`, `to` or `cc` (index containment queries, keyset by item id, one transaction per page) and writes the missing `senderPeople` and `recipientsPeople` edges with `createRelationWithClient` and `EMAILS_RELATION_CONTEXT`. Edges that exist are skipped. Skip deleted items. Envelope addresses are stored as received (not lowercased), so the containment query tries the normalized address and the form the person's `emails` property carries, and each candidate is confirmed in code with `normalizeEmailAddress` before an edge is written.
5. Add tests: adding an address to a person links older emails as sender and as recipient; re-running writes nothing new; an address owned by another person is not linked; removing an address removes no edge.

## Scope

### In scope

- The envelope index, the keyed job, and idempotent edge writing for newly claimed addresses.

### Out of scope

- Allowing many emails per sender: #1457.
- Linking mail sent from Semprec: #1480.
- Removing edges when an address is removed from a person; the product owner decided the edges are kept and removal is deferred.

## Acceptance criteria

- When a person gains an address that appears as sender of older emails, then those emails get a `senderPeople` edge to the person.
- When the address appears in `to` or `cc` of older emails, then they get a `recipientsPeople` edge.
- When the same address is saved again, then no duplicate edge appears and the job enqueues nothing.
- When an address is already owned by a different person, then no edge to the second person is created.
