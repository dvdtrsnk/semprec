## Context

Model tier rationale: A queued, chunked job plus one index, each following an existing pattern, but it writes relation edges across a tenant's mail and must be idempotent.

When a person gains an email address, the existing mail from that address is not linked to them. `reindexPersonEmails` (`backend/packages/data/src/mail/personEmailIndexStore.ts`) only updates `person_email_index`, which maps an address to a person. Links from emails to people (`Emails.senderPeople`, `Emails.recipientsPeople`) are written only when an email is ingested (`mail/personLinkingActions.ts`), so earlier emails of that address stay unlinked. There is also no index over `mail_message_meta.envelope` (migration `0006_mail_sync.sql`), so finding emails by address would scan the table.

This builds on #1457, which allows one person to be the sender of many emails.

Decision (product owner): removing an address from a person does not remove the edges already created; this issue only adds links. Removing edges is deferred.

Execution contract: [[2026-11-03-person-mail-link-jobs-reconcile-current-index-ownership]]. The keyed object payload is a validated wake-up hint; pending replacement must not lose earlier currently owned addresses. No change to the tenant queue envelope, replacement mode or existing conflict return shape.

Envelope addresses are stored as received (not lowercased), so the containment query tries the normalized address and the form the person's `emails` property carries, and each candidate is confirmed in code with `normalizeEmailAddress` before an edge is written.

## Scope

### In scope

### Out of scope

## Acceptance criteria

- When a person gains an address that appears as sender of older emails, then processing while the address is currently owned links previously sender-unlinked emails with a senderPeople edge. An already recorded sender takes precedence, including after reassignment: preserve it and add no second sender. Two committed additions before keyed execution must both be reconciled; a new claim during a held pass has a later pass covering earlier mail ids.
- When the address appears in `to` or `cc` of older emails, then processing current owned addresses creates their `recipientsPeople` edges; a removed/reassigned address is not authority for new links to the old owner. Existing edges survive later removal.
- When the same address is saved again, then no duplicate edge appears and the job enqueues nothing.
- When an address is already owned by a different person, then no edge to the second person is created. For a later valid reassignment, preserve any old recorded sender, allow current-owner linking on an unlinked message and retain many-recipient behavior. Prove idempotent replay and one held actual job/shared-linker overlap with backend blocking and owned settlement; unsupported transaction/isolation admission fails before protected writes.
