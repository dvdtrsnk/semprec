## Context

Model tier rationale: The storage shape of the rule follows an architecture decision written by a blocking issue, so the exact seams are not fully known up front, and the rule is persisted data on every Event that all later recurrence work reads; an ambiguous seam is resolved upward.

Events cannot repeat today: the Events database (`backend/packages/data/src/seed/seedTenDatabases.ts`) has no recurrence. Tasks already recur with fixed rules (`backend/packages/data/src/tasks/taskRecurrenceRule.ts`: `weekdays`, `monthDates`, `nthWeekday`) stored in `task_recurrence` (migration `0004_ten_databases.sql`), but that rolling model creates the next Task when one is done, which is not how a calendar series works: a recurring Event is one stored series whose occurrences are computed. #1365 records the recurrence model for Tasks and Events in an ADR, deciding whether the rule is a property of the item or a separate row, and fixing the names `seriesId` and `occurrenceDate`. This issue adds the rule to Events in the way that ADR decides and reads that ADR first.

The rule vocabulary is the existing fixed-rule schema, so one rule means the same for Tasks and Events: a daily series is `weekdays` with all seven days, "weekdays only" is Monday to Friday, weekly is the weekday of the series start `date`, monthly is `monthDates` with the day of the start `date`. The presets that translate the user's choices into a rule are defined for Tasks by #1665 and must be reused, not copied.

Decision: an Event with a rule is a series: its own `date` is the first occurrence and the rule says on which later dates it repeats; there is no end condition in this version (a series repeats until it is deleted).

Decision: only rules that pass the fixed-rule schema are stored; anything else is rejected with 400 `validation_failed` (field `recurrence`), on create and on update, from every write path.

Shared-file ordering: this issue also waits for #1803, #1808 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `canonical-keys`, `state-writes` and `testing`. Read the ADR created by #1365 before starting; when it says the rule is a property of the item, follow steps 1-4 with that property; when it says it is a separate row or table, store the Event's rule in the equivalent structure it describes and keep steps 3-5.

1. Seed: add the rule property to the Events property list in `backend/packages/data/src/seed/seedTenDatabases.ts` with the key, type and owner the ADR decides (user-owned, validated), declared after the People properties of #1795. Add its display name to `backend/packages/data/src/seed/i18n/cs.json` and `en.json` (`property.events.<key>.name`).
2. Cutover: add `backend/packages/data/src/calendar/eventsRecurrenceCutoverMigration.ts` that inserts the same definition into each existing Events database by direct SQL (`schema_locked`; pattern `transcription/transcriptsCatalogCutoverMigration.ts`), idempotent, skipped without an Events database, and register it in `runTenantCutoverMigrations` in `backend/packages/data/src/db/tenantCutoverMigrations.ts`.
3. Rule logic: add `backend/packages/data/src/calendar/eventRecurrenceRule.ts` with `parseEventRecurrenceRule(raw)` (the fixed-rule schema from `tasks/taskRecurrenceRule.ts`) and the pure function `eventRecurrenceOccursOn(rule, seriesStartDate, date)` (true when `date` is on or after the start date and matches the rule; a `monthDates` day that a short month lacks is skipped for that month; `nthWeekday` with `n` -1 is the last such weekday).
4. Validation hook: add `backend/packages/data/src/calendar/eventRecurrenceHook.ts` with create and update hooks for the Events database rejecting an invalid rule (400, field of the rule property), and register them in `backend/packages/data/src/domainWriteHooks.ts`.
5. Tests: a weekdays-only rule (Monday to Friday) from Monday 12 Oct 2026 occurs on 12-16 Oct and 19 Oct, not on 17-18 Oct; monthly on the 31st skips April; `nthWeekday` -1 Friday gives the last Friday; an invalid rule is 400 from the generic API, Semp and MCP; a fresh seed and a cut-over tenant have identical definitions; the cutover is idempotent.

## Scope

### In scope

- The Event recurrence rule: storage as the ADR decides, seed and cutover, the fixed-rule parsing and `occursOn` logic, and write validation.

### Out of scope

- The recurrence ADR itself and the Task presets and routes: #1365, #1665.
- Materializing an occurrence: #1843. Expanding occurrences in the timeline: #1877. Recording matching: #1850.
- An editing route or sheet for the rule and the choice "this occurrence, this and following, whole series": not in v1 (product owner decision); they are added once the design provides them.
- An end date or occurrence count: not in v1 (product owner decision); a series is ended by hand by deleting it.
- A yearly rule: not built in this version.

## Acceptance criteria

- When an Event is saved with a valid fixed rule, then the rule is stored; when the rule is invalid, then the response is 400 `validation_failed`.
- When a rule `weekdays` Monday to Friday starts on Monday 12 Oct 2026, then it occurs on 12-16 Oct and 19 Oct and not on 17 or 18 Oct.
- When a monthly rule is on the 31st, then months without a 31st have no occurrence.
- When the cutover runs for an existing tenant, then Events gains the property; a second run changes nothing.
