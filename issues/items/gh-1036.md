## Context

Model tier rationale: Postgres partition DDL changes lock behavior and must preserve catalog equivalence, RLS and grants.

`items` is `PARTITION BY LIST (database_id)` with one partition per database and no default partition (`backend/packages/data/src/db/migrations/0001_core_schema.sql:66-81`). `createDatabase` creates the partition inside its own transaction by calling `create_items_partition($1::uuid)` (`backend/packages/data/src/chokePoint/databasesStore.ts:110`).

That `SECURITY DEFINER` function (`0048_create_items_partition_function.sql:23-32`) runs `CREATE TABLE public.items_p_<hex> PARTITION OF public.items FOR VALUES IN (<id>)`. This takes an `ACCESS EXCLUSIVE` lock on `items` until the caller commits (`0048…sql:12-14`; `docs/operations/database-roles.md:63-64`; `docs/adr/2026-09-27-runtime-ddl-through-security-definer-functions.md:60-61`). While any user creates a database, or a tenant is provisioned with its couple of dozen system databases, every other tenant's item reads and writes queue behind it. That couples tenants' availability and leaks a timing signal across them.

`ALTER TABLE … ATTACH PARTITION` takes only `SHARE UPDATE EXCLUSIVE` on the parent. That lock conflicts with neither `ACCESS SHARE` (reads) nor `ROW EXCLUSIVE` (writes); it holds `ACCESS EXCLUSIVE` only on the table being attached. A freshly created empty table therefore attaches without a scan.

#1021 already replaced this function's body to refuse a database outside the current tenant. That guard stays exactly as it is. The function's signature, owner, `search_path`, name scheme and grants are unchanged, so the previous release calls it the same way.

## Task

Load `db-migrations` (a function replaced in a forward-only, rollback-safe migration) and `adr-conventions`.

1. **Migration.** Take the next free migration ordinal at commit time. Name it `…_attach_items_partitions.sql`. It runs `CREATE OR REPLACE FUNCTION create_items_partition(database_id uuid) RETURNS void LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, public`. Body:
   - first, #1021's tenant guard, copied verbatim from that PR's migration;
   - `partition_name := 'items_p_' || replace(database_id::text, '-', '')`;
   - `EXECUTE format('CREATE TABLE public.%I (LIKE public.items INCLUDING ALL EXCLUDING INDEXES EXCLUDING COMMENTS)', partition_name)`. The partition gets its indexes and foreign keys from the attach, as with `PARTITION OF`. It must not copy the table comment: that would make the partition look like a classified table.
   - `EXECUTE format('ALTER TABLE public.items ATTACH PARTITION public.%I FOR VALUES IN (%L)', partition_name, database_id)`.

   Then re-state `REVOKE EXECUTE … FROM PUBLIC` and `GRANT EXECUTE … TO semprec_data`. The header comment states:
   - the new lock (`SHARE UPDATE EXCLUSIVE` on `items`, `ACCESS EXCLUSIVE` on the new table only);
   - that concurrent partition creations still serialize, because the lock conflicts with itself;
   - that the change is additive: same signature and grants, and the previous release behaves the same.

   Do not edit `0048` or `0050`. `drop_items_partition` is unchanged.
2. **Docs.** In `docs/operations/database-roles.md`, replace the lock sentence of "DDL the API role needs" (`:63-64`) with the new lock behaviour.
3. **ADR.** Add `docs/adr/<YYYY-MM-DD>-items-partitions-attached-under-share-update-exclusive.md` (`area: [backend]`). It narrows the lock consequence of `[[2026-09-27-runtime-ddl-through-security-definer-functions]]` (`:60-61`) without superseding it. Record:
   - the tenant-coupling reason;
   - the rejected alternative: keeping `PARTITION OF` and pre-creating partitions in bulk;
   - that concurrent creations still serialize.

   Do not edit the old ADR.
4. **Tests.** New integration test `backend/packages/data/src/__tests__/itemsPartitionAttach.test.ts`. Call the function under the same tenant setup #1021's tests use for a successful call.
   - **Locks.**
     - Connection A: open a transaction that runs `createDatabase` (`backend/packages/data/src/chokePoint/databasesStore.ts:62`) and keep it open.
     - Connection B, with `SET lock_timeout = '1s'`, against a database created before A began, must all succeed:
       - `SELECT count(*) FROM items`;
       - an `INSERT INTO items`;
       - an `UPDATE` of an existing item.
     - `pg_locks` for A's backend shows no `AccessExclusiveLock` on `'items'::regclass`.
     - Commit A; inserting into the new database then succeeds.
   - **Catalog equivalence.** Create a reference partition with `CREATE TABLE … PARTITION OF public.items FOR VALUES IN (<random uuid>)` as the test superuser. The function's partition must match it on:
     - columns: name, type, not-null, default expression, identity and generated;
     - constraint definitions, and index definitions with the table name normalised;
     - owner;
     - no ACL, no comment, `relrowsecurity = false`, `relispartition = true`;
     - a bound of `FOR VALUES IN ('<id>')`.
   - **Grants.**
     - `has_function_privilege('semprec_data', 'create_items_partition(uuid)', 'EXECUTE')` is true;
     - it is false for `semprec_side` and `public`;
     - `prosecdef` is still true.

## Scope

### In scope
- Replacing `create_items_partition`'s DDL with create-then-attach, keeping #1021's guard, grants and naming; the lock, catalog and grant tests; the doc sentence and the ADR.

### Out of scope
- `drop_items_partition` and the trash purge.
- The tenant guard itself (#1021).

- Pre-creating partitions or changing the partition key.

## Acceptance criteria

- While one transaction is inside `createDatabase` (partition created, not yet committed), another session's `SELECT`, `INSERT` and `UPDATE` on `items` for an existing database complete within a 1 s `lock_timeout`. The first transaction holds no `AccessExclusiveLock` on `items` (integration, `itemsPartitionAttach.test.ts`).
- After commit, items can be inserted into and read from the new database exactly as before (integration, same file). The existing `chokePoint` and `databasesStore` suites pass unchanged (integration).
- A partition created by the function is catalog-equivalent to one created with `PARTITION OF` on every point listed in Task 4: columns and defaults, constraints, indexes, owner, no ACL, no comment, no RLS flag, bound (integration, same file).
- `EXECUTE` on `create_items_partition(uuid)` is held by `semprec_data` only, and the function is still `SECURITY DEFINER` (integration, same file). `leastPrivilegeRoles.test.ts` still shows `semprec_side` refused (integration).
- A database outside the current tenant is still refused exactly as #1021's tests assert; those tests pass unchanged (integration).
- `docs/operations/database-roles.md` and the new ADR describe the `SHARE UPDATE EXCLUSIVE` behaviour. The old ADR is unchanged (review).
