## Context

Model tier rationale: A new tenant table with row-level security plus a state-dependent rule in the pre-write transform and its cleanup on purge span a migration, the choke point and the purge path, though each follows an existing pattern.

Projects have a deadline in `date`. A long-term project has no deadline: moving a project to the `longTerm` status clears its deadline but remembers it, and moving it back restores the remembered deadline. Today `status` and `date` are independent user properties; nothing clears or restores anything.

The remembered deadline is not a property: a property would appear in the schema, in facets and in search. It lives in a tenant-scoped table `project_kept_dates` keyed by item. Rules, applied in the pre-write transform registered by #1520 (built on #1422):
- resulting status `longTerm` reached from another status: store the current `date` value (the patch's, else the stored one) in `project_kept_dates` and set `date` to null in the same write; if there is no date, store nothing;
- leaving `longTerm` for another status: if the patch carries no `date`, set `date` to the kept value and delete the row; if the patch carries a `date`, use it and delete the row;
- an incoming `date` (other than null) while the resulting status is `longTerm` is refused with a `ValidationError` on `field: 'date'` (HTTP 400, message that long-term projects have no deadline).

Decision: the kept value is stored as the exact JSON value of the `date` property (column type `jsonb`), so date-only and date-time values round-trip unchanged. Trashing a project keeps its row; purging a project deletes it with the other item dependents (`deleteItemDependents` in `backend/packages/data/src/chokePoint/itemTrash.ts`).

## Task

Load `db-migrations`, `state-writes`, `error-handling` and `testing`.

1. Add a migration creating `project_kept_dates (tenant_id, item_id, kept_date jsonb NOT NULL, updated_at)` with the tenant conventions of the neighbouring tables (tenant column default, row-level security policy, tenant-leading primary key `(tenant_id, item_id)`; `item_id` has no foreign key because `items` is partitioned, like `task_recurrence`), as `backend/packages/data/src/db/migrations/NNNN_project_kept_dates.sql` (next free ordinal at commit time). Expand-only.
2. Add a small store (`backend/packages/data/src/projects/projectKeptDateStore.ts`: get, upsert, delete by item id) and extend the Projects transform in `projectWriteTransform.ts` with the three rules above, in the same transaction as the item write.
3. Delete the row in `deleteItemDependents` (`itemTrash.ts`).
4. Tests: `inProgress` with date 30 Nov to `longTerm` gives `date: null` and one kept row; back to `inProgress` restores 30 Nov and removes the row; `PATCH date` on a long-term project answers 400 `field: 'date'`; `{ status: 'longTerm', date: '2026-11-30' }` in one patch answers 400; leaving `longTerm` with an explicit new date uses the new date; the kept value does not appear in `GET /api/schema`, item reads or search; purging a trashed project removes the row; another tenant cannot read it.

## Scope

### In scope

- The kept-date table, the clear-and-restore rules, the 400 on a date for long-term projects, and the purge cleanup.

### Out of scope

- Unpinning finished projects: #1520.
- The completion date: #1586.
- Any read endpoint for the kept value.
- A planned status: none is added; the status catalog stays `inProgress`, `longTerm`, `done`, `archived`.

## Acceptance criteria

- When a project with a deadline of 30 Nov is set to `longTerm`, then `date` is null in the response; when set back to `inProgress`, then `date` is 30 Nov again.
- When `date` is patched on a long-term project, then the answer is 400 with `field: 'date'`.
- The kept value does not appear in `GET /api/schema`, in item reads or in search.
- When a trashed project is purged, then its kept-date row is gone.
- The behavior is identical for writes through `/mcp`.
- The full backend `pnpm run verify` passes.
