## Behavior specification

Mail and Semp: reply drafts, mail tools, send approval and MCP sending.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: mail-semp-1 (Semp drafts replies, mail tools for Semp)

#### (a) Decisions adopted from open questions

- Is drafting a fixed "always" behavior or a setting per account or project? -> fixed behavior -> the design shows only "always". -> Decided by the product owner: reply drafts are always on; v1 adds no per-account or per-project setting (#1941).
- Is "answer expected" judged by AI before any agent session? -> yes, a cheap ai-gateway call; exhausted budget skips silently with no agent_run_error -> it avoids spending a full run. -> Decided by the product owner: a cheap AI call judges it, and an exhausted budget skips it without an error (#1941).
- Merging runs of one thread: design note proposes a queue job key `mail-draft:<threadId>`; adopted instead a run-time check that the triggering message is still the newest inbound message of the thread -> same outcome without touching the heartbeat enqueue path (the agent lane is serial). Revisit if a job key is preferred.
- Bulk mail is not back-filled (`is_bulk` false for old rows) -> old rows only matter for future runs and the known-sender gate also applies.
- Draft tools need no approval (nothing leaves the account); sending does.
- Delta frame for "Semp is writing the draft" carries `{ kind: "mailDraftBody", draftId, body }` on the existing `agent:delta` frame; the indicator ends with the run.
- A `mailThread` ref to a merged-away id is stored as given and translated when read.

#### (b) Open questions for the product owner

- Selecting the run project (thread's project, else Email) was assigned by the design note to the issue about passing the triggering item, but it needs the Threads database, so it was placed in the issue that drafts the reply; confirm.
- The guidance cutover rewrites the Email project guidance only if it equals the stored conversion of the original seeded text; confirm that an edited guidance should simply be left alone.
- Paths assumed for files created by other issues: mail/mailThreadsStore.ts, mail/mailSummaryStore.ts, mail/mailAgentTools.ts, backend/packages/shared/src/sempMessageRefs.ts.
- How a tool running in an agent run publishes `agent:delta` (the publisher available inside tool handlers) is not confirmed against the code.
- The extension point by which a module expands a draft ref into turn context depends on the ref expansion issue and was assumed.

#### (c) Behavior delivered

Mail from known people (not bulk, not the user's own address) wakes Semp in the thread's project, or in the Email project when the thread has none. A cheap AI check decides whether an answer is expected; if so Semp writes exactly one reply draft per thread (updating it for later messages unless the user edited it), the mailbox marks such threads and counts them in a "Semp drafts" box, and the draft disappears when the user answers on their own. Semp has tools to read a thread and create or update drafts, gets them under the approval and grant rules recorded in one ADR for all module agent tools, can rewrite an open draft from a chat message that references it while the client sees live typing, and chat messages can reference a mail thread, including one that was merged into another.


### Decisions: mail-semp-2 (sending by Semp and MCP clients)

#### (a) Decisions adopted from open questions

- Tool name: `mail.draft.send { draftId }` (proposed) rather than `send_email` with to, subject and body -> adopted; the label in an approval card stays "<mailbox> · <tool>".
- Is the send permission per project or per project and account? -> per project (it is today a project property), so every account shows the same count. -> Decided by the product owner: per project; one rule is simpler and every account shows the same count (#1635, #1913).
- A pending request exists at most once per draft; the draft hash is stored and a changed draft ends with execution status `conflict` and nothing is sent.
- A user, and an MCP client with a human session, send without approval; permission for agents is evaluated on the actor's project AND the thread's project, and a project assigned on a thread by an agent or Semp's sorting never adds permission. -> Decided by the product owner: in v1 every send by an agent or a run-credential MCP client goes through approval (risk class `outbound`), also in a project with the permission; autonomous sending is not switched on in v1 (#1913, #1385).
- The permission count/list route is read-only; no app way to switch it on. -> Decided by the product owner: read-only in the app; switching on autonomous sending is a high-risk outbound action and v1 does not offer it (#1635).

#### (b) Open questions for the product owner

- Name of the send tool in the product: `mail.draft.send` (adopted) or `send_email` with arguments.
- Path assumptions for files created by other issues: mail/mailboxesStore.ts (mailbox list), mail/mailAgentTools.ts.
- The exact shape in which deferred module tools return a pending approval to the agent is defined by the deferral issue and assumed here.

#### (c) Behavior delivered

An agent or an MCP client using a run credential can send a prepared draft only through approval: in v1 an approval request with the draft hash is always created, also in a project with the send permission, and the mail is sent exactly once after approval (a changed draft is not sent, a rejection leaves the draft). The permission is checked on the actor's project and the thread's project, never moved by changing a thread's project. A user or an MCP client with a human session sends without approval. Semp's mail tools, including sending, are also available over MCP under the same grants. The account detail can show how many projects are allowed to send mail on their own.
