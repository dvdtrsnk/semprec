## Context

Model tier rationale: Extends the values route to two new envelope parts (relations and step toggles) whose shapes and validators come from other issues, so uncertainty about those seams and the edited-key accounting for them is high.

#1892 lets the user edit field values of the proposal envelope with `PATCH /api/proposals/:id/values`. A proposal can also propose relations to existing items (#1426 accepts and validates them in database envelopes) and extra steps such as "create a follow-up task" or "add a new person" that the user can switch on or off (#1479 validates multi-step envelopes). The card must let the user change those too: add or remove a related item, and switch a secondary step on or off, in the same request that edits values.

Decision: the body gains two optional parts next to `set`: `relations` (per ref and relation property key, the full replacement list of target item ids, using the relation shape defined by #1426) and `steps` (`{ [ref]: { enabled: boolean } }`). Both are stored in `userOverrides` beside the field values, under reserved key names for the ref (`relations`, `enabled`) that cannot collide with a property key, and count in `userEditedKeys` as `ref.relations.<propertyKey>` and `ref.enabled` when they differ from `aiProposal`. The primary step (`primary`) cannot be switched off. A disabled step's field keys are not counted (consistent with the hidden-field rule of #1928). Validation uses the same validators confirm uses for relations and steps; no new validation rules are invented here.

## Acceptance criteria

- When `steps: { followup: { enabled: false } }` is sent for a two-step card, then the effective envelope omits that step on confirm and `userEditedKeys` contains `followup.enabled`.
- When the step is switched back on, then `followup.enabled` leaves `userEditedKeys`.
- When a field of a step was edited and the step is then switched off, then that field is not counted in `userEditedKeys`.
- When `relations` replaces a relation list on the primary step, then the effective envelope carries the new list and `userEditedKeys` contains `primary.relations.<propertyKey>`.
- When a relation target does not exist or the relation is not allowed for the target database, then the request fails with the same validation error confirm would raise and nothing is written.
- When `steps.primary.enabled = false` is sent, then the request fails with a validation error.
