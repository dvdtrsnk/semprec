## Context

Model tier rationale: One more custom route on the already-built lock, version-check and compose path of the values route, with existing fixtures, and no new concurrency or tenant contract.

After the user has edited fields of a proposal card by hand (#1892), the card offers a "return the proposal" action that discards every manual value and shows what the assistant last proposed. Manual values live in `userOverrides` and `userEditedKeys` on the Processing proposal, and the assistant's last output in `aiProposal` (kept by #1471); the stored `proposal` is the effective envelope composed from them. For a card whose type was refined, `aiProposal` already holds the values for the chosen type, so the reset returns those and not the first computation.

Decision: reset is a user action that is allowed in the same statuses as value edits (`proposed`, `needsClarification` with a chosen type, fixable `invalid`); locked cards are refused. Decision: when nothing is edited the request still succeeds and returns the card unchanged (no history entry is written for a no-op).

Shared-file ordering: this issue also waits for #1906, #1910 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `resetProposalOverridesWithClient(client, config, proposalId, input)` in `backend/packages/data/src/inbox/proposalActions.ts`: lock the proposal, check status and the optional `ifVersion` (same `ConflictError` with `{ current }` as #1892), and, when `userEditedKeys` or `userOverrides` is non-empty, write `userOverrides = {}`, `userEditedKeys = []`, `proposal = readAiProposal(properties)` and a history entry with `kind: "reset"` in one `updateItemWithClient` call. Revalidate the restored envelope with `assertValidEnvelopeForCard`; the status becomes `proposed` as in the values route when it was a fixable `invalid`.
2. Add `createResetProposalOverridesRouteHandler(pool)` in `inboxRouteHandlers.ts` (body `{ ifVersion? }`, one `withTransaction`) and register `POST /api/proposals/:id/reset-overrides` in `inboxModuleManifest.ts` with justification `transactional-semantics`.
3. Add the route matrix entry in `backend/services/semprec-api/src/routeMatrix.ts` and a cross-tenant case in `backend/services/semprec-api/src/__tests__/tenantIsolationRoutes.test.ts`.
4. Tests for the acceptance criteria.

## Scope

### In scope

- `POST /api/proposals/:id/reset-overrides` clearing field-value overrides.

### Out of scope

- Resetting relation and step-toggle overrides (#1920 defines where those are stored; if they are kept in `userOverrides` this route already clears them).
- Reopening a rejected proposal (#1937).
- Idempotency keys for this route (#1894).

## Acceptance criteria

- When a card has two edited fields and `reset-overrides` is called, then `proposal` equals the last `aiProposal`, `userOverrides` is empty and `userEditedKeys` is empty.
- When the assistant recomputed after a type was chosen, then reset returns the recomputed values, not the first computation.
- When `ifVersion` is older than the card's `updatedAt`, then the response is 409 `version_conflict` with the current card in `details.currentItem`.
- When the card is `confirmed` or `rejected`, then the request fails with a validation error.
- When nothing is edited, then the card is returned unchanged and no history entry is added.
- When another tenant's proposal id is used, then the route answers as for an unknown id.
