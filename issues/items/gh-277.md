**Blocked by:** #276

## Context

The two workflow pull requests that set this repository's automation up — #42 (the code-review workflow) and #43 (the release workflow) — carry four review findings that were never addressed. Three are still present on `develop`; the fourth (the code-review job having no `timeout-minutes`) was fixed separately by pull request #66, which raised the job timeout to 30 minutes, so it is not part of this issue. These are the only findings in this batch outside `backend/` and `web/`.

**1. No timeout on the CLI install** (`code-review.yml`). The `curl -fsSL https://claude.ai/install.sh | bash` step has neither `--max-time` nor `--connect-timeout`, so a slow or unresponsive endpoint hangs the step until the job's 30-minute timeout fires. The job timeout bounds the damage; a connect timeout prevents it.

**2. Workflow-level write permission** (`release.yml`). `permissions: contents: write` is declared at workflow level rather than on the job that needs it. There is one job today, so nothing is over-permissioned yet, but any job added later inherits repository write access it may not need.

**3. A missing version silently becomes a `vnull` release** (`release.yml`). The "Determine version" step runs `jq -r '.version' backend/package.json`, which prints the literal string `null` when the field is absent, and the existing `0.0.0` guard does not catch it, so `VERSION` becomes `null`, `TAG` becomes `vnull`, and the workflow proceeds to create a release under that tag.

## Task

- **`code-review.yml`** — add `--max-time` and `--connect-timeout` to the `curl` that installs the CLI, so an unresponsive endpoint fails the step quickly instead of hanging it until the job timeout. Leave the existing `timeout-minutes: 30` on the job as it is.
- **`release.yml`** — move `permissions: contents: write` from the workflow level onto the job that creates the release, so a future job starts with no inherited write access. Make the version guard reject a missing field: treat the literal `null` that `jq -r` prints for an absent `.version` in `backend/package.json` as invalid alongside the existing `0.0.0` case, and fail the step with a clear message instead of tagging `vnull`.

Both files are GitHub Actions workflows with no test harness in this repository, so the verification is by inspection: state in the pull request which line implements each of the three points.

## Scope

### In scope

- The three workflow changes above, in `.github/workflows/code-review.yml` and `.github/workflows/release.yml`.

### Out of scope

- `.github/workflows/ci.yml` and the CI tier redesign — the vacuously passing build/test gate is #250's subject, and touching `ci.yml` here would collide with it.
- The `code-review` check's `neutral` conclusion satisfying branch protection, which is the process gap that let this batch's findings merge in the first place: it is a branch-protection decision, not a workflow edit, and is recorded in #265 as untracked.
- Any change to what the review bot or the release pipeline actually does.

## Acceptance criteria

- The code-review job's CLI install cannot hang indefinitely on an unresponsive endpoint, and the job's existing `timeout-minutes: 30` is unchanged.
- `release.yml` declares `contents: write` on the job rather than the workflow.
- A `backend/package.json` without a `.version` field fails the release step with a clear message instead of producing a `vnull` tag.
- `.github/workflows/ci.yml` is untouched.
