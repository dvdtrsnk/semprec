### Requirement gh-1942: [transcripts 18/19] Suggest speakers again when an Event is linked or gains participants

#### Context

Model tier rationale: A new queue task enqueued from a relation-edge hook that fires for writes from three processes, which must stay idempotent under concurrent edge writes, must not run on dry-run validation, and must refresh cards owned by another module's actions without overwriting user decisions; the checkpoint and trigger rules are subtle and affect paid calls.

The speaker step of the transcription pipeline (`runSuggestSpeakersStep` in `backend/services/semprec-transcribe/src/transcriptionTask.ts`) runs once per pipeline run, and its checkpoint (`computed.suggestSpeakers` on the source Files item) is written even when nothing could be suggested. A transcript whose Event is linked after the pipeline ran (the user confirms the Event card, uploads with an Event later, or links it by hand), or whose Event gains a participant later, therefore never gets speaker suggestions. `docs/adr/2026-09-23-speaker-mappings-are-edges-proposed-on-transcript-cards.md` accepted that as a consequence ("cannot expect suggestions for a transcript whose Event was linked after its pipeline run").

This issue removes that limitation. After an edge write that links a transcript to an Event (Transcripts `event`) or adds or removes a participant of an Event (Events `people`), a new core task `transcriptSpeakerSuggestion` is enqueued in the same transaction for each affected transcript. It runs the same suggestion logic as the pipeline step, so the cards of #1640 are created or refreshed with the new candidates. Edge writes come from several processes (the transcription worker's match step, `semprec-api` for confirm and the generic relation endpoint, `semprec-agents` for Semp), so the trigger is the relation-edge-changed hook of #1530, which runs after the write in the writing process and never during the dry-run validation of `assertRelationCreatableWithClient` (a revise of an Event card that is not confirmed must enqueue nothing). Transcripts can share an Event (#1464), so an Events `people` change fans out to every transcript linked to that Event. The runner for short model tasks is the one created by #1624.

Decisions:

- The task does not touch `item_automation` (no attempt is counted) and does nothing when the transcript has no `segments` yet (the pipeline step will ask when it gets there) or no unmapped speaker.
- The step's checkpoint is bound to what was asked: it now records the Event id and the sorted candidate person ids next to `proposedSpeakers`. The pipeline step and the task skip the model call only when the current Event and candidates equal the checkpoint's; otherwise they ask again.
- Cards that already exist are not duplicated (their idempotency keys stay). A card that is `needsClarification` and has no user entry in its history is refreshed by the producer with the new `context`, and, when the model is now confident, a `relation` envelope and status `proposed`. A card that is `proposed`, `confirmed` or `rejected`, or that the user touched, is never changed.
- One job per transcript: `jobKey` `transcript-speaker-suggestion:<transcriptId>`, so many edge writes in a short time converge on one run.

### Requirement gh-1950: [calendar-invites 09/13] Apply invitation replies from incoming mail

#### Context

Model tier rationale: It lets inbound email from outside the system change stored participant state, which needs sender verification against the invited address and a system-writer ownership rule on a user-visible edge, so a mistake lets anyone forge a reply.

When the user invites people to an Event (#1774), the attendees answer with an iMIP `METHOD:REPLY` email. The calendar module already reads incoming calendar parts for requests: #1929 delivers the iCalendar parser (`calendar/icalendarParser.ts`), `readCalendarPartsOfEmail` (`calendar/emailCalendarParts.ts`) and the `onItemEvent` create heartbeat on Emails with its seed and cutover. ### Requirement gh-1953: [calendar-invites 10/13] Send the iMIP REPLY after a response commits

#### Context

Model tier rationale: It adds an outbound email side effect that must be coupled to a database commit, retried across provider transports and idempotent on redelivery, and it writes the iTIP reply format that external calendar clients interpret.

#1944 lets the user answer an invitation and commits the new status. The organizer must then be told: an iMIP `METHOD:REPLY` message has to reach them from the mailbox that received the invitation. ### Requirement gh-1957: [calendar-module 15/15] Expose calendar operations as Semp agent tools and MCP tools

#### Context

Model tier rationale: It exposes writes that send email and change tasks and events to an AI agent and to MCP clients behind a capability and an approval requirement, so the approval and grant wiring is a safety-relevant contract.

The calendar module has operations that Semp and external MCP clients should be able to perform, with the same validation as the app: answering an invitation (#1944) and placing a task into an event or taking it out (#1764). An agent completes a task through the generic item write (`item.patch` with `status: "done"`), and the Tasks update hook of #1781 records the completion in the event (decided by the product owner: every completion before the end of an event counts as a completion in the event, wherever the task is ticked), so there is no separate complete-in-event tool. Module agent tools are composed into Semp sessions by #1523, can be marked as needing approval by #1791, are exposed over `POST /mcp` by #1580, and the rule for granting them is recorded by #1385. The calendar timeline tool is a separate issue (#1952). The generic `relation.put` on an event's hosted tasks is rejected with 403, so these tools are the agent's way to change that relation.

This issue declares the three write tools in the calendar manifest and implements their handlers. A handler calls the same domain function as the corresponding route handler, not the HTTP route, so choke-point validation is identical and nothing is duplicated.

Tools (names are the manifest tool names; each has a zod input schema and a one-line description):

- `calendar.respondToInvitation` `{ invitationId, response, calendarId? }`: always requires approval, because answering sends an email to the organizer. Without an approval, a call creates an approval request and sends nothing.

The tools use one capability, `calendar.write`, declared in the calendar manifest; if the grant ADR names a different id, use that one.

Decision: calendar tools see hidden calendars; hiding is a display preference only.

### Requirement gh-1960: [calendar-ics 02/06] Fetch subscribed ICS feeds per tenant

#### Context

Model tier rationale: The server periodically requests user-supplied URLs for every tenant, so it combines SSRF defence, resource limits, per-tenant fan-out and failure isolation, which is a cross-process, security-sensitive contract.

Once a subscription calendar has a validated URL (#1925), the server must download the feed regularly. This issue builds the download mechanism only: a periodic job that, per tenant, requests each subscription calendar's URL with conditional headers and hands a changed feed body to a consumer. Turning the feed into events is #2004; until it registers a consumer, a downloaded feed is only recorded as fetched. #1957 exposes calendar operations to agents and the module manifest ordering follows it.

Existing building blocks: the periodic scheduler `CORE_CRONTAB` and the task catalog in `backend/packages/data/src/worker.ts` and `backend/packages/queue/src/index.ts` (`CORE_TASK_NAMES`, `CORE_TASK_AFFINITY`, `TASK_TENANCY`); per-tenant fan-out with `forEachActiveTenant` (`backend/packages/data/src/tenancy/forEachActiveTenant.ts`, `docs/adr/2026-10-06-system-work-fans-out-per-tenant.md`; the pattern is `handleMailAccountSyncSweepTask` in `mail/mailSyncJob.ts`); chunked transactions for large sweeps (`docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`); the outbound client `createOutboundHttp` in `backend/packages/data/src/net/outboundAddressPolicy.ts`, which pins DNS resolution to public addresses at connect time, refuses IP-literal hosts and refuses redirects (`docs/adr/2026-10-16-connect-time-outbound-address-checks.md`, host egress rules in `docs/adr/2026-10-03-host-egress-filtered-by-service-uid.md`).

Decisions:
- The sweep runs hourly (a crontab entry at minute 25); each feed is requested at most once per run.
- Limits: request timeout 20 seconds, response body at most 5 MiB (a larger body aborts the download), at most 100 subscription calendars processed per tenant per run; a redirect is a failed download.
- State per subscription calendar is kept in a new tenant table `calendar_feed_state` (calendar item id, `etag`, `last_modified`, `last_fetched_at`, `last_status`, `last_error_code`); the stored `etag` and `last_modified` are advanced only after the consumer succeeded, so a failed import is retried.
- A failed download or a failed consumer never deletes or changes data fetched earlier; the failure is recorded as a short error code and logged without feed content or the URL's query string.
