## Context

Model tier rationale: One contract change touching the job, the heartbeat configuration and an ADR, with an ownership rule that must stay narrow, but with existing fixtures and a known cutover pattern.

The library metadata job (`backend/packages/data/src/library/libraryMetadataJob.ts`) is driven by an `action_config` stored on two heartbeats per tenant in `project_heartbeats` (one `onItemEvent` trigger and one daily 04:00 retry sweep per library database; built by `metadataActionConfig` in `seed/seedLibraryModule.ts`). Today its schema `libraryMetadataJobConfigSchema` is `{ source, coverKey, secondaryRatingKey?, sourceUrlKey? }` and `LibraryMetadataFetchResult` is `{ cover?, secondaryRating?, sourceUrl? }`. The job writes only these keys, all `owner: system`, through `allowedSystemKeys`. Every config currently has `source: "none"` and the fetcher is a no-op.

Real sources also return the author, the year, the movie/series type and the ISBN. Those properties are `owner: user` (`author` and `type` today, `year` on Movies, and `year`/`isbn` on Books after #1514). Writing a user-owned property from a job would be a second writer under `docs/adr/2026-09-10-single-writer-ownership-model.md`, so the exception must be explicit and narrow.

Decision: an explicit, declared handoff. The library module contract (`library/libraryModuleContract.ts`) names which user-owned keys automation may fill, and the job writes such a key only when the item's current value is empty (missing, null or empty string) and the item's automation state is not `locked`. A value the user entered is never overwritten, and a value filled by automation can be changed by the user afterwards. (The alternative, separate `sourceAuthor`/`sourceYear` system fields shown as `user ?? source`, is not adopted.)

Decision: the config keys for these fields are `authorKey`, `yearKey`, `typeKey` and `isbnKey`, all optional, so a database without a given property (Books have no `type`, Movies no `isbn`) simply omits it.

Fetchers that fill these fields come in #1655 (books) and #1706 (movies).

Shared-file ordering: this issue also waits for #1573 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `db-migrations`, `adr-conventions` and `testing`.

1. Extend `LibraryMetadataFetchResult` with `author?: string`, `year?: number`, `type?: string`, `isbn?: string`, and `libraryMetadataJobConfigSchema` with optional `authorKey`, `yearKey`, `typeKey`, `isbnKey`.
2. Extend `LibraryModuleContract` and its zod schema with an optional `automationFillableKeys` (keys automation may fill when empty); set it to `["author", "year", "isbn"]` for Books and `["year", "type"]` for Movies, and make `metadataActionConfig` in the seed emit the matching `authorKey`/`yearKey`/`typeKey`/`isbnKey`. Set the source to `openLibrary` for Books and `tmdb` for Movies.
3. In the job, write each user-owned field only when it is in the contract's fillable set, the value is non-empty, the item's current value is empty and the automation row (read `FOR UPDATE`, as the job already does) is not `locked`. System-owned fields keep today's behavior. A provided `type` must be a valid option of the property.
4. Add `backend/packages/data/src/library/libraryHeartbeatConfigCutoverMigration.ts`: for the tenant in scope, rewrite the `action_config` of the Books and Movies library heartbeats (both the trigger and the retry sweep) to the new keys and sources. Idempotent: a tenant already on the new config is untouched; model it on `transcription/transcriptionRequeueHeartbeatCutoverMigration.ts`. Register it in `tenantCutoverMigrations.ts`.
5. Add an ADR `docs/adr/2026-10-25-library-automation-fills-empty-user-owned-fields.md` (see `adr-conventions`) recording the handoff rule, why not a second writer, and the rejected alternative.
6. Tests with an in-test fake fetcher: an empty `author` is filled; a user-entered `author` is not changed; a locked item gets nothing; the cutover turns `source: "none"` configs into `openLibrary` and `tmdb` with the new keys and a second run changes nothing.

## Acceptance criteria

- When the fake fetcher returns an author for a book with an empty `author`, then it is stored; when the user had entered an author, then it is unchanged.
- When the item is `locked`, then no field is written.
- When the cutover runs on an existing tenant, then both heartbeats of Books have `source: "openLibrary"` and those of Movies `source: "tmdb"` with the new key names; running it again changes nothing.
- When a fetcher returns a `type` that is not an option of the property, then the field is skipped and the rest of the result is still applied.
- When the ADR is listed, then it follows the repository ADR format.
