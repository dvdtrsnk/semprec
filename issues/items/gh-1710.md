**Blocked by:** #1621, #1707
**Model tier:** medium

## Context

Model tier rationale: One queued fan-out job on an existing hook and invalidation pattern, bounded by batching, with the main risk being unbounded project sizes and tenant lane use.

An item's derived area and an event's derived company live on its project, so changing a project's area or company changes what every item in that project shows, yet none of those items is written. Clients that hold those items would keep showing the old value until something else refreshed them. This issue announces the change to all affected items.

Today relation edge writes publish no invalidations of their own, and #1621 makes them publish one for each of the two items the edge joins, which here are the project and the area or company, but not for the items that merely depend on the project. #1530 adds the hook that runs after an edge is written or deleted. Background fan-outs run as queued tasks in per-tenant lanes (`rollup/recompute.ts` shows the pattern with `tenantLane`), in batches per `docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`. #1595 defines which databases depend on a project (its configuration list).

Decisions:

- Invalidation is thin: one item invalidation per affected item, sent after the batch commits, as other item writes do; clients refetch.
- Affected items are every live item related to the project through the configured project properties (tasks, events, files, health records).
- The job key is per project so several quick changes collapse into one fan-out.

Shared-file ordering: this issue also waits for #1707 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes` and `testing`.

1. Queue: add the task `derivedValuesInvalidate` (payload `{ projectItemId }`) to `CORE_TASK_NAMES`, `CORE_TASK_AFFINITY` (`api`) and `TASK_TENANCY` (`tenant`) in `packages/queue/src/index.ts`, and its handler to the task list in `packages/data/src/worker.ts`.
2. Add `backend/packages/data/src/derived/projectDerivedValueHook.ts` (new): the edge-changed hook from #1530, registered in `domainWriteHooks.ts`. When an edge is created or deleted on the relation definition behind `Projects.area` or `Projects.company` (either side), it enqueues `derivedValuesInvalidate` for the project item with `enqueueJob` in the same transaction: queue name `tenantLane("derived-values-invalidate")`, job key `derived-values-invalidate:<projectItemId>`, a small `maxAttempts`.
3. Add `backend/packages/data/src/derived/projectDerivedValueInvalidation.ts` with the handler. It pages through the project's related items in batches of a fixed size (keyset on item id, one committed transaction per batch, per the chunked-transaction ADR), skipping trashed items, and after each batch's commit sends `notifyInvalidation` (scope `item`, op `update`, with the item's `databaseId`, `itemId` and current `updatedAt`) for each. A trashed or missing project sends nothing. A rerun is harmless.
4. Tests: changing a project's area enqueues one job and, once it runs, announces every task, event, file and health record of the project and nothing else; a project with more items than one batch is fully covered; two quick changes collapse to one job; changing the company announces the project's events (and the others harmlessly); a trashed project announces nothing; the job for one tenant never touches another tenant's items; a failing batch retries without announcing items twice in a way that matters (announcements are idempotent refetch triggers).

## Scope

### In scope

- The hook on project area and company edges, the queued job, and per-item invalidations in batches.

### Out of scope

- Invalidations for the two endpoints of an edge write: #1621.
- The derived read and the write guard: #1595 and #1662.
- Reindexing search documents when a project's area changes: not planned yet; it waits for a product decision.

## Acceptance criteria

- When a project's area changes, then each live task, event, file and health record of that project receives an item invalidation after commit.
- When a project's company changes, then its events receive an item invalidation.
- When several changes happen in quick succession, then one fan-out runs for the project.
- When the project is trashed or missing, then no invalidation is sent.
- A project with many items is handled in independent committed batches; items of other tenants are never announced.
