### Requirement gh-1686: [mail-accounts 19/30] Connect a Gmail or Outlook mailbox through OAuth

#### Context

Model tier rationale: This is a new authentication-adjacent flow that mixes a public callback, an authenticated completion, an external token exchange outside the transaction and a multi-row atomic write, with account-takeover risks if any step is wrong.

A user can add a Google or Microsoft mailbox by signing in at the provider. The app asks the server for an authorization link, the provider shows its consent window, and the app hands the result back so the server creates the mailbox and starts downloading mail. Today no route exists for this: `backend/packages/data/src/mail/mailAccountSyncStateStore.ts` says the connect flow does not exist, and no `authorization_code` exchange exists in `oauthTokenExchange.ts`.

It builds on: the one-time state storage (#1483), the authorization-code exchange (#1484), the server-owned provider address (#1454), the Gmail and Graph sync transports (#1505, #1508) and custom module routes that receive composition-root dependencies (#1460). Reauthorizing an existing mailbox from the app (#1742) builds on this flow.

Module custom routes are always authenticated (`backend/services/semprec-api/src/adapter/customRouteMount.ts`). The one public route that this flow needs, the provider redirect target, is wired by hand in `backend/services/semprec-api/src/app.ts`, following the Microsoft Graph webhook route, and has an entry with a `publicReason` in `routeMatrix.ts`.

Decision: the public callback writes nothing and returns only the code and state to the app; the app then calls the authenticated completion route. The state is consumed (single use) before the provider exchange, so a provider failure requires a new start.

Decision: the redirect target is configured as the web callback URL for this deployment (a single configured redirect URI); the native-app hand-off (universal link or URL scheme) is an open product question and does not change this server contract.

Decision: scopes are the minimum for read, triage, draft and send. Google: `gmail.modify`, `gmail.send` (read access is covered by modify; `gmail.compose` is added only when drafts are uploaded to the provider). Microsoft through `/common`: `Mail.ReadWrite`, `Mail.Send`, `offline_access`, `User.Read` (without it `GET /me` returns 403). Google requests `access_type=offline` and `prompt=consent` so a refresh token is returned on repeat sign-ins.

Shared-file ordering: this issue also waits for #1685 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`. Follow `docs/adr/2026-09-10-bracket-non-transactional-calls-with-staleness-checked-transactions.md` for the call outside the transaction.

1. `POST /api/mail/mailboxes/oauth/start` with `{ provider: "gmail" | "outlook" }` returns `{ authorizeUrl }`. It creates a state through #1483 (new account, no mailbox id), builds the provider URL with the S256 code challenge, the state, the redirect URI and the scopes above, and returns only the URL. Justification `transactional-semantics`.
2. `GET /api/mail/oauth/callback` is public, wired in `app.ts`, with a `routeMatrix.ts` entry carrying a `publicReason`. It writes nothing and does not read the session; it passes the `code` and `state` (or the provider's error) on to the app. Tokens and codes are never logged.
3. `POST /api/mail/mailboxes/oauth/complete` with `{ state, code }` (authenticated, justification `transactional-semantics`):
   - consumes the state for the calling user; a state of another user, already used or expired answers 400 `validation_failed` and creates nothing;
   - a state that carries a mailbox id (reauthorization) is not handled by this issue and answers 400 until #1742 adds that branch;
   - outside any transaction exchanges the code through #1484 and fetches the provider's own address and aliases (Gmail `users.getProfile` and `settings.sendAs`; Graph `/me`);
   - in one transaction creates the Mailboxes item (name `Gmail` or `Outlook`, `provider`, `addresses` written through the helper from #1454), stores the refresh token as `oauth2_refresh_token` with `storeCredential`, creates the sync state (`gmail_api` or `graph_api`) with `provider_account_address` (and `gmail_watch_email_address` for Gmail) and calls `enqueueMailAccountSync(client, ...)`;
   - an address that an existing mailbox of the tenant already has does not create a second mailbox: the route answers 409 and names that mailbox, so the app can offer reauthorization;
   - a provider refusal, a cancelled consent or an error creates nothing; a Microsoft work account that needs administrator approval answers 400 `mail_admin_consent_required` (add the code to `ITEM_ERROR_CODES` and `ITEM_ERROR_STATUS_BY_CODE`).
4. Register both authenticated routes in the mail module manifest `customRoutes` and the route matrix. The live-sync lifecycle picks up the new mailbox on its next discovery pass; the handler may also trigger `reconcileOnce()` from the injected dependencies.
5. Neither the refresh token, access token, code nor verifier appears in any response, log line or tenant export.

### Requirement gh-2030: [mail-accounts 22/30] Clean up a removed mailbox at the provider after commit

#### Context

Model tier rationale: It handles a mailbox's refresh token after the credential row is gone, coordinates a running live-sync lifecycle across the composition root and makes best-effort calls to two providers, where a leaked secret, a failing removal or a lifecycle that keeps running are each easy mistakes.

#1690 adds `DELETE /api/mail/mailboxes/:id`, which removes the mailbox's credential and sync state in one transaction. After the commit three things still run outside Semprec's database: the hosted live-sync lifecycle of the mailbox (IMAP IDLE, Gmail watch or Graph subscription, hosted by the live-sync root in `backend/packages/data/src/mail/mailLiveSyncRoot.ts`, which discovers mailboxes every 60 seconds), the Gmail watch or Graph subscription at the provider, and the OAuth grant the provider still honors. Side effects follow the commit (`docs/adr/2026-09-10-side-effects-follow-the-commit.md`). Route dependencies come from the composition root (#1460).

Decision: the cleanup is best effort and never fails the removal; the removal has already committed when it runs.

#### Task

Load `error-handling`, `io-hardening` and `testing`.

1. In `backend/packages/data/src/mail/mailboxRemoval.ts`, inside the removal transaction and before the credential is deleted, read what the provider cleanup needs (the provider, the Gmail watch or Graph subscription id and, for OAuth mailboxes, the refresh token) into memory only. It is never written to the database, a job payload or a log.
2. ### Requirement gh-1697: [transcripts 06/19] Inherit a transcript's project, company and people from its Event

#### Context
