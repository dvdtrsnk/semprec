## Context

The only `BlobStorageWriter` implementation is `LocalFsBlobStorageWriter` (`backend/packages/data/src/mail/blobStorage.ts:54`), which writes under a base directory. Every production construction of it falls back to `/tmp`:

- `backend/services/semprec-api/src/serve.ts:77` — `new LocalFsBlobStorageWriter(process.env.FILES_STORAGE_DIR ?? "/tmp/semprec-files")` (uploaded Files blobs, `POST /api/files`, `GET /api/blobs/:id`);
- `backend/services/semprec-transcribe/src/queueRuntime.ts:27` and `backend/services/semprec-transcribe/src/transcriptionTask.ts:798` — the same expression as default parameters;
- `backend/packages/data/src/worker.ts:101-103` — `mailBlobStorage` default parameter `new LocalFsBlobStorageWriter(process.env.MAIL_ATTACHMENTS_DIR ?? "/tmp/semprec-mail-attachments")` (mail attachments).

`deploy/shared/.env.example` defines neither `FILES_STORAGE_DIR` nor `MAIL_ATTACHMENTS_DIR`, and `deploy/provision.sh` creates no data directory for them (`ensure_release_tree`, lines 188-197, creates `releases`, `shared` (`0700 root:root`) and `shared/bin`). So on a provisioned host every uploaded file and every mail attachment lands in `/tmp`, which Debian cleans on reboot, while the `blobs` rows that reference them survive in Postgres — the restore test would then compare rows against bytes that no longer exist. Note `/opt/semprec/shared` is `0700 root:root`, so a subdirectory owned by `semprec` under it would not be traversable by the `User=semprec` services (`deploy/systemd/semprec-api.service`); the directories must live beside it, not inside it.

Sibling issue #649 changes the backup/restore scripts to cover these directories; it depends on the names fixed here. Sibling #648 wires the api queue runtime's mail arguments and relies on the `worker.ts` default parameter for `mailBlobStorage`, which this issue makes environment-driven.

## Task

1. **Provisioning** — in `deploy/provision.sh`, after the `semprec` user exists and inside/next to `ensure_release_tree`, create `$SEMPREC_ROOT/data` (`0755 root:root`), `$SEMPREC_ROOT/data/files` and `$SEMPREC_ROOT/data/mail-attachments` (both `0750 semprec:semprec`, via `install -d -o semprec -g semprec -m 0750`; extend or parallel `ensure_directory` so it accepts an owner — it currently hardcodes `root:root`). Re-running provision must leave existing directories and their contents untouched. Extend `deploy/provision.test.sh` (the block at lines 88-92) to assert both directories exist with mode `750`; the test's `install` mock (line 56) strips `-o`/`-g` before calling the real `install`, so make it also append `install $*` to `$TEST_STATE/commands` and assert a line matching `install -d -o semprec -g semprec -m 0750 .*/opt/semprec/data/files` (and the same for `mail-attachments`) was recorded.
2. **Configuration** — in `deploy/shared/.env.example`, add a `# ---- Blob storage ----` section immediately after the `SEMPREC_MIGRATE_DATABASE_URL` block (lines 73-78) with `FILES_STORAGE_DIR=/opt/semprec/data/files` and `MAIL_ATTACHMENTS_DIR=/opt/semprec/data/mail-attachments`, each with a comment naming which process writes there (`semprec-api` and `semprec-transcribe` for files; `semprec-api`'s mail sync for attachments) and that the directories are created by `provision.sh`. Do not touch the `MINIO_*` block (#649 rewrites it).
3. **Code defaults** — in `backend/packages/data/src/mail/blobStorage.ts`, export `resolveBlobStorageDir(envVarName: "FILES_STORAGE_DIR" | "MAIL_ATTACHMENTS_DIR"): string`: returns `process.env[envVarName]` when set and non-empty; otherwise, when `process.env.NODE_ENV === "test"` (vitest sets it), returns the previous `/tmp/semprec-files` / `/tmp/semprec-mail-attachments` default; otherwise throws `new Error(`${envVarName} is not set`)`. Replace the four expressions above with `new LocalFsBlobStorageWriter(resolveBlobStorageDir("FILES_STORAGE_DIR"))` / `resolveBlobStorageDir("MAIL_ATTACHMENTS_DIR")`. Add `resolveBlobStorageDir` to the existing export line for `./mail/blobStorage.js` in `backend/packages/data/src/index.ts` (line 246) — edit that one line only. `semprec-api`'s `serve.ts` thereby fails at startup (via `installFatalHandlers`) with `FILES_STORAGE_DIR is not set` in a non-test environment without the variable; `semprec-transcribe` the same; the api's mail task list fails the same way for `MAIL_ATTACHMENTS_DIR` when `createCoreTaskList` evaluates its default.
4. **Tests** — `backend/packages/data/src/__tests__/blobStorageDir.unit.test.ts` (new, no Postgres): with `NODE_ENV=test` and the variable unset → the `/tmp` default; with the variable set → that value (in any `NODE_ENV`); with `NODE_ENV=production` and the variable unset → throws naming the variable. Restore `process.env` after each case.

## Scope

### In scope
- Persistent, provisioned directories; the two environment variables; the fail-fast resolver replacing the four `/tmp` fallbacks; the unit test.

### Out of scope
- Backing those directories up and restoring them (#649).
- Removing or reconfiguring MinIO (`deploy/docker-compose.yml`, `MINIO_*` variables).
- Any object-storage (S3) writer; `LocalFsBlobStorageWriter` stays the only implementation.
- Wiring `mailBlobStorage` explicitly in the api queue runtime (#648 leaves it on the default this issue defines).

## Acceptance criteria

- When `provision.sh` runs on a fresh host, `/opt/semprec/data/files` and `/opt/semprec/data/mail-attachments` exist, owned by `semprec:semprec`, mode `0750`; a second run changes nothing.
- When `FILES_STORAGE_DIR` is unset and `NODE_ENV` is not `test`, `semprec-api` and `semprec-transcribe` exit non-zero at startup with an error naming `FILES_STORAGE_DIR`; when `MAIL_ATTACHMENTS_DIR` is unset under the same condition, the api task list construction fails naming `MAIL_ATTACHMENTS_DIR`.
- When the variables are set, uploads through `POST /api/files` and mail attachments are written under those directories (verifiable in the existing `filesAndBlobsHandler.test.ts` by pointing `FILES_STORAGE_DIR` at a temporary directory).
- When `NODE_ENV=test` and the variables are unset, the previous `/tmp` paths are used, so the existing test suites run unchanged.
- `deploy/shared/.env.example` documents both variables with the `/opt/semprec/data/...` values.
