## Context

Model tier rationale: This adds a persisted index contract that is rewritten inside every item write transaction for every tenant, plus a tenant-scoped backfill job, so a mistake corrupts search for all databases or slows or breaks every write.

Global search needs one searchable text document per item. Today `item_search_index` (`item_id` primary key, `database_id`, `search_vector`, `updated_at`; created in `0006_mail_sync.sql`, under tenant row-level security since `0060_tenant_row_level_security.sql`) is filled only by mail: `mail/ingest.ts` and `mail/mailSyncJob.ts` call `reindexItemSearch` (`mail/search.ts`, `ON CONFLICT (item_id) DO UPDATE`) with subject, body and attachment text. No other database is indexed, so Tasks, Events, Projects, Areas, People, Companies, Files, Health records, the Journal and user-created collections cannot be found.

The choke point already runs create and update hooks inside the write transaction (`chokePoint/hooks.ts`; registration in `domainWriteHooks.ts`). This issue registers an indexing hook there, builds the document, and backfills existing data. It is the foundation the other search issues build on: #1652 keeps documents fresh when related data changes, #1589 changes how the vector is built and queried, #1658 adds page and journal text, and #1842 and #1857 read the index.

Decisions:
- Emails are skipped. The Emails database rows belong to the mail module (single-writer ownership, `docs/adr/2026-09-10-single-writer-ownership-model.md`); a generic rebuild on a `read` or `flagged` update would overwrite the mail row with poorer text. The mail sender and reindexing of existing mail are owned by #1591 and #1741.
- Labels of `select` and `multi_select` values are resolved in the locale of the tenant's earliest-created active user (`users.locale`, default `cs`), through the existing choke-point label catalogs (`chokePoint/i18n/cs.json`, `en.json`) with a user-added option's own `label` taking precedence.
- The area of an item with a project is read by following the item's project relation to that project's area relation inside the builder, so this issue does not depend on a derived-area read.
- Relation values are edges, not properties, so an item created together with its relations is indexed by the create hook without them; their text arrives through the edge fan-out in #1652.

## Task

Load `state-writes`, `canonical-keys`, `db-migrations` and `testing`.

1. Add an optional `searchFields?: string[]` to `ModuleDatabaseDescriptor` in `backend/packages/module-registry/src/manifest.ts`. A key names a property of that database; for a relation property the linked items' titles are used. A key that names no property of the database is ignored (so a later issue can add `place` to Events once that property exists).
2. Declare `searchFields` for the ten system databases in `seed/systemDatabasesModuleManifest.ts`: each database's title and text-bearing properties as seeded in `seed/seedTenDatabases.ts`, plus its relation properties whose linked titles should be searchable (Tasks: project; Events: project, people; Projects: area, company; People: companies; Files: projects, healthRecords, companies; Health records: projects). People e-mails and phones are added when those properties exist.
3. Add `backend/packages/data/src/search/itemSearchDocument.ts`: a pure builder from an item, its database descriptor and resolved related titles to one text document. Source: values of the declared `searchFields`; for a database without `searchFields` (user-created collections) the default rule: every property of type `title`, `text`, `longText` and `url`, and the labels of `select` and `multi_select` values. Always include the titles of linked project, area, people and company items (only items that are not soft-deleted), and for an item that has a project, also the title of that project's area. For a Journal day, include the `inbox.text` of its entries from `computed.inboxItems` (`inbox/journalInboxCompute.ts`).
4. Add `backend/packages/data/src/search/itemSearchIndexer.ts` with `indexItem(client, itemId)` (load item, database, related titles in a few batched queries, build the document, upsert the row with `to_tsvector('czech', document)`) and a single place that owns the vector SQL expression so #1589 changes it in one spot. Never index the Emails database (resolve it by `owner_module_id`), a soft-deleted item, or an item whose database is missing.
5. Register an item create hook and an item update hook in `domainWriteHooks.ts` that call `indexItem` in the write transaction. A failure rolls the write back like any other hook failure.
6. Add the batch backfill: a core task `itemSearchBackfill` (`CORE_TASK_NAMES`, `CORE_TASK_AFFINITY` `api`, tenant tenancy in `TASK_TENANCY`, handler registered in `worker.ts`) with payload `{ databaseId?, afterItemId?, onlyMissing }`. It walks non-deleted, non-Emails items by keyset on item id, indexes one committed chunk at a time (`docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`), and enqueues its continuation under a job key that includes the cursor, on `tenantLane("item-search-index")`. With `onlyMissing` it skips items that already have a row. Export an `enqueueItemSearchBackfill(client, options)` helper for the later issues.
7. Enqueue `{ onlyMissing: true }` once per maintained tenant on every deploy: add `runItemSearchBackfillCutover(pool)` using `forEachMaintainedTenant` (role `semprec_data`, `docs/adr/2026-10-08-deploy-time-tenant-work-runs-as-the-runtime-role.md`) and call it from `db/runMigrationsCli.ts` after `grantQueueSchemaPrivileges`, because `runTenantCutoverMigrations` runs before the queue schema exists. A new tenant has no data and is indexed by the hooks.

## Scope

### In scope

- The search document builder, the choke-point hooks, `searchFields` in the manifest contract, and the one-time and per-deploy backfill of existing items.

### Out of scope

- Reindexing when related items, edges, titles, trash state, schema or locale change: #1652.
- Diacritic-insensitive and prefix matching and the query builder: #1589.
- Page text, journal text and the `body` column: #1658.
- Adding Events `place` to its `searchFields`: whichever issue adds the Events `place` property (#1416) appends it.
- The mail sender in the text and reindexing of existing mail: #1591, #1741.
- Semp chat indexing: it waits for the thread entity and is not planned in this batch.
- Any search operation or route: #1842.

## Acceptance criteria

- When a Task "Odeslat fakturu" is created, its `item_search_index` row exists in the same transaction, and it is gone if that transaction rolls back.
- When a Task has a project, the document contains the project title and the title of the project's area.
- When an Emails item is updated (for example `read` toggled), its search row is not touched.
- When a user-created collection gets an item with a text, long text, url or select value, the document contains it; a `select` label is in the locale of `users.locale`.
- A Journal day's document contains the text of its Inbox entries.
- When the deploy backfill runs for a tenant with items created before this change, every non-deleted, non-Emails item has a row; running it again changes nothing for items that already have one.
- A tenant never reads or writes another tenant's rows (covered by the tenant isolation suite for the new task).
