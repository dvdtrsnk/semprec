**Blocked by:** #198, #90

## Context

First of two parts of the write-back slice that completes the `mail-live-sync` batch (approved behavior in #194). It builds on the live-sync host of #195, the IMAP IDLE lifecycle of #196, and the canonical read/flagged properties and authenticated mutation event from #90. This part delivers the provider-independent write-back consumer, the desired/current state persistence, and the IMAP adapter. #199 adds the Gmail and Graph adapters on top of the same consumer and state.

## Task

- Consume the canonical Email `read`/`flagged` mutation event from #90 (authenticated, originating from the UI or the AI) inside the mailsync host of #195 and dispatch the four transitions read/unread/flag/unflag to a per-provider write-back adapter.
- Persist per message the desired state (what the user asked for) and the current provider state (what the provider last confirmed) so that: a provider-originated update observed by reconcile that matches the desired state is not echoed back to the provider; a retry of an already-applied write is idempotent; and a pending write survives a restart.
- Implement the IMAP adapter: `STORE ... FLAGS.SILENT` on the message's UID (using the UID metadata already persisted for IMAP messages), updating the current state on success.
- Provider failure uses the existing sync error/retry mechanism; the desired state stays pending until a later attempt or reconcile converges.
- Ship the write-back adapter interface with the Gmail and Graph implementations left as explicit not-yet-implemented stubs: for those accounts the desired state is persisted and stays pending (no provider call, no error), so #199 can flush it once the adapters exist.

## Scope

### In scope

- Mutation-event consumer, desired/current state persistence, IMAP `STORE FLAGS.SILENT` adapter, sync error/retry wiring, adapter interface with pending stubs for Gmail/Graph, tests, and necessary documentation.

### Out of scope

- Gmail `users.messages.modify` and Graph `PATCH` adapters, cross-provider convergence tests — #199.
- Schema and UI controls — #90 / #27.

## Acceptance criteria

- All four transitions work against the fake IMAP provider and update the current state.
- A provider-originated flag change that reconcile brings in does not produce a write back to the provider (no echo loop).
- A failed IMAP write retries through the existing sync error path and converges; a repeated write of an already-applied state is a no-op.
- A second IMAP client sees a change made in our UI within one live round trip.
- For Gmail and Graph accounts the desired state is persisted as pending and no provider call is attempted.
