**Blocked by:** #1975
**Model tier:** high

## Context

Model tier rationale: Confirm writes the day period, page content and two relations in one transaction with the status transition and must stay idempotent under retry, which is a difficult atomicity and idempotency contract across three modules.

After #1975, a proposal card can carry a validated `journalEntry` envelope `{entityKind: "journalEntry", target: <Journal database id>, properties: {date, markdown, areaId?, projectId?}}`, but confirm answers 409 for it. `confirmProposalWithClient` in `backend/packages/data/src/inbox/proposalActions.ts` currently handles `database` (creates an item), `relation` (transcript cards) and `pageContent` (one block appended via `putBlockWithClient(target, {id: proposal.id, ...}, 'ai_agent')` without a position, inside the same transaction as the `proposed -> confirmed` transition, with a block id equal to the proposal id so a retry is idempotent).

Journal days are created lazily. #1541 delivers `ensureJournalPeriodDoc(kind, key)` semantics: create the period item and its page document if missing, in one request. #1679 delivers inserting Markdown at a placement into a page (`page.insert`). #1545 adds the Journal-to-Projects relation, next to the existing Journal-to-Areas relation. Relations are written with `createRelationWithClient` (`backend/packages/data/src/chokePoint/relationOps.ts`), which is idempotent.

Decision: the inserted blocks are authored by `user`, the acting user who confirmed (decided by the product owner); the step result lists their ids (`blockIds`, #1648) as the record that Semp proposed them.
Decision: with a project, a journal entry's area is derived from the project, so only the project edge is written; without a project the area is the entry's own value (#1991 rejects an envelope with both).
Decision: the entry is appended at the end of the day's page.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In `confirmProposalWithClient`, replace the explicit 409 for `journalEntry` with a real branch executed in the same transaction as the `proposed -> confirmed` transition:
   - ensure the day period item and its page for `properties.date` using the #1541 helper (kind `day`, key `YYYY-MM-DD`);
   - insert `properties.markdown` at the end of that page with the #1679 `page.insert`, origin `user`; the ids of the inserted blocks are derived deterministically from the proposal id and the block's order (for example a UUID v5 of the proposal id plus the index), so the retry of a confirm does not add blocks. If the `page.insert` signature of #1679 cannot take caller-supplied ids, extend it minimally inside this issue and name it in the pull request;
   - when `projectId` is present, create the `project` edge (#1545) and no own `area` edge (the area is derived from the project); when only `areaId` is present, create the Journal `area` edge from the day to the area; both with `createRelationWithClient`;
   - set `resultItemId` to the day item id and `resultLabel` to the day key (`YYYY-MM-DD`); the client composes the toast text.
2. Idempotency: confirming an already confirmed journal-entry proposal returns the stored result and writes nothing; if the transition lost a race, no page content and no edge may remain.
3. Re-validate at confirm time (as the other kinds do): the area and project still exist and are live, and the Journal database id still matches; otherwise 409 with the card left proposed.
4. Tests in `backend/packages/data/src/__tests__/proposalActions.test.ts`: confirm with a date that has no day yet creates the day, its page and appends the entry at the end after existing blocks; `doc_updates.created_by` is `user`; an entry with a project gives the day a `project` edge and no own `area` edge; an entry with only an area gives an `area` edge; confirming twice adds no block; a deleted project at confirm time gives 409 and writes nothing.

## Acceptance criteria

- When a card with date 2026-10-16 is confirmed and no day exists, then the day, its page and the appended entry exist and the card is `confirmed`.
- When the day already has blocks, then the entry is added after them and the existing blocks keep their order.
- When the same proposal is confirmed a second time, then no block is added and the same `resultItemId` and `resultLabel` are returned.
- When the envelope names a project, then the day has a `project` edge and no own `area` edge; when it names only an area, the day has an `area` edge; re-confirming does not duplicate the edges.
- When the written document updates are inspected, then `created_by` is `user`.
- When the project was deleted after the card was computed, then confirm answers 409 and nothing is written.
- When any step of the confirm fails, then the card stays `proposed` and no partial page content remains.
