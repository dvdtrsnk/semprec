**Blocked by:** #1486
**Model tier:** high

## Context

Model tier rationale: Introduces a new tenant-owned table with row-level security, tenant classification and composite foreign keys, plus a write on the confirm path and an explicit delete in the permanent-delete path, so a mistake leaks across tenants or leaves orphan rows.

A created item does not know how it came into being. `confirmProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) stores only `resultItemId` and `resultLabel` on the card. The reverse lookup is possible only as a filtered query of Processing proposals by `resultItemId` (`backend/packages/data/src/views/filterCompiler.ts`), which finds just the primary item and cannot return the source Inbox item or the capture time (the source relation has no inverse and the REST envelope does not include it). Multi-step proposals (#1486) create several items from one capture, and list screens need the answer for many rows, so a per-item lookup through the card does not scale.

Permanent deletion removes dependent rows by hand in `deleteItemDependents` (`backend/packages/data/src/chokePoint/itemTrash.ts`) because `items` carries no foreign keys to dependents. Tenant export and purge are driven by the tenancy catalog (`backend/packages/data/src/tenancy/tenantExportJob.ts`, `tenantPurgeJob.ts`) from the `COMMENT ... 'semprec:tenancy=tenant'` convention set in `0058_table_tenancy_classification.sql`.

Decision: one mechanism serves every database. A side table `item_origins` records, for each item created by a confirmed proposal, which card, Inbox item or transcript and capture time produced it. Files do not get a separate origin link; they read this table. Readers are #1967 (single item) and #1716 (list flag); #1943 removes rows on undo and #1703 relies on it when an attachment moves into Files.

## Task

Load `db-migrations`, `state-writes` and `testing`.

1. Add a migration creating `item_origins`: `tenant_id` (not null), `item_id`, `proposal_id`, `inbox_item_id` (nullable), `source_transcript_id` (nullable), `captured_at` (timestamptz, not null), `capture_channel` (text, not null); primary key or unique `(tenant_id, item_id)`; composite tenant foreign keys in the style of `0083_tenant_composite_foreign_keys.sql` where the referenced tables have a `(tenant_id, id)` key; row-level security policy identical to the sibling tenant tables; `COMMENT ON TABLE item_origins IS 'semprec:tenancy=tenant'`; least-privilege grants matching sibling tables; an index on `(tenant_id, proposal_id)`.
2. In `confirmProposalWithClient`, inside the confirming transaction, insert one `item_origins` row for every item a step creates (not for items that are only patched or linked). `inbox_item_id` comes from the card's source Inbox item, `source_transcript_id` from the transcript edge for transcript cards, `captured_at` from the source Inbox item's capture time (the card's creation time for transcript cards), and `capture_channel` is `inbox` for Inbox cards and `transcript` for transcript cards.
3. In `deleteItemDependents`, delete the item's `item_origins` row.
4. Confirm that tenant export and purge pick the new table up from the catalog; add it explicitly (and a test) only if the catalog does not.
5. Tests: confirm of a two-step proposal writes two rows; a repeated confirm writes no duplicate; permanent deletion removes the row; the table is classified `tenant` in the tenancy catalog test; another tenant cannot read the row.

## Scope

### In scope

- The `item_origins` table with row-level security and tenant classification, written on confirm, deleted with the item.

### Out of scope

- Reading origin through an endpoint; #1967.
- The list-row flag; #1716.
- Writing a visible note into the item's page; #1735.
- Removing the row when a confirmation is undone; #1943.

## Acceptance criteria

- When a proposal that creates two items is confirmed, then `item_origins` has two rows with the card id, the source Inbox item id and the Inbox item's capture time.
- When the same confirm is repeated, then no row is added or changed.
- When a created item is permanently deleted, then its `item_origins` row is gone in the same transaction.
- When tenant B queries `item_origins` as its own role, then it sees no row of tenant A, and the table appears as `tenant` in the tenancy catalog.
- A tenant export contains the rows and a tenant purge removes them.
