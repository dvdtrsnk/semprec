## Context

Model tier rationale: One additive nullable column with a wrapper-level argument that must be stripped before validation at two entry points, touching agent-facing tool schemas but leaving every strict REST and MCP input unchanged.

Product behavior: when Semp asks for approval, it can say why in its own words ("You last filled in Mood in August..."), and the user sees that reason next to the request.

Today an approval request records what will run but not why. `createPendingApprovalRequest` in `backend/packages/data/src/mcp/approvalRequestsStore.ts` takes no reason. Generic operation inputs are `.strict()` Zod schemas, and the agent tool parameters are the operation's JSON schema (`backend/services/semprec-agents/src/agentSessionComposition.ts`); MCP tool parameters are free-form.

Decision: the reason is an optional argument that exists only in the agent-facing tool schema. For generic operations it is named `reason`; for MCP tools it uses the reserved key `semprecReason`, because the third-party tool's own parameters are free-form and a plain `reason` could collide with a real argument. The tool wrapper removes it from the input before validation and passes it only to the creation of the request. The operation input, `canonicalInput`, `resource_snapshot`, REST and `/mcp` stay unchanged, so a REST `item.delete` with a `reason` field still fails strict validation with 400.

Decision: the reason is limited to 500 characters (longer input is rejected by the wrapper with a validation error to the model), stored as plain text, returned to the owner in the request view, and never written to logs.

This issue is independent of the description snapshot (#1683); both add a nullable column to the same table in separate migrations.

## Task

Load `db-migrations`, `io-hardening`, `state-writes` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_approval_requests_reason.sql` (next free ordinal at commit time): `ALTER TABLE approval_requests ADD COLUMN reason text NULL`, with `CHECK (reason IS NULL OR char_length(reason) <= 500)`.
2. Store: add `reason: string | null` to `ApprovalRequest`, to the row mapping and to `CreatePendingApprovalRequestInput` (optional); `createPendingApprovalRequest` writes it.
3. Generic operations: in the composition of agent tools for the approval-gated operations, add an optional `reason` string (max 500) to the tool schema only; strip it from the model's arguments before the operation input is validated, and pass it to `preflightDestructiveApproval` so it reaches the insert. Operations that do not require approval do not get the argument.
4. MCP tools: add the optional `semprecReason` argument to the schema of approval-gated MCP tools and have `createApprovalGatedMcpInvokeTool` remove it from `args` before they are stored in the payload and before the tool is invoked, passing it to the insert.
5. Return `reason` in the queue entry and decision view (`approvalRequestsQueue.ts`); `null` when absent.

## Scope

### In scope

- The `reason` column, the agent-only argument for generic and MCP approval-gated tools, and returning it in the request view.

### Out of scope

- The localisable description of the action: #1683.
- Showing the reason in pushes or in the thread.
- Any change to the strict operation input schemas, REST routes or `/mcp`.
- Requiring a reason (it stays optional).

## Acceptance criteria

- When an agent calls an approval-gated operation with `reason`, the pending request returns that text in `reason`; `payload.canonicalInput` and `resource_snapshot` do not contain it.
- When an agent calls an approval-gated MCP tool with `semprecReason`, the request returns it and the stored `args` and the arguments later sent to the MCP server do not contain it.
- When the reason is longer than 500 characters, no request is created and the model receives a validation error.
- When a request is created without a reason, `reason` is `null`.
- A REST `item.delete` call with a `reason` field answers 400 (strict input).
- The reason does not appear in application logs.
