**Model tier:** medium

## Context

Model tier rationale: It adds two conditions to an existing compiler following the established relation-condition pattern and test fixtures, with the only subtlety being that edges to soft-deleted targets must not count.

Some collection queries need to ask whether an item has any value in a relation at all: "files without a project", "items with no linked person". The filter tree cannot say this. `is_empty` / `is_not_empty` are scalar conditions, and `compileCondition` in `backend/packages/data/src/views/filterCompiler.ts` deliberately rejects them on a relation property with the message that the property must be filtered with `relation_contains` / `relation_not_contains`, which only test for one specific target item. There is no condition for "no edge" or "any edge".

The first consumer is the per-database area filter (#1597): a file or a health record that has no project but carries its own area must match that area, so the filter needs "the project relation is empty" next to "the own area contains X". The second is the "No value" bucket of facets (#1759), and related collections (#1839) and the Tasks today view overview (#1798) depend on it as well.

The condition set exists in two copies that must stay identical: `backend/packages/data/src/views/filterTree.ts` and `backend/packages/shared/src/genericOperations/filterSort.ts`. #1363 already extended both with `relation_path_contains` and extended `FilterProperty`; this issue edits the same files after it lands, which is why it is ordered after it.

Decision: an edge to a soft-deleted item does not count as a value. A file whose only project was deleted counts as having no project. Rationale: the item no longer appears anywhere in the product, so it must not hide the file from "no project".

## Task

Load `canonical-keys` and `testing`.

1. Add the conditions `{ type: "relation_is_empty" | "relation_is_not_empty", property: <relationKey> }` to both filter-tree copies (`FILTER_CONDITION_TYPES`, the `FilterCondition` union, the zod schema) with identical validation. There is no `value`.
2. In `filterCompiler.ts` compile `relation_is_empty` to `NOT EXISTS` and `relation_is_not_empty` to `EXISTS` over `item_relations` for the property's relation definition and side. The edge only counts when its other end is a live item: join to `items` pinned to the target database id with `deleted_at IS NULL`, using the same partition-pruning shape as #1363. The relation-definition id and the target database id are bound `$N` parameters; only the `item_a`/`item_b` side names are interpolated, taken from the registered definition.
3. Extend the guard in `compileCondition`: the two new conditions are valid only on a relation property (same error as `relation_contains` otherwise), and the existing error message on `is_empty` over a relation now names the new conditions as well.
4. Tests in `filterCompiler.unit.test.ts`, `filterSort.unit.test.ts` and a database-backed test (a new `relationEmptinessFilter.test.ts` next to the one added by #1363) covering the acceptance criteria.

## Scope

### In scope

- The two emptiness conditions, their validation, SQL and tests, in both filter-tree copies.

### Out of scope

- The two-hop path condition: #1363.
- Combining emptiness with area into a declared per-database filter: #1597.
- Facet bucket computation: #1759.
- Changing `is_empty` / `is_not_empty` semantics for scalar properties.

## Acceptance criteria

- When Files are queried with `relation_is_empty` on `projects`, then files with no project are returned, and so is a file whose only project is soft-deleted; a file with at least one live project is not.
- When Files are queried with `relation_is_not_empty` on `projects`, then exactly the complement (within live files) is returned.
- When `relation_is_empty` or `relation_is_not_empty` names a non-relation property, then the request fails with a 400 `ValidationError` on that property.
- When `is_empty` names a relation property, then it is still rejected, and the message points to the relation conditions.
- Both filter-tree copies accept and reject identical inputs for the new types, and the compiled SQL binds the definition id and database id as parameters.
