**Blocked by:** #1519, #1784
**Model tier:** medium

## Context

Model tier rationale: One generic validation in the shared item write path with a clear rule, but it affects every select in every database, so the unchanged-value exemption, writer scoping and a prior data audit need care.

A select or multi-select value is not checked against the property's options when an item is written: `assertWritableProperties` and the rest of `createItemWithClient` and `updateItemWithClient` (`backend/packages/data/src/chokePoint/itemWrites.ts`) look only at ownership and type, so an unknown key such as `"neznamy"` is stored and then shows without a label. #1784 validates sleep values and, to cover select values there, adds a temporary check in the sleep write hooks (`backend/packages/data/src/sleep/sleepWriteHooks.ts`) that this issue replaces.

This issue adds the check for all databases at the choke point. It builds on the writer kind (#1415), the create defaults and title rule (#1389, #1519, which edit the same function) and the per-module pre-write transform (#1422), whose position in `itemWrites.ts` this follows. #1814 adds the same check for Inbox proposals.

Decisions:
- Applies to user and agent writers; system and internal writers are not checked (as with the non-empty title rule), because mail, transcription and similar ingest paths write their own values.
- On update only keys in the patch are checked, and a value equal to the one already stored is accepted, so a client that resends a whole record does not fail on an old unknown value.
- `null` and an empty array clear the value and are accepted.
- Before this change is merged, the implementer runs a read-only audit over the dev database fixtures of unknown select keys and records the count per database in the pull request; no audit code ships. Reason: to know in advance whether any production path writes a non-catalog value.

## Task

Load `state-writes`, `error-handling`, `canonical-keys` and `testing`.

1. In `itemWrites.ts` add `assertSelectValuesKnown(properties, patch, stored, writer)`, called by `createItemWithClient` and `updateItemWithClient` right after `assertWritableProperties` (and after the title rule), for writers of kind `user` and `agent`. For each patched key whose property is a `select`, the value must be `null` or a string in `config.options[].key`; for a `multi_select`, an array of strings each in `config.options[].key`. Violations throw `ValidationError` with `field` the property key and a message naming the unknown value.
2. On update, skip a key whose new value deep-equals the stored one.
3. Remove the temporary select check from `sleep/sleepWriteHooks.ts` and rely on this one; the sleep tests still pass.
4. Tests for REST, an agent `item.patch` and MCP (identical error body): `tags: ["neznamy"]` on Health records fails with 400 `field` `tags`, `["medication"]` passes; a `select` with an unknown key fails on create and update; `null` clears; resending an unchanged unknown stored value succeeds; a system writer (for example mail ingest) is unaffected; a database without select properties is unaffected; the sleep select cases still fail as before.

## Touches

## Scope

### In scope

- The catalog check for select and multi-select values on item create and update by user and agent writers, in every database.

### Out of scope

- Inbox proposal envelopes: #1814.
- Creating missing options: #1699.
- Validating values written by system and internal writers.
- Cleaning up stored unknown values.

## Acceptance criteria

- When a PATCH sets Health records `tags` to `["neznamy"]`, then the response is 400 `validation_failed` with `details.field` `tags`; `["medication"]` is accepted.
- When a patch resends a stored unknown value unchanged, then it succeeds.
- When `null` or an empty array is sent, then the value is cleared.
- When an assistant `item.patch` or an MCP write sends an unknown key, then it receives the same error as REST.
- When a system writer writes an item, then no select check applies.
