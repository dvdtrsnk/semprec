## Context

Model tier rationale: Atomic database, partition and ordered property creation includes tenant-scoped relation guards and REST-only schema authorization. These cross-module contracts warrant the high tier.

`POST /api/databases` (`database.create`) creates a bare database and partition atomically; separate property calls can leave a partial collection. Add an optional ordered list to create all state in one transaction, building on #1528 icon/color. The fixed title is first, then supplied properties. Omission retains bare creation.

Decision: a title property (type `title`, key `name`) is created first, only when `properties` is present (an empty list creates just the title). Its display name is the optional input field `titlePropertyName`, default `"Name"`; the `POST /api/databases` route fills it with `"Název"` for a Czech user. Without `properties` the operation behaves exactly as today.

Decision: only these property types are accepted in the list: `text`, `number`, `select`, `date`, `checkbox`, `url`, `file` and `relation`. Anything else (`title`, `rollup`, `multi_select`, computed types) is a validation error. A relation entry must carry `targetDatabaseId` and `cardinality` (the client sends them), is created unlocked and without an inverse side.

Decision: `properties` is accepted only from a human REST session (`actor.restSession`). A call through the agent-tool or MCP composition roots that includes `properties` is rejected with a forbidden error, because `database.create` is gated by the database-write capability while property creation is gated by the separate schema-write capability.

## Scope

### In scope

- The optional `properties` and `titlePropertyName` input, the single-transaction creation with all-or-nothing behavior, the REST-only restriction and the locale-based title name.

### Out of scope

- Icon and color storage and validation: #1528.
- Inverse relation sides, rollups, multi-select and computed properties on creation: use the existing property endpoints afterwards.
- Letting an agent create a collection with properties: it stays on the separate property operations, which carry the schema-write capability.
- Granting a project agent write access to a collection it did not create: #1810 and #1841.
- Returning the created properties in the create response (the clients read them from the existing properties endpoint).

## Acceptance criteria

- `POST /api/databases` with `{ "name": "Gift ideas", "properties": [text "recipient", date "when", select "status"] }` returns 201; `GET /api/databases/:id/properties` then lists `name` (type `title`, "Název" for a Czech user), `recipient`, `when`, `status` in that order, and the database accepts item writes immediately.
- When the third property has an invalid select config, a duplicate key, or a relation to a missing database, the response is a 4xx error and no database, items partition or property of that request exists afterwards.
- A relation entry without `targetDatabaseId` or `cardinality` is rejected with a validation error naming the missing field; a relation whose target belongs to another tenant fails exactly as an unknown id does.
- An entry of type `rollup`, `title` or `multi_select` is rejected.
- An agent or MCP caller that sends `properties` receives a forbidden error and nothing is written; the same caller creating a bare database still succeeds.
- `POST /api/databases` without `properties` behaves as before (no title property is created).
- Legacy lists retain key order; later ordinary properties follow the positioned initial list in key order. A populated upgrade preserves null legacy positions and previous-release compatible reads/writes.
- A malformed relation target UUID is a field validation error before SQL; valid uppercase IDs work and foreign versus unknown IDs remain indistinguishable.
