**Blocked by:** #1528
**Model tier:** high

## Context

Model tier rationale: It makes one operation write a database, its partition, a title property and several properties (including tenant-scoped relation targets) atomically, and it must keep `database.create` from becoming a schema-write path for agent actors that only hold the database capability, which is an authorization contract; at that uncertainty the higher tier is chosen.

The app's "New collection" form collects a name and a list of properties (Text, Number, Select, Date, Checkbox, Link, Relation, File; the title "Name" is fixed and always first) and saves them together. Today `POST /api/databases` (`database.create`, `DatabaseCreateInputSchema` in `backend/packages/shared/src/genericOperations/schemas.ts`, `.strict()`) accepts only `{ name, parentItemId }`; the database and its `items_p_*` partition are created in one transaction by `createDatabase` in `backend/packages/data/src/chokePoint/databasesStore.ts` (called from `databaseOps.ts`), and it creates no title property. Properties are then added one by one through `POST /api/databases/:id/properties` (`propertiesStore.createProperty`, or `createRelationPropertyWithClient` for relations). That is 1+N non-atomic calls: a failure on the third leaves a half-built collection behind.

This issue adds an additive, optional `properties` list to the create input so the whole collection is created in one transaction, and a failure anywhere creates nothing. It builds on #1528, which extends the same create input with `icon` and `color`.

Decision: a title property (type `title`, key `name`) is created first, only when `properties` is present (an empty list creates just the title). Its display name is the optional input field `titlePropertyName`, default `"Name"`; the `POST /api/databases` route fills it with `"Název"` for a Czech user. Without `properties` the operation behaves exactly as today.

Decision: only these property types are accepted in the list: `text`, `number`, `select`, `date`, `checkbox`, `url`, `file` and `relation`. Anything else (`title`, `rollup`, `multi_select`, computed types) is a validation error. A relation entry must carry `targetDatabaseId` and `cardinality` (the client sends them), is created unlocked and without an inverse side.

Decision: `properties` is accepted only from a human REST session (`actor.restSession`). A call through the agent-tool or MCP composition roots that includes `properties` is rejected with a forbidden error, because `database.create` is gated by the database-write capability while property creation is gated by the separate schema-write capability.

## Task

Load `state-writes`, `error-handling`, `canonical-keys` and `testing`.

1. In `schemas.ts` extend `DatabaseCreateInputSchema` with optional `titlePropertyName` (non-empty string) and `properties`: an array of at most 50 entries, each `{ key, name, type, config? }` for the non-relation types above, or `{ key, name, type: "relation", targetDatabaseId, cardinality }` (`one_to_one`, `one_to_many`, `many_to_many`), using the same per-entry rules as `PropertyCreateInputSchema` minus `databaseId`. Keys within the list must be unique and different from `name`; a duplicate is a validation error naming the key.
2. Add a choke-point operation (in `backend/packages/data/src/chokePoint/databaseOps.ts`) that, in one `withTransaction`: creates the database with `createDatabase` (including `icon`/`color` from #1528), creates the title property, then creates each listed property in order with `propertiesStore.createProperty` or `createRelationPropertyWithClient` (the computed-key collision guard applies), and publishes one schema invalidation for the new database after commit. Any error rolls the whole transaction back, so no database, partition or property remains.
3. In `genericApplicationService.ts` `createDatabase`: when `properties` is present, reject a non-REST actor with a forbidden error before any write, otherwise call the new operation; when absent, keep today's path. The return value stays the `Database`.
4. In `databasesHandler.ts` forward `properties` and `titlePropertyName` from the body on `POST /api/databases`, defaulting `titlePropertyName` from the caller's locale as decided above.
5. Update the generated agent-tool and MCP schema expectations affected by the wider create schema (`mcpGenericOperationsContract.test.ts`, `genericOperationAgentToolsContract.test.ts`, `genericOperationsContract.test.ts`, `operationCatalog.unit.test.ts`, `schemas.unit.test.ts`).
6. Tests: create with a title and three properties returns the database and `GET .../properties` lists the title first, then the three in order; a second property with an unknown relation target, or a third property with a duplicate key or a bad select config, leaves no new database, partition or property; a relation to another tenant's database fails like an unknown id and leaves nothing; an agent actor sending `properties` is forbidden and writes nothing; omitting `properties` still creates a bare database as before.

## Scope

### In scope

- The optional `properties` and `titlePropertyName` input, the single-transaction creation with all-or-nothing behavior, the REST-only restriction and the locale-based title name.

### Out of scope

- Icon and color storage and validation: #1528.
- Inverse relation sides, rollups, multi-select and computed properties on creation: use the existing property endpoints afterwards.
- Letting an agent create a collection with properties: it stays on the separate property operations, which carry the schema-write capability.
- Granting a project agent write access to a collection it did not create: #1810 and #1841.
- Returning the created properties in the create response (the clients read them from the existing properties endpoint).

## Acceptance criteria

- `POST /api/databases` with `{ "name": "Gift ideas", "properties": [text "recipient", date "when", select "status"] }` returns 201; `GET /api/databases/:id/properties` then lists `name` (type `title`, "Název" for a Czech user), `recipient`, `when`, `status` in that order, and the database accepts item writes immediately.
- When the third property has an invalid select config, a duplicate key, or a relation to a missing database, the response is a 4xx error and no database, items partition or property of that request exists afterwards.
- A relation entry without `targetDatabaseId` or `cardinality` is rejected with a validation error naming the missing field; a relation whose target belongs to another tenant fails exactly as an unknown id does.
- An entry of type `rollup`, `title` or `multi_select` is rejected.
- An agent or MCP caller that sends `properties` receives a forbidden error and nothing is written; the same caller creating a bare database still succeeds.
- `POST /api/databases` without `properties` behaves as before (no title property is created).
