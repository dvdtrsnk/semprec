## Context

Model tier rationale: A new notification kind with a database constraint change and one producer hook, relying on the problem writer from its blocker, so exact call sites carry some uncertainty.

Assistant problems (failed sync, a stuck assistant, repeated failures) are tracked as deduplicated problems by #1459: one problem per source, raised through `raiseProblem`, each with a `severity` stored in `semp_problems`. The source events still write their own notifications (for example `mail_sync_error` on every failed job), so four sync failures of one mailbox would send four pushes. The design wants one push per problem.

Decisions: a new kind `semp_problem` is written by `raiseProblem` only when a problem is created or when an existing problem's severity increases; its severity comes only from `semp_problems.severity` (an expired sign-in is a critical problem like any other); its `transition_instance` is the problem id plus the severity so another raise at the same severity creates no new `semp_problem` notification or additional push; distinct occurrences still update problem bookkeeping and source notifications remain governed by their producers; its category is `problems` and the push filter of #1443 applies to it. Source notifications of problem kinds are still stored but are no longer pushed (`push: false` in the kind policy of #1440 for problem kinds other than `semp_problem`).

Title decision: use the generic localized `notification.semp_problem.title` catalog entry without problem-specific title parameters. The current `raiseProblem` input and stored row contain no problem title; detailed problem text is a separate read-time concern. Do not synthesize a notification title from internal kinds, source identifiers or provider text. See `issues/batches/backend/decisions/batch-08-spec-reconciliation.md`.

## Acceptance criteria

- When a problem is created, then exactly one `semp_problem` notification is written and pushed according to its severity and the user's preferences.
- When four sync failures of one mailbox occur, then one push is sent.
- When the same problem is raised again at the same severity, then no new `semp_problem` notification or additional push is produced. A distinct occurrence still updates the problem bookkeeping, and source notifications may still be stored by their producers. Repeating an identical `occurrenceKey` retains gh-1459's existing replay semantics; no blanket absence of SQL writes is claimed.
- When a problem's severity rises, then one new notification is written.
- When a `*_resolved` notification is written, then it is never pushed.
- For users with locale `cs` and `en`, the actual `raiseProblem` notification and its fan-out payload use the respective generic `notification.semp_problem.title` catalog text. The title contains no unresolved placeholder, internal problem kind, source identifier or provider text; existing severity, deduplication and preference rules remain unchanged.
