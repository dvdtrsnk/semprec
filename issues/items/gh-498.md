## Context

#500 rebuilds `createChokePoint()` in `backend/packages/data/src/chokePoint/chokePoint.ts` as a composition of per-domain section objects. Composing them with object spread (`{ ...a, ...b }`) would let a later section silently overwrite an earlier section's method of the same name. The result would be a choke-point method quietly replaced by another, with no error. This issue delivers the merge helper that turns such a collision into an immediate error. #500 is its first caller.

## Task

Create `backend/packages/data/src/chokePoint/mergeOps.ts` with `export function mergeOps(...parts)`:
- Typed so that the result is the intersection of the parts' types. A call with zero parts returns an empty object type.
- At runtime, it throws an `Error` whose message names the key when any own enumerable key appears in more than one part.
- Otherwise it returns a new object with every part's own enumerable properties. It never mutates a part.

Add unit tests in `backend/packages/data/src/__tests__/mergeOps.unit.test.ts` (unit tier: nothing that touches Postgres):
- disjoint parts merge, and each method keeps its `this`-free behavior;
- a duplicate key throws, and the message contains the key;
- zero parts and one part;
- the parts are not mutated.

## Touches

- backend/packages/data/src/chokePoint/mergeOps.ts (new file)

## Scope

## Acceptance criteria

- `pnpm run verify` in `backend/` passes.
- The unit tests above pass. A TypeScript check in the test, for example an `expectTypeOf` or an assignment, shows that `mergeOps({ a: () => 1 }, { b: () => "x" })` has both `a` and `b` with their original types.
