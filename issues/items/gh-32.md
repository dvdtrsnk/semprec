**Blocked by:** #31

## Context

Pi-agent-core so far (issues #30-31) handles agent-run lifecycle, budgets, and MCP integration/tools. The decision logic for what an agent is allowed to do has several layers, and this issue introduces the last of them:

- **Layer 1** — a binary, synchronous grant check at the whole-project level (e.g. `capabilities.email.send.autonomous`, yes/no, no waiting state). It answers "is this project even allowed to use this tool autonomously at all."
- **Layer 2** — structural separation of the kind Semprec's `confirm` uses for the Inbox: the AI never holds write authority itself, no matter what has been granted.
- **Layer 3** — sandboxing (process/subprocess isolation of a tool at runtime) — consciously deferred to v2, out of scope for this issue.
- **Layer 4** (this issue) — the **approval queue**. It handles a third, different case than layers 1-2: the tool *is* available and *is* granted at the project level, but this particular call is risky enough (`ModuleManifest.agentTools[].requiresApproval` + `riskClass`, fields the manifest already carries) that it deserves a judgment call on this **specific instance** of the call — deleting this particular item, paying this particular amount — not just a static project-wide yes/no.

The difference between "per-instance" and "per-project": layer 1 asks "is this project even allowed to delete/pay at all" (once, statically, at the configuration level). Layer 4 asks "is exactly this action, with exactly these arguments, allowed to happen right now" (every single time, at the level of one tool call).

## Task

Implement the approval queue as the fourth decision layer in pi-agent-core:

1. An `approval_requests` table as the waiting state for risky tool calls.
2. A choke-point handler in the MCP-invoke layer that, for a `requiresApproval` tool, reacts by inserting a row and immediately, synchronously returning a synthetic result — never by waiting.
3. A choke-point "Approve"/"Reject" action available only to a logged-in user, with an atomic state transition.
4. A `TASK_NAMES.approvalExecute` job (the name is already reserved in the task catalog) that is enqueued exclusively on approval and performs the deferred call.
5. A global, system-wide (not per-project) overview of pending requests.

### Data model

```sql
CREATE TABLE approval_requests (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  agent_run_id uuid NOT NULL REFERENCES agent_runs(id),
  tool_name text NOT NULL,
  risk_class text NOT NULL,          -- snapshot from the manifest at request time; does not change even if the manifest shifts later
  payload jsonb NOT NULL,            -- exactly the choke-point call (resource + arguments) that would be executed
  status text NOT NULL DEFAULT 'pending',   -- 'pending' | 'approved' | 'rejected'
  requested_at timestamptz NOT NULL DEFAULT now(),
  decided_at timestamptz,
  decided_by uuid REFERENCES users(id)
);
```

### Mechanism — key architectural points

**Never enqueue until a decision has been made.** `graphile-worker` has no primitive for "job waits on an external event" (verified directly in its documentation) — only `runAt`, time-based polling. The correct shape is therefore not "enqueue a job, keep it paused" but "nothing goes into the queue until it has been decided." A `requiresApproval` tool call reacting at the choke point only inserts an `approval_requests` row (`pending`) — creating the request itself enqueues nothing. Only **on approval** is the `TASK_NAMES.approvalExecute` job enqueued — a name the task catalog already reserved.

**No expiry.** A request has no time limit after which it automatically lapses — it stays `pending` until a human actively resolves it, no matter how long that takes (the same rule as the delegated-session and Semp-conversation memory policy elsewhere, just applied to waiting for a decision instead of waiting for the next message). No expiry job, no `expired` state — one fewer moving part that would run continuously and not solve anything essential.

**Atomic, choke-point decision.** The decision ("Approve"/"Reject") is a choke-point action callable only in the context of a logged-in user (the same restriction as `confirm` for the Inbox and the `email.send` grant check), and it changes state atomically via `UPDATE approval_requests SET status = ... WHERE id = ... AND status = 'pending'` — the same `ifVersion`/optimistic pattern used elsewhere for concurrent writes. A second click on an already-decided request simply updates no row — there is no need for special-case handling of "already decided." Note that authentication itself only arrives in issue #34 — until it lands, the "logged-in user" restriction is unenforced by design (the whole system still runs open), and #34 retrofits enforcement in front of this action along with every other endpoint.

**Rejection = default nothing happens.** On approval, the `approvalExecute` job is enqueued, performs the deferred choke-point call from `payload`, and flips the row to `approved`/executed. On rejection, no `approvalExecute` job is ever created — the default is that **nothing happens** until someone actively approves, the exact opposite of the OpenClaw default "YOLO mode" (`approvalPolicy: 'never'` as the default for local sessions, per its own documentation) — considered and rejected as a model to follow.

**KEY DECISION — a turn is never literally paused; execution is fully disconnected from the conversation.**

The tool-calling protocol (identically in the Anthropic and OpenAI shapes that `pi-ai` builds on) requires this structurally: an assistant message with N `tool_use` blocks must get back N corresponding `tool_result` blocks **all at once** before the conversation can continue with another turn — it is not possible to send three results now and a fourth an hour later. This is confirmed by what was already verified in the pi source regarding parallel tool calls: `executeToolCallsParallel` waits on a single `Promise.all` across the whole batch. So when an agent calls several tools in parallel in one turn and only one of them requires approval, that one call cannot block the rest of the batch or wait on a human — it must return a result immediately, exactly like the others.

The MCP-invoke handler therefore reacts to a `requires_approval` tool purely synchronously: it inserts an `approval_requests` row (`pending`) and immediately returns a synthetic `tool_result` ("awaiting approval, request ID X") — not an error, not a wait, just a different kind of successful result. The turn completes normally (the agent typically responds with something like "I've submitted the payment for approval") and the `agent_run` ends normally, `status = 'done'` — **no** additional new state, because from pi's point of view this particular run genuinely ran to completion; nothing inside it is waiting.

The actual execution at decision time is therefore completely **disconnected** from this conversation — it is neither a continuation of it nor a reconstruction of it (an earlier version of this block got this wrong; it is corrected here): the `approvalExecute` job, on approval, only performs the deferred choke-point call from `payload` and flips the row to `approved`/executed. No new `Agent` instance is created, nothing is injected back into any turn — the `agent_run` in question is long since closed and stays that way. The result is written to the audit trail (`approval_requests` plus the corresponding choke-point write); Semp does not actively hear about the outcome — the `agent_run` is long closed, nothing in it is waiting for a reply. The user does, however: the **creation** of the request itself also creates a row in `notifications` (an earlier version of this paragraph claimed no notification infrastructure would exist due to push-notification limitations for a server without a public domain/TLS; that limitation was since removed elsewhere, so the claim no longer held). As a result, the 24-hour memory policy described elsewhere in pi-agent-core does not apply here either — for the approval queue there is nothing to hold in memory or reconstruct, because the turn that triggered the request is already finished at the moment the request is created.

**A global list, not per-project.** Approval is a systemic human responsibility, not a property of one project — a request could have originated from any project's agent. Semprec therefore gets one central place in the navigation (alongside the VIZE/MOCK/BACKEND pattern of this page) with all `pending` `approval_requests` rows across the whole system, not a partial list tucked away on the page of the agent that raised it — otherwise the user would have to know which project to check just to find out that something is waiting. Each list item links back to the project/`agent_run` it came from (context for "why did the agent even call the tool"), but the overview itself — "what am I waiting on" — is one, system-wide.

## Scope

### In scope

- Migration/table for `approval_requests` per the schema above.
- Choke-point handler in the MCP-invoke layer: detecting `requiresApproval`/`riskClass` from the manifest, inserting the row, returning the synchronous synthetic `tool_result`.
- Approve/Reject choke-point action with atomic `UPDATE ... WHERE status = 'pending'`, restricted to a logged-in user.
- Job handler for `TASK_NAMES.approvalExecute`: performing the deferred call from `payload`, transitioning to `approved`/executed.
- Global, system-wide overview of pending (`pending`) requests in Semprec's navigation, linking back to the source project/`agent_run`.
- Creating a `notifications` row when a request is created.
- Ensuring an `agent_run` completes normally (`status = 'done'`) even when it contains a pending approval — no new run state.

### Out of scope

- The sandbox layer (layer 3) — runtime process isolation of a tool, consciously deferred to v2. The approval queue answers "should this action be allowed to happen at all" (once, before execution); the sandbox would answer "what is the action allowed to do while it runs" (continuously) — a different question, a different mechanism.
- Any expiry/timeout mechanism for `pending` requests — consciously left out, see above.
- A chat message (DM reply) as the authoritative source of a decision — considered and rejected (see below).
- Notification delivery channels beyond the existing `notifications` row (the specific push/email channel is handled elsewhere).
- Anything related to isolating the whole server from the outside world (single public process behind Caddy) — a different boundary, a different mechanism, handled elsewhere.

Considered and rejected: using a chat reply (DM reply) as the authoritative decision source, following the pattern of Hermes's "DM pairing." Verified that Hermes's "DM pairing" actually only handles device-identity pairing, not approval of an individual action — the real approval flow is a separate, chat-reply-driven mechanism with its own documented race conditions (a second pending request in the same session is silently dropped; FIFO decision-making ignores which specific request the user actually replied to) and a split state between the MCP reply and the authoritative approval state (`resolved: true` can come back while the real approval remains `pending`). Semprec already has exactly one source of truth — `approval_requests.status`, changed only through the choke point — and a chat/push notification (wherever Semprec sends notifications in the future) may only *reference* this row, never itself decide; otherwise it would create exactly the two parallel, divergence-prone sources of truth that the Hermes bug demonstrates as a real risk, not a theoretical one.

## Dependencies

- **Issues #30–#31** (agent-runtime lifecycle/budget, MCP integration/tools): the approval queue attaches directly to the MCP-invoke handler and references `agent_runs.id` — without them there is no choke point to insert into.

- **Task catalog** — `TASK_NAMES.approvalExecute` must already be a reserved name (it is, per the specification); this issue implements its handler.
- **Optimistic concurrency pattern** (`ifVersion`/`WHERE status = 'pending'`) — a convention introduced elsewhere in the specification, applied here only.
- **`notifications` infrastructure** — must exist so that the creation of a request can create a notification row.
