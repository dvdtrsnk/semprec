## Behavior specification

Areas and projects: properties, rules, overview and related items.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: areas-projects-1

#### (a) Adopted decisions
- Seed default areas for new tenants? -> Decided by the product owner: only the system area "(unplanned)", which statistics need and which is excluded from them, is created for every tenant; all other areas are created by the user (lean v1). Built by #1997; user areas are not seeded.
- Does the user reorder areas? -> no UI/API now; a new area gets position = max + 1 on create (serialized by an advisory lock), explicit position kept -> matches the "new = last" lean in both area notes.
- icon/color null? -> allowed, means client default -> notes say null = default.
- Color list -> the 9 hex values (4 overview + 5 more of the inbox-card palette), case-insensitive compare -> closed list from the notes.
- Area `active` backfill meaning "no value" -> key absent or null; explicit false untouched.
- Company/health-record cardinality -> one_to_many with the area as the "one" side, existing edges stay valid.
- Area note conversion marker -> kept inside the area's Yjs doc (`meta` map: legacyNoteSource, legacyNoteBlockIds); later legacy edits replace only generated blocks; tier raised to high.
- Related counts vs click-through -> count equals the returned filter's content, no default quick filter added by clients (the note's recommended option).
- Archived databases in related rows -> excluded.
- Related Mail row click-through -> filter null; client uses thread query params with the record id.
- Related order storage -> `relatedOrder {order, omit}` on the record type's database descriptor; unlisted collections follow database display order then name.
- delete-impact subtreeItemCount -> included now (cheap, optional for clients).
- Projects: done/archived + pinned true -> 400 field pinned; status change unpins in the same write.
- Long-term kept deadline stored as jsonb in new table project_kept_dates; purge deletes it.
- completedAt -> set on first entry to done/archived (tenant time zone date), kept between done and archived, cleared when reopened, no backfill; ownerProcess `systemDatabases`.
- Planned status for projects -> Decided by the product owner: no new status; the design data is corrected to an existing status, and the status catalog stays `inProgress`, `longTerm`, `done`, `archived`.
- Subtitles such as "every month", "gifts 2 of 6", "start 2 Nov" -> Decided by the product owner: the subtitle is derived by one general rule from existing properties (recurrence, start date, task progress); no summary property is added. No backend issue: the inputs are existing properties and the generic grouped count.
- Company and colour of a project -> Decided by the product owner: they are set as ordinary properties (`company`, `color`) in the project detail; no dedicated endpoint.
- completedAt for already finished projects -> Decided by the product owner: not backfilled; the date is written on the next completion.
- Hand-written area note text after the legacy note changes -> Decided by the product owner: never overwritten; only generated blocks are replaced, hand-written text is the user's own value.

#### (b) Open questions remaining for the product owner
- None.

#### (c) User-visible behavior
Areas get an icon from a fixed set, a color from a fixed palette and a position, so the overview can list them in a chosen order with their own look. Every tenant has one system area "(unplanned)" that cannot be deleted and is left out of statistics; all other areas are created by the user. New areas are active by default and appear on the overview; deactivating one hides it but changes nothing else. An area can hold several companies and several health records (each still belongs to one area). The area note becomes the area's page, converted once from the old note text. Every record page can show a "related" list: how many connected records each collection has (including tasks and events reached through projects), in a sensible fixed order, and tapping a row opens that collection filtered to those records; agents see only collections they may access. Before deleting something the app can show what the deletion affects (connected records, nested records, subpages, links). Finished or archived projects are unpinned automatically and cannot be pinned, long-term projects hide their deadline and get it back when they return to active work, and finished projects remember when they were completed.


### Decisions: areas-projects-2

#### (a) Adopted decisions
- Pinned project order mechanism (pinnedOrder vs curated view vs title) -> `Projects.pinnedOrder` number property; new pin goes last, unpin clears it, cutover numbers existing pinned projects by title -> simplest explicit option, no extra view concept. -> Decided by the product owner: pinnedOrder holds the order and unpinning clears it.
- Area overview horizon -> 14 days counting today -> the proposal in the notes. -> Decided by the product owner: the horizon is 14 days for "Upcoming" and "Events soon".
- Events in the overview -> counted/listed when they start from now to the horizon end; events already running need an event end field delivered elsewhere.
- Overview counts and limit -> counts computed before the 20-entry limit; "today" in the tenant time zone.
- Eligible projects -> live, not archived, not systemActive; active project = inProgress or longTerm.
- Open tasks of done projects in openTaskCount -> Decided by the product owner: they count; only archived, system and soft-deleted projects are excluded, so open tasks do not silently disappear because a project is finished.
- Inconsistent area and collection counts in the design data -> Decided by the product owner: the owner unifies the design data against one canonical sample data set; until then the implementation and its tests follow the stored data, not the numbers in the design.
- Area overview route lives in the systemDatabases manifest (customRoutes, single-consumer-read) per the program decision.

#### (b) Open questions remaining for the product owner
- Realtime invalidation for moved tasks/area changes is delivered by the relation-invalidations issue; the overview issue has no dependency on it, so confirm it should be listed as a blocker of the client work, not of this issue.

#### (c) User-visible behavior
An area page shows how many active projects it has, tiles for tasks due today and all open tasks, how many events are coming, and a chronological upcoming list of tasks and events from the area's projects with each project's color, computed in the user's time zone. The overview lists pinned projects in the order they were pinned; finished projects drop off, and re-pinning puts a project last.
