## Context

Model tier rationale: One schema change with a tenant-composite key and a unique index, following the existing 0083/0084 pattern, plus a narrow store seam, with no new authorization or concurrency contract of its own.

A failed agent run cannot be tried again as a linked successor. `agent_runs` (`backend/packages/data/src/db/migrations/0001_core_schema.sql` and later) has `parent_run_id` for delegation and `heartbeat_id`, but nothing says "this run is the second attempt of that run". `createAgentRun` in `backend/packages/data/src/agentRuns/agentRunsStore.ts` inserts a root row with no such link, and `AgentRunRow` has no attempt number.

Retrying a failed tick run, and showing a run's retries as one row with "second attempt", both need a chain of attempts: each retry points to the run it retries and carries its attempt number. This issue adds that chain to the data model and a store seam to write and read it. #1458 fills the chain for the queue's automatic attempts, #1908 writes it for a user-requested retry, and #1911 and #1915 use it to decide whether a failure was recovered.

Decision: the chain is linear. A run can be retried at most once, enforced by a unique key, so two concurrent retry requests for the same run create one successor. The link is a tenant-composite reference like the other run references (`agent_runs_parent_run_id_tenant_fkey` in 0083), so a link can never cross tenants.

## Task

Load `db-migrations`, `state-writes` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_agent_run_retry_chain.sql` (next free ordinal at commit time): add `retry_of_run_id uuid` and `attempt integer NOT NULL DEFAULT 1 CHECK (attempt >= 1)` to `agent_runs`; add the composite foreign key `(tenant_id, retry_of_run_id) REFERENCES agent_runs (tenant_id, id)` as `NOT VALID`; create `UNIQUE INDEX agent_runs_tenant_retry_of_run_id_uq ON agent_runs (tenant_id, retry_of_run_id)` (nulls stay distinct, so non-retries are unaffected). A second migration file `NNNN_validate_agent_run_retry_chain.sql` validates the key, as 0083 and 0084 do. Both are additive. The `agent_runs_tenant_id_id_uq` parent key already exists (0064).
2. In `agentRunsStore.ts`, add `retryOfRunId: string | null` and `attempt: number` to `AgentRunRow` and `AGENT_RUN_ROW_COLUMNS`, and optional `retryOfRunId` and `attempt` to `CreateAgentRunInput`; `createAgentRun` writes them (defaults: null and 1).
3. Add `createChainedAgentRun(client, input)` (same file) that requires `retryOfRunId`, inserts with `ON CONFLICT (tenant_id, retry_of_run_id) DO NOTHING` and returns the new row, or `null` when the run was already retried. The new run takes its `actor_user_id` from the retried run.
4. Add `getRetrySuccessorId(client, runId): Promise<string | null>` returning the id of the run whose `retry_of_run_id` is `runId`, or `null`.
5. Check every existing `INSERT ... ON CONFLICT` on `agent_runs` against the new unique index (the db-migrations skill requires this); there is currently none, and the pull request says so.

## Scope

### In scope

- The `retry_of_run_id` and `attempt` columns, the tenant-composite key, the unique successor index, and the store functions to create a chained run and read a run's successor.

### Out of scope

- Linking a heartbeat run to its occurrence and chaining the queue's automatic attempts: #1458.
- The retry endpoint, its eligibility rules and error codes: #1908.
- Retrying a Semp chat reply (it uses an attempt number on the reply itself): #1926.
- Showing the chain in run lists: #1914.

## Acceptance criteria

- When a run is created without a link, then `attempt` is 1 and `retryOfRunId` is null.
- When a chained run is created for a run that has no successor, then it is inserted with the given `attempt`; when it is created again for the same run, then `createChainedAgentRun` returns `null` and no second row exists.
- When two chained runs for the same run are created concurrently, then exactly one row is inserted.
- When a chained run points to a run of another tenant, then the insert is rejected by the database.
- `getRetrySuccessorId` returns the successor's id, or `null` for a run that was not retried.
- A migration run against a database with existing runs succeeds and leaves them as attempt 1.
