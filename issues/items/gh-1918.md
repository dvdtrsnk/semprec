## Context

Model tier rationale: Two id-less user-narrowed scopes on the established realtime catalog with a handful of write sites that must be enumerated from the counting function, following the pattern of the preceding scope issues.

A user can change notification preferences on one device and see the change on another, and the app badge and the per-tab counts change when the number of pending decisions changes. Nothing signals either today. This issue adds two realtime scopes, `notificationPreferences` and `badgeCounts`, both without payload fields, following exactly the shape and wiring of the earlier scopes in this chain (see #1868): the `invalidation` message type with a `scope` discriminator in `backend/packages/realtime/src/pgNotifyPublisher.ts`, the `OutboundFrame` variants in `protocolV1.ts`, the `InvalidationEvent` variants in `backend/packages/data/src/realtimeHook.ts`, the mapping in `syncServer.ts` and the parser in `backend/packages/realtime-client/src/serverFrame.ts`. Rules of `docs/adr/2026-10-16-tenant-scoped-realtime-fan-out.md` apply: thin payload, tenant from Postgres, no replay, publish only after commit with `runAfterCommit`.

Both frames are narrowed to the sockets of the user they concern (`userId` set), since preferences and counts are per user.

- `notificationPreferences`: published when a user's stored notification preferences change, from the preference store delivered by #1441.
- `badgeCounts`: published whenever an input of the pending-decisions count defined by #1828 changes for a user. The implementer lists those writes by reading the queries of that counting function (a pending approval request appearing, being decided or terminalized, and the other states it counts), publishes next to each of them, and names them in the pull request. A write that does not change the count still may publish; a missing publication is the defect to avoid.

Reading the new numbers stays REST: the client refetches the preference and count endpoints. The next scope in the chain is the account scope #1946.

## Task

Load `state-writes`, `canonical-keys`, `io-hardening` and `testing`.

1. Add the two variants to `InvalidationEvent` (with `userId`), `RealtimeMessage` (+ `parseRealtimeMessage`), `OutboundFrame` (`{ type: "invalidate", scope: "notificationPreferences" }` and `{ type: "invalidate", scope: "badgeCounts" }`), the `invalidation` case of `syncServer.ts` (call `sendToTenant(tenantId, frame, parsed.userId)`), and `parseServerFrame`.
2. Create `backend/packages/data/src/notifications/notificationInvalidation.ts` exporting `publishNotificationPreferencesInvalidation(client, userId)` and `publishBadgeCountsInvalidation(client, userId)`, each deferring `notifyInvalidation` with `runAfterCommit`.
3. Call the first from the preference write of #1441; call the second next to every write that changes an input of the count from #1828.
4. Tests: a frame to the user's sockets for each publication; another user or tenant gets nothing; rollback sends nothing; a test per counted input write.

## Scope

### In scope

- The `notificationPreferences` and `badgeCounts` scopes end to end and their publication on preference changes and count-input writes.

### Out of scope

- Storing preferences: #1441; counting pending decisions: #1828.
- Pushing the badge number inside APNs payloads.
- The account scope: #1946.

## Acceptance criteria

- When a user changes notification preferences, then that user's sockets in the tenant receive `invalidate` with scope `notificationPreferences`.
- When a write changes the pending-decisions count of a user, then that user's sockets receive `invalidate` with scope `badgeCounts`.
- When a different user of the tenant or a socket of another tenant is connected, then it does not receive either frame.
- When the transaction rolls back, then no frame is sent.
- Neither frame carries any field besides its type and scope.
