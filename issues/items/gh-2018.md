## Context

Model tier rationale: It widens what an agent run may read across project boundaries, an authorization rule with a sensitive-data exception that depends on the grant model, so a missed case would leak another project's run results.

Schema Core declares the read-only agent tools `heartbeat.list` and `heartbeat.history` and the write tool `heartbeat.trigger` (`backend/packages/data/src/scheduler/heartbeatAgentTools.ts`). All three derive the project only from the persisted `agent_runs.project_item_id` of the calling run (`resolveCallingProjectItemId`) and accept no project id, so a run can see only its own project's heartbeats. #1523 composes these tools into agent sessions and keeps that rule. Semp chat runs belong to the system project Semprec and are linked to their Semp thread through `agent_runs.thread_id` (#1452).

Decision: chat is the general place for questions, so a run of a Semp thread of kind `chat` reads the heartbeats of every project of the tenant (read only), for example the weekly journal cleanup. `heartbeat.trigger` keeps the own-project rule for every run, and runs that are not chat runs keep seeing only their own project. Heartbeats of a sensitive project are left out unless access is granted: a heartbeat is omitted when its project holds a grant (`agent_database_grants`, #1810) on a database flagged `sensitive` (#1808) and the calling run's project holds no grant on that database, because the heartbeat's run results could reveal that data.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In `heartbeatAgentTools.ts` add a scope resolver used by `heartbeat.list` and `heartbeat.history`: when the calling run's `thread_id` points at a Semp thread of kind `chat` (delegated runs inherit the thread, #1452), the scope is every project of the tenant minus the projects excluded by the sensitive rule above; otherwise it is the run's own project as today. The project is still never taken from the tool arguments.
2. `heartbeat.list` in the tenant scope returns every heartbeat of the projects in scope, each entry with `projectItemId` and `projectName` added; `heartbeat.history` accepts a `heartbeatId` of any project in scope and answers an id outside the scope with the same not-found error as an unknown id.
3. `heartbeat.trigger` is unchanged: it stays limited to the calling run's own project for chat runs too.
4. Tests: a chat thread run lists the heartbeats of the Semprec project and of another project with their project names; it reads the history of the other project's heartbeat; a heartbeat of a project that holds a grant on a sensitive database is absent for a chat run whose project has no grant on it and present when it has one; an item thread run and a heartbeat run still see only their own project; `heartbeat.trigger` of another project's heartbeat from a chat run gives the not-found error; another tenant's heartbeats never appear.

## Touches

## Scope

### In scope

- Tenant-wide, read-only heartbeat visibility for Semp chat runs, with the sensitive-project exception.

### Out of scope

- Composing module tools into sessions; #1523.
- Triggering another project's heartbeat from chat (not allowed).
- The grant model and the sensitive flag themselves; #1810 and #1808.

## Acceptance criteria

- When a Semp chat run calls `heartbeat.list`, then it gets the heartbeats of every project of the tenant with their project names, except those of a project with a sensitive-database grant the chat run's project lacks.
- When a chat run calls `heartbeat.history` for another project's heartbeat, then it gets that heartbeat's runs.
- When a run that is not a chat run calls either tool, then it sees only its own project's heartbeats, as before.
- When a chat run calls `heartbeat.trigger` for another project's heartbeat, then it gets the not-found error and nothing is triggered.
