## Context

Model tier rationale: Production tenant-isolation security sign-off requires independent adversarial review and verification of deployment, rollback, key erasure and restore invariants.

**This issue is supervised and accepted by the parent controller thread thr_pz39tcih5r under the owner's explicit delegation.** It is the evidence-based security gate before a second account can exist. Independent review is performed in a separate agent context, not by the implementing worker. No human-signature-only stop applies to this backend program. Recovered local code already contains #1087's guard-drop migration and invitation route. A fully migrated local database therefore is not physically protected by that removed index. The production second-tenant gate remains an operational prerequisite; its sign-off has not been granted by local implementation or this source approval.

Going live is safe only when all of the following are true at once: strict enforcement runs in production and a one-release rollback would also land on strict code (`deploy.sh --rollback` targets only the release directly before the newest, `docs/adr/2026-09-24-rollback-one-release-back-with-checked-migrations.md`); the database invariants hold (#1085 checks them at every deploy); the host is hardened (#996–#1074); export, deletion and restore behave as specified (#1043–#1078); and someone other than the implementers has attacked the design. The approved specification accepts that deleted content stays in encrypted backups until their 12-month retention expires, while a deleted tenant's secrets become unrecoverable within 7 days (its `tenant_keys` are excluded from the long-retention backup, #1064) and a restore replays the `tenant_deletions` ledger (#1078).

`docs/operations/tenancy.md` was created at the release checkpoint (#1058); this issue adds its `## Security gate` section.
