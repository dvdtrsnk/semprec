## Behavior specification

Choke point: pre-write transforms, edge/delete/restore hooks and writer kind.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: choke-point-hooks-1

#### (a) Decisions adopted

- Where does a transform's lock apply? -> Row lock (`lockItemById`) whenever the database has any registered pre-write transform -> the transform contract hands it `stored`; Tasks updates therefore lock on every update, not only on `timeFrom`/`timeTo` writes (values unchanged).
- Which keys do rollup recompute and the timezone check use after a transform? -> Keys of the transformed patch -> the design note says rollups receive the prepared patch; side effect: Tasks `time` is now a recognized written key.
- Does a transform get `writerKind`? -> Not in #1422; added by writer-kind 01 only if #1422 lands first (design note wording) -> avoids a dependency edge #1422 -> writer-kind.
- Edge-changed `op` for repeated create of an existing edge -> `create` (the call site cannot distinguish); `delete` only when an edge was actually removed, none for a missing edge -> keeps the contract simple and avoids noisy hooks.
- Recursion on the same relation -> a small re-entrancy check in the runner that throws -> design note says a hook must not recursively change the same relation; a loud failure beats a stack overflow.
- Delete/restore hook scope -> delete hook per newly soft-deleted row, restore hook only per actually restored row of the same epoch, both with the shared `deletedAt`; purge excluded -> design note wording, purge is a different path.
- Who threads `writerKind` into trash entry points? -> writer-kind 01 (accepts and carries it), #1601 consumes it -> keeps #1601 free of signature churn.
- Default writer when nothing is passed -> `system` -> conservative for internal callers.
- Inbox proposal confirm -> `user` for the whole transaction (design note decision); approved agent op via `approvalExecute` -> `agent` with request's run id.
- Is a write through `/mcp` with a human session a user or an agent write? -> Decided by the product owner: an agent (MCP client) write bound to the user whose session it is (`writerKind: 'agent'` without run ids, `onBehalfOfUserId` set); everything written through `/mcp` is written by a tool, and an audit of what Semp or an agent changed must not hide it. Only a human REST session is `user`. (#1415)
- Tiers: #1422 high (new write-path/ownership contract, lock, replay; tier_hint was null), #1530 medium, #1601 medium, writer-kind medium (as hint).

#### (b) Open questions for the product owner

- None blocking. Technical question left to the implementer of #1422: whether Tasks `time` rollups should now recompute on writes (adopted: yes, because the transformed patch drives them); if tests show a behavior change in an existing Tasks rollup, flag it in the PR.

#### (c) User-visible behavior

This chunk shows nothing directly in the UI. It gives the backend three shared building blocks that later features rely on: values can be normalized or derived just before an item is saved (so times like "9:00" are stored as "09:00" and derived values such as a task's time are consistent however the item was written), the system can react inside the same save whenever a link between two items is created, changed or removed, and it can react whenever an item and everything nested under it is moved to the trash or restored, with the ability to refuse the action. Every write also records whether a person, an agent acting for a person, or the system made it, so later features can treat manual changes, Semp's changes and automatic changes differently (for example in approvals and in keeping inherited values in sync).
