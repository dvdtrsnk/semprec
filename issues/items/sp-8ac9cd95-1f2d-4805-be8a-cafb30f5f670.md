## Context

Model tier rationale: One known mechanism (a universal link into a new screen) across the Apple entitlements, the app's URL handling, one shared use case with its ViewModel and one SwiftUI screen; the server endpoint already exists.

The owner moved the dev server behind `alldots.app` (a Cloudflare Worker proxies `alldots.app`, `api.alldots.app` and redirects `www.alldots.app` to the server). The server serves `/.well-known/apple-app-site-association` on these domains with `applinks` for `CX4M83TG32.cz.alldots.app` and one component: `/` with the query `page=password-reset` (the password-reset link). The server mails the link as `<APP_BASE_URL>/?page=password-reset#token=<token>` and consumes it with `POST /api/auth/password-reset/consume` `{ "token", "newPassword" }`, answering 400 with codes `password_reset_token_invalid`, `password_reset_token_expired`, `password_reset_token_consumed` (and a validation error for a weak password) — see `web/src/api/authOperations.ts` and `backend/packages/data/src/auth/passwordResetActions.ts`. The Apple app can request a reset link (Profile) but cannot open one: it declares no Associated Domains and handles no universal link, so today the link only works in the browser. If the app claimed the domain without handling the link, the reset would break, so both land together.

## Task

1. Add the Associated Domains entitlement `applinks:alldots.app` to the iOS and the macOS entitlements of the app target (`mobile/apple/Projects/App/Entitlements/`).
2. Handle an incoming universal link in the app scene (SwiftUI `onOpenURL`/`onContinueUserActivity(NSUserActivityTypeBrowsingWeb)`): a URL on `alldots.app` whose query has `page=password-reset` and whose fragment carries `token=<token>` opens a "Set a new password" sheet; any other URL is ignored. The token never appears in logs or analytics.
3. Add a shared use case and ViewModel (`:shared:domain`/`:shared:data`/`:shared:presentation`, exported through the umbrella and a CoreKit bridge) that consumes the token against the server of the link's origin (`https://alldots.app`) with `POST /api/auth/password-reset/consume`, mapping each 400 code to its own failure state and a weak-password refusal to a validation state; success shows a confirmation and lets the person sign in (no automatic sign-in).
4. The sheet: two secure fields (new password, repeat), a submit button disabled while the passwords differ or are empty or while sending, the failure messages, and the confirmation; copy in English and Czech; accessibility identifiers.
5. Record in an ADR (load `adr-conventions`) that the app's only external entry points are the OAuth callback scheme and this one universal link, per `mobile/apple/review-rules/tasks/security.md`.

## Scope

### In scope

- The entitlement, the link handling, consuming the token and the sheet.

### Out of scope

- Android app links, other deep links, changing the server's AASA or `APP_BASE_URL`, signing in automatically after the reset.

## Acceptance criteria

- The built app's entitlements contain `com.apple.developer.associated-domains` with `applinks:alldots.app` on iOS and macOS.
- Opening `https://alldots.app/?page=password-reset#token=abc` shows the sheet; other URLs do nothing.
- A valid token and matching passwords set the password (200) and show the confirmation; each of the three token codes and a weak password show their own message; no request is sent while the passwords differ.
- Shared tests cover the use case's request and every outcome mapping; CoreKit and feature tests cover the bridge mapping and the sheet's states.
