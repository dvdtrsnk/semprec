## Approved behavior specification

### Source behavior: [19/22] Observability — logs, healthchecks, alerting, metrics

## Context

Issues 1–18 built the whole functional Semprec system: the data model, modules, the agent runtime, the REST/WS API, notifications, deployed on a single Linux server (five systemd processes — `semprec-api`, `semprec-agents`, `semprec-transcribe`, `semprec-ai-gateway`, `semprec-mailsync@<id>` — plus a Docker stack for Postgres/MinIO). The system runs headless, with nobody watching a terminal — no one is staring at a console to notice that something crashed or just quietly stopped working.

This issue builds observability on top of that: how to tell the system is running, how to find the cause when it isn't doing what it's supposed to, and how a human finds out without having to actively watch logs. The same yardstick applies here as everywhere else in the project: state is structured data in Postgres, checkable mechanically and readable in the app, not a free-form log someone has to comb through on the hope of finding something. The one thing the database itself cannot cover — Postgres or the entire server going down — gets its own dedicated path out, completely independent of the rest of the Semprec stack.

The next issue (#20, "Operations — Caddy, backups, secrets, provisioning") covers the infrastructure around the running server. This issue is purely the software/code layer of observability built on top of that infrastructure — no overlap with provisioning, backups, or secrets management.

## Task

Implement five connected observability layers over the running five-process + Docker stack.

**1. Structured logging.** A shared `pino` logger module lives in `packages/shared` — each of the five Node processes takes a root logger from it, named for itself, so there's one shared config to run instead of five independent ones. Output goes to stdout only; there are no private log files and no second collection service — systemd/journald is the single collector. Every `semprec-*` unit gets a `SyslogIdentifier` (`semprec-api`, `semprec-mailsync@<id>`, …), so `journalctl -u semprec-agents` is the complete history of one process and a `journalctl -t` filter spans all of them. The Docker stack plugs into the same place via `logging: driver: journald` in the Compose file — Postgres/MinIO logs land in the same journald as the Node processes, one place for the whole server. Retention is configured in `journald.conf` (`Storage=persistent`, `SystemMaxUse=2G`, `MaxRetentionSec=90day`) — logs are diagnostics, not the source of truth (the source of truth for what actually *happened* in the system is the `agent_runs`, `notifications`, `credential_access_log`, and `ai_gateway_calls` tables, which fall under the backup strategy; journald is never backed up at all).

Content is governed by a rule enforced in configuration, not by discipline: what gets logged is identity, not content — `itemId`, not property values; `message_id`, not the email body; a tool's name, not arguments that might carry sensitive data. Secrets never appear at all: `pino`'s `redact` config masks known paths (`*.password`, `*.token`, `authorization` headers) as a backstop, but the primary rule is that a decrypted credential never enters a log call in the first place — access to secrets already has its own structured trail elsewhere, so logging doesn't duplicate it as plaintext. Levels: `info` for lifecycle events, `warn` for recoverable errors (a retry will happen), `error` for definitive failures; `debug` is off by default, togglable per process via `LOG_LEVEL` in `shared/.env` — a process restart, not a redeploy.

Rejected: a log aggregator (Loki/Grafana or ELK) or private log files with logrotate. An aggregator answers "how do I search logs across fifty servers" — Semprec has one server, and `journalctl` with a time/unit filter over it gives the same capability journald already provides for free, so an aggregator would add one or two more running services, its own retention, and its own disk to babysit for nothing gained. Private log files with logrotate are a worse version of the same idea — the app would reinvent rotation, permissions, and fsync handling that systemd already does, and `journalctl` would stop being the one place to look. Revisit only if the server count grows, not before.

**2. Correlation ID.** A single `traceId` field, no distributed-tracing stack. Without correlation, a structured log is just a pile of lines — "everything that happened because of this Inbox item" passes through `semprec-api` (the HTTP write), the Postgres queue, `semprec-agents` (the tick, the agent run), and `semprec-ai-gateway` (the LLM call): four processes, one cause. The chosen solution doesn't copy a distributed-tracing stack (an OpenTelemetry collector would be one more process for a single user) — just one field propagated through paths that already exist:

- **traceId**: a uuid minted at every entry point of the system — an HTTP/WS request in `semprec-api`, a heartbeat-scheduler tick and the start of an `agent_run` in `semprec-agents`, a sync cycle in `semprec-mailsync@`. Inside a process it's carried by `AsyncLocalStorage` and a `pino` child logger — no threading a parameter through every function.
- **across the queue**: processes only talk to each other through Postgres, so the only legal path is the payload — the `enqueueJob` helper stamps `traceId` from the active context into the shared payload envelope automatically, and the `registerTask` wrapper restores it into `AsyncLocalStorage` on the other side. The zod schemas for jobs carry the envelope once, not per job type, so no producer can forget it — nobody writes it by hand.
- **across HTTP to the gateway**: the AI gateway is an HTTP proxy, so `traceId` travels as an `x-trace-id` header and the gateway logs it alongside the `agent_run_id` that `ai_gateway_calls` already carries.
- **bound fields**: alongside `traceId`, the logger automatically carries `agentRunId` (inside a run), the job name + job id (inside a worker), and the mailbox id (inside mailsync) — so `journalctl | grep traceId` returns the complete story of one cause across every unit, ordered by time.

**3. Healthchecks.** `systemd Restart=always` (plus `RestartSec`/`StartLimitIntervalSec`, so a crash loop doesn't spin forever) handles a process that *crashed*. It does not handle a process that's alive but not working — a frozen event loop, a deadlock at startup. Detection follows the same pattern the system already uses for external services: state is materialized in Postgres and checked mechanically, not guessed at.

```sql
CREATE TABLE process_heartbeats (
  process text PRIMARY KEY,     -- 'api' | 'agents' | 'transcribe' | 'ai-gateway' | 'mailsync:<mailbox item_id>'
  pid integer NOT NULL,
  version text NOT NULL,        -- release tag the process is running, so version drift between processes is visible at a glance
  started_at timestamptz NOT NULL,
  beat_at timestamptz NOT NULL
);
```

Each process UPSERTs its own row every **15 seconds** from a plain `setInterval` — deliberately from the event loop, not a separate thread: a frozen event loop stops beating, which is exactly the condition being detected. A beat older than **60 seconds** is stale. This is an honest boundary on what a beat can detect: a dead process and a frozen event loop, nothing more — a process hanging on an `await` for a network connection that's silently dead (typically mailsync with an IDLE socket killed by a NAT timeout without an RST) has a perfectly healthy event loop and keeps beating. That's a third failure class, handled by the mail-sync progress check described under Alerting below, rather than overloading the heartbeat with something it can't measure in principle. The expected set of rows is not a config file but state derived from data, in the same spirit as the module registry's "if a module participates, that's a runtime fact read from the DB": four fixed processes plus one `mailsync:<id>` per active mailbox — a missing beat for an active mailbox means the corresponding `semprec-mailsync@<id>` instance isn't running even though the data says it should be. This is an infra table outside the generic items model, written directly by processes — the choke-point guards user and agent data, not process heartbeats.

Rejected: a systemd watchdog via `sd_notify` (`Type=notify` + `WatchdogSec`). This is the standard systemd answer to a frozen process, and a duplicate one for Semprec: Node has no native `sd_notify` support (it's a unix datagram socket outside the core API), so this would mean either a native addon dependency or spawning the `systemd-notify` binary on every ping — and it would detect the exact same condition (the event loop stopped ticking) that `process_heartbeats` already detects, just without the side benefits of a DB row (app visibility, version drift, the derived set of mailsync instances, an input for alerting). One mechanism that does both, instead of two that overlap. The cost: a stale process won't restart itself, only report — for the rare "hanging but not crashed" state, a notification plus a manual `systemctl restart` is an appropriate response, not a reason to build a second watchdog channel.

Chosen: `GET /healthz` on `semprec-api` — a shallow check plus the freshness of the `agents` beat, because alerting stands on it. This is the only HTTP healthcheck in the system, unauthenticated (returns only `{"status":"ok"}`, no data), exposed over the public domain. It checks exactly two things: `SELECT 1` against Postgres, and the freshness of the `process_heartbeats` row for the `agents` process — otherwise 503. Why `agents` specifically and not all five: `/healthz` has to answer "does the path by which an internal alert reaches me actually work" — and that path runs through Postgres (data), `semprec-api` (WS/push registration), and `semprec-agents` (the heartbeat scheduler plus the graphile-worker consumer, i.e. the notification fanout). When any of those three is down, internal notifications don't arrive — and that's exactly when the external monitor (below) needs to start shouting. An outage of the other processes (mailsync, transcribe, gateway) is, by contrast, an internal degradation: the notification path itself still works, so it reports the outage on its own — `/healthz` doesn't drop to 503 for that, or the external alarm would duplicate what already arrived via push.

**4. Alerting**, split into two paths along a bootstrap problem named up front: the notification channels (in-app WS, web push, APNs) run through `semprec-api` + graphile-worker + Postgres. A hard consequence follows: when api, agents, or Postgres itself goes down, the system cannot tell anyone by itself — a dead messenger can't deliver news of its own death. The cut is drawn exactly along that boundary: everything the notification path is able to report (because it's still alive) goes through it; only the failure of the path itself gets a dedicated external mechanism that depends on none of the Semprec stack.

Chosen — hard failure: a dead-man's-switch. A small systemd timer/service pair (`semprec-deadman.timer`, every 5 minutes) on the same server runs: `curl -fsS https://<domain>/healthz && curl -fsS https://hc-ping.com/<uuid>` — the ping to the external service only fires **when** the public `/healthz` answered 200. healthchecks.io (hosted, free tier is enough for a handful of checks; open source, so self-hosting it later on a *different* machine stays an open path, not vendor lock-in) expects a periodic ping — if one doesn't arrive within its window plus grace period, it sends an alert by email/push through its own infrastructure, which shares nothing at all with the Semprec server. This single dead path covers every hard-failure scenario at once: the whole server died (the timer isn't running), Postgres or agents died (`/healthz` returns 503), api or Caddy died or the TLS certificate expired (curl against the public domain fails — the ping deliberately goes over the domain, not localhost, so it validates the entire chain a real user goes through too). A detection latency of roughly 5–10 minutes is appropriate for a personal server.

An add-on for an immediate signal: every `semprec-*` unit gets `OnFailure=semprec-failping@%n.service` — a one-shot unit that curls the `/fail` URL of the same healthchecks.io check, with the name of the failed unit in the body. With `Restart=always`, `OnFailure` only fires once a unit actually ends up in the `failed` state — i.e. after the restart limit is exhausted, not on every transient crash that systemd already recovered from by itself. No second external service, no private SMTP — same check, a second kind of ping. The ping URL (outbound, low sensitivity — anyone who has it can at most falsely reassure the monitor) lives in `shared/.env` alongside the other bootstrap secrets.

Rejected: an uptime monitor (Uptime Kuma or similar) on the same server, or alerting for hard failures through the system's own `notifications`. A self-hosted uptime monitor on the same machine is structurally blind to exactly the most important scenario — the server itself dying: a monitor that died along with what it monitors doesn't alert. A second server just for monitoring would solve the problem, but at the cost of an entire extra machine to operate for a single user — the dead-man's-switch gives the same guarantee for one systemd timer. And alerting hard failures through the system's own `notifications` is exactly the circular dependency this section names up front: a channel can't be both the thing being watched and the watcher. Both rejected — not as bad tools in general, but as the wrong shape for one server.

Chosen — internal degradation: a deterministic `observability.checkSystem` heartbeat action feeding into `notifications`, edge-triggered through state rows. This is the other half of the cut: states where the system is running but something inside it is degrading. They're reported by a new `heartbeatAction`, `observability.checkSystem` (same category as the module registry's drift check), run by the heartbeat scheduler every minute. It's a plain SQL check, no LLM involved — the same principle applied elsewhere in the system: if an ordinary query can compute it, the agent layer doesn't get involved. It checks four things:

1. `process_heartbeats` against the derived expected set (a stale or missing beat → `process_stale`).
2. Queue depth — graphile-worker holds jobs in Postgres, so "how many jobs are past the threshold and how old is the oldest overdue one" is a single read-only SELECT, isolated to this one place (→ `queue_backlog`).
3. **Mail sync progress.** `mail_account_sync_state` carries a column named `next_expected_activity_at`, which each of the sync adapters computes for itself from its own liveness semantics (an IMAP reconcile window, a Gmail watch expiry, a Graph subscription expiry — the three adapters have three different meanings of "quiet is fine," so a single flat threshold over a raw `last_activity_at` timestamp isn't enough). The check is therefore one uniform predicate over a value the adapter has already guaranteed for itself, not an outside interpretation of a raw timestamp: `next_expected_activity_at < now()` → `mail_sync_stalled`. This is deliberately the *second* line of defense — the first lives inside mailsync itself (an `imapflow` socket timeout plus TCP keepalive on the IMAP connection, and a hard deadline on the IDLE cycle, so a silently dead socket from a NAT timeout without an RST falls into reconnect on its own); this check catches the case where even that didn't work, because it measures the outcome (sync is happening), not the mechanism.
4. `mail_account_sync_state.last_error` and permanently failed jobs, as a cross-check against places that already write notifications on their own.

The state of each check lives not in process memory but in its own small infra table — restarting `semprec-agents` must not mean a second round of the same notifications:

```sql
CREATE TABLE observability_checks (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  check_key text NOT NULL UNIQUE,   -- 'process:agents' | 'process:mailsync:<item_id>' | 'queue' | 'mail_activity:<item_id>'
  status text NOT NULL,             -- 'ok' | 'alerting'
  detail text,                      -- human-readable reason for the last transition (beat age, queue depth, ...)
  changed_at timestamptz NOT NULL DEFAULT now()
);
```

The write is **edge-triggered**, not level-triggered: a notification is created on the *transition* `ok → alerting` (a beat was fresh and went stale; the queue crossed its threshold), not on every minute-by-minute run that sees the same bad state again — otherwise a persistent fault would produce sixty notifications an hour and bury everything else. For the queue, a hysteresis: the threshold to enter `alerting` is (pending jobs > 100, or the oldest overdue job > 10 minutes), and re-arm back to `ok` only happens after dropping below half that — the same reason a thermostat doesn't switch at one exact temperature. The state row also satisfies the existing `notifications` contract (`source_table`/`source_id` are NOT NULL uuid — the schema doesn't change): a notification of the new kind references `source_table = 'observability_checks'`, `source_id =` the id of the state row whose transition triggered it — this holds even for `queue_backlog`, which otherwise has no source row of its own (it's an aggregate over the queue), and that's exactly why the transition is materialized as a row instead of allowing a NULL exception in `notifications`. `user_id` is the system's single account (v1 scope) — `checkSystem` reads it from `users`, no "who does this belong to" heuristic needed until multi-user exists. Delivery then runs unchanged through the existing notification fanout — no fourth channel; the new `kind` values are `process_stale`, `queue_backlog`, `mail_sync_stalled`.

**5. Metrics.** `GET /api/system-health` plus a "System status" block on the Semprec project page — the same pattern already used and proven for AI usage tracking (`ai_gateway_calls` → a usage endpoint → a usage graph, delivered by issue #30), no new table, just an aggregating read over a source of truth that already exists. Operational metrics get identical treatment: a new read-only endpoint, `GET /api/system-health`, aggregates current state from tables earlier layers already introduced — `process_heartbeats` (running/stale, version, uptime), `observability_checks` (what's currently `alerting` and since when), the graphile-worker queue (pending/overdue/permanently failed), `item_automation` (`status='error'` counts per database), `agent_runs` (error runs over the last 7 days), `mail_account_sync_state` (last activity and error per mailbox). On the Semprec project page this renders a **System status** block next to the usage block (the usage block ships in issue #30) — the same place a user already looks at cost, now also health. This is an aggregating read outside the item model — exactly the category of exception the existing rule for the usage endpoint already allows, no new precedent.

Deliberately **without** historical time-series: the only question with a time dimension that actually gets asked in practice is "how much is AI costing me" — and that's already answered by `ai_gateway_calls`, where history exists as a byproduct of billing, not as a metric for its own sake. Collecting extra samples of queue depth or latency into a new table would mean retention, downsampling, and a cleanup job for data nobody is asking about. When a concrete question actually arises ("is the queue growing over time?"), one narrow table gets added for it then.

Rejected: Prometheus + Grafana (or VictoriaMetrics/netdata) on the server. This is the canonical answer to metrics — and a bad trade for one user on one server: two more standing services (scraper + dashboard) with their own config, retention, disk, and auth; a second UI outside the app that would get visited a couple of times a year; and `/metrics` endpoints in every process — all for graphs whose underlying data the app can already show from its own system tables. It would also split the source of truth: process state would live once in `process_heartbeats` (for alerting) and again in Prometheus (for graphs). Revisit only on real growth to multiple servers, not preemptively.

**6. Error tracking.** Rejected: Sentry, self-hosted or hosted. Self-hosted Sentry is its own small infrastructure — the official compose stack runs dozens of containers (Kafka, ClickHouse, Redis, and friends) with recommended multi-gigabyte RAM; running that alongside six Semprec processes for one user's errors is a mismatch not worth debating long. Hosted Sentry is lighter, but it ships stack traces — which in this system routinely carry fragments of personal data (Inbox item text in a job payload, an email subject in a sync error) — to a third party, directly against the reason the whole system is self-hosted in the first place; and its main value-adds (deduplicating the same error across thousands of users, release health, source maps for a minified frontend) solve problems a single-user backend doesn't have. Error telemetry already exists in the system anyway — it's just named differently.

Chosen: three layers that already stand. Errors the user needs to *act on* are already structured data in Semprec, not log lines: `item_automation.status='error'` plus a reason string, `agent_runs.status='error'`, `mail_account_sync_state.last_error` — and all three already write to `notifications`. That **is** error tracking at this layer: the error arrives by push, the link points at the specific item, and the state can't be dismissed except by fixing it. The second layer is diagnostic: the same moment of failure writes a `pino` `error` log with a stack trace and `traceId` to journald — the notification says *what* happened and where, `journalctl | grep traceId` says *why*. Deduplicating a repeated error is handled by the edge-triggering above, plus retry discipline that already exists (graphile-worker backoff, the daily re-batch for `item_automation`) — not a fingerprinting engine.

The third layer is policy for the unexpected: `uncaughtException`/`unhandledRejection` means a **fatal log and immediate exit**, not "log it and carry on" — a process left running in an undefined state is exactly the kind of silent inconsistency the `agent_runs` startup sweep and the store-then-delete discipline elsewhere in the system work hard to rule out. Restarting is systemd's job (`Restart=always`); a repeated crash reaches the operator via the `OnFailure` /fail ping above; and unfinished work recovers through mechanisms that already exist: the job queue returns unclaimed jobs, the startup sweep closes orphaned runs, IMAP reconcile catches sync back up. The error path therefore has no state machine of its own — just a hard rule for when to crash, and reliance on recovery mechanisms designed earlier, specifically for this.

## Scope

### In scope
- A shared `pino` module in `packages/shared`, wired into all five processes, with `redact` and `LOG_LEVEL`.
- `SyslogIdentifier` for the systemd units, `logging: driver: journald` for Compose, `journald.conf` retention settings.
- `traceId` propagation (minting, `AsyncLocalStorage`, carrying it through the queue envelope and the `x-trace-id` header, bound logger fields).
- Migration and writes for `process_heartbeats`, plus derivation of the expected process set.
- `GET /healthz` on `semprec-api`.
- The `semprec-deadman.timer`/`.service` pair plus the `OnFailure=semprec-failping@%n.service` unit.
- The `observability.checkSystem` heartbeat action, the `observability_checks` migration, and the three new `notifications.kind` values.
- `GET /api/system-health` plus the "System status" block on the project page.
- `uncaughtException`/`unhandledRejection` policy across all five processes.
- The `mail_account_sync_state.next_expected_activity_at` column and the per-adapter computation it depends on, to the extent the `mail_sync_stalled` check consumes it (the adapters themselves belong to the IMAP sync core issue).

### Out of scope
- A log aggregator (Loki/Grafana, ELK).
- A distributed-tracing stack (an OpenTelemetry collector).
- The systemd `sd_notify`/`WatchdogSec` watchdog.
- An uptime monitor on the same server, or alerting hard failures through the system's own `notifications`.
- A metrics stack (Prometheus/Grafana/VictoriaMetrics/netdata), `/metrics` endpoints.
- Historical time-series metrics in a new table.
- Sentry (self-hosted or hosted) or any other external error-tracking SaaS.
- Provisioning of unit files, Caddy configuration, backups, the secrets catalog and rotation, `shared/.env` bootstrapping — all of that belongs to issue #20. This issue only assumes an existing `shared/.env` and existing `semprec-*` units and adds directives/variables to them, without managing the rest of the operations layer.
- Registering a healthchecks.io account and creating the check (a manual operational step).

## Dependencies
- Data model and DB structure (issues #21, #22) — the infra tables `process_heartbeats`/`observability_checks` follow the conventions of the existing schema.
- Module registry and heartbeat scheduler (`moduleRegistry.checkDrift`, issue #29) — `observability.checkSystem` is a new heartbeat action in the same category.
- Job queue / graphile-worker (the `packages/queue` engine with `enqueueJob`/`registerTask`, issue #21; the runtime `TASK_NAMES` merge, issue #29) — `traceId` plugs into the existing envelope, and `queue_backlog` reads the `graphile_worker` schema.
- `agent_runs` and the AI gateway (`ai_gateway_calls`, the usage endpoint, the usage graph — delivered by issue #30) — the pattern copied for `system-health`.
- The mail sync module (`mail_account_sync_state`, IMAP reconcile) — needs the new `next_expected_activity_at` column, computed per adapter.
- The notification system (`notifications`, the notification fanout) — new `kind` values, no schema change.
- The deployment layer (five systemd units + Compose) — this issue adds directives to it, but the unit files and provisioning themselves belong to issue #20.
- `shared/.env` and `packages/shared` conventions.
