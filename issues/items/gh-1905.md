**Model tier:** high

## Context

Model tier rationale: It adds a derived date that depends on recurrence expansion and the tenant time zone, must stay correct as days pass (a daily recomputation), and changes the sort, filter and grouping behavior of the Events collection, so date and daylight-saving mistakes are visible to every user.

The Events collection lists each Event once, grouped and ordered by day. A recurring Event (the rule from #1817) is one row but occurs on many days, so a stored `date` (its first day) places it in the past. The collection must show a series once, at its nearest occurrence from today, and sort, group and filter by that day. The generic view query sorts and filters by stored properties only (`views/sortCompiler.ts`, `views/filterCompiler.ts`); a value that depends on "today" has to be stored and kept fresh.

This issue adds the system-owned Events property `nextOccurrenceDate` (type `date`, owner system, locked): the date of the nearest occurrence on or after today in the tenant time zone; for an Event without a recurrence rule it equals the Event's own `date`; for a series that has ended it is the date of its last occurrence. With it, the existing sort, group and relative-date filter features (#1524) work on recurring Events unchanged.

Decision: the value is a plain stored date in the tenant time zone, recomputed (a) inline when an Event is created or when its `date`, `endDate` or recurrence rule changes, and (b) by a daily heartbeat for recurring Events whose stored value is before today. The occurrence list comes from the expansion function of #1877. Database date comparisons rely on the session time zone being UTC (#1596).

Decision: ties on the same day are ordered by the existing sort tie-breakers; this issue adds no other sort key.

Shared-file ordering: this issue also waits for #1901 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. In `backend/packages/data/src/seed/seedTenDatabases.ts`, add to the Events property list `nextOccurrenceDate` (type `date`, owner `system`, `locked: true`), declared like the derived `time` property. Add its display name `property.events.nextOccurrenceDate.name` to `backend/packages/data/src/seed/i18n/cs.json` and `en.json`.
2. Add `backend/packages/data/src/calendar/nextOccurrenceDate.ts` with `computeNextOccurrenceDate(event, today, timeZone)`, using the occurrence expansion function from #1877 (no second expansion logic): the first occurrence on or after `today`, else the last occurrence, else the Event's `date`.
3. Add the pre-write transform for Events (the registry from #1422), in `backend/packages/data/src/calendar/nextOccurrenceDateTransform.ts`, that computes the value on create and when `date`, `endDate` or the recurrence rule is in an update; register it in `backend/packages/data/src/domainWriteHooks.ts`. The caller cannot set the property (owner system gives 403 on a generic write).
4. Add the heartbeat action `calendar.refreshNextOccurrence` (`backend/packages/data/src/calendar/nextOccurrenceRefreshAction.ts`, validated `action_config`) that, per tenant, recomputes the value for every live recurring Event whose stored value is before today, writing through the choke point as the calendar module's system process, in batches of 200 Events per transaction. Seed it as a `dailyTime` heartbeat (shortly after midnight in the tenant time zone) in the calendar module's system project, list it in `heartbeatActions` of `backend/packages/data/src/calendar/calendarModuleManifest.ts`, add its id to `KNOWN_HEARTBEAT_ACTION_IDS` in `backend/packages/data/src/manifest/knownActionIds.ts`, and register the handler in `backend/services/semprec-api/src/actionRegistryComposition.ts`. Seeding goes into `backend/packages/data/src/seed/seedCalendars.ts` (the calendar module's seed function).
5. Add one cutover `backend/packages/data/src/calendar/nextOccurrenceDateCutoverMigration.ts`, registered in `runTenantCutoverMigrations` in `backend/packages/data/src/db/tenantCutoverMigrations.ts`, that inserts the property definition into each existing Events database by direct SQL (identical to the seed), backfills the value of every Event in batches of 500, and creates the heartbeat for tenants that lack it. Idempotent; skipped when the tenant has no Events database.
6. Tests: a Standup with a weekday rule since 12 Oct has `nextOccurrenceDate` 16 Oct on Friday 16 Oct and 19 Oct when computed on Saturday 17 Oct; a non-recurring Event has its own `date`; an ended series shows its last occurrence; changing the rule recomputes on write; the daily action advances stale values and leaves current ones untouched; a generic write of the property is 403; the cutover backfills existing Events, is idempotent and skips a tenant without Events; sorting the Events collection by the property lists the series at its next day.

## Acceptance criteria

- When a recurring Event is read on a day after its first day, then `nextOccurrenceDate` is its nearest occurrence on or after today in the tenant time zone.
- When a non-recurring Event is read, then `nextOccurrenceDate` equals its `date`.
- When midnight passes in the tenant time zone, then the daily action moves stale values to the next occurrence without touching current ones.
- When the Events collection is sorted by the property, then a series appears once at its next day.
- When a client writes the property directly, then the response is 403.
