**Blocked by:** #113

## Context

Autonomous delivery requires repeatable unit, real-database integration, and cross-module smoke coverage. This part formalizes the first two tiers as mechanism and configuration, not as a CI pipeline. Vitest is already configured in `backend/vitest.config.ts` with a single `test` script and an embedded-Postgres `globalSetup` (`backend/packages/data/src/testSupport/globalSetup.ts`) plus `getTestPool`/`resetDatabase` in `backend/packages/data/src/testSupport/testDb.ts`; this part turns that into two explicitly separated tiers with stable scripts. The sibling part #114 builds on these scripts and adds the third tier, the named e2e harness with one cross-module scenario. #115 uses the integration tier for its load-all and inactive-projection tests.

## Task

- **Unit tier.** Configure Vitest unit tests that run with no DB (no `globalSetup`, no `TEST_DATABASE_URL`), and include tests for the filter-tree compiler, property migration conversion functions (the converters invoked by #111), and next-heartbeat-fire-time computation.
- **Integration tier.** Provide an ephemeral real-PostgreSQL integration harness (never a mocked DB), building on the existing `testSupport` lifecycle: a fresh database provisioned for the run, structural migrations applied through the runner from #224, isolated state between tests, and teardown at the end. Include integration tests for owner/locked enforcement at the choke point, the idempotency key, and one concurrency guarantee from this batch (for example concurrent `moduleRegistry.checkDrift` runs from #112 or concurrent data-migration runners from #111).
- **Scripts.** Expose stable local scripts in `backend/package.json` that run the unit tier alone, the integration tier alone, and both together, each with isolated setup/teardown so runs do not interfere with each other or with a developer database.

## Scope

### In scope

- Unit and integration test configuration, fixtures, the ephemeral PostgreSQL lifecycle, the representative tests named above, and the scripts.

### Out of scope

- The e2e harness and its cross-module scenario (#114).
- Mocked-DB substitutes and CI workflow files.

## Acceptance criteria

- The unit suite runs with no database available and passes; the integration suite runs independently and both run together through one script.
- Integration tests use real PostgreSQL and clean their state, so repeated runs and any test order produce the same results.
