## Context

Model tier rationale: It widens the schema of three locked system databases for every existing tenant, so a wrong cutover step corrupts shared system schema, and it fixes a cardinality contract that later issues depend on.

A transaction needs to be findable from its company, its project and its document: a spend belongs to a project, comes from a company, and is backed by a scanned invoice. Companies, Projects and Files already exist, but `seedTenDatabases` locks their schema, so other modules link to them one-directionally without an inverse (Emails.attachments to Files, Movies.watchedWith to People). Relation cardinalities available are `one_to_one`, `one_to_many` and `many_to_many` (`CreateRelationPropertyInput` in `backend/packages/data/src/chokePoint/relationPropertyOps.ts`); `many_to_one` does not exist. A `one_to_many` from side A means each B belongs to exactly one A, which is what a transaction needs (one company, one project, one document per transaction).

Decision: make the links bidirectional and temporarily unlock the three databases: add `Companies.transactions`, `Projects.transactions` and `Files.transactions` as `one_to_many` with inverses `transactions.company`, `transactions.project` and `transactions.document`, then lock the schemas again. Reason: the inverse makes the single value structural, so a transaction cannot have two companies, and the project, company and file pages can show their transactions with the generic relation machinery. The unidirectional alternative would need a hook to enforce the single value and a special reader.

For existing tenants these properties come from a per-tenant cutover, not SQL: `properties.tenant_id` has `DEFAULT app_tenant_default()`, which returns NULL outside a tenant scope, so a plain SQL migration cannot insert them. The per-tenant cutover loop is `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`), and new tenants are seeded by `seedSystem` (`backend/packages/data/src/seed/seedSystem.ts`); #1511 added the Finance seed and cutover this builds on. The Area is not stored on a transaction; an area finds its transactions through the project, which is read by the related-items mechanism (#1839), not by this issue.

What builds on it: #1607 validates amounts, #1651 declares inheritance of company and project from the document along `transactions.document`, and #1590 lets a client create a transaction and its links atomically.


Shared-file ordering: this issue also waits for #1549 because both edit the same files listed in Touches.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Create `backend/packages/data/src/seed/seedFinanceLinks.ts` exporting `seedFinanceLinksInTransaction(client, computedKeyRegistry)`. In one transaction, after `LOCK TABLE properties IN EXCLUSIVE MODE` (as `transcription/transcriptsCatalogCutoverMigration.ts` does), it looks up the databases `companies`, `projects`, `files` and `transactions` by module id, sets `schema_locked = false` on `companies`, `projects`, `files` only if they were locked, creates the three relation properties with `createRelationPropertyWithClient` (`one_to_many`, source Companies/Projects/Files named `transactions`; inverse on `transactions` named `company`, `project`, `document`, both sides `locked: true`), then restores `schema_locked = true`. Property names are `null` (labels come from the catalogs).
2. Skip any of the three whose property already exists, so the function is idempotent.
3. Call it from `seedSystem` right after the Finance seed of #1511, and from `runFinanceModuleProvisioningCutover` as a separate step that runs on every pass after the Finance seed step (even when the Finance databases already exist, because a tenant may have received them before this issue), under the same advisory lock, so new and existing tenants converge to the same schema.
4. Add the Czech and English labels for `transactions.company`, `transactions.project`, `transactions.document` and for the new `transactions` property on Companies, Projects and Files to the catalogs of the modules that own those databases (`backend/packages/data/src/seed/i18n/cs.json` and `en.json`).
5. Tests: after a new tenant seed and after the cutover on an existing tenant the three relations exist with their inverses and the three databases are locked again; a second cutover run changes nothing; a transaction linked to a project and a company is returned from the project's and the company's `transactions` relation; setting a second company on the same transaction replaces the first (single value); no other property or lock of the three databases changed; a second tenant is unaffected.

## Acceptance criteria

- When a transaction is linked to the project Rekonstrukce koupelny and the company Siko, then it appears in the project's and in the company's `transactions`, and the project's area finds it through the project.
- When a second company is set on a transaction that already has one, then the transaction has only the second.
- When the cutover runs on an existing tenant, then Companies, Projects and Files have the `transactions` property, the three databases are schema-locked again, and a second run changes nothing.
- When another tenant exists, then its schema is not touched.
