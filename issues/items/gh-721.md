## Context

`web/src/views/mailbox/MailboxClient.tsx`, `MailboxPanes`: the on-screen message list is `messages` (line 483-486: `triagedMessages ?? messagesResource.value`), an overlay that a completed triage applies to what is already rendered instead of re-fetching. `runTriage` (lines 537-600, `useCallback` with `messages` in its deps at line 600) awaits the backend (`setMessageFlag`/`moveMessages`), then:

- line 577 `setTriagedMessages(messages.filter((message) => !succeeded.has(message.id)))` for a move (archive/delete);
- line 581 `setTriagedMessages(messages.map(…))` for a flag change;
- line 571 `setCursorId((current) => nextCursorAfterRemoval(messages.map((m) => m.id), current, result.succeeded))` and line 559 `countUnread(messages, …)`.

All four read the `messages` array captured when the action **started**. Two overlapping actions (press `e` on one message, then `e` on the next before the first PATCH resolves; or two quick row buttons) each capture the same pre-triage list: the second to resolve overwrites the overlay with "original list minus its own message", so the message the first action removed reappears in the list until the folder is re-read. The same stale capture miscounts `unreadMoved` and the cursor when a flag change overlaps a move.

The existing tests in `web/src/views/mailbox/__tests__/MailboxTriage.test.tsx` resolve every operation immediately, so the overlap never occurs there.

## Task

- In `runTriage`, derive the new overlay from the **current** overlay, not the captured array: both `setTriagedMessages` calls become functional updates `setTriagedMessages((current) => (current ?? loadedMessages).filter(…))` / `.map(…)`, where `loadedMessages` is the resolved `messagesResource.value` (or `[]`) — the base when no overlay exists yet. Keying is by `message.id` (the `succeeded` set), so a message already removed by a concurrent action stays removed.
- Read the list for `countUnread` and `nextCursorAfterRemoval` from a ref that always holds the latest rendered `messages` (`const messagesRef = useRef(messages)` kept current in a `useEffect(() => { messagesRef.current = messages; }, [messages])`) instead of the captured `messages`, and drop `messages` from the `useCallback` deps. Do not assign the ref during render (eslint-plugin-react-hooks v7 flags it).
- Test in `MailboxTriage.test.tsx`, in the `row actions` block: wrap the fake operations so `linkItem`/`unlinkItem` (the move path) return promises the test resolves by hand (a deferred per call); archive message A, then archive message B while A's promise is still pending; resolve A, then B; assert the list contains neither A nor B and still contains the remaining message. A second case does the same with two overlapping "mark read" flag changes and asserts both rows show as read and the folder's unread count dropped by two.

- When two archive actions overlap (the second starts before the first resolves) and both succeed, neither message is in the list after both resolve, in either resolution order.
- When a flag change and a move overlap, the unread count delta reflects the read flags as they were when each action resolved, not when it started.
- Every existing case in `MailboxTriage.test.tsx`, `MailboxClient.test.tsx` and `MailboxCompose.test.tsx` passes unchanged; `pnpm run verify` in `web/` passes.
