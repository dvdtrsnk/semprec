## Approved behavior specification

This epic preserves the complete approved behavior of source issue #74, inlined here so the epic is self-contained.

### Source behavior: [mail-search-czech-dict 01/01] Install hunspell cs_CZ dictionary and switch Czech full-text search off the simple+unaccent fallback

## Context

Issue #26 (IMAP Sync Core, merged into `develop`) added Postgres full-text
search over synced email content. Its migration
(`backend/packages/data/src/db/migrations/0006_mail_sync.sql`) builds a
`czech` text search configuration on top of the always-available `simple`
parser plus the `unaccent` extension, instead of the hunspell-backed `cs_CZ`
dictionary configuration the original spec asked for. The migration's own
comment explains why: "a hunspell dictionary is an operating-system-level
asset (dictionary files under the Postgres `tsearch_data` directory), not
something a SQL migration can install — it has to be provisioned by server
setup," and names issue #40 as where that provisioning belongs.

That reference turns out not to be accurate: issue #40 ("Operations — Caddy,
backups, secrets, provisioning") defines `provision.sh`'s complete list of
system dependencies explicitly — "Node LTS + pnpm, Docker + Compose, Caddy,
restic, `ffmpeg`/`ffprobe`, systemd unit files ... journald configuration ...
the service user, the bare `/opt/semprec` directory tree" — and its own
"Reference to the specification" section has no mention of hunspell,
dictionaries, or Postgres text search configuration anywhere. Issue #40 does
not, in fact, cover installing the `cs_CZ` hunspell dictionary files or
wiring Postgres to use them. This gap has been re-flagged as an unmet
acceptance criterion in every review round on PR #71 without ever landing in
an issue that actually owns it.

## Task

1. Extend `provision.sh` (delivered by issue #40, this issue builds on top of
   it) with the OS-level package(s) needed to make a `cs_CZ` Czech hunspell
   dictionary available to Postgres's `tsearch_data` directory on the target
   Debian/Ubuntu-family server (the `hunspell-cs` package plus copying/
   symlinking its `.dict`/`.affix` files into Postgres's `tsearch_data`
   directory in the format `CREATE TEXT SEARCH DICTIONARY` expects).
2. Add a new migration that creates a hunspell-backed `ispell` dictionary
   (`CREATE TEXT SEARCH DICTIONARY czech_hunspell (TEMPLATE = ispell,
   DictFile = cs_CZ, AffFile = cs_CZ, StopWords = czech)` or the equivalent
   for whatever files `provision.sh` lands) and repoints the existing `czech`
   text search configuration's mapping to use it ahead of the current
   `simple`+`unaccent` fallback, so `websearch_to_tsquery('czech', ...)` and
   `ts_rank_cd` (already used unchanged by `search.ts`) start benefiting from
   real Czech stemming instead of literal word matching.
3. Make the migration degrade gracefully in an environment where the
   dictionary files aren't present (CI, local dev without running
   `provision.sh`) — the existing `simple`+`unaccent`-only behavior must keep
   working there, since neither CI nor a fresh local checkout will have run
   `provision.sh` against a real server.

## Scope

### In scope

- The `provision.sh` addition (OS package + `tsearch_data` file placement)
  and the new migration that upgrades the `czech` text search configuration
  to use it, with a documented, tested fallback for environments without the
  dictionary installed.

### Out of scope

- Any other part of issue #40's provisioning scope (Caddy, backups, secrets,
  CI dependency-cruiser matrix) — untouched by this issue.
- Any change to `search.ts`'s query parsing, ranking, or the Gmail-style
  search operators — all already correct per issue #26's review and unrelated
  to which dictionary backs the `czech` configuration.
- PDF/DOCX attachment text extraction's `pdf-parse`/`mammoth` vs. `pdftotext`
  choice — a separate, already-justified deviation from issue #26, not
  revisited here.

## Acceptance criteria

- `provision.sh` installs a Czech hunspell dictionary package and places its
  files where Postgres's `tsearch_data` directory expects them, idempotently
  (re-running `provision.sh` doesn't fail or duplicate the install).
- On a server where `provision.sh` has run, the `czech` text search
  configuration's word-token mapping resolves through the hunspell-backed
  dictionary (verified via `ts_lexize` or an equivalent query against the
  live dictionary, not just against `simple`).
- On an environment without the dictionary files present (CI, a fresh
  migration run with no `provision.sh`), the migration still applies
  successfully and full-text search over Czech email content continues to
  work via the existing `simple`+`unaccent` behavior — no hard failure.

## Decisions

- **Question:** Which boundary is load-bearing? **Adopted answer:** Provision OS assets. **Reason:** It preserves approved source behavior.
- **Question:** Which boundary is load-bearing? **Adopted answer:** Fallback to simple+unaccent without assets. **Reason:** It preserves approved source behavior.
- **Question:** Which boundary is load-bearing? **Adopted answer:** Activate databases migrated before provisioning. **Reason:** It preserves approved source behavior.
