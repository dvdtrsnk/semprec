**Blocked by:** #973

## Context

Unique and foreign-key checks ignore row-level security. While tenant tables carry a global unique key, a second tenant inserting the same value gets a unique violation, so the key becomes an existence oracle and a cross-tenant collision. The tenancy ADR from #968 therefore decided that every unique index on a tenant table leads with `tenant_id`. The exceptions are a server-generated surrogate key and a key scoped by the server-generated id of a parent row in the same tenant. The `tenant_id` column comes from #972; tables are classified `semprec:tenancy=tenant` by table comment (#971), and row-level security comes from #973.

This change is the expand half of expand/contract. It adds a tenant-leading unique index beside each legacy global one and leaves the legacy ones in place. The previous release and today's code use the legacy keys as `ON CONFLICT` arbiters and constraint names, for example `isUniqueViolation(err, "databases_key_unique")` at `backend/packages/data/src/chokePoint/databasesStore.ts:94`. Each new index is a superset of its legacy key's columns, so it cannot fail on existing data, and it never changes arbiter inference: Postgres infers only indexes whose column set equals the conflict target. Later issues switch code to the new keys subsystem by subsystem, and #1065 drops the legacy keys and `resource_grants`.

This issue also adds the `(tenant_id, id)` unique keys that #1066's composite foreign keys `(tenant_id, x_id) → parent(tenant_id, id)` reference. A foreign key may reference a non-partial unique index.

The full set of unique indexes on tenant tables at `origin/develop` comes from `backend/packages/data/src/db/migrations/`, which a reviewer can re-derive with `grep -n -i "unique\|primary key"`. They fall into four groups:
- **Legacy global keys:**
  - `databases_key_unique (key)` (`0028_database_keys_nullable_names.sql:14`)
  - `idempotency_keys` PK `(key)` (`0001_core_schema.sql:164`)
  - `person_email_index` PK `(email)` (`0006_mail_sync.sql:127`)
  - `mail_message_meta_provider_msg_uq (provider_message_id)` (`0006:71-72`)
  - `blobs_content_hash_uq (content_hash)` (`0004_ten_databases.sql:37`)
  - `notifications_dedupe_idx (source_table, source_id, kind, transition_instance)` (`0030_notifications_schema.sql:67-68`)
  - `manifest_drift_findings_active_idx (kind, dedupe_key)` (`0030:27-29`)
  - the `module_migrations` and `module_migration_progress` PKs `(module_id, database_key, from_version, to_version)` (`0011:15`, `0051:18`)
  - `docs_item_id_idx (item_id)` (`0003_docs.sql:22`)
  - `resource_grants (resource_type, resource_id, grantee_user_id)` (`0001:139`). This table is dropped later (#1065); until then it gets the tenant-leading twin `resource_grants_tenant_uq (tenant_id, resource_type, resource_id, grantee_user_id)` so the uniqueness rule holds.
- **Surrogate primary keys:** a single `id` column defaulting to `gen_random_uuid()` or a `bigserial` sequence.
- **Parent-scoped keys:** keyed by a server-generated id of a row in the same tenant, so a cross-tenant collision needs another tenant's unguessable id. Where the parent is a regular table, #1066's composite foreign keys bind parent and child to one tenant. Item ids cannot carry a foreign key (`items` is partitioned with primary key `(database_id, id)`, `0001_core_schema.sql:3-19`), so the code writing an item-keyed row resolves the item inside the tenant (#1017 for stored references).
- **`mail_account_sync_state_graph_subscription_id_uq`:** kept global by decision (`0041_graph_webhook_client_state.sql:15-16`). It holds a provider-assigned id that a router function later resolves to its tenant.

## Acceptance criteria
- `findOrCreateBlob` (`backend/packages/data/src/blobs/blobsStore.ts`) uses a bare `ON CONFLICT DO NOTHING` instead of the targeted `ON CONFLICT (content_hash) WHERE content_hash IS NOT NULL`: with a second unique index on `content_hash`, a concurrent identical insert would otherwise trip the non-arbiter index with a unique violation. The existing concurrent-upload tests keep passing (integration). This is the only arbiter change in this issue; switching blobs to the tenant key stays with #1008.
- Each of the 23 new indexes (including `resource_grants_tenant_uq`) exists with exactly the columns and predicate listed, and `seedSystem` still succeeds with them in place (integration, `tenancyCatalog.test.ts`).
- Every unique index on every tenant-classified table satisfies the uniqueness rule. A unique index created without `tenant_id` and outside both lists fails the rule, and the failure names it (integration).
- Within one tenant, a second system database with the same `owner_module_id` is rejected with `23505` on `databases_tenant_system_module_uq`. A second non-system database with the same `owner_module_id` is still accepted (integration).
- Inserting a duplicate database key through the choke point still raises the existing `ConflictError` (409), because the legacy `databases_key_unique` is still the constraint hit first. The existing integration suite, including every `ON CONFLICT` path, passes unchanged (integration).
- The migration-compatibility unit check passes without an exemption marker (unit).
