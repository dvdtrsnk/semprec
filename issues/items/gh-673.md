## Context

`triggerOnItemEventHeartbeats` in `backend/packages/data/src/scheduler/schedulerStore.ts` (lines 303-325) runs on **every** choke-point item create, update and delete, inside that write's transaction (`itemWrites.ts` lines 177 and 279, `itemTrash.ts` line 50). Its query (lines 310-317) is

```sql
SELECT id, action_id FROM project_heartbeats
 WHERE enabled AND rule ->> 'kind' = 'onItemEvent' AND rule ->> 'databaseId' = $1 AND rule ->> 'event' = $2
```

`project_heartbeats` has indexes only on `next_fire_at` (partial, `project_heartbeats_due_idx`), `project_item_id` and the guidance-drift unique index (`0001_core_schema.sql` lines 109-112, `0035_agent_guidance_drift.sql` line 77) — nothing covers the JSONB expressions, so every item write sequentially scans the whole table. The table grows with every project's heartbeats (ten are seeded per install already), and this scan sits on the hot path of every write while holding the write's row locks.

Migration rules: `docs/adr/2026-09-10-expand-contract-forward-only-migrations.md` (a new index is an additive expand step).

## Task

1. New migration `backend/packages/data/src/db/migrations/NNNN_project_heartbeats_on_item_event_idx.sql` (next free ordinal at commit time):

   ```sql
   CREATE INDEX project_heartbeats_on_item_event_idx
     ON project_heartbeats ((rule ->> 'databaseId'), (rule ->> 'event'))
     WHERE enabled AND rule ->> 'kind' = 'onItemEvent';
   ```

   with a header comment naming `triggerOnItemEventHeartbeats` as the query it serves and stating that the partial predicate must match that query's `WHERE` verbatim for the planner to use it. No change to the query text in `schedulerStore.ts` is needed — its predicate already matches — but add a one-line comment above the query pointing at the index by name so the two stay aligned.
2. Test in `backend/packages/data/src/__tests__/scheduler.test.ts` (integration): `pg_indexes` contains `project_heartbeats_on_item_event_idx`; and, with `SET LOCAL enable_seqscan = off` in a transaction, `EXPLAIN (FORMAT JSON)` of the exact query from `triggerOnItemEventHeartbeats` (copy it verbatim into the test, or export the SQL string as a constant from `schedulerStore.ts` and use that) shows an `Index Scan`/`Bitmap Index Scan` node on that index — proving the partial predicate matches the query, which a bare index-exists check cannot.
