## Context

No production process ever runs an agent session. The agents runtime (`backend/services/semprec-agents/src/queueRuntime.ts:33-34`) calls `createAgentTaskList(pool, actionRegistry, moduleRegistry)` with the default `agentRunTask`/`delegatedAgentRunTask`, which are `noopAgentQueueTask` (`backend/packages/data/src/agentWorker.ts:17,28-29`) — an `agentRun` or `delegatedAgentRun` job completes instantly and does nothing. The `core.agentRun` heartbeat action (`coreAgentRunAction(pool, runAgent)`, `backend/packages/data/src/scheduler/actions.ts:55-85`) is registered by #641 with a placeholder `RunAgentFn` that throws, so the seeded `newEmail` heartbeat currently closes every run as `error`. `@semprec/agent-runtime` exports the whole session lifecycle — `runAgentSession`/`runAgentTurn`/`pushRunStatus`/`extractResultSnapshot` (`backend/packages/agent-runtime/src/lifecycleAdapter.ts`), `registerPiProviders`, `createProjectAgentGuidanceSystemPromptOverride`, `createGenericOperationAgentTools`/`listGrantedGenericOperationAgentTools`, `createApprovalGatedMcpInvokeTool` — but every `createAgentSession` in the repository is a test fake: nothing constructs a pi-agent-core `Agent` outside `backend/packages/agent-runtime/src/__tests__/piRuntimeContract.unit.test.ts`. `semprec-agents` gained its `@semprec/agent-runtime` dependency and its startup ordering in #642.

Two shapes must be reconciled. `runAgentSession` creates its own `agent_runs` row, while `coreAgentRunAction` already created one and expects `runAgent({ agentRunId, projectItemId, task })` to run against it and return `{ result }` (it then calls `finishAgentRun` itself, or `finishAgentRunWithErrorNotification` on throw). So the executor for an existing row is the part of `runAgentSession` after `createAgentRun` (lines 133-165): `pushRunStatus(running)` → `createAgentSession({ task, systemPromptOverride })` → `runAgentTurn` → `finishAgentRun(done, extractResultSnapshot(last))` + `pushRunStatus(done)`, with the error branch symmetric.

Model egress: per `docs/adr/2026-09-10-ai-gateway-monopoly-on-provider-calls.md`, no provider SDK call or API key may exist in this process. `registerPiProviders` (`piProviders.ts:24-28`) assumed the gateway proxies the providers' own APIs; it does not — `semprec-ai-gateway` serves only `/internal/complete`, `/internal/diarize`, `/internal/transcribe` (`backend/services/semprec-ai-gateway/src/app.ts:22-26`). pi-ai ships a `pi-messages` API (`@earendil-works/pi-ai` `dist/api/pi-messages.d.ts`): one `POST <baseUrl>/messages` with `{ model, context, options }` answered by an SSE stream of assistant-message events, usable through `createProvider({ api: "pi-messages", baseUrl, auth })` from the package root. This issue composes the session against that protocol pointed at the gateway; the gateway route that implements it is a prerequisite owned outside this batch (see Out of scope) — until it exists, production runs fail at the first model call with the gateway's 404, recorded as `agent_runs.status='error'` exactly like any provider failure, which is the intended failure mode rather than a silent no-op.

## Scope

### In scope
- One mechanism: a queued `agentRun`/`delegatedAgentRun` job, or a fired `core.agentRun` heartbeat, executes a real pi-agent-core session for its `agent_runs` row with the run's granted generic-operation and MCP tools, through the gateway-addressed `pi-messages` model, and persists the lifecycle exactly as `runAgentSession` does.

### Out of scope
- The `POST /internal/pi/messages` (pi-messages protocol) route on `semprec-ai-gateway` with budget check and `ai_gateway_calls` accounting — prerequisite for production runs to succeed, delivered by the last issue of this batch (independent side of the protocol, not a blocker); this issue's e2e test uses pi's faux provider instead.
- Hosting `SempConversation`, `DelegationRegistry`/`createDelegateTool`, the supervisor HTTP surface, conversation reconstruction/compaction on wake, and the `heartbeat.trigger` agent tools (`heartbeatAgentTools.ts`).
- Any producer of `agentRun` jobs (none exists; the heartbeat path is the production entry point).
- Startup repair (#642) and the action registries (#641).

## Acceptance criteria

- When an `agentRun` job `{ agentRunId }` for a `running` row is claimed by `createAgentsQueueRuntime`, a pi session runs with the run's task, and afterwards the row is `status='done'` with `result` equal to the model's final text and `agent_run_events` holds `run_status`/`turn_start`/`message`/`turn_end`/`run_status` in order (plus `tool_use`/`tool_result` pairs when tools were called); a model or tool failure leaves `status='error'`, a `run_status(error)` event and one `agent_run_error` notification.
- When the seeded `core.agentRun` heartbeat fires, the same terminal state is reached through `coreAgentRunAction`, and the heartbeat records success.
- When an `agentRun` job names a row that is not `running`, nothing is written.
- Every model call leaves the process only as `POST <AI_GATEWAY_BASE_URL>/messages` with `Authorization: Bearer <AI_GATEWAY_INTERNAL_TOKEN>`; no provider SDK import and no provider key exist in `semprec-agents` (`grep -rn "ANTHROPIC_API_KEY\|api.anthropic.com\|api.openai.com" backend/services/semprec-agents backend/packages/agent-runtime` is empty).
- `semprec-agents` refuses to start without `AI_GATEWAY_BASE_URL`, `AI_GATEWAY_INTERNAL_TOKEN` or `AGENT_MODEL`, naming the missing variable.
