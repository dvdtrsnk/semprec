## Context

Model tier rationale: Restoring an independently retained secret-key artifact requires a precise trusted-data boundary, compatibility with older main dumps and failure-safe ownership without defeating crypto-shredding.

Independent batch19 R1 at 7550fba23bcd86cc963287797d2ec07ed8832c13 found that restoring the newest tenant-keys.dump into an older main snapshot can fail its tenant foreign key: a new tenant/key may have been created after the main snapshot. The same interleaving is possible between the two original dump commands. No live recovery was run. This owns F2 and explicitly corrects the earlier gh-1064 restore assumption without rewriting that historical record.

Apply `docs/adr/2026-11-03-offline-compatible-tenant-key-restore.md` within its exact scope. Selected contract: constrained Docker-exec PostgreSQL16 client, checked one-entry TOC, private owned staging database on the same verified instance, typed batches, non-owner scoped target insert with real FK/RLS, and actual backend/child/DROP settlement. The parent verified pg_restore16.15/public flags and a synthetic real TOC in the pinned configured image; this is feasibility only. Monthly host Node uses a validated random loopback port with a generated private password (no trust on published host access) and a dedicated narrow non-owner role only inside its owned disposable cluster. Real recovery supplies an existing suitable role; the CLI changes no live target grants. Preserve timestamp microseconds, explicit offline partial-import failure, bounds and no older-key fallback. No public barrel API or schema migration.

Apply `docs/adr/2026-11-03-offline-restore-owns-execs-on-an-authenticated-loopback-bridge.md` as the narrow exception to the earlier internal-network topology. Use only a fresh dedicated user-defined bridge with masquerade disabled, effective loopback/password authentication and exact owned resources. This is not a claim of universal egress isolation. Retain exact daemon exec IDs through actual settlement; a Docker CLI exit, missing SQL backend or successful DROP alone does not prove daemon exec settlement. No production or shared network change.

## Task

1. Before source implementation, provide a finite public-tool feasibility/design inventory to the parent: select a concrete offline key import that admits only keys for tenants actually present in the restored main snapshot, keeps exact wrapped bytes and key metadata, validates archive/row shape, and leaves tenant FK/RLS/security constraints enforced in the restored target. Parent must pin the selected protocol and exact new paths in an append-only decision before implementation. Do not select a protocol silently.
2. Preserve separate main/key retention, exclusion of key data from long-retention main snapshots, no master key/decryption in the restore test, and genuine missing-key recovery limits. Never reconstruct erased keys from an older artifact as a fallback; never silently import an incompatible tenant key or relabel a missing-key failure as success.
3. Once the exact protocol is approved, apply it both to the monthly restore test and the disaster-recovery runbook. Own and settle every temporary process/resource/artifact; keep secret key rows, dumps and raw errors out of logs. Fail closed on malformed/untrusted shape or uncertain cleanup.
4. Prove a real older main dump plus newer key artifact containing one additional tenant key, compatible retained keys, a legitimately removed key, malformed input and owned cleanup failure. Include actual PostgreSQL FK enforcement, not only a shell mock; do not decrypt or read production data.

## Acceptance criteria

- A newer artifact's key for a tenant absent from the restored main snapshot cannot make the compatible-key restore fail or be imported into the target; compatible rows preserve their exact bytes and the target FK stays enforced.
- A removed/expired key is not recovered by falling back to an older snapshot, and missing-key consequences are reported truthfully.
- Malformed input and cleanup failures fail closed with no secret-bearing output, and owned work is actually settled.
- Local real PostgreSQL and complete affected hermetic suites pass; no production restore, retention or crypto-shred timing PASS is claimed.
