## Context

Model tier rationale: This writes several rows atomically (item, encrypted password, server settings, sync state, queued job) after a network check outside the transaction, creating a credential-handling route with a tenant-wide duplicate rule.

A user can add an iCloud mailbox (address plus app-specific password) or a generic IMAP mailbox (address, password, IMAP and SMTP hostnames) and have mail start downloading. Today there is no route that creates a mailbox. `external_credentials` already accepts the `app_password` and `plain_password` credential types, but nothing writes them for a new mailbox, and the places for server settings, the IMAP sync transport and custom-route dependencies come from earlier issues.

It builds on: the stored IMAP and SMTP settings (#1473), the IMAP sync transport that reads those settings (#1510), custom routes that receive composition-root dependencies (#1460), the server-owned provider address and the helper that writes it (#1454) and the credential check (#1569). Rate limiting of this route is #1750.

Decision: the user name defaults to the e-mail address when the request has none, because the form has no such field.

Decision: an address already held by any mailbox of the tenant (compared on the stored provider address and on the mailbox's address list, case-insensitively) answers 409 and creates nothing, rather than reauthorizing; reconnecting an existing password mailbox is separate work.

Shared-file ordering: this issue also waits for #1729 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening`, `canonical-keys` and `testing`. Follow `docs/adr/2026-09-10-bracket-non-transactional-calls-with-staleness-checked-transactions.md`.

1. Add the route `POST /api/mail/mailboxes` with body `{ provider: "icloud" | "generic", address, password, imapHost?, smtpHost?, username? }` (authenticated, justification `transactional-semantics`), implemented as a custom route of the mail module (handler in the mail module, registered in `mailModuleManifest.ts` `customRoutes` and in `routeMatrix.ts`). Validate the body; `imapHost` and `smtpHost` are required for `generic` and rejected for `icloud`.
2. Outside any transaction, call `verifyMailCredentials` from #1569 with the username defaulted to the address.
3. In one transaction create: the Mailboxes item (name `iCloud` or `Jiný účet` as the seeded default for the generic provider, `provider`, `addresses` through the helper from #1454); the credential through `storeCredential` (`app_password` for iCloud, `plain_password` for generic); the server settings from #1473 using the verified host, port and security of both protocols; the sync state with sync mode `imap` and `provider_account_address` set to the address; and `enqueueMailAccountSync(client, ...)`.
4. Re-check the duplicate rule inside the transaction; on a conflict (including a unique-index conflict from a concurrent request) answer 409 and roll everything back.
5. Return the created mailbox in the usual item envelope; the password is never in a response, log line or tenant export.

## Scope

### In scope

- The create route for iCloud and generic IMAP mailboxes and its atomic writes and duplicate rule.

### Out of scope

- The verification itself and its error codes (#1569).
- Per-user attempt limits (#1750).
- Google and Microsoft sign-in (#1686).
- Editing the stored server settings or password of an existing mailbox.

## Acceptance criteria

- When the password is wrong, then the response is `mail_auth_failed` for generic and `mail_app_password_required` for iCloud, and no item, credential, server settings or sync state exists afterwards.
- When a generic server offers IMAP only on 143 with STARTTLS, then the stored settings hold port 143 and `starttls`; a server without TLS ends in `mail_tls_failed`.
- When the mailbox is added, then a sync job is queued in the same transaction and mail downloads without further action.
- When the address already belongs to a mailbox of the tenant, then the response is 409 and nothing is created; two concurrent identical requests create exactly one mailbox.
- The password is not present in the response, logs or the tenant export.
