## Context

Model tier rationale: One new IMAP operation and its use right after an existing transport, with the main care being failure isolation so a successful send is never reported as failed.

Gmail and Microsoft Graph store a copy of a sent message in the provider's Sent folder by themselves. An IMAP provider (iCloud, generic) does not: SMTP delivers the message but the account's Sent folder on the server does not get it, so other mail apps would not see what was sent from Semprec. `backend/packages/data/src/mail/imapFlowClient.ts` has no append method.

This builds on the SMTP transport (#1634). The synced copy of the message that later appears in the Sent folder deduplicates onto the item created at send time, because ingestion matches on the mailbox and Message-ID (`mail/ingest.ts`).

Decision: the append runs after a successful SMTP submission and is best effort; a failure is logged with a fixed classification and does not fail the send, since the message has been delivered.

## Task

Load `io-hardening`, `error-handling` and `testing`.

1. Add `appendMessage(path, raw, flags)` to the IMAP client (`ImapMailClient` in `imapReconcile.ts` and `ImapFlowMailClient`), using IMAP APPEND with the `\Seen` flag.
2. In the SMTP transport of `imap` mailboxes, after a successful submission, resolve the mailbox's Sent folder path (the folder with special purpose `sent`) and append the same raw MIME through a policy-checked IMAP connection obtained like the sync worker's. No Sent folder, or an append failure, is logged and ignored.
3. Respect the account's IMAP connection limiter for the append connection.

## Acceptance criteria

- When a message is sent from an IMAP mailbox, then the provider's Sent folder contains it with the same Message-ID and the `\Seen` flag.
- When the later sync reads that copy, then it deduplicates onto the existing item and creates no second one.
- When the append fails, then the send still succeeds and the failure is logged without message content.
