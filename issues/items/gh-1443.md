## Context

Model tier rationale: Changes the push decision and the APNs payload of the central fan-out job across several files using the two prerequisite tables, with many branching rules that each need a test, but no new storage or process.

`handleNotificationFanoutTask` (`notifications/notificationFanoutJob.ts`) fans out to active push registrations. This issue filters delivery and adds an APNs-only interruption level; APNs and Web Push keep their existing payload fields.

With #1440 (category and severity of each kind) and #1441 (the user's preferences) the job can decide. A notification is always stored (the in-app unread list and the status screens still use it); only the push is filtered.

Decisions: preferences are read when the job runs, so a change takes effect for pushes not yet sent; a missing preferences row means the defaults of #1441; `info` and kinds with `push: false` are never pushed; a category switched off means no push and no `push_deliveries` rows; problems follow `problemsLevel` (`off` none, `critical` only critical, `all` critical and warning); reminders and invitations follow their category switch (the server stores the reminders switch only, they are scheduled on the phone).

Interruption level (APNs only): approvals `time-sensitive` (the app holds the entitlement); problems with the summary switch on: `warning` `passive` and `critical` `time-sensitive`; with it off: both `active`; invitations and everything else `active`. The scheduled summary itself is switched on by the user in the phone's settings; the switch here only changes the interruption level.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. In `handleNotificationFanoutTask`, after loading the notification, read the user's preferences (`getNotificationPreferences`) and the kind's policy (`policyForKind`). Return without claiming delivery rows when the policy has `push: false`, the category is switched off, or the problems level excludes the severity.
2. Add `interruptionLevel?: "passive" | "active" | "time-sensitive"` to `NotificationPushPayload` (`push/pushSenders.ts`), computed in the job by the rules above, and send it in `sendApnsNotification` as `aps["interruption-level"]`. Web Push ignores it.
3. Add tests in `notificationFanoutJob.test.ts` for each rule: approvals off stores the notification and sends nothing; problems level `critical` drops a warning and sends a critical with `time-sensitive` (summary on) or `active` (summary off); `info` is never sent; invitations and reminders switches; approvals are `time-sensitive`; the default preferences apply without a row; a preference changed between enqueue and run is honored. No current kind uses invites/reminders: test both on/off branches through `pushInterruptionLevelFor` and verify the job calls it before delivery claims. Report real-job integration for these categories as NOT RUN/unreachable; the issues introducing their kinds must add it. Do not invent kinds for this test.

## Acceptance criteria

- When approvals are switched off, then an `approval_pending` notification is stored and no push is sent.
- When the problems level is `critical`, then a warning problem sends no push and a critical one is sent with interruption level `time-sensitive` when the summary is on and `active` when it is off.
- When a notification is of an `info` kind, then it is never pushed.
- When there is no preferences row, then the defaults apply.
