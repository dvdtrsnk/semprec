## Context

Model tier rationale: A lock-order change on the trash of an Event, a destructive path that shares value link rows with the propagation job, the link engine and several release hooks. The change is one ordering clause and one argument, but a wrong order would open a new deadlock between processes that PostgreSQL ends with an error nobody maps, so the schedules have to be run with real concurrent transactions in both orders.

The accepted ADR `docs/adr/2026-11-15-a-user-edge-write-on-a-link-rules-via-relation-locks-the-rules-target-item-before-ending-value-links.md` (source sp-5419cac1) states the order of the rows of one transcript, file or task: the item row, then the `project` link row, then `people`, then `company`. It lists three paths of the tree that take value link rows against that order and end with `40P01`. This source repairs the first of them (verified by reproduction in a scratch copy of the tree at the integration tip with production calls on pools of the runtime role `alldots_data`):

- Moving an Event to the Trash runs `valueLinkSourceDeleteHook` (`valueLinks/valueLinkSourceDeleteHook.ts`), which detaches every value link the Event is a source of with `deleteValueLinkSourcesBySourceItem` (`chokePoint/valueLinksStore.ts`). That function selects the links `ORDER BY l.id FOR UPDATE`. For a transcript linked to the Event, those are its `project` and `people` links.
- Removing the transcript's `event` edge (a user `deleteRelation` of `Transcripts.event`) runs the engine's edge-changed hook, which evaluates the rules in catalog order and so locks the `project` link, then the `people` link (`linkRuleEdgeHook`), and then the release hook `transcriptCompanyLinkReleaseEdgeChangedHook` (`transcription/transcriptCompanyLinkRelease.ts`), which locks `project`, `people` and `company` the same way.
- When the transcript's `people` link has the smaller id, the trash takes `people` then `project` and the edge removal takes `project` then `people`. With a third transaction holding the `project` link row, the edge removal started first and the trash second, the two end with `40P01` (reproduced: outcomes `committed` and `deadlock`, the trash losing). With the `project` link's id the smaller, both commit.

The other orders in the tree agree with the order in the ADR where it matters: the propagation job (`handleLinkPropagation`) sorts the links of a page by item id and locks, for each, the item row and then that one link. So the consistent total order for a trash that detaches links of several items is the item id, then the position of the link's rule in the rule catalog (`loadLinkRules` in `valueLinks/linkRuleCatalog.ts`, the order in which the engine evaluates the rules of one item), then the link id as a tiebreak. `moveValueLinkItemSources` and `lockOnValueLinksOfProperties` order by link id; the first moves the sources of a task, which are links of a different rule from those an Event feeds, and the second share-locks the links of the two sides of one edge, at most one per item, so neither orders several links of one item that an Event feeds (not measured).

The purge's call of the same function (`deleteItemDependents` in `chokePoint/itemTrash.ts`) runs after the Event's edges are deleted and under the tenant purge lock; it cannot meet the edge removal and is not changed.

## Task

1. In `chokePoint/valueLinksStore.ts`, give `deleteValueLinkSourcesBySourceItem(client, sourceItemId, ruleKeyOrder: readonly string[] = [])` a third parameter and lock the links `ORDER BY l.item_id, array_position($2::text[], l.rule_key), l.id FOR UPDATE`, with `ruleKeyOrder` as `$2` (a link whose rule is not in the list, or an empty list, sorts after the others and by link id). Update its docstring: the order is the item id, the position of the rule in `ruleKeyOrder` and the link id. The returned array keeps the order of the locks. `itemTrash.ts` is not edited and keeps calling it without the argument.

## Scope

### In scope

- The order in which the trash of an Event locks the value links it detaches.

### Out of scope

- The order of the release hooks and of the engine's edge-changed hook, `detachEventFromLinks` and `releaseCompanyLinks`: unchanged.
- The trash of an Event that hosts a task which is also sourced from it (the task row after the links): a separate source.
- The replay of an approved `relation.delete`, `relation.put` or `relation.set`: a separate source.
- The deadlocks of schedule B that the 2026-11-15 ADR records (a `relation.set` against an edge write on `Transcripts.project`).
- The purge's call (`deleteItemDependents`), `moveValueLinkItemSources`, `lockOnValueLinksOfProperties` and the propagation job.
- Any new lock, table, hook kind or migration.

## Acceptance criteria

- When a user removes a transcript's `event` edge and another user trashes that Event, with a third transaction holding the transcript's `project` link row, then neither call ends with a deadlock, in both start orders and whichever of the transcript's `project` and `people` links has the smaller id; both commit.
- When the trash of an Event detaches the links of several items, then it locks them in the order item id, rule position in the catalog, link id.
- When the trash completes, then the transcript has no value link row, keeps its project and company edges, and every other behaviour of the Event's trash is as before.
- The purge of a trashed Event is unchanged.
- The ADR of this source exists and the accepted ADRs it names are not edited.
