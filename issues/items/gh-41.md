## Context

Semprec's implementation queue has 22 sequential issues; this is **#21 of 22** — the last feature module. Only the deployment-process issue (22/22) follows it, and nothing depends on this one. The pipeline built here rests on third-party providers and internal mechanisms introduced earlier:

- **#21 (schema engine)** established that a meeting recording is, from the first moment, an ordinary row in the Files database (no special entity), and gave the system the `owner_process` drift check, the `item_automation` state model, the choke-point `Idempotency-Key` mechanism, and the `migration_cursor` pattern for resumable batch runs.
- **#24 (Files as a database)** established Files as one of the ten hardcoded system databases with a blob layer and `content_hash` dedup — thanks to that, uploading a recording is just another file, not a special path.
- **#37 (generic endpoints)** established the choke-point as the single write surface (`POST`/`PATCH /api/items`, the relation endpoint, the `confirm`/`revise` mechanism over Processing Suggestions) — this module adds no new write mechanism, it only uses that one.

This issue is the **last feature module in the queue**. It introduces no new data model — the Transcriptions database with its pipeline properties (`status`/`date`/`link`) and `computed.segments`/`summaryByInstruction`, Processing Suggestion cards with `kind = 'transcript'`, the `semprec-transcribe` process shell, and the `TASK_NAMES.transcriptionJob` queue type already exist in the topology; `semprec-ai-gateway` already lists both DeepInfra and pyannoteAI as providers. What is genuinely new here: **two providers** (DeepInfra Whisper ASR, pyannoteAI diarization) and **one pure merge function**. Everything else is reuse of mechanisms that already exist.

## Task

Implement batch transcription of uploaded meeting recordings as a deterministic pipeline inside the `semprec-transcribe` process, across three layers:

**1. Input and trigger**

A recording enters the system exclusively through the existing upload route `POST /api/files` — there is no special transcription-upload endpoint; a file is a file, whatever happens to it afterward. The relevant guarantee that route already gives: the blob and the Files row (`properties.file = { blobId }`) are created in **one transaction, only after the whole upload stream has been read** — the Files row never exists first with an empty property filled in later by a PATCH, so the `onItemEvent 'create'` handler always sees a populated `blobs.mime_type`, with no race against the upload. Idempotency is not solved again here either: content itself is the key — an interrupted or repeated upload converges, via `blobs.content_hash` dedup, onto the same Files row, never a second file and a second paid pipeline. Offline capture from a phone (record a meeting, no signal, send later via Shortcuts) is solved for free by the same mechanism.

Triggering is a mechanical rule, not an agent decision: the Semprec project's `project_heartbeats` gets a second entry alongside "Process Inbox" — `{ kind: 'onItemEvent', databaseId: 'files', event: 'create' }`, the same event shape used elsewhere for matching emails to People. The handler (runs inside `semprec-agents`) is purely mechanical (no LLM — same category as the `person_email_index` lookup) and deliberately makes **zero writes**: if the new file's `blobs.mime_type` starts with `audio/` and the row was not created by the mail pipeline (a mailbox attachment row is recognizable by an existing edge from Emails.`attachments`; a voice message inside an email must never trigger a paid transcription on its own — the user requests attachment transcription explicitly, and step 0 of the pipeline with the same idempotent key also works as a direct action), it enqueues `TASK_NAMES.transcriptionJob` with payload `{ fileItemId }` and `jobKey: transcription-job:${fileItemId}` — the same dedup shape as Semprec's own tick, with the key derived from the source file because the Transcriptions row does not exist yet at that point. Everything else — creating the Transcriptions row, running `ffprobe`, writing `status` — happens only in step 0 of the job itself, inside `semprec-transcribe` (pipeline below). If the handler created the row itself, there would be two writers of `owner: 'system'` fields in two processes — exactly the drift the `owner_process` check exists to catch; and enqueue-with-no-writes is naturally idempotent besides: a repeated handler run just collapses a second job onto the same `jobKey`, never a duplicate transcription.

Why automatic triggering rather than a manual button as the only path: "the user remembers to click Transcribe" is a hope-based step running against the project's own grain — it relies on human memory instead of structure. The mechanical MIME rule is deterministic, cost is bounded by the gateway's budget cap, and a per-item opt-out exists via `item_automation.status = 'locked'` ("do not touch again"). For files outside the automatic rule — typically video with an audio track, or files uploaded before the module was enabled — an explicit action route `POST /api/transcriptions` exists with body `{ fileItemId }` (registered by the same manifest rule as other action routes): it does exactly what the handler does, i.e. enqueues the same job with the same `jobKey`; a file that already has a Transcriptions row gets a 409 `transcription_exists` (an additive error code on the standard error contract) pointing at `/rerun` below — never a second transcription. `ffmpeg`, in the preparation step, pulls the audio track out of video the same way it transcodes audio.

**2. Pipeline — seven steps, a checkpoint after each**

```
0. create      choke-point create of the Transcriptions row with a derived Idempotency-Key
               transcription:${fileItemId} → a repeated run gets the same row, never a
               second one; name from the filename, status = processing,
               link -> Files row, item_automation pending
1. prepare     ffmpeg: transcode to 16 kHz mono Opus (~7 MB/h; pulls the audio track out of video)
               ffprobe: recording length, creation_time -> date
2. diarize     gateway.diarize() -- pyannoteAI, the ENTIRE recording in one call
               -> speaker turns [{ speaker: 'SPEAKER_00', start, end }]
3. ASR         gateway.transcribe() -- DeepInfra Whisper large-v3, 15-min chunks with a 30 s overlap,
               language detected on chunk 1 and passed explicitly to every later chunk
4. merge       pure function, no I/O: words x turns -> computed.segments [{ speaker, text, startsAt, endsAt }]
5. summarize   gateway.complete() -- Claude over the merged transcript -> computed.summaryByInstruction
6. match       deterministic time window against Events -> edge directly, otherwise a card kind='transcript'

-- producers (enqueue only, never a write): the onItemEvent handler in semprec-agents,
--   and the action routes in semprec-api:
--   enqueueJob(TASK_NAMES.transcriptionJob, { fileItemId }, { jobKey: `transcription-job:${fileItemId}` })
-- registerTask(TASK_NAMES.transcriptionJob, ...) lives only in semprec-transcribe
--   (one handler owner per task name) -- and only it performs the choke-point writes
--   of this pipeline, and only it calls ffmpeg/ffprobe
-- after every step the intermediate result is written to items.computed -> retry resumes from
--   the last completed step, already-paid-for steps are never paid for again (see state model below)
```

`ffmpeg`/`ffprobe` are a system-level server dependency (provisioning concern, not an npm dependency); `semprec-transcribe` is the only process that calls them. Transcoding to 16 kHz mono Opus is not a cosmetic optimization: it keeps a two-hour meeting under ~15 MB, safely below the upload limits of hosted ASR endpoints, and it is also the format chunking operates on — the cut point is nudged to the nearest silence at the boundary (`ffmpeg silencedetect`), because a chunk that ends mid-word is a known source of Whisper hallucinations at boundaries.

ASR uses Whisper large-v3 via DeepInfra — a provider already named in the gateway's provider list, adding no new vendor or credential. Whisper large-v3 is an open model with reference-quality output for both Czech and English, always returns segment-level timestamps (and word-level timestamps where the endpoint exposes them — the merge function below has defined behavior for both granularities, nothing is improvised at runtime), and is billed per minute of audio — an hour-long meeting costs on the order of single-digit cents. Because the output format (Whisper JSON with segments and times) is not proprietary, a future switch to self-hosting would be an adapter swap inside the gateway, not a pipeline rewrite — self-hosted ASR (whisper.cpp/faster-whisper) is rejected for v1 only because Semprec runs on a single Linux server with no guaranteed GPU, not rejected forever.

An all-in-one provider (AssemblyAI/Deepgram — ASR and diarization in a single call) was considered and rejected: it would add a fourth vendor beyond the two already named, would couple ASR and diarization to one vendor so replacing either means replacing both (the opposite of the gateway's one-function-one-swappable-adapter contract), and generalist ASR APIs have consistently worse diarization quality than the specialized pyannote — exactly the part of the output the speaker-mapping step below depends on. The merge step that this would "save" is a pure function with unit tests — the cheapest kind of code the system has.

Diarization runs over the **entire** recording in a single `gateway.diarize()` call (pyannoteAI) — the gateway contract (`complete()`/`transcribe()`/`embed()`) gains a fourth function, `diarize()`, with the same pre-call budget check and `ai_gateway_calls` write as the other three. The asymmetry in chunking is deliberate: diarization is **never** chunked, because speaker labels (`SPEAKER_00`, `SPEAKER_01`, ...) are anonymous identities valid only within a single run — chunked diarization would return per-chunk labels needing re-identification across chunks, an extra error-prone layer solving a problem that need not exist. ASR, by contrast, can safely be chunked: text has no global identity, only order. Overlap dedup is a mechanical rule, not fuzzy text matching, and the cut in the middle of the overlap band applies **symmetrically to both chunks**: from the earlier chunk, segments whose time midpoint falls **after** the midpoint of the band are dropped; from the later chunk, segments whose midpoint falls **before** it are dropped — every instant of the recording ends up with exactly one owner, no text duplicated, none skipped. A deterministic cut, the same result on every run.

Language: Whisper can auto-detect, but per-chunk detection could flip languages mid-recording because of a few English sentences in an otherwise Czech meeting. So language is detected once, on the first chunk, and passed explicitly to every later chunk — the whole recording is transcribed in one dominant language. The detected value is stored in `computed.language` — a derived pipeline output, same category as `segments`, no new schema property.

Merging: a word belongs to the speaker turn whose span covers the word's time midpoint; a word not covered by any turn falls to the time-nearest turn. Consecutive runs of words from the same speaker are merged into segments; a segment additionally breaks on a pause longer than ~1.5 s so the output reads like a conversation, not monolithic blocks. Where the ASR endpoint does not return word-level times, a coarser fallback applies: the whole ASR segment gets the speaker with maximum time overlap — less precise at speaker-change boundaries, but still fully deterministic, never "it'll work out somehow." The whole merge step is a pure function with no I/O — a natural fixture-test candidate (edge cases: overlapping turns, a word spanning a boundary, missing word timestamps, the symmetric overlap cut at chunk boundaries). Its output shape is exactly the mock's segment shape (`segmenty` in the mock; canonically `segments`) — `{ speaker, text }` extended with `startsAt`/`endsAt` — the same shape another module already hashes into `fingerprint` (`sha256({text, startsAt, endsAt})`) for Processing Suggestion cards.

**3. Output**

`semprec-transcribe` writes through the choke-point package in-process (the same third adapter pattern used elsewhere, e.g. `AgentTool` in `semprec-agents`) with the identity of the system process — and because row creation itself is step 0 of the job as of this revision, it holds literally that the `owner: 'system'` fields `status`/`date`/`link` are written by this process and no other, exactly as the Transcriptions database catalog entry prescribes: producers (the heartbeat handler, the action routes) perform no writes at all, only enqueue. Those fields carry an `owner_process` tag identifying the transcription pipeline, so any drift from this guarantee would be caught by a drifting heartbeat, not discovered later during debugging. `status` transitions: `processing` -> `done`, or -> `error` — a fourth select value the mock did not have, added via a code-level migration of the system schema (the only allowed path for changing a system database's schema). Without it, a failed transcription would sit in the UI forever as "Processing" — exactly the silent no-op that `item_automation` forbids elsewhere. `status` carries no error detail — that lives in `item_automation.error` below; the select is a display pill, not an error log.

`segments`, `summaryByInstruction`, `language`, and the step checkpoints all go into `items.computed` — this was already decided when the Transcriptions database was cataloged ("derived output of the transcription pipeline, written only by the background worker"), and the pipeline simply fills it in. All of these keys are declared by the module in its `ModuleDatabaseSpec`'s `computedKeys`; a computed-write for an undeclared key is rejected. The summary is generated by `gateway.complete()` (Claude) over the merged transcript according to a chosen instruction — the instruction is an input, the output is a cache: regenerating with a different instruction is a new pipeline step, never a manual edit of `computed`. Because all writes go through the choke-point, the UI sees state transitions live over the realtime WebSocket channel for free — the same fan-out as any other change to `items`, no transcription-specific push mechanism.

Matching to an Event: the final pipeline step tries to match the transcription mechanically, without an LLM — same decision category as the `person_email_index` lookup. Candidates are Event rows with `type` in {`standup`, `meeting`} and `date` (with time) inside the window [recording start - 30 minutes, recording end] — a meeting that started early, or a recording started late, still falls inside. Exactly one candidate -> the Transcription<->Event edge (an existing 1:1 relation) is written directly, done. Zero candidates, or more than one, -> **no guessing**: a Processing Suggestion card is created with `kind = 'transcript'` and `sourceTranscript` — these are exactly the "unmatched transcriptions" already assigned to Semprec's own heartbeat processing, now with a concrete mechanism instead of just a name. The card's `proposal` carries either creation of a new Event (`entityKind: 'database'`, `target` = Events, `properties` estimated from the transcript — an existing shape, unchanged) or linking to an existing one: `entityKind` gains a third value, `'relation'`, which `confirm` maps onto the existing generic relation-write operation (`PUT /api/items/:id/relations/...`) — no new write mechanism, just a third branch over the ones `confirm` already has (create-item, block append). In both cases `confirm` also writes the Transcription<->Event edge in the same transaction — it knows which transcription the card belongs to from `sourceTranscript`, and a cross-database write in one transaction is exactly what `confirm` exists as the single place to do. The same generic envelope `{ entityKind, target, properties }` and full overwrite via `revise` apply here as for Inbox cards — a chat clarification can flip a suggestion from "create a new Event" to "attach to that existing one" in one move.

Speakers: `computed.segments` carry **permanently** anonymous diarization keys (`SPEAKER_00`, ...) — the transcript is never rewritten after people are later assigned. This is not laziness: rewriting segment text would change `fingerprint` and invalidate unlocked cards over the same source, and more importantly it would conflate two things with different lifecycles — what was said (an immutable pipeline output) versus who we believe said it (a revisable assignment). The mapping lives separately: a new relation **Transcriptions.speakers -> People** (N:N, `owner: user`, added to the Transcriptions catalog entry), where each edge carries `item_relations.metadata = { speaker: 'SPEAKER_00' }` — a third use of that same generic field (after edge-level ratings, and the IMAP UID case) — the value belongs to the relationship (this person is this voice in this recording), not to either side. The UI composes names only at render time: a mapped key renders as a person, an unmapped one as "Speaker 1" — a missing mapping is a normal state, not an error.

Who maps: manually in the UI (the relation is `owner: user`, assigning or correcting it is an ordinary choke-point write) — and AI may only **suggest** a mapping, on a card with `kind = 'transcript'`, estimated from the matched Event's participants (the Event -> People relation) and address forms in the text, confirmed by a human via `confirm` — the same enforced separation of suggestion from write as everywhere else. Voiceprint identification (pyannoteAI offers it — enroll a person's voiceprint, then deterministic matching) is deliberately not introduced for v1: it would mean a new category of sensitive biometric data with its own storage and consent from the people involved, in exchange for saving one confirmation click on a card. Deferred, not rejected — the card-based path covers the need.

State model and retry: the job's state machine invents nothing new — it is literally `item_automation` on the Transcriptions row: `pending` -> `done`/`error`/`locked`, `attempts` as a cumulative counter, `error` carrying the reason as text. Retry policy matches other batch jobs, including the reasoning: a `graphile-worker` job with `max_attempts: 3` and built-in exponential backoff; after permanent failure, a daily heartbeat takes over, re-enqueuing `error` rows in a fresh batch with the same `jobKey: transcription-job:${fileItemId}` (`fileItemId` derived from the row's `link`) — until it either succeeds or someone locks the row (`locked` = "do not retranscribe," the one state the heartbeat itself never sets). The transition to `error` writes a `notifications` row (`kind: 'automation_error'`) in the same transaction, so a failed transcription reaches the user as a push notification, not as something discovered by opening a table by chance. Manual retry has its own action route, `POST /api/transcriptions/:id/rerun` (enqueues the same `jobKey`; a `locked` row returns 403) — the same manifest rule as the other action routes above.

The queue delivers at-least-once: a process crash between finished work and job acknowledgment means the handler runs again — the pipeline is built for exactly that, twice over. Step 0, with its deterministically derived `Idempotency-Key transcription:${fileItemId}`, converges onto the same Transcriptions row, never creating a second one (and a second paid pipeline); checkpoints then make the rest of retry cheap, not just possible: the intermediate result of each step (raw ASR chunks, diarization turns) is written to `items.computed` right after that step finishes, so a repeated run resumes from the last completed step — a crash after diarization does not pay for diarization again. The same "resumable checkpoint, not all-or-nothing" principle used elsewhere for `migration_cursor` on batch migrations — more important here because the middle steps cost real money, not just time.

Cost: every gateway call (diarization, each ASR chunk, the summary) writes a row into `ai_gateway_calls` with `agent_run_id = NULL` — exactly the case that column was designed to anticipate. The pre-call budget check applies here too: a long recording over the daily cap means a rejected call, the job falls into `error` with a notification, and the daily retry tries again after the budget window rolls over — no special "transcription is exempt from budget" mode. For ASR/diarization calls, `input_tokens`/`output_tokens` are left `NULL` — the unit of measurement for these calls is audio time, not tokens, and it is written into its own column, `audio_seconds`, instead of being folded into the token totals, which would corrupt the token view on the workload dashboard. `cost_usd` is always the real price, so the cost view sees transcription in full; the token view deliberately measures only LLM load, and `NULL` (rather than zero) means no future "average tokens per call" metric is ever skewed by it.

## Scope

### In scope

- Extending `project_heartbeats` with an `onItemEvent` entry for the Files database, plus the mechanical MIME handler in `semprec-agents` (no writes, enqueue only)
- Action routes `POST /api/transcriptions` (explicit trigger, 409 on an existing row) and `POST /api/transcriptions/:id/rerun`
- The `semprec-transcribe` process: sole owner of `registerTask(TASK_NAMES.transcriptionJob, ...)`, sole caller of `ffmpeg`/`ffprobe`
- The seven-step pipeline, including checkpointing into `items.computed` after every step
- Extending the `semprec-ai-gateway` contract with a fourth function, `diarize()` (pyannoteAI), alongside `complete()`/`transcribe()`/`embed()`; DeepInfra Whisper large-v3 for ASR
- The merge function (pure, no I/O) as a testable unit
- Extending the `status` select with the value `error` (code-level system-schema migration)
- Deterministic matching to Events via a time window, plus a Processing Suggestion card on ambiguity
- The `Transcriptions.speakers -> People` relation with `metadata.speaker` on the edge, including AI-suggested mapping on a card
- Reuse of the `item_automation` state model, retry/backoff policy, `notifications` write, and `ai_gateway_calls` cost tracking without changing their mechanism
- Adding the `ffmpeg`/`ffprobe` system dependencies to the provisioning script

### Out of scope

- **Phase 2 — meeting bot and live captions.** Deliberately deferred, not forgotten. A bot joining Meet/Zoom/Teams and streamed ASR for live captions are not introduced in this issue, not even preparatorily. Named reuse for the future phase: the value `status = 'recording'` (already exists in the select, just unused in v1), the upload/blob layer for a recording that grows incrementally, the entire merge function, the matching window, and the card pipeline (a bot is just a different audio producer — the pipeline from step 2 onward is identical), and the gateway's `diarize()`/`transcribe()` contract. Genuinely new in the future phase would only be bot infrastructure as a producer, and a streamed transport for live captions over the existing realtime WebSocket channel as another message type. What's being decided is **when**, not **how**.
- Self-hosted ASR (whisper.cpp/faster-whisper) — rejected for v1 (no guaranteed GPU on the server); in the future, only an adapter swap inside the gateway thanks to the independent output format.
- Voiceprint speaker identification (biometric matching via pyannoteAI enrollment) — deferred; the card-based path with manual/AI-suggested mapping covers the need.
- A watch folder on the server's disk — rejected as an anti-pattern outside the database structure.
- An all-in-one provider (AssemblyAI/Deepgram, ASR+diarization in one call) — rejected: a fourth vendor for no reason, couples two specialists to one vendor, worse diarization quality than the specialized pyannote.
