## Context

Model tier rationale: One new read operation built on the existing filter compiler and choke-point read path, with defined seams in the shared catalog, REST and MCP and an existing fixture style, though it spans many hotspot files and groups by two property kinds.

Counts shown across the app (the number next to each collection on the overview, the "N items" header, the open-task badge, the "5 tasks, 2 today" line on a project row and the "2 people" line on a company row, the column counts on a board) cannot be derived from the paged query. `countItems` exists only inside the choke point (`backend/packages/data/src/chokePoint/itemReads.ts`, backed by `itemsStore.countItems`) and is not in the operation catalog or REST. There is no grouped aggregation at all, and rollups (`backend/packages/data/src/rollup/config.ts`) cannot filter their target items and cannot be added to a locked database through the API, so they are not used for these counts.

This issue adds one batched operation, `item.count`, that returns a count per database and optionally per group. It builds on `totalCount` (#1406), which established the count-by-filter semantics, and on the collection filter that module manifests declare (#1647). It is built on by facets (#1759), the area overview (#1760), the overview summary route (#1837), the Tasks today view count (#1798) and free-text search in counts (#1857).

A relation count is read from the relation edges. A relation edge write publishes no invalidation today, so clients' relation-based counts can go stale until #1621 lands; this issue adds no invalidation of its own.

Decision: counts exclude soft-deleted items always (no `inTrash` option), and a deleted item that is restored is counted again. Decision: the overview's "today tasks" count is just `item.count` over the filter of the Tasks today view (#1798); this issue adds no task-specific logic. Decided by the product owner: the badge counts only open tasks for today (the open-only Today filter of #1798, 7 rather than 8 in the design), because a badge says what is left to do, as the overview does. Decision (product owner): an archived database is in the trash, so its items are counted nowhere and counts match what the user sees: an entry for an archived database returns `count: 0` and no groups, and a relation `groupBy` leaves out targets that lie in an archived database (an item whose only edges point into archived databases counts in the `null` group), matching the relation reads of #1404 and #1518.

Shared-file ordering: this issue also waits for #1704 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. Add the operation `item.count` to the catalog: name in `operationNames.ts`, capability `core.item.read` (non-destructive) in `capabilities.ts`, input/output types in `schemas.ts` and `port.ts`, binding in `bindings.ts`. Input: `{ items: [{ databaseId, filter?, groupBy?, collection? }] }` with 1 to 20 entries (`.strict()`, more than 20 is a 400). Output: `[{ databaseId, count, groups?: [{ key, count }] }]` in input order.  The board's column counts, the project-row "5 tasks, 2 today" and the company-row "2 people" are all expressed with this one shape: the board is `groupBy` on the grouping select under the full filter; the project row is one entry grouped by the task-to-project relation (not-done tasks) plus a second entry in the same batch with an added `date_relative` today condition; the company row is `groupBy` on the people-to-companies relation.
2. `filter` is the same filter tree `database.query` takes (`filterNodeSchema`, so relative dates and numeric conditions work once their issues land). `collection: true` ANDs the collection filter that the database's module manifest declares (#1647); a database without a declared collection filter is counted unfiltered.
3. `groupBy` is a property key. For a relation property (project to area, task to project, person to companies) `groups` has one entry per distinct target item id that occurs, counted over the filtered items (an item linked to two targets counts in both groups); items with no edge are returned as `{ key: null, count }` only when there are any. For a `select` property `groups` has one entry per stored option key that occurs and `null` for items without a value, ordered by the option order in `config.options` (the board uses this for its columns). A non-groupable property type or unknown key is a 400 `field: "groupBy"`. `count` is always the total of the filtered items.
4. Implement in the data layer: a grouped count function next to `countItems` in `backend/packages/data/src/chokePoint/itemsStore.ts`, exposed through `itemReads.ts` and the choke point type in `chokePoint.ts`. One SQL statement per entry, every value a bound `$N` parameter, `deleted_at IS NULL`, and no item or relation target whose database has `archived_at` set (an entry for an archived database counts 0). Resolve every `databaseId` under the caller's tenant: an unknown and a foreign database id answer identically (the same not-found response `database.query` gives).
5. Add `POST /api/items/count` in `backend/services/semprec-api/src/itemsHandler.ts` mapping the body to the operation, add it to `routeMatrix.ts` (tenant-scoped, non-public) and to the cross-tenant route cases in `__tests__/tenantIsolationRoutes.test.ts`. The MCP and agent tools derive from the catalog; update their contract tests.
6. Tests: nine collections in one call (counts exclude deleted items; restore counts again); an entry for an archived database returns 0 and its restore counts the items again; a relation `groupBy` whose targets lie in an archived database omits those groups; `groupBy` of a relation over active projects returns one count per area; a select `groupBy` on the board property returns option order with the stored counts; `collection: true`; 21 entries is a 400; foreign database id behaves like an unknown one.

## Scope

### In scope

- The `item.count` operation over REST, MCP and agent tools: batch of up to 20 databases, filter, relation and select grouping, optional collection filter.

### Out of scope

- `includeCount` on queries: #1406.
- Facet counts per property: #1759.
- The `q` free-text parameter in counts: #1857.
- Realtime invalidation of relation-based counts when an edge changes: #1621.
- The Tasks today view definition and which tasks it counts: #1798.
- Excluding archived databases from rollups (#1359) and from facets (#1759).

## Acceptance criteria

- When one batch contains a not-done-tasks entry grouped by project and a second entry with an added today condition, then both return per-project counts in one response.
- When one call asks for the nine overview collections, then the response has nine entries in request order, each with the number of non-deleted items; Projects with the collection filter excludes system projects.
- When an item is soft-deleted, then the count drops; when it is restored, then it is counted again.
- When a database is archived, then an entry for it returns `count: 0`, and a relation `groupBy` over another database no longer lists targets in the archived database; after the database is restored, both count again.
- When `groupBy` is the area relation over active projects, then `groups` has one count per area that occurs plus the total in `count`.
- When `groupBy` is a select property, then groups come in option order, with `null` last.
- When the batch has more than 20 entries or `groupBy` names an unsupported property, then the request fails with a 400.
- When a database id belongs to another tenant, then the response is identical to the one for a nonexistent id.
