## Context

Model tier rationale: Requires deciding, from the transaction structure of the agent-run event writer, whether out-of-order NOTIFY delivery is a product bug or only a test assumption; one file either way.

`backend/packages/agent-runtime/src/__tests__/lifecycleAdapter.test.ts`, test "announces durable events as thin references and sends message_update only on the ephemeral stream", failed once during a full backend verify on 2026-10-22 under host load. It compares the `eventId`s announced on `semprec_events`, in delivery order, with `agent_run_events` ids ordered by `id`. It received `[1, 3, 2, 4, 5]` instead of `[1, 2, 3, 4, 5]`. A re-run passed.

Postgres delivers a `NOTIFY` at commit, while `agent_run_events.id` is taken at insert. If two event writes run in overlapping transactions, a later id can commit, and so be announced, first. Either the lifecycle adapter writes events concurrently, and a subscriber can then see events out of order in production, or the test assumes an order that the contract never promised.

## Task

Load `testing` and `error-handling`.

1. Read how `runAgentSession` / the lifecycle adapter (`backend/packages/agent-runtime/src/lifecycleAdapter.ts`) and `backend/packages/data/src/agentRuns/agentRunEventsStore.ts` write and announce events. Determine whether two event writes for one run can be in flight at once.
2. If they can, serialize the writes for one run so that announcement order equals `id` order, and keep the test's ordered assertion. Add a test that would fail without the serialization.
3. If they cannot, find what else reorders delivery. If ordered delivery is not a guarantee of the contract, compare the announced ids with the stored ids as sorted sets and say why in a one-line comment.
4. Run the test file 30 times in a row and report the result in the pull request.
