## Context

Model tier rationale: One new pure module over luxon with defined inputs and outputs and existing time-zone fixtures, but daylight-saving edge cases are subtle and many later issues depend on its exact semantics.

The calendar needs one shared definition of today, now, the boundaries of a day and a week, and when an Event or Task ends, all in the tenant's time zone. Today the pieces are scattered: `systemSettings.timezone` (read by `getSystemTimezone` in `backend/packages/data/src/systemSettings.ts`, default Europe/Prague) is used by task recurrence (`backend/packages/data/src/tasks/nextDueDate.ts`, luxon), heartbeats and AI budgets, and `backend/packages/data/src/timezone.ts` holds only `assertValidTimezone`. Date filters and sorts cast to `timestamptz` in the database session zone (`views/filterCompiler.ts`, `views/sortCompiler.ts`), which is a separate concern handled by #1596. `timezone.ts` sits outside the domains, so the choke point may import it (`backend/dependency-cruiser.rules.json`, rule `chokepoint-knows-no-domain`), and the new module must live beside it for the same reason.

Events and Tasks are stored as wall-clock values in the tenant's zone: a `date`, an optional `endDate`, and `timeFrom` and `timeTo` as `"HH:MM"` (see #1416). Invitations, shared calendars and ICS imports carry an instant plus an IANA zone and are converted to wall-clock on acceptance or import (that conversion belongs to those issues). Changing the tenant's zone does not change stored wall-clock values; reminders are recomputed.

Several issues use this module: the calendar timeline (#1717), tasks inside events (#1780), reminders (#1719), relative date filters (#1522), invitations (#1944), subscribed events (#2004), sleep nights (#1792), the schema projection's tenant block (#1531), recording matching (#1813) and the Events migration (#1797).

Decisions:
- A Task has no default end. A Task with `timeFrom` and no `timeTo` is a short task at its start time: its effective end equals its start, and the calendar client draws it as a short block. No end and no length is stored or computed that the user did not enter; there is no default Task length constant.
- Daylight saving follows luxon defaults: a non-existent wall-clock (29 March 2026, 2:30 in Europe/Prague) moves forward; an ambiguous one (25 October 2026, 2:30) takes the earlier offset. A day has 23, 24 or 25 hours for "lasts" and "ended" computations.

## Task

Load `testing`.

1. Create `backend/packages/data/src/calendarTime.ts` (next to `timezone.ts`, importing nothing from domains) exporting pure functions that take the zone and an optional clock, with luxon:
   - `today(zone, now?)` as `YYYY-MM-DD`; `now(zone, now?)` as wall-clock date and time;
   - `dayBounds(date, zone)` and `weekBounds(date, zone)` with weeks Monday to Sunday;
   - `eventEnd(event, zone)` from `endDate ?? date` and `timeTo` (an all-day Event ends at the end of its last day; `"24:00"` is midnight at the end of that day);
   - `taskEffectiveEnd(task, zone)` using `timeTo`, or, when a timed Task has no `timeTo`, its start (`date` plus `timeFrom`), for Tasks only;
   - `isEnded(end, zone, now?)`;
   - `wallClockToInstant(date, time, zone)` and `instantToWallClock(instant, zone)` with the daylight-saving rules above.
2. Add a small loader `getCalendarClock(client)` that reads the tenant's zone with `getSystemTimezone` once and returns the bound helpers, for callers that already hold a client.
3. Tests with a fixed clock: at 23:30 UTC on 16 October the Europe/Prague `today` is `2026-10-17`, independent of the server zone; 25 October 2026 2:30 resolves to a single instant (`+02:00`); 29 March 2026 2:30 moves forward; the 25 October day is 25 hours; `eventEnd` for an event 24.–25. October without times is the end of the 25th; a timed Task without an end ends at its start; week bounds start on Monday.

## Scope

### In scope

- The pure calendar time module, its loader, and its tests.

### Out of scope

- Pinning the database session zone and the filter and sort casts: #1596.
- Using the module in the timeline, filters, reminders, migration and other callers; each caller issue wires it in.
- Exposing a tenant block with the zone and today to clients: #1531.
- Converting invitation, ICS or subscription instants on arrival: #1944 and #2004.
- A default or configurable Task length: a Task without an end has none, and no property is added.
- Realtime invalidation of relation edges: #1621.

## Acceptance criteria

- When the clock is 23:30 UTC on 16 October 2026, then `today` for Europe/Prague returns `"2026-10-17"` regardless of the process or database zone.
- When the wall-clock 25 October 2026 2:30 is converted in Europe/Prague, then exactly one instant results, with offset `+02:00`; for 29 March 2026 2:30 the result is moved forward.
- When the length of 25 October 2026 in Europe/Prague is requested, then it is 25 hours.
- When an Event runs 24.–25. October with no times, then its end is the end of 25 October; with `timeTo` `"24:00"` it is midnight at the end of that day.
- When a Task has `timeFrom` and no `timeTo`, then its effective end equals its start (no default length is added); an Event is never handled by this rule.
- When a week is requested for any date, then it starts on Monday and ends on Sunday.
