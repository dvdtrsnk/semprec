**Blocked by:** #1031

## Context

`backend/packages/data/src/credentials/externalCredentialsStore.ts` is the only code that encrypts and decrypts third-party secrets:

- `storeCredential` (`:39-49`) seals with `encryptSecret` (secretbox, no associated data) directly under `CREDENTIALS_MASTER_KEY`. It writes `key_version`, and an `ON CONFLICT (item_id)` upsert replaces the row.
- `getDecryptedCredential` (`:81-101`) first logs the attempt to `credential_access_log`, then decrypts with `resolveMasterKeyFromEnv(key_version)`.

The callers:

- the proposal confirm path, inside its transaction (`backend/packages/data/src/inbox/proposalActions.ts:283`);
- mail sync (`mail/mailSyncJob.ts:224`) and mail send (`mail/send.ts:204`). Both pass the `Pool` on purpose, so the access-log insert survives a failed decrypt.
- MCP connections (`mcp/mcpConnectionFactory.ts:128`). They map a decrypt error without a string `code` to `credential_decryption_failed` (`:135-150`).

#1031 added:

- `sealSecret`/`openSecret` (XChaCha20-Poly1305 with associated data) in `@semprec/credentials`;
- the tenant-owned `tenant_keys` table;
- `getTenantDataKey(client)` and `getOrCreateTenantDataKey(client)` in `backend/packages/data/src/credentials/tenantKeysStore.ts`. Both resolve the tenant through `app_tenant_default()` and return `{ tenantId, dataKey }`.

Credentials move to the tenant key in steps that stay one-release rollback safe:

1. **This issue** teaches the reader both schemes and adds the `scheme` marker. Every write stays on the master key.
2. **#1060** switches new writes to the tenant key. It runs only after the release checkpoint #1058 has confirmed that a release with this read path runs in production. A rollback from that release therefore lands on code that can open `tenant` rows.
3. **#1062** re-encrypts the existing rows.
4. **#1069** retires the master scheme.

So this issue changes no stored secret. The `tenant` branch only reads rows that later releases write, which is the point of shipping it first: say so in the PR description and in the function's doc comment, so it is not mistaken for dead code.

## Task

Load `db-migrations`, `state-writes` and `error-handling`.

1. **Migration** (take the next free ordinal at commit time; additive):
   ```sql
   ALTER TABLE external_credentials ADD COLUMN scheme text NOT NULL DEFAULT 'master';
   ALTER TABLE external_credentials ADD CONSTRAINT external_credentials_scheme_check
     CHECK (scheme IN ('master', 'tenant'));
   ```
   The constant default causes no table rewrite. The previous release's inserts omit the column and get `master`, which is exactly what they write.
2. **`externalCredentialsStore.ts`:**
   - Add a module-private `credentialAssociatedData(tenantId: string, itemId: string): Buffer`. It returns the UTF-8 bytes of `semprec:external-credential:v1:<tenantId>:<itemId>`, both values in lowercase canonical UUID text. #1060 seals with the same function.
   - `storeCredential`: behaviour unchanged (secretbox under the master key, `key_version`), except that the insert and the `ON CONFLICT (item_id) DO UPDATE` both set `scheme = 'master'` explicitly. A re-store over a `tenant` row then never leaves a mismatched marker.
   - `getDecryptedCredential`:
     - Also select `tenant_id` and `scheme`; validate `scheme` with `assertKnownValue`.
     - The access-log insert is unchanged and still runs before any decrypt attempt.
     - `master` → today's path.
     - `tenant` → `getTenantDataKey(client)`. When the key is missing, or its `tenantId` differs from the row's `tenant_id`, throw a plain `Error("No data key for this credential's tenant")` without a `code`. Otherwise return `openSecret(…, credentialAssociatedData(row.tenant_id, input.itemId)).toString("utf8")`.
   - Update the header comment: this file is still the only place that decrypts, and it reads both schemes.
3. **Tests** go in `backend/packages/data/src/__tests__/externalCredentialsStore.test.ts` (new).
   - A `tenant` row is fabricated the way #1060 will write it: `getOrCreateTenantDataKey`, then `sealSecret` with the documented associated-data bytes, then a raw `INSERT … scheme = 'tenant'`.
   - A legacy row is made by `storeCredential`, or by a raw `INSERT` that omits `scheme`.
   - Inside a transaction, a tenant's scope is set with #975's `withTenantTransaction(pool, tenantId, fn)`.
   - `Pool`-level cases (the logged-attempt case) run while tenant zero is the only tenant, so the sole-tenant fallback of `app_tenant_default()` resolves it without a scope.

## Scope

### In scope
- The `scheme` column.
- The explicit `master` marker on writes.
- Dual-scheme reading.
- The shared associated-data function.

### Out of scope
- Sealing new credentials under the tenant key (#1060).
- Re-encrypting existing `master` rows (#1062).
- Retiring the `master` scheme, the secretbox functions and `key_version` (#1069).
- Backups of `tenant_keys` (#1064).
- Deleting a tenant's key on account deletion (#1049).
- Changes to `credential_access_log`.

## Acceptance criteria

All integration. Two-tenant cases use #975's `createTestTenant(pool)` and `createRuntimeRolePool(adminPool, "semprec_data")`.

**Master rows**
- `storeCredential` still writes a `master` row with `scheme = 'master'`, decryptable through `getDecryptedCredential`, with exactly one `credential_access_log` row per attempt.
- A row inserted without `scheme`, as the previous release inserts, reads back as `scheme = 'master'` and decrypts.

**Tenant rows**
- A fabricated `tenant` row in tenant zero decrypts to its plaintext and is logged.
- `storeCredential` over an existing `tenant` row turns it back into a `master` row that decrypts to the new plaintext.

**Binding**
- Item X's `tenant` `ciphertext`/`nonce` copied onto item Y's row (same tenant, `scheme = 'tenant'`) make decryption of Y throw. The attempt is still logged when called with the `Pool`.
- Tenant A's `tenant` ciphertext copied onto one of tenant B's rows makes decryption of that row in B's scope throw.
- After the tenant's `tenant_keys` row is deleted, decrypting its `tenant` rows throws.

**Error shape**
- The thrown error carries no `code` property, so `connectMcpServer` maps it to `credential_decryption_failed`.

**Regression**
- The existing mail sync, mail send and MCP suites pass unchanged, including `mcpConnectionFactory.test.ts:236-254`, which still forces a failure through `key_version` on a `master` row.
