## Context

`POST /mcp` accepts two kinds of bearer token (`backend/services/semprec-api/src/mcp/mcpHandler.ts:88-113`):
1. **A restricted MCP run credential.** It is resolved first by `resolveMcpRunCredential` (`:94`, `backend/packages/data/src/mcp/mcpRunCredentialAction.ts:90-95`), which calls `getActiveMcpRunCredentialByTokenHash` (`backend/packages/data/src/mcp/mcpRunCredentialsStore.ts:69-93`). That query joins `agent_run_mcp_credentials` to `agent_runs` and requires an unexpired credential and a `running` run (`:79-83`). The actor is `{ userId: actor_user_id, runId, agentProjectItemId }`, with the capability subset.
2. **Otherwise, a human session** through `authenticateRequest` (`:111-112`).

#981 changed the handler in three ways:
- `resolveActor` returns `tenantId` for a session actor;
- the run-credential lookup at `:94` runs inside `runAsSystem("mcp-run-credential-lookup")`;
- everything after `resolveActor` runs inside `runInTenant(tenantId, …)`; a run-credential actor's tenant is resolved interim from the credential owner with `getUserTenantBinding` (401 without an active binding). This issue replaces that interim lookup with the credential row's own `tenant_id`.

A credential actor's request still runs with no tenant scope, and its lookup runs in system scope. `agent_runs` is a tenant table under a RESTRICTIVE RLS policy `tenant_isolation` (`tenant_id = (SELECT app_tenant_default())`, with `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())`). So the join finds the run only while exactly one tenant exists. With two tenants, or after the strict switch (#1067), every credential would stop working. The tenant cannot come from the run either: the run is invisible until the tenant is known.

`agent_run_mcp_credentials` (`backend/packages/data/src/db/migrations/0043_agent_run_mcp_credentials.sql:16-26`) is a **global** table (`semprec:tenancy=global`), because its token is resolved before any tenant is known. Like `users`, it now carries the owning tenant explicitly, so the token resolves to `(tenant)` in the global plane. Everything else is read under RLS inside that tenant.

Minting happens at `POST /api/agent-runs/mcp-credentials` (`backend/services/semprec-api/src/agentRunHandler.ts:60-89`). The handler checks only that `projectItemId` is a non-empty string (`:26-28`) and passes it straight to `mintMcpRunCredential` (`mcpRunCredentialAction.ts:63-81`), which calls `createAgentRun` with it (`:69-74`). `agent_runs.project_item_id` has no FK, so any string is accepted:
- a non-UUID value fails in Postgres, with a 500;
- a random UUID, or another tenant's Projects item id, is stored as the run's `agentProjectItemId`. The response echoes it back (`:84`).

The run must belong to a project of the caller's tenant. A foreign project id must behave exactly like a non-existent one.

Tenancy state this issue builds on:
- `runInTenant(tenantId, fn)`, `runAsSystem(reason, fn)` and `currentTenantScope()` come from `@semprec/shared`.
- `withTransaction`, autocommit `pool.query` on a `createPool` pool and `pool.connect()` clients set the GUC `app.tenant_id` from the ambient scope: `''` for system scope.
- Every tenant table has `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)`.
- `tenants(id, status ∈ provisioning|active|suspended|deleting)` is global.
- #980 answers 401 for a session whose tenant is not `active`, exactly like a bad token.

## Task

Load `db-migrations` (additive column on a live table), `state-writes` (the mint transaction and its pre-check), `io-hardening` (a bearer token resolved before the tenant is known) and `error-handling` (unknown, expired and inactive tokens must be indistinguishable).

1. **Migration.** Take the next free migration ordinal at commit time, for example `NNNN_agent_run_mcp_credentials_tenant.sql`:
   `ALTER TABLE agent_run_mcp_credentials ADD COLUMN tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id);`
   `COMMENT ON TABLE agent_run_mcp_credentials IS 'semprec:tenancy=global';`
   - The default is non-volatile, so it is evaluated once: every existing row gets tenant zero without a table rewrite.
   - The previous release's inserts omit the column and keep working under the same default.
   - The header comment says the table stays global (token resolved before the tenant is known), why `tenant_id` is still needed, and that the change is additive and rollback-safe.
   - No new grants: the column rides on the table's existing grants.
2. **Store (`mcpRunCredentialsStore.ts`).**
   - `createMcpRunCredential` takes the tenant from the run itself, in one statement: `INSERT INTO agent_run_mcp_credentials (tenant_id, agent_run_id, token_hash, capabilities, expires_at) SELECT r.tenant_id, r.id, $2, $3, $4 FROM agent_runs r WHERE r.id = $1 RETURNING …`. Keep `requireSingleRow`.
   - Add `getMcpRunCredentialTenantByTokenHash(client, tokenHash): Promise<string | null>`. It runs `SELECT c.tenant_id FROM agent_run_mcp_credentials c JOIN tenants t ON t.id = c.tenant_id WHERE c.token_hash = $1 AND c.expires_at > now() AND t.status = 'active'`, a global-plane read.
   - `getActiveMcpRunCredentialByTokenHash` adds `AND c.tenant_id = r.tenant_id` and returns `tenantId` as a new field of the exported `ActiveMcpRunCredential` type.
   - Neither raw hash lookup is exported from `@semprec/data` (`backend/packages/data/src/index.ts:363-371` stays unchanged).
3. **Resolution (`mcpRunCredentialAction.ts`).** `resolveMcpRunCredential` becomes `(pool: Pool, token: string): Promise<ActiveMcpRunCredential | null>`:
   - First, inside `runAsSystem("mcp:runCredentialTenant", …)` with a `withTransaction`, it reads the token's tenant with `getMcpRunCredentialTenantByTokenHash`. `null` returns `null`.
   - Then, inside `runInTenant(tenantId, …)` with a `withTransaction`, it reads `getActiveMcpRunCredentialByTokenHash` under RLS.
   - Unknown, expired, run-not-running and inactive-tenant tokens all return `null`. It must be called with no scope or from a system scope, since `runAsSystem` throws inside a tenant scope. Update the docstring.
4. **Mint guard (`mcpRunCredentialAction.ts`).** `mintMcpRunCredential` takes a `PoolClient`: its only production caller passes one from `withTransaction` (`agentRunHandler.ts:78-80`). After `assertCapabilityIds` (`:67`) and before `createAgentRun`, on the same client, it requires a live item of the Projects database: `getDatabaseByModuleId(client, PROJECTS_MODULE_ID)`, then `getItemById`, then `deletedAt === null`. This mirrors `assertAuthenticatedAgentIdentity` (`backend/packages/data/src/chokePoint/authorization.ts:44-69`); under RLS, a foreign item is invisible. Otherwise it throws `new NotFoundError("Project not found")` with no details. A missing Projects database stays a plain `Error`, an infrastructure fault.
5. **Handlers.**
   - `agentRunHandler.ts`: validate `projectItemId` with `assertUuid(…, "projectItemId")` (`backend/services/semprec-api/src/adapter/requestValidation.ts:25-30`).
   - `mcpHandler.ts`: inside #981's `runAsSystem("mcp-run-credential-lookup")` wrapper, the credential branch calls `resolveMcpRunCredential(pool, bearerToken)` without its own `withTransaction`, and `resolveActor` returns `credential.tenantId` as the actor's `tenantId`. The existing `runInTenant(tenantId, …)` around the post-resolution work then applies to credential actors too. Nested `runAsSystem` and entering a tenant from system scope are both allowed (#978).
   - The session fallback and every response shape stay unchanged.
6. **Tests.** Update the callers that mint with a random project id, or call `resolveMcpRunCredential` on a client, to seed a Projects item and use the new signatures:
   - `backend/services/semprec-api/src/mcp/__tests__/mcpHandler.test.ts:253`;
   - `backend/services/semprec-api/src/__tests__/agentRunHandler.test.ts:121-215`;
   - `backend/packages/data/src/__tests__/mcpRunCredentialExpiry.test.ts:24-31,70,96`;
   - `backend/services/semprec-api/src/mcp/__tests__/mcpGenericOperationsContract.test.ts:55`.
   Then add the cases below.

## Acceptance criteria

All integration tier.
- **Column (`mcpRunCredentialExpiry.test.ts` or a new store test).** A credential minted inside tenant zero's scope stores `tenant_id` = its run's `tenant_id`. The column is `NOT NULL` with default `app_tenant_default()`, and the table comment is `semprec:tenancy=global`.
- **Credential path runs in its tenant (`mcpHandler.test.ts`).** A valid credential's `tools/list` and `tools/call` succeed exactly as before. The operation executes inside `runInTenant(<the credential's tenant>)`, observable as `currentTenantScope()` in a spied operation or the GUC in its transaction.
- **Indistinguishable refusals (`mcpHandler.test.ts`).** Each of the following answers the same 401 body as an unknown token:
  - an unknown token;
  - an expired credential;
  - a credential whose run is no longer `running`;
  - a credential of a tenant whose `status` was set to `suspended` (restored afterwards).
- **Mint guard (`agentRunHandler.test.ts`).**
  - A non-UUID `projectItemId` gets 400 `validation_failed`.
  - A random UUID, a non-Projects item id (e.g. a Tasks item) and a soft-deleted Projects item each get 404 `{ error: "Project not found", code: "not_found" }`, with no `agent_runs` or credential row created.
  - A live Projects item gets 201 as before.
- **Foreign ids (second tenant from `createTestTenant(pool)`, listeners over `createRuntimeRolePool(pool, "semprec_data")`, both from #975's `@semprec/data/testSupport`).**
  - Tenant B's session minting with tenant A's Projects item id gets a response byte-identical to the random-UUID case.
  - A's credential calling `item.get` with B's item id gets the same result as an unknown id, and `item.list` on A's database never returns B's rows.
  - Each tenant's credential resolves into its own tenant.
- **Rollback safety (review).** The migration only adds a defaulted column and restates the comment. The previous release's mint insert, which omits `tenant_id`, still succeeds.
