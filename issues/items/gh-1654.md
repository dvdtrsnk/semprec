**Model tier:** medium

## Context

Model tier rationale: A small extension of an existing, already-validated upload mechanism (allow one more relation and test it) over the existing streaming handler, with no new lifecycle or isolation contract.

A task can have attachments: files uploaded from the phone (camera, photo library or file browser) and linked to the task. In the data model an attachment is a Files item linked to the task through `Files.tasks` (created by #1540); removing an attachment only removes the link, the file stays in the Files collection (`DELETE /api/items/:taskId/relations/files/:fileId`).

Today `POST /api/files` (`backend/services/semprec-api/src/filesHandler.ts`, `createFilesRequestListener`, which uses `ingestUploadedFile` from `blobs/fileUploadStore.ts`) is a streaming listener with `Content-Type` and `X-Filename` headers and the size limit from the `maxFileSizeMb` setting. It cannot be replaced by a custom module route because module routes go through `createAdapterRequestListener`, which buffers the body as JSON before the handler runs. Uploads deduplicate by content hash: when the bytes match an existing non-deleted file, `ingestUploadedFile` returns it (`created: false`, HTTP 200) and creates nothing new.

#1645 adds the shared upload mechanism: the request headers `X-Attach-To-Item` (an item id) and `X-Attach-Relation` (a relation key on the Files side) so an upload is linked to an item in the same request, with the target validated before the stream is read and again inside the ingest transaction, deduplication handled (an existing file gets only the new link, 200; a new file 201), an invalid target answered 404, and a relation key that is not a Files relation answered 400 with field `X-Attach-Relation`. This issue makes tasks a valid target of that mechanism using the relation key `tasks`. Decision: attachments go through `POST /api/files` and its content deduplication (one Files item can be attached to two tasks, and the client does not edit the file after upload), not through a two-step blob upload followed by an item create.

File type detection and the metadata returned for attachments (size, MIME type) belong to #1410 and #1412; the project shown on an attachment belongs to #1702, which builds on this issue.

Decision: when an existing file with its own project is attached to a task, the file keeps its own project; inheriting the task's project is decided by #1702.

## Task

Load `io-hardening`, `state-writes` and `testing`.

1. Allow `tasks` as an `X-Attach-Relation` value with a task item as the target in the attach-target validation that #1645 introduces (the Files-side relation `Files.tasks`, target database Tasks). Where H12 holds a registry of allowed relation keys, add the entry there; no new code path is added to the handler.
2. A target task that does not exist, is in the trash, or belongs to another tenant is answered 404 before the body is read; no blob and no Files item are created. A relation key that is not a relation of the Files database is answered 400 with `{field: "X-Attach-Relation"}`.
3. Tests (real database, through the HTTP listener): upload of a JPG and a PDF with `X-Attach-To-Item` set to a task and `X-Attach-Relation: tasks` creates the Files items and the `Files.tasks` edges; the same bytes uploaded for two tasks yield one Files item and two edges, the second response being 200; an unknown or deleted task yields 404 and creates no blob and no Files item; `X-Attach-Relation` naming a key that is not a Files relation yields 400 with field `X-Attach-Relation`.

## Scope

### In scope

- Making tasks an accepted attach target of the shared upload headers, and the tests proving it.

### Out of scope

- The upload headers and their generic validation: #1645.
- File type from content and blob metadata in task reads: #1410, #1412.
- Inheriting the task's project onto attachments: #1702.
- Removing an attachment (the existing relation delete route already does it).

## Acceptance criteria

- When a JPG or PDF is uploaded with `X-Attach-To-Item` of an existing task and `X-Attach-Relation: tasks`, then a Files item exists with the correct type and a `Files.tasks` edge to that task.
- When the same bytes are uploaded to two different tasks, then one Files item exists with two edges, and the second response is 200.
- When the target task is missing or in the trash, then the response is 404 and no blob and no Files item exist.
- When `X-Attach-Relation` names a key that is not a relation of Files, then the response is 400 with field `X-Attach-Relation`, and nothing is created.
