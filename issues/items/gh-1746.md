## Context

Model tier rationale: A new durable desired/current-state table and write-back across three providers (UID MOVE with fallback, Gmail labels, Graph move with id change), with failure and idempotency ownership in the sync worker.

Archiving or deleting a message in Semprec must also move it at the mail provider, otherwise the next sync puts it back. Today nothing moves messages at the provider: `imapFlowClient.ts` only has `setMessageFlag`, `graphRestClient.ts` only `patchMessage`, and the Gmail client `modifyMessageLabels` (`backend/packages/data/src/mail/`). Flag changes already follow the desired/current-state pattern of `docs/adr/2026-09-20-desired-current-state-sync-for-provider-writebacks.md` (`mail_message_flag_sync_state`, drained by the reconcile of the sync owner, `mail/mailFlagWriteback.ts`). Moves follow the same pattern. The provider sync transports are built by #1510 (IMAP), #1505 (Gmail) and #1508 (Graph).

Facts: on IMAP the UID lives on the `Emails.folder` relation edge's metadata (`mail/folderMembershipStore.ts`) and a moved message gets a new UID in the target folder; the flag write-back targets a UID, so the edge's UID must be updated after a move or later flag writes hit a wrong UID. Gmail archive means removing the `INBOX` label, delete means `users.messages.trash`. Graph moves with `POST /me/messages/{id}/move` to `archive` or `deleteditems` and returns a new message id, which replaces `mail_message_meta.provider_message_id`.

The routes that record moves are #1917 (archive and trash) and the restore route of #2033 (back to the inbox); this issue builds the durable queue and the provider writes for all four targets.

Decisions: the table holds one row per message; a pending move is never undone by the reconcile (the folder edge is not restored while desired and current differ); after a bounded number of attempts (default 5) a row is marked `failed` with a reason (for example the message no longer exists at the provider) and stops being retried; `desired_purpose` is `archive`, `trash`, `inbox` or `sent`: restoring a thread from Archive or Trash records `inbox` for an incoming message and `sent` for the user's own message (the product owner decided that everything archived or trashed can be restored); a row whose desired purpose already matches the message's location at the provider is confirmed without a provider call.

3. Extend the transports: IMAP `moveMessage(path, uid, targetPath)` using `UID MOVE`, and when the server lacks the MOVE capability `UID COPY` + `\Deleted` + `UID EXPUNGE`, returning the new UID (COPYUID) when the server reports it, the target being the folder with the matching `specialPurpose` (`archive`, `trash`, `inbox`, `sent`) of the message's mailbox; Gmail archive (remove `INBOX`), trash (`users.messages.trash`), inbox (`users.messages.untrash` when the message is in Trash, then add `INBOX`) and sent (`users.messages.untrash`; the `SENT` label stays on the message); Graph `moveMessage(id, destination)` with `archive`, `deleteditems`, `inbox` or `sentitems`, returning the new id.
4. Drain pending moves in the reconcile of each provider next to the flag write-back: IMAP rewrites the `{ uid }` metadata of the moved `Emails.folder` edge; Graph overwrites `provider_message_id`; a message that does not exist at the provider ends the row as `failed`. While a row is pending the reconcile does not recreate the old folder edge.
5. Add tests with provider fakes: each provider moves and confirms for each of the four purposes; IMAP without MOVE uses the fallback; after an IMAP move a later flag write targets the new UID; a Graph move changes the provider message id; a missing message becomes `failed` after the attempt limit; a retry after a partial failure is idempotent; tenant isolation of the table.

## Scope

### In scope

- The move queue table and store, the three provider move writes, and draining them in the reconcile.

### Out of scope

- The routes that record moves and move folder edges locally: #1917.
- The restore route that records `inbox` and `sent` moves and moves the folder edges locally: #2033.
- Running the sync worker in production.

## Acceptance criteria

- When a pending archive move exists, then the next reconcile moves the message at the provider and marks the row `done`, and the reconcile does not recreate the inbox edge.
- When a pending `inbox` move exists for a message in Trash, then Gmail untrashes it and adds `INBOX`, IMAP moves it to the Inbox folder and Graph moves it to `inbox`, and the row is `done`; a pending `sent` move puts an own message back in the Sent folder (Gmail: untrash only).
- When a desired purpose already matches the message's location at the provider, then the row is confirmed without a provider call.
- When an IMAP server lacks MOVE, then COPY, `\Deleted` and EXPUNGE are used.
- When an IMAP message was moved, then the folder edge carries the new UID and a later flag write-back uses it.
- When a Graph message is moved, then `provider_message_id` holds the new id.
- When the provider no longer has the message, then after the attempt limit the row is `failed` with a reason and is not retried.
