## Context

Model tier rationale: A mechanical, idempotent reorder of four option lists following an existing cutover pattern, with no new contract.

Option order now drives sorting and filter-sheet order (#1408), but the system catalogs seed their options in an order that does not match how the app presents them (`backend/packages/data/src/seed/seedTenDatabases.ts`): project status [inProgress, done, archived, longTerm], person relationship [parent, therapist, closeFriend, girlfriend, client, neighbor], health-record status [resolved, monitoring], event type [event, standup, meeting]. Seeded schemas are locked, so existing tenants only change through a code-level cutover (`runTenantCutoverMigrations` in `db/tenantCutoverMigrations.ts`, pattern of `transcription/transcriptsCatalogCutoverMigration.ts`).

This issue changes the order for new tenants (seed) and existing tenants (cutover). It builds on the unified relationship list (#1549), which adds colleague, craftsman and doctor to the same People option list, and is built on by the health-record tag work (#1700).

Decision: target order is projects status [inProgress, longTerm, done, archived]; health records status [monitoring, resolved]; people relationship [client, closeFriend, parent, girlfriend, therapist, neighbor, colleague, craftsman, doctor] (confirmed by the product owner; this option list of the People relationship property is the one place the order is defined); events type [meeting, standup, event]. Decision: the cutover only reorders. It keeps each stored option object as it is (colors, extra fields), never adds or removes an option, ignores target keys that are not stored, and appends stored keys that are not in the target list at the end in their current order.

Shared-file ordering: this issue also waits for #1575 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations` and `testing`.

1. In `seedTenDatabases.ts` set the four `selectConfig([...])` lists to the target order for fresh installs (the People list as it stands after #1549, reordered; do not re-add options that issue owns).
2. Add `backend/packages/data/src/seed/selectOptionOrderCutoverMigration.ts` exporting a function run per tenant: `LOCK TABLE properties IN EXCLUSIVE MODE`, resolve the four properties through their databases (`getDatabaseByModuleId` as the transcripts cutover does), compute the reordered `config.options`, `UPDATE properties SET config = jsonb_set(config, '{options}', $2::jsonb)` only when the order differs, skip a missing database or property. Idempotent: a second run writes nothing.
3. Call it from `runTenantCutoverMigrations` in `db/tenantCutoverMigrations.ts`.
4. Tests: a tenant seeded with the old order is reordered; a second run writes nothing; stored extra keys are kept at the end; a missing database is a no-op; option colors survive.

### Out of scope

## Acceptance criteria

- When a fresh tenant is seeded, then the four lists are in the target order.
- When the cutover runs on a tenant with the old order, then each list is reordered and every option keeps its other fields.
- When the cutover runs again, then it writes nothing.
- When a stored option is not in the target list, then it stays after the target options in its previous relative order.
