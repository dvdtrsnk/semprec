### Requirement gh-1816: [mail-threads 23/28] Publish thin mail-thread realtime invalidations

#### Context

Model tier rationale: A new realtime frame crosses the data layer, the NOTIFY publisher, the sync server and the client parser, and its tenant and user scoping is a cross-process isolation contract.

Realtime today only tells a client that an item changed or that a database schema changed. Relation edges send nothing, so a mail thread, which is a group of Emails items, cannot be refreshed reliably in the Mail screen, the mailbox counts, the thread detail or the overview when new mail arrives. Invalidations are thin references (`docs/adr/2026-09-12-thin-user-scoped-realtime-invalidations.md`) and are fanned out per tenant, optionally narrowed to one user's sockets (`docs/adr/2026-10-16-tenant-scoped-realtime-fan-out.md`).

The data layer emits `InvalidationEvent` (`backend/packages/data/src/realtimeHook.ts`); `@semprec/realtime` wires it to NOTIFY (`pgNotifyPublisher.ts`, `wireHooks.ts`), `syncServer.ts` turns it into an `OutboundFrame` (`protocolV1.ts`), and the client parses it in `backend/packages/realtime-client/src/serverFrame.ts`. #1811 adds the first user-facing frame of this kind in the same chain, and later frame additions are ordered after it so the shared catalog files do not conflict.

This issue adds the mail thread frame and wires mail ingest to it. The other mail writers (marking read, flagging, archiving, sending, drafts, project assignment) wire it in their own issues, which wait for this one: #1865, #1867, #1896, #1869, #1872.

#### Task

2. Add `{ type: "invalidate"; scope: "mailThread"; threadId: string }` to `OutboundFrame` in `backend/packages/realtime/src/protocolV1.ts`; add the matching `invalidation` variant to `RealtimeMessage` and to `parseRealtimeMessage` in `pgNotifyPublisher.ts` (a `threadId` that is not a UUID is dropped).
3. In `syncServer.ts`, map the invalidation to the new frame and send it with `sendToTenant(tenantId, frame, parsed.userId)`, unchanged tenant and user narrowing.
4. In `backend/packages/realtime-client/src/serverFrame.ts`, parse the new frame (reject a non-string `threadId`).
5. In `ingestEmailMessage` (`mail/ingest.ts`), after the message is stored and its thread resolved, register `runAfterCommit(client, () => notifyInvalidation({ scope: "mailThread", threadId }))` once per newly created message, with no `userId`. A rolled-back ingest sends nothing.
6. Add tests in the realtime and client packages (frame round trip, malformed payload dropped, tenant isolation, user narrowing) and an ingest test (one invalidation after commit, none after rollback).

### Requirement gh-1863: [realtime-derived 01/07] Add user-scoped invalidations for agent runs

#### Context

Model tier rationale: It extends the closed realtime protocol across publisher, listener, server and client and attaches publication to many run and approval transitions that must fire only after commit and only to the right tenant and user, so a missed or misdelivered frame is a cross-process isolation defect.

A running agent run shows new steps and a changing status label without a reload, and the "latest runs" list and the project's attention dot change live ("Working..." becomes resolved, "executing..." becomes "executed after approval"). Today only one run can be watched (`agent:watch` with `agent:event` / `agent:delta`, `backend/packages/realtime/src/agentRunWatch.ts`), and nothing tells a client that a run was created, finished, or changed its approval state. `agent_runs` rows are not items, so no `invalidate` frame exists for them.

The realtime layer is a closed catalog. `OutboundFrame` in `backend/packages/realtime/src/protocolV1.ts` lists every frame a client can receive, `RealtimeMessage` and `parseRealtimeMessage` in `backend/packages/realtime/src/pgNotifyPublisher.ts` list every payload inside the `{ tenantId, message }` NOTIFY envelope, and `InvalidationEvent` in `backend/packages/data/src/realtimeHook.ts` is what the data layer hands to `notifyInvalidation` (turned into a NOTIFY by `wireRealtimeHooks`). It is delivered only to the sockets of the run's `actor_user_id` (`AgentRunRow.actorUserId`, `backend/packages/data/src/agentRuns/agentRunsStore.ts`) inside the tenant. It is published when a run is created, when it finishes (done or error, including the startup-repair close), and whenever the run's derived display status or approval state can change (#1820 derives the display status from the run status plus a pending approval). Publish `agentRuns` together with the approval request invalidation, through one shared helper, so the two cannot drift.

The summary of the answer in the Semp chat is refreshed by the `sempThread` scope (#1395), not by this one. Later issues in the chain add the project agent scope (#1866) and the rest.

### Requirement gh-2023: [agent-usage 11/12] Refresh Semp status when the gateway first refuses a call for the tenant's cap

#### Context

Model tier rationale: It adds a cross-process side effect to the AI gateway's refusal path, which must stay exactly as it is, publish only after the budget transaction has rolled back, and deduplicate per tenant and window inside a long-running process.

#1871 derives two Semp status problems at read time from the budget summary of #1456: "AI has no limit set" (`aiBudgetMissing`) and "Limit exhausted, resets at {time}" (`aiBudgetExhausted`). Clients re-read `GET /api/semp-status` when they receive a Semp status invalidation (#1868), but nothing publishes one when a budget runs out, so a connected app keeps showing the old status (and the problem count in the profile and the overview stays stale) until the user reopens the screen.

Today the AI gateway refuses a call in `assertWithinBudget` (`backend/packages/ai-gateway/src/gateway.ts`): it distinguishes the causes `noTenantBudget`, `tenantDaily`, `tenantMonthly`, `globalDaily` and `globalMonthly` only for the log, rolls the reservation back and throws the same `BudgetExceededError` for every cause.

This issue makes the gateway publish the Semp status invalidation of #1868 the first time in a window that it refuses a call because of the tenant's own budget. The refresh at the reset instant, when the exhausted problem disappears, is #2024.

Decisions: (1) Only a refusal caused by the tenant's own state (`noTenantBudget`, `tenantDaily`, `tenantMonthly`) publishes; a refusal caused by an operator-wide cap (`globalDaily`, `globalMonthly`) does not, because it is not the tenant's state and must not be revealed. (2) The first such refusal in a window publishes one invalidation, deduplicated in the gateway process per tenant and window (the reset time of the exhausted window; for `noTenantBudget` the current day in the tenant's time zone). A repeat after a process restart is harmless because invalidations are idempotent. (3) Publishing never changes the refusal.

#### Task

Load `ai-gateway`, `state-writes` and `testing`.

1. In `assertWithinBudget` (`gateway.ts`), when the refusal cause is `noTenantBudget`, `tenantDaily` or `tenantMonthly`, publish the Semp status invalidation of #1868 for that tenant, once per tenant and window as decided above, using the publisher that #1868 provides. Publish only after the refusal's transaction has rolled back (never inside the budget lock's transaction). A publish failure is logged with the tenant id only and swallowed; the caller receives the same `BudgetExceededError` as before.
2. Keep the deduplication state in the gateway process, bounded (an entry is dropped once its window has passed).
3. Tests: a first tenant-cap refusal publishes exactly one invalidation for that tenant and a second refusal in the same window none; a refusal in the next window publishes again; a refusal for a missing budget row publishes once; an operator-wide refusal publishes none; when publishing throws, the refusal and its error are unchanged and no reservation remains.

The voice rows written by the streaming speech-to-text route of #1396 (operation `voice_transcribe_stream`, one row per reserved chunk) and the text-to-speech route of #1399 (operation `voice_synthesize`) carry neither, so per-run and per-reply usage (#1822, #1889) never include speech.

Callers: the voice session of #1734 streams the user's speech to speech-to-text and the answer of a queued turn to text-to-speech; the read-aloud route of #1626 synthesizes one stored message.

Decision: the attribution unit is the Semp assistant message of the turn, as for the other calls of a turn. Text-to-speech of an answer, live or read aloud, carries that message's id and its run id. The speech of a spoken question carries the id of the assistant message created for the turn that the question started; the run id is not known yet when that speech is consumed, so these rows carry the message only, and the run is reached through `semp_messages.agent_run_id`.

Decision: speech that never becomes a message (muted, ended or a stop command) keeps no attribution and counts only in the tenant's totals.

The Voice activity in the AI usage report is a label of the two voice operations in the operation breakdown and is not part of this issue.

### Requirement gh-2024: [agent-usage 12/12] Refresh Semp status when an exhausted AI budget window resets

#### Context

Model tier rationale: A one-shot scheduled job enqueued from the AI gateway's refusal path must fire at an exact time boundary and stay idempotent across processes and restarts, and it is not yet settled which process may enqueue into the job queue.

### Requirement gh-1822: [agent-usage 09/12] Aggregate AI spend per agent run

#### Context
