## Context

The Inbox tick (`createSemprecTickAction` in `backend/packages/data/src/inbox/inboxTickAction.ts`, lines 457-575) reads the existing Processing proposal through `findExistingProposal` (lines 133-152), which uses the unlocked `itemsStore.getItemById` (line 148), and later writes it back with `updateItemWithClient(... status: "proposed" ...)` (lines 519-535) without `ifVersion` and without re-reading its status. Between that read and that write sits the LLM call (`computeProposalEnvelope`, line 504). A user's confirm/reject (`confirmProposalWithClient` in `backend/packages/data/src/inbox/proposalActions.ts` locks the row with `lockLiveProposal`, line 40, and commits `status: 'confirmed'`) that commits in that window is overwritten: the tick's `LOCKED_PROPOSAL_STATUSES` check (line 501) ran against the stale snapshot, and `updateItemProperties` only locks at write time with no version check, so the confirmed card silently flips back to `proposed` with a stale envelope. The same stale-snapshot write exists in `writeNeedsClarification` (lines 359-387, the `existingProposal` branch) and `invalidateProposalForDeletedSource` (lines 413-434).

`backend/review-rules/rules.md`: a pre-check that decides whether a write is allowed is only a guard when it runs inside the same transaction as the write and on the row that write targets. Sibling issue C5 of this batch moves the LLM call out of the transaction and reuses the guard this issue adds.

## Task

1. `inboxTickAction.ts`: new module-private `lockUnlockedProposal(client, config, snapshot: ItemRow): Promise<ItemRow | null>` that runs `itemsStore.lockItemById(client, config.processingProposalsDatabaseId, snapshot.id)` and returns the locked row only when it exists, `deletedAt === null`, its `status` is not in `LOCKED_PROPOSAL_STATUSES`, and `updatedAt === snapshot.updatedAt`; otherwise it logs one structured line — a module-level `const logger = createLogger("inbox-tick")` from `@semprec/shared`, the same shape as `backend/packages/data/src/mail/logger.ts` (`docs/adr/2026-09-13-shared-structured-process-logging.md`) — `logger.info({ proposalId, reason }, "Skipping proposal write")` with `reason` one of `'gone' | 'deleted' | 'locked' | 'changed'`, and returns `null`.
2. Every write to an existing proposal in this file — the revise write (lines 519-535), `writeNeedsClarification`'s update branch, and `invalidateProposalForDeletedSource`'s update — first calls `lockUnlockedProposal`; on `null` it returns without writing. Each of those `updateItemWithClient` calls passes `ifVersion: locked.updatedAt` (the locked row's version), so the choke point's own check is the second line of defence. The `history` patch is computed from the locked row's `properties.history`, not the earlier snapshot.
3. Test in `backend/packages/data/src/__tests__/inboxTickProposal.test.ts` (integration): seed a typed Inbox item with an existing `proposed` card; inject a `computeProposal` fake that, before returning a new envelope, runs `confirmProposalWithClient` for that card in its own `withTransaction(pool, ...)` and awaits it; after the tick resolves, the card's `status` is still `confirmed`, its `proposal`/`fingerprint` are unchanged, and its `history` has no "Revised the proposal" entry. A second test: the same fake soft-deletes the card instead; the tick writes nothing and does not throw. Existing tests in that file keep passing unchanged.

## Scope

### In scope
- The locked re-check before every tick write to an existing proposal, `ifVersion` on those writes, and the concurrency tests.

### Out of scope
- Moving the LLM call out of the transaction (sibling issue C5 of this batch).
- A concurrent tick creating a second card for a source with no existing card (a different race, not observed).
- `proposalActions.ts` (already locks).

## Acceptance criteria

- When a confirm commits while the tick is between its read and its write, the card stays `confirmed` with its confirmed envelope and the tick writes nothing to it.
- When a card is soft-deleted or its `updatedAt` changed between the tick's read and its write, the tick skips the write and logs the reason instead of throwing.
- When nothing changed, the tick's revise/needsClarification/invalid writes land exactly as before (existing `inboxTickProposal.test.ts` cases pass).
