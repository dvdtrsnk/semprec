**Blocked by:** #978

## Context

Today every scheduled sweep runs once over the whole database. They are the eleven crontab tasks in `backend/packages/data/src/worker.ts:81-92`, among them:
- the heartbeat sweep;
- doc compaction and history cleanup;
- trash purge;
- run-event retention and MCP credential expiry;
- the mail sweeps;
- the observability check.

Row-level security now hides every tenant row unless the current tenant matches. That works through the transition only because a scope-less or system-scope query falls back to the sole tenant (`app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())`, from #968). Once enforcement is strict (#1067), system scope sees no tenant rows at all. A sweep must therefore visit each tenant in that tenant's own scope.

#978 added the tenant scope, exported from `@semprec/shared`:
- `runInTenant(tenantId, fn)` and `runAsSystem(reason, fn)`. `runAsSystem` inside a tenant scope, and a different tenant inside a tenant scope, both throw `TenantScopeConflictError`.
- `currentTenantScope()`.
- Every `withTransaction`, `pool.query` and `pool.connect()` on a `createPool` pool sets the GUC `app.tenant_id` from the scope.

#968 added the global table `tenants(id uuid PK, status text CHECK IN ('provisioning','active','suspended','deleting'), created_at, status_changed_at)`.

This issue builds the one helper that every per-tenant sweep issue then uses: #984, #985, #986, #987, #988, #989 and #999. It does not convert any sweep itself. Cross-tenant identifiers and operator aggregates are a different mechanism (router functions, #997).

Sweeps already commit in chunks and stop at a per-tick cap (`docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`), and each re-selects its due rows by predicate. That makes re-running a sweep for a tenant that already succeeded safe.

Testing needs more than one active tenant. The single-tenant guard prevents that in the shared test database unless the two-tenant harness from #975 is present. That harness drops the guard in the test database only, and provides `createTestTenant(pool, options?: { status })` and `getTenantZeroId()` in `backend/packages/data/src/testSupport/tenantFixtures.ts`.

## Task

Load `error-handling` (aggregated failures, nothing swallowed), `adr-conventions` (new ADR) and `state-writes` (the work runs ordinary transactions inside the tenant).

1. Create `backend/packages/data/src/tenancy/forEachActiveTenant.ts` exporting `forEachActiveTenant(pool: Pool, work: (tenantId: string) => Promise<void>): Promise<void>`. Callers use exactly this two-argument shape. The whole body runs inside `runAsSystem("tenant-fan-out", …)`, so it may be called with no scope or from a system scope. Called from a tenant scope, it throws `TenantScopeConflictError` before doing anything.
   1. It reads `SELECT id FROM tenants WHERE status = 'active' ORDER BY id` (typed row). No active tenant means it resolves without calling `work`.
   2. **Rotating start.** It keeps one process-local call counter. Call number `n` (0-based) starts at index `n mod k` of the `k` ordered ids and wraps around, so no tenant is always first.
   3. It visits the tenants sequentially. For each one it awaits `runInTenant(id, () => work(id))`. A thrown error is logged at error level with `{ err, tenantId }` and collected, and the loop continues with the next tenant. The calling job's `jobName` is already on the record through the trace context.
   4. After the loop, if any tenant failed, it throws `new AggregateError(errors, \`forEachActiveTenant: ${failed} of ${k} tenants failed\`)`, where `errors` are the original errors, unwrapped. The calling job then fails and graphile-worker retries it. Otherwise it resolves.
2. Export it from `backend/packages/data/src/index.ts` with one new export line, and add `forEachActiveTenant` to `EXPECTED_RUNTIME_EXPORTS` in `backend/packages/data/src/__tests__/publicSurface.test.ts`. That test freezes the package's runtime surface (`publicSurface.test.ts:44,537-538`).
3. Add the ADR `docs/adr/<YYYY-MM-DD>-system-work-fans-out-per-tenant.md` (`status: accepted`, `area: [backend]`). It records:
   - **The decision.** Scheduled system work runs in a system scope, enumerates active tenants with `forEachActiveTenant`, and does the existing per-tenant work inside `runInTenant`, sequentially, with the rotating start. One tenant's failure never skips the others, and failures are aggregated and rethrown so the job retries.
   - **Consequences.**
     - Each sweep keeps its own per-tenant chunk cap, so one tenant's backlog delays the others by at most one chunk. Each sweep issue owns this.
     - Suspended, provisioning and deleting tenants are skipped.
     - Cross-tenant identifiers and operator aggregates go through router functions instead (#997).
   - **Rejected alternatives.**
     - A runtime role with `BYPASSRLS` sweeping all tenants at once: one bug becomes a full cross-tenant leak.
     - One queued job per tenant per tick: more queue rows and contention for no isolation gain over a per-tenant transaction.
   - **References.** `[[2026-09-28-chunked-transactions-for-large-background-sweeps]]` and the tenant-scope ADR added by #978, by its slug.
4. Add `backend/packages/data/src/__tests__/forEachActiveTenant.test.ts` (integration). It creates the extra tenants with #975's `createTestTenant(pool, { status })`, imported from `../testSupport/testDb.js`. Tenant zero (`getTenantZeroId()`) also counts as an active tenant unless the test changes its status.

## Acceptance criteria

All criteria are integration tests in `forEachActiveTenant.test.ts`.

- **Visit and scope.** With three active tenants, one call visits each exactly once. Inside `work`:
  - `currentTenantScope()` is `{ kind: "tenant", tenantId: <the id passed to work> }`;
  - a `withTransaction` in `work` reads `app_current_tenant()` as that id.
- **Skipping.** Tenants whose status is `suspended`, `provisioning` or `deleting` are never passed to `work`.
- **No active tenant.** With no active tenant, the call resolves and `work` is never invoked.
- **Failures.** When `work` throws for the second visited tenant:
  - the third tenant is still visited;
  - one error record carrying `tenantId` is written;
  - the call rejects with an `AggregateError` whose `errors` contains exactly the thrown error (same instance) and whose message names `1 of 3`.
- **Rotation.** Over three consecutive calls, each of the three tenants is visited first exactly once, and every call still visits all three.
- **Called from a tenant.** Called inside `runInTenant(T)`, it rejects with `TenantScopeConflictError` and `work` is never invoked.
- **Scope restored.** After the call settles, resolved or rejected, the caller's scope is unchanged.
- **Export.** `forEachActiveTenant` is a runtime export of `@semprec/data`, and the frozen-surface test passes.
