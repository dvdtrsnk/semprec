## Context

Model tier rationale: The spec gives both SQL statements, the new file, its signature and error labels verbatim, so the change is transcription.

Harvest issue #1099 collected the open review findings of merged pull requests. This draft covers the finding of PR #944 at `backend/packages/data/src/migrationJob/propertyTypeMigration.ts:176`: the two `UPDATE items` statements in the property type migration's batch loop (the `jsonb_set` conversion at :176 and the `properties - $3` key removal at :189) run directly through `client.query`, bypassing the choke-point that owns every write to item state. The bypass pre-dates PR #944, which only wrapped the statements in `requireAffectedRows`. The choke-point's own `updateItemWithClient` cannot be reused as-is: it merges a patch with `||` so it cannot remove a key, it refuses soft-deleted rows, and it fires hooks and heartbeats, none of which this migration does today. The fix is therefore a dedicated choke-point-owned write primitive with the same SQL, not a change of behavior.

## Task

1. Create `backend/packages/data/src/chokePoint/itemMigrationWrites.ts` exporting `migrateItemPropertyWithClient(client: PoolClient, input)`, where `input` is `{ databaseId: string; itemId: string; key: string; change: { kind: "set"; value: unknown } | { kind: "remove" } }`. For `set` it runs exactly `UPDATE items SET properties = jsonb_set(properties, ARRAY[$3]::text[], $4::jsonb), updated_at = now() WHERE database_id = $1 AND id = $2`; for `remove` exactly `UPDATE items SET properties = properties - $3, updated_at = now() WHERE database_id = $1 AND id = $2`. Each statement's result goes through `requireAffectedRows` and keeps the existing error labels `"property type migration value conversion update"` (set) and `"property type migration dropped value update"` (remove). It runs no hooks, enqueues no heartbeat and emits no invalidation, as today.
2. In `backend/packages/data/src/migrationJob/propertyTypeMigration.ts`, replace the two `client.query("UPDATE items ...")` calls in the batch loop with calls to `migrateItemPropertyWithClient` (`set` for a converted value, `remove` for a dropped one). The `markPropertyMigrationDroppedValues` call stays immediately before the `remove` call, inside the same transaction. Nothing else in the file changes.

## Scope

### In scope

### Out of scope
- The direct `UPDATE items` in `moduleDataMigration.ts`, which the finding did not flag.
- Routing the migration through `updateItemWithClient`, running domain hooks or heartbeats for migrated rows, or emitting invalidations for them.
- Any other change to `propertyTypeMigration.ts`, including `enqueuePropertyTypeMigration` and its `console.error` line.

## Acceptance criteria

- `migrateItemPropertyWithClient` with `kind: "set"` replaces only `key` in the item's `properties`, leaves the other keys intact and advances `updated_at`; with `kind: "remove"` it deletes only `key` and advances `updated_at`. Both work on a soft-deleted item.
- Either kind against a `(databaseId, itemId)` that matches no row throws, with the labels named in Task item 1.
- `propertyTypeMigration.ts` no longer contains the text `UPDATE items`.
- The existing `propertyTypeMigration.test.ts` cases pass unchanged, including "rolls the batch back when the converting UPDATE affects zero rows" and "rolls the batch back when the dropping UPDATE affects zero rows".
