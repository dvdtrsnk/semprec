## Context

Model tier rationale: Two module tools declared against authorization, grant and approval mechanisms that blocking issues implement, plus a small extraction of an existing handler, verified by existing session and manifest fixtures; the enforcement itself is not built here.

Sleep can be changed by the user in the app, and the user can also ask Semp to change an alarm ("move tomorrow's alarm to 7:00"). Plans and settings are ordinary items, so Semp changes them with the generic `item.patch`; the validation and the one-plan-per-day rule apply through the write hooks (#1784, #1799). A single night is different: it needs a find-or-create and the answer is a resolved night, which is the PUT route (#1835); reading nights needs the plan resolver behind `GET /api/sleep/nights` (#1809). Module agent tools are declared in the manifest (`ModuleAgentToolDescriptor` in `backend/packages/module-registry/src/manifest.ts`: `name`, `handlerExport`, optional `capability`) but reach an agent session only through #1523, which also lets module capabilities into `grantedCapabilities`; tools that need human approval are deferred by #1791; the rule for approval and project grants of module tools is the ADR recorded by #1385. The sleep databases are sensitive (#1808) and a project reads or writes them only with a database grant (#1810); the writer kind of an agent write is threaded by #1415.

This issue adds the two sleep tools to the sleep module. A write by an agent enqueues the resync push through the existing hooks (#1838).

Decisions:
- Capabilities `sleep.read` and `sleep.write` are declared in the manifest; `sleepNightsGet` needs `sleep.read`, `sleepNightSet` needs `sleep.write`.
- `sleepNightSet` never deletes: a null value means "follow the plan", like the PUT route.
- Approval: `sleepNightSet` is a non-destructive write that only creates or updates items, so it runs without human approval and declares no `requiresApproval`.
- Access: both tools are available only when the user has granted the run's project access to the sleep databases (#1810). Without that grant they never read or write sleep data: a call answers 403 `forbidden` and writes nothing.
- Read access is checked with the project's database grants inside the same transaction as the read; a write is checked by the data layer because it carries the agent writer kind and the project item id.

## Task

Load `ai-gateway`, `state-writes`, `error-handling` and `testing`.

1. In `backend/packages/data/src/sleep/sleepRouteHandlers.ts` extract the transaction body of `sleepNightPut` into an exported `upsertSleepNight(client, { night, fields }, writeOptions)` that takes the writer options of #1415; the route calls it with the human writer, behavior unchanged.
2. Add `backend/packages/data/src/sleep/sleepAgentTools.ts` with the two handlers and their argument schemas (strict, canonical camelCase keys, the dates and times validated as in #1784):
   - `sleepNightsGet { from, to }` returns what `loadSleepNights` (#1809) returns for the same range, after checking the project's read grant on the sleep databases in the same transaction.
   - `sleepNightSet { night, bedTime?, wakeTime?, alarm? }` calls `upsertSleepNight` with writer kind `agent` and the agent project item id, and returns the resolved night.
3. In `sleepModuleManifest.ts` declare `capabilities: ["sleep.read", "sleep.write"]` and the two `agentTools` entries (with the capability of each and the handler and schema exports the descriptor of #1523 requires; the manifest module re-exports them).
4. Tests: an agent session with the project's grants lists both tools and `sleepNightSet` with `{ night: "2026-10-16", wakeTime: "07:00", alarm: true }` yields the night 00:00 to 07:00 with an alarm, leaves the weekend plan unchanged and enqueues the job `sleep-resync:<tenantId>` in the same transaction; without a grant to the sleep databases both tools answer 403 `forbidden`; without the capability the tools are absent; invalid values give a 400 error result; other tenants are unaffected.

## Scope

### In scope

- The `sleepNightsGet` and `sleepNightSet` tools, their manifest declaration and capabilities, and the shared night-upsert function.

### Out of scope

- Composing module tools into sessions and granting module capabilities: #1523; deferring tools that need approval: #1791; the approval and grant rule itself: #1385.
- Per-database grants and sensitive marking: #1810 and #1808.
- Changing plans and settings: the generic `item.patch` is used.
- Exposing the sleep tools over `POST /mcp`: not planned yet; it waits for a product decision.
- Agent guidance text of the Sleep system project: decided not to be done.
- Referencing a night in a chat message: #1853.

## Acceptance criteria

- When the agent calls `sleepNightSet` with `{ night: "2026-10-16", wakeTime: "07:00", alarm: true }` and the project has the grants, then the night is 00:00 to 07:00 with an alarm, written at once without an approval request, the weekend plan is unchanged and a `sleep-resync:<tenantId>` job is enqueued in the same transaction.
- When the run has no grant to the sleep databases, then both tools answer 403 `forbidden` and nothing is read or written; with the grant they succeed.
- When the project lacks the `sleep.read` or `sleep.write` capability, then the corresponding tool is absent.
- When `night` is `2026-13-01` or a time is `7:5`, then the tool returns a validation error and writes nothing.
- When `sleepNightsGet` is called for a range, then it returns the same nights as `GET /api/sleep/nights`.
