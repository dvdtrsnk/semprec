## Context

This is issue 13 of 22 in the sequential "Semprec" implementation queue. Issues #30–#32 delivered the whole `packages/agent-runtime`: run lifecycle and budget cap, MCP integration, and the approval queue for risky calls. This task is the **last** in the pi-agent-core series and closes it with two things:

1. Heartbeats (already defined as a data entity in `project_heartbeats`) get a manual/agent entry point — an agent must be able to see them and trigger them on demand as an ordinary tool (`AgentTool`), not as a special UI-only mechanism sitting outside the normal tool layer.
2. The whole pi-agent-core integration effort is closed out with two final architectural decisions: how the `pi-*` package is versioned and tested against future upgrades, and how the division of responsibility across all of `packages/agent-runtime` reads under the SOLID principles.

The deterministic trigger mechanisms already in place — time-based triggers and the event-based `onItemEvent` rule over `project_heartbeats` — stay exactly as they are, the only mechanisms that fire on their own; the tools introduced here only add a manual path alongside them, never a replacement.

The following issue (#34, "Auth/authz — who gets in") builds on this one but is **not part of it** — user/client authentication and authorization are handled separately.

## Task

### 1. Three heartbeat tools as `AgentTool`

Introduce three new entries in the core module's manifest (the same place `agentTool.delegate` already lives):

- **`heartbeat.list`** — returns the project's current heartbeat configuration straight from `project_heartbeats`: full `rule` objects, the assignment/purpose text, active state, and `last_fired_at`. It covers heartbeats executed by a deterministic `heartbeatAction` with no agent run as well; detailed history is what `heartbeat.history` below is for. No separate `heartbeat.inspect` is introduced — `rule` is a small object and `list` already returns it in full; a fourth tool would only add a round trip and another entry in the tool array, no new information.
- **`heartbeat.trigger({ heartbeatId })`** — fires a run right away, out of turn, but only for heartbeats with a **time-based rule**. For heartbeats with an **event-based rule** (`{ kind: 'onItemEvent', … }`) it fires no run at all and returns a deterministic error `heartbeat_event_triggered` (HTTP 409), added as an additive new code to the error contract — the same category as `owner_violation` ("this will never work, don't try it differently"): an event-driven run only makes sense against a concrete `itemId` coming from a real event, no "advance-able" scheduled run exists, and a `heartbeatFire` job without an `itemId` would have no defined work to do. This is not a loss of capability — the deterministic path to trigger an event-based heartbeat already exists and the agent has the right to use it anyway: writing to the source item through the choke-point event fires it on its own (e.g. editing an unconfirmed Inbox item is itself a new tick).
- **`heartbeat.history({ heartbeatId, limit })`** — returns the last N (default 10) runs from `agent_runs`: status, timestamps, `result` — never full transcripts (those live in `agent_run_events`) — the same bounded-result discipline delegation already holds for the supervisor's context.

All three tools operate **exclusively over the project of their own run** — the target project is **not a parameter**: it is taken solely from `project_item_id` of the running `agent_run`. An agent therefore cannot, by construction, list or trigger a heartbeat belonging to another project — no confused-deputy case to guard against. Reaching another project's heartbeat is only possible through the existing delegation relay ("go run heartbeat X and give me the result back") — the same relay pattern this section already uses for cross-project communication, no supervisor-only exception on top.

Registration goes through the same path as every other tool — the ModuleRegistry allowlist — **without** `requiresCapability` and **without** `requiresApproval` (see the rejected alternative below for why).

### 2. Trigger mechanics

- `heartbeat.trigger` enqueues the **same typed job** the heartbeat scheduler in `semprec-agents` already uses for scheduled runs: `enqueueJob(TASK_NAMES.heartbeatFire, { heartbeatId, triggeredByRunId })`.
- The origin is carried by **the payload, not a guess by the handler**: the scheduler omits `triggeredByRunId`, the tool sends the id of its own run — and the job handler writes it into `parent_run_id` when it creates the `agent_runs` row. Without this field the handler would have no way to know who invoked the run; graphile-worker has no other channel back to the caller.
- **Dedup is deliberately per origin, not shared**: the scheduler enqueues with `jobKey: \`heartbeat-fire:${heartbeatId}\``, the manual trigger with `jobKey: \`heartbeat-fire:manual:${heartbeatId}\``. A single shared key was considered (a manual trigger and a pending scheduled run would collapse into one) and rejected because of the replace semantics of `jobKey`: a new job with the same key *replaces* the pending one, payload included, so attribution of the collapsed run would follow whichever enqueue happened last — the agent's trigger could vanish from the history without a trace (the scheduler enqueued after it and overwrote `triggeredByRunId`), even though the tool reported success, or conversely the scheduled occurrence could get pinned on the agent. Exactly the kind of nondeterministic audit trail `heartbeat_id`/`parent_run_id` exist to prevent. The price of separate keys: a manual and a scheduled run occasionally meet back-to-back as two runs — cheap, because a heartbeat run is convergent (it processes pending state; a second run right after the first finds the work already done and exits), and the history shows two honest records instead of one with a false attribution. An agent calling trigger in a loop still collapses onto its own manual key into a single pending job. Two supporting rules, without which the dedup would have gaps: the scheduler enqueues **only at the moment of maturity** (`run_at` = now), never ahead of time with a future `run_at` — forward scheduling is held by the scheduler itself over `project_heartbeats`, not by the queue, so a replace can never push pending work into the future; and the open point about the exact behavior of `jobKey` against an already-*running* (not just pending) job — needs verifying against the specific library version — applies here unchanged.
- For a heartbeat with an **event-based rule** (`{ kind: 'onItemEvent', … }`, including the `newEmail` generalization) `heartbeat.trigger` fires no run and returns the deterministic `heartbeat_event_triggered` error described above.
- History for event-based heartbeats is not empty either: the event path's `heartbeat-fire` job carries the `heartbeatId` of the event rule that fired the tick, and the handler writes it into `agent_runs.heartbeat_id` for every agent run spawned from that tick — so `heartbeat.history` against, say, "Process Inbox" (today's only named Semp heartbeat) returns real daily runs, not a permanently empty list.
- The run is written to `agent_runs` with a new nullable column **`heartbeat_id`** — without it, history for a specific heartbeat couldn't be queried at all, the table so far did not record *which* heartbeat a run executed — and with the existing `triggered_by = 'heartbeat'`. The `triggered_by` enum therefore needs **no change**: it says the run executes a heartbeat definition, and the "scheduler vs. manual trigger" distinction is carried by `parent_run_id` — NULL for both scheduled and event-based runs, the id of the calling run for a manual one, written by the handler from `payload.triggeredByRunId` (the same field delegation already uses to make the run tree visible — and thanks to the payload plus separate `jobKey`s, the combination is genuinely unambiguous, not just asserted). If a "Run now" button is added to the UI later, it would write `triggered_by = 'user'` + `heartbeat_id`, and history would pick it up too, because it queries by `heartbeat_id`, not by `triggered_by` — the mechanism is ready, the button is not being built now.

### 3. Explicitly out of scope for history

Deterministic `heartbeatActions` with no agent run (e.g. `processLibraryMetadata`) may be fired by `heartbeat.trigger` — the `heartbeatFire` job handler just calls the registered handler instead of starting an agent session for them — but they create **no `agent_runs` row**. Their state is tracked separately (status/attempts/last_attempt_at per item) and `heartbeat.history` does not cover them. If a full run log for them turns out to be needed, that is a small additive log table later — not a reason to bend `agent_runs` now into recording runs that are not agent runs at all.

### 4. `pi-agent-core` as a pinned library dependency + contract tests

- `pi-ai`/`pi-agent-core`/`pi-coding-agent` live in `package.json` as an **exactly pinned** dependency (no `^`/`~` range, locked in the lockfile too) — an upgrade is always an explicit, reviewed PR bumping one number, never a silent side effect of a routine `pnpm install`.
- Add a small suite of **contract tests** to the integration test suite (module-contract issue) that do not test Semprec's own logic but the actual pi behavior this whole series relies on, e.g.: `config.toolExecution` defaults to `'parallel'`; the `Agent`/`AgentSession` constructor does not spawn a subprocess; `estimateContextTokens`/`shouldCompact` can be called on a bare message array with no running session; `compact()` still requires a `CompactionPreparation` (not a bare array).
- This test suite runs in CI against the actually installed `pi-*` version on every PR — if an upgrade breaks one of these assumptions, the build fails with a clear message ("pi changed behavior we depend on") instead of failing silently in production later.

Every decision in this series relies exclusively on the **public, documented export** of the `pi-ai`/`pi-agent-core`/`pi-coding-agent` packages (`createAgentSession()`, `resourceLoader.systemPromptOverride`, `config.toolExecution`, `compact()`/`shouldCompact()`/`estimateContextTokens()`/`CompactionSettings`) — nowhere does Semprec reach into pi's internal, unexported modules, and nowhere does it depend on the not-yet-released `AgentHarness` path (that was the explicit reason `systemPromptOverride` was chosen over the richer but undelivered `AgentHarness.systemPrompt` callback). Even patterns borrowed from pi's own `examples/` (subprocess delegation, `mapWithConcurrencyLimit`) are **rewritten as Semprec's own implementation**, never imported straight from `examples/` — those are not part of the package's public contract and can move or disappear between versions without warning. This is the answer to "can pi be upgraded later without breaking Semprec" — not because pi guarantees it, but because Semprec never touches its internals and every dependency on its public behavior is named and tested.

### 5. SOLID architecture — summary for all of `packages/agent-runtime`

Document (in the package's code/README, not only in this specification) the division of responsibility as an explicit SOLID mapping — not decoration, but naming what the decisions above already force in practice:

- **SRP** — `pi-agent-core` = only the single-run loop + context compaction; `semprec-agents` = orchestration/delegation/lifecycle bookkeeping; `semprec-ai-gateway` = egress to providers + budget; `ModuleRegistry` = tool allowlist; `agent_runs` = audit, with a `unit` discriminator (invocation vs. session, see issue #30) so that audit and aggregation over it stay one unit of work, not two silently mixed ones. Pi's narrow scope actually forces this — it has no ambition of its own to do more, so Semprec cannot accidentally stack more responsibilities into one layer even if it wanted to.
- **OCP** — the `systemPromptOverride` callback is an extension point without touching pi internals — a new type of project agent arrives via a new callback and a set of `AgentTool`s, not a patch to the core.
- **LSP** — every session — Semp's own or any project agent's — is created through the same `createAgentSession()` + `ResourceLoader` path, interchangeably, without special-casing "this one is the supervisor". The same principle already established for `agent_runs.project_item_id` on the supervisor's run — no special value, no extra mechanism.
- **ISP** — `ModuleRegistry`/`AgentTool` registration means an agent sees only the tools it has a grant for in its permission manifest — the principle of "absence of capability, not runtime blocking" is literally interface segregation tailored to the caller, not one fat interface with locked parts; the MCP explicit sync and the approval queue are the same principle applied one level further — to the very first appearance of a capability, and to an individual risky call instance.
- **DIP** — `semprec-agents` (high-level policy) depends on an abstraction — the system-prompt callback contract and the tool list — not on pi internals; provider calls go through `semprec-ai-gateway`'s `complete()`/`transcribe()`/`diarize()`/`embed()` contract, not directly to the `pi-ai` driver, so swapping a provider — or even swapping pi for a different harness later — touches one layer, not the whole system.

## Scope

### In scope

- `heartbeat.list`, `heartbeat.trigger`, `heartbeat.history` as `AgentTool` entries in the core module, registered through the ModuleRegistry allowlist.
- Scoping to the run's own project exclusively via `project_item_id` of the running `agent_run` (no project parameter on any of the three tools).
- `heartbeatFire` job mechanics: `triggeredByRunId` in the payload, propagation to `parent_run_id`, separate `jobKey`s for scheduler vs. manual trigger.
- New nullable column `agent_runs.heartbeat_id` + migration.
- Deterministic `heartbeat_event_triggered` (409) error for triggering an event-based heartbeat, added to the error contract.
- Pinning `pi-ai`/`pi-agent-core`/`pi-coding-agent` to an exact version in `package.json` and the lockfile.
- Contract test suite against the documented behavior of the `pi-*` packages, wired into CI.
- Documenting the SOLID mapping for `packages/agent-runtime` as a whole.

### Out of scope

- Approval queue for the manual trigger — considered and rejected: the trigger itself writes nothing; it only moves up in time a run the scheduler would fire anyway, with the same assignment and the same boundaries; every real write inside that run goes through the choke-point and the approval queue from issue #32 exactly the same way, whether the run was fired by cron at midnight or by an agent right now. The one real extra risk — an agent calling trigger in a loop — is handled by mechanisms that already exist: dedup on the manual `jobKey` and the daily budget cap.
- `heartbeat.inspect` as a fourth tool — rejected, `rule` is a small object and `heartbeat.list` already returns it in full.
- A run log for deterministic `heartbeatActions` with no agent run (`agent_runs` rows for them) — if this turns out to be needed, it is solved later with a small additive log table, not by extending `agent_runs`.
- A "Run now" UI button (`triggered_by = 'user'`) — the mechanism is ready (it queries by `heartbeat_id`, not `triggered_by`), but the button is not built in this task.
- The exact behavior of `jobKey` against an already-*running* (not just pending) job — remains an open point to verify against the specific graphile-worker version, not tested as part of this task.
- Auth/authz (who may run agents/heartbeats at all) — issue #34.

## Dependencies

- Requires `project_heartbeats` and its `rule`/`last_fired_at` shape (existing from the heartbeat specification).
- Requires the deterministic scheduler and the `onItemEvent` rule over `project_heartbeats`, including the `heartbeatFire` job in the task catalog (`TASK_NAMES`) — must exist before this task, not introduced here.
- Requires the `ModuleRegistry` allowlist mechanism and the `agentTool.delegate` pattern (module-contract issue / issue #30) — heartbeat tools register through the same path.
- Requires the approval queue and the budget cap from issue #32 — referenced by the rejected alternative (approving the trigger) and by the argument for the manual trigger's safety.
- Requires the existing `agent_runs` table and the `triggered_by` enum (`'heartbeat'` value) — extended with a `heartbeat_id` column, not introduced from scratch.
- Requires the error contract (existing `owner_violation` pattern) to add `heartbeat_event_triggered`.
- Blocks issue #34 (Auth/authz) only in the sequential sense — no functional dependency.
