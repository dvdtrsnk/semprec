## Behavior specification

Finance: module, transactions, summary, budget and expense from invoice.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: finance-1

#### Adopted from open questions
- Data source (manual / invoices from Inbox / bank import) -> manual writes and the Inbox invoice step (#1748) only; bank import is not planned and waits for a product decision -> credentials and a sync worker are a separate program. The "hide the Finance row until decided" note is a client matter.
- Bank accounts and multiple currencies -> not planned; currency is a select with only CZK.
- Budget model -> `monthlyBudget` on each category, total is the sum (#1511, #1585) -> no extra database, matches the design.
- Transaction `name` -> a free description; lists show the company when present (#1511).
- Links to locked Companies, Projects and Files -> variant (b): unlock temporarily and add inverses (#1553) -> single value is structural and the related-items mechanism needs no special reader (the touches hint of the program also pointed to the cutover variant).
- Agent write gate -> variant (a) approval (not Inbox proposals); default grant: reading open, writing needs a grant and then approval; only item create and patch on the two Finance databases are covered (#1815).
- Budget state thresholds -> inBudget up to 89 %, nearLimit 90-100 %, over above 100 % (#1585); texts left to the client.
- "Spent" basis -> by `date`, unpaid expenses included (#1585).
- Document with several projects or companies -> take over nothing (#1651, relies on the single-valued rule of the propagation engine).
- Category on an expense from the Inbox -> optional `categoryId` accepted in the step; absent means no category (#1748).
- `source` of manual rows -> left empty and read as manual; only `inbox` is ever written (#1511).

#### Open questions for the product owner
- Should the Inbox card get a Category field (the design's expense detail shows a category but the card has none)?
- Should a manually created transaction get `source: manual` written explicitly (needs a Finance-owned default)?
- Should relation writes on finance items by the assistant also need approval?
- Do design screens need to be added for budget settings, category management, marking paid, all transactions and Finance in the Related columns?
- Should `dueDate` of unpaid expenses count toward the month instead of `date`?

#### Delivered behavior
Every tenant gets a Finance project with Transactions and Finance categories (Bydlení, Jídlo a nákupy, Doprava), labelled in Czech and English. A transaction has an amount (always positive, with type expense or income), CZK currency, date, due date, paid status and links to a company, a project, a document and a category; the server rejects zero or negative amounts. The Finance overview reads one summary: spent this month against the total budget, percent used, state (in budget, near limit, over), days left, and each category's used share, computed in the user's time zone. Expenses created from an invoice in the Inbox take the company and project of the invoice until the user changes them, and the assistant can read the summary but any assistant write to Finance waits for the user's approval.
