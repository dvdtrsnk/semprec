**Blocked by:** #674, #681, #707

## Context

Review follow-ups harvested in #728, both on failure paths of mail sync:

- PR #298 — `backend/packages/data/src/mail/ingest.ts:199`: after a `provider_message_id` conflict, the lookup `getMailMessageMetaByProviderMessageId(client, input.providerMessageId as string)` casts a `string | null | undefined` field (`ingest.ts:56`). The invariant that the partial unique index only fires on non-null ids holds today, but nothing in the code enforces it.
- PR #302 — `backend/packages/data/src/mail/mailLiveSyncRoot.ts:141`: in account discovery, if `client.query("ROLLBACK TO SAVEPOINT discover_account")` throws, control leaves the `catch` before `options.onLifecycleError?.(item.id, "discover", err)` (line 144) runs, so the original seeding error is discarded and only the rollback error surfaces.

Issues #674 and #681 edit `ingest.ts`, and #707 edits `mailLiveSyncRoot.ts` and its test; this issue starts from those files as they leave.

## Task

1. `ingest.ts`: replace the `as string` cast with an explicit guard — when `input.providerMessageId` is `null` or `undefined` on the conflict path, rethrow the original error `err` — and pass the narrowed value to `getMailMessageMetaByProviderMessageId`.
2. `mailLiveSyncRoot.ts`: in the per-account `catch` of discovery, call `options.onLifecycleError?.(item.id, "discover", err)` before `ROLLBACK TO SAVEPOINT discover_account`, so the original error is reported even when the rollback throws.

## Touches

- backend/packages/data/src/mail/ingest.ts (the provider-id conflict `catch` only)
- backend/packages/data/src/mail/mailLiveSyncRoot.ts (the discovery per-account `catch` only)
- backend/packages/data/src/__tests__/mailLiveSyncRoot.test.ts

## Scope

### In scope

- The two changes above and a test for the second.

### Out of scope

- What discovery does with the rest of the page after a failed rollback.
- Any other cast or error path in `ingest.ts` or `mailLiveSyncRoot.ts`.

## Acceptance criteria

- `ingest.ts` contains no `as string` on `providerMessageId`, the backend typecheck passes, and the existing provider-id conflict convergence tests in `mailSync.test.ts` still pass.
- A test in `mailLiveSyncRoot.test.ts` gives `createMailLiveSyncRoot` a pool whose client fails one account's sync-state seed statement and then fails `ROLLBACK TO SAVEPOINT discover_account`, and asserts `onLifecycleError` was called with that account's item id, `"discover"` and the seed statement's error.
