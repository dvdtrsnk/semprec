## Context

Registering a push subscription re-binds an existing active registration to the caller, whoever owns it. `upsertWebPushSubscription` in `backend/packages/data/src/push/pushSubscriptionsStore.ts` (lines 64-78) runs `INSERT ... ON CONFLICT (endpoint) WHERE revoked_at IS NULL AND endpoint IS NOT NULL DO UPDATE SET user_id = EXCLUDED.user_id, session_id = EXCLUDED.session_id, p256dh = ..., auth_secret = ...` (lines 71-73); `upsertApnsSubscription` (lines 89-103) does the same on `device_token` (lines 96-98). Both docstrings describe this as the intended "refreshed in place (new owning user/session, refreshed keys)" behaviour. The consequence: any authenticated user who knows another user's endpoint or device token takes the registration over — the victim stops receiving notifications and the attacker's session becomes the one whose logout revokes it.

Sibling B10 of this batch edits `pushSubscriptionActions.ts` (endpoint validation) — a different file.

## Task

- In both upserts, restrict the conflict update to the same owner by appending `WHERE push_subscriptions.user_id = EXCLUDED.user_id` to the `DO UPDATE` clause. When the active row belongs to a different user the statement now affects no row and `RETURNING` yields nothing; in that case throw `new ConflictError("'endpoint' is already registered to another account", { field: "endpoint" })` (web push) or `new ConflictError("'deviceToken' is already registered to another account", { field: "deviceToken" })` (APNs) from the store, instead of letting `requireSingleRow` raise a generic error. `ConflictError` (`../errors.js`) is status 409, code `version_conflict` — the adapter's one 409 code in its closed enum; adding a dedicated code is out of scope, and the `details.field` names the colliding field. Same-owner conflicts keep today's in-place refresh (`session_id`, keys, `updated_at`), and a revoked row still leaves the partial index empty, so re-registration after revocation stays a plain insert.
- Rewrite both docstrings: a registration is owned by the user who created it; a token or endpoint legitimately moving to another account (a shared device, a new login on the same browser profile) requires the old account to revoke it first (`POST /api/push-subscriptions/:id/revoke`, logout, or session revocation), after which the new account's registration is a fresh insert.
- `registerPushSubscription` and the route handler need no change: the `ConflictError` propagates through `withTransaction` and the custom-route mount answers it as 409 `version_conflict`.
- Tests in `backend/packages/data/src/__tests__/pushSubscriptions.test.ts`, inside `describe("registration and reactivation")` (integration tier):
  - user A registers web-push endpoint `https://push.example/shared` with `p256dh: "key-a"`; user B registering the same endpoint rejects with `ConflictError`; A's row is unchanged (`userId` A, `p256dh` `"key-a"`, `sessionId` A's session) and `listPushSubscriptionsForUser(pool, B.id)` is empty.
  - after A revokes it, B registers the same endpoint successfully and gets a new active row (`revokedAt` null, `userId` B), while A's row stays revoked.
  - the same two cases for an APNs `deviceToken`.
  - the existing "re-registering the same active endpoint updates the existing row" case (same user) must keep passing unchanged.

## Scope

### In scope

- Owner-scoped conflict updates and the 409 for a cross-user collision.

### Out of scope

- Validating the endpoint URL itself — sibling issue B10 of this batch (`pushSubscriptionActions.ts`).
- A new error code in `services/semprec-api/src/adapter/errorContract.ts`'s closed enum.
- Any migration: the partial unique indexes from migration 0031 already express the invariant; only the upsert's update predicate changes.
- Automatic transfer of a registration between accounts.

## Acceptance criteria

- When user B registers an endpoint (or device token) that user A holds an active registration for, the call fails with a 409 whose `details.field` names `endpoint` / `deviceToken`, and A's row is byte-for-byte unchanged.
- When user A revokes that registration and B registers the same endpoint, B gets a new active row and A's row stays revoked.
- When the same user re-registers an active endpoint, the row is refreshed in place with the same `id`, as today.
- Every existing case in `pushSubscriptions.test.ts` and `push/__tests__/pushRouteHandlers.test.ts` passes unchanged.
