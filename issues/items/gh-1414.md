## Context

Model tier rationale: One mechanism (widening the converter signature and loading the tenant's context once per run) in a single runner with existing fixtures, but it sits on the module data migration path that rewrites persisted rows for every tenant.

Module data migrations are declared in a module manifest as `dataMigrations` (`backend/packages/data/src/seed/systemDatabasesModuleManifest.ts`, today only Tasks 1.0.0 to 1.1.0 through `converterExport: "backfillTaskTimeProperties"`). The runner `runModuleDataMigration` in `backend/packages/data/src/migrationJob/moduleDataMigration.ts` runs one transition for one tenant: batched, id-ordered, in two passes with `SKIP LOCKED`, resumable, and guarded by a per-tenant advisory lock (`docs/adr/2026-09-28-two-pass-skip-locked-module-data-migration.md`). The converter type is `ModuleDataMigrationConverter = (properties) => properties`, a pure synchronous function with no access to the tenant's time zone, the item id or a logger. The runner writes with a direct `UPDATE items`, outside the choke point, so no hooks, no inline derivation and no invalidation run.

Converting stored Events dates into wall-clock dates and times (#1797) needs the tenant's time zone, the item id for the log, and a logger that must not carry property values. This issue gives converters that context and nothing else. The Tasks converter must keep working unchanged. The idempotence and two-pass contract stay; this issue extends the existing ADR's contract rather than replacing it.

Decision: the context is `{ timezone, itemId, log }`. The runner reads the time zone with `getSystemTimezone` (`backend/packages/data/src/systemSettings.ts`) once per tenant run, and `log` is a logger that accepts only the item id and a short reason code.

Shared-file ordering: this issue also waits for #1411 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes` and `testing`.

1. Change `ModuleDataMigrationConverter` to `(properties, context) => properties` with `context: { timezone: string; itemId: string; log: (reason: string) => void }`. A converter that declares only the first parameter must continue to compile and behave identically, so `backfillTaskTimeProperties` and every existing test converter are unchanged.
2. In `runModuleDataMigration`, load the tenant's time zone once after the advisory lock is taken and pass a context per item. `log` writes one structured entry carrying the tenant-scope logger fields, the item id and the reason, never any property value.
3. Keep the converter type in `backend/packages/module-registry/src/manifest.ts` and `registry.ts` (`ModuleDataMigrationDefinition["converter"]`) in step with the new signature.
4. Update the converter contract text in `docs/adr/2026-09-28-two-pass-skip-locked-module-data-migration.md` with a short section describing the context argument (an addition, not a new decision).
5. Tests: a converter receives the tenant's zone (two tenants with different zones in one run each see their own), the item id of the row, and a `log` call produces an entry without property values; the existing Tasks migration test passes untouched; a second run still writes nothing.

## Scope

### In scope

- The converter context (time zone, item id, logger) and the runner change that supplies it.

### Out of scope

- Any concrete converter that uses the context: #1797.
- Calling the choke point, hooks or invalidation from the runner; the runner keeps writing directly.
- Any change to the two-pass, locking or resumability behavior.

## Acceptance criteria

- When a converter reads `context.timezone`, then it equals the tenant's configured time zone, and tenants in the same run with different zones each get their own.
- When a converter calls `context.log`, then the log entry contains the item id and the reason and no property values.
- When the existing Tasks 1.0.0 to 1.1.0 migration runs, then its results are identical to before and its converter source is unchanged.
- When a migration runs twice, then the second run changes no row and leaves `updated_at` untouched.
