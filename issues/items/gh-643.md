## Context

`mintMcpRunCredential` (`backend/packages/data/src/mcp/mcpRunCredentialAction.ts:63-81`) creates a root `agent_runs` row with `triggered_by='mcp'`, `status='running'` (line 69-74) and one `agent_run_mcp_credentials` row with `expires_at = now() + MCP_RUN_CREDENTIAL_TTL_SECONDS` (1 h, line 17 and 77-78; table from migration `0043`). `getActiveMcpRunCredentialByTokenHash` (`mcpRunCredentialsStore.ts:69-93`) only honours a credential while `c.expires_at > now() AND r.status = 'running'`, so the credential stops authenticating on its own — but nothing ever finishes the run. Every credential ever minted leaves an `agent_runs` row `running` forever: it shows as an active run in `GET /api/agent-runs/:id`, counts as "running" for `listRunningAgentRuns`, and would be mass-closed as `error` (one `agent_run_error` notification each) by the startup repair, which is why #642 excludes `triggered_by='mcp'` rows from repair and leaves their lifecycle to this issue. There is no credential revocation path in the codebase (the only "revoke" is `mcpGrantsAdminStore.ts`'s project grant revocation, unrelated), so expiry is the only terminal event.

The api runtime is the queue's only scheduler (`CORE_CRONTAB`, `backend/packages/data/src/worker.ts:78-86`); every core task name lives in `CORE_TASK_NAMES` with an entry in `CORE_TASK_AFFINITY` (`backend/packages/queue/src/index.ts:28-104`), and `assertTaskListMatchesAffinity` at `backend/services/semprec-api/src/queueRuntime.ts:63-64` requires the api task list to match `resolveTaskAffinitySets(...).api` exactly.

## Task

1. **Task name** — in `backend/packages/queue/src/index.ts`, add `MCP_RUN_CREDENTIAL_EXPIRY_SWEEP: "mcpRunCredentialExpirySweep"` to `CORE_TASK_NAMES` and `[CORE_TASK_NAMES.MCP_RUN_CREDENTIAL_EXPIRY_SWEEP]: "api"` to `CORE_TASK_AFFINITY`. Extend `backend/packages/queue/src/__tests__/taskAffinity.unit.test.ts` with the new name.
2. **Handler** — new file `backend/packages/data/src/mcp/mcpRunCredentialExpiry.ts` exporting `handleMcpRunCredentialExpirySweepTask(pool: Pool): Promise<{ finishedRunIds: string[] }>`. In one `withTransaction`: select `c.agent_run_id, c.expires_at` from `agent_run_mcp_credentials c JOIN agent_runs r ON r.id = c.agent_run_id WHERE c.expires_at <= now() AND r.status = 'running' AND r.triggered_by = 'mcp' FOR UPDATE OF r SKIP LOCKED` (typed row, `docs/adr/2026-09-10-typed-rows-at-the-postgres-boundary.md`); for each row call `finishAgentRun(client, agentRunId, "done", "MCP run-credential expired at <expires_at ISO>")` (`backend/packages/data/src/agentRuns/agentRunsStore.ts:135-146`, which already asserts the affected row count) and then `insertAndNotifyAgentRunEvent(client, agentRunId, "run_status", { kind: "run_status", status: "done" })` (`agentRunEventsStore.ts:66`) so run watchers see the same terminal event `runAgentSession` emits. Status is `done`, not `error`: the credential reaching its TTL is the normal end of that run, so no `agent_run_error` notification is written. Do not add the new module to `backend/packages/data/src/index.ts` — `worker.ts` imports handlers by relative path, and the barrel is a conflict hotspot edit; keep it internal.
3. **Registration** — in `backend/packages/data/src/worker.ts`: add the crontab line `10 * * * * ${CORE_TASK_NAMES.MCP_RUN_CREDENTIAL_EXPIRY_SWEEP}` to `CORE_CRONTAB` (hourly, ten past — the TTL is one hour, so a lapsed credential's run closes within the next hour) and the handler `[CORE_TASK_NAMES.MCP_RUN_CREDENTIAL_EXPIRY_SWEEP]: async () => { await handleMcpRunCredentialExpirySweepTask(pool); }` in `createCoreTaskList`'s `handlers` map. Because `createApiCoreTaskList` derives from it, the api runtime picks it up with no change to `backend/services/semprec-api/src/queueRuntime.ts`.
4. **Tests**:
   - `backend/packages/data/src/__tests__/mcpRunCredentialExpiry.test.ts` (new, integration): mint a credential via `mintMcpRunCredential`, `UPDATE agent_run_mcp_credentials SET expires_at = now() - interval '1 minute'`, run the handler → the run is `status='done'`, `result` mentions the expiry, `finished_at` set, a `run_status` event with `status: "done"` exists, `resolveMcpRunCredential(pool, token)` returns `null`, and no `agent_run_error` notification exists. A second run of the handler returns `finishedRunIds: []` and changes nothing. An unexpired credential's run stays `running`. A `triggered_by='heartbeat'` run that happens to be `running` is untouched.
   - `backend/services/semprec-api/src/__tests__/queueRuntime.test.ts`: add the new identifier to `EXPECTED_CRONTAB_IDENTIFIERS` (lines 12-21), which is the composition assertion that the api runtime actually installs this cron.

## Scope

### In scope
- The hourly sweep task (name, affinity, crontab, handler, tests) that closes runs whose MCP credential has expired.

### Out of scope
- Excluding `triggered_by='mcp'` runs from startup repair (#642).
- A revocation endpoint or any change to `POST /api/agent-runs/mcp-credentials`, the credential TTL, or `getActiveMcpRunCredentialByTokenHash`.
- Deleting expired `agent_run_mcp_credentials` rows (they are the audit trail of which run a token authenticated).

## Acceptance criteria

- When an `agent_run_mcp_credentials` row's `expires_at` is in the past and its run is `running`, the next `mcpRunCredentialExpirySweep` run leaves that run `status='done'` with `finished_at` set and a result text naming the expiry, and appends a `run_status`/`done` event.
- When the sweep runs again, or while the credential is still valid, nothing changes; runs with `triggered_by <> 'mcp'` are never touched by it.
- When `createApiQueueRuntime` starts, `graphile_worker._private_known_crontabs` contains `mcpRunCredentialExpirySweep` alongside the existing identifiers, and `assertTaskListMatchesAffinity` passes for both runtimes.
- No `agent_run_error` notification is written by this sweep.
