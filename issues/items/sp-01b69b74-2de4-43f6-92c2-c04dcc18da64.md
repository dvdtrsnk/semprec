## Context

Model tier rationale: A bounded extension of the seed reconcile that changes existing select property configs in carried tenants; it must stay strictly additive.

The seed reconcile (sp-61e09e8c-f4bf-418e-bb1c-0e9df00c81bd) adds missing system property and relation definitions to already seeded tenants and reports, but never changes, an existing definition whose config differs. A v0.1.12-shaped tenant's `calendars.kind` select lists `own`, `system`, `subscription`; the current seed adds `account`. Item writes refuse an option a select property does not list, so calendar sync of an internet account fails on carried production data. This blocks the production cutover.

Decision: the reconcile also appends, to an existing system select (or multi-select) property, the options the current seed defines and the tenant lacks, keeping the tenant's existing options, their order and any option the seed no longer defines. Option metadata of an existing option (label, colour, order) is not changed. Every other config difference stays report-only.

## Task

Load `state-writes`, `db-migrations`, `canonical-keys` and `testing`.

1. In `seed/seedReconcile.ts`, when a system select or multi-select property exists in a tenant and the fresh seed's option list contains values the tenant's config lacks, append those options (with the seed's option definition) to the tenant's config in the reconcile transaction, through the same schema write the seed uses. Count them in the run's log (fixed tags, keys only).
2. A config difference that is not purely missing options stays reported as today and is not changed.
3. Update `docs/architecture/migrations-and-seeding.md` (the additive reconcile rule) and `docs/operations/production-cutover-to-develop.md` (remove the `calendars.kind` blocker once the dry run shows it fixed).

## Scope

### In scope

- Appending missing select options of system properties during the seed reconcile.

### Out of scope

- Removing, renaming or reordering options; changing any other config.
- Running anything against production (owner).

## Acceptance criteria

- A tenant whose `calendars.kind` lists `own`, `system`, `subscription` lists `own`, `system`, `subscription`, `account` after the seed CLI runs, and a Calendars item with kind `account` can then be created by the calendar sync writer.
- A second run changes nothing.
- An option present in the tenant but absent from the seed is kept.
- A select property whose difference is not only missing options is reported and left unchanged.
- The cutover dry run against a v0.1.12-shaped dump reports no config difference for `calendars.kind` and still exits 0.
