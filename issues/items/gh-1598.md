## Context

Model tier rationale: One known mechanism (a per-module pre-write transform) reusing the existing Tasks time derivation pattern and a shared helper, with deterministic inputs and outputs, but it touches the write path of every Events create and update.

#1416 adds `endDate`, `timeFrom`, `timeTo` and the system-owned `time` to Events. Today nothing derives or normalizes them. Tasks already do: `deriveTaskTime` (`backend/packages/data/src/tasks/deriveTaskTime.ts`) is called inline from `backend/packages/data/src/chokePoint/itemWrites.ts` before the row is written (decision record `docs/adr/2026-09-19-derived-system-properties-computed-inline-at-choke-point.md`). Item hooks in `chokePoint/hooks.ts` run only after the write and return void, so they can reject but cannot change a value; this is why the transform must run in the pre-write step that #1422 adds to the choke point, which receives the stored state and the patch. #1536 introduces `normalizeWallClockTime(value, { allow2400 })` in `backend/packages/data/src/timezone.ts` for the Tasks time fields; this issue reuses it (if the helper's ownership or options differ in the merged version, align this issue to the merged helper rather than duplicating it).

Events created from a transcript today carry `date` as a UTC instant (`transcription/transcriptEventMatch.ts`, confirmed through `createItemWithClient` in `inbox/proposalActions.ts`), and older clients may still send such a value. Those must keep working.

Decisions:
- A timed Event with a start and no end gets an end one hour later, clipped to `"24:00"`. Reason: the assistant and imports create such Events, and rejecting them would break those callers.
- The transform works on the wall-clock in the tenant time zone (`getSystemTimezone` in `backend/packages/data/src/systemSettings.ts`, default Europe/Prague).

This issue changes values only. Rejecting invalid combinations is #1663.

Shared-file ordering: this issue also waits for #1593, #1597 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. Add `backend/packages/data/src/calendar/eventTime.ts` with a pure function that takes the stored properties (or none on create), the patch and the tenant time zone, and returns the properties to write. Register it as the Events pre-write transform through the mechanism #1422 provides, so it runs for REST, agent and MCP writes alike.
2. In it:
   - Normalize `timeFrom` and `timeTo` with `normalizeWallClockTime(value, { allow2400: true })` (for example `"9:00"` becomes `"09:00"`). A value that cannot be read is left unchanged for #1663 to reject.
   - When the Event is single-day (`endDate` null or equal to `date`) and `timeFrom` is set but `timeTo` is not, set `timeTo` to `timeFrom` plus one hour, clipped to `"24:00"`.
   - Derive `time` as `"HH:MM–HH:MM"` (same format as `Tasks.time`) from `timeFrom` and `timeTo`; null when the Event is all-day.
   - Transition rule: when `date` carries an offset or `Z` (for example `"2026-10-16T08:00:00Z"`), convert it in the tenant time zone to `date` (`YYYY-MM-DD`) plus `timeFrom`, and add `timeTo` per the one-hour rule. A `date` with a time but no offset is read as wall-clock. A date-only `date` is untouched. An unreadable `date` is left unchanged.
3. The transform runs on the merged state (stored properties plus patch) so a patch that changes only `timeFrom` recomputes `time` and keeps `timeTo` as stored; the derived `time` is written in the same write, so a create or update has a single `updatedAt`.
4. Tests: `"9:00"` and `"11:30"` store `"09:00"` and `"11:30"` and `time` `"09:00–11:30"`; start only gives a one-hour end; `"23:30"` start gives `"24:00"`; all-day gives `time` null; an instant `date` converts for Europe/Prague and for a tenant set to America/New_York; REST, agent `item.patch` and MCP writes all reach the same transform.

## Scope

### In scope

- Time normalization, the default end, the derived `time` and the offset-to-wall-clock transition rule, applied before the write.

### Out of scope

- Rejecting invalid dates and times, and the rules between fields: #1663.
- Migrating already stored `date` values: #1797.
- The pre-write transform mechanism itself and the shared time helper: #1422 and #1536.
- Daylight-saving behavior beyond the conversion in the tenant zone: #1418 provides the calendar time module.

## Acceptance criteria

- When an Event is created with `date` `"2026-10-16"`, `timeFrom` `"9:00"` and `timeTo` `"11:30"`, then it stores `"09:00"`, `"11:30"` and `time` `"09:00–11:30"` with one `updatedAt`.
- When an Event is created with `timeFrom` `"14:00"` and no `timeTo`, then it stores `timeTo` `"15:00"`; with `timeFrom` `"23:30"` it stores `"24:00"`.
- When an Event has no `timeFrom`, then `time` is null.
- When `date` is `"2026-10-16T08:00:00Z"` in a Europe/Prague tenant, then the Event is stored as `date` `"2026-10-16"`, `timeFrom` `"10:00"`, `timeTo` `"11:00"`; in an America/New_York tenant `"2026-10-16T14:00:00Z"` becomes `timeFrom` `"10:00"`.
- When a patch changes only `timeFrom`, then `time` is recomputed from the stored `timeTo` in the same write.
- When an Event is written through REST, an agent `item.patch` or MCP, then the same values are stored.
