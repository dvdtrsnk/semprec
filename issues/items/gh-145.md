**Blocked by:** #235

## Context

Issue #235 gave databases a stable key and made system names nullable overrides. Option labels of `select`/`multi_select` properties follow the same override pattern one level down: the stored item value stays a bare English camelCase token that filters and SQL predicates rely on, and only the shape of `properties.config.options` changes so a label can be translated (#146/#147) or manually overridden.

## Task

Migrate every system `select`/`multi_select` option from a bare string to `{ key: string, label?: string }`. Preserve stable stored values such as `notDone`, `done`, and `wontDo`: a shipped option string `s` becomes `{ key: s }`; an option string that a user added or renamed at runtime, which is not part of the shipped catalog, becomes `{ key, label }` with `label` set to that string so its display text is preserved as an explicit override. Update validators, serializers, seeds, and typed-filter assumptions without rewriting item property values. Until #147 wires the catalog resolver, a serializer that needs a display string for an option without `label` emits the raw option `key`, matching the placeholder rule from #235.

## Scope

### In scope

- Schema/data migration of every system `select`/`multi_select` option, validators, serializers, typed filters, module seeds, and rollback-safe validation of malformed option configurations.

### Out of scope

- `databases.key` and nullable names — delivered by #235.
- Translation files and resolution, delivered by #146.
- Translation of user-created content.

## Acceptance criteria

- Every system option has a stable key and optional override, while existing item values and SQL predicates retain the same tokens.
- Migration tests cover upgrade and rollback-safe validation of malformed option configurations.
- Typed filters on `select`/`multi_select` properties return the same items before and after the migration.
