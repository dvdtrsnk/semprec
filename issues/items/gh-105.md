**Blocked by:** #104

## Context

An agent may propose processing but must never hold authority to write a destination directly.

## Task

Restrict Semprec's agent grant to creating/updating Processing proposals; omit target database/page write grants. Implement user-context actions `POST /api/proposals/:id/confirm`, `/reject`, and `/revise`. Confirm is the sole cross-destination path: for `database`, call the generic create-item choke point; for `pageContent`, call the existing block-append mechanism. Persist `resultItemId` and `resultLabel`, then lock as confirmed. Reject writes no target and locks as rejected. Revise accepts `{message}`, appends history, and may replace the complete proposal including `entityKind`; partial patch semantics are forbidden. Make transitions atomic and deterministic under duplicate requests. Authentication enforcement is retrofitted by the later auth batch; no circular dependency is introduced here.

## Scope

### In scope

- Grant separation, three actions, transition validation, target execution, and result linkage.

### Out of scope

- Auth implementation and direct AI target writes.

## Acceptance criteria

- An agent cannot call target writes through its grant.
- Confirm executes one generic destination write and is idempotent under retry.
- Reject never writes a destination.
- Revise can switch database to page content atomically and records the conversation.
