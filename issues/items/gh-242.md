**Blocked by:** #163

## Context

All four traffic classes work (#160–#163). This first of two final slices makes server-side failures and slow clients deterministic rather than creating silent holes or unbounded memory: every stream type already has a reliable resume path (Yjs state vector, `agent_run_events` cursor, reconnect refetch, unread fetch), so the server can answer both a LISTEN outage and backpressure with a blunt, correct disconnect. #164 builds the client-side reconnect and per-stream recovery that these disconnects rely on.

## Task

In `packages/realtime` (the WS server in `semprec-api`):

- **Heartbeat**: send an RFC 6455 protocol-level ping every 30 seconds (a control frame, not an application message — browsers and `URLSession` answer on their own). A connection that has not answered with a pong before the next ping is closed, targeting a detection window of about 90 seconds. The session revalidation against `sessions` defined in #160 as the fallback for a lost revocation NOTIFY runs in this same ping tick.
- **LISTEN outage**: when the dedicated LISTEN connection is lost or re-established, or the process shuts down in a controlled way, close every socket with close code 1012 ("Service Restart"). There is nothing to replay — NOTIFY is never persisted — so every client is forced through its resume path.
- **Limits**: reject client frames over 2 MB and reject more than 32 open `doc:open` subscriptions per connection. The number of connections per session is not capped.
- **Coalescing**: the per-socket outgoing queue coalesces pending invalidations per (`databaseId`, `itemId`), keeping only the one with the newest `updatedAt`.
- **Backpressure**: if a socket's `bufferedAmount` still exceeds 4 MB, close it with close code 1013 ("try again later"). Never silently drop individual stream frames of any type, and never grow an unbounded queue.
- Server-side fault-injection tests: LISTEN loss, controlled (deploy) shutdown, and slow consumer.

## Scope

### In scope

- Ping/pong, LISTEN-outage and shutdown closure, frame and subscription limits, invalidation coalescing, backpressure closure, and server fault-injection tests.

### Out of scope

- Client reconnect with exponential backoff and jitter, per-stream recovery orchestration, and client-side fault scenarios — #164.
- Replaying missed NOTIFY events, per-type selective dropping, realtime metrics/alerting, or connection caps per session.

## Acceptance criteria

- LISTEN loss and controlled shutdown close all clients with 1012; slow consumers close with 1013; revoked sessions remain 4401; a connection without a pong is closed within the ~90 second window.
- Memory remains bounded under repeated invalidations (pending invalidations for the same row coalesce to one carrying the newest `updatedAt`) and oversized frames or excess subscriptions are rejected deterministically.
- Server fault-injection tests for LISTEN loss, deploy shutdown, and slow consumer pass with no frame silently dropped.
