## Context

Every implementation pull request in this repository is reviewed by the code-review bot. Its findings are meant to be fixed, or answered with a concrete justification, before the pull request merges — but the `code-review` check reports `neutral` when it has non-blocking findings, and `neutral` satisfies branch protection. As a result a number of findings were merged into `develop` unaddressed.

An audit of every merged pull request that carries a review-memory note — #42, #43, #61, #62, #64, #65, #68, #71, #208, #209, #210, #254, #256, #257, #258, #259, #260, #261, #263, #264 — found **39** findings still marked `open` (#64, #65, #68, #71 and #257 have their findings recorded as fixed; #255 carries no note at all). Each was re-verified against the code on `develop`:

- **6 are already fixed** — all of #254's findings were closed by the follow-up pull request #255, which merged separately and left #254's memory table stale.
- **1 is already fixed** — the `emailSendAutonomous` scope finding on `seedTenDatabases.ts`: the property is no longer part of the shared Projects schema, and `mailSend.test.ts` now asserts it is not a declared property at all.
- **2 are already tracked** — the two `passesItemRelationFilter` findings from #258 are the subject of #262.
- **1 is already fixed** — the code-review job's missing `timeout-minutes` from #42 was closed by pull request #66, which set it to 30 minutes.
- **29 are real and still present.** This batch closes those 29.

The findings are grouped by the code they touch rather than one issue per finding, so each issue is one coherent pull request. Provenance is recorded below and inlined in each issue; no issue requires reading a pull request to be implementable.

## Decisions

- **Group by touched code, not one issue per finding.** *Reason:* several findings sit in the same function or the same file; separate issues would collide on the same lines and force needless rebases, and a single-line fix is not a coherent pull request.
- **Keep the test-only findings in one issue (08).** *Reason:* it touches no production code beyond one export, so it can be verified purely by the suites and does not interact with the behavioral issues before it.
- **Do not re-litigate findings the implementing agent answered.** *Reason:* where an agent replied to a finding with a concrete justification instead of a code change — the `draft.ts` "agent writes state directly" thread on #210, answered from #95's Task text and #92's spec — that answer stands and the finding is not reopened here.
- **Re-verify every finding against `develop` before filing.** *Reason:* the bot's review-memory tables are per-pull-request and are never updated when a later pull request fixes the code, so `open` in the table does not mean open in the tree — 10 of the 39 were already handled, by #255, by a follow-up on `seedTenDatabases.ts`, by #66, and by #262.
- **Where a finding offered two fixes, pick one in the issue.** *Reason:* an unsupervised agent cannot choose. For the `resolveFolders` contract (09) the doc comment is corrected to match the code, rather than making the code re-resolve folders mid-lifecycle, because re-resolution is behavior #196 never asked for.
- **Prescribe the fix that actually holds, not only the one the bot suggested.** *Reason:* for 01 the bot's `slotsToFill` suggestion still lets the very call that raised the limit take a slot before the woken waiters resume, so the issue prescribes a synchronous slot hand-off and says why the simpler fix is insufficient.
- **A "deleted" item is a soft-deleted row, not a missing one.** *Reason:* `itemsStore.getItemById` has no `deleted_at` filter and nothing in this repository hard-deletes items, so a null check alone would not cover the scenario the mailbox findings describe; issue 03 guards on `null` **or** `deletedAt`.
- **A sync pass for a removed mailbox is a terminal no-op, not a recorded failure.** *Reason:* the mailbox item is the row a sync status would be written to. The `catch` block's `updateItemWithClient` throws `NotFoundError` on a soft-deleted item and rolls back the `recordSyncError` in the same transaction, and a task that can never succeed must not be retried forever — so issue 03 returns early instead of throwing, and leaves the error path untouched.
- **Fix only what was flagged.** *Reason:* these issues exist to clear review debt, not to reopen design. Where a finding's neighbourhood suggested a wider change (validating `time` alongside `date`, adding rollups to `inboxItemTypes`, re-resolving folders on reconnect), the wider change is explicitly out of scope in the issue that borders it.
- **Include the workflow findings, exclude the CI redesign.** *Reason:* #42's and #43's findings are ordinary unaddressed review debt in files nothing else touches, so issue 12 closes them. `ci.yml` is a different thing: pull request #278 has since turned it into a real fast tier (backend type-check, web build and unit tests), and #250 adds the ephemeral-PostgreSQL integration tier on top, so touching `ci.yml` here would only collide with that.
- **The root-cause process gap is tracked nowhere, and this batch does not fix it.** *Reason:* the reason these findings merged at all is that the `code-review` check reports `neutral` when it has non-blocking findings, and `neutral` satisfies branch protection, so a pull request with open findings merges green. #249 defines required-check names and #250 adds the test tiers, but neither mentions the `code-review` check, and #278 repaired the build gate without touching branch protection — so nothing currently tracks this. It is a branch-protection decision for a human, not code; until it is made, this batch will need filing again.
- **Restructuring the Gmail and Graph branches in issue 02 is deliberate.** *Reason:* the finding names only the IMAP limiter wait, but the transaction those three branches share is what has to be split, so the other two cannot be left untouched; their behavior is unchanged.
