### Requirement gh-1925: [calendar-ics 01/06] Store a validated subscription URL on calendars

#### Context

Model tier rationale: One new property plus a validating and normalizing pre-write transform and a cutover follow existing patterns, but the save-time check is the only gate that keeps user-supplied URLs the server will later fetch from reaching internal addresses, so it needs careful tests (raised from low to medium for that security contract).

Calendars can be of several kinds; one kind is a subscription: a calendar whose events come from an external iCalendar feed at a URL the user provides. This issue lets a subscription calendar store that URL. It does not fetch anything. #1600 seeds the Calendars system database (with its `kind` property including `subscription`); #1901 seeds the invitations database in the same calendar module seed, and the new property is added after it in the seed order. #1960 (fetching) and #1962 (storing the events) build on this.

A stored URL that the server later requests must pass the baseline of `docs/adr/2026-09-27-ssrf-protection-for-stored-outbound-urls.md`, checked when it is stored: `isBaselineOutboundUrl` in `backend/packages/data/src/net/storedOutboundUrl.ts` accepts only `https:` URLs without credentials or an explicit port whose host is a DNS name that is neither `localhost` nor an IP literal. A DNS name that resolves to an internal address is stopped later, at connect time, by the fetch in #1960 (`docs/adr/2026-10-16-connect-time-outbound-address-checks.md`). Because a `webcal://` URL is rewritten before it is stored, the check runs as a pre-write property transform of the calendar module (the mechanism of #1422, which runs inside `createItemWithClient` and `updateItemWithClient` before the row is written and may return a changed patch or throw `ValidationError`); item hooks run only after the write and cannot change a value. Running in the choke point, it covers REST, `/mcp`, agent tools and the proposal path. The URL rules follow the existing `mcpServerItemCreateHook` in `backend/packages/data/src/mcp/mcpServerWriteHook.ts`.

Decisions:
- `subscriptionUrl` is allowed only on calendars whose `kind` is `subscription`; writing a non-null value to any other calendar is a `ValidationError` on `field: 'subscriptionUrl'`.
- A subscription calendar may exist without a URL (it is simply not fetched).
- `webcal://` URLs are accepted: on save the server rewrites the scheme to `https://` (host, path and query unchanged) and stores the `https://` form, which then passes the same baseline check as any other URL. Apart from that only `https:` is accepted; `http:` and every other scheme are rejected.
- `null` and the empty string clear the URL.

Shared-file ordering: this issue also waits for #1923 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1929: [calendar-invites 06/13] Parse iMIP invitations from stored mail

#### Context

Model tier rationale: It parses attacker-controlled iCalendar text from incoming mail and writes tenant data from it, with size limits, upsert idempotency under concurrent delivery and a parser that a second issue reuses, so a mistake is both a security and a data-integrity defect.

The mail sync already stores an iMIP invitation's calendar part: in `walkBodyStructure` (`backend/packages/data/src/mail/imapFlowClient.ts`) and its Gmail equivalent, a `text/calendar` leaf that is neither the plain-text nor the HTML body goes into the attachment parts, and `ingestAttachments` (`backend/packages/data/src/mail/attachments.ts`) writes it to blob storage, records a `mail_attachments` row with its `content_type`, and links a Files item to the Emails item through `Emails.attachments`. Nothing reads these parts as calendar data. Mail ingest (`mail/ingest.ts`) does not write to other databases and must keep not doing so (`docs/adr/2026-09-10-single-writer-ownership-model.md`): the calendar module reacts to the new Emails item instead.

This issue adds that reaction, the same way `mail.linkPeopleByEmail` (`mail/personLinkingActions.ts`) and the Inbox tick (`inbox/inboxTickAction.ts`) react to item creation: an `onItemEvent` create heartbeat on Emails whose action reads the calendar part, parses `METHOD:REQUEST` and upserts a row in the Invitations database from #1901. Decision: in this issue a higher `SEQUENCE` for a known `UID` updates the invitation only while its status is still `pending`; for an answered invitation this issue changes nothing. Carrying an organizer's update into an answered invitation and its Event (keeping the user's answer and edits) is #2007, which extends this action.

Decision (product owner): a recurring invitation (`RRULE`) is stored as one invitation for the first occurrence; the recurrence rule is ignored. Recurrence is a separate batch.

Decision: no new dependency; a small parser for the needed iCalendar subset is written in the repository (line unfolding, `BEGIN`/`END` nesting, parameters, quoted values, text unescaping).

### Requirement gh-1930: [semp-replies 07/08] Regenerate the latest Semp reply

#### Context

Model tier rationale: Regeneration rewrites what the model sees of the conversation (skipping a stored event range, dropping a live session) under races with new messages and compaction, and a wrong refusal rule would repeat tool writes, so it is a cross-process history and concurrency contract.

A user can ask Semp to produce a reply again from the latest answer ("Regenerate"). Today nothing like this exists: the conversation of a thread is rebuilt from `agent_run_events` by `walkStoredEntries` in `backend/packages/agent-runtime/src/conversationReconstruction.ts`, where a `compaction` event replaces all earlier history with its payload, and a live session in the registry (#1565) holds the in-memory history. The REST error contract in `backend/services/semprec-api/src/adapter/errorContract.ts` has no codes for refused regeneration.

After this issue the user can regenerate the latest successful reply of a thread. A new assistant message is queued as the next attempt of the same user message; the replaced answer is removed from what the model sees on later turns. It builds on the changed-item list of replies (#1885), which decides whether a turn wrote anything, and on the queued turn handler (#1727). It uses the `attempt` column and the unique index on (reply, attempt) introduced with the retry endpoint (#1926).

Decision: regeneration replaces, it does not keep versions. The old answer stays readable in the stored messages (with its steps) but is marked as replaced and is invisible to the model; the client shows only the newest attempt.

Decision: regeneration is refused for a turn that wrote anything. A turn with a non-empty list of changed items, or one that created an approval request, answers 409 `regenerate_after_writes`: regenerating only the text without tools is not offered, because repeating the turn would repeat its writes.

Decision: if the thread has written a compaction checkpoint after the replaced turn (an event id above `event_to_id`), the replaced answer is already folded into the checkpoint and cannot be removed: 409 `regenerate_after_compaction`.

Decision: only the latest message of the thread with status `done` can be regenerated, otherwise 409 `regenerate_not_latest`. Regeneration of an older answer (branching) is not offered.

Decision: the regenerated turn sends the original user message again as a new user turn, as the retry does; the duplicate user turn in the model history is accepted. A regeneration counts against the AI budget like any turn.

### Requirement gh-1931: [semp-replies 08/08] Raise and resolve a Semp problem for a failed reply

#### Context

Model tier rationale: One known mechanism (raise and resolve a deduplicated problem in the same transaction as the message result) over an existing problem store, with a clear dedupe key; the risk is transactional ordering, which the tests pin.

The status view lists problems that need the user's attention. A failed chat reply is one of them: the user should see "Semp did not finish the task", and the entry should disappear, with a "completed" line in history, once a retry succeeds. Today a failed turn only produces the run-level `agent_run_error` notification, which links to the agent run page and not to the chat.

The store for problems, with its `raiseProblem` and `resolveProblem` operations, is delivered by #1459. A reply is classified as failed or incomplete by #1907 (status `error`, or `done` with an `incompleteReason` from the function of #1890). The manual retry of #1926 creates a new assistant message with the same `reply_to_message_id` and an incremented `attempt`.

Decision: the dedupe key is `agents:reply:<reply_to_message_id>`, so all attempts of one reply are one problem; a failed retry raises it again (occurrence count goes up), a successful attempt resolves it.

Decision: both the raise and the resolve happen in the same transaction that stores the message result, so a rolled-back result never leaves a problem behind and a stored failure never lacks one. The problem carries no user content: it points to the message and thread by id; its title and text are rendered at read time by #1555.

Decision: the actions of the problem are `retryPrompt` (target: the message id, using `POST /api/semp/threads/:id/messages/:messageId/retry` of #1926) and `openChat` (target: the thread id and message id). Rendering them is the job of #1555; this issue stores the source reference needed to build them: `source_table` `semp_messages` and `source_id` the failed message id, plus the thread id in the problem's references.

#### Task

Load `state-writes` and `testing`.

1. In the turn handler (`backend/services/semprec-agents/src/sempMessageTask.ts`), in the transaction that writes the final state of an assistant message, call `raiseProblem` (category `agents`, kind `reply`, severity `warning`, `dedupe_key` `agents:reply:<reply_to_message_id>`, source the message) when the result is status `error` or the reply is incomplete according to the function of #1890.

### Requirement gh-1932: [agent-runs 20/21] List chat answers as separate rows

#### Context

Model tier rationale: Replaces the row identity of the run list for chat sessions with per-message rows, joining runs, Semp messages, attempt chains and cost attribution, with several distinct edge cases (retries, tick-thread turns, system-triggered turns, interim fallback), so the uncertainty is highest of the four and the higher tier is chosen.

A chat with Semp is one `unit = 'session'` agent run per project, so in the run list (#1909) a long conversation would be one row with the first task as title and the cost and duration of the whole session. The product shows each answer of the agent as its own entry: what the user asked, how long that answer took and what it cost. The conversation messages are stored in `semp_threads` and `semp_messages` (#1367); an assistant message stores its duration (#1860), a failed reply can be retried and the attempts of one answer share a reply identity (#1926), and gateway calls are attributed to the message they answer (#1744).

Decisions:
- A row for a chat answer represents one assistant message. Retried attempts of the same answer collapse into one row showing the latest attempt, with `attempt` set to its number.
- `title` is the text of the user message the assistant message replies to (`reply_to`). When the reply is to a system message with no text (a system-triggered turn such as the outcome of an approval), the title is a localized label chosen by the system message's `system_key` (for example for keys under `approval.outcome.*`), with a generic localized fallback for unknown keys.
- A turn in a heartbeat tick thread (a follow-up question or the continuation after an approval outcome) is a session run triggered by the user, and its `triggerLabel` is "Tik" according to `semp_threads.kind` of the thread, not "Chat".
- Until a project has any Semp messages for a session run (runs written before messages existed), that session run stays one row with the title of its first task.
- Other runs (heartbeat, MCP) remain one row each as in #1909 and #1914.

### Requirement gh-1937: [inbox-proposals 15/19] Reopen a rejected proposal

#### Context

Model tier rationale: One status transition on a single card with an existing locking and history pattern, but it deliberately relaxes the "locked card never changes" rule, so the guards need care.

A discarded card is final today. `LOCKED_PROPOSAL_STATUSES` (`confirmed`, `rejected`, in `backend/packages/data/src/inbox/inboxTypesStore.ts`) is honored by revise (`reviseProposalWithClient` throws), by the Inbox tick that skips locked cards (`inboxTickAction.ts`) and by reject (refuses `confirmed`). The user can discard a card by mistake with no way back, and the Inbox "undo" control must return the last decision to the stack with the values the card had.

#1845 adds `POST /api/proposals/:id/reject`. #1912 adds reset-overrides, which establishes the card's effective envelope (AI proposal plus user overrides) that must survive a discard unchanged. #1943 extends the same route so a confirmed card can be reopened too; this issue only handles `rejected`.

The state a card had before it was discarded is not recorded, so reopen recomputes nothing: it sets `proposed` when the stored envelope passes the existing envelope validation and `invalid` otherwise.
