## Context

Model tier rationale: Replaces an in-process background step with a durable outbox row and a queue job that talks to the provider, with at-least-once delivery, an idempotence check against the server, retry, a user-visible problem and a new tenant table.

Follow-up of sp-d4a5d05a-622e-45a1-9e0d-a881db6f2d93 (F14), on the coordinator's review: the detached Sent copy ran only in the API process, so a crash or restart between the SMTP acceptance and the APPEND lost the provider's Sent copy, and the shutdown drain only narrowed that window. Nothing stores the sent message's raw MIME today: `buildOutgoingMime` builds it per send and only attachments are blobs, so the bytes must be stored.

Decisions:

- `createSmtpMailTransport` opens no IMAP connection: an accepted send answers `needsSentCopy: true` (`MailTransportResult`). The Sent-copy saver, the detached-copy tracker, its `alldots-api` wiring and the shutdown drain are removed; the response still returns right after the acceptance and the finalization.
- New tenant table `mail_sent_copies` (baseline edited in place): id, mailbox, Message-ID, the accepted bytes, `failed_at`; unique per (tenant, mailbox, Message-ID); cascades with the mailbox item; left out of the tenant export (transient, the message is exported as its Emails item).
- `recordPendingSentCopy(client, …)` inserts the row and enqueues `mailSentCopy` (tenant task, job key `mail-sent-copy:<copyId>`, 8 attempts with graphile-worker's exponential backoff, about 1.5 h) on the caller's transaction: `sendDraftEmail`'s finalization (draft route, approved agent send, MCP send). The invitation jobs have no transaction that records their send, so they record right after the acceptance in a transaction of their own, retried, never thrown (a throw would send the invitation again), logged as an error when it still fails.
- The job (`handleMailSentCopyTask`) runs under the account's IMAP connection slot: `SEARCH HEADER Message-ID` in the Sent folder, APPEND with `\Seen` only when absent, then deletes the row. A repeated run after an APPEND whose deletion did not commit appends nothing. A mailbox that is gone, in the trash or with Mail off ends the copy without an APPEND (logged). Every other failure (no settings, credential or Sent folder, a refused or failed command) keeps the row and rethrows for the retry; the final attempt marks the row failed and raises the mailbox's `mailSentCopyFailed` problem (category mail, warning, `mail:sentCopy:<mailbox>`). The next appended copy of the mailbox gives every failed copy a new job; the problem resolves once none is left.
- `ImapFlowMailClient.hasMessageWithId` fails when the search did not run rather than answering "absent".

## Scope

### In scope

- A durable, idempotent Sent copy for every SMTP send and the removal of the in-process copy.

### Out of scope

- Storing the raw MIME of Gmail or Graph sends.
- A web or mobile action for the new problem beyond the status report's text.
- Any request against a real server.

## Acceptance criteria

- A draft send through an SMTP-like transport answers without any IMAP call, and its finalization committed one `mail_sent_copies` row with the accepted bytes and one keyed `mailSentCopy` job with the tenant's envelope and 8 attempts.
- With nothing of the sending process left (only the committed row and job), a worker run appends the copy once to Sent with `\Seen` and removes row and job.
- A run repeated after an APPEND whose deletion did not commit only searches and appends nothing; a further run finds no row.
- A refused APPEND keeps the row and rethrows; the final attempt marks the row failed and raises one `mailSentCopyFailed` problem for the mailbox; the next appended copy re-queues it, and once it is in, the problem is resolved.
- A copy of a trashed mailbox ends without an APPEND.
- The SMTP transport, send, compose-after-connect, invitation, tenancy catalog, RLS, item foreign key, export, status report and shutdown tests stay green.
