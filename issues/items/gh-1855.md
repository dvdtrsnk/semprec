## Context

Model tier rationale: An additive change to one existing read route, filter and row shape over fixtures that already cover the trash list, with title and path read from item state only.

The trash screen lists recently deleted items across all databases with their collection name, deletion time and days left. The list route, `GET /api/trash/items`, is delivered by #1851: it returns only the roots of a cascade, skipping items of inline databases whose parent was deleted in the same transaction. Pages are items of the hidden `pages` database (#1393), which is not a collection, and they are trashed together with their parent page or host in one transaction (#1723, #1763). Without a change they would appear as many rows of an unknown "Pages" collection, each without a readable name or place. The title of a page is the `title` property of its Pages item, mirrored from the parent document (#1725, #1715), so it is available without loading any document.

This issue teaches the trash list about pages: a nested page trashed with its parent is not a row of its own, and a page that is the root of a deletion is shown as a page with its title and the path to it.

Decisions:
- A Pages item is skipped as a non-root when its `parentItemId` points to an item that is deleted with the same `deletedAt` (a page, or a host item).
- For a root page the row keeps the fields of #1851 and adds `page: { title, path }`, where `path` is the chain of ancestors from the host to the parent as `[{ itemId, title, trashed }]` (host titles from the host item's `title`-typed property, page titles from the mirror), read from items including trashed ones, with a visited-set guard. The client labels such a row "Page" instead of using the collection name; `databaseName` stays the hidden database's localized name.
- The hidden database never appears in the trashed-databases list (it is a system database).

## Task

Load `testing` and `error-handling`.

1. In the trash items handler of #1851 extend the selection to skip non-root Pages items as defined above (same `deletedAt` as the parent, using the parent link and no document reads), keeping ordering, paging and `totalCount` consistent with the filter.
2. Add the `page` object to rows whose item is in the `pages` database, computed with one batched read of the ancestor items per page of results (no per-row queries beyond that), including trashed ancestors.
3. Tests: deleting a subpage that has two nested pages gives one row with `page.title` and a path `Notes > Release checklist`-style chain of titles; deleting a project with subpages gives the project's row and none for its subpages; a page trashed on its own earlier than its deleted parent gets its own row; paging and `totalCount` stay correct across a page of results made of both kinds; a renamed page shows the new title; another tenant's trash is not visible.

## Acceptance criteria

- When a subpage with two nested pages is deleted, then the trash list has one row for it with `page.title` and a `page.path` of its ancestors, and no rows for the nested pages.
- When a project with subpages is deleted, then the list shows the project row only.
- When a nested page was trashed on its own before its parent, then it has its own row.
- When a page is renamed, then the row shows the new title; `totalCount` and paging are unaffected by page rows being skipped.
