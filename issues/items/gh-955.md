## Behavior specification (approved)

Part of the multi-tenancy program specified in #950:

1. Each tenant has a daily and a monthly AI cap set only by an admin (`tenant_ai_budgets`); a tenant without a budget row is refused (fail closed); tenant zero inherits today's settings values.
2. A global safety cap from the gateway environment (`AI_GLOBAL_DAILY_CAP_USD`, `AI_GLOBAL_MONTHLY_CAP_USD`) applies on top; refusal for the tenant cap and for the global cap look identical.
3. Under the existing single reservation lock the gateway checks tenant spend (in the tenant's timezone) and global spend (UTC, via a router function).
4. A user's AI usage report shows only their own calls and their own caps.
5. The budget properties disappear from the user-editable settings item (contract, in a later release).

## Decisions

- **Why not per-tenant locks?** → The global cap needs one serialization point anyway.
- **Why move caps out of the settings item?** → Today any session or agent can patch its own budget there.
- **What does "a missing cap refuses" mean exactly?** → A tenant without a `tenant_ai_budgets` row is refused every call; a `NULL` daily or monthly column means no tenant cap for that window (the global cap still applies). → Tenant zero keeps today's `monthlyBudgetUsd: null` semantics.

## Out of scope

The admin endpoint and page to set caps (#958, #959).
