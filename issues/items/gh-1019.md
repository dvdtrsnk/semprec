## Context

Model tier rationale: The writer is specified, but its per-admin nested transactions, aggregate failure and rollback-driven retry need careful handling.

Operational alerts still go to the earliest-created account (`getEarliestUserId`):

- **`observability.checkSystem`.** `notifyObservabilityAlert` (`backend/packages/data/src/observability/observabilityCheckSystem.ts:20-40`) is used by:
  - `process_stale` (`:52-57`);
  - `queue_backlog`, for both the backlog check (`:115-120`) and the permanently-failed-jobs check (`:152-154`);
  - the mailbox stall check (`mail_sync_stalled`). #999 moved that one into the `forEachActiveTenant` fan-out and the tenant table `tenant_observability_checks`. Its alert uses `sourceTable: "tenant_observability_checks"`, but its recipient lookup is unchanged.

  #999 runs the whole handler inside `runAsSystem("observability:checkSystem", …)`. Each operator alert is written with `sourceTable: "observability_checks"`, the transitioned check's id, and `transitionInstance: "<job id>:<check key>"`. The alert is written inside the same transaction as the check's transition (`transitionObservabilityCheck`, `backend/packages/data/src/observability/observabilityChecksStore.ts:22-57`), so a sustained fault notifies exactly once.
- **`backup_restore_failed`.** `recordRestoreTestResult` (`backend/packages/data/src/observability/restoreTestResult.ts:26-51`) writes it the same way, with `transitionInstance: "<runId>:backup:restoreTest"` (`:38-48`). It is invoked by `restoreTestResultCli.ts:12-21` from `deploy/systemd/scripts/semprec-restore-test.sh`.

The decided behaviour:
- **Operator kinds go to every admin.** `process_stale`, `queue_backlog` and `backup_restore_failed` go to every admin as content-free rows. Their payloads stay exactly what they are today: `{ process, beatAt }`, `{ pending, oldestAgeMs }`, `{ count }` and `{ runId, failedCheck }`.
- **Mailbox stalls go to the tenant's user.** `mail_sync_stalled` is a tenant event and goes to the mailbox's tenant's user. No admin ever receives a mailbox id or `lastError`. This covers both producers of `mail_sync_stalled` in the per-tenant pass: the sync-state stall check from #999 and the live-sync heartbeat staleness check (`process:mailsync:<id>` rows in `tenant_observability_checks`, payload `{ mailboxItemId, beatAt }`) from #1000.

What earlier issues provide:
- `users.role` (`'admin' | 'member'`), `users.tenant_id` (1:1), and global `tenants.status`.
- `getTenantUserId(client)` (#1018).
- The `@semprec/shared` scope: `runInTenant(tenantId, fn)`, `runAsSystem(reason, fn)`, `currentTenantScope()`. `withTransaction` sets `app.tenant_id` from it at `BEGIN`.
- `runInTenant` may be entered from a system scope, but `runAsSystem` inside a tenant scope throws `TenantScopeConflictError`.

`notifications` is a tenant table with row-level security, so an admin only ever sees rows of their own tenant. Each admin's row must therefore be written in a transaction opened inside that admin's tenant; the system-scope check transaction cannot write it.

The legacy global `notifications_dedupe_idx (source_table, source_id, kind, transition_instance)` remains until #1065. Two admins can only coexist under it if each recipient gets its own `transitionInstance`.

## Task

Load `state-writes` (writes across tenants, ordering against the check's commit), `error-handling` (a failed recipient must roll back the transition so the retry redelivers) and `io-hardening` (connections held while nesting transactions).

1. **Recipients.** In `backend/packages/data/src/auth/usersStore.ts`, add `listAdminRecipients(client: Pool | PoolClient): Promise<Array<{ userId: string; tenantId: string }>>`. It runs `SELECT u.id AS user_id, u.tenant_id FROM users u JOIN tenants t ON t.id = u.tenant_id WHERE u.role = 'admin' AND t.status = 'active' ORDER BY u.created_at, u.id`, with a typed row.
2. **Operator writer.** Add `backend/packages/data/src/observability/operatorAlerts.ts`, which `backend/packages/data/src/index.ts` does not re-export, with `writeOperatorAlert(pool, client, input): Promise<string[]>`.
   - `input` is `{ kind: "process_stale" | "queue_backlog" | "backup_restore_failed"; checkId: string; transitionInstance: string; payload: Record<string, unknown> }`.
   - It reads recipients through `client`, the caller's open system-scope transaction.
   - For each admin, sequentially, it runs:
     ```ts
     await runInTenant(admin.tenantId, () =>
       withTransaction(pool, (c) =>
         writeNotification(c, {
           userId: admin.userId, kind, linkHref: null,
           sourceTable: "observability_checks", sourceId: input.checkId,
           transitionInstance: `${input.transitionInstance}:${admin.userId}`,
           payload: input.payload,
         }),
       ),
     );
     ```
   - It returns the ids. With no admin it returns `[]`.
   - Each admin's row commits before the caller's transaction does.
   - One admin's failed write does not skip the others. The error is logged with `{ err, tenantId }` and collected. After the loop, any failure is rethrown as `new AggregateError(errors, "writeOperatorAlert: <failed> of <n> admins failed")`, the same failure contract as `forEachActiveTenant` and its ADR (#983). This needs no new ADR.
   - The rethrow rolls back the caller's transition, and the job's retry redelivers. A retry reuses the same job id, so the same per-recipient key applies, and admins already written are deduplicated by `writeNotification`.
   - Document in the docstring: at most two connections are held, and delivery is at least once with exactly one row per admin and transition.
3. **Check system.** In `observabilityCheckSystem.ts`:
   - The three operator call sites call `writeOperatorAlert(pool, client, …)` with `checkId: transition.id`, `transitionInstance` set to `"<helpers.job.id>:<checkKey>"`, and today's payloads.
   - The mailbox stall notification uses `getTenantUserId(client)` inside its tenant transaction. It skips when the result is null, and its payload and source are unchanged.
   - Remove `getEarliestUserId` from the file and rewrite the comment at `:20`.
4. **Restore result.** In `recordRestoreTestResult`, a failed run calls `writeOperatorAlert(pool, client, …)` with `kind: "backup_restore_failed"`, `checkId: transition.id`, `transitionInstance` set to `"<result.runId>:<RESTORE_TEST_CHECK_KEY>"`, and `payload: { runId, failedCheck }`.
   - `RecordRestoreTestResultOutcome` becomes `{ notificationIds: string[] }`, empty for a passed run or with no admin.
   - Update the docstrings at `:10-25`.
   - In `restoreTestResultCli.ts`, run the call inside `runAsSystem("restore-test-result", ...)`. Print `restore test failure recorded, but no admin exists to notify` when a failed run returns no ids.
5. **Public surface.** Add `listAdminRecipients` to the runtime-export list in `backend/packages/data/src/__tests__/publicSurface.test.ts`.
6. **Tests.** Update `backend/packages/data/src/__tests__/observabilityCheckSystem.test.ts` and `backend/packages/data/src/__tests__/restoreTestResult.test.ts`.
   - Their account fixture becomes tenant zero's admin: `createUser(..., { tenantId: getTenantZeroId(), role: "admin" })`. The `tenantId` and `role` options come from #968, and `getTenantZeroId` from #975's harness.
   - Further tenants come from `createTestTenant(adminPool)`, with their users created the same way (`role: "admin"` or `"member"`).
   - While a second tenant exists, the task runs on `createRuntimeRolePool(adminPool, "semprec_data")` inside `runAsSystem`, and fixture writes to tenant tables run inside `runInTenant`. Cross-tenant assertions read through the superuser pool.
   - Inject a recipient failure with a test-created `BEFORE INSERT` trigger on `notifications` that raises for one `user_id`, dropped in `finally`.

## Acceptance criteria

- **Every admin, once.** Tenant zero's admin and tenant B's admin, plus tenant C with a member only. A `process_stale` transition writes exactly one notification per admin, each with that admin's `user_id` and `tenant_id`. C gets none. Each payload is exactly `{ process, beatAt }`. (integration, `observabilityCheckSystem.test.ts`)
- **Retry deduplicates.** Re-running the task with the same job id after a successful tick writes no further rows. (integration, `observabilityCheckSystem.test.ts`)
- **Failed recipient rolls back.** While B's admin's insert is forced to fail:
  - the task rejects with an `AggregateError`;
  - the `process:<name>` check is not left `alerting`;
  - tenant zero's admin already holds a row, because one failure skips no other admin.

  After the trigger is dropped, a re-run with the same job id leaves exactly one row per admin. (integration, `observabilityCheckSystem.test.ts`)
- **Inactive admins.** An admin whose tenant is `suspended` receives nothing. With no admin at all, the transition is still recorded and nothing is written. (integration, `observabilityCheckSystem.test.ts`)
- **Queue checks.** The backlog check and the permanently-failed-jobs check reach every admin with payloads `{ pending, oldestAgeMs }` and `{ count }` only. (integration, `observabilityCheckSystem.test.ts`)
- **Mailbox stall.** A stalled mailbox in tenant B notifies B's user only. No admin of another tenant gets a row. No operator-kind row in any tenant contains `mailboxItemId` or `lastError`. (integration, `observabilityCheckSystem.test.ts`)
- **Restore failure.** A failed restore run writes one `backup_restore_failed` per admin with payload `{ runId, failedCheck }` and returns their ids. The same run recorded again returns the same ids and writes nothing. A passed run returns `[]`. With no admin, the failure is still recorded and `[]` is returned. (integration, `restoreTestResult.test.ts`)
- **Ordering.** `listAdminRecipients` returns only admins of `active` tenants, ordered by creation. (integration, `observabilityCheckSystem.test.ts`)
