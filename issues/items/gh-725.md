## Context

`web/src/views/mailbox/MailboxClient.tsx`, `MailboxPanes`' folder-list load (`useAsyncResource`, lines 447-462) is a serial waterfall of independent requests:

1. `listItems(foldersDatabaseId)` — the folders (needed by everything after);
2. `Promise.all(folders.map(countItems…))` — one unread count per folder, already concurrent (line 452-454);
3. `await loadMailboxes(operations, config)` (`web/src/views/mailbox/accounts.ts` lines 10-20) — one `getItem` or `listItems` on the Mailboxes database;
4. `await loadFolderMailboxes(operations, config, folders, mailboxes)` (`accounts.ts` lines 27-46) — for an unscoped view, one `listItems` **per mailbox**, issued sequentially in a `for … of` loop with `await` inside (lines 38-44).

Steps 2 and 3-4 do not depend on each other, and step 4's per-mailbox reads do not depend on each other, so a view over M mailboxes with N folders pays roughly `1 + 1 + 1 + M` round trips in series (the N counts overlap). The backend has no grouped count and relation edges are not part of item properties (`relation_contains` is a filter, `web/src/api/genericOperations.ts` line 48), so the request count itself cannot drop without a backend change; the latency can. Depends on sibling issue G6 of this batch, which edits `MailboxPanes` first.

## Task

- In `accounts.ts` `loadFolderMailboxes`, replace the sequential loop with `Promise.all(mailboxes.map((mailbox) => operations.listItems(…)))` and fold the pages into the map afterwards (deterministic: iterate `mailboxes` in order when writing `map`, so a folder linked to two mailboxes resolves the same way as today — the last mailbox wins). Update the function's docblock ("one query per mailbox, in parallel").
- In `MailboxPanes`' folder-list loader, run the unread counts and the mailbox chain concurrently: `const [counts, { mailboxes, folderMailbox }] = await Promise.all([Promise.all(folders.map(countItems…)), loadMailboxes(…).then((mailboxes) => loadFolderMailboxes(…).then((folderMailbox) => ({ mailboxes, folderMailbox })))])` (or an equivalent shape). A failure in either branch still rejects the whole resource, as today.
- Tests:
  - `web/src/views/mailbox/__tests__/accounts.test.ts` (new, pure — no rendering): with a `GenericOperations` stub whose `listItems` returns deferred promises, `loadFolderMailboxes` for two mailboxes issues both `listItems` calls before either resolves, and the resulting map is the same as the sequential result for the fixture (`createMailboxBackend` from `web/src/test/mailboxFixture.ts`).
  - `web/src/views/mailbox/__tests__/MailboxClient.test.tsx`, new case in the panes block: wrap `createFakeOperations` so `countItems` returns a deferred promise; assert that `listItems` for the Mailboxes database has been called while the counts are still pending, then resolve and assert the folders render with their counts.
