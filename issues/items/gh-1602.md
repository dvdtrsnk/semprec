**Blocked by:** #1540
**Model tier:** medium

## Context

Model tier rationale: One pre-write transform rule over two new system-owned properties, using the transform seam and schema delivered by blockers, with simple deterministic fixtures.

When a task is not done on its planned day, the product carries it forward day by day (the nightly move is #1674) and the calendar shows traces of the days it was carried through (#1884). For that the system must remember the first day the task was planned for, and its time on that day. Today nothing stores it: the Tasks schema in `backend/packages/data/src/seed/seedTenDatabases.ts` has no `since`, `sinceTime` or `completedOn`, and `date`, `timeFrom`, `timeTo` and `status` are owned by `user`. A choke-point item hook runs after the write and cannot change the stored value (`backend/packages/data/src/chokePoint/hooks.ts`), so the value must be written before the write, in the Tasks transform.

#1540 adds `since` (date) and `sinceTime` (json `{from, to}`) to the Tasks schema as `system` properties owned by the `tasks` process, and #1422 adds the per-module pre-write transform. This issue implements the rule inside that transform. #1674 and #1780 write the same fields through the same rule; #1884 reads them.

Decisions: `since` is never cleared once set (the product keeps the first planned day for the traces even after the task is completed or moved earlier; no clearing rule is specified); "today" is the date in the system timezone setting (`getSystemTimezone`), not the device timezone (decided by the product owner: one zone from the settings for rollover and display, no automatic device zone in v1); `effectiveDate` equals `date` until #1780 introduces event-derived days.

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. In the Tasks transform, when a write changes `date` of a task whose `status` is `notDone`, whose current `effectiveDate` is before today, and whose `since` is empty: set `since` to the current `effectiveDate`, and set `sinceTime` to the current `{from: timeFrom, to: timeTo}` only when the current `effectiveDate` equals the stored `date` and a time exists (otherwise leave `sinceTime` empty).
2. A later change of `date` never overwrites an existing `since` or `sinceTime`. A change of `date` of a task whose current date is today or later, or of a task with a status other than `notDone`, does not set `since`.
3. Client writes of `since` and `sinceTime` are rejected as for any `system` property. Both fields are returned by every item read (GET, query, search, timeline) through the normal property serialization; add a test that GET and a view query include them.
4. Export the rule as a function that the nightly job (#1674) and the event-day recalculation (#1780) call, so the three writers share one rule.
5. Tests: a task of 13 October 10:00 to 11:00 moved to 14 October on 14 October has `since` 13 October and `sinceTime` `{10:00, 11:00}`; moved again on 16 October, `since` stays 13 October; moved to 20 October 9:00, `since` does not change; PATCH `date` on a task dated today or later or on a done task sets no `since`.

## Scope

### In scope

- The first-planned-day rule in the Tasks transform and its shared function.

### Out of scope

- The Tasks schema entries for `since`, `sinceTime`: #1540.
- The nightly move that also uses the rule: #1674.
- Recalculating `since` when adding a task to an event changes its effective day: #1780.
- Traces and `carriedFrom` in the calendar timeline: #1884.
- The completion day field `completedOn`: #1544.

## Acceptance criteria

- Task of 13 October 10:00 to 11:00, not done, moved to 14 October: `since` is 13 October and `sinceTime` is `{from: 10:00, to: 11:00}`.
- On 16 October `since` is still 13 October; moving the task to 20 October at 9:00 leaves `since` unchanged.
- PATCH `date` on a task dated today or later, or on a done task, does not create `since`.
- A client write of `since` or `sinceTime` returns 403.
