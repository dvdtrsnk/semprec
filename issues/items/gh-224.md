**Blocked by:** #110

## Context

Transactional schema changes and resumable item-content conversions solve different failure modes, and the module contract keeps them as two separate mechanisms. This part delivers the first one: the forward-only runner over the flat, numbered `db/migrations/*.sql` sequence for structural/system schema. A runner already exists as `runMigrations` in `backend/packages/data/src/db/migrate.ts` (bookkeeping table `schema_migrations`, lexically sorted `.sql` files, one transaction per file); this part formalizes it as the delivered tooling, with tests and a repository script, rather than reinventing it. The sibling part #111 builds on this runner (it ships its own structural migration through it) and delivers the second mechanism: `module_migrations`, `properties.migration_cursor`, and resumable batched data conversions. #112 onward and every later batch add their DDL as further numbered files applied by this runner.

## Task

Provide a forward-only runner over the flat numbered `db/migrations/*.sql` sequence for structural/system schema, built on `backend/packages/data/src/db/migrate.ts`:

- The sequence is one flat, numbered list of `.sql` files under `backend/packages/data/src/db/migrations/` (currently `0001_core_schema.sql` … `0007_mail_delivered_to_and_dsn.sql`), forward-only, with no per-module versioning — one shared transactional schema. No down migrations exist.
- The runner applies every not-yet-applied file exactly once, in ascending file-name order, each file inside its own transaction, and records the applied file in `schema_migrations` in that same transaction. A file that fails is rolled back, the runner stops, and no later file is applied; the failed file is retried on the next run.
- Re-running the runner against an up-to-date database is a no-op.
- Expose the runner as a stable repository script (a `package.json` script in `backend/`) that applies the directory against the configured database, and keep it usable by the integration test harness (`backend/packages/data/src/testSupport/`) that provisions an ephemeral database.
- Add unit/integration coverage for the ordering, once-only application, and rollback-and-stop behavior above.

## Scope

### In scope

- The structural runner, its bookkeeping, its transactional failure behavior, the repository script, and its tests.

### Out of scope

- `module_migrations`, `properties.migration_cursor`, batched resumable data conversions, and their concurrency guards (#111).
- Down migrations and background property-retyping behavior beyond invoking its converter.

## Acceptance criteria

- Structural migrations apply once in order; a second run applies nothing and changes nothing.
- A file that fails mid-way leaves no partial effect of that file, is not recorded in `schema_migrations`, and no later file is applied in that run.
- The repository script applies the directory end-to-end against an empty database.
