## Context

Model tier rationale: One known mechanism (a new hook registry invoked at three existing write sites in the same transaction) with existing relation-write test fixtures, but it must cover every internal edge writer and avoid recursion.

Today the only relation-edge hook is the validating `registerRelationEdgeWriteHook` (`backend/packages/data/src/chokePoint/hooks.ts`). It runs in `chokePoint/relationOps.ts` before `relationsStore.createItemRelation` (in `createRelationWithClient` and `updateRelationWithClient`) and also in a dry run from `assertRelationCreatableWithClient` (used by `inbox/proposalActions.ts`). It can reject an edge and check its metadata but cannot react to a committed change. `deleteRelationWithClient` calls no hook at all. A domain that must react to a link appearing, changing or going away (search reindexing, last-contact derivation, inherited values, the Inbox tick, speaker suggestions, thread-task people) therefore has no place to do it inside the writing transaction.

This issue adds that place: a second registry of hooks that run after the edge row has been written, with the operation and both endpoints. It builds on #1415 for the `writerKind` it hands every hook, and on #1422 because both issues edit `hooks.ts` and `domainWriteHooks.ts` (shared files, so they land in order). Later work registers against it: #1652, #1660, #1593, #1710, #1718, #1780, #1923, #1942, #1697 and #1669. #1601 adds the equivalent for item delete and restore after this one.

Decisions:
- `op` is `create` for every `createRelationWithClient` write, including a repeat create that replaces the metadata of an existing edge (the call site cannot tell, and the registry contract stays simple); `update` for `updateRelationWithClient`; `delete` only when `deleteRelationWithClient` actually removed an edge. An idempotent delete of a missing edge calls no hook.
- A hook may write other rows, but must not write the same relation (same definition and endpoints) again. The contract is enforced by a small re-entrancy check in the runner (Task 4) so a violation fails fast instead of looping.

Shared-file ordering: this issue also waits for #1520 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In `chokePoint/hooks.ts` add `registerRelationEdgeChangedHook(hook)`, the types `RelationEdgeChangedHookContext` and `RelationEdgeChangedHook`, and `runRelationEdgeChangedHooks(context)`. Context: `{ client, op: 'create' | 'update' | 'delete', relationDefinitionId, propertyId, itemA, itemB, metadata, writerKind }`, where `itemA`/`itemB` are the normalized stored sides, `metadata` is the stored metadata after the write (the removed edge's metadata for `delete`), and `writerKind` and the agent fields come from the shape introduced by #1415. Hooks run sequentially in registration order; the first rejection propagates and rolls the whole write back. Registering the same function twice is a no-op. Extend `clearHooksForTests`.
2. In `relationOps.ts` call `runRelationEdgeChangedHooks` after `createItemRelation` (op `create`), after `updateItemRelationMetadata` finds its edge (op `update`) and after `deleteItemRelation` returns an edge (op `delete`), each in the caller's transaction, after the rollup enqueue. Do not call it from `assertRelationCreatableWithClient` or on a 404/no-op path.
3. Because the hook is wired into the `*WithClient` functions, internal writers (the REST and agent relation operations, Inbox confirmation, mail folder edges, task recurrence, inbox type deletion) trigger it too. Document this in the header comment of `relationOps.ts` so the contract is visible. The validating `registerRelationEdgeWriteHook` and its call sites stay unchanged.
4. Guard recursion: the runner keeps a per-transaction set of `(relationDefinitionId, itemA, itemB)` currently being hooked; a hook that writes the same edge again throws an internal error naming the edge instead of looping.
5. Tests: unit tests for the registry; integration tests that create, update and delete (REST relation delete and an internal `deleteRelationWithClient`) each deliver the right `op` and both endpoints, that `assertRelationCreatableWithClient` runs no changed-hook, that a thrown error returns the write (no edge row remains), and that the recursion guard fires.

## Scope

### In scope

- The edge-changed registry, its three call sites in `relationOps.ts`, the re-entrancy guard and the tests.

### Out of scope

- Carrying `writerKind` into the relation write functions themselves: #1415.
- The hooks that consume it (search, last contact, inherited values, Inbox tick and the others named in Context), each in its own issue.
- Delete and restore hooks for items: #1601.
- Changing the validating edge write hook or its dry-run use.
- Relation operations that do not exist yet (`relation.set`, create-with-relations): they call the same `*WithClient` functions when added.

## Acceptance criteria

- A hook registered with `registerRelationEdgeChangedHook` receives `op: 'delete'` and both endpoints on a REST relation delete and on an internal `deleteRelationWithClient` call that removes an edge.
- A hook receives `op: 'create'` on a link and `op: 'update'` on a metadata replacement through `updateRelationWithClient`.
- A delete of an edge that does not exist calls no hook.
- `assertRelationCreatableWithClient` never runs an edge-changed hook.
- When a hook throws, the write is rolled back: the edge row is absent (create) or unchanged (update, delete).
- A hook that writes the same edge it was called for fails with an internal error instead of recursing.
- The transcript speaker validation hook behaves exactly as before.
