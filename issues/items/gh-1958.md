## Context

Model tier rationale: One idempotent one-time backfill that calls existing raise functions from five existing sources, run per tenant after migration; the care needed is idempotency and choosing the same keys as the producers, with existing cutover fixtures.

After the problem producers are deployed (#1911, #1465, #1506, #1945), failures that already exist at deploy time would stay invisible in the Semp status view until they fail again: a mailbox that has been failing for days, an unresolved drift finding, a tick that failed last night. This issue raises problems for the current failure state once, at deploy.

Post-migration data steps that read and write tenant rows run as application code for every maintained tenant (`runTenantCutoverMigrations` in `backend/packages/data/src/db/tenantCutoverMigrations.ts`, see `docs/adr/2026-09-10-app-code-post-migration-steps.md`), each inside the tenant's scope. This backfill is one more such step. It uses the problem store of #1459 and the same dedupe keys as the producers.

Decision: the backfill is idempotent and never inflates counts. Every raise carries `occurrenceKey` `backfill`, so running it again, or running it after a producer already raised the problem, adds nothing. It creates problems for the following current states only:
- mailboxes with `syncStatus` `error` or `needsReauthorization` and mailboxes with a `mail_sync_stalled` alerting check -> `mail:<mailboxItemId>`, `since` = `failing_since` if known, otherwise the last activity time;
- active guidance drift findings -> `guidance:<projectId>:<fingerprint>`;
- heartbeats whose last occurrence failed (`last_error` set) -> `agents:heartbeat:<heartbeatId>`;
- items outside the transcripts database whose library automation status is error -> `automation:<databaseId>`;
- transcripts whose `item_automation.status` is error -> `transcription:<transcriptId>` (the key and the kind that #1945 uses; a transcript is never counted into an `automation:` problem).
Operator problems (restore test, stale process) are not backfilled: their alerts re-fire on the next check.

Shared-file ordering: this issue also waits for #1950 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `testing` and `db-migrations`.

1. Add `backend/packages/data/src/semp/sempProblemsBackfillCutoverMigration.ts` exporting `runSempProblemsBackfillCutoverMigration(pool)`, which for the current tenant scope reads the five sources above, builds the keys with the same builders as the producers, and calls `raiseProblem` with `occurrenceKey` `backfill`, in batches inside transactions. It skips a tenant without a user.
2. Register it in `runTenantCutoverMigrations` in `backend/packages/data/src/db/tenantCutoverMigrations.ts` after the existing steps.
3. Tests: a mailbox in `needsReauthorization` gets a `critical` problem with the right `since`; a second run changes nothing; a problem a producer already raised keeps its count; a resolved source (healthy mailbox, resolved finding) gets none; a tenant without a user is skipped; tenants are isolated.

## Scope

### In scope

- The one-time, idempotent backfill of problems for the current mailbox, drift, tick, library automation and transcription failures.

### Out of scope

- The producers (#1911, #1465, #1506, #1945) and the store (#1459).
- Backfilling operator problems, failed chat replies and budget problems.
- Resolving problems whose source later recovers (#1915).

## Acceptance criteria

- When the step runs on a tenant with a mailbox in `needsReauthorization`, then a `critical` `mail:<mailboxItemId>` problem exists.
- When the step runs twice, then no problem changes and no `occurrence_count` increases.
- When a producer already raised a problem for the same key, then the backfill leaves its count and `first_seen_at` unchanged.
- When a source is healthy or resolved, then no problem is created for it.
- When one tenant's backfill fails, then the other tenants' backfills still complete and the failure is reported.
