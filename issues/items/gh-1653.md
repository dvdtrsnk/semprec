## Context

Model tier rationale: A single rule declaration over existing relations using the propagation engine and fixtures from the preceding issues, with the main risk being the union and removal behavior of a many-valued target.

A file belongs to one or more projects, and a project has at most one company. The file's companies should follow: they are the union of the companies of all its projects, and they update when the file's projects change or a project's company changes. A company the user adds by hand ends this for the whole property.

Today `Files.projects` (many-to-many with `Projects.files`), `Projects.company` (single-valued, inverse of `Companies.projects`) and `Files.companies` (many-to-many with `Companies.files`) all exist in the seeded schema (`seed/seedTenDatabases.ts`), and nothing connects them: a file's companies are only what someone wrote. #1411 provides the rule declaration and validation, and #1593 the engine that creates links, copies and propagates. This issue declares the first real rule, which needs no new relation. The same rule is later the second hop of chains where a file's project itself comes from a task, thread or event (#1898, #1756).

Decision: empty company sources keep the file empty but linked (`on`); a later company propagates through #1593. No special-case engine change.

Shared-file ordering: this issue also waits for #1647 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

1. In `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` add one entry to the manifest's `linkRules`:
   `{ key: "fileCompaniesFromProjects", source: { databaseKey: "projects", propertyKey: "company" }, target: { databaseKey: "files", propertyKey: "companies" }, via: { databaseKey: "files", relationKey: "projects" } }`.
   Use the existing database key constants from `seed/tenDatabaseKeys.ts`.
2. Make sure the rule passes `validateLinkRules()` and the drift check against the seeded schema, and that the engine from #1593 handles it without special cases. Fix defects found in the engine only if they are in the rule-agnostic code path, and describe them in the pull request.
3. Tests over the seeded ten databases: a file attached to Web for client and Bathroom renovation (companies Novak Web s.r.o. and Siko Koupelny a.s.) has both companies as `inherited` with two sources; changing a project's company flows to the file through the job; removing one project from the file removes its company from the file; adding a company by hand to the file (through the file's own write) ends the link for the whole property (`inheritedBroken`, `brokenBy: "user"`), and a later change of a project's company does not change the file; a file with a hand-set company before its first project keeps it as own and gets no link; a file whose projects have no company stays empty.

## Acceptance criteria

- When a file with projects Web for client and Bathroom renovation is read with `include=links`, then `links.companies` is `inherited` with two sources and the file's companies are the two projects' companies.
- When a project's company changes, then the file's companies update through the propagation job.
- When a user adds a company to the file by hand, then the link is `inheritedBroken` with `brokenBy: "user"` and later project company changes no longer reach the file.
- When all projects are removed from the file, then the companies stay as the file's own values and the link no longer exists.
- Existing files are not changed by deploying the rule.
