## Context

Model tier rationale: It lets a confirmed Inbox proposal change a locked database's schema inside the confirm transaction, combining proposal validation, a schema write under user authority and exactly-once semantics for a card that can be confirmed twice.

The assistant may find a tag that does not exist ("Herbs"). Today it cannot propose it: an unknown key is rejected (#1814), and the assistant has no way to create an option. With #1699 (an operation that adds an option to a select on a locked database) and the grounding of #1990, a proposal can name a new option by label, the card shows it as new, and confirming the card creates the option and uses it in the same transaction.

This is only released together with a card design that shows a new value as new and lets the user edit it; the backend part is specified here and waits for that design.

Decisions:
- An envelope may carry `newOptions: [{ propertyKey, label, color? }]` for a `select` or `multi_select` of the target database. A property value then names the new option by its label placed in the `properties` as `{ newOption: "<label>" }` in the place of a key.
- Validation (tick, revise, confirm): the property exists and is a select or multi-select; at most 3 new options per proposal; the label has 1 to 60 characters; a label that matches an existing option (same rule as #1699) is rejected as `option_label_exists`, and the computation should then use the existing key.
- Confirm runs the equivalent of `property.option.add` for each new option first, in the confirm transaction, substitutes the generated keys into the properties, and then creates the item. If any step fails, nothing is committed, including the option.
- A new option is created only when the person confirms; a rejected or discarded card creates nothing.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Extend the proposal envelope schema and `assertValidProposalEnvelope` (`backend/packages/data/src/inbox/inboxTickAction.ts`) with `newOptions` and the `{ newOption }` value form, with the rules above; the old envelope shape is unchanged.
2. In `confirmProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`), before creating the target item, add each new option using the option-add logic of #1699 on the same client, replace each `{ newOption }` by the returned key, then continue as today. Re-confirming a confirmed proposal creates nothing twice.
3. Extend the grounding of #1990 only to tell the model that a new tag may be proposed with `newOptions` when no listed option fits.
4. Tests: confirming a proposal with a new tag "Bylinky" creates the option and the health record carrying its key in one transaction; a failing item create (for example a missing title) leaves the option uncreated; a label matching Medication is rejected; four new options are rejected; a discarded card creates no option; confirming twice yields one option and one item; an envelope without `newOptions` behaves as before.

## Scope

### In scope

- The `newOptions` envelope field, its validation, and creating the options atomically on confirm.

### Out of scope

- The option-add operation and its rules: #1699.
- Grounding in the existing catalog: #1990.
- The card UI that marks a value as new.
- Letting the assistant create options outside a confirmed proposal.

## Acceptance criteria

- When a proposal with a new tag "Bylinky" is confirmed, then the option exists in the schema and the created health record carries its key, in one transaction.
- When the item create fails during confirm, then the option is not created.
- When a new option's label equals an existing one (for example "léky"), then validation rejects it with `option_label_exists`.
- When a card is discarded, then no option is created.
- When the same proposal is confirmed twice, then exactly one option and one item exist.
