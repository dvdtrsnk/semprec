## Context

Model tier rationale: Advisory locking and migration conflicts change scope; concurrency and repeated execution need explicit proof.

`runModuleDataMigration` (`backend/packages/data/src/migrationJob/moduleDataMigration.ts:60-108`) converts one manifest-declared transition `(moduleId, databaseKey, fromVersion, toVersion)` over a module database's items. Design: `docs/adr/2026-09-28-two-pass-skip-locked-module-data-migration.md`. Five parts are still global:
- **Lock.** On a dedicated `pool.connect()` client it takes a session advisory lock keyed `module-data-migration:<moduleId>:<databaseKey>:<from>:<to>` (`:41-45,66-73`). If another runner holds it, the run is a no-op.
- **Done check.** It returns early when `module_migrations` already holds the transition (`:76-80`).
- **Database lookup.** It resolves the database with `getDatabaseByModuleId` (`:82-83`).
- **Done marker.** After converting it records the marker with `INSERT ... ON CONFLICT (module_id, database_key, from_version, to_version) DO NOTHING` and deletes the progress row (`:87-101`).
- **Progress.** Progress is upserted with `ON CONFLICT (module_id, database_key, from_version, to_version) DO UPDATE` (`:182-197`).

Both tables are keyed globally by the transition (`backend/packages/data/src/db/migrations/0011_module_data_migrations.sql:9-16`, `0051_module_migration_progress.sql:10-19`). So once tenant zero has run a transition, another tenant's run of it is skipped, or turned into a no-op by tenant zero's lock.

Tenancy state this issue builds on:
- `module_migrations` and `module_migration_progress` are tenant tables. Each row carries `tenant_id DEFAULT app_tenant_default()` and the RESTRICTIVE `tenant_isolation` policy `tenant_id = (SELECT app_tenant_default())`.
- `app_tenant_default()` is `COALESCE(app_current_tenant(), app_sole_tenant())` over the GUC `app.tenant_id`.
- `pool.connect()` clients and `withTransaction` apply the ambient `runInTenant` / `runAsSystem` scope (`@semprec/shared`) to that GUC.
- Under a runtime role, the done check and `getDatabaseByModuleId` (which since #1001 filters `system` and throws when ambiguous) are therefore per tenant already.
- #1005 made `provisionTenant` and the deploy-time `runSeed` call `runModuleDataMigrations` inside `runInTenant`, on a `semprec_data` pool.
- #974 added the tenant-leading unique indexes `module_migrations_tenant_uq` and `module_migration_progress_tenant_uq`, each on `(tenant_id, module_id, database_key, from_version, to_version)`, beside both legacy primary keys. Those stay until #1065.

Arbiter choice:
- The marker insert becomes target-less `ON CONFLICT DO NOTHING`, so every unique index is an arbiter: both today, the tenant-leading one after #1065.
- The progress upsert needs a target for `DO UPDATE`, so it names the tenant-leading index. The per-tenant advisory lock serializes every writer of one tenant's progress row, so the non-arbiter legacy key cannot race it.

Until #1065, a second tenant's marker for a transition another tenant already recorded still meets the legacy primary key. The `DO NOTHING` silently skips it, and the idempotent converter simply reruns next time. The guard index keeps that state out of production.

## Task

Load `state-writes` (the marker and progress writes) and `error-handling` (the missing-tenant path must fail before any lock is taken).

1. **Tenant of the run.** Right after `pool.connect()` (`:66`), read `SELECT app_tenant_default()::text AS tenant_id` on the dedicated client, as a typed row.
   - When it is `NULL` (no tenant scope while several tenants exist), throw a plain `Error` saying a module data migration must run inside a tenant scope. Throw before taking any lock; the existing `finally` still releases the client.
2. **Lock key.** `lockKey` takes the tenant id and returns `module-data-migration:<tenantId>:<moduleId>:<databaseKey>:<fromVersion>:<toVersion>`. Use the same key for lock and unlock.
3. **Arbiters.**
   - The `module_migrations` insert (`:88-93`) uses `ON CONFLICT DO NOTHING` with no conflict target.
   - `writeProgress` (`:182-197`) uses `ON CONFLICT (tenant_id, module_id, database_key, from_version, to_version) DO UPDATE SET pass = EXCLUDED.pass, cursor = EXCLUDED.cursor`.
   - Do not add hand-written `tenant_id` predicates to the reads; RLS confines them.
4. **Docstrings.** `runModuleDataMigration` and `runModuleDataMigrations` describe one tenant's transition. Their callers run them inside that tenant's scope.
5. **Tests.** New `backend/packages/data/src/__tests__/moduleDataMigrationPerTenant.test.ts`, on the two-tenant runtime-role harness of #975: `createTestTenant()` and a `semprec_data` pool.
   - Each tenant gets its own fixture system database for the transition's `databaseKey`, created in its own scope with `createDatabase(..., { name, system: true, ownerModuleId })`, plus items.
   - The existing `moduleDataMigration.test.ts` (owner pool, one tenant) must keep passing unchanged.

## Acceptance criteria

All integration tests (`*.test.ts`) on the #975 harness unless stated.
- **Per-tenant data.** Tenant zero has already run and recorded transition T. A run of T inside tenant B's scope still converts B's items. In tenant zero's scope, tenant zero's marker is unchanged and tenant zero's items are not touched again.
- **Per-tenant lock.** The test holds the session advisory lock of tenant zero's key for T on its own connection. A run of T in tenant B's scope converts B's items. A run of T in tenant zero's scope returns without converting anything.
- **Same-tenant exclusivity.** Two concurrent runs of T in one tenant record T once, and the converter runs over each item at most once per pass. This is the existing concurrency case, repeated under `semprec_data` in tenant B's scope.
- **Progress per tenant.** A run in B's scope that fails mid-way leaves only B's progress row behind: none is visible in tenant zero's scope. A retry in B's scope resumes from B's recorded cursor and pass.
- **No scope, several tenants.** Called with no tenant scope while two tenants exist, the run rejects with the tenant-scope error. Nothing is converted, and no advisory lock remains held: `pg_locks` shows none for either tenant's key.
- **Single tenant unchanged.** With one tenant and no scope, every case in the existing `moduleDataMigration.test.ts` passes.
