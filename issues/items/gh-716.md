## Behavior specification (approved)

Make the web client (`web/`, React + TypeScript on Vite) actually reach `semprec-api`, authenticate against it and behave correctly on the screens that exist today. After this batch: `pnpm dev` proxies every `/api/*` route (including the `/api/sync` WebSocket upgrade) and `/mcp` to the backend instead of answering `index.html` for the generic item/view routes; a production deploy builds `web/dist` into the release and Caddy serves it as a static SPA with the backend-owned prefixes reverse-proxied; the client bootstraps its session from `GET /api/auth/session`, shows a login page (`?page=login`, also the target of the setup wizard's link) on 401 — at load or mid-session — and offers a logout; the never-mounted parallel stack (`view-types/**`, `AuthenticatedApiClient`, `AuthenticatedWebProvider`, the `cs.json`/`en.json` catalog pipeline) is deleted and the two web ADRs that describe it are superseded by ADRs describing the live stack; `ToolsBlock` loads under `<StrictMode>`; two overlapping mailbox triage actions never resurrect a message; the approval queue adapter validates its list response and no longer sends a client-chosen decider; the app locale comes from the session user and dates/currency follow it; the remaining hardcoded labels resolve through `messages.ts`; the setup token is stripped from the URL after it is read; the mailbox folder-list load runs its independent requests concurrently.

## Decisions

- How does a mid-session 401 reach the login page without editing seven adapters? → A `fetch` wrapper (`createSessionFetch`) passed as the `fetchImpl` option every adapter already accepts; it dispatches an `unauthorized` event the `App` subscribes to. The auth and setup adapters get the raw `fetch`. → One new module, no adapter edits, and a failed login (401) cannot bounce the app.
- Is the login adapter an ADR violation while `2026-09-14-authenticated-api-boundary-in-web-client` is still `accepted`? → No: the ADR's `AuthenticatedApiClient`/`AuthenticatedWebProvider` are never mounted, so there is no boundary to extend; the login adapter follows the live per-adapter pattern (`setupOperations.ts`, `agentRunOperations.ts`). Issue G4 supersedes the ADR. → Keeps the P0 login issue unblocked; the ADR is retired in the same batch.
- Delete or wire the parallel stack? → Delete it (`view-types/**`, `authenticatedWebContext.tsx`, `authenticatedApiClient.ts`, `cs.json`/`en.json`, `useLocalizedString.ts`, tests), add the duplicate-registration guard to `views/viewRegistry.ts`, and write two new ADRs that supersede the two 2026-09-14 web ADRs (frontmatter-only edits on the old ones). → The live stack (`api/genericOperations.ts` + `views/viewRegistry.ts`) is what every screen uses; two zod schemas, two renderer prop shapes and two i18n pipelines is exactly the drift both ADRs were written to prevent.
- Where do the `/api`-prefix lists live for dev and prod? → `web/vite.config.ts` proxies `/api` (with `ws: true`) and `/mcp`; `deploy/Caddyfile` reverse-proxies `/api/*`, `/mcp`, `/healthz` and serves everything else from `/opt/semprec/current/web/dist` with an `index.html` fallback; each file's comment names the other. → Both lists are short and stable; a shared constant across a Vite config and a Caddyfile is not expressible.
- One issue or two for "i18n and locale source"? → Two: the locale-source mechanism (session `user.locale`, `Intl` date/currency formatting) and the hardcoded-label mechanism (new `messages.ts` keys). → A reviewer can approve either without reading the other; ISSUE_FORMAT's one-mechanism rule.
- What replaces raw `error.message` in `ErrorState`? → A translated detail keyed on the HTTP status when present (`state.error.status`) or a transport message otherwise (`state.error.transport`). → Adapter messages are English technical strings; the status is the only user-meaningful part.
- Where is the `?token=` stripped? → In `SetupWizard` on mount via `history.replaceState`, not in `main.tsx`. → Testable with jsdom; `main.tsx` is the untested composition root.
- Where does the `Math.random()` key fix go? → Into the approval-queue adapter issue (G7), which already edits `ApprovalQueue.tsx`. → Avoids a third concurrently-eligible issue touching that file.
- Does the mailbox N+1 issue add a grouped-count endpoint? → No; the backend has no grouped count and unread counts are already batched. The issue only makes `loadFolderMailboxes` concurrent and overlaps it with the count requests. → No backend change belongs in a web-client batch.
