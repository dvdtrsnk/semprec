## Context

Model tier rationale: One new property plus a validating and normalizing pre-write transform and a cutover follow existing patterns, but the save-time check is the only gate that keeps user-supplied URLs the server will later fetch from reaching internal addresses, so it needs careful tests (raised from low to medium for that security contract).

Calendars can be of several kinds; one kind is a subscription: a calendar whose events come from an external iCalendar feed at a URL the user provides. This issue lets a subscription calendar store that URL. It does not fetch anything. #1600 seeds the Calendars system database (with its `kind` property including `subscription`); #1901 seeds the invitations database in the same calendar module seed, and the new property is added after it in the seed order. #1960 (fetching) and #1962 (storing the events) build on this.

A stored URL that the server later requests must pass the baseline of `docs/adr/2026-09-27-ssrf-protection-for-stored-outbound-urls.md`, checked when it is stored: `isBaselineOutboundUrl` in `backend/packages/data/src/net/storedOutboundUrl.ts` accepts only `https:` URLs without credentials or an explicit port whose host is a DNS name that is neither `localhost` nor an IP literal. A DNS name that resolves to an internal address is stopped later, at connect time, by the fetch in #1960 (`docs/adr/2026-10-16-connect-time-outbound-address-checks.md`). Because a `webcal://` URL is rewritten before it is stored, the check runs as a pre-write property transform of the calendar module (the mechanism of #1422, which runs inside `createItemWithClient` and `updateItemWithClient` before the row is written and may return a changed patch or throw `ValidationError`); item hooks run only after the write and cannot change a value. Running in the choke point, it covers REST, `/mcp`, agent tools and the proposal path. The URL rules follow the existing `mcpServerItemCreateHook` in `backend/packages/data/src/mcp/mcpServerWriteHook.ts`.

Decisions:
- `subscriptionUrl` is allowed only on calendars whose `kind` is `subscription`; writing a non-null value to any other calendar is a `ValidationError` on `field: 'subscriptionUrl'`.
- A subscription calendar may exist without a URL (it is simply not fetched).
- `webcal://` URLs are accepted: on save the server rewrites the scheme to `https://` (host, path and query unchanged) and stores the `https://` form, which then passes the same baseline check as any other URL. Apart from that only `https:` is accepted; `http:` and every other scheme are rejected.
- `null` and the empty string clear the URL.

Shared-file ordering: this issue also waits for #1923 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

1. Add property `subscriptionUrl` (type `url`, `owner: 'user'`) to the Calendars database in the calendar module's seed (the seed file #1600 created), after the invitations database seeding of #1901.
2. Add a cutover step in a new file next to the calendar seed, registered in `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`), that adds the property to the Calendars database of every maintained tenant (suspended ones included) under `LOCK TABLE properties IN EXCLUSIVE MODE` when it is missing. A second run changes nothing; a tenant without a Calendars database is skipped. Pattern: `backend/packages/data/src/transcription/transcriptsCatalogCutoverMigration.ts`.
3. Add a pre-write transform for the calendar module (registered with `registerItemPreWriteTransform` from #1422 in `domainWriteHooks.ts`) that acts only on the Calendars database and only when `subscriptionUrl` is in the patch: it rewrites a `webcal://` value to `https://`, then applies the rules above to the result and returns the patch with the normalized value, or rejects with `ValidationError` (`field: 'subscriptionUrl'`, HTTP 400 `validation_failed`).
4. Add i18n keys `property.calendars.subscriptionUrl.name` ("Adresa odběru" in `seed/i18n/cs.json`, "Subscription URL" in `en.json`) and bump the calendar module manifest version.
5. Tests: `http://example.com/a.ics` and `https://127.0.0.1/a.ics` and `https://localhost/a.ics` and `https://user:pw@example.com/a.ics` and `https://example.com:8443/a.ics` are all rejected with 400; `https://example.com/a.ics` is stored; `webcal://example.com/a.ics` is stored as `https://example.com/a.ics`; `webcal://127.0.0.1/a.ics` is rejected with 400; a URL on a non-subscription calendar is rejected; the same checks through `/mcp`; the cutover is idempotent and covers a suspended tenant.

## Scope

### In scope

- The `subscriptionUrl` property, its validation on every write path, the cutover for existing tenants, labels and tests.

### Out of scope

- Fetching feeds and connect-time address checks: #1960.
- Parsing feeds and storing their events: #2004, #1966.
- A UI or endpoint for adding a subscription; it comes with the interface design, not in this batch.
- Hiding or recoloring a subscribed calendar.

## Acceptance criteria

- When a subscription calendar is saved with an `http://` URL or a URL whose host is an IP address, then the answer is 400 `validation_failed` with `field: 'subscriptionUrl'` and nothing is stored.
- When it is saved with a valid `https://` DNS URL, then the value is stored and returned.
- When it is saved with `webcal://example.com/a.ics`, then `https://example.com/a.ics` is stored and returned; a `webcal://` URL whose `https://` form fails the baseline check is rejected with 400.
- When a URL is written to a calendar that is not a subscription, then the answer is 400.
- When an agent or `/mcp` client writes an invalid URL, then it is rejected the same way.
- After the cutover every tenant's Calendars database has the property; running it again changes nothing.
- The full backend `pnpm run verify` passes.
