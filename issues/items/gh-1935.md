## Context

Model tier rationale: One tenant-scoped read route that composes counts from several existing stores with a shared counting rule, using the established custom-route and isolation-test patterns and no write or lifecycle changes.

The project detail shows a row "Semp in this project" with a subtitle ("Instructions - 3 tools - 2 tasks") and an attention dot when something needs a person. There is no route for it: below `/api/projects/:id` only `mcp-grants` exists (`backend/services/semprec-api/src/mcpAgentPageHandler.ts`), and the numbers are scattered over five sources.

This issue adds `GET /api/projects/:id/agent-summary` as a manifest custom route with the `single-consumer-read` justification (`docs/adr/2026-09-11-module-manifest-custom-routes.md`), registered in `backend/packages/data/src/chokePoint/schemaCoreModuleManifest.ts` next to `systemHealthReport` (the module that owns the project agent system tables). Custom routes from manifests are dispatched before the hand-wired handlers, so it does not collide with the `mcp-grants` regex.

Response:

```
{
  hasGuidance: boolean,
  guidanceUpdatedAt: string | null,
  grantedToolCount: number,
  enabledHeartbeatCount: number,
  attention: {
    activeDriftFindings: number,
    failingHeartbeats: number,
    pendingApprovals: number,
    needsAttention: boolean
  }
}
```

Sources (one query per source, no per-row queries; all for the given project, the caller's tenant only):

- `hasGuidance`, `guidanceUpdatedAt`: the project's guidance record introduced by #1449 (`project_agent_guidance`); `hasGuidance` is true when a record exists with non-empty content.
- `grantedToolCount`: `counts.effective` from the same counting function as the grants list (#1455: granted, registration active, server active). It must call that function, not re-implement the rule.
- `enabledHeartbeatCount`: heartbeats of the project with origin `user` that are enabled, using the origin distinction from #1438. System heartbeats are not counted.
- `attention.activeDriftFindings`: rows of `agent_guidance_drift_findings` for the project with status `active`.
- `attention.failingHeartbeats`: user-origin heartbeats whose last occurrence has status `failed`, from the listing in #1910.
- `attention.pendingApprovals`: `approval_requests` with status `pending` whose run (`agent_runs.project_item_id`) belongs to the project.
- `needsAttention`: any of the three attention counts is greater than zero.

Decision (by the product owner): the dot reflects all three signals (active deviation from the instructions, a failing heartbeat, a waiting approval), not only the deviation shown in the first design. One dot means "needs attention"; the project detail tells the reason apart from the three counts.

A project id that is not a live Projects item of the caller's tenant (foreign, trashed or unknown) answers 404, identically.

Shared-file ordering: this issue also waits for #1930 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Scope

### In scope

- `GET /api/projects/:id/agent-summary` with the fields above, tenant-scoped and read-only.

### Out of scope

- Refreshing the summary in clients when the setup or runs change: #1866 and #1863.
- Computing any source (guidance, grants, heartbeats, findings, approvals) differently from its owner.
- Listing the findings, heartbeats or approvals themselves.

## Acceptance criteria

- For a project with guidance, three effective grants, two enabled user heartbeats and one active drift finding, the response is `{ hasGuidance: true, grantedToolCount: 3, enabledHeartbeatCount: 2, attention: { activeDriftFindings: 1, ..., needsAttention: true } }`.
- A grant on an inactive server and a system-origin heartbeat are not counted.
- When a user heartbeat's last occurrence failed, then `failingHeartbeats` counts it; when a run of the project has a pending approval, then `pendingApprovals` counts it; with all three attention counts zero, `needsAttention` is false.
- A project of another tenant, a trashed project and an unknown id all return the same 404; tenant B never sees tenant A's counts.
