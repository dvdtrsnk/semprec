**Blocked by:** #225, #113

## Context

Issue #225 formalized the unit and real-PostgreSQL integration tiers with stable scripts. This part completes the three-tier toolset with the third, smallest tier: a named e2e harness for the riskiest cross-module flows, with one representative scenario rather than complete coverage. It reuses the ephemeral PostgreSQL lifecycle from #225. #115 and later batches add scenarios to this harness as they introduce cross-module flows.

## Task

- Add a named e2e harness (its own Vitest configuration and include pattern, clearly distinguished from the unit and integration tiers) that boots the relevant modules through `ModuleRegistry` (#108) and the public contracts they expose, against the ephemeral PostgreSQL lifecycle from #225.
- Add one representative cross-module scenario that crosses a module boundary only through public contracts (registry projections, the choke point, or registered queue tasks) — never through a module's private internals.
- Extend the local scripts from #225 so the e2e tier runs alone and so that all three tiers run together, with isolated setup/teardown.

## Scope

### In scope

- E2E harness configuration, the representative scenario, and the scripts.

### Out of scope

- The unit and integration tiers (#225).
- Complete e2e coverage for every module, mocked-DB substitutes, and CI workflow files.

## Acceptance criteria

- All three suites run independently and together.
- The representative e2e crosses a module boundary through public contracts and passes against real PostgreSQL.
