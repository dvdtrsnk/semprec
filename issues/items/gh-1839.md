**Model tier:** high

## Context

Model tier rationale: This adds a new catalog operation reachable by agents over MCP whose counts must respect soft deletion, archived databases and per-database agent grants, across many relation shapes (including one-way edges read from the target side), so a mistake leaks existence or counts across an authorization boundary.

A record page shows, below its content, a "related" section: one row per collection with the number of records connected to the open record, and tapping a row opens that collection already filtered to those records. Today there is no way to ask for it. `item_relations` is readable from both ends (indexes on `item_a` and `item_b` in `0001_core_schema.sql`), but the generic operation catalog (`backend/packages/shared/src/genericOperations/operationNames.ts`) has no edge read or count, and no related endpoint exists. Several relations are one-directional (no inverse property): Files.area, Journal.area, Events.people, Events.actionItems, Movies.watchedWith, Emails sender and recipient people, Emails.attachments, Transcripts.speakers. The counts must still include them from the target side.

This issue adds the operation `relation.related` and `GET /api/items/:id/related`. It builds on: #1517 (the declared per-record-type order), #1404 (relation reading primitives), #1407 (database display order), #1810 (per-database grants), #1363 (one extra relation hop in filters), #1526 (emptiness filters), #1597 (per-database area filters declared in manifests), #1538 (Events linked to Areas). The mail row for projects requires #1573 (a Threads database) and the journal row for projects requires #1545 (Journal to Projects); until those exist the rows are simply absent. #1856 (delete impact) and #1874 (mail thread counts for people) build on this.

Response: a JSON array of `{ databaseKey, databaseId, count, via, filter }` where `via` is `direct` or `project`, and `filter` is a ready filter tree the client can pass to the database query for that collection. For the Threads database `filter` is `null`: the client opens mail threads with the viewed record's id as `projectId`, `areaId` or `personId` according to its type.

Decisions:
- The count equals the number of records the returned `filter` selects; the response carries no default quick filter and clients do not add one when opening a row.
- Archived databases are excluded (a record in an archived database is not counted).

Shared-file ordering: this issue also waits for #1837 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `testing` and `canonical-keys`.

1. Add `relation.related` to the operation catalog: name in `operationNames.ts`, input (`itemId`) and output schemas in `schemas.ts`, method in `port.ts`, capability `core.item.read` non-destructive in `capabilities.ts`, binding in `bindings.ts`, implementation in `genericApplicationService.ts`; update the catalog size assertions and contract tests. It is automatically available over MCP and to agents under the same name.
2. Add `GET /api/items/:id/related` in `backend/services/semprec-api/src/itemsHandler.ts`, dispatching `relation.related`; register the route in `routeMatrix.ts` and `__tests__/tenantIsolationRoutes.test.ts`.
3. Implement the read in a new `backend/packages/data/src/chokePoint/relatedOps.ts`: one SQL query over `relation_definitions` and `item_relations` covering both sides of every relation that targets or originates from the viewed record's database, including one-way relations from the target side (`item_b`). Count distinct records; exclude soft-deleted records on both ends, internal and system-process databases, empty collections and archived databases.
4. Add the step through a project for area and company records: Tasks only via projects; Files, Health records and Events via projects, with the record's own area counted only for items that have no project (for Events through the area link of #1538); Companies by their own area; no duplicates (a file with its own area and a project of the same area counts once); all projects of an area are included, finished ones too. For a company, events of its projects count as `via: project`; a manually set company on an event counts only when the event has no project. The `filter` of each row is the database's area filter from the manifest (#1597) or `relation_contains` / `relation_path_contains` for direct and project-path rows.
5. Mail: the Threads row for a project uses the thread's project, for an area goes through projects, for a company uses the thread's company. For a person, add a small contributor registry in this issue (a module registers a function returning an extra row for a record type) and leave it empty; #1874 fills it for people. Recordings count for a project through the event's transcript and for a person through transcript speakers.
6. Authorization: reject an unknown or other-tenant id like `item.get` does; for agent callers omit any collection the agent has no grant for (the row is absent, not zero).
7. Order rows by the record type's `relatedOrder` (#1517), skipping its `omit` keys; collections not listed follow by database display order (#1407), then custom databases by name.
8. Tests: the acceptance cases below, including the one-way relation case, de-duplication, trash and restore, archived database, grant omission, and tenant isolation.

## Scope

### In scope

- The operation, its REST route, the counting rules for direct and through-project relations, ordering, grant filtering, and the empty contributor registry.

### Out of scope

- Declaring the order and the area filters: #1517, #1597.
- Mail thread counts for a person: #1874.
- The delete-impact preview built on this operation: #1856.
- Missing relations in other collections (thread to project, tasks to people): they appear automatically once those relations exist.

## Acceptance criteria

- `relation.related` for a project returns only non-empty collections in the declared order and without Tasks.
- For an area it returns Projects including finished ones, and Tasks and Events with `via: project`; Journal and People are not returned.
- For a person it counts events through `Events.people` although People has no inverse property.
- A file that has its own area and also a project of that area is counted once; a soft-deleted file is not counted and is counted again after restore.
- An agent without a grant for the health records database gets no health records row.
- A record id from another tenant answers like an unknown id.
- The full backend `pnpm run verify` passes.
