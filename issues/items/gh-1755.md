**Blocked by:** #1727
**Model tier:** high

## Context

Model tier rationale: Partitioning worker capacity between chat and other agent work is a cross-process concurrency contract in the queue runtime, and an error leaves chat starved or ticks starved.

A user waiting for a chat reply should not wait because every job slot of the agents process is occupied by a long heartbeat run. In `backend/packages/queue/src/index.ts` jobs have no priority (`EnqueueJobOptions`), and a worker process runs `QUEUE_CONCURRENCY` jobs at once (default 4); `runWorker` in `backend/services/semprec-agents/src/queueRuntime.ts` starts one runner for all agent tasks. Ticks already run on their own lane, so a tick delays chat only when all slots are busy. graphile-worker's job priority (lower number first) only orders waiting jobs and never interrupts a running one, so priority alone cannot guarantee a free slot.

Builds on the queued turn task (#1727) and the lane decision (#1370).

Decision: reserve capacity with a separate runner for `sempMessage` (own concurrency), and add priority only as a supplement. The conservative alternative, to drop the capacity requirement and keep a shared runner, is rejected because a waiting chat reply is the most visible latency.

## Task

Load `testing`.

1. In `queueRuntime.ts` of `semprec-agents`, split the task list: a second `runWorker` runner handles only `sempMessage` with its own concurrency (`SEMP_CHAT_QUEUE_CONCURRENCY`, default 2), and the existing runner handles all other agent tasks and module tasks. Both runners are stopped by `stop()`, and `assertTaskListMatchesAffinity` still checks the union of the two lists.
2. In `backend/packages/queue/src/index.ts` add an optional `priority` to `EnqueueJobOptions`, passed to `graphile_worker.add_job` (`runWorker` already accepts a `taskList` and a `concurrency` override in its options, so the second runner needs no new runner option). `sempMessage` jobs are enqueued with a lower number (earlier) than `heartbeatFireAgent`.
3. Document `SEMP_CHAT_QUEUE_CONCURRENCY` next to `QUEUE_CONCURRENCY` in `deploy/shared/env/settings.env.example`, and validate it the same way `resolveQueueConcurrency` validates the general value.
4. Tests: with all slots of the general runner busy, a queued `sempMessage` still starts; a waiting `sempMessage` enqueued later is claimed before a waiting `heartbeatFireAgent` of equal age when both wait on the same runner; `stop()` stops both runners.

## Scope

### In scope

- A dedicated runner and concurrency for `sempMessage`, optional job priority, the environment variable and tests.

### Out of scope

- Changing how heartbeats choose their lane (#1370 fixes the Semp lane only).
- Recovery of interrupted turns (#1732).
- Per-thread queues or per-tenant caps beyond the lane serialization.

## Acceptance criteria

- When the general runner is saturated with agent jobs, a new `sempMessage` job still starts within normal polling latency.
- When both a `sempMessage` and a `heartbeatFireAgent` are waiting on a shared runner, the `sempMessage` is claimed first.
- Stopping the agents queue runtime waits for and stops both runners.
- Registered handlers across both runners equal the agents affinity set.
