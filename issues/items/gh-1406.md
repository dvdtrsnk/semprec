## Context

Model tier rationale: One known mechanism (an optional count computed with the existing filter compiler) across the shared schema, the data layer and the REST envelope, verifiable with the existing query fixtures and no new isolation or persistence contract.

`database.query` and `view.query` return only `{ items, nextCursor }` (`ItemPage` in `backend/packages/shared/src/genericOperations/rows.ts`, `toItemQueryEnvelope` in `backend/services/semprec-api/src/adapter/itemQueryEnvelope.ts`). A client that shows "13 items" above a paged list has to page through everything to learn the number. A matching count already exists inside the data layer: `countItems` in `backend/packages/data/src/chokePoint/itemsStore.ts` takes the same `buildFilterSql` as `listItems`, and `queryItemsCore` in `backend/packages/data/src/views/viewQuery.ts` is the one engine both `queryDatabaseItems` and `queryViewItems` run. Both input schemas (`DatabaseQueryInputSchema`, `ViewQueryInputSchema` in `schemas.ts`) are `.strict()`, so an unknown field is rejected today.

This issue lets a caller ask for the total number of items matching the query's filter, independent of paging. It is the foundation for the batched item counts and facet counts that build on it (#1709), and the same field is what a collection header ("N items") reads.

Decision: the count is opt-in (`includeCount: true`), so existing callers and the extra `count(*)` cost are unchanged. Decision: the count ignores `limit`, `cursor` and `sort`, honors `filter`, and excludes soft-deleted items unless `inTrash` is true (the same `includeDeleted` the page uses). Free-text search (`q`) is not part of this issue; when it is added to these queries (#1857) it must not change `totalCount`.

## Task

Load `testing` and `error-handling`.

1. In `backend/packages/shared/src/genericOperations/schemas.ts`, add `includeCount: z.boolean().optional()` to the shared `queryFields`, so both `DatabaseQueryInputSchema` and `ViewQueryInputSchema` accept it. Add an optional `totalCount: number` to the paged output type used by `database.query` and `view.query` (`Page`/`ItemPage` in `rows.ts`, wired in `port.ts`). The field is present only when `includeCount` was true.
2. In `backend/packages/data/src/views/viewQuery.ts`, add `includeCount` to `QueryViewOptions`, `DatabaseQueryInput` and `ViewQueryInput` (validated like `inTrash`: a non-boolean is a 400 with `field: "includeCount"`), and to `QueryViewResult` as `totalCount?: number`. In `queryItemsCore`, when requested, compute the count with `countItems` using the same compiled filter and `includeDeleted`, ignoring cursor, limit and sort, inside the same transaction as the page. For a filtered or linked view the count uses the view's effective filter (the request override, else the stored `config.filter`), exactly as the page does. For a curated view (`databaseId === null`) the count is the number of live members of the view (members whose item is not deleted, or all members when `inTrash` is true).
3. Pass the flag through `backend/packages/application/src/genericApplicationService.ts` (`queryView`, `queryDatabase`) and the REST handlers in `backend/services/semprec-api/src/itemsHandler.ts` and `viewsHandler.ts` (read `body.includeCount`). Extend `ItemQueryEnvelope`/`toItemQueryEnvelope` with `totalCount` only when the result carries it. The MCP and agent tools derive their schemas from the shared catalog, so no separate MCP code is needed; keep their contract tests green.
4. Tests: filter `Status in {inProgress, longTerm}` over a fixture with 13 matching items returns `totalCount` 13 with `limit: 5`; the same count with a `cursor` from page 2; a soft-deleted match is not counted and is counted after restore; `inTrash: true` counts per the page's `includeDeleted`; a curated view; a non-boolean `includeCount` is a 400; omitting the flag leaves the response without `totalCount`.

## Scope

### In scope

- The opt-in `includeCount` input and `totalCount` output on `database.query` and `view.query`, over REST, MCP and agent tools.

### Out of scope

- A batched count across databases with grouping: #1709.
- Facet counts per property: #1759.
- The `q` free-text parameter and its exclusion from the count: #1857.
- Any new filter condition (relative dates, numbers): #1522, #1534.

## Acceptance criteria

- When a query filters `status in [inProgress, longTerm]` (13 matches) with `includeCount: true` and `limit: 5`, then the response has 5 items and `totalCount` 13.
- When the client follows `nextCursor` to later pages, then `totalCount` stays 13 on every page.
- When a matching item is soft-deleted, then `totalCount` drops by one; when it is restored, it returns.
- When `includeCount` is omitted or false, then the response has no `totalCount` and runs no count query.
- When `includeCount` is not a boolean, then the request fails with a 400 naming the `includeCount` field.
- When the same filter is sent to `POST /api/databases/:id/query` and `POST /api/views/:id/query` for a view over that database, then both return the same `totalCount`.
