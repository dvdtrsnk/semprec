## Context

Model tier rationale: One known mechanism (a relation check in an existing heartbeat action plus a per-tenant action_config cutover) across a seed, an action and a cutover migration, with the existing transcription tests as fixtures, but it changes persisted heartbeat config on every tenant.

Today the `core.filesTranscriptionTrigger` heartbeat action (`backend/packages/data/src/transcription/transcriptionActions.ts`, `createFilesTranscriptionTriggerAction`) fires on every Files item creation. It enqueues a transcription job for a file whose blob is `audio/*` and that carries no `Emails.attachments` edge, because an emailed audio attachment is not a standalone recording. The heartbeat's `action_config` (`{ filesDatabaseId, attachmentsRelationPropertyId }`, validated by `filesTranscriptionTriggerConfigSchema`) is resolved once at seed time in `backend/packages/data/src/seed/seedSystem.ts`.

#1588 adds the `Files.events` relation (property key `events`), so a file can be attached to a calendar Event. #1645 lets the upload request attach the file to an item in the same transaction, so the `Files.events` edge exists when the Files item is committed, and the trigger (which runs after commit) sees it. #1574 adds the recording upload endpoint; that issue also changes this same trigger, so the two must be merged one after the other.

Without this issue, an audio file attached to an Event (for example a voice memo on a meeting) would be transcribed as if it were a standalone recording and would create a Transcriptions row the user never asked for.

Decision: an audio file attached to an Event is a plain attachment, not a recording. It is not transcribed and does not become a recording; recordings are created only through the recording upload endpoint from #1574.

Shared-file ordering: this issue also waits for #1675 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `db-migrations` and `testing`.

1. In `transcriptionActions.ts`, extend `filesTranscriptionTriggerConfigSchema` with an optional `eventsRelationPropertyId` (uuid). Optional so a heartbeat that has not been cut over yet keeps working with its old config.
2. In `createFilesTranscriptionTriggerAction`, after the existing `Emails.attachments` check and before `enqueueTranscriptionJob`, resolve the relation definition for `eventsRelationPropertyId` with `relationsStore.getRelationDefinitionByPropertyId` and list the file's edges with `relationsStore.listRelationsForItem`. If at least one `Files.events` edge exists, return without enqueuing. Update the docstring to say an Event attachment is skipped like an email attachment.
3. In `seed/seedSystem.ts`, resolve the `Files.events` property with `propertiesStore.getPropertyByKey(client, tenDatabases.files.id, <events key>)` and put its id into the `Files transcription trigger` heartbeat's `actionConfig` as `eventsRelationPropertyId`. Throw if the property is missing, in the same way the existing attachments lookup does.
4. Add a per-tenant cutover that sets `eventsRelationPropertyId` in the `action_config` of the existing `Files transcription trigger` heartbeat (`project_heartbeats` row with `action_id = 'core.filesTranscriptionTrigger'`) on populated installs. Follow `transcription/transcriptionRequeueHeartbeatCutoverMigration.ts` and `docs/adr/2026-09-10-app-code-post-migration-steps.md`: a new file `transcription/transcriptionTriggerEventsCutoverMigration.ts`, one transaction, idempotent (no-op when the key is already set, when the heartbeat does not exist, or when the Files database or its `events` property does not exist yet), and registered in `runTenantCutoverMigrations` in `db/tenantCutoverMigrations.ts`.
5. Tests: unit tests in `transcription/__tests__/transcriptionActions.test.ts` (audio file with a `Files.events` edge is skipped; a standalone audio file is still enqueued; an old config without `eventsRelationPropertyId` still works) and a cutover test next to `transcriptsCatalogCutoverMigration.test.ts` (sets the key, second run is a no-op).

## Scope

### In scope

- Skipping transcription for an audio Files item that has a `Files.events` edge.
- The new optional config key, its seed value and its per-tenant cutover.

### Out of scope

- Creating the `Files.events` relation (#1588) and attaching a file to an item at upload (#1645).
- The recording upload endpoint and its own transcription path (#1574).
- Making an Event audio attachment appear as a recording.
- Changing the trigger for any other relation or file type.

## Acceptance criteria

- When an audio file is created with a `Files.events` edge, then no transcription job is enqueued and no Transcriptions row appears.
- When a standalone audio file with no `Emails.attachments` and no `Files.events` edge is created, then a transcription job is still enqueued.
- When the heartbeat's `action_config` has no `eventsRelationPropertyId` (not yet cut over), then the action still runs and behaves as before.
- On a fresh install, the seeded `Files transcription trigger` heartbeat carries `eventsRelationPropertyId`.
- When the cutover runs on a tenant seeded earlier, then the existing heartbeat gains `eventsRelationPropertyId`; running it again changes nothing, and a tenant without the heartbeat is left alone.
