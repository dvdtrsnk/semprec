**Blocked by:** #1903
**Model tier:** high

## Context

Model tier rationale: A multi-id restore in one transaction with a savepoint per id, where a rolled-back id must also discard the after-commit realtime announcements it queued and a restore hook's rejection must not abort the others; this is transaction and cleanup-ownership logic that is easy to get subtly wrong.

Restoring is a single-item operation today. `POST /api/items/:id/restore` brings an item and the part of its cascade that was trashed with it back, idempotently (`restoreItemWithClient` in `backend/packages/data/src/chokePoint/itemTrash.ts`, which is not exported), and answers `403 database_archived` for an item of an archived database. `POST /api/databases/:id/restore` clears `archived_at` (`databasesStore.restoreDatabase`, announced as a schema change by the choke point's database operations). The "Recently deleted" screen lets the user select several rows of one tab (items or databases) and restore them together; a client can call the single routes in a loop, which works, but is slow, not atomic in its announcements and cannot tell "this one was refused" from "this one failed".

This issue adds `POST /api/trash/restore`, a custom route of the schemaCore module. Each id is restored in its own savepoint inside one transaction: one id's refusal rolls back only that id and the others still restore. A refusal that matters in practice is a restore hook rejecting an item, for example a Journal day whose period already has a live entry (#1601 introduces the item restore hook that can reject; the Journal rule that uses it is #1603). It lists archived databases for the client's selection through #1873 and trashed items through #1851.

Decisions:

- The body is `{ itemIds: uuid[], databaseIds: uuid[] }`, at most 100 ids in total (duplicates merged), at least one; a mixed body is accepted (a client sends one tab's ids). Databases are restored first, then items, so items of a just-restored database restore in the same call.
- Result per id: `restored` (also for an item that was not trashed: restore is idempotent), `not_found` (unknown id, or another tenant's id: the same status), `database_archived` (an item whose database is archived), `conflict` (restore rejected with `409`). Any other failure is not caught per id: it aborts the request with its normal error, because it means a defect, not a refusal.
- The response is `200 { results: [{ id, kind: "item" | "database", status }] }` in request order (databases first), even when every id was refused.

Shared-file ordering: this issue also waits for #1903 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Export `restoreItemWithClient` from `itemTrash.ts` and add `databaseRestoreWithClient(client, id, actingUserId)` to `backend/packages/data/src/chokePoint/databaseOps.ts` (the counterpart of `databaseArchiveWithClient`: `databasesStore.restoreDatabase` plus the schema invalidation), and make `createDatabaseOps().restoreDatabase` use it.
2. Add `withSavepoint(client, fn)` to `backend/packages/data/src/db/pool.ts`: runs `fn` between `SAVEPOINT` and `RELEASE`, and on an error rolls back to the savepoint and discards the `runAfterCommit` callbacks that were queued since the savepoint began, so a refused id announces nothing after the commit; the error is rethrown to the caller. Add unit tests, including a callback queued before the savepoint surviving and one queued inside it being discarded.
3. Add `createTrashRestoreRouteHandler(pool)` to `trashRouteHandlers.ts` (`POST /api/trash/restore`, justification `transactional-semantics`): validate the body strictly (UUIDs, limits above, unknown keys rejected); in one `withTransaction`, restore each database id and then each item id through `withSavepoint`, mapping a not-found database or item to `not_found`, `ForbiddenError` with code `database_archived` to `database_archived`, and a `409` from a restore hook to `conflict`. Restoring an item resolves its database by looking the item up by id (including deleted items) in the tenant's databases. The realtime announcements are the ones the single restores make (item announcements per restored row, schema announcement per restored database).
4. Register the route in `schemaCoreModuleManifest.ts` (name `restoreTrash`, `POST /api/trash/restore`, handler re-exported), `routeMatrix.ts` (`"restore trash"`), `tenantIsolationRoutes.test.ts` (a foreign id answers `not_found`, exactly like an unknown id, and tenant A's rows stay trashed) and `chokePointWriteBoundary.unit.test.ts`.
5. Tests in `backend/packages/data/src/trash/__tests__/trashRestore.test.ts`: restoring 3 ids of which one does not exist restores 2 and reports `not_found` for the third; a database and its (previously trashed) items restore together when sent in one body; a Journal day whose period already has a live entry returns `conflict`, stays in the trash and the deleted task in the same request is restored; an item of an archived database returns `database_archived`; a repeat call returns `restored` for all and changes nothing; the announcements after commit exist for restored ids only; more than 100 ids and an empty body are `400 validation_failed`.

## Scope

### In scope

- The bulk restore route, the savepoint helper that also discards queued after-commit announcements, and the exports it needs.

### Out of scope

- The restore hooks and the Journal rule that rejects a restore: #1601, #1603.
- Listing what can be restored: #1851, #1873.
- Permanent deletion of selected rows or emptying the trash: not planned yet; it waits for a product decision.
- Changing the single-item restore route's behavior.

## Acceptance criteria

- When three ids are sent and one does not exist, two are restored and the third is reported `not_found`.
- When one selected Journal day cannot be restored because its period already has a live entry, it is reported `conflict` and stays in the trash, while the other selected ids are restored.
- A refused id leaves no realtime announcement behind; restored ids are announced as with the single restore.
- A repeated call is idempotent; another tenant's ids are answered like unknown ones.
- More than 100 ids, an empty body or a malformed id is `400 validation_failed`.
