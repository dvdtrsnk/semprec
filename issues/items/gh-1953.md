## Context

Model tier rationale: It adds an outbound email side effect that must be coupled to a database commit, retried across provider transports and idempotent on redelivery, and it writes the iTIP reply format that external calendar clients interpret.

#1944 lets the user answer an invitation and commits the new status. The organizer must then be told: an iMIP `METHOD:REPLY` message has to reach them from the mailbox that received the invitation. Today `sendDraftEmail` (`backend/packages/data/src/mail/send.ts`) is the only send function and no production code calls it; `OutgoingMailMessage` (`mail/smtpClient.ts`) knows only text and html. The outgoing MIME builder with an optional calendar part is delivered by #1491, and the per-mailbox transports by #1634 (SMTP), #1637 (Gmail API) and #1753 (Microsoft Graph). This issue builds the reply content and the job that sends it; it does not add a transport.

The send must happen only after the answer committed and must not happen when the transaction rolled back. So the respond handler enqueues a queue job inside its own transaction (commit-coupled, the same pattern as `enqueueNotificationFanout` in `notifications/notificationFanoutJob.ts`), and a module task sends it with retries.

Decision: the attendee address in the reply is the address the invitation was delivered to (`mail_message_meta.delivered_to_address`, resolved at ingest by `mail/deliveredTo.ts`), falling back to the first line of the receiving mailbox's `Mailboxes.addresses` (parsed with `parseAddressListProperty`).

Decision: a reply is sent for `accepted`, `tentative` and `declined` of an invitation of kind `invite` that has an organizer address; nothing is sent for `acknowledged`. The user can change an answer (#1944), and every change sends a new reply with the new `PARTSTAT`; answering with the answer already stored sends nothing. A failure after the retries is logged with the invitation id and a reason code and does not undo the answer.

The same `text/calendar` serialization is also needed by #1774 for requests and cancellations. This issue creates the low-level writer (`icalendarWriter.ts`: escaping, 75-octet line folding, CRLF, property emission); whichever of the two issues merges second extends the existing file instead of creating another one.

Shared-file ordering: this issue also waits for #1952 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. Add `backend/packages/data/src/calendar/icalendarWriter.ts` with the low-level serialization helpers and `buildItipReply({ uid, sequence, organizerEmail, attendeeEmail, attendeeName?, partstat, summary, startsAt, endsAt, allDay })`, which returns a `VCALENDAR` with `METHOD:REPLY`, one `VEVENT` carrying `UID`, `SEQUENCE`, `DTSTAMP`, `ORGANIZER`, one `ATTENDEE` with `PARTSTAT` `ACCEPTED`, `TENTATIVE` or `DECLINED`, and the original `DTSTART`/`DTEND`.
2. Add `backend/packages/data/src/calendar/invitationReplyJob.ts` with the task payload schema `{ invitationId, response, respondedAt }`, `enqueueInvitationReply(client, { invitationId, response, respondedAt })` (job key `invitation-reply:<invitationId>:<respondedAt>`, so a repeated enqueue of the same answer collapses while a changed answer gets its own job) and the handler. The handler loads the invitation in the tenant scope; when its current `respondedAt` differs from the payload's (the answer was changed again before this job ran), it ends without sending, because the newer answer has its own job. Otherwise it resolves the receiving mailbox and the attendee address (see Context), builds the message with the MIME builder from #1491 (a short plain-text body, the subject `Accepted: <title>`, `Tentative: <title>` or `Declined: <title>`, and the `text/calendar; method=REPLY` part) addressed to `organizerEmail`, and sends it through the transport the mailbox provider uses (#1634, #1637, #1753). A transient transport failure rethrows so the queue retries with backoff; a permanent one (mailbox deleted, no usable transport for the provider, no organizer address) is logged and ends the job without retry.
3. Declare the task in `taskNames` of `backend/packages/data/src/calendar/calendarModuleManifest.ts` (name `calendarSendInvitationReply`, `queueAffinity` `api`), exporting the payload schema and the handler from that file.
4. In `createRespondToInvitationRouteHandler` (`backend/packages/data/src/calendar/invitationRouteHandlers.ts`), call `enqueueInvitationReply` inside the existing transaction after the status write, for `accepted`, `tentative` and `declined` of an `invite`, including a changed answer. An unchanged repeated answer (no write) and a rolled-back answer enqueue nothing.
5. Register the task handler where the API runtime merges module tasks (`mergeModuleTaskList` in `backend/packages/data/src/moduleTasks.ts` already does this for manifest tasks; wire any composition-root dependency, for example the mail send adapter factory, in `backend/services/semprec-api/src/queueRuntime.ts`).
6. Tests: `buildItipReply` output (folding of long lines, escaping of commas and newlines in the summary, each `PARTSTAT`); accepting enqueues one job and the job sends one message from the receiving mailbox's address with `ATTENDEE` equal to the delivered-to address; a failing transaction enqueues nothing; a transient transport failure is retried and a repeated run sends no second distinct job; a declined answer sends `DECLINED`; changing an accepted answer to `tentative` enqueues a second job that sends `TENTATIVE`; a job whose answer was superseded before it ran sends nothing; `acknowledged` sends nothing.

## Acceptance criteria

- When the user accepts an invitation, then after the commit one `METHOD:REPLY` message with `PARTSTAT=ACCEPTED` is sent to the organizer from the mailbox that received the invitation, and `ATTENDEE` is the address the invitation was delivered to.
- When the answering transaction fails, then no reply is enqueued or sent.
- When the transport fails transiently, then the job is retried and at most one reply is delivered per answer.
- When the user declines, then the reply carries `PARTSTAT=DECLINED`; when a notice is acknowledged, then nothing is sent.
- When the user changes an accepted answer to `tentative`, then a new reply with `PARTSTAT=TENTATIVE` is sent to the organizer; when the answer is changed again before the first reply job runs, only the latest answer is sent.
- When the organizer address is missing or the mailbox no longer exists, then the job ends without retry and the answer stays recorded.
