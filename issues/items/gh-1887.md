**Blocked by:** #1437, #1789, #1860
**Model tier:** medium

## Context

Model tier rationale: One read-side projection that batches a lookup onto an existing endpoint using existing store functions and fixtures, with no new write or authorization contract.

Semp chat replies carry a stored step summary (#1860); a step that asked for approval needs its current state when the thread is read, otherwise the card shows "waiting" forever and an older conversation cannot show what became of an old request. Requests are linked to tool calls by #1618; the conflict reason comes from #1437; clients learn that something changed from the invalidation of #1789 and refetch.

This issue makes the steps returned for a thread message include the live state of each step's approval request. It reads the request fresh on every read; the stored summary is never rewritten when a request is decided.

Decision: the live state is attached only for steps that carry an `approvalRequestId`; the list read is batched in a single query per message page, not one query per step.

## Task

Load `state-writes` (read-side only) and `testing`.

1. In the Semp thread messages read (the endpoint and store that return messages with their step summaries), collect the `approvalRequestId` of every step in the returned page, load those requests in one tenant-scoped query owned by the approval module, and attach to each such step `approval: { status, executionStatus, conflictReason }` where `conflictReason` comes from `approvalConflictReason` of #1437.
2. A request that no longer exists, or that belongs to another user than the caller, yields `approval: null` on the step, indistinguishable between the two cases.
3. The payload, argument values and execution result are never returned; only the three fields above.
4. Keep the stored step summary untouched; the live object is added at read time only.

## Acceptance criteria

- A step whose request was approved and executed returns `approval.status = "approved"` and `executionStatus = "succeeded"`.
- A step whose request is pending returns `executionStatus = "not_approved"`; after rejection it returns `status = "rejected"`.
- A conflicted request returns `conflictReason` with its key.
- A page with many approval steps performs one request lookup, not one per step.
- A request of another user or tenant yields `approval: null`, identical to a missing request.
- The response contains no payload, arguments or execution result.
