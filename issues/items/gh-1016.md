**Blocked by:** #984, #992

## Context

Graphile Worker runs jobs that share a `queue_name` one at a time, and jobs without one in parallel, up to the worker's concurrency. `QUEUE_CONCURRENCY_DEFAULT = 4` is at `backend/packages/queue/src/index.ts:313`. `enqueueJob` passes `options.queueName` straight to `graphile_worker.add_job` (`index.ts:193-235`).

Two kinds of work need a lane per tenant.

**Serialized work.**
- Every Inbox tick runs on the single global queue `semprec-tick` (`SEMPREC_TICK_QUEUE_NAME`, `backend/packages/data/src/inbox/inboxTickKeys.ts:3-4`). The lane closes the race of two ticks for one Inbox item both creating a Processing-proposal card.
- `createActionQueueAffinity()` maps the `semprec.tick` action to that name (`backend/packages/data/src/scheduler/actions.ts:34-51`).
- `triggerOnItemEventHeartbeats` applies the map when it enqueues a heartbeat fire job (`backend/packages/data/src/scheduler/schedulerStore.ts:303-327`, `queueName` at `:324`). Inbox ticks are `onItemEvent` heartbeats only (`backend/packages/data/src/seed/seedInboxPipeline.ts:245-257`), so this is the only place the name is used.
- With several tenants, one tenant's tick backlog would delay every other tenant's ticks.

**Bulk work.** These are enqueued with no queue name, so one tenant can occupy every worker slot:
- `enqueueRollupRecompute` (per-cell) and `enqueueRollupBackfill` (`backend/packages/data/src/rollup/recompute.ts:26-47`). The backfill enqueues one per-cell job per row of the database (`recompute.ts:155-183`).
- `enqueuePropertyTypeMigration` (`backend/packages/data/src/migrationJob/propertyTypeMigration.ts:105-116`).
- `enqueueTranscriptionJob` (`backend/packages/data/src/transcription/transcriptionJob.ts:49-56`), which covers minutes of audio work.

What earlier issues provide:
- The tenant scope in `@semprec/shared`: `runInTenant(tenantId, fn)`, `runAsSystem(reason, fn)`, and `currentTenantScope()`, which returns `{ kind: 'tenant', tenantId } | { kind: 'system', reason } | undefined`.
- Every producer above already runs inside its tenant:
  - choke-point writes run in the HTTP request's tenant;
  - queue jobs run in the tenant their envelope carries;
  - heartbeats are swept per tenant (#984);
  - the transcription worker runs in its job's tenant (#992).

Outside a tenant scope the lane falls back to today's naming. Jobs already queued when this deploys keep their queue name and drain. The only overlap is a `semprec-tick` tick that is running at deploy time racing a new-lane tick for the same Inbox item. A queued, not yet running, job under the same job key is replaced in place by the new enqueue. A rollback opens the same window in reverse. Both are accepted; no job migration.

## Task

Load `state-writes` (enqueues inside the write's transaction) and `adr-conventions` (a new cross-cutting queue convention).

1. **Lane helper.** Add `backend/packages/data/src/tenancy/tenantLane.ts`, exporting `tenantLane(lane: string): string | undefined`.
   - Inside a tenant scope it returns `` `${lane}:${tenantId}` ``.
   - In a system scope or with no scope it returns `undefined`.
   - Do not export it from `backend/packages/data/src/index.ts`; only this package uses it.
2. **Inbox ticks.** At `schedulerStore.ts:324`, the base name `queueAffinity.get(row.action_id)` becomes `tenantLane(base) ?? base` when it is defined, and stays `undefined` otherwise. Inbox ticks then land on `semprec-tick:<tenantId>`. `SEMPREC_TICK_QUEUE_NAME` keeps the value `semprec-tick` as the base lane name. Update its doc comment (`inboxTickKeys.ts:3`) and the `ActionQueueAffinity` / `createActionQueueAffinity` comments (`actions.ts:34-48`): the map holds base lane names, and enqueue appends the tenant.
3. **Bulk lanes.** Add `queueName: tenantLane(<LANE>)` to the four enqueues below. Each `<LANE>` is a module-private constant in its file; outside a tenant scope the queue name stays unset, as today.
   - `enqueueRollupRecompute`: `rollup-recompute`.
   - `enqueueRollupBackfill`: `rollup-backfill`. It is a separate lane so a running backfill does not hold back per-cell recomputes.
   - `enqueuePropertyTypeMigration`: `property-type-migration`.
   - `enqueueTranscriptionJob`: `transcription`.
4. **ADR.** Add `docs/adr/<YYYY-MM-DD>-per-tenant-queue-lanes.md`. It records:
   - serialized work and bulk or heavy work run on a `<lane>:<tenantId>` queue derived from the enqueuing scope, never from payload data;
   - the lanes this issue creates;
   - why outside a tenant scope the lane falls back to today's naming;
   - that a new task of either kind must pick a lane.
5. **Tests.**
   - `backend/packages/data/src/__tests__/tenantLane.unit.test.ts` (new; no Postgres).
   - `backend/packages/data/src/__tests__/tenantQueueLanes.test.ts` (new). Read `queue_name` the way `pendingTickJobs` does in `backend/packages/data/src/__tests__/inboxTick.test.ts:39-48` (`graphile_worker._private_jobs` left-joined to `_private_job_queues`).
   - One added case in `inboxTick.test.ts`.

## Scope

### In scope
- Per-tenant queue names for Inbox ticks, rollup recompute and backfill, property type migration and transcription; the helper; the ADR; the tests.

### Out of scope
- A per-tenant cap on concurrently running agent runs (#1047).
- Lanes for mail sync or any other task.
- Rewriting the queue name of jobs already queued at deploy time.
- Stamping or validating the job envelope's tenant (#982, #1061).

## Acceptance criteria

- **Helper.** `tenantLane("x")` returns `x:<T>` inside `runInTenant(T)`, and `undefined` inside `runAsSystem(...)` and with no scope. Two different tenant scopes yield two different names. (unit, `tenantLane.unit.test.ts`)
- **Tick lane.** Inside `runInTenant(<tenant zero>)`, creating an Inbox item through the choke point enqueues its tick job with `queue_name = 'semprec-tick:<tenant zero id>'`. With no scope, the existing `inboxTick.test.ts` cases still see `semprec-tick`. (integration, `inboxTick.test.ts`)
- **Bulk lanes.** Inside `runInTenant(<tenant zero>)`, the four enqueues land on these queue names:
  - `enqueueRollupRecompute`: `rollup-recompute:<id>`;
  - `enqueueRollupBackfill`: `rollup-backfill:<id>`;
  - `enqueuePropertyTypeMigration`: `property-type-migration:<id>`;
  - `enqueueTranscriptionJob`: `transcription:<id>`.

  Outside a tenant scope, each has a NULL `queue_name`. (integration, `tenantQueueLanes.test.ts`)
- **Backfill fan-out.** The per-cell jobs that `backfillRollup` enqueues while running in tenant zero's job scope land on `rollup-recompute:<id>`. (integration, `tenantQueueLanes.test.ts`)
- **Job keys.** The job keys of all five kinds are unchanged, so a repeat enqueue still collapses onto one job. (integration, `tenantQueueLanes.test.ts`)
- **ADR.** The ADR exists and is accepted. (review)
