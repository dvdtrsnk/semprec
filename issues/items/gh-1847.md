## Context

Model tier rationale: This projection decides what of a tool call is shown to the client, so a leaked argument or result exposes credentials or approval arguments, and it adds a new locale-dependent catalog and several response fields at once; at this uncertainty the higher tier is chosen.

#1821 serves `GET /api/agent-runs/:id/steps` with steps grouped and paged but carrying only identity, timing and state. This issue fills in what a client shows for each step, using the structured tool event fields from #1424 (operation, MCP registration, target ids), #1527 (approval request id, field changes) and #1374 (interrupted calls written as ordinary error results).

Each step additionally carries: `title`, `targetName`, `change {property, from, to}`, `summary`, and for approval steps `approvalRequestId` (the state of an approval step is #1862). The title is localized on the server by the session user's `users.locale` from a message catalog keyed by operation and target database. Example titles: `database.query` over the task database is "searching tasks", `item.patch` in the task database is "changing a task", `item.create` is "creating a task" (written in `cs` and `en`). Title, target name and change are separate fields so that a client can compose both a run-detail row (title plus "<target>: <property> -> <value>") and a chat row (title plus target, with the change as meta). This catalog is also the one the per-reply step summary uses (#1860), so it lives in a shared module, not in the handler.

Today a title cannot be derived for a call without an `operation`; rows stored before #1424 fall back to a generic title built from the model-facing `name`, with no target.

Decisions:

- Thinking blocks of the model are never returned (decided by the product owner: the user sees steps, tools and the result, which is enough for an audit). A model "plan" step is the assistant message that precedes tool calls; its text is not returned.
- What a step exposes (decided by the product owner): only the structure of the step: the tool (`operation` or the MCP server and tool), the state, the time, the link to an approval request and a localized result summary. `summary` is rendered from a catalog key and structured parameters (for example a result count), never from result text. Tool arguments, tool results, the model's text and raw error text are never returned, the same as for the `conflictReason` of approval requests. `change` is composed only from the structured `details.changes`, and a tool result redacted as sensitive (#1827) yields no `change`.
- Token usage is shown only in the per-reply summary (#1860); the run's steps show only real actions, so no "summary" model step with tokens is added (decided by the product owner).
- The `end` step summarises counts: number of tool steps and number of approval steps, so a client can show "3 tools, no approvals".

## Task

Add the step catalog module (new, in `backend/packages/data/src/agentRuns/`): a function `stepTitle(locale, operation | mcp, targetDatabaseModuleId)` and the `cs` / `en` message tables, keyed by canonical English keys. Add the catalog keys to `backend/packages/data/src/seed/i18n/cs.json` and `en.json` only if the existing seed i18n files are the project's catalog for server-produced strings; otherwise keep the tables in the new module. Unknown operation or database falls back to a generic localized title.
2. Extend the step projection from #1821: resolve the target database (from `targetDatabaseId`, or from the item for an item-only call) and `targetName` (the item's display name) in one batched lookup per page, not per step (use the same batched item read pattern as the approval queue). Compose `change {property, from, to}` from `details.changes` (first entry); `longText` property values are shortened. For an `approval` step (a tool step whose result has `details.approvalRequestId`), set `kind: "approval"` and `approvalRequestId`.
3. Compose `summary` from a catalog key per operation and structured result fields only, and never emit the arguments, the result content, the model's text or a raw error text of a step; read payloads only through the typed parser from #1424 (never an unchecked cast).
4. Read the user's locale from the session user (`users.locale`) in the handler and pass it to the projection.
5. Tests: titles and fields in `cs` and `en` for `database.query`, `item.patch`, `item.create` and an MCP tool (server name present); `change` composed from `details.changes`; a call that created an approval request has `kind: "approval"` and its request id and no argument key or value; no step of an MCP call contains its arguments or output (assert with a token in both); a failed call returns no raw error text; a plan step returns no model text; an interrupted call from #1374 projects as an error step; one batched lookup for a page with several steps.

## Scope

### In scope

- Localized title, target name, change and summary on each step, the exclusion of arguments, results, model text and raw errors, the `approval` step kind with its request id, and the `end` summary counts.

### Out of scope

- Paging, cursor and authorization of the route: #1821.
- The `waitingApproval` state and `approvalState` of an approval step: #1862.
- Persisting a per-reply summary on a Semp message: #1860 (it reuses this catalog).
- Returning tool arguments or results in any form, including a token usage step.
- Dedicated calendar and transcript steps; they have no titles until their tools exist.
- Nested steps of delegated sub-runs.

## Acceptance criteria

- When a step is `item.patch` on a task, then the step has `operation: "item.patch"`, the localized title for changing a task (per `users.locale`), `targetName` equal to the task's name and `change` with the property, previous and new value.
- When a step is an MCP tool call, then it has `mcp.serverName` and a title that names the tool.
- When a call created an approval request, then the step has `kind: "approval"` and `approvalRequestId` equal to the request id, and no argument of the call.
- No step contains a tool's arguments, a tool's result content, the model's text or a raw error text; an MCP call with a token in its input and output shows neither.
- When the run was interrupted by a restart, then the interrupted call is an `error` step.
- Thinking content never appears in any response field.
- A page with N steps performs a constant number of lookups for targets, not N.
