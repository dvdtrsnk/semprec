**Blocked by:** #142

## Context

Authentication flows (#139–#142) are complete, but no account exists yet and no supported path creates one. This issue delivers the server-side bootstrap: a `/setup` API flow that creates the only account exactly once, through the same internal account-creation function a future signup would use. #234 builds the web wizard over this API, and #143 then protects every existing route and lists this API among the documented public exceptions.

## Task

Implement the `/setup` API flow available only when `SELECT count(*) FROM users` is zero and the query token matches `SETUP_TOKEN`. Reuse one internal account-creation function that validates email/password, hashes with Argon2id, and inserts the user; do not create a public signup route. Serialize competing setup attempts so only one account can be created. Once any user exists, return 404 before token validation. Add the required `SETUP_TOKEN` configuration contract for the one-time bootstrap process and shared secret file. The setup API is unauthenticated by design (there is no user yet); #143 records it in the exceptions list.

## Scope

### In scope

- First-account setup API, the shared account-creation function, race safety, and the `SETUP_TOKEN` configuration contract.

### Out of scope

- The setup web wizard — delivered by #234.
- Retroactive route protection and the route-matrix test — delivered by #143.
- Provisioning the production secret file, delivered by the operations batch.
- Public signup, additional accounts, roles, TOTP, and login-screen localization.

## Acceptance criteria

- The `/setup` API works only with zero users and the correct token, permits exactly one winner under concurrency, then always returns 404.
- Setup and hypothetical future signup share the same internal account-creation logic without exposing `/signup`.
- The created account can log in through #140 immediately after setup.
