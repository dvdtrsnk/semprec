## Context

Model tier rationale: A new queue task in `semprec-transcribe` that writes into existing Inbox cards owned by another module's actions, racing with user edits and with the card's own confirm and revise paths, around a paid model call made outside any transaction; the lock ordering, the protection of user-edited fields and the idempotency of retries are the hard parts.

The Inbox card of a recording (a card for the recording's Event or for one speaker) can be corrected by the user in words: they give Semp an instruction such as "it was the call with the accountant". #1870 mounts `POST /api/proposals/:id/revise` and, for a transcript card with a message and no envelope, only records the instruction in the card's history. Nothing acts on it yet. Today `reviseProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) takes a ready envelope, no model is involved, and a transcript card is only ever created by the transcription worker (`transcriptEventMatch.ts`, `transcriptSpeakerSuggestion.ts`).

This issue makes the instruction act. When a message-only revise is recorded on a transcript card, the same transaction enqueues a new core task `transcriptCardRecompute`. The task runs in `semprec-transcribe`, reads the transcript, the card (its `context`, current proposal and edit state) and the instruction, asks the AI gateway for a new proposal outside any transaction, and writes the result back under the card's row lock. The write follows the card-state model of the Inbox work: the model's answer goes to `aiProposal` and bumps `aiVersion` (#1471), the history gets an entry of kind `threadRevision` (#1430), and the effective `proposal` is composed by the server so that values the user edited by hand (`userEditedKeys`, protected by #1921 and #1892) are not overwritten unless the instruction explicitly asks to change them. The queue runner for short model tasks is the one created with #1624 (it keeps the fast row-creation task from waiting behind a gateway call).

Decisions:

- The model may only choose among the candidates already on the card (`context.candidates` for an Event card, `context.alternatives` for a speaker card, plus the card's current target) or edit the fields of the current new-item proposal. An instruction that cannot be satisfied this way leaves the proposal unchanged and adds a history entry saying so.
- The role of a card never changes: an Event card stays an Event card and a speaker card stays a speaker card; a result that would switch the role is discarded like any invalid result.
- A key the user edited by hand is changed only when the model lists it in `explicitlyChangedKeys`, which it must do only when the instruction names that field; the key then stays in `userEditedKeys`.
- Locked cards (`confirmed`, `rejected`) are never recomputed; the task is a no-op for them.
- The content of the transcript and of the instruction is never logged.

Shared-file ordering: this issue also waits for #1939 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Scope

### In scope

- The `transcriptCardRecompute` task, its enqueueing from the message-only revise, the gateway operation and the guarded write of the result, with the ADR.

### Out of scope

- The revise route and the recording of the message: #1870.
- Protecting manual edits, the effective-proposal composition and the reset of overrides: #1892, #1912, #1921.
- Undoing a confirmed or rejected card: #1937, #1943.
- Recomputing cards of kind `inbox` (done by the Inbox tick and the agent tool) and the agent tool itself: #1906.
- Giving the model candidates beyond those on the card (free search over Events and People).

## Acceptance criteria

- When the user tells Semp "it is the accountant call" on a recording's Event card, the card's proposal becomes a link to that candidate Event and its history has a `threadRevision` entry.
- When the user hand-edited the start of a new meeting and then gives an instruction that does not mention the start, the start is unchanged; when the instruction names the start, it changes and stays marked as user-edited.
- When the instruction is given on a speaker card, the proposed person changes and the card stays a speaker card.
- When the job is retried after the write, there is exactly one `threadRevision` entry and no second gateway call.
- Neither application logs nor the history contain the transcript text; a confirmed or rejected card is never changed.
