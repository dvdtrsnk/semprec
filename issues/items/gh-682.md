## Context

`getOrCreateJournalItem` (`backend/packages/data/src/journal/journalStore.ts`, lines 47-69) creates the Journal item for a period through `createItemWithClient` with the deterministic idempotency key `journal:<databaseId>:<type>:<period>` (line 65). That key is permanent, but the item it reserves is not:

- After the period item is trashed and purged, `itemsStore.insertItem` (`backend/packages/data/src/chokePoint/itemsStore.ts`, lines 62-98) finds the `idempotency_keys` reservation, `getItemById` (line 92) returns `null`, and line 97 throws `ConflictError("Idempotency key reservation exists but its item is missing")` — on every later write for that period, forever. (Sibling issue C2 makes the purge delete the reservation from now on; reservations orphaned before C2 merges stay in production data, so this branch remains reachable.)
- Before any purge, a soft-deleted period item is returned as-is: `getItemById` (lines 27-34) has no `deleted_at` filter, so `createItemWithClient` hands the journal caller a trashed item and the caller writes into the trash.

This issue depends on C12 because both change the reused-key branch of `insertItem` (C12 moves it into `insertItemWithReplay` and makes it report `created: false`; a fresh item created here after releasing a stale reservation reports `created: true`, so its create side effects fire).

## Task

1. `itemsStore.insertItem` — after C12 the body lives in `insertItemWithReplay`; the line numbers below refer to today's `insertItem` — in the reused-key branch (after `reserved.item_id` is known), lock the reservation row — `SELECT item_id, database_id FROM idempotency_keys WHERE key = $1 FOR UPDATE` replaces the plain select at lines 70-73 — then load the item with `getItemById`. If the item is missing **or** `deletedAt !== null`, delete the reservation (`DELETE FROM idempotency_keys WHERE key = $1`, checked with `requireAffectedRows`), and fall through to the normal insert path below with a fresh reservation for `generatedId` (re-run the `INSERT ... ON CONFLICT (key) DO NOTHING RETURNING item_id`; it now succeeds because the row was deleted under the lock). The existing `ConflictError` at line 97 goes away; document in the function comment that a reservation whose item is gone or trashed is treated as free. The existing `reserved === undefined` branch (lines 77-84) stays and now also covers a second transaction that waited on the lock while the first one released and re-reserved the key — it fails with that `ConflictError` and the caller retries, as today. Keep the different-database `ConflictError` (lines 85-90) as is.
2. `findIdempotentReplay` (lines 118-130): return `null` when the reserved item is soft-deleted, so `assertDatabaseWritableForCreate` in `itemWrites.ts` does not treat a trashed item as a satisfied replay.
3. `getOrCreateJournalItem`: no signature change; its doc comment gains one sentence that a trashed or purged period item is replaced by a fresh one on the next write.
4. Tests, new file `backend/packages/data/src/__tests__/journalStore.test.ts` (integration, seeded ten databases like `tenDatabases.test.ts`): (a) create a day item, soft-delete it through the choke point, call `getOrCreateJournalItem` for the same day → a different, live item id is returned, the old row stays trashed, `idempotency_keys` for that key points at the new item; (b) create a day item, delete its `items` row and leave the reservation behind by hand (`DELETE FROM items ...` via the test pool, simulating a pre-C2 purge), call `getOrCreateJournalItem` → a new live item, no throw; (c) two concurrent `getOrCreateJournalItem` calls for a never-created day still converge on one item.

## Scope

### In scope
- The reservation release for a missing or trashed item, the replay lookup's `deletedAt` filter, and the journal tests.

### Out of scope
- Deleting reservations at purge time (C2) and suppressing create side effects on replay (C12).
- Any change to `getItemById`'s general semantics (other callers rely on it returning trashed rows).

## Acceptance criteria

- When the item reserved by an idempotency key has been purged (row absent, reservation present), the next `createItemWithClient` with that key creates a new item, points the reservation at it and does not throw.
- When the item reserved by an idempotency key is soft-deleted, the next `createItemWithClient` with that key creates a new live item and leaves the trashed one untouched; `findIdempotentReplay` returns `null` for that key.
- When two transactions race to create the same never-created period, exactly one item exists afterwards.
