## Context

Model tier rationale: One failure branch in the existing tick with retry semantics tied to the queue's final attempt, and the staleness check reused from the success path; the cases are few and testable with a stubbed gateway.

When the model call in the tick fails today, the error propagates, the heartbeat job is retried up to three times (`maxAttempts` 3) and then a heartbeat error is recorded; the Inbox item itself never shows anything, so the user sees an item that silently stays unprocessed. The gateway call signals one failure type, `AiGatewayFailedError`, with a `reason` of `timeout`, `http`, `budget_exceeded` or `invalid_response` (`backend/packages/shared/src/aiGatewayClient.ts`). A budget rejection is not worth retrying. The heartbeat fire task tells the action whether this is the last queue attempt through `ActionContext.isFinalAttempt` (`backend/packages/data/src/scheduler/actions.ts`).

#1434 builds the computation and the tick wiring; #1451 adds the `computeFailed` and `computing` options of the card `status`. This issue records the failure on the card. The Inbox list shows a failed card with the state "proposal failed" and a Retry action (#1807), the day's Inbox summary reads the status (#1489), and a recompute recovers from the failed state (#1955). Recording the failure on a card is what keeps a failed capture from silently disappearing.

Decision: a `budget_exceeded` failure is recorded immediately and does not throw. A `timeout`, `http` or `invalid_response` failure still throws (so the queue retries) except on the final attempt, where it is recorded and does not throw. Any other error type propagates as it does today.

Decision: the failed card is stored with `status: computeFailed`, a `history` entry `{ author: "ai", message: "Computing the proposal failed: <reason>.", at }` using only the reason code (never the provider's text), and `fingerprint: null`, so the next change of the item or an explicit recompute computes again instead of being skipped by the unchanged-fingerprint rule. An existing `proposal` stays stored.

Decision: when no card exists yet one is created (`kind: inbox`, the `sourceInbox` edge) in `computeFailed`, like `writeNeedsClarification` does. A locked card (`confirmed` or `rejected`) is never touched.

Decision: the write goes through the same staleness checks as a successful result: if the item changed or was deleted while the call was in flight, nothing is written, because a newer tick is already queued.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In `createSemprecTickAction` (`backend/packages/data/src/inbox/inboxTickAction.ts`) wrap the `computeProposal` call: catch `AiGatewayFailedError`; for `budget_exceeded`, or for any other reason when `context.isFinalAttempt` is true, run a new write transaction `writeComputeFailure` and return; otherwise rethrow.
2. Implement `writeComputeFailure` next to `writeTickResult`, reusing `lockUnlockedProposal`, the source-item re-checks and `findExistingProposal`: create or update the card as in the Decision, with `allowedSystemKeys` for `status`, `fingerprint`, `history` (and `kind` on create).
3. Keep the success path unchanged and make sure a later successful tick for the same item replaces `computeFailed` with `proposed` and a fresh fingerprint.
4. Tests with a stubbed computation: `budget_exceeded` creates a `computeFailed` card with the history entry and does not throw; `timeout` on attempt one and two throws and writes nothing, on the final attempt writes the card and does not throw; a failure for an item that changed meanwhile writes nothing; a failure never touches a `confirmed` or `rejected` card; after a failure the next successful tick makes the card `proposed`; the history message contains the reason code only.

## Acceptance criteria

- When the gateway reports `budget_exceeded`, then the item's card has status `computeFailed` with a history entry naming the reason, and the tick does not throw.
- When the gateway times out, then the tick throws and the job is retried; after the third attempt the card has status `computeFailed`.
- When the item was edited while the failed call was in flight, then no card is written.
- When a card is `confirmed` or `rejected`, then a failure never changes it.
