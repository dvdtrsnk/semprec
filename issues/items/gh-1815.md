**Blocked by:** #1713, #1810
**Model tier:** high

## Context

Model tier rationale: This adds an authorization contract for agent writes to money data on top of the new approval deferral mechanism, including replay of a create operation, so a mistake either leaks write access or loses an approved write.

Today any assistant run can write into any database where property ownership allows it: `ManifestDatabase.writable` is not enforced, and the generic operation gateway (`backend/packages/application/src/genericOperationGateway.ts`) holds an agent back only for the five destructive operations (ADR `docs/adr/2026-09-18-non-destructive-generic-operations-bypass-agent-approval.md`). Money data should not be changed by the assistant without a person agreeing. Two blockers provide the pieces: #1810 makes the data layer refuse an agent write to a database it has no grant for (403 `forbidden`), and #1713 lets the choke point defer a flagged agent write to an approval request (typed error `ApprovalRequiredForWrite` carrying a list of reasons, snapshot kinds `item_patch`, `relation_put`, `relation_set`, exactly-once replay). #1423 defines the closed set of risk classes (`unclassified`, `read`, `write`, `destructive`, `outbound`, `breaksLink`) with a CHECK on `approval_requests.risk_class`.

This issue joins them for Finance: with a grant, an assistant write into `transactions` or `financeCategories` is not executed but becomes an approval request with its own risk class, and runs once if a person approves.

Decisions:
- Variant chosen: approval (not Inbox proposals). Reason: the approval mechanism of #1713 is the planned way to gate non-destructive agent writes and keeps the assistant's write path unchanged.
- Default: reading Finance stays allowed without a grant; writing needs a grant (403 without it), and with a grant every write still needs approval.
- Covered writes: an agent `item.create` into `transactions` or `financeCategories`, and an agent `item.patch` of an item in them. Relation writes on finance items, and deletes (already approval-gated as destructive), are unchanged. Reason: keeps one mechanism and one reason; relation writes are not planned yet and can be added as another reason later.
- A new reason kind `financialDatabase` is added to the reason list of the deferral error, and a new risk class `financial` to the closed set. A snapshot kind `item_create` is added (the snapshot is the target database id and a hash of the proposed properties); replay creates the item exactly once. The `item_patch` kind from #1713 is reused.
- Changing a taken-over value is reported as ending the link by #1758; this issue does not change that.


Shared-file ordering: this issue also waits for #1758, #1768, #1791 because both edit the same files listed in Touches.

## Acceptance criteria

- When an assistant run without a grant creates a transaction, then the response is 403 `forbidden`; reading transactions still works.
- When a run with a grant creates a transaction, then an approval request with risk class `financial` exists and no item was created.
- When that request is approved, then exactly one transaction is created; approving again creates no second one; rejecting creates none.
- When an assistant run with a grant patches a transaction, then the patch becomes an approval request and the item is unchanged until approved.
- When a user writes a transaction, or an assistant writes to another database, then the behavior is as before.
