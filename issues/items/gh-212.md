**Blocked by:** #211, #21, #115

## Context

Issue #211 normalized the relation edge contract (`RelationEdge`, `CreateRelationInput`, `UpdateRelationInput`, `callerItemId`, idempotent operations, endpoint validation). The completed foundation validates ownership for JSON property patches but does not apply the same rule to relation writes: a public caller can add or remove an edge through a system-owned relation property, `CreateRelationPropertyInput` cannot express per-side ownership, and internal system writers (seeds, mail, tasks) go through the same unprotected functions. Relation-property creation also configures the property after creation, which fails when the new property is locked.

This second part adds relation-definition ownership and the protected system entry points, and migrates every internal caller onto them. #82 builds on it by enforcing cardinality under concurrency and repairing canonical relation-property config.

## Task

- Extend `CreateRelationPropertyInput` to `{ sourceDatabaseId, key, name, targetDatabaseId, cardinality, owner, ownerProcess, locked, inverse?: { key, name, owner, ownerProcess, locked } }`, where each `owner` is `'user' | 'system'`, `ownerProcess` is required and non-empty exactly when that side's owner is `system` and must be absent otherwise, and each `locked` is an explicit boolean. The source fields describe `property_id_a`; `inverse` describes `property_id_b`. Persist each side's values independently. Public callers may create only `owner: 'user'` definitions; protected system creation additionally requires the context rule below for every system-owned side.
- On create, update-metadata, and delete of an edge, the exact property named by `relationPropertyId` authorizes the operation. Paired properties may have different owners: only the property named by the caller governs that call. Reject public user/agent writes when it is `owner: system`, using `owner_violation`.
- Add protected `SystemRelationWriteContext { ownerProcess: string }` entry points in the data package, unavailable on the public facade: `createRelationWithClient(client, input: CreateRelationInput, context): Promise<RelationEdge>`, `updateRelationWithClient(client, input: UpdateRelationInput, context): Promise<RelationEdge>`, and `deleteRelationWithClient(client, input: Omit<CreateRelationInput, 'metadata'>, context): Promise<void>` (the input/output shapes are the ones defined in #211). Public-facade methods use these same input/output shapes without accepting a context. The protected relation-definition creator (`createRelationPropertyWithClient`) takes the extended `CreateRelationPropertyInput` plus the same context. A system create/write succeeds only when every system-owned property it acts through has `owner_process` exactly equal to `context.ownerProcess`; otherwise return `owner_violation`.
- Migrate every existing internal relation-definition and relation-edge call site to these protected functions and pass the process id registered for that module/action: the seeds (`seedTenDatabases`, `seedEmailModule`, `seedLibraryModule`), the mail writers (`ingest`, `draft`, `send`, `attachments`, `folderDiscovery`, `imapReconcile`, `gmailReconcile`, `graphReconcile`, `personLinkingActions`), `tasks/advanceTaskRecurrence`, and any journal/library writer that creates relation definitions or edges. No internal caller may fall back to the public facade.
- Create relation definitions and both property configs before applying requested locks, so `locked: true` succeeds atomically without a temporary externally visible unlocked schema.
- Add real-Postgres integration tests for public ownership rejection, authorized internal writes (matching and mismatching `ownerProcess`, mixed-owner paired definitions), and locked one-way and paired relation-property creation.

## Scope

### In scope

- Per-side ownership of relation definitions and the protected `SystemRelationWriteContext` entry points.
- Migration of every internal relation writer to its registered process identity.
- Atomic locked relation-property creation ordering.

### Out of scope

- Edge type normalization, idempotent create/update/delete contracts, and endpoint validation; #211 delivered these.
- Cardinality enforcement under concurrency, additive indexes/constraints, canonical config persistence for one-directional properties, one-directional `targetDatabaseId` validation, and the fail-loud config repair migration; #82 delivers these.
- REST routing; issue #37 projects this corrected choke-point behavior over HTTP.
- Module registry and PostgreSQL runtime roles; issues #29 and #40 own those boundaries.
- Domain-specific relation rules.

## Acceptance criteria

- A public caller cannot add, change, or remove an edge through an `owner: system` relation property; the rejection is `owner_violation`.
- Both sides of a paired definition persist their independently requested owner, owner process, and locked state, and every existing internal system writer supplies its registered process identity through the protected entry points.
- A system write whose `context.ownerProcess` differs from the `owner_process` of any system-owned property it acts through returns `owner_violation`.
- Public callers cannot create `owner: 'system'` relation definitions, and `ownerProcess` is accepted exactly when that side's owner is `system`.
- Creating a locked one-way or paired relation property succeeds atomically, with no externally visible unlocked intermediate state.
- The new integration tests reproduce the former gaps and pass against real PostgreSQL.
