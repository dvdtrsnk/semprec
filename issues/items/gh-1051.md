## Context

Model tier rationale: The exact catalog query, error type and four call sites are given verbatim.

Tenant isolation is enforced by Postgres row-level security on every tenant table (#973: a RESTRICTIVE `tenant_isolation` policy plus a PERMISSIVE `tenant_rows` policy, RLS `ENABLE`d but deliberately not `FORCE`d). Postgres skips RLS entirely for a superuser, for a role with `BYPASSRLS`, and for the table owner — and it treats any member of the owning role as the owner. Every table is owned by the migrating role, which is the Postgres superuser that `deploy.sh` connects as through `SEMPREC_MIGRATE_DATABASE_URL` (`deploy/shared/.env.example:76-81`, moved to `deploy/shared/env/migrate.env.example` by #996). So one wrong connection string — a service pointed at the migrate URL — silently turns isolation off for that whole process. The tenant-isolation ADR added by #968 (`docs/adr/<date>-tenant-isolation-through-row-level-security.md`, decision D5) chose "no `FORCE`; every service asserts its role at startup" instead.

Today each long-running service creates its pool and starts querying with no such check:

- `backend/services/semprec-api/src/serve.ts:94` `createPool`, then `wireRealtimeHooks` (`:95`), `startProcessHeartbeat` (`:100`), the dispatcher and queue runtime;
- `backend/services/semprec-agents/src/serve.ts:23` `createPool`, then `startProcessHeartbeat` (`:27`) and `repairInterruptedRuns` (`:39`);
- `backend/services/semprec-transcribe/src/serve.ts:11` `createPool`, then `wireRealtimeHooks` (`:14`) and `startProcessHeartbeat` (`:15`);
- `backend/services/semprec-ai-gateway/src/serve.ts:13` `createPool` (after `resolveStartupConfig`, `:11`), then `startProcessHeartbeat` (`:17`).

The two runtime roles are `semprec_data` and `semprec_side` (`backend/packages/data/src/db/migrations/0040_least_privilege_roles.sql:33-47`; `semprec_data` is a member of `semprec_side`). #997 added `semprec_router`, a `NOLOGIN BYPASSRLS` role that owns the router functions — a runtime role must never be a member of it. #1085 later checks the same role facts from the catalog at every deploy; this issue is the per-process half.

## Task

Load `error-handling` (a startup failure that must propagate, an error message that names the role but never the connection string) and `io-hardening` (a pooled connection used at startup).

1. Create `backend/packages/data/src/db/runtimeRoleAssertion.ts` exporting:
   - `type RuntimeRoleViolation = "superuser" | "bypassrls" | "memberOfPrivilegedRole" | "ownsPublicRelation"`;
   - `class RuntimeRoleAssertionError extends Error` with `readonly role: string` and `readonly violations: readonly RuntimeRoleViolation[]`;
   - `assertRuntimeRole(pool: Pool): Promise<void>`, which runs exactly one catalog query inside `runAsSystem("runtime-role-assertion", …)` (the scope API from #978, so the check neither logs `tenant_scope_missing` nor throws `TenantScopeMissingError` in strict mode):
     ```sql
     SELECT r.rolname, r.rolsuper, r.rolbypassrls,
       EXISTS (SELECT 1 FROM pg_roles m
               WHERE m.oid <> r.oid AND (m.rolsuper OR m.rolbypassrls)
                 AND pg_has_role(r.oid, m.oid, 'MEMBER')) AS member_of_privileged_role,
       EXISTS (SELECT 1 FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
               WHERE n.nspname = 'public' AND pg_has_role(r.oid, c.relowner, 'MEMBER')) AS owns_public_relation
     FROM pg_roles r WHERE r.rolname = current_user
     ```
     Read it with a typed row. Every true flag adds its violation; when there is at least one, throw `RuntimeRoleAssertionError` with the message `Refusing to start: database role "<rolname>" violates <violations joined by ", ">; runtime services must connect as semprec_data or semprec_side`. The message never contains the connection string or a password. A missing row (impossible for `current_user`) throws a plain `Error` naming the query. No `catch` anywhere: the error propagates.
2. Export `assertRuntimeRole` and `RuntimeRoleAssertionError` on one new line directly after the `./db/pool.js` export at `backend/packages/data/src/index.ts:3` — that line only — and add both names, in sorted position, to `EXPECTED_RUNTIME_EXPORTS` in `backend/packages/data/src/__tests__/publicSurface.test.ts:44`, which freezes the package's runtime exports.
3. In each of the four `serve.ts` files, add `await assertRuntimeRole(pool);` immediately after its `createPool(...)` line and before every other use of the pool listed in Context. `installFatalHandlers` (already installed at the top of each file) turns the rejection into a fatal log and a non-zero exit.
4. Write the tests listed under Acceptance criteria. The module docstring cites the tenant-isolation ADR's decision that runtime roles are neither superuser nor `BYPASSRLS` and own no table; no new ADR is needed.

### Out of scope

## Acceptance criteria

- Integration (`runtimeRoleAssertion.test.ts`): with the superuser test pool (`getTestPool()`), `assertRuntimeRole` rejects with `RuntimeRoleAssertionError` whose `violations` include `superuser` and whose message names the role and contains neither the password nor the connection string.
- Integration: with pools from `createRuntimeRolePool(adminPool, "semprec_data")` and `createRuntimeRolePool(adminPool, "semprec_side")` (`@semprec/data/testSupport`, #975), it resolves.
- Integration: a test-created `LOGIN NOSUPERUSER BYPASSRLS` role yields exactly `bypassrls`; a test-created login role granted membership in a test-created `NOLOGIN BYPASSRLS` role yields `memberOfPrivilegedRole`; a test-created login role that owns a table in `public`, and another that is only a member of that owner, each yield `ownsPublicRelation`. Every test role and table is dropped after the test.
- Integration: with `process.env.SEMPREC_TENANT_SCOPE = "strict"` (read on every call by `enforceTenantScope`, #978; restored afterwards) and no surrounding scope, the call against a runtime-role pool resolves; with `warn` it logs no `tenant_scope_missing`.
- Integration, one per service: importing that service's `serve.js` with its database URL variable set to the superuser `TEST_DATABASE_URL` (plus whatever other variables its startup requires, as `serveStartupConfig.test.ts` already does for semprec-api) rejects with `RuntimeRoleAssertionError`; the database, reset before the import, then holds no `process_heartbeats` row for that service's process name (nothing touched the pool before the check).
