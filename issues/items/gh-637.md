## Context

A non-UUID path id reaches Postgres and surfaces as a 500. The adapter's route table captures every `:name` segment as `([^/]+)` (`backend/services/semprec-api/src/adapter/routeTable.ts`, `compilePath`, line 39), `requireStringParam` in `backend/services/semprec-api/src/adapter/requestValidation.ts` (lines 11-17) checks only non-emptiness, and the bespoke handlers use the same `([^/]+)` capture (`REVOKE_SESSION_PATH` in `authHandler.ts` line 116, `AGENT_RUN_PATH` in `agentRunHandler.ts` line 35, `APPROVAL_REQUEST_PATH` in `approvalRequestsHandler.ts` line 41, `VISIT_NOTIFICATION_PATH` in `notificationsHandler.ts` line 20, `BLOB_PATH` in `blobsHandler.ts` line 24, `MCP_GRANTS_PATH` / `MCP_TOOL_REGISTRATION_PATH` in `mcpAgentPageHandler.ts` lines 41-42) and `requireParam` in `backend/packages/data/src/push/pushRouteHandlers.ts` (lines 18-24). The value is bound to a `uuid` column, Postgres raises `22P02 invalid input syntax for type uuid`, and the handler's generic branch answers 500.

Verified on `develop` HEAD with an authenticated probe: `GET /api/items/foo`, `GET /api/databases/foo`, `GET /api/views/foo`, `GET /api/properties/foo`, `PUT /api/views/foo/items/foo`, `PUT /api/items/foo/relations/exampleKey/foo`, `POST /api/auth/sessions/foo/revoke`, `GET /api/blobs/foo`, `GET /api/agent-runs/foo`, `PATCH /api/approval-requests/foo`, `POST /api/notifications/foo/visit`, `POST /api/push-subscriptions/foo/revoke` and `PATCH /api/mcp-tool-registrations/foo` (with a valid body) all returned 500. The two transcription custom routes already answer `400 validation_failed` with `details: { field: "id" }` (`backend/packages/data/src/transcription/transcriptionRouteHandlers.ts` lines 118 and 191, via `z.string().uuid()`), which is the precedent this issue generalises.

Depends on #635 (edits the same `authHandler.ts`) and #629 (edits the same `approvalRequestsHandler.ts`); those must merge first so the handler edits do not collide. Sibling B8 later edits every bespoke handler's `catch` block and is sequenced after this issue.

## Task

- Response contract (decided): a syntactically invalid id is `400 validation_failed` with `details: { field: "<param name>" }` and message `'<param name>' must be a UUID string` — the same response the transcription routes already give and the shape `backend/review-rules/rules.md` prescribes for a body value Postgres would reject. Not 404: a malformed id is a client-shape error, and the adapter's `not_found` keeps meaning "well-formed id, no such row".
- In `requestValidation.ts` add and export:
  - `assertUuid(value: string, name: string): string` — returns `value` when it matches `/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i`, else throws `new ValidationError(\`'${name}' must be a UUID string\`, { field: name })`.
  - `requireUuidParam(params, name): string` — `assertUuid(requireStringParam(params, name), name)`.
- Adapter route families — replace `requireStringParam` with `requireUuidParam` for every id-valued parameter: `id` in `databasesHandler.ts` (6 sites), `propertiesHandler.ts` (3), `viewsHandler.ts` (`id` and `itemId`, every site), `itemsHandler.ts` (`id` and `targetItemId`; **not** `propertyKey`, which is a property key, not an id).
- Bespoke handlers — right after each regex match, pass the captured group through `assertUuid(...)` before it is used: `authHandler.ts` revoke branch (`sessionId`, name `"id"`), `agentRunHandler.ts` (`agentRunId`, `"id"`), `approvalRequestsHandler.ts` (`approvalRequestId`, `"id"`), `notificationsHandler.ts` (`notificationId`, `"id"`), `blobsHandler.ts` (`blobId`, `"id"`), `mcpAgentPageHandler.ts` (`projectItemId` as `"id"`, and `mcpToolRegistrationId` as `"mcpToolRegistrationId"` in both routes, only when group 2 is present for the grants route). Each of these handlers already answers a `ValidationError` from its `catch` block at status 400, in its own top-level shape; keep that shape.
- `backend/packages/data/src/push/pushRouteHandlers.ts`, `createRevokePushSubscriptionRouteHandler`: validate `ctx.params.id` with a module-level `z.string().uuid()` schema exactly as `transcriptionRouteHandlers.ts` does (`zod` is already a dependency of `@semprec/data`), throwing `new ValidationError("'id' must be a UUID string", { field: "id" })`. The data package cannot import the API adapter, so this one site does not use `assertUuid`.
- Do not change the route regexes to a UUID pattern: a regex miss falls through to the wrong route or a bare 404, hiding the field name; the validators above produce the documented 400.
- Tests:
  - `backend/services/semprec-api/src/adapter/__tests__/requestValidation.unit.test.ts` (unit tier): `assertUuid` accepts a lowercase and an uppercase UUID, rejects `"foo"`, a UUID with a trailing character, and an empty string, each with `details.field` equal to the name.
  - One integration case per route family, each asserting status 400, `code`/`error.code` `validation_failed` and `field: "id"` (or the parameter's name) for the literal id `foo`: `itemsHandler.test.ts` (`GET /api/items/foo` and `PUT /api/items/<valid>/relations/exampleKey/foo` → `field: "targetItemId"`), `databasesHandler.test.ts`, `propertiesHandler.test.ts`, `viewsHandler.test.ts` (`PUT /api/views/<valid>/items/foo` → `field: "itemId"`), `authHandler.test.ts` inside `describe("POST /api/auth/sessions/:id/revoke")`, `agentRunHandler.test.ts`, `approvalRequestsHandler.test.ts`, `filesAndBlobsHandler.test.ts` inside `describe("GET /api/blobs/:id")`, `mcpAgentPageHandler.test.ts`, `push/__tests__/pushRouteHandlers.test.ts`, and a new `backend/services/semprec-api/src/__tests__/notificationsHandler.test.ts` (there is none today; model its server setup on `agentRunHandler.test.ts`) with the `POST /api/notifications/foo/visit` case.

## Scope

### In scope

- UUID validation of every id-valued path parameter listed above, at the adapter and in the bespoke and push custom-route handlers, with the 400 contract stated.

### Out of scope

- The bespoke handlers' `catch`-block error bodies — sibling issue B8 of this batch.
- The blob download's streaming code — sibling issue B12 (it edits a different region of `blobsHandler.ts`).
- `POST /mcp` — its JSON-RPC params are validated by the operation schemas; sibling B9 covers its authentication.
- The transcription and proposal custom routes (already validate or already 404).
- Body-level id fields (`projectItemId`, `databaseId`, ...) — those are validated by their zod schemas or are a separate concern.

## Acceptance criteria

- When any listed route is called by an authenticated client with the path id `foo`, the response is 400 with code `validation_failed` and `details.field` naming the parameter; no `22P02` error is logged.
- When the same route is called with a syntactically valid but unknown UUID, the response is unchanged from today (404 for the read/decide routes, `revoked: false` for the revoke routes).
- `assertUuid` accepts both letter cases and rejects any string that is not exactly one RFC 4122-shaped UUID.
- Every existing case in the touched test files still passes unchanged.
