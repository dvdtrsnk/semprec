## Context

Model tier rationale: Changes the connection ownership of the IMAP move phase, whose steps have exactly-once and uncertain-outcome rules, without changing any step.

End-to-end test of the dev server against a real Purelymail account (F25 follow-up). `drainImapMoves` (`mail/mailMessageMoveSync.ts`) opens a new IMAP connection (TLS, LOGIN, LOGOUT) for every pending move of a pass and closes it after that move, so archiving or trashing N threads costs N connection setups before the pass's own reconcile connection; at Purelymail's ~0.5 s connect and login each, ten archived threads add about 5 s to the pass that writes them back.

Reproduced with the fake IMAP account: three archived INBOX threads, one pass, four connections (three for the moves, one for the reconcile).

Decisions:

- The move phase opens one connection for its first move and runs every following move over it; it closes it after the last move, as before on every way out.
- A move whose provider outcome is unknown (a command that threw or answered without a usable result, or a preparation that returned no result, which `ImapFlowMailClient` reports for a failed or timed-out command) closes the connection at once; the next move opens a new one. A clean refusal (UIDVALIDITY changed, message not found, unsupported capability, no COPYUID) keeps it.
- A move failure that ends the phase still closes the connection; a close failure never replaces that failure. A close failure at the end of an otherwise successful phase fails it with the existing fixed `IMAP move provider cleanup failed unexpectedly`.
- Reusing the reconcile's connection for the move phase was rejected here: a move-used `ImapFlowMailClient` reports cleanup failure from `close()`, which the reconcile treats as never rejecting.

## Task

Load `io-hardening`, `error-handling`, `testing`.

1. `mail/mailMessageMoveSync.ts`: `drainImapMoves` reuses one connection across its moves as decided.
2. Tests in `__tests__/imapMoveWritebackConnection.test.ts` through the archive route and the production sync job with the fake IMAP account.
3. `docs/architecture/domain-mail-and-inbox.md`, Provider moves.

## Scope

### In scope

- Connection reuse inside one IMAP move phase.

### Out of scope

- Gmail and Graph move phases.
- Sharing one connection between the move phase and the reconcile of the first round.
- Any request against a real server.

## Acceptance criteria

- Three archived threads are moved by one pass over one move-phase connection plus the reconcile's: two connections opened and two closed (four before).
- A move whose MOVE command fails stays uncertain and is not repeated, and the next move runs over a newly opened connection; every opened connection is closed.
- The existing move sync, single-flight and mail sync tests stay green.
