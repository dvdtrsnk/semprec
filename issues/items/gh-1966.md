**Model tier:** high

## Context

Model tier rationale: Expanding RRULE with exceptions and overrides across time zones and daylight-saving changes inside the shared timeline is intricate, and a mistake shows wrong events to every reader.

Many subscribed feeds contain repeating events (weekly meetings, yearly anniversaries). #2004 imports each event once and skips overrides; this issue makes repeating subscribed events appear on the right days. The recurrence model for Tasks and Events is the one recorded in the recurrence ADR (#1365): occurrences are virtual, computed when the timeline is read, and an exception is materialized only when needed; #1877 expands Events' own rules in the timeline and this issue feeds subscribed events into the same expansion. Subscribed events are read-only (all properties owner `system`, process `calendar`), so nothing is ever materialized for them: exceptions and overrides are data on the stored rows.

Decisions:
- Three further `subscribedEvents` properties, all `owner: 'system'`, `ownerProcess: 'calendar'`: `recurrenceRule` (text, the feed's `RRULE` value verbatim), `exceptionDates` (text, a JSON array of the excluded occurrences' original starts as tenant wall-clock ISO strings, from `EXDATE`), and `recurrenceId` (text, nullable, the overridden occurrence's original start as a tenant wall-clock ISO string, set only on override rows).
- An override (`RECURRENCE-ID`) is stored as its own row with the same `uid` as its master, `recurrenceId` set; the upsert key becomes `(calendar, uid, recurrenceId)`. On expansion, an occurrence whose original start equals an override's `recurrenceId` is replaced by the override.
- Supported `RRULE` parts: `FREQ` (DAILY, WEEKLY, MONTHLY, YEARLY), `INTERVAL`, `COUNT`, `UNTIL`, `BYDAY`, `BYMONTHDAY`, `BYMONTH`. A rule using any other part is not expanded: the event is shown once at its own start, the import continues, and the unsupported rule is counted in a log line without feed content.
- Occurrences are computed in the event's original time zone and then converted to the tenant wall-clock model, so a 09:00 New York series keeps its local meaning across daylight-saving changes.
- Expansion is limited to the timeline's requested range; an unbounded series produces no more rows than the range needs.

Shared-file ordering: this issue also waits for #1964 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `io-hardening`, `canonical-keys` and `testing`.

1. Add the three properties to the `subscribedEvents` seed and extend the cutover step of #1962 (or add a second idempotent step registered in `runTenantCutoverMigrations`) so existing tenants get them; add i18n keys in `seed/i18n/cs.json` and `en.json`; bump the calendar manifest version.
2. Extend the importer of #2004 (`backend/packages/data/src/calendar/subscribedEventsImport.ts`) to store `recurrenceRule` and `exceptionDates` on masters and to import override components as separate rows, with the new upsert key and the same unchanged/disappeared handling.
3. Register subscribed events (the read-only timeline source of #2005) with the occurrence expansion of #1877 in the timeline implementation of #1717 (through the extension point that expansion defines), including exception filtering and override substitution, and the range limit. Entries stay `readOnly: true`.
4. Tests: a weekly series appears on each week in the requested range and not outside it; an `EXDATE` day is absent; an override changes one day's time and title; a `COUNT=3` rule stops after three; a series that crosses a daylight-saving change keeps its local hour; an unsupported rule yields a single occurrence and the import succeeds; re-importing is a no-op.

## Scope

### In scope

- Storing recurrence data for subscribed events and expanding it in the timeline with exceptions and overrides.

### Out of scope

- The `subscribedEvents` database: #1962. Importing events: #2004. The read-only timeline source: #2005.
- Recurrence of the user's own Events: #1817, #1877.
- Unsupported `RRULE` parts (for example `BYSETPOS`) and `RDATE`.
- Materializing or editing occurrences of a subscribed event.

## Acceptance criteria

- A weekly subscribed event appears once per week within the requested timeline range and nowhere outside it.
- An occurrence listed in `EXDATE` does not appear; an overridden occurrence appears with the override's time and title.
- A `COUNT=3` series yields exactly three occurrences.
- A series that crosses a daylight-saving change keeps the same local start time.
- A feed with an unsupported rule still imports and shows the event once.
- Re-importing an unchanged feed writes nothing.
- The full backend `pnpm run verify` passes.
