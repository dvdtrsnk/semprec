## Context

Model tier rationale: One additive response include across three generic read operations plus a post-commit invalidation, on existing fixtures, but it touches shared generic operation schemas and realtime so the compatibility rules must be checked.

After #1708, `item_automation` rows carry `status` (`pending | done | notFound | error | locked`), `attempts`, `last_attempt_at`, `error_code` and `source`. No API returns them: the client cannot tell "still searching for the cover" from "not found" and cannot show a retry hint. The time of the next attempt is held by the retry heartbeat in `project_heartbeats.next_fire_at`. Another gap: the realtime invalidation of an item is published only when the job wrote a property (`updateItemWithClient` is called only with a non-empty patch), so a run that finds nothing leaves the tile stuck on "searching".

Decision: the state is exposed through an additive `include=automation` on `item.get`, `database.query` and `view.query` (generic operations), for any database whose rows have `item_automation` entries, not as a library-only field in the generic envelope.
Decision: the response shape is `automation { status: pending|found|notFound|error|locked, attempts, lastAttemptAt, nextAttemptAt, source, errorCode }`; the stored `done` maps to `found`. The `locked` value is reported as stored; no endpoint to lock or unlock is added here.
Decision: `nextAttemptAt` is the `next_fire_at` of the database's retry-sweep heartbeat, and is null for `found` and `locked`.

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. Add `include=automation` to the item and collection query schemas in `backend/packages/shared/src/genericOperations/schemas.ts` (`item.get`, `database.query`, `view.query`), additively and optional (the `include` parameter does not exist in these schemas today; if the relations include of #1518 has introduced it by then, extend its enum, otherwise add the parameter here as an optional list of strings), and to the capability description the same way other includes are declared. Implement it in the application layer by a batched read of `item_automation` for the returned item ids (one query for a page, no per-row query) joined with the retry heartbeat's `next_fire_at` per database.
2. Items without a row get no `automation` field (or `null`), not an error.
3. After each library job run finishes (found, notFound or error), publish the item's realtime invalidation after commit with `runAfterCommit`, even when no property was written (see how `notifyInvalidation` is used in `libraryMetadataJob.ts` and `realtimeHook.ts`).
4. Tests: a book added by name only returns `automation.status: "pending"`; after a found run `found` and a client invalidation is observed even though only the status changed; a not-found title returns `notFound` with `nextAttemptAt` equal to the retry heartbeat's `next_fire_at`; a 503 fixture returns `error` with `errorCode: "sourceUnavailable"` and `attempts` increased; a request without the include is byte-identical to today; a database without automation rows is unaffected.

## Scope

### In scope

- `include=automation` on the three generic reads, `nextAttemptAt`, and the invalidation after every run.

### Out of scope

- Recording `notFound`, codes and sources and retrying them: #1708.
- Cover override, removal and re-search by the user: #1793.
- A toggle to lock or unlock an item's automation: not in v1 (the whole-item lock is dropped from the design; undo and the trash provide reversibility).

## Acceptance criteria

- When a book was added by title only, then `item.get` with `include=automation` returns `status: "pending"`.
- When the job finishes without writing any property, then the client receives an invalidation for the item.
- When a title was not found, then the response has `status: "notFound"` and `nextAttemptAt` equal to the retry heartbeat's next fire time (04:00 in the tenant's time zone).
- When a source was unavailable, then `status: "error"`, `errorCode: "sourceUnavailable"`, and `attempts` is increased; the response contains no exception text.
- When `include=automation` is not requested, then responses are unchanged.
- When a view or database query returns many items, then the state is loaded with one batched read.
