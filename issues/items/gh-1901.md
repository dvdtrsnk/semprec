## Context

Model tier rationale: One known mechanism (a system database seeded with owner-system properties plus a per-tenant cutover) across seed, manifest, cutover and i18n seams with existing seed fixtures, but it fixes a persisted schema and ownership contract that four later issues write to.

Calendar invitations do not exist in the backend today. The `invites` table (`0077_invites.sql`) and the account-invitation flow in `backend/packages/data/src/tenancy/invites.ts` are invitations to join Semprec as a user; they are unrelated and must not be reused or renamed.

This issue gives the calendar module a place to store an incoming meeting invitation until the user answers it. It adds one system database, `invitations`, owned by the calendar module (the module manifest, `calendarModuleManifest.ts`, is registered by an earlier issue; the system Calendars database comes from #1600). It creates no rows and no behavior: #1929 fills it from incoming mail, #1944 answers an invitation, #1953 sends the reply, and #1954 notifies the user.

Single-writer ownership (`docs/adr/2026-09-10-single-writer-ownership-model.md`): every property of this database is `owner: 'system'` with `ownerProcess` set to the calendar module id, so a generic `PATCH` of any property (for example `status`) is rejected with 403 `forbidden` by `assertWritableProperties` in `backend/packages/data/src/chokePoint/itemWrites.ts`. Mail ingest never writes to this database; only the calendar module's own code paths do. The calendar module id has to be a member of `KNOWN_OWNER_PROCESS_IDS` in `backend/packages/data/src/manifest/knownActionIds.ts` (added when the calendar module was registered), otherwise `core.driftCheck` reports the properties as orphans.

Decision: the representation of time is an instant plus the sender's zone, because an invitation is an external boundary (an Event itself is stored as wall-clock values in the tenant time zone, converted on acceptance by #1944). `startsAt` and `endsAt` are ISO-8601 UTC instants; `timeZone` keeps the IANA name from the invitation. For an all-day invitation (`allDay` true) `startsAt` is the first day and `endsAt` the last day (inclusive), both at 00:00 UTC, and `timeZone` is unused.

Decision: the suggested calendar of an invitation is always the default calendar in this version; a smarter suggestion is not built.

Decision: the database is created for new tenants by the seed and for populated tenants by a cutover, the same way #1600 does for the Calendars database, because `seedSystem` finishes with `already-seeded` for an existing tenant.

Shared-file ordering: this issue also waits for #2034 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys`, `db-migrations` and `testing`.

1. Add `backend/packages/data/src/seed/invitationsKeys.ts` exporting `INVITATIONS_MODULE_ID = "invitations"` (the `databases.owner_module_id` and key, the same convention as `seed/emailModuleKeys.ts`).
2. Add `backend/packages/data/src/seed/seedInvitationsDatabase.ts` exporting `seedInvitationsDatabaseInTransaction(client, ...)`. It creates the system `invitations` database, owned by the same system project item as the Calendars database, with these properties (canonical English camelCase keys), all `owner: 'system'` and `ownerProcess` = the calendar module id:
   - `title` (title)
   - `startsAt`, `endsAt` (date, `includeTime: true`; `endsAt` may be empty)
   - `timeZone` (text), `allDay` (checkbox)
   - `place` (text), `organizerName` (text), `organizerEmail` (text)
   - `status` (select: `pending`, `accepted`, `tentative`, `declined`, `acknowledged`, `cancelled`; `cancelled` means the organizer cancelled the meeting)
   - `respondedAt` (date, `includeTime: true`)
   - `uid` (text), `sequence` (number)
   - `kind` (select: `invite`, `sharedCalendarNotice`)
   - relations, all one-directional (the target schemas are locked), `many_to_many`, system-owned with the same `ownerProcess`: `suggestedCalendar` to Calendars, `event` to Events, `sourceEmail` to Emails, and `mailbox` to Mailboxes (the mailbox that received the invitation). Each is single-valued in practice; writers enforce that, the schema does not.
   Then set `schema_locked = true` on the database, as the other module seeds do.
3. Call the new seed function from `backend/packages/data/src/seed/seedSystem.ts` after the Calendars seed call from #1600 (and after the Events changes of #1843 land in the same file, so the two edits do not overlap).
4. Add a per-tenant cutover `backend/packages/data/src/calendar/invitationsDatabaseCutoverMigration.ts` that creates the same database on a tenant that does not have it yet, using the same seed function in one transaction. It is idempotent (no-op when the database already exists) and does nothing for a tenant without a Calendars database. Register it in `runTenantCutoverMigrations` in `backend/packages/data/src/db/tenantCutoverMigrations.ts` after the Calendars cutover. Follow `docs/adr/2026-09-10-app-code-post-migration-steps.md` and `transcription/transcriptionRequeueHeartbeatCutoverMigration.ts`.
5. Declare the database in the `databases` array of `backend/packages/data/src/calendar/calendarModuleManifest.ts` (key `invitations`), after the entry the Calendars database uses.
6. Add the Czech and English display names of the database, its properties and the select options to the calendar module catalog, `backend/packages/data/src/calendar/i18n/cs.json` and `en.json`, in the key style the Inbox module catalog uses (`database.invitations.name`, `property.invitations.<key>.name`, `property.invitations.status.option.<option>`).
7. Tests: a fresh seed creates the database with exactly these properties, types and owners and a locked schema; a generic `PATCH` of `status` returns 403; the cutover adds the database to a tenant seeded earlier, is idempotent on a second run, and leaves another tenant untouched; a user of another tenant cannot read its rows (row-level security).

## Scope

### In scope

- The `invitations` system database, its properties and relations, its ownership, the seed for new tenants and the cutover for existing ones.

### Out of scope

- Creating invitation rows from incoming mail: #1929.
- Answering an invitation and creating or trashing its Event: #1944.
- Sending the reply message: #1953.
- Notifications, push and the pending badge: #1954.
- Invitations from other Semprec users (`sharedCalendarNotice` rows have no producer): shared calendars are not planned yet; they wait for a product decision.

## Acceptance criteria

- When a new tenant is seeded, it has an `invitations` system database with the listed properties, types and owners and a locked schema.
- When the cutover runs for an existing tenant, it gains the same database; a second run changes nothing; a tenant without a Calendars database is left alone.
- When a client sends a generic `PATCH` that sets `status` on an invitation row, then the response is 403 `forbidden`.
- When `core.driftCheck` runs on a seeded tenant, then it reports no orphan properties for this database.
- A user of another tenant cannot list or read the rows of this database.
