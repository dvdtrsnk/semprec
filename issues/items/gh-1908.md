**Blocked by:** #1458, #1890, #1904
**Model tier:** high

## Context

Model tier rationale: This adds a mutating endpoint whose correctness depends on concurrent-request deduplication, queue-job semantics, chain-uniqueness handling and tenant isolation, plus new entries in the closed error contract, so the higher tier is chosen.

A failed scheduled run of a user's automatic task ("tick") cannot be retried. `backend/services/semprec-api/src/agentRunHandler.ts` serves only `GET /api/agent-runs/:id` and `POST /api/agent-runs/mcp-credentials`. The only way to re-run a heartbeat is the manual trigger (`heartbeat.trigger` in `backend/packages/data/src/scheduler/heartbeatAgentTools.ts` and the HTTP trigger from #1453), which is a fresh manual run, not a retry of a given failed run, and it leaves no link between the two.

With the retry chain (#1448) and the occurrence link (#1458) a retry can be precise: the user asks to retry one failed run, and the system starts one new run of the same heartbeat that points back at it with the next attempt number. Whether a run counts as failed, including the case of a reply that finished but left a failed tool call, comes from the shared display status (#1820, extended by #1890). Closing the problem that the original failure raised is done by #1915 when the retry succeeds. Retrying a Semp chat reply is a different mechanism (#1926).

The scheduler's fire task (`createHeartbeatFireTaskForAffinity` in `backend/packages/data/src/scheduler/sweep.ts`) requires exactly one payload discriminator out of `occurrenceId`, `itemId` and `triggeredByRunId`. `ActionContext` and `coreAgentRunAction` (`scheduler/actions.ts`) create the run row inside the worker, per job attempt; a `running` row must never be created ahead of the worker, because startup repair closes every `running` run after a restart, and no `queued` status is added because the web client reads the status as the closed enum `running | done | error`. The closed error contract `ITEM_ERROR_CODES` in `backend/services/semprec-api/src/adapter/errorContract.ts` has no code for retry refusals.

Decisions (decided by the product owner):
- Scheduled tick runs get both: the automatic chain of attempts (#1458), and after the chain has failed, a manual retry from the run detail through this endpoint.
- Only a run that belongs to a scheduled occurrence can be retried. A run started by a manual fire or an item event has no occurrence, so its remaining automatic attempts cannot be seen from the run; it answers `not_retryable` and is not retried. (The person can still start the automation anew with the manual trigger of #1453; that is a new run, not a retry.)
- The retry job is enqueued with a single attempt (`maxAttempts` 1), so a failed retry is a final failure with its notification and can be retried again by the user, instead of silently extending the chain by automatic attempts.
- The two refusals have distinct codes: `retry_pending` means "an automatic attempt may still run, try later", `not_retryable` means "this run can never be retried".

Shared-file ordering: this issue also waits for #1904 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Add `POST /api/agent-runs/:id/retry` in `agentRunHandler.ts`, inside the existing authenticated `runInTenant` scope. It validates the id with `assertUuid`, loads the run (a run of another tenant does not exist under row-level security and answers 404 like any unknown id), and decides in this order:
   - `not_retryable` (409) unless the run's `triggeredBy` is `heartbeat`, it has a `heartbeatOccurrenceId`, and its display status (the shared derivation from #1820, which includes an incomplete reply from #1890) is `error`;
   - `not_retryable` (409) when `getRetrySuccessorId` (#1448) finds a successor (only the last link of a chain can be retried);
   - by the occurrence status: `queued` or `running` gives `retry_pending` (409, an automatic attempt may still run); `cancelled` gives `not_retryable`; `failed` or `succeeded` is terminal and allowed (a `succeeded` occurrence with a run in display status `error` is the incomplete-reply case);
   - the heartbeat being disabled, or its rule being event-triggered, answers 409 with the same codes and messages as the HTTP manual trigger from #1453, which carries the same requirements.
2. Enqueue through the shared `enqueueManualHeartbeatFire` from #1453 (add optional parameters for the extra payload key, the job key and `maxAttempts` if it lacks them), inside one transaction with the checks above. Payload `{ heartbeatId, retryOfRunId }`; job key `heartbeat-fire:retry:<runId>` from a new `retryHeartbeatFireJobKey` in `schedulerStore.ts`; same task name and agent-run lane as the manual trigger. Two concurrent requests for the same run therefore merge into one job. Respond `202` with `{ jobKey }`.
3. In `sweep.ts`, accept `retryOfRunId` as a fourth payload discriminator (exactly one of the four is still required) and pass it as `ActionContext.retryOfRunId` (`actions.ts`).
4. In `coreAgentRunAction`, when `context.retryOfRunId` is set: load the retried run (missing: log ids and return without running); create the new run with `createChainedAgentRun` (#1448) with `attempt` = the retried run's attempt plus 1, the same `heartbeatId`, `projectItemId`, `task` and `heartbeatOccurrenceId`; when the insert reports that the run was already retried, return without running the agent. Do not insert a `running` row from the endpoint.
5. Add `retriedByRunId` (from `getRetrySuccessorId`) to the `GET /api/agent-runs/:id` response so a client sees that a retry exists.
6. Add `not_retryable` and `retry_pending` to `ITEM_ERROR_CODES` and `ITEM_ERROR_STATUS_BY_CODE` (both 409) in `errorContract.ts`, with matching `ChokePointError` subclasses in `backend/packages/data/src/errors.ts`.
7. Register the route: an entry named "retry agent run" in `routeMatrix.ts`, its mapping in `ROUTE_HANDLER_FILES` of `chokePointWriteBoundary.unit.test.ts`, and its isolation case (a run of another tenant answers 404 and writes nothing) in `tenantIsolationRoutes.test.ts`.

## Scope

### In scope

- The retry endpoint, its eligibility rules and error codes, the retry payload discriminator and worker handling for a heartbeat run, and `retriedByRunId` on the run detail.

### Out of scope

- The schema for the chain and the occurrence link: #1448 and #1458.
- Retrying a Semp chat reply: #1926. A run that was not triggered by a heartbeat answers `not_retryable`.
- Closing the problem raised by the original failure when the retry succeeds: #1915.
- Realtime invalidation of agent runs after the retry starts: #1863.
- Retry for runs started by a manual fire or an item event (they have no occurrence): decided not to be done; they answer `not_retryable`.
- Any button, copy or client behavior.

## Acceptance criteria

- When a failed run of a terminal occurrence is retried twice at the same time, then exactly one job exists for the key `heartbeat-fire:retry:<runId>`, and exactly one new run exists with `attempt` n + 1, `retryOfRunId` set, and the same `task`, `projectItemId`, `heartbeatId` and occurrence, processed on the agent-run lane.
- When a retry is requested while the occurrence is still `queued` or `running` (an automatic attempt is pending), then the answer is 409 `retry_pending` and no job is enqueued.
- When the run succeeded, already has a successor, was not triggered by a heartbeat, or has no occurrence, then the answer is 409 `not_retryable`.
- When the heartbeat is disabled or event-triggered, then the answer is 409 with the manual trigger's code.
- When the run belongs to another tenant or does not exist, then the answer is 404 and nothing is enqueued.
- When a run finished with an incomplete reply (display status `error`, occurrence `succeeded`), then it can be retried.
- When the worker finds that the retried run already has a successor, then it creates no run and does not start the agent.
- `GET /api/agent-runs/:id` of the original run returns the retry's id as `retriedByRunId` once it exists, and `null` before.
- The retry job runs with one attempt: a failing retry produces one `agent_run_error` notification and can itself be retried.
