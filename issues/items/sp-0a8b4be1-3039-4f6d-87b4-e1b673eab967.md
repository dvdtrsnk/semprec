### Requirement gh-1518: [relation-api 02/05] Expand relations inline with include=relations

#### Context

Model tier rationale: A single response shape is added across three read paths (item get, database query, view query) with a constant-query-count guarantee, bounded fan-out limits, one nested level and tenant and archive filtering, so a mistake leaks data or turns a page read into N+1 queries.

Every screen that shows an item's links (a person's companies and projects, a project's area as a colored label, a movie's "watched with" people) currently needs one edge read per item and one item read per target. `GET /api/items/:id` returns only the stored envelope (`itemEnvelope.ts`), with `?include=path` as the single supported include, and `database.query` / `view.query` return `{ items, nextCursor }` with no link data at all. #1404 adds the edge read; this issue adds the one inline expansion that all callers use, so clients render a list of 50 projects with their area labels in one request.

It also builds on #1412, which exposes blob metadata for file and image properties; projected file or image properties of a target return that metadata. Later issues (#1595, #1842, #1771) reuse the expansion.

Decisions (conservative defaults):
- Colour and icon of a target are returned whenever the target's database defines them, without any projection request.
- Only one nested level exists: when a projected key of a target is itself a relation (a project's area), it returns a reduced `[{ id, databaseKey, title, color, icon }]` and is never expanded further.
- Archived-database targets are excluded exactly like deleted targets. Decided by the product owner: archiving a database behaves as the trash everywhere, so expansion and reads omit its items.
- Unknown relation keys in `include` fail the whole request with `400` rather than being silently ignored.

Shared-file ordering: this issue also waits for #1509 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1521: [relation-api 03/05] Replace a single-valued relation atomically with relation.set

#### Context

Model tier rationale: One locking write path over existing store and catalog seams, but it must serialize concurrent writers on an item row and change an agent-visible approval contract, so the transaction ordering needs care.

Single-valued relations (a project's area, a task's project: the `item_b` side of a `one_to_many` definition, and either side of a `one_to_one` definition) can hold only one edge. The trigger from migration `0013_relation_cardinality.sql` rejects a second edge with `409 cardinality_violation`, so moving a task to another project is today a `DELETE` followed by a `PUT` in two transactions: a failure between them leaves the task without a project, and `relation.delete` is a destructive operation that an agent can only perform after approval. Each client also has to read the current edge first, and #1404 now provides that read.

This issue adds the operation `relation.set`, which replaces the single edge of a single-valued relation atomically, or clears it. #1590 reuses its single-valued handling for creation, #1621 publishes the invalidations its writes produce, #1713 and #1758 make an agent's `relation.set` wait for approval when it would break a value link, and #1702 and #1833 call it.

Decisions:
- `relation.set` is its own catalog operation, not a `replace` flag on `relation.put`, so MCP and the approval layer can treat replacing an edge differently from adding one.
- The operation is non-destructive and carries the ordinary write risk class (the `write` class of #1423); replacing an existing edge needs no approval. ### Requirement gh-1621: [relation-api 05/05] Publish realtime invalidations for relation edge writes

#### Context

Model tier rationale: One additive realtime frame carried through the existing publish, parse and fan-out seams with established tests, but it is emitted from a transaction hot path shared by internal writers and must dedupe and respect tenant scoping.

Edge writes need relation invalidations because item timestamps do not change. This member owns their publication from createRelationWithClient, updateRelationWithClient and deleteRelationWithClient, including API, relation.set, initial relations and internal writers. Decisions:
- The canonical scope name is `relation` (singular).
- The frame is thin: no `updatedAt`, no stale-echo rule, no edge content. A client reacts by refetching whatever it shows for that item and key (an item detail or list read with `include=relations`, a related-items read, a count).

- The target end of a one-directional relation (a definition with `propertyIdB = null`, such as a file's area) has no property key of its own, but it still receives a thin invalidation with `propertyKey: null`, so the links shown at the target (links pointing back at it) do not go stale. - Required backend tests and functional scenarios exercise production paths, including relevant failures, tenant isolation, concurrency, idempotency and populated-tenant migrations.
- Independent review has no unresolved medium-or-higher findings. Confirmed findings are fixed and affected evidence is rerun against the final candidate SHA.
- The full backend `pnpm run verify` passes. No web or mobile verification is required. A missing external service or required live-provider check is BLOCKED/NOT RUN, never PASS.
- Only after this entire gate passes may this batch and its approved source records be completed with individual handovers pointing to the verified implementation. All source approvals must still match their specifications.
- The next sequential batch starts only after this batch's gate passes; a failure holds advancement.
