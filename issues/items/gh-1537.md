**Blocked by:** #1431, #1521, #1529
**Model tier:** medium

## Context

Model tier rationale: A read-only custom route over existing stores with a precise multi-record resolution rule, where tenant isolation and the guarantee of no side effects are the risks.

The Journal screen opens a day, a week, a month, a quarter or a year. Today there is no Journal route: a client can only run `POST /api/databases/:journalId/query` filtered on type and period, and the item envelope carries neither the page id (`docId`) nor any content. The day's Inbox summary lives in `item.computed.inboxItems` (`backend/packages/data/src/inbox/journalInboxCompute.ts`). A period that has never been written has no row at all, and merely viewing it must not create one.

There is no uniqueness constraint on type and period. A trashed entry that is restored (see #1666) can leave two live rows for one period; the reservation key `journal:<journalDb>:<type>:<period>` in `idempotency_keys` points at the one the write path currently uses (the most recently created live row; `items` has no `created_at`, and `updated_at` changes on every edit, so it cannot be used to order them).

This issue depends on #1431 for key validation and period description. #1613 later fills the Markdown fields, #1721 adds the day's events, and #1541 creates the period lazily on first write.

Decision: this is a `single-consumer-read` custom route and never calls the get-or-create path.

Shared-file ordering: this issue also waits for #1521, #1529 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `io-hardening`, `error-handling` and `testing`.

1. Add `GET /api/journal/periods/:type/:period`. `type` is one of year, quarter, month, week, day; `period` is validated with `parseJournalPeriodKey` (#1431); invalid type or key answers 400 `validation_failed`.
2. Resolve `item` as the live Journal row (`deleted_at IS NULL`) with that type and period; if two are live, the one the reservation key points at, falling back to the reservation's target only when it is live. No row means `item: null`.
3. Respond with `{ type, period, range: { from, to }, path, today, item, docId, markdown }` where `path` is `describeJournalPeriods` output as `{ year, quarter, month, week, day }` each `{ period, range: { from, to } }`, `today` is the tenant's current day, `docId` is the existing page's id or `null`, and `markdown` is `null` for now.
4. For `type = day` add `week: { period, range, itemId, docId, markdown }` (the entry of the day's ISO week, `itemId` and `docId` null if absent) and `inbox` equal to the day item's `computed.inboxItems` (`[]` when the day has no entry).
5. For `type = month` add `weeks: [{ period, range, itemId, docId, markdown }]` for every ISO week overlapping the month (`weeksOfMonth`), resolved with one query for all weeks.
6. Use the tenant zone from system settings. Never insert an item or a doc. No session answers 401; another tenant's data is never visible (tenant scope, row-level security).
7. Declare the route in the system databases module manifest `customRoutes` with justification `single-consumer-read`, add the handler and its export, an entry in `routeMatrix.ts` and in `tenantIsolationRoutes.test.ts`.
8. Tests: day on an empty tenant returns `item` and `docId` null with week `2026-W42` ranged 2026-10-12 to 2026-10-18 and creates no rows; 2027-01-01 reports week `2026-W53`; `week/2027-W53` is 400; month 2026-10 returns five weeks and an existing week has `itemId` and `docId`; quarter 2026-Q4 range is 2026-10-01 to 2026-12-31; with two live rows the reserved one wins.

## Scope

### In scope

- The side-effect-free period read with its path, week, weeks and day Inbox summary.

### Out of scope

- Page Markdown content; #1613.
- The day's events; #1721.
- Creating a period or its page; #1541.
- Enforcing a single live row per period; #1666 prevents the cases it can.

## Acceptance criteria

- When the day 2026-10-16 is read on an empty tenant, then `item` and `docId` are null, `week.period` is `2026-W42` with range 2026-10-12 to 2026-10-18, and no item or doc row exists afterwards.
- When 2027-01-01 is read as a day, then `week.period` is `2026-W53`; when `week/2027-W53` is requested, then 400.
- When month 2026-10 is read, then five weeks are returned and `2026-W40` has range 2026-09-28 to 2026-10-04; an existing week has `itemId` and `docId`.
- When two live rows exist for one day, then the one the reservation points at is returned.
- A request without a session answers 401.
