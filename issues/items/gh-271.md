**Blocked by:** #270

## Context

Issue #102 added `deleteInboxTypeWithClient` in `backend/packages/data/src/inbox/inboxTypesStore.ts`. Deleting an Inbox item type clears the `type` relation on every referencing Inbox item that is not locked (an item is locked when it has a `confirmed`/`rejected` Processing proposal), then soft-deletes the type item. A post-merge review of #102's pull request raised two findings that were never addressed; both are still on `develop`.

**1. The delete diverges from the choke-point's own delete contract.** The function calls `itemsStore.softDeleteItem` directly, but the choke-point's `softDeleteItem` (in `backend/packages/data/src/chokePoint/chokePoint.ts`) additionally lists the item's remaining edges and calls `enqueueRollupRecomputeForEdge` for each. No rollup property exists on `inboxItemTypes` today, so the omission is a silent no-op right now — but it breaks the established pattern, and the day a rollup is added over this relation the recompute will be dropped with no visible error.

**2. N+1 queries while checking locks.** For every edge in `typeEdges`, the function issues one `listRelationsForItem` call for that Inbox item's proposals, and then one `getItemById` per proposal, all inside a single transaction — O(n × m) round trips for a type with many referencing items.

## Task

- After the `itemsStore.softDeleteItem` call in `deleteInboxTypeWithClient`, mirror the choke-point pattern: call `relationsStore.listAllRelationsForItem(client, input.typeItemId)` (it returns every relation of the item and takes no filter — the ordering after the soft delete is what makes these the edges to recompute) and enqueue a rollup recompute for each, exactly as `chokePoint.ts`'s `softDeleteItem` does at its `for (const edge of edges) await enqueueRollupRecomputeForEdge(client, edge)` line.
- `enqueueRollupRecomputeForEdge` is currently module-private in `backend/packages/data/src/chokePoint/chokePoint.ts`. Export it from that file (and re-export it from `packages/data/src/index.ts` only if the package's existing export style requires it) and call it, rather than reimplementing the enqueue in `inboxTypesStore.ts`. Exporting it is the only change permitted in `chokePoint.ts`.
- Replace the per-item, per-proposal lookups with batched reads: fetch the proposal edges for all referencing Inbox items, and then the proposal items themselves, in bulk rather than one query per item and one per proposal. Two traps here. First, `itemsStore.getItemsByIds` already exists but its query ends with `AND deleted_at IS NULL`, while the current per-proposal read uses `getItemById`, which has **no** such filter — swapping one for the other would silently change the lock rule, because a soft-deleted `confirmed`/`rejected` proposal locks an Inbox item today and would stop doing so. Add a bulk items read that mirrors `getItemById`'s lack of a `deleted_at` filter (or give the existing helper an explicit opt-in), and say in a comment why. Second, the "relations for many items at once" read is genuinely missing from `relationsStore`; add that one helper alongside the existing ones, following their style. The lock rule itself must not change: an Inbox item is locked when at least one of its `sourceInbox` proposals has a status in `LOCKED_PROPOSAL_STATUSES`, locked items keep their `type` relation, and unlocked items have it cleared.
- Keep the existing `triggerOnItemEventHeartbeats(..., "delete", ...)` call and the `ItemRow | null` return contract.

Extend `backend/packages/data/src/__tests__/inboxPipeline.test.ts` so it covers deleting a type referenced by several Inbox items — some locked, some not — and asserts three things.

First, that exactly the unlocked ones lose their `type` relation.

Second, that the rollup-recompute step runs for the edges that survive the delete. Do **not** try to create a rollup property as a fixture: `seedInboxPipeline.ts` sets `schema_locked = true` on `inbox`, `inboxItemTypes` and `processingProposals`, so `createProperty` throws `ForbiddenError` there. Assert it through the instrumented client instead — `enqueueRollupRecomputeForEdge` always calls `findDependenciesByRelationDefinition`, which issues a SELECT even when there are no rollup dependencies, so that query is observable. The referencing item must be a **locked** one, whose `type` edge survives the delete: for unlocked items `deleteRelationWithClient` already performs this lookup on its own (`chokePoint.ts`), so a test built on them passes with or without the fix. With the fix, the surviving edge produces one further dependency lookup after the soft delete; without it, none.

Third, the batching. Count queries through the same instrumented client, recording SQL text, and assert that the **lock lookup** no longer scales with the number of proposals per item: clearing a relation is still one `deleteRelationWithClient` per unlocked item, so the total query count necessarily grows with the number of referencing items. Match the lock-resolution reads by their SQL text (the `item_relations` select the new bulk helper issues, and the bulk `items` select) and assert that count is fixed regardless of how many proposals each Inbox item has — do not assert on the overall total.

## Scope

### In scope

- The rollup-recompute step and the batched lock lookup in `deleteInboxTypeWithClient`.
- The two bulk read helpers this needs: one "relations for many items" read in `relationsStore.ts`, and one bulk items read in `itemsStore.ts` that — unlike `getItemsByIds` — does not filter on `deleted_at`, so the lock rule is preserved exactly.
- Exporting `enqueueRollupRecomputeForEdge` from `chokePoint.ts` so the delete path can reuse it.
- The test above.

### Out of scope

- `createInboxTypeWithClient`, the archive path, and `listActiveInboxTypes` (#270).
- Adding any rollup property to `inboxItemTypes` — this issue only makes the delete path honor rollups that may exist later.

## Acceptance criteria

- Deleting an Inbox item type runs the same rollup-recompute step the choke-point's `softDeleteItem` runs, over the edges that survive the delete — demonstrated by the instrumented-client assertion the Task describes: deleting a type referenced by a locked Inbox item issues a `findDependenciesByRelationDefinition` lookup for that surviving edge after the soft delete, where today it issues none.
- Deleting a type referenced by N Inbox items no longer issues a number of queries proportional to N times the number of proposals per item.
- Locked Inbox items keep their `type` relation and unlocked ones lose it, exactly as before, and the existing Inbox pipeline tests pass.
