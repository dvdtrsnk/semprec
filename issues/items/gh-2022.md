## Context

Model tier rationale: One additive response field from a distinction the decision action already computes, in one handler and one view type, with existing decision tests; no new route, transition or authorization rule.

When a person approves or rejects a request, the app must tell whether this tap actually made the decision or the request had already been decided, for example from a notification action on another device, so it can show "Already decided" instead of a false confirmation. Today a repeated `PATCH /api/approval-requests/:id` on a decided request answers 200 with the current state, indistinguishable from the first decision. `decideAndEnqueueApprovalRequest` in `backend/packages/data/src/mcp/approvalDecisionAction.ts` already knows which case happened (#1789 and #1772 rely on its `unchanged` result).

#1786 adds the read of one request and the pending count to the same handler and explicitly leaves this field out; this issue adds it.

Decision: `outcome` is a top-level field beside the existing decision view fields of the `PATCH` response (additive REST contract, no envelope change); the status code stays 200 for both cases. `GET /api/approval-requests` and `GET /api/approval-requests/:id` do not carry it, because it describes one decide call, not stored state.

## Task

Load `testing` and `error-handling`.

1. `PATCH /api/approval-requests/:id`: add `outcome: "decided" | "unchanged"` to the response: `decided` when this call performed the transition, `unchanged` when the request was already decided. Use the distinction `decideAndEnqueueApprovalRequest` already computes; expose it on its result if it is not exposed yet. Do not change the transition or its exactly-once behavior.
2. Tests: a pending request decided once answers `outcome: "decided"`; the same request decided again (same or opposite decision) answers 200 with the current state and `outcome: "unchanged"`, and no second execution job is queued; a foreign or unknown id still answers the existing 404.

## Acceptance criteria

- When a pending request is decided, the `PATCH` response has `outcome: "decided"`.
- When the same request is decided again, the response is 200 with the current state and `outcome: "unchanged"`, and no second execution job is queued.
- `GET /api/approval-requests` and `GET /api/approval-requests/:id` responses do not contain `outcome`.
