## Context

Model tier rationale: It adds a column to the partitioned `items` table with a backfill over existing tenant data and changes the sort specification and keyset cursor shared by every collection query, a wide persisted-data and query contract.

The library list's default order is "most recently added first". The `items` table has `updated_at` (used as the optimistic-concurrency version `ifVersion`) and `deleted_at` but no creation time (`backend/packages/data/src/db/migrations/0001_core_schema.sql`). A sort by `updated_at` would reorder items whenever they are edited, and a sort spec can only name property keys: `lookupSortProperty` in `backend/packages/data/src/views/sortCompiler.ts` resolves `sort.property` against the database's properties, and a user-created collection may legitimately have its own property called `createdAt`, so a system field must not share the namespace of property keys.

Decision: creation time is stored in a general `items.created_at timestamptz NOT NULL DEFAULT now()` column, not as a per-database property.
Decision: existing rows get their creation time approximated by their last change time (`updated_at`), because the true time is unknown; rows of the same age therefore sort by last edit.

Plan:
- Migration adds the column. Adding it to the partitioned parent is a metadata-only change; existing rows read as the time of the `ALTER`. Partitions created later are created `LIKE items`, so they carry the column.
- A per-tenant data cutover backfills in batches: `UPDATE items SET created_at = updated_at WHERE created_at > updated_at` is both the filter and the idempotency check (a row written after the `ALTER` has `created_at <= updated_at`, an old row not yet backfilled has `created_at > updated_at`). It must never change `updated_at`.
- The item envelope gets an additive `createdAt`.
- `SortSpec` accepts either `{ property, direction }` or `{ system: "createdAt" | "updatedAt", direction }`, validated with zod; the keyset cursor encodes and compares the system column; all keys keep `NULLS LAST` and an `id ASC` tie-break.

#1524 (Czech collation and title tie-break) is the preceding change to `sortCompiler.ts`; this issue builds on it. The Tasks data migration #1657 rewrites `updated_at`, so its backfill ordering relative to this one matters: this backfill must run before it, which is why #1657 waits for this issue.

Shared-file ordering: this issue also waits for #1588 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

1. Migration `backend/packages/data/src/db/migrations/NNNN_items_created_at.sql (next free ordinal at commit time)`: `ALTER TABLE items ADD COLUMN created_at timestamptz NOT NULL DEFAULT now()`. Follow `docs/adr/2026-10-08-items-partitions-attached-under-share-update-exclusive.md` for the lock behavior and set a lock timeout; verify that item partitions created through the partition function and tenant export/purge code that lists `items` columns still work.
2. Backfill cutover `backend/packages/data/src/db/itemsCreatedAtBackfillCutoverMigration.ts`, registered in `tenantCutoverMigrations.ts`: batched updates as above, one transaction per batch, runtime role under tenant scope. It does not touch `updated_at`.
3. Expose `createdAt` (ISO string) on the item envelope: `ItemRow` in `backend/packages/data/src/types.ts`, the mapping and column lists in `backend/packages/data/src/chokePoint/itemsStore.ts`, and the item row schema in `backend/packages/shared/src/genericOperations/rows.ts`. Additive: existing clients ignore it.
4. Extend the sort spec in `backend/packages/data/src/views/sortSpec.ts` and its shared copy in `backend/packages/shared/src/genericOperations/filterSort.ts` with the `system` variant; reject a spec that has both `property` and `system`. In `sortCompiler.ts` compile a system key to its column (`created_at` or `updated_at`) and make `compileSortKeyset` compare the same expression. In `backend/packages/data/src/views/viewQuery.ts` encode and validate the cursor value for a system key (an ISO timestamp).
5. Tests: sorting by `{system: "createdAt", direction: "desc"}` returns the latest added item first and pages stably across at least three pages with equal timestamps; a collection with its own property named `createdAt` sorts by that property for `{property: "createdAt"}` and by the system column for `{system: "createdAt"}` without confusion; the backfill sets old rows' `created_at` to their `updated_at`, is idempotent, and leaves `updated_at` unchanged; a foreign cursor value is a 400.

## Scope

### In scope

- The `items.created_at` column, its batched backfill, the additive `createdAt` on item rows, and system-field sorting with a stable keyset cursor.

### Out of scope

- Filtering by system timestamps: not planned yet.
- Czech collation and title tie-break: #1524.
- Normalizing Tasks dates: #1657.
- Backdating true creation times; old items are approximated by their last change.

## Acceptance criteria

- When items are listed with `sort: [{ system: "createdAt", direction: "desc" }]`, then the most recently added item is first, and paging by cursor visits every item exactly once.
- When the backfill has run, then every pre-existing item has `createdAt` equal to its `updatedAt` and `updatedAt` is unchanged; running it again changes nothing.
- When a collection has its own property `createdAt`, then a sort by `{ property: "createdAt" }` uses that property and `{ system: "createdAt" }` uses the column.
- When a sort spec names both `property` and `system`, or an unknown system field, then the request is rejected with 400.
- When an item is read, then its envelope includes `createdAt`; clients that ignore it keep working.
- When a new item is created, then `createdAt` is set by the database and is not changed by later updates.
