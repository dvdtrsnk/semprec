**Blocked by:** #630

## Context

`requestPasswordReset` in `backend/packages/data/src/auth/passwordResetActions.ts` (lines 62-92) promises in its docstring (lines 45-54) that a known and an unknown email resolve indistinguishably, but it does not: for an unknown email it returns right after one `SELECT` inside `withTransaction` (line 71), while for a known email it commits the token and then `await`s `mailer.sendPasswordResetEmail(...)` (lines 84-91) before resolving. `NodemailerPasswordResetMailer` (`backend/packages/data/src/auth/passwordResetMail.ts`, `DEFAULT_SEND_TIMEOUT_MS = 30_000`, line 23) can take up to 30 s on a slow SMTP server. `POST /api/auth/password-reset/request` (`backend/services/semprec-api/src/authHandler.ts`, lines 184-198) awaits the action before answering, so a caller can enumerate registered emails by response time.

Depends on #630, which edits the import block of the same file (`passwordResetActions.ts`); this issue edits `requestPasswordReset` and adds an import of its own.

## Task

- In `requestPasswordReset`, move the send into the transaction's after-commit hook so the function resolves as soon as the token row commits, for a known and an unknown email alike:
  - Import `runAfterCommit` from `../db/pool.js` (the file already imports `withTransaction` from there).
  - Inside the `withTransaction` callback, after `createPasswordResetToken`, register `runAfterCommit(client, () => { void mailer.sendPasswordResetEmail({ to: user.email, resetUrl: buildPasswordResetUrl(input.appBaseUrl, token) }).catch((err) => console.error("requestPasswordReset: failed to send the password-reset email", err)); })`. The callback is synchronous by contract (`docs/adr/2026-09-10-side-effects-follow-the-commit.md`): it starts the send and attaches the same catch-and-log the function has today; nothing awaits it.
  - Delete the post-transaction `if (!created) return;` / `try { await mailer.send... }` block; the callback needs `created` no longer, so the transaction callback can return `void`.
  - Rewrite the docstring: the token commits first (a rollback sends no mail), the mail is dispatched after `COMMIT` without being awaited, a send failure is logged and never surfaces (the ADR's "a callback's failure is invisible to its caller" consequence — a user who never receives the mail requests again), and the response no longer carries a timing signal from SMTP. Drop the claim "no distinguishable timing-free signal".
- The HTTP handler needs no change.
- Tests:
  - `backend/packages/data/src/__tests__/passwordResetActions.test.ts`, inside `describe("requestPasswordReset")` (integration tier): a fake mailer whose `sendPasswordResetEmail` records the call and returns a promise that resolves only when the test calls a `release()` function; `await requestPasswordReset(pool, mailer, ...)` resolves for a known email while that promise is still pending, and the recorded `to` is the user's email; then `release()`. Add a second case: a mailer that rejects → `requestPasswordReset` still resolves `undefined` and the token row exists (`countRecentPasswordResetTokens` is 1).
  - `backend/services/semprec-api/src/__tests__/authHandler.test.ts`, inside `describe("POST /api/auth/password-reset/request")`: build the listener for this one test with a deferred mailer of the same shape; `POST` with a known email → 200 `{ ok: true }` before `release()` is called; then `release()`.
  - The existing cases that read `mailer.sent` right after the response keep passing because the fake mailer records the call synchronously at the start of `sendPasswordResetEmail`; do not change them.

## Scope

### In scope

- Dispatching the reset mail after commit, unawaited, with the same catch-and-log.
- The docstring correction and the two deferred-mailer tests.

### Out of scope

- `resetPassword` and the minimum-length check — #630.
- Moving the send into a queue job with retries (the ADR's alternative for effects that need a delivery guarantee); a reset mail that fails to send is recovered by requesting again, as the current docstring already states.
- Any change to `passwordResetMail.ts`, its timeout, or `PASSWORD_RESET_MAX_REQUESTS_PER_WINDOW`.
- The `POST /api/auth/password-reset/consume` branch.

## Acceptance criteria

- When `POST /api/auth/password-reset/request` is called with a known email and the mailer's send has not yet resolved, the response is already 200 `{ ok: true }`.
- When the mailer's send rejects, `requestPasswordReset` still resolves `undefined`, the `password_reset_tokens` row exists, and the failure is logged.
- The send is registered through `runAfterCommit` inside the `withTransaction` callback — `grep -n "runAfterCommit" backend/packages/data/src/auth/passwordResetActions.ts` finds it — so a rolled-back token transaction sends nothing.
- Every existing case in both `describe` blocks still passes unchanged.
