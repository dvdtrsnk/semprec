**Blocked by:** #974

## Context

An item gets at most one doc: a Yjs page or canvas. The `docs` table enforces this with the global unique index `docs_item_id_idx ON docs (item_id)` (`backend/packages/data/src/db/migrations/0003_docs.sql:11-13,22`). `getOrCreateDoc` (`backend/packages/data/src/docs/docsStore.ts:54-108`) creates the row lazily on the first content write:
- it reads an existing doc with `getDocByItemId`, `WHERE item_id = $1` (`:22-27`);
- it requires a live item through `getItemsByIds` (`:66-67`);
- it inserts with `INSERT ... ON CONFLICT (item_id) DO NOTHING` (`:70-73`);
- on a conflict it re-reads the winner (`:97-107`).

The docstring (`:49-52`) calls the concurrent first-write race "rare" in "a single/two-user system". `deleteDocByItemId` deletes `WHERE item_id = $1` (`:115-117`).

`ON CONFLICT (item_id)` infers its arbiter from the column list, and only `docs_item_id_idx` matches it. #1065 drops that legacy index after the checkpoint release. From then on the statement has no matching constraint, so every first content write to a page or canvas fails. Nothing else switches this statement before then.

Tenancy state this issue builds on:
- `docs` is a tenant table: `tenant_id uuid NOT NULL DEFAULT app_tenant_default()`, plus the RESTRICTIVE `tenant_isolation` policy `tenant_id = (SELECT app_tenant_default())`.
- `app_tenant_default()` is `COALESCE(app_current_tenant(), app_sole_tenant())` over the GUC `app.tenant_id`, which `withTransaction` sets from the ambient `runInTenant` / `runAsSystem` scope (`@semprec/shared`).
- `getDocByItemId`, `getItemsByIds` and `deleteDocByItemId` therefore already see only the caller's tenant under a runtime role.
- #974 added `docs_tenant_item_id_uq ON docs (tenant_id, item_id)` and the parent key `docs_tenant_id_id_uq ON docs (tenant_id, id)` beside `docs_item_id_idx`. The legacy index stays until #1065.

Arbiter choice (the same as the idempotency, blob and person-index switches):
- The insert moves to `ON CONFLICT DO NOTHING` with no conflict target, so every unique index on `docs` is an arbiter: today the legacy one and `docs_tenant_item_id_uq`, after #1065 only `docs_tenant_item_id_uq`. `docs_pkey` and `docs_tenant_id_id_uq` are arbiters too, but they cover the server-generated `id` and never conflict.
- An explicit `ON CONFLICT (tenant_id, item_id)` would leave `docs_item_id_idx` as a non-arbiter while it exists. A concurrent first write to one item could then fail with a raw unique violation on the legacy index instead of converging on the winner.

## Task

Load `state-writes` (the insert and its conflict re-read run in the caller's transaction) and `error-handling` (the conflict paths must keep their current outcomes).

1. **Arbiter.** In `getOrCreateDoc` (`docsStore.ts:70-73`), replace `ON CONFLICT (item_id) DO NOTHING` with `ON CONFLICT DO NOTHING`, with no conflict target.
   - The rest of the function is unchanged: the existing-doc read, the live-item check, the snapshot and baseline-history inserts, the winner re-read and both `ConflictError` kind checks.
   - Do not add hand-written `tenant_id` predicates; RLS confines the reads and the delete.
2. **Docstring.** Rewrite `:49-52`:
   - at most one doc per item within a tenant, enforced by `docs_tenant_item_id_uq`;
   - the insert is arbitrated by every unique index on `docs`;
   - the concurrent first-write race converges on the winner.

   Drop the "single/two-user system" remark.
3. **Tests.** New `backend/packages/data/src/__tests__/docsPerTenant.test.ts`.
   - Cases needing a second tenant, or the post-#1065 schema, run in one transaction on `getTestPool()` (the owner), rolled back at the end:
     - `DROP INDEX IF EXISTS tenants_single_tenant_guard`;
     - `DROP INDEX docs_item_id_idx`;
     - insert a second `tenants` row;
     - create one database per tenant with `databasesStore.createDatabase(client, ...)`, and items with `itemsStore.insertItem`, or raw SQL where an item needs an explicit id;
     - `SET LOCAL ROLE semprec_data`;
     - switch tenants with `SELECT set_config('app.tenant_id', $1, true)`.

     Integration files run one at a time (`fileParallelism: false`, `backend/vitest.integration.config.ts:20`).
   - The race case runs on today's schema with two connections from `getTestPool()`, as `backend/packages/data/src/__tests__/moduleDataMigration.test.ts:202-253` does: one open transaction, and `pg_blocking_pids` to wait until the second caller blocks.

## Acceptance criteria

All integration tests (`*.test.ts`).
- **Single tenant unchanged.** With one tenant, every case in `backend/packages/data/src/__tests__/docs.test.ts` passes unchanged: lazy creation, idempotent repeat writes, the different-kind conflict, the live-item requirement and the baseline checkpoint.
- **Concurrent first write, today's schema.** Both `docs_item_id_idx` and `docs_tenant_item_id_uq` are in place:
  - a first `getOrCreateDoc(item, "page")` inside an open transaction, and a second call on another connection that blocks on it;
  - after the first commits, the second resolves to the same doc id without an error;
  - there is exactly one `docs`, one `doc_snapshots` and one baseline `doc_snapshot_history` row for the item.
- **Without the legacy index.** With `docs_item_id_idx` dropped (rolled-back transaction):
  - a repeat `getOrCreateDoc(item, "page")` returns the same doc, and only one `docs` row exists;
  - `getOrCreateDoc(item, "canvas")` rejects with `ConflictError`.

  This proves the code no longer needs the legacy index.
- **Same item id in two tenants.** With the legacy index dropped, two tenants under `semprec_data` each hold an item with the same id (inserted with an explicit id into each tenant's own database). Then:
  - `getOrCreateDoc` succeeds in both tenants;
  - each tenant's `getDocByItemId` returns its own doc, with distinct doc ids.
- **Foreign item.** In tenant B's scope under `semprec_data`:
  - `getOrCreateDoc` with tenant A's item id rejects with `NotFoundError`, and no `docs` row is created in either tenant;
  - `getDocByItemId` with A's item id returns `null`;
  - `deleteDocByItemId` with A's item id leaves A's doc in place.
