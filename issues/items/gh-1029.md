## Context

Model tier rationale: Existing schemas and hooks gain precisely specified MCP validation guards.

`mcpServers.connectionConfig` is a `json` property with `owner: "user"` (`backend/packages/data/src/seed/seedMcpModule.ts:84`). Its `stdio` variant names a host `command`, `args` and `env` (`backend/packages/data/src/mcp/mcpConnectionConfig.ts:11-25`). Its `sse` and `http` variants carry only a `url` (`:27-35`), which the connection factory later fetches from the server.

The config is validated only on the proposal path. `assertValidMcpServerProposalProperties` (`backend/packages/data/src/mcp/mcpServerProposal.ts:92-105`, called from `backend/packages/data/src/inbox/inboxTickAction.ts:322-324`) checks the shape and a credential denylist. Every other path stores any JSON:
- REST `POST /api/databases/:id/items` and `PATCH /api/items/:id`;
- MCP `semprec.item.create` and `semprec.item.patch`;
- the agents' `item_create` and `item_patch` AgentTools.

All of them go through `createGenericApplicationService` (`backend/packages/application/src/genericApplicationService.ts:261-279`) into `createItemWithClient` and `updateItemWithClient` (`backend/packages/data/src/chokePoint/itemWrites.ts:155`, `:252`). The proposal confirm path creates the item through `createItemWithClient` too (`backend/packages/data/src/inbox/proposalActions.ts:276-279`).

`docs/adr/2026-09-27-ssrf-protection-for-stored-outbound-urls.md` requires every stored outbound URL to pass a baseline check when it is stored. That check is implemented today only by `validateWebPushEndpoint` (`backend/packages/data/src/push/webPushEndpointValidation.ts:23-50`). MCP remote URLs never get it, so any writer can store `http://127.0.0.1:5432/` or a link-local address for the server to call. Approved rule: remote MCP uses `https` to a public DNS host.

The choke point's domain hooks (`backend/packages/data/src/chokePoint/hooks.ts`, registered in `backend/packages/data/src/domainWriteHooks.ts`, per `docs/adr/2026-09-30-choke-point-domain-hooks-through-a-per-process-registry.md`) are the single place every item write passes, but there is only an update hook (`hooks.ts:11-25`). `createItemWithClient` runs no hook, and the dependency rule `chokepoint-knows-no-domain` forbids `chokePoint/` from importing `mcp/` directly.

#1030 builds on this hook to confine the `stdio` transport. #1034 adds connect-time address checks for remote URLs.

## Task

Load `state-writes` (the guard runs inside the write's transaction), `io-hardening` (a stored outbound URL), `error-handling` and `adr-conventions`.

1. **Item-create hook.** In `hooks.ts`:
   - add `ItemCreateHookContext { client: PoolClient; database: DatabaseRow; item: ItemRow; properties: Record<string, unknown> }`;
   - add `registerItemCreateHook` and `runItemCreateHooks`, with the same `Set` semantics as the update registry;
   - `clearHooksForTests` also clears the new set.

   `createItemWithClient` calls `runItemCreateHooks` after a real insert, not on an idempotent replay (`itemWrites.ts:181-186`), and before `triggerOnItemEventHeartbeats`. A rejection rolls the insert back.
2. **Baseline URL rule.** New `backend/packages/data/src/net/storedOutboundUrl.ts` exports `isBaselineOutboundUrl(value: string): boolean`, moving the exact rules of `validateWebPushEndpoint`:
   - scheme `https:`;
   - no userinfo;
   - no explicit port;
   - the host is not `localhost`, not `*.localhost` (trailing root dot included) and not an IP literal.

   `validateWebPushEndpoint` delegates to it; its message and `field` are unchanged.
3. **Storable config.** In `mcpConnectionConfig.ts`, add `assertStorableMcpConnectionConfig(value: unknown): McpConnectionConfig`. It runs `assertValidMcpConnectionConfig`, then for `sse` and `http` requires `isBaselineOutboundUrl(url)`. Every failure throws `ValidationError` with `{ field: "connectionConfig" }`. `assertValidMcpConnectionConfig` stays shape-only, because the connection factory's `parseConnectionConfig` (`backend/packages/data/src/mcp/mcpConnectionFactory.ts:114-120`) keeps using it.
4. **The hook.** New `backend/packages/data/src/mcp/mcpServerWriteHook.ts` exports `mcpServerItemCreateHook` and `mcpServerItemUpdateHook`. Each acts only when `database.ownerModuleId === MCP_SERVERS_MODULE_ID` and the written properties contain `connectionConfig`, and then calls `assertStorableMcpConnectionConfig`. Register both in `domainWriteHooks.ts`. This covers REST, `/mcp`, AgentTools and the proposal confirm path, because all of them write through `createItemWithClient` or `updateItemWithClient`.
5. **Proposals.** `assertValidMcpServerProposalProperties` calls `assertStorableMcpConnectionConfig` where it now calls `assertValidMcpConnectionConfig` (`mcpServerProposal.ts:103`), so a remote URL that fails the baseline never becomes a proposal card. The credential denylist is unchanged.
6. **ADR.** Add `docs/adr/<YYYY-MM-DD>-item-create-domain-hooks.md`, standalone, referencing `[[2026-09-30-choke-point-domain-hooks-through-a-per-process-registry]]`. It records the third registry, `registerItemCreateHook`, and when it runs: after a real insert, never on a replay. It also records that MCP remote URLs now follow `[[2026-09-27-ssrf-protection-for-stored-outbound-urls]]` through `isBaselineOutboundUrl`.
7. **Existing fixtures.** Most tests insert `mcpServers` rows with `itemsStore.insertItem`, which bypasses hooks, and are unaffected. `createGrantedTool` in `backend/packages/agent-runtime/src/__tests__/mcpInvokeTool.test.ts:46-52` writes through `createItemWithClient` and points at the live `http://127.0.0.1` contract servers (`mcpContractServers.ts:268`, `:360`); it inserts its row with a raw `INSERT INTO items` instead of changing its URL (that package cannot import `itemsStore`). Any other fixture that writes a non-baseline remote URL through the choke point and does not talk to a live server switches to an `https` DNS URL.

## Scope

### In scope
- The item-create hook registry, the shared baseline URL rule, the storable-config check, the MCP server write hook on every write path, the proposal-side check, and the ADR.

### Out of scope
- Restricting the `stdio` transport, writer provenance, and the proposal `stdio` ban (#1030).
- Re-checking the transport at spawn and the child environment (#1033).
- Resolved-address checks at connect time (#1034).
- Applying the proposal credential denylist to non-proposal writes.

## Acceptance criteria

- **Refused on every write path.** A `connectionConfig` with `{ transport: "http", url: "http://mcp.example.com/mcp" }`, `https://127.0.0.1/mcp`, `https://localhost/mcp`, `https://user:pw@mcp.example.com/` or `https://mcp.example.com:8443/` is refused through each path below with 400 `validation_failed` and `details.field = "connectionConfig"`, and no row is written or changed:
  - REST create and REST `PATCH`;
  - `item.create` and `item.patch` through `createGenericOperationGateway().invoke` with an agent actor;
  - `semprec.item.create` over `/mcp`.

  (integration, `mcpServerConfigWrites.test.ts`)
- **Accepted remote config.** `{ transport: "http", url: "https://mcp.example.com/mcp" }` is accepted through the same paths. A malformed shape is refused the same way as a bad URL. (integration, `mcpServerConfigWrites.test.ts`)
- **Proposals.** A proposal envelope with a non-baseline remote URL is rejected at proposal validation (integration, `mcpServerProposal.test.ts`). Confirming a stored envelope whose URL fails the baseline is refused by the re-run proposal validation with `connectionConfig` (integration, `mcpServerWriteHook.test.ts`).
- **Create hooks run once.** A registered create hook runs once per real insert, inside its transaction: a throwing hook leaves no row. It does not run on an idempotency-key replay. (integration, `mcpServerWriteHook.test.ts`)
- **Out-of-scope writes untouched.** Writes to other databases, and `mcpServers` writes that do not touch `connectionConfig`, are unaffected. A `stdio` config of valid shape is still accepted, as today. (integration, `mcpServerWriteHook.test.ts`)
- **URL rule.** `isBaselineOutboundUrl` accepts and rejects exactly the cases `validateWebPushEndpoint`'s tests cover, and `backend/packages/data/src/push/__tests__/webPushEndpointValidation.unit.test.ts` passes unchanged. (unit, `storedOutboundUrl.unit.test.ts`)
