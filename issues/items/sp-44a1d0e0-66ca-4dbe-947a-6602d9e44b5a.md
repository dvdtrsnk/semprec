### Requirement gh-1467: [agent-usage 05/12] Classify usage units by operation and exclude failed calls from counts

#### Context

Model tier rationale: It changes the semantics of existing counts in a report other screens read, so each change needs targeted tests, but the mechanism is a single query rewrite in one file.

The AI usage report (`backend/packages/data/src/aiGateway/aiUsageReport.ts`, served by `GET /api/ai-usage`) has two accuracy problems today:

- It counts every row with `COUNT(*)`, so a `failed` call (cost 0) is counted as a call, and a `reserved` row (an in-flight call holding an estimate) is counted as a normal one without any hint that its cost is an estimate.
- It decides whether a group is audio or tokens from `audio_seconds IS NOT NULL`. A reserved or failed audio call has `audio_seconds` NULL, so it falls into a token group of a transcription or diarization model, producing a false token row for Whisper or the diarization model.

The operation recorded in `ai_gateway_calls.operation` (migration 0034) tells the truth: `transcription_transcribe` and `transcription_diarize` are audio calls (`services/semprec-ai-gateway/src/audioHandler.ts`); `agent_turn`, `transcript_summary`, `transcript_speaker_suggestion` and `agent_guidance_drift` are token calls. This issue fixes both problems in the existing `rows`; #1472 and #1477 build the per-model and per-operation breakdowns on the corrected data. It follows #1462 because both edit the same file.

#### Task

Load `testing`.

2. Exclude `failed` calls from the `rows` query (`c.status <> 'failed'`), so `callCount` counts only reserved and settled calls. Totals do not change because failed rows cost 0.
3. Within a group, sums are numbers for the group's own unit and null for the other: a token group has `inputTokens`/`outputTokens` as numbers (0 when every call is still reserved) and `audioSeconds` null; an audio group has `audioSeconds` as a number (0 when reserved) and token fields null.

5. Tests: a failed call does not change `callCount`; a reserved transcription call appears in an audio row, never in a token row; a reserved call sets `estimated` true and a range with only settled calls gives false; existing assertions on other fields still pass.

### Requirement gh-1448: [agent-runs 05/21] Chain agent run retries with an attempt number

#### Context

Model tier rationale: One schema change with a tenant-composite key and a unique index, following the existing 0083/0084 pattern, plus a narrow store seam, with no new authorization or concurrency contract of its own.

A failed agent run cannot be tried again as a linked successor. `agent_runs` (`backend/packages/data/src/db/migrations/0001_core_schema.sql` and later) has `parent_run_id` for delegation and `heartbeat_id`, but nothing says "this run is the second attempt of that run". `createAgentRun` in `backend/packages/data/src/agentRuns/agentRunsStore.ts` inserts a root row with no such link, and `AgentRunRow` has no attempt number.

Retrying a failed tick run, and showing a run's retries as one row with "second attempt", both need a chain of attempts: each retry points to the run it retries and carries its attempt number. This issue adds that chain to the data model and a store seam to write and read it. #1458 fills the chain for the queue's automatic attempts, #1908 writes it for a user-requested retry, and #1911 and #1915 use it to decide whether a failure was recovered.

Decision: the chain is linear. A run can be retried at most once, enforced by a unique key, so two concurrent retry requests for the same run create one successor. The link is a tenant-composite reference like the other run references (`agent_runs_parent_run_id_tenant_fkey` in 0083), so a link can never cross tenants.

### Requirement gh-1458: [agent-runs 06/21] Link heartbeat runs to their occurrence and chain queue attempts

#### Context

Model tier rationale: One schema link plus threading two values through the scheduler's fire path and the agent-run action, using the existing occurrence fixtures, where attempts of one job already run one after another on the per-tenant agent-run lane.

A heartbeat occurrence (`heartbeat_occurrences`) is retried by the queue up to `max_attempts` (3) times. `coreAgentRunAction` (`backend/packages/data/src/scheduler/actions.ts`) creates a fresh `agent_runs` row for each attempt of the job, closes a non-final attempt as `error` without a notification, and throws so the next attempt waits in the queue; the `agent_run_error` notification is written only for the last attempt. Nothing connects the runs of one occurrence: the handler context (`ActionContext`) carries `heartbeatId`, `projectItemId`, `itemId`, `triggeredByRunId` and `isFinalAttempt`, but neither the occurrence id nor the attempt number. `runScheduledOccurrenceFire` in `backend/packages/data/src/scheduler/sweep.ts` knows both (`occurrenceId` and `helpers.job.attempts`) and does not pass them on. Runs go through the per-tenant `agent-run` lane, so the attempts of one job never overlap.

With the retry chain from #1448, those automatic attempts can form a chain: attempt 1, 2, 3, each pointing at the run it follows, all tied to the occurrence. That is what lets a run list show a tick that failed twice and succeeded the third time as one row (#1914), and lets #1908 know whether an automatic retry is still pending for a failed run.

Decision: only runs started from a scheduled occurrence are linked. Runs started by a manual fire or an item event have no occurrence (`heartbeat_occurrence_id` stays null) and keep `attempt` 1.

#### Task
