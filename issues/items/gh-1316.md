## Behavior specification

Inbox core: shared prerequisites, cards, capture, type catalog and proposal compute.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: inbox-core-1

#### (a) Decisions adopted from open questions
- inbox_attachment_extraction: require projectItemId, or not like transcript_summary? -> Required (Semprec project). Reason: it runs inside the project-owned tick, like agent_guidance_drift, so cost attribution fits. transcript_event_pick (runs in semprec-transcribe, no project) is registered without a projectItemId, like transcript_summary; the design note text was ambiguous on this one.
- Show a card in computing state in the stack and count? -> Decided by the product owner: a `computing` card is shown in the stack with a compute indication but is not counted until it has a proposal; the user must see that the capture arrived (#1807, #1823, #1811, #1425).
- Order inside a group: capture time (date + time); approval by requested_at; transcript by finish time (Transcripts.date until it exists); then id -> Decided by the product owner.
- No paging: at most 200 cards plus total (ADR no-speculative-generality) -> Decided by the product owner.
- Realtime inboxCards: tenant-wide delivery, userId only narrows; thin message without content.
- #1451: aiProposal backfilled as a copy of proposal; context declared as an opaque json property (shape defined by #1870); reason only for inbox cards; candidates separate from typeCandidates.
- #1425: unknown target module or entity kind falls back to cardKind clarify instead of throwing.
- Approval cards in the list: only source tick or mcp (including delegated runs from a tick), never chat -> Decided by the product owner: approvals from chat are handled in the chat, so they are not shown twice.

#### (b) Open questions remaining for the product owner
- Confirm that transcript_event_pick should not be attributed to a project.
- Package check: semprec-agents has no @semprec/realtime dependency today; #1383 adds it (verify module-boundaries allows it).
- No path problems found: all Touches that do not exist yet are files created by these issues.

#### (c) User-visible behavior of this chunk
Inbox cards of all kinds (new task, page content, file, transcript without an event, speaker question, cannot-be-used proposal, clarification, and approvals from automatic jobs or MCP) are delivered by one server read in a stable group order (approvals, proposals, invalid, clarifications, transcripts), each with its resolved source, localized kind and target labels. Cards whose proposal is still being computed appear in the stack with a computing indication, and cards whose computation failed appear with a Retry action; neither is counted until it has a proposal. A count of open items is available for the header and other surfaces. Changes made by background runs, the transcription process or another device reach every device of the tenant live (stack and count refresh without reloading), because the agents process now publishes realtime messages. Behind the scenes the card store gets the state properties and the gateway the operations that later Inbox features (reasons, recognized types, overrides, compute failures, transcript candidates) build on.

### Decisions: inbox-core-2

#### (a) Decisions adopted from open questions
- Where does a voice note come from (device dictation or server audio)? -> Decided by the product owner: captureChannel `voice` only records how the item was captured; in v1 a voice note is dictated on the device (text), server-side audio comes later with recordings (#1964).
- Separate capture screens later? -> Decided by the product owner: not modeled; captureChannel/sourceApp are plain properties (#1964).
- Capture date/time format -> `YYYY-MM-DD` real calendar date and `HH:mm` 24h; Journal day in the tenant timezone; only creates are validated, edits are not (#1432).
- Capture route body -> text required (non-empty) until attachments exist, typeId must be an active type, 201 with item envelope, Idempotency-Key replays return the original (#1961). captureChannel required on the route, sourceApp max 80 chars, addedAt written only by the capture helper (#1964). Text required until attachments exist -> Decided by the product owner.
- Type lock error codes -> second type edge = cardinality_violation, frozen type after confirmed/rejected = proposal_locked (#1620); locking check reads the card under a row lock (#1669). When the type locks -> Decided by the product owner: once the card is confirmed or rejected; one card, one type.
- Allowed type targets -> explicit constant: ten system databases minus journal and transcripts (#1436), plus mcpServers (#1973); a module added later extends the constant together with a select option and its own cutover. Stored types with journal/transcripts are not migrated; writes reject. -> Decided by the product owner: ten system databases without Journal and Transcripts, plus MCP; a module added later (for example Finance) adds its target by extending the constant together with the select option and its cutover.
- Default catalog -> Idea, Task, Event, Thought, Mood, Note, Contact with the methods/targets in #1977 (Idea/Thought/Mood targets are proposals); once-only seeding via a settings-item marker property; names by the tenant user's locale (cs if none); a default type of a module added later is seeded by that module's own step. -> Decided by the product owner: seven default types, the Idea, Thought and Mood targets are proposals, seeded once per type key in the user's language (Czech by default); a module added later adds its default type once and deleted types are not restored.
- GET /api/inbox-types -> additive processingMethod, targetDatabaseKey, targetLabel (#1439).
- Recognition candidate form (typeId vs target) -> both are accepted: type-id candidates for clarification tiles, direct targets allowed above the threshold with no extra card property (#1500).
- Confidence threshold -> 0.7 as a single constant (#1500) -> Decided by the product owner: below it Semp asks; the threshold is one constant, not a setting.
- Fingerprint of an untyped item -> unchanged (empty emoji), so recognition never loops (#1500).
- Reason -> model text in the user's locale, capped at 500, replaced at every recompute; mechanical writes store null; invalid cards none (#1495).

#### (b) Open questions that remain for the product owner

- May users rename and archive the default types (no HTTP management route exists)?
- Names of default types for a tenant provisioned before its first user exists are Czech (fixed at seeding time).
- #1961 is blocked by #1959 (proposal options route) only because both edit the Inbox manifest and handler file; consider whether that edge is necessary.

#### (c) User-visible behavior of this chunk
Items can be captured through one request that stores text, date, time, optional type, how it was captured and the app it came from; a repeated request does not duplicate it, and every item lands on its Journal day whichever way it was created. A new tenant starts with a ready set of item types (idea, task, event, thought, mood, note, contact) and the capture UI can read what each type does and where it files. Inbox types can only be saved with valid targets, including MCP servers. Once a card is confirmed or rejected, the item's type is frozen and can never have two types. An item without a type is recognized by the assistant: it is proposed directly when the assistant is sure and otherwise asks with two to four type choices, and every card can show a short localized reason.

### Decisions: inbox-core-3

#### (a) Decisions adopted from open questions
- One structured call in semprec-api, or an agent session with tools in semprec-agents? -> One structured call through /internal/complete (operation inbox_proposal, attributed to the Semprec project via ActionContext.projectItemId); web/registry tools stay in agent sessions, except the deterministic ARES lookup (#1989). Reason: design note potreba 1 and 4.
- Show a computeFailed card in the Inbox or only in Semp's status? -> Decided by the product owner: the card is shown in the Inbox with the state "proposal failed" and a Retry action; a capture must never silently disappear. #1485 records the status and history entry, #1807 lists the card and the recompute route (#1955) backs Retry.
- budget_exceeded vs transient failures -> budget_exceeded recorded immediately without throwing; timeout/http/invalid_response throw and are recorded only on the final queue attempt (#1485). The failed card keeps fingerprint null so the next change recomputes.
- Page content target in the first computation -> the model's target is validated afterwards and page candidates arrive with the context (#1987); until then page proposals usually end as needsClarification (#1434).
- Context bounds -> 20 entries per kind, events from capture date -1 day to +14 days, names cut to 100 chars, request budget 900 KiB with a fixed drop order (events, companies, people, areas, projects); sensitive databases contribute nothing without a project grant, not even a count (#1987) -> Decided by the product owner: the context stays bounded; health data is never sent without an explicit project grant.
- Relations -> ids must come from the request's context, one-valued keep one id, many-valued at most 10 (#1488).
- Multi-step -> at most 6 operations, a single operation stays a single-write envelope, all validation by the blocker (#1492) -> Decided by the product owner: at most 6 operations.

#### (b) Open questions that remain for the product owner
- Path assumptions to verify by the implementer: proposalComputation.ts and proposalContext.ts are new files named here and referenced by #1989, #1992, #1993 and #1495/#2; the grant-enforcing read function name comes from #1810.
- #1434 introduces projectItemId and result reason/confidence in inboxTickAction.ts; #1495 adds locale to the same input type (blocked by #1434, so no overlap).

#### (c) User-visible behavior of this chunk
Inbox items now get proposals computed by the assistant: the heartbeat no longer fails, each item gets a card with values filled in from the text, resolving relative dates ("tomorrow at 9") against the time the item was captured in the user's timezone, using the user's existing projects, areas, people, companies and nearby events (but never health data without a grant), linking the record to existing projects/people/companies, and proposing several connected records at once when the text names them. If the computation fails (budget exhausted, or timeouts after three attempts) the card is recorded as failed, shown in the Inbox with a Retry action, and recovers on the next edit or recompute.
