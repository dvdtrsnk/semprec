**Blocked by:** #1955
**Model tier:** medium

## Context

Model tier rationale: One derived read rule in the card read model plus one branch in the existing recompute action, driven by a time constant, with no new storage, lifecycle state or tenant contract; the clock-dependent cases need careful tests.

A proposal card goes to `computing` when the user picks a type (#1947) or asks for a recompute (#1955); the tick then writes `proposed`, or `computeFailed` when the computation fails (#1485). If the tick never finishes (a lost job, a crashed worker), the card stays in `computing` indefinitely and the Inbox list (#1807) shows an endless computing indication. The product owner decided that the computing state has a visible timeout: after it, the card shows an error with a Retry action, because endless spinning is unpredictable. Recording a failed computation on the card stays with #1485; this issue only makes the timeout visible and retryable.

Decision: the timeout is one constant, `COMPUTING_TIMEOUT_MS`, set to 10 minutes; it is not a setting.

Decision: nothing is written when the timeout passes. When `GET /api/inbox/cards` (#1807) builds a card whose stored status is `computing` and whose `updatedAt` is older than the timeout, it returns the card with `status: "computeFailed"` and `computeTimedOut: true`, so the client shows the same "proposal failed" state and Retry action as for a recorded failure. Such a card stays uncounted, like every `computing` and `computeFailed` card. If the tick finishes later, its result replaces the state as usual.

Decision: Retry calls `POST /api/proposals/:id/recompute` (#1955). That route returns a `computing` card unchanged and enqueues no second job; for a card past the timeout it instead proceeds as for any other accepted status: it writes `computing` again (new `updatedAt`), appends a `recompute` history entry and triggers the Inbox tick heartbeat. A card computing within the timeout stays idempotent.

## Task

Load `state-writes` and `testing`.

1. In `backend/packages/data/src/inbox/inboxCardsStore.ts` export the constant `COMPUTING_TIMEOUT_MS` and a pure helper `isComputingTimedOut(card, now)` (stored status `computing` and `updatedAt` older than `now - COMPUTING_TIMEOUT_MS`), and apply it when building each card so a timed-out card is returned as decided above. The count is unchanged.
2. In `recomputeProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) treat a `computing` card for which `isComputingTimedOut` is true as an accepted status (write `computing`, the history entry and the heartbeat trigger) instead of returning it unchanged.
3. Tests with a controlled clock: a card computing for less than the timeout is listed as `computing`; after the timeout it is listed as `computeFailed` with `computeTimedOut: true`, the stored card is unchanged and the count does not include it; recompute on it enqueues one tick job and the card is `computing` again with a new `updatedAt`; recompute within the timeout enqueues nothing; a late tick result turns a timed-out card into `proposed`.

## Scope

### In scope

- Reporting a card stuck in `computing` past the timeout as failed in the card list, and letting recompute retry it.

### Out of scope

- Recording compute failures on the card (#1485).
- A background sweep that stores `computeFailed`; the timeout is applied on read only.
- The type-change route (#1947) and the Retry button in the client.
- Push notifications about failures.

## Acceptance criteria

- Given a card in `computing` whose `updatedAt` is older than `COMPUTING_TIMEOUT_MS`, when `GET /api/inbox/cards` is read, then the card has `status: "computeFailed"` and `computeTimedOut: true`, and the stored card still has status `computing`.
- Given a card in `computing` updated within the timeout, then it is listed with `status: "computing"`.
- When recompute is called on a timed-out card, then the card is `computing` with a new `updatedAt`, its history has a `recompute` entry and exactly one tick job is enqueued.
- When recompute is called on a card computing within the timeout, then the card is returned unchanged and no job is enqueued.
- A timed-out card is not included in `GET /api/inbox/cards/count`.
