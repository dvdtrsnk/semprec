## Context

`runAgentSessionForRun` in `backend/packages/agent-runtime/src/lifecycleAdapter.ts` closes an agent run with two separate writes: `finishAgentRun` (or `finishAgentRunWithErrorNotification` on the error path) flips the `agent_runs` row to its terminal status, then `pushRunStatus` writes the matching `run_status` event. When the caller passes a bare `Pool`, the two writes are not in one transaction, so a poller can observe the row as `done`/`error` before its final `run_status` event has committed. That window made `services/semprec-agents/src/__tests__/agentRun.e2e.test.ts` ("closes the row as error with one agent_run_…") fail once in CI on 2026-09-30 (run 36701706682, PR #845's branch).

PR #845 (issue #737) tried to fix it in passing by reordering the two writes. That was out of #737's scope, and five review rounds on the reordering kept surfacing new partial-failure states: an event committed with the row still `running`, a `done` event followed by an `error` event for the same run when `finishAgentRun` throws after `pushRunStatus(done)` committed, and an events-table failure being reported as a session failure. All of these come from the two writes not being atomic. Reordering them cannot fix that. The change was reverted from #845 and moved here. Its commits (58956ae, 327a705, 137de8d, 49bbea3 on #845's branch) and the review threads on #845 are a useful record of the failure modes a test list has to cover.

## Task

- In `runAgentSessionForRun`, make each terminal close atomic. On the success path, `finishAgentRun(..., "done", ...)` and `pushRunStatus(..., "done")` commit together. On the error path, `finishAgentRunWithErrorNotification` and `pushRunStatus(..., "error")` commit together. When `client` is a bare `Pool`, open one transaction for the pair with the repository's transaction helper (`withTransaction`, `backend/packages/data/src/db/pool.ts`). When the caller already passes a `PoolClient` inside its own transaction, reuse that client as today.
- A failure of the success-path close must not be reported as a session failure that then writes an `error` event on top of a committed `done`. Because the pair is atomic, a failed success close commits neither write, so the error path's close is the only terminal state that lands.
- Write the terminal `run_status` event only when the close actually closed the row: `finishAgentRun` and `finishAgentRunWithErrorNotification` return `false` when the row was no longer `running` (another closer, such as startup repair or a duplicate job, already closed it). On `false`, skip that path's `pushRunStatus`, so a race never yields a second terminal event. `closeUncomposedRun` in `backend/services/semprec-agents/src/agentRunTasks.ts` already does exactly this inside its `withTransaction` (`if (!(await finishAgentRunWithErrorNotification(...))) return;`), covered by the e2e test "writes no error event for a run closed elsewhere before its failed composition closes it" — follow it as the precedent. On the success path a `false` close still returns the row as `getAgentRun` reads it; on the error path it still rethrows the session error.
- Keep the existing `logger.error` for a failed error-path close and keep rethrowing the session error.
- Tests in `backend/packages/agent-runtime/src/__tests__/lifecycleAdapter.test.ts` for every acceptance criterion below. How a test injects a terminal-write failure is the implementer's choice; note that `finishAgentRunWithErrorNotification` branches on `client instanceof Pool`, so whatever the test passes as a bare pool must still be a real `Pool` instance.

## Scope
### In scope
- Making each terminal close in `runAgentSessionForRun` (row status + terminal `run_status` event) atomic on a bare `Pool`, skipping the terminal event when the close returned `false`, and the tests for both.

### Out of scope
- Any change to `runAgentTurn`, `pushRunStatus`'s payload, `finishAgentRun` / `finishAgentRunWithErrorNotification` themselves, or the event consumers.
- `runAgentSession`'s own `createAgentRun` + `running` status write, and `closeUncomposedRun` / `claimRunningRun` in `agentRunTasks.ts`.
- `backend/services/semprec-agents/src/__tests__/agentRun.e2e.test.ts`: it has no retry or wait that only papers over this race, so it is not changed; it must keep passing.

## Acceptance criteria

- With a bare `Pool`, a session that succeeds leaves the row `done` and exactly one terminal `run_status` event (`done`). A session that throws leaves the row `error` and exactly one terminal event (`error`).
- If the terminal `pushRunStatus` fails persistently (every attempt throws, for `done` and `error` alike), the row stays `running` and no terminal `run_status` event is committed: each pair rolled back. A test covers this for a session that succeeds and for a session that throws.
- If `pushRunStatus(..., "done")` fails once, the success pair rolls back, the error-path close then succeeds, and the row ends `error` with exactly one terminal event (`error`) and no `done` event. A test covers this.
- If `finishAgentRun` throws on the success path, no `done` event is committed, and the run ends with exactly one terminal event (`error`). A test covers this.
- If the row is closed elsewhere while the session runs (so the close returns `false`), this session writes no terminal `run_status` event on either path, and the row keeps the status the other closer set. A test covers each path.
- With a caller-supplied `PoolClient` inside the caller's own transaction (`runAgentSessionForRun` for a run row committed beforehand), the caller's `ROLLBACK` leaves the row `running` with no terminal `run_status` event from the session. A new test covers this; no existing test passes a `PoolClient`.
- `pnpm run verify` in `backend/` passes, including `agentRun.e2e.test.ts` unchanged.
