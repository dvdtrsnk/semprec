## Context

Model tier rationale: An agent-callable write on proposal cards with authorization (only the thread's own card), a lock rule, history attribution and realtime invalidation, crossing the Inbox store, agent tools and threads.

An Inbox item thread lets the user talk to Semp about one proposal card ("this is something else", "belongs to another project", "fill in the missing details"). Semp sees the capture and its own proposal, and can revise the proposal. Today:

- `reviseProposalWithClient` and `rejectProposalWithClient` exist in `backend/packages/data/src/inbox/proposalActions.ts` but are not exposed as agent tools. `reviseProposalWithClient` takes a finished envelope and a required `message`, validates the envelope with `assertValidEnvelopeForCard`, refuses a card whose status is locked (`confirmed` or `rejected`), and writes a history entry with author `user` only.
- The `proposal`, `status` and `history` keys are system-owned, so a generic item update cannot write them. The comment in `inboxModuleManifest.ts` that says confirm, reject and revise go through a generic item update is outdated.
- History entries are `{ author: "ai" | "user", message, at }` (`appendHistoryEntry` in `inbox/inboxTickAction.ts`); typed history entries come from #1430.
- The architecture decision that agent writes are proposals allows this: a revision keeps the card a proposal and the target database is written only when the user confirms.

Builds on #1523 (module tools in sessions), #1385 (how module tools are granted and approved), #1870 (the revise route with an optional message), #1471 and #1892 (proposal `aiProposal` upkeep and the values patch validation), and #1620 and #1727 (thread messages and turns). #1938 and #1939 build on this tool.

Decisions:
- The agent composes the whole revised envelope; the tool validates and stores it, and does not compute one.
- The tool may change kind, target, relations and keys the user edited by hand, because the instruction comes from the user; the user-edit rules of #1471 apply.
- The tool never writes to the target database.
- No tool-specific history wording: the entry is `{ author: "ai", kind: "threadRevision", threadId, messageId }` plus the message.

## Task

Load `state-writes`, `error-handling`, `canonical-keys` and `testing`.

1. Add the `inbox.proposal.revise` module agent tool to the Inbox manifest, with strict arguments `{ proposalId, entityKind?, target?, properties, message? }`.
2. The handler revises through the same path as the revise route of #1870, with validation identical to the values patch of #1892. Extend `reviseProposalWithClient` with an `author` parameter (default `user`, unchanged for the route) so the tool writes a history entry `{ author: "ai", kind: "threadRevision", threadId, messageId }`; the thread and message ids are resolved from the persisted run, not from arguments.
3. A card with a locked status yields an error result and leaves the envelope unchanged. An invalid envelope (for example a target outside the allowed databases) yields an error result with no write, like the route.
4. In an item thread the tool works only for the thread's own card; any other card id gives an error result that does not reveal whether it exists.
5. After a successful revision, publish the Inbox card invalidation (as #1811 defines) so the client redraws the card.
6. Return a result for the thread step that states success (the step mapping is the domain of the thread-step issues).
7. Correct the outdated comment in `inboxModuleManifest.ts`.
8. Tests: a revision of an open card changes the envelope and adds an AI history entry; a confirmed card is refused and unchanged; an invalid envelope writes nothing; card B cannot be revised from the thread of card A; the history entry carries thread and message ids; the target database is untouched.

## Scope

### In scope

- The revise tool, its attribution, lock and own-card rules and card invalidation.

### Out of scope

- Reading the card in a thread: #1623.
- Loading the card context into item threads and the user-edit rules for thread revisions: #1938.
- Splitting one Inbox source into several cards: #1939.
- Mapping the tool call to thread steps and changed-item cards, which belong to the thread-history issues.
- Draft and page-block writing tools; the mail and page domains own them.

## Acceptance criteria

- When the thread agent revises an open card, then the envelope is replaced and history gains an entry with author `ai` and kind `threadRevision`.
- When the card is confirmed or rejected, then the tool returns an error and the envelope is unchanged.
- When the envelope is invalid, then the tool returns an error and nothing is written.
- When the thread of card A passes the id of card B, then card B does not change.
- When a revision succeeds, then the card's invalidation is published.
