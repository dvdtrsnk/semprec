## Context

PR #361 introduced `push_subscriptions`
(migration `0031_push_subscriptions.sql`). Its own header comment states a deleted
session is not FK-cascaded away, "just orphaned of its session link" (i.e.
`session_id` becomes `NULL`) — but the column is declared
`session_id uuid REFERENCES sessions(id)` with no `ON DELETE` clause, which defaults
to `NO ACTION`: deleting a session that still has push subscription rows referencing
it would instead fail with a foreign-key violation, not orphan the row as documented.

## Task

Add a new additive migration under `backend/packages/data/src/db/migrations/` (next
free ordinal after the current highest, `0051`) that drops the existing
`push_subscriptions_session_id_fkey` constraint and re-adds it as
`session_id uuid REFERENCES sessions(id) ON DELETE SET NULL`, matching the behavior
the original migration's comment already documents. Leave
`0031_push_subscriptions.sql` itself unchanged — migrations are additive/expand-only,
never edited after merge.

## Touches

- backend/packages/data/src/db/migrations/ (new migration file, next free ordinal)

## Scope

### In scope

- Changing `push_subscriptions.session_id`'s foreign key to `ON DELETE SET NULL`.

### Out of scope

- Any other column or constraint on `push_subscriptions`.
- Building the "future admin purge" feature itself the comment references — only the
  FK behavior it depends on.

## Acceptance criteria

- Deleting a `sessions` row that a `push_subscriptions` row references no longer
  raises a foreign-key violation.
- After that deletion, the referencing `push_subscriptions` row still exists with
  `session_id` set to `NULL`.
- Deleting a `sessions` row with no referencing `push_subscriptions` rows is
  unaffected.
