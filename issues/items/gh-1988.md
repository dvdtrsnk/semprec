**Blocked by:** #1382, #1984, #1986
**Model tier:** high

## Context

Model tier rationale: It adds the first writer of per-project tool grants outside the AGENT page, an authorization boundary that must stay unreachable from agents and that crosses the confirm request, a queue job and the grant tables.

The Inbox card for an MCP server lets the user pick which projects may use the server and whether it is read-only or read and write. The ADR from #1382 decides that a human confirm may set those grants under strict limits (human-supplied selection, only the confirmed server's tools, only `read` and `write` classes, `requires_approval` untouched, nothing reachable from agents). Tools only exist after the first sync, so the selection travels with the sync job that #1976 enqueues after the confirm (`mcpServerSync`, job key `mcp-server-sync-<mcpServerItemId>`), and the job applies it once the sync has registered the tools.

Grants live in `project_mcp_grants` and are written today only by `setProjectMcpGrant` in `backend/packages/data/src/mcp/mcpGrantsAdminStore.ts`, reached from the AGENT page route through `setProjectMcpGrantForAgentPage` in `mcpAgentPageGrants.ts`. The raw store is deliberately not exported from `backend/packages/data/src/index.ts`. Risk classes come from the closed set defined by #1423 (`unclassified`, `read`, `write`, `destructive`, `outbound`, `breaksLink`).

Decision: the confirm request body carries an optional `grants` object `{ level: "read" | "readWrite", projectItemIds: string[] }` next to `credential`. It is never part of the proposal envelope, history, `aiProposal`, `userOverrides` or the computation context.

Decision: if the sync fails, no grant is written; the server item shows `syncStatus: error`, and the user grants tools on the AGENT page after a successful retry (#1972).

Decision: new tools are registered as `unclassified` until #1979 classifies them from the server's tool annotations on sync, so before that issue lands a confirm grants nothing; this is the safe default, and the user grants tools on the AGENT page.

Decision: grants are applied for every active registration of the server that has an allowed class at the moment of the first successful sync. A tool added by a later sync is not granted automatically.


Shared-file ordering: this issue also waits for #1984, #1986 because both edit the same files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `testing` and `adr-conventions`.

1. In `inboxRouteHandlers.ts` parse the optional `grants` field of the confirm body next to `parseConfirmCredential`: `level` must be one of the two values, `projectItemIds` a non-empty array of at most 50 distinct UUIDs. Reject `grants` unless the proposal targets `mcpServers`, with the same kind of validation error as for a stray credential.
2. In `confirmProposalWithClient` verify, inside the confirm transaction, that every project id is an existing live Projects item of the tenant, then pass the validated selection to `enqueueMcpServerSync` (#1976) as an additional payload field. The payload holds only ids and the level.
3. Add `applyConfirmedMcpGrants(client, { mcpServerItemId, projectItemIds, level })` in a new file `backend/packages/data/src/mcp/mcpConfirmGrants.ts` that imports `setProjectMcpGrant` by relative path. It selects the server's active registrations whose `risk_class` is `read` (level `read`) or `read` or `write` (level `readWrite`) and grants each of them to each project in one transaction. It never touches `requires_approval` or `risk_class`. Only `handleMcpServerSyncTask` calls it, after a successful sync. The function is not exported from `index.ts`.
4. Extend `handleMcpServerSyncTask` to apply the selection from its payload after the sync reported `syncStatus: ok`, and to skip it on failure.
5. Tests: with `readWrite` the read and write tools of the server are granted to exactly the chosen projects and a destructive, outbound, breaksLink and unclassified tool is not; with `read` a write tool is not granted; `requires_approval` is unchanged on every registration; a failed sync grants nothing; a project id of another tenant or a trashed project makes the confirm fail and roll back; the grants object is not found in the stored proposal, history or job payload beyond ids and level; no agent tool, `/mcp` operation or run-credential path can call the function (the existing unreachability test for the admin store is extended).

## Scope

### In scope

- Accepting a grant selection on the MCP-server confirm and applying it after the first successful sync, within the ADR's limits.

### Out of scope

- The ADR itself (#1382), the sync route (#1972) and the sync job (#1976).
- Changing risk classes, `requires_approval` defaults, or default classification of tools from annotations (#1979).
- Granting tools discovered by later syncs, and revoking grants.
- Any grant write from agents, `/mcp` or run credentials.

## Acceptance criteria

- When an MCP server card is confirmed with a key, level `readWrite` and two project ids, then after the first successful sync exactly the `read` and `write` tools of the server are granted to those two projects and no other tool or project is granted.
- When the level is `read`, then tools classed `write` are not granted.
- When the sync fails, then no grant exists and the server shows `syncStatus: error`.
- When a project id does not belong to the tenant, then the confirm fails and nothing is created.
- No path from an agent, `/mcp`, a run credential or a proposal envelope can write a grant.
