**Blocked by:** #1434, #1479
**Model tier:** medium

## Context

Model tier rationale: One extension of the computation to emit an ordered list of steps in the shape defined and validated elsewhere, with bounds and reference checks; the multi-step validation itself is delivered by the blocker.

Some captured items need more than one write: a new person at a new company, a task and a note, moving a project to another area. A proposal envelope holds one write today. #1479 defines the multi-step envelope (an ordered list of steps whose kinds, such as create, update and link, and whose references between steps are defined there) and validates it; #1434 builds the computation, #1987 supplies the workspace context with ids and #1488 fills relations of a single write. This issue lets the computation return steps and turns them into a stored multi-step envelope. Detecting that a "new" company or person already exists and replacing the create by a link is #1992.

Decision: the model returns `operations`, an ordered array. Each operation has one of the step kinds #1479 accepts, the target database as a module id, the properties or the existing item id it works on, and an optional local `alias` that later operations use to refer to a record created earlier in the same list. The model may not invent an existing item id: every id must come from the workspace context.

Decision: bounds — at most 6 operations per proposal; more are dropped from the end and the proposal then ends in `needsClarification` through validation if it became inconsistent. A single-operation answer is stored as the ordinary single-write envelope, not as a one-step list, so nothing changes for the common case.

Decision: all validation is the blocker's. This issue only builds the envelope, drops operations with an unknown target database module id or a missing mandatory field, and relies on `assertValidProposalEnvelope` for the rest; a failure goes to the existing `needsClarification` path.

## Scope

### In scope

- Letting the computation return several ordered operations and storing them as a multi-step envelope.

### Out of scope

- The multi-step envelope shape and its validation and confirm (#1479).
- Relations of a single write (#1488) and duplicate detection (#1992).
- Editing or toggling steps on a stored card.
- Proposals that move a project between areas through the card editor.

## Acceptance criteria

- When an item names a new person at a new company, then the stored proposal is a multi-step envelope with the person, the company and the link between them, and it passes envelope validation.
- When the model returns one operation, then the stored envelope is the ordinary single-write one.
- When more than 6 operations are returned, then only the first 6 are kept.
- The computation never writes to a target database or the Inbox.
