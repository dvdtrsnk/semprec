## Context

Model tier rationale: One extension of the computation to emit an ordered list of steps in the shape defined and validated elsewhere, with bounds and reference checks; the multi-step validation itself is delivered by the blocker.

Proposal computation may emit bounded ordered steps; envelope validation and atomic confirm remain owned by their existing contracts.

Decision: the model returns `operations`, an ordered array. Each operation has one of the step kinds #1479 accepts, the target database as a module id, the properties or the existing item id it works on, and an optional local `alias` that later operations use to refer to a record created earlier in the same list. The model may not invent an existing item id: every id must come from the workspace context.

Decision: keep at most the first 6 operations, with existing filtering and envelope checks. Only a sole eligible create into the resolved target is representable as an ordinary single-write envelope; copy its properties and filtered relations, never substitute top-level content for an explicit different operation.

Decision: structural/value validation remains `assertValidProposalEnvelope`'s. Normalize unknown targets/missing mandatory fields as specified; reject invalid membership or nonrepresentable remaining operations to `needsClarification`. No target is written by computation.

Use gh-1488's bounded context foundation; #1987 retains its grant/facts/recompute scope. Enforce matching-database request membership, aliases to eligible creates and existing before-state/graph/transform guards.

## Scope

### In scope

- Letting the computation return several ordered operations and storing them as a multi-step envelope.

### Out of scope

- The multi-step envelope shape and its validation and confirm (#1479).
- Relations of a single write (#1488) and duplicate detection (#1992).
- Editing or toggling steps on a stored card.
- Proposals that move a project between areas through the card editor.

## Acceptance criteria

- When an item names a new person at a new company, then the stored proposal is a multi-step envelope with the person, the company and the link between them, and it passes envelope validation.
- A sole eligible matching create stores an ordinary single-write envelope with its own properties/filtered relations. A sole update/link, wrong-target create, nonempty answer reduced to zero or unrepresentable alias ends in `needsClarification` with no substituted create or target write, even if plausible top-level properties exist. Absent/initially empty operations preserve the normal single-write path.
- When more than 6 operations are returned, then only the first 6 are kept.
- The computation never writes to a target database or the Inbox.
- A valid computed multi-step update stores server before/matching after values and confirms through the existing guards; a target change after formation refuses confirm without partial writes. Tests cover changed relations, deterministic transform additions, deferred pin order without prediction or preflight allocation, unsupported targets/preparation and repeated-item rejection. Baselines never leave for the model or refresh at confirm.
