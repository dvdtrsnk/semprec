## Approved behavior specification

This epic preserves the complete approved behavior of source issue #67, inlined here so the epic is self-contained.

### Source behavior: [tasks-time-fix 01/01] Compute derived tasks.time from timeFrom/timeTo

## Context

Issue #24 ("Ten hardcoded databases") defined the Tasks database's `time`
property as derived, `owner: system`, `locked: true`, composed from the
`timeFrom`/`timeTo` properties. The property was correctly declared and
correctly locked against direct edits (the choke-point rejects writes to it),
but no code was ever added to actually compute and store its value — it is
schema-correct but functionally dead: every task's `time` reads as unset,
regardless of `timeFrom`/`timeTo`.

This issue closes that gap. It does not change the schema from #24, only adds
the missing derivation logic.

## Task

Whenever a Tasks item's `timeFrom` and/or `timeTo` property is written (via
the choke-point's generic property-write path — the same path issue #24's
`assertWritableProperties` guard already protects `time` from), recompute and
store `time` as a derived value in the same write, following the pattern
already used elsewhere in the choke-point for other `owner: system` derived
properties.

Value format (24-hour, zero-padded `HH:MM`):
- both `timeFrom` and `timeTo` set: `"HH:MM–HH:MM"` (en dash, e.g. `"09:00–10:30"`)
- only `timeFrom` set: `"HH:MM"` (e.g. `"09:00"`)
- only `timeTo` set: `"HH:MM"` (the `timeTo` value alone)
- neither set: `time` is `null`

The recompute must happen atomically with the `timeFrom`/`timeTo` write (same
transaction) — there must be no window where `timeFrom`/`timeTo` and `time`
are inconsistent with each other for a readable row.

## Scope

### In scope
- The derivation function (pure: `(timeFrom, timeTo) -> string | null`).
- Wiring it into the choke-point's Tasks item write path so `time` is
  recomputed on every write that touches `timeFrom` or `timeTo`, in the same
  transaction.
- A migration/backfill for any existing Tasks rows seeded by #24 that already
  have `timeFrom`/`timeTo` set but a stale/unset `time`.

### Out of scope
- Changing the `time` property's type, ownership, or lock status (unchanged
  from #24).
- Any UI/display formatting beyond the stored string value itself.
- Localizing the format (the stored value is a canonical machine value, not a
  user-facing label — same rule as every other canonical key in #24).

## Acceptance criteria

- Creating a Tasks item with both `timeFrom` and `timeTo` set results in
  `time` equal to the `"HH:MM–HH:MM"` string.
- Updating only `timeFrom` on an existing item (leaving `timeTo` unset)
  recomputes `time` to just the `timeFrom` value.
- Clearing both `timeFrom` and `timeTo` sets `time` back to `null`.
- Attempting to write `time` directly is still rejected exactly as before
  (this issue does not relax that guard).
- A test exercises all four branches above (both set / timeFrom only / timeTo
  only / neither).

## Decisions

- **Question:** Which boundary is load-bearing? **Adopted answer:** Store a canonical string from timeFrom/timeTo. **Reason:** It preserves approved source behavior.
- **Question:** Which boundary is load-bearing? **Adopted answer:** Recompute in the same transaction and retain direct-write lock. **Reason:** It preserves approved source behavior.
