### Requirement gh-1904: [trash 06/06] Restore trashed items and databases in bulk

#### Context

Model tier rationale: A multi-id restore in one transaction with a savepoint per id, where a rolled-back id must also discard the after-commit realtime announcements it queued and a restore hook's rejection must not abort the others; this is transaction and cleanup-ownership logic that is easy to get subtly wrong.

Restoring is a single-item operation today. `POST /api/items/:id/restore` brings an item and the part of its cascade that was trashed with it back, idempotently (`restoreItemWithClient` in `backend/packages/data/src/chokePoint/itemTrash.ts`, which is not exported), and answers `403 database_archived` for an item of an archived database. `POST /api/databases/:id/restore` clears `archived_at` (`databasesStore.restoreDatabase`, announced as a schema change by the choke point's database operations). The "Recently deleted" screen lets the user select several rows of one tab (items or databases) and restore them together; a client can call the single routes in a loop, which works, but is slow, not atomic in its announcements and cannot tell "this one was refused" from "this one failed".

This issue adds `POST /api/trash/restore`, a custom route of the schemaCore module. Each id is restored in its own savepoint inside one transaction: one id's refusal rolls back only that id and the others still restore. A refusal that matters in practice is a restore hook rejecting an item, for example a Journal day whose period already has a live entry (#1601 introduces the item restore hook that can reject; the Journal rule that uses it is #1603). It lists archived databases for the client's selection through #1873 and trashed items through #1851.

Decisions:

- The body is `{ itemIds: uuid[], databaseIds: uuid[] }`, at most 100 ids in total (duplicates merged), at least one; a mixed body is accepted (a client sends one tab's ids). Databases are restored first, then items, so items of a just-restored database restore in the same call.
- Result per id: `restored` (also for an item that was not trashed: restore is idempotent), `not_found` (unknown id, or another tenant's id: the same status), `database_archived` (an item whose database is archived), `conflict` (restore rejected with `409`). Any other failure is not caught per id: it aborts the request with its normal error, because it means a defect, not a refusal.
- The response is `200 { results: [{ id, kind: "item" | "database", status }] }` in request order (databases first), even when every id was refused.

### Requirement gh-1908: [agent-runs 17/21] Retry a failed heartbeat run from the API

#### Context

Model tier rationale: This adds a mutating endpoint whose correctness depends on concurrent-request deduplication, queue-job semantics, chain-uniqueness handling and tenant isolation, plus new entries in the closed error contract, so the higher tier is chosen.

A failed scheduled run of a user's automatic task ("tick") cannot be retried. `backend/services/semprec-api/src/agentRunHandler.ts` serves only `GET /api/agent-runs/:id` and `POST /api/agent-runs/mcp-credentials`. The only way to re-run a heartbeat is the manual trigger (`heartbeat.trigger` in `backend/packages/data/src/scheduler/heartbeatAgentTools.ts` and the HTTP trigger from #1453), which is a fresh manual run, not a retry of a given failed run, and it leaves no link between the two.

With the retry chain (#1448) and the occurrence link (#1458) a retry can be precise: the user asks to retry one failed run, and the system starts one new run of the same heartbeat that points back at it with the next attempt number. Whether a run counts as failed, including the case of a reply that finished but left a failed tool call, comes from the shared display status (#1820, extended by #1890). Closing the problem that the original failure raised is done by #1915 when the retry succeeds. Retrying a Semp chat reply is a different mechanism (#1926).

The scheduler's fire task (`createHeartbeatFireTaskForAffinity` in `backend/packages/data/src/scheduler/sweep.ts`) requires exactly one payload discriminator out of `occurrenceId`, `itemId` and `triggeredByRunId`. `ActionContext` and `coreAgentRunAction` (`scheduler/actions.ts`) create the run row inside the worker, per job attempt; a `running` row must never be created ahead of the worker, because startup repair closes every `running` run after a restart, and no `queued` status is added because the web client reads the status as the closed enum `running | done | error`. The closed error contract `ITEM_ERROR_CODES` in `backend/services/semprec-api/src/adapter/errorContract.ts` has no code for retry refusals.

Decisions (decided by the product owner):
- Scheduled tick runs get both: the automatic chain of attempts (#1458), and after the chain has failed, a manual retry from the run detail through this endpoint.
- Only a run that belongs to a scheduled occurrence can be retried. A run started by a manual fire or an item event has no occurrence, so its remaining automatic attempts cannot be seen from the run; it answers `not_retryable` and is not retried. (The person can still start the automation anew with the manual trigger of #1453; that is a new run, not a retry.)
- The retry job is enqueued with a single attempt (`maxAttempts` 1), so a failed retry is a final failure with its notification and can be retried again by the user, instead of silently extending the chain by automatic attempts.
- The two refusals have distinct codes: `retry_pending` means "an automatic attempt may still run, try later", `not_retryable` means "this run can never be retried".

Shared-file ordering: this issue also waits for #1904 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

It validates the id with `assertUuid`, loads the run (a run of another tenant does not exist under row-level security and answers 404 like any unknown id), and decides in this order:

### Requirement gh-1914: [agent-runs 19/21] Collapse retried heartbeat attempts into one row

#### Context

Model tier rationale: A single read-side collapse rule inside an existing list query, with a cost sum and a per-attempt breakdown over the same rows, depending on the retry-chain columns from a blocker; the main risk is correct selection of the latest attempt and correct grouping of costs, which existing fixtures can verify.
