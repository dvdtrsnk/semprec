## Behavior specification

Mail accounts: transports, live sync, OAuth and password accounts, sync state.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: mail-accounts-1

#### Adopted decisions
- Mail server settings: table with host, port, security, username; host DNS name only, ports 993/143/465/587; explicit-port exception recorded in a new ADR; password stays in `external_credentials`.
- IMAP/SMTP connect safety: resolve once through the outbound policy lookup, connect to the vetted address, keep the original host as TLS servername; a refused address returns the same error as an unreachable server (`mail_server_unreachable`) so routes cannot scan the network; the connect-time ADR's known gap gets an appended note.
- OAuth token rotation: new refresh token persisted in the same tenant scope before the new access token is used, refreshes of one mailbox serialized; a persist failure fails the refresh loudly.
- Missing provider configuration (OAuth client, Pub/Sub keys, https `APP_BASE_URL`): process still starts, the feature is not hosted, one warning is logged, accounts fall back to the periodic sweep.
- Custom route dependencies: factory signature becomes `(pool, dependencies)`; the live-sync member is late-bound because the root is created after the dispatcher.
- Lifecycle hosting is a dispatcher by sync mode; an unhosted mode keeps the noop lifecycle.
- Gmail Pub/Sub: three env keys in one group of `api.env.example`; service account JWT signed with `node:crypto`; routing address is the provider-verified one; dispatcher stops before the pool.
- Graph `notificationUrl` = `APP_BASE_URL` + `/api/mail/graph/webhook`, hosted only for an https origin.

#### Open questions for the product owner
- None blocking. Operational (not planned yet): provisioning the GCP Pub/Sub topic, subscription and service account, and the OAuth client credentials on hosts.
- The ADR for the standard mail ports and the append to the connect-time ADR are decisions the maintainers should confirm.

#### User-visible behavior
Mailboxes of every kind finally synchronize on the server: Gmail and Outlook accounts through their APIs (with Microsoft's rotating refresh tokens kept valid), and iCloud or other IMAP accounts through the server settings the user entered. New mail shows up without manual refresh: IMAP via IDLE, Gmail via Pub/Sub push, Outlook via webhook subscriptions; when push is not configured the periodic sweep still syncs everything. A mailbox pointing at an internal or loopback address cannot be connected and looks like any other unreachable server.


### Decisions: mail-accounts-2

#### Adopted from open questions
- iOS return from OAuth (universal link vs custom URL scheme) -> server contract is a single configured redirect URI, public callback writes nothing and forwards code+state; native hand-off left to the app -> keeps the server independent of the choice.
- "Outlook.com" label in the design -> not a backend matter; backend names the mailbox `Outlook` and supports both personal and Entra ID accounts via `/common`.
- State consumed before the provider exchange -> single use even on provider failure -> a retried or replayed code cannot be reused.
- Duplicate address with an existing mailbox on OAuth -> 409 naming the mailbox, so the app can offer reauthorization (#1742); on password accounts -> 409 and nothing created. -> Decided by the product owner: 409 and nothing is created.
- Existing non-Gmail mailboxes have null `provider_account_address` after the migration -> null never blocks; filled on next connect/reauth.
- Throttle counts every attempt that reaches the network, not only failures -> prevents using the route as a password oracle.

#### Open questions for the product owner
- iOS return from OAuth: universal link or custom URL scheme (affects the redirect URI configured per provider).
- Should the design label "Outlook.com" become "Outlook / Microsoft 365"?
- Should reconnecting an existing password mailbox (changed password) be a separate flow? Not planned here.

#### User-visible behavior
A user can add a Google or Microsoft mailbox by signing in at the provider (consent window limited to reading, triaging, drafting and sending mail); the mailbox appears with the address reported by the provider, named Gmail or Outlook, and its mail starts downloading. Signing in again with an address that is already connected does not create a second mailbox; a cancelled or failed sign-in or an expired or foreign link creates nothing, and a Microsoft work account that needs administrator approval gets a specific error. A user can also add an iCloud or generic IMAP mailbox with address and password: the server tries secure ports only, verifies the login for IMAP and SMTP before saving, gives specific errors (wrong password, iCloud app password needed, server unreachable, no TLS), stores the password encrypted, and starts downloading. Repeated attempts are limited to 10 per 15 minutes per user. The mailbox address can no longer be edited through generic item writes or by an agent.


### Decisions: mail-accounts-3

#### Adopted from open questions
- Hide the connection limit for Gmail API and Graph mailboxes (design note leaned yes) -> the API returns `connectionLimit.applies = false` for non-IMAP sync modes and the client hides it -> the limit only governs IMAP. -> Decided by the product owner: the limit applies only to IMAP.
- Revocation versus expiry cannot be told apart (both `invalid_grant`) -> a single `reauthorization` reason -> avoids a false distinction in banner text. -> Decided by the product owner: one reason, "sign-in needed".
- `syncStatus` `never` -> derived when serving (property missing and initial sync not completed); the sync job stays the only writer.
- `syncStatus` is written only on change -> avoids an item update and realtime event on every pass.
- Existing accounts at migration time -> backfill last success and initial sync from `last_activity_at` where there is no error; failing accounts get `failing_since` and kind `other`.
- Problem severity: `needsReauthorization` critical; other failures use the lowest problem level for background failures (#1506). -> Decided by the product owner: loss of access is critical, every other failure uses the lowest level.
- Restore of a removed mailbox -> restore hook recreates a default sync state, `syncStatus` `needsReauthorization`; reauthorization accepts the signing-in address when the stored provider address is null and no other mailbox holds it. -> Decided by the product owner: as drafted.
- Generic `DELETE` of a Mailboxes item answers 403 (design note proposed).
- `connectionLimit` null/unset is valid (provider default); otherwise integer 1-15.
- Removal impact counts: threads counted only when all their non-deleted messages belong to the mailbox; Files from attachments are kept. -> Decided by the product owner: threads only when all their messages belong to the mailbox; files stay.
- One issue = one mechanism (product owner): mailbox removal is split into the removal route and transaction (#1690) and sibling issues for the chunked soft-delete of folders and messages (#2029), the best-effort provider cleanup after commit (#2030), the refusal of a generic delete (#2031), and the restore hook (#2032).

#### Open questions for the product owner
- The administrator health report and the observability check detail still carry the provider error text; the design note only requires mail routes and notifications to be free of it. Should they be changed too (not planned yet)?
- Path note: `/api/mail/summary` named in the design note does not exist on develop; no issue touches it.

#### User-visible behavior
Each mailbox shows a stable sync status: OK, syncing for the first time, failing since a given time (with one reason: sign-in needed, too many connections, or other) and the time of the last successful sync, which no longer moves when a sync fails. The mailbox list and detail come from one endpoint, including the effective connection limit (shown only for IMAP accounts), restricted to 1-15. A failing mailbox is reported as one Semp problem that merges repeated reports and resolves when sync recovers, and notifications never carry provider error text. A user can sign in again for an expired Google or Microsoft mailbox (a different account is refused) and mail resumes within a minute. Before removing a mailbox the app can show how many messages, drafts and threads are affected; removal deletes credentials and sync state immediately, moves the mailbox's folders and messages to the trash, stops its sync, revokes access at the provider where possible, and a restored mailbox needs signing in again. Permanent deletion leaves no mail rows behind.
