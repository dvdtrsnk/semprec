## Context

Model tier rationale: A single response shape is added across three read paths (item get, database query, view query) with a constant-query-count guarantee, bounded fan-out limits, one nested level and tenant and archive filtering, so a mistake leaks data or turns a page read into N+1 queries.

Every screen that shows an item's links (a person's companies and projects, a project's area as a colored label, a movie's "watched with" people) currently needs one edge read per item and one item read per target. `GET /api/items/:id` returns only the stored envelope (`itemEnvelope.ts`), with `?include=path` and `?include=links` already supported; `item.get`, `database.query` and `view.query` already accept `include: ["links"]` from #1403 to attach value links. Relation target expansion is not yet available. #1404 adds the edge read; this issue adds the one inline expansion that all callers use, so clients render a list of 50 projects with their area labels in one request.

It also builds on #1412, which exposes blob metadata for file and image properties; projected file or image properties of a target return that metadata. Later issues (#1595, #1842, #1771) reuse the expansion.

Decisions (conservative defaults):
- Colour and icon of full and reduced nested targets are resolved independently without a projection request: a non-empty string in the target item's schema-defined `color` (type `color`) or `icon` (type `text`) property takes precedence over the collection metadata resolved in Task 4; omit each field if no value resolves.
- Only one nested level exists: when a projected key of a target is itself a relation (a project's area), it returns a reduced `[{ id, databaseKey, title, color?, icon? }]` and is never expanded further.
- Archived-database targets are excluded exactly like deleted targets. Decided by the product owner: archiving a database behaves as the trash everywhere, so expansion and reads omit its items.
- Unknown relation keys in `include` fail the whole request with `400` rather than being silently ignored.

Shared-file ordering: this issue also waits for #1509 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys`, `io-hardening`, `error-handling` and `testing`.

1. Define the expansion contract in `shared/genericOperations`: an optional `include` input on `item.get`, `database.query` and `view.query` accepting the existing array form (`[]` or `["links"]`) or a strict object `{ links?: boolean, relations?: { <propertyKey>: string[] } }`; `links: true` requests the existing value links, while false or omission does not, and both fields may be supplied together. An omitted `relations` field requests no expansion; an empty relations map selects no keys. The relations map carries the projections (an empty array means expand the key with no projected properties). Define an output `relations: { [propertyKey]: ExpandedRelationTarget[] }` plus `relationsTruncated: string[]` on each returned item. `ExpandedRelationTarget` is `{ id, databaseId, databaseKey, title, color?, icon?, metadata, properties?, blobs? }`. For projected file and image properties, `blobs` is a top-level field on each expanded target, alongside `properties`, with shape `Record<propertyKey, { blobId: string, byteSize: number, mimeType: string, filename: string | null }>` as in #1412 and `ItemEnvelope`. Only projected file/image keys with visible blob metadata appear; omit `blobs` when none qualify. Keep the projected property values unchanged; do not add per-property blob arrays.
2. REST: `?include=relations` on `GET /api/items/:id`, combinable with the existing `path` and `links` tokens (`?include=path,links,relations`); projections via `relations.<propertyKey>=name,date` query parameters. `database.query` / `view.query` bodies accept both Task 1 include forms, including `include: { links: true, relations: { <key>: [propertyKeys] } }`. `?include=relations` without any `relations.<propertyKey>` parameters selects every relation key of the item's database with no extra properties, then applies the 5-key cap: more than 5 keys fails the whole request with `400 validation_failed`, `field: "include.relations"`, even if some keys have no targets. Never choose a subset or exempt a database. When such parameters are present, expand only their named keys; `relations.<propertyKey>=` selects that key with no projected properties, allowing callers to select at most 5 keys explicitly.
3. Limits, enforced in the schema and in the read: at most 5 relation keys per request, at most 10 projected properties per key, at most 50 targets per item and key. Targets are ordered by edge id, or by `metadata.addedAt` when the edge carries it. When more than 50 live targets exist the first 50 are returned and the key is listed in `relationsTruncated`. An unknown relation key, an unknown projected property, or an exceeded limit is `400 validation_failed` with the offending `field`.
4. Implement the expansion as one batched read module in the data package: for a page of item ids, one query for the edges of all requested relation properties, one for the target items grouped by target database, one for the target databases (key, system, color, icon), and, only when a projected key is a relation, one for its reduced targets. The number of SQL statements must not depend on the number of items or targets on the page. Edges to soft-deleted targets and to targets in archived databases are dropped before the per-key limit is applied. For both full and reduced nested targets, apply the per-item precedence above, then use the existing `CollectionMetadataResolver`: system databases use their module manifest descriptor (not stored icon/color columns); non-system databases use their non-null stored value, otherwise the existing defaults `database` for icon and `#FF9500` for color. A missing system descriptor or missing descriptor field supplies no fallback value. The caller supplies the resolver, built with `createCollectionMetadataResolver` from the loaded module registry, through the application/read facade into the expansion; REST handlers and generic-operation composition roots must supply the same resolution behavior. The expansion store does not load manifests or a registry itself. Resolve metadata in memory without per-target SQL. Omit unresolved `color` and `icon` fields independently, never emit null for them. Expansion is read-only: do not persist resolved metadata, update system database columns, or add any database write.
5. Run the expansion inside the same tenant scope as the surrounding read (`runInTenant`); a target outside the caller's tenant can never appear. Wire the module into `item.get`, `database.query` and `view.query` in `genericApplicationService.ts` and the REST adapters.
6. Tests: integration tests for the person example (a company and a project with the project's area label nested), the 51st target producing `relationsTruncated`, a query-count assertion for a page of 50 items (the statement count equals the count for 1 item), deleted and archived targets, a one-directional relation, `400` cases, blobs on a projected file property, and tenant isolation.

## Scope

### In scope

- The shared include contract, limits and output shape; the batched expansion module; wiring into `item.get`, `database.query` and `view.query` over REST, MCP and the agent tools.

### Out of scope

- The edge read operation itself: #1404.
- Derived values such as an item's area through its projects: #1595.
- Grouped search results: #1842.
- Expansion deeper than one level, and expansion in any other operation.

## Acceptance criteria

- When a person is fetched with `include=relations` and a projection of the project's area, then the response lists the person's companies and projects with title, colour and icon, and each project carries its area as a reduced target. Both target shapes follow Task 4: an Area item's own color/icon and a Project item's own color override collection metadata even without projection; absent item values fall back to manifest values for system databases or stored/default values for non-system databases. Unresolved fields are omitted independently (not null), all three read paths agree, and expansion performs no database writes.
- When a key has 51 live targets, then 50 are returned in order and the key is listed in `relationsTruncated`.
- When 50 items are queried with `include=relations`, then the number of SQL statements equals that of querying one item.
- When a target is deleted or in an archived database, then it is absent and does not consume the 50-target limit.
- When a request names an unknown key or exceeds 5 keys or 10 projected properties, then it fails with `400` naming the field. This includes a bare REST `include=relations` on a database with more than 5 relation keys (`field: "include.relations"`); explicit selection of at most 5 keys remains valid.
- When a projected property is a file or image, then its unchanged value is in `properties` and its visible blob metadata is in the expanded target's top-level `blobs[propertyKey]` map entry with `blobId`, numeric `byteSize`, `mimeType` and nullable `filename`; no per-property blob array is added, and `blobs` is omitted when empty.
- Existing `include: []` and `include: ["links"]` requests remain valid on all three operations; `{ links: true }` returns the same links, and `{ links: true, relations: { <key>: [] } }` returns both. REST `include=path,links,relations` preserves path and links alongside the selected relation expansion.
- When the caller belongs to another tenant, then no foreign target appears.
