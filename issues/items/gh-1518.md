## Context

Model tier rationale: A single response shape is added across three read paths (item get, database query, view query) with a constant-query-count guarantee, bounded fan-out limits, one nested level and tenant and archive filtering, so a mistake leaks data or turns a page read into N+1 queries.

Every screen that shows an item's links (a person's companies and projects, a project's area as a colored label, a movie's "watched with" people) currently needs one edge read per item and one item read per target. `GET /api/items/:id` returns only the stored envelope (`itemEnvelope.ts`), with `?include=path` as the single supported include, and `database.query` / `view.query` return `{ items, nextCursor }` with no link data at all. #1404 adds the edge read; this issue adds the one inline expansion that all callers use, so clients render a list of 50 projects with their area labels in one request.

It also builds on #1412, which exposes blob metadata for file and image properties; projected file or image properties of a target return that metadata. Later issues (#1595, #1842, #1771) reuse the expansion.

Decisions (conservative defaults):
- Colour and icon of a target are returned whenever the target's database defines them, without any projection request.
- Only one nested level exists: when a projected key of a target is itself a relation (a project's area), it returns a reduced `[{ id, databaseKey, title, color, icon }]` and is never expanded further.
- Archived-database targets are excluded exactly like deleted targets. Decided by the product owner: archiving a database behaves as the trash everywhere, so expansion and reads omit its items.
- Unknown relation keys in `include` fail the whole request with `400` rather than being silently ignored.

Shared-file ordering: this issue also waits for #1509 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys`, `io-hardening`, `error-handling` and `testing`.

1. Define the expansion contract in `shared/genericOperations`: an `include` input on `item.get`, `database.query` and `view.query` carrying `{ relations: { <propertyKey>: string[] } }` (an empty array means expand the key with no projected properties), and an output `relations: { [propertyKey]: ExpandedRelationTarget[] }` plus `relationsTruncated: string[]` on each returned item. `ExpandedRelationTarget` is `{ id, databaseId, databaseKey, title, color?, icon?, metadata, properties?, blobs? }`. As in #1412 and the existing gh-1518 decision, `blobs` is an optional top-level map keyed by projected file/image property key, with `{ blobId: string, byteSize: number, mimeType: string, filename: string | null }` metadata for visible blobs only. Omit an empty map; keep projected property values unchanged. Do not add per-property blob arrays.
2. REST: `?include=relations` on `GET /api/items/:id`, combinable with `path` (`?include=path,relations`); projections via `relations.<propertyKey>=name,date` query parameters. `database.query` / `view.query` bodies take `include: { relations: { <key>: [propertyKeys] } }`. `?include=relations` without any projection expands every relation key of the item's database with no extra properties.
3. Limits, enforced in the schema and in the read: at most 5 relation keys per request, at most 10 projected properties per key, at most 50 targets per item and key. Targets are ordered by edge id, or by `metadata.addedAt` when the edge carries it. When more than 50 live targets exist the first 50 are returned and the key is listed in `relationsTruncated`. An unknown relation key, an unknown projected property, or an exceeded limit is `400 validation_failed` with the offending `field`.
4. Implement the expansion as one batched read module in the data package: for a page of item ids, one query for the edges of all requested relation properties, one for the target items grouped by target database, one for the target databases (key, color, icon), and, only when a projected key is a relation, one for its reduced targets. The number of SQL statements must not depend on the number of items or targets on the page. Edges to soft-deleted targets and to targets in archived databases are dropped before the per-key limit is applied.
5. Run the expansion inside the same tenant scope as the surrounding read (`runInTenant`); a target outside the caller's tenant can never appear. Wire the module into `item.get`, `database.query` and `view.query` in `genericApplicationService.ts` and the REST adapters.
6. Tests: integration tests for the person example (a company and a project with the project's area label nested), the 51st target producing `relationsTruncated`, a query-count assertion for a page of 50 items (the statement count equals the count for 1 item), deleted and archived targets, a one-directional relation, `400` cases, blobs on a projected file property, and tenant isolation.

## Acceptance criteria

- When a person is fetched with `include=relations` and a projection of the project's area, then the response lists the person's companies and projects with title, colour and icon, and each project carries its area as a reduced target.
- When a key has 51 live targets, then 50 are returned in order and the key is listed in `relationsTruncated`.
- When 50 items are queried with `include=relations`, then the number of SQL statements equals that of querying one item.
- When a target is deleted or in an archived database, then it is absent and does not consume the 50-target limit.
- When a request names an unknown key or exceeds 5 keys or 10 projected properties, then it fails with `400` naming the field.
- When a projected property is a file or image with visible blob metadata, its unchanged value is in `properties` and metadata is in top-level `blobs[propertyKey]` with numeric `byteSize` and nullable `filename`; no per-property array is added, unprojected/invisible blobs are absent, and an empty map is omitted.
- When the caller belongs to another tenant, then no foreign target appears.
