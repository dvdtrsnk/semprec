## Context

Model tier rationale: A pair of human-only REST routes over the grants store from the previous issue, following an existing custom-route and admin-store pattern, with a clear authorization rule that agents cannot reach the write.

#1810 adds `agent_database_grants` and enforces them. The user needs a way to see and change what the Semp agent of a project may read and write. Today the equivalent for tools is `GET /api/projects/:id/mcp-grants` and `PATCH /api/projects/:id/mcp-grants/:grantId` (`services/semprec-api/src/mcpAgentPageHandler.ts`), which reach the user-only mutations through wrappers so the package barrel never exposes them to agent code. Module-declared routes are registered through `customRoutes` in a module manifest (ADR `2026-09-11-module-manifest-custom-routes`; examples in `chokePoint/schemaCoreModuleManifest.ts` with handlers re-exported from the manifest file).

Decisions:
- `GET /api/projects/:id/database-grants` lists every database a grant can matter for: the sensitive databases and the user-created ones, each with `databaseId`, `key`, `name`, `sensitive`, `system` and the project's current `access` (`none`, `read` or `write`). Without a stored row the access is `none` for a sensitive database and `write` for a user-created one (#1810). Non-sensitive system databases are not listed, because they are always open.
- The list backs the client's collection list in the project's Semp settings (Collections), with one "Semp may read" toggle per collection; sensitive collections are off by default (decided by the product owner).
- `PATCH /api/projects/:id/database-grants` takes `{ databaseId, access }` with access `none`, `read` or `write`. Setting the database's default access (`none` for a sensitive database, `write` for a user-created one) removes the stored row; any other value is stored. A database that is not listed (an open system database) is rejected with 400.
- Both routes need an authenticated user session. An agent run credential cannot reach them.
- The project must exist and not be in the trash, else 404.

Shared-file ordering: this issue also waits for #1839 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `io-hardening`, `error-handling` and `testing`.

1. Add the admin write functions (`setAgentDatabaseGrant`, `removeAgentDatabaseGrant`) in a store file that is not exported from the package barrel, plus a wrapper exported for the route handlers only, as `mcpAgentPageGrants.ts` does.
2. Add `createListAgentDatabaseGrantsRouteHandler` and `createPatchAgentDatabaseGrantRouteHandler` (strict zod body, UUID path parameter, closed access values) and declare both as `customRoutes` in `chokePoint/schemaCoreModuleManifest.ts` with the justification `single-consumer-read` for the read and `transactional-semantics` for the write, re-exporting the handlers from that file.
3. Register both routes in the route matrix and the tenant isolation test.
4. Tests: list shows sensitive and user-created databases with the right access (a sensitive database without a row as `none`, a user-created database without a row as `write`); patch to `read`, `write` and `none` changes the enforcement of #1810 on the next agent call; an open system database is rejected; an unknown or trashed project is 404; another tenant's project is 404; an unauthenticated request is refused; an agent run credential cannot call either route.

## Scope

### In scope

- The two routes, the admin store and wrapper, manifest registration and tests.

### Out of scope

- The grants table, the check and its enforcement: #1810.
- The client screen (the collection list with a "Semp may read" toggle per collection); its design is delivered by the product owner.
- Grants for module tools or MCP tools, which have their own mechanism.

## Acceptance criteria

- When the user patches a sensitive database to `write` for a project, then that project's agent can write to it; patching to `none` removes the access again.
- When the list is read, then it contains only sensitive and user-created databases with the project's current access; a sensitive database without a row shows `none` and a user-created database without a row shows `write`.
- When the user patches a user-created database to `none` for a project, then that project's agent can no longer read it; patching it back to `write` removes the stored row.
- When an agent run credential calls either route, then the request is refused.
- When the project belongs to another tenant, then the response is 404.
