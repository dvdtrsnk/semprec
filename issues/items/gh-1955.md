## Context

Model tier rationale: A custom route that follows the lock, version check and tick-trigger pattern already built for the type-change route, with the merge behavior owned by the blocker, so only the route's own status and kind rules are new.

Sometimes the assistant's proposal is out of date or wrong in a way the source text does not show (a thread instruction, a failed computation, changed context): the product needs a way to ask for a fresh computation of an existing Inbox card without touching its source. The tick only recomputes when the source fingerprint changes. #1947 introduced the transient card status `computing` and made the tick bypass its fingerprint gate for a card in that status; #1921 made the tick's recompute keep user-edited keys; #1434 provides the tick.

This issue adds `POST /api/proposals/:id/recompute { ifVersion? }`, a custom route (justification `transactional-semantics`: status change and job trigger commit together) only for cards of `kind: inbox`.

Decision: a `kind: transcript` card returns 400 (`ValidationError` on `kind`); transcript cards are recomputed from a user instruction by a separate route. Locked cards (`confirmed`, `rejected`) answer 409 `proposal_locked`; an `invalid` card whose `invalidReason.code` is `sourceDeleted` answers a `ValidationError`; any other status is accepted. A card already `computing` is returned unchanged (idempotent, no second job). The history entry has `kind: "recompute"` and `author: "user"`.

## Scope

### In scope

- `POST /api/proposals/:id/recompute` for `kind: inbox` cards, status `computing`, tick trigger.

### Out of scope

- The tick's gate bypass and the type-change route (#1947).
- Keeping user-edited keys during the recompute (#1921).
- Showing a failed computation (the list returns `computeFailed` cards, #1807) and the client's Retry button that calls this route.
- Treating a card stuck in `computing` past a timeout as failed (#2026).
- Recomputing transcript cards from an instruction (a separate transcript issue).

## Acceptance criteria

- When `recompute` is called on a `proposed` card with an edited `title`, then the card becomes `computing`, and after the tick it is `proposed` with other fields recomputed and `title` unchanged; the history has a `recompute` entry.
- When the card has `kind: transcript`, then the response is 400.
- When the card is `confirmed` or `rejected`, then the response is 409 `proposal_locked`.
- When `ifVersion` is stale, then the response is 409 `version_conflict` with the current card.
- When the card is already `computing`, then the call returns it and no second job is enqueued.
- When another tenant's proposal id is used, then the route answers as for an unknown id.
