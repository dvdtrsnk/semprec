**Model tier:** medium

## Context

Model tier rationale: One known mechanism (a nullable column read through every user read path and returned from login), but it crosses the authentication path and a global identity table, so every read and the login response need their existing tests re-checked.

The signed-in user has no name today. `users` holds `id`, `created_at`, `email`, `password_hash`, `locale` (default `'cs'`), `tenant_id` and `role`; the `System settings` item's `name` is the name of the assistant, not of the person. The profile screen needs to show the person's name (initials are composed by the client, falling back to the e-mail), so the backend has to store an optional display name and return it wherever the user object is returned.

Today the user object is built from `UserRow` (`backend/packages/data/src/auth/types.ts`: `id`, `email`, `passwordHash`, `locale`, `createdAt`) and `PublicUser` (`backend/packages/data/src/auth/authActions.ts`, the same without `passwordHash`). It is read in three places: `mapRow`, `getUserByEmail`, `getUserById` and the `RETURNING` of `createUser` in `backend/packages/data/src/auth/usersStore.ts`, and the hand-written `SELECT` plus row mapping in `getUserByEmailWithTenantStatus` in `backend/packages/data/src/tenancy/tenantsStore.ts`. `POST /api/auth/login` (`backend/services/semprec-api/src/authHandler.ts`) returns `{ user }` (web) or `{ token, user }` (native) with no `role`, even though `lockUserTenantBinding` already reads the role inside the login transaction; `GET /api/auth/session` returns `{ user: { ...identity.user, role }, session }`.

Issue #1262 rewrites the tenant resolution in `getUserByEmailWithTenantStatus` and `lockUserTenantBinding`; this issue edits the same queries afterwards, so it must build on the merged result.

Decision: the display name is not added to `GET /api/admin/accounts`. An administrator does not see account content under the admin-role-without-content-access ADR, and the name is profile content; so `accountsAdminStore.ts` is untouched.

Decision: the avatar colour is not stored. The client derives it from the user id, so no colour column is created.

Later issues build on this one: #1704 (profile language update returns the user) and #1513 (writes the name at account creation).

## Task

Load `db-migrations`, `state-writes` and `testing`.

1. Add the migration `backend/packages/data/src/db/migrations/NNNN_users_display_name.sql (next free ordinal at commit time)`: `ALTER TABLE users ADD COLUMN display_name text NULL`. No default, no backfill: existing accounts keep `NULL`. The runtime role already has `UPDATE` on `users` (0057), so no grant change.
2. Add `displayName: string | null` to `UserRow`; `PublicUser` inherits it. Extend `UserDbRow`, `mapRow`, `getUserByEmail`, `getUserById` and the `RETURNING` list of `createUser` in `usersStore.ts`, and the `SELECT` and mapping of `getUserByEmailWithTenantStatus` in `tenantsStore.ts`. Fix every other place that constructs a `UserRow` or `PublicUser` so the project type-checks.
3. Return `role` from `login`: `LoginResult` gains `role: UserRole`, taken from the `lockUserTenantBinding` result already read in the login transaction (no extra query). `POST /api/auth/login` returns `user: { ...result.user, role: result.role }`, the same shape `GET /api/auth/session` returns, in both the web and the native response.
4. Tests: `GET /api/auth/session` and `POST /api/auth/login` return `user.displayName` (`null` for an account created without one, and the stored string once set directly in SQL) and login returns `user.role`; `createUser` returns `displayName: null`.

## Scope

### In scope

- The nullable `users.display_name` column, its propagation through every user read, and `role` in the login response.

### Out of scope

- Writing the name: at account creation and invitation acceptance #1513; later edits through a profile update come with the design of the editing screen (decided by the product owner).
- Changing the language: #1704.
- Exposing the name in `GET /api/admin/accounts` (decided against above).
- An avatar colour column or a photo (avatar colour decided as deferred: v1 stays lean).
- Adding `displayName` to the account export: #1513.

## Acceptance criteria

- When an account created before this change logs in, then `POST /api/auth/login` returns `user.displayName: null` and `user.role`.
- When `users.display_name` is set for a user, then `GET /api/auth/session` returns that string in `user.displayName`.
- When the migration runs on a database with existing users, then they all have `display_name` `NULL` and nothing else changes.
- `GET /api/admin/accounts` output is unchanged.
- The full backend `pnpm run verify` passes.
