### Requirement gh-1660: [people 03/03] Derive People lastContact from events, mail and transcripts

#### Context

Model tier rationale: A derived system-owned property fed by three source databases needs correct tenant-scoped queue ownership, idempotent recomputation across edge, date, trash and restore changes, a time-based sweep and a backfill, so a missed trigger silently shows a stale value.

People has no "last contact" date. The product shows it per person and sorts and filters on it ("long without contact" means more than 30 days ago; people with no date are not counted). This issue adds `People.lastContact` as a read-only value derived by the backend from the person's past activity, never typed by a user.

Decision: derived, not manual. The date is the latest date of any past item in which the person took part: an Event linked through `Events.people`, an Email linked through `Emails.senderPeople` or `Emails.recipientsPeople` (the e-mail's `date`), and a Transcript linked through `Transcripts.speakers`. Only sources dated at or before the current moment count, and trashed sources do not count. A person with no qualifying source has no value. The date is stored as a calendar date (`YYYY-MM-DD`) in the tenant timezone (`getSystemTimezone` in `backend/packages/data/src/systemSettings.ts`).

Property: `lastContact`, type `date`, `owner: "system"`, `ownerProcess: "people"`. Because it is system-owned, `assertWritableProperties` in `backend/packages/data/src/chokePoint/itemWrites.ts` already rejects any user write with 403; only the recompute writes it, through `updateItemWithClient` with `allowedSystemKeys: ["lastContact"]` and `systemOwnerProcess: "people"`. The owner process id `people` must be added to `KNOWN_OWNER_PROCESS_IDS` in `backend/packages/data/src/manifest/knownActionIds.ts` in this same issue; otherwise `core.driftCheck` reports the property as an orphaned system property.

What it builds on:

- #1457 makes `Emails.senderPeople` many-to-many. Today it is one-to-many, so a second e-mail from the same sender fails with `cardinality_violation` in `linkEmailToPeople` (`backend/packages/data/src/mail/personLinkingActions.ts`), and e-mail based contact dates cannot be correct.
- #1535 edits the same tenant cutover registry (`db/tenantCutoverMigrations.ts`); this issue is ordered after it.
- #1530 adds the hook that fires after a relation edge is written or deleted, and #1601 adds hooks for item delete and restore. Edge hooks run before the write and soft-delete and restore do not run hooks today (`chokePoint/relationOps.ts`, `chokePoint/itemTrash.ts`), so those two blockers are what makes the triggers below possible. Do not call the recompute from `itemTrash.ts` directly.

Later, the relative-date filter issue #1522 builds the "long without contact" filter on this property.

Shared-file ordering: this issue also waits for #1622, #1656 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1647: [collection-schema 13/14] Declare quick filters, default sorts and collection and picker filters in module manifests

#### Context

Model tier rationale: One declarative mechanism (new optional descriptor fields on module database manifests, validated and projected through the existing schema read path) with existing manifest and catalog-coverage fixtures, but it spans the module-registry package, six manifests, two label catalogs and the projection, so it is more than a mechanical edit.

Each collection screen in the app offers a row of quick-filter chips (for example Projects: Active, Done, Archived, All), opens on a default one, sorts by a default order, and shows only the items that belong in a collection or in a picker. None of this exists in the backend: `ModuleDatabaseDescriptor` in `backend/packages/module-registry/src/manifest.ts` is only `{ key, name, defaultViewType? }`, `ModuleRegistry.getDatabases()` projects just those, and `GET /api/schema` (`manifest/schemaProjection.ts`) carries no per-database view hints, so every client hard-codes them. A view's stored `ViewConfig` (`views/viewConfig.ts`) can hold a `filter` and `sort`, but the seed creates one default view per database with no filter.

Two data facts shape the filters. `systemActive` is set only on system-module projects (true, or false when deactivated), so a user project has no `systemActive` key; a filter `not(equals systemActive true)` would drop every user project, whereas `is_empty systemActive` keeps exactly the user projects. And the filter compiler (`views/filterCompiler.ts`) turns `in` into `= ANY(...)` and a missing key yields NULL, so `not(in status [done, archived])` also drops a project with no status; a picker that must keep status-less projects therefore needs an explicit `is_empty status` branch.

Builds on #1360 (the property projection), #1522 (relative date conditions for the date-based chips, evaluated in the tenant time zone), #1534 (numeric comparison conditions) and #1413 (aligned Czech labels in the same catalogs this adds keys to). #1709 adds the option that applies a database's collection filter to counts and queries.

Decision: chip, default-sort and date-label texts are catalog keys (`labelKey`) resolved against the owning module's catalog for the caller's locale; `/api/schema` returns resolved labels only.

Decision: the module-registry package treats a filter as an opaque JSON object, because the filter grammar lives in the data package. The data package parses every declared filter with `filterNodeSchema` and checks every referenced property key against the seeded properties in a unit test, so an invalid declaration fails CI rather than startup.

Decision (product owner): one project picker is used everywhere a project is chosen. By default it hides done and archived projects through `pickerFilter` and keeps projects without a status; it can show the hidden ones by querying with the Projects `collectionFilter` alone (user projects in any status). A done project stays a valid relation target: the picker filter is a read hint and restricts no write.

Decision (product owner): "Recent" Files means a date in the last 30 days, computed as everywhere: the `last30` preset of #1522, D-30 through today inclusive.

Decision (product owner): every collection has a default sort in the schema. Events and Tasks sort by `date` ascending; every other collection sorts by creation time descending (newest first). This issue declares the two date sorts; the creation-time default for every other database needs the system-timestamp sort of #1594 and is #1995.

### Requirement gh-1645: [health 01/09] Attach an uploaded file to an item in the same upload request

#### Context

Model tier rationale: One extended upload route that creates an edge in the same transaction as the file, reusing an existing transaction-aware upload variant, but it adds a caller-chosen target id that needs tenant-safe validation and cleanup of streamed bytes on failure.

Attaching a file to an item (a lab result to a health record, later a document to a task or an event) takes two requests today: `POST /api/files` (`backend/services/semprec-api/src/filesHandler.ts`, `Content-Type` and `X-Filename`, streamed body, 201 for a new file and 200 for an identical upload) and then `PUT /api/items/:fileId/relations/healthRecords/:recordId`. The two are not atomic, and a failure between them leaves a file nobody linked. `ingestUploadedFile` (`backend/packages/data/src/blobs/fileUploadStore.ts`) opens its own transaction. #1574 adds a transaction-aware variant that runs a caller function with the open client after the Files item is resolved; this issue uses it.

This issue adds two optional headers to `POST /api/files` so the file and its edge commit together. It becomes the single owner of attaching an upload to an item: #1654 (tasks) and #1698 (events) use these headers instead of their own.

Decisions:
- Headers: `X-Attach-To-Item` (uuid of the target item) and `X-Attach-Relation` (the key of a relation property on the Files database that leads to the target's database, for example `healthRecords`). Both or neither; one without the other is 400 `validation_failed` with `field` the missing header. Without them behavior is unchanged.
- A target that is unknown, trashed, or in another tenant answers the same 404 (no enumeration). A relation key that is not a relation of Files to the target's database answers 400 `validation_failed` with `field: "X-Attach-Relation"`. Nothing is stored in either case, and streamed bytes are deleted.
- An identical upload (`created` false) reuses the existing Files item and only adds the edge; an edge that already exists is a no-op; the response is 200. A new file is 201.
- The picker for an existing file stays the plain `PUT` on the relation; no change.
