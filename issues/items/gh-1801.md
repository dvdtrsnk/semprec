## Context

Model tier rationale: One read route plus a shared pure state function over existing edges and the event end of the time module, with fixtures for each state, but the evaluation order across several events must be exact because the calendar timeline reuses it.

An event lists the tasks that sit in it, and each row shows what happened to the task in relation to this event. The states, evaluated in order, are: done later (completed outside this event on another day), done here, done in another event, moved on to a later event, missed (the event ended and the task is not done), open. A short event shows only a count. Today nothing reads the host edges: #1764 writes `Tasks.hostEvents` ordered by the edge's `addedAt`, #1781 writes `Tasks.completedInEvent`, #1780 derives the visibility, and the event end comes from the calendar time module (#1418).

This issue adds `GET /api/events/:id/tasks` and the pure function that decides a task's state in an event, which the calendar timeline reuses (#1880); #1819 reuses the counts for the deletion confirmation.

Decisions:
- State per task, evaluated in this order: (1) the task is `done`, has no `completedInEvent` edge and its `completedOn` differs from this event's `date`: `doneElsewhere` with `completedOn`; (2) its `completedInEvent` edge points to this event, or it is `done` without an edge and `completedOn` equals this event's `date`: `done`; (3) its `completedInEvent` edge points to another event: `doneElsewhere` with that event's `eventName`; (4) this event is not the last live host event of the task: `moved` with the name of the last one; (5) this event has ended and the task is not done (`notDone` or `wontDo`): `missed`; (6) otherwise `open`.
- `counts` is `{ open, total }` where `open` is the number of `open` plus `missed` rows and `total` the number of rows.
- Trashed tasks and trashed host events do not count. Tasks are listed in the order of the event's edges by `addedAt` ascending.

Shared-file ordering: this issue also waits for #1797 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `io-hardening`, `error-handling` and `testing`.

1. Add `backend/packages/data/src/tasks/taskStateInEvent.ts` with the pure `taskStateInEvent({ task, event, hostEvents, now, timezone })` and the reader `readEventTasks(client, eventId)` (batched: edges, tasks, the other host events and their names, no per-row queries) returning `{ eventId, tasks: [{ taskId, title, state }], counts }`, where `state` is `{ kind: "open" | "missed" | "done" }`, `{ kind: "doneElsewhere", completedOn }`, `{ kind: "doneElsewhere", eventName }` or `{ kind: "moved", lastEventName }`. Export an `eventTaskCounts(client, eventIds)` for the timeline and for deletion confirmations.
2. Add the route `GET /api/events/:id/tasks` as a custom route in `systemDatabasesModuleManifest.ts` (justification `single-consumer-read`: one consumer, an event's task rows with their per-event state, which no generic read returns), with the handler in `backend/packages/data/src/tasks/eventTasksRouteHandler.ts`, a `routeMatrix.ts` entry, the `ROUTE_HANDLER_FILES` mapping and the two-tenant test case. A missing or trashed event is a 404.
3. Tests: for an event 15 October 13:00 to 14:00 hosting a task nobody completed, the state is `open` before 14:00 and `missed` after, with `counts` `{ open: 1, total: 1 }`; for a task hosted by three events in order, the first event reports `moved` with the name of the third; a task completed in the event reports `done`; one completed in another event reports `doneElsewhere` with that event's name; one completed from the list on 16 October reports `doneElsewhere` with that date; trashed tasks and events do not count; each state boundary of the order is covered; another tenant's event is a 404.

## Acceptance criteria

- When the event has ended and a hosted task is not done, then its state is `missed` and `counts` is `{ open: 1, total: 1 }`; before the end it is `open`.
- When a task sits in three events, then the state in the first is `moved` with the name of the third.
- When a task was completed in this event, in another event, or from the list on another day, then the state is `done`, `doneElsewhere` with the event name, or `doneElsewhere` with the date.
- When a task or host event is trashed, then it is not counted.
- When another tenant's event is requested, then the response is 404.
