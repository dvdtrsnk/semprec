## Context

Semprec moves from one human account per deployment to one isolated tenant per user: a tenant is one user's complete Semprec environment (1:1 with its user; no sharing between users, now or planned). Nothing in the schema knows about tenants yet. `users` is `id`, `created_at` (`backend/packages/data/src/db/migrations/0001_core_schema.sql:21-24`) plus `email`, `password_hash`, `locale` (`0025_auth_schema.sql:8-13`) — no role, no owner. The only account path outside tests, `bootstrapFirstAccount` (`backend/packages/data/src/auth/authActions.ts:174-190`), refuses once any user exists and inserts through `createAccount` → `createUser` (`authActions.ts:47-59`, `backend/packages/data/src/auth/usersStore.ts:26-40`).

This issue builds the foundation every later tenancy issue uses and changes no behaviour for the current user. Its ADR is what the review rules (#969), table classification (#971), `tenant_id` columns (#972), row-level security (#973) and tenant-leading uniqueness (#974) implement. The decisions to record:

- **Isolation:** shared schema, `tenant_id` on every tenant-owned row, Postgres row-level security (RLS). Rejected: schema per tenant (migrations ×N per deploy break one-pass deploys and one-release rollback; a `search_path` slip fails open), database per tenant (pools, `LISTEN`, crons ×N), application-only `WHERE tenant_id` (~434 query sites; one miss is a silent leak), an instance per user (not one system).
- **Tenant entity:** global `tenants(id, status ∈ provisioning|active|suspended|deleting, created_at, status_changed_at)`; `users.tenant_id` UNIQUE (1:1); `users.role ∈ admin|member`. Rejected `tenant_id = user_id` (deletion must outlive the PII-bearing user row; a tenant exists in `provisioning` before its user can log in) and memberships (sharing is excluded).
- **Fail closed, rollback safe:** `app_current_tenant()` = `NULLIF(current_setting('app.tenant_id', true), '')::uuid` (the `NULLIF` is load-bearing: after a transaction-local `set_config` ends the placeholder reads `''`, not NULL); `app_sole_tenant()` = the tenant id when exactly one `tenants` row exists, else NULL; `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())` during the transition. Every tenant table will get `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)`, RLS enabled, a RESTRICTIVE policy `tenant_isolation USING/WITH CHECK (tenant_id = (SELECT app_tenant_default()))` and a PERMISSIVE `tenant_rows USING (true) WITH CHECK (true)` (restrictive, so no future permissive policy can widen it). While exactly one tenant exists, scope-less code — including the previous release — behaves as today. A later strict switch redefines `app_tenant_default()` as `app_current_tenant()` only, flipping every default and policy atomically.
- **Guard:** `CREATE UNIQUE INDEX tenants_single_tenant_guard ON tenants ((true))`. Only the go-live issue drops it, after a maintainer security sign-off; test databases drop it in their setup only.
- **No `FORCE ROW LEVEL SECURITY`:** tables are owned by the migrating superuser, which bypasses RLS anyway. Instead every service will assert at startup that its role is not superuser, not `BYPASSRLS` and owns no table, and a catalog test asserts the runtime roles hold no privilege on any `items_p_*` partition (RLS on the partitioned `items` parent is bypassable by addressing a partition).
- **Classification:** every table carries `COMMENT ON TABLE <t> IS 'semprec:tenancy=tenant'` or `'semprec:tenancy=global'`, written by the migration that creates it; a catalog test fails on an unclassified table (no TypeScript registry).
- **Uniqueness:** every unique index on a tenant table leads with `tenant_id`, except a server-generated surrogate key or a key scoped by the server-generated id of a parent row in the same tenant (e.g. `properties (database_id, key)`: a collision then needs another tenant's unguessable id, and later composite tenant-consistent foreign keys bind parent and child to one tenant) — FK and unique checks ignore RLS, so a global unique key is an existence oracle, a collision and a cross-link. Kept global: `users.email`, token hashes, `graph_subscription_id`, push endpoint/device token, process and check keys.

## Task

Load `db-migrations` (the migration), `state-writes` (the bootstrap write), `error-handling` (the missing-sole-tenant path) and `adr-conventions` (the ADR).

1. Migration `backend/packages/data/src/db/migrations/NNNN_tenants.sql` (take the next free migration ordinal at commit time). Additive: the previous release never names the new columns and keeps working.
   - `CREATE TABLE tenants (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), status text NOT NULL DEFAULT 'provisioning' CHECK (status IN ('provisioning','active','suspended','deleting')), created_at timestamptz NOT NULL DEFAULT now(), status_changed_at timestamptz NOT NULL DEFAULT now());` and `COMMENT ON TABLE tenants IS 'semprec:tenancy=global';`
   - `CREATE UNIQUE INDEX tenants_single_tenant_guard ON tenants ((true));` with a SQL comment that only the go-live migration drops it.
   - Tenant zero, unconditionally (fresh installs too): `INSERT INTO tenants (status) VALUES ('active');`
   - `GRANT SELECT, INSERT, UPDATE, DELETE ON tenants TO semprec_side;` — the existing rule for a table the choke point does not write (`docs/operations/database-roles.md:41-48`); `semprec_data` inherits it (`0040_least_privilege_roles.sql:47`). The runtime roles need `SELECT` because `app_sole_tenant()` runs with the caller's privileges.
   - `ALTER TABLE users ADD COLUMN tenant_id uuid REFERENCES tenants(id), ADD COLUMN role text NOT NULL DEFAULT 'member' CHECK (role IN ('admin','member'));` and `CREATE UNIQUE INDEX users_tenant_id_key ON users (tenant_id);` — `tenant_id` stays nullable (NOT NULL is a later contract step); NULLs never collide, so fixtures creating several tenant-less users keep working.
   - Bind the existing account: `UPDATE users SET tenant_id = (SELECT id FROM tenants), role = 'admin' WHERE id = (SELECT id FROM users ORDER BY created_at ASC, id ASC LIMIT 1);` — a deployment has at most one user today; a no-op on a fresh install.
   - The functions — `LANGUAGE sql STABLE`, not `SECURITY DEFINER`, objects schema-qualified:
     ```sql
     CREATE FUNCTION app_current_tenant() RETURNS uuid LANGUAGE sql STABLE AS
       $$ SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid $$;
     CREATE FUNCTION app_sole_tenant() RETURNS uuid LANGUAGE sql STABLE AS
       $$ SELECT t.id FROM public.tenants t WHERE (SELECT count(*) FROM public.tenants) = 1 $$;
     CREATE FUNCTION app_tenant_default() RETURNS uuid LANGUAGE sql STABLE AS
       $$ SELECT COALESCE(public.app_current_tenant(), public.app_sole_tenant()) $$;
     ```
     A SQL comment on `app_tenant_default()` says its body is transitional and the strict switch replaces it with `SELECT public.app_current_tenant()`. `STABLE` is required: a later `ADD COLUMN ... DEFAULT app_tenant_default()` relies on a non-volatile default being evaluated once and stored as a fast default (no table rewrite).
2. `backend/packages/data/src/tenancy/tenantsStore.ts` (new): `getSoleTenantId(client: Pool | PoolClient): Promise<string>` runs `SELECT app_sole_tenant() AS id` and throws `new Error("Expected exactly one tenant, found none or several")` when it is NULL — an invariant violation surfacing as a 500, never mapped onto a domain error. Nothing else.
3. `backend/packages/data/src/auth/types.ts`: `export type UserRole = "admin" | "member";` — a type only, so `@semprec/data`'s frozen runtime surface (`__tests__/publicSurface.test.ts:537-538`) is unchanged and `backend/packages/data/src/index.ts` is not edited.
4. `usersStore.ts`: `CreateUserInput` gains optional `tenantId?: string` and `role?: UserRole`; `createUser` writes them when given and otherwise leaves the column defaults (NULL, `'member'`). `UserRow`, `mapRow` and all reads stay unchanged.
5. `authActions.ts`: inside `bootstrapFirstAccount`'s advisory-locked transaction, after the token check (`authActions.ts:185-186`), call `getSoleTenantId(client)` and create the account with `{ tenantId, role: "admin" }` (thread both through `createAccount`). The returned `PublicUser` is unchanged. The docstring says the first account becomes tenant zero's admin.
6. ADR `docs/adr/<YYYY-MM-DD>-tenant-isolation-through-row-level-security.md` (`status: accepted`, `area: [backend]`, `supersedes: []`) recording every decision above with its rejected alternatives. Consequences state that (a) earlier decisions resting on a single human account, e.g. `[[2026-09-12-per-process-agent-run-watch-registry]]`'s earliest-user owner and `[[2026-09-12-thin-user-scoped-realtime-invalidations]]`, are superseded one by one by the issues that change that code; (b) an operator with database superuser access can read every tenant (accepted; no per-user content encryption).

The fresh-install, upgrade and guard cases run on a scratch database created and dropped by the test, following the `withFreshDatabase` pattern local to `__tests__/czechHunspellSearch.test.ts:31-66` (which runs the real `runMigrations` at line 135), migrated from a temporary directory holding every migration file before this one (the copy pattern of `__tests__/migrationCompatibility.test.ts:47-58`), then this file added and `runMigrations` run again. ## Acceptance criteria
- On a scratch database migrated through this migration, `tenants` has exactly one row, status `active`; `app_sole_tenant()` and `app_tenant_default()` return its id; `obj_description('tenants'::regclass, 'pg_class')` is `semprec:tenancy=global` (integration, `tenantEntity.test.ts`).
- On a scratch database where two users were inserted before this migration (previous-release shape, naming neither new column), the earliest gets `tenant_id` = tenant zero and `role = 'admin'`; the other keeps `tenant_id` NULL and `role = 'member'` (integration).
- On a scratch database, a second `INSERT INTO tenants` fails with SQLSTATE `23505` naming `tenants_single_tenant_guard` (integration).
- In a session that never set `app.tenant_id`, `app_current_tenant()` is NULL; inside a transaction after `set_config('app.tenant_id', <uuid>, true)` it returns that uuid and `app_tenant_default()` returns it too; on the same connection after that transaction commits, `app_current_tenant()` is NULL again and `app_tenant_default()` returns tenant zero; a non-uuid setting makes both calls fail with invalid input syntax rather than fall back (integration).
- After `resetDatabase`, `bootstrapFirstAccount` creates a user with `tenant_id` = the sole tenant and `role = 'admin'`, and its result has exactly the keys it had before (`id`, `email`, `locale`, `createdAt`) (integration).
- Inside a rolled-back transaction that deleted every `tenants` row, `getSoleTenantId(client)` throws the invariant error (integration).
- `createUser` without `tenantId`/`role` stores NULL/`member`, and two such users coexist; with them it stores the given values (integration).
- `publicSurface.test.ts` and the migration-compatibility unit check (`migrationCompatibility.unit.test.ts`) pass unchanged; the ADR has complete frontmatter and a filename date matching `date` (unit / review).
