### Requirement gh-1366: [block-editor 01/13] Record the block model in an ADR

#### Context

Model tier rationale: The change is a single decision document, but it fixes a persisted CRDT data contract and a module-placement choice that every later page issue builds on, so it needs more than mechanical care.

Semprec stores page content as Yjs documents (`docs`, `doc_snapshots`, `doc_updates`; added by #23). Today the only content model is `backend/packages/data/src/docs/blocks.ts`: a block is a `Y.Map` inside `doc.getMap('blocks')` with `sys:id`, `sys:flavour` (any string), `sys:children` (a plain JS array that is overwritten whole) and arbitrary scalar fields. There is no type registry, no ordering, no validation, and `listBlocks` returns map iteration order. `WS /api/sync` (`backend/packages/realtime/src/docSync.ts`) applies any Yjs update a client sends through `mutateYDoc`, so the server cannot reject a malformed block after the fact. Tests use a different convention (a root block `{id: 'root', flavour: 'page'}` plus `'paragraph'` blocks with a `content` field), which collides with the product's `page` block type (a subpage).

The product editor shows these block types: text, three heading levels, bullet, number, todo (with a done flag), quote and page (a subpage link). Every type has an indent level 0-5; bullet markers and numbering such as "1.1" are drawn by the renderer, not stored. Shift+Enter inserts a soft line break inside a block, text carries bold, italic, code and link formatting, and a document is never empty. The same page is routinely open on a phone, a Mac and the web at once, so concurrent editing must converge. On iOS and macOS the editor runs in a WKWebView with the same JavaScript/Yjs code as the web (decision of #23, point 7; no native JSON block API is built for any client).

This issue only records the decisions in an ADR. #1539 implements the shared model from it, #1394 builds the page operation ADR on top of it, and #1393 records where subpages live.

Decisions (the conservative option each time; the ADR records the alternative that was rejected):

- Decision: block order lives in a top-level shared type `doc.getArray('order')` (`Y.Array<string>` of block ids), not in a root block of the `blocks` map and not as a fractional index on each block. Top-level shared types merge by name, whereas two clients creating a root `Y.Map` under the same key concurrently makes Yjs discard one side together with the ids it inserted. The list is flat; hierarchy exists only through the per-block `indent`.
- Decision: the text of a block is a `Y.Text` with the attributes `bold`, `italic`, `code` and `link` (`{href}`). A soft line break is a `\n` character inside the `Y.Text`.
- Decision: every block type keeps its `indent` (0-5), also non-list types. Markdown cannot express indent on non-list blocks; how the Markdown format carries it is decided by #1608, not by the block model.
- Decision: the WebSocket sync path cannot reject part of a Yjs update, so validity is enforced at read time (normalization) and strictly on every server-side write.

Semp should support a live voice mode: the user speaks, sees their words appear, and hears Semp answer, in a Semp thread. Today the backend has only batch transcription of recordings. `semprec-transcribe` calls the AI gateway routes `/internal/transcribe` (Whisper through `deepInfraWhisperProvider.ts`) and `/internal/diarize` (`pyannoteProvider.ts`) beside `/internal/complete` and `/internal/pi/messages`. There is no streaming speech-to-text and no text-to-speech. The realtime protocol (`backend/packages/realtime/src/protocolV1.ts`) has no audio frames; its binary frames are Yjs documents with a 16-byte prefix. Audio calls are recorded in `ai_gateway_calls` with `audio_seconds` and never carry an agent run id. Budgets are per tenant with a global safety cap, reserved under an advisory lock (ADRs `2026-10-16-per-tenant-ai-budgets-with-a-global-safety-cap` and `2026-09-27-ai-budget-reservations-under-a-global-advisory-lock`). Slow consumers are closed rather than buffered (ADR `2026-09-16-realtime-outage-and-backpressure-close-rather-than-buffer`).

This issue writes the ADR that fixes the voice design. #1396 (streaming speech-to-text), #1399 (streaming text-to-speech) and #1546 (the authenticated voice channel) implement the pieces according to it, and #1734 joins them to Semp threads.

Decisions to record in the ADR (the author may refine the details but must state each explicitly):
- Pipeline: speech-to-text, then a normal agent turn, then text-to-speech, not a speech-to-speech model. Reason: the turn reuses the thread queue, tools, approvals and step history unchanged, and every provider call stays in the gateway.
- Providers: Czech is primary. Retain OpenAI TTS as the provisional engineering default and ElevenLabs as the documented alternative; no comparative Czech listening test has been performed. Record this status and the ten-passage, two-listener blind protocol honestly. #1399 owns pre-production-release listening qualification; it does not block local backend implementation/integration. - Budget: audio of unknown length reserves budget in fixed chunks of seconds, one `ai_gateway_calls` row per chunk, settled with real `audio_seconds`; exhaustion ends the stream with a clear error. Voice audio rows are attributed to the Semp thread turn and the agent run they serve, in the same way as the other gateway calls of a turn, and appear as their own Voice activity in AI usage reports; they count against the tenant's budget.
- Audio is never stored.
- Interruption: user speech while Semp speaks stops the speech output only; it does not cancel the agent turn. The next turn waits in the thread's queue. Voice cancels a running agent turn only on an explicit stop command of the user ("Stop", "Zruš"), and then as an ordinary cancellation of the turn; a write waiting for approval is never executed without the approval.
- Backpressure: an overloaded voice channel is closed, not buffered.

### Requirement gh-1365: [tasks-recurrence 01/11] Record the recurrence model for Tasks and Events in an ADR

#### Context

Model tier rationale: Documentation-only change, but it fixes a data-model contract that several later issues build on, so the ADR must name the exact stored shape and ownership and weigh a real alternative.

Recurring tasks work today as a rolling chain. `task_recurrence` (created in `backend/packages/data/src/db/migrations/0004_ten_databases.sql`) holds one row per task with `item_id`, `mode` (`fixed` or `floating`), `rule` (jsonb) and `active`. When a task is set to `done`, `taskRecurrenceItemUpdateHook` (`backend/packages/data/src/tasks/taskRecurrenceItemUpdateHook.ts`) runs `advanceTaskRecurrenceWithClient` in the same transaction: it creates the next task instance, inserts a new `task_recurrence` row for it and deactivates the old row. Instances know nothing about a series or about the day of the occurrence they stand for. There is no way to show a series history, complete a future day in advance, or mark a day as missed.

Events will get recurrence as well (#1817), and the calendar timeline must expand occurrences of both Tasks and Events the same way (#1886, #1877). Before either is built, the product needs one decision on how an occurrence is represented. This issue records that decision as an ADR. No code changes.

Decision: adopt the option the product leans to. A recurring series is described by one rule and one template, and an occurrence that has a state (done, missed, moved, or otherwise edited) is a real item of the owning database (Tasks or Events). Future occurrences that have no state of their own are only projected, never stored. Completing a task occurrence creates the next one, as today. The rejected alternative is to store the rule as an owner-user property of the Tasks database (`recurrence`), keep every occurrence virtual, materialize only exceptions and drop `task_recurrence`; the ADR must state why it was rejected: generic queries, counts and search work on stored items only, and a virtual-only model would lose them for open occurrences.

### Requirement gh-1370: [semp-threads 02/19] Decide the queue shape for Semp thread turns – ADR

#### Context

Model tier rationale: The decision fixes a cross-process queue concurrency and tenant fairness contract that every later Semp turn, recovery and capacity issue builds on, so a wrong choice is expensive to reverse and the tier is raised for that uncertainty.

Every message a user sends in a Semp chat must get its own reply, a user may write in another thread while one is still being answered, and automatic ticks must not block chat. Today nothing in the queue is shaped for this. `backend/packages/queue/src/index.ts` closes the agents runtime's task catalog in `AGENT_TASK_NAMES` (`heartbeatFireAgent`, `agentRun`, `delegatedAgentRun`), and `EnqueueJobOptions` has `jobKey`, `jobKeyMode`, `maxAttempts`, `runAt` and `queueName` but no priority. A worker process runs 4 jobs at once (`QUEUE_CONCURRENCY`). `docs/adr/2026-10-08-per-tenant-queue-lanes.md` serializes work on a `<lane>:<tenantId>` queue built by `tenantLane()` (`backend/packages/data/src/tenancy/tenantLane.ts`), and heartbeat agent fires already run on their own `agent-run:<tenantId>` lane (`resolveAgentRunLane` in `backend/packages/data/src/scheduler/actions.ts`). A process that stops without a graceful stop leaves a queue's lock held until graphile-worker treats it as stale (4 hours), so the number of queues a design creates also decides how much recovery work a crash can leave behind.

The next issue (#1727) adds a `sempMessage` task that runs one thread turn. It needs to know which queue that task is enqueued on. This issue records that decision as an ADR and changes no code.

Decision: serialize Semp thread turns per tenant on one lane named through `tenantLane('semp-chat')` (first option below), not on one queue per thread. It is the conservative choice: it keeps the existing lane convention, adds no new queue per thread, needs no per-tenant cap and no cleanup of empty queues, and cannot let several threads of one tenant fill every slot of a process. Its cost is that two threads of the same tenant answer one after the other; threads of different tenants and ticks (which stay on their own lane) still run in parallel.
