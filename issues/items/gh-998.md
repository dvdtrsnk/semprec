**Blocked by:** #990, #997

## Context

Gmail push uses one Cloud Pub/Sub pull subscription shared by every watched account (`backend/packages/data/src/mail/gmailPubSubClient.ts:24-36`). Each message carries `{ emailAddress, historyId }` (`:94-115`).

Today every Gmail-mode mailbox lifecycle runs its **own** pull loop against that shared subscription (`backend/packages/data/src/mail/gmailWatchLifecycle.ts:140-179`). It does three things:
- skips messages whose `emailAddress` differs from its own account's (`:165`), leaving them unacknowledged for redelivery;
- enqueues `mailAccountSync` for a match (`:167`);
- acknowledges what it handed off (`:173-177`).

With several tenants this has two consequences:
- every puller leases and inspects every tenant's notifications;
- a message for an address connected in two tenants is acknowledged by whichever puller sees it first, so the other tenant's mailbox never hears of it.

The watch renewal loop (`:128-138`) persists only expiry and cursor (`recordGmailWatchRegistration`, `backend/packages/data/src/mail/mailAccountSyncStateStore.ts:156-167`). That `UPDATE` does not check its affected-row count. No column records which account address a watch was registered for, so nothing in the database can map an address to its mailboxes.

None of this is wired in production yet. `semprec-api` hosts the live-sync root with the noop lifecycle factory (`backend/services/semprec-api/src/serve.ts:122-131`), and neither the Gmail lifecycle factory nor the Pub/Sub transport is exported from `@semprec/data`. This issue fixes the tenancy shape of that library code. It does not wire it.

The decision, recorded in the cross-tenant router functions ADR added by #997 (`docs/adr/<date>-cross-tenant-router-functions.md`):
- **one** process-wide dispatcher pulls the shared subscription in system scope;
- it routes each message's address through a `semprec_router`-owned `SECURITY DEFINER` function to every matching `(tenant, mailbox)`;
- it enqueues each target's sync inside that target's tenant;
- it acknowledges the message **once**, only after every target was handed off.

Routing uses the address the Google account behind the mailbox's credential was watched as, never the user-editable `Mailboxes.addresses` property. Otherwise one tenant could claim another's pushes.

Tenancy state this issue builds on:
- #997 created the `NOLOGIN BYPASSRLS` role `semprec_router`, the pattern (column-level `SELECT`, pinned `search_path`, `EXECUTE` only to `semprec_data`, ids-only results) and the roles-doc section that lists router functions.
- #990 discovers mailboxes per tenant and starts each hosted lifecycle inside its mailbox's tenant scope, so a lifecycle's loops inherit that scope.
- `runInTenant(tenantId, fn)` and `runAsSystem(reason, fn)` come from `@semprec/shared`. Entering a tenant from system scope is allowed.
- `enqueueJob` stamps the envelope `tenantId` from the current scope (#982).
- `mail_account_sync_state` is a tenant table under RLS; `tenant_id` is defaulted from the scope.

## Task

Load `db-migrations` (additive column, index, router function), `io-hardening` (a long-lived pull loop, its backoff and its shutdown), `state-writes` (the targeted update's affected-row check; enqueue as the durable hand-off) and `error-handling` (partial failure across targets).

1. **Migration.** Take the next free migration ordinal at commit time, for example `NNNN_gmail_watch_address_routing.sql`. Additive only:
   - `ALTER TABLE mail_account_sync_state ADD COLUMN gmail_watch_email_address text;` (nullable).
   - `CREATE INDEX mail_account_sync_state_gmail_watch_email_idx ON mail_account_sync_state (gmail_watch_email_address) WHERE gmail_watch_email_address IS NOT NULL;` It is not unique: one address may be connected in several tenants.
   - `GRANT SELECT (item_id, tenant_id, sync_mode, gmail_watch_email_address) ON mail_account_sync_state TO semprec_router;`
   - `CREATE FUNCTION route_gmail_address(email_address text) RETURNS TABLE (tenant_id uuid, mailbox_item_id uuid) LANGUAGE sql STABLE SECURITY DEFINER SET search_path = pg_catalog, public AS $$ SELECT s.tenant_id, s.item_id FROM public.mail_account_sync_state s WHERE s.sync_mode = 'gmail_api' AND s.gmail_watch_email_address = email_address $$;`
   - Then `ALTER FUNCTION … OWNER TO semprec_router`, `REVOKE EXECUTE … FROM PUBLIC`, and `GRANT EXECUTE … TO semprec_data`.
   - A header comment explains the column's source and the routing.
2. **Store (`mailAccountSyncStateStore.ts`).**
   - `RecordGmailWatchRegistrationInput` gains `emailAddress: string`. `recordGmailWatchRegistration` also sets `gmail_watch_email_address = $4`, the already-normalized value, and checks its affected-row count with `requireAffectedRows`, as `recordGraphSubscriptionRegistration` does (`:229-241`).
   - Add `routeGmailAddress(client: Queryable, emailAddress: string): Promise<Array<{ tenantId: string; mailboxItemId: string }>>`. It normalizes with `normalizeEmailAddress` (`backend/packages/data/src/mail/personEmailIndexStore.ts:3-5`), calls `route_gmail_address($1)` and validates each row's two uuids.
3. **Per-mailbox lifecycle (`gmailWatchLifecycle.ts`).** `createGmailWatchLifecycleFactory` keeps the immediate `enqueueMailAccountSync` on `start()` and the renewal loop, and loses the pull loop and its options.
   - The renewal passes `emailAddress: normalizeEmailAddress(<getAccountEmailAddress result>)` to `recordGmailWatchRegistration`.
   - Document on `getAccountEmailAddress` that it must return the address of the Google account the credential authenticates, which is the address Gmail puts in each notification, never `Mailboxes.addresses`.
   - `onError`'s phase becomes `"watch"` only.
4. **Transport (`gmailPubSubClient.ts`, and the `GmailWatchTransport` type).** `pull()` and `acknowledge(ackIds)` drop their unused `mailboxItemId` parameter. The subscription belongs to the deployment, not to a mailbox. `registerWatch(mailboxItemId, credential)` is unchanged.
5. **Dispatcher (`gmailWatchLifecycle.ts`).** Export `createGmailPubSubDispatcher(pool, transport, options)`, returning `{ start(): Promise<void>; stop(): Promise<void> }`.
   - Options: `pullEmptyBackoffMs`, `pullErrorBaseDelayMs`, `pullErrorMaxDelayMs` (today's defaults and `pullErrorBackoffDelayMs`), and `onError(target: { tenantId, mailboxItemId } | null, phase: "pull" | "route" | "enqueue" | "acknowledge", err)`.
   - `start()` launches one loop inside `runAsSystem("mail:gmailPubSubDispatcher", …)` and returns. It is called with no scope or from a system scope; `runAsSystem` throws inside a tenant scope. `stop()` resolves the shared stop promise and awaits the loop, as the lifecycle does today.
   - For each pulled notification:
     - route it with `routeGmailAddress` (its own `withTransaction`; a failure → `onError(null, "route")`, not acknowledged);
     - for each target, run `runInTenant(target.tenantId, () => enqueueMailAccountSync(pool, target.mailboxItemId))`. A rejection → `onError(target, "enqueue", err)`, called inside that target's tenant scope. The other targets still run;
     - the message is acknowledged only when every target succeeded. A message with **no** target is acknowledged too: nobody watches that address any more, and redelivering it forever helps no one.
   - All ack ids of one pull go out in **one** `acknowledge` call. A rejection → `onError(null, "acknowledge")`.
6. **Tests.**
   - Rewrite the pull-related cases of `backend/packages/data/src/__tests__/gmailWatchLifecycle.test.ts:160-252,282-303` against the dispatcher, and add an address assertion to the registration cases at `:108-158`. The fake transport's `pull`/`acknowledge` lose the mailbox parameter.
   - New `backend/packages/data/src/__tests__/gmailAddressRouting.test.ts` holds the function and two-tenant cases.

## Acceptance criteria

All integration tier.
- **Function shape (`gmailAddressRouting.test.ts`).**
  - `route_gmail_address(text)` is `SECURITY DEFINER`, owned by `semprec_router`, with `search_path=pg_catalog, public`.
  - `EXECUTE` is held by `semprec_data` only.
  - `semprec_router` cannot `SELECT mail_account_sync_state.last_error`.
  - As `semprec_data` with `app.tenant_id` set to a random UUID (via `createRuntimeRolePool(pool, "semprec_data")` from #975's `@semprec/data/testSupport` inside `runInTenant`, or `SET LOCAL ROLE` plus `set_config`): a direct `SELECT` finds no rows, while the function still returns tenant zero's Gmail mailbox for its address. As `semprec_side` the call fails with `42501`.
  - Only `sync_mode = 'gmail_api'` rows are returned.
- **Watched address persisted (`gmailWatchLifecycle.test.ts`).** After a renewal with `getAccountEmailAddress` returning `" User@Example.com "`, the row's `gmail_watch_email_address` is `user@example.com`. Renewal on a mailbox without a sync-state row reports `onError(id, "watch", …)`.
- **Fan-out within a tenant (`gmailWatchLifecycle.test.ts`).** Two Gmail mailboxes in tenant zero are registered for the same address, and the dispatcher pulls one notification for it:
  - each mailbox gets exactly one pending `mailAccountSync` job, and both envelopes carry tenant zero;
  - `acknowledge` is called once, with that one ack id.
- **Two tenants (`gmailAddressRouting.test.ts`; tenant B from `createTestTenant(pool)`, dispatcher over `createRuntimeRolePool(pool, "semprec_data")`, both from #975).** The same address is watched in tenant zero and tenant B:
  - one notification yields one job per mailbox, each envelope carrying its own tenant;
  - the message is acknowledged exactly once.
- **Partial failure (`gmailWatchLifecycle.test.ts`).** When `enqueueMailAccountSync` rejects for one of two targets (stubbed via `vi.mock` with `importOriginal`):
  - the other target's job exists;
  - nothing is acknowledged;
  - `onError` received exactly that target and phase `"enqueue"`.
- **Unknown address and malformed input (`gmailWatchLifecycle.test.ts`).** A notification for an address no mailbox watches creates no job and is acknowledged. A malformed Pub/Sub entry is still left unacknowledged (`gmailPubSubClient.ts:160-167`).
- **Loop behaviour (`gmailWatchLifecycle.test.ts`).**
  - Repeated pull failures back off with the capped growing delay and reset after a success.
  - `stop()` halts the loop with no further `pull` or enqueue.
  - The per-mailbox lifecycle never calls `pull` or `acknowledge`.
- **System scope.** With `SEMPREC_TENANT_SCOPE=strict` and a pool from `createPool`, the dispatcher started and stopped from a context with no scope routes and enqueues without `TenantScopeMissingError`.
