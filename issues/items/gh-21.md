## Context

This is the very first issue in the sequence of 22 issues that together implement the Semprec backend (a pnpm/TypeScript monorepo). It builds on nothing — it is the foundation everything else stands on: the data model (`packages/data`), through which every write and read in the whole system passes.

The core design decision: no DDL per database. The user creates their own "databases" in the UI (Projects, Movies, Tasks...) and their own columns ("properties") on them, but at the Postgres level it is still just a handful of fixed tables — metadata about databases and properties kept separate from a universal row store with `properties jsonb`. This is the same hybrid pattern used by AFFiNE (relational Postgres for structured data, a separately handled binary layer for free-form content — that binary layer is out of scope, handled by a different section/issue).

On top of this foundation, this slice adds two things that were missing from the initial picture:

1. **Who may write a property's value** (not just whether its definition can be deleted) — two independent questions, both needing separate handling.
2. **One generic service choke-point**, through which every write in the system passes — from the user in the UI, from an API client, and from an AI agent. This choke-point is where all the rules below are enforced (who may write what, idempotency, optimistic concurrency, validation). Its scope is deliberately narrow: it is the single CRUD/query path for the four generic resource tables — `databases`/`items`/`properties`/`views` — plus `item_relations`. It is **not** a choke-point over every bespoke table in the system; tables with their own non-generic invariant (starting with `project_heartbeats`, described below) get their own narrowly-typed domain-store module instead, protected by the same import ban and Postgres role restrictions as the generic engine, but with code that knows nothing about the generic item engine and vice versa. This keeps the dependency direction correct (DIP): specific domain modules depend on the shared write-enforcement package, not the other way around, and the generic engine is not bloated with per-table special cases.

This foundation additionally underpins: the periodic/event-driven task mechanism (heartbeats), the AI agent audit/delegation tree (supervisor → project agents), and an aggregation engine over relations (rollup).

## Task

### Metadata schema layer

```sql
CREATE TABLE databases (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name text NOT NULL,
  parent_item_id uuid REFERENCES items(id),         -- set only for an inline DB created inside page content
  owner_project_item_id uuid REFERENCES items(id),  -- a row in Projects — Projects are just items too, no special table
  owner_module_id text,                             -- 'emails', 'finance', NULL = a free-form user DB
  schema_locked boolean NOT NULL DEFAULT false,      -- a module owns the schema, the user must not be able to break it
  system boolean NOT NULL DEFAULT false,             -- one of the ten hardcoded system DBs, cannot be deleted
  archived_at timestamptz
);

CREATE TABLE properties (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  database_id uuid NOT NULL REFERENCES databases(id) ON DELETE CASCADE,
  key text NOT NULL,               -- stable jsonb key, NEVER renamed
  name text NOT NULL,              -- user-visible label, freely renamable
  type text NOT NULL,              -- text|number|select|multi_select|date|relation|rollup|files...
                                    -- NOTE: 'formula' is deliberately NOT in the v1 enum (see the formula section below)
  config jsonb NOT NULL DEFAULT '{}',
  locked boolean NOT NULL DEFAULT false,   -- schema cannot be deleted / key renamed / retyped
  owner text NOT NULL DEFAULT 'user',      -- 'user' | 'system' — who may write the VALUE
  owner_process text,               -- nullable identifier of the process/module that actually fills this field (see owner_process below)
  migration_status text NOT NULL DEFAULT 'stable',  -- 'stable'|'pending'|'running'|'done'|'partial'
  UNIQUE (database_id, key)
);

CREATE TABLE relation_definitions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  property_id_a uuid NOT NULL UNIQUE REFERENCES properties(id) ON DELETE CASCADE,
  property_id_b uuid UNIQUE REFERENCES properties(id) ON DELETE CASCADE,  -- NULL = one-directional relation
  cardinality text NOT NULL DEFAULT 'many_to_many'
);
```

### Universal row storage

```sql
CREATE TABLE items (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  database_id uuid NOT NULL REFERENCES databases(id),
  properties jsonb NOT NULL DEFAULT '{}',
  computed jsonb NOT NULL DEFAULT '{}',   -- cache for rollup values plus declared module cache keys; written EXCLUSIVELY by the background worker/internal function, never by the generic update path
  updated_at timestamptz NOT NULL DEFAULT now(),
  deleted_at timestamptz                  -- soft delete (trash); full trash semantics are out of scope for this issue
) PARTITION BY LIST (database_id);

CREATE INDEX items_props_gin ON items USING gin (properties jsonb_path_ops);

CREATE TABLE item_relations (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  relation_definition_id uuid NOT NULL REFERENCES relation_definitions(id) ON DELETE CASCADE,
  item_a uuid NOT NULL REFERENCES items(id) ON DELETE CASCADE,
  item_b uuid NOT NULL REFERENCES items(id) ON DELETE CASCADE,
  metadata jsonb NOT NULL DEFAULT '{}',  -- a value belonging to the RELATIONSHIP itself (e.g. a rating on a "ratable" relation), not to either side
  UNIQUE (relation_definition_id, item_a, item_b)
);
```

Important: **relation values never live in `items.properties`** — only ever in `item_relations`. A `relation`-typed property's `config` merely points at a `relation_definitions` row.

### Locked vs. owner — two independent axes

- **`locked`** (on `properties`) governs SCHEMA: may the property be deleted / its key renamed / its type changed? Independent of who may write the value.
- **`owner`** (`'user' | 'system'`, on `properties`) governs VALUE: who may write the field's content?

Model example of the distinction: the "agents" property (the structured equivalent of AGENT.md — four fixed sections: Purpose, What the agent may do, What the agent may not do, General instructions) must exist on every project (`locked: true` — the schema must not be breakable), but its CONTENT is fully in the user's hands (`owner: 'user'`). Conversely a property like a movie's critic-rating field is also `locked`, but its value may only be written by a heartbeat process, never by the user (`owner: 'system'`). The combinations are independent — both are needed.

### The generic choke-point

No bespoke endpoints per database. A single CRUD/query service over `databases`/`items`/`properties` (views are out of scope for this issue, see Scope below) that:

- enforces `schema_locked`/`locked` on schema writes,
- enforces `owner` on value writes — a user attempting to overwrite an `owner: 'system'` field always gets **403**, regardless of whether the request came from the UI, a generic API client, or an AI agent,
- is the only place a write can happen at all — a system DB's schema (deleting/adding/retyping a property) can only be changed by a code-level migration with direct DB access, outside the running API.

**Scope boundary (important):** this generic engine is the single CRUD/query path for exactly four generic resources — `databases`, `items`, `properties`, `views` (views land in a later issue, but the engine's contract already reserves the shape for them) — plus `item_relations`. It does **not** extend to every table in the system. Tables that need a transactionally-enforced invariant tied directly to the write (like the heartbeat scheduling logic below) get their own narrow domain-store module inside the same protected write layer instead of being folded into the generic engine, and modules with no such invariant (mail metadata, notifications, etc., introduced by later issues) are written through a plain shared pool outside this package entirely, because a second enforcement mechanism there would only duplicate protection module ownership already gives them.

### Idempotency and optimistic concurrency

Solved once at the choke-point level, not per module (motivated by offline mobile clients caching writes and sending them in a batch after reconnecting, but applies generally to any unreliable write):

- `create-item` accepts an optional `Idempotency-Key` (an opaque string, typically a UUID from clients; an internal producer may use a deterministically derived key, e.g. `transcription:fileItemId`). The server stores it alongside the ID of the created row; a repeated request with the same key returns the same result, not a second extra row.
- `update-item` carries `ifVersion` (the value of `items.updated_at` the client last held). A match means a clean write. A mismatch returns **409** with the row's current state, not a silent overwrite.
- No vector clocks or CRDTs — for a system with only one writing device at a time, a single "what version I built on" pointer is enough. A genuine conflict (two different devices independently edited the same row) is the one case an `ifVersion` mismatch catches — and it must be detected, not silently merged.
- **Important detail:** writes to `computed` (rollup results) must NOT advance `items.updated_at`/the `ifVersion` token — otherwise background recomputation would cause spurious 409s on the client's next properties write, even though properties never changed.

### Property type migration

When `properties.type` changes to a type that requires converting existing values (e.g. text → number):

- A one-off migration job runs: `migration_status` moves through `pending` → `running` → `done`/`partial`.
- It walks all `items` of the database, and for each row attempts to convert the old value to the new type using a fixed, small set of conversion functions per type pair (text→number: numeric parsing).
- An unconvertible value is NOT overwritten with an error — it is left empty, and the row is logged as failed (resulting state `partial`).
- It runs **eagerly, once, immediately** on the type change — never lazily on read. The state "some rows still have the old format" must never be permanent.
- For type pairs with no meaningful conversion (e.g. select → relation), conversion is **not offered at all** — the user must create a new property and manually empty/archive the old one. No destructive in-place retyping.

### Heartbeats — structured configuration, not a property

Heartbeats are not `items.properties` — they are their own table, `project_heartbeats`, tied to `project_item_id` (a similar pattern to `agent_runs`), because they need typed trigger validation, not free-form JSONB.

```sql
CREATE TABLE project_heartbeats (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  project_item_id uuid NOT NULL REFERENCES items(id),
  name text NOT NULL,               -- label for the UI/permission manifest, e.g. "Process Inbox"
  rule jsonb NOT NULL,
  --   { kind:'dailyTime', at:'09:00' }                -- calendar-anchored (fixed)
  -- | { kind:'weekly', days:['mon'], at:'09:00' }      -- calendar-anchored (fixed)
  -- | { kind:'everyNDays', n:3, at:'09:00' }           -- floating
  -- | { kind:'interval', minutes:30 }                  -- floating, pure duration
  -- | { kind:'onItemEvent', databaseId, event:'create'|'update'|'delete' }  -- event-driven, no "next time" at all
  action_id text NOT NULL,          -- an action identifier resolved through a simple in-process registry; INTENTIONALLY not an FK
  action_config jsonb NOT NULL DEFAULT '{}',
  enabled boolean NOT NULL DEFAULT true,   -- pause, not delete
  next_fire_at timestamptz,          -- the single source of truth for "when next"; NULL for onItemEvent
  last_fired_at timestamptz,
  last_error text,                   -- last permanent failure after retries are exhausted
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX project_heartbeats_due_idx
  ON project_heartbeats (next_fire_at) WHERE enabled AND next_fire_at IS NOT NULL;
CREATE INDEX project_heartbeats_project_idx
  ON project_heartbeats (project_item_id);
```

One row = one trigger for one action (never an array of triggers in one row) — scheduling state (`next_fire_at`, last run/error) belongs to one specific trigger, not "one of several."

One core action always exists: `core.agentRun` — "run the agent owning the project with the task from `action_config.task`." The actual implementation of running an AI agent (an LLM session) is NOT part of this issue — implement `core.agentRun` as a pluggable interface/stub that creates an `agent_runs` row and calls an injected "run the agent" function; the real implementation arrives in a later issue about agent orchestration. Other `action_id` values (module actions) are intentionally not foreign-keyed — modules register themselves at process runtime, not in the DB. For this issue, implement a simple in-process registry (a map of `action_id → handler`) as a temporary stand-in for the full module registry that arrives in a separate module-system issue.

**Writes go through their own enforced module, not the generic engine (SRP):** writes to `project_heartbeats` — including computing/recomputing `next_fire_at` — go through a dedicated `SchedulerStore` module inside the write-enforcement package, protected by the same import ban and Postgres role restrictions as the generic item engine, but implemented independently of it (it knows nothing about the generic item engine, and the generic engine knows nothing about it). The scheduling logic (turning `rule` + timezone + `last_fired_at` into the next `next_fire_at`) lives entirely inside `SchedulerStore` as a pure function — it is never embedded inside the generic query engine, and the generic engine never computes or touches `next_fire_at`.

**Timezone:** a new property `timezone` (`text`, an IANA identifier, default `'Europe/Prague'`, `owner: 'user'`, `locked: true`) in the "System settings" system DB (see the supervisor section below) — one timezone for the whole system, not per user (the heartbeat scheduler runs without a user session, it has no "current user"). `at` times in `rule` are local wall-clock time in that timezone; conversion to `next_fire_at` (a UTC timestamptz) is done by a timezone-aware library, never manual offset arithmetic. DST: a non-existent local time (spring-forward) resolves to the first following valid instant; an ambiguous time (fall-back) resolves to the first occurrence. Changing the timezone property recomputes `next_fire_at` for every enabled time-based heartbeat in the same transaction.

**Catch-up after downtime:** on startup, the first sweep finds any `next_fire_at` in the past and runs it exactly ONCE, immediately — not at the next scheduled time, not once per missed occurrence. `next_fire_at` is a single value (not a queue), so "I owe three runs" cannot structurally be represented. The next due time after a run (regular or catch-up):
- **fixed** (`dailyTime`, `weekly`) — computed purely from the rule, regardless of when the catch-up run actually happened.
- **floating** (`everyNDays`, `interval`) — computed from the actual run time (`last_fired_at` + the interval).
- `onItemEvent` needs no catch-up at all — the choke-point and the job queue run on the same server, so if the server isn't running, no event can be lost in the first place; a job already in the queue survives a restart.

**Scheduler:** a static entry in the job queue's cron table (no in-process `setInterval`) triggers a sweep every minute that, in a single transaction, selects `SELECT ... WHERE enabled AND next_fire_at <= now() FOR UPDATE SKIP LOCKED`, advances `next_fire_at`, and enqueues a job with `jobKey: heartbeat-fire:${heartbeatId}`. Critically: "exactly once" is guaranteed by the **row lock** (`FOR UPDATE SKIP LOCKED`), not by transaction atomicity nor by `jobKey` — two overlapping sweeps could, under READ COMMITTED, both select the same row. `jobKey` is only a second, softer safety net for jobs still waiting in the queue.

Creating or editing a heartbeat is deterministic at write time — the choke-point (via `SchedulerStore`) computes/recomputes `next_fire_at` in the same transaction on insert and on every change to `rule`, using the same pure function as the sweep. Disabling is a plain `enabled = false` update. Re-enabling recomputes `next_fire_at` from the moment of re-enabling — occurrences missed while paused are not caught up.

`onItemEvent` rows are invisible to the sweep (`next_fire_at IS NULL`). They are fired by the choke-point's write path instead: after a write to the watched DB, it enqueues `{ heartbeatId, itemId }` with `jobKey: heartbeat-fire:${heartbeatId}:${itemId}` (dedup per heartbeat×item pair).

Handler failure: retry/backoff with `max_attempts: 3`; once exhausted, `last_error` is written and, **in the same transaction**, a row is written to `notifications` with kind `heartbeat_error`. The full `notifications` table (typology, delivery channels) is out of scope for this issue; implement a minimal `notifications` table sufficient for this write (`id`, `kind text`, `payload jsonb`, `created_at`, enough for `heartbeat_error` with a reference to the heartbeat and an error message) — the full schema is completed by a later issue. A failed run does NOT block the next occurrence.

Heartbeat run history = a query over `agent_runs.heartbeat_id`, no second run-log table.

### AGENT.md as system prompt — two layers

The `agents` property (Purpose/May do/May not do/General instructions) carries two different things under one label:

1. **Enforced boundary** — anything mechanically checkable at the choke-point (`owner: 'system'` fields, row-level `locked`). Holds regardless of what the text says.
2. **Guided boundary** — things no schema can capture (tone, task priority) — text is the only tool that works here, because it is a matter of judgment.

The text stays free-form (the LLM reads natural language). The risk: the text can drift out of sync with the actual schema.

**Solution — a generated permission manifest:** a given project agent's system prompt is assembled on EVERY run from three layers, in this order:
1. a fixed meta-preamble shared by all agents,
2. a **permission manifest generated directly from the schema** for that project (which properties/DBs are `owner: user` vs. `system`/`locked`, which actions require confirmation) — computed at runtime, never hand-maintained,
3. the hand-written `agents` text.

The manifest is never persistently cached — it is computed synchronously from the current state of `properties`/`databases`/`project_heartbeats` at the start of every `agent_run` (a small, indexed query scoped to one project, not a scan of the whole system).

A mismatch between the manifest and the text (the text claims "may do X", the schema no longer allows X) is watched by a separate **drift heartbeat check** — it reports the mismatch (via `notifications`, above), it does not stay silent about it.

**`owner_process`:** `owner: 'system'` says WHO MAY NOT write, not who may. Without a further record, a field can become orphaned (no process actually fills it). Solution: a new nullable column, `properties.owner_process text` — a free-form identifier of the process/module that actually fills the field (e.g. `'library.processLibraryMetadata'`). It is not enforced as an FK (modules register at runtime). The same class of drift heartbeat reports an `owner: 'system'` property with an empty `owner_process`, or one that doesn't match any currently active module.

### Delegation: supervisor → project agents

The main agent (the supervisor) tasks project agents without knowing the details of their work — its own context stays clean. A project agent completes its task and returns only the result, not intermediate steps. The catalog of project agents available to the supervisor is just a brief directory (each active project's `agents.Purpose`) — the full manifest + text is assembled only once an agent actually starts running.

```sql
CREATE TABLE agent_runs (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  project_item_id uuid REFERENCES items(id),
  parent_run_id uuid REFERENCES agent_runs(id),   -- set on delegation, or on a heartbeat.trigger issued from another run
  heartbeat_id uuid REFERENCES project_heartbeats(id),  -- set for a run that executes a heartbeat
  triggered_by text NOT NULL,       -- 'user' | 'heartbeat' | 'supervisor' | 'mcp'
  unit text NOT NULL DEFAULT 'invocation',  -- 'invocation' | 'session' — session rows will later cover multi-exchange agent conversations; present now so agent_runs doesn't need a later backfill (full session semantics land in the pi-agent-core issues)
  task text NOT NULL,                -- the assignment handed to the agent — the only thing crossing the boundary inward
  status text NOT NULL DEFAULT 'running',   -- 'running' | 'done' | 'error'
  result text,                       -- only the final result — the only thing crossing the boundary outward
  started_at timestamptz NOT NULL DEFAULT now(),
  finished_at timestamptz
);
```

This is also the system's main audit trail (who/what started which agent, with what task, when, with what result). `parent_run_id` makes the delegation tree visible after the fact.

**The supervisor is Semprec.** The supervisor's name is "**Semp**" (data in the DB, not a string hardcoded in code). Its home is the system project "Semprec" — with its own `agents` text, its own `project_heartbeats`, and the role of home for the whole system's global settings. `agent_runs.project_item_id` for a supervisor run points at Semprec's row in Projects.

Semprec gets its own DB, **System settings**: a single, non-deletable row (`schema_locked`, no "+ New" in the UI), whose properties are freely extended over time. First property: `name` (`text`, `owner: 'user'`, `locked: true`), value "Semp". This value is actually read at runtime and interpolated into the supervisor's meta-preamble prompt.

The choke-point does not consult this table AT ALL today. Yes/no, nothing in between. (The `users` table itself — authentication, roles, session management — is out of scope for this issue, referenced only as an FK; implement a minimal `users(id)` table sufficient for this reference — full user management is handled by a later issue.)

### Rollup engine

A rollup is always an aggregation across **one** relation property of the same database (e.g. "count of a project's tasks", "latest task date").

```sql
-- properties.config for type: 'rollup'
{
  "relationPropertyKey": "tasks",   -- a relation property of the SAME database; the target DB is resolved via relation_definitions
  "targetPropertyKey": "date",      -- properties.key in the target DB; required for everything except 'count'
  "aggregation": "latest"           -- a value from the closed enum below
}

-- v1 closed enum of aggregations (extension = a code migration of the enum, never a data change):
--   count                              count of non-deleted linked rows — no targetPropertyKey
--   count_filled | count_empty         how many linked rows have/lack a value — any non-relation type
--   percent_filled | percent_empty     the same as a 0-1 proportion
--   sum | avg | min | max              targetPropertyKey of type number only
--   earliest | latest                  targetPropertyKey of type date only
```

Validation at the choke-point on both creation and every change: `relationPropertyKey` must exist in the same DB and be `type: 'relation'`; `targetPropertyKey` must exist in the relation's target DB and have a type compatible with the aggregation; **`targetPropertyKey` must not itself be `rollup` or `relation`** (keeps invalidation single-hop, no transitive chains). A violation is `validation_failed` (400) with per-field detail.

The computed value lives in `items.computed` under the property's key. This shares a namespace with module cache keys (transcription, Inbox summaries) — guarded mechanically: a module declares its cache keys in its manifest (`computedKeys`); the choke-point refuses to create a property whose `key` collides with a declared module cache key; the internal computed-write function refuses a module write under an undeclared/colliding key.

Three things v1 deliberately does not do (later additive extensions): aggregation over `item_relations.metadata` (ratings on edges), aggregation over relation-property fill state, per-rollup filtering of source rows.

**Materialized reverse dependency index:**

```sql
CREATE TABLE rollup_dependencies (
  rollup_property_id uuid PRIMARY KEY REFERENCES properties(id) ON DELETE CASCADE,
  relation_definition_id uuid NOT NULL REFERENCES relation_definitions(id) ON DELETE CASCADE,
  source_database_id uuid NOT NULL REFERENCES databases(id),
  source_property_key text                                    -- NULL = membership only (count)
);
CREATE INDEX rollup_dependencies_source_idx ON rollup_dependencies (source_database_id, source_property_key);
CREATE INDEX rollup_dependencies_reldef_idx ON rollup_dependencies (relation_definition_id);
```

The row is created/changed in the SAME transaction as the write to the rollup property. Deleting the rollup property itself cleans up the dependency via `ON DELETE CASCADE`. The opposite direction (deleting/retyping the source property a rollup depends on) is NOT left to cascade — a mirror validation is enforced instead (below).

**Mirror lifecycle validation:** a `DELETE` on a relation property checks dependent rollups via `rollup_dependencies_reldef_idx`; a `PATCH` changing a source property's type checks via `rollup_dependencies_source_idx` and verifies the new type's compatibility against every dependent rollup's aggregation. If it doesn't comply — the operation is rejected (`validation_failed`, 400, `details.dependentRollups`). The user's path is two explicit steps: first delete/redirect the dependent rollup, then delete/retype the source. Silently "invalidating" the rollup instead of rejecting the operation was considered and rejected (see Reference below).

**Deterministic recompute flow:**
```
write via the choke-point (PATCH properties / PUT·DELETE relation / soft delete·restore)
  → in the SAME Postgres transaction:
      lookup rollup_dependencies (an indexed query keyed by event type)
      resolve affected parents via item_relations
      enqueueJob(rollupRecompute, { rollupPropertyId, itemId }, { jobKey: rollup-recompute:${rollupPropertyId}:${itemId} })
job (worker):
  → one aggregation SQL query over item_relations JOIN items (WHERE deleted_at IS NULL)
  → overwrite items.computed[rollupKey] via the internal function (the generic update path refuses this field — computed_readonly, 403)
  → realtime channel invalidation (out of scope for this issue — just ensure the write hook exists/is callable)
```

Exactly three events trigger a recompute: (a) a change to the aggregated property's value, (b) a change to an `item_relations` edge, (c) soft delete/restore of a source row. A recompute is always a **full recompute of one cell** from current state, never an incremental delta. `jobKey` per (rollup, parent) collapses a burst of rapid edits into one fresh recompute.

**Backfill:** creating a rollup property (or changing its config) enqueues `rollup-recompute:${rollupPropertyId}:full`, which itself NEVER writes cells — it walks all non-deleted rows via keyset pagination and enqueues a standard per-cell job for each, with the same `jobKey` shape as live triggers (this resolves the race by construction, not by luck). A crash mid-enumeration just means a fresh run from the start (no checkpoint needed, since enqueue is jobKey-idempotent and cheap). A completed property-type data migration (above) ends with an explicit enqueue of the same full job for dependent rollups.

### Formula — deliberately out of v1

`formula` is **entirely excluded** from the v1 `properties.type` enum (not "reserved with a note"). Nothing in today's catalog needs a formula — computed fields today are `owner: 'system'` properties written by module code.

- A separate `SchedulerStore` module for `project_heartbeats`, inside the same protected write-enforcement package but architecturally independent of the generic engine — same import ban and Postgres role restrictions, own code path. All `next_fire_at` scheduling logic (rule → next due time, sweep advance, insert/edit recompute) lives inside `SchedulerStore`, never inside the generic engine.
- Idempotency-Key + ifVersion optimistic concurrency at the choke-point.
- Property type migration (eager conversion job).
- Heartbeat infrastructure: schema, `rule` validation (zod discriminated union), `next_fire_at` computation per trigger type (fixed/floating), catch-up policy, minute-granularity sweep scheduler with `FOR UPDATE SKIP LOCKED`, the `onItemEvent` write path through the choke-point, timezone (`timezone` property + DST handling).
- Job queue infrastructure sufficient for heartbeats and rollup: build `packages/queue` on **graphile-worker**, with `registerTask`/`enqueueJob` wrappers and a `CORE_TASK_NAMES` constant (transactional enqueue, `jobKey` dedup, retry/backoff with `max_attempts: 3`). Note: the runtime `TASK_NAMES` merge (CORE + module manifests) happens in the module-system issue (#29), not here.
- The AGENT.md two-layer model: a generated permission manifest (computed at runtime, never cached) + drift check (a heartbeat reporting a manifest↔text mismatch and an `owner_process` with no corresponding module).
- The `owner_process` column and its drift detection.
- The delegation model: the `agent_runs` table (including the `unit` column, described minimally for future use), `parent_run_id`, the supervisor "Semp"/Semprec as a data record (a system project + a "System settings" DB with a `name` property). Actually RUNNING an LLM agent should be implemented as a pluggable interface/stub (see below, out of scope).
- `resource_grants` — schema only, no enforcement beyond the binary owner/agent_run check.
- The rollup engine in full: config validation, the `rollup_dependencies` index, mirror lifecycle validation, the deterministic recompute flow (three trigger events, full cell recompute, backfill), the `computed` namespace (declared module keys vs. rollup keys).
- `formula` excluded from the v1 type enum (comment/enum only, no implementation).

### Out of scope

- **Views, filters, and sorting** (issue 02) — `views.config.filter`, the filter tree, anything about displaying/querying data beyond the base choke-point. This issue's filter-tree mention is only a precedent for a validated-jsonb pattern, nothing more.
- A full **ModuleManifest/ModuleRegistry** system (module registration, `heartbeatActions`, `computedKeys`, drift check over the whole registry) — implement only a minimal in-process registry (a map of `action_id → handler`) as a temporary stub; the full system arrives in a separate module-system issue (09). This also covers the module-extensible `heartbeatRuleKinds` registration mechanism mentioned in the specification (letting a module add its own heartbeat trigger `kind` without touching core) — the five core trigger kinds above are all this issue implements; the extensible registration point is future work for the module-system issue.
- Actually **running an AI agent / LLM session** (`AgentSession`, runtime prompt assembly, agent MCP tools) — implement `core.agentRun` as an interface that creates an `agent_runs` row and calls an injected/pluggable function; the real implementation is a later issue about agent orchestration.
- The full **notifications** system (typology, delivery channels, WS/push) — only a minimal table sufficient for the `heartbeat_error` write.
- The **realtime channel** (LISTEN/NOTIFY fan-out to WS) — just ensure rollup/property invalidation has a hook to attach to later; actual delivery to clients is out of scope.
- Specific **module heartbeat actions** and their business logic — belong to the modules that define them.
- The **formula engine** implementation (v2, deliberately deferred).
- Full **user/auth management** (`users` table only as a minimal FK-referential stub).
- Actual **sharing enforcement** (`resource_grants` consultation in the choke-point for non-owner requests) — schema exists, enforcement doesn't.
- Binary/blob storage for free-form content (a separate layer outside this section).
