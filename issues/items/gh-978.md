## Context

Row-level security now guards every tenant table: #973 gave each one a RESTRICTIVE policy `tenant_isolation USING/WITH CHECK (tenant_id = (SELECT app_tenant_default()))` plus a PERMISSIVE `tenant_rows USING (true) WITH CHECK (true)`. #968 created the functions those policies read:

- `app_current_tenant()` = `NULLIF(current_setting('app.tenant_id', true), '')::uuid` (STABLE). The `NULLIF` matters: once a transaction-local `set_config` ends, the GUC reads `''`, not NULL.
- `app_sole_tenant()` returns the id of the only `tenants` row while exactly one row exists, and NULL otherwise.
- `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())`. This is the transition definition: #1067 later redefines it as `app_current_tenant()` alone.

Nothing sets `app.tenant_id` yet. So every query still falls back to the sole tenant, and nothing in the code knows which tenant it is working for.

This issue adds that knowledge and pushes it into Postgres. Every later `mt-context` issue (authentication, listeners, queue, fan-out) only enters a scope. This issue is where the scope reaches the database.

Facts about the code (develop @ 737a1219):
- `withTransaction` (`backend/packages/data/src/db/pool.ts:75-122`) is the only sanctioned transaction opener (`docs/adr/2026-09-29-withtransaction-is-the-sole-transaction-opener.md`). It issues `BEGIN` or an isolation variant at `pool.ts:83-89`.
- `createPool` (`pool.ts:19-35`) returns a plain `pg` `Pool`. All four services and the three data-layer CLIs build their pool with it:
  - `backend/services/semprec-api/src/serve.ts:94`, `backend/services/semprec-agents/src/serve.ts:23`, `backend/services/semprec-transcribe/src/serve.ts:11`, `backend/services/semprec-ai-gateway/src/serve.ts:13`;
  - `backend/packages/data/src/db/runMigrationsCli.ts:18`, `backend/packages/data/src/db/runSeedCli.ts:9`, `backend/packages/data/src/observability/restoreTestResultCli.ts:13`.
- The same pool is handed to graphile-worker as `pgPool` (`backend/services/semprec-api/src/queueRuntime.ts:80`).
- Test pools are plain `new Pool` (`backend/packages/data/src/testSupport/testDb.ts:61`). Only the `withTransaction` part of this issue applies to them.
- `withClient` (`pool.ts:156-163`) acquires through `pool.connect()`.
- pg-pool 3.x has two behaviours that matter here:
  - Its own `Pool.prototype.query` acquires through `this.connect(callback)`. An overridden `connect` is therefore re-entered by an un-overridden `query`.
  - It reassigns `client.release` on every checkout.
- `AsyncLocalStorage` precedent: `backend/packages/shared/src/traceContext.ts:19,46-54`.
- A socket's event callbacks run in the async context in which the socket was opened. A pooled connection first opened inside one request's tenant would deliver its LISTEN `notification` and `error` events in that tenant's scope for the rest of its life. This issue prevents that (Task step 3.3).

## Task

Load `adr-conventions` (new ADR), `io-hardening` (pooled-client acquire/release), `error-handling` (rollback/reset paths) and `state-writes` (`withTransaction`, `runAfterCommit`).

1. **Create `backend/packages/shared/src/tenantScope.ts`** and export it from `backend/packages/shared/src/index.ts` with one `export * from "./tenantScope.js";` line. It contains:
   - `export type TenantScope = { readonly kind: "tenant"; readonly tenantId: string } | { readonly kind: "system"; readonly reason: string }`.
   - `export class TenantScopeConflictError extends Error` and `export class TenantScopeMissingError extends Error`. Each sets its own `name`. Neither extends `ChokePointError`, so both surface as a 500.
   - `runInTenant<T>(tenantId: string, fn: () => T): T`:
     - It throws `TypeError` and does not call `fn` unless `tenantId` is a canonical UUID. Store it lower-cased.
     - With no current scope, or inside a system scope, it enters the tenant.
     - Inside the same tenant it just runs `fn`.
     - Inside a different tenant it throws `TenantScopeConflictError`.
   - `runAsSystem<T>(reason: string, fn: () => T): T`:
     - `reason` must be non-empty.
     - It enters `{ kind: "system", reason }` from no scope or from a system scope. The inner reason wins.
     - Inside a tenant scope it throws `TenantScopeConflictError`. Otherwise system scope would be a way to leave one tenant and enter another.
   - `currentTenantScope(): TenantScope | undefined`.
   - `enforceTenantScope(site: string): TenantScope | undefined`. When a scope is active it returns it. Otherwise it applies the mode read from `SEMPREC_TENANT_SCOPE` on every call:
     - Unset, `""` or `warn` means warn mode. It logs at warn level, message `tenant_scope_missing`, with `{ site, stack }`, then returns `undefined`. It logs at most once per distinct stack per process, kept in a set capped at 1,000 stacks; once the set is full, every further novel stack still logs.
     - `strict` throws `TenantScopeMissingError` naming `site`.
     - Any other value throws an `Error` naming the value.
     - The release checkpoint (#1058) counts these `tenant_scope_missing` records, and #1067 flips the default to `strict`.
   - `runDetachedAsSystem<T>(reason: string, fn: () => T): T`. It runs `fn` in a fresh system scope regardless of the current scope. Its only permitted use is opening shared, long-lived I/O resources whose event callbacks must never inherit a caller's tenant. Today that means Task step 3.3. It is never used to run work.
   - Use `AsyncLocalStorage.run` only, never `enterWith`.
   - Create this module's logger (`createLogger("tenant-scope")`) lazily on first use. #979 makes `logger.ts` import this file, so a top-level call would hit the import cycle.
2. **Change `withTransaction`.**
   - Before acquiring a client, call `enforceTenantScope("withTransaction")`. In strict mode the error is thrown before any connection is taken.
   - When a scope exists, run `SELECT set_config('app.tenant_id', $1, true)` right after the `BEGIN` statement, for every isolation variant. Pass the tenant id, or `''` for a system scope.
   - A failing `set_config` takes the existing rollback/release path, and the original error propagates.
   - On a pool from `createPool`, acquire the client without the session-level hook from step 3.1, so a transaction pays exactly one extra statement.
   - With no scope (warn mode), behave exactly as today.
3. **Make `createPool` return a scope-applying pool.** It is still typed `Pool`, so call sites do not change.
   1. `connect()`, both the promise and the callback form:
      - Call `enforceTenantScope("pool.connect")`.
      - With a scope, run `SELECT set_config('app.tenant_id', $1, false)` after checkout. Install a per-checkout `release` wrapper that runs `RESET app.tenant_id` before handing the client back. If the reset fails, release it with that error so `pg` destroys it, and log it. The caller's `release()` never throws.
      - If the checkout `set_config` fails, release the client with the error and reject with the original error.
   2. `query(textOrConfig, values?)`, the promise forms:
      - Call `enforceTenantScope("pool.query")`.
      - With a scope, run `BEGIN`, `SELECT set_config('app.tenant_id', $1, true)`, the statement, then `COMMIT` on a client acquired without the session hook, and resolve with the statement's result.
      - On failure, `ROLLBACK`. A failing `ROLLBACK` destroys the client. Reject with the original error.
      - With no scope (warn mode), keep today's plain pass-through. Apply enforcement exactly once per call, not again through pg-pool's internal `this.connect`.
   3. Open every physical connection inside `runDetachedAsSystem("database-connection", …)`. For example, pass `pg` a `Client` subclass whose `connect` runs inside it. Its socket callbacks then run in system scope.
4. **Add the ADR** `docs/adr/<YYYY-MM-DD>-tenant-scope-propagation.md` (`status: accepted`, `area: [backend]`). It records:
   - the scope API and its nesting table;
   - the three pool paths and the GUC `app.tenant_id`;
   - the warn/strict modes;
   - the containment rules:
     - long-lived loops, listeners and registries start inside `runAsSystem` and re-enter a tenant explicitly per message or job;
     - tenant identity never comes from request bodies, model output, or headers set by untrusted callers;
     - no `enterWith`;
     - connections are opened detached.
   - the rejected alternative: an explicit tenant DB handle on every call. It touches nearly every file and every in-flight issue, and it still needs a runtime guard.
   - that the scoped autocommit `pool.query` is a single-statement transaction inside `pool.ts`. Its client never escapes, so no `runAfterCommit` callback can attach. It cites `[[2026-09-29-withtransaction-is-the-sole-transaction-opener]]` (not superseded) and the row-level-security ADR added by #968 by its slug.

## Acceptance criteria

The unit criteria live in `tenantScope.unit.test.ts` and touch no Postgres. The integration criteria live in `tenantScopePool.test.ts` and run on `createPool(process.env.TEST_DATABASE_URL)`.

- **Unit:** scope reporting.
  - Outside any scope, `currentTenantScope()` is `undefined`.
  - Inside `runInTenant(T)` it is `{ kind: "tenant", tenantId: T }`, and inside `runAsSystem("r")` it is `{ kind: "system", reason: "r" }`.
  - The outer scope is restored after `fn` returns and after it rejects.
- **Unit:** nesting.
  - Same-tenant re-entry runs `fn`.
  - A different tenant inside a tenant throws `TenantScopeConflictError` without calling `fn`, and so does `runAsSystem` inside a tenant.
  - A tenant inside system enters it, and system inside system takes the inner reason.
- **Unit:** argument checks. `runInTenant("abc")`, `runInTenant("")` and a UUID with trailing characters each throw `TypeError`; `runAsSystem("")` throws; in every case `fn` is not called.
- **Unit:** two concurrent `Promise.all` branches in different tenants each observe only their own tenant across `await` and `setTimeout`.
- **Unit:** enforcement modes.
  - With `SEMPREC_TENANT_SCOPE` unset or `warn`, `enforceTenantScope("x")` outside a scope returns `undefined` and writes one warn record `tenant_scope_missing` with `site` and `stack`. A second call from the same call site writes none.
  - With `strict` it throws `TenantScopeMissingError` naming the site.
  - With `bogus` it throws an `Error` naming `bogus`.
  - Inside a scope it returns the scope and logs nothing.
- **Unit:** `runDetachedAsSystem` inside `runInTenant(T)` runs `fn` in a system scope, and `T` is current again afterwards.
- **Integration:** with `T` a random UUID, `SELECT app_current_tenant()` returns `T` inside `runInTenant(T)` through:
  - `withTransaction` (default, `repeatable_read` and `serializable`);
  - `pool.query`;
  - an autocommit statement on a `pool.connect()` client.
- **Integration:** inside `runAsSystem`, all three paths read `current_setting('app.tenant_id', true)` as `''` and `app_current_tenant()` as NULL.
- **Integration (no leak):** on a `max: 1` pool, after a scoped `pool.query`, a scoped connect/release and a scoped `withTransaction`, the next unscoped checkout has the same `pg_backend_pid()` and never reads `T` from `current_setting('app.tenant_id', true)`.
- **Integration:** a scoped `pool.query` with a syntax error rejects with the original Postgres error. The next statement on the same connection is not in an aborted transaction and sees no tenant.
- **Integration:** a scoped `pool.connect()` client whose backend was killed with `pg_terminate_backend` before release:
  - `release()` does not throw;
  - the connection is discarded;
  - the next checkout works on a new `pg_backend_pid()`.
- **Integration:** with `SEMPREC_TENANT_SCOPE=strict` and no scope, `withTransaction`, `pool.query` and `pool.connect` reject with `TenantScopeMissingError`. `pool.totalCount` is unchanged and no client is left checked out.
- **Integration:** with no scope in warn mode, the three paths run their statements unchanged (no `set_config`).
- **Integration:** a LISTEN client opened on a fresh pool inside `runInTenant(T)` delivers `notification` events with `currentTenantScope()` of kind `system`, not `T`.
- **Integration:** a `runAfterCommit` callback registered inside a scoped `withTransaction` fires after `COMMIT`, and sees the caller's scope.
