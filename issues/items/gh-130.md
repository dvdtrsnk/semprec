**Blocked by:** #128

## Context

Granted tools may still require a human judgment for each concrete invocation. This baseline must land before the later generic-operation audit issue evolves its persistence and replay protocol.

## Task

Create `approval_requests` with UUID id, non-null agent run id, tool name, risk-class snapshot, exact deferred choke-point payload, status `pending|approved|rejected`, request/decision timestamps, and nullable deciding user. In the outbound MCP invoke choke point, when a visible tool has `requiresApproval`, transactionally insert one pending request, enqueue nothing, and immediately return a successful synthetic tool result containing the request id and awaiting-approval state. The agent turn and run complete normally as `done`. Non-approval tools continue directly. Pending rows have no expiry.

## Scope

### In scope

- Baseline table, synchronous request writer, synthetic result, and normal run completion.

### Out of scope

- Decision execution, sandboxing, expiry, notification delivery (owned by #149), and #89's later resource snapshots/exactly-once columns.

## Acceptance criteria

- A mixed parallel tool turn receives one result for every call without waiting.
- Approval-required calls cause no external tool effect and no queued job.
- Request metadata is an immutable invocation-time snapshot.
- Request creation either commits once or rolls back without a partial pending row.
