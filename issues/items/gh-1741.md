**Model tier:** medium

## Context

Model tier rationale: A chunked per-tenant rewrite of the search index that must rebuild attachment text from stored bytes without losing it, following an existing job pattern but with a real data-loss risk if done naively.

Two things leave existing mail with a stale search index: the sender has not been indexed (#1591), and the search configuration changes when Czech word search is activated (#1589). The only existing repair is `mailSearchReindexSweep` (`handleMailSearchReindexSweepTask` in `backend/packages/data/src/mail/mailSyncJob.ts`, daily). It reindexes only Emails missing from `item_search_index` and builds the text from `name` and `body` only; running it over indexed rows would drop the text of PDF/DOCX attachments, which is extracted at ingest (`mail/attachmentTextExtraction.ts`, `ingestAttachments` in `mail/attachments.ts`) and kept only in the index, not stored anywhere else.

Decision: the job rebuilds the text exactly as ingest does through `buildMailSearchText` (subject, body, attachment text, sender), re-extracting attachment text from the stored bytes of the message's `mail_attachments` rows. It reads bytes from the mail attachments storage the worker already has; an attachment whose bytes cannot be read, or whose text cannot be extracted, contributes no text and does not fail the message. Deleted messages are skipped. The same job serves the reindex after Czech word search is activated for mail rows the generic indexer leaves out.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. Add a core task `mailSearchTextReindex` (`CORE_TASK_NAMES` in `backend/packages/queue/src/index.ts`, handler in `worker.ts`) that runs `forEachActiveTenant` and, for each tenant, pages through non-deleted Emails items by id (keyset, one transaction per page, `docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`).
2. For each item, build the text with `buildMailSearchText` from the item's subject, body, the sender from `mail_message_meta.envelope.from` and the extracted text of its attachments, and recompute `search_vector` through `reindexItemSearch`.
3. Make it idempotent and resumable: a retry restarts from the beginning and produces the same index. It must not be enqueued by `mailSearchReindexSweep`; enqueue it once at deploy under a fixed job key, and expose an enqueue function for use after Czech search activation.
4. Add tests: after the job a message is found by its sender and by its PDF attachment text; a deleted message is not in the index; a missing attachment file does not fail the job; a second run changes nothing; another tenant's index rows are untouched.

## Scope

### In scope

- The per-tenant, chunked rebuild of the mail search index including sender and attachment text.

### Out of scope

- The sender at ingest and the shared text builder: #1591.
- Changing the search configuration or query builder: #1589.
- Changing `mailSearchReindexSweep`.

## Acceptance criteria

- When the job runs on existing mail, then a message is found by its sender's name and its PDF/DOCX attachment text remains searchable.
- When a message is deleted, then it is not in the index after the job.
- When an attachment file is missing, then the job still completes for the rest.
- When the job runs twice, then the index is unchanged the second time.
