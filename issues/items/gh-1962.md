## Context

Model tier rationale: One system-owned database delivered through the established seed, cutover and i18n path for fresh and existing tenants; the pattern exists, but the ownership settings are what keeps subscribed events read-only, so they need explicit tests.

Subscribed calendars show events the user cannot edit. They need a place to be stored before a feed can be imported (#2004 imports the feed downloaded by #1960, #2005 shows the stored events in the calendar timeline of #1717, and #1966 adds recurrence). This issue adds only that place: the `subscribedEvents` database. #1971 (dropping `includeTime` from the Events date config) is ordered after this issue in the seed order.

Ownership: every property of Events is owned by the user, so a read-only event cannot live in Events (`assertWritableProperties` in `backend/packages/data/src/chokePoint/itemWrites.ts`). Instead a system database `subscribedEvents` belongs to the calendar module, with all properties `owner: 'system'` and `ownerProcess: 'calendar'`; the generic write path then refuses any user, agent or `/mcp` write with 403 `forbidden`, and the later import writes through the choke point's system-owner-process option (`systemOwnerProcess`).

Properties: `uid` (text), `title` (title), `startsAt` (date with time), `endsAt` (date with time, nullable), `timeZone` (text, the feed's original IANA zone, nullable), `allDay` (checkbox), `place` (text, nullable), and a relation `calendar` to the Calendars database (one calendar has many subscribed events).

Decision: a subscribed event that disappears from its feed is moved to the trash (soft delete), not deleted permanently; the existing 30-day purge removes it, so tasks and recordings linked to it are not lost at once and the removal is reversible. This database therefore keeps the generic trash behavior and adds no hard-delete path; the import issue applies the rule.

Shared-file ordering: this issue also waits for #1958 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Declare the `subscribedEvents` database in the calendar module manifest (database descriptor) and seed it (properties above, all `owner: 'system'` with `ownerProcess: 'calendar'`, the relation to Calendars, locked schema) in the calendar module seed after the Calendars seed of #1925.
2. Add a cutover step `backend/packages/data/src/calendar/subscribedEventsCutoverMigration.ts`, registered in `runTenantCutoverMigrations`, that creates the database, properties and relation for existing tenants when missing (idempotent, suspended tenants included; a tenant without a Calendars database is skipped). Pattern: `backend/packages/data/src/transcription/transcriptsCatalogCutoverMigration.ts`.
3. Add i18n keys for the database and each property in `seed/i18n/cs.json` and `en.json` ("Odebrané události"/"Subscribed events" and so on); bump the manifest version.
4. Tests: a fresh seed has the database with the properties, owners and relation above; the cutover creates it for an existing tenant and a second run changes nothing; a generic `POST` into the database and a `PATCH /api/items/:id` on a row created with the system writer answer 403 `forbidden` over REST and `/mcp`; a system write with `systemOwnerProcess` `calendar` succeeds.

## Scope

### In scope

- The `subscribedEvents` database, its system-owned properties and its relation to Calendars, for fresh and existing tenants.

### Out of scope

- Storing the subscription URL: #1925; downloading: #1960.
- Parsing a feed and writing subscribed events: #2004.
- Showing subscribed events in the calendar timeline: #2005.
- Recurring subscribed events (`RRULE`, `EXDATE`, `RECURRENCE-ID`): #1966.
- Czech public holidays and birthdays, which are generated rather than imported: #1804, #1800.
- Editing, hiding or recoloring individual subscribed events.

## Acceptance criteria

- When a new tenant is seeded, then it has a `subscribedEvents` database whose properties are all system-owned by the calendar module, with a `calendar` relation to Calendars.
- When the cutover runs for an existing tenant, then the database is created; a second run changes nothing.
- When a user, agent or `/mcp` client creates or patches a subscribed event through the generic write path, then the answer is 403 `forbidden`.
- When the calendar module writes a subscribed event with its system owner process, then the write succeeds.
- The full backend `pnpm run verify` passes.
