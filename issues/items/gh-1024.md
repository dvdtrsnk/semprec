## Context

Model tier rationale: One UPDATE helper and one call inside the reset transaction are specified exactly.

`push_subscriptions` is a global identity-plane table (no `tenant_id`, no row-level security), user-scoped in code like `sessions`. A registration is meant never to outlive the session that created it:
- `logout` and `revokeUserSession` cascade to the session's registrations through `revokePushSubscriptionsForSession` (`backend/packages/data/src/auth/authActions.ts:220-223`, `:232-240`; `backend/packages/data/src/push/pushSubscriptionsStore.ts:146-157`).
- A deleted session only orphans its registrations. `session_id` is set to NULL (`backend/packages/data/src/db/migrations/0054_push_subscriptions_session_id_on_delete_set_null.sql:7-10`), and the row stays active.

Password reset breaks this:
- `resetPassword` (`backend/packages/data/src/auth/passwordResetActions.ts:118-138`) is the recovery path for a compromised account. It revokes every session of the user (`:137`, `revokeAllSessionsForUser`, `backend/packages/data/src/auth/sessionsStore.ts:116-122`).
- It never touches `push_subscriptions`. A device an attacker registered before the reset therefore keeps receiving the account's push notifications after the password changed. So does any session-less registration.
- The reset route already runs `resetPassword` inside `withTransaction` (`backend/services/semprec-api/src/authHandler.ts:202-204`).

#1014 last changed `pushSubscriptionsStore.ts` (silent rebind of an endpoint). #1041 reuses the user-wide revocation added here when an admin suspends an account.

## Task

Load `state-writes` (a set-based revocation whose zero count is legitimate, committed with the reset).

1. **Store.** Add `revokeAllPushSubscriptionsForUser(client: Pool | PoolClient, userId: string): Promise<number>` to `pushSubscriptionsStore.ts`.
   - It runs `UPDATE push_subscriptions SET revoked_at = now(), updated_at = now() WHERE user_id = $1 AND revoked_at IS NULL`. This covers session-less rows too.
   - It returns `rowCount`. Zero is a legitimate outcome: a user may have no registrations.
   - Its docstring names both callers' intent: every registration of a user ends when the account's access is reset.
2. **Reset.** Call it in `resetPassword` right after `revokeAllSessionsForUser`, on the same client, so it commits or rolls back with the password change. Add one sentence to `resetPassword`'s docstring (`:95-117`) saying push registrations are revoked with the sessions.
3. **Public surface.** Add `revokeAllPushSubscriptionsForUser` to the runtime-export list in `backend/packages/data/src/__tests__/publicSurface.test.ts`. The store is re-exported by `export *` at `backend/packages/data/src/index.ts:295`, so `index.ts` itself needs no edit.
4. **Tests.**
   - Add the reset cases to `backend/packages/data/src/__tests__/passwordResetActions.test.ts`.
   - Add the count cases to `backend/packages/data/src/__tests__/pushSubscriptions.test.ts`.

## Scope

### In scope
- The user-wide push-registration revocation, its use in `resetPassword`, and their tests.

### Out of scope
- Silently rebinding an endpoint registered by another account (#1014).

- The password-reset page and link format (#1076).
- Per-IP throttling of reset requests (#1073).

## Acceptance criteria

- **Reset revokes.** After a successful `resetPassword`, every previously active registration of that user is revoked: web push, APNs, and a row whose `session_id` is NULL. Another user's registrations stay active. (integration, `passwordResetActions.test.ts`)
- **Failed reset.** A reset rejected for an invalid, consumed or expired token, or for a too-short password, revokes no registration. (integration, `passwordResetActions.test.ts`)
- **Atomic with the reset.** When the reset transaction rolls back after the revocation, the registrations are active again and the password is unchanged. Force the rollback, for example by throwing after `resetPassword` inside the test's own `withTransaction`. (integration, `passwordResetActions.test.ts`)
- **Count.** `revokeAllPushSubscriptionsForUser` returns the number of rows it revoked. It returns 0 for a user with no active registration, and 0 again when called a second time. (integration, `pushSubscriptions.test.ts`)
