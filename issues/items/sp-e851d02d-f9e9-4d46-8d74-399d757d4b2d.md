### Requirement gh-1835: [sleep 10/13] Upsert and reset a single night through PUT /api/sleep/nights/:night

#### Context

Model tier rationale: A custom write route that must create-or-update exactly one item per night under an advisory lock, stay inside the choke point so hooks, realtime and heartbeats apply, and be idempotent under concurrent retries.

Changing one night (a different bedtime, wake time or alarm for a single date) is stored as an exception item in `sleepNights` (#1776) that overrides the plan field by field. The generic API can express this only as two requests, a POST with an `Idempotency-Key` followed by a PATCH with a mandatory `ifVersion`; a drag in the calendar and an agent do not hold a version, and the answer a client needs is the resolved night (plan merged with exception), not the raw item. There is no "write by date" operation: `updateItemWithClient` without `ifVersion` merges by property key, `itemsStore.hardDeleteItem` removes only trashed rows, and a custom route must not write outside the choke point or do CRUD over module data (decision record `2026-09-11-module-manifest-custom-routes`). The pattern for "one item per key" is `getOrCreateJournalItem` in `backend/packages/data/src/journal/journalStore.ts`.

This issue adds `PUT /api/sleep/nights/:night`. It builds on the value rules and the per-night advisory lock key of #1784 and on the read route and loader of #1809; the resync push (#1838) and the sleep agent tools (#1840) build on it.

Decisions:
- The route is justified as `transactional-semantics`: a find-or-create plus a patch in one transaction, a response that is a resolved night, and callers that do not hold an item version.
- "Reset to plan" is a PUT with every field null. The exception item stays with all fields null (`changed` false) and is not deleted, consistent with 30-day restore for deleted items. If no item exists and every field is null, nothing is written.
- An exception is allowed for a night without a plan, and for past and future nights alike. The server does not enforce 5 or 15 minute steps.
- Old exceptions are kept as history; past exceptions are never pruned.

Shared-file ordering: this issue also waits for #1828 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1838: [sleep 11/13] Enqueue a debounced sleep resync push after sleep writes, deletes and timezone changes

#### Context

Model tier rationale: A new cross-process job triggered from write, delete, restore and system-setting hooks inside the write transaction, with debounce semantics and per-tenant delivery to device registrations, so a wrong trigger or key leaks pushes across tenants or loses reschedules.

The iPhone schedules the alarm and the bedtime reminder itself, so it must learn when sleep data changed on another device, on the web or through an agent. The backend neither rings nor schedules anything. With #1445 it can send a silent background push. Today the scheduler's heartbeats (`onItemEvent`) fire on create, update and delete but not restore, and a heartbeat needs a registered action id, a handler and a seeded row; the System settings timezone change is handled in `itemWrites.ts` by `recomputeAllForTimezoneChange`. Jobs are enqueued with `enqueueJob` (`backend/packages/queue/src/index.ts`) inside the writing transaction, with `jobKey`, `jobKeyMode: "replace"` and `runAt`. Registrations live in the global `push_subscriptions` table (channel `web_push` or `apns`, platform `web`, `ios` or `macos`, `device_token`, `apns_environment`), read with `listPushSubscriptionsForUser` and revoked with `revokePushSubscriptionByProviderInvalidation` (`push/pushSubscriptionsStore.ts`).

This issue adds the job `sleep.resync`: after any change to sleep data it sends one silent push `{ kind: "sleepResync" }` to the user's iOS registrations about 30 seconds later. Several changes inside the window collapse into one push. It builds on the sleep hook chain (#1784, #1799), the PUT route (#1835), the delivered module (#1779), the delete and restore hooks (#1601) and #1445. The agent tools for sleep nights (#1840) rely on it so agent writes reach the phone.

Contract for the iOS client (not implemented here): after a `sleepResync` push, on a realtime invalidation, at launch and in a background refresh, it reads `GET /api/sleep/nights` for the next 14 nights, schedules a system alarm with a fixed date for every night whose `alarm` is true (not a weekly repeat, because of exceptions) using `alarmSound` and a `alarmSnooze` repeat after 9 minutes, schedules a local reminder at `prepReminderAt` when it is not null, and cancels everything when `enabled` is false. When `enabled` and `muteSemp` are both true, the client does not schedule local notifications (task reminders, calendar alerts) inside the window from `bedAt` to `wakeAt` of the resolved nights: it moves them to `wakeAt` and reschedules after a resync push. The bedtime reminder and the alarm are never moved.

Decisions:
- Only iOS registrations (`channel` `apns`, `platform` `ios`, not revoked) receive the push; macOS and web nothing. iPad registrations also use platform `ios`, so they receive it too and the iPad rings the alarm as well; there is no per-device setting.
- No server-side bedtime reminder is sent as a visible notification and no row is created in `notifications`; the bedtime reminder is a local notification on iOS only.
- The job payload carries only the tenant id; the handler finds the user through `users.tenant_id` (one user per tenant).

Shared-file ordering: this issue also waits for #1819 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1839: [areas-projects 12/13] Add the relation.related operation

#### Context

Model tier rationale: This adds a new catalog operation reachable by agents over MCP whose counts must respect soft deletion, archived databases and per-database agent grants, across many relation shapes (including one-way edges read from the target side), so a mistake leaks existence or counts across an authorization boundary.

A record page shows, below its content, a "related" section: one row per collection with the number of records connected to the open record, and tapping a row opens that collection already filtered to those records. Today there is no way to ask for it. `item_relations` is readable from both ends (indexes on `item_a` and `item_b` in `0001_core_schema.sql`), but the generic operation catalog (`backend/packages/shared/src/genericOperations/operationNames.ts`) has no edge read or count, and no related endpoint exists. The counts must still include them from the target side.

This issue adds the operation `relation.related` and `GET /api/items/:id/related`. It builds on: #1517 (the declared per-record-type order), #1404 (relation reading primitives), #1407 (database display order), #1810 (per-database grants), #1363 (one extra relation hop in filters), #1526 (emptiness filters), #1597 (per-database area filters declared in manifests), #1538 (Events linked to Areas).
