**Model tier:** high

## Context

Model tier rationale: This introduces a new authorization-adjacent contract in which the choke point aborts an agent transaction and the approval gateway must snapshot, revalidate and exactly-once replay three new write kinds, so it is high.

Today an agent write reaches the approval queue only in two cases: one of five destructive generic operations (`database.archive`, `property.delete`, `view.delete`, `item.delete`, `relation.delete`, flagged by `requiresApproval` in `backend/packages/shared/src/genericOperations/capabilities.ts`), or an external MCP tool that requires approval. Every other agent write, including `item.patch`, `relation.put` and `relation.set`, executes immediately (ADR `docs/adr/2026-09-18-non-destructive-generic-operations-bypass-agent-approval.md`). The gateway (`backend/packages/application/src/genericOperationGateway.ts`) only knows `DestructiveOperationName` (the five kinds), and `ResourceSnapshotKind` and the projection in `backend/packages/data/src/chokePoint/destructiveProjection.ts` also cover only those five. Approved requests are replayed exactly once (ADR `docs/adr/2026-09-18-exactly-once-execution-of-approved-destructive-operations.md`) through `replayApprovedGenericOperation`, with the execution wiring in `backend/packages/data/src/mcp/approvalRequestExecution.ts`. `item.patch` needs an `ifVersion`, which would be stale by the time an approved request runs. The generic application service port (ADR `docs/adr/2026-09-17-generic-application-service-port.md`) forbids a pre-check in the gateway followed by a separate write, so the decision to defer must be made inside the write's own transaction.

This issue builds the general mechanism: the choke point decides, inside the write transaction, that an agent write needs approval; it aborts with a typed error; the gateway turns that into an approval request with a resource snapshot; after approval the write is replayed exactly once with revalidation. It builds on the writer kind that #1415 threads into item and relation writes (so the choke point can tell an agent from a user), on `relation.set` from #1521, on the description and impact snapshot of #1683, and on the closed risk class set of #1423.

Decision: this issue builds the mechanism without a production trigger. Decided by the product owner: a plain `relation.set` that replaces an existing edge is an ordinary non-destructive write with the `write` risk class of #1423 and executes immediately; approval is forced only by the value-link-break flag that #1758 adds on top of this mechanism, and only when a link really breaks. Every other non-destructive agent write stays immediate.

Decision: only an agent writer that carries an `agentRunId` (#1415) is deferred, because an approval request belongs to a run. An `/mcp` call with a human session is recorded as an agent write without a run and stays immediate, as such calls are today.

Decision: no separate detail route for approval requests. Decided by the product owner: the approval detail view uses the existing single-request read `GET /api/approval-requests/:id` (#1786); another route would be an unnecessary special path.

Decision: the request description is rendered from the description template mechanism of #1683, and the risk class is taken from the closed set of #1423; this issue does not add new risk classes.

What builds on it: #1758, #1846 and #1913 extend the same files and rely on the gateway being able to defer a non-destructive operation; #1789 and #1772 consume the resulting requests.

## Task

Load `adr-conventions`, `state-writes`, `error-handling` and `testing`.

1. Add an ADR under `docs/adr/` (dated, narrowing `2026-09-18-non-destructive-generic-operations-bypass-agent-approval`): a non-destructive agent write is deferred to approval exactly when the choke point flags it inside its own transaction; the ADR states that a plain `relation.set` replacing an edge is not flagged (ordinary `write` risk class, no approval) and that each flagged case is added to the ADR by the issue that introduces it (the first is the value-link break of #1758); every other non-destructive agent write remains immediate.
2. In the choke point, add a typed error `ApprovalRequiredForWrite` (next to `ApprovalRequiredError` in `backend/packages/data/src/errors.ts`) carrying a list of reasons; the reason union is open and has no production kind in this issue (#1758 adds `breaksLinks`). Add the helper the choke point uses to raise it from inside a write transaction, using the writer kind from #1415: it raises only for an agent writer with an `agentRunId`, so the transaction rolls back and leaves no partial write. User writers, system writers and agent writers without a run never raise it. `relation.set` replacing an edge does not raise it.
3. Extend `DestructiveOperationName`/the operation name union in the gateway and `ResourceSnapshotKind` with `item_patch`, `relation_put` and `relation_set`; extend `DestructiveOperationCheck`, `computeDestructiveResourceProjection`, `buildDestructiveCheck` and `executeDestructiveWithClient` accordingly. For `relation_set` the snapshot hashes the current edge set of the relation on the source item. All three kinds are wired and tested, but no production trigger flags them in this issue. Replay does not use `ifVersion`: the snapshot hash replaces it.
4. In `GenericOperationGateway.invoke`, catch `ApprovalRequiredForWrite` from the application service, create the approval request (description and impact per #1683, risk class per #1423, resource snapshot) and throw `ApprovalRequiredError` with `approvalRequestId` and link, as for destructive operations.
5. Extend `replayApprovedGenericOperation` and `approvalRequestExecution.ts` so an approved request of these kinds is revalidated against the snapshot and executed exactly once on the same transaction; if the snapshot no longer matches (the edge set changed, a source or target was deleted), the request terminalizes as a conflict and nothing is written. Rejection changes nothing.
6. Cover with tests, using a reason raised by a write hook registered only in the test: an agent `relation.set` flagged this way produces a request and leaves the relation unchanged with no partial write; an agent `relation.set` replacing an edge without a flag executes immediately and creates no request; the same flagged write by a user, or by an `/mcp` call with a human session, executes immediately; approval executes once and a concurrent change before approval yields a conflict; rejection changes nothing.

## Scope

### In scope

- The deferral mechanism, the typed error, the three new snapshot kinds, snapshot-hash revalidation and exactly-once replay.
- The narrowing ADR, which records that a plain edge replacement is not deferred.

### Out of scope

- Breaking value links as a trigger, the `breaksLinks`/`endsInheritance` payload and the `breaksLink` description and risk class: #1758.
- Heartbeat tools approval: #1846; email send approval: #1913.
- Realtime invalidation and thread outcome posts for approval requests: #1789, #1772.
- Any production trigger, including a trigger for `relation.set` replacing an edge (decided: not deferred).
- A separate detail route for approval requests: not added (decided by the product owner); the detail view reads one request with `GET /api/approval-requests/:id` of #1786.

## Acceptance criteria

- When an agent write is flagged inside its transaction (in tests, by a test-only reason), then an approval request is created, the call returns an approval-required error and the relation is unchanged with no partial write.
- When an agent calls `relation.set` replacing a different edge, on an empty relation or with the edge it already has, and nothing flags it, then it executes immediately and no approval request is created.
- When a user, or an `/mcp` call with a human session, makes a flagged write, then it executes immediately.
- When the request is approved, then the replacement executes exactly once, even if the replay task runs twice.
- When the relation's edges changed between request and approval, then the request ends as a conflict and nothing is written.
- When the request is rejected, then the relation is unchanged.
- The new ADR exists, states which agent writes are deferred, and states that a plain `relation.set` replacement is not.
