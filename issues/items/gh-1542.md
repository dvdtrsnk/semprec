**Model tier:** medium

## Context

Model tier rationale: One additive property on a locked schema delivered by a direct-SQL cutover that also edits an existing relation definition, with the cutover fixture pattern available, but changing an existing relation definition on populated data is the risky part.

An Event has action items: tasks that came out of the event (`Events.actionItems`, a many-to-many relation to Tasks that is one-directional today, `property_id_b` null in `relation_definitions`, declared in `backend/packages/data/src/seed/seedTenDatabases.ts`). From the Tasks side nothing is known about its source event: `relation_contains` filters work only on the side that owns the property (`views/filterCompiler.ts`), so the app cannot ask "which tasks came from this event" with a Tasks query, and a task cannot show its source. Tasks and Events are `schema_locked`, so an existing tenant can receive a new property only through a code-level cutover that writes SQL directly, as `backend/packages/data/src/transcription/transcriptsCatalogCutoverMigration.ts` does for Transcripts and registered in `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`). This is a different link from a task hosted in an event (#1764): that relation is `Tasks.hostEvents`.

This issue adds the inverse property `Tasks.sourceEvents` of `Events.actionItems`. #1724 builds on it to make a new task inherit the project and people of its source event. Other issues refer to the same property as the owner of this inverse.

Decisions:
- The relation stays many-to-many and user-owned on both sides; whether a task may have several source events is not narrowed here.
- The property key is `sourceEvents`, its name is not stored (null) and is resolved from the catalogs.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. In `seedTenDatabases.ts` declare `Events.actionItems` as a two-sided relation with the inverse property `Tasks.sourceEvents` (owner `user`, many to many), so a freshly seeded tenant has both sides before the schemas are locked.
2. Add `backend/packages/data/src/tasks/tasksSourceEventsCutoverMigration.ts` (modeled on `runTranscriptsCatalogCutoverMigration`) and register it in `runTenantCutoverMigrations`: per tenant, in a transaction with the same table lock, do nothing when the Tasks or Events database or the `actionItems` property is missing or `Tasks.sourceEvents` already exists; otherwise insert the `sourceEvents` property on Tasks with raw SQL, set `property_id_b` of the relation definition of `Events.actionItems` to it, and set its `config` to `{ relationDefinitionId, targetDatabaseId: <Events database id> }`. Existing edges stay as they are and become visible from both sides. Running it twice changes nothing.
3. Add `property.tasks.sourceEvents.name` to `backend/packages/data/src/seed/i18n/cs.json` and `en.json`.
4. Tests: a fresh seed and a cut-over tenant have the same Tasks schema; existing `actionItems` edges are returned from the Tasks side (`relation_contains` query on `sourceEvents` returns the tasks of an event); a PUT of an edge from either side appears on both; `GET /api/schema` shows the property with Czech and English labels; the cutover is idempotent and does nothing for a tenant without the databases; the drift checks report nothing.

## Scope

### In scope

- The inverse property `Tasks.sourceEvents` for new and existing tenants and its labels.

### Out of scope

- Inheriting project and people from the source event: #1724.
- The hosted-in-event relation: #1540 and #1764.
- Creating a task together with the relation: #1590.
- Changing the cardinality of the relation: not planned yet; it waits for a product decision.

## Acceptance criteria

- When a Tasks query uses `relation_contains` on `sourceEvents` with an event id, then it returns the tasks that are action items of that event.
- When the cutover runs on an existing tenant, then existing action-item edges are visible from both sides and a second run changes nothing.
- When an edge is written from either side, then it is readable from both.
- When `GET /api/schema` is called, then `sourceEvents` appears with Czech and English labels, and a freshly seeded tenant has the same schema as a cut-over one.
