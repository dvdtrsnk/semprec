**Model tier:** low

## Context

Model tier rationale: The migration steps and every dead export to delete are enumerated exactly.

The settings item's `dailyBudgetUsd` and `monthlyBudgetUsd` properties no longer do anything:

- #1035 moved enforcement to the admin-owned `tenant_ai_budgets` table.
- #1048 moved the usage report's caps there too.
- No code path reads the properties any more.

They still exist, though, and mislead:

- Every tenant's System settings database still has both property rows, and its item still has both keys. They came from `seedSystem` (`backend/packages/data/src/seed/seedSystem.ts:169-195`) and from the retrofit `0019_settings_ai_budgets.sql:18-32`.
- `seedSystem`, which #1005's `provisionTenant` runs for every new tenant, still creates them.
- They are `owner: "user"`, so a user can still edit them and see no effect.
- Dead code remains in `backend/packages/data/src/systemSettings.ts`: `DEFAULT_DAILY_BUDGET_USD` (`:9`), `AiBudgets` (`:44-48`), the budget fields of `SettingsProperties` and `toSettingsProperties` (`:50-70`), `toAiBudgets` (`:72-77`), `readSettingsProperties` (`:79-92`) and `getAiBudgets` (`:94-101`).

This is the **contract step**. It must ship in a release after the code switch: the release one back must no longer read the properties. That holds for every release from #1048 on, and the release checkpoint #1058 confirms such a release ran in production. The settings database is not a module-manifest database. It is created directly by `seedSystem` with `schema_locked = true`, so its schema changes through a SQL migration using the same unlock/write/relock sequence `0019` uses (`:16`, `:34`).

## Task

Load `db-migrations` (contract step, data change in a migration) and `state-writes`.

1. **Migration** (take the next free ordinal at commit time). A header comment states that it is a contract step and names the issues that stopped reading the properties. For every `databases` row with `owner_module_id = 'systemSettings' AND system`, across all tenants (the migrating role bypasses row-level security):
   - set `schema_locked = false`;
   - `DELETE FROM properties WHERE database_id = <id> AND key IN ('dailyBudgetUsd', 'monthlyBudgetUsd')`;
   - `UPDATE items SET properties = properties - 'dailyBudgetUsd' - 'monthlyBudgetUsd' WHERE database_id = <id> AND (properties ? 'dailyBudgetUsd' OR properties ? 'monthlyBudgetUsd')`;
   - set `schema_locked = true` again.

   A database without the properties is skipped, so re-running changes nothing. On a fresh install the settings database does not exist yet at migration time, so the migration is a no-op there.
2. **`seedSystem.ts`:** remove the two `createProperty` calls, the two item values, the issue-#120 comment and the `DEFAULT_DAILY_BUDGET_USD` import. The settings database keeps `name` and `timezone`.
3. **`systemSettings.ts`:**
   - Delete `DEFAULT_DAILY_BUDGET_USD`, `AiBudgets`, `toAiBudgets`, `readSettingsProperties` and `getAiBudgets`.
   - Reduce `SettingsProperties`/`toSettingsProperties` to `timezone`. A non-string `timezone` must still throw (`:61-69`).
   - `getSystemTimezone`, `getSystemSettingsDatabaseId` and `getSystemSettingsItemId` keep their behaviour.
4. **`publicSurface.test.ts`:** remove `DEFAULT_DAILY_BUDGET_USD` and `getAiBudgets` from `EXPECTED_RUNTIME_EXPORTS` (`:62`, `:246`).
5. **Tests:**
   - `systemSettings.test.ts`: drop the budget cases and keep the timezone and malformed-timezone cases.
   - `settingsAiBudgetsMigration.test.ts`: it still covers `0019`, which still runs on old databases. Assert its backfill by reading the settings row and the `properties` rows with SQL instead of `getAiBudgets`.
   - Add `backend/packages/data/src/__tests__/settingsBudgetPropertiesRemoval.test.ts`. It builds the legacy shape (property rows plus item keys) and executes the migration file's SQL, the way `settingsAiBudgetsMigration.test.ts:10-13` does for `0019`.

## Scope

### In scope
- Removing both properties and both item keys from every tenant's settings.
- No longer seeding them.
- Deleting the dead budget code from `systemSettings.ts`.

### Out of scope
- Changes to `tenant_ai_budgets`, enforcement or the report (#1004, #1035, #1048).
- The admin budgets UI (#1081).
- Removing the `timezone` property or any other settings key.
- Editing migration `0019` itself: migrations that already ran are never changed.

## Acceptance criteria

- Set up two tenants with `createTestTenant(pool)` from #975's harness, both settings databases in the legacy shape. After the migration (integration):
  - no `properties` row with key `dailyBudgetUsd` or `monthlyBudgetUsd` exists in either settings database;
  - neither settings item has either key;
  - `name` and `timezone` values are unchanged;
  - both databases are `schema_locked = true` again.
- Running the migration a second time changes nothing (integration).
- A tenant provisioned after this change gets a settings database whose properties are `name` and `timezone` only, and an item without budget keys (integration, through `provisionTenant`).
- `getSystemTimezone` still returns the configured timezone, and a non-string `timezone` still throws "Malformed system settings properties" (integration).
- `@semprec/data` no longer exports `getAiBudgets` or `DEFAULT_DAILY_BUDGET_USD`, and `publicSurface.test.ts` passes (integration).
- The gateway and usage-report suites pass unchanged, proving nothing still reads the removed properties (integration).
