## Context

Model tier rationale: One well-specified protocol exchange added next to an existing token function, with secret-handling care (no tokens in errors) but no new persisted contract.

Connecting a Gmail or Outlook mailbox (#1686) must trade the authorization code the provider returns for a refresh token. `backend/packages/data/src/mail/oauthTokenExchange.ts` today only implements the `refresh_token` grant (`refreshAccessToken`); it has no `authorization_code` grant and no PKCE. `MICROSOFT_TOKEN_URL` already points at the `/common` endpoint, which is what lets both personal Outlook.com and Entra ID work accounts sign in, and `GOOGLE_TOKEN_URL` is exported next to it.

This issue adds the exchange function only. It does not persist anything; #1686 calls it outside the database transaction and stores the result.

Decision: the function takes the redirect URI, code, PKCE verifier and client credentials as input and returns the refresh token and the access token with its expiry. A response without a refresh token is an error, because the mailbox could not be synchronized after the first hour.

## Task

Load `error-handling`, `io-hardening` and `testing`.

1. In `backend/packages/data/src/mail/oauthTokenExchange.ts` add `exchangeAuthorizationCode({ tokenUrl, clientId, clientSecret, redirectUri, code, codeVerifier })` that POSTs a form body with `grant_type=authorization_code`, `code`, `redirect_uri`, `client_id`, `client_secret` and `code_verifier`, with the same 15 second timeout as `refreshAccessToken`.
2. Validate the JSON response the way `refreshAccessToken` does (object, non-empty string `access_token`, numeric `expires_in`) and additionally require a non-empty string `refresh_token`. Return `{ accessToken, expiresAt, refreshToken }`.
3. Map a 400 or 401 from the provider to a typed error that distinguishes "the authorization code was rejected" from other failures. Microsoft's `invalid_grant` or `consent_required` family for a tenant that needs administrator approval is surfaced as its own error kind (so #1686 can answer `mail_admin_consent_required`); this issue only classifies it, it does not add the HTTP error code.
4. No error message, thrown value or log line may contain the code, the verifier, the client secret or any token. Include only the status and the provider's short error code field.

## Scope

### In scope

### Out of scope

- Generating states, verifiers or challenges (#1483).
- Looking up the account address and aliases, and creating the mailbox (#1686).
- Changes to `refreshAccessToken` or persisting a rotated refresh token.

## Acceptance criteria

- When the provider returns a valid response, then the function returns the refresh token, access token and expiry; the request body contains `grant_type=authorization_code` and the `code_verifier`.
- When the response lacks a refresh token, access token or numeric `expires_in`, then the function throws.
- When the provider answers 400 or 401, then the thrown error is the typed "code rejected" error, and an administrator-consent response is distinguishable from it.
- When any failure is thrown, then its message and any logged text contain none of the code, verifier, secret or tokens (asserted in a test with sentinel values).
