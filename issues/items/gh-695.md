**Blocked by:** #671, #684

## Context

`runAfterCommit(client, callback)` (`backend/packages/data/src/db/pool.ts:10-27`) parks a callback in a module-level `WeakMap<PoolClient, Array<() => void>>` keyed by the pooled client; only `withTransaction` (`pool.ts:30-61`) drains that list after its `COMMIT` (or discards it on rollback). Two production code paths open transactions by hand and never drain it:

- `repairInterruptedRuns` (`backend/packages/agent-runtime/src/startupRepair.ts:36-69`): `pool.connect()`, `BEGIN`, `finishAgentRunWithErrorNotification` per orphaned run, `COMMIT`. `writeNotification` (`backend/packages/data/src/notifications/notify.ts:112`) registers `notifyNotificationCreated` through `runAfterCommit` for each `agent_run_error` notification it writes.
- `createPoolClientTransactionRunner` (`backend/packages/data/src/projectAgentGuidanceStore.ts:110-135`): `BEGIN ISOLATION LEVEL ...`, `COMMIT`. The guidance drift action (`backend/packages/application/src/projectAgentGuidance/driftAction.ts:119-190`) writes its findings' notifications through `notifications.create(tx, ...)` → `createGuidanceNotificationWriter` → `writeNotification`, inside this runner.

Because the key is the pooled `PoolClient` object, the parked callbacks are not merely lost: they stay attached to that client, and the next `withTransaction` that happens to acquire the same client from the pool fires them after *its* commit (or deletes them on *its* rollback). A guidance-drift `notification_created` push therefore reaches the realtime layer late, attached to an unrelated transaction, or never — and the startup repair's `agent_run_error` pushes behave the same way.

#671 changes `withTransaction`'s rollback handling (original error preserved, client discarded when `ROLLBACK` fails) and lands first; this issue extends the same function. D1 reorders the two writes inside `repairInterruptedRuns`, which this issue re-brackets.

## Task

1. **`withTransaction` accepts an isolation level.** In `pool.ts`, change the signature to `withTransaction<T>(pool: Pool, fn: (client: PoolClient) => Promise<T>, options: { isolation?: TransactionIsolationLevel } = {}): Promise<T>` with `TransactionIsolationLevel` imported from `@semprec/shared` (`backend/packages/shared/src/projectAgentGuidance.ts:38`, `"repeatable_read" | "serializable"`). The opening statement becomes `BEGIN` (no option), `BEGIN ISOLATION LEVEL REPEATABLE READ` or `BEGIN ISOLATION LEVEL SERIALIZABLE`. Everything else — commit, after-commit drain, #671's rollback/discard handling — is unchanged and now applies to both call sites below. Document the option and state in the doc comment that this is the only sanctioned way to open a transaction on a pooled client, because `runAfterCommit` depends on it.
2. **Guidance runner delegates.** `createPoolClientTransactionRunner(pool)` becomes `{ withTransaction: (options, work) => withTransaction(pool, work, { isolation: options.isolation }) }`; delete its hand-rolled `BEGIN`/`COMMIT`/`ROLLBACK` block and update its docstring (after-commit hooks registered by stores inside the runner now fire after the commit).
3. **Startup repair delegates.** `repairInterruptedRuns` becomes `return withTransaction(pool, async (client) => { ...the existing loop with D1's order...; return { repairedRunIds } })`; delete the manual `connect`/`BEGIN`/`COMMIT`/`ROLLBACK`/`release`. Keep the docstring's single-transaction rationale.
4. **Tests**:
   - `backend/packages/data/src/__tests__/pool.unit.test.ts` (unit, existing fake-pool pattern): `withTransaction(pool, fn, { isolation: "serializable" })` issues `BEGIN ISOLATION LEVEL SERIALIZABLE` as its first query; `{ isolation: "repeatable_read" }` issues `BEGIN ISOLATION LEVEL REPEATABLE READ`; no option issues plain `BEGIN`; the after-commit callbacks registered inside `fn` run after `COMMIT` in each variant.
   - `backend/packages/data/src/__tests__/projectAgentGuidanceStore.test.ts` (integration, existing `createPoolClientTransactionRunner` describe): inside `runner.withTransaction({ isolation: "repeatable_read" }, ...)` call `runAfterCommit(tx, spy)` → the spy has run once when the promise resolves; inside a `work` that throws after registering the spy → the spy never runs and no later `withTransaction(pool, ...)` on the same pool fires it (run one afterwards and assert the spy count is still 0); the transaction's `SHOW transaction_isolation` inside `work` reads `repeatable read` / `serializable` respectively.
   - `backend/packages/agent-runtime/src/__tests__/startupRepair.test.ts` (integration): install a hook with `setNotificationCreatedHook` (`backend/packages/data/src/realtimeHook.ts:92`) capturing events; repairing two orphaned runs fires exactly two `notification_created` events, after `repairInterruptedRuns` resolves; a repair whose transaction fails (a pool wrapper rejecting the `COMMIT` query) fires none, and a subsequent unrelated `withTransaction(pool, ...)` fires none either. Restore the hook in `afterEach`.

## Scope

### In scope
- The `isolation` option on `withTransaction`, the two call sites delegating to it, and the tests above.

### Out of scope
- `withTransaction`'s rollback/discard semantics (#671) and the order of writes inside `repairInterruptedRuns` (D1).
- `migrate.ts`'s own `BEGIN` (`backend/packages/data/src/db/migrate.ts:26`), which runs no store code and registers no callbacks.
- Serialization-failure retries for the guidance runner.

## Acceptance criteria

- When the guidance drift action commits its findings transaction, every `notification_created` realtime hook registered during it fires exactly once, immediately after that commit; when the transaction rolls back, none fires — then or later.
- When `repairInterruptedRuns` commits, one `notification_created` hook fires per `agent_run_error` notification it wrote; when it fails, none fires.
- `withTransaction(pool, fn, { isolation })` opens the transaction at the requested isolation level, observable through `SHOW transaction_isolation` inside `fn`.
- `grep -rn 'query("BEGIN' backend/packages backend/services --include=*.ts` outside `pool.ts` and `migrate.ts` finds nothing.
