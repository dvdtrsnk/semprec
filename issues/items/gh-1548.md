## Context

Model tier rationale: This adds a new owner-authorized write route with optimistic concurrency under serializable isolation, a delete path that also changes heartbeats and findings, and a tenant-isolation test, so several contracts must be right together.

Guidance has one data/shared owner in project_agent_guidance; the existing application service retains ownership transfer. Data custom routes must not import application. Preserve its 32 KiB/owner rules and the section API:

- `GET /api/projects/:id/agent-guidance` returns `{ sections: { purpose, allowed, notAllowed, generalInstructions }, updatedAt, ownerUserId }`. Each section is Markdown; an empty string is an empty section. A project without guidance returns 200 with four empty sections, `updatedAt: null`, `ownerUserId: null`.
- `PUT /api/projects/:id/agent-guidance` with `{ sections, expectedUpdatedAt }` returns 200 `{ sections, updatedAt }`.

Decisions:

- Both routes are `customRoutes` of the systemDatabases module manifest (`backend/packages/data/src/seed/systemDatabasesModuleManifest.ts`; module ownership per `docs/adr/2026-09-10-single-writer-ownership-model.md`), declared per `docs/adr/2026-09-11-module-manifest-custom-routes.md`: GET as `single-consumer-read` (the shape exists for one consumer, the AGENT page), PUT as `transactional-semantics` (guidance row, heartbeat and findings change in one transaction). The handlers live in `packages/data`, built on the shared ports and stores; the rules of the existing service are reimplemented there for sections, and the existing service stays for ownership transfer.
- The server composes the canonical Markdown with `composeProjectAgentGuidanceMarkdown` (from #1449) and stores it; GET parses it back. Parsing splits on the four reserved heading lines (`## Purpose`, `## Allowed`, `## Not allowed`, `## General instructions`, matched as whole lines). Text before the first reserved heading (a row not written by this API) is returned at the start of `generalInstructions`, so nothing is lost; the next PUT canonicalizes it.
- A PUT section containing a whole line equal to a reserved heading is rejected with 400 `validation_failed`, `details: { field: "sections.<key>", reason: "reserved_heading" }` (fenced code blocks are not special-cased, to keep parse and compose exact inverses).
- `expectedUpdatedAt` is the exact returned ISO millisecond revision (null when absent), compared in application code under `loadForUpdate`. The data owner issues monotonically increasing revisions across upsert, transfer and delete/recreate using the tenant/project receipt in `docs/adr/2026-11-05-monotonic-project-guidance-revisions.md`; this is a logical revision, not authoritative wall-clock audit time. A mismatch, or a PostgreSQL serialization failure `40001`, answers 409 `version_conflict` with the route returning its own body `{ error: { code: "version_conflict", details: { current: { sections, updatedAt, ownerUserId } } } }` (a custom route may return its own body; the generic error mapper would drop the non-flat details). No row is changed on conflict.
- Unknown project id: 404 `not_found`. Non-UUID `:id`: 400 `validation_failed`.
- Payload above 32 KiB after composition: 400 `validation_failed`, `details: { field: "sections", reason: "too_long" }`.
- All four sections empty: the row is deleted (new `delete` on the store), the project's drift heartbeat is disabled, active drift findings of the project are resolved in the same transaction without writing notifications (there is no guidance left to be in conflict), and the response is 200 with four empty sections and `updatedAt: null`. With no existing row, an all-empty PUT (with `expectedUpdatedAt: null`) is a no-op 200.
- Only the row's owner may write. The first write to a project without a row makes the caller the owner if the caller is the tenant's user (`guidanceReferenceStore.requireUser`), else 403 `owner_violation`.

Shared-file ordering: this issue also waits for #1546 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Acceptance criteria

- When a project has no guidance, then GET answers 200 with four empty sections and `updatedAt: null`.
- When the owner PUTs sections with the current `expectedUpdatedAt`, then the response holds the same sections and a new `updatedAt`, the project's next agent prompt contains "## Project-specific guidance" with the new text, and an enabled `core.agentGuidanceDrift` heartbeat exists.
- When a second client PUTs with the old `expectedUpdatedAt`, then it gets 409 `version_conflict` with the current content in `details.current`, and nothing is overwritten. A concurrent pair of writes ends with one success and one 409.
- When a section contains a line `## Allowed`, then the response is 400 `validation_failed` with `field` `sections.<key>` and `reason` `reserved_heading`.
- When the composed document is above 32 KiB, then 400 `too_long`; when the caller is not the owner, then 403 `owner_violation`.
- When all four sections are empty, then the row is gone, the heartbeat is disabled and the project's active drift findings are resolved without notifications.
- The isolation test shows tenant B cannot read or write tenant A's guidance (404 for A's project id).
