**Blocked by:** #989

## Context

**Today's wiring.** `semprec-api` resolves `mailboxesDatabaseId` once at boot. It builds `createMailLiveSyncRoot(pool, mailboxesDatabaseId, createNoopMailLiveSyncLifecycleFactory(pool), { onLifecycleError })` and awaits `start()` (`backend/services/semprec-api/src/serve.ts:122-131`). Shutdown calls `stop()` (`backend/services/semprec-api/src/shutdown.ts:115`).

**The root** (`backend/packages/data/src/mail/mailLiveSyncRoot.ts:101-248`):
- Discovery (`:125-161`) pages `listItems(client, mailboxesDatabaseId)` in that one database. It seeds each account's `mail_account_sync_state` with `ensureMailAccountSyncState` under a per-account `SAVEPOINT`.
- `reconcileOnce` (`:173-207`) gives each active account one lifecycle (`lifecycleFactory({ mailboxItemId, syncMode })`, then `start()`). It starts a `mailsync:<id>` process heartbeat (`:189-197`) and stops the lifecycles of accounts no longer discovered (`:203-206`).
- `start()` runs one pass, then a `setInterval` that defaults to 60 s (`:211-238`). `stop()` awaits any in-flight pass and stops every lifecycle (`:239-246`).

**Lifecycles.** The noop lifecycle enqueues one `mailAccountSync` (`:45-52`). The transport lifecycles (`backend/packages/data/src/mail/imapIdleLifecycle.ts`, `gmailWatchLifecycle.ts`, `graphWebhookLifecycle.ts` in the same directory) keep loops, timers and sockets that query the pool and enqueue jobs from their own callbacks. Those callbacks inherit the async scope `start()` ran in.

**Process heartbeats.** `startProcessHeartbeat` (`backend/packages/data/src/health/processHeartbeats.ts:67-90`) UPSERTs the global `process_heartbeats` table from a `setInterval`. Two kinds of caller use it:
- the root, once per account;
- each service at top level, with no scope: `backend/services/semprec-api/src/serve.ts:100`, `backend/services/semprec-agents/src/serve.ts:27`, `backend/services/semprec-transcribe/src/serve.ts:15`, `backend/services/semprec-ai-gateway/src/serve.ts:17`. Every such tick is a scope-less query.

**Tenancy state this issue builds on:**
- Every tenant table carries `tenant_id` under a RESTRICTIVE RLS policy `tenant_isolation`: `tenant_id = (SELECT app_tenant_default())`, with `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())` over the GUC `app.tenant_id`.
- `withTransaction`, autocommit `pool.query` and `pool.connect()` clients set that GUC from the ambient scope: `runInTenant(tenantId, fn)` sets the tenant and `runAsSystem(reason, fn)` sets `''` (`@semprec/shared`).
- A query without any scope logs `tenant_scope_missing` (warn mode) or throws `TenantScopeMissingError` (strict mode).
- Rule for long-lived loops: start them inside `runAsSystem`, and re-enter a tenant explicitly for each unit of work.
- With ids captured at boot, only tenant zero's mailboxes are ever discovered. In system scope with two tenants, RLS hides every mailbox.
- `enqueueJob` stamps the envelope `tenantId` from the current scope (#982).
- Since #989, `mailAccountSync` jobs resolve their mail databases in their own tenant.
- `forEachActiveTenant` (#983, `backend/packages/data/src/tenancy/forEachActiveTenant.ts`, exported from `@semprec/data`) runs the callback inside `runInTenant(tenantId, …)` for each tenant with `status = 'active'`. It is called from a system scope and starts at a rotating offset. Failures are collected and rethrown as one `AggregateError` after all tenants. If the merged signature differs from `forEachActiveTenant(pool, async (tenantId) => …)`, use the merged one.

## Task

Load `io-hardening` (a long-lived loop whose lifecycles open connections, and a shutdown that must not hang), `error-handling` (one tenant's failure is isolated and reported) and `state-writes` (discovery writes `mail_account_sync_state`).

1. **Signature.** Drop `mailboxesDatabaseId`: `createMailLiveSyncRoot(pool, lifecycleFactory, options)`.
2. **System scope.** `start()` and `reconcileOnce()` run inside `runAsSystem("mail:liveSync", …)`, so the discovery interval created in `start()` also runs in system scope. Callers need no scope.
3. **Per-tenant discovery.** Discovery calls `forEachActiveTenant(pool, async (tenantId) => …)`.
   - For each tenant, resolve the tenant's Mailboxes database with `resolveMailModuleIds(client)` inside the pass, then page `listItems` exactly as today, keeping the per-account `SAVEPOINT` seeding.
   - Record `{ tenantId, syncMode }` per discovered account.
   - The callback catches its own failure: it reports `options.onLifecycleError?.("*", "discover", err)` and records the tenant as failed, so that tenant neither aborts the pass nor triggers the helper's rethrow.
   - A failure of the tenant enumeration itself still rejects `reconcileOnce`, as today.
4. **Hosting.** `HostedEntry` gains `tenantId`.
   - Call `lifecycle.start()` and `lifecycle.stop()` inside `runInTenant(entry.tenantId, …)`. Everything a lifecycle does, now or later from its own timers and sockets, then runs in its mailbox's tenant.
   - Start the per-account process heartbeat after `start()` resolves, outside that callback, i.e. in the root's system scope.
   - `MailLiveSyncAccount` and `MailLiveSyncLifecycleFactory` stay unchanged: a lifecycle reads its tenant from the ambient scope.
5. **Stopping.**
   - After a pass, stop every hosted entry whose account was not discovered, unless its tenant is in the failed set. A failed tenant keeps its current lifecycles until a later pass succeeds.
   - A tenant that is no longer `active` is not enumerated, so its lifecycles stop on the next pass.
   - `stop()` keeps its contract: await the in-flight pass, then stop every entry, each in its own tenant.
   - Rewrite the docstrings at `:81-100` to say discovery runs per active tenant.
6. **Heartbeat ticks.** In `processHeartbeats.ts`, `startProcessHeartbeat` runs each tick's UPSERT inside `runAsSystem("processHeartbeat", …)`; `process_heartbeats` is a global table. A synchronous throw from entering the scope must reach `onError` like a failed UPSERT and must never escape the timer callback. No other function in that file changes.
7. **`serve.ts`.** Remove the boot resolution at `:125` and the imports it alone used (`resolveMailModuleIds`, `withTransaction`). Construct the root without an id and update the comment at `:122-124`. Change nothing else in `serve.ts`.
8. **Tests.**
   - Move `backend/packages/data/src/__tests__/mailLiveSyncRoot.test.ts` and `backend/services/semprec-api/src/__tests__/mailLiveSyncComposition.test.ts` to the new signature. Their behavioural assertions stay unchanged, except: the rollback-failure case (`mailLiveSyncRoot.test.ts:582-614`) now expects `reconcileOnce()` to resolve, with an added `("*", "discover", rollbackErr)` report; and the four connect counts (`:410`, `:436`, `:479`, `:561`) rise to cover the tenant enumeration's connection.
   - New `backend/packages/data/src/__tests__/mailLiveSyncRootPerTenant.test.ts` uses the two-tenant runtime-role harness of #975: `createTestTenant()` and a runtime-role pool. The superuser pool bypasses RLS.
   - Tenant B's minimal mail fixture is made inside `runInTenant(B, …)` with `createDatabase(client, { name, system: true, ownerModuleId })` for `emails`, `files`, `folders` and `mailboxes`. Leave `key` unset; `databases_key_unique` stays global until #1001.

## Acceptance criteria

All of these are integration tests (`*.test.ts`), with two tenants under the runtime role unless stated otherwise.
- **Per-tenant hosting.** Tenant zero (seeded) has mailbox M0 and tenant B (minimal fixture) has mailbox MB. After `reconcileOnce()`, called with no ambient scope, both are hosted, and all of the following hold:
  - a factory spy sees `currentTenantScope()` equal to `{ kind: 'tenant', tenantId: B }` inside MB's `start()`, and tenant zero's inside M0's;
  - MB's `mail_account_sync_state` row carries B's `tenant_id`;
  - with the noop factory, the `mailAccountSync` job enqueued for MB has envelope `tenantId` B.
- **Discovery failure isolation.** Tenant B has no mail databases. The pass resolves, calls `onLifecycleError("*", "discover", err)` once with the missing module ids, and still hosts M0.
- **A failed tenant keeps its lifecycles.** MB is hosted. B's discovery is then made to fail (e.g. the test clears `owner_module_id` on B's Files database). The next pass reports the error and does not call MB's `stop()`. After B is repaired, MB is still the same hosted entry, not restarted.
- **Deactivation.** B's `tenants.status` is set to `suspended`. The next pass calls MB's `stop()`, which sees B's scope, and stops MB's heartbeat. M0 is untouched.
- **Heartbeat ticks.** A `startProcessHeartbeat` started with no ambient scope writes its `process_heartbeats` row on every tick. With tenant-scope enforcement in strict mode, `onError` is never called.
- **Single tenant unchanged.** Every existing case in `mailLiveSyncRoot.test.ts` passes on the new signature, with the adjustments step 8 names: restart safety, `syncMode` switch, `stop()` awaiting an in-flight pass, and a soft-deleted mailbox stopping. So does every case in `mailLiveSyncComposition.test.ts`.
