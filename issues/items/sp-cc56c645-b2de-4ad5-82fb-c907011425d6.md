### Requirement gh-1906: [semp-turns 12/12] Add the inbox.proposal.revise agent tool

#### Context

Model tier rationale: An agent-callable write on proposal cards with authorization (only the thread's own card), a lock rule, history attribution and realtime invalidation, crossing the Inbox store, agent tools and threads.

An Inbox item thread lets the user talk to Semp about one proposal card ("this is something else", "belongs to another project", "fill in the missing details"). Semp sees the capture and its own proposal, and can revise the proposal. Today:

- `reviseProposalWithClient` and `rejectProposalWithClient` exist in `backend/packages/data/src/inbox/proposalActions.ts` but are not exposed as agent tools. `reviseProposalWithClient` takes a finished envelope and a required `message`, validates the envelope with `assertValidEnvelopeForCard`, refuses a card whose status is locked (`confirmed` or `rejected`), and writes a history entry with author `user` only.
- The `proposal`, `status` and `history` keys are system-owned, so a generic item update cannot write them. The comment in `inboxModuleManifest.ts` that says confirm, reject and revise go through a generic item update is outdated.
- History entries are `{ author: "ai" | "user", message, at }` (`appendHistoryEntry` in `inbox/inboxTickAction.ts`); typed history entries come from #1430.
- The architecture decision that agent writes are proposals allows this: a revision keeps the card a proposal and the target database is written only when the user confirms.

Builds on #1523 (module tools in sessions), #1385 (how module tools are granted and approved), #1870 (the revise route with an optional message), #1471 and #1892 (proposal `aiProposal` upkeep and the values patch validation), and #1620 and #1727 (thread messages and turns). #1938 and #1939 build on this tool.

Decisions:
- The agent composes the whole revised envelope; the tool validates and stores it, and does not compute one.
- The tool may change kind, target, relations and keys the user edited by hand, because the instruction comes from the user; the user-edit rules of #1471 apply.
- The tool never writes to the target database.
- No tool-specific history wording: the entry is `{ author: "ai", kind: "threadRevision", threadId, messageId }` plus the message.

#### Task

Load `state-writes`, `error-handling`, `canonical-keys` and `testing`.

1. Add the `inbox.proposal.revise` module agent tool to the Inbox manifest, with strict arguments `{ proposalId, entityKind?, target?, properties, message? }`.
2. The handler revises through the same path as the revise route of #1870, with validation identical to the values patch of #1892. Extend `reviseProposalWithClient` with an `author` parameter (default `user`, unchanged for the route) so the tool writes a history entry `{ author: "ai", kind: "threadRevision", threadId, messageId }`; the thread and message ids are resolved from the persisted run, not from arguments.
3. A card with a locked status yields an error result and leaves the envelope unchanged. An invalid envelope (for example a target outside the allowed databases) yields an error result with no write, like the route.
4. In an item thread the tool works only for the thread's own card; any other card id gives an error result that does not reveal whether it exists.
5. After a successful revision, publish the Inbox card invalidation (as #1811 defines) so the client redraws the card.
6. Return a result for the thread step that states success (the step mapping is the domain of the thread-step issues).
7. Correct the outdated comment in `inboxModuleManifest.ts`.
8. Tests: a revision of an open card changes the envelope and adds an AI history entry; a confirmed card is refused and unchanged; an invalid envelope writes nothing; card B cannot be revised from the thread of card A; the history entry carries thread and message ids; the target database is untouched.

### Requirement gh-1921: [inbox-editing 14/23] Keep user-edited keys when a proposal is recomputed

#### Context

Model tier rationale: Changes the staleness and concurrency contract of the tick's write transaction (what counts as "the row changed") and the merge of assistant output with user values under a row lock, where a mistake silently loses either the user's edits or the assistant's result.

The inbox card shows "Edited by hand: N. Semp will not overwrite these values on the next recompute." Manual values (`userOverrides`, `userEditedKeys`) are written by #1892; the assistant's latest output is kept in `aiProposal` with a write counter `aiVersion` (#1471); the stored `proposal` is the effective envelope composed from the two. Today the tick (`backend/packages/data/src/inbox/inboxTickAction.ts`) knows nothing about this and has two problems for edited cards:

1. `reviseProposal` replaces `proposal` wholesale, so a recompute after the source text changed would overwrite manual values.
2. `lockUnlockedProposal` re-reads the proposal under `FOR UPDATE` and treats the row as `changed` (the AI result is discarded and, because writing to Processing proposals does not trigger another tick and the source fingerprint is unchanged, never recomputed) whenever `updatedAt` differs from the snapshot. A manual `PATCH values` during the AI call moves `updatedAt`, so the assistant's result would be lost.

Decision: staleness is decided by the card's `fingerprint` and `aiVersion`, not by `updatedAt`. A concurrent manual edit does not discard an assistant result; a concurrent assistant write, a status lock (`confirmed`/`rejected`), a deletion or a different fingerprint still does. The write transaction still passes the freshly locked row's `updatedAt` as `ifVersion`, so the choke point's own conflict check is unaffected.

Decision: a user instruction typed in the item thread may change a protected key; that exception belongs to #1938. The tick, the explicit recompute and the user revise never change a key listed in `userEditedKeys`.

#### Task

Load `state-writes`, `testing` and `error-handling`.

1. In `lockUnlockedProposal`, replace the `locked.updatedAt !== snapshot.updatedAt` test with a comparison of `fingerprint` and `aiVersion` (a missing `aiVersion` counts as 0) between the locked row and the snapshot; keep the gone, deleted and locked reasons and the serialization-failure branch as they are. Log `changed` when either differs.
2. In `reviseProposal` (and the create-or-revise path of `writeTickResult`), under the lock, write only the assistant parts from the new result: `aiProposal` (via the helper from #1471, which increments `aiVersion`), `fingerprint` and the history entry. Compute the effective `proposal` from the locked row's current `userOverrides` with `composeEffectiveEnvelope` and recompute `userEditedKeys` with `computeUserEditedKeys` (both in `backend/packages/data/src/inbox/proposalOverrides.ts`, from #1892). A manual value therefore survives, and a key whose manual value now equals the new assistant value drops out of `userEditedKeys`.
3. When the new envelope's `entityKind` or `target` differs from the previous `aiProposal`'s, or an override key no longer exists on the new target, drop those overrides for this recompute (they cannot apply); the history entry then has `kind: "recompute"` and the message names the dropped keys. Overrides on keys that still apply are kept.
4. `writeNeedsClarification` writes `aiProposal: null` and `proposal: null` as before, and leaves `userOverrides` and `userEditedKeys` untouched; they apply again when a later valid assistant output arrives.
5. Set `kind: "recompute"` on the history entry written by `reviseProposal`.
6. Tests in `inboxTickProposal.test.ts`: recompute after a source text change keeps an edited title; a manual `PATCH values` committed while `computeProposal` is in flight leaves the assistant result stored in `aiProposal` with `aiVersion` +1 and the manual title still effective; a confirm during the call still discards the result; a second assistant write during the call still discards it.

#### Touches

- backend/packages/data/src/inbox/inboxTickAction.ts (lockUnlockedProposal, reviseProposal, writeTickResult, writeNeedsClarification)
- backend/packages/data/src/__tests__/inboxTickProposal.test.ts
- backend/packages/data/src/__tests__/inboxTick.test.ts

#### Scope

##### In scope

##### Out of scope

- Versioning the fingerprint (#1606).

#### Acceptance criteria

- When the source text changes and the tick recomputes, then the manually edited `title` stays and the other fields take the new assistant values.
- When a manual `PATCH values` commits while the assistant call is running, then the assistant result is stored in `aiProposal`, `aiVersion` grows by one and the manual value is still in `proposal` and `userEditedKeys`.
- When the card is confirmed or rejected while the call is running, then nothing is written.
- When another assistant write bumped `aiVersion` while the call was running, then the older result is discarded.
- When the new assistant envelope has another target, then overrides are dropped and the history entry has `kind: "recompute"` naming them.
- When the assistant output fails validation, then the card is `needsClarification` with `proposal` null and the overrides remain stored.

### Requirement gh-1894: [inbox-proposals 14/19] Store idempotent responses for Inbox card actions

#### Context

Model tier rationale: Adds a tenant-owned table that stores and replays response bodies, so tenant and user scoping, expiry and cleanup must be exactly right to avoid replaying one user's data to another.

The iOS app queues card actions offline and replays them. `Idempotency-Key` is honored today only when creating an item (`backend/services/semprec-api/src/itemsHandler.ts` passes it to `item.create`; the `idempotency_keys` table maps a key to the created item). Card actions are not creations: a repeated `PATCH /api/proposals/:id/values` from #1892 would apply twice and add two history entries.

Confirm and reject are already idempotent through the card state (and #1852 keeps that precedence), so they need nothing here.

Decision: a new table stores the first response per key; a repeat with the same key on the same route by the same user returns the stored status and body without running the action again. Rows expire after 24 hours.

#### Task

Load `db-migrations`, `state-writes`, `io-hardening` and `testing`.

1. Add a migration creating `idempotent_responses`: `tenant_id` (not null), `user_id`, `key` (text), `route` (text, the route template, for example `PATCH /api/proposals/:id/values`), `request_hash` (text), `status` (int), `body` (jsonb), `created_at`, `expires_at`; unique `(tenant_id, user_id, key, route)`; row-level security like sibling tenant tables; `COMMENT ON TABLE idempotent_responses IS 'semprec:tenancy=tenant'`; grants like sibling tables; index on `expires_at`.
2. Add a store with `runIdempotent(client, { tenantScope, userId, key, route, requestHash }, action)`: inside one transaction, take an advisory lock on the key, return the stored response if present and the request hash matches, answer 400 `validation_failed` (idempotency key reused with a different request) if the hash differs, otherwise run the action, store its status and body, and return it. 3. Apply it to `PATCH /api/proposals/:id/values` when an `Idempotency-Key` header is present; absent header leaves the route unchanged. The other card routes apply the same helper in the issues that mount them.

### Requirement gh-1934: [inbox-editing 17/23] Normalize hidden fields on confirm

#### Context

Model tier rationale: One pass over the confirm path that drops hidden values using the shared visibility function, with fixtures for each affected database, but a wrong rule would silently erase a stored value.

A card hides fields whose condition is false: an all-day task or event hides its time part, a long-term project hides its due date, a person with a chosen contact kind shows only that one field. Today confirm writes the whole envelope as it was proposed, so a value the assistant proposed for a field the user can no longer see (for example start and end times on an all-day task) would be stored anyway. #1825 puts the editor schema with `when` and `timeHiddenWhen` conditions on cards, and the shared visibility evaluation `isFieldVisible` in `backend/packages/data/src/inbox/editorSchema.ts` is the one #1928 adds for required-field checks; this issue reuses it and edits the same confirm function, so it must land after that issue. Events carry nullable `timeFrom` and `timeTo` once #1416 has added them, where a null `timeFrom` means all-day.

Decision: the confirm path writes what the editor shows. For every field the schema hides, the corresponding properties are omitted from the created item (an empty value; for Events, `timeFrom` and `timeTo` are explicitly null). The time part of a `datetime` field with `timeHiddenWhen` true maps to the `timeFrom` and `timeTo` properties of the target. Pseudo fields never reach the item.

Decision: for an MCP server card, hidden fields are dropped (`url`/credential for stdio, `command` for http), a card whose transport is `stdio` is refused at confirm with a `ValidationError` on `transport` (a model-authored host command never becomes a card, see `docs/adr/2026-10-16-stdio-mcp-confined-to-admin-tenants.md`), and a server with transport `http` or `sse` is written as `{ transport, url }`.

### Requirement gh-1938: [inbox-editing 18/23] Load the card context into item threads and apply thread-revision rules to inbox.proposal.revise

#### Context

Model tier rationale: Defines what an AI thread turn is allowed to change on user-edited state and how that is stored, across a prompt-composition seam and a validated write, with ownership of protected user values at stake.

In the thread attached to an Inbox item the user tells Semp what to do differently ("it is something else", "it belongs to another project", "fill in the missing details"). Semp should see the whole capture and what it proposed from it, answer, and change the card; the card then redraws. Four pieces exist or are planned: the thread's chat transport (#1620), the queued thread turns run in semprec-agents (#1727), the revision tool `inbox.proposal.revise` (#1906) that validates a revised envelope and stores it through the revise route, and manual edits with `userOverrides` / `userEditedKeys` / `aiProposal` (#1471, typed history in #1430). Today the thread's prompt knows nothing about the card, `reviseProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) takes a finished envelope and a mandatory message and does not record where the revision came from, and a revision would overwrite fields the user edited by hand.

This issue does two things on the one flow "a thread turn revises a card": it gives the turn the card as context, and it defines the rules of the revision when the tool is called from a thread. The tool itself (#1906) is not re-built here.

Decision: no separate read tool is introduced; the card context is inserted into the thread turn's prompt. The context contains the source (text, capture date and time, type, attachment names), the effective envelope, `userEditedKeys`, the history and the user's message. A thread turn on an item without an open card gets no card context.

Decision: a revision from a thread is written as the assistant's output with these rules. The tool passes the full revised envelope. For every key in the previous `userEditedKeys`, `aiProposal` keeps the previous assistant value and `userOverrides` takes the value of the revised envelope, so a key the instruction did not touch stays protected and a key the instruction changed ("it belongs to another project") is changed but remains user-owned (it stays in `userEditedKeys`). All other keys are written to `aiProposal`. If the revision changes `entityKind` or `target`, all overrides are dropped by the rule of #1924. The history entry has `author: "ai"`, `kind: "threadRevision"`, the thread id and the message id. `aiVersion` is incremented.

Decision: only the card whose source item is the thread's subject can be revised from that thread; a `confirmed` or `rejected` card is read-only for the thread and the tool returns an error.

Decision (product owner): the item a confirmed card created is an ordinary item and the thread may edit it. For a `confirmed` card the context lists the created items from the card's `results` (#1648: `itemId`, `databaseKey`, `label`), and the thread edits them with the same item tools as any other item, through the choke point; nothing here bypasses it. When such a Semp write would end an inherited value link, the choke point defers it to an approval carrying the warning that it ends the link (#1758); this issue adds no rule of its own.

Load `state-writes`, `ai-gateway`, `error-handling` and `testing`.

1. Add `loadInboxCardThreadContext(client, itemId)` in a new `backend/packages/data/src/inbox/threadCardContext.ts`: returns the structure above for a live open card, the source plus the card's status and its created items (from `results`) for a `confirmed` card, and `null` otherwise; the text rendering for the prompt (bounded length per field, user text clearly delimited as data, never as instructions) lives next to it.
2. Wire it into the thread-turn prompt composition in `semprec-agents` (the code added by #1727; the composition root is `backend/services/semprec-agents/src/agentSessionComposition.ts`) for threads whose subject is an Inbox item.

### Requirement gh-1901: [calendar-invites 05/13] Seed an invitations system database

#### Context

Model tier rationale: One known mechanism (a system database seeded with owner-system properties plus a per-tenant cutover) across seed, manifest, cutover and i18n seams with existing seed fixtures, but it fixes a persisted schema and ownership contract that four later issues write to.

Calendar invitations do not exist in the backend today. The `invites` table (`0077_invites.sql`) and the account-invitation flow in `backend/packages/data/src/tenancy/invites.ts` are invitations to join Semprec as a user; they are unrelated and must not be reused or renamed.

This issue gives the calendar module a place to store an incoming meeting invitation until the user answers it. It adds one system database, `invitations`, owned by the calendar module (the module manifest, `calendarModuleManifest.ts`, is registered by an earlier issue; the system Calendars database comes from #1600). ### Requirement gh-1905: [calendar-module 13/15] Order recurring Events by their next occurrence

#### Context

Model tier rationale: It adds a derived date that depends on recurrence expansion and the tenant time zone, must stay correct as days pass (a daily recomputation), and changes the sort, filter and grouping behavior of the Events collection, so date and daylight-saving mistakes are visible to every user.

The Events collection lists each Event once, grouped and ordered by day. A recurring Event (the rule from #1817) is one row but occurs on many days, so a stored `date` (its first day) places it in the past. The collection must show a series once, at its nearest occurrence from today, and sort, group and filter by that day. The generic view query sorts and filters by stored properties only (`views/sortCompiler.ts`, `views/filterCompiler.ts`); a value that depends on "today" has to be stored and kept fresh.

This issue adds the system-owned Events property `nextOccurrenceDate` (type `date`, owner system, locked): the date of the nearest occurrence on or after today in the tenant time zone; for an Event without a recurrence rule it equals the Event's own `date`; for a series that has ended it is the date of its last occurrence. With it, the existing sort, group and relative-date filter features (#1524) work on recurring Events unchanged.

Decision: the value is a plain stored date in the tenant time zone, recomputed (a) inline when an Event is created or when its `date`, `endDate` or recurrence rule changes, and (b) by a daily heartbeat for recurring Events whose stored value is before today. The occurrence list comes from the expansion function of #1877. Database date comparisons rely on the session time zone being UTC (#1596).

Decision: ties on the same day are ordered by the existing sort tie-breakers; this issue adds no other sort key.

Shared-file ordering: this issue also waits for #1901 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.
