## Context

Post-merge review on #99's PR (#258) flagged two medium-severity findings in `passesItemRelationFilter` (`backend/packages/data/src/scheduler/itemRelationFilter.ts`) that landed on `develop` unaddressed — the PR auto-merged seconds before Relay's merge-gate could react to the review's `neutral` check conclusion.

## Task

Fix `passesItemRelationFilter`'s join on `items`:

- Add a `deleted_at IS NULL` guard on the joined `items` row. `softDeleteItem` does not delete `item_relations` rows, so a soft-deleted folder item (e.g. a folder that was junk and was later deleted) currently remains visible through the join and can still gate the filter.
- Include `database_id` in the join condition (`JOIN items related ON related.id = CASE WHEN r.item_a = $3 THEN r.item_b ELSE r.item_a END`). `items` is a LIST-partitioned table partitioned by `database_id`; without it in the join, Postgres cannot prune partitions and scans all of them.

## Scope

### In scope

- The `deleted_at` guard and the `database_id` join-condition fix in `passesItemRelationFilter`.
- Test coverage for both: a soft-deleted folder no longer gates the filter, and the join plan (or an equivalent regression test) confirms partition pruning is possible.

### Out of scope

- Any other behavior of the `newEmail` heartbeat rule from #99 — this issue only addresses the two flagged findings.

## Acceptance criteria

- A message related only to a soft-deleted folder is treated as if that relation doesn't exist by `passesItemRelationFilter`.
- The join includes `database_id`, letting Postgres prune to a single partition.
- Existing `newEmailHeartbeat` tests from #99 still pass.
