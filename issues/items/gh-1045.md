**Model tier:** low

## Context

Model tier rationale: One transaction with three named lookups and one refusal constant is specified exactly.

`agentTool.delegate` lets a supervisor run hand a task to a project agent. `createDelegateTool` (`backend/packages/agent-runtime/src/delegateTool.ts:33-50`) passes the model's own tool arguments `{ targetProjectItemId, task }` (`:4-7`) straight to `DelegationRegistry.delegate` (`backend/packages/agent-runtime/src/delegationRegistry.ts:125-217`).

The only check on the target is a UUID format check (`:131-133`). Its comment says authorization "belongs to the permission manifest the not-yet-built composition root" resolves (`:126-130`). The new-session path then calls `createAgentRun(this.pool, { projectItemId: input.targetProjectItemId, parentRunId: input.supervisorRunId, … })` (`:176-182`). `agent_runs.project_item_id` has no foreign key (`backend/packages/data/src/db/migrations/0001_core_schema.sql:116`). As a result:
- any well-formed id gets a run and a session: a nonexistent project, a trashed one, or once several tenants exist another tenant's project id;
- the supervisor run itself is never looked up.

Registry entries are keyed by `${supervisorRunId}:${targetProjectItemId}` (`:70-72`), and an entry is reused only by the same supervisor run (`:145-169`).

Neither the registry nor the tool is wired into a service yet: grepping `backend/services` finds no use. The check belongs in the registry so that any future composition root inherits it.

What earlier issues provide:
- RLS hides other tenants' `agent_runs`, `databases` and `items` once `app.tenant_id` is set from the scope.
- #991 runs every agents-process job, and so every supervisor turn and its tool calls, inside `runInTenant(job tenant)`. `withTransaction(this.pool, …)` therefore sees only that tenant's rows.

`guidanceReferenceStore.requireProjectsItem` (`backend/packages/data/src/projectAgentGuidanceStore.ts:80-92`) shows the existing pattern for validating a project id: `getDatabaseByModuleId(tx, PROJECTS_MODULE_ID)`, then `getItemById(tx, database.id, id)`. Both, and `PROJECTS_MODULE_ID`, are exported from `@semprec/data` (`backend/packages/data/src/index.ts:37`, `:40`, `:137`).

## Task

Load `io-hardening` (model output is untrusted input) and `error-handling` (a missing Projects database is an infrastructure failure, not "not found").

1. **Resolve the target in the run's tenant.** In `DelegationRegistry.delegate`'s new-session path, after the key is reserved in `pendingKeys` (`:171`) and before `reconstruct`/`createAgentRun`, open one `withTransaction(this.pool, …)` that checks three things:
   - `getAgentRun(client, input.supervisorRunId)` is visible;
   - `getDatabaseByModuleId(client, PROJECTS_MODULE_ID)` exists. If it does not, throw a plain `Error`, as `requireProjectsItem` does.
   - `getItemById(client, projects.id, input.targetProjectItemId)` returns a row with `deletedAt === null`.
2. **One answer for every refusal.** If the supervisor run or the target is not visible or not live, return `{ ok: false, error: UNKNOWN_DELEGATION_TARGET_MESSAGE }`, exported as a constant with the text `"targetProjectItemId does not name a project this run can delegate to"`. The message is identical for:
   - a random UUID;
   - another tenant's project;
   - a trashed project;
   - a non-Projects item.

   No `agent_runs` row is created, `createAgentSession` is not called, and `pendingKeys` is released by the existing `finally` (`:215-217`). The UUID format guard (`:131-133`) stays first.
3. **Reuse unchanged.** An existing entry for `(supervisorRunId, targetProjectItemId)` was validated when it was created. Keep the reuse path (`:145-169`) unchanged, with no extra query on the hot path.
4. **Tests.**
   - `backend/packages/agent-runtime/src/__tests__/delegationRegistry.test.ts` and `delegateTool.test.ts` today delegate to hard-coded, nonexistent UUIDs (e.g. `delegationRegistry.test.ts:113`; `delegateTool.test.ts:59`, `:89`). Switch them to real items in the seeded Projects database.
   - Add the criteria below. The cross-tenant case uses the two-tenant runtime-role harness of #975 (`createTestTenant`, `createRuntimeRolePool`, `getTenantZeroId` from `@semprec/data/testSupport`), because the superuser test pool bypasses RLS.

## Scope

### In scope
- Resolving the supervisor run and the target project inside the current tenant before a delegated session is created, with one indistinguishable refusal.

### Out of scope
- Wiring the delegate tool into a service.
- Per-project permission manifests (not part of this issue).
- Running agent jobs in their tenant (#991).
- Who a delegated run's `actor_user_id` is (#1018).
- Capping concurrent runs per tenant (#1047).

## Acceptance criteria

- **Live target delegates.** Delegating to a live item of the tenant's Projects database creates one `agent_runs` row with `parent_run_id` = the supervisor and `project_item_id` = the target, and returns the session's final message as before. (integration, `delegationRegistry.test.ts`)
- **Unknown, trashed or wrong-database target refused.** A random UUID, a trashed Projects item, or a Tasks item each return `{ ok: false, error: UNKNOWN_DELEGATION_TARGET_MESSAGE }`. No `agent_runs` row is created and `createAgentSession` is never called. (integration, `delegationRegistry.test.ts`)
- **Cross-tenant target refused identically.** With the supervisor run in tenant A, delegating to a live tenant-B Projects item returns exactly the same result as a random UUID, and creates no row in either tenant. (integration, runtime-role harness)
- **Foreign supervisor run refused.** A supervisor run id not visible in the current tenant is refused the same way. (integration, runtime-role harness)
- **Retry after refusal.** After a refusal, an immediate second call for the same key is not answered with `BUSY_ERROR_MESSAGE`, because the reservation was released. (integration, `delegationRegistry.test.ts`)
- **Tool result.** `createDelegateTool` maps the refusal to `{ error: true, result: UNKNOWN_DELEGATION_TARGET_MESSAGE }`. (integration, `delegateTool.test.ts`)
- **Format guard.** A malformed id still returns the existing format error without querying. (integration, `delegationRegistry.test.ts:790-812`)
