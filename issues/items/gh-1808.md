## Context

Model tier rationale: An additive column plus seed and cutover changes in shared hotspot files and two read surfaces, on a known pattern; no enforcement logic is added here, but the flag is read by the access check, so the backfill must be exact.

Some databases hold data that an AI agent should not read or write by default: health records, and the sleep settings, plans and nights. Today the backend has no notion of sensitivity: `databases` has `system` and `schema_locked` but nothing that marks content as sensitive (`backend/packages/data/src/db/migrations/0001_core_schema.sql`, `chokePoint/databasesStore.ts`), and the Health records database is seeded by `seed/seedTenDatabases.ts`. The sleep databases are seeded by the sleep module (#1776) and backfilled into existing tenants (#1779). `GET /api/databases` serves the database envelope (#1407 added its display fields in `services/semprec-api/src/adapter/databaseEnvelope.ts`) and `GET /api/schema` serves the schema projection (`manifest/schemaProjection.ts`).

This issue adds the flag. #1810 reads it in SQL, in the same transaction as the access it guards, to decide which databases an agent needs an explicit grant for. #1827 reads it to redact tool results. The flag is a column rather than a manifest entry for exactly that reason.

Decisions:
- The flag is set by the system only; there is no user-facing way to mark a custom database sensitive in this issue.
- The flagged keys are `healthRecords`, `sleepSettings`, `sleepPlans` and `sleepNights`, kept in one exported constant.
- Human REST access to these databases is unchanged.

Shared-file ordering: this issue also waits for #1798 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `canonical-keys` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_<name>.sql` (next free ordinal at commit time): `ALTER TABLE databases ADD COLUMN sensitive boolean NOT NULL DEFAULT false`. Additive only.
2. Add `sensitive` to the database row type, the store's column list and mapping (`databasesStore.ts`, `types.ts`), and let `createDatabase` accept it (system databases only).
3. Add a constant with the four sensitive database keys. Create `healthRecords` with `sensitive: true` in `seed/seedTenDatabases.ts` and the three sleep databases with it in the sleep seed from #1776.
4. Add an idempotent cutover step to `db/tenantCutoverMigrations.ts` that sets `sensitive = true` for those keys in every maintained tenant; running it again changes nothing.
5. Return `sensitive` from `GET /api/databases` (the database envelope and the shared `Database` type) and from `GET /api/schema` (the database projection).
6. Tests: a newly provisioned tenant has `sensitive` true exactly for the four keys; an existing tenant after the cutover does too; a second cutover run changes no row; the two endpoints return the flag; a non-system database cannot be created as sensitive.

## Scope

### In scope

- The column, the flag values in seed and cutover, and exposing the flag on the two read endpoints.

### Out of scope

- Enforcing anything based on the flag: #1810.
- Redacting tool results in run history: #1827.
- A way for users to mark their own databases sensitive; not planned yet.
- Client display of the flag.

## Acceptance criteria

- When a tenant is provisioned, then `sensitive` is true for `healthRecords`, `sleepSettings`, `sleepPlans` and `sleepNights` and false for every other database.
- When the cutover runs on an existing tenant, then the same databases become sensitive; running it again changes nothing.
- When `GET /api/databases` or `GET /api/schema` is read, then each database carries `sensitive`.
- The migration is additive and the previous release keeps working against it.
