## Context

Model tier rationale: A provisioning step that renders one small file from deployment configuration plus one Caddy handler with a response header, verified by the existing hermetic Caddy and provisioning tests, but the file's app identifier must be exact or iOS silently ignores it, so it is more than a mechanical edit.

The password-reset email links to `<APP_BASE_URL>/?page=password-reset#token=<token>` (`buildPasswordResetUrl` in `backend/packages/data/src/auth/passwordResetActions.ts`), which opens the web app. A user who has the iOS app installed should land in the app's new-password screen instead. iOS decides that from an Apple App Site Association file served by the domain. Today there is none: `deploy/Caddyfile` serves `web/dist` with a fallback to `index.html` for any path without a file, so `/.well-known/apple-app-site-association` would return the web app's HTML. The token stays in the URL fragment (`docs/adr/2026-10-17-secret-link-tokens-travel-in-the-url-fragment.md`); the app's new-password screen calls the existing `POST /api/auth/password-reset/consume`.

Deployment configuration already reaches Caddy this way: `deploy/provision.sh` (`render_caddy_environment`) reads `SEMPREC_DOMAIN` from the `monitor` secret group (`/opt/semprec/shared/env/monitor.env`, template `deploy/shared/env/monitor.env.example`), writes it to `/etc/caddy/semprec.env`, validates the Caddyfile and reloads Caddy; when the value is empty it warns and leaves Caddy unconfigured.

The Swift project does not exist in the repository yet (`apple/` holds only a README and the native-session bridge contract), so the Associated Domains entitlement and the new-password screen are client work for the app issues and are not part of this one.

Decisions (by the product owner):
- The association matches only the reset link: path `/` with query `page=password-reset`. The invitation link is never claimed as a Universal Link; it stays an ordinary link.
- The Apple Team ID and the bundle id are supplied by the owner from the Apple Developer account. They are deployment configuration, never hard-coded in the repository: two new keys of the `monitor` group, `SEMPREC_APPLE_TEAM_ID` and `SEMPREC_IOS_BUNDLE_ID`. The app identifier in the file is `<SEMPREC_APPLE_TEAM_ID>.<SEMPREC_IOS_BUNDLE_ID>`.
- The file is rendered by provisioning outside the web build, served with `Content-Type: application/json`, no redirect, no extension, at `/.well-known/apple-app-site-association`. When either key is empty, no file is rendered (an earlier one is removed), provisioning prints a warning naming the missing key (never a value), and the path answers 404, never the web app's HTML.

## Task

Load `testing`.

1. In `deploy/shared/env/monitor.env.example` add `SEMPREC_APPLE_TEAM_ID=` and `SEMPREC_IOS_BUNDLE_ID=` with a comment explaining that they come from the Apple Developer account and form the app identifier of the association file; update the file's header comment that lists what the group holds.
2. In `deploy/provision.sh` add a step next to `render_caddy_environment` that reads both keys from `monitor.env` and, when both are set, writes `/etc/caddy/apple-app-site-association` (root-owned, mode 0644) with `{"applinks":{"details":[{"appIDs":["<TEAMID>.<BUNDLE_ID>"],"components":[{"/":"/","?":{"page":"password-reset"},"comment":"Password-reset link"}]}]}}`; when either is empty, remove the file if present and print a warning naming the missing key. Never print a value. The step runs before Caddy is reloaded.
3. In `deploy/Caddyfile` add a handler for exactly `/.well-known/apple-app-site-association`, placed before the catch-all web handler, that serves the file from `/etc/caddy` with `Content-Type application/json`, without the `try_files` fallback, so a missing file is a 404.
4. Extend `deploy/Caddyfile.test.sh` (or a sibling script it invokes) so the hermetic Caddy run asserts, with a rendered file: status 200, `Content-Type` `application/json`, the body is the rendered JSON and not the web app's `index.html`; without the file: status 404 and not the web app's HTML; and that the existing access-log filtering assertions still pass. Make the served directory overridable for the test the same way the test already overrides `SEMPREC_DOMAIN`.
5. Extend `deploy/provision.test.sh` with cases for the new step: both keys set renders the exact JSON with the joined app identifier; an empty key renders nothing, removes an earlier file and prints the warning without any value.
6. Add a one-paragraph note to `apple/README.md` stating that the app must declare `applinks:<domain>` in its Associated Domains entitlement, and to `deploy/README.md` stating that the operator sets the two keys in `monitor.env` and reruns provisioning.

## Acceptance criteria

- When both keys are set and provisioning runs, then `GET /.well-known/apple-app-site-association` on the Caddy-served domain answers 200 with `Content-Type: application/json` and the JSON body whose `appIDs` is `["<SEMPREC_APPLE_TEAM_ID>.<SEMPREC_IOS_BUNDLE_ID>"]`, not the web app's HTML, and without a redirect.
- The `components` entry matches only the `page=password-reset` query on `/`.
- When either key is empty, then provisioning renders no file, prints a warning naming the key and no value, and the path answers 404.
- No Team ID or bundle id value appears anywhere in the repository.
- The existing Caddy access-log test (no query string or `Referer` in the log) still passes.
