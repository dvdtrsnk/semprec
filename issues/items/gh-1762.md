## Context

Model tier rationale: One known mechanism (a read-only custom route paging over an existing read function with a keyset cursor) across a defined route seam with existing isolation fixtures, but the cursor must stay stable across pages and days.

The calendar timeline route of #1717 returns every Event, Task and derived entry inside a date range for the calendar views. A list ("agenda") view needs the same entries as one continuing list from a day, in either direction, without the client choosing a range. Today there is no such route and the generic collection queries cover one database at a time.

This issue adds `GET /api/calendar/agenda?from=YYYY-MM-DD&direction=forward|backward&limit=50&cursor=` as a custom route of the calendar module (justification `single-consumer-read`, the same as the timeline). It calls the same timeline read function as #1717 (`readCalendarTimeline` in `backend/packages/data/src/calendar/timelineRead.ts`) and so inherits its item shape, ordering inside a day, hidden-calendar behavior (everything is returned; the client hides by calendar), the exclusion of trashed items and the time zone of the tenant.

Behavior: the response is `{ items: [...timeline items...], nextCursor }`. Items are ordered by day, then by the timeline's order inside a day; forward goes to later days, backward to earlier days (days descending, the order inside a day unchanged). Days with no entries are skipped. An item that spans several days appears once, on the first day it is shown in the direction of travel (for the first page, the `from` day). `limit` defaults to 50 and is at most 200. The server reads the timeline in windows of 31 days and stops when `limit` items are collected or a scan horizon of 366 days from `from` is reached.

Decision: the cursor is an opaque string encoding the day and the id of the last returned item; the next page continues after that item on that day, and if the item no longer exists it continues from the next day. When the scan horizon is reached before `limit`, `nextCursor` points to the day after the horizon so the client may continue, until five years from `from`, after which it is `null`. `nextCursor` is also `null` when nothing is left in the direction.

Decision: an invalid `from`, an unknown `direction`, a `limit` outside 1-200 or a malformed cursor returns 400 `validation_failed`.

Shared-file ordering: this issue also waits for #1760 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Acceptance criteria

- When the agenda is requested from 16 Oct 2026 forward with `limit` 5, then the 5 nearest items are returned with a `nextCursor`, and the next page continues without duplicates.
- When there are no entries on a day, then that day does not appear.
- When `direction` is `backward`, then earlier days are returned from the nearest backwards.
- When the parameters are invalid, then the response is 400 `validation_failed`.
- When another tenant has entries in the range, then none of them is returned.
