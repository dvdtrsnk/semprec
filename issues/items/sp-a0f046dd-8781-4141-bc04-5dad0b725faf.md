## Context

Model tier rationale: The restore runbook must preserve the deletion-replay security boundary across refusal and cleanup, while keeping recovery operations offline and the documented commands executable.

Independent batch19 R1 at 7550fba23bcd86cc963287797d2ec07ed8832c13 found that deploy/README.md starts services before handling replay exit1. replayTenantDeletionsCommand already fails on lastAdmin/unexpectedStatus, and replayOneTenant intentionally leaves a refused tenant unchanged. Following the current numbered sequence can expose a restored deleted account. No production restore was observed. This corrective issue owns F1; gh-1086 remains docs-only and open.

## Task

1. Preserve the replay CLI's refusal and identity/privacy behavior. Correct the restore activation procedure so every replay failure/refusal stops before any user-facing service activation. Resolve refusals while offline and rerun; only an independently verified successful replay allows activation. Preserve idempotence and disclosure of deletions newer than the available ledger.
2. Put the concrete fail-closed activation contract in the runbook with one directly executable gated command sequence. Do not rely on a comment, on the operator skipping an earlier numbered start step, or on forced deletion of the final admin. If an executable helper is necessary, submit its exact path/protocol to the parent before adding it.
3. Prove the actual documented command sequence locally with owned fake activation commands and a forwarding real replay refusal/success boundary where feasible: zero activation after exit1/refusal, malformed ledger, unexpected CLI failure and missing native entry; activation occurs only after a complete success. Preserve existing refusal and retry tests; do not claim that a simulation is a production rehearsal.
4. Record the exact discrepancy with historical gh-1078 Task ordering and the correction in a new decision record. Historical accepted ADR bodies/specifications/handovers remain immutable.
