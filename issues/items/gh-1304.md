## Behavior specification

Semp threads: thread entity, messages, memory, send, queue, list and search.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: semp-threads-1

#### (a) Adopted decisions
- "Approval card ('Semp wants to approve') dragged onto the bubble: forbid in the client or open the originating thread?" -> no item thread is created for it; a `subject` that is not an existing Inbox item is a 400 -> the card is not an Inbox item, conservative server behavior (#1620). Client may still choose to open the originating thread.
- "Processed Inbox item (proposal confirmed/rejected): read-only thread or edit the created item?" -> server answers 409 `proposal_locked` to any new message, so the thread is read-only for sending; editing the created item is left to the a related issue decision -> conservative, matches the design note's current behavior (#1620).
- Should the client be allowed to open (read-only) a thread for a processed Inbox item, and should the design show a state for it? -> Decided by the product owner: yes; the thread of a processed item can be opened read-only (history reads as usual, sending is 409 `proposal_locked`, #1620) and the design gets a state for it.
- Should a user be able to continue an approval-card conversation in the originating thread? -> Decided by the product owner: yes; the conversation can continue and the card stays in the thread. An approval is decided only on the card or in the approval list, never by text in the conversation (#1620).
- "Sync the active thread between devices (`semp_threads.last_opened_at`) or client-only?" -> client-only; no column, client falls back to the list route when its remembered thread is missing -> no schema cost, no cross-device requirement stated (#1543).
- Wake run `project_item_id` by thread kind: heartbeat project for tick, Semprec project for chat and item (#1565), as the design note states.
- Column-list `ON DELETE SET NULL (thread_id)` on `agent_runs` so `tenant_id` is never nulled (#1452).

#### (b) Open questions for the product owner
- None.

#### (c) User-visible behavior
Semp conversations become durable, parallel threads: free chats created by their first message, one thread per Inbox item for editing it, and one per automatic task. Every message, from the user and from Semp, is stored permanently, so a reopened thread loads its whole history even months later, and event retention no longer removes it. The app can open any thread, page through its history, and send a message that is accepted immediately and answered asynchronously, with live updates signalled through realtime. Semp keeps each thread's own memory, including the user's questions, and several threads run side by side without blocking each other. Restarts of the service no longer raise false errors for idle threads, and a turn interrupted mid-tool-call no longer prevents the thread from being continued. Messages to a thread whose Inbox proposal is already decided are refused with a clear error, while the thread stays readable. A conversation can continue next to a pending approval card, but approving or rejecting happens only on the card or in the approval list.

### Decisions for job semp-threads-2

#### (a) Decisions adopted from open questions

- Queue shape: FIFO per tenant on `tenantLane('semp-chat')` (a) or per-thread queues with a cap (b)? -> adopted (a) -> conservative: reuses the existing lane convention, needs no cap or queue cleanup, cannot let several threads of one tenant fill all process slots. The ADR (#1370) records (b) as a rejected alternative that a later ADR may adopt.
- Priority and reserved capacity (point 5): keep or drop? -> adopted: keep, via a separate runner with its own concurrency for `sempMessage` (`SEMP_CHAT_QUEUE_CONCURRENCY`, default 2); job priority is only a supplement -> priority cannot interrupt running jobs, so only reserved concurrency guarantees a free slot.
- Interrupted turns after restart: continue or fail? -> adopted: fail with `error_code` `interrupted`; retry is manual -> continuing would repeat tool writes.
  -> Decided by the product owner: an interrupted reply ends with an error and retrying is manual (#1732; the manual retry is #1926).
- Job retries: `maxAttempts` 1 and `unsafe_dedupe` job key per assistant message -> avoids duplicated tool writes and a second concurrent run from a replacing enqueue.
- Rename, delete and archive of threads -> Decided by the product owner: not in v1; threads are not renamed, deleted or archived (#1729, #1769).
- Approval-request activity bump placed in the shared `createPendingApprovalRequest` -> covers gateway, MCP and module-tool producers with one write.

#### (b) Open questions remaining for the product owner

- `pendingApproval.sourceKind`: exact value set (destructive operation name vs `mcpInvoke` vs module tool) is assumed to come from the request snapshot of #1683; confirm what the client needs.
- `subject.label` (card caption such as "Soubor + úkol"): assumed to be stored in the thread's subject snapshot by #1367; confirm the source of the label.
- Delegated runs: the list and the activity bump assume delegated runs carry the thread id (#1452); confirm, otherwise the thread must be resolved through `parent_run_id`.

#### (c) User-visible behavior of this chunk

Every message a user sends in a Semp chat is answered by its own reply, in the order sent; the user can write in another thread meanwhile, and automatic ticks do not block chat because chat has its own queue lane and reserved capacity. A reply interrupted by a restart or a shutdown ends as a clear error and the next message is processed. The chat list shows all of the user's chats and Inbox item threads (or only automatic tasks) ordered by last activity, with a title, a 140-character preview of the last message, and a pending-approval indicator that moves the thread to the top when an approval is requested; titles of automatic-task and Inbox-item threads follow the current heartbeat name and item text.

### Decisions for job semp-threads-3

#### (a) Decisions adopted from open questions

- Search the whole message history, or title and preview only? -> adopted: thread-level search (title and displayed preview) is the default (#1737); history search (#1783) is written as a complete issue but is to be implemented only after the product decision -> the design note leans to deciding first; the list works without it.
  -> Decided by the product owner: search covers the title and the preview; whole-history search (#1783) stays deferred until a later decision.
- Preview match scope -> adopted: the 140 code points the row shows, not the full last message -> a hit the user cannot see would be unexplained.
- Matching technique for the list -> unaccent + ILIKE substring with escaped `%`, `_`, `\`; lemma/prefix full-text only for history search.
- Attribute the generated title to the run, or only to the operation? -> adopted: operation `semp_thread_title` only, no project item, no run header -> avoids a new trusted header and verification in the gateway.
- Title generation failures (error, exhausted budget) -> title stays NULL, no retry, client shows start of first message.
- Title generation never overwrites a title set by the user (`title_source` `user`) or an existing title; only chat threads are titled.
- Chat group of global search -> visible only to the signed-in human; omitted for agent and MCP actors -> chat history is private to the user; conservative.
  -> Decided by the product owner: conversations are only for the signed-in human (privacy); agents and MCP never search them.
- Chat search row has no `itemId`/`databaseId`; match rule identical to the thread list.
- Message vector: one combined vector (`czech` || `czech_simple`), system messages and text-less messages not indexed, no snippet; operator-run reindex after Hunspell activation (not scheduled).

#### (b) Open questions remaining for the product owner

- Should whole-history search (#1783) show a snippet in results (needs a design change)? Only relevant once whole-history search is decided.
- Global chat search has one owner, #1854; title/preview filtering belongs to #1737. These are separate consumers of the same matching rule, not duplicate implementations.
- #1854 edits shared operation schema and the application service registration (hotspot files) that #1842 also touches; ordering follows the listed blocker.

#### (c) User-visible behavior of this chunk

The chat list has a working search: typing a word narrows the list to chats whose title or preview contains it, regardless of case or accents, and "Nothing found" appears when nothing matches. New chats get a short automatic title in the user's language after the first answer (until then the start of the first message is shown); if the AI budget is exhausted the chat simply keeps its untitled look. Global search gains a Chats group that lists matching conversations with their last-activity time and opens the thread, and, once the product confirms it, search also finds chats by what was said inside them, including inflected forms.
