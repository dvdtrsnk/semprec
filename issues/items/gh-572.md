## Context

The review follow-ups pipeline (epic #565) harvests the findings the code-review bot left `open` on merged pull requests. The bot remembers its findings in one issue comment per pull request, its **review memory**. The harvest (a later issue in this batch) needs to find that comment, decode it, and turn it into validated data. This issue is that reader, and nothing else.

What the bot (`dvdtrsnk/code-review-bot`, `scripts/review/memory_store.py`) writes:

- The memory is its own issue comment on the pull request: a visible "🧠 **Review memory**" table, with the marker `<!-- crb-memory:v1:z:<payload> -->` as its last line. The comment is updated in place. If loading fails, the bot saves a second note, so a pull request can carry more than one; the bot itself reads the **newest** comment containing the prefix.
- The payload is `base64.b64encode(zlib.compress(json_utf8, 9))`: the standard base64 alphabet (`+`, `/`, `=` padding) with no line breaks, and zlib-wrapped deflate (RFC 1950), so Node decodes it with `zlib.inflateSync`, not `inflateRawSync`. The bot extracts it as the text between the prefix and the next `-->`, stripped.
- Two identities post it: `github-actions[bot]` (the Actions review workflow) and `bb-agent-relay[bot]` (Relay's review pipeline). Only those two are trusted; the repository is public, so anyone else could post a comment containing the prefix.
- The JSON has `version`, `project_id`, `pr_number`, `head_sha`, `base_sha`, `verdict_*` fields, `findings`, `events` and `notes`. Each finding has `key` (ten lowercase hex characters), `path`, `line` (integer), `severity` (`critical`, `high`, `medium` or `low`), `category`, `description` (clipped to 300 characters, ending in `…` when clipped), `anchor`, `status` (`open`, `resolved`, `wontfix` or `fixed`), `first_seen_sha`, `last_seen_sha` (full SHAs, or `""`), `runs`, `discussion_id` and `note`. Memories written before the bot renamed the field (every one from #280 to #399, 88 of the 153 memories above #266) carry the pull request number as `mr_iid` instead of `pr_number`. Real example, from #551's memory: `{"key": "a54c723e71", "path": "backend/packages/data/src/chokePoint/relationEdgeContext.ts", "line": 27, "severity": "low", "category": "stale-comment", "description": "The JSDoc on `SystemRelationWriteContext` says \"see `assertRelationSideCreatable`/`assertRelationPropertyWritable` below\", but after the move only `assertRelationPropertyWritable` is in this file; `assertRelationSideCreatable` lives in `chokePoint.ts`, so the cross-reference is stale.", "anchor": "", "status": "open", "first_seen_sha": "fb113d8602cc8695c53443ccc0dcbf6d063c5381", "last_seen_sha": "fb113d8602cc8695c53443ccc0dcbf6d063c5381", "runs": 1, "discussion_id": "", "note": ""}`.

The bot's own reader is tolerant and silently skips malformed entries. This reader deliberately is not: the epic decided that a trusted memory which cannot be decoded, or does not have this shape, fails the harvest run, naming the pull request. A silent skip would lose findings, and a format change in the bot must surface.

## Task

Create `.github/scripts/review-followups/memory.mjs`, a zero-dependency ES module with a header comment summarising the format above, exporting:

1. `TRUSTED_REVIEW_BOT_LOGINS` — a frozen array: `github-actions[bot]`, `bb-agent-relay[bot]`.
2. `MEMORY_MARKER_PREFIX = "<!-- crb-memory:v1:z:"`.
3. `selectMemoryComment(comments)` — `comments` is an array of `{ id: number, author: string, createdAt: string (ISO-8601), body: string }`. Returns the comment whose author is in `TRUSTED_REVIEW_BOT_LOGINS` and whose body contains the prefix, newest by `createdAt` (ties: higher `id`), or `null` when there is none.
4. `decodeMemory(body)` — extracts the payload as the bot does (after the prefix, up to the next `-->`, trimmed), rejects anything outside the standard base64 alphabet, inflates with `zlib.inflateSync`, decodes UTF-8 and parses JSON. Throws an `Error` saying which of those stages failed.
5. `parseMemory(value, prNumber)` — validates the decoded value and returns `{ findings }`, where each finding is `{ key, path, line, severity, category, description, anchor, status, discussionId, firstSeenSha, lastSeenSha }` (camelCase, the same values). Throws an `Error` naming the field when:
   - the value is not an object, the pull request number — `pr_number`, or `mr_iid` when `pr_number` is absent — is not `prNumber`, or `findings` is not an array;
   - any finding lacks, or has the wrong type for, one of the fields it returns — `key` must be ten lowercase hex characters, `path` a non-empty string, `line` an integer ≥ 0, `severity` one of the four values, `status` one of the four values, and every other returned field a string.

   Fields it does not return (`runs`, `note`, `events`, `notes`, `verdict_*` …) are ignored whatever their shape, so the bot can add fields without breaking the harvest.
6. `memory.test.mjs` next to it, using `node:test` and `node:assert/strict`, covering every Acceptance criterion below. Its fixture is a payload built in the test with `zlib.deflateSync` and base64, plus the real #551 payload below, which the test must decode to the finding quoted in Context:

## Acceptance criteria

1. `selectMemoryComment` returns the newest trusted comment containing the prefix; it ignores a newer comment by any other author, a trusted comment without the prefix, and returns `null` for an empty list or when no comment qualifies; equal `createdAt` resolves to the higher `id`.
2. `decodeMemory` on a comment whose last line is `<!-- crb-memory:v1:z:<the #551 payload> -->` returns an object whose `pr_number` is 551 and whose single finding matches the one quoted in Context.
3. `decodeMemory` throws, naming the stage, for: no prefix, a payload with a character outside the base64 alphabet, a payload that is valid base64 but not zlib data, zlib data that is raw deflate (made with `deflateRawSync`), and zlib data whose content is not JSON.
4. `parseMemory(decoded, 551)` returns the #551 finding in camelCase; `parseMemory(decoded, 552)` throws naming `pr_number`. A payload carrying `mr_iid: 551` and no `pr_number` parses the same way; one carrying neither throws naming `pr_number`.
5. `parseMemory` throws, naming the field, for a finding with a missing `key`, an eleven-character key, `line: "27"`, `severity: "info"`, `status: "closed"` and `path: ""`; it does not throw for a finding with an extra unknown field or a malformed `events` entry.
6. `node --test .github/scripts/review-followups/memory.test.mjs` passes with no network access.
