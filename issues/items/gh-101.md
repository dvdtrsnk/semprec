**Blocked by:** #99

## Context

The ten system databases do not include the three databases required by Inbox processing.

## Task

Seed database keys `inbox`, `inboxItemTypes`, and `processingProposals` with localized display metadata. Inbox has mandatory user-owned `date` and `time`, user-owned `text`, nullable user-owned relation `type`, and system-owned relation `journalDay`. The client must supply date and time; the server must never replace them with its current date. Resolve `journalDay` at write time through the existing lazy Journal-day mechanism. Seed proposal properties exactly: `kind` (`inbox|transcript`), nullable `sourceInbox`/`sourceTranscript`, `fingerprint`, `proposal`, `history`, `status`, nullable `resultItemId`, and nullable `resultLabel`. Add `GET /api/inbox-types`, returning active types as `{ id, emoji, label }`; relations store the id, never emoji.

## Scope

### In scope

- Baseline schemas, ownership, canonical keys, Journal relation, and type listing.

### Out of scope

- Processing behavior, type lifecycle, proposal endpoints, and Shortcuts UI.

## Acceptance criteria

- Repeated seed is idempotent and validates the exact schema.
- Missing date or time is rejected; delayed capture preserves supplied values.
- Journal day is lazily resolved once and relation integrity is enforced.
- An Inbox item without `type` can be created and later enters `needsClarification`; renaming a type's emoji does not break Inbox relations.
