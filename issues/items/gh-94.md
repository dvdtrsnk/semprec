**Blocked by:** #93

## Context

Background consumers must not mark mail read as an IMAP side effect, and real providers reject excessive concurrent connections.

## Task

Use `BODY.PEEK[]`, never `BODY[]`, whenever content is fetched without an explicit user mark-read action, including AI/background reads. Add a per-account IMAP concurrency limiter and provider-aware backoff for connection-limit responses such as Gmail's simultaneous-connection rejection. Retries must respect the persisted mail sync state and must not create parallel retry storms.

## Scope

### In scope

- Background PEEK semantics, per-account connection limits, and delayed backoff.

### Out of scope

- Live IDLE/push synchronization, partial-fetch fallback, oversized attachments, and message-id conflict hardening, which remain in their existing issues.

## Acceptance criteria

- Background body fetch leaves `\\Seen` unchanged.
- An explicit mark-read path still maps to `\\Seen`.
- Concurrent work for one account never exceeds its configured/provider limit.
- A connection-limit response schedules delayed retry rather than immediate recursion.
