## Context

Model tier rationale: Restoring a CRDT document as a forward update must keep concurrent editors' state consistent and bounded by the history retention rules, which is easy to get subtly wrong.

Retained page history rebuilds a historical document from checkpoints and mirrored updates, with future/expired errors. Restore compares that historical state to live blocks and applies a forward user-authored update without rewriting history. Agent restore remains approval-gated.

Decision: the operation is registered with capability `core.item.write` and `requiresApproval: true` for agent callers.

## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Add `restoreDocVersion(pool, docId, at)` in `docs/docHistory.ts` (or a sibling file) that opens the version with `openDocVersionAt`, then in one transaction under the document lock computes block-level changes against the current state and applies them through the existing doc mutation path with origin `user`. A block present now but not then is removed; a block present then but not now is re-created with its fields and children; changed blocks are reset. Apply `2026-11-01-page-restore-locks-live-items-and-update-identity`: lock/recheck the live item before its document in projection and mutation, and bind approval to retained bigint update identity as a decimal string.
2. Add the operation `page.restoreVersion` following the page operation family conventions of #1394: input `{ itemId, at }` (ISO 8601), output the new block ids summary; errors 404 for an unknown or non-page item, 400 for a future `at`, 410 `history_not_retained` outside the retention window. Register it in the shared operation catalog with its binding and REST route. Validate itemId as a case-insensitive canonical UUID-shaped string before SQL.
3. Tests: restore after an agent edit returns the page to its earlier blocks; a concurrent edit made after `at` by another client is not lost beyond the restored blocks; restoring to the current time changes nothing; a restore is itself restorable; retention errors.

## Acceptance criteria

- When `page.restoreVersion` is called with a time before an assistant edit, then the page returns to its blocks from that time and the restore is recorded as a new update authored `user`.
- When `at` is older than the retention window, then the response is 410 `history_not_retained`; when `at` is in the future, 400.
- When an agent calls the operation without approval, then it is held for approval.
- A stale live check cannot restore a deleted page. Distinct updates invalidate approval despite colliding timestamps; compaction/retention preserve update identity and old versionless approvals conflict.
