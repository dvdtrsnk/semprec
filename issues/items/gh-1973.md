## Context

Model tier rationale: An additive select-option change on a schema-locked database through seed, cutover and i18n, following an existing pattern, plus extending the validation constant and an existence check.

An Inbox item type with `processingMethod: database` names its target in `targetDatabase`, a `select` whose options are the ten system databases (`backend/packages/data/src/seed/seedInboxPipeline.ts`; labels in `backend/packages/data/src/inbox/i18n/en.json` and `cs.json`). One destination that the Inbox must be able to propose into is missing: MCP servers (database module id `mcpServers`, `backend/packages/data/src/seed/mcpModuleKeys.ts`; the tick already treats it specially, see the credential gate in `assertValidProposalEnvelope`). The tick resolves a target with `getDatabaseByModuleId`, so it works as a target once it is selectable and valid.

The Inbox item types database is `schema_locked`, so adding options for existing tenants needs a per-tenant cutover in `backend/packages/data/src/db/tenantCutoverMigrations.ts` (pattern: `runTranscriptsCatalogCutoverMigration`; `docs/adr/2026-09-10-app-code-post-migration-steps.md`). The write validation is the hook of #1436, which owns the explicit allow-list constant of targets; this issue extends that constant. A module added later that ships its own database follows the same three steps: one more option in the seed, one more id in the constant, and a cutover that appends the option for existing tenants. The Inbox seed and cutover registration are shared with the capture properties of #1964, so this issue is ordered after it. The default type catalog (#1977), the recipe proposals (#1974) and the journal method (#1975) build on the extended list.

Decision: only `mcpServers` is added as an option (appended, no existing option changes or moves). A type may target an added option only when that database exists in the tenant, checked at write time in the hook, so a target whose module is not delivered to the tenant cannot be saved.

Decision: the existing options `journal` and `transcripts` stay in the list, because stored types may use them; the hook of #1436 rejects new writes with them.

Shared-file ordering: this issue also waits for #1971 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `canonical-keys` and `testing`.

1. In `seedInboxPipeline.ts` extend the `targetDatabase` options with `mcpServers` (use the module id constant).
2. Add `property.inboxItemTypes.targetDatabase.option.mcpServers` to `inbox/i18n/en.json` (MCP servers) and `cs.json` (MCP servery).
3. Add a per-tenant cutover in a new file `backend/packages/data/src/inbox/inboxTypeTargetOptionsCutoverMigration.ts` that appends the missing options to the `targetDatabase` property config (lock, idempotency check, update; no-op when the Inbox item types database does not exist yet; never reorders or removes options) and register it in `runTenantCutoverMigrations`.
4. Extend `INBOX_TYPE_TARGET_DATABASES` (from #1436) with `mcpServers` and make the type write hook reject an added target when `getDatabaseByModuleId` finds no such database (400 `validation_failed`, `field` `targetDatabase`).
5. Tests: a populated tenant gains the option and a second run changes nothing; a fresh seed matches a cutover tenant; a type with target `mcpServers` is accepted when the MCP servers database exists and rejected with `field` `targetDatabase` when it does not; `journal` is still rejected; the i18n coverage test passes.

### Out of scope

## Acceptance criteria

- After the cutover a populated tenant's `targetDatabase` accepts `mcpServers`, and a second run changes nothing.
- When a type targets `mcpServers`, then the write is accepted; when the tenant has no MCP servers database, then it is rejected with `field` `targetDatabase`.
- A type with target `journal` is still rejected.
- The option has labels in both locales.
