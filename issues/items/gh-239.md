## Context

Issue #238 established the `semprec-api` REST adapter with shared auth, validation, the item envelope, and the error contract. The central principle of the generic REST surface is that no module, project, or new feature ever needs its own CRUD routes — their data is always databases + properties + views served by the generic surface. This slice builds the one mechanism by which an endpoint is allowed to exist outside that generic set: registration of named custom routes through the ModuleRegistry manifest, mounted into the flat `/api` namespace at startup, with a process crash on path collision. #154 then enforces statically that these handlers can never write core tables; #158 registers the file/blob routes through this mechanism.

## Task

Extend ModuleRegistry route manifests (the module manifest contract from #115) to mount named custom routes into the flat `/api` namespace:

- A module manifest declares each custom route by name with its HTTP method and path under `/api`, and the handler it maps to. Routes are mounted into `semprec-api` at startup, using the adapter from #238 (shared auth, validation, status mapping, serialization) — a custom route gets no private auth or error path.
- **Fail-fast on collision**: a duplicate method-plus-path registration crashes the process at startup, identifying both owning modules in the failure. This is a startup decision, never a runtime one.
- **The escape-hatch rule**: a custom route may only exist for an action with its own transactional semantics (a cross-database write in one transaction, an aggregate read outside the item model, a binary upload) or for a read shortcut shaped for exactly one consumer — never for CRUD over module data. Every manifest entry must state which of the two justifications applies; the registry rejects an entry without one.
- Register the existing named exceptions through this mechanism, each in the flat `/api` namespace: `/api/proposals/:id/confirm` (proposal confirmation), `/api/inbox-types` (inbox types), push registration, and `/api/ai-usage` (delivered by #121). Their handlers must not reimplement domain rules — they remain thin mappings onto the service functions that already own those rules.
- `POST /api/files` and `GET /api/blobs/:id` are delivered later by #158 and must register through this same manifest mechanism; leave nothing for #158 to invent beyond its manifest entries and handlers.

## Scope

### In scope

- The route manifest extension, startup mounting into flat `/api`, method-plus-path collision fail-fast, and the exception-policy field with its validation.
- Registration of the proposal-confirm, inbox-type, push-registration, and AI-usage routes through the manifest.
- Tests for mounting, collision, and policy validation.

### Out of scope

- The adapter foundation, item envelope, and error contract — delivered by #238.
- The dependency-cruiser write-boundary rule and the handler contract tests — #154.
- File/blob routes themselves — #158 (they only register through the mechanism built here).
- Generic resource endpoints (#155, #156, #157); WebSocket, MCP, and AgentTool adapters.

## Acceptance criteria

- Duplicate method-plus-path registration crashes startup with both owning modules identified in the error.
- Every registered custom route is served under flat `/api`, authenticates through the shared adapter, and returns errors in the #238 contract.
- A manifest entry without a transactional-semantics or one-consumer-read justification is rejected at startup.
- The proposal-confirm, inbox-type, push-registration, and AI-usage routes are reachable only through manifest registration and their handlers contain no domain rules.
