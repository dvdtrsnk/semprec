## Context

Model tier rationale: One locking write path over existing store and catalog seams, but it must serialize concurrent writers on an item row and change an agent-visible approval contract, so the transaction ordering needs care.

Single-valued relations (a project's area, a task's project: the `item_b` side of a `one_to_many` definition, and either side of a `one_to_one` definition) can hold only one edge. The trigger from migration `0013_relation_cardinality.sql` rejects a second edge with `409 cardinality_violation`, so moving a task to another project is today a `DELETE` followed by a `PUT` in two transactions: a failure between them leaves the task without a project, and `relation.delete` is a destructive operation that an agent can only perform after approval. Each client also has to read the current edge first, and #1404 now provides that read.

This issue adds the operation `relation.set`, which replaces the single edge of a single-valued relation atomically, or clears it. #1590 reuses its single-valued handling for creation, #1621 publishes the invalidations its writes produce, #1713 and #1758 make an agent's `relation.set` wait for approval when it would break a value link, and #1702 and #1833 call it.

Decisions:
- `relation.set` is its own catalog operation, not a `replace` flag on `relation.put`, so MCP and the approval layer can treat replacing an edge differently from adding one.
- The operation is non-destructive and carries the ordinary write risk class (the `write` class of #1423); replacing an existing edge needs no approval. Decided by the product owner: only the value-link-break flag of #1758 forces approval, and only when a link really breaks. The operation is therefore exposed to agents and MCP like `relation.put`.
- A `one_to_one` set whose requested target already holds an edge to a third item fails with `409 cardinality_violation`; it never takes that edge away from the other item. Decided by the product owner: silently ending another item's link would break the rule that links are never broken without an explicit action.
- `targetItemId: null` clears the relation, and is idempotent.
- Setting the same target that is already set is a no-op that returns the existing edge.

Shared-file ordering: this issue also waits for #1518 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `canonical-keys` and `testing`.

1. Add `relation.set` to the catalog: `RelationSetInputSchema` `{ relationPropertyId, callerItemId, targetItemId: string | null }` (strict), operation name, `InputByOperation` / `OutputByOperation` (the new edge, or `null` after a clear), capability `core.item.write` (`nonDestructive`, no `requiresApproval`), port method and binding. It is exposed to agent tools and MCP (`semprec.relation.set`) through the catalog like the other generic operations; add no exclusion. Update the operation-count comments and tests.
2. Add `setRelationWithClient` in `relationOps.ts`: load the relation edge context and apply the same checks as `createRelationWithClient` (archived databases, system-owner writability, endpoint validity, edge hooks). Accept only the single-valued side: side B of a `one_to_many` definition, or either side of a `one_to_one` definition; for any other property the call is `400 validation_failed` with `field: "propertyKey"` (REST) or `field: "relationPropertyId"` (catalog).
3. In one transaction: lock the caller item row with `itemsStore.lockItemById`, read its current edge on this definition, delete it when it differs from the requested target, then insert the new edge (or insert nothing for `null`). Concurrent sets for the same item serialize on the row lock, so two simultaneous sets end with exactly one edge, and a failed insert rolls back the delete. A `one_to_one` definition whose requested target already holds an edge to a third item still fails with `409 cardinality_violation`; do not steal edges from other items.
4. Enqueue rollup recomputes for both the deleted and the inserted edge, as `createRelationWithClient` and `deleteRelationWithClient` do.
5. Add the application service method and the REST route `PUT /api/items/:id/relations/:propertyKey` with body `{ targetItemId: string | null }` (the existing three-segment route for `put` stays), and register it in `routeMatrix.ts`. The response is the edge envelope, or `{ deleted: true }` after a clear.
6. Tests: moving a project to another area succeeds without a `409`; an agent replacing an edge with `relation.set` executes immediately without an approval request; `semprec.relation.set` appears in the agent tool and MCP listings; a `one_to_one` set onto a target held by a third item returns `409` and leaves both existing edges; two concurrent sets leave one edge; a failed insert (archived target database) keeps the old edge; set on a `many_to_many` property returns `400`; clearing; the no-op repeat; rollup recompute for both edges.

## Scope

### In scope

- The `relation.set` operation for single-valued relation sides, its transaction and locking, REST route, and catalog registration.

### Out of scope

- Approval when an agent's `relation.set` would break a value link: #1713 (mechanism) and #1758 (trigger).
- Creating an item together with its relations: #1590.
- Realtime invalidation of edge writes: #1621.
- The after-write hook for edge changes: #1530.

## Acceptance criteria

- When a project's area is set to another area, then the old edge is gone, the new one exists, and no `409` is returned.
- When two sets for the same item run concurrently, then exactly one edge remains.
- When the insert fails, then the previous edge is still present.
- When `relation.set` targets a `many_to_many` property or the many side of a `one_to_many`, then the call fails with `400` naming the field.
- When `targetItemId` is `null`, then the edge is removed, and repeating the call succeeds.
- When the target is already set, then the call returns the existing edge without writing.
- When the property is system-owned or a database is archived, then the same errors as `relation.put` are returned.
- When an agent replaces an existing edge with `relation.set`, then it executes immediately and no approval request is created.
- When a `one_to_one` set targets an item that already holds an edge to a third item, then the call fails with `409 cardinality_violation` and no edge changes.
