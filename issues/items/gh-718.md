## Context

The web client has no session lifecycle. `grep -rn "auth/login\|auth/session\|auth/logout" web/src` finds nothing, although `semprec-api` serves all three (`backend/services/semprec-api/src/authHandler.ts`, `createAuthRequestListener`; inventoried in `backend/services/semprec-api/src/routeMatrix.ts` lines 64-70, 106, 114):

- `POST /api/auth/login` with JSON `{ email, password, platform: "web" }` → `200 { user: { id, email, locale, createdAt } }` plus a `Set-Cookie: semprec_session=…; Path=/; HttpOnly; Secure; SameSite=Lax` header (the token is never in the body for `platform: "web"`); any failure (unknown email, wrong password, lockout) → `401 { error: "Invalid or missing credentials", code: "unauthorized" }`; a malformed body → `400 { error, code: "validation_failed" }`.
- `GET /api/auth/session` → `200 { user: {…}, session: { id, platform } }` with a valid cookie, `401` otherwise.
- `POST /api/auth/logout` → `200 { ok: true }` and a `Set-Cookie` that clears the cookie; `401` without a session.

Every adapter under `web/src/api/` sends `credentials: "same-origin"` and assumes the cookie exists; `httpGenericOperations.ts` line 26 (`UNAVAILABLE_STATUSES`) maps a 401 to an `unavailable` error state, so an unauthenticated user sees "Not available" on every screen with no way to sign in. `web/src/views/setup/SetupWizard.tsx` line 40 links the freshly created account to `?page=login`, which `web/src/main.tsx` does not route — it falls through to `ViewHost` with `viewId=""`. `main.tsx` lines 28-29 still claim "vite.config.ts's dev proxy attaches" a bearer secret (it never did; sibling issue G1 of this batch fixes the proxy itself and leaves this comment to this issue).

Note on `docs/adr/2026-09-14-authenticated-api-boundary-in-web-client.md`: the `AuthenticatedApiClient`/`AuthenticatedWebProvider` it prescribes are never mounted by `main.tsx`/`App.tsx` (nothing outside `web/src/view-types/**` and their own tests imports them), so there is no live boundary to extend; the login adapter below follows the pattern every live adapter uses (`setupOperations.ts`, `agentRunOperations.ts`: a `create*Operations({ baseUrl, fetchImpl })` factory with zod parsing at the edge). Sibling issue G4 of this batch deletes that stack and supersedes the ADR; say this in the PR description.

Sibling issue G7 later edits `main.tsx`/`App.tsx` (approval route), sibling G8a reads the session user's `locale` this issue exposes.

## Task

One mechanism — the session lifecycle: bootstrap, login, mid-session expiry, logout.

1. **Auth adapter** — `web/src/api/authOperations.ts` (new):
   - `export const sessionUserSchema = z.object({ id: z.string(), email: z.string(), locale: z.string(), createdAt: z.string() })`; `export type SessionUser`.
   - `createAuthOperations({ baseUrl, fetchImpl? }): AuthOperations` with:
     - `login({ email, password }): Promise<SessionUser>` — `POST ${baseUrl}/auth/login`, JSON body `{ email, password, platform: "web" }`, `credentials: "same-origin"`, `Content-Type: application/json`; parse `{ user: sessionUserSchema }`; a 401 throws `OperationError("unavailable", <server error string or default>, 401)`; other non-OK statuses throw `retryable` with the server's `{ error }` message when the body has one (same `readErrorMessage` shape as `setupOperations.ts`; copy it, do not import across adapters); transport and parse failures are `retryable`.
     - `getSession(): Promise<SessionUser | null>` — `GET ${baseUrl}/auth/session`; parse `{ user: sessionUserSchema }`; **401 resolves `null`** (an anonymous visitor is an ordinary outcome, not an error); everything else non-OK throws `retryable`.
     - `logout(): Promise<void>` — `POST ${baseUrl}/auth/logout`; 200 and 401 both resolve (a session that is already gone is logged out); other statuses throw `retryable`.
   - Never read or store the token: the cookie is `HttpOnly` and the body never carries it.
2. **Session-aware fetch** — `web/src/api/sessionFetch.ts` (new): `createSessionFetch(onUnauthorized: () => void, fetchImpl: typeof fetch = globalThis.fetch.bind(globalThis)): typeof fetch` — calls `fetchImpl`, and when `response.status === 401` calls `onUnauthorized()` before returning the response unchanged. Adapters keep their own status handling.
3. **Login page** — `web/src/views/login/LoginPage.tsx` (new) with `web/src/views/login/login.css` (new, the `setup.css` form look): props `{ auth: AuthOperations; onLoggedIn: (user: SessionUser) => void }`; email (`autoComplete="username"`) and password (`autoComplete="current-password"`) fields, a submit button; while submitting the fields and button are disabled and the button reads `login.submitting`; a 401 renders `login.error.invalid` in a `role="alert"` paragraph and keeps the form; any other failure renders `login.error.failed` with `{message}`; success calls `onLoggedIn(user)`. All labels via `useTranslate()`.
4. **i18n** — add to both `en` and `cs` in `web/src/i18n/messages.ts`: `login.title` ("Sign in" / "Přihlášení"), `login.email`, `login.password`, `login.submit` ("Sign in" / "Přihlásit se"), `login.submitting`, `login.error.invalid` ("The email or password is not correct" / "E-mail nebo heslo není správné"), `login.error.failed` ("Signing in failed: {message}" / "Přihlášení se nezdařilo: {message}"), `login.logout` ("Sign out" / "Odhlásit se"), `login.logoutFailed` ("Signing out failed: {message}" / "Odhlášení se nezdařilo: {message}"), `login.signedInAs` ("Signed in as {email}" / "Přihlášen(a) jako {email}").
5. **Bootstrap in `App`** (`web/src/App.tsx`):
   - New props: `auth: AuthOperations`, `sessionEvents: EventTarget`, `login?: true` (the `?page=login` route).
   - Session state `{ status: "loading" } | { status: "anonymous" } | { status: "authenticated"; user: SessionUser } | { status: "failed"; error: OperationError }`. On mount, unless the `setup` route is present (the wizard runs before any user exists — never call `getSession()` for it), call `auth.getSession()`: a user → `authenticated`; `null` → `anonymous`; a thrown error → `failed`, rendered with `ErrorState` and a retry that re-runs the bootstrap.

## Acceptance criteria

- When the app loads with no session cookie (or an expired one), `GET /api/auth/session` returns 401 and the login page is rendered; no other adapter request is issued before login.
- When valid credentials are submitted, `POST /api/auth/login` is sent with `platform: "web"`, the browser stores the `HttpOnly` cookie from `Set-Cookie`, the header shows `Signed in as <email>`, and the routed content renders.
- When wrong credentials are submitted, the page shows the invalid-credentials message and the form stays usable; the app does not navigate.
- When an authenticated user opens `/?page=login`, the app navigates to `/`.
- When any adapter receives a 401 mid-session, the login page replaces the content without a reload.
- When the user clicks "Sign out", `POST /api/auth/logout` is sent and the login page is shown; the next `GET /api/auth/session` returns 401.
- When the URL is `/?page=setup&token=…`, the wizard renders and `GET /api/auth/session` is never called; its success link `?page=login` opens the login page.
- `pnpm run verify` in `web/` passes; the tests named above exist and pass.
