## Context

Model tier rationale: It adds a third kind of approval request with exactly-once execution after a human decision and conflict detection against a snapshot, spanning agents, queue and notifications.

#1523 puts module agent tools into agent sessions. Some of them change data and must not run on the agent's say alone. Approval requests exist today for two producers: MCP invocations and generic operations. `ApprovalRequestSafeSummary` in `backend/packages/data/src/mcp/approvalRequestsQueue.ts` knows only `mcpInvoke | genericOperation`, and `handleApprovalRequestExecuteTask` in `backend/packages/data/src/mcp/approvalRequestExecution.ts` executes only these two.

This issue adds the third producer. The tools of #1846, #1949, #1957 and #1840 use it.

Builds on: #1728 (thread activity bump on a new request), #1683 (localizable description snapshot), #1618 (link to the tool call), #1789 (realtime invalidation), #1772 (outcome posted into the thread) and #1787 (notification linked by source).

Shared-file ordering: this issue also waits for #2002 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `ai-gateway` and `testing`. Because `mcp/approvalRequestExecution.ts` is a hotspot, keep the change to the new kind's branch.

1. Add `requiresApproval?: boolean` and an optional `snapshotExport` (a handler export that returns a snapshot of the source the call affects) to `ModuleAgentToolDescriptor`.
2. In the session composition from #1523, a tool with `requiresApproval` does nothing when called: it creates an approval request and returns a result telling the model the call awaits human approval.
3. Add the `moduleTool` payload and a safe summary variant `{ kind: "moduleTool", toolName, argKeys }`; the request records the description (as #1683 defines), the tool call id (#1618), the snapshot, and bumps the thread's activity (#1728).
4. On creation it also creates the `approval_pending` notification linked by source (#1787).
5. After approval, `handleApprovalRequestExecuteTask` resolves the handler through `ModuleRegistry`, recomputes the snapshot, and when it differs records a `conflict` outcome without running the handler; otherwise it runs the handler exactly once (the existing claim mechanism) and records the outcome. It then publishes the realtime `approvalRequest` event and the system message with the outcome (#1789, #1772).
6. Tests: a tool with `requiresApproval` creates a request of kind `moduleTool` and runs nothing; approval executes once even if the task is delivered twice; a changed source gives `conflict` and no execution; rejection runs nothing; a missing handler records an error outcome.

### Out of scope

- The shared parts of the approval pipeline named above, each delivered by its own issue.

## Acceptance criteria

- When the agent calls a tool with `requiresApproval`, then a request of kind `moduleTool` exists and the handler has not run.
- When it is approved, then the handler runs exactly once, also if execution is delivered twice.
- When the source changed between request and approval, then the outcome is `conflict` and the handler did not run.
- When it is rejected, then the handler never runs.
