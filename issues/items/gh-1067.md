## Context

Model tier rationale: The migration and default flip are specified, but binding every test-created user to a tenant requires finding and fixing fixtures across the whole suite.

Isolation fails closed only once nothing falls back to "the sole tenant". #968 created three SQL functions:

- `app_current_tenant()` = `NULLIF(current_setting('app.tenant_id', true), '')::uuid` (STABLE; the `NULLIF` matters because the setting reads `''` after a transaction-local `set_config` ends, and system scope sets `''`);
- `app_sole_tenant()` = the tenant id when exactly one `tenants` row exists, else NULL;
- `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())` — the transitional definition.

Every tenant table's `tenant_id` default is `app_tenant_default()` (#972), and its RESTRICTIVE policy `tenant_isolation` is `USING/WITH CHECK (tenant_id = (SELECT app_tenant_default()))` (#973). Redefining that one function therefore flips every default and every policy atomically. In code, `enforceTenantScope(site)` in `backend/packages/shared/src/tenantScope.ts` (#978) reads `SEMPREC_TENANT_SCOPE` on every call: unset, `""` or `warn` mean warn mode (log `tenant_scope_missing` with the stack and proceed), `strict` throws `TenantScopeMissingError`, anything else throws. `withTransaction`, `pool.query` and `pool.connect` on a `createPool` pool call it whenever no scope is active. `users.tenant_id` was added nullable by #968; every user has been bound to a tenant since then (the existing user to tenant zero, every new account by `bootstrapFirstAccount`).

This is a contract step and ships in a release after the checkpoint release (#1058): the release a rollback lands on sets a scope on every path (proven in production), no longer runs tenant jobs without a tenant (#1061) and already has the composite foreign keys (#1066). `SET NOT NULL` is flagged by the migration check (`backend/packages/data/src/db/migrationCompatibility.ts:106`) unless the file carries an exemption line.
