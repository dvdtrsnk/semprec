## Context

Model tier rationale: One status transition on a single card with an existing locking and history pattern, but it deliberately relaxes the "locked card never changes" rule, so the guards need care.

A discarded card is final today. `LOCKED_PROPOSAL_STATUSES` (`confirmed`, `rejected`, in `backend/packages/data/src/inbox/inboxTypesStore.ts`) is honored by revise (`reviseProposalWithClient` throws), by the Inbox tick that skips locked cards (`inboxTickAction.ts`) and by reject (refuses `confirmed`). The user can discard a card by mistake with no way back, and the Inbox "undo" control must return the last decision to the stack with the values the card had.

#1845 adds `POST /api/proposals/:id/reject`. #1912 adds reset-overrides, which establishes the card's effective envelope (AI proposal plus user overrides) that must survive a discard unchanged. #1943 extends the same route so a confirmed card can be reopened too; this issue only handles `rejected`.

Decision: reopen leaves the stored proposal, user overrides and earlier history untouched and appends one history entry of kind `reopened`. The state a card had before it was discarded is not recorded, so reopen recomputes nothing: it sets `proposed` when the stored envelope passes the existing envelope validation and `invalid` otherwise.

Shared-file ordering: this issue also waits for #1935 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `reopenProposalWithClient(client, config, proposalId, { ifVersion? })` in `backend/packages/data/src/inbox/proposalActions.ts`: lock the card; if `proposed` return it unchanged (idempotent); if `rejected` validate the stored envelope with the existing validation and set `proposed` (or `invalid` when it no longer validates), append a history entry of kind `reopened` and enqueue the Journal inbox recompute; if `confirmed` answer 400 `validation_failed` with field `status` (extended by #1943); an optional `ifVersion` follows the check order of #1852 (state first, then version, then 409 `version_conflict`).
2. Allow the one explicit `rejected -> proposed` transition in the module's locked-status handling so the generic tick and revise guards keep treating `confirmed` and `rejected` as locked everywhere else.
3. Add `POST /api/proposals/:id/reopen` with optional body `{ ifVersion? }`, a handler in `inboxRouteHandlers.ts`, a `customRoutes` entry in `inboxModuleManifest.ts`, and entries in `routeMatrix.ts` and `tenantIsolationRoutes.test.ts`.
4. Tests: reject then reopen returns the card to `proposed` with the same envelope and overrides; reopening twice is a no-op; reopening a confirmed card answers 400; stale `ifVersion` answers 409; the reopened card is listed by `GET /api/inbox/cards` again; the tick still skips `rejected` cards.

## Scope

### In scope

- Reopening a `rejected` card with a `reopened` history entry and an optional version check.

### Out of scope

- Reopening a `confirmed` card and reverting its writes; #1943.
- Cancelling follow-up jobs; #1984.
- Any time limit on reopening: none is applied (the undo is unlimited).
- Type replacement and recompute of the card; #1947.

## Acceptance criteria

- When a rejected card is reopened, then it is `proposed` again with the same proposal and overrides, and it appears in `GET /api/inbox/cards`.
- When reopen is called on a `proposed` card, then it returns 200 unchanged.
- When reopen is called on a `confirmed` card, then it answers 400 `validation_failed` with field `status`.
- When `ifVersion` is stale on a rejected card, then it answers 409 `version_conflict` and the card stays `rejected`.
