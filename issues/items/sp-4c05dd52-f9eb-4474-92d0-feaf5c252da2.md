### Requirement gh-1944: [calendar-invites 07/13] Respond to an invitation and create or trash its Event in one transaction

#### Context

Model tier rationale: A new tenant-facing mutation that changes an invitation's status and creates, restores or trashes an Event across two databases in one transaction, with a status machine that allows changing an answer, caller-chosen calendar validation and cross-tenant isolation, so a defect corrupts calendar data or leaks across tenants.

#1929 fills the Invitations database from incoming mail with `pending` rows. This issue lets the user answer one. It adds `POST /api/calendar/invitations/:id/respond`, a custom route of the calendar module (the program rule: the calendar module registers its own routes only for calendar-specific resources such as invitations; Tasks and Events routes belong to the systemDatabases module). A custom route is justified here as `transactional-semantics`: the status change and the Event write must commit together, which the generic item endpoints cannot express.

Behavior of an answer:

- `accepted` and `tentative` create an Event for the invitation (title, place, wall-clock start and end in the tenant time zone) in the chosen calendar, link it through the invitation's `event` relation, and set `status` and `respondedAt`. Both answers produce the same Event; the calendar shows a `tentative` answer as unconfirmed attendance from the invitation's status (#2008 returns it in the calendar timeline), so nothing tentative-specific is written to the Event.
- When the invitation already has an `event` edge (the user changes an earlier answer), no second Event is created: a live linked Event is kept unchanged (the user's own edits stay), and a linked Event that is in the trash (after an earlier `declined`) is restored through the existing restore path (`restoreItemWithClient`).
- `declined` sets `status` and `respondedAt`, and moves the invitation's Event to the trash if one exists (the Event is not deleted permanently).
- `acknowledged` is accepted only for a row of kind `sharedCalendarNotice` and only moves its status; an invitation of kind `invite` accepts the other three answers only.
- The tenant time zone and "wall clock" conversion use the calendar time module from #1418. A timed invitation without an end gets no explicit end; the Events pre-write transform from #1598 supplies the default. An all-day invitation becomes an Event with `timeFrom` empty, `date` the first day and `endDate` the last day when it differs. Writing the Event goes through the choke point, so the date and time validation from #1663 applies and a failure rolls everything back.
- The calendar is `calendarId` from the body when given, otherwise the invitation's `suggestedCalendar`. The Event is created with that calendar passed at creation, in the way #1761 defines for callers that choose their own calendar, so the default-calendar create hook does not add a second one.

Decision (product owner): an answer can be changed. Answering an invitation that is already `accepted`, `tentative` or `declined` with a different answer applies the new answer as above and sets a new `respondedAt`; #1953 then sends a new reply to the organizer. Answering with the answer that is already stored changes nothing and returns the invitation unchanged. Answering an invitation whose status is `cancelled` (the organizer cancelled it) returns 409 `conflict`.

Decision (product owner): the Event created from an invitation has `type` `meeting`.

Decision: a chosen calendar has to be a live, user-owned calendar (not a system or subscription calendar); otherwise the request fails with 400 `validation_failed` (field `calendarId`).

The reply message to the organizer is sent by #1953 after this transaction commits; this issue does not send anything.

Shared-file ordering: this issue also waits for #1937 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-2006: [calendar-invites 12/13] Cancel an invitation and trash its Event when the organizer sends CANCEL

#### Context

Model tier rationale: Attacker-controlled inbound mail changes a stored invitation and moves a user's Event to the trash, so the sender check, the per-`UID` serialization and the idempotency must be exact; a mistake lets a forged message remove meetings from the calendar.

#1929 reads the calendar parts of every new Emails item in the `calendar.ingestInvitation` heartbeat action (`backend/packages/data/src/calendar/invitationIngestAction.ts`) and creates or updates an invitation for `METHOD:REQUEST`; it leaves `METHOD:CANCEL` untouched. #1901 gives the invitation `status` the option `cancelled`. #1944 creates the Event of an accepted or tentative invitation and links it through the invitation's `event` relation, and refuses to answer a `cancelled` invitation. #1954 writes the invitation's notification and resolves it when the user answers; the `pendingInvites` badge counts only `pending` invitations.

When the organizer cancels the meeting, an invitation that stays as it is would leave an invalid meeting in the calendar. This issue applies the organizer's `CANCEL`: the invitation becomes `cancelled` and its Event goes to the trash, where the user can restore it.

Decision (product owner): a `CANCEL` from the organizer moves the Event created from the invitation to the trash (restorable, never deleted permanently) and marks the invitation `cancelled`.

Decision: a `CANCEL` is applied only when the message's own sender address (`mail_message_meta.envelope.from`) equals the invitation's `organizerEmail` (case-insensitive), the same sender rule #1950 uses for replies; SPF/DKIM is not checked. A `CANCEL` whose `SEQUENCE` is lower than the stored `sequence` is stale and ignored.

Decision: the user's answer (`respondedAt`) is kept for the record; only `status` changes. Cancelling sends nothing to anybody.

#### Task

Load `state-writes`, `io-hardening` and `testing`.

   - check the sender rule above and the `SEQUENCE` rule; on a mismatch do nothing and log the email item id with a reason code;
   - when `status` is already `cancelled`, do nothing;

   A failure in any step rolls the whole email's transaction back; the action never throws for a malformed or unmatched message. Logs never carry the invitation content.

Tests (in `backend/packages/data/src/calendar/__tests__`): a `CANCEL` from the organizer's address for a pending invitation sets `cancelled` and its notification is resolved; for an accepted invitation it also trashes the linked Event, and restoring that Event from the trash works; a `CANCEL` from another sender, for an unknown `UID`, or with a lower `SEQUENCE` changes nothing; a second processing of the same email is a no-op; `pendingInvites` no longer counts a cancelled invitation; answering a cancelled invitation through the respond route stays 409; a `REQUEST` with a higher `SEQUENCE` for a cancelled invitation changes nothing.

### Requirement gh-2008: [calendar-invites 08/13] Return a tentative invitation answer on its Event in the calendar timeline

#### Context

Model tier rationale: One additive enrichment of existing timeline Event items through a single batched lookup over the invitations database, using the existing timeline fixtures; no new write path or ownership contract.

#1944 lets the user answer an incoming invitation `accepted` or `tentative`; both create the same Event, linked from the invitation through its one-directional `event` relation, and the answer can be changed later. ### Requirement gh-1939: [inbox-editing 19/23] Split one Inbox source into several proposal cards

#### Context

Model tier rationale: Introduces a new producer of Inbox cards, a schema change on Processing proposals and a change to the tick's card selection, so ownership, tenant data migration and lifecycle consistency all matter.

When the user writes "split this into several items" in an Inbox item's thread, one capture such as a shopping note and a deadline should become several proposal cards. #1380 records the decision this issue implements: a user-context Inbox-module action creates the sibling cards; the first card remains the source's primary card and the only one the tick recomputes; siblings carry `splitFromProposalId` and are ignored by the tick. The agent tool infrastructure (#1906) provides registration of Inbox agent tools, and multi-step envelopes (#1378) define how a card with several steps is stored; a split produces several cards, each with its own (possibly multi-step) envelope.

Decision: the tool is `inbox.proposal.split` with arguments `{ proposalId, cards: [{ entityKind, target, properties }, ...], message? }` (at least two and at most the maximum fixed by the ADR). ### Requirement gh-1940: [transcripts 17/19] Recompute a transcript card from a user instruction

#### Context

Model tier rationale: A new queue task in `semprec-transcribe` that writes into existing Inbox cards owned by another module's actions, racing with user edits and with the card's own confirm and revise paths, around a paid model call made outside any transaction; the lock ordering, the protection of user-edited fields and the idempotency of retries are the hard parts.

The Inbox card of a recording (a card for the recording's Event or for one speaker) can be corrected by the user in words: they give Semp an instruction such as "it was the call with the accountant". #1870 mounts `POST /api/proposals/:id/revise` and, for a transcript card with a message and no envelope, only records the instruction in the card's history. Nothing acts on it yet. Today `reviseProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) takes a ready envelope, no model is involved, and a transcript card is only ever created by the transcription worker (`transcriptEventMatch.ts`, `transcriptSpeakerSuggestion.ts`).

This issue makes the instruction act. When a message-only revise is recorded on a transcript card, the same transaction enqueues a new core task `transcriptCardRecompute`. The task runs in `semprec-transcribe`, reads the transcript, the card (its `context`, current proposal and edit state) and the instruction, asks the AI gateway for a new proposal outside any transaction, and writes the result back under the card's row lock. The write follows the card-state model of the Inbox work: the model's answer goes to `aiProposal` and bumps `aiVersion` (#1471), the history gets an entry of kind `threadRevision` (#1430), and the effective `proposal` is composed by the server so that values the user edited by hand (`userEditedKeys`, protected by #1921 and #1892) are not overwritten unless the instruction explicitly asks to change them. The queue runner for short model tasks is the one created with #1624 (it keeps the fast row-creation task from waiting behind a gateway call).

Decisions:

- The model may only choose among the candidates already on the card (`context.candidates` for an Event card, `context.alternatives` for a speaker card, plus the card's current target) or edit the fields of the current new-item proposal. An instruction that cannot be satisfied this way leaves the proposal unchanged and adds a history entry saying so.
- The role of a card never changes: an Event card stays an Event card and a speaker card stays a speaker card; a result that would switch the role is discarded like any invalid result.
- A key the user edited by hand is changed only when the model lists it in `explicitlyChangedKeys`, which it must do only when the instruction names that field; the key then stays in `userEditedKeys`.
- Locked cards (`confirmed`, `rejected`) are never recomputed; the task is a no-op for them.
- The content of the transcript and of the instruction is never logged.

Shared-file ordering: this issue also waits for #1939 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.
