## Behavior specification

Semp turns: attachments, ref expansion, prompt and tools.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: semp-turns-1

#### (a) Adopted decisions
- Recording ref target (Transcripts item or Files audio?) -> Transcripts `item` ref -> it holds summary, speakers, segments; audio reachable from it.
- E-mail ref: `item` on Emails vs mail thread kind -> `item` here; `mailThread` added by #1933 -> that issue owns thread data.
- Which kinds the schema defines -> item, block, transcriptSegment, mailAttachment, agentRun, approvalRequest; later kinds are added by the issues that bring their data -> keeps the union closed without inventing unbuilt data.
- Is the 20-ref limit counted before dedup? -> before (submitted array) -> conservative.
- Trashed item as a ref -> accepted, purged/foreign rejected -> trash is restorable.
- Block ref validation -> block id must exist in the item's doc; segment ref only requires a Transcripts item.
- agentRun/approvalRequest label in history -> truncated run task / approval description (my choice; confirm).
- File text: extract at turn time vs persistent extraction (open question) -> turn time, size cap 10 MB, nothing persisted -> conservative, no new storage contract.
- Limits 8000 chars per ref and 32000 per turn kept as named constants.
- Confirm the 8000 / 32000 character limits and the 10 MB extraction cap -> Decided by the product owner: the limits stay 8000 / 32000 characters and the extraction cap 10 MB (#1733, #1740).
- Should a file attached from the chat "+" button become a permanent Files item or a temporary blob? -> Decided by the product owner: a permanent Files item through `POST /api/files`; one file mechanism, and it can be moved to the trash (#1740).
- Expanded refs are never persisted; user message keeps refs only -> design note rule.
- Images: replaced by text placeholder when they do not fit the 4 MB budget; newest first.
- Chat system prompt composes with project guidance; date goes in a per-turn user prefix.
- Item threads get a fixed read-only generic operation set (database.list/get, property.list/get/getByKey, view.list/get/query, item.get, database.query).
- Do chat runs see heartbeats of all projects? -> Decided by the product owner: yes; Semp in chat reads the heartbeats of every project of the tenant (read only), because chat is the general place for questions; sensitive projects without a granted access are left out. #1523 keeps the own-project rule; #2018 widens `heartbeat.list` and `heartbeat.history` for chat runs, `heartbeat.trigger` stays own-project.
- Which timezone does the per-turn date prefix use? -> Decided by the product owner: the timezone of the system settings (the `timezone` of the System settings item); a device only proposes a change for the user to confirm, so the day rollover and the date in a turn use the same value (#1738).
- Module capabilities in grantedCapabilities follow the ADR of #1385.

#### (b) Open questions for the product owner
- None.

#### (c) Behavior delivered
A user can attach objects (tasks, events, e-mails, notes blocks, transcript passages, files, attachments, people, Inbox items, runs, approvals) to a message to Semp. The backend checks that every attached object exists and belongs to the user, stores it once, and shows it in the thread history under its current name or as trashed or no longer existing. For each turn, Semp receives the objects with their surroundings (an e-mail thread, neighbouring blocks, transcript context, text of PDF and DOCX files, and images as images), within size limits and without storing the expanded content. Chat turns use a chat prompt and know today's date in the timezone of the system settings; Inbox card threads only read. Module tools (such as heartbeat tools) become available to Semp, in chat Semp can read the automatic tasks of every project (except sensitive ones without access), and tools that change data wait for the user's approval and run exactly once after it.


### Decisions: semp-turns-2

#### (a) Adopted decisions
- Who composes the revised envelope -> the thread agent; the tool only validates and stores -> design note and design agree.
- May the tool change kind, target, relations and hand-edited keys -> yes (user instruction), user-edit rules owned by #1471 / #1938.
- History attribution for AI revisions -> `{author: ai, kind: threadRevision, threadId, messageId}` -> ids resolved from the persisted run, never from arguments.
- Tool input shape -> `{proposalId, entityKind?, target?, properties, message?}` (not `{proposalId, instruction}`), as the design note decides.
- The thread-revision rules from the cancelled #1938 are part of this issue, as the design note states; #1938 now only loads card context.
- Step and changes mapping (tool_use/tool_result to steps, changed-item cards) is not in this issue (thread-history issues own it); the tool only returns a clear result.

#### (b) Open questions for the product owner
- None blocking. Check that #1430 already types the `threadRevision` history kind; if not, this issue adds it (listed in Touches).

#### (c) Behavior delivered
In an Inbox item thread, Semp can correct the proposal card of that item at the user's request (change what it is, which project it belongs to, fill in missing details). The correction replaces the card's proposal, is attributed to the AI in the card history with the thread and message it came from, never touches the real target data (the user still confirms), is refused for confirmed or rejected cards, and cannot affect any other card. The card redraws immediately.
