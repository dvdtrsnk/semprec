## Context

`observabilityCheckSystem` runs every minute (`backend/packages/data/src/worker.ts:87`, handler at `:210-212`). `handleObservabilityCheckSystemTask` (`backend/packages/data/src/observability/observabilityCheckSystem.ts:209-217`) runs four check families. Each one upserts its state into the single table `observability_checks` (`backend/packages/data/src/db/migrations/0039_observability_checks.sql`): `check_key text UNIQUE`, `status`, `detail jsonb`, `changed_at`. The upsert goes through `transitionObservabilityCheck` (`backend/packages/data/src/observability/observabilityChecksStore.ts:22-57`). On a genuine ok-to-alerting flip the family notifies through `notifyObservabilityAlert` (`observabilityCheckSystem.ts:21-40`).

Three families are operator signals with content-free details:
- `process:<name>` (`:43-60`, `{ process, present, beatAt }`);
- `queue:backlog` (`:107-122`, `{ pending, oldestAgeMs }`);
- `queue:permanentlyFailedJobs` (`:138-156`, `{ count }`).

The fourth, `checkMailSync` (`:171-199`), is per mailbox:
- it reads **every** `mail_account_sync_state` row (`listAllMailAccountSyncStates`, `backend/packages/data/src/mail/mailAccountSyncStateStore.ts:321-324`);
- it deletes orphaned `mail:` rows (`observabilityChecksStore.ts:64-76`);
- it writes one global row per mailbox, `mail:<mailboxItemId>`, whose `detail` holds the provider's raw `lastError` (`:185-189`). Its notification payload does too (`:192-195`).

A tenant's mailbox state and error text thus land in a global table. With several tenants they would be read back, together with every other tenant's, by `getAlertingChecks` in the System report (`backend/packages/data/src/observability/systemHealthReport.ts:97-103`).

`mail_account_sync_state` is a tenant table. Under a RESTRICTIVE RLS policy (`tenant_id = (SELECT app_tenant_default())`, with `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())`), the system-scope read sees mailboxes only while exactly one tenant exists. With two tenants, or after the strict switch (#1067), every mailbox check would silently vanish.

Mailbox checks therefore move into a new **tenant** table, `tenant_observability_checks`, evaluated per tenant. `observability_checks` keeps only the global, content-free families. The System report keeps showing the caller's own mailbox alerts, so nothing changes for today's single user.

Tenancy state this issue builds on:
- Every tenant table is created with these, in its own migration:
  - `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)`;
  - `COMMENT ON TABLE … IS 'semprec:tenancy=tenant'`;
  - RLS enabled, with the RESTRICTIVE policy `tenant_isolation` `USING/WITH CHECK (tenant_id = (SELECT app_tenant_default()))` and the PERMISSIVE policy `tenant_rows USING (true) WITH CHECK (true)`;
  - every unique index leading with `tenant_id`.
- The catalog conformance test (`backend/packages/data/src/__tests__/tenancyCatalog.test.ts`) checks all of that.
- `runInTenant`, `runAsSystem` and `currentTenantScope` come from `@semprec/shared`. `withTransaction` and the pool set `app.tenant_id` from the scope: `''` for system.
- #982 lists `observabilityCheckSystem` as a `system` task in `TASK_TENANCY`, so the runner calls its handler inside `runAsSystem`.
- #983 added `forEachActiveTenant(pool, work: (tenantId) => Promise<void>)` (`backend/packages/data/src/tenancy/forEachActiveTenant.ts`, exported from `@semprec/data`).
  - It runs inside its own `runAsSystem` and calls `work` inside `runInTenant(tenantId, …)` for each `active` tenant, starting at a rotating offset.
  - A throwing tenant does not stop the others. The failures are rethrown together as one `AggregateError`.

## Task

Load `db-migrations` (new tenant table), `state-writes` (upserts, deletes, notification after the transition) and `error-handling` (one tenant's failure must not hide the others').

1. **Migration.** Take the next free migration ordinal at commit time, for example `NNNN_tenant_observability_checks.sql`.
   - Create `tenant_observability_checks (id uuid PRIMARY KEY DEFAULT gen_random_uuid(), tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id), check_key text NOT NULL, status text NOT NULL CHECK (status IN ('ok','alerting')), detail jsonb NOT NULL DEFAULT '{}'::jsonb, changed_at timestamptz NOT NULL DEFAULT now(), UNIQUE (tenant_id, check_key))`.
   - Add the `semprec:tenancy=tenant` comment.
   - `ENABLE ROW LEVEL SECURITY` with `tenant_isolation` (RESTRICTIVE) and `tenant_rows` (PERMISSIVE), exactly as above.
   - Per `docs/operations/database-roles.md` ("Extending the grants"), `GRANT SELECT, INSERT, UPDATE, DELETE ON tenant_observability_checks TO semprec_side`. `semprec_data` inherits it.
   - Additive and rollback-safe: the previous release never reads the table.
2. **Store (`observabilityChecksStore.ts`).** Add `transitionTenantObservabilityCheck(client, checkKey, compute)` and `deleteOrphanedTenantObservabilityChecks(client, checkKeyPrefix, currentCheckKeys)`.
   - Same contracts as the global pair, on `tenant_observability_checks`: `FOR UPDATE` read, `ON CONFLICT (tenant_id, check_key)`, and `changed_at` advancing only on a flip.
   - They rely on RLS and the column default for the tenant. No hand-written `tenant_id` predicate.
   - Sharing a body with the global pair is fine, if the table name is a closed union, never interpolated from input.
3. **Check system (`observabilityCheckSystem.ts`).** `handleObservabilityCheckSystemTask` keeps its signature. It runs in the system scope the task runner provides; tests call it inside `runAsSystem`. In order:
   - (a) the process, backlog and failed-job families, unchanged, on `observability_checks`;
   - (b) `deleteOrphanedObservabilityChecks(client, "mail:", [])`, which purges every legacy global `mail:` row, so a rollback-and-forward cannot leave stale `lastError` behind;
   - (c) `forEachActiveTenant(pool, …)` running today's `checkMailSync` body per tenant on the tenant table. The read sees only that tenant's mailboxes, orphans are deleted per tenant, and `detail` keeps `{ mailboxItemId, nextExpectedActivityAt, lastError }` because the row is tenant-owned;
   - when any tenant fails, the handler rejects after all tenants were attempted.
   - `notifyObservabilityAlert` takes the source table: `mail_sync_stalled` notifications use `sourceTable: "tenant_observability_checks"` and the tenant row's id. The recipient lookup is unchanged.
   - Update the docstrings.
4. **System report (`systemHealthReport.ts`, `getAlertingChecks` only).** Return the alerting rows of `observability_checks` plus the alerting rows of `tenant_observability_checks` visible in the caller's scope (`UNION ALL`), ordered by `changed_at`. The `AlertingCheck` shape is unchanged.
5. **Tests.**
   - Update the mail cases of `backend/packages/data/src/__tests__/observabilityCheckSystem.test.ts:176-229` to read the tenant table, and wrap its `runCheck` helper in `runAsSystem`. Add the single-tenant cases below there.
   - New `backend/packages/data/src/__tests__/tenantObservabilityChecks.test.ts` holds the report and two-tenant cases.
   - Both files delete `tenant_observability_checks` rows in `beforeEach`, because a `resetDatabase` that truncates only its fixed `TABLES` list would miss the new table. `backend/packages/data/src/testSupport/testDb.ts` is not edited.

## Acceptance criteria

All integration tier.
- **Catalog.** `tenancyCatalog.test.ts` passes with the new table: classified tenant, defaulted `tenant_id`, both policies, and the tenant-leading unique key.
- **Mail checks move (`observabilityCheckSystem.test.ts`).** After one run with an overdue mailbox, an errored mailbox (`last_error = 'boom'`) and a healthy one:
  - `tenant_observability_checks` holds `mail:<id>` rows `alerting`, `alerting` and `ok`, each with tenant zero's `tenant_id`;
  - `observability_checks` has no `mail:` row, and none of its rows' `detail::text` contains `boom`;
  - the overdue mailbox produced exactly one `mail_sync_stalled` notification whose `source_table` is `tenant_observability_checks` and whose `source_id` is that row's id.
- **Hysteresis kept (`observabilityCheckSystem.test.ts`).** A second run with the same state writes no second notification, and `changed_at` is unchanged. Recovery flips the row to `ok`.
- **Orphans and legacy rows (`observabilityCheckSystem.test.ts`).**
  - Deleting a mailbox's sync-state row removes its tenant check on the next run.
  - A pre-existing global `observability_checks` row `mail:<uuid>` with a `lastError` detail is deleted by the next run.
- **Global families unchanged (`observabilityCheckSystem.test.ts`).** The existing `process:` and `queue:` cases pass unchanged.
- **Report keeps the user's alerts (`tenantObservabilityChecks.test.ts`).** `alertingChecks` contains an alerting `tenant_observability_checks` row alongside an alerting global row, ordered by `changed_at`, and omits `ok` rows.
- **Two tenants (`tenantObservabilityChecks.test.ts`; tenant B from `createTestTenant(pool)`, checks run over `createRuntimeRolePool(pool, "semprec_data")`, both from #975's `@semprec/data/testSupport`).**
  - A stalled mailbox in tenant B yields an alerting row with B's `tenant_id` and nothing in tenant zero's rows.
  - Inside tenant zero's scope, `getSystemHealthReport` lists none of B's checks.
  - A suspended tenant's mailboxes are not evaluated.
  - A failure injected into B's pass, e.g. a trigger raising on B's insert, still commits tenant zero's checks, and the handler rejects.
