**Model tier:** medium

## Context

Model tier rationale: One matching mechanism rewritten over an existing function with existing fixtures; the care needed is time-zone and daylight-saving correctness, which the calendar time module of #1418 already encapsulates.

The pipeline's match step (step 6, `runMatchStep` in `backend/services/semprec-transcribe/src/transcriptionTask.ts`) calls `matchTranscriptToEvent` in `backend/packages/data/src/transcription/transcriptEventMatch.ts`. Today it is deliberately non-LLM and works on Events that carry a single text `date`: `MATCHABLE_EVENT_TYPES` is `standup` and `meeting` ("a plain event never is"), the `date` must look like a date with a time (`DATE_WITH_TIME_RE`), it is parsed with `Date.parse` in the server's zone, and an Event is a candidate when its start lies in `[recording start - 30 minutes, recording end]`. One candidate gets the Transcripts `event` edge; zero or several create one `kind = transcript` card in Processing proposals with a "create a new Event" envelope. The recording start is `Transcripts.date` (a UTC instant) and its end is that plus the duration from the prepare checkpoint.

That rule matches by start time only, so a meeting that began long before the recording and runs through it is missed, a meeting that ended before the recording but started within 30 minutes of it is matched, and wall-clock values without an offset are read in the wrong zone. Events now store a date, a wall-clock start and end and an optional end date (#1416, migrated by #1797), and an Event may have several transcripts (#1464).

This issue changes the candidate rule to interval overlap in the tenant's time zone. It is the single owner of the pairing rule; the content-based recommendation for ambiguous cases is #1848, and recurring-event occurrences that are not stored as items yet are matched by #1850.

Decisions:

- Overlap is strict: an Event is a candidate when its start is before the recording end and its end is after the recording start. Touching boundaries do not overlap.
- An Event without a `timeTo` is treated as a point at its start: it is a candidate only when that moment falls inside the recording interval.
- The old 30-minute lead is removed; all-day Events (no `timeFrom`) are never matched, nor are Events of type `event`.
- An Event whose stored values do not parse is skipped, not an error (user input must not fail the pipeline).

## Task

Load `testing` and `canonical-keys`.

1. In `transcriptEventMatch.ts` replace `listCandidateEventIds` and the helpers it uses (`MATCH_WINDOW_LEAD_MS`, `DATE_WITH_TIME_RE`, `parseDateWithTime` for Events) with an overlap rule: for each live Event of type `standup` or `meeting` that has `date` and `timeFrom`, its interval is `[date + timeFrom, (endDate ?? date) + timeTo]` interpreted in the tenant's time zone (`getSystemTimezone`, `backend/packages/data/src/systemSettings.ts`), converted to instants with the calendar time module from #1418 (if that module has no wall-clock-to-instant conversion, add one there with tests, DST gap and overlap included). Candidates are ordered by interval start, then id.
2. Keep the outcomes and their contracts: exactly one candidate gets the Transcripts `event` edge (also when that Event already has other transcripts, as #1464 allows); zero or several candidates create the single suggestion card with the existing idempotency key. A transcript that already has an Event edge or card is left untouched. The "create a new Event" envelope of the card must stay valid for the new Events schema: its `date` becomes the recording's date in the tenant's time zone as `YYYY-MM-DD` (the former UTC instant is no longer a valid Events date). Everything else about that envelope (start and end times, project, participants, name) is #1818.
3. Update the JSDoc of `matchTranscriptToEvent` and the comments that describe the old window, and the history line written on the card, so they describe overlap.
4. Update `backend/packages/data/src/transcription/__tests__/transcriptEventMatch.test.ts` and the match step tests in `backend/services/semprec-transcribe/src/transcriptionTask.test.ts` to the new rule, including: a meeting 12:30-14:00 against a recording 13:52-14:39; a meeting 13:25-13:40 against the same recording; type `event`; an all-day Event; an Event with date `2026-10-14`, `timeFrom` 13:30, `timeTo` 14:30 compared in `Europe/Prague` with the recording's UTC time; an overnight Event with `endDate`; an Event without `timeTo`; an unparsable value; two candidates.

## Scope

### In scope

- The interval-overlap candidate rule in the tenant's time zone and its tests.
- Keeping the card's "new Event" envelope valid by giving it a date-only `date`.

### Out of scope

- Recommending one of several candidates from the recording's content: #1848.
- Start and end times, project, participants and the name of a proposed new meeting: #1818.
- Matching occurrences of recurring Events that are not stored as items: #1850.
- Leaving a transcript without any card when nothing overlapped: not built (decided by the product owner; such a recording gets the card proposing a new meeting, which the user can reject).

## Acceptance criteria

- A meeting 12:30-14:00 is a candidate for a recording 13:52-14:39; a meeting 13:25-13:40 is not.
- An Event of type `event` and an all-day Event are never candidates.
- An Event with date `2026-10-14`, `timeFrom` 13:30 and `timeTo` 14:30 overlaps a recording that starts at 11:45 UTC on that day when the tenant's zone is `Europe/Prague`.
- A single candidate that already has another transcript is linked directly, with no card.
- Two candidates create exactly one card, and a second run of the step creates no second card or edge.
