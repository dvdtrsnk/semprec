## Behavior specification (approved)

Part of the multi-tenancy program specified in #950. Admin plane and account lifecycle:

1. `/api/admin/*` requires the admin role, runs in system scope (row-level security shows it no tenant rows) and reads only global tables and content-free aggregates; every admin mutation is written to `admin_audit_log`; there is no impersonation.
2. Admins list accounts (email, role, status, created, last seen), see operational health as counts, set per-tenant AI caps and see per-tenant spend; `/api/system-health` shows a user only their own tenant.
3. Admins create, list and revoke invitations; the link carries the token in the URL fragment, is shown once and is mailed when SMTP is configured; acceptance itself ships with go-live (#961).
4. Admins suspend, reactivate and change roles; the last admin can never be suspended, demoted or deleted; a deactivated tenant's sockets, live sync, Semp conversation and running runs are torn down.
5. A user can export all their data through an authenticated, expiring download.
6. A user (after password re-authentication) or an admin can delete an account — an admin deletes their own account only through the self-service route with re-authentication, never through the admin route: status `deleting`, sessions and push registrations revoked, tenant key shredded, then a chunked purge of every tenant row, partition and file, ending in a PII-free tombstone; a backup restore re-applies recorded deletions.

## Decisions

- **Why does the admin plane run in system scope?** → It then cannot read tenant content by construction, not only by review.
- **Why the token in the fragment?** → Caddy access logs record request URIs.
- **Why a tombstone ledger?** → So that restoring an older backup never resurrects a deleted tenant.

Invitation acceptance (#961); the web pages (#959).
