## Context

Model tier rationale: One guard on the existing relation write path using the configuration from the read-side issue, with a small set of well-defined cases, but it sits on the choke point write path for every relation edge.

A value that is derived cannot also be set by hand. #1595 computes an item's area from its projects and an event's company from its project. This issue makes the write side agree: while an item has a project, writing an own area (or, for events, an own company) is refused, so the derived value never disagrees with a stored one.

Today the choke point accepts those writes. `Files.area`, `Health records.area` and `Events.company` are plain manual relations; #1538 adds `Events.area`. The edge write path is `createRelationWithClient` in `chokePoint/relationOps.ts`, whose shared checks (`loadCreatableRelationEdgeContext`) also run for the dry run of Inbox proposals (`assertRelationCreatableWithClient`), so a guard placed there covers both real writes and proposals. #1991 makes proposal envelopes reject derived relations by reusing the check this issue exports.

Decisions:

- Existing data: manual edges that already exist on items with a project stay in storage and in relation reads, and nothing is deleted or migrated; the derived value is authoritative in `derived` (see the read issue). Decided by the product owner: old manual edges stay, the derived value is read, new ones cannot be created, deleting is allowed.
- Only creating (putting) an edge is refused. Deleting an own edge stays allowed, so a manual value can always be removed.
- The rule applies to every writer, including Semp and system writers.
- "Has a project" means at least one live (not trashed) project edge on the item.
- An event without a project may still have a manual company and a manual area (its own value), as before. Decided by the product owner: without a project there is nothing to derive from, so both stay own values.
- A Journal entry carries an area like any other item (decided by the product owner): while it has a live project (the Journal-to-Projects relation `project` of #1545) an own area is refused; without a project it keeps its manual area.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In `backend/packages/data/src/derived/derivedValueSources.ts` (created by #1595) add the guarded list: `files.area` via `files.projects`, `healthRecords.area` via `healthRecords.projects`, `events.area` via `events.project`, `events.company` via `events.project`, `journal.area` via `journal.project`.
2. Add `backend/packages/data/src/chokePoint/derivedValueGuard.ts` exporting `assertNotDerivedValueWrite(client, { edgeContext, callerItemId, targetItemId })`. A relation definition has two sides; the guard checks both: for each side, if that side's property is on the guarded list and its item has a live project, throw `ValidationError` with `{ field: <the guarded property key> }` (`area` or `company`) and a message that the value is derived from the item's project. The check goes through the database key of the property's database and the property key.
3. Call it from `loadCreatableRelationEdgeContext` in `relationOps.ts` (after the endpoint checks), so `createRelationWithClient` and the proposal dry run share it. Do not call it from `deleteRelationWithClient` or the metadata update.
4. Tests: `relation.put` on `Files.area` for a file with a project is 400 with field `area`; for a file without a project it succeeds; the same for `Health records.area` and `Events.area`; `relation.put` on `Journal.area` for a Journal day with a live project is 400 with field `area`, and for a Journal day without a project it succeeds; `Events.company` for an event with a project is 400 and without one succeeds; writing through the inverse side (for example `Companies.meetings` for an event with a project) is also refused; deleting an existing own edge succeeds; an existing own edge on an item that later gets a project is left in place; a trashed-only project does not count; the Inbox proposal dry run is refused the same way; another tenant's items are not consulted.

## Scope

### In scope

- Refusing creation of own area and own event company edges while the item has a live project, on both edge sides and in the proposal dry run.

### Out of scope

- The derived read: #1595.
- Rejecting derived relations in proposal envelopes up front: #1991.
- Cleaning up, hiding or migrating existing manual edges: decided not to be done (they stay; nothing is migrated).
- Stashing a manual value when an item gets its first project and restoring it when the project is removed: not planned yet; it waits for a product decision.
- Realtime invalidation on project area or company changes: #1710.

## Acceptance criteria

- When `relation.put` on `Files.area` targets a file that has a project, then the response is 400 with field `area` and no edge is written; on a file without a project it succeeds.
- When `relation.put` on `Journal.area` targets a Journal day that has a live project, then the response is 400 with field `area`; on a Journal day without a project it succeeds.
- When `relation.put` on `Events.company` targets an event with a project, then the response is 400; on an event without a project it succeeds.
- When the same edge is put from the inverse side, then it is refused in the same way.
- When an own edge is deleted, then the delete succeeds regardless of projects.
- When an Inbox proposal would write a refused edge, then the proposal check rejects it.
