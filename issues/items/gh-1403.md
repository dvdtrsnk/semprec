## Context

Model tier rationale: This adds a new tenant-scoped table with row-level security and composite tenant keys and a batched read path shared by three operations, so a tenant-isolation hole or a per-row query pattern is easy to introduce and expensive to find later.

A value on an item can be one of three kinds: the user's own, inherited from a source item, or (set up in a later issue) derived. Today nothing records that. `items.properties` holds plain jsonb values, and the values that a matrix of relations would naturally copy (a file's project, a file's company, an event's people) are plain edges in `item_relations` whose `metadata` says nothing about where the edge came from. No read path (`item.get`, `database.query`, `view.query`) can tell a client whether a value was set by a person or taken over from another item, so no client can show "inherited from task Send the invoice".

This issue lays the storage and the read side only. It adds two tenant tables and an additive `links` field on item reads. Nothing writes a link row in production code yet; rows exist only through test fixtures until #1593 (creation and propagation) lands. #1516 makes user and agent writes end a link, #1656 cleans up when a source is deleted, and #1595 adds the derived kind to the same `links` shape. Later inheritance rules (a thread inheriting from its sender, attachments inheriting from a thread or task, and similar) register only their own rules on top of this model.

Decisions:

- A link covers the whole value of one property on one item (the full set of related items for a relation property), never a single related item. This is why the unique key is `(tenant_id, item_id, property_key)`.
- A link is stored beside the value, not in the edge's `metadata`, because its state must survive the edge being replaced or removed.
- No row means the value is the user's own. A row with state `on` reads as `inherited`; state `broken` reads as `inheritedBroken`.
- `links` is opt-in through `include=links`, so existing callers and list queries pay nothing.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Add a migration creating two tables, both classified `COMMENT ON TABLE ... IS 'semprec:tenancy=tenant'`, with `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)`, row-level security enabled, and the `tenant_isolation` (restrictive) and `tenant_rows` (permissive) policies written exactly as in `0078_tenant_exports.sql`. Grant `semprec_side` the same privileges that table has, and make sure the API role can read and write them the way it does `item_relations` (the tenancy catalog test is the check).
   - `value_links`: `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`, `item_id uuid NOT NULL`, `property_key text NOT NULL`, `rule_key text NOT NULL`, `state text NOT NULL DEFAULT 'on' CHECK (state IN ('on', 'broken'))`, `broken_by text CHECK (broken_by IN ('user', 'agent'))`, `broken_at timestamptz`, `updated_at timestamptz NOT NULL DEFAULT now()`. A CHECK ties the columns together: state `on` requires `broken_by` and `broken_at` to be NULL, state `broken` requires both to be set. `UNIQUE (tenant_id, item_id, property_key)` and `UNIQUE (tenant_id, id)` (the target of the composite key below). There is no foreign key to `items` (it is partitioned with a composite key); cleanup is the job of the purge path in #1656.
   - `value_link_sources`: `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`, `link_id uuid NOT NULL`, `source_kind text NOT NULL CHECK (source_kind IN ('item', 'senderDomain'))`, `source_item_id uuid`, `source_property_key text NOT NULL`, `domain text`. A CHECK makes `item` require `source_item_id` and forbid `domain`, and `senderDomain` require `domain` and forbid `source_item_id`. A composite key `(tenant_id, link_id) REFERENCES value_links (tenant_id, id) ON DELETE CASCADE`, the index `(tenant_id, source_item_id)` for "which links hang on this source", and partial unique indexes that stop the same source being listed twice for one link (one per kind). One link may have several sources (a file's company comes from each of its projects). The `senderDomain` kind is created here so #1897 needs no second migration; nothing in this issue writes it.
2. Add `backend/packages/data/src/chokePoint/valueLinksStore.ts` (SQL only, taking a `PoolClient`): insert a link with its sources (used by fixtures and later by #1593), list links by item ids in one query, list sources by link ids in one query, and the row types. Validate rows with the existing row-validation helpers (`dbRowValidation.ts`).
3. Add `backend/packages/data/src/chokePoint/valueLinkReads.ts` with `getValueLinksForItems(client, itemIds)`. It returns, per item id, an object keyed by property key whose entries are:
   `{ valueKind: "inherited" | "inheritedBroken", sources: [{ kind: "item", itemId, databaseKey, title, propertyKey } | { kind: "senderDomain", domain, propertyKey }], brokenBy: "user" | "agent" | null, brokenAt: string | null }`.
   Resolve source titles and `databaseKey` (the database's `owner_module_id`) in batches: one query for links, one for sources, one items lookup for all source ids, one database lookup. It must not query per item or per source. A source whose item cannot be resolved (missing or in the trash) is left out of `sources`; the entry itself is still returned.
4. Expose it through the choke point facade (`chokePoint.ts`) and the data barrel, then wire an `include` list into the three reads:
   - `shared/src/genericOperations/schemas.ts`: an optional `include: z.array(z.enum(["links"]))` on `item.get`, `database.query` and `view.query`. `rows.ts`: an optional `links?` field on `Item`.
   - `genericApplicationService.ts`: when `include` contains `links`, attach `links` to each returned item (an empty object when the item has none); otherwise do not add the field.
   - REST: `GET /api/items/:id?include=links` (the existing `include=path` keeps working; `include` is parsed as a comma-separated list, so `path,links` returns both), and an `include` array in the bodies of `POST /api/databases/:id/query` and `POST /api/views/:id/query`. `adapter/itemEnvelope.ts` and `adapter/itemQueryEnvelope.ts` pass `links` through only when present.
5. Tests, using fixtures that insert link rows directly: an item with one source returns the entry with the source title, `databaseKey` and `propertyKey`; an item with two sources returns both; a broken row returns `inheritedBroken` with `brokenBy` and `brokenAt`; an item without a row has no entry; without `include=links` the field is absent; a query page of N items runs a constant number of queries; another tenant's rows are invisible, including through a source id that belongs to the other tenant.

## Scope

### In scope

- The two tables, their row-level security, and the store and read function over them.
- The additive `links` field on `item.get`, `database.query` and `view.query` behind `include=links`, over REST and MCP (MCP gets it through the shared operation schemas).

### Out of scope

- Writing link rows from product code, and propagating values: #1593.
- Ending a link when a user or Semp writes the value: #1516.
- The `link.unlink` and `link.relink` operations: #1587.
- Removing links when their source is trashed or purged: #1656.
- The `derived` value kind and derived values on reads: #1595.
- Writing `senderDomain` sources: #1897.

## Acceptance criteria

- When a file has a link row for `projects` with one `item` source (task Send the invoice, database key `tasks`, property key `project`), then `GET /api/items/:id?include=links` returns `links.projects` with `valueKind: "inherited"` and that source including its title.
- When the link has two sources, both are returned.
- When the row's state is `broken`, the entry reads `inheritedBroken` with `brokenBy` and `brokenAt` set.
- When an item has no row for a property, `links` has no entry for it; when `include` is not given, the item has no `links` field at all.
- When `database.query` or `view.query` is called with `include: ["links"]` for a page of items, each item carries its own `links`, and the number of SQL statements does not grow with the page size.
- The same `include` works through MCP `item.get`, `database.query` and `view.query`.
- Rows of another tenant are never returned, and the tenancy catalog test and the tenant export and purge tests pass with the two new tables.
