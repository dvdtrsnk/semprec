## Context

Model tier rationale: The provenance fields are specified, but they must be threaded through several layers without letting any non-REST writer set them.

An `mcpServers` item whose `connectionConfig` has `transport: "stdio"` names a host `command`, `args` and `env` (`backend/packages/data/src/mcp/mcpConnectionConfig.ts:11-25`). The connection factory spawns it as a child of `semprec-api` or `semprec-agents` (`backend/packages/data/src/mcp/mcpConnectionFactory.ts:177-203`).

`connectionConfig` is an `owner: "user"` property (`backend/packages/data/src/seed/seedMcpModule.ts:84`). Any writer can therefore store a host command:
- a REST user;
- an external MCP client over `/mcp`;
- an agent through the `item_create` and `item_patch` AgentTools;
- a Semp proposal: `assertValidMcpServerProposalProperties` accepts `stdio` (`backend/packages/data/src/mcp/mcpServerProposal.ts:92-105`, and the test at `backend/packages/data/src/__tests__/mcpServerProposal.test.ts:102`).

With several users this is remote code execution on the host for anyone, and for any model that can be prompted.

Approved rule: `stdio` is allowed only in an admin's tenant, and only when a human configured it, never an agent. Proposals are model-authored and `/mcp` clients are AI clients, so both count as agents. Everyone else uses remote MCP over `https`.

#1029 added:
- `registerItemCreateHook` beside the update registry in `backend/packages/data/src/chokePoint/hooks.ts`;
- `mcpServerItemCreateHook` and `mcpServerItemUpdateHook` in `backend/packages/data/src/mcp/mcpServerWriteHook.ts`, which call `assertStorableMcpConnectionConfig` on every write path, proposal confirm included.

What the hook cannot see yet is who wrote:
- `createItem` and `patchItem` forward only `actor.userId` (`backend/packages/application/src/genericApplicationService.ts:261-279`), and hook contexts carry no writer;
- `AuthenticatedActor` (`backend/packages/shared/src/genericOperations/actor.ts:9-13`) cannot tell a REST human from an `/mcp` session client: both are `{ userId }`;
- `restActor` (`backend/services/semprec-api/src/adapter/genericBinding.ts:70-72`) is the only place that builds the REST human actor.

Since #968, `users` has `role ∈ admin|member` and `tenant_id`, and `createUser` accepts `{ tenantId, role }`. `app_tenant_default()` is the current tenant, falling back to the sole tenant until #1067. #1033 reuses this issue's policy helper to re-check at spawn.

## Task

Load `state-writes` (the check runs inside the write's transaction), `error-handling` and `adr-conventions`.

1. **Writer provenance.**
   - `AuthenticatedActor` gains `restSession?: true`. Only `restActor` sets it; the MCP and AgentTool composition roots never do, and no input schema accepts it.
   - `createItem` and `patchItem` in `genericApplicationService.ts` pass `humanWriterUserId: actor.userId` to the choke point only when `actor.restSession === true && actor.agentProjectItemId === undefined`.
   - In `backend/packages/data/src/chokePoint/itemWrites.ts`, `createItemWriteOps().createItem/updateItem` (`:389-399`) take it as an optional third argument. `CreateItemWithClientOptions` and `UpdateItemWithClientOptions` (`:131-136`, `:228-240`) gain `humanWriterUserId?: string`; every internal caller leaves it unset.
   - `ItemCreateHookContext` and `ItemUpdateHookContext` (`hooks.ts`) gain `humanWriterUserId?: string`, filled from those options.
2. **Policy helper.** New `backend/packages/data/src/mcp/stdioTransportPolicy.ts` exports `tenantAllowsStdio(client: Queryable, userId?: string): Promise<boolean>`, which runs
   `SELECT EXISTS (SELECT 1 FROM users WHERE role = 'admin' AND tenant_id = app_tenant_default() AND ($1::uuid IS NULL OR id = $1))`.
3. **Hook rule.** In both MCP server hooks, after `assertStorableMcpConnectionConfig`: a `stdio` config requires `humanWriterUserId` to be set and `tenantAllowsStdio(client, humanWriterUserId)` to be true. Otherwise throw `ValidationError` with `{ field: "connectionConfig" }`, with one message that does not say whether the writer was an agent, an `/mcp` client or a non-admin.
4. **Proposals.** `assertValidMcpServerProposalProperties` rejects `transport: "stdio"` with `{ field: "connectionConfig" }` before its other checks, so a model-authored host command never becomes a card. At confirm, the stored envelope is refused again by the same proposal validation, which `assertValidEnvelopeForCard` re-runs before `createItemWithClient` (`proposalActions.ts:150`, `:264`, `:276`); the create hook is a backstop this path does not reach.
   - Keep `assertNoCredentialShapedEnvKeys` (`mcpServerProposal.ts:41-53`): it checks `env` whatever the transport, and the non-strict `sse`/`http` schemas drop an unknown `env` key instead of rejecting it, so it still guards remote configs. Move its env-key cases (`mcpServerProposal.test.ts:128-152`) to an `http` config).
   - The case at `:102` now expects rejection.
5. **ADR.** Add `docs/adr/<YYYY-MM-DD>-stdio-mcp-confined-to-admin-tenants.md`. It records:
   - the rule, and that `/mcp` clients and proposals count as agents;
   - `restSession` and `humanWriterUserId` as the writer provenance, an extension of `[[2026-09-30-choke-point-domain-hooks-through-a-per-process-registry]]` (standalone);
   - the proposal ban;
   - that #1033 re-checks at spawn and #1070 sandboxes the child.
6. **Fixtures.** A fixture that writes a `stdio` config through the choke point must use a REST writer bound to the sole tenant with `role: "admin"`, or, where no REST writer is reachable, pass the sole tenant's admin as `humanWriterUserId` to `createItemWithClient`: `createGrantedTool` in `backend/packages/data/src/__tests__/approvalRequestExecution.test.ts:52-58` does the latter. Fixtures using `itemsStore.insertItem` or a raw insert (`mcpInvokeTool.test.ts`, per #1029) are unaffected.

## Acceptance criteria

- **Admin human allowed.** A REST `POST /api/databases/<mcpServers>/items` with a `stdio` config, by a user bound to the sole tenant with `role = 'admin'`, succeeds. (integration, `mcpServerStdioWrites.test.ts`)
- **Everyone else refused.** Each of these gets 400 `validation_failed` with `details.field = "connectionConfig"` and an identical message, and no row is written or changed:
  - the same REST write after the user's `role` is set to `member`;
  - a REST `PATCH` switching an `https` server to `stdio` by a member;
  - `item.create` through `createGenericOperationGateway().invoke` with an agent actor (`runId` and `agentProjectItemId` set);
  - `semprec.item.create` over `/mcp` with the admin's own session bearer.

  (integration, `mcpServerStdioWrites.test.ts`)
- **Proposals.** A proposal envelope with a `stdio` config is rejected at proposal validation (integration, `mcpServerProposal.test.ts`). An admin confirming a stored `stdio` envelope is refused by the re-run proposal validation (integration, `mcpServerWriteHook.test.ts`).
- **Policy helper.** `tenantAllowsStdio` is true for an admin bound to the current tenant, false for a member, false for an admin of no tenant, and, without a user id, true exactly when the tenant has an admin user. (integration, `stdioTransportPolicy.test.ts`)
- **Remote unaffected.** Remote (`https`) configs are accepted from every writer, as in #1029. (integration, `mcpServerStdioWrites.test.ts`)
