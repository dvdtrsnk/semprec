**Blocked by:** #1713, #1786
**Model tier:** medium

## Context

Model tier rationale: This adds one more trigger and payload to an already existing deferral mechanism across known gateway, snapshot and store seams with existing fixtures, so it is medium.

A value link records that a target item's value (for example a file's project) is inherited from a source item (for example the task the file belongs to). #1516 makes a user or agent write that changes such a value break the link (the link goes from on to broken and records who broke it). Without this issue an agent could end such a link silently, the file would stop following the task's project and nobody would be told.

#1713 provides the generic mechanism: inside the write transaction the choke point flags an agent write, throws `ApprovalRequiredForWrite`, the gateway turns it into an approval request with a resource snapshot, and the approved write is revalidated and replayed exactly once; `item_patch`, `relation_put` and `relation_set` are already snapshot kinds, but nothing triggers it yet: a plain `relation.set` that replaces an edge is an ordinary non-destructive write with the `write` risk class and needs no approval (decided by the product owner). #1587 adds `link.unlink`, which also ends a link. This issue adds the first trigger: an agent write that would break a value link.

Decision: only agent writers with a run (`agentRunId`, #1415) are deferred; a user write that breaks a link stays immediate (as #1516 defines), and so does an `/mcp` call with a human session, which #1415 records as an agent write without a run (the link still records `broken_by` agent). A write by an agent to a property that has no active link stays immediate, including a `relation.set` that replaces an edge of such a property. `relation.delete` already requires approval; only its payload gains the same link information.

Decision (product owner): the request text describes the operation that really runs, so the approval is not misleading. For a file whose project follows a task, it names the write of the file's project relation to the new project, not a generic "change the file's project".

Decision (product owner): no separate detail route. The approval detail view reads one request with the existing `GET /api/approval-requests/:id` (#1786), so the link information is returned there too.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In the choke point write path from #1516, when the writer is an agent with an `agentRunId` and the write would turn an active value link into a broken one, add a reason `{ kind: "breaksLinks", links: [...] }` to the `ApprovalRequiredForWrite` of #1713. This applies to `item.patch`, `relation.put`, `relation.set` and `link.unlink`; for `relation.delete` the existing approval gets the same payload instead of a new trigger.
2. Request payload: `breaksLinks: [{ itemId, itemName, propertyKey, sourceItemId, sourceItemName, sourceDatabaseKey, newValueName }]` and, where the broken link was feeding inheritance of further values, `endsInheritance: [{ itemId, propertyKey, sourceName }]`. `propertyKey` is the canonical English camelCase key. The two lists are additive fields on the request view returned by the list `GET /api/approval-requests` and by the single-request read `GET /api/approval-requests/:id` (#1786); no new route.
3. Description: render the localisable template `approval.breaksLink` of the description mechanism (#1683) with params `{ itemName, databaseKey, propertyName, sourceItemName, sourceDatabaseKey, newValueName }`, and set the risk class `breaksLink` and the risk level from #1423 and #1730. The template text names the write that really runs: setting the property `propertyName` of `itemName` to `newValueName` (for a relation property, writing that relation), then which link ends and what the item stops following; it never describes the write as a generic change of the item. Add the template to the i18n catalogs for both locales.
4. Snapshot: for these requests the resource snapshot hash covers the affected value links (their state and source) and the current value of the property, replacing `ifVersion`.
5. Replay: before executing, revalidate the snapshot. If the source was deleted, the user already removed the link, or the value differs, the approval is invalidated and terminalizes as a conflict with nothing written. On a valid replay the write executes exactly once and the link is marked broken with `broken_by` = agent.
6. Tests: an agent changing a file's project while linked to a task creates a request with `breaksLinks` naming the source task and leaves the file and link unchanged; approval executes once and the link is broken by the agent; the user unlinking in between invalidates the approval; an agent write to a property without a link executes immediately; `relation.set` onto an empty relation, and `relation.set` replacing an edge of a relation without an active link, are immediate while replacing a different edge on a linked relation defers; the same write through `/mcp` with a human session is immediate and breaks the link with `broken_by` agent; the rendered description of the file case names the write of the file's project relation and the task it stops following; `GET /api/approval-requests/:id` returns `breaksLinks`; rejection leaves value and link unchanged.

## Scope

### In scope

- The value-link-break trigger for agent writes and the link payload, description, risk class and snapshot of those requests.
- Revalidation and `broken_by` agent on approved replay.

### Out of scope

- The generic deferral mechanism, the typed error, the snapshot kinds and the narrowing ADR: #1713.
- How links are stored and broken by users: #1516; `link.unlink` and `link.relink` themselves: #1587.
- Showing the broken link and a "take over again" action in the item detail.
- A separate detail route for approval requests: not added (decided by the product owner); the single-request read is #1786.

## Acceptance criteria

- When an agent changes a property that has an active value link, then an approval request with `breaksLinks` (source item name included) is created, the property is unchanged and no partial write remains.
- When the request is approved, then the write executes exactly once and the link is broken with `broken_by` agent.
- When the user removed the link, or the source was deleted, before approval, then the approval is not executed and ends as a conflict.
- When an agent writes a property without a link, `relation.set` onto an empty relation, or `relation.set` replacing an edge of a relation without an active link, then it executes immediately.
- When the request is for an agent changing a file's project that follows a task, then its description names the write of the file's project relation to the new project and the task the file stops following.
- When the request is read with `GET /api/approval-requests/:id`, then it carries the same `breaksLinks` and `endsInheritance` as the list.
- When the request is rejected, then the value and the link are unchanged.
- When a user, or an `/mcp` call with a human session, performs the same write, then it executes immediately.
