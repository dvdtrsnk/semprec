**Blocked by:** #275, #22

## Context

Three lower-severity findings from the post-merge reviews of #21's and #22's pull requests were never addressed and are still on `develop`. All three are read/write-consistency cleanups outside the choke-point's item path, which #275 covers.

**1. `reorderViewItem` skips the view-level lock that `addViewItem` takes.** In `backend/packages/data/src/chokePoint/viewItemsStore.ts`, `addViewItem` opens with `SELECT id FROM views WHERE id = $1 FOR UPDATE` and an explicit comment: without it, two concurrent calls can read the same `MAX(position)` (or match the same `position >= $2` shift) and tie on a position, and there is no `UNIQUE (view_id, position)` constraint to catch that. `reorderViewItem` performs the same kind of position shifting but takes only a row-level `FOR UPDATE` on the moved item, so two concurrent reorders on one view — reachable directly through `chokePoint.reorderViewItem` — can produce tied positions and a non-deterministic `ORDER BY position`.

**2. `queryFilteredView` re-parses an already-parsed filter.** In `backend/packages/data/src/views/viewQuery.ts`, the `buildFilterSql` hook calls `compileFilterNode(parseFilterNode(config.filter), ...)`, but `config.filter` is typed `FilterNode | undefined` because `parseViewConfig` already validated it when the config was loaded. The re-parse is redundant work on every `queryView` call.

**3. The drift check reads the manifest outside its own transaction.** In `backend/packages/data/src/manifest/driftCheck.ts`, `createDriftCheckAction` takes a separate `readClient` from the pool for `generatePermissionManifest`, releases it, and only then opens the transaction that runs the orphan check and writes the notification. If the schema changes between the two reads, the manifest and the orphan check describe different schema states.

## Task

- **`viewItemsStore.ts`** — take the same view-level lock in `reorderViewItem` that `addViewItem` takes, as its first statement (`SELECT id FROM views WHERE id = $1 FOR UPDATE`), before the current `SELECT position ... FOR UPDATE` on the moved row. Carry over the explanatory comment so the two functions read the same way.
- **`viewQuery.ts`** — drop the redundant `parseFilterNode` call and pass the already-validated `config.filter` straight to `compileFilterNode`. Note that `ViewConfig.filter` is typed `FilterNode | undefined` and the current ternary narrows on `filterProperties`, not on the filter, so simply deleting the call does not type-check: hoist `const filterNode = config.filter;` above and build both `filterProperties` and the `buildFilterSql` hook off that one narrowed binding. Behavior is unchanged — `filterProperties` is computed exactly when `config.filter` is present.
- **`driftCheck.ts`** — run `generatePermissionManifest` inside the same `withTransaction` that performs the orphan check and writes the notification, using that transaction's client, and drop the separate `readClient` checkout/release. The manifest result is still discarded (its text comparator does not exist yet); the point is that both reads see one schema snapshot.

Add tests:

- in `backend/packages/data/src/__tests__/views.test.ts`, a concurrency test asserting that two concurrent `chokePoint.reorderViewItem` calls on the same view leave every position distinct. There is no concurrency test in that file to copy — `addViewItem`'s lock landed without one — so follow the concurrency-test pattern used in `backend/packages/data/src/__tests__/docs.test.ts` and `mailSend.test.ts` (drive both calls in parallel against the real pool and assert on the resulting rows). Two racing reorders do not tie deterministically, so run enough parallel pairs that an unlocked implementation reliably produces a duplicate position, and say in a comment why the loop is there;
- keep the existing drift-check and view-query tests passing — no new test is required for the redundant-parse removal, which is behavior-preserving by construction.

## Scope

### In scope

- The view-level lock in `reorderViewItem`, the redundant parse removal in `viewQuery.ts`, the single-transaction drift check, and the concurrency test above.

### Out of scope

- The choke-point item and relation-property paths — those are #275.
- Adding a `UNIQUE (view_id, position)` constraint or otherwise changing the view-items schema: the lock is what the existing design relies on, and a migration is not part of this finding.
- Implementing the manifest text comparator, which is a later issue's work.

## Acceptance criteria

- Two concurrent reorders on the same view no longer produce two view items sharing a position.
- `queryFilteredView` compiles the filter without re-parsing it, and the existing view-query tests still pass unchanged.
- `createDriftCheckAction` generates the manifest and runs the orphan check against one transaction, with no separate pool checkout — there is no test harness for this one, so it is verified by inspection: point at the changed lines in the pull request description.
