## Context

Model tier rationale: Two new nullable columns are a persisted-data contract that crosses the migration, the store, the shared input schemas, the application service and the REST envelope, which is more than the mechanical low tier even though each step follows an existing pattern.

A user-created collection ("Gift ideas") should look like the built-in ones: it has an icon and a color, picked when it is created or changed later, and a new collection without a pick shows the app's default (an orange database icon). Today the `databases` table (`backend/packages/data/src/db/migrations/0001_*.sql`) has no `icon` or `color` column, `DatabaseCreateInputSchema` accepts only `name` and `parentItemId`, and `DatabasePatchInputSchema` accepts only `name` (`backend/packages/shared/src/genericOperations/schemas.ts`). `database.patch` ends in `renameDatabase` (`backend/packages/data/src/chokePoint/databaseOps.ts` and `databasesStore.ts`), and `PATCH /api/databases/:id` forwards only `name` (`backend/services/semprec-api/src/databasesHandler.ts`).

#1407 declares icon and color for system databases in the module manifests and adds `icon` and `color` to the database envelope (null for a user-created database, because no column existed). This issue stores them for user-created databases, makes `database.create` and `database.patch` accept them, and fills the default at read time. The one-call creation of a collection with its properties, #1592, builds on the create input extended here.

Decision: the defaults (icon `database`, color `#FF9500`) are applied when reading and are never written; a row without a pick stays `NULL` so a later change of the default needs no data migration.

Decision: icon and color of a system database stay owned by its module manifest. A patch that sets either on a system database is rejected with a forbidden error, and the columns of system databases remain `NULL`. Renaming a system database keeps working as today.

Decision: a patch may set `icon` or `color` to `null` to return to the default.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Add a migration adding nullable `databases.icon text` and `databases.color text`, with CHECK constraints: `color` matches `^#[0-9A-F]{6}$` and `icon` matches `^[a-z][a-z0-9-]{0,63}$` (both allowing `NULL`). Existing rows keep `NULL`. Confirm the runtime database role can write the new columns under the existing least-privilege role setup.
2. Add `icon` and `color` (nullable strings) to the `Database` type in `backend/packages/shared/src/genericOperations/rows.ts` and to `DatabaseRow`, `DatabaseDbRow`, `mapDatabaseRow` and `DATABASE_COLUMNS` in the data package.
3. Extend `DatabaseCreateInputSchema` with optional `icon` and `color`, and `DatabasePatchInputSchema.patch` with optional nullable `icon` and `color` (same formats as the constraints; hex color is normalized to upper case before it is stored). Patch keeps rejecting an empty patch and unknown keys.
4. Persist them: `createDatabase` in `databasesStore.ts` writes them for non-system databases; replace the name-only patch path (`renameDatabase`) by a patch that updates any of `name`, `icon`, `color` in one statement and still emits the schema invalidation (`notifyInvalidation({ scope: "schema", ... })`). Keep `renameDatabase` as a thin caller if other code uses it. Setting `icon` or `color` on a system database throws the existing forbidden error type.
5. Update `createDatabase` and `patchDatabase` in `backend/packages/application/src/genericApplicationService.ts` to pass the new fields through, and the `POST` and `PATCH /api/databases` routes in `databasesHandler.ts` to forward `icon` and `color` from the body.
6. Resolve the appearance in the collection metadata resolver added by #1407 (`backend/packages/data/src/manifest/collectionMetadata.ts`): for a user-created database, `icon` is the stored value or `"database"` and `color` the stored value or `"#FF9500"`; for a system database the manifest value is unchanged. Export the two default constants.
7. Tests: store tests for create, patch and reset-to-null; schema tests for rejected formats (`"red"`, `"#12345"`, an icon with spaces); a system-database patch of `color` is rejected while a rename succeeds; handler tests for the acceptance criteria; the migration test pattern used by the existing migration tests (columns exist, constraint rejects a bad value).

## Scope

### In scope

- The two columns, their input validation, their persistence on create and patch, and the read-time defaults in the envelope.

### Out of scope

- Declaring icon and color of system databases: #1407.
- Creating a collection together with its properties in one call: #1592.
- Renaming, deleting and adding properties to user-created collections from the app: they already exist as separate operations and are not changed here.
- An allowed-icon vocabulary: the backend validates only the format; the clients own which names they can render.

## Acceptance criteria

- `POST /api/databases` with `{ "name": "Gift ideas", "icon": "gift", "color": "#34c759" }` returns the database with `icon: "gift"` and `color: "#34C759"`.
- `POST /api/databases` with only a name returns `icon: "database"` and `color: "#FF9500"`, and the table row has `NULL` in both columns.
- `PATCH /api/databases/:id` with `{ "color": "#007AFF" }` changes only the color; with `{ "icon": null }` the icon returns to `"database"`.
- A color that is not `#RRGGBB` or an icon that is not lower-case kebab-case is rejected with a validation error (HTTP 400).
- `PATCH` of `icon` or `color` on a system database returns 403, while `PATCH` of its `name` keeps working, and its envelope still carries the manifest icon and color.
- A schema invalidation is published after an icon or color change.
