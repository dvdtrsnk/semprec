**Blocked by:** #1987
**Model tier:** medium

## Context

Model tier rationale: One extra, bounded section in the computation context built from an existing read, with clear exclusion rules and no new persisted data.

When someone captures "call with Petr on Thursday at two", the proposal should suggest a sensible end time. The best signal is how long the user's earlier events with the same people lasted. The proposal computation (#1434) receives a bounded workspace context from #1987 (active projects, areas, people, companies and events around the mentioned time, each with ids and a per-kind limit). That context has no durations.

Events get an end time of day (`timeTo`) next to `timeFrom`, an optional `endDate` for events that end on another day, and a `place` once #1416 lands. Until an event has both `timeFrom` and `timeTo` its length is unknown. Events link to People through the user-owned `people` relation.

Decision: durations are added only when the proposal's target is the Events database, to keep the model request small for every other kind.

Decision: only same-day events with both times set count. An event with an `endDate`, a missing time, an all-day event or a non-positive length is skipped, so a multi-day trip never skews the suggestion.

Decision: the context carries, for each person already in the context's People list, up to the five most recent such events as `{ eventId, minutes, startDate }` plus no event names, to keep the section small and free of free text.

## Task

Load `canonical-keys` and `testing`.

1. In the context builder introduced by #1987 (in `backend/services/semprec-api/src/`), add a `pastEventDurations` section: a map from person item id to an array of at most five `{ eventId, minutes, startDate }` entries, newest first.
2. Add a read function in `backend/packages/data/src/` (for example `inbox/pastEventDurations.ts`) that, for a list of person ids, lists live Events linked to them through `people` that satisfy the Decision above, ordered by `date` descending, using one query for all people, not one per person. It reads only.
3. Include the section only when the target database is Events; cap the section so the request body stays under the gateway limit already enforced by the context builder.
4. Mention the section in the model instructions so a suggested `timeTo` follows the person's usual length when a mention fits; the model remains free to ignore it.
5. Tests: durations are computed from `timeFrom` and `timeTo`; events with `endDate`, without times, with zero or negative length, or trashed are skipped; at most five per person, newest first; the section is absent for a non-Events target; a stubbed gateway receives the section for a call with a known person.

## Scope

### In scope

- The durations read, its place in the bounded context and the model instruction.

### Out of scope

- The Events schema (#1416), the context builder itself and its limits (#1987).
- Writing a default end time on the server when the model omits one.
- Reminder or travel values of Events (#1714).

## Acceptance criteria

- When a proposal for an Events item is computed and the context contains Petr, then the gateway request carries the lengths in minutes of Petr's last same-day events, newest first, at most five.
- When an earlier event has an `endDate` or no `timeTo`, then it does not appear in the section.
- When the target is not Events, then the section is not in the request.
- The request body stays within the existing size bound.
