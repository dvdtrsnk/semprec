## Context

Model tier rationale: A new write route that locks a proposal, merges user values into a server-composed envelope, enforces optimistic concurrency and must never accept an MCP credential, so it carries authorization, concurrency and persisted-state contracts.

The inbox card lets the user edit every field of the proposal by hand (text, Markdown, date, time, single and multi select, multi-value chips, toggle, segment, color, list pick), including the fields of secondary steps, and marks an edited field. Today there is no way to do that: `proposal`, `status` and `history` are system-owned on Processing proposals (seeded in `backend/packages/data/src/seed/seedInboxPipeline.ts`), so the generic `PATCH /api/items/:id` rejects them with `ForbiddenError` (`assertWritableProperties` in `backend/packages/data/src/chokePoint/itemWrites.ts`), and that stays. The only user-facing proposal routes are `POST /api/proposals/:id/confirm` (`createConfirmProposalRouteHandler` in `backend/packages/data/src/inbox/inboxRouteHandlers.ts`, registered as a custom route with justification `transactional-semantics` in `backend/packages/data/src/inbox/inboxModuleManifest.ts`) and the revise route mounted by #1870.

This issue adds `PATCH /api/proposals/:id/values`. It builds on #1471 (the proposal keeps the assistant's last output in `aiProposal`; legacy rows without it are read as `aiProposal = proposal`), on #1430 (history entries carry `kind` and `keys`) and on the revise route from #1870 (route mounting and optional-message conventions). Card-state properties `aiProposal`, `userOverrides`, `userEditedKeys` and `aiVersion` exist from #1451.

Product behavior: the request body is `{ set: { [ref]: { [key]: value } }, ifVersion? }`. `ref` addresses a step of the card; a single-step envelope has the single ref `primary`. The stored `proposal` stays the effective envelope (assistant output plus overrides) composed by the server, so confirm and existing clients need no change. An edited field is one whose value differs from the assistant's value: its `ref.key` is in `userEditedKeys`, and it drops out again when the user sets the value back to the assistant's. Excluding keys of fields that the card's editor schema hides is added later by #1928; until then every edited key is counted.

Decision: validation follows confirm (`assertValidEnvelopeForCard`); required-field checks are not part of this issue (they are warnings on edit and an error on confirm, both added by #1928). Decision: allowed card statuses are `proposed`, `needsClarification` after a type is chosen, and `invalid` unless its `invalidReason.code` is `sourceDeleted` (such a card can only be discarded, see #1482); a successful edit of a fixable `invalid` card moves it back to `proposed` and clears `invalidReason`. Locked cards (`confirmed`, `rejected`) are refused with the same `ValidationError` as revise. Decision: `ifVersion` is the card's `updatedAt`, as on the generic PATCH; a mismatch is a 409 `version_conflict` whose `details.currentItem` is the current card (raise `ConflictError` with `{ current }`, which `adapter/errorContract.ts` projects).

Shared-file ordering: this issue also waits for #1889 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

2. Add `updateProposalValuesWithClient(client, config, proposalId, input)` in `backend/packages/data/src/inbox/proposalActions.ts`: lock the proposal (`lockLiveProposal`), check status and `ifVersion`, merge `set` into `userOverrides`, recompute `userEditedKeys` (a `ref.key` is edited iff its override differs from the same key in `readAiProposal`; setting back to the assistant's value removes the override), compose the effective envelope = assistant envelope with overrides applied per ref, validate it with `assertValidEnvelopeForCard`, and write `proposal`, `userOverrides`, `userEditedKeys`, `status` (`proposed`) and a `history` entry with `kind: "userEdit"` and `keys` in one `updateItemWithClient` call with the needed `allowedSystemKeys`. Never accept a credential: for an `mcpServers` target the composed envelope must pass `assertValidMcpServerProposalProperties`, so a credential key in `set` is a `ValidationError`.
4. Return the updated card (the route's response is the card envelope, as for confirm).
5. Add the route handler `createUpdateProposalValuesRouteHandler(pool)` in `backend/packages/data/src/inbox/inboxRouteHandlers.ts`, in one `withTransaction`, validating the body (`set` an object of objects, `ifVersion` an optional string) with `ValidationError`. Register it in the Inbox module manifest as `PATCH /api/proposals/:id/values` with justification `transactional-semantics` (lock, merge and history in one transaction) and export the handler from `inboxModuleManifest.ts`.
6. Add a route matrix entry in `backend/services/semprec-api/src/routeMatrix.ts` and a cross-tenant case in `backend/services/semprec-api/src/__tests__/tenantIsolationRoutes.test.ts`, following the `confirm proposal` entries.

## Scope

### In scope

- `PATCH /api/proposals/:id/values` with `set` and `ifVersion` for field values of existing steps, edited-key tracking, history entry and 409 handling.

### Out of scope

- Relations and step enable/disable in the body (#1920).
- Clearing all overrides (#1912).
- Protecting overrides when the assistant recomputes (#1921) and clearing them on a target change (#1924).
- Accepting editor-schema pseudo fields such as an all-day switch in `set`, required-field warnings and excluding hidden fields from the edited count (#1928), hidden-field normalization on confirm (#1934) and the editor schema itself (#1825).
- Idempotency keys for this route (#1894).

## Acceptance criteria

- When `PATCH values` sends `{ set: { primary: { title: "Poslat fakturu Alze" } } }` on a `proposed` card, then the stored `proposal` carries that title, `userEditedKeys` is `["primary.title"]` and the history gains an entry with `kind: "userEdit"` and `keys: ["primary.title"]`.
- When the title is set back to the assistant's value, then `userEditedKeys` no longer contains it.
- When the generic `PATCH /api/items/:id` targets `proposal`, then it still returns 403.
- When `ifVersion` is older than the card's `updatedAt`, then the response is 409 `version_conflict` with the current card in `details.currentItem` and nothing is written.
- When the card is `confirmed` or `rejected`, then the request fails with a validation error and nothing is written.
- When the target is an MCP server database and `set` contains a credential key, then the request fails with a validation error.
- When an unknown ref or key is sent, then the request fails with a validation error naming it.
- When a `needsClarification` card with a chosen type or a fixable `invalid` card is edited successfully, then its status becomes `proposed` and `invalidReason` is cleared.
- When an `invalid` card whose `invalidReason.code` is `sourceDeleted` is edited, then the request fails with a validation error and nothing is written.
- When another tenant's proposal id is used, then the route answers as for an unknown id.
