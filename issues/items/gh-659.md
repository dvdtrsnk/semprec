## Context

`docs/adr/2026-09-24-choke-point-composed-from-domain-modules.md` splits the generic choke point into per-domain modules and forbids those modules from importing one another (`no-choke-point-domain-cross-import`), but nothing stops a choke-point module from importing a *domain folder*, and two do:

- `backend/packages/data/src/chokePoint/itemWrites.ts` line 30 imports `recordDesiredMailMessageFlags` from `../mail/mailMessageFlagSyncStore.js` (and line 29 `EMAILS_MODULE_ID` from `../seed/emailModuleKeys.js`) and calls it in `updateItemWithClient` at lines 276-278, guarded by `database.ownerModuleId === EMAILS_MODULE_ID`, so a patch to an Email item records the desired IMAP flag state in the same transaction.
- `chokePoint/relationOps.ts` line 26 imports `assertSpeakerEdgeWritable` and `isTranscriptSpeakersProperty` from `../transcription/transcriptionSpeakerEdges.js`; `assertRelationEdgeMetadataValid` (lines 90-104) calls them, and is itself called at lines 118, 136 and 164 (create-check, create, metadata update), so a Transcript `speakers` edge is validated before it is written.

Both are the right *behaviour* (the write and its domain side effect share one transaction, per `docs/adr/2026-09-10-side-effects-follow-the-commit.md`), but the generic write path now knows two domains by name, and every further domain wanting the same will add another import. No import-boundary rule catches it. About sixty call sites in every domain call `createItemWithClient` / `updateItemWithClient` / `createRelationWithClient` directly with a client (mail sync, inbox, docs, library, tasks, transcription…), so the hook set cannot be threaded through `ChokePointDeps`/`createChokePoint` — it has to be a per-process registry, the pattern `docs/adr/2026-09-12-per-process-agent-run-watch-registry.md` and `docs/adr/2026-09-12-per-process-doc-sync-subscription-registry.md` already use. This is a new cross-cutting mechanism and needs its own ADR in the same pull request (`backend/review-rules/rules.md`: a new pattern without an ADR is a finding).

The data-integrity batch has an issue that adds a task-recurrence call to `updateItemWithClient` in the same `itemWrites.ts` (advance the recurrence when a Tasks item reaches its done status), explicitly keeping it "a single hook point" for this issue to move. Depends on #653, which edits `dependency-cruiser.rules.json` and `module-boundaries.unit.test.ts` first.

## Task

- New `backend/packages/data/src/chokePoint/hooks.ts` (a shared module in the sense of the choke-point ADR — no domain module owns it):
  ```ts
  export interface ItemUpdateHookContext {
    client: PoolClient;
    database: DatabaseRow;
    item: ItemRow;               // the row as written by updateItem
    propertiesPatch: Record<string, unknown>;
  }
  export type ItemUpdateHook = (context: ItemUpdateHookContext) => Promise<void>;
  export interface RelationEdgeWriteHookContext {
    client: PoolClient;
    edgeContext: RelationEdgeContext;   // from ./relationEdgeContext.js
    callerItemId: string;
    targetItemId: string;
    metadata?: Record<string, unknown>;
  }
  export type RelationEdgeWriteHook = (context: RelationEdgeWriteHookContext) => Promise<void>;
  export function registerItemUpdateHook(hook: ItemUpdateHook): void;
  export function registerRelationEdgeWriteHook(hook: RelationEdgeWriteHook): void;
  export async function runItemUpdateHooks(context: ItemUpdateHookContext): Promise<void>;
  export async function runRelationEdgeWriteHooks(context: RelationEdgeWriteHookContext): Promise<void>;
  ```
  Each registry is a module-level `Set` (registering the same function twice is a no-op); `run*` awaits hooks sequentially in registration order and lets the first rejection propagate (it is inside the caller's transaction, so the write rolls back exactly as the direct call did).

If the data-integrity task-recurrence change has merged by then and `updateItemWithClient` also calls a `tasks/` function keyed on `database.ownerModuleId === TASKS_MODULE_ID` and the done-status transition, move that call behind the same hook in exactly the same way (a `tasks/` hook module registered in `domainWriteHooks.ts` below, receiving the same context; it needs the pre-update row, so extend `ItemUpdateHookContext` with `previous: ItemRow | null` only if that call actually needs it, loading it once in `updateItemWithClient`). If it has not merged, leave nothing for it: `runItemUpdateHooks` is the single hook point that issue was told to use. The existing `TASKS_MODULE_ID` / `deriveTaskTime` derivation at lines 246-266 stays a direct import (derived system property, `docs/adr/2026-09-19-derived-system-properties-computed-inline-at-choke-point.md`).

## Scope

### In scope

- The two registries, the two hook implementations, the composition file, the boundary rule with its fixtures, the ADR, and the tests that prove the hooks still fire and the rule fires.

### Out of scope

- Moving `scheduler/`, `rollup/`, `views/`, `seed/`, `tasks/` (the `deriveTaskTime` derivation), `migrationJob/`, `systemSettings.ts`, `timezone.ts` or `realtimeHook.ts` imports out of `chokePoint/`, or listing them in the rule.
- A manifest-declared hook (`ModuleManifest` field plus registry resolution in `packages/module-registry`) — the per-process registry is the decision; the manifest route can supersede it later.
- Hooks for `createItemWithClient`, `itemDeleteWithClient` or `deleteRelationWithClient` — no domain needs one today (`docs/adr/2026-09-10-no-speculative-generality-beyond-issue-scope.md`).
- Removing the dead `modules/` rules — #653 (already merged when this issue starts).
- The JSONB cast clean-up in `mail/personLinkingActions.ts` and `inbox/` — #655.

## Acceptance criteria

- When an Emails item is patched through `updateItem` (or `updateItemWithClient`) in a process that loaded `@semprec/data`, a `mail_message_flag_sync_state` row is written in the same transaction, exactly as before; when the transaction rolls back, no row remains.
- When a Transcript `speakers` edge is created or its metadata updated with a key another person already holds, the write is rejected with the same `ValidationError` as today at all three call sites.
- When `pnpm run check:boundaries` runs on a tree where any file under `chokePoint/` other than `schemaCoreModuleManifest.ts` and `itemTrash.ts` imports from one of the listed domain folders, it fails with `chokepoint-knows-no-domain`; on the merged tree it passes, and `grep -rn "from \"../\(mail\|transcription\)/" backend/packages/data/src/chokePoint` matches nothing.
- `docs/adr/` contains the new ADR with valid frontmatter, and `git diff --stat docs/adr/` shows no change to any existing file other than the frontmatter of `2026-09-28-module-transactional-side-effects-inline-at-choke-point.md`, which is marked superseded by the new ADR when the task-recurrence call moved behind the hook.
- `pnpm run test:unit` runs `hooks.unit.test.ts` green; `pnpm run test:integration` passes with the listed test files importing `domainWriteHooks.js`.
