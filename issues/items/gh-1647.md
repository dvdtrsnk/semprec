## Context

Model tier rationale: One declarative mechanism (new optional descriptor fields on module database manifests, validated and projected through the existing schema read path) with existing manifest and catalog-coverage fixtures, but it spans the module-registry package, six manifests, two label catalogs and the projection, so it is more than a mechanical edit.

Each collection screen in the app offers a row of quick-filter chips (for example Projects: Active, Done, Archived, All), opens on a default one, sorts by a default order, and shows only the items that belong in a collection or in a picker. None of this exists in the backend: `ModuleDatabaseDescriptor` in `backend/packages/module-registry/src/manifest.ts` is only `{ key, name, defaultViewType? }`, `ModuleRegistry.getDatabases()` projects just those, and `GET /api/schema` (`manifest/schemaProjection.ts`) carries no per-database view hints, so every client hard-codes them. A view's stored `ViewConfig` (`views/viewConfig.ts`) can hold a `filter` and `sort`, but the seed creates one default view per database with no filter.

Two data facts shape the filters. `systemActive` is set only on system-module projects (true, or false when deactivated), so a user project has no `systemActive` key; a filter `not(equals systemActive true)` would drop every user project, whereas `is_empty systemActive` keeps exactly the user projects. And the filter compiler (`views/filterCompiler.ts`) turns `in` into `= ANY(...)` and a missing key yields NULL, so `not(in status [done, archived])` also drops a project with no status; a picker that must keep status-less projects therefore needs an explicit `is_empty status` branch.

Builds on #1360 (the property projection), #1522 (relative date conditions for the date-based chips, evaluated in the tenant time zone), #1534 (numeric comparison conditions) and #1413 (aligned Czech labels in the same catalogs this adds keys to). #1709 adds the option that applies a database's collection filter to counts and queries.

Decision: chip, default-sort and date-label texts are catalog keys (`labelKey`) resolved against the owning module's catalog for the caller's locale; `/api/schema` returns resolved labels only.

Decision: the module-registry package treats a filter as an opaque JSON object, because the filter grammar lives in the data package. The data package parses every declared filter with `filterNodeSchema` and checks every referenced property key against the seeded properties in a unit test, so an invalid declaration fails CI rather than startup.

Decision (product owner): one project picker is used everywhere a project is chosen. By default it hides done and archived projects through `pickerFilter` and keeps projects without a status; it can show the hidden ones by querying with the Projects `collectionFilter` alone (user projects in any status). A done project stays a valid relation target: the picker filter is a read hint and restricts no write.

Decision (product owner): "Recent" Files means a date in the last 30 days, computed as everywhere: the `last30` preset of #1522, D-30 through today inclusive.

Decision (product owner): every collection has a default sort in the schema. Events and Tasks sort by `date` ascending; every other collection sorts by creation time descending (newest first). This issue declares the two date sorts; the creation-time default for every other database needs the system-timestamp sort of #1594 and is #1995.

Shared-file ordering: this issue also waits for #1642 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys` and `testing`.

1. Extend `ModuleDatabaseDescriptor`, its zod schema and `ModuleDatabaseProjection` / `getDatabases()` in `module-registry/src/manifest.ts` and `registry.ts` with optional fields:
   - `quickFilters`: `[{ key, labelKey, filter?, sort?, isDefault? }]` (`filter` an opaque JSON object, omitted means "All"; `sort` a list of `{ property, direction }`),
   - `defaultSort`: `{ property, direction }`,
   - `dateLabels`: `{ pastLabelKey, noDateLabelKey }`,
   - `collectionFilter` and `pickerFilter`: opaque JSON filter objects.
   Manifest parsing rejects more than one `isDefault: true` per database and duplicate quick-filter keys.
2. In the data package, validate every declared filter with `filterNodeSchema` (a unit test over all module manifests, also checking property keys exist in the seeded database).
3. Declare in `seed/systemDatabasesModuleManifest.ts` and `library/libraryModuleManifest.ts`:
   - Projects: Active (`in status [inProgress, longTerm]`, default), Done (`in status [done]`), Archived (`in status [archived]`), All. `dateLabels` for the Due filter ("Overdue", "No due date"). `collectionFilter` = `is_empty systemActive`. `pickerFilter` = `and(is_empty systemActive, or(is_empty status, not(in status [done, archived])))`.
   - Events: Upcoming (default, sorted by `date` ascending), Today, This week, Next week, Past (sorted by `date` descending), All, using the relative date condition from #1522 on `date`; `defaultSort` `date` ascending.
   - People: All, Clients (`relationship in [client]`), Close (`in [closeFriend, parent, girlfriend]`), Others (`in [therapist, neighbor]`).
   - Tasks: `defaultSort` `date` ascending (no quick filters).
   - Files: All, Recent (`date_relative` preset `last30` on `date`), PDF (`type in [pdf]`), Images (`[jpg]`), Spreadsheets (`[xlsx]`), Documents (`[docx]`).
   - Health records: All, Monitoring (`status in [monitoring]`), Resolved (`[resolved]`).
   - Books: All, To read, Reading, Read (`status in [toRead]`, `[reading]`, `[read]`); Movies: All, Planned, Watching, Watched (`[planned]`, `[watching]`, `[watched]`). Neither has a default chip.
4. Add the chip, date-label and sort-related catalog keys to `seed/i18n/{en,cs}.json` and `library/i18n/{en,cs}.json` (key pattern `quickFilter.<database>.<key>` and `dateLabel.<database>.past|noDate`), with Czech and English texts; the catalog coverage tests must pass.
5. Project them in `GET /api/schema`: add to each database in `SchemaDatabaseProjection` `quickFilters: [{ key, label, filter?, sort?, isDefault }]`, `defaultSort?`, `dateLabels?: { past, noDate }`, `collectionFilter?` and `pickerFilter?`. A database without declarations returns empty `quickFilters` and omits the rest. User-created databases never have any.
6. Tests: manifest rejection cases; every declared filter parses; `/api/schema` returns localized chips; running `database.query` with the Projects `collectionFilter` returns only user projects (no system project, no deactivated one with `systemActive: false`); with the Projects `pickerFilter` it returns neither a done nor an archived project but does return a project with no status, and with the `collectionFilter` alone it returns the done and archived user projects too; `relation.put` of a task's project to a done project succeeds; `/api/schema` has `defaultSort` `date` ascending on Events and Tasks; the Files Recent chip uses `last30`.

## Scope

### In scope

- The descriptor fields, their validation, their localized projection in `/api/schema`, and the declarations for Projects, Events, People, Files, Health records, Books and Movies, plus the Tasks default sort.

### Out of scope

- Applying a collection filter inside `item.count` and queries through a `collection: true` option (#1709).
- Recipes quick filters: the Recipes module declares its own with this mechanism when it is created (#1707).
- The "Long without contact" People chip: it needs the derived last-contact value (#1660).
- The creation-time default sort (newest first) for every database other than Events and Tasks, including user-created databases: #1995, because it needs the system-timestamp sort of #1594.
- Sorting by option order and Czech collation (#1408, #1524).
- Any client rendering of chips or active state.

## Acceptance criteria

- When `GET /api/schema` is requested, then Projects has a quick filter "Active" with `isDefault: true` and filter `in status [inProgress, longTerm]`, and Books has "To read" with `isDefault: false` and no default chip.
- When `/api/schema` is requested with a Czech account, then chip and date labels are Czech; with an English account they are English.
- When `database.query` runs with the Projects `collectionFilter`, then it returns only user projects: no system project and no project with `systemActive: false`.
- When `database.query` runs with the Projects `pickerFilter`, then done and archived projects are absent and a project without a status is present; with the `collectionFilter` alone, done and archived user projects are present.
- When a task's project is set to a done project, then the write succeeds.
- When `GET /api/schema` is requested, then Events and Tasks have `defaultSort` `{ property: "date", direction: "asc" }`, and the Files "Recent" chip filters with `date_relative` preset `last30`.
- When a manifest declares two default quick filters or an unparsable filter, then the manifest is rejected.
- When a user-created database is listed, then it has no quick filters and no collection or picker filter.
