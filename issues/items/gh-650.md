## Context

`createMailLiveSyncRoot(pool, mailboxesDatabaseId, lifecycleFactory, options)` (`backend/packages/data/src/mail/mailLiveSyncRoot.ts:92`) is the mailsync composition root: it discovers active Mailbox items, seeds each one's `mail_account_sync_state` row via `ensureMailAccountSyncState`, and hosts one `MailAccountLifecycle` per account for as long as it stays active. `createNoopMailLiveSyncLifecycleFactory(pool)` (lines 40-47) is the lifecycle every sync mode uses until a real transport exists: `start()` enqueues one immediate `mailAccountSync` through `enqueueMailAccountSync`, `stop()` is a no-op. Nothing in `backend/services/` calls either function — the root runs only in `backend/packages/data/src/__tests__/mailLiveSyncRoot.test.ts`. Consequently no Mailbox ever gets a `mail_account_sync_state` row, `listAccountsDueForSync` (`mailAccountSyncStateStore.ts:307`) is always empty, and the five-minute `mailAccountSyncSweep` never enqueues anything even after #648 wires `mailModuleIds`.

The deployment pretends a separate process exists: `deploy/systemd/semprec-mailsync@.service` (`ExecStart=... services/semprec-mailsync/dist/serve.js %i`) points at a service that does not exist in `backend/services/`; `deploy/provision.sh:18-24` installs the unit (`SERVICE_UNITS`); `deploy/deploy.sh:28,149-152,161-163,174-176,245-252` enumerates active `semprec-mailsync@*` instances and restarts them; `deploy/deploy.test.sh:93,144-150,192,206-207,231` fakes a `semprec-mailsync@alice` instance; `deploy/provision.test.sh:96,112,118` asserts the unit is installed; `deploy/README.md:27,63`, `README.md:47`, `backend/services/README.md:1` and `docs/operations/database-roles.md:29` mention it. The live-sync root's own docstring (`mailLiveSyncRoot.ts:82-91`) requires exactly one instance per database — `semprec-api` is that single long-lived process (it already hosts the mail queue jobs and the Graph webhook route), so the root belongs in `backend/services/semprec-api/src/serve.ts`, and the phantom unit goes.

Depends on #648 for `resolveMailModuleIds` (the `mailboxesDatabaseId`), on #644 because both edit `deploy/deploy.sh`, `deploy/deploy.test.sh` and `deploy/README.md`, and on #645 because both edit adjacent lines of `deploy/provision.test.sh`, `deploy/provision.sh` and `serve.ts`. The `mailsync:<id>` process-heartbeat expectation in `backend/packages/data/src/health/processHeartbeats.ts:93-101` is deliberately untouched here (ops epic).

## Task

1. **Host the root in `semprec-api`** — in `backend/services/semprec-api/src/serve.ts`, after `createApiQueueRuntime(...)` (line 104): resolve `mailboxesDatabaseId` with `resolveMailModuleIds` (from `@semprec/data`, #648) inside `withTransaction(pool, ...)`, build `const mailLiveSync = createMailLiveSyncRoot(pool, mailboxesDatabaseId, createNoopMailLiveSyncLifecycleFactory(pool), { onLifecycleError: (mailboxItemId, phase, err) => logger.error({ err, mailboxItemId, phase }, "Mail live-sync lifecycle failed") })` and `await mailLiveSync.start()`. Pass it to `createGracefulShutdown({ server, queueRuntime, mailLiveSync, pool, logger })`.
2. **Shutdown ordering** — in `backend/services/semprec-api/src/shutdown.ts`, add `mailLiveSync: { stop(): Promise<void> }` to `CreateGracefulShutdownOptions` and stop it in `runShutdown` after the HTTP drain and before `queueRuntime.stop()` (a lifecycle's `start()` enqueues jobs; stopping the root before the queue runner means no new enqueue races the runner's stop), logging and continuing on failure like `queueRuntime.stop()` does. Update the docstring's sequence description. The heartbeat is still not part of this sequence (`docs/adr/2026-09-17-shutdown-ordering-with-late-heartbeat-stop.md`).

Update `deploy/README.md` lines 27 and 63 (the restart list), `README.md:47`, `backend/services/README.md:1` and the `semprec-mailsync` row of `docs/operations/database-roles.md` to say mail live-sync runs inside `semprec-api`.

## Scope

### In scope
- Hosting the single live-sync root in `semprec-api` with the noop lifecycle factory, its place in the shutdown sequence, and removing every trace of the non-existent `semprec-mailsync@` unit.

### Out of scope
- Real IMAP IDLE / Gmail Pub/Sub / Graph subscription lifecycle factories (`createBoundedImapIdleLifecycleFactory`, `createGmailWatchLifecycleFactory`, `createGraphWebhookLifecycleFactory`) — they need mailbox onboarding first (separate finding).

## Acceptance criteria

- When `semprec-api` starts on a seeded database containing an active Mailbox item, a `mail_account_sync_state` row exists for it within one discovery pass and one `mailAccountSync` job was enqueued for it; a soft-deleted Mailbox gets no row and its lifecycle is stopped on the next pass.
- When `semprec-api` receives `SIGTERM`, the live-sync root stops after the HTTP drain and before the queue runner, and shutdown completes even if the root's `stop()` rejects.
- After the change, `grep -rn "semprec-mailsync" deploy/ README.md backend/services/README.md docs/operations/` returns nothing, `deploy/provision.sh` installs four service units, and `deploy.sh` restarts exactly `semprec-ai-gateway`, `semprec-api`, `semprec-agents`, `semprec-transcribe`.
