## Context

Model tier rationale: An additive read-model extension over one existing listing function and handler that joins two blockers' data and fixes one shared counting rule, with existing fixtures and no new write path.

`GET /api/projects/:id/mcp-grants` (`backend/services/semprec-api/src/mcpAgentPageHandler.ts`, `listMcpToolGrantsForProject` in `backend/packages/data/src/mcp/mcpAgentPageGrants.ts`) returns `{ rows }` where each row has the tool, its server name, `mcpServerOnline` (the server item's `active` flag) and `granted`. The project screen also needs a header such as "3 of 5 enabled", a per-server state (connected or offline, greyed rows) and the localized label. It builds on #1391 (the localized `displayLabel` per row) and #1450 (the last connection result per server).

Additive response changes, keeping every existing field:

- each row: `displayLabel` stays as #1391 delivers it, and gains `effective: boolean`;
- each row: `server: { state: "connected" | "offline", lastConnectedAt: string | null, lastErrorReason: string | null }`;
- top level: `counts: { effective: number, total: number }`.

The single counting rule (shared with the project summary #1935, which must call the same function): a grant is `effective` when it is `granted`, its registration is `active`, and its server item is active (`mcpServerOnline`). `total` is the number of active registrations listed. A tool of an inactive server that is granted is greyed and not counted as effective. A server that is active but whose last connection failed is `offline` in `server.state` but its tools still count as effective, because the run catalog still offers them. `state` is `offline` when the server item is not active, or when the last recorded connection failed (`last_error_reason` is not null); otherwise `connected` (including a server never called yet). `lastConnectedAt` and `lastErrorReason` come from #1450 and are extensions beyond the on/off flag; `lastErrorReason` is one of the fixed connection error codes and never contains a secret.

## Acceptance criteria

- For a project with five active registrations of which three are granted on active servers, the response has `counts: { effective: 3, total: 5 }`.
- A granted tool of an inactive server has `effective: false`, `server.state: "offline"` and is not counted in `effective`.
- When the last connection to an active server failed with `handshake_failed`, then `server` is `{ state: "offline", lastErrorReason: "handshake_failed", ... }` and its granted tools are still counted as effective; after the next successful call it is `connected`.
- A server never called has `state: "connected"` and null `lastConnectedAt`.
- All previous fields of each row are still present.
