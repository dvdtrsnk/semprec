### Requirement gh-1701: [account 13/15] Let a signed-in user change their password

#### Context

Model tier rationale: A new authenticated credential-change route that re-verifies the password under a row lock, shares the login lockout, and revokes sessions, push registrations and outstanding reset tokens atomically, so it is an authentication and concurrency contract.

A signed-in user can change the password only by asking for a reset email (`POST /api/auth/password-reset/request`, then `consume`). `consume` revokes every session and push registration of the account, which also signs out the device the change was started from, and the user never proves they know the current password. There is no authenticated password change.

`deleteOwnAccount` (`backend/packages/data/src/tenancy/deleteAccount.ts`) already shows the pattern for re-verifying a signed-in user's password: it reads the failure streak with `getFailureStreak` before verifying (a locked (email, IP) pair is not verified), records a failed `recordLoginAttempt` on a wrong or locked attempt, throws `ReauthenticationFailedError` (HTTP 403 `reauthentication_failed`, deliberately not 401, which clients treat as "signed out"), and compares `password_hash` under a `FOR UPDATE` row lock. `passwordResetStore.ts` can create, count and consume reset tokens but cannot invalidate unconsumed ones. This issue builds on #1650, whose `revokeOtherUserSessions` keeps the caller's session and revokes the rest with push registrations.

Decision: the profile "change password" action is a proper change (current password plus new password), not a reset email. Resetting by email stays available for the sign-in screen.

Shared-file ordering: this issue also waits for #1699 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Add `POST /api/auth/password-change` in `authHandler.ts` with body `{ currentPassword, newPassword }`, authenticated with `authenticateRequest`. Missing or non-string `currentPassword` is 400 `validation_failed` (`details.field` `currentPassword`); a `newPassword` shorter than `MIN_PASSWORD_LENGTH` (8) is 400 with `details.field` `newPassword`.
2. Add an action `changePassword(pool, input)` in a new `backend/packages/data/src/auth/passwordChangeActions.ts` modelled on `deleteOwnAccount`: first `getFailureStreak(email, ip)` and, when the pair is locked, skip verification, record `recordLoginAttempt({ succeeded: false })` and throw `ReauthenticationFailedError`; otherwise verify `currentPassword` with `verifyPassword`; a wrong password records a failed attempt and throws the same error. The client IP comes from `clientIpFromRequest` like login.
3. On a correct password, in one `withTransaction`: lock the user row `FOR UPDATE`, compare its `password_hash` with the verified one (different means a concurrent change, throw `ReauthenticationFailedError`), write the new Argon2id hash, call `revokeOtherUserSessions` (#1650) with the current session id, and mark every unconsumed reset token of the user consumed. Record a successful attempt so the lockout streak resets.
4. In `passwordResetStore.ts` add `consumeAllPasswordResetTokensForUser(client, userId)` (`UPDATE password_reset_tokens SET consumed_at = now() WHERE user_id = $1 AND consumed_at IS NULL`). A reset link issued before the change then fails with `password_reset_token_consumed`.
5. Respond 200 `{ "ok": true }`. The current session and its push registrations stay valid.
6. Register the route in `routeMatrix.ts` ("change password", `POST /api/auth/password-change`, `account`), add its case to `__tests__/tenantIsolationRoutes.test.ts` and map it to `authHandler.ts` in `ROUTE_HANDLER_FILES` of `__tests__/chokePointWriteBoundary.unit.test.ts`.
7. Add tests for each acceptance criterion below, including the concurrent-change race and lockout sharing with login.

#### Acceptance criteria

- When `currentPassword` is wrong, then the response is 403 `reauthentication_failed` (not 401), a failed attempt is recorded toward the (email, IP) lockout, and the calling token still works.
- When the (email, IP) pair is locked out, then the password is not verified and the response is 403 `reauthentication_failed`.
- When `currentPassword` is correct and `newPassword` is valid, then the response is 200, the new password logs in and the old one does not; the calling token keeps working; every other session of the user gets 401 and its push registrations are revoked.
- When a reset link was requested before the change, then consuming it afterwards returns 400 `password_reset_token_consumed`.
- When `newPassword` has 7 characters, then the response is 400 `validation_failed` with `details.field` `newPassword`.
- When two changes race with the same current password, then at most one succeeds and the other is 403.

### Requirement gh-1687: [account 12/15] Replace the previous session of the same installation at login

#### Context

Model tier rationale: Revoking a session inside the login transaction must be race-free for two simultaneous logins of one installation and must keep the push and realtime cascades consistent, which is a concurrency and session-ownership contract.

Every login creates a new session. An app that is reinstalled or signs in again on the same phone gets a fresh row each time, so the signed-in devices list would grow with ghost entries of the same phone and the old tokens stay valid until they idle out. With #1354 each native session records the installation's `deviceId`, and #1650 provides `revokeOtherSessionsForUser` and the push-cascade action.

This issue makes a login with a `deviceId` replace the user's earlier active session(s) carrying that same `deviceId`. `login` in `backend/packages/data/src/auth/authActions.ts` already creates the session inside one `withTransaction` after `lockUserTenantBinding`; the replacement happens in that transaction. `listActiveSessionsForUser` (#1583) then shows one row per installation.

Decision: only sessions of the same user with the same non-null `deviceId` are replaced; a login without `deviceId` (web, or an older client) replaces nothing.

#### Task

Load `state-writes`, `error-handling` and `testing`.

1. In `sessionsStore.ts` add `revokeSessionsForDevice(client, userId, deviceId, exceptSessionId)`: `UPDATE sessions SET revoked_at = now() WHERE user_id = $1 AND device_id = $2 AND id <> $3 AND revoked_at IS NULL RETURNING id`, firing `fireSessionRevoked` for each id (deferred to commit). It uses the partial index from #1354.
2. In `login` (`authActions.ts`), inside the existing success transaction and after `createSession`, when `input.device?.deviceId` is set, call it, then `revokePushSubscriptionsForSession` for every revoked id on the same client. To make two concurrent logins of one installation serialize, take a transaction-scoped advisory lock keyed on the user and `deviceId` (`pg_advisory_xact_lock(hashtext('semprec_device:' || $1 || ':' || $2))`) before creating the session, so exactly one active session per `(user, deviceId)` remains.
3. Add tests: a second login with the same `deviceId` revokes the first token (401), its push registrations and its WebSocket (4401 after commit); a login with a different `deviceId` or none revokes nothing; another user using the same `deviceId` is unaffected; two concurrent logins with one `deviceId` leave exactly one active session; a failed login (wrong password, locked out) revokes nothing.

### Requirement gh-1702: [tasks-core 08/11] Inherit a task's project onto its attachments

#### Context

Model tier rationale: This issue only declares one rule on an already-built link-rule mechanism and proves the Tasks-specific behavior with existing fixtures, but it touches the shared module manifest and depends on several blockers' contracts, so it is not low.

An attachment shown on a task also shows a project. By default an attachment takes the project of its task and follows it: changing the task's project changes the project of every attachment that still follows it, "no project" included (an attachment of a task without a project receives the project when the task gets one). The user can end the following by changing an attachment's project by hand or cancelling the link, and can restore it; a file that the user gave its own project keeps it when the task's project changes. A file has one visible project.

The mechanism is not built here. #1403 to #1656 store the links with their state (following or broken) and expose them on items, break a link when a user or an agent writes the target value, provide `link.unlink` and `link.relink`, and detach links when a source is deleted. #1411 lets a module manifest declare a link rule and validates it; #1593 propagates a changed source value to the targets that still follow it. A rule names a source property, a target property and the relation that connects them (the `via`). Agent writes that would break a link go through approval (#1713, #1758).

What this issue adds is the Tasks rule: source `Tasks.project`, target `Files.projects`, via `Files.tasks`. It builds on #1654 (attaching an upload to a task creates the `Files.tasks` edge, which is the moment the link is created), on #1521 (`relation.set` replaces a task's single project atomically, which is the change that propagates) and on #1621 (realtime invalidation for the edge writes the propagation performs).

Decision: a file attached to two tasks keeps the link only to the task it was uploaded to first; the file never gets the union of two tasks' projects, because a file has one visible project. This is the conservative option; a union is not built.

Decision: when an existing file that already has its own project is attached to a task, the file keeps its own project and the link starts broken; the task's project is not forced onto it.

Shared-file ordering: this issue also waits for #1697 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

Load `state-writes` and `testing`.

1. Declare in the systemDatabases module manifest (`backend/packages/data/src/seed/systemDatabasesModuleManifest.ts`) one link rule using the declaration shape from #1411: source `Tasks.project`, target `Files.projects`, via `Files.tasks`. The rule must pass that issue's manifest validation (source and target properties exist, the via relation connects the two databases).
2. Behavior to hold, using only the mechanism's operations (no custom propagation code):
   - Attaching a file (new or existing without its own project) to a task creates a link in the state following, and the file takes the task's project, or none.
   - Changing the task's project with `relation.set` on `Tasks.project`, including to none, replaces the project set of every following file with the new one (an empty set for none).
   - A user or agent write to `Files.projects` of a following file breaks the link (`links.projects` reports it broken with the writer); a later change of the task's project does not touch that file.
   - `link.unlink` and `link.relink` on such a file work as the mechanism defines; relink restores the task's project.
3. Tests (real database, through the choke point and the HTTP surface where the mechanism exposes it) for each behavior above, including a file attached to two tasks (the first task's link wins) and a task with no project.

### Requirement gh-1709: [collection-query 11/12] Add the batched item.count operation with grouping

#### Context

Model tier rationale: One new read operation built on the existing filter compiler and choke-point read path, with defined seams in the shared catalog, REST and MCP and an existing fixture style, though it spans many hotspot files and groups by two property kinds.

Counts shown across the app (the number next to each collection on the overview, the "N items" header, the open-task badge, the "5 tasks, 2 today" line on a project row and the "2 people" line on a company row, the column counts on a board) cannot be derived from the paged query. `countItems` exists only inside the choke point (`backend/packages/data/src/chokePoint/itemReads.ts`, backed by `itemsStore.countItems`) and is not in the operation catalog or REST. There is no grouped aggregation at all, and rollups (`backend/packages/data/src/rollup/config.ts`) cannot filter their target items and cannot be added to a locked database through the API, so they are not used for these counts.

This issue adds one batched operation, `item.count`, that returns a count per database and optionally per group. It builds on `totalCount` (#1406), which established the count-by-filter semantics, and on the collection filter that module manifests declare (#1647). It is built on by facets (#1759), the area overview (#1760), the overview summary route (#1837), the Tasks today view count (#1798) and free-text search in counts (#1857).

A relation count is read from the relation edges. A relation edge write publishes no invalidation today, so clients' relation-based counts can go stale until #1621 lands; this issue adds no invalidation of its own.

Decision: counts exclude soft-deleted items always (no `inTrash` option), and a deleted item that is restored is counted again. Decision: the overview's "today tasks" count is just `item.count` over the filter of the Tasks today view (#1798); this issue adds no task-specific logic. Decided by the product owner: the badge counts only open tasks for today (the open-only Today filter of #1798, 7 rather than 8 in the design), because a badge says what is left to do, as the overview does. Decision (product owner): an archived database is in the trash, so its items are counted nowhere and counts match what the user sees: an entry for an archived database returns `count: 0` and no groups, and a relation `groupBy` leaves out targets that lie in an archived database (an item whose only edges point into archived databases counts in the `null` group), matching the relation reads of #1404 and #1518.

Shared-file ordering: this issue also waits for #1704 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

Load `state-writes`, `canonical-keys` and `testing`.

1. Add the operation `item.count` to the catalog: name in `operationNames.ts`, capability `core.item.read` (non-destructive) in `capabilities.ts`, input/output types in `schemas.ts` and `port.ts`, binding in `bindings.ts`. Input: `{ items: [{ databaseId, filter?, groupBy?, collection? }] }` with 1 to 20 entries (`.strict()`, more than 20 is a 400). Output: `[{ databaseId, count, groups?: [{ key, count }] }]` in input order.  The board's column counts, the project-row "5 tasks, 2 today" and the company-row "2 people" are all expressed with this one shape: the board is `groupBy` on the grouping select under the full filter; the project row is one entry grouped by the task-to-project relation (not-done tasks) plus a second entry in the same batch with an added `date_relative` today condition; the company row is `groupBy` on the people-to-companies relation.
2. `filter` is the same filter tree `database.query` takes (`filterNodeSchema`, so relative dates and numeric conditions work once their issues land). `collection: true` ANDs the collection filter that the database's module manifest declares (#1647); a database without a declared collection filter is counted unfiltered.
3. `groupBy` is a property key. For a relation property (project to area, task to project, person to companies) `groups` has one entry per distinct target item id that occurs, counted over the filtered items (an item linked to two targets counts in both groups); items with no edge are returned as `{ key: null, count }` only when there are any. For a `select` property `groups` has one entry per stored option key that occurs and `null` for items without a value, ordered by the option order in `config.options` (the board uses this for its columns). A non-groupable property type or unknown key is a 400 `field: "groupBy"`. `count` is always the total of the filtered items.
4. Implement in the data layer: a grouped count function next to `countItems` in `backend/packages/data/src/chokePoint/itemsStore.ts`, exposed through `itemReads.ts` and the choke point type in `chokePoint.ts`. One SQL statement per entry, every value a bound `$N` parameter, `deleted_at IS NULL`, and no item or relation target whose database has `archived_at` set (an entry for an archived database counts 0). Resolve every `databaseId` under the caller's tenant: an unknown and a foreign database id answer identically (the same not-found response `database.query` gives).
5. Add `POST /api/items/count` in `backend/services/semprec-api/src/itemsHandler.ts` mapping the body to the operation, add it to `routeMatrix.ts` (tenant-scoped, non-public) and to the cross-tenant route cases in `__tests__/tenantIsolationRoutes.test.ts`. The MCP and agent tools derive from the catalog; update their contract tests.
6. Tests: nine collections in one call (counts exclude deleted items; restore counts again); an entry for an archived database returns 0 and its restore counts the items again; a relation `groupBy` whose targets lie in an archived database omits those groups; `groupBy` of a relation over active projects returns one count per area; a select `groupBy` on the board property returns option order with the stored counts; `collection: true`; 21 entries is a 400; foreign database id behaves like an unknown one.

### Requirement gh-1717: [calendar-module 05/15] Serve a calendar timeline across Events and Tasks

#### Context

Model tier rationale: It adds the central calendar read that merges two databases with relations, tenant-zone day arithmetic, tolerant handling of invalid stored values and an extension point that six later issues plug into, so a mistake is visible in every calendar view and for every tenant.

There is no calendar read today. A client can query one database at a time (`POST /api/databases/:id/query`, `views/viewQuery.ts`), the item envelope carries no relations (`backend/services/semprec-api/src/adapter/itemEnvelope.ts`), and a project or people can only be found by extra queries. Date filters cast to `timestamptz` in the database session time zone (`views/filterCompiler.ts`), and an invalid stored date makes the whole query fail. The tenant time zone is read with `getSystemTimezone` (`backend/packages/data/src/systemSettings.ts`). The calendar views need one call that returns everything that happens in a date range: Events, Tasks and, in later issues, derived entries such as birthdays, holidays, sleep nights and recurring occurrences.

This issue adds `GET /api/calendar/timeline?from=YYYY-MM-DD&to=YYYY-MM-DD[&shape=compact]`, a custom route of the calendar module with justification `single-consumer-read` (`docs/adr/2026-09-11-module-manifest-custom-routes.md`), and the shared read function behind it, `readCalendarTimeline`, which the agenda (#1762) and the Semp tool (#1952) reuse. The client never computes anything: no merging, grouping or day arithmetic. Time arithmetic uses the calendar time module of #1418; date and time format checks reuse the validators of #1663 and #1536.

Request rules: `from` and `to` are dates, `to` is not before `from`, the range is inclusive of both days, and it is at most 93 days (a protection; a month grid is at most 42 days); otherwise 400 `validation_failed`.

Response: `{ timezone, today, now, from, to, items }`, where `timezone` is the tenant zone and `today` and `now` come from the calendar time module. Each item has `kind` (`event` or `task` in this issue), `id`, `databaseId`, `title`, `type` (the Event type, otherwise null), `date`, `endDate`, `timeFrom`, `timeTo`, `effectiveTo` (the end time used for display after the defaults of the time module; for a timed Task without an end it equals `timeFrom`, since a Task has no default length), `hasEnd` (whether an end was stored), `allDay` (no `timeFrom`), `calendarId` (an Event's `Events.calendar` edge, or the live default calendar when an older Event has no edge; the id of the calendar with system key `tasks` for a Task; null if the tenant has no calendars yet), `status` (a Task's status, otherwise null), `place`, `project` (`{ id, name, color }` or null), `people` (`[{ id, name }]`), `updatedAt` (for `ifVersion`) and `readOnly` (false for stored items). With `shape=compact` (the month view) each item has only `id`, `kind`, `title`, `calendarId`, `allDay`, `date`, `endDate`, `timeFrom`, `status`, `updatedAt` and `readOnly`.

Selection: an Event is included when its `date` is on or before `to` and its last day (`endDate`, else `date`) is on or after `from`; a multi-day Event appears once, with its range. A Task is included when its display day (its `date`) is inside the range; a done Task is included with status `done`, a `wontDo` Task is not, and trashed items never are. A row whose stored date or times are not valid is left out of the response (never a 500), with a log line carrying the item id.

Order: by day, and inside one day: all-day Events, then Tasks without a time, then timed Events, then timed Tasks; inside a group by `timeFrom`, then title (compared with the tenant user's locale collation, `cs` by default), then id. The same order serves the day view and both month views.

Extension point: further sources (birthdays, holidays, sleep nights, task and Event occurrences, subscribed events, task-in-event state, traces) are separate issues. They plug into a list of timeline sources in `calendar/timelineSources.ts` (`{ id, readItems(client, context) }`, each returning items for the range and the shared context of time zone, `today` and `now`), so adding a source never edits the core merge. Items from sources that are not stored rows have a synthetic `id` and `readOnly` true.

Decision: hidden calendars are not filtered on the server; every item carries its `calendarId` and the client hides according to the calendar's `hidden` flag.

Decision: a multi-day Event is returned once with its range, not once per day.

Decision: an Event without a calendar edge (created before the calendar cutover) is kept as it is and is returned with the default calendar's id as `calendarId`; the read writes no edge.

Decision: nothing is cached; the client refetches after the realtime invalidations of Events, Tasks, People, calendars and edges.

Shared-file ordering: this issue also waits for #1709 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.
