### Requirement gh-1805: [agent-runs 09/21] Return title, project, trigger, duration and approval counts on the agent run detail

#### Context

Model tier rationale: One additive read extension of an existing endpoint with batched lookups and an extra actor check, built on columns other issues add, with a web client that must keep parsing; no schema or write contract of its own.

`GET /api/agent-runs/:id` (`backend/services/semprec-api/src/agentRunHandler.ts`) returns the bare `AgentRunRow` (`id`, `projectItemId`, `parentRunId`, `heartbeatId`, `triggeredBy`, `unit`, `task`, `status`, `result`, `startedAt`, `finishedAt`, `actorUserId`) read from `getAgentRun`. It relies only on tenant row-level security and does not compare `actorUserId` with the session user (the realtime watch does: `backend/packages/realtime/src/agentRunWatch.ts`). A client that opens a run needs more than that: a human title, the project name, who or what started it, how long the work took, and what happened to approvals. The web client reads this endpoint through `web/src/api/agentRunOperations.ts` with a strict `status` enum, so the change must be additive.

This issue adds those fields in one batched read. It builds on the link from a run to its conversation thread (#1452), the thread of a heartbeat run (#1557) and the recorded MCP client name (#1788), which supply `trigger.threadId` and `trigger.mcpClientName`.

New fields (the existing ones stay unchanged):

- `title`: the run's `task`; for a heartbeat run, the heartbeat's `project_heartbeats.name`, because `task` is the action's configured task text there (`backend/packages/data/src/scheduler/actions.ts`).
- `projectName` (name of the project item, read in one batch like the approval queue does with `getItemsByIds`) and `heartbeatName`.
- `durationMs`: only for runs with `unit = invocation` and `triggeredBy` other than `mcp`; otherwise `null`, because a session run stays open for up to a day of idleness and an MCP run until its credential expires, so `finishedAt - startedAt` is not the time the work took.
- `trigger {kind, threadId, mcpClientName}`: `kind` is `user`, `tick`, `mcp` or `supervisor`. A follow-up turn in a heartbeat tick thread is a session run with `triggeredBy = user`; its `trigger.kind` is `tick` (from the thread kind) and `threadId` is the tick thread. `threadId` is `null` for MCP runs, and `mcpClientName` is `null` unless the run is an MCP run with a recorded name.
- `approvals {count, pending, approved, rejected, requestIds}`: aggregated from `approval_requests.agent_run_id` in one grouped query.

Decision: a run whose `actorUserId` differs from the session user answers 404, the same as an unknown id (defense in depth; a tenant has exactly one user today). This applies to the whole route, not only to the new fields.

Later issues build on this: the display status #1820, steps #1821, spend #1822, the one-reply scope #1889, error summaries #1824 and the project run list #1909.

Shared-file ordering: this issue also waits for #2003 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

2. Add one data-layer function (in `backend/packages/data/src/agentRuns/`) that, for a run, returns the extra fields with a constant number of queries: the project item name, the heartbeat name, the thread id and kind, and the grouped approval counts. No query per field per run.
3. Extend the response with the fields above. Existing fields keep their names, types and values; the web zod schema must still parse the response unchanged (add a contract test that parses a new response with the current schema).
4. Tests: a chat run has `trigger.kind` `user`, the thread id and `durationMs` filled; a heartbeat run has the heartbeat's name as `title`, `trigger.kind` `tick` and the tick thread id; an MCP run after the initialize handshake with a client name returns `trigger.mcpClientName` and `durationMs: null`; a session run has `durationMs: null`; a run with one pending and one approved request has the right `approvals`; another tenant's run is 404.

### Requirement gh-1820: [agent-runs 10/21] Derive a display status that shows a pending approval

#### Context

Model tier rationale: One shared pure derivation with a small rule table, wired into one existing response, with existing fixtures to extend; no persisted-data or authorization contract.

`agent_runs.status` is only `running`, `done` or `error`. A run that asked for a human decision is closed as `done` by the agent turn (the tools return "awaiting a decision" and the job `approvalExecute` later only executes the operation; it neither wakes the run nor writes an event), so a client reading `status` would show "done" for a run that is in fact waiting on the user. The run detail from #1805 already returns the approval counts of the run.

This issue adds `displayStatus` (`running`, `done`, `waiting_approval`, `error`) as a pure function over a run row and its approval counts, evaluated at read time and never stored, and returns it on the run detail. The function is shared on purpose: the project run list (#1909), the failed-call detection for a reply (#1890), the heartbeat list (#1910), the retry endpoint (#1908) and the run invalidations (#1863) all reuse it, so every surface agrees about "waiting".

Rules:

- `error` when `status = error`.
- `waiting_approval` when at least one approval request of the run is `pending`.
- `running` when `status = running`.
- `done` otherwise. A request that is `approved` with `execution_status = queued` already counts as `done`, not as waiting: the user has decided.

A tick that continues after a decision does so in a new turn with its own run and its own display status (#1775); the original run becomes `done` once nothing is pending.

Decision: the unfinished-reply case (a reply that ended without finishing, which also reads as `error`) is added to the same function by #1890; this issue does not implement it, and the function is written so that an additional input can be added without changing callers.

#### Task

Load `testing`.

1. Add `deriveRunDisplayStatus(run, approvals)` (pure, in `backend/packages/data/src/agentRuns/`) implementing the rules above, and export the `AgentRunDisplayStatus` type. It takes the run `status` and the approval counts, not a database client.
2. Add `displayStatus` to the response of `GET /api/agent-runs/:id` using the approval counts already loaded by #1805 (no extra query).
3. Unit tests for every rule and for precedence (`error` beats `waiting_approval`; a run `done` with one pending request is `waiting_approval`; with the request approved and queued it is `done`); one route test for a tick run with one pending request (`displayStatus: waiting_approval`, `approvals.pending: 1`) that becomes `done` after approval.

- backend/packages/data/src/__tests__/agentRunDisplayStatus.unit.test.ts (new)

#### Scope

##### In scope

##### Out of scope

- Using the status in the run list, heartbeat list, retry and invalidations: #1909, #1910, #1908, #1863.

#### Acceptance criteria

- When a run with `status = done` has one pending approval request, then `displayStatus` is `waiting_approval`.
- When that request is approved and queued for execution, then `displayStatus` is `done`.
- When `status = error`, then `displayStatus` is `error` even with a pending request.
- When `status = running` and nothing is pending, then `displayStatus` is `running`.
- `status` and every existing field of the response are unchanged.

### Requirement gh-1827: [sensitive-data 03/09] Redact sensitive tool results from agent run history

#### Context

Model tier rationale: One redaction rule applied where run events are persisted, with a clear marker that replay accepts; the pi message shape and the replay path must be checked, which keeps it above low.

`agent_run_events.payload` stores whole messages, including `tool_result`, and is the source of conversation reconstruction after a restart or a wake (`packages/agent-runtime/src/conversationReconstruction.ts`, events written by `recordPersistentEvent` in `packages/agent-runtime/src/lifecycleAdapter.ts`). Retention is bounded (`AGENT_RUN_EVENTS_RETENTION`) but the content stays readable in the database meanwhile. Encryption per tenant protects only external credentials. When an agent reads a health record or a sleep night, the full item therefore lands in the event history.

With #1808 (the `sensitive` flag) and #1810 (agent access to those databases only with a grant), this issue keeps the content of sensitive items out of stored run history.

Decisions:
- Redaction, not shorter retention (the first of the two options considered).
- The stored `tool_result` of a content-bearing operation on a sensitive database is replaced by the fixed marker `[redacted: sensitive]`. Content-bearing operations: `item.get`, `item.create`, `item.patch`, `item.delete`, `item.restore`, `database.query` and `view.query`. Operations that return only structure or ids are not redacted.
- The live session in memory still holds the real result, so the running turn is unaffected. Reconstruction receives the marker, so a resumed run continues without the sensitive content and the agent reads the item again with a tool if it needs it.
- Tool call arguments and the agent's own text are not redacted here; see Out of scope.

#### Task

Load `state-writes`, `io-hardening` and `testing`.

1. In `genericOperationAgentTools.ts`, mark the result of a content-bearing operation as sensitive when its database (the item's database, or the queried database) has `sensitive = true`, using the same transaction-time lookup as the access check. Carry the mark on the tool result in a form the lifecycle adapter can see.
2. In `lifecycleAdapter.ts`, when persisting a `tool_result` event that carries the mark, replace its content with `[redacted: sensitive]` and drop the mark. The live delta stream, which is never persisted, is unchanged.
3. Make sure reconstruction passes the marker through as an ordinary tool result and still pairs every tool call with a result.
4. Tests: a sensitive `item.get` is stored redacted while the same call on a non-sensitive item is stored in full; `database.query` on `sleepNights` is redacted; after a restart the reconstructed history contains the marker and no property value of the item; the running turn still sees the real result; no log line and no error message of the redaction path contains item values.

- backend/packages/agent-runtime/src/lifecycleAdapter.ts
- backend/packages/agent-runtime/src/conversationReconstruction.ts (only if the marker needs handling)
- backend/packages/agent-runtime/src/__tests__/ (new redaction tests)
- backend/packages/data/src/__tests__/ (reconstruction test if placed there)

#### Scope

##### In scope

- Redacting the stored tool results of content-bearing operations on sensitive databases and replay of the marker.

##### Out of scope

- The flag and the grants: #1808 and #1810.
- Redacting tool call arguments (values the agent writes), assistant text that quotes sensitive content and compaction summaries: #2001, which builds on the mark added here.

- When a run is resumed after the redaction, then it continues from the marker without the sensitive content.

- No log or error message of this path carries item values.

### Requirement gh-2001: [sensitive-data 04/09] Redact sensitive tool call arguments, assistant text and compaction summaries

#### Context

Model tier rationale: This changes what is persisted for every agent message after a sensitive read and must keep reconstruction and compaction consistent; an over-broad rule breaks resumed runs, a too narrow one leaks sensitive values, and the choice is not obvious from existing code.

#1827 replaces the stored `tool_result` of a content-bearing operation on a sensitive database with `[redacted: sensitive]` (`packages/agent-runtime/src/lifecycleAdapter.ts`). The same values still reach `agent_run_events` in three other ways: as arguments of the agent's tool calls (a value it writes into a health record), as assistant text that quotes what it read, and through a compaction checkpoint (`packages/agent-runtime/src/compaction.ts`, stored as a `compaction` event and used by `conversationReconstruction.ts`).

Decisions (decided by the product owner):
- Tool call arguments, assistant text and compaction summaries that carry sensitive values are redacted in the same way as the source; otherwise the values would leak past the permission.
- Tool call arguments: the stored arguments of a content-bearing write (`item.create`, `item.patch`) to a sensitive database, and of every tool call issued later in a turn that already has a marked result, are replaced by the marker; the tool name and call id stay, so every call still pairs with its result.
- Assistant text: once a turn has a tool result marked sensitive by #1827, the assistant text persisted after it in that turn is stored as the marker.
- Compaction: a compaction checkpoint is built only from the reconstructed, redacted history, so it never sees an unredacted value.
- The live session in memory is unchanged; only persisted events are redacted.

3. When persisting assistant text after a marked result in the same turn, store the marker instead of the text.
4. Make sure compaction is computed from the reconstructed, redacted entries (`conversationReconstruction.ts`), never from the live session, and that the stored checkpoint holds no unredacted value.

### Requirement gh-1999: [sensitive-data 08/09] Inherit sensitivity for files, transcripts and Inbox entries linked to a sensitive record

#### Context

Model tier rationale: This widens an authorization check from a per-database flag to a per-item rule derived from relation edges, evaluated in the same transaction as every agent read, so a missed path or a stale edge leaks health data.

#1808 marks whole databases as `sensitive` and #1810 denies an agent (and #1827 redacts from run history) the items of those databases. Data about a sensitive record also lives outside them: a Files item attached to a health record (the Files to Health records relation), a transcript of a doctor's visit, an Inbox entry about it. Today such an item is read in full by an agent without any grant.

Decisions (decided by the product owner):
- Sensitivity is inherited from the item it belongs to: an item of the `files`, `transcripts` or `inbox` database (by owner module) that has a live relation edge to an item of a sensitive database is treated as sensitive.
- Transcripts and Inbox entries are not classified by their content in this version; they are sensitive only when linked to a sensitive record.
- An inheriting item is readable and writable by an agent only when its project has the matching access to every sensitive database the item is linked to; the refusal is the same `ForbiddenError` with code `forbidden` as in #1810. The user-attached ref allowance of #1849 applies to the attached item itself as before.

#### Task

Load `state-writes`, `error-handling` and `testing`.

1. Add one exported constant with the inheriting owner modules (`files`, `transcripts`, `inbox`) next to the sensitive keys of #1808, and `sensitiveSourceDatabaseIds(client, itemId)` in `agentGrants/` that returns the ids of the sensitive databases an item of an inheriting database is linked to through live edges (both edge directions, endpoints not soft-deleted), in one query.
2. In `assertAgentDatabaseAccess` (#1810), for an item of an inheriting database, also require the requested access on each database returned by step 1, in the same transaction and before the read or write.
3. In list and query reads of an inheriting database (`database.query`, `view.query`, item lists) for an agent, omit the items that fail step 2 instead of refusing the whole query, and keep `totalCount` consistent with the rows returned; relation targets that fail it are returned as `{ id, hidden: true }`.

### Requirement gh-1807: [inbox-core 15/22] Add GET /api/inbox/cards with server-side ordering and resolved sources

#### Context

Model tier rationale: One new tenant-scoped read route that follows the existing custom-route and route-matrix pattern, but it merges two sources (stored cards and pending approvals) and must respect the tenant isolation test that has one case per surface.

The Inbox shows one stack of cards of all kinds, ordered by group: approvals, then proposals, then invalid cards, then clarifications, then transcript cards. Today a client can only read cards generically (`POST /api/databases/:id/query`, `GET /api/items/:id`), the item envelope (`backend/services/semprec-api/src/adapter/itemEnvelope.ts`) returns no relation edges, and pending approvals come from a separate `GET /api/approval-requests` (`backend/packages/data/src/mcp/approvalRequestsQueue.ts`, pending only, without the source of the run). The Inbox module (`backend/packages/data/src/inbox/inboxModuleManifest.ts`) mounts only `POST /api/proposals/:id/confirm` and `GET /api/inbox-types`. No server code decides the kind of a card; that is delivered by #1425.

This issue adds `GET /api/inbox/cards`, the single read the Inbox needs. It builds on #1425 (card kind), #1766 (the source of an approval request) and #1785 (the shared resolver behind the approval queue with a source filter, which this route reuses so both lists agree). The count (#1823), the realtime invalidations (#1811), the editor schemas (#1825) and the reject route (#1845) build on it. Other issues add fields to the card additively.

Decision: the order inside a group is chronological by capture time (Inbox `date` and `time`), for an approval by `requested_at`, for a transcript card by the transcript's finish time (until that exists, the transcript `date`), then by id.
