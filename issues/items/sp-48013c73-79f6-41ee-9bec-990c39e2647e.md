### Requirement gh-1781: [tasks-in-events 06/10] Count a completion before the event ends as completed in the event

#### Context

Model tier rationale: One Tasks update hook that writes or removes a protected edge in the same transaction as a status change, on existing hook, relation-write and event-end seams, verified with real-database fixtures.

A task that sits in an event (#1764) is part of that event until the event ends. When it is completed before the event has ended, the completion belongs to that event: the task is then shown as done only inside the event ("done in the event") and disappears from its day, from the Tasks list and from counts. This holds wherever the task is ticked: in the event, in the Tasks list, on the task's own screen, or by an agent. A completion made after the event has ended is an ordinary completion and is shown in the event as "done later". Today completion is `PATCH /api/items/:id` with `status: done`; #1544 sets `completedOn` (today by default, a past day allowed, a future day rejected) and `completedAt`, and an existing Tasks update hook advances a recurring task to its next instance inside the same transaction when `status` becomes `done` (`tasks/taskRecurrenceItemUpdateHook.ts`). #1540 created the protected relation `Tasks.completedInEvent` with the inverse `Events.completedTasks` (single-valued on the task side, owned by the system, owner process `tasks`, so a generic edge write answers 403 `owner_violation`). #1764 orders a task's host events by the edge's `addedAt`; #1780 derives visibility from the live host events and uses the event end of the calendar time module (#1418).

This issue adds the Tasks update hook that records a completion in the event from the status change itself and keeps the edge consistent with the status. Reading the state per event is #1801; hiding completed-in-event tasks from lists and counts is part of the visibility predicate of #1798; agent and MCP tools are #1957.

Decisions:
- Decided by the product owner: every completion made before the end of the event counts as a completion in the event, wherever it is made. There is no separate complete-in-event route; the ordinary status write is the only path.
- The event the completion belongs to is the task's last live host event by `addedAt`, provided that event has not ended at the moment of the write. If that event has already ended, no edge is written and the completion is an ordinary one.
- `completedOn` follows the ordinary rule of #1544 (today by default); this issue does not change it.
- Setting `status` to `notDone` or `wontDo` by any route removes the `completedInEvent` edge in the same transaction; that is also how a completion in the event is undone.
- A repeated `done` on a task that already has the edge changes nothing.

Shared-file ordering: this issue also waits for #1780 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

Load `state-writes`, `error-handling`, `canonical-keys` and `testing`.

1. Add a Tasks update hook `taskCompletedInEventHook` in `backend/packages/data/src/tasks/taskCompletedInEventHook.ts`, registered in `domainWriteHooks.ts`, that runs in the writing transaction for every Tasks write, whatever route or writer made it:
   - when the write changes `status` to `done` and the task has no `completedInEvent` edge, read the task's live host events (edges of `Tasks.hostEvents` ordered by `addedAt`, joined to live Events), take the last one, and if its end (the event end of #1418) is later than now, create the `completedInEvent` edge to it with the system context `{ ownerProcess: "tasks" }`;
   - when a write leaves `status` as `notDone` or `wontDo`, delete the task's `completedInEvent` edge if any.
2. The hook does not change `completedOn`, `completedAt` or any other property, and runs after the Tasks transform so the recurrence advance of a recurring task still happens in the same transaction.
3. Tests (real database, controlled clock): a task in an event 15 October 13:00 to 14:00 completed by `PATCH /api/items/:id {status: "done"}` at 13:30 gets the `completedInEvent` edge to that event; the same completion at 14:30 gets no edge; a task in a future event completed before that event ends gets the edge; a task in two events gets the edge to the one added last; a task without host events gets no edge; a repeated `done` writes nothing; `PATCH {status: "notDone"}` and `{status: "wontDo"}` remove the edge; a generic relation PUT or DELETE on `completedInEvent` from either side is 403 `owner_violation`; a recurring task completed in an event also gets its next instance in the same transaction; a foreign tenant's task is never touched.

### Requirement gh-1784: [sleep 04/13] Validate sleep values and keep one settings item and one night exception per key in sleep write hooks

#### Context

Model tier rationale: Concurrent creates and updates must produce one settings item and one exception per night under advisory locks in the same transaction as the write, and the new error code extends the closed API error contract, so a mistake silently allows duplicates or deadlocks.

#1776 gives every tenant three locked sleep databases, but nothing checks the values written into them. The choke point validates only unknown keys, rollups, relations and ownership (`assertWritableProperties` in `backend/packages/data/src/chokePoint/itemWrites.ts`); a select value is checked against its catalog by nobody (the general check arrives with #1802). Create hooks run inside the write transaction after the row is inserted (`runItemCreateHooks`) and an error from a hook rolls the write back; update hooks run after the write in the same transaction (`chokePoint/hooks.ts`); domain hooks are registered only in `backend/packages/data/src/domainWriteHooks.ts`. `ConflictError` in `backend/packages/data/src/errors.ts` has the fixed code `version_conflict`, and `ITEM_ERROR_CODES` in `backend/services/semprec-api/src/adapter/errorContract.ts` is a closed list with no code for a duplicate.

This issue adds the value rules and the "one item per key" rules for the three sleep databases in one write hook file. Settings are a singleton per user, and a night may have at most one exception item. It builds on the module (#1776), the per-module pre-write transform (#1422, used to normalize times), the shared `normalizeWallClockTime` helper (#1536) and the hook registry order of #1601 (the three hook issues share `hooks.ts` and `domainWriteHooks.ts`). Later issues add to the same files in the same chain: one plan per wake day (#1799), the PUT route for a single night (#1835, which takes the same advisory lock) and the resync push (#1838). The temporary select check here is removed when #1802 validates selects generally.

Decisions:
- Validation always runs over the merged item (the stored properties with the patch applied), so a partial PATCH is judged as a whole.
- Times are accepted as `H:MM` or `HH:MM` and stored as zero-padded 24-hour `HH:MM` (a pre-write transform); `24:00` is not valid for sleep times.
- Uniqueness is enforced on non-deleted items only; restoring a trashed duplicate is not checked here.
- A duplicate answers 409 with the new code `duplicate_item` and `details.field`.

### Requirement gh-1793: [library 10/11] Let the user override, remove and re-search a cover

#### Context

Model tier rationale: It introduces a manual-override state machine that must coexist with a system-owned property and a background job without creating a second writer, plus a new retry route that touches the job queue and the automation lock state, so ordering and ownership errors are easy to make.

The `cover` property of Books and Movies is `owner: system` (`backend/packages/data/src/seed/seedLibraryModule.ts`): a user write gets 403 from `assertWritableProperties` in `backend/packages/data/src/chokePoint/itemWrites.ts`, and only the library metadata job writes it. If a user path could change or delete `cover`, that would be a second writer under `docs/adr/2026-09-10-single-writer-ownership-model.md`. Users still need to choose their own cover (a photo or an image), remove the cover, and ask the automation to look again. Today `setItemAutomationLocked` in `backend/packages/data/src/library/itemAutomationStore.ts` has no caller, and the only retry is the nightly 04:00 sweep.

Decision: the manual cover lives in separate user-owned properties, so each value has one writer:
- `coverOverride` (type `image`, owner `user`): `{ blobId }` of the chosen image;
- `coverRemoved` (type `checkbox`, owner `user`): the user removed the cover;
- `coverSource` (type `select`, owner `user`, options `candidate | userPhoto | userImage`): where the override came from.
The cover shown to the user is: nothing if `coverRemoved`, else `coverOverride` if set, else `cover`. The job keeps writing only `cover` (and the other fields), so a manual choice is never overwritten and the author and other data are still filled.
Decision: removing a cover sets `coverRemoved` only and does not lock the whole item (the automation still fills other data). No lock or unlock route is added here.
Decision: "search again" clears `coverOverride`, `coverRemoved` and `coverSource`, lifts a `locked` state, resets the automation row to `pending` and enqueues the job at once instead of waiting for 04:00.

Builds on #1768 (state and invalidation after each run) and #1401 (upload of a standalone image blob through `POST /api/blobs`, and collection of unused blobs). #1812 builds on this issue for candidates.

### Requirement gh-1795: [calendar-recurrence 01/08] Add birthday properties to People

#### Context

Model tier rationale: One known mechanism (two user-owned properties on a locked system database, a validating write hook and a per-tenant cutover) across defined seed, hook and cutover seams, with the People.emails and transcripts cutovers as fixtures.

The People database has `name`, `relationship` and `contact` (`backend/packages/data/src/seed/seedTenDatabases.ts`) and `emails` (added by `seedEmailModuleInTransaction`). There is no birthday, and People is `schema_locked`, so an existing tenant can receive a property only through a code-level cutover that writes SQL directly (`transcription/transcriptsCatalogCutoverMigration.ts` is the pattern). Date filters and sorts cast a `date` value to `timestamptz` (`views/filterCompiler.ts`, `views/sortCompiler.ts`), so a value that is not a full valid date, such as `--MM-DD`, would break a People view sorted or filtered by it.

This issue adds the data the calendar needs to show birthdays: `People.birthday` (a full valid date `YYYY-MM-DD`) and `People.birthdayYearKnown` (checkbox), both owned by the user. The timeline source that turns them into calendar entries is #1800.

Decision: when the year is not known, the client stores a placeholder leap year (2000) with `birthdayYearKnown` false, so a birthday on 29 February is storable; the calendar uses only month and day. The backend does not rewrite the year; it only requires a real calendar date.

Decision: an empty `birthday` (null or absent) is valid and clears it.

Shared-file ordering: this issue also waits for #1793 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1799: [sleep 07/13] Keep each wake day in at most one sleep plan through a sleepPlans write hook

#### Context

Model tier rationale: Moving a wake day between plans rewrites other plans inside the same write transaction, and concurrent and cross-moving writes need a retry loop and deadlock mapping to behave correctly, so the concurrency contract is subtle.

A user's sleep plans are keyed by the weekday on which they wake. Each day belongs to at most one plan, and a plan may have no days. #1784 validates the shape of `wakeDays` but not the relation between plans. Today `updateItemProperties` locks the written row (`lockItemById ... FOR UPDATE`) and update hooks run only after the write, in the same transaction (`backend/packages/data/src/chokePoint/itemWrites.ts`); there is no pre-write hook that could serialize before the row lock. A nested `updateItemWithClient` call re-runs all update hooks, and omitting `ifVersion` there merges by property key without a version check. The pattern for a domain hook that calls back into the choke point is `backend/packages/data/src/tasks/taskRecurrenceItemUpdateHook.ts` (decision records `2026-09-30-choke-point-domain-hooks-through-a-per-process-registry` and `2026-10-09-item-create-domain-hooks`). The REST adapter's error contract (`backend/services/semprec-api/src/adapter/errorContract.ts`) does not map Postgres `40P01` (deadlock detected) today.

This issue adds the invariant "a day is in at most one plan" to the plan hooks of #1784 (it extends the same `sleep/sleepWriteHooks.ts` and registration chain). When a plan takes a day, the other plans lose it, in the same transaction, so a client moves a day with a single PATCH of the receiving plan. The resolver (#1792) and the resync push (#1838) rely on it.

Decisions:
- A plan keeps its empty `wakeDays` if it loses all days; the server does not delete it and does not enforce "at least one plan".
- Plans restored from the trash can bring back an occupied day; this issue does not check restores. Until the next edit, the plan with the lower `position` wins, ties by lower id (the resolver rule of #1792).
- A position is sent by the client; equal positions are allowed.

Shared-file ordering: this issue also waits for #1795 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

Load `state-writes`, `error-handling` and `testing`.

1. In `backend/packages/data/src/sleep/sleepWriteHooks.ts` add a create and update hook for `sleepPlans` (registered in `domainWriteHooks.ts` after the validation hooks of #1784). After a write whose merged item has non-empty `wakeDays`, select the other non-deleted plans of the database that contain any of those days (`SELECT ... FOR UPDATE`, ordered by id) and remove the taken days from each through `updateItemWithClient` without `ifVersion` (so their hooks, realtime invalidation and `updatedAt` apply). Repeat the select as a new statement until it returns no row: under READ COMMITTED a single statement does not see a row that a concurrent transaction just committed, and without the loop two concurrent writes taking the same day from a third plan could leave the day in two plans. The nested update lowers only other plans' days, so it does not recurse into further changes.
2. Catch a Postgres deadlock (`40P01`) raised while locking plans (two plans exchanging days concurrently lock each other) and rethrow it as `ConflictError` (HTTP 409) so the client repeats the request. Only the hook's own lock statements are covered; no other mapping changes.
3. Tests (real database): moving `sat` and `sun` plus `fri` into the weekend plan removes `fri` from the weekday plan in the same transaction and both items have a new `updatedAt`; two concurrent writes taking `sat` from one plan into two different plans leave `sat` in exactly one plan; two concurrent cross moves (A takes a day from B while B takes a day from A) end with one success and one 409 that succeeds when repeated; non-crossing concurrent moves both succeed; a plan saved with `wakeDays` `[]` is stored; an agent `item.patch` moving a day without approval runs the same hook.
