## Context

The owner asked on 2026-11-23 for the mobile apps to keep their data on the device, to work without a connection, to send what was changed offline once a connection is back, to be fast because they read that local copy, and to keep following the server's live changes through `WS /api/sync` (a change made in the Daily Note on the iPhone must reach every device of the account). The logic belongs to the shared Kotlin layer, so both apps get it.

Until now every screen read the server on every open (only the mail thread lists were kept, `FileMailThreadListCache`), a write without a connection failed, a cold start without a connection stopped at "server unreachable", and the note editor discarded a local change when the page had changed elsewhere. The Android app has no signed-in screens; the Apple app carries every screen named below.

## Decisions

- Question: Should a sync library (PowerSync, Realm, Couchbase Lite, Ditto, ElectricSQL, Store5) or a Yjs replica on the device (Yrs through Gobley/UniFFI) do the work?
  - Adopted answer: No library. The shared data layer keeps the server's answers and queues the writes itself, on the `CacheFiles` file functions the mail cache already uses.
  - Reason: PowerSync, the only complete Kotlin Multiplatform sync engine, replicates Postgres through logical replication, which bypasses the row-level security that isolates tenants, and needs another service and a Postgres restart. Realm's device sync ended in September 2025, Couchbase Lite and Ditto need their own servers, ElectricSQL has no mobile write path and Store5 only caches reads. Yrs needs a Rust toolchain in every mobile build, and the native note editor works on Markdown, not on a Yjs document.
- Question: Replicate rows into a local database, or keep the answers of the routes the screens already call?
  - Adopted answer: Keep the answers, per request, and show the queued writes on top of them.
  - Reason: The screens read server read models (the calendar timeline, the agenda, the overview, the diary period) whose derivations (recurrence, sleep, birthdays, rollups) would otherwise be implemented a second time on the device. Kept answers stay exactly what the server computed.
- Question: Does the server need a change feed?
  - Adopted answer: No backend change. A reconnecting device reads again, as the realtime decisions already say; the frames of the sync socket mark kept answers stale while connected.
  - Reason: The existing decisions keep the server free of replay buffers, and the personal data set is small enough that reading the offline set again after a reconnect is cheap.
- Question: How do offline note edits meet edits made elsewhere?
  - Adopted answer: The device keeps the version it last read beside its own text and merges three ways (blocks, then the characters of a block) when the server has moved on, instead of discarding the local change.
  - Reason: The native editor already writes canonical Markdown against an `ETag`; a three-way merge on the device needs no new server operation and keeps both sides of edits made in different places.
- Question: What is kept offline?
  - Adopted answer: Tasks (reminders), events, calendars and invitations, projects, areas, people, companies and the other collections, the diary with its notes, pages, the Inbox, sleep, the overview and the reminders the device schedules. Mail, files and their contents, recordings, transcripts, search and Semp stay online only.
  - Reason: The owner excluded mail and files as too large to be useful offline.

## Behavior specification

- Reading: a screen of the offline set opens with what the device kept, without waiting for the network when nothing has changed since; it reads the server again after any write and after the sync socket reports a change or reconnects, and without a connection it shows what was kept.
- Starting: a cold start without a connection opens the signed-in app when the device checked that session before.
- Writing: a change made without a connection is kept on the device, shown at once in every kept list and calendar it belongs to, and sent in the order it was made as soon as a connection is back; a change the server then refuses is dropped and reported.
- Notes: a note can be read and edited without a connection; edits made on two devices meanwhile are merged; a change saved by another device reaches an open note through the sync socket.
- Warming: when the app connects, it reads the offline set (task lists, catalogs, the calendar around today, the agenda, the diary around today, the overview, invitations, calendars, sleep, the Inbox) so it is there before it is needed.
- Status: the app shows when it is offline with changes waiting, and when changes could not be saved.
- Ending the session (signing out, a session the server refuses) removes everything kept for it.
