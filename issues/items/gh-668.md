## Context

`rebaselineDocHistory` in `backend/packages/data/src/docs/docHistory.ts` (lines 31-107) folds the retention window's tail into a new baseline checkpoint and then deletes what the baseline made redundant. It replays `doc_history_updates` rows with `update_id > checkpoint.through_update_id AND created_at <= cutoff` in `(created_at, update_id)` order (lines 73-78), takes `throughUpdateId` from the **last row of that order** (lines 83-84), and deletes `WHERE update_id <= throughUpdateId` (lines 100-103). Those two keys are not aligned: `doc_updates.created_at` (mirrored into `doc_history_updates`, `docPersistence.ts` lines 173-177) is `now()` = transaction start time, while `id`/`update_id` is a `bigserial` assigned at insert. A transaction that started earlier but inserted later gets a *lower* `created_at` with a *higher* `update_id` than a concurrent one. Concretely: A starts at t1, B starts at t2 > t1, B inserts first (`update_id` 10, `created_at` t2), A inserts second (`update_id` 11, `created_at` t1). With `t1 <= cutoff < t2`, the replay applies 11 and not 10, sets `throughUpdateId = 11`, and the delete removes 10 — an update that was never folded into any baseline. `openDocVersionAt` (lines 228-233) then can never replay it either (`update_id > through_update_id`), so that edit is lost from history permanently. The window is narrow (two overlapping append transactions straddling the cutoff) but the loss is silent and unrecoverable.

Separately, `runDocHistoryCutoverMigration` (`backend/packages/data/src/docs/docHistoryCutoverMigration.ts`) claims at lines 27-30 that `LOCK TABLE docs IN EXCLUSIVE MODE` "excludes any concurrent doc creation/write for the duration of the cutover". It does not: appends write `doc_updates`/`doc_history_updates` and lock `doc_snapshots` rows (`loadDocWithClient`), none of which touch `docs`, and `EXCLUSIVE` does not block the `ACCESS SHARE` reads of `docs` an append makes. The cutover is a one-time, idempotency-guarded step that has already run wherever `through_update_id` is `NOT NULL`, so the fix there is the docstring, not the behaviour.

## Task

1. `rebaselineDocHistory`: choose the boundary by `update_id` contiguity, not by timestamp order. Replace the replay query (lines 73-78) with: select `update_id, update` for `doc_id = $1 AND update_id > $2 AND update_id < COALESCE((SELECT min(update_id) FROM doc_history_updates WHERE doc_id = $1 AND update_id > $2 AND created_at > $3), 9223372036854775807) ORDER BY update_id ASC` — i.e. every row after the checkpoint up to (excluding) the first row, in id order, whose `created_at` is past the cutoff. `throughUpdateId` is the last replayed `update_id` (or the checkpoint boundary when nothing was replayed) — now by construction every row with `update_id <= throughUpdateId` has been applied, so the delete at lines 100-103 removes only folded updates. The new baseline's `represented_at` stays `cutoff` (rows past the gap with `created_at <= cutoff` but a higher id are retained and replayed by `openDocVersionAt`, which reads `update_id > through_update_id AND created_at <= at`; Yjs updates are commutative, so the state at `cutoff` is the same set either way). Update the function's doc comment (lines 7-30) to state the boundary rule and why timestamp order cannot be used.
2. `openDocVersionAt`: order the replay by `update_id ASC` only (line 231) — ordering is irrelevant to the CRDT merge and `(created_at, update_id)` suggests a guarantee that does not exist; adjust its doc comment (lines 148-152).
3. `docHistoryCutoverMigration.ts`: replace the comment at lines 27-30 with what the lock actually does (serialises concurrent cutover runs and blocks concurrent `docs` row inserts/updates; it does not exclude appends to existing docs, which the cutover tolerates because it only runs once, before any release that appends `doc_history_updates` is live). No code change.
4. Tests, new `backend/packages/data/src/__tests__/docHistoryRetention.test.ts` (integration): build the interleaving by hand — insert two `doc_updates`/`doc_history_updates` pairs for one doc with `update_id` 10 (`created_at` after the cutoff) and 11 (`created_at` before the cutoff) plus an earlier baseline checkpoint, run `rebaselineDocHistory` with a retention that puts the cutoff between them, and assert row 10 still exists, `through_update_id` of the new baseline is the checkpoint boundary (nothing before the gap), and `openDocVersionAt(now)` reconstructs both updates; the existing happy-path behaviour — rows before the cutoff are folded and deleted — is asserted in the same file.

## Scope

### In scope
- The id-contiguous rebaseline boundary, the replay order, the cutover docstring, and the tests.

### Out of scope
- Deleting `doc_history_updates` by `expires_at`: an expired row that has not been folded into a baseline (a doc whose rebaseline keeps failing, or the gap rows above) would be lost from reconstruction, so the rebaseline remains the only deleter; `expires_at` and its index stay unused (a later contract step may drop them).
- `getOrCreateDoc`'s live-item check (sibling issue C14).
- Doc rows orphaned by the purge (sibling issue C2).

## Acceptance criteria

- When two appends straddle the retention cutoff with inverted id/timestamp order, the rebaseline never deletes an update it did not fold, and `openDocVersionAt` for a later timestamp still reflects both edits.
- When every update before the cutoff is contiguous by id, the rebaseline folds and deletes them exactly as before.
- The cutover migration's comment no longer claims to exclude concurrent doc writes.
