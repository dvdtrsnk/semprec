## Context

`backend/services/semprec-api/src/shutdown.ts` builds this service's shutdown sequence: `runShutdown` (lines 97-111) awaits `drainServer` (which calls `server.close()`, polls `closeIdleConnections()` and, after `drainTimeoutMs` = `SHUTDOWN_DRAIN_TIMEOUT_MS` (60 s), calls `closeAllConnections()`), then `queueRuntime.stop()`, then `endPool`. It never touches the realtime sync server. `backend/packages/realtime/src/syncServer.ts` implements `SyncServer.close()` (lines 464-475): it sets `closed`, detaches and releases the `LISTEN` pool client, sends every connected socket RFC 6455 close code 1012 ("Service Restart", `SERVICE_RESTART_CLOSE_CODE`) and awaits `wss.close()`. `backend/services/semprec-api/src/serve.ts` creates the sync server at line 100 (`const syncServer = await createSyncUpgradeHandler(pool)`) and calls `createGracefulShutdown({ server, queueRuntime, pool, logger })` at line 108 without it.

Consequence on every deploy restart: each upgraded `/api/sync` socket is a live connection on the `net.Server`, so `server.close()`'s callback never fires while a client is connected; the drain runs for the full 60 s, `closeAllConnections()` then destroys the sockets without any close frame (clients see an abnormal 1006, not the 1012 their reconnect logic — `reconnect.e2e.test.ts` "recovers after a controlled server shutdown (deploy)" — is written for), and the `LISTEN` client is released only by `pool.end()`, which `endPool` bounds at `POOL_END_TIMEOUT_MS` (5 s) and logs as a failure. `docs/adr/2026-09-16-realtime-outage-and-backpressure-close-rather-than-buffer.md` requires a controlled shutdown to deliver a real close code; `docs/adr/2026-09-17-shutdown-ordering-with-late-heartbeat-stop.md` fixes the drain-then-pool ordering this issue slots into.

Issue #650 later adds a `mailLiveSync` step to the same `runShutdown` and creates `__tests__/shutdown.test.ts`; this issue lands first and #650 extends the file.

## Task

1. In `backend/services/semprec-api/src/shutdown.ts`:
   - Add `syncServer: { close(): Promise<void> }` to `CreateGracefulShutdownOptions` (a structural type, so the test can pass a fake; the real `SyncServer` from `@semprec/realtime` satisfies it).
   - In `runShutdown`, immediately before `await drainServer(...)`: `try { await syncServer.close(); } catch (err) { logger.error({ err, signal }, "syncServer.close() failed"); }` — a failing close is logged and the sequence continues, matching how `queueRuntime.stop()` is handled. Calling it before `server.close()` is safe: `SyncServer.handleUpgrade` rejects every upgrade once `close()` has run (`syncServer.ts` lines 448-456), so no socket can attach in between.
   - Update the docstring (lines 83-90) to name the new first step: close the sync server (1012 to every client, `LISTEN` client released), then drain HTTP, then stop the queue runtime, then end the pool.
2. In `backend/services/semprec-api/src/serve.ts` line 108, pass `syncServer` into `createGracefulShutdown({ server, syncServer, queueRuntime, pool, logger })`. Nothing else in `serve.ts` changes.
3. Tests — `backend/services/semprec-api/src/__tests__/shutdown.test.ts` (new, integration tier `*.test.ts`, embedded Postgres via `getTestPool`/`resetDatabase` from `@semprec/data/testSupport`):
   - Build a real `http.Server` whose `upgrade` handler forwards `/api/sync` to `createSyncUpgradeHandler(pool)` exactly as `serve.ts` does (the harness in `reconnect.e2e.test.ts` shows the shape: `createServer(dispatch)`, `server.on("upgrade", ...)`, `listen(0)`); authenticate a `ws` client through a seeded session (`seedSystem` + the auth helpers the e2e test uses) and wait for the socket's `open`.
   - Call `createGracefulShutdown({ server, syncServer, queueRuntime: { stop: async () => {} }, pool: dedicatedPool, logger })("SIGTERM")` where `dedicatedPool` is a separate `new Pool({ connectionString: process.env.TEST_DATABASE_URL })` so the shared test pool is never ended, and `drainTimeoutMs` is left at its default. Assert: the promise settles in under 5 s (measure with `performance.now()`), the client's `close` event carries code 1012, and the logger recorded no `pool.end() did not settle` / `syncServer.close() failed` error line (capture the logger as `semprec-ai-gateway`'s `shutdown.test.ts` does).
   - A second case: `syncServer.close` rejects — the shutdown still resolves, `queueRuntime.stop` was called, and the rejection was logged with `syncServer.close() failed`.

## Acceptance criteria

- When `semprec-api` receives SIGTERM with one authenticated `/api/sync` client connected, the shutdown promise settles in under 5 s and that client observes close code 1012.
- When `syncServer.close()` rejects, the shutdown still stops the queue runtime and ends the pool, and `syncServer.close() failed` is logged once.
- When no sync client is connected, the sequence behaves exactly as before (drain, queue stop, pool end).
