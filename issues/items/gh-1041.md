**Blocked by:** #1024, #1040
**Model tier:** medium

## Context

Model tier rationale: The lock, guard and mutations are specified, but they touch login and reset refusal paths and need a concurrent last-admin test.

An admin can suspend and reactivate accounts and change roles, and at least one admin must always remain. Every admin mutation is audit-logged, and an admin never enters another tenant's content.

A tenant's lifecycle is the `status` column of the global `tenants` table: `provisioning | active | suspended | deleting`, with `status_changed_at`. Every user owns exactly one tenant (`users.tenant_id`) and has a `users.role ∈ admin | member`. Since #980, `verifySessionToken` already answers a session whose tenant is not `active` with the same `UnauthorizedError` as a bad token, so a suspended user's open sessions stop authenticating at once.

What is still missing:

- **Login.** `login` (`backend/packages/data/src/auth/authActions.ts:105-140`) verifies the password and creates a session regardless of tenant status, so a suspended user would get a session that then fails on every request.
- **Password reset.** `requestPasswordReset` (`backend/packages/data/src/auth/passwordResetActions.ts:63-88`) issues tokens and `resetPassword` (`:118-138`) consumes them for any user, so a suspended account could still be password-reset.
- **Revocation.** Nothing revokes a suspended user's sessions or push registrations. `revokeAllSessionsForUser` (`backend/packages/data/src/auth/sessionsStore.ts:116-122`) revokes sessions and fires `session_revoked` after commit, which closes that user's sockets with 4401. #1024 added `revokeAllPushSubscriptionsForUser(client, userId): Promise<number>` to `backend/packages/data/src/push/pushSubscriptionsStore.ts`, used on password reset (zero is a legitimate count).
- **Status writes.** No writer changes `tenants.status` after provisioning. The tenant store is `backend/packages/data/src/tenancy/tenantsStore.ts`. It exports `TenantStatus` and `getUserTenantBinding(client, userId): Promise<{ tenantId; status: TenantStatus; role: UserRole } | null>`, the lookup `verifySessionToken` uses (#980).

The admin plane (#1037):

- `createAdminRoutes` in `backend/services/semprec-api/src/adminHandler.ts`: `admin: true` routes return 403 `admin_required` to members and run in `runAsSystem`.
- `backend/packages/data/src/tenancy/accountsAdminStore.ts` provides `listAccounts` / `AdminAccountSummary` and `recordAdminAction(client, { actorUserId, action, targetTenantId, details })`. The actions `accountSuspended`, `accountReactivated` and `accountRoleChanged` are reserved for this issue.
- `accountsAdminStore.ts` is barred by ESLint from importing `runInTenant`. Everything here touches only global tables.

Later issues build on the guard and the status transition: #1042 tears down a deactivated tenant's in-process state, and #1049 reuses both for account deletion.

## Task

Load `state-writes` (guards inside the write's transaction, affected-row checks), `io-hardening` (new admin routes), `error-handling` (new 409 refusals) and `canonical-keys` (new error codes).

1. **Status transition** — in `tenantsStore.ts`, add `transitionTenantStatus(client: PoolClient, tenantId: string, from: readonly TenantStatus[], to: TenantStatus): Promise<{ id: string; status: TenantStatus; statusChangedAt: string }>`. It is one `UPDATE tenants SET status = $to, status_changed_at = now() WHERE id = $1 AND status = ANY($from) RETURNING …`. On zero rows, an existing tenant gets `new ChokePointError(409, "invalid_account_status", …)` and a missing one gets `NotFoundError`. It is the only writer of `tenants.status` outside provisioning.
2. **Last-admin guard** — in `accountsAdminStore.ts`:
   - `lockAdminMembership(client)` runs `SELECT pg_advisory_xact_lock(hashtext('semprec_admin_membership'))`.
   - `assertAnotherActiveAdminRemains(client, userId)` counts users with `role = 'admin'` whose tenant is `active`, excluding `userId`. When that count is 0 it throws `LastAdminError`, a new exported class extending `ChokePointError` with `(409, "last_admin", "At least one active admin must remain")`.
   - Every mutation below takes the lock first and applies the guard only when the target is currently an active admin.
3. **Mutations** — in `accountsAdminStore.ts`. Each takes `(client: PoolClient, input: { actorUserId; targetUserId })` and runs entirely inside the caller's transaction: the lock, then the target `users` row read `FOR UPDATE` (missing: `NotFoundError`), then the guard, the write and the audit row.
   - `suspendAccount`:
     - transition `active → suspended`;
     - `revokeAllSessionsForUser`;
     - `revokeAllPushSubscriptionsForUser`;
     - `recordAdminAction(… "accountSuspended", targetTenantId)`.
   - `reactivateAccount`: transition `suspended → active` and record `accountReactivated`. Sessions stay revoked; the user logs in again.
   - `changeAccountRole(client, { actorUserId, targetUserId, role })`: an unchanged role returns the account without an audit row. Otherwise it runs the guard when demoting an active admin, executes `UPDATE users SET role = $2 WHERE id = $1` with `requireAffectedRows`, and records `accountRoleChanged` with `details: { from, to }`.
   - Each returns the target's `AdminAccountSummary`. An admin may act on themselves; the guard alone decides.
4. **Login and reset refusal**:
   - In `login`, after the password check succeeds, a user whose `getUserTenantBinding` is `null` or whose status is not `active` is recorded as a failed attempt and gets the same `UnauthorizedError`. No session is created, and the timing and response equal a wrong password.
   - In `requestPasswordReset`, such a user (same `getUserTenantBinding` check) takes the same silent no-op path as an unknown email.
   - In `resetPassword`, after consuming the token, throw `PasswordResetTokenError("invalid")` for such a user. The caller's transaction rolls back, so the token stays unconsumed and no password changes.
5. **Routes** in `createAdminRoutes` (all `admin: true`; `:userId` checked with `assertUuid`; each in one `withTransaction`):
   - `POST /api/admin/accounts/:userId/suspend` answers `200 { "account": AdminAccountSummary }`.
   - `POST /api/admin/accounts/:userId/reactivate` answers `200 { "account": AdminAccountSummary }`.
   - `PUT /api/admin/accounts/:userId/role` takes the body `{ "role": "admin" | "member" }` and answers `200 { "account": AdminAccountSummary }`. Any other `role` value is 400 `validation_failed`, field `role`.
   - Add the three route-matrix entries (`admin: true`) and their `ROUTE_HANDLER_FILES` mappings, and the new runtime exports to `EXPECTED_RUNTIME_EXPORTS`.

## Scope

### In scope
- Suspension, reactivation and role changes, with their audit rows.
- The last-admin guard and the tenant status transition function.
- Login and password-reset refusal for non-active tenants.

### Out of scope
- Tearing down in-process state when a tenant leaves `active`: sockets by tenant, mail live sync and Semp entries (#1042), and running agent runs (#1050).
- Account deletion and the `deleting` status (#1049).
- Per-IP throttling of login and reset (#1073).
- Exposing `role` in the web session and the admin accounts page (#1079).
- Invitations (#1040).

## Acceptance criteria

- When an admin suspends tenant B's member:
  - B's tenant is `suspended` with a new `status_changed_at`;
  - every B session has `revoked_at` set and a `session_revoked` event fires after commit for each;
  - every B push registration is revoked;
  - one `accountSuspended` audit row names B's tenant;
  - B's next request with an old cookie answers 401;
  - tenant A is unchanged.

  (integration, `adminHandler.test.ts`, two tenants via `createTestTenant()` from #975)
- When the suspended user logs in with the correct password, the response is the same 401 as a wrong password, no session row is created, and a failed attempt is recorded (integration, `authActions.test.ts`).
- When a password reset is requested for the suspended user, the response is the same 200 and no token row is written. When a token issued before the suspension is consumed, the result is `invalid`, the token stays unconsumed and the password hash is unchanged (integration, `passwordResetActions.test.ts`).
- When the account is reactivated, the tenant is `active`, an `accountReactivated` audit row exists, and the user can log in again. Reactivating an `active` account, or suspending a `suspended` one, answers 409 `invalid_account_status` and writes no audit row (integration, `adminHandler.test.ts`).
- When the only active admin tries to demote or suspend themselves, the response is 409 `last_admin`, and nothing changes (no audit row). With a second active admin present, the same request succeeds (integration, `adminHandler.test.ts`).
- When two admins concurrently demote each other on two connections, exactly one succeeds and the other receives 409 `last_admin`, leaving one admin (integration, `accountsAdminStore.test.ts`).
- When `PUT …/role` sends the target's current role, the response is 200 and no audit row is written. When it sends `"owner"`, the response is 400 with field `role`. A role change writes `accountRoleChanged` with `{ from, to }`, and the new role is effective on the target's next request (integration, `adminHandler.test.ts`).
- When `:userId` is unknown, each route answers 404. A `member` gets 403 `admin_required` and an anonymous caller gets 401 (integration, `adminHandler.test.ts`, `routeMatrix.test.ts`).
