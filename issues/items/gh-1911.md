## Context

Model tier rationale: One known mechanism (raising a deduplicated problem from existing failure paths) at three call sites with an existing store, but the dedupe key depends on the retry chain and the transaction placement must be right at each site.

Today a failed heartbeat tick leaves two unconnected notifications. `notifyHeartbeatError` in `backend/packages/data/src/scheduler/sweep.ts` writes `heartbeat_error` in the sweep's transaction and knows only the heartbeat and the job id. `createAgentRunAction` in `backend/packages/data/src/scheduler/actions.ts` writes `agent_run_error` through `finishAgentRunWithErrorNotification` (`backend/packages/data/src/agentRuns/agentRunsStore.ts`) in another transaction, and only on the final attempt of an occurrence. A tick whose run ends `done` but whose answer left a failed tool call (the reply written into the tick thread by #1557) raises neither.

With the problem store of #1459 these become one entry per cause: the user sees one problem per failing heartbeat, however many retries and notifications it produced. The readers are the status API (#1555), recovery (#1915) and the backfill (#1958).

It builds on: the structured error code of runs (#1446), the retry chain of runs (#1448, `retry_of_run_id` links an attempt to the previous one), the function that tells whether a reply left a failed tool call (#1890) and the tick thread messages (#1557).

Decision: dedupe keys. A failure of a heartbeat tick, whether reported by the sweep or by the run action, is `agents:heartbeat:<heartbeatId>` (the run action has `context.heartbeatId`). A failed run that is not a heartbeat tick and not a chat turn is `agents:run:<id of the first run of its retry chain>`, that is the run reached by following `retry_of_run_id` until it is `NULL`. Runs triggered by a user conversation are excluded: a failed chat turn is a problem per reply (#1931).

Decision: severity is `warning` for a failed run and for a tick reply that left a failed tool call. `occurrenceKey` is the id of the failed run, or the job id for the sweep failure, so a replay adds nothing.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In `scheduler/sweep.ts`, call `raiseProblem` (category `agents`, kind `agentHeartbeat`, source `project_heartbeats`/heartbeat id, `dedupe_key` `agents:heartbeat:<heartbeatId>`) next to `writeNotification` in `notifyHeartbeatError`, in the same transaction.
2. In `scheduler/actions.ts`, where the run action closes a failed final attempt with `finishAgentRunWithErrorNotification`, raise the problem in the same transaction as the run close and the notification: kind `agentHeartbeat` with the heartbeat key when `context.heartbeatId` exists, otherwise kind `agentRun` with `agents:run:<first run of the chain>` and `project_item_id` of the run. Skip runs triggered by a user conversation.
3. When a tick thread reply is written with a failed tool call according to the function of #1890, raise `agents:heartbeat:<heartbeatId>` (severity `warning`) in the same transaction as the message write, because the run is `done` and no `agent_run_error` appears.
4. Put the key builders in `backend/packages/data/src/semp/agentProblemKeys.ts`.
5. Tests: a failed tick (`heartbeat_error` plus `agent_run_error`) gives exactly one active problem with the heartbeat key; three failed attempts of the same occurrence give one problem; a failed delegated run gives one problem keyed by the first run of its chain; a chat turn failure raises none here; a rollback of the failure transaction leaves no problem; a tick reply with a failed tool call raises the heartbeat problem.

## Scope

### In scope

- Raising the heartbeat and agent run problems at the three failure sites above, with their dedupe keys.

### Out of scope

- The problem store (#1459), resolving on a later success (#1915) and the backfill of existing failures (#1958).
- Problems for failed chat replies (#1931).
- Retrying a failed tick (#1908) and the notification wording.

## Acceptance criteria

- When a heartbeat tick fails with both `heartbeat_error` and `agent_run_error`, then one active problem `agents:heartbeat:<heartbeatId>` exists.
- When a delegated or other non-tick run fails after retries, then one problem keyed by the first run of the retry chain exists.
- When a tick run ends `done` but its reply left a failed tool call, then the heartbeat problem is raised in the transaction of the message write.
- When the failure transaction rolls back, then no problem exists.
- When a user conversation turn fails, then this issue raises nothing.
