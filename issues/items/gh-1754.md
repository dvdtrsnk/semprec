**Model tier:** medium

## Context

Model tier rationale: A new tenant-scoped table with row-level security and one write route over it, following the repository's existing tenant-table migration and custom-route patterns; the state is small and has no cross-item side effects.

Meeting notes (#1695) contain action items as data inside `computed.meetingNotes.actionItems`; `computed` has no user write path (only cache writers write it), so what the user did with an item cannot live there. The user can tell Semp to follow another person's action item ("Sledovat" in the product), and later add one of their own items as a task (#1767). Both need a per-item state that survives restarts and is the same on every device.

This issue creates that store and the follow action. The state is per transcript and action item id (the item's position in the stored array, which is never rewritten). A tenant has one user, so the state is per tenant. It builds on #1695 for the notes and is built on by #1767, which creates the task for an item and reads the state back out in the transcript detail endpoint.

Decisions:

- The table allows three states: `added`, `noted`, `dismissed`. This issue writes only `noted`; `added` is written by #1767; `dismissed` is reserved and has no writer yet.
- "Open" is the absence of a row. Clearing the follow state deletes the row.
- By the product owner: in v1 the followed state is only stored; Semp does nothing with followed items (no reminders, no checks in later recordings).
- `owner_person_id` is the person mapped to the item's `ownerSpeaker` at the time of the write, or `null`.

Shared-file ordering: this issue also waits for #1724, #1747 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Items have the composite primary key `(database_id, id)`, so no foreign key to items can be declared; the dependents cleanup in step 2 keeps the table consistent.
2. In `deleteItemDependents` (`backend/packages/data/src/chokePoint/itemTrash.ts`) delete the rows of a purged item from this table (`WHERE transcript_item_id = $1`), so purging a transcript leaves no state behind. Add a test next to the existing purge tests.
3. Add `backend/packages/data/src/transcription/transcriptActionItemStates.ts` with the store functions: `listActionItemStates(client, transcriptId)`, `setActionItemState(client, input)` (upsert), `clearActionItemState(client, transcriptId, actionItemId)`. Validate rows read back with the row type and `assertKnownValue`. Writers lock the transcript row first (`itemsStore.lockItemById`), so two concurrent writers for one transcript serialize.
4. Add the route `PUT /api/transcripts/:id/action-items/:actionItemId/state` with body `{ state: "noted" | null }` as a custom route of the systemDatabases module (`systemDatabasesModuleManifest.ts`, justification `transactional-semantics`: the existence check of the item, the owner lookup and the write commit together). Behavior: a non-UUID transcript id or a non-integer `actionItemId` is `400 validation_failed`; an unknown or foreign transcript, or an `actionItemId` outside `computed.meetingNotes.actionItems`, is `404`; `noted` upserts the row with `owner_person_id` from the `speakers` edge of the item's `ownerSpeaker`; `null` deletes the row; setting `noted` on an item whose state is `added` is refused with `400 validation_failed` (field `state`, reason `alreadyAdded`) and `null` on an `added` item is refused the same way, because undoing an added item removes its task and belongs to #1767. The response is `{ actionItemId, state }`, `state` being `noted` or `null`.
5. Register the route in `routeMatrix.ts`, `tenantIsolationRoutes.test.ts` (case table and request list) and the handler mapping of `chokePointWriteBoundary.unit.test.ts`, re-export the handler in the export block of `systemDatabasesModuleManifest.ts`, add tests in `backend/packages/data/src/transcription/__tests__/transcriptActionItemStates.test.ts` (set, repeat set is idempotent, clear, unknown item, foreign tenant, owner person recorded, `added` refusal, purge cleanup).

## Scope

### In scope

- The per-tenant state table, its cleanup on purge, and the store functions.
- The "follow" write (`noted` and its removal) as one route.

### Out of scope

- Creating a task from an action item, undoing it, and returning the state in the transcript detail endpoint: #1767.
- Reminders and checks for followed items: not in v1 (decided by the product owner).
- Using the `dismissed` state.

## Acceptance criteria

- When the user follows an action item, a second identical call changes nothing and returns the same response; clearing the state returns `state: null`.
- When the transcript id is unknown or belongs to another tenant, the response is the same `404`; the same for an action item index that does not exist.
- When a transcript is purged, its state rows are gone.
- The state rows of one tenant are invisible to another (row-level security) and the tenant isolation route test covers the new route.
- Following an item whose state is `added` is refused with `400 validation_failed`.
