**Blocked by:** #226, #114

## Context

Issue #226 authored manifests for the schema/data core, views, blocks/docs, and the ten system databases. This part authors the second group: the library module, mail sync/mailbox, and the Inbox pipeline — the modules with real tasks, workers (per-mailbox instances), heartbeat actions (`semprec.tick`), and data migrations. #115 then removes the remaining module-id branches from core and adds the load-all and inactive-projection tests across all manifests from both parts.

## Task

Create a `ModuleManifest` for each of the following existing modules, based on their actual databases, capabilities, tools, views, actions, rules, tasks, workers, and migrations — a retrofit of existing data logic, not a rewrite:

- library (`0005_library_module.sql`),
- mail sync and mailbox (`0006_mail_sync.sql`, `0007_mail_delivered_to_and_dsn.sql`, the per-mailbox worker rows consumed by #110, and the mailbox view types),
- the Inbox pipeline (#101–#106: the `inbox`, `inboxItemTypes`, and `processingProposals` databases, the `semprec.tick` heartbeat action, the `onItemEvent` registration, and the `journal-inbox` view type).

For each manifest, verify that `ModuleRegistry.loadModule()` loads it and that it passes the load-time structural check without modifying the module's data behavior; add a load test per manifest in the integration tier from #225.

## Scope

### In scope

- Manifests for the three modules above and their per-manifest load tests.

### Out of scope

- Manifests for core schema, views, docs, and the ten system databases (#226).
- Removing core module-id branches, the load-all test, and inactive-projection tests (#115).
- Agent runtime implementation and new module behavior.

## Acceptance criteria

- Each of the three modules loads through `ModuleRegistry.loadModule()` and passes structural validation, including its declared tasks, workers, heartbeat actions, and view types.
- Loading the manifests changes no stored data and no module data behavior.
