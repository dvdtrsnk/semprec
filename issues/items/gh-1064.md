**Blocked by:** #1031, #1063, #995

## Context

#1031 introduced per-tenant data keys. Each tenant's key lives in the tenant-owned table `tenant_keys` (`tenant_id`, `wrapped_key`, `wrap_nonce`, `master_key_version`, `created_at`), wrapped under `CREDENTIALS_MASTER_KEY`. The tenant's credentials end up sealed under it: new ones from #1060 on, existing ones after #1062's re-encryption. Deleting a tenant's key row is the crypto-shred that makes its secrets unrecoverable. That holds only if no backup that outlives the deletion still contains the wrapped key. The master key is never backed up (`deploy/README.md:139-144`).

Today the daily backup `deploy/systemd/scripts/semprec-backup.sh` works like this:

- It dumps the whole database into one custom dump (`:46-47`).
- It snapshots that dump together with the two blob directories (`:50`).
- It keeps snapshots with `restic forget --keep-daily 14 --keep-weekly 8 --keep-monthly 12 --prune` (`:51`).

So a wrapped key would survive in the repository for up to 12 months. The monthly restore test `deploy/systemd/scripts/semprec-restore-test.sh` restores `latest` with no path filter (`:127`), runs `pg_restore` (`:145-151`), and checks the items, doc snapshots and blobs (`:153-212`). It reports a failed step by passing a check name to the data-layer CLI, which accepts only the names in `RESTORE_TEST_FAILED_CHECKS` (`backend/packages/data/src/observability/restoreTestResultArgs.ts:6-18`).

The decision, recorded in #1031's ADR: `tenant_keys` data is excluded from the long-retention dump and backed up separately with 7-day retention. A deleted tenant's secrets therefore leave the backup repository within about a week, even for someone who holds the master key, while the content itself follows the existing 12-month retention.

Two consequences, documented by this issue:

- **Disaster recovery needs both halves.** A recovery restores a main snapshot and a key snapshot. A main snapshot older than the oldest key snapshot cannot open its tenants' credentials, and those users reconnect their mailboxes and MCP servers.
- **Older snapshots still hold tenant zero's key.** Main snapshots taken between #1031's deploy and this one contain tenant zero's wrapped key inside the dump until they age out. No other tenant can exist before go-live, which depends on this issue.

## Task

Load `io-hardening` (backup I/O and failure paths) and `error-handling`.

1. **`semprec-backup.sh`**
   - Add `--exclude-table-data=public.tenant_keys` to the main `pg_dump`. The table's schema stays in the dump.
   - After the main dump, write a second custom dump with `pg_dump --format=custom --data-only --table=public.tenant_keys` to `/var/backups/semprec/tenant-keys.dump`. Use the same temporary-file-then-`mv` pattern and clean the partial file on exit.
     - Taking it after the main dump means every credential in the main dump has its key in the key dump, because keys are only ever created or deleted, never updated.
     - A failing key dump fails the run before any `restic` call.
   - Run `restic backup` twice:
     - the existing main snapshot, unchanged and without the key dump;
     - a separate snapshot of the key dump alone.
   - Apply retention per kind:
     - `restic forget --path /var/backups/semprec/postgres.dump --keep-daily 14 --keep-weekly 8 --keep-monthly 12` for the main snapshots, which also matches the existing untagged ones;
     - `restic forget --path /var/backups/semprec/tenant-keys.dump --keep-within 7d` for the key snapshots;
     - then one `restic prune`.
   - The forgets run only after both backups succeed.
2. **`semprec-restore-test.sh`**
   - Restore the main snapshot with `restic restore latest --path /var/backups/semprec/postgres.dump`. A bare `latest` would now pick whichever snapshot kind ran last.
   - After `pg_restore`, add check `tenantKeysExcluded`: `SELECT count(*) FROM tenant_keys` must be `0`.
   - Then add check `tenantKeysRestore`:
     - restore the newest key snapshot with `restic restore latest --path /var/backups/semprec/tenant-keys.dump` into the same work directory;
     - require a non-empty key dump;
     - restore it with `pg_restore --data-only --exit-on-error --no-owner --no-privileges` into the disposable database. The foreign key to `tenants` then proves every key belongs to a restored tenant.
   - Run both checks after `docSnapshotsState` and before `blobObjects`.
   - The test never needs the master key and never decrypts anything.
3. **Check names.** Add `tenantKeysExcluded` and `tenantKeysRestore`, in run order, to `RESTORE_TEST_FAILED_CHECKS`, and extend `backend/packages/data/src/__tests__/restoreTestResultArgs.unit.test.ts`.
4. **Hermetic tests**
   - `semprec-backup.test.sh`: the docker mock returns different content for the key dump. Assert:
     - both `pg_dump` command lines;
     - both `restic backup` lines, with the key dump absent from the main one;
     - both `forget` lines and the single `prune` after them.

     Add failure cases for the key dump and for the key snapshot.
   - `semprec-restore-test.test.sh`: the restic mock honours `--path`, and the docker mock answers the new query and the second `pg_restore`. Add `assert_failure` cases for both new checks, and assert that each `restic restore` names its `--path`.
5. **`deploy/README.md`**: in "Encrypted off-site backups" and "Monthly restore test" (`:128-169`), describe:
   - the two dumps and two retention policies;
   - the 7-day crypto-shred bound, measured from the last backup that still held a deleted tenant's key;
   - that retention is measured relative to the newest key snapshot, so it stops advancing while backups do not run;
   - the recovery order (main dump, then the key dump data-only);
   - the disaster-recovery consequence and the older main snapshots that still hold tenant zero's key (see Context).

## Scope

### In scope
- Excluding `tenant_keys` data from the main dump.
- The separate key dump and snapshot with 7-day retention.
- Path-filtered restores and the two new restore-test checks.
- The documentation.

### Out of scope
- Replaying recorded deletions after a restore (#1078, which builds on these scripts).
- Deleting a tenant's key row (#1049).
- Per-service environment files and the backup unit's environment (#996).
- Any change to blob backup or main retention.
- Rewriting existing snapshots.
- Decrypting credentials in the restore test.

## Acceptance criteria

**Backup** (script test: `bash deploy/systemd/scripts/semprec-backup.test.sh`)
- A successful run records:
  - a main `pg_dump` with `--exclude-table-data=public.tenant_keys`;
  - a key `pg_dump` with `--data-only --table=public.tenant_keys`, written to `/var/backups/semprec/tenant-keys.dump`;
  - a main `restic backup` of the main dump and both blob directories, without the key dump;
  - a separate `restic backup` of the key dump alone;
  - `forget --path …/postgres.dump --keep-daily 14 --keep-weekly 8 --keep-monthly 12`, then `forget --path …/tenant-keys.dump --keep-within 7d`, then one `prune`.
- A failing key dump: the run exits non-zero, no `restic` command runs and no partial `tenant-keys.dump.tmp` remains.
- A failing key `restic backup`: the run exits non-zero and no `forget` runs.

**Restore test** (script test: `bash deploy/systemd/scripts/semprec-restore-test.test.sh`)
- A valid fixture passes. Its commands show two path-filtered `restic restore latest` calls and a data-only `pg_restore` of the key dump.
- A restored main database with any `tenant_keys` row fails at `tenantKeysExcluded`. A missing or unrestorable key dump fails at `tenantKeysRestore`. Each failure records exactly one result, pings `/fail` once and leaves no disposable state.

**Check names** (unit)
- `parseRestoreTestResultArgs(["failed", "<id>", "tenantKeysExcluded"])` and the same with `"tenantKeysRestore"` both parse.
