### Requirement gh-1792: [sleep 05/13] Resolve planned sleep nights in the tenant's timezone

#### Context

Model tier rationale: One pure function with defined inputs and outputs and existing daylight-saving fixtures, but the plan, exception and wall-clock rules are subtle and four later features call it directly.

A "night" is identified by the calendar date of the evening it starts (`2026-10-16` is the Friday night into Saturday). The plan that applies to a night is the plan whose `wakeDays` contain the weekday of the following morning. Today nothing computes this: the sleep databases exist (#1776) but no code turns plans, exceptions and settings into concrete times, and the building blocks live elsewhere: `getSystemTimezone` (`backend/packages/data/src/systemSettings.ts`, default Europe/Prague), `assertValidTimezone` (`backend/packages/data/src/timezone.ts`), the shared calendar time module `backend/packages/data/src/calendarTime.ts` from #1418, and the daylight-saving rule of `scheduler/nextFireAt.ts` (a non-existent wall-clock time moves forward, an ambiguous one takes the earlier occurrence).

This issue adds the pure resolver that turns stored sleep data into planned nights in the tenant's time zone. Callers read the rows and pass them in: the HTTP route (#1809), the calendar timeline (#1806), holding push delivery inside the sleep window (#1794) and expanding a night reference in an agent turn (#1853); the agent tools and the iOS client get the same result through the route.

Decisions:
- `durationMinutes` is the difference of the wall-clock times (bedtime to wake time as shown on a clock), not elapsed time, so a night that gains or loses an hour at a daylight-saving change keeps its planned length (the night of 24 October 2026 in Europe/Prague is 510, not 570). Real instants are in `bedAt` and `wakeAt`. When the wake time is not after the bedtime, the duration is 0.
- The wake time is always on the day after `night`; a bedtime before 12:00 is after midnight (on the day after `night`), a bedtime from 12:00 belongs to the evening of `night`.
- A night with no plan and no exception is omitted. A night with an exception but no plan uses the base 23:00 bedtime, 07:00 wake time and `alarm` false, with `planId` and `planName` null.
- The resolver always computes nights, also when the sleep plan is switched off; callers decide what to do with `enabled`.

#### Task

Load `testing`.

1. Add `backend/packages/data/src/sleep/resolveSleepNights.ts` exporting `resolveSleepNights({ settings, plans, nights, from, to, timezone })`, pure and without I/O. `settings` carries `prepReminder` and `prepReminderMinutes`; `plans` are `{ id, name, wakeDays, bedTime, wakeTime, alarm, position }` (non-deleted only); `nights` are exception items `{ night, bedTime, wakeTime, alarm }` with nullable fields; `from` and `to` are `YYYY-MM-DD` and inclusive; an invalid date, an invalid zone or `from > to` throws `ValidationError`. Export it and its input and output types from `backend/packages/data/src/index.ts`.
2. For each date in the range, in ascending order: take `wakeDay` as the weekday (`mon`..`sun`) of `night + 1 day`; the plan is the first plan, ordered by `position` and then by `id`, whose `wakeDays` contain it. Exception fields that are not null override the plan's fields; an exception with all fields null changes nothing.
3. Each returned night is `{ night, planId, planName, bedTime, wakeTime, alarm, changed, bedAt, wakeAt, durationMinutes, prepReminderAt }`. `changed` is true when the exception has at least one non-null field. `bedAt` is `night` plus `bedTime` when `bedTime` is 12:00 or later, otherwise the next day plus `bedTime`; `wakeAt` is the next day plus `wakeTime`; both are instants rendered as ISO strings with the zone's offset, converted with `calendarTime.ts` (`wallClockToInstant`). `prepReminderAt` is `bedAt` minus `prepReminderMinutes`, or null when `prepReminder` is false.
4. Tests with fixed data in Europe/Prague: `2026-10-16` resolves to the weekend plan 00:00 to 08:30, alarm false, `bedAt` `2026-10-17T00:00:00+02:00`, `wakeAt` `2026-10-17T08:30:00+02:00`, 510 minutes, `prepReminderAt` `2026-10-16T23:30:00+02:00`; `2026-10-15` resolves to the weekday plan 23:00 to 06:45, alarm true, 465 minutes; an exception `{ wakeTime: "07:30" }` on `2026-10-16` keeps the plan's bedtime and has `changed` true; a night without plan and exception is omitted; an exception `{ bedTime: "22:00" }` without a plan gives 22:00 to 07:00 with null `planId` and `planName`; `2026-10-24` gives `wakeAt` `2026-10-25T08:30:00+01:00` with 510 minutes; `2027-03-27` gives `wakeAt` `2027-03-28T08:30:00+02:00`; a wake time of 02:30 on 28 March 2027 resolves exactly as `nextFireAt` resolves that wall-clock time (the test pins the result); two plans containing the same day resolve to the lower `position`, ties by lower `id`; a plan with `wakeDays` `[]` never matches.

- When `2026-10-15` is resolved, then the weekday plan applies with 465 minutes and alarm true.

- When the range crosses the end of daylight saving (`2026-10-24`), then `wakeAt` carries the `+01:00` offset and the duration stays 510.
- When two plans contain the same day, then the one with the lower `position` (then lower `id`) wins.

### Requirement gh-1794: [sleep 06/13] Hold push delivery inside the user's sleep window

#### Context

Model tier rationale: This changes when every push notification is sent, in the hottest delivery path, with deferred re-enqueue semantics, failure fallbacks and exactly-once delivery that depend on the job-key behavior of the queue, so a mistake drops or duplicates notifications.

Semprec sends every notification to all of the user's push registrations immediately. `handleNotificationFanoutTask` (`backend/packages/data/src/notifications/notificationFanoutJob.ts`) loads the notification, calls `claimPushDeliveryTargets` (rows in `push_deliveries`, the durable exactly-once key per notification and registration) and sends through the web push and APNs adapters. `enqueueNotificationFanout` enqueues the core task `notificationFanout` with `jobKey` `notification-fanout:<notificationId>` and `jobKeyMode: "preserve_run_at"`. The server knows nothing about sleep. With the sleep plan in place the user can ask Semp to stay quiet while asleep: the sleep window of a night is the time from its bedtime to its wake time, as resolved by #1792 (plan, exception and the tenant's time zone), and it applies only while the sleep plan is on, also for a night without an alarm.

This issue holds pushes inside that window and sends them at wake time. It builds on the notification category map (#1440) and the preference-aware fan-out (#1443), on the night resolver (#1792) and on the APNs chain (#1445); the APNs work that follows in the same file (#1829, #1831, #1826) goes after it. The iOS side (not moving local notifications into the window) is the contract written into #1838; the alarm and the bedtime reminder are local and are not affected here.

Decisions:
- Hold, do not send silently: a held notification keeps its row and its realtime frame at once (an open app shows it), and only the push is postponed. A quiet APNs variant (`interruption-level: passive`) is not used, because web push has no equivalent.
- The exception is the notification category `approvals` of the kind-to-category map (#1440): approval pushes are never held. No second constant of kinds is added.
- A later wake time (an exception written after the hold) is honored when the deferred job runs, because the window is checked again then. An earlier wake time does not send earlier; the push waits for the originally scheduled time.
- A failure to resolve the window or to read the sleep data never drops a push: it is sent immediately and the failure is logged without notification content.

#### Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Add `backend/packages/data/src/sleep/sleepMuteWindow.ts` exporting `findSleepMuteUntil(client, now)`: read the settings, plans and exceptions of the tenant, resolve the nights from yesterday to today in the tenant's time zone with `resolveSleepNights`, and return the latest `wakeAt` of a night whose window contains `now` (bedtime inclusive, wake time exclusive) when `enabled` and `muteSemp` are both true; otherwise `null`. If the settings item does not exist, return `null`.
2. In `handleNotificationFanoutTask`, after the preference filter of #1443 and before `claimPushDeliveryTargets`: unless the notification's kind belongs to category `approvals`, call `findSleepMuteUntil`. When it returns a time, enqueue the same `notificationFanout` task with payload `{ notificationId }`, `jobKey` `notification-fanout-deferred:<notificationId>:<wakeAt ISO>`, `jobKeyMode: "preserve_run_at"`, `maxAttempts` 10 and `runAt` equal to the returned time, and return without claiming or sending. When it returns `null` or throws, continue as today (on a throw, log the notification id and error class only).
3. When the deferred job runs, the same check applies again: a later wake time defers once more; otherwise the push is sent through the existing claim and send path, so `push_deliveries` rows are created only at the real send and a registration never receives a second delivery.
4. Give the handler an injectable clock (an optional `now` function in its dependencies) for tests; production uses the real time.
5. Tests with a fixed clock and the tenant's time zone, on a real database: a notification created at `2026-10-17T02:00:00+02:00` during the night `2026-10-16` (00:00 to 08:30) is held and its deferred job is scheduled for 08:30, with the notification row and realtime frame present and no `push_deliveries` row; the deferred job at 08:30 sends once; with `muteSemp` false or `enabled` false the push goes out at once; an exception `wakeTime` `09:00` written after the hold makes the 08:30 run defer to 09:00; a notification at 23:45 before a midnight bedtime is sent at once; an `approval_pending` notification at 02:00 is sent at once; a failing sleep read sends at once and logs without content; running the original job twice produces one deferred job.

- When a held notification is delivered, then each registration receives exactly one push.

### Requirement gh-1710: [links 10/12] Invalidate a project's items when its area or company changes

#### Context

Model tier rationale: One queued fan-out job on an existing hook and invalidation pattern, bounded by batching, with the main risk being unbounded project sizes and tenant lane use.

An item's derived area and an event's derived company live on its project, so changing a project's area or company changes what every item in that project shows, yet none of those items is written. Clients that hold those items would keep showing the old value until something else refreshed them. This issue announces the change to all affected items.

Today relation edge writes publish no invalidations of their own, and #1621 makes them publish one for each of the two items the edge joins, which here are the project and the area or company, but not for the items that merely depend on the project. #1530 adds the hook that runs after an edge is written or deleted. Background fan-outs run as queued tasks in per-tenant lanes (`rollup/recompute.ts` shows the pattern with `tenantLane`), in batches per `docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`. #1595 defines which databases depend on a project (its configuration list).

Decisions:

- Invalidation is thin: one item invalidation per affected item, sent after the batch commits, as other item writes do; clients refetch.
- Affected items are every live item related to the project through the configured project properties (tasks, events, files, health records).
- The job key is per project so several quick changes collapse into one fan-out.

Shared-file ordering: this issue also waits for #1707 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

Load `state-writes` and `testing`.

1. Queue: add the task `derivedValuesInvalidate` (payload `{ projectItemId }`) to `CORE_TASK_NAMES`, `CORE_TASK_AFFINITY` (`api`) and `TASK_TENANCY` (`tenant`) in `packages/queue/src/index.ts`, and its handler to the task list in `packages/data/src/worker.ts`.
2. Add `backend/packages/data/src/derived/projectDerivedValueHook.ts` (new): the edge-changed hook from #1530, registered in `domainWriteHooks.ts`. When an edge is created or deleted on the relation definition behind `Projects.area` or `Projects.company` (either side), it enqueues `derivedValuesInvalidate` for the project item with `enqueueJob` in the same transaction: queue name `tenantLane("derived-values-invalidate")`, job key `derived-values-invalidate:<projectItemId>`, a small `maxAttempts`.
3. Add `backend/packages/data/src/derived/projectDerivedValueInvalidation.ts` with the handler. It pages through the project's related items in batches of a fixed size (keyset on item id, one committed transaction per batch, per the chunked-transaction ADR), skipping trashed items, and after each batch's commit sends `notifyInvalidation` (scope `item`, op `update`, with the item's `databaseId`, `itemId` and current `updatedAt`) for each. A trashed or missing project sends nothing. A rerun is harmless.
4. Tests: changing a project's area enqueues one job and, once it runs, announces every task, event, file and health record of the project and nothing else; a project with more items than one batch is fully covered; two quick changes collapse to one job; changing the company announces the project's events (and the others harmlessly); a trashed project announces nothing; the job for one tenant never touches another tenant's items; a failing batch retries without announcing items twice in a way that matters (announcements are idempotent refetch triggers).

### Requirement gh-1719: [calendar-reminders 02/04] Compute reminder fire times in the tenant time zone

#### Context

Model tier rationale: One pure function over the shared calendar time module with a clear rule table and existing time-zone fixtures, but daylight-saving and all-day edge cases make the exact semantics load-bearing for two later issues.

Reminders for Events and Tasks need one definition of "when does this fire". Today no such definition exists: `Tasks.notifications` is a checkbox with no behavior (`backend/packages/data/src/seed/seedTenDatabases.ts`), Events have no reminder properties, and the notification system (`backend/packages/data/src/notifications/notify.ts`) only knows system alerts. #1416 adds the Event fields and #1714 guarantees their values are valid. The calendar time module from #1418 (`backend/packages/data/src/calendarTime.ts`) converts wall-clock dates and times to instants in the tenant's time zone. The calendars database from #1600 carries a per-calendar `notify` switch.

This issue adds the single pure function that turns one item into a fire instant (or "no reminder"). #1858 calls it to build a feed for the phone's local scheduler, and any future server-side push would call the same function.

Rules, as product behavior:
- A timed Event fires at its start minus `travelMinutes` minus `alertMinutes`.
- An all-day Event (no `timeFrom`) fires at 09:00 of its first day minus `alertMinutes`; with 1 day before it fires at 09:00 the previous day, with 15 minutes at 08:45. `travelMinutes` is ignored for all-day Events.
- A Task with `notifications` on fires at its `timeFrom`; without a time, at 09:00 of its `date`. A Task has no alert offset.
- A birthday entry fires at 09:00 of its date. A holiday entry fires only when its calendar's `notify` is on.
- Nothing fires for: an item in the trash, a Task whose status is `done` or `wontDo`, a cancelled occurrence, or an item whose calendar has `notify` false. A hidden calendar still fires; only `notify` mutes.
- Wall-clock to instant follows the daylight-saving rules of #1418.

Decisions:
- The 09:00 all-day hour is a fixed constant defined here, `ALL_DAY_REMINDER_HOUR = 9`; there is no setting for it.
- A Task carried over to a later day (by #1884) reminds only on its stored `date`, not every day. Reason: a carried-over task is already visible in Today as "moved from ...", so a daily reminder would be redundant.
- The system Tasks calendar's `notify` flag never mutes Tasks; `Tasks.notifications` is the only switch for a Task. Reason: the Tasks calendar is seeded with `notify` false by default and would otherwise silence every task reminder.

#### Task

Load `testing`.

1. Create `backend/packages/data/src/calendar/reminderFireTime.ts` exporting `ALL_DAY_REMINDER_HOUR` and a pure function `computeReminderFireAt(input, zone)` returning an ISO instant string or `null`. `input` is a discriminated union by `kind`: `event` (`date`, `timeFrom?`, `alertMinutes?`, `travelMinutes?`), `task` (`date`, `timeFrom?`, `notifications`, `status`), `birthday` (`date`), `holiday` (`date`), each with `calendarNotify: boolean`, `trashed: boolean` and `cancelled: boolean`. It uses `wallClockToInstant` from `calendarTime.ts`.
2. Export the reason a reminder is suppressed through a second function `reminderSuppression(input)` returning a string code or `null`, so tests and later callers can tell "no alert set" from "muted".
3. Tests with a fixed zone Europe/Prague: a meeting at 10:00 with `alertMinutes` 15 and `travelMinutes` 30 fires at 09:15 local; an all-day Event with `alertMinutes` 1440 fires at 09:00 the previous day, with 15 at 08:45; a Task with notifications on and `timeFrom` 14:00 fires at 14:00, without a time at 09:00; trashed, `done`, cancelled and `calendarNotify` false return `null`; a reminder across 29 March 2026 moves forward and across 25 October 2026 resolves to one instant.
