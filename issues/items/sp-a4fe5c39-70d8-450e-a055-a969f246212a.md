## Context

Model tier rationale: Changes how one calendar Event's push job is serialised and how every adapter's create path stays idempotent, with a lease on the push state row, a requeue protocol across graphile-worker job keys, and a duplicate branch that trashes Events.

Local review of PR #2089 (feat/internet-accounts @ 7d93041ef), findings 1, 2, 4 and 13, verified against the code:

- **Graph create transactionId from field content** (`adapters/graph/graphEventMapping.ts` `graphTransactionIdOf`, used by `graphCalendarAdapter.ts` `putEvent`). Two local Events with equal fields in one calendar get the same `transactionId`; when Graph answers the second create with the first Event, `eventPushJob.ts` `createRemote` finds the first local Event holding that remote id, takes it for a sync duplicate and trashes it (`deleteEventRemoteStates` + `itemDeleteWithClient`).
- **Two push jobs of one Event can run together.** `enqueueCalendarEventPush` sets a job key but no lane; a keyed re-enqueue of a running job clears its key and adds a new job (`@alldots/queue`), and the job reads its plan unlocked. A newer edit can then be lost on a 412 merge, or one Event created twice at the provider.
- **Google and CalDAV creates are not idempotent.** Google inserts without an id; CalDAV writes a random resource name (and a random UID without `icalUid`). A lost answer, or a `CalendarAccountSyncBusyError` while storing the result, retries the create and makes a second provider Event.
- **The stored base snapshot is cast, not parsed** (`eventPushJob.ts` `baseFieldsOf`: `as unknown as RemoteEventFields`).

Decisions:

- `PutRemoteEventInput.createKey`: the local Event's id on every create the push makes.
- Graph: `transactionId` from calendar, `createKey` and fields. Graph does not document what it answers to a repeated `transactionId`; keeping the fields in it means a repeat may only ever return an Event with the same fields, never an older version.
- Google: the event id is base32hex of a hash of calendar, `createKey` and a generation (0–7). A 409 with a live event at that id writes the fields onto it (`PATCH`, `If-Match`); a cancelled one moves to the next generation (Google keeps deleted ids); a 409 for an id Google does not have stays the refusal it is today.
- CalDAV: the resource name (and, without `icalUid`, the UID) from a hash of `createKey`; a create's 412 there reads the resource and replaces it with the fields (`If-Match`).
- The duplicate branch trashes another local Event holding the created remote id only when it has no `calendar_event_push_state` row (the sync made it and nothing here changed it); otherwise the push is `conflict` and both Events stay.
- One push job per Event: `calendar_event_push_state.lease_id`/`lease_until` (baseline edited in place). The prologue claims a pending row whose lease is free or expired (adapter deadline + 8 min); a job finding it held re-enqueues the Event's push with `runAt` the lease's end and returns `deferred`; the holder releases in `finally` and, when a newer revision is pending, enqueues it at once. A per-Event queue lane was rejected: it leaves one graphile queue row per Event ever pushed.
- `baseFieldsOf` parses with the sync's fields schema (exported from `calendarSyncApply.ts`); an invalid stored base is an unexpected failure of the push.

## Acceptance criteria

- A create whose answer was lost, repeated after a local edit, leaves one provider Event with the edited fields, mapped to the local Event (job, fake provider).
- A pass that imports the created Event between the write and its store: its Event is trashed, ours kept. A provider answer naming the remote id another local Event with a push state holds: that Event and its remote state are untouched, the push is `conflict`.
- A second push job of an Event while one runs returns `deferred` and its job waits; when the first ends with a newer revision pending, the job is due at once and pushes it as an update; two provider writes in total.
- A stored base with fields outside the contract fails the push before any provider write.
- Graph: same Event and fields repeat the `transactionId`; another Event with equal fields, or the same Event with changed fields, do not. Google: a deterministic base32hex id; a 409 on a cancelled event moves to the next id, on a live one patches it with `If-Match`. CalDAV: a repeated create of one Event writes onto its first resource (one new resource, new fields); another Event gets another resource and UID.
- Each new test fails without its fix; the existing calendar sync, push, invitation, notification, tenancy and adapter tests stay green.
