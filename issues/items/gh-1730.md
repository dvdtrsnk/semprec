**Blocked by:** #1423, #1683
**Model tier:** medium

## Context

Model tier rationale: A single pure derivation plus a static metadata flag exposed on two existing projections, covered by table-driven tests, with no new migration or authorization contract.

Product behavior: the approval screen marks an action "irreversible" only when it truly cannot be undone. Deleting an item moves it to the trash for 30 days, so it is not marked irreversible; deleting a property is. Actions that send something out or end a value link are marked as such.

Today `OPERATION_METADATA` in `backend/packages/shared/src/genericOperations/capabilities.ts` has no notion of reversibility. `item.delete` is a soft delete (`items.deleted_at`, `item.restore`, purge after 30 days in `trash/purgeExpiredTrash.ts`) and `database.archive` has `database.restore`. There is no restore for `property.delete`, `view.delete` or `relation.delete`; the schema has no soft-delete marker for properties, views or relations. For MCP tools, the only signal is the risk class.

This issue builds on #1423 (the closed `RiskClass` set) and #1683 (the description whose `restorableDays` the clients show for reversible deletes). #1773 puts the risk level into the push body.

Decision: `item.delete` and `database.archive` are reversible; `property.delete`, `view.delete` and `relation.delete` are not; an MCP tool with class `destructive` is irreversible.

Decision: the request view returns `riskLevel` as a closed key (`irreversible | outbound | breaksLink | write`); labels are client catalog strings, not stored text.

## Task

Load `testing`.

1. Add `reversible: boolean` to `OperationMetadata` and set it per operation as in the Decision above (all non-approval operations `true`).
2. Export a pure function `deriveApprovalRiskLevel({riskClass, operationName?})` from `capabilities.ts` (or a sibling file in the same folder): `breaksLink` class gives `breaksLink`, `outbound` gives `outbound`, `destructive` gives `irreversible` unless the operation is flagged `reversible`, anything else (`write`, `read`, `unclassified`, reversible destructive) gives `write`.
3. Add `riskLevel` to the queue entry and the decision view in `approvalRequestsQueue.ts`, computed from the request's `riskClass` and, for generic operations, the operation name in the payload.
4. Cover with a table-driven unit test over all five approval-gated operations, an MCP `destructive` tool, an `outbound` tool and a `breaksLink` request.

### Out of scope

## Acceptance criteria

- When an `item.delete` request is listed, `riskLevel` is `write`; when a `property.delete` request is listed, it is `irreversible`.
- A `database.archive` request has `riskLevel` `write`; `view.delete` and `relation.delete` are `irreversible`.
- A request with class `breaksLink` has `riskLevel` `breaksLink`; one with class `outbound` has `outbound`.
- An MCP request with class `destructive` has `riskLevel` `irreversible`; `unclassified` gives `write`.
- All previous fields of the responses are unchanged.
