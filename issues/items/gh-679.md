## Context

`createItemWithClient` in `backend/packages/data/src/chokePoint/itemWrites.ts` (lines 145-189) calls `itemsStore.insertItem` (line 172) and then, unconditionally, `triggerOnItemEventHeartbeats(client, databaseId, "create", item.id, ...)` (line 177) and `runAfterCommit(... notifyInvalidation({ op: "create" ... }))` (lines 178-187). `insertItem` (`backend/packages/data/src/chokePoint/itemsStore.ts`, lines 58-107) implements Idempotency-Key replay: a repeat call with an already-reserved key returns the row the first call created (line 93) and inserts nothing. The caller cannot tell the two outcomes apart, so every replay — a client retrying `POST /api/items` after a timeout, Journal's `getOrCreateJournalItem` on every write to an existing day, mail ingest converging on a known message — re-fires the `onItemEvent` `create` heartbeats (e.g. the Inbox tick, `semprec.tick`, or the person-linking action) and re-announces an `op: 'create'` invalidation for an item that already existed. Only the archived-database replay path (`assertDatabaseWritableForCreate`, lines 103-121, returning at line 151) already skips both.

This issue depends on C11 because both edit `itemWrites.ts` (C11 adds the Tasks hook to `updateItemWithClient`; this issue changes `createItemWithClient`).

## Task

1. `itemsStore.ts`: the current body of `insertItem` becomes an exported `insertItemWithReplay(client, input): Promise<{ item: ItemRow; created: boolean }>` — `created: false` on the reused-key branch (line 93), `true` after the `INSERT` (line 106) — and `insertItem` keeps its signature as a one-line wrapper returning `.item` (its ~25 direct callers in seeds and tests stay untouched). The doc comment (lines 52-57) moves to `insertItemWithReplay` and states the flag.
2. `createItemWithClient`: call `insertItemWithReplay`; when `created` is `false`, return `item` immediately — no `triggerOnItemEventHeartbeats`, no `notifyInvalidation`; when `true`, the existing side effects run unchanged. Update the doc comment.
3. Tests in `backend/packages/data/src/__tests__/itemWrites.test.ts` (integration): create an item with an `Idempotency-Key` on a database with an enabled `onItemEvent create` heartbeat (`createHeartbeat`, see `scheduler.test.ts`'s pattern) and count `graphile_worker` jobs for its fire task; a second `createItem` with the same key returns the same id and the job count is unchanged; with `setInvalidationHook` capturing events, the replay emits no `op: 'create'` event while the first call emitted exactly one.

## Touches

## Scope

### In scope
- The `created` flag on `insertItem` and the gated create side effects in `createItemWithClient`, plus tests.

### Out of scope
- Releasing a reservation whose item is missing or trashed (sibling issue C3, which also edits `insertItem`).
- Replay handling of relation or view writes.

## Acceptance criteria

- When `createItemWithClient` is called with an idempotency key whose item already exists, it returns that item and no heartbeat job is enqueued and no `create` invalidation is announced.
- When the key is new, the item is created and exactly one `create` heartbeat trigger and one `create` invalidation fire, as before.
