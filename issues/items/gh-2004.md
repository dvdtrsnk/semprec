## Context

Model tier rationale: This parses untrusted feed content, converts time zones into the tenant's wall-clock model and keeps a system-owned database in sync by upsert and soft delete in chunked transactions, so a mistake corrupts or loses the stored events of every subscription.

#1960 downloads each subscription calendar's feed on a schedule and hands a changed body to a consumer registered with `registerCalendarFeedConsumer`; no consumer is registered yet, so a downloaded feed is only recorded as fetched. #1962 adds the read-only `subscribedEvents` database (system-owned by the calendar module) where the events of a feed are stored. This issue provides the consumer that turns a feed body into stored subscribed events. Time conversion uses the calendar time module of #1418 (the tenant's wall-clock model). #2005 shows the stored rows in the calendar timeline, and #1966 adds recurrence on top of this importer.

Decisions:
- The feed parser is the library `ical.js`, added as an exact pinned 2.x version dependency of `@semprec/data` (the backend has no iCalendar parser today); the parse runs on the already size-capped body from #1960, inside a try/catch that turns a malformed feed into a recorded failure (the consumer throws, so #1960 keeps its validators) without changing stored events.
- Timed events: DTSTART and DTEND (including `TZID` and UTC `Z` forms) are converted to the tenant's wall-clock time with the module from #1418; the original zone name is kept in `timeZone`. Floating times (no zone) are taken as already in the tenant's wall-clock time.
- All-day events (`VALUE=DATE`): `allDay` is true, `startsAt` is the date and `endsAt` is the inclusive last day (the feed's exclusive DTEND minus one day), or null for a single day.
- Recurrence is not interpreted here: components with `RECURRENCE-ID` are skipped, and a component with `RRULE` is stored as a single event at its own start. #1966 replaces that.
- Upsert key is `(calendar, uid)`. An unchanged event is not rewritten (no `updated_at` change, no invalidation).
- A UID that disappears from the feed is moved to the trash through the choke point (soft delete), never deleted permanently; the existing 30-day purge removes it, and a UID that reappears later is created as a new item.
- Import runs in chunked transactions for large feeds (`docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`).
- All writes use the choke point with the system owner process `calendar` (`systemOwnerProcess`), so the generic ownership check keeps refusing user, agent and `/mcp` writes.

## Task

Load `state-writes`, `io-hardening`, `error-handling`, `canonical-keys` and `testing`.

1. Add `ical.js` (exact pinned 2.x version) to `backend/packages/data/package.json` and update the workspace lockfile.
2. Implement the feed consumer in `backend/packages/data/src/calendar/subscribedEventsImport.ts`: parse the body, convert each `VEVENT` per the decisions above, upsert by `(calendar, uid)` into `subscribedEvents` with the calendar's relation, skip unchanged rows, and soft-delete the live rows of that calendar whose UID is no longer in the feed.
3. Register the consumer with `registerCalendarFeedConsumer` from #1960 at the place where the calendar module registers its process hooks.
4. Tests: a feed with two events creates two items linked to the calendar; a second import of the same feed changes nothing (no `updated_at` change); a feed without one event moves it to the trash and it is restorable; a UID that reappears after that creates a new item; an event `2026-10-20T09:00` in `America/New_York` is stored as wall-clock 15:00 with `timeZone` `America/New_York` for a tenant in `Europe/Prague`; a floating time is stored unchanged; an all-day event keeps its inclusive date range; a malformed or truncated feed leaves stored events unchanged and makes the consumer fail; a `RECURRENCE-ID` component is skipped and an `RRULE` component is stored once.

## Scope

### In scope

- Parsing a downloaded feed, converting its times, and keeping the `subscribedEvents` rows of one calendar in sync (upsert, unchanged skip, soft delete of disappeared events).

### Out of scope

- The `subscribedEvents` database: #1962. Storing the URL: #1925. Downloading and the consumer registry: #1960.
- Showing subscribed events in the calendar timeline: #2005.
- Recurring subscribed events (`RRULE`, `EXDATE`, `RECURRENCE-ID`): #1966.
- Deleting disappeared events permanently; they go to the trash.
- A user-triggered refresh of a feed.

## Acceptance criteria

- A feed with two events creates two `subscribedEvents` items; importing it again changes nothing.
- When an event is removed from the feed, then its item is moved to the trash (restorable for 30 days), not deleted permanently.
- An event at 2026-10-20 09:00 `America/New_York` is stored at wall-clock 15:00 for a tenant whose time zone is `Europe/Prague`, with the original zone kept.
- A malformed or truncated feed does not delete or alter events imported earlier, and the consumer reports a failure.
- A component with `RECURRENCE-ID` is skipped; a component with `RRULE` is stored once at its own start.
- The full backend `pnpm run verify` passes.
