## Context

`convertInBatches` in `backend/packages/data/src/migrationJob/moduleDataMigration.ts` (lines 87-119) is the runner for every manifest-declared module data migration (`ModuleManifest.dataMigrations`, today `backfillTaskTimeProperties` on Tasks from `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts`). Three defects:

1. **Lost concurrent writes.** Each batch runs `SELECT id, properties FROM items ... ORDER BY id ASC LIMIT $2` (lines 96-100) without `FOR UPDATE`, converts in memory, then `UPDATE items SET properties = $3::jsonb` (lines 104-107) — a full replace. A choke-point `updateItemProperties` (`itemsStore.ts`, `properties = properties || $3`) that commits between the batch's read and its write is overwritten with the pre-edit properties.
2. **Rows skipped.** The cursor is the last converted `id` and ids are random UUIDs (`gen_random_uuid()`), so a row inserted while the run is in progress with an `id` below the cursor is never visited. A row whose lock is held by another transaction would, with `SKIP LOCKED`, be skipped for the same reason.
3. **Cursor keyed by database, lock keyed by transition.** Progress lives in `databases.migration_cursor` (one column, migration `0011_module_data_migrations.sql`), while the advisory lock (`lockKey`, line 21) is per `(moduleId, databaseKey, fromVersion, toVersion)`. Two transitions on the same database (e.g. two modules, or `1.0.0→1.1.0` and `1.1.0→1.2.0` declared together) run concurrently and clobber each other's cursor.

Converters are pure functions `(properties) => properties`; `backfillTaskTimeProperties` (`backend/packages/data/src/tasks/deriveTaskTime.ts`, line 17) is idempotent (returns its input unchanged once the derived value is right). Sibling issue C15 of this batch reuses the batch-locking helper this issue introduces for the single-property type migration. Migration rules: `docs/adr/2026-09-10-expand-contract-forward-only-migrations.md`.

## Task

1. New migration `backend/packages/data/src/db/migrations/NNNN_module_migration_progress.sql` (next free ordinal at commit time):

   ```sql
   CREATE TABLE module_migration_progress (
     module_id text NOT NULL, database_key text NOT NULL, from_version text NOT NULL, to_version text NOT NULL,
     pass smallint NOT NULL DEFAULT 1 CHECK (pass IN (1, 2)),
     cursor uuid,
     PRIMARY KEY (module_id, database_key, from_version, to_version)
   );
   GRANT SELECT, INSERT, UPDATE, DELETE ON module_migration_progress TO semprec_side;
   ```

   Header comment: in-progress state of one transition, deleted when its `module_migrations` row is recorded; `databases.migration_cursor` is left in place unused (its removal is a later contract step). The `semprec_side` grant follows `0040_least_privilege_roles.sql`'s side-table convention (`semprec_data` inherits it).
2. New `backend/packages/data/src/migrationJob/itemBatch.ts` exporting `lockItemBatch(client: PoolClient, input: { databaseId: string; afterId: string | null; pageSize: number; skipLocked: boolean }): Promise<Array<{ id: string; properties: Record<string, unknown> }>>` — `SELECT id, properties FROM items WHERE database_id = $1 [AND id > $3] ORDER BY id ASC LIMIT $2 FOR UPDATE [SKIP LOCKED]`. Doc comment: must run inside the caller's transaction; the rows stay locked until it commits.
3. `convertInBatches` becomes two passes over the same loop, keyed by the transition (`readProgress`/`writeProgress` on `module_migration_progress`, upserted by primary key; `readCursor` and the `databases.migration_cursor` writes at lines 70, 112 and 121-127 are removed):
   - pass 1: `lockItemBatch(..., { skipLocked: true })`; for each row, `converter(row.properties)`, then `UPDATE items SET properties = $3::jsonb, updated_at = now() WHERE database_id = $1 AND id = $2 AND properties IS DISTINCT FROM $3::jsonb` — a full replace is safe only because the row is locked for the batch's whole transaction, and the `IS DISTINCT FROM` guard keeps `updated_at` (the `ifVersion` token) untouched on a row the converter left as is; commit and record `{ pass: 1, cursor: lastRow.id }`;
   - pass 2, once pass 1 reaches the end: reset the cursor to `NULL` with `pass = 2` and run the identical loop with `skipLocked: false` (block on a held row instead of skipping) — every row inserted or skipped during pass 1 is visited now, and every already-converted row costs a read only;
   - after pass 2: in one transaction, insert the `module_migrations` row (as today, lines 63-71) and `DELETE FROM module_migration_progress` for the transition. Resuming after a crash continues from the recorded `(pass, cursor)`.
4. `ModuleDataMigrationConverter`'s doc comment states the contract the two-pass design relies on: a converter is idempotent — `converter(converter(p))` deep-equals `converter(p)` — and the second pass is what guarantees every row is visited exactly once in the sense of "converted at least once, rewritten only when the converter changes it".
5. Tests in `backend/packages/data/src/__tests__/moduleDataMigration.test.ts` (integration; keep the existing four cases, adapting the cursor helper at lines 44-48 to `module_migration_progress`): (a) a concurrent `chokePoint.updateItem` on a row of the batch in flight (open a second connection, lock the row with `SELECT ... FOR UPDATE`, start the migration with `pageSize: 1`, apply the choke-point patch and commit while the batch is blocked/skipping) is preserved after the run, and the converter's change is applied too; (b) a row inserted with an id lower than the pass-1 cursor while pass 1 is running (insert it from the converter callback of the first batch) is converted by pass 2; (c) two transitions for the same database key with different `toVersion`s run concurrently and both record their `module_migrations` rows with no leftover `module_migration_progress` rows; (d) a run resumed after a forced failure in pass 2 continues in pass 2 (no pass-1 re-run).

## Scope

### In scope
- The batch lock, the guarded write, the second pass, the transition-keyed progress table and the tests.

### Out of scope
- Dropping `databases.migration_cursor` (contract step, later release).
- The single-property type migration (`propertyTypeMigration.ts`) — sibling issue C15 reuses `lockItemBatch`.
- The migration runner's own advisory lock (`db/migrate.ts`) and `migrationCompatibility.ts` blind spots.

## Acceptance criteria

- When a choke-point update commits on a row while the data migration is running, the update survives and the converter's change is applied to the same row.
- When a row is inserted during the run with an id below the cursor, it is converted before the transition is recorded.
- When two transitions on the same database run concurrently, each records its own `module_migrations` row and neither leaves progress state behind.
- When a run is interrupted, the next run resumes from the recorded pass and cursor and never rewrites a row whose converted shape is already stored (`updated_at` unchanged on such rows).
