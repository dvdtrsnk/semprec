## Context

Model tier rationale: One mechanism (enriching the persisted tool event payloads) across the pi session bridge, the tool composition root and a typed payload parser, with existing fixtures to extend and no new authorization, lifecycle or schema contract.

Every agent tool call is logged in `agent_run_events` as a `tool_use` row and a `tool_result` row (`backend/packages/agent-runtime/src/lifecycleAdapter.ts` persists whatever `toAgentMessage` in `backend/services/semprec-agents/src/piAgentSession.ts` produces). Today `tool_use` carries only `{toolCallId, name, arguments}` and `tool_result` only `{toolCallId, name, result, isError}`. The `name` is the model-facing tool name from `toModelToolName` in `backend/services/semprec-agents/src/agentSessionComposition.ts`: a generic operation `item.patch` becomes `item_patch`, and an MCP tool becomes `mcp_<toolName>` without its server. The server name and registration id are only known when the tools are composed (`createMcpTools`), and are not stored anywhere on the event. A reader of the log therefore cannot tell which generic operation or which MCP registration a step used, or which database or item it touched, without re-deriving it from a lossy name and unvalidated arguments.

This issue records that identity on both events so later readers (run step projection, the per-reply step summary, failed-call detection, guidance drift detection) can rely on it. It changes no table: `agent_run_events.payload` is jsonb. Per the ADR `docs/adr/2026-09-10-typed-rows-at-the-postgres-boundary.md` the payload is typed and mapped at the boundary: this issue adds the typed payload definitions and a parser for them, and readers must use the parser rather than casting.

Decision: `targetDatabaseId` and `targetItemId` are taken only from the tool call arguments (`databaseId` for `database.query` and `item.create`, `itemId` for the item operations) and are absent when the arguments do not name them. They are never parsed out of the model-visible result text. A reader that needs the database of an item-only call resolves it from the item at read time.

Decision: events written before this change have no `operation` or `mcp` fields; the parser returns them as absent and never guesses from `name`.

Builds on nothing. The structured result fields (approval request id, field changes) are added on top of this shape by #1527; the step projection by #1847; failed-call detection by #1890; drift detection by #1629.

## Task

Load `canonical-keys`, `io-hardening` and `testing`.

1. In `backend/packages/agent-runtime/src/types.ts` (or a new `toolEventPayload.ts` next to it, re-exported from `index.ts`), define the typed payloads `ToolUseEventPayload` and `ToolResultEventPayload`. Both carry, in addition to today's fields: optional `operation` (a `GenericOperationName`, dotted, for example `item.patch`), optional `mcp` `{toolRegistrationId, serverItemId, serverName, toolName}`, optional `targetDatabaseId` and `targetItemId` (strings). Exactly one of `operation` and `mcp` is present for a Semprec-composed tool. Export `parseToolEventPayload(kind, payload: unknown)` returning the typed payload or `null` for a payload that does not match (unknown JSON never throws).
2. In `piAgentSession.ts`, extend `PiAgentSessionFactoryOptions` with `toolEventMetadata: ReadonlyMap<string, ToolEventMetadata>` keyed by the model-facing tool name (`ToolEventMetadata` is `{operation}` or `{mcp}`). `toAgentMessage` (or the subscriber around it) adds `operation` / `mcp` to the `tool_use` and `tool_result` it emits, derives `targetDatabaseId` / `targetItemId` from the call arguments, and the `tool_result` repeats the target fields of its `tool_use` (matched on `toolCallId`). A tool name missing from the map produces the same payload as today.
3. In `agentSessionComposition.ts`, build the map from the tools that survive `withUniqueNames`: generic operation tools register `{operation}` (the dotted name from `GENERIC_OPERATION_NAMES`), MCP tools register `{mcp}` from the grant (`mcpToolRegistrationId`, `mcpServerItemId`, `mcpServerName`, `toolName`). Pass the map to `createPiAgentSessionFactory`.
4. Extend the unit tests in `services/semprec-agents/src/__tests__/piAgentSession.unit.test.ts` and `agentSessionComposition.unit.test.ts`, and add a parser unit test: a generic call persists `operation: "item.patch"`; an MCP call persists `mcp` with server name and registration id; target ids come from arguments; a legacy payload parses with the new fields absent; a malformed payload parses to `null`.

## Scope

### In scope

- Recording `operation`, `mcp`, `targetDatabaseId` and `targetItemId` on `tool_use` and `tool_result` payloads, and the typed parser for those payloads.

### Out of scope

- Approval request id and field changes on the result: #1527.
- The shape of the synthetic result written for an interrupted run: #1374.
- Any read endpoint or projection of these events: #1821, #1847.
- Rewriting or backfilling events already stored.
- Dedicated calendar or transcript tools; they would register their own metadata when they exist.

## Acceptance criteria

- When the agent calls the generic operation `item.patch`, then the stored `tool_use` and `tool_result` rows both have `operation` equal to `item.patch`, and `name` stays `item_patch`.
- When the agent calls a granted MCP tool, then both rows carry `mcp.serverName`, `mcp.toolRegistrationId`, `mcp.serverItemId` and `mcp.toolName`, and no `operation`.
- When the call arguments contain `itemId` or `databaseId`, then both rows carry the matching `targetItemId` / `targetDatabaseId`; when they do not, the fields are absent.
- `parseToolEventPayload` returns the typed payload for a new row, the payload with absent optional fields for a row stored before this change, and `null` for a malformed payload.
- Event payload size stays below the existing 1 MiB write bound and the reconstruction of a stored conversation (`piConversationHistory`) still accepts the enriched rows.
