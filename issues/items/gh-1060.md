## Context

Model tier rationale: The sealing change is three specified steps in one function with enumerated test cases.

#1031 gave every tenant a data key in the tenant-owned table `tenant_keys`, wrapped by `CREDENTIALS_MASTER_KEY`. It added:

- `getOrCreateTenantDataKey(client)` (`backend/packages/data/src/credentials/tenantKeysStore.ts`), which resolves the tenant through `app_tenant_default()` and returns `{ tenantId, dataKey }`;
- `sealSecret`/`openSecret` (XChaCha20-Poly1305 with associated data) in `@semprec/credentials`.

#1032 added the `external_credentials.scheme` column (`master` | `tenant`) and made `getDecryptedCredential` open both schemes. A `tenant` row is opened with the tenant's key and the associated data from the module-private `credentialAssociatedData(tenantId, itemId)` in `backend/packages/data/src/credentials/externalCredentialsStore.ts`, built from `semprec:external-credential:v1:<tenantId>:<itemId>`. Every write still seals with secretbox under the master key, with `scheme = 'master'` written explicitly.

This issue switches the write side. Every new or replaced credential gets sealed under its tenant's key and bound to `tenant_id‖item_id`. That makes it unreadable on another row or in another tenant, and shreddable by deleting the key row (#1049).

**Why this waits for #1058.** The release checkpoint confirms that a release containing #1032's dual read runs in production. A one-release rollback from the release that ships this issue therefore lands on code that can open the `tenant` rows it wrote. Without the checkpoint, the previous release could not read them.

The callers are unchanged:

- the proposal confirm path, inside its transaction (`backend/packages/data/src/inbox/proposalActions.ts:283`);
- tests that store on a `Pool` (e.g. `backend/packages/data/src/__tests__/mailSend.test.ts:115`).

`getOrCreateTenantDataKey` works on both: on a `Pool` each statement is auto-committed, and inside a transaction the key creation rolls back with the caller.

## Task

Load `state-writes` and `error-handling`.

1. In `externalCredentialsStore.ts`, `storeCredential` does the following:
   - gets the key with `getOrCreateTenantDataKey(client)`;
   - seals with `sealSecret(input.plaintext, key.dataKey, credentialAssociatedData(key.tenantId, input.itemId))`;
   - inserts `(tenant_id, item_id, credential_type, ciphertext, nonce, key_version, scheme)` with `tenant_id = key.tenantId`, `key_version = 1` and `scheme = 'tenant'`;
   - in `ON CONFLICT (item_id) DO UPDATE`, sets `credential_type`, `ciphertext`, `nonce`, `key_version` and `scheme`.
2. Remove `StoreCredentialInput.keyVersion` (`:34-35`). No caller passes it, and for a `tenant` row the wrapping version lives in `tenant_keys.master_key_version`. Document that `key_version` is not meaningful on `tenant` rows.
3. `getDecryptedCredential` is unchanged.
4. `backend/packages/data/src/__tests__/mcpConnectionFactory.test.ts:236-254` forces a decryption failure by bumping `key_version`, which a `tenant` row ignores. Corrupt one ciphertext byte instead.
5. In `backend/packages/data/src/__tests__/externalCredentialsStore.test.ts`, replace the hand-fabricated `tenant` rows with `storeCredential` where the case is about written rows. Add the cases below.

## Scope

### In scope
- Tenant-key sealing for every new or replaced credential.
- Removing the unused `keyVersion` input.

### Out of scope
- The read path and the `scheme` column (#1032).
- Re-encrypting existing `master` rows (#1062).
- Retiring the `master` scheme and the secretbox functions (#1069).
- Backups (#1064).
- Deleting a tenant's key (#1049).
- Changes to `credential_access_log`.

## Acceptance criteria

All integration. Two-tenant cases use #975's `createTestTenant(pool)`, `createRuntimeRolePool(adminPool, "semprec_data")` and `withTenantTransaction(pool, tenantId, fn)`.

**Writing**
- `storeCredential` in tenant zero writes a row with `scheme = 'tenant'` and `tenant_id` = tenant zero. `getDecryptedCredential` returns the plaintext and writes exactly one `credential_access_log` row.
- Storing over an existing `master` row turns it into a `tenant` row that decrypts to the new plaintext.
- In a tenant without a key, `storeCredential` inside a transaction that then throws leaves neither the credential nor a `tenant_keys` row.
- The MCP-server proposal confirm path with a credential stores a `tenant` row.

**Binding**
- A `tenant` ciphertext written by `storeCredential` for item X, copied onto item Y's row, makes decryption of Y throw.
- Copied onto a row of tenant B, it makes decryption in B's scope throw.

**Callers**
- `connectMcpServer` on a corrupted `tenant` ciphertext rejects with `McpConnectionError` reason `credential_decryption_failed`, and the plaintext appears nowhere in the error.
- The existing mail sync, mail send and MCP suites pass unchanged.
