## Context

Model tier rationale: One shared repository, one domain use case and one shared ViewModel change how an event is created and how a refused create is reported, with commonTest coverage; no exported type, no Swift or Android change.

On production, creating an event in any calendar other than the default fails and the next tap duplicates it. `HttpCalendarRepository.createIn` posts `POST /api/databases/:eventsDb/items` with only `properties`; the server's create hook (`defaultCalendarCreateHook`) links the new Event to the default calendar in the same transaction, and `Events.calendar` is single-valued. The follow-up `PUT /api/items/:id/relations/calendar/:calendarId` then answers 409 `cardinality_violation`. `ApiClient` maps 409 to `FailureKind.REJECTED`, which the new item sheet shows as "Check the title and the time: the end has to come after the start." (`newItem.rejected`). The Event stays in the default calendar, the sheet stays open, and the next submission creates a second Event.

The server already creates atomically: the create body accepts `relations: [{ "propertyKey": "calendar", "targetItemIds": [id] }]`, and the hook writes no default edge when the initial relations name `calendar`. It also honours an `Idempotency-Key` header: a replay of a key returns the stored item without a second create and without reading the body again, and a key used for another database is refused with 409.

Moving an existing event to another calendar happens only through the generic item screen's relation picker (`ItemPickerFlow`), which calls `PUT /api/items/:id/relations/:propertyKey` with `{ "targetItemId" }` (`relation.set`, one transaction replacing the single target). The calendar screens have no calendar picker for an existing event. Other create paths of the repository family (`HttpCalendarCatalogRepository.create`, invitation answers, duplicate, `HttpTaskRepository`, `HttpMeetingRepository`) make no follow-up relation write, or already send relations in the create.

## Task

Load `kmp-shared`, `shared-viewmodel`, `error-handling`, `testing` and `mobile-verify`.

1. Data: `HttpCalendarRepository.create` sends the chosen calendar of an event in the create body's `relations` (`calendar`, one target) and makes no follow-up relation write; an event without a chosen calendar and every task send no `relations`. The task repetition (`PUT /api/tasks/:id/recurrence`) stays as it is.
2. Data and domain: `NewCalendarItem` carries the `submissionKey` of the person's submission, and the create `POST` sends it as the `Idempotency-Key` header.
3. Presentation: `NewCalendarItemViewModel` generates the key once per submission and reuses it when the same form is submitted again after a failure (including a timeout or a network failure). It makes a new key after a successful create, after `NewItemAction.Edited`, and when a submitted form differs from the last one.
4. Domain and presentation: `CreateCalendarItem` answers a `NewCalendarItemOutcome`: `Created(itemId)`, or `BreaksRules` for a form its own checks refuse before the server is asked. The ViewModel shows `FailureKind.REJECTED` (the form message) only for a form the rules refuse; a refusal by the server (400, 409, 422) is an unexpected failure (`failure = null`, the generic message), and other failures keep their `FailureKind`.

## Scope

### In scope

- Creating an event in a chosen calendar in one request, an idempotent create, and the refusal message of the new item sheet.

### Out of scope

- Backend changes.
- A calendar picker for an existing event on the calendar screens (none exists); the generic item picker already replaces the relation atomically.
- Android and Swift: the exported state, actions and effects do not change.

## Acceptance criteria

- Creating an event in a chosen calendar sends exactly one `POST` with `relations` naming that calendar and an `Idempotency-Key`, and no `PUT`.
- Creating an event in the default calendar, or a task, sends no `relations`.
- Submitting the same form again after a failed attempt reuses the key; a new submission after success, after an edit, or with a different form gets a new key.
- A server refusal of the create is not reported as the "check the title and the time" form message; a form the rules refuse still is.
