**Blocked by:** #1482, #1905, #1912
**Model tier:** high

## Context

Model tier rationale: Registers write hooks that lock and rewrite other rows inside the triggering transaction, with lock ordering against concurrent confirm and a new index-backed lookup across every database, so concurrency and cross-database isolation are the main risks.

An open proposal that points at an existing item (the project a task would be created in, a person to link, a company, the page an entry would be appended to) becomes unusable when that item is archived or deleted in the meantime. Nobody notices today: the card stays `proposed` and `confirm` re-checks only the envelope shape and target database. The card should flip to `invalid` at the moment the referenced item changes, in the same transaction, and flip back when the item is restored or un-archived. #1482 defines `invalidReason` and the fixable/final distinction; #1426 defines how a referenced item's state (archived, done, deleted) is evaluated, which this issue reuses; #1601 adds the item delete and restore hooks to the choke point (`registerItemDeleteHook`, `registerItemRestoreHook`, next to the existing `registerItemUpdateHook` in `backend/packages/data/src/chokePoint/hooks.ts`).

Decision: Processing proposals get a system property `referencedItemIds` (an array of item ids; created with the card-state properties, see #1451) holding every item the effective envelope refers to: relation targets of `entityKind: relation` and of relation parts of database envelopes, the page of a `pageContent` envelope, and the targets of any further steps. Every writer of `proposal` writes it from one helper, `referencedItemIdsOf(envelope)`.

Decision: the hooks apply to items of any database (the referenced target can be a project, area, person, company, journal day or a subpage); the lookup uses the existing `items_props_gin` index (`properties @> {"referencedItemIds": [<id>]}`) restricted to the Processing proposals database and status `proposed`. Only `archived` projects (Projects `status = archived`) and deleted items invalidate; a project that is merely `done` stays selectable and keeps open proposals valid (decided by the product owner: a done project is a valid target and nothing is invalidated silently).

Decision: the hook locks matched proposals with `FOR UPDATE SKIP LOCKED`, so it never waits for a confirm that holds the proposal lock first (the opposite lock order would deadlock). A proposal skipped because it is being confirmed right now is not invalidated; that confirm validates its targets through the evaluation from #1426.

Shared-file ordering: this issue also waits for #1905 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `testing` and `error-handling`.

1. Add `backend/packages/data/src/inbox/proposalReferences.ts` with `referencedItemIdsOf(envelope)` and have every writer of `proposal` write `referencedItemIds` with it: the tick's `reviseProposal`/create path and `writeNeedsClarification` (empty array) in `inboxTickAction.ts`, `reviseProposalWithClient` in `proposalActions.ts`, the two transcript card creators in `backend/packages/data/src/transcription/`, and every other function in `proposalActions.ts` that writes `proposal` at the time of implementation (the edit and reset routes, if present). Add `referencedItemIds` to each `allowedSystemKeys`. A test iterates the exported writers and fails if one writes `proposal` without `referencedItemIds`.
2. Add `invalidateProposalsForItem(client, config, itemId, reasonCode)` which finds `proposed` proposals referencing the item, writes `status: "invalid"`, `invalidReason` `{ code, field, itemId, label }` (field = the editor field whose value is that item), and a history entry with `kind: "invalidated"`, in the caller's transaction.
3. Register hooks in `backend/packages/data/src/domainWriteHooks.ts`: an item update hook for Projects that calls it with `targetArchived` when `status` becomes `archived` and, when it leaves `archived`, restores matching `invalid` cards (reason `targetArchived`, same item) to `proposed` after re-validating the envelope; an item delete hook (any database) calling it with `targetDeleted`; an item restore hook (any database) restoring `targetDeleted` cards for that item the same way.
4. The restore step revalidates with `assertValidProposalEnvelope`; a card whose envelope is no longer valid stays `invalid`.
5. Tests: archiving a project turns the open task proposal into `invalid` with `targetArchived`, field `project`, in the same transaction; choosing another project via the edit route returns it to `proposed`; deleting a referenced person gives `targetDeleted`, restoring the person returns the card to `proposed`; a proposal being confirmed (locked by another transaction) is not waited on; a locked (`confirmed`) proposal is untouched; other tenants' proposals are never touched.

## Scope

### In scope

- `referencedItemIds` maintenance by every proposal writer and the update, delete and restore hooks that invalidate and revalidate open proposals.

### Out of scope

- The `invalidReason` shape and the final/fixable distinction (#1482).
- Restoring a deleted source Inbox item (#1604).
- Heartbeat-based detection (Projects and Companies have no `onItemEvent` heartbeats and People's belong to the mail module).
- Marking `done` projects invalid.

## Acceptance criteria

- When a project referenced by an open task proposal is archived, then in the same transaction the proposal is `invalid` with `invalidReason` `{ code: "targetArchived", field: "project" }`.
- When another project is chosen with the edit route, then the card returns to `proposed`.
- When a person referenced by an open proposal is deleted, then the card is `invalid` with `targetDeleted`; when that person is restored, the card returns to `proposed`.
- When a proposal is `confirmed`, `rejected` or already `invalid`, then the hooks leave it alone.
- When a proposal's lock is held by a concurrent confirm, then the hook does not block and does not change it.
- When any writer stores a `proposal`, then `referencedItemIds` equals the ids referenced by it.
- A tenant's items never invalidate another tenant's proposals.
