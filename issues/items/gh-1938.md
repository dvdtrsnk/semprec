## Context

Model tier rationale: Defines what an AI thread turn is allowed to change on user-edited state and how that is stored, across a prompt-composition seam and a validated write, with ownership of protected user values at stake.

In the thread attached to an Inbox item the user tells Semp what to do differently ("it is something else", "it belongs to another project", "fill in the missing details"). Semp should see the whole capture and what it proposed from it, answer, and change the card; the card then redraws. Four pieces exist or are planned: the thread's chat transport (#1620), the queued thread turns run in semprec-agents (#1727), the revision tool `inbox.proposal.revise` (#1906) that validates a revised envelope and stores it through the revise route, and manual edits with `userOverrides` / `userEditedKeys` / `aiProposal` (#1471, typed history in #1430). Today the thread's prompt knows nothing about the card, `reviseProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) takes a finished envelope and a mandatory message and does not record where the revision came from, and a revision would overwrite fields the user edited by hand.

This issue does two things on the one flow "a thread turn revises a card": it gives the turn the card as context, and it defines the rules of the revision when the tool is called from a thread. The tool itself (#1906) is not re-built here.

Decision: no separate read tool is introduced; the card context is inserted into the thread turn's prompt. The context contains the source (text, capture date and time, type, attachment names), the effective envelope, `userEditedKeys`, the history and the user's message. A thread turn on an item without an open card gets no card context.

Decision: a revision from a thread is written as the assistant's output with these rules. The tool passes the full revised envelope. For every key in the previous `userEditedKeys`, `aiProposal` keeps the previous assistant value and `userOverrides` takes the value of the revised envelope, so a key the instruction did not touch stays protected and a key the instruction changed ("it belongs to another project") is changed but remains user-owned (it stays in `userEditedKeys`). All other keys are written to `aiProposal`. If the revision changes `entityKind` or `target`, all overrides are dropped by the rule of #1924. The history entry has `author: "ai"`, `kind: "threadRevision"`, the thread id and the message id. `aiVersion` is incremented.

Decision: only the card whose source item is the thread's subject can be revised from that thread; a `confirmed` or `rejected` card is read-only for the thread and the tool returns an error.

Decision (product owner): the item a confirmed card created is an ordinary item and the thread may edit it. For a `confirmed` card the context lists the created items from the card's `results` (#1648: `itemId`, `databaseKey`, `label`), and the thread edits them with the same item tools as any other item, through the choke point; nothing here bypasses it. When such a Semp write would end an inherited value link, the choke point defers it to an approval carrying the warning that it ends the link (#1758); this issue adds no rule of its own.

## Task

Load `state-writes`, `ai-gateway`, `error-handling` and `testing`.

1. Add `loadInboxCardThreadContext(client, itemId)` in a new `backend/packages/data/src/inbox/threadCardContext.ts`: returns the structure above for a live open card, the source plus the card's status and its created items (from `results`) for a `confirmed` card, and `null` otherwise; the text rendering for the prompt (bounded length per field, user text clearly delimited as data, never as instructions) lives next to it.
2. Wire it into the thread-turn prompt composition in `semprec-agents` (the code added by #1727; the composition root is `backend/services/semprec-agents/src/agentSessionComposition.ts`) for threads whose subject is an Inbox item.
3. Add `reviseProposalFromThreadWithClient(client, config, { proposalId, subjectItemId, threadId, messageId, entityKind?, target?, properties, message? })` in `proposalActions.ts` implementing the rules above, validating the revised envelope with `assertValidEnvelopeForCard` (so the MCP credential guard and relation checks apply as for a manual edit), and refusing a card that does not belong to `subjectItemId` or is locked.
4. Make the `inbox.proposal.revise` handler (the file added by #1906) call it with the thread id and message id taken from the run context, never from model arguments.
5. Tests: the instruction "it is an event, not a task" turns the card into an event proposal, history has `threadRevision` with the thread id, and nothing is created in any target database; an instruction that changes an edited `title` changes it and the title stays in `userEditedKeys`; an untouched edited key is unchanged and protected; a target change drops overrides; a card of another item and a locked card are refused; the context loader returns the effective envelope, edited keys and history, the created items for a confirmed card, and `null` for no card; with a confirmed card an instruction edits the created task through the item tools while the revise tool still refuses the card.

## Scope

### In scope

- The card context in thread prompts and the thread-specific revision rules.

### Out of scope

- The `inbox.proposal.revise` tool itself (#1906) and the revise route.
- Splitting a source into several cards (#1939).
- Read tools that look up missing details (web, registers) and the thread's tool set.
- The item tools a thread uses to edit a created item and the approval for writes that end a value link (#1758); this issue only puts the created items into the context.

## Acceptance criteria

- When the user writes "it is an event, not a task" in the item thread, then the card becomes an event proposal, its history gains a `threadRevision` entry with the thread id and message id, and no item is created in a target database.
- When the instruction changes a manually edited `title`, then the new title is stored and remains in `userEditedKeys`.
- When the instruction does not touch an edited key, then its value and its protection remain.
- When the revision changes the target database, then manual values are dropped.
- When the card is `confirmed` or `rejected`, or belongs to another item, then the tool call fails with an error and nothing is written.
- When the thread turn starts for an item with an open card, then the prompt contains the source, the effective envelope, the edited keys and the history.
- When the card is `confirmed`, then the prompt lists the items it created, an edit of the created task asked for in the thread goes through the item tools and the choke point, and the card itself stays read-only.
