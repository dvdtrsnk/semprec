## Context

Model tier rationale: The deletion transaction is fully specified, but it composes re-authentication, lockout, last-admin locking and tenant entry across two routes.

A user can delete their own account after re-entering their password, and an admin can delete any account. At least one active admin must always remain. Deletion:

- revokes access at once;
- crypto-shreds the tenant's secrets;
- leaves the tenant in status `deleting` for the purge (#1055) to erase every row, partition and file and record a PII-free tombstone.

This issue is the request half. It flips the tenant to `deleting`, revokes everything and shreds the key in one transaction.

What exists to build on:

- **Re-authentication and lockout.** `login` (`backend/packages/data/src/auth/authActions.ts:105-140`) checks the lockout streak with `getFailureStreak` (`backend/packages/data/src/auth/loginAttemptsStore.ts:70`) and `lockoutDurationSeconds`, verifies with `verifyPassword` (`backend/packages/data/src/auth/passwordHash.ts:13`) against a dummy hash when needed, and records every failure with `recordLoginAttempt` (`loginAttemptsStore.ts:31`) as an auto-committed statement on the pool. The client IP comes from `clientIpFromRequest(req, { trustProxy })` (`backend/services/semprec-api/src/clientIp.ts:15`). `AppOptions.trustProxy` (`backend/services/semprec-api/src/app.ts:36`) reaches `createAccountRoutes(pool, options)` (#1043).
- **Revocation.** `revokeAllSessionsForUser` (`backend/packages/data/src/auth/sessionsStore.ts:116-122`) revokes every session and fires `session_revoked` after commit. `revokeAllPushSubscriptionsForUser(client, userId)` (`backend/packages/data/src/push/pushSubscriptionsStore.ts`, #1024) revokes every push registration of a user.
- **Status and admins** (#1041). `transitionTenantStatus(client, tenantId, from, to)` in `backend/packages/data/src/tenancy/tenantsStore.ts` answers 409 `invalid_account_status` on a wrong current status. In `backend/packages/data/src/tenancy/accountsAdminStore.ts`, `lockAdminMembership(client)` and `assertAnotherActiveAdminRemains(client, userId)` throw `LastAdminError` (409 `last_admin`).
- **Audit** (#1037). `recordAdminAction(client, { actorUserId, action: "accountDeletionRequested", targetTenantId, details })`.
- **Teardown signal** (#1042). `publishTenantDeactivated(client, tenantId)` issues the NOTIFY inside the transaction. `semprec-api` then drops that tenant's sockets and mail live sync (#1042), and `semprec-agents` cancels its in-flight agent runs (#1050).
- **Key shredding.** The wrapped data key of each tenant is the single row of the tenant table `tenant_keys` (#1031). Deleting that row makes every `scheme = 'tenant'` credential undecryptable. #1060 (sealing new credentials under the tenant key) and #1062 (re-encrypting existing ones) land after this issue, so credentials written before them stay master-sealed and are not shredded by this issue.
- **Scope.** `tenant_keys` is protected by row-level security, so the key can only be deleted from a transaction opened inside `runInTenant(targetTenantId, …)`. The scope's GUC is set when `withTransaction` begins, not per statement.
  - The admin plane runs in `runAsSystem`, and ESLint bars `adminHandler.ts` and `accountsAdminStore.ts` from importing `runInTenant`.
  - Deletion therefore lives in its own data-layer module. It enters the target tenant only to run this one write transaction and reads no content. Entering a tenant from system scope is allowed; only entering a *different* tenant from inside a tenant scope throws `TenantScopeConflictError`.

## Task

Load `state-writes` (guards and writes in one transaction, affected-row checks), `io-hardening` (re-authentication on a destructive route, throttling), `error-handling` and `canonical-keys` (new error codes).

1. New `backend/packages/data/src/tenancy/deleteAccount.ts`:
   - `ReauthenticationFailedError extends ChokePointError` with `(403, "reauthentication_failed", "Password is incorrect")`. It is deliberately not a 401, so the web client's "401 means signed out" handling is not triggered by a typo.
   - `beginTenantDeletion(client: PoolClient, tenantId: string): Promise<void>`:
     - First, assert that `currentTenantScope()` is `{ kind: 'tenant', tenantId }` and throw otherwise, as fail-closed wiring protection.
     - Then:
       - `transitionTenantStatus(client, tenantId, ["active", "suspended"], "deleting")`;
       - `revokeAllSessionsForUser` and `revokeAllPushSubscriptionsForUser` for the tenant's user;
       - `DELETE FROM tenant_keys WHERE tenant_id = $1` (zero rows is legitimate for a tenant that never stored a credential);
       - `publishTenantDeactivated(client, tenantId)`.
     - Add a docstring stating the crypto-shred guarantee.
   - `deleteOwnAccount(pool, input: { userId; tenantId; password; ip })`:
     1. Look up the user.
     2. Apply exactly `login`'s lockout check and timing-safe verification. A locked pair or a wrong password records a failed attempt with `recordLoginAttempt(pool, …)` and throws `ReauthenticationFailedError`.
     3. Then, in `runInTenant(tenantId, () => withTransaction(pool, …))`: `lockAdminMembership`, re-read the user `FOR UPDATE`, run `assertAnotherActiveAdminRemains` if the user is an admin of an active tenant, then `beginTenantDeletion`.
   - `SelfDeletionRequiresReauthenticationError extends ChokePointError` with `(403, "self_deletion_requires_reauthentication", "Delete your own account through the account page")`.
   - `deleteAccountAsAdmin(pool, input: { actorUserId; targetUserId })`:
     1. If `targetUserId === actorUserId`, throw `SelfDeletionRequiresReauthenticationError` before any query. An admin deletes their own account only through `POST /api/account/delete`, with password re-authentication.
     2. Resolve the target's `tenant_id` from `users`. A missing user is `NotFoundError`.
     3. Then, in `runInTenant(targetTenantId, () => withTransaction(pool, …))`: `lockAdminMembership`, re-read the target `FOR UPDATE`, apply the guard as above, run `beginTenantDeletion`, and write `recordAdminAction(client, { actorUserId, action: "accountDeletionRequested", targetTenantId, details: {} })`.
   - Export the module through `backend/packages/data/src/index.ts`, and update `EXPECTED_RUNTIME_EXPORTS`.
2. **Routes:**
   - In `createAccountRoutes` (`backend/services/semprec-api/src/accountHandler.ts`), add `POST /api/account/delete` with body `{ "password": string }` (non-empty; otherwise 400 `validation_failed`, field `password`). It calls `deleteOwnAccount` with `identity.user.id`, `identity.tenantId` and `clientIpFromRequest(ctx.req, { trustProxy: options.trustProxy ?? false })`, and answers `202 { "status": "deleting" }`.
   - In `createAdminRoutes`, add `POST /api/admin/accounts/:userId/delete` (`admin: true`, `assertUuid`), which calls `deleteAccountAsAdmin` and answers `202 { "account": AdminAccountSummary }`.
   - Add two route-matrix entries (the admin one with `admin: true`) and their `ROUTE_HANDLER_FILES` mappings.

## Scope

### In scope
- Self and admin deletion requests, re-authentication with the login lockout, the last-admin guard, status `deleting`, revocations, key shredding and the deactivation signal.

### Out of scope
- Erasing rows, partitions and files, the tombstone, and enqueueing the purge (#1055 picks up every `deleting` tenant).
- Re-applying deletions after a restore (#1078).
- The account page (#1083).
- Per-IP aggregate throttling (#1073).
- Cancelling a deletion: `deleting` has no way back.

## Acceptance criteria

- When tenant B's user posts the correct password to `/api/account/delete`:
  - the response is 202;
  - B's tenant is `deleting`, every B session is revoked (B's next request answers 401) and every B push registration is revoked;
  - B's `tenant_keys` row is gone, and decrypting a `scheme = 'tenant'` credential fabricated for B the way #1032's tests do (`getOrCreateTenantDataKey`, `sealSecret`, a raw insert with `scheme = 'tenant'`) now fails;
  - the deactivation NOTIFY was delivered after commit;
  - no audit row is written;
  - tenant A, including its key and credentials, is unaffected.

  (integration, `accountHandler.test.ts` and `deleteAccount.test.ts`, two tenants via `createTestTenant()` from #975)
- When the password is wrong, the response is 403 `reauthentication_failed`, a failed login attempt is recorded for (email, IP), and nothing else changes. Once the failure streak reaches `login`'s lockout, even the correct password is refused the same way until the lockout lapses (integration, `deleteAccount.test.ts`).
- When `password` is missing or empty, the response is 400 with field `password` (integration, `accountHandler.test.ts`).
- When the only active admin deletes their own account through `/api/account/delete`, or another admin deletes them, the response is 409 `last_admin` and nothing changes. With a second active admin present, both requests succeed (integration, `deleteAccount.test.ts`).
- When an admin calls `POST /api/admin/accounts/:userId/delete` with their own user id, the response is 403 `self_deletion_requires_reauthentication`, whether or not another active admin exists. Nothing changes: the tenant stays as it was, sessions and key are intact, no audit row is written and no notification is published (integration, `adminHandler.test.ts`).
- When an admin deletes B's member, the response is 202 with `status: "deleting"`, the same effects as the self path hold, and one `accountDeletionRequested` audit row names B's tenant (integration, `adminHandler.test.ts`).
- When a `deleting` account is deleted again, the response is 409 `invalid_account_status`. An unknown `:userId` answers 404, a `member` calling the admin route gets 403 `admin_required`, and an anonymous caller gets 401 on both routes (integration, `adminHandler.test.ts`, `routeMatrix.test.ts`).
- When the deleted user logs in with the correct password, the response is the same 401 as a wrong password (integration, `deleteAccount.test.ts`).
- When `beginTenantDeletion` is called in a transaction whose scope is system or another tenant, it throws before any write (integration, `deleteAccount.test.ts`).
