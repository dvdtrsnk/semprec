## Context

The review follow-ups pipeline (epic #565; decision recorded in the ADR that #567 added, `docs/adr/*-merged-review-findings-become-proposed-follow-up-issues.md`) keeps all of its state in GitHub: labels plus HTML markers inside issue bodies and comments. Three later scripts read that state — the harvest (never harvest a finding twice), the triage `prepare` step (never propose an already-published finding) and the triage `publish` step (reuse an existing epic) — and two write it. This issue defines the marker grammar and the one function that turns issues and comments into the ledger, so all of them agree on it.

Nothing else in the batch depends on this module's internals; they call its exports.

The repository is public: anyone can open an issue or comment, but only a collaborator can label an issue. That is why a body counts only on an issue carrying a pipeline label, and a comment counts only when `bb-agent-relay[bot]` wrote it — that is the identity the triage publishes under. Markers also count only when they stand alone on their own line. A review finding about this very module may quote a marker inside a table cell or a JSON string, and a quote must never be read as a ledger entry.

## Task

Create `.github/scripts/review-followups/markers.mjs`, a zero-dependency ES module with a header comment that says what it owns and names the ADR from #567 by its path, exporting:

1. `LABELS` — a frozen object: `harvested: "followups:harvested"`, `harvest: "followups:harvest"`, `ready: "followups:ready"`, `issue: "followups:issue"`, `proposed: "spec:proposed"`.
2. `PUBLISHER_LOGIN = "bb-agent-relay[bot]"`.
3. Render and parse functions for four markers. A marker is recognised only when a line of the text, after trimming trailing whitespace and `\r`, is exactly the marker:
   - finding marker `<!-- crb-followup:v1 pr=<n> key=<key> -->` — `renderFindingMarker({ pr, key })`, `parseFindingMarkers(text)` → array of `{ pr, key }` in order of appearance;
   - harvest marker `<!-- crb-followup-harvest:v1 prs=<n>,<n>,... -->` (ascending, no duplicates, at least one) — `renderHarvestMarker(prs)`, `parseHarvestMarker(text)` → array of numbers, or `null` when absent;
   - epic marker `<!-- crb-followup-epic:v1 harvest=<n> -->` — `renderEpicMarker(harvest)`, `parseEpicMarker(text)` → number or `null`;
   - result marker `<!-- crb-followup-result:v1 harvest=<n> -->` — `renderResultMarker(harvest)`, `parseResultMarker(text)` → number or `null`.

   `<n>` is a positive integer without leading zeros; `<key>` is exactly ten lowercase hex characters (the bot's key is `sha1(...).hexdigest()[:10]`). Every render function throws on an argument that does not satisfy that grammar (and `renderHarvestMarker` on an empty, unsorted or duplicate list). A line that starts like a marker but does not match the grammar exactly is not a marker.
4. `findingId({ pr, key })` → the string `"<pr>:<key>"`, the key every set below uses.
5. `computeLedger(issues)` — pure. Input: an array of `{ number, labels: string[], body: string, comments: { author: string, body: string }[] }` (`comments` may be empty for issues whose comments were not fetched). Output:
   - `harvested`: a `Set` of finding ids from finding markers in the bodies of issues labelled `followups:harvest` or `followups:issue`, plus from comments on `followups:harvest` issues whose author is `PUBLISHER_LOGIN` and whose body carries a result marker;
   - `terminal`: the same, except the bodies of `followups:harvest` issues;
   - `harvestedPrs`: a `Set` of pull request numbers from harvest markers in the bodies of `followups:harvest` issues;
   - `epics`: a `Map` from harvest issue number to epic issue number, from epic markers in the bodies of `followups:issue` issues; when two epics name the same harvest, the lower issue number wins.

   An issue with neither label contributes nothing, whatever its body says. The issue's open or closed state does not matter.
6. `markers.test.mjs` next to it, using `node:test` and `node:assert/strict`, covering every Acceptance criterion below.

## Scope

### In scope

- The marker grammar, `LABELS`, `PUBLISHER_LOGIN` and `computeLedger`, with tests.

### Out of scope

- Fetching issues or comments from GitHub — the GitHub access layer issue in this batch.
- Any other document format (the harvest issue's JSON block, the triage input and proposal files) — other issues in this batch.
- Wiring the tests into `verify` or CI — other issues in this batch.

## Acceptance criteria

1. Each render function's output, parsed back by its parse function, returns the original values.
2. `renderFindingMarker` throws for `pr` 0, negative, non-integer or with leading zeros, and for a key that is not exactly ten lowercase hex characters; `renderHarvestMarker` throws for an empty, unsorted or duplicate list.
3. A marker embedded in a longer line (a table cell, a JSON string, text before or after it on the same line) is not parsed; the same marker alone on a line with trailing spaces or `\r` is.
4. A malformed marker line (wrong version, missing field, uppercase key, key of nine or eleven characters) is ignored by the parse functions.
5. `computeLedger`: a finding marker in a `followups:harvest` body is in `harvested` but not `terminal`; in a `followups:issue` body it is in both; in a result comment by `bb-agent-relay[bot]` on a harvest issue it is in both.
6. `computeLedger` ignores a result comment by any other author, a comment without a result marker, a comment on a `followups:issue` issue, and every marker in the body of an issue with neither pipeline label.
7. `computeLedger` returns the pull requests of every harvest marker in a `followups:harvest` body in `harvestedPrs`, and maps a harvest number to the lower of two epic numbers when two `followups:issue` bodies carry the same epic marker.
8. Closed and open issues contribute identically.
9. `node --test .github/scripts/review-followups/markers.test.mjs` passes with no network access.
