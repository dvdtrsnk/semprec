## Context

Model tier rationale: The limiter, its limits and wiring are specified, but sliding-window eviction, IPv6 /64 keying and the timing floor still need careful implementation.

The public authentication routes live in `createAuthRequestListener` (`backend/services/semprec-api/src/authHandler.ts:124-267`).

- **Login.** `login` locks out one *(email, IP)* pair after `LOCKOUT_THRESHOLD` failures (`backend/packages/data/src/auth/authActions.ts:105-138`, `backend/packages/data/src/auth/loginLockout.ts:1-17`). There is deliberately no per-email aggregate (`authHandler.ts:150-153`). Nothing limits one address that tries many emails, i.e. credential stuffing, which with several accounts now has more than one target.
- **Password-reset request.** It caps tokens per *account* (`backend/packages/data/src/auth/passwordResetActions.ts:21-29,74-75`) but not per address. Its response time also differs by path: an unknown email returns after one lookup, while a known one also counts tokens and inserts one (`:70-87`). That difference is an account-existence oracle.
- **Password-reset consume.** It has no throttle at all (`authHandler.ts:190-207`).
- **Invitation acceptance.** #1087 adds this public route later. It must use the same per-address limit.

`clientIpFromRequest` (`backend/services/semprec-api/src/clientIp.ts:15-22`) already yields the trusted client address (last `X-Forwarded-For` hop behind Caddy when `TRUST_PROXY=1`). Production runs exactly one semprec-api process (`deploy/systemd/semprec-api.service`), so an in-process limiter sees every request. #1041 last changed `authActions.ts` and `passwordResetActions.ts` (suspended accounts). #1076 and #1088 expect a throttled request to answer `429` with an `error` string.

## Task

Load `io-hardening` (rate limits on public edges), `error-handling` (which outcomes count, what the caller sees) and `adr-conventions`.

1. **Limiter.** New `backend/services/semprec-api/src/clientIpThrottle.ts`:
   - `export type ThrottledAction = "login" | "passwordResetRequest" | "passwordResetConsume" | "invitationAccept"`.
   - `export const CLIENT_IP_THROTTLE_LIMITS`, each a sliding window of `{ maxEvents, windowSeconds }`:
     - `login`: 30 per 900 s;
     - `passwordResetRequest`: 10 per 3600 s;
     - `passwordResetConsume`: 10 per 3600 s;
     - `invitationAccept`: 10 per 3600 s.
   - `export function throttleKeyForIp(ip: string): string`:
     - IPv4 as is;
     - an IPv4-mapped IPv6 address (`::ffff:a.b.c.d`) as its IPv4;
     - any other IPv6 as its `/64` prefix, since one host commonly holds a whole `/64`.
   - `export function createClientIpThrottle(options?: { now?: () => number; maxKeys?: number; limits?: Partial<typeof CLIENT_IP_THROTTLE_LIMITS> })` returns `{ retryAfterSeconds(action, ip): number | null; record(action, ip): void }`:
     - `retryAfterSeconds` returns `null` while the key is under its limit. Otherwise it returns whole seconds (≥ 1) until the oldest counted event leaves the window.
     - State is per `(action, key)`, expired events are pruned on access, and at most `maxKeys` (default 50,000) keys are held. When full, it drops keys with only expired events first, then the least recently recorded key.
     - The docstring states the single-process assumption and that a restart clears all windows.
2. **Wiring in `authHandler.ts`.**
   - `AuthRequestListenerOptions` gains `clientIpThrottle?`, defaulting to one `createClientIpThrottle()` per listener.
   - For the three public routes, compute `ip` with `clientIpFromRequest` once. Before reading the body, a throttled request answers `sendJson(res, 429, { error: "Too many attempts; try again later", code: "rate_limited" }, { "Retry-After": String(seconds) })`.
   - What counts toward each limit:
     - login: an `UnauthorizedError` from `login`, recorded before rethrowing;
     - reset request: every accepted request, recorded before `requestPasswordReset`;
     - consume: a `PasswordResetTokenError`, recorded before rethrowing.

     Validation failures (400) count toward none.
   - The per-account reset cap and the *(email, IP)* login lockout stay as they are.
3. **Equal timing.**
   - In `passwordResetActions.ts`, export `PASSWORD_RESET_REQUEST_MIN_DURATION_MS = 400`.
   - `requestPasswordReset` resolves no earlier than that many milliseconds after it was called, on every non-throwing path: unknown email, per-account cap reached, token issued.
   - The mail send stays un-awaited after commit.
   - Update the docstring (`:46-62`).
4. **ADR.** Add `docs/adr/<YYYY-MM-DD>-per-ip-auth-throttles-held-in-process.md`. Record:
   - the decision: an in-memory sliding window in semprec-api;
   - the rejected alternative: a Postgres table plus a retention sweep, for pre-authentication rows that are worthless after an hour;
   - the single-process assumption;
   - the `/64` grouping;
   - that the DB-backed lockout keeps its role per `[[2026-09-27-auto-committed-writes-for-records-that-must-survive-a-failure]]`.
5. **Tests.**
   - New unit test `backend/services/semprec-api/src/__tests__/clientIpThrottle.unit.test.ts`, with an injected clock.
   - Extend `backend/services/semprec-api/src/__tests__/authHandler.test.ts`, injecting a throttle with small `limits`.
   - Extend `backend/packages/data/src/__tests__/passwordResetActions.test.ts` for the timing floor.

## Acceptance criteria

- With a limit of N per window, the *N+1*-th counted event from one address is refused with a `retryAfterSeconds` equal to the seconds until the oldest event expires. Once the window passes it is allowed again (unit, `clientIpThrottle.unit.test.ts`).
- Actions and addresses are independent:
  - the four actions keep separate counters;
  - two addresses in the same IPv6 `/64` share a counter, while addresses in different `/64`s or different IPv4 addresses do not;
  - `::ffff:192.0.2.1` and `192.0.2.1` share one (unit, `clientIpThrottle.unit.test.ts`).
- At `maxKeys`, a new key evicts a key with only expired events before it evicts the least recently recorded live key (unit, `clientIpThrottle.unit.test.ts`).
- After the login limit of failed logins from one address, each across a different email, the next login from that address answers `429` with `code: "rate_limited"` and a positive integer `Retry-After`, even with correct credentials (integration, `authHandler.test.ts`). In the same test:
  - another forwarded address still logs in;
  - successful logins and 400 validation failures do not count.
- After the reset-request limit from one address, the next request answers `429` and creates no `password_reset_tokens` row. Below the limit the response stays `200 { ok: true }` for known and unknown emails alike (integration, `authHandler.test.ts`).
- After the consume limit of invalid-token attempts from one address, even a valid token from that address answers `429` and is not consumed (integration, `authHandler.test.ts`).
- `requestPasswordReset` takes at least `PASSWORD_RESET_REQUEST_MIN_DURATION_MS` for an unknown email, a capped account and a fresh token alike. The existing "answers a known email before the mail send has resolved" test still passes (integration, `passwordResetActions.test.ts` and `authHandler.test.ts`).
