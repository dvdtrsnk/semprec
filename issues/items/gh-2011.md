**Blocked by:** #1665, #1713
**Model tier:** high

## Context

Model tier rationale: It routes a system-owned property of the generic item write into the series store inside the write transaction and adds an approval trigger with snapshot revalidation and exactly-once replay to the agent deferral mechanism, so a mistake either lets an agent rewrite future occurrences without approval or replays a stale series change.

Semp, the in-app agent, cannot set or change a task's recurrence today. #1665 adds the human routes `PUT` and `DELETE /api/tasks/:id/recurrence` with their store helpers in `backend/packages/data/src/tasks/taskRecurrenceStore.ts`; #1605 exposes the result as the system-owned Tasks property `recurrence` (`{preset, mode, rule}`), which a generic write currently rejects with 403. A module agent tool is not wanted: it would bypass the generic operation catalog and its approval rules (`docs/adr/2026-09-18-non-destructive-generic-operations-bypass-agent-approval.md`, `docs/adr/2026-09-10-agent-writes-are-proposals-not-direct-writes.md`). #1713 adds the mechanism in which the choke point flags an agent write inside its own transaction with `ApprovalRequiredForWrite`, the gateway (`backend/packages/application/src/genericOperationGateway.ts`) turns it into an approval request with a resource snapshot, and the approved write is revalidated and replayed exactly once; the `item_patch` snapshot kind exists there with no trigger yet.

Decision (product owner): Semp gets recurrence through the generic item write with the same risk rules as other properties. Changing the rule of an existing series or ending it changes future occurrences, so for an agent writer it always requires approval. Setting a recurrence on a task that has no series follows the rule for any other property write and executes immediately. A user writer is never deferred. The 403 that #1605 returns for a client write of `recurrence` is replaced by the handling below; `seriesId` and `occurrenceDate` stay rejected with 403.

## Task

Load `state-writes`, `error-handling`, `canonical-keys` and `testing`.

1. In the Tasks pre-write transform, accept `recurrence` in a generic item patch of a Tasks item: `{preset}` or `{mode, rule}` (validated exactly as the PUT route of #1665) or `null`. Remove it from the stored patch and apply it in the same transaction through the store helpers of #1665: on a task without a series it creates the series; on a task with a series it replaces the rule; `null` deactivates the series. A task without a `date` gets the same 400 as the route. Lock order stays items, then `task_recurrence`. The value of `recurrence` in the response is the refreshed projection.
2. When the writer is an agent and the task has an active series, a `recurrence` value that differs from the current rule, or `null`, adds the reason `{ kind: "changesSeries", seriesId, from, to }` to the `ApprovalRequiredForWrite` of #1713 (`to` is null when the series ends) and the transaction rolls back with nothing written. The same value as the current rule executes as a no-op.
3. Snapshot and replay: for these requests the `item_patch` snapshot hash covers the series row (`series_id`, `active`, `mode`, `rule`) and the task's `date`; replay revalidates it and terminalizes as a conflict with nothing written when it changed; a valid replay applies the change exactly once through step 1.
4. Description and risk: render the localisable template `approval.changesSeries` of the description mechanism used by #1713 with params `{ taskName, fromRule, toRule }` (an ended series renders the end), with the risk class `write` from the closed set; add the template to the Czech and English catalogs.
5. Tests: an agent patch setting `{preset: "weekly"}` on a non-recurring task creates the series immediately; an agent patch changing a weekly series to `monthly` creates an approval request and leaves the rule unchanged; an agent patch with `recurrence: null` on a series creates an approval request; approval applies the change once even if the replay runs twice; a user changing the rule between request and approval yields a conflict; rejection changes nothing; a user generic patch of `recurrence` executes immediately; a patch without a task `date` returns 400.

## Scope

### In scope

- `recurrence` in the generic Tasks item patch, the approval trigger for an agent changing or ending a series, its snapshot, replay, description and tests.

### Out of scope

- The human recurrence routes and their store helpers: #1665.
- Series-level edits of name, times and other template fields: #1667.
- The deferral mechanism itself: #1713.
- A module agent tool or a proposal card for recurrence: not built.

## Acceptance criteria

- When Semp sets a weekly recurrence on a task that is not recurring, then the series exists immediately and the response carries `recurrence` and `seriesId`.
- When Semp changes the rule of an existing series or ends it, then an approval request is created, the call returns an approval-required error and the series is unchanged.
- When that request is approved, then the change is applied exactly once; when the series changed in the meantime, then the request ends as a conflict and nothing is written; when it is rejected, then nothing changes.
- When a user changes or ends a recurrence through the generic item write, then it executes immediately.
- When the patch targets a task without a `date`, then the response is 400 and nothing changes.
