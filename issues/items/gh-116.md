### Source behavior: [10/22] pi-agent-core — lifecycle events + budget cap

## Context

Issues #21–#29 built the data layer, views, modules, and their contract (`ModuleManifest`/`ModuleRegistry`). This issue introduces `packages/agent-runtime` — the wrapper around AI agents that will act on the system through that contract.

**Why `pi-agent-core` is not an orchestration layer.** `pi-ai`/`pi-agent-core`/`pi-coding-agent` (packages from `github.com/earendil-works/pi`, MIT license, author Mario Zechner, Earendil Inc.) are an **external, exactly-pinned** npm dependency — not part of this monorepo, not code Semprec writes or maintains. They deliberately solve a narrow problem only: the tool-calling loop, the state of one run, and context compaction *inside* that one run. They do not solve orchestration across multiple concurrent agents, budget across them, MCP tool registration, or the question of "when a run is definitively over" — pi's own design philosophy states sessions are "long-lived by intent" (its documented example use case is a Slack thread recycled indefinitely). Concretely, this means:

- concurrent agent sessions are cheap in-process objects — no subprocess per project (`Agent`/`AgentSession` constructors do no subprocess spawning or file I/O; `SessionManager.inMemory()` gives zero persistence when none is needed; pi's own RPC docs recommend using `AgentSession` directly instead of spawning a subprocess for a Node.js host),
- supervisor→project-agent delegation is handled as an in-process `AgentSession`, not a subprocess — even though pi ships its own official subprocess-based sample extension for exactly this pattern; Semprec takes the *shape* (bounded return: only the target agent's final assistant message comes back, never the full transcript, so the project agent's conversation never inflates the supervisor's own context) but not the subprocess mechanism, since in-process sessions are already established as cheap,
- parallel tool calls within a single turn are already handled by `pi` itself (`executeToolCallsParallel`, `packages/agent/src/agent-loop.ts:489-554`, triggered automatically whenever a turn's assistant message contains more than one tool-call block and no tool forces `executionMode: 'sequential'`) — Semprec does not need its own concurrency cap on top of this,
- compaction of a run's own history is free — `packages/agent/src/index.ts` exports working `compact`/`shouldCompact`/`CompactionSettings` with `"threshold"`/`"overflow"` triggers,
- but the boundary of "a run is over, its session is discarded and never recycled for an unrelated trigger" is Semprec's own convention, not something pi enforces or even offers — this issue is what implements that boundary, plus the global budget cap that sits next to it.

Delegation itself is structurally one-directional: the delegation `AgentTool` exists only in Semp's own manifest — no project agent ever receives it (hardcoded absence, not a `project_mcp_grants` toggle, since no per-project policy decision is needed here). Project agents therefore cannot delegate further or loop back; when two project agents need to "talk to each other," Semp relays between them as intermediary — there is no direct agent-to-agent channel.

This issue introduces `packages/agent-runtime` as the wrapper over this external dependency. The follow-on issue #31 (MCP integration + tool grants) builds on this package, but MCP integration itself is **not part of this issue** — only lifecycle and budget are handled here.

## Task

Build `packages/agent-runtime` as a thin wrapper over `pi-agent-core` that:

**1. Lifecycle events → `agent_runs`.** Map pi's own streaming sequence for one run (`agent_start → turn_start → message_start/update/end → turn_end → agent_end`) onto the `agent_runs` audit table (schema from issue #21):
- `agent_start` → `INSERT agent_runs (status='running', started_at=now(), triggered_by, project_item_id, parent_run_id)`.
- `turn_start`, completed `message`s, `tool_use`/`tool_result`, `turn_end` → appended as rows to `agent_run_events` (the turn-level log this issue creates — see the table below), plus a WS push for live progress. Only `message_update` streaming deltas are WS-ephemeral: they produce a push and never a row in any persistent table — losing one costs nothing, because the final text of each turn is persisted anyway as the completed `message` event.
- `agent_end` → `UPDATE agent_runs SET status='done'|'error', finished_at=now()` and discard the `AgentSession` from the in-memory registry — the session is never recycled for a subsequent, unrelated trigger (a later heartbeat or delegation always gets a fresh session; the only exception is Semp's own conversation with the user, point 2 below, where "the next message" is *not* an unrelated trigger).

Every `agent_runs` row also carries a `unit` discriminator column (established on the table by issue #21, alongside the columns above): `'invocation'` is the default, covering one-shot heartbeat/MCP-triggered runs; `'session'` marks a run that is one long-lived, resumable multi-turn `AgentSession` under management by this issue (a delegated session or Semp's own user conversation, both described below) rather than a single call. This issue is responsible for setting `unit='session'` on the rows it manages this way — without the distinction, aggregations over `agent_runs` (the budget dashboard, "average run length," "runs per day" in the observability work) would silently mix second-long one-shot calls with multi-hour sessions as if they were comparable units of work; with it, any such aggregation knows to bucket by `unit` rather than sum across it. The `task`/`result` columns on the row still hold only the first request and the last response as a snapshot; the full turn-by-turn transcript lives in `agent_run_events` (created by this issue — see below; issue #38 later consumes and extends it for the realtime/WS layer).

**Table `agent_run_events` — created here (authoritative definition).** This issue both writes it (the turn-level events above, the startup sweep's synthetic `tool_result` in point 4) and reads it (reconstruction in points 2–3), so its creation belongs here, not later in the queue. Its shape is dictated by reconstruction and resume: `id` is a monotonic cursor that provides the ordering for the `Entry[]` reconstruction below and later doubles as the `afterEventId` resume cursor in the WS protocol — issue #38 (realtime/WS `/api/sync`) consumes and extends this table (cursor replay, thin NOTIFY after commit), it does not define it.

```sql
CREATE TABLE agent_run_events (
  id bigserial PRIMARY KEY,                 -- monotonic cursor: resume and Entry[] reconstruction ordering
  agent_run_id uuid NOT NULL REFERENCES agent_runs(id),
  kind text NOT NULL,                       -- 'turn_start' | 'message' | 'tool_use' | 'tool_result' | 'turn_end' | 'run_status'
  payload jsonb NOT NULL,                   -- full message (AgentMessage shape) -- source for reconstruction, not just display
  at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX agent_run_events_run_idx ON agent_run_events (agent_run_id, id);
```

**2. In-memory session registry.** `packages/agent-runtime` holds a process-memory registry of open delegated conversations, keyed by the pair **(supervisor `agent_runs` id, target project)** — not by target project alone, so that two unrelated Semp runs never share one session to the same project agent. Each entry holds the live `AgentSession` object, the id of the corresponding `agent_runs` row, a `busy: boolean` flag, and the timestamp of the last request.

- A further delegation onto the same key within **24 hours** of the last activity reuses the same `AgentSession` (a new message into the same conversation, not a new session), so the project agent retains full context of prior exchanges. After 24 hours of inactivity (a plain timer reset on every activity — purely in-process state, no new table or job needed since it is not state that must survive a process restart) the in-memory object is discarded and the corresponding `agent_runs` row is closed (`status='done'`, `finished_at=now()`). The conversation itself is **not** lost: a later delegation onto the same key, whether a minute or a month afterward, is reconstructed from `agent_run_events` (a new `Agent` instance built with `initialState.messages` from the stored transcript) and resumes exactly where it left off.
- Concurrent duplicate delegations onto the same key (no concurrency cap exists on delegation fan-out, see below, so within one turn Semp can in principle fire two parallel delegations at the same target project) are rejected explicitly: `busy` is set true just before dispatch and back to false on response; a second call onto a key that is already `busy` is never dispatched and returns an error `tool_result` to Semp ("this project is already handling another request from this run, retry next turn") instead of being silently blocked or overwritten.
- Semp's own conversation with the user follows the identical policy (24h in-memory, then resumable indefinitely via the same `agent_run_events` reconstruction) but differs from a delegated session in one respect: it never "ends" the way a completed delegated task does — going quiet for 24 hours pauses it, it does not close it as done-and-finished; the next user message, whether a minute or a month later, resumes the same conversation. Each such "wake-up" is technically a new `agent_runs` row (`triggered_by='user'`, `unit='session'`, `project_item_id` pointing at Semprec itself) inheriting context from prior rows in the same conversation via reconstruction — auditable, separately budgeted units of work that appear, from the user's side, as one uninterrupted conversation.

**3. Context-size check before resuming a long-sleeping conversation.** Reconstruction (both cases above) assembles a fresh `Agent` instance with `initialState.messages` from the **entire** stored history in `agent_run_events` — but a conversation kept alive for months through repeated sleep/wake cycles can itself grow past what fits in the context window before a single new turn even starts. "Resumable indefinitely" does not mean it indefinitely fits in context. Before the first new turn on a reconstructed conversation, this package must run the check standalone, without a live session: `estimateContextTokens(messages)` (`packages/agent/src/harness/compaction/compaction.ts:216`) against the reconstructed `AgentMessage[]` array, then `shouldCompact(tokens, contextWindow, settings)` (`:247`) to decide. If compaction is needed, the convenient high-level wrapper (`AgentLane.compact()`, documented as a "standalone operation" on a resumed session) is an unfinished stub in pi's own repository (`this.unavailable("compact")`) and cannot be used — instead, the reconstruction code must itself wrap the stored history (which already carries ordering and timestamps from logging) into the `Entry[]` tree shape (`id`/`parentId`/`seq`/`timestamp`/`message`) that the low-level `prepareCompaction(pathEntries, settings)` and `compact()` primitives actually require, and call those directly.

**4. Startup sweep.** Run once at `semprec-agents` process start, before the process accepts any new triggers (heartbeats, delegations, user messages):
- **Step 1 — sweep:** any `agent_runs` row with `status='running'` at this point is guaranteed orphaned (the in-memory registry is always empty right after a restart, so no such run can genuinely still be alive) — close it (`status='error'`, `finished_at=now()`, reason `"interrupted_by_restart"` in the error field).
- **Step 2 — transcript repair:** if the last event in `agent_run_events` for that run is an unfinished `tool_use` with no matching `tool_result` (the process crashed mid tool call), append a synthetic `tool_result` describing the interruption — preserving the tool-calling protocol invariant (every `tool_use` must be paired) on the stored log, not just on a live conversation, so a later reconstruction doesn't build a protocol-invalid history.

The sweep does not itself "resume" anything, and does not need to: recovery is handled entirely by mechanisms this same specification already establishes for other reasons. A heartbeat-triggered run's underlying item naturally stays in the `pending`/`error` set the heartbeat processes on its next tick — retry is free. A delegated run, once closed as `error` with a valid `tool_result`, surfaces to Semp on its next reconstruction as exactly the kind of failure the busy-flag rejection above already trains it to react to — it sees the error and can retry. Semp's own user conversation is reconstructed on the next user message regardless of how the prior run ended. The sweep only needs to leave the data in a state from which these existing continuation paths work naturally.

**5. Global budget cap enforced in `semprec-ai-gateway`.** `semprec-ai-gateway` is the single egress point to all providers (issue #28) — `complete()`/`transcribe()`/`diarize()`/`embed()`, called from `semprec-agents` and elsewhere (transcription pipeline, embeddings) — so it is the one place that sees every AI cost in the system regardless of whether it originated inside an `agent_run`, a delegated session, or entirely outside the agent loop.

- **How agent calls actually reach the gateway:** `AgentOptions.streamFn` (`packages/agent/src/agent.ts:102`) is a mandatory parameter of the tool-calling loop — an arbitrary async function supplied by the caller, with no dependency on `pi-ai` at all; `createAgentSession()` builds this internally from `modelRuntime`/`model`, and `pi-ai`'s own provider adapters read the request endpoint from `model.baseUrl`, never a hardcoded constant. The documented way to override this `baseUrl` for **all models under a given provider at once**, regardless of which specific model an agent picks, is `pi.registerProvider("anthropic", { baseUrl: "…" })` (and the same for `"openai"`). `semprec-agents` registers `semprec-ai-gateway` as an Anthropic/OpenAI-API-compatible proxy this way exactly once, at process startup — not per session, not per call — so every session (Semp's, delegated, any future type) is structurally forced through the same egress point; no individual `Agent`/`AgentSession` can bypass it.
- **`ai_gateway_calls` table:**
  ```sql
  CREATE TABLE ai_gateway_calls (
    id bigserial PRIMARY KEY,
    at timestamptz NOT NULL DEFAULT now(),
    provider text NOT NULL,
    model text NOT NULL,
    input_tokens integer,           -- NULL = this call has no token concept (diarize()/transcribe()); NOT the same as 0
    output_tokens integer,          -- same
    audio_seconds numeric,          -- NULL unless the call has audio input; native unit for diarize()/transcribe()
    cost_usd numeric NOT NULL,
    agent_run_id uuid REFERENCES agent_runs(id)   -- nullable, not every call originates inside a run (transcription, embeddings)
  );
  ```
  `input_tokens`/`output_tokens` are nullable deliberately, not just by default: `complete()`/`embed()` always populate them, `diarize()`/`transcribe()` leave them `NULL` because their native unit is audio time, not tokens — and `NULL` ("this function has no token concept") and `0` ("a call happened with zero tokens") are different facts a shared value would silently conflate (an `AVG` over stored zeros would be quietly biased low). `audio_seconds` gets its own native column for the same reason, rather than being back-computed from `cost_usd`.
- **Two independent caps**, both nullable = uncapped, in System Settings under Semprec, both `owner: user`: `dailyBudgetUsd` (default **50**) as a fast guard against a runaway loop, and `monthlyBudgetUsd` (default **unlimited**) as the overall ceiling — a monthly-only cap would let a runaway loop (Semp stuck delegating in a circle, a heartbeat firing too often) burn through tens of dollars in a single day before anyone noticed.
- Before every provider call, the gateway computes both sums in one query:
  ```sql
  SELECT
    SUM(cost_usd) FILTER (WHERE at >= date_trunc('day', now()))   AS spent_today,
    SUM(cost_usd)                                                  AS spent_month
  FROM ai_gateway_calls
  WHERE at >= date_trunc('month', now())
  ```
  and rejects the call outright if either non-null cap is exceeded, rather than letting it proceed and dealing with the state mid-turn. A rejected call drives the triggering `agent_run` to `status='error'` the same way as any other unrecoverable runtime error — visible in the audit trail, resolved by raising the cap (or setting it to unlimited) or waiting for the day/month window to roll over.
- **Accepted imprecision:** concurrent calls near the cap can jointly overshoot it slightly (check-then-act, no lock) — acceptable for a personal system with a soft limit; enforcing an exact cap would require a serializing lock across every gateway call, defeating the concurrency that free parallel delegation (above) deliberately provides.
- **Rejected alternative — budget as a sum over the delegation tree, per project:** summing `ai_gateway_calls.cost_usd` (via `agent_run_id`) across the entire `parent_run_id` tree of a given Semp run, per project. Rejected: it would need a recursive query on every budget decision; it would only see costs generated inside agent runs, missing transcription/embeddings entirely; and it answers a question (per-project budget instead of one global budget) nobody has asked for yet. For a single-user, self-hosted system (not a multi-tenant SaaS), one global monthly cap is sufficient and simpler — per-project budget is a clean additive extension for later (another System Settings column, another condition in the same check), not something to design ahead of an actual need.

## Scope

### In scope
- `packages/agent-runtime`: wrapper over `createAgentSession()` from `pi-agent-core`, the `systemPromptOverride` hook, and the delegation `AgentTool` implemented as an in-process `AgentSession` (never a subprocess).
- In-memory session registry with 24h TTL, keyed by (supervisor run id, target project) for delegations and by the user's own conversation for Semp's direct chat; the `busy` flag rejecting concurrent duplicate delegation calls onto the same key; reconstruction of a sleeping conversation from `agent_run_events`.
- Creating the `agent_run_events` table plus its index (authoritative DDL above), and writing the turn-level events (`turn_start`, completed `message`, `tool_use`/`tool_result`, `turn_end`, run status changes) into it from the lifecycle mapping.
- The context-size check (`estimateContextTokens`/`shouldCompact`) and the low-level `Entry[]`/`compact()` compaction path run before resuming any reconstructed conversation.
- Mapping `agent_start`/`agent_end` lifecycle events onto `agent_runs` INSERT/UPDATE, including setting the `unit` column (`'invocation'` default, `'session'` for the delegated/user-conversation sessions this issue manages).
- Startup sweep: closing orphaned `running` rows, repairing a dangling `tool_use`/`tool_result` pair.
- Extending `semprec-ai-gateway` with `pi.registerProvider()` `baseUrl` routing, the `ai_gateway_calls` table and its writes, and the daily/monthly budget check.
- The `GET /api/ai-usage` read endpoint backed by `ai_gateway_calls`, and the "Utilization" cost/token usage graph on the Semprec system page, including the reference line for the daily cap (`dailyBudgetUsd`).

### Out of scope
- MCP integration (server/tool registration, sync) — issue #31.
- Sandbox/process isolation for tool execution — deliberately deferred to v2.
- A separate concurrency cap over parallel delegations/tool calls — pi's own `executeToolCallsParallel` already handles this; do not add a second mechanism on top.
- Per-project/per-agent budget — the rejected alternative above; remains an open, additive future extension, not part of this issue.
- The WS delivery/streaming protocol over `agent_run_events` (the `afterEventId` cursor replay, the NOTIFY fan-out, the `agent:watch` message) — issue #38 consumes and extends the table this issue creates; this issue only produces the rows and the WS pushes.
- Any persistent write for `message_update` streaming deltas — these produce only a WS push, never a row in any persistent table (turn-level events, by contrast, are persisted to `agent_run_events` by this issue).

## Dependencies
- **Depends on #29** (module contract) — `packages/agent-runtime` reads the `agentTools`/`capabilities` fields from `ModuleManifest` that issue #29 defines, and uses the `ModuleRegistry` mechanism issue #29 built to assemble a given agent's available tools.
