**Blocked by:** #1392, #1813
**Model tier:** medium

## Context

Model tier rationale: A second paid pipeline step that copies the existing speaker-suggestion pattern (gateway call outside any transaction, checkpoint written with the card), plus one gateway operation registration and one new ADR; no new lifecycle or isolation contract.

When a recording overlaps two or more Events, #1813 creates a single suggestion card in Processing proposals whose envelope proposes a new Event, and the user has to work out which meeting it was. The recording's content usually settles it (a recording about "sprint" and "iOS" belongs to the sprint planning, not to the accountant call that overlapped it). This issue adds a model call that recommends one of the overlapping Events from the meeting notes (#1695) and puts the recommendation, the candidates and the reason on the card.

Today the transcription worker (`semprec-transcribe`) already makes one comparable paid call, the speaker suggestion (`backend/services/semprec-transcribe/src/speakerSuggestion.ts`, `runSuggestSpeakersStep` in `transcriptionTask.ts`, `backend/packages/data/src/transcription/transcriptSpeakerSuggestion.ts`): it reads a snapshot, calls `gateway.complete()` outside any transaction, and then creates the cards and writes a checkpoint on the source Files item in one transaction. `docs/adr/2026-09-23-transcription-worker-writes-event-match-results.md` describes the match step as a deterministic, non-LLM step; this issue adds a paid recommendation to that step, which needs its own ADR (see Task).

The card carries its display data in the `context` property that #1451 adds to Processing proposals (candidates, reason and recording facts are read only by clients). The gateway operation map in `backend/services/semprec-ai-gateway/src/completeHandler.ts` (`OPERATION_REQUIRES_PROJECT_ITEM`) is also edited by #1392; both add independent entries.

Decisions:

- The model never writes the Event edge. Whatever it recommends, the outcome is a card the user confirms; with no usable recommendation the card keeps the new-Event envelope from #1813.
- A recommendation is used only when its `eventId` is one of the candidates; anything else counts as no recommendation. The call is made only for two or more candidates (zero or one never pays).
- The reason is written by the model in the tenant user's UI language (`users.locale`), one short sentence.
- The recording quote shown on the card is chosen deterministically, not by the model: the first segment of at least five words, shortened to 120 characters.
- The operation is named `transcript_event_match` and is not attributed to a project (`projectItemId: null`), like the other transcript operations.

## Task

Load `ai-gateway`, `adr-conventions`, `state-writes`, `canonical-keys` and `testing`.

1. Gateway: add `["transcript_event_match", false]` to `OPERATION_REQUIRES_PROJECT_ITEM` in `completeHandler.ts`, extend the operation lists in the doc comments of `completeHandler.ts` and `backend/packages/shared/src/aiGatewayClient.ts`, and add a case to `backend/services/semprec-ai-gateway/src/__tests__/completeHandler.test.ts` (the operation is accepted without a project and its call row stores the operation, so the usage report counts it).
2. Worker request and parser: add `backend/services/semprec-transcribe/src/eventRecommendation.ts` with `buildEventRecommendationRequest(notes, candidates, locale)` and `parseEventRecommendationContent`. The request is `gateway.complete()` with `operation: "transcript_event_match"`, `temperature: 0`, `responseSchema` `{ eventId: ["string","null"], reason: string }` (required, no additional properties). The user message contains the meeting notes' title, summary and short summary and, for every candidate, its id, name, date, times, project name and participant names. Obtain the notes with the token replacement of #1695 (`renderMeetingNotes`); the model is told to answer `eventId: null` when it cannot tell.
3. Data side, in `backend/packages/data/src/transcription/transcriptEventMatch.ts`: when #1813's candidate rule yields two or more candidates, `matchTranscriptToEvent` no longer creates the card itself but returns the candidate details (id, name, `date`, `timeFrom`, `timeTo`, `endDate`, project id and name) so the step can ask; add `createTranscriptEventCard(client, { transcriptId, candidates, recommendation })`, used by the step after the call. The card is created with the existing idempotency key `transcript-suggestion:<transcriptId>`, `status: proposed`, a history line saying how many Events overlapped and whether one was recommended, and `context`: `{ role: "event", candidates: [...], reason, recommendedEventId, recording: { durationSeconds, speakerCount, quote: { segmentIndex, text } } }` (the schema of `context` is the one defined by #1451); `candidates` and `reason` are never written to other properties. The envelope is `{ entityKind: "relation", target: <the recommended Event id>, properties: { propertyKey: "event" } }` (the same shape the speaker-mapping cards use with `speakers`) when there is a recommendation, otherwise the new-Event envelope of #1813. The envelope passes `assertValidProposalEnvelope`.
4. Step: change `runMatchStep` in `transcriptionTask.ts` into a bracketed step like `runSuggestSpeakersStep`: read a snapshot in a repeatable-read transaction (the candidates, and whether an edge, a card or the checkpoint already exists); if two or more candidates and no checkpoint, call the gateway outside any transaction; then, in one transaction that re-locks the transcript, create the card and write the checkpoint `eventRecommendation` (`{ recommendedEventId, reason }`) on the source Files item with `writeComputed`. Declare `TRANSCRIPTION_EVENT_RECOMMENDATION_COMPUTED_KEY` in `transcriptionComputedKeys.ts`, register it in the computed key registry in `seed/seedSystem.ts`, export it from `packages/data/src/index.ts`. A retry after the call succeeded never pays again; a locked transcript is skipped like in the other steps. A failed gateway call fails the step like the summary does (retried by the job).
5. ADR: add `docs/adr/<date it is written>-transcription-recommends-the-event-of-an-ambiguous-recording.md` (standalone, no `supersedes`; reference `[[2026-09-23-transcription-worker-writes-event-match-results]]` and `[[2026-09-23-speaker-mappings-are-edges-proposed-on-transcript-cards]]`). It records: the match step may make one paid recommendation call when two or more Events overlap; the recommendation only ever shapes a card, never an edge; the call is bracketed and checkpointed; the `transcript` card production sites stay the match and suggestion steps of `semprec-transcribe` (the table of the speaker-mappings ADR is unchanged); the operation `transcript_event_match` is unattributed to a project.
6. Tests: request/parse unit tests; the step with two candidates and a recommendation (card with relation envelope and complete `context`), with `eventId: null`, with an `eventId` that is not a candidate, a retry after a successful call (no second call, one card), one candidate (edge, no call), zero candidates (no call, card from #1813).

## Scope

### In scope

- The recommendation call, its operation registration, checkpoint, card `context` and relation envelope, and the ADR.

### Out of scope

- The overlap rule itself: #1813.
- Letting the user pick another candidate or reject the card: #1870 and the existing reject route.
- Taking over the Event's project and people after the card is confirmed: #1697; suggesting speakers again after linking: #1942.
- The label of the new operation in the usage breakdown by operation: #1477.
- A card for a recording that overlapped no Event with a recommendation: no model call is made there.

## Acceptance criteria

- When a recording overlaps two Events and the model recommends one of them, one card exists with a relation envelope to that Event, `context.candidates` listing both, `context.reason`, `context.recommendedEventId` and the recording facts, and no Transcripts `event` edge is written.
- When the model answers `null` or an id that is not a candidate, the card keeps the new-Event envelope and `recommendedEventId` is `null`.
- When the job is retried after the model answered, no second gateway call is made and there is still one card.
- When only one Event overlaps, no model call is made and the edge is written as before.
- The gateway accepts `transcript_event_match` without a project, and the usage report counts the call.
