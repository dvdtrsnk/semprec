## Context

Model tier rationale: One small validation added to the existing item create and patch paths, reusing the property list they already load and the writer kind threaded by a blocker, with an existing test pattern; the only care is the enumerated internal callers.

In the app, the new-item form disables Save until the name is filled. The backend does not enforce it: `createItemWithClient` and `updateItemWithClient` in `backend/packages/data/src/chokePoint/itemWrites.ts` accept an item whose title property (the property of type `title`, key `name` in the system databases) is missing, empty or only whitespace, so a client bug, an agent call or an API user can create nameless items that then show as blank rows.

Builds on #1389 (the same create path, which now applies defaults before this check) and #1415 (the writer kind - user, agent or internal - that item writes now receive). #1802 adds select-value validation on the same paths after this.

Decision: the rule applies when the writer kind is user or agent, and only to a title property whose owner is `user`. Internal writers keep their current behavior unchanged, because several of them legitimately create items whose title is written later or derived (see the list below). On create, a missing, null, empty or whitespace-only title is rejected; on patch, a title key that is present and null, empty or whitespace-only is rejected, and a patch that does not mention the title is unaffected.

Decision: surrounding whitespace is not trimmed on storage; the rule only rejects values that are blank after trimming.

Decision (product owner): Transcripts are exempt. A transcript takes its displayed name from its event or from the recording date, so an empty stored title is valid for it; the rule applies to every other collection. The exemption is the database owned by the transcripts module (`TRANSCRIPTS_MODULE_ID` from `seed/tenDatabaseKeys.ts`), for every writer kind.

Internal callers of `createItemWithClient` to confirm unaffected (they run with the internal writer kind or write a system-owned title): `journal/journalStore.ts` (title owner is system), `inbox/inboxStore.ts`, `inbox/inboxTickAction.ts`, `inbox/proposalActions.ts` (creates the item a confirmed proposal describes), `tasks/advanceTaskRecurrenceWithClient.ts` (copies the recurring task's name), `transcription` item creation, mail ingest, and file-upload item creation.

## Task

Load `error-handling` and `testing`.

1. In `itemWrites.ts` add one helper used by both `createItemWithClient` and `updateItemWithClient`: find the database's property of type `title` with `owner: "user"` from the property list the function already loaded; skip the check for the Transcripts database (owner module `TRANSCRIPTS_MODULE_ID`); when the writer kind is `user` or `agent`, throw `ValidationError` with `field` equal to that property's key (for example `name`) when the value is blank as described in the decision. No new database query.
2. In `createItemWithClient` run the check on the properties after #1389's defaults are merged and before the insert, so a rejection leaves no row and no event.
3. Confirm each internal caller listed above still passes its existing tests; where an internal path would be affected, it is wrong to relax the rule for user and agent - report it in the pull request instead.
4. Tests: create with `name: "   "`, `""`, `null`, and no `name` is rejected with 400 and `field` `name` for a user and for an agent; a valid name is accepted; patching `name` to blank is rejected; patching another property of an item is unaffected; a database with no user-owned title property is unaffected; a user or an agent creating or patching a Transcripts item with an empty title succeeds; the internal paths above still create their items.

## Scope

### In scope

- Rejecting a blank user-owned title on item create and patch for user and agent writers, with `ValidationError` on the title key, in every database except Transcripts.

### Out of scope

- Applying property defaults (#1389).
- Validating select values against the option catalog (#1802).
- Enforcing the rule for internal writers, or trimming stored titles.
- The writer-kind threading itself (#1415).

## Acceptance criteria

- When a user creates an item with `name: "   "`, then the call fails with 400 and `field` `name` and no item exists.
- When an agent creates an item with no `name`, then the call fails with 400 and `field` `name`.
- When a user patches `name` to an empty string, then the call fails with 400; when they patch only another property, then it succeeds.
- When inbox capture, transcription, task recurrence, mail ingest and file upload create items, then they succeed as before.
- When a database has no user-owned title property, then create and patch behave as before.
- When a user or an agent creates or patches a transcript with an empty title, then the write succeeds.
