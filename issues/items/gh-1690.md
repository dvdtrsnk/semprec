## Context

Model tier rationale: This removes a mailbox's credential, sync state and server settings together with soft-deleting the mailbox in one transaction, a destructive change to secret-bearing rows where a partial write leaves a live secret behind or loses the mailbox.

Today a mailbox can only be soft-deleted with the generic `DELETE /api/items/:id`: `softDeleteItem` (`backend/packages/data/src/chokePoint/itemTrash.ts`) cascades only into embedded databases, not into the mailbox's Folders and Emails, and nothing removes `external_credentials`, `mail_account_sync_state`, `mail_folder_sync_state` or the server settings, so a deleted mailbox keeps its secret and its live lifecycle.

This issue adds the dedicated removal route and its one transaction. It builds on: the stored server settings (#1473), composition-root dependencies for module routes (#1460) and the sync state and its recorded facts (#1497). The counts the app shows beforehand are #1501. Row-level cleanup on final deletion is #1691.

Removing a mailbox is split into single-mechanism issues that build on this route: soft-deleting the mailbox's folders and messages in a chunked background job, the best-effort cleanup at the provider after commit, refusing the generic delete of a Mailboxes item, and restoring a removed mailbox as needing reauthorization. They are #2029, #2030, #2031 and #2032.

Decision: the removal sets `syncStatus` to `needsReauthorization` in the same transaction, because the credential is gone; a mailbox restored from the trash then shows that state.

Shared-file ordering: this issue also waits for #1689 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Add `DELETE /api/mail/mailboxes/:id` as a custom route of the mail module (authenticated, tenant-scoped, justification `transactional-semantics`); an unknown or foreign mailbox answers 404.
2. Implement the removal in `backend/packages/data/src/mail/mailboxRemoval.ts` as one transaction: set `syncStatus` to `needsReauthorization`, soft-delete the Mailboxes item by its own system path, and delete its credential (`deleteCredential`), its `mail_account_sync_state` row, the `mail_folder_sync_state` rows of its folders and its server settings row. Any failure rolls back all of it.
3. Export the removal function from the barrel and add the route to the route matrix and the tenant isolation test.
4. Tests: a removed mailbox has no credential, sync state, folder sync state or server settings and its item is in the trash with `syncStatus` `needsReauthorization`; a failure injected after the credential delete leaves every row as it was; a mailbox of another tenant answers 404 and is unchanged; a second removal of the same mailbox answers 404.

## Scope

### In scope

- The removal route and its single transaction: the mailbox soft-delete, the `needsReauthorization` status, and deleting the credential, sync state, folder sync state and server settings.

### Out of scope

- The impact report (#1501).
- Soft-deleting the mailbox's folders and messages: the chunked removal job (#2029).
- Stopping the hosted lifecycle, cancelling a Gmail watch or Graph subscription and revoking the token at the provider (#2030).
- Refusing a generic `DELETE /api/items/:id` of a Mailboxes item (#2031).
- The restore hook for a removed mailbox (#2032).
- Deleting rows when an item is permanently purged (#1691).
- The reauthorization flow (#1742).
- Tables added by later mail features (message actions, provider drafts); their removal is added where they are introduced.

## Acceptance criteria

- When a mailbox is removed, then no credential, sync state, folder sync state or server settings remain for it, and the Mailboxes item is in the trash with `syncStatus` `needsReauthorization`.
- When any step of the removal fails, then nothing is removed and the mailbox is unchanged.
- When the mailbox belongs to another tenant or does not exist, then the response is 404 and nothing changes.
