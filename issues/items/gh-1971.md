## Context

Model tier rationale: A single contract step (seed plus direct-SQL cutover on a `schema_locked` database) with an existing pattern, but it edits persisted schema config for every tenant and must land in a later release than the migration it follows.

The Events `date` property is declared with `config: { includeTime: true }` in `backend/packages/data/src/seed/seedTenDatabases.ts`. Nothing in the backend, web or Apple clients reads `includeTime` (only seeds declare it), but clients receive the config through the schema projection. After #1797 has converted every stored Event to a date plus separate `timeFrom` and `timeTo`, the flag is misleading: `date` is always a plain day. Removing it is the contract step of the expand/contract sequence in `docs/adr/2026-09-10-expand-contract-forward-only-migrations.md`: it must ship in a release after the one that carries the conversion, so a rollback target still sees the old shape. The Events database is `schema_locked`, so existing tenants get the change through a per-tenant cutover with direct SQL registered in `backend/packages/data/src/db/tenantCutoverMigrations.ts` (pattern: `transcription/transcriptsCatalogCutoverMigration.ts`).

Subscribed events live in their own read-only database, added by #1962; this issue only touches the Events `date` property and must be placed after that issue in the seed order so the end of the Events seed chain stays in one place.

Shared-file ordering: this issue also waits for #1966 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `adr-conventions` and `testing`.

1. In `seedTenDatabases.ts`, remove `config: { includeTime: true }` from the Events `date` property (leave the other databases' `date` properties alone).
2. Add a cutover (for example `backend/packages/data/src/calendar/eventsDateIncludeTimeContractCutoverMigration.ts`) that removes `includeTime` from the existing Events `date` property config, in the tenant's scope, idempotently, no-oping when the database or the key is absent. Register it in `runTenantCutoverMigrations`.
3. Tests: a fresh seed gives Events `date` without `includeTime`; the cutover removes the key on a database created by the previous seed, leaves other config keys intact, and is idempotent.
4. The pull request records the release it ships in and confirms the release containing #1797 is already deployed.

## Scope

### In scope

- Removing `includeTime` from the Events `date` config in the seed and in existing tenants.

### Out of scope

- The data conversion itself: #1797.
- `includeTime` on any other database's `date` property (Email, MCP and other modules keep theirs).
- Dropping the time-carrying `date` shape from clients; clients already use `timeFrom` and `timeTo`.

## Acceptance criteria

- When a new tenant is seeded, then the Events `date` property has no `includeTime` key.
- When the cutover runs for an existing tenant, then the Events `date` config no longer has `includeTime`, other config keys are unchanged, and a second run changes nothing.
- When the cutover runs for a tenant without an Events database, then it does nothing and does not fail.
