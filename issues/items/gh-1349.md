## Behavior specification

Sensitive data: health records grants and Semp/MCP sensitivity.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: sensitive-data-1

#### (a) Adopted decisions
- Fixed health list vs databases.sensitive in the first grants issue -> use `databases.sensitive` (#1808 is a blocker of #1810 in the job's dependency data; the program's resolved deps override the earlier design note wording about a fixed list).
- Default for custom (non-system) databases without a grant (design note wording "zakázané") -> denied for read and write; non-sensitive system databases stay open -> follows design note; behavior change to confirm. -> Decided by the product owner: no; user-created databases stay readable and writable for agents as today, and only databases marked sensitive are denied by default (#1810). The user can switch a user-created database off for a project (#1841).
- Relation put -> write grant on both endpoint databases -> conservative.
- Refusal type -> ForbiddenError code forbidden, no item content in message; a missing item stays not found.
- Same-transaction guarantee -> grant row read FOR SHARE inside the write transaction, so a revoke waits.
- Do grants apply to runs outside a project (open question) -> they apply to the run's project; runs without a project cannot call generic operations at all today.
- Who grants -> the signed-in user through REST only; admin write functions are not exported from the package barrel (as the MCP grants).
- REST list shape -> only sensitive and user-created databases are listed; PATCH on an open system database is rejected (no deny overrides) -> conservative.
- UI for the grants -> Decided by the product owner: a simple list of collections with a "Semp may read" toggle in the project's Semp settings, section Collections; sensitive collections are off by default; the product owner delivers the screen design. The list is served by #1841.
- Does X3 apply to virtual refs (sleep night) (open question) -> X3 covers refs naming an item; sleep night refs use the same allowance in #1853.
- X3 scope -> one turn (not the whole run/thread), read only, only the referenced item id; relation targets stay hidden -> strictest reading.
- Redaction vs shorter retention (open question) -> redaction with fixed marker `[redacted: sensitive]` on tool results of item.* / database.query / view.query.
- Leaks outside sensitive databases (attachments, transcripts, relation filters, rollups) -> Decided by the product owner: close attachments of sensitive records and filters and aggregations over sensitive databases, because sensitivity is inherited from the item; transcripts and Inbox entries are not classified by content in this version and are sensitive only when linked to a sensitive record (#1999: inherited sensitivity; #2000: filters and aggregations).
- External AI clients using a human token on /mcp -> Decided by the product owner: sensitive databases are denied by default for them too; any model receives sensitive data only with an explicit permission (#1998).
- Tool call arguments, assistant text and compaction summaries with sensitive values -> Decided by the product owner: redacted in the same way as the source, otherwise they leak past the permission (#2001, built on #1827).
- Per-tenant encryption of sensitive content -> not done.

#### (b) Open questions for the product owner
- None remaining; all were decided by the product owner (see (a)).

#### (c) Behavior delivered
Health records and the sleep databases are marked as sensitive. By default the Semp agent of a project can no longer read or write them, and neither can an external AI client connected to /mcp with the user's token; the user's own collections stay available to Semp as today. In the project's Semp settings the user sees a list of collections with a "Semp may read" toggle each (sensitive ones off by default) and can grant or withdraw access per collection (a REST API for it is provided), and the grant is checked inside the same transaction as the read or write it guards. Unreadable databases disappear from the agent's database list and schema, and unreadable relation targets show only as hidden. When the user attaches a single item (for example a health record) to a message, Semp can read that one item in that turn without a grant, but cannot write it and loses access in the next turn. Files, transcripts and Inbox entries linked to a sensitive record are protected the same way, and the agent cannot filter or aggregate over a sensitive database it may not read. Content of sensitive items that the agent reads, and anything the agent writes or says about them in that turn, is not kept in stored run history or compaction summaries; a resumed conversation sees a redaction marker instead. Human use of the same data is unchanged.
