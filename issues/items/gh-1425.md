## Context

Model tier rationale: A pure, side-effect-free derivation function with a table-driven unit test, in one new file and one existing export, without storage, lifecycle or tenant contracts.

The Inbox shows one stack of cards of different kinds: new task, new page content, a file plus a follow-up task, a transcript without an event, a speaker question, a proposal that cannot be used, an item that needs clarification, and a pending approval. The server must name each card's kind in one canonical place so that the card list, the editor schema and the target label are all derived from the same value instead of each client guessing.

Today nothing derives it. `transcriptCardRole` in `backend/packages/data/src/inbox/proposalActions.ts` only tells an event card from a speaker card (a `relation` envelope on `Transcripts.speakers` is a speaker, everything else is an event). The Processing proposals card (`seed/seedInboxPipeline.ts`) carries `kind` (inbox or transcript), `status` and the `proposal` envelope with `entityKind` of `database`, `pageContent` or `relation`. The target database of a `database` envelope identifies its module through `databases.owner_module_id`. The page-content processing method (`processingMethod = pageContent`, `inbox/inboxTypesStore.ts`) targets the Journal or a page.

This issue adds the derivation for the shapes that exist today and exposes it to the card list route (#1807). Kinds that depend on other work are added by those issues to the same function: the journal entry kind by #1975, the recording kind by #1978, the MCP server kind by #1973, and the primary step of a multi-step proposal by #1492.

Decision: `cardKind` is a string union, camelCase values stored nowhere (derived on read): `task`, `event`, `page`, `journal`, `project`, `area`, `company`, `person`, `health`, `file`, `recording`, `mcp`, `invalid`, `clarify`, `transcriptEvent`, `speaker`, `approval`. `baseKind` is the kind of the target the card writes or edits (for an `invalid` card and for a clarification converted into a concrete kind, the kind the card edits). The whole union is declared now so later issues extend the function, not the type.

## Task

Load `canonical-keys` and `testing`.

1. Create `backend/packages/data/src/inbox/inboxCardKind.ts` exporting the `InboxCardKind` union (values above) and a pure function `deriveInboxCardKind(input)` returning `{ cardKind, baseKind }`. The input is the card's `kind`, `status`, stored envelope (or none) and, for a `database` envelope, the `ownerModuleId` of the target database; an approval request is derived by a separate exported constant helper returning `{ cardKind: "approval", baseKind: "approval" }`.
2. Rules for the shapes that exist today: `status = needsClarification` gives `clarify`; a card in `computing` or `computeFailed` (listed with its compute state) gets `cardKind` and `baseKind` by the rules below from its stored envelope when it has one, and `clarify` for both when it has none; `status = invalid` gives `invalid` with `baseKind` from the stored envelope (the editable kind) when one exists, else `invalid`; a transcript card gives `transcriptEvent` or `speaker` through `transcriptCardRole` (export it from `proposalActions.ts` for this use); an inbox card with a `database` envelope maps the target's `ownerModuleId` to `task`, `event`, `project`, `area`, `company`, `person`, `health` or `file` (the people, companies, areas, events, tasks, health records, files and projects modules of the ten databases); a `pageContent` envelope gives `journal` when it places into the day's Journal page and `page` otherwise. An unknown `ownerModuleId` or entity kind never throws: it yields `baseKind` equal to the nearest known fallback and `cardKind` `clarify`, so a future kind cannot break the list.
3. Unit tests (table-driven) covering every rule above, the invalid card with and without an envelope, the unknown-module fallback, and that the function is pure and does not read the database.

## Scope

### In scope

- The type, the derivation for today's shapes and their unit tests.

### Out of scope

- The list route that calls it: #1807.
- Kinds that need schema or modules not yet present: journal entry (#1975), recording (#1978), MCP server (#1973), primary step of a multi-step proposal (#1492).
- Localized labels of kinds and targets; they are produced by the list route via i18n.

## Acceptance criteria

- Given an inbox card whose envelope targets the Tasks database, then `cardKind` and `baseKind` are both `task`.
- Given an invalid card whose stored envelope targets Tasks, then `cardKind` is `invalid` and `baseKind` is `task`.
- Given a transcript card with a `relation` envelope on `speakers`, then `cardKind` is `speaker`; with a `database` envelope on Events, `transcriptEvent`.
- Given a `pageContent` envelope for the Journal, then `cardKind` is `journal`; for another page, `page`.
- Given an unknown target module, then the function returns without throwing.
- Given a card in `computing` without a stored envelope, then `cardKind` is `clarify`; given a `computeFailed` card whose envelope targets Tasks, then `cardKind` is `task`.
