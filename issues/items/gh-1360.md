## Context

Model tier rationale: One known projection change across the schema read path (store read, resolver, response type) with existing manifest and schema-handler test fixtures, but it adds a relation-definition lookup to a shared read, so it is not a one-file mechanical edit.

The client builds filter chips, new-item forms and option pickers from `GET /api/schema`. Today `backend/packages/data/src/manifest/schemaProjection.ts` returns, per property, only `key`, `name`, `owner`, `locked` and (for select and multi-select) `options: [{ key, label }]` — the `ResolvedProperty` type in `backend/packages/data/src/manifest/catalogResolution.ts`. It has no property `id`, no `type` and no `config`, so a client cannot tell a select from a date, cannot render the right control in a new-item form, and cannot know which properties a filter can be built on. `GET /api/databases/:id/properties` has `type` and labels but no config, and `GET /api/properties?databaseId=` has the config but not localized.

What the data already holds: a relation property stores `config.targetDatabaseId` (written by `relationPropertyOps.ts`), its cardinality lives in the `relation_definitions` row (`getRelationDefinitionsByPropertyIds` in `chokePoint/relationsStore.ts`), a date property may carry `config.includeTime`, and a number property may later carry `config.filterPresets`.

Builds on nothing. #1584 adds option colors to this projection, #1622 adds numeric filter presets, #1647 adds quick filters per database, and #1597 declares area filters per database; all of them read the property shape this issue establishes.

Decision: the projection is additive. Existing fields keep their names and meaning, so current clients keep working. Select options stay in the existing `options` array and are not repeated inside `config`.

Decision: a number property is filterable only when its `config.filterPresets` is a non-empty array. Until #1622 lands no number property has presets, so none is filterable yet; the rule is implemented here so the later issue only has to store presets.

## Task

Load `testing` and `canonical-keys`.

1. Extend `ResolvedProperty` in `manifest/catalogResolution.ts` with `id` (the property row id), `type` (the `PropertyType`), `config` and `filterable: boolean`. `resolveProperty` fills `id` and `type` from the `PropertyRow`.
2. `config` is a typed projection, not a dump of the stored object:
   - `relation`: `{ targetDatabaseId, cardinality }`. `targetDatabaseId` comes from the stored `config.targetDatabaseId`; `cardinality` comes from the property's relation definition as stored. A relation property with no readable definition returns `config: {}` rather than failing the whole response.
   - `date`: `{ includeTime }`, boolean, `false` when the stored config has no value.
   - `number`: `{ filterPresets }` passed through as stored when present, otherwise `{}`. Validation and localization of presets belong to #1622.
   - every other type: `{}`. For `select` and `multi_select` the options stay in `options`.
3. `filterable` is true for `select`, `multi_select`, `relation`, `date` and `checkbox`, true for `number` only when `config.filterPresets` is a non-empty array, and false for every other type.
4. In `generateSchemaProjection` (`manifest/schemaProjection.ts`) load the relation definitions for the relation properties of all listed databases in one batched query (`getRelationDefinitionsByPropertyIds`), not one query per property, and pass them to `resolveProperty`.
5. Label localization stays exactly as today (catalog `cs`/`en` for the caller's locale); no new label keys are needed.
6. Add tests in the manifest/schema test suites: a select, a relation, a date with `includeTime`, a number without presets, a number with stored presets, and a text property; assert `id`, `type`, `config` and `filterable` for each, and assert the relation lookup is a single batched query.

## Scope

### In scope

- The new `id`, `type`, `config` and `filterable` fields on every property of `GET /api/schema`.
- The batched relation-definition lookup needed for `cardinality`.

### Out of scope

- Colors on select options (#1584).
- Validation, storage and localized labels of `filterPresets` and `emptyPreset` (#1622).
- Quick filters, default sorts, collection and picker filters (#1647).
- Default values and required title in the schema (#1389, #1519).
- Changing `GET /api/databases/:id/properties` or `GET /api/properties`.

## Acceptance criteria

- When a client calls `GET /api/schema`, then the Projects `status` property has `type: "select"`, a non-empty `id`, `filterable: true` and its `options`.
- When a relation property is listed, then its `config` has `targetDatabaseId` equal to the target database id and `cardinality` equal to the stored relation definition's cardinality.
- When a date property with `includeTime: true` is listed, then `config.includeTime` is `true`; without the key it is `false`.
- When a number property has no `filterPresets`, then `filterable` is `false`; when it has a non-empty `filterPresets`, then `filterable` is `true` and the presets are present in `config`.
- When a text, long-text, url or file property is listed, then `filterable` is `false` and `config` is `{}`.
- When the schema is requested, then the number of relation-definition queries does not grow with the number of relation properties.
- Labels and option labels are localized as before for both `cs` and `en` callers.
