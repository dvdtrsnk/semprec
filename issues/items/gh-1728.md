## Context

Model tier rationale: A small write added to a shared approval-request producer path, but it runs inside the producers' transactions for every request source and must not change their behavior or ordering.

The Semp thread list orders threads by last activity. A thread where an agent has just asked for approval must rise to the top, even if the run that asked started hours earlier (a tick that started at 21:00 and asked at 21:40 has activity at 21:40). Today the only producer of an approval request is `createPendingApprovalRequest` in `backend/packages/data/src/mcp/approvalRequestsStore.ts`, called from two places inside their own transactions: `preflightDestructiveApproval` in `backend/packages/application/src/genericOperationGateway.ts` (destructive generic operations) and `createApprovalGatedMcpInvokeTool` in `backend/packages/agent-runtime/src/mcpInvokeTool.ts` (MCP tool calls); module agent tools that need approval (#1791) will call the same function. The request is linked to a thread only through its run (`agent_runs.thread_id`, #1452); its description and impact are stored by #1683, and the link to its tool call by #1618. The structured tool result fields are #1527.

The list that shows this ordering is #1729. Other events that move activity (a message, a tick run, an approval outcome posted into the thread, #1772) are separate issues.

## Task

Load `state-writes` and `testing`.

1. In `createPendingApprovalRequest` (`approvalRequestsStore.ts`), in the same statement sequence as the insert and therefore the same transaction, update the activity of the requesting run's thread: `UPDATE semp_threads SET last_activity_at = GREATEST(last_activity_at, now()) WHERE id = (SELECT thread_id FROM agent_runs WHERE id = $1)`. A run with no thread (`thread_id` is null) updates nothing and creates the request as before. Never lower an existing `last_activity_at`: PostgreSQL `now()` is the transaction start time, so a transaction that started earlier can reach this update after a newer activity was committed.
2. Because the bump lives in the shared function, both current producers and the module-tool producer of #1791 get it without their own code. Change `genericOperationGateway.ts` and `mcpInvokeTool.ts` only if their call to `createPendingApprovalRequest` needs a changed argument.
3. Tests: a request created from the gateway path and one from the MCP path each raise the thread's `last_activity_at` to the creation time; a run without a thread leaves every thread untouched; a rolled-back request transaction leaves `last_activity_at` unchanged; a delegated run's request bumps the thread its run is linked to; a request transaction started before a newer committed activity preserves that newer activity.

## Acceptance criteria

- When an agent run linked to a thread creates an approval request (destructive operation or MCP tool call), then the thread's `last_activity_at` is the later of its existing value and the request's creation time.
- When a request transaction started before a newer activity committed on that thread, then creating the request never moves the activity backwards.
- When the run has no thread, then request creation behaves as before and no thread row changes.
- When the surrounding transaction rolls back, then the thread's `last_activity_at` is unchanged.
- A tick that started earlier stores its later request time in the linked tick thread's `last_activity_at`.
