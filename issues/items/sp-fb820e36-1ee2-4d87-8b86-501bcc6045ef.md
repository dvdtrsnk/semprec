## Context

Model tier rationale: A classification flag added to one error class and read in one route handler, on a path that handles the OAuth code, verifier and client secret. The change is small and adds no route, table or column, but the code redaction it must keep intact is the privacy boundary of the connect flow, so the tests must pin both sides of it.

`POST /api/mail/mailboxes/oauth/complete` (`createMailOauthCompleteRouteHandler` in `mail/mailOauthRouteHandlers.ts`, source #1686) exchanges the caller's `code` at the provider's token endpoint with `exchangeAuthorizationCode` (`mail/oauthTokenExchange.ts`). When the token endpoint answers 400 or 401, the exchange reads the provider's short `error` code (`readProviderError`, restricted to the fixed set `PROVIDER_ERROR_CODES`: `invalid_request`, `invalid_client`, `invalid_grant`, `unauthorized_client`, `unsupported_grant_type`, `invalid_scope`, `consent_required`) and throws `MailAuthorizationCodeRejectedError(message, providerError)`. Before it does so it blanks that code to `null` when it occurs inside the submitted `code`, the PKCE verifier or the client secret (`providerCode.includes(secret)`), so no thrown message or field can contain a secret. The handler then answers 400 `validation_failed` (field `code`) only when `error.providerError === "invalid_grant"`; every other refusal propagates, so the adapter logs it and answers a generic 500, because `invalid_client` and the others are faults of this deployment and not of the caller's input (fix `55e9665c` of #1686).

The recheck of #1686 found the defect this source fixes (`issues/handovers/gh-1686.md`, finding 6, verified against the code at the integration tip): a caller-chosen `code` that is a substring of the provider's error token, such as `a`, `grant` or `invalid_grant`, makes the redaction blank `invalid_grant` to `null`, so the handler no longer recognizes the provider's answer and the request ends 500 and is logged as an unexpected error instead of answering 400. The state is already consumed, nothing is created and no secret is logged, so the harm is a wrong status and a spurious error log line on input the caller chose. No provider issues such a code.

The redaction itself is right and stays: the provider's error code is one of seven fixed strings and can never contain a secret that is not equal to part of it, but the thrown error must keep containing nothing that equals part of a secret. What is wrong is that the handler classifies the answer from the redacted field. The classification has to be carried by something that cannot hold a secret.

## Task

Load `error-handling`, `io-hardening` and `testing`.

1. In `mail/providerTypes.ts`, give `MailAuthorizationCodeRejectedError` a third constructor parameter `readonly grantRefused: boolean`: true when the token endpoint refused the grant itself (`invalid_grant`), false for every other refusal. It is a boolean, not a string, so it can never carry a secret. Update the docstring.
2. In `exchangeAuthorizationCode` (`mail/oauthTokenExchange.ts`), compute `grantRefused` from the provider's error code before the redaction: `providerCode === "invalid_grant"` (the value `readProviderError` returned). Pass it as the third argument. The redaction of `providerError` and the message text (`status <n>` plus `, error <code>` only when the code survived) do not change.
3. In `mail/mailOauthRouteHandlers.ts` (the `catch` after the exchange), answer 400 `validation_failed` with `field: "code"` when `error instanceof MailAuthorizationCodeRejectedError && error.grantRefused`, and no longer compare `error.providerError`. Update the comment that explains the mapping: the classification is carried by `grantRefused` because `providerError` is blanked when the caller's code happens to contain it. Every other refusal still propagates.
4. Tests:
   - `__tests__/oauthTokenExchange.test.ts`: an `invalid_grant` answer gives `grantRefused: true` whatever the secrets are, including when the submitted `code` is `a`, `grant` or `invalid_grant` and when the client secret is `invalid_grant`; in each of those cases `providerError` is `null` and the message is `OAuth code exchange rejected the authorization code (status 400)` without the error code, and for the secret `invalid_grant` neither the message nor `JSON.stringify(error)` contains it, as the existing redaction test requires; `invalid_client`, `invalid_request`, an unknown code and a non-JSON body give `grantRefused: false`; the Microsoft administrator-consent answers still throw `MailAdminConsentRequiredError`.
   - `__tests__/mailOauthRoutes.test.ts`, next to the existing "answers 400 validation_failed for a code the provider refuses as invalid_grant": completing with the code `a` (and with `invalid_grant`) against a fake provider that answers `invalid_grant` answers 400 `validation_failed` with `details.field` `code`, creates nothing and leaves the state used; the same code against a fake provider that answers `invalid_client` still propagates the unexpected error and creates nothing.
   - `services/semprec-api/src/__tests__/mailOauthHttp.test.ts`: the same request over HTTP answers 400 `validation_failed`, not 500.

## Scope

### In scope

- Classifying the token endpoint's `invalid_grant` answer independently of the redaction of its error code.

### Out of scope

- Weakening or reshaping the redaction: `providerError` is still `null` when it occurs inside the code, the verifier or the client secret, and no message or field gains a secret.
- A live Google or Microsoft sign-in; the provider is a fake in every test.
- Any other mapping of a provider refusal (`mail_admin_consent_required`, the 500 for a deployment fault) and the reauthorization branch of `complete`.
- The public callback route, which passes `code` and `state` on and never exchanges.

## Acceptance criteria

- When a caller completes a sign-in with a `code` that is a substring of `invalid_grant` (`a`, `grant`) or equal to it, and the token endpoint answers `invalid_grant`, then the answer is 400 `validation_failed` with field `code`, nothing is created and the state is used.
- When the token endpoint answers `invalid_client`, an unknown error or a non-JSON body, then the answer is still the unexpected error (generic 500 over HTTP) and nothing is created, whatever the submitted code is.
- When the client secret, the verifier or the code contains the provider's error code, then `providerError` is `null`, the thrown message does not name the error code and, for a secret equal to the code, no message or serialized form of the error contains it, as before.
