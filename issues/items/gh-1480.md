## Context

Model tier rationale: One write added to the existing send finalization, reusing the existing linking logic, with the main care being transaction scope and idempotency.

Mail sent from Semprec never gets linked to people. The `Link Emails to People` heartbeat (`mail.linkPeopleByEmail`, `backend/packages/data/src/mail/personLinkingActions.ts`) fires only on Emails item creation and reads `mail_message_meta`. A draft (`mail/draft.ts`) has no `mail_message_meta` row when it is created, so the action returns at `if (!meta) return`, and when the sent copy later arrives from the provider's Sent folder, ingest finds the existing row and takes the `existing` branch, which creates nothing and fires no create event. So `senderPeople` and `recipientsPeople` are never filled for sent mail.

`sendDraftEmail` (`mail/send.ts`) finalizes the draft in one transaction (updates the item, moves it from Drafts to Sent). That transaction already knows the envelope and has the item id, so it is the natural place to link.

This builds on #1457, which allows a person to be the sender of many emails; without it the second sent email to the same person would fail. The people derived from a conversation (#1923) and sending over HTTP (#1896) build on this.

Decision: the linking logic is extracted from the heartbeat action into a function that takes the envelope and item id, and both the heartbeat action and `sendDraftEmail` call it, so the two cannot drift. The sent message's sender is the mailbox address; it is linked when it matches a person like any other address.

## Task

Load `state-writes` and `testing`.

1. Extract the body of `createLinkEmailToPeopleAction` into an exported function `linkEmailEnvelopeToPeople(client, { itemId, envelope, emailsDatabaseId, senderPeopleKey, recipientsPeopleKey })` in `personLinkingActions.ts` that resolves the two relation properties, looks up people with `lookupPersonIdByEmail`, and writes the edges with `createRelationWithClient` and `EMAILS_RELATION_CONTEXT`. The action keeps its behavior and calls the function.
2. Make the linking idempotent: an edge that already exists is skipped and not an error.
3. In the finalization transaction of `sendDraftEmail`, call the function with the envelope used for the send (from, to, cc, bcc), so a failure rolls back the finalization with the rest.
4. Add tests in `backend/packages/data/src/__tests__/mailSend.test.ts`: a sent message to a known address gets a `recipientsPeople` edge, and to the person who owns the mailbox address a `senderPeople` edge; an unknown address leaves the relation empty; two sent emails to the same person both link; the existing heartbeat action tests still pass.

## Scope

### In scope

- Linking `senderPeople` and `recipientsPeople` for mail sent from Semprec in the send finalization.

### Out of scope

- Allowing many emails per sender: #1457.
- Linking existing emails when a person gains an address: #1571.
- Any change to when the heartbeat fires.

## Acceptance criteria

- When a draft is sent to an address owned by a person, then the sent email has a `recipientsPeople` edge to that person.
- When a draft is sent from an address owned by a person, then the sent email has a `senderPeople` edge to that person.
- When two sent emails go to the same person, then both are linked and neither send fails.
- When linking is attempted twice for one email, then no duplicate edge is created and no error is raised.
