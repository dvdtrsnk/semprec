## Context

Model tier rationale: A write hook that enqueues a job in the writer's transaction plus a job that edits values other users may have changed by hand creates concurrency and ownership questions on a data path used by mail ingest.

The people of a task made from a thread follow the conversation: when a new person joins the thread (copied in, or the sender of a later message), the task gets them too, unless the people of that task were changed by hand. Senders and recipients are linked to people by the heartbeat action `mail.linkPeopleByEmail` after ingest (asynchronously) and for sent mail by #1480, so edges `Emails.senderPeople` and `Emails.recipientsPeople` appear at different times. The edge-changed hook after a write is #1530. Tasks created from a thread already carry their people as inherited values (#1900); a manual change ends following (#1516).

Decisions: only additions are propagated; removing an edge never removes a person from a task. A person who belongs to the tenant's own mailbox addresses is never added.

Shared-file ordering: this issue also waits for #1916, #2033 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `testing` and `canonical-keys`.

1. Register a relation edge changed hook (the registration function added by #1530) in `domainWriteHooks.ts` for the properties `Emails.senderPeople` and `Emails.recipientsPeople`. On an added edge it enqueues, in the same transaction, a single-flight job `mailSyncThreadTaskPeople` keyed by the message's thread, with payload `{ threadItemId, personId }`. A hook for another property does nothing.
2. Declare the job as a module task in `mail/mailModuleManifest.ts` (`taskNames`). The job resolves the thread's tasks through Threads.tasks and, for each task whose `Tasks.people` link is still unbroken (state on, not `inheritedBroken`), adds the person as an inherited value from the thread unless already present. A task whose link is broken is left alone.
3. Row-lock each task before changing its people so the job and a concurrent manual edit serialize, and re-check the link state under the lock.
4. Publish the usual item invalidation for each task changed.

## Scope

### In scope

- The hook, the job and the propagation of added participants to tasks with unbroken people.

### Out of scope

- Creating tasks and their first people (#1900).
- Removing people when a participant disappears.
- Showing the tasks in the thread detail (#1692).

## Acceptance criteria

- When a new person is linked to a message of a thread, a task of that thread with inherited people gets that person.
- When the task's people were changed by hand, the person is not added.
- A person for the tenant's own address is not added.
- Running the job twice for the same person leaves the task's people unchanged.
