## Context

Model tier rationale: Derived values stored on the task are recomputed from several sources (host edges, event dates and ends, the task's own date) inside the writing transaction, with a time-zone-dependent rule, a shared first-planned-day rule and a data migration, so a missed trigger leaves tasks wrongly hidden or on the wrong day.

A task placed in an event (#1764) disappears from every list, count, search and calendar day until the last of its host events has ended, and meanwhile its day is the day of the event that was added last. Today there is no such state. #1540 created two derived Tasks properties, both owned by the system and written only by the Tasks process: `hiddenUntil` (date with time) and `effectiveDate` (date). #1422 gives Tasks a pre-write transform, #1530 an after-write hook for relation edges, and #1418 the time-zone-aware event end. #1602 exports the first-planned-day rule that records `since` and `sinceTime` when a task moves on, and #1657 normalized stored dates and times. Event ends come from the Events properties of #1416 (the end is `endDate` or `date` plus `timeTo`; a timed event without `timeTo` gets its end filled by #1598; an event without times ends at the end of its last day).

This issue stores the derived values and keeps them correct. Readers use them: lists and counts (#1798), the nightly move (#1674) and the calendar (#1880); the job that reveals a task at the end time is #1782; deleting and restoring an event is #1819.

Decisions:
- The derived values are stored, not computed on read, and a job reveals tasks at the end time (#1782).
- `hiddenUntil` is stored as a UTC ISO instant. It is the latest end among the task's live host events when that end is later than now, otherwise null.
- `effectiveDate` equals `date` when the task has no live host event. While `hiddenUntil` is set, it is the `date` of the live host event added last. When every live host event has ended, it is the later of the task's `date` and that last-added event's `date`.
- Only live (not trashed) events count. An event without a `date` is ignored.
- When a recomputation changes the `effectiveDate` of a task that is `notDone`, whose previous `effectiveDate` is before today and whose `since` is empty, the same transaction also records `since` and `sinceTime` with the rule exported by #1602.

Shared-file ordering: this issue also waits for #1770, #1778 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `db-migrations`, `canonical-keys` and `testing`.

1. Add `backend/packages/data/src/tasks/taskHostEventState.ts` exporting the pure `computeTaskHostState({ date, hostEvents, timezone, now })` (host events as `{ eventId, addedAt, date, endDate, timeFrom, timeTo }` already filtered to live ones, ordered by `addedAt`) returning `{ hiddenUntil, effectiveDate }` by the decisions above, using the event end of the calendar time module (#1418).
2. In the same file add `recomputeTaskHostState(client, taskId)`: lock the task row, read its live host events (edges of `Tasks.hostEvents` ordered by the edge `addedAt`, joined to live Events), call the pure function, and when a value differs write `hiddenUntil` and `effectiveDate` (and `since`/`sinceTime` by the rule above) through `updateItemWithClient` with the allowed system keys, so realtime and hooks apply. A missing or trashed task is a no-op.
3. Triggers, all in the writing transaction: (a) an edge-changed hook (#1530) on the `hostEvents` / `hostedTasks` relation recomputes the task; (b) an Events update hook, when a write changes `date`, `endDate`, `timeFrom`, `timeTo` or the derived `time`, recomputes every live task hosted by that event; (c) the Tasks pre-write transform (#1422, the transform of #1536) sets `effectiveDate` in the same patch whenever a write changes `date` and on create (reading the task's host events through the context client; no host events gives `date`). Register the hooks in `domainWriteHooks.ts`.
4. Backfill: add the converter `backfillTaskEffectiveDate(properties)` (pure and idempotent: sets `effectiveDate` to `date` when `effectiveDate` is empty and `date` is a string; changes nothing else), re-export it from `seed/systemDatabasesModuleManifest.ts`, register a `dataMigrations` entry for `tasks` from `1.2.0` to `1.3.0` and raise the manifest `version` to `1.3.0`.
5. Tests: with an event on 15 October 13:00 to 14:00 in Europe/Prague, adding the task sets `hiddenUntil` to 14:00 local and `effectiveDate` 15 October; a task in an event on 20 October that is then added to one on 18 October stays hidden until the end of the 20th with `effectiveDate` 18 October; adding the first event again reorders and changes `effectiveDate`; extending the event moves `hiddenUntil`; after all events have ended (clock moved), `hiddenUntil` is null and `effectiveDate` is the later of `date` and the last event's day; removing every edge gives `effectiveDate` equal to the (possibly new) `date`; a trashed event is ignored; the since rule fires only under its conditions; the migration sets `effectiveDate` on every task with a `date` and a second run changes nothing.

## Acceptance criteria

- When a task is added to the event 15 October 13:00 to 14:00, then `hiddenUntil` is 14:00 that day in the tenant zone and `effectiveDate` is 15 October.
- When a task sits in an event on 20 October and is then added to one on 18 October, then it stays hidden until the end of 20 October and `effectiveDate` is 18 October; adding the first event again changes the order and `effectiveDate`.
- When an event's end or date changes, then every live task it hosts is recomputed in the same transaction.
- When all live host events have ended, then `hiddenUntil` is null and `effectiveDate` is the later of the task's `date` and the day of the event added last.
- When a task has no host events, then `effectiveDate` equals `date`; after the migration every task with a `date` has the same `effectiveDate`, and a second run changes nothing.
