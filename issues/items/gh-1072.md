**Blocked by:** #997, #1009
**Model tier:** low

## Context

Model tier rationale: One header is added at enumerated write sites with exactly described tests.

No semprec-api response carries a `Cache-Control` header; `grep -rn "Cache-Control" backend/services/semprec-api/src` finds nothing. Response bodies hold one tenant's content: items, mail, blobs, session details. A browser may keep any of them in its disk cache and replay them from there. That includes a shared device after a sign-out, which #1075 turns into a full reload. Caddy does not cache today (`deploy/Caddyfile`), but the API must not depend on every hop behaving that way.

Every response is written in one of three places:
- `sendJson` (`backend/services/semprec-api/src/adapter/http.ts:8-12`). Every adapter route, every bespoke listener, `/mcp`, `/healthz`, and every error and 404 path goes through it. Callers merge extra headers such as `Set-Cookie` in through its `headers` argument.
- `createBlobsRequestListener` writes its own heads (`backend/services/semprec-api/src/blobsHandler.ts:137` 304, `:145` 416, `:167` 206, `:170` 200). #1009 moved its authorization in front of the conditional 304 branch.
- The Graph webhook writes two heads itself (`backend/services/semprec-api/src/graphWebhookHandler.ts:50` the `text/plain` validation echo, `:85` the 202 acknowledgement).

`res.end()` calls after `headersSent` (e.g. `adapter/adapterRoute.ts:116`) add no new head.

## Task

Load `io-hardening` (response headers on every HTTP edge).

1. **`sendJson`.**
   - In `adapter/http.ts`, export `const NO_STORE = "no-store"`.
   - `sendJson` writes `{ "Content-Type": "application/json; charset=utf-8", ...headers, "Cache-Control": NO_STORE }`. Cache-Control comes last, so no caller can weaken it.
   - Update its docstring.
2. **Blob downloads.** In `blobsHandler.ts`, every `res.writeHead` (304, 416, 206, 200) includes `"Cache-Control": NO_STORE`. Do not change the ETag, `Range` or `Content-Disposition` logic.
3. **Graph webhook.** In `graphWebhookHandler.ts`, both `res.writeHead` calls (`:50`, `:85`) include `"Cache-Control": NO_STORE`. Change nothing else.
4. **Tests.**
   - In the existing `backend/services/semprec-api/src/adapter/__tests__/http.unit.test.ts`, update the exact-headers assertion of the `sendJson` case (`:34-45`) and add cases using its `fakeResponse` stub:
     - `sendJson` sets `Cache-Control: no-store`;
     - it keeps a caller's `Set-Cookie`;
     - a caller-supplied `Cache-Control: max-age=60` is overridden.
   - New integration test `backend/services/semprec-api/src/__tests__/cacheControl.test.ts`, built on the dispatcher like `routeMatrix.test.ts` (`:36-57`):
     - every `surface: "api"` entry of `ROUTE_MATRIX` (`backend/services/semprec-api/src/routeMatrix.ts`), requested without credentials, answers with `cache-control: no-store`;
     - with an authenticated session and one uploaded file, `GET /api/blobs/:id` answers `no-store` in each case:
       - a full download (200);
       - a `Range: bytes=0-0` download (206);
       - a matching `If-None-Match` (304);
       - an unsatisfiable range (416);
       - an unknown id (404);
     - `POST /api/mail/graph/webhook?validationToken=abc` (200, body `abc`) and a `POST` with `{"value": []}` (202) both answer `no-store`.

## Scope

### In scope
- `Cache-Control: no-store` on every HTTP response semprec-api writes, and the tests proving it per route.

### Out of scope
- Caddy configuration and caching of the web client's static files (`deploy/Caddyfile`).
- Origin checks on unsafe methods and the WebSocket upgrade (#1044). The `/api/sync` upgrade has no cacheable response.
- Web-client fetch options (#1075 and the web adapters).
- Removing ETag/304 support from blob downloads. It stays, for non-browser clients.
- Tenant routing of Graph notifications (#997).

## Acceptance criteria

- When any `surface: "api"` route in `ROUTE_MATRIX` answers an unauthenticated request, the response has `cache-control: no-store`. A route added to the matrix later is covered automatically (integration, `cacheControl.test.ts`).
- When an authenticated user downloads a blob in full, by range, revalidates with a matching `If-None-Match`, asks for an unsatisfiable range, or asks for an unknown id, each response (200, 206, 304, 416, 404) has `cache-control: no-store`. The 304 still carries the `ETag` (integration, `cacheControl.test.ts`).
- When Graph posts a validation token or a notification batch, the 200 and 202 responses have `cache-control: no-store` (integration, `cacheControl.test.ts`). The validation body is still byte-identical to the token (existing `graphWebhookHandler.test.ts`).
- `sendJson` sets `Cache-Control: no-store` even when a caller passes another `Cache-Control`, and it keeps every other caller header (unit, `adapter/__tests__/http.unit.test.ts`).
- The existing suites (`routeMatrix.test.ts`, `filesAndBlobsHandler.test.ts`, `blobsHandlerAbort.test.ts`, `authHandler.test.ts`, `graphWebhookHandler.test.ts`) pass unchanged (integration).
