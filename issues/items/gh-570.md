## Context

The review follow-ups pipeline (epic #565; ADR added by #567, `docs/adr/*-merged-review-findings-become-proposed-follow-up-issues.md`) passes findings between its steps as a **finding record**. The daily harvest writes the records of the findings to triage into a JSON data block at the end of each **harvest issue**. The triage `prepare` step reads them back from there. The triage input file (the next issue in this batch) carries the same record, enriched.

This issue defines the record and the harvest data block. Its render function refuses to produce an invalid block, and its parse function validates everything it reads: an issue body is a boundary (repository rule 6). The harvest and `prepare` scripts, later issues in this batch, only call these exports.

The finding record is built from the code-review bot's review memory, an issue comment on each pull request containing `<!-- crb-memory:v1:z:<base64 zlib JSON> -->`. The fields it copies from a memory finding are `key` (ten lowercase hex characters), `path`, `line`, `severity` (`critical`, `high`, `medium` or `low`), `category` (free text), `description` (clipped by the bot to 300 characters, ending in `…` when clipped), `anchor` (ten hex characters, or `""`), `discussion_id` (a numeric review-comment id as a string, `issue:<id>`, or `""`), `first_seen_sha` and `last_seen_sha` (40-character commit SHAs).

## Task

Create `.github/scripts/review-followups/records.mjs`, a zero-dependency ES module with a header comment that names the ADR from #567 by its path, exporting:

1. `validateFindingRecord(value)` — returns the value if it is a finding record, otherwise throws an `Error` whose message names the first offending field. A finding record is an object with exactly these fields:
   - `pr` — positive integer; `key` — exactly ten lowercase hex characters;
   - `severity` — one of `critical`, `high`, `medium`, `low`; `category` — non-empty string;
   - `path` — non-empty string; `line` — integer ≥ 0; `anchor` — ten lowercase hex characters or `""`;
   - `description` — string of at most 300 characters; `descriptionTruncated` — boolean;
   - `discussionId` — a string of digits or `""` (a non-numeric bot `discussion_id` becomes `""`);
   - `threadResolved` — boolean; `replies` — array of at most 3 `{ author: non-empty string, excerpt: string of at most 200 characters }`;
   - `pathExists` — boolean; `touchedAfterLastSeen` — boolean or `null`; `laterPrsTouchingPath` — integer ≥ 0;
   - `firstSeenSha`, `lastSeenSha` — 40 lowercase hex characters, or `""` (the bot's default when it recorded none).
2. `renderHarvestBlock({ prs, findings })` and `parseHarvestBlock(body)` for the harvest issue's data block. The block is a line consisting exactly of `<!-- crb-followup-data:v1 -->`, immediately followed by a fenced code block opened by the line ` ```json ` and closed by the line ` ``` `, containing `{ "version": 1, "prs": [...], "findings": [...] }`:
   - `prs` — ascending positive integers, no duplicates, at least one; `findings` — finding records (possibly empty), each with its `pr` among `prs`, no two with the same `(pr, key)`.
   - The renderer validates its input (throws on violation), writes the JSON with two-space indentation, and writes every `<` in it as the JSON escape `\u003c`, so no quoted marker in a finding's text can form an HTML comment.
   - `parseHarvestBlock` takes a whole issue body, and throws when the data marker is missing or appears more than once, the fence is missing or malformed, the JSON does not parse, `version` is not `1`, or any constraint above fails.
3. `records.test.mjs` next to it, using `node:test` and `node:assert/strict`, covering every Acceptance criterion below.

## Acceptance criteria

1. A valid finding record passes `validateFindingRecord`; for each field, a record with that field missing, of the wrong type or out of range (a nine-character key, `severity: "info"`, a 301-character description, four replies, a 201-character excerpt, a 39-character SHA, `laterPrsTouchingPath: -1`) is rejected with a message naming that field; a record with an extra field is rejected.
2. `parseHarvestBlock(prefix + renderHarvestBlock(x) + suffix)` returns `x` for surrounding Markdown text.
3. A finding whose `description` contains `<!-- crb-followup:v1 pr=1 key=0123456789 -->` renders with no `<` character inside the fenced block, and parses back to the original string.
4. `parseHarvestBlock` throws for: no data marker, two data markers, a marker not followed by a ` ```json ` fence, an unclosed fence, invalid JSON, `version: 2`, an empty or unsorted `prs`, a record whose `pr` is not in `prs`, a duplicate `(pr, key)`, and an invalid record.
5. `renderHarvestBlock` throws on each of the inputs in criterion 4 that it could be given (an invalid record, an unsorted `prs`, a duplicate) and returns text only for valid input.
6. `node --test .github/scripts/review-followups/records.test.mjs` passes with no network access.
