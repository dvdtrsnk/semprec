## Context

Model tier rationale: Adds a tenant-owned table that stores and replays response bodies, so tenant and user scoping, expiry and cleanup must be exactly right to avoid replaying one user's data to another.

The iOS app queues card actions offline and replays them. `Idempotency-Key` is honored today only when creating an item (`backend/services/semprec-api/src/itemsHandler.ts` passes it to `item.create`; the `idempotency_keys` table maps a key to the created item). Card actions are not creations: a repeated `PATCH /api/proposals/:id/values` from #1892 would apply twice and add two history entries.

Confirm and reject are already idempotent through the card state (and #1852 keeps that precedence), so they need nothing here.

Decision: a new table stores the first response per key; a repeat with the same key on the same route by the same user returns the stored status and body without running the action again. Rows expire after 24 hours.

## Task

Load `db-migrations`, `state-writes`, `io-hardening` and `testing`.

1. Add a migration creating `idempotent_responses`: `tenant_id` (not null), `user_id`, `key` (text), `route` (text, the route template, for example `PATCH /api/proposals/:id/values`), `request_hash` (text), `status` (int), `body` (jsonb), `created_at`, `expires_at`; unique `(tenant_id, user_id, key, route)`; row-level security like sibling tenant tables; `COMMENT ON TABLE idempotent_responses IS 'semprec:tenancy=tenant'`; grants like sibling tables; index on `expires_at`.
2. Add a store with `runIdempotent(client, { tenantScope, userId, key, route, requestHash }, action)`: inside one transaction, take an advisory lock on the key, return the stored response if present and the request hash matches, answer 400 `validation_failed` (idempotency key reused with a different request) if the hash differs, otherwise run the action, store its status and body, and return it. Failed actions (4xx/5xx) are not stored.
3. Apply it to `PATCH /api/proposals/:id/values` when an `Idempotency-Key` header is present; absent header leaves the route unchanged. The other card routes apply the same helper in the issues that mount them.
4. Delete expired rows opportunistically on each write (bounded batch) and in the permanent-delete path of the card item.
5. Export/purge: the table is transient; add it to `EXPORT_EXCLUDED_TABLES` in `tenantExportJob.ts` and keep it in the purge set.
6. Tests: repeated PATCH values with the same key returns the same response and history has one entry; same key with a different body fails; a different user with the same key gets a fresh execution; an expired row is ignored; tenant B cannot see tenant A's rows.

### Out of scope

- Applying the helper to reset-overrides, type change, recompute and reopen; each route's own issue (#1912, #1937) calls the helper.
- Confirm and reject, which are idempotent through card state (#1852).
- Item creation idempotency, which stays on `idempotency_keys`.

## Acceptance criteria

- When PATCH values is sent twice with the same `Idempotency-Key` and body, then both responses are identical and history has exactly one entry for it.
- When the same key is sent with a different body, then the second call fails with `validation_failed` and nothing is applied.
- When a different user of the same tenant uses the same key, then the action runs.
- When the stored row is older than 24 hours, then the action runs again.
- When another tenant queries the table, then it sees no row.
