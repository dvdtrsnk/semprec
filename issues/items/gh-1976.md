**Model tier:** medium

## Context

Model tier rationale: One new core queue task enqueued in an existing transaction, following the established approvalExecute pattern, with an outbound call that already goes through the connect-time address check; the failure and retry semantics are the part to get right.

Confirming an Inbox card that proposes an MCP server creates the `mcpServers` item and stores the optional credential in the same transaction (`confirmProposalWithClient` in `backend/packages/data/src/inbox/proposalActions.ts`, credential through `storeCredential`). Nothing then loads the server's tools, so the new server has no `mcp_tool_registrations` and the user would have to find and press a separate button. #1972 adds the human route that runs `syncMcpServerTools` (`backend/packages/data/src/mcp/mcpSync.ts`); this issue runs the same sync automatically after the confirm.

The side effect follows the commit (`docs/adr/2026-09-10-side-effects-follow-the-commit.md`): the confirm transaction enqueues a queue job, and the job runs after the commit, so the sync never sees an uncommitted server or credential and never blocks the confirm. Core tasks are declared in `CORE_TASK_NAMES` and `CORE_TASK_AFFINITY` of `backend/packages/queue/src/index.ts` and given a handler in `createCoreTaskList` (`backend/packages/data/src/worker.ts`); `approvalExecute` is the model (`decideAndEnqueueApprovalRequest` enqueues with a derived `jobKey`). The sync records `syncStatus` (`ok` or `error`), `lastSynced` and `syncError` on the server item through the choke point, which also announces the change to connected clients. Later issues build on the job key: the tool-annotation defaults (#1979), the tool-label suggestions (#1983) and the cancellation of follow-up jobs when a confirmation is undone (#1984). The job never writes project grants: the user grants tools on the project's AGENT page (#1382).

Decision: the task is `mcpServerSync` with payload `{ mcpServerItemId, actingUserId }`, runtime affinity `api`, and the stable job key `mcp-server-sync-<mcpServerItemId>`, so a second enqueue for the same server collapses onto the pending job.

Decision: no queue retries (`maxAttempts` 1). A failed sync is already recorded as `syncStatus: error` with a safe `syncError`, so the handler swallows a recorded `McpConnectionError` or tool-list `ValidationError`; the user retries through the route of #1972. An unexpected error still throws.

Decision: the enqueue happens for any confirm that creates an `mcpServers` item, with or without a credential (servers with browser-based authorization have none).

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In `packages/queue/src/index.ts` add `MCP_SERVER_SYNC: "mcpServerSync"` to `CORE_TASK_NAMES` and `"api"` to `CORE_TASK_AFFINITY`.
2. In `mcpSync.ts` add `enqueueMcpServerSync(client, { mcpServerItemId, actingUserId })` using `enqueueJob` with the job key above and `maxAttempts: 1`, and `handleMcpServerSyncTask(pool, payload)` that calls `syncMcpServerTools(pool, mcpServerItemId, { actorId: actingUserId })` and swallows only the recorded failure types. A server item that no longer exists is a no-op.
3. Register the handler in `createCoreTaskList` in `worker.ts` (`requireString` on both payload fields) and make sure `createApiQueueRuntime` still passes its affinity check.
4. In `confirmProposalWithClient`, after the item is created and the credential stored, call `enqueueMcpServerSync` when the target database is `mcpServers`. Pass the acting user from the confirm route (`createConfirmProposalRouteHandler` in `inboxRouteHandlers.ts` reads it from the request identity) as a new optional parameter.
5. Export what the other packages need through `backend/packages/data/src/index.ts`.
6. Tests: the job exists after the confirm commits and not when the confirm rolls back; confirming twice leaves one pending job; running the handler against a test MCP server registers its tools and sets `syncStatus: ok`; against an unreachable server it records `syncStatus: error`, does not throw and is not retried; a confirm for a non-MCP target enqueues nothing; the credential is never part of the payload.

## Scope

### In scope

- The `mcpServerSync` task, its enqueue in the MCP-server confirm and tests.

### Out of scope

- The human sync route (#1972).
- Applying project grants or choosing which tools to enable: never done by the confirm or this job; the user grants tools on the project's AGENT page (#1382).
- Retrying a failed sync automatically, and undoing a queued sync when a confirmation is undone (#1984).
- Any change to what a sync registers.

## Acceptance criteria

- When an MCP server card is confirmed, then after the commit one `mcpServerSync` job exists with the key `mcp-server-sync-<id>` and a payload without any credential.
- When the job runs against a reachable server, then its tools are registered and the server item shows `syncStatus: ok`; clients connected to the tenant receive the item change.
- When the server is unreachable, then the item shows `syncStatus: error` with a safe message, and the job is not retried.
- When the confirm fails and rolls back, then no job is enqueued.
