**Blocked by:** #272

## Context

Four test-coverage findings from post-merge reviews (of #97's, #101's and #103's pull requests) were never addressed. None of them is a production-code defect — each is a test that passes for the wrong reason or a delivered behavior with no test at all — and all four are still on `develop`. They are grouped here because the whole change is test-only.

**1. `web/src/api/__tests__/httpGenericOperations.test.ts` — `linkItem` body never asserted.** The link/unlink test records only `url` and `method` in its `calls` array, so the POST body `{ targetItemId }` that `httpGenericOperations.linkItem` sends is never checked. Dropping the body, or renaming the key, would keep the test green.

**2. `backend/packages/data/src/__tests__/inboxPipeline.test.ts` — partial idempotency assertion.** The "re-running the seed is idempotent" test asserts only that the `inbox` database count stays at 1 after a second `seedSystem` call. `inboxItemTypes` and `processingProposals` are seeded by the same guard but are never asserted, so a future regression in either would not be caught.

**3. `backend/packages/data/src/__tests__/inboxTick.test.ts` — test double does not mirror the production handler.** `capturingTickRegistry` casts `actionConfig` straight to `{ inboxDatabaseId: string }` with no validation, bypassing the boundary check the production `semprec.tick` handler performs. That handler (`backend/packages/data/src/inbox/inboxTickAction.ts`) parses its config through `semprecTickActionConfigSchema = z.object({ inboxDatabaseId: z.string().uuid() })`, so it rejects an absent value, a non-string, **and** a string that is not a UUID. With a misconfigured heartbeat the double would silently pass `undefined` to `getItemById` instead of throwing the way production does.

**4. `backend/packages/data/src/__tests__/inboxTick.test.ts` — queue affinity tested on one path only.** Queue-affinity routing is asserted for the create path (`createInboxItemWithClient` with an explicit `queueAffinity` map), but #103 also threads `queueAffinity` through `chokePoint.updateItem` and `chokePoint.softDeleteItem`, and neither is covered — two of the three `onItemEvent` kinds have no test.

## Task

- **`httpGenericOperations.test.ts`**: widen the `calls` array to `Array<{ url: string; method?: string; body?: unknown }>` and record the request body in the `fetchImpl`. The parse must be conditional — `httpGenericOperations.unlinkItem` sends a bodyless `DELETE`, so the unguarded `JSON.parse(String(init?.body))` used by the neighbouring tests throws `SyntaxError` on that second call; record `init?.body === undefined ? undefined : JSON.parse(String(init.body))` or equivalent. The existing assertion in that test is an `expect(calls).toEqual([...])` over `{ url, method }` objects, which fails for the link call once the pushed objects carry a `body` key (Vitest's `toEqual` ignores keys whose value is `undefined`, so the bodyless unlink entry would still match) — rewrite it so it still pins both calls' url and method and additionally asserts the link call's body: `expect(calls[0]).toMatchObject({ body: { targetItemId: "f2" } })`, with the unlink call asserted to carry no body.
- **`inboxPipeline.test.ts`**: extend the idempotency test to assert that the `inboxItemTypes` and `processingProposals` database counts are also still 1 after the second `seedSystem` call.
- **`inboxTick.test.ts`**: make `capturingTickRegistry` validate `actionConfig` through the very schema the production handler uses instead of casting — import `semprecTickActionConfigSchema` from `backend/packages/data/src/inbox/inboxTickAction.ts` (export it from that module if it is not exported yet; that export is the only production-file change this issue permits) and `parse` the raw config with it, so the double rejects an absent value, a non-string and a non-UUID string exactly as production does.
- **`inboxTick.test.ts`**: add a direct test that invokes `capturingTickRegistry`'s handler with a malformed `actionConfig` (missing `inboxDatabaseId`, and a non-UUID string) and expects it to throw, so the mirroring is asserted rather than assumed.
- **`inboxTick.test.ts`**: add a test that builds a choke-point with a non-empty `queueAffinity` map (`new Map([[SEMPREC_TICK_ACTION_ID, SEMPREC_TICK_QUEUE_NAME]])`) and asserts that the `onItemEvent` jobs enqueued by `chokePoint.updateItem` and by `chokePoint.softDeleteItem` carry the expected `queue_name`, mirroring the existing create-path assertion.

## Scope

### In scope

- The four test changes above, in the three named test files, plus the direct test of the validated double.
- Exporting `semprecTickActionConfigSchema` from `backend/packages/data/src/inbox/inboxTickAction.ts` so the test can use the production schema.

### Out of scope

- Any production-code change other than exporting `semprecTickActionConfigSchema`. If one of these tests fails against current production behavior, that is a defect to report on this issue rather than to fix here.
- The slow embedded-Postgres runtime of the backend suite.

## Acceptance criteria

- The `linkItem` test fails if the request body or the `targetItemId` key is removed.
- The seed idempotency test fails if a second `seedSystem` call duplicates the `inboxItemTypes` or `processingProposals` database.
- `capturingTickRegistry` rejects an `actionConfig` whose `inboxDatabaseId` is absent, not a string, or not a UUID — the same inputs the production handler's schema rejects — asserted by a test that hands the double a malformed config directly and expects it to throw.
- Queue-affinity routing is asserted for the update and soft-delete paths as well as the create path.
- `pnpm test` in `backend/` and `pnpm test` in `web/` both pass.
