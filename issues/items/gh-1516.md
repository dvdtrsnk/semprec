## Context

Model tier rationale: This changes the authorization and ownership contract of the choke point's two write paths (a new ownership handoff for a user-owned property) and must keep link state consistent inside the write transaction for both sides of an edge, so a mistake silently breaks or preserves links for every inheriting rule.

An inherited value follows its source until a person or Semp changes it on purpose. #1403 stores links and exposes them on reads; this issue makes the choke point maintain their state. #1415 threads a writer kind (`user`, `agent` or `system`) into item and relation writes; this issue is the first consumer of it.

Today the choke point does not know why a value changed. `updateItemWithClient` (`chokePoint/itemWrites.ts`) rejects relation keys in a properties patch, so plain properties are written there; relation values are edges written by `createRelationWithClient`, `updateRelationWithClient` and `deleteRelationWithClient` (`chokePoint/relationOps.ts`). `assertRelationPropertyWritable` (`chokePoint/relationEdgeContext.ts`) returns immediately for a property whose owner is `user`, so nothing stops a background process writing a user-owned relation. The single-writer ownership ADR (`docs/adr/2026-09-10-single-writer-ownership-model.md`) requires an explicit, declared handoff before a process may write a property it does not own.

Decisions:

- Only `user` and `agent` writes end a link. Every `system` write leaves the state unchanged, including a system write under the process id `valueLinks`.
- A link ends only when the value actually changes: patching a property to the value it already holds, putting an edge that already exists, deleting an edge that does not exist, and replacing edge metadata do not end it. This keeps a client that saves a whole form from ending links by accident.
- Adding a value (a second project, an own company) ends the link of the whole property, as does removing or replacing one. The first writer to end it is recorded; a later write to an already broken link changes nothing.
- An edge belongs to two items, and the linked property may be on either side. A write through the relation property of the project (`Projects.files`) adds a project to the file's `projects` value, so the link of the file's side is the one that ends. The check therefore resolves both sides of the relation definition.
- Handoff: the process `valueLinks` may write a user-owned property only while a `value_links` row with state `on` exists for that item and property key; otherwise it is rejected with `owner_violation` (403). This is the declared handoff the ownership ADR asks for, and it is also recorded under Decisions in the batch epic. The transformed-key extension is recorded in the batch 11 handoff ADR.

#1593 is the system writer that uses the handoff; it must create the row (state `on`) before it writes the value. #1587 builds the explicit unlink and relink operations on the same state, and #1758 asks for approval before Semp ends a link.

## Scope

### In scope

- Ending a link on user and agent writes for plain properties and relation edges, in the writer's transaction.
- The `valueLinks` handoff check on both write paths.
- Invalidation of items whose link state changed through an edge write.

### Out of scope

- Storing links and the read field: #1403.
- The explicit `link.unlink` and `link.relink` operations: #1587.
- Asking for approval before an agent write ends a link: #1758.
- Creating link rows and copying values: #1593.
- Cleanup when a source is trashed or purged: #1656.

## Acceptance criteria

- When a user changes a linked property through REST, then the link reads `inheritedBroken` with `brokenBy: "user"`; when Semp does it through MCP, then `brokenBy: "agent"`.
- When a `system` writer (including process `valueLinks`) changes the value, then the state stays `on`.
- When a second project is added to a file with a linked `projects` value, then the link is broken; relinking is a separate operation.
- When a write does not change the value (same value, existing edge, absent edge, metadata only), then the state is unchanged.
- On a visible live item, a valueLinks user-key write, including a transform-added null/equal value, without its own `on` row gets 403 `owner_violation` with no value, link or event written.
- The state change and the value change commit or roll back together.
- Rows of another tenant are never read or changed.
- Protected valueLinks relation contention follows the scoped ADR: fixed 409 value_link_busy, full rollback of prior state/jobs/events even after catch/savepoint, and exact timeout restoration or rollback. Prove both source/advisory orders, populated-rollup queue cycle, A/B/replay/update/delete/hooks/pre-held compositions, 403/busy precedence, owner lifetime and unrelated error identity; no global deadlock claim.
