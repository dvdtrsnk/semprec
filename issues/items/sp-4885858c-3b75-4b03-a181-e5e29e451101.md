### Requirement gh-1698: [calendar-events 08/12] Skip transcribing audio attached to an Event

#### Context

Model tier rationale: One known mechanism (a relation check in an existing heartbeat action plus a per-tenant action_config cutover) across a seed, an action and a cutover migration, with the existing transcription tests as fixtures, but it changes persisted heartbeat config on every tenant.

Today the `core.filesTranscriptionTrigger` heartbeat action (`backend/packages/data/src/transcription/transcriptionActions.ts`, `createFilesTranscriptionTriggerAction`) fires on every Files item creation. It enqueues a transcription job for a file whose blob is `audio/*` and that carries no `Emails.attachments` edge, because an emailed audio attachment is not a standalone recording. The heartbeat's `action_config` (`{ filesDatabaseId, attachmentsRelationPropertyId }`, validated by `filesTranscriptionTriggerConfigSchema`) is resolved once at seed time in `backend/packages/data/src/seed/seedSystem.ts`.

#1588 adds the `Files.events` relation (property key `events`), so a file can be attached to a calendar Event. #1645 lets the upload request attach the file to an item in the same transaction, so the `Files.events` edge exists when the Files item is committed, and the trigger (which runs after commit) sees it. #1574 adds the recording upload endpoint; that issue also changes this same trigger, so the two must be merged one after the other.

Without this issue, an audio file attached to an Event (for example a voice memo on a meeting) would be transcribed as if it were a standalone recording and would create a Transcriptions row the user never asked for.

Decision: an audio file attached to an Event is a plain attachment, not a recording. It is not transcribed and does not become a recording; recordings are created only through the recording upload endpoint from #1574.

Shared-file ordering: this issue also waits for #1675 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Follow `transcription/transcriptionRequeueHeartbeatCutoverMigration.ts` and `docs/adr/2026-09-10-app-code-post-migration-steps.md`: a new file `transcription/transcriptionTriggerEventsCutoverMigration.ts`, one transaction, idempotent (no-op when the key is already set, when the heartbeat does not exist, or when the Files database or its `events` property does not exist yet), and registered in `runTenantCutoverMigrations` in `db/tenantCutoverMigrations.ts`.

### Requirement gh-1743: [recordings 16/17] Release a trashed Event's transcript edge and keep its inherited values as own

#### Context

Model tier rationale: A narrow change to two existing paths (match and card confirm) around a stale edge to a trashed event, with the related inheritance behavior covered by tests built on blockers.

Deleting an event is a soft delete (`chokePoint/itemTrash.ts`); relations stay until purge. Two things follow. First, the cardinality trigger ignores `deleted_at`, and `matchTranscriptToEvent` (`transcription/transcriptEventMatch.ts`) treats any `event` edge as linked (`listRelationsForItem` does not filter deleted counterparts), so a transcript whose event is in Trash returns `alreadyLinked` and cannot be attached to another event (the write ends in `cardinality_violation`). Second, the project, company and people a transcript took over from the event must stay with it as its own values when the event is deleted (the company too, although it came through the project), and a restore must not reconnect them. Those value links are detached by #1656 and inherited by #1697; the cardinality now allows several transcripts per event (#1464).

This issue makes the match and the confirm of a pairing card treat an edge to a trashed event as no link: the edge is removed in the same transaction as the new link. A transcript whose event is in Trash is shown as having no event (that read side is #1636); after a restore the original edge is back in effect only if it was not replaced. The generic `PUT` of the edge keeps returning `cardinality_violation` until the app offers an explicit "assign to event" action, because that is a deliberate user write.

#### Task

Load `state-writes`, `error-handling` and `testing`.

1. In `matchTranscriptToEvent` compute the transcript's existing edges excluding counterparts with `deleted_at` set; only a live edge returns `alreadyLinked`. When linking a candidate, delete a stale edge to a trashed event in the same transaction first.
2. In the confirm path of a pairing card (`inbox/proposalActions.ts`, the `database` envelope on Events and the `event` relation envelope) delete a stale edge to a trashed event in the same transaction before writing the new edge.
3. Add an integration test of the whole sequence with the blockers' behavior: delete an event, check the transcript keeps its project, company and people as own values with no value links, restore the event and check the values are not reconnected, and that a transcript of a trashed event can be attached to another event by the match and by a card confirm.

### Requirement gh-1712: [transcripts 07/19] Backfill meeting notes for older transcripts

#### Context

Model tier rationale: A per-tenant sweep that re-enters the existing idempotent job and checkpoint seams, plus a small change to how a failed re-run of a finished transcript is recorded; paid-call fan-out is bounded by the selection predicate and per-tenant budgets.

#1695 makes structured meeting notes (`computed.meetingNotes`) part of every finished transcript. Transcripts finished before that change have segments and a free-text summary but no notes, so their detail view would stay without title, decisions and action items. Re-running the pipeline for such a transcript is cheap and safe: `enqueueTranscriptionJob` (`backend/packages/data/src/transcription/transcriptionJob.ts`) re-enqueues under the original job key and every step resumes from its checkpoint, the summarize step skips when its key exists, so the paid audio stages (diarization, speech recognition) are not repeated. Only the summarize call is paid again.

System work runs per tenant (`docs/adr/2026-10-06-system-work-fans-out-per-tenant.md`); the post-migration cutovers already do (`runTenantCutoverMigrations` in `backend/packages/data/src/db/tenantCutoverMigrations.ts`, which runs every registered cutover once for each maintained tenant in that tenant's scope).

Decision: the sweep is a tenant cutover that enqueues only transcripts that are `done`, have `computed.segments`, have no `computed.meetingNotes`, and whose `item_automation` is not `error`, `locked` or `pending`. Failed rows are already handled by the daily requeue sweep, a locked row must never be touched, and a pending row is already being worked on. Because the predicate selects on the missing key, running the cutover repeatedly converges and does not enqueue a transcript whose notes exist.

Shared-file ordering: this issue also waits for #1707 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1699: [health 02/09] Add and rename select options on schema-locked databases

#### Context

Model tier rationale: It relaxes the schema-lock rule for a defined class of schema writes on system databases, adds a new operation across the shared catalog, authorization, REST and approval seams, and needs a lock to avoid lost concurrent updates.

Options of a select or multi-select can be changed only through `PATCH /api/properties/:id` with the whole `config.options` array (operation `property.patch`, capability `core.schema.write`, not destructive), and only on a database that is not schema-locked (`updatePropertyConfig` calls `assertPropertySchemaMutable` in `backend/packages/data/src/chokePoint/propertiesStore.ts`, which throws `SchemaLockedError` or `PropertyLockedError`). Every system database is schema-locked, so Health records (and every other system select) cannot get a new tag. Also, replacing the whole array loses a concurrent addition.

This issue adds two narrow operations, `property.option.add` and `property.option.update`, that may change only the option list of a select or multi-select on a locked database, and records that exception to the lock rule in an ADR. It builds on #1584, which defines the optional `color` on options and its validation (`assertValidSelectOptions`). #1994 uses it to create an option while confirming an Inbox proposal.

Decisions:
- Exposed over REST and the generic catalog only. It is not exposed as an agent tool or MCP tool; the assistant proposes a new option through an Inbox proposal (#1994) and a person confirms it. Reason: a schema change is sensitive and must be approved by the user, so the assistant can never create an option through a tool.
- The key is generated by the server from the label: ASCII camelCase without diacritics ("Dentální hygiena" gives `dentalniHygiena`); a collision with an existing key gets a numeric suffix (`bylinky2`). An empty result uses `option`.
- A label that matches an existing option's label, case- and diacritics-insensitive, in the stored label or in the Czech or English catalog label of that option ("léky" equals Medication), is refused with 409 and the new additive error code `option_label_exists` carrying the existing option's `key`.
- At most 100 options per property and a label of 1 to 60 characters; otherwise 400 `validation_failed`.
- Removing an option is out of scope.
- A property that is itself `locked` still refuses (`PropertyLockedError`), and `property.patch` on a locked database still refuses with `SchemaLockedError`.

Shared-file ordering: this issue also waits for #1693 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.
