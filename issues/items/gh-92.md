## Approved behavior specification

This epic preserves the complete approved behavior of source issue #27, inlined here so the epic is self-contained.

### Source behavior: [07/22] Mailbox UI, sending, and heartbeats over email

## Context

The mock (`mock.html`) currently represents emails as a plain table with tabs and inline reply. Issue #26 ("IMAP sync core") replaces that with a real synchronization mechanism between the IMAP server and the local DB — structured `envelope`, `thread_id`, `message_id`, thread reconstruction, folder sync. This task (issue #27) builds on top of the data layer from issue #26: it delivers the layer through which the user and the AI actually use email — the mailbox UI, sending drafts and messages, and heartbeats over the inbox. Without this layer, issue #26 would only deliver invisible synchronization with no interface.

The mock already contains one important thing that needs to be carried forward and tightened: the Email project's AGENT.md explicitly forbids the agent from sending a message without draft approval, but allows it to create a draft. So far this is only a textual instruction that the agent may or may not follow. This task turns it into an enforced rule at the generic API level.

## Task

Build three things on top of the data layer from issue #26:

1. **Mailbox UI as a dedicated registered view type** (`mailbox-client`) — not an extension of the generic table, but a bespoke component with its own layout that underneath uses the purely generic layer (relations, create-item endpoint, property model).
2. **API for creating drafts and sending** — the same call for the user and for the AI, but with an enforced difference in behavior depending on who/what triggered the call. Creating a draft is always allowed; sending is always enforced to require confirmation unless the project explicitly grants autonomy.
3. **Generalization of the heartbeat trigger over the inbox** — as a generic mechanism that the (not yet started) package-tracking project can later be built on.

All three points come with a set of concrete edge cases that need to be solved so the module is usable over real mailboxes (Gmail, a custom domain behind an MTA), not just a demo.

## Scope

### In scope

**Mailbox UI (new view type `mailbox-client`)**
- Registered as another record in the `views` table (the same mechanism as the Journal's `temporal-switcher`, from the Journal issue) — not configuration on top of the generic Table view, because the interaction model (hover actions, multi-pane collapse, keyboard navigation) differs too much from the table renderer.
- Layout: a sidebar of folders/labels with an unread count on each; a message list with hover actions (archive/delete/mark read directly on the row, not only after checking a box); a reading pane on the right that collapses into a single pane with a back button on narrow displays/iOS (the `UISplitViewController` pattern).
- Keyboard shortcuts and bulk selection for fast triage (`j`/`k` to move, `e` to archive) — today's mock has none of these features.
- "New email" as a floating/minimizable window separate from inline reply in a thread (Gmail pattern — don't navigate away from a message being read just to compose a new one).
- No special data path underneath the component: the `emails.folder` relation for filtering by folder, the generic create-item endpoint for both compose and draft, the generic property model for `read`/`flagged`.
- The Roundcube Elastic skin as a reference shape (responsive 3-pane layout) to look at, not to copy (GPLv3 — no code is taken from it).

**Sending and drafts**
- `email.draft.create` is AI-callable like any other create-item endpoint — creating a draft never requires confirmation.
- `email.send` requires explicit human confirmation unless the project's AGENT.md explicitly grants autonomous sending (default: not granted).
- Sending goes through SMTP (the same OAuth2/app-password authentication as IMAP from issue #26).
- The sent message is optimistically inserted into Emails directly into the Sent folder (per `special purpose = sent`) and is deduplicated via `mail_message_meta.message_id` once the next IMAP sync confirms it in the real mailbox.
- Enforcement mechanics at the choke point: `email.send` checks whether the request came directly from an authenticated user session (`triggered_by = 'user'`) or from inside an `agent_run`. In the latter case, the choke point additionally checks whether the permission manifest for the Email project carries an explicit grant, `capabilities.email.send.autonomous`. Without the grant (default), the request ends in a 403 immediately, with nothing to wait for — the draft remains in Emails as an ordinary row, visible and sendable by the user through the Mailbox UI. With the grant, it goes straight through. No "pending approval" state is stored anywhere — it's a binary decision made at call time, not a queue. (The generic approval queue — layer 4 of the four-layer enforcement model — is deliberately not used for this case: it is a tool for per-instance decisions on risky calls, not for a question that can always be decided in advance at the whole-project level.)
- Detection of which address (for an account with multiple aliases, e.g. "custom domain" with dev@/support@ aliases) a message actually arrived at, so the UI can default-prefill the correct "From". Determined once at ingest time and stored (not recomputed on every render), in this order:
  1. `Delivered-To` header (highest occurrence if there are several — only a convention, not mandatory)
  2. `X-Original-To` (Postfix, the address before alias expansion)
  3. `Envelope-To` (Exim equivalent)
  4. a match of `To`/`Cc` against the mailbox's registered aliases (misses delivery via BCC, the weakest but last usable signal)
  5. the mailbox's primary address as the final fallback
  This works reliably only on a custom domain behind a real MTA (exactly the mock's case); hosted mailboxes (Gmail/iCloud as foreign infrastructure) typically don't preserve these headers when forwarding, so there it relies mainly on the To/Cc fallback. In the compose window, "From" is a plain dropdown, defaulting to the alias derived by this rule from context (the message being replied to, or the folder currently open).

**Heartbeats over email**
- The `newEmail` trigger (the mock already has it as a heartbeat trigger type) is generalized to "a new item in Emails with an edge to a Folder whose `special purpose = inbox`" — semantically the same across providers, the same way the tabs in the Emails view work today.
- Spam and Trash (`special purpose = junk / trash`) are deliberately excluded from the trigger — otherwise every spam wave would flood the heartbeat/AI attention queue.
- This is the generic mechanism that the (not yet started) parcel-tracking project is meant to be built on later — a heartbeat over the inbox that can recognize "this looks like a shipment notification" (the mock has this as a seed heartbeat, "New parcel for pickup → task") using the same `heartbeatAction` mechanism (ModuleManifest) that is used for library modules — here specifically the core action `core.agentRun` with a payload in `action_config`. No new heartbeat infrastructure, just another use case over the same one.

**Cases that weren't mentioned but without which the module wouldn't be complete** (exactly these):
1. **Structured To/Cc/Bcc** — solved above via `envelope` (issue #26) — without it the AI can't reliably reply-all or recognize hidden recipients.
2. **Bounce/DSN (failed delivery)** — a message of type `multipart/report` with `Content-Type: message/delivery-status` is a reply from the system, not a person — it should be recognized and linked back to the original outgoing message (via `References`), not filed as an ordinary new email in the inbox.
3. **Flag/importance** — a separate `owner:'user'` property `flagged` mapped to the IMAP `\Flagged` flag, added alongside the existing `read` (`\Seen`).
4. **Linking to People by address** — a new `People.emails` property plus a deterministic `person_email_index`, no AI involved.
5. **Provider limits and throttling** — Gmail: ~15 concurrent IMAP connections per account, daily bandwidth quotas — the sync worker must limit concurrency per account and back off on "too many simultaneous connections" instead of retrying immediately.
6. **`BODY.PEEK[]`, not `BODY[]`** — reading content without intending to mark it read (e.g. the AI reads a message in the background before the user has opened it) must use the PEEK variant — otherwise IMAP itself sets `\Seen` as a side effect of the fetch.
7. **Migration of existing mock data** — existing Emails rows lack `envelope`/`thread_id`/`message_id` — a one-off data migration (`module_migrations`) backfills them: where the raw header/MIME is stored, it is parsed directly; where it isn't, `envelope` is reconstructed as best as possible from the existing `sender`/`recipients` text fields and the row is flagged `migration_status: 'partial'` (the same column/state used for property retyping) — not a silent loss of threading.

### Out of scope

- The IMAP sync worker itself, MIME/envelope parsing, thread reconstruction, the folder sync mechanism — delivered by issue #26; here they are only consumed.
- "Inbox as a real database" — a separate area, issue #28, not part of this task.
- The generic approval queue (layer 4 of the four-layer enforcement model) as a mechanism in itself — here it is only explained why it is deliberately not used for `email.send`.
- The parcel-tracking project itself — not yet started; the heartbeat generalization only prepares an entry point for it.
- Full-text search over emails (FTS/tsvector) — not directly related to the UI/sending/heartbeats handled here.

## Dependencies

This task cannot start without what issue #26 delivers:
- The Emails table with `envelope`, `thread_id`, `message_id` populated after IMAP sync — the Mailbox UI, "From" alias detection, and the heartbeat trigger all depend on it.
- The `mail_message_meta` table and its `message_id`-based dedup mechanism — used when optimistically inserting a sent message into Sent.
- Folder/`folders` sync and the `emails.folder` relation — the Mailbox UI filters by folder through this relation, no custom one.
- Thread reconstruction (`References`/`In-Reply-To`) — the linking of a bounce/DSN message back to the original outgoing email builds on it.
- The SMTP/IMAP OAuth2 and app-password authentication layer introduced for sync — sending reuses it, it does not introduce its own.

It also relies on existing platform mechanisms outside issue #26: the `views` table and view-type registration mechanism (the same as the Journal's `temporal-switcher`), the choke-point `triggered_by` distinction between user and agent_run (issue #21), and the `heartbeatAction`/ModuleManifest mechanism (issue #29) introduced for library modules.
