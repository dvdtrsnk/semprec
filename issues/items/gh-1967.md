**Blocked by:** #1659, #1963
**Model tier:** medium

## Context

Model tier rationale: A single read-only route over one table with existing route-registration, tenant-isolation and error-contract patterns, but it must hide the existence of other tenants' items.

#1659 records, for each item created by confirming a proposal, which card and Inbox item produced it and when it was captured. Nothing exposes that yet. A detail screen needs to show "Added from Inbox on 16 Oct at 18:02: <captured text>" and the sibling items created by the same capture. The only way today is a filtered query of Processing proposals by `resultItemId` (`backend/packages/data/src/views/filterCompiler.ts`), which finds just the primary item and returns neither the source nor the capture time.

This is a custom route because it joins `item_origins`, the card and the source Inbox item for one consumer (the item detail screen), which the generic item surface cannot express; this is the single-consumer-read case. #1963 makes the source text of an Inbox capture available for captured uploads, so the route can return the text for those too.

Decision: an item that was not created from a confirmed proposal (created by hand or by an agent) has no origin row, and the route answers 404 for it, the same as for an unknown id.

## Task

Load `io-hardening`, `error-handling` and `testing`.

1. Add `GET /api/items/:id/origin` returning `{ proposalId, inboxItemId, capturedAt, captureChannel, sourceText, siblings: [{ itemId, label }] }`.
   - `sourceText` is the text of the source Inbox item (and for a captured upload, the text #1963 stores), `null` when the origin is a transcript.
   - `siblings` are the other items with the same `proposal_id`, each with its title label, excluding the item itself and excluding soft-deleted items.
   - 404 `not_found` when the item does not exist, belongs to another tenant, is soft-deleted, or has no origin row; the body is identical in all four cases.
2. Register the route in the Inbox module manifest as a custom route with its justification, implement the handler in `inboxRouteHandlers.ts` over a read in the origins store, and add the entry to `routeMatrix.ts` and the route list in `tenantIsolationRoutes.test.ts`.
3. Tests: origin of a confirmed item; 404 for a hand-created item; 404 for another tenant's item with the same body as for an unknown id; siblings of a two-step confirm.

## Scope

### In scope

- The single-item origin read and its route registration.

### Out of scope

- Writing origin rows; #1659.
- A per-row flag for lists; #1716 (list screens must not call this route per row).
- Storing captured upload text; #1963.

## Acceptance criteria

- When the item was created by confirming an Inbox proposal, then the route returns that card's `proposalId`, the Inbox item id, its `capturedAt` and the source text.
- When the item was created by hand, then the route returns 404 `not_found`.
- When the item belongs to another tenant, then the response is byte-identical to the one for a nonexistent id.
- When the proposal created two items, then each one's `siblings` contains the other and not itself.
