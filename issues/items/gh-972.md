## Context

Row-level security needs a tenant on every tenant-owned row. #968 created `tenants` with exactly one row, tenant zero, kept single by the unique index `tenants_single_tenant_guard`. It also created three `STABLE` SQL functions:
- `app_current_tenant()` = `NULLIF(current_setting('app.tenant_id', true), '')::uuid`
- `app_sole_tenant()` = the tenant id when exactly one `tenants` row exists, else NULL
- `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())`

#971 classified 43 tables `semprec:tenancy=tenant` by table comment and started `backend/packages/data/src/__tests__/tenancyCatalog.test.ts`.

The decided column shape is `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)`. Postgres evaluates a non-volatile `ADD COLUMN ... DEFAULT` once and stores the result as the column's missing value, so the table is not rewritten. Here that result is tenant zero, because no scope is set during a migration and exactly one tenant exists. Existing rows therefore become tenant zero without a rewrite. The same holds for the partitioned `items` (`0001_core_schema.sql:71-79`): the column propagates to every `items_p_*` partition, and to partitions `create_items_partition` creates later (`0048_create_items_partition_function.sql:23-32`).

The previous release never names the column. Its inserts take the default, so they land in tenant zero, and its reads are unaffected. Every `SELECT *` site maps rows field by field (e.g. `backend/packages/data/src/mcp/mcpToolRegistrationsStore.ts:50`, `mcp/approvalRequestsStore.ts:130`), so no response gains the column. The lexical expand/contract check accepts `ADD COLUMN ... NOT NULL` with a `DEFAULT` (`backend/packages/data/src/db/migrationCompatibility.ts:107-113`).

When a second tenant exists and no scope is set, `app_sole_tenant()` is NULL. A scope-less insert then fails on `NOT NULL`. That fail-closed behaviour is intended.

### Out of scope

- Tenant-leading unique indexes and the `(tenant_id, id)` parent keys (#974).
- Composite tenant-consistent foreign keys (#1066).
- `NOT NULL` without the fallback, i.e. the strict switch (#1067).

- Setting `app.tenant_id` from application code (#978).
- Changing any query or store to read or write `tenant_id`.

## Acceptance criteria
- On the migrated test database, every table classified `semprec:tenancy=tenant` has `tenant_id uuid NOT NULL DEFAULT app_tenant_default()` with a foreign key to `tenants(id)`, and so does every `items_p_*` partition (integration, `tenancyCatalog.test.ts`).
- On a scratch database migrated to the previous migration, rows that existed before this migration all read `tenant_id` = tenant zero after it. The `relfilenode` of `databases`, of the `items_p_*` partition and of `notifications` is unchanged, which proves there was no rewrite (integration, `tenantIdColumn.test.ts`).
- A database and an item created through the choke point, and a `notifications` row inserted without naming `tenant_id`, get tenant zero (integration).
- An insert naming a `tenant_id` that is not in `tenants` fails with SQLSTATE `23503` (integration).
- With a second tenant present and no `app.tenant_id`, an insert into a tenant table that does not name `tenant_id` fails with SQLSTATE `23502`. With `app.tenant_id` set to that tenant inside the transaction, the same insert succeeds and stores that tenant's id (integration).
- The existing integration suite passes unchanged, and the migration-compatibility unit check passes without an exemption marker (unit / integration).
