## Context

`backend/services/semprec-api/src/mcp/mcpHandler.ts` documents that `POST /mcp` "never accepts a cookie" (`extractBearerToken` docstring, line 79), but `resolveActor` (lines 114-139) only uses the bearer token to look up a restricted run credential; when no credential resolves — including when there is no `Authorization` header at all — line 137 falls back to `authenticateRequest(pool, req)` from `../authHandler.js`, whose `extractToken` (lines 55-65) reads the `semprec_session` cookie when there is no bearer header. A browser session's cookie therefore authenticates the MCP JSON-RPC endpoint, contradicting the handler's own stated contract. (`docs/adr/2026-09-18-mcp-json-rpc-transport-for-the-generic-operation-catalog.md` only requires that `authenticateRequest` resolve the caller with no MCP-specific credential type; this issue keeps that and merely refuses to consult the cookie channel.)

Depends on #638, which edits this handler's error-serialising lines first.

## Task

- In `resolveActor`, when `extractBearerToken(req)` returns `null`, throw `new UnauthorizedError()` (import from `@semprec/data`) immediately — never call `authenticateRequest` without a bearer token. Keep the existing order for a present bearer token: run-credential lookup first, then `authenticateRequest` (which, for a bearer token, still enforces `SESSION_DELIVERY_CHANNEL_BY_PLATFORM`, so a web session's token presented as bearer is rejected too). The `catch` in `handleRequest` already answers `UnauthorizedError` with 401.
- Update the docstring above `createMcpRequestListener` (lines 93-100, "The actor is derived one of two ways") to state that a request with no bearer token is rejected before any session lookup and that the web session cookie is never consulted.
- Test in `backend/services/semprec-api/src/mcp/__tests__/mcpHandler.test.ts` (integration tier), next to "rejects an unauthenticated request": log a user in with `platform: "web"` through `login(pool, ...)`, send `POST /mcp` with a `tools/list` body, the header `Cookie: ${SESSION_COOKIE_NAME}=<token>` (import `SESSION_COOKIE_NAME` from `../../authHandler.js`) and no `Authorization` header → 401.

### In scope

### Out of scope

- Listing `POST /mcp` in the route matrix — sibling issue B6 of this batch.

- CSRF tokens or `Origin` checks for cookie-authenticated routes generally — deliberately outside this batch.

## Acceptance criteria

- When `POST /mcp` is called with a valid web-session cookie and no `Authorization` header, the response is 401.
- When `POST /mcp` is called with a valid native-session bearer token or a valid restricted run credential, behaviour is unchanged: every existing case in `mcpHandler.test.ts` and `mcpGenericOperationsContract.test.ts` still passes.
- When `POST /mcp` is called with no credentials at all, the response is still 401 (the existing case).
