## Context

Model tier rationale: One new write route over the atomic multi-block operations that already exist, with placement resolution and caller-supplied ids as the only new logic, plus two seams (agent and user origin) that reuse existing verification fixtures.

Pages have no HTTP surface and no way to append or add content at a chosen position. Every doc write goes through `mutateDocWithClient(client, docId, origin, fn)` in `backend/packages/data/src/docs/docPersistence.ts`, with `origin` of `user`, `ai_agent` or `system`, and `getOrCreateDoc` in `backend/packages/data/src/docs/docsStore.ts` creates a page doc lazily. There is no block validation beyond `backend/packages/data/src/docs/blocks.ts`.

This issue adds inserting Markdown into a page at a placement: at the start, at the end, or right after a given block. #1608 parses Markdown into blocks, #1610 provides the atomic multi-block operation that inserts several blocks in one transaction, and #1394 fixes the operation name and shape. Several callers build on it: #1681 (confirming a page-content proposal at the user's chosen placement, idempotently), #1981 (confirming a journal entry into the day's page), #1735 (an origin note on a created item), #1726 (merging duplicate journal entries) and #1844 (agent classification). The idempotent confirm in #1681 needs deterministic block ids, so the caller can supply them.

Decision: page links (`semprec://page/<id>`) are not accepted by insert in this issue. Validating a link against the subpages of the host depends on subpage ownership that this issue does not build on, so insert rejects Markdown containing a page link with `400`. Links are handled by the replace operation #1765.

Shared-file ordering: this issue also waits for #1678 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Decision (batch 38 R1 reconciliation): R1 reconciliation: the HTTP insert accepts a session or a scoped run credential through the existing caller resolver and gateway, retaining capability intersection and database grants; only page.insert gets this listener path. Keep /page/insert. Each flat parser element, including indented blocks, needs one supplied block id. afterBlockId anchors relative indentation at the target; overflow of the existing maximum is refused without writes. Empty Markdown still validates placement without creating a document. start/end preserve parsed indentation.

## Task

Load `state-writes`, `io-hardening`, `error-handling` and `testing`.

1. Add `insertPageMarkdown(client, itemId, {placement, markdown, blockIds?, origin})` in `backend/packages/data/src/docs/pageMarkdown.ts` (the file is created by #1678 if it has merged; otherwise create it). It gets the doc with `getOrCreateDoc(client, itemId, "page")`, parses `markdown` with the parser from #1608, and inserts the blocks with the atomic operation from #1610 inside one `mutateDocWithClient` call. Return `{blockIds}` in document order. After parsing, call `assertItemLinksExist` from #1614 on the same tenant-scoped write client before content persistence; an invalid item reference aborts the entire write, including lazy document creation and other effects.
2. Placement is `"start"`, `"end"` or `{afterBlockId}`. `"start"` puts the blocks before the first block, `"end"` after the last, `{afterBlockId}` right after that block at the same nesting level. An unknown `afterBlockId` returns a `ValidationError` mapped to `400`; nothing is written.
3. Optional `blockIds`: an array the caller supplies, one id per top-level block produced by the parse (a count mismatch is `400`). Ids must be valid block ids and not already present in the doc; a collision is `409`. Without it, ids are generated.
4. Invalid Markdown (a block type not allowed, a page-type block in a light host, or any page link, see the decision) returns `400` with nothing written and no doc created for a failed parse.
5. Origin comes from the caller: `user` for a session, `ai_agent` when the request carries an agent run credential (same detection the MCP gateway uses); a system caller passes `system`.
6. Add `POST /api/items/:id/page/insert` with body `{placement, markdown, blockIds?}` returning `200 {blockIds}` in `pageMarkdownHandler.ts`, authenticated and tenant-scoped like the other item routes. Register the operation in the generic operation catalog under the name from #1394 and add the route to `routeMatrix.ts`.
7. Tests: insert at `end` appends after the last block and returns the ids; `start`; `afterBlockId`; unknown `afterBlockId` writes nothing; caller ids are used and a collision is `409`; an invalid block type is `400`; the doc is created lazily on the first insert; the update row carries the correct `created_by` for user and agent callers.

## Scope

### In scope

- Inserting parsed Markdown blocks at `start`, `end` or after a block, atomically, with optional caller-supplied ids and the caller's origin.

### Out of scope

- Reading a page as Markdown: #1678.
- Replacing a page and the If-Match version check: #1765.
- Accepting page links in inserted Markdown, creating subpages from Markdown: #1765 covers links on replace only; insert stays link-free.
- Placement under a heading by its text, idempotent confirm and proposal handling: #1681.
- Agent capability classification and approval policy: #1844.

## Acceptance criteria

- When Markdown is inserted with placement `end`, then its blocks follow the last block and the response lists their ids in order.
- When placement is `start` or `{afterBlockId}`, then the blocks land before the first block or directly after that block.
- When `afterBlockId` does not exist, then the response is `400` and the doc is unchanged.
- When the caller supplies `blockIds`, then exactly those ids are used; when one already exists in the doc, then the response is `409` and nothing is written.
- When the Markdown contains a disallowed block type or a page link, then the response is `400` and nothing is written.
- When the item has no doc yet, then the first insert creates it and the content appears.
- When the caller is an agent run, then the stored update is attributed to `ai_agent`; for a session user it is `user`.

- For item links, actual authenticated HTTP writes accept a live local target; unknown, foreign, deleted and malformed targets return identical safe 400 `validation_failed` bodies with the Markdown field path, and leave documents, updates and relation edges unchanged.
