**Blocked by:** #1924, #1940, #1944
**Model tier:** high

## Context

Model tier rationale: A new route that changes a relation edge, clears user-owned state, changes the card lifecycle (a new transient status) and triggers an out-of-band job in one transaction, with a locked-card conflict and an optimistic version check, so concurrency and lifecycle ownership are both at stake.

An Inbox item that the assistant could not classify shows as "needs clarification" with tiles for the possible types; choosing one should immediately turn the card into a proposal of that type, keeping the source. An already typed item can be moved to another type the same way. Today the type is chosen by writing the relation `Inbox.type` through `PUT /api/items/:id/relations/type/:typeId`; the relation is many-to-many, so the tick simply takes the first edge, and nothing runs the tick after an edge write (heartbeats fire on item create, update and delete only, `triggerOnItemEventHeartbeats` in `backend/packages/data/src/scheduler/schedulerStore.ts`). Even if it did run, the tick's fingerprint gate would end it when the emoji and text did not change.

This issue adds the single route for changing an item's type: `PUT /api/inbox/items/:id/type { typeId, ifVersion? }`, a custom route with justification `transactional-semantics` (edge replacement, state clearing and job trigger must commit together). It builds on: #1669 (the type of an item is locked once its card is decided), #1924 (the helper that decides which manual values survive a destination change), #1937 (reopening decided cards, which the lock rule respects) and #1434 (the tick exists in the api runtime). The related issue #1718 also reacts to a type-edge change; both can fire, and the tick job key replaces a pending job, so a double trigger is harmless.

Decision: the route does not compute the proposal. It marks the card `computing` and enqueues the tick; the tick, seeing a card in `computing`, bypasses the fingerprint gate for it (this issue adds that bypass; the status `computing` exists with the card-state properties, #1451). Until the tick finishes the card reports `computing`; the result arrives as `proposed` with the new type's values stored as `aiProposal`. Decided by the product owner: the switch goes through the `computing` interstate, one general mechanism for every recompute, and proposals are not precomputed for candidate types.

Decision: errors: unknown or archived type -> `ValidationError` on `typeId`; a card that is `confirmed` or `rejected` -> 409 with code `proposal_locked` (reuse the error class if #1669 introduced one, otherwise add `ProposalLockedError` in `backend/packages/data/src/errors.ts` and the code to the adapter's error contract); a card whose `updatedAt` differs from `ifVersion` -> 409 `version_conflict` with the current card. `ifVersion` refers to the proposal card; an item without a card takes no `ifVersion`.

Shared-file ordering: this issue also waits for #1940, #1944 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Add `changeInboxItemTypeWithClient(client, config, { itemId, typeId, ifVersion?, actingUserId })` in a new `backend/packages/data/src/inbox/inboxTypeChange.ts`, in the caller's transaction: lock the live Inbox item and its live card (`findExistingProposal`), check the lock and `ifVersion`, validate the type is an active Inbox item type, delete every existing `type` edge of the item and create the new one (so exactly one remains) through the relation operations, and, when a card exists, write `status: "computing"`, clear `userOverrides` and `userEditedKeys` where the helper from #1924 says the destination changed (the new destination is derived from the type's processing method and target database), and a history entry `kind: "typeChosen"` (`author: "user"`). Then call `triggerOnItemEventHeartbeats(client, inboxDatabaseId, "update", itemId)` so the existing Inbox tick heartbeat runs.
2. In `inboxTickAction.ts`'s `readTickSnapshot`, skip the fingerprint gate when the existing card's status is `computing`; the write phase already sets `proposed` and stores the new `aiProposal` and fingerprint.
3. Add `createChangeInboxItemTypeRouteHandler(pool)` in `inboxRouteHandlers.ts` (body `{ typeId, ifVersion? }`, one `withTransaction`) and register `PUT /api/inbox/items/:id/type` in `inboxModuleManifest.ts` with justification `transactional-semantics`. Add the matrix entry and the cross-tenant case.
4. Tests: choosing a type on a `needsClarification` card leaves exactly one `type` edge, sets `computing` and enqueues the tick, and a tick run turns it into a `proposed` card of that type with unchanged source; the same on an item without a card (the tick creates it); `confirmed` card -> 409 `proposal_locked`; stale `ifVersion` -> 409 `version_conflict`; edited task title is cleared when the type moves to an event type and kept (when the key exists) for the same destination; foreign tenant answers as unknown.

## Scope

### In scope

- `PUT /api/inbox/items/:id/type`, the single-edge replacement, clearing manual values, the `computing` status and the tick bypass for it.

### Out of scope

- A recompute that does not change the type (#1955).
- Locking the type edge once a card is decided (#1669); this route only reports the lock as 409.
- Precomputing candidate proposals for all types (decided not to be done).
- Recording a failed computation on the card (a separate failure-state issue).
- Introducing a separate "choose type" route: this is the only type-change route.

## Acceptance criteria

- When `PUT /api/inbox/items/:id/type` is called for an untyped item with a `needsClarification` card, then the item has exactly one `type` edge, the card is `computing`, and after the tick it is `proposed` with values of the chosen type and the same source.
- When the card is `confirmed` or `rejected`, then the response is 409 with code `proposal_locked` and nothing changes.
- When `ifVersion` does not equal the card's `updatedAt`, then the response is 409 `version_conflict` with the current card.
- When a task card with an edited title is moved to an event type, then `userOverrides` and `userEditedKeys` are empty and a `typeChosen` history entry exists.
- When an item has no card yet, then the route succeeds without `ifVersion` and the tick creates the card.
- When `typeId` is not an active Inbox item type of this tenant, then the response is 400.
