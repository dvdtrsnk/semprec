## Context

Model tier rationale: One many-to-many relation added to two schema-locked system databases through the seed and a raw-SQL per-tenant cutover, with an existing cutover pattern and fixtures, plus a confirm test over the existing multi-step mechanism.

The Inbox card for a health note can also propose a follow-up check as a task ("Check-up at the doctor", 30 October). Today nothing connects a task to the health record it came from: Tasks have only a project, and Health records link to Files, an Area and Projects. Without a link the follow-up appears in no health context and the record cannot show its open tasks.

This issue adds one relation, `Tasks.healthRecords` with inverse `HealthRecords.tasks`, many-to-many, user-owned. Both databases are schema-locked, so new tenants get it from the seed and existing tenants from a per-tenant cutover in `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`) written, like the Tasks schema cutover of #1540, with raw SQL on `properties` and `relation_definitions` after a table lock, because `createRelationPropertyWithClient` refuses a locked database (pattern: `backend/packages/data/src/transcription/transcriptsCatalogCutoverMigration.ts`). #1540 owns the other new Tasks properties; this issue owns only this relation, and is its only owner.

It builds on atomic multi-step confirm (#1486), which creates a record and a task and can carry a relation from the second step to the first step's item, on the new tags and their colors (#1700, #1705), and on the sensitive-database marking (#1808) because all of them edit the same seed and cutover files.

Decision: a follow-up task links to the record through this new relation (not through a project "Regular check-ups", and not unlinked). Reason: it is the only structure that answers "what is open for this record" without inventing a project.
Decision: a card for a health record carries no Area of its own and confirm writes no `area` edge. When the record has a project, its area is derived from the project as for every other item (#1595); without a project the Area stays empty unless the user sets it.

Shared-file ordering: this issue also waits for #1833 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. In `seedTenDatabases.ts` add the relation `Tasks.healthRecords` (`many_to_many`, user-owned, inverse `HealthRecords.tasks`) in the relations pass, before the schemas are locked.
2. Add `backend/packages/data/src/seed/healthRecordTasksCutoverMigration.ts`: per tenant, resolve the Tasks and Health records databases (do nothing when either is missing), `LOCK TABLE properties IN EXCLUSIVE MODE`, skip if `Tasks.healthRecords` exists, otherwise insert the two properties, the `relation_definitions` row and the property `config` (`relationDefinitionId`, `targetDatabaseId`) with raw SQL. Register it in `runTenantCutoverMigrations`. A second run changes nothing.
3. Add the Czech and English labels for both new properties in `seed/i18n/cs.json` and `en.json` (`property.tasks.healthRecords.name` "Zdravotní záznamy" / "Health records"; `property.healthRecords.tasks.name` "Úkoly" / "Tasks").
4. Tests: a new and an existing tenant have both properties and the relation; a second cutover run changes nothing; both databases stay schema-locked; a Task can be linked to a record and appears in the record's `tasks`; a confirmed multi-step proposal with a health record step and an enabled task step creates both with the edge in one transaction, and with the task step disabled only the record; the confirmed record has no `area` edge; the existing single-item envelope still works.

## Acceptance criteria

- When a tenant is created or upgraded, then Tasks have `healthRecords` and Health records have `tasks`, many-to-many, and both databases stay locked.
- When the cutover runs twice, then the second run changes nothing.
- When a multi-step health proposal with the task step enabled is confirmed, then the record and a task dated 30 October exist, linked, in one transaction; with the task step disabled only the record exists.
- When a task is linked to a record, then it appears in the record's `tasks`.
- When a health proposal is confirmed, then the created record has no `area` edge.
