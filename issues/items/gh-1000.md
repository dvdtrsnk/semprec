**Blocked by:** #990, #999

## Context

The live-sync root beats one `process_heartbeats` row per hosted mailbox, named `mailsync:<mailboxItemId>` (`backend/packages/data/src/health/processHeartbeats.ts:17-19`). Since #990, the root discovers mailboxes per tenant and starts that heartbeat in its own system scope. Every tick runs in system scope. `process_heartbeats` stays a global table.

`observabilityCheckSystem`'s process family (`backend/packages/data/src/observability/observabilityCheckSystem.ts:43-60`) evaluates `getExpectedProcessHeartbeatStatuses` (`processHeartbeats.ts:127-147`). That function builds its list from `getExpectedProcessNames` (`:107-110`): the four `FIXED_PROCESS_NAMES` (`:15`) plus `getActiveMailSyncProcessNames` (`:99-104`). The latter reads `mail_account_sync_state JOIN items`, two tenant tables. For every expected process the family writes a **global** `observability_checks` row `process:<name>` with detail `{ process, present, beatAt }`, and notifies `process_stale` with `{ process, beatAt }` on a flip (`:52-57`). So today:
- **Mailbox ids reach the global plane.** A tenant's mailbox ids land in global `process:mailsync:<id>` rows and in `process_stale` alerts. #1019 sends every `process_stale` alert to every admin.
- **The check breaks after the strict switch.** It reads tenant tables from system scope, so it sees mailboxes only while exactly one tenant exists (`app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())`). With two tenants, or after the strict switch (#1067), every mailbox's liveness check silently disappears.
- **Stale rows are never cleaned up.** Nothing deletes a `process:mailsync:<id>` row whose mailbox is gone.

#999 already moved per-mailbox sync-stall checks (`mail:<id>`) into the tenant table `tenant_observability_checks`. It is RLS-protected, has its tenant defaulted from the scope, and is unique on `(tenant_id, check_key)`. Those checks are evaluated inside `forEachActiveTenant(pool, work)` (#983), and the stall notification is `mail_sync_stalled` with `sourceTable: "tenant_observability_checks"`. #999 also added:
- `transitionTenantObservabilityCheck` and `deleteOrphanedTenantObservabilityChecks` (`backend/packages/data/src/observability/observabilityChecksStore.ts`);
- the `sourceTable` parameter of `notifyObservabilityAlert`;
- the per-tick purge of legacy global `mail:` rows.

This issue applies the same split to mailbox liveness. The global family keeps only the four fixed processes. Each mailbox's `mailsync:<id>` staleness becomes a tenant check, evaluated inside its tenant.

Tenancy state this issue builds on:
- `runInTenant`, `runAsSystem` and `currentTenantScope` come from `@semprec/shared`.
- `withTransaction` sets `app.tenant_id` from the scope.
- `TASK_TENANCY` makes `observabilityCheckSystem` a system task (#982), so its handler runs inside `runAsSystem`.
- `forEachActiveTenant` runs `work` inside `runInTenant` per `active` tenant and rethrows failures together after all tenants.
- `SEMPREC_TENANT_SCOPE=strict` throws `TenantScopeMissingError` for a query with no scope.

## Task

Load `state-writes` (upserts, deletes, the notification after the transition) and `error-handling` (one tenant's failure must not hide the others).

1. **Global family (`observabilityCheckSystem.ts`, `checkProcessHeartbeats`).** Evaluate only the statuses whose `process` is one of `FIXED_PROCESS_NAMES`. Filter the result of `getExpectedProcessHeartbeatStatuses`; `processHeartbeats.ts` is not changed. Global rows, details and `process_stale` payloads keep their current shape for those four names.
2. **Legacy purge.** In the same system pass, next to #999's `mail:` purge, call `deleteOrphanedObservabilityChecks(client, "process:mailsync:", [])`. Every legacy global `process:mailsync:<id>` row is then removed on every tick, including after a rollback and redeploy.
3. **Per-tenant liveness.** Inside #999's `forEachActiveTenant` callback, after the stall checks, do the following in the tenant's own transactions:
   - Read `getExpectedProcessHeartbeatStatuses(client)` and keep the entries whose `process` is **not** one of `FIXED_PROCESS_NAMES`. Under RLS these are exactly this tenant's active mailboxes' `mailsync:<id>` processes. The heartbeat rows themselves are read from the global `process_heartbeats` table by name.
   - Remove orphans with `deleteOrphanedTenantObservabilityChecks(client, "process:mailsync:", <current keys>)`.
   - For each entry, `transitionTenantObservabilityCheck(client, "process:" + process, …)`: status `alerting` when `stale`, otherwise `ok`; detail `{ process, present, beatAt }`.
   - On a flip to `alerting`, notify through `notifyObservabilityAlert` with:
     - kind `mail_sync_stalled`, which is a tenant event; `process_stale` stays an operator kind for the fixed processes;
     - `sourceTable: "tenant_observability_checks"` and the tenant row's id;
     - payload `{ mailboxItemId, beatAt }`. Take `mailboxItemId` from the process name after the `mailsync:` prefix (`mailSyncProcessName`, `processHeartbeats.ts:17-19`), and check that it is a UUID.
   - The recipient lookup is unchanged.
   - A tenant whose pass throws is reported through the helper's aggregated rethrow. The handler rejects after all tenants, and the global family's commits stand.
4. **Docstrings.** Update `checkProcessHeartbeats`' and the handler's docstrings to say process liveness is global for the four fixed processes and per tenant for mailboxes.
5. **Tests.**
   - Add single-tenant cases to `backend/packages/data/src/__tests__/observabilityCheckSystem.test.ts`, running `runCheck` inside `runAsSystem`.
   - New `backend/packages/data/src/__tests__/tenantMailSyncLiveness.test.ts` holds the two-tenant and strict-mode cases.
   - An active mailbox needs a real Mailbox item, because `getActiveMailSyncProcessNames` joins `items`: `seedSystem`, then a Mailboxes item, then `ensureMailAccountSyncState`. Its liveness comes from `upsertProcessHeartbeat(pool, { process: mailSyncProcessName(id), … })`, backdated or omitted.
   - Both files delete `tenant_observability_checks` rows in `beforeEach`, as #999's tests do.

## Scope

### In scope
- Restricting the global process family to the four fixed processes.
- Purging legacy global `process:mailsync:` rows.
- Per-tenant `process:mailsync:<id>` checks in `tenant_observability_checks`, with their `mail_sync_stalled` notification.

### Out of scope

- Any change to `processHeartbeats.ts` or to `notificationKinds.ts`; no new kind.

## Acceptance criteria

All integration tier.
- **Global plane is mailbox-free (`observabilityCheckSystem.test.ts`).** Tenant zero has an active mailbox whose `mailsync:<id>` heartbeat is 5 minutes old, and the four fixed processes are fresh. After one run:
  - `observability_checks` has no row whose `check_key` or `detail::text` contains the mailbox id;
  - no `process_stale` notification exists;
  - `process:api`, `process:agents`, `process:transcribe` and `process:ai-gateway` exist as `ok`.
- **Tenant check fires once (`observabilityCheckSystem.test.ts`).** In the same setup, `tenant_observability_checks` holds `process:mailsync:<id>` as `alerting`, with tenant zero's `tenant_id` and detail `{ process, present: true, beatAt }`. Exactly one `mail_sync_stalled` notification exists, with payload `{ mailboxItemId: <id>, beatAt }`, `source_table` `tenant_observability_checks` and `source_id` the row's id. A second run adds no notification.
- **Missing heartbeat and recovery (`observabilityCheckSystem.test.ts`).**
  - An active mailbox with no heartbeat row alerts with `present: false`.
  - A fresh heartbeat flips the row to `ok`.
  - A later fault notifies again.
- **Orphans and legacy rows (`observabilityCheckSystem.test.ts`).**
  - Soft-deleting the Mailbox item removes its `process:mailsync:<id>` tenant row on the next run.
  - A pre-existing global `observability_checks` row `process:mailsync:<uuid>` is deleted by the next run.
- **Fixed processes unchanged (`observabilityCheckSystem.test.ts`).** The existing `process_stale` cases for `agents` and `transcribe` pass unchanged, with `source_table` `observability_checks`.
- **Two tenants (`tenantMailSyncLiveness.test.ts`; tenant B from `createTestTenant(pool)`, checks run over `createRuntimeRolePool(pool, "semprec_data")`, both from #975's `@semprec/data/testSupport`).**
  - Tenant zero and tenant B each have one active mailbox with a stale heartbeat. One run yields one alerting `process:mailsync:<id>` row per tenant, each with its own `tenant_id`. Each tenant's notification names only its own mailbox.
  - A suspended tenant's mailbox is not evaluated.
- **Works under strict enforcement (`tenantMailSyncLiveness.test.ts`).** With `SEMPREC_TENANT_SCOPE=strict` and a pool from `createPool`, the handler called inside `runAsSystem` evaluates both tenants' mailboxes and raises no `TenantScopeMissingError`. This is the setup in which the old system-scope derivation would see no mailbox at all.
