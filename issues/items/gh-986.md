## Context

Two daily crontab entries run the same 30-day trash purge: `itemTrashPurgeSweep` at 03:45 and `trashPurge` at 04:00 (`backend/packages/data/src/worker.ts:86,88`). Both handlers call `handleItemTrashPurgeSweepTask(pool, mailBlobStorage)` (`worker.ts:202-209`), which calls `purgeExpiredTrash` (`backend/packages/data/src/trash/purgeExpiredTrash.ts:26-70`).

`purgeExpiredTrash` reads candidates with `itemsStore.findItemsDeletedBefore` (`backend/packages/data/src/chokePoint/itemsStore.ts:264-279`). That query runs directly on the partitioned `items` parent, keyset-paged on `(database_id, id)`, 500 rows per page. For each root it calls `chokePoint.purgeExpiredTrashSubtree` (`backend/packages/data/src/chokePoint/itemTrash.ts:251-302`), which runs in its own transaction and:
- re-checks the root's eligibility;
- walks the expired subtree;
- hard-deletes rows and their dependents (relations, view items, idempotency keys, docs, recurrence, automation, search index, unreferenced blobs; `itemTrash.ts:189-204`);
- drops emptied inline databases together with their `items_p_*` partitions (`dropDatabaseWithPartition`, `backend/packages/data/src/chokePoint/databasesStore.ts:198-204`).

After each subtree commits, the purge deletes the blob bytes best-effort. A failed subtree or blob delete is logged and skipped.

Every table touched is tenant-owned. Tenancy state this issue builds on:
- Each tenant table carries `tenant_id` under a RESTRICTIVE RLS policy `tenant_isolation` (`tenant_id = (SELECT app_tenant_default())`, with `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())` over the GUC `app.tenant_id`).
- `withTransaction`, autocommit `pool.query` and `pool.connect()` clients set that GUC from the ambient scope: `runInTenant(tenantId, fn)` sets the tenant and `runAsSystem(reason, fn)` sets `''` (`@semprec/shared`).
- In system scope, tenant rows are visible only while exactly one tenant exists. With two tenants, or after the strict switch (#1067), the purge would find no candidates.
- Both purge tasks are `tenancy: 'system'` crontab tasks, so the task runner calls them inside `runAsSystem`.
- #983 added `forEachActiveTenant` (`backend/packages/data/src/tenancy/forEachActiveTenant.ts`, exported from `@semprec/data`). Called from a system scope, it runs the callback inside `runInTenant(tenantId, …)` for each tenant with `status = 'active'`, starting at a rotating offset. A throwing tenant does not stop the others. After all tenants were attempted, the failures are rethrown as one `AggregateError`, so the job is retried.
- This issue calls it as `forEachActiveTenant(pool, async () => …)`. If the merged signature differs, use the merged one.

Running each tenant's purge inside its own scope also does the following:
- keeps the blob reference check (`deleteBlobIfUnreferenced`) to that tenant's rows;
- runs the partition drop in the owning tenant, which #1021 will require when it makes the partition DDL functions refuse a database outside the current tenant.

## Acceptance criteria

All of these are integration tests (`*.test.ts`), with two tenants under the runtime role unless stated otherwise.
- **Per-tenant purge.** Tenant zero and tenant B each have one item trashed 31 days ago and one trashed 1 day ago. One `itemTrashPurgeSweep` run permanently removes both 31-day-old items and keeps both 1-day-old items.
- **Blob bytes.** Tenant B's expired Files item references a blob that nothing else references. After the run, its `blobs` row is gone and `storage.delete` was called with its storage key after the subtree's transaction committed. A live Files item's blob in tenant zero is untouched.
- **Inline database.** Tenant B's expired item owns an inline database whose rows were all cascade-trashed with it. The inline `databases` row and its `items_p_*` partition are dropped during B's pass. No tenant zero database is affected.
- **Per-candidate failure stays per candidate.** Tenant B has an expired item in an archived database, whose purge is rejected and logged, and another expired item in a writable database. B's second item and tenant zero's expired item are still purged.
- **Inactive tenant.** An expired item of a tenant whose `status` is `suspended` is not purged.
- **Single tenant unchanged.** With only tenant zero, the existing `purgeExpiredTrash.test.ts` cases pass.
