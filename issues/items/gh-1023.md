## Context

Model tier rationale: Each of the six predicates is given exactly and the test technique follows an existing suite.

`items` is `PARTITION BY LIST (database_id)` with one `items_p_<hex>` partition per database (`backend/packages/data/src/db/migrations/0001_core_schema.sql:1-18`). Every tenant brings about 25 databases. A query on `items` without a `database_id` predicate plans every partition of every tenant. Row-level security still hides the other tenants' rows (`items` and `databases` carry the RESTRICTIVE `tenant_isolation` policy `tenant_id = (SELECT app_tenant_default())`), but each such lookup's cost grows with the tenant count.

#1003 pruned the three such reads in `backend/packages/data/src/chokePoint/itemsStore.ts`. It added `visibleDatabaseIds(client: Queryable): Promise<string[]>` (`SELECT coalesce(array_agg(id), '{}') AS ids FROM databases`, so under RLS: the current tenant's databases, archived ones included) and bound its result as `database_id = ANY($n::uuid[])`.

Only a bound array prunes. node-postgres plans unnamed statements with the parameter values, so the plan keeps just the matching partitions, and an empty array plans to `One-Time Filter: false`. A sub-select `ANY(ARRAY(SELECT …))` leaves every partition in the plan. Both were verified with `EXPLAIN` on PostgreSQL 15, including an inner join that carries the bound array in its `ON` clause.

A sweep of every `FROM`/`JOIN`/`UPDATE items` in `backend/packages` and `backend/services` at `origin/develop` leaves five partition-key-less lookups outside `itemsStore.ts`:
- `listLiveViewItemsAfter` (`backend/packages/data/src/chokePoint/viewItemsStore.ts:21-50`, join at `:41`). It pages curated views (`backend/packages/data/src/views/viewQuery.ts:195`), and its docstring (`:21-27`) records the cross-partition scan.
- `generatePermissionManifest` reads the project item's properties with `SELECT properties FROM items WHERE id = $1` (`backend/packages/data/src/manifest/permissionManifest.ts:161-164`).
- `deleteBlobIfUnreferenced` checks for a referencing item with `SELECT 1 FROM items WHERE properties @> …` (`backend/packages/data/src/blobs/blobsStore.ts:90-110`, subquery at `:103`). The trash purge calls it.
- `getActiveMailSyncProcessNames` runs `… JOIN items i ON i.id = s.item_id WHERE i.deleted_at IS NULL` (`backend/packages/data/src/health/processHeartbeats.ts:92-104`). The process-health report calls it through `getExpectedProcessNames` (`:107-110`).
- `listPendingImapFlagWrites` joins `items folder ON folder.id = CASE …` (`backend/packages/data/src/mail/mailMessageFlagSyncStore.ts:113-158`, join at `:131`). The IMAP reconciler calls it (`backend/packages/data/src/mail/imapReconcile.ts:346`).

The sweep found these already pruned:
- `listErroredItemAutomationForDatabases` binds `i.database_id = ANY($1::uuid[])` (`backend/packages/data/src/library/itemAutomationStore.ts:165-171`).
- `backend/packages/data/src/mail/search.ts:48` filters `i.database_id = $1`.
- `search.ts:207`'s `LEFT JOIN items i ON … i.database_id = s.database_id` with `s.database_id = $1` plans a single partition (verified).
- `folderDiscovery.ts`, `send.ts:118`, `transcriptEventMatch.ts:78`, `itemRelationFilter.ts:49`, `mailLegacyEmailMigration.ts:193`, `recompute.ts`, `itemBatch.ts`, `propertyTypeMigration.ts`, `systemSettings.ts`, `itemTrash.ts:294`, and the MCP joins in `mcpAgentTools.ts`, `mcpAgentPageGrants.ts` and `mcpToolInvocation.ts` all carry a `database_id` predicate.

`getItemAutomationErrorCounts` (`backend/packages/data/src/observability/systemHealthReport.ts:134-144`) is the sixth such lookup: it joins `items` by id only. #1052 keeps that query and adds only an `item_automation` tenant predicate, so this issue prunes it too, after #1052.

## Task

Load `state-writes` (`deleteBlobIfUnreferenced` guards a destructive delete; the predicate must not change which rows count as references).

1. **Share the helper.** In `itemsStore.ts`, export `visibleDatabaseIds` from the module. `backend/packages/data/src/index.ts` names its `itemsStore.js` exports individually (`:39-41,265`), so the package's public surface does not change. Do not add it to `index.ts`.
2. **Prune the six lookups.** Each calls `visibleDatabaseIds` on the same client or pool it then queries, and binds the result as a new `$n::uuid[]` parameter:
   - `listLiveViewItemsAfter`: `JOIN items i ON i.id = m.item_id AND i.database_id = ANY($n::uuid[])`.
   - `generatePermissionManifest`: `SELECT properties FROM items WHERE id = $1 AND database_id = ANY($2::uuid[])`.
   - `deleteBlobIfUnreferenced`: the `NOT EXISTS` subquery gains `database_id = ANY($3::uuid[]) AND`.
   - `getActiveMailSyncProcessNames`: `JOIN items i ON i.id = s.item_id AND i.database_id = ANY($1::uuid[])`.
   - `listPendingImapFlagWrites`: the `folder` join gains `AND folder.database_id = ANY($4::uuid[])`.
   - `getItemAutomationErrorCounts`: `JOIN items i ON i.id = ia.item_id AND i.database_id = ANY($n::uuid[])`, keeping the predicate #1052 added.

   Results must be identical to today's for every caller. Do not add hand-written `tenant_id` predicates. Update each docstring that mentions the cross-partition scan, at least `viewItemsStore.ts:21-27`.
3. **Tests.** New `backend/packages/data/src/__tests__/remainingLookupPruning.test.ts`, using the same technique as #1003's `itemLookupPruning.test.ts`. Everything runs in one transaction on `getTestPool()` (the owner), rolled back at the end:
   - `DROP INDEX IF EXISTS tenants_single_tenant_guard`, then insert a second `tenants` row;
   - create each case's fixtures in each tenant's own scope with `SELECT set_config('app.tenant_id', $1, true)`, then `SET LOCAL ROLE semprec_data`;
   - wrap the client so the test records the SQL and parameters each function sends, then run `EXPLAIN (FORMAT JSON)` on that statement with those parameters and collect the scanned `items_p_*` relation names.

   Integration files run one at a time (`fileParallelism: false`, `backend/vitest.integration.config.ts:20`).

- **Plans.** With two tenants under `semprec_data` and tenant B in scope, the plan of the statement each of the six functions (`getItemAutomationErrorCounts` through `getSystemHealthReport`) sends scans only B's `items_p_*` partitions, none of tenant zero's.

  - `generatePermissionManifest` for B's project reads that project's `emailSendAutonomous`.
