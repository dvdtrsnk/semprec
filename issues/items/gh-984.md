## Context

`CORE_CRONTAB` fires `heartbeatSweep` every minute (`backend/packages/data/src/worker.ts:81`, handler at `:114-116`). `handleHeartbeatSweepTask` (`backend/packages/data/src/scheduler/sweep.ts:73-81`) runs `sweepDueHeartbeats` page by page, each page in its own `withTransaction`, for at most `MAX_SWEEP_CHUNKS = 50` pages (`sweep.ts:70`) of `SWEEP_CHUNK_SIZE = 100` rows (`backend/packages/data/src/scheduler/schedulerStore.ts:341`). One tick therefore handles at most 5,000 due rows for the whole database. Each page (`schedulerStore.ts:463-519`) does four things:
- selects due rows `ORDER BY id … FOR UPDATE SKIP LOCKED` (`:475-481`);
- reads the timezone with `getSystemTimezone(client)` (`:485`), which reads the visible `systemSettings` database's settings item (`backend/packages/data/src/systemSettings.ts:29-42`);
- inserts a `heartbeat_occurrences` row and advances `next_fire_at`;
- enqueues the fire job with `enqueueJob` (`:503-514`).

The only due-row index is `project_heartbeats_due_idx (next_fire_at) WHERE enabled AND next_fire_at IS NOT NULL` (`backend/packages/data/src/db/migrations/0001_core_schema.sql:109-110`). The page/cap design is recorded in `docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`.

Tenancy state this issue builds on:
- Every tenant table (here `project_heartbeats`, `heartbeat_occurrences`, `databases`, `items`) carries `tenant_id`. A RESTRICTIVE RLS policy `tenant_isolation` filters it with `tenant_id = (SELECT app_tenant_default())`.
- `app_tenant_default()` is `COALESCE(app_current_tenant(), app_sole_tenant())`. `app_current_tenant()` reads the transaction-local GUC `app.tenant_id`.
- `withTransaction` and the pool from `createPool` set that GUC from the ambient scope: `runInTenant(tenantId, fn)` sets the tenant, and `runAsSystem(reason, fn)` sets `''` (`@semprec/shared`).
- In system scope, tenant rows are visible only while exactly one tenant exists. With two tenants, or after the strict switch (#1067), nothing is visible, so a sweep that stays in system scope silently fires nothing.
- Since #982, the queue envelope is `{ traceId, tenantId: string | null, payload }`. `enqueueJob` stamps `tenantId` from the current scope. `heartbeatSweep` is a `tenancy: 'system'` task, so the runner calls its handler inside `runAsSystem`.
- #983 added `forEachActiveTenant` (`backend/packages/data/src/tenancy/forEachActiveTenant.ts`, exported from `@semprec/data`). Called from a system scope, it runs the callback inside `runInTenant(tenantId, …)` for every `tenants` row with `status = 'active'`, starting at a rotating offset. A throwing tenant does not stop the others. After every tenant was attempted, the failures are rethrown together as an `AggregateError`, so the job is retried.
- This issue calls it as `forEachActiveTenant(pool, async (tenantId) => …)`. If the merged signature differs, use the merged one; only the semantics above matter here.

Running each tenant's pass in its own scope means the following:
- each tenant's heartbeats are scheduled in that tenant's own settings timezone;
- occurrence rows default to the right `tenant_id`;
- every fire job's envelope carries that tenant, which the fire task restores (#982);
- one tenant's backlog cannot use up another tenant's tick.

## Acceptance criteria

All of these are integration tests (`*.test.ts`), with two tenants under the runtime role unless stated otherwise.
- **Per-tenant timezone and stamping.** Tenant zero (settings timezone `Europe/Prague`) and tenant B (`America/New_York`) each have one due `dailyTime` heartbeat. One `heartbeatSweep` run produces all of the following:
  - each heartbeat gets a `queued` occurrence;
  - each heartbeat's new `next_fire_at` is the rule's next local time in its own tenant's timezone;
  - each `heartbeat_occurrences` row carries its heartbeat's `tenant_id`;
  - each enqueued fire job's envelope `tenantId` is its heartbeat's tenant.
- **Per-tenant cap.** With `maxChunksPerTenant: 1`, tenant zero has 101 due heartbeats and tenant B has 1. After one run, 100 of tenant zero's are advanced, 1 is still due, and B's is advanced, whatever the iteration order. A second run advances the last one.
- **Failure isolation.** A failing page in tenant B, injected with a test-only trigger raising on `heartbeat_occurrences` inserts for B's heartbeat, does not stop tenant zero's due heartbeat from being fired and committed, and the handler rejects.
- **Inactive tenant.** A due heartbeat of a tenant whose `status` is `suspended` stays due.
- **Single tenant unchanged.** With only tenant zero, the existing `scheduler.test.ts` sweep cases pass.
- **Index.** After migrations, `pg_indexes` shows `project_heartbeats_tenant_due_idx` on `(tenant_id, next_fire_at)` with predicate `enabled AND next_fire_at IS NOT NULL`, and `project_heartbeats_due_idx` still exists.
