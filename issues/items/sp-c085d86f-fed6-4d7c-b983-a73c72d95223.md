### Requirement gh-1845: [inbox-proposals 12/19] Add POST /api/proposals/:id/reject

#### Context

Model tier rationale: A thin custom route over an existing, already idempotent action, following the registration pattern of the confirm route, with the work concentrated in route matrix and tenant-isolation registration.

`rejectProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) already discards a card without writing a destination: it locks the card, returns an already `rejected` card unchanged, refuses a `confirmed` one with a 400 `validation_failed` (field `status`), appends a history entry ("Rejected by user." or the supplied message) and enqueues the Journal inbox recompute. It has no HTTP route: only `POST /api/proposals/:id/confirm` is registered (`createConfirmProposalRouteHandler` in `backend/packages/data/src/inbox/inboxRouteHandlers.ts`, declared in `inboxModuleManifest.ts`), and a generic `PATCH /api/items/:id` cannot set `status` because that property is system-owned. A client therefore cannot discard a card.

Discarding must work for every card state the user can see: complete, incomplete, needing clarification, invalid, and transcript cards. After a transcript card is discarded its pairing state is derived by #1636 (the list read), and re-creating it after a rerun is prevented by the card's idempotency key; speaker questions are handled by #1640. Approval cards are not Processing proposals and are rejected through `PATCH /api/approval-requests/:id`, which this issue does not change.

This issue builds on #1807 (the card list, whose acceptance criterion about a rejected card disappearing is checked here), #1823 (the count) and #1430 (typed history entries; the history entry written here uses the `rejected` kind). #1852 adds an optional version check, #1937 reopens a rejected card, and #1870 mounts the revise route and relies on the reject route existing.

Decision: the route is a custom route because a reject is a status transition with a history entry and a Journal recompute in one transaction, which the generic item update cannot express.

Shared-file ordering: this issue also waits for #1843 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1850: [calendar-recurrence 06/08] Match recordings to virtual event occurrences

#### Context

Model tier rationale: It changes the transcription worker's matching decision and the proposal confirm path across two processes, adds a new ownership-sensitive write at confirm time, and must keep an exactly-one-materialization guarantee, so a mistake links recordings to the wrong occurrence or creates duplicate Events.

The transcription worker matches a finished recording to an Event in `matchTranscriptToEvent` (`backend/packages/data/src/transcription/transcriptEventMatch.ts`): one matching Event is linked, otherwise a Processing proposal card (`kind` `transcript`) is created for the user; the worker writes the match result under `docs/adr/2026-09-23-transcription-worker-writes-event-match-results.md`, and a card's confirm runs in `inbox/proposalActions.ts` as the user's own action. The matching by time-interval overlap, and the `candidates` list on the card, are delivered by #1813 and #1451. Matching considers only stored Events, so a recording of a daily Standup whose occurrence has not been materialized finds nothing.

This issue lets a recording match the virtual occurrence of a recurring Event. The worker never materializes an occurrence (any further worker write is a new decision under that ADR); instead the virtual occurrence goes onto the card as a candidate, and it becomes a real Event only when the user confirms the card.

Behavior:

- Candidate search also considers live recurring Events of a matchable type (`standup`, `meeting`) and expands them over the recording's time window with `expandEventOccurrences` (#1877), keeping only occurrences that overlap the window and are virtual (a materialized occurrence is a stored Event and is found by the normal path; a cancelled date is skipped).
- A virtual occurrence is never linked directly, even when it is the only candidate: a card is always created, and the occurrence appears among the card's `candidates` as an object `{ seriesId, occurrenceDate }` next to the existing candidate variant for stored Events (leave the existing variant unchanged).
- The card's proposed link is a relation proposal whose target is the occurrence's synthetic id `<seriesId>@<date>`.
- On confirm, in the same transaction, if the target is a synthetic id the confirm path calls `materializeEventOccurrence` (#1843) and uses the real item for the Transcripts-Events edge; the recording ends up linked only to that occurrence. A repeated confirm links the same item (the materialization is idempotent).

Decision: materialization at confirm is the adopted behavior; storing an occurrence date as edge metadata on the series, or a new decision about worker writes, is not done.

#### Task

Load `state-writes`, `testing` and `canonical-keys`.

1. In `backend/packages/data/src/transcription/transcriptEventMatch.ts`, add virtual-occurrence candidates to the candidate search as described, and make a virtual candidate always produce a card (never an automatic link). Add the `{ seriesId, occurrenceDate }` candidate variant to the card's `candidates`.
2. In `backend/packages/data/src/inbox/proposalActions.ts` (confirm of a transcript card with a `relation` envelope on the Transcripts `event` property) and in the envelope validation `assertValidProposalEnvelope` of `inbox/inboxTickAction.ts`, accept a synthetic occurrence id as the target when `parseOccurrenceId` (#1843) succeeds and the series exists; at confirm, materialize it and write the edge to the real item inside the confirm transaction.
3. Tests: a recording at 9:01 on Wednesday 14 Oct 2026 for a weekday 9:00-9:30 Standup series creates a card whose candidates contain `{ seriesId, occurrenceDate: "2026-10-14" }` and links nothing; confirming it materializes the 14 Oct occurrence and links the recording only to it, other occurrences stay virtual; confirming twice links the same item; a materialized occurrence is matched as a stored Event without a card when it is the only candidate; a cancelled date is not a candidate; a series of an unmatchable type is ignored; a synthetic id with an unknown series or a non-occurrence date is rejected at card validation.

#### Touches

### Requirement gh-1852: [inbox-proposals 13/19] Accept an optional ifVersion on confirm and reject

#### Context

Model tier rationale: One additive optimistic-concurrency check reusing the existing 409 contract on two already-locked actions, with a subtle precedence rule between state and version.

A card can be recomputed by Semp or resolved on another device between the moment the user sees it and the moment the decision arrives. Decisions must apply to what the user actually saw. `confirmProposalWithClient` and `rejectProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) lock the card row (`lockLiveProposal`) but accept no version. The generic item update already offers the contract: an `ifVersion` equal to the item's `updatedAt`, answered on mismatch with 409 `version_conflict` and `details.currentItem` (`backend/packages/data/src/chokePoint/itemsStore.ts`, `backend/services/semprec-api/src/adapter/errorContract.ts`).

Decision: `ifVersion` is optional on both routes, because a required field would break existing clients (ADR `docs/adr/2026-09-11-additive-only-rest-contract-no-url-versioning.md`); without it behavior is exactly as today. Decision: state takes precedence over version, so a retry of a decision that already took effect succeeds (an offline queue replays actions): confirm on an already `confirmed` card and reject on an already `rejected` card return today's idempotent 200 even with a stale `ifVersion`. A card locked in an incompatible status keeps today's 400 `validation_failed` with field `status`, now also carrying `details.currentStatus`.

This builds on #1845, which adds the reject route. New card routes introduced by other issues (values, reset-overrides, type change, recompute, reopen, revise) accept `ifVersion` in their own issues; the `proposal_locked` code for them is introduced by #1620.

#### Task

Load `state-writes`, `error-handling` and `testing`.

1. Accept an optional `ifVersion` string (the card's `updatedAt`) in the body of `POST /api/proposals/:id/confirm` and `POST /api/proposals/:id/reject`; validate its shape and pass it to the actions.
2. In both actions, after the row is locked and the status short-circuit for the idempotent case, compare `ifVersion` with the locked card's `updatedAt`; on mismatch throw the existing conflict error so the response is 409 `version_conflict` with `details.currentItem` set to the card, and write nothing.
3. Order of checks: (a) card missing -> 404; (b) idempotent terminal state (confirm on `confirmed`, reject on `rejected`) -> 200 unchanged, ignoring `ifVersion`; (c) incompatible status -> 400 `validation_failed` with field `status` and `details.currentStatus`; (d) `ifVersion` mismatch -> 409; (e) proceed.
4. Tests: stale `ifVersion` on an open card -> 409 and no write; current `ifVersion` -> success; stale `ifVersion` on an already confirmed card -> 200 unchanged; no `ifVersion` -> unchanged behavior; the same matrix for reject.

#### Touches

- backend/packages/data/src/inbox/proposalActions.ts (confirm and reject: version check)
- backend/packages/data/src/inbox/inboxRouteHandlers.ts (body parsing for both handlers)
- backend/packages/data/src/inbox/__tests__/inboxRouteHandlers.test.ts

#### Scope

##### In scope

- Optional `ifVersion` on confirm and reject, the precedence rule and `details.currentStatus` on the 400.

##### Out of scope

- `ifVersion` on values, reset-overrides, type change, recompute, reopen and revise; each is added in the issue that mounts that route (for example #1892, #1912, #1937, #1870).
- The `proposal_locked` error code for new routes; #1620.
- Idempotent replay of stored responses; #1894.

#### Acceptance criteria

- When confirm is called on an open card with an outdated `ifVersion`, then it answers 409 `version_conflict` with `details.currentItem` and nothing is written.
- When confirm is called on an already confirmed card with an outdated `ifVersion`, then it answers 200 with the card unchanged.
- When confirm or reject is called without `ifVersion`, then behavior is as before this issue.
- When a card has an incompatible status, then the answer is 400 `validation_failed` with field `status` and `details.currentStatus`.

### Requirement gh-1834: [transcripts 14/19] Attach transcript segment refs to Semp messages

#### Context

Model tier rationale: A new ref kind plugged into the generic message-ref validation and the turn-context expansion of the Semp chat, reusing the segment reading of the transcript tools; the surface is small, but it depends on two contracts (ref validation hooks and turn expansion) owned elsewhere, so the integration seams are the risk.

A user can drag the Semp bubble onto a stretch of a transcript to give it to Semp as context, and Semp receives a reference, not text. A message ref is stored with the message (validated and stored by #1682); this issue defines everything specific to a transcript segment ref `{ kind: "transcriptSegment", itemId, startsAt, endsAt }`, where `itemId` is a Transcripts item and `startsAt` and `endsAt` are seconds on the recording's timeline. It builds on the read tools of #1832, whose segment reading (names, bounded ranges, surrounding segments) it reuses.

Three things are specific to this kind: validating that the ref points at a transcript and a sensible range, expanding it into the text given to the model when a turn is prepared, and giving it a label and a state for the message history. The generic validation checks that the item exists in the tenant and that the pair item/database matches; the history shows a trashed transcript as recoverable and a purged one as gone; both are generic behaviors of the ref machinery and apply here unchanged.

Decisions:

- Validation is per kind: the item must be a live item of the Transcripts database of the tenant; `0 <= startsAt <= endsAt`; the range must not exceed the limit of `transcript.segment.get` (200 segments or 15 minutes). A range reaching past the end of the recording is accepted and clamped when expanded.
- Expansion gives the model the segments of the range with the speakers' names plus three segments of context on each side, using the same function as `transcript.segment.get`; the stored message keeps only the ref (with its label), never the expanded text. The text is never logged.
- The label of the ref is the transcript's display name with the time range (for example "Client meeting 5:12-6:30"); the history resolves it from the current name, so a renamed transcript shows its new name.

### Requirement gh-1851: [trash 02/06] List trashed items across databases

#### Context

Model tier rationale: One read route with a non-trivial query (cascade roots, archived databases, keyset paging) and a small migration, following the custom-route and tenant-isolation test patterns already in the repository; no write path and no new lifecycle.

Items are soft-deleted (`items.deleted_at`) and purged 30 days later by the daily sweep (`backend/packages/data/src/trash/purgeExpiredTrash.ts`, issue 156). A client can restore one item (`POST /api/items/:id/restore`) and can read the trashed items of one known database (`POST /api/databases/:id/query` with `inTrash: true`, which mixes live and trashed items), but nothing lists everything the user deleted across all databases, and nothing tells how many days remain before an item is purged. The "Recently deleted" screen needs exactly that: the newest deleted first, with where each item came from and the days left.

This issue adds `GET /api/trash/items`, a read-only custom route of the schemaCore module (`backend/packages/data/src/chokePoint/schemaCoreModuleManifest.ts`, justification `single-consumer-read`). It also makes the retention length a shared constant (`purgeExpiredTrash.ts` currently holds it as a local `DEFAULT_RETENTION_DAYS = 30`), because both the sweep and this listing must agree on when an item is purged. The route is ordered after #1837 only because both add a route to the same manifest and route matrix. The listing of archived databases (#1873), the purge of archived databases (#1875), the account summary counts (#1903) and the listing of trashed pages (#1855) build on it.

Decisions:

- Only roots of a delete cascade are listed. An item of an inline database (a database owned by another item through `databases.parent_item_id`) whose owner item was deleted at the same moment (same `deleted_at`) was trashed together with it and is not a separate row; an item trashed on its own, at a different time, is a root.
- Items of archived databases are not listed (archived databases appear in the database listing).
- `daysLeft` is the number of whole calendar days from today to the purge day, both taken in the tenant's time zone (System settings `timezone`): an item deleted today has 30, one deleted 26 days ago has 4, never below 0.
- `databaseName` is the stored name for a user database and the localized catalog name (the user's `users.locale`) for a system database; `databaseKey` and `ownerModuleId` are `null` where the database has none.

Shared-file ordering: this issue also waits for #1845, #1846 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

4. Response: `{ items: [{ item, databaseId, databaseKey, ownerModuleId, databaseName, deletedAt, purgeAt, daysLeft }], totalCount, nextCursor }` where `item` has the shape of the item envelope (`id`, `databaseId`, `properties`, `computed`, `updatedAt`, `deletedAt`), `purgeAt` is `deletedAt` plus `RETENTION_DAYS`, `totalCount` counts all roots matching the same predicate regardless of the cursor, and `nextCursor` is `null` on the last page. ### Requirement gh-1856: [areas-projects 13/13] Preview the impact of deleting an item

#### Context

Model tier rationale: One read-only endpoint composes counts from an existing computation and an existing subtree walk across defined seams with existing fixtures, and writes nothing.

Before a user (or an agent asking for approval) deletes a record, the product shows what the deletion affects: the connected records per collection, the records nested inside it, its subpages, and the places that link to it. Deletion is soft (items go to the trash and are restorable for 30 days; `backend/packages/data/src/chokePoint/itemTrash.ts`), but the confirmation must always state the impact on connected records. No preview exists today.

This issue adds `GET /api/items/:id/delete-impact`. The connected-record counts come from #1839. The subpage count comes from `collectSubpageTree` of #1723 and the link count from #1403 (value links); the response fields for them are defined here and filled once those exist. #1876 and #1882 build on this preview.

Response: `{ related: [{ databaseKey, count }], subtreeItemCount, subtreePageCount, linksToOwn: [{ itemId, propertyKey }] }`.
- `related` is the counts of `relation.related` (without filters and flags).
- `subtreeItemCount` is the number of records inside the item's inline databases, recursively (the walk `collectItemSubtree` in `itemTrash.ts`, root excluded; export it for this use).
- `subtreePageCount` is the number of all pages nested below the item at any depth (the length of `collectSubpageTree` exported by #1723, root excluded); for a host (project, area, event, Journal day) it counts every page below the host's page, for a page every page below that page. It is named differently from the direct `subpageCount` of `page.get` (#1615) so the two cannot be confused. Decided by the product owner: the confirmation states the full impact, so nested pages are counted at every depth ("also deletes 7 subpages").
- `linksToOwn` lists value links that point at this item (the `itemId` and `propertyKey` of each link source).

Decision: `subtreeItemCount` is included now; it is cheap, and the response shape is stable for clients that ignore it.

This endpoint is REST-only, a read of the same shape as `GET /api/items/:id` (core item read permission), not a new catalog operation; if it needs a port method, follow `docs/adr/2026-10-01-rest-only-port-extension-methods.md`. It must not change the approval request payload or the exactly-once hash in `chokePoint/destructiveProjection.ts`.

Shared-file ordering: this issue also waits for #1851 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1882: [tasks-core 11/11] Trash a whole recurring series and report what deleting a task affects

#### Context

Model tier rationale: Deleting and restoring a whole series is a wide destructive data change with cascade-epoch ownership, restore correctness, approval-snapshot staleness and a recurrence-rule side effect that must all stay consistent in one transaction.

What the user sees: deleting a task moves it to Recently deleted and keeps it restorable for 30 days. Deleting any instance of a repeating task deletes the whole series; restoring any one of them brings the whole series back and turns the repeat rule on again. The confirmation always states what else is affected: how many attachments stay in Files (and keep the project they got from the task as their own), how many instances the series has, and how many events the task is placed in (those events simply stop showing it). Values that other items inherited from the deleted task become their own and are not re-linked on restore.

Today (backend/packages/data):

- `chokePoint/itemTrash.ts` `itemDeleteWithClient` soft-deletes an item together with its cascade subtree (`collectItemSubtree`), all rows sharing one `deletedAt`; `restoreItem` restores only rows whose `deletedAt` equals the root's (the cascade epoch). Purge after 30 days deletes edges, docs, `task_recurrence` rows and search entries (`deleteItemDependents`). Soft delete keeps the edges. The item delete in `itemTrash.ts` runs no domain hook.
- A series is a set of separate Tasks rows, one active instance carrying an active `task_recurrence` row (`tasks/taskRecurrenceStore.ts`: `getTaskRecurrence`, `setTaskRecurrenceActive`, `deleteTaskRecurrence`). After #1605 every instance carries a `seriesId`.
- `item.delete` by an agent needs approval; the approval snapshot comes from `chokePoint/destructiveProjection.ts` and covers only the root item. #1856 adds a preview of what deleting an item affects (counts of dependent and related items); it does not know about series.

What this builds on: #1601 (delete and restore domain hooks called for every row of the subtree sharing the epoch, and only for really restored rows, with the matching amendment of the hooks ADR and of the `itemTrash.ts` exception in `dependency-cruiser.rules.json`), #1656 (links whose source is deleted are detached and not re-linked on restore, driven by that hook), #1856 (impact preview) and #1605 (series identity).

Decision: the whole series is trashed under one shared `deletedAt`, so one restore of any instance restores all of them and nothing else; this reuses the existing epoch rule instead of a second restore mechanism.

Decision: events keep their edges to a deleted task (soft delete keeps edges) and simply ignore it; restoring the task shows it in them again.

Heartbeat triggers, rollup recompute and invalidations run for every deleted row exactly as for the existing subtree.
2. In the restore path, restoring any one of them restores all rows with that epoch (this is the existing behavior once the rows share it) and, through the restore hook from #1601, sets the series' `task_recurrence.active` back to true on exactly one instance: the one that was active when the series was deleted. Which instance that was is recorded by the delete hook in the same transaction (store it where the series rule already lives; do not add a second source of truth for activeness). A restore of an instance never creates a new instance.
3. Delete and restore hooks (Tasks): on delete, record the active instance; on restore, re-activate. Verify that `value-links 04` detaches links whose source is the deleted task and that restoring does not re-link them (a test only; the mechanism is not changed here).
4. Impact reporting: extend the preview from #1856 with `seriesInstanceCount` (0 for a non-series task), the count of attachments (`Files.tasks` edges) and the count of host events (`Tasks.hostEvents` edges), and make the destructive projection for `item.delete` (`destructiveProjection.ts`) include the same numbers in the snapshot so an approval granted for one impact is not executed if the series gained an instance in the meantime (the existing staleness check then reports the conflict with the current numbers).
5. Tests (real database): deleting one instance of a three-instance series puts all three in the trash with one `deletedAt`; restoring any one brings all back with exactly one active recurrence; a non-series task is unaffected; an agent `item.delete` shows the impact numbers in the approval and is refused as stale after a new instance appears; links of attachments become independent on delete and stay so after restore; purge after 30 days removes the whole series including its recurrence row.
