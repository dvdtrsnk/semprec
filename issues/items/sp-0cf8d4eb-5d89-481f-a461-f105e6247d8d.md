## Context

Model tier rationale: One data mapping, one shared ViewModel state and the calendars sheet's sections gain the account identity, with the CoreKit bridge, the Apple new item picker, copy and tests; no new module, route or backend change.

On production data a person has the own calendars "Osobní", "Rodina" and "Práce" and an iCloud internet account whose synced calendars are "Osobní", "Rodina", "Work", "Timelog", "Jmeniny" and "♥️". Account calendars are Calendars items with `kind` `account`, `name` null (the shown name is `remoteName`) and the relation `account` to the Mailboxes item of the account, whose title property is `name` (for example "iCloud") and whose `addresses` (long text, separated by new lines or commas) start with the primary address (for example `david@tresnak.cc`).

The calendar picker of the new item sheet (`newItem.calendar`, `NewItemFormView`) lists every calendar that takes new events in one flat menu, so "Osobní" and "Rodina" each appear twice with nothing that tells them apart, and the chosen value in the form row is just the name. The calendars are read by `HttpCalendarCatalogRepository.calendars()` with `{"include":{"relations":{"account":[]}}}`; `CalendarStoredItem.toCalendar()` keeps only the account's id (`CalendarInfo.accountId`). Read-only account calendars and system calendars are already excluded by `CalendarInfo.takesNewEvents`.

The calendars sheet (`calendar.calendars`, `CalendarListViewModel`) already shows the calendars of each internet account in a section under the account's name (`CalendarAccountSection`), but not the account's address. The details sheet of an event has no calendar picker, and Android has neither the new item sheet nor the calendars sheet (`NewCalendarItemViewModel` and `CalendarListViewModel` are Apple-only in the architecture policy), so there is no Android part.

## Task

Load `kmp-shared`, `shared-viewmodel`, `apple-swiftui`, `canonical-keys`, `testing` and `mobile-verify`.

1. Data: the calendars query expands the account relation with its `addresses` (`{"include":{"relations":{"account":["addresses"]}}}`), and `CalendarRelationTarget` decodes the target's `title` and `properties` (a hidden target has neither). `CalendarInfo` gains `accountName` (the target's title, `null` when blank) and `accountAddress` (the first non-blank entry of `addresses`), both only for an account calendar.
2. Presentation, new item sheet: `NewItemState` carries `groups: List<NewItemCalendarGroup>` instead of a flat list; `calendars` stays as the flattened list in the same order. The first group holds the own calendars (`account` `null`), then one group per internet account in the order its first calendar is listed, with `NewItemAccount(id, name, address)`; account calendars the server names no account for share one group with an empty id. Only calendars with `takesNewEvents` are offered, and an empty group is left out. Each `NewItemCalendar` gains `qualifier: NewItemCalendarQualifier`: `NONE` when no other offered calendar has the same name (trimmed, case-insensitive); otherwise `OWN` for an own calendar, `ACCOUNT_NAME` for an account calendar whose account has a name no other offered account has, and `ACCOUNT_ADDRESS` when the account's name is missing or shared and it has an address (else `ACCOUNT_NAME`).
3. Presentation, calendars sheet: `CalendarAccountSection` gains `address` (the account's primary address from the internet accounts read with the list).
4. Apple: CoreKit values and mappings for the groups, the account, the qualifier and the section address, with `SharedCalendarSheetMappingTests` and `SharedCalendarListMappingTests` cases. The new item calendar row opens a menu with one section per group: the own one titled with the existing `calendars.group.own`, an account one titled "name · address" (either alone when the other is missing, `calendars.account.unnamed` when both are), each calendar with its colour dot and a check on the chosen one. The row shows the chosen calendar's dot and name, followed by " · " and its qualifier (`calendars.group.own`, the account name or the address) when the qualifier is not `NONE`. The account header of the calendars sheet shows the address under the name. No new copy key is needed.
5. Tests: commonTest for the mapping (account name and address from the expanded relation, a hidden or missing target, the query body) and for the new item ViewModel (own before account groups, two accounts, ambiguous names on both sides with each qualifier, read-only and system calendars excluded, a server-unnamed account); the calendars sheet test for the address; Swift feature tests over `ScriptedNewItemScreenModel` for the menu sections and the row's label.
