**Blocked by:** #103

## Context

Every Inbox source needs an explicit, deduplicated proposal state. #101 seeded the `processingProposals` database and its properties, #102 gave Inbox item types an explicit `processingMethod`, and #103 dispatches one deduplicated `semprec.tick` job per changed Inbox item. This part implements the tick handler itself: the fingerprinting rules for both source kinds, the create / revise / skip gate that keeps AI calls from being wasted on unchanged sources, and the locked-card rule. The sibling part #104 builds on this handler and adds the remaining status transitions (`needsClarification` for a missing or deleted type, `invalid` for a deleted source), proposal envelope validation, and history entries. #105 later adds the user-context confirm/reject/revise actions on top of the rows computed here.

## Task

Implement the `semprec.tick` action (the handler registered for the heartbeat event job from #103) over the proposal database:

- **Fingerprints.** Fingerprint Inbox sources (`kind = 'inbox'`) as SHA-256 of the canonical type emoji and text. Retain the transcript fingerprint shape `{text,startsAt,endsAt}` for shared proposal rows (`kind = 'transcript'`); the same `fingerprint` property holds both shapes. Store the computed value in the proposal's `fingerprint` property.
- **Create / revise / skip gate.** For the source item named by the job, look up its proposal row (`sourceInbox` = the item). Create a proposal only when none exists; revise an existing one only when it is unlocked and its stored fingerprint differs from the newly computed one. In every other case (unchanged fingerprint, or a locked proposal) return without any AI call and without any proposal write.
- **Locked cards.** Never recompute a proposal whose `status` is `confirmed` or `rejected`, regardless of source changes.
- **Recognized type.** When the source's `type` resolves to an existing Inbox item type with a `processingMethod`, produce `status = proposed` with a `proposal` payload of exactly the generic envelope `{ entityKind, target, properties }`: `entityKind` is `pageContent` or `database` according to the type's `processingMethod`; `target` is the target page id or the type's `targetDatabase` id; `properties` is the map of values (for `database` the properties the concrete target database requires, for `pageContent` the content of the new block). The content-level decision (which project/page, which property values) is invoked through one injectable proposal-computation function backed by the LLM call; its prompt engineering is out of scope.
- **No target write.** Proposal computation must never write to any target database or page; the only rows it creates or updates are in `processingProposals`.
- **Stubs for #104.** In this part, a source whose `type` is missing or cannot be resolved, and a tick whose source item no longer exists, return without creating or modifying a proposal; the `history` property is written as `[]` on create and left untouched on revise. #104 replaces these three gaps with `needsClarification`, `invalid`, and history entries respectively.

## Scope

### In scope

- The `semprec.tick` handler, both fingerprint shapes, the create/revise/skip gate, the locked-card rule, the `proposed` status with the generic envelope, and the no-target-write guarantee.

### Out of scope

- `needsClarification` and `invalid` transitions, envelope validation, and history entries (#104).
- Concrete prompt engineering, confirmation writes (#105), and UI (#106).

## Acceptance criteria

- An event for a source whose fingerprint is unchanged makes no AI call and no proposal write.
- A first event for a source with a recognized type creates exactly one `proposed` row whose `proposal` has exactly the keys `entityKind`, `target`, and `properties`, and whose `fingerprint` equals SHA-256 of the canonical emoji and text.
- An edit that changes the fingerprint of an unlocked proposal revises that same row rather than creating a second one.
- A `confirmed` or `rejected` proposal is never modified by any later tick, even when the source changes.
- Transcript-kind proposal rows keep the `{text,startsAt,endsAt}` fingerprint shape.
- No tick run writes a row into any database or page other than `processingProposals`.
