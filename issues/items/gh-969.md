**Blocked by:** #968

## Context

The backend review bot is told that cross-user authorization does not matter. `backend/review-rules/context.md:26-40` says `bootstrapFirstAccount` is the only path to `createUser`, that "this deployment can therefore never have more than one human account", and: "Do not report missing per-user authorization (a second human user reading or writing another human user's data) as a finding". It then names actor type as the one real authorization boundary.

That stops being true with #968. Each user now gets one tenant: their complete, isolated Semprec environment. No user may ever see, infer or be notified about another user's data, and no sharing exists or is planned. A foreign id must behave exactly like a non-existent id: same status, same body. Global uniqueness must never act as an existence oracle. Isolation is enforced twice, by Postgres row-level security on every tenant table and by an explicit tenant scope on every code path, and a missing scope means "nothing visible / write refused", never "everything visible". #968 added the `tenants` table, `users.tenant_id`/`users.role`, the SQL functions `app_current_tenant()`, `app_sole_tenant()` and `app_tenant_default()`, the `tenants_single_tenant_guard` index, and the ADR `docs/adr/<date>-tenant-isolation-through-row-level-security.md`. Take its exact filename from that pull request.

Cross-tenant access becomes this platform's most severe defect class. The reviewer must hold every later tenancy pull request to it, starting with #971..#974. Many code paths still predate tenant scoping and are moved onto it by their own issues, and the rules must not turn every pull request that merely touches such code into a finding. The actor-type paragraph (`Actor.type`, `assertViewWritable`, agent proposals) stays valid and is kept.

## Task

Load `adr-conventions` (the rules cite the ADR rather than restate it). The pull request description must quote the removed paragraph, because `backend/review-rules/tasks/review-rules.md` item 1 treats a removed rule as a finding unless the issue calls for it, and this issue does.

1. `backend/review-rules/context.md`: replace the paragraph at lines 26-40 (from "Tenancy: `bootstrapFirstAccount`" to "a human-vs-human check is not.") with two paragraphs.
   - **Tenancy:** Semprec is multi-tenant: one tenant per user, holding all of that user's data and agents, and no sharing. Isolation is enforced by RLS on every table classified `semprec:tenancy=tenant` and by an explicit tenant scope (`app.tenant_id`) on every code path. Missing scope fails closed. Until go-live, `tenants_single_tenant_guard` keeps a deployment at one tenant, and the transitional `app_tenant_default()` falls back to that sole tenant, so the previous release keeps working. Code written before tenant scoping is moved onto the scope by dedicated issues: do not report a pre-existing scope-less query that the pull request neither adds nor changes. Earlier ADRs that rest on a single human account (`docs/adr/2026-09-12-per-process-agent-run-watch-registry.md`, `docs/adr/2026-09-12-thin-user-scoped-realtime-invalidations.md`) describe code that is being replaced. They justify no new single-account code. Cite the tenancy ADR.
   - **Actor type:** keep the existing actor-type text as written (`Actor.type` is `'user' | 'ai_agent' | 'system'`, `assertViewWritable`, both ADR links, "a missing or bypassable `actor.type === 'ai_agent'` check is the real privilege-escalation shape"). Say that it is the second authorization boundary, alongside tenant.
2. `backend/review-rules/rules.md`: append these rules. Each states its reason in one clause and cites the tenancy ADR.
   - A migration that creates a table states `COMMENT ON TABLE <t> IS 'semprec:tenancy=tenant'` or `'semprec:tenancy=global'` in the same file. A tenant table also gets, in that file, `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)`, `ENABLE ROW LEVEL SECURITY`, the RESTRICTIVE `tenant_isolation` policy (`USING`/`WITH CHECK (tenant_id = (SELECT app_tenant_default()))`) and the PERMISSIVE `tenant_rows` policy (`USING (true) WITH CHECK (true)`). Global is only for identity-plane, admin-plane and operator tables that hold no user content. Missing any of these: high.
   - A unique index, unique constraint or primary key on a tenant table that does not lead with `tenant_id` is high, unless it is a server-generated surrogate key or is scoped by the server-generated id of a parent row in the same tenant (such as `properties (database_id, key)`). Reason: unique and foreign-key checks ignore RLS, so a global key is an existence oracle and a cross-tenant collision.
   - Tenant identity taken from a request body, query string, path segment, a header an untrusted caller can set, a job payload field, or model output: critical. Its only sources are the authenticated session, the queue job envelope stamped from the producer's scope, a NOTIFY payload stamped by its publisher, an internal-token-authenticated caller cross-checked against a row visible in that tenant, an MCP run credential, and a router function resolving an external identifier (a Graph subscription id, a Gmail address) to its tenant.
   - New code that reads or writes a tenant table must run in a scope established from one of those sources, or as explicit system work under the next rule. New code that relies on the transitional sole-tenant fallback as its tenant, or that picks "the" user or tenant by earliest, first or `LIMIT 1`, is high. It is critical when it lets one tenant reach another's rows.
   - Cross-tenant system work enumerates tenants and does each tenant's work inside that tenant, and one tenant's failure must not skip the others. The alternative is a `SECURITY DEFINER` function owned by a dedicated `NOLOGIN BYPASSRLS` router role: column-level `SELECT` only, pinned `search_path`, `EXECUTE` revoked from `PUBLIC` and granted to one runtime role, returning only ids or numbers. Any of the following is critical: granting a runtime role `BYPASSRLS`, superuser or table ownership; `SET row_security = off`; a permissive policy that widens visibility; one query reading several tenants' rows.
   - A `SECURITY DEFINER` function that reads or writes a tenant table without confining itself to `app_current_tenant()` (filtering by it, or verifying the referenced row's tenant) is critical.
   - An endpoint, socket frame, MCP tool or job must answer another tenant's id exactly as it answers a random id: same status, body and headers, and no branch such as an ETag/304 check taken before the tenant check. A difference is critical.
   - A log line or error message carrying user content (item properties, mail subjects, bodies or addresses, file names, prompts, model output) is high. Log ids and counts.
3. `backend/review-rules/tasks/security.md`: append numbered items.
   - Any path by which one tenant's request, job, socket, agent or notification can read, write, infer or be told about another tenant's data: critical. Name the shape, using the tenancy rules in `rules.md`.
   - A change that weakens enforcement: critical. This covers a runtime role gaining `BYPASSRLS`, superuser or table ownership; RLS disabled, or a tenant policy dropped or loosened, on a tenant table; and a tenant-classified table reclassified global without the issue calling for it.
   - User content reaching a log call or an error returned to a client: high.
