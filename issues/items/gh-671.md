## Context

`withTransaction` in `backend/packages/data/src/db/pool.ts` (lines 29-61) is the transaction runner for every choke-point write and most module writes. Its failure path (lines 53-57) is:

```ts
} catch (err) {
  afterCommitCallbacks.delete(client);
  await client.query("ROLLBACK");
  throw err;
}
} finally {
  client.release();
}
```

When `ROLLBACK` itself rejects — the connection dropped mid-transaction, the server terminated the backend, a statement timeout fired on the rollback — the rejection from `client.query("ROLLBACK")` replaces `err`: the caller sees `Connection terminated` (or similar) instead of the error that actually aborted the work, and the log line that would have explained the failure is gone. Then `finally` calls `client.release()` with no argument, which returns the client to the pool as healthy; `pg`'s `Pool` only destroys a client on `release(err)` (a truthy argument), so a connection in an unknown state — possibly still inside an aborted transaction if the rollback failed for a non-fatal reason — is handed to the next caller, whose first statement fails with `current transaction is aborted, commands ignored until end of transaction block`.

`createPoolClientTransactionRunner` in `backend/packages/data/src/projectAgentGuidanceStore.ts` (lines 108-130) already handles the first half (swallows the rollback error to propagate the original) but not the second; it is not in scope here. This file is a hotspot: an ops-resilience issue and an agent-runtime issue both build on this fix, so the Touches list is exactly this file and its unit test.

## Task

1. `withTransaction`: track the client's health in a local `let releaseError: Error | undefined`. In the failure path, wrap the rollback: `try { await client.query("ROLLBACK"); } catch (rollbackErr) { releaseError = rollbackErr instanceof Error ? rollbackErr : new Error(String(rollbackErr)); console.error("withTransaction: ROLLBACK failed; discarding the connection", rollbackErr); }` and always `throw err` (the original). In `finally`, call `client.release(releaseError)` — `pg` destroys the client when the argument is truthy and pools it otherwise. Keep the change to the rollback failure only: a `COMMIT` failure already flows into the same `catch`, so its `ROLLBACK` attempt decides whether the connection is kept. Document the two guarantees in the function's doc comment (line 28): the original error is what propagates, and a connection whose rollback failed never goes back into the pool.
2. Tests in `backend/packages/data/src/__tests__/pool.unit.test.ts` (unit, fake client — same `fakePool` pattern as the existing `withClient` block): (a) `fn` throws `E1`, the fake's `query("ROLLBACK")` rejects with `E2` → the returned promise rejects with `E1` and `release` was called once with `E2`; (b) `fn` throws `E1`, rollback resolves → rejects with `E1` and `release` was called once with no argument; (c) `fn` resolves → `release()` with no argument and the after-commit callbacks ran; (d) `COMMIT` rejects and `ROLLBACK` rejects → rejects with the commit error, `release` called with the rollback error.

## Scope

### In scope
- Preserving the original error across a failed `ROLLBACK` and discarding the connection in that case, plus unit tests.

### Out of scope
- `createPoolClientTransactionRunner` (`projectAgentGuidanceStore.ts`) and `withClient`.
- Retry/backoff on connection loss, pool sizing, statement timeouts (ops-resilience epic, which depends on this issue).
- Any change to `runAfterCommit` semantics.

## Acceptance criteria

- When `fn` throws and the subsequent `ROLLBACK` fails, the caller receives `fn`'s error, not the rollback error, and the client is released with the rollback error so the pool discards it.
- When `ROLLBACK` succeeds, the client is released healthy and the caller receives `fn`'s error, exactly as today.
- When the transaction commits, behaviour is unchanged (callbacks run after `COMMIT`, client released healthy).
