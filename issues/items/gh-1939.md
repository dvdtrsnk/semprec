**Model tier:** high

## Context

Model tier rationale: Introduces a new producer of Inbox cards, a schema change on Processing proposals and a change to the tick's card selection, so ownership, tenant data migration and lifecycle consistency all matter.

When the user writes "split this into several items" in an Inbox item's thread, one capture such as a shopping note and a deadline should become several proposal cards. #1380 records the decision this issue implements: a user-context Inbox-module action creates the sibling cards; the first card remains the source's primary card and the only one the tick recomputes; siblings carry `splitFromProposalId` and are ignored by the tick. The agent tool infrastructure (#1906) provides registration of Inbox agent tools, and multi-step envelopes (#1378) define how a card with several steps is stored; a split produces several cards, each with its own (possibly multi-step) envelope.

Decision: the tool is `inbox.proposal.split` with arguments `{ proposalId, cards: [{ entityKind, target, properties }, ...], message? }` (at least two and at most the maximum fixed by the ADR). The first entry revises the primary card (as a thread revision, with the rules of the revision flow), the others become new sibling cards with `kind: "inbox"`, `status: "proposed"`, `aiProposal` equal to their envelope, `aiVersion` 1, a `sourceInbox` edge to the same source and `splitFromProposalId`. History entries have `author: "ai"`, `kind: "threadRevision"` and the thread and message ids from the run context.

Decision: the action runs in one transaction with the primary card row-locked; a locked primary card, a card not belonging to the thread's item or an invalid envelope in any entry fails the whole split and writes nothing. Sibling cards are never recomputed by source edits.

Shared-file ordering: this issue also waits for #1929, #1937 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Scope

### In scope

- The split action, the `inbox.proposal.split` tool, the sibling marker and the tick ignoring siblings.

### Out of scope

- The decision record (#1380) and thread context and revision rules (#1938).
- Recomputing a sibling from source edits (never) or on demand (the recompute route works per card).
- Merging cards back or moving a step between cards.

## Acceptance criteria

- When the thread asks to split a source into two, then two cards exist for the source: the primary revised and a sibling with `splitFromProposalId` equal to the primary's id; nothing is created in any target database.
- When the source text is edited afterwards, then the tick recomputes only the primary card.
- When the primary card is `confirmed`, then the split fails and no card is created or changed.
- When any entry fails validation, then no card is created and the primary is unchanged.
- When a sibling is confirmed, then the primary and other siblings are unaffected.
- When a tenant is migrated, then existing Processing proposals databases have the new property.
