## Context

Once B1 makes failed login attempts persist, the address they are keyed on becomes load-bearing — and it is wrong. `backend/services/semprec-api/src/authHandler.ts`, `POST /api/auth/login` branch, passes `ip: req.socket.remoteAddress ?? "0.0.0.0"` (currently line 163) to `login`. `backend/services/semprec-api/src/serve.ts` binds the listener to `127.0.0.1` (line 126, "bound to loopback explicitly") and `deploy/Caddyfile` fronts it with `reverse_proxy 127.0.0.1:8080` (line 40). Nothing in the service reads `X-Forwarded-For`, so every request from every client arrives with `remoteAddress === "127.0.0.1"`.

Consequence: `getFailureStreak(client, email, ip)` (`backend/packages/data/src/auth/loginAttemptsStore.ts`) scopes the streak per `(email, ip)`, and with one shared ip value it degenerates to per-email. Anyone who sends `LOCKOUT_THRESHOLD` (5) wrong passwords for the owner's email locks the owner out from everywhere for up to `LOCKOUT_MAX_SECONDS` (3600 s, `backend/packages/data/src/auth/loginLockout.ts`), and can keep doing so.

Depends on #628 (same handler branch; that issue changes the `login(...)` call this one adds the `ip:` argument to). Sibling B7 later edits a different branch of the same handler.

## Task

- Create `backend/services/semprec-api/src/clientIp.ts` exporting `clientIpFromRequest(req: IncomingMessage, options: { trustProxy: boolean }): string`:
  - When `options.trustProxy` is `true` and `req.headers["x-forwarded-for"]` is a non-empty string, return the **last** comma-separated entry, trimmed. Caddy's `reverse_proxy` appends the peer address it saw to any incoming `X-Forwarded-For`, so the last entry is the one hop the proxy vouches for; earlier entries are client-controlled and must not be used.
  - Otherwise (flag off, header absent, or the last entry is empty after trimming) return `req.socket.remoteAddress ?? "0.0.0.0"` — the exact expression the handler uses today.
  - No IP parsing or normalisation beyond trimming; the value is an opaque throttle key.
- Wire the flag through the existing composition root, not `process.env` in the handler:
  - `AuthRequestListenerOptions` in `authHandler.ts` gains `trustProxy?: boolean` (default `false`), and the login branch passes `ip: clientIpFromRequest(req, { trustProxy: options.trustProxy ?? false })`. Add a short comment at that line recording the throttle-key rule below.
  - `AppOptions` in `backend/services/semprec-api/src/app.ts` gains `trustProxy?: boolean`, forwarded to `createAuthRequestListener`.
  - `backend/services/semprec-api/src/serve.ts` reads `const trustProxy = process.env.TRUST_PROXY === "1";` next to the other env checks and passes it to `createDispatcher`. Any other value, including unset, means `false`.
  - `deploy/shared/.env.example`: append a `# ---- Reverse proxy ----` section explaining that semprec-api sits behind Caddy on the same host (`deploy/Caddyfile`), that `TRUST_PROXY=1` makes it read the last `X-Forwarded-For` hop as the client address for login throttling, and that it must be `1` in every deployment provisioned from `deploy/`; then the line `TRUST_PROXY=1`. Every existing test that calls `createDispatcher` or `createAuthRequestListener` keeps working because the option is optional.
- Throttle-key rule (decided here, record it in the comment at the `ip:` line): the streak stays scoped per `(email, ip)` exactly as `getFailureStreak` implements it today, and **no** per-email aggregate lock is added. A per-email lock would recreate the owner-lockout this issue removes (an attacker from any address could trigger it); per-address scoping means an attacker only ever locks their own address, while Argon2id verification keeps distributed guessing expensive. No data-layer change.
- The helper is used by the login branch only. `POST /api/auth/password-reset/request` and `POST /api/setup` do not consume a client address today; giving them address-keyed throttling is a new mechanism and is out of scope.
- Tests:
  - New `backend/services/semprec-api/src/__tests__/clientIp.unit.test.ts` (unit tier, no Postgres; build a minimal `{ headers, socket: { remoteAddress } }` object cast to `IncomingMessage`): flag off ignores the header; flag on with `"203.0.113.9, 198.51.100.4"` returns `"198.51.100.4"`; flag on with the header absent returns the socket address; flag on with `" 198.51.100.4 "` returns the trimmed value; missing socket address returns `"0.0.0.0"`.
  - `backend/services/semprec-api/src/__tests__/authHandler.test.ts`, inside `describe("POST /api/auth/login")`: construct the listener with `trustProxy: true` in the file's `beforeEach` (existing cases send no forwarded header, so their behaviour is unchanged), then: `LOCKOUT_THRESHOLD` wrong passwords with `X-Forwarded-For: 203.0.113.9`, followed by the correct password with `X-Forwarded-For: 198.51.100.4` → 200, and the correct password with `X-Forwarded-For: 203.0.113.9` → 401.

## Scope

### In scope

- The `clientIpFromRequest` helper, its `TRUST_PROXY` wiring, and its use as the login throttle key.
- Documenting the per-`(email, ip)` rule.

### Out of scope

- Persisting failed attempts at all — #628 (this issue depends on it).
- Address-keyed throttling for password-reset requests or `POST /api/setup` (setup-token brute-force limiting is deliberately outside this batch).
- Any change to `deploy/Caddyfile`, `deploy/deploy.sh` or the systemd units; Caddy already forwards the header.
- Validating the `:id` of `POST /api/auth/sessions/:id/revoke` — sibling B7; the handler's error body — sibling B8.

## Acceptance criteria

- With `trustProxy: true`, when a client sends `LOCKOUT_THRESHOLD` wrong passwords for an email with `X-Forwarded-For: 203.0.113.9`, a correct-password request with `X-Forwarded-For: 198.51.100.4` is answered 200 and one with `X-Forwarded-For: 203.0.113.9` is answered 401.
- With `trustProxy: false` (the default), the `X-Forwarded-For` header has no effect and the socket address is used, so every existing `authHandler.test.ts` and `routeMatrix.test.ts` case passes unchanged.
- `clientIpFromRequest` returns the last forwarded hop, trimmed, and never an earlier entry.
- `deploy/shared/.env.example` documents `TRUST_PROXY=1`; `serve.ts` treats any value other than the string `1` as `false`.
