## Context

Model tier rationale: A multi-database copy that must create an item and its relation edges atomically and idempotently under a client-supplied key, with a whitelist that excludes invitation, recording and recurrence state, so a wrong field list silently duplicates or leaks data.

The catalog of generic operations has no duplicate (`backend/packages/shared/src/genericOperations/operationNames.ts`), and the only precedent for copying an item's edges inside a transaction is `copyRelationEdges` in `backend/packages/data/src/tasks/advanceTaskRecurrenceWithClient.ts`. The calendar needs one operation that copies an Event or a Task to a new date and time: the user duplicates the selected calendar item, or pastes a copied one.

This issue adds `POST /api/calendar/items/:id/duplicate`. Routes over Events and Tasks belong to the systemDatabases module (program rule), so it is declared in `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` with justification `transactional-semantics` (item and edges commit together, with an idempotency key). `/api/tasks/:id/duplicate` is not built; this is the only route.

Request body: `{ date, timeFrom?, timeTo?, endDate? }` with an optional `Idempotency-Key` header. The new item is written through the choke point, so the Events validation of #1663 and the Tasks validation of #1536 apply to the new date and times. A repeated request with the same key returns the item created the first time and copies nothing again.

Whitelist (copied) for an Event: `name`, `type`, `place`, `url`, `description`, `alertMinutes`, `travelMinutes`, and the edges `project`, `people`, `calendar`, `area`, `files`, plus `company` for an Event that has no project. For a Task: `name`, `timeFrom`, `timeTo`, `flagged`, `description`, `notifications`, `status` set to `notDone`, and the edges `project`, `people`, `files`; a recurring Task gets the same recurrence rule and starts a new series from the copy's date (through the series-identity function of #1605). Edges whose relation property does not exist on the database yet (for example `area`, `files` or `company` before their own issues land) are skipped, not an error.

Not copied: recordings (the transcript edge), action items, hosted tasks and hosting events, invitations and RSVP (the `invitation` part of every participant edge is dropped), `completedOn`, `completedAt`, `completedInEvent`, `since`, `sinceTime`, `seriesId`, `occurrenceDate`, `createdAt`, the item's page, and derived values (`time`, and area or company reached through a project).

Decision: the new date and times come from the body; a copy of an all-day item has no `timeFrom` and keeps the source's length: when the source has an `endDate` and the body has none, `endDate` is shifted by the same number of days as `date`.

Decision: a copied Task that was done is `notDone`.

Shared-file ordering: this issue also waits for #1793 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Scope

### In scope

- The duplicate route for Events and Tasks, the whitelists, atomic edge copy and idempotency.

### Out of scope

- Moving an item (cut and paste): it is a normal update of date and times.
- The delete-impact preview and the effects of deleting an Event on its tasks and inherited values: #1856.
- Creating an Event with its relations in one write: #1777.
- Copying inherited values as inherited: not planned; copied values become the copy's own.

## Acceptance criteria

- When an Event is duplicated to a new date and time, then the copy has the whitelisted properties and edges, a new id, and none of the excluded ones.
- When the same `Idempotency-Key` is sent twice, then only one copy exists.
- When the new times are invalid (for example `timeTo` `24:15`), then the response is 400 and nothing is created.
- When a done Task is duplicated, then the copy is `notDone` without completion data and keeps people and files.
- When an Event with invited people is duplicated, then the copy's people are only linked, with no invitation.
- When the source belongs to another tenant, then the response is 404.
