**Blocked by:** #21

## Context

Semprec is a single-user, self-hosted system where structured data (tasks, people, projects, emails, ...) is stored as rows with properties through a generic schema engine (issue #21). That layer handles well-queryable, typed fields — but it does not handle free-form, fine-grained content: page text broken into paragraphs/headings/lists/nested databases, or a canvas/whiteboard with drawn and embedded elements.

Free-form content needs fine-grained merging of concurrent changes — two devices editing the same page offline, an AI agent writing a note into a page while the user is looking at it, a canvas that both an agent and the user draw into at the same time. Last-write-wins at the whole-row level (how the structured `items.properties` layer works today) would simply discard one side of the change under concurrency. The answer is a CRDT (Conflict-free Replicated Data Type) — specifically the `yjs` library (MIT license, pure JS/TS, no extra framework).

This is the one place in the entire data layer where something genuinely **new** is being built alongside structured data, not an extension of what issue #21 already put in place. The chosen approach is a custom implementation inspired by the architecture of BlockSuite (the editor engine behind AFFiNE, MIT licensed) — **not adopted code**. The AFFiNE server (`packages/backend/server`) is Enterprise Edition requiring a paid subscription and is unusable license-wise; only the architectural pattern is adopted (a block as a `Y.Map` with a `sys:children` array, canvas as a flat map of typed elements), rewritten from scratch. The `yjs` library itself remains a direct dependency.

## Task

Build the CRDT layer for page content (blocks) and canvas/whiteboard on top of `yjs`, including Postgres persistence, compaction, version history, and wiring into the realtime transport. The goal is a functional, production-usable foundation on top of which a concrete editor UI and the concrete databases from the schema engine will later run (outside this task).

### 1. Why two storage mechanisms — a deliberate choice, not a compromise

The system will permanently have two parallel persistence-and-merge mechanisms side by side:

- structured data (rows/properties from issue #21) — cell-level last-write-wins in relational Postgres, with live client-to-client propagation handled by the realtime layer (out of scope here, see the realtime section below).
- free-form page content and canvas — binary CRDT documents in separate tables.

This is not an architectural compromise or something left unfinished — it is exactly the pattern AFFiNE itself uses: relational Postgres for structured data plus separate binary snapshot/update tables for CRDT documents. Structured data doesn't need CRDT (concurrent conflicts at single-cell granularity are rare and last-write-wins is sufficient for them); free-form content does need it, because concurrent edits genuinely happen there (two fingers on two devices, an agent drawing into the canvas while the user is watching).

Implement both stores as separate, independent mechanisms — there is no attempt to unify them into a single consistency model.

### 2. Data model — tables

```sql
CREATE TABLE docs (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  item_id uuid REFERENCES items(id) ON DELETE CASCADE,
  kind text NOT NULL DEFAULT 'page'      -- 'page' (block tree) | 'canvas' (surface elements)
);

CREATE TABLE doc_snapshots (
  doc_id uuid PRIMARY KEY REFERENCES docs(id) ON DELETE CASCADE,
  state bytea NOT NULL,          -- merged binary Yjs update
  state_vector bytea NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE doc_updates (        -- append-only log, periodically compacted into the snapshot
  id bigserial PRIMARY KEY,
  doc_id uuid NOT NULL REFERENCES docs(id) ON DELETE CASCADE,
  update bytea NOT NULL,
  created_by text NOT NULL DEFAULT 'user',  -- 'user' | 'ai_agent' | 'system' — from the Yjs transact() origin
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE doc_snapshot_history (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  doc_id uuid NOT NULL REFERENCES docs(id) ON DELETE CASCADE,
  state bytea NOT NULL,
  taken_at timestamptz NOT NULL DEFAULT now(),
  expires_at timestamptz NOT NULL,      -- retention window (e.g. 30 days), cleanup job deletes after expiry
  created_by text NOT NULL              -- 'user' | 'ai_agent' | 'system' — who/what triggered the squash
);
```

`items` is the table from the schema engine (issue #21) — `docs.item_id` is a foreign key into an existing row, not a new entity independent of the schema engine. `docs` has a 1:1 or 0:1 relationship to `items` — an item may or may not have a doc.

### 3. A doc is created lazily, only when a page actually gets content

A row in `docs` is **not** created automatically for every item in the system (every task, every person, every email). It is created the first time the page's content is actually initialized — the user writes the first block, or the AI writes a note. Most rows in the structured databases (tasks, people, emails) never get free-form content at all, only structured properties from issue #21 — forcing every item to carry an empty CRDT document from the start would be pure operational cost with no purpose (write amplification on item creation, useless empty rows in `doc_snapshots`).

Implementation: creation of a `docs` row (and the accompanying `doc_snapshots` row holding an empty Yjs document) is triggered explicitly by the first content-write operation against that item (the first `PUT`/mutation of a block or canvas element), not by a migration or a trigger on `items` row creation. The same database (e.g. Projects) can therefore have items with and without content side by side — that is the expected, normal state, not an edge case.

### 4. A block is a `Y.Map`, a canvas is typed elements — exactly why the AI can work with it

A **block** (`kind = 'page'`) carries:
- `sys:id` — the block's identifier
- `sys:flavour` — the block type (paragraph, heading, list, nested database, ...)
- `sys:children` — an array of child IDs

The page tree is therefore a flat map of blocks plus ID lists, not nested objects — each block is its own `Y.Map` inside the shared Yjs document, and hierarchy arises from ID references, not from nesting the data structure.

A **canvas element** (`kind = 'canvas'`) carries, as structured, typed data:
- a type (shape / connector / text / drawing)
- `xywh` — position and size
- `index` — fractional indexing for z-order (ordering overlaps without renumbering the whole layer when inserting between two existing elements)

A canvas element is **not a pixel bitmap** — it is a structured representation exactly like a database row. That is the only way the requirement "AI fully understands canvas content and can redraw it" actually works — the agent reads and writes elements through a generic API exactly as it would edit a database row, not through image analysis/OCR.

Technically this does not run through a SQL/JSONB query (a block/canvas element lives inside a binary Yjs update, not in a queryable column), yet it is still a fully programmatic, not image-based, approach:

1. the agent service loads `doc_snapshots` plus the following `doc_updates` for the given `doc_id`
2. it replays them into a headless `Y.Doc` — the plain `yjs` package, no browser/DOM (the same pattern used unmodified by the production `y-websocket-server` in Node.js)
3. it reads/writes the specific nested shared type, e.g. `doc.getMap('elements').get(id)`, exactly as the editor would
4. the mutation goes through `doc.transact(fn, 'ai_agent')` — the Yjs `origin` parameter of the transaction is propagated into both `doc_updates.created_by` and `doc_snapshot_history.created_by`, so attribution of "who wrote this specific update" exists at the level of the individual write, not just at the checkpoint level
5. the resulting binary change is written back as a new `doc_updates` row

One required server-side configuration: **`doc.gc = false`** on the server-side headless `Y.Doc` instance — with default garbage collection, Yjs permanently discards deleted content, which would break exactly what `doc_snapshot_history` exists for (browsing older versions must be able to reconstruct deleted content too).

### 5. Compacting `doc_updates`

Without compaction, `doc_updates` grows unbounded — an append-only log of every single mutation. The `yjs` library itself does not handle compaction; it is a pattern each persistence adapter builds on its own, and it is remarkably consistent across reference adapters: `y-leveldb` defines `PREFERRED_TRIM_SIZE = 500` and triggers a flush when reading a document once the stored update count crosses that threshold; `y-postgresql` does the same with a default threshold of 200.

Implement the same shape:
- threshold of **~200-500 updates per `doc_id`**
- threshold checked **lazily on read** of the document, plus a **periodic sweep** that catches up documents that are rarely opened (so the log doesn't grow indefinitely just because nobody has read that doc in a while)
- the merge runs in **a single Postgres transaction**:
  1. read `doc_snapshots` plus the pending `doc_updates` for the given `doc_id`
  2. replay into a headless `Y.Doc` (`Y.applyUpdate`)
  3. write the new `state`/`state_vector` (`Y.encodeStateAsUpdate` / `Y.encodeStateVector`)
  4. delete the merged rows from `doc_updates`
- the step order is mandatory: **store-then-delete, never the reverse** — the new snapshot must be safely written first, only then may the source updates be deleted
- thanks to the commutativity and idempotence of CRDT merging, an update arriving just before/after the flush converges to the same resulting state without special locking — the Postgres ACID transaction gives a stronger guarantee here than pure JS-only adapters have (they only handle concurrency via an in-process promise queue)

### 6. Version history — periodic checkpoints with expiry

`doc_snapshots`/`doc_updates` only answer "what is the current state". Without a third table, "open the page/canvas as it looked a week ago" is only theoretically reconstructible by replaying the entire `doc_updates` log from the start — not a usable mechanism for a log that grows over time. AFFiNE solves this the same way (confirmed directly in their production schema): a separate table of periodic full checkpoints, independent of the ongoing update log — that is `doc_snapshot_history` above.

Implementation rules:
- written by a **periodic squash job**, not synchronously with every edit (ongoing changes are handled by `doc_updates`)
- retention is a **time window managed by a cleanup job** (e.g. 30 days), not a metered tier — this is only the mechanism itself, not a business layer built on top of it
- "open an old version" reads the **nearest checkpoint before the requested time** and, if needed, computes the remainder from `doc_updates` between the checkpoint and now — it never replays the full log from document creation

### 7. Web natively, iOS/macOS through a shared WebView editor — not native Swift CRDT

Decision: the surface editor (page content, canvas) on iOS/macOS runs inside a **WKWebView**, using the same JS/TS code as the web. One implementation of the CRDT logic across platforms, not two to keep in sync. The rest of the native app (navigation, tables, board views, notifications) stays purely native Swift/SwiftUI over the generic REST/query API from the schema engine (issue #21) — that doesn't need CRDT at all, it only concerns structured data.

Reasons the native alternative was rejected:
- **`yswift` (formerly `y-uniffi`)**, the official Swift binding to Yjs, is effectively abandoned — over 2 years without a commit, no maintainer, confirmed directly by the `yrs` core author. The risk is operational, not technical: hit a bug in the Rust layer, and the fix is on you, upstream won't help.
- **Automerge** has an actively maintained `automerge-swift` binding, but it is not wire-compatible with Yjs — switching would mean two different CRDT formats and the need to bridge them on the server, not a simpler solution.
- AFFiNE itself, with a much bigger budget and a working UniFFI Rust→Swift pipeline (which it uses for storage), deliberately chose **not** to do CRDT merging natively — on both iOS and Android it runs the same JS `yjs` code as the web, via Capacitor/WebView.

A future reconsideration, not today's decision: if `yswift` or another native binding matures, moving to a fully native editor is a later step, outside the scope of this task.

Realtime presence (who is currently in the document, live cursors) is **deliberately not being built yet** — it's the standard, cheap Yjs Awareness protocol (ephemeral state over the same WS channel, never persisted), but for a system with 1-2 users the payoff is essentially zero. Not forgotten, just deferred: when needed, it rides the existing WS fan-out as another message type, not a new mechanism (see point 8).

### 8. Realtime transport — an extension of the existing system, not a new one

Binary Yjs update frames travel over the **same channel** as row-level changes to structured data: the custom WS server over Postgres LISTEN/NOTIFY. An insert into `doc_updates` triggers fan-out exactly the same way an insert/update into `items` triggers fan-out today. Do not implement a separate WS server or a parallel realtime mechanism for CRDT frames — it is one realtime system serving both data kinds (structured and CRDT), distinguished only by message type on the same fan-out channel.

If the realtime WS layer over Postgres LISTEN/NOTIFY from issue #21 (or a related issue) does not yet exist in a usable form, this task must extend it with a new message type for CRDT update frames — not rebuild it from scratch.

## Scope

### In scope

- The `docs`, `doc_snapshots`, `doc_updates`, `doc_snapshot_history` tables (schema exactly as in point 2), including migration.
- Backend logic for lazily creating a `docs` row on the first content mutation of a given item (point 3).
- Server-side headless `Y.Doc` handling: loading the snapshot plus following updates, applying updates, writing new update rows, with `doc.gc = false`.
- API for reading/writing blocks (page doc) and canvas elements (canvas doc) through generic operations over the shared Yjs types (`Y.Map` for blocks, a flat map of typed elements for canvas) — sufficient for both a future editor UI and agent writes to operate on top of it.
- Write attribution (`created_by`: `user` / `ai_agent` / `system`) propagated from the Yjs `origin` parameter into both `doc_updates` and `doc_snapshot_history`.
- Compaction job/logic per point 5 (lazy trigger on read plus periodic sweep, threshold 200-500, single Postgres transaction, store-then-delete).
- Periodic squash job for `doc_snapshot_history` (point 6), plus a cleanup job deleting expired records, plus an API/function for "open an old version" (nearest checkpoint plus remainder computed from `doc_updates`).
- Extending the existing WS/LISTEN-NOTIFY fan-out with a new message type carrying a binary CRDT update frame (point 8) — wired to inserts into `doc_updates`.
- Choosing and integrating `yjs` as a direct dependency (server and client), without the rest of the BlockSuite/Lit stack.

### Out of scope

- **A concrete editor UI** (rich text editor components, canvas rendering/drawing tools, drag & drop) — this task builds the data and synchronization layer, not the user interface on top of it.
- **The ten hardcoded databases** (issue #24) — concrete instances over the schema engine that will, among other things, use this CRDT layer for their free-form content. Handled separately, in a follow-up issue.
- **Realtime presence / the Awareness protocol** (cursors, who is in the document) — deliberately deferred, see point 7, not part of this task.
- **WKWebView integration on the iOS/macOS native app side** — the architectural decision (shared web editor) is part of this task's scope, but the native Swift/SwiftUI app itself and wrapping the WKWebView component is separate (later) work outside this backend-focused task.
- Migrating to a different CRDT engine (Automerge, etc.) — explicitly rejected, see point 7.
- A native Swift CRDT binding (`yswift`) — explicitly rejected, see point 7.

## Dependencies

- **Issue #21 (schema engine)** — hard dependency. `docs.item_id` is a foreign key into an `items` row from the schema engine; lazy doc creation (point 3) is tied to the existence of an item in that layer. Without a working schema engine, the `docs` table has nothing to reference.
- **Realtime WS transport over Postgres LISTEN/NOTIFY** (whether part of issue #21 or a separate issue handling realtime for structured data) — a soft/extending dependency: this task extends that layer with a new message type (point 8), it does not build it from scratch. If it does not yet exist in usable form when this issue is worked on, implement a minimal fan-out mechanism over LISTEN/NOTIFY as part of this task and mark it as shared infrastructure for a future extension to structured data.

## Reference to the specification

Source specification: `vize/backend.html`, lines 1503-1715.

The source specification draws on the following external references, worth knowing for implementation:

- **BlockSuite** — the editor engine behind AFFiNE, MIT licensed. Source of the architectural pattern (block as `Y.Map` with `sys:children`, canvas as a flat map of typed elements) — only the shape is adopted, not the code.
- **AFFiNE** (`packages/backend/server`) — Enterprise Edition, unusable as a whole due to licensing (paid subscription required for production deployment beyond a small free tier). Source of the two-store pattern (Postgres + binary CRDT tables) and of the `doc_snapshot_history` pattern (periodic checkpoints with retention).
- **`yjs`** — the CRDT library itself, MIT, a direct dependency. `Y.applyUpdate`, `Y.encodeStateAsUpdate`, `Y.encodeStateVector`, `doc.transact(fn, origin)`, `doc.gc` are the concrete APIs the implementation works with.
- **`y-leveldb`** — reference persistence adapter, source of the `PREFERRED_TRIM_SIZE = 500` compaction pattern.
- **`y-postgresql`** — reference persistence adapter over Postgres, default compaction threshold of 200 updates.
- **`y-websocket-server`** — reference pattern for a headless `Y.Doc` running in Node.js without a browser/DOM, the same pattern the agent service uses to read/write docs on the server.
- **`yswift` / `y-uniffi`** — the official, but effectively abandoned, Swift binding to Yjs (2+ years without a commit, confirmed by the `yrs` author). Rejected as a basis for a native editor, see point 7.
- **Automerge / `automerge-swift`** — an alternative CRDT engine with an actively maintained Swift binding, but a wire format incompatible with Yjs. Considered and rejected, see point 7.
- **Anytype** — independently arrived at the same conclusion as point 3 (lazy creation of free-form content): their "layout" type concept determines whether a type carries a free body at all. In Semprec the equivalent rule is instance-per-item (lazy `docs` row creation), not type-per-schema, because the same database can have items with and without content side by side.
