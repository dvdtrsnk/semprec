## Behavior specification

Semp replies: run steps, changed objects, failures and retry.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions for job semp-replies-1

#### (a) Decisions adopted from open questions

- When is model generation its own step? -> Decided by the product owner: only an intermediate assistant message with text (followed by more tool calls or a later assistant message in the turn) is a `model` step; the final answer is never a step -> deterministic from events, matches "summary after loading the transcript is a step, the answer after '3 steps' is not".
- What may a step show of inputs and results? -> Decided by the product owner: only counts, durations, timestamps, target names and structured field `before -> after` from structured tool results; never free text from arguments/results; nothing (no `detail.params` and no `before -> after`) for items in sensitive databases -> steps and changes are stored permanently on the message, outside event retention, so redaction is applied when writing and protects privacy permanently.
- Previous values: adopted a read inside the write transaction returned additively as `previous` of `item.patch` (#1429); the REST PATCH body is unchanged (field stripped) -> keeps the public REST contract and the catalog of 29 operations.
- Pending delete -> Decided by the product owner: not a change, only a `wait` step; an approval executed later is not added to the reply's changes, because a reply is a closed record.
- Should changed-item cards open the object? -> Decided by the product owner: yes, a changed-item card opens the object. Each card in message history carries the item id and database id of the changed item (an additive contract change, #1888), and the design is updated to make the cards tappable.
- Retry/regenerate -> Decided by the product owner: retry allowed on the latest message when it is `error` or a `done` reply with an incomplete reason; regeneration replaces (no versions), only for the latest `done` reply, refused for turns with writes (409 `regenerate_after_writes`) or after compaction; older answers are not regenerated (no branching) -> writes must never be executed twice.
- Both retry and regenerate re-send the original user message as a new user turn -> Decided by the product owner: the duplicate user turn in the model history is accepted; it is the simplest solution and breaks nothing.
- Failed-reply problem -> Decided by the product owner: one problem per reply, dedupe key `agents:reply:<reply_to_message_id>`, raised/resolved in the result transaction; a cancelled turn raises no problem.
- No raw exception text is stored or logged for message failures (decided by the product owner, for privacy and to keep the Inbox uncluttered); texts are rendered at read time from an i18n catalog by code and params.

#### (b) Open questions remaining for the product owner

- Which link should the existing `agent_run_error` notification of a failed chat turn use (agent run page vs chat/status view)?
- Retry owns the `attempt` column and index (#1926); regeneration (#1930) explicitly depends on it. Failed-reply problems have one producer owner, #1931; no duplicate issue is to be removed. Preserve ordering of the shared message stores and route registrations.

#### (c) User-visible behavior of this chunk

Under each Semp reply in chat the user sees a summary of what Semp did (number of steps, total time, whether it waits for approval, failed, or succeeded on a second try) and can expand the steps with short details such as the old and new value of a changed field; this stays available after 30 days. Cards under the reply show the items it created or changed with their current state, loaded together with the history; tapping a card opens the object. When a reply fails, the user gets a plain-language reason (budget, model error, timeout of a connected service), a "Try again" action that replaces the failed card with a new attempt, and a matching entry in the Semp status view that resolves itself once a retry succeeds. The user can also regenerate the latest answer if it made no changes.
