## Context

Model tier rationale: Three additive properties on a schema-locked database delivered through the established seed, cutover and i18n path, plus the capture route change that fills them; the pattern exists and the verification fixtures are in place.

An Inbox item records where and when the user wrote it (`date`, `time`) but not how it was captured, from which app it was shared, or when the server received it. The cards and the Journal list need three facts: a voice note versus typed text versus a share, the name of the app a share came from (for example a mail client or a dictation app), and the server time at which the item was accepted, which differs from the `date`/`time` the user captured it at (offline capture can arrive hours later). The Inbox database (`backend/packages/data/src/seed/seedInboxPipeline.ts`, module id `inbox`) is `schema_locked`, so a new property reaches existing tenants through a per-tenant cutover in `backend/packages/data/src/db/tenantCutoverMigrations.ts` (pattern: `runTranscriptsCatalogCutoverMigration`; `docs/adr/2026-09-10-app-code-post-migration-steps.md`). Labels of the Inbox properties live in `backend/packages/data/src/inbox/i18n/en.json` and `cs.json`.

The capture route #1961 is where the values enter; this issue extends it. The card-state properties of Processing proposals are a separate cutover (#1451), and the properties written by attachment recognition belong to later issues. Items that already exist keep these properties empty. Both this issue and the type-target options (#1973) edit the Inbox seed and its cutover registration, so the type-target change is ordered after this one.

Decision: `captureChannel` is a user-owned `select` with the options `typed`, `voice`, `share`; `sourceApp` is a user-owned `text` (the displayed app name, at most 80 characters, trimmed); `addedAt` is a system-owned `date` with `includeTime`, `ownerProcess` the Inbox module id, set by the server at accept time as an ISO timestamp.

Decision: the capture route requires `captureChannel` and accepts an optional `sourceApp`; a missing or unknown channel is 400 `validation_failed` with `field` `captureChannel`. The generic item create does not require them and leaves `addedAt` empty, because `addedAt` is written only by the capture helper.

Decision (product owner): the `voice` value only records how the item was captured. In v1 a voice note is dictated on the device and arrives as text; server-side audio for voice notes comes later with recordings. Separate capture screens are not modeled.

Shared-file ordering: this issue also waits for #1962 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. In `seedInboxPipeline.ts` add the three properties to the Inbox property list (extend `PropSpec` and `createProps` with `ownerProcess`, as `seedTenDatabases.ts` does).
2. Add names and option labels to `inbox/i18n/en.json` and `cs.json` (`property.inbox.captureChannel.name`, `...option.typed|voice|share`, `property.inbox.sourceApp.name`, `property.inbox.addedAt.name`).
3. Add a per-tenant cutover in a new file `backend/packages/data/src/inbox/inboxCapturePropertiesCutoverMigration.ts`, following the lock, idempotency-check and raw-SQL insert shape of `transcriptsCatalogCutoverMigration.ts`: it adds each missing property with the same owner and owner process as the seed and does nothing when the Inbox database does not exist yet. Register it in `runTenantCutoverMigrations`.
4. Extend `CreateInboxItemInput` and `createInboxItemWithClient` with `captureChannel`, `sourceApp` and the server clock for `addedAt`, writing `addedAt` through `allowedSystemKeys: ["addedAt"]` with `systemOwnerProcess` set to the Inbox module id.
5. Extend the capture handler of #1961 with the body fields and validation of the Decision.
6. Tests: a populated tenant gains the three properties and a second cutover run changes nothing; a fresh seed has the same shape; a capture stores the channel, the source app and an `addedAt` close to the server time that is independent of the sent `date`/`time`; a capture without a channel or with `captureChannel: "email"` is 400; `sourceApp` over 80 characters is 400; a user cannot write `addedAt` through the generic item PATCH; the i18n coverage test passes.

## Scope

### In scope

- The three properties on fresh and populated tenants and their capture-route write path.

### Out of scope

- The capture route itself and the create hook (#1961, #1432).
- The source of an attachment (camera, scan, library, files, share) and recognition text: they belong to the attachment records.
- Displaying the channel and source in the Journal list.
- Server-side audio for voice notes (it comes with recordings, not in v1).
- Backfilling `addedAt` for existing items.

## Acceptance criteria

- After the cutover a populated tenant's Inbox database has `captureChannel`, `sourceApp` and `addedAt`, and a second run changes nothing.
- When an item is captured with channel `share` and source app `Mail`, then both are stored, and `addedAt` is the server's receive time, not the sent `date`/`time`.
- When the channel is missing or not one of the three options, then the capture is 400 with `field` `captureChannel`.
- A user cannot set `addedAt` through the generic item update.
