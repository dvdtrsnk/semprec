## Context
Review of pull request #419 found that in `backend/packages/data/src/observability/systemHealthReport.ts` (currently around line 118), the `permanent` column is computed as `count(*) FILTER (WHERE attempts >= max_attempts) AS permanent`, with no `locked_at IS NULL` guard — unlike the `pending` (line 116) and `overdue` (line 117) columns, which both filter on `locked_at IS NULL`. As a result, a job currently locked for its final attempt (`locked_at` not null, `attempts = max_attempts`) is counted as permanently failed even though it has not yet actually failed.

## Task
- In `backend/packages/data/src/observability/systemHealthReport.ts`, add a `locked_at IS NULL` guard to the `permanent` column's `FILTER` clause, matching the guard already used by the `pending` and `overdue` columns.

## Touches
- backend/packages/data/src/observability/systemHealthReport.ts (the `permanent` column's SQL `FILTER` clause only)
- backend/packages/data/src/__tests__/systemHealthReport.test.ts (new test coverage for the locked final-attempt job, next to the existing "counts pending, overdue, and permanently-failed queue jobs separately" test)

## Scope
### In scope
- The `permanent` column's filter condition.

### Out of scope
- The `pending` and `overdue` columns, or any other column in the same query.

## Acceptance criteria
- A job with `locked_at` not null and `attempts = max_attempts` is not counted in `permanent`.
- A job with `locked_at` null and `attempts >= max_attempts` is still counted in `permanent`.
