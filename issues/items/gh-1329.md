## Behavior specification

Calendar events: time model, conversion, details and event header.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: calendar-events-1

#### (a) Decisions adopted from open questions

- Wall-clock in tenant zone vs instant plus zone -> wall-clock in the tenant time zone (Events and Tasks); instants only at invitation, shared-calendar and ICS boundaries, converted on arrival -> Decided by the product owner: wall-clock in the account's zone, instants only at the boundaries, so a zone change predictably does not move stored events.
- Timed Event without an end: +1 h or reject -> +1 h, clipped to 24:00 (new writes in the pre-write transform, converted Events in the migration) -> Decided by the product owner: one rule for every write (user, Semp, import) through the choke point.
- Default end of migrated Events: +1 h or by type -> +1 h for all (#1797) -> Decided by the product owner: one general mechanism instead of rules per Event type.
- Design change (end date label, All day in the new-event sheet) -> not adopted in the backend; no `allDay` property, all-day is `timeFrom` null -> Decided by the product owner: all-day is an empty start time; a separate `allDay` property would duplicate that meaning.
- Event "own page" definition and `hasPage` -> not part of this chunk (belongs to the page-summary issue); the atomic create issue does not depend on it -> Decided by the product owner: settled in the page-summary issue, not blocking here.
- Default type for calendar-created Events and mapping of "Invited" text -> Decided by the product owner: `type` stays empty (the user's own value), and the "Invited" label is shown by clients from the participant's role, never as a type (#1777) -> the simplest default; the wider decision lies outside the atomic create.
- Custom route `POST /api/calendar/events` -> not planned; create hook ordering ((not planned yet) edges before the default-calendar hook, hook skipping when a calendar edge exists) is the adopted mechanism.
- Tasks' end default -> Decided by the product owner: none. A timed Task without an end is a short task at its start time, drawn by the calendar as a short block; its effective end equals its start and no length is stored or computed (#1418) -> a stored end would create a duration the user did not enter.
- Daylight saving -> luxon defaults (non-existent wall-clock moves forward, ambiguous takes the earlier offset) -> Decided by the product owner: common and predictable behavior.
- Person subtitle rule -> left to clients; not a backend issue here.
- Format and cross-field validation scope -> format only for keys in the patch, cross-field only when date, endDate, timeFrom or timeTo change, so unmigrated Events stay editable.

#### (b) Open questions for the product owner

- Source of the "Fakturace" subtitle for a person (no backend source exists).
- Exact order of `dataMigrations` for Events 1.0.0 to 1.1.0 relative to other Events-schema owners (assumed after the Tasks-related migrations of the task-events work).

#### (c) User-visible behavior of this chunk

Calendar events gain a proper time model: a first day, an optional last day, and optional start and end times in the user's own time zone. An event without a start time is an all-day event; a multi-day or overnight event has an end date. Times are normalized (9:00 becomes 09:00), a timed event without an end gets a one-hour default (a timed task without an end gets none and is a short task at its start), and a readable range such as 10:00-11:30 is derived and stored; invalid combinations (end before start, an end without a start, a multi-day timed event without an end time) are rejected with a clear field-level error, the same way from the app, the assistant and MCP. Events also carry place, link, description (Markdown with checklists), and alert and travel minutes. Existing events are converted automatically to the new shape in each tenant's time zone, and a person's page can list the events they attend. A new event with its calendar, project and people is created in one step, or not at all. Underneath, a shared time module defines "today", day and week boundaries and when an event ends in the user's time zone (including daylight-saving changes), and database date comparisons no longer depend on the server's time zone.


### Decisions: calendar-events-2 (#1698 and C)

#### Adopted from open questions
- Audio attached to an Event as a recording? -> No. It is a plain attachment, not transcribed (#1698). -> Decided by the product owner: a recording is created only by recording an Event or by confirming a recording card in the Inbox; nothing is transcribed silently.
- Remove attachment: unlink only, or move file to trash? -> Unlink only; file stays in Files, inherited project and company stay as own values (#1756). -> Decided by the product owner: inherited values stay as own values per the link rules; the trash is for explicitly deleting a file.
- Trigger config: add `eventsRelationPropertyId` (optional) rather than resolving by key at runtime -> adopted, with a per-tenant action_config cutover. Reason: matches the existing attachments pattern; optional keeps un-migrated heartbeats working.

#### Open questions for the product owner
- Event description vs meeting notes page: one value or two (Events.description and the item page)? Not in B or C; affects a related issue / design.
- Where exactly link rules are declared (assumed systemDatabasesModuleManifest.ts); depends on #1411's final shape. The implementer of C must confirm.

#### User-visible behavior (epic paragraph)
A file attached to a calendar event shows up under the event; it is not mistaken for a standalone recording, so an audio attachment is not transcribed. The attachment takes the event's project automatically, and its company follows from that project. Removing the attachment only detaches it from the event: the file stays in the Files collection and keeps the project and company it received.
