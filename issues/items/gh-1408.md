## Context

Model tier rationale: One sorting mechanism in the sort compiler, but it must stay consistent between the ORDER BY and the keyset cursor predicate, which existing pagination fixtures verify.

`backend/packages/data/src/views/sortCompiler.ts` sorts a `select` by the text of its key (`properties ->> key`), so statuses appear alphabetically (archived, done, inProgress, longTerm) instead of in the order the property's `config.options` declares (in progress, long-term, done, archived). Sorting by a group property, which `viewQuery.ts` prepends as the group sort for a grouped view, has the same problem. Pagination uses a keyset cursor (`compileSortKeyset`), so the order and the cursor predicate must use the same expression or pages skip or repeat rows.

This issue makes a select sort, and a select used as group, follow the declared option order. It is built on by Czech text collation (#1524) and by group direction on grouped views (#1532).

Decision: an item whose value is empty, or is a key no longer in `config.options`, sorts after all options in either direction (the empty-value-last rule of the existing sorts), ties broken by id as today. Decision: multi-select properties are not sorted by option order here.

## Task

Load `testing`.

1. In `sortCompiler.ts`, for a sort key whose property type is `select`, sort by the zero-based position of the stored value in the ordered array of keys from `config.options`: `array_position($N::text[], properties ->> $K)`, the key array bound as one parameter, `NULLS LAST`. Descending reverses option order, still with empty or unknown values last.
2. Make `compileSortKeyset` use the same position expression, comparing against the position of the cursor row's value (bind the cursor value and compute its position with the same array). A cursor value that has no position takes the null branch. `viewQuery.ts` needs no format change to the cursor token; update `castableTo` and the sort-key handling there only if the shared helper requires it.
3. Tests: sorting projects by status returns in progress, long-term, done, archived, project without a status last; descending reverses the options but keeps the empty one last; a group property sorts groups in option order; three-page keyset pagination over a select sort returns every row once and in order, including the empty and unknown values.

## Acceptance criteria

- When items are sorted ascending by a select with options [inProgress, longTerm, done, archived], then they come in exactly that option order, items without a value last.
- When sorted descending, then option order reverses and items without a value are still last.
- When a grouped view groups by that select, then groups appear in option order.
- When the result is paged in three pages with the keyset cursor, then no row is missed or repeated.
