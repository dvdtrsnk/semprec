**Blocked by:** #1568, #1907, #1922
**Model tier:** medium

## Context

Model tier rationale: One new endpoint that creates a queued assistant message through an existing enqueue path, with a uniqueness constraint for the race and fixtures from the thread and queue issues, but it depends on the history reconstruction accepting an interrupted tool call, so the tests must pin that seam.

When Semp's reply fails or comes back incomplete, the chat offers "Try again" (and the same action is offered from the status view). Today there is no retry: a broken turn simply drops the session (`backend/packages/agent-runtime/src/sempConversation.ts`), and the user would have to retype the question. The REST error contract (`backend/services/semprec-api/src/adapter/errorContract.ts`, closed `ITEM_ERROR_CODES` with `ITEM_ERROR_STATUS_BY_CODE`) has no code for a refused retry.

After this issue the user can retry the latest failed reply of a thread: a new assistant message is queued as another attempt of the same reply, runs through the queued turn handler of #1727, and takes the place of the failed one in the chat. The failed attempt stays stored with its own steps, so the history still shows what was tried.

It builds on: failure classification and the stored error (#1907, which also decides what counts as an incomplete reply); the thread turn queue (#1727); closing idle sessions and pairing dangling tool calls (#1568); and the interrupted tool result shape (#1374). The same retry also serves the status view action (#1931, #1931), and #1932 lists replies as separate rows using `attempt`.

A reply that failed has already told the agent what it did: the tool results of the failed attempt stay in the history the agent sees for the retry, so it knows which changes were made. A tool call left without a result by the failed attempt is paired with a synthetic tool result in the regular tool result shape (#1568, #1374); the shape written by the startup repair in `backend/packages/agent-runtime/src/startupRepair.ts` would make waking the thread for a retry throw, and must not be what is used.

Decision: the retry sends the original user message again as a new user turn, resolved through `reply_to_message_id`. The duplicate user turn in the model history is accepted: it is the simplest solution and breaks nothing.

Decision: a retry is allowed on the latest message of the thread when it is an assistant message with status `error`, or with status `done` and an incomplete reply (the function of #1890 reports a reason). Anything else, including an older message or a successful reply, is refused with `retry_not_latest`.

Shared-file ordering: this issue also waits for #1922 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `io-hardening`, `db-migrations`, `error-handling` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_semp_messages_attempt.sql` (next free ordinal at commit time): add `attempt integer NOT NULL DEFAULT 1` to `semp_messages` and a unique index on (`tenant_id`, `reply_to_message_id`, `attempt`) for assistant messages, so two concurrent retries cannot both succeed.
2. Add the route `POST /api/semp/threads/:id/messages/:messageId/retry` as a `RouteDefinition` next to the message routes of #1543 (`backend/services/semprec-api/src/sempMessagesHandler.ts`; confirm the file name against that PR). It checks, in one transaction under the thread's row lock, that `messageId` is the last message of the thread, is an assistant message, and is retryable as decided above. Otherwise it answers 409 `retry_not_latest`. It then inserts a new assistant message with the initial status used by the send path, the same `reply_to_message_id`, `attempt` = previous attempt + 1, and calls `enqueueSempMessage` for it in the same transaction. It answers 202 `{ messageId }`.
3. Add `retry_not_latest` to `ITEM_ERROR_CODES` and to `ITEM_ERROR_STATUS_BY_CODE` (status 409) in `errorContract.ts`, additively.
4. In the turn handler of #1727 (`backend/services/semprec-agents/src/sempMessageTask.ts`), find the user message of an assistant message through `reply_to_message_id` (not through its position), so a later attempt sends the right user text and refs.
5. Return `attempt` on every assistant message in the history response of #1543, so the client shows only the newest attempt of one `reply_to_message_id` and can mark a second attempt.
6. Register the route in the route matrix and the route-to-handler mapping of the write-boundary test.
7. Tests: retry of the latest failed reply creates attempt 2 with the same `reply_to_message_id` and a queued job; retry of an older message or of a successful reply gives 409 `retry_not_latest`; two concurrent retries create one new message; after a retry whose first attempt left an interrupted tool call, the thread's history reconstruction succeeds and the agent turn runs; a tenant cannot retry another tenant's message.

## Scope

### In scope

- The retry endpoint, the `attempt` column, the new error code, and making the history of a failed attempt usable for the retry.

### Out of scope

- Regenerating a successful reply (#1930).
- Classifying failures (#1907) and raising or resolving the status entry (#1931).
- Writing the synthetic tool result for dangling calls (#1568, #1374); this issue only requires that the history after it reconstructs.
- Removing the duplicated user turn from the model history.
- Retry of heartbeat runs (#1908).

## Acceptance criteria

- When the latest assistant message of a thread failed and the user retries it, then a new assistant message with `attempt` 2 and the same `reply_to_message_id` is created, a turn is queued, and the response is 202 with its id.
- When the message is not the latest in the thread, or is a successful reply, then the response is 409 `retry_not_latest` and nothing is created.
- When two retries of the same message arrive at once, then exactly one succeeds.
- When the first attempt left a tool call without a result, then the retry turn still starts and the thread history reconstructs without an error.
- When another tenant calls the endpoint with this message id, then it answers as for an unknown message.
