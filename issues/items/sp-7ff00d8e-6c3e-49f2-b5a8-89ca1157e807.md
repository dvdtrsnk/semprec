## Context

Areas are a system database (`areas`) above Projects: a project belongs to one area, Events, Companies and Health
records relate to an area, Files and Journal days link to one one-directionally, Sleep settings point at one, and
Tasks, Files, Events, Health records and Journal days read a derived area through their project. Every collection
declares an `areaFilter` template, the Apple app has an area screen and an Areas section in the overview, and Mail,
Tasks, Search and the Inbox carry area filters, facets, kinds and prompt fields.

The owner decided on 2026-11-27 that this layer is hard to understand and manage and brings no real value. Areas are
removed entirely. Projects keep everything else and gain tags, and the projects collection is filtered by tag.

The database is recreated from the single baseline before every deploy
(`docs/architecture/migrations-and-seeding.md`), and the baseline holds no area-specific DDL, so the removal is a
seed and code change with no migration and no data conversion.

## Decisions

- Question: How are project tags stored?
  - Adopted answer: A user-owned `multi_select` property `tags` on Projects with no shipped options, the same shape as
    Health records `tags`. A person adds a tag through `POST /api/properties/:id/options`.
  - Reason: The filter compiler, facets, option operations and the mobile filter sheet already handle `multi_select`;
    a separate Tags database would be another layer of the kind being removed.
- Question: How is the projects collection filtered by tag?
  - Adopted answer: The existing filter sheet, plus a horizontal bar of tag chips above the list. The bar is declared
    by the server per database (`facetBarProperty` in the module manifest, published in `GET /api/schema`) and only
    Projects declares it. The bar and the sheet edit the same selection.
  - Reason: The collection screen is one schema-driven engine; a per-database switch in the app would break that.
- Question: What does selecting several tags mean?
  - Adopted answer: Any of them (the existing `in` operator, which is overlap on a `multi_select`).
  - Reason: No new filter operator.
- Question: Are tasks filtered by their project's tags?
  - Adopted answer: No. The tasks area filter is removed without replacement; the project filter stays.
  - Reason: Not requested.
- Question: What happens to the derived-value mechanism?
  - Adopted answer: Its area half is removed; the Event company derived through the project stays.
  - Reason: The company derivation is unrelated to areas.

## Behavior specification

- Projects have a `tags` property; a tag can be created, set on a project and cleared, in the API and in the Apple
  project settings; the project detail and its collection row show its tags.
- The projects collection shows a tag bar when at least one tag exists; tapping a chip toggles it in the same
  selection the filter sheet edits; the result is the projects having any selected tag, combined with the active
  quick filter.
- No area exists anywhere: no `areas` database, relation, derived value, filter template, route, search group, inbox
  card kind or target, proposal field, mail filter or facet, sleep field, screen, overview section, string or test.
- Android and web need no change; they have no area code.
