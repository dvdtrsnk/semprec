**Model tier:** high

## Context

Model tier rationale: It adds a cross-database step to the atomic multi-step Inbox confirm (file plus expense plus links) whose validation failure must roll back the file as well, touching a path where a partial write corrupts user data.

An Inbox card for an invoice photo can offer "File and expense": the picture is saved as a file in Files and, if the toggle "Create expense" is on, an expense is created in Finance with the amount, the due date and the file as its document. Today a proposal creates exactly one item: `confirmProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`, served by `POST /api/proposals/:id/confirm`) takes the envelope `{ entityKind, target, properties }` and creates one item. #1486 extends confirm to multi-step proposals: an ordered list of operations, each with a reference, a role (`primary` or `secondary`) and an `enabled` flag, committed atomically with refs resolvable between steps. #1703 adds the step that moves the Inbox attachment's blob into a Files item (the primary step). #1511 provides the `transactions` database, #1607 validates amounts, and #1651 makes the expense take the invoice's company and project from the file along `document`.

This issue defines and runs the expense step of that envelope.

Decisions:
- The expense step is a `secondary` step, `enabled` only when the card's "Create expense" toggle is on. It runs after the file step and links back to it by reference. Order matters: the file's company and project must exist before the expense is linked, because the expense takes them over.
- The server never parses a display string like "4 820 Kc". The client sends canonical values: `amount` as a number greater than 0 and `currency` `CZK`.
- The step creates a `transactions` item with `type: expense`, `paymentStatus: unpaid`, `date` = the document date, `dueDate` as given, `source: inbox`, `sourceInbox` = the Inbox item, and `document` = the file step's item. `source` and `sourceInbox` are set by the server, never accepted from the envelope.
- An invalid amount (zero, negative, not a number) fails the whole confirm with 400 `validation_failed` naming the step reference and the field `amount`, and nothing is created, not even the file.
- An optional `categoryId` in the step is accepted (an existing Finance category) so a card can offer a category; when absent the expense has no category. Whether the card shows a category field is a client decision.


Shared-file ordering: this issue also waits for #1743 because both edit the same files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `canonical-keys` and `testing`.

1. Define the expense step kind in the multi-step envelope: target database `transactions`, allowed properties `amount`, `currency`, `date`, `dueDate`, `note`, `name`, optional `categoryId`, and the reference to the file step as `document`. Reject any other property, including `source`, `sourceInbox`, `type` and `paymentStatus`, with 400 `validation_failed`. Put the definition and validation in `backend/packages/data/src/inbox/expenseProposalStep.ts` and call it from the envelope validation of #1479.
2. In confirm (`proposalActions.ts`), execute the step after the file step inside the single transaction: create the transaction with the fixed values above, the amount and currency from the envelope, `source` `inbox`, `sourceInbox`, `document` linked to the file step's item (so the link rules of #1651 apply), and the optional category.
3. When the step is disabled, create nothing for it; the file is created as before.
4. Tests, against the real schema: confirm with the toggle on creates the file and a transaction (4 820 CZK, due 23 October, document set, company and project taken from the file as `inherited` links) in one commit; with the toggle off only the file; `amount` 0, -5 and a string fail with 400 naming the step and `amount` and create nothing (not even the file); an envelope carrying `source` or `type` is rejected; a failing step after the file step rolls the file back; two confirms of the same proposal create one transaction; a card whose file has two projects gives an expense without a project.

## Scope

### In scope

### Out of scope

- The multi-step envelope, its validation framework and the atomic confirm itself: #1479 and #1486.
- Moving the attachment's blob into Files: #1703.
- Taking company and project over from the file: #1651.
- Making `transactions` an allowed Inbox target type: #1973 and #1977.
- Reading the invoice (supplier, amount, dates, "by Friday"): #1970; adding a new company: #1989.
- Editing card fields by hand: #1471.
- Whether the card shows a category field: a client decision, not planned here.

## Acceptance criteria

- When a card with "Create expense" on is confirmed with amount 4 820 and due date 23 October, then one commit creates the file and a transaction with `type` expense, `paymentStatus` unpaid, `source` inbox, the document set, and company and project taken from the file.
- When "Create expense" is off, then only the file is created.
- When the amount is 0, negative or not a number, then the response is 400 `validation_failed` naming the step and `amount`, and no file and no transaction exist.
- When the envelope tries to set `source` or `type` on the step, then confirm is rejected.
- When the same proposal is confirmed twice, then exactly one transaction exists.
