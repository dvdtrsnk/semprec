### Requirement gh-1604: [inbox-editing 06/23] Return a proposal to proposed when its source is restored

#### Context

Model tier rationale: One generic trigger added on restore plus a guarded transition in the tick's read phase, within existing seams and fixtures, but it touches the choke point restore path and the tick's gating so the change needs careful tests.

When an Inbox item is deleted, its proposal card becomes `invalid` with reason `sourceDeleted` (#1482). If the user then restores the item from the trash, the card should come back as `proposed`. Today it does not: `restoreItemWithClient` (`backend/packages/data/src/chokePoint/itemTrash.ts`) only announces an invalidation to clients and, unlike `itemDeleteWithClient` (which calls `triggerOnItemEventHeartbeats(..., "delete", ...)`), triggers no heartbeat, so `semprec.tick` never runs; and even if it ran, the tick's fingerprint gate in `inboxTickAction.ts` (the source's fingerprint is unchanged) would end the tick before anything is written.

Decision: restoring an item triggers the database's `onItemEvent` heartbeats with event `update`, generically for every restored row (the restore is a change of the item); the Inbox's existing `update` heartbeat then runs the tick. Heartbeat registrations for other databases that listen to `update` will also run on restore; that is accepted because a restored item is a real change for them.

Decision: in the tick's read phase, an existing proposal with `status: "invalid"` and `invalidReason.code: "sourceDeleted"` whose source is now live is returned to `proposed` regardless of the fingerprint: `status: "proposed"`, `invalidReason: null`, history entry `kind: "reopened"`. If the source text changed while it was in the trash (the fingerprint differs) the normal recompute path continues afterwards. If the stored envelope no longer validates, the card goes to `needsClarification` instead.

2. In the tick's read phase (`inboxTickAction.ts`, before the fingerprint short-circuit) add the guarded transition above, using `lockUnlockedProposal` for the write.
3. Tests: delete then restore an Inbox item runs the tick and the card is `proposed` with `invalidReason` null; the transition happens when the fingerprint is unchanged; an edited-while-trashed source recomputes; a card invalid for `targetArchived` is not touched by a source restore; a locked card is untouched; restoring a non-Inbox item still works and triggers its own `update` heartbeats only.

### Requirement gh-1625: [block-editor 09/13] Publish thin doc invalidations from doc updates

#### Context

Model tier rationale: A new realtime frame with per-document throttling timers must stay tenant-isolated and leak-free across socket close and shutdown, which is a cross-process isolation and cleanup-ownership contract.

Page previews outside the editor (the project notes card, journal weeks and rows) must refresh when a page changes on another device, even though the client has no document open. Today the realtime server only tells sockets about a document when they opened it: `WS /api/sync` fans a `doc_update` NOTIFY out through `docSync.fanOutDocUpdate` (`backend/packages/realtime/src/docSync.ts`) to the sockets subscribed to that `docId`, carrying the Yjs bytes. `OutboundFrame` (`backend/packages/realtime/src/protocolV1.ts`) has `invalidate` frames for scope `item` and `schema` only, and `syncServer.ts` already sends those to every socket of a tenant (`sendToTenant`). The existing `invalidationCoalescer.ts` is a per-socket queue that sends immediately when the socket is drained and only merges while a client is behind; it has no time window and no trailing edge.

#1405 records `last_edited_at` and `last_edited_by` on `docs`. #1621 establishes the extended `scope` chain in `OutboundFrame` that this issue extends with one more scope. #1863 builds on the same union afterwards.

Decisions:

- Decision: the frame is derived inside `@semprec/realtime` from the existing `doc_update` message; no second publisher is added to the data layer. The realtime process looks up the document's `itemId` and `databaseId` and its `last_edited_at` under the message's tenant scope (`runInTenant`).
- Decision: the throttle is a new mechanism keyed by (tenant, docId), separate from `invalidationCoalescer` (which is per-socket and item-scoped). One timer state per document in the process, not per socket.
- Decision: the throttle window is 1 second, leading and trailing: the first event for a document in a quiet period is sent at once; further events within the window are merged, and one final frame carrying the newest `lastEditedAt` is sent at the end of the window.

Controller reconciliation: issues/batches/backend/decisions/batch-23-spec-reconciliation.md, sections 5, governs the exact added paths and existing-owner contract. Other Task/AC obligations remain.

Additional controller reconciliation section 9 in issues/batches/backend/decisions/batch-23-spec-reconciliation.md governs the snapshot/lookup reservation and transient-error behavior.

2. Add `docInvalidationThrottle.ts` in `backend/packages/realtime/src`: a per-(tenant, docId) leading and trailing 1-second throttle that calls a send callback with the newest pending value.
