## Behavior specification

Semp status: problems, resolution, history and services.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions for job semp-status-1

#### (a) Decisions adopted from open questions

- Where does the task name in "Semp did not finish the task" come from? -> the title of the thread the failed reply belongs to; omitted when empty; the message text is never used -> conservative, no new generated title and no user message text in a status card. -> Decided by the product owner: the name is taken from the thread title; when the title is empty it is omitted and the user's text is not used.
- Problems store no user content (ids, keys, counters only); titles and texts are rendered at read time in the user's locale -> wording and locale changes apply to existing problems.
- Push for new/escalated problems is not sent by the store; `raiseProblem` returns `created`/`merged`/`escalated` for the push issue.
- Replays of the same job/run must not inflate counts -> `raiseProblem` takes an optional `occurrenceKey` compared with the stored last key (added to the table).
- Dedupe keys: `mail:<mailboxId>` (error, reauthorization and stall are one problem; reauthorization is `critical` and escalates), `agents:heartbeat:<heartbeatId>`, `agents:run:<first run of the retry chain>`, `agents:reply:<reply_to_message_id>`, `guidance:<projectId>:<fingerprint>`, `automation:<databaseId>`, `backup:restoreTest`, `agents:process`.
- Chat conversation runs are excluded from the run-level problem (they are covered by the per-reply problem).
- Operator problems (`backup_restore_failed`, stale `semprec-agents`) are written only for administrators, per administrator in their own tenant, as the operator notification is; `queue_backlog` stays a notification.
- The backfill runs as a per-tenant cutover step, is idempotent (`occurrenceKey` `backfill`) and does not backfill operator problems or failed chat replies.
- The status response is built incrementally: this chunk returns `{ activeCount, problems }`; `services`, `resolvedRecent` and the budget problem are added additively by later issues.
- Banner = most severe active `critical` problem in category `mail` or `agents`; `instanceId` = problem id (a recurrence is a new row, hence a new instance).
- Action descriptors are `{ kind, target }` ids only; the operations behind them are other endpoints.

#### (b) Open questions remaining for the product owner

- Planning overlaps to resolve in the dependency graph: #1931 and #1931 both raise/resolve the failed-reply problem with the same key (one should be dropped); #1506 and #1506 both raise the mailbox sync problem (and #1506 also covers resolve); #1911/#3 keep separate key-builder files to avoid a shared-file collision but still both edit `index.ts` barrels and `sempProblemsStore` callers.
- #1555 renders the cause of failed runs/replies from error codes of #1446/#1907, which are not listed as its blockers; rendering falls back to generic text when no code is stored. Confirm whether those blockers should be added.
- Should a failed chat reply that the user cancels ever show as a problem (adopted: no)?
- Whether `calendar` problems (subscription feeds) and the AI budget problem should use the same card shape (adopted: yes, added by their own issues).

#### (c) User-visible behavior of this chunk

The Semp status view lists everything that currently needs the user's attention as one entry per cause: a mailbox that is not syncing (merged from all failed attempts, with the start of the streak and a critical level when sign-in expired), a task Semp did not finish in chat or a failed automatic task, drift in agent guidance, library automation errors, and for administrators a failed backup test or a stuck Semp process. Each entry has a plain-language title and explanation in the user's language, a count of merged reports and actions such as sign in again, try again or open the chat. Failures that already exist when the feature is deployed appear immediately. A lightweight summary gives the profile its count and the chat a banner for the most serious problem that affects Semp, which comes back as a new notice if the problem returns after being resolved.


### Decisions for job semp-status-2

#### (a) Decisions adopted from open questions

- Do positive events that are not recoveries (passing restore test without earlier failure, emptied queue) belong in history? -> adopted: no; history lists only resolved problems -> keeps history tied to problems and avoids global admin-only events in a tenant view. -> Decided by the product owner: history contains only resolved problems; positive events would flood it.
- Calendar row in Services without a source -> adopted: omitted until subscription feeds exist, then added additively. -> Decided by the product owner: the Calendar row appears only with the first ICS subscription; public holidays computed in code do not create it.
- `transcript_event_match` in AI usage -> not decided here (belongs to the AI usage issues); this chunk does not touch AI usage.
- Resolution kinds: `recovered` for all recoveries (the title is chosen by problem kind) and `sourceDeleted` for problems closed because the source was deleted; deleted-source resolutions are hidden from history. The transcription kind uses `recovered` instead of a separate `transcriptionCompleted` value.
- A tick is recovered only when its run ended `done` and its reply left no failed tool call; a successful run in a retry chain resolves the chain's run problem.
- Also resolved (beyond what the design shows): stale-process and library automation problems, so no raised problem stays open after recovery.
- History capped at the 100 newest; window seven days; pruning deletes resolved rows older than thirty days, never active ones. -> Decided by the product owner: seven-day window, cap of 100 entries, resolved problems deleted after thirty days; active problems are never deleted.
- Restore test time: `ranAt` parsed from the run id, no script change, no migration; rows without it are read from `runId`; tenants only see `{ lastTestAt, ok }`.
- Service state/since come from the active problem of the service (by category, or mailbox key for mail).
- Transcription service counts only the caller tenant's `transcriptionJob` jobs (queued = unlocked, running = locked).

#### (b) Open questions remaining for the product owner

- Planning issues to resolve in the dependency graph: #1945 bundles two mechanisms (problem raise/resolve and the services-list entry) because the plan assigns both to one issue; consider splitting. #1915 touches five unrelated recovery sites and could be split per source. #1919 does not depend on #1915's `sourceDeleted` constant being merged first only through the listed dependency, which is fine.
- #1558 and #1459 / #1919 may each add migrations or edit the problems store; ordering is by the listed blockers.
- Resolution title wording for heartbeat, process and library automation recoveries is my proposal (the design shows only mail, reply, guidance and restore-test titles); confirm.
- Closing related notifications/pushes on resolve (#1463) and sending the status invalidation (#1868) are left to their own issues; the resolve call sites in this chunk will need to trigger them (ordering to be confirmed).

#### (c) User-visible behavior of this chunk

When something that was wrong starts working again - a mailbox syncs, a failed automatic task runs fine, a task Semp could not finish succeeds on retry, a transcript is produced, a guidance drift is fixed, the monthly backup test passes - its entry leaves the active problems in the same moment and appears in a "Resolved in the last 7 days" section with a plain sentence such as "Gmail mailbox is syncing again", newest first; entries disappear from history after 30 days. The Services list shows Semp and agents, each mailbox with provider and last activity, meeting transcripts with how many jobs are queued and running, and backups with the date of the last restore test, each marked Running or Error with the time the error started.
