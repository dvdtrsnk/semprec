## Context

Model tier rationale: Existing tenant iteration and cutover mechanisms are composed with bounded pool cleanup and isolated failures.

`runMigrationsCli.ts` (`backend/packages/data/src/db/runMigrationsCli.ts:17-39`) runs the SQL migrations and then a fixed list of application-code steps. `backend/packages/data/src/testSupport/globalSetup.ts:110-121` runs the same list for the test database. The pattern is recorded in `docs/adr/2026-09-10-app-code-post-migration-steps.md`. It runs under `SEMPREC_MIGRATE_DATABASE_URL` (the table owner, so RLS does not apply) with no tenant scope. The steps fall into three groups.

Schema-guarded one-time cutovers. Each returns at once when its column is already `NOT NULL`, needs table ownership for its `ALTER TABLE ... SET NOT NULL`, and only ever ran before a second tenant could exist:
- `runDocHistoryCutoverMigration` (`backend/packages/data/src/docs/docHistoryCutoverMigration.ts:39-44`);
- `runAgentRunsActorUserIdCutoverMigration` (`backend/packages/data/src/agentRuns/agentRunsActorUserIdCutoverMigration.ts:29-33`);
- `runApprovalRequestExecutionStatusCutoverMigration` (`backend/packages/data/src/mcp/approvalRequestExecutionStatusCutoverMigration.ts:38-42`).

Global steps that read no tenant rows:
- `activateCzechHunspellSearch` (text-search configuration);
- `ensureQueueSchema` and `grantQueueSchemaPrivileges`;
- `runHeartbeatFireQueueSplitMigration`, which returns as soon as no legacy `heartbeatFire` job exists (`backend/packages/data/src/scheduler/heartbeatFireQueueSplitMigration.ts:36-51`). No release since that split enqueues one.

Data-driven cutovers that read and write tenant rows on every deploy:
- `runTranscriptsCatalogCutoverMigration` (`backend/packages/data/src/transcription/transcriptsCatalogCutoverMigration.ts:20-94`). It resolves Transcripts and People with `getDatabaseByModuleId`, then adds the `error` status option, the `speakers` relation and the pipeline `owner_process`.
- `runTranscriptionRequeueHeartbeatCutoverMigration` (`backend/packages/data/src/transcription/transcriptionRequeueHeartbeatCutoverMigration.ts:20-46`). It checks `project_heartbeats` for the requeue heartbeat and creates it on the trigger's project.

With a second tenant and the owner role, the data-driven pair breaks. #1001's `getDatabaseByModuleId` throws on the ambiguous Transcripts database, so the deploy fails. The heartbeat check would also see another tenant's heartbeat and skip this one. Without a scope, every step's `withTransaction` also logs `tenant_scope_missing` in warn mode and throws under strict enforcement.

Tenancy state this issue builds on:
- From #1005:
  - `createPool(url, { role: "semprec_data" })`;
  - `assertRowSecurityActive(queryable)`;
  - `forEachMaintainedTenant(pool, fn)` (`backend/packages/data/src/tenancy/provisionTenant.ts`). It runs `fn` inside `runInTenant` for every `provisioning`, `active` or `suspended` tenant. A failure does not stop the others, and all failures end in one `AggregateError`.
  - Its ADR: deploy-time steps that read or write tenant rows run per tenant on a `semprec_data` pool.
- `runAsSystem(reason, fn)` comes from `@semprec/shared`.
- #975 provides the two-tenant runtime-role harness. It also edits `globalSetup.ts`, so this issue follows it.

Decision: no step is retired. The data-driven pair runs once per tenant under RLS; every other step stays global inside an explicit system scope.

## Task

Load `state-writes` (the cutovers write tenant rows), `error-handling` (per-tenant failures, and closing two pools) and `db-migrations` (post-migration steps).

1. **Per-tenant cutovers.** New `backend/packages/data/src/db/tenantCutoverMigrations.ts` exports `runTenantCutoverMigrations(pool: Pool): Promise<void>`.
   - It calls `assertRowSecurityActive(pool)`.
   - Then `forEachMaintainedTenant(pool, async () => { await runTranscriptsCatalogCutoverMigration(pool); await runTranscriptionRequeueHeartbeatCutoverMigration(pool); })`.
   - The two cutover bodies stay unchanged. Their `LOCK TABLE` statements are permitted to `semprec_data`, which has `UPDATE` on `properties` and `project_heartbeats`.
   - Update both files' header docstrings: the cutover runs once per tenant, in that tenant's scope, under RLS.
2. **CLI (`runMigrationsCli.ts`).**
   - Create a second pool `createPool(connectionString, { statementTimeoutMs: 0, role: "semprec_data" })`.
   - Wrap the whole sequence in `runAsSystem("deploy migrations", …)`, keeping today's order. Replace the two transcription calls with `runTenantCutoverMigrations(tenantPool)` at the same position (before `ensureQueueSchema`).
   - End both pools in `finally`. A failure to end one must not skip ending the other, nor replace the error that ended the run.
3. **`globalSetup.ts` (lines 110-121).**
   - Mirror the CLI: wrap the block in `runAsSystem("test database setup", …)`.
   - Replace the two transcription calls with `runTenantCutoverMigrations` on a `{ role: "semprec_data" }` pool created from the same connection string, and end that pool too.
   - Keep the rest of #975's setup as it is.
4. **Tests.** New `backend/packages/data/src/__tests__/tenantCutoverMigrations.test.ts`, on the #975 harness.
   - Build the old-shape fixtures the way `backend/packages/data/src/transcription/__tests__/transcriptsCatalogCutoverMigration.test.ts` and `transcriptionRequeue.test.ts` do, but in each tenant's own scope: seed the tenant, then remove `speakers`, the `error` option and the requeue heartbeat.
   - Both existing cutover tests must keep passing as they are.

## Scope

### In scope
- Running the two data-driven cutovers per tenant on a `semprec_data` pool.
- Running the CLI and test setup inside a system scope.
- The docstrings and the tests.

### Out of scope
- The `getEarliestUserId` call inside `runAgentRunsActorUserIdCutoverMigration` (`agentRunsActorUserIdCutoverMigration.ts:53`), which belongs to #1020.
- Changing or deleting the schema-guarded cutovers, the Hunspell activation, the queue schema steps or the `heartbeatFire` split.
- Stamping a tenant onto legacy queued jobs (#1061).
- Seeding and module data migrations (#1005, #1006).

## Acceptance criteria

All integration tests (`*.test.ts`) on the #975 harness.
- **Both tenants upgraded.** Tenant zero and tenant B each have an old-shape Transcripts database and no requeue heartbeat. One `runTenantCutoverMigrations` call on the `semprec_data` pool, inside `runAsSystem`, leaves each tenant, in its own scope, with:
  - the `error` status option and the pipeline `owner_process` on `status`/`date`/`link`;
  - a `speakers` relation whose `targetDatabaseId` is that tenant's own People database;
  - exactly one requeue heartbeat, on that tenant's own project, whose `actionConfig.transcriptsDatabaseId` is its own Transcripts database.
- **Idempotent.** A second call changes no `properties`, `relation_definitions` or `project_heartbeats` row in either tenant.
- **Partial state.** Only tenant B lacks the requeue heartbeat. The call creates B's heartbeat and none for tenant zero.
- **Deleting tenant.** A `deleting` tenant's old-shape Transcripts database is left untouched.
- **Failure isolation.** When B's cutover throws (a test-only trigger raising on `properties` updates of B's Transcripts database), tenant zero is still upgraded, and the call rejects with an `AggregateError` naming B.
- **Owner pool refused.** On the owner pool (`getTestPool()`), `runTenantCutoverMigrations` rejects with the RLS error and writes nothing.
- **Existing behaviour kept.**
  - The integration tier starts with the reworked `globalSetup`.
  - The existing tests pass unchanged: `transcriptsCatalogCutoverMigration.test.ts`, `transcriptionRequeue.test.ts`, `docHistoryCutoverMigration.test.ts`, `approvalRequestExecutionStatusCutoverMigration.test.ts` and `heartbeatFireQueueSplitMigration.test.ts`.
