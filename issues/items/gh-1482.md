## Context

Model tier rationale: One structured system property written at the single existing invalid transition, one guard on the revise path and a few catalog strings, using existing fixtures and no new lifecycle or tenant contract.

A proposal card becomes `invalid` when it can no longer be used; the user sees "This proposal can't be used" with a sentence explaining why, for example that the project the task was meant for has since been archived and the user should choose another project or ask Semp to recompute. Today `invalid` is produced only by `invalidateProposalForDeletedSource` in `backend/packages/data/src/inbox/inboxTickAction.ts`, when the source Inbox item is deleted; it writes just `status` and `history`, so nothing says why the card is invalid, and a card whose source is gone is not distinguishable from one that could be repaired. `reviseProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) even moves an `invalid` card back to `proposed` while its source is still deleted.

The Processing proposals database has an `invalidReason` system property (#1451). This issue defines and writes it, and separates two kinds of invalid card: a card whose source is deleted is final (it can only be discarded), a card whose target was archived or deleted is fixable (choosing another target on the edit route returns it to `proposed`, see #1892). The later issue #1916 writes the target-side reasons reactively.

Decision: `invalidReason` is `{ code: "sourceDeleted" | "targetArchived" | "targetDeleted", field, itemId, label }`: `field` is the editor field concerned (empty for the source), `itemId` the item that caused it, `label` the item's name at that time. The warning sentence is not stored; it is rendered from the code and the label through the Inbox catalogs in the caller's locale.


Deletion precedence (parent reconciliation): an open proposal includes an unlocked card already invalid for targetArchived, targetDeleted or a missing legacy reason. When its source is deleted, sourceDeleted supersedes that fixable reason and revise is refused. Repeated processing of the same sourceDeleted state is idempotent and adds no invalidation history. Confirmed/rejected cards remain untouched. Final means not repairable by revise while source-deleted; a later genuine source restoration is handled separately by the existing gh-1604 guarded validation/reopen contract. A restore tick that still sees a target-side reason, with no intervening source-deletion transition, does not clear that reason.

## Task

Load `state-writes`, `canonical-keys`, `error-handling` and `testing`.

1. In `inboxTickAction.ts` define and export the zod schema and type of `invalidReason`, a helper `isFinalInvalid(properties)` (`status === "invalid"` and `invalidReason.code === "sourceDeleted"`), and make `invalidateProposalForDeletedSource` write `invalidReason: { code: "sourceDeleted", field: "", itemId: <source id>, label: <source text excerpt> }` together with `status` and `history` (add `invalidReason` to `allowedSystemKeys`; history entry `kind: "invalidated"`).
2. In `reviseProposalWithClient`, refuse a card for which `isFinalInvalid` is true with a `ValidationError` on `status`; when a fixable invalid card is revised, clear `invalidReason` in the same write.
3. Add `renderInvalidReason(reason, locale)` in `backend/packages/data/src/inbox/invalidReason.ts` that returns the localized sentence, and the catalog entries for the three codes in `backend/packages/data/src/inbox/i18n/en.json` and `cs.json` (each ends by offering to choose another target or recompute, except `sourceDeleted`).
4. Tests: deleting a source stores the reason; a revise of that card is refused; revising a card with `targetArchived` clears the reason; rendering is localized and falls back to English; a legacy invalid card without `invalidReason` is treated as fixable.

## Scope

### In scope

- The `invalidReason` shape, writing `sourceDeleted`, the final/fixable distinction on revise, and the localized sentence.

### Out of scope

- Writing `targetArchived` and `targetDeleted` when a referenced item changes (#1916).
- Returning to `proposed` when the source is restored (#1604).
- Exposing the sentence on the card list (a separate list issue).
- Refusing the edit route for a final invalid card (the edit route reads `invalidReason` itself, see #1892).

## Acceptance criteria

- When the source Inbox item of any unlocked open proposal is deleted, including one already invalid for a fixable target reason or without a legacy reason, then the card is `invalid` with `invalidReason.code` `sourceDeleted` and the source's id. Repeated processing of that same final state is a no-op; locked confirmed/rejected cards remain unchanged.
- When a card with `sourceDeleted` is revised, then the call fails with a validation error and the card is unchanged.
- When a card with `invalidReason.code` `targetArchived` is revised to a valid envelope, then it becomes `proposed` and `invalidReason` is null.
- When the sentence is rendered for locale `cs` and `en`, then each is localized and contains the item label.
- A legacy `invalid` card without `invalidReason` can still be revised.
