## Context

Model tier rationale: One new fingerprint function and a version-aware comparison at the two existing call sites, with the compatibility rule being the only subtle part, within existing fixtures and no new lifecycle or tenant contract.

Inbox proposal freshness must include type identity, capture facts and attachment identity, while preserving v1 comparison and transcript-card scope.

Decision: the new fingerprint is versioned. Version 2 is the SHA-256 of a canonical JSON object `{ v: 2, typeId, text, date, time, attachmentHashes, transcribedText }` stored as the string `v2:<hex>`. `typeId` is the Inbox item type's id, `date` and `time` the item's capture date and time, `attachmentHashes` the sorted `blobs.content_hash` values of the item's attachments (a legacy NULL uses that blob's canonical UUID instead, with no byte read or backfill) (the counted blob references added by #1564), and `transcribedText` the transcript text of its audio attachments, an empty string when there is none. A stored value that does not start with `v2:` is a version 1 value and is compared with the old formula over the current `(emoji, text)`; so a version 1 card is recomputed only when its emoji or text really changed, and is then stored as version 2.

Decision: until audio attachments are transcribed from the Inbox, `transcribedText` is always `""`; the field is part of the shape so a later change populates it without another fingerprint version. Attachment hashes are read inside the tick's read transaction, not taken from the job payload.

Scope clarification: freshness is checked when the existing tick is invoked. This issue does not introduce enqueue ownership for low-level attachment or type-relation writes; direct tick execution is not proof of automatic dispatch. Existing v1 comparison and hashed-blob v2 values stay compatible.

## Scope

### In scope

- The version 2 fingerprint, the version 1 compatibility comparison and their use in the tick.

### Out of scope

- Forcing a recompute independently of the fingerprint (#1947, #1955).
- Storing attachments (#1564) and transcribing audio attachments.
- Fingerprints of transcript cards (`kind: transcript` keep their own shape).

## Acceptance criteria

- When the capture time of an Inbox item changes and the tick next runs, then it recomputes its proposal.
- When an attachment is added to or removed from an item and the tick next runs, then it recomputes, including legacy NULL hashes; when only attachment order changes, it does not.
- When another type with the same emoji is chosen and the tick next runs, then it recomputes.
- When this version is deployed and a card holds a version 1 fingerprint, then nothing is recomputed until its emoji or text changes, and the recompute stores a `v2:` fingerprint.
- When the fingerprint is unchanged, then the tick makes no AI call, as before.
