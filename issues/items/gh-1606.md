## Context

Model tier rationale: One new fingerprint function and a version-aware comparison at the two existing call sites, with the compatibility rule being the only subtle part, within existing fixtures and no new lifecycle or tenant contract.

The tick (`semprec.tick`, `backend/packages/data/src/inbox/inboxTickAction.ts`) decides whether to recompute an Inbox item's proposal by comparing the stored `fingerprint` with `computeInboxFingerprint(emoji, text)` (`backend/packages/data/src/inbox/fingerprint.ts`), a SHA-256 over the type's emoji and the item's text. Anything else that shapes the proposal is invisible to it: changing the capture date or time, adding or removing an attachment, or choosing another type that happens to share the emoji changes nothing and nothing is recomputed. The tick does not run at all today, so no stored fingerprint of this kind exists in production; but cards created before this change will carry the old value once the tick ships, and they must not all be recomputed at the first edit after deployment.

Decision: the new fingerprint is versioned. Version 2 is the SHA-256 of a canonical JSON object `{ v: 2, typeId, text, date, time, attachmentHashes, transcribedText }` stored as the string `v2:<hex>`. `typeId` is the Inbox item type's id, `date` and `time` the item's capture date and time, `attachmentHashes` the sorted `blobs.content_hash` values of the item's attachments (the counted blob references added by #1564), and `transcribedText` the transcript text of its audio attachments, an empty string when there is none. A stored value that does not start with `v2:` is a version 1 value and is compared with the old formula over the current `(emoji, text)`; so a version 1 card is recomputed only when its emoji or text really changed, and is then stored as version 2.

Decision: until audio attachments are transcribed from the Inbox, `transcribedText` is always `""`; the field is part of the shape so a later change populates it without another fingerprint version. Attachment hashes are read inside the tick's read transaction, not taken from the job payload.

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. In `fingerprint.ts` add `computeInboxFingerprintV2(input)` (canonical, key-order independent, `attachmentHashes` sorted) returning `v2:<hex>`, and `isFingerprintCurrent(stored, { v2Input, legacyEmoji, legacyText })` which compares as decided above. Keep `computeInboxFingerprint` for the version 1 comparison.
2. Add a reader in `inboxTickAction.ts` that resolves the item's attachment hashes from `blobs.content_hash` for its attachment references inside the tick's read transaction.
3. Use `isFingerprintCurrent` at the gate in `readTickSnapshot`, and compute and store the version 2 fingerprint wherever the tick stores one (`writeTickResult` stale check, `reviseProposal`, create, `writeNeedsClarification`), comparing the snapshot fingerprint to the freshly computed one in the same version.
4. Tests in `inboxTick.test.ts` / `inboxTickProposal.test.ts` and a unit test for `fingerprint.ts`: change of capture date or time, adding or removing an attachment and choosing a type with the same emoji each change the version 2 value; reordering attachments does not; a version 1 card with unchanged emoji and text is not recomputed; a version 1 card with changed text is recomputed and ends with a `v2:` fingerprint; the stale-write check still skips a result computed against an older source.

## Scope

### In scope

- The version 2 fingerprint, the version 1 compatibility comparison and their use in the tick.

### Out of scope

- Forcing a recompute independently of the fingerprint (#1947, #1955).
- Storing attachments (#1564) and transcribing audio attachments.
- Fingerprints of transcript cards (`kind: transcript` keep their own shape).

## Acceptance criteria

- When the capture time of an Inbox item changes, then the tick recomputes its proposal.
- When an attachment is added to or removed from an item, then the tick recomputes; when only the attachment order changes, it does not.
- When another type with the same emoji is chosen, then the tick recomputes.
- When this version is deployed and a card holds a version 1 fingerprint, then nothing is recomputed until its emoji or text changes, and the recompute stores a `v2:` fingerprint.
- When the fingerprint is unchanged, then the tick makes no AI call, as before.
