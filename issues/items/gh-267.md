**Blocked by:** #266

## Context

Two paths in the mail code hold an open PostgreSQL transaction across work that is not database work. Both were flagged by post-merge reviews (of #93's and #94's pull requests) and neither was addressed; both are still present on `develop`. Holding a pooled connection across an unbounded external wait is how a pool gets exhausted under load, and it is the same defect in two places, so one issue fixes both.

**1. `backend/packages/data/src/mail/mailSyncJob.ts`.** `handleSyncMailAccountTask` opens `withTransaction(pool, async (client) => { ... })` and, inside that callback, calls `await imapConnectionLimiter.run(payload.mailboxItemId, connectionLimit, async () => { ... reconcileImapAccount(client, imap, shared) ... })`. The limiter can make that call wait up to `ACCOUNT_QUEUE_WAIT_TIMEOUT_MS` (3 minutes) for a free IMAP slot, and the database connection is pinned for the whole wait. If the wait times out, the transaction correctly aborts and the error propagates — but a pool slot was held for three minutes for nothing.

**2. `backend/packages/data/src/migrationJob/mailLegacyEmailMigration.ts`.** `runMailLegacyEmailMigrationJob` calls `await withTransaction(pool, (client) => migrateLegacyItem(client, row, fetchRawMime))`, and `migrateLegacyItem`'s first statement is `const rawMime = await fetchRawMime(item.id)`. `LegacyRawMimeFetcher` is an injected fetcher whose real implementations do remote I/O, so a slow or unavailable source holds an open transaction — and can trip transaction idle timeouts — for as long as it takes. The per-item transaction itself is deliberate (it keeps the `mail_threads` write and the `mail_message_meta` write atomic per item, from an earlier fix) and must be preserved.

## Task

**`mailSyncJob.ts`** — split the single transaction into a short read-only prologue and the write transaction, so no long wait happens while a connection is held. Concretely:

- Move the existing prologue out of the write transaction into its own short `withTransaction`: the `Promise.all` over the three `getPropertyByKey` calls and `getItemById(mailboxesDatabaseId, payload.mailboxItemId)`, plus the "Email module schema is missing an expected relation property" check. These are read-only lookups of stable ids, so reading them in their own transaction changes nothing about the pass. Place this prologue at the **top of the `try` block — before the `mail_account_sync_state` read and before `getDecryptedCredential`** — and reuse its results in all three branches. (Consequence worth knowing: for a mailbox that has neither a schema nor a sync-state row, the schema error now surfaces before the "never connected" one. That ordering is intentional; #268 relies on the prologue being readable before any credential work.)
- Assign `mailboxProvider` from that prologue read, keeping its current purpose, and update its now-stale comment ("Set inside the transaction below…"), which describes the old placement: the `catch` block still needs it to compute the provider-aware connection-limit backoff. Keep the read of the mailbox item exactly as it is today, including the optional chaining (`mailboxItem?.properties`) — guarding a missing mailbox is #268's job, not this issue's.
- For the `imap` branch, resolve `connectionLimit` from the prologue's values and then call `imapConnectionLimiter.run(...)` **outside** any transaction, opening the write transaction **inside** the limiter's task lambda. That transaction does what it does today: build `shared`, create the IMAP client, `reconcileImapAccount`, and the `syncStatus: "ok"` write with `MAILBOX_SYNC_STATUS_ALLOWED_KEYS`.
- The `gmail_api` and `graph_api` branches do not go through the limiter: each keeps a single write transaction containing its reconcile call and the same `syncStatus: "ok"` write, now built from the prologue's already-read ids. Touching these two branches is deliberate even though the finding names only the IMAP path — the prologue they share is what moves, so leaving them untouched is not an option; their behavior is unchanged.
- Leave the `catch` block untouched — the attachment cleanup, `MailConnectionLimitError` backoff, `MailReauthorizationRequiredError` status and `recordSyncError` paths all stay exactly as they are.

**`mailLegacyEmailMigration.ts`** — move the external fetch out of the transaction:

- Call `fetchRawMime(row.id)` before `withTransaction`, then pass the resulting value into the transaction: `const rawMime = await fetchRawMime(row.id); await withTransaction(pool, (client) => migrateLegacyItem(client, row, rawMime));`.
- Change `migrateLegacyItem` to accept the already-fetched raw MIME value (the type `LegacyRawMimeFetcher` resolves to) instead of the fetcher function.
- Keep one transaction per item, and keep the existing behavior when the fetcher returns nothing.

Add tests that fail without these changes. Both belong in `backend/packages/data/src/__tests__/mailSync.test.ts`, which already exercises both the sync task and `runMailLegacyEmailMigrationJob`:

- **Migration** — wrap the pool in a thin recorder that logs every `BEGIN`/`COMMIT` its clients issue. There is no pool-wrapper precedent in `backend/` to copy and `withTransaction` is typed against `pg.Pool`, so build the recorder as a `Proxy` over the real pool (or `Object.create(pool)` with an overridden `connect`) and pass it where a `Pool` is expected; inject a `LegacyRawMimeFetcher` that appends a marker to the same log, and assert that an item's fetch marker appears before that item's `BEGIN`. Do not assert "the fetcher's own query is not blocked": a `pg.Pool` hands out other connections freely, so that holds on the unfixed code too and proves nothing.
- **Sync** — the mail sync tests already build the job with injected adapters and a real pool. Set `connectionLimit: 1` on the Mailboxes item (the property is seeded by `seedEmailModule.ts`) so that two concurrent passes for that account genuinely contend — with the default limit of 2 (`imapConnectionLimitForProvider`) they never wait and the test would pass vacuously. While the second pass is waiting for its slot, assert it holds no pooled connection: measure checked-out clients as `pool.totalCount - pool.idleCount` (`totalCount` alone counts created clients and never drops), or count checkouts and check-ins through the same kind of pool wrapper. The test pool is shared by the suite, so compare against a baseline rather than an absolute number: sample it with the first pass already in flight and nothing else running, then sample again while the second pass is waiting for its slot. With the fix the waiting pass adds 0 checked-out clients, without it exactly 1. On the current code the waiting pass holds one connection; with the fix it holds none until the slot is granted.

## Scope

### In scope

- Splitting the sync transaction into a read-only prologue plus a write transaction opened inside the limiter, in `mailSyncJob.ts`.
- Moving `fetchRawMime` outside the per-item transaction in `mailLegacyEmailMigration.ts`.
- Test coverage for both.

### Out of scope

- The limiter's own slot accounting (#266).
- Null or soft-delete handling for the mailbox item in `mailSyncJob.ts` — that is #268.
- The `catch` block's error recording, and any change to what the migration writes or to `mail_message_meta`/`mail_threads` content.

## Acceptance criteria

- A sync pass that waits for an IMAP connection slot holds no pooled database connection while it waits; the write transaction opens only after the slot is granted.
- The reconcile work for an IMAP account still runs inside exactly one transaction, and a failure inside it still rolls back and is still recorded by the unchanged `catch` block.
- The `gmail_api` and `graph_api` branches still reconcile and write `syncStatus: "ok"` in one transaction each.
- The legacy migration fetches an item's raw MIME before opening that item's transaction, and each item is still migrated inside its own transaction.
- The full existing mail test suite passes.
