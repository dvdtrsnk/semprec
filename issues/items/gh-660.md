## Behavior specification (approved)

The data layer (`backend/packages/data/src/`) holds a set of verified single-mechanism defects across the choke point, trash purge, journal, inbox tick, module data migrations, view queries, rollups, tasks, docs, blobs, the transaction runner and mail dedupe. The goal of this batch is that each of those mechanisms behaves as its own documentation already claims: the API role can create a database in production; a purge removes everything an item owns; a journal period survives the trash and purge of its item; a user's confirm is never overwritten by the tick and the tick never holds a transaction across an LLM call; data migrations convert every row exactly once without losing concurrent writes; sorted and curated views page correctly and rollup columns filter and sort; rollup sources cannot be deleted from under a rollup and recomputes serialise; task recurrence exists in the product; idempotent replays fire no create side effects; doc history never deletes an unfolded update and docs are only created for live items; a failed upload leaves no bytes behind; a failed `ROLLBACK` neither masks the real error nor returns a broken connection to the pool; duplicate property keys are a 409; item writes do not scan `project_heartbeats`; and one mail message delivered to two mailboxes is two items with independent flag state that converges with the provider in both directions. Every issue is one mechanism with its own integration tests against embedded Postgres (`testSupport/globalSetup.ts`), except the transaction-runner fix, which is unit-tested with a fake client.

## Decisions

- **Partition DDL goes through `SECURITY DEFINER` functions, not schema grants.** `create_items_partition(uuid)` / `drop_items_partition(uuid)` are owned by the migrating role with `EXECUTE` granted to `semprec_data` only; granting `CREATE` on `public` would not suffice (`must be owner of table items`) and would widen the role.
- **Purge deletes the dependents named in the audit plus `item_search_index`; module side tables wait for module hooks.** `mail_*`, `project_*`, `mcp_*`, `agent_*` rows keyed by item are listed out of scope for the pre-tenancy module-hook refactor rather than hard-coded into the generic purge.
- **A shared blob is never deleted.** The purge removes a `blobs` row and its bytes only when no other item (any partition, live or trashed) and no `mail_attachments` row references it; bytes are deleted after the purge transaction resolves.
- **The tick guard is lock-then-re-check immediately before the write, not a lock held from the read.** Locking at read time would hold the row across the LLM call; the guard (`lockUnlockedProposal` + `ifVersion`) is written so the bracketing issue reuses it unchanged as its write-side staleness check. The source-side check is the fingerprint recomputed under the write transaction; a stale result is dropped, not retried, because the edit that made it stale already enqueued a newer tick.
- **Module data migrations: `FOR UPDATE` + full replace + a second pass, progress in a new `module_migration_progress` table.** With the row locked for the batch's transaction a full replace cannot lose a write, so no key-merge is needed; a second pass with blocking locks visits rows inserted or skipped during pass 1; converters are documented as idempotent. A per-transition table replaces the single `databases.migration_cursor` column (left in place for a later contract step). The single-property type migration reuses the same `lockItemBatch` helper.
- **Sorted views page with an opaque composite keyset cursor** (base64url JSON of the sort values plus id), compiled as the standard OR-of-prefix predicate with explicit `NULLS LAST` handling, so every sort the compiler can express pages correctly.
- **Rollup recompute keeps `writeComputed`'s "never bump `updated_at`" rule.** The audit's "send an updated `updatedAt`" is dropped: the rule is a documented design decision (spurious `ifVersion` 409s) and no client consumes item invalidations yet; the announcement is moved after commit, that is all.
- **Source-property delete refusal mirrors the relation case (400 `validation_failed`, `dependentRollups`)** instead of the audit's 409 `ConflictError`, so the two refusals of the same class have one shape.
- **Task recurrence hooks into `updateItemWithClient` at one point** (Tasks database, `status: 'done'`), calling a client-scoped advance; the existing `active` row lock makes the re-entrant `done` write inside `advanceTaskRecurrence` a no-op, so no bypass flag is needed. Moving this behind module hooks belongs to the pre-tenancy epic.
- **`insertItem` keeps its signature; `insertItemWithReplay` returns `created`.** ~25 seed/test callers stay untouched; only `createItemWithClient` gates its side effects.
- **Doc history: the rebaseline boundary is id-contiguous; `expires_at` on `doc_history_updates` is not used for deletion.** Deleting expired-but-unfolded updates would lose them from every later baseline, so the rebaseline stays the only deleter.
- **`getOrCreateDoc` checks the item is live on the create path only.** An existing doc of a trashed page stays readable and writable so restore keeps working.
- **File upload keeps stream-then-dedupe (the hash needs the bytes) and makes both sides follow the commit**: cleanup of the streamed key on any transaction failure, dedup-duplicate deletion via `runAfterCommit`. No temp-key/rename method is added to `BlobStorageWriter`.
- **`withTransaction` releases with the rollback error** so `pg` discards the connection; `createPoolClientTransactionRunner` is left alone.
- **Duplicate property key maps to the existing `ConflictError`** (`{ field: 'key', reason: 'duplicate' }`), with a per-store `isUniqueViolation` helper as the two existing stores have.
- **Mail identity becomes `(mailbox_item_id, message_id)` in one release, dropping `UNIQUE (message_id)` as the Task's explicitly breaking change.** Two rows with one `message_id` cannot coexist otherwise; the migration carries an `expand-contract-exemption` line and states that a rollback of that release breaks the previous release's `ON CONFLICT (message_id)` (fix-forward only). The backfill resolves the mailbox through the folder and mailbox relation edges in SQL; `NOT NULL` is a later contract step.
- **Flag observations win only over a converged state.** A pending user write keeps its desired value (the ADR's rule); a converged pair adopts the observed value and the Emails item is patched through the choke point so the state row and the item agree. IMAP re-fetches flags for known UIDs with `CHANGEDSINCE` when CONDSTORE is available, a full flag fetch otherwise; Gmail/Graph observations for known messages are a separate finding.
- **Dependency edges added for file overlap only where edits genuinely collide**: purge ← partition function (shared migration pattern), journal ← purge and replay flag (same `insertItem` branch), replay flag ← recurrence hook (same `itemWrites.ts`), bracketing ← tick guard (same handler), rollup columns and curated paging ← keyset paging (same compiler/query module), property-type migration ← data migration (shared `lockItemBatch`), flag observation ← per-mailbox identity (same ingest/reconcile files). Everything else is parallel with region-narrowed Touches (`itemsStore.ts`, `worker.ts`).

## Out of scope

- `views_one_default_per_db` allowing several default curated views per database.
- `parentItemId` validation on `createDatabase`.
- An advisory lock around the migration runner (`db/migrate.ts`).
- `migrationCompatibility.ts` blind spots (statements it does not model).
- `dbRowValidation` coverage of every row mapper (pre-tenancy epic).
- Relation endpoint pre-checks outside the write transaction.
- Module side tables keyed by item in the purge (`mail_*`, `project_*`, `mcp_*`, `agent_*`) and the module-hook refactor of the generic write path (pre-tenancy epic).
- Gmail/Graph flag observations for known messages; real IMAP/Gmail/Graph transports and mailbox onboarding.
- Dropping `databases.migration_cursor`, `doc_history_updates.expires_at`, and adding `NOT NULL` to `mail_message_meta.mailbox_item_id` (contract steps for later releases).
