## Context

Model tier rationale: Adds an existing enqueue call at the exits of one function using an established pattern, with no new contract.

Each Journal day entry caches a list of its Inbox items in `items.computed.inboxItems`, including the status of each item's processing card (`backend/packages/data/src/inbox/journalInboxCompute.ts`). The recompute job `JOURNAL_INBOX_RECOMPUTE` is enqueued on capture (`inboxStore.ts`), in the read phase of the Inbox tick (`readTickSnapshot` in `inbox/inboxTickAction.ts`) and on confirm, reject and revise (`proposalActions.ts`). The write phase of the tick, `writeTickResult` and the `writeNeedsClarification` it calls, creates or revises the card but enqueues no recompute, so the cached status of the item stays at its old value (or null) until something else touches the item. After a recompute the item of the day is announced to clients with an invalidation after commit.

#1489 adds the processing state and proposal summary to the same cache; it relies on the cache being recomputed whenever the tick writes a card.

## Task

Load `state-writes` and `testing`.

1. In `inbox/inboxTickAction.ts`, in the same transaction as each card write of the tick's write phase, call `enqueueJournalInboxRecomputeForInboxItem(client, sourceItemId)`. Cover every path that writes a card: creating a new proposal, revising an existing proposal (`reviseProposal`), and `writeNeedsClarification` (both its create and revise branches). Do not add a card-write-phase enqueue on stale skips. Preserve the independent gh-106 read/source-change enqueue, including edits and deletions.
2. Tests: after a tick that creates a card, a recompute job for the item's day is enqueued with the day's job key; same for a revised card and for a needs-clarification write; a stale-skipped write phase adds no enqueue or card write beyond the independent source trigger; running the job makes `computed.inboxItems[].status` equal to the new card status.

## Acceptance criteria

- When the tick writes a new card for an Inbox item, then a day recompute is enqueued in the same transaction and, once run, the item's `status` in `computed.inboxItems` is the card's status.
- When the tick revises a card or writes needs-clarification, then the same happens.
- When the write phase skips because the item changed or was deleted, then no additional card-write-triggered recompute or card write occurs. The independent gh-106 source-change/read-phase refresh remains; tests distinguish both phases rather than relying only on a coalesced job count.
