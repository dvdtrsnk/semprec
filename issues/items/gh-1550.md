## Context

Model tier rationale: It swaps the live-sync composition root's lifecycle factory for a dispatcher by sync mode and wires an existing IDLE lifecycle to the new transport, with existing fakes, but it is long-lived connection ownership in the api process.

The api process hosts the mail live-sync root (`createMailLiveSyncRoot`, `backend/packages/data/src/mail/mailLiveSyncRoot.ts`) from `backend/services/semprec-api/src/serve.ts`. It currently passes `createNoopMailLiveSyncLifecycleFactory(pool)`, whose `start()` only enqueues one `mailAccountSync`; the periodic sweep does the rest, so new mail appears only after the next sweep. The lifecycles for real live sync exist but are hosted by nothing: `createBoundedImapIdleLifecycleFactory` (`mail/imapIdleLifecycle.ts`) with the imapflow-backed `createImapFlowIdleTransport` (`mail/imapIdleClient.ts`), `createGmailWatchLifecycleFactory` and `createGraphWebhookLifecycleFactory`.

This issue replaces the noop factory with a dispatcher that picks the lifecycle factory by the account's `syncMode` (`imap`, `gmail_api`, `graph_api`), and hosts the IMAP IDLE one. The Gmail and Graph ones follow in #1739 and #1745; all three edit the same part of `serve.ts` and are chained.

The IDLE connections are opened through `openImapFlow`, the address-checked connect step of #1478's factory that `openImapConnection` wraps (`docs/adr/2026-10-29-imap-idle-connections-through-the-shared-imap-connect-step.md`), using the stored server settings (#1473). The sync adapter of #1510 is not reused: it returns the sync wrapper `ImapFlowMailClient`, which keeps the client private and takes no IDLE options, so the IDLE transport cannot be built on it.

Decision: an account whose sync mode has no hosted lifecycle gets the existing noop lifecycle, so the sweep keeps syncing it.

## Scope

### In scope

- The lifecycle dispatcher by sync mode and hosting of IMAP IDLE in the api process.

### Out of scope

- Gmail watch and the Pub/Sub dispatcher: #1739.
- Graph subscriptions: #1745.
- The IMAP sync adapter itself: #1510.
- Reporting sync problems to the user: #1506.

## Acceptance criteria

- When a new message arrives in an IMAP account, then a sync is enqueued from the IDLE signal without waiting for the periodic sweep.
- When an account uses another sync mode, then it still gets the noop lifecycle and is synced by the sweep.
- When the process stops, then all IDLE connections are closed before the database pool.
- When the account's host is refused by the address policy, then the lifecycle backs off and retries without taking down the process.
- When the IDLE transport opens a connection, then it is the connected client `openImapFlow` returns, built with the policy lookup and the IDLE `maxIdleTime` and `socketTimeout`; the transport itself never connects.
