## Context
Review of pull request #429 found that `dispatchGenericOperation` in `backend/services/semprec-api/src/adapter/genericBinding.ts` (currently around lines 42-43) extracts a `field` for its error response from `parsed.error.issues[0].path`, and that this loses the field for validation failures against `PropertyCreateInputSchema` (`backend/packages/shared/src/genericOperations/schemas.ts`), which is a `z.union([...])` of a non-relation member and a relation member.

`field` is not always `undefined` for this schema. Zod 4 (4.4.3 in `backend/pnpm-lock.yaml`) collapses a union failure into the single member's own issues when only one member produced non-aborting issues — e.g. `name: ""` already yields one `too_small` issue at `path: ["name"]`, so `field` is `"name"` today. A top-level `invalid_union` issue with `path: []` only arises when every member fails with an aborting issue: a wrong `type` (`invalid_value`), a missing required field (`invalid_type`), or an extra key rejected by `.strict()` (`unrecognized_keys`). In that case `issues[0].path` is empty and `field` is `undefined`, even though one member's own issues name the real field. The per-member issues are on the `invalid_union` issue's `errors: $ZodIssue[][]`, one array per member in declaration order.

Two concrete payloads (both sent with valid `databaseId`, `key` and `name`) and what Zod 4.4.3 reports for them:
- `type: "relation"`, `cardinality: "one_to_many"`, `locked: false`, no `targetDatabaseId`: the non-relation member has 2 issues (`invalid_value` at `type`, `unrecognized_keys` at `[]`), the relation member has 1 (`invalid_type` at `targetDatabaseId`). The correct field is `"targetDatabaseId"`.
- `type: "bogus"`: the non-relation member has 1 issue (`invalid_value` at `type`), the relation member has 4. The correct field is `"type"`.

Taking "the first issue with a non-empty path across all members" returns `"type"` for the first payload, which is wrong. Picking the member with the fewest issues, then that member's first issue with a non-empty path, returns `"targetDatabaseId"` and `"type"` respectively (verified against the real schema shape under Zod 4.4.3).

The same extraction is duplicated verbatim in `parseInput` in `backend/packages/application/src/genericOperationGateway.ts` (currently around lines 158-160), the path the agent tools and MCP take through `createGenericOperationGateway`'s `invoke`, so the agent/MCP path loses the field the same way. Both call sites are fixed together through one shared helper.

The existing test in `backend/services/semprec-api/src/__tests__/databasesHandler.test.ts` ("returns 400 for an unknown property type", currently around line 292) only asserts `body.error.code`, which does not catch this. The REST error envelope carries the field in `body.error.details.field` (see the `expect(body.error.details).toEqual({ field: "id" })` assertion around line 120 of the same file).

## Task
- Add one exported helper in `backend/packages/shared/src/genericOperations/` (a new file, e.g. `validationIssueField.ts`, re-exported from `backend/packages/shared/src/genericOperations/index.ts`) that takes a failed parse's Zod issues and returns the `field` string or `undefined`:
  - if the first issue is not `invalid_union`, keep today's behaviour: its `path` joined with `.` when non-empty, otherwise `undefined`;
  - if the first issue is `invalid_union`, pick the union member (from its `errors` array) with the fewest issues — the first such member in declaration order on a tie — and return that member's first issue with a non-empty `path`, joined with `.`; if that member has no such issue, return `undefined`.
- Replace the inline `field` extraction in `dispatchGenericOperation` (`backend/services/semprec-api/src/adapter/genericBinding.ts`) and in `parseInput` (`backend/packages/application/src/genericOperationGateway.ts`) with a call to that helper. Each call site keeps its existing `ValidationError` construction (message from the first issue, `{ field }` details only when `field` is defined).
- Tests:
  - a unit test for the helper covering a non-union issue with a path, a non-union issue without a path, an `invalid_union` resolved through the fewest-issues member, the tie-break, and a chosen member with no path-bearing issue;
  - in `databasesHandler.test.ts`, extend "returns 400 for an unknown property type" to assert `body.error.details` is `{ field: "type" }`, and add a case posting a relation payload without `targetDatabaseId` (with `cardinality` and `locked` present) asserting a 400 with `body.error.details` `{ field: "targetDatabaseId" }`;
  - in `backend/packages/application/src/__tests__/genericOperationGateway.test.ts`, add a case invoking `property.create` with each of the two payloads and asserting the thrown `ValidationError`'s `details` is `{ field: "targetDatabaseId" }` and `{ field: "type" }` respectively.

## Scope
### In scope
- The shared `field`-extraction helper, its use at both call sites (REST `dispatchGenericOperation` and the gateway's `parseInput`), and the tests listed in the Task.

### Out of scope
- Any other error-mapping logic in `genericBinding.ts` or `genericOperationGateway.ts`, including the error `message`, which stays the first issue's message.
- Changing `PropertyCreateInputSchema` itself (e.g. into a discriminated union).
- Naming a field for payloads where the chosen member's issues carry no path (e.g. a lone `.strict()` extra key) or where the fewest-issues member is not the one the caller meant (e.g. `type: "relation"` with `targetDatabaseId`, `cardinality` and `locked` all missing still yields `"type"`); `field` stays as the helper's rule produces it.
- Any change to how a transport serializes a `ValidationError` (e.g. `backend/services/semprec-api/src/mcp/mcpHandler.ts`, which already forwards its details as the JSON-RPC error's data, or the agent-runtime tools).

## Acceptance criteria
- `POST /api/databases/:id/properties` with `{ "key": "title", "name": "Title", "type": "bogus" }` returns 400 with `body.error.code` `"validation_failed"` and `body.error.details` equal to `{ "field": "type" }`.
- `POST /api/databases/:id/properties` with `{ "key": "rel", "name": "Rel", "type": "relation", "cardinality": "one_to_many", "locked": false }` (no `targetDatabaseId`) returns 400 with `body.error.details` equal to `{ "field": "targetDatabaseId" }`.
- `createGenericOperationGateway(pool).invoke("property.create", ...)` with the same two payloads (plus a `databaseId`) rejects with a `ValidationError` whose `details` are `{ field: "type" }` and `{ field: "targetDatabaseId" }` respectively.
- A failure whose first issue is not `invalid_union` keeps today's `field` (e.g. `name: ""` still yields `{ field: "name" }`), covered by the helper's unit test.
- The helper's unit test covers every branch named in the Task, including the tie-break and the no-path member.
- These tests fail if either call site reverts to reading only `issues[0].path`, or if the helper switches to "first issue with a non-empty path across all members".
