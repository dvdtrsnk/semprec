## Context

Model tier rationale: It adds a create hook that runs on every Event insert from every write path (REST, Semp, MCP, Inbox confirm), so an ordering or cardinality mistake breaks Event creation across the product.

#1600 gives each tenant a `calendars` database with one default calendar and links every existing Event to it through the single-valued relation `Events.calendar`. Events created afterwards have no calendar. The choke point offers a per-process registry of item-create hooks (`chokePoint/hooks.ts`, `registerItemCreateHook`, registered in `backend/packages/data/src/domainWriteHooks.ts`; `docs/adr/2026-10-09-item-create-domain-hooks.md`), which runs inside the insert's transaction after a real insert and never on an idempotency-key replay. A calendar edge written there is committed or rolled back together with the Event.

This issue makes every new Event belong to exactly one calendar: the default calendar unless the caller chose another. A caller that chooses its own calendar (the invitation answer of #1944, the atomic Event create of #1777) creates the Event through a helper that passes the choice to the hook.

Decision: the hook adds the default calendar only when the Event has no `calendar` edge at that moment in the same transaction; an edge written before the hook runs (for example by relations given at creation) wins and the hook does nothing.

Decision: if the tenant has no `calendars` database yet (the cutover of #1600 has not run), the hook does nothing, so Event creation never breaks during a rollout. If the database exists but has no live default calendar, the write fails with a server error and a log line; the invariant is guarded by #1778.

Decision: the chosen calendar must be a live calendar whose `kind` is empty or `own`; a system or subscription calendar, a trashed one, an unknown id or an id of another tenant is rejected with 400 `validation_failed` (field `calendarId`).

Shared-file ordering: this issue also waits for #1757 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `backend/packages/data/src/calendar/defaultCalendarCreateHook.ts` exporting `defaultCalendarCreateHook: ItemCreateHook`. It applies only to the Events database. It resolves the Calendars database (`getDatabaseByModuleId`), returns when there is none, returns when the new Event already has a `calendar` edge, and otherwise creates the edge with `createRelationWithClient` on the `Events.calendar` property to the chosen calendar (see step 2) or to the live calendar with `isDefault` true.
2. In the same file export `withChosenCalendar(calendarId, fn)` (an `AsyncLocalStorage` scope, the mechanism `runInTenant` already uses) and `createEventInCalendar(client, input, calendarId, options?)`, which runs `createItemWithClient` for an Event inside `withChosenCalendar`. The hook reads the scope and validates the calendar as decided above.
3. Register the hook in `backend/packages/data/src/domainWriteHooks.ts`.
4. Export `createEventInCalendar` from `backend/packages/data/src/index.ts` and from the frozen list in `backend/packages/data/src/__tests__/publicSurface.test.ts`.
5. Tests: an Event created through the generic endpoint, through Semp's generic operations and through the Inbox confirm path gets an edge to `Personal`; `createEventInCalendar` with `Work` gives exactly one edge, to `Work`; an Event that already has a calendar edge before the hook runs keeps it; a system calendar, a trashed calendar and a foreign id are rejected with 400 and no Event remains; an idempotent replay of a create adds no second edge; a tenant without a calendars database creates Events normally; a failed create leaves no edge.

## Scope

### In scope

- The default-calendar create hook for Events, the chosen-calendar scope and the `createEventInCalendar` helper.

### Out of scope

- The calendars database, rows and cutover: #1600.
- Guarding system calendars, colour format and the single default: #1778.
- Creating an Event together with arbitrary relations in one write: #1777.
- Changing the calendar of an existing Event: the user replaces the edge with the relation operations.
- Returning the calendar id in the timeline: #1717.

## Acceptance criteria

- When an Event is created without a calendar by any path, then it has exactly one edge to the default calendar.
- When an Event is created with `createEventInCalendar` for the Work calendar, then it has exactly one edge, to Work.
- When the chosen calendar is a system, subscription, trashed or foreign calendar, then the response is 400 `validation_failed` with field `calendarId` and no Event is stored.
- When an Event create is replayed with the same idempotency key, then no second edge is created.
- When the tenant has no calendars database, then Event creation still succeeds.
