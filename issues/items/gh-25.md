## Context

This is issue 5 of 22 in the sequential implementation queue for the Semprec project. It builds on:

- **Issue #21** (schema engine) — the generic data model (`items` / `item_relations` / property ownership `owner: user|system`) that this module is built on top of.
- **Issue #22** (views) — generic view definitions, including the "library-grid" view (card grid instead of a table).
- **Issue #24** (ten hardcoded databases) — the first concrete instantiation of the schema engine, serving as a precedent, and the issue that created the shared `blobs` table this module's cover images point into. This task is the *second* wave, but unlike #24 it does not introduce one specific database — it introduces a **generic contract** that two different concrete databases (Books, and Movies/TV) both sit on without any structural difference between them.

Books and Movies/TV are not catalog entries from the hardcoded-databases section — they are full **system projects**, the same class as Email or Personal Finance, just sharing one simple pattern: an owned DB, a card grid instead of a table, and a heartbeat process that fills in/cleans up metadata. The goal of this issue is for Movies/TV to come into being as the second concrete instantiation of the same "library module" contract, not as a separate parallel implementation next to Books.

The follow-on issue #26 (IMAP sync core) is from a completely different domain (email) and is unrelated to this task's scope — it is mentioned only because the shared blob layer (the `blobs` table from issue #24) that this issue builds on will later be reused there too (see Dependencies).

## Task

Implement a generic "library module" contract on top of the schema engine from issue #21 and populate it for two concrete domains — Books, and Movies/TV — as two instances of the same pattern, not two separate solutions. Specifically:

1. **Use of the shared blob layer** (the `blobs` table, which exists from issue #24) for real binary content (here: cover images), replacing the current simplification of "deterministically generated hex color as a placeholder cover."
2. **Row-level status and lock** for automation over items — replacing the ad-hoc, user-toggleable boolean checkbox that used to serve simultaneously as a status flag and an informal lock, and that had no way to represent an error.
3. **A single path for adding an item** — both UI and AI (agent) create items through the same generic create-item endpoint; no special path for AI.
4. **Definition of the generic "library module" contract** — a named set of property slots that each concrete domain (Books, Movies) fills in with its own keys and ownership semantics (`owner: user` vs. `owner: system`).
5. **Ratable relation** — a rating that belongs to the relationship between two entities (Movie ↔ Person), not to either side of the relationship, stored as metadata on the edge in `item_relations`.
6. An open point to record (not to design in detail within this issue): heartbeats as a general consistency tool across system projects, beyond metadata enrichment.

### Blob layer for cover images

The shared `blobs` table **already exists from issue #24** (created there as the prerequisite for the Files database; it is not library-specific and will later also serve email attachments). This issue introduces no blob DDL — it only stores cover images through the existing table. `content_hash` is nullable there; for cover images in this issue it's enough that the column exists — enforcing dedup logic for this specific use case is not part of the scope.

The `cover` property is of type `image`; its value in `properties` is `{ blobId }`. Until the heartbeat finds/downloads the image, the UI shows a placeholder — a solid color plus an emoji glyph (`coverGlyph`) remains as the fallback for the missing state, not as the target design.

### Row-level status and lock — replacing the ad-hoc checkbox

The previous `processedByHeartbeat` was a plain, user-toggleable boolean that simultaneously signaled status *and* acted as an informal lock, and did not handle error states at all (the heartbeat would only skip "unprocessed," never "processed incorrectly"). Replace it with a dedicated table, not a generic property:

```sql
-- No Postgres FK to items(id): items (issue #21) is PARTITION BY LIST (database_id)
-- with composite PK (database_id, id), so a bare REFERENCES items(id) cannot be
-- expressed — the same constraint already documented and worked around in
-- item_relations (0001), task_recurrence and view_items.item_id (0002/0004), and
-- docs.item_id (0003). item_automation follows the same established pattern:
-- item_id is a plain indexed uuid with referential integrity enforced at the
-- application layer, not by Postgres.
CREATE TABLE item_automation (
  item_id uuid PRIMARY KEY,
  status text NOT NULL DEFAULT 'pending',   -- 'pending' | 'done' | 'error' | 'locked'
  error text,                                 -- detail of the last error, only when status = 'error'
  attempts integer NOT NULL DEFAULT 0,
  last_attempt_at timestamptz
);
```

Rules:

- The heartbeat processes rows where `status IN ('pending', 'error')` — not just "not done" but also "finished incorrectly." Previously such an error would silently fall into a no-op.
- `locked` is the only status the heartbeat may never set or leave on its own — it is an explicit, permanent "hands off," settable only by the user (or by an AI with the appropriate permission in that project's `AGENT.md`).
- On success the heartbeat sets `done`; on failure it sets `error` plus the reason text in `error` and increments `attempts`.

**Retry policy:** a new job in the queue (`graphile-worker`) with `max_attempts: 3` — the first three attempts run in quick succession, with graphile-worker handling the backoff between them itself (its built-in exponential backoff, no custom logic). When the third attempt also fails, the job ends up permanently failed and `item_automation.status` stays `error`. From there, a separate daily heartbeat takes over (a plain time trigger, no event needed) that once a day walks all rows with `status = 'error'` and re-schedules a fresh batch for each one (a `TASK_NAMES.libraryMetadata` job, using the `jobKey` dedup pattern `library-metadata:${itemId}`) — i.e. up to 3 more attempts, once a day, until it either succeeds (`done`) or the row is manually locked by a user/authorized AI (`locked`). `attempts` thus becomes a cumulative counter across the whole history for observability, while the decision of "retry within this batch or not" is left to the queue engine, not to custom logic layered over the same field.

### Adding an item — UI and AI, the same path

The library-grid view gets its own "+ Add" button wired to the same generic create-item endpoint (issue #21) that the regular table and the AI's MCP tool also use. No special extra path for AI — the AI calls the same API as the user, and that project's `AGENT.md` (the same mechanism as for every other project) tells it exactly what it's allowed to do: typically create an item with a name, never write to `owner: 'system'` fields (`cover`, external ratings) — those remain reserved for the heartbeat process regardless of who requests the write.

### The generic "library module" contract

A set of named slots that each concrete domain fills in:

- **coverKey** — a property of type `image`, `owner: system` (see blob layer above).
- **subtitleKey** — a property shown under the title on the card (author for Books, year for Movies).
- **ratingKey** — the primary, purely user-entered rating; the heartbeat never touches it.
- **secondaryRatingKey / secondaryRatingLabel** — an optional external rating (e.g. a critics'/ČSFD-style rating for Movies), `owner: system`.
- **sourceUrlKey** — an optional link to the source page (`type: url`, `owner: system`); present for Movies, not present for Books.
- **statusKey** — a user-facing status pill (reading/watching status).
- **coverGlyph** — an optional emoji overlay fallback while `cover` is missing.

`processedKey` from the previous model goes away — its role is taken over by `item_automation.status`. The heartbeat action is a single generic type, `processLibraryMetadata`, driven by a config object (what the data source is, how it maps onto `coverKey`/`ratingKey`/etc.), not a separate action per module.

Movies/TV is the second concrete instantiation of the same contract — in addition to what Books use, it also uses `secondaryRatingKey` and `sourceUrlKey`. "Movie" vs. "Series" remains just a label next to `statusKey`, with no dedicated season/episode structure — an in-progress series is tracked as free text in notes, unchanged. The one deviation from the previous (mock) model: `year` must be `type: number`, not text — it needs to be sortable and filterable as a range.

### Ratable relation — the rating belongs to the relationship, not to either side

Movies have an additional "Watched with" → People relation, where each person also carries their own 1–5 star rating. This rating belongs directly in the value of the relationship, not as a property on the movie or on the person: `{ rating: 4 }` in `item_relations.metadata` (issue #21) on the specific edge between a Movie and a Person. It is written by the owner of the movie (you), not by the person themselves — it's a record of "how it went for me / for them," not an authenticated third-party rating. This structured data (rating on the edge, not free text) is meant to eventually make it possible to infer specific people's taste and recommend based on it — the aggregation/recommendation itself is not being built now, but the model must not block it: it should be a plain query over `item_relations.metadata` grouped by person.

### Open point — heartbeats as a general consistency tool

This is **not** part of the implementation scope of this issue, just a point to record in the backlog: `processLibraryMetadata` is only one concrete case of a heartbeat action. The future intent is to also use heartbeats to enforce best practices and consistency across system projects generally, not just metadata enrichment — this remains undesigned, no concrete API/schema is proposed in this issue.

Similarly open: the concrete metadata source for Movies in production (candidates are TMDb/OMDB — there is no public API for the ČSFD-style rating source) is an open question, not a decision of this issue; for implementation it's enough that `processLibraryMetadata` is designed configurably (a config object determines the source and the mapping), so swapping the source doesn't require a change to the contract.

## Scope

### In scope

- A property of type `image` with value `{ blobId }` over the existing `blobs` table (issue #24), wired to `coverKey`.
- The `item_automation` table (status/lock/error/attempts) and its wiring into the heartbeat queue.
- Configuration of the `graphile-worker` job `TASK_NAMES.libraryMetadata` with `max_attempts: 3` and the `jobKey` pattern `library-metadata:${itemId}`.
- A daily time-triggered heartbeat that re-queues rows with `status = 'error'`.
- A generic create-item endpoint wired to both the library-grid view and the AI's MCP tool (no special AI path).
- Definition and documentation of the generic "library module" contract (the seven named slots above).
- Concrete instantiation of the contract for Books and for Movies/TV, including the `owner: system` vs. `owner: user` distinction at the level of individual properties.
- Changing the `year` property's type to `number`.
- `item_relations.metadata` carrying `{ rating }` for the Movie–Person relation.
- Placeholder fallback (color + `coverGlyph`) while `cover` is missing.

### Out of scope

- The concrete choice and integration of an external metadata source for Movies (TMDb/OMDB, etc.) — only a configurable slot, not an actual integration.
- Aggregation/recommendation derived from ratable relations (data model only, no query/analytics layer).
- Extending heartbeats to general best-practice enforcement across system projects — remains an open backlog point.
- Season/episode structure for series — remains free text in notes.
- Anything from the IMAP sync core (issue #26) — the blob layer is only established generically here; wiring it to email attachments is out of scope for this task.
- Dedup logic over `content_hash` for cover images (the column exists, but enforcing dedup behavior for this specific use case is not addressed here).
- Heartbeats as `AgentTool` (`heartbeat.list`/`heartbeat.trigger`/`heartbeat.history`) — that is general infrastructure handled elsewhere in the sequence (heartbeat engine/AgentTool layer); this task only relies on it as an already-existing mechanism, it does not introduce it.
