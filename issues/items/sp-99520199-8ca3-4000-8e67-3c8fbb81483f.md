## Context

Model tier rationale: Changes the shared mail thread classification every list, count and thread action reads, the IMAP move planning of a message held in two folders, the flag observation of the IMAP pass, the SMTP send path's Sent-copy timing and the IMAP IDLE connection, each with exactly-once and lock-order constraints.

End-to-end test of the dev server against a real Purelymail account (IMAP `imap.purelymail.com:993`, SMTP `smtp.purelymail.com:465`). The account sends only from itself, so every test mail is self-addressed (From = To = the account).

- F13: `POST /api/mail/threads/:threadId/read` `{read:true}` and `/flag` `{flagged:true}` answer 200 for a self-addressed message in INBOX, but nothing is written: `mail_message_flag_sync_state.desired_state` stays false and IMAP never gets `\Seen`/`\Flagged`.
- F14: `POST /api/mail/drafts/:id/send` takes 3.3–4.1 s.
- F15: a new INBOX message became visible in `GET /api/mail/threads` only after 22–25 s while IMAP IDLE live sync ran.
- F18 (v0.3.1): `/archive` and `/trash` move the self-addressed message on IMAP, but `/restore` answers 200 and the message is afterwards in neither INBOX nor Archive.
- F16: after a reply (`POST /api/mail/drafts` `{mode:"reply"}`, then `/send`) the original thread did not show ≥3 messages (original in INBOX + Sent copy + reply) within 180 s, and no "Re:" thread did either.

Reproduced with a fake IMAP account (`testSupport/fakeImapAccount.ts`, an in-memory `ImapMailClient` with folders, UIDs, flags, APPEND and MOVE) driven through the real draft, send, sync-pass and thread-action entry points:

- A message Semprec sends to its own account is one Emails item: the send's claim row, the Sent copy the saver appends and the copy the server delivers to INBOX share one Message-ID and converge per mailbox. The item has two folder edges carrying UIDs, Sent and INBOX.
- F13 root cause: the thread actions and the thread list's `unread` classify a copy as incoming only when `NOT own AND NOT has_sent` (`mailThreadActions.ts`, `mailThreadCopyCtes`). Mail to oneself is both own (sender is a mailbox address) and in Sent, so read and flag select nothing and still answer 200; the list never shows it unread. Archive, trash and restore refuse it with 409 `mail_move_source_unverified` because the IMAP move source must be the only edge with a UID. The item's flags also flip with whichever copy a pass observes last; the Sent copy is `\Seen`, so the delivered unread message reads as read after every pass.
- F18 root cause: restore sends a copy that is not received to Sent. A message to oneself that the server delivered and another client kept no Sent copy of is, once trashed or archived, the user's own (sender is a mailbox address) and in no Inbox, so restore moves it to Sent. The folder it left is not kept: a completed move replaces `source_evidence` with the new location.
- F16: threading is correct. The reply resolves to the original thread through `In-Reply-To`/`References`, and both copies of each message converge on one item, so the original thread holds exactly two messages (original, reply), each in INBOX and Sent; no separate "Re:" thread exists. The expected "≥3" counted the Sent copy as a message of its own. Covered by a regression test; no code change.
- F14 root cause: the send request is synchronous by design (`docs/architecture/domain-mail-and-inbox.md`, Sending: claim → provider send → finalization, failures answered as 4xx, no automatic retry). Within it, the SMTP transport submits, closes, and only then opens a new IMAP connection (TLS, LOGIN), appends the Sent copy and logs out, all in sequence. At ~150 ms RTT each connection setup costs about a second.
- F15: the IDLE connection's client is imapflow with its default `autoIdleDelay` of 15 s, so after every connect (and every reconnect) IDLE starts 15 s after the SELECT; a server sends EXISTS for a delivery only inside IDLE (or in a command response), so a message delivered in that window is reported up to 15 s late, and the pass that follows adds its own connect-and-fetch time. Signal → enqueue is immediate (no debounce); the job key gives one follow-up pass while one runs. Purelymail's own IDLE push timing and its delivery delay cannot be measured without the real server.

Decisions:

- A copy is **received** when it is in an Inbox or Junk folder, when it has its own copy beside a Sent copy that carries a UID (an IMAP server keeps mail to oneself twice), or when its sender is no mailbox address of the tenant and it is in no Sent folder. `mailThreadCopyCtes` exposes it as `received`; the thread list's and the summary's `unread` and every thread action's `incoming` use it (actions still exclude Drafts copies). Only the Sent copy of mail to oneself is the user's own.
- Read and flag answer truthfully: `read:false` and `flagged:true` on a thread without a received message are 409 `mail_thread_no_received_message` with nothing written; `read:true` and `flagged:false` with nothing to change stay 200 no-ops.
- An IMAP move of an item that is also in another folder takes the one provider message outside Sent and keeps the Sent copy's edge with its UID; archive and trash of mail to oneself move the delivered copy, restore brings it back to INBOX (received), the Sent copy stays in Sent. One desired move per item stays the model.
- A flag observation of the Sent copy is ignored while the item has a copy with a UID in another folder: the item's `read`/`flagged` follow the delivered copy. `applyObservedMailMessageFlags` takes the observed folder.
- Sending stays synchronous and exactly-once (claim unchanged). The IMAP connection for the Sent copy opens while SMTP submits; APPEND runs only after the server accepted the message; on a refused submission the opened connection is closed without an APPEND before the error is answered.
- An archive or trash desire records `restore_purpose` (`inbox` or `sent`, the folder the copy leaves; kept from an earlier desire when it leaves neither) on `mail_message_move_sync_state`; restore returns a copy there and falls back to received → Inbox, own → Sent without a record.
- The IDLE connection enters IDLE as soon as its folder is selected (`autoIdleDelay` 0 on that connection only, which issues no other command), so no load is added.

## Acceptance criteria

- Against the fake IMAP account, `read:true` on a self-addressed thread sets the item read, records `desired_state` true and the next pass STOREs `\Seen` on the INBOX UID; `read:false` answers `unread:true`; `flagged:true` STOREs `\Flagged`; the list shows the self-addressed thread unread while its delivered copy is unread, also after a pass re-observes the `\Seen` Sent copy.
- `read:false` and `flagged:true` on a thread of sent mail only are 409 `mail_thread_no_received_message` and write nothing; `read:true` and `flagged:false` there stay 200.
- Archive and trash of a self-addressed thread move the INBOX copy on the server and keep the Sent copy and its edge; restore brings it back to INBOX.
- Mail to oneself delivered to INBOX only, trashed or archived and then restored, is back in INBOX on the server and nowhere else.
- A reply to a self-addressed message lands in the original thread, which then lists two messages, each in INBOX and Sent.
- With an SMTP and an IMAP endpoint of the same latency, a send finishes in about one connection setup less than before; the APPEND never runs for a refused submission and the IMAP connection is closed on every path.
- The IDLE transport reports a message delivered right after it connected within a second, not after imapflow's 15 s auto-IDLE delay.
- The existing mail test files stay green.
