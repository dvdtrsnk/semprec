## Context

`recomputeRollupCell` in `backend/packages/data/src/rollup/recompute.ts` (lines 91-134) recomputes one rollup cell on a plain `pool.connect()` client: the aggregation `SELECT` (lines 107-114), the `writeComputed` (line 117) and the `getItemById` for the announcement (line 121) each autocommit separately, with no lock on the target item. Two defects:

1. **An older job can land after a newer one.** Every triggering write enqueues a per-cell job under the same job key (`rollupRecomputeJobKey`), which replaces a *pending* job but not one already running. When job A (from an older write) is running its aggregation while job B (from a newer write) starts, B can read the newer state, write it, and then A writes its older aggregate over it — the cell then holds a stale value until the next write to any source row. Nothing serialises the two.
2. **One malformed date fails the whole job.** `aggregationSql` for `earliest`/`latest` (lines 83-86) casts `(t.properties ->> $3)::timestamptz` with no guard, unlike `sum`/`avg`/`min`/`max` (lines 76-78) which pre-filter with a regex. A single source row holding `"tomorrow"` (a `date` property is a JSON string, nothing validates it at write time) makes the query throw `invalid input syntax for type timestamp with time zone`, graphile-worker retries three times (`maxAttempts: 3`) and gives up, and the cell stays at its previous value indefinitely.

`writeComputed` deliberately never advances `items.updated_at` (`itemsStore.ts`, lines 377-383: a background recompute must not cause a spurious `ifVersion` 409); the announced `updatedAt` therefore does not change on a recompute, and this issue keeps that contract (see Out of scope).

## Task

1. `recomputeRollupCell` runs inside `withTransaction(pool, ...)`: first `itemsStore.lockItemById(client, rollupProperty.databaseId, itemId)` — if it returns `null` (target purged) return without writing — then the dependency/property loads, the aggregation `SELECT`, `writeComputed`, and `runAfterCommit(client, () => notifyInvalidation({ scope: 'item', databaseId, itemId, op: 'update', updatedAt: locked.updatedAt }))`. The `FOR UPDATE` on the target row serialises two jobs for the same cell: the second one blocks until the first commits and then aggregates the current state, so the last committed value is always computed from the newest source state. Replace the comment at lines 118-120 accordingly.
2. `aggregationSql` `earliest`/`latest`: guard the cast the way the numeric branch does — `min((CASE WHEN (t.properties ->> $3) ~ '^\d{4}-\d{2}-\d{2}(T[\d:.+\-Z]*)?$' THEN (t.properties ->> $3)::timestamptz END))` (same for `max`), so a value that is not an ISO 8601 date/date-time is ignored instead of failing the query. Put the regex in one module-level constant shared by both branches and comment that a garbage date contributes nothing, exactly as a garbage number does for `sum`.
3. Tests in `backend/packages/data/src/__tests__/rollup.test.ts` (integration): (a) `latest` over three children where one holds `"tomorrow"` computes the latest of the two valid dates and the job succeeds on its first attempt; (b) serialisation — hold `SELECT ... FOR UPDATE` on the parent row from a second connection, start `recomputeRollupCell` (it must block: assert it has not resolved after 200 ms), change a child's value through the choke point on the second connection, release the lock, and assert the cell holds the aggregate including the change; (c) a recompute for a purged target item (delete the row directly) returns without throwing and writes nothing.

## Scope

### In scope
- The transactional, row-locked recompute; the guarded date cast; the tests.

### Out of scope
- Advancing `updated_at` on a computed write or adding a separate computed-version token to the invalidation event: `writeComputed`'s "never bump the `ifVersion` token" rule is a documented design decision (`itemsStore.ts`, lines 377-383) that this batch does not reverse; a client that needs to refresh rollup cells on invalidation has to refetch regardless of `updatedAt` (no client consumes item invalidations yet).
- Reading rollup values in view filters/sorts (sibling issue C8) and the source-delete guard (C9).
- `backfillRollup`'s paging.

## Acceptance criteria

- When two recompute jobs for the same cell overlap, the value stored after both commit is the aggregate of the source state at the time the later one ran.
- When a source row holds a non-ISO string in the aggregated date property, `earliest`/`latest` ignore it and the job completes on its first attempt.
- When the target item no longer exists, the job returns cleanly (no error, no retries).
- The invalidation for a recomputed cell is announced only after the transaction commits.
