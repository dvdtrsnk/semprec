## Context

This is the harvest itself (epic #565, Part 1): the script the daily `harvest-review-followups` GitHub Action runs. It collects the code-review bot's open findings from merged pull requests into one **harvest issue** labelled `followups:ready`, which Relay's triage workflow then picks up. It is deterministic and uses no AI. Every decision is already implemented and tested elsewhere, and this script only fetches, calls, renders and writes:

- #569 `markers.mjs`: `LABELS`, `renderHarvestMarker(prs)`, `renderFindingMarker({ pr, key })`, `computeLedger(issues)`;
- #570 `records.mjs`: `validateFindingRecord`, `renderHarvestBlock({ prs, findings })`;
- #572 `memory.mjs`: `selectMemoryComment(comments)`, `decodeMemory(body)`, `parseMemory(value, prNumber)`;
- #573 `github.mjs`: `clientFromEnv`, and the endpoints `listIssuesWithLabel`, `listIssueComments`, `listMergedPullRequests`, `listReviewThreads`, `listTreePaths`, `createIssue`, `addLabels`, `closeIssue`;
- #575 `select.mjs`: `pendingWork`, `candidatePullRequests`, `classifyPullRequest`, `createHarvestPlan` (cap 30);
- #576 `hints.mjs`: `hintsApi(client)`, `computeHints(api, { pr, mergedAt, base, findings })`.

The approved behavior this script must deliver:

- **Backpressure.** Write nothing while work is pending.
- **Floor.** Only pull requests from the fixed floor up: `HARVEST_MIN_PR`, set to 266 in the workflow, because #265 audited everything up to #264.
- **Undecodable memory.** A trusted memory that cannot be decoded fails the whole run before any write, naming the pull request. A human then fixes the harvester, or labels that pull request `followups:harvested` by hand to skip it.
- **Issue before labels.** The harvest issue is created first, and only then are the pull requests labelled `followups:harvested`. A crash in between re-labels on the next run instead of losing findings, because the pull requests are in the issue's harvest marker.
- **Record-only issue.** When a run finds only skipped findings (a resolved thread with the bot's exact `Fixed.` reply), it still records them: in a harvest issue that is closed at once and has no `followups:ready`. Their markers keep them out of every later harvest.
- **Body limit.** A body over 60,000 characters (GitHub's limit is 65,536) fails the run before any write.
- **`dry_run`.** A run with `dry_run` reports exactly what it would write and writes nothing.

## Task

Create `.github/scripts/review-followups/harvest.mjs`, a zero-dependency ES module and CLI with a header comment describing the run and its environment variables:

1. Export `runHarvest(api, { minPr, dryRun })`. `api` bundles the #573 endpoints listed above, bound to a client, plus the four functions of `hintsApi`. It returns a report object. Steps, in this order:
   1. **Backpressure.** Call `pendingWork` on the open issues labelled `followups:harvest` or `followups:issue`. If anything is pending, return `{ pending: [...] }` without any other call.
   2. **Ledger.** Call `computeLedger` over every issue, in any state, labelled `followups:harvest` (with its comments) or `followups:issue`. Then call `listTreePaths("develop")`.
   3. **Scan.** For each pull request of `candidatePullRequests(listMergedPullRequests("develop"), { minPr })`, in order:
      - if its number is in `ledger.harvestedPrs`, offer it as `alreadyRecorded`;
      - otherwise read its comments, select the memory comment, and decode and parse it. On any error, throw an `Error` naming the pull request, before any write;
      - read its review threads only when an open finding not in the ledger has a numeric `discussionId`;
      - classify it and offer it to the plan; stop at the first `"stop"`.
   4. **Hints.** For each pull request with harvested findings, call `computeHints` with `base: "develop"` and add the two hint fields to its records. Every record must pass `validateFindingRecord`.
   5. **Render** (see 2 below). Throw when the body exceeds 60,000 characters.
   6. **Write**, unless `dryRun`:
      - with harvested findings: create the issue with labels `followups:harvest` and `followups:ready`;
      - with only skipped findings: create it with `followups:harvest` only, then close it;
      - with nothing: create no issue;
      - then, and only then, add `followups:harvested` to every pull request in the plan's `prs` and `labelOnly`.

   The report is `{ pending, scanned, prs, labelOnly, harvested, skipped, stoppedAt, issue }`. `issue` is `{ number }` of the created issue, or, in a dry run, `{ title, bodyLength }` of the one that would be created, or `null`.
2. The harvest issue. The **title** is `Review follow-ups: <N> finding(s) to triage from PR #<first>–#<last>` (`from PR #<n>` for a single pull request). A record-only issue is titled `Review follow-ups: nothing to triage from PR #<first>–#<last> (<M> fixed on the PR)`. The **body**, in this order:
   - the harvest marker for the plan's `prs`, on the first line;
   - one sentence saying the issue was collected by `.github/workflows/harvest-review-followups.yml` and is triaged by Relay's `triage-review-followups` workflow;
   - `### Findings to triage (<N>)`: a table of PR, severity, category, `path:line` and description;
   - `### Skipped — fixed on the pull request (<M>)`: a table of PR, `path:line` and description, or `None.`;
   - one finding marker per harvested and skipped finding, each on its own line;
   - the data block from `renderHarvestBlock({ prs, findings })`.

   In table cells, `|` is escaped as `\|`, newlines become spaces and `<` becomes `&lt;`, so no text from a finding can form a marker line.
3. Export `main(env, api)`, called with `process.env` only when the module is executed directly. It reads `HARVEST_MIN_PR` (required, a positive integer) and `DRY_RUN` (required, exactly `true` or `false`), and builds `api` from `clientFromEnv(env)` when `api` is omitted. It prints the report as readable lines. It appends the same report as Markdown to the file named by `GITHUB_STEP_SUMMARY` when that variable is set. It exits 1 on any error.
4. `harvest.test.mjs` next to it (`node:test`, `node:assert/strict`, a fake in-memory `api` recording every write), covering every Acceptance criterion below.

## Scope

### In scope

- The orchestration, the harvest issue's title and body, the write order, dry-run, the report and job summary, with tests.

### Out of scope

- The workflow file, its schedule, permissions and the creation of labels. That is a maintainer-implemented issue in this batch.
- Any change to the selection rules, the cap, the hints or the formats. Those belong to the modules this script calls.
- Triage. That is Relay's workflow, fed by this issue's output.

## Acceptance criteria

1. With an open `followups:harvest` issue, or an open issue carrying `followups:issue` and `spec:proposed`, `runHarvest` returns `pending` with that number and makes no call other than the two open-issue listings.
2. Pull requests below `minPr`, or already labelled `followups:harvested`, are never read.
3. A pull request whose trusted memory comment does not decode makes `runHarvest` reject with an error naming that pull request, and the fake records no write.
4. With findings on three pull requests (12, 15 and 5 harvested), the created issue holds the first two pull requests' 27 findings, carries `followups:harvest` and `followups:ready`, and only those two pull requests are labelled `followups:harvested`. The third is neither read beyond the plan nor labelled.
5. The issue is created before any pull request is labelled. When `createIssue` throws, no pull request is labelled.
6. A pull request listed in an existing harvest issue's harvest marker is labelled and contributes no finding. A finding already marked in any harvest issue is not harvested again.
7. With only skipped findings, the created issue carries `followups:harvest` only, is closed, and lists the skipped findings in the Skipped table with one finding marker each. With no finding at all, no issue is created and the scanned pull requests are labelled.
8. The body's first line is the harvest marker for the taken pull requests. Each harvested and skipped finding has its marker on its own line. `parseHarvestBlock` (#570) applied to the body returns the harvested records, hint fields included.
9. A finding description containing `|`, a newline and `<!-- crb-followup:v1 pr=1 key=0123456789 -->` renders in the table without breaking the row. `parseFindingMarkers` (#569) on the body finds no marker for `pr=1`.
10. A plan whose rendered body exceeds 60,000 characters makes `runHarvest` reject before any write.
11. With `dryRun: true`, the fake records no write, and the report's `issue` gives the title and body length that would have been created.
12. `main` rejects when `HARVEST_MIN_PR` is missing or `0`, or when `DRY_RUN` is `yes`. With `GITHUB_STEP_SUMMARY` pointing at a temporary file, it appends the report to it.
13. `node --test .github/scripts/review-followups/harvest.test.mjs` passes with no network access.
