## Behavior specification

Semp on pages and Journal: tools, write policy, change list and weekly tidy tick.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: semp-pages-1

#### (a) Decisions adopted
- Semp page write policy: direct or proposal? -> Direct block insertion authored `ai_agent`; `page.replace` and deletions require approval until version restore exists (the design note's recommendation) -> insertion is additive and attributable.
- Journal for Semp: page-family operation (a) or module agent tools (b)? -> (a), `page.ensureJournalPeriod` plus page.get / page.insert -> module tools are not composed into sessions yet.
- Version restore authorship -> `user`, forward update on the live document, never rewriting history -> design note point 3.
- Whether to relax `page.replace` approval after restore exists -> Decided by the product owner: no; `page.replace` keeps requiring approval also with version restore, because it is a large destructive change (#1400, #1844).
- Which project owns the weekly cleanup tick -> the system project "Semprec" -> no Journal project exists and Journal is a system database.
- Duplicate journal entries: merge or only prevent? -> Decided by the product owner: the assistant prevents duplicates and only proposes a merge for approval; a merge changes links, so it must never run silently. The merge function (#1726: the oldest entry survives, the duplicate is trashed and recoverable for 30 days) runs only through an approval-gated operation (#2017); the weekly tick finds duplicated periods and lets the assistant propose them (#1883).
- Project notes in the prompt -> separate delimited user-data block, 32 KiB limit, truncated at a block boundary with subpage list -> design note point 1, injection-safe framing.
- "What Semp changed" list authorship -> reports stored `created_by` values (#1680).
- Which author is recorded for user-confirmed proposal writes? -> Decided by the product owner: the user, because confirming makes the write the user's decision, with the note "proposed by Semp" recorded on the Inbox card (per-step block ids, #1648); user-confirmed proposal blocks are stored as `user`, so the AI-agent filter of the change list shows only what Semp wrote on its own (#1400, #1680; the confirm paths are switched by #1681 and #1981).
- Should the tick be able to delete a Journal property? -> Decided by the product owner: no; user-owned properties on system collections are excluded, so the tick has nothing to delete (#1883).

#### (b) Open questions for the product owner
- None.

#### (c) User-visible behavior
Semp can read pages as Markdown with subpage and block references, insert text into any page it has write access to (including a journal day or week, creating it when missing), and a page can be restored to an earlier state within 30 days. Writes respect per-project database permissions and sensitive-database defaults; replacing or deleting content needs the user's approval. A project's notes are part of what Semp knows when working on the project. The user can ask what Semp changed on a page (only what Semp wrote on its own; text the user confirmed from a proposal counts as the user's), and every Sunday at 21:00 Semp tidies the journal: proposes merging duplicate entries for the user's approval, adds the missing week summary and links calendar events in the day's text.
