## Behavior specification

Block editor and pages over HTTP: block model, atomic ops, Markdown, realtime.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions for job block-editor-1

#### (a) Decisions adopted from open questions

- Block order in `doc.getArray('order')` or fractional index? -> top-level `Y.Array` of ids (flat, hierarchy via indent) -> top-level shared types merge by name; a concurrently created root `Y.Map` loses one side; also the design note's recommended option. The ADR (block-model issue 1) records the rejected fractional index.
- Indent of text, headings and quotes: forbid or preserve? -> preserve in the model (indent 0-5 on every type); the Markdown format carries it for non-list blocks in a `<!-- semprec:block ... -->` comment -> the acceptance criterion requires a `text` block to read back with indent 5, so forbidding it in the model contradicts it; lossless is the conservative choice.
  -> Decided by the product owner: indent 0-5 on every block type; one general model without per-type exceptions.
- Page operations: generic catalog or custom routes in the docs manifest? -> generic catalog (one operation per issue) -> the design note's recommendation; reads and writes of a page are item sub-resources needed on REST, MCP and agent tools alike.
- Where the shared block module lives -> left to the ADR (root-level workspace shared with web/, or a module outside backend/); constraint stated: no `pg` or Node-only dependency. Issues use the placeholder "block model module directory fixed by the ADR" in Touches.
- Empty document -> read as one synthetic empty text block (`id: null`), nothing written until the first real insert, so reads stay side-effect free.
  -> Decided by the product owner.
- Order tie-break for blocks missing from `order` -> ascending id (deterministic across clients).
- Splitting a block (Enter) -> the new block keeps type and indent, `done` false.
  -> Decided by the product owner.
- Operations involving a `page` block (set type to/from page, duplicate a page, merge) -> refused with typed errors in the pure module; handled by the subpage issues.
- Existing docs sweep -> not planned; the ADR records that read-time normalization suffices because production has no docs.
- `last_edited_*` backfill -> not built (no docs in production; no-speculative-generality ADR).
  -> Decided by the product owner: production has no documents, read-time normalization is enough; no migration or backfill of existing documents (#1366, #1405).
- Doc invalidation throttle -> new per-(tenant, docId) module in `@semprec/realtime`, 1 s leading + trailing, derived from the existing `doc_update` message; the per-socket coalescer is not extended.
- Markdown line-start escaping (`16\. 10.`) -> adopted as required by the source; the WebView editor must adopt it.
- Markdown-format text property -> `config.format = 'markdown'` on `text`/`longText`, validated with `parseMarkdown({allowPage: false})` on item create/update; the only property switched on here is the Inbox card `text`; existing values are not rewritten.
  -> Decided by the product owner: Markdown format only for the Inbox card text for now; it is extended only when a concrete need arises, and existing values are not rewritten (#1675).
- `page.get` before dependent issues land -> `text` and `headings` null/empty until the Markdown conversion exists, `breadcrumbs` null for subpage items, `lastEdited*` null until the doc-edit-time issue lands; `subpageCount` counts `page` blocks.

#### (b) Open questions remaining for the product owner

- Does the project's "Edited" label include edits of subpages? (affects the doc-edit-time and invalidation issues; not decided, both implement per-document behavior only.)
- Which exact Inbox field does "Markdown in Inbox envelopes" mean? The Processing proposals `proposal` property is JSON, not text; the Inbox card `text` property was used. Confirm.
- Cross-issue gap: nothing fills `page.get` `text`/`headings` after the Markdown conversion issue lands (page-summary issue has no blocker on it), nor `subpageCount`-adjacent breadcrumbs for subpages. Suggest either adding a blocker from the page-summary issue to the Markdown conversion issue, or a small follow-up issue.
- Cross-issue gap: the page summary issue and the doc-edit-time issue are unordered; both carry a conditional wiring step for `lastEditedAt`/`lastEditedBy`. Suggest a real blocker edge in one direction.
- Where the block model module lives (the ADR decides; Touches paths remain symbolic until then).
- Agent capability and approval class of page operations are provisional (refined by the agent policy issues).

#### (c) User-visible behavior delivered by this chunk

Pages become reachable and safe to edit from several devices at once: a project (or any item) can have a page of structured blocks (text, three heading levels, bullets, numbers, to-dos, quotes and subpage links, each with indentation and bold/italic/code/link formatting), and two phones, a Mac and the web can edit it simultaneously without losing blocks or order. Block edits such as splitting, joining, moving, restyling, indenting, duplicating and deleting behave consistently everywhere, and a page is never empty. Clients can read a page summary (blocks, counts, headings, title, breadcrumbs) without creating it, and explicitly create a page for an item. Pages and text fields can be exchanged as predictable Markdown (so Semp and other tools never change a block's type by accident), the app records when and by whom a page was last edited, and other devices learn about edits to pages they do not have open so previews refresh within about a second.


### Decisions: block-editor-2

#### Adopted from open questions
- Vanished page link: trash in the same transaction, or sweep? -> Trash in the same transaction via the trash operation of #1723; the sweep (#1749) stays a safety net. Reason: atomic, immediately visible result of the edit.
  -> Decided by the product owner: when the user deletes a subpage link, the subpage goes to the trash in the same transaction, the app shows a toast with Undo, and the page stays restorable for 30 days; the orphan sweep stays a safety net. The replace response lists the trashed pages so the client can offer Undo, and Undo is the restore of #1723, which puts the block back at its place (#1765, #1723).
- Insert and page links (not in the design note) -> insert rejects any page link with 400 because #1679 does not depend on the subpage issues; links are handled only by replace. Reason: avoid validating links without the subpage relation available.
- ETag form -> strong quoted ETag of base64url(sha256(snapshot)); stable across compaction, changes on pure deletion.
- Missing doc on GET -> 200 empty body, no doc created; the ETag equals that of an empty doc.

#### Open questions for the product owner
- Should insert be able to add links to existing subpages (e.g. Semp linking a child page)? Currently rejected; would need a dependency on #1676.
- Is 409 on stale If-Match enough, or should the response include the current Markdown to ease client merge? Currently only the current ETag header.

#### Delivered behavior
Clients can read any page as Markdown (without its title) together with a version token, replace the whole page by sending Markdown back with that token (stale or missing token is rejected, unchanged blocks keep their identity, and removing or renaming a page link trashes or renames the subpage atomically), and insert Markdown at the start, end or after a given block, optionally with caller-chosen block ids. Reading never creates a page; the first write does.
