## Context

Model tier rationale: One read endpoint and store query over existing tables with established route, cursor and tenant-isolation test fixtures, but several joins (last message, pending approvals, heartbeat, subject) and the tenant-isolation route matrix need care.

The chat list in Semp shows every thread of the user ordered by last activity, grouped into days by the client, with a title, a preview line and the state of a waiting approval. The client also needs the list filtered by kind: chats and Inbox item threads together ("my chats"), or automatic task (tick) threads alone. Nothing of this exists on the backend: there is no thread list and no Semp route yet; threads and messages are introduced by #1367, runs are linked to threads by #1452, and approval requests get a localisable description from #1683. An approval request has no link to a thread of its own; the link goes through the requesting run's thread (`agent_runs.thread_id`). The time zone used by the client for day groups is the `Timezone` property in System settings (`backend/packages/data/src/timezone.ts`, `seed/seedSystem.ts`); grouping and prefixes ("Automatic task", "Inbox item") are client work and are not done here.

Search over this list is built on top of it by #1737, and the approval source on a request reuses the title resolver defined here (#1766).

Shared-file ordering: this issue also waits for #1725 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys`, `io-hardening` and `testing`.

1. Add `GET /api/semp/threads` (a `RouteDefinition` mounted like the thread detail route of #1543) with query parameters `kind` (comma-separated subset of `chat`, `item`, `tick`; default `chat,item`), `subjectInboxItemId` (uuid), `cursor` and `limit` (default 50, maximum 100). Validate every parameter; an unknown `kind` value or a malformed cursor or id is a validation error. Response: `{ rows, nextCursor }`, ordered by `last_activity_at DESC, id DESC`, the cursor being an opaque encoding of that pair.
2. Row shape: `{ id, kind, title, preview, lastActivityAt, hasPendingApproval, pendingApproval, heartbeat, subject }`. `kind` filters on the stored `semp_threads.kind` only.
   - `preview`: the thread's last message selected through a `LATERAL` subquery on the thread/created-at index from #1367; text without Markdown, cut to 140 Unicode code points plus an ellipsis when longer; for a system message the value is the structured `{ key, params }` instead of text. The list does not parse a whole stored message: the text preview is built from at most the first 1000 code points of the stored text. A message longer than that always gets the ellipsis, also when those 1000 code points show 140 code points or fewer once Markdown is removed, and Markdown syntax that the 1000 code points cut off before it closes (for example a link whose target ends beyond them) can remain in the preview as written.
   - `hasPendingApproval`: true when a pending `approval_requests` row exists whose run (including delegated runs) has this thread's id; `pendingApproval`: `{ description, sourceKind }` of the newest such request (description from #1683), otherwise `null`.
   - `title`: chat threads return the stored `title` (null until one is generated, the client then shows the start of the first message); tick threads return the heartbeat's current `project_heartbeats.name`; item threads return an i18n template ("Edit: <item name>") filled from the Inbox item's current text, read live at request time and never stored. Put that resolver in one shared function so #1766 can reuse it, and add its template key to `seed/i18n/cs.json` and `en.json`.
   - `heartbeat`: `{ id, name, projectItemId, projectName }` for tick threads, otherwise `null`.
   - `subject`: for item threads `{ inboxItemId, proposalId, exists }`: the two ids the thread stores (`subject_inbox_item_id` and `subject_proposal_id` of #1367; `proposalId` is `null` when the thread stores none), with `exists` computed live (false when the Inbox item is gone); otherwise `null`. This is the subject of the thread detail (#1543) plus `exists`. Export the mapper so the thread detail response (#1543) can return the same shape.
3. `subjectInboxItemId` returns the thread(s) for that Inbox item, so the client can reopen an item thread.
4. Reads run under the caller's tenant and ownership rules from #1367; a thread of another tenant or user never appears. Add the route to `routeMatrix.ts` and to the tenant-isolation route test.
5. Tests: kind filtering, ordering and cursor paging, preview truncation and system-message shape, pending approval of a delegated run, live rename of a heartbeat and live change of item text, isolation across tenants.

## Scope

### In scope

- The list endpoint with its filters, paging, preview, approval state, heartbeat, subject and live title resolution.

### Out of scope

- Bumping `last_activity_at` when an approval request is created (#1728); until that lands the ordering follows message activity.
- Search and the automatic chat title (#1737, #1769).
- Attaching the thread source to approval requests (#1766; it only calls the shared title resolver).
- Rename, delete and archive of threads: not in v1 (decided by the product owner).
- Day grouping, time formatting and the "Automatic task" / "Inbox item" prefixes (client).
- A card caption (`label`) and a proposal target on `subject`: a thread stores only the two ids of #1367, no issue defines a stored snapshot of them, and the source of the caption is an open product question recorded in the epic (#1304).
- A capture time (`capturedAt`) on `subject`: a thread stores none. Its live source is the Inbox item's own `date` and `time`, which a client reads from the item whose id the row carries. The list does not copy it, because a live value is gone together with the Inbox item (when `exists` is false) and would fix the meaning of the field before the question above is answered. All three fields can be added to `subject` later without changing the fields delivered here.

## Acceptance criteria

- When `kind=tick` is requested, only tick threads are returned; when `kind=chat,item` is requested (or omitted), no tick thread is returned.
- When a thread has a pending approval of a delegated run, then `hasPendingApproval` is true with its description; after the request is decided, it is false and `pendingApproval` is `null`.
- When a heartbeat is renamed or the Inbox item text changes, the next list response shows the new title without any write to the thread.
- When the text of the last message without Markdown, read from the first 1000 code points of its stored text, is longer than 140 code points, the preview is 140 code points plus an ellipsis; a system message is returned as `{ key, params }`.
- When two requests page through the list with the returned cursor, no row is skipped or repeated and the order is `lastActivityAt` descending.
- A user never sees threads of another tenant or another user.
