## Context

Model tier rationale: Two link rules declared against inheritance mechanisms that the blockers build and verify, plus tests of a cross-relation scenario; it writes user-owned relations as a system writer, so the ownership handoff and the self-person filter must be exactly right.

An action item in an event's detail becomes a task. Such a task should take over the event's project and the event's participants (without the tenant's own person) and keep following them until the user or Semp changes them; the company then follows from the project. Today a created task has no such values: `Events.actionItems` relates events to tasks, #1542 adds the inverse `Tasks.sourceEvents`, #1540 adds `Tasks.people`, and creating a task together with its relation edge is one request with #1590. The mechanism for inherited values exists in pieces: rules are declared in a module manifest (`linkRules`, #1411), edge and source changes propagate through hooks and a job (#1593), a user or agent write ends a link (#1516), and the rule schema has a value filter that leaves out the tenant's own person (#1697, which declares the analogous rules for transcripts; #1509 stores the own person). Inherited values are system writes with the owner process `valueLinks`.

This issue declares the two rules for tasks that came from an event, hands the target relations to the value-link process, and tests the whole behavior. The company is not a task value (it is derived from the project when read). Attachments follow in their own issue (#1702 and the attachment rules) and recordings in #1697.

Decisions:
- Creating a task from an action item uses the generic item create with the relation to the source event and an `Idempotency-Key`; no custom route is added.
- Rules: `Events.project` to `Tasks.project` and `Events.people` to `Tasks.people`, both via the `Tasks.sourceEvents` edge, the second leaving out the tenant's own person.
- The behavior of #1516 applies unchanged: a value the user set before the edge existed is kept and not linked; a value changed by the user or Semp after inheritance stops following; removing the edge leaves the values as own.

Shared-file ordering: this issue also waits for #1720 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. In `linkRules` of `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` declare `taskProjectFromEvent` (source `events.project`, target `tasks.project`, via `tasks.sourceEvents`) and `taskPeopleFromEvent` (source `events.people`, target `tasks.people`, via `tasks.sourceEvents`, with the own-person `valueFilter` that #1697 added to the rule schema), and declare the ownership handoff of `Tasks.project` and `Tasks.people` to the `valueLinks` process in the same way #1697 does for the transcript relations.
2. Fix gaps specific to Tasks (relation keys, the handoff of `Tasks.project`, whose inverse is `Projects.tasks`, and of `Tasks.people`) here; the engine is not changed.
3. Tests with real seeded databases and the item create of #1590: creating a task with `relations: [{ propertyKey: "sourceEvents", targetItemIds: [event] }]` yields, in one transaction, the event's project and its participants without the tenant's own person, all with link state `on` and the event as source; the same `Idempotency-Key` creates no second task; changing the event's project changes the project of tasks that still follow it and not of one the user changed by hand; adding a participant to the event reaches the tasks; removing the `sourceEvents` edge leaves the values as the task's own; a task created without a source event gets nothing; the Inbox dry run of an action-item proposal creates no values.

## Acceptance criteria

- When a task is created with a `sourceEvents` relation to "Meeting with the client", then it has that event's project and the event's participants without the tenant's own person, all marked inherited with the event as source, and the task and values are created in one transaction.
- When the same `Idempotency-Key` is sent again, then no second task is created.
- When the event's project changes, then the task's project changes with it, except for a task whose project the user changed by hand.
- When the source edge is removed, then the task keeps the values as its own.
- When a task is created without a source event, then no values are inherited.
