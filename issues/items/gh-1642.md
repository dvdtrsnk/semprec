**Blocked by:** #1421, #1582, #1603, #1636
**Model tier:** medium

## Context

Model tier rationale: A transactional custom route that soft-deletes two linked items plus their open cards and a restore hook that brings both back from the Trash, built on blocker mechanisms, reversible but touching several stores.

The app offers no way to delete a recording on its own yet; a recording is a Transcripts item plus the source Files item it was transcribed from (`Transcripts.link`). Deleting one without the other leaves an orphan, and a still-running pipeline would keep paying (#1582 now stops it cleanly).

This issue adds `DELETE /api/transcripts/:id`, a module-manifest custom route in the system-databases module with justification `transactional-semantics`: in one transaction it soft-deletes the transcript and its source Files item into the generic Trash and sets the open pairing and speaker cards of the transcript (kind `transcript`, status `proposed` or `needsClarification`) to `rejected`. Restoring the transcript from the generic Trash (`POST /api/items/:id/restore`) also restores its source Files item, through an item restore hook registered with the registry of #1601. The detail endpoint (#1576) does not show deleted transcripts. It uses the stop behavior of #1582 and the derived-blob purge of #1421 when the retention period ends.

Decisions (by the product owner):
- The app does not offer deleting a recording until the design includes it; this issue is implemented once the app has the delete action.
- A deleted recording goes into the generic Trash and is restored from it; there is no dedicated restore route. Restoring only the transcript must therefore bring its source file back too, otherwise the source file would stay deleted.

Shared-file ordering: this issue also waits for #1603, #1636 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Add the route (handler in `transcription/transcriptionRouteHandlers.ts`, `customRoutes` entry in `seed/systemDatabasesModuleManifest.ts`, `routeMatrix.ts`, tenant isolation route test). An unknown or foreign id answers the same 404.
2. DELETE: in one transaction soft-delete the transcript and the Files item found by `Transcripts.link` through the choke-point trash operations, reject the open cards; already-deleted items make the call idempotent.
3. Restore: add an item restore hook for Transcripts (registered through `registerItemRestoreHook` of #1601 in `domainWriteHooks.ts`) that, when a transcript is restored from the Trash, restores the Files item found by `Transcripts.link` in the same transaction when that Files item is in the Trash with the same `deletedAt` as the transcript (the two were trashed together by step 2); a Files item trashed on its own at another time stays in the Trash. Cards that were rejected by the delete stay rejected.
4. Tests: delete during processing stops the pipeline via #1582; delete is idempotent; restoring the transcript through `POST /api/items/:id/restore` returns both; a source file trashed separately is not restored with it; foreign tenant gets 404.

## Scope

### In scope

- Deleting a recording as one unit into the generic Trash, rejecting its open cards, and restoring its source file together with it from the Trash.

### Out of scope

- The pipeline stop: #1582; the derived-blob purge: #1421.
- The item restore hook registry itself: #1601.
- A dedicated restore route for recordings.

## Acceptance criteria

- When `DELETE /api/transcripts/:id` is called, then the transcript and its source file are in Trash and its open cards are rejected; a second call changes nothing.
- When the transcript is restored from the generic Trash (`POST /api/items/:id/restore`), then its source file is back too.
- When the id is unknown or belongs to another tenant, then the response is 404.
