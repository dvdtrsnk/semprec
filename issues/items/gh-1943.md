## Context

Model tier rationale: A cross-database transactional reversal of arbitrary earlier writes with optimistic-concurrency preconditions, hard and soft deletes and credential removal, where an error destroys or leaves behind user data.

A confirmed card is final today: `confirmProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) writes the destination items and relation edges and locks the card, and `rejectProposalWithClient` refuses a `confirmed` card. The Inbox undo must return the last confirmed decision to the stack with the values it had.

What the repository offers for reversal:
- Items go to the trash with `softDeleteItem` and return with `restoreItem` (`backend/packages/data/src/chokePoint/itemTrash.ts`). Relation edges have no soft delete: deleting an item leaves its edges and a restore only recomputes them. `deleteRelationWithClient` (`backend/packages/data/src/chokePoint/relationOps.ts`) deletes an edge for good.
- A transcript's speaker display name is composed from the `speakers` edge (`backend/packages/data/src/transcription/transcriptionRouteHandlers.ts`), so deleting the edge restores the "Speaker N" label.
- Page blocks have `deleteBlock` (`backend/packages/data/src/docs/blocks.ts`) but no REST path.
- A stored MCP credential is removed with `deleteCredential` (`backend/packages/data/src/credentials/externalCredentialsStore.ts`).

#1648 stores `results[]` on the card, each with the item id and the `updatedAt` after the step, and #1659 records an origin row per created item. #1937 provides the reopen route and transition for rejected cards; #1379 records the contract this issue implements. #1984 cancels jobs that confirmation queued.

Decision (product owner): no time limit applies; the `updatedAt` precondition is the only guard, and when it fails the undo is refused with an explanation and overwrites nothing. Decision (product owner): an approval card does not support undo and `reopen` on it is not offered (the exactly-once ADR stays as is); an executed approved action is reverted by restoring from the trash or by a new change. Decision: for a transcript card, undoing deletes the `event` or `speakers` edge as the confirmation wrote it; Decision (product owner): when the confirmation moved an Inbox attachment into Files (#1703, for example a confirmed recording), the undo reverses everything except the file. The Files item stays live in Files with its content and its origin row (the user can move it to the trash), it is not part of the `updatedAt` precondition, and the reopen response says so explicitly in `keptItems: [{ itemId, databaseKey, label, reason: "attachmentMovedToFiles" }]`. There is no reverse operation of the move.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Extend `POST /api/proposals/:id/reopen` (from #1937) and `reopenProposalWithClient` so a `confirmed` card is reopened in one transaction, following the ADR from #1379.
2. Precondition check before any write: for every `results[]` entry that created or changed an item, the current `updatedAt` equals the stored one; a missing item (permanently deleted) or any mismatch aborts with 409 `version_conflict` whose details carry the changed item (`itemId`, `databaseKey`, `label`) so the client can explain why nothing was undone, and nothing is written. A Files item kept by the rule above is not checked.
3. Reverse in this order, all in the same transaction:
   a. delete step edges created between existing items (link steps, transcript `event` and `speakers` edges) with `deleteRelationWithClient`;
   b. restore `before` values of items the confirmation patched (update steps), using the values recorded for the step;
   c. remove page blocks inserted by the confirmation by the ids derived from the proposal;
   d. soft-delete the items the confirmation created, together with their origin rows (#1659) removed, except a Files item that received a moved Inbox attachment, which stays;
   e. delete a credential stored for a created MCP server item.
4. Set the card to `proposed` with its original effective envelope, clear `resultItemId`, `resultLabel` and `results`, append a `reopened` history entry and enqueue the Journal inbox recompute; return `keptItems` next to the card (an empty array when nothing was kept).
5. Tests: reopen a confirmed task proposal sends the task to the trash and returns the card to `proposed` with identical values; after the task is edited, reopen answers 409 and nothing changes; a page-insert confirmation reopens by deleting only the inserted blocks; a speaker-mapping confirmation deletes the `speakers` edge and the speakers read shows "Speaker N" again; a two-step proposal is reversed atomically (a failure in the second reversal rolls back the first); undoing a confirmation that moved an attachment into Files reverses the other steps, leaves the Files item live and lists it in `keptItems`.

## Scope

### In scope

- Reopening a confirmed card by reversing its recorded writes atomically with the `updatedAt` precondition.

### Out of scope

- Cancelling queued transcription and MCP sync jobs and removing what they produce; #1984.
- The route registration and rejected-card reopen; #1937.
- Undoing approval requests (decided: not supported; an executed action is reverted through the trash or a new change).
- A time limit on undo (decided: none).
- Moving a file back from Files to the Inbox item (decided: the file stays in Files).

## Acceptance criteria

- When a confirmed task proposal is reopened, then the created task is in the trash, the card is `proposed` with the same values and the origin row is gone.
- When the created task was edited after confirmation, then reopen answers 409 `version_conflict` with the task and nothing is changed.
- When a confirmed page-insert proposal is reopened, then only the inserted blocks are removed.
- When a confirmed speaker mapping is reopened, then the `speakers` edge is deleted and `GET /api/transcripts/:id/speakers` shows the placeholder name again.
- When one reversal step fails, then no step is applied.
- When a confirmation that moved an Inbox attachment into Files is undone, then every other write is reversed, the Files item is still live, and the response lists it in `keptItems` with reason `attachmentMovedToFiles`.
