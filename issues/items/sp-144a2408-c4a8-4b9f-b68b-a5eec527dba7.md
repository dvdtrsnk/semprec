### Requirement gh-1568: [semp-threads 10/19] Close idle thread sessions on shutdown and pair dangling tool calls

#### Context

Model tier rationale: It changes shutdown and startup-repair ownership of agent run state across processes and must keep a protocol invariant intact, so an error leaves threads that can never be woken again.

Two restart problems block durable threads.

First, after a restart `startupRepair.ts` (`backend/packages/agent-runtime/src/`) closes every `running` run except MCP runs as `error` with an `agent_run_error` notification. A thread session that is idle (its last event is `turn_end`) stays `running` for up to 24 hours, so every deploy would raise a false error notification for every thread active in that window.

Second, a turn that ends by error or cancellation can leave an unpaired `tool_use`; `validateProtocolInvariants` then throws and the thread cannot be woken. Today only startup repair fills the gap, in a shape (`error: true`, result a string, no `isError`) that `toPiMessages` rejects, so even a repaired thread cannot wake. #1374 defines the single regular tool result shape and fixes `startupRepair.ts` for it; this issue uses it for the in-flight cases.

Builds on #1565 (registry per thread) and #1374. #1732 and #1926 build on this.

Required shape of the synthetic result (from #1374): `{ toolCallId, name, isError: true, result: { content: [{ type: 'text', text }], details: { error: true } } }`.

#### Task

Load `state-writes`, `error-handling` and `testing`.

1. Graceful shutdown in `services/semprec-agents/src/shutdown.ts` closes every idle thread session (last event `turn_end`) as `done`, without an `agent_run_error`. Startup repair applies the same rule for idle sessions it finds after a crash: close as `done`, no error notification; a session that was mid-turn is still closed as `error` with the notification as before. Apply existing tenant-data logging rules throughout this shutdown module: report only a fixed error category and signal, never a raw error tree or arbitrary error name; preserve current ordering, deadlines, exit and pool-close continuation.
2. When a turn ends with an error or is cancelled (the path through `lifecycleAdapter.ts`, `failRun`), pair every dangling `tool_use` of that turn immediately with a synthetic tool result in the shape above, so the thread can be woken again without waiting for a restart. Pairing, terminal close, notification and terminal event share one managed transaction as specified by decision §9. A failed recovery must not commit a terminal unpaired run; preserve original and recovery failures and leave it repairable rather than claim an immediate wake during a database failure.
3. Tests: restarting with an idle thread session creates no `agent_run_error` and the thread wakes again afterwards; a turn cancelled mid-tool-call leaves a paired history, `validateProtocolInvariants` passes, and the next wake succeeds; a mid-turn session at restart is still closed as error with its notification; delegated and MCP runs behave as before.

### Requirement gh-1527: [agent-runs 07/21] Return the approval request id and field changes as structured tool result fields

#### Context

Model tier rationale: One mechanism (structured fields on the tool result) across two tool adapters and the pi bridge, reusing an output field another issue adds to the write transaction, with existing tool contract tests to extend.

The agent's tools return only text to the model and to the log. `createTool` in `backend/packages/agent-runtime/src/tools/generic/genericOperationAgentTools.ts` returns `{error, result}` where `result` is `JSON.stringify(output)`; for a call that needs human approval, `pendingApprovalResult` here and in `backend/packages/agent-runtime/src/mcpInvokeTool.ts` return the sentence "Approval request <id> has been created ..." and the request id exists nowhere else on the event. `approval_requests` has no column that links it back to the tool call. `agentSessionComposition.ts` turns these into the pi result `{content, details: {error}}`, which `agent_run_events` stores as `tool_result.result`.

This issue adds two structured fields to the stored `tool_result.result.details`, so readers never parse the result text:

- `approvalRequestId`: when the call created an approval request, the id of that request (for generic operations and for MCP tools).
- `changes`: for a successful `item.patch`, a list of `{key, before, after}` per changed property.

Decision (previous values): `before` comes from the `item.patch` operation output itself. #1429 makes `item.patch` return the previous values of the patched properties from inside the write transaction, as an additive output field; this issue reads that field. A best-effort read outside the transaction is not allowed because it could report a value that was never the real previous one. If the output carries no previous value for a key, retain that key in `changes` and omit only its `before` member, as required by Task 5 and the acceptance criterion. The existing longText content exclusion still applies.

Decision (values): `after` is the value from the call arguments (`properties`). Both `before` and `after` are shortened to a bounded length when they are strings, and a `longText` property never has its content stored: its `changes` entry keeps the key and records only that the value changed (no `before`/`after`). Keys are the canonical property keys.

Builds on #1424 (the typed tool event payload, extended here for `details`) and #1429. Later readers: the approval-request link to its tool call #1618, the changed-items record per reply #1885, the step summary #1860, the thread activity bump #1728 and the step projection #1847.

The text sentence for the model stays unchanged.

### Requirement gh-1728: [semp-threads 13/19] Bump thread activity when an approval request is created

#### Context

### Requirement gh-1533: [project-mcp 05/08] Give MCP tools stable server-qualified model names
