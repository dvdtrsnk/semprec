## Context

Model tier rationale: A documentation-only decision record that fixes a cross-cutting envelope shape later issues will implement literally, so its claims about transactions and refs must match the code.

One Inbox proposal sometimes has to do more than create one item: a file from an attachment plus a follow-up task, a company plus a new person, a health record plus a follow-up task, a new area plus moving a project into it, a transcript's speaker mapped to a new person. Today the envelope is `{ entityKind, target, properties }` (`proposalEnvelopeSchema` in `backend/packages/data/src/inbox/inboxTickAction.ts`, a `z.object` that drops unknown keys) and means exactly one write. `confirmProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) is locked, idempotent and one transaction, and already writes several things atomically in two special cases (an Event plus its transcript edge; an MCP server plus its credential), but returns one `resultItemId` and `resultLabel`. Relations of single-step envelopes are added by #1426; moving an existing item is a step kind of its own. Later issues validate (#1479) and confirm (#1486) the shape recorded here, and any later composite proposal (for example a step that a future module adds) must adopt exactly this one shape.

## Task

Load `adr-conventions`.

1. Add the ADR `docs/adr/2026-10-25-multi-step-proposal-envelope.md` (status accepted, area `backend`, `supersedes: []`) recording these decisions with the alternatives and the reasons:
   - Shape: the envelope gains an optional `operations` array. Each step: `ref` (unique within the proposal, used by user edits, for example `primary`), `op` (`create`, `update` or `link`), `databaseKey` (for `create`) or `itemId` (for `update` and `link`), `properties`, `relations` (targets may be an item id or `{ ref }` naming another step of the same proposal), `role` (`primary` or `secondary`), `optional` and `enabled` (booleans). An `update` step carries `before` and `after` of every relation and property it changes so it can be shown, reverted and audited. An `update` step is a general write of the existing item's properties and relations through the item-write choke point, under the same validation, approval and risk rules as any other item update; a project's status is not a special case.
   - Compatibility: a single-step envelope stays valid unchanged; a multi-step envelope keeps the top-level `entityKind`, `target` and `properties` equal to its primary step so every existing reader and the `confirm` contract (`resultItemId` and `resultLabel` are the primary step's result) keep working; `operations` lists all steps including the primary one.
   - Skipping: a step is neither validated nor written when `enabled` is false, or when it is `optional` and nothing refers to its `ref` any more (a removed "new" chip, another company chosen, another person chosen).
   - Refs: only to steps of the same proposal, no cycles, exactly one primary step; steps are written in dependency order.
   - Confirm: all steps in one transaction under the proposal's row lock; any failure rolls everything back and returns 400 naming the `ref` and the `field`; moving to another "one"-side owner is `deleteRelationWithClient` of the old edge plus `createRelationWithClient` of the new one in the same transaction; the properties of an `update` step are written with the choke point's item update in the same transaction.
   - Rejected alternatives: child proposals created after the first confirm (non-atomic, leaves half-done work, doubles the cards the user sees) and encoding extra steps inside `properties`; multiple cards for one source remain a separate mechanism governed by a separate decision on splitting one source into several cards.
2. State that user edits address a step by `ref` (`primary` for a single-step envelope), which is the key `userOverrides` uses.
