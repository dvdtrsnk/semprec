## Context

Model tier rationale: This issue only declares one rule on an already-built link-rule mechanism and proves the Tasks-specific behavior with existing fixtures, but it touches the shared module manifest and depends on several blockers' contracts, so it is not low.

An attachment shown on a task also shows a project. By default an attachment takes the project of its task and follows it: changing the task's project changes the project of every attachment that still follows it, "no project" included (an attachment of a task without a project receives the project when the task gets one). The user can end the following by changing an attachment's project by hand or cancelling the link, and can restore it; a file that the user gave its own project keeps it when the task's project changes. A file attached to two tasks of different projects holds both (see the decisions below).

The mechanism is not built here. #1403 to #1656 store the links with their state (following or broken) and expose them on items, break a link when a user or an agent writes the target value, provide `link.unlink` and `link.relink`, and detach links when a source is deleted. #1411 lets a module manifest declare a link rule and validates it; #1593 propagates a changed source value to the targets that still follow it. A rule names a source property, a target property and the relation that connects them (the `via`). Agent writes that would break a link go through approval (#1713, #1758).

What this issue adds is the Tasks rule: source `Tasks.project`, target `Files.projects`, via `Files.tasks`. It builds on #1654 (attaching an upload to a task creates the `Files.tasks` edge, which is the moment the link is created), on #1521 (`relation.set` replaces a task's single project atomically, which is the change that propagates) and on #1621 (realtime invalidation for the edge writes the propagation performs).

Decision (corrected by `issues/decisions/gh-1702.md`): a file attached to two tasks follows both. `Files.projects` holds many projects, and the link engine of #1593 makes a many-valued target the union of the values of all its sources, so the file holds the projects of both tasks, once each when they are the same. A change of one task's project replaces only that task's contribution. An option that keeps only the first task is not built: it needs a new engine option and its own cases.

Decision (corrected by `issues/decisions/gh-1702.md`): when an existing file that already has its own project is attached to a task, the file keeps its own project and gets no link; the task's project is not forced onto it. The engine creates a link only into an empty property that has no link (#1593, decided by the product owner in the epic #1326), and a link never starts broken: `broken_by` is `user` or `agent` only. `link.relink` on that property answers 409, as on any property without a link.

Shared-file ordering: this issue also waits for #1697 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `adr-conventions` and `testing`.

1. Declare in the systemDatabases module manifest (`backend/packages/data/src/seed/systemDatabasesModuleManifest.ts`) one link rule using the declaration shape from #1411: key `fileProjectsFromTasks`, source `Tasks.project`, target `Files.projects`, via `Files.tasks`. A comment on the entry records the ownership handoff, as the entries of #1697 and #1724 do: `Files.projects` stays `owner: user` and the `valueLinks` process writes it only while the file's link is `on`. The rule must pass that issue's manifest validation (source and target properties exist, the via relation connects the two databases).
2. Behavior to hold, using only the mechanism's operations (no custom propagation code):
   - Attaching a file (new or existing without its own project) to a task creates a link in the state following, and the file takes the task's project, or none.
   - Attaching an existing file that already has its own project leaves that project as it is and creates no link: `links.projects` has no entry for it, a later change of the task's project does not reach it, and `link.relink` on it answers 409.
   - Attaching a file to a second task adds that task as a source of the file's link, and the file holds the projects of both tasks. A change of one task's project replaces only that task's contribution, and detaching one task (deleting its `Files.tasks` edge) leaves the file following the other alone. No code makes the first task win.
   - Changing the task's project with `relation.set` on `Tasks.project`, including to none, replaces the project set of every following file with the new one (an empty set for none).
   - A user or agent write to `Files.projects` of a following file breaks the link (`links.projects` reports it broken with the writer); a later change of the task's project does not touch that file.
   - `link.unlink` and `link.relink` on such a file work as the mechanism defines; relink restores the task's project.
3. Tests (real database, through the choke point and the HTTP surface where the mechanism exposes it) for each behavior above, including a file attached to two tasks (it holds both tasks' projects), a file with its own project (kept, no link, not changed by a later change of the task's project) and a task with no project.
4. Existing tests: the rule breaks tests that were written before it, and they are brought in line with the smallest change that keeps what each proves; no assertion is weakened. The fixture rule `fixtureSingle.fileProjects` of `backend/packages/data/src/__tests__/linkRuleEdgeHook.test.ts` runs the other way over `Tasks.files` and closes a cycle with the new rule (`Link rules form a cycle`), so it gets a source, a target and a via that no real rule runs the other way, and it still proves that a single-valued target fed by a multi-valued source is left alone. Every write of a `Tasks.project` edge now queues a `valueLinksPropagate` job and needs a tenant scope, so a test that writes one without a scope runs it inside the scope its other writes use: when this was decided, `backend/packages/data/src/__tests__/tenDatabases.test.ts`, `backend/packages/data/src/__tests__/proposalActions.test.ts` and `backend/packages/data/src/chokePoint/__tests__/relationOps.test.ts` failed that way. Run every integration test file that writes a task with a project, and name in the handover each existing file changed, with its reason.
5. ADR: add `docs/adr/<date it is written>-a-files-projects-follow-its-tasks-by-a-link-rule.md` (`status: accepted`, `area: [backend]`, `supersedes: []`), referencing `[[2026-09-10-single-writer-ownership-model]]`, `[[2026-11-10-transcript-values-are-inherited-by-link-rules-whichever-process-writes-the-edge]]` and `[[2026-11-11-action-item-tasks-inherit-project-and-people-by-link-rules]]`. It records: the rule and the ownership handoff of `Files.projects`; that a file attached to two tasks holds the union of their projects; that a file with its own project keeps it and gets no link; that nothing is backfilled; and that `Files.projects` is the target of this rule and the via relation of `fileCompaniesFromProjects`, so a task's project reaches the file's company in a second hop. It adds no order of its own for a user or agent edge write on that relation.

## Acceptance criteria

- When a task's project is changed to another project, then the project of every attachment that follows it changes with it, and an attachment with its own project is unchanged.
- When an attachment of a task without a project is attached and the task later gets a project, then the attachment gets that project.
- When a task's project is set to none, then following attachments end up with no project.
- When a user changes the project of a following attachment, then its link is reported broken by the user, and the task's next project change leaves it alone; `link.relink` makes it follow the task's project again.
- When the manifest is loaded, then the rule validates without errors.
- When a file is attached to two tasks of different projects, then it holds the projects of both tasks, and a change of one task's project changes only that task's project of the file.
- When an existing file with its own project is attached to a task, then it keeps its project, has no `projects` link, and a later change of the task's project leaves it unchanged.
- The ADR of Task step 5 exists.
