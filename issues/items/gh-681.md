**Blocked by:** #674

## Context

Email `read`/`flagged` are user-owned properties that must converge with the provider in both directions (`docs/adr/2026-09-20-desired-current-state-sync-for-provider-writebacks.md`). Today only one direction works:

1. `recordObservedMailMessageFlags` (`backend/packages/data/src/mail/mailMessageFlagSyncStore.ts`, lines 45-60) upserts `current_state` on conflict and never touches `desired_state`. Once the user has marked a message read (`desired_state = true`, later confirmed `current_state = true`), a change made on the phone (message marked unread on the server) arrives as an observation that sets `current_state = false` while `desired_state` stays `true`; `listPendingImapFlagWrites` (lines 79-123) then sees `current IS DISTINCT FROM desired` and writes `\Seen` back — the provider-side change is reverted, every time. The Emails item's own `read` property is never updated by an observation either: `ingestEmailMessage` seeds the flags only at creation (`backend/packages/data/src/mail/ingest.ts`, lines 116-121) and, for an existing item, only calls `recordObservedMailMessageFlags` (lines 205-212).
2. For IMAP, observations never arrive for a known message: `reconcileImapFolder` (`backend/packages/data/src/mail/imapReconcile.ts`, lines 173-174) fetches only `UID >= uidnext` (`fetchMessagesSince`), and `fetchVanishedSince` in `backend/packages/data/src/mail/imapFlowClient.ts` (lines 369-391) drains a `CHANGEDSINCE` fetch for expunges only — its comment "flags themselves are picked up by fetchMessagesSince's next pass" is false for UIDs the folder already knows.

This issue depends on C21: per-mailbox Emails items are what make an observation attributable to one mailbox's copy. As with C21, no live transport exists; the reconcile logic is tested through the fake `ImapMailClient` in `backend/packages/data/src/__tests__/mailSync.test.ts` (`fakeImapClient`, line 1157), and the `ImapFlowMailClient` method added here is exercised through the `fakeImapFlow` helper (line 2959).

## Task

1. **Observation wins when nothing is pending.** `recordObservedMailMessageFlags`'s `ON CONFLICT ... DO UPDATE` also sets `desired_state = CASE WHEN mail_message_flag_sync_state.current_state IS NOT DISTINCT FROM mail_message_flag_sync_state.desired_state THEN EXCLUDED.current_state ELSE mail_message_flag_sync_state.desired_state END` — a converged row adopts the observed value as the new desired state; a row with a pending write (`current` differs from `desired`) keeps the user's intent and the write-back proceeds (the ADR's "never replace a *differing* desired value" holds; a converged pair is not a differing one). Document this in the function comment.
2. **The item follows the observation.** New `backend/packages/data/src/mail/mailFlagObservation.ts` exporting `applyObservedMailMessageFlags(client: PoolClient, input: { emailsDatabaseId: string; messageItemId: string; flags: readonly string[] })`: inside the caller's transaction, `SELECT property_key, desired_state, current_state FROM mail_message_flag_sync_state WHERE message_item_id = $1 FOR UPDATE`; for each of `read`/`flagged` (`messageFlagProperties(flags)`), when the row is absent or converged (`current IS NOT DISTINCT FROM desired`) and the observed value differs from the item's stored property (`getItemById`), patch the item through `updateItemWithClient(client, { databaseId: emailsDatabaseId, itemId, propertiesPatch: { [key]: observed } })` — the choke point's Emails branch (`itemWrites.ts`, lines 276-278) records `desired_state = observed` itself — then call `recordObservedMailMessageFlags` for the observed values (sets `current_state`; the row is now converged on the observed value). When the row is pending, only `recordObservedMailMessageFlags` runs (no item patch). `ingest.ts` lines 205-212 (the existing-item path) call `applyObservedMailMessageFlags` instead of `recordObservedMailMessageFlags` directly; the creation path is unchanged (flags are seeded into the item at insert).
3. **IMAP re-fetches flags for known UIDs.** `ImapMailClient` (`imapReconcile.ts`, lines 44-63) gains `fetchFlagsChangedSince(path: string, sinceModSeq: number | null): Promise<Array<{ uid: number; flags: string[] }>>` — `sinceModSeq` non-null: a `CHANGEDSINCE` fetch of `1:*` with `{ uid: true, flags: true }` (CONDSTORE), returning every UID whose flags changed; `null` (no CONDSTORE, or first pass after a UIDVALIDITY reset): a full `{ uid: true, flags: true }` fetch of `1:*`. `ImapFlowMailClient` implements it (peek-only, no body fetch — the same `fetch` call `fetchVanishedSince` already makes, with `flags: true`); correct the comment at line 385. `reconcileImapFolder`: after the new-message loop and before the vanished pass, when `state.uidvalidity` is set (not the initial sync), call `fetchFlagsChangedSince(params.folderPath, capabilities.has('CONDSTORE') && state.highestmodseq ? Number(state.highestmodseq) : null)`, and for each returned UID below `sinceUid` resolve the item with `findEmailItemIdByFolderUid` and call `applyObservedMailMessageFlags`. `fakeImapClient` gains a default `fetchFlagsChangedSince: async () => []`.
4. Tests in `mailSync.test.ts` (integration): (a) a message marked read through `chokePoint.updateItem` (desired `true`), confirmed by the write-back path (`recordConfirmedMailMessageFlag`), then observed unread via `fetchFlagsChangedSince` → the item's `read` is `false`, the state row is `desired = current = false`, and `listPendingImapFlagWrites` is empty; (b) a pending write (desired `true`, current `false`) plus an observation of `false` → the item stays `read: true`, the write stays pending; (c) an observation equal to the pending desired value (`true`) → the row converges with no item patch and no pending write; (d) the fake client records that `fetchFlagsChangedSince` was called with `null` when the fake advertises no CONDSTORE and with the stored `highestmodseq` when it does; (e) `ImapFlowMailClient.fetchFlagsChangedSince` through `fakeImapFlow`: passes `changedSince` only when a modseq is given and returns `{ uid, flags }` pairs.

## Scope

### In scope
- Observation-wins-when-converged, the item patch that follows an observation, and the IMAP known-UID flag re-fetch, with tests.

### Out of scope
- Gmail/Graph flag observations for known messages (their reconcile paths carry no flag data today; a separate finding).
- Per-mailbox message identity (C21).
- Flag write-back scheduling and retries (`mailFlagWriteback.ts`).

## Acceptance criteria

- When a message's flag state is converged and the provider reports a different value, the Emails item's `read`/`flagged` property and both halves of `mail_message_flag_sync_state` take the provider's value and no write-back is queued.
- When a user change is pending write-back and the provider reports the old value, the user's value stays desired and the write-back still happens.
- When an IMAP folder is reconciled after its initial sync, flag changes on already-known UIDs are fetched (`CHANGEDSINCE` when the server has CONDSTORE and a modseq is stored, a full flag fetch otherwise) and applied through the same observation path.
