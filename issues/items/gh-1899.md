## Context

Model tier rationale: Deterministic prefill logic on the existing draft create route, with clear rules and fixtures, but it spans threading headers, recipient selection and localized quoting.

Reply, reply-all and forward should start a prefilled draft in one operation. Today these actions do not exist in the backend, so the app would have to assemble recipients, subject and quote itself. The message envelope is stored in `mail_message_meta.envelope`, the threading headers (`message_id`, `references`) and thread id in the same table, and the address the message was delivered to in `delivered_to_address` (`backend/packages/data/src/mail/deliveredTo.ts`).

It builds on: the draft routes (#1867), the one-thread read (#1632), Reply-To parsing (#1499) and draft attachments (#1895, used for forwards). Sending the draft is #1896.

Decision: reply-all puts all selected recipients into `to`, because the compose window has no Cc field; Cc stays empty.

## Task

Load `canonical-keys`, `error-handling` and `testing`.

1. Extend `POST /api/mail/drafts` handling of `mode` and `sourceEmailId`: for `reply`, `replyAll` and `forward`, load the source message and compute the draft before the create, ignoring conflicting values for the computed fields in the request body.
2. Recipients: `reply` goes to the message's Reply-To, otherwise its sender. `replyAll` adds the source's To and Cc recipients, excluding all of the mailbox's own addresses and duplicates. `forward` has no recipients.
3. `from` is the address the source was delivered to (`delivered_to_address`) when it belongs to the mailbox, otherwise the mailbox's primary address.
4. Subject: prefix `Re: ` or `Fwd: ` unless the subject already starts with that prefix (case-insensitive), so a reply to "Re: Offer" stays "Re: Offer".
5. Threading: `in_reply_to` is the source's Message-ID, `references` is the source's references plus its Message-ID, `thread_id` is the source's thread. Forward keeps the source thread id only as the originating thread; it sets no `in_reply_to`.
6. Body: below an empty line, a header line localized in the user's locale (`users.locale`, texts in the mail i18n catalogs: "On {date}, {name} wrote:" and the Czech equivalent) followed by the source's plain text, each line prefixed with `> `. A forward uses a "Forwarded message" header with the original sender, date, subject and recipients.
7. A forward copies the source's attachments to the new draft through the attachment interface of #1895.

## Scope

### In scope

- Prefill for reply, reply-all and forward on draft creation.

### Out of scope

- The draft routes themselves (#1867), attachment handling (#1895), Reply-To parsing (#1499).
- HTML quoting; the draft body is plain text.
- Sending (#1896).

## Acceptance criteria

- When replying to all on a message from Gmail, then `to` contains none of the mailbox's own addresses and `from` is the address the message was delivered to.
- When the source subject is "Re: Offer", then the reply subject is "Re: Offer".
- When the source has a Reply-To, then the reply goes to that address.
- The draft's `in_reply_to` is the source's Message-ID and `references` ends with it.
- When forwarding a message with attachments, then the new draft has its own copies and the original message keeps them.
- The quote lines start with `> ` and the header text follows the user's locale.
