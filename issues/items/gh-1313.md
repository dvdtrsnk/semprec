## Behavior specification

Inbox editing: manual values, recompute, editor schema, pickers, invalid proposals, refine and revise.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: inbox-editing-1

#### (a) Adopted decisions
- Migration vs backfill of `aiProposal` -> no data migration; readers treat a missing `aiProposal` as the stored `proposal`, aiVersion as 0, first write materializes it -> avoids a hotspot migration and is safe because overrides cannot pre-exist.
- Who increments `aiVersion` -> every assistant/revise write through the shared helper in #1471 -> one place, needed by the staleness check in #1921.
- `ifVersion` semantics for values/reset -> card `updatedAt`, 409 via ConflictError `{ current }` -> same as generic PATCH.
- Required fields at edit time -> warnings only (response body), enforcement at confirm is #1928.
- Allowed statuses for edit/reset -> proposed, needsClarification with chosen type, fixable invalid (becomes proposed); locked refused.
- Reset with nothing edited -> succeeds, returns card, no history entry.
- History vocabulary -> one closed `kind` enum shared by all flows; thread revision = `threadRevision` with author ai; messages stay English.
- Tick staleness -> fingerprint + aiVersion instead of updatedAt; manual edits never discard an assistant result.
- needsClarification from the tick -> keeps overrides stored, effective proposal null.
- Destination change -> clears all overrides (kind reset); same destination keeps only keys the new destination has. Tick recompute drops overrides only when destination or key no longer applies (#1921), explicit/revise changes via #1924 helper.
- Relations/steps overrides stored in `userOverrides` under reserved names, counted as `ref.relations.<key>` and `ref.enabled`; primary step cannot be disabled.
- Shared pure helpers live in new `inbox/proposalOverrides.ts` (created in #1892) to avoid a proposalActions <-> inboxTickAction import cycle.

#### (b) Open questions for the product owner
- Exact wire shape of `relations` in PATCH values (depends on the relation shape chosen in #1426).
- Whether hidden-field exclusion from the edited count should be implemented before the editor schema exists (currently: all keys counted until #1825).

#### (c) User-visible behavior
The user can edit any field of an Inbox proposal card, including secondary steps, relations and step switches. Edited fields are marked and counted ("Edited by hand: N"), the assistant's later recomputes (after the source changes) keep those values, and a result computed while the user was editing is no longer lost. A "return the proposal" action discards all manual values and restores what the assistant last proposed. Changing the card's destination (for example task to event) clears the manual values. Conflicting edits from two clients get a 409 with the current card.

### Decisions: inbox-editing-2

#### (a) Adopted decisions
- Who owns the editor schema -> the module manifest of the card's target database, keyed by base kind; MCP schema in the Inbox manifest until an MCP manifest exists -> the server must enforce required-ness/conditions on confirm, so it must own the schema.
- Localization -> server resolves labels/placeholders from module catalogs per users.locale (English fallback), card carries resolved strings -> no catalog keys on the wire.
- Required fields -> ValidationError with details.field (+ref) on confirm; warnings only on PATCH values -> work in progress must be saveable.
- Warnings transport -> additive `warnings` array on the item response via the custom-route result.
- Pseudo fields (allDay, followupTask, followDate, ...) -> closed set, stored in userOverrides, used as condition inputs, never written to the created item; a future module adds its own step keys by extending the set.
- Hidden fields -> not validated, excluded from userEditedKeys, omitted from what confirm writes (Events timeFrom/timeTo explicit null).
- MCP stdio card -> refused at confirm (existing ADR confines stdio to admin).
- Options route (#1959) -> closed field set; order current value, suggested, edge count, name; none choice last for project/company and first otherwise; archived/deleted targets listed only as the current value. Is a `done` project unusable -> Decided by the product owner: no; it is a valid target, the picker hides it by default (`includeDone=true` lists it, and it is always listed when it is the current value), Semp does not offer it, and open proposals with it stay valid; nothing is cancelled silently (#1959, #1916).
- Option initials from the server, person color derived by the client -> Decided by the product owner: the color is derived in the client; a new field on People would be unnecessary.
- invalidReason -> {code, field, itemId, label}; sentence rendered from catalogs, not stored; sourceDeleted is final, target* fixable; legacy invalid cards without reason are fixable.
- Reactive invalidation -> hooks apply to items of any database (answers "which databases are target pages"); only archived projects and deleted items invalidate; `done` projects do not; hooks use FOR UPDATE SKIP LOCKED to avoid deadlock with confirm.
- Restore of a source -> restoreItemWithClient triggers onItemEvent "update" heartbeats generically; tick returns invalid/sourceDeleted cards to proposed regardless of fingerprint.
- Page host list for options/hook is "any database" rather than a fixed list.
- Card list shows the invalid reason -> Decided by the product owner: yes, a short reason, so the user knows why a card cannot be confirmed (#2027).
- Transcript Event/speaker choice controls and the recording card schema -> Decided by the product owner: not planned yet; added with the design of the recording card (#1417, #1825).

#### (b) Open questions for the product owner
- Where is the all-day switch stored when the assistant itself proposes an all-day task (userOverrides pseudo key vs derived from empty times)? Currently only explicit user/assistant pseudo values count; absent means false.
- Is the `referencedItemIds` system property created by the card-state properties issue? The job text assumes yes.

#### (c) User-visible behavior
Every Inbox card comes with a server-defined editor: the right control for each field, grouped, with Czech or English labels and placeholders, required fields marked, and fields that appear only under conditions (an all-day item hides its time, a long-term project hides its due date, a switched-off follow-up task hides its due date). Saving a half-filled card is allowed, with warnings; processing a card with a missing required field is refused naming the field, and values for hidden fields are not stored. Pickers for project, area, people, company and page come from one endpoint with the current value first, the suggestion next, then the most used choices, archived targets shown greyed out and done projects hidden unless asked for. A proposal becomes "can't be used" with a clear reason, also shown in the card list, when its project/person/page is archived or deleted (immediately, in the same action), becomes usable again when the target is restored, or when the user picks another one; a card whose source was deleted can only be discarded, but comes back when the source is restored from the trash.

### Decisions: inbox-editing-3

#### (a) Adopted decisions
- Precompute proposals for all candidate types vs compute after the choice -> Decided by the product owner: through the transient status `computing`, one general mechanism for every recompute that needs no precomputed candidates per type; the design of the interstate follows (#1947).
- Force-recompute mechanism -> a card in `computing` bypasses the tick's fingerprint gate; routes set `computing` and trigger the existing Inbox `update` heartbeat -> no new job payload; works with job-key replacement.
- 409 code for decided cards -> `proposal_locked` (new error class unless the type-lock issue added one).
- ifVersion on type change -> refers to the proposal card's updatedAt; items without a card take none.
- Recompute on transcript cards -> 400; recompute of an already `computing` card is idempotent.
- Fingerprint v2 -> `v2:<sha256>` of {v:2, typeId, text, date, time, sorted attachment content hashes, transcribedText}; v1 values compared with the old formula so deployment recomputes nothing; transcribedText is "" until audio attachments are transcribed from the Inbox (-> Decided by the product owner: audio transcripts enter the fingerprint only once that transcription exists).
- Visible timeout of `computing` -> Decided by the product owner: yes; after a timeout the card shows an error with a Retry action (#2026); recording a compute failure stays with #1485.
- Thread revision on protected keys -> instruction may change a protected key; value goes to userOverrides (stays in userEditedKeys); aiProposal keeps the previous assistant value; target change drops overrides.
- Confirmed/rejected card in a thread -> the card is read-only, tool error. Editing the created item from the thread -> Decided by the product owner: yes; it is an ordinary item and the thread edits it with the same tools through the choke point; a Semp write that ends an inherited value link requires approval with the warning "Ends the link" (#1938, #1758).
- Split -> user-context Inbox-module action creates siblings (not the tick); primary stays the tick's only card; siblings marked `splitFromProposalId` and recomputed only on explicit request (-> Decided by the product owner: a source edit recomputes only the edited card; sibling cards are never changed silently); max cards per split fixed in the ADR (suggested 10).
- No separate read tool; card context is inserted into the thread prompt.

#### (b) Open questions for the product owner
- None remaining.

#### (c) User-visible behavior
The user can pick a type for an unclear Inbox item (or change it) and the card is rebuilt for that type from the same source, showing a computing state meanwhile (and an error with Retry if it takes too long); manual values are cleared when the destination changes. A recompute can be requested for any open card and keeps the values the user edited. Capture time, attachments and type changes now trigger a recomputation, while existing cards are not recomputed on deployment. In the item thread Semp sees the full capture and its proposal, can change the card on instruction (even a value the user edited by hand, which then stays marked as hand-edited), and can split one capture into several cards, of which only the first follows later edits of the source. The item a confirmed card created can be edited from the thread like any other item.
