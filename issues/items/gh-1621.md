## Context

Model tier rationale: One additive realtime frame carried through the existing publish, parse and fan-out seams with established tests, but it is emitted from a transaction hot path shared by internal writers and must dedupe and respect tenant scoping.

When an edge is created, updated or deleted, nothing is announced. `createRelationWithClient`, `updateRelationWithClient` and `deleteRelationWithClient` in `backend/packages/data/src/chokePoint/relationOps.ts` never call `notifyInvalidation`. An item write is announced after commit (`runAfterCommit` in `chokePoint/itemWrites.ts`, through `realtimeHook.ts`) with `scope: "item"` and a required `updatedAt` that clients use to drop stale echoes, but an edge write changes no item's `updatedAt`. So moving a task to another project, adding a company to a person, or changing a project's area leaves every other open session showing the old links until it reloads.

Today the frame catalog knows only `scope: "item"` and `scope: "schema"`: `OutboundFrame` in `backend/packages/realtime/src/protocolV1.ts`, the `RealtimeMessage` union and `parseRealtimeMessage` in `backend/packages/realtime/src/pgNotifyPublisher.ts`, and the `invalidation` branch of `backend/packages/realtime/src/syncServer.ts`. Fan-out is to the sockets of the writing tenant only, narrowed to one user when `userId` is set (`docs/adr/2026-10-16-tenant-scoped-realtime-fan-out.md`). Edges are also written outside the API process: `copyRelationEdges` in `tasks/advanceTaskRecurrenceWithClient.ts`, the mail reconcilers (`mail/imapReconcile.ts`, `gmailReconcile.ts`, `graphReconcile.ts`), the inbox and the transcription service, which wires realtime through `wireRealtimeHooks` in `services/semprec-transcribe/src/serve.ts`.

This issue adds the one `relation` invalidation frame and publishes it from the three edge write functions, so every edge writer is covered at once, including `relation.put`, `relation.delete`, `relation.set` (#1521) and `item.create` with relations (#1590). It is the single owner of this frame for every area; later issues only consume it (#1710, #1709, #1764, #1702, #1770).

Decisions:
- The canonical scope name is `relation` (singular).
- The frame is thin: no `updatedAt`, no stale-echo rule, no edge content. A client reacts by refetching whatever it shows for that item and key (an item detail or list read with `include=relations`, a related-items read, a count).
- At most one event per `(itemId, propertyKey)` per transaction.
- The target end of a one-directional relation (a definition with `propertyIdB = null`, such as a file's area) has no property key of its own, but it still receives a thin invalidation with `propertyKey: null`, so the links shown at the target (links pointing back at it) do not go stale. Decided by the product owner.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. Add `{ type: "invalidate", scope: "relation", databaseId, itemId, propertyKey: string | null, op: "put" | "delete" | "metadata" }` additively to `OutboundFrame` (`protocolV1.ts`), the matching `InvalidationEvent` variant (`realtimeHook.ts`, with optional `userId`) and the `RealtimeMessage` / `parseRealtimeMessage` pair (`pgNotifyPublisher.ts`), validating every field and rejecting a malformed payload. The NOTIFY payload stays under the existing size cap. Preserve the exact key when the complete serialized relation message is at most 7000 UTF-8 bytes; otherwise publish the same relation message with `propertyKey: null`, meaning refetch all incoming and outgoing links for this item. Preserve IDs, op and optional user restriction. This is an explicit broader invalidation, never a truncated key, dropped event, storage-key rewrite or failed committed write. Validate bounded UUID/op fields before this size decision; reject malformed messages. The PostgreSQL-generated tenant envelope remains unchanged.
2. In `syncServer.ts`, map the new message to the outbound frame and send it with `sendToTenant(tenantId, frame, parsed.userId)`. Update the per-socket coalescer (`invalidationCoalescer.ts`) so relation frames coalesce on `(itemId, propertyKey)`, with `null` as a key of its own, and never replace item-scope frames.
3. In `relationOps.ts`, after each of `createRelationWithClient`, `updateRelationWithClient` and `deleteRelationWithClient` writes, register one `runAfterCommit` callback per end of the edge (the caller item with its own property key, the target item with the key of the other side of the definition; for a one-directional definition the target end has no property, so its frame carries `propertyKey: null`). `op` is `put` for create, `metadata` for update and `delete` for delete; a delete that removed no edge publishes nothing. Deduplicate within the active managed transaction by `(itemId, propertyKey)`, retaining the last complete event through the internal `runAfterCommitKeyed` facility owned by `db/pool.ts` (module-private symbol namespace, unambiguous tuple key). Keep one callback slot at first-registration order; replace its pending callback for subsequent writes. This invocation-owned state is discarded on every rollback/commit failure and cleared after terminal processing, so pooled-client reuse cannot retain keys. Require the exact active managed client before registration; do not change legacy `runAfterCommit` semantics or transaction opening, isolation, commit/rollback, error identity or client release.
4. Carry the acting user: add an optional `actingUserId` to the three edge input types and pass it from the application service for user and agent writes; it only narrows recipients. Internal writers that pass none reach every socket of the tenant.
5. Make `semprec-transcribe` and other non-API processes need no extra wiring: the callback uses `notifyInvalidation`, which `wireRealtimeHooks` already binds. Add a test that exercises it from a non-API caller path.
6. Document the client contract in the `protocolV1.ts` header comment: an invalidation for `(itemId, propertyKey)` means refetch what shows that link; an invalidation with `propertyKey: null` means refetch all incoming and outgoing links for that item, including the one-directional target and oversized-key cases. Update `packages/realtime-client` types so an older client that does not know `scope: "relation"` ignores the frame, and a current one exposes it.
7. Tests: a put and delete through REST and through an agent produce a frame per end after commit and none after a rollback; a task moved between projects produces frames for the task and both projects; an edge on a one-directional relation (a file's area) produces a frame for the file with its key and one for the area with `propertyKey: null`; a mail-folder sync that writes ten edges for one item publishes one event for that item and key; the message goes only to sockets of the writing tenant; a recorded old-client handler ignores the new scope; `parseRealtimeMessage` rejects bad payloads. Also cover last-op replacement, callback order, throw/COMMIT-failure disposal, exact same pooled-client reuse after rollback and successful commit, unmanaged/mismatched-client refusal, and real NOTIFY/socket delivery for oversized multibyte/escaped keys with the envelope under PostgreSQL's limit.

## Acceptance criteria

- When an edge is created or deleted through REST or by an agent, then, after commit, both ends receive a `relation` frame with `op` `put` or `delete`; when the transaction rolls back, nothing is sent.
- When a task is moved to another project, then another session receives frames for the task, the old project and the new project.
- When an edge of a one-directional relation is created or deleted, then the source item receives a frame with its property key and the target item a frame with `propertyKey: null`.
- When one transaction writes ten edges to the same item and key, then one event for that item and key is published.
- When the write comes from `semprec-transcribe` or another non-API process, then the frame arrives as it does from `semprec-api`.
- When the writer belongs to one tenant, then only that tenant's sockets receive the frame; with an acting user, only that user's sockets.
- When an older client receives `scope: "relation"`, then it ignores the frame.

- When a managed transaction rolls back or COMMIT fails, keyed relation callbacks never fire or survive into a later transaction on the same client; successful transactions publish the last event per key in first-registration order.
- When a valid relation message exceeds 7000 UTF-8 bytes, the bounded PostgreSQL notification and delivered relation frame carry `propertyKey: null` with the same tenant/item/database/op/user restriction; normal-size keys remain exact and null requests a full incoming/outgoing-link refetch.
