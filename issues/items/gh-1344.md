## Behavior specification

Calendar invitations: incoming invites, participants and e-mail invitations.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: calendar-invites-1

#### (a) Decisions adopted from open questions

- Change an answer after responding, and show accepted/tentative events in the calendar -> drafted as: an answer is final (a second respond is 409), no tentative marker. -> Decided by the product owner: an answer can be changed (a new REPLY is sent) and a "maybe" answer is shown on the Event as unconfirmed attendance; a final answer would contradict reversibility. Applied in #1944 and #1953; the timeline marker is #2008.
- CANCEL from the organizer: new cancelled state and Event to trash? -> drafted as: CANCEL ignored in v1, no cancelled state. -> Decided by the product owner: a CANCEL moves the created Event to the trash (restorable) and marks the invitation cancelled; ignoring it would leave an invalid meeting in the calendar. Status option in #1901, refusal to answer in #1944; the handling is #2006.
- Does a time or place change reset replies to pending? -> no, statuses are kept and an updated REQUEST with a higher SEQUENCE is sent -> least destructive option. -> Decided by the product owner: statuses are kept and an updated invitation with a higher SEQUENCE is sent.
- Default mailbox for invitations (setting) or choice on each send? -> mailboxId is required on each request that sends invitations; no default setting -> no setting exists and the sheet shows the sending account. -> Decided by the product owner: the mailbox is chosen on each send; no further setting in v1.
- Recurring invitation (RRULE) -> stored as one invitation for the first occurrence, rule ignored -> recurrence is a separate batch. -> Decided by the product owner: only the first occurrence; recurrence is a separate batch.
- Sequence update of an answered invitation -> drafted as: ignored, only pending invitations update. -> Decided by the product owner: the update is written into the created Event as an adopted value that stays until the user's first change; the user's answer stays and the user's manual edits are not overwritten. Delivered by #2007.
- Event type for an Event created from an invitation -> `meeting` -> the invitation is a meeting; recording matching depends on the type. -> Decided by the product owner: type `meeting`.
- Timed invitation without an end -> no explicit end; the Events pre-write transform supplies the default.
- Unknown TZID in an invitation -> fallback to the tenant time zone with a reason-coded log line -> avoids dropping the invitation. -> Decided by the product owner: the tenant time zone and a log line; the invitation is not dropped.
- Authenticity of REPLY mail -> sender address must equal the attendee address, no SPF/DKIM check -> prevents a trivial forged reply by an unrelated sender. -> Decided by the product owner: the sender address matching the attendee is enough for v1.
- REPLY SEQUENCE -> not compared; latest reply wins.
- Outgoing iCalendar times -> UTC instants, no VTIMEZONE; all-day events use DATE with exclusive DTEND.
- Restore of a deleted Event -> sends nothing. -> Decided by the product owner: nothing is sent; outgoing messages would need an explicit user action.
- Organizer edge creation -> created by the bulk participants route when it sends the first invitation; the edge validation only checks it.
- Notification for a new invitation -> once at first creation, category invites, link_href null, payload carries the invitation id.
- pendingInvites badge -> counts every pending invitations row (invite and notice kinds). -> Decided by the product owner: it counts every pending invitation, notices included.

#### (c) User-visible behavior of this chunk

When a meeting invitation arrives by email, the app creates a pending invitation (title, time, place, organizer, suggested calendar) and sends a push notification with Accept, Maybe and Decline actions; the badge counts pending invitations. Answering Accept or Maybe adds the event to the chosen or suggested calendar, Decline removes an existing one to the trash; the answer can be changed later (each change sends a new reply), an event answered Maybe is shown as unconfirmed attendance, and the organizer gets a standard calendar reply from the mailbox that received the invitation after the answer is saved. When the organizer updates an answered meeting, the event takes the new values for every field the user has not changed; when the organizer cancels it, the invitation is marked cancelled and the event goes to the trash. The notification disappears once answered. In the other direction, each event has participants with a role (organizer or attendee) and, for invited people, an invitation state (pending, accepted, maybe, declined); the participant list can be read and replaced in one step, optionally emailing invitations to those with an address (others are only linked). Invitations, updates after a time or place change, and cancellations (removal of a person or deletion of the event) are emailed from a chosen mailbox as standard calendar messages, and replies from invitees arriving by email update their state automatically.
