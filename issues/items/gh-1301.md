## Behavior specification

Calendar module: calendars, timeline, agenda, editing and Semp tools.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: calendar-module-1

#### (a) Decisions adopted from open questions

- Deleting a calendar: Events to trash or move to the default? -> Events go to the trash with the calendar (same deletion time), restore brings both back (#1803) -> Decided by the product owner: the confirmation states the number of Events.
- Colour: only from the calendar, or per Event? -> only from the calendar, no Event colour property -> Decided by the product owner.
- Tasks always in the Tasks calendar, or a calendar picker on tasks? -> always the Tasks calendar -> Decided by the product owner.
- Colour and notify for the Sleep calendar -> rows carry them like the others; the Sleep plan is handled elsewhere -> Decided by the product owner: Sleep behaves like the other calendars.
- Delete calendar confirmation with an event count -> the count comes from a separate delete-impact preview; the backend does not require confirmation -> Decided by the product owner: the client always shows the confirmation with the Event count from the delete-impact preview.
- Duplicating a recurring Task: new series or only the occurrence? -> new series from the copy's date -> Decided by the product owner.
- Copying inherited values and shared attachments -> copied values become the copy's own; missing relation properties are skipped -> Decided by the product owner.
- Events collection and recurring Events: stored derived `nextOccurrenceDate` kept fresh by a daily job -> sort, group and filter reuse the generic features.
- Multi-day Events inside "Today" via an end property -> left to the filter features; this chunk adds no filter.
- Which calendar writes may skip approval -> none; all three calendar tools require approval (completing a task in an event is the generic item write, #1781), answering an invitation always -> Decided by the product owner: answering an invitation sends email, so it always needs approval.
- Module tool names over MCP -> `semprec.<toolName>`, with a startup refusal of any module tool named like a generic operation -> manifest names are already namespaced and nothing can shadow a generic operation.
- Where calendar routes live -> the agenda and invitation routes in the calendar module; the duplicate route, which acts on Events and Tasks, in the systemDatabases module -> program rule on single-writer route ownership.
- Default calendar for an Event created while the cutover has not run -> no assignment instead of failing (#1761) -> Decided by the product owner: such an older Event without a calendar is kept and shown in the default calendar (the timeline returns the default calendar's id for it, #1717).
- A deleted default calendar -> the oldest remaining own calendar becomes the default (#1803) -> Decided by the product owner.
- Search in the calendar -> not built here; owned by the global search issues -> Decided by the product owner: the calendar uses the global search operation (#1842) with scope event and task; the calendar agenda only lays the results out by date.
- Deleting a calendar cancels its Events' invitations? -> Decided by the product owner: yes, but only after a confirmation. Each trashed Event with invited people sends cancellations through the Event delete reaction (#1803, #1774); the client's delete dialog states how many invited people will receive a cancellation (counted by the read route of #2003), and Semp can delete a calendar only with approval (`item.delete` requires it).

#### (b) Open questions for the product owner

- Should the design add the agenda list screen (its layout is not designed)?
- Should the Events collection show multi-day Events that are in progress under "Today"?

#### (c) User-visible behavior of this chunk

The calendar becomes a module with its own calendars: Personal, Work, Family and Health plus read-only Tasks, Birthdays, Sleep and Czech public holidays, with a default calendar, colours, visibility and notification settings that sync across devices. Every Event belongs to exactly one calendar (the default unless chosen), system calendars cannot be renamed or deleted, the last own calendar cannot be deleted, and deleting a calendar moves it and its Events to the trash so restoring brings both back; before deleting, the app always confirms and says how many Events and how many invited people (who will receive a cancellation) are affected. An Event or Task can be duplicated to a new date and time with a safe copy of its project, people, files and details (without recordings, invitations or completion state). A calendar agenda list pages through entries from any day in either direction, and recurring Events show once in the Events collection at their next occurrence. Semp and external MCP clients can use the calendar's tools (answer an invitation, complete or place a task in an event) with approval, and other modules' tools appear over MCP under their own names.


### Decisions: calendar-module-2

#### (a) Decisions adopted from open questions

- Multi-day Event: once with a range, or once per day? -> once, with its range -> Decided by the product owner: the client lays it across days.
- Timeline hidden calendars -> not filtered by the server; every item has `calendarId`, the client hides by the calendar's flag -> Decided by the product owner: Semp sees hidden calendars.
- Sleep night crossing midnight: one item or two day parts? -> one item, as the resolver returns it -> Decided by the product owner.
- Day view reads nights directly from the sleep endpoint, making the sleep timeline issue unnecessary? -> the timeline carries nights anyway -> day and month are served by one call.
- Design change to unify both month views (order, tasks without time, hidden filter, full titles, dragging) -> not adopted in the backend; the timeline returns one consistent order and `calendarId` for both -> Decided by the product owner: unifying the views is client work.
- Cross-tenant calendar sharing: mirroring (A) or invitations and ICS only (B)? -> B, recorded in an ADR (#1364); mirroring would need a new ADR superseding the "no sharing" part of the tenant isolation ADR -> Decided by the product owner: invitations and ICS only; sharing between tenants is out of v1 and contradicts tenant isolation.
- Can a shared-calendar recipient write? -> moot (no sharing in v1) -> Decided by the product owner.
- Timeline source extension point -> a source list in `timelineSources.ts` so six later sources do not edit the merge.
- Timeline string ordering -> compared with the tenant user's locale collation (cs by default), ties by id.
- Semp timeline tool capability -> `calendar.read`; the final capability id follows the grant decision for module tools.

#### (b) Open questions for the product owner

- Should the calendar day read sleep from the timeline (as built) or directly from the sleep endpoint?

#### (c) User-visible behavior of this chunk

The calendar screens (day, week strip, month) are fed by one call that returns everything in a date range in the user's own time zone: events (a multi-day event once, with its range), tasks with status, place, project, people, the calendar each belongs to, ordered consistently (all-day events, tasks without time, timed events, timed tasks); invalid stored values are skipped rather than breaking the screen. Sleep nights and the "prepare for sleep" reminder appear in the day view when sleep is enabled and shown in the calendar, and a night that crosses midnight is one entry. Semp and external assistants can ask for the same timeline through a read-only tool. There is no sharing of calendars between Semprec users in this version: people receive meetings by email invitation and can follow external calendars by ICS link, and the decision is recorded.
