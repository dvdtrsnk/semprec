## Context

`createAgentRunWatchRegistry(...).watch` (`backend/packages/realtime/src/agentRunWatch.ts:139-152`) authorizes an `agent:watch` frame by loading `getEarliestUserId(pool)` and `getAgentRun(pool, runId)` in parallel and rejecting when `ownerUserId !== userId` (line 150). The comment above it says "agent_runs has no per-row user column", which stopped being true with migration `0042_agent_runs_actor_user_id.sql` plus `agentRunsActorUserIdCutoverMigration.ts` (which sets `actor_user_id NOT NULL`): every `agent_runs` row now carries the user its writes are attributed to (`AgentRunRow.actorUserId: string`, `backend/packages/data/src/agentRuns/agentRunsStore.ts:27-35` — the session user for a user-triggered root run, the setup owner for heartbeat/system runs, the parent's actor for a delegated run). The current check therefore lets only the earliest-created account watch any run, and denies the user a run was actually triggered by whenever that user is not the earliest account.

`syncServer.test.ts` (`backend/packages/realtime/src/__tests__/syncServer.test.ts:930-952`) holds the `users` SELECT open to prove an `agent:unwatch` can overtake a pending watch; after this change the pending query is the `agent_runs` SELECT, so that test's lock target moves.

## Task

1. In `agentRunWatch.ts` `watch`, drop the `getEarliestUserId` call and import; load `run` with `getAgentRun(pool, runId)` alone and authorize with `run !== null && run.actorUserId === userId` (keep the existing pending-token and `ws.readyState` checks and the "unknown run is indistinguishable from unauthorized" behaviour: both fall through to `finishPendingWatch` + `return`). Rewrite the comment block (lines 141-144) to say the run's `actor_user_id` is the authorized watcher and that the column is `NOT NULL` after 0042's cutover, so no fallback exists.
2. **Tests** (`backend/packages/realtime/src/__tests__/syncServer.test.ts`, integration, in the existing `createSyncServer watched agent runs (issue #163)` describe):
   - A run created with `createAgentRun(pool, { triggeredBy: "user", task, userId: <second user> })` is watchable by that second user (replay of an existing event arrives) and not by the earliest user (no frame within the existing wait window).
   - A heartbeat-triggered run (`createAgentRun` without `userId`, so `actor_user_id` falls back to the earliest user) is watchable by the earliest user only.
   - Update the "cancels a watch when agent:unwatch arrives while its authorization query is pending" case to hold its blocking lock against `agent_runs` instead of `users` — `LOCK TABLE agent_runs IN ACCESS EXCLUSIVE MODE` in the blocking transaction, the same shape the test used for `users`; a row-level `FOR UPDATE` would not block `watch()`'s plain non-locking `SELECT` in Postgres, so it cannot serve this test (amended 2026-09-28: the original sentence prescribed `FOR UPDATE`) — and its comment accordingly.

### Out of scope

## Acceptance criteria

- When a user sends `agent:watch` for a run whose `actor_user_id` equals their user id, they receive the replay and live `agent_run_event`/`agent_run_delta` frames for that run, regardless of whether they are the earliest-created account.
- When a user sends `agent:watch` for a run whose `actor_user_id` is a different user, they receive no frames for that run, exactly as for an unknown run id.
- `agentRunWatch.ts` no longer imports or calls `getEarliestUserId`.
