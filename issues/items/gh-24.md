**Blocked by:** #23

## Context

Semprec is built on top of a generic schema engine (issue #21: value ownership via `owner: user/system`, generic `properties`/`rows`/`relations`, `relation_definitions`/`item_relations`) and on top of generic views with filtering and sorting (issue #22). This issue is the first concrete application of both: it defines the ten system databases that exist in the mock as a fixed set, each with its own properties and mutual relationships.

The description below is derived from how these databases *behave for the user* in the mock, not from how they are implemented there (the mock's relations are purely textual, without real IDs — that is a prototype simplification). The target is always a real `relation_definitions`/`item_relations` link from the schema engine (issue #21), never an ad-hoc field.

In a few places the mock contains inconsistencies relative to how the system should behave as a whole — these are explicitly flagged as a "fix" below and must be resolved by unifying the model, not by copying the mock literally. Where the mock is silent (does not define a behavior), Notion-like behavior is used as the default pattern.

The follow-up issue #25 ("Books and Movies/TV — generic library module") builds directly on this one but is NOT part of it — it covers a different pair of databases with a different character (library/catalog items, not operational system databases).

## Task

Implement all ten databases as instances of the generic schema engine from issue #21 — each is a `schema_locked` set of system properties (structure is not user-editable), but the user can still add their own extra properties unless stated otherwise for a given database. Relationships between them must be real `relation_definitions` records with bidirectional visibility wherever indicated, never one-directional or textual fields.

**Canonical keys are English camelCase.** All stored identifiers below — `databases.key` values, property keys, and select-option values — are English camelCase. The Czech names ("Oblasti", "Projekty", ...) and Czech option labels are display labels only, resolved per the app language setting (`users.locale`) by the i18n layer (issue #35, position 15/22); they are never stored as keys.

### 1. Areas (key `areas`, Czech label "Oblasti")

**Relations:** → Projects (1:N) · → Health records (1:1, bidirectional) · → Companies (1:1, bidirectional).

System database, non-editable schema, but the user can add their own extra properties.

**Properties:**
- `name` — `title`, owner: user
- `active` — `checkbox`, owner: user
- `note` — `text`, owner: user. In the mock this property is called `sledovane` and visually suggests a link (an arrow icon), but it is actually free-form note text, not a relation. Renamed to `note` so the name no longer promises a link it doesn't have.

### 2. Projects (key `projects`, Czech label "Projekty") — badge "hub"

**Relations:** → Areas (N:1, "Hub") · → Companies (N:1, bidirectional).

**Fix:** the mock models the link to a company as a free-form select ("Osobní"/"MeguMethod"), not as a relation. Unified with the existing Companies→Projects relation, so this becomes a real N:1 relation, not text.

Projects is the target of backlinks from 6 other databases (Tasks, People, Files, Events, Health records, Companies) — hence the "hub" badge. It has a mandatory `locked` property `agents` (a 4-section equivalent of an AGENT.md, owner: user) and its own `project_heartbeats` structure (defined in issue #21). System projects (modules such as Email, Personal finance...) additionally have a `systemActive` property — such a project can only be deactivated, never deleted.

**Properties:**
- `name` — `title`, owner: user
- `pinned` — `checkbox`, owner: user — pin to Home (mock label "Označeno")
- `status` — `select` (`inProgress`/`done`/`archived`/`longTerm`), owner: user
- `date` — `date`, owner: user
- `color` — `color`, owner: user
- `agents` — `longText`, 4 fixed sections (Purpose/Allowed/Not allowed/General instructions), owner: user, `locked: true` — must exist for every project
- `systemActive` — `checkbox`, owner: user, `locked: true` (deactivation only, never deletion), only present on system projects. **Fix:** the mock types it as `text` even though it behaves as a toggle.

### 3. Tasks (key `tasks`, Czech label "Úkoly")

**Relations:** → Projects (N:1, optional).

The `time` property is a derived, non-editable value (owner: system), composed from `timeFrom`/`timeTo`.

Task recurrence (new — the mock does not have it) runs through a separate `task_recurrence` table with two modes:
- **fixed calendar rule** — weekdays, specific dates within a month, or an "nth given weekday" (e.g. "second Tuesday") — computes the next due date purely from the rule, regardless of when the previous instance was completed;
- **floating interval** — computes the next due date from the actual completion date.

This is a rolling model: at any given moment only one open instance of a recurring task exists; completing it creates the next one.

```sql
CREATE TABLE task_recurrence (
  item_id uuid PRIMARY KEY REFERENCES items(id) ON DELETE CASCADE,
  mode text NOT NULL,             -- 'fixed' | 'floating'
  rule jsonb NOT NULL,
  -- fixed:    {kind:'weekdays', days:['mon','wed','fri']}
  --         | {kind:'month_dates', dates:[1,15]}
  --         | {kind:'nth_weekday', n:2, weekday:'tue'}   -- n:-1 = last in month
  -- floating: {unit:'days'|'weeks'|'months', n:2}
  active boolean NOT NULL DEFAULT true
);
```

**Properties:**
- `name` — `title`, owner: user
- `status` — `select` (`notDone`/`done`/`wontDo`), owner: user
- `date` — `date`, owner: user
- `timeFrom` / `timeTo` — `time`, nullable, owner: user
- `time` — derived from `timeFrom`/`timeTo`, owner: system, `locked: true` — not directly editable
- `notifications` — `checkbox`, owner: user
- `persistent` — `checkbox`, owner: user (mock label "Vytrvalé")

### 4. People (key `people`, Czech label "Lidé")

**Relations:** → Projects (N:N) · → Companies (N:N, bidirectional).

The link to Companies must be N:N, not 1:1 — when a person moves to a different company, they get a link to both (the current and the former one); the old link is not removed.

**Properties:**
- `name` — `title`, owner: user
- `relationship` — `select` (Parent/Therapist/Close friend/Girlfriend/Client/Neighbor...), owner: user — a closed but extensible list, not free text
- `contact` — `select` with emoji values (📞 Phone / ✉️ Email), owner: user

The People↔Emails link (the `emails` address-list property, the derived `senderPeople`/`recipientsPeople` relations, and the `person_email_index`) is NOT part of this issue — it is added later by issue #26's migration, which owns the Emails domain.

### Shared `blobs` table (prerequisite for the Files DB)

The Files DB's `file` property needs somewhere to point for actual binary content, so the shared `blobs` table is created in this issue, right before the Files DB. It is not Files-specific — it will later also be used by library cover images (issue #25) and email attachments:

```sql
CREATE TABLE blobs (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  mime_type text NOT NULL,
  byte_size bigint NOT NULL,      -- bigint, not integer — the upload limit elsewhere in the system runs into gigabytes
  storage_key text NOT NULL,       -- object key in object storage (MinIO)
  source_url text,                 -- where it was downloaded from, for re-fetch/debug; NULL for manually uploaded blobs
  content_hash text,                -- sha256 of the content; nullable — not every use case needs it right away
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX blobs_content_hash_uq ON blobs (content_hash) WHERE content_hash IS NOT NULL;
```

`content_hash` is intentionally nullable at this stage — hash-based dedup only starts to matter once the same content (an email attachment, a cover image) is repeatedly downloaded/uploaded. It is enough that the column and the partial unique index exist; dedup enforcement logic is not part of this issue.

### 5. Files (key `files`, Czech label "Soubory")

**Relations:** → Areas (N:1) · → Projects (N:N) · attachments for Health records and Companies (N:N, bidirectional).

**Added:** the mock's Files database has no property at all for the actual file content, only metadata about it — without it the database could describe a file but not actually store it. The `file` property of `type: 'file'` carries a `{ blobId }` value pointing into the `blobs` table (created above).

**Properties:**
- `name` — `title`, owner: user
- `type` — `select` (PDF/XLSX/DOCX/JPG...), owner: user
- `date` — `date`, owner: user
- `file` — `type: 'file'`, value `{ blobId }` over the `blobs` table, owner: user

### 6. Events (key `events`, Czech label "Události")

**Relations:** → Projects (N:1) · → People (N:N) · → Transcripts (1:1, bidirectional) · → Tasks (N:N, action items from a meeting) · → Companies (N:N, bidirectional).

**Fix:** the mock has `firma` as a free-form multiSelect ("Osobní"/"MeguMethod") — the same inconsistency as the mock's Projects `firma`. Unified with the existing Companies→Events relation ("meetings").

**Properties:**
- `name` — `title`, owner: user
- `type` — `select` (`event`/`standup`/`meeting`), owner: user
- `date` — `date` with time, owner: user

### 7. Health records (key `healthRecords`, Czech label "Zdravotní záznamy")

**Relations:** → Files (N:N, attachments) · → Projects (N:N) · → Areas (1:1, bidirectional).

**Fix:** the mock has the link to Areas one-directional only (from Areas); unified to bidirectional.

**Properties:**
- `name` — `title`, owner: user (labeled "Název" in the mock)
- `date` — `date`, owner: user
- `status` — `select` (`resolved`/`monitoring`), owner: user
- `subject` — `text` with an emoji icon (e.g. "🧑 Heduš", "🐕 Max"), owner: user — stays text, not a relation to People, because it also covers pets, which do not and should not exist in the People database
- `type` — `select` (`health`/`condition`/`symptom` — the mock's `typ-zdravi`/`typ-stav`/`typ-priznak` values translated to canonical keys), owner: user
- `tags` — `multi_select`, owner: user, an extensible list taken from the mock (Blood tests, Medication, Epilepsy, Dental hygiene...)

The question of AI access to sensitive content (health data about people and pets) is NOT part of this issue — it is a question of agent behavior across projects (agent/security review), not a schema question.

### 8. Companies (key `companies`, Czech label "Firmy")

**Relations:** → People (N:N, bidirectional) · → Events (N:N, meetings) · → Projects (N:1, bidirectional) · → Files (N:N).

**Properties:**
- `name` — `title`, owner: user
- `ico` — `text`, owner: user (IČO, the Czech company registration number — kept as the established domain term, already ASCII lowercase)
- `web` — `url`, owner: user

### 9. Transcripts (key `transcripts`, Czech label "Transkripce")

**Relations:** → Events (1:1, bidirectional) · → People (N:N, `speakers` — mapping of diarized speakers to people; the edge carries `{ speaker }` metadata; the exact mapping mechanics are outside the scope of this issue and are handled by the transcription-pipeline issue).

**Fix:** the mock leaves the status property freely editable, but it is purely a pipeline status — the owner must be system, written only by the transcription process; a fourth value, `error`, is added there on top of the mock's three.

The mock's Transcripts rows additionally carry `segmenty` (a segment-by-segment transcript, `{speaker, text}` — canonical computed key `segments`) and `shrnutiByInstrukce` (an AI summary based on a chosen instruction — canonical computed key `summaryByInstruction`) — the mock code itself marks these as non-generic, outside the normal cell values. These belong in `items.computed` (the cache from issue #21, written only by a background worker), NOT in `properties` — this is a derived output of the transcription pipeline; the user never edits it directly, only reads it.

**Properties:**
- `name` — `title`, owner: user
- `status` — `select` (`recording`/`processing`/`done`/`error`), owner: system, not editable by the user
- `date` — `date` with time, owner: system — the recording time, not user input
- `notes` — `longText`, owner: user
- `link` — `url` to the source audio, owner: system

### 10. Journal (key `journal`, Czech label "Deník") — badge "custom view"

**Relations:** → Areas (N:1, optional, nullable).

**Fix:** the mock has this link hardwired to a single Area, "Osobní", for absolutely every Journal entry regardless of content — this is an obvious simplification of demo data, not an architectural intent (it makes no sense for every day/week/month to belong to one fixed area). In reality: the field has no default value and stays empty until the user or an AI with write permission sets it — typically for a longer period where it makes sense (e.g. "vacation week" tagged to the Leisure area, "quarterly review" tagged to the Work area), not for every single day.

Journal is a system database like the others (NOT a separate `journal_pages` table, as an older version of the specification proposed — that proposal dates from a time when block-based page content did not yet exist; it exists now). A day's content runs on the same block/`docs` engine as other pages (defined outside this issue).

Journal is `schema_locked` and has no manual item creation via "+ New" — an item for a given date is created implicitly (lazily) by the first write, whether from the user via the UI or from automated processing.

Hence the "custom view" badge: instead of the Table/Board views from issue #22, Journal has its own "temporal-switcher" view type (year → quarter → month → week → day), which is not defined in issue #22 and is specific only to this database.

**Properties:**
- `name` — `title`, owner: system, generated (e.g. "📓 2026", "📓 2026-Q3"...)
- `type` — `select` (`year`/`quarter`/`month`/`week`/`day`), owner: system
- `period` — `text`, owner: system — a formatted label describing the date range

## Scope

### In scope

- Schema definitions (properties, types, owner, locked flags) for all ten databases exactly as specified above.
- Real relations between all ten databases via `relation_definitions`/`item_relations` (issue #21) — including bidirectional ones wherever indicated.
- Three specific fixes to mock inconsistencies: Projects→Companies and Events→Companies (from a free-form select/multiSelect to a real relation unified with the existing Companies→Projects/Companies→Events relation), Health records↔Areas (from one-directional to bidirectional), Transcripts `status` and Projects `systemActive` (owner/type changed to system-managed).
- The `task_recurrence` table and its two modes (fixed calendar rule, floating interval), including the rolling model of a single open instance.
- The shared `blobs` table (DDL + partial unique index on `content_hash`), created here as the prerequisite for the Files database.
- The `file` property of type `file` on the Files database as the link to the `blobs` table.
- Placing `segments`/`summaryByInstruction` in `items.computed`, not in `properties`.
- Lazy creation of Journal items on first write, plus the "temporal-switcher" view type.
- The mandatory `agents` property and `project_heartbeats` on Projects in its hub role toward the other six databases.
- Seeding default `created_by = 'system'` views for each of the ten system databases (the views infrastructure exists from issue #22).

### Out of scope

- Books and Movies/TV — generic library module (follow-up issue #25).
- The Email/inbox database and its own schema, including the People↔Emails link property, the `emails` address-list property on People, and `person_email_index` — all of that is owned and added by issue #26's migration.
- Transcription-pipeline mechanics and speaker diarization (only the `speakers` relation is referenced; the actual processing belongs to a separate transcription issue).
- The block/`docs` engine that Journal's content runs on (only referenced; the engine itself is defined elsewhere).
- Security/agent review of access to sensitive health data.
- The "temporal-switcher" view type as a general concept (only its use for Journal; the general definition of view types comes from issue #22, but this specific type is not defined there and must be defined here just for Journal's purposes).

## Dependencies

- **Issue #21** (schema engine, value ownership, generic properties/rows/relations, `relation_definitions`/`item_relations`, `items.computed`) — all ten databases are instances of it; this issue cannot be implemented without it.
- **Issue #22** (views, filters, sorting) — the standard views (Table/Board) over these databases build on it, and the seeded default system views use its infrastructure; Journal additionally needs a non-trivial extension for the "temporal-switcher" view.
- Email/inbox schema (out of scope; the People↔Emails link is added later by issue #26's migration).
