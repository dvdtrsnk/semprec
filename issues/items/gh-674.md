## Context

`ingestEmailMessage` (`backend/packages/data/src/mail/ingest.ts`, lines 90-227) is the one writer that turns a fetched message into an Emails item for all three sync adapters. It dedupes by RFC 5322 `Message-ID` alone: `getMailMessageMetaByMessageId(client, input.messageId)` (line 94), backed by `mail_message_meta.message_id text NOT NULL UNIQUE` (`backend/packages/data/src/db/migrations/0006_mail_sync.sql`, line 62) and `upsertMailMessageMeta`'s `ON CONFLICT (message_id) DO UPDATE` (`backend/packages/data/src/mail/mailMessageMetaStore.ts`, lines 97-128). A `Message-ID` is global: the same message delivered to two of the user's mailboxes (a CC to a work and a private address, a mailing list on both) is one physical message with one id. With two Mailbox items synced, the second mailbox's sync finds the first mailbox's item and only links it into its own folder (line 214-223), so one Emails item is a member of folders of two mailboxes. Everything keyed by the item is then shared across mailboxes: the `read`/`flagged` properties, and `mail_message_flag_sync_state` (`0045_mail_message_flag_sync_state.sql`, keyed by `message_item_id`), whose pending writes `listPendingImapFlagWrites` (`backend/packages/data/src/mail/mailMessageFlagSyncStore.ts`, lines 79-123) resolves through *every* folder edge of the item — marking the message read in mailbox A writes `\Seen` to its copy in mailbox B, and a later observation from B flips A back. The mail sync path is wired into the API runtime by #648 (`mailModuleIds`); the real transports are not (no mailbox onboarding exists), so this issue is written against the ingest/meta code and its existing tests (`backend/packages/data/src/__tests__/mailSync.test.ts`), not a live server.

Migration rules: `docs/adr/2026-09-10-expand-contract-forward-only-migrations.md` — the `UNIQUE (message_id)` constraint has to go in this same release for the fix to work at all (two rows with one `message_id` cannot coexist otherwise), which is the ADR's "intentionally breaking change explicitly called for by the linked issue's Task": after this release, the previous release's `ON CONFLICT (message_id)` has no arbiter and a `deploy.sh --rollback` would break mail ingest (fix-forward only). The lexical compatibility check does not flag `DROP CONSTRAINT`, so the file still carries an `-- expand-contract-exemption:` line stating this. Sibling issue C22 (flag observation) depends on this issue.

## Task

1. New migration `backend/packages/data/src/db/migrations/NNNN_mail_message_meta_per_mailbox.sql` (next free ordinal at commit time):
   - `ALTER TABLE mail_message_meta ADD COLUMN mailbox_item_id uuid;` (nullable; no FK — `items` is partitioned).
   - Backfill in SQL: for every row, set `mailbox_item_id` to the Mailbox item reached through the message's folder edge and that folder's mailbox edge — resolve the two relation definitions by property key (`properties.key = 'folder'` on the database with `owner_module_id = 'emails'`, and `properties.key = 'folders'` on the database with `owner_module_id = 'mailboxes'`, via `relation_definitions.property_id_a/property_id_b`), pick one folder edge per message (`DISTINCT ON (message item)` ordered by the folder item id), and leave rows with no resolvable edge `NULL`. Idempotent (`WHERE mailbox_item_id IS NULL`).
   - `CREATE UNIQUE INDEX mail_message_meta_mailbox_message_uq ON mail_message_meta (message_id, mailbox_item_id);` (the two columns in either order satisfy this criterion — the uniqueness is over the pair; `message_id`-leading is preferred so the index also serves the legacy `getMailMessageMetaByMessageId` lookup; amended 2026-09-28 after the implementer chose that order deliberately) then `ALTER TABLE mail_message_meta DROP CONSTRAINT mail_message_meta_message_id_key;` with the exemption line and a header comment explaining the per-mailbox identity, the rollback consequence, and that `NOT NULL` on `mailbox_item_id` is a later contract step.
2. `mailMessageMetaStore.ts`: `MailMessageMetaRow`/`UpsertMailMessageMetaInput` gain `mailboxItemId: string | null`; `upsertMailMessageMeta` inserts it and uses `ON CONFLICT (mailbox_item_id, message_id) DO UPDATE` (a `NULL` mailbox never conflicts — callers that pass `null` are the legacy migration only); new `getMailMessageMetaByMailboxAndMessageId(client, mailboxItemId, messageId)`; `getMailMessageMetaByMessageId` stays for the legacy migration's collision check and documents that it returns the first of possibly several rows.
3. `ingest.ts`: `IngestEmailMessageInput.mailboxItemId: string` (required); the dedup lookup at line 94 becomes `getMailMessageMetaByMailboxAndMessageId(client, input.mailboxItemId, input.messageId)`; the upsert passes `mailboxItemId`. Update the doc comment (lines 79-89): dedup is per mailbox.
4. Callers: `reconcileImapFolder` (`ReconcileImapFolderParams.mailboxItemId` becomes required, `backend/packages/data/src/mail/imapReconcile.ts` lines 65-83, passed at line 176-187; `reconcileImapAccount` already passes it), `gmailReconcile.ts` (line 152) and `graphReconcile.ts` (line 148) pass `params.mailboxItemId`; `mail/send.ts`'s claim upsert (lines 216-223) passes `input.mailboxItemId`; `migrationJob/mailLegacyEmailMigration.ts`'s two upserts (lines 128, 153) pass `mailboxItemId: null`.
5. Tests: `backend/packages/data/src/__tests__/mailSync.test.ts` — the same `messageId` ingested for two different `mailboxItemId`s produces two Emails items, each linked only to its own mailbox's folder; the same `messageId` ingested twice for one mailbox still converges on one item (existing dedup case, now with the new field); `listPendingImapFlagWrites` for mailbox A after marking A's item read returns only A's folder edge; the existing IMAP/Gmail/Graph reconcile cases pass with `mailboxItemId` added to their inputs. `mailSend.test.ts`: the Sent-folder sync of a just-sent message converges on the draft item for the sending mailbox. `newEmailHeartbeat.test.ts` and `itemRelationFilter.test.ts`: add `mailboxItemId` to their `ingestEmailMessage` inputs (compile-only change). The backfill is covered by an integration case in `mailSync.test.ts` that inserts a meta row with `mailbox_item_id = NULL` plus its folder/mailbox edges, re-runs the migration file read from disk (the `selectOptionKeysMigration.test.ts` pattern, lines 13-24 — so every statement in the file must be idempotent: `ADD COLUMN IF NOT EXISTS`, `CREATE UNIQUE INDEX IF NOT EXISTS`, `DROP CONSTRAINT IF EXISTS`, the backfill's `WHERE mailbox_item_id IS NULL`) and asserts the column is filled.

## Scope

### In scope
- Per-mailbox message identity: the column, backfill, unique index, constraint drop, the ingest/upsert switch, caller updates and tests.

### Out of scope
- Observed-flag reconciliation and re-fetching flags for known UIDs (sibling issue C22).
- `mail_message_meta_provider_msg_uq` (provider ids are per account; not observed to collide).
- `NOT NULL` on `mailbox_item_id` (later contract step) and threading across mailboxes (`mail_threads` stays global).
- Real IMAP/Gmail/Graph transports and mailbox onboarding.

## Acceptance criteria

- When the same `Message-ID` is ingested for two mailboxes, two Emails items exist, each linked only to folders of its own mailbox, with independent `read`/`flagged` state; a pending flag write for one mailbox never targets the other mailbox's folder.
- When the same `Message-ID` is ingested twice for one mailbox, one item exists (dedup unchanged within a mailbox).
- After the migration, every pre-existing `mail_message_meta` row with a folder edge carries the right `mailbox_item_id`, and the migration file passes `check-migration-numbering` and the compatibility unit test via its stated exemption.
