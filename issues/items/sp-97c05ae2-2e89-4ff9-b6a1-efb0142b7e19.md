## Context

Model tier rationale: Changes the per-minute stall verdict of every mailbox (two check families, the pass lease, the notification and Semp problem they raise) and the transition primitive every observability check uses, with lock ordering against running sync passes and concurrent check runs.

Production evidence (dev VPS v0.3.5, fresh database, one Purelymail IMAP mailbox added about 15:09 UTC, IMAP IDLE live sync on, an e2e test sending, flagging and moving mail 15:10–15:20 UTC; every pass succeeded, no errors logged): at exactly 15:17:00 UTC the `notifications` table got two `mail_sync_stalled` notifications ("Synchronizace pošty se zasekla") and one `semp_problem`, i.e. the minute cron's `observabilityCheckSystem`. At 15:21 `mail_account_sync_state` showed `last_activity_at` 15:18:13, `next_expected_activity_at` 15:48:13, `last_successful_sync_at` 15:18:13, `failing_since` and `last_failure_kind` NULL. The mailbox was healthy, and was reported stalled twice.

Root cause, from the code:

- **`mail:<id>` reads a scheduling instant as a deadline.** An IMAP pass that ends with backfill or folder work left (`complete = false`: the ten-message budget, a folder moved on by another pass) records `next_expected_activity_at = now()` so the sweep resumes it even if the follow-up is lost, and asks for a rerun (`requestMailSyncRerun`); the release enqueues the follow-up, which claims the lease and runs for seconds (connection, LIST/STATUS, fetches at the VPS's RTT). `checkMailSync` alerts as soon as `next_expected_activity_at < Date.now()`, so a tick that falls between such a pass and the end of its follow-up flips the check to `alerting`, notifies and raises the `mailSyncError` problem, although a pass holds the lease or just finished. Under the e2e's steady deliveries, flags and moves such passes run all the time. The `semp_problem` of the evidence can come only from this family.
- **The heartbeat family judges the mailbox on the live-sync host alone.** `checkMailSyncLiveness` alerts on a `mailsync:<id>` heartbeat older than 60 s or missing, whatever the passes do. The heartbeat is installed only once the root hosts the account (discovery every 60 s) and stops whenever the root retires the lifecycle (Mail switched off and on again, sync mode change, a discovery that leaves the account out); a mailbox whose passes keep succeeding is then reported stalled until the root hosts it again. Which of these gaps occurred on the VPS cannot be read from the evidence; two notifications plus one problem in one tick is exactly what both families produce together for one mailbox.
- **Two families notify independently.** Each writes its own `mail_sync_stalled` (different check rows, different `transitionInstance`), so one stalled mailbox can notify twice in one tick.
- **A first transition is not serialized.** `transitionCheckIn` reads the previous status `FOR UPDATE`, but a missing row locks nothing: two concurrent check runs both see `null`, both upsert, and both report `transitionedToAlerting`, each notifying under its own job id.

Decisions:

- **A running pass holds the verdict.** While the mailbox's pass lease is live (`pass_lease_token` set and `pass_lease_expires_at > now()`), both mailbox checks keep their previous status (`ok` when there is none): no alert and no recovery, so a pass in flight neither reports a stall nor flaps an alerting check. A holder that died stops renewing and its lease expires after five minutes, so a stuck pass is judged again then.
- **Overdue means overdue by more than a grace.** `next_expected_activity_at` counts as overdue only once it is more than `MAIL_SYNC_STALL_GRACE_MS` (10 minutes, two runs of the five-minute sweep, which re-enqueues every due account) in the past. A backfill's "due now" is therefore met by its follow-up or the sweep before it can alert; a mailbox whose passes really stopped still alerts. `last_error` still alerts at once (a failed last pass is a real failure).
- **A recent successful pass vouches for the mailbox.** The heartbeat family alerts only when, besides the stale or missing heartbeat, no pass is running and none succeeded within the same grace (`last_successful_sync_at`). A dead live-sync host still alerts once its passes stop.
- **Time is the database's.** The overdue, recent-success and lease predicates are computed in SQL with `now()` under the sync state row lock, not against the worker's clock.
- **One notification per mailbox per episode.** Both families of a mailbox take the mailbox's sync state row `FOR UPDATE` first, then transition their own check row. A family that flips to `alerting` notifies only when the other family's check of the same mailbox is not already `alerting`. Only `mail:<id>` raises the Semp problem, as today. Both check rows stay as they are for the health report.
- **First transitions are serialized.** `transitionCheckIn` inserts a missing row (`ON CONFLICT DO NOTHING`) before it locks it, so a concurrent run waits for the first one's commit and sees its status; a sustained fault transitions, and notifies, once whichever run gets there first. This applies to the global checks too.

## Task

Load `state-writes`, `error-handling`, `testing`.

1. `observability/observabilityChecksStore.ts`: `transitionCheckIn` inserts a missing row before locking it, then updates it; add a status read for another check key of the caller's tenant.
2. `mail/mailAccountSyncStateStore.ts`: a row-locking read for the stall check that returns the row plus `passRunning`, `overdue` and `recentlySynced` computed with the database clock and a given grace.
3. `observability/observabilityCheckSystem.ts`: `checkMailSync` and `checkMailSyncLiveness` use it (lease hold, grace, recent success), and each notifies only when the other family's check of the mailbox is not alerting.
4. Tests as in the Acceptance criteria; the existing stall tests use an overdue time beyond the grace.

## Scope

### In scope

- The two mailbox stall predicates, their lease and grace handling, the cross-family notification dedupe, the transition serialization, tests.

### Out of scope

- Why the VPS's live-sync heartbeat went stale or missing (host lifecycle, discovery cadence, pool sizing); this issue makes the check robust to it.
- The pass lease, the backfill budget, the sweep cadence and the IDLE lifecycle themselves.
- Notification copy, kinds, the Semp problem's severity rules and the health report.
- Any request against a real server.

## Acceptance criteria

- Against the production `mailAccountSync` handler with a fake IMAP account: after a pass that leaves backfill (more than ten new messages) the check finds the mailbox `ok` with its follow-up only queued, also with the mailbox's heartbeat stale; no `mail_sync_stalled` notification and no Semp problem are written.
- While a pass holds the lease (held at its folder listing) and `next_expected_activity_at` lies beyond the grace in the past with a stale heartbeat, the check writes no notification and no problem and leaves both checks `ok`; once that pass finished, a check still writes nothing.
- A mailbox with no pass running, `next_expected_activity_at` an hour overdue and a stale heartbeat gets exactly one `mail_sync_stalled` notification and one Semp problem, also over repeated ticks; a lease whose holder died (expired) does not prevent it.
- Two check runs started concurrently against that stalled mailbox write one notification and one problem; two concurrent runs against a stale fixed process write one `process_stale` notification per admin.
- The existing observability, liveness, Semp problem, notification, mail sync and isolation test files stay green.
