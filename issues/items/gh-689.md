**Blocked by:** #687

## Context

`coreAgentRunAction` (`backend/packages/data/src/scheduler/actions.ts:55-85`) is the `ActionHandler` behind every `core.agentRun` heartbeat. The fire task (`backend/packages/data/src/scheduler/sweep.ts`, `createHeartbeatFireTaskForAffinity` and `runScheduledOccurrenceFire`) invokes it once per graphile-worker attempt (`maxAttempts: 3` for both sweep-driven and manual fires). On each attempt the handler creates a new `agent_runs` row (line 64) and, when `runAgent` throws, closes it with `finishAgentRunWithErrorNotification` (line 80), which writes an `agent_run_error` notification keyed on the run id. A heartbeat run that fails three times therefore produces three `error` runs and three `agent_run_error` notifications, plus the `heartbeat_error` notification the fire task writes on the final attempt — four notifications for one failed occurrence.

Line 80-81 has a second defect: `await withTransaction(pool, (client) => finishAgentRunWithErrorNotification(...)); throw err;` — when the close-and-notify transaction itself throws (database outage, `writeNotification` failing), that error replaces `err`, so the job's `last_error` and the retry decision are based on the bookkeeping failure and the original `runAgent` error is lost from every log and row.

`ActionContext` (`actions.ts:8-15`) carries no attempt information, so the handler cannot tell a retry from a final attempt; the fire task has it (`helpers.job.attempts`, `helpers.job.max_attempts`, already used at `sweep.ts:191,257`). This issue lands after D4 because D4 restructures the two handler call sites in `sweep.ts` that this issue extends.

One `agent_runs` row per attempt is kept on purpose: each attempt is a real session with its own events, and re-opening a finished run would break the finish-once contract sibling issue D1 of this batch establishes.

## Task

1. **`ActionContext.isFinalAttempt`.** In `actions.ts` add `isFinalAttempt?: boolean` to `ActionContext` with a docstring: set by the heartbeat fire task from the queue job's `attempts >= max_attempts`; `undefined` for a caller outside the queue (treated as final — a direct caller has no retry). In `sweep.ts`, both `handler(...)` calls pass `isFinalAttempt: helpers.job.attempts >= helpers.job.max_attempts` (the scheduled path computes the same expression already inside its `catch`; hoist it to a `const` above the `try` and reuse it in both places).
2. **Notify once, on the final attempt only.** In `coreAgentRunAction`'s `catch`: when `context.isFinalAttempt === false`, close the run with `finishAgentRun(pool, run.id, "error", message)` (no notification); otherwise keep `finishAgentRunWithErrorNotification` inside `withTransaction`. Document in the handler's docstring that a non-final attempt's run is closed as `error` silently and the `agent_run_error` notification is written by the final attempt only, so a failed occurrence yields exactly one `agent_run_error` (linking to the last attempt's run) plus the fire task's one `heartbeat_error`.
3. **Never mask the original error.** Wrap the close (both variants) in its own `try/catch`: on failure `logger.error({ err: closeErr, agentRunId: run.id, heartbeatId: context.heartbeatId }, "core.agentRun: failed to record failed agent run lifecycle")` and fall through to `throw err` (the original). `logger` is a module-local `const logger = createLogger("scheduler")` from `@semprec/shared` (the pattern `backend/packages/data/src/transcription/transcriptionActions.ts:25` uses).
4. **Tests** — new file `backend/packages/data/src/__tests__/coreAgentRunAction.test.ts` (integration; seed a user so notifications can be written, create a heartbeat, call `coreAgentRunAction(pool, runAgent)` directly with a hand-built `ActionContext`):
   - `runAgent` rejects; called with `isFinalAttempt: false` twice and `isFinalAttempt: true` once → three `agent_runs` rows with `status='error'` and `result` = the message, exactly one `agent_run_error` notification, whose `source_id` is the third run's id; each call rejects with the original error.
   - `isFinalAttempt` omitted and `runAgent` rejects → one run in `error` and one notification (direct-caller semantics).
   - `runAgent` rejects with `new Error("model failed")` and the pool wrapper makes the close transaction's `connect()` reject with `new Error("db down")` → the handler rejects with `model failed` (not `db down`), and the run row is still `running` (documented consequence: the next startup repair closes it).
   - Through the fire task: a `core.agentRun` heartbeat fired via `createHeartbeatFireAgentTask` with a rejecting `runAgent` and `helpers.job.attempts = 3, max_attempts = 3` → one `agent_run_error` and one `heartbeat_error` notification; with `attempts = 1` → zero `agent_run_error` notifications and the run row in `error`.
   The two existing `core.agentRun` cases in `scheduler.test.ts` (lines 239-300) must keep passing unchanged.

## Touches

## Scope

### In scope
- `isFinalAttempt` on `ActionContext`, single-notification error close in `coreAgentRunAction`, the non-masking wrap, and the tests above.

### Out of scope
- Reusing one `agent_runs` row across attempts (rejected: see Context).
- The fire task's own final-attempt handling and `heartbeat_error` notification (D4) and sweep chunking (sibling issue D5).
- Passing `isFinalAttempt` to any other `ActionHandler` implementation's logic (they may ignore the new optional field).
- `finishAgentRun`'s return value (sibling issue D1); this handler may ignore it because it created the run in the same call.

## Acceptance criteria

- When a `core.agentRun` occurrence fails on all three attempts, exactly one `agent_run_error` notification and one `heartbeat_error` notification exist for it; the three attempts' `agent_runs` rows are all `error`.
- When a non-final attempt fails, its run is closed as `error` and no `agent_run_error` notification is written.
- When the close-and-notify write fails after `runAgent` failed, the handler rejects with the `runAgent` error and the close failure appears only in the log.
- A caller invoking `coreAgentRunAction` without `isFinalAttempt` gets the pre-existing behaviour (run closed as `error` with one notification).
