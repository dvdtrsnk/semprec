## Context

This is Part 2 of the review follow-ups pipeline (epic #565): the Relay workflow that triages a harvest issue. It turns the issue into proposed follow-up issues, or into reasoned rejections. Everything it runs already exists:

- #583's daily harvest creates a harvest issue labelled `followups:harvest` + `followups:ready`, whose body carries a JSON data block of findings;
- #577's `.github/scripts/review-followups/prepare.mjs --harvest-issue <n> --out <dir>` writes `<dir>/input.json`. It reads GitHub and needs the `GITHUB_*` variables;
- #581's skill `.claude/skills/triage-review-followups/SKILL.md` has one section per agent prompt: orient, verify, decompose, audit, fix. Each ends with `Relay-Step-Status: pass`, or `blocked` when the input is missing. It writes only `.followups/proposal.json` (plus working files) and never touches GitHub;
- #578's `validate.mjs --input <file> --proposal <file>` exits 0 or prints one `- ` line per violation and exits 1. It works offline;
- #580's `publish.mjs --input <file> --proposal <file>`, as `bb-agent-relay[bot]`, creates the epic and the issues labelled `followups:issue` + `spec:proposed`, posts the triage-result comment, removes `followups:ready` and closes the harvest issue. It needs the `GITHUB_*` variables.

**Required Relay feature.** This workflow needs the command-step option `github-api: true` from dvdtrsnk/bb-plugin-relay#57, deployed on the Relay host. With it, Relay starts its loopback token proxy for the step and sets `GITHUB_API_URL`, `GITHUB_GRAPHQL_URL`, `GITHUB_REPOSITORY` and a placeholder `GITHUB_TOKEN` in the job's environment. The real Relay App token never enters the job. Without the option, a command step has no GitHub credential. Today `gh` in a command step only works because the host happens to be logged in as the maintainer's personal account, which is exactly the authorship the epic rules out. Do not merge this workflow before that plugin version is running.

Relay facts this workflow relies on (bb-plugin-relay, `workflows/format.ts`, `workflows/steps/command.ts`, `src/server/workflows/claims.ts`):

- **Worktree.** A `command` step before the first `agent` step runs in a throwaway Relay checkout, whose files are removed when the step ends. After an agent step, it runs in that agent's worktree. So a first agent step (`orient`) is what creates the worktree `prepare` writes into.
- **Shared thread.** All agent steps of a run share one thread and worktree, based on a freshly fetched `origin/develop`.
- **Claim.** An issue trigger has no claim label. On success the claim is released, so the run must close the issue or drop the trigger label, which `publish` does. On failure Relay retries the whole run from scratch with back-off, up to 5 times, and then adds `agent:blocked`. On blocked, the claim holds only while a park label (`agent:blocked` / `agent:needs-human-action`) is present.
- **Blocked-by parsing.** `respect-blocked-by` reads the first line containing "blocked by" in the body. A harvest issue's findings may contain that phrase, so it is disabled here.
- **Integrity.** An agent can edit any file in its worktree. The deterministic steps must run the `develop` copy of `.github/scripts/review-followups/`, so each such step first fails when that directory differs in any way from the worktree's `develop` fork point (committed, staged, unstaged or untracked). The epic decided that this parks the run.

**Protected path, maintainer-implemented.** `.relay/**` is in `.relay/config.yml`'s `protected-paths`. This issue is implemented by the maintainer, never dispatched to Relay, and must not be labelled `agent:ready`. Validate the file with `bb relay validate` before merging.

## Task

This issue is maintainer-implemented (protected path).

1. Add `.relay/workflows/triage-review-followups.md` with `id: triage-review-followups` and a `name`:
   - `priority: 30`, with a comment: below the review/merge/fix flows, which finish work already in flight, and above `implement-issue` (20), so a pending harvest does not starve behind new implementations;
   - `max-concurrent: 1`;
   - trigger `issues: { label: followups:ready, exclude-labels: [agent:blocked, agent:needs-human-action], respect-blocked-by: false, skip-if-open-pull-request: false }`.

   Steps, in this order:

   | Step | Kind | What it does |
   |---|---|---|
   | `pickup` | `comment` | a one-line pickup note |
   | `orient` | `agent` | prompt `#orient` |
   | `integrity` | `command` | the integrity check alone; `on-failure: blocked` |
   | `prepare` | `command` | `github-api: true`; runs the integrity check, then `node .github/scripts/review-followups/prepare.mjs --harvest-issue {{issueNumber}} --out .followups` |
   | `verify` | `agent` | prompt `#verify` |
   | `decompose` | `agent` | prompt `#decompose` |
   | `audit` | `agent` | prompt `#audit` |
   | `validate` | `command` | the integrity check, then `node .github/scripts/review-followups/validate.mjs --input .followups/input.json --proposal .followups/proposal.json`; on failure go to `fix` |
   | `publish` | `command` | `github-api: true`; the integrity check, then `node .github/scripts/review-followups/publish.mjs --input .followups/input.json --proposal .followups/proposal.json`; `on-failure: blocked`; `on-success: end` |
   | `fix` | `agent` | prompt `#fix`, which passes the validator's output (`{{steps.validate.outputTail}}`); then `validate-2` |
   | `validate-2` | `command` | as `validate`; on success go to `publish`; on failure go to `fix-2` |
   | `fix-2` | `agent` | prompt `#fix-2`, which passes `{{steps.validate-2.outputTail}}`; then `validate-3` |
   | `validate-3` | `command` | as `validate`; on success go to `publish`; `on-failure: blocked` — Relay turns a spent `max-rounds` budget after a failing command into a failed run, so the loop is unrolled |

   - `on-failure`: a comment saying the run failed and Relay retries it with back-off.
   - `on-blocked`: add `agent:blocked`, then a comment with `{{errorLine}}` telling the maintainer to remove `agent:blocked` to re-run. A re-run starts again at `prepare` and never re-proposes a published finding.
2. The body has the prompt sections `## prompt: orient`, `## prompt: verify`, `## prompt: decompose`, `## prompt: audit`, `## prompt: fix` and `## prompt: fix-2`. Each one tells the agent to follow the same-named section of `.claude/skills/triage-review-followups/SKILL.md` (`fix-2` follows the `fix` section), and adds nothing else except, in `fix` and `fix-2`, the validator output. Above them, a short description says what the workflow does, what each step is for, and why `orient` exists.
3. In `.github/ISSUE_FORMAT.md`'s Labels table, add `triage-review-followups` to the workflows whose `on-blocked` chain sets `agent:blocked`, and say that there it parks a harvest issue.

   - in both cases a triage-result comment by `bb-agent-relay[bot]` and the harvest issue closed without `followups:ready`.
