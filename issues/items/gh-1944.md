## Context

Model tier rationale: A new tenant-facing mutation that changes an invitation's status and creates, restores or trashes an Event across two databases in one transaction, with a status machine that allows changing an answer, caller-chosen calendar validation and cross-tenant isolation, so a defect corrupts calendar data or leaks across tenants.

#1929 fills the Invitations database from incoming mail with `pending` rows. This issue lets the user answer one. It adds `POST /api/calendar/invitations/:id/respond`, a custom route of the calendar module (the program rule: the calendar module registers its own routes only for calendar-specific resources such as invitations; Tasks and Events routes belong to the systemDatabases module). A custom route is justified here as `transactional-semantics`: the status change and the Event write must commit together, which the generic item endpoints cannot express.

Behavior of an answer:

- `accepted` and `tentative` create an Event for the invitation (title, place, wall-clock start and end in the tenant time zone) in the chosen calendar, link it through the invitation's `event` relation, and set `status` and `respondedAt`. Both answers produce the same Event; the calendar shows a `tentative` answer as unconfirmed attendance from the invitation's status (#2008 returns it in the calendar timeline), so nothing tentative-specific is written to the Event.
- When the invitation already has an `event` edge (the user changes an earlier answer), no second Event is created: a live linked Event is kept unchanged (the user's own edits stay), and a linked Event that is in the trash (after an earlier `declined`) is restored through the existing restore path (`restoreItemWithClient`).
- `declined` sets `status` and `respondedAt`, and moves the invitation's Event to the trash if one exists (the Event is not deleted permanently).
- `acknowledged` is accepted only for a row of kind `sharedCalendarNotice` and only moves its status; an invitation of kind `invite` accepts the other three answers only.
- The tenant time zone and "wall clock" conversion use the calendar time module from #1418. A timed invitation without an end gets no explicit end; the Events pre-write transform from #1598 supplies the default. An all-day invitation becomes an Event with `timeFrom` empty, `date` the first day and `endDate` the last day when it differs. Writing the Event goes through the choke point, so the date and time validation from #1663 applies and a failure rolls everything back.
- The calendar is `calendarId` from the body when given, otherwise the invitation's `suggestedCalendar`. The Event is created with that calendar passed at creation, in the way #1761 defines for callers that choose their own calendar, so the default-calendar create hook does not add a second one.

Decision (product owner): an answer can be changed. Answering an invitation that is already `accepted`, `tentative` or `declined` with a different answer applies the new answer as above and sets a new `respondedAt`; #1953 then sends a new reply to the organizer. Answering with the answer that is already stored changes nothing and returns the invitation unchanged. Answering an invitation whose status is `cancelled` (the organizer cancelled it) returns 409 `conflict`.

Decision (product owner): the Event created from an invitation has `type` `meeting`.

Decision: a chosen calendar has to be a live, user-owned calendar (not a system or subscription calendar); otherwise the request fails with 400 `validation_failed` (field `calendarId`).

The reply message to the organizer is sent by #1953 after this transaction commits; this issue does not send anything.

Shared-file ordering: this issue also waits for #1937 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `backend/packages/data/src/calendar/invitationRouteHandlers.ts` exporting `createRespondToInvitationRouteHandler`. It parses the body with zod (`{ response: "accepted" | "tentative" | "declined" | "acknowledged", calendarId?: uuid }`) and in one `withTransaction`:
   - loads the invitation row `FOR UPDATE` in the caller's tenant scope; an unknown id, or an id of another tenant, is 404 `not_found` identical in both cases;
   - checks the kind/response pairing (400 `validation_failed`, field `response`) and that `status` is not `cancelled` (409 `conflict`); when `response` equals the stored `status`, returns the invitation without writing anything;
   - for `accepted`/`tentative`: when the invitation has no `event` edge, resolves and validates the calendar, creates the Event and creates the invitation's `event` edge; when it has one, keeps a live linked Event unchanged and restores a trashed one with `restoreItemWithClient` (`calendarId` is then ignored);
   - for `declined`: trashes the linked Event if there is one, through the existing trash path (`chokePoint/itemTrash.ts`);
   - writes `status` and `respondedAt` as the calendar module's system owner process.
   Return the updated invitation item.

## Scope

### In scope

- The respond route, its status machine including a changed answer, the Event creation, restore or trashing, and its tests and route registrations.

### Out of scope

- Sending the iMIP reply to the organizer: #1953.
- Resolving the invitation's notification and the pending badge: #1954.
- Returning the `tentative` answer with the Event in the calendar timeline: #2008.
- Marking an invitation `cancelled` when the organizer cancels it: #2006; this issue only refuses to answer a cancelled one.
- A Semp agent tool and MCP tool for answering (it needs approval because it sends mail): #1957.
- Answering invitations from other Semprec users: shared calendars are not planned yet; they wait for a product decision.

## Acceptance criteria

- When the user answers `accepted` for a pending invitation, then an Event exists on Thursday 22 Oct 2026 13:00-14:00 (tenant zone) in the chosen or suggested calendar, the invitation links to it, and its status is `accepted` with `respondedAt` set.
- When the Event write or its validation fails, then the invitation stays `pending` and no Event exists.
- When the user answers `declined`, then the status is `declined`, and a previously linked Event is in the trash.
- When an `accepted` invitation is answered `tentative`, then its status is `tentative` with a new `respondedAt` and the same linked Event still exists unchanged.
- When a `declined` invitation whose Event is in the trash is answered `accepted`, then that Event is restored and linked, and no second Event exists.
- When an invitation is answered with the answer it already has, then nothing is written.
- When a `cancelled` invitation is answered, then the response is 409 `conflict` and nothing changes.
- When the id belongs to another tenant or does not exist, then the response is 404 and nothing is read or written.
- When a client sends a generic `PATCH` of `status`, then the response is still 403.
