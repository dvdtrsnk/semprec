## Context

`semprec-ai-gateway` has no shutdown path. `backend/services/semprec-ai-gateway/src/serve.ts` creates a pool, calls `startProcessHeartbeat(...)` and **discards the `ProcessHeartbeatHandle` it returns**, builds the dispatcher, and calls `server.listen(...)`. It registers no signal handler — `grep -rn "SIGTERM\|SIGINT" backend --include=*.ts --exclude-dir=node_modules --exclude-dir=dist` returns nothing, so no first-party service has one. `installFatalHandlers` covers only `uncaughtException`/`unhandledRejection`, and exits non-zero.

On an ordinary deploy or `systemctl restart`, the process is therefore killed where it stands: in-flight `POST /internal/complete` requests die mid-response, the heartbeat interval keeps firing until the process dies (it is `unref()`ed, so it does not hold the process open), and the pool is never closed.

The in-flight case is what makes this worth doing in this service specifically. `withTokenAccounting` in `backend/packages/ai-gateway/src/gateway.ts` budget-checks, then awaits the provider call, then writes the `ai_gateway_calls` row. A process killed between the provider returning and that INSERT loses a call that was already paid for — and `getGatewaySpend` in `backend/packages/data/src/aiGateway/aiGatewayCallsStore.ts` reads `ai_gateway_calls` back to enforce the daily and monthly caps, so every such loss under-counts spend against the cap. The window is narrow, but it is open on every restart and it silently loosens a budget control.

#91 gives `semprec-api` and the new `semprec-agents` their own SIGTERM/SIGINT paths as part of standing up their queue runtimes, and specifies its own ordering there. This issue does not depend on it and does not constrain it: `semprec-ai-gateway` hosts no graphile-worker runner, #91's own shutdown work lands in the other two services' roots, and the two changes share no file, export or helper. Either may land first.

## Task

Add a bounded, idempotent graceful shutdown to `semprec-ai-gateway`.

Add `backend/services/semprec-ai-gateway/src/shutdown.ts` exporting:

- `SHUTDOWN_DRAIN_TIMEOUT_MS = 60_000`. Derived, not chosen: the only caller of this service, `backend/packages/ai-gateway-client/src/httpAiGatewayClient.ts`, sets `REQUEST_TIMEOUT_MS = 60_000`. A shorter drain would cut off exactly the paid-for provider call this issue exists to protect, while the caller is still waiting for it. systemd's `DefaultTimeoutStopSec` of 90 s already exceeds this, so the unit files #176 installs need no change for this to work.
- `DRAIN_POLL_INTERVAL_MS = 50` and `POOL_END_TIMEOUT_MS = 5_000`.
- `createGracefulShutdown({ server, pool, heartbeat, logger, drainTimeoutMs })`, returning `shutdown(signal: string): Promise<void>`. `drainTimeoutMs` is optional and defaults to `SHUTDOWN_DRAIN_TIMEOUT_MS`; it exists because `backend/vitest.integration.config.ts` sets `testTimeout: 30_000`, so the timeout branch is otherwise unreachable in the tier this issue assigns it to. It is for tests and for no other purpose.
- `registerShutdownSignals(shutdown)`, which wires `process.on("SIGTERM", ...)` and `process.on("SIGINT", ...)` so each handler awaits `shutdown(signal)` and then calls `process.exit(0)`. `on`, not `once`: `once` removes the listener after the first signal, so a second SIGTERM during a drain of up to 60 s would fall through to Node's default action and kill the process mid-INSERT — the exact loss this issue exists to close. `shutdown()`'s own idempotency makes the repeat harmless. It lives here rather than inline in `serve.ts` so the registration itself is testable — `serve.ts` is a top-level side-effecting script that requires `DATABASE_URL`, `ANTHROPIC_API_KEY` and the `AI_GATEWAY_*` variables at import.

Dependencies are injected rather than reached for, matching the separation `startupConfig.ts` already uses to keep `serve.ts` a thin wiring script. Import `Pool` as `import type { Pool } from "pg"` (as `app.ts` and `completeHandler.ts` already do — `@semprec/data` exports `createPool`, not `Pool`) and `ProcessHeartbeatHandle` as `import type` from `@semprec/data`, so a `.unit.test.ts` covering `registerShutdownSignals` does not pull Postgres into the unit tier. Tests live under `src/__tests__/`.

`shutdown()` runs these steps in this order:

1. `server.close()` to stop accepting new connections while in-flight `/internal/complete` requests finish their response. (On Node ≥19 `close()` already reaps connections that are idle at that instant; the work that matters is step 2.)
2. Call `server.closeIdleConnections()` again every `DRAIN_POLL_INTERVAL_MS` until the `server.close()` callback fires or `drainTimeoutMs` elapses, whichever comes first. A poll is prescribed deliberately: `createGracefulShutdown` is handed a bare `server`, so there is no way to observe an already-dispatched response finishing, and attaching a `request` listener at construction time would be a permanent side effect on the server that this issue does not authorise. The repetition is load-bearing, not defensive: `httpAiGatewayClient` calls this service with global `fetch` (undici), which is keep-alive by default, so a socket whose response has just completed becomes an *idle* connection that `server.close()` does not revisit. Measured on Node 22 with one request in flight: `server.close()` alone, or a single `closeIdleConnections()` at close time, both leave several seconds of dead wait before the close callback fires — whichever binds first, the server's `keepAliveTimeout` or undici's own pooled-socket timeout — while polling collapses the drain to the request's own duration.
3. On the timeout path only, call `server.closeAllConnections()` so a request still hanging on a slow provider cannot hold the process open.
4. Clear the drain timer and the poll timer, on every path, so neither can stall an integration test's teardown.
5. `heartbeat.stop()`, immediately before step 6 and **not** earlier. During steps 1–4 the process is genuinely alive and still serving, so its `process_heartbeats` row must keep beating: `PROCESS_HEARTBEAT_STALE_AFTER_MS` is 60_000 — the same order as this drain's own bound — and `checkProcessHeartbeats` in `backend/packages/data/src/observability/observabilityCheckSystem.ts` sweeps `FIXED_PROCESS_NAMES`, which includes `ai-gateway`, flipping a stale row to `alerting` and writing a `process_stale` notification to a user. Its `* * * * *` entry sits in `CORE_CRONTAB`, which no process runs yet — #91 stands the worker up — so this alarm is dormant today and live once #91 lands. Stopping the heartbeat at step 1 would start that clock while the service is still serving; on an ordinary sub-second drain neither ordering matters, but on a drain that runs toward its bound, with a replacement that is slow to start beating, only the late stop stays under the threshold. Stopping it here still cancels every *future* tick before step 6 ends the pool. It does not cancel a tick already dispatched: `stop()` is `clearInterval` and nothing else, and `tick()` is fire-and-forget, so one outstanding UPSERT may still be in flight — which is what step 6's own bound below exists to survive.
6. `await pool.end()`, raced against `POOL_END_TIMEOUT_MS`. This bound is not optional: `createPool` sets no `query_timeout` or `connectionTimeoutMillis`, and nothing in this repository sets `statement_timeout`, so `pool.end()` waits on every checked-out client — including a heartbeat UPSERT still outstanding from step 5, or the timeout path's own `recordTokenGatewayCall`. Against a hung or unreachable database, which is exactly the state an operator restarts a service in, an unbounded `pool.end()` never settles, `registerShutdownSignals` never reaches `process.exit(0)`, and systemd escalates to SIGKILL — reintroducing the failure this issue exists to prevent. Clear this bound's own timer as soon as `pool.end()` settles, whether it resolves or rejects. When the bound wins instead, log it via `logger.error` and resolve anyway, and attach a `.catch` to the losing `pool.end()` promise so its later rejection cannot become an unhandled rejection — `pg` exposes no way to abandon a pool whose `end()` is still outstanding, and calling `end()` a second time rejects, so the promise is left to settle on its own and `process.exit(0)` ends it.

`shutdown()` is idempotent: the second and later calls return the same in-flight promise, perform no second teardown, and log nothing. It never rejects — a teardown step that throws (a rejecting `pool.end()`) is logged via `logger.error` and the promise still resolves, because a shutdown path that throws is a shutdown path that hangs the unit. This includes a late rejection from either `server.close()`'s callback or the `pool.end()` promise after its own bound already won the race: it must not surface as an unhandled rejection, which `installFatalHandlers` would turn into `process.exit(1)` in the middle of the shutdown.

Logging, through the existing `logger`: on the normal path exactly two structured lines — one when shutdown begins, carrying the signal, and one when it completes, carrying the signal and whether the drain finished on its own or hit the timeout — plus one `logger.error` per failed teardown step.

Check `docs/adr/` first: if a process-lifecycle or shutdown ADR already exists by the time this is implemented — #91 may have landed first and recorded one — extend or reference it instead of adding a second. Otherwise add an ADR under `docs/adr/` recording the shutdown ordering and why the heartbeat stops late rather than first. Load the `adr-conventions` skill before writing or editing it. This is the repository's first signal handling: no ADR covers process lifecycle and no rule in `backend/review-rules/` does either, which puts it inside rule 8 of `backend/review-rules/tasks/architecture.md` (a new architectural pattern with no ADR — medium severity — and `.github/workflows/code-review.yml` sets `REVIEW_BLOCK_SEVERITY: medium`, so it blocks the merge). Record the rejected alternative explicitly: a shared shutdown helper in `@semprec/shared`, rejected because #91 specifies its own ordering for two services that have a queue runner, and that ordering names no heartbeat step — though `semprec-api` does run one and discards its handle exactly as this service does, and unifying the two before either exists would be generality ahead of a second real caller.

In `backend/services/semprec-ai-gateway/src/serve.ts`: capture the `ProcessHeartbeatHandle` that `startProcessHeartbeat` already returns instead of discarding it, build the shutdown with it, and call `registerShutdownSignals(shutdown)`.

## Scope

### In scope

- `backend/services/semprec-ai-gateway/src/shutdown.ts` and its wiring in `backend/services/semprec-ai-gateway/src/serve.ts`.
- Capturing and stopping the process heartbeat handle in this service.
- One ADR under `docs/adr/` for the shutdown ordering decision.
- Integration-tier tests (`*.test.ts` — the path needs a real pool) driving `shutdown()` directly against a real `http.Server` on an ephemeral port with a keep-alive client, and a `*.unit.test.ts` covering `registerShutdownSignals` against a stub shutdown and a patched `process.exit`. The failure branches — a rejecting `pool.end()`, one that never settles, and the log-line assertions — are driven with a stub pool and a capturing logger, since a real pool cannot be made to hang or reject on `end()`.

### Out of scope

- Shutdown for `semprec-api` and `semprec-agents` — #91 covers those two services and specifies its own ordering.
- Cancelling an in-flight provider HTTP call. A request still in flight when the drain deadline passes has its socket destroyed by step 3; its handler may then still attempt `recordTokenGatewayCall` against the pool step 6 ended, which rejects; that rejection is caught by `handleRequestTraced`'s outer catch in `completeHandler.ts`, which logs `"Unexpected error handling request"` and writes a 500 onto the already-destroyed socket (harmless on Node 22 — it neither throws nor raises an unhandled rejection). That is a new terminal state, not today's SIGKILL, and closing it is not this issue's work.
- Any new column, status or "stopped" marker on `process_heartbeats`, and any change to how a deliberately stopped process is distinguished from a crashed one. Step 5's ordering keeps an ordinary deploy under the staleness threshold; a shutdown that somehow exceeds it would still alert, and making that distinction explicit is observability work this issue does not own.
- The systemd unit definitions — owned by #176, which does not currently mention `TimeoutStopSec`. None is needed: systemd's `DefaultTimeoutStopSec` of 90 s already exceeds this issue's 60 s drain plus 5 s pool bound. Recorded here so whoever writes those units knows the coupling exists.
- Making the drain timeout configurable through an environment variable. The optional `drainTimeoutMs` injection exists for tests; it adds no deployment configuration surface.
- Changing `installFatalHandlers`, which keeps exiting non-zero on an uncaught exception and is shared with `semprec-api`.

## Acceptance criteria

- With a request in flight against a real server, `shutdown("SIGTERM")` lets that request finish and receive its normal response body, and resolves only after it has.
- When that in-flight request is a `POST /internal/complete` whose provider call has already returned, its `ai_gateway_calls` row is present after `shutdown()` resolves — the loss this issue exists to close. (Read it back on a second pool: the injected one is ended by then.)
- With a keep-alive client connected and one request in flight, `shutdown()` resolves within one second of that response finishing, rather than waiting out the keep-alive timeout.
- After `shutdown()` resolves, the server accepts no new connection.
- A request still open when `drainTimeoutMs` elapses does not prevent `shutdown()` from resolving: it resolves within that bound plus a small margin, and its completion log line reports that the drain hit the timeout.
- After `shutdown()` resolves, the pool has been ended — a subsequent `pool.query(...)` rejects.
- With a real handle from `startProcessHeartbeat(pool, identity, { intervalMs })` and a drain held open by an in-flight request for longer than `intervalMs`, `process_heartbeats.beat_at` for `ai-gateway` advances at least once while the drain is in progress (read back on a second pool), and `stop()` — observed through a spy wrapping the real handle — is called before the pool is ended.
- `SHUTDOWN_DRAIN_TIMEOUT_MS` is `60_000`, `POOL_END_TIMEOUT_MS` is `5_000`, and `createGracefulShutdown` uses `SHUTDOWN_DRAIN_TIMEOUT_MS` when `drainTimeoutMs` is omitted.
- Calling `shutdown()` twice — concurrently and sequentially — tears down once, both calls resolve, and the second call emits no log line.
- A teardown step that throws (a rejecting `pool.end()`) produces a `logger.error` line and still leaves `shutdown()` resolved, not rejected.
- A `pool.end()` that rejects after its bound already won the race produces no unhandled rejection.
- On the normal path `shutdown()` emits exactly two log lines: the first carries the signal it was called with, the second carries the signal and whether the drain completed or hit the timeout.
- `registerShutdownSignals` registers a handler for both `SIGTERM` and `SIGINT`, and each awaits the injected `shutdown` before exiting with code 0. Delivering the same signal twice invokes `shutdown` twice and does not kill the process.
- On the timeout path, a connection still open when the drain bound elapses is destroyed: the client observes the connection close rather than a completed response.
- When `pool.end()` does not settle within `POOL_END_TIMEOUT_MS`, `shutdown()` still resolves and emits a `logger.error` line.
- `docs/adr/` carries an ADR covering this shutdown's step ordering, why the heartbeat stops at step 5 rather than step 1, and the rejected shared-helper alternative — either newly added here, or an existing process-lifecycle ADR extended to cover them.
- `serve.ts` passes the handle returned by `startProcessHeartbeat` into `createGracefulShutdown` and calls `registerShutdownSignals`. Verified by inspection of the diff, as #277 did for its workflow change — importing `serve.ts` in a test would boot a real service.
