**Blocked by:** #1479, #1807
**Model tier:** medium

## Context

Model tier rationale: One read-side resolver that turns the stored `before` and `after` of update steps into localized labels inside the existing card read model, with batched lookups and the ref targets of the same proposal; no writes, storage or tenant contract.

A multi-step proposal (#1378, #1479) can carry `update` steps that change an existing item: move a project to another area, or change a value such as a project's `status`. Each `update` step stores `before` and `after` of every key it changes. The product owner decided that the card must say what will change (for example that a project moves from area Work), because nothing may happen silently; the design adds the text. The client cannot compose it from the envelope: `before` and `after` hold item ids and canonical keys, not item names or option labels in the user's language, and a target may be another step of the same proposal (`{ ref }`) that does not exist yet. The card list `GET /api/inbox/cards` (#1807) returns the effective envelope only.

Decision: every card whose effective envelope has active `update` steps (skipped steps are left out, as in #1479) carries `changes: [{ ref, itemId, itemLabel, field, fieldLabel, from, to }]`, one entry per changed key. `from` and `to` are `{ value, labels }`: `value` is the stored value (an array of item ids for a relation, the canonical key for a select, the raw value otherwise) and `labels` the display labels (current item names for a relation, the localized option label for a select, an empty array otherwise). A `{ ref }` target is labelled with the title the referenced step would create. `itemLabel` and `fieldLabel` are localized in the locale the list already uses for its labels. Labels are resolved on read, never stored. Cards without `update` steps carry no `changes`.

## Task

Load `canonical-keys`, `io-hardening` and `testing`.

1. Add `describeUpdateSteps(client, envelope, locale)` in a new `backend/packages/data/src/inbox/proposalChanges.ts`: for each active `update` step, build the entries above from `before` and `after`; resolve all item names of a page of cards in one items lookup; resolve field and option labels through `resolveCatalogLabel` and the module catalogs; label `{ ref }` targets from the referenced step's title property.
2. Call it from `backend/packages/data/src/inbox/inboxCardsStore.ts` when building the cards and add `changes` to the card.
3. Tests: a proposal moving a project from area Work to a new area created by another step returns one entry with `field` `area`, `from.labels` `["Work"]` and `to.labels` with the new area's title; an `update` step changing a project's `status` to `done` returns the localized option labels of both values in Czech and English; a disabled `update` step contributes nothing; a page of 50 cards resolves names with a constant number of queries; a card without `update` steps has no `changes`.

## Scope

### In scope

- The `changes` description of active update steps on cards of the card list.

### Out of scope

- The multi-step envelope, its validation and confirm (#1378, #1479, #1486).
- The sentence shown on the card; the client composes it from `changes`.
- Changes of create and link steps; they are described by their own fields.

## Acceptance criteria

- Given a card whose update step moves project "Accounting" from area Work to area Finance, when `GET /api/inbox/cards` is read, then the card's `changes` has an entry with `field` `area`, a localized `fieldLabel`, `from.labels` `["Work"]` and `to.labels` `["Finance"]`.
- Given an update step that changes a project's `status`, then the entry carries the canonical keys in `value` and the localized option labels in `labels`.
- Given an update step whose target is another step of the same proposal, then `to.labels` holds the title that step would create.
- A disabled or skipped update step and a card without update steps contribute no entries.
