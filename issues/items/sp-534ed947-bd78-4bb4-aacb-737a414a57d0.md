### Requirement gh-1579: [areas-projects 07/13] Keep the deadline of long-term projects

#### Context

Model tier rationale: A new tenant table with row-level security plus a state-dependent rule in the pre-write transform and its cleanup on purge span a migration, the choke point and the purge path, though each follows an existing pattern.

Projects have a deadline in `date`. A long-term project has no deadline: moving a project to the `longTerm` status clears its deadline but remembers it, and moving it back restores the remembered deadline. Today `status` and `date` are independent user properties; nothing clears or restores anything.

The remembered deadline is not a property: a property would appear in the schema, in facets and in search. It lives in a tenant-scoped table `project_kept_dates` keyed by item. Rules, applied in the pre-write transform registered by #1520 (built on #1422):
- resulting status `longTerm` reached from another status: store the current `date` value (the patch's, else the stored one) in `project_kept_dates` and set `date` to null in the same write; if there is no date, store nothing;
- leaving `longTerm` for another status: if the patch carries no `date`, set `date` to the kept value and delete the row; if the patch carries a `date`, use it and delete the row;
- an incoming `date` (other than null) while the resulting status is `longTerm` is refused with a `ValidationError` on `field: 'date'` (HTTP 400, message that long-term projects have no deadline).

Decision: the kept value is stored as the exact JSON value of the `date` property (column type `jsonb`), so date-only and date-time values round-trip unchanged. Trashing a project keeps its row; purging a project deletes it with the other item dependents (`deleteItemDependents` in `backend/packages/data/src/chokePoint/itemTrash.ts`).

### Requirement gh-1530: [choke-point-hooks 03/04] Add a relation edge changed hook after edge writes and deletes

#### Context

Model tier rationale: One known mechanism (a new hook registry invoked at three existing write sites in the same transaction) with existing relation-write test fixtures, but it must cover every internal edge writer and avoid recursion.

Today the only relation-edge hook is the validating `registerRelationEdgeWriteHook` (`backend/packages/data/src/chokePoint/hooks.ts`). It runs in `chokePoint/relationOps.ts` before `relationsStore.createItemRelation` (in `createRelationWithClient` and `updateRelationWithClient`) and also in a dry run from `assertRelationCreatableWithClient` (used by `inbox/proposalActions.ts`). It can reject an edge and check its metadata but cannot react to a committed change. `deleteRelationWithClient` calls no hook at all. A domain that must react to a link appearing, changing or going away (search reindexing, last-contact derivation, inherited values, the Inbox tick, speaker suggestions, thread-task people) therefore has no place to do it inside the writing transaction.

This issue adds that place: a second registry of hooks that run after the edge row has been written, with the operation and both endpoints. It builds on #1415 for the `writerKind` it hands every hook, and on #1422 because both issues edit `hooks.ts` and `domainWriteHooks.ts` (shared files, so they land in order). Later work registers against it: #1652, #1660, #1593, #1710, #1718, #1780, #1923, #1942, #1697 and #1669. #1601 adds the equivalent for item delete and restore after this one.

Decisions:
- `op` is `create` for every `createRelationWithClient` write, including a repeat create that replaces the metadata of an existing edge (the call site cannot tell, and the registry contract stays simple); `update` for `updateRelationWithClient`; `delete` only when `deleteRelationWithClient` actually removed an edge. An idempotent delete of a missing edge calls no hook.
- A hook may write other rows, but must not write the same relation (same definition and endpoints) again. The contract is enforced by a small re-entrancy check in the runner (Task 4) so a violation fails fast instead of looping.

Shared-file ordering: this issue also waits for #1520 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1517: [areas-projects 02/13] Order related collections in module manifests

#### Context

Model tier rationale: Adding one optional descriptor field to the module manifest schema and filling it for three record types follows the existing manifest pattern, with no new lifecycle, authorization or persisted-data contract.

Every record page shows a "related" section at the bottom: one row per collection that has records connected to the open record, in a fixed, meaningful order that depends on the type of the open record (a project does not list Tasks because its page shows them in a section of their own; an area does not list Journal). Today nothing declares such an order. The operation that computes the rows (#1839) needs it, so this issue only declares and exposes the order data.

Decision: the order is declared on the database whose record is being viewed (the "record type"), as `relatedOrder: { order: string[]; omit?: string[] }`. `order` lists database keys; `omit` lists keys never shown for that record type. Databases not named in either list come after the listed ones, ordered by the database display order from #1407 and then, for user-created databases, by name; that fallback is applied by the consumer, not stored here. Keys of databases belonging to modules that are not active are ignored when the order is resolved, and an unknown key is ignored rather than rejected, so a manifest may name databases of optional modules.
