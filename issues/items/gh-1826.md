**Blocked by:** #1794, #1710
**Model tier:** medium

## Context

Model tier rationale: A new queue job that sends a silent push through an adapter delivered by a blocker and must stay out of the delivery ledger, with best-effort retry semantics and a Web Push variant.

After a notification is resolved (#1463), a phone that already received the visible push still shows it. A silent push tells the device to remove it. Silent (background) pushes are sent by `sendApnsBackgroundPush` from #1445 (`apns-push-type: background`, `apns-priority: 5`, no notification row). This job reuses it. The delivery ledger `push_deliveries` (migration `0032_push_deliveries.sql`) has a unique `(notification_id, push_subscription_id)`, so a second push for the same notification cannot be recorded there, and a dismiss is not a delivery of a notification anyway.

Sleep-window holding (#1794) applies to visible pushes; a silent dismiss is invisible, so it is not held. This issue is only ordered after it because both edit the same push files.

Decisions: dismiss is best effort (an error is retried by the queue a few times, never blocks anything); it is sent to all APNs registrations of the user, and to Web Push registrations as a payload `{ dismiss: [ids] }`; visible Web Push notifications get `tag = notification_id` so the service worker can close the matching one.

## Task

Load `io-hardening`, `state-writes` and `testing`.

1. Add a core task `pushDismiss` (`CORE_TASK_NAMES`, handler in `worker.ts`) taking `{ userId, notificationIds }`. It loads the user's active push registrations and sends, for APNs, `sendApnsBackgroundPush` with payload `{ dismiss: [notificationId...] }` and, for Web Push, a message `{ dismiss: [...] }`. A permanent failure (dead registration) revokes it as the fan-out job does; a transient failure fails the job so the queue retries it (`maxAttempts` 3). It writes no `push_deliveries` rows.
2. In `resolveNotificationsBySource` (#1463), after resolving, enqueue `pushDismiss` in the same transaction with the ids of notifications whose push could have been shown (kinds with `push: true` in the kind policy of #1440), grouped per user.
3. In `push/webPushAdapter.ts`, add `tag: notificationId` to the visible message payload.
4. Add tests with sender fakes: resolving enqueues one job per user; the job sends a background push with the ids and a Web Push dismiss; no `push_deliveries` row is written; a dead registration is revoked; a transient failure is retried; `info` kinds enqueue nothing.

## Scope

### In scope

- The best-effort dismiss job for APNs and Web Push, outside the delivery ledger, and its enqueue from the resolve helper.

### Out of scope

- Resolving notifications: #1463; reconcile on app open: #1559.
- The background push sender itself: #1445; collapse and thread ids: #1829.
- Service worker behavior in the web client.

## Acceptance criteria

- When a notification is resolved, then every APNs registration of its user receives a background push naming its id, and the push is not recorded in `push_deliveries`.
- When sending fails transiently, then the job is retried; when a registration is dead, then it is revoked.
- When a kind is never pushed, then no dismiss is sent.
