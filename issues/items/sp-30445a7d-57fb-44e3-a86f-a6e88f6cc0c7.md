## Context

Model tier rationale: Changes the cross-process execution contract of every mail sync pass (a per-mailbox lease with a rerun flag that every trigger reaches through the job), the IMAP pass's folder-change detection and the provider client's command sequence, with lock-order, crash-recovery and exactly-once-follow-up constraints.

Production evidence (dev VPS v0.3.3, one Purelymail IMAP account with about 20 messages in six folders INBOX, Sent, Drafts, Archive, Trash, Junk, IMAP IDLE live sync on), journal of `alldots-api` during an end-to-end run (send, flag, read, archive, trash, restore, inbound APPEND):

- up to five `mailAccountSync` passes of the same account ran at the same time; their durations grew 9.8 s, 15.9 s, 20.9 s, 25.6 s, 28.5 s;
- a quiet pass of this tiny mailbox took about 6.5 s;
- inbound mail became visible about 9.6 s after the IMAP APPEND.

Root causes, from the code:

- Every trigger already goes through `enqueueMailAccountSync` with the job key `mail-account-sync:<mailbox>` (IDLE signal, Gmail and Graph push, sweep, user flag and move write-back through `mailMessageFlagSyncStore` and `mailThreadActions`, Mail switch, sign-in, the unfinished backfill). graphile-worker coalesces a repeat enqueue only onto a job that is not running: for a running job it clears that job's key and inserts a new one, which another worker (concurrency 4) starts at once. Each trigger during a pass therefore starts another pass. The comment in `imapConnectionLimiter.ts` ("across processes the sync jobKey already serializes passes") is not true.
- The concurrent passes then queue behind each other in the per-account IMAP connection limiter (two connections for a generic provider, one held by the IDLE session), which is why each one took about 5 s longer than the one before it.
- A quiet IMAP pass asks the server, per folder, SELECT four times (`selectFolder`, and `mailboxOpen` again in `fetchMessagesSince`, `fetchFlagsChangedSince` and `fetchVanishedSince`, which imapflow sends every time), UID SEARCH for new UIDs, FETCH of the flags and UID SEARCH ALL (or a VANISHED fetch), about seven round trips per folder even when nothing changed, plus LIST and LSUB. At the measured RTT that is the 6.5 s.
- An IDLE EXISTS enqueues a pass at once, but the pass waited behind the passes already queued in the limiter and then walked every folder.

Decisions:

- **Single flight per mailbox.** `mail_account_sync_state` gains `pass_lease_token`, `pass_lease_expires_at` and `pass_rerun_requested`. A `mailAccountSync` job claims the lease in a short transaction that locks the sync state row. When another pass holds an unexpired lease, the job sets `pass_rerun_requested` and completes without any provider call. The pass renews the lease in each of its write transactions (`enterSyncPass`) and ends at its next transaction when the lease is no longer its own. When the pass ends, on every path, one transaction releases the lease and, when a rerun was requested, enqueues exactly one follow-up pass. The unfinished backfill requests the rerun the same way instead of enqueueing a job of its own. A crashed holder blocks for at most the lease duration (5 minutes), not graphile-worker's 4-hour stale-lock reset that a named job queue would leave behind.
- **Folder change detection.** On a server with CONDSTORE the pass lists the folders with their STATUS (UIDVALIDITY, UIDNEXT, HIGHESTMODSEQ, MESSAGES), inline with LIST where the server offers LIST-STATUS. A folder whose four values equal its stored sync state is skipped: no SELECT, no fetch and no write transaction. `mail_folder_sync_state` gains `message_count`, recorded with the other cursors. For a folder that did change, the client selects it once and the new-message search runs only when UIDNEXT moved; the flag and vanish fetches run only when HIGHESTMODSEQ or the message count moved. A server without CONDSTORE keeps the full flag and vanish fetches (it offers no other way to see a flag change), with one SELECT per folder.
- **The folder list is not cached across passes.** LIST is the change detector for added and removed folders and carries the STATUS data in the same round trip, so a cache would save no command and could miss a new folder.
- **IDLE and write-back.** An IDLE signal, a flag write-back and a move write-back keep enqueueing the same coalesced pass; with unchanged folders skipped, such a pass touches only the folders that changed (the INBOX for a delivery, the source and target of a move) plus the queued STOREs, and it starts as soon as the running pass releases the lease.

## Scope

### In scope

- The pass lease and rerun flag for every sync mode, the IMAP folder change detection, the client's SELECT reuse, the fakes, tests and the architecture document.

### Out of scope

- The move drain's connection per move (`drainImapMoves` opens its own owned connection for each claimed move, by design of the move uncertainty model).
- The Gmail and Graph passes' provider calls inside their transaction.
- A no-CONDSTORE flag-change shortcut, IDLE on folders other than the ones it hosts today, a per-folder pass triggered by IDLE.
- Pool size, worker concurrency, job priorities.
- Any request against a real server.

## Acceptance criteria

- With a real graphile-worker runner at concurrency 4, N enqueues of one mailbox's `mailAccountSync` while its pass runs result in at most one pass at any moment and exactly one follow-up pass after it; no trigger is lost (a trigger after the follow-up started gives one more).
- A job that finds the lease held makes no provider call and leaves `pass_rerun_requested` set; the release enqueues exactly one keyed job; a lease whose holder died is claimed after it expires; a pass that lost its lease writes nothing more.
- Against the loopback IMAP server with 80 ms injected per-command latency and six folders holding about 20 messages, a quiet pass on a CONDSTORE server sends no SELECT, SEARCH or FETCH, and its command count and wall time are asserted (with and without LIST-STATUS); a server without CONDSTORE sends one SELECT per folder.
- After a delivery to INBOX signalled through IDLE while a pass runs, the follow-up starts when that pass ends, selects only INBOX and the message is visible within a bound asserted in the test.
- A flag write-back pass sends the STORE without fetching unchanged folders.
- The existing mail, IMAP, IDLE, thread action, observability and isolation test files stay green.
