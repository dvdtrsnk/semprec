## Context

Model tier rationale: One known mechanism (a pre-image read inside the existing update transaction) crossing the choke point, the shared operation contract and the REST adapter, with existing item-write fixtures, and no new authorization or isolation contract.

When a Semp reply changes an item, the chat needs to show what the value was before ("due today 14:00 -> tomorrow 9:00"). Today the `item.patch` generic operation returns only the new item state: `patchItem` in `backend/packages/application/src/genericApplicationService.ts` calls `chokePoint.updateItem`, which runs `updateItemWithClient` (`backend/packages/data/src/chokePoint/itemWrites.ts`) and `itemsStore.updateItemProperties`, and the result is a plain item. There is no item history and no author on an update, so the previous values cannot be reconstructed afterwards.

Decision: `item.patch` additively returns the previous values of exactly the patched keys, read inside the same transaction that writes the new values (under the row lock the update already takes). A best-effort read before the write, outside the transaction, would be wrong under concurrent edits, so it is not used. The addition is a new output field of a catalog operation, so the agent tool surface keeps calling only operations of the catalog; no port method outside the catalog and no amendment of the ADR `rest-only-port-extension-methods` is needed.

Decision: the REST `PATCH /api/items/:id` response body does not change; the REST handler drops the new field, so the public REST contract stays as it is. Only the generic operation output (agent tools, MCP, the gateway) carries it.

#1527 builds on this: it writes the field changes (`key`, `before`, `after`) into the structured tool result. Nothing in this issue stores or displays them.

## Task

Load `state-writes` and `testing`.

1. In `backend/packages/data/src/chokePoint/itemsStore.ts`, make the update of an item's properties return the previous values of the patched keys together with the updated row, taken in the same statement or in a `SELECT ... FOR UPDATE` of the same transaction. A key that was absent before is reported as `null`. Only the keys in the patch appear.
2. Carry the result through `updateItemWithClient` (`itemWrites.ts`) and the choke point `updateItem` so callers that ignore it keep working unchanged.
3. In `backend/packages/shared/src/genericOperations/schemas.ts` and `port.ts` change the output type of `item.patch` to the item plus `previous: Record<string, unknown>`. Update `patchItem` in `genericApplicationService.ts` to return it.
4. In `backend/services/semprec-api/src/itemsHandler.ts` strip `previous` from the REST response so the body is exactly what it is today.
5. Tests (with the existing item-write fixtures): a patch of two keys returns both previous values; a key that was unset returns `null`; two concurrent patches of the same key each see the value the other committed (no stale pre-image); a rejected patch (version conflict) returns nothing; the REST response has no `previous`.

## Scope

### In scope

- The additive `previous` output of `item.patch`, read in the write transaction, and keeping the REST body unchanged.

### Out of scope

- Writing field changes (`key`, `before`, `after`) into tool results (#1527).
- Previous values for `item.create`, `item.delete`, `item.restore` and relation operations.
- Any item history table or author of a change.
- Redacting previous values of sensitive databases; that happens where they are stored (#1860, #1885).

## Acceptance criteria

- When `item.patch` changes a due date, then the operation output contains the item and `previous` with the old due date.
- When a patched key had no value, then `previous` has that key with `null`.
- When two patches of one key run concurrently, then each output's `previous` is the value committed immediately before that patch.
- When the patch is rejected, then no previous values are returned and nothing is written.
- When the item is patched over REST, then the response body has the same shape as before and no `previous`.
