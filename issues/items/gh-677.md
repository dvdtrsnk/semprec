## Context

A rollup property's value is never in `items.properties`: the recompute worker writes it with `itemsStore.writeComputed` (`backend/packages/data/src/chokePoint/itemsStore.ts`, lines 384-399) into `items.computed` under the rollup property's key, and the generic write path refuses the key (`assertWritableProperties` in `chokePoint/itemWrites.ts`, `computed_readonly`). The view compilers do not know this: `compileCondition` in `backend/packages/data/src/views/filterCompiler.ts` (lines 72-75) builds `textField = properties ->> $key` / `jsonField = properties -> $key` for every non-relation property, and `compileSort` in `backend/packages/data/src/views/sortCompiler.ts` (line 17) builds `properties ->> $key`. So a filter on a rollup (`equals`, `is_empty`, `before`, ...) never matches — `properties ->> 'total'` is NULL on every row — and a sort on a rollup is a no-op (every key NULL, `NULLS LAST` ties broken by id). The property type is already available to both: `FilterProperty.type` (`filterCompiler.ts`, lines 10-14) and the `propertyTypes` map passed to `compileSort`.

`items.computed` is shared with declared module cache keys (`backend/packages/data/src/chokePoint/computedKeyRegistry.ts`), but those keys are refused as property keys (`assertNoComputedKeyCollision`), so no *property* other than a rollup lives in `computed` — the type check is the complete rule. This issue depends on C7 because both change `sortCompiler.ts`'s per-key expression builder.

## Task

1. `sortCompiler.ts`: the per-key expression helper C7 extracted picks the column by type — `computed` for `type === 'rollup'`, `properties` otherwise — and the cast for a rollup is derived from its aggregation via the rollup's `config` (`parseRollupConfig` in `backend/packages/data/src/rollup/config.ts`: `count*`/`sum`/`avg`/`min`/`max`/`percent_*` → `::numeric`, `earliest`/`latest` → `::timestamptz`). To have the config, `compileSort`'s and `compileSortKeyset`'s `propertyTypes: Map<string, PropertyType>` parameter becomes `properties: Map<string, Pick<PropertyRow, 'type' | 'config'>>` (built in `viewQuery.ts`'s `queryItemsCore` from the `listPropertiesByDatabase` result it already has, line 58). Both `compileSort` and the keyset predicate use the same helper, so a sorted rollup pages correctly.
2. `filterCompiler.ts`: `compileCondition` chooses `computed` for `property.type === 'rollup'` for both `textField` and `jsonField`; the `before/after/on_or_*`/`date_range` casts and the `is_empty`/`is_not_empty` forms are unchanged otherwise. `FilterProperty` gains nothing (type is enough here — the date conditions already cast with `::timestamptz`, and a numeric `equals` compares as text exactly as it does for a `number` property today).
3. Tests, new `backend/packages/data/src/__tests__/rollupViewFilters.test.ts` (integration): two databases linked by a relation with a `sum` rollup and a `latest` rollup on the parent; after `handleRollupRecomputeTask` has run for the parents, `queryDatabaseItems` with `equals`/`is_empty`/`is_not_empty` on the sum rollup and `after` on the latest rollup return the right parents, a `sort` on the sum rollup orders parents by the computed value (asc and desc; a parent with no edges has a `null` sum — `recomputeRollupCell` stores `null` for every aggregation but `count` when there are no rows — and sorts last both ways), and paging through the sorted rollup with `limit: 1` (C7's keyset) visits every parent once. Add one unit case to `backend/packages/data/src/__tests__/filterCompiler.unit.test.ts`: a rollup-typed property compiles to a `computed ->>` predicate and a text property still compiles to `properties ->>`.

## Scope

### In scope
- Column selection by property type in both compilers, the rollup cast from its aggregation, and the tests.

### Out of scope
- Rollup recompute correctness (sibling issue C10) and rollup config validation.
- Filtering/sorting on module cache keys in `computed` (not properties; no view surface exposes them).
- Curated views (C19).

## Acceptance criteria

- When a view filter targets a rollup property, rows match on the value in `items.computed` under that key (`equals`, emptiness and date conditions all work).
- When a view sort targets a rollup property, rows are ordered by the computed value with nulls last, and paging through that sort visits every row once.
- When a filter or sort targets a non-rollup property, the compiled SQL is byte-for-byte what it was before (the existing `filterCompiler.unit.test.ts` cases pass unchanged).
