## Context

Model tier rationale: Lets one redirect move where a CalDAV session may send the account's Basic credential, so the account's own server is resolved and stored without letting any later server answer choose a host for the login.

End-to-end finding against a real CalDAV deployment, verified in the code: the CalDAV credential is scoped to the origin discovery starts at (`calendar/sync/adapters/caldav/caldavHttp.ts`, `caldavCredentialScope`). A generic account whose `https://<domain>/.well-known/caldav` redirects to another host, which RFC 6764 allows (a custom domain delegating to its provider), is refused as `invalidResponse` by the sync and as `caldav_server_invalid` by the connect, so it never syncs unless the person knows the provider's CalDAV address.

Decisions:

- **Delegation only while the account has no server.** A session opened with `resolveServer` and a well-known start (`/.well-known/caldav`) lets the first hop of its first request redirect to another server whose address the account could have been set up with (`allowsWellKnownDelegation`: `isStorableCalDavUrl`, i.e. https, a DNS name that is no local name, the default port, no userinfo; under the test policy any address without userinfo). The outbound policy still vets the request, so a private address is refused. The scope moves to that server for the rest of the session; every later redirect and server-named address outside it is refused as today.
- **Where the resolved server is stored.** In the existing `mail_account_server_settings.caldav_url`: no schema change. At connect (a body's well-known `caldavUrl`, verified with `resolveServer: true`) the delegated server is stored instead of the body's address. In a sync pass of an account without `caldav_url`, the adapter reports it (`CalendarSyncAdapter.delegatedServerUrl`) and the job stores it right after the calendar listing through mail's `recordResolvedCalDavUrl` (Mailboxes item `FOR SHARE`, then an update only while `caldav_url IS NULL`), so a password replacement, which rewrites the row under the item's `FOR UPDATE`, never overwrites it with a stale `null`. The rest of the pass uses the delegated server.
- **After discovery.** An account with `caldav_url` set never resolves again: every discovery starts there, a password replacement verifies it with `resolveServer: false`, and a redirect off it is refused.

## Scope

### In scope

- Resolving and storing a generic account's CalDAV server from a well-known delegation.

### Out of scope

- iCloud's discovery, the outbound address policy itself, the web and mobile connect forms, any schema change.

## Acceptance criteria

- At connect a well-known `caldavUrl` redirecting to another server is followed; the verification reports that server, the login goes only to it after the well-known request, and the route stores it as the account's `caldav_url`.
- A pass of an account without `caldav_url` stores the delegated server, and the next pass starts there; an account with a `caldav_url` keeps it.
- With a stored server (`resolveServer: false`, or a stored well-known address) the same redirect is refused by connect and sync, and the other server receives no request.
- After the delegation, a calendar home back on the well-known origin and a second redirect off the delegated server are refused.
- `allowsWellKnownDelegation` refuses plain http, a private or loopback IP literal, a local name, another port and userinfo under the production policy; a delegation to an address the outbound policy refuses fails as unreachable.
- The existing CalDAV adapter and password route tests stay green.
