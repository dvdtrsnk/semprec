## Context

Model tier rationale: A privilege-escalation fix in the SECURITY DEFINER functions that every tenant write path calls, and a change of the deploy-time tenancy verifier that the security gate relies on. A wrong search_path, a missed function or a verifier that still accepts the exploitable shape leaves a runtime role able to become database superuser.

Finding R2-DB-1 (high) of the gh-1086 external review, reproduced for this source at `e6387779b` (identical tree to the integration tip): `create_items_partition(uuid)` (`0072_attach_items_partitions.sql`) and `drop_items_partition(uuid)` (`0061_tenant_checked_partition_functions.sql`) are `SECURITY DEFINER`, owned by the migrating superuser, with `SET search_path = pg_catalog, public`. When `pg_temp` is not listed, PostgreSQL searches the session's temporary schema first for relation and type names. The bodies use unqualified type names (`partition_name text`, `database_id::text`, and through the nested `app_current_tenant()` an unqualified `::uuid`). A session of `semprec_data` that creates `pg_temp.pwn(pg_catalog.text)` and `CREATE DOMAIN pg_temp.text AS pg_catalog.text CHECK (pg_temp.pwn(value))` and then calls `create_items_partition` on one of its own databases runs `pwn` as the owner: the review observed `current_user=postgres session_user=semprec_data`, `ALTER ROLE semprec_data SUPERUSER` succeeded, and through `drop_items_partition` `GRANT semprec_router TO semprec_data` succeeded. The decision agent reproduced the same mechanism on `postgres:16-alpine` 16.15 (the production image) with a minimal superuser-owned definer function of the same shape: `rolsuper` became true; after `ALTER FUNCTION ... SET search_path = pg_catalog, public, pg_temp` the identical script ran no `pwn` and `rolsuper` stayed false.

The five router functions owned by `semprec_router` (`route_graph_subscription(text)` 0069, `route_gmail_address(text)` 0071, `ai_global_spend()` 0073, `ops_health_counts()` 0075, `ai_tenant_spend()` 0076) carry the same `search_path = pg_catalog, public`. The review did not break them (their bodies name no type at run time and qualify every table), but `semprec_router` is `BYPASSRLS`, so they get the same setting as defence in depth.

Finding R2-DB-5: `findDefinerFunctionViolations` in `backend/packages/data/src/db/tenancyInvariants.ts` counts any `search_path=` entry in `proconfig` as pinned, so `verifyTenancyCli` prints `tenancy: verified` for the exploitable catalog. The verifier runs at every deploy (#1085) and is the gate's evidence for the database invariants.

`ALTER FUNCTION ... SET search_path` changes only `proconfig`: owner, ACL, signature and body stay, and the previous release calls the functions the same way, so the migration is backward compatible under `docs/adr/2026-09-10-expand-contract-forward-only-migrations.md`. Integration tests create temporary tables themselves (for example `databaseOps.test.ts`), so revoking `TEMPORARY` on the database is not part of this source.

Keep the existing `has no pinned search_path` detail when there is no setting. Otherwise add, in this order and each at most once per function:

The function's query covers every schema except `pg_catalog` and `information_schema` (replace the `p.pronamespace = 'public'::regnamespace` filter); the migrated database has no definer function outside `public`, so 'finds no violation on the migrated database' still passes.

## Scope

### In scope

- `pg_temp` as the last `search_path` element of all seven `SECURITY DEFINER` functions in any schema of the database.
- A verifier rule and catalog tests that refuse any other `search_path` shape, including the exact catalog of R2-DB-1.
- A regression test that replays the review's exploit as `semprec_data` and fails on the unfixed function.

### Out of scope

- Rewriting function bodies to qualify type names, and any change of `app_current_tenant()`, `app_tenant_default()` or `app_sole_tenant()`.
- `REVOKE TEMPORARY ON DATABASE`, and any change of grants, owners or role attributes.
- The side-role containment of R2-DB-2 and R2-DB-3 (source `[security-gate 02/06]`).
- Running the verifier or the migration against production, any production deployment, and any change to gh-1086 itself.
- Any change under `web/` or `mobile/`, and web or mobile verification.

## Acceptance criteria

- When the migrations have run, then every `SECURITY DEFINER` function in any schema of the database (all seven are in `public`) has `proconfig` `{"search_path=pg_catalog, public, pg_temp"}` and `findTenancyViolations` returns no violation.
- When `create_items_partition(uuid)` has `search_path = pg_catalog, public` (the catalog of R2-DB-1), then `findTenancyViolations` reports exactly one `definerFunction` violation for it with the detail `search_path does not end with pg_temp`, and `verifyTenancy` exits 1 instead of printing `tenancy: verified`.
- When a definer function's `search_path` lists `pg_temp` before its end, names a non-existing schema, or names a schema in which `semprec_data`, `semprec_side` or `PUBLIC` may create objects, then the verifier names that function with the matching detail, also when the function is in a schema other than `public`.
- When `semprec_data`, logged in with its own password, creates a `pg_temp.text` or `pg_temp.uuid` domain whose check runs a function and then calls `create_items_partition` or `drop_items_partition` on its own database, then that function never runs as another role and `semprec_data` stays non-superuser; with the pre-fix `search_path` restored, the same test case rejects with `escalated as` the owner.
- When the previous release runs against the migrated schema, then its calls of the seven functions behave as before (same signatures, owners, grants and bodies).
