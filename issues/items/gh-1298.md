## Behavior specification

Collection metadata and schema for forms, filters and labels.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions for job collection-schema-1

#### (a) Decisions adopted from open questions

- Project status color set and label ("Archive" in collection vs "Archived" in detail) -> Decided by the product owner: the detail-view set (inProgress #007AFF, longTerm #AF52DE, done #34C759, archived #8E8E93) stored in the backend, the label from the catalog -> one color set everywhere, changed in one place. (#1584)
- Default values: first option of every group select vs listed only -> Decided by the product owner: listed only (Projects inProgress, Books toRead, Movies planned, Tasks notDone, Areas active true, Files date today), no default for anything else, so no data is created that the user did not enter; mechanism is generic `config.default`. (#1389)
- Project picker -> Decided by the product owner: the same picker everywhere; by default it hides done and archived projects (status-less projects stay) but can show them; a done project stays a valid relation target. (#1647)
- Colors for People options colleague, craftsman, doctor -> Decided by the product owner: neutral #8E8E93 until the design supplies values. (#1584)
- Journal period options -> no colors; the orange belongs to an "all" chip, not a stored option -> nothing to store.
- Quick filter "Recent" Files -> Decided by the product owner: date within the last 30 days, computed as everywhere (D-30 through today inclusive, the `last30` preset). (#1647)
- Default sort per collection -> Decided by the product owner: one general rule in the schema; Events and Tasks by date ascending, every other collection (user-created ones too) by creation time descending, newest first. (#1647 declares the date sorts; the creation-time fallback is #1995)
- Sort spec shape in the manifest uses the existing view `{ property, direction }` rather than `{ key, direction }` -> reuse the existing SortSpec type.
- Number filter presets: `labelKey` plus optional literal `label` override; only lte and gte -> custom databases without catalog need a readable label; eq is rejected per acceptance.
- Title required: enforced for user and agent writer kinds only, missing title on create also rejected; patch rejects a present blank title -> follows the notes (internal paths are listed and left unchanged).
- May Transcripts have an empty title? -> Decided by the product owner: yes; a transcript takes its name from its event or the recording date, so an empty stored title is valid; the rule applies to every other collection. (#1519)
- Relation cardinality in the schema is projected as stored on the relation definition for both sides (no inversion for the inverse side).

#### (b) Open questions for the product owner

- Colors for Journal period options, if any.
- The Tasks/Projects "Termín" labels' semantics.
- Whether Ostatní (Others) in People should include the new relationship options added by the unified list.
- Whether the inverse side of a one-to-many relation should report the flipped cardinality.

#### (c) User-visible behavior

Every collection screen can build its filter chips, default order, forms and option colors from one schema response: each property reports its type, configuration (relation target and cardinality, date with time, numeric thresholds, defaults) and whether it can be filtered; select options carry a color; numeric properties such as ratings expose named thresholds ("5 stars", "4 and up", "No rating"); each collection reports its quick-filter chips with a default, its default sort, and which items belong in the collection or in a project picker (user projects only, no finished or archived ones). A new item starts with sensible values (project In progress, task Not done, file dated today) and a blank name is rejected for people and for Sempa.


### Decisions: collection-schema-2

#### (a) Decisions adopted from open questions

- Where do user-created collections appear and how are they managed? -> Decided by the product owner: in a separate overview section after the system collections, ordered by name, managed like the system collections (rename, delete to the trash). The server only marks them client-visible (no overview or switcher order); the order is the client's. No backend change. (#1407)
- Group "When" of Tasks on the server or in the client? -> Decided by the product owner: in the client; the grouping (Today, Tomorrow, Later) is presentation over the data and depends on local time, so the server stays generic and v1 builds it in the client. (#1409)
- Remember view and sort per collection on the server or on the device? -> Decided by the product owner: on the device; it is a convenience on one device, and server sync is added when it is needed (not in v1). (#1407, #1409)
- Project status `archived` label ("Archiv" vs "Archivováno")? -> Decided by the product owner: the label comes from the catalog (the current "Archivováno"), with one color set everywhere. (#1584)
- clientVisible rule -> derived from orders or user-created, plus an explicit optional `clientVisible: true` descriptor override for Areas, Emails, Transcripts. Reason: the source's formula names three databases that have neither order; an override is cleaner than key-name special cases.
- Order of GET /api/databases vs id-keyed `database.list` cursor -> the handler reads all pages, sorts, and pages the sorted list with an opaque keyset cursor encoding the sort tuple. Reason: keeps the response shape and stays stable when a row is archived between pages.
- Defaults of icon and color for user-created collections -> applied on read only, never written. Reason: source says so; no later data migration if defaults change.
- Icon/color on system databases via patch -> rejected (403); manifest stays authoritative.
- Search placeholder with no catalog entry -> `null`, never the raw key; generic custom-collection sentence lives in the system databases catalog (`collection.custom.searchPlaceholder`).
- Title property in one-call create -> created (key `name`) only when `properties` is present; display name from `titlePropertyName`, default "Name", REST route sets "Název" for Czech users. Reason: no catalog exists for user-created databases, and the actor carries no locale.
- Property types in one-call create -> text, number, select, date, checkbox, url, file, relation (relation unlocked, no inverse). Reason: the types the new-collection form offers.
- Authorization of `properties` in database.create -> only human REST sessions; agent and MCP actors are forbidden from sending it. Reason: database.create is gated by the database-write capability, property creation by the separate schema-write capability.
- Gallery config -> `columns` (2|3) and `aspect` ("3:4"|"4:3") required, `coverKey` optional and not checked for existence; built-in types get a definition source so validation runs on create and patch.
- Ack for a replayed or no-op update -> acknowledged. Reason: content is durable and the client indicator would otherwise stay on "Saving".
- Client update id encoding -> optional trailing varString after the update bytes in the existing y-protocols payload; 1-64 chars of [A-Za-z0-9_-]; invalid means no id (persisted, not acknowledged).
- protocolV1.ts overlap with relation-api 05 and the doc invalidation issue -> stated as non-overlapping (different declarations), no ordering edge added.

#### (b) Open questions remaining for the product owner

- Concrete icon names and colors for the system collections (the issue proposes an initial table; the source gave none except the custom default orange database icon).
- Wording of the search placeholders for collections the source did not name (Tasks, Events, Journal, Companies, Areas, Transcripts, Emails) and the capitalization inconsistency in the named ones ("v Projektech" capitalized, "v knihách" not).

#### (c) User-visible behavior of this chunk

Collections now describe themselves to the app. The overview lists Projects, Events, People, Companies, Files, Health records, Books and Movies and series in a fixed order, each with its own icon and color, while the collection switcher uses its own fixed order (Projects, Tasks, Events, Journal, People, Companies, Files, Health records) and hides Books and Movies; internal databases stay out of both. Every collection also carries its own search hint ("Hledat v Lidech", "Hledat ve filmech a seriálech", "Hledat ve sbírce" for your own collections). Users can give their own collections an icon and a color (orange database icon by default), and create a new collection together with all its properties in one step, so a failure never leaves a half-built collection behind. A new Gallery layout is available for photo-led collections such as Files and Recipes (2 or 3 columns, 3:4 or 4:3 tiles). Czech and English labels of the system collections match the wording used in the app (for example "Oblast", "Termín", "Přílohy", "Sleduje se", "Kvartál"), without changing any saved filter or view. Finally, the page editor can tell when an edit has really been stored: the server confirms each persisted page update to the device that sent it.
