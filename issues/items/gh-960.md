## Behavior specification (approved)

Part of the multi-tenancy program specified in #950. Prove isolation, then make it strict and remove the transitional pieces:

1. Every service refuses to start under a superuser, `BYPASSRLS` or table-owner role.
2. Exhaustive two-tenant suites under the runtime roles prove that every route (REST and MCP), every realtime frame type and every queue task isolates tenants: a foreign id behaves exactly like a random id and no list, frame or job crosses tenants; a new route, frame or task without an isolation case fails the suite.
3. Release checkpoint 1 (maintainer): a context-complete release runs in production with zero `tenant_scope_missing` warnings for 7 days, the global AI caps are configured, and every user is bound to a tenant.
4. After the checkpoint: legacy queued jobs are stamped and tenant tasks without a tenant are refused; the legacy global unique keys and the dormant `resource_grants` table are dropped; composite tenant foreign keys are added and validated; `app_tenant_default()` becomes strict and `users.tenant_id` NOT NULL.
5. Every deploy verifies the tenancy invariants in the catalog and fails before activation if one is broken.
6. The AI gateway endpoints get their own exhaustive two-tenant suite.
7. Release checkpoint 2 (maintainer): the strict release, with tenant-key credential writes and finished re-encryption, runs clean in production before the contract steps that need it.

## Decisions

- **Why a maintainer checkpoint?** → Relay merges continuously but releases are promoted by the maintainer; the strict switch must ship in a release after one that is proven context-complete, so a one-release rollback lands on proven code.

## Out of scope

The security sign-off and invitation acceptance (#961).
