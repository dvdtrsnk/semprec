## Context

Model tier rationale: Changes when the draft send route answers relative to the IMAP Sent copy of an SMTP send, which touches the exactly-once send contract, the shared IMAP connection budget and the API shutdown order.

End-to-end test of the dev server against a real Purelymail account (F14): `POST /api/mail/drafts/:id/send` takes 1.85–4 s, a reply up to 10–20 s.

Trace of the request (`mail/mailDraftSend.ts`, `mail/send.ts`, `mail/mailTransport.ts`, `mail/imapConnectionLimiter.ts`): a few short transactions, then the claim transaction, then `transport.send`, then the finalization transaction; no sync pass is awaited and no lock is held across the provider call. Inside `createSmtpMailTransport.send` the SMTP submission (connect, TLS, AUTH, MAIL, RCPT, DATA) runs while the Sent-copy saver opens its IMAP connection, and the send then waits for the APPEND and LOGOUT. The saver opens that connection only inside the account's IMAP connection slot (`sharedImapConnectionLimiter`, limit 2 for a provider without its own, such as Purelymail). The account's IDLE connection holds one slot for good, and a running sync pass holds the other for its whole run (passes up to 11.5 s were measured). A reply is sent right after the user read the thread, when an IDLE- or write-back-triggered pass is usually running, so the response waits for the rest of that pass, then for an IMAP connect, the APPEND and the LOGOUT. Reproduced with fakes (SMTP 1.5 s, IMAP connect 0.5 s, APPEND 0.2 s, LOGOUT 0.1 s): 1.80 s without contention, 3.80 s while a pass held the second slot for 3 s.

The documented contract (`docs/architecture/domain-mail-and-inbox.md`, Sending) keeps the submission synchronous for a reason: a refusal (auth, unreachable, recipient rejected) is the answer, and the claim decides exactly-once (a failed send deletes its claim, no automatic retry). That stays. The wait for the Sent copy after acceptance is avoidable: its failure already never fails the send, and the Semprec item is in Sent from the finalization.

Decisions:

- `createSmtpMailTransport` takes an optional `DetachedSentCopies`. With it, an accepted submission hands its running Sent copy to it and answers at once; the copy keeps its connection slot, APPEND-after-acceptance and `sent_copy` failure log. A refused submission still waits for the copy, so the unused connection is closed before the refusal is answered.
- `createDetachedSentCopies()` holds the copies until they settle; `drain(timeoutMs)` says whether all settled in time.
- `createMailTransportFactory` passes `detachedSentCopies` through. `semprec-api` creates one in `serve.ts` and gives it to the dispatcher's send transports (`AppOptions.detachedSentCopies`), so the draft send route, the approved agent send and the MCP draft send answer early. Queue jobs that send (invitations) keep waiting for the copy.
- Shutdown drains the copies after `mailLiveSync.stop()` (whose IDLE connections free the slots a waiting copy needs) and before `queueRuntime.stop()`, at most `SENT_COPY_DRAIN_TIMEOUT_MS` (30 s); copies still running then are logged.
- A queue job per copy was rejected: the raw message (attachments included) would have to be stored or rebuilt byte for byte.

## Scope

### In scope

- Answering an accepted SMTP send before its Sent copy in `semprec-api`, and draining those copies at shutdown.

### Out of scope

- Sending through a queue job, SMTP connection pooling, a provider-specific connection limit for Purelymail.
- Gmail and Graph transports, which keep no Sent copy of their own.
- Any request against a real server.

## Acceptance criteria

- With both IMAP connection slots of the account taken, an accepted send through a transport with detached copies answers in about the submission time (under two submission latencies, before the slot frees; with the fakes above 1.50 s instead of 3.80 s), opens no IMAP connection before a slot frees, and the copy is appended and its connection closed once one does.
- A detached copy's APPEND failure leaves the send successful and logs `{ mailboxItemId, stage: "sent_copy" }` without message content.
- A refused submission with detached copies answers its refusal only after the overlapped IMAP connection was closed, without an APPEND.
- Shutdown drains the copies after the live-sync stop and before the queue runtime, bounded by `SENT_COPY_DRAIN_TIMEOUT_MS`, logs copies left running and still runs every later step.
- The existing SMTP transport, send, compose-after-connect and shutdown tests stay green.
