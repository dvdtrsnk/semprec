## Context

Changes to `.github/workflows/**` and to `review-rules/**` match no platform's `scope.md`, so they are merged with no code review at all.

Proven on PR #412, whose only change was `.github/workflows/code-review.yml`. The review run's own log:

```
[10:46:06] found platform: .        (rules: .../review-rules)
[10:46:06] found platform: backend  (rules: .../backend/review-rules)
[10:46:06] found platform: web      (rules: .../web/review-rules)
[10:46:06] found platform: apple    (rules: .../apple/review-rules)
[10:46:06]   skipped  [.]: .github/workflows/code-review.yml
[10:46:13] No platforms were reviewed (all skipped or no matching files).
[10:46:13] gh-check: completed with conclusion 'success'
```

The required `code-review` check went green in 8 seconds without a single agent running.

The four `scope.md` include lists today:

| platform | includes |
|---|---|
| `.` | `docs/adr/*.md`, `.claude/skills/**/*.md`, `.bb/skills/**/*.md`, `.bb/AGENTS.md`, `README.md` |
| `backend` | `packages/**/*.ts`, `modules/**/*.ts`, `services/**/*.ts`, `**/*.sql`, `**/*.json`, `**/*.yml`, `**/*.yaml` — all relative to `backend/` |
| `web` | `**/*.ts`, `**/*.tsx`, `**/*.js`, `**/*.jsx`, `**/*.css` — relative to `web/` |
| `apple` | `**/*.swift` — relative to `apple/` |

Nothing covers the repository's `.github/` directory or its `review-rules/` directories.

## Why this matters more than it looks

`.github/workflows/code-review.yml` is the most load-bearing configuration in the repository. It defines the `code-review` Check Run that branch protection requires, the job timeout, the pinned revision of the review bot, the block severity, and the finalizer that writes the `crb-outcome` marker an orchestrator reads. A change there can disable the merge gate entirely, and no reviewer sees it.

`review-rules/**` is the specification the reviewer enforces. A change that weakens or deletes a rule is exactly the kind of change that should be read by someone, and it is currently the kind that cannot be.

At least five pull requests merged in the last two days (#403, #406, #408, #409, #412) changed only that workflow and were therefore never reviewed.

## An open question this issue must answer, not assume

The root platform `.` has **no `tasks/` directory**, unlike `backend`, `web` and `apple`, which each have two or three. `build_platform_agent_prompt` in the review bot discovers task files with `for tf in "$rules_dir/tasks/"*.md` and logs `tasks (0): none` when there are none.

What a platform with zero tasks actually does when it matches a file has not been observed — the root platform has never matched a changed file in any run inspected. It may produce an empty findings set and pass silently, or fail as "agent produced no findings file". **Determine which, empirically, before relying on it.** Widening a scope onto a platform that cannot review is worse than the present state, because it converts an honest "nothing was reviewed" into a green check that appears to mean something.

## Task

Bring `.github/workflows/**` and every `review-rules/**` directory inside the review scope of a platform that can actually review them, and give that platform the review tasks it needs to do so.

## Scope

### In scope

- The `scope.md` include lists, and whichever platform takes ownership of these paths.
- Review tasks for that platform, if it does not have any — covering at minimum what a reviewer should catch in CI configuration: a change that weakens or removes a required check, a permissions grant wider than the job needs, a secret exposed to an untrusted step, a pinned dependency silently unpinned, and a timeout or concurrency setting that can strand a required check.
- `.bb/AGENTS.md` if this changes where a contributor should expect review to happen.

### Out of scope

- Changing branch protection, required contexts, or the workflows themselves.
- Changing the review bot (`dvdtrsnk/code-review-bot`). If a defect there blocks this, report it rather than working around it here.
- Adding new platforms beyond what is needed, or rescoping `backend`, `web` or `apple`.

## Acceptance criteria

1. A pull request whose only change is `.github/workflows/code-review.yml` is reviewed by at least one platform, and that platform runs at least one review task.
2. A pull request whose only change is a file under any `review-rules/` directory is likewise reviewed by at least one platform.
3. The verdict for such a pull request is determinate — it is either a pass with findings reported, or a pass with none, and never a technical failure caused by the platform having nothing to run.
4. The behaviour of `backend`, `web` and `apple` on their own files is unchanged: a pull request touching only `backend/**/*.ts` is reviewed by exactly the platforms it is reviewed by today.
5. The evidence for the open question above is recorded in the pull request description: what a zero-task platform does when it matches a file, and how that was established.
