## Context

Model tier rationale: A new streamed upload route and a periodic cleanup job built from existing seams (the file upload store, blob reference check, per-tenant fan-out), with a shared reference-count rule that must not delete a blob still in use.

Today `POST /api/files` (`services/semprec-api/src/filesHandler.ts`, `blobs/fileUploadStore.ts` `ingestUploadedFile`) streams bytes to storage, de-duplicates the blob by content hash and always creates a Files item (returning the existing one with HTTP 200 on a hash match). There is no way to upload an image that is only a blob, for use in an image property such as a recipe photo, a book cover or an Inbox attachment. `deleteBlobIfUnreferenced` (`blobs/blobsStore.ts`) counts only `properties.file.blobId` and `mail_attachments` as references, so deleting a Files item whose bytes equal an image property's blob would purge that blob. Blob bytes are removed best effort after the commit (`docs/adr/2026-09-28-blob-bytes-deleted-best-effort-after-the-commit.md`) and tenant export reads bytes from the files storage root (`docs/adr/2026-10-17-tenant-data-export-archive.md`).

This issue adds `POST /api/blobs`, widens the reference rule to image properties, and adds a daily cleanup of unreferenced standalone blobs. Later issues build on it: #1564 adds Inbox attachments as a further counted reference, #1963 attaches uploaded blobs to captured Inbox items, #1661 creates the Files item on save from an uploaded blob, and #1793 lets the user replace a cover with an uploaded blob.

Decision: the cleanup age is 24 hours after the blob was created, and runs once a day.

Shared-file ordering: this issue also waits for #1355 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `io-hardening`, `error-handling`, `state-writes` and `testing`.

1. Add `ingestUploadedBlob` to `blobs/fileUploadStore.ts` (or a sibling file in `blobs/`), reusing the streaming, size cap, content-hash dedup and duplicate-bytes cleanup of `ingestUploadedFile` but creating no item. Bytes go to the files storage root (`FILES_STORAGE_DIR`) under a `blobs/` key prefix. After writing and before the database transaction, read at most the first 64 KiB through storage and call the shared gh-1410 detector. A new blob stores detected MIME, or `application/octet-stream` when unknown; the input MIME controls header admission only. Dedup returns the existing blob and metadata unchanged. This integration is completed with gh-1410 in the same batch.
2. Add `POST /api/blobs` to `services/semprec-api` (handler beside `filesHandler.ts`, routed in `app.ts` and listed in `routeMatrix.ts`), authenticated like `/api/files`, with the same `maxFileSizeMb` limit (413 `payload_too_large`) and `Content-Type` required. It returns 201 with `{ blobId, byteSize, mimeType }`; an identical upload returns the existing blob with 200. The route accepts only `image/*` content types here and answers other types with 400 (field `Content-Type`); later issues widen the allowed set when they need it.
3. Extend `deleteBlobIfUnreferenced` so that a blob also counts as referenced when any visible item has an image property naming it. Enumerate the image property keys from the schema (`photo`, `cover`, `coverOverride`, and any other property of type `image`) rather than hardcoding names where the property table allows it. Keep the existing `visibleDatabaseIds` guard.
4. Add a daily job `blobsUnreferencedSweep` (task name registered in `packages/queue/src/index.ts` with its lane, crontab line in `worker.ts`, handler in `blobs/`) that runs through `forEachActiveTenant` in batches, selects blobs created more than 24 hours ago, calls `deleteBlobIfUnreferenced` for each, and removes the bytes best effort after the commit.
5. Tests: upload creates a blob and no Files item; dedup; size cap; non-image rejected; a Files item purge keeps a blob an image property uses; the sweep removes a stale unreferenced blob and keeps a referenced or a fresh one; a foreign tenant's blob is untouched. Exercise standalone HTTP detection with real image bytes, unknown bytes, PDF bytes carrying an image header, and dedup onto an existing blob with different persisted MIME.

### Out of scope

## Acceptance criteria

- When an image is posted to `/api/blobs`, then the response contains `blobId`, `byteSize` and `mimeType`, and no Files item exists for it.
- When the same bytes are posted again, then the same `blobId` is returned.
- When a Files item is purged and its blob is also named by an image property, then the blob and its bytes remain.
- When a standalone blob has no referencing file property, image property or mail attachment and is older than 24 hours, then the daily job deletes the row and, after commit, its bytes; a newer or referenced blob is kept.
- When a non-image Content-Type header or an oversized body is posted, then the response is 400 or 413 respectively and no bytes remain in storage.
- When new standalone bytes are posted with an image header, the stored and returned MIME follows detected content (including PDF), or is `application/octet-stream` when unknown; no Files item is created. A dedup hit preserves and returns the existing blob metadata unchanged.
