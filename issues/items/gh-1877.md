## Context

Model tier rationale: It decides, for every recurring series, which occurrence dates are virtual, real or cancelled inside a range, and it must stop the core Events source from also returning the series row, so an error duplicates, drops or double-counts calendar entries for every user with a recurring event.

The calendar timeline (#1717) merges sources registered in `backend/packages/data/src/calendar/timelineSources.ts`; its core Events source returns stored Events rows. A recurring Event (#1817) is one row whose occurrences are computed, and an occurrence that has an exception or a link is a real item (#1843). The sleep source (#1806) was added before this one in the same list. This issue expands series into occurrences for the requested range and gives other readers one function to do the same: the Events collection ordering (#1905) and subscribed event expansion (#1966) use `expandEventOccurrences`.

Behavior of `expandEventOccurrences(series, from, to)`: the dates in `[from, to]` on which `eventRecurrenceOccursOn` is true for the series; for a multi-day series an occurrence is included when it overlaps the range (its length is the series' `endDate` minus `date`). For each date: if a live occurrence item exists for `(seriesId, date)` the entry is that item (a real id, `overridden` true); if the occurrence item is in the trash the date is cancelled and omitted; otherwise the entry is virtual with the id `<seriesId>@<date>`, `readOnly` true (a client calls the materialize route of #1843 before editing it), and the series' details with `date` and `endDate` set to the occurrence. Entries carry `seriesId`, `occurrenceDate` and `overridden`; the compact shape also carries `seriesId` and `occurrenceDate` so a month can tell exceptions apart.

Timeline integration: the core Events source skips every Event that has a recurrence rule or a `seriesId` (those come only from this source, so the series row is not shown twice and a materialized occurrence is not shown twice); this source returns all occurrences of the live series whose range overlaps the request, including the real ones.

Decision: expansion works on dates and wall-clock times (stored as such), so daylight-saving changes do not move an occurrence.

Decision: a series is expanded for at most the request's range (at most 93 days), and at most 100 occurrences per series per request.

## Acceptance criteria

- When a weekday series starts on Monday 12 Oct 2026, then the timeline for 12-23 Oct returns ten occurrences 9:00-9:30.
- When one occurrence is materialized and moved, then only that entry differs and is a real item with `overridden` true; the others stay virtual with ids `<seriesId>@<date>`.
- When a materialized occurrence is in the trash, then that date is absent.
- When the timeline is read, then the series row itself is not returned in addition to its occurrences.
