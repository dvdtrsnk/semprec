### Source behavior: [11/22] pi-agent-core — MCP integration + tool grants

## Context

This issue, the second in the pi-agent-core series, addresses two connected requirements around MCP (Model Context Protocol): how the system discovers what tools an MCP server offers, and how it decides which of those tools a specific project's agent is allowed to see.

The MCP specification itself (`modelcontextprotocol.io`, Security Considerations section) makes a strong claim about its own safety: the client "SHOULD always [have] a human in the loop with the ability to deny tool invocations" and "MUST consider tool annotations to be untrusted unless they come from trusted servers." Its own Session Hijacking section goes further and names the exact risk this design addresses: a server that changes its offered tools between calls (via `notifications/tools/list_changed`, an optional `listChanged` capability) "could [leave a client] with tools that they were not aware were enabled." Independent security research (Invariant Labs, "Tool Poisoning Attacks," April 2025) calls this a *rug pull*: a server offers a harmless tool, earns trust, then silently changes its description or behavior at runtime.

The specification's reference flow (server sends `list_changed` → client re-calls `tools/list` → gets an updated list) is designed to be *reactive* — but nothing in the specification forces a client to actually listen for that flow (it's a SHOULD on the server, no MUST on the client). Ignoring `list_changed` and requiring a manual resync is therefore not a protocol violation — it is a legitimate, just less common, implementation choice, and it closes exactly the gap the specification itself names but does not solve.

Verified directly against the documentation of two comparable projects, not just assumed: OpenClaw by default gates tools that lack MCP "safety annotations" per call, but `--approval approve` disables this gate entirely for the whole server, and tools *with* an annotation bypass the gate "by design" — trusting a claim the server makes about itself, exactly what the MCP spec labels MUST-NOT (annotations must be treated as untrusted unless they come from a trusted server). Hermes is worse: it registers tools automatically at startup with no approval step at all (only an optional `include`/`exclude` filter) — and its own issue tracker has an open, confirmed bug where destructive MCP tools are auto-denied without ever showing the user a prompt, i.e. a gate that doesn't even work as intended. Semprec's default position is the opposite of both: nothing from an MCP server is visible until a human explicitly synchronizes it and it passes the default `requires_approval`.

## Task

Implement MCP integration as **one explicit, human-triggered sync step** (no subscription to `list_changed`, no live reactivity), plus a **third "Tools" block on the project's AGENT page**, where visibility is granted per project and per tool — mechanically enforced through the generated permission manifest, not a text instruction in the `agents` field.

Specifically:

1. **System DB "MCP servers"** owned by Semprec (same architectural pattern as "Mailboxes owned by Emails" from issue #26): name, connection config, `active` toggle, `sync_status` pill, `last_synced` timestamp. Credentials (token/API key) go into the shared `external_credentials` table (issue #26), encrypted via `packages/credentials` — never as a plain `text` property.
2. **Semp is allowed to propose connecting a server**, but not to sync it. The proposal goes through the standard `entityKind: 'database'` proposal/confirm path (issue #28): Semp prepares a card with name and URL, a human confirms via `confirm`. The proposal's `properties` jsonb never carries a credential — a human fills that into a separate field within the same confirm step.
3. **The "Synchronize tools" action** — a strictly human action, outside `confirm` and outside the reach of any future grant (structural unavailability to AI, not just a default denial). It calls `tools/list` on the server and materializes the response into `mcp_tool_registrations`. A newly synced tool defaults to `requires_approval = true` and `risk_class = 'unclassified'` until a human manually reclassifies it.
4. **Active registrations project into the `ModuleRegistry` pool** exactly like `agentTools` entries from a module manifest (issue #29) — one unified source of truth for what exists in the system at all; MCP is just another source feeding it, not a second registry alongside the first.
5. **A "Tools" block on the project's AGENT page** — a third block below Purpose/Allowed/Forbidden/General instructions and Heartbeats, using the same visual pattern already used elsewhere for multi-row toggleable lists (the `active` checkbox on Mailboxes/Accounts) — no new UI idiom. The list contains every active `mcp_tool_registrations` row across the whole system (not just servers "belonging" to this project — an MCP server is a system-level resource, and any project can pick individual tools from it), with a checkbox whose state is directly `project_mcp_grants.granted` for the pair (this project, this tool).
6. **Extend the generated permission manifest** (issue #21) with a fourth source: on every `agent_run`, the list of `AgentTool` entries from the MCP source is restricted to the intersection of "active registration" ∩ "`project_mcp_grants.granted = true` for this project" — an unchecked tool in a project *does not exist* in the queue of tools the agent receives, the same "absence of capability, not runtime blocking" logic issue #29 describes for `requiresCapability`. If a tool additionally has `requires_approval = true` (above), the grant only makes it available in the tool set — every individual invocation still goes through the approval queue (a later issue); these are two independent gates, not one.
7. **A generic MCP-invoke handler** inside `semprec-agents` (where `agentLoop` lives, so the live MCP transport connections must live there too) — it accepts a tool name and arguments, looks up the `mcp_tool_registrations` row, forwards the call over the stored transport (stdio/SSE/HTTP depending on server config), and returns the result back into the agent loop exactly like any native `AgentTool` handler.

## Scope

### In scope

- System DB "MCP servers" under Semprec (schema per point 1 above) + extending `external_credentials` with MCP servers as a second kind of owner alongside mail accounts.
- The proposal/confirm path for `entityKind: 'database'` targeting MCP servers, including the separated non-credential/credential write within the confirm step.
- The `mcp_tool_registrations` and `project_mcp_grants` tables exactly per the specification's schema (unique index on `(mcp_server_item_id, tool_name)`, primary key on `(project_item_id, mcp_tool_registration_id)`).
- The "Synchronize tools" action (calling `tools/list`, materializing into `mcp_tool_registrations`, defaults `requires_approval = true`, `risk_class = 'unclassified'`) — purely human-triggered, with no path through `confirm` or any other grant.
- Projecting active registrations into the `ModuleRegistry` pool as `agentTools`.
- The third "Tools" block on the project's AGENT page (checkbox pattern, `project_mcp_grants.granted`, defaulting to `false` for both a new tool and a new project).
- Extending the manifest generator with the fourth source (intersection of active registration ∩ grant).
- The generic MCP-invoke handler in `semprec-agents` (stdio/SSE/HTTP transport, wired into `agentLoop`).
- `project_mcp_grants` as a purely `owner: user` table with no AI write path at all (not even through `confirm`).
- Minimal manual editing of `risk_class` / `requires_approval` on an existing registration (a human can reclassify a tool after sync).

### Out of scope

- **The actual approval queue** that enforces `requires_approval = true` on individual invocations at runtime — that is a later issue ("pi-agent-core — approval queue," #32). This task only stores `requires_approval`/`risk_class` as data; the runtime gate on invocation does not belong here.
- Any automatic/heuristic classification of `risk_class` — just a column with a default and manual editing.
- Listening for `notifications/tools/list_changed` or any reactive/subscription variant of sync — deliberately rejected (see Context).
- The trust-on-connect pattern (automatically exposing tools when a server connects, or switching to an "approve everything" mode) — considered and rejected, following OpenClaw/Hermes as cautionary examples.
- Anything from the lifecycle events / budget cap in `packages/agent-runtime` (#30) — the MCP-invoke handler plugs into budget accounting through the already-existing mechanism; the mechanism itself is not changed here.
