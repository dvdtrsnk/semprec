## Context

Model tier rationale: A guard in the Tasks pre-write transform, one idempotent converter of an existing module data migration, and a change of one read statement and its response shape. It reuses existing mechanisms, adds no table, route or column and changes no authorization, but it touches stored task data, so a mistake in the converter or in the isolation of its test would reach existing rows.

Source #1692 added `tasks` to `GET /api/mail/threads/:threadId` (`THREAD_TASKS_SQL` and `listThreadTasks` in `backend/packages/data/src/mail/mailThreadDetail.ts`). Its handover and acceptance receipt record two readings that the owner has now decided.

Decision 1: a task always has a status. Today a Tasks item can be stored without one. `Tasks.status` has `config.default` `notDone` (`seed/seedTenDatabases.ts`; installed on tenants seeded earlier by `runPropertyDefaultsCutoverMigration`), and `createItemWithClient` (`chokePoint/itemWrites.ts`) fills it in, but only for a key the caller did not name: it runs after the Tasks pre-write transform and keeps a key that is present. A create that names `status: null` therefore stores no status (the test "puts not-done tasks first" in `mailThreadDetailTasks.test.ts` relies on this), a patch of `status: null` clears it, and a task stored before the default existed has none. `prepareTaskWrite` in `tasks/taskPreWriteTransform.ts` does not look at `status`, and `assertSelectValuesKnown` lets a user or agent write `null` into any select. The thread detail then sorts such a task into the group of `done` tasks (`COALESCE(... = 'notDone', false)`) and answers `status: null`. Both holes are closed here: the write path refuses to store a task without a status, and the existing rows are filled by a Tasks data migration, the mechanism the Tasks transitions 1.0.0 to 1.3.0 already use (`dataMigrations` in `seed/systemDatabasesModuleManifest.ts`, applied per tenant by `runModuleDataMigrations` through `provisionTenant` in the deploy seed step). The fill value is `notDone`, the property's own default. A task with a status keeps it.

Decision 2: a trashed project or person is not left out of a task. It is listed with a marker that it is in the trash. The code already marks a trashed object that is reached from another record with `state: "active" | "trashed"` (`SempRefContext` in `semp/sempRefReadContext.ts`, `SempRefResolution` in `shared/src/sempMessageRef.ts`, where a trashed item keeps its label). The task's `project` and `people` entries take the same `state` field.

The thread detail is read in the caller's tenant scope and every table of the statement is tenant-scoped (`app_tenant_default()`); both changes keep that.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys`, `testing` and `adr-conventions`.

1. In `prepareTaskWrite` (`tasks/taskPreWriteTransform.ts`), before the early return for a patch that names none of `name`, `date`, `timeFrom`, `timeTo`: when the patch has the key `status` and its value is not a string with at least one character, throw `ValidationError("Property 'status' must be a task status", { field: "status" })`. A create that does not name `status` is unchanged (the property default fills it in); an update that does not name `status` is unchanged, so a write to a legacy status-less row that names no status still succeeds. `prepareTaskProposal` calls `prepareTaskWrite`, so a proposal is refused the same way. Which strings are allowed stays with `assertSelectValuesKnown`.
2. Add `tasks/backfillTaskStatus.ts` exporting `backfillTaskStatus(properties)`: when `status` is missing, `null` or not a string with at least one character, return the properties with `status` set to `"notDone"`; otherwise return the same object. It is pure and idempotent and changes no other key.
3. In `seed/systemDatabasesModuleManifest.ts` add `export { backfillTaskStatus } from "../tasks/backfillTaskStatus.js";` beside the other Tasks converters and one `dataMigrations` entry directly after the 1.2.0 to 1.3.0 one: `databaseKey` `TASKS_MODULE_ID`, `fromVersion` `"1.3.0"`, `toVersion` `"1.4.0"`, `converterExport` `"backfillTaskStatus"`, with a comment that names this issue and that the manifest `version` is not lowered or raised for it, as for the entries before it. The runner (`migrationJob/moduleDataMigration.ts`) is not changed: it converts every item of the Tasks database of the tenant in scope, trashed ones included, in row-locked batches, and rewrites a row only when the converter changes it.
4. In `taskRow`, `status` is `z.string()`. The rest of the order (date ascending with undated last, creation time, id) and the one-statement-plus-one-links-read shape are unchanged.

## Scope

### In scope

- Refusing a Tasks write that names a status which is not a nonempty string, and filling the status of stored tasks that have none.
- Listing a trashed project or person of a thread task with `state: "trashed"`, and `state: "active"` on the live ones.
- Removing the status-less case from the order and the type of the thread detail's tasks.

### Out of scope

- A SQL migration, a column, an index or a constraint: the status stays a JSON property of `items`.
- Checking that a status is one of the catalog options (`assertSelectValuesKnown` keeps that).
- A `state` field on any other response, and the `links` of a task.
- Showing a trashed task in the thread detail, or any change to the thread messages and header.
- Any other reader of `status` (the Today view, the day rollover, recurrence): they already treat `notDone` as open.
- Creating tasks from a thread (#1900) and syncing people (#1923).

## Acceptance criteria

- When a Tasks item is created with `status` `null`, `""` or a number, or updated to one of them, then the write is refused with a validation error on `status` and nothing is stored; when a task is created without `status`, then it is stored with `notDone`.
- When the Tasks 1.3.0 to 1.4.0 transition has run for a tenant, then every task of that tenant, a trashed one included, has a nonempty string `status`; a task that already had one keeps it and its `updated_at`; a second run changes nothing.
- When one tenant runs the transition, then a status-less task of another tenant is not changed.
- When a task of the thread has a project in the trash, then the thread detail lists `project` as `{ id, state: "trashed" }` with no `name`; when it has a person in the trash, then the person is listed as `{ id, state: "trashed" }` with no `name`, after the live people, who stay in name order; live projects and people carry `state: "active"`.
- When a task is in the trash, then it is still not listed.
- When the detail lists tasks, then each has a string `status`, those with `notDone` come first, and the rest of the order is as before.
