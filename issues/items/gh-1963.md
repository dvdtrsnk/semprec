## Context

Model tier rationale: One extension of an existing capture route and an upload allowlist across known seams, with tenant isolation and a clear rejection table, using the blob upload route and attachment store that blockers deliver.

An Inbox item is captured with `POST /api/inbox/items` (#1961). A photo, scanned document, audio note or shared file belongs to that capture. The client first uploads the bytes with `POST /api/blobs` (#1401), which stores a blob without a Files item, then sends the blob ids in the capture. Today `POST /api/blobs` accepts only `image/*`, and the capture route knows no attachments. #1564 created the `inbox_attachments` table and its store.

Decisions:
- Allowed attachment types (by the blob's stored mime type, which is decided from the bytes and never from the client's header, see #1410): PDF, JPEG, PNG, XLSX, DOCX (the types Files knows), and audio M4A (`audio/mp4`, `audio/x-m4a`) and MP3 (`audio/mpeg`). HEIC is not allowed: the iPhone client converts HEIC to JPEG before upload, and the server does not convert HEIC. Further types are added only when they are needed.
- A capture may have an empty `text` when it has at least one attachment (a photo with no words is a normal capture).
- At most 10 attachments per capture; the same `blobId` twice in one request is a validation error.
- A blob id that does not exist or belongs to another tenant answers the same as any invalid blob id (no enumeration).
- Rejections are all-or-nothing: if one attachment is refused, no Inbox item and no attachment is created.

## Task

Load `io-hardening`, `error-handling`, `state-writes` and `testing`.

1. Add `backend/packages/data/src/inbox/attachmentTypes.ts` exporting `INBOX_ATTACHMENT_MIME_TYPES` and `isAllowedInboxAttachmentMime(mime)` with the list above.
2. Widen `POST /api/blobs` (`backend/services/semprec-api/src/blobUploadHandler.ts`, `ingestUploadedBlob` in `backend/packages/data/src/blobs/fileUploadStore.ts`) from images only to the allowlist plus images already allowed. Detect the stored mime from the first bytes: the detector of #1410 for documents and images, and a new small detector in `backend/packages/data/src/blobs/audioTypeDetection.ts` for M4A (an ISO-BMFF `ftyp` box with brand `M4A `, `mp42` or `isom` and an `audio/mp4` result) and MP3 (`ID3` tag or an MPEG frame sync). A body whose detected type is not allowed answers 415 `unsupported_media_type`; the size limit stays 413.
3. Extend the body of `POST /api/inbox/items` with `attachments: [{ blobId, source }]` (strict; `source` one of the five values). Validate each blob in the caller's tenant, then its stored mime against the allowlist: unknown or foreign blob gives 400 `validation_failed` with `field: "attachments"`; a mime outside the list gives 415 `unsupported_attachment_type` with `details: { blobId, mimeType }` so the client can show a message.
4. Insert the attachment rows with `insertInboxAttachments` in the same transaction as the Inbox item, in array order. The capture response lists them as `{ attachmentId, blobId, mimeType, byteSize, source }`.
5. Add the cases to `routeMatrix.ts` and `tenantIsolationRoutes.test.ts`.
6. Tests: a photo-only capture creates the item and one attachment, and no Files item; a capture with a PDF and an M4A creates two ordered attachments; a HEIC blob, a foreign blob id and an unknown id are refused and nothing is created; 11 attachments or a repeated `blobId` give 400; an audio upload with an MP3 body labeled `image/jpeg` is stored as `audio/mpeg`; `POST /api/blobs` with an executable is 415.

## Scope

### In scope

- Accepting the allowlisted types at `POST /api/blobs`, and attaching uploaded blobs in the capture transaction with the rejections above.

### Out of scope

- The attachment table and store: #1564.
- Moving an attachment into Files: #1703.
- Metadata and thumbnails: #1965.
- Converting HEIC on the server: not planned (the client converts to JPEG).
- Adding or removing attachments of an existing Inbox item.
- Where the Journal replaces its single attachment; that is a client rule.

## Acceptance criteria

- When a photo-only capture is posted with a valid blob id, then an Inbox item and one attachment are created, `text` may be empty, and no Files item exists.
- When a blob of another tenant, an unknown blob or a HEIC blob is named, then the capture is refused and no item or attachment exists.
- When an MP3 body is uploaded with a wrong `Content-Type`, then the blob's mime is `audio/mpeg`.
- When an unsupported type is uploaded to `/api/blobs`, then the response is 415 and no bytes remain.
- When more than 10 attachments or a repeated `blobId` are sent, then the response is 400.
