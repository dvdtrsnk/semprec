### Requirement gh-1825: [inbox-editing 09/23] Return editor schemas on Inbox cards

#### Context

Model tier rationale: Wide declaration surface across several module manifests and catalogs plus a locale-aware resolver wired into the card read contract, where a wrong condition or missing label silently changes what every card editor shows and what confirm will later enforce.

#1417 defines how a module declares an editor schema per card base kind (groups, controls, required flags, conditions, catalog keys for labels and placeholders) and declares the one for MCP server cards. The Inbox card list (#1807) returns each card with its base kind (the kind of thing the card creates; an invalid card carries the base kind it edits). This issue completes the read side: every card in the list carries an `editorSchema`, localized for the caller, and the other base kinds declare their schemas.

Decision: the card response carries a resolved, localized schema, never catalog keys: `editorSchema: { baseKind, groups: [{ key, fields: [{ key, control, inputType?, label, placeholder?, required?, when?, timeHiddenWhen?, optionsSource?, info? }] }] }`. The locale is the caller's `users.locale` (`ctx.identity.user.locale`), resolved with `resolveCatalogLabel` and the module's catalogs as in `createTranscriptSpeakersRouteHandler` (`backend/packages/data/src/transcription/transcriptionRouteHandlers.ts`), English fallback. The schema is part of the card's additive fields, so existing clients ignore it.

Decision: step fields live in the schema of the card's base kind as pseudo fields that carry a `when` on their step switch (for example, on a task or file card, `followupTask` toggle and `followDate` with `when followupTask equals true`), matching how the card shows them; the storage of those values is the business of the multi-step proposal work and is not decided here. The pseudo field keys come from a closed list; a module added later that brings its own step adds its keys by extending that list.

Decision: a card whose base kind has no declaration gets `editorSchema: null`; an `invalid` card gets the schema of the base kind it edits (a full task schema for an invalid task card).

### Requirement gh-2028: [inbox-proposals 11/19] Describe what the update steps of a proposal change on Inbox cards

#### Context

Model tier rationale: One read-side resolver that turns the stored `before` and `after` of update steps into localized labels inside the existing card read model, with batched lookups and the ref targets of the same proposal; no writes, storage or tenant contract.

A multi-step proposal (#1378, #1479) can carry `update` steps that change an existing item: move a project to another area, or change a value such as a project's `status`. Each `update` step stores `before` and `after` of every key it changes. The product owner decided that the card must say what will change (for example that a project moves from area Work), because nothing may happen silently; the design adds the text. The client cannot compose it from the envelope: `before` and `after` hold item ids and canonical keys, not item names or option labels in the user's language, and a target may be another step of the same proposal (`{ ref }`) that does not exist yet. The card list `GET /api/inbox/cards` (#1807) returns the effective envelope only.

Decision: every card whose effective envelope has active `update` steps (skipped steps are left out, as in #1479) carries `changes: [{ ref, itemId, itemLabel, field, fieldLabel, from, to }]`, one entry per changed key. `from` and `to` are `{ value, labels }`: `value` is the stored value (an array of item ids for a relation, the canonical key for a select, the raw value otherwise) and `labels` the display labels (current item names for a relation, the localized option label for a select, an empty array otherwise). A `{ ref }` target is labelled with the title the referenced step would create. `itemLabel` and `fieldLabel` are localized in the locale the list already uses for its labels. Labels are resolved on read, never stored. Cards without `update` steps carry no `changes`.

#### Task

Load `canonical-keys`, `io-hardening` and `testing`.

1. Add `describeUpdateSteps(client, envelope, locale)` in a new `backend/packages/data/src/inbox/proposalChanges.ts`: for each active `update` step, build the entries above from `before` and `after`; resolve all item names of a page of cards in one items lookup; resolve field and option labels through `resolveCatalogLabel` and the module catalogs; label `{ ref }` targets from the referenced step's title property.
2. Call it from `backend/packages/data/src/inbox/inboxCardsStore.ts` when building the cards and add `changes` to the card.
3. Tests: a proposal moving a project from area Work to a new area created by another step returns one entry with `field` `area`, `from.labels` `["Work"]` and `to.labels` with the new area's title; an `update` step changing a project's `status` to `done` returns the localized option labels of both values in Czech and English; a disabled `update` step contributes nothing; a page of 50 cards resolves names with a constant number of queries; a card without `update` steps has no `changes`.

Count changes that trigger a refresh in this issue are: an approval request created or decided, and a change of the user's badge switches. Invitation and Inbox changes call the same enqueue helper from their own issues (#1954).

### Requirement gh-1918: [realtime-derived 04/07] Add notification preference and badge count invalidations

#### Context

Model tier rationale: Two id-less user-narrowed scopes on the established realtime catalog with a handful of write sites that must be enumerated from the counting function, following the pattern of the preceding scope issues.

A user can change notification preferences on one device and see the change on another, and the app badge and the per-tab counts change when the number of pending decisions changes. Nothing signals either today. This issue adds two realtime scopes, `notificationPreferences` and `badgeCounts`, both without payload fields, following exactly the shape and wiring of the earlier scopes in this chain (see #1868): the `invalidation` message type with a `scope` discriminator in `backend/packages/realtime/src/pgNotifyPublisher.ts`, the `OutboundFrame` variants in `protocolV1.ts`, the `InvalidationEvent` variants in `backend/packages/data/src/realtimeHook.ts`, the mapping in `syncServer.ts` and the parser in `backend/packages/realtime-client/src/serverFrame.ts`. Rules of `docs/adr/2026-10-16-tenant-scoped-realtime-fan-out.md` apply: thin payload, tenant from Postgres, no replay, publish only after commit with `runAfterCommit`.

Both frames are narrowed to the sockets of the user they concern (`userId` set), since preferences and counts are per user.

- `notificationPreferences`: published when a user's stored notification preferences change, from the preference store delivered by #1441.
- `badgeCounts`: published whenever an input of the pending-decisions count defined by #1828 changes for a user. The implementer lists those writes by reading the queries of that counting function (a pending approval request appearing, being decided or terminalized, and the other states it counts), publishes next to each of them, and names them in the pull request. A write that does not change the count still may publish; a missing publication is the defect to avoid.

Reading the new numbers stays REST: the client refetches the preference and count endpoints. The next scope in the chain is the account scope #1946.
