## Context

Model tier rationale: Adding one optional descriptor field to the module manifest schema and filling it for three record types follows the existing manifest pattern, with no new lifecycle, authorization or persisted-data contract.

Every record page shows a "related" section at the bottom: one row per collection that has records connected to the open record, in a fixed, meaningful order that depends on the type of the open record (a project does not list Tasks because its page shows them in a section of their own; an area does not list Journal). Today nothing declares such an order. The operation that computes the rows (#1839) needs it, so this issue only declares and exposes the order data.

A module manifest describes each of its databases with `ModuleDatabaseDescriptor` in `backend/packages/module-registry/src/manifest.ts` (`key`, `name`, `defaultViewType`), validated by the Zod schema in the same file and projected by `ModuleRegistry.getDatabases()` in `backend/packages/module-registry/src/registry.ts`. #1407 extends the same descriptor with display order and visibility of databases (`switcherOrder`); this issue builds on that so both additions touch the descriptor in sequence.

Decision: the order is declared on the database whose record is being viewed (the "record type"), as `relatedOrder: { order: string[]; omit?: string[] }`. `order` lists database keys; `omit` lists keys never shown for that record type. Databases not named in either list come after the listed ones, ordered by the database display order from #1407 and then, for user-created databases, by name; that fallback is applied by the consumer, not stored here. Keys of databases belonging to modules that are not active are ignored when the order is resolved, and an unknown key is ignored rather than rejected, so a manifest may name databases of optional modules.

Shared-file ordering: this issue also waits for #1417, #1515 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys` and `testing`.

1. Add the optional `relatedOrder` field to `ModuleDatabaseDescriptor` and its Zod schema (non-empty strings, no duplicates within or across `order` and `omit`), and include it in `ModuleDatabaseProjection` returned by `ModuleRegistry.getDatabases()`.
2. Add a registry accessor `getRelatedOrder(databaseKey)` that returns `{ order, omit }` with keys of inactive modules and unknown keys removed, or `undefined` when the database declares none.
3. Declare, in `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` (version bump if the manifest content is versioned in tests):
   - projects: order `projects`, `events`, `files`, `threads`, `transcripts`, `companies`, `people`, `journal`; omit `tasks`;
   - areas: order `projects`, `tasks`, `events`, `files`, `threads`, `healthRecords`, `companies`, `people`, `books`, `movies`; omit `journal`;
   - people: order `projects`, `tasks`, `events`, `files`, `threads`, `transcripts`, `companies`, `people`, `journal`; omit nothing.
   Use the existing database key constants where they exist; `threads` is a key of a module delivered elsewhere and stays a string literal. Recipes are not related to Areas, so `recipes` is not listed for areas.
4. Unit-test the schema (accepts valid, rejects duplicates and empty strings), the projection, and the accessor with an inactive module and an unknown key.

## Acceptance criteria

- When a manifest declares `relatedOrder` with a duplicate key or an empty string, then manifest validation fails.
- When `getRelatedOrder("projects")` is called, then it returns the project order with `tasks` omitted.
- When a listed key belongs to an inactive module or matches no database, then it does not appear in the result and nothing throws.
- When a database declares no `relatedOrder`, then `getRelatedOrder` returns `undefined`.
- The full backend `pnpm run verify` passes.
