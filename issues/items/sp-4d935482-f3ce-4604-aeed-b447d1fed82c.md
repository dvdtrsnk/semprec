### Requirement gh-1573: [mail-items 01/15] Make every mail thread an item in a Threads database

#### Context

Model tier rationale: This adds a persisted-data contract (a new system database, new `mail_threads` columns, a per-tenant cutover with a batched backfill) and changes the thread merge path that moves edges between items, so a mistake corrupts existing tenant data.

A mail thread is not an item today. `mail_threads` (migration `0006_mail_sync.sql`) has only `id` and `subject_hint`, `createMailThread` and `reassignThread` in `backend/packages/data/src/mail/mailMessageMetaStore.ts` insert and delete its rows, and `resolveThreadId` in `mail/threading.ts` calls them during ingest. Emails have no relation to Projects or Companies. Because a thread is not an item, it cannot hold a project or a company, be added to a Semp message, be filtered by project, or own attachments and tasks. This issue makes every thread an item of a new system database Threads owned by the mail module, with two user-owned single-valued relations, Threads.project and Threads.company.

Facts that shape the design:

- The databases of the ten-database seed are `schema_locked` before `seed/seedEmailModule.ts` runs, and `createProperty` rejects a locked database (`chokePoint/propertiesStore.ts`). So the new relations live on the Threads side and are one-directional, exactly like `Emails.attachments` and `Files.area`.
- An existing tenant receives schema changes only through a per-tenant cutover (`db/tenantCutoverMigrations.ts`; the pattern is `transcription/transcriptsCatalogCutoverMigration.ts`).
- A generic `relation.put` goes through the choke point and not through a module writer, so "at most one project per thread" must be a relation-edge write hook (`registerRelationEdgeWriteHook`, the pattern is `transcriptSpeakerEdgeWriteHook` in `transcription/transcriptionSpeakerEdges.ts`, registered in `domainWriteHooks.ts`). A relation-edge hook runs before an edge write, also in dry runs, and not on delete.

Decisions: the public thread id stays `mail_threads.id` everywhere (API, related counts); the new `mail_threads.item_id` is internal and must never be exposed. The item `name` is the subject of the first message and is not renamed later. Threads.project and Threads.company are `owner: user` because users and Semp write them through the generic `relation.put`.

This issue builds on #1493 (merged thread ids stay resolvable through an alias written when two threads merge). It is the foundation for #1869, #1872, #1638, #1874, #1612 and #1839.

Shared-file ordering: this issue also waits for #1530, #1552, #1572 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1574: [recordings 05/17] Add the recording upload endpoint with event context and recording time

#### Context

Model tier rationale: It adds an authenticated streaming upload route that accepts a caller-chosen event id (a tenant-isolation and enumeration contract), a new tenant table with row-level security, and a transaction that must enqueue exactly one transcription run under concurrent and repeated uploads.

Today a recording enters the system only through `POST /api/files` (`backend/services/semprec-api/src/filesHandler.ts`, routed by hand in `app.ts`): a raw stream with `Content-Type` and `X-Filename`, a 100 MB cap, 201 for a new file and 200 for a content-hash duplicate. `ingestUploadedFile` (`backend/packages/data/src/blobs/fileUploadStore.ts`) opens its own transaction and accepts no client. The heartbeat action `core.filesTranscriptionTrigger` (`transcription/transcriptionActions.ts`) then enqueues `transcriptionJob { fileItemId }` for an `audio/*` Files item with no `Emails.attachments` edge; video is transcribed only through `POST /api/transcriptions`. The first pipeline step, `runCreateStep` in `backend/services/semprec-transcribe/src/transcriptionTask.ts`, writes only `name` (the `X-Filename`), `status` and `link`; the prepare step later writes the Transcripts `date` from the media's `creation_time`, else the upload time. An event is attached only afterwards by the end-of-pipeline match.

This issue reverses the earlier decision that a recording enters only through `/api/files` and producers merely enqueue a job. A recording made or imported next to an event now carries that event, the time it was recorded, and may be a video whose audio track is transcribed. It adds `POST /api/recordings`, a `recording_requests` table that keeps the per-recording context on the Files item (not in the job payload, which requeue, rerun and replace overwrite), and the intake function that enqueues the job in the upload's own transaction. Attaching a plain file to an event stays with `POST /api/files` and #1645, which reuses the transaction-aware upload variant added here. It builds on #1464 (several transcripts per event). It unblocks #1644 (writes the transcript-to-event edge), #1624 (fast transcript row), #1627 (language and speaker count), #1698 and #1986 (explicit no-event decision, stored in the same table).

iOS contract (documentation only, no server work): the client uploads from a file with a background URLSession (a repeated upload is safe, see dedup below), encodes AAC mono 64 kbit/s (about 29 MB per hour, so 1.5 h fits the limit), sends a video as its extracted m4a audio track, and handles Discard and Pause itself; the `recording` transcript status stays unused.

Decisions:
- When the same bytes were already uploaded and the transcript exists, a request carrying `X-Event-Id` for a live event with no event edge on that transcript links it in the same transaction; the same event is a no-op; a different event, or an existing `recording_requests` row for a different event, answers 409 `recording_linked_elsewhere { transcriptId, eventId }` and writes nothing.
- An event in Trash at request time or by the transaction is treated as no event (`eventId: null`) and normal matching runs.
- `event_decision` is created with default `'none'` and no CHECK constraint; #1986 defines further values.

Shared-file ordering: this issue also waits for #1572 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1576: [transcripts 03/19] Add the transcript detail endpoint

### Requirement gh-1640: [transcripts 04/19] Ask about every unmapped speaker with quotes, reason and alternatives

#### Context

Model tier rationale: This reshapes how every speaker card is produced (a card for every unmapped speaker, with or without a suggestion and an envelope) and widens what a transcript card may carry and confirm (relations on an Event proposal, a new Person with the speaker edge), in the shared proposal confirm and revise paths; the role-switch and atomicity rules of those paths are easy to break and affect every card kind.

Today the transcription worker's speaker step (`runSuggestSpeakersStep` in `backend/services/semprec-transcribe/src/transcriptionTask.ts`, `backend/packages/data/src/transcription/transcriptSpeakerSuggestion.ts`, `backend/services/semprec-transcribe/src/speakerSuggestion.ts`) asks the model once, only when the transcript is linked to an Event with named participants, and creates a `transcript` card only for each speaker the model mapped to a participant. The card has a `relation` envelope through `speakers` with `{ speaker }` metadata, no reason, no quotes, no alternatives. A speaker the model could not place gets nothing, so the user is never asked "who is this speaker?", and the card cannot offer a person who is not a participant of the Event, nor a new person. The role of a transcript card (Event or speaker) is derived from its stored envelope, so a card without an envelope could be revised into an Event proposal.

This issue makes the question complete. Every unmapped speaker gets a card; the card carries what the user needs to decide (a reason, two or three quotes, when the speaker first talks, the source transcript, the alternatives) in its `context` (the property added by #1451); when the model is not sure the card is `needsClarification` with no envelope and the user's choice is a revise (#1870). It also covers the envelope work that cards need for this: an Event proposal on a transcript card may carry relations (the envelope relations and their atomic write on confirm of #1476, for example the project of a new meeting), and a speaker card may propose a new Person created together with the speaker edge. The tenant's own person (#1509) is always a candidate. The proposed meeting of #1818, the manual assignment of #1770 and the re-asking of #1942 build on this issue.

Decisions:

- By the product owner: candidates are the participants of the transcript's Event (with a name) and the tenant's own person, even when the own person is not a participant. A person already mapped to another speaker key is excluded from the suggestion and from the alternatives, because the model cannot map one person to two keys.
- The model is called once for all unmapped speakers and only when there is at least one candidate. With no candidate the cards are created without a call, as `needsClarification` cards with empty alternatives.
- Quotes are chosen by code, not by the model: up to three of the speaker's segments with at least six words, the longest first, then shown in time order, each shortened to 140 characters. `firstStartsAt` is the start of the speaker's first segment. The reason is written by the model in the tenant user's UI language (`users.locale`).
- `context.alternatives[].title` is always `null`: by the product owner, no job-title property is added in v1. `invitationStatus` comes from the Event participant edge or is `null`.
- By the product owner: one person under two speaker keys is not supported; a person already mapped to a speaker is not offered for another key.
- A speaker card keeps its role for life; the role of a card without a stored envelope is read from `context.role`.
