## Context

The review follow-ups harvest (epic #565) runs daily and decides, for merged pull requests, which of the code-review bot's open findings go into the next harvest issue. Every one of those decisions is pure given the data, so this issue puts them in one module with no I/O, where each rule is tested directly. The harvest script (a later issue) fetches the data, calls these functions and writes the result.

It builds on:

- #569 `markers.mjs`: `LABELS`, `findingId({ pr, key })` → `"<pr>:<key>"`, and `computeLedger(issues)` → `{ harvested, terminal, harvestedPrs, epics }`;
- #570 `records.mjs`: the finding record and `validateFindingRecord`;
- #572 `memory.mjs`: `TRUSTED_REVIEW_BOT_LOGINS` (`github-actions[bot]`, `bb-agent-relay[bot]`) and `parseMemory`, whose findings are `{ key, path, line, severity, category, description, anchor, status, discussionId, firstSeenSha, lastSeenSha }`.

It also consumes review threads in the shape the GitHub access layer (a sibling issue in this batch) returns: `[{ isResolved, comments: [{ databaseId, author, body }] }]`, where the first comment is the thread's root and `author` is a REST-style login (`github-actions[bot]`).

The rules, as approved in the epic:

- **Backpressure.** A harvest writes nothing while any open issue carries `followups:harvest`, or carries both `followups:issue` and `spec:proposed`.
- **Candidates.** Pull requests merged into `develop` with number ≥ the fixed floor, without `followups:harvested`, in ascending number.
- **Findings.** Only `status: open`; never one whose `(pr, key)` is already in the ledger's `harvested` set.
- **Threads.** The bot opens an inline thread for medium and above, and its `discussion_id` is then the numeric id of the thread's root comment. The only deterministic skip is a resolved thread with a reply from a trusted bot whose body is exactly `Fixed.` — the bot's sole wording for a confirmed fix. Every other finding is harvested with `threadResolved` and up to the last three replies as excerpts.
- **Missing path.** Never a skip; recorded as `pathExists: false`.
- **Cap.** At most 30 harvested findings per harvest issue. A pull request is never split, pull requests are taken in order, the first one with harvested findings is always taken whatever its count, and taking stops before the one that would exceed the cap.
- **Crash safety.** A pull request already listed in a harvest issue's harvest marker (the ledger's `harvestedPrs`) is only labelled, never harvested again.

## Task

Create `.github/scripts/review-followups/select.mjs`, a zero-dependency ES module with no I/O, with a header comment stating the rules above, exporting:

1. `HARVEST_CAP = 30`.
2. `pendingWork(openIssues)` — input `[{ number, labels: string[] }]`; returns the ascending numbers of the issues that hold back a harvest under the backpressure rule (an empty array means "go").
3. `candidatePullRequests(pullRequests, { minPr })` — input `[{ number, mergedAt, labels }]`; returns those with `number >= minPr` and without `followups:harvested`, ascending by number.
4. `classifyPullRequest({ pr, memoryFindings, threads, treePaths, ledger })` — `memoryFindings` is `parseMemory(...).findings` or `null` when the pull request has no memory; `threads` is the review-thread array (may be empty); `treePaths` is a `Set` of paths on `develop`; `ledger` is `computeLedger`'s result. Returns `{ harvest, skipped }`:
   - it considers only findings with `status === "open"` whose `findingId` is not in `ledger.harvested`;
   - for a finding whose `discussionId` is all digits, the thread is the one whose first comment's `databaseId`, as a string, equals it;
   - **skipped**: that thread is resolved and one of its replies (every comment after the first) has an author in `TRUSTED_REVIEW_BOT_LOGINS` and a body that, trimmed, is exactly `Fixed.`. It is returned in `skipped` as `{ pr, key, path, line, category, description }`;
   - **harvested**, everything else, as a finding record without its two hint fields: `pr`, `key`, `severity`, `category`, `path`, `line`, `anchor`, `description` from the memory finding; `descriptionTruncated` — `description` ends with `…`; `discussionId` — the id when all digits, otherwise `""`; `threadResolved` — the matched thread's `isResolved`, `false` without a matched thread; `replies` — the last three replies of the matched thread as `{ author, excerpt }`, where `excerpt` is the reply body's first 200 characters, `[]` without a matched thread; `pathExists` — `treePaths.has(path)`; `firstSeenSha`, `lastSeenSha` from the memory finding;
   - both lists keep the memory's order; `memoryFindings === null` returns two empty lists.
5. `createHarvestPlan({ cap = HARVEST_CAP } = {})` returning `{ offer(result), plan() }`. `offer` takes `{ pr, alreadyRecorded: boolean, harvest, skipped }` (pull requests offered in ascending order) and returns `"take"` or `"stop"`:
   - `alreadyRecorded` → `"take"`, recorded as label-only (its findings are ignored);
   - no harvested findings → `"take"` (its skipped findings are kept);
   - no harvested findings taken so far → `"take"`, whatever its count;
   - the running total plus its count would exceed `cap` → `"stop"`, and every later `offer` returns `"stop"` without changing anything;
   - otherwise `"take"`.

   `plan()` returns `{ prs, labelOnly, harvest, skipped, stoppedAt }`: `prs` — ascending numbers of the taken pull requests that were not label-only; `labelOnly` — ascending numbers of the label-only ones; `harvest` and `skipped` — the concatenated findings in offer order; `stoppedAt` — the number of the first pull request refused, or `null`.
6. `select.test.mjs` next to it (`node:test`, `node:assert/strict`) covering every Acceptance criterion below.

## Scope

### In scope

- The five exports above and their tests.

### Out of scope

- Fetching anything, computing the hint fields `touchedAfterLastSeen` / `laterPrsTouchingPath`, rendering the harvest issue, and labelling — later issues in this batch.
- Any skip other than the exact `Fixed.` rule: resolved threads without it, human replies and missing paths are all harvested by design.

## Acceptance criteria

1. `pendingWork` returns an open `followups:harvest` issue, and an issue with both `followups:issue` and `spec:proposed`; it does not return an issue with `followups:issue` alone (an epic or an approved issue) or with `spec:proposed` alone.
2. `candidatePullRequests` drops a pull request below `minPr` and one labelled `followups:harvested`, keeps a pull request at exactly `minPr`, and sorts ascending.
3. `classifyPullRequest` ignores findings with status `resolved`, `wontfix` or `fixed`, and an open finding whose `findingId` is in `ledger.harvested`.
4. A resolved thread with a `github-actions[bot]` reply `Fixed.` (and with a `bb-agent-relay[bot]` reply ` Fixed. ` padded with whitespace) makes the finding `skipped`.
5. Each of these is **harvested** with `threadResolved: true`: a resolved thread with no reply; one whose only reply is a human's `Fixed.`; one whose trusted-bot reply is `Fixed. Thanks`; one whose reply is `will do in a follow-up`. An unresolved thread with a trusted `Fixed.` reply is harvested with `threadResolved: false`.
6. `replies` holds the last three of five replies, in order, each excerpt cut to 200 characters; a finding with `discussionId` `issue:123` or `""`, or whose thread is not found, gets `discussionId: ""` (for the non-numeric ones), `threadResolved: false` and `replies: []`.
7. `pathExists` is `false` for a path absent from `treePaths`, and the finding is still harvested; `descriptionTruncated` is `true` exactly when the description ends with `…`.
8. With `cap` 30: offering pull requests with 12, 15 and 5 harvested findings takes the first two and stops at the third (`stoppedAt` is its number); a first pull request with 31 findings is taken; after a stop, a pull request with 0 findings also gets `"stop"`.
9. A pull request with only skipped findings, or with nothing, is taken without counting towards the cap and appears in `prs`; an `alreadyRecorded` one appears in `labelOnly` only, and its findings are not in `harvest`.
10. Every harvested entry, with `touchedAfterLastSeen: null` and `laterPrsTouchingPath: 0` added, passes `validateFindingRecord` from #570.
11. `node --test .github/scripts/review-followups/select.test.mjs` passes with no network access.
