### Requirement gh-1476: [inbox-proposals 04/19] Write proposal relations atomically on confirm

#### Context

Model tier rationale: Extends the existing atomic confirm with a loop of edge writes following the transcript-card precedent in the same transaction, with existing fixtures, so mainly rollback behavior needs care.

A confirmed Inbox proposal today creates one item (`confirmProposalWithClient` in `backend/packages/data/src/inbox/proposalActions.ts` calls `createItemWithClient` with the envelope's `properties` only). #1426 lets a `database` envelope carry `relations` (`{ [relationPropertyKey]: targetItemId[] }`) and validates them while the card is built or edited, but confirm ignores them, so a confirmed task would be created without its project. A transcript card already shows the needed pattern: its confirm creates an Event and then the Transcripts-to-Event edge through `createRelationWithClient` in the same transaction.

This issue makes confirm write the item and all of its edges as one unit.

Decision: the edges are written after the item is created, in the order of the keys and ids in the envelope, each through `createRelationWithClient` with the new item as caller; a failure of any single edge aborts the whole transaction (no item, no edges, the card still `proposed`) and surfaces the edge's own canonical error with `details.field` set to the relation key. Targets are validated again by the write itself (existence, archived databases, ownership, cardinality), which is the full check; the pre-checks of #1426 are advisory.

2. An empty `relations` or none at all behaves exactly as before. The idempotent early return for an already `confirmed` proposal is unchanged and writes no edges again.
3. Tests: a task proposal with `relations: { project: [<id>] }` confirms into a task plus the project edge in one transaction; a nonexistent target id gives 400 with `field` `project` and no task exists afterwards; a cardinality violation on the second relation rolls back the item and the first edge; a repeated confirm does not duplicate edges; a transcript card confirm is unchanged.

### Requirement gh-1486: [inbox-proposals 06/19] Confirm multi-step proposals atomically

#### Context

Model tier rationale: Atomic multi-write confirmation must preserve rollback, stale-state guards, idempotency and acting-user semantics.

Confirm already locks the card and is transactional/idempotent; #1476 adds relations and #1479 validates multi-step envelopes. This issue executes their active steps atomically.

Decision: active steps are executed in dependency order (a step before every step that refers to its `ref`); skipped steps (disabled, or optional and unreferenced) are neither validated again nor written. `create` writes the item through `createItemWithClient` and its relations through `createRelationWithClient`; targets given as `{ ref }` use the id of the item created by that step. `link` writes the declared edges between existing items. `update` moves an existing item's "one"-side relation: `deleteRelationWithClient` of the old edge (`before`) and `createRelationWithClient` of the new one (`after`) in the same transaction. The `properties` of an `update` step are written with `updateItemWithClient` as the acting user, so the choke point applies the same validation, approval and risk rules as to any other item update (decided by the product owner; a project's status is not a special case). Any failure rolls the whole transaction back, leaves the card `proposed` and returns 400 with `details: { ref, field }`. `resultItemId` and `resultLabel` are those of the primary step; the response is the card as before. Per-step results are reported by #1648 and are not stored here.

Decision: confirm now passes the acting user (`actingUserId`) to the item writes so realtime notifications go only to that user, and the writes are made as that user. The route handler (`createConfirmProposalRouteHandler` in `inboxRouteHandlers.ts`) supplies the id from the authenticated identity; callers without a user (tests, internal) pass none, which keeps today's behavior. Product policy: confirmed blocks will be user-authored under #1681 (including legacy pageContent) and #1981 (journalEntry), with #1648 block ids.
