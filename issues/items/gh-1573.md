## Context

Model tier rationale: This adds a persisted-data contract (a new system database, new `mail_threads` columns, a per-tenant cutover with a batched backfill) and changes the thread merge path that moves edges between items, so a mistake corrupts existing tenant data.

Mail threading stores id/subject_hint in mail_threads through mailMessageMetaStore and threading.ts. This adds a mail-owned Threads system database and item identity, with user-owned project/company values, so threads can support the stated relations and filters.

Facts that shape the design:

- The databases of the ten-database seed are `schema_locked` before `seed/seedEmailModule.ts` runs, and `createProperty` rejects a locked database (`chokePoint/propertiesStore.ts`). So the new relations live on the Threads side and are one-directional, exactly like `Emails.attachments` and `Files.area`.
- An existing tenant receives schema changes only through a per-tenant cutover (`db/tenantCutoverMigrations.ts`; the pattern is `transcription/transcriptsCatalogCutoverMigration.ts`).
- A generic `relation.put` goes through the choke point and not through a module writer, so "at most one project per thread" must be a relation-edge write hook (`registerRelationEdgeWriteHook`, the pattern is `transcriptSpeakerEdgeWriteHook` in `transcription/transcriptionSpeakerEdges.ts`, registered in `domainWriteHooks.ts`). A relation-edge hook runs before an edge write, also in dry runs, and not on delete.

Decisions: the public thread id stays `mail_threads.id` everywhere (API, related counts); the new `mail_threads.item_id` is internal and must never be exposed. The item `name` is the subject of the first message and is not renamed later. Threads.project and Threads.company are `owner: user` because users and Semp write them through the generic `relation.put`.

This issue builds on #1493 (merged thread ids stay resolvable through an alias written when two threads merge). It is the foundation for #1869, #1872, #1638, #1874, #1612 and #1839.

Shared-file ordering: this issue also waits for #1530, #1552, #1572 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Structural merge, nil/nowait hook modes and lifecycle follow docs/adr/2026-11-05-mail-thread-item-merges-transfer-existing-relations.md and the batch28 reconciliation record.

All supported incident Threads relation mutations reserve their Threads endpoints through existing write/delete domain hooks, per docs/adr/2026-11-05-thread-relation-writers-reserve-thread-endpoints.md. This explicitly extends the earlier structural-merge writer boundary.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_mail_threads_items.sql (next free ordinal at commit time)`: add `mail_threads.item_id uuid` (nullable, unique per tenant where not null) and `mail_threads.created_at timestamptz NOT NULL DEFAULT now()`. Keep the existing tenant column, row-level security and composite key conventions of the table.
2. Seed (fresh installs): in `seed/seedEmailModule.ts` create the database Threads (module id `threads`, constant `THREADS_MODULE_ID` in `seed/emailModuleKeys.ts`) with a system-owned `name` title property and the relation properties `project` (to Projects) and `company` (to Companies), both `many_to_many`, `owner: user`, one-directional. Lock the database with the other three. Declare the database in `mail/mailModuleManifest.ts` (`databases`). Build the database in one shared function used by both the seed and the cutover so there is a single definition.
3. Ingest: change `createMailThread` so that, in the same transaction, it also creates the Threads item (name = subject hint or "(no subject)") through `createItemWithClient` and stores `item_id`; `created_at` is the creation time.
4. Cutover for existing tenants: `mail/threadsDatabaseCutoverMigration.ts` exporting `runThreadsDatabaseCutoverMigration(pool)`, registered in `db/tenantCutoverMigrations.ts`. It returns when the Emails database does not exist; creates the Threads database and relations if missing; then backfills every thread without `item_id` in batches of 200 per transaction (item per thread; `created_at` = the earliest `date` of the thread's Emails, else keep the default). Running it again changes nothing.
5. Relation-edge hook `mail/threadValueEdges.ts`, registered in `domainWriteHooks.ts`: adding an edge on Threads.project or Threads.company when the thread already has an edge to a different item is rejected with `validation_failed` on that property; re-adding the same target is accepted. Reserve all incident Threads endpoints through the existing write/delete hooks, including incoming/new-definition edges, and recheck their state after acquiring the item locks; project/company retain the single-value rule.
6. Merge: in `reassignThread` (same transaction, next to the alias written by #1493), soft-delete the losing Threads item and move its edges to the winner: for Threads.project and Threads.company take the loser's value only when the winner has none; for every other relation property of Threads (the later tasks and attachments relations) move all edges, skipping duplicates. The winner keeps its own item; then the `mail_threads` row of the loser is deleted as today. The finer "own value beats inherited value" rule is added by #1869.

## Scope

### In scope

- The Threads database, the two relations, `item_id` and `created_at`, the single-value hook, the cutover with backfill, and the merge handling.

### Out of scope

- Inheriting company and project from the sender and the own-over-inherited merge rule (#1869); assigning a project by Semp (#1872).
- The Threads.attachments and Threads.tasks relations (#1898, #1612); the generic merge in step 6 already moves their edges once they exist.
- Rejecting or translating a message ref that points at a Threads item (ref validation, #1682); no API returns `item_id`.
- Exposing company and project in thread responses (#1897).

## Acceptance criteria

- When a new thread is created by ingest, a Threads item with the same subject exists in the same transaction and `mail_threads.item_id` points at it.
- After the cutover runs for a tenant that had threads, every thread has an item and `created_at` equals its earliest message date; running the cutover a second time changes nothing and works on a fresh install without error.
- When a generic `relation.put` sets Threads.project, it is stored; a `relation.put` of a second, different project is rejected with `validation_failed`.
- When two threads merge, exactly one Threads item stays undeleted, it carries the project and company (the winner's own, else the loser's), and the old thread id still resolves to the new thread.
