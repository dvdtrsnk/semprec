**Model tier:** medium

## Context

Model tier rationale: One bounded addition to the proposal computation input using existing catalog and facet reads, but it determines what the model is told and what health data may enter a prompt, so the grant behavior needs care.

When the assistant turns an Inbox note ("at the doctor: blood pressure 135/85, measure for two weeks") into a proposed health record, it must pick values the database actually knows: the Type, the Status, the Tags, and a person for "Who" (David, Heduš, Max (dog)). Today the proposal computation (#1434) is given the capture time, time zone and a bounded workspace context (#1987) but not the option lists of the target database or the values already used in its free-text fields. A model that does not know them invents keys, and an invented key is only caught afterwards (#1814).

This issue gives the computation, for whichever database it proposes into, the catalog of that database: for every `select` and `multi_select` property the allowed option keys with labels in the user's language, and for the text properties the values already in use with their counts, read through `database.facets` (#1759). The output is still only validated keys. It builds on the new health tags (#1700) because Blood pressure must be offered, and on the unknown-key check (#1814), which catches what slips through. #1994 extends it to proposing new options.

Decisions:
- The catalog applies to every target database, not only Health records.
- Option labels use the requesting user's `users.locale` (Czech or English) with the stored key beside each label; the model must answer with keys only.
- Text values: for each user-owned `text` property other than the title, up to 20 distinct values with counts, for at most 5 properties per database. They are read as the same actor and under the same grants as the workspace context of #1987; when the read is not permitted, no values are included and the options (schema, not data) still are.
- The proposed date is the capture day given by #1987; this issue does not change it.

## Task

Load `ai-gateway`, `io-hardening` and `testing`.

1. Add `backend/packages/data/src/inbox/proposalTargetCatalog.ts` exporting `buildTargetCatalog(client, databaseId, locale)` returning `{ selects: [{ propertyKey, multi, options: [{ key, label }] }], textValues: [{ propertyKey, values: [{ value, count }] }] }`, with options resolved through the module catalog (`resolveCatalogLabel` in `@semprec/module-registry`) and text values from the facets read, bounded as above and never containing a title.
2. Include the result in the input the computation of #1434/#1987 builds for the target database (the prompt assembly module those issues created; name it in the pull request), as a clearly delimited block, and extend the prompt instructions to say that select values must be option keys from the list and text values should reuse a listed value when it fits.
3. Tests with a stubbed gateway: the request for a Health records target carries `type`, `status` and `tags` with Czech labels (including Krevní tlak) and `subject` values David 3, Heduš 1, Max (pes) 1; an English user gets English labels; a target database with no selects adds no block; a read denied for text values still sends the options; a stubbed answer with `tags: ["bloodPressure"]` produces a normal proposal and `tags: ["neznamy"]` a `needsClarification` card via #1814.

## Scope

### In scope

- The per-target catalog of options and known text values, its inclusion in the proposal computation input and prompt, and tests.

### Out of scope

- The computation, the registration of the tick and the capture-time context: #1434 and #1987.
- Computing relations and multi-step operations: #1488 and #1492.
- The facets operation: #1759.
- Rejecting invalid keys: #1814.
- Proposing options that do not exist yet: #1994.

## Acceptance criteria

- When a proposal is computed for Health records, then the gateway request carries the `type`, `status` and `tags` options with labels in the user's language and the `subject` values with counts.
- When the user's locale is English, then the labels are English.
- When reading text values is not permitted, then the request still carries the option lists and no text values.
- When the stubbed answer uses a valid key, then a normal proposal is stored; when it uses an unknown key, then the card is `needsClarification`.
