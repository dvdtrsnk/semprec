## Context

Model tier rationale: One seeded system item, one locked marker property and an idempotent per-tenant cutover follow the existing system-project and cutover patterns, but the cutover writes data into every maintained tenant and must stay idempotent under concurrent runs, which keeps it above low.

The seed creates no areas (`seedTenDatabasesInTransaction` in `backend/packages/data/src/seed/seedTenDatabases.ts` creates the Areas database with `name`, `active` and `note`; #1515, #1554 and #1556 extend it). Statistics need one system area that collects unplanned items and that they leave out of their own figures. Every other area is created by the user; no further default areas are seeded.

The Projects database already marks its system projects with the locked checkbox `systemActive` (`seedTenDatabases.ts`), seeded `true` by `seedSystem.ts` and the module seeds. The item delete paths refuse an item whose `systemActive` is `true` regardless of its database (`itemDeleteWithClient` in `chokePoint/itemTrash.ts`, the `item.delete` case in `chokePoint/destructiveProjection.ts`), and reads exclude system projects with the filter `is_empty systemActive`. This issue reuses the same key on Areas so the system area is protected and filtered the same way.

The Areas database is schema-locked after seeding, so existing tenants get the property and the area through the per-tenant cutover in `backend/packages/data/src/db/tenantCutoverMigrations.ts` (`runTenantCutoverMigrations`, every maintained tenant including suspended ones, under row-level security; pattern `transcription/transcriptsCatalogCutoverMigration.ts`: one transaction, `LOCK TABLE properties IN EXCLUSIVE MODE`, an idempotency check, then the writes).

Decisions:
- Exactly one system area per tenant: `name` from the i18n key `seed.areas.unplanned.name` resolved from the Czech catalog, which is the product default ("(neplánováno)" in `cs.json`, "(unplanned)" in `en.json`), `systemActive: true`, `active: true`.
- The system area is identified by `systemActive: true`, never by its name, so a rename does not break statistics.
- No other areas are created for new or existing tenants.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Add property `systemActive` (type `checkbox`, `owner: 'user'`, `locked: true`, the same declaration as on Projects) to the Areas database in `seedTenDatabases.ts`, with i18n key `property.areas.systemActive.name` ("Systémově aktivní" in `cs.json`, "System active" in `en.json`).
2. Add `backend/packages/data/src/seed/seedUnplannedArea.ts` exporting `ensureUnplannedArea(client, areasDatabaseId)`: when no live area with `systemActive: true` exists, insert one with the values from Decisions through `itemsStore.insertItem`; otherwise do nothing. Take `pg_advisory_xact_lock` keyed by the Areas database id first so two concurrent calls create one area. Call it from `seedTenDatabasesInTransaction` after the Areas database and its properties exist.
3. Add a cutover step (new `backend/packages/data/src/seed/areasUnplannedCutoverMigration.ts`, registered in `runTenantCutoverMigrations`) that, for each maintained tenant with an Areas database, adds the `systemActive` property when missing under `LOCK TABLE properties IN EXCLUSIVE MODE` and then calls `ensureUnplannedArea`. A tenant without an Areas database is a no-op; a second run changes nothing.
4. Add i18n key `seed.areas.unplanned.name` to `seed/i18n/cs.json` and `en.json`, and bump the `version` of `seed/systemDatabasesModuleManifest.ts` (update the tests that assert it).
5. Tests: the acceptance criteria below.

## Scope

### In scope

- The `systemActive` property on Areas, the one system area for new and existing tenants (suspended ones included), its labels, the idempotent cutover and tests.

### Out of scope

- Seeding any other area: the user creates them.
- Excluding the system area from a particular statistic or count: each statistic applies `is_empty systemActive` on Areas in its own issue.
- Icon, color and position of areas: #1515. Defaulting `active`: #1554.
- Hiding the system area from area lists or pickers.

## Acceptance criteria

- When a new tenant is seeded, then its Areas database holds exactly one area with `systemActive: true` and the name "(neplánováno)", and no other area.
- After the cutover, a tenant created before this change (including a suspended one) has the `systemActive` property on Areas and exactly one system area; running the cutover again, or twice concurrently, still leaves exactly one.
- When the system area is deleted through `DELETE /api/items/:id`, `/mcp` or an agent tool, then the answer is 403 with `field: "systemActive"` and the area stays live.
- When the system area is renamed, then it is still the only area with `systemActive: true`, and a later cutover run creates no second one.
- `database.query` on Areas with the filter `is_empty systemActive` returns the user's areas without the system area.
- The full backend `pnpm run verify` passes.
