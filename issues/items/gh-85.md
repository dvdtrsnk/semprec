## Task

Register action id `core.agentGuidanceDrift`. A qualifying project is exactly a Projects item with a `project_agent_guidance` row. Add partial unique index `project_heartbeats_guidance_drift_unique ON project_heartbeats(project_item_id, action_id) WHERE action_id = 'core.agentGuidanceDrift'`. Before creating it, the migration locks matching rows per project, keeps the lowest-id row, sets its rule to `{ kind: 'dailyTime', at: '04:30' }` and enabled=true, and deletes other matching rows; projects without one are inserted with `ON CONFLICT` against that identity. Creating/updating guidance and install backfill use the same upsert. Exactly one enabled heartbeat therefore survives concurrent/repeated installation and writes. The action loads `loadProjectAgentGuidance(projectItemId).markdown`, the locale of that same row's current `ownerUserId`, and the freshly generated permission manifest for the same project/locale. It calls `semprec-ai-gateway.complete()` (through the `AiGatewayClientPort` from #215) with budget attribution `{ projectItemId, operation: 'agent_guidance_drift' }`, temperature 0, the fixed system instruction `Compare project guidance with mechanically enforced manifest facts. Return only schema-valid contradictions; do not infer permissions absent from the manifest.`, and one user message containing two delimiter-labelled verbatim blocks `GUIDANCE` and `PERMISSION_MANIFEST`. Use the gateway's configured structured-output model; this issue introduces no model id or provider override. Validate output as `{ contradictions: Array<{ claim: string; guidanceExcerpt: string; manifestFacts: string[]; severity: 'blocking' | 'warning' }> }` with non-empty fields.

Add `agent_guidance_drift_findings(id uuid primary key, project_item_id uuid not null, fingerprint text not null, payload jsonb not null, status text not null check (status in ('active','resolved')), first_seen_at timestamptz not null, last_seen_at timestamptz not null, resolved_at timestamptz, unique(project_item_id, fingerprint))`. Fingerprint each contradiction with the self-contained algorithm below; sort returned contradictions by fingerprint before writes. Upsert active findings and resolve formerly active fingerprints absent from a successful comparison.

Fingerprint algorithm (implement it once in shared code; no external canonicalization specification or library is implementer truth): sort `manifestFacts` by ascending Unicode code point, then recursively serialize `{ claim, guidanceExcerpt, manifestFacts, severity }` with JSON primitives using standard JSON escaping, arrays in their normalized order, and object keys in ascending Unicode code-point order, with no whitespace; reject non-finite numbers. Hash the UTF-8 bytes with SHA-256 and output lowercase hexadecimal.

Add `notifications.payload jsonb not null default '{}'::jsonb` and extend #36's kind catalog with `agent_guidance_drift` and `agent_guidance_drift_resolved`. Export `createNotification(tx, input)` from `packages/notifications/src/createNotification.ts`, where `tx` is the caller's open database transaction and `input` is `{ userId, kind, title, linkHref, sourceTable, sourceId, payload }`; it inserts the notification and enqueues #36's fanout job in that same transaction, returning the notification id. Both finding transitions call this writer with `userId = project_agent_guidance.owner_user_id`; if the guidance row disappeared before execution, fail the action without changing finding state or creating a notification. Resolve titles via #35's locale resolver using keys `notification.agentGuidanceDrift.title` and `notification.agentGuidanceDriftResolved.title`, shipping Czech and English values in the core module catalogs; English fallbacks are `Agent guidance conflicts with permissions` and `Agent guidance conflict resolved`. Use `linkHref = /projects/{projectItemId}/agent-guidance`, `sourceTable = agent_guidance_drift_findings`, and `sourceId = findingId`. Active payload is `{ projectItemId, fingerprint, claim, guidanceExcerpt, manifestFacts, severity }`; resolved payload is `{ projectItemId, fingerprint }`. Gateway/validation failure changes no finding state and is thrown.

Define `GuidanceDriftFindingStore<Tx>` in shared with transaction-scoped `listActive(tx, projectItemId): Promise<Finding[]>`, `upsertActive(tx, finding): Promise<{ finding: Finding; transitionedToActive: boolean }>`, and `resolve(tx, findingId, resolvedAt): Promise<{ finding: Finding; transitionedToResolved: boolean }>`; returned `finding.id` is the notification source id. Only insert or resolved-to-active returns `transitionedToActive=true` and emits an active notification; only an active-to-resolved change returns `transitionedToResolved=true` and emits a resolved notification. Repeated active observations only update `last_seen_at`. Define `GuidanceNotificationWriter<Tx>.create(tx, input)` in shared. `packages/data` implements the finding store; `packages/notifications` adapts `createNotification` to the writer port. Define the manifest dependency exactly as generic `GuidanceManifestPort<Tx> = { render(tx: Tx, input: { projectItemId: string; userId: string; locale: string }): Promise<string> }`. `createAgentGuidanceDriftAction<Tx>({ transactions, guidance, references, findings, notifications, manifest, gateway, clock })` lives in `packages/application/src/projectAgentGuidance` (the placement rules of #214 apply) and is composed in `semprec-api` from application/data/notification dependencies; `references.requireUserLocale` (defined in #214) is the only locale lookup used by the action.

The action uses two transactions around the non-transactional gateway call, both opened with `transactions.withTransaction({ isolation: 'repeatable_read' }, ...)` on the port defined in #214. The pre-gateway read transaction loads one consistent `{ projectItemId, ownerUserId, guidanceUpdatedAt, markdown, locale, permissionManifest }`: guidance supplies owner/revision, `requireUserLocale` supplies that owner's locale, and the manifest port renders for the same project/user/locale before commit, receiving that transaction's own `tx` so the data-backed generator reads the identical database snapshot as guidance, owner, and locale. Capture `permissionManifest` as the exact rendered string. After validated gateway output, the write transaction reloads guidance and requires both `owner_user_id` and `updated_at` to equal the captured revision before any finding/notification write. A mismatch throws retryable `guidance_changed` and writes no transitions or notifications; the retry repeats the entire read/compare flow. After the guidance owner/revision check and before any write, call `manifest.render(tx, { projectItemId, userId: ownerUserId, locale })` again in the same write transaction and require byte-for-byte equality with the captured string; a mismatch throws retryable `guidance_context_changed`, rolls back, and retries the entire comparison, never transitioning findings or writing notifications. Only after both checks does it resolve the same current owner's locale again for notification titles and atomically persist findings/fanout. Gateway failure occurs before the write transaction and changes no state. Tests mutate a permission grant/schema input during the gateway call and prove stale output is discarded. A concurrency test mutates guidance/locale/manifest inputs between individual phase-one reads and proves the gateway receives one coherent snapshot, never a READ COMMITTED mixture.

Replace the no-op `GuidanceHeartbeatStore` injected in #214 with the concrete `packages/data` implementation. `GuidanceHeartbeatStore.upsertDriftHeartbeat` persists the exact values `name = 'Detect agent guidance drift'`, `rule = { kind: 'dailyTime', at: '04:30' }`, `action_id = 'core.agentGuidanceDrift'`, `action_config = {}`, and `enabled = true`. It reads the canonical System Settings timezone in the supplied transaction and sets `next_fire_at` using the existing scheduler `computeNextFireAt(rule, transaction_timestamp, timezone)` helper. On conflict it updates name/rule/action_config/enabled and recomputes `next_fire_at` only when the stored rule, timezone-derived schedule, or enabled state differs; repeated unchanged upserts preserve an already-valid next occurrence. Duplicate reconciliation applies these same values to the retained lowest-id row.

## Acceptance criteria

- A statement claiming permission for a mechanically forbidden action creates one `agent_guidance_drift` notification and active finding.
- Repeated identical findings do not create notification spam.
- Removing the contradiction resolves the active finding on the next successful check.
- Gateway errors or malformed output are observable as check failures and are never treated as no drift.
- Repeated install/backfill produces exactly one enabled 04:30 daily heartbeat for every existing and new qualifying project.
- `loadProjectAgentGuidance` is the only hand-written guidance projection used by both the system prompt and drift action; generated AGENT.md content is never compared as guidance.
- Active/resolved transitions use `createNotification` with `project_agent_guidance.owner_user_id`, title, link, source, persisted payload, and transactional fanout.
- A missing guidance/owner row fails the action and writes neither finding transitions nor notifications.
- Reordering otherwise identical gateway object keys, contradiction rows, or `manifestFacts` does not change fingerprints or create duplicate findings.
- Concurrent install/guidance writes reconcile to the one indexed drift heartbeat, and the composed action atomically persists findings plus notifications through injected transaction-scoped ports.
- Guidance transfer/update during the gateway call fails the revision check with `guidance_changed`; stale comparison output never changes findings or notifies a different owner.
- Permission-manifest change during the gateway call fails with `guidance_context_changed`; stale output writes nothing.
- Drift-heartbeat insert, conflict update, duplicate reconciliation, and timezone scheduling persist the exact canonical fields above.
- Both comparison phases use PostgreSQL REPEATABLE READ, and the drift request traverses the #215 `/internal/complete` route with `{ projectItemId, operation: 'agent_guidance_drift' }` attribution.
