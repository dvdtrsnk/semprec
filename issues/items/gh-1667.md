**Blocked by:** #1665
**Model tier:** medium

## Context

Model tier rationale: One new endpoint that applies a patch to a stored template and to a bounded set of open items, using the series storage and write paths that already exist.

A recurring task detail screen has to separate two kinds of edit. Changing the time, the name or another field of a recurring task edits the whole series, including future occurrences. Dragging one occurrence or ticking it done affects only that occurrence (that is #1720). Today a task and its recurrence row are updated only through the generic item PATCH, which changes the single instance and never the following ones, because instances share nothing.

#1605 stores a `template` (`name`, `timeFrom`, `timeTo`, `notifications`, `persistent`, `flagged`, `description`) on the one `task_recurrence` row per series and gives each instance a `seriesId`. The advance logic and the projection of virtual occurrences (#1672) take their properties from that template. This issue adds the endpoint that edits the template together with the current open instance.

Decision: occurrences that were already materialized and are still open (status `notDone`) and dated on or after the current open instance are updated with the series change, because the product shows them as part of the series; done, wontDo and missed occurrences are never rewritten, and fields that are specific to one occurrence (`date`, `occurrenceDate`, `status`, `completedOn`) are never part of a series change. An occurrence that was moved on its own (#1720) keeps its date: its date is its own value and a series edit never moves it (decided by the product owner).

Shared-file ordering: this issue also waits for #1665 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Add `PATCH /api/tasks/series/:seriesId` accepting any subset of the template fields `{name, timeFrom, timeTo, notifications, persistent, flagged, description}`, with the same validation the item write applies to those properties. An unknown field, or a field belonging to a single occurrence, gets 400. An unknown or foreign `seriesId` gets the same not-found response.
2. In one transaction, lock the current instance, then the `task_recurrence` row `FOR UPDATE`, merge the patch into `template`, and apply the same patch to the current open instance and to the open materialized occurrences described in the Context decision, through the Tasks write path (not by direct SQL on `items`). Past occurrences stay unchanged.
3. Respond with the series (`seriesId`, `template`, `recurrence`, current instance id).
4. Register the route in `customRoutes` of the `systemDatabases` manifest (single-writer ownership ADR `docs/adr/2026-09-10-single-writer-ownership-model.md`), add it to `routeMatrix.ts` and the tenant isolation route test.

## Scope

### In scope

- The series patch endpoint, the template update and the propagation to the current and open materialized occurrences.

### Out of scope

- Moving, completing or editing one occurrence only: #1720.
- Setting or clearing the recurrence rule: #1665.
- Producing virtual occurrences from the template: #1672.
- Changing the series start date: it is handled by the date write of #1665.

## Acceptance criteria

- PATCH a series with `timeFrom: "08:00"` changes the template and the current open instance; an open materialized future occurrence also gets `08:00`.
- After that, a done occurrence in the same series keeps its old `timeFrom`.
- Afterwards, moving today's occurrence to 08:00 through the occurrence endpoint of #1720 does not change the template or the other occurrences.
- PATCH with `date` or `status` returns 400; PATCH of an unknown series returns not found.
