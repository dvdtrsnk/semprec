## Context

`getExpectedProcessNames` (`backend/packages/data/src/health/processHeartbeats.ts` lines 98-102) returns the four fixed process names plus `getActiveMailSyncProcessNames` (lines 92-96): one `mailsync:<item_id>` (`mailSyncProcessName`) per row of `mail_account_sync_state`. `getExpectedProcessHeartbeatStatuses` marks each expected name `present: false, stale: true` when no `process_heartbeats` row exists, and `checkProcessHeartbeats` (`observability/observabilityCheckSystem.ts` lines 42-56) raises a `process_stale` alert for it. `startProcessHeartbeat` is called from exactly four places — the `serve.ts` of api, agents, transcribe and ai-gateway — so no `mailsync:<id>` row is ever written. Today that is invisible only because no `mail_account_sync_state` row exists in production; #650 hosts `createMailLiveSyncRoot` (`backend/packages/data/src/mail/mailLiveSyncRoot.ts`) inside `semprec-api`, whose discovery pass seeds one row per active Mailbox item (`ensureMailAccountSyncState`, lines 134-137) — from that moment every connected mailbox is a permanent `process_stale` alert.

Two things must line up: the root must beat once per hosted account, and the expected set must be the hosted set. On the second point `getActiveMailSyncProcessNames` reads every `mail_account_sync_state` row, but the root hosts only mailboxes `listItems` returns (non-deleted); nothing deletes a sync-state row when a Mailbox item is soft-deleted, so a deleted mailbox would be expected forever after its lifecycle stopped. `mail_account_sync_state.item_id` is the Mailbox item's id (`0006_mail_sync.sql`).

## Task

1. In `mailLiveSyncRoot.ts`:
   - `HostedEntry` gains `heartbeat: ProcessHeartbeatHandle | null`.
   - In `reconcileOnce`, after `await lifecycle.start()` resolves (inside the `try`, not on the error path), start `startProcessHeartbeat(pool, { process: mailSyncProcessName(mailboxItemId), pid: process.pid, version: process.env.APP_VERSION ?? "0.0.0" }, { onError: (err) => options.onLifecycleError?.(mailboxItemId, "heartbeat", err) })` and store the handle on the entry; a lifecycle whose `start()` threw gets no heartbeat (so it goes stale and is alerted on — the intended signal). Add `"heartbeat"` to the `phase` union in `MailLiveSyncRootOptions.onLifecycleError`.
   - In `stopHosted`, call `entry.heartbeat?.stop()` before `lifecycle.stop()`. `stop()` on the root therefore stops every heartbeat; the rows go stale rather than being deleted, matching `startProcessHeartbeat`'s documented contract.
   - Update the root's docstring (lines 75-91): each hosted account beats its own `mailsync:<id>` process heartbeat for as long as it is hosted.
2. In `processHeartbeats.ts`, change `getActiveMailSyncProcessNames` to `SELECT s.item_id FROM mail_account_sync_state s JOIN items i ON i.id = s.item_id WHERE i.deleted_at IS NULL` and update its docstring: the expected set is exactly what the live-sync root hosts — active (non-deleted) mailboxes.
3. Tests:
   - `backend/packages/data/src/__tests__/mailLiveSyncRoot.test.ts` (existing, integration): after `start()` with one active mailbox, `process_heartbeats` has a row `mailsync:<itemId>` with `beat_at` within the last second; `getExpectedProcessHeartbeatStatuses` reports it `present`/not stale; after the mailbox is soft-deleted and `reconcileOnce()` runs, the account's `stop()` was called and no further beat is written (advance a short `intervalMs`, e.g. build the root with the existing fake factory and observe `beat_at` unchanged after 2× the interval); a lifecycle whose `start()` throws gets no heartbeat row; `onLifecycleError` receives phase `"heartbeat"` when the UPSERT fails (drop the table's INSERT privilege for the test role, or spy on `pool.query` to reject once).
   - `backend/packages/data/src/__tests__/processHeartbeats.test.ts` (existing): `getExpectedProcessNames` includes `mailsync:<id>` for a sync-state row whose Mailbox item is active and excludes one whose item has `deleted_at` set.

## Scope

### In scope
- Per-account heartbeats in the live-sync root, the expected-set query, and the tests.

### Out of scope
- Hosting the root in `semprec-api` and its shutdown step (#650).
- Deleting `mail_account_sync_state` rows for deleted mailboxes (the check now ignores them).
- Heartbeat interval or staleness thresholds (`PROCESS_HEARTBEAT_INTERVAL_MS`, `PROCESS_HEARTBEAT_STALE_AFTER_MS`).

## Acceptance criteria

- When the live-sync root hosts a mailbox, `process_heartbeats` gains a `mailsync:<mailboxItemId>` row that is re-upserted every `PROCESS_HEARTBEAT_INTERVAL_MS`, and `checkProcessHeartbeats` reports no `process_stale` for it.
- When that mailbox is soft-deleted, its heartbeat stops and it is no longer in the expected set, so no alert is raised for it.
- When a hosted lifecycle's `start()` throws, no heartbeat is started for that account and the existing alert path reports it stale.
