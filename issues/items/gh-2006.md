**Model tier:** high

## Context

Model tier rationale: Attacker-controlled inbound mail changes a stored invitation and moves a user's Event to the trash, so the sender check, the per-`UID` serialization and the idempotency must be exact; a mistake lets a forged message remove meetings from the calendar.

#1929 reads the calendar parts of every new Emails item in the `calendar.ingestInvitation` heartbeat action (`backend/packages/data/src/calendar/invitationIngestAction.ts`) and creates or updates an invitation for `METHOD:REQUEST`; it leaves `METHOD:CANCEL` untouched. #1901 gives the invitation `status` the option `cancelled`. #1944 creates the Event of an accepted or tentative invitation and links it through the invitation's `event` relation, and refuses to answer a `cancelled` invitation. #1954 writes the invitation's notification and resolves it when the user answers; the `pendingInvites` badge counts only `pending` invitations.

When the organizer cancels the meeting, an invitation that stays as it is would leave an invalid meeting in the calendar. This issue applies the organizer's `CANCEL`: the invitation becomes `cancelled` and its Event goes to the trash, where the user can restore it.

Decision (product owner): a `CANCEL` from the organizer moves the Event created from the invitation to the trash (restorable, never deleted permanently) and marks the invitation `cancelled`.

Decision: a `CANCEL` is applied only when the message's own sender address (`mail_message_meta.envelope.from`) equals the invitation's `organizerEmail` (case-insensitive), the same sender rule #1950 uses for replies; SPF/DKIM is not checked. A `CANCEL` whose `SEQUENCE` is lower than the stored `sequence` is stale and ignored.

Decision: the user's answer (`respondedAt`) is kept for the record; only `status` changes. Cancelling sends nothing to anybody.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. In `createInvitationIngestAction` (`backend/packages/data/src/calendar/invitationIngestAction.ts`), handle `METHOD:CANCEL` for the first `VEVENT` without `RECURRENCE-ID`, in the same per-email transaction and under the same transaction-scoped advisory lock on the `UID` hash that `REQUEST` uses:
   - look up the invitation with that `uid` through the choke point's read path; when there is none, do nothing;
   - check the sender rule above and the `SEQUENCE` rule; on a mismatch do nothing and log the email item id with a reason code;
   - when `status` is already `cancelled`, do nothing;
   - otherwise write `status` `cancelled` and the `CANCEL`'s `sequence` as the calendar module's system owner process; when the invitation has a live linked Event, move it to the trash through the existing trash path (`chokePoint/itemTrash.ts`); resolve the invitation's notification with the same resolve call #1954 uses in the respond transaction (matching `source_table = 'items'` and `source_id` = the invitation id).
   A failure in any step rolls the whole email's transaction back; the action never throws for a malformed or unmatched message. Logs never carry the invitation content.
2. Tests (in `backend/packages/data/src/calendar/__tests__`): a `CANCEL` from the organizer's address for a pending invitation sets `cancelled` and its notification is resolved; for an accepted invitation it also trashes the linked Event, and restoring that Event from the trash works; a `CANCEL` from another sender, for an unknown `UID`, or with a lower `SEQUENCE` changes nothing; a second processing of the same email is a no-op; `pendingInvites` no longer counts a cancelled invitation; answering a cancelled invitation through the respond route stays 409; a `REQUEST` with a higher `SEQUENCE` for a cancelled invitation changes nothing.

## Scope

### In scope

- Applying an organizer's `CANCEL` to an incoming invitation: the `cancelled` status, trashing its Event, resolving its notification.

### Out of scope

- The `cancelled` status option itself: #1901. Refusing to answer a cancelled invitation: #1944.
- Cancellations of meetings the user organizes (outgoing `CANCEL`): #1774.
- Recurring invitations and cancelling a single occurrence (`RECURRENCE-ID`): not in v1.
- Any message to the organizer or to other participants.

## Acceptance criteria

- Given a pending invitation "Sprint review" from petr@novak-web.cz, when an email from petr@novak-web.cz with `METHOD:CANCEL` for its `UID` arrives, then the invitation's status is `cancelled`, its notification is resolved and `pendingInvites` drops by one.
- Given an accepted invitation with a linked Event, when the organizer's `CANCEL` arrives, then the invitation is `cancelled` and the Event is in the trash, not deleted; restoring the Event brings it back.
- When a `CANCEL` for that `UID` comes from a different sender address, or carries a lower `SEQUENCE` than stored, then nothing changes.
- When the same `CANCEL` email is processed twice, then the second run changes nothing.
- When the respond route is called for a cancelled invitation, then it answers 409 `conflict`.
