## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: AGENT.md project instructions and drift detection (job agent-md-1)

#### Adopted decisions

- Where do the seed texts for new accounts come from once the `agents` property is removed? -> The five seed texts move into one exported constant map (keyed by seeded project name) that seeds, the cutover and account creation all use. Reason: the tenant zero seed runs before any user exists, and the property disappears in the last issue of the chain.
- Which rows does the cutover skip? -> Tenants without a user, and converted documents above 32 KiB (warning log with ids only). Reason: owner is NOT NULL; the size limit is a hard contract.
- How is legacy text split? -> Line-start markers `Purpose:`, `Allowed:`, `Not allowed:`, `General instructions:`; text without markers goes entirely into General instructions; text before the first marker is prepended to General instructions.
- Does the cutover also create the drift tick? -> Yes, with each inserted row, because migration 0035 backfilled heartbeats only for rows that existed then.
- Where does the guidance HTTP code live, given `packages/data` cannot import `packages/application`? -> In `packages/data` (route handlers plus reusable in-transaction `loadGuidanceSections` / `saveGuidanceSections`), owned by the systemDatabases module manifest. The existing application service stays for ownership transfer. Reason: program decision on custom routes; dependency direction.
- Conflict body -> 409 `version_conflict` with the route returning its own body containing the current sections, `updatedAt` and owner (the generic error mapper would drop non-flat details). `expectedUpdatedAt` is compared as the ISO string after `SELECT ... FOR UPDATE`, because the column has microsecond precision.
- Reserved heading -> whole-line match of the four headings anywhere in a section (code fences not special-cased) so compose and parse are exact inverses.
- Unknown project id on the guidance routes -> 404 `not_found` (the old service used 400 with a `not_found` reason).
- All sections empty -> row deleted, drift heartbeat disabled, active findings resolved without notifications.
- Web editor -> plain multi-line text fields per card (no shared Markdown editor exists in the repo); autosave 800 ms; "Saving..."/"Saved"; 409 shows the current server text and never retries automatically.
- Removing `projects.agents` in the same release as the page switch -> accepted as the ADR's "explicit breaking change" exception; the only reader is the page, rollback shows an empty card, data stays in `project_agent_guidance`.
- Fingerprint identity -> SHA-256 of canonical JSON of `{projectItemId, kind, operation|mcpTool, databaseId}`. The permission check's AI response schema gains a required `subject {operation, databaseId}` copied from the manifest, so the permission fingerprint is deterministic too. Old fingerprints are dropped without migration (findings table is empty in practice).
- Behavior groups -> (operation or MCP tool, target database id) from `tool_use` events of the last 14 days, at least 3 distinct runs; AI reports only groups not mentioned in `allowed` or `notAllowed`; evidence `{runIds (latest 20), count}`; severity warning; gateway not called when no group qualifies.
- Reconcile -> permission and behavior passes resolve only their own kind; if one throws the other still runs.
- `allow` / `forbid` on a `permission` finding -> 400 `not_applicable` (no suggestions exist for that kind); `dismiss` accepted for both.
- Decided findings -> `allow`/`forbid` resolve with `resolution_choice`, `dismiss` uses new status `dismissed`; neither is reopened by `upsertActive`. Findings resolved by the nightly tick (no choice) may still reopen.
- `resolutionTitle` -> produced in the guidance notification writer from the payload `kind` (default `permission`), so the nightly auto-resolve path gets it without editing `driftAction.ts` (avoids a file clash between the behavior-detection issue and the resolve issue, which have no ordering between them).
- GET drift response -> `{guidanceUpdatedAt, findings[]}` (additive: the client needs `guidanceUpdatedAt` for `expectedGuidanceUpdatedAt`).
- Behavior drift `dismiss`: should a dismissed behavior finding ever return (for example after N days or when the count grows)? -> Decided by the product owner: no, dismissal is permanent; behavior must be predictable and the user must not be bothered by the same finding again.
- Should "Add to Allowed / Forbid" also be offered for permission findings (needs AI-generated lines)? -> Decided by the product owner: no; changing permissions from AI-suggested lines is risky, and permissions change only explicitly in the project settings.
- Should the manual resolve push-notify? -> Decided by the product owner: no; the manual resolve is the user's own action, which the user already knows about, so a push would be noise (the resolved kind is never pushed, #1440).
- How is a system project recognized when its guidance is seeded at account creation? -> Decided by the product owner: by a stable key plus the `systemActive` flag, never by its name; renaming a system project must not break the assignment of its guidance. The stable key is the module id of the system database the project owns (#1449).
- Is the same behavior under two different databases two separate findings? -> Decided by the product owner: yes; the database is part of the finding's subject, so each finding can be dismissed separately.

#### User-visible behavior delivered by this chunk

Every project now has one place for its instructions: four sections (Purpose, Allowed, Not allowed, General instructions) stored as the Markdown the agent actually receives in its prompt. Existing instructions (including the system projects' texts) are carried over automatically, and new accounts get them too. The owner edits the sections on the project's AGENT page with automatic saving after 800 ms, and a second device with stale content gets a conflict instead of overwriting. Each night Semp also compares the instructions with what the agent really did over the last 14 days; when three or more runs did something the instructions never mention (for example creating tasks from GitHub issues), the page offers a card with two ready-made lines: add it to "Allowed" or to "Not allowed". Choosing one appends the line to the right section in one step (or dismisses the card), the finding closes and does not come back, and permission mismatches and behavior mismatches both close themselves when they stop being true.
