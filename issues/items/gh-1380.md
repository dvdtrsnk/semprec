## Context

Model tier rationale: A documentation-only decision record, but it settles who may create Inbox cards and how the tick treats several cards for one source, which later implementation relies on literally, so the reasoning must be checked against the code.

In the item thread the user can say "split this into several items". One Inbox source then needs several proposal cards. Today the relation `Processing proposals.sourceInbox` is many-to-many, but the tick (`findExistingProposal` in `backend/packages/data/src/inbox/inboxTickAction.ts`) works with the first live card of a source only, and the existing ADRs `docs/adr/2026-09-23-processing-proposals-card-creation-owned-per-kind.md` (superseded by `docs/adr/2026-09-23-speaker-mappings-are-edges-proposed-on-transcript-cards.md`) make `semprec.tick` the only producer of `kind: inbox` cards and state that a new producer or a new place of production is a new decision. `docs/adr/2026-09-10-agent-writes-are-proposals-not-direct-writes.md` additionally says an agent never writes to a target database directly. This issue records the decision; the implementation is #1939.

Decision to record (conservative option): the thread's agent tool does not create cards itself. The tool calls an Inbox-module proposal action (`splitInboxSourceWithClient` in `proposalActions.ts`'s module, in the module that owns Processing proposals) in a user-context request on behalf of the thread, so the write goes through the choke point inside the module's transaction and the card is still a proposal, never a target write. Reasons: the split instruction exists only in the thread, the tick sees only the source and cannot reproduce it; creating the siblings asynchronously in the tick would require persisting the instruction on a card and would let the user see an edited primary card but no siblings; a synchronous module action returns all cards in one transaction and realtime update.

Decision to record: the first card of a split stays the source's primary card and the only one the tick recomputes. Sibling cards carry a system property `splitFromProposalId` (the primary card's id); `findExistingProposal` and the tick ignore any card with it set. A sibling is recomputed only on an explicit request (the recompute route or a thread revision), never by a source edit. The primary card's fingerprint continues to follow the source. Confirm, reject and the other card actions work per card.
