## Context

Model tier rationale: New notification kinds with batching rules that must not fire during initial sync or for the user's own changes.

The owner wants "Family: Peter added Dinner, Fri 19:00" when someone else changes a calendar whose notify switch is on.

Decision: a change is "someone else's" when it was applied by `calendarSync` and was not the echo of a local push. Google and Graph provide the last modifier only partly; the creator or organizer name is used when it is not the user, otherwise the copy omits the person ("Family: new event Dinner, Fri 19:00").

## Task

Load `state-writes`, `db-migrations`, `error-handling`, `io-hardening`, `canonical-keys` and `testing`.

1. Kinds `calendar_event_added`, `calendar_event_changed`, `calendar_event_cancelled` with a new preference key `calendarChanges` (default on) in `NOTIFICATION_KINDS`, the CHECK constraint, the policy and en/cs titles.
2. The sync apply collects added, changed (time, place or title) and cancelled events per calendar whose `notify` is true; it writes one notification per event, or one summary notification "Family: 5 changes" when a pass has more than 3 for a calendar.
3. No notifications during an account's initial sync (`initial_sync_completed_at` null) or for events whose change was a local push echo.
4. The push opens the event (`link_href` to the event) and carries `event_id` and `calendar_id`.
5. Add `calendarChanges` to notification preferences (backend read and write, default true).

## Scope

### In scope

- The kinds, batching, quiet initial sync and the preference.

### Out of scope

- Client handling of the push (APNs client issue).

## Acceptance criteria

- A remote added event in a notify calendar produces one push; the same in a calendar with notify off produces none.
- The first sync of a new account produces no notification.
- Five changes in one pass produce one summary.
- A local edit that comes back from the provider produces nothing.
