## Context

Model tier rationale: A new tenant-classified table with row-level security and one read/partial-update route pair, following existing table and custom-route conventions, with defined validation rules.

Push is a pointer; errors appear in context and assistant status. Users choose interruptions rather than a notification-center UI. Persist approval/invitation/reminder switches, problem level and summary behavior, and badge-count choices. The existing fan-out is `notifications/notificationFanoutJob.ts`.

Decision: a missing row means the defaults: `approvals`, `invites`, `reminders` on; `problemsLevel` `critical`; `problemsSummary` on; `badgeApprovals` and `badgeInvites` on; `badgeInbox` off. Reminders are planned by the phone; the server only stores the switch. The change reaches the user's other devices through the preference invalidation added by #1918; the filter and the badge read these values (#1443, #1891).

Shared-file ordering: this issue also waits for #1404 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Acceptance criteria

- When a user has no row, then GET returns the defaults.
- When PATCH sends `{ "approvals": false }`, then only that field changes and GET returns it.
- When PATCH sends an invalid enum value or an unknown key, then the response is 400 and nothing is written, including a mixed valid/invalid patch. Unknown keys produce a fixed message and `details.field = "body"` without reflected key/value content in errors, details or logs; known invalid fields keep their canonical field names.
- When another user or tenant requests preferences, then they never see this user's values.
