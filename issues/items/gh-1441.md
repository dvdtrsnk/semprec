## Context

Model tier rationale: A new tenant-classified table with row-level security and one read/partial-update route pair, following existing table and custom-route conventions, with defined validation rules.

There is no notification center in the app: push is a pointer to where a thing is, errors are shown in context and summarized in the assistant's status, and the user only chooses what may interrupt them. The settings screen lets the user switch push on or off per category (approvals, calendar invitations, task reminders), choose a level for assistant problems (off, only critical, all), choose whether problems are sent in a scheduled summary, and choose which counts appear on the app icon badge (pending approvals, invitations, Inbox items). Nothing stores these today (the push fan-out is described in `backend/packages/data/src/notifications/notificationFanoutJob.ts`).

Decision: a missing row means the defaults: `approvals`, `invites`, `reminders` on; `problemsLevel` `critical`; `problemsSummary` on; `badgeApprovals` and `badgeInvites` on; `badgeInbox` off. Reminders are planned by the phone; the server only stores the switch. The change reaches the user's other devices through the preference invalidation added by #1918; the filter and the badge read these values (#1443, #1891).

Shared-file ordering: this issue also waits for #1404 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `state-writes` and `testing`.

1. Add the migration `backend/packages/data/src/db/migrations/NNNN_notification_preferences.sql` (next free ordinal at commit time) creating `notification_preferences (tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id), user_id uuid NOT NULL REFERENCES users(id), approvals boolean NOT NULL DEFAULT true, invites boolean NOT NULL DEFAULT true, reminders boolean NOT NULL DEFAULT true, problems_level text NOT NULL DEFAULT 'critical' CHECK (problems_level IN ('off','critical','all')), problems_summary boolean NOT NULL DEFAULT true, badge_approvals boolean NOT NULL DEFAULT true, badge_invites boolean NOT NULL DEFAULT true, badge_inbox boolean NOT NULL DEFAULT false, updated_at timestamptz NOT NULL DEFAULT now(), PRIMARY KEY (tenant_id, user_id))`, with tenancy comment, row-level security, both policies and the grants of `docs/operations/database-roles.md`.
2. Add `backend/packages/data/src/notifications/notificationPreferencesStore.ts` with `getNotificationPreferences(client, userId)` (defaults when no row) and `patchNotificationPreferences(client, userId, patch)` (upsert of only the supplied fields).
3. Add `GET /api/notification-preferences` and `PATCH /api/notification-preferences` as custom routes: handlers in `notifications/notificationPreferencesRoutes.ts`, declared in `chokePoint/schemaCoreModuleManifest.ts` (`single-consumer-read` for GET, `transactional-semantics` for PATCH), `routeMatrix.ts` entries with tenancy `tenant`, and an entry in `ROUTE_HANDLER_FILES` of `services/semprec-api/src/__tests__/chokePointWriteBoundary.unit.test.ts`. The caller's own preferences only.
4. Response of both: `{ approvals, invites, reminders, problemsLevel, problemsSummary, badgeApprovals, badgeInvites, badgeInbox, updatedAt }` (camelCase). PATCH accepts any subset; an unknown key, a non-boolean for a boolean field or a `problemsLevel` outside `off|critical|all` is a 400 naming the field; an empty object changes nothing and returns the current values.
5. Add tests: defaults without a row; partial PATCH keeps the other fields; validation errors; two users and two tenants do not see each other's rows; the route matrix and tenant isolation tests cover the new routes.

## Scope

### In scope

- The preferences table, store and the GET and PATCH routes.

### Out of scope

- Using the preferences to filter push: #1443; using the badge switches: #1891.
- Notifying the user's other devices of a change: #1918.
- Planning reminders (done on the phone).

## Acceptance criteria

- When a user has no row, then GET returns the defaults.
- When PATCH sends `{ "approvals": false }`, then only that field changes and GET returns it.
- When PATCH sends an invalid enum value or an unknown key, then the response is 400 and nothing is written.
- When another user or tenant requests preferences, then they never see this user's values.
