**Model tier:** high

## Context

Model tier rationale: This adds one item row lock to the generic relation write path that every user and agent edge write on a link rule's via relation goes through, against a reproduced deadlock, and it has to be shown not to open another cycle with the callers that lock an item row, a relation definition or a value link row first; a wrong order replaces one deadlock by another, as the first design of this source did (`issues/decisions/sp-5419cac1-f4a7-4717-b870-4f244b1ad166.md`). The title names that first design (the edge-changed hooks before the link break); the Task below is authoritative.

The link engine (#1593) locks a target item row before that item's value link row: the propagation job (`valueLinks/linkPropagation.ts`) and the engine's edge-changed hook (`valueLinks/linkRuleEdgeHook.ts`) call `itemsStore.lockItemById` and then `valueLinksStore.lockValueLink`. `docs/adr/2026-11-05-value-link-propagation-keeps-separate-hop-budgets.md` makes this the rule, and `docs/adr/2026-11-01-value-link-item-updates-lock-item-before-handoff.md` gave item updates the same order.

A user or agent write of a relation edge does the opposite since #1516. `createRelationWithClient`, `createRelationIfAbsentWithClient` and `deleteRelationWithClient` in `backend/packages/data/src/chokePoint/relationOps.ts` write or delete the edge row, then call `breakValueLinksForRelationEdge` (`chokePoint/valueLinkWrites.ts`), which ends the `on` link of each side with one `UPDATE` and so holds the link row, and only afterwards call `runRelationEdgeChangedHooks`, where the engine's hook locks the item row when the relation is the via relation of a rule.

This closes a cycle for a relation that is the target of one rule and the via relation of another: `Transcripts.project` since #1697 (target of `transcriptProjectFromEvent`, via of `transcriptCompanyFromProject`) and `Files.projects` with #1756 (target of `fileProjectsFromEvents`, via of `fileCompaniesFromProjects`). A user removes or adds a project on an item whose project link is `on`: the write ends the link row and then waits for the item row in the engine's hook. Meanwhile the propagation job of the Event's project, or the engine's hook for another via edge of the same item, holds the item row and waits for the link row. PostgreSQL ends one of the two with `40P01`. For `Files.projects` this was reproduced during the review of #1756 with production calls on both sides under the `alldots_data` runtime role: the user's `deleteRelation` failed with `40P01`, which no error mapping covers, and was rolled back. A propagation job that loses is retried up to three times and then dropped, which leaves the old value on an item whose link is still `on`. `Transcripts.project` has the same shape and was read, not run.

`docs/adr/2026-11-01-value-link-relations-use-nonblocking-admission-and-scoped-lock-waits.md` left the link break of ordinary edge writes unchanged, says that a newly confirmed remaining cycle is another design decision, and names both blocking orders as conflicting. Both were read against the code for this issue; nothing was run:

- A blocking item row lock at the place of the link break comes after the definition advisory lock that the cardinality trigger takes on every edge insert (`db/migrations/0013_relation_cardinality.sql`) and holds to the end of the transaction. `setRelationWithClient`, the update preconditions of a proposal (`inbox/proposalSteps.ts`) and the Threads merge lock the item row first and that definition afterwards. For a relation that is a rule target and no rule's via relation (`Transcripts.company`, `Files.companies`) such a lock would open a cycle that does not exist today.
- A blocking item row lock before the edge write conflicts with a transaction that already holds the definition lock from an earlier insert of the same definition (`createItemWithRelationsWithClient` writes several edges of one definition), while a single edge write holds the item row and waits for that definition.

Decision (corrected by `issues/decisions/sp-5419cac1-f4a7-4717-b870-4f244b1ad166.md`): the first design of this source, running the edge-changed hooks directly after the edge write and before the link break, is withdrawn. It removes the cycle above and opens another one. The engine's hook for `Transcripts.project` locks the transcript's `company` value link row (rule `transcriptCompanyFromProject`) and the break then locks the `project` link row, while moving the transcript's Event to the Trash takes the two rows the other way round and without the transcript row: `valueLinkSourceDeleteHook` deletes the `project` link, then `transcriptCompanyLinkReleaseItemDeleteHook` locks the `company` link, as `docs/adr/2026-11-10-transcript-values-are-inherited-by-link-rules-whichever-process-writes-the-edge.md` records (the release of a removed `event` edge takes `project`, `people`, then `company` as well). A worker reproduced it with production calls: with a third transaction holding the `company` link row and the user's write started first, one of the two ends with `40P01`, while both commit on the unchanged write path.

Decision: the order of the rows of one transcript, file or task that the write path of this source takes is the item row, then the `project` link row, then the `people` link row, then the `company` link row. The propagation job and the engine's hook take the item row and then link rows, the release of a removed `event` edge takes `project`, `people`, `company` under the item row, and the trash of an Event takes the `company` link of each transcript last and, for a transcript, never its item row. The edge write of a user or agent breaks that order, because the break takes the `project` link row before the engine's hook takes the item row. The write takes that item row first instead: a new kind of hook, run right after the edge row is written or deleted and before anything in the write locks a value link row, locks the item rows that the engine's hook locks for this edge, which are the target item of each link rule whose via relation is the written one, in rule order, with the same `lockItemById` call and the same blocking wait. The edge-changed hooks, the link break, the rollup enqueue and the announcement keep their order and their arguments after it, and the engine's hook finds the row already locked by its own transaction.

Decision: the order above is not a total order of every path, and the decision does not claim it. Three paths that exist on the tip take value link rows against it and end with `40P01` against a writer that follows it; each was measured with production calls on the tip and with the prototype of the decision record, and none is repaired here. (a) The trash of an Event takes the `project` and `people` links it feeds in the order of their link ids (`deleteValueLinkSourcesBySourceItem` selects `ORDER BY l.id FOR UPDATE`), while the release of a removed `event` edge takes `project` and then `people`: a user `deleteRelation` of the transcript's `event` edge against `softDeleteItem` of its Event, with a third transaction holding the `project` link row, ends with `40P01` when the `people` link has the smaller id. (b) The trash of an Event that hosts a task which is also sourced from it takes the task's `project` and `people` links in the source detach and then the task row in `eventHostedTasksDeleteHook`, while the propagation of `taskProjectFromEvent` takes the task row and then its `project` link: with a third transaction holding the task row, the propagation started first and the trash second, one of the two ends with `40P01`. (c) The replay of an approved agent `relation.delete`, `relation.put` or `relation.set` (`replayApprovedGenericOperation`) runs the destructive projection check on the same transaction before the write, which share-locks the `on` links of the edge's sides (`reserveEdgeLinks`), so it holds the `project` link row before the new lock takes the item row: schedule A with the propagation waiting for the transcript row first ends with `40P01` for the replay. The new lock therefore repairs the user edge write, and an agent edge write that needs no approval, and not the replay of an approved agent write.

Decision: where the lock sits. It is taken after the edge row is written or deleted, so it comes after the definition advisory lock of the cardinality trigger exactly as the engine's lock does today, and only for a user or agent write: a system write never ends a link, and the protected writes of the `valueLinks` process keep their nonblocking admission untouched. For a relation that is the via relation of a link rule this adds no position the write does not already have, so it opens no cycle with `setRelationWithClient`, the update preconditions of a proposal or the Threads merge that the engine's hook does not already open, and the schedule-B deadlocks on `Transcripts.project` stay as they are on the tip. The two blocking locks above stay rejected: the lock is neither taken for a relation that is no rule's via relation nor before the edge write. A prototype of this order, run against the reproduction of Task step 1 on the integration tip, is recorded in the decision record; the worker measures it again and Task step 2 says when it stops.

Decision: a relation that is no rule's via relation keeps its behaviour: the write locks no item row and ends the link as today. A transaction that ends a link in one edge write and reaches the same item's row only in a later statement is not covered; it is recorded as a limit. System writes are unchanged; they never end a link. An agent write under a run that is not approved takes `FOR SHARE` on the `on` link rows of the edge's sides in its approval check (`valueLinkApproval.ts`) and ends in an approval refusal when it finds one; in `createRelationWithClient` the new lock comes before that check, and the other approval checks are not changed. This is recorded as a limit, and so is the replay of an approved agent `relation.delete`, `relation.put` or `relation.set`: its projection check (`reserveEdgeLinks`, `FOR SHARE NOWAIT`) holds the `on` link rows before the write reaches the new lock (see the Decision above).

## Scope

### In scope

- The order in which an ordinary edge write on a link rule's via relation takes the item row and the value link rows, the hook kind that carries it, its tests and the ADR.

### Out of scope

- A blocking item row lock for a relation that is no rule's via relation, and a blocking item row lock before the edge write. The lock of Task step 2 is neither.
- A nonblocking reservation of the item row with a busy refusal for user or agent edge writes. It would refuse requests that wait today and is a decision of its own.
- The link engine, its hooks and the propagation job: #1593. `linkRuleEdgeHook` changes only by sharing the computation of its target item with the new hook.
- The admission protocol and the busy error of `valueLinks` relation writes.
- Item updates, which already lock the item first.
- Repairing a deadlock of schedule B that exists on the tip; it is recorded.
- The order in which the trash of an Event, the release of a removed `event` edge and the approval check of an agent write take value link rows. They follow the order of the Context, or are recorded as a limit with a measured deadlock (the trash of an Event against the release of a removed `event` edge, the trash of an Event that hosts a task it is the source of, the replay of an approved agent write), and are not changed.
- Mapping `40P01` to an API error, and retries of a refused request.
- The link rules themselves: #1653, #1697, #1756.

## Acceptance criteria

- When a user removes the project edge of a transcript whose project link is `on` while the propagation of its Event's project works on the same transcript, then both settle without a deadlock error, in both orders, with the outcomes of Task step 3.
- When a user edge write, or an agent edge write that needs no approval, on a rule's via relation would end an `on` link while another transaction holds that item's row, then the write waits for the row and holds no value link row of that item.
- Every case of Task step 1 that settled on the tip settles after the change with the same outcome.
- When a user edge write touches a relation that is no rule's via relation, then it does not wait for a transaction that holds its item's row.
- The edge-changed hooks of an ordinary edge write run once with the arguments they had, a `system` edge write behaves as before and runs no before-link-break hook, and the existing value-link write, link-rule and relation admission tests pass; a test that had to change is named in the handover with its reason.
- The ADR exists and reviews the composition as Task step 4 says.
