**Blocked by:** #1697
**Model tier:** high

## Context

Model tier rationale: This reorders two steps of the generic relation write path that every user and agent edge write goes through, against a reproduced deadlock, and it has to be shown not to open another cycle with the callers that lock an item row or a relation definition first; a wrong order replaces one deadlock by another.

The link engine (#1593) locks a target item row before that item's value link row: the propagation job (`valueLinks/linkPropagation.ts`) and the engine's edge-changed hook (`valueLinks/linkRuleEdgeHook.ts`) call `itemsStore.lockItemById` and then `valueLinksStore.lockValueLink`. `docs/adr/2026-11-05-value-link-propagation-keeps-separate-hop-budgets.md` makes this the rule, and `docs/adr/2026-11-01-value-link-item-updates-lock-item-before-handoff.md` gave item updates the same order.

A user or agent write of a relation edge does the opposite since #1516. `createRelationWithClient`, `createRelationIfAbsentWithClient` and `deleteRelationWithClient` in `backend/packages/data/src/chokePoint/relationOps.ts` write or delete the edge row, then call `breakValueLinksForRelationEdge` (`chokePoint/valueLinkWrites.ts`), which ends the `on` link of each side with one `UPDATE` and so holds the link row, and only afterwards call `runRelationEdgeChangedHooks`, where the engine's hook locks the item row when the relation is the via relation of a rule.

This closes a cycle for a relation that is the target of one rule and the via relation of another: `Transcripts.project` since #1697 (target of `transcriptProjectFromEvent`, via of `transcriptCompanyFromProject`) and `Files.projects` with #1756 (target of `fileProjectsFromEvents`, via of `fileCompaniesFromProjects`). A user removes or adds a project on an item whose project link is `on`: the write ends the link row and then waits for the item row in the engine's hook. Meanwhile the propagation job of the Event's project, or the engine's hook for another via edge of the same item, holds the item row and waits for the link row. PostgreSQL ends one of the two with `40P01`. For `Files.projects` this was reproduced during the review of #1756 with production calls on both sides under the `semprec_data` runtime role: the user's `deleteRelation` failed with `40P01`, which no error mapping covers, and was rolled back. A propagation job that loses is retried up to three times and then dropped, which leaves the old value on an item whose link is still `on`. `Transcripts.project` has the same shape and was read, not run.

`docs/adr/2026-11-01-value-link-relations-use-nonblocking-admission-and-scoped-lock-waits.md` left the link break of ordinary edge writes unchanged, says that a newly confirmed remaining cycle is another design decision, and names both blocking orders as conflicting. Both were read against the code for this issue; nothing was run:

- A blocking item row lock at the place of the link break comes after the definition advisory lock that the cardinality trigger takes on every edge insert (`db/migrations/0013_relation_cardinality.sql`) and holds to the end of the transaction. `setRelationWithClient`, the update preconditions of a proposal (`inbox/proposalSteps.ts`) and the Threads merge lock the item row first and that definition afterwards. For a relation that is a rule target and no rule's via relation (`Transcripts.company`, `Files.companies`) such a lock would open a cycle that does not exist today.
- A blocking item row lock before the edge write conflicts with a transaction that already holds the definition lock from an earlier insert of the same definition (`createItemWithRelationsWithClient` writes several edges of one definition), while a single edge write holds the item row and waits for that definition.

Decision: no lock is added. In an ordinary edge write the edge-changed hooks run directly after the edge row is written or deleted, and the links are ended after them. The item row lock that the engine's hook already takes then comes before the link row, as in the propagation job, and the write takes exactly the locks it takes today.

Decision: this order was derived by reading. It is kept only if the reproduction of Task step 1 confirms it; Task step 2 says when the worker stops instead.

Decision: a relation that is no rule's via relation keeps its behaviour: the write locks no item row and ends the link as today. A transaction that ends a link in one edge write and reaches the same item's row only in a later statement is not covered; it is recorded as a limit. System writes are unchanged; they never end a link.

## Task

Load `state-writes`, `error-handling`, `testing` and `adr-conventions`.

1. Reproduce first, before any change, in `backend/packages/data/src/__tests__/valueLinkEdgeBreakLockOrder.test.ts` (new), on a `semprec_data` runtime-role pool with production calls on both sides. Fixture: a transcript linked to an Event whose project has a company, so that the transcript's `project` and `company` links are `on`. Record the outcome of every schedule on the tip in the handover.
   - Schedule A, the defect: the `valueLinksPropagate` handler for a change of the Event's project and a user `deleteRelation` on the transcript's `project` edge both wait for the transcript row, which a third transaction holds, and are released; once for each order in which the two wait. If no order ends with `40P01` on the tip, stop and report that instead of changing the code.
   - Schedule B, callers that lock the item first: a user `setRelationWithClient` (the `relation.set` operation) on the transcript's `project` against a user edge write of the same relation definition for the same transcript that reaches the transcript row only in the engine's hook (a `deleteRelation` of its edge, or a `createRelation` when it has none), and the same pair on `company`, each in both orders. This is the baseline: what each case does on the tip is recorded, including a deadlock.
2. In `createRelationWithClient`, `createRelationIfAbsentWithClient` and `deleteRelationWithClient`, move the call of `runRelationEdgeChangedHooks` to directly after the edge row is written or deleted, ahead of `breakValueLinksForRelationEdge`. The link break, the rollup enqueue and the announcement keep their order among themselves, the hooks get the same arguments, and a link is still ended only by an actual insert or delete of a user or an agent. Change nothing in `valueLinkWrites.ts`, the engine, the Threads merge or the admission protocol of the `valueLinks` relation writes. Before the change, read every edge-changed hook registered in `domainWriteHooks.ts` and name in the handover each one that reads a value link of the written edge's own sides. Stop and report, with the logs and without a committed production change, when one of these holds: such a hook needs that link to be ended before it runs; a case of step 1 that settled on the tip ends with `40P01` after the change; schedule A still ends with `40P01`.
3. Turn the reproduction into permanent tests of the settled outcomes. Schedule A, both orders: no transaction ends with `40P01`; the user's write commits the removed edge and the link broken by the user; the propagation writes nothing to the transcript once the link is broken, and an attempt of it that ends with the busy refusal of the relation admission (`value_link_busy`) succeeds when it is run again. Schedule B: every case that settled on the tip asserts the same outcome; a case that ends with `40P01` on the tip gets no permanent test and is named in the handover and in the ADR of step 4. Add: while a third transaction holds the item row, a user edge write on `Transcripts.project` that would end the `on` link waits for the row and holds no value link row of the transcript; a user edge write on a relation that is no rule's via relation does not wait for a transaction that holds its item's row; the first breaker of a link stays recorded; the edge-changed hooks of an ordinary write run once.
4. ADR: add `docs/adr/<date it is written>-ordinary-edge-writes-run-edge-hooks-before-ending-value-links.md` (`status: accepted`, `area: [backend]`, `supersedes: []`). Its Context references `[[2026-11-01-value-link-relations-use-nonblocking-admission-and-scoped-lock-waits]]`, `[[2026-11-01-value-link-item-updates-lock-item-before-handoff]]` and `[[2026-11-05-value-link-propagation-keeps-separate-hop-budgets]]` and says that it decides the cycle those ADRs left open for the link break of ordinary edge writes; their bodies are not edited. Its Decision states the three decisions above and why neither blocking item row lock was taken. Its Consequences review the composition with the measured outcomes: schedules A and B, the three schedules the relation ADR measured, a transaction that already holds proposal, definition or edge locks, and the rollup enqueue; and they state the limits: the multi-statement transaction named above and every deadlock of schedule B that exists on the tip and that this issue does not repair.

## Scope

### In scope

- The order of the edge-changed hooks and the link break in ordinary edge writes, its tests and the ADR.

### Out of scope

- A blocking item row lock in the relation write path, at the link break or before the edge write.
- A nonblocking reservation of the item row with a busy refusal for user or agent edge writes. It would refuse requests that wait today and is a decision of its own.
- The link engine, its hooks and the propagation job: #1593.
- The admission protocol and the busy error of `valueLinks` relation writes.
- Item updates, which already lock the item first.
- Repairing a deadlock of schedule B that exists on the tip; it is recorded.
- Mapping `40P01` to an API error, and retries of a refused request.
- The link rules themselves: #1653, #1697, #1756.

## Acceptance criteria

- When a user removes the project edge of a transcript whose project link is `on` while the propagation of its Event's project works on the same transcript, then both settle without a deadlock error, in both orders, with the outcomes of Task step 3.
- When a user or agent edge write on a rule's via relation would end an `on` link while another transaction holds that item's row, then the write waits for the row and holds no value link row of that item.
- Every case of Task step 1 that settled on the tip settles after the change with the same outcome.
- When a user edge write touches a relation that is no rule's via relation, then it does not wait for a transaction that holds its item's row.
- The edge-changed hooks of an ordinary edge write run once with the arguments they had, a `system` edge write behaves as before, and the existing value-link write, link-rule and relation admission tests pass; a test that had to change is named in the handover with its reason.
- The ADR exists and reviews the composition as Task step 4 says.
