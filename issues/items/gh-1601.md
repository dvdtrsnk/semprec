## Context

Model tier rationale: One known mechanism (two hook registries called from the existing trash cascade in the same transaction) with an existing trash test fixture, but the per-row epoch semantics of restore and the all-or-nothing rollback need care.

Moving an item to the trash and restoring it are implemented in `backend/packages/data/src/chokePoint/itemTrash.ts`. `itemDeleteWithClient` collects the item's subtree (`collectItemSubtree`: the item, the inline databases it owns, their rows, recursively), soft-deletes every row with one shared `deletedAt` (Postgres `now()` is fixed inside the transaction), and `restoreItemWithClient` restores only the subtree rows whose `deletedAt` equals the root's (the "cascade epoch"), so rows trashed earlier or later on their own stay trashed. Neither function runs any hook: the dependency-cruiser rule `chokepoint-knows-no-domain` (`backend/dependency-cruiser.rules.json`) exempts `itemTrash.ts` with the comment that "no domain needs a delete hook today". Domains now do: calendar deletion with events, journal day restore, recording and transcription cleanup, search reindexing, last-contact derivation, invitations, mailbox removal, recurring-series trash and value-link detaching all need to run inside the same transaction as the trash or restore and be able to veto it.

This issue adds an item delete hook and an item restore hook to the registry in `chokePoint/hooks.ts`, the same way ADR `2026-10-09-item-create-domain-hooks` added the create hook. It builds on #1530 (the three hook issues share `hooks.ts` and `domainWriteHooks.ts`, so they land in order) and on #1415 for the `writerKind` it passes. Consumers include #1803, #1819, #1666, #1652, #1660, #1780, #1656, #1882, #1723, #1904, #2031, #2032, #1691, #1945, #1774, #1916, #1784 and #1838.

Decisions:
- The delete hook runs for every row of the cascade that was actually soft-deleted in this call (not for rows already in the trash), root first, after that row's soft delete. The restore hook runs only for rows actually restored, i.e. whose `deletedAt` matched the cascade epoch, after that row's restore.
- A hook receives the row after the change plus the shared `deletedAt` of the cascade (for restore, the epoch that was cleared), so a consumer can tell which rows were trashed together.
- `itemDeleteWithClient` called on an already-trashed root and a restore of a live root stay idempotent no-ops and call no hook.
- Permanent purge of trashed items is not part of this issue and runs no hook.

Shared-file ordering: this issue also waits for #1599 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `testing` and `adr-conventions`.

1. In `chokePoint/hooks.ts` add `registerItemDeleteHook`, `registerItemRestoreHook`, the types `ItemDeleteHookContext` / `ItemRestoreHookContext` (`{ client, database, item, rootItemId, deletedAt, writerKind, agentRunId?, actingUserId? }`) and `runItemDeleteHooks` / `runItemRestoreHooks`; sequential, in registration order, first rejection propagates; same-function double registration is a no-op; extend `clearHooksForTests`. `database` is the `DatabaseRow` of the row's database.
2. In `itemDeleteWithClient` call `runItemDeleteHooks` for each row `softDeleteItem` returned, and in `restoreItemWithClient` call `runItemRestoreHooks` for each restored row, both inside the existing transaction and before the transaction commits. A thrown error rolls back the whole cascade (all rows stay as they were). Accept `writerKind` (and the agent fields) through the options added by #1415 and pass them to every hook.
3. Update the `chokepoint-knows-no-domain` rule in `backend/dependency-cruiser.rules.json`: keep `itemTrash.ts` exempt only for the blobs/docs/library cascade imports it still needs, and rewrite the comment so it no longer says no domain needs a delete hook. Add a guard so no other domain import is added to `itemTrash.ts`.
4. Add an ADR under `docs/adr/` of the shape of `2026-10-09-item-create-domain-hooks` for the delete and restore hooks, and amend the `itemTrash.ts` exception paragraph of `2026-09-30-choke-point-domain-hooks-through-a-per-process-registry`.
5. Tests: unit tests for the registries; integration tests in the existing trash tests that a cascade delete calls the delete hook once per newly trashed row with the same `deletedAt`, a restore calls the restore hook only for rows of the same epoch, an independently trashed child is skipped, and a throwing hook leaves every row unchanged (delete and restore).

## Scope

### In scope

- The two registries, their calls from the soft-delete and restore cascades, the rollback guarantee, the dependency rule update and the ADR.

### Out of scope

- Any consumer hook: calendar, journal, search, mail, transcription, recurring series and the others named in Context each register their own.
- Hooks on permanent purge of trashed items and on database or property archive and delete.
- Carrying `writerKind` into the trash entry points: #1415 (this issue only passes it on).
- The edge-changed hook: #1530.

## Acceptance criteria

- When `DELETE /api/items/:id` trashes an item with a cascade, the delete hook is called once for every newly trashed row with the same `deletedAt`, root first.
- When `POST /api/items/:id/restore` restores it, the restore hook is called only for the rows actually restored (those of the same cascade epoch), and not for a child that was trashed separately.
- Deleting an already-trashed item or restoring a live item calls no hook.
- When a delete or restore hook throws, the whole request fails and every row of the cascade is exactly as before.
- `pnpm` dependency-cruiser validation passes with the updated `chokepoint-knows-no-domain` rule.
