## Context

Model tier rationale: Adds a new card kind and a cross-module relation to the Processing proposals schema with a per-tenant cutover, and changes the confirm path, the single sanctioned cross-destination write, so that one transaction writes a task, its thread edge and inherited values.

The product owner decided that Semp never creates a task from a mail thread silently: Semp proposes the task in the Inbox, the user can edit the proposal, and only the user's confirm creates the task. The Inbox already has this mechanism. A card is an item of the Processing proposals database (`seed/seedInboxPipeline.ts`) with `kind` (`inbox` or `transcript`), `status`, the `proposal` envelope and `history`; `confirmProposalWithClient` in `backend/packages/data/src/inbox/proposalActions.ts` is the only path that turns a card into a target item, and `assertValidEnvelopeForCard` validates every envelope written by revise or confirm. A transcript card shows the precedent for a card that belongs to a source item other than an Inbox item: it is linked to its transcript through the Processing proposals relation `sourceTranscript`, and its confirm writes the extra edge in the same transaction.

A task made from a thread must not be a plain task: it needs the edge Threads.tasks (#1612) and the thread's project and the conversation's people as inherited values. #1900 puts exactly that in one exported transactional function of `mail/threadTasks.ts` (Tasks item, Threads.tasks edge, inherited Tasks.project and Tasks.people). This issue adds the card kind for a thread and makes its confirm call that function. The tool with which Semp creates such a card is #2035. The card kinds of the Inbox list are derived by `deriveInboxCardKind` (#1425).

Decisions:
- A thread task card has `kind` `mailThread`, is linked to the thread's Threads item through the new Processing proposals relation `sourceThread`, and carries a `database` envelope targeting Tasks.
- The editable part of the card is the task's `name` and optional `date`. Its project and people are not part of the envelope: they come from the thread at confirm, as for a task created by the route of #1900, and the user changes them on the task afterwards (which ends the inheritance). A `relations` entry, any other property, or another target or entity kind on a `mailThread` card is a validation error.
- Confirm runs as the user. When the source Threads item is deleted (for example merged away) confirm answers 409 `conflict` and the card stays `proposed`.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys`, `error-handling` and `testing`.

1. Schema: add the option `mailThread` to the Processing proposals `kind` select, and the relation property `sourceThread` from Processing proposals to Threads (`many_to_many`, `owner: system`, owner process the Processing proposals module, one-directional), on fresh installs in the seed step that runs once both databases exist, and for existing tenants in `mail/threadTaskProposalCutoverMigration.ts` exporting `runThreadTaskProposalCutoverMigration(pool)`, registered after the Threads tasks cutover of #1612 in `db/tenantCutoverMigrations.ts`. The cutover returns when either database does not exist and adds only what is missing; running it twice changes nothing.
2. In `assertValidEnvelopeForCard`, for a `kind = mailThread` card: require a `database` envelope whose target is the Tasks database and whose `properties` contain a non-empty `name` (up to 500 characters) and optionally a calendar `date`, and nothing else; reject `relations`; resolve the card's `sourceThread` edge (a card without one is a validation error on `sourceThread`). Revise therefore keeps the same constraints.
3. In `confirmProposalWithClient`, for a `mailThread` card: instead of `createItemWithClient`, call the exported function of #1900 with the source Threads item, the envelope's `name` and `date`, and the user as writer; `resultItemId` is the new task and `resultLabel` its name. A deleted source Threads item answers 409 `conflict` before anything is written. Reject is unchanged. The idempotent return of an already confirmed card is unchanged.
4. In `inbox/inboxCardKind.ts`, derive `cardKind` `task` and `baseKind` `task` for a `mailThread` card with a Tasks envelope.
5. Tests: confirming a `mailThread` card creates in one transaction a task with the edited name and date, the Threads.tasks edge, and the thread's project and people as inherited values; a card edited before confirm uses the edited name; a `relations` entry, another property or another target is rejected on revise and on confirm; a deleted source thread gives 409 and no task; a repeated confirm creates nothing twice; a transcript or inbox card confirm is unchanged; the cutover is idempotent; the card derives `task`.

## Scope

### In scope

- The `mailThread` card kind, the `sourceThread` relation with its cutover, the envelope rules for such a card, its confirm through the function of #1900, and its derived card kind.

### Out of scope

- The Semp tool that creates thread task cards: #2035.
- Editing the project or people of the task on the card; they are changed on the task after confirm.
- The task creation route and its inherited values: #1900; keeping people in sync later: #1923.

## Acceptance criteria

- When a user confirms a `mailThread` card, then one transaction creates the task with the card's name and date, the Threads.tasks edge from the source thread, and the thread's project and the conversation's people as inherited values, and the card is `confirmed` with `resultItemId` set to the task.
- When the card's name was edited before confirm, then the task carries the edited name.
- When a revise or confirm of a `mailThread` card carries `relations`, another property, another target or another entity kind, then it is rejected with a validation error and nothing is written.
- When the source Threads item is deleted, then confirm answers 409 and no task exists; the card stays `proposed`.
- When the cutover runs twice, then the second run changes nothing.
- An Inbox card and a transcript card confirm exactly as before.
