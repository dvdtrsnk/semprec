## Context

Model tier rationale: Three relation pairs added to a locked system schema through the established seed-plus-cutover pattern, with existing fixtures for both the seed and the cutover; no new lifecycle, but a schema change on every populated tenant, so the cutover must be idempotent and correct on cardinality.

A transcript belongs to a project and a company and has participants, the same as an Event does. Today the Transcripts database has only two relations: `event` (the inverse of `Events.transcript`) and `speakers` (to People, with the speaker key as edge metadata), created by the seed in `backend/packages/data/src/seed/seedTenDatabases.ts` and, for a tenant seeded earlier, by `runTranscriptsCatalogCutoverMigration` in `backend/packages/data/src/transcription/transcriptsCatalogCutoverMigration.ts` (the system databases are `schema_locked`, so only a code-level cutover can add properties to a populated install). The pattern for a single-valued many-to-one relation is `Companies.projects` (property A, the "one" side, `one_to_many`) with the single-valued inverse `Projects.company`.

This issue adds the storage the transcript needs: a project, a company and participants, as relations separate from `speakers` (a participant of the recording is not necessarily a mapped speaker). The values are user-owned relations; taking them over from the Event is #1697, writing the recording's project at creation is #1696, and filtering the transcript list by them is #1581.

Decisions:

- `Transcripts.project` and `Transcripts.company` are single-valued (a transcript has at most one project and one company). The "many" side is `Projects.transcripts` and `Companies.transcripts`, which are property A of `one_to_many` definitions.
- `Transcripts.people` is `many_to_many` with the inverse `People.transcripts`.
- All six properties are `owner: user`; later changes of who may write them (inherited values) are made by #1697.

## Task

Load `db-migrations`, `canonical-keys` and `testing`.

1. Seed: in `seedTenDatabases.ts` add three `relate(...)` calls after the existing Transcripts relations: Projects `transcripts` (A) with inverse Transcripts `project`, `one_to_many`; Companies `transcripts` (A) with inverse Transcripts `company`, `one_to_many`; Transcripts `people` with inverse People `transcripts`, `many_to_many`. Add the property names to `backend/packages/data/src/seed/i18n/en.json` and `cs.json` (`property.transcripts.project.name`, `property.projects.transcripts.name`, `property.transcripts.company.name`, `property.companies.transcripts.name`, `property.transcripts.people.name`, `property.people.transcripts.name`).
2. Cutover: extend `runTranscriptsCatalogCutoverMigration` with the same three pairs for a populated tenant, in the style it already uses for `speakers` (raw SQL because the helper enforces `schema_locked`): for each pair that is missing, insert both property rows, the `relation_definitions` row (`property_id_a` the "one" side for the two `one_to_many` pairs, `cardinality` as above) and point both properties' `config` at the relation definition and the target database. It does nothing when the target database does not exist yet, and a second run changes nothing. Keep the table lock the function already takes.
3. Tests: extend `backend/packages/data/src/transcription/__tests__/transcriptsCatalogCutoverMigration.test.ts` (cutover creates the three pairs on a database seeded without them, is idempotent, leaves existing `event` and `speakers` untouched) and add a seed test that a fresh install has them; a relation test that a second company for one transcript is refused with `cardinality_violation`, a second project likewise, while several people are accepted and appear from both sides.

## Acceptance criteria

- On a fresh install, Transcripts has `project`, `company` and `people` relations whose inverses `transcripts` exist on Projects, Companies and People.
- On a populated tenant, the cutover adds the same properties and relation definitions without changing any existing edge, and running it again changes nothing.
- A transcript can have one project and one company; a second value is refused with `cardinality_violation`. A transcript can have several people.
