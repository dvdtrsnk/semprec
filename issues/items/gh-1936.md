**Model tier:** medium

## Context

Model tier rationale: Extends an existing validated ref schema with one new optional field and one resolution path, within the fixtures of the message-ref store, but the cross-check between message and run must be right for tenant isolation, so medium rather than low.

A row of the project run list can be dragged into the chat as an attachment ("this run"). Semp message refs are defined by #1369 and validated and stored by #1682; a ref of kind `agentRun` identifies a run by `agentRunId`. For a heartbeat or MCP run that is enough. For a chat run it is not: the list (#1932) shows one row per answer, but the session run behind it holds the entire conversation, so attaching only the run would give Semp all of it instead of the one answer the user dragged.

This issue lets the `agentRun` ref carry the answer. Decision: `messageId` is optional on an `agentRun` ref; tick and MCP rows are attached without it, chat answer rows with it.

## Task

Load `canonical-keys`, `io-hardening`, `state-writes` and `testing`.

1. Extend the `agentRun` variant of the message ref schema from #1369 with an optional `messageId` (uuid). The kind stays `agentRun`, field names stay English camelCase.
2. In the validation step from #1682, when `messageId` is present, require that the message exists in the caller's tenant, is an assistant message, and belongs to the thread of the run named by `agentRunId`. A message that is missing, foreign (other tenant) or that does not belong to that run is rejected with the same validation error the store already returns for an unknown ref target, indistinguishable between the two cases.
3. Store the ref with `messageId` in the same shape as other refs, and return it unchanged in thread history.
4. When Semp's context is built from an `agentRun` ref that carries `messageId`, resolve it to that answer only (the answer's question, steps summary and result), not the whole session. Without `messageId` the behavior of #1682 is unchanged.
5. Reject `messageId` on any ref kind other than `agentRun`.

## Scope

### In scope

- The optional `messageId` on `agentRun` refs: schema, validation, storage and context resolution.

### Out of scope

- The list rows and their `messageId`: #1932.
- Resolving ref labels and trash state in thread history: #1684.
- Refs to messages of other kinds, or attaching several answers in one ref.

## Acceptance criteria

- When a ref `{ kind: "agentRun", agentRunId, messageId }` is posted with an assistant message of that run, it is accepted, stored and returned unchanged in history.
- When `messageId` names a message of another run, a user message, an unknown id or a message of another tenant, the post is rejected with the same error in every case.
- When `messageId` is present on a non-`agentRun` ref, the post is rejected.
- When the ref has no `messageId`, validation and context behave exactly as before.
- When Semp reads a ref with `messageId`, the context contains only that answer, not the rest of the session.
