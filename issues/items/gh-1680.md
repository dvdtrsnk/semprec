**Blocked by:** #1400, #1679
**Model tier:** medium

## Context

Model tier rationale: A read-only endpoint computed by replaying CRDT history with bounded cost; it builds on existing history primitives, but replay correctness needs fixtures.

After the assistant edits a page the user should see what changed. Page history is stored as `doc_history_updates` rows holding only the update bytes, the author (`created_by`) and the time (`backend/packages/data/src/docs/docPersistence.ts`); block ids are not stored and must be obtained by replaying the updates onto the nearest checkpoint, the way `openDocVersionAt` in `docs/docHistory.ts` does (30-day retention). Blocks written by a proposal the user confirmed are stored with author `user` (#1400; the confirm paths are switched by #1681 and #1981), so filtering on `ai_agent` returns only direct assistant writes.

This issue adds `GET /api/items/:id/page/changes?since=&by=ai_agent` returning `[{ at, blockIds, kind }]` with `kind` one of `insert`, `update`, `delete`, computed by replaying the history from the checkpoint at or before `since` and comparing the block map before and after each update. Reversal uses `page.restoreVersion` (#1617).

Decision: the endpoint reports exactly the stored authors. Blocks inserted by a user-confirmed proposal are stored with author `user` (decided by the product owner), so they do not appear under `by=ai_agent`; that Semp proposed them is recorded on the Inbox card, not in this list.

Shared-file ordering: this issue also waits for #1679 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `io-hardening`, `error-handling` and `testing`.

1. Add `listPageChanges(pool, docId, { since, by })` in `docs/` that opens the checkpoint at or before `since`, applies `doc_history_updates` in id order, and for each update with the requested `created_by` emits a change entry from the difference of block maps (new ids are `insert`, removed ids `delete`, changed fields or children `update`). One entry per update; consecutive updates are not merged.
2. Add the HTTP route `GET /api/items/:id/page/changes` (query: `since` ISO 8601 required, `by` one of `user`, `ai_agent`, `system`, default `ai_agent`, optional `limit` bounded). Require read access to the item's database as for any item read; `since` older than retention gives 410 `history_not_retained`; a future `since` gives 400; an item without a page gives an empty list.
3. List the route in `routeMatrix.ts` and the tenant isolation test.
4. Tests: an insertion, an edit and a deletion by the assistant yield `insert`, `update`, `delete` with the right block ids; user edits, including an update written with author `user` by a confirmed proposal, are excluded with `by=ai_agent` and listed with `by=user`; retention and validation errors; a foreign tenant gets 404.

## Acceptance criteria

- When the assistant inserted, edited and deleted blocks, then the endpoint with `by=ai_agent` returns entries of kind `insert`, `update` and `delete` with the affected block ids.
- When a block was written with author `user` by a confirmed proposal, then it is not listed with `by=ai_agent`.
- When `since` is older than the retention window, then the response is 410 `history_not_retained`.
- When the item belongs to another tenant, then the response is 404.
