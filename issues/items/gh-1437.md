## Context

Model tier rationale: One pure classification function applied to two read views plus a small discriminator added to the MCP outcome write, all covered by existing approval fixtures, with no new lifecycle or isolation contract.

When approved execution of a request does not happen, the request ends with `execution_status = 'conflict'` and a payload in `execution_result_jsonb` (`backend/packages/data/src/mcp/approvalRequestsStore.ts`). For a generic operation, `terminalizeApprovalRequestAsConflict` writes `{ error: { code: "version_conflict", details } }` where `details` holds `currentResource` and, when the choke point rejected the replay, `reason` (the `ChokePointError` code, for example `not_found`, `owner_violation`, `database_archived`); no `reason` means the resource snapshot differed from the one approved. For an MCP call, `recordApprovalRequestOutcome` writes a plain string and `settleStaleApprovalRequestClaim` writes a fixed "unknown outcome" string, so the failure causes are indistinguishable. The decision view returned by `PATCH /api/approval-requests/:id` (`toApprovalRequestDecisionView` in `backend/packages/data/src/mcp/approvalRequestsQueue.ts`) deliberately hides the execution result, so a client can show "conflict" but never why.

This issue adds one derived field, `conflictReason`, that names the reason as a stable key, so a client can say why an approved request was not carried out. It reuses no other issue's output; #1887 and #1862 read the same field and the same mapping for the step state of a run.

Decision: the field is a translation key `{ key }` only, never raw error text or values from the arguments or the resource, because the execution result can contain both.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `approvalConflictReason(executionStatus, executionResult)` in a new `backend/packages/data/src/mcp/approvalConflictReason.ts`, returning `{ key: string } | null` (`null` unless `executionStatus === "conflict"`). Mapping for generic operations: no `reason` in the details gives `approval.conflict.changed`; `not_found` gives `approval.conflict.deleted`; `owner_violation` gives `approval.conflict.provenanceChanged`; `database_archived` gives `approval.conflict.archived`; any other reason gives `approval.conflict.other`. Mapping for MCP: grant revoked or registration/server inactive gives `approval.conflict.toolUnavailable`; the tool call itself failing gives `approval.outcome.failed`; a stale-claim settlement gives `approval.conflict.other`.
2. So that MCP cases are distinguishable, make the MCP outcome write record a closed `outcomeKind` (`toolUnavailable`, `callFailed`, `staleClaim`) next to the text in `execution_result_jsonb`: change `recordApprovalRequestOutcome` and `settleStaleApprovalRequestClaim` (and their call sites in `approvalRequestExecution.ts`) accordingly. Rows written before this change fall back to `approval.conflict.other` for MCP and map by `reason` for generic operations.
3. Add `conflictReason: { key: string } | null` to `ApprovalRequestDecisionView` and `ApprovalRequestQueueEntry`-style views that expose `executionStatus` in `approvalRequestsQueue.ts`, filled from the function above. The execution result itself stays out of every view.
4. Export the function from `backend/packages/data/src/index.ts` for the step state derivation.

## Scope

### In scope

- The classification function, the MCP outcome discriminator, and `conflictReason` on the decision view.

### Out of scope

- The single-request read and pending count endpoint: #1786.
- Using the mapping on run steps: #1862 and #1887.
- Posting the outcome into a thread: #1772.
- Client strings for the keys (the client owns the catalog).

## Acceptance criteria

- A generic request that conflicted because the snapshot differed returns `conflictReason.key = "approval.conflict.changed"`; with reason `not_found`, `owner_violation` or `database_archived` it returns `deleted`, `provenanceChanged` or `archived`; with any other reason it returns `approval.conflict.other`.
- An MCP request whose grant was revoked before execution returns `approval.conflict.toolUnavailable`; one whose tool call errored returns `approval.outcome.failed`.
- A request that is not in `conflict` returns `conflictReason: null`.
- No view contains the execution result text or argument values.
