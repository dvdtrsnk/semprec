## Context

Both long-lived queue runtimes start graphile-worker through `runWorker` (`backend/packages/queue/src/index.ts` lines 250-252), which forwards `RunnerOptions` untouched; neither `createApiQueueRuntime` (`backend/services/semprec-api/src/queueRuntime.ts` lines 66-71) nor `createAgentsQueueRuntime` (`backend/services/semprec-agents/src/queueRuntime.ts` lines 42-46) nor the transcribe runtime passes `concurrentJobs`, so graphile-worker's default of 1 applies: each process runs one job at a time. A mail sync, a library-metadata fetch, a notification fanout and the every-minute `observabilityCheckSystem` all queue behind each other, and one slow job delays the health check.

Raising concurrency exposes the second half: `semprec.tick`, the Inbox action, declares `SEMPREC_TICK_QUEUE_NAME = "semprec-tick"` (`backend/packages/data/src/inbox/inboxTickAction.ts` line 30, "all Inbox ticks serialize against each other"), but that constant is only ever put into an affinity map by tests (`__tests__/inboxTick.test.ts`). Production builds every choke point with the default `createActionQueueAffinity()` (`backend/packages/data/src/scheduler/actions.ts` lines 34-36), which returns an *empty* `Map`: `createChokePoint` (`chokePoint/chokePoint.ts` line 21), `genericOperationGateway.ts` line 98, and `triggerOnItemEventHeartbeats`' own default (`scheduler/schedulerStore.ts` line 308) all route ticks with `queue_name = NULL`. Two ticks for the same Inbox item (a capture followed by a quick edit) would then run concurrently, both observe "no proposal yet" and create two Processing-proposal cards. #676 moves the tick's LLM call out of its transaction and re-checks for an existing card in the write transaction, which narrows but does not close the race (two write transactions can still both see no card); serialization per queue is what closes it. `docs/adr/2026-09-19-task-queue-affinity-routing.md` covers which *runtime* owns a task; this issue is about which *queue* serializes it.

The tick constants cannot be imported into `actions.ts` directly: `inboxTickAction.ts` → `chokePoint/itemWrites.ts` → `scheduler/schedulerStore.ts` → `scheduler/actions.ts` is a value-import chain, and `backend/dependency-cruiser.rules.json` forbids any cycle through `packages/data/src/chokePoint/`. Sibling issue F4a edits `registerTask`, directly above `runWorker` in the same file, and sibling F7a appends the `.env.example` section this issue adds a line to, so this issue lands after both.

## Task

1. **Leaf module for the tick keys** — add `backend/packages/data/src/inbox/inboxTickKeys.ts` (new) holding `SEMPREC_TICK_ACTION_ID = "semprec.tick"` and `SEMPREC_TICK_QUEUE_NAME = "semprec-tick"` with their current doc comments; `inboxTickAction.ts` re-exports both (`export { SEMPREC_TICK_ACTION_ID, SEMPREC_TICK_QUEUE_NAME } from "./inboxTickKeys.js"`) so every existing importer and `__tests__/publicSurface.test.ts` are unaffected.
2. **Production affinity map** — `createActionQueueAffinity()` in `scheduler/actions.ts` returns `new Map([[SEMPREC_TICK_ACTION_ID, SEMPREC_TICK_QUEUE_NAME]])` (importing from `../inbox/inboxTickKeys.js`); update its docstring: this is the production routing table, callers pass an explicit map only to override it. Change `triggerOnItemEventHeartbeats`' default parameter (`schedulerStore.ts` line 308) from `new Map()` to `createActionQueueAffinity()` so the direct `createItemWithClient` / `createInboxItemWithClient` / `inboxTypesStore.ts` paths that pass no map route ticks too. No other call site changes.
3. **Concurrency** — in `backend/packages/queue/src/index.ts`, export `QUEUE_CONCURRENCY_DEFAULT = 4` and `resolveQueueConcurrency(env: NodeJS.ProcessEnv): number` (`QUEUE_CONCURRENCY` unset or empty → 4; a positive integer string → that value; anything else → `throw new Error("QUEUE_CONCURRENCY is not a positive integer: <raw>")`). `runWorker` becomes `graphileRun({ concurrentJobs: resolveQueueConcurrency(process.env), ...options })` — an explicit `options.concurrentJobs` wins. In `backend/services/semprec-transcribe/src/queueRuntime.ts` line 39 pass `concurrentJobs: 1` with a comment (one ffmpeg/ASR pipeline per host; the `TRANSCRIPTION_JOB` handler is CPU- and disk-bound). The api and agents runtimes do not change.
4. **Documentation** — in `deploy/shared/.env.example`, add `QUEUE_CONCURRENCY=4` with a two-line comment (what it bounds, that transcribe ignores it) at the end of the `# ---- Listeners ----` section that sibling issue F7a appended at the end of the file.
5. **Tests**:
   - `backend/packages/queue/src/__tests__/queueConcurrency.unit.test.ts` (new, unit): `resolveQueueConcurrency({})` → 4; `{ QUEUE_CONCURRENCY: "8" }` → 8; `"0"`, `"-1"`, `"abc"`, `"2.5"` → throw naming the variable.
   - `backend/packages/data/src/__tests__/inboxTick.test.ts` (existing, integration): the case "with no queue affinity supplied, the job runs unaffinitized (queue_name is null)" (lines 226-234) inverts — with no map supplied the job's `queue_name` is `semprec-tick`; add a case that `createChokePoint(pool)` with defaults routes update and delete ticks to `semprec-tick`; the explicit-map cases stay as they are.
   - `backend/packages/data/src/__tests__/queueConcurrency.test.ts` (new, integration, real graphile schema): register a task `probe` through `registerTask` that records `start`/`end` timestamps per job and sleeps 300 ms; `runWorker({ pgPool, taskList, noHandleSignals: true })` with `QUEUE_CONCURRENCY` unset; enqueue two `probe` jobs with `queueName: "semprec-tick"` and two with no queue; wait for all four; assert the two `semprec-tick` runs do not overlap (`second.start >= first.end`) and the two unaffinitized runs do overlap (`second.start < first.end`). Stop the runner.

## Scope

### In scope
- The production tick routing, the concurrency knob, and the tests above.

### Out of scope
- A per-item tick queue (`semprec-tick:<itemId>`) — deliberately not done; the global queue is the documented contract and the Inbox is single-user capture.
- Registering the tick handler in the api runtime (#641) and bracketing its LLM call (#676).
- Supersession handling in `registerTask` (F4a) and failed-row pruning (F4b).
- Any change to `createApiQueueRuntime` / `createAgentsQueueRuntime`.

## Acceptance criteria

- When two Inbox captures for different items and one edit of the first item happen within a second on a production-configured process, `graphile_worker.jobs` shows all three `heartbeatFireCore` jobs with `queue_name = 'semprec-tick'`, at most one of them runs at any moment, and the first item ends up with exactly one Processing-proposal card.
- When `QUEUE_CONCURRENCY` is unset, `semprec-api` and `semprec-agents` each run up to 4 unaffinitized jobs at once; `semprec-transcribe` runs 1.
- When `QUEUE_CONCURRENCY=abc`, each runtime fails at startup with an error naming the variable.
