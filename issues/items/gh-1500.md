**Model tier:** high

## Context

Model tier rationale: It changes the central decision path of the tick (what happens to an untyped item) and its staleness and fingerprint rules, with a confidence threshold and an AI-driven branch; a wrong detail either loops recomputation or deletes a proposal on the next edit.

An Inbox item without a type is valid ("Add a Linear MCP", a photo of a receipt, a goal with a date). Today the tick (`readTickSnapshot` in `backend/packages/data/src/inbox/inboxTickAction.ts`) resolves the type only from the `type` edge; with no edge it writes a `needsClarification` card with no proposal, no candidates and no AI call (`writeNeedsClarification`), and repeats that on every edit. The product wants the opposite: the assistant works out what the item is, proposes it directly when it is sure, and asks only when it is not.

#1434 builds the model-backed `computeProposal` and registers the tick; #1451 adds the card properties `recognizedTypeId` (text) and `typeCandidates` (json) used here. The `type` relation of an Inbox item is user-owned (`docs/adr/2026-09-10-single-writer-ownership-model.md`), so the tick can never write it; picking a type is the user's action (the replacement route, #1947). Where a type is chosen by a user, `typeCandidates` is only read there.

Decision: recognition runs for an untyped item, including every time its text changes (the fingerprint changes), and is the only writer of `recognizedTypeId` and `typeCandidates`. The `type` edge is never written.

Decision: the model returns ranked candidates, each either `{ typeId, confidence }` (an active Inbox item type of the tenant, whose catalog is part of the request) or `{ targetDatabaseKey, confidence }` (one of `areas`, `projects`, `tasks`, `people`, `files`, `events`, `healthRecords`, `companies`, `mcpServers`), with `confidence` between 0 and 1. Candidates with an unknown type id, an inactive type or an unknown key are dropped.

Decision: the threshold is a single constant `RECOGNITION_CONFIDENCE_THRESHOLD = 0.7`, kept in one place so it can be tuned without a schema change.

Decision: at or above the threshold the tick computes the proposal for the best candidate exactly as for a typed item and stores `recognizedTypeId` (type-id candidates only; a direct target is remembered by the stored envelope's target database and needs no extra field). Below it the card is `needsClarification` with a localized `reason` and up to four distinct `typeCandidates` `{ typeId, label, targetDatabaseKey }` taken from the ranked valid type-id candidates, padded to two with unused valid active types in list order. If fewer than two valid active types exist, offer all that exist (zero or one), keep `needsClarification` with no proposal, and explain the shortage in the localized reason; never invent or duplicate types. Valid types belong to the tenant, are active and undeleted, and have a supported processing method and a valid target for that method.

Decision: new fingerprints remain v2 (#1606). For an untyped source use `computeInboxFingerprintV2` with `typeId: ""` and the current source text, date, time, attachment hashes and transcribedText (still `""` on this tip); never include the recognized type or direct target. Preserve `isFingerprintCurrent` compatibility for stored v1 values, using `legacyEmoji: ""` and the source text for an untyped source. Recognition therefore cannot change its own fingerprint or trigger a recomputation loop; `fingerprint.ts` behavior is unchanged.

Decision: an item with neither text nor any recognized attachment content (supplied by a later attachment-extraction step once it exists) has nothing to recognize and goes to `needsClarification` without a model call, as today.

## Task

Load `state-writes`, `error-handling`, `ai-gateway` and `testing`.

1. In `readTickSnapshot` preserve the existing typed path when a valid `type` edge resolves. For an untyped item, honor the existing locked-card and fingerprint gates first: an unchanged fingerprint reuses the existing recognition result without a call. Otherwise enter recognition again, including after every text change and every change covered by v2; neither the existing card's `recognizedTypeId` nor its recognized direct target bypasses recognition after such a change. Preserve the no-text/no-content exception. Add `recognition: true` and the valid active-type catalog (id, name, emoji, processing method, target) to the snapshot and to `ProposalComputationInput` for this recognition path.
2. In `proposalComputation.ts` (#1434) add a recognition mode: an extended response schema with ranked `candidates`, the instruction text, and the filtering of invalid candidates. Return `{ candidates, ...proposal result for the best one }`; a single call serves both the recognition and, above the threshold, the proposal.
3. In `inboxTickAction.ts` apply the threshold. At or above: build the envelope as for a typed item (type-id candidate: the type's processing method and target; direct target: `entityKind: "database"` with that database's id), write the card with `recognizedTypeId` (when applicable), and clear `typeCandidates`. Below (including no valid candidates): write `needsClarification` with up to four distinct valid type candidates, padding to two from unused valid active types in catalog order; if only zero or one exists, offer that many and explain the shortage in the localized reason. Set `recognizedTypeId` null, no proposal and the localized reason of #1495 when that issue is present. Never invent types or use a direct target as a type candidate.
4. Add `recognizedTypeId` and `typeCandidates` to the tick's `allowedSystemKeys`. Keep the staleness check (`writeTickResult` and its shared source check) comparing the same v2 source fingerprint and source type-edge resolution captured before the call: an untyped snapshot must still have no type edge, and a typed snapshot must still resolve the same source type. Do not compare an untyped source with the newly recognized type or target as if it were a source edge. Store the source v2 fingerprint on the recognition result, including clarification cards, so an unrelated edit cannot change or repeatedly recompute it.
5. Tests with a stubbed computation: an untyped item with confidence 0.9 produces a `proposed` card and the `type` edge stays absent; a later unrelated update leaves the card unchanged; a text edit reruns recognition for both a prior recognized type and a prior direct target; changes to date, time or attachment hashes rerun recognition under v2 while stored v1 compatibility is preserved; setting the recognition result does not change the source fingerprint; a source edit or type-edge change during computation discards the stale result; confidence 0.5 produces `needsClarification` with two to four distinct candidates when at least two valid active types exist; an unknown or archived type id is ignored; one valid model candidate gets padded when another catalog type exists; catalogs with zero or one valid active type yield respectively zero or one candidate, no proposal and a localized shortage reason; an item with no text and no content makes no call; a locked card is never recomputed; the tick never writes `Inbox.type`.

## Scope

### In scope

- Recognition of an untyped item, the confidence threshold, the two outcomes and the unchanged-fingerprint rule.

### Out of scope

- The card properties (#1451), the computation and its context (#1434, #1987) and the reason text (#1495).
- Replacing an item's type from a candidate tile and recomputing (#1947).
- Extracting content from attachments and transcribing voice notes (#1980).
- Creating hidden system types for projects, areas or other direct targets.

## Acceptance criteria

- When an untyped item is recognized with confidence at or above 0.7, then a `proposed` card exists for the best candidate, the item still has no `type` edge, and a later update that leaves the fingerprint current leaves the card as it is. A changed source fingerprint reruns recognition even if the card already has a recognized type or direct target; new results store v2 with an empty source type id, preserving #1606 inputs and stored-v1 compatibility.
- When confidence is below 0.7 (or no valid candidates remain), then the card is `needsClarification` with a reason and two to four distinct valid type candidates when at least two exist. With fewer valid active types, it carries all that exist (zero or one), no proposal and a localized reason explaining the shortage; no type is invented or duplicated.
- When the model names a type id that is unknown or archived, then it is not offered or used.
- When the item has no text and no content, then no model call is made.
