**Blocked by:** #1780
**Model tier:** medium

## Context

Model tier rationale: One delayed-job mechanism on existing queue primitives with a recompute function from the blocker, with the care that the job must be correct when the end moves or the queue runs late.

A task hidden inside its events must come back when the last of them ends (#1780 stores `hiddenUntil` and recomputes `effectiveDate`). Nothing writes at that moment: realtime sends only writes, so without a write a client would not learn that the task is visible again, and the same `updatedAt` would even be skipped as a stale echo. The queue (`backend/packages/queue/src/index.ts`) supports `enqueueJob` with `runAt`, `jobKey` and `jobKeyMode: "replace"`; task names are camelCase entries of `CORE_TASK_NAMES` with an affinity and a `TASK_TENANCY` entry; a replace does not cancel a job that is already running.

This issue adds the job that recomputes the state at the end time and so makes the write that reveals the task. The visibility filter that lists apply (hidden until empty or before now) already keeps results right if the queue runs late; the job only ensures the realtime invalidation and the final stored state.

Decisions:
- The job never blindly clears `hiddenUntil`: it recomputes from the current edges and event ends and writes the result, so an event that was extended in the meantime keeps the task hidden and the job enqueues itself again.
- The enqueue happens inside `recomputeTaskHostState` whenever it leaves `hiddenUntil` set.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add the task `taskHostEventEnded` to `CORE_TASK_NAMES` (as `TASK_HOST_EVENT_ENDED`), `CORE_TASK_AFFINITY` (`api`) and `TASK_TENANCY` (`tenant`) in `backend/packages/queue/src/index.ts`, with its handler registered in `backend/packages/data/src/worker.ts`.
2. In `recomputeTaskHostState` (#1780), after computing the state, when the resulting `hiddenUntil` is set, enqueue `taskHostEventEnded` with payload `{ taskId }`, `runAt` equal to `hiddenUntil`, `jobKey` `taskHostEventEnded:<taskId>` and `jobKeyMode: "replace"`, in the same transaction.
3. The handler recomputes the task through `recomputeTaskHostState` in the tenant scope; a missing or trashed task, or a state that did not change, is a completed no-op. If `hiddenUntil` is still in the future the recompute has enqueued the next run.
4. Tests: a task in an event ending at 14:00 is revealed by the job (`hiddenUntil` null, a realtime item invalidation) once the clock passes 14:00; extending the event after the enqueue does not reveal the task early and the job runs again at the new end; a job that runs a few seconds before the end re-enqueues itself; a trashed task or an event deleted in between does not fail the job; the job key makes repeated recomputes leave one pending job.

## Touches

## Scope

### In scope

- The end-of-event job, its enqueue and its recompute-then-write behavior.

### Out of scope

- The stored derivation and its other triggers: #1780.
- Deleting and restoring a host event: #1819.
- The list and calendar filters that hide tasks: #1798, #1880.

## Acceptance criteria

- When the last host event of a task ends, then the job writes `hiddenUntil` null and the client receives an invalidation, so the task is back in lists.
- When an event is extended after the job was enqueued, then the task is not revealed early and the job runs again at the new end.
- When the job runs slightly before the end time, then it enqueues itself again.
- When the task is trashed or the state is unchanged, then the job completes without a write.
