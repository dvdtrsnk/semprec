## Context

Model tier rationale: The link format, adapter methods, route, page states and ADR content are all specified exactly.

The backend has served password reset since issue #142, but the web client has no page for it, and the emailed link points at a route the client does not serve:

- `POST /api/auth/password-reset/request` with `{ email }` always answers `200 { ok: true }`, for a known and an unknown address alike (`backend/services/semprec-api/src/authHandler.ts:174-188`).
- `POST /api/auth/password-reset/consume` with `{ token, newPassword }` answers `200 { ok: true }` (`authHandler.ts:190-206`). A rejected token is a `400` whose body is `{ error, code }` with `code` one of `password_reset_token_invalid`, `password_reset_token_expired`, `password_reset_token_consumed` (`backend/packages/data/src/errors.ts:142-163`); a password shorter than 8 characters is a `400` with `code: "validation_failed"` and does not consume the token (`backend/packages/data/src/auth/passwordResetActions.ts:118-123`). A successful reset revokes every session of the user (`passwordResetActions.ts:137`).
- The mailed link is `<APP_BASE_URL>/reset-password?token=<token>` (`passwordResetActions.ts:31-38`). Caddy serves `index.html` for that path (`deploy/Caddyfile`, final `handle` block), but the client routes only on `?page=` query parameters (`web/src/main.tsx:28-66`), so the link opens an empty app. The token also travels in the query string, where it reaches access logs and `Referer` headers.

Decision for the multi-user program (the invitation link of #1040 already follows it): secret-bearing links carry their token in the URL **fragment** (`#token=…`), which the browser never sends to the server or in a `Referer`, and the page clears it from the address bar on mount (as `SetupWizard` does for its query token, `web/src/views/setup/SetupWizard.tsx:32-39`). The new link is `<APP_BASE_URL>/?page=password-reset#token=<token>`. The token is base64url (`backend/packages/data/src/auth/token.ts:19`), so it needs no encoding in the fragment.

#1024, #1041 and #1073 edit `passwordResetActions.ts` (push revocation, non-active tenants — whose reset fails as `password_reset_token_invalid` — and per-IP throttling); this issue changes only the link it builds. Adapter pattern: `docs/adr/2026-09-29-web-client-calls-the-api-through-operations-adapters.md`; the `/api/auth/*` adapter is `web/src/api/authOperations.ts`.

## Task

Load `canonical-keys` (new `?page=` key and user-facing strings), `error-handling` (status-to-outcome mapping in the adapter and the page) and `adr-conventions` (step 8) before starting.

1. **Link format (backend)** — in `backend/packages/data/src/auth/passwordResetActions.ts`, replace `PASSWORD_RESET_PATH` and `buildPasswordResetUrl` (`:31-38`) so the link is built as `new URL("/", appBaseUrl)`, `url.searchParams.set("page", "password-reset")`, `url.hash = "token=" + token`. The query string carries no token. Update the two assertions and helpers that parse the token from the query: `backend/packages/data/src/__tests__/passwordResetActions.test.ts` (`tokenFromUrl` at `:39-43`, assertion at `:69`) and `backend/services/semprec-api/src/__tests__/authHandler.test.ts` (`tokenFromResetUrl` at `:39-43`, assertion at `:439`). Read the token with `new URLSearchParams(new URL(url).hash.slice(1)).get("token")`.
2. **Adapter** — extend `AuthOperations` in `web/src/api/authOperations.ts` (and its doc comment, `:4-9`) with:
   - `requestPasswordReset(email: string): Promise<void>` — `POST {baseUrl}/auth/password-reset/request`, JSON body `{ email }`, `credentials: "same-origin"`. Resolves on any 2xx. Any other status throws `OperationError("retryable", <server error string or "Request to /auth/password-reset/request failed with <status>">, status)`.
   - `resetPassword(input: { token: string; newPassword: string }): Promise<void>` — `POST {baseUrl}/auth/password-reset/consume`, JSON body `{ token, newPassword }`. Resolves on 2xx. A `400` whose body parses as `{ error: string, code: string }` with `code` in the three `password_reset_token_*` values throws `OperationError("unavailable", error, 400)`. Every other non-2xx throws `OperationError("retryable", <server error string or the generic message>, status)`.
   - Transport failures throw `retryable`, as the existing `send` helper does (`:48-54`). A response body can be read only once: for `resetPassword`'s non-2xx branch, read it once and `safeParse` it with a zod schema `{ error: z.string(), code: z.string() }`; elsewhere reuse `readErrorMessage` (`:107-116`). No unchecked cast.
3. **Route** — in `web/src/main.tsx`, when `page === "password-reset"`, build `passwordReset = { token }`, where `token` is `new URLSearchParams(window.location.hash.slice(1)).get("token")`, with an empty string normalised to `null`. Add the route to the composition-root doc comment (`:14-27`).
4. **App** — in `web/src/App.tsx`, add `export interface PasswordResetRoute { token: string | null }` and an optional `passwordReset` prop. Render `<PasswordResetPage token={…} auth={auth} />` outside `SessionGate`, exactly like `setup` (`:93-95`), and skip the session bootstrap for it (`useSession`'s `skip`, `:87`).
5. **Page** — add `web/src/views/passwordReset/PasswordResetPage.tsx` (plus `passwordReset.css` if it needs styles). All labels come from i18n.
   - `token === null`: an email form. Submitting calls `requestPasswordReset`. On success, the form is replaced by a confirmation that does not say whether the address has an account. On failure, the form stays with the error message (`role="alert"`).
   - `token !== null`: on mount, remove the fragment from the address bar with `window.history.replaceState(window.history.state, "", url)`, where `url` is the current URL with `hash = ""`. No history entry is added, and `?page=password-reset` stays. The page keeps the `token` prop. A new-password form (`type="password"`, `autoComplete="new-password"`) calls `resetPassword`:
     - success → a success state that says the password changed and every session was signed out, with a link `?page=login`;
     - `unavailable` → an invalid-link state ("invalid, expired or already used"), with a link `?page=password-reset` to request a new one;
     - `retryable` → the form stays enabled with the message, so the user can retry with the same token.
   - Controls are disabled while a request is pending.
6. **Login link** — in `web/src/views/login/LoginPage.tsx`, add a link `?page=password-reset` (label `login.forgotPassword`) below the form.
7. **i18n** — add `login.forgotPassword` and a `passwordReset.*` namespace to both `en` and `cs` in `web/src/i18n/messages.ts`.
8. **ADR** — add `docs/adr/<YYYY-MM-DD>-secret-link-tokens-travel-in-the-url-fragment.md` (date of your commit, `status: accepted`, `area: [backend, web]`), unless `docs/adr/` already holds an ADR recording this rule (check with `grep -ril fragment docs/adr/`). It records:
   - **Decision:** a link that carries a secret token puts it in the fragment (`#token=`), not the query string, and the page that reads it clears the fragment on mount with `history.replaceState`.
   - **Reason:** query strings reach access logs and `Referer` headers; fragments reach neither.
   - **Rejected alternative:** query tokens plus log scrubbing — the setup wizard's existing `?token=` stays as it is.
   - **Consequences:** the invitation link (`/?page=invite#token=`) and the reset link follow the rule.
9. **Tests** — see the acceptance criteria. Update the `stubAuth` helpers in `web/src/__tests__/App.test.tsx` and `web/src/views/login/__tests__/LoginPage.test.tsx` for the two new methods.

## Acceptance criteria

- When a reset is requested for a known email, the mailed link equals `<APP_BASE_URL>/?page=password-reset#token=<token>`, its query string contains no `token`, and the token read from the fragment resets the password through `POST /api/auth/password-reset/consume` (integration, `passwordResetActions.test.ts` and `authHandler.test.ts`).
- `requestPasswordReset` posts `{ email }` as JSON with same-origin credentials to `/api/auth/password-reset/request` and resolves on 200; a 429 or 500 rejects as `retryable` carrying the status and the server's `error` string; a network failure rejects as `retryable` (web unit, `authOperations.test.ts`).
- `resetPassword` posts `{ token, newPassword }` to `/api/auth/password-reset/consume` and resolves on 200. Each of the three `password_reset_token_*` codes rejects as `unavailable` with status 400; a 400 `validation_failed` rejects as `retryable` with the server's message; a network failure rejects as `retryable` (web unit, `authOperations.test.ts`).
- When the page opens at `/?page=password-reset#token=abc`, the address bar afterwards shows `/?page=password-reset` with no fragment, `window.history.length` is unchanged, and submitting a new password sends `token: "abc"` (web unit, `web/src/views/passwordReset/__tests__/PasswordResetPage.test.tsx`).
- With a token, a successful reset shows the success state and a link to `?page=login`; an `unavailable` rejection shows the invalid-link state with a link to `?page=password-reset`; a `retryable` rejection keeps the form enabled and shows the message (web unit, `PasswordResetPage.test.tsx`).
- Without a token, the email form is shown. After a successful request, the same confirmation appears whatever the address. A rejected request keeps the form and shows the message in an alert (web unit, `PasswordResetPage.test.tsx`).
- With a `passwordReset` route, `App` renders the page without the header and never calls `getSession` (web unit, `App.test.tsx`).
- The login page shows a link to `?page=password-reset` (web unit, `LoginPage.test.tsx`).
- Every new key exists in both `en` and `cs`; `docs/adr/` records the fragment-token rule; `pnpm run verify` passes in `web/` and `backend/`.
