**Blocked by:** #160, #152

## Context

The authenticated transport exists. Thin data changes and durable notifications can now flow over an implicit per-user channel while REST/unread state remains authoritative.

## Task

Standardize transactional NOTIFY on `semprec_events`: core item/database/property/view writes emit only kind, identifiers, operation, and `updatedAt`; document writes emit document and update IDs; notification commits emit the notification ID; payloads stay safely below PostgreSQL's limit. The API fetches referenced durable rows when needed and broadcasts item/schema invalidations to every socket for the owning user, never full item rows. Emit notification frames with the complete notification read-model row to every socket for its user. On client connect/reconnect, define that active views/open items refetch through REST before accepting invalidations and unread notifications refetch through #36. Echoed invalidations remain harmless because clients compare `updatedAt` to cached versions.

## Scope

### In scope

- Transactional publishers, thin user-scoped fanout, durable-notification fanout, client refetch protocol.

### Out of scope

- Fine-grained database/item/view subscriptions, full-row invalidations, and persistent invalidation logs.

## Acceptance criteria

- Rolled-back writes emit no event; committed events cannot precede their state.
- Cross-user delivery is impossible and every invalidation stays a thin reference.
- Integration tests prove lost invalidations heal by bounded active-state refetch and lost notification frames by unread fetch.
