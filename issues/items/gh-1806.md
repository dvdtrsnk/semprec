## Context

Model tier rationale: One known mechanism (a timeline source that maps an existing resolver's output) across the source extension point and an existing resolver, but night boundaries around midnight and daylight-saving changes make the day mapping easy to get wrong.

The calendar timeline (#1717) is assembled from sources registered in `backend/packages/data/src/calendar/timelineSources.ts`. The calendar day view also draws sleep: the end of last night in the morning, the start of tonight in the evening and a "prepare for sleep" reminder. The sleep plan and its per-night exceptions are owned by the sleep module; the function that computes the planned nights in the tenant's time zone is `resolveSleepNights` (#1792), and a single night is edited elsewhere (#1835). This issue adds the sleep source to the timeline; it only reads.

Behavior: for a requested range `[from, to]` the source asks the resolver for the nights `[from - 1 day, to]`, so that a night that starts the evening before `from` and ends inside the range is included, and returns one item per night with `kind` `sleep`, `id` `sleep:<night>` (the night's date key), `readOnly` false, and the resolver's fields `night`, `planId`, `bedTime`, `wakeTime`, `alarm`, `changed`, `bedAt`, `wakeAt` and `prepReminderAt`. A night is one item even when it crosses midnight; the client draws the part that falls in each day.

If sleep is disabled or its "show in calendar" setting is off (both owned by the sleep module's settings), the source returns no nights. A hidden Sleep calendar does not change the response; the client hides by the calendar's `hidden` flag.

Decision: a night crossing midnight is one item, as the resolver returns it, not two day parts.
