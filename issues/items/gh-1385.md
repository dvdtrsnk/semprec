## Context

Model tier rationale: The ADR fixes the authorization and approval contract that every module's agent tools and the mail send path will follow, so a wrong decision propagates into several later implementations.

Agent tools declared by modules are not yet usable. `agentTools` in module manifests (`ModuleAgentToolDescriptor`: name, handler export, optional capability) is only projected by `ModuleRegistry.getAgentTools`; `createAgentSessionFactoryForRun` composes only the generic operations and MCP grants of the project; and `/mcp` exposes only `semprec.<generic operation>`. Without approval an agent may run only non-destructive generic operations (`docs/adr/2026-09-18-non-destructive-generic-operations-bypass-agent-approval.md`); a module tool that writes outside the generic catalog has no rule. Sending mail from an agent or an MCP client is, in code, `assertEmailSendAuthorized` in `mail/send.ts`: an agent without the project property `emailSendAutonomous` gets a 403 and nothing is queued, which is not what the product wants. Per-database grants of projects are introduced by #1810. Module tools are composed into sessions by #1523 and deferred for approval by #1791; the mail tools are #1927 and the send flow is #1913. This ADR also decides the shared rule for the calendar tools (#1957), the Inbox proposal revision tool (#1906) and approval-gated heartbeat tools (#1846), and for MCP exposure (#1580).

## Task

Load `adr-conventions`. Write exactly one new ADR file; no code.

1. Create `docs/adr/YYYY-MM-DD-module-agent-tools-approval-and-grants.md` (creation date) with the frontmatter and sections of `docs/adr/README.md`, status `accepted`, area `backend`. Decide and state, with the alternatives considered:
   - Classification: every module tool declares a risk class from the closed risk class set shared by generic operations, MCP and approval requests and an approval mode: `none`, `always`, or `unlessProjectPermitted`. A tool that only reads, or writes through operations of the non-destructive generic catalog, or creates drafts that nothing sends, needs no approval; a destructive or outbound tool needs approval.
   - Grants: a module tool appears in a run only when the run's project holds the grant of the tool's capability; a read tool needs read grants on the module's databases, a write tool needs write grants, in terms of the per-database grants of #1810. An ungranted tool is absent, not denied.
   - MCP: tools are exposed over `/mcp` only to the extent decided by an addendum owned by #1580; the same classification and grants apply to a run credential; a human session acts with the user's permissions and is not subject to approval; its writes are still recorded as agent (MCP client) writes bound to that user (`writerKind: 'agent'` without run ids, #1415), so audits of agent changes include them.
   - Mail send chapter: an agent or an MCP client with a run credential that sends creates an approval request (risk class `outbound`) instead of failing with a 403. Decided by the product owner: in v1 every such send goes through approval, also when a project has `emailSendAutonomous`; no permission lets a mail leave without approval in v1, and a project written on a thread by an agent or by Semp's sorting never changes this. An MCP client with a human session sends as the user without approval, and the ADR says so explicitly. This chapter replaces the earlier rule that an unpermitted send ends in a 403 without a queued request (issues #27 and #92).
2. State consequences and how a later tool descriptor field maps to the approval mode, without implementing it.
