### Requirement gh-1524: [collection-query 05/12] Sort text with Czech collation and tie-break by title

#### Context

Model tier rationale: One known mechanism (collation on text sort keys) whose risk is keeping the ORDER BY and the keyset predicate identical, which the existing pagination fixtures verify, plus a deploy-time collation availability check.

Text sorts in `backend/packages/data/src/views/sortCompiler.ts` use the database default collation (`postgres:16-alpine`, `deploy/docker-compose.yml`) and no `COLLATE` anywhere, so Czech names do not order by the Czech alphabet ("Chalupa" belongs after "Hrad", "Řeka" after "Rybník") and equal names have no stable secondary order beyond item id. Select and group ordering was handled in #1408, which this builds on in the same file. Time-based sorting by recurrence (#1905), system timestamp sorts (#1594) and the database session zone pin (#1596) build on it.

Decision: when the title is not itself the sort key, ties are broken by title (same collation), then by id. Decision: if ICU collations are not present in the image, create them with `CREATE COLLATION ... provider = icu` activated on deploy, following `docs/adr/2026-09-23-host-asset-dependent-database-features-activate-on-every-deploy.md`.

### Requirement gh-1522: [collection-query 04/12] Add relative date conditions evaluated in the tenant time zone

#### Context

Model tier rationale: A new filter condition whose result depends on the clock and the tenant time zone, added to two copies of the filter tree and the SQL compiler, with day-boundary, week-start and multi-day-range semantics where an off-by-one or a UTC leak silently returns wrong items and stored views change meaning daily.

The filter tree (`backend/packages/data/src/views/filterTree.ts`, mirrored in `backend/packages/shared/src/genericOperations/filterSort.ts`) knows only absolute dates: `before`, `after`, `on_or_*` and `date_range` compile to `::timestamptz` comparisons (`filterCompiler.ts`) in the database session's zone. A collection cannot express "today", "this week", "upcoming", "last 7 days" or "past", so each client would compute absolute bounds itself, saved views would freeze at the day they were saved, and the tenant's time zone (`getSystemTimezone` in `backend/packages/data/src/systemSettings.ts`) would be ignored.

This issue adds one condition, `date_relative`, that is evaluated at query time in the tenant's zone. The shared "today and day bounds in the tenant zone" calendar time module is delivered by #1418 and must be reused rather than reimplemented. It is built on by numeric conditions (#1534), facets (#1759), the quick filters and default sorts declared in manifests (#1647) and the Tasks today view (#1798).

Decision: `last7` is D-7 to D and `last30` is D-30 to D (days inclusive, so 8 and 31 calendar days). Decision: weeks start on Monday and all boundaries are inclusive. Decision: the "Overdue" label for projects is a presentation label of `past`, with no extra status condition.

#### Task

Load `canonical-keys`, `error-handling` and `testing`.

1. Add the condition `{ type: "date_relative", property, endProperty?, preset }` to `FILTER_CONDITION_TYPES`, `FilterCondition` and the zod schema in both `filterTree.ts` and `filterSort.ts` (keep the two identical; `filterSort.unit.test.ts` pins them). `preset` is either one of `today`, `tomorrow`, `thisWeek`, `nextWeek`, `thisMonth`, `upcoming`, `past`, `onOrBeforeToday`, `last7`, `last30`, `thisYear`, `olderThan30`, `beforeNow`, or `{ fromDays: int, toDays?: int }` (days relative to today, inclusive, negative is the past, no `toDays` means no upper bound; `fromDays <= toDays`, both within +/-36500, otherwise 400). `property` and `endProperty` must be date properties; anything else is a 400 with the property as `field`.
2. Semantics, with D = today in the tenant zone: `upcoming` day >= D; `past` day < D; `onOrBeforeToday` day <= D; `today` D; `tomorrow` D+1; `thisWeek` D to the coming Sunday; `nextWeek` next Monday to next Sunday; `thisMonth` D to the last day of the month; `last7` D-7..D; `last30` D-30..D; `thisYear` Jan 1 to Dec 31 of D's year; `olderThan30` day < D-30; `beforeNow` the value as an instant is earlier than now (date-only values compare as day < D). A value is reduced to a calendar day in the tenant zone (a date-only string is used as written; a timestamp is converted with `AT TIME ZONE`), so 00:30 in Europe/Prague belongs to the new day even when it is the previous day in UTC. A null or missing value never matches.
3. With `endProperty`, the condition matches when the interval [`property`, `endProperty` or `property` when empty] intersects the preset's range (a multi-day event running 21 to 23 October matches `today` on the 22nd).
4. In `filterCompiler.ts` compile the condition to day-range comparisons whose bounds are computed once per query from the time module and bound as `$N` parameters (no clock call inside SQL), so a stored `ViewConfig.filter` containing it gives a different result on the next day without being edited. The compile entry points (`compileFilterNode`) receive the tenant zone and "now" through an added context argument; update every caller (`viewQuery.ts`, `itemReads.ts`).
5. Tests with an injectable clock: on Thursday 22 Oct 2026 `thisWeek` is 22-25 Oct, `nextWeek` is 26 Oct-1 Nov, `{ fromDays: 2, toDays: 9 }` is 24-31 Oct, an event 21-23 Oct with `endProperty` matches `today`; at 00:30 Europe/Prague the new day applies; a stored view with `upcoming` changes result on the next day; `past` over projects returns overdue projects and not ones without a date; invalid presets and non-date properties are 400.

### Requirement gh-1526: [collection-query 06/12] Filter relations by emptiness

#### Context

Model tier rationale: It adds two conditions to an existing compiler following the established relation-condition pattern and test fixtures, with the only subtlety being that edges to soft-deleted targets must not count.

Some collection queries need to ask whether an item has any value in a relation at all: "files without a project", "items with no linked person". The filter tree cannot say this. `is_empty` / `is_not_empty` are scalar conditions, and `compileCondition` in `backend/packages/data/src/views/filterCompiler.ts` deliberately rejects them on a relation property with the message that the property must be filtered with `relation_contains` / `relation_not_contains`, which only test for one specific target item. There is no condition for "no edge" or "any edge".

The first consumer is the per-database area filter (#1597): a file or a health record that has no project but carries its own area must match that area, so the filter needs "the project relation is empty" next to "the own area contains X". The second is the "No value" bucket of facets (#1759), and related collections (#1839) and the Tasks today view overview (#1798) depend on it as well.

The condition set exists in two copies that must stay identical: `backend/packages/data/src/views/filterTree.ts` and `backend/packages/shared/src/genericOperations/filterSort.ts`. #1363 already extended both with `relation_path_contains` and extended `FilterProperty`; this issue edits the same files after it lands, which is why it is ordered after it.

Decision: an edge to a soft-deleted item does not count as a value. A file whose only project was deleted counts as having no project. Rationale: the item no longer appears anywhere in the product, so it must not hide the file from "no project".

### Requirement gh-1596: [calendar-events 04/12] Pin the database session time zone to UTC

#### Context

Model tier rationale: This changes the session time zone of every database connection and the semantics of every date filter and sort, so a subtle mistake alters query results across all modules and tenants and needs careful verification.

Date filters and date sorts cast stored strings to `timestamptz` in the SQL: `backend/packages/data/src/views/filterCompiler.ts` (the before, after, on-or-before, on-or-after and between conditions) and `backend/packages/data/src/views/sortCompiler.ts` (`sortKeyCast` returns `::timestamptz` for `date` properties and for earliest/latest rollups). A `timestamptz` cast of a string without an offset uses the database session's `TimeZone`. Nothing sets that zone: `createPool` in `backend/packages/data/src/db/pool.ts` passes only the optional role and the statement timeout, and deployment does not set it. The result of a date filter on the same data therefore depends on the server's configuration, and a date-only value such as `2026-10-16` is turned into a midnight instant in whatever zone the session has.

Events and Tasks store wall-clock dates and times in the tenant zone (#1416); relative filters such as "today" are computed in the application from the tenant zone by the calendar time module (#1418). The database must not add a second, hidden zone. This issue makes comparisons deterministic: every connection runs in UTC, and date-only values are compared as dates instead of through an instant. It belongs to the chain of issues that edit the view compilers, after the sort collation change #1524, and the ordering of recurring Events by next occurrence (#1905) builds on it.

Decision: values with a time and without an offset keep being read as UTC instants after this change (only the session default changes from the server's zone to UTC); date-only operands and date-only stored values are compared with `::date` so they never depend on a zone.

#### Task

Load `testing`.

1. In `createPool` (`backend/packages/data/src/db/pool.ts`), set `TimeZone` to `UTC` on every connection through the startup options (`-c TimeZone=UTC`), combined with the existing `-c role=...` option when both apply, so the setting also holds for pooled connections.
2. In `views/filterCompiler.ts`, when the operand of a date condition is a date-only string (`YYYY-MM-DD`), compare the property as `::date` instead of `::timestamptz`; operands with a time keep `::timestamptz`.
3. In `views/sortCompiler.ts`, keep `::timestamptz` for sort keys but guarantee that date-only values sort by day: cast with a pattern guard so a date-only string is cast through `::date` first. Do not change the select, text or number sort behavior.
4. Tests: with the session zone deliberately set to a non-UTC value in the test database, date filters and sorts return the same rows as with UTC; a date-only filter on `2026-10-16` matches Events dated that day regardless of the zone; a datetime filter result is unchanged from before for values with an offset; a fresh pool reports `SHOW TimeZone` as UTC for both the plain and the `role` variants.
