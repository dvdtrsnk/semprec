**Blocked by:** #227, #114

## Context

Issues #226 and #227 authored manifests for every module delivered through source issues #21–#28. Core consumers, however, still contain module-id special cases (for example the `moduleId === JOURNAL_MODULE_ID` view-type branch in `backend/packages/data/src/seed/seedTenDatabases.ts`). This part finishes the retrofit: it replaces those branches with registry projections and proves the whole set of manifests loads together and that deactivation removes projected participation. The agent-runtime batch (#117 onward) reads `agentTools`/`capabilities` through the registry that this part makes complete.

## Task

- Replace every `if (moduleId === ...)` behavior switch in core consumers with the corresponding `ModuleRegistry` projection (`viewTypes()`, `heartbeatActions()`, `workers()`, `taskNames()`, `heartbeatRuleKinds()`, and the `agentTools`/`capabilities` accessor), without changing module data behavior. Whatever a branch decided must now be declared on the module's manifest from #226/#227 and read through the projection.
- Add a load-all structural test that loads every manifest from #226 and #227 through `ModuleRegistry` in one process and passes the structural check.
- Add inactive-module projection tests: with a module's `modules.active` flag off, every projection excludes it while its stored data remains intact.

## Scope

### In scope

- Removal of equivalent core special cases across the retrofit of source issues #21–#28, the load-all test, and the inactive-projection tests.

### Out of scope

- Authoring the manifests themselves (#226, #227).
- Agent runtime implementation and new module behavior.

## Acceptance criteria

- Every existing module loads together and passes structural validation in the load-all test.
- Core has no `if (moduleId === ...)` behavior switch.
- Deactivation removes all projected participation while preserving stored data.
