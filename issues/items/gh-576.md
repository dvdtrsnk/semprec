**Blocked by:** #573

## Context

The code-review bot's review memory is frozen at the last review before a pull request merges, so an `open` finding is often already fixed: all 6 high findings above #266 turned out to be fixed on `develop` — 4 by later commits of their own pull request, 2 by a follow-up pull request (#369). The review follow-ups pipeline (epic #565) never skips a finding for that reason, because only the AI verify step with evidence may conclude "already fixed". But two cheap, deterministic hints on each harvested finding tell verify where to look first:

- `touchedAfterLastSeen` — the pull request had commits after the finding's `last_seen_sha` (the head the bot last reviewed) that modified the finding's path;
- `laterPrsTouchingPath` — how many other pull requests have since changed that path on `develop`.

Measured on the 103 open findings above #266: `last_seen_sha` is in the pull request's final commit list for 97. For the other 6 a rebase before merge replaced it, and the hint is then unknown (`null`), not `false`.

This issue computes the two hints. The harvest script (a later issue) calls it for every finding it harvests and stores the result in the finding record, whose fields `touchedAfterLastSeen` (boolean or `null`) and `laterPrsTouchingPath` (integer ≥ 0) are defined in `.github/scripts/review-followups/records.mjs`.

It uses these endpoints from #573's `.github/scripts/review-followups/github.mjs`: `listPullRequestCommits(client, prNumber)` (commit SHAs in order; GitHub returns at most 250), `getCommitFiles(client, sha)` (every `filename` and `previous_filename`), `listCommitsTouchingPath(client, { branch, path, since })` and `listPullRequestsForCommit(client, sha)` (`[{ number, mergedAt }]`).

## Task

Create `.github/scripts/review-followups/hints.mjs`, a zero-dependency ES module with a header comment stating what each hint means and when it is `null`, exporting:

1. `hintsApi(client)` — binds the four #573 endpoints to `client` and returns `{ listPullRequestCommits(pr), getCommitFiles(sha), listCommitsTouchingPath({ branch, path, since }), listPullRequestsForCommit(sha) }`. This object is the only way `computeHints` reaches GitHub, so tests pass a fake.
2. `computeHints(api, { pr, mergedAt, base, findings })` — `findings` are `{ key, path, lastSeenSha }`. Returns a `Map` from `"<pr>:<key>"` to `{ touchedAfterLastSeen, laterPrsTouchingPath }`:
   - `touchedAfterLastSeen`:
     - `null` when `lastSeenSha` is `""`, when it is not in the pull request's commit list, or when the list has 250 entries (GitHub's cap, so later commits may be missing);
     - otherwise `true` when any commit listed after `lastSeenSha` has `path` among its files (either name of a rename), else `false`.
   - `laterPrsTouchingPath`: the number of distinct pull request numbers, other than `pr`, returned by `listPullRequestsForCommit` for the commits of `listCommitsTouchingPath({ branch: base, path, since: mergedAt })`.
   - Within one call, the commit list is fetched once, each commit's files once, each path's commit list once, and each commit's pull requests once, however many findings share them.
   - Any error from `api` propagates. A hint is never guessed from a failed call.
3. `hints.test.mjs` next to it (`node:test`, `node:assert/strict`, a fake `api` that counts calls) covering every Acceptance criterion below.

## Scope

### In scope

- The two hints, their caching within one call, and tests.

### Out of scope

- Using the hints to skip anything — never; the verify step decides.
- Writing the hints into records or issues — the harvest issue of this batch.
- Following renames across later pull requests (`listCommitsTouchingPath` matches the path as given).

## Acceptance criteria

1. With commits `[a, b, c]` and `lastSeenSha: a`, the hint is `true` when `c` modifies the path, `false` when neither `b` nor `c` does, and `true` when `b` renamed the file from the path.
2. The hint is `false` when `lastSeenSha` is the last commit, and `null` when `lastSeenSha` is `""`, absent from the list, or the list has 250 entries.
3. `laterPrsTouchingPath` counts distinct pull requests across commits (two commits of one pull request count once), excludes `pr` itself, and is 0 when no commit touches the path since `mergedAt`.
4. `listCommitsTouchingPath` is called with `branch: base`, the finding's `path` and `since: mergedAt`.
5. Three findings on the same path of one pull request cause exactly one `listPullRequestCommits` call, one `listCommitsTouchingPath` call, and one `getCommitFiles` / `listPullRequestsForCommit` call per distinct commit.
6. An error thrown by any `api` function rejects `computeHints` with that error.
7. `node --test .github/scripts/review-followups/hints.test.mjs` passes with no network access.
