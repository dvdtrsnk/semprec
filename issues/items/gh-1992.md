## Context

Model tier rationale: One deterministic post-processing step over the computed envelope using two existing lookups, but its result must be expressed in the new multi-step envelope shape and stay within the no-write rule of the computation.

Capturing "the bakery with registration number X" or "Lucie, lucie@brainz.cz" for a company or person that already exists must not create a second record. Today a proposal can only create a record; nothing compares it to existing Companies or People. The existing lookups are: Companies carries a plain-text `ico` property (no index), and People carries `emails` (one address per line) with the `person_email_index` table maintained by `backend/packages/data/src/mail/personLinkingActions.ts` and read through `lookupPersonIdByEmail` and `normalizeEmailAddress` in `backend/packages/data/src/mail/personEmailIndexStore.ts`.

The proposal computation is built by #1434 and receives its context from #1987. Proposals can express relations and several steps once #1426 (relations in a database envelope) and #1479 (validation of multi-step envelopes, including the link step) land; this issue emits the link step defined there for a nested record and, for the proposal's own record, the existing-item primary step that #1479 accepts (an `update` step that changes nothing), because the validation of #1479 refuses a primary `link` step (`assertValidEnvelopeOperations` in `inboxTickAction.ts`) and this issue does not change that validation. The computation must never write to the target databases or the Inbox, so the lookups are plain reads done outside any write transaction, and the result is only an envelope.

Decision: a duplicate is found by exact match only: the same normalized IČO for a company, the same normalized e-mail address (via `person_email_index`) for a person. There is no fuzzy name matching.

Decision: when a duplicate is found, the create is replaced by an operation that refers to the existing record, and nothing of the existing record is written: no property and no relation edge. Merging captured values into it is a separate user action. The replacement keeps the `alias` of the create it replaces (so its step `ref` and every `{ alias }` target that names it stay valid), drops that create's `database`, `properties` and `relations`, and names the existing item as `itemId`. A nested record (a create that is not the proposal's own) becomes a `link` operation. The proposal's own record, which is the first `create` into the type's target database (the operation `buildProposalSteps` makes primary), becomes an `update` operation with no `properties` and no `relations`, marked `primary: true`. The reason for the `update`: #1479 refuses a primary `link` step but accepts an `update` primary, an `update` that changes nothing needs no `before` and no `after`, and confirming it writes nothing (`executeProposalSteps` only locks the item and checks that it still exists). The validation of #1479 and the confirm of #1486 are not changed by this issue.

Decision: the operation shape of the computation result gets two small extensions, because a replaced primary is no longer a create into the target database and a list of one operation is not a multi-step answer today. `ProposalComputationOperation` (`proposalOperations.ts`) gets an optional `primary: true`, set only by the duplicate step and never accepted from the model's answer; `buildProposalSteps` makes the operation marked `primary` the primary step, before its existing rule, and does not copy the marker into the stored step. `buildProposalEnvelope` (`inboxTickSnapshot.ts`) builds a multi-step envelope when the result has more than one operation or any operation is marked `primary`, so one replaced primary is stored as a one-step envelope whose top-level `properties` are the primary step's, `{}`. A single unmarked operation stays what it is today.

Decision: phone numbers are not compared in this issue; People has no phone property yet (#1535 adds it).

## Task

1. In `proposalComputation.ts` (introduced by #1434), add a duplicate-detection step that runs after the model result (and after the registry name step of #1989 when present) and before the envelope is returned.
2. Companies: normalize the computed `properties.ico` (trim, remove spaces, left-pad to eight digits). If a live (not trashed) Companies item has the same value, replace the create of that company as the Decision above says, with that item's id as `itemId`. Add a read helper in `backend/packages/data/src/` (for example `companyIcoLookup` in the Inbox area) that finds a live company by exact `ico`; it reads only.
3. People: split the computed `properties.emails` into addresses, normalize each with `normalizeEmailAddress` and ask `lookupPersonIdByEmail`. On the first hit that names a live (not trashed) People item replace the create of that person as the Decision above says, with the existing person's id as `itemId`. `person_email_index` keeps the addresses of a person who was moved to the Trash and `lookupPersonIdByEmail` still returns that person, so a hit on a trashed person is skipped like an unknown address and the next address is tried; check it with an existing read of `@semprec/data` that does not return a trashed item. A person whose address is unknown stays a create.
4. When a nested record of a multi-step proposal (a person with a new company) matches an existing one, only that record becomes a link; the other steps are kept.
5. The detection never writes. It works on the computation's result (`ProposalComputationResult`), not on a stored envelope: when the result has no `operations` and the target database is Companies or People, it reads the top-level `properties`; otherwise it reads every `create` operation into Companies or People. A result that carries `invalidProposal` is returned unchanged. When the own record of a result without `operations` is a duplicate, the result gets the one `update` operation of the Decision, marked `primary`, and its top-level `properties` are no longer read by the envelope builder. Add the optional `primary` to `ProposalComputationOperation` and to the primary choice of `buildProposalSteps` (`backend/packages/data/src/inbox/proposalOperations.ts`) and the one-operation rule to `buildProposalEnvelope` (`backend/packages/data/src/inbox/inboxTickSnapshot.ts`), exactly as the Decision describes. Two operations that the replacement would make name the same existing item (for example a `link` the model gave to a company and a company create that has its IČO) are left as they are, and `prepareComputedUpdates` then refuses the answer as a repeated mutation of one item, so its card is stored as `needsClarification` (`docs/adr/2026-11-01-computed-proposal-updates-capture-server-preconditions.md`). Do not change `assertValidEnvelopeOperations` or the confirm: the envelope the tick builds from the result passes `assertValidProposalEnvelope` unchanged (measured on the integration tip: a primary `update` with no properties and a nested `link` step validate, a primary `link` step is refused).

## Scope

### In scope

- Exact-match duplicate detection for Companies by IČO and People by e-mail, producing a step that refers to the existing record (a `link` step, or for the proposal's own record an `update` step that changes nothing).

### Out of scope

- Registered-name verification (#1989).
- Matching by phone number and fuzzy matching by name.
- How the card presents or lets the user override a step that refers to an existing record (a separate design request).
- Merging captured values into the existing record.

## Acceptance criteria

- When the computed company has IČO `07654321` and a live company with that value exists, then the proposal's primary step refers to that company (an `update` step of its id that changes nothing), no step creates a company, and the tick stores the card as `proposed`.
- When the computed company has a new IČO, then the proposal creates it together with its new person and the person-to-company edge.
- When the computed person has `lucie@brainz.cz` and that address is indexed for an existing person, then the proposal's primary step refers to that person (an `update` step of its id that changes nothing), no step creates a person, and the tick stores the card as `proposed`.
- When a person with a new company has the IČO of an existing company, then the person create stays and its company is a `link` step to the existing company.
- When the computed person's address is indexed only for a person in the Trash, then the proposal creates the person and the tick stores the card as `proposed`.
- The computation writes no row in any database.
