## Context

Model tier rationale: One deterministic post-processing step over the computed envelope using two existing lookups, but its result must be expressed in the new multi-step envelope shape and stay within the no-write rule of the computation.

Capturing "the bakery with registration number X" or "Lucie, lucie@brainz.cz" for a company or person that already exists must not create a second record. Today a proposal can only create a record; nothing compares it to existing Companies or People. The existing lookups are: Companies carries a plain-text `ico` property (no index), and People carries `emails` (one address per line) with the `person_email_index` table maintained by `backend/packages/data/src/mail/personLinkingActions.ts` and read through `lookupPersonIdByEmail` and `normalizeEmailAddress` in `backend/packages/data/src/mail/personEmailIndexStore.ts`.

The proposal computation is built by #1434 and receives its context from #1987. Proposals can express relations and several steps once #1426 (relations in a database envelope) and #1479 (validation of multi-step envelopes, including the link step) land; this issue emits the link step defined there. The computation must never write to the target databases or the Inbox, so the lookups are plain reads done outside any write transaction, and the result is only an envelope.

Decision: a duplicate is found by exact match only: the same normalized IČO for a company, the same normalized e-mail address (via `person_email_index`) for a person. There is no fuzzy name matching.

Decision: when a duplicate is found, the create step is replaced by a link step to the existing record and no field of the existing record is changed. Merging captured values into it is a separate user action.

Decision: phone numbers are not compared in this issue; People has no phone property yet (#1535 adds it).

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. In `proposalComputation.ts` (introduced by #1434), add a duplicate-detection step that runs after the model result (and after the registry name step of #1989 when present) and before the envelope is returned.
2. Companies: normalize the computed `properties.ico` (trim, remove spaces, left-pad to eight digits). If a live (not trashed) Companies item has the same value, replace the create of that company with the link step to its id. Add a read helper in `backend/packages/data/src/` (for example `companyIcoLookup` in the Inbox area) that finds a live company by exact `ico`; it reads only.
3. People: split the computed `properties.emails` into addresses, normalize each with `normalizeEmailAddress` and ask `lookupPersonIdByEmail`. On the first hit replace the create of that person with the link step to the existing person. A person whose address is unknown stays a create.
4. When a nested record of a multi-step proposal (a person with a new company) matches an existing one, only that record becomes a link; the other steps are kept.
5. The detection never writes, and works on the envelope the computation returns, so `assertValidProposalEnvelope` still accepts the result.
6. Tests: a Companies proposal with an IČO of an existing company becomes a link (use an IČO string that is not check-digit valid to prove only exact equality is used); a new IČO stays a create; a person with an address that is in `person_email_index` becomes a link and an unknown address stays a create; a nested company match keeps the person create; no row is written by the computation; a trashed company with the same IČO is not a duplicate.

## Scope

### In scope

- Exact-match duplicate detection for Companies by IČO and People by e-mail, producing link steps.

### Out of scope

- Registered-name verification (#1989).
- Matching by phone number and fuzzy matching by name.
- How the card presents or lets the user override a link (a separate design request).
- Merging captured values into the existing record.

## Acceptance criteria

- When the computed company has IČO `07654321` and a live company with that value exists, then the proposal links to it and creates no company.
- When the computed company has a new IČO, then the proposal creates it together with its new person and the person-to-company edge.
- When the computed person has `lucie@brainz.cz` and that address is indexed for an existing person, then the proposal links to that person.
- The computation writes no row in any database.
