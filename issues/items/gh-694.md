**Blocked by:** #693

## Context

An `mcpInvoke` approval request snapshots its target at request time (`McpInvokeApprovalRequestPayload { mcpToolRegistrationId, mcpServerItemId, args }`, `backend/packages/data/src/mcp/approvalRequestsStore.ts:71-75`). When the human approves it — possibly hours later — `handleApprovalRequestExecuteTask` (`backend/packages/data/src/mcp/approvalRequestExecution.ts`, mcpInvoke path) only reloads the server item (`loadServerItem`, `WHERE id = $1 AND deleted_at IS NULL`) and calls the tool. It never re-evaluates what `resolveGrantedMcpTool` (`backend/packages/data/src/mcp/mcpToolInvocation.ts:48-88`) checks at request time: `project_mcp_grants.granted = true` for the run's project, `mcp_tool_registrations.active = true`, and the server item's `properties ->> 'active' = 'true'`. A grant revoked (`setProjectMcpGrantForAgentPage`), a registration deactivated by a later sync (`deactivateMcpToolRegistrationsNotIn`), or a server switched inactive between request and approval is therefore still executed against the third-party server.

`executeMcpInvocation`'s docstring already says it "does not re-check authorization itself" and expects the caller to. D7 restructures this handler (claim, stale settlement, outcome guard); this issue adds the re-check between the claim and the call.

## Task

1. In `approvalRequestExecution.ts`, after the claim succeeds and before any connection is opened, replace the `loadServerItem` transaction with one transaction that:
   - loads the request's run: `getAgentRun(client, claimed.agentRunId)` (`agentRunsStore.ts`);
   - when the run exists and has a `projectItemId`, calls `resolveGrantedMcpTool(client, run.projectItemId, payload.mcpToolRegistrationId)`;
   - treats a missing run, a `null` `projectItemId`, a `null` target, or a target whose `mcpServerItemId !== payload.mcpServerItemId` or `toolName !== claimed.toolName` identically: the outcome is `{ error: true, result: "This MCP tool is no longer available to the requesting project: its grant was revoked, or its registration or server is inactive." }` — recorded through `recordApprovalRequestOutcome` exactly like the existing "server no longer exists" outcome, no connection opened.
   - on success, uses `target.serverItem` for `executeMcpInvocation` (so `loadServerItem` becomes unused — delete it).
   Update the handler docstring: the approval snapshot fixes *what* is called (args, tool, server), never *whether* it may still be called; that is re-derived from current state at execution time, the same three-way check the request-time resolver performs.
2. **Tests** (`backend/packages/data/src/__tests__/approvalRequestExecution.test.ts`, existing fixtures; each case approves the request first, then changes state, then drains the queue):
   - grant revoked (`setProjectMcpGrantForAgentPage(..., granted: false)`) → row `conflict`, `execution_error = true`, result = the message above, the contract server received no tool call;
   - registration deactivated (`UPDATE mcp_tool_registrations SET active = false`) → same;
   - server item set `properties.active = false` → same;
   - nothing changed → executed and `succeeded` (the existing happy-path case keeps passing).

## Scope

### In scope
- The execution-time re-authorization of an approved `mcpInvoke` request and its tests.

### Out of scope
- The claim/outcome protocol, stale-claim settlement and idempotency key (D7).
- Re-validating the snapshotted `args` against a changed `tool_schema` (the approved args are what the human saw; a schema change is the server's concern).
- The generic-operation replay path, which does its own provenance re-check in `packages/application`.

## Acceptance criteria

- When the project's grant for the tool is revoked, the tool's registration is deactivated, or the server item is inactive at execution time, the approved request is recorded as `conflict` with the "no longer available" message and no MCP connection is opened.
- When grant, registration and server are still active, execution proceeds exactly as before.
- `approvalRequestExecution.ts` no longer contains `loadServerItem`; the server item used for the connection comes from `resolveGrantedMcpTool`.
