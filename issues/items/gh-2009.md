## Context

Model tier rationale: It deletes a property definition and strips its stored values from every Tasks item of every tenant with raw SQL on a schema-locked database, which is a wide destructive data change even though the property has no behavior; batching and idempotency must be exact.

`backend/packages/data/src/seed/seedTenDatabases.ts` creates the Tasks property `persistent` (checkbox, owner `user`) with the i18n labels `property.tasks.persistent.name` in `seed/i18n/cs.json` and `en.json`. No code gives it a meaning: the only reader is `advanceTaskRecurrenceWithClient` (`backend/packages/data/src/tasks/advanceTaskRecurrenceWithClient.ts`), which copies it into the next recurring instance (#1673 keeps that copy an explicit allowlist). No screen of the design shows it.

Decision (product owner): Tasks properties without described behavior are not kept in v1 (no speculative generality); if one is needed later, it comes back with concrete behavior. `persistent` is removed. `notifications` is not removed: the calendar reminders batch gives it its behavior (#1719, the task reminder switch).

The Tasks schema cutover of #1540 is the pattern for per-tenant schema changes on locked databases (raw SQL on `properties`, registered in `runTenantCutoverMigrations` in `backend/packages/data/src/db/tenantCutoverMigrations.ts`, following `docs/adr/2026-09-10-app-code-post-migration-steps.md`).

Shared-file ordering: this issue also waits for #1668 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Decision (batch 37 reconciliation): Also omit persistent from virtual occurrence properties and public series templates. Keep the legacy internal template boolean parseable; no template-row backfill or other field change.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Remove `persistent` from the Tasks property list in `seedTenDatabases.ts` and its label keys from `seed/i18n/cs.json` and `seed/i18n/en.json`.
2. Remove the `persistent` line from the properties copied in `advanceTaskRecurrenceWithClient.ts`, and from its header comment in `backend/packages/data/src/tasks/advanceTaskRecurrence.ts`.
3. Add a per-tenant cutover `backend/packages/data/src/tasks/tasksPersistentRemovalCutoverMigration.ts`, registered in `runTenantCutoverMigrations` after the Tasks schema cutover of #1540: it resolves the tenant's Tasks database (no-op without one), removes the key `persistent` from the stored properties of every Tasks item that has it (trashed items included) in batches of 500 ids, each batch in its own transaction, idempotent through `properties ? 'persistent'`, and then deletes the `persistent` property definition of the Tasks database. A second run changes nothing.
4. Update any test or fixture that lists the Tasks properties (for example `backend/packages/data/src/__tests__/databaseKeysNullableNames.test.ts`).
5. Tests: a fresh seed has no `persistent` property; the cutover on a tenant seeded with the old shape removes the definition and the stored values (also on trashed items) and leaves every other property value unchanged; a second run is a no-op; a tenant without Tasks is skipped; completing a recurring task creates the next instance without `persistent`; `GET /api/schema` no longer lists it.

## Acceptance criteria

- When a new tenant is seeded, then its Tasks database has no `persistent` property.
- When the cutover runs for a tenant seeded before this change, then no Tasks item (trashed ones included) stores `persistent`, the property definition is gone, and every other stored value is unchanged; a second run changes nothing.
- When a recurring task is completed, then the next instance has no `persistent` value.
- When `GET /api/schema` is called after the cutover, then Tasks lists no `persistent` property.
