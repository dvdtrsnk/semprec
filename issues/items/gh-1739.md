**Blocked by:** #1454, #1550
**Model tier:** high

## Context

Model tier rationale: It adds a process-wide cross-tenant Pub/Sub puller with its own service-account credential and a shutdown-ordering requirement (stop before the pool, redeliver unacknowledged messages), which is difficult cleanup ownership plus a new secret.

After #1550, `backend/services/semprec-api/src/mailLiveSyncLifecycles.ts` dispatches the live-sync lifecycle by sync mode and hosts IMAP IDLE; Gmail accounts still get the noop lifecycle. The Gmail pieces already exist but nobody calls them: `createGmailWatchLifecycleFactory` and `createGmailPubSubDispatcher` (`backend/packages/data/src/mail/gmailWatchLifecycle.ts`) and `createGmailPubSubTransport` (`mail/gmailPubSubClient.ts`). The watch registers `users.watch` per account under that account's own OAuth grant; one process-wide dispatcher pulls the deployment's shared Pub/Sub subscription and routes each notification to the mailboxes watching the address (cross-tenant router functions, `docs/adr/2026-10-07-cross-tenant-router-functions.md`). The Pub/Sub calls authenticate as the application's own Google service account, not as a user: a user's Gmail OAuth grant has no Pub/Sub scope.

The routing key is the Google account's address. It must come from the provider-verified address that #1454 stores on the mailbox, never from the user-editable `Mailboxes.addresses`; otherwise one tenant could claim another's notifications. The Gmail REST sync transport is #1505. The shutdown order of the api process is fixed by `docs/adr/2026-09-27-semprec-api-shutdown-ordering.md` and implemented in `backend/services/semprec-api/src/shutdown.ts` (`createGracefulShutdown`).

Decision: configuration is three keys read from the environment and documented in one group of `deploy/shared/env/api.env.example` (`docs/adr/2026-10-03-per-service-secret-groups.md`): `GMAIL_PUBSUB_TOPIC` (`projects/<p>/topics/<t>`), `GMAIL_PUBSUB_SUBSCRIPTION` (`projects/<p>/subscriptions/<s>`) and `GMAIL_PUBSUB_SERVICE_ACCOUNT_KEY_PATH` (path to the service account JSON key). The Pub/Sub access token is obtained by signing a service-account JWT assertion (RS256, `node:crypto`) and exchanging it at Google's token endpoint, cached until shortly before expiry; the key file is read at startup, never logged.
Decision: with any of the three keys or the Gmail OAuth client missing, the process starts, the Gmail lifecycle is not hosted (Gmail accounts keep the noop lifecycle and the sweep), and one warning is logged.

## Task

Load `io-hardening`, `error-handling` and `testing`.

1. Add `backend/services/semprec-api/src/gmailPubSubConfig.ts`: reads the three keys, validates formats, loads the service account key, and exposes `getPubSubAccessToken()` as described; returns `null` plus a reason when incomplete.
2. In `mailLiveSyncLifecycles.ts` set `hosted.gmail_api` to `createGmailWatchLifecycleFactory(pool, createGmailPubSubTransport({ getGmailAccessToken, getPubSubAccessToken, topicName, subscriptionName }), { getCredential, getAccountEmailAddress, onError })`: `getGmailAccessToken` uses `refreshAndPersistAccessToken` (#1481) with the Gmail OAuth client; `getCredential` uses `getDecryptedCredential` (purpose `gmail_watch`); `getAccountEmailAddress` reads the server-owned, provider-verified address from #1454.
3. Create one `createGmailPubSubDispatcher` per process in `serve.ts`, start it after the live-sync root starts, and stop it in `createGracefulShutdown` before the pool ends and before the live-sync root's database use ends (add an option and an ordered step in `shutdown.ts`; follow the shutdown-ordering ADR and update its test). Messages in flight and not yet acknowledged are left for Pub/Sub to redeliver.
4. Add the three keys, with explanatory comments, to a single group in `deploy/shared/env/api.env.example`; check `deploy/provision.test.sh` still passes.
5. Tests with fakes: a notification for a watched address enqueues one sync for each target mailbox; the dispatcher is stopped before the pool in the shutdown test and an unacknowledged message is not acknowledged; the routing address is the provider-verified one, not `addresses`; with the config missing, one warning is logged and a Gmail account gets the noop lifecycle; the service-account token is cached and never logged.

## Scope

### In scope

- Hosting the Gmail watch lifecycles and the single Pub/Sub dispatcher, its configuration and shutdown order.

### Out of scope

- Provisioning the GCP topic, subscription and service account.
- The Gmail sync transport: #1505. The verified-address storage: #1454.
- IMAP IDLE: #1550. Graph: #1745.

## Acceptance criteria

- When a Gmail account receives a message, then the Pub/Sub notification enqueues a sync for its mailbox without waiting for the sweep.
- When the process stops, then the dispatcher stops before the pool ends, and a pulled but unacknowledged notification is delivered again later.
- When Pub/Sub keys or the Gmail OAuth client are missing, then the process starts, one warning is logged, and Gmail accounts are still synced by the sweep.
- When notifications are routed, then the address used is the provider-verified one.
- When logs and errors are inspected, then neither the service account key nor any token appears.
