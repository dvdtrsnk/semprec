## Context

Model tier rationale: A populated-tenant raw-SQL cutover changes schema-locked properties and relations; the existing fixture pattern does not remove that risk.

Deliver the group schema in one idempotent populated-tenant cutover and fresh seed; later value writers reuse it without repeated schema edits.

Today's behavior:

- `backend/packages/data/src/seed/seedTenDatabases.ts` creates Tasks with `name`, `status` (`notDone`/`done`/`wontDo`), `date`, `timeFrom`, `timeTo`, `time` (owner `system`, no `ownerProcess`), `notifications`, `persistent`, plus `Tasks.project` (inverse of `Projects.tasks`). Events has `actionItems` pointing at Tasks, one-directional. People has no `tasks` relation and Files has no `tasks` relation.
- `relate()` in that seed passes no `SystemRelationWriteContext`, so a relation owned by the system cannot be created from it yet. Tenants that were seeded earlier receive nothing from the seed. `backend/packages/data/src/db/tenantCutoverMigrations.ts` (`runTenantCutoverMigrations`) is the place for per-tenant data cutovers; `backend/packages/data/src/transcription/transcriptsCatalogCutoverMigration.ts` is the pattern: it inserts `properties`, `relation_definitions` and the property `config` with raw SQL, because `createRelationPropertyWithClient` calls `propertiesStore.createProperty`, which throws `SchemaLockedError` on a locked database. Per `docs/adr/2026-10-08-deploy-time-tenant-work-runs-as-the-runtime-role.md`, only this per-tenant step changes tenant rows; the migration role does DDL only.
- Edge ownership is checked only on the side the caller names (`chokePoint/relationEdgeContext.ts`, `assertRelationPropertyWritable`), and an inverse side defaults to owner `user` (`chokePoint/relationPropertyOps.ts`). A relation that is system-owned must therefore carry owner `system` and `ownerProcess` `tasks` on both sides; `Mailboxes.folders`/`mailbox` in `seed/seedEmailModule.ts` is the existing two-sided example.
- `KNOWN_OWNER_PROCESS_IDS` in `backend/packages/data/src/manifest/knownActionIds.ts` does not list `tasks` (`TASKS_MODULE_ID` is defined in `seed/tenDatabaseKeys.ts`). `Tasks.time` is `owner: system` with an empty `owner_process`, so `core.driftCheck` (`manifest/driftCheck.ts`) reports it, and `moduleRegistry.checkDrift` reports an unknown `owner_process` such as `tasks`.

Decision: the description is a `longText` property holding Markdown. It stays readable by Semp and by search and is trivially copied; a per-item page is not used for it.

Decision: the people and files links of a task are plain user-owned many-to-many relations.

Decision: the set below is created by this one issue. The property for a task's source events (`Tasks.sourceEvents`, the inverse of `Events.actionItems`) is not part of it; #1542 owns it. The creation time of a task is the generic item creation timestamp (#1594), not a Tasks property.

The recurrence ADR from #1365 fixes ownership and projection but does not choose the projection property type. The parent schema reconciliation selects the existing json type with config `{}` for `recurrence`, compatible with #1605's declared `{preset, mode, rule}` projection. `sinceTime` likewise uses json for #1602's `{from, to}` pair. See `issues/batches/backend/decisions/batch-26-spec-reconciliation.md`. Existing scalar `Tasks.time` and the accepted recurrence ADR body remain unchanged.

Later issues that write these properties are blocked on this one, among them #1544, #1654, #1673, #1764, #1602, #1605, #1668, #1674, #1724, #1588 and #1796.

Shared-file ordering: this issue also waits for #1538 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Add the new properties to the seed (`seedTenDatabases.ts`, phase 1 for scalars, phase 2 for relations, before schemas are locked) and to one new per-tenant cutover, `runTasksSchemaCutoverMigration`, registered in `runTenantCutoverMigrations`. The cutover mirrors `runTranscriptsCatalogCutoverMigration`: it resolves the tenant's Tasks, Events, People and Files databases, takes the same lock, skips every property that already exists by `(database_id, key)` and inserts the missing ones with raw SQL (properties, `relation_definitions`, then the property `config` with `relationDefinitionId` and `targetDatabaseId`). It does nothing when a database is missing (fresh install; the seed ships the target shape). Running it twice changes nothing.
2. Scalar properties on Tasks, canonical keys English camelCase:
   - `flagged`: checkbox, owner `user`.
   - `description`: longText, owner `user`.
   - `since` (date) and `sinceTime` (json object `{from, to}`): the first planned day and its stored time bounds for a task that moved on, as #1602 specifies; owner `system`, `ownerProcess` `tasks`. `sinceTime` uses ordinary JSON property config `{}`, not the scalar/display `time` type.
   - `completedOn` (date): owner `user`. `completedAt` (date with time): owner `system`, `ownerProcess` `tasks`.
   - `hiddenUntil` (date with time) and `effectiveDate` (date): derived, owner `system`, `ownerProcess` `tasks`.
3. Recurrence series properties on Tasks as recorded by the #1365 ADR: `seriesId` (text) and `occurrenceDate` (date), owner `system`, `ownerProcess` `tasks`, and `recurrence` (json, config `{}`), owner `system`, `ownerProcess` `tasks`. This is the schema for the ADR's projection; #1605 owns populating its `{preset, mode, rule}` value and the series storage. Do not write recurrence item values or alter the existing recurrence table/hook in this schema issue.
4. The status select gets a new option `missed`; the stored key of the open option stays `notDone` and only its i18n label changes (English "Open"; Czech "Otevřeno"). Existing items keep their values. The cutover appends the option to `properties.config.options` only if absent.
5. Relations, all many-to-many unless stated, created in the seed through `relate()`, which gains an optional `SystemRelationWriteContext` argument and passes `{ ownerProcess: "tasks" }` for the system ones; in the cutover through raw SQL:
   - `Tasks.people` with inverse `People.tasks`, owner `user`.
   - `Tasks.files` with inverse `Files.tasks`, owner `user`.
   - `Tasks.hostEvents` with inverse `Events.hostedTasks`, owner `system`, `ownerProcess` `tasks` on both sides.
   - `Tasks.completedInEvent` with inverse `Events.completedTasks`, owner `system`, `ownerProcess` `tasks` on both sides; single-valued on the task side (`Events.completedTasks` is the "one" side of a `one_to_many`).
6. Set `ownerProcess` `tasks` on `Tasks.time` in the seed and in the cutover (`UPDATE ... WHERE owner_process IS DISTINCT FROM`), and add `TASKS_MODULE_ID` to `KNOWN_OWNER_PROCESS_IDS`.
7. i18n: add `property.tasks.<key>.name` for each new Tasks property, `property.people.tasks.name`, `property.files.tasks.name`, `property.events.hostedTasks.name`, `property.events.completedTasks.name`, `property.tasks.status.option.missed` and the changed label of `property.tasks.status.option.notDone`, in both `seed/i18n/cs.json` and `seed/i18n/en.json`. Property names are stored as null and resolved from the catalogs; do not store literal names.
8. Tests: cutover applied to a tenant seeded with the old shape yields the same schema as a fresh seed; a second run is a no-op; `GET /api/schema` shows all new properties with Czech and English labels; `core.driftCheck` and `moduleRegistry.checkDrift` report no finding for any Tasks or Events property introduced or updated by this issue; separately assert and report the unchanged preexisting Events.time orphan; a generic PUT or DELETE of an edge through either side of `hostEvents` or `completedInEvent` returns 403 `owner_violation`.

Tasks.seriesId is an internal UUID projection, excluded from declared search fields.

## Acceptance criteria

- When a tenant seeded before this change runs `runTenantCutoverMigrations`, then its Tasks, Events, People and Files schemas contain every property and relation listed above, and a second run changes no row.
- When `GET /api/schema` is called after the cutover or on a fresh seed, then every new property appears with a Czech and an English label.
- When `core.driftCheck` and `moduleRegistry.checkDrift` run after the cutover, then neither reports a finding for a Tasks or Events property introduced or updated by this issue. The unchanged preexisting `Events.time` owner-process orphan remains reported separately; do not suppress it, assign a placeholder owner or claim the complete databases are drift-free.
- When a generic edge PUT or DELETE targets `hostEvents`, `hostedTasks`, `completedInEvent` or `completedTasks` from either side, then the response is 403 `owner_violation`.
- When items exist before the cutover, then their stored property values are unchanged.
