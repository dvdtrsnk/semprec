## Context

Model tier rationale: A new queued task that couples a persisted message lifecycle, a long-lived in-memory session, per-tenant queue ordering and abort handling is a cross-process concurrency contract, and a mistake duplicates tool writes or loses replies.

Queued thread turns use the existing conversation registry and persisted run history.

Use the existing agents composition roots; thread turns reuse SempConversation and the run-bound session factory.

It builds on: the thread-keyed conversation registry (#1565), user turns stored as run events (#1566), the HTTP send path (#1620), thread invalidations over realtime (#1395), the queue-shape ADR (#1370: queue `tenantLane('semp-chat')`, `maxAttempts: 1`, `unsafe_dedupe` job key per assistant message) and the run-bound session factory with `onTurnStart` (#1398). Later issues build on this one: recovery (#1732), reserved capacity (#1755), titles (#1769), ref expansion (#1733), the chat system prompt (#1738), retry and regeneration (#1926, #1930), voice turns (#1734), tick continuation (#1775, #1731) and others.

Batch31 owner reconciliation: the send route is sempThreadsHandler.ts, and the existing CHECK-constrained pre-run assistant status is queued, never pending. Existing sempThreads/sempThreadsStore.ts owns thread/message reads and send writes; semp/sempMessagesStore.ts is the existing message-write owner for status, event range and activity operations. Keep those owners, transaction checks and post-commit invalidation; do not add direct message SQL to the agents service.

Read docs/adr/2026-11-06-semp-wake-replays-bounded-complete-history.md. Compose real bounded complete reconstruction, never the empty default or a fake compaction adapter. Replay at most 2000 stored event rows/expanded entries and 262144 UTF-8 payload bytes; overflow fails before the model with no truncation or checkpoint. Reuse the existing in-flight helper by a narrow export.

Follow docs/adr/2026-11-06-semp-message-order-and-session-freshness.md: shared ordered insertion, pair exclusion for freshness checks, and exact cached reply identity/content comparison. Conservatively wake on mismatch; no model-time database lock or new persistent sequence.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. In `backend/packages/queue/src/index.ts` add `SEMP_MESSAGE: "sempMessage"` to `AGENT_TASK_NAMES` and `[AGENT_TASK_NAMES.SEMP_MESSAGE]: "tenant"` to `TASK_TENANCY`. Add an `enqueueSempMessage(client, { threadId, assistantMessageId })` helper (in `backend/packages/data`, next to the other agent enqueue helpers) that calls `enqueueJob` with the payload `{ threadId, assistantMessageId }`, `queueName: tenantLane('semp-chat')` (throw if it is `undefined`, i.e. outside a tenant scope), `maxAttempts: 1`, `jobKey: sempMessage:<assistantMessageId>` and `jobKeyMode: 'unsafe_dedupe'`.
2. Call that helper from the send path of #1620 in the same transaction that inserts the user message and the queued assistant message, so a committed message always has a job and a rolled-back one has none.
3. In `createAgentTaskList` and the agents queue runtime options, add a `sempMessageTask` handler slot (default no-op), and compose the real handler in `serve.ts`.
4. Add `backend/services/semprec-agents/src/sempMessageTask.ts` with `createSempMessageTask(...)`, wrapped in `withInFlightRegistration` so the abort signal reaches the session. The handler:
   - reads the assistant message and its thread under the tenant scope; if the message is missing or no longer `queued` (a redelivered or superseded job), logs and returns;
   - sets the message `running`;
   - sends the user text and refs of the preceding user message into the thread's `SempConversation` entry with `createAgentSessionForRun` set to the run-bound factory, the abort signal, and `onTurnStart` writing `agent_run_id` and `event_from_id` on the assistant message;
   - after the prompt, stores the assistant texts of the turn in order, the last event id as `event_to_id`, and status `done`; on a thrown error stores status `error` and rethrows nothing that would let the queue retry (the job ends, `maxAttempts` is 1);
   - finally publishes the `sempThread` invalidation from #1395;
   - treats an in-memory session as valid only when it processed the thread's latest message; otherwise it wakes a new session from the stored history (#1566).
   A system-authored message (a tick continuation) is handled the same way; its producers are #1775 and #1731.
5. Tests: two messages sent in quick succession in one thread produce two replies in order and no busy error; a thrown error marks the message `error` and the job is not retried; a tenant deactivation aborts a running turn; a redelivered job for a finished message is a no-op.

## Scope

### In scope

- The `sempMessage` task: name, tenancy, enqueue, handler, status and event-range writes, invalidation, in-flight abort.

### Out of scope

- Recovery of interrupted `running` messages and shutdown handling (#1732).
- Reserving worker capacity or priorities (#1755).
- The chat system prompt and date (#1738), ref expansion (#1733), titles (#1769), step summaries (#1860), error classification (#1907) and manual retry (#1926).

## Acceptance criteria

- When two messages are sent quickly into one thread, then two assistant messages become `done` in sending order and no `SEMP_BUSY` is returned.
- When messages are sent in threads of different tenants, then their turns run concurrently.
- When a turn throws, then the assistant message has status `error`, the job is not attempted again and the next message of the thread is processed.
- When the job runs, the assistant message has `agent_run_id`, `event_from_id` and `event_to_id` set, and a `sempThread` invalidation is published.
- When a message is not `queued` at job start, then the handler does nothing.
- When a message insert rolls back, then no `sempMessage` job exists.
