# Module contract — `ModuleManifest`, `ModuleRegistry`, migrations, drift, testing

## Context

The monorepo skeleton (pnpm workspace) is scaffolded by issue #21 — `packages/data`, `packages/module-registry`, `packages/agent-runtime`, `packages/queue`, `packages/realtime`, `packages/credentials`, `packages/shared`, and empty `modules/` and `services/` directories exist by the time this issue starts (most as empty packages; `packages/data` and `packages/queue` carry real code from issue #21). This issue is the **first real implementation work in `packages/module-registry`** — until now there was no code defining what a module's manifest actually is, how the core reads it, or how core and modules stay in contract over time.

Issues #21–#28 (schema engine, view types, blocks, hardcoded databases, library module, IMAP, inbox) were built **without a formal module contract** — they wrote directly against the choke-point (`packages/data`), with no `ModuleManifest` and no `ModuleRegistry` class. That is a deliberate ordering, not debt: a contract introduced only now gets validated against existing, already-working examples instead of being designed on paper with nothing to check it against. This issue therefore also includes retrofitting modules #21–#28 with the manifest — a retrofit of their existing data logic, not a rewrite.

The follow-on issue #30 (`pi-agent-core` — lifecycle events + budget cap) builds on `packages/agent-runtime` and on the manifest's `agentTools` field, but the agent runtime itself (agentLoop, budget enforcement) is **not part of this issue** — this issue only defines and populates the contract that `pi-agent-core` will read.

The manifest shape below reflects a SOLID-principles pass that was applied directly to this section of the spec, replacing an earlier draft:
- **Open/Closed:** a module that wants its own heartbeat trigger kind, or its own namespaced queue task, must be able to add one without touching core code. Two new optional manifest fields exist for exactly this: `heartbeatRuleKinds` (a module-defined heartbeat trigger kind, instead of patching a central zod enum) and `taskNames` (a module-owned, namespaced queue task name, instead of adding a line to one shared `TASK_NAMES` literal that everyone edits).
- **Interface Segregation:** `ModuleRegistry` must not hand every consumer the whole manifest object. It exposes narrow, typed projections instead — `heartbeatActions()`, `heartbeatRuleKinds()`, `workers()`, `viewTypes()`, `taskNames()`, plus the equivalent for `agentTools`/`capabilities` — so each consumer (tool resolution, heartbeat scheduler, worker supervisor, view renderer, queue) depends only on its own slice and is unaffected when an unrelated manifest field is added or changed.
- **Dependency Inversion:** the startup drift/structural check, which today only validates that every `agentTools`/`workers` entry has a matching exported handler, is extended to also validate `project_heartbeats.action_id` and `properties.owner_process` against the manifest built by `ModuleRegistry` — so a dangling reference to a module that no longer registers that action/ownership fails loudly at startup (and periodically thereafter), instead of surfacing only when something tries to use it in production.

## Task

Populate `packages/module-registry` (and, where useful, `packages/shared` for shared types) with real code that:

1. Defines `ModuleManifest` as a TypeScript contract — the only way the core knows a module exists and what it can do. No `if (moduleId === 'emails')` anywhere in core.
2. Implements a `ModuleRegistry` class with `loadModule()` (an explicit, deploy-time path passed at process startup — a known-path dynamic `import()`, never directory scanning, never runtime plugin discovery) plus a runtime read of the `modules.active` DB flag to decide whether a loaded module currently participates.
3. Exposes the manifest to consumers only through narrow, typed projection getters (`heartbeatActions()`, `heartbeatRuleKinds()`, `workers()`, `viewTypes()`, `taskNames()`, and the equivalent for `agentTools`/`capabilities`) — never the raw manifest object — so adding an eleventh manifest field never forces every existing consumer to be revisited.
4. Introduces a load-time structural check (every `agentTools`/`workers` entry must have a matching exported handler, or startup fails loudly — never silently ignored).
5. Treats migrations as two separate mechanisms depending on which problem is being solved (see Scope below).
6. Introduces manifest drift detection as a new core `heartbeatAction` — a second layer of checking alongside the load-time structural check, running periodically even without a process restart — and extends the same check to validate `project_heartbeats.action_id` and `properties.owner_process` against the manifest, not just `agentTools`/`workers`.
7. Builds a three-tier testing toolset (unit / integration against an ephemeral Postgres / small e2e suite) as mechanism and configuration — not as a GitHub Actions pipeline.
8. Retrofits the modules from issues #21–#28 onto the new manifest, so the contract is validated against real code, not just written down.

## Scope

### In scope

- **`ModuleManifest` interface** (in `packages/shared` or `packages/module-registry`, whichever is the cleaner typing boundary): `id`, `version`, `name`, `removable`, `systemProject`, `databases: ModuleDatabaseSpec[]`, `capabilities`, `agentTools` (existing shape, unchanged), plus four fields added by this revision on top of the existing shape:
  - `viewTypes?: { type: string; handlerExport: string }[]`
  - `heartbeatActions?: { id: string; handlerExport: string }[]`
  - `heartbeatRuleKinds?: { kind: string; schemaExport: string; nextFireAtExport: string }[]` — lets a module add its own heartbeat trigger kind without patching a core zod enum
  - `taskNames?: { name: string; payloadSchemaExport: string; handlerExport: string }[]` — lets a module add its own namespaced queue task name instead of editing a central task-name literal it doesn't own
  plus `workers` and `migrations`. All new fields are added as further optional fields of the same manifest — never as a second registry alongside the first.
- **`ModuleRegistry` class**: `loadModule(path)` with explicit `import()`; runtime read of `modules.active` (tool resolution, heartbeat scheduler, worker supervisor, and database pickers all read it through the registry, never the table directly); load-time structural check of handlers that fails loudly on mismatch.
- **Narrow typed projections (Interface Segregation)**: `ModuleRegistry` must expose per-aspect getters — `heartbeatActions()`, `heartbeatRuleKinds()`, `workers()`, `viewTypes()`, `taskNames()`, and the equivalent narrow accessor for `agentTools`/`capabilities` used by tool resolution — each returning only the merged list across active modules for that one aspect. No consumer should hold a reference to the whole manifest object.
- **"Absence of capability, not runtime gating" principle**: a tool without a matching `requiresCapability` grant is never added to the agent's tool array in the first place — implement as a filtering step inside `ModuleRegistry`, not as a runtime check inside the handler.
- **Runtime `TASK_NAMES` merge**: the runtime `TASK_NAMES` object, assembled at `ModuleRegistry` startup from `CORE_TASK_NAMES` (defined in `packages/queue`, issue #21) plus the `taskNames` entries of all active modules' manifests, and registered with the queue engine via its `registerTask` API. The queue engine itself (graphile-worker, `registerTask`/`enqueueJob`) is delivered by issue #21 and only consumed here — this issue owns the merge and the module-task registration, not the engine.
- **Worker supervisor consumption of the manifest `workers` field**, including per-row scaling: from the merged `workers()` projection, derive the set of worker processes that should exist — one process per active row where the manifest demands it (e.g. `semprec-mailsync@<id>`, one instance per active mailbox row) — and keep that derivation/registration current as rows are activated and deactivated. The systemd template units themselves (`semprec-mailsync@.service` etc.) come from issue #40; this issue owns only the derivation/registration logic that decides which instances should exist.
- **Wiring module-registered `heartbeatRuleKinds` into the scheduler**: the heartbeat scheduler (which lives in issue #21) must validate `project_heartbeats` rows against the union of core rule kinds and the merged `heartbeatRuleKinds()` projection, and dispatch `nextFireAt` computation for module-defined kinds to the module's `nextFireAtExport`. The manifest field and its projection are defined above; this bullet owns the consumption side — the registry-driven extension of the scheduler's validation union and dispatch — while the scheduler itself stays in issue #21.
- **Structural migrations** (choke-point tables — `databases`/`items`/`properties` and system tables): a flat, numbered list of `db/migrations/*.sql` files, forward-only, no per-module versioning (one shared transactional schema). Deliver the runner/tooling that applies this directory.
- **Data migrations** (when the shape of `items.properties` content changes): a `module_migrations` table (`module_id`, `database_key`, `from_version`, `to_version`, `ran_at`) plus a script carried by the manifest per version pair. Implement `migration_cursor uuid` on `properties` — the last successfully converted `item_id` — and cursor-based batch pagination, so a retry after a crash resumes from the cursor instead of restarting from zero or silently re-converting already-migrated rows.
- **Drift detection**: `moduleRegistry.checkDrift` as a new, standalone core `heartbeatAction`, registered and run periodically alongside the load-time structural check. It repeats the same pair of checks the structural check does at startup — every distinct `action_id` in `project_heartbeats` matches an active `heartbeatAction`, and every distinct `owner_process` in `properties` matches an active module in the currently built `ModuleRegistry` — but against the live DB state, so drift introduced between two restarts (manual DB edits, a manifest upgrade during development) doesn't stay silent until the next deploy. It shares only the concept of one findings channel with the (not-yet-built) AGENT.md drift detector, not an implementation — build it as its own independent mechanism.
- **Static check of module boundaries**: `dependency-cruiser` (or equivalent) configuration as a tool/lint rule that fails the build if `modules/X/**` imports anything from `modules/Y/**` outside its registered entry point. Extend the same rule to `services/*` boundaries as well. Ship as a runnable script/config in the repo.
- **Three-layer testing infrastructure**:
  1. Unit (vitest, no DB) — configuration plus a first set of tests for logic with no side effects (the `filter`-tree compiler from the views section, property-type migration conversion functions, next-heartbeat-fire-time computation).
  2. Integration against a real, ephemeral Postgres (never a mocked DB) — a harness for `owner`/`locked` enforcement at the choke-point, the idempotency key, and any concurrency guarantee introduced by this issue (e.g. concurrent drift-check runs).
  3. A small, named e2e suite — scaffolding for the riskiest cross-module flows; in this issue, build the harness and at least one representative scenario, not a complete suite for every module.
- **Retrofit issues #21–#28**: write a `ModuleManifest` for each existing module (schema engine, views, blocks, hardcoded databases, library, IMAP, inbox) based on its actual `databases`/`capabilities`/`agentTools`, and verify that `ModuleRegistry.loadModule()` can load it and pass the structural check without modifying its data logic.

### Out of scope

- **GitHub Actions / CI pipeline itself** — the dependency-cruiser rule and the testing layers are delivered in this issue as runnable tools/scripts/configuration in the repo, not as `.github/workflows/*.yml`. Wiring into CI is separate work.
- **The task queue engine itself** (`packages/queue` on `graphile-worker` — `registerTask`/`enqueueJob`, `CORE_TASK_NAMES`) — delivered by issue #21, consumed here. Note the boundary: the engine is out of scope, but the runtime `TASK_NAMES` merge (CORE_TASK_NAMES + active modules' manifest `taskNames`, assembled at `ModuleRegistry` startup) **is** in scope of this issue — see In scope.
- **The six systemd processes / `services/*` topology** (`semprec-api`, `semprec-agents`, `semprec-mailsync@<id>`, `semprec-transcribe`, `semprec-ai-gateway`) — the unit files and process management are operational work in issue #40; this issue owns only the derivation/registration of which per-row worker instances should exist (see In scope).
- **`packages/agent-runtime`** (agentLoop, lifecycle events, budget cap) — that is issue #30 (`pi-agent-core`), which builds on the manifest's `agentTools` field, but the runtime implementation itself does not belong here.
- **`packages/credentials`** (encryption/decryption of third-party secrets) — a separate package from issue #26 (IMAP sync core), a different responsibility.
- **The AGENT.md drift detector** proposed alongside the data layer (issue #21) — still only proposed, not built; the drift detection in this issue is an independent implementation, not an extension of something that doesn't exist yet.
- **The exact behavior of `graphile-worker`'s `jobKey` dedup mechanism under concurrency with an already-*running* (not just pending) job** — left open to verify against the concrete library version in issue #21 (`packages/queue`), where the queue engine is built.

## Dependencies

- Requires the monorepo skeleton (`packages/data`, `packages/module-registry`, `packages/shared`, `modules/`, `services/`) — scaffolded by issue #21, in place before this issue starts.
- Requires the modules from issues #21–#28 as the retrofit target — without their existing code (schema engine, views, blocks, hardcoded databases, library, IMAP, inbox) the manifest cannot be validated against real examples.
- Requires the heartbeat/scheduler mechanism (heartbeat-fire) from issue #21, as consumed by issues #26–#28 — the drift-check `heartbeatAction` plugs into it as one more action, and the `heartbeatRuleKinds` wiring (see In scope) extends its validation union; it does not introduce a new scheduler from scratch.
- Requires `packages/queue` (graphile-worker, `registerTask`/`enqueueJob`, `CORE_TASK_NAMES`) from issue #21 — the runtime `TASK_NAMES` merge in this issue registers module tasks with that engine. Does not depend on `packages/agent-runtime` — that arrives in issue #30.
- Issue #30 (`pi-agent-core`) depends on this issue — it reads the `agentTools` and `capabilities` fields of the manifest defined here.
