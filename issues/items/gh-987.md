## Context

Two crontab sweeps close out agent-run state (`backend/packages/data/src/worker.ts:89,91`, handlers at `:213-218`).

**`agentRunEventsRetention`** runs daily at 04:20 and calls `handleAgentRunEventsRetentionTask` (`backend/packages/data/src/agentRuns/agentRunEventsRetention.ts:40-83`).
- One `pool.query` groups every conversation key `(project_item_id, triggered_by, parent_run_id)` with its latest `compaction` event id across the whole `agent_run_events` table (`:41-47`).
- It then deletes events older than 30 days, of finished `unit='session'` runs, below that id, in batches of 1,000, one transaction per batch (`:50-81`).
- The grouping is by key only. `agent_runs.project_item_id` is nullable (`backend/packages/data/src/db/migrations/0001_core_schema.sql:116`) and `agent_run_events.id` is one global `bigserial` (`backend/packages/data/src/db/migrations/0015_agent_run_events.sql:2`). Two tenants' conversations with equal keys would therefore share one `max(e.id)`: one tenant's later checkpoint would let the sweep delete the other tenant's post-checkpoint events, which reconstruction still reads.

**`mcpRunCredentialExpirySweep`** runs hourly at :10 and calls `handleMcpRunCredentialExpirySweepTask` (`backend/packages/data/src/mcp/mcpRunCredentialExpiry.ts:20-46`). In one transaction it:
- selects expired `agent_run_mcp_credentials` joined to `running` `triggered_by='mcp'` runs, `FOR UPDATE OF r SKIP LOCKED` (`:22-28`);
- calls `finishAgentRun(…, "done", …)` and `insertAndNotifyAgentRunEvent(… "run_status" …)` for each.

`agent_run_mcp_credentials` is a global table (its token is resolved before any tenant is known). `agent_runs` and `agent_run_events` are tenant tables, so in a tenant scope the join yields only that tenant's runs. The `run_status` event, and the realtime notification that carries the publisher's tenant once #1025 lands, are then written in the run's own tenant.

Tenancy state this issue builds on:
- Each tenant table carries `tenant_id` under a RESTRICTIVE RLS policy `tenant_isolation` (`tenant_id = (SELECT app_tenant_default())`, with `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())` over the GUC `app.tenant_id`).
- `withTransaction`, autocommit `pool.query` and `pool.connect()` clients set the GUC from the ambient scope: `runInTenant(tenantId, fn)` sets the tenant and `runAsSystem(reason, fn)` sets `''` (`@semprec/shared`).
- In system scope, tenant rows are visible only while exactly one tenant exists. With two tenants, or after the strict switch (#1067), both sweeps would find nothing.
- Both are `tenancy: 'system'` crontab tasks, so the task runner calls them inside `runAsSystem`.
- #983 added `forEachActiveTenant` (`backend/packages/data/src/tenancy/forEachActiveTenant.ts`, exported from `@semprec/data`). Called from a system scope, it runs the callback inside `runInTenant(tenantId, …)` for each tenant with `status = 'active'`, starting at a rotating offset. A throwing tenant does not stop the others. After all tenants were attempted, the failures are rethrown as one `AggregateError`, so the job is retried.
- This issue calls it as `forEachActiveTenant(pool, async () => …)`. If the merged signature differs, use the merged one.

The two sweeps are independent applications of the same fan-out; steps 1 and 2 can be reviewed separately.

## Acceptance criteria

All of these are integration tests (`*.test.ts`), with two tenants under the runtime role unless stated otherwise.
- **Retention is per tenant even for equal keys.** Tenant zero and tenant B each have a finished `unit='session'` conversation with the same key (`project_item_id` NULL, `triggered_by='user'`, `parent_run_id` NULL). Each conversation has events older than 30 days both before and after its own `compaction` event, and B's checkpoint id is lower than tenant zero's. One run produces all of the following:
  - each tenant's pre-checkpoint old events are deleted;
  - each tenant's own checkpoint and every event after it are kept, in particular B's events between B's checkpoint and tenant zero's checkpoint;
  - the returned `deleted` equals the total across both tenants.
- **Running runs untouched.** Old pre-checkpoint events of a `running` run are kept in either tenant.
- **Per-tenant expiry.** Tenant zero and tenant B each have a `running` mcp run whose credential expired, and B also has a `running` mcp run whose credential is still valid. One expiry run produces all of the following:
  - both expired runs become `done`, and both ids are returned;
  - the valid one stays `running`;
  - each new `run_status` event row carries its run's `tenant_id`.
- **Expiry failure isolation.** A test-only trigger raises on `agent_run_events` inserts for B's run. Tenant zero's expired run is still finished and committed, B's run stays `running`, and the handler rejects.
- **Inactive tenant.** A tenant whose `status` is `suspended` keeps its expired mcp run `running` and its old events.
- **Single tenant unchanged.** With only tenant zero, the existing retention and expiry test files pass.
