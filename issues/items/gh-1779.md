## Context

Model tier rationale: One registration of an already known module as a per-tenant cutover step, verified by an idempotency test, but it must also reach suspended tenants and run safely beside the seed's advisory lock.

#1776 seeds the sleep module for newly provisioned tenants only: `seedSystem.ts` returns early for an already seeded tenant, so a new system database never reaches existing ones by that path. The existing-tenant delivery step for a new system module is a per-tenant cutover call in `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`, one `forEachMaintainedTenant` pass run on every deploy through `runSeedCli` and `provisionTenant`; the existing `runTranscriptsCatalogCutoverMigration` is the model), and #1707 introduces it for Recipes. This issue registers the sleep module with that same step instead of writing a module-specific cutover.

After this issue every tenant, new or existing, has the three sleep databases, the settings item and the default plans of #1776. Later issues build on it: relating sleep settings to an area (#1833), enqueueing the iOS resync push (#1838) and marking databases as sensitive (#1808).

Decision: a sleep step is added to `runTenantCutoverMigrations`, following the per-tenant cutover pattern #1707 uses for Recipes. If an existing tenant already has any of the three sleep databases, the step leaves it untouched; it checks existence only and never repairs or alters an existing sleep database (changes to already delivered databases need their own idempotent step, see #1833).

Shared-file ordering: this issue also waits for #1712 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `db-migrations` and `testing`.

1. Register `seedSleepModuleInTransaction` (#1776) as one per-tenant cutover step in `runTenantCutoverMigrations` (the same pattern as the Recipes step of #1707): skip when `getDatabaseByModuleId(client, "sleepSettings")` finds the database (the three databases are always created together in one transaction), otherwise call the seed function with the tenant's Projects database id and the view type registry. The step already holds the seed's advisory lock (2331) and runs for every maintained tenant, including suspended ones.
2. Do not add the sleep module to any per-tenant data migration; do not change the seed function.
3. Tests: an existing tenant seeded before the sleep module (simulate by deleting the sleep rows or using a fixture seeded without the module) gets exactly the three databases, one settings item and two plans after the step, with the plan names in the tenant user's language ("Pracovní dny" and "Víkend" for a Czech user, #1776); a second run changes nothing (same ids, no extra items); a suspended tenant is covered; another tenant's data is untouched.

## Touches

- backend/packages/data/src/__tests__/ (existing-tenant delivery and idempotency tests)

## Scope

### In scope

- Delivering the sleep module to existing tenants through the shared step, and its idempotency test.

### Out of scope

- The module, databases and seed themselves: #1776.
- Altering an already delivered sleep database (new properties, relations): the issue that needs it adds its own idempotent step, for example #1833.
- Marking the databases as sensitive for existing tenants: #1808.
- Any new realtime or push behavior: #1838.

## Acceptance criteria

- When a deploy runs `provisionTenant` for an existing tenant without sleep databases, then the tenant has `sleepSettings`, `sleepPlans` and `sleepNights` (locked, `clientVisible` false), one settings item and the two default plans.
- When the same step runs a second time, then no row is added, changed or duplicated.
- When the tenant is suspended, then it is delivered the same way.
- When two tenants exist, then the step changes only the tenant it runs for.
