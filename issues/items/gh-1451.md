## Context

Model tier rationale: This adds persisted-data contract to a schema-locked, tenant-owned database through a per-tenant cutover with a backfill, and many later issues read and write the new properties, so a mistake in the shape or in idempotency is expensive to repair.

Processing proposals (`databases.owner_module_id = 'processingProposals'`) is the card store of the Inbox pipeline. Today `backend/packages/data/src/seed/seedInboxPipeline.ts` gives it the system-owned properties `kind` (inbox, transcript), `fingerprint`, `proposal` (json envelope), `history`, `status` (needsClarification, proposed, confirmed, rejected, invalid), `resultItemId` and `resultLabel`, plus the relations `sourceInbox` and `sourceTranscript`. The database is `schema_locked`, so a new property or select option on an already provisioned tenant needs both a seed change (fresh installs) and a per-tenant cutover in `backend/packages/data/src/db/tenantCutoverMigrations.ts` (today `runTranscriptsCatalogCutoverMigration` and `runTranscriptionRequeueHeartbeatCutoverMigration`, see `docs/adr/2026-09-10-app-code-post-migration-steps.md`). `parseStoredProposalEnvelope` drops any key of the envelope it does not know, and the card has nowhere to keep the state that the planned Inbox features need.

This issue adds all card-state properties in one cutover, so that the many issues that fill them neither collide on the seed and cutover files nor each re-run a cutover. Properties are system-owned; each is filled by the mechanism of a later issue (the producers of inbox and transcript cards, the revise and edit routes, the recognition and failure steps). This issue only declares them and backfills one of them.

Properties to add, all `owner: system`:

- `aiProposal` (json): the last proposal written by an automated producer, the base that "return to the assistant's proposal" restores.
- `userOverrides` (json): the user's manual field overrides.
- `userEditedKeys` (json): keys of fields the user edited by hand.
- `aiVersion` (number): counter of automated proposal versions.
- `reason` (text): localized explanation of a proposal, used only by cards of kind `inbox`.
- `recognizedTypeId` (text): id of the Inbox item type the assistant recognized for an untyped item.
- `typeCandidates` (json): candidate item types for an item that needs clarification.
- `candidates` (json): candidate events and speakers shown on transcript cards.
- `invalidReason` (json): structured reason a card is invalid.
- `referencedItemIds` (json): ids of items a proposal refers to.
- `results` (json): per-step confirm results.
- `context` (json): producer-written data of a transcript card (role, speaker, candidates, alternatives, reason). Only the producer of a card writes it and clients only read it; it never carries transcript text. The exact shape is defined by the issue that fills it (#1870 and the transcript producers); here it is only declared as an opaque json property.

`status` additionally gets the options `computing` and `computeFailed` (additive; no existing option changes).

Decision: `reason` is only for `inbox` cards and `candidates` stays a separate property from `typeCandidates`, as in the card design; transcript candidates, alternatives and reasons live inside `context`.

Decision: for existing cards `aiProposal` is backfilled with a copy of `proposal` (only where `proposal` is set and `aiProposal` is empty), so "return to the assistant's proposal" works on cards created before this change.

Shared-file ordering: this issue also waits for #1449 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `canonical-keys` and `testing`.

1. In `seedInboxPipeline.ts`, add the properties above to the Processing proposals property list with the types and `system` owner listed in Context, and add `computing` and `computeFailed` to the `status` select options. Keys are English camelCase.
2. Add the matching i18n names and option labels to the seed catalogs `backend/packages/data/src/inbox/i18n/en.json` and `cs.json` (the Inbox module catalogs, where the existing `processingProposals` labels live) (keys follow the existing pattern `property.processingProposals.<key>.name` and `property.processingProposals.status.option.<option>`).
3. Add a per-tenant cutover, in a new file `backend/packages/data/src/inbox/processingProposalsCardStateCutoverMigration.ts` following the lock, idempotency-check and bulk-backfill shape of `transcriptsCatalogCutoverMigration.ts`. It adds each missing property (raw SQL, because `propertiesStore.createProperty` refuses a locked database), adds the two missing `status` options, and backfills `aiProposal = proposal`. Properties get the same `owner_process` as the existing system properties of this database. It does nothing when the Processing proposals database does not exist yet (fresh install). Running it twice changes nothing.
4. Register the cutover in `runTenantCutoverMigrations` in `backend/packages/data/src/db/tenantCutoverMigrations.ts`.
5. Tests in `backend/packages/data/src/__tests__/tenantCutoverMigrations.test.ts` (or a sibling) for: a populated tenant gains every property and both options; `aiProposal` equals `proposal` on existing cards and a card without a proposal stays empty; a second run changes nothing; a fresh seed already has the same shape as a cutover tenant; a client cannot write a system property through the item PATCH path.

## Scope

### In scope

- Declaring the properties and status options on fresh and populated tenants, and the `aiProposal` backfill.

### Out of scope

- Writing or reading any of the new properties from proposal producers or routes. They are filled by #1471, #1495, #1500, #1648, #1482, #1848, #1978, #1640, #1975, #1485 and #1850.
- The zod schema and the role handling of `context`, and the revise route (#1870).
- Surfacing `computing` and `computeFailed` cards in the Inbox list (#1807).

## Acceptance criteria

- After the cutover a populated tenant's Processing proposals database has every property listed in Context, system-owned, and `status` accepts `computing` and `computeFailed`.
- When a card existed before the cutover with a `proposal`, then its `aiProposal` equals that `proposal`.
- When the cutover runs a second time, no row, property or option changes.
- A freshly seeded tenant has the same properties and options as a cutover tenant.
- Writing any new property through the generic item update API as a user is rejected because the owner is system.
