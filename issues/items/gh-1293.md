## Context

Model tier rationale: one known mechanism (two GitHub Actions jobs that call an existing entry point) across defined seams, with the pipeline itself already written and tested in `mobile/scripts/verify`; the uncertainty is runner toolchain setup, not a new contract.

#1292 added the mobile platform under `mobile/`: a Kotlin Multiplatform shared layer, a native Android app, and one SwiftUI codebase for iOS and macOS. Its whole pipeline runs through one entry point, `mobile/scripts/verify [all|architecture|shared|android|apple] [--ios-simulator <UDID>] [--android-serial <serial>]` (see `mobile/docs/verify.md`). `.github/workflows/ci.yml` builds and tests `backend/` and `web/` only. Today the mobile pipeline runs only where an author runs it by hand, and the instructions say so in several places.

This issue changes `.github/workflows/**`, a protected path (`.relay/config.yml` `protected-paths`). It is **maintainer-implemented and must not be dispatched to Relay**; it carries no `agent:ready`.

## Task

Add two jobs to `.github/workflows/ci.yml` that run the mobile pipeline on every pull request and every push to `develop`/`main` whose changes touch `mobile/**`:

- **`mobile-android`** on `ubuntu-latest`:
  - set up Node.js 22 and a Temurin JDK 17 (inside the 17–23 range `mobile/scripts/verify` enforces for Gradle 8.13);
  - use the runner's preinstalled Android SDK (`ANDROID_HOME`);
  - run `mobile/scripts/verify architecture android`.
- **`mobile-apple`** on a GitHub-hosted Apple-silicon macOS runner with Xcode 26 or newer:
  - set up Node.js 22 and a JDK 17;
  - install exactly the Tuist version in `mobile/apple/.tuist-version` and the SwiftLint version in the `swiftlint_version` line of `mobile/apple/.swiftlint.yml`;
  - select the Xcode with `DEVELOPER_DIR`;
  - run `mobile/scripts/verify shared apple`.

Both jobs:
- skip the device steps, which report NOT RUN without `--ios-simulator` / `--android-serial`;
- upload `mobile/build/verify/` as an artifact when the job fails.

Neither job becomes a required check in this issue.

Then make every document that says CI does not build `mobile/` true again, naming the two jobs and the device steps they do not run:
- `docs/operations/required-checks.md`: list `mobile-android` and `mobile-apple` as reported but not required;
- `.bb/AGENTS.md`;
- `.claude/skills/finish/SKILL.md`;
- `.bb/skills/implement-issue/SKILL.md`;
- `mobile/review-rules/context.md`, `mobile/android/review-rules/context.md` and `mobile/apple/review-rules/context.md`;
- a new ADR for the decision to run mobile CI only on changes under `mobile/` (`docs/adr/2026-10-24-monorepo-holds-backend-web-and-mobile.md` records that CI does not build mobile, and its body is frozen).

## Scope

### In scope
- The two jobs, their path condition, toolchain setup pinned to the repository's own pins, and the failure artifact.
- The document updates listed in Task.

### Out of scope
- Making either job a required check (a branch-protection change, admin only) and adding it to Relay's `wait-checks` or `REQUIRED_CHECKS`. That is a follow-up once the jobs have proven stable.
- Device steps in CI (simulators or emulators on runners).
- Running `mobile/scripts/verify` in the Relay workflows (#1294).
- Any change under `mobile/` other than the three review-rules context sentences.

## Acceptance criteria
- A pull request that changes a file under `mobile/` runs `mobile-android` and `mobile-apple`, and each job's log ends with the verify summary of its steps, all PASS except the device steps reported NOT RUN.
- A pull request that changes nothing under `mobile/` does not run either job's verify command, and its other checks are unaffected.
- A deliberately broken mobile change (for example a Kotlin compile error under `mobile/shared/`) makes the corresponding job fail. The uploaded `mobile/build/verify/` artifact contains the failing command's log.
- The Tuist and SwiftLint versions the `mobile-apple` job installs equal `mobile/apple/.tuist-version` and `swiftlint_version`. Verify's own version checks pass on the runner.
- `docs/operations/required-checks.md` lists both contexts as not required. No instruction file, skill or review-rules context still says that CI does not build `mobile/`.
