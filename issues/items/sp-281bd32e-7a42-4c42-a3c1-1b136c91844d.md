## Context

Model tier rationale: Touches the OAuth state machine and credential replacement for live accounts; a wrong scope merge silently breaks mail sync.

Google and Microsoft accounts hold mail-only scopes (`gmail.modify`, `gmail.send`; `Mail.ReadWrite`, `Mail.Send`, `offline_access`, `User.Read`). Calendars need `https://www.googleapis.com/auth/calendar` and `Calendars.ReadWrite`. New accounts ask for what the user switched on; existing accounts get additional consent when Calendars is switched on.

Decision: the granted scope set is stored per account (`mail_account_sync_state.granted_scopes`, text array) from the token response's `scope` field.
Decision: switching Calendars on for an OAuth account without the calendar scope sets the account's calendar status to `needsConsent` instead of syncing; the client then starts the consent flow.

## Task

Load `state-writes`, `db-migrations`, `error-handling`, `io-hardening`, `canonical-keys` and `testing`.

1. Make the OAuth provider settings per service: `PROVIDER_SETTINGS` gains calendar scopes; `POST /api/mail/mailboxes/oauth/start` accepts `{ provider, services: ["mail","calendars"] }` (default `["mail"]`) and stores the requested services in `mail_oauth_states` (new column `services text[]`).
2. Extend `POST /api/mail/mailboxes/:id/reauthorize` to accept `services` and to request the union of the account's enabled services; record the `scope` of the token response in `granted_scopes` on connect and reauthorize.
3. When `calendarsEnabled` turns true for an OAuth account whose `granted_scopes` lacks the calendar scope, keep the switch on and expose `calendarStatus: "needsConsent"` in the mailbox rows (the calendar sync issues read the same status).
4. Add `redirectTarget: "app"` to oauth/start: the stored state remembers it and `GET /api/mail/oauth/callback` then answers 302 to `semprec://oauth?state=…&code=…` instead of echoing JSON; the URL is built only from the stored state, never from the request.
5. Update `docs/architecture/domain-mail-and-inbox.md` (OAuth) and the operations env example with the calendar scopes; Google's consent screen must list the calendar scope.

## Scope

### In scope

- Scopes per service, consent for added services, the stored granted scopes and the app redirect.

### Out of scope

- Calendar sync itself.
- Client sign-in UI (mobile issue of this batch).

## Acceptance criteria

- When a Google account is connected with services mail and calendars, then the authorize URL asks for the Gmail and Calendar scopes and the account stores the granted scopes.
- When Calendars is switched on for a mail-only Google account, then its calendar status is `needsConsent` and mail sync is unaffected.
- When reauthorization with services mail and calendars completes for the same address, then the credential is replaced, the granted scopes include the calendar scope and the calendar status leaves `needsConsent`.
- When oauth/start was called with `redirectTarget: "app"`, then the callback answers 302 to `semprec://oauth` with the state and code; without it the JSON echo is unchanged.
- A different account address on reauthorization still answers `mail_reauth_wrong_account`.
