**Model tier:** medium

## Context

Model tier rationale: One more id-less tenant-wide scope on the established realtime catalog plus two after-commit publish calls in existing MCP write paths, following the preceding scope issues; the tenant isolation of the frame is the part that needs careful tests.

The project detail shows a summary row of the project's Semp setup with its tool count and attention dot, and #1866 publishes the `projectAgent` scope when one project's setup changes. Switching an MCP server on or off, or synchronizing its tools, changes the effective tools of every project that has grants on that server, and today no frame announces it.

The product owner decided that such a server-wide change sends one realtime event for the tenant, not one per project: the client then refreshes the summary of the projects it has open, and every other project is computed fresh when it is next loaded. The fan-out stays within the tenant.

This issue adds the realtime scope `mcpServers`, without payload fields, delivered to every socket of the tenant, following exactly the shape and wiring of the earlier scopes in this chain (#1951 and before): the `invalidation` message type with a `scope` discriminator in `backend/packages/realtime/src/pgNotifyPublisher.ts`, the `OutboundFrame` variant in `backend/packages/realtime/src/protocolV1.ts`, the `InvalidationEvent` variant in `backend/packages/data/src/realtimeHook.ts`, the mapping in `backend/packages/realtime/src/syncServer.ts` and the parser in `backend/packages/realtime-client/src/serverFrame.ts`. Rules of `docs/adr/2026-10-16-tenant-scoped-realtime-fan-out.md` apply: thin payload, tenant from Postgres, no replay, publish only after commit with `runAfterCommit`.

Decisions: (1) One frame per server-wide change, never one `projectAgent` frame per project. (2) The frame goes to every socket of the tenant (no `userId`): a sync is a background write with no acting user, and a tenant has one user. (3) The frame carries no ids; the client refreshes the open project summaries and tool lists.

Publication points (each publishes `mcpServers` once after commit):

- an update of an item of the MCP servers database whose patch contains `active` (the server switched on or off), in the item update hook `mcpServerItemUpdateHook` (`backend/packages/data/src/mcp/mcpServerWriteHook.ts`), which runs inside the write's own transaction;
- a successful tool synchronization in `syncMcpServerTools` (`backend/packages/data/src/mcp/mcpSync.ts`), in the transaction that writes the registrations.

## Task

Load `state-writes`, `canonical-keys`, `io-hardening` and `testing`.

1. Add the `mcpServers` variant to `InvalidationEvent`, `RealtimeMessage` (+ `parseRealtimeMessage`), `OutboundFrame` (`{ type: "invalidate", scope: "mcpServers" }`), the `invalidation` case of `syncServer.ts`, and `parseServerFrame`.
2. Create `backend/packages/data/src/mcp/mcpServersInvalidation.ts` exporting `publishMcpServersInvalidation(client)` that defers `notifyInvalidation({ scope: "mcpServers" })` with `runAfterCommit`.
3. Call it at the two publication points above, in the same transaction as the write. A failed synchronization (which leaves the registrations unchanged) does not publish.
4. Tests: a frame when a server's `active` is switched off and on, and after a successful sync; no frame for an update of an MCP server item that does not touch `active`, for a failed sync, or when the transaction rolls back; delivery reaches the sockets of the tenant only; the client parser accepts the frame and drops one with an unknown scope.

## Scope

### In scope

- The `mcpServers` scope end to end and its publication when a server is switched on or off and after a successful sync.

### Out of scope

- A `projectAgent` frame per project for server-wide changes (decided against: one tenant-wide frame instead).
- Changes of one project's setup: #1866.
- Creating or deleting an MCP server item; clients re-read when the screen opens.
- The client refresh of the open project summaries (client work) and the project summary route.

## Acceptance criteria

- When a person switches an MCP server off or on, then every socket of the tenant receives exactly one `invalidate` frame with scope `mcpServers` and no ids.
- When a tool synchronization of a server succeeds, then the tenant's sockets receive one `mcpServers` frame; when it fails, then none.
- When the transaction rolls back, then no frame is sent.
- When a socket of another tenant is connected, then it does not receive the frame.
- No `projectAgent` frame is published per project for a server-wide change.
