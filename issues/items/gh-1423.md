## Context

Model tier rationale: One shared closed enum threaded through generic operation metadata, the MCP snapshot and the approval table, plus a backfill-then-CHECK migration; the pieces follow existing patterns but the persisted-data constraint needs care.

Product behavior: every action that needs approval carries one risk class from a single fixed list, so the approval screen, pushes and the agent prompt describe risk consistently.

Today `backend/packages/shared/src/genericOperations/capabilities.ts` defines `RiskClass = "destructive"`; `OPERATION_METADATA` gives the five approval-gated operations `riskClass: "destructive"` and every other operation `riskClass: null`. `approval_requests.risk_class` is free text without a CHECK (migration 0021); it receives the generic operation's class or a copy of `mcp_tool_registrations.risk_class`, which is free text defaulting to `'unclassified'` (migration 0020) and settable to any string through `setMcpToolRiskClass` in `backend/packages/data/src/mcp/mcpGrantsAdminStore.ts`. `mail/send.ts` lets an agent send e-mail without approval when the grant `emailSendAutonomous` exists; this issue does not change `mail/send.ts` (the send flow is #1913).

#1730 builds the reversibility and risk level on this set; #1979, #1913 and #1713 use it; a module added later that needs another class extends the closed set.

Decision: the closed set is `unclassified`, `read`, `write`, `destructive`, `outbound`, `breaksLink`. Reading operations are `read`, other non-destructive operations are `write`, the five approval-gated operations stay `destructive`.

Decision: the CHECK is added to `approval_requests.risk_class` only, after unknown values are backfilled to `unclassified`. Validating `mcp_tool_registrations` writes and its CHECK is owned by #1979. Until then the snapshot into an approval request maps an unknown registration value to `unclassified`, so inserts can never violate the CHECK.

Decision (product owner): `outbound` applies to every outbound action, including an e-mail sent by an agent, not only to MCP tools. In v1 every such send goes through approval and autonomous sending is not switched on. This issue only defines the value; producing `outbound` requests is #1713 and #1913.

## Task

Load `db-migrations`, `state-writes` and `testing`.

1. In `capabilities.ts` replace the type with a runtime-exported closed list `RISK_CLASSES = ["unclassified", "read", "write", "destructive", "outbound", "breaksLink"] as const`, `type RiskClass`, and `isRiskClass(value: string): value is RiskClass`; re-export from the package barrel.
2. `OperationMetadata.riskClass` becomes non-null `RiskClass`: `database.list|get|query`, `property.list|get|getByKey`, `view.list|get|query`, `item.get` are `read`; the other non-destructive operations are `write`; `database.archive`, `property.delete`, `view.delete`, `item.delete`, `relation.delete` are `destructive`. Update the `nonDestructive`/`destructive` helpers and the call site in `preflightDestructiveApproval` (remove the non-null assertion). `requiresApproval` is unchanged.
3. Migration `backend/packages/data/src/db/migrations/NNNN_approval_requests_risk_class_check.sql` (next free ordinal at commit time): `UPDATE approval_requests SET risk_class = 'unclassified' WHERE risk_class NOT IN (<the six>)`, then `ALTER TABLE approval_requests ADD CONSTRAINT approval_requests_risk_class_check CHECK (risk_class IN (<the six>))`.
4. Row mapping in `approvalRequestsStore.ts` validates `risk_class` with `isRiskClass` and types `ApprovalRequest.riskClass` as `RiskClass`; `createPendingApprovalRequest` takes `RiskClass`. In `createApprovalGatedMcpInvokeTool`, normalise the registration's `riskClass` to a known value (unknown becomes `unclassified`) before inserting.
5. Add `riskClass.*` label keys for the six values in Czech and English to the client catalog.

## Scope

### In scope

- The shared closed class list, operation classification, the approval table CHECK with backfill and the normalised MCP snapshot.

### Out of scope

- A CHECK or validated PATCH on `mcp_tool_registrations.risk_class`, and defaults from MCP annotations: #1979.
- Reversibility and the derived risk level: #1730.
- Producing `breaksLink` and `outbound` requests: #1713 and #1913.
- Changing which operations require approval.

## Acceptance criteria

- Every generic operation in `OPERATION_METADATA` has a `riskClass` from the closed list; reads are `read`, the five approval-gated ones are `destructive`, other writes are `write`.
- When the migration runs on a database with an approval request whose `risk_class` is not in the list, that row reads back as `unclassified`; afterwards an insert with an unknown class fails at the database.
- When an MCP tool whose registration holds an unknown class raises an approval request, the request is created with `unclassified`.
- `isRiskClass` accepts exactly the six values.
- Czech and English labels exist for all six values.
