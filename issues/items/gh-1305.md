## Behavior specification

Approvals: source routing, list, description, risk, execution state, push and MCP.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

#### Decisions adopted

- Source column on approval_requests? -> No; source is derived at read time (thread kind, else root run's triggered_by via iterative parent walk). Reason: thread link also exists on delegated runs; avoids a migration.
- Heartbeat started from chat: chat or tick? -> tick. Reason: design note rule, follows the run that raised the request.
- MCP server/tool names on source or operation? -> on the operation (safeSummary), for every source; resolved at read time, null if the server item is gone.
- Default filter for the approvals list (chat only or all)? -> Decided by the product owner: all sources; the approvals list is one general list and filtering by source is optional. No-params response unchanged, filtering is opt-in (#1785). Reason: additive-only contract.
- Search q -> unaccent ILIKE over thread title, heartbeat name, tool/operation name and description.params strings; not payload values, not full text.
- Who owns PATCH `outcome`? -> Decided by the product owner: the title of #1786 describes only what it does (reading one request and counting pending ones); the decision outcome is #2022.
- Description storage -> template key + params, never rendered text; old rows NULL; endsInheritance omitted until value-link work; MCP description carries only {serverName, toolName}.
- May the MCP approval description carry argument values (recipient, subject)? -> Decided by the product owner: partly. The description and the push never contain argument values; the detail of one request in the app shows them to its owner (for example recipient and subject), because an outgoing action cannot be decided responsibly without them (#2021, with credential-like values redacted).
- Should the impact on linked items appear on Semp's approval requests too? -> Decided by the product owner: yes; the approval card of a Semp request must show the number of linked items and the "Ends the link" warning, because Semp never ends a link silently. The backend already returns the description with `linkedCount` (and `endsInheritance` once filled) on every view (#1683, #1786); the card is client work.
- Does `outbound` also apply to an agent sending e-mail? -> Decided by the product owner: yes, the outbound flag applies to every outbound action, including e-mail sent by an agent. In v1 every send goes through approval; autonomous sending is not switched on (#1423; the send flow #1913 is adjusted accordingly).
- Which agent-run step data may the "details in the agent run" link expose? -> Decided by the product owner: only the structure of the steps: tool, state, time, link to the approval and a localized result summary. Arguments, results, model text and raw errors are not shown, the same as for `conflictReason` (#1847).
- Reason argument -> `reason` for generic ops, `semprecReason` for MCP, stripped by the wrapper, max 500 chars, not logged.
- Risk class set -> unclassified/read/write/destructive/outbound/breaksLink; CHECK only on approval_requests after backfill; unknown MCP registration values normalised to unclassified on snapshot; registration CHECK left to #1979.
- Reversibility -> item.delete and database.archive reversible; property/view/relation delete irreversible (no restore path exists in schema); MCP destructive = irreversible.

#### Open questions for the product owner

- None remaining for this chunk.

#### User-visible behavior

Approval requests now say where they came from. A request raised in a chat with Semp lives in that chat (a pending section with a count, a badge on the bubble, a card in the thread); requests from automatic tasks and external MCP clients go to the Inbox. The approvals screen lists pending and decided requests, newest first, filtered by source and searchable, and can reopen a single request and show a pending count. Each request describes in plain, localised words what will happen and what it affects (for example how many items lose a value, also for Semp's own requests), shows its owner the values of an outgoing MCP action in its detail, may carry Semp's own reason, and is labelled irreversible, outbound or link-ending only when that is true (deleting an item, which can be restored for 30 days, is not called irreversible). Deciding twice shows "already decided" instead of an error. MCP requests name the server and the tool.


### Decisions: approvals-2

#### (a) Decisions adopted from open questions
- Link from request to tool call is one-directional and nullable -> requests without a tool call id (non-agent paths, old rows) keep NULL -> avoids backfill and keeps all non-agent paths unchanged.
- Realtime approval invalidation is delivered only to the request owner's sockets inside the tenant -> matches the thin user-scoped invalidation ADR; no leakage to other users of a tenant.
- conflictReason exposes only a translation key, never raw error text -> execution results can contain argument values and resource content.
- MCP failure causes are made distinguishable by a closed outcomeKind written next to the result (toolUnavailable, callFailed, staleClaim); old rows fall back to approval.conflict.other -> the previous plain string cannot be classified.
- Outcome message in the thread: no message for runs without a thread; one message per request and outcome (idempotent on job redelivery); no new turn is created.
- Conflict and failed MCP call both post approval.outcome.conflict from the thread-message issue (see open question 1).
- Live approval state on steps is read at request time in one batched query; the stored step summary is never rewritten; a foreign or missing request yields approval: null.
- Notification body is rendered at write time in the recipient locale from the description key and params plus a reversibility sentence; never includes MCP argument values.
- APNs approvalRequestId travels in the payload, taken from source_id; no new column. Category APPROVAL_REQUEST; time-sensitive interruption level decided by the preference mechanism of the notification-preferences issues.
- Notification links: chat request -> ?page=semp-chats&tab=semp&approvalRequestId=<id>; tick or MCP request -> ?page=inbox&approvalRequestId=<id>; unknown source falls back to Inbox; user=<userId> dropped. The ApprovalRequiredError link returned to agents is left unchanged.
- MCP initialize: supported protocol versions 2025-06-18, 2025-03-26, 2024-11-05; echo the client's version if supported, else the newest; serverInfo.version is the API package version; notifications without id answer 202 empty; non-POST answers 405 with Allow: POST.
- MCP client name: trimmed, control characters stripped, truncated to 64, display only; a repeated initialize overwrites; only run-credential callers write it.

#### (b) Open questions remaining for the product owner
1. Dependency gap: #1772 cannot distinguish a failed MCP call from a conflict without the outcomeKind added by #1437, and the DAG has no edge between them. Either add an edge #1437 -> #1772 (then #1772 can post approval.outcome.failed) or accept that failed is posted as conflict for now.
2. Page names for notification links (semp-chats, inbox, tab=semp) must be confirmed with the clients.
3. Should /mcp calls made with a human session (no run credential) also go through approval of destructive operations? Today they execute immediately; unchanged here.
4. If a mail-sending example stays in the Inbox card design, who creates the draft that the card links to? The backend has none for MCP calls.

#### (c) User-visible behavior of this chunk
A person who asked Semp to do something risky sees the request in the right place and its fate follows it: the request is tied to the exact step of the conversation that raised it, and after the person approves or rejects it (on any device) the card in the chat updates live from "waiting" to "approved and done", "rejected" or "not done because the data changed", with a reason when it did not run. The conversation gets a short system note about the result, so Semp knows in its next turn what happened, and the chat list preview shows the request as handled. The push notification now says "Semp needs approval", states what Semp wants to do and whether it can be undone, can be approved or rejected straight from the lock screen, breaks through focus mode, and opens the chat tab for requests from a chat or the Inbox for requests from automatic tasks and MCP clients. MCP clients such as Claude Desktop can complete the standard handshake, and requests raised by their runs show which client they came from.


### Decisions: approvals-3

#### (a) Adopted decisions
- Where does `outcome` live in the response? -> top-level field beside the existing decision-view fields -> additive-only REST contract; no envelope change.
- Should `GET /api/approval-requests` also carry it? -> no -> outcome describes a single decide call, not stored state.
- Should the web client change here? -> no -> backend-only issue; client work is separate.

#### (b) Open questions for the product owner
- None remaining. Decided by the product owner: the decision outcome clause is dropped from the title of #1786; the outcome is delivered by #2022.

#### (c) User-visible behavior
When a user approves or rejects an approval request, the app can now tell whether this tap actually made the decision or the request had already been decided (for example from a notification action on another device). In the second case the app can show "Already decided" instead of a false confirmation. Nothing else about deciding changes: only the owner can decide, anyone else gets the same not-found answer.
