## Context

Model tier rationale: One guard inside an existing choke-point helper that moves relation edges, one log line that gains a field, and tests on the merge's existing harness. It adds no table, route or column and changes no authorization, but the helper decides which edges of a merged Journal entry stay behind, so a wrong guard would drop or keep a link.

Source #1726 added `mergeJournalDuplicates` (`journal/mergeJournalDuplicates.ts`). It moves each edge of the user-owned Journal relations from the duplicate to the survivor with `moveRelationEdgesWithClient` (`chokePoint/relationOps.ts`), and the Inbox `journalDay` edges with `moveJournalDayEdges`, which calls the same helper. For each edge the helper first asks `relationCreationRefusal` (the checks of `assertRelationCreatableWithClient`) whether the edge could be created on the receiving item. An edge the choke point refuses stays on the duplicate and is returned in `refused`, which the merge returns as `refusedEdges` and writes as one `info` line of the `journal` logger after the commit. Only after that check does the helper delete the edge from the duplicate and call `createRelationIfAbsentWithClient`, which leaves an edge the survivor already has as it is (its metadata is kept and the duplicate's copy is only deleted).

The recheck of #1726 found two defects that were left open (`issues/handovers/gh-1726.md`, "Follow-ups"; both verified against the code at the integration tip):

1. The refusal check comes before the "already has it" case. When both entries are linked to the same item and that item is in the Trash, the check refuses the edge for the survivor because its other endpoint is not live, although the survivor already holds exactly that edge. The merge then reports the edge in `refusedEdges` and logs it, and leaves the duplicate's copy behind, although nothing is lost. A caller that tells the user from `refusedEdges` would report a lost link that is not lost.
2. The log line carries the refusal's `code`, which is always `validation_failed`, and not its `field`, so it does not say why an edge was refused. `field` is what tells the refusals apart: `callerItemId` or `targetItemId` for an endpoint that is in the Trash or missing, the property key (for example `area`) for a value derived from the item's project, and `null` for an edge a domain edge-write hook refuses. It holds only a fixed name, no user content. The accepted ADR of #1726 says "The line carries no `field`, name or content"; this source narrows that sentence, so it needs its own ADR (accepted ADR bodies are never edited).

Both changes keep the shape of `MoveRelationEdgesResult`, `RefusedRelationEdge`, `MergeJournalDuplicatesResult` and the lock order of the merge.

## Task

Load `state-writes`, `error-handling`, `testing` and `adr-conventions`.

1. In `moveRelationEdgesWithClient` (`chokePoint/relationOps.ts`), for each edge of `fromItemId`, before `relationCreationRefusal` runs: normalize the edge as it would be written for `toItemId` (`normalizeRelationSides` with the relation definition already loaded by the helper) and read it with `relationsStore.getItemRelationByTuple`. When the receiving item already holds that edge (same relation definition, same two items, same orientation), delete the edge of `fromItemId` through `deleteRelationWithClient` with the same arguments as today, count it in `moved`, and write nothing on `toItemId`: no `relationCreationRefusal`, no `createRelationIfAbsentWithClient`, and no entry in `refused`. Every other edge keeps today's path (refusal check, then delete, then `createRelationIfAbsentWithClient`). Update the docstring of `moveRelationEdgesWithClient` and of `RefusedRelationEdge`: an edge the receiving item already holds is never reported as refused, whatever state its other item is in.
2. In `journal/mergeJournalDuplicates.ts`, add `field` to the fields of the existing `info` line (`survivorId`, `mergedItemId`, `relationPropertyId`, `otherItemId`, `code`, and now `field`, which is `null` when the refusal names none). Keep the message text and the `runAfterCommit` registration. Update the docstring of `mergeJournalDuplicates` (its text says the line carries "ids and the refusal's code only") and the comment above the log loop.
3. Add `docs/adr/<date>-a-journal-merge-does-not-refuse-an-edge-the-survivor-holds-and-logs-the-field-of-each-refusal.md` (the date is the day it is written; `area: [backend]`, `supersedes: []`, standalone). Its Context references `[[2026-11-10-journal-duplicate-merge-locks-the-reservation-before-both-entries]]` and says that it narrows two statements of that record without editing it: an edge the survivor cannot take is refused "for an item in the Trash" also when the survivor already holds that edge, which it now never is, and "the line carries no `field`, name or content", which now carries `field`. The Decision states both rules and why: the first so that `refusedEdges` names only edges that were really left behind, the second so that the log line says why (`field` is one of a fixed set of names: `callerItemId`, `targetItemId`, a property key, or `null` for a domain hook, never an item's name or content). Its Consequences say that the sentence "an edge to a trashed item does not reach the survivor when that item is restored later" holds only for an edge the survivor did not already have.
4. Tests, in `__tests__/mergeJournalDuplicates.test.ts` (the existing harness and describe of #1726; the existing tests are not weakened):
   - both entries are linked to the same Area (a user-owned Journal relation, no project on either entry), the Area is moved to the Trash, and the merge runs: the result has `refusedEdges: []`, the survivor keeps its edge to the Area, the duplicate has no edge to it any more, and the refused-edge log is not called;
   - the same with the Area live: unchanged result, the survivor's edge keeps its own metadata (the existing test "keeps an edge the survivor already has as it is" still passes);
   - an edge only the duplicate has, to an Area in the Trash, is still left on the duplicate and reported with `field: "targetItemId"` (the existing refusal test still passes);
   - every refused-edge log call carries `field` with the same value as the matching `refusedEdges` entry (`"targetItemId"` for the trashed endpoint, `"area"` for the stored area against a derived one, `null` for the hook refusal), and the existing exact `toEqual` expectations of the log calls are updated to include it;
   - the existing test of the relation with a cardinality limit still fails with the insert's `CardinalityViolationError` and changes nothing.

## Scope

### In scope

- Not reporting, not logging and not refusing an edge the receiving item already holds, in the generic edge move.
- The `field` of a refusal in the merge's log line.

### Out of scope

- The result shapes (`MoveRelationEdgesResult`, `RefusedRelationEdge`, `MergeJournalDuplicatesResult`), the code of a refusal and the lock order of the merge.
- The Inbox `journalDay` move beyond what the generic helper changes for it: `inbox/moveJournalDayEdges.ts` is not edited.
- Moving an edge whose creation is refused by cardinality (the move still fails with the insert's `CardinalityViolationError`, as documented).
- Any other caller of `moveRelationEdgesWithClient` (it has no other caller today; if one appears, it gets the same rule through the helper).
- The operation that calls the merge (#2017) and its answer.

## Acceptance criteria

- When both Journal entries of a period are linked to the same item that is then moved to the Trash, then the merge returns `refusedEdges: []`, logs no refused edge, the survivor keeps its edge and the duplicate keeps none.
- When only the duplicate is linked to an item in the Trash, then the edge stays on the duplicate and is returned in `refusedEdges` with `field: "targetItemId"`, as before.
- When the merge leaves a refused edge behind, then the `info` line carries `field`, equal to the `field` of the matching `refusedEdges` entry, `null` when the refusal names none.
- When an edge the survivor already holds has other metadata than the duplicate's, then the survivor's metadata is kept, as before.
- The ADR of this source exists and the accepted ADR of #1726 is not edited.
