## Context

PR #356 (`registry.ts`) flagged that `ModuleRegistry.loadModule` calls
`loadModuleCatalogs(path)` (async file I/O) before `assertExportsExist` and
`assertDataMigrationsReferenceOwnDatabases` (pure synchronous checks over the
already-parsed manifest). When a module fails either synchronous check, the catalog
file reads that already ran are wasted work — the module load will be rejected
regardless of what's on disk.

## Task

In `backend/packages/module-registry/src/registry.ts`'s `loadModule` method, reorder
the calls so `assertExportsExist(path, manifest, imported)` and
`assertDataMigrationsReferenceOwnDatabases(path, manifest)` run before
`loadModuleCatalogs(path)`. `assertCatalogKeysAvailable` still runs after
`loadModuleCatalogs` since it needs the loaded catalogs. No other call in this
sequence is reordered.

## Touches

- backend/packages/module-registry/src/registry.ts (`loadModule`)

## Scope

### In scope

- Reordering the four calls named above so the two synchronous checks precede the
  catalog load.

### Out of scope

- Any other check or ordering in `loadModule`.

## Acceptance criteria

- Loading a module whose manifest fails `assertExportsExist` throws that error
  without `loadModuleCatalogs` having been called (observable via a spy on the
  catalog loader in a test).
- Loading a module whose manifest fails `assertDataMigrationsReferenceOwnDatabases`
  throws that error without `loadModuleCatalogs` having been called.
- Loading a valid module still succeeds and its catalogs are loaded and committed as
  before.
