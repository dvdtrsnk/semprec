## Context

Model tier rationale: Extends the existing atomic confirm with a loop of edge writes following the transcript-card precedent in the same transaction, with existing fixtures, so mainly rollback behavior needs care.

A confirmed Inbox proposal today creates one item (`confirmProposalWithClient` in `backend/packages/data/src/inbox/proposalActions.ts` calls `createItemWithClient` with the envelope's `properties` only). #1426 lets a `database` envelope carry `relations` (`{ [relationPropertyKey]: targetItemId[] }`) and validates them while the card is built or edited, but confirm ignores them, so a confirmed task would be created without its project. A transcript card already shows the needed pattern: its confirm creates an Event and then the Transcripts-to-Event edge through `createRelationWithClient` in the same transaction.

This issue makes confirm write the item and all of its edges as one unit.

Decision: the edges are written after the item is created, in the order of the keys and ids in the envelope, each through `createRelationWithClient` with the new item as caller; a failure of any single edge aborts the whole transaction (no item, no edges, the card still `proposed`) and surfaces the edge's own canonical error with `details.field` set to the relation key. Targets are validated again by the write itself (existence, archived databases, ownership, cardinality), which is the full check; the pre-checks of #1426 are advisory.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In `confirmProposalWithClient`, after `createItemWithClient` for a `database` envelope (and its credential and transcript-edge steps), resolve each `relations` key to the relation property of the target database and call `createRelationWithClient` for every target id; reuse `requireRelationPropertyId`-style lookup; wrap errors so `details.field` carries the relation key.
2. An empty `relations` or none at all behaves exactly as before. The idempotent early return for an already `confirmed` proposal is unchanged and writes no edges again.
3. Tests: a task proposal with `relations: { project: [<id>] }` confirms into a task plus the project edge in one transaction; a nonexistent target id gives 400 with `field` `project` and no task exists afterwards; a cardinality violation on the second relation rolls back the item and the first edge; a repeated confirm does not duplicate edges; a transcript card confirm is unchanged.

## Scope

### In scope

- Writing the envelope's relations in the confirm transaction with all-or-nothing behavior.

### Out of scope

- Validation of relations before confirm (#1426).
- Multi-step confirm and moving an existing item (#1486).
- Rejecting derived relations (#1991).

## Acceptance criteria

- When a task proposal with `relations: { project: [<project id>] }` is confirmed, then the task and the `Tasks.project` edge exist after one transaction.
- When a relation target id does not exist, then confirm returns 400 with `field: "project"` and no task is created and the card stays `proposed`.
- When the second of two relations fails, then no item and no edge from this confirm exists.
- When a confirmed proposal is confirmed again, then it returns as-is and no edge is created twice.
