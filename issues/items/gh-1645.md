## Context

Model tier rationale: One extended upload route that creates an edge in the same transaction as the file, reusing an existing transaction-aware upload variant, but it adds a caller-chosen target id that needs tenant-safe validation and cleanup of streamed bytes on failure.

Attaching a file to an item (a lab result to a health record, later a document to a task or an event) takes two requests today: `POST /api/files` (`backend/services/semprec-api/src/filesHandler.ts`, `Content-Type` and `X-Filename`, streamed body, 201 for a new file and 200 for an identical upload) and then `PUT /api/items/:fileId/relations/healthRecords/:recordId`. The two are not atomic, and a failure between them leaves a file nobody linked. `ingestUploadedFile` (`backend/packages/data/src/blobs/fileUploadStore.ts`) opens its own transaction. #1574 adds a transaction-aware variant that runs a caller function with the open client after the Files item is resolved; this issue uses it.

This issue adds two optional headers to `POST /api/files` so the file and its edge commit together. It becomes the single owner of attaching an upload to an item: #1654 (tasks) and #1698 (events) use these headers instead of their own.

Decisions:
- Headers: `X-Attach-To-Item` (uuid of the target item) and `X-Attach-Relation` (the key of a relation property on the Files database that leads to the target's database, for example `healthRecords`). Both or neither; one without the other is 400 `validation_failed` with `field` the missing header. Without them behavior is unchanged.
- A target that is unknown, trashed, or in another tenant answers the same 404 (no enumeration). A relation key that is not a relation of Files to the target's database answers 400 `validation_failed` with `field: "X-Attach-Relation"`. Nothing is stored in either case, and streamed bytes are deleted.
- An identical upload (`created` false) reuses the existing Files item and only adds the edge; an edge that already exists is a no-op; the response is 200. A new file is 201.
- The picker for an existing file stays the plain `PUT` on the relation; no change.

Shared-file ordering: this issue also waits for #1642 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `io-hardening`, `error-handling`, `state-writes` and `testing`.

1. In `filesHandler.ts` read the two headers and validate them before reading the body: uuid format; both-or-neither; the relation key must be a relation property of the Files database whose other side is the target item's database; the target item must exist, not be trashed and belong to the caller's tenant (a read-only query that answers 404 identically for unknown and foreign ids).
2. Call the transaction-aware upload variant from #1574 with a function that, in the same transaction, re-checks the target is live, and creates the edge with `createRelationWithClient` (`backend/packages/data/src/chokePoint/relationOps.ts`) so cardinality and edge hooks apply; an existing edge is skipped.
3. Map errors: target gone inside the transaction gives 404 and rolls the file back; a cardinality violation keeps its 409.
4. Add the cases to `backend/services/semprec-api/src/routeMatrix.ts` (if the entry needs the headers noted) and `backend/services/semprec-api/src/__tests__/tenantIsolationRoutes.test.ts`.
5. Tests: upload with `X-Attach-To-Item` of a health record and `X-Attach-Relation` `healthRecords` returns 201 and the edge exists; the same bytes attached to a second record return 200 with one Files item and two edges; repeating the same request is a no-op with 200; an unknown or foreign target returns 404 and no blob, Files item or edge exists; relation key `neznamy` returns 400 with `field` `X-Attach-Relation`; one header alone returns 400; without the headers the route behaves as before.

## Scope

### In scope

- The `X-Attach-To-Item` and `X-Attach-Relation` headers on `POST /api/files`, their validation, and creating the edge atomically with the file.

### Out of scope

- The transaction-aware upload variant itself: #1574.
- Using the headers from tasks and events: #1654 and #1698.
- Creating an item together with its relations: #1590.
- Reading the attachments of an item: #1404 and #1518.
- Taking the area, project or company of the file from the target.

## Acceptance criteria

- When a file is uploaded with `X-Attach-To-Item` of a health record and `X-Attach-Relation` `healthRecords`, then the response is 201 and the Files item is linked to the record.
- When the same content is uploaded for a second record, then the response is 200, there is one Files item, and it has two edges.
- When the target does not exist, is trashed or belongs to another tenant, then the response is 404 and no blob, file or edge is created.
- When `X-Attach-Relation` is not a relation from Files to the target's database, then the response is 400 with `field` `X-Attach-Relation` and nothing is created.
- When neither header is sent, then the route behaves as before.
