**Blocked by:** #624

## Context

`backend/services/semprec-ai-gateway/src/structuredProviders/anthropicProvider.ts` performs exactly one `fetch` per `complete()` and turns every non-2xx status into a `ProviderCallError` (the `!res.ok` branch), which `completeHandler.ts` maps to **502 `provider_failed`**. Anthropic answers 429 (rate limited) and 529 (overloaded) routinely and transiently, and both carry a `retry-after` header; a single such response currently fails the whole gateway call, and the caller — `packages/ai-gateway-client/src/httpAiGatewayClient.ts`, which also fails fast on any non-2xx — surfaces `AiGatewayFailedError("http")`. Nothing retries at any layer. The retry belongs in the gateway's adapter (the one place that sees the provider's status and headers) and nowhere else, so a request is never retried at two layers.

E3 (see the pull request that closed it) threaded `request.signal` into this adapter and combined it with the 55 s timeout; this issue reuses that signal so a retry loop stops as soon as the caller is gone, and turns the per-attempt timeout into one deadline shared by all attempts (a retry must never push the route past the client's 60 s budget).

## Task

In `anthropicProvider.ts`:

- Module constants: `MAX_ATTEMPTS = 3`, `RETRY_BASE_DELAY_MS = 500`, `RETRY_MAX_DELAY_MS = 8_000`, `RETRYABLE_STATUSES = new Set([429, 529])` plus any `500 <= status <= 599`. Keep `ATTEMPT_DEADLINE_MS = 55_000` as the single deadline for the whole `complete()` call.
- Create the deadline signal **once** per `complete()`: `const deadline = AbortSignal.timeout(55_000); const signal = request.signal ? AbortSignal.any([deadline, request.signal]) : deadline;` and pass the same `signal` to every attempt's `fetch`.
- Retry loop around the `fetch` + status check: on a retryable status, cancel the body (E5's `res.body?.cancel()`), compute the delay as `min(RETRY_MAX_DELAY_MS, retryAfterMs ?? fullJitter(RETRY_BASE_DELAY_MS * 2 ** (attempt - 1)))` where `retryAfterMs` parses the `retry-after` header as integer seconds or as an HTTP-date (both are valid; ignore an unparsable value), and full jitter is `Math.random() * base`. Sleep on a timer that also resolves early when `signal` fires; after the sleep, if `signal.aborted`, throw `ProviderCallError` naming the abort reason (`TimeoutError` for the deadline, `AbortError` for the caller) — do not start another attempt. If the remaining time to the deadline is smaller than the computed delay, do not sleep and do not retry: throw the `ProviderCallError` for the last status.
- A `fetch` rejection (network error) is **not** retried — that is today's behaviour and the transport-failure contract `completeHandler.ts` documents. Only the listed statuses are. A non-retryable status (400, 401, 403, 404, ...) throws immediately as today.
- The final `ProviderCallError` message for exhausted retries is `Anthropic responded with HTTP <status> after <n> attempts`.
- Log nothing inside the adapter (it has no logger today); the handler's existing error log covers the final failure.

Unit tests in `backend/services/semprec-ai-gateway/src/structuredProviders/__tests__/anthropicProvider.unit.test.ts` (`vi.useFakeTimers()` + `vi.stubGlobal("fetch", fetchMock)` with `mockResolvedValueOnce` sequences; `vi.spyOn(Math, "random").mockReturnValue(0.5)` to fix the jitter):

- 529 then 200 → resolves with the tool_use input; `fetch` called twice; the second call happened only after the jittered delay elapsed (`advanceTimersByTimeAsync`).
- 429 with `retry-after: 2` then 200 → the second `fetch` happens no earlier than 2000 ms.
- 429 with `retry-after` as an HTTP-date 3 s in the future then 200 → second `fetch` no earlier than ~3000 ms.
- 500 three times → rejects with `ProviderCallError` whose message ends `after 3 attempts`; `fetch` called exactly three times; every non-2xx `Response`'s body was cancelled.
- 400 → rejects after one `fetch`.
- 529 then the request's signal is aborted during the backoff → rejects with `ProviderCallError` before any second `fetch`.
- both `fetch` calls receive the same `signal` object.

## Scope

### In scope

- The retry loop, backoff, `retry-after` parsing, the shared deadline, and the unit tests above.

### Out of scope

- Retries in `deepInfraWhisperProvider.ts` / `pyannoteProvider.ts` (re-sending a 100 MiB upload is a different trade-off) and in either HTTP client (`httpAiGatewayClient.ts`, `audioGatewayClient.ts`).
- Retrying network-level `fetch` rejections.
- Changing the 55 s deadline, the client's 60 s budget, or `completeHandler.ts`'s error mapping.
- Any change to `completeHandler.ts`, `structuredProviders/types.ts` or the audio adapters.

## Acceptance criteria

- When Anthropic answers 429 or 529 and then 200 within the deadline, `POST /internal/complete` answers 200 with the second response's content and the settled `ai_gateway_calls` row carries the second response's usage.
- When Anthropic answers a retryable status three times, the route answers 502 `provider_failed`, exactly three provider requests were made, and the reservation row is `'failed'`.
- A `retry-after` header (seconds or HTTP-date) is honoured as the minimum wait before the next attempt, capped at 8 s.
- No retry starts after the caller disconnects or after the 55 s deadline, and the total time a `complete()` call can take stays under 55 s.
- `pnpm run test:unit` (in `backend/`) passes with the new tests.
