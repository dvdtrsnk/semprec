## Context

Model tier rationale: One known mechanism (update and create hooks that validate and normalize a single module's items) across the same hook files as the previous calendar issue, with a transactional default-switch that needs a lock, but no new cross-process or authorization contract.

#1600 seeds the `calendars` database and #1761 assigns Events to it. Nothing yet protects its rows. A generic write of the system-owned `kind` and `systemKey` is already rejected with 403 by the choke point's ownership check, but a client can still rename a system calendar, store a malformed colour, or leave the tenant with zero or two default calendars. This issue adds the rules for the module's own rows, as hooks in the same files and registration as #1761.

Rules, applied on create and update of a calendar:

- `name` of a calendar whose `kind` is `system` or `subscription` cannot change: 403 `forbidden` (field `name`). `color`, `hidden` and `notify` can.
- `color` must match `#RRGGBB` (six hexadecimal digits): otherwise 400 `validation_failed` (field `color`).
- Exactly one live own calendar has `isDefault` true. Setting `isDefault` true on a calendar clears it on the previous default in the same transaction. Setting it true on a system or subscription calendar is 400 (field `isDefault`). Clearing it on the only default, without setting another, is 400 (field `isDefault`).

Decision: the default switch takes a transaction-scoped advisory lock keyed by the Calendars database id before it reads or changes any `isDefault`, so two concurrent switches serialize and the tenant never ends with two defaults.

Deleting a calendar (including the default) is #1803; a default that is deleted passes the flag on there.

Shared-file ordering: this issue also waits for #1777 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `backend/packages/data/src/calendar/calendarRowHooks.ts` exporting `calendarItemCreateHook` and `calendarItemUpdateHook`, applying only to the Calendars database, implementing the rules above. The default switch writes the other row through `updateItemWithClient`; the new default is written first so the clearing of the old one is never the removal of the only default.
2. Register both hooks in `backend/packages/data/src/domainWriteHooks.ts`.
3. Tests: renaming `Birthdays` and the holidays (both system) and a subscription calendar is 403, renaming `Work` works; `color` `#FF9500` passes, `blue` and `#FFF` are 400 with field `color`; setting `isDefault` on `Work` clears it on `Personal` in one transaction; setting it on `Birthdays` is 400; clearing it on `Work` while it is the only default is 400; creating a calendar with `isDefault` true switches the default; a generic write of `kind` or `systemKey` stays 403; two concurrent switches leave exactly one default.

## Scope

### In scope

- The name, colour and single-default rules for calendar rows on create and update.

### Out of scope

- Seeding the rows and the ownership of `kind` and `systemKey`: #1600.
- Assigning calendars to Events: #1761.
- Deleting and restoring calendars and passing the default on deletion: #1803.
- Per-device syncing of visibility and colour: the generic item invalidation already carries it.

## Acceptance criteria

- When a client renames a system or subscription calendar, then the response is 403 `forbidden`; a rename of an own calendar succeeds.
- When a client sends a colour that is not `#RRGGBB`, then the response is 400 `validation_failed` with field `color`.
- When a client sets `isDefault` on another own calendar, then the previous default is cleared in the same transaction and exactly one default remains.
- When a client sets `isDefault` on a system calendar or clears it on the only default, then the response is 400 with field `isDefault`.
- When a client writes `kind` or `systemKey`, then the response is 403.
