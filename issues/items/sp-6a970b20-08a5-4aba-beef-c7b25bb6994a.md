## Context

Model tier rationale: One catalog-writing startup step, its transaction and lock, and a concurrency test on a fresh database.

End-to-end finding on the dev server, verified in the code: on a clean deploy alldots-api, alldots-agents and alldots-transcribe start together, and each queue runtime runs `ensureQueueSchema` then `grantQueueSchemaPrivileges` (`backend/packages/queue/src/index.ts`). The grant step (`GRANT ... ON ALL TABLES/SEQUENCES/FUNCTIONS IN SCHEMA graphile_worker`, `ALTER DEFAULT PRIVILEGES`, `CREATE POLICY alldots_side_all`) updates the same catalog rows in every process, and Postgres refuses the second concurrent update of one catalog row: alldots-agents crashed with `DatabaseError: tuple concurrently updated` (XX000, `heapam.c simple_heap_update`) at `grantQueueSchemaPrivileges` <- `createAgentsQueueRuntime`, and systemd restarted it. Reproduced locally: six concurrent grant calls on a fresh `graphile_worker` schema fail in every round.

The other startup steps shared by several services were checked: graphile-worker's own `runMigrations` (in `ensureQueueSchema` and again in `runWorker`) inserts each migration's row first and treats a unique violation or an existing schema as another process's success, and the search task registration is `INSERT ... ON CONFLICT DO NOTHING`; neither failed in the concurrent runs. The data migrations run only in the deploy CLI, and the remaining startup steps are service-specific.

Decisions:

- `grantQueueSchemaPrivileges(client)` runs inside a transaction and first takes the transaction advisory lock `(2335, 0)`, so a second process waits for the first commit, re-grants what is already granted and finds the policies present.
- `@alldots/queue` cannot import `withTransaction` (`@alldots/data` depends on it), so `installQueueSchema(pool)` in `@alldots/data` (`db/queueSchema.ts`) runs `ensureQueueSchema` and then the grants in one `withTransaction`, under `runAsSystem("queue-schema")`. Every caller of the old two-call pair calls it instead.
