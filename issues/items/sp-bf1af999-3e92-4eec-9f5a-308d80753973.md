## Context

Model tier rationale: Removes several upgrade mechanisms that span the seed, the migration runner's checks, deploy tooling, CI, the architecture and operations documents and the agent instructions, and must tell each upgrade-only path apart from a runtime feature that looks similar, without weakening tests of kept behaviour.

Owner decision (David, 2026-11-21), recorded verbatim in `issues/decisions/sp-bf1af999-3e92-4eec-9f5a-308d80753973.md`: Alldots has never been released. Until the owner's first real production deployment, the backend assumes it is the very first version: no schema versioning, no migrations beyond the single baseline, no upgrade, carry or reconcile paths for existing databases, and no compatibility code for older data shapes. The dev VPS database is wiped and recreated on every deploy; the operator wipes it separately, outside `deploy.sh`. The switch to production rules is a future, separate change made at the owner's first production deployment.

The repository still carries machinery written for upgrading an existing database: the additive reconcile of already seeded tenants (`seed/seedReconcile.ts`, `readFreshSystemSeed`, `runSeedCli.js --strict`), the production cutover runbook and its dry-run script, the lexical expand/contract compatibility check with its example migrations, the migration-ordinal check that only polices future migration files, and reader fallbacks or operator tools that exist only for rows an older code version wrote. The documents and agent instructions state forward-only, expand/contract rules "after the first production release".

Load `implement-issue`, `adr-conventions`, `db-migrations`, `state-writes`, `testing`.

1. Rules. `.bb/AGENTS.md` ("What this repository is strict about" item 3 and every other mention of migrations, expand/contract, backfills or cutovers), `.bb/skills/db-migrations/SKILL.md`, `.bb/skills/implement-issue/SKILL.md`, `backend/review-rules/`, `.github/ISSUE_FORMAT.md`, `docs/architecture/migrations-and-seeding.md` (and its index rows in `docs/architecture/README.md`), `docs/architecture/delivery-and-operations.md`, `docs/operations/migrations.md`, `docs/operations/releases.md`, `docs/operations/tenancy.md`, `docs/operations/seeding.md` and `deploy/README.md` state as current fact: the backend handles no versions and no migrations and always assumes the first version; a schema change edits `0001_baseline.sql` and the seed in place; no backfill, data cutover, reconcile of already seeded tenants or compatibility branch for old data; the deployed database is recreated from the baseline; production rules are introduced at the owner's first production deployment.
2. Remove the seed reconcile: `seed/seedReconcile.ts`, `readFreshSystemSeed`, the reconcile step of `runSeed`, the `--strict` option of `runSeedCli`, their tests and docs. The seed provisions a fresh tenant and leaves an already provisioned tenant as it is.
3. Remove the production cutover tooling: `deploy/scripts/cutover-dry-run.sh`, `docs/operations/production-cutover-to-develop.md` and every reference.
4. Remove the expand/contract compatibility check (`db/migrationCompatibility.ts`, `db/migrationExamples/`, both `migrationCompatibility` tests) and the migration-ordinal check (`scripts/check-migration-numbering.mjs`, its package script, its `verify` and CI steps). `runMigrations` keeps applying the baseline to an empty database.
5. Remove any other code that exists only to upgrade or read data written by an older code version (operator reindex tools for columns added later, repairs of states no current writer produces, legacy-shape reader fallbacks, tests that set up such states), deleting tests that only cover removed code. Runtime features that look similar stay. Each removal is listed with its reason in the handover.
6. Deploy on a wiped database: `deploy.sh` migrates the baseline, seeds and verifies tenancy on an empty database; no reset step is added to `deploy.sh`.

## Scope

### In scope

- The rule change in instructions and documents, and removing upgrade-only code, tooling and tests.

### Out of scope

- The production rules themselves (forward-only, expand/contract, versioning), introduced at the owner's first production deployment by a separate change.
- A database reset step in `deploy.sh`.
- Runtime features: property type changes, search reindexing after edits, mail and calendar sync reconcile, idempotent provisioning.
- Agent skills installed outside the repository; the handover lists which still state the old rule.
- Anything under `mobile/`; connecting to any server.
