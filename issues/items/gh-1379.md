## Context

Model tier rationale: Documentation-only decision record, but it carves an exception into an accepted decision and must state the exact reversal rules the next issue implements.

Confirmed and rejected Processing proposals are locked: the code treats `confirmed` and `rejected` as final (`LOCKED_PROPOSAL_STATUSES` in `backend/packages/data/src/inbox/inboxTypesStore.ts`; the Inbox tick, revise and reject honor it), and the card-ownership decision in `docs/adr/2026-09-23-processing-proposals-card-creation-owned-per-kind.md` describes post-creation actions as confirm, reject and revise. The Inbox needs an undo of the last decision, which for a confirmed card means reversing writes across several databases, a pattern with no precedent in the repository and a real alternative (never allow undo; or only undo before follow-up jobs start).

#1943 implements the undo of a confirmed proposal and must follow the contract recorded here.

## Task

Load `adr-conventions`.

1. Add `docs/adr/2026-10-25-undoing-a-confirmed-proposal-reverses-its-recorded-writes.md` with the frontmatter from `docs/adr/README.md` (`status: accepted`, `area: [backend]`, `supersedes: []`). It does not edit the older ADR's body; it states it narrows the "a confirmed or rejected card never changes again" rule by naming the reopen routes as the only exit.
2. Record the decision: a confirmed card can be reopened in one transaction, driven by the per-step results and origin rows recorded at confirm, with these reversal rules:
   - Items created by the confirmation are soft-deleted (their relation edges stay and return with a restore), except the file below.
   - A Files item that received an Inbox attachment moved at confirm stays in Files (there is no reverse operation of the move); the undo result names it explicitly so the user can move it to the trash.
   - Relation edges created between items that already existed (link steps, a transcript card's event or speaker edge) are deleted for good.
   - Items patched by the confirmation get the values they had before restored.
   - Page blocks inserted by the confirmation are removed by the ids derived from the proposal.
   - A credential stored for a connected MCP server is deleted.
   - The card returns to `proposed` with its original effective envelope; history gains a `reopened` entry.
3. Record the precondition: every item created or changed by the confirmation must still have the `updatedAt` stored in the card's results; otherwise the undo is refused with 409 `version_conflict` carrying the changed item, because undoing over a later edit would destroy it; the refusal names the changed item so the client can explain it, and nothing is overwritten.
4. Record the follow-up processes: queued jobs started by a confirmation are cancelled and what they would have produced is removed (a queued transcription and the transcript item it creates, a queued MCP tool sync); see #1984.
5. Record that there is no time limit, and that approval requests (decided through the approvals route with exactly-once execution) are not undoable by this mechanism; the exactly-once decision for approved destructive operations is not changed. An executed approved action is reverted by restoring from the trash or by a new change.
6. Record the alternatives rejected (forbid undo; undo only before follow-ups; a time window).

## Scope

### In scope

- The decision record only.

### Out of scope

- Any code; the undo itself is #1943 and the cancellation of follow-up jobs is #1984.
- Reopening a rejected card; #1937.
- Undo of approval requests (decided not to be supported; it would change the exactly-once ADR for approved destructive operations).

## Acceptance criteria

- The ADR exists with valid frontmatter and states the reversal rule for each kind of write listed above.
- The ADR states the `updatedAt` precondition and the 409 behavior.
- The ADR names the approval requests as out of the mechanism and states the absence of a time limit.
- The ADR states that a file moved into Files at confirm stays there and is named in the undo result.
- No existing ADR file body is edited.
