**Model tier:** high

## Context

Model tier rationale: A one-shot scheduled job enqueued from the AI gateway's refusal path must fire at an exact time boundary and stay idempotent across processes and restarts, and it is not yet settled which process may enqueue into the job queue.

#1871 derives the "Limit exhausted, resets at {time}" problem (`aiBudgetExhausted`) in `GET /api/semp-status` at read time, and the gateway publishes one Semp status invalidation of #1868 at the first refusal in a window caused by the tenant's cap (#2023). When the window rolls over (the next midnight, or the first day of the next month, in the tenant's time zone, as `resetsAt` of #1456 reports it), the problem disappears from the next status read, but a connected client is not told, so it keeps showing the exhausted problem until it re-reads the status on its own.

This issue adds a one-shot job that runs at the `resetsAt` instant and publishes the same Semp status invalidation, so clients drop the exhausted problem when the window resets.

Decisions: (1) The job is enqueued together with the first refusal's invalidation, with a job key made of the tenant and the reset time, so a second enqueue for the same window is a no-op. (2) `runAt` equals `resetsAt`. (3) The job only publishes the invalidation; it reads and writes no budget data.

## Task

Load `ai-gateway`, `state-writes` and `testing`.

1. Add a tenant-scoped one-shot job next to the existing tenant jobs in the data package that publishes the Semp status invalidation of #1868 for its tenant, following `state-writes` and the existing tenant-scoped job conventions.
2. In `assertWithinBudget` (`backend/packages/ai-gateway/src/gateway.ts`), at the same point where the first tenant-cap refusal of a window (`tenantDaily` or `tenantMonthly`) publishes its invalidation, enqueue that job with the job key `(tenant, resetsAt)` and `runAt` = `resetsAt`, after the refusal's transaction has rolled back. An enqueue failure is logged with the tenant id only and swallowed; the refusal is unchanged. If the gateway process cannot enqueue, enqueue from the process that owns the queue after receiving the same signal and say so in the pull request.
3. Tests: the first tenant-cap refusal enqueues one job with `runAt` equal to the reset time in the tenant's time zone (daily and monthly); a second refusal in the same window enqueues nothing new; running the job publishes one invalidation for the tenant and the next status read no longer lists the exhausted problem; an operator-wide refusal and a missing budget row enqueue nothing; an enqueue failure leaves the refusal unchanged.

## Touches

- backend/packages/ai-gateway/src/gateway.ts (enqueue the reset-time job with the first tenant-cap refusal)
- the scheduled job file for the reset-time invalidation (new, in the data package next to the existing tenant jobs)
- the job registration list of the process that runs tenant jobs (one entry)
- backend/packages/ai-gateway/src/__tests__ (new cases for the enqueue)
- the data package tests of the new job (new)

## Scope

### In scope

- The one-shot reset-time job, its idempotent enqueue with the first tenant-cap refusal, and the invalidation it publishes.

### Out of scope

- The status problems: #1871.
- The invalidation at the first refusal: #2023.
- A missing budget row has no reset time and gets no job.
- Any change to what the gateway refuses or to the refusal message.

## Acceptance criteria

- When a tenant's daily cap is first reached, then a job is scheduled for the next midnight in the tenant's time zone; for the monthly cap, for the first day of the next month.
- When further calls are refused in the same window, then no further job is scheduled.
- When the reset instant passes, then a Semp status invalidation is published once for that tenant and the next status read no longer lists the exhausted problem.
- When only an operator-wide cap refuses a call, then no job is scheduled.
- The gateway refusal behaves exactly as before, including when enqueueing fails.
