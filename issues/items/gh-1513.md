**Blocked by:** #1387, #1087
**Model tier:** medium

## Context

Model tier rationale: Input validation on two public, unauthenticated account-creation paths plus one export field, using an existing column and existing flows, with one of the paths owned by a not-yet-merged issue.

#1387 adds the nullable `users.display_name` column and returns it with the user, but nothing writes it: `createUser` (`backend/packages/data/src/auth/usersStore.ts`) takes `email`, `passwordHash`, `locale`, `tenantId` and `role`. Accounts are created through two public routes. `POST /api/setup` (`backend/services/semprec-api/src/setupHandler.ts`) takes `{ email, password }` and calls `bootstrapFirstAccount` (`backend/packages/data/src/auth/authActions.ts`) for the very first account. Invitation acceptance, delivered by #1087, takes `{ token, password }` and creates the invited account in one transaction. The account export (`accountEntry` in `backend/packages/data/src/tenancy/tenantExportJob.ts`) writes `email`, `locale`, `role` and `createdAt` for the account, so the name should appear there once it exists.

Decision: `displayName` is optional on both routes. Absent or `null` stores `NULL`. A string is trimmed and must be 1 to 80 characters after trimming; otherwise the request fails with a 400 `validation_failed` carrying `field: 'displayName'`. A blank string is invalid, not silently turned into `NULL`.

## Task

Load `io-hardening`, `error-handling` and `testing`.

1. Add `displayName?: string` to `CreateUserInput` and write it to `users.display_name` in `createUser`.
2. Add one shared validator in `backend/packages/data/src/auth` (for example `normalizeDisplayName(value: unknown): string | null`) implementing the decision above, with the 80-character limit as an exported constant, and use it in both routes.
3. `POST /api/setup`: accept optional `displayName`, validate it before any account work, pass it through `bootstrapFirstAccount` (`BootstrapFirstAccountInput`) to `createAccount`.
4. Invitation acceptance: accept the same optional `displayName` next to `token` and `password` in the route and store function delivered by #1087, and pass it to `createUser` in the same transaction. Validation happens before the token is consumed, so an invalid name does not burn the invitation.
5. Add `displayName` to the object `accountEntry` writes in `tenantExportJob.ts`.
6. Tests for each path: a valid name is stored and returned by `GET /api/auth/session`; omitted gives `null`; 81 characters, a blank string and a non-string give 400 with `field: 'displayName'`; for invitation acceptance an invalid name leaves the invitation usable; the export file contains `displayName`.

## Scope

### In scope

- Optional `displayName` at first-account setup and invitation acceptance, its validation, and its presence in the account export.

### Out of scope

- The column and the read paths: #1387.
- Editing the name after account creation. Decided by the product owner: it comes with the design of the editing screen.
- Showing the name in the administrator account list.

## Acceptance criteria

- When `POST /api/setup` carries `displayName: "  David  "`, then the created user's `displayName` is `David`.
- When `displayName` is omitted on setup or invitation acceptance, then the account is created with `displayName: null`.
- When `displayName` has 81 characters, is blank, or is not a string, then the request returns 400 `validation_failed` with `field: 'displayName'` and creates nothing.
- When invitation acceptance fails validation of the name, then the invitation can still be accepted afterwards.
- The account export contains `displayName` (`null` when unset).
- The full backend `pnpm run verify` passes.
