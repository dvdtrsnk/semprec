**Blocked by:** #2006
**Model tier:** high

## Context

Model tier rationale: Inbound mail rewrites fields of a user's Event, and the rule that a field the user edited is never overwritten has to be decided per field against the value the invitation last supplied, under the per-`UID` lock of concurrent deliveries; a mistake silently overwrites user data.

#1929 creates an invitation from an iMIP `REQUEST` and, for a higher `SEQUENCE` of a known `UID`, updates it only while it is `pending`; for an answered invitation it changes nothing. #1944 lets the user answer: `accepted` and `tentative` create an Event from the invitation's title, place and times (converted to wall-clock values in the tenant time zone) and link it through the invitation's `event` relation; `declined` trashes it. #1954 notifies only when an invitation is first created.

When the organizer moves an already accepted meeting, the user's calendar must follow without losing the user's own changes. This issue applies a higher-`SEQUENCE` `REQUEST` to an answered invitation and its Event.

Decision (product owner): an organizer's update is written into the Event created from the invitation as an adopted value that stays until the user's first change: a field the user has not changed takes the new value, a field the user has changed keeps the user's value. The user's answer stays as it is.

Decision: "not changed by the user" means the Event's current stored value equals the value the invitation's previous fields produce through the same invitation-to-Event mapping #1944 uses. No extra copy of the adopted values is stored.

Decision: the update creates no notification (#1954) and sends nothing to the organizer.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. Move the invitation-to-Event field mapping of the respond handler (`backend/packages/data/src/calendar/invitationRouteHandlers.ts`, from #1944: title, place, `date`, `endDate`, `timeFrom`, `timeTo` from `startsAt`, `endsAt`, `allDay` and the tenant time zone) into `backend/packages/data/src/calendar/invitationEventFields.ts` as a pure function `invitationEventFields(invitation, timeZone)`, and call it from the respond handler without changing its behavior.
2. In `createInvitationIngestAction` (`backend/packages/data/src/calendar/invitationIngestAction.ts`), under the existing per-`UID` advisory lock, handle a `REQUEST` with a higher `SEQUENCE` for an invitation whose `status` is `accepted`, `tentative` or `declined`:
   - compute the old Event fields from the stored invitation and the new ones from the parsed `VEVENT` with `invitationEventFields`;
   - update the invitation's parsed fields, `sequence` and `sourceEmail`, keeping `status` and `respondedAt`;
   - when the invitation has a live linked Event, write through the choke point (`updateItemWithClient`) only the Event fields whose stored value equals the old computed value and whose new computed value differs; leave every other field as stored. A trashed Event (after `declined`) is not touched.
   A `cancelled` invitation and an equal or lower `SEQUENCE` still change nothing. A failing Event validation rolls back the whole email's transaction and is logged with the email item id and a reason code.
3. Tests (in `backend/packages/data/src/calendar/__tests__`): for an accepted "Sprint review" 13:00-14:00 on 22 Oct 2026, an update to 14:00-15:00 moves the Event and keeps status `accepted`; after the user renamed the Event, an update that changes title and place keeps the user's title and writes the new place; after the user moved the Event to 16:00, an organizer's time change leaves 16:00; a declined invitation gets the new fields while its trashed Event stays unchanged; an equal `SEQUENCE` changes nothing; no notification is written; the respond handler's tests from #1944 still pass with the extracted mapping.

## Scope

### In scope

- Applying a higher-`SEQUENCE` `REQUEST` to an answered invitation and, field by field, to its live Event, and extracting the shared mapping.

### Out of scope

- Updating a pending invitation: #1929.
- Organizer cancellations: #2006.
- Resetting the user's answer, notifying the user, or sending a reply on an update.
- Recurring invitations: not in v1.

## Acceptance criteria

- Given an accepted invitation whose Event the user has not edited, when the organizer moves the meeting to 14:00-15:00, then the Event is at 14:00-15:00 and the invitation is still `accepted`.
- Given the user renamed that Event, when the organizer changes the title and the place, then the Event keeps the user's title and shows the new place.
- Given the user moved the Event to 16:00, when the organizer changes the time, then the Event stays at 16:00.
- Given a declined invitation whose Event is in the trash, when an update arrives, then the invitation's fields are updated and the trashed Event is unchanged.
- When the update has an equal or lower `SEQUENCE`, or the invitation is `cancelled`, then nothing changes.
