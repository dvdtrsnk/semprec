## Context

`repairInterruptedRuns(pool)` (`backend/packages/agent-runtime/src/startupRepair.ts:35-70`) is the startup orphan repair: every `agent_runs` row still `status='running'` after a process restart was abandoned mid-flight, so it closes each one as `error` with reason `interrupted_by_restart` (writing the `agent_run_error` notification in the same transaction) and appends a synthetic `tool_result` after an unpaired trailing `tool_use`. Its docstring (lines 18-21) says "#91 must call this function first, before installing its graphile-worker runner" — but no file under `backend/services/` calls it. `backend/services/semprec-agents/src/serve.ts` goes straight from `loadFullModuleRegistry()` (line 30) to `createAgentsQueueRuntime` (line 34), and `backend/services/semprec-agents/package.json` does not even depend on `@semprec/agent-runtime`.

Consequence: a crashed run stays `running` forever, and if its last event is a `tool_use`, `validateProtocolInvariants` in `backend/packages/agent-runtime/src/conversationReconstruction.ts:100-103` throws `reconstructed history has N unmatched tool_use call(s)` on every later wake of that conversation.

One class of `running` rows is not an orphan: `mintMcpRunCredential` (`backend/packages/data/src/mcp/mcpRunCredentialAction.ts:69-74`) creates a root run with `triggered_by='mcp'` whose only purpose is to authenticate `POST /mcp` calls for up to `MCP_RUN_CREDENTIAL_TTL_SECONDS` (1 h); no in-process session drives it, so a restart does not interrupt it. Repairing those rows would close every live MCP credential and emit one `agent_run_error` notification each on every restart. Their lifecycle (closing them when the credential expires) is #643; this issue only excludes them from repair.

Sibling issue #647 (agent sessions from `semprec-agents`) builds on the dependency and the `serve.ts` ordering this issue introduces.

## Task

1. Add `"@semprec/agent-runtime": "workspace:*"` to `dependencies` in `backend/services/semprec-agents/package.json` and refresh `backend/pnpm-lock.yaml` (`pnpm install` from `backend/`). Check `backend/dependency-cruiser.rules.json` / `backend/packages/module-boundaries` still pass with a service depending on `@semprec/agent-runtime` (`semprec-api` already does not; `agent-runtime` already depends on `@semprec/data`, `@semprec/application`, `@semprec/realtime`, `@semprec/shared`, `@semprec/module-registry`).
2. In `repairInterruptedRuns` (`startupRepair.ts`), skip rows whose `triggeredBy === "mcp"` (the `AgentRunRow` field, `backend/packages/data/src/agentRuns/agentRunsStore.ts:20`): they are neither closed nor given a synthetic `tool_result`, and are not included in `repairedRunIds`. Document why in the docstring (credentialed MCP runs are closed by their credential's expiry sweep, not by restart). No change to `listRunningAgentRuns`.
3. In `backend/services/semprec-agents/src/serve.ts`, after `loadFullModuleRegistry()` and before `createAgentsQueueRuntime(...)`, call `const { repairedRunIds } = await repairInterruptedRuns(pool);` and log `logger.info({ repairedRunCount: repairedRunIds.length }, "Repaired interrupted agent runs")`. It runs to completion before the queue runner is installed, so no `heartbeatFireAgent`/`agentRun` job can be claimed while the sweep is in flight. A failure of the repair is fatal for startup (let it throw; `installFatalHandlers` already logs and exits non-zero). Shutdown ordering (`backend/services/semprec-agents/src/shutdown.ts`) is unchanged: the repair is a one-shot startup step with nothing to stop, consistent with `docs/adr/2026-09-17-shutdown-ordering-with-late-heartbeat-stop.md`.
4. Tests:
   - Extend `backend/packages/agent-runtime/src/__tests__/startupRepair.test.ts` (integration): a `running` run with `triggeredBy: "mcp"` is left `running`, gets no synthetic event and no notification, while a `running` `heartbeat` run with a trailing `tool_use` in the same sweep is closed and paired.
   - New `backend/services/semprec-agents/src/__tests__/startupRepairComposition.test.ts` (integration): a helper `runStartupSequence(pool, moduleRegistry)` is not extracted — instead the test imports `repairInterruptedRuns` and `createAgentsQueueRuntime` and calls them in the same order `serve.ts` does, with a `running` run whose last event is `tool_use` and a `running` `triggered_by='mcp'` run present beforehand. It asserts: the first is `status='error'`, `result='interrupted_by_restart'`, its events end with a `tool_result` carrying `error: true`; the second is still `running` with no new events; and only then does the queue runtime start (assert the runtime handle is returned after the repair resolved).

## Scope

### In scope
- The dependency, the `triggered_by='mcp'` exclusion, the `serve.ts` call before the queue runtime, and the two tests above.

### Out of scope
- Closing MCP-credential runs when their credential expires (#643).
- Running agent sessions, `registerPiProviders`, `agentRun` job handlers (#647); this issue does not touch `queueRuntime.ts`.
- Any change to the shutdown sequence or to `listRunningAgentRuns`.

## Acceptance criteria

- When `semprec-agents` starts with `agent_runs` rows in `status='running'` whose `triggered_by` is `heartbeat`, `user` or `supervisor`, each is `status='error'` with `result='interrupted_by_restart'` and an `agent_run_error` notification before the first queue job is claimed; a row whose last event was `tool_use` has a trailing synthetic `tool_result` with `error: true`.
- When such a row has `triggered_by='mcp'`, it is still `status='running'` after startup, with no new `agent_run_events` and no notification.
- When `repairInterruptedRuns` throws, `semprec-agents` exits non-zero without starting its queue runner.
- `backend/services/semprec-agents/package.json` lists `@semprec/agent-runtime` and `pnpm install --frozen-lockfile` succeeds.
