## Behavior specification

Health records: schema, select options, writes with relations and Inbox voice notes.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: health-1

#### Adopted from open questions
- "Who" (David / Heduš / Max (dog)) as text with facets, or a select -> stays text; the filter and the Inbox card get their offer and counts from facets (#1990); no cutover of the locked schema (a related issue point 4, variant a) -> Decided by the product owner: stays text with the offer taken from facets; there is no separate option list, and both the filter and the Inbox card take the values generically from facets.
- May users or the assistant create tags -> only via the new option operations (#1699, REST only) and a confirmed Inbox proposal (#1994); not exposed to agent/MCP tools; both wait for a card design that marks a new value -> Decided by the product owner: only through the option operations and a confirmed Inbox proposal; Semp cannot create options through tools. A schema change is sensitive and must be approved by the user.
- Label equal to an existing option (case/diacritics insensitive, cs and en) -> 409 `option_label_exists` carrying the existing key (#1699) -> Decided by the product owner: as stated; the client then uses the existing option, so no duplicates arise.
- Select validation scope -> user and agent writers only, changed keys only, unchanged stored values accepted (#1802).
- Link between follow-up task and health record -> new Tasks.healthRecords <-> HealthRecords.tasks many-to-many (#1836), not a "Regular check-ups" project and not unlinked -> Decided by the product owner: the new many-to-many relation; a general relation is cleaner than a detour through a project.
- Area for a record created from the Inbox -> the card carries no Area of its own; when the record has a project, its area is derived from the project as for every item (#1595), without a project it stays empty (#1836) -> Decided by the product owner: not as an own value; derived from the project when there is one, otherwise empty.
- Quote saved to the record page -> no -> Decided by the product owner: no; the quote stays with the proposal as its source and the record page belongs to the user.
- "Add..." on attachments -> both flows: upload with `X-Attach-To-Item` (#1645) and picking an existing file with the existing relation PUT -> Decided by the product owner: both flows, the same attachment pattern as for tasks and events.
- Files list subtitle "date - Health record" -> derived from the Files.healthRecords edge via include=relations (no backend work).
- Text values of the target database offered to the model -> only when the read is permitted for the Semp project (#1990) -> Decided by the product owner: as stated; health data never reach the model without an explicit permission.
- New tag order -> appended after existing four (#1700).

#### Open questions for the product owner
- Projects on a health record: the backend has HealthRecords.projects (many-to-many) but the design has no Projects property. Add it to the design (area then derived from the project), or remove the relation by a contract migration? No issue is written until decided.
- Default date of a new record: the design shows an empty date; confirm (property defaults give "today" only to Files.date).
- Should the 4 colors of Epilepsy and Dental hygiene be defined?
- Does the audit before #1802 find non-catalog values in real data (to be run by the implementer)?

#### Delivered behavior
Health records get two more tags, Blood pressure and Prevention, with colors, for every tenant. The server now refuses select and multi-select values that are not in the property's options when a person or the assistant writes an item or when an Inbox proposal is revised or confirmed. The assistant is told the target database's allowed options and the names already in use, so "doctor: blood pressure 135/85" is proposed as a record with the Blood pressure tag. A follow-up check can be proposed as a task linked to the record. A file can be uploaded and attached to a record in one request. When a design is available, users can add and rename options on the system collections, and a confirmed proposal can create a new tag; the assistant never creates an option without the user's confirmation.
