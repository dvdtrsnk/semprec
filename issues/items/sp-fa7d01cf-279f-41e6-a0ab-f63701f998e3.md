### Requirement gh-1401: [recipes 01/04] Upload standalone image blobs and collect unused ones

#### Context

Model tier rationale: A new streamed upload route and a periodic cleanup job built from existing seams (the file upload store, blob reference check, per-tenant fan-out), with a shared reference-count rule that must not delete a blob still in use.

Today `POST /api/files` (`services/semprec-api/src/filesHandler.ts`, `blobs/fileUploadStore.ts` `ingestUploadedFile`) streams bytes to storage, de-duplicates the blob by content hash and always creates a Files item (returning the existing one with HTTP 200 on a hash match). There is no way to upload an image that is only a blob, for use in an image property such as a recipe photo, a book cover or an Inbox attachment. `deleteBlobIfUnreferenced` (`blobs/blobsStore.ts`) counts only `properties.file.blobId` and `mail_attachments` as references, so deleting a Files item whose bytes equal an image property's blob would purge that blob. Blob bytes are removed best effort after the commit (`docs/adr/2026-09-28-blob-bytes-deleted-best-effort-after-the-commit.md`) and tenant export reads bytes from the files storage root (`docs/adr/2026-10-17-tenant-data-export-archive.md`).

This issue adds `POST /api/blobs`, widens the reference rule to image properties, and adds a daily cleanup of unreferenced standalone blobs. Later issues build on it: #1564 adds Inbox attachments as a further counted reference, #1963 attaches uploaded blobs to captured Inbox items, #1661 creates the Files item on save from an uploaded blob, and #1793 lets the user replace a cover with an uploaded blob.

Decision: the cleanup age is 24 hours after the blob was created, and runs once a day.

Shared-file ordering: this issue also waits for #1355 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1564: [inbox-attachments 02/08] Store Inbox attachments as counted blob references

#### Context

Model tier rationale: A new tenant-owned table with row-level security plus a change to the shared blob reference rule and the permanent-delete path, where a mistake either leaks across tenants or deletes bytes that are still in use.

A photo, scan, audio note or shared file can be attached to an Inbox item before anything is filed. Today the Inbox has no attachment: `Inbox` (`backend/packages/data/src/seed/seedInboxPipeline.ts`) has only `date`, `time` and `text`, and the property type `file` is used by no database. Files are created at once by `POST /api/files`. The product decision is that an attachment stays with the Inbox item until the person confirms the proposal; only then does a Files item appear, by moving the same bytes (no copy). Until then, and after the item is discarded, no Files item exists, and the attachment is kept until the Inbox item is permanently deleted.

This issue creates the one attachment model for the Journal and the Inbox and makes it a counted blob reference. Blob bytes are shared by content hash (`findOrCreateBlob`), so the rule that decides when bytes may be deleted matters: `deleteBlobIfUnreferenced` (`backend/packages/data/src/blobs/blobsStore.ts`) counts only `properties.file.blobId` of items and `mail_attachments` (and, after #1401, image properties). `deleteItemDependents` (`backend/packages/data/src/chokePoint/itemTrash.ts`) removes an item's dependent rows by hand on permanent delete and frees only the item's own `file` blob.

#1963 lets a capture attach uploaded blobs, #1703 moves an attachment into Files on confirm, #1965 adds recognition metadata, and #1606 and #1969 read attachments.

Decisions:
- One general attachment model serves every kind of attachment and allows several attachments per Inbox item (`position` orders them). The cap of 10 per capture is enforced by the capture route (#1963); limiting the Journal to one attachment is a client rule, so nothing here caps the count.
- An attachment is a row of its own, not a Files item and not an item property, so the Inbox item's schema stays unchanged.
- A discarded (trashed) Inbox item keeps its attachment rows; they are removed when the item is permanently deleted.

### Requirement gh-1410: [files 01/04] Detect file type from content on upload

#### Context

Model tier rationale: One known mechanism (sniff the stored bytes, then record the result) across the upload store, a shared detector and one per-tenant cutover, verified with existing upload fixtures, but a parser over untrusted bytes and a populated-install schema change warrant care.

The Files collection shows a type badge (PDF, XLSX, DOCX, JPG) for every file. Audio attachments and recordings are also stored as Files, so the generic types must also recognise audio. Today the type is never filled in. `POST /api/files` (`backend/services/semprec-api/src/filesHandler.ts`) streams the body into `ingestUploadedFile` (`backend/packages/data/src/blobs/fileUploadStore.ts`), which stores the client's `Content-Type` header verbatim as the blob's `mime_type` and creates the Files item with only `{ name, file: { blobId } }`, so `files.type` and the blob's real mime are whatever the client claimed or nothing. A client that labels a PDF as `image/jpeg` gets a wrong mime, and the blob is later served with that mime by `GET /api/blobs/:id`.

Decisions:
- The type is detected from the stored bytes (magic bytes, plus ZIP entry names for Office files), never from `Content-Type` or the file extension.
- The Files `type` select gains the options `png`, `heic` and `audio`, in addition to `pdf`, `xlsx`, `docx`, `jpg`. The task attachment tiles need png and heic. `audio` (label "Zvuk" in Czech, "Audio" in English) is one option for both m4a and mp3, because audio attachments and recordings are stored as Files and must get a type. This issue is the only place that changes `Files.type` options; the tasks schema issue does not touch them.
- HEIC is converted to JPEG on the client (iOS photo picker in compatible mode); this issue still recognises HEIC bytes so a server-side fallback can build on the detector.
- An unknown or unrecognised content gets no `type` value (property absent; there is no generic "other" type, a generic filter for an empty value finds these files) and the blob mime `application/octet-stream`, which `GET /api/blobs/:id` already serves as an attachment with `nosniff`.
- An upload that deduplicates onto an existing live Files item returns that item unchanged; detection does not rewrite it.

The standalone upload path and its integration with this detector are owned by #1401 in the same batch: image-header admission is retained, but new blob MIME comes from detected bytes or `application/octet-stream`; dedup preserves existing metadata.

Shared-file ordering: this issue also waits for #1389 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

Load `canonical-keys`, `db-migrations`, `io-hardening` and `testing`.

1. Add `backend/packages/data/src/blobs/fileTypeDetection.ts` exporting `detectFileType(head: Buffer): { type: "pdf" | "xlsx" | "docx" | "jpg" | "png" | "heic" | "audio"; mimeType: string } | null`. Signatures: `%PDF-` (within the first 1024 bytes), JPEG `FF D8 FF`, PNG 8-byte signature, HEIC/HEIF an ISO-BMFF `ftyp` box with brand `heic`, `heix`, `heif`, `mif1`, `msf1`, `hevc` or `hevx`; m4a an ISO-BMFF `ftyp` box with major or compatible brand `M4A ` or `M4B ` (`audio`, mime `audio/mp4`); mp3 an `ID3` tag at offset 0 or an MPEG audio Layer III frame header at offset 0 (byte `FF`, then the 11-bit frame sync and layer bits `01`) (`audio`, mime `audio/mpeg`); a ZIP (`PK\x03\x04`) is `xlsx` when an entry name starting with `xl/` is present and `docx` when one starting with `word/` is present (scanned in the local file headers within the first 64 KiB), otherwise unknown. Tests: detector unit tests per type (including an m4a and an mp3 with and without an `ID3` tag) including a ZIP without Office entries, an empty buffer and a truncated header; an upload test where a PDF sent as `image/jpeg` stores `type = pdf` and blob mime `application/pdf`; an unknown-content upload stores no type and `application/octet-stream`; the cutover test (populated install gains the options, second run changes nothing).

### Requirement gh-1412: [files 02/04] Expose blob metadata for file and image properties

Relations can be written through the catalog (`relation.put`, `relation.delete`, `PUT`/`DELETE /api/items/:id/relations/:propertyKey/:targetItemId`) but not read. The only readers are internal: `relationsStore.listRelationsForItem` and `listRelationsForItems` in `backend/packages/data/src/chokePoint/relationsStore.ts`, which take a relation definition id and return raw stored edges (`itemA`, `itemB`, `metadata`). A client or agent that wants to know which projects a person belongs to, or which area a file points at, has no way to ask. This is worst for one-directional relations (a relation definition with `propertyIdB = null`, such as a file's area, an event's people or a movie's watched-with list): the target database has no inverse property, so the link cannot be read from the target side, and today it cannot be read from the source side either.

This issue adds a read-only catalog operation `relation.list` that returns the live edges of one item, optionally narrowed to one relation property. It is the single read primitive for edges. #1518 builds inline expansion (`include=relations`) on the same resolution rules, #1521 reads the current edge before replacing it, and #1839 builds on the same edge listing.

Decision: the operation requires `core.item.read`, is non-destructive and needs no approval, and its MCP name is `semprec.relation.list` (the catalog prefixes `semprec.` automatically).

Shared-file ordering: this issue also waits for #1401 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1592: [collection-schema 11/14] Create a custom database with its properties in one call

#### Context

Model tier rationale: It makes one operation write a database, its partition, a title property and several properties (including tenant-scoped relation targets) atomically, and it must keep `database.create` from becoming a schema-write path for agent actors that only hold the database capability, which is an authorization contract; at that uncertainty the higher tier is chosen.

The app's "New collection" form collects a name and a list of properties (Text, Number, Select, Date, Checkbox, Link, Relation, File; the title "Name" is fixed and always first) and saves them together. ### Requirement gh-1617: [semp-pages 02/09] Restore a page to an earlier version

#### Context

Model tier rationale: Restoring a CRDT document as a forward update must keep concurrent editors' state consistent and bounded by the history retention rules, which is easy to get subtly wrong.

It builds on the operation family of #1394.

Decision: the operation is registered with capability `core.item.write` and `requiresApproval: true` for agent callers.
