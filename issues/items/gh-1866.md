## Context

Model tier rationale: One more scope on the established realtime catalog, with several write sites in existing stores that need an after-commit publish call and tenant-wide delivery, following the pattern set by the preceding scope issues.

The project detail shows a summary row (instructions, tools, tasks) and an attention dot. When the project's agent setup changes, the client must re-read that summary. Today nothing signals it. This issue adds the realtime scope `projectAgent` with payload `{ projectItemId: string }`, following exactly the shape and wiring that the agent runs scope #1863 and the earlier scopes in this chain introduced (the `invalidation` message type with a `scope` discriminator in `backend/packages/realtime/src/pgNotifyPublisher.ts`, the `OutboundFrame` variant in `protocolV1.ts`, the `InvalidationEvent` variant in `backend/packages/data/src/realtimeHook.ts`, the `syncServer.ts` mapping and the client parser in `backend/packages/realtime-client/src/serverFrame.ts`). Rules from `docs/adr/2026-10-16-tenant-scoped-realtime-fan-out.md` apply: thin payload, tenant from Postgres, no replay, publish only after commit with `runAfterCommit`.

Decision: the frame is delivered to every socket of the tenant (no `userId`), because heartbeat outcomes and drift findings are background writes with no acting user, and a tenant has one user.

Publication points (each publishes `projectAgent` for the affected project after commit):

- saving the project's agent guidance (the save path from #1548);
- changing a project's MCP tool grant (`setProjectMcpGrant` in `backend/packages/data/src/mcp/mcpGrantsAdminStore.ts`, reached through `setProjectMcpGrantForAgentPage`);
- creating, changing the rule of, enabling, disabling or deleting a user heartbeat of the project (`backend/packages/data/src/scheduler/schedulerStore.ts`);
- raising or resolving a guidance drift finding (`backend/packages/data/src/guidanceDrift/agentGuidanceDriftFindingsStore.ts`).

The summary also depends on failing heartbeats and pending approvals; those change with the end of a run or a request decision and are covered by the `agentRuns` frame, so the client refreshes the summary on either frame (#1863). Server-wide changes (a server switched off, a sync) affect every project's tool count and do not publish `projectAgent` per project; as decided by the product owner, they send one tenant-wide frame instead, after which the client refreshes the summaries of the projects it has open. That frame is #2025.

#1868 adds the next scope in the chain.

## Task

Load `state-writes`, `canonical-keys`, `io-hardening` and `testing`.

1. Add the `projectAgent` variant to `InvalidationEvent`, `RealtimeMessage` (+ `parseRealtimeMessage`, validating `projectItemId` with `isUuid`), `OutboundFrame` (`{ type: "invalidate", scope: "projectAgent", projectItemId }`), the `invalidation` case of `syncServer.ts`, and `parseServerFrame`.
2. Create `backend/packages/data/src/projectAgent/projectAgentInvalidation.ts` exporting `publishProjectAgentInvalidation(client, projectItemId)` that defers `notifyInvalidation({ scope: "projectAgent", projectItemId })` with `runAfterCommit`.
3. Call it at each publication point above, in the same transaction as the write.
4. Tests: a frame per publication point; coalesced calls in one transaction are fine to send twice but a rollback sends none; delivery reaches the sockets of the project's tenant only.

## Scope

### In scope

- The `projectAgent` scope end to end and its publication on guidance, grant, heartbeat and finding changes.

### Out of scope

- Run lifecycle and approval frames: #1863.
- Server-wide tool changes: one tenant-wide frame, delivered by #2025; no per-project fan-out.
- Semp status and the later scopes: #1868, #1918, #1946, #1951.
- The project summary route that the client refreshes.

## Acceptance criteria

- When a project's guidance is saved, a grant is toggled, a user heartbeat is created, enabled, disabled or deleted, or a drift finding is raised or resolved, then the tenant's sockets receive `invalidate` with scope `projectAgent` and that project's id.
- When the transaction rolls back, then no frame is sent.
- When a socket of another tenant is connected, then it does not receive the frame.
- A frame with a malformed project id is dropped by the listener and by the client parser.
