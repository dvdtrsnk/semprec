## Context

`resolveRelationProperty` in `backend/services/semprec-api/src/itemsHandler.ts` resolves a relation route's `:propertyKey` path segment to exactly one RELATION-typed property (issue #219). It does this by calling `property.list` for the caller item's database and filtering the full result set in memory:

```ts
const properties = await dispatchGenericOperation(service, "property.list", actor, { databaseId: item.databaseId });
const matches = properties.filter((property) => property.key === propertyKey && property.type === "relation");
```

This is O(N) in the database's property count, on every `PUT`/`DELETE /api/items/:id/relations/:propertyKey/:targetItemId` call. Before #219's rebase, this used `chokePoint.getPropertyByKey(databaseId, key)` — an O(1) lookup backed by the `UNIQUE(database_id, key)` index.

## Why the direct lookup can't just be restored

`getPropertyByKey` doesn't satisfy #219's requirements for this resolution step:
- It doesn't filter by property type, so a non-relation property with a matching key would incorrectly resolve.
- On no match it doesn't produce the `404 not_found` shape `{ resource: 'relationProperty', databaseId, propertyKey }` that #219 requires.
- It returns at most one row, so it can't detect or report the multiple-match/ambiguous case (`409 validation_failed` with `{ field: 'propertyKey', reason: 'ambiguous' }`) at all.

## Proposed fix

Add a `property.getByKey` operation to `GenericApplicationPort` that takes `{ databaseId, key, type? }` (or equivalent) and does the indexed lookup plus the type filter and ambiguity detection in one call, backed by the database rather than an in-memory scan. `resolveRelationProperty` would then dispatch that single operation instead of `property.list` + `Array.filter`.

This wasn't done as part of #219 itself because #219 explicitly closes the generic-operation catalog at exactly 28 operations (its acceptance criteria require "parameterized contract tests across all 28 operations"), and adding a 29th operation for this one call site is the kind of scope growth `docs/adr/2026-09-10-no-speculative-generality-beyond-issue-scope.md` rules out for that issue. This issue tracks it as deliberate follow-up work instead.

## Task

- Add a `property.getByKey` operation (input schema, port method, binding) to the generic-operation catalog, implemented as an indexed query in `packages/data`'s choke-point.
- Update `resolveRelationProperty` in `itemsHandler.ts` to use it instead of `property.list` + in-memory filter.
- Keep the existing 404/409 response shapes exactly as `resolveRelationProperty` currently produces them.

## Out of scope

- Any other call site currently using `property.list`.
