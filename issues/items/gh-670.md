## Context

`ingestUploadedFile` in `backend/packages/data/src/blobs/fileUploadStore.ts` (lines 50-92) is `POST /api/files`' pipeline: it streams the body to storage under a fresh key (`storage.writeStream`, line 59) **before** opening the transaction, then in `withTransaction` (lines 70-91) dedupes the blob by content hash and creates the Files item. Two ways this leaves storage and rows out of step:

1. If anything inside the transaction throws — `findOrCreateBlob`, `findFileItemByBlobId`, or `createItemWithClient` (line 86; e.g. the Files database archived, a `ForbiddenError` on a system property, a connection error) — the transaction rolls back but the bytes written at line 59 stay on disk under a key no `blobs` row references. Nothing ever removes them.
2. On a content-hash dedup hit (line 79), `storage.delete(storageKey)` runs **inside** the transaction (line 80). If the transaction then fails, the duplicate bytes are gone (harmless) — but if it succeeds the deletion already happened before commit, and a failed `delete` (an I/O error) aborts a transaction whose database work was fine. `docs/adr/2026-09-10-side-effects-follow-the-commit.md`: an effect a rollback must not have made visible runs after commit via `runAfterCommit`, never inside.

Streaming before the transaction is unavoidable — the content hash that drives the dedup only exists once the bytes have been written — so the fix keeps the write-then-dedupe shape and makes both sides of it follow the commit. `BlobStorageWriter` (`backend/packages/data/src/mail/blobStorage.ts`, lines 37-47) gains no new method; `delete(storageKey)` is enough.

## Task

1. `ingestUploadedFile`: wrap the `withTransaction(...)` call in `try/catch`; on any throw, `await input.storage.delete(storageKey)` (a rolled-back transaction kept nothing, so the streamed bytes are always garbage on this path), log a failure of that cleanup with `console.error` (the package's convention for a best-effort cleanup, see `trash/purgeExpiredTrash.ts` line 31) and rethrow the original error. The `MaxBytesExceededError`/stream-failure path before the transaction (lines 62-68) is unchanged — `writeStream` already removed its partial bytes.
2. On a dedup hit (`blob.storageKey !== storageKey`), replace the inline `await input.storage.delete(storageKey)` (line 80) with `runAfterCommit(client, () => { void input.storage.delete(storageKey).catch((err) => console.error(...)); })` — the duplicate bytes are removed only once the row that references the *kept* blob has committed; if the transaction rolls back, step 1's catch removes them instead.
3. Doc comment (lines 34-49): add the two orderings and cite the ADR slug.
4. Tests, new `backend/packages/data/src/__tests__/fileUploadStore.test.ts` (integration, with an in-memory `BlobStorageWriter` fake that records `writeStream`/`delete` calls and can be told to throw from `delete`): (a) archive the Files database so `createItemWithClient` throws `database_archived`; after the rejected call the fake has one `delete(storageKey)` call and no `blobs` row for that hash; (b) upload identical bytes twice; the second call resolves with `created: false`, the fake's `delete` was invoked exactly once, with the second key, and the first key's bytes are still present in the fake; (c) the discriminating case for "after commit, not inside": the fake's `delete` is told to throw, identical bytes are uploaded twice, and the second call still resolves with `created: false` and the existing item (a `delete` inside the transaction would have aborted it and rejected the call); the error is logged; (d) after (a), no bytes remain in the fake for the failed upload's key.

## Scope

### In scope
- Cleanup of the streamed bytes when the transaction fails, and after-commit deletion of a dedup duplicate, plus the tests.

### Out of scope
- `mail/attachments.ts`'s `ingestAttachments` (same pattern, mail module; not part of this finding).
- A temp-key + rename protocol on `BlobStorageWriter` (a fresh random key that no row references is already a temporary key; a rename adds an interface method every implementation would have to grow for no additional guarantee).
- Blob bytes removal on purge (sibling issue C2).

## Acceptance criteria

- When the transaction inside `ingestUploadedFile` fails after the bytes were streamed, the bytes under that key are deleted before the error propagates and no `blobs` row references them.
- When an upload dedups onto an existing blob, the duplicate bytes are deleted only after the transaction has committed, and a failure of that deletion does not fail the upload.
- When the upload is a new blob, the bytes stay and the `blobs` row references their key, as before.
