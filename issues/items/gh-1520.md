## Context

Model tier rationale: One small rule registered with the pre-write transform mechanism from its blocker, touching one new file and one registration line, with existing item-write fixtures and no new lifecycle or persisted-data contract.

A project that is done or archived must not stay pinned to the overview: setting its status to done or archived unpins it, and pinning a done or archived project is refused. Today the Projects database (`seedTenDatabases.ts`: `pinned` checkbox, `status` select with `inProgress`, `done`, `archived`, `longTerm`) enforces nothing; both properties are plain user-owned values written through `PATCH /api/items/:id`. Item update hooks run only after the write and cannot change the patch (`backend/packages/data/src/chokePoint/itemWrites.ts`), so the rule needs the per-module pre-write transform from #1422. That issue builds the registry in the choke point; this one only registers a rule for the Projects database through the composition point `backend/packages/data/src/domainWriteHooks.ts`.

The rule applies to every writer (the user, and Semp over `/mcp` or agent tools) because the choke point is the single write path. #1579 (long-term deadline) and #1586 (completion date) register further rules for the same database after this one and extend the same file.

Decision: when a write sets `status` to `done` or `archived` and the stored or incoming `pinned` is true, the transform sets `pinned` to false in the same write and the response shows it. When the incoming patch itself sets `pinned: true` while the resulting status is `done` or `archived`, the write is refused with a `ValidationError` on `field: 'pinned'` (HTTP 400). The check uses the status after the patch is applied.

Shared-file ordering: this issue also waits for #1515 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Create `backend/packages/data/src/projects/projectWriteTransform.ts` exporting the Projects pre-write rule described above, using the registration API from #1422; apply it for item create and item update.
2. Register it in `backend/packages/data/src/domainWriteHooks.ts` (one import and one registration line).
3. Tests (through the real choke point): patching `status: done` on a pinned project returns `pinned: false` in the same response; the same via `archived`; patching `pinned: true` on a done project answers 400 with `field: 'pinned'`; patching `{ status: 'done', pinned: true }` together answers 400; patching `pinned: true` on an in-progress or long-term project works; the same behavior through the `/mcp` path.

### Out of scope

- The transform registry itself: #1422.

- Recording the completion date: #1586.
- Ordering of pinned projects on the overview.
- Hiding system projects from the collection and counts.

## Acceptance criteria

- When a pinned project is patched to status `done` or `archived`, then the same response shows `pinned: false`.
- When a done or archived project is patched with `pinned: true`, then the answer is 400 with `field: 'pinned'` and nothing is stored.
- When the same patch sets status `done` and `pinned: true`, then the answer is 400 with `field: 'pinned'`.
- The behavior is identical when Semp writes through `/mcp`.
- The full backend `pnpm run verify` passes.
