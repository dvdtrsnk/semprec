## Context

Model tier rationale: One known mechanism (declaring a read-only module agent tool over an existing read function) across defined seams with existing tool and MCP fixtures, and no new authorization contract beyond a capability read.

The calendar timeline read function `readCalendarTimeline` (#1717) serves the app's route. Semp, and external clients over MCP, need the same data to answer questions about the user's day or week. Module agent tools are composed into Semp sessions by #1523 and listed and called over `POST /mcp` by #1580; this issue adds the first calendar tool, so a calendar read reaches both from one declaration. The tool is read-only, so it needs no approval.

Decision: the tool is named `calendar.timeline`, takes `{ from, to }` (dates, same limits as the route: at most 93 days), returns the same items as the route (full shape), and does not filter hidden calendars, because the assistant works with hidden calendars too.

Decision: the tool needs the capability `calendar.read`, declared in the calendar manifest; if the module-tool grant decision names a different id, use that one.

Shared-file ordering: this issue also waits for #1950 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Acceptance criteria

- When Semp calls `calendar.timeline` for a range, then it receives the same items as `GET /api/calendar/timeline` returns for that range.
- When an MCP client calls `semprec.calendar.timeline`, then the same items are returned.
- When the capability is not granted, then the tool does not appear and calling it is indistinguishable from an unknown tool.
- When the range is longer than 93 days, then the call fails with a validation error.
