**Blocked by:** #213, #83, #136

## Context

Issue #213 introduced `heartbeat_occurrences`, floating scheduling from the first handler attempt, and the handler discriminator, treating every conflict on `(heartbeat_id, scheduled_for)` as an idempotent no-enqueue result. That leaves a legitimate gap: after edit-away/edit-back or disable/re-enable, the recomputed schedule can land on a timestamp whose occurrence was already cancelled, and a queued occurrence can hold a stale snapshot that would be cancelled at handler start even though the current rule is valid for the same timestamp.

This final part defines the reactivation rules for cancelled and queued conflicts and the generation protocol that makes reactivation safe against an old handler still finishing its job.

## Task

Occurrence insertion uses `INSERT ... ON CONFLICT (heartbeat_id, scheduled_for) DO UPDATE` only when the existing row has `status = 'cancelled'`: atomically replace `rule_snapshot`, set `status='queued'`, clear `first_started_at/last_error`, return the existing occurrence id, and enqueue that id with its occurrence job key in the same transaction. A conflict with queued/running/succeeded/failed is an idempotent no-enqueue result and never advances `next_fire_at` a second time. Thus edit-away/edit-back and disable/re-enable can legitimately reactivate the same timestamp, while completed or live work cannot duplicate. Tests cover both cycles at identical `scheduled_for` plus overlapping sweeps.

Queued conflicts have one additional race rule. Under the heartbeat+occurrence locks, if the existing row is `queued` and PostgreSQL-jsonb-unequal to the current rule, replace `rule_snapshot`, clear cancellation/error fields, preserve the occurrence id/status, and call `enqueueJob` again with the same occurrence job key and `jobKeyMode: 'preserve_run_at'`; the pending job is reused, and a concurrently starting handler waits for the lock then sees the new snapshot. Queued equal is a pure no-op. Only running/succeeded/failed conflicts are non-reactivatable. A deterministic edit→sweep-conflict→handler test proves the current valid same-timestamp rule fires once instead of being cancelled.

Add `generation integer not null default 1` to `heartbeat_occurrences`; this generation protocol supersedes the same-key wording above and the `{ heartbeatId, occurrenceId }` payload/key defined in #213. Every scheduled payload is `{ heartbeatId, occurrenceId, generation }` and its key is `heartbeat-fire:${heartbeatId}:${occurrenceId}:${generation}`. Initial insert uses generation 1. Reactivating cancelled or replacing a queued stale snapshot increments generation, resets fields/status, and enqueues the distinct new-generation key. At handler start, after locking, payload generation must equal row generation; a stale generation is a successful no-op and cannot change status/schedule. Therefore an old handler may finish/remove only its old key, never the reactivated job. Running/succeeded/failed rows remain non-reactivatable. Tests pause an old handler after cancellation commit, reactivate/enqueue the next generation, finish the old job, and prove the new generation still fires exactly once.

## Scope

### In scope

- Cancelled and queued occurrence reactivation on the same `scheduled_for`, and the generation column/payload/job-key protocol.
- Reactivation, stale-snapshot, and generation-race tests.

### Out of scope

- The occurrence table, sweep insertion, fixed versus floating scheduling, first-attempt locking, and the handler discriminator; #213 delivered these.
- Starting the long-lived worker process; the final issue in this batch owns that composition root.
- New rule kinds or module registry integration.
- UI/history tooling for heartbeats.

## Acceptance criteria

- A cancelled occurrence is atomically reactivated on the same timestamp after rule/enable restoration; non-cancelled conflicts never duplicate or advance twice.
- A queued stale-snapshot conflict atomically reuses its occurrence/job with the new snapshot, including the handler-start race.
- Generation-specific payloads/job keys prevent an old cancelled handler from consuming or removing a reactivated occurrence.
- The #213 guarantees (floating from actual execution, fixed calendar alignment, at-most-once advancement per occurrence, exactly-once enqueue under overlapping sweeps) still hold with the generation payload and key.
