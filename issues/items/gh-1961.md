**Blocked by:** #1959
**Model tier:** medium

## Context

Model tier rationale: One thin module custom route over an existing helper, with the registrations every route needs (manifest, route matrix, isolation test) and idempotency to preserve.

Capturing an Inbox item today means the generic item create, which knows nothing about the type edge: the client would have to create the item and then a relation in two requests, with no common transaction. `createInboxItemWithClient` (`backend/packages/data/src/inbox/inboxStore.ts`) already writes the item and its optional `type` edge together and, after #1432, the create hook validates the date and time and links the Journal day. It has no caller outside tests, and there is no capture route.

The Inbox module registers its routes through its manifest (`customRoutes` in `backend/packages/data/src/inbox/inboxModuleManifest.ts`, handlers in `inboxRouteHandlers.ts`, mounted by `mountCustomRoutes` in `semprec-api`); `POST /api/proposals/:id/confirm` and `GET /api/inbox-types` are the examples. A custom route handler receives the authenticated request context (`req`, `identity`, `params`, `body`), so it can read the `Idempotency-Key` header the way `backend/services/semprec-api/src/itemsHandler.ts` does for the generic create. The proposal-options route #1959 also adds an entry to the same manifest and handler file, so this issue is ordered after it. #1964 extends this route with the capture channel, source app and received time, and #1963 adds attachments to it.

Decision: the body is `{ text, date, time, typeId? }`. Until attachments exist (#1963) `text` must be a non-empty string after trimming; `date` and `time` follow the rules of #1432.

Decision: `typeId` must be the id of a live Inbox item type whose `status` is `active`; an unknown, trashed or archived type is 400 `validation_failed` with `field` `typeId`. Omitting it creates an untyped item.

Decision: the response is 201 with the item envelope. A replayed `Idempotency-Key` returns the original item and writes no second item and no second `type` edge.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. Add `createCaptureInboxItemRouteHandler(pool)` to `inboxRouteHandlers.ts`: validate the body, resolve the Inbox and Inbox item types databases by module id, inside one `withTransaction` check for an idempotent replay first (`itemsStore.findIdempotentReplay`) and return that item untouched, otherwise call `createInboxItemWithClient` with the validated input and the header's idempotency key if the header is present.
2. Re-export it from `inboxModuleManifest.ts` and declare `{ name: "captureInboxItem", method: "POST", path: "/api/inbox/items", handlerExport: "createCaptureInboxItemRouteHandler", justification: "transactional-semantics" }` in `customRoutes` (the item and its type edge commit together).
3. Add the route to `ROUTE_MATRIX` in `backend/services/semprec-api/src/routeMatrix.ts` and a handler in `backend/services/semprec-api/src/__tests__/tenantIsolationRoutes.test.ts` (a foreign type id answers like a random one and leaves tenant A unchanged).
4. Tests: valid capture creates the item with its `journalDay` edge and type edge in one transaction; missing `date`, missing `time`, `time: "abc"`, empty `text` and an archived or foreign `typeId` each return 400 with the `field`; the same `Idempotency-Key` twice returns the same item id; no partial item exists when the type check fails.

## Scope

### In scope

- `POST /api/inbox/items` with text, date, time and optional active type, idempotent, with its registrations and tests.

### Out of scope

- The create hook that validates and links the day (#1432).
- Capture channel, source app and received time (#1964).
- Attachments and text-less capture with an attachment (#1963).
- Changing the type of an existing item and the type lock (#1669).

## Acceptance criteria

- When a client posts `{ text, date, time }` with valid values, then the response is 201 and the item exists with a `journalDay` edge on the capture day in the tenant's timezone.
- When `date` or `time` is missing, or `time` is `abc`, then the response is 400 with the failing `field`.
- When the same `Idempotency-Key` is sent twice, then one item exists and both responses carry its id.
- When `typeId` is archived, trashed or from another tenant, then the response is 400 with `field` `typeId` and nothing is created.
- The route appears in the route matrix and passes the tenant isolation test.
