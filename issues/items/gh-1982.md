## Context

Model tier rationale: One mapping through the existing tick snapshot and envelope builder with existing fixtures, but it depends on the computation function delivered by a blocker, so the interface must be read before coding.

The Semprec tick (`createSemprecTickAction` in `backend/packages/data/src/inbox/inboxTickAction.ts`) computes a proposal for an Inbox item. `readTickSnapshot` derives the envelope kind from the item type's `processingMethod`: `database -> database`, anything else `-> pageContent`. `ProposalComputationResult` is `{target?, properties}`; the LLM never chooses the kind. `buildProposalEnvelope` turns the snapshot and result into the envelope. The tick computation function (`ComputeSemprecProposalFn`) gets its production implementation in #1434.

After #1975, a type may have `processingMethod: 'journal'` and `journalEntry` envelopes validate. Mapping the method to `pageContent` with the day as target would be wrong: the day may not exist yet and `pageContent` needs an existing target. So the tick must map `journal` to `journalEntry` explicitly.

Decision: the model returns only `{date?, markdown, areaId?, projectId?}`; the server supplies `target` (the tenant's Journal database id) and defaults `date` to the date of the source Inbox item when the model omits it. The area of a Journal entry is derived from its project, so when the model returns both, the server drops `areaId` before validation.

## Task

Load `ai-gateway`, `testing` and `state-writes`.

1. In `readTickSnapshot`, map `processingMethod: 'journal'` to `entityKind: 'journalEntry'` and resolve the Journal database id (owner module `journal`) into the snapshot, in the same way `targetDatabaseId` is resolved for `database`. Extend `ComputedProposalEntityKind` and `ProposalComputationInput` accordingly (the input carries the resolved Journal database id and the source item's date).
2. In `buildProposalEnvelope`, build `{entityKind: 'journalEntry', target: <Journal database id>, properties}` where `properties` come from the computation result; set `properties.date` to the source item's date when missing; when the result carries both `areaId` and `projectId`, omit `areaId`. Reject a result that carries a `target` of its own (server-owned).
3. Make the compute function's prompt/instructions and output schema (as delivered by #1434) cover the `journal` method: output `{date?, markdown, areaId?, projectId?}`, with the candidate areas and projects the existing computation context already supplies. If #1434 has no such context for this method, pass only ids the validation of #1975 would accept.
4. The envelope goes through the existing `assertValidProposalEnvelope`; an invalid computed result (no markdown, a `page` block, unknown area) is recorded the way other invalid computations are today and does not create a card with an invalid envelope.
5. Tests in `backend/packages/data/src/__tests__/inboxTickProposal.test.ts`: an item of a `journal` type produces a `journalEntry` card with the Journal database as target and the item date as default; a result with an area and a project produces a card with only `projectId`; a result with a `page` block is rejected; a `pageContent` or `database` type is unchanged.

### Out of scope

## Acceptance criteria

- When an Inbox item of a type with `processingMethod: 'journal'` is ticked, then a card with `entityKind: 'journalEntry'` and the Journal database as `target` is created.
- When the computation returns no date, then the stored `properties.date` equals the source item's date.
- When the computation returns both an area and a project, then the stored envelope carries `projectId` and no `areaId`.
- When the computation returns a `target` or markdown containing a `page` block, then no card with that envelope is created.
- When the type's method is `pageContent` or `database`, then the envelope kind and behavior are unchanged.
