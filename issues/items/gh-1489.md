## Context

Model tier rationale: Extends one derived cache with several fields drawn from cards and envelopes owned by other issues, additively, where the main risks are the interfaces to those cards and keeping the cache free of localized text.

The Journal day shows its Inbox items; an item with an attachment also shows what Semp proposes for it (target database, project, follow-up steps) and, until a proposal arrives, a "Semp is preparing a proposal" state. Today each cached element of `computed.inboxItems` (`backend/packages/data/src/inbox/journalInboxCompute.ts`) holds `id`, `date`, `time`, `text`, `type` and `status`, where `status` is the Processing proposals card status or `null` when no card exists. The cache cannot tell "no card yet" from "failed", carries no summary of the proposal, and the day is not recomputed when the tick writes a card until #1390.

This builds on #1451 (card-state properties, including a `computing` state), #1434 (the tick runs in production) and #1485 (the card gets a `computeFailed` state). Requirement on #1485: the `computeFailed` state must also be written when a transient compute error has exhausted its retries, otherwise "preparing" would show forever.

Decision: the proposal summary is computed for every item whose card is in `proposed` state, not only for items with attachments; the client decides which to display. Cached values are canonical keys and user data only (no localized text); the client builds labels from the schema.

## Task

Load `canonical-keys` and `testing`.

1. In `computeJournalInboxItems` add `processing` to each summary element: `pending` when no card exists yet or the card status is `computing`; `failed` when the card status is `computeFailed`; otherwise the card's status. Keep `status` as it is.
2. Add `proposalSummary` for items whose card is `proposed`: `{ entityKind, documentKind, targetDatabaseKey, targetItemId, targetItemName, projectItemId, projectName, areaItemId, areaName, followUps: [{ databaseKey, name, amount, currency }] }`, with `null` for unknown parts. `entityKind` and the target come from the card's stored envelope; `documentKind` from the document recognition result stored on the card when it exists, else `null`; `followUps` from the steps of a multi-step envelope when the card has them (#1479), else `[]`; names are read from the target, project and area items in the same recompute; `proposalSummary` is `null` for any other card state.
3. Keep the change additive: existing fields and their meaning are unchanged; extend the `JournalInboxItemSummary` type.
4. Tests: an item with no card has `processing: 'pending'`; a `computing` card also `pending`; a `computeFailed` card `failed`; a `proposed` Files card yields `proposalSummary.targetDatabaseKey = 'files'` and project and area names; the cache contains no localized strings; the day item is announced after each recompute.

## Scope

### In scope

- The `processing` and `proposalSummary` fields of the day's Inbox cache.

### Out of scope

- Recomputing on tick writes; #1390.
- Attachments in the summary; #1969.
- Writing the compute-failure state itself; #1485.
- Type changes from the day; #1718.

## Acceptance criteria

- When the tick has produced a proposed card for an Inbox item, then its cached element has `processing: 'proposed'` and a `proposalSummary` with the target database key, without any further change to the Inbox item.
- When an item has just been captured and has no card, then `processing` is `pending`; when its card is `computeFailed`, then `failed`.
- When the summary is read, then it contains no localized text.
