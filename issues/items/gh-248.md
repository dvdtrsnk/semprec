**Blocked by:** #185, #84

## Context

First of two parts of the retry/recovery slice that completes the `batch-transcription` batch (approved behavior in #179). It builds on the checkpointing pipeline (#182, #183) and the matching/speaker work (#184, #185). This part defines the queue retry policy, the `item_automation` state machine of Transcriptions rows, and the transactional failure notification. #186 builds on it with the daily requeue heartbeat and the manual rerun route.

## Task

- Configure `TASK_NAMES.transcriptionJob` with `max_attempts: 3` and graphile-worker's built-in exponential backoff. Every attempt reuses the checkpoints from #182 and #183: already-paid stages are never repeated.
- Maintain `item_automation` on the Transcriptions row as the job state machine: `pending` -> `done` / `error` / `locked`; `attempts` as a cumulative counter incremented on every attempt; `error` carrying the failure reason as text. `status` stays a display pill (`processing` -> `done` or `error`) and carries no error detail.
- On permanent failure (last attempt exhausted, or a budget rejection from the gateway), set `item_automation.status = 'error'`, `status = error`, and in the same transaction create a `notifications` row with `kind: 'automation_error'` through the canonical notification writer from #149 — exactly one notification per permanent failure.
- On eventual success, set `item_automation.status = 'done'`, clear `error`, and set `status = done` without producing duplicate output (the checkpoints ensure the result is written once).
- `locked` is a per-item opt-out set only by a user ("do not touch again"); the pipeline itself never sets it and never runs on a locked row.

## Scope

### In scope

- Queue retry configuration, `item_automation` state transitions with cumulative `attempts`/`error`, transactional `automation_error` notification, success clearing, tests, and necessary documentation.

### Out of scope

- The daily requeue heartbeat and `POST /api/transcriptions/:id/rerun` with the 403 on locked rows — #186.
- Meeting bot, live captions, watch folder, voiceprints — never (see #179).

## Acceptance criteria

- A transient failure retries at most three queue attempts with exponential backoff, and each retry resumes from the last checkpoint without repeating a paid gateway call.
- Permanent failure stores `item_automation.status = 'error'`, the cumulative `attempts`, the `error` text, `status = error`, and exactly one `automation_error` notification, all committed together (a rolled-back transaction leaves none of them).
- Success after earlier failures clears the actionable error, sets `done`, and produces no duplicate computed output or duplicate edges.
- A row with `item_automation.status = 'locked'` is never processed by the handler.
