**Blocked by:** #646

## Context

The `approvalExecute` job handler `handleApprovalRequestExecuteTask` (`backend/packages/data/src/mcp/approvalRequestExecution.ts:61-103`), on the `mcpInvoke` payload path (lines 85-102), runs three separate transactions around one external call:

1. `claimApprovalRequestExecution` (`approvalRequestsStore.ts:241-250`): `UPDATE approval_requests SET executed_at = now() WHERE id = $1 AND status = 'approved' AND executed_at IS NULL RETURNING *`.
2. `executeMcpInvocation` (`mcpToolExecution.ts:78-97`) outside any transaction: `handle.client.callTool({ name, arguments })` with no idempotency marker; its `finally { await handle?.close(); }` (line 95) means a rejecting `close()` replaces whatever the `try` returned — a successful tool result becomes the job's error.
3. `recordApprovalRequestOutcome` (`approvalRequestsStore.ts:270-282`): `UPDATE approval_requests SET execution_error, execution_result_jsonb, execution_status = CASE ... END, executed_at = COALESCE(executed_at, now()) WHERE id = $1` — no state guard, so it overwrites a row in any state.

A process crash (or a transient database error) between 1 and 3 leaves the row `status='approved'`, `execution_status='queued'`, `executed_at` set: graphile-worker redelivers the job, the claim returns `null` (`executed_at IS NOT NULL`), the handler returns successfully, and the request stays "queued" forever with nobody knowing whether the tool ran. Nothing can ever record its outcome.

`execution_status`'s allowed values are fixed by the `CHECK` constraint `approvalRequestExecutionStatusCutoverMigration.ts:84-88` adds (`not_approved`, `queued`, `succeeded`, `conflict`, `legacy_terminal`); "executing" is already expressed as `queued AND executed_at IS NOT NULL` (the claim semantics migration `0022_approval_request_execution.sql` documents), so no new column or value is introduced. `terminalizeApprovalRequestAsConflict` (`approvalRequestsStore.ts:298`) already guards on `execution_status = 'queued'`; `recordApprovalRequestOutcome` is brought to the same standard.

#646 injects the generic-operation replay into the API queue runtime and lands first (its composition test exercises this handler). Sibling issue D7b of this batch re-checks grants/registration at execution time on top of this issue's structure.

## Task

1. **Claim guards on the execution state.** `claimApprovalRequestExecution`: add `AND execution_status = 'queued'` to the `WHERE`. Docstring: the claim is the exclusive "executing" marker; a second delivery sees `null`.
2. **Outcome write is state-guarded and reports whether it wrote.** `recordApprovalRequestOutcome` returns `Promise<boolean>`: `WHERE id = $1 AND execution_status = 'queued'`; `true` when `rowCount === 1`, `false` when the row is no longer `queued` (already settled by another delivery); replace `requireAffectedRows` with that check and update the docstring (the generic "no replay handler" path keeps calling it and now logs on `false`).
3. **Stale-claim settlement** — new function in `approvalRequestsStore.ts`, `settleStaleApprovalRequestClaim(client: Queryable, id: string, staleAfterMs: number): Promise<"settled" | "in_flight" | "not_claimed">`:
   - `UPDATE approval_requests SET execution_status = 'conflict', execution_error = true, execution_result_jsonb = $2::jsonb WHERE id = $1 AND status = 'approved' AND execution_status = 'queued' AND executed_at IS NOT NULL AND executed_at < now() - make_interval(secs => $3 / 1000.0)` with `$2 = JSON.stringify("The deferred MCP tool call was claimed by an earlier delivery that never recorded its outcome; the tool may or may not have run.")` → `"settled"` when `rowCount === 1`.
   - Otherwise `SELECT execution_status, executed_at FROM approval_requests WHERE id = $1`: `queued` with `executed_at` set → `"in_flight"`; anything else → `"not_claimed"`.
   - Docstring: `conflict` is the only terminal failure value the column allows; the result text is what distinguishes an unknown outcome from a revalidation conflict.
4. **Handler flow** (`approvalRequestExecution.ts`, mcpInvoke path), with a module-private `const MCP_APPROVAL_CLAIM_STALE_AFTER_MS = 10 * 60 * 1000` (documented: comfortably above the MCP SDK's 60 s request timeout plus `connectMcpServer`'s connect timeout, so a claim older than this can only belong to a delivery that died) and a module-local `const logger = createLogger("mcp")` from `@semprec/shared`:
   - `claimed === null` → `const verdict = await withTransaction(pool, (c) => settleStaleApprovalRequestClaim(c, id, MCP_APPROVAL_CLAIM_STALE_AFTER_MS))`; `"settled"` → `logger.warn({ approvalRequestId }, "settled a stale MCP approval execution claim as conflict")`, return; `"in_flight"` → `throw new Error("approval request <id> execution claim is still in flight; retrying later")` (a retriable failure — graphile-worker's default backoff keeps redelivering until the claim is stale); `"not_claimed"` → return (rejected/terminal/unknown, as today).
   - After the claim: call `executeMcpInvocation(pool, { serverItem, toolName }, payload.args, { idempotencyKey: claimed.id })`.
   - `const recorded = await withTransaction(pool, (c) => recordApprovalRequestOutcome(c, claimed.id, outcome)); if (!recorded) logger.warn({ approvalRequestId }, "MCP approval outcome discarded: the request was already settled by another delivery")`.
   - Update the handler docstring paragraph starting "An mcpInvoke payload keeps the pre-#89 flow unchanged" to describe this protocol.
5. **`executeMcpInvocation`** (`mcpToolExecution.ts`): add `idempotencyKey?: string` to `McpInvokeOptions` (documented: sent as `_meta.idempotencyKey` on `tools/call`, the MCP-permitted request metadata slot, so a server that de-duplicates can recognise a redelivered call — this process never re-calls a claimed request, the key is for the server's benefit); pass `_meta: { idempotencyKey }` in the `callTool` params when set. Replace `finally { await handle?.close(); }` with a `finally` that awaits `close()` inside its own `try/catch` and logs `logger.warn({ err }, "MCP connection close failed after tools/call")` — the `try`'s return value or the `catch`'s error result is never replaced by a close failure. `mcpInvokeTool.ts` re-exports `McpInvokeOptions` and needs no change.
6. **Test support**: `backend/packages/data/src/testSupport/fixtures/mcpStdioContractServerScript.mjs` records `request.params._meta ?? null` as `lastToolCall.meta`; `mcpContractServers.ts` `ContractToolCall` gains `meta: Record<string, unknown> | null` and the sse/http servers record it the same way.
7. **Tests**:
   - `backend/packages/data/src/__tests__/approvalRequestExecution.test.ts` (integration, existing fixtures): (a) after a normal approve+drain, the contract server's `getLastToolCall().meta` is `{ idempotencyKey: <request id> }`; (b) an approved request whose row is set directly to `executed_at = now() - interval '11 minutes'` (still `queued`) → draining the queue leaves it `execution_status='conflict'`, `execution_error=true`, `execution_result_jsonb` = the unknown-outcome text, and the contract server received no tool call; (c) the same with `executed_at = now()` → the job fails with the in-flight error, the row is unchanged, the server received no call; (d) `recordApprovalRequestOutcome` on a `conflict` row returns `false` and changes nothing; (e) a rejected request is still never executed.
   - `backend/packages/data/src/mcp/__tests__/mcpToolExecution.unit.test.ts` (new, `vi.mock("../mcpConnectionFactory.js")`): a handle whose `callTool` resolves `{ content: [{ type: "text", text: "ok" }] }` and whose `close` rejects → `executeMcpInvocation` resolves `{ error: false, result: "ok" }`; a handle whose `callTool` rejects and `close` rejects → resolves `{ error: true, result: "MCP tool call failed for an unexpected reason" }`; the `callTool` spy received `_meta: { idempotencyKey: "abc" }` when the option is set and no `_meta` key when it is not.

## Acceptance criteria

- When an approved `mcpInvoke` request is executed, the MCP server receives `_meta.idempotencyKey` equal to the request id and the row ends `succeeded` or `conflict` with the tool's result — a `close()` failure after the call never changes that.
- When a delivery claimed a request more than 10 minutes ago and never recorded an outcome, the next delivery marks the row `conflict` with the unknown-outcome text and does not call the tool.
- When a delivery claimed a request less than 10 minutes ago, the next delivery fails retriably without calling the tool, and the row is unchanged.
- When an outcome write finds the row already settled, it writes nothing and the handler logs the discard instead of throwing.
- `recordApprovalRequestOutcome` never changes a row whose `execution_status` is not `queued`.
