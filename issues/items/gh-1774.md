## Context

Model tier rationale: It adds outbound email jobs coupled to database commits, reacting to Event updates and deletes through choke point hooks, with retry and failure semantics across provider transports and snapshot payloads for data that may be gone by the time the job runs.

The user can link people to an Event and invite them by email (#1757 stores the invitation state on the edge, #1790 writes it). Nothing sends the invitation: `sendDraftEmail` (`backend/packages/data/src/mail/send.ts`) is a function no production code calls, `createSmtpClient` is never supplied, and `OutgoingMailMessage` (`mail/smtpClient.ts`) has only text and html. The outgoing MIME builder with an optional calendar part (#1491) and the per-mailbox transports (#1634 SMTP, #1753 Microsoft Graph, and the Gmail API transport from #1637 if present) are delivered elsewhere. Events have a stable `icalUid` and a `icalSequence` that increases when the time or place changes (#1599). The choke point can run item delete and restore hooks (#1601).

This issue sends the meeting invitation messages: an iTIP `REQUEST` to a newly invited person, an updated `REQUEST` with a higher `SEQUENCE` when the time or place of an Event with invited people changes, and a `CANCEL` when an invited person is removed or the Event is deleted. Sending runs as a queue job enqueued in the same transaction as the change (commit-coupled, as `enqueueNotificationFanout` does), so a rolled-back change sends nothing and a committed one is retried until delivered.

Decision: the iCalendar times in an outgoing message are UTC instants (`Z`), converted from the Event's wall-clock values in the tenant time zone with the helpers of the calendar time module (#1418); an all-day Event uses `DATE` values and an exclusive `DTEND`. No `VTIMEZONE` is emitted.

Decision: an updated `REQUEST` does not reset the recorded replies to `pending`; each invited person keeps their last reply status until they reply again.

Decision: restoring a deleted Event from the trash does not send a new invitation.

Decision: the organizer address is the first line of the sending mailbox's `Mailboxes.addresses`; the attendee address is the `email` stored on the edge's invitation (the first line of `People.emails` when the invitation was written).

The low-level serialization helpers (`calendar/icalendarWriter.ts`) are shared with the reply message of #1953; whichever of the two issues merges second extends the existing file instead of creating another one.

Shared-file ordering: this issue also waits for #1762, #1763 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. Add or extend `backend/packages/data/src/calendar/icalendarWriter.ts` with `buildItipRequest(...)` and `buildItipCancel(...)`: `VCALENDAR` with `METHOD:REQUEST` or `METHOD:CANCEL`, one `VEVENT` with `UID`, `SEQUENCE`, `DTSTAMP`, `DTSTART`/`DTEND`, `SUMMARY`, `LOCATION`, `ORGANIZER` (the mailbox address) and one `ATTENDEE` (`ROLE=REQ-PARTICIPANT`, `RSVP=TRUE`, `PARTSTAT=NEEDS-ACTION`), and `STATUS:CANCELLED` for a cancel.
2. Add `backend/packages/data/src/calendar/eventInvitationJob.ts` with the task payload schema, `enqueueEventInvitation(client, input)` and the handler. The payload is `{ method: "REQUEST" | "CANCEL", eventId, personId, mailboxId, attendeeEmail }`; a `CANCEL` payload also carries a snapshot (`uid`, `sequence`, title, start, end, place, all-day flag) because the Event or the edge may be gone when it runs. Job key: `event-invitation:<eventId>:<personId>:<method>:<sequence>`.
   - `REQUEST`: reads the live Event (skips with a log line when it is missing or trashed) and its `icalUid`/`icalSequence`, builds the message with the MIME builder from #1491 (short plain-text body plus the `text/calendar; method=REQUEST` part) from the mailbox address to `attendeeEmail`, sends it through the transport of the mailbox's provider, and only after success writes `invitation.sentAt` on the participant edge with the system writer kind.
   - `CANCEL`: builds `METHOD:CANCEL` with `SEQUENCE` = snapshot sequence + 1, sends it the same way, and writes nothing to the edge (it may be gone).
   - A transient transport failure rethrows so the queue retries with backoff, leaving the invitation `pending` without `sentAt`; a permanent one (mailbox deleted, no usable transport for the provider, no address) is logged with a reason code and ends the job.
3. Add an Events item update hook (registered next to the other hooks in `backend/packages/data/src/domainWriteHooks.ts`): when an update changed `icalSequence`, enqueue a `REQUEST` for every participant edge of the Event whose invitation has been sent (`sentAt` set) and is not `declined`.
4. Add an Events item delete hook using the hook point from #1601: enqueue a `CANCEL` (with snapshot) for every participant edge of the Event that carries an invitation. No restore hook.
5. Declare the task in `taskNames` of `backend/packages/data/src/calendar/calendarModuleManifest.ts` (name `calendarSendEventInvitation`, `queueAffinity` `api`) and wire any composition-root dependency in `backend/services/semprec-api/src/queueRuntime.ts`.
6. Tests: inviting enqueues one `REQUEST` which sends one message from the chosen mailbox to the person with the right `UID`, `SEQUENCE` and times, then sets `sentAt`; a transient failure leaves `sentAt` empty and the status `pending` and the job is retried; moving the start of an Event with a sent invitation enqueues a `REQUEST` with the higher `SEQUENCE` and does not reset statuses, while renaming it does nothing; deleting the Event enqueues a `CANCEL` for each invited person with the same `UID`; restoring it sends nothing; a rolled-back change enqueues nothing; a `CANCEL` still runs after the edge was deleted; all-day and timed Events serialize correctly.

## Scope

### In scope

- Serializing and sending `REQUEST` and `CANCEL`, the commit-coupled job with retry, recording `sentAt`, and the Event update and delete hooks that enqueue them.

### Out of scope

- The participant edge shape and routes that write invitations and enqueue the first `REQUEST` and removal `CANCEL`: #1757, #1790.
- Applying replies: #1950.
- The MIME builder and the transports: #1491, #1634, #1637, #1753.
- Copying sent messages to the provider's Sent folder: #1641.
- Resetting replies to pending on a time change: not done (product owner decision); statuses are kept and the updated `REQUEST` with the higher `SEQUENCE` is sent.
- Sending invitations on restore of a deleted Event: not built.

## Acceptance criteria

- When a person is invited, then one message with `METHOD:REQUEST` is sent from the chosen mailbox to their address, and only after it succeeds does the edge's invitation get `sentAt`.
- When sending fails transiently, then the invitation stays `pending` without `sentAt` and the job retries.
- When the start or place of an Event with sent invitations changes, then an updated `REQUEST` with the higher `SEQUENCE` is sent to each invited person who has not declined, and their reply statuses are unchanged.
- When an invited person is removed or the Event is deleted, then a `METHOD:CANCEL` with the same `UID` is sent; restoring the Event sends nothing.
- When the change that triggered a job is rolled back, then no job exists.
