## Context

Model tier rationale: Two declarative rules over an existing propagation engine, but the end-to-end behavior of taking over single values from many-valued documents needs integration tests against the real schema.

An expense created from an invoice should start with the company and the project of that invoice, and follow the invoice if its project changes, until a person (or the assistant) sets its own. The value-link machinery already exists as separate pieces: #1411 lets a module declare rules in its manifest (`linkRules`: `{ key, source: {databaseKey, propertyKey}, target: {databaseKey, propertyKey}, via: {databaseKey, relationKey} }`), #1593 creates and propagates links when a `via` edge appears and when the source changes, and #1516 turns a link `inheritedBroken` when a user or the assistant writes the target. #1553 gives `transactions` a single-valued `document` (to Files), `company` and `project`. A file's `projects` and `companies` are many-valued, while a transaction has one project and one company.

Decision: a document with two or more projects (or companies) gives the expense no value for that property and creates no link; a document with exactly one gives it. Reason: choosing "the first" would be arbitrary and would break the link when the order changes. This is the single-valued-target rule already specified for the propagation engine (#1593); this issue relies on it and tests it for Finance.
Decision: "No project" or "No company" chosen by a person is an empty write: the link ends without an edge, and "take over again" (#1587) restores the document's value.


Shared-file ordering: this issue also waits for #1646 because both edit the same files listed in Touches.

## Task

Load `canonical-keys` and `testing`.

1. In `financeModuleManifest.ts` (#1353) add two `linkRules`: `expenseCompanyFromDocument` (source `files.companies`, target `transactions.company`, via `transactions.document`) and `expenseProjectFromDocument` (source `files.projects`, target `transactions.project`, via `transactions.document`).
2. Check the registry validation and the drift check (#1411) pass with these rules over the seeded schema (the guard test over `loadFullModuleRegistry()` must report no finding).
3. Integration tests against the real schema, using the engine of #1593: setting `document` on a transaction takes over the file's single project and company and records an `inherited` link; changing the file's project changes the transaction's project and the link stays `inherited`; a user changing the transaction's project makes it `inheritedBroken` with `brokenBy` user and later file changes do not touch it; relink returns the file's project; the same write by the assistant gives `brokenBy` agent; clearing the project ("no project") ends the link with no edge and relink restores the file's project; a file with two projects gives the transaction no project and no link; a transaction without a document is untouched.

## Acceptance criteria

- When a transaction's `document` is set to a file with one project and one company, then the transaction has that project and company and both links are `inherited`.
- When the file's project changes, then the transaction's project changes and stays `inherited`.
- When a user changes the transaction's project, then the link is `inheritedBroken` with `brokenBy` user and later changes of the file do not alter the transaction; relink restores the file's project.
- When the assistant changes it, then `brokenBy` is agent.
- When the project is cleared to "no project", then the project is empty, there is no edge, and relink restores the file's project.
- When the file has two projects, then the transaction takes over no project and has no link for it.
