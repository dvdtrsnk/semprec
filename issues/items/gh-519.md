**Blocked by:** #508

## Context

Since #508, `backend/packages/data/src/chokePoint/itemReads.ts` holds the item reads. Every read method there runs its store call inside `withTransaction(pool, …)`, except `findItemIncludingDeleted`, which passes `pool` straight to `itemsStore.getItemsByIdsIncludingDeleted`. The result is the same, but it is the one read that bypasses the pattern the others follow, so the next reader has to work out whether the difference is deliberate.

## Task

Change `findItemIncludingDeleted` to run `itemsStore.getItemsByIdsIncludingDeleted(client, [itemId])` inside `withTransaction(pool, async (client) => …)`, exactly as `findItem` does, returning `item ?? null`. Keep its JSDoc.

## Touches

- backend/packages/data/src/chokePoint/itemReads.ts (`findItemIncludingDeleted` only)
- backend/packages/data/src/__tests__/chokePoint.test.ts (new cases in the `findItem` describe block)

## Scope

### In scope
- The one method and its tests.

### Out of scope
- Any other read method, and `itemsStore`.

## Acceptance criteria

- `pnpm run verify` in `backend/` passes. `src/__tests__/publicSurface.test.ts` passes unmodified.
- `chokePoint.test.ts` covers `findItemIncludingDeleted`: it returns a live item, returns a trashed item (with `deletedAt` set), and returns `null` for an unknown id.
- No method in `itemReads.ts` passes `pool` to a store function directly.
