## Context

Model tier rationale: This introduces a new tenant-scoped table holding encrypted PKCE secrets with single-use, owner-bound consumption semantics, so isolation, cryptography and race behavior all have to be right.

OAuth mailbox connection (#1686) needs owner-bound single-use state against forged callbacks and encrypted PKCE storage before an item exists. Existing item-keyed credentials cannot represent that pending stage.

This issue adds only the storage mechanism: the table, its store functions and its expiry sweep. The start and complete routes that use it are #1686.

Decision: the `state` value sent to the provider is a random opaque token; only its SHA-256 hash is stored, so a database read never yields a usable state. The PKCE verifier is stored encrypted under the tenant data key, with associated data binding it to the tenant and the state row, and it is never returned by any API, never logged and never exported.

## Task

Load `db-migrations`, `state-writes`, `io-hardening` and `testing`.

1. Add a migration `backend/packages/data/src/db/migrations/NNNN_mail_oauth_states.sql` (next free ordinal at commit time) creating `mail_oauth_states`: `id uuid` primary key, `tenant_id` (default `app_tenant_default()`, tenant-classified with the `semprec:tenancy=tenant` comment, row-level security policies and grants exactly as `0078_tenant_exports.sql` does), `user_id` referencing `users`, `provider` constrained to `gmail` or `outlook`, `mailbox_item_id` nullable (null means a new account; set means reauthorizing that mailbox), `state_hash` unique per tenant via `(tenant_id, state_hash)`, encrypted verifier columns (`code_verifier_ciphertext`, `code_verifier_nonce`), `created_at`, `expires_at` (creation time plus 10 minutes) and `used_at` nullable. Additive and rollback-safe.
2. Add `backend/packages/data/src/mail/mailOauthStatesStore.ts` with:
   - `createMailOauthState(client, { userId, provider, mailboxItemId })`: generates the random state and the PKCE verifier, seals the verifier with the tenant data key helpers used by `externalCredentialsStore.ts` (own associated data string, e.g. `semprec:mail-oauth-state:v1:<tenantId>:<stateRowId>`), inserts the row and returns `{ state, codeChallenge }` (S256 challenge). The plaintext verifier is not returned.
   - `consumeMailOauthState(client, { state, userId })`: in one statement marks the row used only if its hash matches, it belongs to `userId`, it is unexpired and `used_at` is null, then returns `{ provider, mailboxItemId, codeVerifier }`; returns `null` in every other case, without telling the caller which condition failed. Two concurrent calls with the same state succeed at most once.
3. Add a periodic cleanup task that deletes expired rows (and rows used more than an hour ago) for every active tenant, following `backend/packages/data/src/mcp/mcpRunCredentialExpiry.ts` (`forEachActiveTenant`, one transaction per tenant). Register it as a new `CORE_TASK_NAMES` entry with its queue affinity and tenant mode entries, a crontab line and a handler in `worker.ts`.
4. Add `mail_oauth_states` to `EXPORT_EXCLUDED_TABLES` in `backend/packages/data/src/tenancy/tenantExportJob.ts` so the tenant export archive never contains state hashes or verifier ciphertext.

## Acceptance criteria

- When a state is created and consumed by the same user within 10 minutes, then the provider, mailbox id and plaintext verifier are returned and `used_at` is set.
- When the same state is consumed a second time, by another user, or after expiry, then `null` is returned and nothing changes.
- When two consume calls race on one state, then exactly one returns a result.
- The database never contains the plaintext state or verifier, and decrypting the verifier under another tenant's key or another row's associated data fails.
- When the sweep runs, then expired rows of every active tenant are deleted and unexpired rows remain.
- The tenant export archive contains no `mail_oauth_states` data, and the tenant-isolation tests show tenant B cannot read tenant A's rows.

- Duplicate state hashes in one tenant are rejected; the same hash may exist independently in another tenant, without cross-tenant reads/writes or consume access to the other tenant row. Preserve applied 0110 and tenant-leading uniqueness.
