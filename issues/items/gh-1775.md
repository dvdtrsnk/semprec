**Blocked by:** #1731, #1772
**Model tier:** high

## Context

Model tier rationale: It enqueues a new agent turn in the same transaction as an approval outcome message, with FIFO ordering, budget accounting and enabled-state gating shared with the queued-turn runner, so ordering or atomicity mistakes spend budget or lose results.

An automation (tick) run that needs a decision creates an approval request and ends as `done`; the agent never learns the outcome. Today `AGENT_BASE_SYSTEM_PROMPT` tells it only to mention pending approvals, and nothing queues a turn after a decision. In the tick thread the run section ends with "The run continues once you decide", and the product wants the result of the continuation to appear in the same section.

When an approval outcome is posted into the requesting thread as a system message (#1772), the thread tells whether the thread is a tick thread. Queued turns are run by #1727; a tick turn has the heartbeat context and tools from #1731. In chat, after approval, no new reply appears (only the card and step change), so no turn is queued there.

Decisions: the continuation applies to tick threads only (in chat it would spend budget without an instruction from the person); a disabled automation does not continue (the system message stays, nothing is queued); a rejection also continues, with the knowledge that the action did not happen and an instruction to do nothing more.

## Task

Load `state-writes`, `error-handling`, `ai-gateway` and `testing`.

1. After the outcome system message is written in a thread of kind `tick` (in the same transaction as that message), enqueue one turn through the queue of #1727 using the system message as the trigger: no user message, an assistant message in `queued` state with `reply_to` the system message. It is ordered FIFO with the other messages of the thread, so a user message sent earlier runs first.
2. The turn runs with the heartbeat's project, the task context from #1731 and the outcome of the request (approved with result, rejected, or failed to execute) in the prompt.
3. The continuation counts against the tenant's budget like any other turn. If the heartbeat is disabled or deleted, no turn is queued and the system message stays.
4. For threads of kind `chat` or `item` nothing is queued after an outcome.
5. Tests: approval from a tick thread writes the system message and queues one turn in the same transaction; rejection continues with the rejection in context; a user message sent earlier runs before the continuation; chat thread queues nothing; disabled heartbeat queues nothing; a rollback of the system message also rolls back the queued turn.

## Scope

### In scope

- Queueing and running one continuation turn after an approval outcome in a tick thread.

### Out of scope

- Posting the outcome message itself: #1772.
- Queue mechanics and turn execution: #1727. Tick turn context and tools: #1731.
- Continuing in chat or item threads.
- Letting a disabled automation finish a started job (not adopted).

## Acceptance criteria

- After an approval decided from a tick thread, the thread contains the system message and a new queued turn whose prompt includes the outcome; the section of the original run shows the continuation's result as a further message.
- After a rejection the continuation runs knowing the action did not happen and performs nothing.
- The continuation runs after a user message sent to the thread earlier.
- No turn is queued for a chat thread, or for a disabled or deleted automation.
