## Context

Model tier rationale: It changes a relation cardinality contract enforced by a database trigger on populated tenants (expand-only cutover), rewrites the event-match decision that creates user-visible links and Inbox cards, and amends an accepted ADR.

An Event can have only one transcript today. `Events.transcript` and `Transcripts.event` are one `one_to_one` relation (`backend/packages/data/src/seed/seedTenDatabases.ts`, "explicit bidirectional 1:1"), enforced by the trigger from `0013_relation_cardinality.sql`, which raises `cardinality_violation`. `matchTranscriptToEvent` (`transcription/transcriptEventMatch.ts`) gives a single candidate event that already has a transcript no edge but a card proposing a new event, and the confirm of a card for an occupied event ends in `cardinality_violation` (`inbox/proposalActions.ts`). A meeting recorded in several parts, however, needs one event with several transcripts, each with its own summary. Events have no recurrence; each occurrence is its own item.

This issue makes the relation `one_to_many` so an event has many transcripts and a transcript has at most one event, and updates the match so a second recording inside one event's window attaches directly. It is independent and unblocks #1574, #1813, #1942 and #1743.

Decision (by the product owner): in v1 each part has its own summary; a combined summary over all parts is not built.

Shared-file ordering: this issue also waits for #1461 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `adr-conventions`, `canonical-keys` and `testing`.

1. Change the seed to `cardinality: "one_to_many"` for the relation whose side A is `Events.transcript` (the "one" side stays the event, so the trigger only guards "a transcript has at most one event"). Update the comment in `seedTenDatabases.ts`. Do not rename `Events.transcript`.
2. Add a tenant cutover `eventTranscriptCardinalityCutoverMigration.ts` in `transcription/` (pattern: `transcriptsCatalogCutoverMigration.ts`) that updates `relation_definitions.cardinality` to `one_to_many` for that relation and is idempotent; register it in `db/tenantCutoverMigrations.ts`. It must not change any existing edge.
3. In `matchTranscriptToEvent` remove the `eventEdges.length === 0` condition and the "single candidate already linked" branch: a single candidate gets the edge even when it already has transcripts. Update the `TranscriptEventMatchOutcome` JSDoc and the comments and tests in `transcriptEventMatch.ts` and `proposalActions.ts` that describe 1:1.
4. Add an ADR addendum under `docs/adr/` to `2026-09-23-transcription-worker-writes-event-match-results.md`: an event has many parts, a transcript at most one event.

## Scope

### In scope

- The cardinality change in seed and cutover, the match behavior, the ADR, and their tests.

### Out of scope

- A lightweight list of transcripts per event: #1636.
- Matching by interval overlap: #1813.
- Recurring events and matching to virtual occurrences: #1850.
- A summary spanning all parts: not in v1 (decided by the product owner); a combined summary of a meeting may come later as notes on the Event.

## Acceptance criteria

- When a second transcript is linked to an event that already has one (`PUT /api/items/<eventId>/relations/transcript/<transcriptId>` or the confirm of a card), then it succeeds.
- When the same transcript is linked to a second event, then `cardinality_violation` is still returned.
- When a second recording falls in the window of exactly one event, then it is linked directly and no Inbox card is created.
- When the cutover runs on a populated tenant, then no edge changes; running it again changes nothing.
