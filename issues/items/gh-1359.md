## Context

Model tier rationale: A filter added to one aggregation query and a recompute enqueue on two lifecycle operations, both with existing patterns and fixtures; the care is making archive and restore recount the right cells without a heavy synchronous walk.

A rollup property (`backend/packages/data/src/rollup/recompute.ts`) aggregates the live items on the other side of a relation. `recomputeRollupCell` counts only targets with `deleted_at IS NULL`, but it does not look at whether the target's database is archived. An archived database is hidden from lists and cannot be written to, yet its items keep being counted by rollups of other databases (and the edges stay visible), so a count on a project can include items of a database the user deleted.

This issue makes an archived database invisible to rollups: its items are not aggregated while it is archived, and archiving or restoring a database recounts the rollups that aggregate it. This is needed because archiving is the user-visible "delete" of a database (it is listed as deleted, #1873, and is purged later, #1875). Other readers that must also ignore archived databases (inline relation expansion #1518, related counts #1839, collection counts #1709, global search #1842) state that as a criterion of their own issues.

Decision: archived and restored databases trigger the existing full recompute job of each affected rollup property (the same job a rollup creation uses) rather than a walk over every edge inside the archive transaction; the job is chunked, idempotent per property and does not hold the archive request.

## Task

Load `state-writes` and `testing`.

1. In `recomputeRollupCell` add the condition that the target's database is not archived (`AND NOT EXISTS (SELECT 1 FROM databases d WHERE d.id = t.database_id AND d.archived_at IS NOT NULL)`), so an archived source database aggregates as ordinary empty input: `count`, `count_filled`, `count_empty`, `percent_filled` and `percent_empty` return 0; `sum`, `avg`, `min`, `max`, `earliest` and `latest` return null. Do not add an archive-only result mode.
2. In `backend/packages/data/src/chokePoint/databaseOps.ts` make the archive (`databaseArchiveWithClient`) and the restore of a database enqueue, in the same transaction, `enqueueRollupBackfill` for every rollup property whose dependency has this database as its `source_database_id` (`rollup/dependencies.ts`; add a lookup by source database if there is none). Zero dependencies is the common case and enqueues nothing.
3. Tests in the rollup and database test suites: a project's count of linked tasks falls when the tasks' database is archived and returns when it is restored; a sum and a count agree; archiving a database that no rollup aggregates enqueues nothing; archiving enqueues one full recompute job per dependent rollup property and a second archive request does not queue a second job (job key); the approved-operation path (`database.archive` executed after an approval) behaves the same because it uses `databaseArchiveWithClient`.

4. Coordinate dependency upsert with source archive/restore using transaction-held source-row FOR SHARE and fresh READ COMMITTED scans under the accepted source-database row-lock ADR. Prove both orders through actual configuration/archive and full/cell jobs, rollback and tenant controls.

## Scope

### In scope

- Ignoring archived source databases in rollup aggregation and recounting on archive and restore.

### Out of scope

- The other readers listed above, which carry the archived-database rule in their own issues.
- Purging an archived database: #1875.
- Rollups whose own (owner) database is archived: they are not read while archived.

## Acceptance criteria

- When a database whose items a rollup counts is archived, the rollup value drops the archived items after the recompute job runs, and returns them when the database is restored.
- Archiving a database no rollup depends on queues no rollup job.
- The approved `database.archive` path recounts exactly like the direct one.
