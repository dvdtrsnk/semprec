## Context

Model tier rationale: It writes user-visible data into every tenant once and must never bring back a type the user deleted or edited, which needs a persisted marker and exact idempotency across fresh provisioning and the repeated per-deploy cutover; a mistake duplicates or resurrects data in all tenants.

A tenant starts with no Inbox item types (`seedInboxPipelineInTransaction` creates the database empty), so the type picker in the capture UI is empty and an item can only be typed after the user has created types by hand. The product has a fixed starting set: Idea, Task, Event, Thought, Mood, Note and Contact, each with an emoji. This issue creates them, using the validation of #1436, the target list as extended by #1973 and the journal processing method of #1975. Other issues build on the existing catalog: the voice-note transcription (#1980).

Types are items of the Inbox item types database (`name`, `emoji`, `status`, `processingMethod`, `targetDatabase`). `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`) runs for every maintained tenant on every deploy, so a seeding step there must be idempotent and must remember which defaults it already created, or a type the user deleted or renamed would reappear at the next deploy. `provisionTenant` (`backend/packages/data/src/tenancy/provisionTenant.ts`) seeds a new tenant without running the cutovers, so a new tenant needs the same seeding on its own path.

Decision: the defaults are

| key | English name | Czech name | emoji | processingMethod | targetDatabase |
|---|---|---|---|---|---|
| idea | Idea | Nápad | light bulb | pageContent | none |
| task | Task | Úkol | check mark | database | tasks |
| event | Event | Událost | calendar | database | events |
| thought | Thought | Myšlenka | thought balloon | journalEntry | none |
| mood | Mood | Nálada | smiling face | journalEntry | none |
| note | Note | Poznámka | memo | pageContent | none |
| contact | Contact | Kontakt | bust in silhouette | database | people |

The key is a stable English camelCase identifier of the default, used only by the marker below; it is not stored on the type. The emoji column names the Unicode character to store in `emoji`. The targets of Idea, Thought and Mood are proposals (decided by the product owner): they are seeded as listed and can be changed later through the type write path without touching this seed.

Decision: the marker is per default, not one flag: a system-owned `json` property `seededDefaultInboxTypes` on the System settings item holding the list of keys already seeded. The cutover adds the property with raw SQL if it is missing (the settings database is `schema_locked`; see the `transcriptsCatalogCutoverMigration.ts` shape). The seeding creates only the defaults whose key is not in the list and appends their keys in the same transaction. A type the user deleted or renamed is therefore never re-created, and a tenant whose types were all deleted is not re-seeded. A module added later that brings its own default type adds one row to the table; existing tenants then receive that one type once at the next deploy, and nothing else changes.

Decision: names use the locale of the tenant's user when one exists, otherwise Czech; `status` is written as `active` explicitly. The locale is fixed at seeding time.

Decision: a default whose target database does not exist in the tenant is skipped and its key is not recorded, so it is created at the first run after that database exists. All seven defaults above target databases that every tenant has.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Add `backend/packages/data/src/inbox/defaultInboxTypes.ts` with the table above as data and `seedDefaultInboxItemTypes(client)`: it reads the list of seeded keys, creates each default whose key is missing with `createItemWithClient` (so the hook of #1436 validates them), skips a default whose target database is absent, and appends the created keys to the marker in the same transaction.
2. Add `backend/packages/data/src/inbox/defaultInboxTypesCutoverMigration.ts`: adds the marker property if missing (no-op when the settings database does not exist), then runs `seedDefaultInboxItemTypes` in one transaction under the same table lock discipline as the other cutovers. Register it in `runTenantCutoverMigrations`.
3. Call `seedDefaultInboxItemTypes` from `provisionTenant` after the system seed and the module data migrations, so a new tenant has the types without waiting for a deploy.
4. Add the marker property (empty list) to the settings seed in `seedSystem.ts` so fresh tenants have it from the start.
5. Tests: a populated tenant gets the types, the marker with all seven keys and no duplicates after a second run; a deleted type and a renamed type are untouched by a later run; a default added to the table after the first run is created once on the next run while the deleted ones stay deleted; a default whose target database is absent is skipped, not recorded, and created once the database exists; a new tenant has the types after provisioning; the Czech locale yields Czech names and an English user English names; every created type passes the type write validation.

## Scope

### In scope

- The default catalog, its once-only seeding per default for existing and new tenants, and the marker.

### Out of scope

- Validation of type writes and the new target options (#1436, #1973).
- The list response with target information (#1439).
- The `journalEntry` method itself and its proposals (#1975).
- Renaming or archiving defaults through an HTTP management route.

## Acceptance criteria

- When a tenant is provisioned, then it has the seven default types, all `active`, with the methods and targets of the table, and `GET /api/inbox-types` returns them.
- When the cutover runs a second time, then no type is added; when the user deleted or renamed a default, then it is not restored or changed.
- When a new default is added to the table after a tenant was seeded, then the next cutover creates only that type, once, and records its key.
- When the tenant's user locale is `en`, then the names are English.
- Every seeded type is accepted by the type write validation.
