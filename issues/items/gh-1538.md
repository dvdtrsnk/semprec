**Blocked by:** #1535
**Model tier:** medium

## Context

Model tier rationale: It applies one known pattern (a locked-schema cutover migration plus a seed change) to a defined pair of system databases, but it edits locked schemas on populated tenants, so the idempotence and per-tenant scoping must be exact.

An event normally gets its area through its project. An event without a project, such as a lunch with the family or a physiotherapy visit, has no way to say which area it belongs to, so it falls out of every area filter. Today there is no relation between Events and Areas: `seed/seedTenDatabases.ts` links Areas to Projects, Companies and Health records, and Files and Journal each have their own `area` relation, but Events only has `project`, `people`, `transcript`, `actionItems` and `company`.

This issue adds that relation. Areas gets a one-to-many relation to Events whose inverse is `Events.area`, so one event has at most one own area and one area has many events. The own area is only meaningful for events that have no project: for an event with a project the area stays derived from the project (#1595), and rejecting an own area on an event with a project is #1662.

Populated installs need a cutover. The Areas and Events databases of existing tenants are schema-locked (`assertDatabaseSchemaUnlocked` in `propertiesStore.ts`), so the fresh-install seed never reaches them and only a code-level migration may add the relation. The pattern to follow is `backend/packages/data/src/transcription/transcriptsCatalogCutoverMigration.ts`: it runs inside `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`) once per maintained tenant under row-level security, is idempotent, no-ops when the databases do not exist yet, and creates a relation by inserting the property, the relation definition and the property config directly with raw SQL (`createRelationPropertyWithClient` cannot be used because it enforces the schema lock).

The relation is needed by the per-database area filters (#1597) and by the related-collections read (#1839).

Decision: `Events.area` is the event's own area and is meant for events without a project only (the product lets only project-less events pick an area). Enforcing that is #1662; this issue adds the relation without a restriction.

Decision: the key collision with the derived area is not an issue. The relation property is the stored own area; the derived area is a read-time value exposed separately by #1595.

Shared-file ordering: this issue also waits for #1535 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `canonical-keys` and `testing`.

1. In `seed/seedTenDatabases.ts`, declare the relation on a fresh install: `relate({ sourceDatabaseId: areas.id, key: "events", name: "Events", targetDatabaseId: events.id, cardinality: "one_to_many", inverse: { key: "area", name: "Area" } })`, next to the existing Areas relations.
2. Add the user-visible names to `seed/i18n/cs.json` and `seed/i18n/en.json`: `property.areas.events.name` ("Události" / "Events") and `property.events.area.name` ("Oblast" / "Area"), following the existing key naming there. This is a hotspot shared with #1413, which is why it comes first.
3. Add `events/eventsAreaCutoverMigration.ts` (or the equivalent location used by the other cutovers under the data package) exporting `runEventsAreaCutoverMigration(pool)`. In one transaction, resolve the tenant's Areas and Events databases with `getDatabaseByModuleId`; return without change if either is missing; skip if `Areas.events` already exists; otherwise lock `properties` in exclusive mode, create `Areas.events` and `Events.area` as relation properties with a `one_to_many` relation definition whose `property_id_a` is `Areas.events`, and set both property configs (`relationDefinitionId`, `targetDatabaseId`) exactly as the seed would. Use `requireSingleRow` / `requireAffectedRows`.
4. Register the cutover in `db/tenantCutoverMigrations.ts` inside the per-tenant callback.
5. Tests: the cutover creates the relation on a seeded tenant without it and is a no-op the second time; a fresh seed already has the same shape; an event can be linked to one area and linking a second area to the same event is rejected by the cardinality rule; two tenants are migrated independently.

## Scope

### In scope

- The Areas to Events one-to-many relation with inverse `Events.area`, for fresh installs (seed) and populated installs (cutover), and its Czech and English names.

### Out of scope

- Rejecting an own area on an event that has a project: #1662.
- Reading the derived area of an event: #1595.
- Using the relation in a filter: #1597.
- Any change to Files.area, Journal.area, Health records.area or Companies.area.

## Acceptance criteria

- When a fresh tenant is seeded, then `Events.area` exists as a single-valued relation to Areas and `Areas.events` as its inverse.
- When the cutover runs on a tenant seeded before this change, then both properties and the relation definition exist afterwards, and running it again changes nothing.
- When a tenant has no Areas or no Events database, then the cutover does nothing and does not fail.
- When an event is linked to a second area, then the write is rejected by the one-to-many cardinality.
- When the cutover runs for several tenants, then each tenant gets its own relation and a failure in one is reported without stopping the others (existing `runTenantCutoverMigrations` behavior).
- The Czech and English labels resolve for both new properties.
