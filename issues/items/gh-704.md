## Context

`backend/packages/data/src/db/pool.ts` `createPool` (lines 6-8) is `return new Pool({ connectionString })`. Every process — the four `serve.ts` entrypoints, `db/runMigrationsCli.ts`, `observability/restoreTestResultCli.ts` — builds its pool through it, and none attaches a `pool.on("error", ...)` listener (`grep -rn "pool.on" backend/services backend/packages` finds nothing). `pg`'s `Pool` emits `'error'` when an *idle* client is dropped by the server (Postgres restart, container recreate, `idle_session_timeout`, a network reset). An `EventEmitter` `'error'` with no listener throws, which lands in `installFatalHandlers` (`backend/packages/shared/src/logger.ts` lines 119-128) as an `uncaughtException` and exits the process with status 1. A single Postgres restart therefore takes down every service at once, and the restart storm feeds the unit start limits sibling issue F2b widens.

The same constructor sets no `connectionTimeoutMillis` (a `connect()` against a hung host waits forever; `docs/adr/2026-09-17-shutdown-ordering-with-late-heartbeat-stop.md` step 5 notes "nothing in this repository sets `statement_timeout` or `connectionTimeoutMillis`") and no per-connection `statement_timeout` (a runaway query holds a pooled client indefinitely). `pg` 8.23 forwards `statement_timeout` as a startup parameter (`lib/client.js` lines 558-560), so it needs no `SET` round-trip.

This issue edits `createPool` only; #671 edits `withTransaction` in the same file and `__tests__/pool.unit.test.ts`, so it lands first. The data package already owns a package-private logger for one subsystem (`backend/packages/data/src/mail/logger.ts`, `createLogger("mail-sync")` from `@semprec/shared`); this issue adds one for the database layer the same way, per `docs/adr/2026-09-13-shared-structured-process-logging.md`.

## Task

1. Add `backend/packages/data/src/db/logger.ts` (new): `export const logger: Logger = createLogger("db");` mirroring `mail/logger.ts`.
2. In `backend/packages/data/src/db/pool.ts`:
   - Export `CONNECTION_TIMEOUT_MS = 10_000` and `STATEMENT_TIMEOUT_MS = 60_000`.
   - Change the signature to `createPool(connectionString: string, options: CreatePoolOptions = {}): Pool` with `export interface CreatePoolOptions { /** Per-connection `statement_timeout`; defaults to STATEMENT_TIMEOUT_MS; `0` disables it (the migrations CLI, whose contract-step cutovers may run longer). */ statementTimeoutMs?: number; }`.
   - Construct `new Pool({ connectionString, connectionTimeoutMillis: CONNECTION_TIMEOUT_MS, ...(statementTimeoutMs > 0 ? { statement_timeout: statementTimeoutMs } : {}) })`.
   - Attach `pool.on("error", (err) => { logger.error({ err }, "Idle pool client errored; the client was discarded"); })` before returning. The docstring states why the listener exists (an unlistened `'error'` is an uncaught exception that `installFatalHandlers` turns into `process.exit(1)`) and that `pg` has already removed the failed client from the pool when this fires, so nothing else needs to happen.
3. In `backend/packages/data/src/db/runMigrationsCli.ts` line 17, call `createPool(connectionString, { statementTimeoutMs: 0 })` with a one-line comment (cutover migrations are not bounded by the runtime statement timeout). The other callers keep `createPool(connectionString)` unchanged.
4. Tests — `backend/packages/data/src/__tests__/pool.unit.test.ts` (existing, unit tier, no Postgres), a new `describe("createPool")`:
   - `createPool("postgres://x").emit("error", new Error("boom"))` does not throw (a listener exists) — spy on the `db` logger via `vi.spyOn(logger, "error")` (import from `../db/logger.js`) and assert it was called once with the error; `pool.end()` in `afterEach` (no connection was ever opened, so `end()` resolves without a server).
   - `createPool("postgres://x").options` carries `connectionTimeoutMillis === 10_000` and `statement_timeout === 60_000`; `createPool("postgres://x", { statementTimeoutMs: 0 }).options.statement_timeout` is `undefined`.

## Acceptance criteria

- When Postgres drops an idle pooled connection under a running `semprec-api`, the process logs one `Idle pool client errored` record and keeps serving; the next query acquires a fresh client.
- When the database host does not answer, `pool.connect()` rejects within ~10 s instead of hanging.
- When a statement runs longer than 60 s on a runtime pool, Postgres cancels it with `canceling statement due to statement timeout`; the migrations CLI's statements are not bounded.
- `pnpm vitest run --config vitest.unit.config.ts packages/data/src/__tests__/pool.unit.test.ts` passes.
