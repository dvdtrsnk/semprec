## Context

Model tier rationale: It introduces a manual-override state machine that must coexist with a system-owned property and a background job without creating a second writer, plus a new retry route that touches the job queue and the automation lock state, so ordering and ownership errors are easy to make.

The `cover` property of Books and Movies is `owner: system` (`backend/packages/data/src/seed/seedLibraryModule.ts`): a user write gets 403 from `assertWritableProperties` in `backend/packages/data/src/chokePoint/itemWrites.ts`, and only the library metadata job writes it. If a user path could change or delete `cover`, that would be a second writer under `docs/adr/2026-09-10-single-writer-ownership-model.md`. Users still need to choose their own cover (a photo or an image), remove the cover, and ask the automation to look again. Today `setItemAutomationLocked` in `backend/packages/data/src/library/itemAutomationStore.ts` has no caller, and the only retry is the nightly 04:00 sweep.

Decision: the manual cover lives in separate user-owned properties, so each value has one writer:
- `coverOverride` (type `image`, owner `user`): `{ blobId }` of the chosen image;
- `coverRemoved` (type `checkbox`, owner `user`): the user removed the cover;
- `coverSource` (type `select`, owner `user`, options `candidate | userPhoto | userImage`): where the override came from.
The cover shown to the user is: nothing if `coverRemoved`, else `coverOverride` if set, else `cover`. The job keeps writing only `cover` (and the other fields), so a manual choice is never overwritten and the author and other data are still filled.
Decision: removing a cover sets `coverRemoved` only and does not lock the whole item (the automation still fills other data). No lock or unlock route is added here.
Decision: "search again" clears `coverOverride`, `coverRemoved` and `coverSource`, lifts a `locked` state, resets the automation row to `pending` and enqueues the job at once instead of waiting for 04:00.

Builds on #1768 (state and invalidation after each run) and #1401 (upload of a standalone image blob through `POST /api/blobs`, and collection of unused blobs). #1812 builds on this issue for candidates.

Shared-file ordering: this issue also waits for #1779, #1784, #1790 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `canonical-keys`, `db-migrations`, `error-handling`, `io-hardening` and `testing`.

1. Seed `coverOverride`, `coverRemoved`, `coverSource` on Books and Movies in `seedLibraryModule.ts`; add per-tenant cutover `backend/packages/data/src/library/libraryCoverOverrideCutoverMigration.ts` (idempotent, same pattern as the Books year/isbn cutover of #1514) registered in `backend/packages/data/src/db/tenantCutoverMigrations.ts`; add i18n names and the three `coverSource` option labels in `library/i18n/cs.json` and `en.json`; bump the library manifest version. Add optional `coverOverrideKey`, `coverRemovedKey`, `coverSourceKey` to `LibraryModuleContract` (`library/libraryModuleContract.ts`) and fill them in the seed so the library grid view config exposes them.
2. Item update hook for library databases (registered in `backend/packages/data/src/domainWriteHooks.ts`): `coverOverride` must reference an existing blob of the tenant and requires `coverSource`; setting `coverOverride` clears `coverRemoved`; setting `coverRemoved: true` requires `coverOverride` to be null; invalid combinations are `ValidationError` (400). Plain item PATCH is the write path for user photo and user image: the client uploads through `POST /api/blobs` (#1401) and then PATCHes `coverOverride` and `coverSource` (`userPhoto` or `userImage`). No Files item is created.
3. Verify and, if needed, extend `deleteBlobIfUnreferenced` in `backend/packages/data/src/blobs/blobsStore.ts` so a blob referenced by `coverOverride` or `cover` is not deleted when a Files item with the same bytes is purged.
4. Custom route `POST /api/items/:id/automation/retry`, declared in `libraryModuleManifest.ts` `customRoutes` (justification `transactional-semantics`), handler exported from the library module and registered in `backend/services/semprec-api/src/routeMatrix.ts`: in one transaction clear the three override properties through the normal user update path, set the automation row to `pending` (also from `locked`), and enqueue the metadata job with `enqueueLibraryMetadataProcessing` (job key derived from the item id, the per-tenant lane applied by `enqueueJob`); respond 202. An item outside a library database or of another tenant is 404. The agent has no tool for this route.
5. Publish the item's realtime invalidation after commit for the retry route; plain PATCHes already invalidate.
6. Tests: PATCH `coverOverride` + `coverSource` works and a following job run leaves `coverOverride` untouched but fills an empty author; removing sets `coverRemoved` and a later run keeps it; retry clears the overrides, enqueues a job that runs within the test's worker loop and ends with `source` set; retry on a locked row unlocks it; invalid combinations are 400; a foreign tenant's item gives 404 (add the route to `tenantIsolationRoutes.test.ts`); a purged Files item with the same bytes does not delete the cover blob.

## Scope

### In scope

- The three user-owned override properties, their validation, the retry route, reference safety of the override blob, realtime invalidation of the retry.

### Out of scope

- Candidate storage, listing and selection: #1812.
- Uploading the image bytes: #1401.
- Lock and unlock of a whole item: not in v1 (the whole-item lock is dropped from the design; undo and the trash provide reversibility).
- Recording automation states and codes: #1708.

## Acceptance criteria

- When the client PATCHes `coverOverride` and `coverSource`, then the next job run does not change `coverOverride` but still fills an empty author.
- When a photo is chosen from the camera, then no item is created in Files, and purging a Files item with the same bytes does not delete the cover blob.
- When `POST /api/items/:id/automation/retry` is called, then the response is 202, the job runs within seconds and, if found, the automation state reports its `source`.
- When the cover was removed, then `coverRemoved` stays true across later job runs, and the item is not locked.
- When `coverRemoved: true` is sent together with a non-null `coverOverride`, or a `coverOverride` of a missing blob, then the response is 400.
- When the item belongs to another tenant or is not a library item, then the retry route answers 404.
