**Blocked by:** #969

## Context

Tenant isolation runs on row-level security over every tenant-owned table. That only works if the set of tenant-owned tables is explicit and stays complete. The tenancy ADR from #968 decided where the classification lives: in the database, as `COMMENT ON TABLE <t> IS 'semprec:tenancy=tenant'` or `'semprec:tenancy=global'`, written by the migration that creates the table. A catalog test fails on any unclassified table, and no TypeScript registry is kept, which would be a hotspot every table-creating issue had to edit. #968 already tagged `tenants` as global, and #969 made the comment a review rule. This issue tags every other existing table and adds the catalog test. #972 (the `tenant_id` columns) and #973 (row-level security) build their own assertions on this classification, in the same test file.

The tables at `origin/develop` are the 51 created by `backend/packages/data/src/db/migrations/0001`..`0054`, plus `schema_migrations`, which the runner creates before any file runs (`backend/packages/data/src/db/migrate.ts:10-15`). Three things are outside the check:
- The `graphile_worker` schema. It is global by construction: it lives in its own schema, which `ensureQueueSchema` creates after the migrations (`backend/packages/data/src/db/runMigrationsCli.ts:32`).
- The `items_p_*` partitions. They are created per database by `create_items_partition` (`0048_create_items_partition_function.sql:23-32`) and classified through their parent, `items`.
- Scratch tables and schemas created by other test files (`__tests__/leastPrivilegeRoles.test.ts:101-111`, `__tests__/migrate.test.ts:15-31`). Integration files run one at a time (`backend/vitest.integration.config.ts:19`), and each of these drops what it creates.
