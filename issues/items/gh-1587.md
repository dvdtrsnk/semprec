## Context

Model tier rationale: One well-defined mechanism across the existing operation catalog, REST and MCP seams, reusing the state and handoff rules from the preceding issue, but it touches several closed-catalog files with compile-time exhaustiveness checks.

A user can stop an inherited value following its source without changing the value ("unlink"), and can start following again ("relink", which takes over the sources' current value). #1516 ends links when a value is written and defines the `valueLinks` handoff. This issue adds the two explicit operations on top. #1758 puts an approval step in front of Semp's use of unlink.

Today the generic operation catalog is closed: `GENERIC_OPERATION_NAMES` in `shared/src/genericOperations/operationNames.ts` lists 29 operations, and `schemas.ts`, `port.ts`, `capabilities.ts` and `bindings.ts` are checked against it at compile time. REST routes are in `semprec-api` (`itemsHandler.ts`, the route table `routeMatrix.ts`), and MCP tools are the same catalog prefixed `semprec.`.

Decisions:

- `link.unlink` keeps the value and sets the state to `broken`; `broken_by` is `user` for a REST actor and `agent` for an agent or MCP actor.
- `link.relink` is the only way back to `on`. It sets the state to `on` first and then writes the sources' current value as the system writer with process `valueLinks`, in one transaction, so the handoff check from #1516 passes.
- A single-source link relinks to that source's value; a link with several sources relinks to the union of their values.
- Unlinking an already broken link returns the current state unchanged. Unlinking an item with no link, relinking an item with no link, and relinking when no source is still alive (every source missing or in the trash) are all `409` with a dedicated error code, and nothing is written.
- If the union has more values than the property's cardinality allows (a single-valued property with several source values), relink is rejected with `409` and nothing is written.

Shared-file ordering: this issue also waits for #1583 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `link.unlink` and `link.relink` to the catalog. Input for both: `{ itemId: string, propertyKey: string }` (`.strict()`). Output for both: `{ itemId, propertyKey }` plus the link entry in the same shape `links[propertyKey]` has on reads. Update `operationNames.ts`, `schemas.ts`, `port.ts` (`unlinkValue` and `relinkValue` on `GenericApplicationPort`), `capabilities.ts` (both non-destructive with `core.item.write`) and `bindings.ts`, and fix every place that asserts the catalog size or lists its names (including the operation catalog test and the MCP tool list).
2. Implement both in `genericApplicationService.ts` on top of two choke point operations in `backend/packages/data/src/chokePoint/valueLinkOps.ts` (new, registered in `chokePoint.ts`). `unlink` takes the writer kind from the actor (as #1415 defines it) and reuses `breakValueLinks`. `relink` locks the link row, loads the live sources, computes the union of the source properties' current values, sets the state to `on` (clearing `broken_by` and `broken_at`), then replaces the target property's value: for a relation property by creating and deleting the differing edges through `createRelationWithClient` and `deleteRelationWithClient` with the `valueLinks` context, for a plain property through `updateItemWithClient` with the `valueLinks` owner process. Keep the source-value resolution private to this file.
3. Raise the 409 cases above as a `ChokePointError` with status 409 and a new code `value_link_conflict`; register the code in the REST error contract (`adapter/errorContract.ts`) the way the other codes are.
4. REST: `POST /api/items/:id/links/:propertyKey/unlink` and `POST /api/items/:id/links/:propertyKey/relink` in `itemsHandler.ts`, both returning 200 with the operation output. Add both routes to `routeMatrix.ts` and to the tenant isolation route test.
5. Send an item invalidation after the commit (same call shape the item write path uses) so clients refetch `links` and the value.
6. Tests: unlink keeps the value and sets `broken`/`user`; the same through MCP gives `agent`; relink restores the source's value and `on`; relink with two sources restores the union; relink with no row, no live source, or an over-cardinality union gives 409 and writes nothing; an unlinked value then followed by a user edit stays `broken`; foreign-tenant item ids behave as not found.

## Scope

### In scope

- The two operations over the shared catalog, REST routes and MCP tools.
- Relink writing the sources' current value under the `valueLinks` handoff.

### Out of scope

- Ending links on ordinary writes and the handoff check itself: #1516.
- Approval before Semp unlinks: #1758.
- Propagating a changed source value to linked items: #1593.
- Any client UI.

## Acceptance criteria

- When `POST /api/items/:id/links/projects/unlink` is called on a file with an inherited project, then the project is unchanged and the link reads `inheritedBroken` with `brokenBy: "user"`; through MCP `semprec.link.unlink` it reads `brokenBy: "agent"`.
- When `relink` is called on a broken link whose source still exists, then the item's value equals the source's current value and the link reads `inherited`.
- When `relink` is called with no link row, with no live source, or with a union the property cannot hold, then the response is 409 `value_link_conflict` and nothing changes.
- When unlink is called on an already broken link, then the response is 200 and the existing `brokenBy` and `brokenAt` are kept.
- Both operations appear in the MCP tool list, require the `core.item.write` capability, and are listed in the route matrix.
