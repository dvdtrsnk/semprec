### Requirement gh-1774: [calendar-invites 03/13] Send meeting invitations, updates and cancellations

#### Context

Model tier rationale: It adds outbound email jobs coupled to database commits, reacting to Event updates and deletes through choke point hooks, with retry and failure semantics across provider transports and snapshot payloads for data that may be gone by the time the job runs.

The user can link people to an Event and invite them by email (#1757 stores the invitation state on the edge, #1790 writes it). Nothing sends the invitation: `sendDraftEmail` (`backend/packages/data/src/mail/send.ts`) is a function no production code calls, `createSmtpClient` is never supplied, and `OutgoingMailMessage` (`mail/smtpClient.ts`) has only text and html. The outgoing MIME builder with an optional calendar part (#1491) and the per-mailbox transports (#1634 SMTP, #1753 Microsoft Graph, and the Gmail API transport from #1637 if present) are delivered elsewhere. Events have a stable `icalUid` and a `icalSequence` that increases when the time or place changes (#1599). The choke point can run item delete and restore hooks (#1601).

This issue sends the meeting invitation messages: an iTIP `REQUEST` to a newly invited person, an updated `REQUEST` with a higher `SEQUENCE` when the time or place of an Event with invited people changes, and a `CANCEL` when an invited person is removed or the Event is deleted. Sending runs as a queue job enqueued in the same transaction as the change (commit-coupled, as `enqueueNotificationFanout` does), so a rolled-back change sends nothing and a committed one is retried until delivered.

Decision: the iCalendar times in an outgoing message are UTC instants (`Z`), converted from the Event's wall-clock values in the tenant time zone with the helpers of the calendar time module (#1418); an all-day Event uses `DATE` values and an exclusive `DTEND`. No `VTIMEZONE` is emitted.

Decision: an updated `REQUEST` does not reset the recorded replies to `pending`; each invited person keeps their last reply status until they reply again.

Decision: restoring a deleted Event from the trash does not send a new invitation.

Decision: the organizer address is the first line of the sending mailbox's `Mailboxes.addresses`; the attendee address is the `email` stored on the edge's invitation (the first line of `People.emails` when the invitation was written).

The low-level serialization helpers (`calendar/icalendarWriter.ts`) are shared with the reply message of #1953; whichever of the two issues merges second extends the existing file instead of creating another one.

### Requirement gh-1778: [calendar-module 08/15] Guard system calendars and keep exactly one default

#### Context

Model tier rationale: One known mechanism (update and create hooks that validate and normalize a single module's items) across the same hook files as the previous calendar issue, with a transactional default-switch that needs a lock, but no new cross-process or authorization contract.

#1600 seeds the `calendars` database and #1761 assigns Events to it. Nothing yet protects its rows. A generic write of the system-owned `kind` and `systemKey` is already rejected with 403 by the choke point's ownership check, but a client can still rename a system calendar, store a malformed colour, or leave the tenant with zero or two default calendars. This issue adds the rules for the module's own rows, as hooks in the same files and registration as #1761.

Rules, applied on create and update of a calendar:

- `name` of a calendar whose `kind` is `system` or `subscription` cannot change: 403 `forbidden` (field `name`). `color`, `hidden` and `notify` can.
- `color` must match `#RRGGBB` (six hexadecimal digits): otherwise 400 `validation_failed` (field `color`).
- Exactly one live own calendar has `isDefault` true. Setting `isDefault` true on a calendar clears it on the previous default in the same transaction. Setting it true on a system or subscription calendar is 400 (field `isDefault`). Clearing it on the only default, without setting another, is 400 (field `isDefault`).

Decision: the default switch takes a transaction-scoped advisory lock keyed by the Calendars database id before it reads or changes any `isDefault`, so two concurrent switches serialize and the tenant never ends with two defaults.

Deleting a calendar (including the default) is #1803; a default that is deleted passes the flag on there.

Shared-file ordering: this issue also waits for #1777 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `backend/packages/data/src/calendar/calendarRowHooks.ts` exporting `calendarItemCreateHook` and `calendarItemUpdateHook`, applying only to the Calendars database, implementing the rules above. The default switch writes the other row through `updateItemWithClient`; the new default is written first so the clearing of the old one is never the removal of the only default.

### Requirement gh-1780: [tasks-in-events 05/10] Derive task visibility and effective day from host events

#### Context

Model tier rationale: Derived values stored on the task are recomputed from several sources (host edges, event dates and ends, the task's own date) inside the writing transaction, with a time-zone-dependent rule, a shared first-planned-day rule and a data migration, so a missed trigger leaves tasks wrongly hidden or on the wrong day.

A task placed in an event (#1764) disappears from every list, count, search and calendar day until the last of its host events has ended, and meanwhile its day is the day of the event that was added last. Today there is no such state. #1540 created two derived Tasks properties, both owned by the system and written only by the Tasks process: `hiddenUntil` (date with time) and `effectiveDate` (date). #1422 gives Tasks a pre-write transform, #1530 an after-write hook for relation edges, and #1418 the time-zone-aware event end. #1602 exports the first-planned-day rule that records `since` and `sinceTime` when a task moves on, and #1657 normalized stored dates and times. Event ends come from the Events properties of #1416 (the end is `endDate` or `date` plus `timeTo`; a timed event without `timeTo` gets its end filled by #1598; an event without times ends at the end of its last day).

This issue stores the derived values and keeps them correct. Readers use them: lists and counts (#1798), the nightly move (#1674) and the calendar (#1880); the job that reveals a task at the end time is #1782; deleting and restoring an event is #1819.

Decisions:
- The derived values are stored, not computed on read, and a job reveals tasks at the end time (#1782).
- `hiddenUntil` is stored as a UTC ISO instant. It is the latest end among the task's live host events when that end is later than now, otherwise null.
- `effectiveDate` equals `date` when the task has no live host event. While `hiddenUntil` is set, it is the `date` of the live host event added last. When every live host event has ended, it is the later of the task's `date` and that last-added event's `date`.
- Only live (not trashed) events count. An event without a `date` is ignored.
- When a recomputation changes the `effectiveDate` of a task that is `notDone`, whose previous `effectiveDate` is before today and whose `since` is empty, the same transaction also records `since` and `sinceTime` with the rule exported by #1602.

### Requirement gh-1782: [tasks-in-events 07/10] Reveal a task when its last event ends

#### Context

Model tier rationale: One delayed-job mechanism on existing queue primitives with a recompute function from the blocker, with the care that the job must be correct when the end moves or the queue runs late.

A task hidden inside its events must come back when the last of them ends (#1780 stores `hiddenUntil` and recomputes `effectiveDate`). Decisions:
- The job never blindly clears `hiddenUntil`: it recomputes from the current edges and event ends and writes the result, so an event that was extended in the meantime keeps the task hidden and the job enqueues itself again.
