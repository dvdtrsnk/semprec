**Blocked by:** #82

## Context

Database archival is intended to decommission a database without deleting it. The completed choke-point currently prevents schema changes in locked databases but still permits create, update, delete, restore, and relation mutations involving items in an archived database.

## Task

Introduce one reusable archived-database guard inside the protected data layer and apply it to every item mutation, including create, property patch, soft delete, restore, and both sides of relation mutations. Reads remain available. Restoring the database itself remains allowed and re-enables mutations. Return HTTP/service status 403 with canonical code `database_archived`. Preserve idempotency semantics: replay of an idempotent create that committed before archival succeeds by returning the existing authoritative row without writing or emitting side effects; this no-write replay is the sole exception. A new key or a replay whose original row no longer exists returns `database_archived`.

## Scope

### In scope

- Choke-point item and relation mutation behavior for archived databases.
- Stable service error behavior and tests.

### Out of scope

- Archive UI or REST routes.
- Hard deletion or purge of databases.
- Changes to `schema_locked` semantics.

## Acceptance criteria

- Every item or relation mutation touching an archived database returns 403 `database_archived` without partial writes or queued side effects, except the explicitly allowed no-write replay of a pre-archive idempotent create.
- Reads continue to work while archived.
- Restoring the database makes the same mutations available again.
- Idempotency replay cannot be used to introduce a new row while archived.
