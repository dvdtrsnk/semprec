## Context

Model tier rationale: One pure retain-or-drop helper with a single call site in the user revise path and an exported contract for the type-change route, using existing fixtures and no new lifecycle or authorization contract.

Manual values on a proposal card (`userOverrides`, `userEditedKeys`, written by #1892) only make sense for the destination they were typed for. When the user changes the card's destination, for example by converting a task into an event, the old values must not leak into the new card. The destination is the pair `entityKind` and `target` of the proposal envelope. Today `reviseProposalWithClient` in `backend/packages/data/src/inbox/proposalActions.ts` replaces the whole envelope, and the type-change route and thread-driven type change come later (#1947).

Decision: when `entityKind` or `target` changes, all overrides and `userEditedKeys` are cleared and a history entry with `kind: "reset"` and a reason message is added. When the destination is the same, only override keys that are properties of the new destination are kept (for a `pageContent` envelope, keys present in the new envelope's `properties`); the others are dropped. This issue delivers the helper and wires it into the user revise; #1947 calls the same helper.

## Task

Load `state-writes` and `testing`.

1. Add `retainOverridesForEnvelope(previousAiEnvelope, nextEnvelope, overrides, targetPropertyKeys)` to `backend/packages/data/src/inbox/proposalOverrides.ts`, returning `{ userOverrides, userEditedKeys, reset: boolean, droppedKeys: string[] }`; `reset` is true when `entityKind` or `target` differ. Export it for #1947.
2. In `reviseProposalWithClient`, load the target database's property keys, call the helper under the existing lock, and write `userOverrides`, `userEditedKeys` and the history entry (`kind: "reset"` with the dropped keys in the message when something was dropped, otherwise the existing revise entry). Add the new keys to `allowedSystemKeys`.
3. Tests in `proposalActions.test.ts` and a unit test for the helper.

## Scope

### In scope

- The retain-or-drop rule on destination change and its use by the user revise.

### Out of scope

- The type-change route and recompute (#1947), which calls this helper.
- Dropping overrides during the tick's recompute (#1921).
- Keeping protected keys against thread revisions (#1938).

## Acceptance criteria

- When a card with an edited task title is revised to an event destination, then `userOverrides` and `userEditedKeys` are empty and the history has an entry with `kind: "reset"`.
- When a card is revised within the same target and two edited keys exist, one of which is not a property of that target, then only the valid key stays in `userEditedKeys`.
- When nothing is edited, then no `reset` entry is added.
- The helper is covered by tests for the changed entityKind, changed target, same destination and empty-override cases.
