## Behavior specification (approved)

Part of the multi-tenancy program specified in #950:

1. Each tenant gets its own data key, wrapped by `CREDENTIALS_MASTER_KEY`; credentials are sealed with an AEAD whose associated data binds them to `tenant_id‖item_id`, so a ciphertext copied to another row or tenant no longer decrypts.
2. New credentials use the tenant key; existing ones are re-encrypted by a resumable job; reads accept both schemes until the master-key-only scheme is retired in a later release.
3. Tenant keys are excluded from the long-retention backup and dumped separately with 7-day retention, so deleting a tenant's key shreds its secrets everywhere within 7 days.

## Decisions

- **Why envelope encryption per tenant?** → Crypto-shredding on account deletion, and ciphertext bound to its row.
- **In which order does it roll out?** → Dual read first; the tenant scheme is written only after the release checkpoint proves a release that reads both schemes runs in production; existing rows are re-encrypted in that same phase; the master-key-only scheme is retired only after the second checkpoint proves the strict release runs in production. → Every step stays safe to roll back by one release.
- **What does disaster recovery lose?** → Nothing within 7 days; older restores lose connected-account secrets, and users reconnect.

## Out of scope

Account deletion itself (#958); per-service secret files (#957).
