## Context

Harvest issue #775 collected three findings, each a test that doesn't verify
everything it should, in three unrelated test files:

- PR #349's `authHandler.test.ts`: "rejects a native session's token when presented
  as a cookie" (line 267) only exercises `platform: "ios"`; no parallel case exists
  for `platform: "macos"`, even though `authHandler.ts` treats both as native
  platforms subject to the same channel-enforcement rejection.
- PR #360's `mcpInvokeTool.test.ts`: the `approval_pending` notification test
  (lines 253-262) `SELECT`s and asserts `user_id, kind, title, source_table,
  source_id, transition_instance` but omits `link_href`, unlike the
  `agent_run_error`, `automation_error`, and `mail_sync_error` notification tests
  elsewhere in this diff, which all assert `link_href`. The production code
  (`mcpInvokeTool.ts:185`) sets `linkHref: \`?page=approvals&user=${userId}\``, which
  this test never checks.
- PR #379's `propertyOps.test.ts` (the rollback test moved here from
  `chokePoint.test.ts`, lines 77-79): asserts `.rejects.toBeInstanceOf(ForbiddenError)`
  for a locked-property rollback, but the specific error `updateProperty` actually
  raises is `PropertyLockedError` (`errors.ts:100`, which currently extends
  `ForbiddenError`). The test passes today only because of that inheritance and would
  keep passing even if a code change started throwing a different `ForbiddenError`
  subclass instead.

## Task

- In `authHandler.test.ts`, add a test parallel to "rejects a native session's token
  when presented as a cookie" that logs in with `platform: "macos"` and asserts the
  same 401 rejection when that token is presented as a cookie.
- In `mcpInvokeTool.test.ts`, add `link_href` to the `SELECT` in the
  `approval_pending` notification test and to its `toMatchObject` assertion,
  expecting `` `?page=approvals&user=${user.id}` ``.
- In `propertyOps.test.ts`, change the rollback test's assertion from
  `.rejects.toBeInstanceOf(ForbiddenError)` to
  `.rejects.toBeInstanceOf(PropertyLockedError)`, importing `PropertyLockedError`
  from `../errors.js`.

## Touches

- backend/services/semprec-api/src/__tests__/authHandler.test.ts (new test case
  alongside the existing ios cookie-rejection test)
- backend/packages/agent-runtime/src/__tests__/mcpInvokeTool.test.ts (the
  `approval_pending` notification test)
- backend/packages/data/src/__tests__/propertyOps.test.ts (the locked-property
  rollback test)

## Scope

### In scope

- The three assertion/coverage gaps named above, each in its own test.

### Out of scope

- Any other test or production code change.

## Acceptance criteria

- A test exists that logs in with `platform: "macos"`, then asserts a 401 when that
  native session's token is presented as a cookie to `GET /api/auth/session`.
- The `approval_pending` notification test's query selects `link_href` and its
  assertion checks `link_href` equals `` `?page=approvals&user=${user.id}` ``.
- The locked-property rollback test asserts
  `.rejects.toBeInstanceOf(PropertyLockedError)`, not the looser `ForbiddenError`.
