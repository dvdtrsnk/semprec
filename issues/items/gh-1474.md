## Context

Model tier rationale: A single call site in `sendDraftEmail` reuses the existing `resolveThreadId` and the existing `threadId` input of `upsertMailMessageMeta`, with no new lifecycle, tenant or persisted-data contract.

A message sent from Semprec never joins a conversation. `sendDraftEmail` (`backend/packages/data/src/mail/send.ts`) claims the draft by calling `upsertMailMessageMeta` (`mail/mailMessageMetaStore.ts`) with `inReplyTo` and `references` but without `threadId`, so the sent message's `mail_message_meta.thread_id` stays `NULL`. A reply sent from Semprec therefore does not appear in the thread of the message it answers, and a thread list built on `thread_id` cannot show it.

Incoming messages get their thread from `resolveThreadId` (`mail/threading.ts`), which looks up the ancestors named in `In-Reply-To` and `References` and any already-synced descendants, and creates a thread when none is found. It must run before the message's own `mail_message_meta` row exists.

Decision: the sent message is threaded at claim time, in the same transaction as the claim insert, and the thread id is never recomputed later. When the provider's Sent folder is later synced, ingest finds the existing row for the same mailbox and message id and keeps this `thread_id` (the upsert only fills it when the new value is non-null).

Threads of messages that were sent before this change are repaired by #1570. The thread list that reads `thread_id` is #1567, and sending a draft over HTTP, which calls this same code, is #1896.

## Task

Load `state-writes` and `testing`.

1. In `sendDraftEmail`, inside the existing claim transaction and before `upsertMailMessageMeta`, call `resolveThreadId` with the newly generated `messageId`, `input.inReplyTo`, `input.references` and `subjectHint: input.subject`, and pass the result as `threadId` to `upsertMailMessageMeta`.
2. Keep the claim semantics unchanged: if the claim insert fails with the primary-key conflict, the call still ends in `ConflictError`, and the SMTP-failure path still deletes the claim row. A thread created for a claim that is rolled back or deleted must not be left orphaned (the resolve call runs in the same transaction as the claim, so a rollback removes it; for the SMTP-failure delete, remove the thread when the deleted row was its only message).
3. Add tests in `backend/packages/data/src/__tests__/mailSend.test.ts`: a reply sent with `inReplyTo` of an existing synced message gets that message's `thread_id`; a send with no ancestors gets a new thread; a retry after SMTP failure leaves no orphan `mail_threads` row.

## Touches

## Scope

### In scope

- Computing and storing `thread_id` for messages sent from Semprec at send time.

### Out of scope

- Threading existing sent messages that have `thread_id` NULL: #1570.
- Joining copies of one message delivered to several mailboxes: #1384.
- Linking sender and recipient people on the sent message: #1480.
- The thread list itself: #1567.

## Acceptance criteria

- When a reply is sent with `inReplyTo` naming a synced message, then the sent message's `mail_message_meta.thread_id` equals that message's `thread_id`.
- When a message without ancestors is sent, then it gets a new thread and a later reply to it joins that thread.
- When the provider's Sent folder is synced afterwards and ingest sees the same message id, then the `thread_id` is unchanged and no second thread exists.
- When the SMTP send fails and the claim is removed, then no empty `mail_threads` row remains.
