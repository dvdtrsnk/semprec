## Context

Model tier rationale: It is the first production wiring of a mail provider into the api queue runtime, combining OAuth client secrets, token refresh with rotation, and a shared factory that two later transports also edit, where a wiring mistake silently disables sync for every tenant.

In production nothing syncs. `createApiQueueRuntime` in `backend/services/semprec-api/src/queueRuntime.ts` passes `undefined` for the mail sync adapters, so `createCoreTaskList` (`backend/packages/data/src/worker.ts`) uses `noopMailSyncAdapterFactory` and the mail sync job (`backend/packages/data/src/mail/mailSyncJob.ts`) fails with "No Gmail adapter configured" for a Gmail-mode account. The clients exist: `GmailRestClient` (`mail/gmailRestClient.ts`) takes a `getAccessToken: () => Promise<string>`. The OAuth client id and secret (`GMAIL_OAUTH_CLIENT_ID`, `GMAIL_OAUTH_CLIENT_SECRET`) are listed in `deploy/shared/env/api.env.example` but no code reads them.

`MailSyncAdapterFactory` (`mailSyncJob.ts`) has three optional members: `createImapClient`, `createGmailClient`, `createGraphClient`. The three transport issues all fill that one factory in `queueRuntime.ts`, which is why they are chained: this one first, then #1508 and #1510.

Builds on #1481, which refreshes the access token and persists a rotated refresh token. Later issues that need a Gmail client build on this one: #1686 (connect a mailbox), #1746 (write moves back to the provider), #1637 (send through the Gmail API), #1739 (watch lifecycles).

Decision: the factory is created in a new file in the api service from the process environment; when the Gmail OAuth client id or secret is missing, `createGmailClient` is left undefined and the process logs one warning at startup (the sync job then fails per account with the existing clear message and the accounts show a sync problem), instead of the process refusing to start.

## Task

Load `io-hardening`, `error-handling` and `testing`.

1. Add `backend/services/semprec-api/src/mailSyncAdapters.ts` exporting `createMailSyncAdapters({ pool, env, fetchImpl? })` that returns a `MailSyncAdapterFactory`. In this issue it fills `createGmailClient(mailboxItemId, credential)`: returns `new GmailRestClient(getAccessToken)` where `getAccessToken` calls `refreshAndPersistAccessToken` (#1481) with `GOOGLE_TOKEN_URL`, the Gmail client id and secret from `GMAIL_OAUTH_CLIENT_ID` and `GMAIL_OAUTH_CLIENT_SECRET`, caching the access token in memory until shortly before its expiry for the life of that client object only.
2. A 400/401 from the refresh surfaces as `MailReauthorizationRequiredError` (already handled by the sync job); no token or secret appears in errors or logs. Apply the bearer-sync privacy ADR below.
3. Pass the factory to `createApiCoreTaskList` in `queueRuntime.ts` in place of `undefined // mailSyncAdapters`.
4. Update the comment in `deploy/shared/env/api.env.example` for the Gmail keys from "once built" to the real consumer.
5. Tests against a fake Gmail HTTP server (injected `fetchImpl`): a Gmail-mode account sync pass through `handleMailAccountSyncTask` (or the job's test entry) ingests the fake messages; an expired access token is refreshed once; a 401 refresh gives `needsReauthorization`; with the client id unset the factory has no `createGmailClient` and one warning is logged.

## Acceptance criteria

- When the Gmail OAuth client is configured, then a sync pass of a Gmail-mode account downloads its mail (fake provider).
- When the access token has expired, then it is refreshed before the request and not again on every request.
- When the provider rejects the stored refresh token, then the account is marked as needing reauthorization.
- When the OAuth client is not configured, then the process starts, logs one warning, and the sync of a Gmail account fails with the existing adapter message.
- When errors or logs are inspected, then no token or client secret appears.
