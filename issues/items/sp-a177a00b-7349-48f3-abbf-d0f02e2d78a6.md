## Context

Model tier rationale: Pure but wide JSON transformations over the answers of a dozen routes, a filter evaluator that must agree with the server's filter tree on the nodes the app sends, and ordering rules; a wrong rule shows data that is not there or hides data that is.

Since `[offline-first 03/07]` a write without a connection waits in the queue of `OfflineLayer` and the repository gets a made-up answer, but the kept answers of `[offline-first 01/07]` still show the state before the write: the screen that reloads after the write shows the old task, the old time of the event, the deleted project. While the queue replays after a reconnect, an answer the server sends before an entry reached it shows the same old state.

The answers are JSON. Items appear as objects with `id`, `databaseId`, `properties` and `relations` (item reads, `POST /api/databases/:id/query` pages `{items, nextCursor}`); the calendar timeline and the agenda answer `{items: [...]}` of entries with `kind` (`event`, `task`, …), `id`, `title`, `date`, `endDate`, `timeFrom`, `timeTo`, `status`, `place`, `calendarId`, `version`, `seriesId`, `occurrenceDate` and `readOnly` (a virtual occurrence has a `seriesId` and is read only); the reminders feed answers objects with `key`, `itemId`, `kind`, `title`, `fireAt`, `startsAt`. The filter tree the app sends (`ItemsApi.kt`: `Filter`, `RelationFilter`) uses `and`, `or`, `equals`, `not_equals`, `is_empty`, `is_not_empty`, `date_relative`, `relation_contains`, `relation_is_empty` and `relation_path_contains`.

## Task

Load `kmp-shared`, `testing`, `error-handling` and `mobile-verify`.

1. Every answer of the offline set that `OfflineLayer` returns (kept or just received) is returned with the queued entries applied in queue order; with nothing queued it is returned unchanged, byte for byte. An answer that cannot be parsed as JSON is returned unchanged.
2. Item changes (`PATCH /api/items/:id`): every object with that `id` and a `properties` object gets the patch's properties (a `null` value is set as `null`); every timeline or agenda entry with that `id` gets `name` as `title` and `date`, `endDate`, `timeFrom`, `timeTo`, `status` and `place` as they are; every reminder of that `itemId` gets `name` as `title`, and is removed when the patch changes `date`, `timeFrom`, `alertMinutes` or `travelMinutes`, or sets `status` to `done` or `wontDo` (the server sends the reminder again once the change reaches it).
3. Deletes (`DELETE /api/items/:id`): every array element that is an object with that `id`, every timeline or agenda entry with that `seriesId` and every reminder of that `itemId` is removed; a kept `GET /api/items/:id` of it answers `404` with an empty body.
4. Creates (`POST /api/databases/:id/items`, made-up item from `[offline-first 03/07]`): `GET /api/items/:newId` answers `200` with the made-up item; the first page (no `cursor`, no `q`, not `inTrash`) of `POST /api/databases/:id/query` of that database includes it when its filter matches the item (nodes other than those listed in the context never match; `date_relative` compares with the device's current day), sorted by the request's first sort key when the item has a value for it, else appended; a timeline or agenda answer whose range holds the item's `date` gets an entry when the database is the `events` or `tasks` database of the kept `GET /api/schema` answer (`kind` `event` or `task`, `title` from `name`, the dates and times, `status` (`notDone` for a task without one), `calendarId` from the `calendar` relation, `version`, not read only). A repeating event created offline shows on its first day until the server has it.
5. Relations: `PUT …/relations/:key/:target` adds `{id, title}` (title from any kept object with that id: its `title`, else `properties.name`, else `properties.title`, else empty) to `relations[key]` of every object with the item's `id` that has `relations`; `DELETE …/relations/:key/:target` removes it; `PUT …/relations/:key` with `targetItemId` replaces the list with that one target or empties it.
6. Occurrences (`POST /api/{events|tasks}/series/:id/occurrences/:date` with a new id): timeline and agenda entries with that `seriesId` and `occurrenceDate` get the new id as `id` and stop being read only.
7. Invitation answers (`POST /api/calendar/invitations/:id/respond` with `{response}`): every object with that `id` and a `properties.status` gets `response` as its status (`accepted`, `tentative`, `declined` or `acknowledged`).
8. Tests (commonTest): one per rule and per branch above, a filter test per node type including a non-matching and an unknown node, the sort placement, an unparsable answer, and through `HttpCalendarRepository`, `HttpTaskRepository`, `HttpCatalogRepository` and `HttpItemRepository` that a write made offline is what the next read returns.

## Scope

### In scope

- Showing queued writes in every answer of the offline set.

### Out of scope

- Expanding the repetitions of an event or a task created offline; computing a moved reminder on the device.
- The overview, sleep and Inbox answers (they show the server's counts until the write reaches it).
- Note pages (`[offline-first 05/07]`).

## Acceptance criteria

- A task completed, renamed or rescheduled offline shows so in the task lists, the item detail, the calendar and the agenda at once and after a restart.
- A task, event or project created offline shows in the lists whose filter it matches and in the calendar range of its date; one deleted offline disappears everywhere and its detail answers not found.
- A relation added or removed offline shows on the item.
- Moving a series occurrence offline shows the moved occurrence; answering an invitation offline shows the new status.
- A reminder of an item deleted, completed or moved offline is not scheduled from the kept feed.
- With nothing queued, answers are exactly what the server sent.
