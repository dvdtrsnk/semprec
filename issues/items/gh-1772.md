## Context

Model tier rationale: It writes a durable message inside three existing transactional sites, including the exactly-once execution transaction and the decision transaction, so a mistake breaks atomicity or double-posts, and it crosses the thread, run and tenant boundaries.

When a person decides an approval request or execution finishes, nothing is written to the conversation the request came from: the agent got only text with the request id and never learns the result, and the thread has no trace of it. Three places end a request: rejection in `decideAndEnqueueApprovalRequest` (`backend/packages/data/src/mcp/approvalDecisionAction.ts`), the generic replay transaction `replayApprovedGenericOperation` (`backend/packages/application/src/genericOperationGateway.ts`), and the MCP outcome writes in `backend/packages/data/src/mcp/approvalRequestExecution.ts`.

This issue adds one system message to the thread of the run that raised the request, in the same transaction as the state change. It builds on the thread and message tables from #1367, the link from runs to threads from #1452, the localisable description snapshot of #1683 (its parameters fill the message), and #1713, which also edits the two execution sites. #1775 (continuing a tick run) and #1791 build on it. The message is context for the agent's next prompt (the prompt reconstruction itself is not changed here) and must not start a new turn.

Decision: a run with no thread (an MCP-initiated run) gets no message. Decision: a conflict and a failed MCP call both post the conflict message, because this issue has no way to tell them apart; splitting out `approval.outcome.failed` follows the `outcomeKind` recorded by #1437.

Controller reconciliation: issues/batches/backend/decisions/batch-23-spec-reconciliation.md, sections 3, governs the exact added paths and existing-owner contract. Other Task/AC obligations remain.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `postApprovalOutcomeMessage(client, request, outcomeKey)` in `backend/packages/data/src/mcp/` (single-writer: it uses the message-writing function owned by the threads module, never raw SQL on `semp_messages`). It resolves the thread through `agent_runs.thread_id`, returns without writing when there is none, and otherwise inserts a system message `{ key: "approval.outcome.<executed|rejected|conflict>", params }` with a reference `{ kind: "approvalRequest", approvalRequestId }`. `params` are the description parameters stored by #1683 (empty object when none), never raw arguments.
2. Call it, on the caller's own transaction client, with `rejected` from `decideAndEnqueueApprovalRequest` when the new status is `rejected` (not on `unchanged`, not on approval); with `executed` from `replayApprovedGenericOperation` after `markApprovalRequestExecutionSucceeded`; with `conflict` after `terminalizeApprovalRequestAsConflict` in both branches; and with `executed` / `conflict` from the MCP outcome path after a recorded outcome (an outcome discarded because the row was already settled posts nothing; a stale-claim settlement posts `conflict`).
3. The write also advances the thread's `last_activity_at` through the threads module function, so list previews show the newest activity. It does not create a Semp message turn, a run or a job.
4. The message is idempotent per request and outcome: a redelivered execution job posts at most one.

### Out of scope

- Client rendering of the keys.

## Acceptance criteria

- When a request from a chat run is rejected, the thread gets one system message `approval.outcome.rejected` with an `approvalRequest` reference, written in the same transaction as the decision, and the thread's `last_activity_at` is updated.
- When it is approved and executes, the thread gets `approval.outcome.executed`; when it ends in conflict it gets `approval.outcome.conflict`.
- A rollback of the decision or the execution write leaves no message.
- A request from a run without a thread writes no message and does not fail.
- Re-delivering the execution job produces no second message.
- No new Semp turn, agent run or job is created by posting the message.
