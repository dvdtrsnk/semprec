**Blocked by:** #269

## Context

Issue #101 introduced the Inbox capture path (`backend/packages/data/src/inbox/inboxStore.ts`) and the active-type listing behind the future `GET /api/inbox-types` (`backend/packages/data/src/inbox/inboxTypesStore.ts`). A post-merge review of #101's pull request raised two findings that were never addressed; both are still on `develop`.

**1. Unvalidated capture date.** `createInboxItemWithClient` guards `date` and `time` with falsy checks only (`if (!input.date) throw new ValidationError(...)`). A malformed but truthy string such as `"not-a-date"` passes. It is then handed to the Journal-day resolution, where `DateTime.fromISO("not-a-date")` produces an invalid `DateTime`, `.toJSDate()` yields `new Date(NaN)`, and `getOrCreateJournalItem` writes a Journal day item whose `period` stringifies to `"null"` — exactly the silent-corruption mode that `timezone.ts`'s `assertValidTimezone` comment warns about. The Inbox item itself is persisted with the bad `date` value too.

**2. Silently truncated type list.** `listActiveInboxTypes` hard-codes `limit: 200` and returns no cursor. With more than 200 active types the caller receives a truncated list with no way to detect the truncation; the underlying `listItems` already caps at 200, so callers cannot opt into more either.

## Task

**`inboxStore.ts`** — after the existing falsy checks in `createInboxItemWithClient`, validate the format of `date` with Luxon, mirroring how `assertValidTimezone` guards the timezone. `time` is deliberately left alone (see Out of scope):

Parse with `DateTime.fromISO(input.date)` and throw `ValidationError("Inbox items require a valid ISO date for 'date'", { field: "date" })` when the result is not `isValid`. This closes the flagged corruption path (an unparseable string reaching Journal-day resolution); tightening it further to reject ISO forms Luxon accepts but that are not calendar dates (`"2026"`, `"2026-W35"`) is not part of this issue. The value must still be passed through verbatim on success — the store must never substitute the server's current date.

**`inboxTypesStore.ts`** — make `listActiveInboxTypes` return every active type instead of a silent first page: page through `listItems` with its cursor until `nextCursor` is null, accumulating the results, and keep returning the same `InboxTypeSummary[]` shape (`id`, `emoji`, `label`) so no caller changes. Keep the existing `buildFilterSql` status filter.

Add tests in `backend/packages/data/src/__tests__/inboxPipeline.test.ts`:

- creating an Inbox item with `date: "not-a-date"` rejects with `ValidationError` on field `date`, and no Journal day item is created;
- `listActiveInboxTypes` returns all active types when more than 200 exist. Note that the listing filters on `properties ->> 'status' = 'active'` while `createInboxTypeWithClient` only writes `status` when it is supplied, so the test must pass `status: "active"` explicitly on every type it creates; create them in as few transactions as the store allows, since the suite runs against a real PostgreSQL instance.

## Scope

### In scope

- ISO validation of `date` in `createInboxItemWithClient`.
- Full pagination in `listActiveInboxTypes`.
- The tests above.

### Out of scope

- The timezone validation, which is already correct, and the `time` field: unlike `date` it never reaches Journal-day resolution, so it was not part of the finding this issue closes.
- Changing `deleteInboxTypeWithClient` or `createInboxTypeWithClient` — the delete path is #271. The new test may of course call `createInboxTypeWithClient` to set up its data; what is out of scope is modifying it.
- Any HTTP route: no HTTP layer exists in this repository yet.

## Acceptance criteria

- An Inbox capture with a truthy but unparseable `date` is rejected with `ValidationError` on field `date`, before any write is attempted.
- A valid capture still stores exactly the supplied `date` and `time` and resolves its Journal day as before.
- With more than 200 active Inbox item types, `listActiveInboxTypes` returns all of them.
