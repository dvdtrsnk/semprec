## Context

Model tier rationale: One reservation step added to one case of the approval projection, copied from the case beside it, with tests on real concurrent transactions. It adds no table or route and does not change what is hashed, but it changes when an approved agent's relation delete is refused as busy, and it sits on the destructive-approval path.

The accepted ADR `docs/adr/2026-11-15-a-user-edge-write-on-a-link-rules-via-relation-locks-the-rules-target-item-before-ending-value-links.md` (source sp-5419cac1) lists three paths of the tree that take value link rows against the order item row, then link row, and end with `40P01`. This source repairs the third: the replay of an approved agent operation. The ADR names `relation.delete`, `relation.put` and `relation.set`; reproduction in a scratch copy of the tree at the integration tip (production calls, pools of the runtime role `semprec_data`) shows that only `relation.delete` deadlocks:

- `replayApprovedGenericOperation` (`packages/application/src/genericOperationGateway.ts`) opens one transaction, runs the destructive projection check (`computeDestructiveResourceProjection` in `chokePoint/destructiveProjection.ts`) and then the write on the same client. The projection of `relation.delete` calls `reserveEdgeLinks`, which share-locks, without waiting, the `on` value links of the edge's two sides. It locks no item row. The write (`deleteRelationWithClient`) then runs the before-link-break hook of the 2026-11-15 ADR, which locks the rule's target item row (the transcript, for `Transcripts.project`) with a blocking wait.
- With the propagation job of the Event's project holding the transcript row and a third transaction holding it first, the propagation started first: the replay holds the `project` link share lock and waits for the transcript row; the propagation gets the row and wants the link (`FOR UPDATE`) and waits for the replay: `40P01` (reproduced: outcomes `committed` for the propagation and `deadlock` for the replay).
- The projections of `relation.put` and `relation.set` lock the caller and the target (and the targets of the old edges, for a set) with `lockItemByIdNowait` before `reserveEdgeLinks`, so they hold the item row before the links and a held row is an `ApprovalResourceBusyError`, not a wait. In the same schedule both end busy (reproduced), so they are not changed.

Decision: the `relation.delete` projection locks the edge's two endpoint item rows without waiting, in the same order as the put/set case (database id, then item id), before it reserves the links; a held row is `ApprovalResourceBusyError` and marks the transaction rollback-only, like every other approval reservation. A row that does not exist (an edge to a purged item can still exist) is skipped. The replay job is retried by the queue when the reservation is busy, and an agent's request-time projection answers busy while an endpoint row is held, as it already does for put and set. The hash of the snapshot does not change: row locks are not part of the projection.

## Scope

### In scope

- Locking the endpoint rows of a `relation.delete` approval check, without waiting, before its value links are reserved.

### Out of scope

- The projections of `relation.put`, `relation.set`, `item.patch`, `link.unlink` and the other kinds: unchanged.
- The before-link-break hook, `deleteRelationWithClient`, the replay gateway and the approval queue.
- The trash of an Event (the other two paths of the 2026-11-15 ADR).
- A change of the snapshot hash or of what a request displays.
- Any new table, route, hook kind or migration.

## Acceptance criteria

- When the replay of an approved `relation.delete` of a link rule's via relation runs against the propagation job that holds the target item's row, then no call ends with a deadlock: the replay is refused as `approval_resource_busy` and the propagation commits.
- When another transaction holds either endpoint row of the edge, then the projection of `relation.delete` is refused as `approval_resource_busy` without waiting and the transaction is marked rollback-only.
- When no endpoint row is held, then the projection, its snapshot hash and the replay's write are as before.
- The projections of `relation.put` and `relation.set` behave as before.
- The ADR of this source exists and the accepted ADRs it names are not edited.
