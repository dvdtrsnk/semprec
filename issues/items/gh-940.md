## Context

Harvest issue #934 collected three findings about failure paths that handle errors more coarsely than their comments claim. Only one of them still describes a real defect on `develop`:

- PR #835, `backend/packages/data/src/testSupport/stalePostgresDirs.ts:51`: the bare `catch` around `stat(dir)` in `sweepStalePostgresDirs` swallows every error, but its comment ("Another process may already have removed this directory") justifies only `ENOENT`. An `EACCES` or `EIO` from `stat` vanishes silently and the directory is skipped as if it were already gone. `sweepStalePostgresDirs` runs at the start of the integration tier's `globalSetup` (`backend/packages/data/src/testSupport/globalSetup.ts:56`).

The other two findings were verified not to reproduce; this issue retires them without a code change (see Out of scope for the evidence).

## Task

1. In `stalePostgresDirs.ts`, make the `catch` around `stat(dir)` continue only when the caught error is an object whose `code` is `"ENOENT"`, narrowed with runtime checks (for example `err instanceof Error && "code" in err && err.code === "ENOENT"`) rather than an `as` cast, and rethrow every other error unchanged. Keep the comment's `ENOENT` justification next to the narrowed check.
2. In `testSupport/__tests__/stalePostgresDirs.unit.test.ts`, add a test in which the mocked `stat` rejects with an error whose `code` is `"EACCES"` and assert that `sweepStalePostgresDirs` rejects with that same error. The existing test "skips a directory removed by another process between readdir and stat" already covers `ENOENT` and stays as it is.

## Touches

- backend/packages/data/src/testSupport/stalePostgresDirs.ts (the `catch` around `stat` only)
- backend/packages/data/src/testSupport/__tests__/stalePostgresDirs.unit.test.ts

## Scope

### In scope

Narrowing the `stat` catch in `sweepStalePostgresDirs` to `ENOENT`, and its `EACCES` test.

### Out of scope

- The `rm` catch in `sweepStalePostgresDirs`, the `readFile` catch in `hasLiveOwner` and the `ErrnoException` cast in `defaultIsPidAlive`, all in `stalePostgresDirs.ts`: not flagged, they stay as they are.
- PR #825, `backend/services/semprec-api/src/blobsHandler.ts:178` (log `ECONNRESET` at debug level like `ERR_STREAM_PREMATURE_CLOSE`): no change. A client that disconnects mid-download, including with a TCP reset, reaches the `pipeline` callback as `ERR_STREAM_PREMATURE_CLOSE`, because `ServerResponse` does not re-emit its socket's `ECONNRESET` as an `error` event (verified on Node 22, the CI version, with both `socket.destroy()` and `socket.resetAndDestroy()` on the client, before and after the response started streaming). The only stream that could hand `pipeline` an `ECONNRESET` is the storage read stream, where it would be a genuine server-side failure that must keep its error-level log.
- PR #872, `backend/packages/data/src/mail/mailLiveSyncRoot.ts:153` (`onLifecycleError` called before `ROLLBACK TO SAVEPOINT discover_account`): no change. A throwing callback propagates out of the `withTransaction` callback, and `withTransaction` (`backend/packages/data/src/db/pool.ts:109-117`) then issues a full `ROLLBACK` and releases the client, so no transaction is left in an aborted state. Moving the savepoint rollback into a `finally` would change nothing observable, and would let a failing rollback replace the callback's error. The only production callback (`backend/services/semprec-api/src/serve.ts:127`) is a `logger.error` call.
- Every other finding of harvest issue #934 and anything adjacent to the lines named in the Task, even in the same file.

## Acceptance criteria

- When `stat` fails with `ENOENT` for a `semprec-pg-*` directory, `sweepStalePostgresDirs` skips it and resolves; the existing `ENOENT` test still passes unchanged.
- When `stat` fails with `EACCES`, `sweepStalePostgresDirs` rejects with that same error; a new test in `stalePostgresDirs.unit.test.ts` covers it.
- The `catch` around `stat` in `stalePostgresDirs.ts` narrows the error without an `as` cast.
