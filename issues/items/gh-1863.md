## Context

Model tier rationale: It extends the closed realtime protocol across publisher, listener, server and client and attaches publication to many run and approval transitions that must fire only after commit and only to the right tenant and user, so a missed or misdelivered frame is a cross-process isolation defect.

A running agent run shows new steps and a changing status label without a reload, and the "latest runs" list and the project's attention dot change live ("Working..." becomes resolved, "executing..." becomes "executed after approval"). Today only one run can be watched (`agent:watch` with `agent:event` / `agent:delta`, `backend/packages/realtime/src/agentRunWatch.ts`), and nothing tells a client that a run was created, finished, or changed its approval state. `agent_runs` rows are not items, so no `invalidate` frame exists for them.

The realtime layer is a closed catalog. `OutboundFrame` in `backend/packages/realtime/src/protocolV1.ts` lists every frame a client can receive, `RealtimeMessage` and `parseRealtimeMessage` in `backend/packages/realtime/src/pgNotifyPublisher.ts` list every payload inside the `{ tenantId, message }` NOTIFY envelope, and `InvalidationEvent` in `backend/packages/data/src/realtimeHook.ts` is what the data layer hands to `notifyInvalidation` (turned into a NOTIFY by `wireRealtimeHooks`). Only `item` and `schema` invalidations exist today.

Rules for every frame added by this program (`docs/adr/2026-10-16-tenant-scoped-realtime-fan-out.md`): the tenant in the envelope is computed by Postgres from the publisher's scope; delivery is `sendToTenant(tenantId, frame, userId?)`; the payload is thin (identifiers, no user text); nothing is replayed, a reconnecting client reloads over REST; a producer publishes only after commit (`runAfterCommit`). This scope is added to the chain of issues that already added the `sempThread`, `approvalRequest`, `inboxCards`, `mailThread`, relation and doc scopes (#1395, #1789, #1811, #1816, #1621, #1625); follow exactly the shape and wiring those introduced (same `invalidation` message type with a `scope` discriminator, same parser style, same client handling).

This issue adds the scope `agentRuns` with payload `{ projectItemId: string | null, agentRunId: string }` (`projectItemId` is null for a run without a project). It is delivered only to the sockets of the run's `actor_user_id` (`AgentRunRow.actorUserId`, `backend/packages/data/src/agentRuns/agentRunsStore.ts`) inside the tenant. It is published when a run is created, when it finishes (done or error, including the startup-repair close), and whenever the run's derived display status or approval state can change (#1820 derives the display status from the run status plus a pending approval). Those approval transitions are exactly the places where #1789 already publishes the approval request invalidation: creating a pending request (`preflightDestructiveApproval` in `backend/packages/application/src/genericOperationGateway.ts` and `createApprovalGatedMcpInvokeTool` in `backend/packages/agent-runtime/src/mcpInvokeTool.ts`), `decideAndEnqueueApprovalRequest` (`backend/packages/data/src/mcp/approvalDecisionAction.ts`), `recordApprovalRequestOutcome`, `markApprovalRequestExecutionSucceeded` and `terminalizeApprovalRequestAsConflict` (`backend/packages/data/src/mcp/approvalRequestsStore.ts`) and `replayApprovedGenericOperation`. Publish `agentRuns` together with the approval request invalidation, through one shared helper, so the two cannot drift.

The summary of the answer in the Semp chat is refreshed by the `sempThread` scope (#1395), not by this one. Later issues in the chain add the project agent scope (#1866) and the rest.

## Task

Load `state-writes`, `canonical-keys`, `io-hardening` and `testing`.

1. Add the `agentRuns` variant to `InvalidationEvent` (`realtimeHook.ts`), to `RealtimeMessage` with a `parseRealtimeMessage` case (validate `agentRunId` and a non-null `projectItemId` with `isUuid`), to `OutboundFrame` (`{ type: "invalidate", scope: "agentRuns", projectItemId, agentRunId }`), and to the `invalidation` case in `syncServer.ts` (map the message to the frame and call `sendToTenant(tenantId, frame, parsed.userId)`).
2. Add the matching case to `parseServerFrame` in `backend/packages/realtime-client/src/serverFrame.ts` and export the frame type from the client barrel if the other scopes are.
3. Create `backend/packages/data/src/agentRuns/agentRunInvalidation.ts` exporting `publishAgentRunInvalidation(client, agentRunId)`: reads the run's `project_item_id` and `actor_user_id` and calls `notifyInvalidation({ scope: "agentRuns", projectItemId, agentRunId, userId })` through `runAfterCommit(client, ...)`; for a bare pool (autocommit statement) it publishes right after the statement. An unknown run id publishes nothing.
4. Call it from `createAgentRun` and `finishAgentRun` (so `finishAgentRunWithErrorNotification` and the startup repair are covered) in `agentRunsStore.ts`, and next to every approval request invalidation listed in Context, using the same helper call site as #1789.
5. Tests: frame parse round trip on server and client; a message with a non-uuid id is dropped; a run's frames reach only the sockets of its actor in its tenant and never another tenant's or another user's; no frame is sent when the transaction rolls back; web decision of a request produces an `agentRuns` frame for the run and its project.

## Scope

### In scope

- The `agentRuns` scope end to end and its publication on run lifecycle and approval transitions.

### Out of scope

- The project agent setup scope: #1866.
- Semp status, preference, badge, account and overview scopes: #1868, #1918, #1946, #1951.
- Refreshing the chat summary: #1395; the approval request scope itself: #1789.
- Streaming steps of a run (`agent:event`, `agent:delta`); replay of missed frames.

## Acceptance criteria

- When a request is decided on the web, then the sockets (including an iOS device) of that user receive an `invalidate` frame with scope `agentRuns` for the run and its project.
- When a run is created or finishes with done or error, then its actor's sockets receive the frame; the frame carries only the two ids.
- When the transaction that caused the change rolls back, then no frame is sent.
- When another user or another tenant is connected, then it never receives the frame.
- A frame with a malformed id is dropped by the listener and by the client parser.
