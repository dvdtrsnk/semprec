## Context

Model tier rationale: One shared repository and two shared ViewModels gain a password sign-in flow and a typed refusal decoding, with their CoreKit bridges, the Apple Account screens, copy and tests; no new module or navigation.

Production users of Settings → Internet accounts see "Kalendáře: Znovu přihlásit" and "Pošta: Chyba synchronizace" on iCloud and generic IMAP accounts whose stored credential is missing, with no way to fix it: only Google and Microsoft accounts offer "Sign in again". Adding an account fails with one message for every refusal ("Server přihlášení odmítl, nebo je tenhle účet už připojený.", `internetAccounts.add.error.refused`), because `ApiClient` maps 400, 409 and 422 to `FailureKind.REJECTED` and the error body is dropped.

The backend adds, in parallel, `PUT /api/mail/mailboxes/:id/password` with JSON `{ "password": string, "username"?: string }` (username omitted keeps the stored one). 200 answers `{ item }` like the password connect route; 400 carries the refusal codes of the connect route; 404 unknown; 409 `mailbox_not_password` for an OAuth mailbox; 429 `rate_limited`. Afterwards the server clears the reauthorization state and syncs, and a mailbox whose credential is missing reports `syncStatus` `needsReauthorization`. Re-adding an address whose old mailbox is in the trash succeeds; a live duplicate answers 409 `provider_account_already_connected`.

Errors are serialized by `toErrorResponseBody` as `{ "error": { "code": … } }`. The refusal codes are `mail_auth_failed`, `mail_app_password_required`, `mail_server_unreachable`, `mail_tls_failed` (mail verification), `caldav_auth_failed`, `caldav_server_unreachable`, `caldav_server_invalid` (CalDAV verification), `provider_account_already_connected` and `rate_limited`.

Android has no Internet accounts screen (`AccountFeature` is Apple-only in the copy policy), so there is no Android part.

## Task

Load `kmp-shared`, `shared-viewmodel`, `apple-swiftui`, `canonical-keys`, `testing` and `mobile-verify`.

1. Data: `ApiResponse.Failure` keeps the error body of the answer (`body`, `null` by default), so other callers keep their `FailureKind`. `HttpMailboxRepository.connect` and a new `updatePassword(mailboxId, password, username)` (`PUT …/:id/password`, `username` sent only when given) decode the error `code` at the boundary (`{ "error": { "code" } }`, a top-level `code` accepted too) into a domain `MailConnectOutcome`: `Connected` or `Refused(MailConnectRefusal)` with `WRONG_CREDENTIALS`, `APP_PASSWORD_REQUIRED`, `SERVER_UNREACHABLE`, `TLS_FAILED`, `CALDAV_REFUSED` (`caldav_auth_failed`), `CALDAV_UNREACHABLE` (`caldav_server_unreachable`, `caldav_server_invalid`), `ALREADY_CONNECTED`, `RATE_LIMITED` (also a 429 without a code). Any other failure stays a `RepositoryResult.Failure`.
2. Presentation: `InternetConnectFailure` gains `WRONG_CREDENTIALS`, `APP_PASSWORD_REQUIRED`, `SERVER_UNREACHABLE`, `TLS_FAILED`, `CALDAV_REFUSED`, `CALDAV_UNREACHABLE`, `ALREADY_CONNECTED`, `RATE_LIMITED`; `REFUSED` remains the generic refusal. A connect refused as already connected names the listed account with that address (`InternetAccountsState.existingAccountId`), and `OpenExisting` opens it.
3. Sign in again is an action for every account that needs it. `InternetAccountDetail.canSignInAgain` and the new `InternetAccountItem.canSignInAgain` are true when mail or calendars need reauthorization and the provider is a browser one (`gmail`, `outlook`) or a password one (`icloud`, `generic`). `SignIn.Again` on the account and `SignInAgain(accountId)` on the list start the existing browser reauthorization for a browser account and open a password sign-in (`InternetPasswordSignIn`: account, address, iCloud or not, submitting, failure) for a password account. `PasswordSignIn.Submit(password, username)` calls `updatePassword` (an empty password is `INVALID_INPUT`, a blank username keeps the stored one), shows progress, maps refusals as in 2, and on success closes the sign-in and reads the account (the list) again; `PasswordSignIn.Cancel` closes it.
4. Apple: CoreKit values and bridge mappings for the new cases, state and actions, with `InternetAccountMappingTests` cases; the Account feature shows a "Sign in again" button in the account's reauthorization section for every account that can sign in again and in each list row that needs it, and a password sign-in sheet (password, optional user name with the address as placeholder, the iCloud app-specific password hint, progress, the failure text); the add form offers to open the existing account when it is already connected. Copy en and cs in the catalog and the copy policy; identifiers in `AccountIdentifiers`.
5. Tests: commonTest for the repository decoding (each code, the 429, the `username` body), the ViewModels (OAuth and password sign-in again from the account and the list, success reads again, every refusal code maps to its failure, already connected names the existing account); Swift feature tests over `ScriptedScreenModel` for the forwarded intents.

## Scope

### In scope

- Password and browser sign-in again from the account and the list; distinct refusal messages for connect and password sign-in again.

### Out of scope

- The backend route and its status derivation (built in parallel).
- Android and web.

## Acceptance criteria

- An iCloud or generic account whose mail or calendars need reauthorization offers "Sign in again"; submitting a password calls `PUT /api/mail/mailboxes/:id/password` and, on success, the account is read again.
- A Google or Microsoft account that needs reauthorization starts the browser reauthorization from the account and from the list.
- Each server refusal code shows its own message in en and cs; already connected offers to open the existing account.
- Calls that map 400, 409 or 422 elsewhere still get `FailureKind.REJECTED`.
