**Blocked by:** #974

## Context

Two mail identities are resolved by lookups across all of `mail_message_meta`.

**Provider message ids.**
- `mail_message_meta_provider_msg_uq` is a partial unique index on `(provider_message_id) WHERE provider_message_id IS NOT NULL` (`backend/packages/data/src/db/migrations/0006_mail_sync.sql:71-72`).
- `ingestEmailMessage` runs its writes under a savepoint. When two sync passes race distinct Message-IDs onto one provider message, it catches the violation, rolls back to the savepoint, and converges onto the winner found by `getMailMessageMetaByProviderMessageId` (`backend/packages/data/src/mail/ingest.ts:104-111,197-209`).
- It recognizes the violation only by name: `isProviderMessageIdConflict` checks `code === "23505"` and `constraint === "mail_message_meta_provider_msg_uq"` (`backend/packages/data/src/mail/mailMessageMetaStore.ts:190-199`).
- The Gmail and Graph reconcilers look messages up by provider id (`backend/packages/data/src/mail/gmailReconcile.ts:174,196`, `backend/packages/data/src/mail/graphReconcile.ts:127`).
- No `ON CONFLICT` uses this index as an arbiter. `upsertMailMessageMeta` arbitrates on `(mailbox_item_id, message_id)` (`mailMessageMetaStore.ts:105-137`; index `mail_message_meta_mailbox_message_uq`, `0053_mail_message_meta_per_mailbox.sql:77-78`).

**Threads.**
- `resolveThreadId` (`backend/packages/data/src/mail/threading.ts:27-67`) joins a thread found through an ancestor's Message-ID (`:35-39`) or a descendant referencing this message (`:44-48`).
- It merges multiple threads with `reassignThread`, which rewrites `mail_message_meta.thread_id` and deletes the emptied `mail_threads` row (`mailMessageMetaStore.ts:226-229`).
- Message-IDs are global, so without tenant confinement one tenant's reply would join, or merge, another tenant's conversation.

Tenancy state this issue builds on:
- `mail_message_meta` and `mail_threads` are tenant tables: `tenant_id DEFAULT app_tenant_default()`, plus the RESTRICTIVE `tenant_isolation` policy `tenant_id = (SELECT app_tenant_default())`.
- `app_tenant_default()` is `COALESCE(app_current_tenant(), app_sole_tenant())` over the GUC `app.tenant_id`.
- Under a runtime role, every lookup, the `UPDATE` and the `DELETE` above are therefore already confined to the caller's tenant. This needs no code change; this issue proves it.
- #974 added a tenant-leading partial unique index on `mail_message_meta (tenant_id, provider_message_id) WHERE provider_message_id IS NOT NULL` named `mail_message_meta_tenant_provider_msg_uq`, beside the legacy one, which #1065 drops.

While both indexes exist, a same-tenant conflict reports whichever index Postgres checks first. After #1065 only the tenant-leading one remains. The name check must accept both, or the savepoint recovery stops working when the legacy index goes.

## Task

Load `error-handling` (the conflict recognition decides between converging and failing) and `state-writes` (the savepoint-guarded ingest).

1. **Conflict recognition.** `isProviderMessageIdConflict` (`mailMessageMetaStore.ts:190-199`) returns true for a `23505` whose `constraint` is `mail_message_meta_provider_msg_uq` or `mail_message_meta_tenant_provider_msg_uq`. Keep both names in one module-level constant list.
   - Update its docstring: both arbiters during the transition, and the legacy one leaves with #1065.
   - `ingest.ts` is unchanged.
2. **No hand-written tenant predicates.** `threading.ts`, the provider-id lookups and the reconcilers stay as they are. Do not add `tenant_id` predicates; RLS confines them.
3. **Tests.** New `backend/packages/data/src/__tests__/mailIdentityPerTenant.test.ts`. Two-tenant cases run in one transaction on `getTestPool()` (the owner), rolled back at the end:
   - `DROP INDEX IF EXISTS tenants_single_tenant_guard`;
   - where the case says so, `DROP INDEX mail_message_meta_provider_msg_uq`;
   - insert a second `tenants` row;
   - `SET LOCAL ROLE semprec_data`;
   - switch tenants with `SELECT set_config('app.tenant_id', $1, true)`.

   `mail_message_meta` has no foreign key to `items`, so item and mailbox ids may be random UUIDs inserted through `upsertMailMessageMeta`. Integration files run one at a time (`fileParallelism: false`, `backend/vitest.integration.config.ts:20`).

## Scope

### In scope
- Recognizing the provider-id conflict from either index.
- Two-tenant tests proving that threading, thread merges and provider-id lookups stay inside the tenant.

### Out of scope
- Dropping `mail_message_meta_provider_msg_uq` (#1065).
- Composite foreign keys such as `(tenant_id, thread_id)` → `mail_threads` (#1066).
- The person email index (#1010).
- Running mail sweeps per tenant (#989).
- Removing message content from log lines (#1074).
- Making provider ids unique per mailbox rather than per tenant.

## Acceptance criteria

All integration tests (`*.test.ts`).
- **Same-tenant conflict, today's schema.** With one tenant and both indexes present, the existing concurrent provider-id case (`backend/packages/data/src/__tests__/mailSync.test.ts:681`) still converges two distinct Message-IDs onto one row without a raw Postgres error.
- **Same-tenant conflict, legacy index dropped.** With `mail_message_meta_provider_msg_uq` dropped (rolled-back transaction):
  - a second row with an existing `provider_message_id` in the same tenant raises an error that `isProviderMessageIdConflict` recognizes;
  - an error from another unique index, such as `mail_message_meta_mailbox_message_uq`, is not recognized.
- **Provider ids across tenants.** With the legacy index dropped and two tenants under `semprec_data`, the same `provider_message_id` stored in tenant A and in tenant B both succeed, and `getMailMessageMetaByProviderMessageId` returns each tenant's own row.
- **Ancestor lookup stays in the tenant.** With two tenants under `semprec_data`, tenant A holds message `<m1@x>` in thread T_A. `resolveThreadId` in B's scope for a message with `In-Reply-To: <m1@x>`:
  - returns a new thread, not T_A;
  - leaves A's row's `thread_id` as T_A in A's scope.
- **Descendant lookup stays in the tenant.** Tenant A holds a message whose `References` contains `<m2@x>`. `resolveThreadId` for `<m2@x>` in B's scope merges nothing: A's `mail_threads` row still exists and A's messages keep their `thread_id`.
- **Merges inside one tenant.** Two of B's own threads bridged by one B message still merge into one, and the emptied thread row is deleted.
