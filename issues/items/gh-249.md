**Blocked by:** #178, #91

## Context

First of three parts of the repository-workflow and CI-gate slice that opens the `deployment` batch (#187). #250 adds the unit, ephemeral-PostgreSQL integration and dependency-check CI tiers under the names defined here; #188 adds the e2e and pi-agent contract tiers. #189 builds on `main` for tag eligibility.

**Branch model — revised 2026-09-24.** This issue originally asked to retire `develop` and move to trunk-based development on `main`. That contradicts the accepted `docs/adr/2026-09-10-develop-main-branching-with-release-promotion.md`, which the repository, Relay and the review bot (`PROMOTION_SOURCE`/`PROMOTION_TARGET` in `.github/workflows/code-review.yml`) are built on. The repository owner decided to keep that ADR: `develop` stays the integration branch every issue targets, and `main` holds released versions only and advances exclusively through a `develop → main` promotion pull request. This issue therefore no longer reconciles or retires anything; it completes the gate for the two-branch model.

What already exists and must be kept, not rebuilt: both `develop` and `main` are protected (pull request required, `strict` required checks `ci`, `review` and `code-review`, enforced for administrators, no force pushes or deletions); `.github/workflows/release.yml` runs on a push to `main`.

## Task

- Extend `.github/workflows/ci.yml` triggers so the `ci` job runs on every pull-request update **and** on every push to `develop` and to `main` (a merge lands as a push). Key the concurrency group so a push run and a pull-request run never cancel each other, and runs on different branches never share a group. Update the file's comment that names the required context on `develop` so it describes both branches.
- Enforce that `main` is reached only by a promotion pull request: a new job (stable name `promotion-source`) that, on a pull request targeting `main`, fails unless the head is `develop` of this repository; on any other event it succeeds without doing anything. Add `promotion-source` to the required checks of `main`'s branch protection only.
- Define the stable required-check names contract in the repository (a short section in `docs/operations/`, linked from `README.md`): the currently required contexts per branch (`ci`, `review`, `code-review`; plus `promotion-source` on `main`), the tier names that #250 and #188 will add (`unit`, `integration`, `dependency-check`, `e2e`, `pi-agent-contract`), and the rule that renaming a job is a contract change that must update branch protection and this document together.
- Record that the two-branch model was re-confirmed over #187's trunk-based proposal in the required-check contract document. The accepted ADR itself is not edited — its body is immutable per `docs/adr/README.md`, and nothing about its decision changes.

## Scope

### In scope

- `ci.yml` triggers, concurrency and the `promotion-source` job; the `main` branch-protection change for `promotion-source`; the required-check names document, including the re-confirmation note.

### Out of scope

- The unit, integration and dependency-check tier jobs — #250.
- The e2e and pi-agent contract tier jobs — #188.
- Retiring `develop`, changing the default branch, or any trunk-based model — rejected (see Context).
- Promoting the current `develop` into `main` (cutting a release) — a release operation, not this issue.
- Auto-deploy on tag push — never (see #187).

## Acceptance criteria

- A direct push to `develop` or `main` is rejected; a pull request with a failing required check cannot be merged into either. (Already true — verify, do not rebuild.)
- A pull request into `main` whose head is not `develop` fails `promotion-source` and cannot be merged; a `develop → main` pull request passes it.
- The `ci` job runs on every pull-request update and on every push to `develop` and `main`, and a push run is not cancelled by a pull-request run or vice versa.
- The required-check names contract is documented and matches the live branch protection of both branches.
- The repository contains no planning content, and nothing from the planning repository is deployable.
