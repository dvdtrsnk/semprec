## Context

`queryItemsCore` in `backend/packages/data/src/views/viewQuery.ts` (lines 51-69) is the one engine behind `POST /api/views/:id/query`, `POST /api/databases/:id/query` and a stored view's own page. When the view or request has any sort (or `groupBy`, which `buildSortSpecs` turns into a leading sort), line 64 drops the incoming cursor — `cursor: sortSpecs.length === 0 ? options.cursor : undefined` — because `itemsStore.listItems` (`backend/packages/data/src/chokePoint/itemsStore.ts`, lines 260-293) only knows `id > $cursor` keyset paging, which is only correct under the default `id ASC` order (see the `ListItemsOptions` comment, lines 248-257). But `listItems` still returns `nextCursor` (line 291) whenever there was a further row, so a client paging a sorted view sends that cursor back and receives page 1 again, forever. `parseCursorInput` (lines 163-172) already knows the two regimes (`usedForKeysetPaging`), which is why the request layer does not reject the cursor either.

Sibling issues C8 (rollup values read from `computed`) and C19 (curated views) of this batch build on the compiler and query module changed here.

## Task

1. `backend/packages/data/src/views/sortCompiler.ts`: alongside `compileSort`, a new exported `compileSortKeyset(sorts: SortSpec[], propertyTypes: Map<string, PropertyType>, cursor: { values: unknown[]; id: string }, params: unknown[]): string` that emits the "rows after this tuple" predicate for the `ORDER BY` that `compileSort` produces (each key `NULLS LAST`, then `id ASC`): the standard OR-of-prefix expansion — for sort keys `k1..kn` and the cursor values `v1..vn`: `(k1 AFTER v1) OR (k1 SAME v1 AND k2 AFTER v2) OR ... OR (k1 SAME v1 AND ... AND kn SAME vn AND id > $id)`. With every key `NULLS LAST`: for a non-null `v`, `AFTER` is `(k > $v OR k IS NULL)` for `asc` and `(k < $v OR k IS NULL)` for `desc`, and `SAME` is `k = $v`; for a null `v`, `AFTER` is `FALSE` (nulls are last and equal among themselves) and `SAME` is `k IS NULL`. Each key expression is the same `(properties ->> $key)::cast` that `compileSort` builds and the bound `$v` gets the same cast — extract the per-key expression builder into a private helper both functions use so they never drift. Every value is a bound parameter; nothing from the cursor is interpolated.
2. `itemsStore.listItems`: `ListItemsOptions` gains `keyset?: { buildAfterSql: (params: unknown[]) => string; encodeCursor: (last: ItemRow) => string }`. When set, `listItems` uses `keyset.buildAfterSql(params)` in place of the `id > $n` predicate (lines 276-279) and `keyset.encodeCursor(lastRow)` for `nextCursor` (line 291); `options.cursor` is ignored in that mode. Update the `ListItemsOptions` comment (lines 248-257): "combining `buildOrderBySql` with `cursor` is unsupported" becomes "a custom order pages through `keyset`".
3. `viewQuery.ts`: sorted queries page with an opaque cursor — `base64url(JSON.stringify({ v: [...sort values of the last row, read from `item.properties[key]`], id }))` — decoded in `queryItemsCore` with a `ValidationError('Invalid cursor', { field: 'cursor' })` on a malformed token, a `v` whose length differs from `sortSpecs.length`, or a non-UUID `id`. `queryItemsCore` passes `keyset` to `listItems` when `sortSpecs.length > 0`, and the plain `cursor` otherwise. `parseCursorInput`'s UUID check stays for the unsorted case; for the sorted case the decode is the validation. `nextCursor` is `null` when the page is the last one (this already holds in `listItems`; keep it).
4. Tests, new `backend/packages/data/src/__tests__/viewQueryPagination.test.ts` (integration): 7 items with a `number` property and a `date` property, some null; for `asc` and `desc`, and for a two-key sort (`groupBy` on a `select` + `date desc`), page with `limit: 3` following `nextCursor` until `null` — the concatenation equals the single unpaged query's order with no duplicates and no gaps, nulls last in both directions; a tampered cursor is a 400 `ValidationError`; a `limit` of 500 is capped to 200 and `nextCursor` is non-null when 201+ rows match; the unsorted case still uses the item-id cursor (existing behaviour, assert the cursor is the last id).

## Scope

### In scope
- Composite keyset paging for sorted/grouped filtered views and database queries, the opaque cursor, and the tests.

### Out of scope
- Reading rollup values from `computed` in the sort/filter compilers (sibling issue C8).
- Curated-view paging (sibling issue C19).
- `countItems`, the mailbox/library view types' own queries, and the web client's paging UI.

## Acceptance criteria

- When a filtered view or database query has a sort, following `nextCursor` yields every matching row exactly once across pages, in the sorted order, and the last page has `nextCursor: null`.
- When the sort key is null for some rows, those rows appear last (for both directions) and are not skipped or repeated across pages.
- When a client sends a malformed or foreign cursor to a sorted query, the response is 400 `validation_failed` naming `cursor`.
- When no sort is given, the cursor is still the last item id and unchanged clients keep working.
