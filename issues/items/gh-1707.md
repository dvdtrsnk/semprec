**Model tier:** medium

## Context

Model tier rationale: One known mechanism (a seeded system module plus one write hook) that follows the existing library-module seed and hook patterns and is verified by seed and hook tests, but it must be idempotent for existing tenants including suspended ones.

Semprec has no Recipes collection today. The ten hardcoded databases are listed in `backend/packages/data/src/seed/tenDatabaseKeys.ts`; the library module (`seed/seedLibraryModule.ts`, `library/libraryModuleManifest.ts`) is the pattern for a module that ships its own system databases, each owned by a system project item (`systemActive: true`, `agents` text) and then locked with `schema_locked`. `seedSystem.ts` skips a tenant that is already seeded, so a new database never reaches existing tenants by that path alone. An image property today stores `{ blobId }` over the shared `blobs` table (the Books `cover` property); nothing checks that the blob exists in the tenant or is an image.

This issue adds Recipes as a system module: a `recipes` database with six properties, a gallery default view type, a system project that owns it, Czech and English labels, delivery to new and existing tenants, and a write check on the photo property. It is the first issue that delivers a new system module to tenants that already exist, through a per-tenant cutover step in `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`, one `forEachMaintainedTenant` pass that deploy already runs through `runSeedCli` and `provisionTenant`; the existing `runTranscriptsCatalogCutoverMigration` is the model). That makes the pattern for any later system module explicit: a manifest, a seed called from `seedSystem.ts` for new tenants, and one cutover step for existing ones. It builds on #1407 (icon, color, order and visibility declared per system database), #1409 (the built-in gallery view type), #1584 (colors on select options) and #1622 (numeric filter presets on number properties). Later issues build on it: #1974 proposes recipes from the Inbox, and #1776 reuses the same seeding mechanism for the sleep module.

Decisions:
- Ingredients and method live only in the item's page content (Markdown blocks), not as structured properties. A shopping list is outside this version.
- Recipes are not linked to Areas: no relation from Recipes to Areas is added.
- The `recipes` database is a system database and cannot be deleted: archiving it is refused like for every system database, so it never appears in Trash. The user can only hide it from the overview, which #2002 adds on top of this one.

Shared-file ordering: this issue also waits for #1697, #1700 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys`, `state-writes`, `db-migrations` and `testing`.

1. Add `backend/packages/data/src/seed/recipesModuleKeys.ts` exporting `RECIPES_MODULE_ID = "recipes"`, and `backend/packages/data/src/recipes/recipesModuleManifest.ts` (`id: "recipes"`, one database `{ key: "recipes", name, defaultViewType: "gallery", icon, color, overviewOrder: 9, switcherOrder }` using the metadata fields delivered by #1407). Register it in `manifest/fullModuleRegistry.ts` (path list and `ALL_MODULE_IDS`) and export it from the `backend/packages/data/src/index.ts` barrel.
2. Add `seedRecipesModuleInTransaction` in `backend/packages/data/src/seed/seedRecipesModule.ts`, modeled on `seedLibraryModuleInTransaction`: create the system project item "Recipes" (`systemActive: true`, `agents` text describing purpose, allowed and not-allowed writes) in the Projects database, create the `recipes` database with it as `ownerProjectItemId`, create the properties below, create the default `gallery` view, then set `schema_locked`.
   - `name` (title, owner user)
   - `category` (select, options `main`, `breakfast`, `dessert` with colors `#FF9500`, `#FFCC00`, `#FF2D55` stored in `config.options[].color`)
   - `prepMinutes` (number, `filterPresets` `[15, 30, 60]` with operator `lte`)
   - `servings` (number)
   - `favorite` (checkbox)
   - `photo` (image `{ blobId }`, owner user)
3. Call the seed function from `seedSystem.ts` for new tenants, and add a per-tenant cutover call in `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`, after the existing cutovers, modeled on `runTranscriptsCatalogCutoverMigration`), so existing tenants, including suspended ones, receive it on deploy. The existing-tenant path runs in the tenant's scope under the seed's advisory lock `(2331, hashtext(tenant_id))`, checks `getDatabaseByModuleId(client, "recipes")` and does nothing when the database exists, so a second run changes nothing.
4. Add Czech and English labels in `seed/i18n/cs.json` and `en.json`: `database.recipes.name` ("Recepty" / "Recipes"), property names, the category option labels, and the collection search placeholder.
5. Add a create/update write hook `recipePhotoWriteHook` in `backend/packages/data/src/recipes/recipePhotoHook.ts`, registered in `domainWriteHooks.ts` beside `mcpServerItemCreateHook`. When a write to a `recipes` item sets `photo`, the hook loads the blob with `getBlob` in the caller's tenant and rejects with `ValidationError` (HTTP 400, field `photo`) when the blob is unknown, belongs to another tenant, or its `mime_type` does not start with `image/`. A foreign and an unknown id answer identically.

## Scope

### In scope

- The `recipes` system database, its six properties, gallery default view type, owning system project, labels, delivery to new and existing tenants, and photo validation.

### Out of scope

- Uploading image blobs and collecting unused ones: #1401.
- Proposing recipes from Inbox links and photos, and the `sourceUrl` property: #1974.
- Default category for a new item, quick filters and default sorts: #1389 and #1647.
- A shopping list ("ingredients to shopping") and structured ingredients: not in this version.
- A relation from Recipes to Areas: not in this version.
- Hiding Recipes from the overview: #2002, which builds on this one.

## Acceptance criteria

- When a new tenant is provisioned, or an existing (including suspended) tenant is deployed to, then a `recipes` database exists with exactly the six properties and Czech labels; running the step again changes nothing.
- When `GET /api/databases` is called, then `recipes` is returned with its icon, color, order and `defaultViewType` `gallery`.
- When `DELETE /api/databases/:id` is called for the `recipes` database, then it is refused like for any system database and the database stays live.
- When a recipe is created with a `photo` whose `blobId` is unknown, from another tenant, or has a non-`image/*` mime type, then the response is 400 with field `photo`; with an image blob of the tenant the write succeeds.
- When items are filtered with `prepMinutes` `lte` 30, then recipes with 10 and 25 minutes match and recipes with 35 minutes or no time do not.
