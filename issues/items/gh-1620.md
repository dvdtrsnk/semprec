## Context

Model tier rationale: One write mechanism (a transactional insert plus job enqueue behind two POST routes) on existing route, store and queue seams, with a closed-error-contract extension that has precedent.

#1367 added the thread and message tables and #1543 the read routes in `backend/services/semprec-api/src/sempThreadsHandler.ts`. Nothing yet lets the app send a message. `SempConversation.send` (`backend/packages/agent-runtime`) can wake and run a turn but nothing calls it, and there is no `/api/semp/*` write route.

This issue accepts a user's message over HTTP, stores it, and queues the work. The reply is produced later by the turn runner (#1727), so the request answers 202 as soon as the user message and a queued assistant message exist. A new chat is created by its first message (there are no empty threads); a message in an Inbox item's thread reuses the existing thread of that item.

The closed error contract (`services/semprec-api/src/adapter/errorContract.ts`, `ITEM_ERROR_CODES`) has no code for a message to an already decided Inbox proposal. `reviseProposalWithClient` currently raises a plain `ValidationError` (400) for locked proposals (`LOCKED_PROPOSAL_STATUSES` = confirmed, rejected). This issue adds the code `proposal_locked` (HTTP 409) additively.

Decisions: (1) a message to a thread whose proposal is confirmed or rejected is refused with 409 `proposal_locked`; the thread of a processed Inbox item can still be opened and read through the read routes of #1543, so it is read-only; (2) the "Semp wants to approve" card is not an Inbox item, so no item thread exists for it, and a `subject` that is not an existing Inbox item is a 400; (3) the user may keep talking in a thread that shows a pending approval card: a message to such a thread is accepted like any other and the card stays in the thread. An approval is decided only on the card or in the approval list, never by the text of a message: sending a message never approves, rejects or otherwise changes a pending approval request.

Builds on this: #1682 validates and stores refs in `context`, #1938 loads card context, #1727 consumes the job, #1906, #1734, #1669 and #1853 extend the same route.

Shared-file ordering: this issue also waits for #1616 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening`, `canonical-keys` and `testing`.

1. In `sempThreadsHandler.ts` add `POST /api/semp/threads` with body `{ text, context?, subject?: { inboxItemId, proposalId? } }` and `POST /api/semp/threads/:id/messages` with `{ text, context? }`. Both are `RouteDefinition`s in the existing route family, registered in `routeMatrix.ts` (tenancy `tenant`) and covered by `tenantIsolationRoutes.test.ts`.
2. In one `withTransaction`: create the thread when needed (kind `item` when `subject` is given, otherwise `chat`; an existing item thread of that Inbox item is reused), insert the `user` message, insert an `assistant` message with `status = 'queued'` and `reply_to_message_id` = the user message, update `last_activity_at`, and enqueue a job `sempMessage` with `{ threadId, assistantMessageId }` (add the task name to `AGENT_TASK_NAMES` and its tenancy to `TASK_TENANCY` in `backend/packages/queue/src/index.ts`; the handler is delivered by #1727). Respond 202 `{ threadId, messageId, assistantMessageId }`.
3. Errors in the closed contract: text empty after trim 400; `subject` pointing to a non-existent Inbox item 400; `context` on an `item` or `tick` thread 400 (only chat threads take refs); a thread whose proposal is `confirmed` or `rejected` 409 `proposal_locked`; a tick thread cannot be posted to here (400); a thread of another tenant or unknown id 404. `context` is stored as given here; ref validation is added by #1682.
4. Add `proposal_locked` to `ITEM_ERROR_CODES` and `ITEM_ERROR_STATUS_BY_CODE` (409) and a dedicated error class in `backend/packages/data/src/errors.ts`; throw it from the send path for locked proposals. Leave `reviseProposalWithClient` behavior unchanged.
5. Message text is never logged.
6. Tests: 202 and both messages present (assistant `queued`) before any job runs; whitespace text 400; context on item thread 400; confirmed proposal 409 in the closed contract; same Inbox item reuses its thread; unknown subject 400; foreign thread 404; a message to a chat thread with a pending approval request is 202 and the request stays `pending` (also when the text says "yes, approve it"); the thread of a confirmed proposal still answers its history read; the job is enqueued exactly once, in the same transaction as the rows (a rollback leaves neither).

## Acceptance criteria

- When a valid message is posted, then the response is 202 and the thread holds the user message and a `queued` assistant reply before the job starts.
- When the text is only whitespace, or context is sent to an item or tick thread, then the response is 400.
- When the Inbox proposal of an item thread is confirmed or rejected, then posting returns 409 `proposal_locked` in the closed error contract.
- When a second message is posted for the same Inbox item, then it lands in the same thread.
- When a message is posted to a chat thread that has a pending approval request, then the response is 202 and the approval request is still `pending` afterwards, whatever the text says.
- When the Inbox proposal of an item thread is confirmed, then the thread and its history can still be read.
- When the transaction rolls back, then no message and no job exist.
