## Context

Model tier rationale: One test file, an existing fixture and one added statement; no production code changes.

`backend/packages/data/src/__tests__/itemRelationFilter.test.ts`, test "only scans the related item's own items_p_* partition, not every database's partition" (#262), is flaky. In CI on pull request #1194 (`integration-shard (3)`) it once reported 20 scanned `items_p_*` partitions instead of the one Folders partition. A rerun of the same commit passed, and it passes locally.

The test runs `EXPLAIN (ANALYZE, FORMAT JSON)` on `ITEM_RELATION_FILTER_QUERY` and counts the partitions the executor actually visited. It assumes the planner picks a plan with runtime partition pruning, a parameterized nested loop in which skipped partitions report zero loops. Which plan the planner picks depends on the statistics of the freshly seeded `items` partitions. The test never collects them, so they are whatever autovacuum's analyze happened to record, if anything, by the time the query runs. That timing varies with host load, so the chosen plan can be one that scans every partition. This is the most likely cause; the Task makes the statistics deterministic so the outcome no longer depends on autovacuum timing.

## Task

Load `testing`.

1. In that test, immediately before the `EXPLAIN (ANALYZE, FORMAT JSON)` query, run `ANALYZE items` on the same pool. `items` is the partitioned parent; `ANALYZE` on it also analyzes its partitions. Add a one-line comment saying the statistics are collected here so the planner's choice does not depend on when autovacuum last ran.
2. Run the test file 30 times in a row locally (for example `for i in $(seq 30); do npx vitest run --config vitest.integration.config.ts packages/data/src/__tests__/itemRelationFilter.test.ts || break; done` in `backend/`) and state the result in the pull request description.
3. If, with fresh statistics, the test fails every time, the planner does not prune this query under realistic statistics and #262's guarantee does not hold. Do not weaken the assertion and do not force a plan with `enable_*` settings. Stop and report it (in a Relay run, `Relay-Step-Status: blocked`), naming the plan node types the `EXPLAIN` output shows.
