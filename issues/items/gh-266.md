**Blocked by:** #93, #94

## Context

`AccountQueue` in `backend/packages/data/src/mail/imapConnectionLimiter.ts` (delivered by #94) bounds how many IMAP tasks may run concurrently for one mailbox account, because real providers enforce a hard simultaneous-connection cap server-side. Callers go through `imapConnectionLimiter.run(accountId, limit, task)`, which calls `queue.setLimit(limit)` for an existing account queue and then `queue.run(task)`. `run` waits in a `waiters` array while `active >= limit`, increments `active` once it proceeds, and decrements it in a `finally` that wakes one waiter.

A post-merge review of #94's pull request found that raising the limit wakes more waiters than there is capacity for. The finding was never addressed and is still on `develop`.

The mechanism: `setLimit` drains waiters in a `while (this.active < this.limit && this.waiters.length > 0)` loop, but resolving a waiter does **not** synchronously increment `this.active` — that happens later, in the woken waiter's async continuation inside `run()`. The loop condition therefore keeps holding as it drains. With `active = 1`, the limit raised to `3` and `waiters = [W2, W3, W4]`, all three are resolved (`1 < 3` throughout) and `active` reaches `4` — one more concurrent IMAP connection than the provider allows.

The bot's suggested fix was to count the free slots before the loop (`slotsToFill = limit - active`). **That is not sufficient, and this issue deliberately does not do it:** `createImapConnectionLimiter.run` calls `setLimit(limit)` and then immediately `queue.run(task)`. With `active = 1`, three waiters and the limit raised to `3`, `slotsToFill` wakes exactly two waiters — and then the very `run()` call that raised the limit finds `active` still `1` (the woken waiters have not resumed yet), takes a slot itself, and the count still reaches `4`. Any fix that decides how many waiters to wake without also reserving their slots has this hole.

## Task

In `backend/packages/data/src/mail/imapConnectionLimiter.ts`, make slot accounting a synchronous hand-off, so a waiter's slot is reserved at the moment it is woken rather than when its continuation happens to resume:

- Add one private helper on `AccountQueue` that wakes waiters and reserves a slot for each as it goes — incrementing `this.active` **before** calling that waiter's `resolve()`, while `this.active < this.limit && this.waiters.length > 0`.
- Have `setLimit` call that helper after assigning the new limit, instead of its current drain loop. Keep the existing explanatory comment about why raising the limit must free waiters immediately.
- Change `run` so a task that had to wait does **not** increment `active` again when it resumes — its slot was already reserved by the waker. A task that finds free capacity immediately still reserves its own slot synchronously before awaiting `task()`.
- Have the `finally` path decrement `active` and then use the same helper, so releasing a slot keeps waking at most as many waiters as there is capacity for.
- The waiter timeout (`ACCOUNT_QUEUE_WAIT_TIMEOUT_MS`) keeps its current behavior: a timed-out waiter is spliced out of `waiters` and rejects, and because it is removed before any slot is reserved for it, no slot leaks. A waiter that has already been resolved must not be woken or reserved twice.

Add a regression test in `backend/packages/data/src/__tests__/mailSync.test.ts`, next to the existing `imapConnectionLimiter` tests, that:

- starts one task for an account under `limit: 1` and leaves it running (`active === 1`),
- queues three further `run(accountId, 1, ...)` calls for the same account, which all wait,
- makes one more call as `run(accountId, 3, ...)`, which raises the limit and also wants to run,
- tracks concurrently-running tasks with a counter incremented on entry and decremented on exit, and asserts the observed maximum never exceeds `3`,
- releases the first task at the end so the queue drains, and asserts that every queued task eventually runs (nothing is stranded by the stricter accounting). Without that release the waiters would sit until `ACCOUNT_QUEUE_WAIT_TIMEOUT_MS` and the test would hang.

## Scope

### In scope

- The slot-reservation change in `AccountQueue` (`setLimit`, `run`, the release path, and the shared wake helper) in `imapConnectionLimiter.ts`.
- The regression test for it.

### Out of scope

- The waiter timeout mechanism itself and the per-provider limit table (`imapConnectionLimitForProvider`, `connectionLimitBackoffSecondsForProvider`) — both stay as they are.
- Where `imapConnectionLimiter.run` is called from relative to an open database transaction — that is #267.

## Acceptance criteria

- With one task active under a limit of 1, three waiting tasks, and a further call that raises the limit to 3, at most 3 tasks for that account run concurrently — including the call that raised the limit.
- Every queued task still eventually runs, and raising the limit still releases as many already-waiting tasks as the new capacity covers, immediately, without waiting for an unrelated in-flight task to finish. The call that raises the limit may now itself queue behind those waiters — that is the intended consequence of reserving slots at wake time, not a regression.
- A waiter that times out still rejects with the existing timeout error and leaves no reserved slot behind.
- The existing `imapConnectionLimiter` tests still pass.
