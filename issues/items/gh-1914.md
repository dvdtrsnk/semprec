## Context

Model tier rationale: A single read-side collapse rule inside an existing list query, with a cost sum and a per-attempt breakdown over the same rows, depending on the retry-chain columns from a blocker; the main risk is correct selection of the latest attempt and correct grouping of costs, which existing fixtures can verify.

The project run list (#1909) returns one row per agent run. A heartbeat tick that fails is retried by the queue, and every automatic attempt is its own `agent_runs` row (today they carry no link to the tick occurrence they belong to). #1458 links heartbeat runs to their occurrence (`heartbeat_occurrence_id`) and chains attempts through `retry_of_run_id`; #1448 defines the attempt number. Without collapsing, a tick that was tried three times would show as three rows in a list limited to the last few runs and push real work out of it.

Decision: a row represents one occurrence; its status, error summary, duration and start time are those of the latest attempt, and `attempt` is that attempt's number.

Decision (product owner): the row's `costUsd` is the sum of the costs of all attempts of the occurrence, so the user sees the real price of the run; the cost of each attempt is shown when the row is expanded. The row therefore carries `attempts`, the list of its attempts with their own cost. Duration is not summed.

Delegation sub-runs (`parent_run_id` set from a `heartbeat.trigger` tool call) are not part of this mechanism: delegation does not run in production, and the list already shows only runs of the session user without `supervisor` runs.

## Task

Load `testing`.

1. In the store read behind the list (#1909, `listProjectAgentRuns` in `backend/packages/data/src/agentRuns/agentRunsStore.ts`), return for each heartbeat occurrence only its latest attempt: among rows sharing `heartbeat_occurrence_id` keep the one that is not the `retry_of_run_id` of any other row (equivalently the highest attempt). Rows without an occurrence id (chat and MCP runs, heartbeat runs started manually) are returned unchanged.
2. Apply the collapse before the `limit` is applied, so that `limit` counts rows after collapsing and the list still returns `limit` rows when enough exist.
3. Fill `attempt` in each row with the attempt number of the returned run (the attempt column or derivation defined by #1448); `1` for runs with no retry.
4. For a collapsed occurrence, set `costUsd` to the sum of the costs of all its attempts and add `attempts: [{ id, attempt, startedAt, durationMs, costUsd, displayStatus }]`, ordered by `attempt` ascending, each with that attempt's own cost from the same batched cost aggregation of #1909 (no query per attempt). A row with a single attempt has `attempts` with one entry equal to the row. Rows without an occurrence id have no `attempts` key.
5. Keep the index of #1909 usable: the query must not load the entire project history to collapse (use a window or `DISTINCT ON` over the occurrence key, bounded by the same ordering).

## Scope

### In scope

- Collapsing automatic retry attempts of one heartbeat occurrence into a single row carrying the latest attempt and its number, the summed cost of all attempts and the per-attempt breakdown.

### Out of scope

- Creating the occurrence link and the retry chain: #1458 and #1448.
- A manual retry from the API: #1908.
- Chat answers and their retries: #1932.

## Acceptance criteria

- When one occurrence has three automatic attempts (the first two errored, the third errored or finished), the list contains exactly one row for it, with `attempt` 3 and the status, error summary, start time and duration of the third run.
- When those three attempts cost $0.01, $0.02 and $0.03, then the row's `costUsd` is $0.06 and its `attempts` lists the three attempts in order with $0.01, $0.02 and $0.03; the number of cost queries does not depend on the number of attempts.
- When the project has 6 occurrences and one of them has 3 attempts, `limit=5` returns 5 rows (collapsing happens before the limit).
- Runs with no occurrence id appear unchanged with `attempt` 1.
- Delegation sub-runs of a supervisor are absent from the list.
- A run of another tenant with the same occurrence id value is never merged into or returned in this tenant's list.
