## Context

The 30-day trash purge (`backend/packages/data/src/trash/purgeExpiredTrash.ts`, `purgeExpiredTrash`, line 19) hard-deletes each expired root through `chokePoint.purgeExpiredTrashSubtree` (`backend/packages/data/src/chokePoint/itemTrash.ts`, lines 198-220), whose delete loop (lines 214-217) calls only `itemsStore.hardDeleteItem` (`backend/packages/data/src/chokePoint/itemsStore.ts`, lines 236-242), which is a bare `DELETE FROM items WHERE database_id = $1 AND id = $2 AND deleted_at IS NOT NULL`. `items` is partitioned with a composite key, so none of the tables that point at an item carry a Postgres FK (see the header notes of `0002_views.sql`, `0003_docs.sql`, `0004_ten_databases.sql`), and nothing else deletes them. After a purge the following rows are orphaned forever:

- `item_relations` (`item_a`/`item_b`), `view_items.item_id`, `idempotency_keys.item_id` (the orphaned reservation is what makes `insertItem` throw `Idempotency key reservation exists but its item is missing` — sibling issue C3 handles the journal side);
- `docs.item_id` and, through its FK cascades, `doc_snapshots`, `doc_updates`, `doc_history_updates`, `doc_snapshot_history` — `runDocHistoryRetentionSweep` (`backend/packages/data/src/docs/docHistory.ts`, line 119, `SELECT id FROM docs`) keeps re-baselining these orphan docs nightly;
- `task_recurrence.item_id`, `item_automation.item_id`, `item_search_index.item_id`;
- `blobs` rows and their bytes for a purged Files item (`properties.file.blobId`);
- inline `databases` rows: `collectItemSubtree` (lines 131-158) walks them via `listDatabasesByParentItem` and purges their rows, but the `databases` row, its `properties`/`views`, and its `items_p_<hex>` partition stay behind.

Separately, `itemsStore.findItemsDeletedBefore` (lines 218-225) loads every expired row system-wide with no `LIMIT`, so the sweep's memory is unbounded.

This issue depends on C1: it adds the `drop_items_partition(uuid)` counterpart of C1's `create_items_partition` in the same `SECURITY DEFINER` shape (the API role does not own `items`, so it cannot `DROP TABLE` a partition either). Constrained by `docs/adr/2026-09-10-side-effects-follow-the-commit.md` (blob bytes are removed only after the row deletion has committed).

## Task

1. New migration `backend/packages/data/src/db/migrations/NNNN_drop_items_partition_function.sql` (next free ordinal at commit time): `CREATE FUNCTION drop_items_partition(database_id uuid) RETURNS void LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, public` whose body runs `EXECUTE format('DROP TABLE IF EXISTS %I', 'items_p_' || replace(database_id::text, '-', ''))`; `REVOKE EXECUTE ... FROM PUBLIC`, `GRANT EXECUTE ... TO semprec_data`. Header comment: same rationale as C1's function, plus that `DROP TABLE` of a partition takes `ACCESS EXCLUSIVE` on the partition and on `items` for the rest of the caller's transaction, which is acceptable because the only caller is the nightly purge (`45 3 * * *`).
2. `itemTrash.ts`: new exported `deleteItemDependents(client: PoolClient, row: ItemRow): Promise<{ blobStorageKey: string | null }>` that, in this order, deletes `item_relations WHERE item_a = $1 OR item_b = $1`, `view_items WHERE item_id = $1`, `idempotency_keys WHERE item_id = $1 AND database_id = $2`, `docs WHERE item_id = $1` (the four doc tables cascade), `task_recurrence WHERE item_id = $1`, `item_automation WHERE item_id = $1`, `item_search_index WHERE item_id = $1`, and — when `row.properties.file.blobId` is a string — deletes the `blobs` row and returns its `storage_key` only if no other `items` row in any partition (live or trashed, `properties -> 'file' ->> 'blobId' = $blobId`; the purged row itself is already gone by then) and no `mail_attachments.blob_id` row references it (content-hash dedup in `blobs/blobsStore.ts`'s `findOrCreateBlob` shares one blob between identical uploads). `purgeExpiredTrashSubtree`'s delete loop runs `itemsStore.hardDeleteItem` first and calls `deleteItemDependents(client, row)` only when it returned `true` — a race-restored row (see `hardDeleteItem`'s `deleted_at IS NOT NULL` guard) keeps every dependent.
3. Inline databases: after the delete loop, for every database id in `subtreeDatabaseIds` other than the root's own `databaseId` whose `items` partition is now empty (`SELECT NOT EXISTS (SELECT 1 FROM items WHERE database_id = $1)`), call a new `databasesStore.dropDatabaseWithPartition(client, id)` that runs `DELETE FROM rollup_dependencies WHERE source_database_id = $1`, `DELETE FROM item_search_index WHERE database_id = $1`, `SELECT drop_items_partition($1::uuid)`, then `DELETE FROM databases WHERE id = $1` (`properties` and `views` cascade by FK) and checks `rowCount` with `requireAffectedRows`. A non-empty inline database (a nested live or too-fresh row stopped the cascade) is left in place, row and partition.
4. `purgeExpiredTrashSubtree` returns `{ purgedItemIds: string[]; blobStorageKeys: string[] }` (the non-null keys collected from step 2). `purgeExpiredTrash(pool, storage: BlobStorageWriter, retentionDays?)` deletes each returned key through `storage.delete(key)` after the subtree call has resolved (the transaction has committed by then), logging and continuing on a storage failure; `handleItemTrashPurgeSweepTask(pool, storage)` and both crontab task entries in `backend/packages/data/src/worker.ts` (`ITEM_TRASH_PURGE_SWEEP`, `TRASH_PURGE`) pass `mailBlobStorage`.
5. Batching: `findItemsDeletedBefore(client, olderThan, after?: { databaseId: string; id: string }, limit = 500)` adds `AND (database_id, id) > ($2, $3)` keyset paging on the composite primary key, `ORDER BY database_id, id LIMIT $4`; `purgeExpiredTrash` loops over pages until a page is shorter than the limit, advancing the keyset from the last row of each page (never re-reading a failed candidate).
6. Tests in `backend/packages/data/src/trash/__tests__/purgeExpiredTrash.test.ts` (integration): after purging a page with a doc, a relation edge, a curated-view membership, an idempotency key, a `task_recurrence` row and an inline database, every listed table has zero rows for the purged ids, the `databases` row and `items_p_<hex>` partition of the inline database are gone, and `docs`/`doc_history_updates` for the page are gone; a purged Files item whose blob is shared with a live Files item keeps the `blobs` row and the fake storage's `delete` is not called; a purged Files item with an unshared blob removes the row and the fake storage's `delete` is called once with its `storage_key` after the purge resolves; 1,001 expired items are purged with the page size overridden to 500 (three pages).

## Scope

### In scope
- Dependent-row deletion, blob row/bytes removal with the shared-blob guard, inline-database drop, keyset batching of the sweep, and their tests.

### Out of scope
- Journal lookups against a purged or soft-deleted period item (sibling issue C3).
- Module side tables keyed by item that this issue does not touch: `mail_message_meta`, `mail_attachments`, `mail_message_flag_sync_state`, `mail_account_sync_state`, `mail_folder_sync_state`, `external_credentials`, `credential_access_log`, `person_email_index`, `project_heartbeats`, `agent_runs`, `resource_grants`, `project_mcp_grants`, `mcp_tool_registrations`, `project_agent_guidance` — their purge hooks belong to the module-hook refactor of the pre-tenancy epic.
- `mail/attachments.ts`'s own blob handling and `blobs/fileUploadStore.ts` (sibling issue C16).

## Acceptance criteria

- When the purge removes an item, `item_relations`, `view_items`, `idempotency_keys`, `docs` (and its four cascade tables), `task_recurrence`, `item_automation` and `item_search_index` contain no row for that item id afterwards, in the same transaction as the `items` delete.
- When the purge removes the last row of an inline database, that database's `databases` row and `items_p_<hex>` partition no longer exist and `listDatabasesByParentItem` for the purged page returns nothing; when a nested row stopped the cascade, the inline database and its partition remain.
- When a purged Files item's blob is referenced by no other item or mail attachment, the `blobs` row is deleted in the purge transaction and `storage.delete(storageKey)` runs after that transaction has committed; when it is shared, neither happens.
- When more than 500 expired items exist, the sweep purges all of them in pages of 500 and never loads more than one page of candidates at a time.
