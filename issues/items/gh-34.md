**Blocked by:** #33

## Context

Issues #21 through #33 built the entire data layer, views, modules, and agent runtime of Semprec — all without any formal authentication or authorization. Yet as far back as #21 (schema engine), the column `resource_grants.grantee_user_id` exists, and since #29 (module contract) the column `approval_requests.decided_by` exists, both with `REFERENCES users(id)`. The `users` table those foreign keys point to was never created, and no login mechanism was ever designed — the system has been effectively open the entire time, running without any concept of "user".

This issue closes that gap retroactively across the whole system: it defines `users`, introduces a session mechanism, and ensures that all existing API paths from issues #21-#33 go through one shared authentication choke-point instead of remaining accessible to anyone.

Scope for v1 is deliberately narrow — one account, no sharing, no roles. `resource_grants` remains a reserved schema for future multi-user operation, but v1 does not populate or use it in any way.

## Task

1. Create the `users`, `sessions`, and `login_attempts` tables per the schema below, and wire the login choke-point that enforces them.

```sql
CREATE TABLE users (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email text NOT NULL UNIQUE,
  password_hash text NOT NULL,
  locale text NOT NULL DEFAULT 'cs',   -- drives both UI and the language of the generated AGENT.md manifest (see issue #35)
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE sessions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES users(id),
  token_hash text NOT NULL UNIQUE,   -- hash of the opaque token, not the token itself (same principle as password_hash)
  platform text NOT NULL,            -- 'web' | 'ios' | 'macos'
  created_at timestamptz NOT NULL DEFAULT now(),
  last_seen_at timestamptz NOT NULL DEFAULT now(),
  expires_at timestamptz NOT NULL,
  user_agent text,
  revoked_at timestamptz
);

CREATE TABLE login_attempts (
  id bigserial PRIMARY KEY,
  email text NOT NULL,
  ip inet NOT NULL,
  succeeded boolean NOT NULL,
  attempted_at timestamptz NOT NULL DEFAULT now()
);
```

2. Implement a single login mechanism for v1: email + password, with the password hashed via **argon2id** (not bcrypt — argon2id is the OWASP-recommended, memory-hard choice, resistant to GPU/ASIC cracking, and there is no legacy reason here to pick a weaker algorithm).
3. The session token is an **opaque** random string issued at login; only its hash is stored in the DB (same pattern as `password_hash`) — **explicitly not a JWT**. Rationale: a JWT gives stateless verification for free, but it cannot be revoked before expiry without a second, stateful blocklist table alongside it — which is the same stateful mechanism, just disguised, without the benefit. An opaque DB-backed token gives immediate revocation (set `revoked_at`) for free — the same "state lives in Postgres, not in a cryptographically self-contained artifact" discipline already applied to `agent_runs` (issue #29).
4. Token delivery differs by platform, but all read/write the same `sessions` table:
   - **Web**: an `httpOnly` + `Secure` + `SameSite=Lax` cookie (JS never sees the token, so XSS cannot steal it).
   - **iOS/macOS** (native Swift/SwiftUI app): the same token returned in the login response body; the app stores it in the Keychain and sends it as an `Authorization: Bearer` header.
   - **Embedded WKWebView editor** (the block/canvas editor inside the native app): receives the token via a JS bridge (`WKScriptMessageHandler`) from the native shell — it does not perform its own second login; it is treated as the app that wraps it, not as a separate client.
   - All three paths are verified by the same choke-point against the same `sessions` table; only the delivery mechanism differs.
5. Multi-device login must work automatically as a consequence of the data model — a `sessions` row represents a *login*, not a *user* (no unique constraint on `user_id`). Logging out or remotely revoking one device (`revoked_at`) must not affect any other concurrent session.
6. Rate-limit the login endpoint: `login_attempts` records success/failure keyed on the (email, IP) pair; the choke-point, before issuing a session, counts failed attempts in the last N minutes and rejects the request above the threshold even with the correct password (exponential window, reset on success).
7. Implement forgotten-password reset over the existing SMTP infrastructure (outbound email, issue #27) — no new external dependency. A short-lived, single-use signed link (same "store the hash, not the value" pattern as the session token) is emailed to `users.email`; it is invalidated immediately on use, and expires (typically after 30 minutes) regardless of use.
8. Bootstrap the first (and only) account via a `/setup` wizard:
   - The route is reachable only when **both** conditions hold: `(SELECT count(*) FROM users) = 0` and a query parameter matches `SETUP_TOKEN`.
   - `SETUP_TOKEN` is generated by a one-time bootstrap step (run manually once, separate from the repeatable `deploy.sh`), written to `shared/.env` alongside the VAPID key pair and APNs key (same bootstrap-secret category, one unified policy — see issue #40), and printed once to the operator's terminal.
   - Once the first `users` row exists, `/setup` permanently returns 404 regardless of the token — DB state is the real gate; the token only resolves the race of who gets in first while the table is still empty.
   - The wizard itself calls no special-case logic — just the same signup logic a hypothetical v2 public signup would use (email + password → `argon2id` hash → `INSERT INTO users`), only unlocked differently.
9. Retroactively wire the authentication choke-point in front of every existing API/view path from issues #22-#33 that did not previously have any authorization — after this issue, no endpoint is implicitly public.

## Scope

### In scope

- The `users`, `sessions`, and `login_attempts` tables and their migrations.
- Login/logout endpoints, argon2id password hashing, opaque session token plus its hash stored in the DB.
- Token delivery for web (httpOnly cookie), the native iOS/macOS app (Keychain + Bearer header), and the embedded WKWebView editor (JS bridge from the native shell).
- Login rate-limiting via `login_attempts` (exponential window on the email+IP pair).
- Password reset over the existing SMTP infrastructure, using a short-lived single-use token.
- The `/setup` bootstrap wizard, gated by an empty `users` table plus `SETUP_TOKEN`.
- Retroactively wiring the auth choke-point in front of every existing API path from issues #21-#33.
- Support for multiple concurrent logins (multiple devices) on one account, arising from the `sessions` data model (a row per login, not per user).

### Out of scope

- Two-factor authentication (TOTP) — deliberately deferred to v2; the `users` schema leaves this open (adding a `totp_secret` column and one step in the login flow later is a purely additive change, not a breaking migration).
- A public self-service signup form — v1 has exactly one account, no `/signup` beyond `/setup`.
- Anything involving more than one account, roles, or role-based permissions — `resource_grants` (issue #21) remains a reserved schema for the future; this issue does not populate or modify it in any way.
- Manual DB intervention (SSH + `UPDATE`/`INSERT`) as an official path for password reset or account creation — a rejected pattern, replaced by `/setup` and the email-based reset.
- i18n/localization of the login screens' UI — that is the next issue, #35 (Czech and English); this issue only ensures the `users.locale` column exists and drives the language of the generated AGENT.md manifest (see issue #35), not the i18n implementation itself.
- Any change to the `external_credentials` table (issue #27) — it remains deliberately separate from `users`/`sessions` because it has a different lifecycle (it is encrypted/decrypted for use on the user's behalf, whereas `users.password_hash` is never decrypted, only verified).

## Dependencies

- **Issue #21 (schema engine)**: `resource_grants.grantee_user_id` already references `users(id)` — this task must finally create the table that FK has pointed to from the start; otherwise the schema engine from #21 could never actually enforce that FK. It also carries forward the same choke-point principle of "verify against data, don't trust the client" (idempotency key) that `login_attempts` applies here to login rate-limiting.
- **Issue #29 (module contract / agent runtime)**: `approval_requests.decided_by` has the same unfulfilled FK on `users(id)` as issue #21 — the second place that was waiting on `users` to exist. It also carries forward the discipline of "state lives in Postgres, not in a cryptographically self-contained artifact" that #29 introduced for `agent_runs` — here applied to choosing an opaque DB session token instead of a JWT.
- Implicit dependency on the existing SMTP infrastructure (outbound email, issue #27) for password reset — no new integration, just reuse.
- Implicit dependency on the `shared/.env` and bootstrap-secret convention (VAPID pair, APNs key — issue #40) for where `SETUP_TOKEN` lives.
