## Context

Model tier rationale: One new read route with a cursor pairing rule over an existing event table, using the existing handler, authorization and route-matrix fixtures; no write path, schema change or new isolation contract.

The only way to read a run's events today is the realtime watch `agent:watch {runId, afterEventId}` in `backend/packages/realtime/src/agentRunWatch.ts`, which replays `listAgentRunEventsAfter` (no limit) and then streams the raw `agent:event` frames; `agent:delta` carries live typing text. There is no REST read of a run's progress, so a client cannot open a finished run, page through a long one, or recover after a reconnect except by replaying raw events. `backend/services/semprec-api/src/agentRunHandler.ts` knows only `GET /api/agent-runs/:id` and `POST /api/agent-runs/mcp-credentials`; the prefix `/api/agent-runs/` is already routed to it in `app.ts`.

This issue adds `GET /api/agent-runs/:id/steps` which groups the stored events into steps and pages over them with a cursor that never splits a tool call. It is the paging and pairing mechanism only. The presentation fields of a step (localized title, target name, change, result summary, approval steps; arguments and results are never returned) are added by #1847; the approval state of an approval step by #1862; scoping to one chat reply by #1889.

Authorization is the same as the run detail from #1805: the run is read under the caller's tenant (another tenant's run is invisible and answers 404) and a run whose `actorUserId` is not the session user also answers 404, the defense in depth pattern of `agentRunWatch.ts`.

Decision (live clients): the realtime `agent:event` and `agent:delta` frames stay raw signals. A client that sees one issues a new `GET .../steps?after=<nextCursor>`; the projection lives only on the server and nothing is duplicated into the realtime protocol.

Decision (history gone): events of finished session runs older than the retention window and before a compaction checkpoint are deleted (`backend/packages/data/src/agentRuns/agentRunEventsRetention.ts`). The response sets `truncatedHistory: true` when the run's first stored event is not its opening `run_status` event (which every run writes first), and still returns the remaining steps.

Shared-file ordering: this issue also waits for #1812 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `io-hardening`, `error-handling` and `testing`.

1. Add `GET /api/agent-runs/:id/steps?after=<eventId>&limit=<n>` to `agentRunHandler.ts`. `after` is an `agent_run_events.id` (string bigint, default: from the start, validated as digits), `limit` defaults to 100 and is capped at 500 (a larger or non-numeric value is a 400 `ValidationError`). Authorization as described in Context (404 for unknown, foreign tenant, or a different actor).
2. Response: `{steps: Step[], nextCursor: string | null, truncatedHistory: boolean}`. In this issue a `Step` is `{stepId, kind, state, at, durationMs, toolCallId, operation, mcp}` with `kind` one of `start`, `plan`, `tool`, `answer`, `end`, `error` and `state` one of `running`, `ok`, `error` (`waitingApproval` and the `approval` kind are added by #1847 and #1862). `stepId` is the id of the step's first event. Mapping: the opening `run_status` running is `start`; an assistant `message` with text that is followed by tool calls is `plan`; a `tool_use` and its `tool_result` (matched on `toolCallId`) are one `tool` step, with `durationMs` from the two event times and `operation` / `mcp` read through the typed parser from #1424; the final assistant `message` without tool calls is `answer`; the terminal `run_status` is `end` (`error` run: an `error` step). A tool step is `error` when the result has `isError === true`, `result.details.error === true`, or (rows stored before the interrupted-result fix) a top-level `error: true`; the interrupted result written by #1374 follows the first two rules. Thinking content is never returned. `turn_start`, `turn_end` and `compaction` produce no step.
3. Cursor rule: events are read in id order and grouped; `nextCursor` is the id of the last event of the last closed step in the page, `null` when the page reached the end of the run and nothing is running. A page never ends between a `tool_use` and its `tool_result`. A tool step whose result has not arrived is returned with `state: "running"` and the cursor stays before it, so the next request returns it again (complete). A request with `after` set to a cursor returns no step twice and skips none.
4. Add the data-layer read the handler needs next to `listAgentRunEventsAfter` in `backend/packages/data/src/agentRuns/agentRunEventsStore.ts` (a bounded `LIMIT` read; a page may read more events than `limit` steps need, but never an unbounded set). Keep the grouping in a pure function so it is unit-testable without a database.
5. Register the route: a `routeMatrix.ts` entry (`tenancy: "tenant"`), `ROUTE_HANDLER_FILES` in `chokePointWriteBoundary.unit.test.ts` (read-only, no write), and cross-tenant / foreign-id cases in `tenantIsolationRoutes.test.ts`.

## Scope

### In scope

- The `steps` route, the step grouping and the step-aligned cursor, `truncatedHistory`, and the authorization and route registration.

### Out of scope

- Localized titles, target names, changes, result summaries and approval steps: #1847.
- The approval state of an approval step: #1862.
- Narrowing steps to one chat reply (`messageId`): #1889.
- Nested steps of delegated sub-runs; delegation does not run in production and has no link from a tool call to its sub-run.
- Any change to the realtime protocol or to what `agent:watch` sends.

## Acceptance criteria

- When a finished run is read page by page with `limit=2` following `nextCursor`, then the concatenated steps equal the steps of one unpaged read in the same order as `agent:watch` replays the events, with no duplicate, no gap and no page ending between a `tool_use` and its `tool_result`.
- When a tool call has no result yet, then its step is returned with `state: "running"` and `nextCursor` stays before it.
- When a tool result has `isError: true`, `details.error: true`, or the legacy top-level `error: true`, then its step has `state: "error"`.
- When `limit` is above 500 or `after` is not a number, then the response is 400; the default limit is 100.
- When the run belongs to another tenant, does not exist, or has a different `actorUserId`, then the response is 404.
- When the run's earliest events were removed by retention, then `truncatedHistory` is `true` and the remaining steps are returned.
