## Behavior specification (approved)

The agent runtime (`backend/packages/agent-runtime/`), the `agent_runs`/`agent_run_events` stores, the heartbeat scheduler (`backend/packages/data/src/scheduler/`), the MCP approval execution path (`backend/packages/data/src/mcp/`) and the realtime run watch (`backend/packages/realtime/src/agentRunWatch.ts`) each carry a verified state-machine, scheduling or execution defect: a finished run can be re-finished with a different status, an expiring delegated session can be reused mid-close, a floating-rule heartbeat can end up permanently unscheduled with no error recorded, the heartbeat sweep is unbounded and all-or-nothing and computes the next fire from the JS clock, a disabled heartbeat can be fired by `heartbeat.trigger`, an approved MCP call can be lost between claim and outcome, after-commit realtime hooks are dropped (or fired late, on an unrelated transaction) by two hand-rolled `BEGIN` blocks, untrusted remote JSON Schemas are compiled per call on a shared Ajv instance, run watching authorizes against the earliest user instead of `agent_runs.actor_user_id`, and a retried heartbeat run notifies on every attempt and masks the original error when the notification write fails. The goal of this batch is that every one of these paths is idempotent, bounded, and records what happened: a run finishes exactly once, an occurrence's final failure always leaves `last_error` and a schedule, an approved MCP call is executed at most once with its outcome (or the fact that it is unknown) persisted, and realtime pushes fire only after the commit that made their rows visible.

## Evidence

- `finishAgentRun` (`backend/packages/data/src/agentRuns/agentRunsStore.ts:135-146`) is `UPDATE agent_runs SET status=$2 ... WHERE id=$1` with no `status='running'` guard; `insertAgentRunEvent` (`agentRunEventsStore.ts:46-59`) neither checks the run's status nor bounds the payload.
- `DelegationRegistry.expire` (`backend/packages/agent-runtime/src/delegationRegistry.ts:242-253`) awaits `finishAgentRun`/`pushRunStatus` without setting `busy`; `delegate()` (line 135) sees a free entry and runs a turn on a run being finished. `SempConversation.pause` (`sempConversation.ts:231-245`) claims `busy` first.
- `walkStoredEntries` (`conversationReconstruction.ts:114-162`) loads every session run (`listSessionAgentRuns`, no LIMIT) and all their events (`listAgentRunEventsByRunIds`) on every wake, then discards everything before the last `compaction` row. `agent_run_events` (migration 0015) has no retention job.
- `sweepDueHeartbeats` (`schedulerStore.ts:437-480`) sets `next_fire_at = NULL` for floating rules and relies on `prepareHeartbeatOccurrenceFire`; in `sweep.ts` that call (line 238) plus `assertActionAffinity`/`registry.get` (245-247, and 177-179 on the manual path) sit outside the `try` whose final-attempt branch records `last_error` and the `heartbeat_error` notification.
- `sweepDueHeartbeats` has no `ORDER BY`/`LIMIT`, runs the whole batch and every `enqueueJob` in one transaction, and computes the next fire from `new Date()` (line 449) although the due check used Postgres `now()`.
- `createHeartbeatTriggerTool` (`heartbeatAgentTools.ts:163-192`) never reads `heartbeat.enabled`.
- `handleApprovalRequestExecuteTask` (`approvalRequestExecution.ts:85-102`): claim in one transaction, `callTool` outside any transaction with no idempotency key (`mcpToolExecution.ts:90`), outcome in a third; `handle.close()` rejecting in `finally` (94-96) replaces the result; a crash between claim and outcome leaves the row `queued` with `executed_at` set forever; `recordApprovalRequestOutcome` (`approvalRequestsStore.ts:270-282`) has no state guard; grants/registration/server activity are not re-checked at execution time.
- `runAfterCommit` callbacks (`pool.ts:10-27`) are drained only by `withTransaction`; `repairInterruptedRuns` (`startupRepair.ts:36-69`) and `createPoolClientTransactionRunner` (`projectAgentGuidanceStore.ts:110-135`) issue raw `BEGIN`/`COMMIT`, so callbacks registered on their client stay in the `WeakMap` and fire on the next unrelated `withTransaction` that reuses the pooled client.
- `mcpInvokeTool.ts:46,59` compiles the remote server's `tool_schema` on a shared `Ajv` instance on every call; nothing bounds schema size, rejects remote `$ref`, or checks `pattern` regexes.
- `agentRunWatch.ts:145-150` authorizes with `getEarliestUserId(pool) !== userId` although `agent_runs.actor_user_id` is `NOT NULL` since migration 0042's cutover.
- `coreAgentRunAction` (`actions.ts:55-85`) writes an `agent_run_error` notification on every graphile attempt (three per failed occurrence) and, at line 80, lets a failing notification write replace the original error.

## Decisions

- **Retention and bounded reconstruction are two issues.** Reading only from the latest compaction and deleting old pre-compaction rows are separable mechanisms (the current walk already discards pre-compaction rows, so deletion is safe without the read change); the retention job also edits the shared crontab that #643 edits.
- **Outcome integrity and execution-time re-authorization of the MCP approval path are two issues.** A reviewer can approve the grant re-check without reading the claim/outcome protocol.
- **The MCP approval path keeps the existing `execution_status` vocabulary.** The `CHECK` constraint on that column is created by the app-code cutover (`approvalRequestExecutionStatusCutoverMigration.ts`) after the SQL migrations, so adding `executing`/`unknown` would require editing an existing migration step. "Executing" is already expressed by `execution_status='queued' AND executed_at IS NOT NULL` (0022's documented claim semantics); an unrecoverable unknown outcome is recorded as `conflict` with an explicit result text. No `claim_token`: the `executed_at IS NULL` claim is already exclusive.
- **A retried heartbeat run keeps one `agent_runs` row per attempt.** Re-opening a finished run contradicts the finish-once invariant this batch introduces and would interleave two attempts' events in one transcript; the fix is to notify only on the final attempt and never mask the original error.
- **The sweep paginates by `id` keyset, not `ORDER BY next_fire_at LIMIT`.** Rows the sweep deliberately leaves due (unparseable rule) would otherwise be re-selected by every chunk of the same sweep and starve everything behind them.
- **`withTransaction` gains an `isolation` option instead of a new `runInTransaction` export.** Both raw-`BEGIN` sites have a `Pool`; the guidance runner only needs the isolation level.
- **`run_status` events are exempt from the running-run guard**, because the terminal `run_status: done|error` event is written after `finishAgentRun` by design. The payload cap is 1 MiB (a `compaction` checkpoint is the largest legitimate payload).
- **The drift-heartbeat upsert's re-enable is not a defect.** Issue #85's spec requires the upsert to set `enabled = true` and a test pins it; that half of the audit finding is dropped.
- **Run watch authorizes on `actor_user_id` only.** The column is `NOT NULL` after the 0042 cutover, so no earliest-user fallback remains.
- **Schema hardening depends on #647 only because of `pnpm-lock.yaml`**: adding `safe-regex` touches the lockfile #647 also edits.
