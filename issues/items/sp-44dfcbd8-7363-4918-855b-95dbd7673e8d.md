## Context

Model tier rationale: One SQL expression in one store function and its tests, following a form the Semp thread list already uses; no schema, lifecycle, authorization or tenant contract changes.

`GET /api/mail/contacts?q=` (#1507; `createMailContactsRouteHandler` in `backend/packages/data/src/mail/mailContactsRoute.ts`) suggests mail recipients from People. `searchMailContacts` in `backend/packages/data/src/mail/personEmailIndexStore.ts` receives a pattern that `escapeContactSearchPattern` built in JavaScript (a backslash before every backslash, `%` and `_`, then `%` on both sides) and compares `unaccent(name) ILIKE unaccent($1) ESCAPE '\'`, and the same for the address. The pattern is therefore folded by `unaccent` after it was escaped.

The `unaccent` dictionary rewrites characters that the JavaScript escape does not touch into the three pattern characters: U+FF05 (fullwidth percent sign) and U+FE6A (small percent sign) become `%`, U+FF3F (fullwidth low line) becomes `_`, and U+FF3C, U+FE68 and U+2216 become a backslash. It also removes combining marks such as U+0301. These mappings were read in the `unaccent.rules` file of the Postgres the integration tests run on. So a request whose `q` is U+FF05 compares against `%%%` and returns every contact, a `q` of U+FF3F matches any single character, a typed U+FF3C turns the character after it into an escaped literal, and a `q` that is only a combining mark folds to `%%` and returns every contact. The read runs in the session's tenant scope, so the result stays inside the caller's tenant: this is a wrong suggestion list, not a leak.

The same defect was found in the review of the Semp thread list search (#1737) and fixed there by folding first and escaping after. This issue brings the contact search to the same order. It is the only other place with this shape: `views/filterCompiler.ts` escapes its pattern and does not fold it.

## Task

Load `testing` and `io-hardening`.

1. In `searchMailContacts`, bind the search text itself as the parameter and build the pattern inside the statement from the folded text: `unaccent` first, then a backslash before every backslash, `%` and `_` of the folded text (the backslash first), then `%` on both sides. Compute the pattern once per statement and use it as the right side of both `ILIKE ... ESCAPE '\'` comparisons (name and address). The text stays a bound parameter and is never concatenated into the query.
2. A search text of which folding leaves nothing (for example a lone combining mark) returns no contacts, as an empty `q` does.
3. Remove `escapeContactSearchPattern` and its unit test file `backend/packages/data/src/mail/__tests__/mailContactsSearch.unit.test.ts`; the function has no other caller and is not exported from the package.
4. Tests in `backend/packages/data/src/__tests__/mailContactsRoute.test.ts`, through `createMailContactsRouteHandler` on the runtime-role pool like the existing cases. With people whose names contain `%`, `_` and a backslash, and people whose names contain none of them: `q` set to each of `%`, `_`, a backslash, U+FF05, U+FE6A, U+FF3F, U+FF3C, U+FE68 and U+2216 returns only the people whose name or address contains the corresponding ASCII character; `q` of a lone U+0301 returns no contacts; `q` of a letter followed by U+0301 still finds a name that contains that letter. The existing cases keep passing unchanged.

## Acceptance criteria

- When `q` is U+FF05 or U+FE6A, then only contacts whose name or address contains `%` are returned; when it is U+FF3F, only those that contain `_`; when it is U+FF3C, U+FE68 or U+2216, only those that contain a backslash.
- When `q` is `%`, `_` or a backslash, then it matches only itself, as before.
- When `q` is only a combining mark, then no contact is returned.
- When `q` is "NOVAK", then a person named "Petr Novák" is still returned.
- When the names of two people differ only in one character and `q` holds a fullwidth low line in its place, then neither is returned unless its name contains `_`.
