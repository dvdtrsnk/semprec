## Context

Model tier rationale: This is the cross-process write engine for inherited values: an after-write hook, a queued tenant-lane job with batching and chained propagation, and system writes into user-owned properties under a new ownership handoff, all of which must stay idempotent, tenant-safe and loop-free.

With the rule declarations from #1411, the link storage from #1403 and the write-time rules from #1516, this issue makes inheritance happen. When a relation edge that joins a target item to a source item is created, the target takes over the source's value and a link row records where it came from. When the source's value later changes, the new value flows to every linked target. When the join edge is removed, the target keeps its value as its own.

Today nothing writes a property from another item. The only item-to-item propagation is the rollup recompute (`rollup/recompute.ts`, jobs keyed per cell) and the journal inbox recompute (`inbox/journalInboxCompute.ts`); both write only into `items.computed`, and only one step. Edge write hooks (`runRelationEdgeWriteHooks` in `chokePoint/hooks.ts`) run before the edge is written, and not at all for deletes, so they cannot observe "an edge now exists"; the dry run of an Inbox proposal (`assertRelationCreatableWithClient`, used in `inbox/proposalActions.ts`) runs them too. #1530 adds a hook that runs after an edge is written or deleted. #1415 lets this issue write as a system writer. Large background work follows `docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`, and jobs run in per-tenant lanes (`tenantLane`).

Decisions:

- Writes made by this issue are system writes with process `valueLinks`; they never change a link's state. The link row is created (state `on`) before the first value write so the handoff check from #1516 passes.
- When a via edge appears and the target already has a value for the rule's target property and no link row, the value is kept as the user's own and no link is created. Only an empty target takes over a value. This also decides the case of a file that already has projects of its own when it is attached to a task.
- A target whose link is `broken` is never written, and a later via edge does not recreate the link.
- A second via edge for a target with an `on` link adds a source and the target becomes the union of all sources' values; union applies to many-valued targets only. For a single-valued target, a source set with more than one value is not inherited: nothing is written and no link is created (an existing link keeps its last value and state).
- Removing a via edge removes that source from the link. Remaining sources recompute the union; with no source left the link row is deleted and the value stays as own.
- Propagation runs along chains (an attachment takes its project from an event and its company from that project), one hop per job. Depth is carried in the job payload and stops at 5; rules are already acyclic.

Shared-file ordering: this issue also waits for #1573 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `canonical-keys`, `error-handling` and `testing`.

1. Queue: add the task `valueLinksPropagate` (payload `{ ruleKey, sourceItemId, depth }`) to `CORE_TASK_NAMES`, `CORE_TASK_AFFINITY` (`api`) and `TASK_TENANCY` (`tenant`) in `packages/queue/src/index.ts`, and its handler to the task list in `packages/data/src/worker.ts`.
2. Add `backend/packages/data/src/valueLinks/linkRuleCatalog.ts`: a per-process memoized read of the validated rules (`loadFullModuleRegistry().getLinkRules()`) and a per-transaction resolver from a rule to property ids, relation definitions and cardinality of the target property in the tenant's schema.
3. Add `backend/packages/data/src/valueLinks/linkRuleEdgeHook.ts`: the edge-changed hook from #1530. For an edge on a rule's `via` relation it finds the target and source items (using the side each belongs to) and: on create, applies the creation rules in the decisions above; on delete, applies the removal rule. For an edge on a rule's source relation property it enqueues propagation for the source item.
4. Add `backend/packages/data/src/valueLinks/linkRuleItemHook.ts`: an item update hook that enqueues propagation when a patched plain property is a rule's source property.
5. Add `backend/packages/data/src/valueLinks/linkPropagation.ts` with the job handler: for a rule and source item it finds `on` links whose sources include that item and rule, pages through them in batches (a separate committed transaction per batch, keyset by link id, per the chunked-transaction ADR), and per link, under a row lock that rechecks the state is still `on`, recomputes the union over all live sources and writes the target property only when it differs (relation values through `createRelationWithClient` and `deleteRelationWithClient`, plain values through `updateItemWithClient`, all with the `valueLinks` system context). A trashed or missing source contributes nothing. After each batch's commit, send an item invalidation for every target whose value changed. The job key is `ruleKey:sourceItemId`, so repeated enqueues collapse; the job is idempotent and a rerun changes nothing.
6. A target write is itself a change of a source property for other rules, so it reaches the hooks from steps 3 and 4 and enqueues the next hop with `depth + 1`; do not enqueue beyond depth 5 and log once per dropped hop.
7. Register the hooks in `domainWriteHooks.ts`.
8. Tests with a fixture rule over real seeded databases: edge create copies the value and creates an `on` link with the source; a second edge produces the union; deleting an edge recomputes then, with none left, deletes the link and keeps the value; a source change flows to all linked targets and not to a `broken` one; an own value is not overwritten and gets no link; a single-valued target with two source values is untouched; a two-hop chain reaches the second target and a six-hop chain stops at depth 5; a trashed source writes nothing; rerunning the job is a no-op; the Inbox proposal dry run creates no link rows; a propagation write never changes a link to `broken`; a foreign tenant's data is never touched.

## Scope

### In scope

- Creating and removing links on via edge changes, and the system writes that copy values.
- The propagation job, its batching, chaining and depth limit.
- The hooks that trigger propagation from plain and relation source changes.

### Out of scope

- Declaring or validating rules: #1411.
- The first real rule (a file's companies from its projects): #1653.
- Other rules: #1724, #1702, #1869, #1898, #1900, #1697, #1756.
- Removing links when a source is trashed or purged: #1656.
- Rule extensions (value filters, sender-domain sources).

## Acceptance criteria

- When a via edge is created for a target with an empty rule property, then the target holds the source's value and a link with state `on` lists that source.
- When the source's property changes, then every `on` target receives the new value through the job, and the item is announced to clients after commit.
- When the target already holds its own value, or its link is `broken`, then propagation does not write it.
- When two sources feed one many-valued target, then the target holds the union; removing one source recomputes it; removing the last keeps the value as own and deletes the link row.
- When rules chain, then a change at the start reaches the end within five hops and no further.
- A dry-run proposal check creates no link; propagation never turns a link `broken`; repeated jobs are no-ops.
- Large link sets are processed in batches that commit independently.
