## Context

Caddy is the single public entry point. Its site block ends with an access log, `log { output stderr; format json }` (`deploy/Caddyfile:57-60`). Caddy's JSON access log records the full request URI (`request.uri`, query string included) and the request headers, including `Referer`. Caddy redacts `Cookie` and `Authorization` by default, but not these two.

Two secrets travel in query strings today, and both reach Caddy as plain requests it serves itself (`deploy/Caddyfile:51-55`):

- **The first-account setup link:** `/?page=setup&token=<setupToken>` (`backend/services/semprec-api/src/routeMatrix.ts:100`, `web/src/main.tsx:26`).
- **The password-reset link:** `/reset-password?token=<token>`, built by `buildPasswordResetUrl` (`backend/packages/data/src/auth/passwordResetActions.ts:31-38`).

After either page loads, every same-origin asset request the browser makes carries the full page URL in `Referer`. So the token lands in the log again, once per asset. The log goes to the systemd journal, kept for 90 days on persistent storage (`deploy/README.md:113-118`). Anyone with journal access can replay a live setup or reset token from it.

This is one of the pre-existing defects fixed first in the multi-tenancy program. That program adds more token-bearing links:
- invitations (#1040, #1088) put their token in the URL fragment;
- #1076 moves the reset token into the fragment as well.

A fragment never reaches the server. This issue makes the access log safe whatever URL shape a client uses.

Caddy is installed from the distribution's own package (`deploy/provision.sh:97`; no Caddy apt repository is added, `:67-83`). The configuration must therefore use filter syntax that older Caddy 2 releases accept. Provisioning runs `caddy validate` (`deploy/provision.sh:275`), so a configuration that does not parse would fail provisioning.

## Task

Load `io-hardening`: secrets must never reach logs, and this edits the edge proxy.

1. In `deploy/Caddyfile`, change only the `log` block (`:57-60`). Keep `output stderr`, and wrap the JSON encoder in Caddy's `filter` encoder using the `fields { … }` block form:
   - apply a `regexp` filter to `request>uri` that removes the first `?` and everything after it, for example `request>uri regexp "[?].*" ""`;
   - apply `request>headers>Referer delete`.

   Every other field stays as it is: method, host, path, status, size, duration, remote address. Add a comment above the block naming the two token-bearing URLs and why `Referer` is dropped.
2. Add `deploy/Caddyfile.test.sh`, a hermetic behaviour test in the style of the other `deploy/*.test.sh`.
   - Use `set -euo pipefail`. It requires `caddy` on `PATH`: when the binary is missing, it exits non-zero with a message saying so.
   - Copy `deploy/Caddyfile` into a `mktemp -d` directory, prepending a global options block `{ admin off }` so that no admin port is bound.
   - Start `SEMPREC_DOMAIN=http://127.0.0.1:<free port> caddy run --config <copy> --adapter caddyfile` in the background, with stderr to a file in that directory. Record its `$!`.
   - Wait for the port to answer, bounded by a timeout. Then request `http://127.0.0.1:<port>/reset-password?token=QUERY-SECRET-<random>` with the header `Referer: http://127.0.0.1:<port>/?page=setup&token=REFERER-SECRET-<random>`.
   - Stop only that PID, then assert:
     - the log has an access entry with `"method":"GET"`, `"uri":"/reset-password"` and a `"status"` field;
     - neither secret string appears anywhere in the log.
   - Clean up in a `trap` that kills only the recorded PID. Never use `pkill`, `killall` or pattern matching.
   - Run it locally before pushing; install `caddy` from the distribution package if needed.

## Scope

### In scope
- Filtering `request>uri`'s query string and `request>headers>Referer` out of the access log, plus the behaviour test.

### Out of scope
- Moving the password-reset token into the URL fragment: #1076.
- Invitation links: #1040, #1088.
- Rate limits on token-consuming endpoints: #1073.
- Response headers such as `Referrer-Policy`, the request-body limits and the reverse-proxy routes. Every other part of `deploy/Caddyfile` stays unchanged.
- `deploy/README.md`, `deploy/provision.sh` and `deploy/provision.test.sh`.
- Caddy's own runtime/error log configuration.

## Acceptance criteria

- When Caddy serves a request whose URI carries a query string, the access log entry keeps the method, the path (as `uri` without `?…`) and the status, and contains no part of the query string (script, `deploy/Caddyfile.test.sh`).
- When a request carries a `Referer` header with a token-bearing URL, no part of that header appears in the access log (script, same test).
- When `caddy` is not on `PATH`, `deploy/Caddyfile.test.sh` exits non-zero and says so (script).
- `SEMPREC_DOMAIN=example.test caddy validate --config deploy/Caddyfile --adapter caddyfile` succeeds, the same check `deploy/provision.sh:275` runs (script, run by hand).
- `git diff` of `deploy/Caddyfile` touches only the `log` block and its comment (review).
