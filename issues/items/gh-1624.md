## Context

Model tier rationale: It adds a second queue worker beside a deliberately single-concurrency pipeline, so the new task, lane and affinity must provably not add parallel ffmpeg/ASR runs while staying idempotent with the job that remains a safety net.

Today the Transcripts row is created by `runCreateStep` at the start of `transcriptionJob` (`backend/services/semprec-transcribe/src/transcriptionTask.ts`): `name`, `status processing`, `link`, idempotency key `transcription:<fileItemId>` and the `computed.create` checkpoint on the Files item; `date` follows only in the prepare step. `semprec-transcribe` runs one `runWorker` with concurrency 1 and a task list holding only `transcriptionJob` (`queueRuntime.ts`: "One ffmpeg/ASR pipeline per host"). The per-tenant lane `transcription:<tenantId>` (`transcription/transcriptionJob.ts`, `docs/adr/2026-10-08-per-tenant-queue-lanes.md`) serializes a tenant's jobs but adds no slots. Every task must be listed in `CORE_TASK_NAMES`, `CORE_TASK_AFFINITY` and `TASK_TENANCY` in `backend/packages/queue/src/index.ts`. A new recording therefore waits behind a running long job (tens of minutes for a 1.5 h meeting) and is not even listed.

This issue creates the Transcripts row immediately: a new fast task `transcriptionCreate` on its own lane and its own small worker. A just-uploaded recording appears as "processing" within seconds, with a provisional `date`, even while another recording is being transcribed. It builds on #1574 (`recorded_at`) and unblocks #1644, #1830, #1978, #1696, #1940 and #1942.

Decision: short LLM tasks (speaker suggestion, card recompute) do not run in this fast worker, because a gateway call would delay `transcriptionCreate`; whichever of #1942 or #1940 lands first adds a third worker for them.

## Task

Load `state-writes`, `testing` and `error-handling`.

1. In `packages/queue/src/index.ts` add task `transcriptionCreate` to `CORE_TASK_NAMES`, `CORE_TASK_AFFINITY` (`transcribe`) and `TASK_TENANCY` (`tenant`), with a lane `transcription-create:<tenantId>` built like `tenantLane`.
2. In `services/semprec-transcribe/src/queueRuntime.ts` start a second `runWorker` with a task list holding only `transcriptionCreate` (concurrency 1). The main runner keeps concurrency 1 and only `transcriptionJob`. Extend `assertTaskListMatchesAffinity` to check every task list.
3. Add `enqueueTranscriptionCreate` beside `enqueueTranscriptionJob`. Its handler reuses `runCreateStep` and writes provisional Transcripts `date` from `recording_requests.recorded_at ?? sourceBlob.createdAt`, `ensureItemAutomation` and Files `computed.create`. The fallback is canonical first blob storage time, which dedup may place before this request. Prepare later refines `date`; only `semprec-transcribe` writes.
4. Enqueue `transcriptionCreate` in the same transaction as `transcriptionJob` in every producer: `POST /api/recordings` (#1574) and `core.filesTranscriptionTrigger`. `transcriptionJob` still calls `runCreateStep` idempotently as a safety net; requeue and rerun are unchanged.
5. A newly created row invalidates Transcripts over realtime as every choke-point create does.
6. Tests: the row exists while the main worker is busy with another job; if `transcriptionCreate` never runs, the job creates the row and no second row appears; the main runner never runs two pipelines at once.

### Out of scope

- Writing the transcript-to-event edge in the create step: #1644.

- Confirming a card that proposes transcribing an attachment: #1978.

## Acceptance criteria

- When a recording is uploaded while the worker is processing another 1.5 h recording, then within 5 seconds a Transcripts query returns its row with status `processing`.
- When `transcriptionCreate` does not run, then `transcriptionJob` creates the row and no second row exists.
- At most one ffmpeg/ASR pipeline runs on a host at a time.
