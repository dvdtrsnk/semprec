**Blocked by:** #21, #115

## Context

The generic data engine stores relation values in `item_relations`, outside `items.properties`. The completed foundation exposes relation edge writes through `createRelationWithClient`/`deleteRelationWithClient` and the public facade, but the input names the caller's item as `itemId`, there is no metadata update operation, delete returns the deleted row, and no endpoint validation exists: an edge may reference a missing, soft-deleted, reversed, or cross-database item, and PostgreSQL foreign keys cannot help because `items` has a partitioned composite primary key.

This is the first of three parts of the relation-integrity work. It fixes the edge contract itself: normalized types, idempotent create/update/delete semantics, and endpoint validation. #212 builds on it by adding relation-definition ownership, the `SystemRelationWriteContext`, and protected entry points; #82 then enforces cardinality under concurrency and repairs canonical relation-property config.

## Task

Harden the generic choke-point relation edge path as one transactional contract:

- Standardize edge types as `RelationEdge = { id: string; relationDefinitionId: string; itemA: string; itemB: string; metadata: Record<string, unknown> }`, `CreateRelationInput = { relationPropertyId: string; callerItemId: string; targetItemId: string; metadata?: Record<string, unknown> }`, and `UpdateRelationInput = { relationPropertyId: string; callerItemId: string; targetItemId: string; metadata: Record<string, unknown> }`. The triple `(relationPropertyId, callerItemId, targetItemId)` identifies an edge from the caller's side and is normalized to the stored definition/item A/item B tuple.
- On create, update-metadata, and delete, the operation must name `relationPropertyId`; that exact property identifies the caller's side of the definition (ownership authorization through that property is added in #212). Normalize paired-property calls so `property_id_a` maps the caller item to `item_a` and `property_id_b` maps it to `item_b`.
- Endpoints are immutable: moving an edge is delete plus create. Create is idempotent on the normalized unique tuple and replaces the entire metadata object when the edge already exists; omitted create metadata means `{}` and therefore also replaces existing metadata with `{}`. Update requires an existing normalized edge, replaces metadata in full (never merges JSON), and otherwise returns `404 not_found` with `{ resource: 'relationEdge', relationPropertyId, callerItemId, targetItemId }`. Both return the normalized `RelationEdge`. Delete is idempotent and returns `void` whether or not the edge existed.
- Expose these operations in the data package as the transactional building blocks `createRelationWithClient(client, input: CreateRelationInput): Promise<RelationEdge>`, `updateRelationWithClient(client, input: UpdateRelationInput): Promise<RelationEdge>`, and `deleteRelationWithClient(client, input: Omit<CreateRelationInput, 'metadata'>): Promise<void>`; the public-facade methods `createRelation`, `updateRelation`, and `deleteRelation` use these same input/output shapes. (#212 adds a mandatory context parameter to the `*WithClient` functions and makes them protected; in this part they keep no context argument.)
- Rename all current `itemId` call sites of relation edge inputs to `callerItemId` (the mail ingest/draft/send/attachment/folder-discovery/reconcile/person-linking writers, `tasks/advanceTaskRecurrence`, and every other caller); no relation edge input may still accept `itemId`.
- Validate that both item IDs exist, are not soft-deleted, and belong to the source and target databases declared by the relation properties. Edge validation loads the named property, treats its own `database_id` as the caller/source database, and reads/validates `config.targetDatabaseId` as the target database; it never infers the target from a missing inverse row. A named property whose config lacks a valid `relationDefinitionId` or `targetDatabaseId` is rejected at load with `validation_failed`. Reject dangling, reversed, or cross-database endpoints with `validation_failed`.
- Add real-Postgres integration tests for invalid endpoints (missing, soft-deleted, reversed, wrong database) and for every edge contract above (duplicate create, missing update, full metadata replacement, immutable endpoints, normalized return shape from both sides of a paired definition, idempotent delete).

## Scope

### In scope

- Relation edge input/output types, normalization, idempotent create/update/delete semantics, and the `callerItemId` rename across the codebase.
- Endpoint existence, soft-delete, and database-membership validation through the choke-point.

### Out of scope

- Per-side relation-definition ownership (`owner`, `ownerProcess`, `locked`), `SystemRelationWriteContext`, protected entry points, `owner_violation` rejection, and migrating internal callers to registered process identities; #212 delivers these.
- Cardinality enforcement under concurrency, additive indexes/constraints, canonical relation-property config persistence, one-directional `targetDatabaseId` validation, and the fail-loud config repair migration; #82 delivers these.
- REST routing; issue #37 projects this corrected choke-point behavior over HTTP.
- Module registry and PostgreSQL runtime roles; issues #29 and #40 own those boundaries.
- Domain-specific relation rules.

## Acceptance criteria

- An edge cannot reference a missing, deleted, reversed, or wrong-database item; each rejection is `validation_failed`.
- Duplicate create, missing update, full metadata replacement, immutable endpoints, normalized return shape, and idempotent delete follow the exact contracts above, and a call through `property_id_b` returns the same normalized `RelationEdge` as the equivalent call through `property_id_a`.
- A relation property with missing or invalid `relationDefinitionId`/`targetDatabaseId` config is rejected with `validation_failed` instead of inferring a target.
- No relation edge input in the codebase accepts `itemId`; every caller passes `callerItemId`.
- The new integration tests reproduce the former gaps and pass against real PostgreSQL.
