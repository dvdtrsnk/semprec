## Context

Model tier rationale: one extra user-owned edge in human confirm plus rerun regression guards. Speaker cards use transcript-speaker-suggestion:<transcriptId>:<speaker>, proposeSpeakerMappings, and the Transcripts speakers edge with speaker metadata; #1640 allows nonparticipants and no Event. Confirm also adds the chosen person to a linked Event's user-owned many-to-many people relation if absent. Both edges and history commit together; failure leaves the card proposed. Preserve existing participant metadata under concurrent ordinary writes via the existing relation owner, not a precheck/upsert. Existing keys prevent rejected/trashed cards returning while labels remain stable across checkpoint resumes; no new storage or label-changing rerun guarantee. Future label changes belong to their own issue.

## Task

Load `state-writes`, `testing` and `canonical-keys`.

1. In `confirmProposalWithClient`, in the branch that writes a transcript card's `speakers` edge, after that edge is written resolve the transcript's linked Event (the Transcripts `event` relation). If there is one and the person has no `Events.people` edge to it, ensure it through the internal createRelationIfAbsentWithClient choke-point sibling as the confirming human (no system context). This sibling shares existing validation/admission, inserts without replacing a conflicting edge's metadata, and emits insertion effects only when inserted. Ordinary createRelationWithClient metadata replacement is unchanged. Record only an actually inserted extra edge in the confirm history's optional addedRelations list ({edgeId, relationPropertyId, callerItemId, targetItemId}, UUIDs); absence remains backward-compatible.
2. Keep the confirm idempotent: confirming an already confirmed card returns it unchanged and writes nothing further.
3. Do not change how `proposeSpeakerMappings` creates cards or its key. Add tests that call it again after a card was rejected and after a card was soft-deleted and assert that no new card for that speaker key is created, and that a second speaker key still gets its card.
4. Tests for item 1: a person who is not a participant is added in the same transaction as the `speakers` edge; a participant is not added twice; a transcript without an Event gets only the `speakers` edge; a failing Event edge write rolls back the `speakers` edge and leaves the card `proposed`.

## Acceptance criteria

- When a speaker card is confirmed with a person who is not in the linked Event's `people`, then the `speakers` edge with `{ speaker }` and the `Events.people` edge both exist after the confirm.
- When the person is already a participant, then no second edge is created.
- When the transcript has no linked Event, then only the `speakers` edge is written.
- When a speaker card was rejected or trashed and the transcription is rerun, then no card for that speaker key is created again.
