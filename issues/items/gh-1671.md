## Context

Model tier rationale: Two small, related changes to the speaker-card lifecycle (an extra edge in the same confirm transaction and a regression guard across reruns), each with existing fixtures, but the confirm writes a user-owned edge that no process wrote before.

A speaker card asks "who is Speaker 3?" and, once confirmed, writes a `speakers` edge from the transcript to a person with `{ speaker }` metadata (`confirmProposalWithClient` in `backend/packages/data/src/inbox/proposalActions.ts`; the edge rules are in `backend/packages/data/src/transcription/transcriptionSpeakerEdges.ts`). Cards are created by `proposeSpeakerMappings` in `backend/packages/data/src/transcription/transcriptSpeakerSuggestion.ts`, one per speaker key, with idempotency key `transcript-speaker-suggestion:<transcriptId>:<speaker>`. #1640 extends the card so it can name a person who is not a participant of the linked Event, or when there is no Event. Two gaps remain around it.

1. The linked Event's participants (`Events.people`, a user-owned many-to-many) do not include the chosen person, so the transcript names a speaker who is not on the meeting. A background process must not write this user-owned relation, but a human confirm may.
2. A card the user rejected or trashed must not come back after the transcription is rerun. The idempotency key already blocks a second card for the same speaker key, whatever the status of the first, as long as a rerun keeps the speaker labels. A rerun that resumes from the stored checkpoints keeps them (segments are written once), but nothing pins this down.

Decision: the confirm adds the person to `Events.people` only when the transcript has a linked Event and the person is not already among its participants. With no linked Event it writes the `speakers` edge only.

Decision: both edges are written in the confirm's own transaction; if the Event edge write fails, the whole confirm fails and the card stays `proposed`.

Decision: the memory of rejected speakers is the existing idempotency key, with no new storage. If a future change lets a rerun produce different speaker labels, the label change itself must be handled by that change; this issue only pins the current behavior with tests.

## Task

Load `state-writes`, `testing` and `canonical-keys`.

1. In `confirmProposalWithClient`, in the branch that writes a transcript card's `speakers` edge, after that edge is written resolve the transcript's linked Event (the Transcripts `event` relation). If there is one and the person has no `Events.people` edge to it, create that edge through `createRelationWithClient` as the confirming human (no system relation context). Record the extra edge in the card's `history` entry for the confirm.
2. Keep the confirm idempotent: confirming an already confirmed card returns it unchanged and writes nothing further.
3. Do not change how `proposeSpeakerMappings` creates cards or its key. Add tests that call it again after a card was rejected and after a card was soft-deleted and assert that no new card for that speaker key is created, and that a second speaker key still gets its card.
4. Tests for item 1: a person who is not a participant is added in the same transaction as the `speakers` edge; a participant is not added twice; a transcript without an Event gets only the `speakers` edge; a failing Event edge write rolls back the `speakers` edge and leaves the card `proposed`.

## Scope

### In scope

- The extra `Events.people` edge in the speaker confirm, and tests that keep rejected or trashed speaker cards from returning after a rerun.

### Out of scope

- Asking about every unmapped speaker, citations and alternatives (#1640), and suggesting again when an Event gains participants (#1942).
- Manual assignment and excluding a person already assigned to another speaker (#1770).
- Creating a new person from the card (#1870).
- Any change to the speaker labels a rerun produces.
- A job-title property on People: not in v1; a position is written in the person's note.

## Acceptance criteria

- When a speaker card is confirmed with a person who is not in the linked Event's `people`, then the `speakers` edge with `{ speaker }` and the `Events.people` edge both exist after the confirm.
- When the person is already a participant, then no second edge is created.
- When the transcript has no linked Event, then only the `speakers` edge is written.
- When a speaker card was rejected or trashed and the transcription is rerun, then no card for that speaker key is created again.
