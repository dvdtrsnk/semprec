# Public REST API: generic endpoints over the choke-point

## Context

Issues 1–16 built the data layer (databases/properties/views/items, `item_relations`, the `blobs` layer with `content_hash` dedup, soft-delete/trash), the module layer (ModuleRegistry, the `semprec-api` process, dependency-cruiser boundaries), and the agent layer (AgentTool, the approval queue, auth/session). Every write already goes through a single choke-point package (`createItem`, `updateItem`, `query`, …) that itself enforces `owner`, `locked`, idempotency, and `ifVersion` — but that package has no HTTP projection yet. This is the only surface through which **everything** talks to the backend: the web UI, the native iOS/macOS app, Shortcuts, agents (AgentTool), and external MCP clients. This task builds that projection: four generic concepts (database, property, view, item), a closed set of operations over them, and an explicit rule for when an endpoint is allowed to exist outside that set. It is the last piece before the realtime layer — issue #38 (WebSocket) builds on top of this, but is a different mechanism (request/response vs. streamed events) and ships separately.

Central principle: **no module, project, or new feature ever needs its own CRUD routes.** Their data is always databases + properties + views, and the generic surface already serves all of it. This is not just a savings in code — it is the same determinism as everywhere else in the system: one surface means one place where `owner`/`locked`/idempotency are enforced, and zero places where enforcement could be forgotten.

## Task

Implement the generic REST surface in the `semprec-api` process as a thin adapter over the existing choke-point package — the adapter must contain no business logic of its own, only mapping of the HTTP request onto the service function and of the result onto the HTTP response. Specifically:

1. **Metadata endpoints** over databases, properties, and views (list/create/detail/patch/delete, with archiving instead of hard delete).
2. **Item endpoints** — create with an `Idempotency-Key` header, detail (with optional `?include=path` for a breadcrumb), patch with `ifVersion` merge by key, soft-delete into trash with cascade, restore symmetric to the cascade.
3. **Query endpoints** — `POST /api/databases/:id/query` and `POST /api/views/:id/query`, both over the typed filter/sort tree, both with keyset pagination (`cursor`/`nextCursor`), producing an identical response shape whether the source is an ad-hoc filter or a stored view configuration.
4. **Relations** — `PUT`/`DELETE /api/items/:id/relations/:propertyKey/:targetItemId` over `item_relations`.
5. **Files** — the one binary surface next to the JSON API: `POST /api/files` (streamed upload, sha256 dedup via `content_hash`) and `GET /api/blobs/:id` (authenticated streamed download with Range/ETag).
6. **A single row shape** — every item in the same envelope (`id, databaseId, properties, computed, updatedAt, deletedAt`); every successful write returns the full authoritative row state (never an empty 204).
7. **A single error contract** — `{ error: { code, details } }` with a closed enum of `code` values.
8. **The escape-hatch rule for non-generic endpoints** — the mechanism (ModuleRegistry manifest, mounting at startup, process crash on path collision) by which the named exceptions (`/api/proposals/:id/confirm`, `/api/inbox-types`, push registration — existing; `/api/ai-usage` — delivered by issue #30) and the new ones (`/api/files`, `/api/blobs/:id`) demonstrably satisfy the law: a custom route may only exist for an action with its own transactional semantics, or for a read shortcut shaped for exactly one consumer — never for CRUD over module data.

## Scope

### In scope

- `GET/POST /api/databases`, `GET/PATCH/DELETE /api/databases/:id` (DELETE = archive; a `system: true` database returns 403 on both archive and delete)
- `POST /api/databases/:id/properties`, `PATCH/DELETE /api/properties/:id` (`schema_locked`/`locked` → 403; changing `type` → 202 plus an async `migration_status` job)
- `POST /api/databases/:id/views`, `PATCH/DELETE /api/views/:id`, `PUT/DELETE /api/views/:id/items/:itemId` (curated view membership — add/reposition/remove)
- `POST /api/databases/:id/items` (`Idempotency-Key` header → 201 with the full row)
- `GET /api/items/:id` (`?include=path` for a breadcrumb; the server assembles the ancestor chain by recursively walking `parent_item_id`, the client never assembles hierarchy itself)
- `PATCH /api/items/:id` (body `{ properties, ifVersion }`, merged by key; a version mismatch returns 409 with `details.currentItem`)
- `DELETE /api/items/:id` (soft delete; cascades to any inline databases under the page and their rows, in one transaction)
- `POST /api/items/:id/restore` (restores the whole subtree, symmetric to the delete cascade)
- The 30-day trash purge: a `graphile-worker` task (registered via `registerTask` on the queue engine from issue #21) that permanently deletes items whose `deleted_at` is older than 30 days, including their cascade subtree — the trash semantics (cascade delete, symmetric restore, purge) live in this issue as one whole
- `POST /api/databases/:id/query` and `POST /api/views/:id/query` (body `{ filter, sort, cursor, limit }` → `{ items, nextCursor }`; keyset pagination, default `limit` 50, max 200; deleted rows excluded by default, `inTrash: true` opts in explicitly)
- `PUT/DELETE /api/items/:id/relations/:propertyKey/:targetItemId`
- `POST /api/files` (raw binary stream in the body, `Content-Type` + `X-Filename` headers, sha256 computed as the stream passes through, dedup via `content_hash`, blob + Files row created in one transaction, deterministic pick of an existing row by lowest `id` when one already references the blob)
- `GET /api/blobs/:id` (authenticated stream; `ETag` = `content_hash`; `Range` support; `Content-Disposition` built from `?filename=`; `?disposition=inline` honored only for an allowlist of safe MIME types, always with `X-Content-Type-Options: nosniff`)
- Upload size limit (`maxFileSizeMb` in System Settings) enforced twice — a fast rejection based on `Content-Length`, and a hard cut via a byte counter during the stream itself
- The unified item envelope and unified error contract (`{ error: { code, details } }`) with a closed set of codes (`owner_violation`, `computed_readonly`, `schema_locked`, `property_locked`, `version_conflict`, `validation_failed`, `not_found`, `approval_required`, `heartbeat_event_triggered`)
- The ModuleRegistry mechanism for mounting module routes into the flat `/api/` namespace, with fail-fast on path collision at startup
- The dependency-cruiser rule: only the choke-point package may import a DB client for writes to `items`/`databases`/`properties`

### Out of scope

- **WebSocket and any realtime/streamed traffic** — `/api/sync` (Yjs CRDT), invalidation events, and anything from the "four kinds of traffic" belongs entirely to issue #38. This task builds only the request/response REST layer; ongoing changes from other sources (agent, heartbeat, a second device) are deliberately not delivered by this surface.
- Presigned MinIO URLs for upload/download (considered and rejected — see Reference below)
- A generic batch endpoint for bulk writes (considered and rejected — Idempotency-Key already solves the underlying problem)
- URL versioning (`/api/v1/…`) — replaced by an evolutionary rule: contract changes are additive only
- The MCP-over-HTTP adapter and AgentTool tools — they share the same choke-point package and the same catalog of operations, but are separate adapters outside this task; this task produces only the REST projection
- A resumable/chunked upload protocol (tus and similar) — deliberately not introduced for v1
- A total storage quota — only a per-file limit is enforced; disk-usage quota is an observability concern, not application logic

## Dependencies

- **Issue #21 (data layer)**: the choke-point package and its functions (`createItem`, `updateItem`, `query`, …) must already exist and enforce `owner`/`locked`/idempotency/`ifVersion` at the service level — the REST adapter re-implements none of that, it only calls it. It also needs, already in place: the `databases`/`properties`/`views`/`items` schema with `parent_item_id` hierarchy, the `item_relations` table (not a jsonb value), the `blobs` layer with a `content_hash` unique partial index, the `deleted_at` soft-delete column and schema basics (only that — the 30-day purge job itself is delivered by this issue, see In scope), and `migration_status` for asynchronous property-type changes. #21 also supplies the queue engine (`packages/queue`, `registerTask`/`enqueueJob` over `graphile-worker`) that the purge job here registers into.
- **Issue #34 (auth)**: session/Bearer authentication (httpOnly cookie on the web, Bearer token from Keychain in the iOS/macOS app) must already exist, because every REST endpoint — `GET /api/blobs/:id` above all — authenticates by calling that same auth layer. It also needs the `approval_required` mechanism (the approval queue) so that the HTTP/MCP adapter can return the `approval_required` error as a 403 with a link to the resulting request (unlike the in-process AgentTool adapter, which translates it into a synthetic success instead).
- Implicitly, also the ModuleRegistry and the `semprec-api` process (module layer, issues 1–16) — REST routes are mounted into it at startup.

## Reference to the specification

`vize/backend.html`, lines 5237-5701.

**Principle "resource + operation, no endpoint per domain"** — the surface is built over four generic concepts (database, property, view, item) and a closed set of operations over them, never over domain-specific names. That yields a concrete path shape:

- `/api/databases`, `/api/databases/:id`, `/api/databases/:id/properties`, `/api/properties/:id`, `/api/databases/:id/views`, `/api/views/:id`, `/api/views/:id/items/:itemId` — the metadata layer
- `/api/databases/:id/items`, `/api/items/:id`, `/api/items/:id/restore` — rows
- `/api/databases/:id/query`, `/api/views/:id/query` — querying via POST body (the typed filter/sort tree from the views/filters issue, not a querystring — a second query language is explicitly unwanted)
- `/api/items/:id/relations/:propertyKey/:targetItemId` — relations

Paths stay **flat regardless of nesting depth** — `parentItemId` is a data relationship, not routing; `/api/items/:id` works identically for a row in a top-level database and for one five levels deep inside inline databases. The breadcrumb is served by `?include=path`; the server assembles the ancestor chain, the client never assembles hierarchy itself. An endpoint outside this catalog may only exist for an action with its own transactional semantics (a cross-database write in one transaction, an aggregate read outside the item model, a binary upload) or for a read shortcut shaped for one specific consumer — never for CRUD over module data; that is enforced by registration through the ModuleRegistry manifest with a process crash on path collision, not a runtime decision.

**Files as the one binary surface next to the JSON API** — two legitimate exception endpoints:

- `POST /api/files`: the body is a raw binary stream (not multipart), metadata lives in headers (`Content-Type`, URL-encoded `X-Filename`). The stream is piped through `stream/promises pipeline()` (backpressure, never the whole file in memory) into a temporary MinIO object and simultaneously through a sha256 hasher. Once the stream finishes, one transaction: look up `blobs.content_hash` — a match means discarding the temp object and using the existing blob; a new hash means moving the object to `blobs/<sha256>` and creating the `blobs` row. If an undeleted Files row already references this blob, that row is returned (200, deterministically the lowest `id`); otherwise a new row is created via `createItem` (201). Upload idempotency falls out of content-addressed dedup for free — stronger than an `Idempotency-Key` header, since it works across devices and sessions, not just for retrying one request.
- `GET /api/blobs/:id`: an authenticated stream (the same identity check as the rest of the surface — cookie/Bearer), `ETag` = `content_hash` (`If-None-Match` → 304), `Range` reads from MinIO for scrubbing/resuming, `Content-Disposition` from `?filename=` (RFC 5987 for diacritics), default `attachment`, `inline` only for an allowlist of safe MIME types plus `nosniff` (otherwise a stored-XSS risk).
- Presigned MinIO URLs were deliberately rejected: on infrastructure grounds (MinIO is not publicly exposed), on enforcement grounds (dedup/limit checks would be bypassable and would have to run as a post-hoc job trusting client-declared metadata), and on auth grounds (a presigned URL is a bearer-capability link outside the revocable `sessions` table).
- A `files` property type on any database other than Files/cover carries a relation to Files rows, not a `blobId` directly — attaching a file is upload + the existing `PUT /api/items/:id/relations/...`, no new endpoint.
- The `maxFileSizeMb` limit (default 2048, empty = no limit) is enforced twice (`Content-Length` check plus a streamed byte counter); there is no total storage quota.

**Other load-bearing decisions the REST layer must honor:**
- The unified item envelope `{ id, databaseId, properties, computed, updatedAt, deletedAt }`; `computed` is read-only (403 on write attempts); `updatedAt` doubles as the `ifVersion` token for the next update — no separate `version` counter.
- Every successful write returns the full authoritative row state (never an empty 204) — offline-first clients never need a second GET.
- Keyset pagination (`cursor`/`nextCursor`), not offset — offset would skip or duplicate rows under concurrent writes.
- The error contract `{ error: { code, details } }` — `code` is a stable, machine-readable enum (a contract primarily for agents), text localization happens client-side; `version_conflict` carries `details.currentItem`.
- Three adapters over one choke-point (REST + MCP-over-HTTP in `semprec-api`, AgentTool in `semprec-agents`) — an adapter must contain no business logic, only mapping; this rule is enforced by a dependency-cruiser boundary, not by convention.
- URL versioning was rejected — replaced by additive contract evolution (new fields/endpoints/error codes, never a breaking change without a transition period).
- A generic batch endpoint was rejected — a sequence of idempotent requests (Idempotency-Key) plus HTTP/2 multiplexing already solves the problem it would address.
