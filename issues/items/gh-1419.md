## Context

Model tier rationale: A single read-path change, but it protects a persisted-data contract that a one-release rollback depends on, so the unknown-kind behavior must be verified on every read and confirm path.

Stored cards carry {entityKind,target,properties}. The existing closed envelope parser throws on future kinds; the read/confirm switch is exhaustive.

The next releases introduce new envelope kinds (the first one is `journalEntry`, written by #1975). Under the repository's rollback rule (`docs/adr/2026-09-24-rollback-one-release-back-with-checked-migrations.md`), the release that is rolled back to must already be able to read what the newer release wrote. So this issue ships first, alone: a release in which a stored envelope with an unknown `entityKind` does not break reading, while no code yet writes such an envelope. Only a later release may start writing a new kind.

Decision: an unknown kind is displayed, never executed. The card is shown with its stored envelope untouched and cannot be confirmed (confirm answers 409). Revise of such a card is also refused with the same 409, because the running release cannot validate a kind it does not know.

This issue is the first link of the journal-entry chain; #1975 builds on it.

## Task

Load `error-handling`, `state-writes` and `testing`.

1. In `inboxTickAction.ts`, change the stored-envelope reading so that a well-formed envelope object (`entityKind` string, `target` string, `properties` object) with an `entityKind` outside `pageContent | database | relation` parses successfully into a distinct "unknown kind" shape instead of throwing. A truly malformed envelope (wrong shape) still throws `Malformed proposal envelope`. The write-side schema used by the tick and by revise stays strict: unknown kinds are still rejected when written by this release.
2. In `proposalActions.ts`, make every read path that parses a stored envelope (card listing/serialization, `assertValidEnvelopeForCard`, the confirm and revise entry points) handle the unknown shape without throwing: the card is returned as stored; `confirmProposalWithClient` and `reviseProposalWithClient` answer a conflict error that maps to HTTP 409 with public primitive details {field:"entityKind",entityKind} identifying the unsupported kind. Retain its descriptive internal message and existing public error envelope/code. Keep the `never` guard in the exhaustive `switch` meaningful (handle the unknown shape before it).
3. Do not add any new entity kind, schema, or writer in this issue.
4. Add tests in `backend/packages/data/src/__tests__/proposalActions.test.ts` (and `inboxTickProposal.test.ts` if the tick reads envelopes): a card whose stored envelope has `entityKind: "someFutureKind"` is listed and read without error, confirm returns 409, revise returns 409, and the card stays in its proposed state; a structurally malformed envelope still throws. Verify confirm through authenticated HTTP: exact conflict details and unchanged card/target state. Test revise at its existing data entry point; do not add a route.

## Acceptance criteria

- When a stored proposal envelope carries an unknown `entityKind` but is otherwise well-formed, then listing and reading the card succeeds and returns the envelope unchanged.
- When such a card is confirmed over HTTP, then the response is 409 with details.entityKind naming the unsupported kind, the card is not transitioned and nothing is written to the target.
- When such a card is revised, then the response is 409 and the stored envelope is unchanged.
- When a stored envelope is structurally malformed, then reading still fails with `Malformed proposal envelope`.
- When the tick or revise writes an envelope with an unknown kind, then it is still rejected as before.
