## Context

Model tier rationale: It adds a validation contract on a user-writable relation edge where only the server may change one part of the metadata, which is an authorization and ownership boundary on a public write path, and a new read endpoint over the same data.

An Event's participants are the edges of `Events.people` (many-to-many, one-directional, declared in `backend/packages/data/src/seed/seedTenDatabases.ts`). Each edge can carry free-form `metadata`: `PUT` of a relation edge accepts `{ metadata }` for any relation (`backend/services/semprec-api/src/itemsHandler.ts`), and `createRelation` replaces the stored metadata as a whole (`ON CONFLICT ... DO UPDATE SET metadata = EXCLUDED.metadata` in `backend/packages/data/src/chokePoint/relationsStore.ts`). The only validation of edge metadata today is `transcriptSpeakerEdgeWriteHook` (`backend/packages/data/src/transcription/transcriptionSpeakerEdges.ts`), registered in `backend/packages/data/src/domainWriteHooks.ts`. A client also cannot list an Event's participants: relations are not part of the item response, and People has no inverse of `Events.people` until #1664 adds it.

This issue gives the edge a defined shape: the participant's role and, for a person who was invited by email, the state of that invitation. It also adds the read endpoint that returns the participants together. Later issues build on it: #1790 writes invitations in bulk, #1774 sends them and records `sentAt`, #1950 records replies, and #1770 uses the "invited" state when it picks transcript speakers.

Edge metadata shape (all keys English camelCase):

```
{ role?: "organizer" | "attendee",
  invitation?: { status: "pending" | "accepted" | "tentative" | "declined",
                 email: string, mailboxId: uuid,
                 sentAt?: ISO instant, respondedAt?: ISO instant } }
```

An edge without `invitation` is a plain link between the Event and a person: nothing is sent to that person. An edge with `{}` metadata (every existing edge) stays valid and means role `attendee`, no invitation.

Decision: `invitation` can be set or changed only by server code that writes with the system writer kind (#1415). A public write (the generic edge `PUT`) must carry the `invitation` object exactly as already stored, or omit it when none is stored; anything else is rejected with 400 `validation_failed`, never silently overwritten. This is needed because the edge `PUT` replaces the whole metadata object.

Decision: `role: "organizer"` is valid only on the edge to the person that #1509 links to the tenant's user, and an Event has at most one organizer edge. An organizer edge is a link only: it carries no `invitation` and is not copied into a recording's people or into task people.

Ownership handoff (`docs/adr/2026-09-10-single-writer-ownership-model.md`): the `invitation` part of this metadata has exactly one writer, the calendar module's invitation code (#1790, #1774 and #1950), always with the system writer kind. This is recorded in the calendar module manifest.

Shared-file ordering: this issue also waits for #1756, #2032 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `canonical-keys` and `testing`.

1. Add `backend/packages/data/src/calendar/eventParticipantEdgeHook.ts` exporting `eventParticipantEdgeWriteHook: RelationEdgeWriteHook`, modeled on `transcriptSpeakerEdgeWriteHook`. It applies only to the `people` property of the Events database and runs on add and on metadata replace (not on removal). It rejects, with `ValidationError` (`field: "metadata"`, a stable `reason` such as `invalidParticipantMetadata`, `invitationReadOnly` or `organizerNotSelf`): unknown keys, an invalid `role`, an invalid `invitation` shape, an `invitation` on an organizer edge, an organizer edge to anyone but the self person, a second organizer edge on the same Event, and, when the writer kind is not system, any `invitation` that differs from the stored one (read the current edge with `relationsStore.listRelationsForItem`). Use the writer kind that #1415 threads into relation writes; read it from the hook context.
2. Register the hook with `registerRelationEdgeWriteHook` in `backend/packages/data/src/domainWriteHooks.ts`.
3. Record the ownership handoff above in the header comment of `backend/packages/data/src/calendar/calendarModuleManifest.ts`.
4. Add `backend/packages/data/src/calendar/eventParticipantsRouteHandlers.ts` with `createListEventPeopleRouteHandler` for `GET /api/events/:id/people`. For a live Event of the caller's tenant it returns `{ people: [{ personId, name, relationship, emails, role, invitation }] }`: `relationship` from People, `emails` the normalized addresses parsed from `People.emails`, `role` defaulting to `attendee`, `invitation` or `null`. The organizer comes first, then the others by name; a trashed person is omitted. An unknown or foreign Event id is 404.
5. Declare the route in `customRoutes` of `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` (name `listEventPeople`, justification `single-consumer-read`, handler re-exported from that file; Events routes belong to the systemDatabases module). Add it to `backend/services/semprec-api/src/routeMatrix.ts` (tenant class), to `ROUTE_HANDLER_FILES` in `backend/services/semprec-api/src/__tests__/chokePointWriteBoundary.unit.test.ts` and to `backend/services/semprec-api/src/__tests__/tenantIsolationRoutes.test.ts`.
6. Tests: hook unit and integration tests for each rejection above and for the accepted shapes (`{}`, a plain role, an invitation written with the system writer kind, a public `PUT` that repeats the stored invitation unchanged); an `PUT` that adds or edits an invitation as a public writer is 400; the route returns the organizer, an accepted, a tentative and a not-invited participant in that shape; another tenant's Event is 404.

## Scope

### In scope

- The edge metadata shape and its validation, including the server-only rule for `invitation`, and the read endpoint for an Event's participants.

### Out of scope

- The inverse `People.events`: #1664.
- Replacing participants in bulk and inviting: #1790.
- Sending requests and cancellations, and recording `sentAt`: #1774.
- Recording replies: #1950.
- Creating the organizer edge: the code that sends the first invitation (#1790) does it; this issue only validates it.

## Acceptance criteria

- When the participants of "Schuzka s klientem" are read, then the response lists the organizer, Petr with an `accepted` invitation, Jana with `tentative` and Karel with `invitation` null.
- When a client writes an edge with invalid metadata (unknown key, bad role, bad invitation status), then the response is 400 `validation_failed` with `field` `metadata`.
- When a public client changes, adds or removes the `invitation` of an edge, then the response is 400 and the stored edge is unchanged; when it repeats the stored `invitation`, the write succeeds.
- When server code writes an `invitation` with the system writer kind, then it is stored.
- Existing edges with empty metadata remain valid and are returned with role `attendee`.
- A second organizer edge, or an organizer edge to a person other than the user's own, is rejected.
