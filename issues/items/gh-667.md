## Context

`advanceTaskRecurrence` (`backend/packages/data/src/tasks/advanceTaskRecurrence.ts`, lines 44-84) implements the Tasks rolling model: completing a recurring task creates the next instance, copies its relation edges, deactivates the old `task_recurrence` row and marks the old task `done`. Its only callers are `backend/packages/data/src/__tests__/tenDatabases.test.ts` and the barrel export in `backend/packages/data/src/index.ts` (line 251); no request handler, heartbeat action or choke-point path invokes it. A user who sets a recurring task's `status` to `done` through `PATCH /api/items/:id` gets no next instance, so recurrence does not exist in the product.

The Tasks-specific hook point already exists in the generic write path: `updateItemWithClient` (`backend/packages/data/src/chokePoint/itemWrites.ts`, lines 231-314) branches on `database.ownerModuleId === TASKS_MODULE_ID` for the derived `time` property (lines 246-265, `docs/adr/2026-09-19-derived-system-properties-computed-inline-at-choke-point.md`). The Tasks `status` select has the options `notDone | done | wontDo` (`backend/packages/data/src/seed/seedTenDatabases.ts`, lines 141-147). `advanceTaskRecurrence` takes a `Pool` and opens its own transaction, so it cannot be called from inside the choke point's transaction as it stands (it would deadlock on the row the caller has locked). The advance must be in the same transaction as the `done` write: a crash between them would leave the rolling model's "exactly one open instance" invariant broken either way.

Sibling issue C12 of this batch also edits `itemWrites.ts` (`createItemWithClient`'s replay side effects) and depends on this issue for that reason.

## Task

1. `advanceTaskRecurrence.ts`: split the body into an exported `advanceTaskRecurrenceWithClient(client: PoolClient, input: AdvanceTaskRecurrenceInput): Promise<ItemRow | null>` — everything from the locked `getTaskRecurrence` (line 49) through `copyRelationEdges` (line 74), **without** the final `updateItemWithClient(... status: 'done')` at lines 76-80. `advanceTaskRecurrence(pool, input)` keeps its signature and becomes `withTransaction(pool, async (client) => { const next = await advanceTaskRecurrenceWithClient(client, input); await updateItemWithClient(client, { databaseId, itemId, propertiesPatch: { status: 'done' } }); return next; })`. The `done` write inside it re-enters the hook from step 2, which finds `task_recurrence.active` already `false` (set at line 72 in the same transaction) and no-ops — no flag is needed; the `active` row lock is the idempotency guard, as its doc comment (`taskRecurrenceStore.ts`, lines 59-66) already describes.
2. `updateItemWithClient`: after `itemsStore.updateItemProperties` (line 267) and before the heartbeat trigger (line 279), when `database.ownerModuleId === TASKS_MODULE_ID && input.propertiesPatch.status === 'done'`, call `advanceTaskRecurrenceWithClient(client, { databaseId: input.databaseId, itemId: item.id, timezone: await getSystemTimezone(client) })` (`backend/packages/data/src/systemSettings.ts`, line 28). It is a no-op when the task has no active recurrence (the common case) and on a repeated `done` write. The nested `createItemWithClient` for the next instance runs its own `triggerOnItemEventHeartbeats`/`notifyInvalidation` as today. `itemWrites.ts` must reach `advanceTaskRecurrenceWithClient` without creating an import cycle through `chokePoint/` — the repository's `no-choke-point-rollup-cycle` dependency rule (`pnpm run check:boundaries`) forbids one. Accepted shape: the `WithClient` function lives in a module under `tasks/` that does not import `itemWrites.ts`, and the item-create function it needs for the next instance is passed in by the caller as a parameter. (Amended 2026-09-28: the original sentence here prescribed a direct import between the two files and accepting the cycle, which the boundary check rejects.)
3. Tests in `backend/packages/data/src/__tests__/tenDatabases.test.ts` (integration; the existing recurrence cases at lines 200-300 keep passing — adapt them only where they assert the old `done` write ordering): a recurring task set to `done` through `chokePoint.updateItem` (no direct call to `advanceTaskRecurrence`) yields exactly one new `notDone` instance with the recurrence carried over and the old row's `task_recurrence.active = false`; a second `done` write on the old task creates nothing; a `done` write on a task without recurrence creates nothing; `done` and the new instance commit together — run the update with `ifVersion` stale so it throws, and assert no instance was created.

## Scope

### In scope
- The single hook point in `updateItemWithClient` for a Tasks `status: 'done'` write and the client-scoped advance it calls, plus tests.

### Out of scope
- Moving this Tasks knowledge (and the existing `time` derivation) behind a module hook — the pre-tenancy epic owns the module-hook refactor of the generic write path; this issue adds exactly one hook call and no hook framework.
- Recurrence for `wontDo`, or un-advancing when a task is set back to `notDone`.
- Idempotent-replay side effects in `createItemWithClient` (sibling issue C12).

## Acceptance criteria

- When a Tasks item with an active recurrence is patched to `status: 'done'` through the choke point, exactly one next instance exists afterwards, created in the same transaction as the `done` write, with the old task's recurrence deactivated.
- When the patched task has no active recurrence, or is patched to `done` a second time, no instance is created.
- When the `done` write fails (stale `ifVersion`), no instance is created.
