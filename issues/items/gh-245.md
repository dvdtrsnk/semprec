**Blocked by:** #181, #176

## Context

This is the first of three parts that together deliver the recording-preparation and paid-stage checkpointing slice of the `batch-transcription` batch (approved behavior in #179). It builds on #180 (Transcriptions catalog with declared computed keys, the Files `onItemEvent` producer, `POST /api/transcriptions`, and the `TASK_NAMES.transcriptionJob` / `jobKey: transcription-job:${fileItemId}` enqueue contract) and on #181 (gateway `diarize()`/`transcribe()` and audio metering).

This part establishes the `semprec-transcribe` process as the single owner of the transcription task handler and implements step 0 of the pipeline: idempotent creation or reuse of the Transcriptions row. #246 adds the ffmpeg/ffprobe preparation step on top of the step runner delivered here, and #182 adds diarization, chunked ASR, and per-stage checkpoint/resume. #183 and later issues append the merge, summary, matching, and retry behavior.

## Task

- Make `semprec-transcribe` the sole transcription task owner: `registerTask(TASK_NAMES.transcriptionJob, ...)` is registered only inside `semprec-transcribe` (one handler owner per task name). Producers (the `onItemEvent` handler in `semprec-agents` and the action routes in `semprec-api` from #180) keep enqueueing only and perform no item writes.
- `semprec-transcribe` writes through the choke-point package in-process with the identity of the system process. It is the only process that writes the `owner: 'system'` fields `status`/`date`/`link` of Transcriptions rows and the only process that will call `ffmpeg`/`ffprobe` (#246 adds the calls; nothing else may call them).
- Implement step 0 (`create`) of the pipeline: a choke-point create of the Transcriptions row with the derived `Idempotency-Key transcription:<fileItemId>`, so that a repeated run gets the same row and never a second one. The created row has `name` derived from the source file's name, `status = processing`, `link` pointing at the Files row, and `item_automation` set to `pending`.
- Implement the step runner that the later parts extend: the job handler executes the pipeline steps in order and, after each step, persists that step's intermediate result into the declared `items.computed` checkpoint keys from #180 before continuing; on a repeated run the handler reads the checkpoints and skips every step whose checkpoint already exists. In this part only step 0 exists; the handler ends after step 0 and leaves the row in `status = processing` / `item_automation = pending` for the steps that #246 and #182 append.
- Register the process in the topology so that `semprec-transcribe` runs as its own systemd unit / composition root using the affinity-safe graphile-worker runtime from #91.

## Scope

### In scope

- `semprec-transcribe` composition root, sole `registerTask(TASK_NAMES.transcriptionJob, ...)` registration, and the in-process choke-point writer with system identity.
- Step 0 with the `Idempotency-Key transcription:<fileItemId>` row creation/reuse and the initial `name`/`status`/`link`/`item_automation` values.
- The ordered step runner with checkpoint read/skip semantics over the declared computed keys.
- Tests, integration, and necessary documentation for the above.

### Out of scope

- ffmpeg/ffprobe normalization, duration/creation-time persistence, and the provisioning dependency — #246.
- Diarization, chunked ASR, and the paid-stage checkpoints themselves — #182.
- Merge, summary, `done` finalization — #183; Event matching — #184; retry, rerun, notifications — #186.

## Acceptance criteria

- Duplicate delivery of the same job (same `jobKey`, or the handler re-run after a crash) reuses exactly one Transcriptions row for the file; no second row and no second `Idempotency-Key` is ever created.
- The created row carries `name` from the filename, `status = processing`, `link` to the Files row, and `item_automation = pending`.
- Only `semprec-transcribe` registers the transcription task handler and only it writes the `owner: 'system'` fields of Transcriptions rows; the `owner_process` drift check does not fire for producers.
- Re-running the handler on a row whose step-0 checkpoint exists skips step 0 and continues with the next step (none yet in this part) without performing any additional write.
