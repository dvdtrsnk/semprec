## Context

Model tier rationale: A durable ordered queue shared by every window of the process, answers made up on the device that the repositories must decode, identifiers created offline and resolved on replay, retry and refusal policy per status; it decides what the server receives and when.

Since `[offline-first 01/07]` reads of the offline set work without a connection, but a write still fails: the person cannot complete a task, move an event or add a project offline. Every write goes through `AuthenticatedApi.send` and the `OfflineLayer` built there; the repositories (`ItemWrites`, `HttpCollectionWrites`, `HttpCalendarRepository`, `HttpItemRepository`, `HttpInvitationRepository`, `HttpJournalRepository`, `HttpInboxCaptureRepository`) build the requests and decode the answers. A create of `POST /api/databases/:id/items` accepts an `Idempotency-Key` header: the server answers a repeated key with the item it already created. `PATCH /api/items/:id` takes `ifVersion` and answers `409` when it is stale; `GET /api/items/:id` answers the current `version`.

Showing the queued writes in the kept answers is `[offline-first 04/07]`; this issue makes the writes wait and arrive.

## Task

Load `kmp-shared`, `testing`, `error-handling`, `adr-conventions` and `mobile-verify`.

1. Queued routes and the answer the device makes up for each (status, body):
   - `POST /api/databases/:id/items`: `201`, the item `{id, databaseId, properties, relations, version, createdAt}` with a new id made on the device, the body's `properties`, its `relations` (`[{propertyKey, targetItemIds}]`) as `{key: [{id, title}]}` (the title of a target taken from any kept answer that holds that id, else empty), and the queue time as `version` and `createdAt`.
   - `PATCH /api/items/:id`: `200`, the newest kept `GET /api/items/:id` item with the body's `properties` merged in and the queue time as `version`; without a kept item, `{id, databaseId: "", properties, version}`.
   - `DELETE /api/items/:id`, `PUT /api/items/:id/relations/:key`, `PUT` and `DELETE /api/items/:id/relations/:key/:target`, `POST /api/items/:id/links/:key/:action`: `204` with an empty body.
   - `POST /api/events/series/:id/occurrences/:date` and `POST /api/tasks/series/:id/occurrences/:date`: `201`, `{id, databaseId, properties, version}` with a new id, the series item's kept `databaseId` and `properties` (with `date` set to the occurrence's date), else empty ones.
   - `PUT` and `DELETE /api/tasks/:id/recurrence`, `PUT /api/tasks/:id/host-events/:event`, `POST /api/calendar/invitations/:id/respond`, `POST /api/inbox/items`: `200` with `{}`.
   - `PUT /api/journal/periods/:type/:period/doc`: `200`, `{itemId}` with a new id.
   Any other write is sent as today and never queued. `POST /api/calendar/items/:id/duplicate` stays unqueued: the server cannot recognize a repeated duplicate.
2. A create of `POST /api/databases/:id/items` without an `Idempotency-Key` gets one before its first attempt, so a repeat after a lost answer never creates a second item.
3. Writing: with nothing queued and the process not offline, a queued route is sent directly; an answer other than `5xx` or `429` is returned as it came; no answer, a `5xx` or a `429` queues the request and returns the made-up answer. While offline, the request is appended, the replay is started and the made-up answer is returned at once. While anything is queued and the process is not offline, the request is appended, the replay is started, and the caller waits up to 10 s for that entry: the server's answer when it was sent, its refusal when it was dropped, the made-up answer otherwise.
4. The queue lives in `<account>/queue.json` of the `OfflineStore` (the entries in order with method, path, query, body, content type, headers, the new id, attempts and the queue time; the map of new ids to server ids; the new ids of dropped entries; the failures), written atomically on every change, cleared with the store. A new id is mapped once its entry is answered: from `id`, or from `itemId` for the diary period.
5. Replay runs one entry at a time per account, in order, for the whole process: on a new entry, on the sync socket connecting, when the offline state ends, and after a failed attempt with a backoff from 1 s doubling to 60 s with jitter. Before an entry is sent, every mapped new id in its path, query and body is replaced by the server id; an entry naming the new id of a dropped entry is dropped. Outcomes: success removes it; no answer stops the replay until the next trigger; a `5xx` or `429` stops it as well and is dropped after 8 attempts; `401` stops it (the session is then forgotten, which clears the queue); `404` of a `DELETE` counts as done; `409` of a `PATCH /api/items/:id` with `ifVersion` reads the item and is sent once more with its current version; every other answer drops the entry. A dropped entry records a failure (the route without ids or body, the `FailureKind`, the time). Every success and every drop makes the kept answers stale and tells every window.
6. `OfflineLayer.status` is a flow of the number of queued entries and the failures, with a call that forgets the failures; nothing shows it yet.
7. Add the ADR `docs/adr/2026-11-23-mobile-writes-wait-in-an-ordered-queue-without-a-connection.md` recording 1–6 and why the queue holds requests rather than domain operations.
8. Tests (commonTest): every route's made-up answer decoded by the repository that sends it; the idempotency key; the direct, queued, waiting and timed-out paths of 3; persistence across a new store; each replay outcome of 5 including id replacement, a dependent entry dropped, the backoff limit and the `409` retry; the status flow.

## Scope

### Out of scope

- Files, blobs and duplicates.

## Acceptance criteria

- Completing a task, moving an event, creating a project or answering an invitation without a connection succeeds on the device, and the request reaches the server, once and in order, when the connection is back.
- A create replayed after a lost answer does not create a second item.
- Requests that name an item created offline reach the server with its server id; when the create was refused, they are dropped too.
- A stale version on replay is retried once with the current version; a refusal is dropped and recorded as a failure; a server error is retried with backoff and dropped after 8 attempts; no connection keeps the entry.
- With a connection and nothing queued, a write and its refusal behave exactly as today.
- The queue survives a restart and is removed when the session ends.
