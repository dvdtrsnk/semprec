## Context

Model tier rationale: One mechanism (accept a new processing method and a new envelope kind) spread over the seed, a per-tenant data cutover and envelope validation, with existing fixtures to verify against; the cutover rewriting existing types keeps it above low.

Inbox item types carry `processingMethod` (`pageContent | database`, `PROCESSING_METHODS` in `backend/packages/data/src/inbox/inboxTypesStore.ts`) and, for `database`, a `targetDatabase` from `TEN_DATABASE_MODULE_IDS`. Cross-field validation lives in `assertValidProcessingConfig` there. A type with `processingMethod: 'database'` and `targetDatabase: 'journal'` is accepted today and its confirmed proposal creates an empty Journal record, because the envelope validation only checks the keys that are present. A `pageContent` proposal needs an existing target item, but the Journal day usually does not exist yet.

This issue gives the voice-note / personal-experience case its own path: a new processing method `journal` and a new proposal envelope kind `journalEntry`. The UI card the user sees has the fields Day (date), Entry (required multi-line Markdown), Project and Area (simple pickers, each optional).

Envelope contract, canonical keys English camelCase:

- `entityKind: "journalEntry"`
- `target`: the id of the Journal database
- `properties`: `{ date: "YYYY-MM-DD", markdown: string (required, non-empty), areaId?: string, projectId?: string }`. The model fills only `{date?, markdown, areaId?, projectId?}`; the stored envelope always carries an explicit `date`, defaulted from the date of the source Inbox item by the tick (#1982).

Decision: project and area are stored as edges on the Journal day item (not only on the inserted block), written at confirm by #1981. Decision: this issue validates both ids independently; the rule that an area is derived when a project is set (so both together are rejected, and an area alone is the entry's own value) is applied by #1991, as decided by the product owner: while a project is chosen the area is read-only and changes only with the project.

Decision (product owner): the blocks written by a confirmed journal entry are authored by `user`, the person who confirmed the proposal; that Semp proposed them is recorded on the card (per-step `blockIds`, #1648).

Builds on: #1419 (readers already tolerate unknown kinds, so this release may start writing `journalEntry`), #1608 (the Markdown parser used to validate the text), #1973 (touches the same type-target rules), and #1383, #1451, #1392 (their changes to `seedInboxPipeline.ts` land first, so the seed edits here apply on top). #1977 (default type catalog) uses the `journal` method name defined here. #1981 and #1982 build on this issue.

## Task

Load `canonical-keys`, `db-migrations`, `state-writes` and `testing`.

1. Add `journal` to `PROCESSING_METHODS` in `inboxTypesStore.ts`. In `assertValidProcessingConfig`: `journal` must not set `targetDatabase`; `processingMethod: 'database'` with `targetDatabase: 'journal'` is rejected with a `ValidationError` naming the `journal` method as the replacement.
2. Seed: add the `journal` option to the `processingMethod` select in `backend/packages/data/src/seed/seedInboxPipeline.ts` and the option label in `backend/packages/data/src/inbox/i18n/en.json` and `cs.json` (`property.inboxItemTypes.processingMethod.option.journal`). Keep the seed file's edit ordered after the changes of #1383-#1392.
3. Per-tenant cutover in `backend/packages/data/src/db/tenantCutoverMigrations.ts`: (a) add the `journal` option to the already-seeded `processingMethod` select property of every tenant; (b) convert every existing Inbox item type with `processingMethod: 'database'` and `targetDatabase: 'journal'` to `processingMethod: 'journal'` with `targetDatabase` removed. The cutover is idempotent. Load `db-migrations` for the data-migration rules.
4. Add `journalEntry` to the write-side proposal envelope schema and to `ProposalEntityKind` in `inboxTickAction.ts`. In `assertValidProposalEnvelope`, for `journalEntry` validate: `target` is the Journal database id of the tenant; `date` is a valid calendar date `YYYY-MM-DD`; `markdown` is a non-empty string that parses with the #1608 parser and contains no `page` blocks; `areaId`, when present, is a live item of the Areas database; `projectId`, when present, is a live item of the Projects database; everything is resolved inside the caller's tenant. Violations are `ValidationError` (400), both when the tick writes the envelope and when revise supplies one.
5. Extend the exhaustive `switch` in `assertValidEnvelopeForCard` (`proposalActions.ts`) so `journalEntry` is accepted on a non-transcript card and rejected on a transcript card with a `ValidationError` on `entityKind`.
6. Revise (`reviseProposalWithClient`, a function without an HTTP route) accepts a `journalEntry` envelope, including a changed `date` and `markdown`. The HTTP route for manual edits is not part of this issue.
7. `confirmProposalWithClient` must not be able to silently mis-handle the new kind: until #1981 lands, a `journalEntry` card answers 409 on confirm (explicit branch), not the `pageContent` path.

## Acceptance criteria

- When an Inbox type is written with `processingMethod: 'journal'` and no `targetDatabase`, then it is accepted; with a `targetDatabase` it is rejected.
- When an Inbox type is written with `processingMethod: 'database'` and `targetDatabase: 'journal'`, then it is rejected with a message pointing to the `journal` method.
- When the cutover runs on a tenant that has a `database`+`journal` type, then the type becomes `journal` without `targetDatabase`; a second run changes nothing.
- When a `journalEntry` envelope has no `markdown`, an empty one, a `page` block, an invalid `date`, an area that is not an Areas item, or a project that is not a Projects item, then tick-write and revise both answer 400.
- When a stored `journalEntry` envelope is revised without a `date`, then it is rejected with 400 (the stored envelope always carries an explicit date; the default from the source item is applied by #1982).
- When a `journalEntry` card is confirmed before the confirm issue lands, then the answer is 409 and nothing is written.
- When a `journalEntry` envelope is placed on a transcript card, then it is rejected.
