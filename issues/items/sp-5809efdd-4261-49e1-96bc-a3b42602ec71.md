## Context

Model tier rationale: This introduces a new persisted-data contract on the device (an outbox that outlives the session), a new identity for whose data it is, and retry and ordering rules that must never lose a record across crashes, restarts, refusals and sign-outs; the existing offline queue's lifecycle is narrowed for one route.

The owner wants to capture into the Alldots Inbox from the iPhone's Action button, with text or a scanned document, without a connection, and never lose what was captured; it must reach the Inbox as soon as the device is online again. Later issues of this batch add the App Intent, the scanner and background sending on Apple; this issue delivers the shared mechanism they and the diary's existing capture row use.

Today `HttpInboxCaptureRepository.capture` (`mobile/shared/data`) first uploads an attached file with `POST /api/blobs` and then creates the item with `POST /api/inbox/items`. Only the second request is a queued route of the offline write queue (`QueuedRoute.INBOX_CAPTURE`, decided in `docs/adr/2026-11-23-mobile-writes-wait-in-an-ordered-queue-without-a-connection.md`), so a capture with a file fails without a connection. Uploading the file early does not help: the server deletes unreferenced standalone uploads after 24 hours (`backend/packages/data/src/blobs/unreferencedBlobSweep.ts`). The queue also drops a write after 8 server errors, after any refusal, and when the session ends (sign-out, or a `401` of a revoked token), and its account key hashes the token (`accountKey` in `FileMailThreadListCache.kt`), so it changes at every sign-in. Each of these loses a capture.

The server already makes repeats harmless: `POST /api/inbox/items` answers a repeated `Idempotency-Key` with the item it already created, and `POST /api/blobs` stores bytes by their content hash, so uploading the same file again stores nothing new.

## Task

1. Add an ADR under `docs/adr/` (load `adr-conventions`) that narrows `2026-11-23-mobile-writes-wait-in-an-ordered-queue-without-a-connection` for Inbox captures: captures leave the write queue and wait in a capture outbox whose rules are the ones below, with the privacy consequence that unsent captures stay on the device after the session ends.
2. Add the capture outbox in `:shared:data`, owned by `OfflineLayer` (one per data directory and process, like the rest of the layer):
   - **Storage.** Each capture is `<dataDirectory>/captures/<owner>/<captureId>.json` (text, day `YYYY-MM-DD`, time `HH:mm`, type id or none, the file's name, media type and source when it has one, the blob id and upload time once uploaded, attempts, the time of the next attempt, the creation time) and, for a file, `<captureId>.bin` beside it. The bytes are written first, then the JSON; both replace the target atomically (written beside and moved over it). A capture exists once its JSON exists, and a `.bin` without its JSON is deleted when the outbox lists the directory. `captureId` is a random UUID, also sent as the `Idempotency-Key`. Add binary `expect`/`actual` file functions beside `CacheFiles.kt` (Apple, Android, JVM) for the bytes.
   - **Owner.** `<owner>` is the hex SHA-1 of the server URL and the id of the signed-in person (the `SessionUser` the offline store keeps for the session), not of the token, so it stays the same across sign-ins of the same person. A capture made while no person is known is refused with a failure and nothing is written.
   - **Lifetime.** `OfflineLayer.clear()` (every end of the session) and keeping one account's offline answers never delete `captures/`. A capture is deleted only after the server answered its `POST /api/inbox/items` with success.
   - **Sending.** One round at a time per process, for the owner of the session signed in now, through the window's sender. Captures go out in creation order, one at a time: the file first (`POST /api/blobs`, raw body) unless an uploaded blob id is recorded, then `POST /api/inbox/items` with the same body `HttpInboxCaptureRepository` sends today and `Idempotency-Key: <captureId>`. No answer, a `5xx`, a `429` or a `401` ends the round and keeps the capture. A refusal of the item that names a type is sent again at once without the type, and the change is written. A refusal of the item that names a blob id is followed, once per round, by a new upload and a new send. Any other refusal of either request keeps the capture, counts the attempt and does not try it again for 1 hour; the round goes on with the next capture. Nothing is ever dropped.
   - **Triggers.** A round starts when a capture is added, when the layer is reached again or a sync socket connects, when a window starts, and after a round that ended without an answer, with a backoff from 1 s doubling to 60 s with jitter, for as long as the process runs.
   - **After a success** the layer's change flow emits, so the open screens of every window read again.
   - **Status.** The number of captures of the signed-in owner counts in `OfflineStatus.waiting`.
3. Route every Inbox capture through the outbox: with an offline layer, `HttpInboxCaptureRepository.capture` adds the capture (returning success once it is written, and a failure when it could not be written) instead of sending it; without one (no data directory) it sends as today. Remove `QueuedRoute.INBOX_CAPTURE` and its uses in `QueuedAnswers` and `QueuedWriteProjection`.
4. Add `suspend fun send(): Boolean` to the outbox's public surface used by later issues: it runs a round now (joining one that runs) and answers whether no capture of the signed-in owner is left. Keep it internal to `:shared:data` until an issue exports it.

## Scope

### In scope

- The outbox, its storage, owner, lifetime, sending, triggers and status as specified, and routing the existing capture repository through it.

### Out of scope

- The App Intent, the document scanner and background sending on Apple (later issues of this batch).
- Showing the captures that wait or were refused one by one, or retrying or editing them by hand.
- Android passing a data directory.

## Acceptance criteria

- A capture with a file made while the server cannot be reached is written to `captures/<owner>/`, and once the server answers it is uploaded and created once: the item request carries the blob id of that upload and `Idempotency-Key` equal to the capture id, and both files are deleted.
- A capture whose item request got no answer after its upload succeeded is sent again later without uploading again, with the same `Idempotency-Key`.
- A restart of the process (a new layer over the same directory) sends the captures the files hold; a `.bin` without its JSON is deleted, and a JSON that names a file whose `.bin` is missing keeps waiting, counted, and is never deleted.
- `clear()` and a sign-in of the same person with a new token leave the captures in place, and the next round sends them; a capture of another person is not sent while someone else is signed in.
- A `5xx`, a `429` and a `401` keep the capture with no attempt limit; a refusal naming a type leads to a send without the type; a refusal naming a blob leads to one new upload; any other refusal keeps the capture and the next attempt waits 1 hour while later captures are still sent.
- Captures go out in creation order, one at a time, and two triggers at once run one round.
- `OfflineStatus.waiting` counts the captures of the signed-in owner, and a successful send makes the layer's change flow emit.
- Without a data directory, `HttpInboxCaptureRepository.capture` behaves as before; `QueuedRoute` no longer contains `POST /api/inbox/items`.
