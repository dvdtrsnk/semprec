## Context

Model tier rationale: Changes how every IMAP pass detects deleted messages (QRESYNC VANISHED, a CONDSTORE message-count check, the fallback UID diff), what a pass does when the last folder copy of a message is gone (a trash through the choke point plus the meta removal) and the provider client's fetch commands, with move-versus-delete ordering across a pass's transactions and the quiet-pass skip.

Production evidence (dev VPS v0.3.4, one Purelymail IMAP account advertising IDLE, CONDSTORE, QRESYNC, MOVE, UIDPLUS and no LIST-STATUS, IMAP IDLE live sync on): a message APPENDed to INBOX appeared in Alldots after 4.4 s. It was then flagged `\Deleted` and EXPUNGEd directly on the server. 123 s later `GET /api/mail/threads` still listed it, although IDLE ran and passes ran.

Root cause, from the code:

- `buildImapFlow` (`mail/mailServerConnections.ts`) creates imapflow without `qresync: true`, so imapflow never sends `ENABLE QRESYNC`. `ImapFlowMailClient.fetchVanishedSince` checks the advertised capability (`capabilities.has("QRESYNC")`), not the enabled one, so on Purelymail it sends `UID FETCH 1:* (UID) (CHANGEDSINCE m)` without the `VANISHED` modifier (imapflow adds it only when QRESYNC is enabled), receives no VANISHED response and returns `[]`.
- The pass then treats `[]` as "nothing vanished" and records the folder's new `message_count` and `highestmodseq`. From the next pass on the folder's STATUS equals the stored state, the quiet-pass skip leaves it alone, and the expunged message is never looked at again. The IDLE `expunge` signal did enqueue a pass; that pass took the same path.
- On a CONDSTORE server without QRESYNC every delivery (UIDNEXT moved) also ran `UID SEARCH ALL`, a full UID listing of the folder, although a delivery alone cannot remove anything.
- A folder edge removed by a vanished UID left an Emails item with no folder at all. Such an item still counts in its thread (`messageCount`, `unread`, `flagged`), in the flagged box and in search.

Decisions:

- **QRESYNC is enabled where advertised.** `buildImapFlow` sets `qresync: true`; imapflow enables only what the server advertises. The client decides by `client.enabled`, not by the advertisement.
- **One FETCH for flags and expunges under QRESYNC.** `ImapMailClient.fetchVanishedSince` is replaced by `fetchChangesSince(path, sinceModSeq)`, which sends one `UID FETCH 1:* (UID FLAGS) (CHANGEDSINCE m VANISHED)` and returns the changed flags and the vanished UIDs (`VANISHED (EARLIER)` and live VANISHED during the command), or `null` when QRESYNC is not enabled on the connection; the caller then uses the CONDSTORE flag fetch and the count check. The VANISHED UIDs count against the flag fetch's result cap.
- **A message-count check decides whether a full UID diff is needed.** In a selected folder the pass knows the stored count C (which described the folder at the stored UIDNEXT), the new UIDs it found at or above the stored UIDNEXT (n, when the search fit the batch) and the vanished UIDs below the stored UIDNEXT that QRESYNC reported (v, 0 without QRESYNC). When `C − v + n` equals the selected `EXISTS`, the reported vanished UIDs are complete (none without QRESYNC) and no `UID SEARCH ALL` is sent. Otherwise, and after a UIDVALIDITY change, a partial batch or an unknown stored count, the pass falls back to the full UID diff it uses today. The check can only add a diff, never hide one: the equation holds with a removal only when an unseen addition below the stored UIDNEXT offsets it, which IMAP excludes (UIDs only grow). With UIDNEXT and the count both as stored nothing was added and nothing removed (unchanged rule). So a CONDSTORE-only server sends `UID SEARCH ALL` only when the count says something left the folder, and a server without CONDSTORE does the same; no periodic full rescan is added, because the check is exact for both and a rescan would only repeat it.
- **The quiet-pass skip stays as it is.** A folder whose HIGHESTMODSEQ or MESSAGES changed is not skipped; an expunge changes at least MESSAGES. The fix is that such a folder now finds what left.
- **The last copy gone means the message is removed.** A vanished UID removes that folder's edge, as today. When the pass ends (its final transaction), every Emails item this pass removed an edge from and that now has no folder edge, no unsettled move and no protected move is trashed through `itemDeleteWithClient` as the system writer, and its meta row goes with `deleteMailMessageMetaOfRemovedItem` (a thread no other message names goes too), exactly as the Mail-off removal does; a later re-delivery of the same Message-ID is then ingested anew instead of converging onto a trashed item. A message with another copy left keeps its item. The removal is idempotent: a second VANISHED for the same UID finds no edge, an already trashed item is returned unchanged, a missing meta row is no failure. The standalone `reconcileImapFolder` removes in its own write transaction.
- **A move by another client stays a move.** The target folder's new UID is ingested onto the existing item (Message-ID dedup per mailbox) and the source edge is removed; because the trash decision waits for the end of the pass, a move whose source and target are both processed in one pass keeps the item (read, flagged, thread links unchanged). When the target's new UID is beyond the pass's budget the source copy is removed and the item trashed; the next pass ingests the target copy as a new item: deleted and recreated, but not lost.
- **IDLE is unchanged in mechanism.** The IDLE connection already signals on `expunge` (EXPUNGE, and VANISHED once QRESYNC is enabled there too), which enqueues the coalesced pass; the pass now finds the expunge.

## Task

Load `state-writes`, `io-hardening`, `error-handling`, `testing`.

1. `mail/mailServerConnections.ts`: `qresync: true` in `buildImapFlow`.
2. `mail/imapReconcile.ts` (`ImapMailClient`): replace `fetchVanishedSince` with `fetchChangesSince`; the fetch half uses it under QRESYNC and the count check before falling back to `fetchAllUids`; `applyImapFolder` returns the emails it removed an edge from; the account pass's final transaction and `reconcileImapFolder` remove the ones left without a folder edge.

## Scope

### In scope

- QRESYNC enablement and VANISHED consumption in the folder pass, the count check, the removal of a message without a folder copy at the end of a pass, the fakes, tests and the architecture document.

### Out of scope

- QRESYNC SELECT parameters (`SELECT … (QRESYNC (…))`), which would fold the flag and vanished data into the SELECT response.
- Gmail-over-IMAP label edges of a message that vanished from All Mail.
- A `mailThread` invalidation for an edge removal that leaves other copies.
- The move drain, IDLE on more folders, per-folder passes, pool size and worker concurrency.
- Any request against a real server.

## Acceptance criteria

- Against the loopback IMAP server with QRESYNC and IDLE (Purelymail's capability set, no LIST-STATUS): an expunge by another client while the IDLE connection idles on INBOX signals the pass, which removes the message (trashed, gone from `listMailThreads`) within a bound asserted in the test (about 1 s at the test's latency).
- With QRESYNC, an expunge discovered by the next pass (no IDLE) is removed with one SELECT and one FETCH in the changed folder and no `UID SEARCH`; with CONDSTORE only, the same pass sends one `UID SEARCH ALL` in that folder; without CONDSTORE it does too. In each case the message is trashed and its thread no longer counts it.
- On a CONDSTORE-only server, a delivery alone sends no `UID SEARCH ALL`.
- A message in a two-message thread that is expunged leaves the thread listed with `messageCount` 1; the other message's item is unchanged.
- A move by another client from INBOX to Archive (QRESYNC) ends with the same Emails item in Archive only, no item trashed, its read state kept.
- A second pass over the same state removes nothing more and fails nothing (idempotent).
- The quiet passes of `imapQuietPass.test.ts` keep their command counts, and a QRESYNC quiet pass sends the same commands as a CONDSTORE one.
- The existing mail, IMAP, IDLE, thread, observability and isolation test files stay green.
