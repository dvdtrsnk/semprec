## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. Add an `inbox.proposal.get` module agent tool to the Inbox module manifest (`agentTools` entry with `handlerExport`), with arguments `{ proposalId }` (strict, UUID).
2. The handler returns capture text, attachments as { attachmentId, name: null } in their existing position order, the effective envelope, userEditedKeys, status and history using current Inbox owners. No authoritative attachment name exists; do not derive one from a UUID, storage key or MIME, or add schema. Preserve existing envelope/content rules without early #1938 behavior.
3. The tool answers only for the card of the calling run's own thread: the run's thread is resolved from persisted run data (as `heartbeatAgentTools.ts` resolves the calling project), never from arguments beyond the id, and any other card id gives a not-found style error that does not reveal whether the card exists.
4. The tool writes nothing and is not approval-gated.
5. Tests: the tool returns the full card for its thread; another card of the same tenant is refused with the same error as a missing one; a card of another tenant is refused; arguments with extra keys are rejected.

Authorization uses persisted calling-run threadId, an actual live item thread/Inbox source, and the current live Processing proposals.sourceInbox association to the requested card in one managed tenant read transaction. A stale/null subject_proposal_id is never sufficient. Resolve identity and association in the authorization statement, then use existing owner parsers/readers; no lock, write or global snapshot promise. Missing run/thread/current association, unlinked/trashed source or card, unrelated same-tenant card and foreign/random IDs all receive the same fixed not-found style refusal. Existing module ownership/capability composition stays unchanged. Add an actual module-tool registry invocation plus no-effect/isolation/stale-hint controls.
