## Context

Model tier rationale: One known mechanism (registering a module manifest in the full registry) across defined seams with existing module-load fixtures, but it activates a new module and owner process for every tenant and edits several shared registration files.

There is no calendar module in the backend today. Modules are composed by `loadFullModuleRegistry` in `backend/packages/data/src/manifest/fullModuleRegistry.ts` (its `ALL_MODULE_IDS` and `MANIFEST_PATHS`), custom routes are mounted from the registry by `backend/services/semprec-api/src/app.ts`, and a system-owned property is only accepted by `core.driftCheck` when its `owner_process` is a member of `KNOWN_OWNER_PROCESS_IDS` (`backend/packages/data/src/manifest/knownActionIds.ts`); otherwise the check reports it as an orphan.

This issue registers an empty `calendar` module so that every later calendar issue (calendars, invitations, reminders, recurrence, timeline, agent tools) adds its databases, routes, actions and tools to one existing manifest instead of racing to create it. It adds no database, route, action or tool and changes no behavior.

Decision: the module id is `calendar` and it is also the owner process of the system-owned properties of the module's databases (for example the status of an invitation), exported as `CALENDAR_MODULE_ID`.

Decision: the module is non-removable and a system project module (`removable: false`, `systemProject: true`), like the Inbox and Mail modules.

Shared-file ordering: this issue also waits for #1411 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.
