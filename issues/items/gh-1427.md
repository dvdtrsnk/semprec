## Context

Model tier rationale: One known mechanism (registering a module manifest in the full registry) across defined seams with existing module-load fixtures, but it activates a new module and owner process for every tenant and edits several shared registration files.

There is no calendar module in the backend today. Modules are composed by `loadFullModuleRegistry` in `backend/packages/data/src/manifest/fullModuleRegistry.ts` (its `ALL_MODULE_IDS` and `MANIFEST_PATHS`), custom routes are mounted from the registry by `backend/services/semprec-api/src/app.ts`, and a system-owned property is only accepted by `core.driftCheck` when its `owner_process` is a member of `KNOWN_OWNER_PROCESS_IDS` (`backend/packages/data/src/manifest/knownActionIds.ts`); otherwise the check reports it as an orphan.

This issue registers an empty `calendar` module so that every later calendar issue (calendars, invitations, reminders, recurrence, timeline, agent tools) adds its databases, routes, actions and tools to one existing manifest instead of racing to create it. It adds no database, route, action or tool and changes no behavior.

Decision: the module id is `calendar` and it is also the owner process of the system-owned properties of the module's databases (for example the status of an invitation), exported as `CALENDAR_MODULE_ID`.

Decision: the module is non-removable and a system project module (`removable: false`, `systemProject: true`), like the Inbox and Mail modules.

Shared-file ordering: this issue also waits for #1411 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys` and `testing`.

1. Add `backend/packages/data/src/calendar/calendarModuleId.ts` exporting `CALENDAR_MODULE_ID = "calendar"`.
2. Add `backend/packages/data/src/calendar/calendarModuleManifest.ts` exporting `manifest: ModuleManifest` with `id: CALENDAR_MODULE_ID`, `version: "1.0.0"`, `name: "Calendar"`, `removable: false`, `systemProject: true`, and empty `databases`, `capabilities` and `agentTools`. Give it a header comment in the style of `inbox/inboxModuleManifest.ts` stating what the module will own.
3. Add `backend/packages/data/src/calendar/i18n/cs.json` and `en.json`, each initially `{}` (an empty catalog is valid; later issues add keys).
4. Register the manifest in `backend/packages/data/src/manifest/fullModuleRegistry.ts` (`ALL_MODULE_IDS` and `MANIFEST_PATHS`), and mirror the same two lists in the tests that enumerate the full module set: `backend/packages/data/src/__tests__/moduleRegistryLoadAll.unit.test.ts` and `backend/packages/data/src/__tests__/systemI18nCatalogCoverage.test.ts`.
5. Add `CALENDAR_MODULE_ID` to `KNOWN_OWNER_PROCESS_IDS` in `backend/packages/data/src/manifest/knownActionIds.ts`.
6. Export `manifest as calendarModuleManifest` and `CALENDAR_MODULE_ID` from `backend/packages/data/src/index.ts`, and add both names to the frozen export list in `backend/packages/data/src/__tests__/publicSurface.test.ts` (this issue extends the public API on purpose).
7. Add `calendar` to the domain folder list of the `chokepoint-knows-no-domain` rule in `backend/dependency-cruiser.rules.json`, so the choke point cannot import calendar code directly.
8. Tests: the full registry loads with the calendar module and no id, name or key collision; the module appears in `/api/schema` with no databases; the owner-process orphan check accepts a property whose owner process is `calendar`.
