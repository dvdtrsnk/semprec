## Context

Model tier rationale: Raising and resolving one deduplicated problem from two existing failure points in the same transactions, using an already-defined problem store, with some ordering and deduplication care.

A failing mailbox should appear in the Semp status as one problem per mailbox, merged from repeated reports, and disappear when the mailbox syncs again. The storage and merge behavior of problems is #1459; this issue connects mail to it. Failure facts (`failing_since`, failure kind) come from #1497.

Today the failure points are in `backend/packages/data/src/mail/mailSyncJob.ts` (a failed pass writes `mail_sync_error` once per job and sets `syncStatus` `error` or `needsReauthorization`) and in the `mail:<mailboxItemId>` observability check (`observabilityCheckSystem.ts`, `mail_sync_stalled`). A successful pass writes `syncStatus` `ok` in `mailSyncJob.ts`, and the check returns to `ok` on its next tick.

Decision: the problem source key is `mail:<mailboxId>`; its start time is `failing_since`, and each report increments the occurrence count. A revoked credential (`needsReauthorization`) is raised as critical; other failures use the problem store's non-critical level for background failures.

Decision: `needsReauthorization` produces only the problem; no additional notification kind is created.

## Task

Apply `docs/adr/2026-11-03-semp-problem-occurrences-retain-episode-receipts.md` within its exact scope.

Load `state-writes` and `testing`.

1. In `mailSyncJob.ts`, in the same transaction that records the failure, raise the problem for `mail_sync_error` and for `needsReauthorization` (critical) using the problem store from #1459, with `since = failing_since`.
2. In the `mail:<mailboxItemId>` check, raise the problem when the check transitions to alerting for `mail_sync_stalled`, with the same source key, so it merges with the sync job's report. Reload and row-lock the current account state inside that transition transaction in the same state-before-problem lock order as sync; a stale enumeration snapshot cannot resolve a newer failure or raise an obsolete one.
3. Resolve the problem in the transaction in which `mailSyncJob.ts` writes `syncStatus` `ok` after a successful pass, and when the check returns to `ok`; resolving an absent problem is a no-op.
4. A connection-limit rejection does not raise a problem on its own; it is raised only if the mailbox stays failing and the stall check alerts.

## Acceptance criteria

- When a mailbox fails several times, then exactly one problem exists with the key `mail:<mailboxId>`, since equal to `failing_since` and the occurrence count equal to the number of reports.
- When the token is revoked, then the problem is critical.
- When the next pass succeeds, then the problem is resolved in the same transaction as `syncStatus` `ok`.
- Within the same persisted active problem episode, a retried job id does not add an occurrence twice, including A, B, retry A. A new episode after recovery has its own receipts.

- Episode receipts are tenant-local, transactional and retained until problem deletion; duplicate reports can still escalate severity without another count, and rollback/pruning/purge preserve receipt consistency. Known prior last keys are seeded lazily, without fabricating unknown historical keys.
- An observability transition reads current locked account state, so a concurrent newer failure cannot be resolved from stale enumeration data; prove both relevant ordering outcomes through actual producers.
