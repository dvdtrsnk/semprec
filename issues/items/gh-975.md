**Blocked by:** #973

## Context

Every later tenancy issue has to prove isolation with two tenants under a runtime role. The test tier as it stands cannot do that:

- **Superuser connections.** Every integration and e2e test connects as the embedded superuser: `getTestPool()` builds `new Pool({ connectionString: TEST_DATABASE_URL })` (`backend/packages/data/src/testSupport/testDb.ts:56-62`), and `TEST_DATABASE_URL` names `postgres` (`globalSetup.ts:105-106`). Superusers and table owners bypass row-level security, so a superuser-based isolation test proves nothing.
- **No second tenant.** The unique index `tenants_single_tenant_guard` (#968) makes a second tenant impossible.
- **Reset by a fixed table list.** `resetDatabase` truncates a hard-coded `TABLES` list (`testDb.ts:8-54`, `64-83`) that already misses `agent_guidance_drift_findings`, which no cascade reaches. After #972, every tenant table references `tenants(id)`, so test tenants can only be removed once every table holding their rows is empty.

The pieces this issue builds on:

- **From #968:** `tenants(id, status ∈ provisioning|active|suspended|deleting, created_at, status_changed_at)` with tenant zero, plus three SQL functions:
  - `app_current_tenant()` returns `NULLIF(current_setting('app.tenant_id', true), '')::uuid`;
  - `app_sole_tenant()` returns the only tenant's id or NULL;
  - `app_tenant_default()` returns `COALESCE(app_current_tenant(), app_sole_tenant())`.
- **From #973:** RLS on the 43 tenant tables, restricted by `tenant_id = (SELECT app_tenant_default())`.

Consequence for tests: once a second tenant exists, the sole-tenant fallback is NULL. Scope-less reads under a runtime role then see nothing, and scope-less inserts fail on `NOT NULL`. That is the intended fail-closed behaviour, and the harness must document it.

The existing precedent for runtime-role tests is `__tests__/leastPrivilegeRoles.test.ts:15-41`. It sets a random password on `semprec_data`/`semprec_side` with `ALTER ROLE` and logs in as them. Integration files run one at a time (`backend/vitest.integration.config.ts:19`, same for e2e), and globalSetup's `process.env` assignments reach every test file, as `TEST_DATABASE_URL` does. Code under `testSupport/` outside `__tests__/` is scanned by the write-safety gate, which flags a `DELETE`/`UPDATE` whose result is never checked (`.github/scripts/check-write-safety.mjs:1-15`, `:54-56`).

## Task

Load `db-migrations` (catalog and guard), `io-hardening` (pool acquisition and release) and `error-handling` (setup failure paths).

1. `backend/packages/data/src/testSupport/globalSetup.ts`: after the migrations and post-migration steps (`globalSetup.ts:111-120`), and before `pool.end()`:
   - read `SELECT app_sole_tenant() AS id`, throwing if it is NULL;
   - export the id as `process.env.TEST_TENANT_ZERO_ID`;
   - run `DROP INDEX IF EXISTS tenants_single_tenant_guard`. Use `IF EXISTS` so the setup keeps working after the go-live migration removes the guard itself. Comment that this happens in the test database only.
2. `backend/packages/data/src/testSupport/tenantFixtures.ts` (new):
   - `getTenantZeroId(): string` reads `TEST_TENANT_ZERO_ID`, throwing a clear error when it is unset.
   - `createTestTenant(pool: Pool, options?: { status?: "provisioning" | "active" | "suspended" | "deleting" }): Promise<string>` inserts a `tenants` row (default `active`) and returns its id.
   - `createRuntimeRolePool(adminPool: Pool, role: "semprec_data" | "semprec_side"): Promise<Pool>`:
     - sets the role's password to a value generated once per module load (`randomUUID()`) via `ALTER ROLE ... WITH PASSWORD` on `adminPool`. Each call re-applies it, because other files, such as `leastPrivilegeRoles.test.ts:38-39`, set their own;
     - returns `createPool(<TEST_DATABASE_URL with that user and password>)` from `backend/packages/data/src/db/pool.ts:19-35`, the production pool constructor, so later pool-level behaviour applies to these pools too. The caller ends the pool.
   - `withTenantTransaction<T>(pool: Pool, tenantId: string, fn: (client: PoolClient) => Promise<T>): Promise<T>` runs `withTransaction(pool, ...)` with `SELECT set_config('app.tenant_id', $1, true)` as its first statement.
   - A file-level docstring stating the harness rules:
     - isolation assertions use a runtime-role pool, never the superuser pool;
     - while a second tenant exists, every write to a tenant table runs inside a tenant (or names `tenant_id`);
     - `resetDatabase` removes every tenant except tenant zero.
3. `backend/packages/data/src/testSupport/testDb.ts`:
   - Rewrite `resetDatabase` to truncate every table in schema `public` except `schema_migrations`, `tenants` included, with `RESTART IDENTITY CASCADE`. Query `pg_class`/`pg_namespace` for `relkind IN ('r','p') AND NOT relispartition`, with identifiers quoted via `format('%I')` or `quote_ident`. Replace the `TABLES` constant.
   - Then re-create tenant zero with `INSERT INTO tenants (id, status) VALUES ($1, 'active')`, using `getTenantZeroId()`, so its id is stable across the run. Insert and truncate keep the write-safety gate satisfied with no unchecked `DELETE`/`UPDATE`.
   - Keep the existing `graphile_worker._private_jobs` truncate and partition drop.
   - Re-export `getTenantZeroId`, `createTestTenant`, `createRuntimeRolePool` and `withTenantTransaction` beside the existing test-only re-exports (`testDb.ts:3-6`), so other packages reach them through `@semprec/data/testSupport` (`backend/packages/data/package.json` `exports`). Nothing is exported from `backend/packages/data/src/index.ts`.
4. `backend/packages/data/src/testSupport/__tests__/tenantFixtures.test.ts` (new, integration) proving the criteria below.

## Acceptance criteria
- After globalSetup, `tenants_single_tenant_guard` does not exist in the shared test database. `getTenantZeroId()` returns the tenant the migration created, and a second `createTestTenant(pool)` succeeds and returns a different id (integration, `tenantFixtures.test.ts`).
- `createTestTenant(pool, { status: "suspended" })` stores status `suspended`. Without options the status is `active` (integration).

- `createRuntimeRolePool` still connects after another file changed the role's password. Simulate this by running `ALTER ROLE semprec_data WITH PASSWORD '<other>'` on the admin pool before calling it (integration).

  - A scope-less `SELECT` on `databases` returns no rows.
  - A scope-less insert fails with SQLSTATE `42501` (the RLS `WITH CHECK` is evaluated before the `NOT NULL` constraint, so `23502` is unreachable for the runtime role).
