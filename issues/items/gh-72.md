## Context

Issue #26 (IMAP Sync Core, merged into develop) built the three sync adapters
(IMAP/imapflow, Gmail REST, Graph REST) over the shared schema, but deliberately
deferred live push-based sync (IMAP IDLE, Gmail Pub/Sub push, Graph webhooks) and
bidirectional flag write-back. Both need a `read`/`flags` property on the Emails
schema and a "mark as read" UI action to originate a write in either direction —
neither exists yet. That schema/UI surface is issue #27's scope (Mailbox UI,
sending, and heartbeats over email). This issue is the sync-infrastructure
counterpart: once #27 adds the schema field and the UI trigger, this issue wires
the live-push transport layer underneath it.

## Task

- IMAP IDLE watcher: hold the connection open per Inbox/All Mail folder (Gmail
  limits an account to ~15 concurrent IMAP connections), renew every <29 minutes
  per RFC 2177, and trigger an early reconcile pass on push instead of waiting
  for the periodic timer.
- Gmail Pub/Sub pull subscription: register via `users.watch()`, renew daily
  (7-day validity), and process `historyId` push notifications by calling
  `history.list`.
- Graph webhook subscription: register against the account's public HTTPS
  endpoint (from issue #40's Caddy/TLS setup), validate within the 3-second
  window Graph requires, renew before the subscription's lifecycle expiry
  (24h-7d depending on subscription type), and process `deltaLink`
  notifications.
- Bidirectional flag write-back: when a user (or the AI) marks a message
  read/unread/flagged in our UI, issue the corresponding provider write — IMAP
  `STORE ... FLAGS.SILENT`, Gmail `users.messages.modify`, Graph `PATCH` —
  sourced from whatever UI action issue #27 adds.
- A long-lived composition-root process to host the IDLE connections and
  push-subscription renewal loops — none of the adapters from #26 stand this up.

## Scope

### In scope

- The three push/IDLE transport mechanisms above.
- The write-back path, once #27 provides the UI trigger and schema field it
  reads from.

### Out of scope

- The `read`/`flags` schema property itself and any "mark as read" UI — both are
  #27's surface, this issue only consumes them.
- Concurrent-insert hardening beyond what #26's `message_id` `ON CONFLICT`
  already provides (noted separately on #26's closing comment, not part of
  this issue).

## Acceptance criteria

- Marking a message read in our UI is observably reflected in the real mailbox
  (visible via a second IMAP/Gmail/Graph client) within one push-notification
  round trip.
- A push notification (IMAP IDLE trigger, Gmail Pub/Sub message, Graph webhook
  call) triggers a reconcile pass without waiting for the periodic timer.
- All three subscription/watch mechanisms self-renew before expiry without
  manual intervention.
