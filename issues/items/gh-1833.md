## Context

Model tier rationale: One additive relation on an already locked, already delivered schema, following an existing cutover pattern, with an idempotency requirement for tenants that have the module and a read-route extension.

The sleep card in the app currently belongs to the Health area by a fixed client rule, because the backend knows no link between the sleep settings and an area. This issue lets the settings item point to the one area whose page shows the sleep card, so the client can place the card from data and the sleep route can say which area it is. It is built only after the product confirms that the card is tied to a chosen area instead of the fixed Health rule; until then no relation and no `areaId` exist and clients keep the fixed rule.

The `sleepSettings` schema is locked by #1776, and existing tenants received the module through #1779, so a new property cannot be created through the normal property API (`assertDatabaseSchemaUnlocked` in `propertiesStore.ts` rejects it); a code-level cutover is the only way, as in `backend/packages/data/src/transcription/transcriptsCatalogCutoverMigration.ts`. Relations are single edges written with `PUT /api/items/:id/relations/:key/:targetId`, which only adds an edge; a one-to-one definition rejects a second edge with `409 cardinality_violation` (trigger `enforce_relation_cardinality`, migration 0013), and replacing the edge atomically is `relation.set` from #1521. The seed file `seed/seedSleepModule.ts` is edited in the order #1776, #1808, then this issue; the sensitivity issue also adds its own idempotent cutover step, so this issue appends another.

Decisions:
- The relation is one-directional (no inverse property on Areas, whose schema is locked), cardinality `one_to_one`, key `area`, owner user.
- Until a user sets it, no edge exists and `areaId` is null; the server sets no default edge.
- Deleting the edge is allowed through the existing relation delete (an agent needs approval).

Shared-file ordering: this issue also waits for #1830 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. In `backend/packages/data/src/seed/seedSleepModule.ts` create the `area` relation property on `sleepSettings` to the Areas database (`createRelationPropertyWithClient`, `one_to_one`, no inverse) before the schema is locked; pass the Areas database id from `seedSystem.ts`.
2. Add `backend/packages/data/src/sleep/sleepSettingsAreaCutoverMigration.ts` (modeled on `runTranscriptsCatalogCutoverMigration`): in a transaction, return when the `sleepSettings` database or the Areas database is missing or the `area` property already exists; otherwise lock `properties`, insert the relation property, the relation definition (`one_to_one`, `property_id_b` null) and the property config with raw SQL (the helper refuses locked schemas). Register it in `backend/packages/data/src/db/tenantCutoverMigrations.ts` after the cutover steps already there.
3. Extend `loadSleepNights` and the response of `GET /api/sleep/nights` (#1809) with `areaId`: the target item of the settings item's `area` edge, or null.
4. Tests: a new tenant has the relation; an existing tenant gets it from the cutover and a second run changes nothing; a second edge from the settings item returns 409 `cardinality_violation`; after `relation.set` to another area the settings item has the new area without a 409; `GET /api/sleep/nights` returns the edge's `areaId` or null.

## Scope

### In scope

- The `sleepSettings.area` relation for new and existing tenants and `areaId` in `GET /api/sleep/nights`.

### Out of scope

- Who sets the area (onboarding, a new settings screen) and the client placement of the card: not planned yet; it waits for a product decision.
- Changing the area type or locking Areas differently: not planned yet; it waits for a product decision.
- The atomic replace operation: #1521.
- Marking the sleep databases as sensitive: #1808.

## Acceptance criteria

- When a new tenant is provisioned, or the cutover runs for an existing tenant, then `sleepSettings` has a one-to-one `area` relation to Areas; a second cutover run changes nothing.
- When a second edge is added from the settings item to another area, then the response is 409 `cardinality_violation`.
- When `relation.set` points the settings item at another area, then the item has the new area and no 409.
- When `GET /api/sleep/nights` is called, then `areaId` is the id of the related area, or null when none is set.
