**Blocked by:** #124

## Context

Issue #123 stores MCP servers in the Semprec-owned `mcpServers` system database with a strict connection configuration for `stdio`, `sse`, or `http`, and keeps their credentials encrypted in `external_credentials` through the existing credentials package. Two later issues need to open a live connection to such a server: the human-only `Synchronize tools` action (#125, which calls `tools/list`) and the outbound MCP-invoke adapter (#128, which calls `tools/call` inside `semprec-agents`). This issue delivers the single connection factory both of them reuse, so transport handling, credential injection, and cleanup are implemented once and contract-tested once. It writes no registrations and exposes nothing to agents.

## Task

Implement one MCP client connection factory as a shared module that both the sync action (#125) and the invoke adapter in `semprec-agents` (#128) import; neither of them may re-implement transports.

- Input is an `mcpServers` item (its stored transport configuration from #123). The factory opens the connection for the configured transport — `stdio`, `sse`, or `http` — completes the MCP `initialize` handshake, and returns a connected client handle plus an explicit `close()`.
- Credentials: resolve the server's credential from `external_credentials` and decrypt it only at connection time, for connection use only; inject it in the transport-appropriate place (for `sse`/`http` as the request authorization/header material, for `stdio` into the child process environment or arguments as the stored configuration declares). The plaintext credential must never appear in logs, thrown errors, the serializable state of the returned client, or anything persisted.
- Cleanup: `close()` releases the transport (terminates the `stdio` child process, closes the SSE/HTTP session). A failed connect or handshake releases whatever was opened before rethrowing. Callers use a try/finally discipline the factory documents.
- Errors: reject a malformed or unsupported transport configuration and a credential decryption failure before opening any connection, with a safe typed error that carries no secret; connection/handshake failures are mapped to the same safe error shape so #125 can record them as the server's sync error.
- Structural non-reactivity: the client does not register any handler for `notifications/tools/list_changed`; a server emitting it has no effect on the connection or on anything else in the system.
- Contract test servers: add minimal MCP contract servers for all three transports to the test support code, each recording the handshake and the credential it received, so this issue's tests and later #125/#128 tests run against identical servers.

## Scope

### In scope

- The connection factory for stdio, SSE, and HTTP, the `initialize` handshake, credential decryption and injection, cleanup, safe error mapping, and the three contract test servers.

### Out of scope

- Calling `tools/list`, validating its response, and materializing registrations — the sync action in #125.
- Calling `tools/call`, argument validation, grant checks, and result mapping — the invoke adapter in #128.
- Reactive sync, `list_changed` handling, automatic trust or classification.

## Acceptance criteria

- For each of stdio, SSE, and HTTP, the factory connects to the contract server from the stored `mcpServers` configuration, completes the handshake, and the contract server observes the injected credential; the plaintext credential is absent from logs, thrown errors, and the returned client's serializable state.
- After `close()`, and after a failed connect, no child process or open socket remains (tests assert this for all three transports).
- Malformed/unsupported transport configuration and credential decryption failure produce the safe typed error without opening a connection.
- A contract server emitting `notifications/tools/list_changed` causes no observable effect; no handler for it exists.
- This issue writes no `mcp_tool_registrations` rows and exposes no AgentTool or MCP operation.
