**Blocked by:** #1543, #1557
**Model tier:** medium

## Context

Model tier rationale: One extension of an existing thread detail read with a bounded join and a derived flag, using the thread store and fixtures from blockers.

The Semp thread detail endpoint (built by #1543) returns a conversation. For a tick thread the client also needs the header of the automation: its name, rule, whether it is enabled, the project it belongs to, whether it can be started now, and whether a run is in progress. Today that information exists only in `project_heartbeats` (`name`, `rule`, `enabled`, `project_item_id`; `backend/packages/data/src/scheduler/schedulerStore.ts`) and in `agent_runs` (`heartbeat_id`, status). Tick threads are written by #1557, which also links runs to the thread.

Decisions: the rule is returned structured (the rule type in `backend/packages/data/src/scheduler/rule.ts`); the label "every Sunday at 21:00" is formatted by the client in the user's timezone. `canTrigger` is true when the heartbeat is enabled and its rule is not `onItemEvent` (event rules fire only from the write that produced the event). `activeRun` is the agent run of this thread that is still running.

## Task

Load `state-writes`, `io-hardening`, `canonical-keys` and `testing`.

1. For a thread of kind `tick`, extend `GET /api/semp/threads/:id` with `heartbeat: {id, name, rule, enabled, projectItemId, projectName, canTrigger}` and `activeRun: {agentRunId, startedAt} | null`. Other thread kinds return neither field (absent, not null).
2. `projectName` is the name of the project item; a deleted heartbeat or project yields a response consistent with the thread detail rules of #1543 (no error for a thread that still exists).
3. `activeRun` is the single run with this `thread_id` and status `running`, if any.
4. Add the fields to the shared response type and the route's response validation. The responses obey tenant isolation (a thread of another tenant is not found).
5. Tests: header of a weekly heartbeat; `canTrigger` false for a disabled heartbeat and for an `onItemEvent` rule; `activeRun` set while a run is running and null afterwards; a chat thread has no `heartbeat` field.

## Scope

### In scope

- `heartbeat` and `activeRun` on the thread detail of a tick thread.

### Out of scope

- Writing runs into the thread: #1557.
- Per-message run timing and status: #1563.
- The manual trigger itself and its error codes: #1453.
- Formatting the rule into text.

## Acceptance criteria

- GET of a tick thread returns `heartbeat` with `name`, structured `rule`, `enabled`, `projectItemId`, `projectName` and `canTrigger`, and `activeRun` null when nothing runs.
- While a run of this thread is running, `activeRun` carries its id and start time.
- `canTrigger` is false for a disabled heartbeat and for an `onItemEvent` rule.
- A chat thread's detail has no `heartbeat` or `activeRun`.
