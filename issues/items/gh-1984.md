**Blocked by:** #1943, #1976, #1978
**Model tier:** high

## Context

Model tier rationale: Cancels asynchronous work across processes whose state may already have advanced (running, finished, or half-written), where a race leaves orphan items or double execution.

A confirmation can queue follow-up work: a transcription job for an uploaded recording, and a tool sync for a newly connected MCP server. #1943 reopens a confirmed card and reverses its synchronous writes, but a job queued by the confirmation would still run afterwards and recreate what the undo removed.

- The transcription job is keyed `transcription-job:<fileItemId>` (`backend/packages/data/src/transcription/transcriptionJob.ts`, `transcriptionJobKey`, `findTranscriptionJobId`) and creates the Transcripts item only when it runs, so before it runs there is nothing to remove, and after it ran there is a Transcripts item to soft-delete.
- #1978 adds the confirmation that queues that transcription, and #1976 queues the MCP tool sync after an MCP server proposal is confirmed. Both record `followUp` (`transcriptionQueued`, `mcpSyncQueued`) in the card's `results[]` (#1648).

Decision: cancellation is best effort for a job that is already running: the undo marks the job cancelled and soft-deletes whatever it already created; a job that finishes later finds its input gone and completes as a no-op (the job handlers re-check their source item). A speaker mapping needs nothing here, since deleting the edge in #1943 is the whole undo.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In the reopen-from-`confirmed` transaction of #1943, for every `results[]` entry with `followUp`:
   - `transcriptionQueued`: remove the queued job by its key if it has not started; if a Transcripts item already exists for the file, soft-delete it (and let the file's own removal follow the item's step as already reversed).
   - `mcpSyncQueued`: remove the queued sync job for the server item if it has not started; if it already ran, the tool registrations it wrote are removed with the soft-deleted server item by the existing server-removal hook.
2. Make the job handlers (transcription job and MCP sync) return without writing when their source item is soft-deleted or gone.
3. Use the jobs' existing enqueue-in-transaction helpers' inverse so that the job removal is part of the same transaction; do not add a new job table.
4. Tests: undo before the worker picks up the job removes the job; undo after a finished transcription soft-deletes the Transcripts item; a handler invoked after the undo writes nothing; undo of a card with no follow-up touches no job.

## Touches

- backend/packages/data/src/inbox/undoConfirmedProposal.ts (follow-up cancellation step)
- backend/packages/data/src/transcription/transcriptionJob.ts (cancel helper and no-op when the source is gone)
- backend/packages/data/src/mcp/mcpSync.ts (cancel helper and no-op when the server is gone)
- backend/packages/data/src/inbox/__tests__/ (follow-up cancellation tests)

## Scope

### In scope

- Cancelling queued transcription and MCP sync jobs, removing a finished transcript item, and making the handlers safe against a removed source.

### Out of scope

- The reversal of synchronous writes and the `updatedAt` precondition; #1943.
- Cancelling a job that is mid-execution beyond making its completion a no-op.
- Speaker-mapping undo, which needs no job handling.

## Acceptance criteria

- When a confirmation that queued a transcription is undone before the job runs, then the job no longer exists.
- When it is undone after the transcription finished, then the Transcripts item is in the trash.
- When a transcription or MCP sync handler runs for an already removed source item, then it completes without writing.
- When the confirmation queued no follow-up, then no job is touched.
