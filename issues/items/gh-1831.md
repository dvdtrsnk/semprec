**Blocked by:** #1773, #1829
**Model tier:** medium

## Context

Model tier rationale: One APNs payload extension on an existing adapter with existing fake-sender fixtures, but it touches a push contract the iOS client registers actions against, so the payload shape must be exact.

After #1773 an approval push says what Semp wants to do, but it still cannot be acted on from the notification and does not break through a focus mode. `sendApnsNotification` in `backend/packages/data/src/push/apnsAdapter.ts` builds only `{ aps: { alert }, link_href, notification_id }`. iOS needs `aps.category` to show the Approve / Reject / Open actions registered by the app, an identifier to say which request the action applies to, and an interruption level so a pending approval is delivered immediately.

This issue builds on the interruption-level mechanism and the per-category preference of #1443, the collapse id, thread id and expiration of #1829, and the sleep-window hold of #1794. #1891 (badge) builds on it. The decision itself is made by the app calling the existing `PATCH /api/approval-requests/:id` with its Bearer session; nothing changes on that endpoint.

Decision: the request id travels in the APNs payload as `approvalRequestId`, taken from the notification's `source_id` when `source_table = 'approval_requests'`; no new column is needed.

## Task

Load `io-hardening` and `testing`.

1. Extend `NotificationPushPayload` (`pushSenders.ts`) with optional `apns: { category?: string; approvalRequestId?: string; interruptionLevel?: "time-sensitive" }`, filled in `notificationFanoutJob.ts` for notifications of kind `approval_pending`: category `APPROVAL_REQUEST`, `approvalRequestId` from `source_id`, interruption level supplied by the classification and preference filter of #1443 (time-sensitive for this kind, and omitted when the user's setting for the approval category does not allow it).
2. In `sendApnsNotification` add `aps.category`, top-level `approvalRequestId` and `aps["interruption-level"]` when present; the collapse id and thread id headers/fields come from #1829 and are not set here.
3. Web Push payloads are unchanged.
4. The payload never contains MCP argument values or the request description beyond the body already rendered by #1773.

## Scope

### In scope

- `aps.category`, `approvalRequestId` and the time-sensitive interruption level on approval pushes.

### Out of scope

- Registering the actions and the Time Sensitive entitlement in the iOS app.
- The body text: #1773. Collapse id, thread id: #1829. Badge: #1891.
- The preference storage itself: #1441.
- The link target: #1787.

## Acceptance criteria

- The APNs request body for an approval notification contains `aps.category = "APPROVAL_REQUEST"`, `aps["interruption-level"] = "time-sensitive"`, `aps.alert.body` and `approvalRequestId` equal to the request id.
- When the user has switched the approval category off or to a quiet setting, the interruption level is not time-sensitive (the mechanism of #1443 decides).
- A notification of any other kind has no category or `approvalRequestId`.
- The payload contains no MCP argument values.
- Deciding an already rejected request with PATCH leaves it `rejected` and returns that status (existing behavior, covered by a regression test).
