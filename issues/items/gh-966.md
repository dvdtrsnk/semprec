## Context

`recomputeJournalInboxDay` (`backend/packages/data/src/inbox/journalInboxCompute.ts:209-232`) is the handler behind the `JOURNAL_INBOX_RECOMPUTE` queue task (`backend/packages/data/src/worker.ts:130`). It rebuilds one Journal day's cached Inbox list under `computed.inboxItems`.

It takes a raw client with `pool.connect()` and runs every statement as its own auto-committed statement:
1. it resolves the pipeline databases;
2. it computes the list (`computeJournalInboxItems`, `:88-172`, many reads);
3. it writes it with `writeComputed` (`:215`);
4. it reads the item back for `updatedAt` (`:219`);
5. it calls `notifyInvalidation` directly (`:220-228`).

So the computed list, the write and the announcement are not one unit. A concurrent recompute or edit can interleave between the reads and the write. The invalidation is tied to no transaction outcome, and the write goes around `withTransaction`, the sole transaction opener (`docs/adr/2026-09-29-withtransaction-is-the-sole-transaction-opener.md`).

Its comment (`:216-218`) says it mirrors `recomputeRollupCell`. That function has since moved to the pattern this codebase expects (`backend/packages/data/src/rollup/recompute.ts:102-145`):
- one `withTransaction`;
- `lockItemById` on the target first, returning quietly when the item is gone;
- `writeComputed`;
- the invalidation registered with `runAfterCommit`, so a rollback publishes nothing.

`docs/adr/2026-09-10-side-effects-follow-the-commit.md` records the rule. `writeComputed` returns the row's `updated_at` (`backend/packages/data/src/chokePoint/itemsStore.ts:448-463`). It throws when no row matches (`:461`), which today fails and retries the job for a day item that no longer exists.

This is one of the pre-existing defects fixed first in the multi-tenancy program. #1025 stamps the publisher's tenant onto every invalidation and relies on each publication following a committed `withTransaction`.

## Task

Load `state-writes` (a write plus its after-commit side effect) and `error-handling` (a rollback path).

1. Rewrite `recomputeJournalInboxDay(pool, journalDayItemId)` in `backend/packages/data/src/inbox/journalInboxCompute.ts` as a single `withTransaction(pool, async (client) => …)` that mirrors `recomputeRollupCell`. Inside it:
   1. Resolve the pipeline databases. Return when any is missing, as today.
   2. Run `const day = await itemsStore.lockItemById(client, databases.journal.id, journalDayItemId)`. When it is `null`, return without writing or publishing. Locking first serializes concurrent recomputes of the same day, so the list written is computed from the latest committed state.
   3. `computeJournalInboxItems(client, databases, journalDayItemId)`.
   4. `const updatedAt = await writeComputed(client, databases.journal.id, journalDayItemId, JOURNAL_INBOX_COMPUTED_KEY, items)`.
   5. `runAfterCommit(client, () => notifyInvalidation({ scope: "item", databaseId: databases.journal.id, itemId: journalDayItemId, op: "update", updatedAt }))`.

   Then delete the raw `pool.connect()`/`release()` and the post-write `getItemById` read. Replace the stale comment with one that cites `recomputeRollupCell`. Import `withTransaction` and `runAfterCommit` from `../db/pool.js`. `handleJournalInboxRecomputeTask` and every `enqueueJournalInboxRecompute*` function stay unchanged.
2. In `backend/packages/data/src/__tests__/journalInboxCompute.test.ts`, add three tests using the existing helpers `captureItem`, `journalDayIdFor` and `computedInboxItems`. Capture events with `setInvalidationHook` from `../realtimeHook.js`, and restore a no-op hook in `afterEach`. Call `recomputeJournalInboxDay` directly so that unrelated choke-point events never interleave.
   - **Success:** exactly one `{ scope: "item", databaseId: journalId, itemId: dayId, op: "update", updatedAt }` event. Its `updatedAt` equals the day item's `updatedAt` read after the call, and the cache holds the captured item.
   - **Rollback:** use a COMMIT-failing pool built like `backend/packages/agent-runtime/src/__tests__/startupRepair.test.ts:194-212`, which intercepts `COMMIT` and discards the contaminated client on release. The call rejects with the injected error, no event is published, `computed.inboxItems` is unchanged, and a later unrelated `withTransaction(pool, async () => undefined)` publishes nothing.
   - **Missing day:** `recomputeJournalInboxDay(pool, randomUUID())` resolves, and nothing is published.

## Scope

### In scope
- Moving the recompute into one `withTransaction` with a row lock, and announcing it through `runAfterCommit`, plus the three tests.

### Out of scope
- Carrying the tenant on invalidation payloads and delivering only to that tenant's sockets: #1025.
- Running the queue task inside a tenant scope: #982.
- Any change to what the cached list contains, to enqueueing, or to job keys.
- Every other `notifyInvalidation` call site, all in `backend/packages/data/src/chokePoint/` and `backend/packages/data/src/rollup/recompute.ts`. They stay unchanged.

## Acceptance criteria

- When a day's recompute commits, exactly one item invalidation for that day is published. It carries the committed `updatedAt`, and the cache holds the day's Inbox items (integration, `journalInboxCompute.test.ts`).
- When the recompute's `COMMIT` fails, the call rejects with that error and no invalidation is published, then or by a later transaction. The day's cached list is unchanged (integration, same file).
- When the day item does not exist, the recompute resolves without writing or publishing (integration, same file).
- The existing cache tests pass unchanged: capture, matching day, type after tick, confirm, reject, revise, deleted item (integration, same file).
- `recomputeJournalInboxDay` no longer calls `pool.connect()` directly (review).
