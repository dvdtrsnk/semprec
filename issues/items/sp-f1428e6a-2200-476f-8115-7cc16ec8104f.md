### Requirement gh-1821: [agent-runs 11/21] Serve agent run steps over REST with a step-aligned cursor

#### Context

Model tier rationale: One new read route with a cursor pairing rule over an existing event table, using the existing handler, authorization and route-matrix fixtures; no write path, schema change or new isolation contract.

The only way to read a run's events today is the realtime watch `agent:watch {runId, afterEventId}` in `backend/packages/realtime/src/agentRunWatch.ts`, which replays `listAgentRunEventsAfter` (no limit) and then streams the raw `agent:event` frames; `agent:delta` carries live typing text. There is no REST read of a run's progress, so a client cannot open a finished run, page through a long one, or recover after a reconnect except by replaying raw events. `backend/services/semprec-api/src/agentRunHandler.ts` knows only `GET /api/agent-runs/:id` and `POST /api/agent-runs/mcp-credentials`; the prefix `/api/agent-runs/` is already routed to it in `app.ts`.

This issue adds `GET /api/agent-runs/:id/steps` which groups the stored events into steps and pages over them with a cursor that never splits a tool call. It is the paging and pairing mechanism only. The presentation fields of a step (localized title, target name, change, result summary, approval steps; arguments and results are never returned) are added by #1847; the approval state of an approval step by #1862; scoping to one chat reply by #1889.

Authorization is the same as the run detail from #1805: the run is read under the caller's tenant (another tenant's run is invisible and answers 404) and a run whose `actorUserId` is not the session user also answers 404, the defense in depth pattern of `agentRunWatch.ts`.

Decision (live clients): the realtime `agent:event` and `agent:delta` frames stay raw signals. A client that sees one issues a new `GET .../steps?after=<nextCursor>`; the projection lives only on the server and nothing is duplicated into the realtime protocol.

Decision (history gone): events of finished session runs older than the retention window and before a compaction checkpoint are deleted (`backend/packages/data/src/agentRuns/agentRunEventsRetention.ts`). The response sets `truncatedHistory: true` when the run's first stored event is not its opening `run_status` event (which every run writes first), and still returns the remaining steps.

Shared-file ordering: this issue also waits for #1812 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1847: [agent-runs 13/21] Project typed, localized step titles, targets and changes

#### Context

Model tier rationale: This projection decides what of a tool call is shown to the client, so a leaked argument or result exposes credentials or approval arguments, and it adds a new locale-dependent catalog and several response fields at once; at this uncertainty the higher tier is chosen.

#1821 serves `GET /api/agent-runs/:id/steps` with steps grouped and paged but carrying only identity, timing and state. This issue fills in what a client shows for each step, using the structured tool event fields from #1424 (operation, MCP registration, target ids), #1527 (approval request id, field changes) and #1374 (interrupted calls written as ordinary error results).

Each step additionally carries: `title`, `targetName`, `change {property, from, to}`, `summary`, and for approval steps `approvalRequestId` (the state of an approval step is #1862). The title is localized on the server by the session user's `users.locale` from a message catalog keyed by operation and target database. Example titles: `database.query` over the task database is "searching tasks", `item.patch` in the task database is "changing a task", `item.create` is "creating a task" (written in `cs` and `en`). Title, target name and change are separate fields so that a client can compose both a run-detail row (title plus "<target>: <property> -> <value>") and a chat row (title plus target, with the change as meta). This catalog is also the one the per-reply step summary uses (#1860), so it lives in a shared module, not in the handler.

Today a title cannot be derived for a call without an `operation`; rows stored before #1424 fall back to a generic title built from the model-facing `name`, with no target.

Decisions:

- Thinking blocks of the model are never returned (decided by the product owner: the user sees steps, tools and the result, which is enough for an audit). A model "plan" step is the assistant message that precedes tool calls; its text is not returned.
- What a step exposes (decided by the product owner): only the structure of the step: the tool (`operation` or the MCP server and tool), the state, the time, the link to an approval request and a localized result summary. `summary` is rendered from a catalog key and structured parameters (for example a result count), never from result text. Tool arguments, tool results, the model's text and raw error text are never returned, the same as for the `conflictReason` of approval requests. `change` is composed only from the structured `details.changes`, and a tool result redacted as sensitive (#1827) yields no `change`.

- The `end` step summarises counts: number of tool steps and number of approval steps, so a client can show "3 tools, no approvals".

### Requirement gh-1862: [agent-runs 14/21] Derive the approval step state from the approval request

#### Context

Model tier rationale: One state-mapping mechanism joining an existing table to the step projection, with a fixed mapping table and existing fixtures; it reads data only and adds no new contract.

A run that asks for an irreversible action does not stop: the tool returns "awaiting a decision" and the run finishes as `done`. The request then lives in `approval_requests` (`backend/packages/data/src/mcp/approvalRequestsStore.ts`): `status` is `pending`, `approved` or `rejected`, and `execution_status` is `not_approved`, `queued`, `succeeded`, `conflict` or `legacy_terminal`. A `conflict` covers every failed execution (the source changed, the MCP tool failed, the grant was revoked, a stuck claim was settled), told apart only by `execution_result_jsonb`. A client showing the run needs one simple per-step state, not these two columns.

#1847 marks a tool step that created an approval request as an `approval` step with its `approvalRequestId`. This issue adds the live `approvalState` of that step, computed at read time from the request row, so the same step reads "waiting", then "executing", then "executed" as the request moves on, without any event being written to the run. When the step's state is derived, the step `state` for `pending` is `waitingApproval`.

The conflict wording comes from #1437, which defines `approval.outcome.failed` for a failed MCP tool call and the `approval.conflict.*` reason keys inside `execution_result_jsonb`.

Decision: the step has no state of its own beyond this mapping; a client learns about a change from the approval request invalidation (#1789) and the agent run invalidation (#1863) and re-reads the steps.

#### Task

Load `state-writes` (read side only) and `testing`.

1. In the step projection, read the approval requests of all approval steps of a page in one batched query (by id, under the caller's tenant; a request that cannot be read leaves the step with `approvalState` absent, never an error for the whole page).
2. Map `approvalState` as: `pending` when `status = pending`; `executing` when `status = approved` and `execution_status = queued`; `executed` when `execution_status = succeeded`; `failed` when `execution_status = conflict` and `execution_result_jsonb` marks the failure as an MCP tool call error (`approval.outcome.failed` per #1437); `conflict` for any other `conflict` or for `legacy_terminal`, with `conflictReason` set to the `approval.conflict.*` key from `execution_result_jsonb`; `rejected` when `status = rejected`.
3. Set the step `state` to `waitingApproval` while `approvalState` is `pending`, to `error` for `failed` and `conflict`, and to `ok` otherwise; add `approvalState` and `conflictReason` to the step shape.
4. Tests, one per mapping row, with an approval request fixture in each state, plus: the same step read before and after a decision returns the new state; a missing request does not break the page.

#### Touches

- backend/packages/data/src/agentRuns/agentRunStepPages.ts (approval state fields)
- backend/packages/data/src/mcp/approvalRequestsStore.ts (batched read by ids, only if none exists)
- backend/packages/data/src/index.ts (barrel export, only if a new read is added)
- backend/packages/data/src/__tests__/agentRunStepProjection.unit.test.ts
- backend/services/semprec-api/src/__tests__/agentRunSteps.test.ts

#### Scope

##### In scope

- `approvalState`, `conflictReason` and the `waitingApproval` step state computed at read time.

##### Out of scope

- Writing the conflict reasons and the failed-outcome marker into `execution_result_jsonb`: #1437.
- Realtime invalidation of the request or the run: #1789, #1863.
- Posting the outcome into the requesting conversation: #1772.
- Waking or continuing the run after a decision: it stays finished.

#### Acceptance criteria

- When the request is `pending`, then the step has `approvalState: "pending"` and `state: "waitingApproval"`.
- When the request is approved and queued, then `approvalState` is `executing`; once it succeeds, `executed`.
- When the request is rejected, then `approvalState` is `rejected`.
- When the data changed before execution, then `approvalState` is `conflict` with a `conflictReason` of the form `approval.conflict.*`.
- When the MCP tool call failed on execution, then `approvalState` is `failed`.
- When a step's request cannot be read, then the page is still returned and that step has no `approvalState`.

### Requirement gh-1860: [semp-replies 02/08] Store a typed step summary on each Semp reply

#### Context

Model tier rationale: This writes a permanent, user-visible summary of tool inputs and results that must exclude sensitive-database content and survives event retention, and it spans the tool result shape, a new migration and token attribution, so a mistake leaks data or mis-states what the agent did.

A Semp reply in chat shows a summary line ("3 steps - 4 s", "2 steps - waiting for you", "2 steps - failed", "3 steps - 9 s - on the second try") and an expandable list of steps, each with a description, a short detail line, a duration and a state of ok, waiting or error. Today none of this is stored with the reply. The raw material exists only as `agent_run_events` (`backend/packages/data/src/agentRuns/agentRunEventsStore.ts`): `tool_use { toolCallId, name, arguments }` and `tool_result { toolCallId, name, result, isError }` as written by `backend/services/semprec-agents/src/piAgentSession.ts`, with `at` as the write time. Token usage is only in `ai_gateway_calls` (`aiGatewayCallsStore.ts`), without a link to a reply until #1744 adds `ai_gateway_calls.semp_message_id`.

This issue computes the summary once, at the end of a turn, and stores it with the assistant message so it is available in message history after retention and without joining events.

It builds on the queued turn handler (#1727), which writes `agent_run_id`, `event_from_id` and `event_to_id` on the assistant message; on structured tool results (#1527: `details.approvalRequestId` and `details.changes` of `{ key, before, after }`); on the typed step projection (#1847: title, target name and change as i18n keys); on token attribution (#1744); on MCP failure kinds (#1444); and on the Semp-thread run model of heartbeat ticks (#1557). #1885 (changed items), #1890 (whether a reply left a failed tool call), #1889, #1887 and #1932 read what is stored here.

Decision: a step of kind `model` is recorded only for an intermediate model generation, that is an assistant message in the turn that carries text and is followed by further tool calls or by a later assistant message in the same turn. The final assistant message of a turn is the reply itself and is never a step. "N steps" counts tool steps plus model steps.

Decision: `errorCode` on a generic operation tool result is introduced here: when a generic operation fails with a `ChokePointError`, the tool result carries `details.errorCode` equal to `ChokePointError.code` (today `genericOperationAgentTools.ts` only puts the code into the result text). For MCP tool results the code is the `failureKind` from #1444.

Decision: what a step may show of inputs and results is conservative. `detail.params` carry only counts, durations, timestamps, names of targets and the `before -> after` of fields from `details.changes`. They never carry free text from tool arguments or results, and for items in a database marked sensitive they carry neither `detail.params` nor `before -> after` (the same redaction as #1827). Steps are stored permanently, outside event retention, so this rule is applied when writing, not when reading.

### Requirement gh-1890: [agent-runs 16/21] Derive whether a Semp reply left a failed tool call

#### Context

Model tier rationale: One read-time derivation over typed step data, extending an existing shared status function with fixtures per case, but it depends on the exact step shape that its blockers define, so the tier is not lowered.

A Semp reply can end normally while one of its tool calls failed: a failed or timed-out tool call is ordinary model input, the model answers anyway, and the run or reply ends `done`. Nothing records whether the reply is complete. Semprec's own tools report failure as `details.error` with `isError` false, and pi sets `isError` only on a thrown exception, so a stored run or reply status cannot tell "answered" from "gave up on a failing tool". Without that, lists could not show "failed - GitHub unavailable" for a tick whose tool failed, and a chat reply could not offer to try again.

This issue derives the answer when a reply is read, from data that already exists, with no new column:

- the typed step summary stored on each Semp reply (#1860), where a tick's run has exactly one reply;
- the tool event fields that identify the operation and the MCP registration (#1424) and the regular shape of interrupted tool results (#1374), which let a failed step be matched with a later successful step of the same tool;
- the failure classification of an MCP call (#1444), written into the step's error code, server id, connector name and timeout;
- the shared display status (#1820), which this issue extends. #1907, #1908, #1909, #1910, #1911 and #1915 read the result.

An MCP-triggered run has no reply, so it never has an incomplete outcome.

Decisions:
- Incompleteness is derived from the steps, not announced by the model in a structured final output (the model's own words are not trusted for status).
- A failed step followed by a successful step of the same tool (same operation, or same MCP registration) within the same reply does not make the reply incomplete: a successful retry cancels the earlier failure.
- Summary text uses the server's name in the nominative, with no declension: "{connector} unavailable", "connection timed out ({seconds} s)", "tool {connector} returned an error". The number of seconds comes from the stored `timeoutMs`, not from a constant.
- The text of the final answer is never composed by code; only the status and short reasons are.

#### Task

Load `canonical-keys`, `state-writes` and `testing`.

1. Add one pure function `deriveReplyOutcome(steps)` in a new `backend/packages/data/src/agentRuns/replyOutcome.ts`, taking the typed steps of one reply. It returns `{ outcome: "complete" }` or `{ outcome: "incomplete", incompleteReason, mcpServerItemId?, connectorName?, timeoutMs? }`. A step counts as failed when it has an error code, or is a generic operation whose result carries `details.error`, or is an interrupted tool result; it is cancelled by a later successful step of the same tool. The reason comes from the failure kind of the last uncancelled failed step: `timeout` gives `toolTimeout`, `unavailable` gives `toolUnavailable`, any other gives `toolError`. Export the `incompleteReason` values `toolTimeout | toolUnavailable | toolError` as a constant.
2. Extend the shared display-status derivation from #1820 so that a run whose reply is incomplete reads as `error` (a run that is still `running` or `pending approval` keeps that status; only a finished run is reclassified). Where that derivation needs the reply, it loads it through the same read the reply list uses.
3. Add `errorSummary` for an incomplete reply to the same read, from the catalog mechanism of #1824: new entries `agentRun.incomplete.toolTimeout`, `toolUnavailable` and `toolError` in the cs and en catalogs with `{connector}` and `{seconds}` placeholders. A run closed with an error code keeps the summary of its error code.
4. Add the derived fields to the Semp message read model that the messages endpoint serializes: `outcome` (`complete` or `incomplete`) always, and `incompleteReason`, `mcpServerItemId` and `timeoutMs` only when incomplete. They are computed on every read; nothing is stored.

### Requirement gh-1911: [semp-status 08/12] Raise heartbeat and agent run failures as one problem

#### Context

Runs triggered by a user conversation are excluded: a failed chat turn is a problem per reply (#1931).
