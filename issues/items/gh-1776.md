## Context

Model tier rationale: One known mechanism (a seeded system module with three locked databases, modeled on the existing library module) with existing seed and manifest fixtures, but it edits several shared registration files and must be idempotent.

Semprec has nothing for sleep today: no tables, databases, routes or seed. The pattern for a module that ships its own system databases is the library module: `backend/packages/data/src/library/libraryModuleManifest.ts` plus `backend/packages/data/src/seed/seedLibraryModule.ts`, which creates a system project item (`systemActive: true`, an `agents` text) in Projects, creates each database with `key` equal to `ownerModuleId`, creates its properties, creates a default view and sets `schema_locked`. A module is active only when it is listed in both `ALL_MODULE_IDS` and `MANIFEST_PATHS` of `backend/packages/data/src/manifest/fullModuleRegistry.ts`. `seedSystem.ts` runs once per tenant and returns early for an already seeded tenant, so existing tenants are handled by #1779.

This issue adds the sleep module and its three databases for newly provisioned tenants. Sleep is a per-user feature (one tenant is one user): one settings item, a few sleep plans keyed by the weekday on which the user wakes, and optional per-night exceptions. Later issues build on it: validation and uniqueness hooks (#1784), the night resolver (#1792), existing-tenant delivery (#1779) and database sensitivity marking (#1808). It builds on the same registration files that #1707 and #1427 also edit, so the order of those issues applies to `fullModuleRegistry.ts`, `index.ts` and `dependency-cruiser.rules.json`, and on #1600 for the order inside `seedSystem.ts`. It uses the system-database metadata shape from #1407.

Decisions:
- Owner: all three databases are owned by one new system project item "Sleep" in Projects (`systemActive: true`), like Books and Movies each have their own, so the project can be deactivated but not deleted and later carries its own agent text and grants.
- The three databases are not collections the user browses: their descriptors declare no `overviewOrder` and no `switcherOrder`, so `clientVisible` resolves to false and they are absent from the collection overview and switcher.
- Seeded plan names follow the tenant user's language, like the other seeded names (the calendars of #1600): the tenant user's `users.locale`, `cs` when no user exists yet. Czech gives "Pracovní dny" and "Víkend", English "Weekdays" and "Weekend", taken from the sleep module catalog at seed time. Once written, plan names are user data: they are stored as plain titles and are not localized again (a later change of the user's language does not rename them).
- `showInCalendar` is only the toggle inside the Sleep sheet. Hiding the Sleep calendar in the calendar list is the `hidden` flag of the calendars row with system key `sleep` (#1600), not a sleep setting.

## Task

Load `canonical-keys`, `state-writes` and `testing`.

1. Add `backend/packages/data/src/seed/sleepModuleKeys.ts` exporting the database keys `SLEEP_SETTINGS_MODULE_ID = "sleepSettings"`, `SLEEP_PLANS_MODULE_ID = "sleepPlans"`, `SLEEP_NIGHTS_MODULE_ID = "sleepNights"` (same shape as `libraryModuleKeys.ts`).
2. Add `backend/packages/data/src/sleep/sleepModuleManifest.ts`: `id: "sleep"`, `version: "1.0.0"`, `name: "Sleep"`, `removable: false`, `systemProject: true`, the three databases `{ key, name }` without order fields, `capabilities: []`, `agentTools: []`, and catalogs `backend/packages/data/src/sleep/i18n/cs.json` and `en.json` with `database.<key>.name`, `property.<key>.<property>.name` and `property.sleepSettings.alarmSound.option.<key>` labels, and the seeded plan names `seed.sleepPlans.weekdays.name` ("Pracovní dny" / "Weekdays") and `seed.sleepPlans.weekend.name` ("Víkend" / "Weekend") (Czech and English). Register it in `manifest/fullModuleRegistry.ts` (`ALL_MODULE_IDS` and `MANIFEST_PATHS`), export it from `backend/packages/data/src/index.ts`, and add `sleep` to the domain list of the `chokepoint-knows-no-domain` rule in `backend/dependency-cruiser.rules.json`.
3. Add `backend/packages/data/src/seed/seedSleepModule.ts` exporting `seedSleepModuleInTransaction(client, projectsDatabaseId, viewTypeRegistry, ...)`, modeled on `seedLibraryModuleInTransaction`: resolve the seed locale (the tenant user's `users.locale`, `cs` when no user exists yet), create the project item "Sleep", then the three databases (`name: null`, `key = ownerModuleId`, `system: true`, `ownerProjectItemId` the project), their properties, a default `table` view each, and finally set `schema_locked`. Properties (canonical English camelCase keys):
   - `sleepSettings`: `name` (title); `enabled`, `prepReminder`, `muteSemp`, `alarmSnooze`, `showInCalendar` (checkbox, owner user); `goalMinutes`, `prepReminderMinutes` (number); `alarmSound` (select with options `morning`, `birds`, `piano`, `vibrateOnly`); `systemActive` (checkbox, owner `system`, locked).
   - `sleepPlans`: `name` (title); `wakeDays` (multi_select with options `mon`, `tue`, `wed`, `thu`, `fri`, `sat`, `sun`); `bedTime`, `wakeTime` (time); `alarm` (checkbox); `position` (number).
   - `sleepNights`: `night` (date, the calendar day of the evening, `YYYY-MM-DD`); `bedTime`, `wakeTime` (time); `alarm` (checkbox). An unset value (null) means "follow the plan".
4. Seed default items: one settings item (all checkboxes true, `goalMinutes` 480, `prepReminderMinutes` 30, `alarmSound` `morning`, `systemActive` true) and two plans named from the catalog in the seed locale: `seed.sleepPlans.weekdays.name` ("Pracovní dny" in Czech, "Weekdays" in English) with `wakeDays` mon to fri, `bedTime` 23:00, `wakeTime` 06:45, `alarm` true, `position` 0, and `seed.sleepPlans.weekend.name` ("Víkend" / "Weekend") with `wakeDays` sat and sun, `bedTime` 00:00, `wakeTime` 08:30, `alarm` false, `position` 1. No night items are seeded.
5. Call `seedSleepModuleInTransaction` from `backend/packages/data/src/seed/seedSystem.ts` after the calendars seed of #1600 and after the Projects database exists.
6. Tests: seeding a new tenant yields exactly the three locked databases with the properties and default items above; a Czech tenant (and a tenant seeded before any user exists) gets the plans "Pracovní dny" and "Víkend", an English tenant "Weekdays" and "Weekend"; changing the user's locale afterwards leaves the stored plan names unchanged; `GET /api/schema` returns Czech labels for the sleep select options for a Czech user; the databases resolve `clientVisible` false; `DELETE /api/items/:id` of the settings item returns 403 with `field: "systemActive"` (the existing `itemTrash.ts` guard); plans and nights can be deleted normally.

## Scope

### In scope

- The sleep module manifest, its three locked system databases, default items, labels and the seed for new tenants.

### Out of scope

- Delivering the module to existing tenants: #1779.
- Value validation, one settings item and one exception per night: #1784; one plan per wake day: #1799.
- Computing nights and the HTTP route: #1792 and #1809.

## Acceptance criteria

- When a new tenant is provisioned, then it has three `schema_locked` system databases `sleepSettings`, `sleepPlans`, `sleepNights`, one settings item and the two plans above, and no night items.
- When a new Czech tenant is seeded, then its plans are named "Pracovní dny" and "Víkend"; for an English tenant "Weekdays" and "Weekend"; when the user's locale changes later, the stored plan names stay as they are.
- When `GET /api/databases` is called, then the sleep databases are returned with `clientVisible` false and without overview or switcher order.
- When `DELETE /api/items/:id` is called for the settings item, then the response is 403 with `field: "systemActive"`; deleting a plan or a night item moves it to the trash.
- When `GET /api/schema` is requested by a Czech user, then the `alarmSound` options carry Czech labels; for an English user, English labels.
- When the module registry is loaded with every manifest, then the sleep manifest loads without a collision and the `chokepoint-knows-no-domain` dependency check passes.
