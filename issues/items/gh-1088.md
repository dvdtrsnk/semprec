## Context

Model tier rationale: The page, adapter, route and four outcomes are fully specified against an existing secret-fragment precedent.

Accounts are created only by an admin's invitation; there is no public signup. An admin creates an invitation on the admin page (#1040, #1080) and receives a one-time link `<APP_BASE_URL>/?page=invite#token=<token>`. The token sits in the URL **fragment**, which the browser never sends to the server or puts in a `Referer`, so it cannot reach access logs.

#1087 delivered the public acceptance endpoint. It is rate-limited per IP. It answers an unknown, expired, revoked or already-used token with one uniform 404, so the response never reveals which case applies. One transaction creates the tenant (`provisioning`) and the user (role `member`) and consumes the invitation; the tenant is then provisioned and becomes `active`, and the new user signs in through the normal login page. Accepting does not create a session. This issue adds the web page that link opens.

What exists in the web client:

- The first-account setup wizard is the closest precedent:
  - it is a public page rendered outside `SessionGate` with session bootstrap skipped (`web/src/App.tsx:87`, `:93-95`);
  - it uses a plain-fetch adapter (`web/src/api/setupOperations.ts:47-85`), where 404 maps to `unavailable` and everything else to `retryable`;
  - it strips its token from the address bar on mount without adding a history entry (`web/src/views/setup/SetupWizard.tsx:32-39`, tested in `web/src/views/setup/__tests__/SetupWizard.test.tsx`).
- The password-reset page (#1076) already reads a token from the fragment in `web/src/main.tsx`, using `new URLSearchParams(window.location.hash.slice(1)).get("token")` with an empty string normalised to `null`, and clears the fragment on mount.
- The adapter pattern is `docs/adr/2026-09-29-web-client-calls-the-api-through-operations-adapters.md`.

The backend contract below comes from #1087. Its merged handler (`backend/services/semprec-api/src/invitationHandler.ts`) and PR description are authoritative. If a path or field differs, bind to the merged handler and say so in your PR description.

- `POST /api/invitations/accept` with `{ token, password }`, no session → `200 { user }`, where `user` is the new account's public user (`{ id, email, locale, createdAt, role, … }`). The tenant has already been provisioned when this answers. If provisioning fails, the answer is a 500 and the account cannot sign in.
- Unknown, expired, revoked or used token → `404 { error }`, identical for all four.
- Password shorter than 8 characters → `400 { error, code: "validation_failed" }`, and the invitation is not consumed.
- Per-IP throttling (#1073's limiter) answers exactly as a throttled login does: a non-2xx with the bespoke `{ error, code }` body.

## Task

Load `canonical-keys` (route key `invite`, labels) and `error-handling` (status mapping).

1. **Adapter** — add `web/src/api/invitationOperations.ts` with `createInvitationOperations({ baseUrl, fetchImpl })`. It uses the plain `fetch`, because the visitor has no session. It exposes `acceptInvitation(input: { token: string; password: string }): Promise<{ email: string }>`: a `POST` with a JSON body and `credentials: "same-origin"`, whose response is zod-parsed (`user.email`; extra fields ignored). Status mapping:
   - `404` → `OperationError("unavailable", …, 404)`;
   - any other non-2xx → `retryable` with the status. The message is the body's `error` string, read best-effort as `readErrorMessage` does in `web/src/api/setupOperations.ts:88-96`; otherwise it is `Request to /invitations/accept failed with <status>`;
   - transport and parse failures → `retryable`.
2. **Route** — in `web/src/main.tsx`, when `page === "invite"`, build `invite = { token, operations: createInvitationOperations({ baseUrl: apiBaseUrl }) }`, with `token` read from the fragment exactly as for `password-reset`, and document `?page=invite#token=<token>` in the doc comment.
3. **App** — in `web/src/App.tsx`, add `export interface InviteRoute { token: string | null; operations: InvitationOperations }` and an `invite?` prop. Render `<InvitationAcceptPage … />` outside `SessionGate`, like `setup`, and add `invite` to the condition that skips the session bootstrap.
4. **Page** — add `web/src/views/invite/InvitationAcceptPage.tsx`. All labels come from i18n.
   - On mount, clear the URL fragment with `window.history.replaceState(window.history.state, "", url)`, where `url` is the current URL with `hash = ""`. This adds no history entry; the component keeps its `token` prop.
   - `token === null` → the invalid-link state immediately, with no request.
   - Otherwise, a form with one password field (`type="password"`, `autoComplete="new-password"`, required) and a submit button. Both are disabled while pending. Outcomes:
     - success → the success state names the created account's email and offers a link `?page=login`;
     - `unavailable` (404) → the invalid-link state: one message for invalid, expired, revoked or used, and no retry;
     - `retryable` → the form stays with the message in a `role="alert"` element. This covers the 400 validation message, a throttled request and a 500.
5. **i18n** — add the `invite.*` keys to `en` and `cs` in `web/src/i18n/messages.ts`.

## Acceptance criteria

- `acceptInvitation` posts `{ token, password }` as JSON with same-origin credentials to `/api/invitations/accept` and resolves to the email from a 200 `{ user }` body. A 404 rejects as `unavailable` with status 404. A 400 and a 429 reject as `retryable` with the status and the body's `error` string. A malformed body or a network failure rejects as `retryable` (web unit, `invitationOperations.test.ts`).
- Opening `/?page=invite#token=abc` leaves `/?page=invite` in the address bar with no fragment and an unchanged `window.history.length`, and submitting a password sends `token: "abc"` (web unit, `web/src/views/invite/__tests__/InvitationAcceptPage.test.tsx`).
- A successful acceptance shows the success state with the returned email and a link to `?page=login` (web unit, `InvitationAcceptPage.test.tsx`).
- A 404 rejection shows the single invalid-link message and no form. A `retryable` rejection keeps the form enabled and shows the message in an alert (web unit, `InvitationAcceptPage.test.tsx`).
- With no token, the invalid-link state is shown and `acceptInvitation` is never called (web unit, `InvitationAcceptPage.test.tsx`).
- With an `invite` route, `App` renders the page without the header and never calls `getSession` (web unit, `App.test.tsx`).
- Every new key exists in `en` and `cs`, and `pnpm run verify` passes in `web/`.
