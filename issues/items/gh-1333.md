## Behavior specification

Ticks: own thread, manual run, continuation and project automations.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: ticks-1

#### Adopted decisions
- Should creating, changing or disabling an automation by an agent go through approval -> yes, approval (module tool request of #1791) -> the approval ADR makes agent writes proposals; direct writes would need an ADR exception.
- Continue a tick run after approval outcome only for ticks -> yes -> in chat it would spend budget without a user instruction.
- Disabled heartbeat and continuation -> blocks the continuation (system message stays) -> design note's proposal.
- Rejection also continues, with the knowledge that nothing happened.
- Only heartbeats with action core.agentRun get a thread (design note acceptance).
- Footer states (finished N s / waiting for approval / error) are composed by the client; backend returns run {startedAt, finishedAt, status}; a run waiting for approval is done in the backend and the client reads the approval from steps (#1860).
- #1562 canTrigger = enabled and rule is not onItemEvent.
- Tiers (no hints): #1557 medium, #1562 medium, #1563 low, #1731 high, #1435 low, #1846 high, #1775 high.
- Repeatedly failing automation -> Decided by the product owner: only reported as a problem, never switched off by the system, because the system does not change the user's settings silently; the problem offers a "Disable" action and the person decides (the action is added to the problem actions of #1555, executed through #1551).
- Design texts to unify -> Decided by the product owner: one wording everywhere: the thread of an automatic task is in the Semp tab (each task has exactly one thread), requests from chat are in the Semp tab, and outputs of automatic tasks are in the Inbox. This is a design text change; the backend behavior already matches it.

#### Open questions for the product owner
- Schema of semp_threads: whether heartbeat_id and the partial unique index already exist after #1367 (#1557 adds them if missing).

#### User-visible behavior (epic paragraph)
Every automatic task of a project that runs an agent has exactly one Semp thread; each run is a section with its start time, summary and result, and a footer showing that it finished (with duration), is waiting for approval in the Inbox, or failed. The thread header shows the task name, schedule, whether it is on, the project and whether it is running now, and offers "Run again". The person can ask the thread a question and Semp answers with the knowledge of the task and its recent runs. When a run asked for approval, the decision continues the run in the same section (also after a rejection); in chat that continuation does not exist. New automations are created, renamed, changed and switched off by asking Semp, always via an approval request that the person accepts in the Inbox.


### Decisions: ticks-2

#### Adopted decisions
- Should a repeatedly failing tick be switched off by the system -> Decided by the product owner: no, only reported as a problem with a "Disable" action (listing returns enabled and lastOccurrence.status separately) -> the system never changes the user's settings silently; the person disables the task through #1551.
- Origin column default -> 'system' for all rows, no seed or data change -> design note.
- Manual run response/errors -> 202 {jobKey, activeRun}; 409 heartbeat_running, 409 heartbeat_disabled, existing 409 heartbeat_event_triggered -> from a related issue requirements merged into #1453.
- Listing status derives from the run (display status, error code), not from occurrence status or raw last_error -> design note.
- PATCH accepts only {enabled}; name/rule/task changed by Semp via approval (#1846).
- GitHub issue triggers (onItemEvent for external service) -> out of scope, not planned yet.
- HeartbeatRunningError class added together with HeartbeatDisabledError (design note names only the latter).
- Tiers (no hints): #1438 low, #2 medium, #3 high, #4 medium.

#### Open questions for the product owner
- Should a running job also merge repeated manual triggers at the queue level (currently handled by the 409 check)?

#### User-visible behavior (epic paragraph)
In the project agent screen the person sees the project's own automatic tasks with name, schedule ("Mon to Fri at 8:30"), the last run (OK, waiting for approval, or failed with a short reason) and a switch that turns the task on or off immediately without catching up missed runs. System automations are not listed and cannot be switched. Tapping "Run again" starts a run now (one run even if tapped twice), and a disabled or event-driven task answers with a clear refusal.
