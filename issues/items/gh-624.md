**Blocked by:** #620, #621

## Context

Two related gaps let a provider call outlive the request that started it, or get cut off while its caller is still waiting:

- `backend/services/semprec-ai-gateway/src/shutdown.ts` sets `SHUTDOWN_DRAIN_TIMEOUT_MS = 60_000` (line 13) and its comment derives that from the completion client's `REQUEST_TIMEOUT_MS` in `packages/ai-gateway-client/src/httpAiGatewayClient.ts` (line 11) — "the only caller of this service". That is no longer true: `backend/services/semprec-transcribe/src/audioGatewayClient.ts` calls `/internal/diarize` and `/internal/transcribe` with `REQUEST_TIMEOUT_MS = 10 * 60_000` (line 72), and `audioProviders/pyannoteProvider.ts` polls a job up to `MAX_POLL_ATTEMPTS = 300` times with a 55 s per-request timeout (lines 14-18, 194-213). At the drain deadline `drainServer` calls `server.closeAllConnections()` (line 41): an audio request in its second minute is destroyed while the provider keeps working and bills the call. The systemd unit `deploy/systemd/semprec-ai-gateway.service` sets no `TimeoutStopSec`, so systemd's 90 s default would SIGKILL a longer drain anyway.
- No `AbortSignal` flows from a request into the provider adapters. `completeHandler.ts` and `audioHandler.ts` never observe the client going away; `anthropicProvider.ts` (line 89), `deepInfraWhisperProvider.ts` (line 57) and `pyannoteProvider.ts` (lines 140, 156, 183, 200) each use only `AbortSignal.timeout(55_000)`. When the caller times out or is killed, the gateway finishes the provider call, pays for it, and writes a response nobody reads — and, after E1, settles a reservation for a result no one received.

E1 (see the pull request that closed it) added the reservation/fail path that this issue's abort handling relies on; E5 (see its pull request) reshaped `anthropicProvider.ts`, which this issue edits again. Sibling issue E6 adds retries on top of the signal plumbing delivered here.

## Task

**Drain timeout owned by the gateway, sized to its longest route**

- In `shutdown.ts` export `COMPLETE_ROUTE_TIMEOUT_MS = 60_000` and `AUDIO_ROUTE_TIMEOUT_MS = 600_000` (each with a comment naming the client constant it mirrors: `httpAiGatewayClient.ts` `REQUEST_TIMEOUT_MS` and `audioGatewayClient.ts` `REQUEST_TIMEOUT_MS`), and define `SHUTDOWN_DRAIN_TIMEOUT_MS = Math.max(COMPLETE_ROUTE_TIMEOUT_MS, AUDIO_ROUTE_TIMEOUT_MS)`. Rewrite the lines 6-12 comment accordingly (it must no longer claim a single caller or that systemd's default suffices).
- `deploy/systemd/semprec-ai-gateway.service`: add `TimeoutStopSec=660` under `[Service]` (600 s drain + 5 s `POOL_END_TIMEOUT_MS` + margin). Add `grep -qx 'TimeoutStopSec=660' "$TEST_ROOT/systemd/system/semprec-ai-gateway.service"` next to the existing unit assertions in `deploy/provision.test.sh`.
- New `backend/services/semprec-ai-gateway/src/__tests__/drainTimeout.unit.test.ts`: `SHUTDOWN_DRAIN_TIMEOUT_MS` equals `Math.max` of the two route constants and is `>= AUDIO_ROUTE_TIMEOUT_MS`.

**Client disconnect aborts the provider call**

- `structuredProviders/types.ts`: `StructuredCompletionRequest` gains `signal?: AbortSignal`. `audioProviders/types.ts`: `DiarizationRequest` and `TranscriptionRequest` gain `signal?: AbortSignal`.
- `completeHandler.ts` and `audioHandler.ts`: per request, `const abort = new AbortController(); res.on("close", () => { if (!res.writableFinished) abort.abort(); });` (a `ServerResponse` emits `close` both on completion and on a premature connection loss; `writableFinished` tells them apart). Pass `signal: abort.signal` into the provider request object. In the error mapping after `invoke()` rejects — `completeHandler.ts`'s `catch` around `complete()` and `audioHandler.ts`'s `handleProviderError` — check `abort.signal.aborted` first: when set, `logger.info({ provider, model, path }, "Client disconnected before the provider call finished")` and return without writing to `res` (the socket is gone; E1's `failGatewayCall` has already flipped the reservation to `failed`). `handleProviderError` needs the signal as an argument.
- `anthropicProvider.ts`, `deepInfraWhisperProvider.ts`: `signal: request.signal ? AbortSignal.any([AbortSignal.timeout(55_000), request.signal]) : AbortSignal.timeout(55_000)` on the `fetch` (Node 22 is what `deploy/provision.sh` installs). An abort surfaces through the existing `catch` as `ProviderCallError` / `AudioProviderCallError` with the error's `name` (`AbortError`) in the message, as today.
- `pyannoteProvider.ts`: the same combined signal on all four `fetch` calls, and the polling loop checks `request.signal?.aborted` before each sleep and after it, throwing `AudioProviderCallError("pyannoteAI diarization aborted by the caller")` — so a disconnect stops the loop within one poll interval instead of after up to 300 attempts.

**Tests**

- `__tests__/completeHandler.test.ts` and `__tests__/audioHandler.test.ts` (integration): the fake provider records `request.signal`; a request issued through `fetch` with its own `AbortController` and aborted while the provider is gated → the provider-side signal becomes `aborted`, the handler emits the info log line, the `ai_gateway_calls` row is `'failed'`, and no unhandled rejection or write-after-end error occurs (assert via `process.on("unhandledRejection")` / the capturing logger).
- `structuredProviders/__tests__/anthropicProvider.unit.test.ts`, `audioProviders/__tests__/deepInfraWhisperProvider.unit.test.ts`: the `fetch` stub receives a `signal` that is already aborted when the request's signal was aborted before the call, and the adapter rejects with its provider error class.
- `audioProviders/__tests__/pyannoteProvider.unit.test.ts` (fake timers, as the existing tests): abort the signal during polling → rejects with `AudioProviderCallError` after at most one more poll interval, and no further `fetch` call is made.
- `__tests__/shutdown.test.ts` "uses SHUTDOWN_DRAIN_TIMEOUT_MS when drainTimeoutMs is omitted" (line 247): update the expected value to the computed constant.

## Scope

### In scope

- The computed drain timeout, the systemd stop timeout, the `AbortSignal` plumbing from both handlers through all three provider adapters, the aborted-request log path, and the tests above.

### Out of scope

- Retrying provider responses (sibling issue E6 of this batch) — this issue only threads the signal E6 will honour.
- Capping concurrent audio requests (sibling issue E7) and recording `operation` on audio rows (sibling issue E4).
- Changing `MAX_POLL_ATTEMPTS`, the 55 s per-request timeouts, or either client's `REQUEST_TIMEOUT_MS`.
- Any change to `deploy/deploy.sh`, `deploy/provision.sh`, or the other units.
- Reporting to the caller whether the provider billed an aborted call (unknowable from the gateway).

## Acceptance criteria

- `SHUTDOWN_DRAIN_TIMEOUT_MS` is `600_000` and is computed from the two exported route constants; the unit file carries `TimeoutStopSec=660` and `deploy/provision.test.sh` asserts it.
- When a client aborts `POST /internal/complete`, `/internal/diarize` or `/internal/transcribe` while the provider call is in flight, the provider adapter observes an aborted signal, the pyannote polling loop stops within one poll interval, the reservation row ends `'failed'`, one info-level log line records the disconnect, and the process emits no unhandled rejection.
- When a request completes normally, its provider signal is never aborted (the `close` handler sees `writableFinished === true`).
- `pnpm run test:unit`, `pnpm run test:integration` (in `backend/`) and `bash deploy/provision.test.sh` pass.
