### Requirement gh-1757: [calendar-invites 02/13] Store participant role and invitation state on Event people edges

#### Context

Model tier rationale: It adds a validation contract on a user-writable relation edge where only the server may change one part of the metadata, which is an authorization and ownership boundary on a public write path, and a new read endpoint over the same data.

An Event's participants are the edges of `Events.people` (many-to-many, one-directional, declared in `backend/packages/data/src/seed/seedTenDatabases.ts`). Each edge can carry free-form `metadata`: `PUT` of a relation edge accepts `{ metadata }` for any relation (`backend/services/semprec-api/src/itemsHandler.ts`), and `createRelation` replaces the stored metadata as a whole (`ON CONFLICT ... DO UPDATE SET metadata = EXCLUDED.metadata` in `backend/packages/data/src/chokePoint/relationsStore.ts`). The only validation of edge metadata today is `transcriptSpeakerEdgeWriteHook` (`backend/packages/data/src/transcription/transcriptionSpeakerEdges.ts`), registered in `backend/packages/data/src/domainWriteHooks.ts`. A client also cannot list an Event's participants: relations are not part of the item response, and People has no inverse of `Events.people` until #1664 adds it.

This issue gives the edge a defined shape: the participant's role and, for a person who was invited by email, the state of that invitation. It also adds the read endpoint that returns the participants together. Later issues build on it: #1790 writes invitations in bulk, #1774 sends them and records `sentAt`, #1950 records replies, and #1770 uses the "invited" state when it picks transcript speakers.

Edge metadata shape (all keys English camelCase):

```
{ role?: "organizer" | "attendee",
  invitation?: { status: "pending" | "accepted" | "tentative" | "declined",
                 email: string, mailboxId: uuid,
                 sentAt?: ISO instant, respondedAt?: ISO instant } }
```

An edge without `invitation` is a plain link between the Event and a person: nothing is sent to that person. An edge with `{}` metadata (every existing edge) stays valid and means role `attendee`, no invitation.

Decision: `invitation` can be set or changed only by server code that writes with the system writer kind (#1415). A public write (the generic edge `PUT`) must carry the `invitation` object exactly as already stored, or omit it when none is stored; anything else is rejected with 400 `validation_failed`, never silently overwritten. This is needed because the edge `PUT` replaces the whole metadata object.

Decision: `role: "organizer"` is valid only on the edge to the person that #1509 links to the tenant's user, and an Event has at most one organizer edge. An organizer edge is a link only: it carries no `invitation` and is not copied into a recording's people or into task people.

Ownership handoff (`docs/adr/2026-09-10-single-writer-ownership-model.md`): the `invitation` part of this metadata has exactly one writer, the calendar module's invitation code (#1790, #1774 and #1950), always with the system writer kind. This is recorded in the calendar module manifest.

Shared-file ordering: this issue also waits for #1756, #2032 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#1600 gives each tenant a `calendars` database with one default calendar and links every existing Event to it through the single-valued relation `Events.calendar`. Events created afterwards have no calendar. The choke point offers a per-process registry of item-create hooks (`chokePoint/hooks.ts`, `registerItemCreateHook`, registered in `backend/packages/data/src/domainWriteHooks.ts`; `docs/adr/2026-10-09-item-create-domain-hooks.md`), which runs inside the insert's transaction after a real insert and never on an idempotency-key replay. ### Requirement gh-1759: [collection-query 12/12] Add the database.facets operation

#### Context

Model tier rationale: A new read operation that compiles many per-property aggregate queries from a caller-supplied filter, with an exclude-self rewrite of the filter tree, several property-type-specific rules and a tenant-isolation surface, spanning shared catalog, data layer and REST, so a subtle error silently produces wrong counts on every filter screen.

A filter sheet on a collection shows, next to each choice, how many items would remain if that choice replaced the selection in that property while every other filter stayed (Status: In progress 7, Long-term 6). Nothing in the backend can produce these counts: counts exist only as the choke-point `countItems`, there is no aggregation by property value, and `is_empty` is rejected on relations by `backend/packages/data/src/views/filterCompiler.ts`.

This issue adds one operation, `database.facets`, that returns for each requested property its choices with counts, computed under the caller's filter with that property's own conditions removed ("exclude-self"), with no free-text search. It builds on the batched counts (#1709), the relative-date and numeric conditions (#1522, #1534), numeric filter presets stored on number properties (#1622), the one-extra-hop relation path condition (#1363), relation emptiness (#1526) and the per-database area filters declared in manifests (#1597). Proposal grounding builds on it (#1990).

Decision (product owner): a view variant is not added; a caller that wants facets under a stored view's filter sends that filter as `filter`, with no special operation. Decision: a condition on the facet's own property nested inside `or` or `not` cannot be removed safely, so it is a 400 with `field: "filter"` rather than a guess. Decision (product owner): an archived database is in the trash and is left out of facets as it is of `item.count` (#1709): facets of an archived database count 0, and relation and path facets leave out targets and intermediate items in archived databases (an item whose only edges point there falls into "no value").

Shared-file ordering: this issue also waits for #1757 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1760: [areas-projects 11/13] Read an area overview with counts and upcoming tasks and events

#### Context

Model tier rationale: A new aggregate read crosses four databases through a two-hop relation path (task to project to area), must be correct in the tenant's time zone and tenant-isolated, and is the contract a later summary route relies on.

An area's page shows, above its content: the number of active projects, tiles for tasks due today and for all open tasks, the number of upcoming events, and a chronological "upcoming" list of tasks and events coming from the area's projects, each with its project's own color. Today none of this can be read in one call. The generic query cannot express "task, via its project, belongs to this area" (`views/filterCompiler.ts`) until #1363 (one extra relation hop in filters); counting needs #1709 (`item.count` with grouping). Relations involved, from `backend/packages/data/src/seed/seedTenDatabases.ts`: `Areas.projects` (one-to-many, inverse `Projects.area`), `Projects.tasks` (inverse `Tasks.project`), `Projects.events` (inverse `Events.project`). A task or event without a project belongs to no area. The Projects database also holds five system projects marked `systemActive` that are never shown or counted.

This issue adds `GET /api/areas/:id/overview`. By the program decision recorded in `docs/adr/2026-09-10-single-writer-ownership-model.md`, routes over Tasks and Events are owned by the `systemDatabases` module, so it is a `customRoutes` entry in `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` with justification `single-consumer-read` (a read shaped for one screen), following `createTranscriptSpeakersRouteHandler` in `transcription/transcriptionRouteHandlers.ts`. #1837 (the global overview summary) builds on the active-project rule defined here.

Response:
`{ activeProjectCount, todayTaskCount, openTaskCount, upcomingEventCount, upcoming: [{ kind: "task"|"event", itemId, title, date, timeFrom, timeTo, status, recurrence, project: { id, title, color } }] }` where `project.color` is the project's own `color` property and `recurrence` is the task's active recurrence rule (`tasks/taskRecurrenceStore.ts`) or null.

Rules:
- Eligible projects are those of the area that are not soft-deleted, not `archived` and not `systemActive`. Projects with status `done` stay eligible, so their open tasks count in `openTaskCount` and appear in `upcoming`.
- `activeProjectCount`: eligible projects with status `inProgress` or `longTerm`.

### Requirement gh-1762: [calendar-module 07/15] Serve a calendar agenda list with a date cursor

#### Context

Model tier rationale: One known mechanism (a read-only custom route paging over an existing read function with a keyset cursor) across a defined route seam with existing isolation fixtures, but the cursor must stay stable across pages and days.

The calendar timeline route of #1717 returns every Event, Task and derived entry inside a date range for the calendar views. A list ("agenda") view needs the same entries as one continuing list from a day, in either direction, without the client choosing a range. Today there is no such route and the generic collection queries cover one database at a time.

This issue adds `GET /api/calendar/agenda?from=YYYY-MM-DD&direction=forward|backward&limit=50&cursor=` as a custom route of the calendar module (justification `single-consumer-read`, the same as the timeline). It calls the same timeline read function as #1717 (`readCalendarTimeline` in `backend/packages/data/src/calendar/timelineRead.ts`) and so inherits its item shape, ordering inside a day, hidden-calendar behavior (everything is returned; the client hides by calendar), the exclusion of trashed items and the time zone of the tenant.

Behavior: the response is `{ items: [...timeline items...], nextCursor }`. Items are ordered by day, then by the timeline's order inside a day; forward goes to later days, backward to earlier days (days descending, the order inside a day unchanged). Days with no entries are skipped. An item that spans several days appears once, on the first day it is shown in the direction of travel (for the first page, the `from` day). `limit` defaults to 50 and is at most 200. The server reads the timeline in windows of 31 days and stops when `limit` items are collected or a scan horizon of 366 days from `from` is reached.

Decision: the cursor is an opaque string encoding the day and the id of the last returned item; the next page continues after that item on that day, and if the item no longer exists it continues from the next day. When the scan horizon is reached before `limit`, `nextCursor` points to the day after the horizon so the client may continue, until five years from `from`, after which it is `null`. `nextCursor` is also `null` when nothing is left in the direction.

Decision: an invalid `from`, an unknown `direction`, a `limit` outside 1-200 or a malformed cursor returns 400 `validation_failed`.

### Requirement gh-1764: [tasks-in-events 03/10] Place tasks into events and take them out

#### Context

Model tier rationale: One write mechanism (three custom routes over one system-owned relation) on existing relation-write, route and manifest seams with defined fixtures, but it writes protected system edges and combines an edge removal with a task update in one transaction.

In the calendar a task can be dropped onto an event and becomes part of it: it stays in the Tasks collection with its own date and time, but until the event ends it is shown only inside the event. A task can sit in several events one after another (adding it to the same event again moves that event to the end of the order, and the last one added decides). Today nothing links a task to a host event: the only task-to-event link is `Events.actionItems` (an action item that came out of the event), and a generic relation write cannot create this one, because the relation is protected. #1540 creates the schema: `Tasks.hostEvents` with the inverse `Events.hostedTasks` (many to many), both sides owned by the system with owner process `tasks`, so a generic edge PUT or DELETE answers 403 `owner_violation` and only the Tasks process can write them (`SystemRelationWriteContext` in `backend/packages/data/src/chokePoint/relationEdgeContext.ts`). An edge write replaces the metadata of an existing edge (`chokePoint/relationOps.ts`), and edge writes publish a realtime frame (#1621). When a recurring task is completed, the next instance does not copy these edges (#1673).

This issue adds the routes that put a task into an event and take it out. What the link means for visibility and the task's day is derived in #1780; completing a task inside an event is #1781; listing an event's tasks is #1801; agent and MCP tools for the same actions are #1957.

Decisions:
- Each edge carries the metadata `{ addedAt }` (an ISO instant filled by the server, never taken from the client). Adding a task to an event it already sits in replaces the metadata with a new `addedAt`, which moves that event to the end of the task's order.
- A task with an active recurrence cannot be placed into an event yet: the call is a 400 `validation_failed` on `taskId` (decided by the product owner). Once a single occurrence can be created (#1720), #2012 places only that occurrence and leaves the series as it is.
- A trashed task or event is a 404. A task that is already done can be placed into an event and nothing else changes.
- Removing a task from all events can also give it a new date and time in the same transaction.
