**Blocked by:** #219, #252, #88, #115, #121, #152, #158, #173

## Context

Issue #252 turned the generic catalog into transport-independent descriptors, strict schemas, a `GenericApplicationPort`, and the binding table; #219 added its single neutral implementation in `packages/application` and rebased REST on the bindings. Agents and MCP callers still have no access to it, and the agent runtime package still has no generic tools. This issue adds the two remaining adapters (in-process AgentTools and the authenticated `POST /mcp` endpoint), capability registration and grant-based filtering, run-derived agent identity, and the approval interceptor that routes destructive agent calls through #32's pending-request writer. #89 replaces the plain approval check with the snapshot-bound preflight and the exactly-once locked execution protocol.

## Task

Create AgentTools in `packages/agent-runtime/src/tools/generic` and an authenticated MCP JSON-RPC endpoint `POST /mcp` in `services/semprec-api/src/mcp`, both over the descriptors, bindings, and port of #252. The MCP surface exposes Semprec's own operations; #31's outbound third-party MCP connections remain separate. AgentTool names are identical to the 28 operation names of #219 and MCP names are the same names prefixed `semprec.` (e.g. `database.restore` / `semprec.database.restore`).

Both process composition roots instantiate the same `genericApplicationService` implementation locally with their own injected data-package connection, so there is no service-to-service call and no second write path. `semprec-api` derives the MCP actor from its authenticated session/Bearer context. `semprec-agents` derives the AgentTool actor only from the current persisted `agent_run` (`runId`, `project_item_id`) plus the run's `actor_user_id` defined below; the tool input cannot provide or override these fields. The data package owns use of the privileged `semprec_data` connection internally, consistent with #40; neither service imports a store, SQL, or the other service. Cross-adapter tests run the same port implementation with these two actor factories and prove spoofed identity cannot alter the resulting authorization decision.

Add immutable nullable `agent_runs.actor_user_id uuid references users(id)` and require it non-null for every new root run: authenticated user-triggered roots capture the session user, heartbeat roots capture the single setup-owner user, and delegated runs copy their parent/root `actor_user_id`. Migration backfills from the parent chain, then the sole setup-owner user, and fails rather than guessing if no unique setup owner exists; afterward set NOT NULL. Missing/mismatched persisted run context returns `owner_violation` before tool construction. No request field or project ownership inference participates.

AgentTools derive exactly `{ runId: row.id, agentProjectItemId: row.project_item_id, userId: row.actor_user_id }` of the `AuthenticatedActor` shape defined in #252. REST/MCP human actors omit the agent fields. #87 consumes this exact `agentProjectItemId`, and contract tests assert it across adapters. Enforce the authenticated actor invariant `agentProjectItemId !== undefined` iff both `runId` and persisted matching run provenance exist; otherwise return `owner_violation` before any approval check.

Both adapters call the same authenticated application service used by REST; they do not import stores or SQL. ModuleRegistry capabilities filter the catalog before tool construction. REST and MCP preserve `approval_required` as 403/JSON-RPC error data; in-process AgentTools return the approval request as a synthetic successful tool result. Equivalence means identical authorization decision, approval id, authoritative data, and domain error code, not identical transport status. Runtime-validate every boundary and add parameterized contract tests across all 28 operations for MCP and AgentTool, and REST/MCP/AgentTool parity tests explicitly covering #83's `database_archived`, actor schema parity, relation type/config patch rejection, and relation route resolution versus direct `relationPropertyId` supply.

Register exactly eight capability ids in the core ModuleRegistry manifest — `core.database.read`, `core.database.write`, `core.schema.read`, `core.schema.write`, `core.view.read`, `core.view.write`, `core.item.read`, `core.item.write` — matching the `requiresCapability` descriptor data of #219. AgentTools are constructed only from the running agent's generated permission-manifest grants. MCP uses the authenticated actor's projected grants; a normal authenticated human session projects all eight core capabilities while restricted service/Bearer identities project only explicitly granted ids. Missing capability omits the operation from AgentTool/MCP discovery and invocation returns the same `not_found`/method-not-found surface as an unknown operation, never a present-but-forbidden tool.

After strict input validation, capability/authz, and before invoking `GenericApplicationPort`, the shared invocation interceptor checks approval only when `actor.agentProjectItemId` exists, using the `requiresApproval`/`riskClass` descriptor data of #219. Human REST/MCP actors execute directly; agent AgentTool/MCP calls marked destructive insert #32's pending request through #32's existing approval-request writer with `tool_name = operationName`, `risk_class = 'destructive'`, non-null `agent_run_id = actor.runId`, and payload `{ operationName, canonicalInput, actor: { runId, agentProjectItemId, userId } }`, then return the transport-specific approval result. `approvalExecute` for such a request reloads the request and persisted run provenance, rejects mismatch with `owner_violation`, and replays the same binding through an internal `{ approvedRequestId }` execution context that bypasses only the already-satisfied approval check, never validation/capability/authz. Neither the bypass token nor actor is part of an external schema. Incoming `POST /mcp` uses JSON-RPC `approval_required` error data; in-process AgentTools and #32's outbound third-party MCP-invoke adapter inside `semprec-agents` return the immediate synthetic successful tool result. These are distinct named adapters, so #32 is not superseded. Both reuse the same request writer and differ only in transport projection. Parameterized tests cover all 28 policy rows, synthetic AgentTool result, MCP error data, human direct execution, and tamper rejection. The `resourceSnapshot` payload member, the transactional `DestructiveApprovalPreflight`, the `approval_pending` notification insert, and the locked exactly-once replay protocol are delivered by #89; this issue must not add them.

## Scope

### In scope

- Generic CRUD/query/relation AgentTools, Semprec MCP adapter, ModuleRegistry capability ids and filtering, `agent_runs.actor_user_id` migration/backfill, run-derived actor, approval interceptor over #32's existing writer with binding replay, contracts, and tests.

### Out of scope

- Descriptors, schemas, port, bindings, and capability/approval metadata, delivered by #252; the application service and the REST adapter rebase, delivered by #219.
- Resource snapshots, `DestructiveApprovalPreflight`, `execution_status`/`execution_result`/`executed_at`, locked exactly-once execution, conflict terminalization, and legacy approval migration, delivered by #89.
- Third-party MCP server transports, owned by #31.
- Domain-specific tools or a second persistence API.
- Automatic approval of agent writes.

## Acceptance criteria

- The three adapters reach the same choke-point service and return the same authoritative row/error contracts.
- An ungranted tool is absent rather than present-but-runtime-blocked.
- No agent/MCP path can bypass ownership, version, idempotency, archive, or relation enforcement.
- External payloads are runtime validated and no `any` crosses the adapter boundaries.
- Spoofed actor/user/project identity fields are rejected; only server-derived authenticated context authorizes calls.
- A parameterized test covers the exhaustive eight-capability mapping for all 28 descriptors and proves ungranted AgentTool/MCP operations are absent from discovery and invocation.
- Relation route resolution and `database_archived` parity are covered in all three adapters.
- Dependency tests prove neither service imports the other and AgentTools use the neutral application implementation with actor identity derived from the persisted run only.
- Actor schema parity and relation type/config patch rejection are covered across REST, MCP, and AgentTool adapters.
- Database restore and property discovery are available through REST/AgentTool/MCP, and all 28 operations have exhaustive capability plus approval/risk tests.
- Agent provenance always supplies non-null run FK; missing/mismatched run context returns `owner_violation` before tool construction; the `actor_user_id` migration backfills or fails as specified.
- Incoming MCP error and outbound/in-process synthetic-success projections are tested separately; tampered request/run provenance is rejected with `owner_violation` at replay.
