## Context

Model tier rationale: This changes the ownership of a locked system property across all existing tenants via a cutover and adds a schema column other mechanisms rely on for identity, so an error affects sending checks, routing and duplicate detection.

The `Mailboxes.addresses` property is declared `owner: "user"` in `backend/packages/data/src/seed/seedEmailModule.ts`. The generic item PATCH and the agent's `item.patch` can therefore change it without approval. The sender check in `backend/packages/data/src/mail/send.ts` compares the `from` address against this list, which is why Gmail Pub/Sub routing (`gmailWatchLifecycle.ts`, migration `0071_gmail_watch_address_routing.sql`) was built on `mail_account_sync_state.gmail_watch_email_address` rather than on `addresses`.

Mailbox connection (#1686 for Google and Microsoft, #1736 for iCloud and generic IMAP) needs an address that comes from the provider and cannot be edited by the user, plus a place to remember it for duplicate detection and for checking that a reauthorization signs in the same account. Gmail watch lifecycles (#1739) also need it to be the routing address.

This issue makes the address server-owned and provider-verified; it does not create any mailbox.

Decision: `provider_account_address` is a new nullable, normalized column, unique per tenant when set. Existing Gmail rows are backfilled from `gmail_watch_email_address`; other existing rows stay null until the next reauthorization or edit by the connect flows, and null never blocks anything.

Shared-file ordering: this issue also waits for #1407, #1451 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Add a migration `backend/packages/data/src/db/migrations/NNNN_mail_provider_account_address.sql` (next free ordinal at commit time): nullable `provider_account_address text` on `mail_account_sync_state`, a partial unique index on `(tenant_id, provider_account_address)` where not null, and a backfill from `gmail_watch_email_address` for `gmail_api` rows. Additive and rollback-safe; the router grants and `route_gmail_address` are unchanged.
2. In `mailAccountSyncStateStore.ts` add a typed writer and reader for the column that normalizes with `normalizeEmailAddress` and surfaces a uniqueness conflict as a distinct error the connect flows can map to "already connected".
3. In `seedEmailModule.ts` declare `Mailboxes.addresses` as `owner: "system"` for fresh tenants.
4. Add a per-tenant cutover `backend/packages/data/src/mail/mailboxAddressesOwnerCutoverMigration.ts` that flips the existing property to `owner = 'system'`, idempotently, following `backend/packages/data/src/transcription/transcriptsCatalogCutoverMigration.ts`, and register it in `backend/packages/data/src/db/tenantCutoverMigrations.ts`. The mail module manifest's data migration list is updated if that is where cutovers are declared for this module.
5. Make the onboarding and reauthorization paths the only writers: expose a system write helper for `addresses` (a single address, normalized, with aliases appended by those flows) that #1686 and #1736 call; no route is added here.

## Scope

### In scope

- The `provider_account_address` column, its accessors, the owner change for fresh and existing tenants and the system write helper.

### Out of scope

- Fetching the provider address and creating the mailbox (#1686, #1736).
- Writing `gmail_watch_email_address` from a watch registration (#1739).
- Any change to how `send.ts` reads `addresses`.

## Acceptance criteria

- When a generic `PATCH` or an agent `item.patch` sets `Mailboxes.addresses`, then it is rejected with 403 `owner_violation`, in a fresh and in a cut-over tenant.
- When the cutover runs twice, then the second run changes nothing; a tenant without a Mailboxes database is skipped.
- When two mailboxes of one tenant get the same provider address (any letter case), then the second write conflicts; the same address in two tenants is allowed.
- After the migration, every existing `gmail_api` row with a watch address has the same value in `provider_account_address`.
- Reading and sending with the existing `addresses` value keeps working for mailboxes created before the change.
