## Context

Every systemd unit loads the one production secrets file `/opt/semprec/shared/.env` (`deploy/systemd/semprec-api.service:14`, `semprec-agents.service:14`, `semprec-transcribe.service:14`, `semprec-ai-gateway.service:14`, `semprec-backup.service:6`, `semprec-restore-test.service:9`, `semprec-dead-man.service:8`, `semprec-failping@.service:8`, `semprec-trash-purge.service:8`). That file holds every key of `deploy/shared/.env.example`: 45 at this writing, plus the seven (#977: `APP_BASE_URL` and `SMTP_*`) that issue declares. They include the superuser `SEMPREC_MIGRATE_DATABASE_URL` (`:76-81`), `CREDENTIALS_MASTER_KEY` (`:28-36`) and every provider key (`:117-150`). A compromise of any process therefore yields every secret, including a connection that bypasses row-level security. The ADR `docs/adr/2026-09-24-immutable-releases-behind-an-atomic-current-symlink.md` already states the migrate connection is one "no running service should hold".

What each process actually reads:
- `CREDENTIALS_MASTER_KEY` (`backend/packages/credentials/src/index.ts:65-67`): semprec-api (mail, `mcpSync`, approval replay) and semprec-agents (`backend/packages/agent-runtime/src/mcpInvokeTool.ts:161,240` → `backend/packages/data/src/mcp/mcpConnectionFactory.ts:128`). Never transcribe or the gateway.
- `AI_GATEWAY_INTERNAL_TOKEN`: api (`backend/services/semprec-api/src/projectAgentGuidanceComposition.ts:50`), agents (`backend/services/semprec-agents/src/modelComposition.ts:34`), transcribe (`backend/services/semprec-transcribe/src/transcriptionTask.ts:796`), gateway (`backend/services/semprec-ai-gateway/src/startupConfig.ts:65`).
- Provider keys and prices: the gateway only (`startupConfig.ts:13,66-67,83-89`).
- `APP_BASE_URL` and `SMTP_*` (#977): semprec-api only (`backend/services/semprec-api/src/serve.ts:61,63-80`).
- `SEMPREC_API_DATABASE_URL`: api (`backend/services/semprec-api/src/serve.ts:36`), transcribe (`backend/services/semprec-transcribe/src/serve.ts:9`), and agents since #963. `SEMPREC_SIDE_DATABASE_URL`: the gateway (`startupConfig.ts:59`) and the restore test (`deploy/systemd/scripts/semprec-restore-test.sh:33,60`).
- `SEMPREC_MIGRATE_DATABASE_URL`: only `deploy/deploy.sh:139,150`.
- `POSTGRES_*`: compose (`deploy/docker-compose.yml:14-16`) and the backup (`deploy/systemd/scripts/semprec-backup.sh:14,46-47`).

Later issues build on the groups defined here: #1035 adds the gateway's global AI caps to `ai-gateway`, #1069 rewrites the `master-key` comment, and #1085 runs its deploy-time check under `migrate`. #1063–#1071 harden the same units further.

## Acceptance criteria

- On a fresh host, `provision.sh` creates `/opt/semprec/shared/env` (`0700`) holding the twelve group files (`0600`), each byte-identical to its template, and creates no `shared/.env` (shell test, `deploy/provision.test.sh`).
- Each installed unit's `EnvironmentFile=` lines are exactly the list in Task 2, with `release.env` last on the four long-running units (shell test, `provision.test.sh`):
  - no unit mentions `/opt/semprec/shared/.env` or `migrate.env`;
  - only `semprec-api.service` and `semprec-agents.service` mention `master-key.env`;
  - only `semprec-backup.service` mentions `postgres.env`.
- Splitting a legacy file (shell test, `provision.test.sh`):
  - **Given** a legacy `shared/.env` holding a distinct value for each of the 52 keys plus one unclaimed key;
  - **then** the first run writes every group file with exactly its keys and the legacy values, leaves the legacy file byte-identical, and names the unclaimed key on stderr;
  - **and** neither stdout nor stderr contains any value.
- A second run leaves an operator-edited group file unchanged and installs a missing group file without touching the others (shell test, `provision.test.sh`).
- The compose call uses `--env-file …/shared/env/postgres.env`, and `postgres.env` is installed before that call. Caddy's `semprec.env` is rendered from `monitor.env` (shell test, `provision.test.sh`).
- The migration and seed transient units carry exactly `EnvironmentFile=…/shared/env/migrate.env`. Without that file, `deploy.sh` exits non-zero with "run provision.sh first" before any build, and deploy output never contains a value from it (shell test, `deploy/deploy.test.sh`).
- Across the twelve templates, every key appears exactly once, and the union is the 52 keys listed in Task 1. `SMTP_PORT=587` and `SMTP_SECURE=false` keep their non-empty template values (shell test, `provision.test.sh`).
- `check_outbound_link_settings` warns exactly as before when it reads from the group files (shell test, `provision.test.sh`: #977's assertions moved to `api.env`/`monitor.env`).
- `deploy/README.md`, the compose and Caddyfile header comments, `docs/operations/database-roles.md` and the new ADR describe the group files, each unit's group list and the legacy-file upgrade path (review).

(The shell tests run by hand, `bash deploy/provision.test.sh` and `bash deploy/deploy.test.sh`; they are not part of `pnpm run verify`.)
