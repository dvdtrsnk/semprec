## Behavior specification (approved)

**Goal.** Findings the code-review bot left `open` on merged pull requests — relevant, but too small to iterate on before merge — become right-sized, parallel-friendly issues that a human approves, without anyone auditing pull requests by hand the way #265 did.

**Evidence** (measured 2026-09-25). 263 pull requests are merged into `develop`; 171 carry the bot's review memory; 138 findings are still `open` in it (108 low, 24 medium, 6 high), 103 of them on pull requests ≥ #266. The memory is frozen at the last review before merge, so `open` is often stale: all 6 high findings above #266 are already fixed on `develop` (4 before their own pull request merged, 2 by #369). #265 reached the same conclusion by hand for everything up to #264.

### Part 1 — Harvest (GitHub Action `harvest-review-followups`: deterministic, no AI)

- **H1.** Runs daily on a cron slot off the hour, and on manual dispatch. A manual dispatch takes `dry_run` (default `true`): it reports what it would do and writes nothing. A scheduled run always writes.
- **H2. Backpressure.** While any open issue carries `followups:harvest`, or any open issue carries both `followups:issue` and `spec:proposed`, the run writes nothing and reports which issues are pending. Throughput is bounded by triage and human approval, not by the calendar.
- **H3. Candidates.** Pull requests merged into `develop`, number ≥ `HARVEST_MIN_PR`, without the label `followups:harvested`, in ascending number. `HARVEST_MIN_PR` is the constant `266` in the workflow file, with its reason beside it: #265 audited every pull request up to #264 and found those memory tables stale. It is a fixed floor, never a moving watermark.
- **H4. Memory.** The newest issue comment on the pull request that is authored by `github-actions[bot]` or `bb-agent-relay[bot]` and contains `<!-- crb-memory:v1:z:`; its payload is standard base64 → zlib → JSON. A pull request without one has nothing to harvest. A trusted comment that cannot be decoded, or whose content does not have the expected shape, fails the whole run before any write, naming the pull request.
- **H5.** Only findings with `status: open` are considered. A finding whose `(pr, key)` already has a ledger marker (L2) is never harvested again.
- **H6. Inline threads.** For a finding whose `discussion_id` is numeric (the bot opens an inline thread for medium and above), the harvest reads that review thread. The **only** deterministic skip: the thread is resolved and one of its replies is authored by a trusted bot login with a body that is exactly `Fixed.` — the bot's sole wording for a confirmed fix (code-review-bot `publish.py` replies `Fixed.` and resolves the thread in the same step) → skipped as `fixed`. Every other case is harvested: `threadResolved` records the thread's state and the last three replies are recorded as excerpts (author and the first 200 characters). T2 decides what a reply means.
- **H7.** `pathExists` records whether the finding's path exists on `develop`. A missing path never drops a finding: code moves, and the defect moves with it.
- **H7b. Hints** (never a skip). `touchedAfterLastSeen`: `true` when a commit of the pull request after the finding's `last_seen_sha` modified the finding's path, `false` when none did, `null` when `last_seen_sha` is not in the pull request's commit list (a rebase replaced it; 6 of 103 findings today). `laterPrsTouchingPath`: how many distinct pull requests other than this one have commits on `develop`, committed at or after this pull request's merge, that modified the path. T2 uses both to prioritise its already-fixed check; the verdict stays AI plus evidence.
- **H8. Cap.** Pull requests are taken in order and all harvested findings of one pull request go into the same harvest issue. Taking stops before the pull request that would bring the total above 30 — except that the first pull request with harvested findings is always taken, whatever its count. Pull requests with nothing to harvest before the stopping point are taken too. Pull requests after it wait for a later run.
- **H9. Output.**
  - At least one harvested finding → one harvest issue labelled `followups:harvest` and `followups:ready`. Its body has a readable table of the findings to triage, a table "Skipped — fixed on the pull request", one finding marker per listed finding (harvested and skipped), the harvest marker listing its pull requests, and one JSON block with the harvested findings' records. The records carry no full finding text (T1 fetches it).
  - No harvested finding but at least one skipped → a record-only harvest issue labelled `followups:harvest` only, closed immediately as completed.
  - Nothing at all → no issue.
  - A body that would exceed 60,000 characters (GitHub's limit is 65,536) fails the run before any write.
- **H10.** Pull requests are labelled `followups:harvested` only after the harvest issue exists. A pull request already listed in any harvest issue's harvest marker (a run that crashed between creating and labelling) is labelled and not harvested again.
- **H11.** The run writes a job summary: pending issues, pull requests scanned, findings harvested and skipped, and where the cap stopped.

### Part 2 — Triage (Relay workflow `triage-review-followups`)

- **T0. Trigger.** An open issue labelled `followups:ready`, excluding `agent:blocked` and `agent:needs-human-action`; `respect-blocked-by: false`; one run at a time.
- **T1. Prepare** (deterministic). Reads the harvest issue and drops findings that already have a terminal ledger marker (L3 — an earlier attempt published them). For the rest it fetches the full inline comment text (description and suggested fix) and the thread replies, each pull request's latest review summary, and the open issues labelled `agent:ready`, `spec:approved` or `spec:proposed` with their `## Touches` sections. Everything is written into the run's worktree; the triage agent needs no GitHub access.
- **T2. Verify** (AI, on `develop` HEAD). Each finding gets exactly one verdict: `valid` (still holds; current location recorded — for `pathExists: false` the agent locates the moved code by symbol or snippet search and `git log --follow`), `already-fixed` (with evidence), `invalid` (the bot was wrong, with evidence), `not-worth` (true, deliberately not fixed, with a reason; low severity or small size is never a reason — batching small fixes is what this pipeline is for), or `already-tracked` (an open issue `#N` covers it). The H7b hints and thread replies prioritise the already-fixed check.
- **T3. Decompose** (AI). `valid` findings become issue drafts under `/define-behavior` Phase 4 and `.github/ISSUE_FORMAT.md`: one mechanism per issue, clustered by touched code, never one issue per one-liner, the size gate, a Touches overlap check against sibling drafts and the open issues from T1 (an overlap becomes a real `#N` blocker), protected-path issues flagged as maintainer-implemented, one prescribed fix per finding, fix only what was flagged. Batch slug `followups-<harvest issue number>`. Two or more drafts → an epic draft: a summary specification, a Decisions section, a link back to the harvest issue, a summary of the rejected and already-fixed findings, and a note that closing the epic retires nothing. One draft → no epic.
- **T4. Audit** (AI). One round, two independent auditor subagents using `/define-behavior`'s auditor prompt in dry-run mode, with its consensus gate and growth check. Only agreed or self-verified findings change a draft; the rest become advisories.
- **T5. Validate** (deterministic). The proposal's shape; each draft's title pattern and numbering in topological order; `**Blocked by:**` as the first line; the sections in order; in-batch references that resolve and form no cycle; no pipeline markers in any body; an epic present exactly when there are two or more drafts, linking the harvest issue; **completeness** — every finding from T1 lands in exactly one draft or exactly one rejection with a non-empty reason (and an issue number for `already-tracked`). A failure goes back to the agent with the validator's output; still failing after two rounds, the run parks (`agent:blocked`).
- **T6. Publish** (deterministic, as `bb-agent-relay[bot]`). Re-validates; reuses this harvest's epic if one exists or creates it; creates the drafts in topological order, replacing in-batch references with real numbers, appending one finding marker per finding, labelling each `followups:issue` and `spec:proposed` and linking it as a sub-issue of the epic; posts a triage-result comment on the harvest issue (created issues, rejected findings with their markers and reasons, advisories); removes `followups:ready`; closes the harvest issue. A publish failure parks the run instead of retrying automatically.
- **T7. Re-runs.** Every re-run starts again at T1, whose terminal filter means an already-published finding is never proposed twice. A parked harvest issue stays open, so H2 holds back new harvests until a human resolves it.
- **T8. Integrity.** The deterministic steps run the `develop` copy of the scripts: a worktree whose `.github/scripts/review-followups/` differs in any way from its `develop` fork point parks the run. Only command steps that opt in reach GitHub, through the Relay App's token proxy (the real token never enters the job); agent steps never do.

### Ledger and human decisions

- **L1.** All state lives in GitHub labels and HTML markers. No watermark, no database.
- **L2. Harvest ledger.** Finding markers in the bodies of issues labelled `followups:harvest` or `followups:issue` (any state), plus in triage-result comments by `bb-agent-relay[bot]` on harvest issues.
- **L3. Terminal ledger.** L2 without the harvest issues' bodies.
- **L4. Approval.** A human swaps `spec:proposed` for `spec:approved` + `agent:ready` (an issue touching a protected path gets `spec:approved` only and is maintainer-implemented). To reshape an issue, edit it, then approve it.
- **L5. Rejection.** Closing a proposed issue retires its findings permanently — its markers stay in the ledger. Reopening it is the undo. Closing an epic decides nothing: each child issue carries its own findings and its own decision.

### Labels

| Label | On | Meaning |
|---|---|---|
| `followups:harvested` | merged pull request | Its open findings were harvested (or it had none) |
| `followups:harvest` | harvest issue | Identity of a harvest issue, kept forever |
| `followups:ready` | harvest issue | Waiting for triage — Relay's trigger; removed by publish |
| `followups:issue` | issue or epic created by publish | Identity of a proposed follow-up, kept forever |
| `spec:proposed` | issue created by publish | Awaiting human approval; never dispatched |

### Out of scope

- Changes to `dvdtrsnk/code-review-bot` (full text for low findings, memory updates after merge).
- Arming follow-up issues automatically — `agent:ready` is always a human's decision.
- Pull requests into `main`, pull requests below #266, pull requests that were not merged.
- Semantic deduplication at harvest time (T3 groups duplicates into one draft).
- Notifications beyond GitHub's own.
- A native Relay step kind that creates issues; the Relay change is limited to letting a command step opt into the existing token proxy.
- A technical guard against the triage agent pushing a branch (the workflow has no push step; the rule is in the prompt).

## Decisions

| # | Question | Adopted answer | Reason |
|---|---|---|---|
| 1 | Which identity writes to GitHub from Relay? | The Relay App, through a command-step opt-in to Relay's existing loopback token proxy (dvdtrsnk/bb-plugin-relay) | Agent-originated issues must be distinguishable from the user's own (repo rule 7). Authorship must not depend on the `gh` login the host happens to have — today a command step's `gh` acts as the maintainer's personal account. Through the proxy the real token never enters the job, which is stronger than masking it, and the proxy already re-mints the one-hour token. |
| 2 | Where does the backlog start? | Fixed floor `HARVEST_MIN_PR = 266`, a constant in the workflow | #265 audited everything up to #264 and found those memory tables stale. A watermark was rejected: out-of-order merges and silent skips on failure. |
| 3 | How big is one harvest? | At most 30 findings; a pull request is never split; oldest first; the first pull request is always taken, even above 30 | Keeps a triage within one bounded AI turn and a batch reviewable in one sitting; the exception stops the cap from dropping a pull request forever. |
| 4 | How often does it run? | Daily cron + backpressure (H2) + manual dispatch; `dry_run` defaults to `true` on a manual run, as in `close-completed-epics.yml` | Inflow reaches 48 findings a week, above one weekly harvest of 30; with backpressure, throughput is bounded by triage and approval, and a no-op run costs nothing. |
| 5 | What about a resolved inline thread? | Skip only on a trusted bot's exact `Fixed.` reply; harvest everything else with `threadResolved` and the reply excerpts | "Resolved" is not "fixed": threads get resolved to satisfy conversation resolution before merge — the exact too-small-to-iterate case. A reply such as "will do in a follow-up" must not silently retire a real finding. Measured: 7 resolved threads above #266, 6 with no reply, 1 with a human reply; none carries `Fixed.`. |
| 6 | What about a path that no longer exists? | Harvest it with `pathExists: false`; T2 locates the moved code | The choke-point split moves code between files; a deterministic "obsolete" drop would lose live defects. |
| 7 | Who reviews the scripts? | `.github/scripts/**` joins the root platform's review scope, first in the batch | Today no scope covers it, so the pipeline's core would merge unreviewed. |
| 8 | Do the tests run? | `test:repo-scripts` in backend `verify` plus a step in the `ci` job, failing when no test file exists | Nothing runs tests under `.github/scripts/` today, and `node --test` with a glob that matches nothing exits 0. |
| 9 | When is there an epic? | Two or more issues from one harvest | Same shape as a `/define-behavior` batch; one issue stands alone. |
| 10 | What does closing a proposed issue mean? | It retires its findings; reopening is the undo; closing an epic decides nothing | The ledger reads markers only, whatever the issue's state — deterministic, with an explicit undo. |
| 11 | Where does the full finding text come from? | Fetched by T1 at triage time, not stored in the harvest issue | Low findings have no full text anywhere (only a 300-character clip in memory); medium and above have it in their inline thread. Storing it would push harvest bodies toward GitHub's 65,536-character limit. |
| 12 | How is the ledger read? | Listing issues by label and parsing markers | GitHub search is eventually consistent and may not index HTML comments. |
| 13 | What about memory that cannot be decoded? | Fail the run, naming the pull request | A silent skip would lose findings; a bot format change must surface. A human can label the pull request by hand to skip it. |
| 14 | How strong is the triage audit? | Two auditor subagents, one round | The consensus gate needs two; human approval is the second gate. All agent steps of a Relay run share one thread, so independence needs subagents. |
| 15 | Which verdicts exist? | `valid`, `already-fixed`, `invalid`, `not-worth`, `already-tracked`; severity and size are never a `not-worth` reason | Keeps "the bot was wrong" apart from "it was fixed", and stops the AI from dropping small findings. |
| 16 | What happens when publish fails? | The run parks; no automatic retry | A retry would repeat side effects; T1's terminal filter makes a human-started re-run safe. |
| 17 | How are the scripts built? | Zero-dependency ES modules in `.github/scripts/review-followups/`, `fetch` with `GITHUB_API_URL` / `GITHUB_GRAPHQL_URL` / `GITHUB_TOKEN`, tests with `node:test` | The same code runs in Actions and behind Relay's proxy (`gh` would ignore the proxy URL); follows `close-completed-epics.mjs`. |
| 18 | Does the triage agent touch GitHub? | No; T1 collects every input | Deterministic inputs and a smaller attack surface. |
| 19 | Which issues are armed? | Issues touching a protected path (`.github/workflows/**`, `.relay/**`) carry no labels and are maintainer-implemented; the rest carry `spec:approved`, and `agent:ready` only after #494 closes | `/define-behavior` Phase 5 never arms a protected-path issue. A merge that changes `.github/workflows/` fails the first push of every Relay run branched before it, and a `review-rules/` change invalidates the bot's stored verdicts, so both wait for #494. |

## Ordering and release

- The review-scope issue changes `review-rules/`, which invalidates every stored review verdict; it merges only after #494 closes.
- The three workflow issues (`ci.yml`, the harvest workflow, the Relay workflow) are maintainer-implemented after #494 closes. The first real harvest runs only once the harvest workflow is merged, after #494 — by then many choke-point findings will verify as already-fixed.
- The Relay workflow needs the command-step `github-api` opt-in from dvdtrsnk/bb-plugin-relay#57 deployed on the Relay host; that change is deployed together with the other pending plugin changes.
