## Context

Model tier rationale: bounded ephemeral file/mail PDF/DOCX/plain-text refs with failure notes. Uploads deduplicate, mail extracts only for search. Use existing extractor and two tenant blob roots; Files refs already cover chat uploads. No new producer, ingest change or persistent Files text/indexing.

## Task

Load `io-hardening`, `error-handling` and `testing`.

1. In the ref expander from #1733, for a ref to a Files item or a `mailAttachment`, load the blob (`getBlob` and the blob storage read stream in `backend/packages/data/src/blobs/` and `mail/blobStorage.ts`).
2. If `isTextExtractableContentType` is true and the blob is within a size cap (named constant, 10 MB), call `extractAttachmentText` and add the text to that ref's section, subject to the per-ref character cap from #1733.
3. For a plain text content type within the cap, add the decoded text the same way. For any other type, or an oversize or failed extraction, keep only the metadata (name, type, size) and add a short note saying why no text is shown. After successful stream cleanup, extraction failure does not fail the turn; typed cleanup failure stops expansion.
4. Tests: a PDF and a DOCX fixture yield their text; an oversize file yields the note; an image or unknown type yields metadata only; a corrupt PDF yields the note and the turn proceeds.

## Acceptance criteria

- When a message refs a PDF or DOCX file, then the model context contains its text (up to the character cap).
- When the file is larger than the cap or has an unsupported type, then only metadata and a note are shown.
- When extraction throws after successful owned-stream cleanup, the turn runs; cleanup failure stops expansion.
