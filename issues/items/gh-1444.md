## Context

Model tier rationale: One classification mechanism applied across the MCP execution seam, the connection factory and the agent tool adapter, with existing unit and integration fixtures for each, and no new persistence, authorization or concurrency contract.

MCP invocation and approval execution currently expose free-text failures. Add safe structured failure metadata through invocation, agent tool details and the approval outcome storage boundary; a failed tool call remains model input and need not fail the run. Existing result text and approval lifecycle behavior stay unchanged. Later reply-failure detection/projection belongs to #1890, #1860 and #1907.

Decision: a tool-call timeout is told apart from a user cancellation by checking `signal?.aborted` first (as the code already does), and a connection timeout is told apart from `handshake_failed` by a new connection error reason rather than by parsing messages.

## Task

Load `error-handling` and `testing`.

1. In `mcpConnectionError.ts`, add the reason `connect_timeout` to `MCP_CONNECTION_ERROR_REASONS`. In `mcpConnectionFactory.ts`, make `withTimeout` reject with a dedicated timeout marker so `connectMcpServer` throws `McpConnectionError("connect_timeout", ...)` with a fixed, secret-free message (transport name only) when the handshake does not finish in time. Every other connect failure stays `handshake_failed`; the existing `address_not_allowed` precedence is unchanged.
2. In `mcpToolExecution.ts`, extend `McpInvokeResult` with an optional `failure` object, present only when `error` is true: `{ failureKind, mcpServerItemId, timeoutMs? }` where `failureKind` is one of `timeout | unavailable | connection | auth | toolError`. Export the `McpFailureKind` type and a `MCP_FAILURE_KINDS` constant. Classification inside `executeMcpInvocation`:
   - `timeout`: the SDK's `tools/call` request timeout (`McpError` with `ErrorCode.RequestTimeout`) when the signal was not aborted, with `timeoutMs` set to `MCP_TOOL_CALL_TIMEOUT_MS`; and `McpConnectionError` reason `connect_timeout`, with `timeoutMs` set to the connection timeout in effect;
   - `connection`: any other `McpConnectionError` (including `handshake_failed`, `address_not_allowed`, `transport_not_allowed`, `stdio_sandbox_unavailable`) except an authentication failure;
   - `auth`: `credential_decryption_failed`, and an `McpError`/HTTP authentication rejection (401 or 403) from the server on connect or call;
   - `toolError`: a normal `tools/call` result with `isError: true`, and any other thrown error;
   - a call cancelled by `signal` keeps its current cancelled result and carries no `failure`.
   The `result` text stays exactly as today (no new text reaches the model), and no exception message is copied into `failure`.
3. Mark both "no longer available" rejections as `unavailable`: `resolveMcpInvocation` and `noLongerAvailableOutcome`. Use the known registration or approval payload server id, omitting it only for `unavailable` when unknown. Preserve actual invocation `failure` through `ApprovalRequestOutcome` and the existing JSONB outcome envelope `{text,outcomeKind?,failure?}`. Validate new structured failure metadata at write/read boundaries; malformed metadata fails closed without exposing its values. Preserve legacy outcomes without failure, result text, outcomeKind, execution status and claim/redelivery guards. Successful or cancelled calls acquire no failure. No DDL/backfill or reply projection. An internal `mcpFailure.ts` may hold the shared closed type/validator without changing current exports.
4. In `createMcpTools` (`agentSessionComposition.ts`), write the classification into the tool result: `details` becomes `{ error, failureKind, mcpServerItemId, connectorName, timeoutMs }`, where `connectorName` is the grant's `mcpServerName` and the other keys are omitted when absent. The arguments-not-an-object early return stays a plain `details: { error: true }` without a `failureKind` (it is not an MCP failure). Keep the keys English camelCase.

## Scope

### In scope

- The `connect_timeout` connection reason, the `failure` classification on `McpInvokeResult`, the `unavailable` rejections, and writing the classification into the agent tool result `details`.

### Out of scope

- Deciding whether a reply is complete or incomplete from the classified steps, and the localized error text built from it: #1890.
- Storing the classification on a reply's step summary: #1860.
- Using the kinds as the error codes of a failed Semp reply: #1907.
- Changing the 60 s and 15 s timeout values, retrying a failed call, or changing what the model sees as the result text.
- Tools of Semprec itself that report errors in `details.error`; they are not MCP calls.

## Acceptance criteria

- When a `tools/call` exceeds its timeout and the run was not cancelled, then the result has `error: true` and `failure` equal to `{ failureKind: "timeout", mcpServerItemId, timeoutMs: 60000 }`.
- When the server does not complete its handshake within the connection timeout, then the result has `failureKind: "timeout"` and the connection timeout as `timeoutMs`; when the connection is refused, then `failureKind` is `connection`.
- When a granted server is disabled or its grant revoked, both direct rejection and real queued approval execution retain `failureKind: "unavailable"` with the known server id. A later read preserves classified invocation failures; legacy outcomes without failure stay readable, malformed new failure metadata is rejected, and redelivery cannot replace a settled outcome or invoke it again.
- When the server answers with `isError: true`, then `failureKind` is `toolError`; when credential decryption fails, then `failureKind` is `auth`.
- When the run's signal aborts the call, then the result carries no `failure`.
- The agent tool result for a failed MCP call contains `failureKind`, `mcpServerItemId`, `connectorName` and, for a timeout, `timeoutMs` in `details`; a successful call contains none of them.
- No `failure` field and no log line contains an exception message from the server.
