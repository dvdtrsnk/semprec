**Model tier:** high

## Context

Model tier rationale: It lets inbound email from outside the system change stored participant state, which needs sender verification against the invited address and a system-writer ownership rule on a user-visible edge, so a mistake lets anyone forge a reply.

When the user invites people to an Event (#1774), the attendees answer with an iMIP `METHOD:REPLY` email. The calendar module already reads incoming calendar parts for requests: #1929 delivers the iCalendar parser (`calendar/icalendarParser.ts`), `readCalendarPartsOfEmail` (`calendar/emailCalendarParts.ts`) and the `onItemEvent` create heartbeat on Emails with its seed and cutover. Mail ingest itself must not write calendar data (`docs/adr/2026-09-10-single-writer-ownership-model.md`), so replies are applied the same way: a second heartbeat action of the calendar module on the creation of an Emails item. `person_email_index` and `lookupPersonIdByEmail` (`backend/packages/data/src/mail/personEmailIndexStore.ts`) map an address to a person; `Events.icalUid` (#1599) maps a `UID` to an Event; the participant edge and its invitation metadata come from #1757, whose `invitation` part only server code with the system writer kind may write.

Decision: a reply is applied only when its `ATTENDEE` address is the address of a person who has an edge with an invitation to the Event with that `UID`, and the message's own sender address (`mail_message_meta.envelope.from`) is the same address (case-insensitive). Anything else is ignored with a reason code in the log. Delivery authenticity (SPF/DKIM) is not checked in this version (product owner decision: the sender match is enough for v1).

Decision: the `SEQUENCE` carried by a reply is not compared; the latest reply wins.

Decision: only `PARTSTAT` values `ACCEPTED`, `TENTATIVE` and `DECLINED` change the status (to `accepted`, `tentative`, `declined`); `NEEDS-ACTION`, `DELEGATED` and others are ignored.

Shared-file ordering: this issue also waits for #1941, #1944 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. Add `backend/packages/data/src/calendar/invitationReplyAction.ts` exporting `CALENDAR_APPLY_INVITATION_REPLY_ACTION_ID = "calendar.applyInvitationReply"` and `createInvitationReplyAction(pool, { storage })`, an `ActionHandler` for `onItemEvent` create on Emails with a zod-validated `action_config` (`{ emailsDatabaseId, eventsDatabaseId, peopleDatabaseId }`). In one transaction per email it skips a delivery-status message, reads the calendar parts with `readCalendarPartsOfEmail`, and for each `METHOD:REPLY` `VEVENT`: finds the live Event by `icalUid`; resolves each `ATTENDEE` to a person with `lookupPersonIdByEmail`; checks the sender rule above; finds that person's edge to the Event and requires an existing `invitation`; then rewrites the edge metadata with the same `role` and `invitation` except `status` (from `PARTSTAT`) and `respondedAt` (now), using the choke point's relation write with the system writer kind. Re-processing the same email leaves the same state. A message with no calendar part, another method, an unknown `UID`, an unknown or uninvited attendee, or a sender mismatch changes nothing and never throws; logs carry the email item id and a reason code only.
2. Register it: export from `backend/packages/data/src/index.ts`; add the id to `KNOWN_HEARTBEAT_ACTION_IDS` in `backend/packages/data/src/manifest/knownActionIds.ts`; list it in `heartbeatActions` of `backend/packages/data/src/calendar/calendarModuleManifest.ts`; register the handler in `backend/services/semprec-api/src/actionRegistryComposition.ts` with the same mail attachment storage as the ingest action.
3. Seed the heartbeat in `seedInvitationsDatabaseInTransaction` (`backend/packages/data/src/seed/seedInvitationsDatabase.ts`): name `Apply calendar invitation replies`, rule `onItemEvent` create on the Emails database, in the same system project as the Invitations database. Add `backend/packages/data/src/calendar/invitationReplyHeartbeatCutoverMigration.ts` for populated tenants (idempotent; no-op when the heartbeat or the needed databases are missing) and register it in `runTenantCutoverMigrations` in `backend/packages/data/src/db/tenantCutoverMigrations.ts`.
4. Extend the ownership handoff comment in `calendarModuleManifest.ts` (added by #1757) to name this action as a writer of `invitation.status` and `invitation.respondedAt`.
5. Tests: a `REPLY` with `PARTSTAT=ACCEPTED` from the invited person's address sets `accepted` and `respondedAt` on their edge; `TENTATIVE` and `DECLINED` likewise; a reply from a different sender address, for an unknown `UID`, for a person without an invitation, with `NEEDS-ACTION`, or with a `REQUEST` method changes nothing; a repeated run is a no-op; an invitation written by this action survives the public edge-write rule of #1757 unchanged; a message from another tenant's context cannot reach this tenant's Events.

## Scope

### In scope

- The reply heartbeat action, its sender and attendee checks, writing the invitation status on the participant edge, and its heartbeat for new and existing tenants.

### Out of scope

- The parser and calendar part reader: #1929.
- Sending requests and cancellations: #1774.
- The edge shape and server-only write rule: #1757.
- Comparing `SEQUENCE`: not done; the latest reply wins.
- Resetting statuses when an Event changes: not done (product owner decision); statuses are kept.
- Handling replies to invitations the user received (answers the user sends): #1953.

## Acceptance criteria

- When an invited person's `METHOD:REPLY` with `PARTSTAT=ACCEPTED` arrives from their own address, then their edge shows `accepted` with `respondedAt` set; `TENTATIVE` shows `tentative` and `DECLINED` shows `declined`.
- When the reply's sender address differs from the attendee address, or the attendee has no invitation to that Event, or the `UID` is unknown, then nothing changes.
- When the same email is processed twice, then the state is the same as after the first time.
- When the email has no calendar part or is not a `REPLY`, then nothing changes and the heartbeat does not fail.
