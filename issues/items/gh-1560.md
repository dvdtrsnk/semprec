**Model tier:** high

## Context

Model tier rationale: This changes which agent run events a compaction checkpoint and the retention job may delete, so a wrong grouping silently destroys another conversation's history; it is a wide destructive-data contract.

Today a Semp conversation is identified by `{projectItemId, triggeredBy: 'user', parentRunId: null}` (`SessionAgentRunsFilter` in `backend/packages/data/src/agentRuns/agentRunsStore.ts`). `listSessionAgentRunEventsFromLastCompaction` in `agentRunEventsStore.ts` and `persistCompaction` in `backend/packages/agent-runtime/src/conversationReconstruction.ts` select events by that filter, and `agentRunEventsRetention.ts` groups session runs by `(project_item_id, triggered_by, parent_run_id)` and deletes events older than 30 days that precede the last compaction checkpoint. Every chat thread would share the same key (Semprec project item, user, no parent), so two threads would reconstruct each other's history and one thread's checkpoint would make the retention job delete the other's events.

#1452 added `agent_runs.thread_id` and the `(tenant_id, thread_id, wake_seq)` index. This issue switches the conversation identity of a thread's main conversation to that column. Delegated supervisor sessions are separate sessions keyed by `(target project, 'supervisor', supervisor run)`; they inherit `thread_id` from their parent (see #1452), so the thread key must not pick them up.

Builds on this: #1565 (registry keyed by thread) and #1566 (user turns as events).

## Task

Load `state-writes`, `testing` and `db-migrations`.

1. Extend `SessionAgentRunsFilter` so a thread conversation is `{ threadId, triggeredBy: 'user', parentRunId: null }`. The existing project-item form stays valid for non-thread sessions. In `listSessionAgentRunEventsFromLastCompaction` (and every query that takes the filter) select by `thread_id` using the new index when `threadId` is given, otherwise as before.
2. Make reconstruction and `persistCompaction` in `conversationReconstruction.ts` accept and use the thread filter, so the checkpoint of a thread is written and read only within that thread's runs. A delegated session (a run with a `parent_run_id`, even though it carries the inherited `thread_id`) must never match a thread filter.
3. Change `agentRunEventsRetention.ts`: group the main conversations of threads by `thread_id` (runs with `thread_id IS NOT NULL`, `triggered_by = 'user'`, `parent_run_id IS NULL`); group all other session runs as before by `(project_item_id, triggered_by, parent_run_id)` excluding those thread main conversations. Keep the rule that nothing after the last checkpoint of a group is deleted and nothing is deleted when a group has no checkpoint.
4. Tests (real database): two threads of one tenant each reconstruct only their own events; a checkpoint written in thread A does not hide, and retention does not delete, thread B's events or a delegated session's events; retention still removes old events before a thread's checkpoint and keeps everything after it; non-thread sessions behave as before. Event content is never logged.

## Scope

### In scope

- Thread-keyed selection, compaction checkpoint and retention grouping of the main conversation.

### Out of scope

- The in-memory conversation registry: #1565.
- Persisting and replaying user turns: #1566.
- Interrupted tool call repair: #1568.

## Acceptance criteria

- When two threads of one tenant have events, then reconstructing one returns only its own entries.
- When thread A writes a compaction checkpoint, then no event of thread B or of a delegated session is hidden or deleted by it.
- When the retention job runs, then events after a thread's last checkpoint are never deleted and a thread without a checkpoint loses nothing.
- When a session is not a thread conversation, then reconstruction and retention behave exactly as before.
