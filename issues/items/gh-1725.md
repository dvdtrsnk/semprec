**Model tier:** medium

## Context

Model tier rationale: One operation that writes two places in one transaction (the Pages item and the parent document) over existing item-write and document-write seams, with a clear no-op and orphan behavior.

A subpage opened full screen shows its title at the top; the user edits it there, and the title must change both in the parent document, where the `page` block's text is the title, and on the Pages item, which breadcrumbs (#2014) and the trash read (#1393). A client that has only the subpage open does not hold the parent document, so it cannot write the block itself. #1676 created the Pages database with the system-owned `title` and `parentItemId` properties, `normalizePageTitle` and the page operations file; page operations are generic catalog members (#1394). The mirror job (#1715) also writes the `title` property, from edits made directly in the parent document.

Decisions:
- `page.rename` writes the item title and the block text in one transaction; if no block of the parent document references the page (an orphan), only the item title changes and the call succeeds.
- Renaming to the current title is a no-op that writes nothing.
- The title goes through `normalizePageTitle` (line breaks become spaces, trimmed, at most 500 characters); an empty title is valid and clients show a placeholder.

Shared-file ordering: this issue also waits for #1722 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `page.rename` to the generic catalog (strict input `{ pageItemId, title }`, output `{ pageItemId, title }` with the stored normalized title, port method, binding, metadata as a non-destructive write on the item-write capability), the application service method, and the route and method recorded for it by the ADR of #1394, with `routeMatrix.ts` and tenant-isolation entries.
2. Add `renamePage` in `backend/packages/data/src/docs/pageOperations.ts`, in one transaction: read the live Pages item (404 otherwise; a host item is a `ValidationError` on `pageItemId`); normalize the title; if unchanged return; update the item's `title` through `updateItemWithClient` with the allowed system key (it takes the row lock); load the parent document by `parentItemId` and, in one `mutateDocWithClient` call with the caller's origin, replace the text of the `page` block whose `pageId` equals the page with the new plain title (no inline attributes).
3. Tests: renaming "Release checklist" changes the block text in the parent and the item's `title`, and the breadcrumbs of its subpage read the new title without loading the parent document; the same rename twice writes once; an orphan page renames its item only; a title with a line break is stored with a space; a title of 501 characters is rejected with nothing written; a failed document write rolls back the item change; a foreign tenant's page is a 404.

## Scope

### In scope

- `page.rename`: normalized title written to the item and to the parent's page block in one transaction.

### Out of scope

- Mirroring titles typed directly in the parent document: #1715.
- Renaming a root page title of a host (stored in the document's `meta`): not part of subpages.
- Replacing a whole page from Markdown with a version check: #1765.
- Agent approval classification: #1844.

## Acceptance criteria

- When "Release checklist" is renamed from its own screen, then the parent block text and the Pages item `title` both show the new title, and breadcrumbs "Notes > Release checklist" are composed without loading the parent document.
- When the same title is sent again, then nothing is written.
- When the parent document has no block for the page, then the item title changes and the call succeeds.
- When the title is longer than 500 characters, then the response is 400 with `field` `title` and nothing changes.
