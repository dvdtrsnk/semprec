## Behavior specification

Inbox proposals: relations, multi-step, confirm result, discard, undo.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: inbox-proposals-1

#### (a) Adopted decisions
- Envelope relation shape -> `relations: { [relationPropertyKey]: targetItemId[] }` beside `properties`; empty array = no edge; only on `database` envelopes.
- Does `done` block a project target -> Decided by the product owner: no; a done project is a valid relation target (for example a late invoice). The picker hides it by default (#1959) and Semp does not offer it as a default target (#1987); only `archived` (and deleted) blocks.
- Cardinality pre-check -> reported, not decided; a "one"-side conflict becomes a move only through a multi-step update step.
- Target-side check -> new `assertRelationTargetLinkableWithClient` in relationOps.ts (caller item does not exist yet); error codes `targetArchived`, `targetDeleted` in `details.code`.
- Derived relations (Events.company, Files.area with a project) -> rejected in proposal validation by reusing the choke point predicate from a related issue. May a journal entry carry an area -> Decided by the product owner: yes, like other items; with a project the area is derived, without a project it is the entry's own value (#1991).
- Multi-step shape -> `operations[]` listing all steps including the primary; top-level fields mirror the primary step for compatibility; refs `{ ref }` as relation targets. May an `update` step change other values than relations -> Decided by the product owner: yes; an `update` step is a general property and relation write through the choke point with the same approval and risk rules, and a project's status is not a special case (#1378, #1479, #1486).
- Skipped steps -> disabled, or optional and unreferenced; not validated or written.
- Confirm of steps -> one transaction, dependency order, rollback with 400 `{ref, field}`; move = delete old edge + create new edge; resultItemId/resultLabel = primary step.
- Confirm passes `actingUserId` to item writes (realtime only to the acting user). Author of inserted page blocks -> Decided by the product owner: the user, because the user confirmed the proposal; the card records that Semp proposed them (per-step `blockIds`, #1648; the page-content and journal confirm paths write the blocks as the user).
- Text on the card explaining a move ("moves from area Work") -> Decided by the product owner: yes, the card says what changes, because nothing may happen silently; the server resolves the labels of the values each update step changes (#2028), and the design adds the text.
- Child proposals rejected in favor of one atomic envelope.

#### (b) Open questions for the product owner
- None remaining.

#### (c) User-visible behavior
A proposal can now carry relations (project, area, people, company) that are checked while the card is built or edited and written together with the new item when it is confirmed (everything or nothing). Choosing an archived or deleted project or a non-existent target is refused with the field named, and relations the system derives itself (an event's company when it has a project) cannot be proposed. One proposal can create several things in one confirmation (a file from an attachment and a follow-up task, a company and a new person, a health record and a follow-up task) or change an existing item (move a project to another area, change its status), with the card saying what changes; optional steps can be switched off or dropped, and if any step fails nothing is created.

### Decisions - inbox-proposals-2

#### (a) Decisions adopted
- Where is the origin note in the page written (editable block vs client-composed)? -> Server writes an editable paragraph at confirm time via page insert (#1735) -> editable, and visible to every client and to agents reading the page as Markdown.
- One origin mechanism for all databases? -> `item_origins` side table (#1659); Files read it, no separate Files origin link (as the design note states) -> single mechanism.
- Origin flag for lists -> computed `fromInbox` on the item envelope, set-based, not stored (#1716) -> cannot drift, no schema change per database.
- Item without origin on GET origin -> 404 identical to unknown id (#1967) -> hides existence, matches the design note AC.
- Origin note wording and scope -> Decided by the product owner: written only for items the confirmation created, reading "Created from Inbox: <item name>" (#1735).
- capture_channel values -> `inbox` / `transcript` literal in this chunk (Inbox has no channel property today) -> keeps issue 2 self-contained; richer channels can be added later.
- Discarded item in the Journal (stays struck-through "discarded" or hidden) -> Decided by the product owner: it stays struck-through as discarded, so it can be brought back (today's behavior, #1845).
- ifVersion required or optional -> optional on confirm and reject -> additive-only REST ADR.
- State vs version precedence -> state wins: repeated confirm/reject of a terminal card returns 200 even with a stale ifVersion -> offline replay safety.
- Idempotent response scope -> keyed per (tenant, user, key, route) with request hash, 24 h expiry, 2xx only -> prevents cross-user replay.
- #1894 only wires PATCH values (its blocker is #1892); other card routes call the helper in their own issues -> issue dependency only covers #1892.

#### (b) Open questions for the product owner
- None remaining.

#### (c) User-visible behavior
After confirming a card, the app gets a structured result for every step (which item was created, where it lives, which day it lands on, linked project, and whether a transcription or MCP sync was queued), so it can show a precise toast with a "Show" link. Every item created from the Inbox remembers its origin: the capture time, the source text and the sibling items from the same capture; detail screens can show "Added from Inbox", list rows get a "from Inbox" marker, and the item's page starts with an editable note "Created from Inbox: <item name>". Cards can be discarded on any state with one action, safely retried from offline queues, and a decision made on a stale view of the card is refused with a conflict instead of overwriting newer changes.

### Decisions - inbox-proposals-3

#### (a) Decisions adopted
- Undo for approval cards (deferred approvalExecute with an undo window, or disable undo)? -> Decided by the product owner: an approval card does not support undo; an executed action is reverted by restoring from the trash or by a new change. The exactly-once ADR is untouched (#1379, #1943).
- Time limit on undoing a confirmation? -> Decided by the product owner: no time limit; the stored `updatedAt` precondition is the only guard, and if items changed in the meantime the undo is refused with an explanation (409 version_conflict naming the changed item) and overwrites nothing.
- Reopen of a rejected card -> sets `proposed` if the stored envelope still validates, otherwise `invalid`; recomputes nothing; proposal, overrides and history preserved plus one `reopened` entry -> prior pre-discard status is not recorded.
- Edges on undo -> edges of created items stay and return with a restore; edges between existing items are deleted for good -> edges have no soft delete (relationOps).
- Follow-up job cancellation is best effort: queued jobs are removed; a finished transcription's Transcripts item is soft-deleted; handlers become no-ops when the source is gone -> avoids orphan items without mid-run kills.
- Undo of a confirmation whose attachment already moved to Files -> Decided by the product owner: the undo reverses everything except the file, which stays in Files (the user can move it to the trash), and the undo result says so explicitly (`keptItems`, #1943, #1379); #1703 has no reverse operation.

#### (b) Open questions for the product owner
- None remaining.

#### (c) User-visible behavior
The top-right Undo control in the Inbox returns the last decision to the stack: a discarded card comes back with its previous values, and a confirmed card is taken back as well: the task, event or file it created goes to Recently deleted, links it made are removed, values it changed are restored, inserted page blocks vanish, a connected MCP server is disconnected and its credential is deleted, and a queued transcription or tool sync is cancelled. A file made from a moved attachment stays in Files, and the undo result says so. It can be repeated card by card without a time limit. If the user has edited a created item since confirming, the undo is refused with a conflict so the edit is never lost.
