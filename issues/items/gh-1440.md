## Context

Model tier rationale: A static lookup table beside an existing constant with a compile-time and test completeness check, and no runtime behavior change.

Notifications have a closed list of kinds (`NOTIFICATION_KINDS` in `backend/packages/data/src/notifications/notificationKinds.ts`, enforced in the database by the `notifications_kind_check` constraint). Push delivery treats them all the same: `notificationFanoutJob.ts` sends every notification to every active push registration of the user. The design decides that push is only a pointer, that users can switch whole categories of push off, and that problems (sync failures, stuck assistant and similar) are pushed by severity. For that, every kind needs a category and a severity.

Decision: each kind maps to a category (`approvals`, `invites`, `reminders`, `problems`), a severity for problems (`critical`, `warning`, `info`) and whether it is eligible for push at all. Severity only exists for problems. The mapping is:

- `approval_pending`: approvals.
- Problems, critical: `mail_sync_error`, `mail_sync_stalled`, and for operators `backup_restore_failed` and `process_stale`.
- Problems, warning: `agent_run_error`, `heartbeat_error`, `automation_error`, `agent_guidance_drift`, and for operators `queue_backlog`.
- Problems, info, never pushed: `agent_guidance_drift_resolved`.

Kinds that do not exist yet (a reauthorization kind, invitation, reminder and transcript kinds) are added to the map by the issues that introduce them; the completeness test forces that. The preferences (#1441) and the fan-out filter (#1443) use this map.

## Task

Load `canonical-keys` and `testing`.

1. In `notificationKinds.ts`, export `NOTIFICATION_CATEGORIES`, `NOTIFICATION_SEVERITIES` and `NOTIFICATION_KIND_POLICY: Record<NotificationKind, NotificationKindPolicy>` where `NotificationKindPolicy` is either `{ category: "approvals" | "invites" | "reminders"; push: boolean }` or `{ category: "problems"; severity: "critical" | "warning" | "info"; push: boolean }`, with the values above (`push` is false exactly for `info`).
2. Export a helper `policyForKind(kind)`.
3. Add a unit test that every entry of `NOTIFICATION_KINDS` has a policy, that no policy exists for an unknown kind, that every `info` kind has `push: false`, and that the listed kinds have the listed category and severity.

### In scope

### Out of scope

- A separate push kind for Semp problems: #1466.

## Acceptance criteria

- When a kind is added to `NOTIFICATION_KINDS` without a policy, then the build or the completeness test fails.
- `approval_pending` is in `approvals`; `mail_sync_error` and `mail_sync_stalled` are `problems`/`critical`; `heartbeat_error` is `problems`/`warning`; `agent_guidance_drift_resolved` is `problems`/`info` with `push: false`.
