**Blocked by:** #1645
**Model tier:** high

## Context

Model tier rationale: A multi-row revocation that must stay atomic with push-registration cascades and post-commit realtime events, with a deliberate exclusion of the caller's own session; getting the ownership or ordering wrong signs out the wrong device or leaks a live token.

The signed-in devices screen offers "sign out all other devices" ("you stay signed in on this device only"). Revoking one session already works: `POST /api/auth/sessions/:id/revoke` calls `revokeUserSession` (`backend/packages/data/src/auth/authActions.ts`), which revokes the row via `revokeSessionForUser`, cascades to `revokePushSubscriptionsForSession`, and `fireSessionRevoked` closes that session's `WS /api/sync` sockets with code 4401 after commit. `revokeAllSessionsForUser` (`sessionsStore.ts`) revokes every session including the caller's and does not touch push registrations; password reset uses it together with `revokeAllPushSubscriptionsForUser`.

This issue adds the "everyone except me" operation, as a reusable store function and a route. It builds on #1583 (same handler region, same route-matrix entries). #1687 reuses the store function to replace the previous session of one installation, and #1701 reuses it to keep the current session when the password changes.

Decision: push registrations are revoked through each revoked session (`revokePushSubscriptionsForSession`). Registrations that have no `session_id` (set to NULL when a session row was removed, `0054`) are left alone, because they are not tied to a device being signed out here.

Shared-file ordering: this issue also waits for #1645 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In `sessionsStore.ts` add `revokeOtherSessionsForUser(client, userId, keepSessionId): Promise<string[]>`: `UPDATE sessions SET revoked_at = now() WHERE user_id = $1 AND id <> $2 AND revoked_at IS NULL RETURNING id`, calling `fireSessionRevoked` for every returned id (deferred to commit when `client` is a transaction client). Return the revoked ids.
2. In `authActions.ts` add an action `revokeOtherUserSessions(client, userId, keepSessionId)` that calls the store function and then `revokePushSubscriptionsForSession` for each revoked id, on the same client, and returns the count.
3. In `authHandler.ts` add `POST /api/auth/sessions/revoke-others`: authenticate, run the action in one `withTransaction`, keep `identity.session.id`, and respond 200 `{ "revokedCount": <n> }`. The path must be matched before and must not collide with `REVOKE_SESSION_PATH`.
4. Register the route in `routeMatrix.ts` (name "revoke other sessions", `POST /api/auth/sessions/revoke-others`, `account`), add its case to `__tests__/tenantIsolationRoutes.test.ts` (a call by another tenant's user revokes none of tenant A's sessions) and map it to `authHandler.ts` in `ROUTE_HANDLER_FILES` in `__tests__/chokePointWriteBoundary.unit.test.ts`.
5. Add tests: after the call only the caller's token works; every other session gets 401; their push registrations are revoked; a connected WebSocket of another session is closed with 4401 after commit; another user's sessions are untouched; with no other sessions `revokedCount` is 0; a rolled-back transaction fires no event.

## Scope

### In scope

- The store function, the action, the route and its matrix registration, with push and realtime cascades.

### Out of scope

- Revoking a session of the same installation at login: #1687.
- Changing a password: #1701 calls the action added here.
- Revoking push registrations that have no session.
- Any change to `revokeAllSessionsForUser`, logout, or single-session revoke.

## Acceptance criteria

- When a user with three active sessions calls the route with one of them, then the response is 200 `{ "revokedCount": 2 }` and only the calling token still authenticates.
- The other two tokens get 401, their push registrations have `revoked_at` set, and their open `WS /api/sync` sockets are closed with 4401.
- The calling session's push registrations stay active.
- Sessions of other users are never revoked.
- If the transaction rolls back, no session is revoked and no realtime event is sent.
