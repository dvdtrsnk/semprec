**Blocked by:** #1601
**Model tier:** high

## Context

Model tier rationale: This adds a contract that runs domain code inside the transaction of a destructive, tenant-scoped purge, with rollback and concurrency behaviour that later features depend on.

The choke point lets a domain act on an item write through a per-process hook registry in `backend/packages/data/src/chokePoint/hooks.ts`: create and update hooks, and since #1601 delete and restore hooks. The permanent purge of trashed items, `purgeExpiredTrashSubtree` in `backend/packages/data/src/chokePoint/itemTrash.ts`, runs no hook. It removes a row with `itemsStore.hardDeleteItem` and then calls `deleteItemDependents`, which imports seven domain stores directly under an exemption of the `chokepoint-knows-no-domain` boundary rule.

`docs/adr/2026-11-07-item-delete-and-restore-domain-hooks.md` left this open on purpose: hooks on the permanent purge "remain undecided; a consumer that needs one needs its own decision", and its rule `item-trash-domain-imports-are-purge-only` refuses any further domain import in `itemTrash.ts`. The mail module is that consumer: purging an email item or a mailbox item must remove the mail rows that belong to it (#1691), and #1691 was written on the assumption that a purge hook registry already exists. No issue delivers it.

Decision: a domain reaches the permanent purge through an item purge hook of the same registry, not through a new import in `itemTrash.ts`. The seven existing direct imports stay as they are.

Decision: a purge hook runs inside the purge transaction, once for every row that this purge actually hard-deleted, after that row's built-in dependents are deleted. It receives the removed row, because the row can no longer be read. A hook that throws fails that subtree's purge transaction, so nothing of the subtree is purged.

Decision: the tenant erase of `docs/adr/2026-10-18-tenant-purge-erases-outside-the-choke-point.md` stays outside the choke point and runs no purge hook.

## Task

Load `state-writes`, `error-handling`, `testing` and `adr-conventions`.

1. In `chokePoint/hooks.ts` add the item purge hook next to the delete and restore hooks: a context type, `registerItemPurgeHook`, `runItemPurgeHooks`, and clearing in `clearHooksForTests`. The context carries the purge transaction's `client`, the removed `item` row as it was before removal, its `database` row and the `rootItemId` of the purged subtree. Hooks run in registration order.
2. In `purgeExpiredTrashSubtree`, for every row for which `itemsStore.hardDeleteItem` reported a removal, call `runItemPurgeHooks` in the same transaction after `deleteItemDependents` for that row. A row that was not removed, for example because a concurrent restore won, gets no hook call. Do not catch a hook's error: it propagates and rolls the transaction back.
3. Add no domain import to `itemTrash.ts` and register no consumer hook. Where the comments of the boundary rules `chokepoint-knows-no-domain` and `item-trash-domain-imports-are-purge-only` in `backend/dependency-cruiser.rules.json` say how a domain reaches the purge, bring them in line with this change; do not change what the rules match.
4. Add an ADR under `docs/adr/`, dated the day it is written, `status: accepted`, `area: [backend]`, `supersedes: []`. Its Context references `[[2026-09-30-choke-point-domain-hooks-through-a-per-process-registry]]` and `[[2026-11-07-item-delete-and-restore-domain-hooks]]` and says that it decides what the latter left undecided for the permanent purge only. Its Decision states the three decisions above and what a hook may rely on: the transaction and tenant scope of the purge, the removed row, and that the row and its built-in dependents are already gone. Hooks on database or property archive and delete stay undecided.

## Scope

### In scope

- The purge hook registry and its call from the permanent purge.
- The decision record.

### Out of scope

- Any consumer hook, including the mail cleanup of #1691.
- Moving the seven existing direct purge imports of `deleteItemDependents` to hooks.
- Hooks on the tenant erase, on soft delete or restore, and on database or property archive and delete.
- Work after the purge transaction commits, such as deleting blob bytes.

## Acceptance criteria

- A registered purge hook is called exactly once for each row a purge hard-deletes, including every row of a purged subtree, with that row, its database row and the subtree's root id.
- Inside the hook the removed row is no longer readable through the hook's client, and a row the hook deletes through that client is gone after the purge commits.
- A hook is not called for a row the purge did not remove: a trashed row newer than the cutoff, a live row, and a row whose trash was restored before the purge reached it.
- When a hook throws, the purge of that subtree fails with the hook's error and every row of the subtree, its built-in dependents and anything the hooks deleted before the failure are still present.
- A hook's client runs under the purging tenant's scope: with the runtime role pool, a query through it does not return another tenant's rows.
- Trashing and restoring an item call no purge hook, and the tenant erase calls none.
- `clearHooksForTests` removes registered purge hooks.
- `pnpm run check:boundaries` passes and `itemTrash.ts` imports no domain module beyond the seven it imported before.
