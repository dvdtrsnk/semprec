## Context

Model tier rationale: Tenant locale must cross the tick snapshot without changing staleness fingerprints or transaction boundaries.

Inbox tick reads a repeatable-read snapshot, computes outside transactions and writes in a second transaction. Read tenant users.locale via getTenantUserLocale for ProposalComputationInput.

Decision: the locale is passed to the injected function as a new input field; this issue does not implement or change the LLM-backed function itself (it is injected and prompt engineering is outside this repository seam).

Decision: a locale change does not invalidate existing proposals. The fingerprint (`computeInboxFingerprint`) is unchanged, so an existing `proposed` card keeps its language and only the next computed proposal uses the new one.

Decision: when no locale resolves (no bound user), the tick uses `cs`, the column default of `users.locale`.

#1704 lets the person change the locale.

## Task

Load `testing`.

1. Add `locale: string` to `ProposalComputationInput`, documented as the language the proposal's person-facing texts must be written in.
2. In `readTickSnapshot`, read the locale with `getTenantUserLocale(client)` inside the existing read transaction, default it to `cs` when `null`, store it in `TickSnapshot`, and pass it as `locale` in the `computeProposal` call in `createSemprecTickAction`.
3. Update the existing test doubles of `computeProposal` only as far as the new field requires, and add tests: the function receives `locale: 'en'` for a user with locale `en`, and `locale: 'cs'` when the tenant has no bound user.

4. Preserve the actual locale string for computeProposal, with only null defaulting to cs; cs/en catalog and recognition normalization remains separate at those consumers. Add a fr regression alongside en/cs; do not silently map fr to en in the computation input.
