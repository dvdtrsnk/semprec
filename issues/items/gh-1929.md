## Context

Model tier rationale: It parses attacker-controlled iCalendar text from incoming mail and writes tenant data from it, with size limits, upsert idempotency under concurrent delivery and a parser that a second issue reuses, so a mistake is both a security and a data-integrity defect.

The mail sync already stores an iMIP invitation's calendar part: in `walkBodyStructure` (`backend/packages/data/src/mail/imapFlowClient.ts`) and its Gmail equivalent, a `text/calendar` leaf that is neither the plain-text nor the HTML body goes into the attachment parts, and `ingestAttachments` (`backend/packages/data/src/mail/attachments.ts`) writes it to blob storage, records a `mail_attachments` row with its `content_type`, and links a Files item to the Emails item through `Emails.attachments`. Nothing reads these parts as calendar data. Mail ingest (`mail/ingest.ts`) does not write to other databases and must keep not doing so (`docs/adr/2026-09-10-single-writer-ownership-model.md`): the calendar module reacts to the new Emails item instead.

This issue adds that reaction, the same way `mail.linkPeopleByEmail` (`mail/personLinkingActions.ts`) and the Inbox tick (`inbox/inboxTickAction.ts`) react to item creation: an `onItemEvent` create heartbeat on Emails whose action reads the calendar part, parses `METHOD:REQUEST` and upserts a row in the Invitations database from #1901. It also delivers the reusable iCalendar parser that #1950 later uses for replies.

Decision: in this issue only `METHOD:REQUEST` creates or updates an invitation. A `METHOD:CANCEL` from the organizer marks the invitation `cancelled` and trashes its Event; that is #2006, which extends this action, so this issue leaves `CANCEL` untouched. `METHOD:REPLY` is handled by #1950; every other method is ignored.

Decision: in this issue a higher `SEQUENCE` for a known `UID` updates the invitation only while its status is still `pending`; for an answered invitation this issue changes nothing. Carrying an organizer's update into an answered invitation and its Event (keeping the user's answer and edits) is #2007, which extends this action.

Decision (product owner): a recurring invitation (`RRULE`) is stored as one invitation for the first occurrence; the recurrence rule is ignored. Recurrence is a separate batch.

Decision: no new dependency; a small parser for the needed iCalendar subset is written in the repository (line unfolding, `BEGIN`/`END` nesting, parameters, quoted values, text unescaping).

Shared-file ordering: this issue also waits for #1925 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. Add `backend/packages/data/src/calendar/icalendarParser.ts`, a pure function `parseICalendar(text)` returning the calendar `METHOD` and, per `VEVENT`: `UID`, `SEQUENCE` (default 0), `SUMMARY`, `LOCATION`, `DTSTART`/`DTEND` (value type `DATE`, UTC `Z`, or local with `TZID`), `ORGANIZER` (address and `CN`), every `ATTENDEE` (address, `CN`, `PARTSTAT`), and whether `RRULE` or `RECURRENCE-ID` is present. Limits: input over 256 KiB or more than 10 `VEVENT` blocks is rejected as a whole. Normalize times to an ISO UTC instant plus an IANA `timeZone`: a `TZID` that luxon accepts as an IANA zone is kept; an unknown `TZID` falls back to the tenant time zone (read with `getSystemTimezone` from `backend/packages/data/src/systemSettings.ts`) and a log line with a reason code only; the invitation is never dropped for it (product owner decision). An all-day event (`VALUE=DATE`) becomes `allDay: true` with `startsAt` the first day and `endsAt` the last day inclusive (the `DTEND` minus one day; empty for a single day), both at 00:00 UTC.
2. Add `backend/packages/data/src/calendar/emailCalendarParts.ts` with `readCalendarPartsOfEmail(client, storage, emailItemId)`: lists the `mail_attachments` rows of the message whose `content_type` is `text/calendar` or `application/ics` and whose `byte_size` is within the parser limit, reads each through `BlobStorageWriter.readStream` using the blob's `storage_key`, and returns the decoded text. A message without such a part returns an empty list.
3. Add `backend/packages/data/src/calendar/invitationIngestAction.ts` exporting `CALENDAR_INGEST_INVITATION_ACTION_ID = "calendar.ingestInvitation"` and `createInvitationIngestAction(pool, { storage })`, an `ActionHandler` for `onItemEvent` create on Emails. It validates `action_config` with a zod schema (`{ emailsDatabaseId, invitationsDatabaseId }`), skips a message with `message_kind = 'dsn'`, reads the calendar parts, and for each `REQUEST` handles the first `VEVENT` that has no `RECURRENCE-ID`, in one transaction per email:
   - take a transaction-scoped advisory lock on a hash of the `UID` so two concurrent deliveries cannot both insert;
   - look up an existing invitation with the same `uid` through the choke point's read path;
   - if none exists, create one with `kind: invite`, `status: pending`, the parsed fields, `sequence`, `organizerName`, `organizerEmail`, the relations `sourceEmail` (this Emails item), `mailbox` (`mail_message_meta.mailbox_item_id`) and `suggestedCalendar` (the calendar flagged as default by #1600);
   - if one exists with a lower `sequence` and `status` `pending`, update its parsed fields, `sequence` and `sourceEmail`; if the `sequence` is equal or lower, or the status is not `pending`, do nothing.
   All writes go through the choke point (`createItemWithClient`, `updateItemWithClient`, `createRelationWithClient`) with the calendar module as the system owner process. A message with no calendar part, with another method, or with a parse failure creates nothing and never throws; logs carry the email item id and a reason code, never the invitation content.
4. Register the action: export it from `backend/packages/data/src/index.ts`; add its id to `KNOWN_HEARTBEAT_ACTION_IDS` in `backend/packages/data/src/manifest/knownActionIds.ts`; list it in `heartbeatActions` of `backend/packages/data/src/calendar/calendarModuleManifest.ts`; register the handler in `backend/services/semprec-api/src/actionRegistryComposition.ts` with a `LocalFsBlobStorageWriter` over `resolveBlobStorageDir("MAIL_ATTACHMENTS_DIR")`.
5. Seed the heartbeat in `seedInvitationsDatabaseInTransaction` (`backend/packages/data/src/seed/seedInvitationsDatabase.ts`): name `Ingest calendar invitations`, rule `onItemEvent` create on the Emails database, owned by the same system project item as the Invitations database. Add `backend/packages/data/src/calendar/invitationIngestHeartbeatCutoverMigration.ts` that creates it for populated tenants (idempotent, no-op when the heartbeat, the Invitations database or the Emails database is missing) and register it in `runTenantCutoverMigrations`.
6. Tests: parser unit tests (plain REQUEST, `TZID` and `Z` times, all-day, folded lines, quoted parameters, over-limit input, malformed input never throws); action integration tests (a REQUEST creates exactly one pending invitation with the default calendar and the receiving mailbox; a higher `SEQUENCE` updates a pending one; an equal one is a no-op; an answered one is untouched; a mail without a calendar part and a `CANCEL` create nothing; a repeated run of the same email creates no duplicate); and a test that an inline `text/calendar` part inside `multipart/alternative` produces a `mail_attachments` row, in the existing IMAP and Gmail classification tests.

## Scope

### In scope

- The iCalendar parser, reading calendar parts of a stored email, the create/update heartbeat action for `REQUEST`, and its heartbeat for new and existing tenants.

### Out of scope

- The Invitations database itself: #1901.
- Answering an invitation and creating its Event: #1944.
- Applying `REPLY` messages to Event participants: #1950.
- Handling `CANCEL` (the `cancelled` status and trashing the Event): #2006.
- Updating an answered invitation and its Event when the organizer changes it: #2007.
- Recurring invitations as a recurring Event: not in v1 (product owner decision); only the first occurrence is stored.
- Notifying the user: #1954.

## Acceptance criteria

- When an email with an iMIP `REQUEST` for "Sprint review" arrives, then exactly one pending invitation exists with its title, start, end, place, organizer, the receiving mailbox and the default calendar as the suggested calendar.
- When a second email carries the same `UID` with a higher `SEQUENCE` while the invitation is pending, then that invitation is updated and no second row exists; an equal or lower `SEQUENCE` changes nothing.
- When the invitation has already been answered, then a later request for the same `UID` changes nothing.
- When an email has no `text/calendar` part, or is a `CANCEL`, then no invitation is created and the heartbeat does not fail.
- When a calendar part is over 256 KiB or has more than 10 events, then it is skipped without an error and without logging its content.
- When the same email is processed twice, then no duplicate invitation is created.
