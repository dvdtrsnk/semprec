**Blocked by:** #90, #115, #175

## Context

The repository defines `CORE_CRONTAB`, task handlers, queue registration, and future worker/service topology, but no concrete long-lived composition root calls graphile-worker `run()`. Before two runtimes (API and agents) can host disjoint handler sets over the same queue, every task must declare which runtime owns it. This issue makes affinity explicit data: a mandatory `queueAffinity` on module task descriptors, affinity on the closed core/agent task-name catalogs, the exhaustive per-runtime handler sets, and ModuleRegistry validation of that data. #222 splits the overloaded `heartbeatFire` task along this affinity, and #91 hosts the two composition roots that consume these sets.

## Task

Evolve #29's module task descriptor exactly from `{ name, payloadSchemaExport, handlerExport }` to `{ name, payloadSchemaExport, handlerExport, queueAffinity: 'api' | 'agents' }`. The field is mandatory for every active module task; install migration assigns `api` to existing deterministic/data/mail/library handlers and `agents` only to handlers that start/continue agent sessions. Missing/unknown affinity fails ModuleRegistry load.

Declare the exhaustive runtime handler sets as exported data. The exhaustive API handler set is `heartbeatSweep`, `heartbeatFireCore`, `rollupRecompute`, `rollupRecomputeFull`, `propertyTypeMigration`, `docCompactionSweep`, `docHistorySquash`, `docHistoryCleanup`, `processLibraryMetadata`, `mailAccountSync`, `mailAccountSyncSweep`, and `mailSearchReindexSweep`, plus module handlers whose manifest declares `queueAffinity: 'api'`. The exhaustive agents set is `heartbeatFireAgent`, `agentRun`, and `delegatedAgentRun`, plus module handlers declaring `queueAffinity: 'agents'`. Add these three agent names to exported `AGENT_TASK_NAMES`; no other name is accepted without updating the closed catalog. Every `CORE_TASK_NAMES` entry carries an `affinity`. The inherited API set also includes `approvalExecute` (#32), `notificationFanout` (#36), and `trashPurge` (#37); add these names to `CORE_TASK_NAMES` with `affinity: 'api'`. `approvalExecute` and `notificationFanout` are enqueue-only. Extend the sole `CORE_CRONTAB` with `0 4 * * * trashPurge`; no other runner/timer schedules it. This supersedes the earlier exhaustive API list by adding these three entries.

The names `heartbeatFireCore` (`affinity: 'api'`) and `heartbeatFireAgent` (`affinity: 'agents'`) are declared in the catalog here; their handlers, the enqueue routing, and the legacy job migration are delivered by #222. Until then the existing `heartbeatFire` name stays in `CORE_TASK_NAMES` as a transitional entry with `affinity: 'api'` so the current handler keeps running; #222 removes it.

ModuleRegistry requires every queue handler descriptor to contain one affinity, rejects unknown affinity, duplicate name across either set, and a core-name override (a module task reusing a `CORE_TASK_NAMES`/`AGENT_TASK_NAMES` name). Expose a shared registry validation function that returns, for a loaded registry, the resolved API set and agents set and proves every active descriptor belongs to exactly one of them; #91 calls it before either service reports readiness and adds the runner-side "active handler missing from its selected runner" check.

## Scope

### In scope

- `queueAffinity` in module task descriptors and install migration, affinity on `CORE_TASK_NAMES`, the three inherited core names, `AGENT_TASK_NAMES`, the `trashPurge` crontab line, exhaustive handler sets as data, ModuleRegistry affinity validation, and tests.

### Out of scope

- `heartbeatFireCore`/`heartbeatFireAgent` handlers, enqueue routing, and legacy heartbeat job migration, delivered by #222.
- The two graphile-worker composition roots, lifecycle, readiness validation against running runners, deployment ownership, and dual-runner integration tests, delivered by #91.
- New task business logic, a second crontab/scheduler, or in-process `setInterval`.

## Acceptance criteria

- Loading a module manifest whose task descriptor lacks `queueAffinity` or declares a value other than `'api'`/`'agents'` fails ModuleRegistry load with an actionable error; the install migration assigns `api`/`agents` to existing module handlers as specified.
- A duplicate task name across the API and agents sets, or a module task overriding a core/agent name, fails ModuleRegistry load with an actionable error.
- `CORE_TASK_NAMES` includes `approvalExecute`, `notificationFanout`, and `trashPurge` with `affinity: 'api'`; `AGENT_TASK_NAMES` exports exactly `heartbeatFireAgent`, `agentRun`, `delegatedAgentRun`; the resolved sets equal the exhaustive lists above plus module handlers by affinity.
- `CORE_CRONTAB` contains `0 4 * * * trashPurge` exactly once and remains the only crontab constant.
- The shared registry validation proves every active descriptor belongs to exactly one set, and the existing `heartbeatFire` handler keeps executing unchanged.
