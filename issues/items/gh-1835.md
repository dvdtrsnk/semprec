## Context

Model tier rationale: A custom write route that must create-or-update exactly one item per night under an advisory lock, stay inside the choke point so hooks, realtime and heartbeats apply, and be idempotent under concurrent retries.

Changing one night (a different bedtime, wake time or alarm for a single date) is stored as an exception item in `sleepNights` (#1776) that overrides the plan field by field. The generic API can express this only as two requests, a POST with an `Idempotency-Key` followed by a PATCH with a mandatory `ifVersion`; a drag in the calendar and an agent do not hold a version, and the answer a client needs is the resolved night (plan merged with exception), not the raw item. There is no "write by date" operation: `updateItemWithClient` without `ifVersion` merges by property key, `itemsStore.hardDeleteItem` removes only trashed rows, and a custom route must not write outside the choke point or do CRUD over module data (decision record `2026-09-11-module-manifest-custom-routes`). The pattern for "one item per key" is `getOrCreateJournalItem` in `backend/packages/data/src/journal/journalStore.ts`.

This issue adds `PUT /api/sleep/nights/:night`. It builds on the value rules and the per-night advisory lock key of #1784 and on the read route and loader of #1809; the resync push (#1838) and the sleep agent tools (#1840) build on it.

Decisions:
- The route is justified as `transactional-semantics`: a find-or-create plus a patch in one transaction, a response that is a resolved night, and callers that do not hold an item version.
- "Reset to plan" is a PUT with every field null. The exception item stays with all fields null (`changed` false) and is not deleted, consistent with 30-day restore for deleted items. If no item exists and every field is null, nothing is written.
- An exception is allowed for a night without a plan, and for past and future nights alike. The server does not enforce 5 or 15 minute steps.
- Old exceptions are kept as history; past exceptions are never pruned.

Shared-file ordering: this issue also waits for #1828 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Add the handler `sleepNightPut` to `backend/packages/data/src/sleep/sleepRouteHandlers.ts` and declare `PUT /api/sleep/nights/:night` in `sleepModuleManifest.ts` (`justification: "transactional-semantics"`). `:night` must be a real `YYYY-MM-DD` date; the body is `{ bedTime?, wakeTime?, alarm? }` (strict; each value is a valid value or null; an absent field is left unchanged); otherwise 400 `validation_failed` with `field`.
2. In one transaction: take `pg_advisory_xact_lock(hashtext('sleepNight:' || <tenant id> || ':' || night))` (the key of #1784), find the non-deleted `sleepNights` item for `night`. If none exists and at least one provided field is non-null, create it with `createItemWithClient` (`night` plus the provided fields); if none exists and all are null or the body is empty, write nothing. If it exists and a provided field differs from the stored value, patch it with `updateItemWithClient` without `ifVersion`; if nothing differs, write nothing. Hooks, validation, realtime invalidation and heartbeats are those of the choke point.
3. Respond 200 with `{ night }`, where `night` is the resolved night from `resolveSleepNights` (#1792) for that date in the same shape as an entry of `GET /api/sleep/nights`, including `prepReminderAt` computed from the exception's bedtime, or `null` when neither plan nor exception applies.
4. Register the route in `routeMatrix.ts`, `ROUTE_HANDLER_FILES` of `chokePointWriteBoundary.unit.test.ts` and `tenantIsolationRoutes.test.ts`.
5. Tests: the acceptance cases below on a real database, including two concurrent PUTs for the same night.

## Scope

### In scope

- `PUT /api/sleep/nights/:night` with find-or-create, partial patch, reset by null fields and the resolved-night response.

### Out of scope

- Value validation and the one-exception-per-night rule themselves: #1784.
- The read route: #1809.
- Enqueueing the resync push after the write: #1838.
- Deleting exceptions or pruning old ones: decided not to be done; past exceptions are kept as history.
- Agent tools for nights: #1840.

## Acceptance criteria

- When `PUT /api/sleep/nights/2026-10-16` is called with `{ "wakeTime": "07:30" }`, then the response night has `bedTime` `00:00`, `wakeTime` `07:30`, `changed` true and the weekend plan is unchanged.
- When a second PUT sends `{ "bedTime": "23:30" }`, then `wakeTime` stays `07:30` and `prepReminderAt` is `2026-10-16T23:00:00+02:00`.
- When `{ "bedTime": "01:30" }` is sent for `2026-10-16`, then `bedAt` is `2026-10-17T01:30:00+02:00`.
- When two PUTs for the same night run concurrently, then exactly one item exists.
- When a PUT sends every field as null for an existing exception, then `changed` is false and the item still exists; for a night without an item, no row is created.
- When a PUT sets `{ "bedTime": "22:00" }` for a night without a plan, then the night is 22:00 to 07:00 with `planId` null.
- When `:night` is `2026-13-01` or `wakeTime` is `7:5`, then the response is 400.
