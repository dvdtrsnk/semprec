## Context

Both production queue runtimes build their heartbeat `ActionRegistry` with `createActionRegistry()` — an empty `Map` (`backend/packages/data/src/scheduler/actions.ts:22-24`) — and never call `.set()` on it: `backend/services/semprec-api/src/queueRuntime.ts:47` (`const actionRegistry = createActionRegistry();`) and `backend/services/semprec-agents/src/queueRuntime.ts:33`. Every heartbeat fire therefore reaches `registry.get(heartbeat.actionId)` in `backend/packages/data/src/scheduler/sweep.ts` (`createHeartbeatFireTaskForAffinity`, line 178-179, and `runScheduledOccurrenceFire`, line 246-247) with no handler and throws `No handler registered for heartbeat action '<id>'`. After the job's third attempt, `recordHeartbeatFailure` and a `heartbeat_error` notification are written — for every seeded heartbeat, on every fire.

Seeded heartbeats that hit this on a fresh install: `core.driftCheck`, `moduleRegistry.checkDrift`, `core.filesTranscriptionTrigger`, `core.transcriptionRequeueSweep` (`backend/packages/data/src/seed/seedSystem.ts:198-263`), `core.libraryMetadataTrigger`, `core.libraryMetadataRetrySweep` (`seedLibraryModule.ts:209-216`), `mail.linkPeopleByEmail` and `core.agentRun` "newEmail" (`seedEmailModule.ts:321-347`), `core.agentGuidanceDrift` (migration `0035_agent_guidance_drift.sql`, daily 04:30 per project). Every handler already exists as a factory returning `ActionHandler`; `backend/services/semprec-api/src/projectAgentGuidanceComposition.ts:36-41` even says "Not yet wired ... to the scheduler's `ActionRegistry`".

Which runtime owns which action is decided by `resolveHeartbeatFireTaskName` (`actions.ts:101-105`): only `core.agentRun` fires on `heartbeatFireAgent` (agents runtime); every other action id fires on `heartbeatFireCore` (api runtime). `assertActionAffinity` (`sweep.ts:70-79`) rejects a handler dispatched to the wrong runtime, so each registry must contain exactly its own affinity's actions.

`semprec.tick` (`SEMPREC_TICK_ACTION_ID`, `backend/packages/data/src/inbox/inboxTickAction.ts:27`, seeded by `seedInboxPipeline.ts:250`) is deliberately not registered here: `createSemprecTickAction(pool, computeProposal)` needs an injected LLM-backed `ComputeSemprecProposalFn` that no composition provides yet. It keeps failing with the current error until a separate issue supplies that computation.

The `core.agentRun` handler (`coreAgentRunAction(pool, runAgent)`, `actions.ts:55-85`) needs a `RunAgentFn`. The real one — an agent session through `@semprec/agent-runtime` — is #647. Until it lands, this issue registers a placeholder that throws, so a fired `newEmail` heartbeat creates its `agent_runs` row and closes it as `error` with the message `semprec-agents has no agent session runtime wired` (via `finishAgentRunWithErrorNotification` inside `coreAgentRunAction`) instead of either the current `No handler registered` error or a misleading `done`.

## Scope

### In scope
- Populating both production action registries with every seeded action id except `semprec.tick`, the placeholder `RunAgentFn`, the `KNOWN_OWNER_PROCESS_IDS` catalog, and the composition tests above.

### Out of scope
- The real `RunAgentFn` / agent session execution (#647).
- Registering `semprec.tick` (needs an LLM proposal computation that does not exist; separate finding).
- Passing `genericOperationApprovalReplay`, `mailModuleIds` or any other `createApiCoreTaskList` argument (#646 and #648).
- Any change to `sweep.ts`, the action handlers themselves, or `KNOWN_HEARTBEAT_ACTION_IDS`.

## Acceptance criteria

- When `createApiActionRegistry` is built against the full module registry, its key set equals `KNOWN_HEARTBEAT_ACTION_IDS` minus `core.agentRun` and `semprec.tick`; `createAgentsActionRegistry` has exactly `core.agentRun`.
- When a `heartbeatFireCore` job fires for a seeded `core.driftCheck` (or any other registered api-affinity action) under `createApiQueueRuntime`, the heartbeat records success (`last_error IS NULL`) and no `heartbeat_error` notification is written.
- When a `heartbeatFireAgent` job fires for the seeded `core.agentRun` heartbeat under `createAgentsQueueRuntime` without a `runAgent` option, an `agent_runs` row exists with `status='error'` and a result naming the unwired runtime, and the job does not fail with `No handler registered`.
- When `moduleRegistry.checkDrift` runs against a freshly seeded database, it publishes no `module_registry_unknown_heartbeat_action` and no `module_registry_orphaned_owner_process` finding.
- `semprec-api` refuses to start without `AI_GATEWAY_INTERNAL_TOKEN`, with an error naming that variable.
