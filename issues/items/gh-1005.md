## Context

Every user owns a tenant, and every tenant needs its own system databases: settings, Projects with the Semprec project, the ten hardcoded databases, the Email, Library, Inbox and MCP module databases, and their heartbeats. Today the seed creates them once for the whole installation:
- `seedSystem` (`backend/packages/data/src/seed/seedSystem.ts:68-302`) takes the single global lock `pg_advisory_xact_lock(2331)` (`:43,116`);
- it returns `already-seeded` as soon as any `systemSettings` database exists anywhere (`:117-120`);
- it then runs the `systemDatabases` module's data migrations (`:300`);
- `runSeed` (`backend/packages/data/src/db/runSeed.ts:15-19`) adds the full module registry's data migrations.

`deploy/deploy.sh:145-151` runs `runSeedCli.js` on every deploy with `SEMPREC_MIGRATE_DATABASE_URL`, which authenticates as `POSTGRES_USER` (`deploy/shared/.env.example:76-81`). That role owns the tables, so row-level security does not apply to it. Under it, every "already seeded?" read, every `getDatabaseByModuleId` and every `module_migrations` check sees all tenants.

Tenancy state this issue builds on:
- Tenant tables carry `tenant_id uuid NOT NULL DEFAULT app_tenant_default()` under the RESTRICTIVE policy `tenant_isolation` (`tenant_id = (SELECT app_tenant_default())`).
- `app_tenant_default()` is `COALESCE(app_current_tenant(), app_sole_tenant())` over the GUC `app.tenant_id`.
- `runInTenant(tenantId, fn)` / `runAsSystem(reason, fn)` (`@semprec/shared`) set that GUC for `withTransaction`, autocommit queries and `pool.connect()` clients. Entering a different tenant inside a tenant scope throws `TenantScopeConflictError`.
- `tenants(id, status ∈ provisioning|active|suspended|deleting, created_at, status_changed_at)` is a global table that `semprec_data` reads and writes.
- #1001 made `databases_key_unique` `(tenant_id, key)`. `getDatabaseByModuleId` now filters `system` and throws when it sees more than one row.
- #983 added `forEachActiveTenant` for cron sweeps over `active` tenants only.
- This issue follows #1004 because both add an export line to `backend/packages/data/src/index.ts`.

The acceptance criteria use the two-tenant runtime-role harness of #975: `createTestTenant()` and a `semprec_data` pool.

Verified on PostgreSQL 15: when a superuser opens a connection with the startup option `-c role=semprec_data`, the connection runs as `semprec_data` and `row_security_active('<table>')` is true; for the superuser itself it is false. node-postgres 8.23 passes `options` through. `semprec_data` holds every grant the seed needs (`backend/packages/data/src/db/migrations/0040_least_privilege_roles.sql:47-80`), plus `EXECUTE` on `create_items_partition` (0048).

## Task

Load `state-writes` (locks, guards and the status transition inside transactions), `error-handling` (per-tenant failures are aggregated, never swallowed), `db-migrations` (module data migrations stay outside the structural transaction) and `adr-conventions` (deploy-time tenant work running as the runtime role is a new cross-cutting pattern).

1. **Pool role (`backend/packages/data/src/db/pool.ts`).**
   - Add `role?: "semprec_data"` to `CreatePoolOptions`. When it is set, `createPool` passes pg's connection option `options: "-c role=semprec_data"`, so every connection of that pool runs as that role.
   - Docstring: this lets a CLI connected as the migrating role do tenant work under RLS.
2. **`seedSystem` per tenant (`seedSystem.ts:113-120`).** The signature is unchanged, so its many test callers keep working. Inside the transaction, before the existing guard:
   - resolve `SELECT app_tenant_default()::text AS tenant_id`, and throw a plain `Error` when it is `NULL` (no tenant scope while several tenants exist);
   - take `SELECT pg_advisory_xact_lock(2331, hashtext($1))` with that id;
   - read `SELECT status FROM tenants WHERE id = $1 FOR SHARE`, and throw when the row is missing or `deleting`;
   - add `AND system` to the existing `systemSettings` check.

   The body after the guard is unchanged. Update the docstring: the lock and the "already seeded" decision are per tenant.
3. **`provisionTenant` (new `backend/packages/data/src/tenancy/provisionTenant.ts`).**
   - Export `assertRowSecurityActive(queryable)`. It runs `SELECT row_security_active('public.databases') AS active`, and when that is false it throws an `Error` saying provisioning must run as a role RLS applies to (e.g. `semprec_data`).
   - Export `provisionTenant(pool: Pool, tenantId: string): Promise<"created" | "already-provisioned">`. It calls `assertRowSecurityActive(pool)`, then runs steps 2-4 inside one `runInTenant(tenantId, …)`:
     2. `seedSystem(pool, createViewTypeRegistry(), createComputedKeyRegistry())`.
     3. `runModuleDataMigrations(pool, await loadFullModuleRegistry())`.
     4. In one `withTransaction`: `SELECT status FROM tenants WHERE id = $1 FOR UPDATE`.
        - `provisioning`: `UPDATE tenants SET status = 'active', status_changed_at = now() WHERE id = $1`, checked with `requireAffectedRows`.
        - `active` or `suspended`: unchanged.
        - `deleting` or missing: throw.
     5. Return `created` exactly when `seedSystem` returned `created`.
   - Export `forEachMaintainedTenant(pool, fn: (tenantId: string) => Promise<void>)`. It reads `SELECT id FROM tenants WHERE status IN ('provisioning','active','suspended') ORDER BY created_at, id`, then for each tenant in turn runs `runInTenant(id, () => fn(id))`. A failing tenant does not stop the others. After all, it throws one `AggregateError` whose message lists the failed tenant ids.
   - Why not `forEachActiveTenant`: a deploy must also finish `provisioning` tenants and keep `suspended` tenants' data shape current. Write this down in the ADR.
4. **`runSeed` (`runSeed.ts`)** becomes `runSeed(pool): Promise<Array<{ tenantId: string; outcome: "created" | "already-provisioned" }>>`. Inside `runAsSystem("deploy seed", …)`, it calls `forEachMaintainedTenant(pool, …)` and runs `provisionTenant` for each tenant.
5. **`runSeedCli.ts`.**
   - Use `createPool(connectionString, { role: "semprec_data" })`.
   - Print one line per tenant: `seed: tenant <id> created system databases` or `seed: tenant <id> already seeded`.
   - Never print the connection string. `deploy/deploy.sh` is unchanged.
6. **Exports.** Add `export { provisionTenant } from "./tenancy/provisionTenant.js";` to `backend/packages/data/src/index.ts`, and add `provisionTenant` to the runtime export list in `backend/packages/data/src/__tests__/publicSurface.test.ts`.
7. **Docs.**
   - Rewrite `docs/operations/seeding.md`: per-tenant provisioning, lock `(2331, hashtext(tenant id))`, the CLI running as `semprec_data`, the new output lines, and which statuses are covered.
   - Add `docs/adr/<YYYY-MM-DD>-deploy-time-tenant-work-runs-as-the-runtime-role.md`. It records three decisions: deploy-time steps that read or write tenant rows run per tenant on a `semprec_data` pool; `provisionTenant` refuses a role RLS does not apply to; the migrating role keeps only DDL and schema-guarded global steps.
8. **Tests.**
   - New `backend/packages/data/src/__tests__/provisionTenant.test.ts` on the #975 harness's `semprec_data` pool.
   - Rework `backend/packages/data/src/__tests__/runSeedCli.test.ts` onto that pool and the new return shape. Its race case stays.

## Acceptance criteria

All integration tests (`*.test.ts`) on the #975 harness, unless stated.
- A `provisioning` tenant B is provisioned on the `semprec_data` pool:
  - `provisionTenant` resolves `created`;
  - in B's scope, `getDatabaseByModuleId` finds B's own `systemSettings`, `projects`, `tasks`, `emails`, `mcpServers` and `inbox` databases;
  - B's status is `active` with a fresh `status_changed_at`;
  - in tenant zero's scope, none of B's databases or items are visible, and tenant zero's are unchanged.
- A second `provisionTenant(B)` resolves `already-provisioned`, and B's `databases` and `items` row counts are unchanged.
- Two concurrent `provisionTenant(B)` calls: exactly one resolves `created`, and B has exactly one `systemSettings` database.
- Provisioning B, as the only tenant provisioned in the test, records B's `module_migrations` rows, visible only in B's scope.
- A `suspended` tenant is seeded and stays `suspended`.
- A `deleting` tenant, or an unknown id, rejects; nothing is written for it.
- `provisionTenant` on the owner pool (`getTestPool()`) rejects with the RLS error before writing anything.
- A pool from `createPool(url, { role: "semprec_data" })` reports `current_user = 'semprec_data'` and `row_security_active('public.databases') = true`.
- `runSeed` over tenant zero, a `provisioning` B, a `suspended` C and a `deleting` D:
  - provisions zero, B and C;
  - leaves D untouched;
  - returns one outcome per provisioned tenant.
- When B's seed fails (B pre-seeded with a conflicting `projects` key), `runSeed` still provisions C, then rejects with an `AggregateError` naming B.
- `seedSystem(pool)` with no scope while two tenants exist rejects and writes nothing. With one tenant, the existing seed tests pass.
- `runSeedCli` prints one line per provisioned tenant in the stated format (integration, `runSeedCli.test.ts`); the ADR exists and is accepted (review).
