**Model tier:** high

## Context

Model tier rationale: Concurrent creates and updates must produce one settings item and one exception per night under advisory locks in the same transaction as the write, and the new error code extends the closed API error contract, so a mistake silently allows duplicates or deadlocks.

#1776 gives every tenant three locked sleep databases, but nothing checks the values written into them. The choke point validates only unknown keys, rollups, relations and ownership (`assertWritableProperties` in `backend/packages/data/src/chokePoint/itemWrites.ts`); a select value is checked against its catalog by nobody (the general check arrives with #1802). Create hooks run inside the write transaction after the row is inserted (`runItemCreateHooks`) and an error from a hook rolls the write back; update hooks run after the write in the same transaction (`chokePoint/hooks.ts`); domain hooks are registered only in `backend/packages/data/src/domainWriteHooks.ts`. `ConflictError` in `backend/packages/data/src/errors.ts` has the fixed code `version_conflict`, and `ITEM_ERROR_CODES` in `backend/services/semprec-api/src/adapter/errorContract.ts` is a closed list with no code for a duplicate.

This issue adds the value rules and the "one item per key" rules for the three sleep databases in one write hook file. Settings are a singleton per user, and a night may have at most one exception item. It builds on the module (#1776), the per-module pre-write transform (#1422, used to normalize times), the shared `normalizeWallClockTime` helper (#1536) and the hook registry order of #1601 (the three hook issues share `hooks.ts` and `domainWriteHooks.ts`). Later issues add to the same files in the same chain: one plan per wake day (#1799), the PUT route for a single night (#1835, which takes the same advisory lock) and the resync push (#1838). The temporary select check here is removed when #1802 validates selects generally.

Decisions:
- Validation always runs over the merged item (the stored properties with the patch applied), so a partial PATCH is judged as a whole.
- Times are accepted as `H:MM` or `HH:MM` and stored as zero-padded 24-hour `HH:MM` (a pre-write transform); `24:00` is not valid for sleep times.
- Uniqueness is enforced on non-deleted items only; restoring a trashed duplicate is not checked here.
- A duplicate answers 409 with the new code `duplicate_item` and `details.field`.

Shared-file ordering: this issue also waits for #1781 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Add `DuplicateItemError` (HTTP 409, code `duplicate_item`, `details: { field }`) to `backend/packages/data/src/errors.ts`, and add `duplicate_item` to `ITEM_ERROR_CODES` and `ITEM_ERROR_STATUS_BY_CODE` (409) in `errorContract.ts`. The change is additive.
2. Create `backend/packages/data/src/sleep/sleepWriteHooks.ts`, gated on `database.ownerModuleId` being `sleepSettings`, `sleepPlans` or `sleepNights`, exporting a pre-write transform and a create and an update hook, and register all three in `domainWriteHooks.ts` (the transform through the registry of #1422 for each of the three module ids).
3. Pre-write transform: normalize every time property present in the patch (`bedTime`, `wakeTime`) with `normalizeWallClockTime(value, { allow2400: false })`; null stays null on `sleepNights`; an unreadable value (`7:5`, `25:00`) is a 400 `validation_failed` with the property key as `field`.
4. Value validation in the create and update hooks, over the merged item; every failure is a 400 `validation_failed` with `field`:
   - `sleepSettings`: `enabled`, `prepReminder`, `muteSemp`, `alarmSnooze`, `showInCalendar` are booleans; `goalMinutes` is one of 420, 450, 480, 510, 540; `prepReminderMinutes` is one of 15, 30, 45, 60; `alarmSound` is one of `morning`, `birds`, `piano`, `vibrateOnly`.
   - `sleepPlans`: `name` is a non-empty string; `wakeDays` is an array of `mon`..`sun` without duplicates (an empty array is valid); `bedTime` and `wakeTime` are required `HH:MM`; `alarm` is a boolean; `position` is an integer greater than or equal to 0.
   - `sleepNights`: `night` is required, a real calendar date `YYYY-MM-DD`; `bedTime` and `wakeTime` are `HH:MM` or null; `alarm` is a boolean or null.
5. One settings item: in the create hook of `sleepSettings`, take `pg_advisory_xact_lock(hashtext('sleepSettings:' || <tenant id>))` (tenant id from `app_tenant_default()`), then count the non-deleted items of the database in a new statement; more than one means `DuplicateItemError` (`field: "sleepSettings"`) and the create is rolled back.
6. One exception per night: in the create hook of `sleepNights`, and in the update hook when the patch changes `night`, take `pg_advisory_xact_lock(hashtext('sleepNight:' || <tenant id> || ':' || night))` (exactly this key; #1835 reuses it) and look for another non-deleted item with the same `night`; found means `DuplicateItemError` (`field: "night"`).
7. Tests (real database): each validation case, `6:45` stored as `06:45`, the 409 for a second settings item, two concurrent POSTs for the same night yielding one item and one 409 `duplicate_item` with `field: "night"`, and a PATCH that moves a night onto an occupied date.

## Scope

### In scope

- Value validation for the three sleep databases, time normalization, one settings item and one exception per night, and the `duplicate_item` error code.

### Out of scope

- One sleep plan per wake day and moving days between plans: #1799.
- The route that upserts a night: #1835.
- General select validation against the option catalog: #1802; this issue's `alarmSound` check is temporary and is removed there.
- Delete and restore behavior of plans (at least one plan, day collisions after restore): decided not to be done in this batch; on a day collision the plan with the lower `position` wins.
- The resync push: #1838.

## Acceptance criteria

- When a write sets `goalMinutes` 485, a plan `wakeDays` `["mon","mon"]`, a night `2026-13-01` or `alarm` `"yes"`, then the response is 400 with the offending `field` and nothing is stored.
- When a plan is written with `bedTime` `6:45`, then `06:45` is stored; `7:5` and `25:00` return 400.
- When a plan is written with `wakeDays` `[]`, then the write succeeds.
- When a second settings item is created, then the response is 409 `duplicate_item`.
- When two concurrent requests create the night `2026-10-16`, then exactly one item exists and the other request gets 409 `duplicate_item` with `field: "night"`.
- When a night item is moved by PATCH onto a date that already has a non-deleted exception, then 409 `duplicate_item`.
- When an agent writes the same invalid value through `item.patch`, then it fails identically.
