## Behavior specification

Calendar recurrence: recurring events, recurring tasks, birthdays and holidays.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: calendar-recurrence-1

#### (a) Decisions adopted from open questions

- Recurrence UI in the new-event sheet and details, and the choice "only this / this and following / whole series" -> not built in the backend (outside the current design); only the rule, occurrences and per-occurrence exceptions -> the design has no such choice. -> Decided by the product owner: not in v1; v1 keeps only the rule, occurrences and per-occurrence exceptions, and the choice "only this / this and following / whole series" is added once the design provides it.
- Recording for an occurrence: materialize at confirm, metadata on the series edge, or a new decision about worker writes? -> materialize when the user confirms the card; the worker never materializes -> recommended option; keeps the worker-writes ADR unchanged. -> Decided by the product owner: the occurrence is materialized when the user confirms the card; nothing is created silently in the background.
- Which name in "Birthday - Jana" -> the given name (first word of the person's name) -> matches the design. -> Decided by the product owner: the given name (first word of the name), as in the design.
- Holidays as a static function or an ICS subscription? -> static function in code for this version (years 2016-2100) -> recommended for v1. -> Decided by the product owner: a static function in code for the years 2016-2100; an ICS subscription would add a dependency on a third-party service with no benefit for v1.
- Birthday and holiday entries open the person / are preview only, chip colours from the calendar -> the entries carry the person id and the calendar id; the rest is client work. -> Decided by the product owner: a birthday opens the person, a holiday is a preview only; chip colours come from the calendar for a consistent look.
- Year unknown for a birthday -> placeholder leap year 2000 stored by the client; the backend only requires a real date -> keeps People views sortable. -> Decided by the product owner: placeholder leap year 2000, the server only requires a real date; the leap year guarantees that 29 February is accepted.
- 29 February birthday in a non-leap year -> shown on 28 February. -> Decided by the product owner: 28 February, so the birthday stays in the same month.
- Cancelling one occurrence -> deleting its materialized item; a trashed occurrence is a cancelled date; restore brings it back. -> Decided by the product owner: the occurrence's materialized item goes to the trash and restoring brings it back; this is reversible and reuses the general trash instead of a special mechanism.
- Series end -> no end condition in this version. -> Decided by the product owner: no end condition in v1; a series can be ended by hand, end conditions are added when needed.
- Sample data (Standup missing days, project Semprec iOS, Standup subtitle) -> not a backend change.
- Events rule storage -> follows the recurrence-model ADR of the blocking issue; the issue instructs the implementer to read it first.

#### (c) User-visible behavior of this chunk

Events can repeat on fixed patterns (every day, weekdays only, weekly, monthly, the n-th weekday). The calendar shows each occurrence at its own date; changing one occurrence's time or place, or linking a recording, task or invitation to it, turns only that occurrence into its own event, and deleting that event cancels that day. A recording that overlaps a recurring event's occurrence is offered to the user as a match and only becomes linked to that single day when the user confirms. Recurring tasks appear in the calendar as occurrences too, each with its own done state, with missed ones not carried past the next occurrence. People can have a birthday (with an optional unknown year); each birthday appears every year as a read-only all-day entry titled with the person's first name in the Birthdays calendar (29 February on 28 February in common years), and Czech public holidays (including the movable Good Friday and Easter Monday) appear in the Public holidays calendar. These entries cannot be edited or deleted as events.
