**Blocked by:** #620

## Context

Before this batch, `withTokenAccounting` / `withAudioAccounting` in `backend/packages/ai-gateway/src/gateway.ts` awaited the provider (`invoke()`) and then a single `recordTokenGatewayCall` / `recordAudioGatewayCall` INSERT with no compensation: when that INSERT failed (pool exhausted, connection reset, statement error), the rejection propagated out of `complete()`; `backend/services/semprec-ai-gateway/src/completeHandler.ts` rethrows anything that is not a `BudgetExceededError`/`ProviderCallError` (line 256) and its outer `catch` (lines 277-278) answers **500 "Internal server error"**. The caller got nothing, the provider had already billed the call, and nothing recorded it.

E1 (see the pull request that closed it) replaced that INSERT with a reservation written before the call and a settle UPDATE (`settleTokenGatewayCall` / `settleAudioGatewayCall`) written after it — one attempt, still with no compensation. The paid-for result is still thrown away when the settle fails. This issue makes the settle step tolerant: retry it, and if it still fails, keep the result and leave the row `reserved` at its estimate (so it keeps counting against the cap) for later reconciliation.

## Task

In `backend/packages/ai-gateway/src/gateway.ts`:

- Introduce `SETTLE_MAX_ATTEMPTS = 3` and `SETTLE_BACKOFF_MS = [100, 300]` (delay before the 2nd and 3rd attempt) as module constants.
- Wrap the settle call of both helpers in one shared private function `settleWithRetry(pool, row, settle: () => Promise<AiGatewayCallRow>, ctx)`:
  - attempt the settle; on rejection, `logger.warn({ err, callId: row.id, attempt, provider: ctx.provider, model: ctx.model }, "ai_gateway_calls settle failed, retrying")`, wait the backoff, try again — up to `SETTLE_MAX_ATTEMPTS` total attempts.
  - after the last failure, `logger.error({ err, callId: row.id, attempts: SETTLE_MAX_ATTEMPTS, provider, model, estimatedCostUsd: ctx.estimatedCostUsd }, "ai_gateway_calls settle failed; row left reserved at its estimate")` and **return normally** so the helper returns the provider result to its caller.
  - A settle rejection is never rethrown to the caller. The retry is for transient database failures, not for a row someone else already changed: change `settleTokenGatewayCall` / `settleAudioGatewayCall` (E1 made them throw via `requireSingleRow` on zero rows) to return `AiGatewayCallRow | null`, `null` when the UPDATE matched no `reserved` row; `settleWithRetry` treats `null` as non-retryable — one error-level log line with `callId` and return. The zero-row case is still acted on by the caller (the log), as the affected-rows review rule requires.
- The fail path from E1 (`failGatewayCall` when `invoke()` rejects) is unchanged.

Tests in `backend/packages/ai-gateway/src/__tests__/gateway.test.ts` (integration; the settle UPDATE runs on `pool.query` directly, so it can be intercepted with `vi.spyOn(pool, "query")` delegating to the original implementation except for SQL matching `/UPDATE ai_gateway_calls/`):

- settle fails twice then succeeds: `complete()` resolves with the provider result, the row ends `'settled'` with the real values, exactly two warn-level log lines were emitted (capture via a spy on the module logger, as `shutdown.test.ts` does with `createCapturingLogger`, or by mocking `./logger.js`).
- settle fails three times: `complete()` still resolves with the provider result, the row stays `'reserved'` with `cost_usd` equal to the estimate, one error-level log line names `callId`.
- the row was flipped to `'failed'` by a concurrent writer before settle (simulate by running `failGatewayCall` inside the intercepted first UPDATE): no retry, one error log, `complete()` resolves.
- use `vi.useFakeTimers()` only if the 100 ms + 300 ms real backoff makes the test slow; real timers are acceptable at these values.

## Scope

### In scope

- Retry with backoff of the settle UPDATE, the log lines, returning the provider result on persistent failure, the `null` zero-row return of the two settle functions, and the tests above.

### Out of scope

- Retrying the reservation transaction or `failGatewayCall` — a failed reservation already rejects the call before any money is spent, and `failGatewayCall`'s failure already logs and rethrows the original error (E1).
- A sweep or scheduled job that reconciles rows left `reserved`.
- Retrying provider calls (sibling issue E6 of this batch) or any change to `completeHandler.ts` / `audioHandler.ts`.

## Acceptance criteria

- When the settle UPDATE fails transiently (fewer than three times), the caller receives the provider result and the row ends `'settled'` with the real usage.
- When the settle UPDATE fails three times, the caller still receives the provider result (HTTP 200 from `/internal/complete` and the audio routes), the row stays `'reserved'` with `cost_usd` equal to the estimate, and an error-level log line carries the row id.
- When the row is no longer `'reserved'` at settle time, no retry happens and the caller still receives the provider result.
- A settle failure never surfaces as a 500 from any gateway route.
