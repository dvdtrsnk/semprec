**Blocked by:** #1821
**Model tier:** low

## Context

Model tier rationale: A thin count route that reuses the list's read model and filter, with the same route-matrix pattern as the list, and no new storage or concurrency.

The Inbox header ("N to process"), the app badge source and the new-chat shortcut all need how many cards wait for a decision. REST has no count today. `GET /api/inbox/cards` (#1807) returns up to 200 cards plus a `total` over the same filter; this issue exposes just that number cheaply so clients and other server features do not fetch the stack to count it.

Decision: this issue owns the single definition of "open Inbox items". Both the list's `total` and this count read it from the same function in the read model; any other server feature that needs the number (the new-chat shortcut that reads this route, and the badge counts for open Inbox items) calls this function and does not re-implement it. This count does not include cards in the states `computing` and `computeFailed`: the list shows them, but a card is counted only once it has a proposal to decide (decided by the product owner), and the list's `total` follows the same rule.

Shared-file ordering: this issue also waits for #1821 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `testing`.

1. In `backend/packages/data/src/inbox/inboxCardsStore.ts` expose `countOpenInboxCards(client)` built on the same query/filter the list uses (the list's `total` must call it, so the two cannot diverge).
2. Add `GET /api/inbox/cards/count` returning `{ total }` as a custom route in `inboxModuleManifest.ts` (name `countInboxCards`, `justification: "single-consumer-read"`) with a handler in `inboxRouteHandlers.ts`. Tenant and user only from the session.
3. Add its case to `backend/services/semprec-api/src/routeMatrix.ts` and `backend/services/semprec-api/src/__tests__/tenantIsolationRoutes.test.ts`.
4. Tests: the count equals `total` of the list, also above 200 open cards; a confirmed card lowers it by one; a card in `computing` or `computeFailed` that the list returns is not counted; a second tenant's session does not see the first tenant's count.

## Scope

### In scope

- The count route, the shared count function and tests.

### Out of scope

- Realtime invalidation when the count changes: #1811.
- The app badge payload and the badge preference; those are separate notification issues that call `countOpenInboxCards`.

## Acceptance criteria

- `GET /api/inbox/cards/count` returns `{ total }` equal to the `total` of `GET /api/inbox/cards`, also when more than 200 cards are open.
- After a card is confirmed, the count is lower by one.
- A card in `computing` or `computeFailed` appears in `GET /api/inbox/cards` but is not included in the count.
- A session of another tenant receives that tenant's own count and never the first tenant's.
