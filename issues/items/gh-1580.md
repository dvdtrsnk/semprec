## Context

Model tier rationale: It extends an authenticated external protocol surface to a new class of tools, with capability gating, tenant scoping, error mapping and a new architecture decision, so a gating mistake exposes tools to the wrong caller.

`POST /mcp` (`backend/services/semprec-api/src/mcp/mcpHandler.ts`, `docs/adr/2026-09-18-mcp-json-rpc-transport-for-the-generic-operation-catalog.md`) answers `tools/list` and `tools/call` for the generic operation catalog only, naming each tool `semprec.<operation>`. A module can declare `agentTools` in its manifest (`{ name, handlerExport, capability? }`; `ModuleRegistry.getAgentTools(grantedCapabilities)` returns the active ones whose capability is granted), but today those are only projected into `/api/schema`: nothing runs them outside an agent session, and #1523 makes them available to Semp's own sessions.

This issue makes the same module tools available to MCP clients, so a module that adds a tool reaches Semp and MCP through one declaration. Examples that exist today: the `schemaCore` module's `heartbeat.list`, `heartbeat.history` and `heartbeat.trigger`.

Decisions:

- MCP tool names for module tools are `semprec.<toolName>` (the manifest tool names are already namespaced, for example `heartbeat.list`). A module tool whose name equals a generic operation name is refused when the listener is created, so a module can never shadow a generic operation.
- A tool is listed and callable only if its `capability` is absent or in the caller's effective capability set (the process-granted set, intersected with a restricted run credential's own set). A tool the caller may not see answers `tools/call` with the same "method not found" error as an unknown tool, never a distinguishable one.
- Module tools are resolved and invoked through the same resolver #1523 uses for agent sessions, not through a second copy.
- Whether a module tool may run without approval is decided by the grant ADR of #1385; this issue exposes every tool its resolver offers and leaves honoring an approval requirement for the first tool that needs it (#1957).

This is a new decision about the MCP surface, so it gets its own ADR that references (and does not edit) the 2026-09-18 transport ADR.

In `createMcpRequestListener` (`backend/services/semprec-api/src/mcp/mcpHandler.ts`) accept the `ModuleRegistry`; in `tools/list` append the module tools for the caller's effective capabilities, each with its input JSON schema; in `tools/call` resolve any other `semprec.` name that matches a module tool through the shared resolver, run it as the caller's actor inside the request's tenant scope, and map errors with the existing mapping (validation to -32602, approval required to -32001, choke-point errors to -32000, unknown or ungranted to -32601). Generic operation handling is unchanged. Throw when the listener is created if an active module tool has the same name as a generic operation.
3. Pass the registry from `backend/services/semprec-api/src/app.ts` where the listener is created.
4. Tests: `heartbeat.list` appears in `tools/list` as `semprec.heartbeat.list` and `tools/call` returns the same data as the tool in an agent session; a tool whose capability is not granted is absent from the list and its call returns the same -32601 as an unknown tool; a restricted run credential only sees the tools whose capability it holds; another tenant's data is never returned; a request without a bearer token is still rejected before any lookup; a module tool named like a generic operation makes listener creation fail; generic operations behave exactly as before.

## Scope

### In scope

- Listing and calling module agent tools over `POST /mcp`, with capability gating and the ADR.

### Out of scope

- Composing module tools into agent sessions and the approval-deferral field: #1523, #1791.
- The rule for granting module tools and when they need approval: #1385.
- Honoring an approval requirement over MCP and the calendar tools themselves: #1957.
- Mail tools over MCP: #1956.

## Acceptance criteria

- When an MCP client lists tools, then module tools whose capability is granted appear next to the generic operations, and ungranted ones are absent.
- When a client calls a granted module tool, then it returns the same data as the tool in an agent session, scoped to the caller's tenant.
- When a client calls an ungranted or unknown module tool, then the answer is the same -32601 error for both.
- The generic operations list and calls are unchanged.
