**Blocked by:** #1002

## Context

`items` is `PARTITION BY LIST (database_id)`, with one `items_p_<hex>` partition per database and primary key `(database_id, id)` (`backend/packages/data/src/db/migrations/0001_core_schema.sql:1-18`). Each tenant brings about 25 system databases plus its own, so the partition count grows with every tenant.

Three reads in `backend/packages/data/src/chokePoint/itemsStore.ts` carry no `database_id` predicate and therefore touch every partition of every tenant:
- `getItemsByIds` (`:390-398`). It backs `GET /api/items/:id` (`backend/packages/data/src/chokePoint/itemReads.ts:78-83`), view membership, docs (`backend/packages/data/src/docs/docsStore.ts:66`), approvals and the inbox.
- `getItemsByIdsIncludingDeleted` (`:407-415`). It backs `DELETE /api/items/:id` and restore (`itemReads.ts:90-95`), the destructive projection and the trash purge.
- `findItemsDeletedBefore` (`:264-280`). The trash purge's candidate scan, which #986 runs once per tenant.

Row-level security already hides other tenants' rows from these queries: `items` carries the RESTRICTIVE `tenant_isolation` policy `tenant_id = (SELECT app_tenant_default())`, and `databases` does too. RLS still leaves every partition in the plan, so each lookup's cost grows with the number of tenants. It also keeps other tenants' partitions in the access path.

The pruning predicate must be a bound array parameter. A `database_id = ANY(ARRAY(SELECT id FROM databases))` sub-select does not prune. Verified with `EXPLAIN ANALYZE` on PostgreSQL 15: every partition was executed, because partition pruning accepts a `= ANY(...)` array only as a constant or an `ARRAY[...]` constructor, not as a sub-plan parameter. A bound array parameter does prune: node-postgres sends unnamed statements, which are planned with the parameter values, so the plan contains only the matching partitions. An empty array plans to `One-Time Filter: false`.

This issue follows #1002 only because both edit `itemsStore.ts`.

## Task

Load `state-writes` (these reads feed write paths such as delete and restore, and must not change which rows they see).

1. **Helper.** Add a private `async function visibleDatabaseIds(client: Queryable): Promise<string[]>` to `itemsStore.ts`:
   - it runs `SELECT coalesce(array_agg(id), '{}') AS ids FROM databases`, with a typed row (`{ ids: string[] }`);
   - under RLS this returns exactly the current tenant's databases, archived ones included, as today;
   - do not add a hand-written `tenant_id` predicate.
2. **Prune the three reads.**
   - `getItemsByIds` and `getItemsByIdsIncludingDeleted`: keep the early `[]` for empty input, then add `AND database_id = ANY($2::uuid[])` bound to the helper's result.
   - `findItemsDeletedBefore`: add the same predicate as a new parameter. Keep its keyset order and paging unchanged.
   - Results must be identical to today's for every caller.
   - Update each docstring: the read is confined to the current tenant's partitions by a database-id list resolved under RLS.
3. **Tests.** New `backend/packages/data/src/__tests__/itemLookupPruning.test.ts`. The two-tenant cases run in one transaction on `getTestPool()` (the owner), rolled back at the end:
   - `DROP INDEX IF EXISTS tenants_single_tenant_guard`, then insert a second `tenants` row;
   - create databases and items in each tenant with `databasesStore.createDatabase` / `itemsStore.insertItem` under `SELECT set_config('app.tenant_id', $1, true)`;
   - `SET LOCAL ROLE semprec_data`.

   To inspect the plan, wrap the client so the test records the SQL and parameters each function sends. Then run `EXPLAIN (FORMAT JSON)` on that statement with those parameters and collect the scanned relation names. Integration files run one at a time (`fileParallelism: false`, `backend/vitest.integration.config.ts:20`).

## Acceptance criteria

All integration tests (`*.test.ts`).
- In tenant B's scope under `semprec_data`:
  - the plan of the statement `getItemsByIds` sends scans only B's `items_p_*` partitions, none of tenant zero's;
  - the same holds for `getItemsByIdsIncludingDeleted` and `findItemsDeletedBefore`.
- In tenant B's scope, `getItemsByIds` and `getItemsByIdsIncludingDeleted` called with one id of B's and one id of tenant zero's return only B's item.

- In the scope of a tenant with no databases, all three return `[]`. The plan is `One-Time Filter: false` and scans no partition.
- With a single tenant and no scope (the transitional default), all three return exactly what they returned before. The existing `itemReads.test.ts`, `itemTrash.test.ts` and `backend/packages/data/src/trash/__tests__/purgeExpiredTrash.test.ts` pass unchanged.
- `getItemsByIds([])` and `getItemsByIdsIncludingDeleted([])` still return `[]` without querying.
