## Context

Login throttling (issue #232's exponential lockout) does not work through HTTP at all. `backend/services/semprec-api/src/authHandler.ts`, `createAuthRequestListener`, `POST /api/auth/login` branch (currently lines 158-166), runs `login()` inside `withTransaction(pool, ...)`. `login()` in `backend/packages/data/src/auth/authActions.ts` (currently lines 98-130) calls `recordLoginAttempt(client, { ..., succeeded: false })` and then `throw new UnauthorizedError()` on both failure branches — the active-lockout branch (lines 105-106) and the unknown-email / wrong-password branch (lines 114-115). `withTransaction` in `backend/packages/data/src/db/pool.ts` (lines 53-56) catches the throw, issues `ROLLBACK` and rethrows, so the `login_attempts` row written by the failed attempt is discarded with the transaction. `getFailureStreak` therefore always reads 0 through HTTP, `lockoutDurationSeconds` never exceeds 0, and password guessing is unthrottled.

Verified against `develop` HEAD with a probe test: six wrong-password `POST /api/auth/login` requests followed by the correct password returned 200, and `SELECT count(*) FROM login_attempts` was 0.

`backend/packages/data/src/__tests__/authActions.test.ts` passes a bare `Pool` (auto-commit) to `login`, which is why its lockout cases pass; `backend/services/semprec-api/src/__tests__/authHandler.test.ts` has no lockout case.

Sibling issue B2 of this batch (keying the lockout on the Caddy-forwarded client IP) depends on this fix; sibling B7 later edits the same handler.

## Task

- Change `login`'s signature in `backend/packages/data/src/auth/authActions.ts` from `login(client: Pool | PoolClient, input: LoginInput)` to `login(pool: Pool, input: LoginInput)`, mirroring `requestPasswordReset(pool, ...)` in `passwordResetActions.ts`, which already owns its own transaction for the same reason. Inside `login`:
  - `getFailureStreak`, the lockout decision, `getUserByEmail`, `verifyPassword` and both `recordLoginAttempt(..., { succeeded: false })` calls run directly on `pool` (auto-commit), so a failed attempt is persisted regardless of the `UnauthorizedError` thrown right after it.
  - The success path — `createSession` plus `recordLoginAttempt(..., { succeeded: true })` — runs inside one `withTransaction(pool, ...)` so the session row and the streak-resetting success row still commit or roll back together.
  - Keep the return type `Promise<LoginResult>`, the `UnauthorizedError` semantics ("same message for every failure reason") and the dummy-hash timing equalisation unchanged. Update the docstring to say why failures are recorded outside the transaction.
- In `backend/services/semprec-api/src/authHandler.ts`, the login branch calls `await login(pool, { ... })` directly instead of wrapping it in `withTransaction`. Nothing else in the handler changes (the `ip:` expression is sibling B2's concern). `withTransaction` stays imported — the other routes still use it.
- Every existing caller already passes a `Pool` (the tests in `authActions.test.ts`, `pushSubscriptions.test.ts`, `push/__tests__/pushRouteHandlers.test.ts`, `mcp/__tests__/mcpGenericOperationsContract.test.ts`, `approvalRequestsHandler.test.ts`, `itemsHandler.test.ts` and others), so no call site outside the handler needs editing; confirm with `pnpm -r run build`.
- Add an HTTP-level test to `backend/services/semprec-api/src/__tests__/authHandler.test.ts` inside the existing `describe("POST /api/auth/login")` block (integration tier, `*.test.ts` against embedded Postgres): create a user; send `LOCKOUT_THRESHOLD` (import from `@semprec/data`) requests with a wrong password; then send the correct password. Assert the final response is 401, and that `SELECT count(*) FROM login_attempts WHERE succeeded = false` equals `LOCKOUT_THRESHOLD + 1` (the locked-out attempt is itself recorded as a failure).

## Scope

### In scope

- Persisting failed login attempts so the existing `getFailureStreak` / `lockoutDurationSeconds` throttle engages through `POST /api/auth/login`.
- The one HTTP-level lockout test described above.

### Out of scope

- Which IP the streak is keyed on (`req.socket.remoteAddress` is the loopback address behind Caddy) — sibling issue B2 of this batch.
- Validating the `:id` segment of `POST /api/auth/sessions/:id/revoke` — sibling issue B7.
- The error body shape of the handler's `catch` block — sibling issue B8.
- Any change to the lockout thresholds in `backend/packages/data/src/auth/loginLockout.ts`, to `login_attempts` retention, or to setup-token brute-force limiting.

## Acceptance criteria

- When a client sends `LOCKOUT_THRESHOLD` wrong-password requests to `POST /api/auth/login` for one email and then the correct password from the same address, the correct-password request is answered 401 and `login_attempts` holds one `succeeded = false` row per request, including the locked one.
- When a client sends fewer than `LOCKOUT_THRESHOLD` wrong passwords and then the correct one, the correct one is answered 200 and a `succeeded = true` row is written in the same transaction as the new `sessions` row.
- `login` accepts a `Pool` only; `pnpm -r run build`, `pnpm run test:unit` and `pnpm run test:integration` pass with no other call site edited.
- Every existing case in `authActions.test.ts` (`describe("lockout (issue #232)")`) still passes unchanged.
