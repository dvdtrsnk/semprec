## Behavior specification

Relations in the API: edge reads, expansion, atomic writes and realtime.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: relation-api-1

#### (a) Adopted decisions
- Should `relation.set` be a flag on `relation.put`? -> No, a separate `relation.set` operation -> MCP and approval need to tell "replace an edge" from "add an edge".
- Should agents get `relation.set` now? -> Yes, exposed to agents and MCP in #1521 -> the product owner decided in the links batch (#1326) that a plain replacement carries the ordinary non-destructive `write` risk class without approval; only a real value-link break forces approval (#1713, #1758).
- Is `relation.list` destructive? -> No, `core.item.read`, no approval -> pure read.
- Do deleted-target and archived-database targets appear in list/expansion? -> No, both excluded -> Decided by the product owner: archiving a database behaves as the trash everywhere (as in the trash batch); expansion and reads omit it. (#1404, #1518)
- Unknown relation key in `include`? -> `400` for the whole request -> explicit failure over silent omission.
- Nesting depth of expansion? -> One level; a projected relation key of a target returns a reduced target -> bounds cost and response size.
- Colour/icon of targets? -> Always returned when the target database defines them -> label rendering needs no projection.
- `item.create` relations semantics? -> Additive only, single-valued keys accept exactly one target, idempotency key covers the whole call.
- Realtime scope name? -> `relation` (singular); thin frame without `updatedAt` -> unified owner is the realtime issue.
- Dedup of events? -> At most one per (itemId, propertyKey) per transaction -> covers bulk mail sync.
- Does the target of a one-directional relation receive a realtime event? -> Decided by the product owner: yes, a thin item invalidation without a property key (`propertyKey: null`), so backlinks at the target do not go stale. (#1621)
- Does a `one_to_one` set steal a target that is already linked to a third item? -> Decided by the product owner: no, it returns `409 cardinality_violation`; silently ending another item's link would break the rule that links are never broken without an explicit action. (#1521)

#### (b) Open questions for the product owner
- None; all were decided by the product owner and are recorded under (a).

#### (c) User-visible behavior
Items can now be read together with their links: one request returns a person with companies and projects (title, colour, icon, and a project's area label), a list of projects with their areas, and any one-directional link such as a file's area. A task or project can be moved to another project or area in a single atomic step, a new item can be saved together with its links in one transaction, and every change to a link is announced in real time to the other open sessions of the same account so that lists and details update immediately.
