**Blocked by:** #974

## Context

`writeNotification` (`backend/packages/data/src/notifications/notify.ts:76-116`) is the one writer of `notifications`. It deduplicates a replayed transition with `ON CONFLICT (source_table, source_id, kind, transition_instance) DO UPDATE SET source_table = notifications.source_table ... RETURNING id, created_at, (xmax = 0) AS inserted` (`notify.ts:87-92`). The arbiter is the global `notifications_dedupe_idx` (`backend/packages/data/src/db/migrations/0030_notifications_schema.sql:67-68`), which names neither the recipient nor the tenant.

So when two recipients get a notification about the same source transition, the second write conflicts with the first recipient's row. The no-op `DO UPDATE` then returns **the first recipient's notification id** to the second caller (`notify.ts:115`) with `inserted = false`, so no row, no fan-out job and no realtime hook exist for the second recipient (`notify.ts:110-113`). With tenants, that is both a dropped notification and another user's id handed back.

What earlier issues provide:
- Every tenant-owned table, `notifications` included, has `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)` and row-level security.
- The SQL functions behind the default:
  - `app_current_tenant()` = `NULLIF(current_setting('app.tenant_id', true), '')::uuid`;
  - `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())` until #1067 makes it `app_current_tenant()` alone.

  An insert that does not name `tenant_id` lands in the current tenant, or in the sole tenant when no scope is set.
- #974 added `notifications_tenant_dedupe_idx ON notifications (tenant_id, user_id, source_table, source_id, kind, transition_instance)` beside the legacy index.
- The legacy index stays until #1065 drops it. That drop is safe only once every writer has moved its arbiter to the new index. For `notifications`, this issue moves it.

Postgres picks its arbiter from the unique indexes whose columns exactly match the `ON CONFLICT` column list. While the legacy index exists, a write that collides only with it raises `unique_violation` (`23505`) instead of being attached to another recipient's row. The collision is the same source transition for a different recipient. Production cannot reach it before #1065: there is one tenant, and `users.tenant_id` is unique, so there is one user. #1019 sends operator alerts to several admins and gives each recipient its own `transitionInstance`.

The change is code only. The previous release keeps its old conflict target, which the legacy index still satisfies.

## Task

Load `state-writes` (the upsert's returned id is trusted by every producer) and `error-handling` (a legacy-only collision must surface, never be mapped onto a success).

1. **Conflict target.** In `writeNotification`, change the conflict target to `ON CONFLICT (tenant_id, user_id, source_table, source_id, kind, transition_instance)`.
   - Keep the `DO UPDATE SET source_table = notifications.source_table` no-op and the `RETURNING id, created_at, (xmax = 0) AS inserted`.
   - Do not add `tenant_id` to the insert column list: the column default fills it from the scope.
   - Before you write it, confirm in #974's migration that `notifications_tenant_dedupe_idx` has exactly these six columns. Inference needs an exact match.
2. **No catch.** A `unique_violation` raised by the legacy index propagates unchanged and rolls back the caller's transaction.
3. **Docstrings.** Rewrite the docstrings that describe the old key:
   - `WriteNotificationInput.transitionInstance` (`notify.ts:38-45`): it identifies one transition for one recipient.
   - `writeNotification` (`notify.ts:54-75`): the dedupe key is per tenant and recipient. A replay returns that recipient's own id. Note the transitional legacy-index behaviour from step 2.
4. **Tests.** Add the cases below to `backend/packages/data/src/__tests__/notify.test.ts`. The two-recipient cases run inside one transaction opened with `withTransaction` on the superuser test pool. The test makes it roll back by throwing a sentinel error it then catches. Inside that transaction:
   - `DROP INDEX IF EXISTS tenants_single_tenant_guard`;
   - insert a second `tenants` row with `status = 'active'`;
   - create one test user per tenant with `createUser`'s `tenantId` option from #968 (`users.tenant_id` is unique);
   - switch tenants with `SELECT set_config('app.tenant_id', $1, true)`;
   - for the post-drop case, `DROP INDEX notifications_dedupe_idx`.

   The rollback restores every dropped index and row.

## Acceptance criteria

- **Replay.** Replaying a transition for the same recipient and tenant still yields exactly one row. Both calls return the same id, and the replay enqueues no second fan-out job and fires no realtime hook. The existing replay and hook tests in `notify.test.ts` pass unchanged. (integration, `notify.test.ts`)
- **Two recipients.** Inside the rolled-back transaction with `notifications_dedupe_idx` dropped, the following holds when tenant zero's user and tenant B's user each get a notification with identical `sourceTable`, `sourceId`, `kind` and `transitionInstance`:
  - there are two rows with two distinct ids;
  - each row carries its own recipient's `user_id` and that recipient's `tenant_id`;
  - each recipient's replay returns that recipient's own id.

  (integration, `notify.test.ts`)
- **Legacy collision.** With `notifications_dedupe_idx` still present, tenant B's write for that same transition rejects with Postgres code `23505` on `notifications_dedupe_idx`. It never returns tenant zero's notification id. (integration, `notify.test.ts`)
- **Scope-less.** With no tenant scope and only tenant zero present, a write lands with tenant zero's `tenant_id`, exactly as before this change. (integration, `notify.test.ts`)
