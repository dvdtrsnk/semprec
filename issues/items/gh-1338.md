## Behavior specification

Mail compose: drafts, reply and forward, sending.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: mail-compose-1

#### Adopted from open questions
- Upload the draft to the provider's Drafts folder? -> No; the draft lives only in Semprec (as today) -> keeps one source of truth until provider drafts are asked for. -> Decided by the product owner: the draft lives only in Semprec; draft synchronization is not in v1.
- "Cancel" in compose: keep the draft; an empty new draft is discarded by the client with DELETE -> no data loss. -> Decided by the product owner: Cancel keeps the draft and an empty new draft is deleted.
- Body: plain text, MIME `text/plain` -> Markdown-to-HTML conversion is left out. -> Decided by the product owner: `text/plain` only; HTML from Markdown comes later (not in v1).
- Reply-all with no Cc field in the compose window: all recipients go to `to`, Cc stays empty. -> Decided by the product owner: all recipients go to To and Cc stays empty as long as the compose window has no Cc field.
- Provider drafts (no `mail_drafts` row) are read-only: PATCH, DELETE and send answer 409 `mail_draft_not_editable`. -> Decided by the product owner: provider drafts are read-only (409).
- Messages synced before Reply-To parsing have no stored Reply-To; replies fall back to From (no backfill).
- Provider limits on total attachments: Gmail 25 MB, Outlook.com 20 MB, iCloud 20 MB, generic `MAX_FILE_SIZE_MB`.
- Contacts suggestions cover People only in this phase. -> Decided by the product owner: limits per provider, otherwise `MAX_FILE_SIZE_MB`; suggestions come from People only.

#### Open questions for the product owner
- Who marks a new draft as read (`read` property)? Not covered by these issues.

#### User-visible behavior
The user can compose a message: the first edit creates a draft that is visible in the Drafts folder, reopening it shows the same recipients and sending mailbox, and edits are versioned so concurrent edits are detected. A draft can be discarded, and attachments can be added (including copies when forwarding) within the provider's size limit. Reply, reply-all and forward start prefilled drafts: recipients from Reply-To or sender (own addresses removed), From as the address the message arrived on, "Re:"/"Fwd:" without doubling, correct threading headers and a localized quoted text. Typing in the To field suggests people by name or address (accent-insensitive). Provider-created drafts stay read-only, and Semp is limited to one unsent draft per thread.


### Decisions: mail-compose-2

#### Adopted from open questions
- Mailbox without a valid sign-in (needsReauthorization) -> the send returns `mail_reauthorization_required` and the draft is kept; no outgoing queue -> avoids silently delaying mail. -> Decided by the product owner: an error asking to sign in again, the draft stays; no outgoing queue in v1.
- Send is for the user only; agent/MCP sends go through approval -> #1913. -> Decided by the product owner: neither Semp nor MCP sends mail without approval; the user always approves an outgoing action.
- Body is text/plain (from the draft decision) -> MIME builder produces only a plain text body plus optional calendar alternative.
- A repeated send returns `mail_draft_already_sent` with `{ emailId, threadId }` instead of `version_conflict` -> lets a client after a timeout learn the result.
- Gmail threading uses the provider thread id of the source message; Graph preserves Message-ID (proved by tests, set via `internetMessageId` on the large path); IMAP APPEND is best effort after SMTP.
- Transport errors are typed in the data layer; HTTP codes are assigned in the send route issue.

#### Open questions for the product owner
- Large Graph messages (over 4 MB): the design note prescribes creating a provider-side message with upload sessions; behavior with MIME-only attachments on Graph should be confirmed against a real account before relying on it.
- Code names `mail_auth_failed` and `mail_server_unreachable` are also introduced by the credential verification work; whichever merges first adds them.

#### User-visible behavior
The user can send a saved draft with one tap. The message leaves from the draft's mailbox through the provider's own route (SMTP for iCloud and generic accounts, the Gmail API or Microsoft Graph for Google and Microsoft), carries replies in the right conversation with In-Reply-To and References, and includes attachments and, for meeting mail, a calendar part. A second tap does not send again and tells the client which message was sent. Sending is refused with a specific reason when there is no recipient, the From address is not the mailbox's, the mailbox needs signing in again, a recipient is rejected, the server is unreachable or the Sent folder is missing, and the draft stays editable. After a successful send the thread shows exactly one new message and the draft card disappears; messages sent from iCloud or generic accounts also appear in the provider's Sent folder.
