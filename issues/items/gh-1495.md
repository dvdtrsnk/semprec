## Context

Model tier rationale: One field added through an existing bracketed write path (compute input, result, write), with a locale lookup and clear overwrite rules; the shapes are fixed by the earlier issues.

A proposal card should say why the assistant proposed what it did, in the user's language (for example "A clear action with a deadline, so a task for tomorrow at 9:00."). Today a card has no such field: the only text is the `history` log, whose entries are fixed English sentences (`appendHistoryEntry` in `backend/packages/data/src/inbox/inboxTickAction.ts`). #1451 adds a system-owned `reason` text property to Processing proposals for cards of kind `inbox`. #1434 builds the model-backed `computeProposal` that the tick calls; its structured output carries the properties, a reason and a confidence, and #1987 later adds the workspace context to its input. Transcript cards fill the same property through their own producers, and the cards list reads it as the card's reason.

The tick follows the bracket in `docs/adr/2026-09-10-bracket-non-transactional-calls-with-staleness-checked-transactions.md`: read transaction, computation outside any transaction, write transaction that re-checks staleness. The user's language is the locale of the tenant's user (`getTenantUserId` in `backend/packages/data/src/auth/usersStore.ts`, passed unchanged as required by gh-1358; `cs` only when no user locale resolves. Catalog and recognition cs/en projection remains separate).

Decision: the computation receives `locale` and must write `reason` in that language; the tick stores the text as returned, trimmed and capped at 500 characters, on every create and every revise, replacing the previous reason.

Decision: a card written by a mechanical path of the tick (no recognized type, failed validation, deleted source) stores `reason: null`, and a card in status `invalid` never gets a reason (a separate field, `invalidReason`, describes that case).

Decision: a computation that returns no reason text stores `reason: null`; it is not an error.

The fixed text for a card created from a clarification choice is delivered with the type-replacement route (#1947); the approval cards read the agent's reason from the approval request (#1420).

Controller reconciliation section 6 in issues/batches/backend/decisions/batch-23-spec-reconciliation.md preserves gh-1358 raw locale, including fr; no computation locale narrowing or fingerprint change.

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. Extend `ProposalComputationInput` with `locale: string` and `ProposalComputationResult` with an optional `reason?: string` in `inboxTickAction.ts`. Resolve the locale in `readTickSnapshot` and carry it in the snapshot.
2. In the production `computeProposal` of #1434 (`backend/services/semprec-api/src/proposalComputation.ts`) put the locale into the request and the instruction text ("write `reason` in this language, one or two sentences, no markup") and return the model's `reason`.
3. In `writeTickResult`, `reviseProposal` and the create path add `reason` (normalized as in the Decision) to the written properties and to the `allowedSystemKeys` list; mechanical writes (`writeNeedsClarification`, `invalidateProposalForDeletedSource`) set `reason: null` or leave it untouched for `invalid`.
4. Keep `parseStoredProposalEnvelope` and the envelope shape unchanged; `reason` is a card property, not part of the envelope.
5. Tests: a stubbed computation returning a Czech reason stores it on a new card and replaces it on a recompute; the stub receives `locale: "cs"` for a Czech user and `"en"` for an English one; a reason over 500 characters is truncated; no reason stores null; `needsClarification` and `invalid` writes carry no model reason; a client cannot write `reason` through the generic item update.

## Acceptance criteria

- When a card is computed for a Czech-speaking tenant user, then its `reason` is the Czech text returned by the computation, and a later recompute replaces it.
- When a card is `invalid` or needs clarification without a computed proposal, then it has no reason.
- When the computation returns a reason longer than 500 characters, then the stored text is cut to 500.
- A user cannot set `reason` through the generic item update.
