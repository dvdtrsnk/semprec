## Context

Model tier rationale: One registration of an item delete hook through the existing per-process hook registry, with the one subtlety that the dedicated removal path must still pass it.

#1690 adds `DELETE /api/mail/mailboxes/:id`, which removes a mailbox's credential and sync state with the mailbox. The generic `DELETE /api/items/:id` can still soft-delete a Mailboxes item without that cleanup, leaving its secret and live lifecycle behind. #1601 adds item delete hooks to the choke point (`registerItemDeleteHook` in `backend/packages/data/src/chokePoint/hooks.ts`), composed per process in `backend/packages/data/src/domainWriteHooks.ts` (`docs/adr/2026-09-30-choke-point-domain-hooks-through-a-per-process-registry.md`).

Shared-file ordering: this issue also waits for #1669 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `backend/packages/data/src/mail/mailboxDeleteHook.ts`: an item delete hook for the Mailboxes database that refuses the delete with a 403 error, so the cleanup cannot be bypassed. The removal of #1690 proceeds past it by its own system path (a marker the removal passes in the hook context), which no generic route, agent tool or `/mcp` operation can set.
2. Register the hook in `domainWriteHooks.ts`.
3. Tests: `DELETE /api/items/:id` on a Mailboxes item answers 403 and the mailbox, its credential and its sync state are unchanged; the same request from an agent is refused the same way; `DELETE /api/mail/mailboxes/:id` still removes the mailbox; deleting an item of another database is unaffected.

## Acceptance criteria

- When `DELETE /api/items/:id` targets a Mailboxes item, then the answer is 403 and nothing changes.
- When the mailbox is removed through `DELETE /api/mail/mailboxes/:id`, then the removal succeeds.
- When an item of another database is deleted, then the hook does not interfere.
