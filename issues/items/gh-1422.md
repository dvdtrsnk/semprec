**Blocked by:** #1402, #1415
**Model tier:** high

## Context

Model tier rationale: This introduces a new write-path contract that every module's item writes can pass through (ownership enforcement on keys a transform adds, a row lock, replay behavior, and a behavior-preserving move of the Tasks time derivation), so a mistake would corrupt or mis-attribute writes across modules.

Today the choke point can only reject a write, never change it. `createItemWithClient` and `updateItemWithClient` (`backend/packages/data/src/chokePoint/itemWrites.ts`) run `runItemCreateHooks` / `runItemUpdateHooks` (`chokePoint/hooks.ts`) after the row is written, and those hooks return `void`. The single pre-write transformation that exists is an inline branch gated on `database.ownerModuleId === TASKS_MODULE_ID` that calls `deriveTaskTime` (`tasks/deriveTaskTime.ts`); on update it takes `lockItemById` only when `timeFrom` or `timeTo` is in the patch. That inline branch is the exception the ADR `2026-09-19-derived-system-properties-computed-inline-at-choke-point` documents and `2026-09-30-choke-point-domain-hooks-through-a-per-process-registry` carves out for `tasks/`.

This issue adds the missing mechanism: a per-process registry of pre-write transforms, one or more per owning module, that receive the incoming patch and return a new patch (or throw `ValidationError`) before anything is written. Several later features need it: normalizing Events times (#1598), validating Tasks titles and dates (#1536), recording a task's completion day (#1544) and first planned day (#1602), recurring-series identity (#1605, #1668), unpinning finished projects (#1520), select-option validation (#1802), sleep validation (#1784), iCalendar identity (#1599) and task visibility (#1780). They each register a transform instead of editing `itemWrites.ts`. The next hook mechanism, #1530, builds on this issue because both edit the hook registry file.

Decisions:
- A transform is attached to a module id and runs only for databases whose `ownerModuleId` equals that id.
- The row lock is taken whenever the database has at least one registered transform (the contract hands `stored` to the transform). For Tasks this means every Tasks update now locks the row, not only updates that touch `timeFrom`/`timeTo`; the resulting values are unchanged.
- Keys of an update that rollup dependency lookup and the timezone check inspect are taken from the transformed patch, so a key a transform adds (for Tasks, `time`) is treated like any other written key.
- `writerKind` is not part of this issue. If it is already on the item write options when this lands (#1415), include it in the transform context; otherwise that issue adds it.

Shared-file ordering: this issue also waits for #1402, #1415 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `testing` and `adr-conventions`.

1. In `chokePoint/hooks.ts` add `registerItemPreWriteTransform(moduleId, fn)`, the exported types `ItemPreWriteTransformContext` and `ItemPreWriteTransform`, `hasItemPreWriteTransform(moduleId)` and `runItemPreWriteTransforms(moduleId, context)`. The context is `{ client, database, stored, patch, humanWriterUserId, writer }`, where `stored` is the locked current `ItemRow` on update and `null` on create, and `writer` is the `WriterIdentity` the create and update hook contexts already carry (#1415 landed before this issue: `options.writer ?? SYSTEM_WRITER`). `fn` returns the new patch (`Record<string, unknown>`) or throws `ValidationError`. Several transforms for one module run sequentially in registration order, each receiving the previous output; registering the same `(moduleId, fn)` twice is a no-op. Extend `clearHooksForTests` to clear the new registry.
2. In `createItemWithClient`, run the transforms for `database.ownerModuleId` after `assertWritableProperties` and before `insertItemWithReplay`. Insert and pass the transformed properties to `runItemCreateHooks`. If `insertItemWithReplay` reports `created: false` (idempotent replay), return the existing item and discard the transform result: nothing new is written and no hook runs.
3. In `updateItemWithClient`, after `assertWritableProperties`, when `hasItemPreWriteTransform(database.ownerModuleId)` is true take `itemsStore.lockItemById` (throw `NotFoundError` for a missing or trashed row), then run the transforms and use the result as the patch passed to `updateItemProperties`, `runItemUpdateHooks`, the rollup-dependency loop and the timezone check (`triggerOnItemEventHeartbeats` takes no patch and is unchanged). Databases with no registered transform take no new lock.
4. Enforce the result: a key the transform added (present in the output, absent from the input) must exist on the database, must not be a `rollup` or `relation` property, and, if its `owner` is `system`, its `ownerProcess` must be `null` or equal the transform's `moduleId`; otherwise throw `ForbiddenError` with code `owner_violation` (`ValidationError` for an unknown key). A `null` `ownerProcess` is allowed because the seeded derived keys (`seedTenDatabases.ts`: Tasks `time`, Events `time`) declare no process and the database's owning module is their single writer, as it was for the inline derivation under `2026-09-19-derived-system-properties-computed-inline-at-choke-point`; `ownerProcess` is a process name (`transcribe`, `valueLinks`), never a module id, so a declared process stays a violation. Keys the caller already sent keep the existing `assertWritableProperties` result.
5. Move the Tasks `time` derivation out of `itemWrites.ts` into a Tasks-owned transform in a new file `backend/packages/data/src/tasks/tasksItemPreWriteTransform.ts` that calls `deriveTaskTime`, and register it in `domainWriteHooks.ts` under `TASKS_MODULE_ID`. Remove the `TASKS_MODULE_ID` and `deriveTaskTime` imports and both inline branches from `itemWrites.ts`. Create writes `time` always; update writes it when the patch contains `timeFrom` or `timeTo`, computed from the patch merged over `stored`. The behavior of every existing Tasks write stays identical.
6. Add an ADR under `docs/adr/` (dated the day it is written, `status: accepted`, `area: [backend]`, `supersedes: [2026-09-19-derived-system-properties-computed-inline-at-choke-point]`) recording the registry and its contract: derived system properties now come from a registered pre-write transform, the ownership rule of item 4 on keys a transform adds, the row lock of item 3, and `itemWrites.ts` names no domain. Per `adr-conventions`, change only the frontmatter of `2026-09-19-derived-system-properties-computed-inline-at-choke-point.md` (`status: superseded`, `superseded-by: <new-slug>`). The new ADR's Context references `[[2026-09-30-choke-point-domain-hooks-through-a-per-process-registry]]` and states what it amends about that ADR's `tasks/` (`deriveTaskTime`) exception: the derivation no longer lives in `itemWrites.ts`. That ADR is accepted and not superseded, so neither its body nor its frontmatter is changed (`docs/adr/README.md`, `review-rules/rules.md`).
7. Tests: unit tests in `chokePoint/__tests__/hooks.unit.test.ts` for the registry (order, duplicate registration, clear); an integration test that a transform's patch is what is stored and gives one `updatedAt`, that a replay with the same `Idempotency-Key` writes nothing and runs no hook, and that a transform adding an owner `system` key of another `ownerProcess` ends in `403 owner_violation`. The existing Tasks `time` tests (`__tests__/tasksTime.test.ts`, `__tests__/deriveTaskTime.unit.test.ts`) pass unchanged.

## Scope

### In scope

- The transform registry, its two call sites, the ownership check on added keys, the Tasks `time` move and the ADR.

### Out of scope

- Any transform other than Tasks `time`: Events normalization (#1598), Tasks validation (#1536), and the other features listed in Context each register their own.
- Reading `writer` inside a transform for any rule: this issue only carries it in the context; the features listed in Context each decide their own use.
- Relation edge and delete/restore hooks: #1530, #1601.
- Changing the hooks that run after a write, or the data migration of stored Tasks values.

## Acceptance criteria

- When a transform registered for Events turns `"9:00"` into `"09:00"`, the stored row contains `"09:00"`, the row has exactly one `updatedAt` change, and the update hooks receive the transformed patch.
- When the same create is repeated with the same `Idempotency-Key`, the existing item is returned, nothing is written, and no transform result, create hook or heartbeat is applied a second time.
- When a transform adds an `owner: system` key whose `ownerProcess` is another module, the write ends in `403 owner_violation` and nothing is stored.
- When a transform throws `ValidationError`, the write fails with `400 validation_failed` and the transaction is rolled back.
- When a database has no registered transform, an update takes no extra row lock and behaves exactly as before.
- The existing Tasks `time` tests pass without modification, and `itemWrites.ts` no longer imports from `tasks/`.
