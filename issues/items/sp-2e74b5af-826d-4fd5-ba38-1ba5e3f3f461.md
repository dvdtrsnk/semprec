### Requirement gh-1434: [inbox-core 05/22] Implement computeProposal and register semprec.tick in the api runtime

#### Context

Model tier rationale: It adds the first model-backed write-adjacent computation of the Inbox, composed into the api runtime with a new registration, the bracket rule (no transaction around the call) and a "never writes" guarantee, and many later issues build on its shape.

The Inbox tick is the heartbeat action `semprec.tick` (`createSemprecTickAction` in `backend/packages/data/src/inbox/inboxTickAction.ts`), fired on create, update and delete of Inbox items. It reads the item and its type in one transaction, calls an injected `ComputeSemprecProposalFn`, then writes a card in a second transaction after re-checking that the item has not changed (`docs/adr/2026-09-10-bracket-non-transactional-calls-with-staleness-checked-transactions.md`). The function type exists but nothing implements it, and `createApiActionRegistry` (`backend/services/semprec-api/src/actionRegistryComposition.ts`) deliberately does not register `semprec.tick` ("absent until an LLM-backed proposal computation exists"). Every Inbox heartbeat therefore fails with "No handler registered", is retried (`maxAttempts` 3) and reports a heartbeat error. The tick is a system process of the `semprec-api` runtime (`heartbeatFireCore`, lane `semprec-tick:<tenant>`), not an agent run.

#1392 registers the gateway operation `inbox_proposal` (it requires a `projectItemId`) on `POST /internal/complete`; the caller sends the `responseSchema`. `createAgentGuidanceDriftActionForApi` in `backend/services/semprec-api/src/projectAgentGuidanceComposition.ts` shows how this process builds the HTTP gateway client (`createHttpAiGatewayClient`, `AI_GATEWAY_PORT`, `AI_GATEWAY_INTERNAL_TOKEN`). Later issues build on this one: the workspace context and capture time (#1987), failure recording (#1485), relations (#1488), multi-step operations (#1492), the reason text and type recognition (#1495, #1500) and recompute routes (#1955).

Decision: one structured call per tick, not an agent session. The result is `{ target?: string, properties: object, reason?: string, confidence?: number }`. The call is attributed to the project the heartbeat belongs to, which is the Semprec project: `ActionContext.projectItemId` is passed by the tick into the computation input as `projectItemId`.

Decision: for a `database` entity kind the computation reads the target database's property catalog (key, type, select option keys) in a short read transaction before the call and gives it to the model; for `pageContent` the model's `target` page id is validated by `assertValidProposalEnvelope` afterwards, and page candidates only arrive with the context of #1987, so until then a page proposal usually ends as `needsClarification` through the existing validation path.

Decision: item text is user data. It is sent in the user message between explicit delimiters and the system instruction says to treat it as data only, never as instructions. The request carries no secrets.

Decision: failures are not handled here. An `AiGatewayFailedError` or any other error propagates, so the job fails and retries as it does today; recording the failure on the card is #1485.

### Requirement gh-1415: [choke-point-hooks 01/04] Thread the writer kind into item and relation writes

#### Context

Model tier rationale: One additive value threaded through known write seams (gateway, application service, item and relation write functions, hook contexts) with existing fixtures, but it must be derived server-side only and cover several internal callers correctly.

Hooks and domain rules need to know who made a write: a person, an agent acting for a person, or the system itself. Examples are telling a manual change of a field from one Semp made, letting a write from a link's source keep the link, approving a change that only Semp may make, and per-database grants for agents. Today this is not available. `createItemWithClient` and `updateItemWithClient` (`backend/packages/data/src/chokePoint/itemWrites.ts`) take only `actingUserId` and `humanWriterUserId`; the latter is set for a human REST session and absent for an agent, `/mcp`, the system and internal callers alike. The `Actor` type (`user | ai_agent | system`) in `chokePoint/authorization.ts` reaches only view writes. Above the choke point, `AuthenticatedActor` (`backend/packages/shared/src/genericOperations/actor.ts`) already carries `userId`, `runId`, `agentProjectItemId` and `restSession`, but `putRelation` and `deleteRelation` in `backend/packages/application/src/genericApplicationService.ts` drop the actor entirely, and item delete and restore pass only the user id. Relation writes carry only `SystemRelationWriteContext` for system-owned properties (`chokePoint/relationEdgeContext.ts`).

This issue adds one additive value, `writerKind`, to all of those paths and to the context of every hook. It builds on nothing. It is the foundation for #1516, #1593, #1713, #1810, #1519, #1802, #1757, #1840, and for the hook issues #1530 and #1601, which always pass it on.

Decisions:
- `writerKind` is `'user' | 'agent' | 'system'`, with optional `agentRunId` and `agentProjectItemId` when it is `'agent'`, and `onBehalfOfUserId` (the user whose session or run made the write) on every `'agent'` value. When a caller supplies nothing the value is `'system'`, the conservative default for internal code.
- A write through `/mcp` with a human session (no run credential) is an `'agent'` write (an MCP client) without `agentRunId` and `agentProjectItemId`, bound to the session's user through `onBehalfOfUserId`. Decided by the product owner: everything written through `/mcp` is written by a tool, and an audit of what Semp or an agent changed must not hide it. Only a human REST session is `'user'`.
- An `'agent'` value without `agentRunId` therefore means an MCP client on a human session. A consumer that needs a run (an approval request, a per-project grant) checks `agentRunId` / `agentProjectItemId`, not `writerKind` alone; this issue changes no approval or grant behavior.
- Confirming an Inbox proposal (`confirmProposalWithClient`) writes as `'user'` for every write in that transaction. An approved agent operation run by the `approvalExecute` job writes as `'agent'` with the approval request's `agentRunId`.
- Hooks already receive `humanWriterUserId`; it stays as it is. `writerKind` is added next to it, not instead of it.
- The item delete and restore entry points accept `writerKind` now, so #1601 can pass it to its hooks without changing signatures again.
- Transform context (#1422): add `writerKind` to it only if that issue has already landed.

### Requirement gh-1426: [inbox-proposals 03/19] Accept and validate relations in database proposal envelopes

#### Context

Model tier rationale: One additive envelope field plus one validation helper over existing relation seams and fixtures; no new lifecycle, but it is the shared validator several later issues depend on, so the error contract must be exact.

Almost every Inbox card sets relations: a task's project and area, a person's company, an area's projects, a page's host, with an explicit "none" choice that means no edge. Today a proposal envelope is `{ entityKind, target, properties }` (`proposalEnvelopeSchema` in `backend/packages/data/src/inbox/inboxTickAction.ts`), a `z.object` that silently drops any other key when the stored value is parsed, and `assertValidProposalEnvelope` rejects relation, rollup and system-owned properties inside `properties`. So a computed relation could not even be stored. `assertRelationCreatableWithClient` (`backend/packages/data/src/chokePoint/relationOps.ts`) validates an edge but requires an existing caller item, which a proposed item does not have yet. Nothing evaluates a target's state (a project that is archived or deleted), and cardinality is only enforced by the database trigger when the edge is written.

This issue lets a `database` envelope carry relations and validates them at the points where the envelope is built or changed. Writing them on confirm is #1476; derived relations are rejected by #1991; later work computes (#1488), edits (#1920), lists options for (#1959) and invalidates (#1916) relations using what is built here.

Decision: the envelope gets an optional `relations: { [relationPropertyKey]: string[] }` next to `properties` (item ids of the targets; an empty array means no edge). The key is the relation property key on the target database. A stored envelope keeps its `relations` when parsed.

Decision: a new helper `assertRelationTargetLinkableWithClient(client, { relationPropertyId, targetItemId })` in `relationOps.ts` checks everything that can be checked without the caller item: the target exists in the relation's other database and is not deleted (`deleted_at`), neither database is archived, the relation property is writable by the user (`owner_violation`), the edge-metadata hooks pass, and a preliminary cardinality check (the target already has an edge where the relation is one-to-one or the target is the "many" side of a one-to-many). Errors are `ValidationError`s (cardinality: `CardinalityViolationError`) with `details: { field: <relation key>, code }`, where `code` is `targetDeleted` for a deleted target and `targetArchived` for a project whose `status` is `archived`. A project with status `done` is not blocked: it is a valid relation target (decided by the product owner; for example a late invoice). Cardinality at write time stays the database trigger's job; the pre-check only reports. Turning a conflict on the "one" side into a move is the multi-step proposal's update step, not an error to hide here.

4. Make sure the three producers of envelopes pass through it: the tick's write phase, `reviseProposalWithClient` and (through the same function) the edit route, without any extra code in those callers beyond type changes.
5. Tests: stored `relations` survive a parse; a deleted target gives 400 with `field` and `code: "targetDeleted"`; an archived project gives `targetArchived`; a nonexistent id gives 400 with the relation key as `field`; a one-to-one target that already has an edge is reported as a cardinality violation; an empty array is accepted; `relations` on a `pageContent` envelope is rejected; another tenant's item id is treated as nonexistent.

### Requirement gh-1403: [links 01/12] Store value links and expose them on items

#### Context

Model tier rationale: This adds a new tenant-scoped table with row-level security and composite tenant keys and a batched read path shared by three operations, so a tenant-isolation hole or a per-row query pattern is easy to introduce and expensive to find later.

A value on an item can be one of three kinds: the user's own, inherited from a source item, or (set up in a later issue) derived. Today nothing records that. `items.properties` holds plain jsonb values, and the values that a matrix of relations would naturally copy (a file's project, a file's company, an event's people) are plain edges in `item_relations` whose `metadata` says nothing about where the edge came from. No read path (`item.get`, `database.query`, `view.query`) can tell a client whether a value was set by a person or taken over from another item, so no client can show "inherited from task Send the invoice".

This issue lays the storage and the read side only. It adds two tenant tables and an additive `links` field on item reads. Nothing writes a link row in production code yet; rows exist only through test fixtures until #1593 (creation and propagation) lands. #1516 makes user and agent writes end a link, #1656 cleans up when a source is deleted, and #1595 adds the derived kind to the same `links` shape. Later inheritance rules (a thread inheriting from its sender, attachments inheriting from a thread or task, and similar) register only their own rules on top of this model.

Decisions:

- A link covers the whole value of one property on one item (the full set of related items for a relation property), never a single related item. This is why the unique key is `(tenant_id, item_id, property_key)`.
- A link is stored beside the value, not in the edge's `metadata`, because its state must survive the edge being replaced or removed.
- No row means the value is the user's own. A row with state `on` reads as `inherited`; state `broken` reads as `inheritedBroken`.
- `links` is opt-in through `include=links`, so existing callers and list queries pay nothing.

A CHECK ties the columns together: state `on` requires `broken_by` and `broken_at` to be NULL, state `broken` requires both to be set. `UNIQUE (tenant_id, item_id, property_key)` and `UNIQUE (tenant_id, id)` (the target of the composite key below).
