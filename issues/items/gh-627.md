## Behavior specification (approved)

Close the verified holes in login throttling, approval attribution, password reset, push subscriptions and error/route hygiene in `backend/packages/data/src/auth/`, `backend/packages/data/src/push/` and `backend/services/semprec-api/src/`. After this batch: a failed login is recorded and throttled through HTTP, keyed on the real client address behind Caddy; an approval decision is attributed to the session that made it and its response carries no argument values; a reset password is at least 8 characters and the reset mail no longer delays the response; a web-push endpoint is an `https` URL to a DNS-named host and a registration cannot be taken over by another account; every authenticated route is in the route matrix; a malformed path id is a 400, not a 500; no bespoke handler forwards nested error details; `POST /mcp` never authenticates a cookie; an aborted blob download releases its file descriptor. Nothing here introduces per-user authorization — this batch fixes what is wrong even with one user.

## Decisions

- How to persist a failed login attempt that the login transaction rolls back? → `login` takes a `Pool`, records failures on it (auto-commit) and wraps only the success path in its own `withTransaction`, mirroring `requestPasswordReset`. → Same guarantee as a discriminated result, but every existing caller already passes a `Pool`, so no call-site churn.
- Which address keys the lockout behind Caddy? → The last `X-Forwarded-For` hop, only when `TRUST_PROXY=1`; streak stays per `(email, ip)` with no per-email aggregate lock. → The proxy appends the peer it saw, so the last hop is the only trustworthy one; a per-email lock would recreate the owner-lockout the fix removes.
- Where is the client-address helper applied? → `POST /api/auth/login` only. → The password-reset request and setup routes consume no address today; address-keyed throttling there is a new mechanism (setup-token limiting is explicitly outside this batch).
- What does a malformed path id return? → `400 validation_failed` with `details: { field }`, not 404. → Matches the two transcription routes that already validate and the review rule for values Postgres would reject; `not_found` keeps meaning "well-formed id, no such row".
- How is "no bespoke handler forwards nested details" tested per handler? → One `toPublicErrorBody` projection unit-tested once, plus a source-scanning unit test asserting no handler file contains `err.details`. → No HTTP path can inject a nested-details error today; the scan is the regression guard.
- Which error does a cross-user push registration collision raise? → `ConflictError` (409, code `version_conflict`) with `details.field`. → It is the adapter's one 409 code in the closed enum; a new code would touch `errorContract.ts` and serialise the batch for a label.
- Which push endpoint hosts are rejected? → Any IP literal (plus `localhost`/`*.localhost`), not a private-range table. → Real push services are DNS names; one rule closes every loopback/private/link-local/mapped range without maintenance. DNS rebinding is documented as not covered.
- Does the PATCH approval response drop `payload`? → Yes; it returns a projection with `safeSummary` instead. → The only client (`web/src/api/approvalQueueOperations.ts`) parses `id`/`status`/`decidedAt`/`decidedBy` only, so nothing deployed reads `payload`; the body field `decidedByUserId` is ignored, not rejected, until the web epic removes it.
- Does `login()` on a bare pool weaken the lockout pre-check guard? → Accepted: the streak read and the failure insert are throttling signals, not a state write the check protects; the session insert and the success record still share one transaction.

## Out of scope

- Per-user authorization of data routes (multi-tenant batch), self-signup/invitations, sliding session renewal, a session-listing route, CSRF tokens / `Origin` checks, setup-token brute-force limiting, unifying the two top-level error shapes.
- Removing `decidedByUserId` and `?user=` from the web client (web epic).
- Address-keyed throttling for password-reset requests or `POST /api/setup`.
- A queue-backed, retried password-reset mail; a private-IP range table or DNS-resolution checks for push endpoints; automatic transfer of push registrations between accounts.
