**Blocked by:** #1684, #1885
**Model tier:** medium

## Context

Model tier rationale: A batched read-side resolver over an existing resolver pattern and message-history endpoint, with one query per kind and the existing fixtures; it adds no write path and no new authorization contract.

A Semp reply stores the list of items it changed (#1885). The chat shows each as a card with a label and current state, and a conversation history can hold many replies, so loading the history must not cost a request per card. Today the history endpoint of #1543 returns the stored messages, and #1684 adds the batched resolution of message references (label, database, trashed state) to it. This issue gives the stored changes the same batched resolution in the same response.

Decision: a changed-item card opens the object. Each card in the response therefore carries the `itemId` and `databaseId` of the changed item as part of the contract (an additive change of the history response), next to what is needed to display it; the client opens the object from these two ids. The navigation itself is client work.

Decision: the resolver of #1684 is reused, not a new one and not `GET /api/items/:id` per card.

## Task

Load `testing`, `io-hardening` and `canonical-keys`.

1. In the message history response of #1543 (the handler and the message mapper it introduced; confirm the file names against that PR, expected `backend/services/semprec-api/src/sempMessagesHandler.ts`), add to each assistant message that has stored `changes` a `changes` array of `{ itemId, databaseId, change, changedKeys, before?, proposalId?, resolved }`, where `resolved` is `{ label, databaseKey, state, values }`:
   - `state` is `active`, `trashed` or `purged`;
   - `values` is the current value of each key in `changedKeys` (so a card after a later change shows the current value, while `before` stays the stored value);
   - `label` and `databaseKey` come from the same resolver and the same rules as #1684.
2. Resolve all changes of all messages in the returned page with one batched lookup per kind (items by id in one query, databases in one query), never per card.
3. An item in a sensitive database resolves with `label` and `state` only and no `values`. An item the viewer is not allowed to read resolves as `purged`-equivalent with no label, the same as the reference resolver does for a missing target.
4. Tests: every card carries the `itemId` and `databaseId` stored for the change; a moved task shows its stored `before` and its current value after a later edit; a history of 20 cards is served with a constant number of queries (assert the query count); a trashed item has `state` `trashed`; a purged item has `state` `purged`; a message without changes has no `changes` key.

## Scope

### In scope

- Resolving stored changes into display data in message history, batched.

### Out of scope

- Storing changes (#1885).
- The client navigation from a card to the object (the client uses `itemId` and `databaseId` from this response).
- Resolving message references (#1684 owns the shared resolver; this issue only reuses it).

## Acceptance criteria

- When a task was moved by a reply and edited again later, then the card carries the stored previous value in `before` and the current value in `resolved.values`.
- When a history with 20 changed-item cards is loaded, then a single GET returns all of them and the number of database queries does not depend on the number of cards.
- When a changed item was deleted afterwards, then its card has `state` `trashed`.
- When a reply asked for a delete that is still pending approval, then its history has no change card for it.
- When a reply changed an item, then its card carries the `itemId` and `databaseId` of that item, so the client can open the object from the card; this holds for every `state`, including `trashed` and `purged`.
