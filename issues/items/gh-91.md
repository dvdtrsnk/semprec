**Blocked by:** #222, #221, #90, #115, #175

## Context

The repository defines `CORE_CRONTAB`, task handlers, queue registration, and future worker/service topology, but no concrete long-lived composition root calls graphile-worker `run()`. Without one, heartbeat sweeps, rollups, migrations, compaction, cleanup, library processing, and mail safety-net jobs never execute in a deployed system. #221 declared queue affinity and the exhaustive API/agents handler sets; #222 split heartbeat firing along that affinity. This issue delivers the two long-lived composition roots that consume those sets, with exactly one crontab owner, clean lifecycle, and deployment ownership.

## Task

Create two affinity-safe graphile-worker composition roots over the same queue, with exactly one crontab owner. `services/semprec-api/src/queueRuntime.ts` installs `CORE_CRONTAB` (including the `0 4 * * * trashPurge` line from #221) and hosts the API handler set of #221: API/data handlers plus module handlers with `queueAffinity: 'api'`. `services/semprec-agents/src/queueRuntime.ts` passes no crontab and hosts the agents handler set of #221: `heartbeatFireAgent`, `agentRun`, `delegatedAgentRun`, plus module handlers with `queueAffinity: 'agents'`. Both receive their process-owned injected pool, run queue migrations idempotently, call `run()` once, and own only their returned Runner; idempotent `stop()` awaits `runner.stop()` and never closes the pool. Each service root stops intake, its runner, then its pool on SIGTERM/SIGINT. Only API installs `CORE_CRONTAB`; agents never installs cron, so this is two consumers but one scheduler.

ModuleRegistry rejects an active handler missing from its selected runner. Before either service reports readiness, the shared registry validation of #221 proves every active descriptor belongs to exactly one runner, and startup fails with an actionable error on missing, duplicate, or invalid-affinity handlers. Adjust the deployment/systemd service definitions so each of the two owning services starts its own queue runtime and no other unit runs a worker.

Integration tests boot both compositions against ephemeral PostgreSQL, use a test API crontab cadence to observe one heartbeat sweep, enqueue one API module task, one agents module task, one deterministic heartbeat and one agent heartbeat, and prove each executes only in its owning runner. They assert one runner per service, exactly one crontab installation, legacy-job migration without duplication (the #222 migration running at API install), startup failure for duplicate/missing/invalid-affinity handlers, and idempotent shutdown/pool ownership. Startup validation and integration tests enqueue `approvalExecute`/`notificationFanout` and run the trash cadence, proving all inherited core tasks have exactly one owner.

## Scope

### In scope

- Two affinity-safe queue composition roots, merged handler registration, single crontab installation, lifecycle, readiness validation, deployment ownership, and tests.

### Out of scope

- Descriptor `queueAffinity`, catalogs, and ModuleRegistry affinity validation, delivered by #221.
- The `heartbeatFire` split and legacy job migration, delivered by #222.
- New task business logic, a second crontab/scheduler, or in-process `setInterval`.
- General systemd provisioning beyond adjusting the service definition needed to start the selected owner.

## Acceptance criteria

- API and agents each call graphile-worker `run()` once; API alone supplies `CORE_CRONTAB`.
- Core cron/API module tasks execute only in API, while agent heartbeat/run and agents-affinity module tasks execute only in agents.
- Missing or duplicate task handlers stop startup with an actionable error.
- Unknown/missing affinity, cross-affinity duplicate, legacy-job duplication, or an unowned active handler stops startup/migration with an actionable error.
- Graceful shutdown leaves no abandoned runner or open owned connection in either service.
- `approvalExecute`, `notificationFanout`, and the `trashPurge` cron cadence execute only in API.
