**Model tier:** high

## Context

Model tier rationale: This changes the agent-run launch path across the API-side scheduler, the agents runtime and a per-tenant heartbeat cutover, so a mistake either starts runs for unwanted mail or silently stops them.

The `newEmail` heartbeat (`seed/seedEmailModule.ts`) fires `core.agentRun` for each new Inbox message, with the static task "A new message arrived in the Inbox." `coreAgentRunAction` in `backend/packages/data/src/scheduler/actions.ts` passes `runAgent` only `{ agentRunId, projectItemId, task }`, so the run does not know which message triggered it, and the only gate is `itemRelationFilter` (Inbox, not Junk or Trash). `core.agentRun` is the only action routed to `heartbeatFireAgent` in `semprec-agents` (`resolveHeartbeatFireTaskName`), where `createRunAgentForHeartbeats` in `services/semprec-agents/src/agentRunTasks.ts` starts the session. Drafting replies (#1941) needs the message identity and must not start for unknown senders, bulk mail (#1502) or the user's own mail.

Decision: the gate is generic in style (an optional `actionConfig` key parsed beside `itemRelationFilter`), evaluates only for item-triggered heartbeats, and fails closed when the message has no metadata.

Shared-file ordering: this issue also waits for #1549 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `io-hardening`, `db-migrations` and `testing`.

1. Extend `RunAgentFn` input with optional `itemId`; `coreAgentRunAction` passes `context.itemId` through and appends the line `Triggering item id: <id>` to the task of an item-triggered run. `createRunAgentForHeartbeats` and the run record keep it so the session sees the same task. Time-based heartbeats are unchanged.
2. Add `scheduler/senderKnownFilter.ts` with `parseSenderKnownFilterConfig(actionConfig.senderKnownFilter)` and `passesSenderKnownFilter(pool, itemId, config)`, applied in `coreAgentRunAction` after `itemRelationFilter`. The message passes only when its `mail_message_meta` envelope sender address is in `person_email_index` (`mail/personEmailIndexStore.ts`), `is_bulk` is false, and the address is not one of the tenant's own mailbox addresses (`Mailboxes.addresses`).
3. Seed: add `senderKnownFilter: {}` (presence enables it) to the `newEmail` heartbeat's action config in `seed/seedEmailModule.ts`.
4. Existing tenants: `mail/newEmailSenderFilterCutoverMigration.ts` exporting `runNewEmailSenderFilterCutoverMigration(pool)`, registered in `db/tenantCutoverMigrations.ts`: it adds the key to the existing `newEmail` heartbeat's action config when missing, and does nothing on a fresh install or a second run (pattern: `transcription/transcriptionRequeueHeartbeatCutoverMigration.ts`).

## Scope

### In scope

- Passing the triggering item to the run and task, the sender-known gate, and the seed and cutover of the `newEmail` heartbeat.

### Out of scope

- Detecting bulk mail (#1502).
- Choosing the thread's project for the run, deciding that an answer is expected, and writing the draft (#1941).
- Approval for sending (#1913).

## Acceptance criteria

- A message from an address that belongs to a person starts a run whose task contains the message's item id; the same message with `is_bulk` true, from an unknown address, or from the tenant's own address starts no run.
- A time-based heartbeat run is unaffected.
- After the cutover the existing `newEmail` heartbeat has the filter; running the cutover twice, or on a fresh install, changes nothing.
