**Blocked by:** #25

## Context

Section 6 of the specification (`vize/backend.html`, lines 2073–2654) covers the email module. The mock (`mock.html`) already has the static data skeleton — the DB **Mailboxes** (1 row = 1 connected IMAP account), **Folders** (folders and labels across accounts, with a `behavior` field distinguishing the IMAP model from the Gmail model, and `special purpose` as a stable semantic key independent of how the folder happens to be named), and **Emails** (a mirror of messages, a reading view like a mail client rather than a generic table) — but no real sync engine, no conversation threading, no secure credential storage, and no reliable attachment handling. This issue covers **only the sync core** of that section: how messages actually move between the real mailbox and our DB and back, how changes are detected, how state conflicts are resolved, and which concrete tables back all of that. Mailbox UI, sending, drafts, and heartbeats over email are the content of the follow-up issue #27 over the same section.

## Task

Build a bidirectional sync engine between a real email mailbox (Gmail, Outlook/M365, iCloud, generic IMAP) and our DB, where **the mailbox on the provider's server is the source of truth, not our DB** — we are just another client of the same mailbox, not a detached copy. This includes:

- three sync adapters (Gmail API, Microsoft Graph, IMAP) over one shared target schema,
- detection and resolution of state conflicts (invalid history/UIDVALIDITY, missed notifications, concurrent writes),
- reconstruction of conversation threads from message headers,
- deterministic linking of senders/recipients to the People DB,
- secure handling of credentials (reversible encryption, not hashing),
- reliable, memory-safe attachment processing,
- HTML body sanitization and full-text search over message content.

## Scope

### In scope

**Provider strategy and account sync state**

- The original plan (uniform plain IMAP across all four providers) turned out to be the worse choice specifically where it matters most: bidirectional flag sync. Gmail does not support QRESYNC at all (only CONDSTORE), so the one-round-trip resync QRESYNC promises never happens on Gmail. IMAP IDLE on Gmail is documented (independently, by Mimestream and Gmail's own native client) to have *higher* latency than Gmail API push, not just lower reliability — and silently dying connections (no error, no timeout) are a common, documented failure mode across client libraries. Both native APIs instead have a purpose-built mechanism for exactly this problem: Gmail `historyId` + `history.list` returns new messages *and* label changes since the last known position in one call; Microsoft Graph `/messages/delta` does the same via `deltaLink`. Plain IMAP has to assemble the same thing from two unreliably-supported extensions.
- Decision: **three sync adapters over one target schema** — a Mailbox gets a `sync_mode` (`gmail_api` / `graph_api` / `imap`), defaulted by `provider` (Gmail → gmail_api, Outlook → graph_api, iCloud/generic → imap), but manually switchable (the same flexibility EmailEngine offers per account). All three adapters write to the same tables (Emails, Folders, `mail_message_meta`) — they differ only in *how* they detect changes and *how* they write them back, not in the target data model.
- Table:
  ```sql
  CREATE TABLE mail_account_sync_state (
    item_id uuid PRIMARY KEY REFERENCES items(id) ON DELETE CASCADE,  -- row in Mailboxes
    sync_mode text NOT NULL,               -- 'imap' | 'gmail_api' | 'graph_api'
    gmail_history_id text,                 -- gmail_api only; history isn't kept forever, full resync is a normal path
    gmail_watch_expires_at timestamptz,    -- watch() is valid 7 days, renew daily
    graph_subscription_id text,            -- graph_api only
    graph_subscription_expires_at timestamptz,  -- max ~7 days (lightweight notifications), 24h for enriched
    last_error text,                       -- most recently captured sync error (see historyId invalidation below)
    last_activity_at timestamptz,          -- last completed sync cycle / IDLE renewal
    next_expected_activity_at timestamptz  -- when this specific adapter itself expects its next activity; progress is watched by observability.checkSystem (issue #39, mail_sync_stalled)
  );
  ```
- `last_activity_at` alone carries a different meaning per adapter — IMAP IDLE renews every few minutes, a Gmail `watch()` is valid 7 days and is renewed daily, a Graph subscription lasts 24 hours to 7 days depending on type — and a single flat "older than X" threshold over that value would either raise false alarms for IMAP (legitimately quiet between IDLE renewals) or catch an expired Gmail/Graph watch too late (silence is fine for days until the watch expires). That is why each account instead maintains `next_expected_activity_at`: after every completed sync cycle, IDLE renewal, or watch/subscription extension, the adapter computes and writes down **by when** it itself expects its next activity, derived from its own liveness semantics — IMAP: the end of the next reconcile window; Gmail: `gmail_watch_expires_at` minus a safety margin for the daily renewal; Graph: the same over `graph_subscription_expires_at`. The observability check (issue #39) then consumes a single uniform predicate — `next_expected_activity_at < now()` — and never needs to know the difference between IDLE, historyId, and deltaLink internally.
- The extra cost is real but one-time and bounded: Gmail requires OAuth verification for a sensitive scope (`gmail.labels` for writing labels without full `gmail.modify`); Graph requires either a publicly reachable HTTPS endpoint for its webhook (must respond within 3s with a validation token), or falls back to plain polling of `/messages/delta` without push notifications. At the time this paragraph was written, a self-hosted deployment without a public domain/TLS couldn't use the webhook — issue #40's Caddy setup has since given the server its own public domain with TLS, so the webhook is today the real, default path; the Caddy configuration itself is designed in issue #40 — the webhook is just an ordinary route on that one public domain, the proxy only terminates TLS for it. Gmail, on the other hand, supports Pub/Sub *pull* subscriptions — no public endpoint is needed at all, which is an advantage for self-hosted deployment regardless of TLS status. Neither API push is guaranteed delivery (Pub/Sub is at-least-once, Graph has its own "missed" lifecycle event) — reconcile as a safety net remains necessary regardless of transport, it just runs over a more resilient primitive (`historyId`/`deltaLink`) than IMAP UIDVALIDITY/MODSEQ.
- Detecting an invalid `gmail_history_id`: Gmail's `history.list` returns `404` (history older than what the API retains) when the stored `historyId` is too old — the worker treats this as a specific, expected state, not a generic error. Reaction: clear `gmail_history_id` (back to `NULL`), write the reason to `mail_account_sync_state.last_error`, and run the same path as the initial sync (a full download of `All Mail`, not incremental) — `historyId` is set again from the response once that completes. Graph's `deltaLink` has an analogous error (`410 Gone`/`resyncRequired`) with the same reaction.

**IMAP adapter (iCloud, generic accounts, and Gmail/Outlook in fallback mode)**

- Every IMAP folder carries `UIDVALIDITY` and `UIDNEXT` — a UID is unique only within the pair (folder, UIDVALIDITY), never alone. New messages: `UID FETCH <old UIDNEXT>:*`. If `UIDVALIDITY` changes between runs, the entire UID cache for that folder is invalid — the server is saying "the folder was rebuilt," and reconcile must run again keyed by `Message-ID`, not by blind re-insert (otherwise duplicates).
- CONDSTORE/QRESYNC (RFC 7162) — `MODSEQ` per message, `HIGHESTMODSEQ` per folder; `UID FETCH ... CHANGEDSINCE <modseq> (FLAGS)` returns only changed flags, `SELECT ... QRESYNC (...)` additionally returns `VANISHED` (deleted UIDs) in one round trip. Not all servers support this (check via `CAPABILITY`) — generic IMAP without CONDSTORE falls back to a full reconcile.
- On servers without CONDSTORE (the `highestmodseq` column below is `NULL`), `VANISHED` is unavailable, so deletions are detected by diff: a full `UID FETCH 1:* (UID)` returns the complete current UID list for the folder, and any locally stored UID that doesn't appear in it is deleted (moved away or removed) — reconcile then marks the corresponding row/edge as deleted the same way it would for a `VANISHED` response.
- Table:
  ```sql
  CREATE TABLE mail_folder_sync_state (
    item_id uuid PRIMARY KEY REFERENCES items(id) ON DELETE CASCADE,  -- row in Folders
    uidvalidity bigint,
    uidnext bigint,
    highestmodseq bigint,             -- NULL = server doesn't support CONDSTORE, falls back to full reconcile
    last_full_reconcile_at timestamptz,
    last_error text
  );
  ```
- IDLE (RFC 2177) holds a connection open and lets the server push changes for exactly one selected folder — it must be renewed at least every 29 minutes, providers support it with varying reliability, and notifications are occasionally simply lost (dropped connection, missing FETCH notice). IDLE is therefore not the only mechanism, just a low-latency trigger: the real source of truth is a periodic full QRESYNC reconcile (typically every 15–60 minutes), and IDLE just triggers it earlier when a push arrives. Gmail limits an account to ~15 concurrent IMAP connections — IDLE is therefore only used on Inbox/All Mail, other folders are polled instead of watched individually.
- This is also the answer to "live propagation from web to the iOS app" and to propagating changes into the **real mailbox** (iCloud Mail/another IMAP client) at the same time: our DB is not the source of truth, the IMAP mailbox is. Our UI/iOS app sync with each other over our own WS server from issue #38 (protocol and resume defined there; LISTEN/NOTIFY on changes in `items`), but that change originated from the sync worker writing to our DB after a `STORE`/`FETCH` against IMAP. Conversely: when a user marks a message read in our UI, the worker issues `UID STORE <uid> +FLAGS.SILENT (\Seen)` against the real mailbox — and because Mail.app is also just an IMAP client of the same mailbox, it sees that change on its own next sync/IDLE cycle entirely on its own, with no direct integration from our side. The Gmail/Graph adapters follow exactly the same principle, just via `users.messages.modify`/Graph `PATCH` instead of IMAP `STORE` — and because it's the account's own official API, it's if anything more direct than IMAP.

**Gmail in IMAP fallback mode**

- This applies only when a Mailbox is explicitly switched to `sync_mode = 'imap'` instead of the default `gmail_api` — in `gmail_api` mode this whole problem doesn't exist, because the Gmail API returns `labelIds` directly on the message, with no UID or "which IMAP folder" concept at all. For completeness, why a naive IMAP sync would fail on Gmail: Gmail doesn't actually store mail in folders — it stores each message once, and IMAP "folders" are a view over labels (exactly what the mock's `behavior` field distinguishes as Folder/IMAP vs. Label/Gmail). The same message with the same content appears with a *different UID* in Inbox and in every label it has — tracking these "folders" separately would clone every multi-label message.
- Fallback-mode solution: sync only `[Gmail]/All Mail` (the `\All` special-use attribute, RFC 6154) as the canonical source, and derive Folder/label membership from `X-GM-LABELS`. Dedup runs on `X-GM-MSGID`, not UID. For iCloud/generic IMAP (the actual default target for this adapter) this whole layer is moot — a message there always lives in exactly one folder.

**Per-folder UID lives on the relationship edge, not on the message**

- The mock already has `emails.folder` as a `relation multi:true` (one message → many Folders at once) — essentially the JMAP model, where `mailboxIds` is a set, not a single parent. The IMAP adapter additionally needs the actual IMAP UID for each such edge (which UID this message has in which folder), to be able to target `STORE`/`FETCH`. Rather than a new join table, this reuses the generic `item_relations.metadata jsonb` field from the schema in issue #21 (the same field issue #25 uses for scoring/ratings on a relationship): the Emails↔Folders edge carries `{ uid: 88213 }`. No new table, just a second use of the same generic field.
- Gmail API and Graph adapters don't need this at all — the Gmail API returns `labelIds` directly on the message (no per-edge position to address), and Graph addresses a message by its own global `id` regardless of which folder it's currently in. Both API adapters instead store their own message ID directly in `mail_message_meta.provider_message_id` — simpler than the IMAP case, not more complicated.
- After a `UIDVALIDITY` change, the old `{ uid: ... }` metadata on that folder's edges is invalid — it doesn't belong to any current message, because the server restarted the UID space from scratch. This is handled by the same reconcile pass that a `UIDVALIDITY` change already forces: for the affected folder, all existing Emails↔Folders edges with metadata from the old validity are dropped/ignored and rebuilt from scratch by matching against the freshly downloaded UID list by `Message-ID` — no separate cleanup step needed, it's a natural consequence of the full reconcile by Message-ID overwriting the edge along with its metadata.

**Conversation threads**

- The mock doesn't handle this at all — a reply is today a new, isolated row in Emails, with no link to the original. A real thread is reconstructed from the RFC 5322 headers `Message-ID`, `In-Reply-To`, and `References` (the accumulated ancestor chain) — the de facto standard is the JWZ algorithm (jwz.org/doc/threading.html): a hash table keyed by `Message-ID`, where a missing ancestor (referenced but not yet delivered/synced) gets a temporary "dummy" container that is filled in once that message arrives — the thread self-heals rather than staying broken forever. Gmail additionally computes its own `X-GM-THRID` (a heuristic based on subject and participants, not exact header matching) — but it only exists for Gmail accounts, so a universal (Gmail + iCloud + generic IMAP) system must use References-based threading as the real mechanism; `X-GM-THRID` is stored only as an auxiliary column for cross-checking on Gmail accounts.
- Tables:
  ```sql
  CREATE TABLE mail_threads (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    subject_hint text                 -- debug/UI only, not the threading key
  );

  CREATE TABLE mail_message_meta (
    item_id uuid PRIMARY KEY REFERENCES items(id) ON DELETE CASCADE,   -- row in Emails
    message_id text NOT NULL UNIQUE,  -- RFC 5322 Message-ID, global dedup key
    in_reply_to text,
    "references" text[],              -- ancestor chain, order preserved
    thread_id uuid REFERENCES mail_threads(id),   -- NULL until the thread is resolved
    provider_thread_id text,          -- X-GM-THRID, Gmail only, auxiliary hint only
    provider_message_id text,         -- Gmail API/Graph API's own message ID; NULL in plain IMAP mode
    envelope jsonb NOT NULL DEFAULT '{}'   -- {from, to:[], cc:[], bcc:[]} structured, see below
  );

  CREATE UNIQUE INDEX mail_message_meta_provider_msg_uq
    ON mail_message_meta (provider_message_id) WHERE provider_message_id IS NOT NULL;
  ```
- Our own outgoing messages (a reply from our UI/AI) must correctly generate a `Message-ID` (our domain), set `In-Reply-To` to the original's `Message-ID`, and `References` to the original's chain plus its `Message-ID` — otherwise the reply won't be threaded correctly, either in Gmail/Mail.app or in our own reconstruction. An optimistic insert (user clicks Send, the row appears immediately, before the next IMAP sync) is deduplicated by `UNIQUE(message_id)` itself — when the sync worker later confirms the same `Message-ID` in Sent, it's an `UPSERT` into the same row (filling in the real IMAP UID on the edge, as above), not a new duplicate entry. The Gmail/Graph adapters get the same role from the partial unique index on `provider_message_id` (above) — a concurrent insert from two overlapping sync runs (e.g. two pages of `history.list` processed in parallel) hits a conflict instead of producing two rows; ingest reacts with `ON CONFLICT (provider_message_id) DO NOTHING`, the first write wins, the second is a no-op.
- `envelope` replaces the mock's `sender`/`recipients` as the structured source of truth (`{ from:{name,address}, to:[...], cc:[...], bcc:[...] }`) — without it, AI can neither "reply all" correctly nor reliably determine who a message actually went to. The `sender`/`recipients` properties in Emails remain as derived display texts (`owner: system`, the same pattern as `time` on Tasks) — the table and the reading view keep showing them as plain text, it's just no longer generated by hand.

**Linking to People by address**

- The mock can't do this today, and it's clear why: the People DB has no property that could hold an email address at all — `contact` is just a select with two icons (call/email), a preferred channel, not a value. In the sample data this shows: "Tomáš Dvořák" is a row in People and a message from `tomas@priklad.example` exists in Emails, but nothing in the mock ties the two together.
- New property **People.emails** (a list of email addresses, `owner: user` — the person themselves confirms which addresses belong to them, no silent machine-added entries). Both this property and the `person_email_index` table below are **created by this issue** — this issue is their sole owner; issue #24's baseline People database does not include them. A person can have multiple addresses (work/personal), hence a list rather than a single value — the same reason the "Custom Domain" Mailbox has an `addresses` field for aliases alongside its main address.
- Table:
  ```sql
  CREATE TABLE person_email_index (
    email text PRIMARY KEY,     -- normalized: lowercase, trimmed
    item_id uuid NOT NULL REFERENCES items(id) ON DELETE CASCADE   -- row in People
  );
  ```
- A reverse index, maintained by the application's write path when `People.emails` changes — the same pattern as the full-text index (application layer, not a DB trigger). `email PRIMARY KEY` isn't just an optimization — it's an **enforced guarantee** that one address never belongs to two different people at once: an attempt to write the same address onto a second People row hits a conflict at the choke point, not a silent overwrite or an ambiguous match later. Ambiguity is resolved at write time, not on every match attempt.
- The matching itself is a **deterministic heartbeat, not AI** — exactly the case where "an ordinary index lookup can compute this" means the agent/LLM layer isn't involved at all (project goal, issue #21: maximize determinism everywhere it's possible). A trigger `{ kind: 'onItemEvent', databaseId: 'emails', event: 'create' }` (the same event shape issue #21 introduced for Semprec) reads the addresses from `mail_message_meta.envelope` after a new message is written, normalizes them, and looks them up in `person_email_index`. New relations `senderPeople` (single, relation → People) and `recipientsPeople` (`multi:true`, relation → People), both `owner: system` — the same pattern as the derived `sender`/`recipients` display texts above. An unmatched address (the vast majority — spam, notifications, strangers) is not an error or an empty value to resolve, the relation simply stays unfilled.
- Deliberately deferred: retroactively matching old emails when a user *later* adds a new address to an existing person. A new address links future messages from that point forward; recomputing history is a small, separately addable extension (one `graphile-worker` backfill job, on demand), not something worth solving up front without an actual need. Creating a **new** People row for an unknown but frequently recurring address stays out of scope of this issue deliberately — that's a judgment call ("does this address deserve a contact?"), not a lookup, so it would (if ever built) go through Semprec's propose/confirm mechanism like anything else AI suggests, not through this deterministic mechanism.

**Attachments**

- A MIME message is composed of `multipart/mixed` (body + real attachments), `multipart/alternative` (plain vs. HTML variant of the same body), and `multipart/related` (HTML body + inline images linked via `Content-ID`/`cid:`, RFC 2387) — real messages typically nest these (mixed → related → alternative). The signal that distinguishes "belongs in Files" isn't the multipart type, but the combination of `Content-Disposition: attachment` (has a filename, meant to be downloaded) vs. `inline`, *together with* whether that part is referenced via `cid:` inside the HTML body — an inline part with a matching `cid:` reference is a rendering asset (a logo in a signature), not a document, and is not added to Files. MIME parsing is a solved, non-trivial problem (base64/quoted-printable encoding, nested multiparts) — an established library (e.g. `mailparser`) is used, not a hand-rolled parser.
- Table:
  ```sql
  CREATE TABLE mail_attachments (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    message_item_id uuid NOT NULL REFERENCES items(id) ON DELETE CASCADE,   -- row in Emails
    blob_id uuid NOT NULL REFERENCES blobs(id),
    filename text NOT NULL,
    content_type text NOT NULL,
    content_id text,                  -- Content-ID, only for inline referenced parts
    disposition text NOT NULL,        -- 'attachment' | 'inline'
    byte_size bigint NOT NULL
  );
  ```
- `blobs.content_hash` dedups the actual binary content — the same invoice forwarded three times is stored once; deleting a message must not delete the blob directly, only remove the reference (reference counting, not immediate physical deletion at zero references). Every attachment that passes the rule above (real, not inline-cid) gets a real row in Files — exactly like the mock already does today in `sendEmailReply` for outgoing attachments — linked through the existing `emails.attachments` relation, so it can be mentioned and shown in the Files DB like any other file.
- Large attachments: the sync worker runs over multiple mailboxes at once — pulling a large attachment entirely into memory before writing it to disk is a direct route to OOM. `imapflow` (the library chosen for this project) has a direct answer: `client.download(uid, part, opts)` returns `content` as a Node.js `ReadableStream`, not a buffer — piped through `stream/promises`' `pipeline()` (not bare `.pipe()` — a documented bug, imapflow #65, truncates the attachment when using `.pipe()` directly) into the file being written, letting Node's streams handle backpressure on their own: a full write buffer slows down reading from the socket, no manual buffering, no in-memory size ceiling. The manual fallback for edge cases is an IMAP partial fetch (`BODY[section]<start.count>`, RFC 3501 §6.4.5) — paginated, chunked reads if the library's high-level streaming fails.
- Provider limits: Gmail 25 MB (over the limit it offers a Drive link instead), Outlook/M365 typically 20–25 MB (admin-adjustable higher), iCloud Mail 20 MB normally / up to 5 GB via Mail Drop (the attachment is then sent as a download link, not a real MIME part — the sync worker must recognize this and store it as a link, not try to download a non-existent attachment). The outgoing side mirrors the same pattern: above 20 MB (a safe threshold even after ~33% base64 bloat) the file is uploaded to `blobs` and a link is inserted into the message body instead of a real MIME attachment — the same UX Gmail/iCloud already provide themselves, just on our side instead of theirs.

**Credentials**

- Reversible encryption, not hashing: hashing (bcrypt/argon2) is one-way, appropriate for verifying a user's own login (the server never needs the original password back). The sync worker, however, needs the real password/token *back*, to log in against the IMAP/SMTP server on every run — that can't be recovered from a hash. What's needed is reversible **encryption**, not a hash.
- Credentials do not live in the generic `properties` model at all — a dedicated table outside the reach of the generic read API (`owner`/`locked` from issue #21 only govern who may *write* a value, not who may *read* it; sensitive values must therefore not pass through the same path as ordinary property reads). Encryption happens at the application layer (not `pgcrypto`) — the key then never passes through an SQL parameter, where it could end up in a query log or `pg_stat_statements`. For a single-user, self-hosted server, one master key (32 bytes, root-owned `shared/.env` — outside git and outside the data backup, issue #40) plus libsodium `crypto_secretbox`/XChaCha20-Poly1305 is adequate — not Vault or a cloud KMS, which solve a multi-tenant problem we don't have.
- This mechanism isn't email-specific — issue #31 runs into the identical need for MCP servers (a token/API key to a third-party server), and anything else in the future needing reversible access to a third-party secret (future integrations like Home Assistant, third-party calendars) will run into it too. The table is therefore **generic**, not email-specific — `item_id` references any row in `items`, whether it's a Mailbox or an MCP server, because both are equally generic `items` rows (issue #21). Duplicating this shape a second time just because the consumer differs would be exactly the duplication issue #29 already named as a problem at module boundaries — one table, one encryption module, several narrow accessors over it.
- The name is deliberately **not** just `credentials` — that name would visually collide with the `users` table for logging into the Semprec UI itself (hashing, not encryption — issue #34), even though structurally they could never be confused (`item_id` here always references an `items` row, a user account has no `items` row at all). `external_credentials` removes that possible future mistake for free, just by naming.
- Tables:
  ```sql
  CREATE TABLE external_credentials (
    item_id uuid PRIMARY KEY REFERENCES items(id) ON DELETE CASCADE,   -- row in Mailboxes, MCP servers, or any future consumer
    credential_type text NOT NULL,    -- 'oauth2_refresh_token' | 'app_password' | 'plain_password' | 'api_key' | 'bearer_token'
    ciphertext bytea NOT NULL,
    nonce bytea NOT NULL,
    key_version smallint NOT NULL DEFAULT 1
  );

  CREATE TABLE credential_access_log (
    id bigserial PRIMARY KEY,
    item_id uuid NOT NULL REFERENCES items(id),
    actor_type text NOT NULL,         -- 'user' | 'sync_worker' | 'smtp_send' | 'mcp_connection_manager' | 'ai_agent'
    actor_id text,
    purpose text NOT NULL,            -- 'imap_sync' | 'smtp_send' | 'test_connection' | 'mcp_connect' | ...
    at timestamptz NOT NULL DEFAULT now()
  );
  ```
- The encryption/decryption logic itself (master key, `crypto_secretbox` calls, `key_version` handling) lives as one shared module in `packages/credentials` (issue #29 — alongside `data`/`module-registry`/`queue` as another core primitive, not tucked away inside the Email module). Only the **encryption mechanism** is shared — access points remain narrow and separated per consumer, not one general "decrypt anything" API that would itself be a wider attack target. Decryption is only allowed through a narrow accessor, never a generic serialization API — and every decryption is logged to `credential_access_log`. "Who is allowed to decrypt" and "who is allowed to attempt it" are two separate controls, not one. An AI agent never has a credential accessor as an `AgentTool` — layer 1 (allowlist, issue #29: "absence of capability, not runtime blocking") simply never includes it, same as any other internal module the agent can't call itself. The call sites in code are the mail sync worker (regular IMAP/API sync) and the SMTP-send service (actual sending) for mail, and the MCP connection manager inside `semprec-agents` (issue #31) for MCP servers — each calls the accessor directly, not through agent tooling. An agent-initiated email send (see the mailbox/sending issue #27) therefore never decrypts anything itself — it just calls `email.send`, and it's the SMTP-send service that uses the accessor internally; likewise an MCP tool invoked by an agent never decrypts anything itself, it just calls `tools/call` through the connection manager, which already has the transport open.
- Decryption frequency differs by consumer, worth stating explicitly rather than leaving implicit: the mail sync worker decrypts on every sync cycle (the OAuth access token is then derived and kept only in process memory, ~1h validity, never persisted — same pattern as above). The MCP connection manager decrypts **once**, when opening a transport to a given server, and holds the plaintext in memory for as long as the connection is alive — not on every individual `tools/call`. Without this distinction, a reader might conclude decryption happens on every tool call, which would flood `credential_access_log` for no matching security benefit (the connection itself is already open; re-decrypting the same secret protects nothing extra).
- Deliberately left simple: `item_id` is the `PRIMARY KEY`, so the table today holds only one credential per `items` row. That's sufficient for mail (one login per mailbox) and MCP (one token per server). If a future consumer (Home Assistant and similar) needs multiple independent secrets per row, widening to a composite key `(item_id, credential_type)` is a small, backward-compatible migration — exactly the kind of decision that should stay simple today and be cheap to change later, not solved up front for a hypothetical need.
- Auth also differs by provider, which the mock doesn't address at all: Gmail and Outlook both require OAuth2 — the same stored *refresh token* drives either `XOAUTH2` SASL (IMAP fallback mode) or direct bearer auth against the Gmail API/Graph (default mode, see above); both providers have disabled direct password login (Microsoft 365 since September 2024). The access token (~1h) is computed at runtime and never persisted. iCloud Mail doesn't support OAuth2 for third parties at all — it requires an App-Specific Password generated at appleid.apple.com, with no expiration but revocable at any time by the user. Revocation (the user disconnects the account in Google/Microsoft settings, or invalidates the App-Specific Password) is a normal state, not a system error — `sync_status` on a Mailbox (the mock already has this as a select) gets a new value `needs re-authorization` alongside the existing OK/Error/Never, and the worker stops retrying and just leaves it waiting on the user.

**HTML sanitization and remote images**

- Messages carry foreign, untrusted HTML content — rendering it in our UI without sanitization is classic XSS (OWASP A03). Sanitization happens at serve time (not once at ingest) via a maintained library with an allowlist — this lets the sanitizer improve over time for already-stored messages, without needing to reprocess them. Remote images (a typical carrier for tracking pixels — confirming to the sender "the message was opened") are not loaded by default, the same as Gmail/Mail.app — with an exposed "Load images" action per message.

**Full-text search**

- The mock has no full-text search at all (just a filter over the visible rows of one open table), and the generic `items`/`properties` model has no single "message text" column to build an ordinary generated `tsvector` over — text-bearing properties differ per DB (`name`+`body`+`sender` for Emails, something else for another DB). This is solved with a separate index table maintained by the application's write path (not a DB trigger — the logic of "which properties of a given DB are searchable" already exists in the application layer, no need to duplicate it in plpgsql), with a periodic reindex job as a safety net for writes outside the standard path (migrations, backfills).
- Table:
  ```sql
  CREATE TABLE item_search_index (
    item_id uuid PRIMARY KEY REFERENCES items(id) ON DELETE CASCADE,
    database_id uuid NOT NULL REFERENCES databases(id),
    search_vector tsvector NOT NULL,
    updated_at timestamptz NOT NULL DEFAULT now()
  );
  CREATE INDEX item_search_index_gin ON item_search_index USING GIN (search_vector);
  CREATE INDEX item_search_index_db_id ON item_search_index (database_id);   -- searches typically filter per-DB
  ```
- Queried via `websearch_to_tsquery` (accepts Google-style syntax — quotes, OR, minus — and unlike `to_tsquery` never fails on malformed input) and ranked via `ts_rank_cd` (rewards terms close together, better for prose than raw frequency), blended with recency — for a personal mailbox "most relevant" usually means "most recent." On top of that, a thin layer of Gmail-style search operators (`from:`, `has:attachment`, `before:`/`after:`, `is:unread`) — structured filters go into `WHERE`, the rest into `websearch_to_tsquery`.
- Postgres has no built-in full-text configuration for Czech — solved via `unaccent` (bundled contrib, diacritic-insensitive matching) plus a hunspell `cs_CZ` dictionary built into a custom `CREATE TEXT SEARCH CONFIGURATION czech`. Attachments (PDF/DOCX) are indexed by extracting text at ingest time (`pdftotext`/poppler-utils for PDF, runs in the low hundreds of ms — a single-user mailbox's volume allows doing this immediately, not lazily) — the output goes into the same index table.
- Deliberately **without** Meilisearch/Typesense/Elasticsearch — a second search service means a second source of truth, a sync pipeline, and another process to operate and back up, which doesn't pay off for a single-user corpus in the thousands-to-low-hundred-thousands range. Revisit only at real growth into tens of millions of items, or a need for large-scale OCR over scanned documents — neither applies now.

### Out of scope

(explicitly: mailbox UI, sending, drafts, and heartbeats over email belong to issue #27, not here)

- Sending email (SMTP-send service, generating an outgoing `Message-ID`/`In-Reply-To`/`References` from a UI "Reply" action).
- Drafts.
- Heartbeats and AI logic over email (aside from the deterministic linking to People described above, which is pure index lookup, not AI).
