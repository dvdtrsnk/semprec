**Model tier:** medium

## Context

Model tier rationale: One validation-and-store mechanism on an existing endpoint, but it is a tenant-isolation check on user-supplied ids, so both the foreign-tenant and the mismatched-pair cases need explicit tests.

#1369 defines the message ref schema. #1620 adds the HTTP endpoint that accepts a chat message for a Semp thread and stores it in the thread's messages table, whose `context` column is meant to carry the attached refs. This issue makes that endpoint validate the refs it receives and store the cleaned list there.

Without it, a client could attach a reference to an object of another tenant, to a deleted-for-good object or to an item filed under the wrong database, and later expansion of the ref (#1733) would fail or leak. Row level security already hides foreign rows, so existence checks run inside the request's tenant scope and a foreign id simply does not exist.

Decisions:
- The limit of 20 refs applies to the submitted array before duplicates are merged. 21 submitted refs are rejected even if some are duplicates.
- A trashed item is a valid ref (the user can still restore it); only a purged or foreign one is rejected.
- For a `block` ref, the item must exist and the block id must exist in the item's document. For a `transcriptSegment` ref, the item must be a Transcripts item; the range is not matched against segments.
- For an `agentRun` ref only the run's existence is checked here. The optional `messageId` is checked by #1936.

What builds on this: #1684, #1733, #1948, #1834, #1771, #1853 and #1849.

## Task

Load `io-hardening`, `error-handling`, `canonical-keys` and `testing`.

1. In the message endpoint from #1620, parse the request's `context` array with the schema from #1369. More than 20 entries, or an entry that does not parse, is rejected with a `ValidationError` (HTTP 400) whose `field` is `context[i]` for the offending index (`context` for the length error). Nothing is stored on rejection.
2. Add a store function that checks existence of each ref inside the caller's tenant transaction, batching by kind:
   - `item`: the `(itemId, databaseId)` pair matches an `items` row; a mismatching database is rejected like a missing item.
   - `block`: the item exists and its document contains the block id (read via `backend/packages/data/src/docs/blocks.ts`).
   - `transcriptSegment`: the item exists in the Transcripts database.
   - `mailAttachment`: a `mail_attachments` row with that id exists.
   - `agentRun`: the `agent_runs` row exists. `approvalRequest`: the approval request exists.
3. Merge duplicates by `messageRefKey` (keep the first, preserve order) and store the cleaned list in the message's `context`.
4. Tests (integration, real tenants via the tenant harness): a ref to another tenant's item gives 400 `context[i]` and stores nothing; an `(itemId, databaseId)` pair that does not match gives 400; the same ref twice is stored once; 21 refs give 400; each kind has an accepted and a rejected case; a trashed item is accepted.

## Scope

### In scope

- Parsing, limit, existence checks, duplicate merge and storing `context`.

### Out of scope

- The schema itself: #1369.
- Resolving labels and trash state when history is read: #1684.
- Expanding refs into the agent turn: #1733.
- Checking `messageId` of an agent run ref: #1936.
- Ref kinds added by #1933, #1771 and #1853, which add their own existence check.

## Acceptance criteria

- When a message carries a ref to an item of another tenant, then the response is 400 naming `context[i]` and no message row is written.
- When the `(itemId, databaseId)` pair does not match the item, then the response is 400 naming `context[i]`.
- When the same object is attached twice, then the stored `context` holds it once.
- When 21 refs are submitted, then the response is 400.
- When a ref points at a soft-deleted item, then the message is accepted.
