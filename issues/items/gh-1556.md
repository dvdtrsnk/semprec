## Context

Model tier rationale: One idempotent data update of two relation definitions in the existing cutover file plus the matching seed change, using the already enforced one-to-many cardinality mechanism.

In the seed (`backend/packages/data/src/seed/seedTenDatabases.ts`) both `Areas.company` and `Areas.healthRecord` are declared `one_to_one` with an `area` inverse. The trigger `enforce_relation_cardinality` (`backend/packages/data/src/db/migrations/0013_relation_cardinality.sql`) reads `relation_definitions.cardinality` on every `item_relations` insert, so today an area can hold at most one company and one health record, and a company or record can belong to one area. The product needs an area with several companies (for example the Work area with two companies) and several health records, while a company or a health record still belongs to at most one area.

The target is `one_to_many` with `Areas.company` / `Areas.healthRecord` as the "one" side (`property_id_a`), exactly how `Areas.projects` is modelled: the area has many targets, each target has at most one area. Existing edges stay valid under the relaxed rule, so no data changes. The property keys stay as they are; plural labels are handled by the label work in #1413.

This builds on #1515, which created the Areas cutover file (`backend/packages/data/src/seed/areasPropertiesCutoverMigration.ts`) and registered it in `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`).

## Task

Load `db-migrations`, `state-writes` and `testing`.

1. In `seedTenDatabases.ts` change the cardinality of the `Areas.company` and `Areas.healthRecord` relations from `one_to_one` to `one_to_many` (keep the inverse `area` properties).
2. Extend the Areas cutover step so that, for every maintained tenant (suspended ones included), it finds the Areas database by its owner module id and runs `UPDATE relation_definitions SET cardinality = 'one_to_many' WHERE property_id_a = <Areas.company or Areas.healthRecord property id> AND cardinality = 'one_to_one'`, inside the same `LOCK TABLE properties IN EXCLUSIVE MODE` transaction. It touches no other relation definition, is a no-op when already relaxed, and a tenant without an Areas database is skipped.
3. Tests: two companies can be attached to one area; the same company attached to a second area fails with `cardinality_violation` (HTTP 409); the same for health records; a second cutover run changes nothing; a suspended tenant is updated; `Areas.projects` and unrelated relations are unchanged.

## Scope

### In scope

- Relaxing the two cardinalities for new and existing tenants, with tests.

### Out of scope

- Plural Czech and English labels: #1413.
- Renaming property keys.
- Changing `Areas.projects`, `Files.area` or `Journal.area`.
- New properties on Areas: #1515.

## Acceptance criteria

- When a second company is attached to an area that already has one, then the write succeeds.
- When a company already attached to one area is attached to another, then the write fails with 409 `cardinality_violation`; the same holds for health records.
- After the cutover, `relation_definitions.cardinality` for `Areas.company` and `Areas.healthRecord` is `one_to_many` for every tenant, including a suspended one; running it again changes nothing.
- Edges that existed before the cutover remain readable from both sides.
- The full backend `pnpm run verify` passes.
