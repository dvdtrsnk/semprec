**Model tier:** medium

## Context

Model tier rationale: One cleanup mechanism hooked into the existing delete transaction and the purge path using established hook and dependent-cleanup patterns, with a narrow tenant-scoped data contract.

A link points at its source items through `value_link_sources` (#1403). When a source item is moved to the trash, the items that inherited from it must keep their values as their own: the link and its source rows disappear, the values stay, and restoring the source does not link them again. When an item is purged for good, its own link rows and the rows that name it as a source go with it.

Today `itemDeleteWithClient` and `restoreItemWithClient` in `chokePoint/itemTrash.ts` leave relation edges in place and run no hooks; #1601 adds delete and restore hooks to the choke point, registered through `domainWriteHooks.ts` (ADR `docs/adr/2026-09-30-choke-point-domain-hooks-through-a-per-process-registry.md`) and run in the same transaction. The purge path removes dependent rows in `deleteItemDependents` (`itemTrash.ts`), which today knows nothing about link rows. #1743, #1882 and #1856 build on this.

Decisions:

- On soft delete of a source item: delete its rows from `value_link_sources`; then delete every `value_links` row that has no source left. A link that still has another live source stays, and later reads and propagation use the remaining sources only.
- The inherited values are not touched: the target properties and edges keep their values and read as own afterwards.
- The restore hook restores nothing.
- On purge: delete the purged item's own `value_links` rows (their sources cascade) and any `value_link_sources` row naming it as source, then the same empty-link cleanup. This runs inside `deleteItemDependents`, in the purge transaction.
- Items that lose a link are announced to clients after the commit so they refetch `links`.

Shared-file ordering: this issue also waits for #1652 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

5. ## Scope

### In scope

- Detaching links whose source is trashed, keeping the inherited values as own.
- Removing link and source rows of purged items.
- Client invalidation for items that lose a link.

### Out of scope

- The delete and restore hook mechanism itself: #1601.
- Releasing a trashed Event's transcript edge: #1743.
- Reporting what deleting an item affects: #1856 and #1882.
- Re-linking after a source is restored (deliberately never automatic).

## Acceptance criteria

- When a source item is soft-deleted, then every item that inherited from it keeps its value, `links` has no entry for that property, and no `value_links` or `value_link_sources` row for it remains.
- When the source is restored, then the inheriting items remain own; no link is recreated.
- When a link has two sources and one is deleted, then the link stays `on` with the other source.
- When an item is purged, then no `value_links` row with its id as `item_id` and no `value_link_sources` row with its id as `source_item_id` remains.
- If any part of the cleanup fails, the item is not deleted (the cleanup shares the delete transaction).
- Rows of another tenant are not read or removed.
