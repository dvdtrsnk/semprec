## Context

Both push adapters resolve their configuration as a *default parameter*: `sendApnsNotification(target, payload, config: ApnsConfig = getApnsConfigFromEnv())` (`backend/packages/data/src/push/apnsAdapter.ts` line 194) and `sendWebPushNotification(target, payload, config: VapidConfig = getVapidConfigFromEnv())` (`backend/packages/data/src/push/webPushAdapter.ts` line 30). `getApnsConfigFromEnv` (lines 36-47) throws when any of `APNS_TEAM_ID`, `APNS_KEY_ID`, `APNS_PRIVATE_KEY_PATH`, `APNS_TOPIC` is unset and also when `readFileSync(privateKeyPath)` fails (`ENOENT`, `EACCES`); `getVapidConfigFromEnv` (lines 11-19) throws when any `VAPID_*` variable is unset. A default parameter is evaluated before the function body, so those throws never reach the adapters' `try`/`catch` that maps provider failures to `PushSendResult`; they propagate out of `senders.sendApns(...)` / `senders.sendWebPush(...)` in `handleNotificationFanoutTask` (`backend/packages/data/src/notifications/notificationFanoutJob.ts` lines 113-116), abort the loop before any other registration is attempted, and fail the `notificationFanout` job, which was enqueued with `maxAttempts: 10` (line 38). A deployment without push credentials — the normal state until an operator configures them — therefore retries every notification's fanout ten times with exponential backoff, settles no `push_deliveries` row, and surfaces as `queue:permanentlyFailedJobs` after the tenth failure.

The existing result type (`backend/packages/data/src/push/pushSenders.ts` lines 20-30) has no outcome for "the server is not configured for this channel". Reusing `permanent-failure` is wrong: the job pairs it with `revokePushSubscriptionByProviderInvalidation` (lines 120-129), which would revoke a perfectly valid device registration because of a server-side gap.

## Task

1. In `backend/packages/data/src/push/pushSenders.ts`, extend `PushSendResult` with `| { outcome: "not-configured"; reason: string }` and document it: the adapter has no usable credentials for its channel; the caller records the delivery as permanently failed with `reason` and must not revoke the registration.
2. In both adapters, move configuration resolution inside the function: `config?: ApnsConfig` / `config?: VapidConfig` (tests keep injecting one); at the top of the body, `try { resolved = config ?? getXConfigFromEnv(); } catch (error) { return { outcome: "not-configured", reason: error instanceof Error ? error.message : String(error) }; }`. For APNs this also covers an unreadable key file — the `readFileSync` error message (`EACCES: permission denied, open '/opt/semprec/shared/apns-key.p8'`) is the reason. The messages already name the variables and never include their values; keep it that way (no secret in `reason`). Rewrite the `getApnsConfigFromEnv` docstring (lines 27-34) to drop the "root:root 0600" claim and say the key file is provisioned readable by the service user by `deploy/provision.sh`.
3. In `handleNotificationFanoutTask`, add a branch before the transient fallback: `result.outcome === "not-configured"` → `withTransaction(pool, (client) => markPushDeliveryFailedPermanently(client, status.id, result.reason))` with no revoke and no entry in `transientFailures`; log once per job and channel with the mail-style structured logger pattern (add `backend/packages/data/src/notifications/logger.ts`, `createLogger("notifications")`, if the notifications directory has none) — `logger.warn({ notificationId, channel, reason }, "Push channel is not configured; delivery marked permanently failed")`. Update the handler docstring (lines 68-81) with the fourth outcome.
4. Tests:
   - `backend/packages/data/src/push/__tests__/apnsAdapter.unit.test.ts` (existing, unit): with `APNS_*` unset, `sendApnsNotification(target, payload)` resolves `{ outcome: "not-configured", reason: /APNS_TEAM_ID/ }` and makes no HTTP/2 request; with the variables set but `APNS_PRIVATE_KEY_PATH` pointing at a nonexistent file, the reason contains `ENOENT`; restore `process.env` after each case.
   - `backend/packages/data/src/push/__tests__/webPushAdapter.unit.test.ts` (new, unit): with `VAPID_*` unset, `sendWebPushNotification(target, payload)` resolves `not-configured` naming `VAPID_PUBLIC_KEY` and `webpush.sendNotification` (spied) is never called.
   - `backend/packages/data/src/__tests__/notificationFanoutJob.test.ts` (existing, integration): a fake sender returning `not-configured` for one of two registrations → the job resolves (does not throw), that registration's `push_deliveries` row has `failed_permanently_at` set and `last_error` equal to the reason, its `push_subscriptions` row is *not* revoked, and the other registration is still delivered.

## Scope

### In scope
- The `not-configured` outcome, both adapters' in-body config resolution, the fanout branch, and the tests.

### Out of scope
- File ownership and modes under `/opt/semprec/shared` (sibling issue F8a of this batch).
- Re-dispatching deliveries that were marked permanently failed while the channel was unconfigured (they stay failed; new notifications deliver once configured).
- Provider error mapping (404/410/`BadDeviceToken`), unchanged.

## Acceptance criteria

- When `VAPID_*` or `APNS_*` is unset (or the `.p8` is unreadable) and a notification is written, the fanout job completes on its first run, every affected `push_deliveries` row has `failed_permanently_at` set with a reason naming the missing variable or the file error, no `push_subscriptions` row is revoked, and one warning per channel is logged.
- When the channel is configured, delivery, transient retry and provider-invalidation behaviour are unchanged (existing `notificationFanoutJob.test.ts` cases pass).
- No `reason` string ever contains a credential value.
