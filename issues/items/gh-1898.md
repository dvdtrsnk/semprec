## Context

Model tier rationale: This adds a relation schema with a per-tenant cutover, a new ingest-time edge write, a link rule that writes a user-owned property from a system process, and a merge repointing of link sources, all of which are persisted-data contracts.

An attachment of a mail message becomes a Files item at ingest (`mail/attachments.ts`, `ingestAttachments`), linked from the message by `Emails.attachments`, with no project, company or people. The intended behavior: an attachment takes the project of its thread, follows later changes of the thread's project, and ends following when a user or Semp sets the file's project by hand. `Files.projects` and `Files.companies` exist as `many_to_many`, `owner: user` relations; writing them from the system needs the explicit ownership handoff of the value-link mechanism (`docs/adr/2026-09-10-single-writer-ownership-model.md`, #1403). Rules are declared in module manifests (#1411) and propagated by `valueLinks.propagate` (#1593). The company of a file follows from its project by #1653; people are not inherited.

The thread-level project comes from #1869; the break rules are #1516. The thread item and merge are #1573.

Decisions: no backfill of attachments that already exist (they keep their values); a file attached from an existing Files item keeps its own source (only a new Files item created by ingest is linked); the link row is created at ingest even when the thread has no project yet.

Shared-file ordering: this issue also waits for #1883, #1896 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `db-migrations`, `canonical-keys` and `testing`.

1. Add the one-directional system-owned relation Threads.attachments (`one_to_many`, Threads side is "one") to Files: in the shared Threads builder of #1573 for fresh installs, and for existing tenants a cutover `mail/threadAttachmentsCutoverMigration.ts` registered after the Threads cutover in `db/tenantCutoverMigrations.ts`. Idempotent.
2. In `ingestAttachments`, for every Files item it creates, write the edge from the message's thread item to the file in the same transaction (the caller passes the thread item id) and create the value-link row with source the Threads item and property `project`, state on.
3. Declare the link rule in `mail/mailModuleManifest.ts`: source Threads.project, target Files.projects, via Threads.attachments. Propagation on every project change of the thread covers all linked attachments, also those that arrive later.
4. User or Semp writes of Files.projects end the link and the unlink and relink operations apply as defined by #1516 and #1587; add tests, no new mechanism.
5. Merge: after the generic edge move of #1573, repoint the sources of the moved files' links from the losing thread item to the winner and run the propagation for them.

## Scope

### In scope

- The Threads.attachments relation, the ingest edge and link, the rule, and the merge repointing.

### Out of scope

- Company of a file through its project (#1653); people on files.
- Returning project and link state in the thread detail (#1922).
- Backfilling existing attachments.
- Which project a thread has (#1869).

## Acceptance criteria

- An attachment ingested into a thread whose project is "Web pro klienta" has Files.projects equal to it; changing the thread's project changes the file's project.
- After the file's project is changed by hand, a later thread project change does not touch it; relink restores following.
- An attachment that arrived before the thread had a project receives the project when the thread gets one, as does a later attachment.
- A file attached from existing Files to a draft does not change its project.
- After a merge of two threads, the loser's attachments follow the winner's project.
