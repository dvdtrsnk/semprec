### Requirement gh-1663: [calendar-events 06/12] Validate Events dates and times at the choke point

#### Context

Model tier rationale: One validation mechanism (create and update hooks raising the existing validation error) with a clear rule table and existing hook fixtures, applied to every write path.

Events `date` is a free string today and nothing checks it (see the comment on `ISO_DATE_PATTERN` in `backend/packages/data/src/rollup/recompute.ts`). #1416 added `endDate`, `timeFrom` and `timeTo` to Events and #1598 normalizes them and derives `time` before the write. This issue rejects what remains invalid, after normalization.

Item hooks (`backend/packages/data/src/chokePoint/hooks.ts`, registered in `backend/packages/data/src/domainWriteHooks.ts`) run after the write inside the same transaction and can reject but not change values; a `ValidationError` (`backend/packages/data/src/errors.ts`) becomes HTTP 400 `validation_failed` with `details.field`. Events have no hook today. Because the choke point is shared, REST, the assistant's `item.patch` and MCP get the same error.

Decisions:
- Format rules apply only to keys present in the patch. Cross-field rules apply only when the patch changes `date`, `endDate`, `timeFrom` or `timeTo`. Reason: Events stored before the conversion in #1797 can have unreadable values and must stay editable (for example renaming) until then.
- An unreadable stored value is treated as null when a cross-field rule runs.
- A multi-day or overnight Event can only be created with an explicit end; a timed single-day Event without an end gets one from #1598.

Shared-file ordering: this issue also waits for #1660 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Decision (batch 37 reconciliation): API-layer parity tests use the real REST dispatcher, agent gateway and MCP listener; data-package tests alone do not prove this boundary.

#### Task

Load `error-handling`, `state-writes` and `testing`.

1. Add an Events create hook and an Events update hook (for example `backend/packages/data/src/calendar/eventValidationHook.ts`) and register both in `backend/packages/data/src/domainWriteHooks.ts`.
2. Rules, each failing with `ValidationError` and the named `field`:
   - `date` is required on create and, if present, must be `YYYY-MM-DD` (field `date`). A `date` carrying a time is accepted only as a value that #1598 already converted; one that survives unconverted is rejected.
   - `endDate`, if present, is `YYYY-MM-DD` and not before `date` (field `endDate`).
   - `timeFrom` and `timeTo` are `HH:MM`; `timeTo` may be `"24:00"`, `timeFrom` may not (fields `timeFrom`, `timeTo`).
   - `timeTo` without `timeFrom` is rejected (field `timeTo`).
   - `endDate` after `date` with `timeFrom` and no `timeTo` is rejected (field `timeTo`).
   - The end (`endDate ?? date`, `timeTo`) must be after the start (`date`, `timeFrom`) when both times exist; equal times, including `"23:55"` to `"23:55"`, are rejected (field `timeTo`).
   - An Event without `timeFrom` (all-day) may span days with no time.
3. Apply format checks only to keys in the patch and cross-field checks only when one of the four keys changes, per the decisions above.
4. Tests, for REST, an agent `item.patch` and MCP (the error body is identical): the rejections above, and the passes below.

### Requirement gh-1666: [journal 14/21] Refuse restoring a journal period that already has a live entry and re-point its reservation

#### Context

Model tier rationale: Hooks into restore, a write path with no domain hook today, and rewrites a concurrency-critical reservation row, so a mistake silently produces duplicate or orphaned Journal entries.

A Journal entry per period is found by the reservation `journal:<journalDb>:<type>:<period>` in `idempotency_keys`, which `getOrCreateJournalItem` (`backend/packages/data/src/journal/journalStore.ts`) uses so that concurrent first writes converge. When an entry is trashed or purged, the next write for that period creates a new entry and the reservation moves to it. Nothing enforces uniqueness of type and period.

Restore (`POST /api/items/:id/restore`, `restoreItemWithClient` in `backend/packages/data/src/chokePoint/itemTrash.ts`) neither touches the reservation nor runs a hook. Two states follow: (a) the old entry is trashed, a new one is live, and restoring the old one leaves two live entries for one period; (b) both are trashed, restoring the old one succeeds but the reservation still points at the trashed new entry, so the next write creates a third entry and again two are live. The design offers no way to delete or restore a Journal period, so these are defensive invariants for the generic delete/restore REST, MCP and Semp. Duplicates that already exist are merged by #1726, which builds on this issue.

#1601 adds the registry for item delete and restore hooks (a hook that throws makes the whole restore fail). This issue registers only the Journal restore hook.

Decision: restoring is refused when a live entry for the same period exists (409), rather than letting a later write restore the trashed entry on its own; the existing behavior of creating a fresh entry is kept. Deleting a Journal entry deletes the entry itself (not only its page).

Shared-file ordering: this issue also waits for #1663 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Decision (batch 37 reconciliation): Serialize the period decision through its reservation and recheck live peers after acquisition. Do not add blocking locks on peer items: concurrent restores already hold their root rows. Document bounded lock scope.

#### Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `journalItemRestoreHook` in the journal module and register it in `backend/packages/data/src/domainWriteHooks.ts`. For an item of the Journal database it runs inside the restore transaction after the restore:
   - if another live Journal row has the same `type` and `period`, throw `ConflictError` (HTTP 409) so the restore is rolled back, with details naming the live entry;
   - otherwise point the reservation `journal:<db>:<type>:<period>` at the restored item (update the existing row, or insert it if it is missing) in the same transaction.
2. Put the reservation re-point in a store function in `journalStore.ts`, using the same key format as `getOrCreateJournalItem`.
3. Scenario tests: (a) old entry trashed, new live, restore old gives 409 and only the new entry is live; (b) both trashed, restore old succeeds, the reservation points at it, and the next `getOrCreateJournalItem` for that period returns the restored entry's id and no third row is created; restoring a non-Journal item is unaffected; restoring a Journal entry nobody else holds works as before.

- backend/packages/data/src/journal/journalRestoreHook.ts (new)

### Requirement gh-1665: [tasks-recurrence 03/11] Set, change and clear a task's recurrence over HTTP

#### Context

Model tier rationale: One new REST mechanism over the already-existing series storage, using the established custom-route and route-matrix pattern, with defined validation rules and existing fixtures.

A task's recurrence rule cannot be set from outside today. `createTaskRecurrence` (`backend/packages/data/src/tasks/taskRecurrenceStore.ts`) is called only by the advance logic and by tests; no route exposes it, and the Tasks module registers no agent tools (`agentTools: []` in `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts`). The supported rules are in `backend/packages/data/src/tasks/taskRecurrenceRule.ts`: fixed `weekdays`, `monthDates`, `nthWeekday`, and floating `{unit, n}`. There is no yearly rule.

#1605 gives each recurring task a `seriesId`, an anchor date and a `recurrence` property. This issue adds the HTTP endpoint that creates, changes and removes the rule. Per the single-writer ownership ADR (`docs/adr/2026-09-10-single-writer-ownership-model.md`) custom HTTP routes over Tasks are owned by the `systemDatabases` module, so the route is registered in that module's `customRoutes`.

The Semp agent does not get a tool in this issue. A module agent tool would bypass the generic operation catalog and the approval exemption described in `docs/adr/2026-09-18-non-destructive-generic-operations-bypass-agent-approval.md` and `docs/adr/2026-09-10-agent-writes-are-proposals-not-direct-writes.md`. Semp reaches recurrence through the generic item write with the same risk rules as other properties, where changing or ending a series always needs approval; that is #2011, which reuses the store helpers added here.

Decisions: the presets here are `daily`, `weekdays`, `weekly` and `monthly`; the yearly rule `yearDates` and its `yearly` preset are added on top of this route by #2010; removing the date of a recurring task is rejected with 400, not treated as switching recurrence off (conservative: the user turns recurrence off explicitly with DELETE).

Shared-file ordering: this issue also waits for #1650, #1657 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Decision (batch 37 reconciliation): A new PUT may reuse its inactive per-item recurrence row with a new series id. DELETE clears all three occurrence identity fields. Non-current occurrences reject PUT/DELETE with 400 on id.

#### Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.
