## Context
Review of pull request #392 found that after `backend/packages/data/src/chokePoint/chokePoint.ts` was reduced to a composition root, `createRelationProperty` (now in `backend/packages/data/src/chokePoint/relationPropertyOps.ts`) takes only `input: CreateRelationPropertyInput` and its `runAfterCommit` call to `notifyInvalidation({ scope: "schema", databaseId })` never passes a `userId`. Every sibling method in `backend/packages/data/src/chokePoint/propertyOps.ts` (`createProperty`, `renameProperty`, `updatePropertyConfig`, `changePropertyType`, `deleteProperty`) threads an `actingUserId?: string` parameter through to `notifyInvalidation`, so `createRelationProperty` is inconsistent with its siblings and the invalidation notification for a relation-property creation is missing the acting user.

## Task
- Add an `actingUserId?: string` parameter to `createRelationProperty` in `backend/packages/data/src/chokePoint/relationPropertyOps.ts`, matching the signature convention already used by `createProperty`, `renameProperty`, `updatePropertyConfig`, `changePropertyType` and `deleteProperty` in the same package.
- Pass that `actingUserId` through to the `notifyInvalidation({ scope: "schema", databaseId, userId: actingUserId })` call inside `createRelationProperty`'s `runAfterCommit`, matching how the sibling methods pass `userId`.
- Update `createRelationProperty`'s caller in `backend/packages/application/src/genericApplicationService.ts` (line 119, inside `createProperty(actor, input)`) to pass `actor.userId` through as `actingUserId`, matching how the sibling call `chokePoint.createProperty(..., actor.userId)` does it.

## Touches
- backend/packages/data/src/chokePoint/relationPropertyOps.ts
- backend/packages/application/src/genericApplicationService.ts (the `createRelationProperty` call site only)
- backend/packages/data/src/__tests__/relationPropertyOps.test.ts (one new test case asserting the invalidation event's `userId`; `itemWrites.test.ts` shows the `setInvalidationHook` capture pattern)

## Scope
### In scope
- Threading `actingUserId` through `createRelationProperty` and its `notifyInvalidation` call, and updating its call site.

### Out of scope
- Any other method in `relationPropertyOps.ts` or `propertyOps.ts`.
- Changing the shape of `CreateRelationPropertyInput` itself.

## Acceptance criteria
- `createRelationProperty` accepts an `actingUserId?: string` parameter.
- The `notifyInvalidation` call inside `createRelationProperty`'s `runAfterCommit` passes `userId: actingUserId`.
- A test calling `createRelationProperty` with an acting user id asserts that the resulting invalidation notification carries that `userId`.
