## Context

`properties` carries `UNIQUE (database_id, key)` (`backend/packages/data/src/db/migrations/0001_core_schema.sql`, line 55; constraint name `properties_database_id_key_key`). `propertiesStore.createProperty` (`backend/packages/data/src/chokePoint/propertiesStore.ts`, lines 180-206) runs the `INSERT` (lines 190-204) with no handling for the unique violation, and `createPropertyOps(...).createProperty` in `chokePoint/propertyOps.ts` (lines 129-150) adds none, so `POST /api/properties` with a key that already exists in that database surfaces a raw Postgres `23505` — a 500 from the API instead of a 4xx that names the field. Every other unique collision in the choke point is mapped: `databasesStore.ts` line 93 (`databases_key_unique` → `ConflictError`), `viewsStore.ts` lines 134/221 (`views_one_default_per_db` → `ConflictError`), each with a local `isUniqueViolation(err, constraint)` helper.

## Task

1. `propertiesStore.ts`: a module-private `isUniqueViolation(err, constraint)` with the same three-line body as `databasesStore.ts` lines 9-12 (a `pg` error with `code === '23505'` and the named `constraint`). `createProperty` wraps its `INSERT` in `try/catch` and, on `isUniqueViolation(err, 'properties_database_id_key_key')`, throws `new ConflictError(\`Property key '${input.key}' already exists in database ${input.databaseId}\`, { field: 'key', reason: 'duplicate' })`; everything else rethrows. `ConflictError` is imported from `../errors.js` (its `status` is 409, `code` `version_conflict` — the existing class, not a new one).
2. Test, new `backend/packages/data/src/__tests__/propertyKeyConflict.test.ts` (integration): creating a property with an existing key in the same database rejects with `ConflictError` (`status 409`, `details` `{ field: 'key', reason: 'duplicate' }`) and leaves exactly one row with that key; the same key in another database succeeds; through the HTTP layer (`backend/services/semprec-api/src/__tests__/propertiesHandler.test.ts`, one new case) `POST /api/properties` with a duplicate key responds 409 with `error.details.field === 'key'`.

## Touches

- backend/packages/data/src/chokePoint/propertiesStore.ts (`createProperty` and the new helper only)
- backend/packages/data/src/__tests__/propertyKeyConflict.test.ts (new)
- backend/services/semprec-api/src/__tests__/propertiesHandler.test.ts (one new case)

## Scope

### In scope
- Mapping the duplicate-key unique violation on property creation to a 409 `ConflictError` and the tests.

### Out of scope
- Renames colliding on key (`renameProperty` changes `name`, not `key`; no key rename exists).
- The source-property delete guard (sibling issue C9).
- Extracting the three per-store `isUniqueViolation` helpers into one shared function.

## Acceptance criteria

- When `POST /api/properties` names a key already present in the target database, the response is 409 with `details.field = 'key'` and `details.reason = 'duplicate'`, and no second row is created.
- When the same key is created in a different database, the request succeeds as before.
- No other error from `createProperty` changes shape.
