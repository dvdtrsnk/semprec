## Context

Model tier rationale: A small change in two producers that must stay in step, but the link depends on the recorded source of the request and the exact destination names are shared with clients, so a wrong branch silently sends a person to the wrong place.

Both producers of the approval notification, `preflightDestructiveApproval` (`backend/packages/application/src/genericOperationGateway.ts`) and `createApprovalGatedMcpInvokeTool` (`backend/packages/agent-runtime/src/mcpInvokeTool.ts`), write the same `linkHref`: `?page=approvals&user=<userId>`. It does not point to the request and it ignores where the request came from. Requests now record their source (#1766: a chat, an automatic task tick, or an MCP client). A request raised in a Semp chat belongs in that chat; one raised by an automatic task or an MCP client belongs in the Inbox.

This issue makes the notification link depend on the source and carry the request id. It builds on #1766 and on #1728, which touches the same creation sites.

Decision: link destinations are `?page=semp-chats&tab=semp&approvalRequestId=<id>` for a chat request and `?page=inbox&approvalRequestId=<id>` for a tick or MCP request; the `user=<userId>` parameter is dropped. The page names must be confirmed with the clients before release. Decision: the `link` field of `ApprovalRequiredError` returned to the agent (`?page=approvals&id=...`) is not changed here.

## Acceptance criteria

- A request raised in a Semp chat produces a notification whose `link_href` is `?page=semp-chats&tab=semp&approvalRequestId=<id>`.
- A request raised by an automatic task tick or by an MCP client produces `?page=inbox&approvalRequestId=<id>`.
- Neither link contains the user id.
- A request with no recorded source links to the Inbox.
- Generic-operation and MCP requests from the same source produce identical links.
