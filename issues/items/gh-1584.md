**Model tier:** medium

## Context

Model tier rationale: One known mechanism (an optional validated `color` on stored select options, projected through the resolver, plus an idempotent per-tenant backfill) across defined store, resolver and cutover seams with existing fixtures, but it writes into schema-locked system databases of existing tenants.

The app shows select values as colored chips: file types, health-record status, event types, people relationships, project status, and the Library statuses. Today a select option is `{ key, label? }` and nothing more (issue 145's catalog shape). `assertValidSelectOptions` in `backend/packages/data/src/chokePoint/propertiesStore.ts` checks only `key` and `label` and lets other fields through unvalidated, and `filterValidOptions` and `resolveProperty` in `backend/packages/data/src/manifest/catalogResolution.ts` return only `{ key, label }`, so a color written today is stored but never reaches `GET /api/schema`. The system databases are schema-locked, so existing tenants can only be changed by a per-tenant cutover registered in `backend/packages/data/src/db/tenantCutoverMigrations.ts` (see `docs/adr/2026-10-08-deploy-time-tenant-work-runs-as-the-runtime-role.md`; `transcription/transcriptsCatalogCutoverMigration.ts` is the pattern: lock, idempotency check, backfill). Fresh installs get their options from `seed/seedTenDatabases.ts` (`selectConfig`) and `seed/seedLibraryModule.ts`.

Builds on #1360 (the property projection this extends) and #1549 (which extends the People `relationship` options to the unified list, including `colleague`, `craftsman` and `doctor`, so this issue colors that final list). #1622 registers its own step in the same cutover file after this one; #1705 colors the health-record tag options and #1699 adds and renames options on locked databases; #1707 seeds Recipes categories with colors using the shape defined here.

Decision: a color is an optional `#RRGGBB` hex string (6 digits, case-insensitive, stored upper-case) on `config.options[].color`. Anything else is a validation error. Absence means "no color", and the client picks its neutral.

Decision (product owner): project status colors use the detail-view set (inProgress `#007AFF`, longTerm `#AF52DE`, done `#34C759`, archived `#8E8E93`) everywhere, and the label stays the catalog label. One color set is used on every screen, so a change is made in one place: the backend value is the single source.

Decision: Journal period options stay uncolored. The design's orange belongs to the "all" filter chip, which is a quick filter (#1647), not a select option; the mechanism here lets a later change color the periods without code.

Decision (product owner): colors for People relationship options that the design has not defined yet (`colleague`, `craftsman`, `doctor`) use neutral `#8E8E93` until the design supplies values.

Shared-file ordering: this issue also waits for #1578 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `canonical-keys`, `state-writes` and `testing`.

1. Extend `assertValidSelectOptions` in `propertiesStore.ts`: when an option has `color`, it must be a string matching `^#[0-9A-Fa-f]{6}$`, otherwise `ValidationError` with `field: "config"`. Normalize to upper-case on write. This covers `property.create`, `property.patch` and the internal config updates, since all go through that function.
2. Extend `ResolvedOption` and `filterValidOptions`/`resolveProperty` in `manifest/catalogResolution.ts` so a valid `color` is returned as `color` on each option in `GET /api/schema`; an option without a color, or with an invalid legacy value, omits `color` (never fails the response).
3. Seed the colors on fresh installs in `seed/seedTenDatabases.ts` and `seed/seedLibraryModule.ts` (extend or replace `selectConfig` so it can take colors):
   - Files `type`: pdf `#FF3B30`, xlsx `#34C759`, docx `#007AFF`, jpg `#FF9500`.
   - Health records `status`: monitoring `#FF9500`, resolved `#34C759`.
   - People `relationship`: client `#007AFF`, closeFriend `#AF52DE`, parent `#FF9500`, girlfriend `#FF2D55`, therapist `#34C759`, neighbor `#8E8E93`, plus the options added by #1549 per the decision above.
   - Events `type`: meeting `#AF52DE`, standup `#007AFF`, event `#FF3B30`.
   - Projects `status`: inProgress `#007AFF`, longTerm `#AF52DE`, done `#34C759`, archived `#8E8E93`.
   - Books `status`: toRead `#8E8E93`, reading `#007AFF`, read `#34C759`. Movies `status`: planned `#8E8E93`, watching `#007AFF`, watched `#34C759`.
   - Journal `type` (year, quarter, month, week, day) gets no colors here: the design colors only an "all periods" chip, which is not a stored option, so there is nothing to store. See the Journal decision above.
4. Add a per-tenant cutover function in a new file (for example `backend/packages/data/src/seed/selectOptionColorsCutoverMigration.ts`) and register it in `runTenantCutoverMigrations`. It resolves each listed database by module id, locks `properties` as the existing cutover does, and for each listed select property sets `color` on the options that are listed and have none yet, leaving every other option field, order, and any color already set (including a user-chosen one) untouched. A database or option that does not exist for the tenant is skipped. A second run changes nothing.
5. Custom databases write colors through `property.create`/`property.patch` with the same validation; no new endpoint.
6. Tests: validation accepts `#ff3b30`, rejects `red`, `#FFF`, `#GGGGGG` and a non-string; `/api/schema` returns colors; the cutover colors an existing tenant's options, preserves a pre-set color and unlisted options, and is a no-op on the second run.

## Scope

### In scope

- Optional hex `color` on select/multi-select options: validation, storage, projection in `/api/schema`.
- Seeded colors for Files, Health records, People, Events, Projects and the two Library status properties, for fresh installs and existing tenants.

### Out of scope

- Numeric filter presets (#1622).
- Colors for the Recipes categories (#1707) and the health-record tag options (#1705).
- Adding, renaming or removing options on locked databases (#1699).
- Reordering option catalogs (#1578).
- Per-option color in the option catalog labels or any client rendering.

## Acceptance criteria

- When `GET /api/schema` is requested on a fresh install, then Projects `status` returns `type: "select"` with options carrying the colors listed above and `filterable: true`.
- When a tenant that existed before this change is migrated, then every listed option has its color, a color already set on an option is unchanged, and running the cutover again changes nothing.
- When `property.create` or `property.patch` contains an option color that is not `#RRGGBB`, then the call fails with a validation error on `config`; a valid lower-case hex is stored upper-case.
- When a stored option has an invalid legacy color, then `/api/schema` still succeeds and omits `color` for that option.
- When a user-created select property has colored options, then `/api/schema` returns them with their colors.
