## Context

Model tier rationale: It is documentation only, but the decision touches the tenant isolation contract, so an inaccurate statement about row-level security or the router functions would mislead later implementers.

Calendar invitations by email and calendar subscriptions by ICS link need nothing between tenants. A third idea, sharing a calendar with another Semprec user so that their app shows the events, does touch tenant isolation, and the accepted decisions currently exclude it:

- `docs/adr/2026-10-03-tenant-isolation-through-row-level-security.md` makes a tenant the complete environment of exactly one user, "with no sharing between users now or planned"; memberships are excluded and migration `0082_drop_legacy_global_unique_keys.sql` removed `resource_grants`.
- `docs/adr/2026-10-07-cross-tenant-router-functions.md` lets code cross tenants only through `SECURITY DEFINER` functions that return ids or numbers, never content.
- `backend/review-rules/rules.md` rates a query that reads rows of more than one tenant, or a policy that widens visibility, as critical.
- A second account (and therefore a second tenant) exists only after #1087; accounts are always created as new tenants.

Any sharing feature therefore needs a decision first. This issue records it. Doing so now prevents a feature from being built on an assumption the architecture forbids.

Decision recorded by this issue (variant B, decided by the product owner): in this version there is no cross-tenant calendar sharing; it is out of v1 and contradicts tenant isolation. Calendars and events are private to their tenant. People get meetings from the calendar through email invitations (iMIP, answered by the invitation feature) and can follow external calendars through ICS subscriptions. Consequently there is no "shared with" subtitle on a calendar and no shared-calendar notice; the `sharedCalendarNotice` kind of the invitations database stays without a producer.

Variant A (mirroring events into the recipient's tenant) is rejected for now. The ADR must say what it would take, so that nobody re-derives it: it contradicts the "no sharing" statement of the tenant isolation ADR, so it would need a new ADR superseding that part and extending the router-functions ADR with a channel through which event content travels from the owner's tenant to the recipient's (for example a global outbox table with per-tenant encryption), because under row-level security and router functions that return only ids no row of one tenant can be read from another; a copy owned by the system would be written in the recipient's tenant by a job running in that tenant; it would need to decide read and write rights, what the recipient sees of private fields (description, attachments, recordings) and what happens when sharing is removed.
