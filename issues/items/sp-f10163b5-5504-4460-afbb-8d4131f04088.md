**Model tier:** high

## Context

Model tier rationale: Introduces durable desired-state write-backs with a three-way merge; races with incoming syncs must not lose either side.

Users and agents edit events in writable account calendars through the choke point. Those changes must reach the provider (epic decision: per-field three-way merge, provider wins on a field changed on both sides).

## Task

Load `state-writes`, `db-migrations`, `error-handling`, `io-hardening`, `canonical-keys` and `testing`.

1. Table `calendar_event_push_state` (event item id PK, operation create|update|delete|move, desired revision, status pending|sent|conflict|failed, attempts, last_error_code) with tenancy and RLS.
2. Write hooks on Events (create, update of synced fields, trash, restore, relation change of `calendar`) in writable account calendars by any writer except `calendarSync`: record desired state in the same transaction and enqueue `calendarEventPush` (key per event, replace).
3. The push job reads the event, its `base_snapshot` and etag outside a transaction, calls the adapter, then in a transaction (rechecking the desired revision) stores the new etag and snapshot. On a conflict, fetch the remote event, merge per field against `base_snapshot` (local wins where remote unchanged; remote wins where both changed), apply the merge locally as `calendarSync`, push again once, and raise the notification `calendar_change_overwritten` when a local value was lost.
4. Moving an event to another calendar of the same account uses the provider move (Google `move`, Graph by delete+create, CalDAV by PUT to the new collection then DELETE); across accounts it is delete + create.
5. The incoming apply skips events whose push is pending and re-queues the push after applying the remote change.
6. A user's or agent's edit of `date`, `endDate`, `timeFrom` or `timeTo` on an Event with a `timeZone` is read in the tenant's time zone and converted to the Event's zone in the Events pre-write transform before it is stored, so the Event keeps its zone and does not move; `calendarSync` writes are stored as sent.
7. Update `docs/architecture/transactions-and-side-effects.md` (Provider write-backs) with calendar events.

## Acceptance criteria

- An event created in the app in a writable synced calendar exists at the provider after the push job.
- When the title changed locally and the place remotely, both changes survive.
- When the title changed on both sides, the remote title wins and `calendar_change_overwritten` is written once.
- An incoming sync during a pending push does not undo the local change.
- Agent writes go through the same path (and still need their usual approval).
- Editing an Event stored at 09:00 America/New_York to 16:00 from a Europe/Prague tenant stores 10:00 America/New_York.
