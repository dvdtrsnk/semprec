## Context

Model tier rationale: One additive value threaded through known write seams (gateway, application service, item and relation write functions, hook contexts) with existing fixtures, but it must be derived server-side only and cover several internal callers correctly.

Hooks and domain rules need to know who made a write: a person, an agent acting for a person, or the system itself. Examples are telling a manual change of a field from one Semp made, letting a write from a link's source keep the link, approving a change that only Semp may make, and per-database grants for agents. Today this is not available. `createItemWithClient` and `updateItemWithClient` (`backend/packages/data/src/chokePoint/itemWrites.ts`) take only `actingUserId` and `humanWriterUserId`; the latter is set for a human REST session and absent for an agent, `/mcp`, the system and internal callers alike. The `Actor` type (`user | ai_agent | system`) in `chokePoint/authorization.ts` reaches only view writes. Above the choke point, `AuthenticatedActor` (`backend/packages/shared/src/genericOperations/actor.ts`) already carries `userId`, `runId`, `agentProjectItemId` and `restSession`, but `putRelation` and `deleteRelation` in `backend/packages/application/src/genericApplicationService.ts` drop the actor entirely, and item delete and restore pass only the user id. Relation writes carry only `SystemRelationWriteContext` for system-owned properties (`chokePoint/relationEdgeContext.ts`).

This issue adds one additive value, `writerKind`, to all of those paths and to the context of every hook. It builds on nothing. It is the foundation for #1516, #1593, #1713, #1810, #1519, #1802, #1757, #1840, and for the hook issues #1530 and #1601, which always pass it on.

Decisions:
- `writerKind` is `'user' | 'agent' | 'system'`, with optional `agentRunId` and `agentProjectItemId` when it is `'agent'`, and `onBehalfOfUserId` (the user whose session or run made the write) on every `'agent'` value. When a caller supplies nothing the value is `'system'`, the conservative default for internal code.
- A write through `/mcp` with a human session (no run credential) is an `'agent'` write (an MCP client) without `agentRunId` and `agentProjectItemId`, bound to the session's user through `onBehalfOfUserId`. Decided by the product owner: everything written through `/mcp` is written by a tool, and an audit of what Semp or an agent changed must not hide it. Only a human REST session is `'user'`.
- An `'agent'` value without `agentRunId` therefore means an MCP client on a human session. A consumer that needs a run (an approval request, a per-project grant) checks `agentRunId` / `agentProjectItemId`, not `writerKind` alone; this issue changes no approval or grant behavior.
- Confirming an Inbox proposal (`confirmProposalWithClient`) writes as `'user'` for every write in that transaction. An approved agent operation run by the `approvalExecute` job writes as `'agent'` with the approval request's `agentRunId`.
- Hooks already receive `humanWriterUserId`; it stays as it is. `writerKind` is added next to it, not instead of it.
- The item delete and restore entry points accept `writerKind` now, so #1601 can pass it to its hooks without changing signatures again.
- Transform context (#1422): add `writerKind` to it only if that issue has already landed.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `chokePoint/writerKind.ts` exporting the `WriterIdentity` type (`{ writerKind: 'user' | 'agent' | 'system'; agentRunId?: string; agentProjectItemId?: string; onBehalfOfUserId?: string }`) and a `SYSTEM_WRITER` constant; export it from `@semprec/data`.
2. Add an optional `writer?: WriterIdentity` to `CreateItemWithClientOptions` and `UpdateItemWithClientOptions` (`itemWrites.ts`) and pass it, defaulted to `SYSTEM_WRITER`, in the contexts of `runItemCreateHooks` and `runItemUpdateHooks` (add the field to `ItemCreateHookContext` and `ItemUpdateHookContext` in `hooks.ts`). Add the same optional value to the `createItem` / `updateItem` facade methods.
3. In `relationOps.ts` add the same optional value to `createRelationWithClient`, `updateRelationWithClient`, `deleteRelationWithClient` and `assertRelationCreatableWithClient` (new optional trailing parameter or options object, existing positional `context` unchanged) and put it in `RelationEdgeWriteHookContext`. Add it to the facade methods. The transcript speaker validation hook keeps working unchanged.
4. Add the same optional value to `itemDeleteWithClient` options, `restoreItemWithClient` and the `softDeleteItem` / `restoreItem` facade methods in `itemTrash.ts`; it is accepted and carried but not yet consumed (the hooks come with #1601).
5. In `genericApplicationService.ts` derive the value from `AuthenticatedActor` with a single function: an actor with `runId` and `agentProjectItemId` is `agent` (both ids carried); an actor with `restSession` is `user`; any other actor (a `/mcp` call with a human session) is `agent` without run ids. Every `agent` value carries `onBehalfOfUserId` = the actor's `userId`. Pass it in `createItem`, `patchItem`, `deleteItem`, `restoreItem`, `putRelation` and `deleteRelation` (these two now use their actor). The value is never read from a request body: external input schemas stay strict, so a `writerKind` field in a body returns `400`.
6. In the destructive-operation executor path used by the `approvalExecute` job (`genericOperationGateway.ts`, `mcp/approvalRequestExecution.ts`), pass `agent` with the request's `agentRunId`, `agentProjectItemId` and the user of the request as `onBehalfOfUserId` to the data-layer call. In `inbox/proposalActions.ts` pass `user` to the create, update and relation writes in `confirmProposalWithClient`. Internal callers that pass nothing (Inbox tick, mail, transcription, task recurrence, jobs, propagation of inherited values) stay `system` by default; do not edit them.
7. Tests: a hook-context test per write path showing the kind (REST PATCH gives `user`; `/mcp` with a human session gives `agent` without run id and with `onBehalfOfUserId` = the session's user; a generic operation of an agent and `/mcp` with a run credential give `agent` with run id and `onBehalfOfUserId`; Inbox capture gives `system`); Inbox proposal confirm gives `user`; an approved operation executed by `approvalExecute` gives `agent` with the request's run id; `relation.put` and `relation.delete` by an agent reach the edge hook with `agent` and run id; a body containing `writerKind` returns `400`.

## Scope

### In scope

- The `writerKind` value and its threading into item writes, relation writes, delete and restore entry points and the item and edge write hook contexts, with the derivation rules and tests above.

### Out of scope

- Using `writerKind` for any decision: value-link breaking (#1516), link rules (#1593, #1713), grants (#1810), title rule (#1519).
- The new hooks that carry it: pre-write transform (#1422), edge-changed (#1530), delete and restore (#1601).
- A `relation.set` operation (not part of this issue; it will use the same parameter when added).
- A `lastWriter` property stored on items.

## Acceptance criteria

- An item update hook sees `user` for a REST PATCH, `agent` without run id and with the session's user as `onBehalfOfUserId` for `/mcp` with a human session, `agent` (with run id and `onBehalfOfUserId`) for an agent's generic operation and for `/mcp` with a run credential, and `system` for an Inbox capture.
- A request body containing `writerKind` is rejected with `400`.
- Confirming an Inbox proposal writes with `user`; the `approvalExecute` job executing an approved agent operation writes with `agent` and the request's run id.
- `relation.put` and `relation.delete` by an agent reach the edge write hook with `agent` and the agent run id.
- Existing validating edge hooks (transcript speakers) and all existing hooks work without modification.
