## Context

`finishAgentRun` (`backend/packages/data/src/agentRuns/agentRunsStore.ts:135-146`) runs `UPDATE agent_runs SET status = $2, result = $3, finished_at = now() WHERE id = $1` and only checks `rowCount` through `requireAffectedRows`. Nothing restricts the transition to a row that is still `running`, so a second close overwrites the first: `runAgentSession` (`backend/packages/agent-runtime/src/lifecycleAdapter.ts:143-151`) can finish a run as `done` after `repairInterruptedRuns` (`startupRepair.ts:42`) already closed it as `error`, and `DelegationRegistry.expire` / `SempConversation.pause` can flip an `error` run back to `done`. `finishAgentRunWithErrorNotification` (`agentRunsStore.ts:163-186`) documents "an `agent_runs` row finishes at most once" as the reason its notification is keyed on the run id — the store never enforced that.

`insertAgentRunEvent` (`backend/packages/data/src/agentRuns/agentRunEventsStore.ts:46-59`) inserts into `agent_run_events` with no check that the run is still `running` (a late turn-loop write after the run was closed silently extends a transcript that reconstruction and the run watch already treat as complete) and no bound on `payload` (a single `tool_result` can carry an arbitrarily large MCP response into a `jsonb` column that every reconstruction reads back in full).

The terminal `run_status` event is written after the close by design (`lifecycleAdapter.ts:143-144` finishes, then `pushRunStatus(client, run.id, "done")`; `delegationRegistry.ts:246-247` and `sempConversation.ts:236-237` do the same), so that one kind must stay writable on a finished run. `repairInterruptedRuns` (`startupRepair.ts:42-59`) closes the run and then appends a synthetic `tool_result` in the same transaction — that order has to flip.

Sibling issues D2 (delegation registry expiry), D3 (reconstruction), D8 (startup repair transaction) of this batch build on this store contract.

## Task

1. **`finishAgentRun` transitions only a running row and reports whether it did.** In `agentRunsStore.ts`, change the statement to `UPDATE agent_runs SET status = $2, result = $3, finished_at = now() WHERE id = $1 AND status = 'running'` and the signature to `Promise<boolean>`: `true` when `rowCount === 1`. When `rowCount` is `0`, run `SELECT status FROM agent_runs WHERE id = $1` on the same client: no row → throw `NotFoundError` (`backend/packages/data/src/errors.ts`) naming the run id; a row (already `done`/`error`) → return `false`. Update the docstring: a lost race is a normal outcome the caller logs, not an error. Remove the now-unused `requireAffectedRows` import if nothing else in the file uses it.
2. **`finishAgentRunWithErrorNotification` returns the same boolean** and writes the `agent_run_error` notification only when the close won (`true`). On `false` it writes nothing and returns `false`.
3. **Callers log a lost close instead of throwing.** In `delegationRegistry.ts` `expire` and `sempConversation.ts` `pause`, capture the boolean; when `false`, `logger.warn({ agentRunId }, "... run was already finished by another writer")` and still proceed to `pushRunStatus` and entry removal (the row is terminal either way). Do not edit `lifecycleAdapter.ts` or `scheduler/actions.ts` (see Out of scope).
4. **`insertAgentRunEvent` refuses a finished run in the same statement as the write.** Replace the plain `INSERT ... VALUES` with `INSERT INTO agent_run_events (agent_run_id, kind, payload) SELECT $1, $2, $3::jsonb FROM agent_runs WHERE id = $1 AND (status = 'running' OR $2 = 'run_status') RETURNING id, agent_run_id, kind, payload, at`. When no row comes back: `SELECT status FROM agent_runs WHERE id = $1` — no row → `NotFoundError`; a finished row → `ConflictError` with message `agent run <id> is <status>; only run_status events may be appended to a finished run`. `insertAndNotifyAgentRunEvent` inherits both behaviours unchanged.
5. **Payload byte cap.** In `agentRunEventsStore.ts` add a module-private `const MAX_AGENT_RUN_EVENT_PAYLOAD_BYTES = 1024 * 1024;` (1 MiB; documented in the docstring as the bound on one `agent_run_events.payload`, sized so a `compaction` checkpoint — the largest legitimate payload — fits). `insertAgentRunEvent` serializes once (`JSON.stringify(payload)`), measures `Buffer.byteLength(serialized, "utf8")`, and throws `ValidationError` (`errors.ts`) with the kind, the byte size and the cap when it exceeds the cap — before any query. Reuse the serialized string for the insert.
6. **Startup repair order.** In `startupRepair.ts` `repairInterruptedRuns`, move the synthetic `tool_result` append (lines 44-59) before `finishAgentRunWithErrorNotification` for the same run, so the append still targets a `running` row. Update the numbered docstring to match the new order.
7. **Tests** (`*.test.ts`, embedded Postgres):
   - `backend/packages/data/src/__tests__/agentRunsStore.test.ts` (new): `finishAgentRun` on a running run returns `true` and sets `status`/`result`/`finished_at`; a second call with the other status returns `false` and leaves `status`, `result` and `finished_at` untouched; an unknown id throws `NotFoundError`.
   - `backend/packages/data/src/__tests__/agentRunErrorNotification.test.ts`: closing an already-`done` run through `finishAgentRunWithErrorNotification` returns `false`, keeps `status='done'` and writes no `agent_run_error` notification.
   - `backend/packages/data/src/__tests__/agentRunEventsStore.test.ts`: a `message` event on a `done` run throws `ConflictError` and inserts nothing; a `run_status` event on a `done` run is inserted; an event on an unknown run id throws `NotFoundError`; a payload one byte over 1 MiB throws `ValidationError` and inserts nothing, a payload exactly at the cap is inserted. Any existing test that appends an event after finishing the run is reordered to append first.
   - `backend/packages/agent-runtime/src/__tests__/startupRepair.test.ts`: the existing "appends a synthetic tool_result" case still passes with the new order (adjust only if it inspects event order relative to the close).

## Scope

### In scope
- The `status='running'` guard and boolean result of `finishAgentRun`/`finishAgentRunWithErrorNotification`, the two logging call sites, the running-run guard and payload cap of `insertAgentRunEvent`, the startup-repair reorder, and the tests above.

### Out of scope
- `runAgentSession` in `lifecycleAdapter.ts` and `coreAgentRunAction` in `scheduler/actions.ts`: both finish a run they created in the same call, may keep ignoring the boolean, and are owned by #647 and sibling issue D11 of this batch respectively.
- Claiming `busy` in `DelegationRegistry.expire` (sibling issue D2).
- Bracketing `repairInterruptedRuns` with `withTransaction` (sibling issue D8) — this issue only reorders the two writes inside the existing block.
- Truncating oversized payloads at their source (tool results) — an over-cap payload is rejected, not shortened.
- Any new public export (`MAX_AGENT_RUN_EVENT_PAYLOAD_BYTES` stays module-private so `publicSurface.test.ts` is untouched).

## Acceptance criteria

- When `finishAgentRun` is called twice for the same run (`done` then `error`, or the reverse), the row keeps the first status, result and `finished_at`; the first call returns `true`, the second `false`, and no exception is thrown.
- When `finishAgentRunWithErrorNotification` loses the close, no `agent_run_error` notification row is written for that run.
- When `DelegationRegistry.expire` or `SempConversation.pause` finds its run already finished, it logs a warning, still records the `run_status` event and removes the in-memory entry.
- When `insertAgentRunEvent` is called with any kind other than `run_status` for a run whose status is `done` or `error`, it throws `ConflictError` and `agent_run_events` gains no row; a `run_status` event for that run is stored.
- When `insertAgentRunEvent` is called with a payload larger than 1 MiB serialized, it throws `ValidationError` naming the size and cap, and nothing is written.
- When `repairInterruptedRuns` finds a running run whose last event is a `tool_use`, the synthetic `tool_result` is stored and the run is closed as `error` in one committed transaction.
