## Context

Model tier rationale: Adds a relation property to a schema-locked system database in populated tenants through hand-written SQL cutover, which must be idempotent, tenant-scoped and consistent with fresh-install seeding.

A journal entry should be linkable to a project (for example "linking this note to the project Half marathon"), and a project's related items should be able to include its journal entries. Today Journal has only the `area` relation (to Areas, many-to-many, no inverse) and no relation to Projects (`backend/packages/data/src/seed/seedTenDatabases.ts`). Journal is schema-locked, so `createRelationPropertyWithClient` is refused; populated tenants receive such a property through a per-tenant cutover migration that inserts the property, relation definition and config with direct SQL, as `backend/packages/data/src/transcription/transcriptsCatalogCutoverMigration.ts` does for `Transcripts.speakers`, run per tenant by `runTenantCutoverMigrations` (`backend/packages/data/src/db/tenantCutoverMigrations.ts`). Plain SQL migrations that insert properties are not a pattern here, because tenant ids are now mandatory on every insert.

The relation is written by the user and by the confirmation of a journal proposal (#1981); #1839 counts it for the project's related collections; #1609 adds the sibling relation to Events through the same path; #1726 uses it when merging duplicate entries.

Decision: the relation is user-owned, many-to-many and one-directional (like `area`), so no inverse property is created on Projects.

Shared-file ordering: this issue also waits for #1542 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `canonical-keys` and `testing`.

1. In `seedTenDatabases.ts` declare the relation `project` on Journal, target Projects, `many_to_many`, owner user, no inverse, right after the `area` relation.
2. Add `journalProjectCutoverMigration.ts` (journal module) and call it from `runTenantCutoverMigrations`: in the tenant's scope, with the properties table locked as the Transcripts cutover does, skip when Journal or Projects is missing, skip when the `project` property already exists, otherwise insert the property, the relation definition and its config with direct SQL, mirroring the three steps of the Transcripts cutover. Running it twice changes nothing.
3. Add the i18n labels `property.journal.project.name` to `seed/i18n/cs.json` ("Projekt") and `seed/i18n/en.json` ("Project").
4. Tests: a populated tenant without the property gets it after the cutover and the relation definition points at Projects; a second run changes nothing; a fresh seed creates the same shape; `relation_contains` filter on `project` returns the Journal rows linked to a project; the schema in Czech returns the label "Projekt".
