**Blocked by:** #1459, #1551
**Model tier:** medium

## Context

Model tier rationale: One read endpoint that renders stored problems into localized text and source-dependent actions with existing route-registration and isolation fixtures; it writes nothing, but the per-kind rendering table is wide, so the tests must cover every kind.

The Semp status view shows problems as cards: a title, a sentence of explanation, since when, how many reports were merged, and actions such as "Sign in again" and "Details" for a mailbox, or "Try again" and "Open chat" for a failed task. Today the only status endpoint is `GET /api/system-health` (`backend/packages/data/src/observability/systemHealthReport.ts`, registered as a `single-consumer-read` custom route in `backend/packages/data/src/chokePoint/schemaCoreModuleManifest.ts`), a technical snapshot of processes, queue depth, mailboxes and error counters. It has no user-facing problems, no text and no actions. Notification titles are rendered when written, from the catalog in `backend/packages/data/src/notifications/i18n` (`notify.ts`).

This issue serves the stored problems (#1459) as the first part of `GET /api/semp-status`. Text is rendered when the status is read, in the locale of the tenant's user, from the stored kind and source, so changing wording or locale applies to existing problems and the database holds no user text.

Later issues extend the same response additively: resolved problems of the last seven days (#1919), the services list (#1561) and a problem derived from a missing or exhausted AI budget (#1871). The lightweight summary and chat banner are #1631.

Decision: the task name in "Semp did not finish the task" is the title of the thread the failed reply belongs to (the thread's stored title); when it is empty, the card text omits the name. The text of the message itself is never used.

Decision: the cause of a run or reply failure is rendered from the stored error code of the run or message (#1446, #1907), not from raw text; if no code is available the text is generic.

Decision: the actions are descriptors, `{ kind, target }`. Their targets are ids; the operations they point to are separate endpoints. Kinds: `reauthMailbox` (mailbox id; #1742), `retryRun` (id of the last failed run of the heartbeat's retry chain, read when serving; #1908), `retryPrompt` (message id; #1926), `retryTranscription` (transcript id; `POST /api/transcriptions/:id/rerun`), `openChat` (`{ threadId, messageId }`), `openThread` (thread id of the tick), `openProject` (project item id), `disableHeartbeat` (heartbeat id; executed by the client through `PATCH /api/heartbeats/:id` with `{enabled: false}` from #1551). The system never disables a failing automation itself; the `disableHeartbeat` action lets the person do it (decided by the product owner). Actions carry no text; the client catalog renders their labels (for `disableHeartbeat` cs "Vypnout", en "Disable").

Shared-file ordering: this issue also waits for #1551 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `io-hardening`, `canonical-keys`, `error-handling` and `testing`.

1. Add the custom route `GET /api/semp-status` (name `sempStatus`, justification `single-consumer-read`) to `backend/packages/data/src/chokePoint/schemaCoreModuleManifest.ts` next to the system health route, with `createSempStatusRouteHandler` exported from the same file and mounted in `backend/services/semprec-api/src/routeMatrix.ts`, the route-to-handler mapping of the write-boundary test and the tenant isolation route test.
2. Add `backend/packages/data/src/semp/sempStatusReport.ts`: read the active problems of the current tenant ordered by severity (`critical` first) and `last_seen_at`, and return `{ activeCount, problems }` where each problem is `{ id, category, severity, title, text, shortText, since, mergedCount, projectName, source { table, id }, affectedService, actions }`. `since` is `first_seen_at`, `mergedCount` is `occurrence_count`, `projectName` is the name of the project item when present, `affectedService` is the category-derived service key (`mail`, `agents`, `calendar` reserved, `transcription`, `backup`, `guidance`, `automation`).
3. Render `title`, `text` and `shortText` (a shorter impact sentence for the banner) per `kind` from new i18n catalogs `backend/packages/data/src/semp/i18n/status.cs.json` and `status.en.json` (or the catalog structure used by the notifications catalog), in the locale of the tenant's user. Parameters come from the source (mailbox name, connector name, thread title, project name); user-controlled values are passed as parameters, never as keys. Build the actions per kind as listed above. A heartbeat problem (`agentHeartbeat`, dedupe key `agents:heartbeat:<heartbeatId>`) gets `disableHeartbeat` with the heartbeat id in addition to `retryRun` and `openThread`, but only when the heartbeat is a user heartbeat (origin marker of #1438, not `system`) and is currently enabled; read both in the same batched lookup as the other source data.
4. Fetch what the rendering needs for all problems in a few batched queries, not one per problem.
5. Tests: a problem merged from 4 reports returns `mergedCount` 4 and the `since` of the first; no title or text contains a raw error string; a failed chat reply problem returns `retryPrompt` with the message id and `openChat` with the thread and message id; a heartbeat problem returns `retryRun` for the last run of its chain and `openThread`; a heartbeat problem of an enabled user heartbeat returns `disableHeartbeat` with the heartbeat id, and one of a disabled or a system heartbeat has no `disableHeartbeat`; every kind renders in Czech and English; with no problems the response is `activeCount` 0 and an empty list; another tenant's problems are never returned; the number of queries does not grow with the number of problems.

## Scope

### In scope

- `GET /api/semp-status` returning active problems with localized text and per-source actions.

### Out of scope

- The services list (#1561), problems resolved in the last seven days (#1919) and the budget problem (#1871).
- The summary and banner endpoint (#1631).
- Executing any action; the operations behind `reauthMailbox`, `retryRun`, `retryPrompt`, `retryTranscription` and `disableHeartbeat` (#1551) are separate endpoints.
- Producing problems (#1911, #1465, #1931, #1506) and the realtime invalidation (#1868).

## Acceptance criteria

- When a mailbox problem was merged from four reports, then the response has `mergedCount` 4 and `since` of the first report, and neither `title` nor `text` contains the raw provider error.
- When a chat reply failed, then its problem has the actions `retryPrompt` with the message id and `openChat` with the thread id and message id.
- When a heartbeat tick failed after retries, then its problem has `retryRun` targeting the last failed run of the chain, `openThread`, and, for an enabled user heartbeat, `disableHeartbeat` with the heartbeat id; the heartbeat itself stays enabled until the person uses that action.
- When there are no active problems, then `activeCount` is 0 and `problems` is empty.
- When the tenant's user locale is English, then all texts are English; no problem of another tenant is returned.
