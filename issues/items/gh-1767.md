## Context

Model tier rationale: A multi-write transaction (task, relation, state row) guarded by an idempotency key and a row lock, with an undo that must not resurrect or double a task, across the transcript, Tasks and People seams and a new cross-database read; the double-click, undo and trashed-task cases are concurrency and cleanup-ownership problems, so the higher tier is warranted.

Meeting notes (#1695) hold the action items of a recording, and #1754 stores what the user did with each (followed it). This issue lets the user turn one of their own action items into a task of the recording's Event and take it back, and it shows the state of each item and the proposals an Event offers.

Today nothing connects action items to tasks: the Events `actionItems` relation (Events to Tasks) is never filled by anything except a recurring task carrying it forward, and the `computed` cache has no user write path. Item creation supports an `Idempotency-Key` through `insertItemWithReplay` (`backend/packages/data/src/chokePoint/itemsStore.ts`): a replay returns the live item, and a reservation whose item is in the trash or purged is released so the same key creates a new item. That is exactly the double-click and undo behavior wanted here.

This issue builds on #1695 (the notes), #1754 (the state table), #1509 (the tenant's own person, which decides which items are "mine"), #1590 (create an item together with its relations in one write) and #1724 (a task linked to an Event inherits the Event's project and people by rule, so this issue does not copy them).

Decisions:

- By the product owner: undo ("Back" after "Added") soft-deletes the task (30-day trash, so it stays restorable) and clears the state; it does not merely detach the task from the item.
- An item is "mine" when its `ownerSpeaker` is mapped through the transcript's `speakers` edge to the person that is the tenant's own person (#1509); everything else, including an item with no owner, is not mine. The task route itself does not refuse another person's item (the client decides what to offer).
- By the product owner: the Event's proposals list offers only items that are open and either mine or without an owner. Another person's item is never offered there, because it belongs to that person. The transcript detail endpoint and this list use one shared function, so the two cannot disagree.
- `added` is only reported while the task is alive; a task deleted or purged elsewhere makes the item `open` again on the next read, and a new task can then be created (the old idempotency reservation is released by the store).
- Following an item (`noted`) does not block adding it: adding replaces the `noted` state.

Shared-file ordering: this issue also waits for #1765 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `canonical-keys`, `error-handling` and `testing`.

1. Add `backend/packages/data/src/transcription/transcriptActionItems.ts` with `listTranscriptActionItems(client, transcriptId, locale)`: the rendered action items of a transcript (use `renderMeetingNotes` from #1695) joined with the stored states, each as `{ id, text, ownerSpeaker, ownerLabel, due, startsAt, state, taskId, isMine }` where `state` is `open | added | noted | dismissed` and `taskId` is set only for `added` with a live task.
2. Return that list as the transcript's `meetingNotes.actionItems` in the detail endpoint (#1576, `transcriptDetail.ts`).
3. Add `POST /api/transcripts/:id/action-items/:actionItemId/task` with body `{ name?, date? }` (custom route of the systemDatabases module, justification `transactional-semantics`). In one transaction: lock the transcript row; read the state row; if the state is `added` with a live task, return it unchanged (`200 { taskId }`); otherwise create the Tasks item `{ name: name ?? the item's rendered text, date: date ?? due, status: "notDone" }` with the `sourceEvents` relation to the transcript's live linked Event when there is one (a transcript without an Event gets a task without that relation), using the relation-aware create from #1590 and the idempotency key `transcript-action-item:<transcriptId>:<actionItemId>`; then upsert the state row as `added` with `task_item_id` and `owner_person_id`. Return `201 { taskId }` for a created task. A non-UUID id or non-integer index is `400 validation_failed`; unknown, foreign or out-of-range ids are `404`.
4. Add `DELETE /api/transcripts/:id/action-items/:actionItemId/task` (same justification): in one transaction with the transcript row locked, when the state is `added`, soft-delete the live task through the choke point (`itemDeleteWithClient`) and delete the state row; when the state is anything else, change nothing. Always `200 { actionItemId, state }` with the resulting state (`null` or `noted`). It is idempotent.
5. Add `GET /api/events/:id/transcript-action-items` (custom route of the systemDatabases module, justification `single-consumer-read`): over every live transcript linked to the Event through Transcripts `event`, return `[{ transcriptId, actionItemId, text, ownerSpeaker, ownerLabel, due, startsAt, state }]` for the items that are `open` and mine or without owner, ordered by transcript `date` then item id. An unknown, foreign or trashed Event is `404`; an Event with no transcript returns `[]`.
6. Register the three routes in `systemDatabasesModuleManifest.ts` (with the handlers re-exported in its export block), `routeMatrix.ts`, `tenantIsolationRoutes.test.ts` (case table and request list) and the handler mapping of `chokePointWriteBoundary.unit.test.ts`.
7. Tests in `backend/packages/data/src/transcription/__tests__/transcriptActionItems.test.ts`: task created with `date` 2026-10-23, the Event relation and the inherited project; two concurrent identical POSTs create one task; the task is trashed elsewhere and the item reads `open`, then a new POST creates a new task; undo trashes the task and clears the state, a repeated undo is a no-op; adding a followed item; a foreign tenant's transcript and Event return the same 404 as unknown ones; the proposals list excludes an item whose task exists, a followed item and another person's item, and includes mine and unowned ones.

## Scope

### In scope

- Creating and undoing a task from an action item, the item state in the detail response, and the Event's proposals list.

### Out of scope

- The `noted` (follow) write and the state table: #1754.
- Copying the project and people from the Event to the task: the rule of #1724 does it when the relation is written.
- What Semp does with followed items: not in v1 (decided by the product owner; the state is only stored, #1754).
- Offering other people's items, or items of clients, in the proposals list: not done (decided by the product owner).
- Creating tasks from transcripts of recurring-event occurrences that are not materialized yet (#1850).

## Acceptance criteria

- When the user adds the item "Send the revised offer" due 2026-10-23, a task with that name and date `2026-10-23` exists, linked to the recording's Event, with the Event's project; calling the route twice, even at the same time, leaves one task.
- When that task is deleted in the Tasks view, the transcript detail shows the item as `open`, and adding it again creates a new task.
- When the user undoes the addition, the task is in the trash for 30 days and the item reads `open`.
- When a transcript has no linked Event, the task is created without an Event link.
- The Event's proposals list contains no item that already has a live task, no followed item and no other person's item.
- A foreign transcript or Event answers exactly like an unknown id.
