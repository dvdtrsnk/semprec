## Context

Model tier rationale: One known mechanism (raise and resolve a problem inside existing transcription transaction paths) plus a tenant-scoped queue count in the services list, over existing fixtures; the tenant filter on the queue is the only sharp edge and has a pattern to copy.

A meeting transcript that fails permanently should show up in the Semp status view, with a "Try again" action, and disappear into the resolved history when a rerun succeeds; the Meeting transcripts service should show how many jobs are waiting and running. Today `recordTranscriptionFailure` (`backend/services/semprec-transcribe/src/transcriptionTask.ts`) sets `item_automation.status` to `error`, patches the transcript's `status` to `error` and writes an `automation_error` notification in the transcription transaction. Nothing raises a problem, nothing closes one on success (`runFinalizeStep`), and nothing exposes the transcription queue to the user. Transcription jobs run in the tenant lane `transcription:<tenantId>` (`backend/packages/data/src/transcription/transcriptionJob.ts`).

This issue builds on the problem store (#1459), the history of resolved problems (#1919, whose title catalog gets the transcription entry here), the stored transcription error code and notification link (#1386), the item delete hook of the choke point (#1601), and the services list (#1561), which it extends with the transcription service. The backfill of existing failures is #1958.

Decision: the problem is `transcription:<transcriptId>` (category `transcription`, kind `transcriptionFailed`, severity `warning`, `source_table` `item_automation`, `source_id` the transcript id). A repeated permanent failure of the same transcript increases `occurrence_count`. This failure is not counted into the `automation:<databaseId>` problem of #1465.

Decision: the successful `finalize` step resolves the problem in the same transaction with resolution kind `recovered`; the resolved title is "Transcript '{name}' completed", with the name read from the transcript at read time. Deleting the transcript resolves its problem with `sourceDeleted` through the delete hook of #1601, so it is not listed in history.

Decision: the service entry is `transcription` with `detail` `{ queued, running }`, counting only the caller's tenant: jobs of the `transcriptionJob` task whose envelope `tenantId` is the tenant, unlocked for `queued` and locked for `running`, read from the queue tables the same way the system health report counts tenant jobs. `state` and `since` come from the active transcription problem.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. In `recordTranscriptionFailure`, after the notification write and in the same transaction, call `raiseProblem` with the key and fields above for a permanent failure (use the attempt count as `occurrenceKey`, like the notification's transition instance).
2. In `runFinalizeStep`, in the same transaction that sets the transcript to `done`, call `resolveProblem` for `transcription:<transcriptId>` with `recovered`.
3. Register a resolve with `sourceDeleted` in the transcript delete hook of #1601 (the transcripts module's hook registration; confirm the file against that PR).
4. Add the transcription title to the resolution catalog of #1919 (`backend/packages/data/src/semp/i18n/status.cs.json`, `status.en.json`).
5. In `sempStatusReport.ts`, add the `transcription` service to `services`: name from the catalog, `detail` `{ queued, running }` from a tenant-scoped query over the queue tables, `state`/`since` from the active problem.
6. Tests: a permanent failure creates one `transcription:<id>` problem and a second failure raises its count; a successful rerun resolves it in the finalize transaction and it appears in the recent history with the transcript name; deleting the transcript resolves it silently; two waiting jobs of another tenant do not count in `queued`; an active problem makes the service `error` with the problem's `since`; a rollback of the failure leaves no problem.

## Scope

### In scope

- Raising and resolving the transcription problem, its resolved-history title, and the transcription service entry with queued and running counts.

### Out of scope

- The problem store (#1459), the status and history readers (#1555, #1919) and the services list shape (#1561).
- The error code and the transcript link on the notification (#1386).
- The rerun endpoint itself (`POST /api/transcriptions/:id/rerun`) and backfilling existing failures (#1958).
- AI usage breakdown by operation.

## Acceptance criteria

- When a transcription fails permanently, then one active `transcription:<transcriptId>` problem exists; when it fails again, then `occurrence_count` is 2.
- When a rerun finishes successfully, then the problem is resolved in the same transaction as the finalize step and appears in recent history with the transcript's name.
- When the transcript is deleted, then its active problem is resolved and not listed in history.
- When another tenant has queued transcription jobs, then they are not counted in this tenant's `queued` or `running`.
- When an active transcription problem exists, then the `transcription` service has `state` `error` and the problem's `since`.
