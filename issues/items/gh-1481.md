## Context

Model tier rationale: It rewrites a stored encrypted secret during background sync, and a lost or racing rotation permanently breaks the account, so concurrency and failure ordering of the credential write carry the risk.

`refreshAccessToken` in `backend/packages/data/src/mail/oauthTokenExchange.ts` implements only the `refresh_token` grant and returns `{ accessToken, expiresAt }`. Microsoft rotates the refresh token on every refresh and returns a new one; the current code drops it, so after the original token expires the account ends in `needsReauthorization`. Google normally returns no new refresh token, but may.

The stored refresh token is the mailbox's credential in `external_credentials` (`credentials/externalCredentialsStore.ts`: `storeCredential` overwrites the one credential of an item; `getDecryptedCredential` reads it, logging the access). The Gmail and Graph REST clients take a `getAccessToken: () => Promise<string>` function. The sync transports (#1505 and #1508) will build that function; this issue gives them a safe way to refresh and persist.

Decision: when the response carries a new `refresh_token`, it is stored in the same tenant scope before the new access token is used; the previous token is replaced only after the new one is durably written. A failure to persist makes the refresh fail loudly (the old token may already be invalid at the provider, so this is logged and reported, never silently ignored).
Decision: concurrent refreshes of one mailbox are serialized (a transaction with `SELECT ... FOR UPDATE` on the credential row or an advisory lock keyed by mailbox id), and a second caller that waited reuses the freshly rotated token instead of presenting the stale one.

## Task

Load `error-handling`, `state-writes` and `testing`.

1. Extend `AccessToken` with `refreshToken?: string` (present only when the provider returned a non-empty `refresh_token`); parse it from the response; never include any token in thrown messages or logs.
2. Add `refreshAndPersistAccessToken` in `backend/packages/data/src/mail/mailOAuthAccess.ts`: given a pool, the mailbox item id, the provider's token URL, OAuth client id and secret, and scope, it (a) locks the mailbox's credential, (b) reads it with `getDecryptedCredential` (actor `sync_worker`, purpose naming the sync mode), (c) calls `refreshAccessToken`, (d) when a new refresh token came back, stores it with `storeCredential` (type `oauth2_refresh_token`) in the same transaction, (e) returns the access token and its expiry. A 400/401 from the provider still throws `MailReauthorizationRequiredError`.
3. Keep `refreshAccessToken` callable with the same inputs for existing callers and tests.
4. Tests: a response with a rotated refresh token leaves the new token in `external_credentials` and the next refresh uses it; a response without one leaves the stored token unchanged; two concurrent refreshes present each stored token exactly once (fake provider counts); a failing persist throws and the access token is not returned; no token string appears in thrown errors or captured logs.

## Scope

### In scope

- Returning and persisting a rotated refresh token with serialized refreshes.

### Out of scope

- Building the Gmail and Graph sync transports that call it: #1505, #1508.
- The first-time exchange of an authorization code: #1484.
- Reauthorizing a mailbox from the app: #1742.

## Acceptance criteria

- When the provider returns a new refresh token, then `external_credentials` holds it afterwards and the following refresh uses it and succeeds.
- When the provider returns no new refresh token, then the stored credential is unchanged.
- When two refreshes for one mailbox run at once, then the provider sees each token at most once.
- When the provider rejects the stored token with 400 or 401, then `MailReauthorizationRequiredError` is thrown.
- When any step fails, then no token value appears in an error message or log line.
