## Context

Migration `0040_least_privilege_roles.sql` created the two runtime roles and granted every table that existed at the time: full DML on the nine choke-point tables to `semprec_data` and `SELECT` to `semprec_side` (`backend/packages/data/src/db/migrations/0040_least_privilege_roles.sql:58-66`), full DML on every other table to `semprec_side`, which `semprec_data` inherits through `GRANT semprec_side TO semprec_data` (`:47`, `:71-82`). There is deliberately no default-privilege rule for tables: "a future migration that adds a new table ... must extend both grants below in the same migration" (`:51-57`, `:68-70`; also `docs/operations/database-roles.md:41-48`). `0051_module_migration_progress.sql:21` follows that convention.

Two later migrations did not:

- `0043_agent_run_mcp_credentials.sql:16-26` creates `agent_run_mcp_credentials` with no `GRANT`.
- `0045_mail_message_flag_sync_state.sql:5-16` creates `mail_message_flag_sync_state` with no `GRANT`.

Neither role can therefore touch them. `semprec-api` runs as `semprec_data` (`docs/operations/database-roles.md:26`), so in production:

- `POST /api/agent-runs/mcp-credentials` fails: `mintMcpRunCredential` (`backend/services/semprec-api/src/agentRunHandler.ts:79`) inserts into `agent_run_mcp_credentials` (`backend/packages/data/src/mcp/mcpRunCredentialsStore.ts:46`).
- Every bearer-authenticated `POST /mcp` fails. The handler resolves the bearer as a run credential first (`backend/services/semprec-api/src/mcp/mcpHandler.ts:94`, a `SELECT` at `mcpRunCredentialsStore.ts:80`).
- The `mcpRunCredentialExpirySweep` cron (`backend/packages/data/src/worker.ts:91`, `backend/packages/data/src/mcp/mcpRunCredentialExpiry.ts:24`) fails on every tick.
- Every Email `read`/`flagged` patch through the choke point rolls back. The Emails item-update hook (`backend/packages/data/src/domainWriteHooks.ts:13`, `backend/packages/data/src/mail/mailMessageFlagSyncStore.ts:52-60`) inserts into `mail_message_flag_sync_state` inside the write's transaction (`mailMessageFlagSyncStore.ts:29-44`). Mail sync's observation and confirmation writes to that table fail as well.

Integration tests connect as the superuser, so nothing caught this. `backend/packages/data/src/__tests__/leastPrivilegeRoles.test.ts` only checks a few named tables. This issue is one of the pre-existing defects fixed first in the multi-tenancy program. It adds the missing grants and a catalog assertion, so the next table created without grants fails CI.

Both tables are module side tables, like the hook-written `task_recurrence` that 0040 already lists among them. The choke point writes them only through a domain hook, never from `backend/packages/data/src/chokePoint/`. So they get the side-table grant.

Later issues build on this check. #968 and every later migration that creates a table must grant it. #976 later narrows `semprec_side` to `SELECT` on the identity tables.

## Task

Load `db-migrations` (this adds a migration). No other skill applies: no production code changes.

1. **Migration.** Add `backend/packages/data/src/db/migrations/NNNN_grant_late_side_tables.sql`. Take the next free ordinal at commit time and check it with `pnpm --filter @semprec/data run check-migration-numbering`. Content:
   ```sql
   GRANT SELECT, INSERT, UPDATE, DELETE ON agent_run_mcp_credentials, mail_message_flag_sync_state TO semprec_side;
   ```
   The header comment must say three things:
   - Both tables were created by 0043/0045 without the grant 0040's convention requires.
   - Both are side tables, so `semprec_data` inherits access through its `semprec_side` membership.
   - The migration is additive only, so the previous release keeps working against it after a rollback.

   Neither table has a serial column, and `0047_side_role_default_sequence_privileges.sql` already covers future sequences. So no sequence grant is needed.
2. **Catalog assertion.** In `backend/packages/data/src/__tests__/leastPrivilegeRoles.test.ts`, add a `describe("runtime role grants cover every table")`. Declare `CHOKE_POINT_TABLES` as the nine tables from 0040 lines 58-61: `databases, properties, relation_definitions, items, item_relations, views, view_items, idempotency_keys, rollup_dependencies`.
   - Select every table with `pg_class` joined to `pg_namespace`, with `nspname = 'public'`, `relkind IN ('r','p')`, `NOT relispartition` (skips the dynamic `items_p_*` partitions) and `relname <> 'schema_migrations'` (the migrator's own bookkeeping, `backend/packages/data/src/db/migrate.ts:11`).
   - Use `has_table_privilege(role, c.oid, priv)` to assert that every listed table has `SELECT` for `semprec_side`, and `SELECT/INSERT/UPDATE/DELETE` for `semprec_data`, directly or by membership.
   - Assert that every table not in `CHOKE_POINT_TABLES` has `INSERT/UPDATE/DELETE` for `semprec_side`, and that every `CHOKE_POINT_TABLES` table has none of the three for `semprec_side`.
   - Assert that every `CHOKE_POINT_TABLES` entry exists, so a typo cannot silently pass.
   - Collect the offending `table:role:privilege` triples into an array and `expect(...).toEqual([])`, so a failure names them.
3. **Writes through the production paths as the runtime roles.** In the same file, reuse the existing role pools (`:15-41`). Create fixtures through `adminPool`: `createUser` and `hashPassword`, as in `backend/packages/data/src/__tests__/mcpRunCredentialExpiry.test.ts:24-31`.
   - `mintMcpRunCredential(dataPool, { projectItemId: randomUUID(), capabilities: ["core.item.read"], userId })` resolves, and `resolveMcpRunCredential(dataPool, minted.token)` returns its run.
   - `withTransaction(dataPool, (client) => recordDesiredMailMessageFlags(client, messageItemId, { read: true }))` resolves, and `sidePool` reads `desired_state = true` back.
   - As `sidePool`, plain `UPDATE` and `DELETE` statements on rows of both tables succeed.
