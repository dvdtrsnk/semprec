## Context

Model tier rationale: One aggregate read route over existing manifest, route-matrix and tenant-isolation fixtures, applying an already built pure resolver, with strict range validation.

#1792 resolves planned sleep nights from plans, exceptions and settings, but nothing serves them. A client could assemble the result itself only by reading three databases and knowing the tenant's time zone, which the generic item endpoints do not expose. Custom module routes are allowed only with a stated justification (`backend/packages/module-registry/src/manifest.ts`, decision record `2026-09-11-module-manifest-custom-routes`) and must be listed in `backend/services/semprec-api/src/routeMatrix.ts`; `transactional-semantics` covers an aggregate read outside the item model.

This issue adds `GET /api/sleep/nights`, the one read the app needs for the sleep card, the night view and the iPhone schedule. Later issues build on it: relating the settings to an area adds `areaId` to the response (#1833), the PUT route for one night returns the same night shape (#1835), and the agent tools for sleep nights reuse the same loader function (#1840).

Decision: the justification for the custom route is `transactional-semantics`: the response is an aggregate of plan, exception, settings and the tenant's time zone, not an item. If the settings item does not exist (the tenant has no sleep module), the route answers 404.

Shared-file ordering: this issue also waits for #1807 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `io-hardening` and `testing`.

1. In `backend/packages/data/src/sleep/sleepRouteHandlers.ts` (new) add a function `loadSleepNights(client, { from, to })` that reads the settings item, the non-deleted plans and the non-deleted night items in the range, reads the zone with `getSystemTimezone`, calls `resolveSleepNights` and returns the response object below; export it for reuse by agent tools. Add the route handler `sleepNightsGet`.
2. Query parameters `from` and `to` are required `YYYY-MM-DD` dates; `from` must not be after `to` and the range may contain at most 62 nights; otherwise `400 validation_failed` with `field` `from` or `to`.
3. Response: `{ enabled, showInCalendar, muteSemp, alarmSound, alarmSnooze, timezone, planCount, goalMinutes, nights: [{ night, planId, planName, bedTime, wakeTime, alarm, changed, bedAt, wakeAt, durationMinutes, prepReminderAt }] }`; `planCount` is the number of non-deleted plans; the nights are those of the resolver for the range. When `enabled` is false the nights are still computed.
4. Declare the route in `backend/packages/data/src/sleep/sleepModuleManifest.ts` (`customRoutes` entry `GET /api/sleep/nights`, `handlerExport: "sleepNightsGet"`, `justification: "transactional-semantics"`; the manifest re-exports the handler) and add it to `routeMatrix.ts` (`tenancy: "tenant"`, not public), to `ROUTE_HANDLER_FILES` in `backend/services/semprec-api/src/__tests__/chokePointWriteBoundary.unit.test.ts` and to the cases of `backend/services/semprec-api/src/__tests__/tenantIsolationRoutes.test.ts`.
5. Tests: the acceptance examples below, an unauthenticated call is 401, and a second tenant sees only its own plans and nights.

## Acceptance criteria

- When `GET /api/sleep/nights?from=2026-10-15&to=2026-10-16` is called with the default plans, then it returns two nights: the weekday plan 23:00 to 06:45 with alarm true and the weekend plan 00:00 to 08:30 with `bedAt` `2026-10-17T00:00:00+02:00`, `durationMinutes` 510 and `prepReminderAt` `2026-10-16T23:30:00+02:00`, plus `enabled`, `timezone` and `planCount` 2.
- When `enabled` is false, then the response has `enabled` false and the nights are computed as before.
- When the range spans 63 nights, `from` is after `to` or a date is malformed, then the response is 400 with `field`.
- When another tenant calls the route, then it sees only its own data.
