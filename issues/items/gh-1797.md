## Context

Model tier rationale: This rewrites the persisted `date` of every stored Event for every tenant, bypassing the choke point, with time-zone and daylight-saving conversion and an idempotence requirement, so a mistake corrupts user data at scale.

Events store `date` as a free string, and Events created from a transcript carry it as a UTC instant (`backend/packages/data/src/transcription/transcriptEventMatch.ts`; the transcript date is written by `semprec-transcribe/src/transcriptionTask.ts` as an ISO string from the recording time or upload time). Nothing reads `config.includeTime`. #1416 added `endDate`, `timeFrom`, `timeTo` and `time` to Events, #1598 defines the write-time conversion for new writes, and #1663 validates them. Events stored before that need the same shape.

Data migrations are declared in `dataMigrations` in `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` and run by `runModuleDataMigration` (`backend/packages/data/src/migrationJob/moduleDataMigration.ts`; two-pass, idempotent, direct `UPDATE items` outside the choke point, so no hook, inline derivation or invalidation runs). Events are owned by the `systemDatabases` module, and `module_migrations` is keyed per tenant, module, database key and version pair, so Events has its own version series separate from Tasks. #1414 gives converters the tenant context `{ timezone, itemId, log }`. This issue adds the Events converter 1.0.0 to 1.1.0. The manifest entry is ordered after the Tasks-related data migrations that #1780 adds and after the migrations of other Events-schema owners earlier in the manifest.

The migration bypasses the choke point, so the converter itself computes `time`. No invalidation is sent; clients refetch after the migration. Pending proposal cards from transcripts that hold a date-time are not migrated: they are converted at confirmation through the transition rule of #1598.

Decisions:
- A converted Event with a time gets an end one hour after its start, clipped to `"24:00"`, same as a new Event. Reason: one general rule for every Event, consistent with new Events; there is no default that depends on the Event type.
- Daylight saving follows the rules of #1418 (a non-existent wall-clock moves forward; an ambiguous one takes the earlier offset), through luxon in the tenant zone.

Shared-file ordering: this issue also waits for #1796 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `db-migrations` and `testing`.

1. Add `convertEventDateToWallClock` (for example in `backend/packages/data/src/calendar/eventDateMigration.ts`) as a converter `(properties, context) => properties`, export it, and add a `dataMigrations` entry for `EVENTS_MODULE_ID` from `"1.0.0"` to `"1.1.0"` with that `converterExport` in `systemDatabasesModuleManifest.ts`. Bump the module version as the Tasks entry does.
2. Conversion of `properties.date`:
   - with an offset or `Z` (`"2026-10-16T08:00:00Z"`, `"...+02:00"`): an instant; convert in `context.timezone` to `date` (`YYYY-MM-DD`), `timeFrom` and `timeTo` = start plus one hour clipped to `"24:00"`;
   - with a time and no offset (`"2026-10-16T10:00"`): wall-clock unchanged, same split;
   - date only (`"2026-10-24"`): all-day, so `timeFrom`, `timeTo` and `time` are null and nothing else changes;
   - anything unreadable: return the properties unchanged and call `context.log` with only the item id.
3. The converter computes `time` (`"HH:MM–HH:MM"`, same format as the write-time derivation of #1598; reuse its function) and never overwrites an `endDate`, `timeFrom` or `timeTo` that is already set.
4. The converter is idempotent: converting its own output yields equal properties, so the second pass and any re-run write nothing and leave `updated_at` untouched.
5. Tests with the Europe/Prague and America/New_York tenants, an event on the daylight-saving change day, an unreadable value, a re-run, and the interaction with a locked row in the second pass.

## Acceptance criteria

- When the migration runs for a Europe/Prague tenant, then `"2026-10-16T08:00:00Z"` becomes `date` `"2026-10-16"`, `timeFrom` `"10:00"`, `timeTo` `"11:00"`, `time` `"10:00–11:00"`; `"2026-10-16T10:00"` becomes `timeFrom` `"10:00"`; `"2026-10-24"` stays all-day with no times.
- When it runs for an America/New_York tenant, then `"2026-10-16T14:00:00Z"` becomes `timeFrom` `"10:00"`.
- When a `date` is `"abc"`, then the Event is unchanged and the log entry holds only its id.
- When the migration runs a second time, then no row changes and `updated_at` is unchanged.
