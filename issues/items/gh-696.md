**Blocked by:** #647

## Context

`validateArguments` in `backend/packages/agent-runtime/src/mcpInvokeTool.ts:52-67` calls `ajv.compile(schema)` on a module-level shared `Ajv` instance (line 46, `strict: false`) for every `resolveMcpInvocation` call, where `schema` is `mcp_tool_registrations.tool_schema` — the remote MCP server's own `tools/list` `inputSchema`, stored verbatim by `syncMcpServerTools` (`backend/packages/data/src/mcp/mcpSync.ts:147-152`, after `validateListedTools` at 83-97 which checks only names). Three problems follow from compiling an untrusted schema per call on a shared instance:

- Ajv documents itself as unsafe for untrusted schemas: a `pattern`/`patternProperties` regex with catastrophic backtracking makes every invocation of that tool (and the event loop of the agents process) hang; a remote `$ref` makes Ajv try to resolve it. Nothing bounds the schema's size. The AI gateway already applies the size and remote-`$ref` policy to its caller-supplied schemas (`backend/services/semprec-ai-gateway/src/schemaValidation.ts:11-33`, `MAX_RESPONSE_SCHEMA_BYTES = 64 * 1024`).
- A schema carrying an `$id` is registered on the shared instance by the first `compile`; the second `compile` of the same `$id` throws `schema with key or id "..." already exists`, so from the second call on every invocation of that tool is rejected with "the tool's registered schema could not be compiled".
- Compilation is the most expensive step of validation and is repeated on every call although the schema changes only when a sync updates the registration (`upsertMcpToolRegistration` bumps `updated_at`, `mcpToolRegistrationsStore.ts:92`).

#647 edits `backend/pnpm-lock.yaml`; this issue adds a dependency and lands after it.

## Task

1. **Sync-time schema policy** — new file `backend/packages/data/src/mcp/mcpToolSchemaPolicy.ts` exporting `assertAcceptableMcpToolSchema(schema: unknown): void`, throwing `ValidationError` (fixed messages, never echoing schema content) when:
   - `schema` is not a plain object;
   - `Buffer.byteLength(JSON.stringify(schema), "utf8") > MAX_MCP_TOOL_SCHEMA_BYTES` (`export const MAX_MCP_TOOL_SCHEMA_BYTES = 64 * 1024`, same bound as the gateway);
   - any `$ref` string anywhere in the document does not start with `#` (walk objects and arrays like the gateway's `assertNoRemoteRef`);
   - any string value under a `pattern` key, or any key of a `patternProperties` object, is not accepted by `safe-regex` (`safeRegex(pattern)` false) or is not a valid `RegExp` (`new RegExp(pattern, "u")` throws) — Ajv's own recommendation for untrusted schemas.
   Add `safe-regex@^2.1.1` to `backend/packages/data/package.json` `dependencies` and `@types/safe-regex` to `devDependencies` (run `pnpm install` so `backend/pnpm-lock.yaml` records both).
   In `mcpSync.ts` `validateListedTools`, call `assertAcceptableMcpToolSchema(tool.inputSchema)` per tool; a violation fails the whole sync exactly like a duplicate name does (`ValidationError` → `syncStatus: 'error'`, prior registrations untouched). Extend the function's docstring with the policy.
2. **Compile once per registration version.** In `mcpToolInvocation.ts`, add `toolSchemaUpdatedAt: string` to `McpToolInvocationTarget` (select `r.updated_at` in `resolveGrantedMcpTool`'s query and map it with `toISOString()`). In `mcpInvokeTool.ts`:
   - delete the shared `ajv` instance;
   - add a module-private `Map<string, { updatedAt: string; validate: ValidateFunction | null }>` keyed by `mcpToolRegistrationId`, bounded to `MAX_COMPILED_SCHEMAS = 256` entries with insertion-order eviction (delete the oldest key when inserting past the bound) — LRU-by-insertion is enough here;
   - `validateArguments(target, args)`: on a cache miss or `updatedAt` mismatch, compile on a **fresh** `new Ajv({ allErrors: true, strict: false })` (so an `$id` can never collide across schemas) and store `validate` (or `null` when compilation throws, so a broken schema is not recompiled per call); a `null` entry yields the existing "could not be compiled" rejection.
   - Rewrite the docstring at lines 48-52 (it currently justifies compiling fresh on every call).
3. **Tests**:
   - `backend/packages/data/src/__tests__/mcpSync.test.ts` (integration, contract server): a server advertising a tool whose `inputSchema` has `pattern: "(a+)+$"` → sync records `syncStatus: 'error'` with a fixed message, no registration is written; the same for a `$ref: "https://evil.example/schema.json"` and for a schema over 64 KiB; a benign `pattern: "^[a-z]+$"` syncs normally.
   - `backend/packages/data/src/__tests__/mcpToolSchemaPolicy.unit.test.ts` (new, unit): each rejection branch and an accepted schema.
   - `backend/packages/agent-runtime/src/__tests__/mcpInvokeTool.test.ts`: two invocations of the same registration compile once (spy on `Ajv.prototype.compile` via `vi.spyOn`), a registration whose `updated_at` changed between calls (re-upsert the registration with a different schema) is recompiled and validates against the new schema, and a schema with `$id` validates on both the first and the second call.

## Scope

### In scope
- The sync-time schema policy, the per-registration compile cache, and the tests above.

### Out of scope
- Re-validating schemas already stored before this change (a re-sync applies the policy; no backfill).
- The AI gateway's own schema validation.
- Execution-time re-authorization of approved requests (sibling issue D7b of this batch) — `resolveGrantedMcpTool`'s new field does not change its authorization logic.
- Exporting `assertAcceptableMcpToolSchema` from `@semprec/data`'s barrel (it is internal to sync; `publicSurface.test.ts` stays untouched).

## Acceptance criteria

- When an MCP server advertises a tool whose input schema contains a catastrophic-backtracking `pattern`, a remote `$ref`, or exceeds 64 KiB, "Synchronize tools" fails with a fixed error and no registration is created or updated.
- When the same granted tool is invoked repeatedly without a re-sync, its schema is compiled once; after a re-sync changes the schema, the next invocation validates against the new schema.
- When a tool schema carries an `$id`, every invocation validates correctly (no "already exists" failure on the second call).
- The agents process holds at most 256 compiled schemas.
