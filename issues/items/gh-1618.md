**Model tier:** medium

## Context

Model tier rationale: One known mechanism (a nullable column plus plumbing of one id through four call sites) with existing approval-request fixtures, but it spans a migration, two approval-creation paths and the agent tool composition root.

An approval request is created when an agent calls a destructive generic operation (`preflightDestructiveApproval` in `backend/packages/application/src/genericOperationGateway.ts`) or a third-party MCP tool that requires approval (`createApprovalGatedMcpInvokeTool` in `backend/packages/agent-runtime/src/mcpInvokeTool.ts`). Today the row only knows its `agent_run_id`. It has no link to the tool call (the step in the run) that produced it, because both `execute(_toolCallId, ...)` implementations in `backend/services/semprec-agents/src/agentSessionComposition.ts` discard the id the model runtime provides. A client therefore cannot tell which step of a conversation a request belongs to, and cannot show that step's live outcome after the person decides.

This issue stores the model-runtime tool call id on the request. The structured tool result field that carries the approval request id back into the step is delivered by #1527; together the two let a step be matched to its request in both directions. #1683 (the localisable description), #1728, #1791 and #1889 build on this link. The thread of a request is not stored here: it is derived through the run (`agent_runs.thread_id`).

Decision: the link is one-directional and nullable. Requests created before this change, and requests whose caller supplies no tool call id (any non-agent-session path), keep `tool_call_id` NULL.

## Task

Load `db-migrations`, `state-writes` and `testing`.

1. Add `backend/packages/data/src/db/migrations/NNNN_approval_requests_tool_call_id.sql` (next free ordinal at commit time): `ALTER TABLE approval_requests ADD COLUMN tool_call_id text` (nullable, no default, expand-only per the expand/contract ADR), plus a partial unique index on `(tenant_id, agent_run_id, tool_call_id) WHERE tool_call_id IS NOT NULL` so a redelivered tool call cannot create two requests for the same step.
2. In `approvalRequestsStore.ts` add `toolCallId: string | null` to `ApprovalRequest`, validate it when mapping the row, accept an optional `toolCallId` in `CreatePendingApprovalRequestInput` and write it in `createPendingApprovalRequest`.
3. Carry the id from the agent tool composition root to both creation paths: `execute(toolCallId, ...)` in `agentSessionComposition.ts` passes it to the generic operation agent tool (`packages/agent-runtime/src/tools/generic/genericOperationAgentTools.ts`), which passes it as an optional invocation option to `GenericOperationGateway.invoke` and on to `preflightDestructiveApproval`; for MCP tools it passes it as an option to the function returned by `createApprovalGatedMcpInvokeTool`. REST and the `/mcp` handler pass nothing.
4. A repeated creation for the same `(agentRunId, toolCallId)` returns the existing pending request instead of failing or inserting a second row (the notification keeps its existing dedupe on `transitionInstance`).

## Scope

### In scope

- The `tool_call_id` column, its unique index, the store type and the plumbing from `execute` to both `createPendingApprovalRequest` call sites.

### Out of scope

- Returning the approval request id as a structured field of the tool result: #1527.
- Storing the localisable description and impact on the request: #1683.
- Exposing `toolCallId` or the request id to clients on step reads: #1887.
- Backfilling `tool_call_id` for existing rows (they stay NULL).

## Acceptance criteria

- When an agent calls a destructive generic operation that needs approval, the created `approval_requests` row has `tool_call_id` equal to the `toolCallId` passed to `execute`.
- The same holds for a call to a granted MCP tool that requires approval.
- A second creation attempt for the same run and tool call id returns the same request id and leaves one row.
- A request created through any path that supplies no tool call id has `tool_call_id` NULL and behaves exactly as before.
- The migration applies on a database with existing approval requests and leaves them readable.
