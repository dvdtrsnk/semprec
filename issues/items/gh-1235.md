**Blocked by:** #1066
**Model tier:** medium

## Context

Model tier rationale: An audit of every write path into `items` against a tenant-isolation rule, plus at most one error mapping and its tests; it touches the isolation contract, so it is above low.

While #1066 was being prepared (branch `mt/1066-tenant-composite-foreign-keys`), its two-tenant test `tenantForeignKeys.test.ts` found an asymmetry. Tenant B inserts an `items` row naming tenant A's database id and gets `23503` on the new `items_database_id_tenant_fkey`. When B names a random UUID instead, the row cannot be routed to any `items_p_*` partition and fails earlier with `23514` (no partition for the value). The composite FK cannot remove this difference, because list partitioning routes the row before any constraint runs. A caller who can observe the raw SQLSTATE can therefore tell "this database id exists in another tenant" from "this id does not exist". That is the existence signal the tenant-isolation ADR forbids (`docs/adr/2026-10-03-tenant-isolation-through-row-level-security.md`).

Whether a production caller can actually observe it depends on the write paths. The choke point's `createItem` resolves the database under row-level security before it inserts (`backend/packages/data/src/chokePoint/itemsStore.ts`, `INSERT INTO items` at the insert helper), and that resolution would already answer both cases with the same not-found. This issue verifies that this holds for every path and closes any gap it finds.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. List every statement in `backend/packages/` and `backend/services/` that inserts into `items` (`grep -rn "INSERT INTO items"`, plus `COPY` and `INSERT … SELECT` into `items`). For each one, record in the pull request description whether its `database_id` comes from a row the caller already read under row-level security in the same transaction.
2. For any path where it does not, resolve the database under row-level security first, inside the same transaction, and answer a foreign or unknown database with the same `NotFoundError` the choke point already uses.
3. Add a two-tenant integration test on the runtime-role pool (`createRuntimeRolePool(adminPool, "semprec_data")`, tenants from `createTestTenant`) for each path changed in step 2. Tenant B naming tenant A's database id and tenant B naming a random UUID must get byte-identical errors, and no row may be written.
4. If no path needs a change, the pull request changes no production code. It adds one test asserting that `createItem` gives identical errors for a foreign and a random database id, and the description records the step 1 audit.

## Touches

- The insert paths found in step 1 that need step 2 (expected: none or few)
- A new or existing two-tenant integration test file for item creation

## Scope

### In scope

- Making a foreign database id and a random one indistinguishable on every item insert path a tenant can reach.

### Out of scope

- Changing the `items` partitioning scheme or `items_database_id_tenant_fkey`.
- Raw-SQL behaviour that only a test or the migrating role can reach.

## Acceptance criteria

- The pull request description lists every `items` insert path and how its `database_id` is resolved.
- Integration: for each tenant-reachable insert path, tenant B naming A's database id and naming a random UUID gets identical errors and writes no row.
