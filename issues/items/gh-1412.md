## Context

Model tier rationale: One additive read-side mechanism across a data-package lookup and the item envelope with existing fixtures, but it must batch blob reads to avoid per-item queries and respect tenant isolation.

The Files gallery shows the size of each file ("2,4 MB") and the cover and photo images need their type. Today the item envelope (`backend/services/semprec-api/src/adapter/itemEnvelope.ts`, `toItemEnvelope`) returns `properties` as stored, so a file or image property is only `{ blobId }`. The `blobs` table has `byte_size` and `mime_type` (`packages/data/src/blobs/blobsStore.ts`, `BlobRow`), but the envelope does not return them, and a client would need one `GET /api/blobs/:id` per item to learn the size. The blobs table has no filename column; the upload's sanitised name lives only in the storage key (`<prefix>/<uuid>-<safe filename>`, built in `ingestUploadedFile`).

Decisions:
- The metadata is a new additive top-level field `blobs` on the item envelope; `properties` is unchanged. It is keyed by property key and covers every property of type `file` or `image` (including `cover` and `photo`) that holds a `blobId` the caller can see.
- `filename` is derived from the storage key (the part after the `<uuid>-` prefix) and is `null` when the key does not follow that shape. No schema change is made.
- The field is omitted (not an empty object) when the item has no file or image property with a blob.

Builds toward #1518, whose inline relation expansion returns the same envelope for related items.

## Task

Load `testing` and `io-hardening`.

1. Add `backend/packages/data/src/blobs/blobMetadata.ts` exporting `loadBlobMetadataForItems(client, items)`: collect the `blobId` of every `file`/`image`-typed property across the given items (property types resolved from the items' databases), fetch the matching `blobs` rows in one query under the caller's tenant scope, and return, per item id, `{ [propertyKey]: { blobId, byteSize: number, mimeType, filename: string | null } }`. A blob id that is not visible or no longer exists is omitted from the map.
2. Extend `ItemEnvelope` with an optional `blobs` field of that shape and populate it for the single-item read/write responses and for the database and view query responses (`itemQueryEnvelope.ts`), through one helper so every path shares the lookup. One query per response, never per item.
3. Add the new field to the response schemas and the OpenAPI/route documentation where the item envelope is described.
4. Tests: an item with `file` returns `blobs.file.byteSize`, `mimeType` and `filename`; an item with `cover` returns `blobs.cover`; a list of 50 items issues a single blob query; an item without blob properties has no `blobs` key; a blob from another tenant never appears.

## Scope

### In scope

- The `blobs` metadata field on item envelopes and query results for file and image properties.

### Out of scope

- Thumbnails or previews (#1965 computes attachment metadata and thumbnails for Inbox attachments).
- Storing a filename column on `blobs`.
- Returning the metadata inside `relation.list` or `include=relations` results (#1518 reuses this field).

## Acceptance criteria

- When a Files item with an uploaded file is read, then the envelope has `blobs.file.byteSize` equal to the stored size, plus `mimeType` and `filename`.
- When a Library item with a `cover` image is read, then `blobs.cover` is present with the same fields.
- When a query returns many items, then the blob rows are fetched in one query.
- When an item has no file or image blob, then the envelope has no `blobs` field and `properties` is unchanged.
- When a blob belongs to another tenant, then it never appears in `blobs`.
