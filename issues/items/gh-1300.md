## Behavior specification

Collection counts, facets, filters, sorting and related filters.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: collection-query-1

#### (a) Adopted decisions

- Does a count include finished-today tasks (badge 7 vs 8)? -> Decided by the product owner: no; the badge counts only open tasks for today (7), because a badge says what is left to do, as the overview does. `item.count` uses the open-only Today filter of #1798. (#1709)
- Last 7 / last 30 days: D-7/D-30 (design, 8 and 31 days) or D-6/D-29? -> Decided by the product owner: D-7..D and D-30..D including today (8 and 31 calendar days), the same in every collection. (#1522)
- Weeks start Monday, all boundaries inclusive -> as in the design note.
- Is totalCount opt-in? -> Yes, `includeCount: true`; ignores limit, cursor, sort; excludes soft-deleted unless `inTrash` -> keeps existing responses and cost unchanged.
- totalCount for a curated view -> number of live members -> a curated view has no filter.
- Facets for views? -> Decided by the product owner: passing the view's filter is enough; only `database.facets`, no special operation. (#1759)
- Facet condition on its own property inside or/not -> 400 field filter -> as the design note specifies.
- Counts of archived databases' items -> Decided by the product owner: an archived database is in the trash, so its items count neither in counts nor in facets; counts match what the user sees. (#1709, #1759; #1359 is not a dependency here)
- Text/URL collation: cs-x-icu for locale cs, und-x-icu otherwise, closed allow-list; ICU collations created on deploy if absent in the image.
- Select option order: values not in options sort with empty values at the end, ties by id.
- Catalog cutover only reorders (keeps option objects, appends unknown stored keys); People order [client, closeFriend, parent, girlfriend, therapist, neighbor, colleague, craftsman, doctor], confirmed by the product owner and defined once in the People relationship options. (#1578)
- Numeric comparisons: stored non-number never matches and never errors (guard with jsonb_typeof).

#### (b) Open questions for the product owner

- Exact shape of the collection filter declared in manifests is owned by the manifest issue; `item.count` `collection: true` only consumes it.

#### (c) User-visible behavior

Collections show accurate numbers without loading every item: the overview shows how many items each collection holds in one request, a collection header shows "N items" after filters, and project and company rows show their task and people counts. The filter sheet shows next to each choice how many items would remain if it replaced the current selection (including zero for status-like choices), board columns show how many cards they hold, and a list can ask for a total count independent of paging. Date filters understand today, this week, upcoming, last 7 days and similar presets in the user's time zone, numeric filters compare time and rating thresholds, statuses sort in their meaningful order, and names sort by the Czech alphabet with stable paging.


### Decisions: collection-query-2

#### (a) Adopted decisions
- Does the indirect filter need "only active projects"? -> No third parameter; callers combine the condition with `and` and a project filter. Reason: conservative, keeps the condition minimal; soft-deleted intermediates never match.
- Is Events.area only for events without a project? -> Yes, as product intent, but the relation itself is unrestricted in this chunk; enforcement is the write-rejection issue (#1662). Reason: the design note confirms it follows the design; avoids duplicating that issue.
- Key collision with derived area? -> None: Events.area is the stored own area, derived area is a read-time value. Reason: per design note.
- Edges to soft-deleted targets in relation_is_empty -> do not count. Reason: design note acceptance criterion.
- Tasks area filter -> project path only (task without project in no area).
- New task from an area-filtered list -> Decided by the product owner: the form pre-fills the area and requires choosing one of the area's projects (one is pre-selected), because a task's area is derived from its project and a task without one would vanish from the list. This is client behavior; the backend already offers the area's projects (the Projects area filter of #1597) and saving the task with its project (#1590), so no issue is added.
- Should area-filtered lists exclude archived (not deleted) projects? -> Decided by the product owner: yes by default, and they can be shown with a filter as elsewhere: #1597 adds a Projects area filter that the client combines with the Projects quick filters (default "Active" hides archived). The area filter itself does not test project status.

#### (b) Open questions for the product owner
- Issue 03 expresses the manifest areaFilter as a template with an area-value slot; the exact manifest type shape is an implementation choice (flagged for review).

#### (c) User-visible behavior
Opening an area (for example Health) and choosing Projects, Files, Health records or Tasks shows exactly the items that belong to that area: tasks and events through their project, files, health records and events without a project through their own area, and journal entries and companies through their own area. Events without a project can now be assigned to an area. A task without a project appears in no area. Saved views that filter by area keep working when a project moves to another area.
