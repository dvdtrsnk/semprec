### Requirement gh-1575: [library 04/11] Let library automation fill empty user-owned fields

#### Context

Model tier rationale: One contract change touching the job, the heartbeat configuration and an ADR, with an ownership rule that must stay narrow, but with existing fixtures and a known cutover pattern.

The library metadata job (`backend/packages/data/src/library/libraryMetadataJob.ts`) is driven by an `action_config` stored on two heartbeats per tenant in `project_heartbeats` (one `onItemEvent` trigger and one daily 04:00 retry sweep per library database; built by `metadataActionConfig` in `seed/seedLibraryModule.ts`). Today its schema `libraryMetadataJobConfigSchema` is `{ source, coverKey, secondaryRatingKey?, sourceUrlKey? }` and `LibraryMetadataFetchResult` is `{ cover?, secondaryRating?, sourceUrl? }`. The job writes only these keys, all `owner: system`, through `allowedSystemKeys`. Every config currently has `source: "none"` and the fetcher is a no-op.

Real sources also return the author, the year, the movie/series type and the ISBN. Those properties are `owner: user` (`author` and `type` today, `year` on Movies, and `year`/`isbn` on Books after #1514). Writing a user-owned property from a job would be a second writer under `docs/adr/2026-09-10-single-writer-ownership-model.md`, so the exception must be explicit and narrow.

Decision: an explicit, declared handoff. The library module contract (`library/libraryModuleContract.ts`) names which user-owned keys automation may fill, and the job writes such a key only when the item's current value is empty (missing, null or empty string) and the item's automation state is not `locked`. A value the user entered is never overwritten, and a value filled by automation can be changed by the user afterwards. (The alternative, separate `sourceAuthor`/`sourceYear` system fields shown as `user ?? source`, is not adopted.)

Decision: the config keys for these fields are `authorKey`, `yearKey`, `typeKey` and `isbnKey`, all optional, so a database without a given property (Books have no `type`, Movies no `isbn`) simply omits it.

Fetchers that fill these fields come in #1655 (books) and #1706 (movies).

Shared-file ordering: this issue also waits for #1573 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

Set the source to `openLibrary` for Books and `tmdb` for Movies.
3. In the job, write each user-owned field only when it is in the contract's fillable set, the value is non-empty, the item's current value is empty and the automation row (read `FOR UPDATE`, as the job already does) is not `locked`. System-owned fields keep today's behavior. A provided `type` must be a valid option of the property.
4. Add `backend/packages/data/src/library/libraryHeartbeatConfigCutoverMigration.ts`: for the tenant in scope, rewrite the `action_config` of the Books and Movies library heartbeats (both the trigger and the retry sweep) to the new keys and sources. Idempotent: a tenant already on the new config is untouched; model it on `transcription/transcriptionRequeueHeartbeatCutoverMigration.ts`. Register it in `tenantCutoverMigrations.ts`.
5. Add an ADR `docs/adr/2026-10-25-library-automation-fills-empty-user-owned-fields.md` (see `adr-conventions`) recording the handoff rule, why not a second writer, and the rejected alternative.

### Requirement gh-1708: [library 08/11] Record notFound and error codes and retry them nightly

#### Context

Model tier rationale: One persisted-state change (a CHECK widening plus two columns) and the job and sweep behavior that use it, on existing fixtures, but the migration touches a tenant-keyed table and the error-text rule is security relevant.

`item_automation` (`backend/packages/data/src/db/migrations/0005_library_module.sql`) has `status` (`pending | done | error | locked`), `error` text, `attempts` and `last_attempt_at`; the store is `backend/packages/data/src/library/itemAutomationStore.ts`. The job (`library/libraryMetadataJob.ts`) writes `done` for any run that did not throw, so "the source found nothing" and "the source found something" are the same state, and on failure `markItemAutomationError` stores the exception message, which can contain URLs and secrets. The 04:00 retry sweep (`library/libraryMetadataActions.ts`, `listErroredItemAutomationForDatabases`) retries only `error` rows, so a title that was not found is never tried again.

After #1655 and #1706, fetchers return an outcome (`found | notFound | error`, `errorCode`, `source`). This issue records that outcome and retries what is worth retrying.

Decisions:
- The stored `done` value is kept and means "found" (the response mapping to `found` belongs to #1768); a new status `notFound` is added to the CHECK.
- `notFound` is decided by the source returning no match, not by a missing cover: a user may remove a cover, and a movie can have data without a cover; neither is `notFound`.
- The exception text is never stored or logged; an error code is stored instead.

Unsupported configured sources follow docs/adr/2026-11-05-library-retries-require-a-supported-live-source-config.md: reject through a fixed typed error before producer/sweep/job automation side effects; this recognized configuration refusal is not gh1708 provider failure mapping. Existing legacy queued jobs retain bounded maxAttempts=3; unsupported live config cannot enqueue another daily metadata batch. No new durable status/code/flag is added; corrected live config resumes ordinary retry, and missing TMDB token remains sourceUnavailable.

### Requirement gh-1593: [links 05/12] Propagate inherited values along link rules

#### Context

Model tier rationale: This is the cross-process write engine for inherited values: an after-write hook, a queued tenant-lane job with batching and chained propagation, and system writes into user-owned properties under a new ownership handoff, all of which must stay idempotent, tenant-safe and loop-free.

With the rule declarations from #1411, the link storage from #1403 and the write-time rules from #1516, this issue makes inheritance happen. When a relation edge that joins a target item to a source item is created, the target takes over the source's value and a link row records where it came from. When the source's value later changes, the new value flows to every linked target. When the join edge is removed, the target keeps its value as its own.

Today nothing writes a property from another item. The only item-to-item propagation is the rollup recompute (`rollup/recompute.ts`, jobs keyed per cell) and the journal inbox recompute (`inbox/journalInboxCompute.ts`); both write only into `items.computed`, and only one step. Edge write hooks (`runRelationEdgeWriteHooks` in `chokePoint/hooks.ts`) run before the edge is written, and not at all for deletes, so they cannot observe "an edge now exists"; the dry run of an Inbox proposal (`assertRelationCreatableWithClient`, used in `inbox/proposalActions.ts`) runs them too. #1530 adds a hook that runs after an edge is written or deleted. #1415 lets this issue write as a system writer. Large background work follows `docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`, and jobs run in per-tenant lanes (`tenantLane`).

Decisions:

- Writes made by this issue are system writes with process `valueLinks`; they never change a link's state. The link row is created (state `on`) before the first value write so the handoff check from #1516 passes.
- When a via edge appears and the target already has a value for the rule's target property and no link row, the value is kept as the user's own and no link is created. Only an empty target takes over a value. This also decides the case of a file that already has projects of its own when it is attached to a task.
- A target whose link is `broken` is never written, and a later via edge does not recreate the link.
- A second via edge for a target with an `on` link adds a source and the target becomes the union of all sources' values; union applies to many-valued targets only. For a single-valued target, a source set with more than one value is not inherited: nothing is written and no link is created (an existing link keeps its last value and state).
- Removing a via edge removes that source from the link. Remaining sources recompute the union; with no source left the link row is deleted and the value stays as own.
- Propagation runs along chains (an attachment takes its project from an event and its company from that project), one hop per job. Depth is carried in the job payload and stops at 5; rules are already acyclic.

Shared-file ordering: this issue also waits for #1573 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.
