**Blocked by:** #1535
**Model tier:** medium

## Context

Model tier rationale: One known text-search mechanism (a second text-search configuration plus a parameterised query builder) over the existing index table and the existing Hunspell test harness, with no new authorization or isolation contract.

Czech search has to match without diacritics and capitalisation, match inflected forms ("faktury" finds "Faktura"), and match a word that is still being typed ("odes fak" finds "Odeslat fakturu"), with every word required. Today:

- The text-search configuration `czech` is `unaccent` + `simple` (`0006_mail_sync.sql`). `0046_czech_hunspell_search.sql` rewrites its mapping to Hunspell `cs_cz` then `unaccent` then `simple` once the dictionaries are installed (`deploy/provision.sh` installs them; `db/runMigrationsCli.ts` calls `activateCzechHunspellSearch` on every deploy). Hunspell stores a recognised word as its lemma with diacritics, so an unaccented query term only matches through the fallback, and rows indexed before activation keep fallback lexemes.
- `searchItems` in `mail/search.ts` queries with `websearch_to_tsquery` (AND, no prefix) and has no production caller.
- CI has no Hunspell dictionary; only `__tests__/czechHunspellSearch.test.ts` copies a small `cs_cz` fixture into the `tsearch_data` of its own fresh database (`withFreshDatabase`, `installAssets`).

This issue gives the index one shape: a vector that combines lemma matches and diacritics-free prefix matches, and the query that reads it. It builds on the document builder and vector SQL owner from #1397 and on the People phone numbers from #1535. The search operation (#1842), the collection filter (#1857), the mail sender (#1591) and Semp message indexing (#1783) all use the vector and query defined here.

Decisions:
- One column, one vector: `search_vector = to_tsvector('czech', doc) || to_tsvector('czech_simple', doc)`. Two columns joined by OR would fail a query where one word matches by lemma and another only without diacritics ("faktury koupelne").
- The client-side habit of trimming the last character off long words is not carried to the backend: stemming plus prefix replace it.
- Phone numbers are normalised to digits in E.164 form with default country code 420 in both the document and the query.
- Emails rows keep the old single-configuration vector until #1591 and #1741 move them to the shared shape.

## Task

Load `db-migrations`, `io-hardening` and `testing`.

1. Add migration `backend/packages/data/src/db/migrations/NNNN_czech_simple_search_config.sql` (next free ordinal at commit time) that creates text-search configuration `czech_simple` (`unaccent` + `simple`, the same chain 0006 gave `czech` before Hunspell). It must not depend on or alter `czech`. In the same migration delete the existing `item_search_index` rows of every database that is not an Emails database (derived data; the per-deploy backfill from #1397 rebuilds them in the new shape).
2. Change the vector expression in `search/itemSearchIndexer.ts` (the single owner from #1397) to `to_tsvector('czech', $doc) || to_tsvector('czech_simple', $doc)`.
3. Add `search/itemSearchQuery.ts` exporting a builder that turns user text into a tsquery: sanitise to word tokens (letters and digits only, dropping `& | ! : ' ( ) < > \ *` and other query syntax), build `(to_tsquery('czech', 'w') || to_tsquery('czech_simple', 'w:*'))` per word (OR between lemma and prefix), AND between words, and pass the token list and everything else only as bind parameters (`$N`), never concatenated into SQL. Empty or token-less input yields no match rather than an error.
4. Add `search/phoneNormalization.ts`: normalise a phone to E.164 digits (strip spaces, dashes, parentheses; a leading `+` or `00` keeps the given country code, otherwise prefix `420`). Use it in the document builder for the People `phones` values and in the query builder to join phone-like digit groups ("777 123 456" becomes one token) before tokenising.
5. After a deploy that newly activates Hunspell (`db/runMigrationsCli.ts`: read whether `czech` is Hunspell-backed before `activateCzechHunspellSearch` and treat false-to-true as the transition), enqueue the tenant-wide non-Emails reindex (`enqueueItemSearchBackfill` with `onlyMissing: false`) for every maintained tenant after the queue schema is ready.
6. Tests: in CI without Hunspell, "ucetnictvi" finds "Účetnictví a faktury", "odes fak" finds "Odeslat fakturu", "faktura koupelna" returns only items containing both, "777123456" and "777 123 456" find a person with phone 777 123 456. In `czechHunspellSearch.test.ts` style (`withFreshDatabase`, `installAssets`) with the fixture extended by "koupelna", "faktury" finds "Faktura_2026-10.pdf" and "koupelně" finds "Rekonstrukce koupelny", and a row indexed before activation is found after the reindex. A query containing `& | ! : '` and parentheses runs as plain text and cannot alter the query structure.

## Scope

### In scope

- The `czech_simple` configuration, the combined vector, the sanitised lemma-or-prefix query builder, phone normalisation, and the reindex after Hunspell activation.

### Out of scope

- Page and journal text, the `body` column and snippets: #1658.
- Moving Emails rows to the combined vector, the mail sender, and reindexing existing mail: #1591, #1741.
- Semp message indexing: #1783.
- Calling the query builder from an operation or a collection query: #1842, #1857.
- Adding the People `phones` property itself: #1535.
- Provisioning the real dictionaries in CI.

## Acceptance criteria

- In CI without Hunspell: "ucetnictvi" finds "Účetnictví a faktury"; "odes fak" finds "Odeslat fakturu"; "faktura koupelna" returns only items with both words; "777123456" and "777 123 456" both find the person with phone 777 123 456.
- With the Hunspell fixture harness: "faktury" finds "Faktura_2026-10.pdf" and "koupelně" finds "Rekonstrukce koupelny"; "faktury koupelne" matches an item that has the first word by lemma and the second only without diacritics.
- After Hunspell is activated and the reindex has run, "faktury" finds a row that was indexed before activation.
- Query values only reach the database as parameters: a test with `&`, `|`, `!`, `:`, `'` and parentheses neither errors nor changes matching semantics.
- Existing Emails rows are not deleted by the migration or rewritten by the reindex.
