**Model tier:** high

## Context

Model tier rationale: Regeneration rewrites what the model sees of the conversation (skipping a stored event range, dropping a live session) under races with new messages and compaction, and a wrong refusal rule would repeat tool writes, so it is a cross-process history and concurrency contract.

A user can ask Semp to produce a reply again from the latest answer ("Regenerate"). Today nothing like this exists: the conversation of a thread is rebuilt from `agent_run_events` by `walkStoredEntries` in `backend/packages/agent-runtime/src/conversationReconstruction.ts`, where a `compaction` event replaces all earlier history with its payload, and a live session in the registry (#1565) holds the in-memory history. The REST error contract in `backend/services/semprec-api/src/adapter/errorContract.ts` has no codes for refused regeneration.

After this issue the user can regenerate the latest successful reply of a thread. A new assistant message is queued as the next attempt of the same user message; the replaced answer is removed from what the model sees on later turns. It builds on the changed-item list of replies (#1885), which decides whether a turn wrote anything, and on the queued turn handler (#1727). It uses the `attempt` column and the unique index on (reply, attempt) introduced with the retry endpoint (#1926).

Decision: regeneration replaces, it does not keep versions. The old answer stays readable in the stored messages (with its steps) but is marked as replaced and is invisible to the model; the client shows only the newest attempt.

Decision: regeneration is refused for a turn that wrote anything. A turn with a non-empty list of changed items, or one that created an approval request, answers 409 `regenerate_after_writes`: regenerating only the text without tools is not offered, because repeating the turn would repeat its writes.

Decision: if the thread has written a compaction checkpoint after the replaced turn (an event id above `event_to_id`), the replaced answer is already folded into the checkpoint and cannot be removed: 409 `regenerate_after_compaction`.

Decision: only the latest message of the thread with status `done` can be regenerated, otherwise 409 `regenerate_not_latest`. Regeneration of an older answer (branching) is not offered.

Decision: the regenerated turn sends the original user message again as a new user turn, as the retry does; the duplicate user turn in the model history is accepted. A regeneration counts against the AI budget like any turn.

## Task

Load `state-writes`, `io-hardening`, `db-migrations`, `error-handling` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_semp_messages_replaced.sql` (next free ordinal at commit time): add `replaced_by_message_id uuid` (nullable, composite tenant foreign key to `semp_messages`) so a replaced answer points to its replacement.
2. Add the route `POST /api/semp/threads/:id/messages/:messageId/regenerate` next to the message routes of #1543 (`backend/services/semprec-api/src/sempMessagesHandler.ts`; confirm the file name against that PR). In one transaction under the thread's row lock it checks, in this order: the message is the last message of the thread, an assistant message with status `done` (else 409 `regenerate_not_latest`); its stored `changes` are empty and no approval request is linked to its run range (else 409 `regenerate_after_writes`); no `compaction` event of the thread's conversation has an id above its `event_to_id` (else 409 `regenerate_after_compaction`). It then inserts a new assistant message in the initial status, same `reply_to_message_id`, `attempt` + 1, sets `replaced_by_message_id` on the old message, and enqueues the turn with `enqueueSempMessage` in the same transaction. Answer 202 `{ messageId }`.
3. In `conversationReconstruction.ts` make the reconstruction of a thread skip every event with `agent_run_id` = the replaced message's run AND `id BETWEEN event_from_id AND event_to_id` for each message that has `replaced_by_message_id` set. Retried failed attempts are not skipped. A replaced range must never split a tool call from its result, so skip the whole range or fail the reconstruction check, never part of it.
4. When the replaced message's session is still live in the registry of #1565, drop it, so the next turn wakes a new session from the reconstructed history.
5. Add `regenerate_not_latest`, `regenerate_after_writes` and `regenerate_after_compaction` (all 409) to `ITEM_ERROR_CODES` and `ITEM_ERROR_STATUS_BY_CODE` in `errorContract.ts`, additively. Return `replaced` (boolean) on assistant messages in the history response so the client can hide replaced answers.
6. Register the route in the route matrix and the route-to-handler mapping of the write-boundary test, and in the tenant isolation route test.
7. Tests: regenerating the latest done reply creates attempt n+1 and replaces the old one; in the following turn the model input does not contain the replaced answer (assert on reconstructed messages); a turn that moved a task answers 409 `regenerate_after_writes` and enqueues nothing; a compaction checkpoint written after the turn gives 409 `regenerate_after_compaction`; an older or non-`done` message gives 409 `regenerate_not_latest`; two concurrent regenerations create one new message; the live session of the thread is dropped.

## Scope

### In scope

- The regenerate endpoint, its refusal rules and codes, marking the replaced answer, hiding it from the model's history, and dropping the live session.

### Out of scope

- Retrying a failed reply (#1926).
- Keeping versions of a reply with switching between them, regenerating older answers, and regenerating only the text of a turn that used tools.
- Recording the changed-item list itself (#1885).
- Removing the duplicate user turn from the model history.

## Acceptance criteria

- When the latest assistant message is `done` and made no changes, then regenerating it creates a new message with the next `attempt` and the same `reply_to_message_id`, queues a turn and answers 202.
- When the next turn runs after a regeneration, then the replaced answer is not part of the model input.
- When the replaced turn moved a task or requested an approval, then the response is 409 `regenerate_after_writes` and no job is queued.
- When a compaction checkpoint was written after the replaced turn, then the response is 409 `regenerate_after_compaction`.
- When the message is not the latest or not `done`, then the response is 409 `regenerate_not_latest`.
- When two regenerations of the same message arrive at once, then exactly one succeeds.
