## Behavior specification

Trash: listing, restore, permanent delete and impact.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Execution status: source requirements are routed to the sequential technical delivery program; approval state is recorded on each canonical issue.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: trash-1

#### (a) Decisions adopted from open questions

- Archiving a database: question "archive = trash with deletion after 30 days, or stay reversible without deadline" -> archive is moving the database to the trash, purged RETENTION_DAYS (30) after archiving; a restore before the deadline loses nothing -> the Recently deleted tab and the deletion confirmation already assume a deadline, and the issues for purging and for rollups exist in the plan. Because this changes what database archive means, #1875 includes a new ADR. -> Decided by the product owner: confirmed; archiving is the trash with permanent deletion after 30 days, and a restore before the deadline loses nothing.
- Items trashed before their database was archived: question "delete with the database or finish the remaining retention after restore" -> the item sweep skips them while the database is archived; the database purge deletes them; after a restore they keep their own remaining retention. -> Decided by the product owner: the draft assumption stands.
- Deadline storage: new nullable column `databases.purge_at` set on archive, cleared on restore; archived databases without a deadline get one (now + 30 days) at the start of every sweep run, so no old archive is deleted right after deployment and a rollback cannot leave a database without a deadline forever.
- Purge sweep placement: reuses the existing daily item-purge sweep task (no new task name or crontab entry), items stage first, database stage second, errors aggregated.
- `purgeAt`/`daysLeft` of archived databases are `null` in #1873 and become real in #1875 (the listing is edited again there).
- `daysLeft`: whole calendar days from today to the purge day in the System settings time zone, minimum 0.
- Deleted-by (user or agent) is not stored; recording it needs a column and is not planned. -> Decided by the product owner: not stored; who deleted an item is in the write audit.
- Bulk restore: a refusal (not found, database archived, restore hook 409) is per id; any other error aborts the request.
- Stored `computed` values of deleted rollup properties in other databases are left in place.
- Trashed-page rows (path, title) are left to the pages issue that follows #1851.
- Recipes shown as deleted in the Trash design while live on the Overview -> Decided by the product owner: Recipes is a system module and cannot be archived (only hidden from the overview); the deleted database in the Trash design is a user collection that the design renames, so the sample data matches across screens. No trash issue changes: #1873 never lists a system database.

#### (b) Open questions remaining for the product owner

- A project shown as deleted still appears under its area as Done in the design, while the backend omits deleted items from queries.
- Should a user be able to delete a database or a trashed item permanently on request ("delete now", "empty the trash")? Not planned.
- Ordering needed by the plan (not decidable inside the issues): #1875 edits the listing added by #1873 and should be ordered after it; #1851/#2/#3 all edit the same manifest and route matrix and are ordered after #1837.

#### (c) User-visible behaviour of this chunk (for the epic body)

Recently deleted shows everything the user deleted across all collections in one list, newest first, with where it came from and how many days are left before it is permanently removed (30 days after deleting); deleted databases are listed on their own tab with their number of remaining items and, once the 30-day deadline applies, how long they can still be restored. The user can select several rows of one tab and restore them in one step; if one row cannot come back (for example a Journal day whose period already has an entry), that row stays deleted and the rest are restored. A deleted (archived) database is now permanently removed after 30 days together with its items, relations, blobs and the matching relation properties and rollups elsewhere, while counts on other items stop including the items of a deleted database and come back if it is restored. The nightly clean-up of deleted items no longer logs errors for items that live inside a deleted database.
