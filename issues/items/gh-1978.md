**Model tier:** high

## Context

Model tier rationale: This adds a new proposal kind whose confirm performs a multi-part write (recording request row, attachment move into Files, two queue jobs) in one transaction in a different process than the transcription worker, on top of attachment, upload and pipeline changes from several blockers; it needs an ownership decision (ADR), and getting the transaction or the idempotency wrong would start paid transcriptions twice or never.

A user can share an audio recording into the Inbox (for example from a voice recorder app). Today an Inbox item has no attachment at all, and an audio file uploaded through `POST /api/files` is transcribed at once by the Files create trigger (`core.filesTranscriptionTrigger`, `backend/packages/data/src/transcription/transcriptionActions.ts`), with no parameters. The product wants the opposite for shared audio: nothing is transcribed (and paid for) until the user confirms a card that shows what is known before transcription (length, recording time, source) and lets them set the transcript's name, language, number of speakers, Event and project.

This issue adds that card. Shared audio is an Inbox attachment row (#1564, attached at capture by #1963), so no Files item and no transcript exist before confirmation. The Inbox tick (`semprec.tick`, `backend/packages/data/src/inbox/inboxTickAction.ts`) produces the card; the confirm, which runs in `semprec-api` (`confirmProposalWithClient`), writes the recording request, moves the attachment into Files (#1703) and enqueues the transcription (#1624 created the fast row-creation task and its runner). The parameters the pipeline honors come from #1627 (language, speaker count) and #1696 (project written onto the transcript); the metadata of the attachment (length, recording time) is computed by #1965 when the client does not send it. The card kind stays `inbox`: a second producer of `transcript` cards would break the producer table of `docs/adr/2026-09-23-speaker-mappings-are-edges-proposed-on-transcript-cards.md`.

Decisions:

- The new envelope kind is `transcription`: `target` is the id of the attachment row and `properties` are the recording parameters (see Task). It is an `inbox` card whose source is the Inbox item that holds the attachment.
- By the product owner: only an audio attachment of 120 seconds or longer (`audioKind` `recording`, #1965) gets this card; a shorter one is a voice note, is transcribed into the item text (#1980) and never gets a recording card. This is the threshold decided for Inbox attachments; the routing in the tick that sends only such attachments to this producer is #1985.
- By the product owner: Event choices on the card are the Events of the recording's local day of type `meeting` or `standup` and the Events with no type (Events coming from a calendar have no type and could not be chosen otherwise), plus "no Event". Events of any other type, such as focus work, are not offered. Events whose stored date cannot be read are skipped, never an error.
- By the product owner: the card proposes a name from the usual Inbox proposal computation when the item has text, otherwise a localized default "Recording D. M. HH:mm". It proposes no language (automatic detection), no speaker count and no project.
- By the product owner: the project follows the chosen Event until the user changes it. The card shows the chosen Event's project (from the candidate); a project the user chose explicitly on the card is the recording's own value. On confirm, an envelope `projectId` that is absent or equal to the chosen Event's project is not written into the recording request, so the transcript takes the Event's project as an inherited value when its Event edge is written (#1644, #1697); a different project is written as the recording's own value (#1696).
- Choosing "no Event" simply leaves the Event unset; remembering that explicit decision so that the pairing step creates no Event card is #1986.
- Rejecting the card transcribes nothing and leaves the attachment with its Inbox item.

Shared-file ordering: this issue also waits for #1967 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `canonical-keys`, `adr-conventions`, `db-migrations`, `error-handling` and `testing`.

1. Envelope: extend `ProposalEntityKind` and `assertValidProposalEnvelope` (`inboxTickAction.ts`) with `transcription`. Validation: `target` is an attachment of the card's source Inbox item in the current tenant and its blob is `audio/*`; `properties` has a non-empty `name`, an optional `recordedAt` (ISO 8601 with offset), optional `language` (ISO 639-1), at most one of `numSpeakersExact` (integer at least 1) and `numSpeakersMin` (integer at least 2), an optional `eventId` (a live Events item) and an optional `projectId` (a live Projects item). Unknown keys are rejected. `parseStoredProposalEnvelope` keeps the new properties.
2. Attachment metadata: store the recording time and length on the attachment (`recorded_at timestamptz NULL`, `duration_seconds integer NULL` on `inbox_attachments`, additive migration `backend/packages/data/src/db/migrations/NNNN_inbox_attachment_audio_metadata.sql (next free ordinal at commit time)`). `POST /api/inbox/items` accepts optional `recordedAt` and `durationSeconds` in each `attachments[]` entry (next to `blobId` and `source`); when the client sends nothing, the values computed by #1965 are used. A shared item's source (`share`) is shown on the card.
3. Producer: in the Inbox tick, an Inbox item with an audio attachment gets a card of kind `inbox` with a `transcription` envelope, recognized by the attachment, not by the item's type or processing method (the restriction to recordings of 120 seconds or longer is applied by the routing of #1985). The card's `context` (the property of #1451; add a `recording` variant to its schema) holds `{ role: "recording", candidates: [{ eventId, name, date, timeFrom, timeTo, endDate, projectId, projectName }], recording: { durationSeconds, recordedAt, source } }`. Candidate Events are those of the recording's local day in the tenant's time zone by `date` and `endDate` whose `type` is `meeting`, `standup` or empty; values still stored as date-times are read tolerantly in code (the leading date part), not through the SQL date-range filter, so one malformed Event value cannot fail the query.
4. Confirm: in `confirmProposalWithClient`, a `transcription` envelope is re-validated, then in the same transaction: write the recording request through the shared recording intake function (#1574) with the envelope's name, recording time, language, speaker count, Event and project, where the project is written only when it is set and differs from the chosen Event's project (see Decisions); move the attachment into Files with the rule of #1703 (a Files item with the same blob is linked instead of duplicated); enqueue `transcriptionCreate` and `transcriptionJob` for the resulting Files item (#1624). `resultItemId` is the Files item and `resultLabel` the name. A failed step rolls back all of it and leaves the card `proposed`; confirming twice does not enqueue twice (the existing "confirmed returns as is" rule plus the jobs' keys). The Files create trigger skips this Files item through its recording request row.
5. Reject needs no new code beyond the reject route (#1845); add a test that a rejected recording card starts no transcription and keeps the attachment.
6. ADR: add `docs/adr/<date it is written>-inbox-recording-cards-confirm-into-recording-intake.md` (standalone; reference `[[2026-09-23-speaker-mappings-are-edges-proposed-on-transcript-cards]]`): the Inbox tick is the only producer of the card; its confirm, running in `semprec-api`, writes the recording request, moves the attachment and enqueues the transcription; the transcription worker still creates every `transcript` card and every Transcripts row. Update the ownership-handoff comment in `inboxModuleManifest.ts`.
7. Tests: card created for shared audio of 23 minutes with candidates (a malformed Event date among them does not break the query; an Event without a type is offered, a focus-type Event and a standup of another day are not); a confirm with the chosen Event's project writes no project into the recording request and the transcript later inherits it from the Event, a confirm with another project writes it as own; client-sent versus computed metadata; confirm writes recording request, Files item and both jobs atomically and the transcript later has the chosen name, date and project; validation failures (attachment of another item, non-audio, two speaker counts, Event of another tenant) write nothing.

## Scope

### In scope

- The `transcription` envelope, the card produced for shared audio, the day's Event candidates, and the confirm that starts the transcription with the chosen parameters.

### Out of scope

- The attachment table, the capture endpoint and the move into Files: #1564, #1963, #1703.
- Computing attachment metadata on the server: #1965; routing every Inbox item by the 120-second threshold in the tick: #1985.
- Honoring language and speaker count in the pipeline and writing the project onto the transcript: #1627, #1696.
- Linking the transcript to the chosen Event in the create step: #1644.
- Remembering an explicit "no Event" decision: #1986.
- Cancelling follow-up jobs when a confirmation is undone: #1984.
- Estimating a better name or project from the recording's content before transcription: not done (decided by the product owner).

## Acceptance criteria

- When audio is shared into the Inbox, it is not transcribed until the card is confirmed, and the card shows its length and recording time before any transcription.
- When the card is confirmed with name "Conversation with the electrician" and a project, the resulting transcript has that name, the recording time as its date and that project, and the attachment is in Files.
- When another Event in the tenant has a malformed `date`, the card's Event choices are still produced.
- The card's Event choices include the day's meetings, standups and Events without a type, and no focus-type Event.
- When the card is confirmed with an Event and the Event's project left as shown, the transcript's project is inherited from the Event; when the user chose another project, the transcript keeps that project as its own value.
- When the card is rejected, no transcript is created and the audio stays with the Inbox item.
- When confirm fails midway, no recording request, Files item or job exists and the card stays `proposed`.
