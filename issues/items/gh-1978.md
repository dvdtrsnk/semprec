## Context

Model tier rationale: This adds a new proposal kind whose confirm performs a multi-part write (recording request row, attachment move into Files, two queue jobs) in one transaction in a different process than the transcription worker, on top of attachment, upload and pipeline changes from several blockers; it needs an ownership decision (ADR), and getting the transaction or the idempotency wrong would start paid transcriptions twice or never.

A user can share an audio recording into the Inbox (for example from a voice recorder app). Today an Inbox item has no attachment at all, and an audio file uploaded through `POST /api/files` is transcribed at once by the Files create trigger (`core.filesTranscriptionTrigger`, `backend/packages/data/src/transcription/transcriptionActions.ts`), with no parameters. The product wants the opposite for shared audio: nothing is transcribed (and paid for) until the user confirms a card that shows what is known before transcription (length, recording time, source) and lets them set the transcript's name, language, number of speakers, Event and project.

This issue adds that card. Shared audio is an Inbox attachment row (#1564, attached at capture by #1963), so no Files item and no transcript exist before confirmation. The Inbox tick (`semprec.tick`, `backend/packages/data/src/inbox/inboxTickAction.ts`) produces the card; the confirm, which runs in `semprec-api` (`confirmProposalWithClient`), writes the recording request, moves the attachment into Files (#1703) and enqueues the transcription (#1624 created the fast row-creation task and its runner). The parameters the pipeline honors come from #1627 (language, speaker count) and #1696 (project written onto the transcript); the metadata of the attachment (length, recording time) comes exclusively from the authoritative server ffprobe metadata owned by #1965. The card kind stays `inbox`: a second producer of `transcript` cards would break the producer table of `docs/adr/2026-09-23-speaker-mappings-are-edges-proposed-on-transcript-cards.md`.

#1965 may omit `recordedAt` when no usable `creation_time` exists; #1985 still routes ready long recordings here. As a conservative consequence of the owner's server-only metadata decision, an unknown recording day means empty automatic Event suggestions and, when the item has no text, an editable localized undated default name. This is derived behavior, not a separate explicit owner choice. Manual controls and #1574's existing optional-time intake/date policy remain; no capture/upload/current time is promoted into card context or attachment metadata.

Decisions:

- Owner decision (server ffprobe metadata): #1965 owns recording duration and recording time in `inbox_attachments.metadata`; this issue only consumes that metadata, creates no second metadata migration or columns and accepts no client override, including on confirm.
- The new envelope kind is `transcription`: `target` is the id of the attachment row and `properties` are the recording parameters (see Task). It is an `inbox` card whose source is the Inbox item that holds the attachment.
- By the product owner: only an audio attachment of 120 seconds or longer (`audioKind` `recording`, #1965) gets this card; a shorter one is a voice note, is transcribed into the item text (#1980) and never gets a recording card. The sole boundary definition is `INBOX_RECORDING_MIN_SECONDS = 120`, owned and exported by #1965; this issue consumes its `audioKind` classification. The routing in the tick that sends only such attachments to this producer is #1985.
- Automatic Event suggestions: when authoritative `recordedAt` is present, offer the Events of the recording's local day of type `meeting` or `standup` and the Events with no type (Events coming from a calendar have no type and could not be suggested otherwise). Events of any other type, such as focus work, are not automatically suggested. Events whose stored date cannot be read are skipped, never an error. When `recordedAt` is absent, the recording day is unknown and automatic `candidates` is empty. Existing manual Event/project selection and "no Event" remain supported in both cases.
- Naming: the card proposes a name from the usual Inbox proposal computation when the item has text; otherwise it uses a localized default "Recording D. M. HH:mm" only when authoritative `recordedAt` is present, or the localized undated generic "Recording" when it is absent. The name stays editable in both cases, as do the existing language and speaker-count controls. It proposes no language (automatic detection), no speaker count and no project.
- By the product owner: the project follows the chosen Event until the user changes it. The card shows the chosen Event's project (from the automatic candidate or the existing manual selection); a project the user chose explicitly on the card is the recording's own value. On confirm, an envelope `projectId` that is absent or equal to the chosen Event's project is not written into the recording request, so the transcript takes the Event's project as an inherited value when its Event edge is written (#1644, #1697); a different project is written as the recording's own value (#1696).
- Choosing "no Event" simply leaves the Event unset; remembering that explicit decision so that the pairing step creates no Event card is #1986.
- Rejecting the card transcribes nothing and leaves the attachment with its Inbox item.

Shared-file ordering: this issue also waits for #1967 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `canonical-keys`, `adr-conventions`, `error-handling` and `testing`.

1. Envelope: extend `ProposalEntityKind` and `assertValidProposalEnvelope` (`inboxTickAction.ts`) with `transcription`. Validation: `target` is an attachment of the card's source Inbox item in the current tenant and its blob is `audio/*`; `properties` has a non-empty `name`, optional `language` (ISO 639-1), at most one of `numSpeakersExact` (integer at least 1) and `numSpeakersMin` (integer at least 2), an optional `eventId` (a live Events item) and an optional `projectId` (a live Projects item). Unknown keys, including client-supplied `recordedAt` and `durationSeconds`, are rejected. Manual `eventId` and `projectId` selections remain valid when automatic `candidates` is empty; membership in those suggestions is not a validation requirement, while the live-item and tenant checks still apply. `parseStoredProposalEnvelope` keeps the new properties.
2. Attachment metadata: consume the existing `metadata jsonb` on `inbox_attachments` and the attachment reader supplied by #1965. Use its optional `durationSeconds` (JSON number of seconds from ffprobe), optional `recordedAt` (ISO 8601 timestamp string from the media `creation_time` tag when present) and optional `audioKind` (`voiceNote` or `recording`) without changing their representation or authority. Absent metadata stays absent; this issue adds no fallback value. Do not create another metadata migration, columns or metadata writer, and do not add duration or recording-time inputs to `POST /api/inbox/items`. A shared item's source (`share`) is shown on the card.
3. Producer: in the Inbox tick, an Inbox item with an audio attachment gets a card of kind `inbox` with a `transcription` envelope, recognized by the attachment, not by the item's type or processing method (the restriction to recordings of 120 seconds or longer is applied by the routing of #1985). The card's `context` (the property of #1451; add a `recording` variant to its schema) has the shape `{ role: "recording", candidates: [{ eventId, name, date, timeFrom, timeTo, endDate, projectId, projectName }], recording: { durationSeconds?, recordedAt?, source } }`, with duration and recording time read from #1965 metadata as in Task 2. Its schema permits `candidates: []` and optional `recording.recordedAt` / `recording.durationSeconds`, omitting unavailable fields. When `recordedAt` is present, candidate Events are those of the recording's local day in the tenant's time zone by `date` and `endDate` whose `type` is `meeting`, `standup` or empty; values still stored as date-times are read tolerantly in code (the leading date part), not through the SQL date-range filter, so one malformed Event value cannot fail the query. When `recordedAt` is absent, create the card with `candidates: []` and perform no recording-day lookup. Preserve the usual proposed name when the Inbox item has text; otherwise use the localized dated default only when `recordedAt` is present, and the localized undated generic "Recording" when absent. Keep the editable name, manual Event/no-Event and project selection, language and speaker-count controls in both branches.
4. Confirm: in `confirmProposalWithClient`, a `transcription` envelope is re-validated, then in the same transaction: write the recording request through the shared recording intake function (#1574) with the envelope's name, language, speaker count, Event and project, and the recording time read from the target attachment's #1965 metadata when present (never from the envelope or client). An absent recording time is passed as absent to #1574's existing optional-time intake; confirm must still succeed with the supported manual controls, without adding a timestamp to the attachment metadata or card context. Preserve #1574's downstream Transcripts date policy. The project is written only when it is set and differs from the chosen Event's project (see Decisions); move the attachment into Files with the rule of #1703 (a Files item with the same blob is linked instead of duplicated); enqueue `transcriptionCreate` and `transcriptionJob` for the resulting Files item (#1624). `resultItemId` is the Files item and `resultLabel` the name. A failed step rolls back all of it and leaves the card `proposed`; confirming twice does not enqueue twice (the existing "confirmed returns as is" rule plus the jobs' keys). The Files create trigger skips this Files item through its recording request row.
5. Reject needs no new code beyond the reject route (#1845); add a test that a rejected recording card starts no transcription and keeps the attachment.
6. ADR: add `docs/adr/<date it is written>-inbox-recording-cards-confirm-into-recording-intake.md` (standalone; reference `[[2026-09-23-speaker-mappings-are-edges-proposed-on-transcript-cards]]`): the Inbox tick is the only producer of the card; its confirm, running in `semprec-api`, writes the recording request, moves the attachment and enqueues the transcription; the transcription worker still creates every `transcript` card and every Transcripts row. Update the ownership-handoff comment in `inboxModuleManifest.ts`.
7. Tests: with authoritative `recordedAt` present, a card is created for shared audio of 23 minutes with local-day candidates and, when item text is absent, the localized dated default name (a malformed Event date among them does not break the query; an Event without a type is offered, a focus-type Event and a standup of another day are not). For a valid 23-minute recording with ready metadata but no `creation_time` tag / `recordedAt` and no item text, assert that the card is still created, `context.recording.recordedAt` is omitted, automatic candidates are empty and the localized default name is the undated generic "Recording". Exercise editing the name, language and speaker count, manual Event/no-Event and project selection despite the empty suggestions, and successful atomic confirm with recording time absent through the existing intake; assert no timestamp is written back to attachment metadata or card context. Retain the item-text naming path in both timestamp cases; a confirm with the chosen Event's project writes no project into the recording request and the transcript later inherits it from the Event, a confirm with another project writes it as own; card context and confirm consume #1965 metadata unchanged; absent probe metadata gains no fallback; client metadata overrides in the envelope are rejected; confirm writes recording request, Files item and both jobs atomically and the transcript later has the chosen name and project, with date following #1574's existing policy (the authoritative recording time when present); validation failures (attachment of another item, non-audio, two speaker counts, Event of another tenant) write nothing.

## Scope

### In scope

- The `transcription` envelope, the card produced for shared audio using #1965 metadata, local-day Event suggestions and a dated default name when recording time is known, an undated default name with empty automatic suggestions when it is unknown, preserved manual controls in both cases, and the confirm that starts transcription with the chosen parameters and the authoritative recording time when present.

### Out of scope

- The attachment table, the capture endpoint and the move into Files: #1564, #1963, #1703.
- Computing, storing and classifying attachment metadata on the server, including its schema and the sole 120-second boundary constant: #1965; routing every Inbox item by that threshold in the tick: #1985.
- A second metadata migration or columns, client-supplied duration or recording time, and fallback metadata values.
- Honoring language and speaker count in the pipeline and writing the project onto the transcript: #1627, #1696.
- Linking the transcript to the chosen Event in the create step: #1644.
- Remembering an explicit "no Event" decision: #1986.
- Cancelling follow-up jobs when a confirmation is undone: #1984.
- Estimating a better name or project from the recording's content before transcription: not done (decided by the product owner).

## Acceptance criteria

- Duration and recording time are consumed from #1965's `metadata` fields with their existing representations; this issue adds no metadata migration, columns or writer and no client metadata inputs to capture. A confirm envelope containing `recordedAt` or `durationSeconds` is rejected without writes.
- Classification and the 120-second boundary remain owned by #1965: 119 seconds is `voiceNote`, 120 and 121 seconds are `recording`. This producer consumes `audioKind` through #1985 routing and defines no second threshold.
- When an audio recording is shared into the Inbox, it is not transcribed until the card is confirmed, and the card shows the duration and recording time available from #1965 metadata before any transcription; absent probe metadata gains no fallback or client-supplied value.
- When the card is confirmed with name "Conversation with the electrician" and a project, the resulting transcript has that name, the recording time from the attachment's #1965 metadata as its date when present and that project, and the attachment is in Files.
- When authoritative `recordedAt` is present and another Event in the tenant has a malformed `date`, the card's automatic Event suggestions are still produced.
- When authoritative `recordedAt` is present, the card's automatic Event suggestions include the recording local day's meetings, standups and Events without a type, and no focus-type Event. With no item text, its editable default name is the localized "Recording D. M. HH:mm" based on that recording time.
- When a valid long recording has ready metadata without `recordedAt` (no usable `creation_time` tag), the card is created with `context.recording.recordedAt` omitted and automatic `candidates: []`. With no item text, its editable default name is localized undated "Recording"; no capture/upload/current time is used to invent a recording day or timestamp.
- With or without authoritative `recordedAt`, a name proposed from item text remains supported, and the name, language, speaker-count, manual Event/no-Event and project controls remain usable. Empty automatic suggestions do not reject a live tenant Event or project chosen manually.
- When a recording without `recordedAt` is confirmed with edited name/language/speaker controls and manual Event/project selection, confirm succeeds atomically through #1574 with recording time absent, moves or links the attachment into Files, and enqueues both jobs once. No recording time is added to attachment metadata or card context; the later transcript follows #1574's unchanged optional-time date policy.
- When the card is confirmed with an Event and the Event's project left as shown, the transcript's project is inherited from the Event; when the user chose another project, the transcript keeps that project as its own value.
- When the card is rejected, no transcript is created and the audio stays with the Inbox item.
- When confirm fails midway, no recording request, Files item or job exists and the card stays `proposed`.
