## Context

Model tier rationale: An exhaustive background-task matrix covers registries, queue affinity and tenant fingerprints across three services.

Background work must never move data, notifications or side effects across tenants. Every queue task belongs to exactly one composition root by affinity: `resolveTaskAffinitySets(moduleRegistry)` (`backend/packages/data/src/moduleTasks.ts:43-59`) returns the `api`, `agents` and `transcribe` name sets, built from `CORE_TASK_NAMES`/`CORE_TASK_AFFINITY` (`backend/packages/queue/src/index.ts:29-119`), `AGENT_TASK_NAMES` (`:127-131`) and every module-declared task. The handlers are composed by `createApiQueueRuntime` (`backend/services/semprec-api/src/queueRuntime.ts:55-77`), `createAgentsQueueRuntime` (`backend/services/semprec-agents/src/queueRuntime.ts:37-60`) and `createTranscribeQueueRuntime` (`backend/services/semprec-transcribe/src/queueRuntime.ts:25-39`). Cron-fired sweeps are listed in `CORE_CRONTAB` (`backend/packages/data/src/worker.ts:81-92`).

The blockers made every task tenant-aware: #982 stamps `tenantId` into the job envelope `{traceId, tenantId, payload}` from the enqueuing scope and `TASK_TENANCY` declares every core and agent task `tenant` or `system` (module tasks are `tenant`); system sweeps run in `runAsSystem` and fan out with `forEachActiveTenant` (#983), doing each tenant's work inside `runInTenant`; the remaining blockers converted each task family and added the export (#1043) and purge (#1055) tasks; the credential re-encryption task arrives later with its own case (#1062). Because a package may not import service code and services may not import each other (`backend/dependency-cruiser.rules.json`, rules `core-knows-nobody` and `no-service-to-service`), the proof is one suite per composition root, each exhaustive over its own affinity set. This is one of the three proofs the release checkpoint #1058 requires.

## Task

No production behaviour changes; no topic skill applies beyond `implement-issue`.

1. Create three integration suites. Each one's `beforeAll` sets `process.env.SEMPREC_TENANT_SCOPE = "strict"` (`enforceTenantScope` from #978 reads it on every call) and `afterAll` restores it; each runs on `createRuntimeRolePool` pools with two tenants A and B from `createTestTenant(adminPool)` (`@semprec/data/testSupport`, #975), provisioned with `provisionTenant(pool, id)` (#1005):
   - `backend/services/semprec-api/src/__tests__/tenantIsolationJobs.test.ts` — the `api` set, with the task list composed exactly as `createApiQueueRuntime` composes it, over a `semprec_data` pool;
   - `backend/services/semprec-agents/src/__tests__/tenantIsolationJobs.test.ts` — the `agents` set, composed as `createAgentsQueueRuntime` does, over the pool role #963 gave semprec-agents, with the fake model the existing agents tests use;
   - `backend/services/semprec-transcribe/src/__tests__/tenantIsolationJobs.test.ts` — the `transcribe` set, composed as `createTranscribeQueueRuntime` does, over a `semprec_data` pool, with the fake audio gateway the existing transcribe tests use.
2. **Exhaustiveness.** Each suite computes its set from `resolveTaskAffinitySets(await loadFullModuleRegistry())` and fails, naming them, when a task name in the set has no case or a case names a task outside the set.
3. **Tenant fingerprint helper** (inside each suite or a shared fixture under the same `__tests__/` directory): for tenant T, inside `runInTenant(T)`, per tenant-classified table (tables whose comment is `semprec:tenancy=tenant`), the row count and an md5 over the ordered row texts. "Nothing of T changed" means T's fingerprint is identical before and after.
4. **Case contract.** Jobs are enqueued with `enqueueJob` inside the stated scope and drained with `runOnce`.
   - A task that `TASK_TENANCY` (#982) declares `tenant` (module tasks count as `tenant`): (a) a job enqueued inside `runInTenant(A)` naming A's fixture rows runs to completion and leaves the fingerprints of B and of tenant zero unchanged; every notification it writes is addressed to A's user. (b) The same payload enqueued inside `runInTenant(B)` ends exactly as the same job naming random UUIDs (same final job state, same error message after ids are replaced with `<id>`) and leaves A's fingerprint unchanged.
   - A task declared `system`: with due work seeded in both A and B, one run performs each tenant's work in that tenant only — A's resulting rows appear only in A's fingerprint, B's only in B's, notifications go to each tenant's own user, and tenant zero's fingerprint is unchanged. A system task that touches no tenant table (e.g. `queueFailedJobsPrune`) asserts all three fingerprints unchanged.
5. If a case fails because a task really leaks, do not change production code here: leave the failing case in the pull request and stop, reporting the task and the leak — the fix belongs to the issue that owns that task.

## Acceptance criteria

- Integration: in each of the three suites, a task name of its affinity set without a case fails the exhaustiveness test naming it, and every name currently in the set — including `heartbeatSweep`, `approvalExecute`, `notificationFanout`, `observabilityCheckSystem`, `mailAccountSync`, `heartbeatFireAgent`, `agentRun`, `delegatedAgentRun`, `transcriptionJob` and the export and purge tasks — has one (the credential re-encryption task does not exist yet; #1062 adds it together with its case).
- Integration: every `tenant` task passes cases (a) and (b) of Task step 4: running for A changes nothing of B or tenant zero, and B's job naming A's ids behaves exactly like one naming random ids while A stays unchanged.
- Integration: every `system` task, with work due in both tenants, writes each tenant's results only into that tenant and addresses each tenant's notifications to its own user.
- All three suites run on runtime-role pools only, with strict scope enforcement in effect.
