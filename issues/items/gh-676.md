## Context

`createSemprecTickAction` (`backend/packages/data/src/inbox/inboxTickAction.ts`, lines 457-575) runs everything inside one `withTransaction(pool, ...)` (line 464), including the injected LLM-backed `computeProposal` call made by `computeProposalEnvelope` (lines 154-183, called at lines 504 and 540). For the whole latency of the AI gateway round-trip (and its retries) the tick holds a pooled connection open in a transaction and — because the action runs on the dedicated `SEMPREC_TICK_QUEUE_NAME` queue (line 30) — the runner for that queue. A slow gateway starves the pool for concurrent requests, and after C4 the proposal row lock would additionally be held across the call if the lock were taken early.

`docs/adr/2026-09-10-bracket-non-transactional-calls-with-staleness-checked-transactions.md` prescribes the shape: a read transaction that snapshots what the call needs plus what is needed to detect staleness, the external call outside any transaction, and a write transaction that re-validates before writing. C4's `lockUnlockedProposal` guard is the write-side staleness check for the proposal row; this issue adds the source-side check (the fingerprint).

## Task

1. Split `createSemprecTickAction`'s handler into three phases:
   - **Read transaction** (`withTransaction`): everything up to and including the fingerprint gate (lines 465-502) and the target-database resolution currently inside `computeProposalEnvelope` (`getDatabaseByModuleId` for `processingMethod === 'database'`). The outcomes that need no LLM call — deleted source → `invalidateProposalForDeletedSource`, unrecognized type → `writeNeedsClarification`, locked card, unchanged fingerprint — are written in this transaction exactly as today and end the tick. Otherwise it returns a snapshot `{ item, type, processingMethod, targetDatabaseId: string | undefined, existingProposal: ItemRow | null, fingerprint }` and commits.
   - **External call**, outside any transaction: `computeProposal({ sourceItem: snapshot.item, type: snapshot.type, entityKind, targetDatabaseId })`, i.e. `computeProposalEnvelope` loses its `client` parameter and becomes a pure function of the snapshot plus the call result (the `'pageContent'`-without-`target` error stays).
   - **Write transaction** (`withTransaction`): reload the source item with `getItemById`; if it is gone or `deletedAt !== null`, or `resolveRecognizedType` now fails, or the recomputed fingerprint differs from `snapshot.fingerprint`, log `{ sourceItemId, reason }` with the C4 logger and return without writing — the edit that changed it has already enqueued a newer tick (the heartbeat-fire job key's replace semantics). Then `assertValidProposalEnvelope(client, envelope)` (on validation failure → `writeNeedsClarification` as today), and the write: for an existing card, through C4's `lockUnlockedProposal` (skip on `null`) with `ifVersion`; for a new card, re-run `findExistingProposal` first — if a card now exists (another tick created one meanwhile) revise it through the same guarded path instead of creating a duplicate; otherwise `createItemWithClient` + `linkSourceInboxRelation` as today.
2. Update the handler's doc comment (lines 439-456) to describe the three phases and cite the ADR slug.
3. Tests in `backend/packages/data/src/__tests__/inboxTickProposal.test.ts` (integration): (a) build the action with a dedicated `new Pool({ connectionString: process.env.TEST_DATABASE_URL, max: 1 })`; the `computeProposal` fake runs `await tickPool.query('SELECT 1')` while it executes — with the call inside the tick's transaction that single connection would be held and the query would never resolve, so the test wraps it in a 2 s timeout and fails on expiry; after the tick, the card exists; (b) the fake edits the source Inbox item's `text` through `chokePoint.updateItem` in its own transaction before returning; after the tick, no card was written for the stale envelope (no `proposed` card, or the existing card unchanged), and a second tick with the new text produces the card for the new fingerprint; (c) the existing "creates exactly one proposed row" and "revises the same row" cases keep passing unchanged.

## Scope

### In scope
- The read/call/write bracketing of the tick, the source-fingerprint staleness check, the duplicate-card re-check on the create path, and the tests.

### Out of scope
- The proposal-row lock and `ifVersion` guard (delivered by C4, reused here).
- Retrying the whole sequence on a stale write (a newer tick job already covers the edit; no retry loop is added).
- The gateway client itself and its timeouts.

## Acceptance criteria

- When the tick calls `computeProposal`, no database transaction and no pooled connection is held by the tick for the duration of that call.
- When the source item changes while the LLM call is in flight, the tick writes nothing for the stale result and the next tick produces the card for the new fingerprint.
- When nothing changes during the call, the tick creates or revises the card exactly as before (existing `inboxTickProposal.test.ts` cases pass).
- When a confirm commits during the call, the card stays `confirmed` (C4's guarantee holds in the new write transaction).
