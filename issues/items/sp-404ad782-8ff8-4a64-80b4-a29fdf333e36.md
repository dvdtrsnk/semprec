### Requirement gh-1813: [transcripts 11/19] Match transcripts to Events by interval overlap

#### Context

Model tier rationale: One matching mechanism rewritten over an existing function with existing fixtures; the care needed is time-zone and daylight-saving correctness, which the calendar time module of #1418 already encapsulates.

The pipeline's match step (step 6, `runMatchStep` in `backend/services/semprec-transcribe/src/transcriptionTask.ts`) calls `matchTranscriptToEvent` in `backend/packages/data/src/transcription/transcriptEventMatch.ts`. Today it is deliberately non-LLM and works on Events that carry a single text `date`: `MATCHABLE_EVENT_TYPES` is `standup` and `meeting` ("a plain event never is"), the `date` must look like a date with a time (`DATE_WITH_TIME_RE`), it is parsed with `Date.parse` in the server's zone, and an Event is a candidate when its start lies in `[recording start - 30 minutes, recording end]`. One candidate gets the Transcripts `event` edge; zero or several create one `kind = transcript` card in Processing proposals with a "create a new Event" envelope. The recording start is `Transcripts.date` (a UTC instant) and its end is that plus the duration from the prepare checkpoint.

That rule matches by start time only, so a meeting that began long before the recording and runs through it is missed, a meeting that ended before the recording but started within 30 minutes of it is matched, and wall-clock values without an offset are read in the wrong zone. Events now store a date, a wall-clock start and end and an optional end date (#1416, migrated by #1797), and an Event may have several transcripts (#1464).

This issue changes the candidate rule to interval overlap in the tenant's time zone. It is the single owner of the pairing rule; the content-based recommendation for ambiguous cases is #1848, and recurring-event occurrences that are not stored as items yet are matched by #1850.

Decisions:

- Overlap is strict: an Event is a candidate when its start is before the recording end and its end is after the recording start. Touching boundaries do not overlap.
- An Event without a `timeTo` is treated as a point at its start: it is a candidate only when that moment falls inside the recording interval.
- The old 30-minute lead is removed; all-day Events (no `timeFrom`) are never matched, nor are Events of type `event`.
- An Event whose stored values do not parse is skipped, not an error (user input must not fail the pipeline).

Candidates are ordered by interval start, then id.

Keep the outcomes and their contracts: exactly one candidate gets the Transcripts `event` edge (also when that Event already has other transcripts, as #1464 allows); zero or several candidates create the single suggestion card with the existing idempotency key. A transcript that already has an Event edge or card is left untouched. The "create a new Event" envelope of the card must stay valid for the new Events schema: its `date` becomes the recording's date in the tenant's time zone as `YYYY-MM-DD` (the former UTC instant is no longer a valid Events date). Everything else about that envelope (start and end times, project, participants, name) is #1818.
3. Update the JSDoc of `matchTranscriptToEvent` and the comments that describe the old window, and the history line written on the card, so they describe overlap.
4. Update `backend/packages/data/src/transcription/__tests__/transcriptEventMatch.test.ts` and the match step tests in `backend/services/semprec-transcribe/src/transcriptionTask.test.ts` to the new rule, including: a meeting 12:30-14:00 against a recording 13:52-14:39; a meeting 13:25-13:40 against the same recording; type `event`; an all-day Event; an Event with date `2026-10-14`, `timeFrom` 13:30, `timeTo` 14:30 compared in `Europe/Prague` with the recording's UTC time; an overnight Event with `endDate`; an Event without `timeTo`; an unparsable value; two candidates.

### Requirement gh-1848: [transcripts 15/19] Recommend the Event for an ambiguous transcript by content

#### Context

Model tier rationale: A second paid pipeline step that copies the existing speaker-suggestion pattern (gateway call outside any transaction, checkpoint written with the card), plus one gateway operation registration and one new ADR; no new lifecycle or isolation contract.

When a recording overlaps two or more Events, #1813 creates a single suggestion card in Processing proposals whose envelope proposes a new Event, and the user has to work out which meeting it was. The recording's content usually settles it (a recording about "sprint" and "iOS" belongs to the sprint planning, not to the accountant call that overlapped it). This issue adds a model call that recommends one of the overlapping Events from the meeting notes (#1695) and puts the recommendation, the candidates and the reason on the card.

Today the transcription worker (`semprec-transcribe`) already makes one comparable paid call, the speaker suggestion (`backend/services/semprec-transcribe/src/speakerSuggestion.ts`, `runSuggestSpeakersStep` in `transcriptionTask.ts`, `backend/packages/data/src/transcription/transcriptSpeakerSuggestion.ts`): it reads a snapshot, calls `gateway.complete()` outside any transaction, and then creates the cards and writes a checkpoint on the source Files item in one transaction. `docs/adr/2026-09-23-transcription-worker-writes-event-match-results.md` describes the match step as a deterministic, non-LLM step; this issue adds a paid recommendation to that step, which needs its own ADR (see Task).

The card carries its display data in the `context` property that #1451 adds to Processing proposals (candidates, reason and recording facts are read only by clients). The gateway operation map in `backend/services/semprec-ai-gateway/src/completeHandler.ts` (`OPERATION_REQUIRES_PROJECT_ITEM`) is also edited by #1392; both add independent entries.

Decisions:

- The model never writes the Event edge. Whatever it recommends, the outcome is a card the user confirms; with no usable recommendation the card keeps the new-Event envelope from #1813.
- A recommendation is used only when its `eventId` is one of the candidates; anything else counts as no recommendation. The call is made only for two or more candidates (zero or one never pays).
- The reason is written by the model in the tenant user's UI language (`users.locale`), one short sentence.
- The recording quote shown on the card is chosen deterministically, not by the model: the first segment of at least five words, shortened to 120 characters.
- The operation is named `transcript_event_match` and is not attributed to a project (`projectItemId: null`), like the other transcript operations.

### Requirement gh-1811: [inbox-core 16/22] Broadcast inboxCards realtime invalidations after card changes

#### Context

Model tier rationale: This adds a new realtime message across the publisher, the wire protocol and the client package, with tenant-scoped fan-out and after-commit emission from several processes, so an error leaks data to another tenant or loses updates.

Cards change without any client action: a new capture produces a proposal, a tick or the transcription process writes or updates a card, a chat revision rewrites it, an approval arrives, and a decision on another device closes it. Clients need to learn that the stack and the count are stale and then re-read `GET /api/inbox/cards` and `GET /api/inbox/cards/count` (#1807, #1823).

Today `RealtimeMessage` in `backend/packages/realtime/src/pgNotifyPublisher.ts` knows invalidations with scope `item` and `schema`, delivered only to sockets of the tenant (`docs/adr/2026-10-16-tenant-scoped-realtime-fan-out.md`, which replaced the thin user-scoped invalidations). Item invalidations are emitted for each item by `backend/packages/data/src/realtimeHook.ts`, and for `approval_requests` only the `approval_pending` notification is sent. The agents process did not publish at all before #1383.

This issue adds an invalidation scope `inboxCards` with the operation `created`, `updated` or `closed`, the `cardId` and an optional `userId`, emitted after commit from every place that changes a Processing proposals card: the tick, the transcription process, the card actions (confirm, reject and the other card actions) and the revision from a Semp thread. Changes to approval requests are announced by the separate approval request invalidation (#1789); a client refreshes the stack on either.

Decision: delivery is to the sockets of the tenant only; `userId` only narrows the delivery within the tenant and is never the sole access boundary. The message is thin: no card content.

### Requirement gh-1818: [transcripts 12/19] Propose a new meeting with wall-clock start and end, project and participants from a transcript

#### Context

Model tier rationale: This changes the confirm path of transcript cards into an atomic multi-write (Event, project relation, participant edges, transcript edge) driven by values the user can revise, across the Events, People and Transcripts isolation seams; a partial write or a cross-tenant id would corrupt data, and the confirm path is shared with every other card.

When no existing Event fits a recording, the pipeline's match step creates a card in Processing proposals that proposes a new Event (`backend/packages/data/src/transcription/transcriptEventMatch.ts`, confirm in `backend/packages/data/src/inbox/proposalActions.ts`). Today that Event is only `{ name: <transcript name>, type: meeting, date: <recording time> }`: the name is whatever the transcript was called (often the source file name), it has no start and end, no project, and no participants. The envelope cannot carry relations (`assertValidProposalEnvelope` in `backend/packages/data/src/inbox/inboxTickAction.ts` rejects relation properties in a `database` envelope), and confirm writes the Transcripts `event` edge after creating the Event.

This issue makes the proposed meeting complete. The card proposes a meeting named "Schůzka D. M." / "Meeting D. M." (day and month of the recording), with the recording's wall-clock start and end in the tenant's time zone, the project of the Event the card recommends (if any), and, on confirm, the participants taken from the speakers already mapped to people. It builds on #1416 (the Events calendar properties `timeFrom`, `timeTo`, `endDate`), on #1509 (the tenant's own person, who must not be added as a participant), and on #1640, which also lets a transcript card's Event proposal carry relations (the envelope relation rules are those of #1426 and #1476). #1830 relies on this issue so that no proposed meeting ever has an empty name. Matching itself is #1813, whose version of `transcriptEventMatch.ts` this issue edits (it already switched the envelope date to a date-only value); the recommendation that supplies the project's source Event is #1848.

Decisions:

- Participants are read at confirm time from the transcript's `speakers` edges as they are then, not frozen into the card; the tenant's own person is excluded. By the product owner: a speaker assignment confirmed after the confirm only adds the person to the Event's participants (the speaker card confirm, #1671, and the manual assignment, #1770, do that); changing or clearing an assignment never removes a participant. This issue writes nothing for later assignments.
- The project is taken from the recommended Event (`context.recommendedEventId` of the card); a card without a recommendation proposes no project.
- By the product owner: when no Event overlapped the recording at all, the card proposing a new meeting is still created (with the complete envelope of this issue) and the user can reject it; a variant without a card is not built.
- The meeting ends on the next day only when the recording crosses local midnight; then `endDate` is set, otherwise it is left unset.

### Requirement gh-1830: [recordings 17/17] Derive the transcript display name instead of copying the filename

#### Context

Model tier rationale: One resolution function used by several readers plus a create-step change and a per-tenant backfill, on existing seams, but it changes a user-visible name chain and must never leave an event proposal without a name.

Today `runCreateStep` (`backend/services/semprec-transcribe/src/transcriptionTask.ts`) copies the upload's `X-Filename` into `Transcripts.name`, which is a user-owned property that nothing later changes. So a recording shows as `IMG_0042.m4a` everywhere that reads `name`: the generic views, Semp's `item.get`, search and the result label of Inbox cards. The event match (`transcription/transcriptEventMatch.ts`) proposes a new event named after the transcript, so an empty `name` would yield an event without a name. The pipeline's text templates live in `transcription/i18n/cs.json` and `en.json`.

This issue derives the title a user sees from one function, `resolveTranscriptDisplayName` in `transcription/`, in this order: the user-entered `name`; otherwise the name of the live linked event (follows a rename); otherwise the translated "Recording D. M. HH:MM" built from `date`, both while the transcript is processing and after it is done, and for an imported file the same as for a recording made in the app. The generated meeting-notes title (#1695) is not part of the chain: it is returned as `suggestedName`, a name Semp proposes that the app shows on the recording's card for the user to edit and confirm; confirming writes the user-owned `name` through the existing item update. The detail endpoint (#1576), the list endpoint (#1636), the Semp read tool (#1832) and the event match all call the function. The create step (#1624) stops copying the filename. The match proposes the event name "Meeting D. M." (#1818), never an empty name.

Decisions:
- By the product owner: a finished transcript without an event gets an AI-generated name only as a proposal (`suggestedName`); until the user confirms it, it is shown as "Recording D. M. HH:MM".
- By the product owner: there is no separate placeholder for processing or for imports (no "New recording", no "Dictaphone - import"); every recording without a name or event uses the one pattern "Recording D. M. HH:MM".
- `suggestedName` is the generated title when the transcript has no user-entered `name`, no live linked event and a non-empty generated title; otherwise `null`.
- `Files.name` keeps the filename; only `Transcripts.name` stops receiving it.
- The create step writes only `recording_requests.name` (when the intake set one), because the pipeline must not invent a user-owned field (single-writer ownership ADR).
- By the product owner: the Transcripts `name` may stay empty, because a transcript takes its title from its event or its recording date; the general rule that requires a non-empty title applies to the other collections and not to Transcripts.

Shared-file ordering: this issue also waits for #1817 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1644: [recordings 13/17] Link a transcript to its upload's event in the create step

#### Context

Model tier rationale: It widens what the transcription worker may write (a relation edge in the create step), which changes an accepted authorization ADR and triggers downstream rules in a second process, and it must stay correct when the event is deleted in between.

A recording made next to an event should belong to it from the start. Today the event is attached only by the match at the end of the pipeline (`transcription/transcriptEventMatch.ts`), by time window; a transcript that already has an `event` edge makes the match return `alreadyLinked`. `suggestSpeakers` takes its candidates only from `Events.people` of the linked event (`transcriptSpeakerSuggestion.ts`). `runCreateStep` (`backend/services/semprec-transcribe/src/transcriptionTask.ts`) writes only `name`, `status` and `link`, and `docs/adr/2026-09-23-transcription-worker-writes-event-match-results.md` limits worker writes to the edge and card produced by the match ("any further write it needs is a new decision").

This issue makes the create step write the `Transcripts.event` edge when the upload named a live event (`recording_requests.event_item_id` from #1574), in the same transaction as the transcript row. The match then returns `alreadyLinked`, speaker suggestion sees the event's participants, and the project, company and people inheritance rules of #1697 run in this process too, through the post-edge-write hook. It builds on #1574 and #1624 (the same `runCreateStep` is now called from the fast task).

Decision: the ADR is amended so the worker may write the `event` edge in the create step, only from `recording_requests`.
