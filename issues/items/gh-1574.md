## Context

Model tier rationale: It adds an authenticated streaming upload route that accepts a caller-chosen event id (a tenant-isolation and enumeration contract), a new tenant table with row-level security, and a transaction that must enqueue exactly one transcription run under concurrent and repeated uploads.

The existing /api/files stream resolves/deduplicates a Files item; its audio heartbeat enqueues transcription, while explicit /api/transcriptions also accepts video. Worker create writes name/status/link; prepare derives date from creation_time then upload time. This issue adds atomic recording context/enqueue without changing those separate entry contracts.

This issue reverses the earlier decision that a recording enters only through `/api/files` and producers merely enqueue a job. A recording made or imported next to an event now carries that event, the time it was recorded, and may be a video whose audio track is transcribed. It adds `POST /api/recordings`, a `recording_requests` table that keeps the per-recording context on the Files item (not in the job payload, which requeue, rerun and replace overwrite), and the intake function that enqueues the job in the upload's own transaction. Attaching a plain file to an event stays with `POST /api/files` and #1645, which reuses the transaction-aware upload variant added here. It builds on #1464 (several transcripts per event). It unblocks #1644 (writes the transcript-to-event edge), #1624 (fast transcript row), #1627 (language and speaker count), #1698 and #1986 (explicit no-event decision, stored in the same table).

Client context only: background URLSession repeats uploads safely; AAC mono64kbit/s gives about29MB/h within100MB. Clients extract video audio and own pause/discard; no client work or recording status is added.

Decisions:
- When the same bytes were already uploaded and the transcript exists, a request carrying `X-Event-Id` for a live event with no event edge on that transcript links it in the same transaction; the same event is a no-op; a different event, or an existing `recording_requests` row for a different event, answers 409 `recording_linked_elsewhere { transcriptId, eventId }` and writes nothing.
- An event in Trash at request time or by the transaction is treated as no event (`eventId: null`) and normal matching runs.
- `event_decision` is created with default `'none'` and no CHECK constraint; #1986 defines further values.

Shared-file ordering: this issue also waits for #1572 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Recording dedup/event/lock/FK semantics follow docs/adr/2026-11-05-recording-intake-coordinates-files-and-transcription.md, including recording_busy rollback-only and first accepted context. The fresh trashed-event201 example does not override duplicate200 or an existing association.

## Scope

### In scope

- The upload route, the `recording_requests` table with intake and purge, video support, dedup and conflict handling, the trigger skip, and the prepare-time `date`.

### Out of scope

- Writing the transcript-to-event edge in the create step: #1644.
- A fast transcript row at upload time: #1624.
- Filling `language`, speaker counts and `project_item_id`: #1627.
- Storing a no-event decision: #1986.
- Attaching a file to an item through `/api/files`: #1645.
- A `POST /api/transcriptions` change; it is not needed.

## Acceptance criteria

- When a video is posted to `/api/recordings`, then it is transcribed without any further call, and the heartbeat does not enqueue it a second time.
- When `X-Recorded-At` is set, then Transcripts `date` equals it even if the upload happens an hour later.
- When `X-Event-Id` names a foreign or nonexistent event, then the response is the same 404 and no blob is stored; when it names a trashed event, then the response is 201 with `eventId` null.
- When the same recording is uploaded again, then no second Files item or transcript is created; with a different event the response is 409 `recording_linked_elsewhere`.
- When the Files item is purged, then its `recording_requests` row is deleted.
