## Context

Model tier rationale: It adds an authenticated streaming upload route that accepts a caller-chosen event id (a tenant-isolation and enumeration contract), a new tenant table with row-level security, and a transaction that must enqueue exactly one transcription run under concurrent and repeated uploads.

Today a recording enters the system only through `POST /api/files` (`backend/services/semprec-api/src/filesHandler.ts`, routed by hand in `app.ts`): a raw stream with `Content-Type` and `X-Filename`, a 100 MB cap, 201 for a new file and 200 for a content-hash duplicate. `ingestUploadedFile` (`backend/packages/data/src/blobs/fileUploadStore.ts`) opens its own transaction and accepts no client. The heartbeat action `core.filesTranscriptionTrigger` (`transcription/transcriptionActions.ts`) then enqueues `transcriptionJob { fileItemId }` for an `audio/*` Files item with no `Emails.attachments` edge; video is transcribed only through `POST /api/transcriptions`. The first pipeline step, `runCreateStep` in `backend/services/semprec-transcribe/src/transcriptionTask.ts`, writes only `name` (the `X-Filename`), `status` and `link`; the prepare step later writes the Transcripts `date` from the media's `creation_time`, else the upload time. An event is attached only afterwards by the end-of-pipeline match.

This issue reverses the earlier decision that a recording enters only through `/api/files` and producers merely enqueue a job. A recording made or imported next to an event now carries that event, the time it was recorded, and may be a video whose audio track is transcribed. It adds `POST /api/recordings`, a `recording_requests` table that keeps the per-recording context on the Files item (not in the job payload, which requeue, rerun and replace overwrite), and the intake function that enqueues the job in the upload's own transaction. Attaching a plain file to an event stays with `POST /api/files` and #1645, which reuses the transaction-aware upload variant added here. It builds on #1464 (several transcripts per event). It unblocks #1644 (writes the transcript-to-event edge), #1624 (fast transcript row), #1627 (language and speaker count), #1698 and #1986 (explicit no-event decision, stored in the same table).

iOS contract (documentation only, no server work): the client uploads from a file with a background URLSession (a repeated upload is safe, see dedup below), encodes AAC mono 64 kbit/s (about 29 MB per hour, so 1.5 h fits the limit), sends a video as its extracted m4a audio track, and handles Discard and Pause itself; the `recording` transcript status stays unused.

Decisions:
- When the same bytes were already uploaded and the transcript exists, a request carrying `X-Event-Id` for a live event with no event edge on that transcript links it in the same transaction; the same event is a no-op; a different event, or an existing `recording_requests` row for a different event, answers 409 `recording_linked_elsewhere { transcriptId, eventId }` and writes nothing.
- An event in Trash at request time or by the transaction is treated as no event (`eventId: null`) and normal matching runs.
- `event_decision` is created with default `'none'` and no CHECK constraint; #1986 defines further values.

Shared-file ordering: this issue also waits for #1572 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `io-hardening`, `error-handling`, `state-writes`, `db-migrations` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_recording_requests.sql (next free ordinal at commit time)`: table `recording_requests (tenant_id, file_item_id, event_item_id, recorded_at, name, language, num_speakers_exact, num_speakers_min, project_item_id, event_decision text NOT NULL DEFAULT 'none', created_at)`, primary key `(tenant_id, file_item_id)`, tenant column default, composite tenant foreign keys, `COMMENT ON TABLE ... IS 'semprec:tenancy=tenant'`, row-level security and grants following `0078_tenant_exports.sql`. The columns `name`, `language`, `num_speakers_*` and `project_item_id` stay NULL here; later issues fill them. Additive only.
2. In `blobs/fileUploadStore.ts` add a variant of `ingestUploadedFile` that runs a caller-supplied function with the open transaction client after the Files item is resolved (same hash dedup and duplicate-bytes cleanup), so the caller's writes commit atomically with the item. Keep `ingestUploadedFile` behavior unchanged.
3. Add `recordRecordingIntake` in `packages/data/src/transcription/recordingIntake.ts`, the only writer of `recording_requests`, which in the transaction: re-checks the event is live, inserts the row (`ON CONFLICT DO NOTHING`), applies the dedup rules above, and, when the Files item has no `computed.create` and no job is queued, calls `enqueueTranscriptionJob` (for audio and video). The Files item row is the source of truth; `deleteItemDependents` (`chokePoint/itemTrash.ts`) deletes the row when the Files item is purged.
4. In `core.filesTranscriptionTrigger` skip a Files item that has a `recording_requests` row, so a late heartbeat does not replace the job and raise `item_automation.attempts`.
5. Add `POST /api/recordings` in `services/semprec-api` (listener modeled on `filesHandler.ts`, mounted in `app.ts`, listed in `routeMatrix.ts` and `__tests__/tenantIsolationRoutes.test.ts`; a streamed body cannot pass the manifest adapter, an exception recorded under `docs/adr/2026-09-11-module-manifest-custom-routes.md`). Headers: `Content-Type` (only `audio/*` or `video/*`, otherwise 400 `validation_failed`), `X-Filename`, optional `X-Event-Id` (uuid) and `X-Recorded-At` (ISO 8601 with offset, otherwise 400). `X-Event-Id` is checked with a read-only query before any body byte is read: a foreign and an unknown id answer the same 404 and nothing is stored. Response: 201 or 200 with `{ fileItemId, created, transcriptId | null, eventId | null }`.
6. In `runPrepareStep` (`semprec-transcribe/src/transcriptionTask.ts`) write Transcripts `date` as `recorded_at ?? creation_time ?? upload time`, reading `recording_requests` for the file.

## Scope

### In scope

- The upload route, the `recording_requests` table with intake and purge, video support, dedup and conflict handling, the trigger skip, and the prepare-time `date`.

### Out of scope

- Writing the transcript-to-event edge in the create step: #1644.
- A fast transcript row at upload time: #1624.
- Filling `language`, speaker counts and `project_item_id`: #1627.
- Storing a no-event decision: #1986.
- Attaching a file to an item through `/api/files`: #1645.
- A `POST /api/transcriptions` change; it is not needed.

## Acceptance criteria

- When a video is posted to `/api/recordings`, then it is transcribed without any further call, and the heartbeat does not enqueue it a second time.
- When `X-Recorded-At` is set, then Transcripts `date` equals it even if the upload happens an hour later.
- When `X-Event-Id` names a foreign or nonexistent event, then the response is the same 404 and no blob is stored; when it names a trashed event, then the response is 201 with `eventId` null.
- When the same recording is uploaded again, then no second Files item or transcript is created; with a different event the response is 409 `recording_linked_elsewhere`.
- When the Files item is purged, then its `recording_requests` row is deleted.
