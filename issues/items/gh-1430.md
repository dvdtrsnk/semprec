## Context

Model tier rationale: One zod schema widened additively plus an optional parameter on an existing helper, in two files with an existing test pattern and no new lifecycle, tenant or persisted-key contract beyond optional fields.

A Processing proposal's `history` is a JSON array of `{ author: "ai" | "user", message, at }` entries (`proposalHistoryEntrySchema`, a `z.object`, in `backend/packages/data/src/inbox/inboxTickAction.ts`). `appendHistoryEntry` parses the stored array with that schema, so any key the schema does not declare is stripped on the next append, and an array holding an entry that fails the schema is treated as empty. A new field added to a history entry by a later issue would therefore be silently lost by the following append. The product needs each entry to say what kind of event it records (a recompute, a manual edit, a reset, a type choice, a revision from the item thread, a confirm, a reject, a reopen, an invalidation) so that the thread and the "return the proposal" flows can read the history, and so that manual edits and thread revisions can name the keys or the thread message involved.

This issue only makes the history entry shape carry that information and lets `appendHistoryEntry` write it. It does not change which events are logged by which action; later issues pass the new fields when they write their own entries.

Decision: one closed `kind` vocabulary is shared by every card flow: `computed`, `userEdit`, `reset`, `typeChosen`, `threadRevision`, `recompute`, `confirmed`, `rejected`, `reopened`, `invalidated`. A revision from the item thread is `threadRevision` with `author: "ai"`; a manual edit is `userEdit` with `author: "user"`. `author` stays `ai | user`. History messages stay plain English strings; localizing them is not planned, because only the thread and the "return the proposal" flows read the history.

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. In `inboxTickAction.ts`, extend `proposalHistoryEntrySchema` with optional fields: `kind` (enum of the ten values above), `keys` (array of strings, used by `userEdit`, entries are `ref.key` strings), `threadId` (string) and `messageId` (string). `message` and `author` are unchanged and stay required. Export the kind enum (or its type) from the same module for reuse.
2. Extend `appendHistoryEntry(history, message, author = "ai")` with a fourth optional parameter `extra?: { kind?; keys?; threadId?; messageId? }`. Entries without `extra` are written exactly as today (no `kind` key). The signature stays backward compatible: `appendHistoryEntry` is part of the public surface test.
3. Existing stored entries with no `kind` keep loading, and appending to a history that contains them leaves them byte-identical in the result. An entry with a `kind`, `keys`, `threadId` or `messageId` survives any number of further appends unchanged.
4. Tests in `proposalActions.test.ts` (data `__tests__`): legacy entry round trip, new entry round trip across two further appends, `keys`-bearing `userEdit` entry, and the existing malformed-history-is-empty behavior still holds.

## Touches

- backend/packages/data/src/inbox/inboxTickAction.ts (proposalHistoryEntrySchema and appendHistoryEntry only)
- backend/packages/data/src/__tests__/proposalActions.test.ts

## Scope

### In scope

- Additive history entry fields and the optional `appendHistoryEntry` parameter.

### Out of scope

- Passing `kind` from existing writers (tick, confirm, reject, revise): each later issue that adds a writer or changes one sets its own `kind`; #1892 writes `userEdit`.
- Localizing history messages.
- Reading history for display or building the thread context (#1938).

## Acceptance criteria

- When an entry `{ author: "user", message, at }` without `kind` is stored and a new entry is appended, then both entries are read back and the old one is unchanged.
- When an entry is appended with `kind: "userEdit"` and `keys: ["primary.title"]`, then after two more appends it still carries both fields.
- When an entry is appended with `kind: "threadRevision"`, `threadId` and `messageId`, then all three survive a later append.
- When the stored history holds an entry that fails the schema, then it is still treated as empty, as before.
- `appendHistoryEntry(history, message)` with no fourth argument produces the same entry shape as before this change.
