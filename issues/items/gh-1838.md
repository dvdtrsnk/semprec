## Context

Model tier rationale: A new cross-process job triggered from write, delete, restore and system-setting hooks inside the write transaction, with debounce semantics and per-tenant delivery to device registrations, so a wrong trigger or key leaks pushes across tenants or loses reschedules.

The iPhone schedules the alarm and the bedtime reminder itself, so it must learn when sleep data changed on another device, on the web or through an agent. The backend neither rings nor schedules anything. With #1445 it can send a silent background push. Today the scheduler's heartbeats (`onItemEvent`) fire on create, update and delete but not restore, and a heartbeat needs a registered action id, a handler and a seeded row; the System settings timezone change is handled in `itemWrites.ts` by `recomputeAllForTimezoneChange`. Jobs are enqueued with `enqueueJob` (`backend/packages/queue/src/index.ts`) inside the writing transaction, with `jobKey`, `jobKeyMode: "replace"` and `runAt`. Registrations live in the global `push_subscriptions` table (channel `web_push` or `apns`, platform `web`, `ios` or `macos`, `device_token`, `apns_environment`), read with `listPushSubscriptionsForUser` and revoked with `revokePushSubscriptionByProviderInvalidation` (`push/pushSubscriptionsStore.ts`).

This issue adds the job `sleep.resync`: after any change to sleep data it sends one silent push `{ kind: "sleepResync" }` to the user's iOS registrations about 30 seconds later. Several changes inside the window collapse into one push. It builds on the sleep hook chain (#1784, #1799), the PUT route (#1835), the delivered module (#1779), the delete and restore hooks (#1601) and #1445. The agent tools for sleep nights (#1840) rely on it so agent writes reach the phone.

Contract for the iOS client (not implemented here): after a `sleepResync` push, on a realtime invalidation, at launch and in a background refresh, it reads `GET /api/sleep/nights` for the next 14 nights, schedules a system alarm with a fixed date for every night whose `alarm` is true (not a weekly repeat, because of exceptions) using `alarmSound` and a `alarmSnooze` repeat after 9 minutes, schedules a local reminder at `prepReminderAt` when it is not null, and cancels everything when `enabled` is false. When `enabled` and `muteSemp` are both true, the client does not schedule local notifications (task reminders, calendar alerts) inside the window from `bedAt` to `wakeAt` of the resolved nights: it moves them to `wakeAt` and reschedules after a resync push. The bedtime reminder and the alarm are never moved.

Decisions:
- Only iOS registrations (`channel` `apns`, `platform` `ios`, not revoked) receive the push; macOS and web nothing. iPad registrations also use platform `ios`, so they receive it too and the iPad rings the alarm as well; there is no per-device setting.
- No server-side bedtime reminder is sent as a visible notification and no row is created in `notifications`; the bedtime reminder is a local notification on iOS only.
- The job payload carries only the tenant id; the handler finds the user through `users.tenant_id` (one user per tenant).

Shared-file ordering: this issue also waits for #1819 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `backend/packages/data/src/sleep/sleepResync.ts` with `enqueueSleepResync(client, tenantId)` (`jobKey` `sleep-resync:<tenantId>`, `jobKeyMode: "replace"`, `runAt` now plus 30 seconds), the payload schema and the job handler. The handler loads the user of the tenant, lists the registrations with `listPushSubscriptionsForUser`, and for each active iOS APNs registration calls `sendApnsBackgroundPush` with `{ kind: "sleepResync" }`; a `permanent-failure` revokes that registration with `revokePushSubscriptionByProviderInvalidation`; a `transient-failure` makes the job fail so the queue retries; no registration is a successful no-op. Declare the task in `sleepModuleManifest.ts` (`taskNames` entry `sleep.resync`, `queueAffinity: "api"`, with the handler and payload schema exported from the manifest module).
2. Enqueue from `sleepWriteHooks.ts` in the write transaction: the create and update hooks of the three sleep databases, and an update hook on the System settings database that fires when the patch contains `timezone`. Register `registerItemDeleteHook` and `registerItemRestoreHook` (#1601) for the sleep databases so a soft delete and a restore of a plan or an exception also enqueue. Register everything in `domainWriteHooks.ts`. No heartbeat, action id or seeded heartbeat row is added.
3. Tests: a PATCH of a plan enqueues one job; ten writes within ten seconds leave one pending job; creating, soft-deleting and restoring a plan and an exception, patching the settings, changing the System settings timezone, and an agent `item.patch` on a sleep item each enqueue; a write in another tenant never enqueues for this tenant; the handler sends exactly one background push per active iOS APNs registration of the user, none to macOS or web registrations, none for a revoked one, and revokes a registration that answers 410; no row appears in `notifications` and `GET /api/notifications/unread` is unchanged.

## Scope

### In scope

- The debounced `sleep.resync` job, its enqueue triggers (create, update, delete, restore, timezone change) and the silent push delivery to iOS registrations.

### Out of scope

- The silent push function itself: #1445.
- The iOS client behavior described in the contract above.
- Holding other pushes inside the sleep window: #1794.
- A visible bedtime-reminder notification from the server, and showing it on the web: decided not to be done; the reminder is local on iOS only.
- Telling an iPhone from an iPad, and naming devices: decided not to be done.
- Pruning old night exceptions: decided not to be done; they are kept as history.

## Acceptance criteria

- When a plan is patched, then within about 30 seconds one background push is sent to each active iOS APNs registration of that user and none to macOS or web registrations.
- When ten sleep changes happen within ten seconds, then one push is sent.
- When a plan or an exception is soft-deleted, when a plan is restored, when the System settings timezone changes, or when an agent writes a sleep item, then a resync is enqueued.
- When the push is sent, then no row is added to `notifications` and `GET /api/notifications/unread` is unchanged.
- When another tenant's sleep data changes, then this tenant's registrations receive nothing.
- When APNs answers 410 for a registration, then that registration is revoked.
