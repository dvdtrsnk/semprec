**Blocked by:** #1653
**Model tier:** medium

## Context

Model tier rationale: One data-migration converter following an existing pattern (`backfillTaskTimeProperties`) and the existing two-pass migration runner, with an idempotency requirement over every stored Tasks row.

Before the Tasks write rules of #1536 existed, any string was accepted for a task's date and times, so existing rows may hold `"9:00"`, `""`, `"25:99"`, `"abc"`, `"2026-02-30"`, an end time without a start time, or an end time that is not later than the start time. A corrupt `date` also breaks date ordering and date filters. This issue repairs stored data once, as a module data migration.

How data migrations work here: `systemDatabasesModuleManifest.ts` lists `dataMigrations` entries `(databaseKey, fromVersion, toVersion, converterExport)`; the module registry (`packages/module-registry/src/registry.ts`) rejects two entries with the same `(databaseKey, fromVersion, toVersion)`, and the runner (`migrationJob/moduleDataMigration.ts`, per `docs/adr/2026-09-28-two-pass-skip-locked-module-data-migration.md`) skips a transition already recorded in `module_migrations`. Tasks has exactly one entry today, `1.0.0` to `1.1.0` (`backfillTaskTimeProperties` in `tasks/deriveTaskTime.ts`, re-exported from the manifest module). This issue adds the next one, `1.1.0` to `1.2.0`, as the only converter for that transition. The module manifest `version` is the version of its latest transition, so it moves to `1.2.0`. A later transition `1.2.0` to `1.3.0` (the effective day) belongs to #1780.

The migration rewrites rows and therefore bumps `updated_at`; creation time is kept separately by #1594 (generic `items.created_at`, backfilled from `updated_at`), which is why that issue must land first.

Decision: unreadable values become null rather than being left in place. Leaving a corrupt `date` would keep breaking date ordering, and nothing can recover the intended value.

Shared-file ordering: this issue also waits for #1653 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `state-writes` and `testing`.

1. Add the converter `normalizeTaskDatesAndTimes(properties)` (name of the export is `normalizeTaskDatesAndTimes`) in `backend/packages/data/src/tasks/normalizeTaskDatesAndTimes.ts`. It reuses `normalizeWallClockTime` from #1536 and `deriveTaskTime`, and returns a new properties object (or the same object when nothing changes):
   - `timeFrom` and `timeTo`: `"H:MM"` becomes `"HH:MM"`; `""` and any unreadable value (`"25:99"`, `"abc"`) become null; `timeTo` may be `"24:00"`, `timeFrom` may not.
   - `date`: a real `YYYY-MM-DD` stays; `""` and any unreadable value (`"2026-02-30"`) become null.
   - When the resulting `date` is null, `timeFrom`, `timeTo` and `time` become null (a start time requires a date).
   - A `timeTo` without `timeFrom`, or not later than `timeFrom`, becomes null.
   - `time` is recomputed from the result.
   - Other properties are untouched. The function is pure and idempotent: `c(c(p))` equals `c(p)`.
2. Register it in `systemDatabasesModuleManifest.ts`: `dataMigrations` entry for `tasks`, `1.1.0` to `1.2.0`, `converterExport: "normalizeTaskDatesAndTimes"`, re-export the function from the manifest module like `backfillTaskTimeProperties`, and set the manifest `version` to `1.2.0`. Keep one converter for the transition.
3. Tests: unit tests for each value class above and for idempotency; a database test that seeds Tasks rows with every corrupt shape, runs the migration, and asserts that no stored task has a time in `H:MM` or `""` form, that dates parse, and that a second run changes nothing and does not touch `updated_at` again.

## Scope

### In scope

- The single converter, its registration as the `1.1.0` to `1.2.0` transition, and the manifest version change.

### Out of scope

- The write-time rules: #1536.
- The effective-day migration (`1.2.0` to `1.3.0`): #1780.
- Any change to Events data.

## Acceptance criteria

- When the migration has run, then no task has a time in `H:MM` or `""` form, and every non-null `date` is a real calendar date.
- When a task holds `date` `"2026-02-30"` or `timeFrom` `"25:99"`, then the migrated value is null, and ordering Tasks by `date` no longer fails.
- When a task has an orphan `timeTo` or a `timeTo` not later than `timeFrom`, then `timeTo` is null and `time` shows only the start time.
- When the migration runs a second time, then no row changes.
- When the module registry loads the manifest, then it accepts exactly one converter per transition.
