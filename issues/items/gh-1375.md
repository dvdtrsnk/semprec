## Context

Model tier rationale: A pure shared function with a contract change to the stored finding payload and the AI response schema, touching a few seams that already have unit-test fixtures.

A guidance drift finding is a nightly-detected mismatch between a project's instructions and what the agent can or does do; the owner sees it as a notification and, later, as a card with actions. Findings are stored in `agent_guidance_drift_findings` (`fingerprint`, `payload`, `status` `active|resolved`, unique per `(project_item_id, fingerprint)`). `upsertActive` reopens a resolved finding with the same fingerprint, and the "decided findings are not reopened" rule the resolve action needs (#1685) also hangs on the fingerprint.

Today the fingerprint is `fingerprintGuidanceDriftContradiction` in `backend/packages/shared/src/guidanceDrift.ts`: a SHA-256 over the AI-written `claim`, `guidanceExcerpt` and `manifestFacts`. The AI rewords those strings from one nightly run to the next, so the same real problem gets a new fingerprint each night: it resolves one finding and opens another, and a reopened/decided state cannot be remembered. The tick `core.agentGuidanceDrift` (`backend/packages/application/src/projectAgentGuidance/driftAction.ts`) is the only caller.

This issue makes the fingerprint depend only on deterministic facts. It is used by the existing permission check now and by the behavior check in #1629, and by the problem-raising work in #1465.

Decisions:

- A finding's identity is its subject: `{ kind: "permission" | "behavior", operation | mcpTool, databaseId | null }`. The fingerprint is the SHA-256 (hex) of the canonical JSON (`canonicalizeJson`) of `{ projectItemId, kind, operation, mcpTool, databaseId }`, where exactly one of `operation` and `mcpTool` is a string and the other is `null`. Nothing generated by AI text enters it.
- For the existing permission check the AI response schema gains a required `subject` per contradiction: `{ operation: string, databaseId: string | null }`, taken from the permission manifest the AI is given (the operation the guidance contradicts and the target database id, or null when the contradiction is not database specific). The prompt tells the AI to copy these values from the manifest, never to invent them.
- The stored payload gains `kind` and `subject`. A payload row written before this change has no `kind`; reading it treats it as `permission` with no subject, and the next nightly run resolves it (its old fingerprint is no longer reported) and opens the new one. The findings table is empty in production today, so no data migration is written.

## Task

Load `canonical-keys` and `testing`.

1. In `backend/packages/shared/src/guidanceDrift.ts` add the type `GuidanceDriftSubject`, add `kind` and `subject` to the contradiction payload type (kind `permission`; the behavior variant is added by #1629) with `validateGuidanceDriftContradiction` accepting rows without them as legacy, and add `fingerprintGuidanceDriftSubject(projectItemId, kind, subject)` implementing the decision above. Remove `fingerprintGuidanceDriftContradiction`.
2. In `driftAction.ts` add `subject` to `AGENT_GUIDANCE_DRIFT_RESPONSE_SCHEMA` (required), validate it, switch the ranking and upsert to the new fingerprint, and extend the system instruction so the AI copies `operation` and `databaseId` from the manifest. When two contradictions share a subject, keep the one with the higher severity (the finding is unique per fingerprint).
3. Update `backend/packages/shared/src/__tests__/guidanceDrift.unit.test.ts` and `backend/packages/application/src/projectAgentGuidance/__tests__/driftAction.unit.test.ts` for the new function and schema.

## Scope

### In scope

- The deterministic fingerprint, the `subject` in the permission check's AI schema and the payload shape.

### Out of scope

- The behavior check and its AI operation: #1629.
- Reopening rules for decided findings and the resolved state: #1685.
- Changing which contradictions the permission check reports.

## Acceptance criteria

- When the AI rewords `claim`, `guidanceExcerpt` and `manifestFacts` of a contradiction about the same operation and database on two nights, then the fingerprint is identical and the finding stays one active finding with an advancing `lastSeenAt`.
- The fingerprint differs when the project, the kind, the operation or MCP tool, or the database id differs, and does not depend on field order.
- When a response contains a contradiction without `subject`, then the action fails validation without changing any finding.
- When a stored payload has no `kind`, then reading it does not throw and it is treated as a permission finding.
