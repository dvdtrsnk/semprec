**Model tier:** medium

## Context

Model tier rationale: The ledger, check, replay and CLI are defined, but they span backup and restore shell scripts with hermetic tests plus a transactional replay.

A deleted account must never come back. A deleted tenant's content does remain in restic snapshots until retention expires (`restic forget --keep-daily 14 --keep-weekly 8 --keep-monthly 12`, `deploy/systemd/scripts/semprec-backup.sh:51`). That is accepted for disaster recovery: its secrets are crypto-shredded, and its key backups age out within 7 days (#1064). But restoring a snapshot taken before a deletion would resurrect the tenant in the live system. The deletions recorded since that snapshot therefore have to be re-applied.

What exists:

- The purge (#1055) erases a `deleting` tenant and, in the same transaction that deletes the `tenants` row, inserts a PII-free tombstone into the global table `tenant_deletions(tenant_id uuid PRIMARY KEY, requested_at, completed_at)`. Within any one consistent dump, no `tenants.id` appears in `tenant_deletions`.
  - The purge runs every minute (`tenantPurge` in `CORE_CRONTAB`) over every tenant with `status = 'deleting'`.
  - `beginTenantDeletion(client, tenantId)` (`backend/packages/data/src/tenancy/deleteAccount.ts`, #1049) flips a tenant to `deleting`, revokes its sessions and push registrations, deletes its `tenant_keys` row and publishes the deactivation signal. It must run in a transaction opened inside `runInTenant(tenantId, …)`.
  - `lockAdminMembership` and `assertAnotherActiveAdminRemains` / `LastAdminError` (`backend/packages/data/src/tenancy/accountsAdminStore.ts`, #1041) guard the last active admin.
- The daily backup (`deploy/systemd/scripts/semprec-backup.sh:39-52`) writes a custom-format dump to `/var/backups/semprec/postgres.dump` through `docker compose … exec -T postgres pg_dump`, using a temporary file and then `mv`. It snapshots the dump and the two blob directories in one `restic backup`. #1064 changed how `tenant_keys` is dumped and retained; build on that version.
- The monthly restore test (`deploy/systemd/scripts/semprec-restore-test.sh`) restores `latest` into a work directory and a disposable PostgreSQL container. It runs named checks (`CURRENT_CHECK=…`, `fail_check`) through `pg_query` (`:102-106`), records the result through a data-layer CLI and destroys everything on exit. Both scripts have hermetic `*.test.sh` behavior tests with mocked `docker`/`restic`.
- Host scripts reach Postgres through small Node entrypoints compiled into `@semprec/data`'s `dist/` (`docs/adr/2026-09-23-host-scripts-record-results-through-a-data-layer-cli.md`; example `backend/packages/data/src/observability/restoreTestResultCli.ts`).
- `deploy/README.md` documents backups (`## Encrypted off-site backups`, line 128) and the restore test (`## Monthly restore test`, line 149). It has no production-restore procedure yet.

## Task

Load `state-writes` (replay reuses the deletion transaction), `error-handling` (a replay that cannot finish must say so) and `io-hardening` (CLI input validation, pool released on every path).

1. **Ledger in every snapshot** — in `semprec-backup.sh`:
   - After the dump and before `restic backup`, write `/var/backups/semprec/tenant-deletions.ledger`, holding one tenant uuid per line, from `docker compose … exec -T postgres psql --username="$POSTGRES_USER" --dbname="$POSTGRES_DB" --no-psqlrc --tuples-only --no-align --set=ON_ERROR_STOP=1 --command="SELECT tenant_id FROM tenant_deletions ORDER BY completed_at, tenant_id"`.
   - Write it through a temporary file and `mv`, removing a partial file on exit as the dump does.
   - Pass it to the same `restic backup` invocation as the dump.
   - A failed ledger query fails the backup before restic runs.
2. **Restore-test check** — add `deletionLedger` to `RESTORE_TEST_FAILED_CHECKS` in `backend/packages/data/src/observability/restoreTestResultArgs.ts:6-18` (and its unit test), as #1064 does for its checks, so a failure can be recorded. Then in `semprec-restore-test.sh`, add a check `deletionLedger` after `check_postgres_contents`. It fails when any of these holds:
   - the restored snapshot has no `var/backups/semprec/tenant-deletions.ledger`;
   - any non-empty line is not a lowercase uuid (validated with a regex before any line is used in SQL);
   - `SELECT count(*) FROM tenants WHERE id = ANY('{…}'::uuid[])` over the ledger ids is not 0;
   - the ledger's line count differs from `SELECT count(*) FROM tenant_deletions`.

   An empty ledger with an empty `tenant_deletions` passes.
3. **Replay** — in `backend/packages/data/src/tenancy/tenantPurgeJob.ts`, add `replayTenantDeletions(pool, tenantIds: readonly string[]): Promise<{ marked: string[]; alreadyDeleting: string[]; absent: string[]; refused: { tenantId: string; reason: "lastAdmin" | "unexpectedStatus" }[] }>`. For each id:
   - no `tenants` row: `absent`;
   - `deleting`: `alreadyDeleting`;
   - `active` or `suspended`: inside `runInTenant(id, () => withTransaction(pool, …))`, take `lockAdminMembership`. If the tenant's user is an admin, run `assertAnotherActiveAdminRemains`, catching only `LastAdminError` and reporting it as `lastAdmin`. Then run `beginTenantDeletion`, giving `marked`;
   - any other status (e.g. `provisioning`): `unexpectedStatus`.

   The purge sweep then erases the marked tenants once `semprec-api` runs.
4. **Ledger parsing** — new pure module `backend/packages/data/src/tenancy/tenantDeletionLedger.ts` with no database import. `parseTenantDeletionLedger(text: string): string[]` ignores blank lines, de-duplicates, and throws an error naming the 1-based line number for any line that is not a uuid.
5. **CLI** — new `backend/packages/data/src/tenancy/replayTenantDeletionsCli.ts`, the same shape as `restoreTestResultCli.ts`:
   - `DATABASE_URL` is required;
   - its single argument is the ledger path;
   - it parses before connecting (exit 2 on bad input, no database write);
   - it runs `replayTenantDeletions` inside `runAsSystem("tenantDeletionReplay", …)`;
   - it prints the four lists' counts and the refused tenant ids;
   - it exits 1 when anything was refused and 0 otherwise;
   - it always ends the pool.
6. **Runbook** — in `deploy/README.md`:
   - Extend the backup section with the ledger file.
   - Extend the restore-test section with the `deletionLedger` check.
   - Add a section `## Re-applying account deletions after a restore`:
     1. Restore the dump.
     2. Fetch the **newest** ledger: `restic dump --path /var/backups/semprec/postgres.dump latest /var/backups/semprec/tenant-deletions.ledger > <file>` (a bare `latest` can resolve to #1064's key-dump-only snapshot). This is newer than the restored snapshot when an older one was restored.
     3. Run the CLI as `semprec_data` (the api's `SEMPREC_API_DATABASE_URL`).
     4. Start the services, after which the purge erases the replayed tenants within a minute.
     5. If the CLI exits 1, resolve each refused tenant by hand.

     State the limit: a deletion completed after the newest snapshot is in no ledger and must be requested again (the 24-hour RPO window). State the 12-month content retention in snapshots.

### Out of scope

## Acceptance criteria

- `parseRestoreTestResultArgs(["failed", "<id>", "deletionLedger"])` parses (unit, `restoreTestResultArgs.unit.test.ts`).

- When the backup runs with a mocked `psql` returning two uuids, `/var/backups/semprec/tenant-deletions.ledger` holds exactly those lines and is an argument of the same `restic backup` call as `postgres.dump`. When the ledger query fails, the script exits non-zero, `restic` is never called and no partial ledger file remains (script, `semprec-backup.test.sh`).
- When the restored snapshot lacks the ledger, has a non-uuid line, lists an id still present in restored `tenants`, or has a line count different from `tenant_deletions`, the restore test fails at check `deletionLedger` and reports it through the existing failure path. A consistent ledger passes (script, `semprec-restore-test.test.sh`).
- With tenant B active, holding sessions and a key, and listed in the ledger, `replayTenantDeletions` marks B:
  - B is `deleting`, its sessions are revoked, its `tenant_keys` row is gone and the deactivation NOTIFY fires;
  - one purge run afterwards removes B and writes its tombstone;
  - an id with no `tenants` row is reported `absent`, and a `deleting` tenant `alreadyDeleting`, both with no change;
  - tenant A is untouched.

  (integration, `tenantDeletionReplay.test.ts`, two tenants via `createTestTenant()` from #975)
- When the ledger lists the only active admin's tenant, that tenant is reported `refused` with reason `lastAdmin` and stays unchanged, while the other listed tenants are still marked (integration, `tenantDeletionReplay.test.ts`).
- When a ledger text contains a blank line, a duplicate and a valid uuid, the parser returns the de-duplicated uuids. A line `not-a-uuid` on line 3 throws naming line 3 (unit, `tenantDeletionLedger.unit.test.ts`).
