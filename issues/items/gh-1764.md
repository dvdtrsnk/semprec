**Model tier:** medium

## Context

Model tier rationale: One write mechanism (three custom routes over one system-owned relation) on existing relation-write, route and manifest seams with defined fixtures, but it writes protected system edges and combines an edge removal with a task update in one transaction.

In the calendar a task can be dropped onto an event and becomes part of it: it stays in the Tasks collection with its own date and time, but until the event ends it is shown only inside the event. A task can sit in several events one after another (adding it to the same event again moves that event to the end of the order, and the last one added decides). Today nothing links a task to a host event: the only task-to-event link is `Events.actionItems` (an action item that came out of the event), and a generic relation write cannot create this one, because the relation is protected. #1540 creates the schema: `Tasks.hostEvents` with the inverse `Events.hostedTasks` (many to many), both sides owned by the system with owner process `tasks`, so a generic edge PUT or DELETE answers 403 `owner_violation` and only the Tasks process can write them (`SystemRelationWriteContext` in `backend/packages/data/src/chokePoint/relationEdgeContext.ts`). An edge write replaces the metadata of an existing edge (`chokePoint/relationOps.ts`), and edge writes publish a realtime frame (#1621). When a recurring task is completed, the next instance does not copy these edges (#1673).

This issue adds the routes that put a task into an event and take it out. What the link means for visibility and the task's day is derived in #1780; completing a task inside an event is #1781; listing an event's tasks is #1801; agent and MCP tools for the same actions are #1957.

Decisions:
- Each edge carries the metadata `{ addedAt }` (an ISO instant filled by the server, never taken from the client). Adding a task to an event it already sits in replaces the metadata with a new `addedAt`, which moves that event to the end of the task's order.
- A task with an active recurrence cannot be placed into an event yet: the call is a 400 `validation_failed` on `taskId` (decided by the product owner). Once a single occurrence can be created (#1720), #2012 places only that occurrence and leaves the series as it is.
- A trashed task or event is a 404. A task that is already done can be placed into an event and nothing else changes.
- Removing a task from all events can also give it a new date and time in the same transaction.

Shared-file ordering: this issue also waits for #1762 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening`, `canonical-keys` and `testing`.

1. Add `backend/packages/data/src/tasks/taskHostEventRouteHandlers.ts` with the three handlers below, and declare them in `customRoutes` of `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` (justification `transactional-semantics`: an edge write with server-filled metadata, and an edge removal together with a task update, which the generic endpoints cannot express). Each runs in one transaction and writes edges through `createRelationWithClient` / `deleteRelationWithClient` with the system context `{ ownerProcess: "tasks" }` on the `Tasks.hostEvents` property.
   - `PUT /api/tasks/:id/host-events/:eventId`: both items must be live (404 otherwise), the task must have no active recurrence (`getTaskRecurrence`), and the edge is created or replaced with `{ addedAt: <now> }`. Answers 200 `{ taskId, hostEvents: [{ eventId, addedAt }] }` ordered by `addedAt` ascending.
   - `DELETE /api/tasks/:id/host-events/:eventId`: removes only that edge; idempotent (a missing edge answers 200 with the current list).
   - `DELETE /api/tasks/:id/host-events` with an optional body `{ date?, timeFrom?, timeTo? }`: removes every host event edge of the task and, when the body has at least one key, patches those properties of the task through `updateItemWithClient` in the same transaction (the Tasks validation of #1536 applies and a rejected value rolls back the edge removals).
2. Register the route entries in `backend/services/semprec-api/src/routeMatrix.ts` (tenant class), `ROUTE_HANDLER_FILES` in `chokePointWriteBoundary.unit.test.ts` and the two-tenant cases in `tenantIsolationRoutes.test.ts`.
3. Tests (real database): the first PUT creates the edge with `addedAt`; a second PUT to the same event moves it last; PUT for three events keeps their order; PUT for a task with an active recurrence is 400; a trashed event or task is 404; DELETE of one event keeps the others; DELETE of all with `{ date: "2026-10-16", timeFrom: "09:00" }` removes every edge and sets the new date and time in one transaction, and with an invalid time nothing changes; a generic `PUT /api/items/:id/relations/hostEvents/:target` still answers 403 `owner_violation`; both the task and the events get the realtime frames of #1621; a task of another tenant is a 404.

## Scope

### In scope

- The three routes, the `addedAt` metadata, the move-to-end rule and the combined removal with a new date and time.

### Out of scope

- The schema of the relation: #1540; not copying it to the next recurring instance: #1673.
- Hiding a task until its events end and deriving its effective day: #1780; revealing it after the end: #1782.
- Completing inside an event and reading an event's tasks: #1781, #1801.
- Placing one occurrence of a recurring task (only that occurrence moves, the series stays): #2012.
- Agent and MCP exposure: #1957.

## Acceptance criteria

- When a task is put into an event, then the edge exists with an `addedAt` set by the server and the response lists the task's host events in order.
- When the same event is put again, then it becomes the last in the order.
- When the task has an active recurrence, a task or event is trashed, or an id is foreign, then the response is 400 or 404 and nothing changes.
- When the task is removed from all events with `{ date, timeFrom }`, then all edges are gone and the task has the new date and time, in one transaction.
- When a generic relation write targets `hostEvents` or `hostedTasks`, then it is refused with 403 `owner_violation`.
