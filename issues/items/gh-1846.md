**Model tier:** high

## Context

Model tier rationale: New agent write tools that go through approval with a staleness snapshot and exactly-once execution, and that must refuse writes to system automations, which is an authorization and isolation contract.

Semp can read automations of a project (`heartbeat.list`, `heartbeat.history`, `heartbeat.trigger` in `backend/packages/data/src/scheduler/heartbeatAgentTools.ts`, declared in `backend/packages/data/src/chokePoint/schemaCoreModuleManifest.ts`), but cannot create, change or switch one off: `createHeartbeat`, `updateHeartbeatRule` and `setHeartbeatEnabled` are only scheduler-store functions with no tool or route. The product says new automations are created by asking Semp in chat.

Agent writes are proposals a person approves (`docs/adr/2026-09-10-agent-writes-are-proposals-not-direct-writes.md`). Tools that belong to a module and require approval are composed into agent sessions and deferred by #1523 and #1791; the approval summary with a localisable description is #1683; the origin column that tells user automations from system ones is #1438; the store functions for name and task are #1435; agent writes flagged for approval at the choke point are #1713. This issue only adds the three tools.

Decisions: creation, change and switching off by an agent go through approval (the alternative of direct agent writes would need its own exception in the approval ADR and is not adopted). The request kind is the module tool request of #1791. `projectItemId` can be any project of the tenant (chat runs on the Semprec project). A system automation cannot be changed by these tools.

Shared-file ordering: this issue also waits for #1841 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening`, `adr-conventions` and `testing`.

1. Add module tools in `schemaCoreModuleManifest.ts` with `requiresApproval`: `heartbeat.create {projectItemId, name, rule, task}` writes a heartbeat with action `core.agentRun` and `origin = 'user'`; `heartbeat.update {heartbeatId, name?, rule?, task?}`; `heartbeat.setEnabled {heartbeatId, enabled}`. Validate `rule` with the existing rule parser including module rule kinds. `update` and `setEnabled` act only on `origin = 'user'`; for a system automation the tool returns a tool error and writes nothing.
2. Approval snapshot: the request stores a hash of `name`, `rule`, `action_config` and `enabled` at request time; at execution the hash is recomputed and a mismatch yields a conflict with nothing written. Execution is exactly once (idempotent on the request id).
3. Add the localised description templates `approval.heartbeatCreate`, `approval.heartbeatUpdate` and `approval.heartbeatSetEnabled` to the snapshot mechanism of #1683 and to `seed/i18n/cs.json` and `en.json`.
4. After a successful execution publish the invalidations `projectAgent` (#1863 publishes user-scoped invalidations) and `sempThread` for the heartbeat's tick thread. Without approval the tools change nothing.
5. Tests: calling a tool without approval changes nothing; after approval the change is applied once; a change to the automation made in between yields a conflict; `heartbeat.create` writes `origin = 'user'` and action `core.agentRun`; update of a system automation is a tool error with no write.

## Acceptance criteria

- `heartbeat.create` and `heartbeat.update` change nothing until approved; after approval they execute once.
- If the automation changed between request and approval, execution reports a conflict and writes nothing.
- An approved `heartbeat.create` creates an automation with origin `user` and action `core.agentRun`.
- `heartbeat.update` or `heartbeat.setEnabled` on a system automation returns a tool error with no write.
- A renamed automation shows the new name in its thread header and the thread list after the invalidation.
