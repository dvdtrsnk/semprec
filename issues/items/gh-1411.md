## Context

Model tier rationale: One declarative mechanism across the manifest schema, the registry load and one drift check, following the existing manifest-validation patterns and test fixtures, with no runtime data writes.

Several inheritance rules are planned: an attachment takes its project from its task or event, a file takes its companies from its projects, a transcript takes project, company and people from its event, and a thread takes company and project from its sender. They share one shape, "copy this property of a source item to this property of a target item, along this relation". This issue lets a module declare such rules in its manifest and makes the registry and the drift check validate them, so each later rule is a few lines in one manifest and a typo or a cycle fails at startup or in CI instead of at runtime.

Today `ModuleManifest` (`backend/packages/module-registry/src/manifest.ts`) declares databases, tasks, workers, routes and so on, but nothing about values copied between items; `ModuleDatabaseDescriptor` is only `{ key, name, defaultViewType? }`. `ModuleRegistry.loadModule` validates one module at a time, with no database access; the schema against a database is checked only by `manifest/driftCheck.ts` and `manifest/moduleRegistryDriftCheck.ts`. This issue declares no rule itself and changes no stored data. #1593 reads the declared rules to create links and propagate values. #1869 and #1697 add the first rules; any module added later declares its own rules the same way.

Decisions:

- A rule is `{ key, source: { databaseKey, propertyKey }, target: { databaseKey, propertyKey }, via: { databaseKey, relationKey } }`. `via` is the relation property that joins a target item to its source item; its `databaseKey` must be the target's database or the source's database, and the relation must lead to the other one. `key` is globally unique and later becomes the `rule_key` of a stored link.
- The object is strict: optional rule extensions (value filters, single-valued target behavior, a source that is not an item) are added by the issues that need them, not guessed here.
- Cross-module references (a rule in one module naming a database of another) cannot be checked while one module loads, so the registry validates all rules in one explicit step after every module is loaded.

Shared-file ordering: this issue also waits for #1407 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys` and `testing`.

1. In `manifest.ts` add `ModuleLinkRuleDescriptor` and an optional `linkRules` array on `ModuleManifest`, plus the strict zod schema in `moduleManifestSchema`. All keys are non-empty strings; export the type from `module-registry/src/index.ts`.
2. In `registry.ts`: claim each rule `key` across modules with the existing duplicate checks (a duplicate across modules or inside one manifest fails the load with the same wording style as other keys). Add `validateLinkRules()` which throws a descriptive error when a rule names a `databaseKey` no loaded module declares, when `via.databaseKey` is neither the source's nor the target's database, or when the graph is cyclic. The graph has one node per `databaseKey.propertyKey` and one edge from each rule's source to its target; the error names the rules on the cycle. Add `getLinkRules()` returning the rules of active modules (with their module id), in manifest order.
3. In `data/src/manifest/fullModuleRegistry.ts` call `validateLinkRules()` after the last `loadModule`, so every consumer of the full registry gets a validated rule set.
4. In `data/src/manifest/driftCheck.ts` add `findInvalidLinkRuleReferences(client, registry)`: against the tenant's seeded schema it reports every rule whose source property, target property or `via` relation property does not exist in the named database, whose `via` property is not a relation, or whose relation does not lead to the other database of the rule. `createDriftCheckAction` reports them to `manifest_drift_findings` as a `link_rule_schema_drift` finding, in the same way it reports orphaned owner processes.
5. Tests: rule schema accepts a valid rule and rejects unknown fields; duplicate rule key across two fixture modules; unknown database key; `via` in an unrelated database; a two-rule cycle and a three-rule cycle; two rules sharing a target are fine; `getLinkRules()` omits rules of inactive modules; `findInvalidLinkRuleReferences` flags a misspelled property key and a non-relation `via`, and returns nothing for a valid fixture rule over the seeded ten databases; and a guard test that runs the check over `loadFullModuleRegistry()` and expects no findings (it is vacuous today and protects every rule added later).

## Scope

### In scope

- The `linkRules` manifest field, its schema, registry validation (keys, databases, `via`, acyclic graph) and `getLinkRules()`.
- The drift check of property and relation keys against the seeded schema, and its guard test.

### Out of scope

- Creating links, copying values and propagating changes: #1593.
- Declaring any real rule in a module manifest; each rule ships with the issue that adds its relation (for example #1697, #1869).
- Rule extensions: value filters, single-valued target behavior and a source that is not an item (the sender domain of #1897).

## Acceptance criteria

- When a manifest has a link rule that references a database no module declares, then loading the full registry fails with an error naming the rule.
- When link rules form a cycle across modules, then validation fails and names the rules on the cycle.
- When two modules declare the same rule key, then loading the second fails.
- When a rule's property key or `via` relation key does not exist in the seeded schema, then the drift check reports a `link_rule_schema_drift` finding, and the guard test over the full registry fails.
- A manifest without `linkRules` loads exactly as before.
