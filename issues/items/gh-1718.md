## Context

Model tier rationale: One hook registration with two follow-up effects on a relation edge, but it must fire for every writer (REST, MCP, agent) and stay silent for dry runs.

An Inbox item's type is a relation edge `Inbox.type` to Inbox item types. Writing or deleting that edge changes neither the Inbox item nor its card, so nothing re-runs the Inbox tick (an `onItemEvent` heartbeat on create, update or delete of an Inbox item; `triggerOnItemEventHeartbeats` in `backend/packages/data/src/scheduler/schedulerStore.ts`) and nothing recomputes the day's cached Inbox summary (`backend/packages/data/src/inbox/journalInboxCompute.ts`). The generic `PUT /api/items/:id/relations/type/:typeId` and `DELETE` therefore leave a proposal based on the old type and a day summary showing the old type. Existing relation-edge hooks run before the write and are validation hooks; they are also called by the dry-run `assertRelationCreatableWithClient`, and `deleteRelationWithClient` runs none.

#1530 adds the "edge changed" hook that runs after an edge is created or deleted. #1669 adds the validation that locks an item's type once its card is decided and limits an item to one type edge. Whether a client may delete the type edge and leave an item without a type is decided there, not here; this issue only reacts to whatever edge change was accepted.

Shared-file ordering: this issue also waits for #1714 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes` and `testing`.

1. Add `inboxTypeEdgeChangedHook` in the Inbox module and register it in `backend/packages/data/src/domainWriteHooks.ts` for the Inbox `type` relation, using the registry of #1530. After an edge create and after an edge delete, in the same transaction, call `triggerOnItemEventHeartbeats(client, inboxDatabaseId, 'update', inboxItemId)` and `enqueueJournalInboxRecomputeForInboxItem(client, inboxItemId)`.
2. The hook must resolve the Inbox item from either side of the edge and do nothing for any other relation.
3. Nothing is enqueued for the dry-run creatability check.
4. The recomputation of the card is left to the tick's fingerprint, which decides whether the changed type needs a new proposal.
5. Tests: `PUT /api/items/:id/relations/type/:typeId` enqueues the tick job and the day recompute and the day's summary shows the new type; `DELETE` of the edge enqueues the recompute; `assertRelationCreatableWithClient` enqueues nothing; the same edge written through an MCP tool and through an agent enqueues the same jobs as REST.

## Scope

### In scope

- Re-running the tick and the day summary after an Inbox item's type edge is created or deleted, for every writer.

### Out of scope

- The edge-changed hook registry; #1530.
- The one-type rule and the lock on decided cards; #1669.
- Replacing the type in one action; #1947.
- The tick computation and its fingerprint; #1434, #1606.

## Acceptance criteria

- When the type edge of an Inbox item is written through the generic relation endpoint, then the tick job and the day recompute are enqueued and the day summary shows the new type.
- When the type edge is deleted, then the day recompute is enqueued.
- When an edge creatability dry run is made for a proposal revision, then nothing is enqueued.
- When the edge is written through MCP or an agent, then the same jobs are enqueued as through REST.
