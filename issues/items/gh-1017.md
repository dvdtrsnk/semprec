**Model tier:** medium

## Context

Model tier rationale: Existing lookups and write transactions enforce defined reference checks, ordering and indistinguishable errors.

`items` is partitioned by `database_id`, so nothing can hold a Postgres foreign key to `items(id)`. Item-id columns are plain uuids whose integrity is "enforced at the application layer" (`backend/packages/data/src/db/migrations/0001_core_schema.sql:8-18`). Three write paths store a reference taken from caller input or from a stored config **without checking that it names anything**.

**1. `parentItemId` on database creation.**
- `POST /api/databases` passes `body.parentItemId` (`backend/services/semprec-api/src/databasesHandler.ts:98-110`).
- It flows through `genericApplicationService.createDatabase` (`backend/packages/application/src/genericApplicationService.ts:77-79`).
- The input schema is only `z.string().optional()` (`backend/packages/shared/src/genericOperations/schemas.ts:28-33`).
- `databasesStore.createDatabase` inserts the value as given (`backend/packages/data/src/chokePoint/databasesStore.ts:62-111`, `:85`). An unknown id becomes a database with a dangling parent, and a non-uuid string becomes a 500.

**2. `onItemEvent` heartbeat rules.**
- An `onItemEvent` rule stores `databaseId` (`backend/packages/data/src/scheduler/rule.ts:10-14`).
- `createHeartbeat` and `updateHeartbeatRule` validate only its shape (`backend/packages/data/src/scheduler/schedulerStore.ts:83-108`, `:180-200`).

**3. View-type configs.**
- `mailbox-client` stores `foldersDatabaseId`, `mailboxesDatabaseId` and `mailboxItemId` (`backend/packages/data/src/views/mailboxClientViewType.ts:26-40`).
- `journal-inbox` stores `inboxDatabaseId` and `journalDayItemId` (`backend/packages/data/src/views/journalInboxViewType.ts:13-26`).
- `viewsStore.validateViewTypeConfig` (`backend/packages/data/src/chokePoint/viewsStore.ts:47-60`, called from `createView` `:114` and `patchView` `:197`) runs only the zod schema and the synchronous `service.validateConfig` (`backend/packages/data/src/chokePoint/viewTypeRegistry.ts:13-24`), which has no database client.
- Views are created and patched by users and agents through the generic operations.

With tenants, a reference to another tenant's item or database must behave exactly like a reference to nothing: same status, same body. Otherwise the error becomes an existence oracle.

What earlier issues provide:
- Every lookup inside a tenant scope already sees only that tenant's rows. `databases` and `items` have row-level security keyed on `app.tenant_id`, which `withTransaction` sets from the scope. #980 runs every adapter route in the caller's tenant.
- So a plain existence lookup by id returns nothing for a foreign id, and checking existence is enough.
- The precedents for the error shape: relation endpoints, which answer `ValidationError` with a `field` (`backend/packages/data/src/chokePoint/relationOps.ts:47-60`), and the view-item existence check (`backend/packages/data/src/chokePoint/viewOps.ts:23-27`).

## Task

Load `state-writes` (a guard on a write, in the write's own transaction) and `io-hardening` (foreign ≡ missing; no existence oracle).

All checks run on the write's own `PoolClient`, before the write. The message never contains the referenced id, so a foreign id and a random one produce byte-identical errors.

1. **`parentItemId`.** In `databasesStore.createDatabase`, when `input.parentItemId` is defined, reject it with `ValidationError("'parentItemId' does not reference an existing item", { field: "parentItemId" })` if any of these holds:
   - it does not match `UUID_RE`, which already exists in that file;
   - `itemsStore.getItemsByIds(client, [id])` returns no row. That covers missing, soft-deleted and foreign items, since `itemsStore.ts:390-398` filters `deleted_at IS NULL`.
2. **Heartbeat rules.** In `createHeartbeat` and `updateHeartbeatRule`, after `parseHeartbeatRule`, if the rule's kind is `onItemEvent` and `getDatabase(client, rule.databaseId)` returns null, throw `ValidationError("'rule.databaseId' does not reference an existing database", { field: "rule.databaseId" })`.
3. **View-type configs.**
   - Add an optional `referenceFields?: { databaseIds?: readonly string[]; itemIds?: readonly string[] }` to `ViewTypeDefinition`.
   - Make `validateViewTypeConfig` async, taking the `PoolClient`. After the existing schema and service checks, in that order, every listed field that holds a string must resolve: `getDatabase` for database ids, `getItemsByIds` for item ids. Otherwise throw a `ValidationError` with the message `Invalid config for view type '<type>': '<field>' does not reference an existing database` (or `item`) and details `{ field: "config.<field>" }`. Absent optional fields are skipped.
   - Await it in `createView` and `patchView`.
   - Declare `referenceFields` in `registerMailboxClientViewType` (`databaseIds: ["foldersDatabaseId", "mailboxesDatabaseId"]`, `itemIds: ["mailboxItemId"]`) and in `registerJournalInboxViewType` (`databaseIds: ["inboxDatabaseId"]`, `itemIds: ["journalDayItemId"]`).
4. **Tests.**
   - Add `backend/packages/data/src/__tests__/tenantReferenceValidation.test.ts`. It uses the two-tenant runtime-role harness from #975:
     - `createTestTenant(adminPool)` for tenant B;
     - `createRuntimeRolePool(adminPool, "semprec_data")`, with `createChokePoint(dataPool)` on it;
     - all fixture and test writes inside `runInTenant(...)`.
   - Fix `backend/packages/data/src/__tests__/heartbeatAgentTools.test.ts:162`, which uses a made-up `databaseId`, to reference a real database.

## Scope

### In scope
- Existence checks inside the tenant for `parentItemId`, the `onItemEvent` rule's `databaseId`, and the database and item ids in `mailbox-client` and `journal-inbox` view configs.

### Out of scope
- `ownerProjectItemId`, which only seeds and module code set, not request input.
- Ids inside heartbeat `action_config`.
- Relation filter values inside view filters, which only narrow a read.
- Key-scoped database resolution (#1001).
- Pruning id-only item lookups to the tenant's partitions (#1003).
- The exhaustive foreign-id route suite (#1053).
- Tenant-consistent composite foreign keys (#1066).

## Acceptance criteria

- **`parentItemId`.** As `semprec_data` in tenant A, `chokePoint.createDatabase({ name, parentItemId })` rejects with `ValidationError` on field `parentItemId` for each of:
  - tenant B's live item;
  - a random uuid;
  - A's soft-deleted item;
  - the string `"not-a-uuid"`.

  The four errors have identical messages and details, and no `databases` row is written. With A's live item it succeeds and the database's `parentItemId` is that item. (integration, `tenantReferenceValidation.test.ts`)
- **Heartbeat rules.** In tenant A, `createHeartbeat` and `updateHeartbeatRule` with an `onItemEvent` rule naming B's database, or a random uuid, reject with `ValidationError` on field `rule.databaseId` with identical messages. The heartbeat row is not written or not changed. With A's database they succeed. Non-`onItemEvent` rules are unaffected. (integration, `tenantReferenceValidation.test.ts`)
- **View configs.** In tenant A, `createView` and `patchView` reject with `ValidationError` on `config.<field>`, with messages identical for B's id and a random id, for each of `mailbox-client`'s `foldersDatabaseId`, `mailboxesDatabaseId` and `mailboxItemId`, and `journal-inbox`'s `inboxDatabaseId` and `journalDayItemId`. With A's own ids they succeed. (integration, `tenantReferenceValidation.test.ts`)
- **Check order.** A `mailbox-client` config with `mailboxItemId` but no `mailboxesDatabaseId` still fails with the existing "mailboxItemId requires mailboxesDatabaseId" error (`backend/packages/data/src/__tests__/mailboxClientView.test.ts:111-127`). (integration)
- **Seeds unaffected.** Seeding still creates the Emails default `mailbox-client` view and the seeded `onItemEvent` heartbeats. `mailboxClientView.test.ts`, `scheduler.test.ts` and `inboxTick.test.ts` pass. (integration)
