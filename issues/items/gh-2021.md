**Blocked by:** #2022
**Model tier:** high

## Context

Model tier rationale: This is the first response that returns stored MCP argument values to a client, so a wrong scope or a missing redaction leaks credentials or exposes values outside the owner's detail; at this uncertainty the higher tier is chosen.

An approval request for an outgoing MCP action (for example sending an e-mail) cannot be decided responsibly without its values, such as the recipient and the subject. Today every client-facing view reduces the payload to `safeSummary` (`backend/packages/data/src/mcp/approvalRequestsQueue.ts`): the tool registration, the server item and the argument names (`argKeys`), never the values. The values are stored in `approval_requests.payload.args` of an `mcpInvoke` request. #1786 adds `GET /api/approval-requests/:id`, which returns one request only to its owner (`getApprovalRequestForOwner`) and answers 404 identically for a foreign, unknown or other-tenant id.

Decision (product owner): the approval description (#1683), the notification body (#1773), the push payload (#1831), the list (#1785) and the search never carry argument values. Only the detail of one request, read by its owner, shows them.

Decision: before they are returned, values are redacted and bounded: the value of every argument whose key, at any depth, contains (case-insensitively) `password`, `secret`, `token`, `apikey`, `api_key`, `authorization`, `cookie` or `credential` is replaced by the string `[redacted]`; a string value longer than 2,000 characters is shortened to 2,000 characters; the whole `arguments` object is capped at 16 KiB, and `argumentsTruncated: true` is set whenever anything was shortened or cut.

## Task

Load `io-hardening`, `testing` and `canonical-keys`.

1. Add a pure `toApprovalRequestArgumentValues(args)` in a new `backend/packages/data/src/mcp/approvalRequestArguments.ts` that applies the redaction and bounds above and returns `{ arguments, argumentsTruncated }`. Export it from the package barrel.
2. In `GET /api/approval-requests/:id` of #1786, add `arguments` and `argumentsTruncated` to the response for a request whose payload is `mcpInvoke`, computed with that function from `payload.args`. For a generic operation request both fields are absent. The `PATCH` response, the list, the count, the description, notifications and push are unchanged and never contain them.
3. Tests: an owner reading a `send_email`-like request gets `to` and `subject` values; an argument named `apiKey` or a nested `authorization` header is `[redacted]`; a 5,000-character body is shortened and `argumentsTruncated` is true; a foreign, unknown or other-tenant id still answers the identical 404; the list, the `PATCH` response and the rendered notification body of the same request contain no argument value.

## Scope

### In scope

- Returning redacted, bounded MCP argument values in the owner's detail of one approval request.

### Out of scope

- Argument values in descriptions, notification bodies, push payloads, the list or search (they stay excluded: #1683, #1773, #1831, #1785).
- Argument values of generic operation requests.
- Any change to the stored payload or to who may read a request.

## Acceptance criteria

- When the owner reads an MCP approval request with `GET /api/approval-requests/:id`, then the response contains its argument values, for example the recipient and the subject of an e-mail.
- When an argument key looks like a credential, then its value is `[redacted]` in the response.
- When values exceed the bounds, then they are shortened and `argumentsTruncated` is true.
- A foreign, unknown or other-tenant id answers the same 404 as before.
- No list, count, `PATCH` response, description, notification or push contains an argument value.
