## Context

Model tier rationale: A single value check added to the shared item write path, but it applies to every writer of every database, so the key-scoped behavior and the unchanged handling of old stored values need careful tests.

Properties of type `color` (today `Projects.color`, and the color properties planned for Areas and select options) hold a color as text, but nothing checks the value. `assertWritableProperties` in `backend/packages/data/src/chokePoint/itemWrites.ts` checks only that the key exists, is not a rollup or relation, and that system-owned keys are written by their owner; no code under `chokePoint/` or `types.ts` validates a value by property type. A card or client that sends "red", "Červená" or an empty hex therefore lands in the database and breaks every renderer that expects `#RRGGBB`.

This issue adds the check once, at the choke point, so that REST, the `/mcp` endpoint, agent tools, proposal confirms and system writers all get the same answer. It validates only the keys present in the write, so rows already stored with another format are neither migrated nor rejected until someone writes that key again.

Decision: the accepted format is exactly `#` followed by six hexadecimal digits, upper or lower case. The value is stored as written (no case change). `null` is accepted and clears the color; any other value (empty string, `#FFF`, a color name, a non-string) is rejected.

## Task

Load `error-handling`, `canonical-keys` and `testing`.

1. In `itemWrites.ts` add a value check that runs in both `createItemWithClient` and `updateItemWithClient` next to `assertWritableProperties`. For each key of the write whose property has `type: "color"`, accept `null` or a string matching `^#[0-9A-Fa-f]{6}$`; otherwise throw `ValidationError` (HTTP 400 `validation_failed`) with `details.field` set to the property key. Keys not present in the write are not inspected.
2. Make the check part of the same code path every writer already uses, so no caller can skip it, including calls that pass `allowedSystemKeys`.
3. Tests in `backend/packages/data/src/__tests__/itemWrites.test.ts`: `#FF3B30` and `#ff3b30` pass on create and update; `Červená`, `red`, `#FFF`, `""`, a number and an object are rejected with `field` equal to the key; `null` clears the value; an update that does not touch the color key succeeds on a row whose stored color is `red`; the rejection happens through the generic REST path as 400 with the field.

## Touches

## Scope

### In scope

- Hex validation of `color` property values on item create and update, for every writer.

### Out of scope

- Migrating or normalizing color values that are already stored.
- Restricting `Areas.color` to a fixed palette and the color of select options (#1584).
- Validation of select option colors and any client-side palette.

## Acceptance criteria

- When a project is written with `color: "#FF3B30"`, then the write succeeds.
- When a project is written with `color: "Červená"` or `"red"`, then the response is 400 `validation_failed` with `field` equal to `color`.
- When a project row already stores `color: "red"` and an update touches only `name`, then the update succeeds and the color is unchanged.
- The same answer is produced by the REST item routes, the `/mcp` item operations and a proposal confirm that writes a color.
