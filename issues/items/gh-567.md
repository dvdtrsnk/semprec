## Context

Epic #565 specifies a pipeline that turns code-review findings left `open` on merged pull requests into proposed follow-up issues. Nothing under `docs/adr/` covers a repository automation that creates issues on its own, keeps its state in GitHub labels and markers, or writes to GitHub as the Relay App. #265 did the same work once by hand, and `.github/workflows/close-completed-epics.yml` is the only scheduled repository automation today (it explains in a comment why it is not a Relay workflow, but has no ADR). The pipeline shapes every later script in this batch and had real alternatives, so it needs its ADR before the code lands. The later issues' header comments name this ADR, which is why they are blocked by this issue.

## Task

1. Add `docs/adr/<YYYY-MM-DD>-merged-review-findings-become-proposed-follow-up-issues.md`, dated the day you write it (the date in the filename and the `date` field match), with frontmatter `status: accepted`, `area: [cross-cutting]`, `supersedes: []`, `superseded-by: null`, and the sections Context, Decision and Consequences.
   - **Context** states: the bot's review memory is frozen at the last review before merge, so `open` is often stale (measured 2026-09-25: 138 open findings across 171 memory-bearing pull requests; all 6 high findings above #266 were already fixed on `develop`); #265 did this audit once by hand and found 10 of 39 already handled; `close-completed-epics.yml` is the only scheduled automation and why Relay cannot host a schedule (its triggers are labels on open issues or pull requests).
   - **Decision** states each of these, one short paragraph or bullet each:
     1. A scheduled GitHub Action harvests open findings of merged pull requests deterministically — no AI — into a harvest issue; a Relay workflow triggered by that issue's `followups:ready` label verifies each finding against `develop`, decomposes the valid ones into issues and audits them.
     2. Every issue the pipeline creates is a proposal: labelled `spec:proposed`, never dispatched until a human swaps it for `spec:approved` + `agent:ready` (repository rule 7 — agent-originated changes are proposals).
     3. All state is in GitHub: the labels `followups:harvested`, `followups:harvest`, `followups:ready`, `followups:issue`, `spec:proposed` and HTML markers in issue bodies and comments. No watermark (out-of-order merges and silent skips on failure) and no database.
     4. A harvest starts only when no harvest issue is open and no follow-up issue awaits approval (backpressure), and takes at most 30 findings; a fixed floor (`HARVEST_MIN_PR = 266`, after #265's audit) bounds the backlog.
     5. Only one thing is skipped deterministically: a resolved inline thread carrying the bot's own exact `Fixed.` reply. Everything else — resolved threads, missing paths — goes to the AI verify step with the facts attached.
     6. The Relay workflow writes to GitHub as the Relay App through Relay's loopback token proxy, opted into per command step, so the real token never enters a job; agent steps get no GitHub access.
     7. The deterministic parts are zero-dependency ES modules under `.github/scripts/review-followups/` with `node:test` tests, calling the REST and GraphQL APIs with `fetch` through `GITHUB_API_URL` / `GITHUB_GRAPHQL_URL` / `GITHUB_TOKEN` so the same code runs in Actions and behind the proxy.
   - **Consequences** states: closing a proposed issue retires its findings permanently (reopening is the undo) and closing an epic decides nothing about its children; a parked triage holds back every later harvest until a human resolves it; the Relay part depends on a Relay plugin feature (dvdtrsnk/bb-plugin-relay#57); the alternatives rejected — a merged-at watermark, periodic manual audits like #265, arming follow-up issues automatically, triage inside GitHub Actions, and `gh` acting as whatever account the Relay host is logged into.
