## Behavior specification

Files: upload, type, metadata, event attachments and origin.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: files-1

#### (a) Adopted decisions
- Thumbnails in the Files gallery? -> No; out of the minimum scope. Reason: the design has none and parsing untrusted PDFs is a new security surface. No issue written. -> Decided by the product owner: v1 has no thumbnails; if they are wanted later, they need their own ADR on the thumbnail source.
- HEIC: client or server conversion? -> Client converts (iOS picker in compatible mode); the detector still recognises HEIC so the server-side fallback issue can build on it. Reason: common libvips/sharp builds lack an HEVC decoder.
- Where do Files.type options grow? -> Only in files 01 (png, heic and audio added by one cutover). Reason: the design note says the tasks schema issue does not touch Files.type.
- Audio types m4a/mp3 in Files.type? -> Decided by the product owner: yes, one type `audio` ("Zvuk") for m4a and mp3 is added in #1410. Reason: audio attachments and recordings move to Files, so the generic types must be able to give them a type.
- Unknown content -> no `type` value and blob mime application/octet-stream. Reason: served as an attachment with nosniff, safest. -> Decided by the product owner: unknown content keeps no type value; the generic filter for an empty value finds it, and an "other" type would be one more special case.
- Blob metadata filename source -> derived from the storage key suffix, nullable; no schema change. Reason: blobs has no filename column and deduplicated blobs are shared.
- Blob metadata placement -> additive top-level `blobs` map on item envelopes and query results; `properties` unchanged.
- Events.files relation -> many_to_many, owner user, inverse Files.events; Tasks.files left to the tasks schema issue.
- Save-from-form -> blob upload then item create with relations; `type` filled server-side from the blob, `date` default via property defaults.

#### (b) Open questions for the product owner
- None remaining.

#### (c) User-visible behavior of this chunk
Users add files from the camera, scanner, photo library or file picker: the app uploads the bytes first with progress, and the file becomes a Files item only when Save is pressed, with the date defaulting to today and the chosen projects attached in one step; cancelling leaves nothing behind and never touches an earlier file with the same content. The file type badge (PDF, XLSX, DOCX, JPG, PNG, HEIC, Audio) is decided by the real content, not by what the client claimed, and each file shows its size. Files can be attached to calendar events and are visible from both the file and the event.
