## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. Add `PATCH /api/heartbeats/:id` with body `{enabled: boolean}` (strict: any other key is a validation error). Apply it with `setHeartbeatEnabled` in one transaction and respond with exactly `{ id, enabled, nextFireAt }` from the persisted result, where nextFireAt is ISO or null. Reuse the existing transaction-scoped lockHeartbeatForManualFire read before the origin check and setHeartbeatEnabled; retain active module-rule resolution and existing disable semantics. Never return raw row/error/action fields or fabricate future #1910 enrichment.
2. A heartbeat with `origin = 'system'` returns 403 `owner_violation` and nothing is written. An unknown heartbeat or one of another tenant returns not found.
3. After enabling, `next_fire_at` is computed from now and missed fires are not caught up; after disabling it is empty.
4. Register as a custom route in `schemaCoreModuleManifest.ts`, add it to the route matrix, `ROUTE_HANDLER_FILES` and the tenant isolation test.
5. Tests: disable then enable recomputes `next_fire_at` from now; PATCH of a system heartbeat returns 403 `owner_violation`; an extra key returns 400; an `onItemEvent` heartbeat can be enabled and keeps no `next_fire_at`.

- A body with any key other than `enabled` returns 400.
- A heartbeat of another tenant is answered as not found.
