## Context

Every third-party secret a user connects lives in `external_credentials` (`backend/packages/data/src/db/migrations/0006_mail_sync.sql:99-106`): IMAP and app passwords, OAuth refresh tokens, MCP API keys. Each one is sealed by `encryptSecret` (`backend/packages/credentials/src/index.ts:33-41`) with libsodium `crypto_secretbox_easy`, directly under the deployment master key `CREDENTIALS_MASTER_KEY` (`resolveMasterKeyFromEnv`, `:65-74`). With several users this has two weaknesses:

1. **No associated data.** A ciphertext copied onto another row, whether another item or another user's, decrypts there.
2. **One key for everyone.** Deleting a user cannot make their secrets unrecoverable from backups while the master key exists.

The decision is per-tenant envelope encryption:

- Each tenant gets a random 32-byte data key (DEK). It is stored in a new tenant-owned table `tenant_keys`, wrapped under the master key with XChaCha20-Poly1305 (IETF), with associated data that binds it to its tenant.
- Credentials are sealed under the DEK with associated data binding them to `tenant_id‖item_id`. This rolls out in one-release-rollback-safe steps:
  1. reading both schemes ships first (#1032);
  2. new writes switch to the DEK (#1060), once the release checkpoint #1058 confirms the dual read is in production;
  3. existing rows are re-encrypted (#1062);
  4. the master-key-only scheme is retired (#1069).
- `tenant_keys` is kept out of the 12-month backup and gets its own 7-day backup (#1064). Deleting a tenant's key row (#1049) then makes its secrets unrecoverable within 7 days, even to someone holding the master key.

This issue delivers the primitives, the table, the key store and the ADR. Nothing calls them yet. The tenant-table conventions come from #968 through #973:

- the tenancy functions `app_current_tenant()`, `app_sole_tenant()` and `app_tenant_default()`, where `app_tenant_default()` resolves to the scope's tenant or, while only one tenant exists, the sole tenant;
- the `semprec:tenancy=…` table comment checked by the catalog test;
- the RESTRICTIVE `tenant_isolation` plus PERMISSIVE `tenant_rows` policy pair.

## Task

Load `db-migrations`, `state-writes`, `error-handling` and `adr-conventions`.

1. **Primitives** in `backend/packages/credentials/src/index.ts`. Existing exports stay unchanged. Add:
   - `export const DATA_KEY_BYTES = 32`.
   - `generateDataKey(): Promise<Buffer>`, using `crypto_aead_xchacha20poly1305_ietf_keygen`.
   - `sealSecret(plaintext: string | Uint8Array, key: Buffer, associatedData: Uint8Array): Promise<EncryptedSecret>`. It uses `crypto_aead_xchacha20poly1305_ietf_encrypt` with a fresh random 24-byte nonce, and throws when `key.length !== 32`.
   - `openSecret(encrypted: EncryptedSecret, key: Buffer, associatedData: Uint8Array): Promise<Buffer>`.
     - On any failure it throws a plain `Error("Failed to open sealed secret: wrong key, associated data or corrupted ciphertext")` and never returns a partial result.
     - The error must not carry a string `code` property: `isLikelyDatabaseError` (`backend/packages/data/src/mcp/mcpConnectionFactory.ts:149`) would treat it as a database failure.
   - `wrapDataKey(dataKey: Buffer, masterKey: Buffer, tenantId: string): Promise<EncryptedSecret>` and `unwrapDataKey(wrapped: EncryptedSecret, masterKey: Buffer, tenantId: string): Promise<Buffer>`.
     - These are `sealSecret`/`openSecret` with associated data = the UTF-8 bytes of `semprec:tenant-key:v1:<tenantId>`, where `tenantId` is the lowercase canonical UUID text.
     - Unwrapping also checks that the result is 32 bytes.
   - Rewrite the module comment (`:3-18`): the secretbox functions have no associated data, and new data uses the sealed scheme.
   - Add no dependency: the package's `libsodium-wrappers ^0.8.4` already provides `crypto_aead_xchacha20poly1305_ietf_*`.
2. **Migration** (take the next free ordinal at commit time):
   ```sql
   CREATE TABLE tenant_keys (
     tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id) PRIMARY KEY,
     wrapped_key bytea NOT NULL,
     wrap_nonce bytea NOT NULL,
     master_key_version smallint NOT NULL,
     created_at timestamptz NOT NULL DEFAULT now()
   );
   COMMENT ON TABLE tenant_keys IS 'semprec:tenancy=tenant';
   ALTER TABLE tenant_keys ENABLE ROW LEVEL SECURITY;
   CREATE POLICY tenant_isolation ON tenant_keys AS RESTRICTIVE FOR ALL
     USING (tenant_id = (SELECT app_tenant_default()))
     WITH CHECK (tenant_id = (SELECT app_tenant_default()));
   CREATE POLICY tenant_rows ON tenant_keys AS PERMISSIVE FOR ALL USING (true) WITH CHECK (true);
   GRANT SELECT, INSERT, DELETE ON tenant_keys TO semprec_side;
   ```
   A migration comment explains:
   - why there is no `UPDATE` grant: rewriting a key row would orphan every credential sealed under it;
   - that `DELETE` is the crypto-shred account deletion uses;
   - why there is no `ON DELETE CASCADE`: the key is deleted deliberately.
3. **Key store** in `backend/packages/data/src/credentials/tenantKeysStore.ts` (new):
   - `export interface TenantDataKey { tenantId: string; dataKey: Buffer }`.
   - `getTenantDataKey(client: Queryable): Promise<TenantDataKey | null>`.
     - It runs `SELECT tenant_id, wrapped_key, wrap_nonce, master_key_version FROM tenant_keys WHERE tenant_id = app_tenant_default()`. The explicit filter sits on top of RLS, so a superuser connection cannot pick another tenant's row.
     - It unwraps with `resolveMasterKeyFromEnv(master_key_version)` and the row's `tenant_id`. An unwrap failure propagates.
   - `getOrCreateTenantDataKey(client: Queryable): Promise<TenantDataKey>`:
     - returns the existing key if there is one;
     - otherwise resolves `SELECT app_tenant_default()`. When that is `NULL` it throws `Error("No tenant scope: refusing to create a tenant data key")` and inserts nothing;
     - else generates a key, wraps it under master key version `1`, runs `INSERT … ON CONFLICT (tenant_id) DO NOTHING` and reads the row back, so two concurrent creators end up with the same key.
     - It works both on a `Pool` and inside a transaction.
   - Never log key material.
4. **ADR** `docs/adr/<date>-per-tenant-envelope-encryption.md`. It records:
   - the decision above, including the associated-data formats: the wrap AD is `semprec:tenant-key:v1:<tenantId>`, and credentials will use `tenant_id‖item_id`;
   - wrap versioning through `master_key_version`;
   - the rollout order: dual read in one release, tenant-key writes and re-encryption only after that release runs in production, then retirement of the old scheme;
   - crypto-shredding by deleting the key row;
   - the backup split, which bounds shredding to 7 days.

   Rejected alternatives: master key plus associated data only (no shredding); DEKs inside the main dump (shredding defeated for 12 months); a key per credential (more keys, no isolation gain).

## Acceptance criteria

**Unit** — `credentialEnvelope.unit.test.ts`, importing only `@semprec/credentials`:
- `sealSecret` → `openSecret` with the same key and associated data returns the plaintext.
- Different associated data, one flipped ciphertext byte, or a different key each throw. The thrown error has no `code` property.
- Two seals of the same plaintext produce different nonces and ciphertexts.
- A key that is not 32 bytes throws.
- `wrapDataKey` → `unwrapDataKey` with the same tenant id returns the key; with another tenant id it throws.

**Integration** — `tenantKeysStore.test.ts`, using the harness from #975 in `backend/packages/data/src/testSupport/testDb.ts`: `createTestTenant(pool)`, `createRuntimeRolePool(adminPool, role)` and `withTenantTransaction(pool, tenantId, fn)`, which sets `app.tenant_id` for the transaction. The store itself needs nothing beyond `app_tenant_default()`.
- The first `getOrCreateTenantDataKey` in tenant zero's scope inserts exactly one row with `master_key_version = 1` and returns a 32-byte key. A second call returns the same bytes and still leaves one row.
- Two concurrent `getOrCreateTenantDataKey` calls in one tenant return identical keys and leave one row.
- Tenants A and B get different keys. In B's scope, `getTenantDataKey` never returns A's key, and a `semprec_side` pool sees no row of A in `tenant_keys`.
- After A's `wrapped_key` and `wrap_nonce` are written into B's row (superuser), `getTenantDataKey` in B's scope throws.
- With two tenants and no scope set, `getOrCreateTenantDataKey` throws and inserts nothing.
- As `semprec_side`, `UPDATE tenant_keys` fails with a permission error, while `SELECT`, `INSERT` and `DELETE` work within the own tenant.
- The tenancy catalog test passes with the new table.
