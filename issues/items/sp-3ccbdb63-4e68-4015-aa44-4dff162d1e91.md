### Requirement gh-2004: [calendar-ics 04/06] Import downloaded ICS feeds into subscribed events

#### Context

Model tier rationale: This parses untrusted feed content, converts time zones into the tenant's wall-clock model and keeps a system-owned database in sync by upsert and soft delete in chunked transactions, so a mistake corrupts or loses the stored events of every subscription.

#1960 downloads each subscription calendar's feed on a schedule and hands a changed body to a consumer registered with `registerCalendarFeedConsumer`; no consumer is registered yet, so a downloaded feed is only recorded as fetched. #1962 adds the read-only `subscribedEvents` database (system-owned by the calendar module) where the events of a feed are stored. This issue provides the consumer that turns a feed body into stored subscribed events. Time conversion uses the calendar time module of #1418 (the tenant's wall-clock model). #2005 shows the stored rows in the calendar timeline, and #1966 adds recurrence on top of this importer.

Decisions:
- The feed parser is the library `ical.js`, added as an exact pinned 2.x version dependency of `@semprec/data` (the backend has no iCalendar parser today); the parse runs on the already size-capped body from #1960, inside a try/catch that turns a malformed feed into a recorded failure (the consumer throws, so #1960 keeps its validators) without changing stored events.
- Timed events: DTSTART and DTEND (including `TZID` and UTC `Z` forms) are converted to the tenant's wall-clock time with the module from #1418; the original zone name is kept in `timeZone`. Floating times (no zone) are taken as already in the tenant's wall-clock time.

- Recurrence is not interpreted here: components with `RECURRENCE-ID` are skipped, and a component with `RRULE` is stored as a single event at its own start. #1966 replaces that.
- Upsert key is `(calendar, uid)`. An unchanged event is not rewritten (no `updated_at` change, no invalidation).
- A UID that disappears from the feed is moved to the trash through the choke point (soft delete), never deleted permanently; the existing 30-day purge removes it, and a UID that reappears later is created as a new item.
- Import runs in chunked transactions for large feeds (`docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`).
- All writes use the choke point with the system owner process `calendar` (`systemOwnerProcess`), so the generic ownership check keeps refusing user, agent and `/mcp` writes.

### Requirement gh-1966: [calendar-ics 06/06] Expand recurring subscribed events

#### Context

Model tier rationale: Expanding RRULE with exceptions and overrides across time zones and daylight-saving changes inside the shared timeline is intricate, and a mistake shows wrong events to every reader.

Many subscribed feeds contain repeating events (weekly meetings, yearly anniversaries). #2004 imports each event once and skips overrides; this issue makes repeating subscribed events appear on the right days. The recurrence model for Tasks and Events is the one recorded in the recurrence ADR (#1365): occurrences are virtual, computed when the timeline is read, and an exception is materialized only when needed; #1877 expands Events' own rules in the timeline and this issue feeds subscribed events into the same expansion. Subscribed events are read-only (all properties owner `system`, process `calendar`), so nothing is ever materialized for them: exceptions and overrides are data on the stored rows.

Decisions:
- Three further `subscribedEvents` properties, all `owner: 'system'`, `ownerProcess: 'calendar'`: `recurrenceRule` (text, the feed's `RRULE` value verbatim), `exceptionDates` (text, a JSON array of the excluded occurrences' original starts as tenant wall-clock ISO strings, from `EXDATE`), and `recurrenceId` (text, nullable, the overridden occurrence's original start as a tenant wall-clock ISO string, set only on override rows).
- An override (`RECURRENCE-ID`) is stored as its own row with the same `uid` as its master, `recurrenceId` set; the upsert key becomes `(calendar, uid, recurrenceId)`. On expansion, an occurrence whose original start equals an override's `recurrenceId` is replaced by the override.
- Supported `RRULE` parts: `FREQ` (DAILY, WEEKLY, MONTHLY, YEARLY), `INTERVAL`, `COUNT`, `UNTIL`, `BYDAY`, `BYMONTHDAY`, `BYMONTH`. A rule using any other part is not expanded: the event is shown once at its own start, the import continues, and the unsupported rule is counted in a log line without feed content.
- Occurrences are computed in the event's original time zone and then converted to the tenant wall-clock model, so a 09:00 New York series keeps its local meaning across daylight-saving changes.
- Expansion is limited to the timeline's requested range; an unbounded series produces no more rows than the range needs.

### Requirement gh-1971: [calendar-events 12/12] Drop includeTime from the Events date config

#### Context

Model tier rationale: A single contract step (seed plus direct-SQL cutover on a `schema_locked` database) with an existing pattern, but it edits persisted schema config for every tenant and must land in a later release than the migration it follows.

The Events `date` property is declared with `config: { includeTime: true }` in `backend/packages/data/src/seed/seedTenDatabases.ts`.
