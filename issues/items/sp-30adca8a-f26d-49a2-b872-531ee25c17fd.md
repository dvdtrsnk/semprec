## Context

Model tier rationale: Changes what one malformed provider item does to a whole account's calendar sync in the Graph and Google adapters, which decides between a stalled account and a dropped Event.

Review finding on the internet-accounts branch, verified in the code: one Event a provider sends that does not match the adapter's schema fails every pass of the account, forever.

- Graph: `deltaRound`, `seriesChanges` and the instance listings parse each item with `parseOrInvalid(graphEventSchema, …)` (a strict `type` enum, integer `reminderMinutesBeforeStart`, …); the mapping's `instantOf`, `originalStartOf`, `scheduleOf` and `seriesStartOf` throw `invalidResponse` for an unreadable time; an occurrence without `seriesMasterId` throws too. Any of these ends the pass.
- Google: `eventsPageSchema` validates `items` as `z.array(googleEventSchema)` (integer reminder minutes, non-negative integer `sequence`, …), so one bad item fails the page; the master read of an incrementally touched series is strict too.
- CalDAV already leaves an unreadable resource out and logs a count (`caldavAdapter.ts` `parseResources`).

Decisions:

- Inside a fetch, an item that is no readable Event is left out and counted in a log line without its content: Graph logs one count per round (`unreadable`), Google one `unreadableEvent` tag per item (as its other skips). Only an unusable page envelope (`value`/`items` not a list, no `deltaLink`, …) still fails the pass.
- Graph: an unreadable time anywhere in a series (master or instance) leaves the whole series out of the fetch, neither upserted nor deleted, since an instance that cannot be placed would read as a deleted occurrence. Graph's mapping errors become `GraphEventUnreadableError`, a subclass of the `invalidResponse` provider error, so `getEvent` and the write paths fail exactly as before.
- Google: a page's items are parsed one by one in the listings (events, a series' instances, the override's instance lookup), and an incrementally touched series whose master cannot be read is left out; `getEvent` and `respondToInvitation` stay strict.
- As for CalDAV, a full fetch then treats the stored copy of a left-out Event as one the provider no longer lists.

## Scope

### In scope

- The fetch paths of the Graph and Google adapters.

### Out of scope

- The calendar listings (a calendar left out would read as removed), the create paths, CalDAV, the apply.

## Acceptance criteria

- A Graph delta round with an item of an unknown `type`, one with an unreadable start, an occurrence without its series and one without an id answers every other Event of the round and logs `{ unreadable: 4 }`.
- A Graph series with an instance whose `originalStart` cannot be read is neither upserted nor deleted; the round's singles are.
- A Graph page whose `value` is not a list still fails as `invalidResponse`.
- A Google pass whose first events page holds three items outside the event schema syncs every other event and logs three `unreadableEvent` skips without the items' content.
- The existing Graph and Google adapter tests stay green.
