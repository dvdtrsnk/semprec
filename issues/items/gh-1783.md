## Context

Model tier rationale: One search mechanism (a stored text-search vector, its index and a query over it) built on an existing Czech search configuration and query shape, with a table-wide migration and several writers of message text, but it neither crosses tenants nor changes authorization.

The thread search of #1737 matches titles and the preview line only. Users also remember what was said inside a conversation. This issue lets the same search find a thread by the text of any of its messages, with inflected forms and without diacritics ("faktury" finds "faktura", "uctenka" finds "účtenka").

Today full-text search exists only for mail: `item_search_index.search_vector`, computed by the application with `to_tsvector('czech', ...)` (`backend/packages/data/src/mail/search.ts`). The `czech` configuration is `unaccent` + `simple` (migration `0006`) and is switched to Hunspell once `activate_czech_hunspell_search()` runs (`0046`); with Hunspell a recognised word is indexed as its lemma with diacritics, so a query without diacritics only matches through a fallback. The matching rules that serve both cases (one combined vector from the `czech` and `czech_simple` configurations, and a query of lemma-or-prefix terms joined by AND, passed as one parameter) are introduced by #1589; this issue reuses them.

Decision: the history search is part of the plan but sits behind a product decision; the issue is complete in itself and is implemented only after that decision is made. Until then the thread list searches titles and previews only.

Decision: the vector is `to_tsvector('czech', text) || to_tsvector('czech_simple', text)`, one column per message, as #1589 does for items. System messages (those with a `system_key`) are not indexed, and messages without text (a reply that is still being produced) have a NULL vector until their text is written.

Decision: no snippet is returned. The list row stays as it is.

In every writer of message text, compute `search_vector` in the same statement on every insert of a non-system message with text and on every update that sets or changes `text`: the user and assistant message inserts of #1620 (`sempThreads/sempThreadsStore.ts`; confirm the file name against that PR), the assistant-text update of #1727 (`semp/sempMessagesStore.ts`; confirm the file name against that PR), and the tick reply insert `finishTickRunWithMessage` in `semp/sempTickThreadStore.ts`. 3. Export `reindexSempMessageSearch(client, { limit, afterMessageId?, onlyMissing })` (the shape of `enqueueItemSearchBackfill`'s options from #1397) that recomputes the vector of up to `limit` non-system messages with text in `id` order after the cursor and returns the last `id` it processed (`null` when none is left), so a caller loops to the end; `onlyMissing: true` restricts it to messages whose vector is NULL. Operators run it with `onlyMissing: true` once after the migration, for the messages that existed before it, and with `onlyMissing: false` after the Hunspell configuration is activated (the stored vectors of earlier messages keep their old lemmas until then); it is not scheduled here.
4. Extend the `q` filter of the thread list (`sempThreadsListStore.ts`, from #1737): a thread also matches when it has a non-system message whose `search_vector` matches the tsquery built by the shared builder of #1589 (terms ANDed, each term lemma OR prefix, the whole query passed as one parameter). The title and preview matches of #1737 stay; a thread matches if either rule does.
5. Tests (the Hunspell cases in the style of `backend/packages/data/src/__tests__/czechHunspellSearch.test.ts`, `withFreshDatabase` and `installAssets` with its `cs_cz` fixture, which lists "faktura", because CI has no Hunspell dictionary): "faktury" finds a thread whose message says "faktura" with Hunspell active, and "uctenka" finds "účtenka" in both modes; two words in one query must both be present (in the same or in different messages of the thread); a system message and a message without text never match; filling the text of an assistant message updates the vector; the backfill indexes existing messages; the query uses the GIN index (explain plan check on a seeded table); another tenant's messages never match.

## Acceptance criteria

- When a message says "faktura" and Hunspell search is active, then `q=faktury` returns its thread.
- When a message says "účtenka", then `q=uctenka` returns its thread in both configurations.
- When `q` has two words that appear in different messages of one thread, then the thread is returned.
- When a system message contains the word, then the thread is not matched by it.
- When the worker writes the text of an assistant message, then the thread becomes findable by that text.
