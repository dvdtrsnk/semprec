## Context

Routes built on the adapter serialise a `ChokePointError` through `toErrorResponseBody` in `backend/services/semprec-api/src/adapter/errorContract.ts`, whose `safeDetails` (lines 98-106) forwards `details` only when it is a flat record of primitives and drops anything else, precisely so a future call site raising an error with a raw row, a foreign key or a file path as `details` cannot leak it (docstring, lines 90-96). The bespoke handlers do not go through it. Each answers `sendJson(res, err.status, { error: err.message, code: err.code, details: err.details })` verbatim:

- `authHandler.ts` line 250
- `setupHandler.ts` line 87
- `notificationsHandler.ts` line 75
- `approvalRequestsHandler.ts` line 134
- `agentRunHandler.ts` line 135
- `mcpAgentPageHandler.ts` line 131
- `schemaHandler.ts` line 54
- `mcp/mcpHandler.ts` lines 199, 203 (`rpcError(..., err.details)`), 207 (`{ code, details: err.details }`) and 218

A `ConflictError` raised with `{ current: ItemRow }` (the shape `chokePoint/itemsStore.ts` uses) or any error carrying a nested object would be sent whole. Today's reachable details happen to be flat, so this is hygiene against the next call site, not an observed leak.

Depends on #637, which edits every one of these handler files first.

## Task

- In `errorContract.ts`:
  - Export the existing primitive-only filter under the name `publicErrorDetails(details: unknown): Record<string, string | number | boolean | null> | undefined` (rename `safeDetails`, keep its body and docstring; `toErrorResponseBody` calls the renamed function).
  - Add and export `toPublicErrorBody(err: ChokePointError): { error: string; code: string; details?: Record<string, string | number | boolean | null> }` returning `{ error: err.message, code: err.code, details: publicErrorDetails(err.details) }` — the bespoke handlers' existing top-level shape (`error` is the message string, unlike the adapter's `{ error: { code } }` envelope), kept as is per `docs/adr/2026-09-11-additive-only-rest-contract-no-url-versioning.md`; only `details` changes, and only when it was never a documented flat record.
- In each of the seven bespoke handlers listed above, replace the verbatim object literal with `toPublicErrorBody(err)` (import from `./adapter/errorContract.js`).
- In `mcp/mcpHandler.ts`: line 218 → `toPublicErrorBody(err)`; line 207 → `{ code: err.code, details: publicErrorDetails(err.details) }`; lines 199 and 203 → `publicErrorDetails(err.details)` as the `data` argument (an `ApprovalRequiredError`'s `{ approvalRequestId, link }` and a `ValidationError`'s `{ field }` are flat and pass through unchanged).
- Tests:
  - `backend/services/semprec-api/src/adapter/__tests__/errorContract.unit.test.ts` (unit tier): `toPublicErrorBody` keeps `error` (message) and `code`; passes a flat `{ field: "x" }` through; returns `details: undefined` for `{ current: { id: "..." } }`, for an array, and for a string; `publicErrorDetails` is exported and behaves identically to the existing "drops details that aren't a flat record of primitives" case.
  - New `backend/services/semprec-api/src/__tests__/bespokeHandlerErrorBodies.unit.test.ts` (unit tier, no Postgres): reads the source of the eight handler files above with `node:fs` and asserts none contains the substring `err.details` — the only permitted occurrences live in `adapter/errorContract.ts`. This is the per-handler guarantee: a handler cannot regress to forwarding details without failing this test, and it needs no way to inject a nested-details error through HTTP.

## Scope

### In scope

- One exported public-error projection applied by every bespoke handler and the MCP JSON-RPC error paths.

### Out of scope

- Unifying the bespoke `{ error: message, code, details }` shape with the adapter's `{ error: { code, details } }` envelope — deliberately not in this batch.
- `/mcp` cookie authentication — sibling issue B9 of this batch (sequenced after this one because it edits the same `mcpHandler.ts`).
- Changing any `err.message` text, or the `413` / `500` branches of the handlers.

## Acceptance criteria

- When a bespoke handler catches a `ChokePointError` whose `details` is a nested object, an array or a non-object, the response body's `details` is absent; when `details` is a flat record of primitives, it is forwarded unchanged; `error` and `code` are unchanged in both cases.
- `grep -rn "err.details" backend/services/semprec-api/src --include=*.ts --exclude-dir=__tests__` matches only `adapter/errorContract.ts`, and `bespokeHandlerErrorBodies.unit.test.ts` enforces that.
- Every existing case in `errorContract.unit.test.ts`, `mcpHandler.test.ts` (including the `-32001` approval-required `data.approvalRequestId` and `-32602` cases) and the handler test files still passes unchanged.
