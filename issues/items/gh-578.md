**Blocked by:** #571

## Context

In the review follow-ups pipeline (epic #565), the triage agent reads the triage input file (#571's `input-file.mjs`: `{ version, harvestIssue, findings, prSummaries, openIssues }`, each finding identified by `(pr, key)`). It verifies each finding, decomposes the valid ones into issue drafts, audits them and writes a **proposal file**. Before anything reaches GitHub, a deterministic **validate** step checks that file. The agent gets the violations back and fixes the proposal; after two failed rounds the run parks. The `publish` step (a later issue) validates again before it writes. This issue defines the proposal format and the validator, and is the only place the format is defined. The triage skill (a later issue) documents it for the agent by pointing here.

What the validator enforces comes from `.github/ISSUE_FORMAT.md` and the approved epic:

- **Completeness.** Every finding from the input lands in exactly one terminal state: in exactly one draft, or in exactly one rejection with a reason. Nothing is dropped, nothing is invented.
- **Relay-parseable issues.** Relay reads an issue's blockers from the first line containing "blocked by". So the first line of every draft is `**Blocked by:** none` or a comma-separated list of references. Draft titles are `[<batch-slug> NN/MM] …`, numbered in topological order: every draft comes after the drafts it is blocked by. The batch slug is `followups-<harvest issue number>`.
- **Section order.** `## Context`, `## Task`, `## Touches`, `## Scope` (with `### In scope` and `### Out of scope`), `## Acceptance criteria`.
- **In-batch references.** Drafts do not have issue numbers yet, so a draft refers to another as `{{draft:<id>}}`. `publish` replaces it with the real `#N` after creating the issues in order.
- **No pipeline markers.** `publish` appends the ledger markers (`<!-- crb-followup:v1 … -->`) itself. A body that already contained one could forge a ledger entry.
- **Epic.** An epic is present exactly when there are two or more drafts, titled `[followups-<H>] … — epic`, and links back to the harvest issue. It lists no drafts, because GitHub renders sub-issues itself (ISSUE_FORMAT's epic rule).
- **Protected paths.** A draft whose Touches name a path under `.relay/`, under `.github/workflows/`, or `.github/scripts/check-protected-paths.mjs` must say `maintainer-implemented` in its Task. Relay refuses those paths, so such an issue must never be armed.

## Task

Create `.github/scripts/review-followups/validate.mjs`, a zero-dependency ES module and CLI whose header comment is the reference description of the proposal format, exporting:

1. `VERDICTS` — a frozen array: `already-fixed`, `invalid`, `not-worth`, `already-tracked`.
2. `validateProposal(input, proposal)`. `input` is a parsed triage input file; `proposal` is any parsed JSON value. Returns an array of violation strings; empty means valid. It never throws on a malformed proposal and reports every violation it finds, not only the first. Each violation names the draft id or the `(pr, key)` it concerns. The proposal format is `{ version, harvestIssue, epic, issues, rejected, advisories }` with exactly these rules:
   - `version` is `1`; `harvestIssue` equals `input.harvestIssue`; `advisories` is an array of strings.
   - `epic` is `null` or exactly `{ title, body }`, both non-empty strings.
   - `issues` is an array of exactly `{ id, title, body, findings }`:
     - `id` is kebab-case (`^[a-z0-9]+(-[a-z0-9]+)*$`) and unique;
     - `findings` is a non-empty array of exactly `{ pr, key }` (positive integer, ten lowercase hex characters).
   - `rejected` is an array of exactly `{ pr, key, verdict, reason }` plus `trackedBy`:
     - `verdict` is in `VERDICTS`; `reason` is non-empty after trimming;
     - `trackedBy` is a positive integer when `verdict` is `already-tracked`, and absent otherwise.
   - **Completeness.** Every input finding's `(pr, key)` appears exactly once across all `issues[].findings` and `rejected`. No `(pr, key)` outside the input appears.
   - **Titles.** With `MM` = the number of drafts, zero-padded to two digits, draft number `i` (1-based, in array order) is titled `[followups-<H> NN/MM] <text>`, where `NN` is `i` zero-padded and `<text>` is non-empty.
   - **Blocked-by line.** The first line of each draft body is exactly `**Blocked by:** none`, or `**Blocked by:** ` followed by `, `-separated references. Each reference is `#<positive integer>` other than `#<H>`, or `{{draft:<id>}}` naming another draft that comes earlier in the array.
   - **Headings.** Each draft body contains the lines `## Context`, `## Task`, `## Touches`, `## Scope`, `### In scope`, `### Out of scope` and `## Acceptance criteria`, each exactly once, in that order.
   - **Placeholders.** Every `{{draft:<id>}}` in a draft body names an existing draft other than itself. The epic body contains no `{{draft:`.
   - **Markers.** No body (drafts and epic) contains `<!-- crb-followup`.
   - **Length.** No body (drafts and epic) exceeds 60,000 characters. GitHub's limit is 65,536, and `publish` appends markers.
   - **Epic presence.** With two or more drafts `epic` is non-null; otherwise it is `null`. The epic title is `[followups-<H>] <text> — epic`, and its body contains `#<H>` not followed by a digit.
   - **Protected paths.** A draft whose `## Touches` section mentions a path starting with `.relay/` or `.github/workflows/`, or the path `.github/scripts/check-protected-paths.mjs`, contains `maintainer-implemented` in its `## Task` section.
3. `main(argv)`, called only when the module is executed directly, with the command line `node validate.mjs --input <input.json> --proposal <proposal.json>`:
   - it parses the input with #571's `parseInputFile` and the proposal as JSON;
   - with no violations it prints one `ok` line with the counts and exits 0;
   - otherwise it prints each violation on its own line starting with `- ` and exits 1;
   - an unreadable file, invalid JSON or a missing argument exits 1 with one line saying which.
4. `validate.test.mjs` next to it (`node:test`, `node:assert/strict`), covering every Acceptance criterion below.

## Scope

### In scope

- The proposal format, `validateProposal`, the CLI and tests.

### Out of scope

- Judging a draft's content (whether the fix is right, whether it is well split). That is the triage agent's audit.
- Writing anything to GitHub. The `publish` issue in this batch does that.
- Checking `#N` references against GitHub. The validator works offline.

## Acceptance criteria

1. A proposal with three drafts in valid topological order, an epic, two rejections (one `already-tracked` with `trackedBy`) and an advisory, covering every input finding once, returns `[]`.
2. A missing finding, a finding in two drafts, a finding in a draft and in `rejected`, and a `(pr, key)` not in the input each yield a violation naming that `(pr, key)`.
3. A rejection with an unknown verdict, a blank `reason`, `already-tracked` without `trackedBy`, and `not-worth` with `trackedBy` each yield a violation.
4. Title violations are reported for `[followups-<H> 1/3]`, a gap in numbering, a wrong `MM`, the wrong harvest number, and an empty title text.
5. A body whose first line is not the Blocked-by line, whose Blocked-by line mixes `none` with a reference, references `#<H>`, or references a later draft or an unknown draft id, is reported. `**Blocked by:** #12, {{draft:a}}` referencing earlier draft `a` is valid.
6. A body missing `## Touches`, with `## Task` before `## Context`, or with `### Out of scope` twice is reported.
7. A `{{draft:x}}` for an unknown id, or for the draft itself, is reported, as is any `{{draft:` in the epic body.
8. `<!-- crb-followup` in a draft body or the epic body is reported.
9. A draft body or epic body of 60,001 characters is reported.
10. Two drafts with a `null` epic, one draft with an epic, an epic title without `— epic`, and an epic body without `#<H>` (or only with `#<H>1`) are each reported.
11. A draft whose Touches list `.github/workflows/ci.yml` and whose Task lacks `maintainer-implemented` is reported. With the phrase present, it is not.
12. A non-object proposal, `issues` not an array, a draft with an extra field, and a duplicate draft id are reported without `validateProposal` throwing.
13. The CLI exits 0 with an `ok` line for a valid pair of files. It exits 1 listing `- ` lines for an invalid proposal, and exits 1 with one line for a missing file, for invalid JSON, and for a missing argument.
14. `node --test .github/scripts/review-followups/validate.test.mjs` passes with no network access.
