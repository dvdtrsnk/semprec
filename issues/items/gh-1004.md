## Context

Today the AI gateway's daily and monthly caps are two `owner: "user"` properties of the single System settings item. `seedSystem` creates `dailyBudgetUsd` and `monthlyBudgetUsd` with the values `50` and `null` (`backend/packages/data/src/seed/seedSystem.ts:169-195`), and `0019_settings_ai_budgets.sql:26-32` retrofits them onto older installs. `getAiBudgets` and `getAiBudgetsWithTimezone` read them (`backend/packages/data/src/systemSettings.ts:72-112`). A missing daily key falls back to `DEFAULT_DAILY_BUDGET_USD = 50` (`:9`, `:74`) and a missing monthly key to `null`. An explicit `null` means "no cap for that window". Any session or agent can patch these properties, and they hold one value for the whole install.

With multiple tenants the caps belong to the operator's admin. They move to a new global table `tenant_ai_budgets` with one row per tenant. Admin routes write it (#1039), the gateway reads it (#1035), and so does the user's own usage report (#1048). The semantics are fixed for every sibling issue:

- A tenant **without a row** may not spend at all (fail closed). A new tenant has no row until an admin sets caps.
- Within a row, a `NULL` cap means that window has no per-tenant cap. The operator's global safety cap from #1035 still applies.

The current user's tenant ("tenant zero", created with the `tenants` table and the tenancy SQL functions by #968) keeps exactly today's caps.

This issue only creates and seeds the table and adds its read accessor. Nothing reads the table yet: the gateway keeps reading the settings item until #1035.

## Task

Load `db-migrations` (a new table plus a data seed in one migration) and `state-writes` (a store over rows that later issues write).

1. **Migration** (take the next free ordinal at commit time; additive):
   ```sql
   CREATE TABLE IF NOT EXISTS tenant_ai_budgets (
     tenant_id uuid PRIMARY KEY REFERENCES tenants(id) ON DELETE CASCADE,
     daily_cap_usd numeric CHECK (daily_cap_usd >= 0),
     monthly_cap_usd numeric CHECK (monthly_cap_usd >= 0),
     updated_at timestamptz NOT NULL DEFAULT now(),
     updated_by uuid REFERENCES users(id) ON DELETE SET NULL
   );
   COMMENT ON TABLE tenant_ai_budgets IS 'semprec:tenancy=global';
   GRANT SELECT ON tenant_ai_budgets TO semprec_side;
   GRANT SELECT, INSERT, UPDATE ON tenant_ai_budgets TO semprec_data;
   ```
   - This is a global table: it gets no `tenant_id` default and no row-level security. It is operator configuration keyed by tenant. The tenancy catalog test from #971 must pass because of the comment.
   - Grants, explained in a migration comment:
     - `semprec_side` (the gateway's role, `docs/operations/database-roles.md:27`) gets `SELECT` only. The gateway must never be able to raise its own caps.
     - `semprec_data` (semprec-api) gets `SELECT, INSERT, UPDATE`. Its admin cap route (#1039) will be the only writer.
     - Nobody gets `DELETE`: a row disappears only with its tenant, through the cascade.
   - In the same migration, seed one row per existing tenant. Only tenant zero can exist, because the single-tenant guard is still in place. Read the caps from that tenant's System settings item: `items` of the `databases` row with `owner_module_id = 'systemSettings' AND system`, joined on `databases.tenant_id = tenants.id`. Map the values exactly as `toAiBudgets` does today:
     - key absent: `50` for daily, `NULL` for monthly;
     - JSON `null`: `NULL`;
     - JSON number: that value, clamped with `GREATEST(value, 0)`. A negative cap refuses every call today, and `0` keeps that.
     - Any other JSON type makes the migration fail with an exception naming the property.
   - If the tenant has no settings item yet, use the defaults `50`/`NULL`. This is the fresh-install case: `deploy/deploy.sh:137-150` runs the migrations before the seed. `updated_by` stays `NULL`, which marks a row no admin has written. Use `INSERT … ON CONFLICT (tenant_id) DO NOTHING`.
   - Keep the whole file safe to execute a second time (`IF NOT EXISTS`, the conflict-ignoring seed), so tests can re-run it.
2. **Store** — new file `backend/packages/data/src/aiGateway/tenantAiBudgetsStore.ts`:
   - `export interface TenantAiBudget { tenantId: string; dailyCapUsd: number | null; monthlyCapUsd: number | null }`
   - `export async function getCurrentTenantAiBudget(client: Queryable): Promise<TenantAiBudget | null>` runs `SELECT tenant_id, daily_cap_usd, monthly_cap_usd FROM tenant_ai_budgets WHERE tenant_id = app_tenant_default()`. `app_tenant_default()` is #968's transitional function: the tenant of the current scope, or the sole tenant while only one exists. It is the same tenant the row-level-security policies resolve.
   - Read the row with a type argument. `numeric` arrives as a string; convert it with `Number`. Return `null` when there is no row, which includes the case where no tenant resolves.
3. **Export** the store from `backend/packages/data/src/index.ts` with one line after `./aiGateway/aiUsageReport.js` (`:126`). Add `getCurrentTenantAiBudget` to `EXPECTED_RUNTIME_EXPORTS` in `backend/packages/data/src/__tests__/publicSurface.test.ts`, which freezes the package's runtime exports (`:537-538`).
4. **Grant coverage.** #962's assertion in `backend/packages/data/src/__tests__/leastPrivilegeRoles.test.ts` requires full DML for both runtime roles on every non-choke-point table; add `tenant_ai_budgets` to its exceptions (`SELECT` only for `semprec_side`, no `DELETE` for `semprec_data`), the same way #976 narrows it for the identity tables.
5. **Tests** go in `backend/packages/data/src/__tests__/tenantAiBudgets.test.ts` (new, integration).
   - `resetDatabase` runs `TRUNCATE users … CASCADE` (`backend/packages/data/src/testSupport/testDb.ts:65-66`). Through the `updated_by` foreign key that also empties this table, so every test creates the rows it needs.
   - Seeding cases delete the row, prepare the settings item, and execute the migration file again, as `settingsAiBudgetsMigration.test.ts:10-13` does for `0019`.
