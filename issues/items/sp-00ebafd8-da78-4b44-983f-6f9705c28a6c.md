### Requirement gh-1726: [semp-pages 04/09] Merge duplicate journal entries of one period

#### Context

Model tier rationale: It merges two live records atomically across page content, several relation kinds and the trash, including edges owned by another process, so a partial failure would lose content or links.

A period (day, week, month) should have exactly one Journal entry, and #1666 stops a restore from creating a second live entry. Duplicates can still exist from earlier data. Journal entries have a page (document), relations such as the area and, after #1545, a project; Inbox items point at a day through a relation owned by the inbox process (`journalDay`), which must be changed with delete plus create using `ownerProcess: 'inbox'`, as #1666 does for a reservation. Decision: the oldest entry survives; the duplicate is trashed (recoverable for 30 days), never hard-deleted.

Decision: a merge changes links, so it never runs silently. The assistant prevents duplicates and only proposes a merge; this function runs after the user approves it, through an approval-gated operation added by #2017. The weekly cleanup heartbeat (#1883) finds the duplicated periods for the assistant and does not call this function itself.

### Requirement gh-1723: [subpages 07/12] Trash and restore a page with its subpages and parent block

#### Context

Model tier rationale: A destructive, recursive write that changes two documents and several items inside the trash transaction, with all-or-nothing rollback, an epoch rule for restore and cross-document position handling, so mistakes lose or duplicate user content.

Deleting a record is the generic `DELETE /api/items/:id` and restoring is `POST /api/items/:id/restore` (`backend/packages/data/src/chokePoint/itemTrash.ts`); both cascade only through inline databases, and the document of an item is removed only when the trash is purged after 30 days (`docsStore.deleteDocByItemId`). A subpage is an item of the hidden `pages` database with a `page` block in its parent's document (#1393, #1676); nothing in the generic cascade reaches either. There must be no `DELETE /api/pages/:id`: it would be CRUD over module data and would bypass the approval an agent needs for `item.delete` (`backend/packages/shared/src/genericOperations/capabilities.ts`). #1601 adds delete and restore hooks to the choke point: the delete hook runs for every row actually trashed in the call, root first, after its soft delete, with the shared `deletedAt`; the restore hook runs for every row actually restored; an error from a hook rolls back the whole cascade.

This issue registers those hooks for Pages items. Deleting a page trashes its subpages and removes its block from the parent document; restoring it brings them back. A host (a project, an area, an event, a Journal day) that is deleted trashes its subpages in #1763; the list of trashed pages is #1855; orphaned pages are swept by #1749; the delete impact preview (#1856) uses the subtree helper added here to state the total number of nested pages a deletion trashes (decided by the product owner: the confirmation states the full impact, all nested pages, not only direct subpages). Deleting a page block in the editor is the deletion of that page through `DELETE /api/items/:id`: the subpage goes to the trash in the same transaction, the client shows a toast with Undo, and Undo is the restore below, which puts the block back at its place (decided by the product owner); the orphan sweep (#1749) stays a safety net.

Decisions:
- Every trashed page, whether it is the deleted root or was trashed as a descendant, removes its own `page` block from its parent's document, and every restored page puts it back. The rule is uniform, so a page restored on its own appears in its parent again.
- The position of the removed block is kept in the parent document itself, in a top-level `Y.Map` named `trashedPages` keyed by the page id with `{ blockId, afterBlockId, indent }`; the entry is deleted when the block is put back. The trashed Pages item is not written (the choke point does not update trashed rows). Entries of pages that are purged stay in the document.
- Restore puts the block back after `afterBlockId` if that block still exists, otherwise at the end of the parent document, with the page's current `title` as its text; if the parent has no document (purged) or already holds a block for the page, nothing is inserted.
- Descendants are restored only if they were trashed in the same transaction as the root (same `deletedAt`); a subpage that was trashed on its own earlier stays in the trash.

Shared-file ordering: this issue also waits for #1718 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1722: [subpages 06/12] Duplicate a page with its whole subtree

#### Context

Model tier rationale: One recursive copy over existing creation, document-write and path seams in a single transaction with a size cap, verified with real documents, but identity remapping across a whole subtree needs care.

A user can duplicate a page: the copy is a sibling next to the original, titled with a "copy" suffix, and it contains a copy of every nested subpage. The design copied only one level and shared the nested pages between original and copy; the server must copy the whole tree so editing the copy never changes the original. #1676 created the `pages` database, the `page` block (whose `pageId` is the Pages item id and whose text is the title), `page.createSubpage` and the parent link `parentItemId`. The shared block model (#1539) reads a document with `readPageBlocks` and writes blocks with `writeBlock` and the operations of #1610, which refuse to duplicate `page` blocks (`page_conversion_required`) because copying a page needs database work; this issue is that database work. Page operations are generic catalog members (#1394).

Decisions:
- `page.duplicate` accepts a Pages item only; a host item (a project, an area, an event) is a `ValidationError` on `pageItemId`.
- Only the root of the copy gets the suffix, localized with the caller's locale through the docs i18n catalog (" (kopie)" for Czech, " (copy)" for English); nested copies keep their titles.
- The copy is placed in the parent document right after the original's `page` block; if the original is an orphan (no block references it), the copy goes to the end of the parent document.
- A `page` block whose page is trashed, purged or missing is not copied (the block is left out of the copy), and a page that appears twice in one tree is copied once per reference as an independent page; cycles are cut by a visited set.
- The copy is capped at 500 pages in total (`MAX_DUPLICATE_PAGES`); a larger tree is a `ValidationError` and nothing is written.
- Copies keep the block order, types, indent, `done` and inline formatting; every block id, page item id and document id is new.

### Requirement gh-1725: [subpages 08/12] Rename a subpage from its own screen

#### Context

Model tier rationale: One operation that writes two places in one transaction (the Pages item and the parent document) over existing item-write and document-write seams, with a clear no-op and orphan behavior.

### Requirement gh-1749: [subpages 09/12] Sweep orphaned subpages into the trash

#### Context

Model tier rationale: A per-tenant background sweep over existing fan-out, chunking and trash seams, but it decides what to trash from document contents, so the orphan rule must be conservative.

A page is created together with its block and removed together with it by the operations of #1676 and #1723, but clients edit documents directly over the sync socket, which writes Yjs updates and runs no domain code. A block of type `page` deleted that way (for example by selecting and deleting it in the editor) leaves the Pages item and its document alive with nothing pointing at them. Per-tenant background work fans out with `forEachActiveTenant` (decision record `2026-10-06-system-work-fans-out-per-tenant`) and large sweeps run in chunked transactions (`2026-09-28-chunked-transactions-for-large-background-sweeps`); the core cron entries are in `CORE_CRONTAB` in `backend/packages/data/src/worker.ts` and the closed task names in `backend/packages/queue/src/index.ts`. #1723 provides the trash hooks that a swept page goes through.

This issue adds a daily sweep that sends orphaned pages to the trash, so they can be restored for 30 days like any deleted item.

Decisions:
- A live Pages item is an orphan when its parent has a document, that document holds no `page` block with its id, and the document's latest update is at least 1 hour old (an editor may be mid-edit).
- A page whose parent has no document, or whose parent is itself trashed, is not swept.
- Moving a page block into another document is not supported by the server (the parent link is not updated), so a moved page counts as an orphan of its old parent and is trashed; this is accepted for now and recoverable.
- The sweep trashes through the choke point's item delete, so the hooks of #1723 (children, anchors) run.

Implement `sweepOrphanedPages(pool)` in `backend/packages/data/src/docs/pageOrphanSweep.ts`: `forEachActiveTenant`, and per tenant, in chunks of at most 200 pages per transaction, group the live Pages items by `parentItemId`, load each parent's document once, read its blocks with `readPageBlocks`, apply the orphan rule above and trash each orphan with the choke point's item delete using writer kind `system`. ### Requirement gh-1737: [semp-threads 16/19] Search Semp threads by title and preview

#### Context

Model tier rationale: One filter added to an existing list query, but titles of automatic-task and Inbox-item threads are resolved live rather than stored, so the search has to match against the same resolved values the list shows, and user input reaches a pattern match.

The chat list has a search field. Typing a word narrows the list to the threads whose title or preview line contains it, without regard to case or diacritics ("uctenka" finds "Účtenka za oběd"); an empty result is shown as "Nothing found". Decision: the preview is searched as displayed, that is the first 140 code points of the last message text, not the whole message. A hit that the user cannot see in the row would be unexplained. System messages have no text preview and never match on it.

Decision: matching is case-insensitive and diacritics-insensitive substring matching (`unaccent` and `ILIKE` over the resolved title and the preview text). The characters `%`, `_` and `\` in the input are escaped so they match literally. Full-text lemma matching is not used here.
