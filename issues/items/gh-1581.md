## Context

Model tier rationale: An extension of an existing list query by two relation filters over relations that another issue adds, verified with fixtures.

The transcript list (#1636) filters by event, person (the `speakers` edge) and pairing. Transcripts get project, company and participant relations in #1470, after which the app shows "Recordings and transcripts" for a project and for a person including meeting participants. The related-collections counts must use the same sets, otherwise the count and the filtered list disagree: after #1470 a project's count must come from `Transcripts.project` and a person's from `Transcripts.speakers` united with `Transcripts.people`.

This issue adds the `projectId` filter and extends the `personId` filter of `GET /api/transcripts` to that union. The `relation.related` counts of #1839 must use the same definition; this issue states it there as a constraint, not by editing that operation.

## Task

Load `testing` and `io-hardening`.

1. Add the `projectId` query parameter to the transcript list handler: transcripts whose `Transcripts.project` edge targets the project (live items only).
2. Change `personId` to match a transcript when the person is in `speakers` or `people`.
3. Validate both as uuids; a foreign or unknown id yields an empty list, not an error.
4. Tests: project and person filters return the expected transcripts, including a person who is only a participant; the combination with `eventId`.

## Scope

### In scope

- `projectId` and the widened `personId` filter on the transcript list.

### Out of scope

- The relations themselves: #1470.
- Changing the related-collection counts: #1839.
- The base list and pairing state: #1636.

## Acceptance criteria

- When `projectId` is a project that transcripts are linked to, then only those transcripts are returned.
- When `personId` is a participant who never spoke, then the transcripts of their meetings are returned.
- When an id is unknown or from another tenant, then the list is empty.
