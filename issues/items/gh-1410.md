## Context

Model tier rationale: One known mechanism (sniff the stored bytes, then record the result) across the upload store, a shared detector and one per-tenant cutover, verified with existing upload fixtures, but a parser over untrusted bytes and a populated-install schema change warrant care.

File type and MIME must describe stored bytes, including audio, rather than client headers or filenames. The shared detector serves Files and standalone upload; unknown content uses the decided fallback. Previously the upload stored the claimed MIME and no detected type.

Decisions:
- The type is detected from the stored bytes (magic bytes, plus ZIP entry names for Office files), never from `Content-Type` or the file extension.
- The Files `type` select gains the options `png`, `heic` and `audio`, in addition to `pdf`, `xlsx`, `docx`, `jpg`. The task attachment tiles need png and heic. `audio` (label "Zvuk" in Czech, "Audio" in English) is one option for both m4a and mp3, because audio attachments and recordings are stored as Files and must get a type. This issue is the only place that changes `Files.type` options; the tasks schema issue does not touch them.
- HEIC is converted to JPEG on the client (iOS photo picker in compatible mode); this issue still recognises HEIC bytes so a server-side fallback can build on the detector.
- An unknown or unrecognised content gets no `type` value (property absent; there is no generic "other" type, a generic filter for an empty value finds these files) and the blob mime `application/octet-stream`, which `GET /api/blobs/:id` already serves as an attachment with `nosniff`.
- An upload that deduplicates onto an existing live Files item returns that item unchanged; detection does not rewrite it.

The standalone upload path and its integration with this detector are owned by #1401 in the same batch: image-header admission is retained, but new blob MIME comes from detected bytes or `application/octet-stream`; dedup preserves existing metadata.

Shared-file ordering: this issue also waits for #1389 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys`, `db-migrations`, `io-hardening` and `testing`.

1. Add `backend/packages/data/src/blobs/fileTypeDetection.ts` exporting `detectFileType(head: Buffer): { type: "pdf" | "xlsx" | "docx" | "jpg" | "png" | "heic" | "audio"; mimeType: string } | null`. Signatures: `%PDF-` (within the first 1024 bytes), JPEG `FF D8 FF`, PNG 8-byte signature, HEIC/HEIF an ISO-BMFF `ftyp` box with brand `heic`, `heix`, `heif`, `mif1`, `msf1`, `hevc` or `hevx`; m4a an ISO-BMFF `ftyp` box with major or compatible brand `M4A ` or `M4B ` (`audio`, mime `audio/mp4`); mp3 an `ID3` tag at offset 0 or an MPEG audio Layer III frame header at offset 0 (byte `FF`, then the 11-bit frame sync and layer bits `01`) (`audio`, mime `audio/mpeg`); a ZIP (`PK\x03\x04`) is `xlsx` when an entry name starting with `xl/` is present and `docx` when one starting with `word/` is present (scanned in the local file headers within the first 64 KiB), otherwise unknown. Pure function, no I/O, never throws on short or malformed input.
2. In `ingestUploadedFile`, after the bytes are written and before the transaction, read the first 64 KiB back through `storage.readStream(storageKey, { start, end })`, run the detector, store the detected mime (or `application/octet-stream`) as the blob's `mimeType`, and create the Files item with `type` set to the detected value (omitted when unknown). The `contentType` input stays accepted but no longer decides the stored mime.
3. Extend the Files `type` options with `png`, `heic` and `audio`: update the select options in `seedTenDatabases.ts` for fresh installs and add the option labels to `seed/i18n/cs.json` and `en.json` (`property.files.type.option.png`, `.heic`, `.audio`; `audio` is "Zvuk" in cs and "Audio" in en).
4. Add an idempotent per-tenant cutover `backend/packages/data/src/blobs/filesTypeOptionsCutoverMigration.ts` (pattern: `transcription/transcriptsCatalogCutoverMigration.ts`) that appends `png`, `heic` and `audio` to the Files `type` property's options when absent (the Files schema is locked, so only a code-level migration may change it), and register it in `runTenantCutoverMigrations`. It no-ops when the Files database does not exist.
5. Tests: detector unit tests per type (including an m4a and an mp3 with and without an `ID3` tag) including a ZIP without Office entries, an empty buffer and a truncated header; an upload test where a PDF sent as `image/jpeg` stores `type = pdf` and blob mime `application/pdf`; an unknown-content upload stores no type and `application/octet-stream`; the cutover test (populated install gains the options, second run changes nothing).

## Scope

### In scope

- Content-based detection, storing the detected type and mime on `POST /api/files`, the exported detector for other upload paths, and the `png`/`heic`/`audio` option extension with its cutover.

### Out of scope

- Ownership of the standalone `POST /api/blobs` route and detector integration belongs to #1401, included in this same batch; this exclusion does not remove that combined requirement.
- Converting HEIC to JPEG on the server: not planned (the client converts HEIC to JPEG before upload).
- Thumbnails: not in v1; they would need their own architecture decision on the thumbnail source.
- A generic "other" type for unknown content: not planned; unknown content keeps no `type` value.
- Showing the detected type anywhere other than the stored properties.

## Acceptance criteria

- When a PDF is uploaded to `POST /api/files` with `Content-Type: image/jpeg`, then the Files item has `type = pdf` and the blob mime is `application/pdf`.
- When a PNG or a HEIC file is uploaded, then `type` is `png` or `heic` on a fresh and on a cut-over install.
- When an m4a or an mp3 file is uploaded, then `type` is `audio` on a fresh and on a cut-over install, and the blob mime is `audio/mp4` or `audio/mpeg`.
- When an `.xlsx` or `.docx` file is uploaded, then `type` is `xlsx` or `docx`; a plain ZIP gets no type.
- When the content is not recognised, then the item has no `type` value and the blob mime is `application/octet-stream`.
- When the cutover runs twice on a populated install, then the Files `type` options contain `png`, `heic` and `audio` exactly once.
- When identical bytes are uploaded again, then the existing item is returned unchanged with HTTP 200.
