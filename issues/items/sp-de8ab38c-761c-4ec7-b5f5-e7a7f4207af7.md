### Requirement gh-1497: [mail-accounts 08/30] Track last successful mailbox sync, failure kind and initial sync

#### Context

Model tier rationale: One migration plus bookkeeping changes in the existing sync job and state store, with defined fixtures, but it sits on the hot path of every mail sync and must not add writes or break the existing status semantics.

The app needs to show, per mailbox, when mail was last synchronized successfully, since when it has been failing, why, and whether the first full pass has finished. Today none of this is recorded. `Mailboxes.syncStatus` (`ok`, `error`, `never`, `needsReauthorization`) is written only by `backend/packages/data/src/mail/mailSyncJob.ts`: `ok` after a pass, `error` for any failure including provider connection limits, `needsReauthorization` for `MailReauthorizationRequiredError`. Nobody writes `never`. The failure classification (`mailSyncFailureKind`) goes to the log only. `mail_account_sync_state.last_activity_at` moves forward on failures as well (`recordSyncError`, `recordConnectionLimitBackoff` in `mailAccountSyncStateStore.ts`), so it cannot answer "last successful sync". Also, `syncStatus` is patched on every pass, even when unchanged.

This issue records the facts; it exposes nothing. #1572 serves them to the app, #1503 uses the failure kind in notifications, #1506 raises and resolves one problem from them, and removal of a mailbox (#1690) deletes the state row.

Decision: retain historical 0115. It backfills successful timestamps from known activity and failing rows with known activity. A queued forward repair labels still-unclassified error rows with NULL activity as `other`, preserving unknown timestamps; this also covers indistinguishable invalidation-only rows, without asserting historical sync failure provenance.

3. In `mailSyncJob.ts` map the existing `mailSyncFailureKind` result (`reauthorizationRequired`, `connectionLimit`, `unexpected`) to the stored kinds (`reauthorization`, `connectionLimit`, `other`) and pass it to the recorders.
4. Make the job write `Mailboxes.syncStatus` only when the value differs from the one it read in the prologue, so repeated identical passes cause no item update.

### Requirement gh-1481: [mail-accounts 05/30] Persist a rotated OAuth refresh token

#### Context

Model tier rationale: It rewrites a stored encrypted secret during background sync, and a lost or racing rotation permanently breaks the account, so concurrency and failure ordering of the credential write carry the risk.

`refreshAccessToken` in `backend/packages/data/src/mail/oauthTokenExchange.ts` implements only the `refresh_token` grant and returns `{ accessToken, expiresAt }`. Microsoft rotates the refresh token on every refresh and returns a new one; the current code drops it, so after the original token expires the account ends in `needsReauthorization`. Google normally returns no new refresh token, but may.

The stored refresh token is the mailbox's credential in `external_credentials` (`credentials/externalCredentialsStore.ts`: `storeCredential` overwrites the one credential of an item; `getDecryptedCredential` reads it, logging the access). The Gmail and Graph REST clients take a `getAccessToken: () => Promise<string>` function. The sync transports (#1505 and #1508) will build that function; this issue gives them a safe way to refresh and persist.

Decision: when the response carries a new `refresh_token`, it is stored in the same tenant scope before the new access token is used; the previous token is replaced only after the new one is durably written. A failure to persist makes the refresh fail loudly (the old token may already be invalid at the provider, so this is logged and reported, never silently ignored).
Decision: use the bounded credential-row transaction exception in `docs/adr/2026-11-02-mail-oauth-rotation-holds-the-credential-lock-through-refresh.md`. A waiting caller reads the committed replacement refresh credential and exchanges it; access tokens are not shared or persisted. Successful committed rotating generations are presented once; a nonrotating credential can be presented again. Provider consumption cannot be rolled back, and commit failure may leave its outcome uncertain.

#### Task

Load `error-handling`, `state-writes` and `testing`.

1. Extend `AccessToken` with `refreshToken?: string` (present only when the provider returned a non-empty `refresh_token`); parse it from the response; never include any token in thrown messages or logs.
2. Add `refreshAndPersistAccessToken` in `backend/packages/data/src/mail/mailOAuthAccess.ts`: given a pool, the mailbox item id, the provider's token URL, OAuth client id and secret, and scope, it (a) locks the mailbox's credential, (b) reads it with `getDecryptedCredential` (actor `sync_worker`, purpose naming the sync mode), (c) calls `refreshAccessToken`, (d) when a new refresh token came back, stores it with `storeCredential` (type `oauth2_refresh_token`) in the same transaction, (e) returns the access token and its expiry. A 400/401 from the provider still throws `MailReauthorizationRequiredError`. Apply the ADR's 15s whole-request deadline, 64 KiB response cap and transaction-local wait/statement bounds; return no access token before commit and do not automatically replay an ambiguous exchange.
3. Keep `refreshAccessToken` callable with the same inputs for existing callers and tests.
4. Tests: a response with a rotated refresh token leaves the new token in `external_credentials` and the next refresh uses it; a response without one leaves the stored token unchanged; two successful concurrent rotating refreshes present each committed generation once (fake provider counts, real operation PIDs/blocking); nonrotating responses preserve the credential; a failing persist throws and the access token is not returned; no token string appears in thrown errors or captured logs. Cover timeout/body bounds, no return before commit, rollback/lock release, and independent mailbox/tenant progress.

## Scope

### In scope

- Exactly embedded backend Tasks/AC, named tests/migrations and production composition roots.
- Coordinate shared files/ordinals without duplicate registrations/owners.
- Independently review the whole batch with an explicit verdict per source criterion.

### Out of scope

- Web/mobile source, screens, navigation, client localization or validation.
- Unlisted requirements except delivered prerequisites.
- Automatic approval/deployment, implementer production security sign-off, or completion based only on written code.

## Acceptance criteria

- Every criterion under every embedded source Acceptance criteria section passes with recorded evidence; none may be sampled, silently omitted or treated as implemented by a stub.
- Required backend tests and functional scenarios exercise production paths, including relevant failures, tenant isolation, concurrency, idempotency and populated-tenant migrations.
- Independent review has no unresolved medium-or-higher findings. Confirmed findings are fixed and affected evidence is rerun against the final candidate SHA.
- The full backend `pnpm run verify` passes. No web or mobile verification is required. A missing external service or required live-provider check is BLOCKED/NOT RUN, never PASS.
- Only after this entire gate passes may this batch and its approved source records be completed with individual handovers pointing to the verified implementation. All source approvals must still match their specifications.
- The next sequential batch starts only after this batch's gate passes; a failure holds advancement.
