**Blocked by:** #1780
**Model tier:** medium

## Context

Model tier rationale: One Tasks update hook that writes or removes a protected edge in the same transaction as a status change, on existing hook, relation-write and event-end seams, verified with real-database fixtures.

A task that sits in an event (#1764) is part of that event until the event ends. When it is completed before the event has ended, the completion belongs to that event: the task is then shown as done only inside the event ("done in the event") and disappears from its day, from the Tasks list and from counts. This holds wherever the task is ticked: in the event, in the Tasks list, on the task's own screen, or by an agent. A completion made after the event has ended is an ordinary completion and is shown in the event as "done later". Today completion is `PATCH /api/items/:id` with `status: done`; #1544 sets `completedOn` (today by default, a past day allowed, a future day rejected) and `completedAt`, and an existing Tasks update hook advances a recurring task to its next instance inside the same transaction when `status` becomes `done` (`tasks/taskRecurrenceItemUpdateHook.ts`). #1540 created the protected relation `Tasks.completedInEvent` with the inverse `Events.completedTasks` (single-valued on the task side, owned by the system, owner process `tasks`, so a generic edge write answers 403 `owner_violation`). #1764 orders a task's host events by the edge's `addedAt`; #1780 derives visibility from the live host events and uses the event end of the calendar time module (#1418).

This issue adds the Tasks update hook that records a completion in the event from the status change itself and keeps the edge consistent with the status. Reading the state per event is #1801; hiding completed-in-event tasks from lists and counts is part of the visibility predicate of #1798; agent and MCP tools are #1957.

Decisions:
- Decided by the product owner: every completion made before the end of the event counts as a completion in the event, wherever it is made. There is no separate complete-in-event route; the ordinary status write is the only path.
- The event the completion belongs to is the task's last live host event by `addedAt`, provided that event has not ended at the moment of the write. If that event has already ended, no edge is written and the completion is an ordinary one.
- `completedOn` follows the ordinary rule of #1544 (today by default); this issue does not change it.
- Setting `status` to `notDone` or `wontDo` by any route removes the `completedInEvent` edge in the same transaction; that is also how a completion in the event is undone.
- A repeated `done` on a task that already has the edge changes nothing.

Shared-file ordering: this issue also waits for #1780 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `canonical-keys` and `testing`.

1. Add a Tasks update hook `taskCompletedInEventHook` in `backend/packages/data/src/tasks/taskCompletedInEventHook.ts`, registered in `domainWriteHooks.ts`, that runs in the writing transaction for every Tasks write, whatever route or writer made it:
   - when the write changes `status` to `done` and the task has no `completedInEvent` edge, read the task's live host events (edges of `Tasks.hostEvents` ordered by `addedAt`, joined to live Events), take the last one, and if its end (the event end of #1418) is later than now, create the `completedInEvent` edge to it with the system context `{ ownerProcess: "tasks" }`;
   - when a write leaves `status` as `notDone` or `wontDo`, delete the task's `completedInEvent` edge if any.
2. The hook does not change `completedOn`, `completedAt` or any other property, and runs after the Tasks transform so the recurrence advance of a recurring task still happens in the same transaction.
3. Tests (real database, controlled clock): a task in an event 15 October 13:00 to 14:00 completed by `PATCH /api/items/:id {status: "done"}` at 13:30 gets the `completedInEvent` edge to that event; the same completion at 14:30 gets no edge; a task in a future event completed before that event ends gets the edge; a task in two events gets the edge to the one added last; a task without host events gets no edge; a repeated `done` writes nothing; `PATCH {status: "notDone"}` and `{status: "wontDo"}` remove the edge; a generic relation PUT or DELETE on `completedInEvent` from either side is 403 `owner_violation`; a recurring task completed in an event also gets its next instance in the same transaction; a foreign tenant's task is never touched.

## Scope

### In scope

- The hook that records a completion before the event's end as completed in the event, and removes the edge on `notDone` and `wontDo`.

### Out of scope

- A separate complete-in-event route: not built (decided by the product owner).
- Hiding completed-in-event tasks from lists, counts and days: #1798.
- Per-event state and the event's task list: #1801.
- Completion day rules: #1544; recurrence advancing: #1670.
- Agent and MCP tools: #1957.

## Acceptance criteria

- When a task that sits in an event is set to `done` by any route before the event's end, then the `completedInEvent` edge to that event exists in the same transaction.
- When it is set to `done` after the event has ended, then no `completedInEvent` edge is written.
- When the task sits in several events, then the completion belongs to the one added last, if that event has not ended.
- When `status` is set to `notDone` or `wontDo` by any route, then the edge is removed in the same transaction.
- When a generic relation write targets `completedInEvent` or `completedTasks`, then it is refused with 403 `owner_violation`.
