## Context

`backend/services/semprec-ai-gateway/src/audioHandler.ts` accepts bodies of up to `MAX_BODY_BYTES = 150 * 1024 * 1024` (line 16) on `POST /internal/diarize` and `POST /internal/transcribe`. `readJsonBody` (lines 34-48) holds the request as an array of chunks, then `Buffer.concat` of them, then the decoded string, and `validateBody` (line 101) decodes the base64 into yet another buffer — three to four full copies of the body per request, i.e. up to ~600 MiB resident for one maximal request. Nothing bounds how many such requests are in flight at once: the dispatcher in `backend/services/semprec-ai-gateway/src/app.ts` (lines 26-29) hands every audio request straight to the listener. Three concurrent maximal requests are enough to exhaust the process's memory, and the only caller (`semprec-transcribe`) already retries its transcription job with graphile-worker's backoff (`max_attempts: 3`, `transcriptionTask.ts`), so a fast 503 is safe for it to receive.

Independent of every other issue in this batch: it touches the dispatcher, not the handlers.

## Task

- New module `backend/services/semprec-ai-gateway/src/audioConcurrencyLimit.ts`:
  - `export const MAX_CONCURRENT_AUDIO_REQUESTS = 2;`
  - `export function createAudioConcurrencyLimit(max: number): { tryAcquire(): (() => void) | null; inFlight(): number }` — an in-process counter. `tryAcquire()` returns a release function when `inFlight < max` (incrementing the counter), else `null`. The release function is idempotent: calling it twice decrements once.
- `backend/services/semprec-ai-gateway/src/app.ts`: `createDispatcher` creates one limit with `MAX_CONCURRENT_AUDIO_REQUESTS` (no new parameter, no env var). In the `/internal/diarize` / `/internal/transcribe` branch, before handing the request to `audioListener`:
  - `const release = limit.tryAcquire()`; when `null`, answer `503` with headers `Content-Type: application/json; charset=utf-8` and `Retry-After: 1`, body `{ "error": "Audio capacity exhausted", "code": "audio_capacity_exhausted" }`, and return without reading the body.
  - otherwise `res.on("close", release)` (`ServerResponse` emits `close` both when the response finishes and when the connection drops, so the slot is freed on every path out) and then dispatch as today.
- Tests, new file `backend/services/semprec-ai-gateway/src/__tests__/audioConcurrencyLimit.test.ts` (integration tier — it drives `createDispatcher` against the embedded Postgres like `audioHandler.test.ts` does, reusing its fake provider and `startServer` shape):
  - with a diarization provider gated on a deferred promise, two concurrent `POST /internal/diarize` requests both reach the provider; a third answers 503 with `code: "audio_capacity_exhausted"` and a `Retry-After` header while the first two are still in flight; releasing the gate completes the first two with 200; a fourth request afterwards answers 200.
  - a request that failed validation (400) or auth (401) still releases its slot: after three such requests, a valid one is not refused.
  - `POST /internal/complete` is never counted: with both audio slots taken, a completion request still reaches its provider.
  - plus a pure unit test file `backend/services/semprec-ai-gateway/src/__tests__/audioConcurrencyLimit.unit.test.ts` for `createAudioConcurrencyLimit`: acquire up to `max`, `null` beyond it, idempotent release.

## Scope

### In scope

- The in-process limit, its wiring in the dispatcher, the 503 response, and the tests above.

### Out of scope

- Any change to `audioHandler.ts` (sibling issues E1, E3 and E4 of this batch edit it), `completeHandler.ts`, `serve.ts` or `startupConfig.ts`.
- Making the cap configurable through an environment variable.
- Changing how `semprec-transcribe`'s `audioGatewayClient.ts` reacts to a 503 (graphile-worker's job retry already covers it).
- Reducing the number of body copies in `readJsonBody`/`validateBody`.

## Acceptance criteria

- When two audio requests are in flight, a third `POST /internal/diarize` or `POST /internal/transcribe` answers 503 with JSON `code: "audio_capacity_exhausted"` and a `Retry-After: 1` header, without its body being read and without any provider or budget call.
- When an in-flight audio request ends — 200, 4xx, 5xx, or the client dropping the connection — its slot is released and the next audio request is admitted.
- `POST /internal/complete` is unaffected by the audio limit.
- `pnpm run test:unit` and `pnpm run test:integration` (in `backend/`) pass with the new test files.
