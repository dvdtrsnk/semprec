## Context

Model tier rationale: One new read operation across the existing catalog, store and REST seams with established fixtures, but it adds a tenant-scoped read over two-sided and one-directional relation definitions that must not leak deleted or foreign targets.

Relations can be written through the catalog (`relation.put`, `relation.delete`, `PUT`/`DELETE /api/items/:id/relations/:propertyKey/:targetItemId`) but not read. The only readers are internal: `relationsStore.listRelationsForItem` and `listRelationsForItems` in `backend/packages/data/src/chokePoint/relationsStore.ts`, which take a relation definition id and return raw stored edges (`itemA`, `itemB`, `metadata`). A client or agent that wants to know which projects a person belongs to, or which area a file points at, has no way to ask. This is worst for one-directional relations (a relation definition with `propertyIdB = null`, such as a file's area, an event's people or a movie's watched-with list): the target database has no inverse property, so the link cannot be read from the target side, and today it cannot be read from the source side either.

This issue adds a read-only catalog operation `relation.list` that returns the live edges of one item, optionally narrowed to one relation property. It is the single read primitive for edges. #1518 builds inline expansion (`include=relations`) on the same resolution rules, #1521 reads the current edge before replacing it, and #1839 builds on the same edge listing.

Decision: the operation requires `core.item.read`, is non-destructive and needs no approval, and its MCP name is `semprec.relation.list` (the catalog prefixes `semprec.` automatically).

Shared-file ordering: this issue also waits for #1401 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys`, `error-handling`, `io-hardening` and `testing`.

1. Add `relation.list` to the closed operation catalog: append it to `GENERIC_OPERATION_NAMES`, add `RelationListInputSchema` (`{ itemId: string, relationPropertyId?: string }`, strict) and a `RelationListEntry` output shape, register it in `InputByOperation`, `OutputByOperation`, `OPERATION_METADATA` (`nonDestructive("core.item.read")`), the service port and the bindings table. Update the "29 operations" counts and comments the exhaustiveness checks and `operationCatalog.unit.test.ts` carry.
2. Output is a list of `{ relationPropertyId, propertyKey, targetItemId, targetDatabaseId, metadata }`. `relationPropertyId` and `propertyKey` identify the property on the listed item's own side, so a many-to-many link seen from either end reports that end's own property.
3. Add a store read in `relationsStore.ts` (or a sibling read module in `chokePoint/`) that, for one item, resolves every relation property of the item's database, finds the edges on that property's definition from the item's side (side A of a definition reads `item_b` as the target, side B reads `item_a`; a definition with `propertyIdB = null` is read only from side A), and returns them in a single batch of queries independent of the number of properties. Edges whose target item is soft-deleted are omitted, as are edges whose target database is archived. A `relationPropertyId` that does not belong to the item's database is a `400 validation_failed` with `field: "relationPropertyId"`.
4. Implement `listRelations` in `genericApplicationService.ts` and run it inside the tenant scope like the other reads. An unknown or deleted `itemId` is `404 not_found`, identical for a foreign-tenant id.
5. Expose `GET /api/items/:id/relations` with the optional `?propertyKey=` filter in `itemsHandler.ts` (resolve the key with the existing `resolveRelationProperty`, `404` for an unknown key) and add the route to `routeMatrix.ts`. The response is `{ relations: [...] }`.
6. Tests: unit tests for the schema and catalog; integration tests for two-way read from both ends of a paired definition, a one-directional relation read from the source, deleted-target omission, `propertyKey` filtering, the unknown-key and foreign-tenant cases, and the MCP/agent tool listing including `semprec.relation.list`.

## Scope

### In scope

- The `relation.list` operation, its REST route and MCP/agent exposure, and the store read behind it.

### Out of scope

- Inline relation expansion in `item.get`, `database.query` and `view.query`: #1518.
- The related-items operation with grouping and ordering: #1839.
- Replacing a single-valued relation: #1521.
- Realtime invalidation of edge writes: #1621.

## Acceptance criteria

- When a file's area relation has no inverse on the Areas database, then `relation.list` for the file returns the area edge with its `targetItemId` and `targetDatabaseId`.
- When the listed relation is paired, then listing from either end returns the other end as `targetItemId` with that end's own `relationPropertyId` and `propertyKey`.
- When a target item is soft-deleted or its database is archived, then its edge is absent from the result.
- When `relationPropertyId` (or the REST `propertyKey`) names a property of another database or an unknown key, then the call fails with `400` or `404` as described and returns no data.
- When the item belongs to another tenant, then the response is identical to that of a nonexistent item.
- When an agent lists its tools, then `relation.list` appears without an approval requirement.
