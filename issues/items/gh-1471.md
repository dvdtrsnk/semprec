## Context

Model tier rationale: One shared write helper applied to every existing proposal writer across data and transcription modules, with existing fixtures, but each writer is on the persisted card state so every one must be re-verified.

The inbox card shows one proposal whose fields the user can edit by hand, with a "return the proposal" action that restores what the assistant originally proposed. To support that, a Processing proposal needs to keep the assistant's last output separately from the effective envelope the user confirms. Card-state properties on Processing proposals are added by #1451: `aiProposal` (the assistant's latest output; for a card whose type was refined, the values for the chosen type), `userOverrides` (`{ [ref]: { [key]: value } }`), `userEditedKeys` (`["ref.key"]`, a single-step envelope uses ref `primary`) and `aiVersion` (integer counter of assistant writes).

Today the stored `proposal` property is the only envelope. It is written by these code paths, which all replace it wholesale: `writeNeedsClarification`, `reviseProposal` and `writeTickResult` in `backend/packages/data/src/inbox/inboxTickAction.ts`; `reviseProposalWithClient` in `backend/packages/data/src/inbox/proposalActions.ts`; and the transcript cards created in `backend/packages/data/src/transcription/transcriptEventMatch.ts` and `transcriptSpeakerSuggestion.ts`. The last assistant output is not kept anywhere separately, and `proposal`, `status` and `history` are system-owned, so only these writers (through `allowedSystemKeys`) may set them.

Decision: `proposal` stays the effective envelope (assistant output plus user overrides) that `confirm` and existing clients read; this issue keeps `proposal` exactly as written today and mirrors it into `aiProposal`. No override exists yet at this point, so both are equal. Composing `proposal` from `aiProposal` and `userOverrides` is done by #1892 and protected during recompute by #1921.

Decision: existing rows created before this change have no `aiProposal`. Instead of a data migration, every reader and writer treats a missing `aiProposal` (and a missing `aiVersion`, as 0) as "the stored `proposal` is the assistant's output". The first assistant write or manual edit on such a row materializes the property. This avoids a backfill step and is safe because no user overrides could exist before this change.

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. Add one exported helper in `backend/packages/data/src/inbox/inboxTickAction.ts`, `aiProposalPatch(existingProperties, envelope | null)`, returning `{ aiProposal: envelope, aiVersion: <previous aiVersion or 0> + 1 }`. Add a reader helper `readAiProposal(properties)` that returns `aiProposal` when set, else the parsed stored `proposal` (legacy rows), else `null`.
2. Make every writer listed above spread `aiProposalPatch` into its `propertiesPatch` next to `proposal`, and add `aiProposal` and `aiVersion` to its `allowedSystemKeys`: `writeNeedsClarification` (both the revise and the create branch; envelope is `null`), `reviseProposal`, the create branch of `writeTickResult`, `reviseProposalWithClient`, and the two transcript card creators. A newly created row starts with `aiVersion` 1.
3. Writers that change only `status` or `history` (confirm, reject, invalidate on source deletion) do not touch `aiProposal` or `aiVersion`.
4. Tests: for each writer, the stored `aiProposal` deep-equals the stored `proposal` after the write and `aiVersion` increments by one per write; a legacy row with no `aiProposal` is updated correctly and `readAiProposal` returns its `proposal`. Extend `inboxTickProposal.test.ts`, `proposalActions.test.ts`, `transcriptEventMatch.test.ts` and `transcriptSpeakerSuggestion.test.ts`.

## Scope

### In scope

- Mirroring every assistant-written envelope into `aiProposal` and counting writes in `aiVersion`, plus the legacy-row fallback.

### Out of scope

- Declaring the `aiProposal`, `userOverrides`, `userEditedKeys` and `aiVersion` properties (#1451).
- Manual edits and composing the effective envelope (#1892).
- Keeping user-edited keys when a recompute runs, and the staleness check based on `aiVersion` (#1921).
- Returning the effective envelope to the last assistant output (#1912).

## Acceptance criteria

- When the tick creates a proposal, then `aiProposal` equals `proposal` and `aiVersion` is 1.
- When the source item changes and the tick recomputes, then `aiProposal` equals the new envelope and `aiVersion` is 2.
- When the tick writes `needsClarification`, then `proposal` and `aiProposal` are both null and `aiVersion` increments.
- When a user revises a proposal through `reviseProposalWithClient`, then `aiProposal` equals the new envelope.
- When a transcript Event card or a transcript speaker card is created, then `aiProposal` equals its `proposal` and `aiVersion` is 1.
- When a proposal is confirmed or rejected, then `aiProposal` and `aiVersion` are unchanged.
- When a legacy row without `aiProposal` is recomputed, then it gains `aiProposal` and `aiVersion` is 1.
