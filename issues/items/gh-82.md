**Blocked by:** #212, #21, #115

## Context

Issue #211 normalized the relation edge contract and endpoint validation; #212 added per-side relation-definition ownership, the protected `SystemRelationWriteContext` entry points, and atomic locked creation. Two severe gaps remain: declared cardinality is not enforced, so concurrent requests can produce a `one_to_one` or `one_to_many` violation, and a one-directional relation property can retain a nonexistent target database because its config is not validated or repaired.

This final part closes the relation-integrity work by enforcing cardinality under concurrency and making relation-property config canonical and durable, including a fail-loud repair migration for existing rows.

## Task

- Enforce cardinality under concurrency after normalization: `one_to_one` permits at most one edge for either `item_a` or `item_b`; `one_to_many` defines `property_id_a`/`item_a` as the one side (one `item_b` may point to only one `item_a`, while one `item_a` may have many `item_b` edges); `many_to_many` permits both sides to repeat. A call through `property_id_b` reverses caller/target into that same normalized model. Lock or constrain relevant edges so concurrent requests cannot violate it, adding any additive indexes or constraints needed for concurrency-safe enforcement.
- Validate `targetDatabaseId` even for a one-directional relation property.
- Persist relation-property config canonically as `{ relationDefinitionId: string, targetDatabaseId: string }` on every side: property A's target is the requested target database; paired property B's target is the source database. A one-way property A retains this same complete config even though `property_id_b` is NULL. Edge validation (as defined in #211) loads the named property, treats its own `database_id` as caller/source database, and reads/validates `config.targetDatabaseId` as the target; it never infers target from a missing inverse row.
- Add a populated migration that scans every relation definition/property. For paired definitions it backfills/repairs each target from the opposite property's `database_id` and verifies both configs reference the same definition. For one-way definitions it preserves an existing valid target UUID and verifies that database exists; if `relationDefinitionId` or `targetDatabaseId` is missing/invalid/inconsistent, abort migration with the offending property id rather than guessing. Runtime loading rejects malformed config with `validation_failed`.
- Add real-Postgres integration tests for every cardinality, invalid databases, concurrency, one-direction target validation, and locked relation creation with complete config, and run the #211/#212 relation suites together with them so the complete choke-point relation path is exercised end to end.

## Scope

### In scope

- Cardinality enforcement through the choke-point and any additive indexes or constraints needed for concurrency-safe enforcement.
- Canonical relation-property config persistence, one-directional target validation, and the repair migration.

### Out of scope

- Edge type normalization, idempotent create/update/delete contracts, and endpoint validation; #211 delivered these.
- Per-side ownership, `SystemRelationWriteContext`, protected entry points, internal-caller migration, and locked-creation ordering; #212 delivered these.
- REST routing; issue #37 projects this corrected choke-point behavior over HTTP.
- Module registry and PostgreSQL runtime roles; issues #29 and #40 own those boundaries.
- Domain-specific relation rules.

## Acceptance criteria

- Concurrent writes cannot produce a state that violates the declared cardinality.
- Creating a locked one-way or paired relation property succeeds with complete config on every side, and a nonexistent target database is rejected even for a one-directional property.
- After process/database reload, a one-way relation still reads its durable target database from property config and rejects a wrong-database endpoint; populated malformed configs fail migration explicitly with the offending property id.
- The new integration tests reproduce the former gaps and pass against real PostgreSQL.
