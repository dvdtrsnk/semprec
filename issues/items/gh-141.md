**Blocked by:** #232, #140

## Context

Login (#140) issues one opaque token regardless of client, and #232 throttles abusive attempts. Safe delivery of that token differs by client platform: browsers must never see it from JavaScript, the native iOS/macOS app stores it in the Keychain, and the embedded WKWebView editor must reuse the native session instead of logging in again. This issue defines those delivery contracts; #143 later relies on the same verification path for every route.

## Task

For web login, deliver the token only in an `httpOnly`, `Secure`, `SameSite=Lax` cookie. For iOS/macOS, return it in the login response contract for immediate Keychain storage and require Bearer use. Define the native shell bridge using `WKScriptMessageHandler` so an embedded editor receives the existing native token and never performs a second login. Reject a requested delivery mode that does not match the declared platform.

## Scope

### In scope

- Cookie/Bearer contracts, platform mismatch rejection, and WKWebView bridge contract.

### Out of scope

- Attempt recording and lockout — delivered by #232.
- Public signup, CAPTCHA, proxy-level rate limiting, or persistent token access from browser JavaScript.

## Acceptance criteria

- Browser responses never contain the token in a readable response body; native responses do and document Keychain storage.
- A delivery mode that does not match the declared platform is rejected and no session is issued.
- The embedded editor reuses the native session and has no login endpoint of its own.
