**Model tier:** medium

## Context

Model tier rationale: One mechanism (calling the existing resolve operation at the places where a source recovers) at five call sites, each in the same transaction as its source write; the care needed is in not closing a tick problem on a run that is only technically successful.

Problems raised for failed sources (#1911, #1465) must close when the source recovers, in the same transaction as the write that proves recovery, so the status view never shows a problem for something that already works, and a rolled-back recovery never closes one. The store (#1459) has `resolveProblem(dedupeKey, resolutionKind)`; nothing calls it yet. Recovery signals exist today:

- A tick that succeeds: `recordHeartbeatSuccess` (`backend/packages/data/src/scheduler/schedulerStore.ts`, called from `scheduler/sweep.ts`) clears `last_error`, but it is also called for a run that ended `done` with an incomplete answer, so it is not proof of recovery.
- Guidance drift: findings are resolved through the findings store (`agent_guidance_drift_findings.resolved_at`) by `backend/packages/application/src/projectAgentGuidance/driftAction.ts`.
- The restore test: `recordRestoreTestResult` (`backend/packages/data/src/observability/restoreTestResult.ts`) switches `backup:restoreTest` to `ok`.
- The stale-process check (`observabilityCheckSystem.ts`) switches `process:<name>` back to `ok`.
- Library automation: a successful job clears the item's automation error.

Mailbox, transcription and chat reply problems are closed by their own producers (#1506, #1945, #1931). The history shown after a problem closes is #1919; closing notifications and pushes belongs to #1463 and the status invalidation to #1868.

It builds on the retry chain of runs (#1448) and on the function that tells whether a reply left a failed tool call (#1890).

Decision: a tick counts as recovered only when its run ended `done` and its reply does not leave a failed tool call according to #1890. The same transaction that closes the run and writes the reply message calls `resolveProblem` for `agents:heartbeat:<heartbeatId>`. A run in a retry chain that succeeds resolves `agents:run:<first run of the chain>`.

Decision: resolutions use `recovered` for every case above; a problem closed because its source was deleted uses `sourceDeleted` (the constant of #1459 gains this value). Deleted-source resolutions are not shown in history (#1919).

Decision: the stale-process and library-automation problems are closed as well (not only the ones the design shows in history), so a problem raised by #1465 is never left open after recovery. A library automation problem closes when a job succeeds and no other item of that database still has an automation error.

## Task

Load `state-writes` and `testing`.

1. Add `sourceDeleted` to the resolution kinds in `backend/packages/data/src/semp/sempProblemsStore.ts`.
2. Heartbeat and runs: in the transaction in which a tick run is closed `done` and its reply written (the run action in `backend/packages/data/src/scheduler/actions.ts` and the writer of the tick thread reply), call `resolveProblem` for the heartbeat key when the recovery condition above holds; for a successful run in a retry chain resolve the chain key.
3. Drift: in `driftAction.ts`, where a finding transitions to resolved, call `resolveProblem` for `guidance:<projectId>:<fingerprint>`. If the findings store's resolve is shared with other kinds of drift, hook it there so every kind is covered.
4. In `restoreTestResult.ts`, when the result is `passed`, resolve `backup:restoreTest` for each administrator in that administrator's tenant, as the failure raised it. In `observabilityCheckSystem.ts`, when `process:semprec-agents` switches back to `ok`, resolve `agents:process` for each administrator.
5. In `libraryMetadataJob.ts`, on a successful job resolve `automation:<databaseId>` if no item of the database has an automation error left.
6. Tests: a failed tick followed by a successful tick resolves the problem in the same transaction as the run close; a successful run whose reply left a failed tool call does not resolve it; a rolled-back recovery leaves the problem active; a resolved drift finding resolves its problem and a reappearing finding creates a new one; a passed restore test resolves the administrators' problem; library automation resolves only when the database has no remaining errors.

## Scope

### In scope

- Resolving heartbeat, run, guidance drift, restore test, stale process and library automation problems when their source recovers.

### Out of scope

- Resolving mailbox (#1506), transcription (#1945) and chat reply (#1931) problems; each is closed by the issue that raises it.
- The history with titles (#1919) and pruning (#1558).
- Closing related notifications and pushes (#1463) and the realtime invalidation (#1868).
- Positive events that are not recoveries from a problem (a restore test that passes with no earlier failure, an emptied queue); they do not appear in history.

## Acceptance criteria

- When a failed tick later runs successfully, then its `agents:heartbeat:<heartbeatId>` problem is resolved in the same transaction as the run close and the message write.
- When a tick run is `done` but its reply left a failed tool call, then its problem stays active.
- When the recovery transaction rolls back, then the problem stays active.
- When a drift finding is resolved, then its problem is resolved; when the same finding returns, then a new problem is created.
- When the monthly restore test passes, then each administrator's `backup:restoreTest` problem is resolved.
