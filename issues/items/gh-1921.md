**Blocked by:** #1892
**Model tier:** high

## Context

Model tier rationale: Changes the staleness and concurrency contract of the tick's write transaction (what counts as "the row changed") and the merge of assistant output with user values under a row lock, where a mistake silently loses either the user's edits or the assistant's result.

The inbox card shows "Edited by hand: N. Semp will not overwrite these values on the next recompute." Manual values (`userOverrides`, `userEditedKeys`) are written by #1892; the assistant's latest output is kept in `aiProposal` with a write counter `aiVersion` (#1471); the stored `proposal` is the effective envelope composed from the two. Today the tick (`backend/packages/data/src/inbox/inboxTickAction.ts`) knows nothing about this and has two problems for edited cards:

1. `reviseProposal` replaces `proposal` wholesale, so a recompute after the source text changed would overwrite manual values.
2. `lockUnlockedProposal` re-reads the proposal under `FOR UPDATE` and treats the row as `changed` (the AI result is discarded and, because writing to Processing proposals does not trigger another tick and the source fingerprint is unchanged, never recomputed) whenever `updatedAt` differs from the snapshot. A manual `PATCH values` during the AI call moves `updatedAt`, so the assistant's result would be lost.

Decision: staleness is decided by the card's `fingerprint` and `aiVersion`, not by `updatedAt`. A concurrent manual edit does not discard an assistant result; a concurrent assistant write, a status lock (`confirmed`/`rejected`), a deletion or a different fingerprint still does. The write transaction still passes the freshly locked row's `updatedAt` as `ifVersion`, so the choke point's own conflict check is unaffected.

Decision: a user instruction typed in the item thread may change a protected key; that exception belongs to #1938. The tick, the explicit recompute and the user revise never change a key listed in `userEditedKeys`.

## Task

Load `state-writes`, `testing` and `error-handling`.

1. In `lockUnlockedProposal`, replace the `locked.updatedAt !== snapshot.updatedAt` test with a comparison of `fingerprint` and `aiVersion` (a missing `aiVersion` counts as 0) between the locked row and the snapshot; keep the gone, deleted and locked reasons and the serialization-failure branch as they are. Log `changed` when either differs.
2. In `reviseProposal` (and the create-or-revise path of `writeTickResult`), under the lock, write only the assistant parts from the new result: `aiProposal` (via the helper from #1471, which increments `aiVersion`), `fingerprint` and the history entry. Compute the effective `proposal` from the locked row's current `userOverrides` with `composeEffectiveEnvelope` and recompute `userEditedKeys` with `computeUserEditedKeys` (both in `backend/packages/data/src/inbox/proposalOverrides.ts`, from #1892). A manual value therefore survives, and a key whose manual value now equals the new assistant value drops out of `userEditedKeys`.
3. When the new envelope's `entityKind` or `target` differs from the previous `aiProposal`'s, or an override key no longer exists on the new target, drop those overrides for this recompute (they cannot apply); the history entry then has `kind: "recompute"` and the message names the dropped keys. Overrides on keys that still apply are kept.
4. `writeNeedsClarification` writes `aiProposal: null` and `proposal: null` as before, and leaves `userOverrides` and `userEditedKeys` untouched; they apply again when a later valid assistant output arrives.
5. Set `kind: "recompute"` on the history entry written by `reviseProposal`.
6. Tests in `inboxTickProposal.test.ts`: recompute after a source text change keeps an edited title; a manual `PATCH values` committed while `computeProposal` is in flight leaves the assistant result stored in `aiProposal` with `aiVersion` +1 and the manual title still effective; a confirm during the call still discards the result; a second assistant write during the call still discards it.

## Scope

### In scope

- The tick's recompute path keeps user-edited keys, and its stale check uses `fingerprint` and `aiVersion`.

### Out of scope

- The explicit recompute route (#1955) and its use of the same merge.
- Thread-driven revision that may change a protected key (#1938, #1940).
- Dropping all overrides on an explicit type or target change (#1924).
- Versioning the fingerprint (#1606).

## Acceptance criteria

- When the source text changes and the tick recomputes, then the manually edited `title` stays and the other fields take the new assistant values.
- When a manual `PATCH values` commits while the assistant call is running, then the assistant result is stored in `aiProposal`, `aiVersion` grows by one and the manual value is still in `proposal` and `userEditedKeys`.
- When the card is confirmed or rejected while the call is running, then nothing is written.
- When another assistant write bumped `aiVersion` while the call was running, then the older result is discarded.
- When the new assistant envelope has another target, then overrides are dropped and the history entry has `kind: "recompute"` naming them.
- When the assistant output fails validation, then the card is `needsClarification` with `proposal` null and the overrides remain stored.
