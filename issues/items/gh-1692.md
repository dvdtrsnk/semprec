**Model tier:** medium

## Context

Model tier rationale: One read-model extension of the thread detail with a batched query over an existing relation and the existing link shape.

The thread detail (#1632) should list the tasks that were made from the thread. After #1612 the tasks are the targets of the edges Threads.tasks; this list contains only tasks linked through that relation, not tasks of the same project or the same people. Completing a task is the generic status change to `done`, nothing special.

Decision: order is not-done tasks first, then by due date ascending with undated tasks last, then by creation time.

Shared-file ordering: this issue also waits for #1690 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `io-hardening`, `canonical-keys` and `testing`.

1. Add `tasks` to the response of `GET /api/mail/threads/:threadId`: an array of `{ id, name, date, status, project, people, links }` for the not-deleted tasks with a Threads.tasks edge from this thread. `project` is `{ id, name } | null`, `people` is an array of `{ id, name }`, `links` has the shape of #1403 with entries only for properties that have a value-link row (`project`, `people`).
2. Resolve tasks, projects, people and links for the thread in batched queries.
3. Add the cases to the tenant-isolation route test.

## Scope

### In scope

- The `tasks` array in the thread detail.

### Out of scope

- Creating tasks (#1900); syncing people (#1923).
- A task list endpoint of its own.

## Acceptance criteria

- The detail returns exactly the tasks that have an edge Threads.tasks from this thread, with project, people and link state.
- A task of the same project without such an edge is not listed; a soft-deleted task is not listed.
- A task whose people were changed by hand shows `links.people.valueKind` equal to `inheritedBroken`.
