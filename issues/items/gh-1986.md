## Context

Model tier rationale: One persisted decision written at confirm and honored in one pipeline step, across two processes (api confirm and the transcription worker), with existing fixtures for both.

After a recording is transcribed, step 6 of the transcription pipeline (`matchTranscriptToEvent` in `backend/packages/data/src/transcription/transcriptEventMatch.ts`) tries to link the transcript to a calendar Event whose time window overlaps the recording. With no candidate, or with several, it always creates a "recording without an event" card (`transcript-suggestion:<transcriptId>`). There is no way for the user to say "this recording belongs to no event" up front, so a user who shares a voice recording and picks "no event" still gets that card, and again after every rerun of the transcription.

#1574 adds the recording request record that carries the context of an uploaded recording, including a column `event_decision` that #1574 created as `text NOT NULL DEFAULT 'none'` with no CHECK constraint: a request that carries no decision holds the default `'none'`, which means the user did not decide, and #1574 leaves further values to this issue. #1978 creates the Inbox card that proposes transcribing an audio attachment and its confirm, which starts the transcription. When the user chose a concrete Event, the edge to it is written directly (#1574, #1644); this issue does not touch that case.

Decision: "no event" is stored only in the recording request's `event_decision` column. No Transcripts property is added. The column keeps the definition #1574 gave it: `'none'` is its default and means the user did not decide, and the explicit "no event" decision is the new value `noEvent` (an English camelCase key, as `canonical-keys` requires). This issue adds no migration that changes the column, its default or its constraint.

Decision: the explicit "no event" choice of the card (#1978) is a new boolean property `noEvent` of its `transcription` envelope. `true` is the choice; `false`, `null` and an absent property mean that nothing was chosen, which is what an Event left unset means in #1978 today. `noEvent: true` together with an `eventId` is refused as a `ValidationError` on the field `noEvent`.

Decision: the decision is written by a function of the recording request store (`recordingIntake.ts`) that the confirm calls after `recordRecordingIntake` has written or found the request in the confirm's transaction, which holds the Files row lock by then. It only sets `noEvent`: a confirm that makes no such choice writes nothing and never clears a stored decision.

Decision: when the decision is `noEvent`, the match step creates no card and links nothing; the transcript stays without an Event. The pairing can still be set manually later.

Decision: any other stored value, the default `'none'` included, leaves the match step exactly as it is today.

## Task

Load `state-writes`, `testing`, `canonical-keys` and `adr-conventions`.

1. In the confirm of the transcription card (`confirmRecordingCard` in `backend/packages/data/src/inbox/recordingCardConfirm.ts`, delivered by #1978), when the card's envelope has `noEvent: true`, write `event_decision = 'noEvent'` on the recording request in the same transaction that writes the request and enqueues the transcription, right after `recordRecordingIntake` returns. A confirm with a chosen Event, or with `noEvent` false, null or absent, writes nothing, so the request keeps the default `'none'`. Add the `noEvent` property to the envelope of #1978 in `recordingCardEnvelope.ts`: the property keys `RECORDING_PROPERTY_KEYS`, the schema and `RecordingCardProperties` (`noEvent` is `false` when it is not `true`), with the refusal of `noEvent: true` next to an `eventId`. Add one constant and two small functions to the recording request store of #1574, `backend/packages/data/src/transcription/recordingIntake.ts` (the module that writes and reads `recording_requests`): `RECORDING_EVENT_DECISION_NO_EVENT = "noEvent"`; `setRecordingEventDecision(client, fileItemId, decision)`, an UPDATE of the request's `event_decision` by tenant and file item whose result goes through `requireAffectedRows`; and `readRecordingEventDecision(client, fileItemId)`, which returns `noEvent` when that is the stored value and null otherwise, also when the request does not exist. Use the setter from the confirm; the write goes through that store, not raw SQL in the confirm. The result of `readRecordingRequest` does not change.
2. In `matchTranscriptToEvent`, before computing candidates and before the existing idempotent-replay checks create anything, look up the recording request of the audio file the transcript was created from (the Files item id that `readTranscriptionSourceFileItemId` reads from the transcript's `link`) with `readRecordingEventDecision`. Put the check at the top of `readOpenMatch`, which `matchTranscriptToEvent` and `readEventRecommendationContext` share, so a recording with the decision `noEvent` also makes no paid recommendation call. When the decision is `noEvent`, return a new outcome `noEventChosen` and write nothing. Extend `TranscriptEventMatchOutcome` with it. The caller, `runEventMatch` in `backend/services/semprec-transcribe/src/eventRecommendationStep.ts`, already treats every string outcome as a finished step, and `transcriptionTask.ts` is not changed.
3. A transcript with no recording request (a file uploaded as a plain Files item) behaves as before.
4. Add no migration. The transcription process (`semprec_side`) already reads `recording_requests` in its prepare and create steps, and migration `0137_recording_requests.sql` grants `SELECT, INSERT, UPDATE, DELETE` on the table to `semprec_side`; the column, its default and its constraint stay as #1574 created them.
5. Tests: a confirm with `noEvent: true` stores `noEvent`, and a confirm without it, also one with a chosen Event, leaves the default `'none'`; the envelope refuses `noEvent: true` together with an `eventId` and a `noEvent` that is not a boolean; `readRecordingEventDecision` returns `noEvent` for the stored value `noEvent` only (a default request, another stored value and a missing request give null); with `noEvent` the match creates no card and no edge, also on a second run (a rerun of the transcription), and `readEventRecommendationContext` returns null for it even with two overlapping Events; with the default `'none'` and no candidate the card is created as before; a transcript without a recording request is unaffected.
6. ADR: add `docs/adr/<date it is written>-the-value-no-event-of-a-recording-requests-event-decision-is-the-explicit-no-event-choice.md` (standalone; reference `[[2026-11-14-inbox-recording-cards-confirm-into-recording-intake]]` and `[[2026-11-05-recording-intake-coordinates-files-and-transcription]]`): the column keeps `'none'` as its default and as "not decided" and `noEvent` is the explicit decision; the card's `noEvent` property; the confirm writes the decision in its own transaction through the store of the recording intake and never clears it; the transcription worker's match step reads it and treats it as a finished step. A revise keeps a user value `noEvent: true` (extend the revise test of recordingCard.test.ts that keeps manual choices); a revise whose assistant envelope names an `eventId` while the kept value is `noEvent: true` is refused with a ValidationError on `noEvent`. The ADR references [[2026-11-14-inbox-recording-cards-confirm-into-recording-intake]], [[2026-11-05-recording-intake-coordinates-files-and-transcription]], [[2026-09-23-transcription-worker-writes-event-match-results]], [[2026-11-13-transcription-recommends-the-event-of-an-ambiguous-recording]] and [[2026-11-11-an-edge-to-a-trashed-event-is-no-link-for-the-match-and-a-pairing-card]], and states that the default `none` is also an `event_decision` and means that the user did not decide, and that the match returns `noEventChosen` before `alreadyLinked` when `noEvent` is stored.

## Acceptance criteria

- When a recording whose recording request names no Event is confirmed with `noEvent: true`, then `event_decision` is `noEvent`, and after the transcription finishes (and after a rerun) there is no "recording without an event" card and no Event edge. A request that already names an Event keeps it (the first accepted values win); the match then returns `noEventChosen` and writes nothing.
- When a recording is confirmed with a chosen Event, then the transcript is linked to that Event and the match step changes nothing.
- When a recording is confirmed without an event choice (`event_decision` stays the default `'none'`) and no Event overlaps, then the "recording without an event" card is created as today.
- The ADR of Task step 6 exists.
