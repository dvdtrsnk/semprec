## Context

Model tier rationale: One SQL query and its docstring in one file plus one test file, but the change must be justified with Postgres planner and runtime-partition-pruning behaviour and verified against EXPLAIN ANALYZE plans under fresh statistics, which is more than a mechanical edit.

#262 required `ITEM_RELATION_FILTER_QUERY` (`backend/packages/data/src/scheduler/itemRelationFilter.ts`, run by `passesItemRelationFilter` for the `newEmail` heartbeat's relation filter) to let Postgres prune `items`, which is `PARTITION BY LIST (database_id)`, to the related item's own partition. Its pull request pinned `related.database_id = op.database_id` in the join condition and added the test "only scans the related item's own items_p_* partition, not every database's partition" in `backend/packages/data/src/__tests__/itemRelationFilter.test.ts`, which runs `EXPLAIN (ANALYZE, FORMAT JSON)` on the query and asserts that only the Folders partition was executed.

That test was flaky in CI (#1198). #1198's Task added `ANALYZE items` right before the `EXPLAIN` so the statistics no longer depend on autovacuum timing. With fresh statistics the test failed 30 out of 30 runs: the planner joined `item_relations` to an `Append` of Seq Scans over all 20 `items_p_*` partitions through a `Hash Join` / `Hash` on `related.id`, and applied `op.database_id` only later as a join filter of the outer `Nested Loop`. Plan node types: Nested Loop, Hash Join, Hash, Append, Seq Scan, Bitmap Heap Scan, BitmapOr, Bitmap Index Scan, Index Scan. Every partition was scanned. So #262's guarantee held only when stale or missing statistics happened to favour a parameterized nested loop. A plain join condition on the partition key never forces runtime pruning: Postgres prunes an `Append` at run time only when the partition-key value is an executor parameter, for example from the outer side of a parameterized nested loop, and the cost model is free to pick a hash join instead.

## Task

Load `testing`.

1. In `ITEM_RELATION_FILTER_QUERY`, replace `JOIN items related ON related.database_id = op.database_id AND related.id = CASE WHEN r.item_a = $3 THEN r.item_b ELSE r.item_a END` and the outer `AND related.deleted_at IS NULL` with a `CROSS JOIN LATERAL` subquery aliased `related`:
   ```sql
   CROSS JOIN LATERAL (
     SELECT item.properties
     FROM items item
     WHERE item.database_id = op.database_id
       AND item.id = CASE WHEN r.item_a = $3 THEN r.item_b ELSE r.item_a END
       AND item.deleted_at IS NULL
     OFFSET 0
   ) related
   ```
   `OFFSET 0` stops the planner from pulling the subquery up into the outer join tree. A lateral subquery that references outer columns can then only be executed as the parameterized inner side of a nested loop, so `op.database_id` reaches the `Append` as an executor parameter and every other partition is pruned at run time, whatever the statistics are. Keep the select list (`related.properties ->> $2 AS value`), the `relation_definitions` / `properties op` / `item_relations` joins, the `WHERE` clause on `$1` and `$3`, and the three positional parameters unchanged. Results do not change: `(database_id, id)` is the primary key of `items`, so the subquery yields at most one row per relation row, as the inner join did, and a missing or soft-deleted related item still drops the row.
2. Update the docstring of `ITEM_RELATION_FILTER_QUERY`: state why a plain join condition is not enough (with reference to #1198) and why the LATERAL subquery with `OFFSET 0` prunes deterministically. Update the comment on `collectExecutedRelationNames` in the test file so that it names the new `item.database_id = op.database_id` lookup.
3. Keep #1198's `ANALYZE items` before the `EXPLAIN`, and the assertion that exactly the Folders partition was executed.
4. Run `itemRelationFilter.test.ts` 30 times in a row under fresh statistics and report the result in the pull request description.

### Out of scope
