**Blocked by:** #273, #196

## Context

Issue #196 added the bounded IMAP IDLE live reconciliation: `backend/packages/data/src/mail/imapIdleLifecycle.ts` hosts one lifecycle per account, resolving the folders to idle on through `ImapIdleTransport.resolveFolders` and running one `runFolderLoop` per folder, and `backend/packages/data/src/mail/imapIdleClient.ts` implements that transport over imapflow. A post-merge review of #196's pull request raised three findings; none was addressed and all three are still on `develop`.

**1. The transport interface's doc comment promises behavior the code does not have.** `ImapIdleTransport.resolveFolders`'s doc says it is called "once per `start()` and again for whichever folder is reconnecting after a hard-cycle recycle or an error — a folder renamed between rounds is picked up the same way any other config drift is, by re-resolving rather than trusting a cached path". `runFolderLoop` takes a fixed `folderPath` parameter and never calls `resolveFolders` again; the same path is reused across every cycle iteration, so a folder rename or addition is only picked up when the lifecycle is stopped and restarted. The contract and the implementation disagree, and the doc is the one that is wrong.

**2. IDLE signal listeners outlive the connection.** `connect()` registers `exists`, `expunge` and `flags` listeners on the imapflow client and never removes them. `ImapFlowIdleConnection.close()` goes through `closeQuietly`, which triggers `client.logout()` → the `close` event → cleanup that removes only the `error`/`close` listeners. If imapflow emits any of the three signals during logout (a final server push before `BYE`), `onSignal` fires and calls `enqueueMailAccountSync` after the caller already considers the connection closed — contradicting the lifecycle's documented guarantee that no further enqueue happens once `stop()` has resolved.

**3. Dead test scaffolding.** In `backend/packages/data/src/__tests__/imapIdleLifecycle.test.ts` the `chokePoint` variable and its `createChokePoint` import are assigned in `beforeEach` and never read by any test.

## Task

- **`imapIdleLifecycle.ts`** — make the `resolveFolders` doc comment state what the code actually does: it is called once per `start()`, the resolved paths are held for the lifetime of that lifecycle, and a folder renamed or added while the lifecycle runs is picked up when the lifecycle is next restarted. Do not restructure `runFolderLoop` to re-resolve on reconnect: re-resolution during a running lifecycle is new behavior that #196 did not ask for, and folder-set drift over a live connection belongs with the later mail-live-sync issues (#197, #198, #251), not here.
- **`imapIdleClient.ts`** — remove the `exists`, `expunge` and `flags` listeners as part of closing a connection, before `closeQuietly`/`logout` can emit anything further, so that once `close()` has resolved no signal can still reach `onSignal`. Note that the listeners are registered in `createImapFlowIdleTransport.connect()` while `close()` lives on `ImapFlowIdleConnection`, which is constructed with the client alone and holds no reference to `onSignal` — pass the handler (or a small "detach signal listeners" callback built at registration time) into the connection so `close()` can remove exactly those three listeners. Do not use `removeAllListeners()`: it would also drop the `error`/`close` listeners the existing cleanup path relies on. Keep that existing `error`/`close` cleanup as it is.
- **`imapIdleLifecycle.test.ts`** — delete the write-only `chokePoint` variable, its `createChokePoint` import, its `beforeEach` assignment, and the `type ChokePoint` import that becomes unused with it.

Add the regression test in `backend/packages/data/src/__tests__/imapIdleClient.test.ts`, not in the lifecycle test: the lifecycle test only has a fake *transport*, while the imapflow double (`FakeImapFlow`, whose `logout()` emits `close`) lives in the client test, and that is the only place the listener behavior is observable. The test emits an `exists` signal from the fake client during logout/close and asserts that `onSignal` does not fire once `close()` has resolved.

## Scope

### In scope

- The corrected `resolveFolders` doc comment.
- Listener removal on connection close in `imapIdleClient.ts`, and its regression test.
- The dead-code removal in `imapIdleLifecycle.test.ts`, including the type import that becomes unused with it.

### Out of scope

- Re-resolving folders during a running lifecycle, and any other change to `runFolderLoop`'s cycle/backoff behavior.
- The Gmail and Graph live-sync paths (#197, #198) and read/flagged write-back (#251, #199).

## Acceptance criteria

- `ImapIdleTransport.resolveFolders`'s doc comment describes the single-call behavior the code implements, with no claim about re-resolution on reconnect.
- After an IDLE connection's `close()` resolves, an `exists`/`expunge`/`flags` emission from the underlying client no longer invokes `onSignal` and enqueues no sync — covered by a test that fails without the listener removal.
- `imapIdleLifecycle.test.ts` has no unused `chokePoint` variable, `createChokePoint` import or `ChokePoint` type import, `pnpm -r run build` in `backend/` succeeds, and the existing IDLE lifecycle and client tests still pass.
