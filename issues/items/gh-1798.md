## Context

Model tier rationale: It composes several existing filter and count capabilities into one seeded system view and adds one narrow protection rule, with a cutover and a unique index, but every piece follows an existing pattern and fixtures.

The Today list is the list of tasks the user should look at today: unfinished tasks whose effective day is today or in the past, plus tasks completed today (a completed task is shown on its completion day `completedOn` from #1544, not on its planned day), minus tasks that are hidden inside a running event or already completed inside an event. The overview shows a badge with the number of open tasks of that list. Web and iOS must read the same list from the server instead of rebuilding the rule, and they need a way to find it that does not depend on its display name.

What this builds on: the effective day, the hidden-until time and the visibility derivation of #1780; the "completed inside an event" relation of #1781; relative date conditions evaluated in the tenant time zone from #1522; emptiness conditions on relations from #1526; and the batched `item.count` from #1709. What builds on this: the overview summary route #1837 calls the count for its tasks badge.

Today (backend/packages/data):

- There is no count route. The generic query returns paged items, and clients count by paging.
- A view row (`db/migrations/0002_views.sql`, `chokePoint/viewsStore.ts`) has no stable key. The default view of each system database is created in `seed/seedTenDatabases.ts` phase 4 with `createdBy: "system"`. `createView` refuses `ownerModuleId` for a built-in view type, so the stable key is stored in the view config instead.
- `assertViewWritable` (`chokePoint/authorization.ts`) protects a system view only against agents ("system_owned"); a human may currently edit or delete it.
- The view config schema is `viewConfigSchema` in `views/viewConfig.ts` (its `filter` is a filter-tree node).

Decision: the badge counts only open (`notDone`) tasks of the Today list; completed tasks of today stay in the list but not in the badge.

Decision (product owner): a completed task is listed and sorted by its completion day, so a task completed today is in Today even when it was planned for a later day, and a task completed on an earlier day is not in Today. A `done` task without `completedOn` (completed before #1544) falls back to its effective day.

Decision: visibility is defined once, in one exported function, and is used by the view and by every count of it.

Shared-file ordering: this issue also waits for #1795 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Add an optional `systemKey` (string) to the view config schema (`views/viewConfig.ts`). Add an expand-only migration `backend/packages/data/src/db/migrations/NNNN_<name>.sql` (next free ordinal at commit time) with a partial unique index on `views (database_id, (config->>'systemKey')) WHERE config ? 'systemKey'`.
2. In `backend/packages/data/src/tasks/todayView.ts` (new) export `TASKS_TODAY_VIEW_KEY = "today"`, `tasksVisibleFilter()` and `tasksTodayFilter({ openOnly })`:
   - visible: the item is not deleted (implicit), `hiddenUntil` is empty or before now (the relative-date condition from #1522), and the `completedInEvent` relation is empty (#1526);
   - today: visible AND ((`status` is not `done` AND `effectiveDate` is today) OR (`effectiveDate` is before today AND `status` equals `notDone`) OR (`status` equals `done` AND `completedOn` is today) OR (`status` equals `done` AND `completedOn` is empty AND `effectiveDate` is today));
   - `openOnly` adds `status` equals `notDone`.
3. Seed a system view on the Tasks database for fresh installs (phase 4 of `seedTenDatabases.ts`) and add an idempotent per-tenant cutover step for existing tenants (registered in `runTenantCutoverMigrations`) that creates it when no view with `systemKey: "today"` exists on Tasks. The view has `createdBy: "system"`, `isDefault: false`, the table view type, the `tasksTodayFilter({ openOnly: false })` filter and `config.systemKey: "today"`. The seed and the cutover run after the properties and relations they filter on exist (they depend on #1780 and #1781).
4. Protect it: in the view update and delete paths, a view whose config has `systemKey` is refused for every actor, human or agent, with 403 `system_owned` (extend `assertViewWritable`; keep the existing agent rules for other views).
5. Counting: add a function `countTasksToday(client)` (or an exported filter builder, whichever fits the `item.count` input) that #1837 uses for the badge: `item.count` over the Tasks database with `tasksTodayFilter({ openOnly: true })`. Do not add a route or an operation here.
6. Tests (real database, controlled clock): a weekly task due on 12 October that is `notDone` appears in Today on 16 October as overdue; a moved task appears under its effective day; a task hidden until an event ends is absent and appears after; a task completed inside an event is absent; a done task of today is in the list and not in the open count; a task dated 22 October completed on 16 October is in the list on 16 October; a task dated 16 October completed on 14 October is not in the list on 16 October; PATCH or DELETE of the view by a human returns 403 `system_owned`; the cutover run twice creates one view; the unique index rejects a second `systemKey: "today"` view.

## Scope

### In scope

### Out of scope

- Protection of other system views.

## Acceptance criteria

- When the Today view is queried on 16 October, then it contains a weekly task due 12 October that is `notDone` and a task moved to today, and does not contain a task hidden inside a running event or a task completed inside an event; after the event ends the hidden task appears.
- When a task planned for 22 October is completed on 16 October, then it is in the Today list on 16 October; when a task planned for 16 October was completed on 14 October, then it is not in the Today list on 16 October.
- When the open count is computed, then it equals the number of `notDone` tasks of the Today list; a done task due today is in the list and not in the count.
- When a human sends PATCH or DELETE for the Today view, then the response is 403 `system_owned`.
- When a client looks up the view by `systemKey` `today` on the Tasks database, then exactly one view is found.
- When the cutover runs twice on an existing tenant, then one Today view exists afterwards.
