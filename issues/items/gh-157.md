**Blocked by:** #156, #82

## Context

Authoritative item lifecycle exists. This slice exposes shared read selection and normalized relation writes.

## Task

Implement `POST /api/databases/:id/query` and `POST /api/views/:id/query` accepting `{ filter, sort, cursor, limit, inTrash? }`, compiling the same typed filter/sort tree and returning `{ items, nextCursor }`. Use deterministic keyset pagination, default 50, maximum 200, exclude deleted rows unless `inTrash=true`, and make stored-view and ad-hoc results identical for equivalent input. Implement `PUT/DELETE /api/items/:id/relations/:propertyKey/:targetItemId` solely through the audited #82 relation choke-point so source/target database compatibility, definition identity, direction normalization, cardinality, paired properties, and ownership are enforced. Return authoritative item/relation state through #154 contracts.

## Scope

### In scope

- Both query sources, pagination/trash behavior, and relation creation/removal.

### Out of scope

- Realtime invalidations, a second filter engine, batch writes, or JSON-embedded relations.

## Acceptance criteria

- Equivalent database/view queries return identical ordered envelopes and stable non-duplicating page cursors.
- Invalid filter/sort/limit/cursor inputs return `validation_failed` without partial results.
- Relation route tests cover direction, every cardinality, paired definitions, foreign property keys, and owner violations.
