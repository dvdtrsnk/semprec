**Model tier:** high

## Context

Model tier rationale: Confirm must place several blocks at a section end inside one transaction with the status transition, with deterministic block ids for idempotency and a stale-heading conflict path, which is a delicate atomicity and ordering contract.

After #1643, a Processing proposal can carry a v2 `pageContent` envelope `{markdown, placement, heading?}` that is validated but not yet written. The old confirm path (`confirmProposalWithClient`, `backend/packages/data/src/inbox/proposalActions.ts`) calls `putBlockWithClient(target, {id: proposal.id, ...}, 'ai_agent')`; the block id equals the proposal id, so a retry is idempotent, but the block has no position and only one block can be written. #1679 delivers `page.insert`: insert Markdown into a page at a placement `start | end | {afterBlockId}`.

Semantics decided here:

- "Under heading X" means at the end of X's section: after the last block before the next heading of the same or a higher level, or the end of the page when there is none.
  Decision: end of section, not directly below the heading.
- The optional `heading` text is inserted as a heading block before the content, one level below the section heading (at most `h3`); when the placement is not under a heading, `h2`.
  Decision: one level below the section heading, never above `h3`.
- Author of the inserted blocks: `user`, the acting user who confirmed (decided by the product owner); that Semp proposed them is recorded on the card (per-step `blockIds`, #1648). This applies to the old `pageContent` shape too, whose `putBlockWithClient(..., "ai_agent")` call in `confirmProposalWithClient` changes to `user`.
  Decision: same author as journal entries (#1981).

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In `confirmProposalWithClient`, replace the explicit 409 for the v2 shape with a branch executed in the same transaction as the `proposed -> confirmed` transition: obtain the page with `getOrCreateDoc(target, 'page')`, then in one `mutateDocWithClient` resolve the placement and call `page.insert`:
   - `end` and `start` map directly;
   - `afterHeading: <id>` is resolved inside that mutation to `{afterBlockId}` of the last block of the section as defined above; if the heading block no longer exists, throw a conflict error mapped to 409 and leave the card `proposed` so the client can offer a new choice;
   - if `heading` is set, insert the heading block first, then the Markdown blocks after it.
   If #1679 cannot express the section end, extend it in this issue with a placement `{endOfSection: headingBlockId}` rather than computing it twice, and name that in the pull request.
2. Block ids are derived deterministically from the proposal id and the block order (for example UUID v5 of `proposal.id` plus index), including the heading block. A second confirm of the same proposal adds nothing and returns the stored result.
3. Result fields: `resultItemId` is the target item id, `resultLabel` its display name (as for the old shape).
4. A target without a page document gets one created; the confirmed content is then its only content.
5. The old shape is not touched, except that its block is now written with origin `user` instead of `ai_agent`.
6. Tests in `proposalActions.test.ts`: confirm with `afterHeading` of heading "Tiles" inserts the optional heading and two bullets at the end of that section and leaves the order of other blocks unchanged; confirming twice adds no block; stale heading gives 409 and no write; project without a doc gets the doc created; `start` and `end` placements; the document updates of a confirmed v2 and old-shape proposal have `created_by` `user` and the step result lists the inserted block ids; old shape otherwise unchanged.

## Acceptance criteria

- When a card with `placement: {afterHeading: <id of "Tiles">}` and two bullets is confirmed, then the bullets (preceded by the optional heading block) are at the end of the "Tiles" section and the order of all other blocks is unchanged.
- When the same proposal is confirmed again, then no block is added.
- When the chosen heading was removed before confirm, then the answer is 409, the card remains `proposed` and nothing is written.
- When the target has no page document, then it is created and contains only the confirmed content.
- When a heading is requested under an `h2` section, then it is an `h3`; under an `h3` section it is still `h3`; with no section it is `h2`.
- When an old-shape card is confirmed, then behavior is identical to today except that the document update has `created_by` `user`.
- When a v2 card is confirmed, then its document updates have `created_by` `user` and the step result lists the inserted block ids.
- When any step fails, then the card is not `confirmed` and no partial blocks remain.
