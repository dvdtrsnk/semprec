## Context

The web client reads and writes every view's data through `createHttpGenericOperations` (`web/src/api/httpGenericOperations.ts:67`). It is constructed in `web/src/main.tsx:38` with `baseUrl` `/api` (`main.tsx:31`). Most of its URLs do not exist on the backend: the backend's route catalogue is `backend/services/semprec-api/src/routeMatrix.ts`, and the item routes are in `backend/services/semprec-api/src/itemsHandler.ts:79-213`.

| Port method | Adapter calls today | Backend serves |
|---|---|---|
| `listItems` | `POST /databases/:db/items/query` (`:82-84`) | `POST /api/databases/:id/query` (`routeMatrix.ts:402`, `itemsHandler.ts:158-174`) |
| `countItems` | `POST /databases/:db/items/count` (`:86-89`) | no count route; only the paged query above |
| `getItem` | `GET /databases/:db/items/:id` (`:91-102`) | `GET /api/items/:id` (`routeMatrix.ts:374`, `itemsHandler.ts:98-121`) |
| `updateItem` | `PATCH /databases/:db/items/:id` with `{ properties }` (`:108-115`) | `PATCH /api/items/:id` with `{ properties, ifVersion }`. `ifVersion` is required (`backend/packages/shared/src/genericOperations/schemas.ts:213-221`) and is the item's `updatedAt` (`backend/services/semprec-api/src/adapter/itemEnvelope.ts:3-8`) |
| `linkItem` | `POST /databases/:db/items/:id/relations/:key` with `{ targetItemId }` (`:117-124`) | `PUT /api/items/:id/relations/:propertyKey/:targetItemId`, idempotent (`routeMatrix.ts:416`, `itemsHandler.ts:175-194`, `schemas.ts:229-238`) |
| `unlinkItem` | `DELETE /databases/:db/items/:id/relations/:key/:target` (`:132-139`) | `DELETE /api/items/:id/relations/:propertyKey/:targetItemId` (`routeMatrix.ts:423`, `itemsHandler.ts:195-212`) |
| `getView` | `GET /views/:id` | exists (`routeMatrix.ts:318`), unchanged |
| `callOperation` | `POST /operations/:id` (`:126-130`) | no such route anywhere in the backend |

Response shapes already match the web schemas:
- the query returns `{ items, nextCursor }` (`backend/services/semprec-api/src/adapter/itemQueryEnvelope.ts:43-50`);
- items are `{ id, databaseId, properties, computed, updatedAt, deletedAt }` (`itemEnvelope.ts:10-29`).

The query's `limit` is capped at 200 (`schemas.ts:17-18`).

Deleting an edge that does not exist answers `404` with body `{ "error": { "code": "not_found", "details": { "resource": "relationEdge", … } } }`. That status and body come from `backend/packages/application/src/genericApplicationService.ts:321-336` and `backend/services/semprec-api/src/adapter/errorContract.ts:118-124`. The port promises that removing an absent edge is a no-op (`web/src/api/genericOperations.ts:72-73`). A missing item or relation property also answers 404, with `resource` `item` or `relationProperty` (`backend/packages/application/src/genericApplicationService.ts:48-52`, `itemsHandler.ts:43-55`).

Callers that are broken today:
- the mailbox unread counts (`web/src/views/mailbox/MailboxClient.tsx:455`) and lists (`:448`, `:471`);
- message reads (`:302`);
- triage flag, archive and delete actions (`web/src/views/mailbox/triage.ts:54`, `:76-78`);
- account discovery (`web/src/views/mailbox/accounts.ts:15-43`);
- the Journal inbox (`web/src/views/journal/JournalInboxList.tsx:47`);
- the agent page header (`web/src/views/agentPage/AgentPage.tsx:61`).

This is one of the pre-existing defects fixed first in the multi-tenancy program, because the later isolation work assumes the web client exercises the real routes.

## Task

No backend skill applies; the change is web-only. Follow `web/review-rules/` and validate every response with zod at the edge.

In `web/src/api/httpGenericOperations.ts`:

1. `listItems(databaseId, request)`: `POST /databases/:databaseId/query` with the request object as the JSON body. Parse the response with `itemPageSchema`.
2. `countItems(databaseId, request)`: page through the same route, then return the summed count.
   - Send `{ filter: request.filter, limit: 200 }` first, then the same body plus `cursor: nextCursor`, and keep following until `nextCursor` is `null`.
   - Parse each page with `itemPageSchema` and sum `items.length`.
   - Any page's failure rejects the whole call, with the existing status classification.
3. `getItem(databaseId, itemId)`: `GET /items/:itemId`, parsed with `itemSchema`.
   - Resolves `null` on a 404, and also when the returned `databaseId` differs from the requested one. This keeps the port's database-scoped contract on an id-only route.
4. `updateItem(databaseId, itemId, patch)`: read the item as in step 3. Then send `PATCH /items/:itemId` with `{ properties: patch, ifVersion: item.updatedAt }` and parse the result with `itemSchema`.
   - When the read finds nothing (404 or another database), reject with `OperationError("unavailable", …, 404)` and send no PATCH.
   - A `409 version_conflict` from a concurrent write surfaces as the existing `retryable` error. There is no automatic retry.
5. `linkItem(databaseId, itemId, relationKey, targetItemId)`: `PUT /items/:itemId/relations/:relationKey/:targetItemId` with no body. The response body is discarded. `databaseId` is not sent, because the backend resolves `relationKey` against the item's own database.
6. `unlinkItem(...)`: `DELETE /items/:itemId/relations/:relationKey/:targetItemId`. Extend `request`/`RequestOptions` so that this call alone:
   - on a 404, parses the response body with a zod schema matching `{ error: { code: "not_found", details: { resource: "relationEdge" } } }` and resolves `undefined` when it matches;
   - rejects as `unavailable` (404) for any other 404 body, a non-JSON body, or a missing body. Other statuses keep the existing classification.
7. Leave `getView` and `callOperation` unchanged. Remove the now-unused `relationPath` helper if nothing uses it. Use `encodeURIComponent` for every path segment.

In `web/src/api/__tests__/httpGenericOperations.test.ts`, update the existing URL assertions to the routes above and add the cases listed under Acceptance criteria. Change the `callOperation` case's description to say no backend route currently serves it.

## Acceptance criteria

All criteria are web unit tests with vitest (`web/src/api/__tests__/httpGenericOperations.test.ts`) and a fake `fetchImpl`. No backend is involved.

- `listItems("db", { filter })` issues `POST /api/databases/db/query` with body `{ filter }` and returns the parsed page.
- `countItems` follows `nextCursor` across pages (for example 200 + 3 items over two requests, the second carrying `cursor`) and returns 203. A 403 on any page rejects with kind `unavailable`, and a 500 rejects with kind `retryable`.
- `getItem("db", "e1")` issues `GET /api/items/e1` and returns the item. It resolves `null` on a 404 and also when the item's `databaseId` is not `db`.
- `updateItem("db", "e1", { read: true })` issues `GET /api/items/e1`, then `PATCH /api/items/e1` with `{ properties: { read: true }, ifVersion: <updatedAt from the GET> }`. When the GET 404s, it rejects with kind `unavailable` and issues no PATCH. A 409 on the PATCH rejects with kind `retryable`.
- `linkItem("db", "e1", "folder", "f2")` issues `PUT /api/items/e1/relations/folder/f2` with no body, and accepts a 200 with a JSON body or a 204.
- `unlinkItem("db", "e1", "folder", "f1")` issues `DELETE /api/items/e1/relations/folder/f1`. It resolves on 200, and on a 404 whose body has `error.code: "not_found"` and `details.resource: "relationEdge"`. It rejects as `unavailable` on a 404 with `resource: "relationProperty"` or with an unparseable body.
- Path segments containing `/` or `?` are percent-encoded.
- `getView` and `callOperation` requests are unchanged.
- `pnpm run verify` in `web/` passes (lint, format, build, tests).
