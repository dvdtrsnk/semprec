**Model tier:** medium

## Context

Model tier rationale: One filter added to an existing list query, but titles of automatic-task and Inbox-item threads are resolved live rather than stored, so the search has to match against the same resolved values the list shows, and user input reaches a pattern match.

The chat list has a search field. Typing a word narrows the list to the threads whose title or preview line contains it, without regard to case or diacritics ("uctenka" finds "Účtenka za oběd"); an empty result is shown as "Nothing found". Today the list endpoint `GET /api/semp/threads` (#1729) has no query parameter. It returns, per thread, a title (the stored title for chats, the current heartbeat name for automatic-task threads, and for Inbox item threads a template filled from the item's current text, all resolved by one shared function) and a preview (the last message cut to 140 code points). The text of the pending approval requests shown above the list is filtered by the approval list endpoint itself (#1785), not here.

This issue adds `q` to that list. Global search over chats (#1854) and search over the whole message history (#1783) build on the same query.

Decision: the preview is searched as displayed, that is the first 140 code points of the last message text, not the whole message. A hit that the user cannot see in the row would be unexplained. System messages have no text preview and never match on it.

Decision: matching is case-insensitive and diacritics-insensitive substring matching (`unaccent` and `ILIKE` over the resolved title and the preview text). The characters `%`, `_` and `\` in the input are escaped so they match literally. Full-text lemma matching is not used here.

## Task

Load `io-hardening`, `canonical-keys` and `testing`.

1. Add the optional query parameter `q` to `GET /api/semp/threads`: trimmed; an empty or whitespace-only value means no filter; a value longer than 100 code points is a validation error. It combines with `kind`, `subjectInboxItemId` and paging: the filter is applied before the page is cut, so `nextCursor` and `limit` keep their meaning.
2. In the list store (`backend/packages/data/src/semp/sempThreadsListStore.ts`, from #1729), apply the filter in SQL over the same resolved title (stored title, live heartbeat name, live Inbox item text) and the 140-code-point preview, so a title that is only known after resolution still matches. Escape the pattern characters and pass the pattern as a parameter, never concatenated into the query.
3. Keep `hasPendingApproval` and every other row field exactly as in the unfiltered list.
4. Tests: "uctenka" finds a thread titled "Účtenka ..." and one whose last message begins with it; case does not matter; a tick thread is found by its current heartbeat name and an item thread by its current item text, including after the name or text changed; text beyond the 140-code-point preview does not match; `%` and `_` in `q` match literally; `q` combined with `kind=tick` and with paging returns a consistent page sequence; nothing is found for an unknown word; another tenant's threads never match.

## Touches

## Scope

### In scope

- The `q` parameter of the thread list: validation, escaping, matching over the resolved title and the displayed preview, paging interplay.

### Out of scope

- Searching approval requests (#1785).
- Searching message text beyond the preview (#1783) and a result snippet.
- The chat group of global search (#1854).
- Highlighting and ranking.

## Acceptance criteria

- When `q=uctenka` is requested, then a thread titled "Účtenka za oběd" is returned, and so is a thread whose last message starts with "Účtenka"; capitalization does not matter.
- When a heartbeat is renamed, then a search for the new name finds its tick thread and one for the old name does not.
- When the matching word is only in the last message beyond its first 140 code points, then the thread is not returned.
- When `q` contains `%` or `_`, then they match only themselves.
- When `q` is empty, then the response is the same as without it; when it is longer than 100 code points, then the response is a validation error.
