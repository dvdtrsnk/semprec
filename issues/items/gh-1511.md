**Model tier:** high

## Context

Model tier rationale: Creating new system databases and a project for every existing tenant through a per-tenant cutover under the shared advisory lock is a cross-tenant persisted-data change whose idempotency and lock ownership must be exact.

#1353 declares the Finance module. This issue creates its data for every tenant: a system project Finance, the databases `transactions` and `financeCategories` with their properties, a default view for each, and the three expense categories from the design. A new tenant gets them from `seedSystem` (`backend/packages/data/src/seed/seedSystem.ts`), which takes the per-tenant advisory lock `(2331, hashtext(tenant_id))` and returns `already-seeded` for a tenant that was seeded earlier, so an existing tenant would never receive a module added later. The repo's answer for that is a per-tenant cutover in `backend/packages/data/src/db/tenantCutoverMigrations.ts` (`runTenantCutoverMigrations`, one `forEachMaintainedTenant` pass under the `semprec_data` role, see ADR `docs/adr/2026-10-08-per-tenant-queue-lanes.md` and `docs/adr/2026-09-10-app-code-post-migration-steps.md`), which deploy already runs through `runSeedCli` and `provisionTenant`. Other modules that must reach existing tenants (recipes, sleep) use the same pattern; this issue follows it.

The model to copy is `seedLibraryModuleInTransaction` (`backend/packages/data/src/seed/seedLibraryModule.ts`): each database is created with `name: null`, `key = ownerModuleId`, `system: true` and an `ownerProjectItemId`, so labels come from the catalog of #1353; the schema is locked at the end with a raw `UPDATE databases SET schema_locked = true`.

What builds on it: #1553 adds the links to companies, projects and documents, #1585 reads categories and budgets, #1748 writes expenses from the Inbox and #1973 and #1977 make transactions an Inbox target.

Decisions:
- A transaction's `name` is a free description; the list shows the company when there is one, otherwise the name.
- Budgets are stored as `monthlyBudget` on each category (a total is their sum); there is no separate budgets database.
- `source` and `sourceInbox` are `owner: "system"` with owner process `inbox` (the Inbox module id), because only the Inbox confirm writes them. A transaction without a `source` is a manual one; no `manual` is ever written by the system.
- The three seeded categories are named as in the design: Bydlení (`house`, `#FF9500`), Jídlo a nákupy (`bag`, `#34C759`), Doprava (`car`, `#007AFF`), with `sortOrder` 1, 2, 3 and no budget. Category rows are ordinary editable items.
- Income is a transaction with `type` `income`, not a category.


Shared-file ordering: this issue also waits for #1509 because both edit the same files listed in Touches.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Create `backend/packages/data/src/seed/seedFinanceModule.ts` exporting `seedFinanceModuleInTransaction(client, projectsDatabaseId, viewTypeRegistry, computedKeyRegistry)`, modelled on `seedLibraryModule.ts`:
   - one Projects item `Finance` with `systemActive: true` and an `agents` text in the style of the library projects (purpose, allowed, not allowed, general instructions);
   - database `transactions` (`ownerModuleId` from the keys file of #1353) with properties: `name` (title), `amount` (number), `currency` (select, option `CZK`), `type` (select, `expense` and `income`), `date` (date), `dueDate` (date), `paymentStatus` (select, `unpaid` and `paid`), `paidAt` (date), `note` (text), `source` (select, `manual` and `inbox`, owner `system`, owner process `inbox`) and `sourceInbox` (relation to Inbox, owner `system`, owner process `inbox`, one-directional);
   - database `financeCategories` with `name` (title), `icon` (select, `house`, `bag`, `car`), `color` (color), `monthlyBudget` (number), `sortOrder` (number);
   - the relation `financeCategories.transactions` (`one_to_many`) with inverse `transactions.category`, both properties unlocked and created together;
   - the three categories above; a default table view per database; both databases `schema_locked = true` at the end.
2. Call it from `seedSystem` after the library module, so a new tenant receives it inside the same transaction and lock.
3. Create `backend/packages/data/src/finance/financeModuleProvisioningCutover.ts` exporting `runFinanceModuleProvisioningCutover(pool)`. In the caller's tenant scope, under the same advisory lock as `seedSystem`, it checks `getDatabaseByModuleId` for both keys and calls the seed in step 1 only when a database is missing (a Projects item `Finance` already present counts as present); it does nothing else. A second run changes nothing.
4. Call it from `runTenantCutoverMigrations` in `tenantCutoverMigrations.ts`, inside the existing per-tenant loop, after the existing cutovers.
5. Tests with the real schema: a new tenant has the project, both databases, all properties and exactly the three categories; an existing seeded tenant gains them after the cutover; running the cutover twice leaves exactly one project and three categories; the Finance project can be deactivated and cannot be deleted (403); the databases cannot be archived; `/api/schema` returns Czech and English labels for `transactions` by `users.locale`; a second tenant is untouched by the first one's cutover.

## Scope

### In scope

- The Finance project, the two databases with their properties, the category relation, the three seeded categories, the default views, and creating all of it for new and existing tenants idempotently.

### Out of scope

- Links from transactions to companies, projects and documents: #1553.
- Validating transaction values: #1607.
- Making Finance an Inbox target: #1973 and #1977.
- Which agents may write to these databases: #1815.
- Importing from a bank, several currencies and bank accounts: not planned yet; they wait for a product decision.

## Acceptance criteria

- When a new tenant is provisioned, then it has the project Finance, the databases `transactions` and `financeCategories` with the properties above, and the three categories.
- When the cutover runs for an existing tenant, then the same objects exist afterwards; running it again changes nothing.
- When the Finance project is deleted, then the response is 403; when it is deactivated, then it succeeds.
- When a database is archived, then the response is 403.
- When `/api/schema` is requested with a Czech and an English user, then `transactions` labels come back in the user's language.
- When two tenants exist, then each has its own Finance objects and the cutover of one never writes into the other.
