## Context

Model tier rationale: It adds the central calendar read that merges two databases with relations, tenant-zone day arithmetic, tolerant handling of invalid stored values and an extension point that six later issues plug into, so a mistake is visible in every calendar view and for every tenant.

There is no calendar read today. A client can query one database at a time (`POST /api/databases/:id/query`, `views/viewQuery.ts`), the item envelope carries no relations (`backend/services/semprec-api/src/adapter/itemEnvelope.ts`), and a project or people can only be found by extra queries. Date filters cast to `timestamptz` in the database session time zone (`views/filterCompiler.ts`), and an invalid stored date makes the whole query fail. The tenant time zone is read with `getSystemTimezone` (`backend/packages/data/src/systemSettings.ts`). The calendar views need one call that returns everything that happens in a date range: Events, Tasks and, in later issues, derived entries such as birthdays, holidays, sleep nights and recurring occurrences.

This issue adds `GET /api/calendar/timeline?from=YYYY-MM-DD&to=YYYY-MM-DD[&shape=compact]`, a custom route of the calendar module with justification `single-consumer-read` (`docs/adr/2026-09-11-module-manifest-custom-routes.md`), and the shared read function behind it, `readCalendarTimeline`, which the agenda (#1762) and the Semp tool (#1952) reuse. The client never computes anything: no merging, grouping or day arithmetic. Time arithmetic uses the calendar time module of #1418; date and time format checks reuse the validators of #1663 and #1536.

Request rules: `from` and `to` are dates, `to` is not before `from`, the range is inclusive of both days, and it is at most 93 days (a protection; a month grid is at most 42 days); otherwise 400 `validation_failed`.

Response: `{ timezone, today, now, from, to, items }`, where `timezone` is the tenant zone and `today` and `now` come from the calendar time module. Each item has `kind` (`event` or `task` in this issue), `id`, `databaseId`, `title`, `type` (the Event type, otherwise null), `date`, `endDate`, `timeFrom`, `timeTo`, `effectiveTo` (the end time used for display after the defaults of the time module; for a timed Task without an end it equals `timeFrom`, since a Task has no default length), `hasEnd` (whether an end was stored), `allDay` (no `timeFrom`), `calendarId` (an Event's `Events.calendar` edge, or the live default calendar when an older Event has no edge; the id of the calendar with system key `tasks` for a Task; null if the tenant has no calendars yet), `status` (a Task's status, otherwise null), `place`, `project` (`{ id, name, color }` or null), `people` (`[{ id, name }]`), `updatedAt` (for `ifVersion`) and `readOnly` (false for stored items). With `shape=compact` (the month view) each item has only `id`, `kind`, `title`, `calendarId`, `allDay`, `date`, `endDate`, `timeFrom`, `status`, `updatedAt` and `readOnly`.

Selection: an Event is included when its `date` is on or before `to` and its last day (`endDate`, else `date`) is on or after `from`; a multi-day Event appears once, with its range. A Task is included when its display day (its `date`) is inside the range; a done Task is included with status `done`, a `wontDo` Task is not, and trashed items never are. A row whose stored date or times are not valid is left out of the response (never a 500), with a log line carrying the item id.

Order: by day, and inside one day: all-day Events, then Tasks without a time, then timed Events, then timed Tasks; inside a group by `timeFrom`, then title (compared with the tenant user's locale collation, `cs` by default), then id. The same order serves the day view and both month views.

Extension point: further sources (birthdays, holidays, sleep nights, task and Event occurrences, subscribed events, task-in-event state, traces) are separate issues. They plug into a list of timeline sources in `calendar/timelineSources.ts` (`{ id, readItems(client, context) }`, each returning items for the range and the shared context of time zone, `today` and `now`), so adding a source never edits the core merge. Items from sources that are not stored rows have a synthetic `id` and `readOnly` true.

Decision: hidden calendars are not filtered on the server; every item carries its `calendarId` and the client hides according to the calendar's `hidden` flag.

Decision: a multi-day Event is returned once with its range, not once per day.

Decision: an Event without a calendar edge (created before the calendar cutover) is kept as it is and is returned with the default calendar's id as `calendarId`; the read writes no edge.

Decision: nothing is cached; the client refetches after the realtime invalidations of Events, Tasks, People, calendars and edges.

Shared-file ordering: this issue also waits for #1709 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Acceptance criteria

- When the timeline is read for 16 Oct 2026, then the items and their order are as listed in the tests above, and the `wontDo` Task is absent.
- When an Event spans 24-25 Oct, then it is returned for a range containing only 25 Oct.
- When the tenant zone is Europe/Prague and it is 23:30 UTC on 16 Oct, then `today` is `2026-10-17`.
- When an Event has an invalid stored date, then it is omitted and the response is 200.
- When the range is longer than 93 days or malformed, then the response is 400 `validation_failed`.
- When the same range is read for another tenant, then no item of this tenant appears.
- When an Event has no `Events.calendar` edge, then its item carries the id of the live default calendar as `calendarId`, and no edge is created by the read.
