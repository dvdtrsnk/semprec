## Context

Model tier rationale: A new aggregate read crosses four databases through a two-hop relation path (task to project to area), must be correct in the tenant's time zone and tenant-isolated, and is the contract a later summary route relies on.

An area's page shows, above its content: the number of active projects, tiles for tasks due today and for all open tasks, the number of upcoming events, and a chronological "upcoming" list of tasks and events coming from the area's projects, each with its project's own color. Today none of this can be read in one call. The generic query cannot express "task, via its project, belongs to this area" (`views/filterCompiler.ts`) until #1363 (one extra relation hop in filters); counting needs #1709 (`item.count` with grouping). Relations involved, from `backend/packages/data/src/seed/seedTenDatabases.ts`: `Areas.projects` (one-to-many, inverse `Projects.area`), `Projects.tasks` (inverse `Tasks.project`), `Projects.events` (inverse `Events.project`). A task or event without a project belongs to no area. The Projects database also holds five system projects marked `systemActive` that are never shown or counted.

This issue adds `GET /api/areas/:id/overview`. By the program decision recorded in `docs/adr/2026-09-10-single-writer-ownership-model.md`, routes over Tasks and Events are owned by the `systemDatabases` module, so it is a `customRoutes` entry in `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` with justification `single-consumer-read` (a read shaped for one screen), following `createTranscriptSpeakersRouteHandler` in `transcription/transcriptionRouteHandlers.ts`. #1837 (the global overview summary) builds on the active-project rule defined here.

Response:
`{ activeProjectCount, todayTaskCount, openTaskCount, upcomingEventCount, upcoming: [{ kind: "task"|"event", itemId, title, date, timeFrom, timeTo, status, recurrence, project: { id, title, color } }] }` where `project.color` is the project's own `color` property and `recurrence` is the task's active recurrence rule (`tasks/taskRecurrenceStore.ts`) or null.

Rules:
- Eligible projects are those of the area that are not soft-deleted, not `archived` and not `systemActive`. Projects with status `done` stay eligible, so their open tasks count in `openTaskCount` and appear in `upcoming`.
- `activeProjectCount`: eligible projects with status `inProgress` or `longTerm`.
- `openTaskCount`: all tasks with status `notDone` of eligible projects, with or without a date, no horizon.
- `todayTaskCount`: `notDone` tasks of eligible projects whose date is today or earlier.
- `upcoming`: `notDone` tasks with a date up to the end of the horizon (overdue ones included) plus events of eligible projects that start from now to the end of the horizon; sorted by date, then time, then title; at most 20 entries. `upcomingEventCount` is the number of events within the horizon, counted before the 20-entry limit. Tasks with status `done` or `wontDo` and soft-deleted tasks and events never appear.
- "Today" and "now" are computed in the tenant's time zone (`getSystemTimezone` in `backend/packages/data/src/systemSettings.ts`), not UTC.

Decisions:
- The horizon is 14 days counting today (the end of the 14th day in the tenant's time zone).
- An event counts as upcoming when its start is not before now; events that already started are not listed until an event end is stored (that field arrives with #1416 and the follow-up listed in Out of scope).

Shared-file ordering: this issue also waits for #1759 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Scope

### In scope

- The route, the five rules above, the 20-entry limit, time-zone handling and tests.

### Out of scope

- The end of an event, tasks hidden inside events, the original day of a moved task, and the flag on a task. These fields are added to `upcoming` by a follow-up issue after the mechanisms exist: #1416, #1780, #1798, #1602, #1673.
- Publishing the realtime invalidation when a task is moved or a project's area changes: #1621; clients refetch the overview when they receive it.
- The global overview summary: #1837.
- Grouped project counts for all areas at once (they use `item.count` directly).

## Acceptance criteria

- Given a test fixture area whose eligible projects hold two `notDone` tasks dated today or earlier and seven `notDone` tasks in total, one of them without a date, the response has `todayTaskCount: 2` and `openTaskCount: 7`, and `upcoming` is ordered by date and time with each entry's project color. Expected values come from the fixture data, not from numbers in the design.
- A `notDone` task of a `done` project counts in `openTaskCount`; a task of an `archived` project does not.
- `activeProjectCount` counts `inProgress` and `longTerm` projects and does not count system projects, finished, archived or deleted ones.
- A task moved to a project of another area is absent on the next read.
- An overdue `notDone` task appears in `upcoming`; a `wontDo` task and a task without a project do not.
- At 00:30 local time in the tenant's time zone, "today" is the local date, not the UTC date.
- A foreign-tenant, unknown or non-area id answers 404.
- The full backend `pnpm run verify` passes.
