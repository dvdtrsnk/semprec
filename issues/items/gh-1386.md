## Context

Model tier rationale: One additive column and two writers in the transcription failure path, following existing item_automation and notification patterns, but it must never leak provider exception text.

When transcription fails permanently, `recordTranscriptionFailure` in `backend/services/semprec-transcribe/src/transcriptionTask.ts` stores the exception message in `item_automation.error`, sets `status = error` and writes an `automation_error` notification with `linkHref` null (the transcription has no page to open). `item_automation` (created in `0005_library_module.sql`, access in `library/itemAutomationStore.ts`) has `status`, `error`, `attempts` and `last_attempt_at` only. Clients therefore cannot tell why a recording failed, and the notification leads nowhere.

This issue stores a stable error code beside the diagnostic message and links the notification to the transcript, so an app can show a localized reason and open the failed recording. `error` stays diagnostic only: no API returns it, and transcript content is never logged. It unblocks #1576 and #1636 (both return the automation state), #1945 and #1582 (the cancellation path writes the code `deleted`).

Decision: the notification link is `?page=transcript&id=<transcriptId>`; clients must have a page for it.

## Task

Load `db-migrations`, `error-handling`, `state-writes` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_item_automation_error_code.sql (next free ordinal at commit time)`: `ALTER TABLE item_automation ADD COLUMN error_code text NULL`. Additive; no backfill.
2. In `library/itemAutomationStore.ts` add `errorCode` (`budgetExceeded | mediaUnreadable | providerFailed | unknown | deleted`) to `ItemAutomationRow`, its mapper and `recordItemAutomationFailure` (new optional argument), validated on read.
3. In `recordTranscriptionFailure` classify the thrown error into a code (budget exhaustion, ffmpeg/probe failure, gateway failure, otherwise `unknown`) and store it with the message; a retry that succeeds clears the code with the error.
4. Give the permanent-failure `automation_error` notification `linkHref` `?page=transcript&id=<transcriptId>`.
5. Tests: each class maps to its code; the message is never part of a notification or any response; the notification link; replaying the same attempt still adds no second notification.

## Scope

### In scope

- The `error_code` column, its classification on transcription failures, and the notification link.

### Out of scope

- Returning `automation` from the transcript endpoints: #1576 and #1636.
- Raising failures as Semp problems: #1945.
- Writing the code `deleted` when the pipeline is stopped for a deleted transcript: #1582.
- Duration and finish time on the transcript: #1469.

## Acceptance criteria

- When a transcription fails permanently, then `item_automation.status` is `error` and `error_code` holds the class of the failure.
- When the failure notification is read, then its link is `?page=transcript&id=<transcriptId>`.
- When a failed run is retried and succeeds, then `error` and `error_code` are cleared.
- The exception text appears in no API response and no log line.
