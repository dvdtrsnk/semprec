## Context

Model tier rationale: One additive column and two writers in the transcription failure path, following existing item_automation and notification patterns, but it must never leak provider exception text.

Transcription failures need stable codes and safe transcript links. Diagnostic error text remains storage-only; retry, deletion and notification behavior must be preserved.

Decision: the notification link is `?page=transcript&id=<transcriptId>`; clients must have a page for it.

## Scope

### In scope

- The `error_code` column, its classification on transcription failures, and the notification link.

### Out of scope

- Returning `automation` from the transcript endpoints: #1576 and #1636.
- Raising failures as Semp problems: #1945.
- Writing the code `deleted` when the pipeline is stopped for a deleted transcript: #1582.
- Duration and finish time on the transcript: #1469.
- PostgreSQL server/infrastructure logging configuration or a general privacy guarantee: separate security supervision. Application/Graphile re-logging remains in scope.

## Acceptance criteria

- When a transcription fails permanently, then `item_automation.status` is `error` and `error_code` holds the class of the failure.
- When the failure notification is read, then its link is `?page=transcript&id=<transcriptId>`.
- When a failed run is retried and succeeds, then `error` and `error_code` are cleared.
- The exception text appears in no API response or owned application/Graphile log, including actual worker retry/final/superseded, setup/step-0 and diagnostic-record/cleanup paths. Distinct sentinels are excluded from those serialized outputs; successful stop/budget/shutdown and retry behavior stays unchanged. Preserve complete raw evidence: an intentionally raised test PostgreSQL server error may appear in its own infrastructure log, which is not an application PASS or proof of production DB-log privacy.
