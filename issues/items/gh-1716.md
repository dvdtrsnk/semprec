## Context

Model tier rationale: One computed flag requires set-based lookup and tenant isolation across production query paths.

#1659 records item_origins. Files and other list results need the Inbox-origin flag without per-row #1967 requests.

Decision: the flag is a read-time computed field on the item envelope, not a stored property, so it cannot drift and needs no schema change on any database. It is additive to the envelope (ADR `docs/adr/2026-09-11-additive-only-rest-contract-no-url-versioning.md`).

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. Add a boolean `fromInbox` to the item envelope returned by item reads and database/view queries, true exactly when an `item_origins` row exists for the item with `capture_channel = 'inbox'`, false otherwise.
2. Compute it for a whole result page with one set-based lookup (`item_id = ANY($ids)` within the tenant), never one query per row.
3. Keep existing envelope fields and ordering unchanged; clients that ignore the field are unaffected.
4. Tests: a Files query containing one item created from an Inbox proposal and one created by hand returns `fromInbox: true` and `false`; the query count for a page of 50 rows does not grow with the row count; an item whose origin row was deleted returns `false`.

5. Exercise a real Files proposal confirmation through the production Files query to prove the flag; measure the set-based origin lookup while the actual production page query runs, not a separately invoked helper. Keep the existing 50-row and deleted-origin cases.

## Acceptance criteria

- When a Files query returns an item created from an Inbox proposal, then that row has `fromInbox: true`; a hand-created row has `fromInbox: false`.
- When a page of 50 rows is returned, then origin is resolved with one query.
- When the origin row is removed (item permanently deleted or confirmation undone), then the flag is false.
