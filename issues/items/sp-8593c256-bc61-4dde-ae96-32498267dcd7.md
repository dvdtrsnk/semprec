## Context

Model tier rationale: Changes how the Graph and Google calendar HTTP answers map onto the sync's error classes, which decide whether an account stops syncing (`needsConsent`), whether a push lets a provider deletion win, and where the bearer token may go.

Review findings on the internet-accounts branch, verified in the code:

- **A provider deletion is lost when the Event has a pending push.** The pass skips the provider's deletion of an Event with an unsettled push and re-queues the push (`calendarSyncApply.ts`), and the push's update then meets 404/410: Graph's `PATCH /me/events/{id}` throws `GraphCalendarRequestError(404)` and Google's `PATCH` a plain `Error`, both recorded as `unexpected` and retried until the push is `failed`. Only a `CalendarSyncEventConflictError` makes the push read the provider's version (`mergeWithRemote`), where `getEvent` → `null` lets the deletion win. CalDAV already answers a gone resource on update as a conflict; deletes of an already-gone Event already succeed on every provider.
- **Any Graph 403 marks the account `needsConsent`.** `graphCalendarHttp.ts` maps every 403 to `CalendarSyncConsentRequiredError`, which stops the account until a new sign-in, although Graph answers 403 `ErrorAccessDenied` also for one shared calendar the account may not read. Graph's error body does not tell the two apart; Google's adapter decides by the scope challenge and reasons.
- **Graph requests follow redirects.** `GraphCalendarHttp.fetchOnce` sends the bearer token without `redirect: "error"` (Google's adapter sets it).
- The finding's "also map Graph 429" is already true: a 429 is retried within `Retry-After` and otherwise ends the pass as `rateLimited` (covered by the existing failure test); nothing changes there.

Decisions:

- An update (`putEvent` with a `ref`) answered 404 or 410 is `CalendarSyncEventConflictError` on Graph and Google.
- A Graph 403 is `CalendarSyncConsentRequiredError` only for the account's own calendar listing (`GET /me/calendars`, which any grant with the calendar scope may read and which every pass sends first) or when `WWW-Authenticate` carries `insufficient_scope`; any other 403 is `GraphCalendarRequestError(403)` (`unexpected`, retried by the queue).
- Every Graph calendar request is sent with `redirect: "error"`.

## Scope

### In scope

- The status mapping of Graph and Google calendar updates, Graph's 403 and Graph's redirects.

### Out of scope

- The create paths (`transactionId`, client ids), the push job, the pass's per-calendar error isolation, CalDAV.

## Acceptance criteria

- A Graph or Google update answered 404 or 410 rejects with `CalendarSyncEventConflictError`, and `getEvent` of that Event answers `null`.
- A Graph 403 to a calendar's delta is `GraphCalendarRequestError` with status 403; the same with an `insufficient_scope` challenge is `CalendarSyncConsentRequiredError`; a 403 to the calendar listing stays `CalendarSyncConsentRequiredError`.
- Every Graph request of a fetch and a listing is sent with `redirect: "error"`.
- The existing Graph and Google adapter tests stay green.
