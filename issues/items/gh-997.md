## Context

`POST /api/mail/graph/webhook` is public: Microsoft Graph is its only caller (`backend/services/semprec-api/src/graphWebhookHandler.ts:26-38`). It answers the validation handshake first (`:48-53`). It then parses the batch (`:55-72`) and calls `handleGraphChangeNotification(pool, notification)` for each item (`:74-79`). It answers 202 whatever the per-notification outcome (`:81-86`).

`handleGraphChangeNotification` (`backend/packages/data/src/mail/graphWebhookNotifications.ts:41-59`) does the following:
- looks the account up by `subscriptionId` (`:46`, `getMailAccountSyncStateByGraphSubscriptionId` at `backend/packages/data/src/mail/mailAccountSyncStateStore.ts:204-213`);
- returns `unknownSubscription` at once when there is no row (`:47`), with no comparison at all. This is a timing difference between "id exists" and "id unknown";
- compares `clientState` in constant time (`:21-25`), but skips the compare when either side is missing (`:48-54`);
- enqueues `mailAccountSync` for the item (`:56`).

Since #981, the body loop runs inside `runAsSystem("graph-webhook")`: there is no session to derive a tenant from. `mail_account_sync_state` is a tenant table under a RESTRICTIVE RLS policy `tenant_isolation` (`tenant_id = (SELECT app_tenant_default())`, with `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())`). So the lookup finds the subscription only while exactly one tenant exists. With two tenants, or after the strict switch (#1067), every Graph notification would be dropped as unknown. Subscription ids stay globally unique (`mail_account_sync_state_graph_subscription_id_uq`, `backend/packages/data/src/db/migrations/0041_graph_webhook_client_state.sql:15-16`).

**Decision (recorded in this issue's ADR).** An external identifier that must be mapped to a tenant before any tenant is known goes through a `SECURITY DEFINER` function owned by a new role `semprec_router`, with these properties:
- `semprec_router` is `NOLOGIN` and `BYPASSRLS`;
- it has column-level `SELECT` on exactly the columns the function reads;
- the function has a pinned `search_path` and schema-qualified objects;
- `EXECUTE` is revoked from `PUBLIC` and granted to exactly one runtime role;
- the function returns only ids or numbers, never content.

The caller then enters `runInTenant(<returned tenant>)` and re-reads everything else under RLS. No runtime role ever gets `BYPASSRLS`. The same pattern serves the Gmail Pub/Sub address (#998), where one process-wide dispatcher routes each message to every matching mailbox in its own tenant and acknowledges it once. Later admin aggregates (global AI spend, per-tenant counts) use it too. It differs from `docs/adr/2026-09-27-runtime-ddl-through-security-definer-functions.md`, whose DDL functions are owned by the migrating superuser: a superuser owner would ignore column-level limits.

Tenancy state this issue builds on:
- `runInTenant(tenantId, fn)` and `runAsSystem(reason, fn)` come from `@semprec/shared`. Entering a tenant from system scope is allowed.
- #982: `enqueueJob` stamps `tenantId` into the job envelope from the current scope.
- #989: the `mailAccountSync` job resolves its module databases per job inside that tenant.
- #976 and #996 last edited `docs/operations/database-roles.md`, which this issue extends.

## Task

Load `db-migrations` (new role, function and grants), `adr-conventions` (new cross-cutting pattern), `io-hardening` (public webhook, constant-time secret compare) and `state-writes` (the enqueue stays inside the tenant's transaction).

1. **Migration.** Take the next free migration ordinal at commit time, for example `NNNN_semprec_router_graph_subscription.sql`. Additive only:
   - Create `semprec_router` if missing: `CREATE ROLE semprec_router NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION BYPASSRLS` inside a `DO` block guarded by `pg_roles`, as `0040_least_privilege_roles.sql:33-42` does. Then pin its attributes with `ALTER ROLE semprec_router NOLOGIN NOSUPERUSER BYPASSRLS`.
   - `GRANT USAGE ON SCHEMA public TO semprec_router; GRANT SELECT (graph_subscription_id, tenant_id) ON mail_account_sync_state TO semprec_router;`
   - `CREATE FUNCTION route_graph_subscription(subscription_id text) RETURNS uuid LANGUAGE sql STABLE SECURITY DEFINER SET search_path = pg_catalog, public AS $$ SELECT s.tenant_id FROM public.mail_account_sync_state s WHERE s.graph_subscription_id = subscription_id $$;`
   - `ALTER FUNCTION route_graph_subscription(text) OWNER TO semprec_router; REVOKE EXECUTE ON FUNCTION route_graph_subscription(text) FROM PUBLIC; GRANT EXECUTE ON FUNCTION route_graph_subscription(text) TO semprec_data;`
   - A header comment explains the pattern, references the ADR, and states that the previous release is unaffected.
2. **Store (`mailAccountSyncStateStore.ts`).** Add `routeGraphSubscription(client: Queryable, subscriptionId: string): Promise<string | null>`. It runs `SELECT route_graph_subscription($1) AS tenant_id` with a typed row and returns the id or `null`. Update the docstring of `getMailAccountSyncStateByGraphSubscriptionId`: it is the in-tenant re-read.
3. **Notification handling (`graphWebhookNotifications.ts`).** `handleGraphChangeNotification(pool, notification)` keeps its signature and outcomes:
   - (a) `routeGraphSubscription` in its own `withTransaction`, in the caller's scope;
   - (b) `null` returns `unknownSubscription`;
   - (c) otherwise, `runInTenant(tenantId, () => withTransaction(pool, …))` runs today's body: the RLS re-read, the clientState check and `enqueueMailAccountSync`, so the job envelope carries that tenant.
   - **Every path performs exactly one `clientStateMatches` call.** Compare against a fixed module-level dummy secret when the subscription is unknown, the row vanished, or no state is stored. Compare against `""` when the notification has none. Only a real match on a stored state is accepted.
   - Update the docstring.
4. **Handler.** `backend/services/semprec-api/src/graphWebhookHandler.ts` stays unchanged. #981 already runs its body loop inside `runAsSystem("graph-webhook")`, from which `handleGraphChangeNotification` enters the routed tenant. Behaviour stays the same:
   - 202 for every parsed batch, whatever each notification's outcome;
   - 400, 413 and 404 for malformed or non-POST requests, as today;
   - the per-notification warning logs only `subscriptionId` and `outcome`.
5. **ADR.** Add `docs/adr/<YYYY-MM-DD>-cross-tenant-router-functions.md`, dated the day you write it, `status: accepted`, `area: [backend]`. It records:
   - **Decision:** everything in the Context paragraph "Decision" above, including the Gmail dispatcher rule.
   - **Alternatives rejected:**
     - a `BYPASSRLS` runtime role, because it puts a cross-tenant reader in every process;
     - a global routing table copying tenant keys out of RLS, because it is a second writer kept in sync by hand;
     - superuser-owned definer functions, because column limits do not apply to them.
   - **Consequences:** every router function needs its migration, a row in `docs/operations/database-roles.md`, and a privilege test.
   - It references `[[2026-09-27-runtime-ddl-through-security-definer-functions]]` and supersedes nothing.
6. **Docs.** In `docs/operations/database-roles.md`, append a section `## Cross-tenant router functions (semprec_router)`. It holds the role's attributes, the rule from the ADR, and a table: function, executing role, returned value, columns read. The first row is `route_graph_subscription(text)`, executed by `semprec_data`, returning a tenant id or `NULL`, reading `mail_account_sync_state(graph_subscription_id, tenant_id)`.
7. **Tests.** New `backend/packages/data/src/__tests__/graphSubscriptionRouting.test.ts` (integration). Extend the `handleGraphChangeNotification` block of `backend/packages/data/src/__tests__/graphWebhookLifecycle.test.ts:281-336`.

  - `route_graph_subscription(text)` is `SECURITY DEFINER`, owned by `semprec_router`, with `search_path=pg_catalog, public` in `proconfig`;

  - `has_column_privilege('semprec_router', 'mail_account_sync_state', 'last_error', 'SELECT')` is false, and it has no table-level `SELECT`.

Use either `createRuntimeRolePool(pool, "semprec_data")` from #975's `@semprec/data/testSupport` inside `runInTenant(<random UUID>)`, or `SET LOCAL ROLE semprec_data` plus `set_config` in a superuser transaction:
  - `SELECT count(*) FROM mail_account_sync_state` returns 0;
  - `route_graph_subscription('<tenant zero's subscription id>')` returns tenant zero's id;
  - an unknown id returns `NULL`;
  - as `semprec_side`, calling it fails with `42501`.
- **Routed handling (`graphWebhookLifecycle.test.ts`).** Called inside `runAsSystem`:
  - a matching notification for tenant zero's mailbox returns `accepted` and leaves one pending `mailAccountSync` job whose envelope `tenantId` is tenant zero;
  - a duplicate collapses into the same job;
  - a wrong `clientState` returns `invalidClientState` with no job;
  - an unknown id returns `unknownSubscription` with no job.
- **Constant-time compare on every path (`graphWebhookLifecycle.test.ts`).** With `node:crypto`'s `timingSafeEqual` replaced by a counting wrapper around the real implementation (`vi.mock` with `importOriginal`), exactly one compare happens for each of these:
  - an unknown subscription;
  - a known subscription without a stored client state;
  - a notification without `clientState`;
  - a mismatch;
  - a match.
- **Two tenants (`graphSubscriptionRouting.test.ts`; tenant B from `createTestTenant(pool)`, calls over `createRuntimeRolePool(pool, "semprec_data")`, both from #975).**
  - A notification for tenant B's subscription enqueues a job whose envelope `tenantId` is B, and nothing for tenant zero.
  - B's subscription id with tenant zero's `clientState` is `invalidClientState`.
- **Webhook responses unchanged (`backend/services/semprec-api/src/__tests__/graphWebhookHandler.test.ts`, existing).** Every existing case passes: 202 for accepted, rejected and unknown notifications alike; 400, 413 and 404 as before.
