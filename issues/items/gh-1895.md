## Context

Model tier rationale: This attaches files that may already belong to another email by sharing blobs, enforces provider-dependent size limits and must own the cleanup of uploaded files when a draft is discarded.

A draft can carry attachments: the user picks a file in the compose window, or forwards a message and its attachments come along. The `Emails.attachments` relation is `one_to_many` and system-owned by the Emails module process (`backend/packages/data/src/seed/seedEmailModule.ts`, `EMAILS_RELATION_CONTEXT` in `emailsRelationContext.ts`), so a Files item belongs to exactly one email and only the module's writer may write the edge. Files are uploaded through `POST /api/files` (limit `MAX_FILE_SIZE_MB`, `backend/services/semprec-api/src/serve.ts`). `attachments.ts` shows how synced attachments create a Files item over a deduplicated blob.

It builds on the draft interface (#1867). Reply and forward (#1899) use it to copy the attachments of a forwarded message.

Decision: provider limits on the total attachment size of a draft are Gmail 25 MB, Outlook.com 20 MB, iCloud 20 MB, and `MAX_FILE_SIZE_MB` for a generic account.

Decision: a file that is already attached to another email is not moved; a new Files item over the same blob is created, so the original message keeps its attachment.

Shared-file ordering: this issue also waits for #1893 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. `POST /api/mail/drafts/:id/attachments` with `{ fileItemId }` and `DELETE /api/mail/drafts/:id/attachments/:fileItemId` (justification `transactional-semantics`, registered in the manifest and route matrix). Only a draft with a `mail_drafts` row that is not sent can be changed (409 `mail_draft_not_editable`, `mail_draft_already_sent`).
2. Attaching writes the `Emails.attachments` edge through the module's writer (`EMAILS_RELATION_CONTEXT`). When the file item already has an attachment edge to another email, create a new Files item over the same blob and attach that one.
3. Reject an attachment that would bring the draft's total size over the provider limit above with 413 `mail_attachment_too_large` (add the code). Detaching removes the edge.
4. When a draft is discarded, soft-delete the Files items that were uploaded to it and are attached nowhere else. Files created by copying are removed the same way. The draft DTO's `attachments` list is filled.
5. Each change publishes the mail-thread invalidation used by the draft routes.

## Scope

### In scope

- Adding and removing attachments on a draft, the size limits, blob-sharing copies and cleanup on discard.

### Out of scope

- Prefilling attachments for a forward (#1899).
- Building the outgoing MIME (#1491).
- Uploading files (the existing files route).

## Acceptance criteria

- When a file is attached, then the draft's DTO lists it and the file is attached to that draft only.
- When a file already attached to another email is attached to the draft, then the other email keeps its attachment and the draft gets its own Files item.
- When the total size would exceed the provider limit, then the answer is 413 `mail_attachment_too_large` and nothing is attached.
- When a draft is discarded, then files uploaded only for it are soft-deleted and files of other emails are untouched.
- A file of another tenant cannot be attached.
