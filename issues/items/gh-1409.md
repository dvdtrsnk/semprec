## Context

Model tier rationale: One new built-in view type whose config validation must also be wired for built-in types, which have no registry definition today, across the view-type registry, the views store and the catalogs, covered by existing view fixtures.

The app shows a gallery layout for photo-led collections: Files (3 columns, 3:4 tiles with a type badge) and Recipes (2 columns, 4:3, photo; the default view of that collection). The backend has no such view type. `BUILTIN_VIEW_TYPES` in `backend/packages/data/src/chokePoint/viewTypeRegistry.ts` is `table`, `board`, `calendar` and `list`; module-registered types such as `library-grid` get a `configSchema` through `registerViewType`, but a built-in type is "always known without registration", so `validateViewTypeConfig` in `backend/packages/data/src/chokePoint/viewsStore.ts` (which looks up `viewTypeRegistry.get(type)`) finds no definition for a built-in type and validates nothing beyond the common fields from `views/viewConfig.ts`. The views module manifest (`views/viewsModuleManifest.ts`) spreads `BUILTIN_VIEW_TYPES` into its `viewTypes`, and the catalog coverage test (`__tests__/systemI18nCatalogCoverage.test.ts`) requires a `viewType.<key>.name` label in both locales for every built-in type.

This issue adds `gallery` as a built-in view type with a validated config. The Recipes module (#1707) uses it as the default view type of its database.

Decision: `columns` and `aspect` are required in a gallery view's config, `coverKey` (the property key whose image is the tile photo) is optional because Files has no cover property. The existence of `coverKey` as a property is not validated, the same as `library-grid` does not validate its keys.

## Task

Load `canonical-keys` and `testing`.

1. Add `"gallery"` to `BUILTIN_VIEW_TYPES` in `viewTypeRegistry.ts`.
2. Add `backend/packages/data/src/views/galleryViewConfig.ts` exporting `galleryViewConfigSchema`: `columns` is `2` or `3`, `aspect` is `"3:4"` or `"4:3"`, `coverKey` is an optional non-empty string. The schema is not strict, so the common view-config fields (`filter`, `sort`, `groupBy`, `visibility` and the rest) remain allowed.
3. Give built-in types a definition source: add `BUILTIN_VIEW_TYPE_DEFINITIONS` (currently only `gallery`, with the schema from step 2 and `clientComponent: "galleryGrid"`) and a `getViewTypeDefinition(registry, type)` in `viewTypeRegistry.ts` that returns the registry entry or else the built-in definition. Use it in `validateViewTypeConfig` in `viewsStore.ts`, which already runs on both create and patch, so an invalid gallery config fails with the existing `ValidationError` on either path. `registerViewType` still refuses to re-register a built-in type.
4. Add `viewType.gallery.name` to `views/i18n/cs.json` ("Galerie") and `views/i18n/en.json` ("Gallery").
5. Tests in `backend/packages/data/src/__tests__/views.test.ts`: accept both valid configurations above; reject missing columns/aspect on create and invalid resulting config on create or patch. PATCH retains omitted members by the existing shallow merge; prove omission succeeds when the stored required members remain valid and explicit invalid columns/aspect is refused. Keep ownerModuleId refusal, REST 400 config-field coverage in viewsHandler.test.ts and localized schema listing in schemaHandler.test.ts.

## Acceptance criteria

- Creating a view of type `gallery` with `columns: 3` and `aspect: "3:4"` succeeds; with `columns: 2`, `aspect: "4:3"` and a `coverKey` it succeeds.
- Creating a gallery view without columns/aspect, or creating/patching an invalid resulting config, is rejected (HTTP 400, field config). PATCH validates stored config shallow-merged with the patch: valid omitted members are retained; explicit invalid columns/aspect is rejected.
- `GET /api/schema` lists `gallery` as a view type named "Galerie" for a Czech user and "Gallery" otherwise.
- The existing built-in types (`table`, `board`, `calendar`, `list`) validate exactly as before.
