## Behavior specification

Value links, link rules, derived values and approval for broken links.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions for job links-1 (value links, link rules, derived values)

#### (a) Decisions adopted from open questions

- Should a file with several projects get a project link from a task at all? -> Adopted: a link is only created when the target property is empty and has no link row; an existing own value is kept and gets no link. -> Decided by the product owner: a link is created only into an empty property without a link; an own value is never overwritten, as the three kinds of values require. Also answers the "target already has its own value when the join edge appears" question. (#1593)
- Cross-cutting: a target whose link was broken is never rewritten, and a later join edge does not recreate the link. -> Keeps the "once ended, it stays ended unless relinked" rule. (link-rules 02, value-links 03)
- Handoff for system writes into user-owned properties -> Adopted: process `valueLinks` may write a user-owned property only while an `on` link row exists; otherwise 403 `owner_violation`. Enforced in value-links 02; the design note asked for it to be recorded in the epic Decisions (no ADR file is added by any issue in this chunk, new_adr=false). -> Matches the single-writer ownership ADR requirement for an explicit handoff.
- When does a write end a link? -> Decided by the product owner: only a real change of the stored value ends a link (same-value patch, existing edge put, absent edge delete, metadata replace do not), so full-form saves do not end links by accident. (#1516)
- Writes from either side of an edge -> Adopted: both sides of the relation definition are checked, so adding a file from the project's side ends the file's link. (value-links 02)
- Existing manual area/company edges on items that have or get a project (delete / keep and ignore on read / remove on first project write) -> Decided by the product owner: old manual edges stay in storage, reads use the derived value, creating new ones is refused, deleting stays allowed; nothing is migrated. (#1595, #1662)
- Events without a project keep their manual company (and manual area). -> Decided by the product owner: without a project there is nothing to derive from, so both stay own values. (#1662)
- Source with several values for a single-valued target -> Decided by the product owner: not inherited, nothing written; the system does not guess which value to pick. (#1593; #1587 relink rejects with 409)
- Removing the last source of a link -> value stays as own, link row deleted. Remaining sources -> union recomputed. (#1593)
- Soft delete of a source -> Decided by the product owner: its source rows and now-empty links are removed, values stay own, restoring the source never relinks (the source-deletion principle); a link with another live source stays. (#1656)
- Derived values opt-in via `include=derived` (not always returned) -> Adopted to avoid cost on list reads; design note said "additive" without naming the switch. (derived-values 01)
- Event company read (derived.company) is placed in derived-values 01 (same mechanism as area), though the design note's point 3 sits in the potreba_ref of issue 02; issue 02 only guards writes.

#### (b) Open questions remaining for the product owner

- Should a manual area/company be stashed and restored when the project is removed from the item?
- Areas have no color or icon property today; derived area returns color/icon null until the product adds them.
- design note point 5 of the derived-values note (filters, sorting and facets by derived area via relation_path_contains/areaFilter, and the search document fan-out) and the point-4 cutover are not covered by any issue in this chunk's list.

#### (c) User-visible behavior of this chunk

Values on an item now know where they came from. A file attached to the task "Send the invoice" shows that project as inherited, with a chain badge naming the task; a file whose projects have companies shows those companies as inherited and keeps them in step when a project's company changes. As soon as a person or Semp changes such a value on purpose (replaces it, adds a second project or an own company, removes it) the item stops following its source and the value is marked as formerly inherited; a person can stop following without changing the value (unlink) or follow the source again (relink). If the source item is deleted, the inheriting items keep their values as their own and restoring the source does not reconnect them. Separately, an item's area (and an event's company) is derived from its project: it cannot be set by hand while the item has a project, it changes everywhere when the project's area changes, and clients are told to refresh the affected items.


### Decisions for job links-2

#### Adopted decisions
- Which writes defer: only agent writes that break an active value link (#1758, on the mechanism of #1713) -> others stay immediate, including a plain `relation.set` replacement -> follows the narrowing of the existing non-destructive-bypass ADR and the product owner's risk-class decision below.
- User writers never defer -> approval protects against silent agent actions only -> matches the design note.
- Replay uses a snapshot hash instead of `ifVersion` -> `ifVersion` would be stale after approval.
- Risk class of a plain `relation.set` edge replacement -> Decided by the product owner: the ordinary non-destructive `write` class, without approval; approval is forced only by the link-break flag, when a link really breaks. `breaksLink` is used only by #1758. (#1521, #1713, #1758)
- Separate GET detail route for approval requests? -> Decided by the product owner: no; the detail view uses the existing single-request read `GET /api/approval-requests/:id` (#1786), and `breaksLinks`/`endsInheritance` are additive on the list and on that read. Another route would be an unnecessary special path. (#1713, #1758)
- Approval text for a file whose project follows a task -> Decided by the product owner: the text describes the real operation, the write of the file's project relation, not a generic "change file project", so the approval is not misleading; the design text is corrected accordingly. (#1758)
- `/mcp` with a human session -> recorded as an agent write without a run (#1415, decided in #1330); it is not deferred, because an approval request belongs to a run, and it still breaks links with `broken_by` agent. (#1713, #1758)

#### Open questions for the product owner
- None; all were decided by the product owner and are recorded above.

#### Delivered behavior
When Semp tries to do something that would silently end a connection between items, for example change the project of a file that follows a task's project, the change is not applied. Replacing the single value of a one-value relation that no connection depends on applies immediately. Instead an approval request appears, naming the real write (for example the file's project relation), the connection that would end and what it stops following. The user approves or rejects it. On approval the change is applied exactly once and the connection is marked as ended by Semp; if anything relevant changed in the meantime (the user removed the connection, the source was deleted), the approval is voided and nothing is written. On rejection nothing changes. Writes by Semp that do not break a connection, and all writes by the user, still apply immediately.
