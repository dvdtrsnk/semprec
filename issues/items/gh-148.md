## Approved behavior specification

This epic preserves the complete approved behavior of source issue #36, inlined here so the epic is self-contained.

### Source behavior: [16/22] Notifications

## Context

The system already generates states that a user finds out about only by manually checking a specific table: an approval request waiting for a decision (issue #32 — approval queue), an agent heartbeat that exhausted its retries and ended in error (issue #21 — the heartbeat `last_error` write site), an item automation that failed, a mailbox sync that broke. An earlier round of decisions deliberately left this without notifications, reasoning that the server had no public domain with TLS, so web push wasn't viable — that reasoning no longer holds, because the server has since gotten its own domain with TLS (Caddy). This task builds the notification mechanism that actively delivers these states (from the issues above, and from a few other, previously built write sites) to the user, instead of making them go look.

## Task

Build a notification layer on top of existing write sites:

1. **`notifications` table** — generic, one row per notifiable event:
   - `id`, `user_id` (FK `users`), `kind` (text — see enumeration below), `title` (ready-made text, not a template rendered at read time), `link_href` (where a click goes — approval queue, a specific item, a mailbox), `source_table`, `source_id`, `created_at`, `read_at` (nullable).
   - Index on `(user_id) WHERE read_at IS NULL` for fast retrieval of unread rows.
   - The row is written in the **same transaction** as the row that caused the notification — no new polling mechanism, no extra watcher.

2. **`push_subscriptions` table** — one table for both web push and APNs (not two parallel ones):
   - `id`, `user_id`, `session_id` (nullable FK `sessions`), `channel` (`web_push` | `apns`), `platform` (`web`|`ios`|`macos`), `endpoint`/`p256dh`/`auth_secret` (web push), `device_token`/`apns_environment` (APNs), `created_at`, `last_used_at`, `revoked_at`.
   - Unique index on `endpoint` where `channel='web_push' AND revoked_at IS NULL`; unique index on `device_token` where `channel='apns' AND revoked_at IS NULL`.
   - `revoked_at` gets set when the provider reports invalidity (APNs 410/`BadDeviceToken`, web push endpoint 404/410) — the same discipline as the `gmail_history_id`/`graph_subscription_id` invalidation elsewhere in the system.
   - The choke-point that revokes `sessions` (manual logout as well as remote revocation of a compromised device) must, in the same transaction, also set `revoked_at` on every `push_subscriptions` row sharing that `session_id` — otherwise a logged-out device would keep receiving push.

3. **Three delivery channels, all leading to the same place (`link_href`):**
   - **In-app over the existing WS channel** (`semprec-api`, HTTP+WS) — a notification is just another message type on the same channel, not a new transport. Broadcast to all active sessions of the given `user_id` at once (multi-device is automatic — no cap on sessions per user), so reading it on one device clears the badge on the others too. On connect, the client also does a one-time fetch of unread rows (`WHERE read_at IS NULL`) — the WS only supplements live delivery, it is not the sole path to state.
   - **Web Push** — a VAPID key pair, a service worker, `Notification.requestPermission()` as an explicit opt-in. The VAPID key is a bootstrap secret in the root-owned `shared/.env` (same category as the AI Gateway keys).
   - **APNs** (iOS/macOS app) — token-based auth via a `.p8` key (Team ID + Key ID), the same bootstrap-secret pattern. The request is a JWT (ES256), valid for at most 1 hour per Apple's limit — the fanout worker caches and reuses the JWT rather than generating a new one per notification. The HTTP/2 call goes to `api.push.apple.com` (production) or `api.sandbox.push.apple.com` (dev/TestFlight) depending on that token's `push_subscriptions.apns_environment`. Payload: alert (title/body) plus `link_href`/`notification_id` in a custom `userInfo` for deep-linking on tap.

4. **Fanout worker** — one `graphile-worker` job per `notifications` row. The job pulls every active (`revoked_at IS NULL`) `push_subscriptions` row for that `user_id` and sends its own call for each (web push and APNs go through the same path, just a different adapter) — `jobKey` dedup, the same pattern used elsewhere in the project, so a duplicate attempt to send the same notification to the same registration doesn't get sent twice.

5. **Read state** — clicking a notification navigates to `link_href` and, in the same request, sets `read_at`. A manual "mark all as read" in the UI is reasonable to have as a convenience, but it is not a mechanism anything else relies on — the source of truth is always the thing the notification links to (a row in `approval_requests`, `agent_runs`, etc.), never the notification itself.

## Scope

### In scope

- Migration: the `notifications` and `push_subscriptions` tables, including the indexes described above.
- Writing to `notifications` in the same transaction, from existing write sites, at minimum:
  - creation of an `approval_requests` row (issue #32 — approval queue) → `kind = 'approval_pending'`.
  - `agent_runs.status = 'error'` — both the startup sweep and at runtime, including gateway budget rejection and unrecoverable run errors (issue #30 — agent lifecycle + budget cap) → `kind = 'agent_run_error'`.
  - `project_heartbeats.last_error` after a heartbeat run exhausts its retries (issue #21) → `kind = 'heartbeat_error'`.
  - `item_automation.status = 'error'` → `kind = 'automation_error'`.
  - `mail_account_sync_state.last_error` → `kind = 'mail_sync_error'`.
  - Reserve (but do not implement beyond the above) `kind` values for `process_stale` / `queue_backlog` / `mail_sync_stalled` (`source_table = 'observability_checks'`) and for `backup_restore_failed` — those write sites belong to other, earlier- or later-built parts of the system and are not the subject of this issue; the enum merely accounts for their future existence.
- CRUD endpoints for `push_subscriptions`: registration on opt-in (web `PushManager.subscribe()`, app `registerForRemoteNotifications`), and revocation on device logout tied to `sessions` revocation.
- Extending the `semprec-api` WS protocol with a message type for notifications (broadcast to all of a user's active sessions) and with an initial "fetch unread" step on connect — implemented as a minimal WS fan-out if the full `WS /api/sync` protocol (issue #38) doesn't exist yet; #38 later absorbs it.
- Fanout worker (`graphile-worker` job per `notifications` row) with adapters for web push and APNs, JWT caching for APNs, `jobKey` dedup.
- An endpoint/mechanism for "read = visited `link_href`," and optionally a manual "mark all as read."

### Out of scope

- Generic REST endpoints over the choke-point for reading/managing notifications (list, detail) — that is issue #37 (generic endpoints over the choke-point).
- Email escalation for unread notifications — explicitly rejected (see Reference), no `emailed_at` column, no heartbeat sweeping this table.
- Actually implementing the observability checks (`process_stale`/`queue_backlog`/`mail_sync_stalled`) and the monthly backup-restore test (`backup_restore_failed`) — this task only reserves the `kind` values for their future writes, it does not build them.
- UI components (badge, notification panel) on top of this mechanism, except where needed to verify delivery.

## Dependencies

- Builds on #32, #33, #34.
- **Issue #32 (approval queue):** the creation of an `approval_requests` row is one of the write sites that, in the same transaction, writes a `notifications` row with `kind = 'approval_pending'` and a `link_href` pointing at the approval queue / the specific request. Without the approval queue from #32, this `kind` would have no source.
- **Issues #30 and #21 (the error write sites):** two states trigger a notification — the `agent_runs.status = 'error'` transition (startup sweep and at runtime, including gateway budget rejection and unrecoverable run errors — write sites from issue #30, agent lifecycle + budget cap) → `kind = 'agent_run_error'`, and the `project_heartbeats.last_error` write after a heartbeat run exhausts its retries (issue #21) → `kind = 'heartbeat_error'`. Without those write sites, these two kinds would have no source.
- **Issue #34 (auth):** determines who a notification may even be sent to — `notifications.user_id` and the broadcast to a user's active `sessions` rely on the authentication/session model from #34 (who is logged in, which devices/sessions belong to them).
- Uses the `semprec-api` WS channel (HTTP+WS, realtime push) as the transport for in-app delivery. The full multiplexed `WS /api/sync` protocol is only formalized later, by issue #38 — so if it doesn't exist yet when this issue lands, this issue implements a minimal WS notification fan-out of its own (the notification message type broadcast to a user's active sessions, plus the one-time unread fetch on connect), which issue #38 later absorbs into the full protocol — the same pattern issue #23 used for delivering its Yjs updates ahead of the formal WS layer.
- Assumes a public domain with TLS (Caddy) for the server — without it, web push does not work (the Push API requires a publicly reachable HTTPS endpoint).

## Reference to the specification

`vize/backend.html`, lines 5034-5236.

**Delivery channels (three, not one):**
1. *In-app* over the existing `semprec-api` WS channel — a notification is just another message type on an already-existing channel, not a new transport. Broadcast to all of a user's active sessions at once; on connect, the client does a one-time fetch of unread rows (`WHERE read_at IS NULL`) — the WS only supplements live delivery, it is not the sole path to state.
2. *Web Push* — VAPID key pair + service worker; previously rejected for lack of a public domain with TLS, viable today because that domain now exists. The VAPID key is a bootstrap secret in `shared/.env`.
3. *APNs* (iOS/macOS app) — token-based `.p8` auth (Team ID + Key ID), one key for both apps, differing only in the `apns-topic` header. JWT (ES256) valid for at most 1h, cached and reused by the fanout worker. Endpoint chosen by `apns_environment` (`sandbox`/`production`).

**Handling multiple pending requests/heartbeats at once:**
- The notification mechanism does no batching or coalescing at write time: every individual event (every new `approval_requests` row, every transition to `error`) writes its own row into `notifications` in the same transaction as the source event — N pending requests means N rows.
- Fanout is likewise one at a time: one `graphile-worker` job per `notifications` row, so N unread notifications means N fanout jobs, not one bulk job. A duplicate send of the same pair (notification × registration) is handled by `jobKey` dedup, not by collapsing multiple notifications into one.
- On the read side, only the unread index (`WHERE read_at IS NULL`) aggregates, and the badge counts/shows the number of unread — the client fetches the whole unread set in one bulk read on connect, but that's a bulk read, not bulk writing/sending.
- The APNs fanout worker caches and reuses its JWT (valid for at most 1h) across calls so it doesn't generate a new JWT per notification as volume grows.

**Explicitly rejected:** email escalation of an unread notification after N minutes via the SMTP infrastructure — rejected permanently, not deferred, because the three chosen channels (in-app, web push, APNs) already cover all of a user's devices. `notifications` therefore has no `emailed_at` column and no heartbeat that sweeps the table to escalate.

## Decisions

- Persistence? Finished title/link rows, because notification rendering must not depend on later source state.
- Delivery? One fanout path with web/APNs adapters, avoiding parallel systems.
- Reliability? Durable unread rows plus best-effort live delivery; WebSocket is not the source of truth.

## Out of scope

- Email escalation, generic notification CRUD, full notification-panel UI, and implementation of observability/backup checks.
