## Context

Model tier rationale: Scopes where a CalDAV session may send the account's Basic credential across redirects and server-named addresses, with an explicit iCloud delegation, and changes how an edit treats a resource ical.js cannot read.

Review findings on the internet-accounts branch, verified in the code:

- **The CalDAV login goes to any host.** `calendar/sync/adapters/caldav/caldavHttp.ts` sets `Authorization` on every hop of the session fetch, including a redirect to another origin, and `caldavClient.ts` resolves every href a server names (`current-user-principal`, `calendar-home-set`, collections, resources) with `new URL(href, base)` and requests it with the login, wherever it points. A server can take the account's password to any host the outbound policy allows.
- **An edit of a resource with a value ical.js cannot read fails as `unexpected`.** `caldavAdapter.ts` `edited()` maps only `CalendarResourceUnreadableError`; ical.js parses a value on first access and throws a plain `Error` (for example `DTEND;TZID=Europe/Prague:garbage`), which escapes `updateResource`, `setAttendeeParticipation` and `removeOccurrence` halfway through `writeFields`/`readFields`.

Decisions:

- **Credential scope.** A session is opened with the URL discovery starts at (iCloud's root, the account's `caldav_url`, or `https://<domain>/.well-known/caldav`). The credential may go to that URL's origin and, only when the start is `https://caldav.icloud.com`, to https hosts `icloud.com` / `*.icloud.com` on the default port without userinfo (Apple's discovery names the account's `pNN-caldav.icloud.com`). Every request and every redirect hop outside the scope is refused before it is sent (`invalidResponse`). A server-named address outside the scope is refused as `invalidResponse`, except a calendar in the home's listing, which is left out (it cannot be read with this login).
- A redirect off the scope is refused rather than followed without the credential: the foreign server's 401 would otherwise read as a refused login (`needsReauthorization`, `caldav_auth_failed`) although the password is right. A domain whose well-known address delegates to another host is set up with its CalDAV address instead.
- **An edit reads the resource whole first.** The edit functions read every value of the resource (every property of every component) before changing anything; an ical.js failure there is `CalendarResourceUnreadableError` (with the cause), which the adapter answers as `invalidResponse` as today. A failure while writing the new fields stays the edit's own.

## Task

Load `io-hardening`, `error-handling`, `testing`.

1. `caldavHttp.ts`: `caldavCredentialScope(start)`; `withCalDavSession` takes `start`; the session fetch refuses a request or redirect outside the scope; `CalDavSession.inScope`.
2. `caldavClient.ts`: every server-named address resolved through the scope; a listed calendar outside it is left out.
3. `caldavAdapter.ts`, `caldavConnectVerification.ts`: pass the start to the session.
4. `caldavIcal.ts`: `editableParts` reads the resource whole and maps an ical.js read failure to `CalendarResourceUnreadableError`.
5. `testSupport/fakeCalDavServer.ts`: record whether a request carried `Authorization`; a configurable calendar-home origin.
6. `docs/architecture/domain-calendar-tasks-and-media.md`, `edges-io-and-errors.md`.

## Scope

### In scope

- The CalDAV session's credential scope and the edit path's reading of a resource.

### Out of scope

- The create path of `putEvent` (its href and UID), the push job, any other provider, the outbound address policy itself.

## Acceptance criteria

- A redirect from the account's server to another origin is refused as `invalidResponse` by the sync and as `caldav_server_invalid` by the connect verification, and the other server receives no request.
- A `calendar-home-set` on another origin is refused and never requested.
- Every request to the account's own server (after the well-known redirect) carries the login.
- `caldavCredentialScope` allows the start's origin and, for an iCloud start only, https `*.icloud.com` on the default port; it refuses another port, another host, a look-alike, plain http and an iCloud host from a generic start.
- An update, an invitation answer and an occurrence's cancellation of a resource holding a value ical.js cannot read fail as `invalidResponse` ("The CalDAV resource is unreadable") after one GET, and the resource is unchanged.
- The existing CalDAV adapter tests stay green.
