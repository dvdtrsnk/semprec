## Context

Model tier rationale: One more id-less user-narrowed scope on the established realtime catalog with a small publisher function and no write sites of its own, following the preceding scope issues.

When a user changes the profile language or display name on one device, their other devices must re-read the profile. This issue adds the realtime scope `account`, without payload fields, narrowed to the sockets of the user whose profile changed, following exactly the shape and wiring of the earlier scopes in this chain (#1918 and before): the `invalidation` message type with a `scope` discriminator in `backend/packages/realtime/src/pgNotifyPublisher.ts`, the `OutboundFrame` variant in `backend/packages/realtime/src/protocolV1.ts`, the `InvalidationEvent` variant in `backend/packages/data/src/realtimeHook.ts`, the mapping in `backend/packages/realtime/src/syncServer.ts` and the parser in `backend/packages/realtime-client/src/serverFrame.ts`. Rules of `docs/adr/2026-10-16-tenant-scoped-realtime-fan-out.md` apply: thin payload (no name, no language in the frame), tenant from Postgres, no replay, publish only after commit with `runAfterCommit`.

This issue delivers the frame, the parser on both ends and the publisher function `publishAccountInvalidation(client, userId)`. It does not call it from any route: the profile update route (`PATCH /api/account/profile`, which stores the display name and the language) belongs to the profile issues (#1387 and #1704) and calls the publisher added here after its own write. The next and last scope in the chain is #1951.

## Task

Load `state-writes`, `canonical-keys`, `io-hardening` and `testing`.

1. Add the `account` variant to `InvalidationEvent` (with `userId`), `RealtimeMessage` (+ `parseRealtimeMessage`), `OutboundFrame` (`{ type: "invalidate", scope: "account" }`), the `invalidation` case of `syncServer.ts` (call `sendToTenant(tenantId, frame, parsed.userId)`), and `parseServerFrame`; export the frame type from the client package barrel as the other scopes are.
2. Create `backend/packages/data/src/auth/accountInvalidation.ts` exporting `publishAccountInvalidation(client, userId)` that defers `notifyInvalidation({ scope: "account", userId })` with `runAfterCommit`, and export it from `backend/packages/data/src/index.ts`.
3. Tests: round trip on listener, server and client; a second socket of the same user and tenant receives the frame; another user of the tenant and another tenant do not; rollback sends nothing; the frame contains only type and scope.

## Scope

### In scope

- The `account` scope end to end and the `publishAccountInvalidation` function.

### Out of scope

- Calling the publisher from the profile update route: the profile issues (#1387, #1704).
- The overview scope: #1951.
- Carrying profile data in the frame.

## Acceptance criteria

- When `publishAccountInvalidation` is called for a user inside a committed transaction, then all sockets of that user in that tenant receive `invalidate` with scope `account` and no other field.
- When the transaction rolls back, then no frame is sent.
- When another user of the same tenant or a socket of another tenant is connected, then it does not receive the frame.
- A malformed account message is dropped by the listener and by the client parser.
