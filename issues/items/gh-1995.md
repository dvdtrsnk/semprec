## Context

Model tier rationale: One fallback rule added to the existing per-database schema projection, reusing the sort shape of a blocker, with existing schema handler fixtures; no new lifecycle, tenant or persisted-data contract.

Every collection screen opens with a default order. The product owner decided one general rule in the schema instead of waiting for a decision per collection: Events and Tasks sort by date ascending, and every other collection, including collections the user created, sorts by creation time descending (newest first).

#1647 adds `defaultSort` to the per-database part of `GET /api/schema` (`SchemaDatabaseProjection` in `backend/packages/data/src/manifest/schemaProjection.ts`) and declares `date` ascending for Events and Tasks in the module manifests; every other database has no declared `defaultSort`, and user-created databases never have declarations. #1594 adds the general `items.created_at` column and the system variant of the sort spec, `{ system: "createdAt" | "updatedAt", direction }`, which database and view queries accept. This issue makes the schema return the creation-time default for every database that declares none, so a client always finds a default sort and never hard-codes one.

Decision: the fallback is computed in the projection and never written into manifests or view configs; a declared `defaultSort` always wins. Decision: the fallback applies to every database the projection returns, system or user-created.
