## Context

Model tier rationale: Touches the shared mail thread CTE every mail list and count reads, restructures the IMAP sync pass from one transaction into a network phase and short write transactions while keeping its idempotency, ordering and guards, and changes how item-event heartbeats and two job producers fan out during mail sync.

Measured on the dev VPS (2-vCPU class, Postgres 16 in Docker, one user, ~33k items including ~15k Emails / 14k threads, one iCloud account with 6 calendars / 1700 Events, initial mail sync running): `GET /api/overview` 1.4 s, `GET /api/account/summary` 1.1 s (five pool connections per request), `GET /api/calendar/timeline` for one week 0.67 s, `GET /api/mail/mailboxes` 0.18 s. In 15 minutes the queue ran 428 `heartbeatFireCore`, 254 `itemSearchReindexDependents`, 206 `valueLinksPropagate` and 90 `mailTriageThreadProject` jobs. The `semprec-api` pool has 10 connections shared by HTTP, graphile-worker (concurrency 4), the LISTEN clients and the mail sync.

Reproduced locally (embedded Postgres 18, a tenant seeded through the production writers: 15 000 Emails in 14 000 threads over five folders, 1 704 Events in 6 account calendars, 600 Tasks, 199 Journal days):

- Overview 171 ms, account summary 152 ms, both dominated by the mail summary statement (145 ms). `EXPLAIN ANALYZE`: the thread copy CTE runs a per-Email lateral folder lookup 15 000 times, re-evaluating the inlined `folder_definition` CTE (an index scan of `properties` and a seq scan of `relation_definitions`) in every loop. The account summary needs only the mailbox counts of that statement and runs it anyway; it opens five transactions at once through `Promise.all` (sessions, mail, trash, Semp status, AI usage). The Overview reads in three transactions in sequence; the Semp status report re-reads its i18n catalogs from disk on every call. No missing index explains any of it: every statement except the mail summary is under 6 ms.
- `heartbeatFireCore`: not a sweep. Every new Email fires three `onItemEvent` `create` heartbeats with deterministic actions (`mail.linkPeopleByEmail`, `calendar.ingestInvitation`, `calendar.applyInvitationReply`), one job per Email each, plus the `newEmail` agent heartbeat. The initial sync ingests ~10 Emails a minute, so ~28 core fires a minute; the two invitation actions find nothing to do for an Email without a calendar part.
- `itemSearchReindexDependents`: the relation edge hook queues an `item` reindex for both ends of every edge, so every Email's folder edge queues a job for the Email, which `indexItem` skips (mail owns Email search rows). One no-op job per Email.
- `valueLinksPropagate`: two per new thread (the first inbound message queues `threadCompanyFromSender` and `threadProjectFromCompany`), not per Email. The project rule resolves from the thread's company; a new thread has neither a company nor a project link yet, so that job writes nothing, and the company rule's edge write queues it anyway when it links a company.
- `mailTriageThreadProject`: one per new thread, the triage itself; left as it is.
- The IMAP pass opens one transaction, takes the mailbox sync guard and the tenant's mail-thread advisory lock, and then talks to the provider inside it: listing folders, selecting, fetching up to ten messages with their bodies, downloading attachments lazily while ingesting, fetching flags and vanished UIDs, and writing flags back.

Decisions:

- Account summary: one REPEATABLE READ transaction on one connection for every figure (the two trash totals keep their shared snapshot); the mail figures come from a mailbox-only statement that shares the summary's mailbox CTE.
- Overview: one transaction for every figure; its unread count reads the thread CTE only over threads that have a copy not read (exact: every unread thread has one, and a kept thread keeps all its copies).
- The thread copy CTE aggregates folder edges once per Email and hash-joins them, restricted to the thread in detail mode and to the candidate threads in unread mode; same results for every caller.
- The Semp status report reads its catalogs once per process (not cached on failure) and runs in the caller's transaction.
- The three deterministic Email-create actions get one fire job per heartbeat and transaction carrying every item id; a batched fire runs the handler per item. Agent actions and every other action keep one job per item.
- The edge hook queues no `item` reindex for an Email end; the first inbound message queues the thread project rule only when the thread has a live company or a project link.
- The IMAP pass does the provider work with no transaction open and writes in short transactions: a prepare transaction, one per folder batch (at most `IMAP_NEW_MESSAGES_PER_PASS`), and a final one; each takes the mailbox sync guard and re-checks the mailbox, then the mail-thread lock. A batch writes only while its folder state still matches the state its fetch started from, so a concurrent pass never regresses a cursor. Attachments are spooled to temp files before the write.
- No index is added and no pool size changes: no statement is slow for lack of one.

## Scope

### In scope

- The read-path, connection-count, IMAP pass and job fan-out changes above, their tests and the architecture documents.

### Out of scope

- The Gmail and Graph passes, which still call their provider inside their transaction.
- Pool sizing, worker concurrency and the LISTEN clients.
- A denormalized per-thread unread count, and any index.
- `mailTriageThreadProject` and the `newEmail` agent heartbeat (one per thread / per Email by design).
- Running anything against the dev VPS or production.

## Acceptance criteria

- `GET /api/account/summary` checks out one pool connection per request and answers the same figures as before.
- `GET /api/overview` checks out one pool connection per request and answers the same figures as before, its unread count equal to the mail summary's.
- On the local dataset the overview and the account summary are at least twice as fast as before (measured numbers in the handover).
- During an IMAP pass no transaction is open and no advisory lock is held while the provider is fetching messages or attachments; the messages are still ingested once, in UID order, and a pass overtaken by another writes nothing for that folder and does not regress its cursor.
- Ingesting a batch of N new Emails in one transaction queues one fire job per deterministic Email-create heartbeat (carrying the N item ids), N agent fire jobs, no `item` reindex job for an Email, and no thread project rule job for a thread without company or project link; a batched fire runs the handler for every item and fails, after running all of them, when one fails.
- The existing mail, calendar, overview, account, search, heartbeat, value link, observability and tenancy test files stay green.
