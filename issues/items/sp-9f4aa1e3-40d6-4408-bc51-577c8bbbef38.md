### Requirement gh-1885: [semp-replies 03/08] Record the items each Semp reply changed

#### Context

Model tier rationale: One known mechanism (deriving a typed list from tool event pairs at turn end and storing it on the message) over existing store and event fixtures, with a redaction rule for sensitive databases but no new authorization contract.

Under a Semp reply the chat shows cards for the objects the reply touched, each with a state such as "tomorrow 9:00 - moved" or "today 16:30 - new". Today nothing records which items a reply changed: the agent run events hold the arguments and results of every tool call (`tool_use` and `tool_result` in `agent_run_events`, written by `backend/services/semprec-agents/src/piAgentSession.ts`), but they are only readable over realtime and are deleted by retention after 30 days. Items have no author or history, so the set of items a reply changed cannot be reconstructed later.

This issue stores that set with the assistant message at the end of the turn, in the same place and transaction as the step summary of #1860. It relies on the structured tool results of #1527 (`details.changes` with `{ key, before, after }`, where `before` comes from the previous values returned by `item.patch`, see #1429's output through #1527). #1888 resolves the stored list into cards at read time, and #1930 uses it to refuse regenerating a turn that wrote anything.

Decision: a delete that is waiting for approval is not a change. It is only a step in `waiting` state (#1860); a change is recorded only for a tool result that actually executed. When the approved delete is executed later, outside the turn, no change is added to the reply.

Decision: `before` is omitted for items in a database marked as sensitive, in the same way as the step summary (#1827); the stored list lives permanently on the message, outside event retention.

#### Task

Load `state-writes`, `canonical-keys`, `db-migrations` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_semp_messages_changes.sql` (next free ordinal at commit time): add `changes jsonb` (nullable) to `semp_messages`.
2. Add `backend/packages/data/src/semp/sempReplyChanges.ts` with a pure function from the events of one turn (`agent_run_id` = the message's run AND `id BETWEEN event_from_id AND event_to_id`, matched by `toolCallId`) to the stored array of `{ itemId, databaseId, change, changedKeys, before?, proposalId? }`. `change` is one of `created`, `updated`, `deleted`, `restored`, `revised`. The mapping is a table keyed by tool name:
   - `item.create` -> `created` (the item id and database id from the result; `changedKeys` are the keys that were set);
   - `item.patch` -> `updated`, `changedKeys` and `before` from `details.changes`;
   - `item.delete` -> `deleted` and `item.restore` -> `restored` (only when the result is not an approval-pending result);
   - `relation.put` and `relation.delete` -> `updated` on the calling item, with the key of the relation property in `changedKeys`;
   - `inbox.proposal.revise` -> `revised`, with `proposalId` from its result.
   Calls that failed (`isError`) or are pending approval produce no entry. If one item is changed several times in a turn the entries are merged: `changedKeys` is the union and `before` keeps the value from the first change of each key.
3. Extend the end-of-turn writer from #1860 (`sempMessagesStore.ts`) so the same transaction also stores `changes` (an empty array when nothing changed).
4. Tests: a moved task has the previous due date in `before`; a created task has `created` and no `before`; a delete awaiting approval yields no entry; two patches of one item merge; a failed call yields no entry; an item in a sensitive database has no `before`.

### Requirement gh-1907: [semp-replies 05/08] Classify Semp reply failures with the shared run error codes

#### Context

Model tier rationale: One known mechanism (mapping known failure causes to a closed code set on a stored message and a read-time user text) across the turn handler, a migration and the history endpoint, with no new authorization or concurrency contract; the main risk is leaking raw exception text, which the tests pin.

When a Semp reply fails, the chat has to say why in plain words ("The calendar connection timed out, so I could not load the meeting record.") and show which step failed. Today a failed turn is closed through `failRun` in `backend/packages/agent-runtime/src/sempConversation.ts`, which stores the raw `err.message` in `agent_runs.result` and raises an `agent_run_error` notification (`finishAgentRunWithErrorNotification` in `backend/packages/data/src/agentRuns/agentRunsStore.ts`). A model failure is a final assistant message with `stopReason: error` turned into a thrown error by `assertModelSucceeded` (`backend/services/semprec-agents/src/piAgentSession.ts`). An exhausted budget is a 403 `budget_exceeded` of the AI gateway (`backend/services/semprec-ai-gateway/src/piMessagesHandler.ts`) that surfaces to the agent as a model error with text. A failing MCP tool does not fail the turn at all: `executeMcpInvocation` (`backend/packages/data/src/mcp/mcpToolExecution.ts`) returns `{ error: true, result }` as ordinary model input.

This issue gives an assistant message two kinds of failure information:

- A reply that the agent finished, but where a tool call failed and was never succeeded by a later successful call of the same tool, is "incomplete". Whether a reply is incomplete is derived when the history is read, by the shared function of #1890; the history returns `incompleteReason` (`toolTimeout`, `toolUnavailable`, `toolError` or `null`). The text shown on the card is the agent's own answer.
- A reply whose turn threw is `error`, with `error_code` and `error_params` stored on the message. `error_code` uses the single closed set of #1446 (`budgetExceeded`, `modelError`, `cancelled`, `interrupted`, `internal`), shared between runs and messages.

It builds on the queued turn handler (#1727), the step summary stored on the message (#1860, whose failed step this issue references), the MCP failure kinds (#1444), the typed budget refusal (#1547) and the tick thread run model (#1557). #1931 and #1926 build on the stored code.

Decision: no raw exception text is stored or logged for a message failure. `error_params` hold only `{ connectorName?, failedStep?: { key, params }, timeoutMs? }`, never user content. The user-facing text is rendered from the code and params at read time from an i18n catalog, in the locale of the user.

Decision: `budgetExceeded` is recognized from the typed budget error of #1547, never by parsing the error text.

Decision: `interrupted` (a restart in the middle of a turn) is written by the recovery of #1732; this issue only makes sure that the code is part of the set and is rendered.

### Requirement gh-2019: [semp-voice 09/09] Cancel a running voice turn on an explicit stop command

#### Context

Model tier rationale: The voice session runs in `semprec-api` while the turn runs in `semprec-agents`, so this adds a new cross-process cancellation signal for one turn, with abort ownership and cleanup of a partly executed turn; at this uncertainty the higher tier is chosen.

In voice mode (#1734) speech from the user while Semp speaks only stops the audio; the agent turn keeps running and the next transcript waits in the thread's queue. The product decided that voice may cancel a running turn, but only when the user says so explicitly ("Stop", "Zruš"), and then as an ordinary cancellation of the turn.

Today a running agent turn can only be aborted for a whole tenant: `withInFlightRegistration` in `backend/services/semprec-agents/src/agentRunTasks.ts` registers an `AbortController` per job under its tenant in `InFlightAgentRuns` (`backend/services/semprec-agents/src/inFlightAgentRuns.ts`), and `serve.ts` aborts all controllers of a deactivated tenant from a Postgres notification listener (`startTenantDeactivationListener`). An aborted turn throws `AgentRunCancelledError`, which closes the run with the error code `cancelled` (#1446) and the reply with status `error` and `error_code` `cancelled` (#1907); dangling tool calls of the turn are paired immediately (#1568). A cancelled turn raises no Semp problem (#1931).

Decision: the stop command is recognized only on a final transcript that, after trimming, lower-casing and removing trailing punctuation, equals exactly one entry of a closed list `VOICE_STOP_COMMANDS = ["stop", "zruš"]`. Such a transcript is never stored as a thread message. Any other transcript, including a longer sentence that contains one of these words, is handled as before.

Decision: cancelling a turn never decides an approval request. A request the turn already created stays pending, and its write is executed only after the person approves it, as for any other request.

In `semprec-agents`, extend `InFlightAgentRuns` with `registerTurn(tenantId, assistantMessageId, controller)` and `abortTurn(tenantId, assistantMessageId): boolean`; the queued turn handler of #1727 (`backend/services/semprec-agents/src/sempMessageTask.ts`) registers the controller of its job under the assistant message it answers, and unregisters on every path. In the voice session handler of #1734 (`backend/services/semprec-api/src/voiceSessionHandler.ts`), add a pure `isVoiceStopCommand(transcript)` in a new `backend/services/semprec-api/src/voiceStopCommand.ts`. On a final transcript that is a stop command: do not create a message; stop speech output (abort the synthesis request, drop queued sentences, send `speaking` end); if the session's thread has an assistant message whose turn is running, call `requestSempTurnCancel` for it in the session's tenant. With no running turn, the command does nothing else.

### Requirement gh-1915: [semp-status 09/12] Resolve problems when their source recovers

#### Context

Model tier rationale: One mechanism (calling the existing resolve operation at the places where a source recovers) at five call sites, each in the same transaction as its source write; the care needed is in not closing a tick problem on a run that is only technically successful.

Problems raised for failed sources (#1911, #1465) must close when the source recovers, in the same transaction as the write that proves recovery, so the status view never shows a problem for something that already works, and a rolled-back recovery never closes one. The store (#1459) has `resolveProblem(dedupeKey, resolutionKind)`; nothing calls it yet. Recovery signals exist today:

- A tick that succeeds: `recordHeartbeatSuccess` (`backend/packages/data/src/scheduler/schedulerStore.ts`, called from `scheduler/sweep.ts`) clears `last_error`, but it is also called for a run that ended `done` with an incomplete answer, so it is not proof of recovery.
- Guidance drift: findings are resolved through the findings store (`agent_guidance_drift_findings.resolved_at`) by `backend/packages/application/src/projectAgentGuidance/driftAction.ts`.
- The restore test: `recordRestoreTestResult` (`backend/packages/data/src/observability/restoreTestResult.ts`) switches `backup:restoreTest` to `ok`.
- The stale-process check (`observabilityCheckSystem.ts`) switches `process:<name>` back to `ok`.
- Library automation: a successful job clears the item's automation error.

Mailbox, transcription and chat reply problems are closed by their own producers (#1506, #1945, #1931). The history shown after a problem closes is #1919; closing notifications and pushes belongs to #1463 and the status invalidation to #1868.

It builds on the retry chain of runs (#1448) and on the function that tells whether a reply left a failed tool call (#1890).

Decision: a tick counts as recovered only when its run ended `done` and its reply does not leave a failed tool call according to #1890. The same transaction that closes the run and writes the reply message calls `resolveProblem` for `agents:heartbeat:<heartbeatId>`. A run in a retry chain that succeeds resolves `agents:run:<first run of the chain>`.

Decision: resolutions use `recovered` for every case above; a problem closed because its source was deleted uses `sourceDeleted` (the constant of #1459 gains this value). Deleted-source resolutions are not shown in history (#1919).

Decision: the stale-process and library-automation problems are closed as well (not only the ones the design shows in history), so a problem raised by #1465 is never left open after recovery. A library automation problem closes when a job succeeds and no other item of that database still has an automation error.
