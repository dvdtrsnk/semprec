## Context

Model tier rationale: New shared write operations, ViewModel actions and failure handling, and an Apple editing UI in project settings, on iOS and macOS, with tests on every layer.

Project settings can choose tags and create one (#2111). The backend can rename and recolor an option (`PATCH /api/properties/:id/options/:key`) and, through the blocking record, delete one (`DELETE /api/properties/:id/options/:key`). The app has no way to manage existing tags.

## Task

1. Shared: repository writes and use cases to rename, recolor and delete a property option, with typed failures. The ViewModel actions refresh the schema and the item afterwards.
2. Apple: a tag management view reached from the Tags section of `ProjectSettingsSheet`. It renames a tag, picks its color from the existing palette, and deletes it after a confirmation that says it is removed from every project.
3. Copy keys in en and cs, accessibility identifiers, and the architecture policy.

## Touches

- mobile/shared (domain, data, presentation) and commonTest
- mobile/apple/Modules/Core/CoreKit and mobile/apple/Modules/Features/Collections (ProjectSettingsSheet, a tag management view, identifiers, Localizable.xcstrings) and tests
- mobile/scripts/architecture-policy.json

## Scope

### In scope

- Renaming, recoloring and deleting a tag from project settings.

### Out of scope

- Android, and tag management for databases other than Projects.

## Acceptance criteria

- Renaming or recoloring calls PATCH and the project shows the new label or color. A refusal shows a failure and changes nothing.
- Deleting asks for confirmation, then calls DELETE. Afterwards the tag is gone from the project and from the tag bar.
- `mobile/scripts/verify architecture shared` passes and the Apple tests pass on an iOS simulator.
