## Context

Model tier rationale: It exposes writes that send email and change tasks and events to an AI agent and to MCP clients behind a capability and an approval requirement, so the approval and grant wiring is a safety-relevant contract.

The calendar module has operations that Semp and external MCP clients should be able to perform, with the same validation as the app: answering an invitation (#1944) and placing a task into an event or taking it out (#1764). An agent completes a task through the generic item write (`item.patch` with `status: "done"`), and the Tasks update hook of #1781 records the completion in the event (decided by the product owner: every completion before the end of an event counts as a completion in the event, wherever the task is ticked), so there is no separate complete-in-event tool. Module agent tools are composed into Semp sessions by #1523, can be marked as needing approval by #1791, are exposed over `POST /mcp` by #1580, and the rule for granting them is recorded by #1385. The calendar timeline tool is a separate issue (#1952). The generic `relation.put` on an event's hosted tasks is rejected with 403, so these tools are the agent's way to change that relation.

This issue declares the three write tools in the calendar manifest and implements their handlers. A handler calls the same domain function as the corresponding route handler, not the HTTP route, so choke-point validation is identical and nothing is duplicated.

Tools (names are the manifest tool names; each has a zod input schema and a one-line description):

- `calendar.respondToInvitation` `{ invitationId, response, calendarId? }`: always requires approval, because answering sends an email to the organizer. Without an approval, a call creates an approval request and sends nothing.
- `calendar.placeTaskInEvent` `{ taskId, eventId }` and `calendar.removeTaskFromEvent` `{ taskId, eventId }`.

Decision: until the grant ADR of #1385 says otherwise, every calendar write by an agent is a proposal (approval required, the default of `docs/adr/2026-09-10-agent-writes-are-proposals-not-direct-writes.md`), so all three tools are declared with the approval requirement; `calendar.respondToInvitation` keeps it permanently because it sends email, the other two may be relaxed later by a change to their declarations. The tools use one capability, `calendar.write`, declared in the calendar manifest; if the grant ADR names a different id, use that one.

Decision: calendar tools see hidden calendars; hiding is a display preference only.

Message references from the Semp bubble to calendar items (events, tasks, recordings, invitations, virtual occurrences, sleep nights, birthdays, holidays) have no planned issue; they wait for the message-ref schema work.

Shared-file ordering: this issue also waits for #1953 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `backend/packages/data/src/calendar/calendarAgentTools.ts` with the three handler factories and their zod schemas, each delegating to the domain function behind the route of its owning issue (#1944, #1764) and returning the same payload as the route.
2. Declare the tools in `agentTools` of `backend/packages/data/src/calendar/calendarModuleManifest.ts` (each with the `requiresApproval` flag from #1791), add `calendar.write` to the manifest `capabilities`, and re-export the factories from that file.
3. In `backend/services/semprec-api/src/mcp/mcpHandler.ts`, honor a module tool's approval requirement over MCP: a `tools/call` for a tool marked `requiresApproval` creates an approval request through the same path agent sessions use and answers with the existing approval-required JSON-RPC error (-32001), without running the handler. (The generic operations keep their documented MCP behavior.)
4. Tests: each tool, called as a session agent and over `POST /mcp` with the capability granted and an approved request, returns what the route returns and applies the same validations; `calendar.respondToInvitation` without approval creates an approval request and sends no email, and with an approved request answers the invitation exactly once; a tool called without the capability is absent and unknown to the caller; another tenant's ids behave as unknown; a hidden calendar's items are readable and writable.

## Scope

### In scope

- The three calendar write tools for Semp and MCP and their approval and capability declarations.

### Out of scope

- The timeline tool: #1952.
- Composing, gating and deferring module tools in sessions, and listing and calling module tools over MCP: #1523, #1791, #1580.
- The grant and approval rule for module tools: #1385.
- The task-in-event routes and the invitation route themselves: #1764, #1944.
- Completing a task in an event: generic `item.patch`, recorded by the hook of #1781.
- Deleting calendar items: it stays the generic delete, which needs approval.

## Acceptance criteria

- When Semp or an MCP client calls `calendar.respondToInvitation` without an approved request, then an approval request exists and no reply email is sent.
- When the approved request is executed, then the invitation is answered exactly once.
- When Semp or an MCP client calls one of the other two tools, then without an approval an approval request is created and nothing changes; once approved, the effect and validation equal those of the app's route.
- When the capability is not granted, then the tools do not appear and calling them is indistinguishable from an unknown tool.
