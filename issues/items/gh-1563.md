## Context

Model tier rationale: A small read-only join that adds three fields to an existing message list response, following the existing thread-read pattern with no new persistence or authorization rule.

A tick thread shows each run as a section: the start time ("Sunday 11 October 21:00"), a summary, and a footer such as "Run finished 42 s", "Waiting for approval in Inbox", or an error. The messages endpoint (`GET /api/semp/threads/:id/messages`, built by #1543) returns messages only. Runs are written into tick threads by #1557 and every assistant message there carries its `agent_run_id`. Run timing and status live in `agent_runs` (`started_at`, `finished_at`, `status`; `backend/packages/data/src/agentRuns/agentRunsStore.ts`).

Decisions: the backend returns data only; the footer text and the approval link are composed by the client. A run whose request is waiting for approval is already `done` in the backend, because the run finishes after creating the request; the client recognises the waiting state from the message steps (filled by #1860), not from `run.status`. The result of a continuation after approval (#1775) appears as another message in the same section, so it carries the same run.

## Task

Load `io-hardening`, `canonical-keys` and `testing`.

1. Each message row returned for a thread with runs carries `run: {startedAt, finishedAt, status} | null` from a join to `agent_runs` on `agent_run_id` (null for a message without a run).
2. The join is a single query for the page of messages, not one query per message. `finishedAt` is null for a running run.
3. Add the field to the shared message type and route validation.
4. Tests: a finished run gives `finishedAt` and `status: done`; a running run gives `finishedAt` null; a failed run gives `status: error`; a user message has `run` null; the query count does not grow with the page size.
