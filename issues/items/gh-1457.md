## Context

Model tier rationale: A per-tenant cutover on a schema-locked relation definition plus the matching seed change follows an existing pattern, but it edits tenant data under a lock and must stay idempotent.

`Emails.senderPeople` links an email to the person who sent it. In `backend/packages/data/src/seed/seedEmailModule.ts` it is declared with cardinality `one_to_many` from the Emails side, and the database trigger `enforce_relation_cardinality` (migration `0013_relation_cardinality.sql`) then allows each person to be linked to at most one email. The second email from the same person fails with a `cardinality_violation`, and `mail.linkPeopleByEmail` (`mail/personLinkingActions.ts`) rolls back its whole linking pass. A person is only ever the sender of one email today.

The correct shape is `many_to_many`: many emails per person. The rule "one message, one sender" is not expressed by cardinality; it is kept by the module's own writer (`mail/personLinkingActions.ts` and `mail/send.ts` write only a single sender edge).

Migration SQL must not modify tenant rows (`docs/adr/2026-10-08-deploy-time-tenant-work-runs-as-the-runtime-role.md`), so existing installations are switched by a per-tenant cutover in `backend/packages/data/src/db/tenantCutoverMigrations.ts`, following `transcription/transcriptsCatalogCutoverMigration.ts` (lock, idempotent check, update). Fresh installs get the new cardinality from the seed.

#1480 and #1571 write sender edges and depend on this. Filtering threads by person (#1638) and the People features that count a person's mail (#1535, #1660) need it too.

Decision: only `senderPeople` changes; `recipientsPeople` is already `many_to_many`, and the Emails-to-Files `attachments` relation keeps its own cardinality.

Shared-file ordering: this issue also waits for #1454 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `db-migrations`, `state-writes` and `testing`.

1. In `seedEmailModule.ts`, declare `Emails.senderPeople` as `many_to_many`.
2. Add `runEmailsSenderPeopleCardinalityCutoverMigration(pool)` in `backend/packages/data/src/mail/emailsSenderPeopleCardinalityCutoverMigration.ts`: in one transaction resolve the tenant's Emails database (no-op when it does not exist), take the same lock the Transcripts cutover takes, find the `relation_definitions` row of the `senderPeople` property, and set `cardinality = 'many_to_many'` only when it is not already so (zero affected rows is legitimate).
3. Call it from `runTenantCutoverMigrations` in `db/tenantCutoverMigrations.ts`.
4. Add tests: a populated tenant with the old cardinality can afterwards link one person to two emails as sender; running the cutover twice changes nothing; a fresh install already has `many_to_many`; re-linking an email whose sender edge already exists through `mail.linkPeopleByEmail` leaves exactly one `senderPeople` edge on it (the module writer, not the cardinality, keeps one sender per email).

## Scope

### In scope

- The seed change and the per-tenant cutover that switches `senderPeople` to `many_to_many`.

### Out of scope

- Writing sender edges for sent mail: #1480.
- Linking older emails when a person gains an address: #1571.
- Any SQL migration that changes tenant rows.

## Acceptance criteria

- When one person sent two emails and both are ingested, then both emails have a `senderPeople` edge to that person and `mail.linkPeopleByEmail` does not roll back.
- When the cutover runs on a tenant seeded with `one_to_many`, then the definition becomes `many_to_many`; when it runs again, nothing changes.
- When a tenant has no Emails database yet, then the cutover does nothing.
- A fresh install's `senderPeople` definition is `many_to_many`.
