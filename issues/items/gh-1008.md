## Context

Model tier rationale: One helper, three key sites and enumerated test updates are specified exactly.

`blobs` rows point at bytes stored by a `BlobStorageWriter` (`backend/packages/data/src/mail/blobStorage.ts:37-47`), under `FILES_STORAGE_DIR` or `MAIL_ATTACHMENTS_DIR` at `<root>/<storage_key>` (`:78-130`). Two global properties have to become per tenant.

**Deduplication is global.** `findOrCreateBlob` (`backend/packages/data/src/blobs/blobsStore.ts:68-88`) inserts with `ON CONFLICT (content_hash) WHERE content_hash IS NOT NULL DO NOTHING`. On a conflict it reads the winner with `getBlobByContentHash` (`:54-59`). The arbiter is `blobs_content_hash_uq` (`backend/packages/data/src/db/migrations/0004_ten_databases.sql:37`). Identical bytes uploaded by two tenants would share one row, and that sharing would confirm to the second tenant that the first already stored those bytes.

**Storage keys carry no tenant.** Three writers create new blobs:
- `POST /api/files` builds `files/<uuid>-<name>` (`backend/packages/data/src/blobs/fileUploadStore.ts:64`; prefix from `backend/services/semprec-api/src/filesHandler.ts:77`).
- Mail attachments build `<mailboxItemId>/<uuid>-<name>` (`backend/packages/data/src/mail/attachments.ts:87`; prefix from `backend/packages/data/src/mail/mailSyncJob.ts:242`).
- The transcription prepare step builds `transcriptions/<uuid>.opus` (`backend/services/semprec-transcribe/src/transcriptionTask.ts:290`), between its snapshot transaction (`:273-282`) and the `createBlob` that records it (`:314-319`).

Bytes stored under a tenant prefix can later be exported and purged per tenant (#1043, #1055). Existing unprefixed keys stay valid: every read goes through the row's `storage_key` as stored.

Tenancy state this issue builds on:
- `blobs` is a tenant table: `tenant_id DEFAULT app_tenant_default()`, plus the RESTRICTIVE `tenant_isolation` policy `tenant_id = (SELECT app_tenant_default())`.
- `app_tenant_default()` is `COALESCE(app_current_tenant(), app_sole_tenant())` over the GUC `app.tenant_id`.
- That GUC is set from the ambient `runInTenant` / `runAsSystem` scope (`@semprec/shared`) by `withTransaction`, autocommit `pool.query` and `pool.connect()` clients.
- `getBlobByContentHash` and `getBlob` are therefore already per tenant under a runtime role.
- #974 added the partial unique index `blobs_tenant_content_hash_uq` on `(tenant_id, content_hash) WHERE content_hash IS NOT NULL` beside `blobs_content_hash_uq`, which stays until #1065.

Arbiter choice:
- `findOrCreateBlob` moves to `ON CONFLICT DO NOTHING` with no conflict target, so every unique index is an arbiter: both today, the tenant-leading one after #1065.
- An explicit `(tenant_id, content_hash)` target would leave the legacy index as a non-arbiter. Two concurrent identical uploads (the convergence promised at `fileUploadStore.ts:42-48`) could then fail with a raw unique violation.

## Task

Load `state-writes` (dedupe inside the write's transaction), `io-hardening` (storage keys become filesystem paths) and `error-handling` (no tenant in scope must fail before bytes are written).

1. **Prefix helper.** In `blobsStore.ts`, export `tenantBlobStorageKey(client: Queryable, key: string): Promise<string>`.
   - It runs `SELECT app_tenant_default()::text AS tenant_id`, as a typed row. It is the same function that fills `blobs.tenant_id`, so a key's prefix and its row's tenant always agree.
   - It returns `` `${tenantId}/${key}` ``.
   - When the tenant is `NULL`, it throws a plain `Error` saying no tenant is in scope for a blob storage key.
   - `blobsStore.ts` is re-exported wholesale (`backend/packages/data/src/index.ts:262`), so `index.ts` needs no edit. Add the new name to the runtime export list in `backend/packages/data/src/__tests__/publicSurface.test.ts`.
2. **Writers.**
   - `fileUploadStore.ts:64`: `await tenantBlobStorageKey(pool, ...)` before streaming, so a missing tenant fails before any byte is written.
   - `attachments.ts:87`: `await tenantBlobStorageKey(client, ...)`.
   - `transcriptionTask.ts`: resolve the normalized key inside the snapshot transaction (`:273-282`), as `await tenantBlobStorageKey(client, "transcriptions/" + randomUUID() + ".opus")`, and pass it to `normalizeAudio` (`:290`). Update the tests that match the `transcriptions/` prefix (`backend/services/semprec-transcribe/src/transcriptionTask.test.ts:283,295,328`) to expect `<tenantId>/transcriptions/`, and with them `readNormalizedLeftovers`' `readdir(join(tmpBlobDir, "transcriptions"))` (`:287`) and the concurrent-run fixture key built at `:429` and sliced at `:466`, so all use the `<tenantId>/transcriptions/` prefix.
3. **Dedupe.**
   - `findOrCreateBlob` uses `ON CONFLICT DO NOTHING` with no conflict target (already in place since #974; keep it).
   - Rewrite the comment at `blobsStore.ts:72-76`.
   - The docstrings of `findOrCreateBlob` and `getBlobByContentHash` say dedupe is per tenant: RLS confines the read-back, and the arbiter is every unique index on `blobs`.
   - Do not add hand-written `tenant_id` predicates.
4. **Tests.** New `backend/packages/data/src/__tests__/blobsPerTenant.test.ts`. Cases needing a second tenant, or the post-#1065 schema, run in one transaction on `getTestPool()` (the owner), rolled back at the end:
   - `DROP INDEX IF EXISTS tenants_single_tenant_guard`;
   - `DROP INDEX blobs_content_hash_uq`;
   - insert a second `tenants` row;
   - `SET LOCAL ROLE semprec_data`;
   - switch tenants with `SELECT set_config('app.tenant_id', $1, true)`.

   Integration files run one at a time (`fileParallelism: false`, `backend/vitest.integration.config.ts:20`).

## Scope

### In scope
- The tenant prefix on every new storage key written by uploads, mail attachments and transcription.
- Per-tenant dedupe that no longer depends on the legacy index.
- The tests.

### Out of scope
- Dropping `blobs_content_hash_uq` (#1065). Until then, identical bytes in a second tenant still meet the legacy index (the guard keeps that state out of production). The "another tenant's identical bytes get their own row" behaviour through `POST /api/files` belongs there.
- Resolving downloads in scope before the conditional branch (#1009).
- Moving or rewriting existing unprefixed bytes; legacy keys stay valid.
- Library covers: `noopLibraryMetadataFetcher` (`backend/packages/data/src/library/libraryMetadataJob.ts:54`) is the only fetcher and writes no bytes. A real fetcher has to use `tenantBlobStorageKey` when it is introduced.
- Export and purge of a tenant's bytes (#1043, #1055), and log content (#1074).

## Acceptance criteria

All integration tests (`*.test.ts`).
- `ingestUploadedFile` (the `POST /api/files` pipeline), with only tenant zero existing and `storageKeyPrefix: "files"`, stores a blob whose `storage_key` starts with `<tenant zero id>/files/`, and writes its bytes under exactly that key. The existing `fileUploadStore.test.ts` and `backend/services/semprec-api/src/__tests__/filesAndBlobsHandler.test.ts` pass unchanged, including concurrent identical uploads converging on one blob and one Files item.
- An ingested mail attachment's blob `storage_key` starts with `<tenant id>/<mailboxItemId>/`. The existing `mailSync.test.ts` passes.
- The transcription prepare step's normalized-audio blob `storage_key` starts with `<tenant id>/transcriptions/`, and the bytes exist there (updated `transcriptionTask.test.ts`).
- In a rolled-back transaction with two tenants, `tenantBlobStorageKey(client, "files/x")` returns `"<B id>/files/x"` with tenant B in scope, and rejects with no `app.tenant_id` set.
- When the tenant cannot be resolved (a stub pool whose `app_tenant_default()` query returns `NULL`), `ingestUploadedFile` rejects, and the fake storage records no `writeStream` call.
- With `blobs_content_hash_uq` dropped (rolled-back transaction), `findOrCreateBlob` called twice with one hash in one tenant returns the same row. This proves the code no longer needs the legacy index.
- With the legacy index dropped and two tenants under `semprec_data`, the same hash in tenant A and then in tenant B:
  - yields two rows, each with its own `tenant_id` and its own key prefix;
  - `getBlobByContentHash` in each tenant returns only that tenant's row.
- A blob row whose `storage_key` has no tenant prefix (a legacy key) is still returned by `getBlob` with that key, and `LocalFsBlobStorageWriter.readStream(storage_key)` reads its bytes. Nothing rewrites legacy keys.
