### Requirement gh-1965: [inbox-attachments 05/08] Compute attachment metadata and thumbnails in semprec-transcribe

#### Context

Model tier rationale: It adds a new background job in the media-processing process that runs ffmpeg over untrusted uploads, new blob references and a re-trigger of the Inbox tick, so resource limits, cleanup ownership and tenant scope all matter.

An Inbox card and the day summary show an attachment as a small preview with facts: "JPG - 2.1 MB", the image size, the audio length "23:14", and when a voice recording was made. The assistant also needs a reduced copy of a photo to read. The bytes and mime type are known after upload (#1963), but nothing computes dimensions, a preview or a duration: `blobs` holds only `mime_type`, `byte_size` and `content_hash`. `ffmpeg` and `ffprobe` may run only in `semprec-transcribe` (`docs/adr/2026-09-22-ffmpeg-confined-to-semprec-transcribe.md`; the only spawn site is `backend/services/semprec-transcribe/src/mediaNormalization.ts`), whose queue lane is `transcribe` (`backend/packages/queue/src/index.ts`).

This issue adds a job there that runs after an attachment is attached and records its metadata. It is the one place that classifies an audio attachment: a short audio note is a voice note, a long one a recording.

What builds on it: #1970 reads the reduced image, #1980 transcribes voice notes, #1985 routes recordings, #1969 returns metadata in the day summary.

Decisions:
- Images (JPEG, PNG) and audio (M4A, MP3) only. PDF page counts and PDF previews need a renderer and are not computed here; a PDF attachment gets mime type and size only, with `pages` null. Reason: the product decided that PDF attachments get no preview and no page count, consistent with Files, which has no previews.
- Image previews are 128 px on the long side (shown at 64 pt on retina screens) as JPEG; the reduced copy for the assistant is a JPEG with the long side at most 1568 px, never enlarged. Both are stored as ordinary blobs and are counted references.
- The audio length comes from `ffprobe`; the recording time is the media `creation_time` tag when present. The device-supplied values of a client are not accepted; the probe is authoritative.
- `audioKind` is `voiceNote` when the duration is less than 120 seconds and `recording` at 120 seconds or longer, as required by #1978. The boundary is the constant `INBOX_RECORDING_MIN_SECONDS = 120` in this issue's module and is the only definition.
- When the job finishes it re-triggers the Inbox item's `onItemEvent` heartbeat (`triggerOnItemEventHeartbeats`) so a card computed earlier is recomputed with the facts.

### Requirement gh-1978: [transcripts 19/19] Propose transcribing an audio attachment from the Inbox

#### Context

Model tier rationale: This adds a new proposal kind whose confirm performs a multi-part write (recording request row, attachment move into Files, two queue jobs) in one transaction in a different process than the transcription worker, on top of attachment, upload and pipeline changes from several blockers; it needs an ownership decision (ADR), and getting the transaction or the idempotency wrong would start paid transcriptions twice or never.

A user can share an audio recording into the Inbox (for example from a voice recorder app). Today an Inbox item has no attachment at all, and an audio file uploaded through `POST /api/files` is transcribed at once by the Files create trigger (`core.filesTranscriptionTrigger`, `backend/packages/data/src/transcription/transcriptionActions.ts`), with no parameters. The product wants the opposite for shared audio: nothing is transcribed (and paid for) until the user confirms a card that shows what is known before transcription (length, recording time, source) and lets them set the transcript's name, language, number of speakers, Event and project.

This issue adds that card. Shared audio is an Inbox attachment row (#1564, attached at capture by #1963), so no Files item and no transcript exist before confirmation. The Inbox tick (`semprec.tick`, `backend/packages/data/src/inbox/inboxTickAction.ts`) produces the card; the confirm, which runs in `semprec-api` (`confirmProposalWithClient`), writes the recording request, moves the attachment into Files (#1703) and enqueues the transcription (#1624 created the fast row-creation task and its runner). The parameters the pipeline honors come from #1627 (language, speaker count) and #1696 (project written onto the transcript); the metadata of the attachment (length, recording time) comes exclusively from the authoritative server ffprobe metadata owned by #1965. The card kind stays `inbox`: a second producer of `transcript` cards would break the producer table of `docs/adr/2026-09-23-speaker-mappings-are-edges-proposed-on-transcript-cards.md`.

#1965 may omit `recordedAt` when no usable `creation_time` exists; #1985 still routes ready long recordings here. As a conservative consequence of the owner's server-only metadata decision, an unknown recording day means empty automatic Event suggestions and, when the item has no text, an editable localized undated default name. This is derived behavior, not a separate explicit owner choice. Manual controls and #1574's existing optional-time intake/date policy remain; no capture/upload/current time is promoted into card context or attachment metadata.

Decisions:

- Owner decision (server ffprobe metadata): #1965 owns recording duration and recording time in `inbox_attachments.metadata`; this issue only consumes that metadata, creates no second metadata migration or columns and accepts no client override, including on confirm.
- The new envelope kind is `transcription`: `target` is the id of the attachment row and `properties` are the recording parameters (see Task). It is an `inbox` card whose source is the Inbox item that holds the attachment.
- By the product owner: only an audio attachment of 120 seconds or longer (`audioKind` `recording`, #1965) gets this card; a shorter one is a voice note, is transcribed into the item text (#1980) and never gets a recording card. The sole boundary definition is `INBOX_RECORDING_MIN_SECONDS = 120`, owned and exported by #1965; this issue consumes its `audioKind` classification. The routing in the tick that sends only such attachments to this producer is #1985.
- Automatic Event suggestions: when authoritative `recordedAt` is present, offer the Events of the recording's local day of type `meeting` or `standup` and the Events with no type (Events coming from a calendar have no type and could not be suggested otherwise). Events of any other type, such as focus work, are not automatically suggested. Events whose stored date cannot be read are skipped, never an error. When `recordedAt` is absent, the recording day is unknown and automatic `candidates` is empty. Existing manual Event/project selection and "no Event" remain supported in both cases.
- Naming: the card proposes a name from the usual Inbox proposal computation when the item has text; otherwise it uses a localized default "Recording D. M. HH:mm" only when authoritative `recordedAt` is present, or the localized undated generic "Recording" when it is absent. The name stays editable in both cases, as do the existing language and speaker-count controls. It proposes no language (automatic detection), no speaker count and no project.
- By the product owner: the project follows the chosen Event until the user changes it. The card shows the chosen Event's project (from the automatic candidate or the existing manual selection); a project the user chose explicitly on the card is the recording's own value. On confirm, an envelope `projectId` that is absent or equal to the chosen Event's project is not written into the recording request, so the transcript takes the Event's project as an inherited value when its Event edge is written (#1644, #1697); a different project is written as the recording's own value (#1696).
- Choosing "no Event" simply leaves the Event unset; remembering that explicit decision so that the pairing step creates no Event card is #1986.
- Rejecting the card transcribes nothing and leaves the attachment with its Inbox item.

Shared-file ordering: this issue also waits for #1967 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Transferred atomic result obligation from #1648: after the actual enqueue succeeds, persist followUp:transcriptionQueued on its matching executed-step result in the SAME confirmation transaction. Enqueue, result and card/resources roll back together. Already-confirmed replay returns unchanged stored results and enqueues nothing. See [[2026-11-03-confirm-results-report-only-enqueued-follow-ups]]. This future producer is not authorized for implementation during batch21.

### Requirement gh-1986: [inbox-cards 07/10] Remember an explicit no-event decision for a recording

#### Context

Model tier rationale: One persisted decision written at confirm and honored in one pipeline step, across two processes (api confirm and the transcription worker), with existing fixtures for both.

After a recording is transcribed, step 6 of the transcription pipeline (`matchTranscriptToEvent` in `backend/packages/data/src/transcription/transcriptEventMatch.ts`) tries to link the transcript to a calendar Event whose time window overlaps the recording. With no candidate, or with several, it always creates a "recording without an event" card (`transcript-suggestion:<transcriptId>`). There is no way for the user to say "this recording belongs to no event" up front, so a user who shares a voice recording and picks "no event" still gets that card, and again after every rerun of the transcription.

#1574 adds the recording request record that carries the context of an uploaded recording, including a column `event_decision` with the values `none` or null (null means the user did not decide). #1978 creates the Inbox card that proposes transcribing an audio attachment and its confirm, which starts the transcription. When the user chose a concrete Event, the edge to it is written directly (#1574, #1644); this issue does not touch that case.

Decision: "no event" is stored only in the recording request's `event_decision` column. No Transcripts property is added.

Decision: when the decision is `none`, the match step creates no card and links nothing; the transcript stays without an Event. The pairing can still be set manually later.

Decision: a decision other than `none` (null) leaves the match step exactly as it is today.

#### Task

Load `state-writes`, `testing` and `canonical-keys`.

1. In the confirm of the transcription card (#1978), when the user's choice for the card's event field is the explicit "no event" value, write `event_decision = 'none'` on the recording request in the same transaction that creates the request or enqueues the transcription. A confirm with a chosen Event or with the field left unset keeps `event_decision` null. Add a small store function next to the one #1574 introduces for that table and use it from the confirm; the write goes through that store, not raw SQL in the confirm.
2. In `matchTranscriptToEvent`, before computing candidates and before the existing idempotent-replay checks create anything, look up the recording request of the audio file the transcript was created from (the key #1574 defines). When `event_decision` is `none`, return a new outcome `noEventChosen` and write nothing. Extend `TranscriptEventMatchOutcome` with it and keep the caller in `backend/services/semprec-transcribe/src/transcriptionTask.ts` treating it as a finished step.
3. A transcript with no recording request (a file uploaded as a plain Files item) behaves as before.
4. If the database role the transcription process runs as cannot read the recording request table, add the grant in a migration instead of widening the process's access elsewhere.
5. Tests: a confirm with "no event" stores `none` and a confirm without a choice stores null; with `none` the match creates no card and no edge, also on a second run (a rerun of the transcription); with null and no candidate the card is created as before; a transcript without a recording request is unaffected.

- transcripts whose `item_automation.status` is error -> `transcription:<transcriptId>` (the key and the kind that #1945 uses; a transcript is never counted into an `automation:` problem).
Operator problems (restore test, stale process) are not backfilled: their alerts re-fire on the next check.
