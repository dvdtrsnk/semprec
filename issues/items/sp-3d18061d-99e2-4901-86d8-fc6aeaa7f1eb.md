## Context

Model tier rationale: Three independent, contained backend fixes (one SQL projection change in the mail thread reads, a self-contained iCalendar VTIMEZONE generator, and a request-scoped lookup object threaded through the calendar timeline sources) with tests; no schema change and no new write path.

Findings from a backend review of the internet-accounts work:

- **F26 — a thread is listed under the subject of its latest message.** `GET /api/mail/threads` and `GET /api/mail/threads/:threadId` take `subject` from the newest live copy of the thread (`mailThreadListQuery.ts`, the `latest` CTE). A conversation started as "[x] M1 hello" is listed as "Re: [x] M1 hello" as soon as a reply arrives, and as "Undelivered Mail Returned to Sender" when a bounce (DSN) from mailer-daemon is threaded into it. The thread reference label (`mailThreadRef.ts`) and the global search group (`mailGlobalSearchGroup.ts`) take the newest message's subject the same way. `mail_threads.subject_hint` is written only when a thread is created and is read only as a fallback by `mailThreadRef.ts`.
- **F12 — every pushed VTIMEZONE lists ~26 years of transitions.** `generateVtimezone` (`calendar/sync/adapters/caldav/caldavIcal.ts`) writes every offset change from one year before to 25 years after the Event's year as RDATE lines: about 80 lines (~3 KB) per Event for Europe/Prague, sent on every CalDAV PUT.
- **F20 — the timeline re-reads the same rows.** A one-week `GET /api/calendar/timeline` on a seeded tenant with Events, Tasks, an Event series, a Task series and a birthday sends 74 statements in its transaction. 21 of them are `getDatabaseByModuleId` reads of the same system `databases` rows (every source and helper resolves Events, Tasks, Calendars, … again), three more re-read `visibleDatabaseIds`, the calendars lookup (`readCalendarIds`) runs six times, the user's locale twice, the tenant clock twice and the `hostEvents` relation definition twice.

Decisions:

- **The conversation's subject is its earliest message's.** A thread's `subject` is the subject of its earliest live message by the same activity key the list orders by (message `date`, else ingest time, else the item's update time; ties by item id), as common mail clients show it. Replies, forwards and DSNs threaded later never change it. The order (newest activity first), the cursor, `lastMessageAt`, `lastSender` and `preview` keep describing the newest message, and search still matches a thread when any of its messages matches. The list, the detail header (which reads the list's detail-only mode), the thread reference label and the global search group use the same rule; `subject_hint` stays the label's fallback for a thread without a live message.
- **A compact VTIMEZONE: the zone's current yearly rule as RRULE observances.** `generateVtimezone(zone, year)` scans the zone's offset changes (luxon, i.e. the runtime's tzdata) from 1 January of `year − 1` to the end of `year + 5`. The longest tail of those changes that follows one yearly rule per direction (same month, weekday, local wall time, offsets, and a day rule `nth`, `last` or "weekday on or after day N" that reproduces every observed day) becomes one STANDARD and one DAYLIGHT observance with `RRULE:FREQ=YEARLY;BYMONTH=…;BYDAY=…` (and `BYMONTHDAY=N..N+6` for the "on or after" form), provided the tail has at least three changes per direction and reaches the window's last year. Changes before that tail (a zone that changed its rule recently) are kept as RDATE observances. A zone with no change after `year` (no DST, or DST abolished) ends with the offset after its last change, so its changes in the window are written as RDATEs and its last observance holds from then on; a zone with no change at all gets one STANDARD observance. When no rule explains the tail (for example a zone whose changes follow a lunar calendar), the window's changes are written as RDATEs, as today but for the 7-year window around the Event only. Every observance's DTSTART is the local wall time of its first onset in the offset before it, as RFC 5545 requires.
- **One lookups object per timeline read.** `readCalendarTimeline` creates a `CalendarTimelineLookups` for its transaction and passes it to every source in `CalendarTimelineContext.lookups`. It reads the system databases the timeline uses in one statement (`getDatabasesByModuleIds`, same failure on several matches as `getDatabaseByModuleId`), the calendars once (default, every `systemKey` → lowest id, read-only account calendars; replaces `readCalendarIds` and `readSystemCalendarId`), the user's locale once, the `hostEvents` relation once and `visibleDatabaseIds` once for every `getItemsByIds` the sources make. The lookups never outlive one read. The callers of `toTimelineItems` and `expandEventOccurrences` outside the timeline (reminders feed, next-occurrence date, transcript event match) create their own lookups object, so their reads share it too. `readEventsTasks` gets a variant that takes the Events database, the relation and the zone the caller already resolved, so the timeline does not read them again.

### Out of scope

- Any schema change.

## Acceptance criteria

- A thread whose first message is "[x] M1 hello" keeps that `subject` in `GET /api/mail/threads` and in the thread detail after a reply "Re: [x] M1 hello" arrives, and after a DSN ("Undelivered Mail Returned to Sender") is threaded into it, while `lastMessageAt` and `lastSender` follow the newest message; the thread reference label shows the same subject.
- A generated VTIMEZONE for Europe/Prague and America/New_York has one STANDARD and one DAYLIGHT observance with an RRULE and no RDATE, and is far shorter than before; Asia/Kolkata has one STANDARD observance; a zone that changed its rule recently is written as RDATEs for the old rule followed by the new state; an Event in the far future (2090) gets the rule too. For each of them ical.js reading the generated VTIMEZONE gives the same UTC offset as the zone itself at every change and around it, across the window and for years after it.
- A one-week `readCalendarTimeline` on the seeded test tenant reads the system databases in one statement, the calendars once, the locale once and the `hostEvents` and `completedInEvent` relation definitions once each, in at most 39 statements (74 before).
- The existing mail thread, mail summary, CalDAV push and ICS, timeline, occurrence, reminders feed and transcript match test files stay green.
