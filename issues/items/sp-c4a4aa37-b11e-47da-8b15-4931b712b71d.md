### Requirement gh-1855: [subpages 11/12] Show trashed pages with their title and path

#### Context

Model tier rationale: An additive change to one existing read route, filter and row shape over fixtures that already cover the trash list, with title and path read from item state only.

The trash screen lists recently deleted items across all databases with their collection name, deletion time and days left. The list route, `GET /api/trash/items`, is delivered by #1851: it returns only the roots of a cascade, skipping items of inline databases whose parent was deleted in the same transaction. Pages are items of the hidden `pages` database (#1393), which is not a collection, and they are trashed together with their parent page or host in one transaction (#1723, #1763). Without a change they would appear as many rows of an unknown "Pages" collection, each without a readable name or place. The title of a page is the `title` property of its Pages item, mirrored from the parent document (#1725, #1715), so it is available without loading any document.

This issue teaches the trash list about pages: a nested page trashed with its parent is not a row of its own, and a page that is the root of a deletion is shown as a page with its title and the path to it.

Decisions:
- A Pages item is skipped as a non-root when its `parentItemId` points to an item that is deleted with the same `deletedAt` (a page, or a host item).
- For a root page the row keeps the fields of #1851 and adds `page: { title, path }`, where `path` is the chain of ancestors from the host to the parent as `[{ itemId, title, trashed }]` (host titles from the host item's `title`-typed property, page titles from the mirror), read from items including trashed ones, with a visited-set guard. The client labels such a row "Page" instead of using the collection name; `databaseName` stays the hidden database's localized name.
- The hidden database never appears in the trashed-databases list (it is a system database).

#### Task

Load `testing` and `error-handling`.

1. In the trash items handler of #1851 extend the selection to skip non-root Pages items as defined above (same `deletedAt` as the parent, using the parent link and no document reads), keeping ordering, paging and `totalCount` consistent with the filter.
2. Add the `page` object to rows whose item is in the `pages` database, computed with one batched read of the ancestor items per page of results (no per-row queries beyond that), including trashed ancestors.
3. Tests: deleting a subpage that has two nested pages gives one row with `page.title` and a path `Notes > Release checklist`-style chain of titles; deleting a project with subpages gives the project's row and none for its subpages; a page trashed on its own earlier than its deleted parent gets its own row; paging and `totalCount` stay correct across a page of results made of both kinds; a renamed page shows the new title; another tenant's trash is not visible.

#### Touches

- the trash items route handler and its row type introduced by #1851 (filter and `page` object)
- backend/services/semprec-api/src/__tests__/ (trash list tests with pages)
- backend/packages/data/src/__tests__/ (query tests)

#### Scope

##### In scope

- Filtering non-root pages from the trash list and adding title and path to root page rows.

##### Out of scope

- Trashing and restoring pages and hosts: #1723, #1763.

#### Acceptance criteria

- When a subpage with two nested pages is deleted, then the trash list has one row for it with `page.title` and a `page.path` of its ancestors, and no rows for the nested pages.
- When a project with subpages is deleted, then the list shows the project row only.
- When a nested page was trashed on its own before its parent, then it has its own row.
- When a page is renamed, then the row shows the new title; `totalCount` and paging are unaffected by page rows being skipped.

### Requirement gh-1992: [inbox-cards 09/10] Detect duplicate companies and people in proposals

#### Context

Model tier rationale: One deterministic post-processing step over the computed envelope using two existing lookups, but its result must be expressed in the new multi-step envelope shape and stay within the no-write rule of the computation.

Capturing "the bakery with registration number X" or "Lucie, lucie@brainz.cz" for a company or person that already exists must not create a second record. Today a proposal can only create a record; nothing compares it to existing Companies or People. The existing lookups are: Companies carries a plain-text `ico` property (no index), and People carries `emails` (one address per line) with the `person_email_index` table maintained by `backend/packages/data/src/mail/personLinkingActions.ts` and read through `lookupPersonIdByEmail` and `normalizeEmailAddress` in `backend/packages/data/src/mail/personEmailIndexStore.ts`.

The proposal computation is built by #1434 and receives its context from #1987. Proposals can express relations and several steps once #1426 (relations in a database envelope) and #1479 (validation of multi-step envelopes, including the link step) land; this issue emits the link step defined there. The computation must never write to the target databases or the Inbox, so the lookups are plain reads done outside any write transaction, and the result is only an envelope.

Decision: a duplicate is found by exact match only: the same normalized IČO for a company, the same normalized e-mail address (via `person_email_index`) for a person. There is no fuzzy name matching.

Decision: when a duplicate is found, the create step is replaced by a link step to the existing record and no field of the existing record is changed. Merging captured values into it is a separate user action.

Decision: phone numbers are not compared in this issue; People has no phone property yet (#1535 adds it).

If a live (not trashed) Companies item has the same value, replace the create of that company with the link step to its id. Add a read helper in `backend/packages/data/src/` (for example `companyIcoLookup` in the Inbox area) that finds a live company by exact `ico`; it reads only.

### Requirement gh-1993: [inbox-cards 10/10] Feed past Event durations into proposal computation

#### Context

Model tier rationale: One extra, bounded section in the computation context built from an existing read, with clear exclusion rules and no new persisted data.

When someone captures "call with Petr on Thursday at two", the proposal should suggest a sensible end time. The best signal is how long the user's earlier events with the same people lasted. The proposal computation (#1434) receives a bounded workspace context from #1987 (active projects, areas, people, companies and events around the mentioned time, each with ids and a per-kind limit). That context has no durations.

Events get an end time of day (`timeTo`) next to `timeFrom`, an optional `endDate` for events that end on another day, and a `place` once #1416 lands. Until an event has both `timeFrom` and `timeTo` its length is unknown. Events link to People through the user-owned `people` relation.

Decision: durations are added only when the proposal's target is the Events database, to keep the model request small for every other kind.

Decision: only same-day events with both times set count. An event with an `endDate`, a missing time, an all-day event or a non-positive length is skipped, so a multi-day trip never skews the suggestion.

Decision: the context carries, for each person already in the context's People list, up to the five most recent such events as `{ eventId, minutes, startDate }` plus no event names, to keep the section small and free of free text.

### Requirement gh-1994: [health 09/09] Propose new select options and create them on confirm

#### Context

Model tier rationale: It lets a confirmed Inbox proposal change a locked database's schema inside the confirm transaction, combining proposal validation, a schema write under user authority and exactly-once semantics for a card that can be confirmed twice.

The assistant may find a tag that does not exist ("Herbs"). Today it cannot propose it: an unknown key is rejected (#1814), and the assistant has no way to create an option. With #1699 (an operation that adds an option to a select on a locked database) and the grounding of #1990, a proposal can name a new option by label, the card shows it as new, and confirming the card creates the option and uses it in the same transaction.

This is only released together with a card design that shows a new value as new and lets the user edit it; the backend part is specified here and waits for that design.

Decisions:
- An envelope may carry `newOptions: [{ propertyKey, label, color? }]` for a `select` or `multi_select` of the target database. A property value then names the new option by its label placed in the `properties` as `{ newOption: "<label>" }` in the place of a key.

- A new option is created only when the person confirms; a rejected or discarded card creates nothing.

#### Task

1. Extend the proposal envelope schema and `assertValidProposalEnvelope` (`backend/packages/data/src/inbox/inboxTickAction.ts`) with `newOptions` and the `{ newOption }` value form, with the rules above; the old envelope shape is unchanged.
2. In `confirmProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`), before creating the target item, add each new option using the option-add logic of #1699 on the same client, replace each `{ newOption }` by the returned key, then continue as today. Re-confirming a confirmed proposal creates nothing twice.
3. Extend the grounding of #1990 only to tell the model that a new tag may be proposed with `newOptions` when no listed option fits.
4. Tests: confirming a proposal with a new tag "Bylinky" creates the option and the health record carrying its key in one transaction; a failing item create (for example a missing title) leaves the option uncreated; a label matching Medication is rejected; four new options are rejected; a discarded card creates no option; confirming twice yields one option and one item; an envelope without `newOptions` behaves as before.

- backend/packages/data/src/inbox/proposalTargetCatalog.ts (prompt note about new options)
- backend/packages/data/src/__tests__ (new new-option proposal tests)

### Requirement gh-1979: [project-mcp 07/08] Default risk class and approval from MCP tool annotations on sync

#### Context

Model tier rationale: One migration plus a deterministic annotation-to-classification mapping inside the existing sync upsert, but it changes which writer owns two user-visible safety columns, so the provenance rules need careful tests.

Today every synced MCP tool is registered with the column defaults of `mcp_tool_registrations` (`risk_class` is `unclassified`, `requires_approval` is true), so every tool asks for approval until a human reclassifies it, and a read-only tool is treated like a destructive one. The server already tells us more: the MCP `tools/list` response carries annotations (`readOnlyHint`, `destructiveHint`, `openWorldHint`), but `listAllTools` and `validateListedTools` in `backend/packages/data/src/mcp/mcpSync.ts` read only `name`, `description` and `inputSchema`, and `upsertMcpToolRegistration` (`mcpToolRegistrationsStore.ts`) never writes the two classification columns. `reclassifyMcpTool` and `PATCH /api/mcp-tool-registrations/:id` are the only writers, and they are per registration, so a setting applies to every project.

This issue derives a default classification from the annotations when a sync creates a registration, and records who set the classification so that a later sync never overwrites a person's choice.

Annotations are hints from the server, not guarantees, so they only choose the default. The closed set of risk classes (`unclassified`, `read`, `write`, `destructive`, `outbound`, `breaksLink`) is owned by #1423; this issue imports that set and does not define classes. The sync is triggered by the sync route #1972 and by the queued sync after a confirmed MCP server proposal #1976; both call `syncMcpServerTools`, which is where this change lives, so both get it.

Mapping, evaluated in this order for a tool whose `annotations` object is present:

1. `readOnlyHint` is true: `riskClass` `read`, `requiresApproval` false.
2. Otherwise `destructiveHint` is not explicitly false (the MCP default is true): `destructive`, `requiresApproval` true.
3. Otherwise `openWorldHint` is explicitly true: `outbound`, `requiresApproval` true.
4. Otherwise: `write`, `requiresApproval` true.

A tool with no annotations at all stays `unclassified` with `requiresApproval` true.

Decision: `openWorldHint` counts only when explicitly true (the MCP default is also true, but treating an absent value as outbound would classify nearly every tool that way and make the class meaningless).

Decision: a registration is re-derived by later syncs only while its `classification_source` is `annotation`; the first manual change through the existing PATCH sets it to `manual`, and a `manual` registration is never rewritten by a sync. Existing rows are backfilled conservatively: a row that still has the defaults (`unclassified` and `requires_approval` true) becomes `annotation`, every other row becomes `manual`, so nothing a person may have set is lost.

Migration `backend/packages/data/src/db/migrations/NNNN_<name>.sql (next free ordinal at commit time)`: add `classification_source text NOT NULL DEFAULT 'annotation' CHECK (classification_source IN ('annotation', 'manual'))` to `mcp_tool_registrations`; backfill existing rows as described above in the same file. Additive and rollback-safe.
2. In `mcpSync.ts`, read `annotations` from each listed tool (keep only the three boolean hints, ignoring anything else), carry them through `validateListedTools`, and pass the derived `riskClass` and `requiresApproval` to the upsert.
3. In `mcpToolRegistrationsStore.ts`, extend `upsertMcpToolRegistration` with optional classification input: on insert, write it; on conflict, update `risk_class` and `requires_approval` only `WHERE classification_source = 'annotation'`; never touch a `manual` row.
4. Put the mapping in a pure function (`classifyMcpToolFromAnnotations`) in a new file `backend/packages/data/src/mcp/mcpToolAnnotationClassification.ts`, typed with the class set from #1423.
5. In `mcpGrantsAdminStore.ts`, make `setMcpToolRiskClass` and `setMcpToolRequiresApproval` also set `classification_source = 'manual'`.

### Requirement gh-1989: [inbox-cards 08/10] Verify Czech companies against ARES during proposal computation

#### Context

Model tier rationale: One deterministic external lookup inserted into an existing bracketed computation, with injectable client tests; the failure handling (never fail the card) is the only subtle part.

A company the user captures with a Czech registration number (IČO) should get its official registered name from the public company register (ARES), so the card is not left with whatever spelling the text or the model produced. Nothing in the backend calls ARES today. The host egress filter is a deny-list of private ranges (`docs/adr/2026-10-03-host-egress-filtered-by-service-uid.md`), so the public host `ares.gov.cz` is reachable from the `semprec-api` process.

The proposal computation is built by #1434 (a `computeProposal` function in `semprec-api`, run by the Inbox tick) and receives its bounded context from #1987. The tick follows `docs/adr/2026-09-10-bracket-non-transactional-calls-with-staleness-checked-transactions.md`: a read transaction, then the non-transactional computation, then a write transaction that re-checks staleness. The ARES call belongs to the middle step only: it runs outside any transaction and never writes. This is the one deterministic lookup the computation makes besides the model call; agent sessions keep using their own tools.

The ARES URL is operator configuration of the service, not a user-supplied URL, so the connect-time address check for stored user URLs does not apply. The URL is a fixed `https://` constant.

Decision: only the registered name is taken over. Registered address and tax id are not stored, because no company property holds them.

Decision: the lookup is best effort. A timeout, a non-2xx answer, an unparseable answer or "not found" leaves the computed properties unchanged and is logged; it never fails the tick, never makes the card `needsClarification` and is never retried by the queue.

Decision: the IČO is checked for format only (eight digits after trimming spaces and left-padding with zeros), not for the check digit, so a number ARES knows is never skipped.
