**Blocked by:** #1842, #1854
**Model tier:** medium

## Context

Model tier rationale: A refactor of one function behind tests that already pin its behaviour for every actor, plus a small per-process registry that follows an accepted pattern. It adds no route, operation, table or migration and changes no answer, but the function decides what an agent may see, so the actor rules (agent grants, `humanActor`) must move without change.

Issue #1864 contributes the `mail` group of global search "using the contribution seam delivered by #1842". #1842 did not deliver one, and #1854, which landed after it, did not either. In `backend/packages/data/src/search/searchItemsQuery.ts` the seven item groups are the closed `GROUP_MODULES` allow-list (owner module ids per group), and the `chat` group is a hard-wired block at the end of `searchItemGroups` that calls `searchSempThreads` when `humanActor` is true and `chat` is in scope. `mail` is accepted as a scope value by `SearchInputSchema` and is a thread-backed group in `SearchGroupSchema` (`shared/src/genericOperations/schemas.ts`), but nothing can fill it, and `ModuleManifest` (`module-registry/src/manifest.ts`) has no field for a search group. The worker of #1864 stopped at its preflight for this reason (`e1-136-mail`).

This issue adds the seam and nothing else: one per-process registry of search groups in `search/`, filled in the composition root `domainWriteHooks.ts`, that `searchItemGroups` reads instead of `GROUP_MODULES` and the `chat` block. The registry is the pattern of `[[2026-09-30-choke-point-domain-hooks-through-a-per-process-registry]]` (a registry the composition root fills, so the reading code names no domain), with the registration rule of `[[2026-11-05-automation-batch-reads-use-the-domain-registry]]` (the same registration twice is a no-op, a different second one is refused). The registry lives in `search/` and not in `chokePoint/hooks.ts`, because search is not a write path and `clearHooksForTests`, which several tests call, must not empty it. A manifest field was not chosen: the search function runs on a `Pool` without a module registry, and loading one into it would change the function's signature and its caller. The record of #1864 names `mailModuleManifest.ts` as the place of its registration; with this seam that registration is one line in `domainWriteHooks.ts`, and #1864 is amended accordingly outside this issue.

The behaviour of the existing groups does not change: the same databases per group, the same order, the same cursors, the same refusals, the same logs and the same actor rules.

## Task

Load `adr-conventions`, `testing`, `state-writes` and `io-hardening`.

1. Add `search/searchGroupRegistry.ts` with two kinds of group, keyed by `SearchGroupType`:
   - an item group `{ type: SearchItemGroupType; ownerModuleIds: readonly string[] }`, registered with `registerItemSearchGroup`;
   - a thread group `{ type: Exclude<SearchGroupType, SearchItemGroupType>; prepare(cursor: string | undefined): ThreadSearchRun }`, registered with `registerThreadSearchGroup`. `prepare` validates the cursor token as the group's own cursor, throws the group's `ValidationError` for a malformed one, and returns the search bound to the parsed cursor: `ThreadSearchRun = (client: PoolClient, request: ThreadSearchRequest) => Promise<{ total: number; items: SearchThreadResult[]; nextCursor: string | null }>`. `ThreadSearchRequest` is `{ q, buildQuery, limit, agentProjectItemId?, humanActor }`: the search text, the shared tsquery builder (`ThreadSearchQueryBuilder` of `sempThreadSearch.ts`), `perGroupLimit`, and the actor facts `searchItemGroups` already has. The group applies its own actor rule from them.
   - `getSearchGroup(type)` returns the registration or `undefined`. Registering the same object twice is a no-op; registering a different group for a type that has one throws. `clearSearchGroupsForTests()` empties the registry and throws unless `NODE_ENV` is `test`, like `clearHooksForTests`. Nothing is added to `index.ts` or the data package's public surface.
2. In `search/searchItemsQuery.ts` remove `GROUP_MODULES` and the `chat` block, and read the registry instead: the requested groups in the fixed order of `SEARCH_GROUP_TYPES`, each with its registration; a requested type without a registration (`mail` until #1864) contributes nothing and is not an error. Item groups use the existing code (`listSearchableDatabases` over the union of their `ownerModuleIds`, `countMatches`, `readPage`, `readSnippets`, `buildSubtitleParts`, the system-project exclusion for `project`). A thread group runs after the item groups, inside the same repeatable-read transaction, through the run `prepare` returned; a result with `total` 0 is omitted as for items. The cursor checks keep their order and messages: the token is checked before anything is searched, for every actor and for a query without a searchable word, with the item cursor shape for an item group and by the thread group's `prepare` when the scope is exactly that group, and a cursor with a scope of more or fewer than one group is refused as today. The early return without a transaction for a query with no searchable word, or with no registered group requested, stays. Update the comments of the file that say the `mail` group is filled by a later issue.
3. In `search/sempThreadSearch.ts` export `sempThreadSearchGroup`, the thread group of `chat`: `prepare` parses the token with `parseSempThreadListCursor` (the refusal of #1854 for a malformed chat cursor is unchanged), and the run returns `searchSempThreads(client, { buildQuery, limit, cursor })` when `request.humanActor` is true and an empty page (`total` 0, no items, `nextCursor` `null`) otherwise, so an agent run or an MCP session still gets no `chat` group.
4. In `domainWriteHooks.ts` register, beside the other registrations, the seven item groups with the owner modules `GROUP_MODULES` held (`task`: Tasks; `event`: Events; `project`: Projects; `area`: Areas; `contact`: People and Companies; `journal`: Journal; `file`: Files) and `sempThreadSearchGroup`.
5. Add `docs/adr/<date>-search-groups-register-through-a-per-process-registry.md` (the date is the day it is written; `area: [backend]`, `supersedes: []`). It records the registry, why it lives in `search/` and is filled by the composition root, why it is not a manifest field, the registration rule, the two kinds of group and the actor rule being the group's own, with `[[2026-09-30-choke-point-domain-hooks-through-a-per-process-registry]]` and `[[2026-11-05-automation-batch-reads-use-the-domain-registry]]` as the mechanisms it extends. Do not edit an accepted ADR.
6. Tests:
   - `search/__tests__/searchGroupRegistry.unit.test.ts` (new): the same registration twice is a no-op, a different second registration for a type throws, `getSearchGroup` of an unregistered type is `undefined`, `clearSearchGroupsForTests` empties it. After importing `domainWriteHooks.js`, the registry holds the seven item groups with exactly the owner modules listed above and the `chat` thread group.
   - `__tests__/searchGroupContribution.test.ts` (new), on the runtime-role pool with two tenants, calling `clearSearchGroupsForTests()` first and registering its own fixtures: one item group over the Tasks database and one thread group for `mail` that records its request and returns fixed entries. The thread group's entries appear after the item groups and before a registered `chat` group in the order of `SEARCH_GROUP_TYPES`; it receives `q`, `perGroupLimit`, `humanActor` and `agentProjectItemId` as `searchItemGroups` got them; its `prepare` receives the cursor only for the scope `["mail"]`; a malformed cursor refused by `prepare` is refused for a person, for an agent and for a query with no searchable word, and the group's run is not called; a requested type without a registration contributes nothing; an item group of another tenant's data never appears.

## Scope

### In scope

- The registry of search groups, its use by `searchItemGroups` for the item groups and for the thread groups, and the registration of the seven existing item groups and of `chat`.

### Out of scope

- The `mail` group and its registration (#1864), including the shape of a mail entry: the Task of #1864 names `itemId`, `databaseId` and `databaseKey` beside `threadId`, while `SearchThreadResultSchema` is strict with `threadId`, `title`, `subtitleParts` and `snippet`. #1864 decides which of the two changes.
- A new group type, a new scope value, a change to `SearchInputSchema`, `SearchOutputSchema` or any shared generic-operation file, the REST route and the MCP tool.
- A `ModuleManifest` field for search groups and any change to `module-registry`.
- A change to ranking, snippets, subtitle parts, visibility rules, limits or the cursor formats of the existing groups.
- Exporting the registry from the data package.

## Acceptance criteria

- When a thread group is registered for `mail` and a search names no scope, then its entries are returned after the item groups and before `chat`, with its own `total`, limited by `perGroupLimit`.
- When the scope is exactly `["mail"]` and a cursor is given, then the group's `prepare` receives that token and its run receives the parsed cursor; when the scope has more than one group, then the cursor is refused as before.
- When a cursor is malformed for the group that owns it, then it is refused with a validation error for a person, for an agent and for a query with no searchable word, and nothing is searched.
- When a requested group type has no registration, then the answer has no group of that type and no error.
- When a person, an agent run or an MCP session searches, then every existing group answers exactly as before: the same databases per group, the same order, the same `total`, `nextCursor` and snippets, no `chat` group for an agent, and the agent's database grants still hide the databases it may not read.
- When two groups are registered for one type with different definitions, then registering the second throws; registering the same one again does nothing.
