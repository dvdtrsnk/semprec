## Context

Model tier rationale: Restructures the calendar sync apply from one transaction into a claimed, resumable sequence of bounded transactions while keeping per-Event idempotency, cursor ordering, invitations, notifications, push re-queues and the lock order; changes the manual sync route's locking; touches the baseline schema and a documented architecture rule.

Production (v0.2.1, one tenant, 2 vCPU VPS): after an iCloud account with Calendars on was added, its first CalDAV pass imported 6 calendars / 1690 events. During the pass 30 API requests failed with 500: `GET /api/account/summary` (statement timeout in `countRoots`), pool connect timeouts in `runTransaction` for `/api/mail/mailboxes`, `/api/overview`, `/api/calendar/timeline`, `/api/account/summary`, and `POST /api/accounts/:id/calendars/sync` (statement timeout in `recordManualCalendarSyncRequest`). `pg_stat_activity` showed one `semprec_data` connection idle in transaction for more than 1m45s, last query `SELECT app_tenant_default()::text AS tenant_id` (the reminders resync create hook that every Event create runs). The initial mail sync of the same account ran concurrently.

Root cause, reproduced locally (scratch profile, embedded Postgres 18, 1980 fake events in 6 calendars): the fetch already runs with no transaction open, but `applyCalendarSync` writes every calendar and Event of the pass in **one transaction** (67.6 s locally, ~34 ms per created Event through the choke point). That transaction holds the account's calendar sync guard and the `calendar_account_sync_state` row `FOR UPDATE` for its whole duration, so the manual sync request's upsert waits on the row lock until the statement timeout; and it pins one of the `semprec-api` pool's 10 connections (pg default; shared by HTTP, graphile-worker with `QUEUE_CONCURRENCY` 4, the LISTEN clients and the mail live sync) for minutes on a 2-vCPU host while the mail initial sync holds another, so HTTP requests (the account summary alone checks out 5 connections at once) wait past the 10 s connect timeout.

`countRoots` is not a slow query: with 14 000 trashed Emails it runs in 6.8 ms (`EXPLAIN ANALYZE`: bitmap scan of `items_deleted_at_idx` and `items_database_id_id_idx`, anti-join by `items_pkey`), and a plain `SELECT` waits on no row lock. Its timeouts are the same contention; no index is added.

The mail IMAP pass holds a transaction across IMAP I/O by design (`IMAP_NEW_MESSAGES_PER_PASS` = 10, the tenant's mail-thread guard held while it downloads), one pooled connection per pass. Changing that is a separate issue (see Out of scope).

Decisions:
- A pass applies in bounded batches, each its own short transaction under the account's guard. A **prepare** transaction re-checks the account and the tracked snapshot, writes the calendars (a new remote calendar gets its `calendar_remote_state` row with no cursor, so it is tracked and a pass that dies is resumed without a second calendar), untracks vanished calendars, computes each calendar's deletions (the same window as today's fetch-then-apply), and claims the account by storing a fresh `apply_pass_id` on `calendar_account_sync_state`. Each **batch** checks the claim and that the account is live with Calendars on, then applies up to a bounded number of Event operations (deletions, then masters, then overrides) and the invitations of the Events it wrote. The **final** transaction checks the claim, stores every calendar's cursor, re-queues pushes, writes the change notifications, records `ok`, clears the claim and resolves the problem. A newer pass's claim supersedes an older one at its next batch, so the cursor stored always belongs to the pass whose batches wrote last. A pass that dies between batches leaves the cursors as they were; the next pass re-applies idempotently by remote id and snapshot.
- The manual sync request never waits on the pass's locks: it takes the account row's share lock and the state row with a transaction-local `lock_timeout` of 50 ms in a savepoint; when a lock is held it still queues the pass (the job key keeps one waiting job) and answers 202 `queued: true` without recording the debounce.
- No pool size change: with bounded batches the pass holds at most one connection per batch and releases it between batches.

## Task

Load `state-writes`, `io-hardening`, `error-handling`, `testing`, `adr-conventions`, `db-migrations`.

1. Baseline: `calendar_account_sync_state.apply_pass_id uuid` (nullable), the id of the pass whose batches are applying.
2. `calendarSyncApply.ts`: replace the single apply with prepare / batches / final as decided, each in its own `withTransaction` under the account guard (same lock order: guard → state row → calendar rows → Event rows). A batch holds at most `CALENDAR_SYNC_BATCH_EVENTS` (50) Event operations. Superseded or skipped at any step ends the pass with that result; the result lists of a pass are the union of its batches. Notifications are collected over the batches and written in the final transaction (filtered by the Events whose invitations were notified in any batch); invitations are reconciled in the batch that wrote their Events.
3. `calendarAccountSyncJob.ts`: drive the steps with no transaction held between them; a test-only `afterBatch` option lets a test stop a pass between batches.
4. `createCalendarAccountSyncRouteHandler`: the non-waiting locking above; 404 / 409 `calendars_disabled` unchanged.
5. `docs/architecture/domain-calendar-tasks-and-media.md`: the apply, notification, invitation, status, trigger and lock-order paragraphs describe the batched apply, the claim and the manual request's locking.

## Scope

### In scope

- The batched, claimed, resumable calendar apply; the non-waiting manual sync request; their tests and the architecture document.

### Out of scope

- The mail IMAP pass holding its transaction across IMAP I/O (fetch-then-apply for mail), to be proposed separately.
- The account summary's five concurrent connections per request, and pool sizing per service.
- The per-Event cost of choke-point creates (~34 ms locally).
- Any index for `countRoots` (not a slow query).
- Running anything against production.

## Acceptance criteria

- A pass of ~2000 fake events completes with every Event created once; no transaction of the pass lasts longer than a few seconds, while concurrently issued timeline, account summary and mailbox list reads on a small runtime pool with a low `statement_timeout` all succeed.
- `POST /api/accounts/:id/calendars/sync` answers 202 promptly while a pass holds the account's guard and its state row lock.
- A pass stopped between batches leaves the cursors unadvanced and the state not `ok`; the next pass completes without duplicate Events or calendars and then advances the cursors.
- A pass superseded by a newer pass's claim stops at its next batch and stores no cursor.
- The existing calendar sync tests stay green.
