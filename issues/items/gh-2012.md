## Context

Model tier rationale: It changes one validation rule of an existing route and relies on the occurrence materialization and lock order of its blockers, with real-database fixtures; no new route, lifecycle or persisted contract.

#1764 adds `PUT /api/tasks/:id/host-events/:eventId`, which puts a task into an event. A task with an active recurrence (the current instance of a series, found with `getTaskRecurrence`) is rejected there with 400 `validation_failed` on `taskId`, because placing the task would hide the whole series. #1720 adds `POST /api/tasks/series/:seriesId/occurrences/:date`, which turns one occurrence of a series into a real item (or returns the item that already exists) without changing the template or the other occurrences; #1605 gives each occurrence item a `seriesId` and an `occurrenceDate`.

Decision (product owner): a recurring task dragged into an event moves into it as that one occurrence only; the series stays as it is. A future occurrence that has no item yet is placed by first materializing it through #1720 and then putting the returned item into the event; no new route is added.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. In the PUT handler of #1764 (`backend/packages/data/src/tasks/taskHostEventRouteHandlers.ts`), replace the 400 for a task with an active recurrence: any task item that has a `seriesId` (the current instance or another materialized occurrence) is placed as that occurrence. The edge is written on that item only; the `task_recurrence` row, the series template and every other occurrence are not changed. Keep the lock order items, then `task_recurrence`, if the row is read.
2. Placing the current instance does not advance or deactivate the series; the series advances only when that occurrence is completed, as before (#1670).
3. Tests (real database): putting the current instance of a daily series into an event creates the edge on that item, leaves the template and the `task_recurrence` row unchanged, and the projection still returns the next occurrences; materializing the 17 October occurrence through #1720 and putting the returned item into an event hides only that occurrence while the 18 October occurrence is still projected; completing the placed occurrence creates the next instance once; the other #1764 rules (trashed task or event 404, foreign tenant 404, move-to-end on a repeated PUT) still hold for occurrences.

## Scope

### In scope

- Accepting an occurrence of a series in the place-into-event route, with only that occurrence affected.

### Out of scope

- Materializing an occurrence: #1720.
- The visibility and day derivation of hosted tasks: #1780.
- Inserting a whole series into an event: not built.
- Client flow that materializes a virtual occurrence before the drop.

## Acceptance criteria

- When the current instance of a recurring task is put into an event, then the response is 200 with the edge, and the series template, its rule and the other occurrences are unchanged.
- When a materialized future occurrence is put into an event, then only that occurrence is hidden until the event ends and the following occurrences are still shown.
- When the placed occurrence is completed, then the next occurrence of the series is created exactly once.
- When the task or event is trashed or foreign, then the response is 404 as in #1764.
