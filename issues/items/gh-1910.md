## Context

Model tier rationale: One read route that assembles data from several already-delivered sources into a defined shape, with a derived status and a localised label, over existing fixtures.

The project agent screen shows the project's automatic tasks: name, a schedule label ("Mon to Fri at 8:30"), the last run ("Last today 8:30, OK"), a switch, and for a failed one "Off, last run failed: GitHub unavailable". There is no HTTP route that lists a project's heartbeats; only `listHeartbeatsByProject` in `backend/packages/data/src/scheduler/schedulerStore.ts` and the agent tool `heartbeat.list`. The raw `last_error` and `heartbeat_occurrences.last_error` are exception text, and a run that ends after creating an approval request is `done`, so the occurrence is `succeeded`; neither is suitable to show.

Inputs from other issues: the origin marker (#1438), the link from a run to its occurrence (#1458), the display status that shows a pending approval (#1820), localised error summaries stored as codes (#1824), the "failed tool call in an otherwise finished reply" flag (#1890), and the tick thread id (#1557). Routes are registered as module custom routes (`docs/adr/2026-09-11-module-manifest-custom-routes.md`).

Decisions: the response carries `enabled` and `lastOccurrence.status` separately, because "off, last run failed" is the combination of `enabled = false` and `failed`; the system never switches an automation off on its own because of failures (whether it should is an open product question).

Shared-file ordering: this issue also waits for #1909 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `io-hardening`, `canonical-keys`, `error-handling` and `testing`.

1. Add `GET /api/projects/:id/heartbeats` returning only heartbeats with `origin = 'user'` of that project: `{id, name, rule, ruleLabel, enabled, nextFireAt, lastOccurrence, threadId}`. `rule` is structured. `ruleLabel` is an i18n-formatted string in the system timezone (`weekly [mon..fri] 08:30` gives "Po-pa v 8:30" in Czech, "Mon-Fri at 8:30" in English) using message keys in `seed/i18n/cs.json` and `en.json`.
2. `lastOccurrence` is `{at, status, errorSummary}` or null. `status` is `ok`, `waiting_approval` or `failed`, derived from the display status of the run linked to the latest occurrence (`heartbeat_occurrence_id`), including a reply that finished with a failed tool call; `errorSummary` is the localised summary from the run's error code. It is not taken from `heartbeat_occurrences.status` or from raw `last_error`.
3. `threadId` is the tick thread of the heartbeat, or null if none exists yet.
4. Register the route in `customRoutes` of `schemaCoreModuleManifest.ts` (single-consumer read), implement the handler, add it to `routeMatrix.ts`, to `ROUTE_HANDLER_FILES` in `chokePointWriteBoundary.unit.test.ts`, and to the tenant isolation route test.
5. Tests: three user heartbeats are returned and a system one (including the new-email automation) is not; a latest run waiting for approval gives `waiting_approval`; a failed latest run gives `failed` with the localised summary; a disabled heartbeat with a failed last run returns `enabled: false` and `status: failed`; `ruleLabel` follows the system timezone setting; another tenant's project is not found.
