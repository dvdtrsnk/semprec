**Blocked by:** #1425, #1623, #1785, #1805
**Model tier:** medium

## Context

Model tier rationale: One new tenant-scoped read route that follows the existing custom-route and route-matrix pattern, but it merges two sources (stored cards and pending approvals) and must respect the tenant isolation test that has one case per surface.

The Inbox shows one stack of cards of all kinds, ordered by group: approvals, then proposals, then invalid cards, then clarifications, then transcript cards. Today a client can only read cards generically (`POST /api/databases/:id/query`, `GET /api/items/:id`), the item envelope (`backend/services/semprec-api/src/adapter/itemEnvelope.ts`) returns no relation edges, and pending approvals come from a separate `GET /api/approval-requests` (`backend/packages/data/src/mcp/approvalRequestsQueue.ts`, pending only, without the source of the run). The Inbox module (`backend/packages/data/src/inbox/inboxModuleManifest.ts`) mounts only `POST /api/proposals/:id/confirm` and `GET /api/inbox-types`. No server code decides the kind of a card; that is delivered by #1425.

This issue adds `GET /api/inbox/cards`, the single read the Inbox needs. It builds on #1425 (card kind), #1766 (the source of an approval request) and #1785 (the shared resolver behind the approval queue with a source filter, which this route reuses so both lists agree). The count (#1823), the realtime invalidations (#1811), the editor schemas (#1825) and the reject route (#1845) build on it. Other issues add fields to the card additively.

Decision: no paging. The route returns at most 200 cards and a `total` of all open cards (no speculative generality; a stack that large is already unusable).

Decision: the order inside a group is chronological by capture time (Inbox `date` and `time`), for an approval by `requested_at`, for a transcript card by the transcript's finish time (until that exists, the transcript `date`), then by id.

Decision (product owner): a card in `computing` is returned with its status so the stack shows it with a compute indication and the user sees that the capture arrived; a card in `computeFailed` is returned so the stack shows it with the state "proposal failed" and a Retry action (the client calls `POST /api/proposals/:id/recompute`, #1955), because a capture must never silently disappear. Both belong to the proposals group and are ordered there by capture time, so a card keeps its place when its computation finishes. Neither is counted in `total` until it has a proposal to decide.

Shared-file ordering: this issue also waits for #1623, #1805 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `canonical-keys`, `io-hardening` and `testing`.

1. Add `GET /api/inbox/cards` as a custom route in `inboxModuleManifest.ts` (name `listInboxCards`, `justification: "single-consumer-read"`, handler `createInboxCardsRouteHandler` exported from `inboxRouteHandlers.ts`). Tenant and user come only from the session.
2. Add the read model in a new file `backend/packages/data/src/inbox/inboxCardsStore.ts`. It returns `{ cards, total }`, where `cards` has at most 200 entries and `total` counts every open card of the set except cards in `computing` and `computeFailed`, which are listed but not counted. The set is: Processing proposals cards of kind `inbox` and `transcript` in the statuses `proposed`, `computing`, `computeFailed`, `needsClarification` and `invalid` (not confirmed, rejected or deleted), plus pending approval requests whose source is a tick or MCP (the same resolver as `GET /api/approval-requests?status=pending&source=tick,mcp`; chat approvals are not cards, and approvals of delegated runs started by a tick are included).
3. Each card has: `cardId`, `source` (`proposal` or `approval`), `cardKind` and `baseKind` (from #1425), `status`, `version` (the item's `updatedAt`, usable as `ifVersion`), the resolved source (for an inbox card the Inbox item with `id`, `text`, `date`, `time` and its `type` as `{ id, name, emoji }`; for a transcript card the transcript with `id`, `name` and `completedAt`, the finish time or until it exists the transcript date), the card's `context` property when set, `targets` as a list of `{ databaseKey, label }`, and the effective envelope. For an approval card the source is the resolved run source instead of an Inbox item. Labels of kinds and targets are localized through the Inbox i18n catalogs (`backend/packages/data/src/inbox/i18n/en.json` and `cs.json`) by `cardKind`; for pages, MCP and transcript cards the label is not a database name.
4. Order groups approval, proposed (including `computing` and `computeFailed` cards), invalid, needsClarification, transcript; inside a group as decided above.
5. Times are ISO 8601; the client composes "today" and "yesterday" using the tenant timezone exposed in the schema.
6. Add a case for the route to `backend/services/semprec-api/src/routeMatrix.ts` and to `backend/services/semprec-api/src/__tests__/tenantIsolationRoutes.test.ts` (the test "has exactly one case per surface" fails without it), including that a second tenant sees none of the first tenant's cards.
7. Tests: five cards of different states and kinds return in the group order; a confirmed, rejected or soft-deleted card, and an approval from chat, are absent; an approval from a run delegated by a tick is present; each card carries the resolved source; more than 200 open cards return 200 and the right `total`; a `computing` and a `computeFailed` card are listed in the proposals group by capture time and are not counted in `total`.

## Scope

### In scope

- The read route, its read model, ordering, resolved sources, localized labels and the isolation case.

### Out of scope

- The count route: #1823. Realtime invalidations: #1811.
- Editor schemas on cards: #1825. Reject: #1845.
- Paging and filtering by query parameters.
- The Retry action of a `computeFailed` card: the recompute route (#1955).
- Per-kind additions such as the journal entry kind (#1975) and the recording kind (#1978); they extend the card additively.

## Acceptance criteria

- Given a tenant with cards proposed, invalid, needsClarification, transcript and a pending approval from a tick, then `GET /api/inbox/cards` returns five cards in the order approval, proposed, invalid, needsClarification, transcript.
- Confirmed, rejected and deleted cards and approvals from chat are not returned.
- An approval requested by a run delegated by a tick is returned.
- An invalid task card has `cardKind` `invalid` and `baseKind` `task`; every card carries its resolved source (text, date, time and type name for an inbox card).
- A second tenant's session sees none of these cards.
- With more than 200 open cards the route returns 200 and `total` is the full count.
- A card in `computing` and a card in `computeFailed` are returned in the proposals group with their `status`, and `total` does not count them.
