**Blocked by:** #168

## Context

`GET /healthz` gates on a process heartbeat that nothing writes, so the endpoint returns 503 permanently.

This is a follow-up to #168, whose PR (#402) merged into `develop` as `0636631`. The code there is a faithful implementation of #168's Task; #168's specification was itself inconsistent with the system as it exists.

`backend/services/semprec-api/src/healthzHandler.ts:30` hardcodes the health signal to the `agents` process:

```ts
return isProcessHeartbeatFresh(client, "agents");
```

`isProcessHeartbeatFresh` (`backend/packages/data/src/health/processHeartbeats.ts:142-154`) returns `false` when no row exists for that process. `startProcessHeartbeat` is called in exactly two places on `develop`:

- `backend/services/semprec-api/src/serve.ts:78` → `process: "api"`
- `backend/services/semprec-ai-gateway/src/serve.ts:16` → `process: "ai-gateway"`

**Nothing writes an `agents` heartbeat.** The standalone agent-runtime process belongs to epic #116, and neither #169, #170 nor #171 stands it up. `backend/packages/agent-runtime/src/logger.ts:3` names a logger `agents`, but a logger label is not a process. So on any real deployment of `develop`, `GET /healthz` returns 503 unconditionally.

The decision taken is to narrow the gate rather than keep the specification: `/healthz` checks PostgreSQL plus the heartbeat of the process that serves the endpoint (`api`), and the `agents` gate moves to the issue that stands the agent-runtime process up, under epic #116. A health endpoint that cannot return 200 is a defect regardless of what a specification says.

Gating on `api`'s own heartbeat is not circular. `SELECT 1` proves the read path; the heartbeat row proves this process's background write loop has run within the stale threshold. A process serving requests whose heartbeat loop has died is genuinely unhealthy, and a liveness probe restarting it is the correct outcome.

#168's fourth acceptance criterion ("healthz checks only PostgreSQL and agents") is superseded by this issue, so the next reader does not re-derive the same conflict.

## Task

In `backend/services/semprec-api/src/healthzHandler.ts`, change the heartbeat freshness gate from the `agents` process to `api`, and correct every docstring that describes the old behaviour — including `isProcessHeartbeatFresh`'s own docstring in `backend/packages/data/src/health/processHeartbeats.ts:141`, which calls itself "`GET /healthz`'s agents-freshness check".

## Scope

### In scope

- The process name the handler gates on, and the docstrings in both files that describe it.
- The handler's existing tests, extended to cover the criteria below.

### Out of scope

- Creating an `agents` or `transcribe` process, or adding a heartbeat writer anywhere. Standing up agent-runtime as a service is epic #116's work; doing it inside a health-endpoint fix is exactly the scope expansion `docs/adr/2026-09-10-no-speculative-generality-beyond-issue-scope.md` forbids.
- Making the gated process configurable, adding a `/readyz`, or extending the response body.
- Changing the response shape, the status codes, the deliberate absence of detail in the body, or the `handleRequestSafely` wrapper. Their rationale is documented in the handler and is unaffected.
- Wiring the endpoint into any deployment, probe or monitor.

## Acceptance criteria

1. `GET /healthz` returns 200 `{"status":"ok"}` when `SELECT 1` succeeds and the `api` heartbeat is fresh.
2. `GET /healthz` returns 503 `{"status":"error"}` when the `api` heartbeat row is missing.
3. `GET /healthz` returns 503 `{"status":"error"}` when the `api` heartbeat row exists but is older than the stale threshold.
4. `GET /healthz` returns 503 `{"status":"error"}` when the database query throws, and the response body is byte-identical to every other 503 — it never reveals which check failed or why.
5. A request with a method other than `GET`, or a path other than `/healthz`, still returns 404 `{"status":"error"}`.
6. No docstring in the repository still claims `/healthz` gates on `agents`.
