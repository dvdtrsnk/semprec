## Context

`manifest_drift_findings` holds the mechanical drift reports of the heartbeat actions. `publishFinding` (`backend/packages/data/src/notifications/findings.ts:17-23`) inserts one with `ON CONFLICT (kind, dedupe_key) WHERE resolved_at IS NULL AND dedupe_key IS NOT NULL DO NOTHING`. Its arbiter is the global partial index `manifest_drift_findings_active_idx` (`backend/packages/data/src/db/migrations/0030_notifications_schema.sql:26-29`). `resolveFindingsNotIn` (`findings.ts:31-42`) resolves every active finding of a kind whose key the current run no longer reproduces.

The only caller is `moduleRegistry.checkDrift` (`backend/packages/data/src/manifest/moduleRegistryDriftCheck.ts:51-78`). Its dedupe keys are natural identifiers: unknown heartbeat action ids (`:57-65`) and orphaned `owner_process` values (`:67-75`). They coincide across tenants, because every tenant is seeded with the same modules. Under the global index, tenant B's finding for a key tenant A already reports is a silent no-op, so B never sees it.

`core.driftCheck` inserts with no `dedupe_key` (`backend/packages/data/src/manifest/driftCheck.ts:80-83`). Neither index covers that insert, so it is unchanged here.

What earlier issues provide:
- `manifest_drift_findings` has `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)`.
- Row-level security on it keeps the RESTRICTIVE `tenant_isolation` policy `USING/WITH CHECK (tenant_id = (SELECT app_tenant_default()))`.
- The SQL functions behind both:
  - `app_current_tenant()` = `NULLIF(current_setting('app.tenant_id', true), '')::uuid`;
  - `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())` until #1067.
- The policy already confines `resolveFindingsNotIn`'s `UPDATE` to the current tenant's rows for every runtime role. Runtime roles are not superuser and do not own the table.
- #974 added `manifest_drift_findings_tenant_active_idx ON manifest_drift_findings (tenant_id, kind, dedupe_key) WHERE resolved_at IS NULL AND dedupe_key IS NOT NULL` beside the legacy one.
- The legacy index stays until #1065 drops it, which needs this writer on the new arbiter first.

While the legacy index exists, a publish that collides only with it raises `unique_violation` (`23505`) and does not silently do nothing. That collision is a second tenant reporting a key another tenant has active. Production has one tenant until after #1065, so only tests can reach it.

The change is code only. The previous release's conflict target is still satisfied by the legacy index.

## Task

Load `state-writes` (an upsert arbiter and a set-based resolve) and `error-handling` (the transitional collision must surface).

1. **Conflict target.** In `publishFinding`, change the conflict target to `ON CONFLICT (tenant_id, kind, dedupe_key) WHERE resolved_at IS NULL AND dedupe_key IS NOT NULL DO NOTHING`.
   - Do not add `tenant_id` to the column list: the default fills it from the scope.
   - Confirm in #974's migration that `manifest_drift_findings_tenant_active_idx` has exactly these columns and this predicate. Postgres infers the arbiter from both.
2. **Resolve stays as is.** Keep the SQL of `resolveFindingsNotIn` unchanged.
3. **Docstrings.**
   - In `findings.ts:10-16` and `findings.ts:25-30`, the dedupe is per tenant. The resolve touches only the current tenant's findings, through row-level security. A legacy-only collision raises `23505`.
   - In the comment at `moduleRegistryDriftCheck.ts:46-49`, the key is `(tenant, kind, dedupeKey)`.
4. **Tests.** Add `backend/packages/data/src/__tests__/findings.test.ts`. The two-tenant cases run inside one transaction opened with `withTransaction` on the superuser test pool. The test makes it roll back by throwing a sentinel error it then catches. Inside that transaction:
   - `DROP INDEX IF EXISTS tenants_single_tenant_guard`;
   - insert a second `tenants` row with `status = 'active'`;
   - switch tenants with `SELECT set_config('app.tenant_id', $1, true)`;
   - run the runtime-role steps after `SET LOCAL ROLE semprec_side` and `RESET ROLE` before superuser assertions. `semprec_side` has DML on `manifest_drift_findings`: `backend/packages/data/src/db/migrations/0040_least_privilege_roles.sql:71-81`.
   - for the post-drop case, `DROP INDEX manifest_drift_findings_active_idx`.

## Acceptance criteria

- **Replay.** Publishing the same `(kind, dedupeKey)` twice in one tenant leaves exactly one active row. (integration, `findings.test.ts`)
- **Same key in two tenants.** Inside the rolled-back transaction with `manifest_drift_findings_active_idx` dropped, tenant B publishes a `(kind, dedupeKey)` that tenant zero has active:
  - B gets its own active row with B's `tenant_id`;
  - tenant zero's row is unchanged.

  (integration, `findings.test.ts`)
- **Legacy collision.** With `manifest_drift_findings_active_idx` still present, tenant B's publish of that same key rejects with Postgres code `23505`. It is not a silent no-op. (integration, `findings.test.ts`)
- **Resolve isolation.** Tenant zero has an active finding for key X, and tenant B has one for key Y of the same kind. `resolveFindingsNotIn(kind, ∅)` runs as `semprec_side` in tenant B. Afterwards B's Y is resolved and tenant zero's X is still active. (integration, `findings.test.ts`)
- **Scope-less.** With no scope and only tenant zero present, `backend/packages/data/src/__tests__/moduleRegistryDriftCheck.test.ts` passes unchanged. (integration)
