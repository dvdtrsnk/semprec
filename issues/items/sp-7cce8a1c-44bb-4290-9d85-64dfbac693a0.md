### Requirement gh-1620: [semp-threads 11/19] Accept Semp chat messages over HTTP

#### Context

The existing durable Semp thread/message and read-route owners now gain transactional HTTP send admission and queued replies.



The closed error contract (`services/semprec-api/src/adapter/errorContract.ts`, `ITEM_ERROR_CODES`) has no code for a message to an already decided Inbox proposal. `reviseProposalWithClient` currently raises a plain `ValidationError` (400) for locked proposals (`LOCKED_PROPOSAL_STATUSES` = confirmed, rejected). Decisions: (1) a message to a thread whose proposal is confirmed or rejected is refused with 409 `proposal_locked`; the thread of a processed Inbox item can still be opened and read through the read routes of #1543, so it is read-only; (2) the "Semp wants to approve" card is not an Inbox item, so no item thread exists for it, and a `subject` that is not an existing Inbox item is a 400; (3) the user may keep talking in a thread that shows a pending approval card: a message to such a thread is accepted like any other and the card stays in the thread. An approval is decided only on the card or in the approval list, never by the text of a message: sending a message never approves, rejects or otherwise changes a pending approval request.

Builds on this: #1682 validates and stores refs in `context`, #1938 loads card context, #1727 consumes the job, #1906, #1734, #1669 and #1853 extend the same route.

Shared-file ordering: this issue also waits for #1616 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

Batch31 reconciliation: queued is the existing durable assistant status from migration0087. Task3 permits text-only messages to existing tick threads because the later included gh1731 explicitly requires user questions there; context remains forbidden on item and tick threads. This narrows the earlier send-only tick refusal and adds no new thread kind or ref expansion.

Item sends follow docs/adr/2026-11-06-inbox-thread-sends-reserve-current-proposals.md: source first, current sourceInbox cards locked NOWAIT, then thread reservation/recheck. Stored or supplied proposalId is not authority. Contention is 409 version_conflict without writes; decided current cards remain 409 proposal_locked.
