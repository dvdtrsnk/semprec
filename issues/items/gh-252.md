**Blocked by:** #88, #115, #121, #152, #158, #173

## Context

The generic data facade is not exposed to agents or MCP callers. The agent runtime package is currently empty, so the claim that UI, API clients, agents, and MCP clients use one choke-point path is not yet true. Before any adapter can exist, the operation catalog itself must become transport-independent data: one closed set of operation descriptors, strict input schemas, a port declaring every method, and one binding table over them.

This first part delivers exactly that data layer inside `packages/shared`. It adds no implementation and changes no runtime behavior: nothing calls the bindings yet. Issue #219 then adds the single neutral implementation in `packages/application` and rebases the REST adapter of #158/#37 onto these bindings; #220 builds the AgentTool and MCP adapters, capability registration/filtering, actor derivation, and the approval interceptor on top of these descriptors; #89 adds the snapshot-bound exactly-once approval execution protocol.

## Task

Create the canonical operation descriptors in `packages/shared/src/genericOperations`. The closed 28-operation catalog is: `database.list`, `database.get`, `database.create`, `database.patch`, `database.archive`, `database.restore`, `property.list`, `property.get`, `property.create`, `property.patch`, `property.delete`, `view.list`, `view.get`, `view.create`, `view.patch`, `view.delete`, `view.query`, `viewItem.add`, `viewItem.remove`, `viewItem.reorder`, `item.get`, `item.create`, `item.patch`, `item.delete`, `item.restore`, `database.query`, `relation.put`, and `relation.delete`. Binary files are excluded. (#220 uses these names verbatim as AgentTool names and, prefixed `semprec.`, as MCP names.)

Extract #37's domain-command validators into transport-independent Zod schemas exported from `packages/shared/src/genericOperations/schemas.ts`. Define `GenericApplicationPort` beside them in `packages/shared/src/genericOperations/port.ts`; it declares the 28 methods/results below without importing any service package. `OperationBinding<I,O> = { input: ZodType<I>; invoke(service: GenericApplicationPort, actor: AuthenticatedActor, input: I): Promise<O> }`; bindings live in `packages/shared`, depend only on the port, and the API/AgentTool/MCP composition roots inject the implementation (REST in #219; AgentTool/MCP in #220). The canonical `GENERIC_OPERATION_BINDINGS` must have exactly this mapping (schema name / port method / result):

```text
database.list     DatabaseListInputSchema     listDatabases          Page<Database>
database.get      DatabaseGetInputSchema      getDatabase            Database
database.create   DatabaseCreateInputSchema   createDatabase         Database
database.patch    DatabasePatchInputSchema    patchDatabase          Database
database.archive  DatabaseArchiveInputSchema  archiveDatabase        Database
database.restore  DatabaseRestoreInputSchema  restoreDatabase        Database
property.create   PropertyCreateInputSchema   createProperty         Property
property.list     PropertyListInputSchema     listProperties         Property[]
property.get      PropertyGetInputSchema      getProperty            Property
property.patch    PropertyPatchInputSchema    patchProperty          Property
property.delete   PropertyDeleteInputSchema   deleteProperty         { deleted: true, propertyId }
view.list         ViewListInputSchema         listViews              Page<View>
view.get          ViewGetInputSchema          getView                View
view.create       ViewCreateInputSchema       createView             View
view.patch        ViewPatchInputSchema        patchView              View
view.delete       ViewDeleteInputSchema       deleteView             { deleted: true, viewId }
view.query        ViewQueryInputSchema        queryView              ItemPage
viewItem.add      ViewItemAddInputSchema      addViewItem            ViewItem
viewItem.remove   ViewItemRemoveInputSchema   removeViewItem         { deleted: true, viewId, itemId }
viewItem.reorder  ViewItemReorderInputSchema  reorderViewItem        ViewItem
item.get          ItemGetInputSchema          getItem                Item
item.create       ItemCreateInputSchema       createItem             Item
item.patch        ItemPatchInputSchema        patchItem              Item
item.delete       ItemDeleteInputSchema       deleteItem             Item
item.restore      ItemRestoreInputSchema      restoreItem            Item
database.query    DatabaseQueryInputSchema    queryDatabase          ItemPage
relation.put      RelationPutInputSchema      putRelation            RelationEdge
relation.delete   RelationDeleteInputSchema   deleteRelation         { deleted: true, relationPropertyId, callerItemId, targetItemId }
```

`Page<T> = { items: T[]; nextCursor: string | null }`; `ItemPage = Page<Item>`. `Database`, `Property`, `View`, `ViewItem`, `Item`, and `RelationEdge` are the authoritative shared row schemas returned by the data/application layer, with `Item` fixed to `{ id, databaseId, properties, computed, updatedAt, deletedAt }` and `RelationEdge` fixed by #82. List/query schemas contain `{ cursor?: string, limit?: number }` with default 50/max 200; queries additionally contain #37's filter/sort/inTrash tree and the relevant `databaseId` or `viewId`. Get/archive/delete/restore schemas contain only the named resource id, so `DatabaseRestoreInputSchema = { databaseId: string }`, `PropertyListInputSchema = { databaseId: string }`, and `PropertyGetInputSchema = { propertyId: string }`; their port methods return authoritative raw `Property[]`/`Property` rows so agents can discover relation property ids. Metadata command schemas are exact strict objects:

```ts
DatabaseCreateInput = { name: string; parentItemId?: string };
DatabasePatchInput = { databaseId: string; patch: { name?: string } };
PropertyCreateInput =
  | { databaseId: string; key: string; name: string; type: Exclude<PropertyType, 'relation'>; config?: Record<string, unknown> }
  | { databaseId: string; key: string; name: string; type: 'relation'; targetDatabaseId: string;
      cardinality: 'one_to_one' | 'one_to_many' | 'many_to_many'; locked: boolean;
      inverse?: { key: string; name: string; locked: boolean } };
PropertyPatchInput = { propertyId: string; patch: { name?: string; type?: PropertyType; config?: Record<string, unknown> } };
ViewCreateInput = { databaseId?: string | null; type: string; name: string; config?: Record<string, unknown>; isDefault?: boolean };
ViewPatchInput = { viewId: string; patch: { name?: string; config?: Record<string, unknown>; isDefault?: boolean } };
```

External metadata schemas never accept system/ownership fields (`system`, `schemaLocked`, `ownerProjectItemId`, `ownerModuleId`, `owner`, `ownerProcess`, `locked`, `createdBy`, `creatorProjectItemId`); those are server-derived or protected internal operations. Metadata updates have no `ifVersion` because #37 defines optimistic concurrency only for item property patches. `ItemCreateInputSchema` is `{ databaseId, properties, idempotencyKey?: string }`; omission preserves #21/#37's non-retry create behavior, while a supplied key activates dedup. `ItemPatchInputSchema` is `{ itemId, properties, ifVersion }`. View-item inputs are `{ viewId, itemId }`, with add/reorder additionally requiring `position: number`. `RelationPutInputSchema` is #82's `CreateRelationInput` and therefore performs idempotent create/full metadata replacement; delete is the same input without metadata and is idempotent. Delete wrapper results above are adapter results; underlying idempotent void deletes are called exactly once.

The relation branch of `PropertyCreateInput` is the sole exception to the ban on external `locked`: its source and inverse `locked` booleans are required. The exact property patch type supersedes the broader code-block shorthand: `PropertyPatchInput = { propertyId: string; patch: { name?: string; type?: Exclude<PropertyType, 'relation'>; config?: Record<string, unknown> } }`; a non-relation therefore cannot transition to relation through patch, and relation-definition changes require #82's protected path and are outside this catalog. The runtime rejections these shapes imply — `400 validation_failed` with `{ reason: 'empty_patch' }` for empty patch objects, and `{ field: 'type' | 'config', reason: 'relation_definition_required' }` when the stored property is `relation` while rename remains allowed — are surfaced by the service and adapter in #219.

Declare the port without argument-order freedom: for every mapping row `K`, its named method has signature `(actor: AuthenticatedActor, input: InputByOperation[K]) => Promise<OutputByOperation[K]>`. `InputByOperation` and `OutputByOperation` are exhaustive mapped types keyed by the 28 literal operation names and reference the exact named input schemas/results in the table; delete outputs are exactly the wrapper objects shown there. The binding `invoke` always calls `service[method](actor, input)` in that order.

Define one shared actor shape: `AuthenticatedActor = { userId: string; runId?: string; agentProjectItemId?: string }`. REST human actors are derived from the authenticated session context and omit the agent fields (#219). External schemas reject all three identity fields. (Agent-side derivation of `runId`/`agentProjectItemId` and its consumption by #87 is delivered by #220.)

All binding schemas are strict objects. Actor/session/runtime identity is excluded from external schemas and injected server-side by the authenticated adapter. Inputs containing `actor`, `agentProjectItemId`, `userId`, or equivalent identity fields therefore fail validation and cannot influence authorization. Use the evolved shared `{ code, details }` domain-error union from #37 plus predecessor additions, explicitly including #83's `database_archived`; per-transport parity tests over that union are added by the consumers (REST in #219, MCP/AgentTool in #220).

Each operation descriptor contains its one literal `requiresCapability`, using this exhaustive mapping: `core.database.read` for `database.list`, `database.get`, `database.query`; `core.database.write` for `database.create`, `database.patch`, `database.archive`, `database.restore`; `core.schema.read` for `property.list`, `property.get`; `core.schema.write` for `property.create`, `property.patch`, `property.delete`; `core.view.read` for `view.list`, `view.get`, `view.query`; `core.view.write` for `view.create`, `view.patch`, `view.delete`, `viewItem.add`, `viewItem.remove`, `viewItem.reorder`; `core.item.read` for `item.get`; and `core.item.write` for `item.create`, `item.patch`, `item.delete`, `item.restore`, `relation.put`, `relation.delete`. These eight ids are pure descriptor data in `packages/shared` here; registering them in the core ModuleRegistry manifest and filtering discovery by grants is #220.

Every descriptor also has exact approval metadata. Reads (`database.list/get/query`, `property.list/get`, `view.list/get/query`, `item.get`) and reversible/non-destructive writes (`database.create/patch/restore`, `property.create/patch`, `view.create/patch`, all `viewItem.*`, `item.create/patch/restore`, `relation.put`) use `requiresApproval: false, riskClass: null`. Destructive operations `database.archive`, `property.delete`, `view.delete`, `item.delete`, and `relation.delete` use `requiresApproval: true, riskClass: 'destructive'`. This exhaustive mapping has one row for all 28 operations and is compile-time checked with the capability mapping. No approval enforcement happens in this batch position; the interceptor consuming this metadata is #220.

Add dependency rules rejecting imports from `packages/shared` to `services/*`. The final catalog is exactly 28 operations.

## Scope

### In scope

- `packages/shared/src/genericOperations`: the 28-operation catalog, `schemas.ts`, `port.ts`, `OperationBinding`, `GENERIC_OPERATION_BINDINGS`, the `AuthenticatedActor` shape, and capability and approval/risk metadata as data.
- The dependency rule forbidding `packages/shared` → `services/*` imports.
- Compile-time exhaustiveness assertions and parameterized tests over the descriptors and the binding table.

### Out of scope

- The `GenericApplicationPort` implementation in `packages/application`, the REST adapter rebase, relation property-key resolution, `POST /api/databases/:id/restore`, property list/get routes, and the REST contract/parity tests; #219 delivers these.
- AgentTools, `POST /mcp`, ModuleRegistry capability registration/filtering, agent actor derivation and `agent_runs.actor_user_id`, and the approval interceptor, delivered by #220.
- Snapshot-bound exactly-once approval execution, delivered by #89.
- Third-party MCP server transports, owned by #31.
- Domain-specific tools or a second persistence API.

## Acceptance criteria

- A compile-time exhaustiveness assertion and a parameterized runtime test prove that the binding table contains exactly the 28 rows and each row uses the named schema, service method, and result contract above.
- A parameterized test proves every descriptor carries exactly the `requiresCapability` and `requiresApproval`/`riskClass` values above, compile-time checked together.
- Spoofed `actor`/`userId`/`agentProjectItemId` fields and system/ownership fields fail schema validation, and every binding schema is a strict object.
- The port's mapped types are exhaustive over the 28 literal names, and a type-level test proves each method's `(actor, input)` order and result type.
- Dependency rules reject imports from `packages/shared` to `services/*`.
- `packages/shared` builds and the existing test suites stay green; no runtime behavior changes, because nothing consumes the bindings yet.
