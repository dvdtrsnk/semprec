## Context

**This issue is maintainer-implemented and must never be labelled `agent:ready`.** It is a release gate: Relay merges continuously, but releases are promoted and deployed by the maintainer, and the steps after this one are only safe against a release that is already running in production.

Every contract and enforcement step of this epic — legacy-envelope rejection (#1061), dropping the legacy global unique keys (#1065), composite foreign keys (#1066) and the strict switch (#1067) — relies on the one-release rollback rule: `deploy.sh --rollback` starts the previous release against the new schema and nothing is unwound (`docs/operations/migrations.md`, `docs/adr/2026-09-24-rollback-one-release-back-with-checked-migrations.md`). Those steps are therefore only safe once the release *before* them already carries the tenant scope on every path. While exactly one tenant exists, `app_tenant_default()` falls back to that sole tenant, so a missed path is invisible in behaviour; the only evidence is the warn-mode log event `tenant_scope_missing` that #978 emits at warn level, with the stack, the first time each distinct code path queries without a scope while `SEMPREC_TENANT_SCOPE` is unset or `warn`; #982 likewise logs `tenant_task_without_tenant` whenever a tenant job runs on its sole-tenant fallback.

The blockers proved isolation in tests: the startup role assertion (#1051) and the exhaustive REST/MCP (#1053), realtime (#1054) and background (#1056) suites; the AI gateway suite (#1057) must be green on the same release. This checkpoint proves the same release in production. Service logs go to journald with 90-day retention (`deploy/systemd/journald-semprec.conf`); releases are tagged with `pnpm --filter @semprec/release run release-tag` and deployed with `deploy/deploy.sh <tag>` (`docs/operations/releases.md`).
