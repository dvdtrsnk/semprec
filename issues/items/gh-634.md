## Context

`GET /api/blobs/:id` in `backend/services/semprec-api/src/blobsHandler.ts` streams the file with `stream.pipe(res)` (line 183) after registering `stream.once("error", ...)` (lines 165-172). `Readable.prototype.pipe` unpipes when the destination closes but never destroys the source: when the client disconnects mid-download, `res` emits `close`, the `fs.ReadStream` returned by `LocalFsBlobStorageWriter.readStream` (`backend/packages/data/src/mail/blobStorage.ts`, line 103) is left paused and open, and its file descriptor is released only when the stream object is garbage-collected — if ever, since nothing references it after `pipe` unpipes it. Under repeated aborted downloads (a gallery scrubbing through large media, a flaky mobile link) the process accumulates open descriptors until `EMFILE`. `stream.pipeline` exists for exactly this: on premature close of either side it destroys the other and reports `ERR_STREAM_PREMATURE_CLOSE`.

Sibling B7 of this batch edits a different region of the same file (the `blobId` extraction at the top of `handleRequest`).

## Task

- In `blobsHandler.ts`, replace the `stream.once("error", ...)` listener and `stream.pipe(res)` with `pipeline(stream, res, (err) => { ... })` from `node:stream` (callback form; the handler must not `await` the download, since `handleRequest` returns once headers are written and `handleRequestSafely` only guards the pre-stream phase). In the callback:
  - `err` undefined → nothing (normal completion).
  - `err` with `code === "ERR_STREAM_PREMATURE_CLOSE"` → the client went away; log at `debug` level with `{ blobId }`, no response action (`pipeline` has already destroyed both streams).
  - any other `err` → `logger.error({ err: streamErr, blobId }, "Error streaming blob")` as today, then `res.destroy()` (headers have always been written by this point, since `res.writeHead` precedes `pipeline`).
- Keep `res.writeHead(200 | 206, headers)` exactly where it is, before the pipeline starts, so `Content-Length`/`Content-Range` semantics are unchanged.
- Test: new `backend/services/semprec-api/src/__tests__/blobsHandlerAbort.test.ts` (integration tier — it needs a real `blobs` row and a session). Build the listener directly with `createBlobsRequestListener(pool, { storage })`, where `storage` is a `BlobStorageWriter` whose `readStream` returns a `PassThrough` (`node:stream`) that has written one chunk and is never ended, recording the instance; `writeStream`/`delete` can throw "not used". Insert a blob row with `createBlob` from `@semprec/data` (`byteSize` larger than the chunk), authenticate with a native-session bearer token (as `filesAndBlobsHandler.test.ts` does), start `fetch` with an `AbortController`, wait until the response headers arrive, call `abort()`, then poll until `passThrough.destroyed === true` (bounded, e.g. up to 2 s). Add a second case that a complete download still ends the stream normally (`passThrough.end()` after the chunk → the body equals the chunk, `destroyed` is true after completion).

### In scope

### Out of scope

- `POST /api/files` upload streaming (`filesHandler.ts`), which already uses its own guarded write path.
- Any change to `LocalFsBlobStorageWriter` or the `BlobStorageWriter` interface.
- Range parsing, ETag or Content-Disposition behaviour (covered by `filesAndBlobsHandler.test.ts`, unchanged).

## Acceptance criteria

- When a client aborts a `GET /api/blobs/:id` download after headers are received, the storage read stream reports `destroyed === true` within the test's bound, and the server logs nothing at `error` level.
- When a download completes, the body is intact and every existing case in `filesAndBlobsHandler.test.ts` (full download, `206` range, `304`, `416`, disposition and filename cases) passes unchanged.
- When the read stream itself errors after headers were sent, the response socket is destroyed and the error is logged, as today.
- `grep -n "\.pipe(" backend/services/semprec-api/src/blobsHandler.ts` returns nothing.
