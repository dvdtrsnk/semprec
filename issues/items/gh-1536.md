**Model tier:** medium

## Context

Model tier rationale: One mechanism (a Tasks pre-write transform with validation) across existing choke-point seams and test fixtures, but it changes the write path of every Tasks item and rejects input that is accepted today, so it is not low.

Today Tasks values are not checked. In `backend/packages/data/src/chokePoint/itemWrites.ts` the derived `time` is computed inline by an `ownerModuleId === TASKS_MODULE_ID` branch in both `createItemWithClient` and `updateItemWithClient` (`tasks/deriveTaskTime.ts`), and the update branch locks the row only when `timeFrom` or `timeTo` is in the patch. Nothing validates the value types: `"9:00"`, `""`, `"25:99"`, `timeTo` without `timeFrom`, `timeFrom` without `date` and an empty `name` are all stored, and `deriveTaskTime` returns the bare `timeTo` when `timeFrom` is null. The only HH:MM pattern in the codebase is the non-exported `timeOfDay` constant in `scheduler/rule.ts` (00:00 to 23:59). PATCH requires `ifVersion` (409 on mismatch).

#1422 adds a per-module pre-write property transform to the choke point (`registerItemPreWriteTransform`), which receives the resulting state of a write and returns the patch to persist, with update hooks, heartbeat triggers and rollup recompute seeing the prepared patch. This issue registers the Tasks transform on it. The transform is built up across several issues; this one owns the derivation of `time`, the time normalization and the validation rules below. Later issues add their own steps to the same transform: `completedOn`/`completedAt` (#1544), `since` (#1602) and the `missed` status (#1668). Events get the same time normalization from #1598, which uses the helper this issue introduces. Stored data written before this rule is repaired by #1657.

Product rules this enforces:

- A task's date is optional. Switching the date off clears the start time, the end time and the derived time in the same write. A start time is allowed only with a date; no start time means an all-day task. An end time is allowed only with a start time, must be later than the start time, and may be `24:00`. The derived `time` is `HH:MM` or `HH:MM–HH:MM`.
- A title cannot be blank.

Decision: an end time equal to the start time is rejected with 400 (field `timeTo`) and is not silently turned into null. Any earlier rule or note that says the opposite is superseded.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `normalizeWallClockTime(value, { allow2400 })` to `backend/packages/data/src/timezone.ts`. It accepts `H:MM` and `HH:MM`, returns zero-padded `HH:MM`, maps `""` to null, accepts `24:00` only when `allow2400` is true, and throws `ValidationError` with the caller's field for anything else (`25:99`, `abc`). Export it from the package for #1598.
2. Create `backend/packages/data/src/tasks/taskPreWriteTransform.ts` and register it for the Tasks database through the interface from #1422. Remove the inline Tasks branches for `time` in `itemWrites.ts` so the derivation exists in exactly one place; `deriveTaskTime` stays and is called from the transform. The transform judges the resulting state (current stored values merged with the patch) and applies:
   - `name` must be non-empty after trimming; otherwise 400 `validation_failed` with field `name`. The value is not rewritten.
   - `date` must be a real calendar date `YYYY-MM-DD` (`2026-02-30` is rejected); `""` becomes null.
   - `timeFrom` and `timeTo` are normalized with the helper (`timeTo` with `allow2400`).
   - `timeFrom` without `date` is rejected (field `timeFrom`).
   - `timeTo` without `timeFrom`, or `timeTo` not later than `timeFrom`, is rejected (field `timeTo`).
   - When the resulting `date` is null, the same write sets `timeFrom`, `timeTo` and `time` to null.
   - `time` is derived from the normalized times.
   Errors use the existing `ValidationError` contract (400, `validation_failed`, `field`); a rejected write stores nothing.
3. Update the ADR amendment obligations that #1422 defines for the Tasks exception, if that issue left a Tasks-specific note to update; otherwise add none.
4. Tests (real database): the acceptance cases below, on create, on PATCH, and through replay of an idempotent create.

## Acceptance criteria

- When a task is PATCHed with `timeFrom` `"9:00"` (and a date), then `timeFrom` is stored as `"09:00"` and `time` as `"09:00"`.
- When `{timeFrom: "10:00"}` is sent for a task without a date, or `{name: "  "}`, or `{date: "2026-02-30"}`, then the response is 400 and nothing is stored.
- When `{timeTo: "15:00"}` is sent without a start time, or `{timeFrom: "10:00", timeTo: "09:30"}`, or `{timeFrom: "23:55", timeTo: "23:55"}`, then the response is 400 with field `timeTo`.
- When `{timeFrom: "23:55", timeTo: "24:00"}` is sent with a date, then it is accepted and `time` is `"23:55–24:00"`.
- When `{date: null}` is sent for a task on 13 October 10:00 to 11:00, then `date`, `timeFrom`, `timeTo` and `time` are all null afterwards.
- When a task is created with the same payload and the same Idempotency-Key twice, then the second call returns the first item and validation does not run a second write.
