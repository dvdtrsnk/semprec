## Context

Model tier rationale: One migration plus a deterministic annotation-to-classification mapping inside the existing sync upsert, but it changes which writer owns two user-visible safety columns, so the provenance rules need careful tests.

Today every synced MCP tool is registered with the column defaults of `mcp_tool_registrations` (`risk_class` is `unclassified`, `requires_approval` is true), so every tool asks for approval until a human reclassifies it, and a read-only tool is treated like a destructive one. The server already tells us more: the MCP `tools/list` response carries annotations (`readOnlyHint`, `destructiveHint`, `openWorldHint`), but `listAllTools` and `validateListedTools` in `backend/packages/data/src/mcp/mcpSync.ts` read only `name`, `description` and `inputSchema`, and `upsertMcpToolRegistration` (`mcpToolRegistrationsStore.ts`) never writes the two classification columns. `reclassifyMcpTool` and `PATCH /api/mcp-tool-registrations/:id` are the only writers, and they are per registration, so a setting applies to every project.

This issue derives a default classification from the annotations when a sync creates a registration, and records who set the classification so that a later sync never overwrites a person's choice.

Annotations are hints from the server, not guarantees, so they only choose the default. The closed set of risk classes (`unclassified`, `read`, `write`, `destructive`, `outbound`, `breaksLink`) is owned by #1423; this issue imports that set and does not define classes. The sync is triggered by the sync route #1972 and by the queued sync after a confirmed MCP server proposal #1976; both call `syncMcpServerTools`, which is where this change lives, so both get it.

Mapping, evaluated in this order for a tool whose `annotations` object is present:

1. `readOnlyHint` is true: `riskClass` `read`, `requiresApproval` false.
2. Otherwise `destructiveHint` is not explicitly false (the MCP default is true): `destructive`, `requiresApproval` true.
3. Otherwise `openWorldHint` is explicitly true: `outbound`, `requiresApproval` true.
4. Otherwise: `write`, `requiresApproval` true.

A tool with no annotations at all stays `unclassified` with `requiresApproval` true.

Decision: `openWorldHint` counts only when explicitly true (the MCP default is also true, but treating an absent value as outbound would classify nearly every tool that way and make the class meaningless).

Decision: a registration is re-derived by later syncs only while its `classification_source` is `annotation`; the first manual change through the existing PATCH sets it to `manual`, and a `manual` registration is never rewritten by a sync. Existing rows are backfilled conservatively: a row that still has the defaults (`unclassified` and `requires_approval` true) becomes `annotation`, every other row becomes `manual`, so nothing a person may have set is lost.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_<name>.sql (next free ordinal at commit time)`: add `classification_source text NOT NULL DEFAULT 'annotation' CHECK (classification_source IN ('annotation', 'manual'))` to `mcp_tool_registrations`; backfill existing rows as described above in the same file. Additive and rollback-safe.
2. In `mcpSync.ts`, read `annotations` from each listed tool (keep only the three boolean hints, ignoring anything else), carry them through `validateListedTools`, and pass the derived `riskClass` and `requiresApproval` to the upsert.
3. In `mcpToolRegistrationsStore.ts`, extend `upsertMcpToolRegistration` with optional classification input: on insert, write it; on conflict, update `risk_class` and `requires_approval` only `WHERE classification_source = 'annotation'`; never touch a `manual` row.
4. Put the mapping in a pure function (`classifyMcpToolFromAnnotations`) in a new file `backend/packages/data/src/mcp/mcpToolAnnotationClassification.ts`, typed with the class set from #1423.
5. In `mcpGrantsAdminStore.ts`, make `setMcpToolRiskClass` and `setMcpToolRequiresApproval` also set `classification_source = 'manual'`.
6. Tests: mapping table, new registration, re-sync of an `annotation` row, re-sync of a `manual` row, and the backfill.

## Scope

### In scope

- The `classification_source` column, the annotation mapping, and the sync and manual-write rules.

### Out of scope

- Defining or changing the set of risk classes and their labels: #1423.
- A per-project override of `requires_approval`: decided not in v1; v1 has only the one global setting on the tool.
- Labels for tools: #1391 and #1983.
- Any new sync entry point: #1972 and #1976.

## Acceptance criteria

- When a sync sees a new tool with `readOnlyHint: true`, then it is stored as `read` with `requiresApproval` false; with `destructiveHint: true`, as `destructive` with approval; with only `openWorldHint: true`, as `outbound`; with annotations present but none of these, as `write`; with no annotations, as `unclassified` with approval.
- When a person changes a tool's class or approval through `PATCH /api/mcp-tool-registrations/:id`, then its `classification_source` is `manual` and the next sync leaves both columns unchanged.
- When a server later changes a hint on a tool whose source is still `annotation`, then the next sync updates the classification.
- When the migration runs on a database with existing registrations, then untouched defaults become `annotation` and all others `manual`; running it twice changes nothing.
