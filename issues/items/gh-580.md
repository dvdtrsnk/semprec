**Blocked by:** #569, #571, #573, #578

## Context

This is the last deterministic step of Relay's `triage-review-followups` workflow in the review follow-ups pipeline (epic #565, T6). After the triage agent's proposal passes #578's validator, **publish** turns it into GitHub state as the Relay App (`bb-agent-relay[bot]`), through Relay's token proxy (#573's `clientFromEnv` reads the proxy's `GITHUB_API_URL` / `GITHUB_GRAPHQL_URL` / `GITHUB_TOKEN` / `GITHUB_REPOSITORY`). The workflow that runs it is a later, maintainer-implemented issue. A publish failure parks the run for a human instead of retrying, and the next attempt restarts from the `prepare` step, which drops every finding already published. So publish must write its ledger markers as it goes, and must refuse to publish a finding that is already in the ledger.

What it builds on:

- #569 `markers.mjs`:
  - `LABELS` (`followups:issue`, `spec:proposed`, `followups:ready`);
  - `renderFindingMarker`, `renderEpicMarker`, `renderResultMarker`;
  - `computeLedger(issues)` → `{ terminal, epics, … }`. `epics` maps a harvest number to its epic's issue number.
- #571 `input-file.mjs`: `parseInputFile`.
- #573 `github.mjs`: `listIssuesWithLabel`, `getIssue`, `listIssueComments`, `createIssue` (→ `{ number, id }`), `addSubIssue(parentNumber, childId)` (the child's numeric `id`), `createComment`, `removeLabel` (a 404 counts as done), `closeIssue`.
- #578 `validate.mjs`: `validateProposal(input, proposal)` → violations. It is also the reference for the proposal format:
  - `{ version, harvestIssue, epic: null | { title, body }, issues: [{ id, title, body, findings: [{ pr, key }] }], rejected: [{ pr, key, verdict, reason, trackedBy? }], advisories: string[] }`;
  - drafts are in topological order and refer to each other as `{{draft:<id>}}`.

The epic, per `.github/ISSUE_FORMAT.md`, never lists its issues. They are linked as GitHub sub-issues, which also lets `close-completed-epics.yml` close it when they are all done. The human then approves each proposed issue by swapping `spec:proposed` for `spec:approved` + `agent:ready`. Nothing here arms anything.

## Task

Create `.github/scripts/review-followups/publish.mjs`, a zero-dependency ES module and CLI with a header comment describing the write order and why it is safe to restart from `prepare`:

1. Export `publishProposal(api, { input, proposal })`. `api` bundles the #573 endpoints listed above, bound to a client. With `H = proposal.harvestIssue`, it does this, in order:
   1. It throws, writing nothing, when `validateProposal(input, proposal)` returns any violation. The error lists them.
   2. It computes `computeLedger` over every `followups:issue` issue (any state) plus issue `H` with its comments. It throws, writing nothing, when any `(pr, key)` of the proposal is in `terminal`: the proposal is stale and the run must restart from `prepare`.
   3. It renders the triage-result comment (item 2 below) with every issue number shown as `#999999`, and throws, writing nothing, when that exceeds 60,000 characters.
   4. **Epic**, when `proposal.epic` is non-null: it reuses `ledger.epics.get(H)` when present. Otherwise it creates the epic with the epic's title and its body followed by a blank line and `renderEpicMarker(H)`, labelled `followups:issue`.
   5. **Drafts**, in array order. For each draft:
      - it replaces every `{{draft:<id>}}` with `#<number>` of the issue already created for that id;
      - it appends a blank line and one `renderFindingMarker` line per finding;
      - it creates the issue with the draft's title, labelled `followups:issue` and `spec:proposed`;
      - when there is an epic, it links the new issue as a sub-issue of the epic by its `id`;
      - it prints `created #<number> <title>` as soon as each issue exists.
   6. **Result comment.** When the proposal has at least one draft or rejection, it posts the triage-result comment on `H`.
   7. It removes `followups:ready` from `H` and closes `H` as completed.

   It returns `{ epic, created: [{ id, number }], rejected }`, where `epic` is a number or `null` and `rejected` is a count.
2. The triage-result comment. Its first line is `renderResultMarker(H)`. It continues with:
   - `### Triage result`;
   - the epic as `Epic: #<n>`, when there is one;
   - a list of the created issues as `- #<n> <title>`;
   - `#### Rejected (<count>)`: a table of PR, key, verdict, reason and `trackedBy`, or `None.`;
   - one `renderFindingMarker` line per rejected finding, each on its own line;
   - `#### Advisories`: the advisories as a list, or `None.`.

   In table cells, `|` is escaped as `\|`, newlines become spaces and `<` becomes `&lt;`. A reason is clipped to 1,000 characters.
3. Export `main(argv, api)`, called only when the module is executed directly, with the command line `node publish.mjs --input <input.json> --proposal <proposal.json>`. It parses both files (`parseInputFile`, `JSON.parse`) and builds `api` from `clientFromEnv` when omitted. It prints the returned summary. It exits 1 on any error, after whatever it already printed.
4. `publish.test.mjs` next to it (`node:test`, `node:assert/strict`, a fake in-memory `api` that records every call in order and can be told to fail at a given call), covering every Acceptance criterion below.

## Scope

### In scope

- The publish order, the epic reuse, placeholder substitution, markers, the result comment, closing the harvest issue, and tests.

### Out of scope

- Labelling anything `spec:approved` or `agent:ready`. That is always a human.
- Retrying a failed call. The workflow parks the run, and a human-started re-run goes through `prepare` again.
- The Relay workflow step and its `github-api` opt-in. That is a maintainer-implemented issue in this batch.

## Acceptance criteria

1. An invalid proposal, a proposal containing a `(pr, key)` that already has a marker in a `followups:issue` body, and a proposal whose result comment would exceed 60,000 characters each make `publishProposal` reject with no write recorded.
2. For three drafts, where `c` is blocked by `{{draft:a}}` and mentions `{{draft:b}}` in its Context, the fake records: the epic created first, then `a`, `b`, `c` in order. Each is created before it is linked as a sub-issue of the epic by its `id`. `c`'s body contains `#<a's number>` and `#<b's number>`, and no `{{draft:`.
3. Each created issue carries exactly `followups:issue` and `spec:proposed`, and its body ends with one finding-marker line per finding of the draft. The epic carries `followups:issue` only, and its body ends with the epic marker for `H`.
4. When `computeLedger` reports an epic for `H` already, no epic is created and the new issues are linked to the existing one.
5. A single-draft proposal with `epic: null` creates no epic and calls `addSubIssue` zero times.
6. The result comment's first line is the result marker for `H`. It lists every created issue, lists every rejection with its verdict and reason, has one finding-marker line per rejected finding, and lists the advisories. `computeLedger` over the resulting state puts every rejected and every drafted finding in `terminal`.
7. A proposal with no drafts and no rejections posts no comment, and still removes `followups:ready` and closes `H`.
8. `followups:ready` is removed and `H` is closed only after every issue and the comment were created. When the fake fails the second `createIssue`, the first issue exists, `H` stays open with `followups:ready`, and `publishProposal` rejects.
9. `main` with a fake `api` and temporary files publishes a valid pair and prints each created issue. It exits 1 on a missing argument or an unparsable file.
10. `node --test .github/scripts/review-followups/publish.test.mjs` passes with no network access.
