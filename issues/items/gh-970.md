**Blocked by:** #969

## Context

Implementers load the convention skills under `.bb/skills/` while they write code: `db-migrations` before a migration, `state-writes` before a write, and `io-hardening` before an edge. `.bb/AGENTS.md` lists what the repository is strict about (`.bb/AGENTS.md:75-90`, seven items). After #969, the backend review bot enforces tenancy rules that none of these documents mention, so an implementer learns them only from findings. That is the failure mode the skills exist to prevent.

#968 added the tenancy ADR, `docs/adr/<date>-tenant-isolation-through-row-level-security.md` (take its exact filename from that pull request). It also added the `tenants` table, `users.tenant_id`/`users.role`, `app_current_tenant()`/`app_sole_tenant()`/`app_tenant_default()` and `tenants_single_tenant_guard`. #969 added the matching rules to `backend/review-rules/rules.md` and `tasks/security.md`. The skills must teach the same rules in the form needed while writing, link the ADR for the reasoning, and contradict neither. The repository-root review task `review-rules/tasks/agent-instructions.md` treats a contradiction between instruction files, or with an ADR, as high (item 1), a wrong checkable claim as high (item 2), and a restated ADR rationale as low (item 3).

## Task

Load `adr-conventions` (link the ADR, never restate it) and read `review-rules/tasks/agent-instructions.md` before writing. Do not name any function or file that does not exist when this merges. In particular the tenant-scope primitive belongs to #978: refer to "the tenant scope (`app.tenant_id`)".

1. `.bb/skills/db-migrations/SKILL.md`: add a section "Every new table declares its tenancy". It covers:
   - the classification comment (`COMMENT ON TABLE <t> IS 'semprec:tenancy=tenant'` or `'semprec:tenancy=global'`) in the migration that creates the table, global only for identity-plane, admin-plane and operator tables without user content;
   - for a tenant table, in that same migration, `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)`, `ENABLE ROW LEVEL SECURITY`, and the RESTRICTIVE `tenant_isolation` policy (`USING`/`WITH CHECK (tenant_id = (SELECT app_tenant_default()))`) plus the PERMISSIVE `tenant_rows` policy (`USING (true) WITH CHECK (true)`), as one short SQL snippet;
   - every unique index or key on a tenant table leads with `tenant_id`, unless it is a server-generated surrogate key or is scoped by the server-generated id of a parent row in the same tenant;
   - grants follow `docs/operations/database-roles.md`;
   - one line linking the ADR for why.

   Extend the frontmatter `description` triggers with `COMMENT ON TABLE`, `tenant_id`, `ROW LEVEL SECURITY`, `CREATE POLICY` and `CREATE UNIQUE INDEX`.
2. `.bb/skills/state-writes/SKILL.md`: add a section "5. Every write stays inside the caller's tenant", plus matching items in "Before committing, check". It says:
   - The tenant comes only from a trusted source: the authenticated session, the queue job envelope, a NOTIFY payload stamped by its publisher, an internal caller verified against a row visible in that tenant, an MCP run credential, or a router function resolving an external identifier to its tenant — the same list as `backend/review-rules/rules.md`. It never comes from a request body, a model's output or a job payload field.
   - Let the `tenant_id` column default stamp the row; RLS `WITH CHECK` refuses a row for another tenant anyway.
   - Existence and uniqueness checks are per tenant, and another tenant's id is handled exactly like a missing id.
   - Cross-tenant system work runs tenant by tenant inside each tenant, never as one query over every tenant.

   Link the ADR. Extend the `description` triggers with `tenant_id` and `app.tenant_id`.
3. `.bb/skills/io-hardening/SKILL.md`:
   - In "Inbound", add two rules. The tenant is derived from the authenticated identity, never from the request. A foreign resource id must produce the same status, body and headers as a random id, so resolve it inside the tenant before any conditional branch (ETag/304, cache headers, early returns).
   - In "Outbound", add that a log line or error message carries ids and counts, never user content (item properties, mail subjects or addresses, file names, prompts, model output).
   - Link the ADR.
4. `.bb/AGENTS.md`: add item 8 to "What this repository is strict about". Each user's data and agents live in that user's own tenant; nothing may let one user see, infer or be notified about another's; isolation is enforced by row-level security plus an explicit tenant scope and fails closed. The item links the ADR and names the three skills above. Keep the existing seven items unchanged.
