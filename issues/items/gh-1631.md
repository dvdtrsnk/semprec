## Context

Model tier rationale: A small read endpoint over the existing problem query with one non-obvious contract (a banner identity that changes with each new occurrence), existing route-registration fixtures, and no writes.

The profile screen shows "Semp status - 2 problems need attention" with a dot, and the chat shows a banner above the main conversation, for example "Gmail mailbox is not syncing - Semp does not see new e-mails right now - Semp status", with a "Hide notice" action. Both need only a count and the most important problem, not the full list. Today the profile and the overview would have to compute a count from `GET /api/system-health`, which has no notion of a user-facing problem.

This issue adds `GET /api/semp-status/summary`, built on the problem read of #1555. Profile and overview counts read the count from here rather than computing their own (#1903, #1837).

Decision: the banner is the most severe active problem that affects Semp itself, that is severity `critical` and category `mail` or `agents`; ties are broken by the latest `last_seen_at`. With no such problem the banner is `null`. A banner is not shown in the thread of an Inbox item; that is the client's decision.

Decision: the banner carries `impactKey` (what Semp cannot do, for example `mailNotSyncing`, derived from the category and kind) and `instanceId`, which equals the problem id. The client hides a notice until the next instance: when a problem is resolved and later occurs again, it is a new problem row with a new id, so a notice the user hid earlier appears again.

Shared-file ordering: this issue also waits for #1630 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Scope

### In scope

- The summary endpoint with the active count and the banner, including the banner selection rule and identity.

### Out of scope

- The full problem list (#1555).
- Hiding a notice; the client stores that choice per `impactKey` and `instanceId`.
- The profile and overview routes that embed the count (#1903, #1837).
- Problems of other categories as banner candidates.

## Acceptance criteria

- When there are no active problems, then `activeCount` is 0 and `banner` is `null`.
- When a critical mailbox problem is active, then `banner` carries its title, short text, an `impactKey` and `instanceId` equal to the problem id.
- When only warning problems are active, then `activeCount` counts them and `banner` is `null`.
- When a problem is resolved and the failure returns, then `banner.instanceId` is different from before.
- When another tenant has problems, then they do not affect the response.
