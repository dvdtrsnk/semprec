### Requirement gh-1841: [sensitive-data 05/09] Manage project database grants over REST

#### Context

Model tier rationale: A pair of human-only REST routes over the grants store from the previous issue, following an existing custom-route and admin-store pattern, with a clear authorization rule that agents cannot reach the write.

#1810 adds `agent_database_grants` and enforces them. The user needs a way to see and change what the Semp agent of a project may read and write. Today the equivalent for tools is `GET /api/projects/:id/mcp-grants` and `PATCH /api/projects/:id/mcp-grants/:grantId` (`services/semprec-api/src/mcpAgentPageHandler.ts`), which reach the user-only mutations through wrappers so the package barrel never exposes them to agent code. Module-declared routes are registered through `customRoutes` in a module manifest (ADR `2026-09-11-module-manifest-custom-routes`; examples in `chokePoint/schemaCoreModuleManifest.ts` with handlers re-exported from the manifest file).

Decisions:
- `GET /api/projects/:id/database-grants` lists every database a grant can matter for: the sensitive databases and the user-created ones, each with `databaseId`, `key`, `name`, `sensitive`, `system` and the project's current `access` (`none`, `read` or `write`). Without a stored row the access is `none` for a sensitive database and `write` for a user-created one (#1810). Non-sensitive system databases are not listed, because they are always open.
- The list backs the client's collection list in the project's Semp settings (Collections), with one "Semp may read" toggle per collection; sensitive collections are off by default (decided by the product owner).
- `PATCH /api/projects/:id/database-grants` takes `{ databaseId, access }` with access `none`, `read` or `write`. Setting the database's default access (`none` for a sensitive database, `write` for a user-created one) removes the stored row; any other value is stored. A database that is not listed (an open system database) is rejected with 400.
- Both routes need an authenticated user session. An agent run credential cannot reach them.
- The project must exist and not be in the trash, else 404.

### Requirement gh-1842: [global-search 05/09] Add the generic search operation with grouped results

#### Context

Model tier rationale: This adds a new tenant-scoped, grant-checked read operation exposed through REST, MCP and agents, with a ranking and result-shaping contract that other issues extend, so an authorization or tenant-isolation mistake leaks data across tenants or databases.

There is no way to search across databases. `searchItems` (`mail/search.ts`) filters one database, is not exported from the `@semprec/data` barrel, and is called only by tests; no `/api/search` route exists in `semprec-api/src/routeMatrix.ts`. The generic operation layer (`shared/genericOperations/*`, dispatched through `dispatchGenericOperation`) already serves REST, MCP (`semprec.<operation>` tools are derived from it) and agents, so a new operation there reaches all three.

The index it reads comes from #1397 (documents) and the vector and query builder from #1589. Related item names for subtitles are loaded in batches with the relation expansion from #1518. For agent actors, only databases an agent has a grant for may be searched, using the per-database grant enforcement from #1810.

Decisions:
- Results are grouped by a fixed set of types, in this order: `task`, `event`, `project`, `area`, `contact` (People and Companies together), `journal`, `file`, `mail`, `chat`. A group is an allow-list of databases by owner module (`tasks`, `events`, `projects`, `areas`, `people` + `companies`, `journal`, `files`), so internal databases (inbox pipeline, mailboxes, folders, MCP servers, settings, processing proposals, the Inbox itself, subpage storage) are never searched. Inbox entries are covered by their Journal day. User-created collections and Health records, Library and Recordings databases are not part of global search in this version (a collection is searched with `q` in its own queries, #1857).
- `mail` and `chat` are accepted scope values; their groups are filled by #1864 and #1854 and are empty here. Thread-backed results carry `threadId` instead of `itemId`, `databaseId` and `databaseKey`, so the schema is a union on group.
- Subtitle data is structural (`subtitleParts`), never localised text: the client composes the Czech text, because relative words ("Dnes") depend on the clock and time zone and MCP clients need no text.
- A task is shown with its project, never with its area (a task has a project or none).
- A company has no kind subtitle: there is no company kind in v1 and no schema change for it.
- The calendar has no search of its own: it calls this operation with `scope` `["event", "task"]`, and the calendar agenda only lays the returned results out by date.
- Search text never reaches logs or error messages: log only the query length and result counts (`backend/review-rules/rules.md`).

### Requirement gh-1857: [global-search 07/09] Accept q in database and view queries and item counts

#### Context

Model tier rationale: An additive optional parameter on three existing operations that reuses one shared match predicate and the existing filter and count machinery, with no new authorization or isolation contract.

Inside a collection (for example the Projects list), the search field has to narrow the visible rows together with the active filter. Today `DatabaseQueryInputSchema` (`shared/genericOperations/schemas.ts`) is `.strict()` and has no text parameter; the only text matching is an `ILIKE` on a single property without diacritic folding (`views/filterCompiler.ts`). The same text index and query that the global search operation uses (#1842, built on #1397 and #1589) can restrict one database's items, and the batched `item.count` operation is delivered by #1709.

Decisions:
- `q` is additive and optional on `database.query`, `view.query` and `item.count`; it is combined with the filter by AND.
- `totalCount` of the two query operations is computed without `q` (the filter-only count, so a "N items" figure does not change while typing). `item.count` applies `q`, because it counts the rows the same search would show.
- Match uses the shared predicate against `item_search_index` rows of that database only; items without a row do not match.

#### Task

Load `canonical-keys`, `io-hardening` and `testing`.

1. Add optional `q` (1 to 200 characters) to the `database.query`, `view.query` and `item.count` inputs in `shared/genericOperations/schemas.ts` (still `.strict()`), the JSON schemas, port types and bindings, and to the REST query-string handlers of the first two (`itemsHandler.ts`, `viewsHandler.ts`).

3. Apply the predicate in the query path of `database.query` and `view.query` (`views/viewQuery.ts` and the filter/sort compilation entry points) and in `item.count`, restricted to the queried `databaseId` and ANDed with the filter. Without `q` the generated SQL is unchanged.
4. `totalCount` ignores `q`; the page of items and `nextCursor` honour it; `item.count` honours it.
5. Never log or echo `q` in errors.
6. Tests: Projects with `q` "novak" and the filter "Aktivní" returns "Web pro klienta" and its `totalCount` equals the filter-only count; `q` with `& | ! : '` runs as plain text; `q` composes with sort and cursor paging; `item.count` with `q` counts only matching rows.

### Requirement gh-1843: [calendar-recurrence 05/08] Materialize an event occurrence on its first exception or link

#### Context

Model tier rationale: It creates items from computed occurrences with a uniqueness guarantee under concurrency and an idempotent contract that three other issues (recordings, task links, invitations) depend on, so a race or a wrong copy duplicates or corrupts calendar data.

A recurring Event is one stored series whose occurrences are computed (#1817); an occurrence is virtual and has the synthetic id `<seriesId>@<YYYY-MM-DD>`. A virtual occurrence cannot be edited or linked to anything, so the first time a user changes one date (a different time or place, a cancellation) or something links to it (a recording, a task placed in the Event, an invitation), it has to become a real Events item. This issue defines that step.

An occurrence item is an Events item with `seriesId` (the identity of the series, as fixed by the ADR of #1365) and `occurrenceDate`, with no recurrence rule of its own. It is unique per `(seriesId, occurrenceDate)`. It is created by copying the series' whitelisted properties and edges with the same helpers as the duplicate operation of #1796 (export them from `calendar/duplicateCalendarItem.ts` if they are not exported yet), with `date` set to the occurrence date and `endDate` shifted to keep the series' length.

The route is `POST /api/events/series/:seriesId/occurrences/:date`. Routes over Events belong to the systemDatabases module, so it is declared in `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` with justification `transactional-semantics` (the existence check, the copy and the edges commit together). It is idempotent: the first call creates the item and answers 201, any later call answers 200 with the same item. After it, the user edits the item with an ordinary `PATCH` with `ifVersion`.

Decision: cancelling one occurrence is deleting its materialized item (the trash); the timeline expansion treats a date whose occurrence item is in the trash as cancelled and does not show it (#1877). Restoring the item brings the occurrence back.

Decision: concurrent materializations of the same occurrence serialize on a transaction-scoped advisory lock keyed by `seriesId` and date, then re-check for an existing item, so exactly one item is ever created.

Shared-file ordering: this issue also waits for #1832, #1842 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Context

Decision: expansion works on dates and wall-clock times (stored as such), so daylight-saving changes do not move an occurrence.

Decision: a series is expanded for at most the request's range (at most 93 days), and at most 100 occurrences per series per request.
