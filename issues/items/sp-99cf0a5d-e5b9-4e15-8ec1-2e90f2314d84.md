## Context

Model tier rationale: An ordering change of two delete hooks of the Event trash, which decides which rows the trash holds while it waits. It is one registration moved and a comment, but the trash, the task propagation and the restore share these rows, so the schedule must be run with real concurrent transactions and the existing trash and restore tests must keep passing.

The accepted ADR `docs/adr/2026-11-15-a-user-edge-write-on-a-link-rules-via-relation-locks-the-rules-target-item-before-ending-value-links.md` (source sp-5419cac1) states that an item's row comes before its value link rows, and lists three paths of the tree that do not follow it. This source repairs the second (verified by reproduction in a scratch copy of the tree at the integration tip, production calls, pools of the runtime role `alldots_data`):

- Moving an Event to the Trash runs its item delete hooks in the order they are registered in `domainWriteHooks.ts`. `valueLinkSourceDeleteHook` (line `registerItemDeleteHook(valueLinkSourceDeleteHook)`) runs first and locks the value links the Event is a source of. `eventHostedTasksDeleteHook` (`tasks/eventHostedTasksHooks.ts`, issue #1819; registered much later, after the host-state hooks of #1780) then recomputes each task the Event hosts, which locks the task rows in id order.
- A task that came from an action item of the Event (`Events.actionItems`, `Tasks.sourceEvents`) is also hosted in the Event (`Tasks.hostEvents`). Its `project` and `people` value links have the Event as a source (rules `taskProjectFromEvent` and `taskPeopleFromEvent`). For such a task the trash takes the task's links first and the task row after them.
- The propagation job for the Event's project (`handleLinkPropagation`, rule `taskProjectFromEvent`) takes the task row and then its `project` link. With a third transaction holding the task row, the propagation started first and the trash second, the trash holds the links and waits for the row, and the propagation gets the row and waits for the link: `40P01` (reproduced: outcomes `committed` for the propagation and `deadlock` for the trash).

Moving the registration of `eventHostedTasksDeleteHook` ahead of `valueLinkSourceDeleteHook` is not enough. The trash would then hold the row of a hosted task while it waits for the link of another task that the Event sources but does not host, and the propagation job (item order: row, link, next row) holds that link while it waits for the hosted task's row (measured: `40P01` for the trash, with a third transaction holding the smaller task's `project` link). Instead, the source detach takes the rows of every Tasks item whose value link it detaches, in item id order, before it takes any link. Then it takes the links in the order of [debt 06/08]. `eventHostedTasksDeleteHook` keeps its place and finds the rows of the hosted tasks already locked. Transcript rows are not taken, because a trash that locks them waits for an open transcription match, which `transcriptTrashedEventEdge.test.ts` forbids. `eventHostedTasksRestoreHook` keeps its place.

## Scope

### In scope

- The rows the source detach locks before it takes the links of the items it detaches.

### Out of scope

- The order in which the source detach locks the links of several items (a separate source).
- The replay of an approved `relation.delete`, `relation.put` or `relation.set` (a separate source).
- The restore hook, the contents of either hook, and `recomputeTaskHostState`.
- The order of any other pair of delete hooks, and `transcriptCompanyLinkReleaseItemDeleteHook`, which stays after the detach.
- Any new lock, table, hook kind or migration.

## Acceptance criteria

- When the trash of an Event that hosts a task which is also sourced from it runs against the propagation of `taskProjectFromEvent`, with a third transaction holding the task row, then neither call ends with a deadlock, in both start orders; both commit.
- When the trash of such an Event waits for a held `project` link row of the task, then it already holds the task row.
- When an Event that hosts tasks is trashed, then each task returns to its day and loses its link to the Event as before, and restoring the Event behaves as before.
- When the trashed Event also sources a task it does not host whose id is smaller than that of a hosted, sourced task, and a third transaction holds the smaller task's project link, then the propagation started first and the trash both commit.
- The ADR of this source exists and the accepted ADRs it names are not edited.
