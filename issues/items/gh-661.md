## Context

`createDatabase` in `backend/packages/data/src/chokePoint/databasesStore.ts` (lines 106-114) creates the new database's `items` partition inside the API transaction by running `CREATE TABLE items_p_<hex> PARTITION OF items FOR VALUES IN ('<id>')` (built with `format('%I ... %L')`, line 111, executed at line 114). Migration `backend/packages/data/src/db/migrations/0040_least_privilege_roles.sql` gives the production API role `semprec_data` only `USAGE` on schema `public` and `SELECT/INSERT/UPDATE/DELETE` on the choke-point tables; the migrating role owns `items`. Reproduced on Postgres 15: a non-owner with `USAGE` only gets `permission denied for schema public`; with `CREATE` on the schema granted it still gets `must be owner of table items`. So `POST /api/databases` (and every other API path into `createDatabase`, e.g. an inline database under a page) fails in production, and `items` has no DEFAULT partition, so a `databases` row without its partition would be unwritable anyway.

`backend/packages/data/src/__tests__/leastPrivilegeRoles.test.ts` never catches this: `seedDatabaseAndItem` (line 29) creates the database through `createChokePoint(adminPool)` — the superuser — and the `semprec_data` tests (lines 129-158) only run raw DML against the already-created partition.

The runtime-role split is `docs/adr/2026-09-17-two-tier-runtime-database-roles.md` (superseded by `docs/adr/2026-09-22-transcription-worker-choke-point-access.md`, which keeps the same two roles); the migration rules are `docs/adr/2026-09-10-expand-contract-forward-only-migrations.md`. Sibling issue C2 of this batch adds the matching `drop_items_partition` function for the purge and depends on the pattern this issue establishes.

## Task

1. New migration `backend/packages/data/src/db/migrations/NNNN_create_items_partition_function.sql` (next free ordinal at commit time) that creates

   ```sql
   CREATE FUNCTION create_items_partition(database_id uuid) RETURNS void
   LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, public AS $$ ... $$;
   ```

   The body runs `EXECUTE format('CREATE TABLE %I PARTITION OF public.items FOR VALUES IN (%L)', 'items_p_' || replace(database_id::text, '-', ''), database_id)` — the identical partition name the code builds today, so existing partitions keep their names. The function is owned by the migrating role (`CURRENT_USER` at migration time, the owner of `items`), followed by `REVOKE EXECUTE ON FUNCTION create_items_partition(uuid) FROM PUBLIC;` and `GRANT EXECUTE ON FUNCTION create_items_partition(uuid) TO semprec_data;` (`semprec_side` gets nothing — it must never create a partition). A header comment states why the function exists (the API role cannot own `items`), that `CREATE TABLE ... PARTITION OF` takes an `ACCESS EXCLUSIVE` lock on `items` for the duration of the caller's transaction exactly as the inline DDL did, and that any further DDL the API role ever needs goes through a function of this shape rather than a schema grant. Additive only: no exemption marker.
2. `databasesStore.createDatabase` replaces the `format(...)` + `client.query(ddl)` pair (lines 106-114) with `await client.query('SELECT create_items_partition($1::uuid)', [database.id])`. Keep the `UUID_RE` sanity check (line 99) and update the comments above it so they describe the function call instead of the escaped DDL.
3. `leastPrivilegeRoles.test.ts`: add to the `semprec_data` describe block a test that calls `createChokePoint(dataPool).createDatabase({ name })` (the role's own pool, not `adminPool`), then `createItem` in it through the same choke point, and asserts both succeed and that `pg_class` contains `items_p_<hex>` for the new id. Add to the `semprec_side` block a test that `sidePool.query('SELECT create_items_partition($1::uuid)', [randomUUID()])` rejects with `/permission denied/`.
4. `docs/operations/database-roles.md`: a new section "DDL the API role needs" describing `create_items_partition`, its ownership/grants, and the rule from the migration header.

## Scope

### In scope
- The `SECURITY DEFINER` partition-creating function, its grants, the `createDatabase` call switch, the role-level test and the operations doc.

### Out of scope
- Dropping a partition when an inline database is purged (`drop_items_partition`) — sibling issue C2 of this batch.
- Validating `parentItemId` on `createDatabase`, and any other `databasesStore` change.
- Changing which role runs migrations or seeds.

## Acceptance criteria

- When `createChokePoint(pool)` with a `semprec_data` connection calls `createDatabase`, the call succeeds, `pg_class` contains the `items_p_<hex>` partition for the new id, and a subsequent `createItem` into that database succeeds — all against embedded Postgres with the roles from migration 0040.
- When a `semprec_side` connection calls `create_items_partition(uuid)`, Postgres rejects it with `permission denied`.
- When migrations run on an existing database, no existing partition is renamed or touched; `check-migration-numbering` and the migration compatibility unit test pass with no exemption marker.
- `docs/operations/database-roles.md` documents the function and the "DDL through a SECURITY DEFINER function, never a schema grant" rule.
