## Context

Model tier rationale: One known mechanism (a property-level default applied inside the existing create transaction) across the property config, the item create path and a per-tenant cutover, with existing choke-point fixtures, but it changes what every create path (including internal ones) persists, so it is not a one-file edit.

When a person adds an item in the app, the form already shows a starting value: a new project starts "In progress", a new task "Not done", a new book "To read", a new file dated today. The backend does not know defaults or required fields (the comment in `backend/packages/data/src/seed/seedInboxPipeline.ts` says so), so an item created without that key is stored without it, and every client must send the value itself. `createItemWithClient` in `backend/packages/data/src/chokePoint/itemWrites.ts` validates writability of the supplied keys and inserts `input.properties` as given; it is also called by many internal paths (journal, inbox, transcription, task recurrence, mail, file upload).

The property `config` is the natural home for a default, and the system databases are schema-locked, so existing tenants receive new config through a per-tenant cutover registered in `backend/packages/data/src/db/tenantCutoverMigrations.ts` (`docs/adr/2026-10-08-deploy-time-tenant-work-runs-as-the-runtime-role.md`).

Builds on nothing. #1519 builds on this create-path change; #1554 backfills missing Areas values; #1661 relies on the Files date default when an upload creates its item; #1802 validates select values on item writes.

Decision: only the listed properties get a default; the mechanism is generic (`config.default`), so a wider set later is a data change, not a code change. Defaults: Projects `status` = `inProgress`, Books `status` = `toRead`, Movies `status` = `planned`, Tasks `status` = `notDone`, Areas `active` = `true`, Files `date` = the token `"today"`. Decided by the product owner: only these listed defaults, and no default for any other property, so no data is created that the user did not enter; the alternative (first option of every group select) is not adopted.

Decision: a default applies only when the key is absent from the create input. An explicit value, including an explicit `null`, is kept as given.

Decision: the token `"today"` is allowed only as the default of a `date` property without `includeTime`, and resolves to the calendar date in the tenant's configured time zone (`getSystemTimezone` in `backend/packages/data/src/systemSettings.ts`), formatted as `YYYY-MM-DD`.

## Task

Load `state-writes`, `db-migrations`, `canonical-keys` and `testing`.

1. Allow `config.default` on a property: validate in `chokePoint/propertiesStore.ts` (the function that validates property config on create and update) that it is a string, number or boolean matching the property type (select/multi_select: a string that is one of the option keys; checkbox: boolean; number: finite number; text: string; date: the string `"today"` only when `includeTime` is not set). Anything else is a `ValidationError` on `config`.
2. In `createItemWithClient`, after the writability check and before the insert, add `config.default` for every property of the database whose key is absent from `input.properties` (resolving `"today"` in the tenant time zone). This applies to every caller, including internal paths. It never overrides a supplied key, never runs on an idempotent replay, and never applies to `item.patch`.
3. Seed the defaults on fresh installs: `seed/seedTenDatabases.ts` (Projects, Tasks, Areas, Files) and `seed/seedLibraryModule.ts` (Books, Movies) per the decision above.
4. Add a per-tenant cutover step (new file registered in `runTenantCutoverMigrations`) that sets `config.default` on those properties of existing tenants when it is not set, leaving every other config key unchanged; a missing database or property is skipped; a second run changes nothing.
5. Expose `default` in the property `config` of `GET /api/schema` for the property types where #1360 projects config: pass `default` through as stored (the `"today"` token is returned as the token, not as a resolved date).
6. Tests: project created without `status` stores `inProgress`; with explicit `status` or explicit `null` keeps it; file created without `date` stores today's date in a non-UTC tenant time zone near midnight; an idempotent replay does not re-apply; `config.default` rejected for a wrong type, an unknown option key and `"today"` on a date with `includeTime`; the cutover is idempotent; existing internal creators (journal, inbox, task recurrence, mail ingest, transcription) still pass their tests.

## Scope

### In scope

- `config.default` validation, application on item create, seed and cutover for the listed properties, and its exposure in the schema config.

### Out of scope

- Making Areas `active` default for items that already exist (#1554).
- Rejecting an empty title (#1519).
- Validating select values against the option catalog on writes (#1802).
- Recipes defaults: the Recipes module sets its own `config.default` when created (#1707).
- Applying defaults on `item.patch` or retroactively to existing items.

## Acceptance criteria

- When a project is created without `status`, then it is stored with `status: "inProgress"`; when `status: "done"` or `status: null` is supplied, then that value is kept.
- When a file is created without `date`, then `date` is today's calendar date in the tenant's time zone, not UTC.
- When a task is created by recurrence or any other internal path without `status`, then it gets `notDone` unless the path supplies one.
- When `property.create` or `property.patch` sets `config.default` to a value that does not fit the property type or option list, then it fails with a validation error on `config`.
- When an existing tenant is migrated, then the listed properties carry their default and a second run changes nothing.
- When `GET /api/schema` is requested, then the Projects `status` property config shows `default: "inProgress"`.
