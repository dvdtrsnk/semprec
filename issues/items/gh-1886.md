## Context

Model tier rationale: It merges projected virtual Task occurrences with stored Tasks in the central calendar read and must exclude the series rows from the core source, so a mistake duplicates or hides Tasks, with carry-over rules from the Tasks work as inputs.

The calendar timeline (#1717) is assembled from sources listed in `backend/packages/data/src/calendar/timelineSources.ts`; its core Tasks source returns stored Tasks. A recurring Task is a series with occurrences (#1605 gives it a series identity, a template and an `occurrenceDate`), and #1672 delivers the projection in the data layer: a function that lists the virtual occurrences of the live series in a date range, with each occurrence's done state and whether it was overridden. A done or one-off-moved occurrence is a real item (#1720). An unfinished occurrence is carried until the day before the next occurrence (#1668 marks missed ones) and the carry-over and trace entries of #1884 are already part of the timeline. This issue adds the entries for recurring Tasks to the timeline; it computes no recurrence itself.

Behavior: the source calls the projection of #1672 for the request range and returns one entry per occurrence with `kind` `task`, `seriesId`, `occurrenceDate`, `done` (the Task `status` `done`), `overridden` (a real item exists for the occurrence), the id `<seriesId>@<date>` for a virtual occurrence or the real item id for a materialized one, `readOnly` true for a virtual occurrence, and the same fields as other Task entries (title, time, project, people, calendar `Tasks`). A missed occurrence is not carried past the day before the next occurrence. The core Tasks source skips every Task that has a `seriesId` (the series row, the template and materialized occurrences all come only from this source), so nothing is returned twice.

Decision: the compact shape carries `seriesId` and `occurrenceDate`, so the month view can tell exceptions apart.
