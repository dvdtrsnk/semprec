**Blocked by:** #247, #82, #89

## Context

Second of two parts of the Event-matching slice of the `batch-transcription` batch (approved behavior in #179). #247 delivered the deterministic time-window match and the `kind = 'transcript'` card with the create-Event proposal shape. This part adds the link-existing shape and makes confirming either shape write the Transcription<->Event edge atomically. #185 builds on these cards for AI-suggested speaker mappings.

## Task

- Add a third `proposal.entityKind` value, `'relation'`, next to the existing values. A `'relation'` proposal keeps the same generic envelope `{ entityKind, target, properties }` and describes linking the transcription to an existing Event.
- The transcript card's `proposal` therefore carries either creation of a new Event (the shape from #247) or linking to an existing one. The match step from #247 is unchanged and never selects among several candidates: both the zero-candidate and the many-candidate case keep the create-Event shape. A card becomes a link-existing proposal only through an explicit human `revise`.
- `confirm` gains a third branch over the existing ones (create-item, block append): for `entityKind: 'relation'` it maps onto the existing generic relation-write operation (`PUT /api/items/:id/relations/...`) — no new write mechanism. For both shapes, `confirm` also writes the Transcription<->Event edge (the transcription is known from `sourceTranscript`) in the same transaction as the Event creation or relation write, so a partial result can never be observed.
- `revise` fully replaces the proposal: a revision can flip a card from "create a new Event" to "link to that existing one" (or back) in one move, using the same envelope.
- Ownership and relation-integrity errors stay canonical (#82); the transcript card obeys the same locking/fingerprint rules as other Processing Suggestion cards.

## Scope

### In scope

- `entityKind: 'relation'`, the link-existing proposal shape reachable through `revise`, the `confirm` relation branch with transactional edge creation for both shapes, full-replace `revise`, tests, and necessary documentation.

### Out of scope

- The time-window query and auto-link — #247.
- LLM candidate selection — never.
- Speaker mapping suggestions — #185.

## Acceptance criteria

- Confirming a create-Event card creates the Event and the Transcription<->Event edge in one transaction; confirming a link-existing card writes the generic relation and the same edge in one transaction. A failure in either write leaves neither.
- `revise` replaces the whole proposal; flipping between the two shapes and then confirming yields exactly one edge.
- Confirm retries are idempotent: a repeated `confirm` of an already-confirmed card creates no second Event or edge.
- Invalid targets (wrong database, archived database, unauthorized relation) are rejected with the canonical error codes from #82.
