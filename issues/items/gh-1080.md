## Context

Model tier rationale: The three adapter methods and the panel's create, list and revoke behaviour are specified exactly in the existing admin patterns.

Accounts are created only by an admin's invitation; there is no public signup. #1040 added the backend:

- a global `invites` table and admin-only routes to create, list and revoke invitations;
- every mutation is audit-logged;
- a re-invite of the same email revokes that email's earlier pending invite;
- the link `<origin>/?page=invite#token=<token>` is returned **once**, in the create response, and mailed to the invitee when SMTP is configured.

The token sits in the URL fragment, which the browser never sends to a server. Whoever holds the link can create the account, so the admin page must show the link exactly once and never keep it beyond the screen it appears on. Acceptance itself ships later (#1087, #1088). Until then an invite is inert, and creating one is safe.

#1079 delivered the admin page (`?page=admin`, rendered only for `role === "admin"`):

- `web/src/api/adminOperations.ts` — `createAdminOperations({ baseUrl, fetchImpl })` and the `AdminOperations` interface (`listAccounts`, `suspendAccount`, `reactivateAccount`, `changeRole`). Every response is zod-parsed. Status mapping: `401/403/404/501` → `unavailable`, everything else → `retryable`. A non-2xx's message is the adapter error body's `error.code` when present.
- `web/src/views/admin/AdminPage.tsx`, which renders `AccountsPanel`, plus the `admin.*` i18n namespace.
- Panels load through `useAsyncResource` (`web/src/views/mailbox/useAsyncResource.ts`) and render the shared states from `web/src/components/StateViews.tsx`. Dates use `formatDateTime(useLocale(), iso)` (`web/src/i18n/format.ts:3-8`).

Backend contract (#1040). If the merged handler (`backend/services/semprec-api/src/adminHandler.ts`) differs, bind to it and say so in your PR description.

`InviteSummary = { id, email, invitedBy: string|null, createdAt, expiresAt, acceptedAt: string|null, revokedAt: string|null, status: "pending"|"accepted"|"revoked"|"expired" }`

- `GET /api/admin/invites` → `200 { invites: InviteSummary[] }`, newest first.
- `POST /api/admin/invites` with `{ email }` → `201 { invite, inviteUrl, emailed: boolean }`. An email that already belongs to an account → `400` with code `validation_failed`.
- `POST /api/admin/invites/:id/revoke` → `200 { invite }`. A non-pending invite → `409` with code `invite_not_pending`; an unknown id → `404`.

## Task

Load `canonical-keys` (status labels) and `error-handling` (create and revoke failures).

1. **Adapter** — extend `AdminOperations` in `web/src/api/adminOperations.ts` with:
   - `listInvites(): Promise<InviteSummary[]>`;
   - `createInvite(email: string): Promise<{ invite: InviteSummary; inviteUrl: string; emailed: boolean }>`;
   - `revokeInvite(inviteId: string): Promise<InviteSummary>`.

   Use zod schemas, `encodeURIComponent` for the id, and the file's existing request and error mapping.
2. **Panel** — add `web/src/views/admin/InvitesPanel.tsx`:
   - **Create form.** An email input (`type="email"`, required, labelled `admin.invites.email`) and a submit button, disabled while pending. On success:
     - `inviteUrl` appears in a read-only text input labelled `admin.invites.link`, with `admin.invites.linkShownOnce`;
     - `admin.invites.emailed` or `admin.invites.notEmailed` is shown according to `emailed`;
     - the email field is cleared and the list reloads.
   - **The URL lives only in component state.** It is never logged or written to any storage. The next creation replaces it, and it is dropped on unmount.
   - **List.** Email, created, expires and the label of the server's `status` (`admin.invites.status.pending|accepted|revoked|expired`), with loading, error (with retry) and empty (`admin.invites.empty`) states.
   - **Revoke** is offered for `pending` rows only. It is disabled while pending and reloads the list on success.
   - **Failures.** A create or revoke failure shows `admin.invites.actionFailed` with the message in a `role="alert"` element, and the list and the form keep their state.
3. **Mount** — render `<InvitesPanel operations={…} />` in `web/src/views/admin/AdminPage.tsx` after the panels already there.
4. **i18n** — add the `admin.invites.*` keys to `en` and `cs` in `web/src/i18n/messages.ts`.
5. **Test stubs** — update every existing `AdminOperations` test stub for the three new methods.

## Scope

### In scope
- The three adapter methods, the invitations panel (create with the one-time link, list, revoke), its mounting, i18n and tests.

### Out of scope
- Any backend change; the invite table, routes, mail and audit are #1040's.
- Accepting an invitation (#1087) and the acceptance page (#1088).
- Account actions and deletion (#1079, #1084); the budgets and health panels (#1081, #1082).
- Re-sending or re-showing a link for an existing invite. A new invite for the same email is the way to get a fresh link.

## Acceptance criteria

- `listInvites` issues `GET /api/admin/invites`, `createInvite("a@example.com")` issues `POST /api/admin/invites` with `{"email":"a@example.com"}`, and `revokeInvite("i 1")` issues `POST /api/admin/invites/i%201/revoke`. All three use same-origin credentials and parse the documented bodies. A 400 rejects as `retryable` with message `validation_failed`, a 409 as `retryable` with message `invite_not_pending`, and a malformed body as `retryable` (web unit, `adminOperations.test.ts`).
- Creating an invite shows the returned `inviteUrl` in a read-only field with the emailed or not-emailed message, clears the email field and reloads the list. A second creation replaces the URL (web unit, `web/src/views/admin/__tests__/InvitesPanel.test.tsx`).
- After the panel unmounts and mounts again, no `inviteUrl` is shown, and nothing was written to `localStorage` or `sessionStorage` (web unit, `InvitesPanel.test.tsx`).
- Rows show the label of their server `status`, and only `pending` rows offer Revoke. A successful revoke reloads the list. A rejected create or revoke shows its message in an alert (web unit, `InvitesPanel.test.tsx`).
- A failed list load shows the error state with a retry that reloads it (web unit, `InvitesPanel.test.tsx`).
- The admin page renders the invitations panel (web unit).
- Every new key exists in `en` and `cs`, and `pnpm run verify` passes in `web/`.
