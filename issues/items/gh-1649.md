**Blocked by:** #1434, #1643
**Model tier:** medium

## Context

Model tier rationale: One conversion step in the tick (heading text to heading id) over a known envelope shape with existing tick fixtures, depending on the computation function delivered by a blocker.

The tick computes proposals before any page is chosen: for `pageContent` the target page is selected by the computation itself, so the computation input cannot contain that page's headings in advance (`ProposalComputationInput` in `backend/packages/data/src/inbox/inboxTickAction.ts` carries only the source item, type, entity kind and target database id). With #1643, a v2 `pageContent` envelope is `{markdown, placement, heading?}`, where the stored `placement` must be `end | start | {afterHeading: <blockId>}`.

So the tick lets the model say where in the page it wants the content in words: `placement` may be `end`, `start` or `{afterHeadingText: "<text>"}`; after the target page is known, the server converts it. The computation function itself is delivered by #1434.

Decision: matching ignores letter case and surrounding whitespace, compares against `h1`-`h3` headings of the chosen target page (read with the non-creating page summary), and takes the first match in document order.
Decision: no match, or a target without a page, falls back to `end`.

## Task

Load `ai-gateway`, `testing` and `state-writes`.

1. Extend the computation contract used by the tick (output schema and instructions delivered by #1434) so that, for `pageContent` types, the model returns the v2 properties `{markdown, placement, heading?}`, where `placement` may use `afterHeadingText`. The old shape `{flavour, ...}` is no longer requested from the model, but a result in it is still accepted and stored unchanged.
2. In the tick's envelope building step (`buildProposalEnvelope`, after the target is known), convert `afterHeadingText` into `{afterHeading: <blockId>}` using the target's headings (the page summary from #1615, already used by #1643), or to `end` when no heading matches.
3. The stored envelope never contains `afterHeadingText`; it passes `assertValidProposalEnvelope` as a v2 envelope.
4. Tests in `inboxTickProposal.test.ts`: `afterHeadingText: "tiles"` against a page with heading "Tiles" is stored as `afterHeading` with that heading's block id; a text with no match is stored as `end`; a target without a page gives `end`; invalid Markdown from the model is rejected like other invalid computations.

## Scope

### In scope

- Model-facing `afterHeadingText` and its server-side conversion to a heading block id or `end` in the tick.

### Out of scope

- Envelope validation: #1643.
- Writing at the placement on confirm: #1681.
- The tick runtime: #1434.
- Listing headings to the user for manual choice: #1959.

## Acceptance criteria

- When the model returns `afterHeadingText: "dlažba"` and the target page has a heading "Dlažba", then the stored envelope has `placement: {afterHeading: <that heading's block id>}`.
- When no heading matches, or the target has no page, then the stored `placement` is `end`.
- When the model returns `end` or `start`, then it is stored as is.
- When the stored envelope is read, then it never contains `afterHeadingText`.
- When the model returns Markdown with a `page` block, then no card with that envelope is created.
