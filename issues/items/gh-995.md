## Context

Every tenant brings its own set of system databases plus the user's own, and each database has its own `items` partition (`backend/packages/data/src/chokePoint/databasesStore.ts:110`). That is about 25 partitions per tenant, each with two indexes today: the primary key and `items_props_gin` (`backend/packages/data/src/db/migrations/0001_core_schema.sql:71-81`).

A statement on `items` that the planner cannot prune locks the parent, every partition and every partition's indexes for the rest of its transaction. Examples are an id-only lookup before #1003, an RLS-filtered scan (the policy filters on `tenant_id`, not on the partition key `database_id`), or `count(*)` in the restore test. At 200 tenants × 25 partitions × 3 relations that is about 15,000 lock-table entries for one statement.

PostgreSQL's shared lock table holds `max_locks_per_transaction × (max_connections + max_prepared_transactions)` entries in total. With the image defaults (64 × (100 + 0) = 6,400), a single such statement fails with `out of shared memory … increase max_locks_per_transaction`. The test harness already hit this exhaustion with too many partitions (`backend/packages/data/src/testSupport/testDb.ts:68-74`).

Two PostgreSQL servers run with defaults today:
- the production container (`deploy/docker-compose.yml:10-24`), with no `command:` and no `-c` flags;
- the disposable container the monthly restore test starts (`deploy/systemd/scripts/semprec-restore-test.sh:136-138`, image `postgres:16-alpine` at `:10`). It runs `SELECT count(*) FROM items` and `max(updated_at)` over every restored partition (`:155-163`).

#1036 removes the exclusive lock partition creation takes. This issue only sizes the shared lock table.

## Task

1. **Production.** In `deploy/docker-compose.yml`, add `command: ["postgres", "-c", "max_locks_per_transaction=2048"]` to the `postgres` service. Add a comment naming the sizing document below. This gives 2048 × 100 = 204,800 lock-table entries, about 13 concurrent unpruned `items` statements at 200 tenants × 25 partitions × 3 relations.
2. **Restore test.** In `deploy/systemd/scripts/semprec-restore-test.sh`, `start_postgres` (`:131-143`) starts the disposable server with the same setting: append `postgres -c max_locks_per_transaction=2048` after `"$POSTGRES_IMAGE"`. In `deploy/systemd/scripts/semprec-restore-test.test.sh`:
   - read the value from `deploy/docker-compose.yml`;
   - assert the recorded `docker run` line ends with `postgres -c max_locks_per_transaction=<that value>`, so the two cannot drift apart.
3. **Sizing document.** Add `docs/operations/postgres-capacity.md` with:
   - the formula: entries per unpruned statement = tenants × partitions per tenant × (1 + indexes per partition); total = `max_locks_per_transaction × (max_connections + max_prepared_transactions)`;
   - the chosen numbers and the headroom they buy;
   - the shared-memory cost, measured on a PostgreSQL 16 server started with `-c max_locks_per_transaction=2048`: `SELECT name, pg_size_pretty(allocated_size) FROM pg_shmem_allocations WHERE name IN ('LOCK hash', 'PROCLOCK hash')`. Record the measured value. Any PostgreSQL 16 the implementer can start works; the embedded server `embedded-postgres` uses in `backend/packages/data/src/testSupport/globalSetup.ts` accepts extra flags;
   - how to watch growth: `SELECT count(*) FROM pg_inherits WHERE inhparent = 'public.items'::regclass`, and when to raise the value again (projected per-statement entries above about a tenth of the total);
   - the operator step:
     - the setting is postmaster-level, so it takes effect only when the container is recreated (`docker compose … up -d` with the env file the `deploy/README.md` compose bullet names);
     - do it in a maintenance window, then confirm with `docker compose … exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SHOW max_locks_per_transaction"'` (the container's own `POSTGRES_USER`; the host shell does not have it);
     - then restart the four services if any of them logged connection errors.

## Scope

### In scope
- `max_locks_per_transaction` for the production and the restore-test PostgreSQL servers, the shell assertion that keeps them equal, and the sizing document.

### Out of scope
- Partition creation's locks (#1036).
- Pruning id-only lookups (#1003).
- `max_connections`, `shared_buffers` or any other server setting.
- The integration tier's embedded server configuration.
- Automating the container recreation in `provision.sh` or `deploy.sh`.
