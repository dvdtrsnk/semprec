## Context

Model tier rationale: One known mechanism (persist a structured array on the card and return it additively) across the existing confirm handler and the card property added by a blocker, with no new tenant or authorization contract.

Today `confirmProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) writes `resultItemId` and `resultLabel` (both `text`, system-owned) on the Processing proposals card and `createConfirmProposalRouteHandler` (`backend/packages/data/src/inbox/inboxRouteHandlers.ts`) answers `POST /api/proposals/:id/confirm` with the updated card only. A client that wants to tell the user what a confirmation did ("Task X is in Tasks", "Event Y is in the calendar", "Saved to Files, follow-up task created") has only one id and one label per card, and nothing about secondary steps, the date a created Event or Journal entry lands on, or whether a transcription or MCP sync was queued as a consequence.

#1486 makes confirm write every step of a multi-step proposal in one transaction. #1451 adds the system-owned `results` property to Processing proposals. This issue fills that property inside the same confirm transaction and returns it in the confirm response, so the client can build the confirmation toast and its "Show" link from the response alone. #1943 reads `results[].updatedAt` to undo a confirmation.

Decision: `results` is additive. `resultItemId` and `resultLabel` keep their current meaning (the primary step) so existing clients are unaffected; the response envelope keeps its current shape and gains one field.

Ownership reconciliation: [[2026-11-03-confirm-results-report-only-enqueued-follow-ups]]. Existing confirm branches enqueue neither transcription nor MCP sync. Actual non-null enqueue/result obligations are retained explicitly in #1978 and #1976; this issue must not preempt their consent/intake/credential producers.

## Task

Load `state-writes`, `canonical-keys` and `testing`.

1. In the confirm path, after every step of the proposal has been written, build `results` as an array with one entry per written step, primary first:
   `{ ref, itemId, databaseKey, label, role, date, linkLabels, followUp, updatedAt, blockIds }`.
   - `ref`: the step reference from the proposal envelope.
   - `itemId` / `databaseKey`: the created or patched item and the database's actual canonical key when present (English camelCase, for example tasks, events, files). databaseKey is string|null: a genuinely keyless custom database yields null. Do not fabricate an id/name/module fallback, assign a system key or reject an otherwise valid custom-target pageContent confirm.
   - `label`: the item's title as `resolveResultLabel` already computes it.
   - `role`: `primary` or `secondary`.
   - `date`: the calendar day the item lives on (Event start day, Journal day), otherwise `null`.
   - `linkLabels`: display labels of the items the step links to (project, company and similar), read inside the transaction.
   - `followUp`: `transcriptionQueued`, `mcpSyncQueued` or `null`. All current non-enqueue confirm branches set null. The actual atomic transcriptionQueued/job obligation is assigned to #1978 and mcpSyncQueued/job to #1976, in the same confirm transaction after successful enqueue; neither is implemented or proved here. Never infer queued work from MIME, database or a later heartbeat.
   - `updatedAt`: the written item's `updatedAt` after the step, used later as the undo version.
   - `blockIds`: ids actually inserted by current legacy pageContent (including a Journal page), excluding origin notes; otherwise an empty array. Future journalEntry kind/confirm belongs to #1975/#1981; its actual blockIds obligation is retained in #1981 Task/AC. Add no new operation here. The authenticated confirming user writes blocks using the existing user writer classification (doc_updates.created_by = user), not ai_agent; this entry records that Semp proposed them. Existing doc storage has no per-user author-id field: this issue introduces no such schema/audit contract and does not claim created_by alone identifies which user.
   For a transcript card, the entry for the transcript's own step carries the transcript item id as `itemId`.
2. Persist the array through the existing confirm `updateItemWithClient` patch (add `results` to `allowedSystemKeys`) together with `status`, `resultItemId`, `resultLabel` and `history`.
3. Return validated stored `results` additively beside the existing FLAT item-envelope fields at top level, preserving id/properties/relations/blobs and the existing blob-aware serializer. Do not introduce a nested item wrapper or raw-body bypass. Extend only the optional typed results item-response field, not arbitrary response extensions. Validate persisted JSON at the data read boundary; a type-only data barrel export is permitted if needed. An already-confirmed card answered idempotently returns the stored `results` unchanged.
4. Cover with tests: a single-step confirm yields one `primary` entry; a two-step Files confirm (file plus a follow-up task) yields `primary` and `secondary` entries with the project in `linkLabels`; every currently non-enqueue confirm yields followUp:null without an invented transcription/MCP job; actual non-null+committed-job tests remain assigned to #1978/#1976; a repeated confirm returns identical `results`; a page-content confirm lists its inserted block ids in blockIds. An actual pageContent confirm targeting a custom keyless database succeeds with databaseKey:null, persists it and replays unchanged; keyed targets retain their actual keys. Validate both variants at the stored-JSON boundary.

## Scope

### In scope

- Building, persisting and returning results on confirm, with null followUp for current non-enqueue paths and explicit future producer obligations. Retain internal per-executed-step ref/itemId/databaseId from executeProposalSteps outcomes; do not reconstruct updated secondary steps from createdItemIds. Preserve existing execution ordering, transaction and return fields.

### Out of scope

- Declaring the `results` property on Processing proposals; #1451 owns it.
- Recording where each created item came from; #1659.
- Reading a confirmation back to undo it; #1943.
- Toast copy and navigation targets, which are client concerns.

## Acceptance criteria

- When a Files proposal with a follow-up task is confirmed, then the response has `resultItemId` of the file and `results` with two entries (`primary`, `secondary`), the project name in `linkLabels`, and every `updatedAt` equal to the item's current `updatedAt`.
- When a current confirm enqueues no transcription/MCP job, its entries have followUp:null; MIME type and later heartbeat do not fabricate a queued result. The original transcriptionQueued plus same-committed-job criterion is transferred intact to #1978; the corresponding MCP criterion is owned by #1976, both NOT RUN here.
- When confirm is called again on a confirmed card, then it returns 200 with the same `results` and writes nothing.
- When a page-content proposal is confirmed, then its entry's `blockIds` are the ids of the inserted blocks.
- When a step fails and the transaction rolls back, then the card has no `results`.
