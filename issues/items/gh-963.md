## Context

`semprec-agents` connects with `SEMPREC_SIDE_DATABASE_URL ?? DATABASE_URL`, and its comment states "this process is never `semprec_data`" (`backend/services/semprec-agents/src/serve.ts:15-21`). That premise no longer holds, because the process hosts the choke point in-process:

- every agent run gets the generic-operation tools from `createGenericOperationAgentTools(pool, moduleRegistry)` (`backend/services/semprec-agents/src/agentSessionComposition.ts:58`);
- those tools dispatch through `createGenericOperationGateway(pool)` (`backend/packages/agent-runtime/src/tools/generic/genericOperationAgentTools.ts:120`);
- the gateway's `createGenericApplicationService(pool)` (`backend/packages/application/src/genericOperationGateway.ts:278`) wraps `createChokePoint(pool)` (`backend/packages/application/src/genericApplicationService.ts:45-46`).

Non-destructive operations such as `item.create`, `item.patch`, `view.create` and `database.create` commit directly, by design (`docs/adr/2026-09-18-non-destructive-generic-operations-bypass-agent-approval.md`). Under `semprec_side`, which has only `SELECT` on the choke-point tables (`backend/packages/data/src/db/migrations/0040_least_privilege_roles.sql:63-66`), every such write fails. The tool then reports "permission denied for table …" to the model (`genericOperationAgentTools.ts:75-79`). `database.create` would also need `EXECUTE` on `create_items_partition`, which is granted to `semprec_data` only (`0048_create_items_partition_function.sql:35-36`).

`semprec-transcribe` was in the same position and moved to `semprec_data`: it reads `SEMPREC_API_DATABASE_URL ?? DATABASE_URL` (`backend/services/semprec-transcribe/src/serve.ts:9-10`), recorded in `docs/adr/2026-09-22-transcription-worker-choke-point-access.md`. That ADR's Decision says "All other non-API services remain `semprec_side` consumers" (`:23-24`), which this issue reverses for `semprec-agents`. Changing that requires a new ADR.

`SEMPREC_API_DATABASE_URL` already lives in the shared `/opt/semprec/shared/.env` that the agents unit loads (`deploy/systemd/semprec-agents.service:14`). So no unit file or operator change is needed.

Later issues assume agents run as `semprec_data`:
- #976 narrows identity-table DML to `semprec_data`;
- #991 runs agent jobs inside their tenant;
- #996 splits per-service secrets;
- #1051 asserts every service's role at startup.
