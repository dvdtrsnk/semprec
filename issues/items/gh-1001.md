**Blocked by:** #974

## Context

Every tenant gets its own copy of the system databases, and they carry the same canonical keys (`tasks`, `projects`, `files`, ...: `backend/packages/data/src/seed/seedTenDatabases.ts:55` sets `key` and `owner_module_id` to the same value). Two lookups still treat those keys as global:

- **`databases.key` uniqueness.** `databases_key_unique` is `UNIQUE (key)` (`backend/packages/data/src/db/migrations/0028_database_keys_nullable_names.sql:13-14`). A second tenant's `tasks` database would hit another tenant's row: the insert fails, and the failure tells the caller that the key exists elsewhere. The code depends on the constraint only by name. `createDatabase` maps a `23505` whose `constraint` is `databases_key_unique` to `ConflictError("Database key '...' is already in use", { field: "key" })` (`backend/packages/data/src/chokePoint/databasesStore.ts:9-13,93-97`). No `ON CONFLICT` anywhere uses it as an arbiter. You can verify this with `grep -rn "ON CONFLICT" backend/packages backend/services`: no hit targets `databases`.
- **Module-id resolution.** `getDatabaseByModuleId` runs `SELECT ... FROM databases WHERE owner_module_id = $1` and returns `rows[0]` (`databasesStore.ts:120-127`). It has no `system` filter, and an ambiguous result goes unnoticed. About thirty production call sites resolve a module's database this way, for example `backend/packages/data/src/migrationJob/moduleDataMigration.ts:82`, `backend/services/semprec-api/src/blobsHandler.ts:96` and `backend/services/semprec-transcribe/src/transcriptionTask.ts:242`. Under row-level security a runtime role sees only its own tenant's rows. A connection that bypasses RLS (the owner/migrating role, or the integration tier's `getTestPool()`) sees every tenant's rows, and would silently take an arbitrary tenant's database.

Tenancy state this issue builds on:
- Every tenant table carries `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)` under the RESTRICTIVE policy `tenant_isolation` (`tenant_id = (SELECT app_tenant_default())`).
- `app_tenant_default()` is `COALESCE(app_current_tenant(), app_sole_tenant())`. `app_current_tenant()` reads the GUC `app.tenant_id`.
- #974 added, beside `databases_key_unique`, the non-partial unique index `databases_tenant_key_uq` on `databases (tenant_id, key)`, and the partial unique index `databases_tenant_system_module_uq` on `(tenant_id, owner_module_id) WHERE system`.
- The legacy global keys are allowlisted in `backend/packages/data/src/__tests__/tenancyCatalog.test.ts` until #1065 drops them.

`databases_key_unique` is not an arbiter, so it can be swapped in place right away: the previous release keeps matching the same constraint name.

## Task

Load `db-migrations` (the swap) and `error-handling` (the ambiguity throw must not become a domain error).

1. **Migration.** Take the next free migration ordinal at commit time, e.g. `NNNN_databases_key_unique_per_tenant.sql`, with a header comment explaining the swap and why it is rollback-safe. In one file (the runner wraps it in a single transaction, so there is no instant without a key uniqueness):
   ```sql
   ALTER TABLE databases DROP CONSTRAINT databases_key_unique;
   ALTER TABLE databases ADD CONSTRAINT databases_key_unique UNIQUE USING INDEX databases_tenant_key_uq;
   ```
   - `USING INDEX` renames `databases_tenant_key_uq` to `databases_key_unique`, so afterwards exactly one unique index covers `(tenant_id, key)`.
   - Rollback safety: the previous release still gets `ConflictError` from the unchanged constraint name, and no `ON CONFLICT` depends on `(key)`. The migration-compatibility check (`backend/packages/data/src/__tests__/migrationCompatibility.unit.test.ts`) flags neither statement, so no exemption marker is needed.
2. **Catalog test.** In `tenancyCatalog.test.ts`, remove `databases_key_unique` from `LEGACY_GLOBAL_UNIQUES` (it now leads with `tenant_id`), and change #974's existence assertion for `databases_tenant_key_uq` to expect that index under its new name `databases_key_unique` (a unique constraint on `(tenant_id, key)`).
3. **`getDatabaseByModuleId` (`databasesStore.ts:120-127`).**
   - Query `WHERE owner_module_id = $1 AND system`.
   - On more than one row, throw a plain `Error` naming the module id and the row count, never a `ChokePointError`: it is an invariant violation, not a client error. Zero rows still return `null`; one row returns it.
   - Update the docstring: under RLS the lookup is per tenant, and a caller that sees several tenants (an RLS-bypassing role) fails instead of picking one.
   - `createDatabase`'s conflict mapping stays as it is.
4. **Test fixtures.** Some fixtures create a non-system database with `ownerModuleId` and then resolve it by module id. Give them `system: true`:
   - `backend/packages/data/src/__tests__/moduleDataMigration.test.ts:35`;
   - `backend/packages/e2e/src/__tests__/crossModuleScenario.e2e.test.ts:109-110` (the data-migration case).

   The other non-system `ownerModuleId` fixtures (`crossModuleScenario.e2e.test.ts:85-86,126`) never resolve by module id, and stay as they are.
5. **Tests.** New `backend/packages/data/src/__tests__/databaseKeysPerTenant.test.ts`. The two-tenant cases run in one transaction on `getTestPool()` (the owner), rolled back at the end:
   - `DROP INDEX IF EXISTS tenants_single_tenant_guard`, then insert a second `tenants` row;
   - switch tenants with `SELECT set_config('app.tenant_id', $1, true)`;
   - `SET LOCAL ROLE semprec_data` where a case needs RLS to apply.

   Integration files run one at a time (`fileParallelism: false`, `backend/vitest.integration.config.ts:20`), so this DDL cannot leak into another test.
