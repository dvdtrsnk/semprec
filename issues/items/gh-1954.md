## Context

Model tier rationale: It extends the closed notification kind catalog with a database constraint migration and defines an actionable APNs payload that an iOS client depends on, across the fanout job, the APNs adapter, the respond transaction and the badge endpoint, so several shared hotspot files change at once.

Today `NOTIFICATION_KINDS` (`backend/packages/data/src/notifications/notificationKinds.ts`) is closed and mirrored by the `notifications_kind_check` constraint (last redefined in migration `0035_agent_guidance_drift.sql`, possibly by later migrations; read the current one). Notification titles are rendered at write time from `backend/packages/data/src/notifications/i18n/{cs,en}.json` (`notify.ts`). The APNs request built by `sendApnsNotification` (`push/apnsAdapter.ts`) carries only `aps.alert.title`, `link_href` and `notification_id`, with no category and no custom data, so a notification cannot offer buttons.

#1929 creates pending invitations from incoming mail and #1944 answers them. This issue makes the user notice a new invitation and lets them answer it from the notification: a `calendar_invitation` notification, pushed with the APNs category `CALENDAR_INVITATION` and the invitation id, so the iOS app (which registers the Accept, Maybe and Decline actions itself) can call `POST /api/calendar/invitations/:id/respond` with its Bearer session. The route already accepts Bearer sessions; nothing changes there.

It builds on the notification work of other issues: the kind classification and the category `invites` (#1440), the per-user preference filter and interruption level in the fan-out (#1443), the resolved-notification mechanism and its silent dismiss push (#1463, #1826), and the badge on pushes and the pending-decisions endpoint (#1828, #1891).

Decision: the notification is created only when an invitation is first created (not on a later update of the same `UID`), once per invitation. Its category is `invites`, it is pushed, and its severity is the lowest one the classification offers for ordinary, non-error notifications.

Decision: `link_href` is `null` (the app opens the invitation from the payload).

## Scope

### In scope

- The `calendar_invitation` notification kind, its producer on first creation, the APNs category and invitation id, resolving it on an answer, and the real `pendingInvites` count.

### Out of scope

- Registering the Accept, Maybe and Decline actions and handling a tapped action on iOS.
- The notification preference storage, category filter and interruption level: #1441, #1443.
- The generic resolve, dismiss and badge mechanisms themselves: #1463, #1826, #1891.
- A notification for an event added to a shared calendar: shared calendars are not planned yet; they wait for a product decision.
- The invitation list: it is the generic query over the Invitations database ordered by `startsAt`, which needs no new code.

## Acceptance criteria

- When a new pending invitation is created from mail, then one `calendar_invitation` notification exists for the tenant's user, and the push carries `aps.category` `CALENDAR_INVITATION` and the invitation id.
- When the same invitation is updated by a higher `SEQUENCE`, then no further notification is created.
- When the user answers the invitation (from the app or from the notification action), then its notification is resolved and `pendingInvites` in the badge counts decreases by one.
- When the `invites` category is switched off, then the notification is stored and no push is sent.
- When the new migration runs on a database with earlier notifications, then all existing rows and kinds remain valid.
