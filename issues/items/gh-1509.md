**Model tier:** high

## Context

Model tier rationale: It adds a new tenant-scoped identity link between the login user and a People item, with a write endpoint that must refuse foreign and unknown ids identically, plus a per-tenant data cutover that seven other issues depend on.

The tenant owner has an account (`users`: id, tenant_id, role, email, locale, in `0001_core_schema.sql`, `0025_auth_schema.sql`, `0056_tenants.sql`) but no link to a person in the People collection. `users` is a global table without row-level security and a foreign key to an item cannot be expressed (items have the composite key `(database_id, id)`), so the link is stored on the tenant side. Because of this the backend cannot tell who "me" is when it attributes an action item to the user, marks the meeting organizer, picks the speaker candidates of a transcript, or leaves the user out of the people of a task or recording.

Today: `System settings` is a singleton database of the tenant (`backend/packages/data/src/seed/seedSystem.ts`, `backend/packages/data/src/systemSettings.ts`) holding the supervisor name and timezone; `People.emails` plus `person_email_index` with `lookupPersonIdByEmail` (`backend/packages/data/src/mail/personEmailIndexStore.ts`) map an address to at most one person per tenant (primary key `(tenant_id, email)`); `GET /api/auth/session` in `backend/services/semprec-api/src/authHandler.ts` returns `{ user, session }` with no person.

This issue stores the link as a relation property on the System settings item, exposes it through the session and a write endpoint, and fills it once per tenant from the user's e-mail. It is independent of the other People issues. It is a blocker of #1767, #1770, #1697, #1757, #1818, #1640 and #1724, which each use "the user's own person" in their own rules.

Decision: the user's own person is an ordinary People item that is hidden from the People collection and from pickers such as "people at an event"; it is not shown as a "Me" row. The backend adds no "is me" flag and does not change the item: the client uses `user.personId` (or a filter `id != personId` on People queries) to leave it out. The person stays reachable through the Profile, and the backend keeps using it elsewhere (for example as a speaker candidate).

Decision: nothing is created automatically. When no person matches the user's e-mail, the link stays empty and the client offers a choice.

Shared-file ordering: this issue also waits for #1475, #1507 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `db-migrations`, `error-handling`, `canonical-keys` and `testing`.

1. Storage. Add a one-way `one_to_one` relation property `selfPerson` from the System settings database to People, `owner: "user"`, created in `seedSystem.ts` for fresh tenants. Purging a person already deletes both edge sides (`deleteItemDependents` in `chokePoint/itemTrash.ts`); a trashed person reads as "not set". The `users` table is not changed.
2. API. Add `PUT /api/auth/self-person` with body `{ personId: string | null }` in `authHandler.ts`. In one transaction: when `personId` is a uuid, require a live (not trashed) People item in the caller's tenant, otherwise respond 404 (a foreign tenant's id and a nonexistent id must be indistinguishable); replace any existing edge (delete, then create) so exactly one remains; with `null`, delete the edge. Respond with `{ personId }`. Add a `personId` field (`string | null`) to `user` in `GET /api/auth/session`, additive; `null` when unset or when the person is trashed.
3. Fill. Create a per-tenant cutover `backend/packages/data/src/tenancy/selfPersonCutoverMigration.ts`, registered in `db/tenantCutoverMigrations.ts`: for the tenant's user, if `selfPerson` is unset and `lookupPersonIdByEmail(client, user.email)` returns a person, create the edge; otherwise leave it unset. It also adds the `selfPerson` property to a populated System settings database by direct insert (idempotent; the schema is locked, as in other cutovers). An address that two people list is reported by `reindexPersonEmails` as a conflict; the cutover simply finds no match for the second person.
4. Add the route to `backend/services/semprec-api/src/routeMatrix.ts`, its `ROUTE_HANDLER_FILES` entry in `backend/services/semprec-api/src/__tests__/chokePointWriteBoundary.unit.test.ts`, and a cross-tenant case to `backend/services/semprec-api/src/__tests__/tenantIsolationRoutes.test.ts`.
5. Tests for the acceptance criteria below.

## Scope

### In scope

- The `selfPerson` link, `PUT /api/auth/self-person`, `user.personId` in the session, and the one-time per-tenant fill from the user's e-mail.

### Out of scope

- Using the link in the rules of #1767, #1770, #1640, #1697, #1757, #1818 and #1724; each owns its own use.
- Leaving the user's own person out of the People collection and out of "people at an event" pickers: done by the client with `personId`.
- Giving the agent run context the user's person (name for summaries and speaker assignment): not planned in this issue.
- Automatically creating a person for the user.

## Acceptance criteria

- When the user sets a live person of the tenant with `PUT /api/auth/self-person`, then `GET /api/auth/session` returns that id as `user.personId`.
- When the person is purged or trashed, then `user.personId` is `null`.
- When `personId` is a person of another tenant or an id that does not exist, then the response is 404 and is identical for both.
- When `personId` is `null`, then the link is removed and the session returns `null`.
- When the cutover runs and the user's e-mail is listed in `person_email_index` for a person of the tenant, then that person is linked; when there is no match, then it stays `null`; running it again changes nothing.
- When tenant B calls the endpoint, then it never reads or modifies tenant A's link.
