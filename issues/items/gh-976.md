## Context

The identity plane decides who a request is and which tenant it belongs to. It is made of `users` (now carrying `tenant_id` and `role`, from #968), `sessions`, `password_reset_tokens`, `login_attempts` and `tenants`.

Today every runtime role can rewrite it. `0040_least_privilege_roles.sql:71-82` grants full DML on `users`, `password_reset_tokens`, `sessions` and `login_attempts` to `semprec_side`, which `semprec_data` inherits through `GRANT semprec_side TO semprec_data` (`0040:47`). #968 granted `tenants` the same way, following the rule for a table the choke point does not write (`docs/operations/database-roles.md:41-48`).

So any process holding the side role can do the following: mint a session, rebind a user to another tenant, promote a user to `admin`, or flip a tenant's status. The processes holding it are `semprec-ai-gateway` and the restore-test recorder (`docs/operations/database-roles.md:24-30`). Once tenants and roles exist, that is a cross-tenant escalation path.

Every legitimate writer runs in `semprec-api`, which connects as `semprec_data`:
- login, logout and session touch (`backend/packages/data/src/auth/authActions.ts:105-140`, `:203-223`);
- first-account setup (`authActions.ts:174-190`);
- password reset (`backend/packages/data/src/auth/passwordResetActions.ts:63-88`, `:118`).

No `semprec_side` process writes these tables. The production services that import the auth stores are all `semprec-api` handlers. `semprec-agents` connects as `semprec_data` after #963, and that issue also edits the role table in `docs/operations/database-roles.md`.

The `bigserial` behind `login_attempts.id` needs sequence `USAGE`. `semprec_data` keeps that through its membership, because `semprec_side` holds `USAGE, SELECT` on all sequences (`0040:89`, `0047_side_role_default_sequence_privileges.sql:13-14`).

## Task

Load `db-migrations`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_identity_tables_api_role_only.sql` (take the next free migration ordinal at commit time):
   ```sql
   GRANT SELECT, INSERT, UPDATE, DELETE ON users, sessions, password_reset_tokens, login_attempts, tenants TO semprec_data;
   REVOKE INSERT, UPDATE, DELETE ON users, sessions, password_reset_tokens, login_attempts, tenants FROM semprec_side;
   ```
   - `semprec_side` keeps `SELECT`, which the restore-test recorder and `app_sole_tenant()` need.
   - The header comment says why. The identity plane is written only by the API process. A side-role compromise must not be able to mint sessions, rebind tenants or change roles.
   - It also says why the previous release keeps working: its API already runs as `semprec_data`, which now holds the grant directly, and no side-role process writes these tables.
2. `docs/operations/database-roles.md`:
   - Add an "Identity tables" section naming the five tables, the split (`semprec_data` DML, `semprec_side` `SELECT`) and the reason.
   - Extend "Extending the grants" (lines 41-48) so that a new identity-plane table is granted the same way, directly to `semprec_data`, not through `semprec_side`.
   - Leave the role table (lines 24-30) to #963's wording.
3. `backend/packages/data/src/__tests__/identityTablePrivileges.test.ts` (new, integration). Log in as each runtime role the way `__tests__/leastPrivilegeRoles.test.ts:15-41` does: its own random password, set via `ALTER ROLE` on the superuser pool. Prove the criteria below.
4. If `__tests__/leastPrivilegeRoles.test.ts` asserts, when this is implemented, that `semprec_side` holds `INSERT`/`UPDATE`/`DELETE` on every non-choke-point table, narrow that assertion to exclude these five tables and nothing else.

## Acceptance criteria
- As `semprec_side`, `INSERT`, `UPDATE` and `DELETE` on each of `users`, `sessions`, `password_reset_tokens`, `login_attempts` and `tenants` fail with `permission denied`, and `SELECT` on each succeeds (integration, `identityTablePrivileges.test.ts`).
- As `semprec_data`, the real flows succeed against these tables: `bootstrapFirstAccount` on an empty `users`, then `login` (session row and login attempt written), `verifySessionToken` (touches `last_seen_at`), `logout`, `requestPasswordReset` with a fake mailer, and `resetPassword` with the captured token (integration).
- As `semprec_data`, a failed login records its `login_attempts` row, which proves sequence access through the inherited grant (integration).
- `has_table_privilege('semprec_data', t, 'INSERT')` is true for each of the five tables even after `REVOKE semprec_side FROM semprec_data` inside a rolled-back transaction. This proves the grant is direct, not inherited (integration).
- `semprec_side` still holds full DML on every other non-choke-point table it held before. `leastPrivilegeRoles.test.ts` passes (integration).
- The migration-compatibility unit check passes without an exemption marker (unit).
