### Requirement gh-1943: [inbox-proposals 16/19] Undo a confirmed proposal

#### Context

Model tier rationale: A cross-database transactional reversal of arbitrary earlier writes with optimistic-concurrency preconditions, hard and soft deletes and credential removal, where an error destroys or leaves behind user data.

A confirmed card is final today: `confirmProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) writes the destination items and relation edges and locks the card, and `rejectProposalWithClient` refuses a `confirmed` card. The Inbox undo must return the last confirmed decision to the stack with the values it had.

What the repository offers for reversal:
- Items go to the trash with `softDeleteItem` and return with `restoreItem` (`backend/packages/data/src/chokePoint/itemTrash.ts`). Relation edges have no soft delete: deleting an item leaves its edges and a restore only recomputes them. `deleteRelationWithClient` (`backend/packages/data/src/chokePoint/relationOps.ts`) deletes an edge for good.
- A transcript's speaker display name is composed from the `speakers` edge (`backend/packages/data/src/transcription/transcriptionRouteHandlers.ts`), so deleting the edge restores the "Speaker N" label.
- Page blocks have `deleteBlock` (`backend/packages/data/src/docs/blocks.ts`) but no REST path.
- A stored MCP credential is removed with `deleteCredential` (`backend/packages/data/src/credentials/externalCredentialsStore.ts`).

#1648 stores `results[]` on the card, each with the item id and the `updatedAt` after the step, and #1659 records an origin row per created item. #1937 provides the reopen route and transition for rejected cards; #1379 records the contract this issue implements. #1984 cancels jobs that confirmation queued.

Decision (product owner): no time limit applies; the `updatedAt` precondition is the only guard, and when it fails the undo is refused with an explanation and overwrites nothing. Decision (product owner): an approval card does not support undo and `reopen` on it is not offered (the exactly-once ADR stays as is); an executed approved action is reverted by restoring from the trash or by a new change. Decision: for a transcript card, undoing deletes the `event` or `speakers` edge as the confirmation wrote it; Decision (product owner): when the confirmation moved an Inbox attachment into Files (#1703, for example a confirmed recording), the undo reverses everything except the file. The Files item stays live in Files with its content and its origin row (the user can move it to the trash), it is not part of the `updatedAt` precondition, and the reopen response says so explicitly in `keptItems: [{ itemId, databaseKey, label, reason: "attachmentMovedToFiles" }]`. There is no reverse operation of the move.

#### Task

Load `state-writes`, `error-handling` and `testing`.

1. Extend `POST /api/proposals/:id/reopen` (from #1937) and `reopenProposalWithClient` so a `confirmed` card is reopened in one transaction, following the ADR from #1379.
2. Precondition check before any write: for every `results[]` entry that created or changed an item, the current `updatedAt` equals the stored one; a missing item (permanently deleted) or any mismatch aborts with 409 `version_conflict` whose details carry the changed item (`itemId`, `databaseKey`, `label`) so the client can explain why nothing was undone, and nothing is written. A Files item kept by the rule above is not checked.
3. Reverse in this order, all in the same transaction:
   a. delete step edges created between existing items (link steps, transcript `event` and `speakers` edges) with `deleteRelationWithClient`;
   b. restore `before` values of items the confirmation patched (update steps), using the values recorded for the step;
   c. remove page blocks inserted by the confirmation by the ids derived from the proposal;
   d. soft-delete the items the confirmation created, together with their origin rows (#1659) removed, except a Files item that received a moved Inbox attachment, which stays;
   e. delete a credential stored for a created MCP server item.
4. Set the card to `proposed` with its original effective envelope, clear `resultItemId`, `resultLabel` and `results`, append a `reopened` history entry and enqueue the Journal inbox recompute; return `keptItems` next to the card (an empty array when nothing was kept).
5. Tests: reopen a confirmed task proposal sends the task to the trash and returns the card to `proposed` with identical values; after the task is edited, reopen answers 409 and nothing changes; a page-insert confirmation reopens by deleting only the inserted blocks; a speaker-mapping confirmation deletes the `speakers` edge and the speakers read shows "Speaker N" again; a two-step proposal is reversed atomically (a failure in the second reversal rolls back the first); undoing a confirmation that moved an attachment into Files reverses the other steps, leaves the Files item live and lists it in `keptItems`.

### Requirement gh-1947: [inbox-editing 20/23] Replace an Inbox item's type and recompute its card

#### Context

Model tier rationale: A new route that changes a relation edge, clears user-owned state, changes the card lifecycle (a new transient status) and triggers an out-of-band job in one transaction, with a locked-card conflict and an optimistic version check, so concurrency and lifecycle ownership are both at stake.

An Inbox item that the assistant could not classify shows as "needs clarification" with tiles for the possible types; choosing one should immediately turn the card into a proposal of that type, keeping the source. An already typed item can be moved to another type the same way. Today the type is chosen by writing the relation `Inbox.type` through `PUT /api/items/:id/relations/type/:typeId`; the relation is many-to-many, so the tick simply takes the first edge, and nothing runs the tick after an edge write (heartbeats fire on item create, update and delete only, `triggerOnItemEventHeartbeats` in `backend/packages/data/src/scheduler/schedulerStore.ts`). Even if it did run, the tick's fingerprint gate would end it when the emoji and text did not change.

This issue adds the single route for changing an item's type: `PUT /api/inbox/items/:id/type { typeId, ifVersion? }`, a custom route with justification `transactional-semantics` (edge replacement, state clearing and job trigger must commit together). It builds on: #1669 (the type of an item is locked once its card is decided), #1924 (the helper that decides which manual values survive a destination change), #1937 (reopening decided cards, which the lock rule respects) and #1434 (the tick exists in the api runtime). The related issue #1718 also reacts to a type-edge change; both can fire, and the tick job key replaces a pending job, so a double trigger is harmless.

Decision: the route does not compute the proposal. It marks the card `computing` and enqueues the tick; the tick, seeing a card in `computing`, bypasses the fingerprint gate for it (this issue adds that bypass; the status `computing` exists with the card-state properties, #1451). Until the tick finishes the card reports `computing`; the result arrives as `proposed` with the new type's values stored as `aiProposal`. Decided by the product owner: the switch goes through the `computing` interstate, one general mechanism for every recompute, and proposals are not precomputed for candidate types.

Decision: errors: unknown or archived type -> `ValidationError` on `typeId`; a card that is `confirmed` or `rejected` -> 409 with code `proposal_locked` (reuse the error class if #1669 introduced one, otherwise add `ProposalLockedError` in `backend/packages/data/src/errors.ts` and the code to the adapter's error contract); a card whose `updatedAt` differs from `ifVersion` -> 409 `version_conflict` with the current card. `ifVersion` refers to the proposal card; an item without a card takes no `ifVersion`.

Shared-file ordering: this issue also waits for #1940, #1944 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-2026: [inbox-editing 22/23] Show a proposal card stuck in computing as failed after a timeout

#### Context

Model tier rationale: One derived read rule in the card read model plus one branch in the existing recompute action, driven by a time constant, with no new storage, lifecycle state or tenant contract; the clock-dependent cases need careful tests.

A proposal card goes to `computing` when the user picks a type (#1947) or asks for a recompute (#1955); the tick then writes `proposed`, or `computeFailed` when the computation fails (#1485). If the tick never finishes (a lost job, a crashed worker), the card stays in `computing` indefinitely and the Inbox list (#1807) shows an endless computing indication. The product owner decided that the computing state has a visible timeout: after it, the card shows an error with a Retry action, because endless spinning is unpredictable. Recording a failed computation on the card stays with #1485; this issue only makes the timeout visible and retryable.

Decision: the timeout is one constant, `COMPUTING_TIMEOUT_MS`, set to 10 minutes; it is not a setting.

Decision: nothing is written when the timeout passes. When `GET /api/inbox/cards` (#1807) builds a card whose stored status is `computing` and whose `updatedAt` is older than the timeout, it returns the card with `status: "computeFailed"` and `computeTimedOut: true`, so the client shows the same "proposal failed" state and Retry action as for a recorded failure. Such a card stays uncounted, like every `computing` and `computeFailed` card. If the tick finishes later, its result replaces the state as usual.

Decision: Retry calls `POST /api/proposals/:id/recompute` (#1955). That route returns a `computing` card unchanged and enqueues no second job; for a card past the timeout it instead proceeds as for any other accepted status: it writes `computing` again (new `updatedAt`), appends a `recompute` history entry and triggers the Inbox tick heartbeat. A card computing within the timeout stays idempotent.

#### Task

Load `state-writes` and `testing`.

1. In `backend/packages/data/src/inbox/inboxCardsStore.ts` export the constant `COMPUTING_TIMEOUT_MS` and a pure helper `isComputingTimedOut(card, now)` (stored status `computing` and `updatedAt` older than `now - COMPUTING_TIMEOUT_MS`), and apply it when building each card so a timed-out card is returned as decided above. The count is unchanged.
2. In `recomputeProposalWithClient` (`backend/packages/data/src/inbox/proposalActions.ts`) treat a `computing` card for which `isComputingTimedOut` is true as an accepted status (write `computing`, the history entry and the heartbeat trigger) instead of returning it unchanged.
3. Tests with a controlled clock: a card computing for less than the timeout is listed as `computing`; after the timeout it is listed as `computeFailed` with `computeTimedOut: true`, the stored card is unchanged and the count does not include it; recompute on it enqueues one tick job and the card is `computing` again with a new `updatedAt`; recompute within the timeout enqueues nothing; a late tick result turns a timed-out card into `proposed`.

- backend/packages/data/src/inbox/proposalActions.ts (recomputeProposalWithClient)

#### Acceptance criteria

- Given a card in `computing` whose `updatedAt` is older than `COMPUTING_TIMEOUT_MS`, when `GET /api/inbox/cards` is read, then the card has `status: "computeFailed"` and `computeTimedOut: true`, and the stored card still has status `computing`.

### Requirement gh-1959: [inbox-editing 23/23] Add GET /api/proposals/:id/options

#### Context

Model tier rationale: A new tenant-scoped read route that merges several source databases into one ordered, localized list and must expose nothing across tenants, with ordering rules derived from relation edge counts.

When the user edits an Inbox proposal card, fields such as project, area, person, company or page open a picker of choices. Today the only way to build such a picker is the generic `POST /api/databases/:id/query`, which cannot express the card's rules: the card's current value first, the assistant's suggestion next, then the most used targets, a "none" choice in a fixed place, archived targets shown but not selectable, steps that would be created shown as "new - will be created", and a stable order. Areas had no color before #1515; People have no color or initials property at all. There is no usage tracking: items have no created timestamp and usage has to be counted from relation edges (`item_relations`).

This issue adds `GET /api/proposals/:id/options?field=<key>`, a custom route registered in the Inbox module manifest with justification `single-consumer-read` (it is shaped for exactly one consumer, the card editor's picker). Relation validation from #1426 defines the state of a target (archived, deleted; a `done` project is a valid target); this route uses the same evaluation for `disabled`. The recomputed suggestion used for ordering is the one on the card's envelope, as updated by recompute (#1955).

Decision: `field` is a closed set: `project`, `area`, `people`, `company`, `page`, `mcpProjects`. Any other value is a `ValidationError`. An optional `includeDone=true` lists `done` projects as ordinary, selectable choices; without it they are hidden (decided by the product owner: a done project is a valid target, the picker only hides it by default). The response is `{ options: Option[] }` with `Option = { id: string | null, ref?: string, label, color?, initials?, disabled, disabledReason?: "archived" | "deleted", hint?, suggested, none?: true }`.

Decision: order is: (1) the card's current value; (2) the suggested target (from the envelope); (3) number of edges of that relation pointing at the target, descending; (4) name, locale-aware ascending. The "none" choice is last for `project` and `company` and first for the others where a none choice exists. An archived or deleted target appears only when it is the card's current value (so an invalid card can show the archived project first, `disabled: true`, `disabledReason: "archived"`); otherwise it is omitted. A `done` project appears when it is the card's current value or when `includeDone=true`, and is then selectable (`disabled: false`). A step of the proposal that would create a new item (for example a new company) is listed with its `ref` instead of an `id`, `suggested: true` and the localized hint "new - will be created".

Decision: `initials` for people are derived on the server from the name (first letters of the first and last word); the color of a person is not stored or returned and the client derives it. Projects return `Projects.color`, areas return `Areas.color`. `mcpProjects` lists every project except the none choice. Pages lists projects, areas and subpages that can host page content (as defined by the page placement work in this program).

Shared-file ordering: this issue also waits for #1956 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

### Requirement gh-1963: [inbox-attachments 04/08] Attach uploaded blobs when capturing an Inbox item

#### Context

Model tier rationale: One extension of an existing capture route and an upload allowlist across known seams, with tenant isolation and a clear rejection table, using the blob upload route and attachment store that blockers deliver.

An Inbox item is captured with `POST /api/inbox/items` (#1961). A photo, scanned document, audio note or shared file belongs to that capture. The client first uploads the bytes with `POST /api/blobs` (#1401), which stores a blob without a Files item, then sends the blob ids in the capture. Today `POST /api/blobs` accepts only `image/*`, and the capture route knows no attachments. #1564 created the `inbox_attachments` table and its store.

Decisions:
- Allowed attachment types (by the blob's stored mime type, which is decided from the bytes and never from the client's header, see #1410): PDF, JPEG, PNG, XLSX, DOCX (the types Files knows), and audio M4A (`audio/mp4`, `audio/x-m4a`) and MP3 (`audio/mpeg`). HEIC is not allowed: the iPhone client converts HEIC to JPEG before upload, and the server does not convert HEIC. Further types are added only when they are needed.
- A capture may have an empty `text` when it has at least one attachment (a photo with no words is a normal capture).
- At most 10 attachments per capture; the same `blobId` twice in one request is a validation error.
- A blob id that does not exist or belongs to another tenant answers the same as any invalid blob id (no enumeration).
- Rejections are all-or-nothing: if one attachment is refused, no Inbox item and no attachment is created.
