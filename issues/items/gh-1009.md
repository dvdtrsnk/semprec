## Context

Model tier rationale: Two lookups merge into one transaction before the existing branches, with enumerated two-tenant tests.

`GET /api/blobs/:id` is a bespoke listener (`backend/services/semprec-api/src/blobsHandler.ts:115-205`). After `authenticateRequest` it handles a request in this order:
1. It reads the row with `getBlob` in a transaction of its own (`:129-130`).
2. It answers `304` with the content-hash `ETag` when `If-None-Match` matches (`:132-140`).
3. It answers `416` for an unsatisfiable `Range` (`:142-148`).
4. Only then does it resolve the download filename, in a second transaction (`resolveDownloadFilename`, `:93-102,152`). That transaction looks up the Files database with `getDatabaseByModuleId` and the lowest-id Files item pointing at the blob with `findFileItemByBlobId`.

Whether a blob exists for the caller is the one decision every branch after it depends on, including the `304` that echoes a content hash. It has to come from the caller's tenant before any conditional branch, and the filename has to come from the same tenant's Files item. A foreign blob id must be indistinguishable from an unknown one: same status and same body, whatever `If-None-Match` or `Range` the request carries.

Tenancy state this issue builds on:
- `blobs`, `databases` and `items` are tenant tables, under the RESTRICTIVE policy `tenant_isolation` (`tenant_id = (SELECT app_tenant_default())`).
- `app_tenant_default()` is `COALESCE(app_current_tenant(), app_sole_tenant())` over the GUC `app.tenant_id`.
- #981 runs this listener inside `runInTenant(<caller's tenant>, …)` (`@semprec/shared`), so `withTransaction` sets that GUC.
- #1008 made blobs per tenant: rows dedupe per tenant, and new storage keys are prefixed `<tenantId>/`.

The acceptance criteria use the two-tenant runtime-role harness of #975: `createTestTenant()`, a `semprec_data` pool, and a user and session bound to each tenant.

## Task

Load `io-hardening` (an edge that streams bytes and answers conditional requests) and `error-handling` (a missing blob maps to the one `not_found` body, nothing else).

1. **One resolution transaction.** Replace the separate `getBlob` transaction (`:129-130`) and `resolveDownloadFilename` (`:93-102`) with one `withTransaction` that runs before any conditional branch:
   - read the blob with `getBlob`;
   - when it exists, resolve the Files database with `getDatabaseByModuleId(client, FILES_MODULE_ID)` and the item with `findFileItemByBlobId`;
   - return `{ blob, filename }`, or `null` when the blob is not visible. Keep the filename fallback to `blob.id` as it is.

   A `null` throws `NotFoundError` and goes through the existing `ChokePointError` path (`:185-189`). That path answers `404` with `{"error":{"code":"not_found"}}` and no other details.
2. **Branch order.** After the resolution come the `If-None-Match` → `304` branch, then the `Range` → `416` branch, then streaming. The streaming, header and disposition logic is otherwise unchanged.
   - Do not add hand-written `tenant_id` predicates; the scope from #981 and RLS confine every read.
   - Update the listener's docstring: what the caller may see is decided first, in the caller's tenant.
3. **Tests.** New `backend/services/semprec-api/src/__tests__/blobsPerTenant.test.ts`, over the listener as `backend/services/semprec-api/src/__tests__/filesAndBlobsHandler.test.ts` builds it, on the #975 harness's `semprec_data` pool. Upload one file per tenant, with different bytes.

## Scope

### In scope
- Resolving the blob and its filename in one transaction inside the caller's tenant, before every conditional branch.
- The two-tenant tests.

### Out of scope
- `Cache-Control: no-store` on API responses, including this listener (#1072).
- Per-tenant blob storage and dedupe (#1008).
- Running the listener in the caller's scope (#981).
- The exhaustive route-isolation suite (#1053).
- Changing the ETag scheme or the inline-safe MIME list.

## Acceptance criteria

All integration tests (`*.test.ts`) on the #975 harness.
- **Foreign id with `If-None-Match`.** User B requests A's blob id with an `If-None-Match` equal to A's `ETag` and gets `404` with body `{"error":{"code":"not_found"}}`. The response has no `ETag`. Status, body and `Content-Type` are byte-for-byte identical to a request for a random UUID.
- **Foreign id with `Range`.** User B requests A's blob id with `Range: bytes=0-0` and gets the same `404` as for a random UUID, never `206` or `416`.
- **Plain foreign request.** User B requesting A's blob id with no conditional header gets the same `404`, and no `readStream` is opened. Use a spy storage to check.
- **Own blob still works.** User A requesting A's blob gets:
  - `200` with the bytes, and `Content-Disposition` naming A's own Files item;
  - `304` for a matching `If-None-Match`;
  - `206` for a valid `Range`;
  - `416` for an unsatisfiable `Range`.

  The existing `filesAndBlobsHandler.test.ts` and `blobsHandlerAbort.test.ts` pass unchanged.
- **Filename fallback.** A's blob with no Files item in A's tenant downloads with the blob id as its filename, even when tenant B has a Files item whose `file.blobId` names that id.
