**Blocked by:** #1774
**Model tier:** medium

## Context

Model tier rationale: One mechanism (making the chosen calendar edge and the other relations visible to the default-calendar hook inside the same create transaction) over existing create, idempotency and relation fixtures, with a small risk in write ordering that the tests pin down.

An Event the user creates in the app carries a title, place, description, optionally a project and a few people, and a chosen calendar, and it must appear as one atomic action. Today `POST /api/databases/:id/items` with an `Idempotency-Key` (`backend/services/semprec-api/src/itemsHandler.ts`) takes properties only; the relation input schema (`ItemCreateInputSchema`) has no relations, so each edge is a separate `PUT /api/items/:id/relations/:propertyKey/:targetItemId`, and a single-valued relation rejects a second PUT with 409 `cardinality_violation` (`chokePoint/relationOps.ts`). A partly created Event with a missing edge is the failure to avoid.

#1590 lets `item.create` take `relations` (for example `{ calendar, project, people }`) and write the item and its edges in one transaction with the Idempotency-Key. #1761 adds a create hook that assigns the default calendar to every Event. These two collide: if the hook always adds the default calendar edge, an Event created with a chosen calendar would end up with both, or with a cardinality error. #1416 gave Events the description and place keys and #1663 validates the date and time keys on the create path used here. The calendar agenda in #1762 reads the created Event.

Decision: the default-calendar hook does not add an edge when the item already has a calendar edge in the same transaction. The create path writes the edges from `relations` before the hook runs (or the hook is given the relations in its context). A custom route `POST /api/calendar/events` is not added; it is a fallback only if the hook cannot be made to see the relations, and that case would be raised before implementing.

Decision: the create sets no default `type`. An Event created from the calendar without a `type` keeps `type` empty (it stays the user's own value), and an invited person's "Invited" label is shown by clients from the participant's role on the edge, never stored as the Event type.

Shared-file ordering: this issue also waits for #1774 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Ensure the `#1590` create path writes the edges from `relations` before the Events create hooks run, or passes the relations to them. Pick one mechanism and describe it in the pull request.
2. Make the default-calendar hook from #1761 a no-op when the new Event already has an edge in its `calendar` relation in this transaction.
3. Confirm that an Event created with `place`, `description` (Markdown with a `- [ ]` line) and `relations` `{ calendar, project, people }` is validated by the Events create hook from #1663, so a bad date or time fails the whole create.
4. Tests: one create writes the Event and five edges (calendar Work, not Personal, one project, three people) in one transaction; an invalid target for any edge creates nothing; the same Idempotency-Key returns the same Event and `description` unchanged; an Event created without `relations` still gets the default calendar; a create with an invalid `timeTo` creates nothing; an Event created without `type` has `type` empty after the create.

## Scope

### In scope

- The ordering between relation edges and the default-calendar hook inside one create, and the tests that prove an Event with a calendar, project and people is created atomically and idempotently.

### Out of scope

- The `relations` input of item creation itself: #1590.
- The default-calendar hook itself: #1761.
- Reading relations back or an Event's page summary and `hasPage`; these belong to the relation read and page-summary work.
- Invitees as free text and invitation sending, alerts and attachments.
- Editing in the detail view: a field patch with `ifVersion`, a project replaced with a single-relation set, people as edges; these use operations that already exist or are delivered by other issues.
- A custom route `POST /api/calendar/events`; it is not planned unless this approach proves impossible.

## Acceptance criteria

- When an Event is created with `place` `"Kancelář, Karlín"`, `description` `"## Agenda"` plus a checklist line, and `relations` for calendar Work, a project and three people, then one transaction creates the Event and five edges, and the Event's calendar is Work, not Personal.
- When any edge target is invalid or the date and time are invalid, then nothing is created.
- When the same `Idempotency-Key` is sent again, then the same Event is returned and `description` is unchanged.
- When an Event is created without a calendar relation, then it receives the default calendar exactly as before.
- When an Event is created without `type`, then its stored `type` is empty.
