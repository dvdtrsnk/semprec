## Context

Model tier rationale: The two-cap check runs under the existing lock with given SQL, but it touches the gateway core, three handlers, startup config and many fixtures.

Every gateway call reserves before it calls the provider. `reserve` (`backend/packages/ai-gateway/src/gateway.ts:53-66`):

1. takes `pg_advisory_xact_lock(hashtext('ai_gateway_budget'))` (`:55`);
2. runs `assertWithinBudget` (`:29-42`);
3. inserts a `reserved` `ai_gateway_calls` row.

`assertWithinBudget` reads the caps from the single settings item through `getAiBudgetsWithTimezone` (`backend/packages/data/src/systemSettings.ts:109-112`) and compares them with `getGatewaySpend` (`backend/packages/data/src/aiGateway/aiGatewayCallsStore.ts:218-229`). The rule is: refuse when `spent >= cap`. The refusal message names the cap and the amount spent (`gateway.ts:35`, `:38-40`). All three handlers return that message verbatim as `403 { error, code: "budget_exceeded" }` (`backend/services/semprec-ai-gateway/src/completeHandler.ts:283-285`, `audioHandler.ts:209-211`, `piMessagesHandler.ts:367-371`). Callers treat that code as permanent (`backend/services/semprec-transcribe/src/transcriptionTask.ts:734-739`). The reservation lifecycle and the lock are recorded in `docs/adr/2026-09-27-ai-budget-reservations-under-a-global-advisory-lock.md`.

What the blockers delivered:

- **#993:** every reservation runs inside the caller's tenant scope, taken from the `x-semprec-tenant-id` header. `ai_gateway_calls` rows carry that tenant. The gateway connects as `semprec_side`, so under row-level security `getGatewaySpend` sums only that tenant's rows.
- **#1004:** the global table `tenant_ai_budgets`, with one admin-owned row per tenant. A missing row means refuse. A `NULL` cap means no per-tenant cap for that window. It also added `getCurrentTenantAiBudget(client)`.
- **#997:** the NOLOGIN `BYPASSRLS` role `semprec_router`, which owns cross-tenant `SECURITY DEFINER` functions. Those functions have column-level `SELECT` only, a pinned `search_path`, `EXECUTE` revoked from `PUBLIC`, and return only numbers or ids.

This issue switches enforcement to two caps, both checked in the same critical section under the unchanged global lock:

- the tenant's own caps, measured in the tenant's own timezone;
- an operator-wide safety cap from the environment, measured over all tenants' spend in UTC.

The global lock stays because one serialization point is what makes a global cap enforceable. A refusal must not reveal which cap tripped. Otherwise a user could infer other users' spend.

**Decision: how the tenant row is read.** "A missing cap refuses" applies to the row, not to its columns:

- A tenant **without** a `tenant_ai_budgets` row is refused every call (fail closed). This includes a call where no tenant resolves.
- A `NULL` `daily_cap_usd` or `monthly_cap_usd` means that window has **no per-tenant cap**. The global safety cap still applies to it.

Without the `NULL` rule, tenant zero would lose today's uncapped monthly window. `monthlyBudgetUsd` is seeded `null` (`backend/packages/data/src/seed/seedSystem.ts:169-195`, `0019_settings_ai_budgets.sql:30-32`), and `null` means "uncapped" today (`systemSettings.ts:44-48`, `:72-77`).

## Acceptance criteria

Two-tenant cases use the harness from #975 in `backend/packages/data/src/testSupport/testDb.ts`: `createTestTenant(pool)` and `createRuntimeRolePool(adminPool, "semprec_side")`, with calls made inside `runInTenant` from `@semprec/shared`.

**Tenant caps**
- Tenants A and B each have a daily cap of `1`. Once A's spend today reaches `1`, a further call in A's scope gets `403 { "error": "AI budget exceeded", "code": "budget_exceeded" }` and no new row is written, while a call in B's scope succeeds (integration).
- Monthly caps behave the same way (integration).
- A tenant with no `tenant_ai_budgets` row is refused and gets no row (integration). This includes a reservation outside any tenant scope while two tenants exist.
- `NULL` caps with spend below the global caps lets the call through (integration).

**Global cap**
- With `globalCaps.dailyCapUsd = 1`, A spends `1` with `NULL` own caps. B's call (`NULL` caps) is then refused with a response body byte-identical to the one A gets from its own cap (integration, handler level).
- The global monthly cap behaves the same way (integration).

**Windows**
- A row timestamped one minute before the tenant's local midnight (in the timezone of its settings item) does not count toward that tenant's daily cap (integration).
- A row one minute before UTC midnight does not count toward the global daily cap (integration).

**Concurrency and logging**
- Of two concurrent calls whose estimates each reach the tenant's daily cap, exactly one is admitted (integration).
- The refusal log line carries `limit` and no amount (integration).

**Router function**
- `ai_global_spend()` returns the total over all tenants even when the caller's RLS shows only its own rows (integration).
- Its owner is `semprec_router`, `PUBLIC` has no `EXECUTE`, and `semprec_side` can call it (integration, catalog query plus a call).

**Migration and startup**
- After the migration, a row with `updated_by IS NULL` holds the current settings values, and a row with `updated_by` set is unchanged (integration).
- `resolveStartupConfig` throws a message naming the variable when either `AI_GLOBAL_*` variable is missing, `0`, negative or non-numeric, and puts the parsed caps into all three handler options otherwise (unit).
