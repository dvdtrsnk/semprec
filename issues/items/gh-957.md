## Behavior specification (approved)

Part of the multi-tenancy program specified in #950. Host and edge hardening so that no process, log or cache can leak one tenant to another:

1. Each systemd service receives only the secrets it needs; runtime units never receive the superuser migration URL.
2. The service uid's outbound traffic is filtered (no private, loopback-except-local-services, link-local, CGNAT, ULA or metadata destinations).
3. `stdio` MCP servers run through a sandbox launcher under a dedicated uid without access to data directories or shared secrets; service units carry systemd sandboxing directives.
4. Every API response is `Cache-Control: no-store`.
5. Item partitions are created without an exclusive lock on `items`; the Postgres lock table is sized for per-tenant partitions.
6. Login, password reset and invitation acceptance are throttled per client IP, and the reset request timing does not reveal whether an account exists.
7. Log lines carry no user content.

## Decisions

- **Why does ops hardening belong to tenancy?** → With many users, any process that can read every secret or reach internal addresses, and any log line with content, is a cross-tenant leak even when RLS is perfect.

## Out of scope

The connect-time address check in code (#954); backups of tenant keys (#956).
