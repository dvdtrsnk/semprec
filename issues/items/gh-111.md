**Blocked by:** #224, #110

## Context

Issue #224 delivered the forward-only structural runner. This part delivers the second, separate mechanism: data migrations for when the shape of `items.properties` content changes, carried as manifest-declared scripts per version pair and executed in resumable batches so a crash retry resumes from a cursor instead of restarting from zero or silently re-converting already-migrated rows. It consumes the `migrations` field of `ModuleManifest` (#108) and ships its own DDL as a numbered structural file applied by the runner from #224. #115 later declares real `migrations` entries on the retrofitted manifests, and #114 covers the conversion functions in the unit tier.

## Task

- **Bookkeeping table.** Add `module_migrations(module_id, database_key, from_version, to_version, ran_at)` for manifest-declared data migration scripts, as a new numbered structural migration file applied by the runner from #224.
- **Cursor column.** Add nullable `properties.migration_cursor uuid` holding the last successfully converted item id, in the same structural migration.
- **Manifest scripts.** Execute the data migration script the manifest carries per version pair (`from_version` → `to_version`) for a given `database_key`, running each script's converter over the items of that database.
- **Batched, resumable execution.** Execute data conversions in deterministic id-ordered batches (cursor-based pagination over `item_id`), committing cursor progress (`properties.migration_cursor`) after each successfully converted batch, so a crash retry resumes after the last committed item and never re-converts already-migrated rows. A failed conversion must never advance the cursor past the failed data; the failing batch is rolled back and the cursor stays at the last committed item.
- **Transition bookkeeping.** Mark a version transition complete — insert its `module_migrations` row and clear the cursor — only after all rows finish. Guard concurrent runners so the same `(module_id, database_key, from_version, to_version)` transition can never be recorded twice.

## Scope

### In scope

- `module_migrations`, `properties.migration_cursor`, manifest-script execution, batching, resume, transactional failure behavior, and the concurrency guard.

### Out of scope

- The structural runner itself (#224).
- Down migrations and background property-retyping behavior beyond invoking its converter.

## Acceptance criteria

- A forced mid-data-migration crash resumes on retry without restarting committed rows, and every row ends converted exactly once.
- Concurrent runners cannot record the same transition twice.
- Failed conversions never advance the cursor past failed data.
- A transition is recorded in `module_migrations` only after all rows of the database finish.
