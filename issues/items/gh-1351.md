## Behavior specification

Realtime for runs, project, Semp status and derived counts.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: realtime-derived-1

#### (a) Adopted decisions
- Frame shapes: every new scope is an `invalidate` frame with a `scope` discriminator, thin ids only: agentRuns {projectItemId|null, agentRunId}, projectAgent {projectItemId}, sempStatus, notificationPreferences, badgeCounts, account, overview (no fields). Follows the pattern introduced by the preceding scope issues in the chain.
- Delivery: the notes say "narrowed to userId". Adopted: agentRuns (run actor), notificationPreferences, badgeCounts and account are narrowed to the concerned user; projectAgent, sempStatus and overview go tenant-wide because their producers are background writes with no acting user (a tenant has one user, so the effect is the same).
- overview producer: only the end of the nightly per-tenant core.tasksDayRollover (also when no task moved); event end = item invalidation of hiddenUntil, problem count = sempStatus (as the notes' correction says). Not published from the global CORE_CRONTAB.
- Server-wide MCP changes (server switched off, sync) do not publish projectAgent per project. -> Decided by the product owner: a server change sends one tenant-wide realtime event and the client refreshes the summary of the projects it has open; the other projects are computed when loaded (fan-out only within the tenant). Delivered by #2025 with the id-less scope `mcpServers`.
- badgeCounts producers are enumerated by the implementer from the count function of the pending-decisions issue (cannot be listed without seeing that code); listed in the PR.
- Each scope issue adds its own client parser case (the realtime-client change is not left to the account issue only).
- Publishing the account frame after PATCH /api/account/profile belongs to the profile issues; this chunk only delivers the frame and publishAccountInvalidation.

#### (b) Open questions for the product owner
- None remaining.

#### (c) User-visible behavior
Connected apps now update without a manual refresh: a running agent run and the latest-runs list change status as the run starts, finishes, waits for approval and is approved elsewhere; the project's Semp summary and attention dot follow guidance, tool, task and finding changes; Semp status problems and services update; notification preferences and badge counts sync across a user's devices; profile language changes propagate to other devices; and the Overview counts refresh at the turn of the day. Frames carry only identifiers and reach only the right tenant (and user where relevant).
