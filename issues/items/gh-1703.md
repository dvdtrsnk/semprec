## Context

Model tier rationale: It moves a user file between two stores inside the atomic multi-step confirm, touching blob ownership, deduplication against existing Files and the transcription trigger, where a partial or doubled write loses or duplicates user data.

Confirm moves an Inbox attachment into Files atomically, without copying bytes, respecting existing Files reuse, origin ownership and downstream explicit transcription.

Decisions:
- The step input is `{ attachmentId }` plus `name` and `date` for the Files item, and the relations the envelope already allows (project, company). The `file` property and `type` are set by the server: `file: { blobId }` of the attachment and `type` from the blob's mime type when that value exists in the Files `type` options, otherwise left unset.
- If a live Files item with the same blob already exists (`findFileItemByBlobId` in `backend/packages/data/src/chokePoint/itemsStore.ts`), no second item is created: the step resolves to the existing item, and none of its properties or relations change. The executor result reports reuse; card/public result reporting and persistent replay are delivered by #1648.
- The attachment must belong to the proposal's own source Inbox item; another attachment id is rejected as 400 `validation_failed`.
- The attachment row is deleted in the same transaction. The blob stays because the Files item references it.
- A Files item created from an Inbox attachment is not auto-transcribed: the Files transcription trigger skips any item that has an `item_origins` row with capture channel `inbox`. Transcribing an audio attachment is proposed explicitly (#1978). Undoing a confirmation is not part of this issue; the undo (#1943) leaves the Files item created from the moved attachment in Files (decided by the product owner), so no reverse operation of the move is needed.

Result boundary: the accepted `2026-10-29-file-from-attachment-proposal-step` ADR assigns persistent/public per-step results to #1648. This Task owns the executor tuple only; preserve the existing confirm ItemRow response and idempotent replay. The actual `POST /api/files` positive transcription control remains mandatory.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Define the "file from attachment" step kind in the multi-step envelope (validation per #1486) in `backend/packages/data/src/inbox/fileAttachmentStep.ts`: allowed fields `attachmentId`, `name` (required, non-empty), `date`, plus the relations the envelope allows; any other property, including `file` and `type`, is rejected with 400.
2. Execute it in confirm (`backend/packages/data/src/inbox/proposalActions.ts`) inside the single transaction: load the attachment through `getInboxAttachment` and check it belongs to the source Inbox item; if a live Files item with the blob exists, resolve the step to it; otherwise create the Files item through the choke point with `{ name, date, file: { blobId }, type }`; then `deleteInboxAttachment`. Record in the executor's step result the Files item id and `created` together with `movedAttachmentId` (the id of the moved attachment), so the undo (#1943) recognizes a Files item that received a moved Inbox attachment and keeps it. Any blobs derived from the attachment (added by #1965) are released by `deleteInboxAttachment` itself.
3. In `core.filesTranscriptionTrigger` skip a Files item that has an `item_origins` row with capture channel `inbox`.
4. Tests: actual authenticated file-step HTTP400 validation_failed/ref/attachmentId for foreign attachment, unchanged card/attachments/items and own-attachment success; file/type/unknown-property HTTP refusal with canonical fields. Also, confirming a photo attachment with a project creates one Files item with the same `blobId`, the project, the origin row and `type` `jpg`, and the attachment row is gone, no second blob exists and the step result carries `movedAttachmentId`; a photo already in Files gives no second item and leaves the existing one unchanged; a foreign attachment id is rejected and nothing is written; a failure after this step rolls back and the attachment row remains; an audio attachment confirmed into Files enqueues no transcription; a Files item uploaded by `POST /api/files` is still transcribed; the Files item created here can be deleted without removing bytes an unconfirmed attachment still uses.

## Scope

### In scope

- The file-from-attachment confirm step, its reuse of an existing Files item with the same blob, deleting the attachment row in the same transaction, and the transcription trigger skip.

### Out of scope

- The multi-step confirm mechanism and the origin rows: #1486 and #1659.
- The attachment model and blob counting: #1564.
- Other steps on the same card that refer to the Files item (for example a follow-up task).
- Proposing the transcription of an audio attachment: #1978.
- Extending the Files `type` options for PNG and audio: #1410; until then such a file has no `type`.
- Undoing a confirmation (#1943). Returning the attachment to the Inbox item: decided not to be done; the file stays in Files.
- Persisting per-step results or changing the public confirm response/replay: #1648. The executor tuple and real upload positive control are in scope above.

## Acceptance criteria

- When a proposal with a file step for a photo attachment is confirmed, then one Files item exists with the attachment's `blobId`, the proposed project and an origin row, the attachment row is deleted, and no second copy of the bytes exists.
- When the same bytes already have a live Files item, then no second item is created and the existing item is unchanged.
- When the attachment id belongs to another Inbox item, then the confirm fails with 400 and nothing is written.
- When a later step fails, then the Files item is not created and the attachment remains.
- When an audio attachment is filed by confirm, then no transcription job is enqueued.
