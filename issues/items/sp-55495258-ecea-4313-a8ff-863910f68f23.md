### Requirement gh-1544: [tasks-core 03/11] Record the day and time a task was completed

#### Context

Model tier rationale: One mechanism (completion-day rules inside the Tasks pre-write transform) over existing seams and fixtures, with several edge cases around time zones and repeat writes that need care.

A task is completed by setting `status` to `done` through `PATCH /api/items/:id` (`ifVersion` required). Today nothing records when: `items` only carry `updated_at`, and no completion property exists. Clients need the day a task was completed to show it on that day (a task completed on the 14th shows there even if its date is the 16th), to end a carried-over chain at the completion day, and to show the right day in the timeline.

What this builds on: the Tasks pre-write transform from #1422 (resulting-state validation, hooks see the prepared patch), the schema from #1540 (`Tasks.completedOn`, a user-owned date, and `Tasks.completedAt`, a system-owned date with time with `ownerProcess` `tasks`), and the tenant time zone helpers (`getSystemTimezone` in `backend/packages/data/src/timezone.ts`; the calendar time module from #1418 when present). What builds on it: #1670 (advance a series past the completed occurrence), #1781 (completing inside an event) and #1884 (carry-over and traces in the timeline).

Behavior of the recurrence hook today: `taskRecurrenceItemUpdateHook` (`tasks/`) fires on every patch with `status: "done"`, but it only advances an active recurrence, so a repeated `done`, or `done` then `notDone` then `done`, creates no second instance, and `done` back to `notDone` leaves two open instances. The series rules are owned by #1670; this issue does not change that hook.

Decision: `completedOn` may not be in the future. A client completing a future occurrence early sends no `completedOn` (so it becomes today); the occurrence day is kept elsewhere (#1720).

Decision (product owner): `completedOn` may be earlier than the task's date or first planned day; the user enters it as it really happened, and that is also how completing a past trace of a moved task works.

Decision (product owner): a completed task is sorted and shown by its completion day (`completedOn`); completing a task never rewrites its planned `date`.

### Requirement gh-1602: [tasks-rollover 01/03] Record a task's first planned day when it moves on

#### Context

Model tier rationale: One pre-write transform rule over two new system-owned properties, using the transform seam and schema delivered by blockers, with simple deterministic fixtures.

When a task is not done on its planned day, the product carries it forward day by day (the nightly move is #1674) and the calendar shows traces of the days it was carried through (#1884). For that the system must remember the first day the task was planned for, and its time on that day. Today nothing stores it: the Tasks schema in `backend/packages/data/src/seed/seedTenDatabases.ts` has no `since`, `sinceTime` or `completedOn`, and `date`, `timeFrom`, `timeTo` and `status` are owned by `user`. A choke-point item hook runs after the write and cannot change the stored value (`backend/packages/data/src/chokePoint/hooks.ts`), so the value must be written before the write, in the Tasks transform.

#1540 adds `since` (date) and `sinceTime` (json `{from, to}`) to the Tasks schema as `system` properties owned by the `tasks` process, and #1422 adds the per-module pre-write transform. This issue implements the rule inside that transform. #1674 and #1780 write the same fields through the same rule; #1884 reads them.

Decisions: `since` is never cleared once set (the product keeps the first planned day for the traces even after the task is completed or moved earlier; no clearing rule is specified); "today" is the date in the system timezone setting (`getSystemTimezone`), not the device timezone (decided by the product owner: one zone from the settings for rollover and display, no automatic device zone in v1); until #1780 owns writing `effectiveDate`, read missing/null/empty `effectiveDate` as stored `date`; a nonempty stored `effectiveDate` takes precedence. This fallback writes neither field.

#### Task

Load `state-writes`, `canonical-keys` and `testing`.

1. In the Tasks transform, when a write changes `date` of a task whose `status` is `notDone`, whose current `effectiveDate` is before today, and whose `since` is empty: set `since` to the current `effectiveDate`, and set `sinceTime` to the current `{from: timeFrom, to: timeTo}` only when the current `effectiveDate` equals the stored `date` and a time exists (otherwise leave `sinceTime` empty).
2. A later change of `date` never overwrites an existing `since` or `sinceTime`. A change of `date` of a task whose current date is today or later, or of a task with a status other than `notDone`, does not set `since`.
3. Client writes of `since` and `sinceTime` are rejected as for any `system` property. Both fields are returned by every item read (GET, query, search, timeline) through the normal property serialization; add a test that GET and a view query include them.
