## Context

Model tier rationale: It adds a nested relation-traversal filter condition whose SQL must stay injection-safe, honour soft deletes on the intermediate hop and keep partition pruning on the `items` table, and it changes a condition set that is duplicated across two packages and that every later collection query builds on.

Collections often need to be narrowed by something that is not a direct property of the item. The motivating case is the area filter: a task has no area of its own, it belongs to a project, and the project belongs to an area. "Tasks in the Work area" therefore means "tasks whose project is in Work", and a task without a project belongs to no area. The same shape applies to files and health records through their many-valued `projects` relation.

Today the filter tree supports one relation condition only: `relation_contains` / `relation_not_contains` on a relation property of the queried database, compiled by `compileRelationCondition` in `backend/packages/data/src/views/filterCompiler.ts` to an `EXISTS` over `item_relations` with the relation-definition id and the target item id as bound parameters. There is no way to follow a second relation. The condition set is defined twice and must stay identical: `backend/packages/data/src/views/filterTree.ts` (the data-layer zod schema, `FILTER_CONDITION_TYPES` and the `FilterCondition` union) and `backend/packages/shared/src/genericOperations/filterSort.ts` (the standalone copy used by the generic operation schemas). `buildFilterProperties` in `backend/packages/data/src/views/filterProperties.ts` hands the compiler a map of the queried database's properties, with each relation property paired to its relation definition and side; it knows nothing about the database on the other end of a relation.

Existing relation schema that this issue relies on: `Tasks.project` and `Events.project` are single-valued, `Files.projects` and `Health records.projects` are many-valued, and `Projects.area` is the inverse of `Areas.projects` (`seed/seedTenDatabases.ts`). A hop through `project` and then `area` is therefore a hop over two relation definitions.

This issue adds the condition `relation_path_contains`. It is the foundation for the per-database area filters (#1597), the emptiness conditions that compose with it (#1526), the area overview (#1760), facets (#1759) and related collections (#1839). Everything that evaluates a filter tree gets the new condition for free, because they all go through `compileFilterNode`: `database.query`, `view.query`, a saved view's `ViewConfig.filter`, and the filtered reads in `chokePoint/itemReads.ts`.

Decision: the condition takes no "only active projects" parameter. A caller that wants it combines the condition with `and` and a filter on the project, which the conservative reading of the open question allows without a third parameter.

Decision: a soft-deleted intermediate item (for example a deleted project) never satisfies the condition, and it is checked in SQL, not left to the caller.

## Task

Load `canonical-keys`, `io-hardening` and `testing`.

1. Add the condition `{ type: "relation_path_contains", path: [relationKey, relationKey], value: <uuid> }` to both copies of the filter tree: `filterTree.ts` (add to `FILTER_CONDITION_TYPES`, the `FilterCondition` union and `filterConditionSchema`) and `shared/src/genericOperations/filterSort.ts` (same three places). `path` is a tuple of exactly two non-empty strings, `value` is validated with `z.uuid()`, matching `relation_contains`. Update the comment above the condition lists that says the two copies must stay identical, and extend `filterSort.unit.test.ts` and `filterCompiler.unit.test.ts` so any existing parity check covers the new type.
2. Extend `buildFilterProperties` so a relation property also carries what the compiler needs for a second hop: the target database id (from the property config's `targetDatabaseId`) and the target database's own relation properties (key, relation definition id, side), resolved in a bounded number of batched queries (not one query per property). Only the relation properties of the target database are needed, and only one level deep. Extend `FilterProperty` in `filterCompiler.ts` accordingly.
3. In `filterCompiler.ts`, compile the new condition to a nested `EXISTS` over `item_relations` (first hop, from the queried item to the intermediate item) and a second `item_relations` row (second hop, from the intermediate item to the `value` item). All ids are bound `$N` parameters; the only text interpolated into the SQL is the `item_a`/`item_b` side column names, taken from registered relation definitions and never from the node. The intermediate item is looked up with the partition-pruning pattern of `ITEM_RELATION_FILTER_QUERY` in `scheduler/itemRelationFilter.ts` (a `CROSS JOIN LATERAL` over `items` pinned to the intermediate database id, with `OFFSET 0`) and must have `deleted_at IS NULL`.
4. Validate the path before compiling. The first key must be a relation property of the queried database and the second key a relation property of that relation's target database; otherwise throw `ValidationError` with `field: "filter"`. A non-relation first or second key, an unknown key and a relation without a resolvable definition all fail the same way. The value of the second hop is not checked for existence (same as `relation_contains`).
5. Tests. Unit tests in `filterCompiler.unit.test.ts` for the SQL shape and for every validation failure. A database-backed test (a new `relationPathFilter.test.ts` next to `itemRelationFilter.test.ts`) over Tasks, Projects and Areas that asserts the results below and runs `EXPLAIN` on the compiled query to prove only the intermediate database's partition is scanned. Include one test that `view.query` with a saved `ViewConfig.filter` using the condition returns the new items after a project is moved to another area, with no change to the view.

## Scope

### In scope

- The `relation_path_contains` condition in both filter-tree copies, its validation, its SQL and the target-database metadata it needs from `buildFilterProperties`.
- Behavior through `database.query`, `view.query` and saved view filters (all use `compileFilterNode`).

### Out of scope

- Conditions that test for an empty relation: #1526.
- Declaring the per-database area filter trees and exposing them in the schema: #1597.
- Counting and faceting with the new condition: #1709 and #1759 reuse the compiler and add nothing here.
- Paths longer than two hops, and a "negated" form of the condition (callers wrap it in `not`).
- Any client-side deep link encoding.

## Acceptance criteria

- When Tasks are queried with `relation_path_contains { path: ["project", "area"], value: <Work area id> }`, then only tasks whose project belongs to Work are returned; a task without a project and a task whose project is soft-deleted are not.
- When Files are queried with `path: ["projects", "area"]`, then a file with several projects is returned if any one of them belongs to the area.
- When a project is moved to another area, then a saved view that uses the condition returns the project's tasks under the new area on the next `view.query`, with no edit to the view.
- When the first path key is not a relation of the queried database, or the second is not a relation of the first one's target database, then the request fails with a 400 `ValidationError` on field `filter`.
- When `value` is not a uuid or `path` does not have exactly two entries, then the request fails with a 400 `ValidationError` on field `filter`.
- The compiled SQL contains no value taken from the filter node; every id is a `$N` parameter, and the `EXPLAIN` test shows no scan over unrelated `items` partitions.
- `filterTree.ts` and `filterSort.ts` accept and reject exactly the same condition inputs.
