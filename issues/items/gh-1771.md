**Blocked by:** #1605, #1733
**Model tier:** medium

## Context

Model tier rationale: It extends an existing closed schema, its validator and its resolver with two new variants following the established pattern, but the occurrence variant has no item id and needs tenant-scoped validation and series lookup, so it is not low.

The user can start a Semp turn from a task: a bubble on a task row, on a future occurrence of a repeating task that exists only as a computed day, or on the trace of a task on a past day. Semp needs to know exactly which task, occurrence or trace was meant, and to see its details without the client sending them.

Today `SempConversation.send(task: string)` (`backend/packages/agent-runtime/src/sempConversation.ts`) carries only text; message references are introduced by other issues. #1369 defines the closed discriminated union of message refs, with `{kind: "item", itemId, databaseId}` for any item, so an ordinary task is already covered by it. #1682 validates and stores refs, checking an item ref by the pair `(itemId, databaseId)` inside the tenant. #1733 expands each ref into the agent's turn context (the resolver). The series identity and occurrence day that this issue refers to come from #1605 (`seriesId`, `occurrenceDate`, and the stored template of a series). Relations of the task are read through the inline expansion from #1518.

Decision: a repeating task's future occurrence that has not been materialized is identified by its series and day, with no item id; a trace of a task on a past day is identified by the task item plus the day.

## Task

Load `io-hardening`, `error-handling` and `testing`.

1. Extend the closed ref union from #1369 with two variants (kind values kebab-free camelCase strings as in the existing union):
   - `{kind: "taskOccurrence", seriesId, occurrenceDate}` where `seriesId` is a non-empty string and `occurrenceDate` is `YYYY-MM-DD`; there is no `itemId`.
   - `{kind: "taskTrace", itemId, databaseId, traceDay}` where `traceDay` is `YYYY-MM-DD`.
   Strict parsing stays: unknown kinds and extra keys are rejected as before.
2. Extend the validation from #1682: a `taskOccurrence` ref is valid only when a series with that `seriesId` exists in the caller's tenant (not deleted); a `taskTrace` ref is valid only when `(itemId, databaseId)` identifies a non-deleted Tasks item in the tenant. A ref to another tenant's series or item is answered exactly like an unknown one (same error, no existence leak).
3. Extend the resolver from #1733 so that, in a turn, each variant expands to text and structured context for the agent:
   - a task item ref: name, status, date, times, `since`, `recurrence`, description, and related project, people and attachments (names only), expanded with the inline relation read;
   - a `taskOccurrence` ref: the series' template properties, the occurrence day, and the same relations of the series template;
   - a `taskTrace` ref: the task as above plus the trace day.
   An unresolvable ref (deleted since it was sent) expands to a short "no longer available" note instead of failing the turn.
4. Tests: schema parse and rejection cases, validation including cross-tenant, and resolver output for each variant, including a materialized and a non-materialized occurrence.

### Out of scope

- The client bubbles.

## Acceptance criteria

- When a message carries `{kind: "taskOccurrence", seriesId, occurrenceDate}` for a series in the tenant, then it is accepted and stored without any item id, and the agent's turn context contains the series' properties and the occurrence day.
- When the series does not exist or belongs to another tenant, then the message is rejected with the same error in both cases.
- When a message carries a `taskTrace` ref whose item is not a Tasks item, then it is rejected.
- When a referenced task was deleted after the message was sent, then the turn proceeds and the context says the task is no longer available.
- When a ref has an unknown kind or an extra key, then it is rejected as before.
