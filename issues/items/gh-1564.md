## Context

Model tier rationale: A new tenant-owned table with row-level security plus a change to the shared blob reference rule and the permanent-delete path, where a mistake either leaks across tenants or deletes bytes that are still in use.

Inbox attachments remain separate rows until confirmed filing moves the same bytes into Files. Trashing keeps attachments; permanent purge removes their references. Shared content-hash blobs require reference-aware collection. Later capture, recognition and display issues consume this store; they remain outside this Task.

Decisions:
- One general attachment model serves every kind of attachment and allows several attachments per Inbox item (`position` orders them). The cap of 10 per capture is enforced by the capture route (#1963); limiting the Journal to one attachment is a client rule, so nothing here caps the count.
- An attachment is a row of its own, not a Files item and not an item property, so the Inbox item's schema stays unchanged.
- A discarded (trashed) Inbox item keeps its attachment rows; they are removed when the item is permanently deleted.

## Acceptance criteria

- When an attachment row names a blob, then deleting a Files item with the same bytes keeps the blob and its bytes.
- When an Inbox item is permanently deleted, then its attachment rows are gone and a blob nothing else uses is deleted with its bytes after the commit; a blob used by a Files item stays.
- When an Inbox item is only trashed, then its attachments remain.
- When another tenant reads attachments, then it sees none of this tenant's rows.
- Both production trash tasks remove committed blob keys from both configured roots after commit; same-tenant purges obey the transaction entry guard, with rollback/no-delete and cross-tenant evidence.
