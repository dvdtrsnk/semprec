**Model tier:** high

## Context

Model tier rationale: A new tenant-owned table with row-level security plus a change to the shared blob reference rule and the permanent-delete path, where a mistake either leaks across tenants or deletes bytes that are still in use.

A photo, scan, audio note or shared file can be attached to an Inbox item before anything is filed. Today the Inbox has no attachment: `Inbox` (`backend/packages/data/src/seed/seedInboxPipeline.ts`) has only `date`, `time` and `text`, and the property type `file` is used by no database. Files are created at once by `POST /api/files`. The product decision is that an attachment stays with the Inbox item until the person confirms the proposal; only then does a Files item appear, by moving the same bytes (no copy). Until then, and after the item is discarded, no Files item exists, and the attachment is kept until the Inbox item is permanently deleted.

This issue creates the one attachment model for the Journal and the Inbox and makes it a counted blob reference. Blob bytes are shared by content hash (`findOrCreateBlob`), so the rule that decides when bytes may be deleted matters: `deleteBlobIfUnreferenced` (`backend/packages/data/src/blobs/blobsStore.ts`) counts only `properties.file.blobId` of items and `mail_attachments` (and, after #1401, image properties). `deleteItemDependents` (`backend/packages/data/src/chokePoint/itemTrash.ts`) removes an item's dependent rows by hand on permanent delete and frees only the item's own `file` blob.

#1963 lets a capture attach uploaded blobs, #1703 moves an attachment into Files on confirm, #1965 adds recognition metadata, and #1606 and #1969 read attachments.

Decisions:
- One general attachment model serves every kind of attachment and allows several attachments per Inbox item (`position` orders them). The cap of 10 per capture is enforced by the capture route (#1963); limiting the Journal to one attachment is a client rule, so nothing here caps the count.
- An attachment is a row of its own, not a Files item and not an item property, so the Inbox item's schema stays unchanged.
- A discarded (trashed) Inbox item keeps its attachment rows; they are removed when the item is permanently deleted.

## Task

Load `db-migrations`, `state-writes` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_inbox_attachments.sql (next free ordinal at commit time)`: table `inbox_attachments (attachment_id uuid PRIMARY KEY DEFAULT gen_random_uuid(), tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id), inbox_item_id uuid NOT NULL, blob_id uuid NOT NULL, position integer NOT NULL, source text NOT NULL CHECK (source IN ('camera','scan','photoLibrary','files','share')), created_at timestamptz NOT NULL DEFAULT now())`, a composite tenant foreign key to `blobs` in the style of `0083_tenant_composite_foreign_keys.sql`, no foreign key to `items` (they are partitioned; dependents are removed by `deleteItemDependents`), unique `(tenant_id, inbox_item_id, position)`, an index on `(tenant_id, blob_id)`, `COMMENT ON TABLE inbox_attachments IS 'semprec:tenancy=tenant'`, row-level security and grants exactly as in `0078_tenant_exports.sql`. Additive only.
2. Add `backend/packages/data/src/inbox/inboxAttachmentsStore.ts` with: `insertInboxAttachments(client, inboxItemId, [{ blobId, source }])` (positions continue after the current maximum), `listInboxAttachments(client, inboxItemIds)` returning `{ attachmentId, inboxItemId, blobId, mimeType, byteSize, source, position }` joined with the blob, `getInboxAttachment(client, attachmentId)` and `deleteInboxAttachment(client, attachmentId)`.
3. Extend `deleteBlobIfUnreferenced` so a blob that any `inbox_attachments` row names is referenced (`AND NOT EXISTS (SELECT 1 FROM inbox_attachments WHERE blob_id = $1)`). This also protects attachment bytes from the unreferenced-blob sweep of #1401.
4. In `deleteItemDependents`, delete the item's `inbox_attachments` rows and release each of their blobs with `deleteBlobIfUnreferenced`; change the return value from one `blobStorageKey` to a list `blobStorageKeys` and update `purgeExpiredTrashSubtree` to collect them, so bytes are removed after commit as today.
5. Confirm tenant export and purge pick the new table up from the tenancy catalog (`tenancyCatalog.test.ts`); add it explicitly only if they do not.
6. Tests: insert, list and delete; the migration's RLS (another tenant sees no rows); a blob named by an attachment is kept when a Files item with the same bytes is purged and when the unreferenced sweep runs; permanently deleting an Inbox item removes its rows and frees blobs nothing else uses, but not one a Files item uses; a trashed Inbox item keeps its attachments.

## Scope

### In scope

- The `inbox_attachments` table, its store, counting it as a blob reference, and cleanup on permanent delete.

### Out of scope

- Uploading bytes and attaching them in a capture: #1963.
- Moving an attachment into Files on confirm: #1703.
- Recognition metadata and thumbnails: #1965.
- Returning attachments in cards and the day summary: #1969.
- Including attachments in the Inbox fingerprint: #1606.
- Reading `GET /api/blobs/:id` with an `Authorization` header.

## Acceptance criteria

- When an attachment row names a blob, then deleting a Files item with the same bytes keeps the blob and its bytes.
- When an Inbox item is permanently deleted, then its attachment rows are gone and a blob nothing else uses is deleted with its bytes after the commit; a blob used by a Files item stays.
- When an Inbox item is only trashed, then its attachments remain.
- When another tenant reads attachments, then it sees none of this tenant's rows.
