## Context

`checkPermanentlyFailedJobs` (`backend/packages/data/src/observability/observabilityCheckSystem.ts` lines 124-138) runs every minute from `observabilityCheckSystem` and counts `SELECT count(*) FROM graphile_worker.jobs WHERE attempts >= max_attempts`; any non-zero count puts the `queue:permanentlyFailedJobs` check into `alerting` and, on the transition, writes a `queue_backlog` notification. Two properties of that query make the alert permanent once it has fired:

- graphile-worker never deletes a permanently failed row (`complete_job` deletes only on success; `fail_job` keeps the row). Nothing in this repository deletes them either. Every genuinely exhausted job — and, until sibling issue F4a lands, every superseded-then-failed one — stays in the table forever, so the check can never return to `ok` and every later failure is invisible behind the first.
- The query does not exclude locked rows. graphile-worker's `add_jobs` (`sql/000018.sql` lines 104-116) sets `attempts = max_attempts` on a *running* job the moment its key is re-added, so a long mail sync that is re-enqueued mid-run counts as "permanently failed" while it is still running and about to succeed.

graphile-worker exposes `graphile_worker.complete_jobs(job_ids bigint[])`, which deletes the given rows unless they are locked (or locked for more than four hours) — the supported way to remove rows without touching `_private_jobs`. `CORE_TASK_NAMES` / `CORE_TASK_AFFINITY` (`backend/packages/queue/src/index.ts` lines 28-109) and `CORE_CRONTAB` plus the `handlers` map in `createCoreTaskList` (`backend/packages/data/src/worker.ts` lines 76-84, 113-...) are the registration points for a new cron task; `__tests__/queueRuntime.test.ts` pins the installed crontab identifiers in `EXPECTED_CRONTAB_IDENTIFIERS`. #643 adds an entry to each of those same places and lands first.

## Task

2. **Prune** — add `backend/packages/data/src/observability/queueFailedJobsPrune.ts` (new):
   - `export const FAILED_JOB_RETENTION_MS = 7 * 24 * 60 * 60 * 1000;`
   - `export async function pruneQueueFailedJobs(pool: Pool, now = new Date()): Promise<number>`: `SELECT id, task_identifier, key, attempts, max_attempts, last_error, updated_at FROM graphile_worker.jobs WHERE attempts >= max_attempts AND locked_at IS NULL AND updated_at < $1` (cutoff = `now - FAILED_JOB_RETENTION_MS`); for each row `logger.warn({ jobId: String(id), jobName: task_identifier, jobKey: key, attempts, lastError: last_error, updatedAt }, "Pruning a permanently failed job")` through a new `backend/packages/data/src/observability/logger.ts` (`createLogger("observability")`, the `mail/logger.ts` pattern); then `SELECT graphile_worker.complete_jobs($1::bigint[])` with the ids and return the number of rows the function returned. No rows → return 0 without logging.
   - `export async function handleQueueFailedJobsPruneTask(pool: Pool): Promise<void>` calling it.
3. **Register** — in `backend/packages/data/src/worker.ts`: add `20 4 * * * ${CORE_TASK_NAMES.QUEUE_FAILED_JOBS_PRUNE}` to `CORE_CRONTAB` and `[CORE_TASK_NAMES.QUEUE_FAILED_JOBS_PRUNE]: async () => { await handleQueueFailedJobsPruneTask(pool); }` to the `handlers` map in `createCoreTaskList` (next to `OBSERVABILITY_CHECK_SYSTEM`). Export `pruneQueueFailedJobs`, `handleQueueFailedJobsPruneTask` and `FAILED_JOB_RETENTION_MS` from `backend/packages/data/src/index.ts` next to the existing `observabilityCheckSystem` export line, and add the two function names to `__tests__/publicSurface.test.ts` if it pins the export list. Add the new identifier to `EXPECTED_CRONTAB_IDENTIFIERS` in `backend/services/semprec-api/src/__tests__/queueRuntime.test.ts`.
4. **Check window** — change `checkPermanentlyFailedJobs`' query to `WHERE attempts >= max_attempts AND locked_at IS NULL AND updated_at >= now() - ($1::bigint * interval '1 millisecond')` with `FAILED_JOB_RETENTION_MS`, and update its docstring: locked rows are still running (their `attempts` may have been bumped by a re-enqueue); rows older than the retention window are about to be pruned and were alerted on when they were young, so the check recovers by itself once no *new* row appears.

Extend `backend/packages/data/src/__tests__/observabilityCheckSystem.test.ts`: `queue:permanentlyFailedJobs` is `ok` with only a locked-and-exhausted row present, `ok` with only an 8-day-old exhausted row, and `alerting` with a fresh unlocked exhausted row.

## Acceptance criteria

- When a job has been permanently failed and unlocked for more than seven days, the next `queueFailedJobsPrune` run logs one warning with its task identifier, key, attempts and last error, and the row is gone afterwards; younger or locked rows are untouched.
- When the only `attempts >= max_attempts` rows are locked or older than seven days, `queue:permanentlyFailedJobs` reports `ok`; a fresh unlocked one flips it to `alerting`.
- `createApiQueueRuntime` installs the `20 4 * * *` entry (the existing crontab test's identifier list includes `queueFailedJobsPrune`).
