**Blocked by:** #1602, #1667, #2009
**Model tier:** high

## Context

Model tier rationale: A new scheduled background mutation that writes user-owned fields through an explicit ownership handover, with chunked per-tenant locking, outage catch-up and realtime invalidation, all of which have concurrency and isolation consequences.

At midnight (in the system timezone) an unfinished one-off task has to move to the next day as an all-day task, day by day until it is done, and then show in Today as "moved from 13 October". A task hidden inside a running event stays where it is and moves only after the event ends. Today no nightly action for Tasks exists. The patterns to follow are the daily action `core.transcriptionRequeueSweep`: its heartbeat on the Semprec project is seeded in `backend/packages/data/src/seed/seedSystem.ts`, the action id is listed in `heartbeatActions` of `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` and in `backend/packages/data/src/manifest/knownActionIds.ts`, the handler is registered in `backend/services/semprec-api/src/actionRegistryComposition.ts`, and an existing deployment gets the heartbeat from `backend/packages/data/src/transcription/transcriptionRequeueHeartbeatCutoverMigration.ts`. Sweeps run per tenant with `FOR UPDATE SKIP LOCKED` chunks (`backend/packages/data/src/scheduler/sweep.ts`, `docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`, `docs/adr/2026-09-28-two-pass-skip-locked-module-data-migration.md`).

`date`, `timeFrom`, `timeTo` and `status` are owned by `user`, so a system writer needs an explicit ownership handover as described by `docs/adr/2026-09-10-single-writer-ownership-model.md` (existing pattern: `convergeObservedEmailFlagsWithClient` in `backend/packages/data/src/mail/mailFlagObservation.ts`). `updateItemWithClient` in `backend/packages/data/src/chokePoint/itemWrites.ts` without an acting user sends an invalidation to every socket of the tenant.

It builds on #1602 (the first-planned-day rule and fields), #1536 (Tasks date and time validation, so the job writes a valid combination) and #1540 (Tasks schema). The recurring-series version of this job is #1677, which extends this action. The event-derived effective day is extended by #1780.

Decision: this is a nightly job that writes `date` (a read model computed without writing was considered and not adopted, so every reader sees the moved date and the same stored value). Per the product owner's preference, the handover is for `date`, `timeFrom`, `timeTo`, and the function is designed so #1677 can add the `missed` status.

Shared-file ordering: this issue also waits for #1667, #2009 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `canonical-keys`, `testing`, `adr-conventions`.

1. Add the action `core.tasksDayRollover`: export `TASKS_DAY_ROLLOVER_ACTION_ID`, a handler factory, a `dailyTime` 00:00 heartbeat on the Semprec project (seed in `seedSystem.ts`, a heartbeat cutover for existing tenants modelled on the transcription requeue cutover, registered in `runTenantCutoverMigrations`), the id in `heartbeatActions` and `KNOWN_HEARTBEAT_ACTION_IDS`, and the handler in `createApiActionRegistry`.
2. Selection: non-deleted tasks that are not recurring (no `seriesId`), have status `notDone`, `effectiveDate` before today in the system timezone, and are visible: `hiddenUntil` empty or before now, and not completed inside an event (`completedInEvent` empty), the same visibility predicate as the Tasks today view (#1798).
3. Update: `date` = today, `timeFrom` = `timeTo` = null, and `since` / `sinceTime` set by the shared rule of #1602.
4. Execution: process per tenant in chunks with `FOR UPDATE SKIP LOCKED`, then a second pass that waits (`FOR UPDATE`) for rows skipped in the first pass, until the predicate returns no rows, bounded by the same chunk cap as the existing sweep (`MAX_SWEEP_CHUNKS_PER_TENANT`); alternatively re-enqueue with job key `tasksDayRollover:<tenantId>` at +5 minutes. Idempotent: a repeated run on the same day changes nothing, and a multi-day outage is caught up with one write per task.
5. Writes go through one dedicated function `rolloverTaskWithClient` in `itemWrites.ts` that performs the explicit ownership handover for `date`, `timeFrom`, `timeTo` (document it with a doc comment pointing to the single-writer ADR). It passes no acting user, so every moved task sends a realtime invalidation, and it does not end an agent takeover and does not start a series advance.
6. Tests per the acceptance criteria, including a row locked during the first pass.

## Scope

### In scope

- The nightly action, its heartbeat seed and cutover, the chunked execution and the ownership-handover write function.

### Out of scope

- The first-planned-day rule itself: #1602.
- Closing recurring occurrences and the `missed` status: #1677.
- Using the event-derived effective day in the selection beyond `date`: #1780 extends the filter.
- Traces and carry-over in the timeline: #1884.
- Following the device timezone for travelling users: not in v1 (decided by the product owner); the system timezone setting is used for the rollover and display, and the app offers to switch it when the device zone changes (client work).

## Acceptance criteria

- A not-done task of 13 October 10:00 to 11:00: after the run on 14 October its `date` is 14 October, its times are empty and `since` is 13 October; after the run on 16 October `date` is 16 October.
- A second run on the same day changes nothing; after a three-day outage one run writes the date of today once.
- A row locked by another transaction during the first pass is moved by the end of the same run.
- A done, wontDo, deleted, recurring or hidden-in-running-event task is not moved; a task whose event ended on 15 October is moved on 16 October with `since` 15 October.
- Every moved task produces a realtime invalidation to the tenant's clients.
