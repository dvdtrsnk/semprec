### Requirement gh-1803: [calendar-module 10/15] Trash and restore a calendar together with its events

#### Context

Model tier rationale: It trashes and restores a calendar together with a possibly large set of Events inside one transaction using shared deletion epochs, enforces which calendars may be deleted and moves the default flag, so an error loses or resurrects user data.

Today `DELETE /api/items/:id` is a soft delete (`itemDeleteWithClient` in `backend/packages/data/src/chokePoint/itemTrash.ts`) that cascades only to inline databases; relation edges stay until the 30-day purge (`trash/purgeExpiredTrash.ts`), and `POST /api/items/:id/restore` restores the rows trashed in the same epoch (the same `deletedAt`). The choke point has no delete or restore hook; #1601 adds them, per process, registered through `domainWriteHooks.ts`. A calendar is a row of the `calendars` database (#1600); its Events are the items on its `Calendars.events` edges.

This issue defines what deleting a calendar means. The user can delete only calendars they created; the system calendars and subscriptions cannot be deleted; the last own calendar cannot be deleted; the deleted default hands the default flag to another own calendar; and the calendar goes to the trash together with its Events so a restore brings back both.

Decision: deleting a calendar moves its Events to the trash with it (they are not moved to the default calendar). An Event that was already in the trash before keeps its own deletion time and is not restored with the calendar.

Decision: when the deleted calendar was the default, the default flag goes to the oldest remaining live own calendar (by creation time, ties by id).

Decision: a restored calendar comes back with `isDefault` false.

Decision: deleting a calendar cancels the meeting invitations of its Events. Every Event trashed here runs the usual item delete side effects, so an Event with invited people sends them a cancellation through the Event delete reaction of #1774. The deletion is always confirmed before it is sent: the client always asks, showing the number of Events and how many invited people will receive a cancellation, and an agent can delete a calendar only through the approval that `item.delete` already requires. The backend itself does not require a confirmation flag.

Requirement on the hook point from #1601: the delete hook may, in the same transaction, move items outside the deleted item's inline subtree (the calendar's Events) to the trash with the same deletion time, and the restore hook may restore the rows of the same epoch. If the hook point cannot do that, this issue writes the cascade itself with the item store's `softDeleteItem` and `restoreItem` and the same epoch.

The 409 for the last own calendar needs its own error code, because `ConflictError` always carries `version_conflict`.

Shared-file ordering: this issue also waits for #1799 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

#### Task

Load `state-writes`, `error-handling` and `testing`.

1. In `backend/packages/data/src/errors.ts`, let `ConflictError` take an optional `code` argument defaulting to `version_conflict` (like `ForbiddenError` does), without changing any existing caller.
2. Add `backend/packages/data/src/calendar/calendarTrashHooks.ts` with `calendarItemDeleteHook` and `calendarItemRestoreHook` for the Calendars database. Delete: reject a `system` or `subscription` calendar with `ForbiddenError` (403 `forbidden`); reject the last live own calendar with `ConflictError` code `last_own_calendar` (409); if the calendar is the default, clear its `isDefault` and set it on the successor chosen above; move every live Event linked to the calendar to the trash with the calendar's deletion time (running the usual item delete side effects). Restore: restore the Events that were trashed in the same epoch; leave `isDefault` false.
3. Register both in `backend/packages/data/src/domainWriteHooks.ts`.
4. Tests: deleting `Sleep` (system) is 403; deleting the only remaining own calendar is 409 `last_own_calendar`; deleting `Personal` (default) makes another own calendar the default in the same transaction; deleting `Family` trashes the calendar and its Events with one deletion time and restoring it brings back both; an Event trashed earlier stays trashed after the restore; a failure in the Events cascade rolls the whole delete back; a calendar of another tenant answers 404; the realtime invalidations for the Events are sent after commit.

### Requirement gh-1796: [calendar-module 09/15] Duplicate an Event or a Task with whitelisted fields and relations in one transaction

#### Context

Model tier rationale: A multi-database copy that must create an item and its relation edges atomically and idempotently under a client-supplied key, with a whitelist that excludes invitation, recording and recurrence state, so a wrong field list silently duplicates or leaks data.

The catalog of generic operations has no duplicate (`backend/packages/shared/src/genericOperations/operationNames.ts`), and the only precedent for copying an item's edges inside a transaction is `copyRelationEdges` in `backend/packages/data/src/tasks/advanceTaskRecurrenceWithClient.ts`. The calendar needs one operation that copies an Event or a Task to a new date and time: the user duplicates the selected calendar item, or pastes a copied one.

This issue adds `POST /api/calendar/items/:id/duplicate`. Routes over Events and Tasks belong to the systemDatabases module (program rule), so it is declared in `backend/packages/data/src/seed/systemDatabasesModuleManifest.ts` with justification `transactional-semantics` (item and edges commit together, with an idempotency key). `/api/tasks/:id/duplicate` is not built; this is the only route.

Request body: `{ date, timeFrom?, timeTo?, endDate? }` with an optional `Idempotency-Key` header. The new item is written through the choke point, so the Events validation of #1663 and the Tasks validation of #1536 apply to the new date and times. ### Requirement gh-1801: [tasks-in-events 08/10] Read an event's tasks with their per-event state

#### Context

An event lists the tasks that sit in it, and each row shows what happened to the task in relation to this event. Decisions:
