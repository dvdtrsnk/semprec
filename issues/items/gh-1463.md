## Context

Model tier rationale: A new column and a helper called from an existing decision transaction, following the existing read-state path, with the care being same-transaction consistency and the realtime event.

A notification only points at something. When the thing is handled (a pending approval decided in the app, on the web or on another device, a problem resolved, an invitation answered), its notification should disappear by itself. Today nothing marks that: `read_at` is set only by `POST /api/notifications/:id/visit` and `POST /api/notifications/mark-all-read` (`backend/packages/data/src/notifications/notificationsStore.ts`, which then publishes `notification_read_state` to connected clients), and `decideAndEnqueueApprovalRequest` (`mcp/approvalDecisionAction.ts`) never touches the approval's notification.

Decisions: a new nullable column `notifications.resolved_at` records that the source was handled; resolving also sets `read_at` (if unset) in the same statement, so connected clients get the existing `notification_read_state` event; notifications are found by `(source_table, source_id)`; for approvals `source_table` is `approval_requests` and `source_id` the request id. The silent dismiss push (#1826) and the reconcile on app open (#1559) build on this. Resolving problems and invitations calls the same helper from their own issues (#1915, #1944); this issue wires approvals only.

## Task

Load `db-migrations`, `state-writes` and `testing`.

1. Add the migration `backend/packages/data/src/db/migrations/NNNN_notifications_resolved_at.sql` (next free ordinal at commit time): `ALTER TABLE notifications ADD COLUMN resolved_at timestamptz` and a partial index on `(tenant_id, user_id, resolved_at) WHERE resolved_at IS NOT NULL`.
2. Add `resolveNotificationsBySource(client, { sourceTable, sourceId })` to `notifications/notificationsStore.ts`: one `UPDATE` setting `resolved_at = now()` and `read_at = COALESCE(read_at, now())` for the unresolved rows of that source, returning the affected rows; it publishes `notification_read_state` after commit (grouped per user) for the rows whose `read_at` changed. Add `resolvedAt` to `NotificationRow`.
3. Call it from `decideAndEnqueueApprovalRequest` with `sourceTable` `approval_requests` and the request id when the call made the decision (outcome `decided`), in the same transaction.
4. Add tests: a decision resolves and reads the approval's notification and publishes one `notification_read_state`; an `unchanged` outcome resolves nothing; a repeat call changes nothing; another user's notification of a different source is untouched; a rolled-back decision leaves the notification unresolved.

## Scope

### In scope

- The `resolved_at` column, the by-source resolve helper and its use for approval decisions.

### Out of scope

- Silent dismiss pushes: #1826; the resolved list for app open: #1559.
- Resolving notifications of problems and invitations: #1915, #1944.

## Acceptance criteria

- When a pending approval is decided, then its notification has `resolved_at` and `read_at` set and connected clients receive `notification_read_state`.
- When the same decision is replayed, then no row changes and no event is sent.
- When the decision transaction rolls back, then the notification is unchanged.
