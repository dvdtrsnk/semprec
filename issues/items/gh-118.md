**Blocked by:** #229, #117

## Context

Issue #229 implemented delegation with a session registry, busy rejection, and a 24-hour TTL after which a delegated session is closed as done. Semp's own conversation with the user follows the same memory policy but differs in one respect: it never ends the way a completed delegated task does. This part adds that pause-and-wake behavior and the per-wake run bookkeeping. #119 builds on it to reconstruct the paused conversation's history before the first resumed turn.

## Task

- Manage Semp's user conversation through the registry and 24-hour in-memory TTL from #229: while the session is in memory, each user message continues the same `AgentSession`.
- On TTL expiry, discard the in-memory object but pause rather than permanently finish the conversation: the conversation key stays resumable indefinitely; the next user message, whether a minute or a month later, resumes the same conversation.
- Each such wake creates a new, separately budgeted `agent_runs` row through #117 with `triggered_by='user'`, `unit='session'`, and `project_item_id` pointing at Semprec itself, inheriting the conversation history from prior wake runs of the same conversation. Inheritance goes through a reconstruction port called at wake; in this part that port is a minimal stub returning no prior history, and #119 fills it with the full reconstruction and context-size check. Record enough on each wake run (the three columns above) for #119 to enumerate the prior runs of the conversation in order.

## Scope

### In scope

- Semp wake semantics, pause on TTL, and per-wake run bookkeeping.

### Out of scope

- The delegation tool, registry, and busy behavior (#229).
- Reconstruction and compaction of the paused history (#119), subprocess isolation, and an additional concurrency cap over pi's parallel calls.

## Acceptance criteria

- A TTL expiry removes memory according to delegated versus Semp semantics: the delegated run is closed as done (#229), while Semp's conversation remains resumable and its next message opens a new wake run.
- Every wake run is a distinct `agent_runs` row with `triggered_by='user'`, `unit='session'`, and Semprec's own `project_item_id`.
- Within the TTL, consecutive user messages continue the same in-memory session without opening a new run.
