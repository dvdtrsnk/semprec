**Model tier:** medium

## Context

Model tier rationale: Coordinates two existing invitation sources so one meeting yields one invitation and one answer.

Invitations arrive today by iMIP in mail ingest; providers also place invitations in the calendar with the user's attendance `needsAction`.

Decision: for an account with Calendars on, iMIP ingest of e-mails received by that account creates no Invitation and no Event; the synced event is the source.

## Task

Load `state-writes`, `db-migrations`, `error-handling`, `io-hardening`, `canonical-keys` and `testing`.

1. When the sync applies an event where the account's address is an attendee with partstat NEEDS-ACTION and the organizer is someone else, create or update an Invitations row linked to the event (kind invite, status pending) and write the `calendar_invitation` notification once per UID and sequence.
2. Answering an invitation linked to a synced event sets the attendee partstat through the adapter (Google `attendees[].responseStatus` with `sendUpdates=all`, Graph `accept`/`tentativelyAccept`/`decline`, CalDAV PUT with the PARTSTAT changed so the server schedules the reply) instead of sending an iTIP REPLY e-mail.
3. iMIP ingest skips e-mails of accounts with Calendars on.
4. A cancellation from the provider sets the invitation `cancelled` and trashes the event as today.

## Scope

### In scope

- Invitations from synced events, answers through providers, iMIP de-duplication.

### Out of scope

- Shared-calendar notices (`sharedCalendarNotice`).

## Acceptance criteria

- A Google invitation appears once in Invitations and once in the timeline.
- Accepting it changes the attendee status at the provider and sends no e-mail.
- The same invitation e-mail received by the account creates nothing.
