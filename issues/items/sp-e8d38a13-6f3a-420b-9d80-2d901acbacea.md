## Context

Model tier rationale: Changes the change detection of the CalDAV adapter for every server without a sync-token, extends the adapter contract with the stored Events' ETags read by the sync pass, and has to keep the iCloud/Fastmail/Nextcloud sync-token path, the apply's deletion semantics and the request bounds intact, proven against a fake server reproducing a real provider's quirks.

Dev server, a real Purelymail account (calendar collection `https://purelymail.com/webdav/1745162/caldav/default/`): pushes from Semprec land (PUT, DELETE), but changes made on the server do not come back. An Event created on the server did not appear after a manual sync (the pass ran and finished `applied` in 2 s with `event_remote_state` empty), and an Event deleted on the server stayed in Semprec. `calendar_remote_state.sync_token` and `ctag` are NULL for the calendar.

Purelymail, verified with curl: PROPFIND `Depth: 0` for `cs:getctag` and `d:sync-token` answers both 404 (no ctag, no sync-token). REPORT sync-collection with an empty `<d:sync-token/>` lists every `.ics` href with its ETag (whether it returns a token is unknown). REPORT calendar-query with `VCALENDAR > VEVENT` and no time-range answers an empty multistatus; with `VCALENDAR` only, or `VEVENT` with a time-range, it lists the Events. calendar-multiget works. PROPFIND `Depth: 1` lists the collection and every `.ics` href.

Root cause: without a sync-token and with no ctag, every pass of the adapter was a full fetch whose only listing was the one request in which the server filters: a calendar-query `VCALENDAR > VEVENT` with the window's time-range (then every listed resource read again by calendar-multiget). Purelymail evaluates that VEVENT comp-filter only partly (empty without a time-range). An empty answer to the adapter's query explains every observation: a full fetch with no upserts is a pass `applied` in seconds that creates nothing and, being full, drops the stored remote state of the window, so a later server-side deletion finds nothing to delete. Inferred, not proven: a fake server given only the curl-verified behaviour (the time-ranged query answering) does not reproduce the empty answer; the old adapter then does see creations and deletions, only re-reading the whole calendar every pass. Which detail of the adapter's query (its three-year range, its exact XML) Purelymail answers empty was not probed, since no request against the real server is made here; the fix therefore stops relying on any server-side filter for servers without a sync-token.

Decisions:
- A server without a sync-token is compared by ETags: an unchanged ctag is still no change; otherwise every resource of the collection is listed with its ETag by PROPFIND `Depth: 1` (a plain WebDAV listing every CalDAV server answers, with no filter), only a resource that is new or whose ETag differs from the stored Events' is read by calendar-multiget in batches of 50, and a stored Event whose resource is no longer listed, or that a re-read resource no longer holds (an override removed from its series), is a deletion. The answer is incremental (`full: false`), so the window does not bound deletions; an Event outside the window is imported like any other.
- The adapter contract's `fetchChanges` options gain `known`: the calendar's stored remote ids, hrefs and ETags (`event_remote_state`), read by the sync pass with its tracked calendars in the prologue transaction (`listEventRemoteRefs`). Google and Graph ignore it.
- A server with a sync-token keeps its path unchanged (sync-collection; a full fetch by the window's calendar-query on a deletion, a changed series or an expired token). A full fetch that finds the server has no sync-token compares by ETags instead.
- A resource that holds no Event (a task, one `ical.js` cannot read) is stored nowhere and is read again by every pass that lists it; no state is added for it.
- Bounds stay: 25 000 responses per answer, 10 MiB per response, 20 s per request, the pass's 5 min deadline, multiget batches of 50.

## Task

Load `state-writes`, `io-hardening`, `error-handling`, `testing`.

1. `adapter.ts`: `fetchChanges(calendar, cursor, { window, signal, known })`.
2. `calendarSyncStore.ts`: `listEventRemoteRefs(client, calendarItemIds)` (read only).
3. `calendarAccountSyncJob.ts`: read the tracked calendars' refs in the prologue and pass each calendar's `known`.
4. `caldavClient.ts`: `listResourceEtags` (PROPFIND `Depth: 1`, `getetag`, member collections left out).
5. `caldavAdapter.ts`: the ETag reconciliation as decided, for every fetch without a sync-token whose ctag is absent or changed.
6. `testSupport/fakeCalDavServer.ts`: a calendar's members by PROPFIND `Depth: 1`, the 404 propstat of version properties a server lacks, switches for no ctag, no sync-token (sync-collection answers only an empty token, with no token) and a VEVENT filter without a time-range answered empty, `behaveLikePurelymail()`, and the hrefs each multiget asked for.
7. `docs/architecture/domain-calendar-tasks-and-media.md`: the contract and the CalDAV change detection.

## Scope

### In scope

- Change detection of CalDAV servers without a sync-token, the `known` refs through the pass, the fake server's Purelymail behaviour, tests and the architecture document.

### Out of scope

- Using a token returned by sync-collection with an empty token (Purelymail's answer shape is unverified).
- Making the sync-token path incremental for deletions and changed series.
- Remembering resources that hold no Event.
- Any request or write against a real server.

## Acceptance criteria

- Against a fake server reproducing Purelymail (no ctag, no sync-token, VEVENT filter without a time-range answered empty), the adapter reads every Event on its first fetch without calendar-query or sync-collection, and an Event created, changed or deleted on the server, and an override removed from its series, is found on the next fetch with only the touched resource read.
- With every ETag unchanged, a fetch sends no GET and no calendar-multiget.
- A sync pass through `handleCalendarAccountSyncTask` with the CalDAV adapter on that fake server applies a server-side creation (`added`) and deletion (`cancelled`, the Event trashed), and a following pass with no change reads no resource.
- A ctag-only server is skipped while its ctag is unchanged and reads only the changed resources otherwise; the sync-token tests (iCloud-style) and the other calendar sync tests stay green.
