## Context

Model tier rationale: The constraint SQL is given and every removal is enumerated, with the compiler catching any leftover reference.

Per-tenant envelope encryption arrived in steps:

- **#1031** gave every tenant a data key wrapped by `CREDENTIALS_MASTER_KEY`, plus `sealSecret`/`openSecret`/`wrapDataKey`/`unwrapDataKey` in `@semprec/credentials`.
- **#1032** added `external_credentials.scheme`. It reads `tenant` rows with the tenant key and `master` rows with the secretbox `decryptSecret` (`backend/packages/credentials/src/index.ts:44-53`) under `resolveMasterKeyFromEnv(key_version)`.
- **#1060** seals every new credential under the tenant key (`scheme = 'tenant'`, bound to `tenant_id‖item_id`).
- **#1062** added the hourly `credentialReencryptSweep`, which re-seals every remaining `master` row through `reencryptCredentialUnderTenantKey` in `backend/packages/data/src/credentials/externalCredentialsStore.ts`. It is registered in:
  - `CORE_TASK_NAMES`/`CORE_TASK_AFFINITY`/`TASK_TENANCY` (`backend/packages/queue/src/index.ts`);
  - `CORE_CRONTAB` plus `createCoreTaskList` (`backend/packages/data/src/worker.ts`);
  - the api runtime's two-tenant task suite (`backend/services/semprec-api/src/__tests__/tenantIsolationJobs.test.ts`).
- **The maintainer checkpoint #1068** confirmed that the strict release runs in production. That release includes the tenant-scheme writes and the sweep, and the checkpoint verified the re-encryption finished: zero `master` rows left.

What remains of the old scheme is a liability:

- A `master` row is not bound to its tenant and item.
- It survives the deletion of its tenant's key.
- The code that opens such rows is the last path that uses the master key directly on a secret.

This is the **contract step**. It must ship in a release after the code switch. The release one back is the strict release confirmed by #1068. It always writes `tenant` rows, so it keeps working against the constraint below.

#1061 also edits `backend/packages/queue/src/index.ts` (the tenancy branch of `registerTask`) and `tenantEnvelope.unit.test.ts`. This issue builds on its merged state, so the two never edit those files concurrently.

## Task

Load `db-migrations` (contract step), `state-writes` and `error-handling`.

1. **Migration** (take the next free ordinal at commit time). A header comment says it is the contract step of the per-tenant credential encryption.
   ```sql
   ALTER TABLE external_credentials ADD CONSTRAINT external_credentials_scheme_tenant_only CHECK (scheme = 'tenant');
   ```
   - If any `master` row still exists, validating the constraint fails the migration, and with it the deploy, before the new code starts. That is the intended guard: never strand a secret.
   - Leave the column's `master` default in place. An insert that omits `scheme` now fails the check, which is the intended fail-closed outcome.
   - In the same migration, complete any queued job of the retired task. Inside a `DO` block guarded by `to_regnamespace('graphile_worker') IS NOT NULL` (the schema does not exist yet on a fresh install at migration time), run `PERFORM graphile_worker.complete_jobs(ARRAY(SELECT id FROM graphile_worker.jobs WHERE task_identifier = 'credentialReencryptSweep' AND locked_at IS NULL))`. `complete_jobs` is the supported deletion path `backend/packages/data/src/observability/queueFailedJobsPrune.ts` already uses. Without this, a leftover job would never be fetched again and would show up as a queue backlog.
2. **`externalCredentialsStore.ts`**
   - Delete `reencryptCredentialUnderTenantKey` and the `master` branch of `getDecryptedCredential`.
   - `scheme` is validated as exactly `tenant`. Any other value throws a plain `Error` after the access-log insert, as a decrypt failure does.
   - Update the header comment.
3. **`@semprec/credentials`**
   - Delete `encryptSecret` and `decryptSecret` (secretbox). Keep `EncryptedSecret`, `MASTER_KEY_BYTES` and `resolveMasterKeyFromEnv`, which now only unwraps data keys.
   - Rewrite the module comment: the master key wraps per-tenant data keys and never seals a credential.
4. **Retire the sweep**
   - Delete `backend/packages/data/src/credentials/reencryptCredentialsJob.ts`.
   - Remove `CREDENTIAL_REENCRYPT_SWEEP` from `CORE_TASK_NAMES`, `CORE_TASK_AFFINITY` and `TASK_TENANCY`, and from the `system` list in `backend/packages/queue/src/__tests__/tenantEnvelope.unit.test.ts`.
   - Remove its `CORE_CRONTAB` line, import and handler entry from `worker.ts`.
   - Update `taskAffinity.unit.test.ts` and `EXPECTED_CRONTAB_IDENTIFIERS` in `backend/services/semprec-api/src/__tests__/queueRuntime.test.ts`.
   - Remove the sweep's case from `backend/services/semprec-api/src/__tests__/tenantIsolationJobs.test.ts`. Its exhaustiveness check fails on a case for a task outside the affinity set.
5. **Env template.** In `deploy/shared/env/master-key.env.example` (the group template #996 created for `CREDENTIALS_MASTER_KEY`), change the variable's comment: it is the key that wraps per-tenant data keys (XChaCha20-Poly1305), no longer a key that encrypts credentials. It still says XSalsa20-Poly1305, carried over from `deploy/shared/.env.example:28-36`.
6. **Tests**
   - Delete `backend/packages/data/src/__tests__/reencryptCredentialsJob.test.ts`.
   - In `externalCredentialsStore.test.ts`, drop the legacy-row cases (they need the deleted `encryptSecret`) and add the cases below.

## Scope

### In scope
- The `scheme = 'tenant'` constraint and the leftover-job cleanup.

### Out of scope

## Acceptance criteria

All integration unless marked.

**Migration**
- Run against a database that still holds a `master` row (constraint dropped first in the test), the migration's SQL fails and leaves the row unchanged.
- Run against a database holding only `tenant` rows, it succeeds. Afterwards inserting a row with `scheme = 'master'`, or without `scheme`, fails with a check violation.
- A pending `credentialReencryptSweep` job is completed (gone from `graphile_worker.jobs`) by the migration. On a database without the `graphile_worker` schema, the migration still succeeds.

**Credential store**
- `storeCredential` followed by `getDecryptedCredential` round-trips in the own tenant.
- Copied ciphertext, a deleted tenant key, and a corrupted ciphertext each still throw, and each attempt is still logged.

**Removals**
- `@semprec/credentials` no longer exports `encryptSecret` or `decryptSecret` (unit, a namespace import of the package).
- `credentialReencryptSweep` no longer appears in `CORE_TASK_NAMES` or `TASK_TENANCY` (unit), in the api runtime's `tenantIsolationJobs.test.ts`, the api runtime's known crontab identifiers or `createApiCoreTaskList`.

**Callers**
- The mail sync, mail send and MCP connection suites pass unchanged.
