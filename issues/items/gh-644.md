## Context

`seedSystem(pool, viewTypeRegistry?, computedKeyRegistry?)` (`backend/packages/data/src/seed/seedSystem.ts:60`) creates the System settings singleton, the Projects database with the Semprec project row, the ten hardcoded databases, the Email/Library/Inbox/MCP module databases and their heartbeats, and finally calls `runModuleDataMigrations(pool, moduleRegistry)` (line 288). Its only callers are tests (`grep -rn "seedSystem(" backend --include=*.ts` outside `__tests__`/`testSupport` finds only `services/semprec-transcribe/src/transcriptionTask.test.ts`). The deploy pipeline runs exactly one CLI: `deploy/deploy.sh:126-134` (`run_migrations`) executes `node packages/data/dist/db/runMigrationsCli.js` under `DATABASE_URL="$SEMPREC_MIGRATE_DATABASE_URL"`, and `backend/packages/data/src/db/runMigrationsCli.ts` runs schema migrations, cutovers and the queue schema — never the seed. There is no seed CLI (`backend/packages/data/scripts/` holds only `check-migration-numbering.mjs`).

A fresh install therefore has no system databases: `getSystemSettingsDatabaseId` (`backend/packages/data/src/systemSettings.ts:10-17`) throws `System settings database has not been seeded`, `assertAuthenticatedAgentIdentity` (`backend/packages/data/src/chokePoint/authorization.ts:53-59`) rejects every agent actor with `The Projects system database does not exist`, and no heartbeat exists to fire.

`seedSystem`'s idempotency guard (`seedSystem.ts:105-109`) is `SELECT id FROM databases WHERE owner_module_id = 'systemSettings'` → return if any row, inside its own `withTransaction`, with no lock: two concurrent invocations both see zero rows and both seed. The existing pattern for this is `SETUP_ADVISORY_LOCK_KEY = 2330n` with `SELECT pg_advisory_xact_lock($1)` in `backend/packages/data/src/auth/authActions.ts:137,173`.

Other issues in this batch assume the seed has run: the api runtime resolves the mail module databases (#648) and the action registries fire seeded heartbeats (#641).

## Task

1. **Advisory lock inside `seedSystem`** — in `seedSystem.ts`, define `const SEED_ADVISORY_LOCK_KEY = 2331n;` (distinct from `SETUP_ADVISORY_LOCK_KEY`) and, as the first statement inside the existing `withTransaction` (before the `existingSettings` query), run `await client.query("SELECT pg_advisory_xact_lock($1)", [SEED_ADVISORY_LOCK_KEY]);`. The guard then runs under the lock, so a second concurrent seed waits and returns early. `runModuleDataMigrations` (after the transaction) is already independently idempotent per its docstring and stays outside the lock.
2. **Seed CLI** — new `backend/packages/data/src/db/runSeedCli.ts`, mirroring `runMigrationsCli.ts`: read `DATABASE_URL` (throw `DATABASE_URL is not set` when missing), `createPool`, then `await seedSystem(pool, createViewTypeRegistry(), createComputedKeyRegistry())` (both from `../chokePoint/`; a fresh per-process registry is what every current caller passes), then `await runModuleDataMigrations(pool, await loadFullModuleRegistry())` (`../manifest/fullModuleRegistry.js`) so data migrations declared by every active module run, not only the `systemDatabases` manifest `seedSystem` loads internally; `pool.end()` in `finally`. Print one line per outcome to stdout (`seed: created system databases` / `seed: already seeded`) — derive it from `seedSystem`'s return value (`"created" | "already-seeded"`), which it decides from its existing `existingSettings` guard inside the advisory-locked transaction — not from a separate `SELECT` before the call, which would let two concurrent runs both report `created` (amended during review of #740); never print connection strings. `tsc` emits it to `dist/db/runSeedCli.js` with no `package.json` change (the `build` script compiles all of `src/`).
3. **`deploy.sh` step** — add `run_seed()` right after `run_migrations()` in `deploy/deploy.sh`, identical in shape (same `systemd-run --uid=semprec --gid=semprec --property=EnvironmentFile="$SHARED_ENV" --working-directory="$staging_dir/backend"`, `/bin/sh -c 'DATABASE_URL="$SEMPREC_MIGRATE_DATABASE_URL" exec node packages/data/dist/db/runSeedCli.js'`, `|| fail "seed failed"`), and call it in `deploy()` immediately after `run_migrations` and before `promote_release`. A seed failure is pre-activation: `current` and the services stay untouched, exactly like a migration failure.
4. **`deploy.test.sh`** — assert `runSeedCli.js` appears in `$TEST_STATE/commands` after `runMigrationsCli.js` on a successful deploy; add a `fail-seed` marker handled by the `systemd-run` mock (fail only the invocation whose arguments contain `runSeedCli.js`) and an `expect_refused 'seed failed' v1.1.0` case that leaves `current` at `v1.0.0` with no partial release, mirroring the existing `fail-migrate` block (lines 170-175).
5. **Docs** — in `deploy/README.md` "Deploying a release" step 3 (lines 58-59), state that the seed CLI runs right after the migrations CLI under the same URL and is a no-op once the system databases exist; add `docs/operations/seeding.md` (short: what `runSeedCli.js` creates, that it is idempotent and lock-protected, that it runs on every deploy, and how to run it by hand for a local database: `cd backend && DATABASE_URL=... node packages/data/dist/db/runSeedCli.js`).
6. **Tests** — `backend/packages/data/src/__tests__/runSeedCli.test.ts` (integration): do not spawn the CLI; put its body in a new `backend/packages/data/src/db/runSeed.ts` exporting `runSeed(pool): Promise<"created" | "already-seeded">` (the registries, `seedSystem` and `runModuleDataMigrations` calls from step 2), have `runSeedCli.ts` call it, and test that function: first call returns `created` and leaves a `systemSettings` and a `projects` database; second call returns `already-seeded` and the `databases` row count is unchanged; two concurrent calls (`Promise.all`) leave exactly one `systemSettings` database.

## Acceptance criteria

- When `deploy.sh <tag>` succeeds, the recorded command sequence contains `runMigrationsCli.js` followed by `runSeedCli.js`, both under `SEMPREC_MIGRATE_DATABASE_URL`; when the seed invocation fails, the deploy exits non-zero with `seed failed`, `current` still points at the previous release and no `releases/<tag>` directory exists.
- When `runSeed(pool)` runs against a migrated, empty database, a `databases` row with `owner_module_id='systemSettings'` and one with `owner_module_id='projects'` exist afterwards and the function returns `created`; a second call returns `already-seeded` and changes no row.
- When two `runSeed(pool)` calls run concurrently, exactly one `systemSettings` database exists afterwards.
- `docs/operations/seeding.md` exists and `deploy/README.md` step 3 mentions the seed CLI.
