## Context

Model tier rationale: A second route over the helpers and write pattern established by the read route, with a small rule difference and no new contract.

The conversation detail has a flag action ("Flag" / "Remove flag"), which must show up in the list, in the Flagged filter and in the Flagged mailbox. A thread is flagged when any of its messages is flagged (`flagged` of the thread list, #1567). Writes must go through `updateItemWithClient` so the provider write-back is recorded (#1494 queues the sync). The route reuses the helpers of #1865 (thread resolution, message classification, invalidation).

Decisions: `flagged: true` flags the last incoming message (and its copies in other mailboxes); `flagged: false` clears the flag on every message of the thread, own messages included; the call is one transaction with one `mailThread` invalidation after commit; versions are loaded by the server.

Shared-file ordering: this issue also waits for #1874, #1892 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Acceptance criteria

- When `flagged:true` is posted, then the thread has a flagged message and appears under `box=flagged`.
- When `flagged:false` is posted, then no message of the thread is flagged.
- When the call succeeds, then exactly one `mailThread` invalidation is sent.
- When the id is unknown or another tenant's, then the response is 404.
