## Context

Model tier rationale: Two-hop batched read composition must preserve provenance, opt-in semantics and tenant separation.

Derived area/company are read from projects, never stored on the source. Project area/company changes affect later reads without writing member items.

Today Files, Health records, Journal and Companies have manual area relations (`Files.area` many-to-many without inverse, `Health records.area`, `Journal.area`, `Companies.area` one-to-one), and `Events.company` is a manual many-to-many with the inverse `Companies.meetings` (`seed/seedTenDatabases.ts`). Nothing computes these, nothing protects them, and no read says whether a value is manual. `Projects.area` is single-valued (a project has at most one area) and `Projects.company` is single-valued. The only derivation today is inside one item (`tasks.time`, `docs/adr/2026-09-19-derived-system-properties-computed-inline-at-choke-point.md`). #1403 adds the `links` read field; this issue adds the third kind of value to it. #1518 provides batched relation reads. #1662 then refuses manual writes where a derived value exists.

Decisions:

- Derived values are computed on read and never stored. They are opt-in with `include=derived` so list queries that do not need them pay nothing; only requesting both `include=derived` and `include=links` additionally lists them in `links` with `valueKind: "derived"`. Links alone retains its prior manual/value-link response and does not compute derived values.
- The area of an item with several projects is the union of those projects' areas, de-duplicated by area id and ordered by title. A project without an area contributes nothing; an item without projects has no `derived` entry for it.
- The event company read is part of this issue because it uses the same mechanism (item to project to attribute); only the guarding of writes is separate.
- An area has `color` and `icon` in the result only if the Areas database has properties with those keys; today it does not, so both are `null`. Adding such properties is not part of this issue.
- A manual edge that already exists on an item with a project stays in storage and in relation reads; the derived value is authoritative in `derived` and `links`. Decided by the product owner: nothing is cleaned up or migrated.
- A Journal entry carries an area like any other item (decided by the product owner): with a project (the Journal-to-Projects relation `project` of #1545) its area is derived from the project; without a project it is the entry's own manual value.

## Acceptance criteria

- When a file has the projects Web for client and Semprec iOS, both in area Work, then `GET /api/items/:id?include=derived` returns `derived.area.values` with Work only; with projects in Work and Home it returns both.
- When a project's area changes, then the next read of its tasks, events and files returns the new area without any item write.
- When a Journal day has the project Web for client, then `derived.area.values` is Work; a Journal day without a project has no `derived.area`.
- When an event has the project Web for client, then `derived.company.values` is Novak Web s.r.o.
- When `include=links` is also given, then `links.area.valueKind` is `derived` with the contributing projects as sources.
- When no `include=derived` is given, then no `derived` field is returned.
- Reading a page of items runs a constant number of queries.
