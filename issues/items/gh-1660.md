## Context

Model tier rationale: A derived system-owned property fed by three source databases needs correct tenant-scoped queue ownership, idempotent recomputation across edge, date, trash and restore changes, a time-based sweep and a backfill, so a missed trigger silently shows a stale value.

People has no "last contact" date. The product shows it per person and sorts and filters on it ("long without contact" means more than 30 days ago; people with no date are not counted). This issue adds `People.lastContact` as a read-only value derived by the backend from the person's past activity, never typed by a user.

Decision: derived, not manual. The date is the latest date of any past item in which the person took part: an Event linked through `Events.people`, an Email linked through `Emails.senderPeople` or `Emails.recipientsPeople` (the e-mail's `date`), and a Transcript linked through `Transcripts.speakers`. Only sources dated at or before the current moment count, and trashed sources do not count. A person with no qualifying source has no value. The date is stored as a calendar date (`YYYY-MM-DD`) in the tenant timezone (`getSystemTimezone` in `backend/packages/data/src/systemSettings.ts`).

Property: `lastContact`, type `date`, `owner: "system"`, `ownerProcess: "people"`. Because it is system-owned, `assertWritableProperties` in `backend/packages/data/src/chokePoint/itemWrites.ts` already rejects any user write with 403; only the recompute writes it, through `updateItemWithClient` with `allowedSystemKeys: ["lastContact"]` and `systemOwnerProcess: "people"`. The owner process id `people` must be added to `KNOWN_OWNER_PROCESS_IDS` in `backend/packages/data/src/manifest/knownActionIds.ts` in this same issue; otherwise `core.driftCheck` reports the property as an orphaned system property.

What it builds on:

- #1457 makes `Emails.senderPeople` many-to-many. Today it is one-to-many, so a second e-mail from the same sender fails with `cardinality_violation` in `linkEmailToPeople` (`backend/packages/data/src/mail/personLinkingActions.ts`), and e-mail based contact dates cannot be correct.
- #1535 edits the same tenant cutover registry (`db/tenantCutoverMigrations.ts`); this issue is ordered after it.
- #1530 adds the hook that fires after a relation edge is written or deleted, and #1601 adds hooks for item delete and restore. Edge hooks run before the write and soft-delete and restore do not run hooks today (`chokePoint/relationOps.ts`, `chokePoint/itemTrash.ts`), so those two blockers are what makes the triggers below possible. Do not call the recompute from `itemTrash.ts` directly.

Later, the relative-date filter issue #1522 builds the "long without contact" filter on this property.

Shared-file ordering: this issue also waits for #1622, #1656 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `db-migrations`, `canonical-keys` and `testing`.

1. Property and labels. Add `lastContact` (`date`, `owner: "system"`, `ownerProcess: "people"`) to the People property list in `seed/seedTenDatabases.ts`; add `property.people.lastContact.name` to `seed/i18n/en.json` ("Last contact") and `seed/i18n/cs.json` ("Poslední kontakt"); add `"people"` (the existing `PEOPLE_MODULE_ID`) to `KNOWN_OWNER_PROCESS_IDS` in `manifest/knownActionIds.ts`.
2. Recompute. Create `backend/packages/data/src/people/lastContact.ts` exporting `recomputePersonLastContact(pool, personId)`. In one transaction it locks the person row, computes the latest qualifying date from the three sources (SQL over `item_relations` joined to the source items, `deleted_at IS NULL`, date not after now), and writes `lastContact` through the choke point only when the value changed (clearing it when no source qualifies). A missing or trashed person is a no-op.
3. Queue. Add the tenant task `peopleLastContactRecompute` (payload `{ personId }`) and the system task `peopleLastContactSweep` to `CORE_TASK_NAMES`, `CORE_TASK_AFFINITY` (api) and `TASK_TENANCY` (recompute tenant, sweep system) in `backend/packages/queue/src/index.ts`. Enqueue with `jobKey: people-last-contact:<personId>` and `queueName: tenantLane("people-last-contact")`, in the same transaction as the triggering write (same shape as `enqueueRollupRecompute` in `rollup/recompute.ts`). Wire both handlers in `createCoreTaskList` in `worker.ts`.
4. Triggers, in `backend/packages/data/src/people/lastContactHooks.ts`, registered in `domainWriteHooks.ts`: (a) the edge-changed hook from #1530 for `Events.people`, `Emails.senderPeople`, `Emails.recipientsPeople` and `Transcripts.speakers`, enqueueing the person on the target side; (b) an item update hook that, when the patch changes `date` on Events, Emails or Transcripts, enqueues every person linked to that item; (c) the delete and restore hooks from #1601 on Events, Emails and Transcripts, enqueuing every person linked to the item.
5. Daily sweep. `handlePeopleLastContactSweep` uses `forEachActiveTenant` and, per tenant and in batches, enqueues a recompute for each person linked to a source whose date fell within the last 24 hours (a future event that has now passed triggers no write otherwise). Add `0 1 * * * peopleLastContactSweep` to `CORE_CRONTAB` in `worker.ts`.
6. Backfill and cutover. Create `backend/packages/data/src/people/peopleLastContactCutoverMigration.ts`: per tenant it adds the `lastContact` property to an existing People database by direct insert (idempotent, as in #1535), sets `owner_process` when the row already exists, and enqueues a recompute for every non-trashed person. Register it in `db/tenantCutoverMigrations.ts` after the phones cutover.
7. Tests, including the scenarios in Acceptance criteria and a tenant isolation case (a recompute in tenant A never reads or writes tenant B).

## Scope

### In scope

- The derived `lastContact` property, its recompute, the triggers from edges, date changes, delete and restore, the daily sweep, and the backfill.

### Out of scope

- A manual last contact date written by users; it is deliberately refused.
- The "long without contact" filter and sorting by this property: #1522.
- Phone numbers: #1535.
- Showing the date in any detail or list screen.
- Counting other kinds of contact (tasks, chat messages).

## Acceptance criteria

- When an event dated 15 Oct (in the past) is linked to a person, then `lastContact` is 15 Oct.
- When the only linked event is tomorrow, then `lastContact` is unchanged; when the sweep runs the day after, then `lastContact` is that event's date.
- When the person is removed from the event, or the event is trashed, then `lastContact` returns to the previous latest date; when the event is restored, then it is set again.
- When an e-mail's `date` changes, or a second e-mail from the same sender arrives, then `lastContact` reflects the latest e-mail date and the action does not fail.
- When a user (or an agent without the owner process) tries to write `lastContact`, then the request is rejected with 403.
- When a person has no qualifying source, then `lastContact` is empty.
- When the cutover runs twice on a populated tenant, then the property exists once and every person is recomputed; another tenant's people are never touched.
