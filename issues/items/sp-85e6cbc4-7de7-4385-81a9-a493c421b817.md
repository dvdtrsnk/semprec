## Context

Semprec connects e-mail accounts (Gmail and Outlook by OAuth, iCloud and generic IMAP by password) and syncs them both ways, but calendars from the same providers reach the app only as read-only ICS subscriptions or e-mailed invitations. The owner wants one "internet account" per provider login, like iOS Settings > Mail > Accounts, where Mail and Calendars are switched on separately, calendars sync both ways efficiently, and the phone is notified when someone else adds or changes an event or sends an invitation in a calendar the user follows (for example the shared green "Family" calendar).

## Decisions

- Question: What is an internet account?
  - Adopted answer: The existing Mailboxes item becomes the account. It gains user-owned service switches `mailEnabled` and `calendarsEnabled`; its credential, server settings, OAuth state and sync state stay where they are. The database key `mailboxes` and the `/api/mail/mailboxes*` routes stay; the label becomes "Internet accounts".
  - Reason: Every mail side table already hangs off this item; a new parent entity would rewrite finished mail sync for no user-visible gain.
- Question: Which calendar providers?
  - Adopted answer: All four from the start: iCloud and generic CalDAV (Fastmail, Nextcloud and similar) over CalDAV, Google over Google Calendar API v3, Microsoft over Microsoft Graph.
  - Reason: Owner decision.
- Question: Contacts?
  - Adopted answer: Not now. No CardDAV, People API or Graph contacts in this epic.
  - Reason: Owner decision.
- Question: How does the iOS app return from an OAuth sign-in?
  - Adopted answer: A custom URL scheme, `semprec://oauth`, through `ASWebAuthenticationSession`.
  - Reason: Owner decision; no associated-domain file is needed.
- Question: What happens when an event changes on both sides between two syncs?
  - Adopted answer: A three-way merge per field against the last synced snapshot: a local change wins on fields the provider did not change; when both changed the same field, the provider's value wins and the local change is reported as overwritten.
  - Reason: Owner decision.
- Question: How does this reach production?
  - Adopted answer: Production moves from the v0.1.x hotfix line to `develop`; that cutover is its own operational record in this epic and is a deployment precondition, not something an agent attests.
  - Reason: Owner decision.
- Question: Who writes synced events?
  - Adopted answer: One system writer, the calendar sync process `calendarSync`, owns the remote identity and applies provider changes through the choke point; user writes to synced calendars are recorded as desired state and pushed by the same process.
  - Reason: One owner, one writer; provider write-backs follow the desired/current pattern.

## Behavior specification

1. Settings show "Internet accounts". Adding one asks for the provider (iCloud, Google, Microsoft, Other). Google and Microsoft sign in in the system browser sheet and return through `semprec://oauth`; iCloud asks for the address and an app-specific password; Other asks for the address, password and the IMAP, SMTP and CalDAV servers it uses.
2. An account shows a switch per service: Mail and Calendars. Turning a service on starts its sync (asking for additional consent for an OAuth account that lacks the scope); turning it off stops it and removes that service's synced data, keeping the account and its sign-in. An account with both services off still exists until removed.
3. Every calendar of an account with Calendars on appears in the calendar list grouped under the account, with the provider's colour (which the user may override locally), the notify switch and visibility. Calendars the user may not write to are read-only.
4. Events created, changed, moved or deleted in the app in a writable synced calendar reach the provider; events created, changed or deleted at the provider (by the user elsewhere or by someone sharing the calendar) reach the app within seconds for Google and Microsoft (push) and within five minutes for CalDAV (polling, plus a sync when the app becomes active).
5. Recurring events, time zones and exceptions round-trip unchanged; the app edits the simple rules it supports and keeps a complex rule as it is.
6. Invitations in a synced calendar appear in Invitations and are answered through the provider. An account with Calendars on does not also import the same invitation from its mail.
7. When someone else adds, changes or cancels an event in a synced calendar whose notify switch is on, the phone receives a push such as "Family: Peter added Dinner, Fri 19:00". The first sync of an account is silent; many changes at once collapse into one notification.
8. Sync problems (sign-in needed, missing permission, provider refused) show on the account and as Semp problems, like mail sync problems today.
