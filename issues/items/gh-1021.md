**Blocked by:** #973, #975

## Context

The runtime roles get their only DDL through two `SECURITY DEFINER` functions owned by the migrating role, per `docs/adr/2026-09-27-runtime-ddl-through-security-definer-functions.md`:

- `create_items_partition(database_id uuid)` (`backend/packages/data/src/db/migrations/0048_create_items_partition_function.sql:23-36`) runs `CREATE TABLE public.items_p_<hex> PARTITION OF public.items FOR VALUES IN (<id>)`.
- `drop_items_partition(database_id uuid)` (`backend/packages/data/src/db/migrations/0050_drop_items_partition_function.sql:20-29`) runs `DROP TABLE IF EXISTS public.items_p_<hex>`.

`EXECUTE` on both is granted only to `semprec_data`. Their callers are `databasesStore.createDatabase` (`backend/packages/data/src/chokePoint/databasesStore.ts:110`, right after inserting the `databases` row in the same transaction) and `dropDatabaseWithPartition` (`databasesStore.ts:201`, before deleting the `databases` row).

A definer function runs as the table owner, so row-level security does not apply inside it. Today either function accepts any uuid:
- `create_items_partition` makes a partition for a database that does not exist, or one that belongs to another tenant;
- `drop_items_partition` drops another tenant's partition, along with every item in it.

A runtime-role caller in one tenant must not be able to touch another tenant's partition through them.

What #973 and its predecessors provide:
- `databases` has `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)` and row-level security.
- The tenancy SQL functions are:
  - `app_current_tenant()` = `NULLIF(current_setting('app.tenant_id', true), '')::uuid`;
  - `app_sole_tenant()` = the tenant id when exactly one `tenants` row exists, else NULL;
  - `app_tenant_default()` = `COALESCE(app_current_tenant(), app_sole_tenant())`.
- #1067 later redefines `app_tenant_default()` to `app_current_tenant()` alone. The check below therefore becomes strict automatically, with no second change to these functions.
- `app.tenant_id` is the caller's session or transaction setting. A `SECURITY DEFINER` function sees the caller's value, because only `search_path` is pinned on these functions.

Rollback safety: the previous release calls the same signatures for databases it just created in the sole tenant. Those always pass the check.

## Task

Load `db-migrations` (a forward-only function replacement). Add no new ADR: the functions keep the shape `docs/adr/2026-09-27-runtime-ddl-through-security-definer-functions.md` requires (one escaped statement, pinned `search_path`, single grantee) and only gain a guard.

1. **Migration.** Take the next free migration ordinal at commit time and add a migration under `backend/packages/data/src/db/migrations/`. It uses `CREATE OR REPLACE FUNCTION` for both functions and keeps for each:
   - the same name, signature and `RETURNS void`;
   - `LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, public`;
   - the same `format()` statement with `%I` and `%L`.

   As the first statement of each body, add:
   ```sql
   IF NOT EXISTS (
     SELECT 1 FROM public.databases d
     WHERE d.id = <function_name>.database_id
       AND d.tenant_id = (SELECT public.app_tenant_default())
   ) THEN
     RAISE EXCEPTION '<function_name>: database % is not a database of the current tenant', <function_name>.database_id
       USING ERRCODE = 'no_data_found';
   END IF;
   ```
   - Qualify the parameter with the function name, which avoids any clash with a column name.
   - A missing database and a foreign one hit the same branch with the same message.
   - `CREATE OR REPLACE` keeps owner and grants, so do not repeat the `REVOKE` and `GRANT` statements. Do say in the migration's header comment that they are unchanged.
   - The header comment also names this issue's reason: definer functions bypass row-level security, so they check the tenant themselves.
2. **Callers unchanged.** `databasesStore.ts` keeps calling both functions as today.
3. **Tests.** Add `backend/packages/data/src/__tests__/itemsPartitionTenancy.test.ts` on the #975 harness:
   - `createRuntimeRolePool(adminPool, "semprec_data")`;
   - `createTestTenant(adminPool)` for tenant B and `getTenantZeroId()` for tenant A;
   - each step runs in `withTenantTransaction(dataPool, tenantId, fn)`;
   - partition existence is checked as superuser with `to_regclass('public.items_p_<hex>')`.

   The scope-less case runs before the test creates tenant B, because a second tenant makes the sole-tenant fallback NULL.

## Scope

### In scope
- The tenant guard in both function bodies, through function replacement, and its tests.

### Out of scope
- Creating partitions with `CREATE TABLE … ATTACH PARTITION` so `items` is not locked `ACCESS EXCLUSIVE` (#1036, which replaces the same function after this one).
- Pruning id-only item lookups to the tenant's partitions (#1003).
- Purging a deleted tenant's partitions (#1055).
- Revoking runtime-role privileges on `items_p_*` partitions, which is the catalog assertion of #973.

## Acceptance criteria

- **Foreign create refused.** Tenant A has a `databases` row with no partition yet; the test inserts it as superuser. As `semprec_data` in tenant B, `SELECT create_items_partition(<A's id>)` fails with SQLSTATE `P0002`, and no `items_p_<hex>` table exists afterwards. In tenant A, the same call succeeds and the partition exists. (integration, `itemsPartitionTenancy.test.ts`)
- **Foreign drop refused.** Tenant A has a database created through `databasesStore.createDatabase`. As `semprec_data` in tenant B, `SELECT drop_items_partition(<A's id>)` fails with SQLSTATE `P0002`. A's partition and its items still exist. (integration, `itemsPartitionTenancy.test.ts`)
- **Unknown id.** Either function called with a random uuid fails with SQLSTATE `P0002` and the same message shape as the foreign case, apart from the id. (integration, `itemsPartitionTenancy.test.ts`)
- **Own tenant unchanged.** In tenant A, `createDatabase` followed by `dropDatabaseWithPartition` creates and then removes A's partition, exactly as before. (integration, `itemsPartitionTenancy.test.ts`)
- **Scope-less, one tenant.** With no `app.tenant_id` set and only tenant zero present, `createDatabase` still creates its partition. This is the previous-release path. (integration, `itemsPartitionTenancy.test.ts`)
- **Hardening kept.** `pg_proc` for both functions still shows `prosecdef = true` and `proconfig` containing `search_path=pg_catalog, public`. `has_function_privilege('semprec_side', ...)` is false and it is true for `semprec_data`. (integration, `itemsPartitionTenancy.test.ts`)
