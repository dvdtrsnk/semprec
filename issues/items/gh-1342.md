## Behavior specification

Tasks in events: link, visibility, completion and event detail tasks.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: tasks-in-events-1 (link, visibility, completion, event detail tasks)

#### (a) Decisions adopted from open questions and gaps

- Stored `hiddenUntil`/`effectiveDate` with an end-of-event job, or a read model? -> stored values (#1780) plus the job (#1782) -> the schema (#1540) and the issue list already assume stored values; E3 stays.
- Recurring task dragged into an event -> rejected with 400 on `taskId` until single-occurrence materialization (#1720) is wired in; the whole-series insertion of the design is not built -> conservative, avoids hiding a whole series.
  -> Decided by the product owner: the 400 stays until a single occurrence can be created; then only that occurrence moves into the event and the series stays (#2012).
- `hiddenUntil` format -> UTC ISO instant; event day = the event's `date`.
- Task day while hidden -> `date` of the live host event added last; after all ended -> later of the task's date and that event's date; no host events -> the task's `date`.
- When is a completion "in the event"? -> Decided by the product owner: every completion made before the end of the event counts as a completion in the event, wherever the task is ticked (list, task screen, event, agent). A task is part of its event until the event ends, so a separate complete-in-event path is an unnecessary special case: #1781 records the completion in the event from the status change itself and adds no route. A completion after the event ended shows as "done later" (`doneElsewhere` with the date) on another day, or as `done` on the same day.
- Completion day -> the ordinary `completedOn` rule of #1544 applies (today by default); a completion is linked to one event only, the last live host event.
- State order for event task rows follows the design: done later, done here, done elsewhere, moved, missed, open; `wontDo` counts as not done.
- Restoring a deleted event -> does NOT put tasks back (principle: restoring a source does not re-link); the restore hook removes the stale `hostedTasks` edges. Delete keeps the edges until restore and only recomputes the tasks.
  -> Decided by the product owner: restoring an event does not return its tasks, in line with the rule that restoring a source does not re-link (#1819).
- Timeline -> selects Tasks by `effectiveDate`, hides tasks with future `hiddenUntil` and tasks completed in an event; event items carry `tasks` and `counts`, task items carry `hostEvent` (with `state`).
- `Tasks.sourceEvents` inverse keeps the relation many-to-many and user-owned (cardinality question left to the owner of a related issue, now cancelled).
- Task from an action item -> generic item create with relations (#1590), no custom route; link rules `taskProjectFromEvent` and `taskPeopleFromEvent` with the own-person filter; the company is not a task value.

#### (b) Open questions that remain for the product owner

- Wording of the event-delete confirmation and of the agent approval request ("Tasks in the event (N) return to their day"): only the count function is provided (#1819); the approval description wording is not assigned to an issue here.
- Events without an end time: the hide period uses the end filled by #1598 (+1 h) while the design computed +30 min; confirm +1 h.
- Cardinality of `Events.actionItems` / `Tasks.sourceEvents` (can a task have several source events?).

#### (c) User-visible behavior

A task dragged onto an event becomes part of it: it keeps its place in the Tasks collection and its own date and time, but disappears from lists, counts, search, areas and the calendar until the last event it sits in has ended, and is shown only inside the events (a task can be added to several events one after another, the last one added decides; adding it again to the same event moves that event to the end). A task completed before its event ends, from anywhere, counts as completed in the event (it then shows as done in that event and leaves the day and the list); inside an event it can also be taken out of this event, or taken out of all events with a new date and time. After the last event ends, an unfinished task comes back on its own, shown as "not done" in the event and as an all-day item on the day derived from its events; deleting an event gives its tasks back immediately, and restoring the event does not put them in again. The event detail lists its tasks with their state (done later, done here, done elsewhere, moved on to another event, not done, open) and counts, and the calendar timeline returns the same data. Tasks created from an event's action items inherit the event's project and participants (without the user's own person) until changed by hand, and action items can be queried from the Tasks side. A recurring task is placed into an event as one occurrence only, and the series stays as it is.
