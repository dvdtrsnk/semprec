## Context

Model tier rationale: One new tenant-scoped table with a partial unique index plus a store following existing mail table conventions, with no new authorization or concurrency contract beyond what the index enforces.

A mail draft needs more than the display fields that `createEmailDraft` in `backend/packages/data/src/mail/draft.ts` writes today (name, sender, recipients as text, body on an Emails item, and an edge to the Drafts folder). The structured parts are missing: the mailbox the draft belongs to, structured recipients (name and address for to, cc and bcc), the thread, the reply mode and its source message, the threading headers, who created and last edited it (the user or the agent), and whether it was sent. Nothing calls `createEmailDraft`, there is no route, and updating or deleting a draft does not exist. Provider drafts (Gmail label DRAFT, IMAP Drafts) are synced as Emails in a drafts folder without any such row.

This issue adds the metadata storage only. The HTTP interface that creates, reads, updates and discards drafts is #1867. Counting threads that have a Semp-written draft (#1694) and retiring one once the user replies (#1902) build on the same table.

Decision: only drafts with a `mail_drafts` row are editable by Semprec. Provider drafts without a row stay read-only.

Decision: the draft lives only in Semprec; uploading it to the provider's Drafts folder is not part of this work.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Add a migration `backend/packages/data/src/db/migrations/NNNN_mail_drafts.sql` (next free ordinal at commit time) creating `mail_drafts`: `email_item_id` primary key (no foreign key to `items`, like the other mail tables keyed by item id), `tenant_id` with the tenancy classification, row-level security and grants as in `0078_tenant_exports.sql`, `mailbox_item_id`, `thread_id` nullable, `mode` constrained to `new`, `reply`, `replyAll`, `forward`, `source_email_item_id` nullable, `in_reply_to` nullable, `references text[]`, `from_address`, `to_recipients`, `cc_recipients`, `bcc_recipients` as `jsonb` arrays of `{ name, address }`, `created_by` and `last_edited_by` constrained to `user` or `agent`, `agent_run_id` nullable, `conversation_id` nullable, `created_at`, `updated_at` and `sent_at` nullable. Add a partial unique index on `(tenant_id, thread_id)` where `created_by = 'agent' AND sent_at IS NULL AND thread_id IS NOT NULL`, so the database allows one unsent Semp draft per thread. Additive and rollback-safe.
2. Add `backend/packages/data/src/mail/mailDraftsStore.ts` with typed insert, get by email item id, update and mark-sent functions, validating rows read back with the project's row validation helpers. A violation of the one-draft-per-thread index surfaces as a distinct error the callers can map.
3. Extend `createEmailDraft` in `draft.ts` so that it can create the metadata row in the same transaction, sets a `date` on the Email item, and accepts structured recipients, mailbox, thread, mode and creator. Existing callers keep working.

## Scope

### In scope

- The `mail_drafts` table, its store and the extension of `createEmailDraft`.

### Out of scope

- Routes, version checks and invalidations (#1867).
- Reply and forward prefill (#1899), attachments (#1895) and sending (#1896).
- Counting or retiring Semp drafts (#1694, #1902).
- Uploading drafts to the provider.
- Marking a new draft as read; that belongs to the work that sets read state on drafts and is not part of this batch.

## Acceptance criteria

- When a draft is created through the store, then the Emails item, the Drafts folder edge and the `mail_drafts` row exist together or not at all.
- When a second unsent draft with `created_by = 'agent'` is inserted for the same thread in a tenant, then the database rejects it; user drafts are not limited, and the same thread id in another tenant is allowed.
- When a draft is marked sent, then a new agent draft for the same thread can be inserted.
- Recipients are stored and read back as `{ name, address }` lists in the original order.
