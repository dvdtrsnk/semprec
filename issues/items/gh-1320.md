## Behavior specification

Journal: period keys, reads, ensure, trash, day view and collection.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions - journal-1

#### (a) Decisions adopted
- temporal-switcher default granularity 'day' or left to the client? -> left to the client; the default stays as is, no change -> not needed for any backend mechanism.
- Keep the 'month' type in the schema although a month has no note of its own? -> kept (recommended) -> removing an option is a contract migration.
- Restoring a trashed period when a live one exists: refuse (409) or let ensure restore the trashed one? -> refuse restore with 409; ensure keeps creating a fresh entry (#1666) -> avoids changing the existing #682 behavior.
- Deleting a Journal entry deletes the entry or only its page? -> the entry (existing behavior); therefore Inbox items are re-linked to the new entry on creation (#1603).
  -> Decided by the product owner: deleting a Journal period deletes the whole period including its entry (to the trash, restorable for 30 days); #1603 is done.
- Relink implemented as a Journal create hook owned by Inbox (#1603) rather than inside getOrCreateJournalItem -> one registration covers every caller (ensure, proposals, subpages, Semp, Inbox capture) and respects the choke-point-knows-no-domain rule.
- Do all-day events and birthdays show in a Journal day? -> Decided by the product owner: yes; the day view shows all-day events and birthdays as a compact row at the top, because the Journal is an overview of the day and its data stays consistent with the calendar. All-day events come with the day's events of kind `event` (#1721); birthdays come from the timeline's birthday source (#2015); public holidays and timed tasks stay excluded.
- Journal day event meta line -> client concern; recommended place and transcript state before project.
- Event row colour -> the calendar's colour via calendarId, no colour on the response (#1881).
- Writes to any period, past or future, with no upper limit (#1541); zone always from the tenant, never from the client.
- Empty page vs absent: markdown "" for an existing empty page, null when there is no entry or page (#1613).

#### (b) Open questions for the product owner
- None.

#### (c) User-visible behavior
The Journal opens on the user's today in their own time zone and shows the right day, ISO week, month, quarter and year for any date, including weeks that straddle a month or year boundary. Viewing an empty period never creates anything; the first write into a day, week, quarter or year note creates the period and its page once, even from two devices at the same time. A day shows its events from the calendar (ordered, with project, place and transcript state, including recurring and overnight events, with all-day events and birthdays in a compact row at the top) and its Inbox items, and a week can be read as formatted text inside its day and month. Journal entries cannot be created by hand through any API, and restoring or recreating a deleted day never leaves two entries for the same day or loses the day's Inbox items.


### Decisions - journal-2

#### (a) Decisions adopted
- proposalSummary for all items or only items with an attachment? -> computed for every item whose card is `proposed`; the client chooses what to show (#1489) -> simpler rule, small cost.
- Journal entry title: user property (a) or derived (b)? -> derived `computed.journalSummary` (first heading, else first non-empty line, plain text, max 80 chars, null without page) (#1711) -> no change to the schema-locked Journal, no cutover, cannot go stale against the page. Consequence: the dependency on #1413 is not needed by this issue.
  -> Decided by the product owner: the title is the derived summary (a derived value); the user does not override it, and a user-editable title is not planned.
- Existing Journal entries get journalSummary only on their next page edit (no backfill) -> keeps the issue to one mechanism.
- '+' on the Journal collection -> Decided by the product owner: '+' opens a period picker (today by default) and creates the period's entry or opens the existing one through the same lazy create route used everywhere else (#1541), so no duplicate can arise; Journal creation stays only through that route and no new backend mechanism is needed.
- User-owned properties on system collections -> Decided by the product owner: not in v1; the schema of system collections is governed by the manifest.
- Type edge deletion leaving an item without a type -> decided in #1669, not here; #1718 reacts to any accepted edge change.
- groupDirection default and Journal group order -> optional, default asc, additive; Journal day-first order is `groupDirection: desc` instead of reordering options (#1532). Seeding the grouped collection view is not planned yet and waits for a product decision.
- Journal -> Projects relation -> user-owned, many-to-many, one-directional, added by per-tenant cutover plus seed (#1545). Journal -> Events relation -> many-to-many, one-directional, added the same way, but system-owned because it is derived from event links in the day's text (#1609).
- Should an event link in day text also create the `events` relation? -> Decided by the product owner: yes; an event link in the day's text adds the `events` relation as a derived value and removing the link removes it; the text is the single source of truth. The link itself stays plain content in the parser (#1614); the relation is derived from the links by #2016.
- Item link in Markdown -> `[Title](semprec://items/<id>)`; unknown and foreign ids return the same 400 (#1614).
- Tick write phase always enqueues the day recompute on every card write path (#1390).
- Requirement on #1485 recorded in #1489: computeFailed must also be written after retries are exhausted, otherwise `pending` never ends.

#### (b) Open questions for the product owner
- Seed the grouped Journal collection view on the server, or let the client create it? Where should its default sort live (view or manifest defaultSort)?

#### (c) User-visible behavior
The Journal day lists its Inbox items with a clear processing state ("Semp is preparing a proposal", failed, or the card status), a summary of what Semp proposes (target database, project, area and follow-up steps) and the attachments with name, type, size, page count and a small thumbnail; the list refreshes when the tick writes a proposal, when attachments change and when an item's type is changed from the day. Journal entries get a short subtitle derived from their page, can be linked to projects, and to calendar events by linking an event in the day's text (with Czech and English labels), and page text can contain links to any item. Grouped lists can be ordered in either direction, so the Journal collection can show days first and years last.
