## Context

Model tier rationale: This adds a new tenant- and user-scoped realtime message across the NOTIFY publisher, the WebSocket protocol and the client, published from three processes' write paths including the exactly-once execution transaction, so the isolation and after-commit ordering contracts are new.

Realtime today only tells a client about items, schemas, notifications, agent run events and revoked sessions (`RealtimeMessage` in `backend/packages/realtime/src/pgNotifyPublisher.ts`, `OutboundFrame` in `backend/packages/realtime/src/protocolV1.ts`). The state of an approval request changes at three moments and none of them is published: when it is created (`preflightDestructiveApproval` in `backend/packages/application/src/genericOperationGateway.ts` and `createApprovalGatedMcpInvokeTool` in `backend/packages/agent-runtime/src/mcpInvokeTool.ts`), when a person decides it (`decideAndEnqueueApprovalRequest` in `backend/packages/data/src/mcp/approvalDecisionAction.ts`), and when execution records its result (`replayApprovedGenericOperation` in `genericOperationGateway.ts` through `markApprovalRequestExecutionSucceeded` / `terminalizeApprovalRequestAsConflict`, and `handleApprovalRequestExecuteTask` in `backend/packages/data/src/mcp/approvalRequestExecution.ts` through `recordApprovalRequestOutcome` / `settleStaleApprovalRequestClaim`). A client that shows a request therefore cannot learn that it was decided elsewhere or that execution finished.

Following the thin-invalidation rule in `docs/adr/2026-09-12-thin-user-scoped-realtime-invalidations.md`, this issue adds one thin message that names the request; the client refetches `GET /api/approval-requests/:id` (delivered by #1786). It reuses the Semp thread invalidation from #1395 for the thread of the request, and the way `semprec-agents` publishes realtime messages from #1383 (the creation path in `mcpInvokeTool.ts` runs in that process). Two of the three write sites it changes (`replayApprovedGenericOperation`, `approvalRequestExecution.ts`) are also changed by #1713, so it follows that issue. #1887 (live step state) and #1863 (the next frame added to the same union) build on it.

Decision: delivery is narrowed to the owner of the request (the actor user of its run), inside the publisher's tenant, like the other user-scoped invalidations; a socket of another tenant or another user of the same tenant receives nothing.

## Task

Load `state-writes`, `io-hardening` and `testing`.

1. Add `{ type: "invalidation"; scope: "approvalRequest"; approvalRequestId: string; userId?: string }` to `RealtimeMessage`, to `parseRealtimeMessage` (UUID-validate `approvalRequestId`; drop a malformed message) and to the invalidation hook event type in `backend/packages/data/src/realtimeHook.ts`.
2. Add the matching outbound frame `{ type: "invalidate"; scope: "approvalRequest"; approvalRequestId: string }` to `OutboundFrame` in `protocolV1.ts`, route it in `syncServer.ts` to the sockets of `userId` only, and add the frame to `backend/packages/realtime-client` with its parser, so a client receives it typed.
3. Publish it with `runAfterCommit` (never before the transaction commits) at the three moments above: after the pending request insert in both creation paths; after the decision in `decideAndEnqueueApprovalRequest` (both approve and reject, not for an `unchanged` result); and after each execution result write in `genericOperationGateway.ts` and `approvalRequestExecution.ts` (generic success, generic conflict, MCP outcome, stale-claim settlement). The discarded-outcome case publishes nothing.
4. At each of these points also publish the Semp thread invalidation from #1395 for the thread of the request's run (`agent_runs.thread_id`); a run without a thread publishes only the approval request message.
5. The creation path in `mcpInvokeTool.ts` publishes through the `semprec-agents` realtime publisher from #1383.

## Scope

### In scope

- The new message and frame, its parsing, user-scoped delivery, the after-commit publishes at creation, decision and every execution result write, and the paired thread invalidation.

### Out of scope

- The REST read the client refetches: #1786.
- The step projection that uses the invalidation: #1887.
- Posting a message into the thread: #1772.
- Notification resolution and badge counts: not part of this issue.

## Acceptance criteria

- When a request is created, decided (approved or rejected) or finishes executing (generic success, generic conflict, MCP success or error, stale claim settled), a socket of the owner receives `{ type: "invalidate", scope: "approvalRequest", approvalRequestId }` exactly once per write.
- A socket of a different tenant, and a socket of another user of the same tenant, receives no such frame.
- A transaction that rolls back publishes nothing.
- A repeated PATCH on an already decided request, and a discarded duplicate outcome, publish nothing.
- A run with a Semp thread also triggers the thread invalidation; a run without one does not.
- `parseRealtimeMessage` returns `null` for an `approvalRequest` message with a non-UUID id.
