## Context

Model tier rationale: This scopes several existing reads (detail, steps, usage) by an event range, an approval link and a gateway attribution across a shared session run, so a wrong boundary mixes another reply's data; it joins six blockers' contracts and must keep tenant and conversation isolation, which is why the higher tier is chosen.

A chat conversation is one long-lived run (`unit = session`) that is reopened for each message, so one run holds many replies. The run detail (#1805), the steps (#1821) and the spend (#1822) all describe the whole run. The chat shows a summary for one reply and a link to see that reply's full progress and cost; that view must show only that reply's facts. Nothing global is added: a reply is a row of the thread message table (#1367) that already stores the run id, the first and last run event of the reply (`event_from_id` .. `event_to_id`), the step summary, duration and token counts (#1860), and its user message as `reply_to`; the gateway calls of the reply are attributed by `ai_gateway_calls.semp_message_id` (#1744); approval requests of the reply are those whose tool call falls in the event range (#1618 adds the tool call id to the request).

This issue adds one optional query parameter, `messageId`, to three reads, with the same semantics:

- `GET /api/agent-runs/:id?messageId=<assistant message id>`: `title` is the text of the user message the reply answers (`reply_to`; when the trigger was a system message without text, such as the continuation of a heartbeat after an approval, an i18n title from the message's `system_key`, for example the `approval.outcome.*` keys), `startedAt` is the reply's start, `durationMs` is the message's stored `duration_ms`, `approvals` counts only requests whose tool call lies in the reply's event range, and `usage` (the spend fields from #1822) covers only gateway calls with this `semp_message_id`.
- `GET /api/agent-runs/:id/steps?messageId=...`: only the steps whose events lie within the reply's range; the cursor and pairing rules of #1821 apply unchanged inside that range.
- The reply's display status uses the same derivation as the run (#1820): `error` when the reply failed (a failed reply status or an error step), `waiting_approval` while one of its requests is pending, `done` otherwise; a retried reply (several attempts with the same `reply_to`) shows the latest attempt, which the summary labels as "on the second attempt".

Rules:

- The message must be an assistant message of run `:id` in the caller's tenant; otherwise the response is 404 (a message of another run, another tenant or an unknown id are indistinguishable).
- Without `messageId`, behavior is exactly today's whole-run behavior.
- After events were deleted by retention, the stored summary on the message survives; `steps?messageId=` then answers with `truncatedHistory: true` and the steps that remain.
- No separate usage route is introduced; usage is a field of the scoped detail.
- For a heartbeat tick (one message per run) the whole run applies and `messageId` is accepted but selects the same data.

Shared-file ordering: this issue also waits for #1876 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `io-hardening`, `error-handling` and `testing`.

1. Add `messageId` parsing and validation (uuid) to the detail and steps routes in `agentRunHandler.ts`, and a resolver that loads the message with its range and verifies it is an assistant message of the run in the caller's tenant (404 otherwise).
2. Scope the detail: title, start, duration, approvals (through the tool call link, constrained to the event range) and usage (through `semp_message_id`), reusing the functions from #1805 and #1822 with the additional filters rather than copying their queries.
3. Scope the steps to the reply's event range and return `truncatedHistory: true` when the range's events were removed by retention while the message's stored summary remains.
4. Apply the display status rules from #1820 (shared function) to the reply.
5. Tests with a session run containing two replies: the detail, steps and usage of reply A never include reply B's approvals, steps or calls; a message of another run returns 404; a message in another tenant returns 404; a run without the parameter returns the whole run; a pending approval of reply B does not make reply A `waiting_approval`; a retried reply returns the latest attempt.

## Scope

### In scope

- The `messageId` parameter on the run detail and the steps, with the scoped title, duration, approvals, usage, steps and display status, and its 404 and retention behavior.

### Out of scope

- Creating the message table, the step summary, the tool call link on approvals and the gateway attribution: #1367, #1860, #1618, #1744.
- The run-level spend aggregation itself: #1822.
- Retrying or regenerating a reply: #1926, #1930.
- Counting a reply with an unfinished tool call as failed: #1890.
- Listing chat answers as run rows: #1932, #1936.

## Acceptance criteria

- When a session run holds two replies and the detail is requested with the first reply's `messageId`, then `approvals`, `usage` and `durationMs` describe only that reply, and the title is the text of the user message it answers.
- When the steps are requested with a `messageId`, then only the steps in that reply's event range are returned, with the same pairing and cursor guarantees as the unscoped route.
- When the message belongs to another run or another tenant, or is not an assistant message, then the response is 404.
- When the request has no `messageId`, then the response equals the whole-run response.
- When a pending approval belongs to another reply of the same run, then this reply is not `waiting_approval`.
- When the events of the reply were removed by retention, then the detail still returns the stored summary data and the steps response has `truncatedHistory: true`.
