## Context

Model tier rationale: A wide destructive data change run by a nightly sweep across every tenant: it removes a database's items, edges, schema pieces in other databases (paired relation properties, dependent rollups) and its table partition, in chunked transactions that must resume after an interruption, with blob bytes removed after commit; mistakes here lose user data or leave dangling schema.

Today archiving a database (`DELETE /api/databases/:id`, the approved `database.archive` operation) only sets `databases.archived_at`: it is reversible and has no time limit, and an archived database is never deleted. The product treats archiving as moving the database to the trash, with the same 30 days to restore as an item has, after which it is deleted for good ("Recently deleted", tab Databases). The item sweep in `backend/packages/data/src/trash/purgeExpiredTrash.ts` already purges items 30 days after deletion (`RETENTION_DAYS`, introduced by #1851).

Decision (decided by the product owner): archiving a database is moving it to the trash; it is purged `RETENTION_DAYS` days after archiving. A restore within that time brings back the database with all its items, edges and schema; nothing is lost before the deadline.

This issue records the deadline when a database is archived, deletes the databases whose deadline passed, and shows the real deadline in the archived-databases listing (#1873). Items of archived databases are left to this purge by the item sweep (#1878), and rollups already ignore archived databases (#1359). The sweep follows `docs/adr/2026-10-06-system-work-fans-out-per-tenant.md` (each tenant in its own scope, one tenant's failure does not skip the others) and `docs/adr/2026-09-28-chunked-transactions-for-large-background-sweeps.md`; blob bytes are removed after commit best-effort as in `docs/adr/2026-09-28-blob-bytes-deleted-best-effort-after-the-commit.md`.

Decisions:

- The deadline is stored in a new nullable column `databases.purge_at`, set to now plus `RETENTION_DAYS` days when a database is archived and cleared when it is restored. Archived databases that have no `purge_at` (archived by the previous release before this one, or by a release rolled back to) get `purge_at = now + RETENTION_DAYS` at the start of each sweep run, so a database archived long ago is deleted no earlier than 30 days after the first sweep that sees it, never immediately after the deployment.
- Only user databases are ever purged (`system = false`); a system database cannot be archived.
- The purge is done by the existing daily item-purge sweep task (no new task name): after the items stage of `handleItemTrashPurgeSweepTask`, each tenant's expired databases are purged. A failure of one stage or one database is logged with the tenant and database ids, does not skip the rest, and fails the task at the end so it is retried.
- An inline database owned by an item of the purged database (an item with a page) is purged first, depth first, with the same procedure.
- Stored `computed` values that other items hold for a deleted rollup property are left in place (they are unreachable without the property and cleaned up by nothing else); this is accepted.

## Task

Load `db-migrations`, `state-writes`, `adr-conventions`, `io-hardening`, `error-handling` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_databases_purge_at.sql (next free ordinal at commit time)`: `ALTER TABLE databases ADD COLUMN purge_at timestamptz` and a partial index on `(purge_at) WHERE purge_at IS NOT NULL`. DDL only; additive and rollback-safe (the previous release ignores the column).
2. `databasesStore.ts`/`types.ts`: add `purgeAt` to `DatabaseRow` and the column list; `archiveDatabase` sets `purge_at = now() + RETENTION_DAYS days` together with `archived_at`; `restoreDatabase` clears it. The REST database envelope is unchanged.
3. Add `backend/packages/data/src/trash/purgeArchivedDatabases.ts` exporting `purgeExpiredArchivedDatabases(pool, storage)` for the current tenant scope: (a) assign missing deadlines as described; (b) select user databases with `archived_at IS NOT NULL` and `purge_at < now()`; (c) for each, in this order, each step its own transaction or chunk and idempotent so an interrupted run continues the next day: delete the database's items (including deleted ones) in chunks of at most 500 with `deleteItemDependents` for each (their edges to other databases, views membership, docs, search index rows, automation state, blobs), first purging inline databases owned by those items; after each commit remove the collected blob bytes from `storage` best-effort; when no item is left, in one final transaction delete the rollup properties in other databases that depend on a relation of this database (and their dependency rows), delete the paired relation property in the other database for every relation property of this database (and for each the relation definition goes with the property by foreign key), then `dropDatabaseWithPartition`; announce a schema change for every other database whose schema changed and for the dropped database after commit. Document in the file why the paired properties of a schema-locked system database may be removed here (they belong to a relation whose other side is being deleted).
4. Wire it into `handleItemTrashPurgeSweepTask` after `purgeExpiredTrash` for each tenant, aggregating errors as described; export from the package index.
5. Change `GET /api/trash/databases` (#1873) to return `purgeAt` from the column and `daysLeft` by the rule of #1851, with the response for a database without a deadline staying `null`.
6. ADR: add `docs/adr/<date it is written>-archived-databases-are-purged-after-the-trash-retention-period.md` (standalone; reference `[[2026-09-28-chunked-transactions-for-large-background-sweeps]]` and `[[2026-10-06-system-work-fans-out-per-tenant]]`): archiving a database is moving it to the trash with the item retention, the deadline column and the self-healing assignment, the purge order and what it removes in other databases, and that restore before the deadline loses nothing.
7. Tests in `backend/packages/data/src/trash/__tests__/purgeArchivedDatabases.test.ts`: a database archived 31 days ago after the deployment disappears with its items, edges, paired inverse properties in another database, dependent rollups and blobs; one archived 29 days ago stays; one archived before the deployment (no deadline) is deleted no earlier than 30 days after the sweep first saw it; an interrupted run (failure after one chunk) resumes and completes; a restore before the deadline clears it; another tenant's databases are untouched; a system database is never selected; blob byte removal failure does not fail the sweep.

## Scope

### In scope

- The purge deadline, the sweep that deletes expired archived databases with everything that hangs on them, and the real deadline in the archived-databases listing.

### Out of scope

- Skipping items of archived databases in the item sweep: #1878.
- Excluding archived databases from rollups: #1359.
- Texts that tell the user an archived database is deleted after 30 days (web and the approval card): client work.
- A manual "delete now" for a database: not planned yet; it waits for a product decision.

## Acceptance criteria

- A database archived 31 days ago (after this change is deployed) is gone after the sweep, with its items, relations to other databases, the paired relation properties in other databases, dependent rollups and its blobs; one archived 29 days ago is still there and restorable.
- A database archived before the deployment is deleted no sooner than 30 days after the first sweep that saw it.
- An interrupted purge resumes on the next run without leaving dangling schema.
- Restoring an archived database clears its deadline; the listing shows the real deadline and days left.
- Other tenants' databases and every system database are untouched.
