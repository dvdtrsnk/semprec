## Context

Model tier rationale: One transaction that combines existing, already guarded writes (the `speakers` edge with its validation hook, a proposal status settle) behind a new route, plus one read route; the care points are the single-person-per-key rules and the edge-then-card ordering, both covered by existing tests of `transcriptionSpeakerEdges.ts`.

A transcript's speakers are anonymous keys (`SPEAKER_00`, ...) that a user maps to people. Today a client maps one through the generic relation endpoint `PUT /api/items/<transcriptId>/relations/speakers/<personId>` with `{ metadata: { speaker } }`. The choke point validates the edge (`assertSpeakerEdgeWritable` in `backend/packages/data/src/transcription/transcriptionSpeakerEdges.ts`: metadata exactly `{ speaker }`, the key must occur in the transcript, no other person may already hold the key), but replacing the person of a key takes two client calls (remove the old edge, add the new one), the write does not settle the Inbox card that asks "who is this speaker" (`transcript-speaker-suggestion:<transcriptId>:<speaker>`), and a client has no way to list the people it could offer: `Events.people` is one-directional and item responses do not include relations.

This issue adds two routes of the systemDatabases module next to the transcript routes it builds on (#1576 owns the manifest and the transcript detail read): `PUT /api/transcripts/:id/speakers/:speaker` assigns, replaces or clears a speaker's person atomically and settles the card, and `GET /api/transcripts/:id/speaker-candidates` returns the people a client can offer. It uses the tenant's own person (#1509), the invitation state on Event participant edges (#1757), and the relation-edge realtime invalidation of #1621 (the edge write publishes it, so other devices refresh).

Decisions:

- By the product owner: the people offered for a speaker are the named participants of the transcript's Event and the user's own person; a person already mapped to a speaker is not offered. The candidates endpoint returns every participant, each with its invitation state and the speaker key it is already mapped to, so the client can hide mapped people; the server applies no invitation filter.
- A person already mapped to another key is refused with `400 validation_failed` and reason `personAlreadyMapped`; nothing is moved silently.
- The response carries `title: null` and the existing `relationship` of the person. By the product owner: no job-title property is added to People in v1, so `title` stays empty.
- By the product owner: a confirmed assignment adds the person to the participants of the transcript's linked Event when they are not among them yet (as the confirm of a speaker card does, #1671). Replacing or clearing an assignment never removes anyone from the Event's participants.
- The organizer of the Event is the tenant's own person and is returned separately as `self`, not in `participants`.

Shared-file ordering: this issue also waits for #1767 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `io-hardening` and `testing`.

1. `PUT /api/transcripts/:id/speakers/:speaker` with body `{ personId: uuid | null }` (custom route of the systemDatabases module, justification `transactional-semantics`). In one transaction: row-lock the transcript; require that `:speaker` occurs in the transcript (`400 validation_failed`, reason `unknownSpeaker`); require, for a non-null `personId`, a live People item; reject a person mapped to a different key with reason `personAlreadyMapped` (include the key they hold); delete the existing `speakers` edge of this key if it points to another person (or `null`); write the new edge with metadata `{ speaker }` through the choke point's relation write (so the existing validation runs); for a non-null `personId`, when the transcript has a live linked Event (Transcripts `event`) and the person has no `Events.people` edge to it, create that edge through `createRelationWithClient` as the requesting user (no system relation context), and never delete an `Events.people` edge when a person is replaced or cleared; settle the open card with idempotency key `transcript-speaker-suggestion:<transcriptId>:<speaker>` if it is `proposed` or `needsClarification`: `confirmed` (with the person as result) when its stored proposal is exactly this person for this key, otherwise `rejected`, with a history entry saying it was settled by a manual assignment. Setting the same person again is a no-op success. Respond `200 { speaker, label, personId }` with the label as `GET /api/transcripts/:id/speakers` would show it. A malformed id is `400`; an unknown or foreign transcript or person is the identical `404`.
2. Add a card-settling function to the proposal actions (`backend/packages/data/src/inbox/proposalActions.ts`) used by the route, locking the card and refusing to touch a locked one.
3. `GET /api/transcripts/:id/speaker-candidates` (justification `single-consumer-read`) returning `{ participants: [{ personId, name, title, relationship, invitationStatus, mappedSpeaker }], self: { personId, name, mappedSpeaker } | null }`: `participants` are the people on the `people` edges of the Event linked to the transcript, in the order of the edges, without the tenant's own person; `invitationStatus` is the status from the edge metadata of #1757 or `null` when the person was linked without an invitation; `mappedSpeaker` is the key the person is mapped to in this transcript or `null`; `title` is always `null`; `self` is the tenant's own person (#1509) or `null` when not set. A transcript without an Event returns no participants but still the own person. Choosing "from People" stays a client query over People that omits the own person.
4. Register both routes in `systemDatabasesModuleManifest.ts` (with the handlers re-exported in its export block), `routeMatrix.ts`, `tenantIsolationRoutes.test.ts` (case table and request list) and the handler mapping of `chokePointWriteBoundary.unit.test.ts`.
5. Tests: assigning an unmapped key makes the detail endpoint (#1576) show the person's name and closes the card; the assigned person becomes a participant of the linked Event, a person already among the participants gets no second edge, and a transcript without an Event writes no participant; replacing a person and clearing leave the Event's participants unchanged; the same person twice; a person mapped to another key (400, nothing changed); unknown key; the card being settled `rejected` when it proposed someone else; a locked card untouched; a second device receives the edge invalidation; candidates for an Event with an invited, a linked-only and an already mapped participant; foreign and unknown ids identical.

## Scope

### In scope

- The atomic assign/replace/clear route with card settling, and the candidates read.

### Out of scope

- Creating the cards for unmapped speakers and their context: #1640.
- Adding the chosen person to the Event's participants when a speaker card is confirmed: #1671 (this issue does it for the manual assignment).
- Roles and invitation states on Event participant edges: #1757.
- The relationship catalog used by the "new person" choice: #1549.
- Letting one person hold two speaker keys.

## Acceptance criteria

- When an unmapped speaker is assigned to a person, one call writes the edge, the transcript detail shows the person's name for that speaker, the speaker card is closed, and another signed-in device receives an invalidation.
- When the person is already mapped to another key, the response is `400 validation_failed` with reason `personAlreadyMapped` and nothing changes.
- When the key is cleared with `personId: null`, the mapping edge is gone and the speaker shows as unmapped again.
- When a speaker of a transcript linked to an Event is assigned to a person who is not a participant, that person is a participant of the Event afterwards; when the assignment is later replaced or cleared, the person stays a participant.
- The candidates read returns each participant with invitation status and mapped key, the own person as `self`, and no organizer in `participants`.
- A foreign tenant's transcript answers exactly like an unknown one.
