## Context

Model tier rationale: It adds a write-side invariant on an edge that clients, the tick and type deletion all touch, and it must serialize against a concurrent confirm or reject of the card, so the locking and the delete path are easy to get subtly wrong.

An Inbox item points at its type through the user-owned `type` relation (`backend/packages/data/src/seed/seedInboxPipeline.ts`, `many_to_many` without an inverse). Nothing limits it: a client can add a second `type` edge, and can change or remove the type after the item's card was confirmed or rejected, which would make a settled card's history lie about what the item was. The rule wanted: an item has at most one type; once its card is `confirmed` or `rejected` the type is frozen. Deleting a type already skips locked items (`deleteInboxTypeWithClient` in `backend/packages/data/src/inbox/inboxTypesStore.ts`), and the locked statuses are the set `LOCKED_PROPOSAL_STATUSES` in the same file.

Edge validation hooks (`registerRelationEdgeWriteHook` in `backend/packages/data/src/chokePoint/hooks.ts`) run before an edge create or replace but not on a delete. #1530 adds a hook that runs after edge writes and deletes inside the same transaction, so a rejection there rolls the delete back. The error code for a locked card, `proposal_locked`, is introduced by #1620 (HTTP 409). Changing a type through a dedicated route and recomputing the card is built on top of this rule (#1947) and the re-run of the tick when the type edge changes is #1718.

Decision: the second-edge rejection uses the existing `cardinality_violation` (409) because the problem is the relation's cardinality, while a frozen type uses `proposal_locked` (409).

Decision: a card counts as locking only when it is live (not trashed) and has status `confirmed` or `rejected`. An item with no card, or with a card in any other status, can change its type.

Decision: the hook inspects the card under a row lock (`SELECT ... FOR UPDATE` through `itemsStore.lockItemById`), so a confirm or reject that is committing at the same time is either seen as committed or makes the type change wait; a type change can never slip in between a confirm's status check and its commit unnoticed.

Shared-file ordering: this issue also waits for #1666 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling` and `testing`.

1. Add `backend/packages/data/src/inbox/inboxTypeLockHook.ts` with two hooks scoped to the relation property `type` of the Inbox database (nothing else): (a) a pre-write hook registered with `registerRelationEdgeWriteHook`, which rejects creating a second `type` edge for an item (`cardinality_violation`) and rejects creating or replacing a `type` edge when the item's card is locked (`proposal_locked`); (b) a post-change hook registered through the mechanism of #1530 that rejects a deleted or replaced `type` edge when the item's card is locked, which rolls the delete back.
2. Find the item's card the way `findExistingProposal` does (the `sourceInbox` edge from Processing proposals, scanning every edge for a live card), read its status under the row lock, and compare with `LOCKED_PROPOSAL_STATUSES`.
3. Register both hooks in `backend/packages/data/src/domainWriteHooks.ts`.
4. Keep `deleteInboxTypeWithClient` working: it already skips locked items, so deleting a type must still succeed and leave locked items pointing at it.
5. Tests: a second `type` edge is 409 `cardinality_violation`; changing or deleting the edge of an item whose card is `confirmed` or `rejected` is 409 `proposal_locked` and leaves the edge; the same on an item with an open card or no card succeeds; a trashed locked card does not lock; deleting a type that locked items point at still works; a confirm racing a type change (two transactions) ends with either the change applied before the confirm or the change rejected, never a changed type under a confirmed card.

## Scope

### In scope

- The single-type and frozen-type rules on the Inbox `type` edge for every writer, with tests.

### Out of scope

- The route that replaces an item's type and recomputes the card (#1947) and re-running the tick on a type change (#1718).
- The `proposal_locked` error code itself (#1620) and the edge-changed hook mechanism (#1530).
- Locking any other Inbox property.

## Acceptance criteria

- When an item already has a `type` edge and a second one is added, then the response is 409 `cardinality_violation`.
- When the item's card is `confirmed` or `rejected` and its type edge is changed or removed, then the response is 409 `proposal_locked` and the edge is unchanged.
- When the card is open or absent, then the type can be changed.
- Deleting an Inbox item type still succeeds and leaves locked items' edges in place.
