**Blocked by:** #1418
**Model tier:** medium

## Context

Model tier rationale: One additive field on an existing response, computed by a function delivered by a blocker, with a small cache and invalidation concern.

Clients need the tenant's time zone and the current calendar day in that zone to open the Journal on today, to stamp the date and time of a captured Inbox item from the device clock, and to detect device clock drift. The zone is the `timezone` property on the single item of the System settings database (`backend/packages/data/src/systemSettings.ts`, `getSystemTimezone`, default `Europe/Prague`); a `PATCH` validates it and triggers `recomputeAllForTimezoneChange`. A client can read it through the generic REST surface today, but there is no dedicated field and no server-side "today". `GET /api/schema` (`backend/services/semprec-api/src/schemaHandler.ts`, `backend/packages/data/src/manifest/schemaProjection.ts`) computes its projection on every request.

#1418 adds the calendar time module whose `today()` is the one computation of "today" in the tenant zone, shared with the calendar timeline.

Decision: the field is added to the schema projection only additively (ADR `docs/adr/2026-09-11-additive-only-rest-contract-no-url-versioning.md`); no existing field changes. The client caches the zone and computes the capture date and time from its own clock in that zone, so `today` is only a drift check on connect and is stale the next day.

## Task

Load `testing` and `canonical-keys`.

1. Extend the schema projection with `tenant: { timezone: string, today: "YYYY-MM-DD" }`: `timezone` from `getSystemTimezone`, `today` from the calendar time module's `today()` in that zone, read inside the same transaction as the rest of the projection.
2. Return it from `GET /api/schema` without changing any existing field or the locale handling.
3. Update the projection type and the schema response tests: the field is present, uses the tenant zone, and reflects a zone change made through the System settings item right after the change (the projection is computed per request, so no cache is added on the server).
4. Test with a controllable clock around local midnight so that `today` differs between the tenant zone and UTC.

## Scope

### In scope

- The additive `tenant.timezone` and `tenant.today` fields of `GET /api/schema`.

### Out of scope

- The calendar time module itself; #1418.
- Pinning the database session time zone; #1596.
- Period key parsing and description; #1431.
- Client-side caching and refetch after a zone change, which are client concerns.

## Acceptance criteria

- When `GET /api/schema` is called for a tenant with zone Europe/Prague, then `tenant.timezone` is `Europe/Prague` and `tenant.today` is the current date in that zone.
- When the zone setting is changed and the schema is requested again, then the new zone and the matching `today` are returned.
- When the response is compared with the one before this change, then every existing field is unchanged.
