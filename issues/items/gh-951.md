## Behavior specification (approved)

Part of the multi-tenancy program specified in #950 (program behaviors and the full decision log live there). This epic makes **every code path run inside an explicit tenant or system scope**, so that row-level security sees the right tenant everywhere:

1. A tenant scope primitive (`runInTenant`, `runAsSystem`, `currentTenantScope`) is applied by `withTransaction` and by every pool checkout; scope-less work is logged (`warn`) until the strict switch makes it an error.
2. Every authenticated HTTP request — adapter routes and every bespoke listener — runs in the caller's tenant; a session whose tenant is not `active` gets the same 401 as a bad token; public routes run in an explicit system scope.
3. Every queued job carries the tenant of the code that enqueued it and runs in it; jobs of inactive tenants complete without doing anything.
4. Every background sweep (heartbeats, docs, trash, retention, credential expiry, mail sync, mail search reindex, observability) runs per active tenant; mail module database ids are resolved per job, never once at process start; mail live sync hosts each tenant's mailboxes in that tenant.
5. The agents and transcribe processes run each job in its tenant; every AI-gateway call carries and is attributed to its tenant.
6. MCP run credentials resolve to their tenant and are minted only for a project of the caller's tenant.
7. Graph webhooks and Gmail Pub/Sub messages are routed to the owning tenant through router-owned functions; one Gmail puller dispatches to every matching mailbox.
8. Per-mailbox stall and live-sync staleness checks live in a tenant table; global observability rows and admin alerts carry no tenant content or mailbox ids.

## Decisions

- **AsyncLocalStorage scope rather than an explicit handle on every call?** → ALS, applied in `withTransaction` and the pool. → An explicit handle touches nearly every file and every in-flight issue and still needs a runtime guard; ALS risks are contained by starting long-lived loops in `runAsSystem` and re-entering a tenant explicitly per job or message.
- **How do sweeps reach every tenant without a bypassing role?** → `forEachActiveTenant` enumerates tenants and runs the existing work inside each; one tenant's failure does not skip the others and is rethrown so the job retries.
- **How are external identifiers routed?** → `SECURITY DEFINER` functions owned by the NOLOGIN `semprec_router` role, returning only `(tenant_id, id)`.
- **Who may set the job envelope's tenant?** → Only `enqueueJob`, from the current scope. → A producer-supplied tenant would be a forgery path.

## Out of scope

Re-keying identities and singletons (#952), realtime delivery (#953), AI budgets (#955), the strict switch (#960).
