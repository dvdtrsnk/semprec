## Behavior specification

Mail threads: fixes, attachments, stable ids, thread API, filters, search and actions.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: mail-threads-1

#### Adopted from open questions
- Should removing an address from a person delete the sender/recipient edges already created? -> No; the jobs only add links -> conservative, no destructive behavior. -> Decided by the product owner: the edges are not removed; removal is deferred (#1571).
- Sent message threading timing -> computed at claim time in `sendDraftEmail`, never recomputed; older data repaired by the backfill -> keeps the send path cheap and the repair in one place.
- Cross-mailbox thread merge target -> a same-`message_id` row in another mailbox wins; when several differ, lowest thread id -> deterministic.
- Backfill of read state on drafts/sent -> goes through `convergeObservedEmailFlagsWithClient` (skip desired-state recording) so no provider write-back state is created.
- Read-projection placement -> per-process registry in `chokePoint/hooks.ts`, applied in the common read ops and public write wrappers, not in the data layer's internal `itemsStore` reads.

#### Open questions for the product owner / implementer
- Envelope addresses are stored as received (not lowercased); the person-linking job (#1571) matches via GIN containment plus code confirmation. Whether to normalize stored envelope addresses (or add an address table) instead is open.
- #1461 changes the web unread filter in `web/src/views/mailbox/config.ts` for views not scoped to one folder (a frontend file inside a backend-design note issue); confirm that is wanted there versus only the aggregation issue (#1688).
- Enqueue point for the thread backfill (#1570): described as a fixed-key core task enqueued once at deploy; the exact deploy hook (cutover step vs. startup) is left to the implementer.

#### User-visible behavior of this chunk
Replies sent from Semprec join the conversation they answer, and a message delivered to several of the user's mailboxes shows up as one conversation, including for mail that was already stored (repaired by a per-tenant backfill). One person can now be the sender of many emails, mail sent from Semprec is linked to the people it was sent to and from, and when a person gains an address their older emails from that address get linked. Drafts and sent mail are no longer counted as unread. Attachments downloaded from mail now open correctly regardless of which storage directory holds the bytes, and email bodies are always returned sanitized (no scripts, event attributes or remote images) on every generic read.


### Decisions: mail-threads-2

#### Adopted from open questions
- Design folder names differ (Spam/Koš vs Nevyžádaná pošta/Odstraněná pošta): system folders are named by `specialPurpose` through the i18n catalog, not by provider names -> stable and localizable. -> Decided by the product owner: named by the folder's purpose through the translation catalog (#1689).
- Label order (alphabetical vs provider order): alphabetical by name after the system folders -> provider order is not guaranteed (Gmail). -> Decided by the product owner: alphabetical after the system folders (#1689).
- Count unit: threads, with the same predicates as the thread list (shared predicate module) -> the design note says the counts must equal the list; the design's 3 vs 5 is the product owner's correction.
- Drafts count: `totalCount` counts messages in the folder; `unreadCount` counts threads. -> Decided by the product owner: counts are threads with the same rules as the list; for Drafts the total counts messages and the unread count counts threads (#1688, #1689).
- Unknown/foreign folder or mailbox ids answer 404 identically.
- Thread list before filters/people/Semp land: `project`/`company` are null, `hasSempDraft` false, `participants` = distinct {name,address} over from/to/cc, `flagged` = any counted message flagged.
- Realtime mail frame: ingest wires it for newly created messages only; other writers wire it in their own issues.

#### Open questions for the product owner
- Design fix for the thread list (m2 Karel Zlatý without relationship label, m3 Jana "Rodina" vs closeFriend, "Outlook" vs "Outlook - práce") and the design count mismatch (3 vs 5) remain design-side tasks.
- Exact `participants` shape and cap are not specified by the design.
- #1816 and the realtime chain depend on #1811 and a related issue; the ordering of OutboundFrame edits was taken from the job's dependency data.

#### User-visible behavior of this chunk
Mail is shown as conversations: a list of threads (newest first) with last sender, message count including sent messages, preview, attachment and flag markers, account badges and sender person, and a thread detail with all messages in date order, sanitized bodies, optional remote images and attachments. Merged conversations keep working through their old ids. Mail screens refresh on their own when new mail arrives. The list can be filtered by inbox, flagged, unread, account and folder, and counts for the overview, profile and sidebar (including folders with unread and total counts) match the list. Gmail accounts show only real folders and labels, with a synthetic Archive for archived mail.


### Decisions: mail-threads-3

#### Adopted from open questions
- IMAP account without an Archive folder: fail with 409 `mail_archive_folder_missing` and change nothing (do not create the folder) -> creating folders on a provider is a larger side effect. -> Decided by the product owner: 409 and nothing changes (#1917).
- Restore from Trash/Archive: the draft had no restore (the design had none). -> Decided by the product owner: a thread in Trash or Archive can be restored back to the inbox; everything deleted can be restored and the design will add it. #2033 adds `POST /api/mail/threads/:threadId/restore` (incoming messages back to Inbox, the user's own messages back to Sent), and #1746 accepts the desired purposes `inbox` and `sent` with their provider writes; #1917 no longer excludes restore as a product rule.
- Contradictory search operators: empty result (200), not 400 -> matches the design. -> Decided by the product owner: an empty result (#1639).
- Thread read/flag semantics: read:true sets all incoming messages (all copies), read:false only the last incoming; flag:true flags the last incoming, flag:false clears all messages. -> Decided by the product owner: as stated (#1865, #1893).
- Archive acts on all accounts' messages in the inbox; trash on all messages of the thread; trash of a thread already only in Trash/Junk is 409 `mail_thread_already_trashed`; a mailbox without Trash is 409 `mail_trash_folder_missing` (codes chosen here). -> Decided by the product owner: as stated (#1917).
- Move retries: 5 attempts then `failed` with a reason (the design note says "N attempts").
- Attachment text for the mail reindex job is re-extracted from stored attachment bytes; unreadable files contribute no text and do not fail the job.
- Mail global search group is one entry per thread, representative item is the last message's Emails item. -> Decided by the product owner: one result per thread, represented by its last message (#1864).

#### Open questions for the product owner / implementer
- #1741 reads attachment bytes from the mail attachments storage only; blobs deduplicated into the files storage root may be skipped. #1487's cross-root helper could be used if the maintainers want to add that dependency.
- #1864 depends on the contribution seam of #1842, which does not exist in the repo yet; the exact registration call is unknown.
- #1746/#5 depend on provider transports (#1505-6) that do not exist yet; interface names in the Touches (providerTypes.ts) are guesses.
- Graph move returns a new message id; whether to switch the client to immutable ids instead was not decided.

#### User-visible behavior of this chunk
Searching mail finds conversations by sender name or address, subject, body text and PDF/DOCX attachment text, with word prefixes and accent-insensitive matching, with the operators is:unread/read/flagged, has:attachment and from:, combined with the other filters; contradictory operators give an empty list. Existing mail is reindexed per tenant without losing attachment text, and mail appears as a group in global search. Marking a conversation read/unread and flagging it works at conversation level and reaches the mail provider promptly; archiving and deleting move the whole conversation (in every account) locally and at the provider (IMAP, Gmail, Microsoft), never permanently deleting, an archived or deleted conversation can be restored to the inbox the same way, and each action refreshes the mail screens through one realtime invalidation.
