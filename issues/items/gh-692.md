## Context

`agent_run_events` (`backend/packages/data/src/db/migrations/0015_agent_run_events.sql`) receives one row per `turn_start`/`message`/`tool_use`/`tool_result`/`turn_end`/`run_status` for every agent run and a `compaction` checkpoint row (`0016_agent_run_events_compaction_kind.sql`) whenever a dormant conversation is compacted on wake. Nothing deletes from it: there is no retention task in `CORE_CRONTAB` (`backend/packages/data/src/worker.ts:78-86`), unlike `doc_history_updates` (`docHistoryCleanup`, `backend/packages/data/src/docs/docHistory.ts`, 30-day `DEFAULT_DOC_HISTORY_RETENTION_DAYS`) and trashed items (`itemTrashPurgeSweep`). A long-lived Semp or delegated conversation keeps every message of its lifetime even though reconstruction (`backend/packages/agent-runtime/src/conversationReconstruction.ts`, `walkStoredEntries`) resets to the latest `compaction` payload and never uses anything before it — those rows are only ever read back by the run-page transcript.

#643 adds the hourly `mcpRunCredentialExpirySweep` core task and edits the same `CORE_TASK_NAMES`/`CORE_TASK_AFFINITY`/`CORE_CRONTAB`/`createCoreTaskList` regions and the API runtime's crontab test; #641 adds export lines to `backend/packages/data/src/index.ts`, the barrel this issue also extends. This issue lands after both. Sibling issue D3 of this batch bounds the reconstruction read to the same checkpoint; the two are independent (the current walk already discards pre-checkpoint rows, so deleting them is safe either way).

## Task

1. **Task name and affinity.** In `backend/packages/queue/src/index.ts` add `AGENT_RUN_EVENTS_RETENTION: "agentRunEventsRetention"` to `CORE_TASK_NAMES` (with a one-line comment naming this issue's purpose) and `[CORE_TASK_NAMES.AGENT_RUN_EVENTS_RETENTION]: "api"` to `CORE_TASK_AFFINITY`. Extend `backend/packages/queue/src/__tests__/taskAffinity.unit.test.ts` wherever it enumerates the api set.
2. **Retention module** — new file `backend/packages/data/src/agentRuns/agentRunEventsRetention.ts` exporting:
   - `AGENT_RUN_EVENTS_RETENTION_DAYS = 30` (documented: rows older than this that precede their conversation's latest `compaction` checkpoint are deleted; the checkpoint itself and everything after it are kept, so reconstruction is unaffected and a run-page transcript older than 30 days may show only its post-checkpoint tail).
   - `handleAgentRunEventsRetentionTask(pool: Pool): Promise<{ deleted: number }>`:
     1. `SELECT r.project_item_id, r.triggered_by, r.parent_run_id, max(e.id) AS compaction_id FROM agent_run_events e JOIN agent_runs r ON r.id = e.agent_run_id WHERE e.kind = 'compaction' AND r.unit = 'session' GROUP BY 1, 2, 3` — one row per conversation that has ever compacted.
     2. For each conversation, loop: `DELETE FROM agent_run_events WHERE id IN (SELECT e.id FROM agent_run_events e JOIN agent_runs r ON r.id = e.agent_run_id WHERE r.unit = 'session' AND r.status <> 'running' AND r.project_item_id IS NOT DISTINCT FROM $1 AND r.triggered_by = $2 AND r.parent_run_id IS NOT DISTINCT FROM $3 AND e.id < $4 AND e.at < now() - make_interval(days => $5) ORDER BY e.id LIMIT $6)` with `$6 = RETENTION_DELETE_BATCH_SIZE` (module-private, 1 000), each batch in its own `withTransaction`, until a batch deletes fewer than the batch size. Sum `rowCount` into `deleted`.
     3. Docstring: batches keep each transaction and lock footprint small (the same reason `docHistoryCleanup` re-baselines per doc); the `r.status <> 'running'` guard never touches a live run; a `compaction` row is never deleted because `e.id < compaction_id` excludes the latest one and an older checkpoint is superseded by it.
3. **Wire it.** In `backend/packages/data/src/worker.ts`: add `20 4 * * * ${CORE_TASK_NAMES.AGENT_RUN_EVENTS_RETENTION}` to `CORE_CRONTAB` (after the `TRASH_PURGE` line) and `[CORE_TASK_NAMES.AGENT_RUN_EVENTS_RETENTION]: async () => { await handleAgentRunEventsRetentionTask(pool); }` to `createCoreTaskList`'s `handlers` (import from `./agentRuns/agentRunEventsRetention.js`). `createApiCoreTaskList` inherits it. In `backend/packages/data/src/index.ts` add `export { AGENT_RUN_EVENTS_RETENTION_DAYS, handleAgentRunEventsRetentionTask } from "./agentRuns/agentRunEventsRetention.js";` directly below the `./agentRuns/agentRunEventsStore.js` export line (line 118); add both names to `publicSurface.test.ts`'s `EXPECTED_RUNTIME_EXPORTS`. In `backend/services/semprec-api/src/__tests__/queueRuntime.test.ts` add `agentRunEventsRetention` to `EXPECTED_CRONTAB_IDENTIFIERS` (the constant #643 extends with its own entry).
4. **Tests** — new `backend/packages/data/src/__tests__/agentRunEventsRetention.test.ts` (integration): one conversation with three session runs and a `compaction` on run 2; set `at = now() - interval '40 days'` on every event of runs 1-2 and leave run 3 recent → after the task, run 1's rows and run 2's rows with `id < compaction id` are gone, the compaction row and run 2's later rows and all of run 3's rows remain; `deleted` equals the number removed. A second conversation without any compaction and 40-day-old rows → untouched. A conversation whose latest run is still `running` with old pre-checkpoint rows → the running run's rows are kept, older finished runs' rows are deleted. Rows younger than 30 days before the checkpoint → kept. Batch size: with 2 500 deletable rows the task runs 3 batches (count `connect()` on a pool wrapper) and deletes all of them.

## Scope

### In scope
- The daily `agentRunEventsRetention` core task, its constant, wiring and tests.

### Out of scope
- Bounding the reconstruction read (sibling issue D3).
- Deleting events of conversations that never compacted, or of `invocation`/heartbeat runs (not covered by the audit finding; they hold one run's worth of events each).
- Deleting `agent_runs` rows, or adding an index on `agent_run_events.at` (the delete is driven by `(agent_run_id, id)` through the existing index).
- Making the retention window configurable through an environment variable.

## Acceptance criteria

- When the `agentRunEventsRetention` task runs, every `agent_run_events` row that is older than 30 days, belongs to a finished `unit='session'` run, and has an id lower than its conversation's latest `compaction` row is deleted, and every other row is kept.
- When a conversation has no `compaction` row, none of its events are deleted.
- The task's crontab entry (`20 4 * * *`) is present in `CORE_CRONTAB`, the task has api affinity, and `createApiQueueRuntime`'s crontab test lists it.
- Deletions happen in batches of at most 1 000 rows per transaction.
