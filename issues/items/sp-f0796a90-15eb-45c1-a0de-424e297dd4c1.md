## Context

Model tier rationale: Changes how one mail sync pass serves the triggers that arrive while it holds the pass lease, which interacts with the single-flight lease, the rerun flag, the move phase and the connection limiter.

End-to-end test of the dev server against a real Purelymail account (F27): new inbound mail became visible 4.4–15.8 s after arrival; Purelymail RTT ~100 ms, connect and login ~0.5 s; passes median 2.4 s, p90 6.9 s, max 11.5 s.

Trace of the path (`mail/imapIdleLifecycle.ts`, `mail/mailSyncJob.ts`, `mail/mailAccountSyncStateStore.ts`): the IDLE signal enqueues `mailAccountSync` at once; when a pass runs, the new job claims, finds the lease held, sets `pass_rerun_requested` and ends; the running pass's release enqueues the follow-up job in the release transaction. So the claim in the finding is right in substance, but the follow-up is not on a later schedule: it is enqueued at release. What a message that arrives during a pass waits for is the rest of that pass plus a whole new job: queue pickup behind every job enqueued earlier (the ingest's heartbeat, reindex and value-link fan-out jobs share the worker's concurrency of 4 and priority 0), the prologue, claim, credential decrypt and move baseline transactions, and a new IMAP connection (TLS, LOGIN, capabilities, ENABLE) before the folder list. Reproduced with the fake IMAP account, 80 ms per command and a 500 ms connect: the message was visible ~1.2 s after the running pass resumed, over a second connection.

Decisions:

- An IMAP pass that completed takes a rerun request in its final transaction (`takeMailSyncRerunRequest`: clears `pass_rerun_requested` only for the lease holder and says whether it was set) and runs another round itself: the pending moves and the move baseline read anew, the move phase when there is a drainable IMAP move, then `reconcileImapAccount` on the pass's open IMAP connection, under the same lease and in the same limiter slot.
- At most `IMAP_PASS_MAX_ROUNDS` (3) rounds per job; a request made during the last round stays set, and the release enqueues the one follow-up job as before, so a busy mailbox does not keep a worker slot for good. An unfinished backfill keeps its release-enqueued follow-up.
- A later round hands the pass's open connection to the move phase, which owns and closes it, and reconnects afterwards; the slot never holds two connections.
- A round writes `syncStatus` only when it changes, so the rounds of one pass make one Mailboxes item update.
- Gmail and Graph passes keep the release-enqueued follow-up.
- A trigger whose claim waits for the final transaction's row lock sees the lease still held, sets the flag after the take, and the release enqueues its follow-up: no trigger is lost and no second pass runs beside the first.

## Scope

### In scope

- In-pass rounds for IMAP passes, their bound and the connection handover to the move phase.

### Out of scope

- Gmail and Graph passes.
- Job priorities or a dedicated queue for mail sync jobs.
- IDLE signal debouncing and Purelymail's own push timing.
- Any request against a real server.

## Acceptance criteria

- A message delivered while a pass runs is imported by that pass's next round: one IMAP connection for the whole job, no follow-up job, and the round selects only INBOX; with 80 ms per command and a 500 ms connect it is visible well under 2 s after the delivery.
- Triggers during the first and second rounds are each served by one more round over the same connection; a trigger during the third round leaves exactly one keyed follow-up job, which opens the job's second connection; never two passes or two connections at once.
- An archive asked for during a pass is moved on the server by the pass's next round.
- The existing single-flight, mail sync, quiet-pass, move sync, stall and live-sync tests stay green.
