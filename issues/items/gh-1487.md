## Context

Model tier rationale: One storage-lookup mechanism shared by the download endpoint and the tenant export, with a defined error contract, but it spans two services and needs the existing export and blob test fixtures.

Downloading a mail attachment fails today. The mail sync worker stores attachment bytes under `MAIL_ATTACHMENTS_DIR` (`backend/packages/data/src/worker.ts`), but `GET /api/blobs/:id` (`backend/services/semprec-api/src/blobsHandler.ts`) reads only from the root the API is composed with, `FILES_STORAGE_DIR` (`backend/services/semprec-api/src/serve.ts`, passed through `app.ts`).

Uploaded files (`blobs/fileUploadStore.ts`) and attachments (`mail/attachments.ts`) share `findOrCreateBlob`, which deduplicates by content hash, so a blob's bytes can lie in either root; even downloading an uploaded file can fail today. The tenant export already handles this: it tries the root chosen by whether the blob has a `mail_attachments` row and, on `ENOENT`, the other root (`openBlob` in `tenancy/tenantExportJob.ts`, recorded in `docs/adr/2026-10-18-tenant-export-cross-root-blob-lookup.md`). `deploy/README.md` already backs up and restores both directories.

Building outgoing MIME with attachments (#1491) also needs to read attachment bytes and reuses the helper this issue extracts.

## Task

Load `io-hardening` and `testing`.

1. Move `openBlob` and the cross-root logic out of `tenancy/tenantExportJob.ts` into a shared helper in `backend/packages/data/src/blobs/openBlobFromRoots.ts`: `openBlobFromRoots({ primary, alternate, storageKey, range? })` returns an opened readable stream or `null` when neither root has the file. It tries `primary`, and only on `ENOENT` the same key in `alternate`; any other read error is thrown without a second attempt. Support the optional byte range used by the download endpoint.
2. Export the helper and a function that decides the primary root for a blob (the blob has a row in `mail_attachments` for the tenant in scope: mail root; otherwise files root) from `backend/packages/data/src/index.ts`.
3. Make `tenantExportJob.ts` use the helper with unchanged behavior (the existing export tests must pass).
4. Change `createBlobsRequestListener` options to take both roots (`files` and `mailAttachments`); `serve.ts` and `app.ts` build the mail root from `MAIL_ATTACHMENTS_DIR` the same way `worker.ts` does and pass both. Use the helper to open the stream before writing headers: a blob found in neither root answers 404 `not_found`, and any other read error answers 500 `internal_error` with no second attempt.
5. Add tests: an attachment downloads from the mail root, including one synced into the Sent folder; an upload deduplicated with an attachment downloads from whichever root holds it; a non-`ENOENT` error returns 500 and the other root is not opened; a foreign tenant's blob still answers like an unknown one.

6. Use actual Gmail Sent reconciliation/attachment ingest and actual upload dedup in the API tests. A testSupport-only re-export of reconcileGmailAccount and needed Gmail client/message types is allowed; no main-barrel export or copied ingest. Then verify authenticated full/range download and tenant denial. Do not substitute synthetic attachment rows for this production evidence.

## Acceptance criteria

- When a blob's bytes are only in the mail attachments root, then `GET /api/blobs/:id` returns the bytes.
- When a blob uploaded as a file is deduplicated with an attachment and its bytes are only in the other root, then the download still succeeds.
- When reading fails with an error other than `ENOENT`, then the response is 500 and the second root is not tried.
- When neither root has the file, then the response is 404 `not_found`.
- The tenant export produces the same archive as before.
