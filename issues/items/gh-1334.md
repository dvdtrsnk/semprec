## Behavior specification

Notifications: preferences, categories, silent push and app badge.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions: notifications-1

#### Adopted from open questions
- With "only critical", should the summary switch be shown only for "all"? -> The backend keeps one `problems_summary` switch that only changes the interruption level (critical `time-sensitive`/`active`, warning `passive`/`active`); whether to show it only for `all` is a client decision. -> Decided by the product owner: one summary switch; the client shows it with both "only critical" and "all", because it only changes the interruption level.
- Badge "Pending approvals": count all pending requests of the user's runs (not only chat) -> Decided by the product owner: all pending requests of the user's runs, the same count as the approval queue; one source of the count.
- Kind policy shape: severity exists only for problems; approvals, invites, reminders carry no severity.
- `semp_problem` severity is dynamic (read from the notification payload); problem-category source kinds become `push: false` in #1466.
- Missing preferences row = defaults (approvals/invites/reminders on, problemsLevel critical, summary on, badge approvals/invites on, badge inbox off). -> Decided by the product owner: these are the defaults.
- APNs: visible pushes get `apns-push-type: alert`, `apns-priority: 10`, 24 h expiration; collapse id and thread id only for sources with durable identity (Semp problem, approval request, invitation); keys over 64 bytes are hashed.
- Badge-only updates are alert-type pushes with only `aps.badge`, debounced per user for 5 s.
- Silent dismiss is not held by the sleep window and is not recorded in push_deliveries; Web Push gets a dismiss payload and a `tag` on visible messages.
- `GET /api/notifications/resolved` returns at most 500 ids, oldest first.

#### Open questions for the product owner / implementer
- #1828: `openInboxItems` is 0 until the Inbox count of #1823 exists and `pendingInvites` is 0 until invitations exist; #1828 has no dependency on #1823, so someone must wire the real Inbox count (a related issue or a follow-up).
- Resolving notifications on problem resolution and invitation response is wired by #1915 and #1944 (not dependencies of #1463); confirm those issues call `resolveNotificationsBySource`.
- #1466 depends on `raiseProblem` from #1459, which does not exist in the repo yet; its file path is a placeholder in Touches.
- Web Push dismiss payload and service-worker handling are an assumption beyond the design note (it only mentions `tag`).

#### User-visible behavior of this chunk
The user can choose which categories of push may reach them (approvals, calendar invitations, task reminders) and how assistant problems are pushed (off, only critical, all, with or without a scheduled summary), and which counts appear on the app icon badge. A problem sends one push however many failures it has, and a repeated push about the same thing replaces the earlier one. When something is handled (for example an approval decided on the web or another device), its notification disappears: connected clients update immediately, phones receive a silent dismiss, and the app reconciles on open. Approvals and critical problems can break through Focus mode, while less severe problems come quietly. The icon badge shows the sum of the counts the user switched on and updates when they change.
