**Blocked by:** #271, #195

## Context

Issue #195 added the live-sync lifecycle host in `backend/packages/data/src/mail/mailLiveSyncRoot.ts`: `discoverActiveAccounts()` pages through the Mailboxes database and seeds `mail_account_sync_state` for each account, `reconcileOnce()` starts and stops hosted lifecycles to match that active set, and the returned root exposes `start()` / `stop()`, where `start()` first awaits one `reconcileOnce()` and then schedules `reconcileOnce` on a `setInterval` stored in `timer` — a closure variable of `createMailLiveSyncRoot`, so each root instance has its own. A post-merge review of #195's pull request raised two findings that were never addressed; both are still on `develop`.

**1. `start()` is not idempotent.** It assigns `timer = setInterval(...)` unconditionally. A second `start()` overwrites the reference to the first interval before it is cleared, so that first interval leaks: it keeps firing `reconcileOnce()` forever, and a later `stop()` clears only the second timer. Two concurrent discovery loops then race over the same hosted map. Note that `timer` is assigned only *after* the initial `await reconcileOnce()`, so testing `timer` alone does not catch two overlapping `start()` calls that are not awaited in sequence.

**2. N+1 transactions during discovery.** Inside the paging loop, `discoverActiveAccounts` opens a separate `withTransaction` per account item to call `ensureMailAccountSyncState` — one transaction for the `listItems` page plus one per item on that page. It is not a correctness bug, but discovery cost grows linearly with account count for no reason.

## Task

- Guard `start()` against a double call with a **generation counter** captured synchronously at the top of `start()`, before the initial `await reconcileOnce()` — testing `timer` is not enough, because `timer` is only assigned after that await, so two un-awaited `start()` calls would both get past a `timer`-based check. When a run is already active, return immediately without re-running the initial reconcile and without scheduling a second interval. `stop()` clears the interval, unsets `timer`, clears the flag, and stops every hosted lifecycle as it does today, so a `start()` after a `stop()` works normally again.
- Cover the interleavings too: if `stop()` runs while `start()` is still awaiting its initial `reconcileOnce()`, that `start()` must not schedule an interval when it resumes — otherwise it installs a timer nothing holds a reference to, which is the same leak one step over. A plain boolean is not enough, because `start()` → `stop()` → `start()` leaves the flag set again by the time the first call resumes and it would schedule anyway. Compare the generation captured at entry with the current one after the await and return without scheduling when they differ; `stop()` bumps the generation.
- Reduce discovery to one transaction per page: today the page's `listItems` call already runs in its own `withTransaction` and each item's `ensureMailAccountSyncState` opens another, so a page of N accounts costs N+1 transactions. Read the page **and** seed every account of that page inside one single `withTransaction`, so a page costs exactly one. Preserve the existing per-account error isolation exactly — one account whose state fails to read or seed must still be reported through `options.onLifecycleError?.(item.id, "discover", err)`, must not drop the other accounts of that page from the active set, and must not abort discovery. Because a failed statement aborts the whole PostgreSQL transaction, wrap each account's `ensureMailAccountSyncState` call in its own `SAVEPOINT` and `ROLLBACK TO SAVEPOINT` on error inside the shared transaction; that is what keeps one page = one transaction while a single account can still fail on its own.

Add tests in `backend/packages/data/src/__tests__/mailLiveSyncRoot.test.ts`, next to the existing live-sync tests:

- calling `start()` twice — both sequentially and as two un-awaited calls — schedules only one interval, and a single `stop()` afterwards leaves no interval firing;
- calling `stop()` while the initial `reconcileOnce()` of `start()` is still in flight leaves no interval scheduled once that `start()` resolves — including the `start()` → `stop()` → `start()` ordering, where the first call must not schedule an interval belonging to a superseded generation;
- discovering a page of N accounts issues one transaction for that page rather than N+1, while an account whose `ensureMailAccountSyncState` fails is still reported through `onLifecycleError` and the remaining accounts of the page still end up in the active set. `ensureMailAccountSyncState` is a direct module import and its inputs cannot be made to fail through seeded data (the `sync_mode` CHECK constraint blocks planting a bad row), so force the failure at the query layer: wrap the pool passed to `createMailLiveSyncRoot` (a `Proxy` over the real pool, since `createMailLiveSyncRoot` is typed against `pg.Pool` and there is no wrapper precedent in `backend/` to copy) so the seeding statement for one chosen account id is rewritten into a statement the **server** rejects. Sending a genuinely failing statement matters: if the wrapper merely rejects locally without reaching PostgreSQL, the transaction is never aborted server-side and an implementation with no savepoints would pass the test just as well.

## Scope

### In scope

- The double-start guard and the batched discovery in `mailLiveSyncRoot.ts`, plus the tests above.

### Out of scope

- The hosted lifecycle implementations themselves and the `stopHosted` path.
- Anything about read/flagged state write-back, which is a later mail-live-sync issue.

## Acceptance criteria

- Calling `start()` a second time does not create a second interval, and a single `stop()` stops all scheduled discovery.
- After `stop()`, calling `start()` again resumes discovery normally.
- Discovering a page of accounts uses exactly one transaction for that page, covering both the page read and every account's state seeding, and an account whose state seeding fails inside it is still surfaced through `onLifecycleError`, is rolled back to its savepoint, and does not remove the other accounts of that page from the active set.
