**Blocked by:** #223, #103

## Context

Issue #223 implemented the `semprec.tick` handler with fingerprinting, the create/revise/skip gate, the locked-card rule, and the `proposed` status, but deliberately left three gaps: sources without a usable type, sources deleted out from under a proposal, and history entries. This part closes those gaps so that every Inbox source ends in an explicit state — never silence — and validates the generic proposal envelope. #105 builds on the complete status set and history log for confirm, reject, and revise; #106 renders the resulting state in Journal days.

## Task

Extend the `semprec.tick` handler from #223:

- **Missing or deleted type.** When the source item has no `type`, or its `type` references an Inbox item type that no longer exists (the deleted-type path from #102), set the proposal to `status = needsClarification` with no pre-filled `proposal` — creating the row if none exists, or revising an unlocked row. This is the same path for both cases; do not add a special case for deleted references.
- **Deleted source.** When the tick's source item no longer exists and an unlocked proposal references it, set that proposal to `status = invalid`. Locked proposals (`confirmed`/`rejected`) are left untouched, per the rule from #223.
- **All five statuses.** With these additions the handler covers the complete state space `needsClarification | proposed | confirmed | rejected | invalid`; the tick itself only ever assigns `needsClarification`, `proposed`, and `invalid` (`confirmed`/`rejected` are assigned by #105).
- **History.** History entries are `{ author: 'ai' | 'user', message, at }`. Replace the `[]` stub from #223: append an `ai` entry whenever the tick creates or revises a proposal or changes its status, so the `history` property is the chat and decision log.
- **Envelope validation.** Validate the generic `{ entityKind, target, properties }` envelope before storing a `proposed` payload: `entityKind` must be `pageContent` or `database`; for `database`, `target` must be an existing target database id and `properties` must satisfy what that target database requires; for `pageContent`, `target` must be a page id and `properties` must carry the new block content. Validation only inspects the destination's requirements; it never executes the write.

## Scope

### In scope

- `needsClarification` and `invalid` transitions, the deleted-type fallback, history entries, and envelope validation.

### Out of scope

- Fingerprints, the create/revise/skip gate, the locked-card rule, and the `proposed` computation (#223).
- Concrete prompt engineering, confirmation writes (#105), and UI (#106).

## Acceptance criteria

- A source with a missing or deleted type yields a `needsClarification` proposal, never silence, and both cases go through the same code path.
- Deleting a source invalidates only its unlocked proposal; a `confirmed` or `rejected` proposal keeps its status.
- Every create, revise, and status change performed by the tick appends one `{ author: 'ai', message, at }` history entry.
- A `proposed` envelope with a wrong `entityKind`, an unknown target, or properties that do not satisfy the destination is rejected before storage, and validation performs no write to the destination.
