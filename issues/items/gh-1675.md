**Blocked by:** #1674
**Model tier:** medium

## Context

Model tier rationale: One write-path validation reusing the parser from #1608 plus a per-tenant cutover for a schema-locked property, both following existing patterns and fixtures, with no new concurrency or authorization contract.

Some text values are edited by a light editor: the same Markdown editor as a page, without subpages. Their stored value is a Markdown string, never a document. #1608 provides `parseMarkdown(md, { allowPage })`. This issue gives a text property a way to declare that its value is Markdown and makes the write path reject a value the parser refuses, in particular a subpage link line (the stored value of a light property cannot reference a subpage).

Today nothing in the schema says a text value is Markdown: `PROPERTY_TYPES` (`backend/packages/data/src/types.ts`) has `text` and `longText`, property `config` is validated only for select options in `chokePoint/propertiesStore.ts`, and item writes go through `assertWritableProperties` in `chokePoint/itemWrites.ts` (used by both `createItemWithClient` and `updateItemWithClient`) with no per-value type check. The Inbox database's user-owned `text` property (`seed/seedInboxPipeline.ts`) is the first holder: the card text captured in the Inbox. The Inbox databases are `schema_locked`, so an already provisioned tenant gets the new config only through a per-tenant cutover in `runTenantCutoverMigrations` (`db/tenantCutoverMigrations.ts`), modeled on `transcription/transcriptsCatalogCutoverMigration.ts`; a plain SQL migration that inserts or updates rows without a tenant id fails after the strict-tenant migration, so it is not the pattern.

Decisions:

- Decision: the declaration is `config.format = 'markdown'` on a `text` or `longText` property; any other `format` value, or `format` on another property type, is a validation error at property creation and patch.
- Decision: an existing stored value is never rewritten or re-validated by the cutover; validation applies to new writes only.
- Decision: the only property this issue switches on is the Inbox card text. Other light values declare the format themselves at creation: the task description (#1540), the event description (#1416, #1777); the agent guidance sections validate in #1548. Book and movie notes are not switched on: the product owner decided that the Markdown format stays on the Inbox card text for now and is extended only when a concrete need arises; existing values are not rewritten. The area description is a page, not a light value (#1619).

Shared-file ordering: this issue also waits for #1674 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Task

Load `state-writes`, `error-handling`, `db-migrations` and `testing`.

1. In `chokePoint/propertiesStore.ts`, accept `config.format` only as the string `'markdown'` and only on `text` and `longText` properties; reject anything else with `ValidationError` (`field: "config"`).
2. In the item write path (`chokePoint/itemWrites.ts`, used by create and update), for every written property whose config has `format: 'markdown'`: require a string value (or null where the property allows clearing), and run `parseMarkdown(value, { allowPage: false })` from the block model module of #1608. A refusal becomes a `ValidationError` carrying the property key as `field` (HTTP 400).
3. Seed: set `config: { format: 'markdown' }` on the Inbox `text` property in `seed/seedInboxPipeline.ts`.
4. Add a per-tenant cutover `inbox/inboxMarkdownFormatCutoverMigration.ts` that sets `config.format = 'markdown'` on the Inbox `text` property of the tenant, idempotently, no-op when the Inbox database does not exist yet, following the lock/idempotency shape of the transcripts catalog cutover; register it in `runTenantCutoverMigrations`.
5. Tests: a write of a value with a subpage link line to a markdown property returns 400 with the property key; a normal Markdown value and plain text are stored unchanged; a property with `format: 'markdown'` on a `number` property is rejected; the cutover adds the format to an Inbox provisioned before this change and is a no-op the second time.

## Scope

### In scope

- The `config.format = 'markdown'` declaration, its write-time validation without subpage blocks, and switching it on for the Inbox card text (seed and cutover).

### Out of scope

- The parser and serializer: #1608.
- Task and event descriptions declaring the format: #1540, #1416, #1777.
- Project agent guidance sections: #1548.
- Book and movie notes and any other text property: not switched on until a concrete need arises (decided by the product owner).
- Rewriting or migrating existing stored values.
- Client rendering of the property.

## Acceptance criteria

- When an item write sets a markdown-format property to Markdown containing a subpage link line, then the response is 400 and the value is not stored.
- When the value is plain text or valid Markdown without a subpage link, then it is stored exactly as sent.
- When a property is created with `config.format` other than `'markdown'`, or on a type other than `text`/`longText`, then creation fails with 400.
- When the cutover runs on a tenant whose Inbox `text` property has no format, then the property gets `format: 'markdown'`; running it again changes nothing.
- A freshly seeded tenant has the Inbox `text` property with `format: 'markdown'`.
