## Context

Model tier rationale: One new tenant-scoped table following the existing row-level-security and composite-foreign-key templates plus two small store functions; the concurrency risk is bounded by a partial unique index and an upsert, but the table must be right for every later producer.

The Semp status view lists problems that need the user's attention ("Gmail mailbox is not syncing", "Semp did not finish a task") and merges repeated reports of the same problem into one entry ("merged from 4 reports"). Today the backend has only notifications: `notifications` (migrations `0030`, `0035`) have no severity, no category and no resolved state, `mail_sync_error` is written once per sync job, and the dedupe pattern that exists (`publishFinding` and `resolveFindingsNotIn` in `backend/packages/data/src/notifications/findings.ts`, over `manifest_drift_findings.dedupe_key`) is for module drift findings only. `GET /api/system-health` (`backend/packages/data/src/observability/systemHealthReport.ts`) is a technical snapshot with no ids, no dedupe key and no user-facing text.

This issue creates the storage and the two write operations every producer will call. Producers write a problem in the same transaction as the source row, next to `writeNotification`: heartbeat and run failures (#1911), guidance drift, library automation and operator problems (#1465), failed chat replies (#1931, #1931), mailbox sync failures (#1506, #1506) and transcription failures (#1945). Readers: the status API (#1555), recovery (#1915), the history of resolved problems and pruning (#1919, #1558), the services list (#1561), the realtime invalidation (#1868), the push for new problems (#1466) and the budget problem (#1871). A backfill of existing failures is #1958.

Decision: a problem stores no user content. It holds ids, keys, categories and counters; titles and texts are rendered at read time (#1555).

Decision: the push for a new or escalated problem is not sent here. `raiseProblem` returns what happened (`created`, `merged` or `escalated`) so the push issue (#1466) can act on it.

Decision: categories are the closed set `mail`, `agents`, `guidance`, `automation`, `transcription`, `backup`. A `calendar` category is added with calendar subscriptions. A missing or exhausted AI budget is not stored: it is derived when the status is read.

## Task

Load `db-migrations`, `state-writes`, `canonical-keys` and `testing`.

1. Migration `backend/packages/data/src/db/migrations/NNNN_semp_problems.sql` (next free ordinal at commit time): table `semp_problems` with `id uuid` primary key, `tenant_id` defaulting to `app_tenant_default()`, `user_id`, `category`, `kind`, `severity` (`critical` | `warning`, check), `source_table`, `source_id`, `dedupe_key`, `project_item_id` (nullable), `occurrence_count integer NOT NULL DEFAULT 1`, `first_seen_at`, `last_seen_at`, `last_occurrence_key text`, `resolved_at`, `resolution_kind`, with the tenancy comment, row-level security policies and `GRANT`s to the runtime role exactly as `0078_tenant_exports.sql` does, and composite tenant foreign keys as `0083_tenant_composite_foreign_keys.sql` does (to `users (tenant_id, id)` and, for the project item, the same way other tables reference items). Create the partial unique index on (`tenant_id`, `dedupe_key`) `WHERE resolved_at IS NULL`, and an index for listing active problems per tenant. Categories are checked in the database.
2. Add `backend/packages/data/src/semp/sempProblemsStore.ts` with:
   - `raiseProblem(client, { userId, category, kind, severity, sourceTable, sourceId, dedupeKey, projectItemId?, since?, occurrenceKey? })`: one `INSERT ... ON CONFLICT` on the partial unique index. A new problem has `occurrence_count` 1 and `first_seen_at` = `since` or now. A repeated call for an active problem increases `occurrence_count` and sets `last_seen_at`, unless `occurrenceKey` equals the stored `last_occurrence_key` (a replay of the same job or run adds nothing). A higher severity (`warning` -> `critical`) escalates the stored severity; a lower or equal one never changes it. Returns `{ problemId, outcome }` with `outcome` one of `created`, `merged`, `escalated`.
   - `resolveProblem(client, { dedupeKey, resolutionKind })`: sets `resolved_at` and `resolution_kind` on the active problem with that key, if any; idempotent; returns whether a row changed. `resolutionKind` is validated against a TypeScript constant (initially `recovered`); #1915 extends it.
   Both take the caller's open transaction and never open one.
3. Export the store from `backend/packages/data/src/index.ts` and add the table to the list of tenant tables in the tenancy catalog test (`backend/packages/data/src/__tests__/tenancyCatalog.test.ts`).
4. Tests: four raises of one key give one row with `occurrence_count` 4 and the first `first_seen_at`; two concurrent raises give one row; escalation raises severity and a later `warning` does not lower it; the same `occurrenceKey` twice counts once; a rolled-back transaction leaves no row; a resolved problem and a new raise with the same key create a second row; another tenant's problem is neither visible nor merged.

## Scope

### In scope

- The `semp_problems` table with isolation, deduplication, occurrence counting, severity escalation and the two store functions.

### Out of scope

- Any producer (#1911, #1465, #1931, #1506, #1945) and the backfill (#1958).
- Serving problems with text and actions (#1555), resolving on recovery (#1915) and pruning (#1558).
- The push of a new or escalated problem (#1466) and the realtime invalidation (#1868).

## Acceptance criteria

- When the same problem is raised four times, then one row exists with `occurrence_count` 4 and `first_seen_at` of the first raise.
- When a `critical` raise follows a `warning` raise of the same key, then the stored severity is `critical` and the outcome is `escalated`; a later `warning` raise leaves it `critical`.
- When a raise is repeated with the same `occurrenceKey`, then the count does not change.
- When the transaction that raised a problem rolls back, then no problem exists.
- When a problem is resolved and the source fails again, then a new active problem is created.
- When tenant B queries problems, then tenant A's rows are not visible.
