## Behavior specification

Account: sessions and devices, sign-in, password change and profile.

This batch was planned from the reviewed design of the iOS app: every issue below states the backend behavior the app needs that `develop` does not provide yet. The issues are linked as sub-issues; their order follows the dependency graph across all batches, foundations first.

Status: drafts awaiting the `/define-behavior` Phase 5 audit. No issue in this batch carries `spec:approved` or `agent:ready` yet.

## Decisions

Decisions adopted while drafting, and questions still open for the product owner (per chunk of the batch):

### Decisions for job account-1

#### (a) Adopted decisions

- Which device fields can a web login set? -> Ignored; the server derives browser name and OS family from the User-Agent. -> A browser must not be able to label itself as an iPhone; the source note only describes server-side matching for web.
- Length limits for device fields (not specified) -> deviceName 1-100, osVersion and appVersion 1-50, deviceId must be a UUID. -> Conservative, bounded input.
- Session TTLs (open question) -> idle 90 days for ios/macos, 30 days for web, absolute ceiling 365 days from created_at; web cookie Max-Age is the ceiling. -> Values proposed in the source note, lean adopted.
- revoke-others and push registrations without session_id (open question) -> Only registrations of the revoked sessions are revoked; session-less registrations are left alone. -> They are not tied to a signed-out device; password reset already covers the user-wide case.
- Password change vs. reset email (open question) -> Proper change with current and new password (#1701 exists in the plan), keeping the current session. -> Mirrors deleteOwnAccount re-authentication; 403 reauthentication_failed so clients do not treat it as sign-out.
- Universal Link (open question) -> Included as #1357 limited to the association file, Caddy serving and a test; invitation links not claimed. -> The Swift project does not exist yet.
- Locale of invitation email -> Locale of the admin who created it (fallback en). Reset email -> users.locale. -> Taken from the source note; invitee has no account.
- /api/server-info body -> Only {product:"semprec"}, no version. -> ADR additive-only REST contract; public route should leak nothing.
- Same-installation replacement -> Only a non-null deviceId triggers replacement, serialized by a per-(user, deviceId) advisory lock. -> Prevents two concurrent logins leaving two sessions.
- Apple Team ID and bundle id for the association file (#1357) -> Decided by the product owner: the owner supplies them from the Apple Developer account; they belong to the deployment configuration, not hard-coded in the repository. #1357 renders the file at provisioning from deployment configuration values.
- Are the idle/ceiling values (90/30/365 days) final? -> Decided by the product owner: yes, 90/30/365 days are enough for v1; the values stay in the server's configuration and the user does not set them.
- Should the password change also notify the user by email? -> Decided by the product owner: no; v1 sends no system notification emails. The user sees the change in the sessions and devices list.
- Should the invitation link ever open as a Universal Link? -> Decided by the product owner: no; the invitation stays an ordinary link, so there is no special case.

#### (b) Open questions for the product owner

- None remaining.

#### (c) User-visible behavior

Users can see every device they are signed in on (kind, name, client version, last activity, sign-in date) with the current device marked, sign out all other devices in one action, and a reinstalled app replaces its previous sign-in instead of adding a ghost device. Sessions of the native apps stay signed in for months while in use (up to a year), web sessions for 30 idle days. The sign-in screen can confirm that an address really is a Semprec server before login. Password-reset and invitation emails arrive in the user's language (the inviting admin's language for invitations). A signed-in user can change the password by entering the current and a new one: other devices are signed out, this device stays signed in, and older reset links stop working. The reset link from the email can open the iOS app when the app is installed.


### Decisions: account-2

#### (a) Decisions adopted
- Display name visible in GET /api/admin/accounts? -> No -> admin role has no content access ADR; name is profile content. accountsAdminStore.ts untouched.
- Avatar colour (a) client-derived or (b) column? -> (a) client-derived from user id, no column -> no design editing exists; conservative, reversible.
- Is "Jazyk Sempa" also the app language? -> Yes, one setting: users.locale -> it already drives collection names, notifications, speaker labels; no second setting.
- Profile PATCH fields now -> locale only; other keys rejected with 400 -> displayName/avatarColor edit not in the design; keeps later additions additive.
- Reindex on locale change -> only when the stored locale actually changed, via #1652 entry point.
- Transcript summary language -> stays in the transcript's language, untouched.
- displayName validation -> optional, trimmed 1-80 chars, blank string is 400 (not NULL); validated before an invitation is consumed.
- Agent language instruction -> sentence in shared base prompt from users.locale; null locale adds nothing; takes effect from the next run.
- Inbox tick locale -> new `locale` field in ProposalComputationInput, default `cs` when no bound user; existing proposals/fingerprint not invalidated by a locale change.
- /api/account/summary vs /api/overview -> kept separate; both read the same owner function.
- Account export/delete in iOS Profile (App Store 5.1.1(v)) -> backend already done; no work here.
- Time zone row in Profile -> not built; out of scope.
- Should the person be able to edit displayName (and later an avatar colour) after creation? -> Decided by the product owner: name editing comes with the design of the editing screen; the avatar colour is deferred, because v1 should stay lean.
- Should transcript summaries follow users.locale instead of the transcript language? -> Decided by the product owner: no; the summary stays in the transcript's language, so it faithfully matches the meeting and can be shared with its participants.
- Is a separate "assistant language" ever wanted, distinct from the app language? -> Decided by the product owner: no; there is one application language, and another setting would add needless complexity to v1.
- Should the Profile show a time-zone row (per-tenant System settings.timezone)? -> Decided by the product owner: no; the time zone is a tenant setting with one place, the system settings, and the profile does not duplicate it.
- Should existing Inbox proposals be recomputed when the language changes? -> Decided by the product owner: no; behavior stays predictable, nothing is silently rewritten and no AI cost arises. The language applies to new proposals.

#### (b) Open questions remaining for the product owner
- None remaining.

#### (c) User-visible behavior (epic paragraph)
The profile screen can show the person's name (stored at account creation, optional) and the person can switch the application and assistant language between Czech and English with immediate effect on collection names, notifications and search labels; Semp and the Inbox proposals then write in that language from their next run. One lightweight summary call gives the profile its row counts: signed-in devices, e-mail accounts and those needing re-login, recently deleted items and databases, Semp problems and this month's AI spend. Login now also returns the account role, like the session endpoint.
