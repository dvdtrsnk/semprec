## Context

Model tier rationale: Reorders the locks of one job's chunk transaction to match the sync pass and corrects the lock-order statements that were not true.

Found in the local review of PR #2089. A Mail-off chunk of the `mailboxRemoval` job (`lockMailOffEpoch`, `mail/mailboxRemovalJob.ts`) takes the tenant's mail-thread guard and then the paused sync state row `FOR SHARE`; its comment says that is the order a sync pass takes them in. A pass's transaction does the opposite: `enterSyncPass` renews the lease with an `UPDATE` of the sync state row and only then takes the mail-thread guard (`inPassTransaction` in `mail/imapReconcile.ts`; the Gmail and Graph reconcilers likewise). A chunk and a pass of an account whose Mail was switched on again while the job still runs can deadlock. The "Lock orders to keep" list in `docs/architecture/domain-mail-and-inbox.md` also puts the mail-thread guard before the sync state row for the pass, which the code does not do.

Decision: the Mail-off chunk takes the sync state row `FOR SHARE` first, then the mail-thread guard, then the Mailboxes item `FOR SHARE`; the comment and the document state the order the code takes. The pass, the removal route and the send claim already take the sync state row before the mail-thread guard.
