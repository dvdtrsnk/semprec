## Context

Model tier rationale: It adds a new tenant table written outside the invocation transaction by two processes, so row-level security, role grants, secret-free error recording and failure isolation of the main call all have to be right.

The server item's `active` is an on/off switch; `syncMcpServerTools` (`mcp/mcpSync.ts`) owns `syncStatus`, `lastSynced` and `syncError` under `2026-09-10-single-writer-ownership-model`. An active server can still be unreachable. Record the last connection observation from invocation (`executeMcpInvocation` in `mcp/mcpToolExecution.ts`) in a separate tenant table, leaving sync-owned item status unchanged.

Table `mcp_server_connection_state`:

- `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)`
- `mcp_server_item_id uuid NOT NULL` (an `items` partition row: no foreign key, like `mcp_tool_registrations`)
- `last_connected_at timestamptz`
- `last_error_reason text CHECK (last_error_reason IS NULL OR last_error_reason IN (<the values of MCP_CONNECTION_ERROR_REASONS in mcpConnectionError.ts>))`
- `updated_at timestamptz NOT NULL DEFAULT now()`
- `PRIMARY KEY (tenant_id, mcp_server_item_id)`

Decision: the primary key leads with `tenant_id`, as the repository's tenancy rules require for tenant tables, instead of the server id alone.

Recording rules in `executeMcpInvocation`: when `connectMcpServer` succeeds, upsert `last_connected_at = now()` and `last_error_reason = NULL`. When it throws `McpConnectionError`, upsert `last_error_reason = <reason>` and leave `last_connected_at` as it was. A failure of the `tools/call` itself after a successful connect is not a connection failure and records a success. The reason is one of the fixed, secret-free codes; no message, URL or credential is stored. The write is a single auto-committed statement on the pool, outside any caller transaction, so it survives the rollback of an enclosing unit of work (`docs/adr/2026-09-27-auto-committed-writes-for-records-that-must-survive-a-failure.md`). A failure while recording is logged and never changes the invocation result.

#1455 reads this table to report server state.

## Scope

### In scope

- The table, its tenancy and grants, and recording the result of connections made by tool calls.

### Out of scope

- Recording the result of connections made by a sync; the sync keeps `syncStatus` and `syncError`.
- Returning the state over HTTP: #1455.
- Retention or history of past attempts; only the last result is kept.
- Probing servers on a schedule.

## Acceptance criteria

- When a tool call fails to connect with reason `handshake_failed`, then the row for that server has `last_error_reason = 'handshake_failed'` and the previous `last_connected_at`; the stored data contains no secret or URL.
- When the next call connects, then `last_error_reason` is `NULL` and `last_connected_at` is current.
- When recording fails, then the invocation still returns its normal result.
- When the surrounding transaction of a caller rolls back, then the recorded failure is still present.
- When tenant B reads the table, then it sees no row of tenant A.
