**Blocked by:** #274, #21

## Context

The choke-point's write path (`backend/packages/data/src/chokePoint/chokePoint.ts`, delivered by #21) is the single sanctioned entry point for schema and item writes. The post-merge review of #21's pull request raised three findings against it; none was addressed and all three are still on `develop`.

**1. `createRelationPropertyWithClient` never validates `targetDatabaseId`.** When `input.inverse` is present the function creates the inverse property in the target database, which fails loudly for a non-existent id. When `input.inverse` is absent nothing ever touches that database, so an arbitrary UUID is accepted and written into the property config by `updatePropertyConfig({ relationDefinitionId, targetDatabaseId })`. Every later read of that relation resolves against a database that does not exist.

**2. `createRelationPropertyWithClient` with `locked: true` always throws.** The property is created with `locked: input.locked`, and the function then calls `propertiesStore.updatePropertyConfig` on that very property to attach `relationDefinitionId`/`targetDatabaseId`. `updatePropertyConfig` runs `assertPropertySchemaMutable`, which throws `ForbiddenError("Property … is locked; its schema cannot be changed")` for any locked property. Creating a locked relation property is therefore impossible today, and the failure surfaces as a permission error rather than as the internal ordering bug it is.

**3. No archived-database guard on item writes.** `createItem`/`updateItem` check property ownership and locking but never check whether the target database is archived (`archived_at IS NOT NULL`). An archived database is logically decommissioned, yet items can still be created and updated in it — `git grep archived_at` in `chokePoint.ts` returns nothing.

## Task

- **Validate the relation target.** In `createRelationPropertyWithClient`, before creating anything, read the target database with `databasesStore.getDatabase(client, input.targetDatabaseId)` and throw `ValidationError` naming the field when it does not exist. Keep the existing behavior of the `inverse` path unchanged (it may now fail earlier, with the clearer error).
- **Make `locked: true` work.** Create the property unlocked, attach the relation definition and target through the existing `updatePropertyConfig` call, and apply the caller's `locked` flag afterwards, so the config write is never attempted against an already-locked property. `propertiesStore` currently exposes no way to set `locked` after creation, so add one narrow function there (in the style of `setPropertyMigrationStatus`) and call it from the choke-point — do not write to the `properties` table directly from `chokePoint.ts`. The inverse property keeps its current unlocked creation. The end state must be identical to what the caller asked for: a locked property whose config carries `relationDefinitionId` and `targetDatabaseId`.
- **Guard archived databases.** Put the guard in the exported `createItemWithClient` and `updateItemWithClient` — not only in the `createChokePoint(...)` facade wrappers — so every declared owning process that writes through them (`journalStore`, `advanceTaskRecurrence`, `mailSyncJob`, the inbox stores) is covered by the same rule. Reject a write to a database whose `archived_at` is set with `ValidationError` naming the database. Reads, soft-delete and restore are unaffected.

Add tests in `backend/packages/data/src/__tests__/chokePoint.test.ts`:

- creating a relation property with a `targetDatabaseId` that does not exist is rejected, and no property or relation definition row is left behind. Use a fresh `randomUUID()` for that id: a non-UUID string would fail earlier in PostgreSQL with `invalid input syntax for type uuid` and would not exercise the new guard;
- `createRelationProperty({ locked: true, ... })` succeeds and returns a locked property whose config carries the relation definition and target database;
- creating and updating an item in an archived database is rejected, while the same operations succeed before archiving.

## Scope

### In scope

- The three guards/fixes in `chokePoint.ts` and their tests, plus the one narrow `locked`-setter added to `propertiesStore.ts`.

### Out of scope

- The manifest drift check and the view stores — those findings are #276.
- Any change to `propertiesStore.assertPropertySchemaMutable` itself: the locked-property rule is correct, only the creation order is wrong.
- Archiving semantics beyond blocking writes (no cascade, no unarchive workflow).

## Acceptance criteria

- A relation property cannot be created with a `targetDatabaseId` that does not name an existing database, with or without an inverse.
- `createRelationProperty` with `locked: true` returns a locked relation property whose config carries `relationDefinitionId` and `targetDatabaseId`, instead of throwing `ForbiddenError`.
- Creating or updating an item in an archived database is rejected; the same calls succeed while the database is not archived.
- The existing choke-point tests still pass.
