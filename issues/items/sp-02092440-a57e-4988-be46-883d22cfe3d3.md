## Context

Model tier rationale: A change of how the whole integration tier selects its tenant-scope mode. It changes no runtime code, but a wrong default either lets a lost scope pass CI or turns several hundred existing test files red at once.

Finding R2-APP-4 (low) of the gh-1086 external review: `backend/packages/data/src/testSupport/globalSetup.ts` sets `process.env.SEMPREC_TENANT_SCOPE ??= "warn"` for every integration test, and `backend/vitest.integration.config.ts` sets `LOG_LEVEL=error`, which also hides the `tenant_scope_missing` warning. Only the isolation suites (#1053, #1054, #1056, #1057) and a few files set `strict` for themselves. Production runs strict (the default since #1067), so a code path that loses its scope and is reached only by ordinary integration tests passes CI and fails in production.

Measured for this source at `e6387779b` (identical tree to the integration tip) in a private copy, with embedded PostgreSQL as the tier uses: the integration tier has 888 test files (`packages/*/src/**/*.test.ts` and `services/*/src/**/*.test.ts` without `*.unit.test.ts` and `*.e2e.test.ts`); 29 of them mention `SEMPREC_TENANT_SCOPE`. A deterministic sample of 30 files (every 30th of the sorted list) run with `SEMPREC_TENANT_SCOPE=strict`: 20 files failed (119 tests failed and 52 were skipped of 351; the failures throw `TenantScopeMissingError` from test fixtures and helpers that write without `runInTenant`), 10 passed; the same 20 files all passed under `warn` (273 of 273 tests). About two thirds of the tier therefore depends on `warn` today, mostly because its fixtures call data functions outside a scope. Converting them is far more than one source.

Decision: a staged approach. This source makes `strict` the default for every test file that does not yet need `warn`, freezes the set that does as an explicit list, and makes the list only shrink. Later sources convert files package by package and remove them from the list; they are created by the controller after this source lands (`issues/decisions/gh-1086.md`).

`backend/vitest.e2e.config.ts` reuses the same `globalSetup.ts` (`globalSetup: ["./packages/data/src/testSupport/globalSetup.ts"]`) and sets only `LOG_LEVEL` in `test.env`, so removing the default there would make the e2e tier strict as well. Measured by the challenge of this source's decision at `e6387779b`: under `SEMPREC_TENANT_SCOPE=strict` 47 of the 52 e2e tests fail (`agentRun.e2e`, `reconnect.e2e`, `crossModuleScenario.e2e`, `transcriptionGatewayComposition`, every trace `TenantScopeMissingError`), under `warn` 51 of 52 pass. The e2e tier therefore keeps `warn` in this source.

Shared-file ordering: this issue also waits for sp-994caf89-dfb8-465d-983f-5698cdc851af because both edit `backend/vitest.integration.config.ts` and `backend/vitest.e2e.config.ts`.

## Scope

### In scope

- Strict as the default tenant-scope mode of every integration test file that is not listed, and a frozen, shrink-only list of the files that still need `warn`.

### Out of scope

- Converting any listed test file or fixture to run under `strict` (later sources).
- Any change of `enforceTenantScope`, the logger, `LOG_LEVEL`, the unit tier, and the e2e tier beyond keeping its `warn` default, or production code.
- The route coverage test of `[security-gate 05/06]`.
- Any production deployment, any change to gh-1086 itself, any change under `web/` or `mobile/`, and web or mobile verification.

## Acceptance criteria

- When an integration test file that is not on the list runs, then `SEMPREC_TENANT_SCOPE` is `strict` for it and a data access outside a scope throws `TenantScopeMissingError`; on the unfixed tier the new probe test fails because the mode is `warn`.
- When a listed file runs, then it runs under `warn` exactly as before, and the integration tier passes unchanged.
- When the list is unsorted, has a duplicate, or names a missing or non-integration file, or when an entry is added that is not in the frozen first list, or a new test file sets `warn` for itself, then `tenantScopeWarnFiles.unit.test.ts` fails.
- When the vitest process is started with an explicit `SEMPREC_TENANT_SCOPE`, then every file runs with that value.
- When the e2e tier runs after the change, then every e2e file still runs under `warn` and the tier passes as before.
