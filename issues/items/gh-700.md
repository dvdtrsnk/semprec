## Context

`enqueueJob` (`backend/packages/queue/src/index.ts` lines 199-226) calls `graphile_worker.add_job(...)` with `job_key_mode` defaulting to `'replace'`. In graphile-worker 0.17.3, `add_job` routes both `'replace'` and `'preserve_run_at'` through `add_jobs` (`sql/000018.sql` line 10), whose first statement (lines 104-116) handles a key that belongs to a job that is *currently locked* — i.e. running — by clearing that row's `key` and setting `attempts = max_attempts` ("in the case of locked existing job create a new job instead as it must have already started executing"), then inserting the replacement job under the key. That is the intended supersede semantics, and every keyed producer in this repository relies on it: `mailAccountSyncJobKey` (`backend/packages/data/src/mail/mailSyncJob.ts` line 73, re-enqueued by the IDLE/webhook lifecycles while a sync runs), `heartbeatFireJobKey` (`backend/packages/data/src/scheduler/schedulerStore.ts` line 323, re-enqueued on every rapid edit of the same item), `journalInboxRecomputeJobKey`, `rollupRecomputeJobKey`, `transcriptionJobKey`, and the two `preserve_run_at` producers (`notificationFanoutJobKey`, `approval-request-execute-<id>`).

The defect is what happens next: when the superseded run then fails — a transient IMAP error, a gateway 5xx, a `TranscriptionLockedError` path that rethrows — graphile-worker's `failJob` leaves the row with `attempts = max_attempts`, so a *transient* failure of a superseded run is recorded as *permanently failed*. The replacement job runs the same work again seconds later, so nothing is actually lost, but the dead row stays forever (nothing deletes it; sibling issue F4b of this batch owns retention and the alert query) and `checkPermanentlyFailedJobs` counts it as an incident.

The fix belongs in the one wrapper every handler goes through: `registerTask` (`index.ts` lines 236-247) already wraps each task to restore its trace context; `createCoreTaskList` / `createAgentTaskList` / `createTranscribeQueueRuntime` all register through it. graphile-worker's `JobHelpers` expose `job` (with `id` and `key`) and `query(text, values)` on the worker's own client.

## Task

1. Add `backend/packages/queue/src/logger.ts` (new): `export const logger: Logger = createLogger("queue");` (the `mail/logger.ts` pattern; `@semprec/queue` already depends on `@semprec/shared`).
2. In `backend/packages/queue/src/index.ts`, extend `registerTask` so the wrapped handler's rejection is inspected before it propagates:
   ```ts
   try { return await run(); }
   catch (err) {
     if (helpers.job?.key != null && await jobKeyWasCleared(helpers)) {
       logger.warn({ err, jobId, jobName: name, jobKey: helpers.job.key }, "Job was superseded by a re-enqueue under the same key while it ran; its failure is not retried");
       return;
     }
     throw err;
   }
   ```
   where `run()` is the existing `withTraceContext(...)` call (both branches) and `jobKeyWasCleared(helpers)` runs `helpers.query<{ key: string | null }>("SELECT key FROM graphile_worker.jobs WHERE id = $1", [helpers.job.id])` and returns `rows[0] !== undefined && rows[0].key === null`. If that lookup itself throws, rethrow the *original* `err` (log the lookup error at `error` level first) — a broken check must never hide a real failure. Returning normally makes graphile-worker `complete_job` the superseded row (it is deleted); the replacement job, already queued under the key, runs the current state of the world. Document in the docstring that this is the only path that swallows a handler error and why (`add_jobs`' locked-key clearing), and that `remove_job` on a running job clears the key the same way, which is also correctly treated as "do not retry".
3. Test — `backend/packages/data/src/__tests__/queueSupersession.test.ts` (new, integration tier: real graphile schema via `ensureQueueSchema`, `getTestPool`/`resetDatabase`; lives in the data package because `@semprec/queue` cannot import `@semprec/data/testSupport`):
   - Register a task `supersedeProbe` through `registerTask` whose first invocation records that it started, awaits a `gate` promise, then throws `new Error("transient")`; its second invocation resolves. Run it with `runWorker({ pgPool, taskList, noHandleSignals: true, concurrentJobs: 1 })`.
   - `enqueueJob(pool, "supersedeProbe", {}, { jobKey: "k", maxAttempts: 3 })`; wait until the handler reports it started; `enqueueJob` the same key again (this clears the running row's key); resolve the gate; wait until the handler has run twice. Assert `graphile_worker.jobs` has no row for `supersedeProbe` at all (the superseded row completed, the replacement ran and completed) and, in particular, no row with `attempts >= max_attempts`. Stop the runner.
   - Control case: the same handler without a second enqueue — after the throw, exactly one `supersedeProbe` row remains with `attempts = 1`, `last_error` containing `transient` and `key = 'k'` (a genuine failure is still retried).

## Scope

### In scope
- Supersession detection in `registerTask`, its logger, and the integration test.

### Out of scope
- Pruning permanently failed rows and the `queue:permanentlyFailedJobs` query (sibling issue F4b of this batch).
- Changing any producer's `jobKeyMode` (`preserve_run_at` has the same locked-key behaviour; `unsafe_dedupe` would drop the re-run the producers rely on).
- `runWorker` concurrency (sibling issue F3).

## Acceptance criteria

- When a job with a `jobKey` is re-enqueued while it is running and the running invocation then throws, the running row completes (is deleted) and the replacement job runs; no `attempts >= max_attempts` row is left behind, and one `Job was superseded` warning is logged.
- When a keyed job throws without having been superseded, graphile-worker retries it exactly as before (`attempts` incremented, `last_error` set, key intact).
- When the supersession lookup itself fails, the handler's original error propagates and the lookup failure is logged.
