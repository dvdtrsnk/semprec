## Context

Model tier rationale: A bounded authenticated read adds an exact timestamp/id continuation contract, preserving PostgreSQL precision and tenant isolation across pages; deterministic implementation and boundary tests require medium effort.

Silent pushes are throttled by iOS and may never arrive, so when the app opens it must reconcile: it asks which of the user's notifications were resolved since it last looked, and hides them. The column and its index come from #1463. Notification routes live in `backend/services/semprec-api/src/notificationsHandler.ts` (unread list, visit, mark all read).

Decisions: follow `docs/adr/2026-11-05-resolved-notification-pagination-keeps-timestamp-ties.md`. GET /api/notifications/resolved requires since and optionally afterId. First-page predicate is resolved_at > since; continuation is the exclusive (resolved_at,id) tuple, ordered ascending, cap500. Response includes only resolved ids/times plus nextCursor. Preserve full PostgreSQL microseconds in this endpoint, strict bounded ISO/UUID validation, authenticated tenant/user filtering and NO_STORE. No resolution writer, other DTO or client change. The API is not a commit-order stream; late commits behind the cursor are an explicit separate limitation.

Shared-file ordering: this issue also waits for #1555 because both edit the same registry, manifest, cutover, route matrix or hook files listed in Touches.

## Acceptance criteria

- When `since` is before a notification was resolved, then that notification's id is returned.
- When another user's notification was resolved, then it is not returned.
- When `since` is missing or not an ISO timestamp, then the response is 400.
