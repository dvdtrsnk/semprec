## Context

Model tier rationale: Every foreign key is listed, but the catalog twin-matching rule and the cross-tenant fixtures for many parent tables need judgment.

Foreign-key checks ignore row-level security: a single-column FK such as `properties.database_id → databases(id)` is satisfied by another tenant's database, so a write path that forgets an existence check can link a row to a foreign parent, and the FK error code (`23503`) versus success becomes an oracle. The tenant-isolation ADR (#968) therefore requires a composite twin `(tenant_id, x_id) → parent(tenant_id, id)` for every reference between tenant-owned rows, added `NOT VALID` and validated afterwards. #974 created the `<table>_tenant_id_id_uq` unique indexes on `(tenant_id, id)` for the tenant parents (`databases`, `properties`, `relation_definitions`, `agent_runs`, `project_heartbeats`, `views`, `docs`, `notifications`, `mcp_tool_registrations`, `mail_threads`, `blobs`); #1065 removed the last legacy global keys. Every tenant table has `tenant_id uuid NOT NULL DEFAULT app_tenant_default() REFERENCES tenants(id)` (#972).

References to cover (child column → parent, as created; `CASCADE` = `ON DELETE CASCADE`, which the twin must repeat):

- `databases(id)` ← `properties.database_id` (`0001_core_schema.sql:45`, CASCADE), `items.database_id` (`0001:73`), `rollup_dependencies.source_database_id` (`0001:145`), `item_search_index.database_id` (`0006_mail_sync.sql:139`), `views.database_id` (`0002_views.sql:13`, CASCADE);

Postgres 16 rejects a `NOT VALID` foreign key on a partitioned table, which `items` is (`0001:71-79`); Postgres 18 accepts it — so CI would not catch that mistake.

## Task

Load `db-migrations` (two-step constraint recipe, lock behaviour, rollback safety).

1. **Migration A** (next free ordinal at commit time): create `users_tenant_id_id_uq ON users (tenant_id, id)` (`users` is global, so #974 did not add one; `users_tenant_id_key` on `tenant_id` alone cannot serve a two-column reference). Then, for every reference listed above except `items.database_id`, add a composite FK `(tenant_id, <column>) REFERENCES <parent>(tenant_id, id)` with the original `ON DELETE` action, `NOT VALID`, named `<table>_<column>_tenant_fkey`. Keep every existing single-column FK.
2. **Migration B** (the following ordinal): `ALTER TABLE … VALIDATE CONSTRAINT` each FK from Migration A; then add `items_database_id_tenant_fkey (tenant_id, database_id) REFERENCES databases(tenant_id, id)` as an ordinary, immediately validated constraint, with a comment explaining the Postgres 16 restriction and that it holds a `SHARE ROW EXCLUSIVE` lock on `items` and `databases` for the length of the scan.
3. Both files are additive (new constraints only), so the previous release keeps working; no exemption comment is needed.
4. In `tenancyCatalog.test.ts`, add a rule (exempting, by name, `tenant_ai_budgets.updated_by`, which an admin of any tenant writes per #1039): every FK whose referencing table is tenant-classified or carries `tenant_id`, and whose referenced table is tenant-classified or is `users`, either maps `tenant_id` to `tenant_id` itself or has a validated (`convalidated`) twin on the same table, referencing the same parent, over `(tenant_id, <same columns>)`. FKs to `tenants(id)` are exempt.
5. Add `backend/packages/data/src/__tests__/tenantForeignKeys.test.ts` (below).

## Scope

### In scope

- Composite twins for every reference listed, the `users_tenant_id_id_uq` key, validation, and the catalog rule.

### Out of scope

- Dropping the single-column FKs (not required for the guarantee).
- `push_deliveries.push_subscription_id` (references the global `push_subscriptions`, which has no `tenant_id`) and `item_id`-style columns, which cannot carry an FK to the partitioned `items`.
- The strict switch (#1067).

## Acceptance criteria

- Integration (`tenancyCatalog.test.ts`): the composite-FK rule passes, and removing any one twin makes it fail naming the table and column.
- Integration (`tenantForeignKeys.test.ts`, tenants A and B from `createTestTenant`, `@semprec/data/testSupport` (#975); the inserts run inside `runInTenant(B)` on a `createRuntimeRolePool(adminPool, "semprec_data")` pool, so the rows pass RLS and only the FK can refuse them): inserting a B row that references A's database, property, view, doc, heartbeat, agent run, thread, blob, notification, tool registration or user fails with `23503`, exactly as with a random UUID; the same inserts referencing B's own parents succeed.
- Integration: deleting an A database, view or doc still cascades to its children exactly as before.
- Integration: after both migrations every FK containing `tenant_id` has `convalidated = true`.
- Review: Migration A contains no foreign key on `items`.
